# The two parameter page implementations

Upstream source code and documentation are cited as `<path>` of `<owner>/<name>@<version>`, that is, the path in the upstream repository at that version. For code, the class and method are also given; for documentation, the section heading. The upstream repositories and versions are listed in [BRIEF.md section 8](../BRIEF.md#8-sources).

This document describes the two parameter pages the deploy engine provides: the Active Choices form (`form: 'active-choices'` in the Jenkinsfile, Active Choices plugin 2.8.11; both example jobs, `examples/pipelines/readwrite/Jenkinsfile` and `examples/pipelines/readonly/Jenkinsfile`, use it) and the plugin-free form (`form: 'basic'` in the Jenkinsfile; uses only what Jenkins provides, and asks for the task parameters with `input` after the build starts). It covers what is on the page, how it is generated, the format of the submitted values, and how the engine turns them into a run plan. Both forms share the shared library under `examples/platform/jenkins/` (`vars/deployPipeline.groovy` and the classes in `src/deploy/`). Both get a plan draft with the same structure as `DEPLOY_PLAN` from `ParameterPage.draft`, which `PlanParser.parse` then validates in one place.

## 1. Comparison

| Capability | Active Choices form | Plugin-free form |
| --- | --- | --- |
| Select host groups | Checkboxes (`TARGET_GROUPS`) | One checkbox per group (`TARGET_web`, etc.) |
| Select tasks | Checkboxes (`PRE_TASKS` / `POST_TASKS`) | One checkbox per task (`PRE_task_a`, etc.) |
| Show only the parameters of the selected tasks | On the same page, as soon as a task is checked | Shown by the `input` step after the build starts |
| Input controls | Number box for integers; drop-down for booleans, enums and the failure policy; " (required)" after the name of a required parameter; one bordered group per task | Text box for strings and integers, checkbox for booleans, drop-down for enums and the failure policy; one flat column |
| Where the filled-in values are recorded | Build parameters (visible under Parameters on the build page) | The `input` submission record; the run plan is printed on the console |
| While waiting for input | Not applicable | The build pauses in the `Plan` stage, which is given no executor, and waits at most 30 minutes; what runs afterwards are the files stashed with `stash` in `Prepare` |
| Triggering from the API / an upstream job | `DEPLOY_PLAN` | `DEPLOY_PLAN` |
| Plugins needed | `uno-choice` | None |

## 2. Parameter definitions can only be generated with `properties()`

The list of host groups comes from `business/inventory/hosts.yml`. The list of tasks and their parameters come from each task directory's `business/tasks/<task>/meta/task.yml`, `meta/argument_specs.yml` and `defaults/main.yml`. All of these are known only by reading the workspace while the build runs. So `deployPipeline` writes the build parameters into the job in the `Prepare` stage by calling `properties([disableConcurrentBuilds(), parameters(new ParameterPage(...).definitions())])`, not in `pipeline { parameters { } }`. Consequences:

- The parameter definitions are updated while a build runs and appear on the parameter page **from the next build on**. A new job must run once first (result NOT_BUILT).
- Deciding "is this the first run" must use the `params` read before `properties()`. So `deployPipeline` first copies `params` to `requested` before calling `properties()`, and `RequestKind.of(requested)` decides (see [BRIEF.md section 4.7](../BRIEF.md#47-the-first-run-only-registers-parameters-params-must-be-read-before-properties)).

## 3. Active Choices form

### 3.1 Scripts on the parameter page cannot see the workspace

Active Choices Groovy scripts run on the Jenkins controller when the user opens the parameter page or changes a checkbox. They have no workspace. So while the build runs, `ParameterPage.definitions` uses `ActiveChoicesForm.literal` to turn the host group and task definitions into Groovy literals and writes them straight into the script text. For example, the script of the host group list (generated by `ActiveChoicesForm.groupsScript`):

```groovy
def groups = ['web': ['web-01', 'web-02'], 'api': ['api-01'], 'worker': ['worker-01', 'worker-02']]
return groups.collectEntries { name, hosts -> [(name): name + ' (' + hosts.join(', ') + ')'] }
```

The script returns `[value: display text]`: the value of the checkbox is `web`, and `web (web-01, web-02)` is shown next to it. The script declares `sandbox: true` and runs in the Groovy sandbox, so it needs no administrator approval.

### 3.2 Return values of sandbox scripts go through an HTML filter

The plugin passes the return value of a sandbox script (a string, each item of a list, each key and value of a Map) through the `SafeHtmlExtendedMarkupFormatter` filter (the `eval` method and the `resolveTypeAndSanitize` method in `src/main/java/org/biouno/unochoice/model/GroovyScript.java` of `jenkinsci/active-choices-plugin@2.8.11`). The filter lets through only basic tags plus `input`, `textarea`, `select` and `option` (the static field `POLICY` of the `SafeHtmlExtendedMarkupFormatter` class in `src/main/java/org/biouno/unochoice/util/SafeHtmlExtendedMarkupFormatter.java` of `jenkinsci/active-choices-plugin@2.8.11`), and rewrites some characters as HTML entities. Input and output when the filter is called directly in the script console (non-ASCII characters are written here as `{U+XXXX}`, and a run of Chinese characters as `{CJK}`):

```
web{U+FF08}a{U+FF09}  =>  web&#xff08;a&#xff09;
{CJK}{U+FF1A}{CJK}  =>  {CJK}&#xff1a;{CJK}
a {U+2014} b  =>  a {U+2014} b
a: b, c (d)  =>  a: b, c (d)
{CJK}{U+3001}{U+3002}{U+FF01}{U+FF1F}  =>  {CJK}{U+3001}{U+3002}&#xff01;&#xff1f;
{U+300C}{U+300D}  =>  {U+300C}{U+300D}
a=b+c  =>  a&#61;b&#43;c
@@x.y  =>  &#64;&#64;x.y
x"z<b>  =>  x&#34;z<b></b>
{U+FF21}{U+FF22}{U+FF11}{U+FF12}  =>  &#xff21;&#xff22;&#xff11;&#xff12;
```

The two kinds of parameter are affected differently:

- **Checkboxes** (`activeChoice`): the display text is then escaped once more by the page template, so the entities are shown literally on the page, for example `web&#xff08;web-01, web-02&#xff09;`. So checkbox labels and the `description` in each task's `meta/task.yml` are ASCII only, without `@ = + "`, and a `description` never contains the word `selected` (BRIEF.md section 5). `Catalog` refuses other descriptions in `Prepare`; `test_description_is_ascii_without_characters_the_active_choices_sanitizer_turns_into_entities` in `test_tasks.py` checks the same before a commit.
- **Dynamic HTML** (`activeChoiceHtml`): the output is inserted into the page as HTML and the browser turns the entities back into characters, so full-width punctuation and the `@@` markers in the form work. But tags and attributes that are not let through are removed: groups can only use `div`, and required parameters can only be marked with text. Input and output of the filter:

```
IN : <label for="x">a</label><input id="x" name="value">
OUT: a<input id="x" name="value" />
IN : <input id="x" name="value" aria-required="true" required aria-label="msg" title="t">
OUT: <input id="x" name="value" />
IN : <input type="text" name="value" placeholder="required" class="jenkins-input">
OUT: <input type="text" name="value" placeholder="required" class="jenkins-input" />
```

`label`, `aria-*`, `title` and `required` on `input` are all removed. So the form writes " (required)" after the parameter name, and gives each text box and number box a `placeholder` (the parameter name, plus " (required)" when required): the browser uses `placeholder` as the accessible name when there is no other name. On a drop-down, only the attributes `id`, `class`, `style`, `disabled`, `multiple`, `name`, `required` and `size` are let through, and none of them can name it.

### 3.3 Parameter form

`PRE_TASK_OPTIONS` is an `activeChoiceHtml` with `referencedParameters: 'PRE_TASKS,PRE_MORE_TASKS'` and `omitValueField: true`. When the checkboxes of either list change, the plugin runs the script generated by `ActiveChoicesForm.optionsScript` again. The script gets the values of both lists (task names separated by commas) and writes a group of input boxes for each selected task; when no task is checked it shows only "No task selected". The HTML on the page after checking `task_c`:

```html
<div style="{group}">
  <div style="{title}"><b>task_c</b> Example task with a choice and a boolean parameter</div>
  <table style="{table}"><tbody>
    <tr><td style="{label}">Order</td><td style="{value}">
      <input type="hidden" name="value" value="@@task_c.order">
      <input type="number" name="value" value="30" placeholder="order" class="jenkins-input" style="{number}">
      <div style="{hint}">smaller numbers run first in this phase</div></td></tr>
    <tr><td style="{label}">On failure</td><td style="{value}">
      <input type="hidden" name="value" value="@@task_c.policy">
      <select name="value" style="{select}"><option value="abort" selected="selected">abort</option><option value="warn">warn</option></select>
      <div style="{hint}">abort: stop the pipeline; warn: mark unstable and continue</div></td></tr>
    <tr><td style="{label}">task_c_mode</td><td style="{value}">
      <input type="hidden" name="value" value="@@task_c.task_c_mode">
      <select name="value" style="{select}"><option value="plan" selected="selected">plan</option><option value="apply">apply</option></select>
      <div style="{hint}">Run mode</div></td></tr>
    <tr><td style="{label}">task_c_verbose</td><td style="{value}">
      <input type="hidden" name="value" value="@@task_c.task_c_verbose">
      <select name="value" style="{select}"><option value="true">true</option><option value="false" selected="selected">false</option></select>
      <div style="{hint}">Whether to print details</div></td></tr>
    <tr><td style="{label}">task_c_label</td><td style="{value}">
      <input type="hidden" name="value" value="@@task_c.task_c_label">
      <input type="text" name="value" value="" placeholder="task_c_label" class="jenkins-input" style="{text}">
      <div style="{hint}">Extra label, may be empty</div></td></tr>
  </tbody></table>
</div>
```

(Line breaks and indentation added for readability; `{group}` and the like stand for the entries of `FormStyle.STYLES`.)

**Styles are defined in one place**: `platform/jenkins/src/deploy/FormStyle.groovy`, a map from element role (`group`, `title`, `table`, `label`, `value`, `text`, `number`, `select`, `hint`) to an inline style. The column widths and spacing of the form are changed there and nowhere else. Only inline styles work: the sanitizer removes `<style>` blocks, removes `class` from everything except `input`, `textarea`, `select` and `option`, and drops CSS properties outside its allowed set (such as `position` and `display`) and values such as `url(...)`; a `div` or `span` left with no attribute is removed with its tag. `test_every_form_style_survives_the_sanitizer` in `test_parameter_page.py` fails when the sanitizer drops any style in `FormStyle.STYLES`. Styling the rest of the page (the checkbox lists, descriptions, buttons) would need a site-wide theme that an administrator installs, so the template does not do it.

The engine decides the control from the parameter type (`ActiveChoicesForm.input`, a `switch` on `ParameterType`), and the script only generates HTML from the result: `choices` -> drop-down; `bool` -> a `true` / `false` drop-down (so that each marker is always followed by exactly one value); `int` -> `type="number"`; anything else -> text box. The field keys in the markers are also generated by the engine (`FormField`). The prefilled values come from the task directory's `defaults/main.yml`. For a required parameter (such as `task_a_message`), the name cell reads `task_a_message (required)`, and the accessible name of the input box is also `task_a_message (required)` (`test_integer_parameter_uses_number_input_and_required_parameter_is_marked_in_text` in `test_parameter_page.py`).

**Changing the selection regenerates the whole form**, and values already typed are lost: the script can see only the values of the referenced parameters (`PRE_TASKS` and `PRE_MORE_TASKS`), not the old values of the form itself. Check all the tasks first, then fill in the parameters (`test_changing_the_selection_regenerates_the_form_and_drops_typed_values`).

### 3.4 Submitted value and parsing

On submit, the plugin collects the values of all input boxes with `name="value"` in the parameter into an array and joins them into one string with `join(",", true)` (the `createValue` method in `src/main/java/org/biouno/unochoice/AbstractUnoChoiceParameter.java` of `jenkinsci/active-choices-plugin@2.8.11`). `join` turns each value into a JSON string (`"` becomes `\"`, `\` becomes `\\`); the second argument `true` only removes the quotes around each value. For example, after filling `task_c_label` in the form above with `x, "y"` and submitting, the value of the build parameter `PRE_TASK_OPTIONS` is:

```
@@task_c.order,30,@@task_c.policy,abort,@@task_c.task_c_mode,plan,@@task_c.task_c_verbose,false,@@task_c.task_c_label,x, \"y\"
```

Commas in a value are the same as the separator, so the engine does not split on commas but on the hidden markers: `ActiveChoicesForm.parseOptions` splits with the regular expression `(?:^|,)@@`. In each piece, the part before the first comma is `task name.field` (`FormField.split` splits it at the first dot), and the rest is the value. `ActiveChoicesForm.jsonUnescape` then restores escapes such as `\"` and `\\`. The run plan on the console and the Ansible output:

```
    - task_c [abort] [task_c_mode:plan, task_c_verbose:false, task_c_label:x, "y"]
    "msg": "worker-01: task_c mode=plan label=x, \"y\""
```

`Selection.draft` then converts by parameter type with `Values.fromForm`: an `int` that can be converted to a 64-bit integer becomes a number, otherwise the original string is kept and `Values.check` in `PlanParser.parse` reports `must be an integer`; `true` / `false` of a `bool` become booleans; an empty value of a non-string parameter means not filled in, and the default is used. Tasks in the same phase are ordered by the run order filled in on the form (see section 3.5), not by the order in which they were checked.

The format itself is ambiguous: when the user types `,@@` in a value, the second half is taken as another field. The engine does not guess; it reports an error. The same field appearing twice, a field that does not belong to a selected task, and a field that is not a declared parameter of that task all fail before any task runs (`test_invalid_form_values_fail_before_any_task_runs` in `test_pipeline_validation.py`).

Values containing commas, quotes, backslashes, `@@`, `=`, `+` and non-ASCII characters reach Ansible unchanged. When `task_a_message` is filled in on the form with `a,"b" c\d, @@x caf\u00e9=1+2` (`\u00e9` here stands for the character U+00E9, e with acute accent), the Ansible output on the console is `"msg": "api-01: a,\"b\" c\\d, @@x caf\u00e9=1+2 (2/2)"` (shown as JSON-escaped; `test_submitted_form_values_reach_ansible_unchanged`).

### 3.5 Main tasks and "Show more", search box, run order

When there are many tasks, the tasks of each phase are split into two lists. The plugin can only draw a checkbox list as a whole and cannot collapse part of it, so "collapsed" is done by making the second list empty:

- `PRE_TASKS`: tasks with `menu: main`, always shown.
- `PRE_SHOW_MORE`: a boolean parameter provided by Jenkins, registered only when the phase has tasks with `menu: more`.
- `PRE_MORE_TASKS`: a `reactiveChoice` checkbox list with `referencedParameters: 'PRE_SHOW_MORE'`. The script (`ActiveChoicesForm.moreTasksScript`) returns an empty Map when `PRE_SHOW_MORE` is empty, otherwise the tasks with `menu: more`. The plugin passes the value of a checked checkbox to the script, and an empty string when it is not checked (the `getElementValue` method of the `Util` class in `src/main/js/Util.ts` of `jenkinsci/active-choices-plugin@2.8.11`). Unchecking it regenerates this list, and the less-used tasks that were checked are cleared with it (`test_showing_more_lists_the_less_used_tasks_and_hiding_them_drops_their_selection`).
- `PRE_TASK_OPTIONS` references both lists (`referencedParameters: 'PRE_TASKS,PRE_MORE_TASKS'`) and generates the form for the tasks selected in either. The engine merges the values of the two lists (`ParameterPage.draft`).

Both checkbox lists set `filterable: true`: a search box appears under the list, and on each key press only the tasks whose text contains the typed text are shown (`test_filter_box_narrows_a_task_list`). The plugin filters on the `keyup` event, so automated tests must type character by character and cannot set the value of the input box directly.

The first row of each task in the parameter form is the run order: a number box with the marker `@@<task>.order`, prefilled with the task's `order`. `Selection.draft` orders the tasks of a phase by these numbers; an empty box uses `order`, and equal numbers are ordered by `order`. A value that is not an integer reports `form field <task>.order must be an integer` (`test_order_typed_on_the_form_decides_the_order_within_a_phase`). Dependencies between tasks are not checked. The run plan is printed on the console before any task runs.

### 3.6 Triggering without the page

The plugin states that Active Choices parameters are meant only for people filling them in on the page, and that they are not guaranteed to work when the build is triggered by plugins, the API or scripts (the "Known Limitations" section of `README.md` of `jenkinsci/active-choices-plugin@2.8.11`). Values passed straight in through `buildWithParameters` do not go through the JSON escaping of the page and are stored as they are, but the engine's `ActiveChoicesForm.jsonUnescape` still processes the backslashes in them; for example `C:\new` becomes `C:`, a line break, `ew`. So the API and upstream jobs pass only `DEPLOY_PLAN`. The integration tests that set `TARGET_GROUPS`, `PRE_TASKS`, `PRE_MORE_TASKS` and `PRE_TASK_OPTIONS` directly (for example `test_selection_runs_tasks_in_catalog_order_on_the_selected_groups_only` in `test_pipeline_runs.py`, `test_invalid_form_values_fail_before_any_task_runs` in `test_pipeline_validation.py`) use only values without backslashes, to simulate a page submission.

When `PRE_MORE_TASKS` is not passed, Jenkins runs its script to get the default value, and at that point the referenced `PRE_SHOW_MORE` is not bound: the script throws `MissingPropertyException` when it reads it, the plugin falls back to the fallback script, the text the fallback script returns becomes the parameter value, and plan validation reports `unknown task '(task list failed)'`. So `moreTasksScript` catches this exception and treats it as not checked (`test_tasks_from_both_lists_run_in_catalog_order_without_typed_orders` and other cases triggered through the API).

## 4. Plugin-free form: checkboxes + input step

### 4.1 Parameter page

With `form: 'basic'`, `ParameterPage.definitions` generates `booleanParam(name: 'TARGET_<group>')` for each host group under `deploy_targets` in the inventory, and `booleanParam(name: '<PRE|POST>_<task name>')` for each task allowed in each phase, plus `SKIP_DEPLOY` (only in the read-write job), `EDIT_TASK_OPTIONS` (checked by default) and `DEPLOY_PLAN`. The parameter page Jenkins provides is static and cannot show or hide other input boxes based on a checkbox, so the task parameters are not on this page.

### 4.2 The form after the build starts

`ParameterPage.draft` (the plugin-free form is handled by its `basicDraft`), when `EDIT_TASK_OPTIONS` is true and tasks are checked, uses `ParameterPage.inputFields` to generate the input fields for each selected task and hands them to the `input` step (the confirm button is "Start", wrapped in a 30-minute `timeout`). `deployPipeline` calls it in the stage `Plan`. That stage is not inside a `node`, so the wait holds no executor and no workspace (`test_waiting_for_the_form_holds_no_executor` in `test_basic_form.py`):

| Input field | Type |
| --- | --- |
| `<phase>.<task>.policy` | `choice`, with the task's default policy first (that is, the default value) |
| `<phase>.<task>.<parameter>`, parameter has `choices` | `choice`, with the default value first; without a default, the original order of `choices` is kept |
| `<phase>.<task>.<parameter>`, `bool` | `booleanParam` |
| `<phase>.<task>.<parameter>`, `str` / `int` | `string`, prefilled with the default |

With `TARGET_web`, `PRE_task_a` and `POST_check_a` checked, the form contains only the 6 fields of these two tasks: `pre.task_a.policy`, `pre.task_a.task_a_message`, `pre.task_a.task_a_repeat`, `pre.task_a.task_a_delay_seconds`, `post.check_a.policy`, `post.check_a.check_a_min_connections` (`test_form_shows_only_selected_tasks_and_its_values_are_used`).

With several input fields, `input` returns `[name: value]`; **with only one input field it returns that value directly** (the `proceed` method in `src/main/java/org/jenkinsci/plugins/workflow/support/steps/input/InputStepExecution.java` of `jenkinsci/pipeline-input-step-plugin@560.v56198a_642157`). A task without parameters (`check_c`) has only the failure policy field, so in that case `basicDraft` builds the Map itself (`test_form_with_a_single_field_returns_its_value`).

After submission, each value is turned into a string and grouped by `<phase>` into the same `[task.field: value]` as in the Active Choices form, and handed to the same `Selection.draft`. Clicking "Abort" makes the build ABORTED, and no task runs (`test_abort_in_the_form_aborts_the_build`).

### 4.3 Not showing the form

- `EDIT_TASK_OPTIONS=false`: all selected tasks use their defaults (`test_without_the_form_every_task_uses_its_defaults`). A task with a required parameter (such as `task_a`) therefore fails validation (`test_without_the_form_a_missing_required_parameter_fails`).
- `DEPLOY_PLAN` not empty: all checkboxes are ignored and no form is shown (`test_deploy_plan_skips_the_form`). Use this when triggering from the API or an upstream job; otherwise the build stops at `input` waiting for someone.
