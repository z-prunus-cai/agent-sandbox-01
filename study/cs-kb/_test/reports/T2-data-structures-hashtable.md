## 4.1 哈希函数

### 4.1.1 哈希表 / 哈希函数的基本定义

哈希表用一个**哈希函数** h 把键空间 U 里的键映射成一个数组下标（槽位 slot / 桶 bucket），键 k 就存到槽 h(k) 里，于是「按键查找」不再需要逐个比对，而是算一次 h(k) 直接跳到位置，期望代价降到 O(1)。CLRS §11.1 先用**直接寻址表**（direct-address table）作引入：如果键就是 0..m−1 的小整数，直接拿键当数组下标即可，无需哈希；哈希表则是当键空间 U 远大于能负担的内存 m 时的「压缩版」——用 h 把庞大的键空间折叠进仅有的 m 个槽。

映射关系写成：

h : U → {0, 1, …, m−1}

对初学者最关键的直觉是「为什么快」：普通数组靠「下标=位置」实现 O(1) 随机访问，但下标必须是紧凑的小整数；现实里的键往往是任意整数、字符串、对象，没法直接当下标。哈希函数就是那台「把任意键翻译成合法下标」的翻译机，翻译一次是常数时间，所以查找也变成常数时间。

由此也能看出哈希表绕不开的核心难题：因为 |U| 通常远大于 m，一定会有两个不同的键被映射到同一个槽（这是**鸽巢原理**的直接后果——m 个槽装不下多于 m 个「不冲突」的键）。这种「不同键落到同一槽」就叫**碰撞（collision）**，如何处理碰撞正是 4.2 和 4.3 两节的主题。可以把直接寻址表理解成哈希表的退化特例：h 是恒等映射、且保证无碰撞。

### 4.1.2 除留余数法（division method）

最简单的一类哈希函数是取模：

h(k) = k mod m

它把键 k 除以表大小 m 取余数当槽号（CLRS §11.3.1）。实现只需一条取模指令，快且直接。

对初学者要讲清的关键是 **m 怎么选**。CLRS 建议避开 2 的幂，取一个不接近 2 的幂的质数。原因用一个最小例子就能感受到：若取

m = 2^p

那么 k mod 2^p 在二进制下等价于「只保留 k 的最低 p 位、把高位全部扔掉」。假如你的键是内存地址、或者都是 8 的倍数这类低位有规律的数据，那么大量键的低 p 位会重复，全部挤到少数几个槽里，碰撞爆炸、性能塌方。取质数（且远离 2 的幂）能让所有位都参与运算，把规律性的键打散得更均匀。这就是「取 m 为质数」这条老生常谈背后的真正理由——不是迷信，而是让高位信息不被丢弃。

### 4.1.3 乘法法（multiplication method）

另一类经典哈希函数是乘法法（CLRS §11.3.2）：

h(k) = ⌊ m · (k · A mod 1) ⌋

其中 A 是一个 0 < A < 1 的常数，`k·A mod 1` 表示取 k·A 的小数部分，再乘 m 向下取整。

它相比除留余数法的好处是：对 m 的取值不敏感，因此可以放心取

m = 2^p

以便用移位等位运算高效实现（这时最后一步取整可以用位移完成）。工作直觉是：k·A 的小数部分在 [0,1) 上分布得很均匀（尤其当 A 是无理数时），乘 m 就均匀铺满 m 个槽。

A 取什么值有讲究。Knuth 建议取黄金比的共轭：

A ≈ (√5 − 1) / 2 = 0.6180339887…

本机核验这个常数值（`python3 -c "import math; print((math.sqrt(5)-1)/2)"`）得 `0.6180339887498949`，与 CLRS 给出的 Knuth 建议值一致。选它的直觉是黄金比是「最难被有理数逼近」的无理数，用它做乘子能让相邻键的小数部分散得最开、最不容易周期性重叠。初学者不必记这个具体数字，记住「乘法法对 m 宽容、常配 m=2^p、乘子取一个好的无理常数」即可。

### 4.1.4 全域哈希（universal hashing，§11.3.3）

全域哈希不是某一个固定的哈希函数，而是一**族**哈希函数 H，使用时从 H 中**随机**挑一个 h 来用。它的定义性质是：对任意两个不同的键 k ≠ l，随机挑出的 h 让它们碰撞的概率不超过 1/m。写成：

Pr_{h ∈ H}[ h(k) = h(l) ] ≤ 1/m

对初学者，这里要解决的问题是「固定哈希函数的软肋」：只要哈希函数是公开且固定的，攻击者就能反推出一堆会落到同一槽的键，专门喂给你，把哈希表打退化（见 4.5）。全域哈希的妙处在于把「针对固定 h 的最坏对抗输入」变成了「随机事件」——因为 h 是运行时随机选的，攻击者事先不知道你会用哪个 h，就没法可靠地构造碰撞。于是无论输入是什么，碰撞的期望都受 1/m 这个界控制。

CLRS 给出一个可直接用的全域族构造：先取一个大于所有键的质数 p，随机选 a ∈ {1,…,p−1}、b ∈ {0,…,p−1}，令

h_{a,b}(k) = ((a·k + b) mod p) mod m

每次换一组随机的 (a, b) 就换了一个哈希函数。这条构造与 4.5.4 讲的「CPython 用随机盐做哈希随机化」是同一思想在工程上的落地：都靠随机化让对手无法预测键落到哪个槽。

### 4.1.5 简单均匀哈希假设（simple uniform hashing）

简单均匀哈希假设（CLRS §11.2）是分析哈希表性能时用的一个理想化前提：假设每个键都**等概率、且相互独立地**散到 m 个槽中的任意一个。

初学者容易把它误当成「哈希函数的性质」——不是。它是一个**分析用的假设**，因为真实哈希函数很难保证严格均匀独立，但如果不作这个假设就没法推公式。4.2、4.3 里所有「期望查找长度 Θ(1+α)」「不成功查找 ≤ 1/(1−α)」的结论，都是在这个理想前提下推出来的。全域哈希（4.1.4）则是让真实行为**逼近**这个理想的手段——它不能让每个键真的独立均匀，但能保证碰撞概率的期望界，从而使实际性能接近理论预测。记忆钩子：简单均匀哈希是「我们希望哈希函数表现成的样子」，全域哈希是「怎么用随机化去接近它」。

### 4.1.6 好哈希函数的判据

一个好的（工程用、非密码学）哈希函数通常要满足：**确定性**（同一个键每次算出同一个值，否则根本没法查找）、输出**近均匀分布**（每个槽被命中的概率都接近 1/m）、**低碰撞**、以及**雪崩效应**（avalanche：输入的一点微小变化会引起输出的大范围变化）。对非密码学的工程哈希，还额外要求**快**。

对初学者，最值得记的是「均匀」和「雪崩」两条的直觉。均匀是目标——槽被用得越平均，每个桶越短，查找越快；雪崩是手段——只有当输入的每一位都能大幅搅动输出时，像「aaa1、aaa2、aaa3」这种只差一位的规律键才会被打散到不同槽，而不是挤成一堆。这也解释了 4.1.2 为什么怕 2 的幂做 m：那等于只看低几位、高位对结果毫无影响，直接违背了雪崩。注意工程哈希不追求「密码学安全」（即不要求「已知哈希值反推原键很难」），它只求快且散得开；抗对抗攻击那层由 4.1.4 的随机化来补。

### 4.1.7 Python `hash()` 的分布观察（本机实证）

CPython 内建的 `hash()` 给出对象的哈希值。对小整数，CPython 直接令

hash(n) = n

（本机 `hash(42)` 输出 `42`）；但有一个特例：`hash(-1)` 不是 −1 而是 **−2**（本机实测 `hash(-1)` 输出 `-2`），因为 −1 在 CPython 的 C 层被保留作「发生错误」的返回标志，所以哈希实现特判把它避开。字符串和 bytes 的哈希则经过 SipHash 并按进程随机加盐（详见 4.5.4）。

给初学者的观察实验与真实输出（本机 Python 3.11.15）：在固定随机种子 `PYTHONHASHSEED=0` 下，`hash('abc')` 恒为 `-4594863902769663758`（连跑两次都一样，可复现）；而不固定种子时，两次独立运行分别得到 `-8453826477982279475` 与 `8969217611660546649`——每次进程启动都变。这直接演示了两件事：整数哈希是稳定可预测的（`hash(42)=42`），字符串哈希则被随机化了。要注意这些具体数字是 CPython 的**实现量**（依赖版本与随机种子），不是任何规范承诺的值，换一个 Python 版本或换一个种子就会不同。

## 4.2 链地址法 / 拉链法

### 4.2.1 基本结构

链地址法（chaining，CLRS §11.2）用一个桶数组 T[0..m−1]，每个桶挂一条链表；所有被哈希到同一个槽的键都串在该桶对应的链表上。CLRS 用的是双向链表。

对初学者的心智模型：把哈希表想成一排 m 个挂钩，每个挂钩下面挂一串卡片。要存一个键，先算 h(k) 找到对应挂钩，把卡片挂到那串的末端（或头部）。碰撞在这里根本不是问题——两个键落到同一个挂钩，就只是挂在同一串上而已，谁也不会挤掉谁、也不会去占用别的挂钩。这跟 4.3 的开放定址形成鲜明对比：链地址「向桶外延伸」，开放定址「在表内另找空槽」。

### 4.2.2 操作与代价

插入是 O(1)（在桶链头部插入即可，不必先查重则更快）。查找和删除需要扫描该键所在的那条桶链，期望代价是：

Θ(1 + α)

其中 α = n/m 是**负载因子**（见 4.4.1），n 是元素总数、m 是桶数。CLRS 用双向链表，是为了让「已经定位到某个结点后删除它」变成 O(1)（双向链表能 O(1) 摘除结点，单向链表还得先找前驱）。

给初学者拆解这个 Θ(1+α)：那个「1」是「算哈希 + 跳到桶」的固定开销，「α」是「平均每条桶链有多长」——因为 n 个元素平均分到 m 个桶，每桶期望 α 个。所以只要我们把 α 控制成一个常数（让 m 跟着 n 一起长，见 4.4），每条链就都很短，查找就是期望 O(1)。反过来，如果放任 n 增长而 m 不变，α 会线性增大，每次查找就得扫越来越长的链——这正是必须做再散列（4.4）的动因。

### 4.2.3 简单均匀哈希下的期望查找长度

在简单均匀哈希假设（4.1.5）下，CLRS 给出两个定理：

不成功查找期望扫描的元素数 = Θ(1 + α)   （CLRS 定理 11.1）

成功查找期望扫描的元素数 = Θ(1 + α/2 − α/(2n)) = Θ(1 + α)   （CLRS 定理 11.2）

对初学者，两个结论的直觉分别是：**不成功查找**必须走到桶链末尾才能确定「不存在」，而桶链平均长 α，所以扫 α 个（加上定位那 1 步）；**成功查找**平均只需扫到链的中段就命中目标，所以大约是 α/2，那个 −α/(2n) 是精确计算里的小修正项，n 大时可忽略。两者的量级都是 Θ(1+α)。最终落点是同一句话：只要 α = O(1)（即 m 与 n 同阶增长），链地址哈希表的所有操作都是期望常数时间。

### 4.2.4 空间开销与优点

链地址的代价是额外的指针/结点开销：每个元素至少多存一个指向下一结点的指针（双向链表则是两个），还有每个链结点对象本身的内存。

但它的优点很实在，尤其对初学者值得记的是这两条：一是**删除简单**（找到结点摘链即可，不像开放定址那样会切断探测链、需要墓碑，见 4.3.5）；二是**α 可以大于 1**。因为桶链可以无限长，即使元素数超过桶数（α>1）表也不会「满」，只是链变长、性能下降而已，是优雅退化而非直接失败。这跟开放定址「所有元素必须存在表内、因此 α ≤ 1 是硬约束、表满就插不进」是本质区别。一句话对比：链地址用空间（指针）换来了对负载因子的宽容和删除的简单。

### 4.2.5 手写链地址哈希表（代码示例，可自足复现）

用 Python 的「列表套列表」就能自足实现一个最小的链地址哈希表，帮助初学者把上面的结构落到代码：

```python
class ChainedHashTable:
    def __init__(self, m=8):
        self.m = m
        self.buckets = [[] for _ in range(m)]   # m 个桶，每个桶是一条链（用 list 代替链表）
    def _idx(self, key):
        return hash(key) % self.m               # 除留余数法定位桶
    def put(self, key, val):
        b = self.buckets[self._idx(key)]
        for i, (k, _) in enumerate(b):
            if k == key:
                b[i] = (key, val)               # 键已存在则覆盖
                return
        b.append((key, val))                    # 碰撞则追加到该桶链末尾
    def get(self, key):
        for k, v in self.buckets[self._idx(key)]:
            if k == key:
                return v
        raise KeyError(key)
```

读这段代码时对初学者要点破的是：`put` 和 `get` 里那个 `for` 循环扫的正是 4.2.2 说的「桶链」；正常情况下每个桶链很短（长度约 α），所以循环几乎是常数次；只有当哈希函数差、或 α 失控时，某个桶链会变得很长，那个 `for` 就退化成线性扫描（这正是 4.5 的退化）。这段实现里桶用 Python `list` 而非真正的链表，是为了简洁；教科书用链表是为了 O(1) 的头插与摘除。

- 二手/第二一手交叉：Pat Morin《Open Data Structures》§5.1 ChainedHashTable（第二个一手源，同样给出期望 O(1+α)）；CS61B sp24 Hashing I「External Chaining」（Java 视角，同一 Θ(1+α) 结论）。

## 4.3 开放定址法

### 4.3.1 基本思想

开放定址法（open addressing，CLRS §11.4）不使用桶外链表，而是把**所有元素都存在表数组内部**。发生碰撞时，按一个**探测序列（probe sequence）**依次尝试下一个槽，直到找到空槽（插入）或找到目标键（查找）。探测序列写成 h(k,0), h(k,1), h(k,2), … ，第二个参数 i 是「这是第几次探测」。

因为元素必须都装在表内的 m 个槽里，开放定址有一条硬约束：

α ≤ 1

即元素数不能超过槽数，表一旦装满就再也插不进（不像链地址可以 α>1）。给初学者的心智模型：开放定址像停车场找车位——你有个「首选车位」h(k)，如果被占了，就按一套固定规则（探测序列）挨个往后试，直到找到空位停下；找车时也按同一套规则挨个看，直到看到你的车（找到）或看到一个空位（说明车不在，停止）。下面三小节就是三种不同的「往后试」的规则。

### 4.3.2 线性探测（linear probing）

线性探测的规则是「被占了就看下一个槽」：

h(k, i) = (h′(k) + i) mod m

其中 h′ 是一个普通哈希函数，i = 0,1,2,… 逐次加一。

它实现最简单，而且**缓存局部性好**——探测的都是内存里连续相邻的槽，CPU 缓存友好，实测常常比理论「更聪明」的方法还快。但它有个著名缺陷叫**一次聚集（primary clustering）**：一旦形成一段连续被占的槽（cluster），任何哈希到这段区间里的新键都会被迫排到这段的末尾、使它更长，而越长的段又越容易吸附后续的键——雪球越滚越大。给初学者的直觉：线性探测让「已经堵的地方更容易继续堵」，长堵车段会自我加长，拖慢落在其中的所有查找。

### 4.3.3 二次探测（quadratic probing）

二次探测把步长从「线性 +i」改成「二次方式增长」：

h(k, i) = (h′(k) + c₁·i + c₂·i²) mod m

初学者要抓住的核心是它解决了什么、又带来什么。它**消除了一次聚集**——因为探测的步长越来越大（跳着走），不会像线性探测那样把连续区间填实，所以不会形成那种自我加长的连续堵塞段。但它带来一个较弱的新问题叫**二次聚集（secondary clustering）**：所有**初始槽相同**的键，会走**完全相同**的探测序列，于是它们仍然会互相排队、互相拖慢，只是程度比一次聚集轻。

一个初学者常踩的坑：c₁、c₂ 和 m 不能随便取，否则探测序列可能只覆盖表中一部分槽，导致「明明还有空位却报表满」。CLRS 指出存在若干可行组合（例如配合 m = 2^p 取 c₁ = c₂ = 1/2，或取 m 为质数并只保证覆盖半张表），细节属实现选择，不同教材给法不一，不是分歧而是「多种可行方案」。

### 4.3.4 双重哈希（double hashing）

双重哈希用**第二个哈希函数**来决定步长，是开放定址里最接近理想的方案：

h(k, i) = (h₁(k) + i·h₂(k)) mod m

首个位置由 h₁ 决定，每次探测跨越的步长由 h₂(k) 决定。

它相对前两者的优势：不同的键即使初始槽相同，只要 h₂ 值不同，探测序列就不同，于是几乎不产生聚集，行为最接近 4.1.5 的「理想均匀探测」。给初学者的关键约束是 **h₂(k) 必须与 m 互质**——否则步长 h₂ 和表长 m 有公因子，探测会在表中打转、只能覆盖部分槽而走不遍全表（类比：在 12 格的钟面上每次跳 4 格，永远只踩到 0/4/8 三格）。常见做法是让 m 取质数，或让 m = 2^p 而强制 h₂ 恒为奇数（奇数与 2 的幂互质）。

### 4.3.5 删除的复杂性 —— 墓碑标记（tombstone）

开放定址里删除很棘手。如果直接把一个槽清空，会**切断探测链**：假设 A、B 因碰撞先后探测落在相邻位置，若把中间的 A 清成空槽，之后查找 B 时探测走到那个空槽会误判「遇到空位 → B 不存在」而提前停止，尽管 B 明明还在后面。

解决办法是不真正清空，而是把该槽标记为 **DELETED / 墓碑（tombstone）**。查找时把墓碑当作「已占用、继续往后探测」，插入时则可以复用墓碑槽。给初学者点破代价：墓碑会累积，它们不算有效元素但仍占着槽、仍会拉长探测链，使**有效负载因子**比真实的 n/m 更糟；因此需要靠再散列（4.4）在重建表时把墓碑一并清掉。这也是为什么「开放定址删除多了性能会悄悄变差」——罪魁就是堆积的墓碑。

### 4.3.6 查找期望代价（与 α 的关系）

在均匀探测假设下，CLRS 给出开放定址的期望探测数（定理 11.6 / 11.8）：

不成功查找期望探测数 ≤ 1 / (1 − α)

成功查找期望探测数 ≤ (1/α) · ln(1 / (1 − α))

初学者只需从公式看趋势：分母是 (1−α)，当 α 趋近 1（表快满了）时分母趋近 0，代价急剧飙升。举个直观的数：α = 0.5 时不成功查找约 2 次探测，α = 0.9 时就变成约 10 次探测，α = 0.99 时约 100 次。这条曲线是「后期爆炸式」的——所以开放定址实践中通常把 α 控制得比链地址更保守（如 ≤ 0.7），一旦超阈值就扩容再散列（4.4）。这也从公式层面解释了为什么开放定址对负载因子比链地址敏感得多。

### 4.3.7 探测序列 / 聚集可视化（可选实证）

可以用一个 Python 数组模拟线性探测与双重探测，往里插入随机键并统计「平均探测长度随 α 上升」的曲线，就能直观看到线性探测的聚集如何让曲线更早、更陡地上翘。本报告未跑该可视化（标为可选实证），但读者可据 4.3.6 的两个公式自行画出理论曲线作对照。

## 4.4 负载因子与再散列 —— CLRS 理论 vs CPython 实现

### 4.4.1 负载因子 α 的支配作用

负载因子定义为元素数与槽数之比：

α = n / m

它是哈希表性能的**单一支配参数**：链地址的期望代价是 Θ(1+α)（4.2.3），开放定址约为 1/(1−α)（4.3.6）——两个公式里出现的都只有 α。

给初学者的收束：想让哈希表保持期望 O(1)，本质上就是「把 α 钉在一个常数阈值以内」。n 会随插入不断增长，如果 m 固定不变，α 迟早失控；所以工程上的对策是**让 m 随 n 一起长**，一旦 α 越过阈值就把表扩大（下一小节）。可以把 α 理解成哈希表的「拥挤度」——它一超标，所有操作都变慢，所以整个哈希表的性能管理，归根到底就是管住这一个数。

### 4.4.2 动态扩容 / 再散列（table doubling，均摊 O(1)）

当插入使 α 超过阈值时，分配一张约两倍大的新表，并把**所有元素重新哈希**迁进去（不能简单内存拷贝，因为 h 依赖 m，m 变了每个键的槽号都得重算）。

单次这样的再散列（rehash）是 O(n)——要搬 n 个元素。听起来很贵，但关键在于**表倍增**：每扩一次容量翻倍，所以再散列发生得越来越稀疏（在第 1、2、4、8、16… 个元素处才触发）。把这些偶发的大开销均摊到每一次插入上，平均每次插入仍是 O(1)。写成均摊结论：

n 次插入的总代价 = O(n)，故均摊每次插入 = O(1)

这套论证叫**均摊分析（amortized analysis，CLRS Ch16）**，常用聚合法或势能法证明。给初学者的直觉类比：像搬家——大多数日子什么都不用搬（O(1) 插入），偶尔翻倍时要把全部家当搬一次（O(n)），但因为「翻倍」让搬家越来越少发生，平摊到每天的搬运量其实是常数。要点破的误区是：均摊 O(1) **不代表每次都 O(1)**——触发再散列的那一次插入确实是 O(n)，只是长期平均下来是常数。

### 4.4.3 缩容（shrink）与阈值滞后

大量删除后表会变得很空（α 很小），可以把表缩小以回收内存。但缩容阈值不能设得和扩容阈值挨着，否则会**抖动（thrashing）**：在阈值附近反复地「插一个就扩、删一个就缩」，每次都触发 O(n) 的重建，性能崩塌。

对策是让缩容阈值显著低于扩容阈值，中间留一条**滞后带（hysteresis）**作缓冲。常见做法例如「装到 2/3 才扩容，但要空到 1/8 才缩容减半」——扩与缩之间隔着一大段，元素数在这段区间里来回也不会触发任何重建。这属于通用的工程直觉。要对初学者澄清一个实现事实：CPython 的 dict 并没有独立的「缩容路径」，它只在因插入触发 resize 时按当前实际用量重算表的大小，删除本身不会主动缩表——所以上面的「1/8 缩容」是通用直觉的举例，不是 CPython 的具体行为。

### 4.4.4 CPython 紧凑 dict 的实现要点（实现量，读源码取证 @v3.11.15）

CPython 的 dict 自 3.6 起采用**紧凑（compact）布局**，把结构拆成两段：一个稀疏的**索引数组** `dk_indices[]`（存的是到 entries 的下标），和一个**紧凑连续**的 `dk_entries[]` 数组（按插入顺序追加地存放每条 (hash, key, value)）。查找走「indices 找到下标 → entries 取数据」的两跳。

这个设计对初学者最值得记的收益是**保序**：因为 `dk_entries[]` 是按插入顺序追加的，只要顺序遍历它就得到插入顺序——这正是「dict 保持插入顺序」这一自 Python 3.7 起的**语言级保证**的实现基础（3.6 是实现细节，3.7 起写进语言规范）。冲突解决用的是开放定址加一个**伪随机扰动（perturb）**探测。以下常量为读 `Objects/dictobject.c` @v3.11.15 原文取证（非凭记忆）：

- 探测递推：`perturb >>= PERTURB_SHIFT; i = (i*5 + perturb + 1) & mask;`，基础序列相当于 `j = (5*j + 1) mod 2^i`；`#define PERTURB_SHIFT 5`。这是一种**伪随机探测**，既不是线性、也不是二次、也不是标准双重哈希——它把哈希值的高位逐步「搅」进探测序列，兼顾打散与初期的缓存局部性。
- 扩容触发：`#define USABLE_FRACTION(n) (((n) << 1) / 3)`，源码注释说明「当表装到 USABLE_FRACTION（当前是三分之二）满时 resize」——即装填到约 **2/3** 触发 resize。
- 增长率：`#define GROWTH_RATE(d) ((d)->ma_used*3)`，注释「无删除地增长时 dict 大小翻倍……GROWTH_RATE 在 3.2 及以前是 used*4，3.3.0 起是 used*2」——3.11 为 **used*3**（在有删除的情形下留更多余量）。

本机观察 dict 扩容的字节数台阶（`sys.getsizeof` 随元素数变化，Py3.11.15 实测）：从第 1 到第 15 个元素，字节数在第 6 个元素处从 224 跳到 352、在第 11 个元素处从 352 跳到 632。即初始 8 槽的表，装到约第 5 个元素（8 的 2/3 ≈ 5.3）就触发扩容——与 USABLE_FRACTION = 2/3 的阈值一致。这给初学者一个可亲手验证的「理论落到实现」的锚点。

### 4.4.5 规范 vs 实现分账（显式）

必须把「教科书理论」和「CPython 的具体选择」分开看，这是本节的核心纪律：

**CLRS 理论**给的是通用框架和界——链地址、开放定址（线性/二次/双重）、α 阈值、表倍增均摊——它们都是「一族方法」和「渐近界」，并不指定任何具体常量。

**CPython dict** 是这族框架里的一组**具体工程选择**，而且它**偏离**了教科书的任一标准探测法：用紧凑双数组（教材用单槽数组）、用 `i*5 + perturb + 1` 的**伪随机探测**（不是线性/二次/双重中的任何一种）、2/3 触发 resize、used*3 的增长率、并额外提供了保序。

两者不能混为一谈：教材回答的是「这一族方法的期望界是多少」，CPython 源码回答的是「这一个实现选定的确定常量是什么」。前者是数学结论、跨实现通用；后者是版本相关的实现量、会随 Python 版本演进（如增长率历史上从 used*4 → used*2 → used*3）。同理，Java 的 `HashMap` 又是另一组不同的具体选择（见 4.5.3），足见「同一套理论，多种实现」。

## 4.5 最坏 O(n) 退化

### 4.5.1 最坏情形

哈希表的期望 O(1) 有一个隐含前提——键被近均匀地散开。当这个前提被彻底破坏、所有键都碰撞到**同一个桶**（链地址）或**同一条探测链**（开放定址）时，哈希表就退化成一条线性结构，查找 / 插入 / 删除都变成：

O(n)

给初学者点破：这时哈希表其实已经「名存实亡」，退化成了一个链表或一段线性扫描的数组区间——4.2.5 代码里那个本应几乎空转的 `for` 循环，现在要扫遍全部 n 个元素。所以「哈希表平均 O(1)」这句话严格说是「期望 O(1)、最坏 O(n)」，最坏这一档在特定输入下是真实会发生的。

### 4.5.2 触发条件

退化有两类触发原因。其一是**坏哈希函数**：分布严重不均，比如用了 h(k)=k mod 2^p 又遇上低位有规律的键（回到 4.1.2 的坑），大量键挤进少数槽。其二是**对抗性输入（adversarial input）**：攻击者知道你用的哈希函数（固定且公开时很容易反推），故意构造大量会落到同一槽的键喂进来——这叫碰撞洪水。

对初学者要强调的是：第二类是「安全问题」而非「运气问题」。普通随机数据几乎不会触发退化，但一个有意的攻击者可以精确地制造它——这就是为什么现代哈希表要引入随机化（下一小节），把「攻击者能预测」变成「攻击者无法预测」。

### 4.5.3 缓解手段：随机化哈希、控 α、桶内改树

有三条主要手段。其一，**全域 / 随机化哈希**（4.1.4）：运行时随机选哈希函数，让攻击者无法预测键落到哪个槽，从而把「可被构造的最坏情形」重新变回「期望情形」。其二，**良好的 α 控制 + 再散列**（4.4）：保持负载因子低，桶链自然短。其三，**桶内改用平衡树**：当某个桶链长到一定程度时，把这条链从链表换成一棵平衡树（红黑树），使单桶最坏从 O(n) 降到 O(log n)。

Java 8+ 的 `HashMap` 是「桶内改树」的著名实现对照：当单个桶的链长达到 **TREEIFY_THRESHOLD = 8** 且表容量 ≥ **MIN_TREEIFY_CAPACITY = 64** 时，把该桶转成红黑树；当树缩到 **UNTREEIFY_THRESHOLD = 6** 时退回链表。给初学者的直觉：阈值取 8 是因为在 0.75 的默认装填下，单桶元素数近似服从均值 λ≈0.5 的泊松分布，链长达到 8 的概率极低（约 6×10⁻⁸），正常数据下几乎永不 treeify，只有在异常（含攻击）分布下才启用这条兜底。作为对照，CPython 的 dict **不做** treeify，它走的是「随机化哈希 + 把 α 保持在 ≤2/3」这条路线——同一个退化问题，Java 和 CPython 选了不同的缓解策略。

### 4.5.4 安全视角：碰撞 DoS 与 hash randomization

哈希碰撞可以被武器化成**拒绝服务攻击（DoS）**：攻击者构造大量碰撞键塞给服务端（如 HTTP 请求参数被存进哈希表），使哈希表退化，让本该 O(1) 的操作变成 O(n)、整体 O(n²)，用很少的请求就拖垮 CPU。

CPython 的对策是对字符串 / bytes 的哈希做**随机化**：默认每个进程启动时按环境变量 `PYTHONHASHSEED` 生成一把随机盐，算法用 **SipHash**。一个版本相关的事实要标清楚：**CPython 3.11 起默认从 SipHash-2-4 改为 SipHash-1-3**（更快；见 PEP 456 与相关 commit / bpo-29410）。设 `PYTHONHASHSEED=0` 可关闭随机化以便复现。

本机真跑证实（Py3.11.15）：`PYTHONHASHSEED=0` 时 `hash('abc')` 恒为 `-4594863902769663758`（可复现）；不设种子时两次独立运行分别得 `-8453826477982279475` 与 `8969217611660546649`（每进程随机）。而整数哈希**不**随机化（`hash(42)` 仍为 42）。给初学者的收束：随机化只保护「攻击者能构造的键类型」（主要是字符串），靠的是让盐不可预测，这样即便攻击者知道算法也算不出你这个进程里键会落到哪——正是 4.1.4 全域哈希思想的工程落地。

### 4.5.5 制造碰撞键观察退化（可选实证）

可以在 `PYTHONHASHSEED=0`（关随机化、结果可复现）下，构造大量满足 `hash(k) % m` 同值的键，塞进一个自写哈希表或观察查找耗时随键数增长的曲线，就能亲眼看到查找从近常数变成线性。本报告未跑该退化计时（标为可选实证），但 4.5.1–4.5.4 的机制已足以解释为何会发生。

- 本机实证：`PYTHONHASHSEED=0` 下 `hash('abc')` 恒定、不设种子时逐进程变化，整数哈希不随机化——均本机 Py3.11.15 实测。
