# L5-09·大主题6 无障碍与包容性设计

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01 ｜先修：HCI-2 可用性的可测量定义、HCI-3 交互设计原则（无直接 CS 前置）｜一手锚点：W3C WCAG 2.2（Recommendation 2023-10-05；编辑更新 2024-12-12，成功准则未变）、WAI-ARIA、ISO/IEC 40500:2025 ｜成熟度：GA（WCAG 2.2 标准侧稳定；ISO 采纳、WCAG 3.0 草案属 ⚙演进快）

无障碍（accessibility）关注让残障人士与处于受限情境的人也能感知、操作、理解并稳定使用数字产品；包容性设计（inclusive design）与通用设计（universal design）是把这一目标前移到设计流程的取向。本报告以 W3C 的 WCAG 2.2 技术标准为骨架，按其四大原则 POUR（Perceivable / Operable / Understandable / Robust）逐层展开，再补合规结构、辅助技术与包容性设计取向。技术标准侧在此收口；关于无障碍的社会正当性、公平获取与法律政策诉求属社会伦理主题，本报告不重复深挖，只在分账处点到为止。

## 6.1 可感知（Perceivable）

### 6.1.1 可感知原则：信息必须能被用户的某种感官接收

可感知是 WCAG 四原则中的第一条，要求界面呈现的信息与组件必须以用户能够感知的方式提供——不能让内容以只有单一感官（例如只有视觉、或只有听觉）才能获取的形式存在。它对应 WCAG 中编号以 1 开头的四条准则（1.1 文本替代、1.2 时基媒体、1.3 可适应、1.4 可区分）。

对初学者最直观的理解方式是"换一个感官通道还能不能拿到同样的信息"。一张图片如果只用像素表达信息，盲人用户的屏幕阅读器就读不出来；一段只有声音的语音提示，聋人用户就接收不到。可感知原则的核心手法就是为每一种感官上"走不通"的内容准备一条替代通道：图配文字、音配字幕、颜色配形状或标签。这条原则不要求你把内容做得"好看"，而是要求信息在任何一个通道被堵死时仍有出路。

### 6.1.2 文本替代（Guideline 1.1）

准则 1.1 只有一条成功准则 1.1.1 Non-text Content（非文本内容，等级 A），要求所有非文本内容（图片、图标、图表、按钮上的图形等）都提供等效的文本替代（text alternative），以便文本能被转换成用户需要的形式，如放大字、语音、盲文或符号。

文本替代之所以是无障碍的第一块基石，是因为文本是唯一能被所有辅助技术自由转换的通用格式：屏幕阅读器把它读成语音，盲文点显器把它变成触觉，翻译工具把它换成别的语言。写替代文本的关键不是"描述这张图长什么样"，而是"这张图在这里承担什么功能"。一个容易踩的坑是给纯装饰性图片也硬写描述——正确做法是把纯装饰图标记为空替代文本（例如 `alt=""`），让辅助技术直接跳过它，否则用户会被无意义的朗读淹没。

### 6.1.3 时基媒体：字幕与音频描述（Guideline 1.2）

准则 1.2 针对随时间播放的媒体（音频、视频）。它要求为纯音频提供文字稿、为视频的对白与关键声音提供同步字幕（captions），并为画面中承载信息而声音里没有的内容提供音频描述（audio description）。不同层级要求逐级加强：预录字幕在 A/AA 级要求，实时字幕（live captions）在 AA 级要求。

字幕和文字稿容易被初学者混为一谈：文字稿（transcript）是一整段可离线阅读的文本，服务的是聋人以及想快速扫读的人；字幕是与画面同步、逐句出现的文本，还要标出"谁在说""有音乐/掌声"等非对白声音信息。音频描述解决的是另一个方向的缺口——盲人用户听得到对白，但看不到画面里"角色默默递出一封信"这类只用视觉表达的关键情节，所以要在对白间隙插入语音描述。

### 6.1.4 可适应内容（Adaptable, Guideline 1.3）

准则 1.3 要求内容能在不丢失信息或结构的前提下，以不同方式呈现（例如更简单的布局、被辅助技术重新组织）。核心成功准则包括 1.3.1 Info and Relationships（信息与关系，A）——视觉上表达的结构（标题、列表、表格的行列关系、表单标签与控件的对应）必须同时用程序可确定的方式标记出来；1.3.2 Meaningful Sequence（有意义的顺序，A）——阅读顺序在代码层面要正确；以及 1.3.5 Identify Input Purpose（识别输入用途，AA）等。

视觉用户靠"看到的排版"理解结构，屏幕阅读器用户靠"代码里标出的结构"理解同一份内容。如果一个标题只是被做大做粗、却没用真正的标题标记，视觉用户看得出层级，屏幕阅读器用户却只听到一句普通文字，导航能力就丧失了。常见错误是用表格纯粹排版、或用连续的粗体假装标题——这会让程序无法确定的结构对辅助技术彻底失效。

### 6.1.5 可区分内容与颜色使用（Distinguishable, Guideline 1.4）

准则 1.4 让内容更容易被看清、听清，把前景从背景中区分出来。它包含一批高频准则：1.4.1 Use of Color（不以颜色作为传达信息的唯一手段，A）、1.4.3 Contrast (Minimum)（文本对比度最低要求，AA）、1.4.4 Resize Text（文本可放大到 200% 不丢失内容，AA）、1.4.10 Reflow（内容在等效 320 CSS 像素宽的视口下重排、无需双向滚动，AA）、1.4.11 Non-text Contrast（非文本对比度，AA）、1.4.12 Text Spacing（用户可覆盖文本间距，AA）。

文本间距 1.4.12 要求即使用户强制调大间距，内容也不裁切、不丢失，其可覆盖的下限为：

行高 ≥ 1.5 × 字号；段间距 ≥ 2 × 字号；字母间距 ≥ 0.12 × 字号；单词间距 ≥ 0.16 × 字号

"不以颜色为唯一手段"是最容易被初学者忽视又最容易改的一条：如果表单只用红色边框表示"这里填错了"，红绿色盲用户就看不出哪里错。正确做法是颜色之外再加一个非颜色线索——文字提示、图标或下划线。Reflow 关注的是低视力用户放大页面后的体验：放大到 400% 时若还要左右来回拖动才能读完一行，阅读几乎不可能，所以内容要能像手机窄屏那样自动重排成单列。

### 6.1.6 对比度比值公式与阈值

对比度用两个颜色的相对亮度（relative luminance）L1（较亮者）与 L2（较暗者）计算，比值定义为：

contrast ratio = (L1 + 0.05) / (L2 + 0.05)

比值范围从 1:1（两色完全相同）到 21:1（纯黑对纯白）。WCAG 对文本对比度的阈值分层级：AA 级要求普通文本 ≥ 4.5:1、大号文本 ≥ 3:1（1.4.3）；AAA 级要求普通文本 ≥ 7:1、大号文本 ≥ 4.5:1（1.4.6 Contrast (Enhanced)）。非文本对比度 1.4.11 要求界面组件与图形对象相对相邻颜色 ≥ 3:1。

公式里那个 0.05 是环境光反射项，用来避免两个都很暗的颜色因分母趋近 0 而算出虚高的对比度，让极暗区间的判定更贴近人眼实际。这里"大号文本"有明确门槛（约 18pt 常规或 14pt 加粗以上），因为字越大笔画越粗，同样的对比度下更容易辨认，所以阈值可以放宽。初学者常犯的错是拿"看起来够清楚"当标准——人眼主观判断不可靠，必须用公式或对比度检查工具量化，尤其浅灰配白这种设计上常见的"高级感"配色往往达不到 4.5:1。

## 6.2 可操作（Operable）

### 6.2.1 可操作原则：界面组件与导航必须能被操作

可操作是第二原则，要求用户界面组件和导航是可操作的——用户能用自己所依赖的输入方式（键盘、开关、语音、触摸等）触达并激活每一个功能。它对应编号以 2 开头的准则（2.1 键盘可访问、2.2 充足时间、2.3 癫痫与身体反应、2.4 可导航、2.5 输入方式）。

理解可操作的关键是意识到"不是每个人都能用鼠标"。运动障碍用户可能只能用键盘或单个开关，盲人用户看不到光标位置只能靠键盘 Tab 顺序移动。因此可操作原则的底线是：凡是鼠标能做的事，键盘也要能做到，而且不能把用户"困住"。

### 6.2.2 键盘可达（Guideline 2.1）

准则 2.1 要求所有功能都能通过键盘接口使用（2.1.1 Keyboard，A），并且键盘焦点不会被卡住无法移出（2.1.2 No Keyboard Trap，A）；WCAG 2.1 起还加入了 2.1.4 Character Key Shortcuts（单字符快捷键可关闭/重映射，A）。

键盘可达是无障碍里牵一发而动全身的一条，因为屏幕阅读器、语音控制、开关设备大多在底层模拟键盘操作，键盘走不通它们全部失效。"键盘陷阱"是一个典型坑：某个自定义弹窗能用 Tab 进去却出不来，鼠标用户点一下别处就走了，纯键盘用户却被永久困住。自定义控件（用 div 拼出来的按钮、下拉框）最容易丢键盘可达性，因为原生 `<button>`、`<a>` 天生可聚焦可回车，而 div 需要手动补上焦点与键盘事件。

### 6.2.3 充足时间（Guideline 2.2）

准则 2.2 要求给用户足够时间阅读和使用内容。2.2.1 Timing Adjustable（可调整时间限制，A）要求任何时间限制都能被关闭、调长或延长；2.2.2 Pause, Stop, Hide（暂停、停止、隐藏，A）要求自动滚动、闪烁或轮播的内容能被用户停下。

不同用户完成同一任务的时间差异极大：认知障碍、低视力或使用屏幕阅读器的人可能需要数倍时间。一个会话在几分钟无操作后自动登出、且不给延长机会，对他们就是把功能锁死。自动轮播的图片横幅也是常见障碍——它不断变化会干扰阅读困难和注意障碍用户，所以必须给一个能停下来的控件。

### 6.2.4 避免癫痫与身体反应（Guideline 2.3）

准则 2.3 的核心是 2.3.1 Three Flashes or Below Threshold（三次闪烁或低于阈值，A），要求页面上任何内容在任意一秒内闪烁不超过三次，除非闪烁足够小且亮度/红色成分低于规定阈值。

这条准则直接关系人身安全：高频闪光可能诱发光敏性癫痫发作。"每秒三次"是一个可直接检验的硬门槛，初学者只要记住"别做每秒闪超过三下的强闪光内容"即可覆盖绝大多数情形。AAA 级的 2.3.2 更严格（完全不允许每秒超过三次闪烁），2.3.3 还涉及可关闭的动效。

### 6.2.5 可导航（Guideline 2.4）

准则 2.4 帮助用户导航、查找内容并知道自己身处何处，成功准则众多：2.4.1 Bypass Blocks（跳过重复区块，如"跳到主内容"链接，A）、2.4.2 Page Titled（页面有标题，A）、2.4.3 Focus Order（焦点顺序合理，A）、2.4.7 Focus Visible（焦点可见，AA）等。WCAG 2.2 在此新增了 2.4.11 Focus Not Obscured (Minimum)（聚焦元素不被完全遮挡，AA）与 AAA 级的 2.4.12、2.4.13。

对纯键盘用户，"焦点在哪"就是他们的"光标在哪"——如果焦点框不可见，或者 Tab 到的元素被固定页头/悬浮 Cookie 横幅盖住，用户就彻底迷失。2.4.11 正是为解决"焦点被吸顶栏遮住"这一现实高频问题而在 2.2 版新增。"跳过区块"链接则让屏幕阅读器与键盘用户不必每页都听/按几十次导航菜单才到正文。

### 6.2.6 输入方式（Guideline 2.5）

准则 2.5 关注指针、手势等多样输入。2.5.1 Pointer Gestures（复杂手势有单指替代，A）、2.5.2 Pointer Cancellation（可取消误触，A）、2.5.3 Label in Name（可见标签包含在可编程名称中，A）。WCAG 2.2 在此新增 2.5.7 Dragging Movements（拖拽动作有非拖拽替代，AA）与 2.5.8 Target Size (Minimum)（目标尺寸最小值，AA）。

目标尺寸最小值要求指针目标至少：

24 × 24 CSS 像素（AA 级 2.5.8；AAA 级 2.5.5 Target Size (Enhanced) 要求 44 × 44 CSS 像素）

小到 24 像素的下限是为运动控制受限和触屏用户设的——太小太密的按钮会频繁误触。2.5.8 提供了"间距足够""别处有等效控件""行内目标""用户代理决定尺寸"等豁免。2.5.7 拖拽替代则针对无法完成精细拖动的用户：凡是需要拖拽的操作（如滑块、拖放排序）都要提供点击式的等效方式。

## 6.3 可理解（Understandable）

### 6.3.1 可理解原则：信息与界面操作必须能被理解

可理解是第三原则，要求内容的信息以及界面的操作方式对用户是可理解的——文字读得懂、界面行为可预测、出错时能被帮着改正。它对应编号以 3 开头的准则（3.1 可读、3.2 可预测、3.3 输入辅助）。

前两条原则解决"能不能拿到、能不能操作"，可理解解决"拿到后看不看得懂、操作起来会不会被绕晕"。它对认知障碍、阅读障碍、语言能力有限的用户尤其重要，但对所有人都有益——没人喜欢措辞晦涩、行为反复无常的界面。

### 6.3.2 可读（Guideline 3.1）

准则 3.1 让文本内容可读、可理解。3.1.1 Language of Page（页面语言可编程确定，A）与 3.1.2 Language of Parts（段落语言，AA）要求在代码中标明内容所用语言；AAA 级还涉及生僻词、缩写、阅读难度等。

标注语言看似小事，却直接决定屏幕阅读器用对不对发音引擎：一段法语若被标成英语，合成语音会读成一串莫名其妙的音节。对多语言页面，逐段标注语言能让辅助技术在英中法之间正确切换发音。

### 6.3.3 可预测（Guideline 3.2）

准则 3.2 要求网页以可预测的方式呈现和运作。3.2.1 On Focus（获得焦点不引发意外的语境变化，A）、3.2.2 On Input（改变输入不自动跳转/提交，A）、3.2.3 Consistent Navigation（导航一致，AA）、3.2.4 Consistent Identification（相同功能标识一致，AA）。WCAG 2.2 新增 3.2.6 Consistent Help（一致的帮助入口，A）。

可预测的直觉是"界面不要在用户没主动触发时擅自变脸"。一个下拉框只要选了个值就立刻跳转页面，会让屏幕阅读器用户措手不及；同一个"搜索"按钮在不同页面时而在左时而在右、图标还不一样，会加重记忆负担。3.2.6 Consistent Help 是 2.2 版针对"用户卡住时能不能稳定找到求助入口"新增的——帮助链接、联系方式在各页面的相对位置应保持一致。

### 6.3.4 输入辅助与错误纠正（Guideline 3.3）

准则 3.3 帮助用户避免和纠正错误。3.3.1 Error Identification（错误可被识别并用文本说明，A）、3.3.2 Labels or Instructions（表单有标签或说明，A）、3.3.3 Error Suggestion（给出纠错建议，AA）、3.3.4 Error Prevention（对法律/财务/数据类提交可复核撤销，AA）。WCAG 2.2 新增 3.3.7 Redundant Entry（避免重复录入，A）与 3.3.8 Accessible Authentication (Minimum)（无障碍认证，AA，AAA 为 3.3.9）。

错误处理是无障碍与普通可用性高度重合的区域。仅用红框标错对色盲用户无效，所以 3.3.1 要求"用文本说明哪里错、错在哪"。3.3.8 Accessible Authentication 是 2.2 版一条影响很大的新增：它禁止把"必须靠记忆或转录（如认知型验证码、记住并输入一串字符）"作为登录的唯一步骤，因为这对认知障碍和读写障碍用户构成硬门槛——应允许粘贴密码、使用密码管理器或生物识别等替代。3.3.7 Redundant Entry 要求同一流程内已填过的信息不必再手填一遍。

## 6.4 健壮（Robust）

### 6.4.1 健壮原则：内容须能被现在与未来的用户代理稳定解析

健壮是第四原则，要求内容足够健壮，能被各种用户代理（包括浏览器和辅助技术）可靠地解释，并随技术演进继续可用。它对应编号以 4 开头的准则（历史上是 4.1）。

前三条原则关注人怎么感知、操作、理解，健壮关注的是"机器（尤其辅助技术）能不能正确读出这份内容"。它是无障碍的技术地基：如果屏幕阅读器无法判断某个控件是按钮还是复选框、是否被勾选，前面做得再好也白搭。

### 6.4.2 兼容性与 Name, Role, Value（4.1.2）

准则 4.1 Compatible 下的核心成功准则是 4.1.2 Name, Role, Value（名称、角色、值，A），要求所有界面组件的名称（用途标签）、角色（它是什么类型的控件）、状态与值都能被程序确定，并在变化时通知辅助技术。

这条准则是自定义控件无障碍的命门。原生 HTML 控件自带名称、角色和状态（`<input type="checkbox">` 天生告诉辅助技术"我是复选框，现在没勾选"）；而用 div/span 拼出来的自定义控件默认什么都不告诉辅助技术，屏幕阅读器只会读出一团无意义的文字。补救方式是通过 WAI-ARIA 显式赋予 role、状态属性和可访问名称，让机器重新"看懂"这个控件。

### 6.4.3 4.1.1 Parsing 的移除（版本变更）

WCAG 2.2 相对旧版的一个显著变化是移除了原 4.1.1 Parsing（解析）准则，规范中明确标注其为"Obsolete and removed（已废弃并移除）"。

4.1.1 原本要求标记语言的元素有完整起止标签、无重复属性、正确嵌套等。移除的理由是：现代浏览器和辅助技术早已能稳健处理这类解析问题，该准则针对的实际障碍在当代已基本消失，继续保留反而制造无意义的合规负担。这是初学者对照新旧版本时最易犯错的地方——很多老资料仍把 4.1.1 列为有效准则，务必以 2.2 版"已移除"为准。它是 WCAG 2.2 中唯一被移除的成功准则，也是 2.2 总数比"2.1 加 9 条新增"少一条的原因。

### 6.4.4 状态消息（4.1.3 Status Messages）

4.1.3 Status Messages（状态消息，AA，自 WCAG 2.1 引入）要求那些不获得焦点也能呈现给用户的状态消息（如"已保存""搜索到 5 条结果""购物车已更新"）能被程序确定角色，从而被辅助技术主动播报。

视觉用户能瞥见页面角落弹出的"操作成功"提示，但如果这条消息没被标为状态消息，屏幕阅读器不会主动读出来，盲人用户就完全不知道刚才的操作有没有生效。用 ARIA 的 live region 标记这类消息，可让辅助技术在焦点不动的情况下即时播报变化。

- 4.1.1 移除、86 条总数与"2.1 的 78 条 + 9 新增 − 1 移除"的算术：WCAG 2.2 规范与多份独立 2.2 变更说明交叉一致（核实 2026-08-01）。

## 6.5 合规等级与准则结构

### 6.5.1 三级一致性等级 A / AA / AAA

WCAG 定义三个一致性（conformance）等级：A（最低）、AA、AAA（最高）。每条成功准则被归入其中一级；要达到某一致性等级，必须满足该级及其以下所有等级的成功准则（达到 AA 需同时满足全部 A 与 AA 准则）。

分级的用意是给出可分阶段落地的门槛：A 级是排除最严重障碍的底线，AAA 级是最高追求。规范明确指出，AAA 不建议、也往往不可能对整站全部内容强制达成（某些 AAA 准则对特定内容类型根本无法满足），所以实践与法规普遍以 AA 作为目标基准。初学者常见误解是"AAA 是每个网站都该冲的目标"——事实上 W3C 本身不推荐把整站 AAA 设为通用要求。

### 6.5.2 规范的四层结构：原则—准则—成功准则—技术

WCAG 采用分层结构：顶层是 4 条原则（POUR），其下是若干条准则（guidelines，是宽泛目标），再下是可测试的成功准则（success criteria，即真正判定通过/不通过的条款并带 A/AA/AAA 等级），最底层是非规范性的充分技术（sufficient techniques）与失败案例（failures），示范如何满足或如何违反。

区分"准则"和"成功准则"对读规范很关键：准则本身不可直接测试（如"让内容可区分"太宽泛），真正拿来打分的是其下具体、可判定的成功准则（如"对比度 ≥ 4.5:1"）。技术层是"怎么做"的建议，不属于规范强制部分——你可以用规范没列出的其它方法达标，只要能满足成功准则即可。

### 6.5.3 成功准则总数与版本演进

WCAG 2.2 共有 86 条成功准则。它在 WCAG 2.1 的 78 条基础上新增 9 条、移除 1 条（4.1.1 Parsing），即 78 + 9 − 1 = 86。

版本脉络：WCAG 2.0 于 2008 年成为 W3C Recommendation（也是最初被采纳为 ISO/IEC 40500:2012 的版本），WCAG 2.1 于 2018 年发布补充移动、低视力与认知方面的准则，WCAG 2.2 于 2023-10-05 成为 Recommendation。按等级细分，多份独立来源给出 A 级 31 条、AA 级 24 条、AAA 级 31 条（合计 86）；此细分为二手实践资料统计、与 86 总数自洽，若需精确到每级请以逐条清点规范为准，此处标「细分数字以规范逐条清点为准」。存在一个常见外部错误是把总数写成 87——那是忘记减去已移除的 4.1.1 所致，应以 86 为准。

### 6.5.4 WCAG 2.2 新增的九条成功准则一览

WCAG 2.2 相对 2.1 新增的 9 条成功准则如下：

2.4.11 Focus Not Obscured (Minimum) — AA
2.4.12 Focus Not Obscured (Enhanced) — AAA
2.4.13 Focus Appearance — AAA
2.5.7 Dragging Movements — AA
2.5.8 Target Size (Minimum) — AA
3.2.6 Consistent Help — A
3.3.7 Redundant Entry — A
3.3.8 Accessible Authentication (Minimum) — AA
3.3.9 Accessible Authentication (Enhanced) — AAA

这 9 条集中回应了三类现实痛点：焦点可见性在有吸顶栏/悬浮层时的失效（2.4.11–2.4.13）、指针操作对运动受限用户的门槛（2.5.7–2.5.8）、以及认知负担（记住帮助入口、重复填表、记忆型登录，3.2.6/3.3.7/3.3.8/3.3.9）。可以看到多数落在 AA 级，意味着以 AA 为目标的项目升级到 2.2 时确有新工作量。

### 6.5.5 一致性要求（Conformance Requirements）

除逐条满足成功准则外，规范还规定了五项一致性要求：达到声称的等级、以完整页面为单位评估、页面处于完整流程中时整条流程都要合规、只用支持无障碍的技术（accessibility-supported）实现功能、且无障碍技术不被页面上其它内容干扰。

初学者常把"合规"理解成"逐条准则勾选完就行"，但一致性要求补上了整体约束：你不能只让首页达标而结账流程中途某页不达标（流程完整性），也不能一边加了替代文本、一边又有别的脚本破坏辅助技术（不干扰）。合规是对"完整页面 / 完整流程"的判定，不是零散控件的加总。

### 6.5.6 ISO/IEC 40500 采纳与法规引用

WCAG 2.2 已被采纳为国际标准 ISO/IEC 40500:2025（W3C WAI 公告日期 2025-10-21）。需注意版本对应关系：ISO/IEC 40500:2025 对应的是 WCAG 2.2 的 2023 年 10 月版本；含 2024-12-12 编辑更新的版本预计后续以 ISO/IEC 40500:2026 形式发布（⚙演进快·锚版本·随时变，核实 2026-08-01，具体发布时间待核）。此前 WCAG 2.0 曾被采纳为 ISO/IEC 40500:2012。

把 WCAG 采纳为 ISO 标准的意义在采购与法律引用层面：许多国家和机构的采购规则要求引用国际标准，ISO 编号让 WCAG 更容易被写进合同与法规（例如欧盟的 EN 301 549 无障碍标准即以 WCAG 为技术基础）。对内容判定而言，ISO/IEC 40500 与对应版本的 WCAG 在技术条款上是同一套东西——采纳只是换了个正式"身份证号"，成功准则本身不变。关于无障碍在法律与社会公平层面的正当性诉求属社会伦理主题，本报告不展开。

## 6.6 辅助技术与包容性设计原则

### 6.6.1 辅助技术（Assistive Technology）概览

辅助技术（AT）是残障用户用来感知、操作计算设备的软硬件中介：屏幕阅读器（把界面读成语音或盲文，如 NVDA、JAWS、VoiceOver）、屏幕放大器、语音控制/语音识别输入、开关设备（switch，用一两个物理按键扫描选择）、替代键盘与眼动追踪等。WCAG 的健壮原则正是为保证内容能被这些 AT 正确解释而设。

理解 AT 的关键是把它看成用户与界面之间的"翻译层"：屏幕阅读器用户听到的不是页面本身，而是 AT 从代码结构里重建出来的一份线性朗读稿。这解释了为什么"视觉上看起来没问题"不等于"无障碍"——AT 读的是代码里的语义（标题、角色、名称、状态），而不是像素。若代码没把语义标出来，AT 就无从翻译。

### 6.6.2 无障碍 API 与 WAI-ARIA

浏览器把网页内容转成一棵无障碍树（accessibility tree）暴露给操作系统的无障碍 API，AT 再从中读取每个元素的名称、角色、状态。当原生 HTML 的语义不够用时（尤其是 JS 拼装的自定义组件），开发者用 WAI-ARIA（Accessible Rich Internet Applications，W3C 规范）补充 role（角色）、state/property（状态与属性，如 `aria-expanded`、`aria-checked`）和可访问名称（如 `aria-label`）。

WAI-ARIA 的第一法则常被总结为"能用原生 HTML 就别用 ARIA"——因为原生元素自带正确语义且经过充分测试，而错误的 ARIA 比没有 ARIA 更糟（会给 AT 传递假信息）。ARIA 只改变 AT 感知到的语义，不改变元素的视觉外观和键盘行为，所以给 div 加了 `role="button"` 还必须自己补上键盘可聚焦和回车/空格激活，否则只是"看起来是按钮、用起来不是"。WAI-ARIA 当前稳定版本为 1.2（W3C Recommendation），后续版本在推进中（⚙演进快·锚版本·随时变，1.3 具体状态待核，核实 2026-08-01）。

### 6.6.3 可访问性 vs 可用性 vs 用户体验 vs 包容性（分账）

可访问性（accessibility）关注产品能否被尽可能广泛的人群、尤其是残障人士使用；可用性（usability）关注特定用户在特定情境下达成目标的有效性、效率与满意度；用户体验（UX）是更宽的伞，涵盖使用前中后的全部主观感受；包容性设计（inclusive design）则是一种把多样人群需求纳入设计过程的方法取向。四者高度交叠但侧重不同。

一个常见混淆是把"无障碍"等同于"给残障人士的特殊照顾"。更准确的框架是：可访问性是可用性面向多样能力人群的延伸——一个满足 WCAG 却让所有人都难用的界面并不算成功。反过来，很多无障碍改进（清晰对比、键盘操作、明确错误提示）对所有人都有益，这正是"路缘坡道效应"（curb-cut effect）：为轮椅设计的坡道，推婴儿车、拉行李箱的人同样受益。在本知识库的划分中，可用性的可测量定义与三维度量另有专章，此处只点明边界。

### 6.6.4 通用设计的七项原则（Universal Design）

通用设计（Universal Design）由建筑学者 Ronald Mace 与北卡州立大学团队提出，目标是让产品与环境"尽可能被所有人使用，无需额外适配或专门设计"。其七项原则为：公平使用（Equitable Use）、灵活使用（Flexibility in Use）、简单直观（Simple and Intuitive Use）、可感知信息（Perceptible Information）、容错（Tolerance for Error）、低体力消耗（Low Physical Effort）、适当的尺寸与操作空间（Size and Space for Approach and Use）。

通用设计源于物理与建筑环境，其精神是"一个方案适配所有人"（one-size-fits-all）。它与 WCAG 的关系是理念与落地：WCAG 可看作把"可感知信息""容错"等通用设计精神在 Web 上具体化、可测试化。初学者不必背下七条，重点是抓住其取向——把多样能力当作设计的默认前提，而非事后打补丁。

### 6.6.5 包容性设计（Inclusive Design）

包容性设计是一种设计方法取向，强调认识到排斥、从多样性中学习、并"为一人解决、惠及多人"（solve for one, extend to many）。微软的包容性设计框架把它概括为三条：识别排斥（Recognize exclusion）、从多样性中学习（Learn from diversity）、为一人解决而惠及多人（Solve for one, extend to many），Kat Holmes 是这一框架的代表推动者之一。

包容性设计常被与通用设计对照：如果说通用设计追求"一个方案适配所有人"（one-size-fits-all），包容性设计更强调"为个体量体裁衣、再向外扩展"（one-size-fits-one），承认人的需求各不相同，靠灵活性而非单一万能方案来覆盖。一个贯穿其中的观念是"情境性障碍"（situational / temporary impairment）：抱着孩子只能单手操作、强光下看不清屏幕、断臂康复期不能用鼠标——每个人都会在某些时刻处于"受限"状态，为永久残障做的设计因此惠及所有人。这与前述路缘坡道效应是同一枚硬币的两面。此处只做设计取向侧的技术性介绍；无障碍作为社会公平与正当性诉求的层面属社会伦理主题，本报告按分账不重复深挖。

### 6.6.6 从 POUR 到设计流程：无障碍如何融入实践

无障碍最有效的落地方式是"从一开始就做"（shift left / born accessible），而不是上线前再补救。把 POUR 拆成设计与开发各环节的检查点——设计阶段就选够对比度的配色、给交互定义键盘行为；开发阶段用语义化 HTML、必要时补 ARIA；测试阶段用自动化工具加屏幕阅读器手动验证——比事后返工成本低得多。

这条与设计流程、评估方法的关系是：无障碍既是一套可评估的准则（可纳入启发式评估与走查），也是一种应贯穿以用户为中心设计全程的约束。自动化检测工具能覆盖的往往只是一部分可机检的准则（如对比度、缺失替代文本），大量准则（如替代文本是否贴切、键盘操作是否合理、认知负担是否过重）仍需人工判断与真实残障用户参与测试。把 AT 用户纳入可用性测试，是验证无障碍是否真正达成、而非仅仅"技术上合规"的关键一步。
