## 03-1.1 关系结构：关系、元组、属性、域，schema vs instance，集合语义

### 03-1.1.1 域、属性、元组、关系：一张表的四个基本零件

关系模型用四个层层嵌套的概念描述一张表。**域（domain）** 是某一列允许取的值的集合，例如「学号的域 = 所有合法学号字符串」「年龄的域 = 非负整数」。**属性（attribute）** 是表中的一列，每个属性关联一个域。**元组（tuple）** 是表中的一行，形式上是各属性各取一个值凑成的一条记录。**关系（relation）** 就是整张表，即若干元组构成的一个集合。Codd 在 1970 年给出的形式定义是：设有域 D₁, D₂, …, Dₙ，一个 n 元关系 r 是这些域的笛卡尔积的一个子集，写作

r ⊆ D₁ × D₂ × … × Dₙ

也就是说，关系里的每个元组 t = (v₁, v₂, …, vₙ) 满足每个分量 vᵢ 都取自对应的域 Dᵢ。DBSC 7e 与 CMU 15-445 L1 用的是同一套定义，只是 DBSC 更强调「关系 = 元组的集合」这一集合论视角。

初学者可以这样对上号：想象一张「学生表」，它有三列 学号 / 姓名 / 年龄——这三列就是三个**属性**；「学号只能是那批合法编号、年龄只能是非负整数」这些各列的取值范围就是各自的**域**；表里「(202301, '张三', 19)」这一整行是一个**元组**；整张学生表（所有行的集合）就是一个**关系**。这里有两个易混点。其一，「域」是「所有可能值」的集合，不是「当前表里出现过的值」的集合——年龄域是全体非负整数，哪怕表里只出现过 18、19、20。其二，日常说的「表」「记录」「字段」，在理论里分别对应「关系」「元组」「属性（的取值）」，读教材时要能在两套词汇间自由切换。

### 03-1.1.2 关系模式（schema）vs 关系实例（instance）：类型与值的区别

**关系模式（relation schema）** 是关系的「结构定义」，即关系名加上它的属性列表（及各属性的域），记作

R = (A₁, A₂, …, Aₙ)

例如 `student = (ID, name, dept_name, tot_cred)`。**关系实例（relation instance）** 则是在某一具体时刻，这个模式下实际存放的那一组元组，通常用小写 r（或 r(R)）表示模式 R 的一个实例。DBSC 7e §2.1 明确区分：模式描述结构、很少变化；实例是数据、随增删改不断变化。一个额外术语，关系的**度数（degree / arity）** 是属性个数 n，**基数（cardinality）** 是元组个数。

打个编程里的比方，关系模式相当于「类的定义」或「结构体的类型声明」，关系实例相当于「这个类当前存活的那一批对象」。类型是稳定的蓝图，值是随时间变化的内容。初学者常把二者混为一谈，导致分不清「改表结构（`ALTER TABLE`，动模式）」和「改表数据（`INSERT/UPDATE`，动实例）」是两码事——前者罕见且往往要停机或加锁，后者是日常操作。还要注意一个命名细节：整个数据库的所有关系模式合起来叫**数据库模式（database schema）**，而某时刻所有关系实例合起来叫**数据库实例**或**数据库状态**。

### 03-1.1.3 关系的集合语义：无重复元组、行无序、列（按名）无序

关系在理论上是一个**集合**，这带来三条硬性性质。第一，**没有重复元组**——集合里元素两两不同，所以理想的关系不会有两行完全一样。第二，**元组之间无序**——集合没有「第几个元素」的概念，所以关系的行没有先后，`ORDER BY` 是显示层的事，不改变关系本身。第三，在关系模型的「具名视角」下，**属性靠名字而非位置来引用**，列的排列顺序也不携带信息（Codd 的原始形式定义用有序笛卡尔积，属性有位置；但现代教材与 SQL 都采用「按名引用」的具名视角，两种视角在表达力上等价）。

理解「集合语义」的关键是问「为什么要去重、无序」。因为关系模型想让数据的**含义完全由值决定**：两条内容一模一样的记录在逻辑上就是同一个事实，重复它没有新增任何信息，反而会让「这个事实成立吗」变成「它出现了几次」的糊涂账；同理，「谁排在前面」若能携带信息，就等于偷偷引入了一个没在属性里声明的隐藏列，破坏了模型的干净。一个常见误解是「既然是集合，那 SQL 表里也不会有重复行」——恰恰相反，这正是理论与实现最著名的分歧，见下一项。

### 03-1.1.4 规范 vs 实现：理论是集合（set）、SQL 默认是多集（bag）

这是本大主题最需要「两边都记、不和稀泥」的分歧点。**规范侧**：关系代数与关系模型把关系当纯集合，自动去重。**实现侧**：SQL 标准（ISO/IEC 9075）与主流实现（SQLite、PostgreSQL）默认采用**多集/包（bag/multiset）语义**——`SELECT` 结果、以及基础的投影都**保留重复行**，只有显式写 `DISTINCT`、或用 `UNION`（不带 `ALL`）这类集合运算时才去重。设计上这样选是为了性能（去重要排序或建哈希，代价高）和信息保留（`SELECT salary` 后想数「有几个人拿这个薪水」就需要重复）。

本机 SQLite 3.45 实证（`sqlite3` 内存库，基线 Py3.11.15 @2026-07-29）印证了这条分歧。建表 `R(a,b)` 插入 `(1,10),(2,20),(2,20),(3,30)`（注意 `(2,20)` 故意重复）：

SELECT b FROM R;          -- 多集：(10),(20),(20),(30)  重复保留

SELECT DISTINCT b FROM R; -- 集合：(10),(20),(30)      去重

SELECT a FROM R UNION ALL SELECT a FROM S;  -- 多集：拼接不去重

SELECT a FROM R UNION     SELECT a FROM S;  -- 集合：去重

真实输出与上面注释完全一致：不带 `DISTINCT`/不带 `ALL` 时留重复，带了才去重。给初学者的落点是——**纸上做关系代数题请按集合去重，但一坐到真实数据库前，默认它是多集**，要不要去重由你用 `DISTINCT`/`UNION` 显式控制。忘记这条，就会写出「本以为唯一、结果一堆重复行」的查询。

## 03-1.2 键：超键、候选键、主键、外键与参照完整性

### 03-1.2.1 超键（superkey）：能唯一确定一行的属性组合

**超键** 是关系模式属性的一个子集，使得在任何合法实例里，没有两个不同元组在这个子集上取值全相同——换句话说，知道了这组属性的值，就能唯一锁定一行。形式化地，属性集 K 是 R 的超键，当且仅当对任意实例 r 中的任意两元组 t₁ ≠ t₂，都有

t₁[K] ≠ t₂[K]

DBSC 7e §2.3 与 CMU 15-445 L1 定义一致。例如学生表里，`{ID}` 是超键，`{ID, name}` 也是超键（加了多余属性照样能区分）。

直觉是「超键 = 足够（甚至过度）用来当身份证的那组列」。「超」字提示它可以含冗余属性——只要包含了某个真正能区分的核心，再多塞几列还是超键。初学者要抓住两点：其一，超键是对「模式」层面的约束，要求「对所有可能的合法实例都成立」，不能因为「当前表里恰好没重复」就断言某列是超键（那可能只是数据凑巧）。其二，判断是否超键，看的是「有没有可能出现两行在这些列上撞车」——姓名通常不是超键，因为现实里允许重名。

### 03-1.2.2 候选键（candidate key）：最小的超键

**候选键** 是「极小超键」——它本身是超键，但去掉其中任何一个属性后就不再是超键（不含任何冗余）。一个关系可以有多个候选键。例如一张 `员工(工号, 身份证号, 姓名, 部门)` 表里，`{工号}` 和 `{身份证号}` 都能唯一确定一个人，它们都是候选键；而 `{工号, 姓名}` 只是超键、不是候选键，因为去掉「姓名」后 `{工号}` 仍是超键，说明「姓名」是多余的。

「极小」这个词初学者容易误读成「属性个数最少的那个」——不是。极小性是针对**单个键内部**说的：这个键里挑不出可删的冗余属性；它不比较不同候选键谁更短。所以两个候选键完全可以一个是单列、一个是三列，只要各自都无冗余，都算候选键。候选键是后面「主键」和第 03-4 大主题「范式」的地基：范式判定里反复出现的「某属性是否属于某候选键」，指的就是这里的候选键。

### 03-1.2.3 主键（primary key）：被选中当默认标识的那个候选键

**主键** 是数据库设计者从若干候选键中**挑选出来**、用作元组默认标识的那一个。它在语义上和候选键一样能唯一确定行，区别只在「被选中、被扶正」这个人为决定。习惯上主键属性在关系模式里加下划线标注，如 `student(ID, name, dept_name)` 中给 ID 加下划线。SQL 里用 `PRIMARY KEY` 声明，它自动带来两条约束：唯一（不重复）且**非空（NOT NULL）**。

理解主键要抓住「候选键是客观事实、主键是主观选择」。一张表客观上可能有多个候选键（工号、身份证号都能当身份证），但设计者要指定一个当「官方 ID」——通常挑稳定、简短、不易变的那个（工号往往比身份证号更适合当主键）。没被选中的候选键在 SQL 里通常用 `UNIQUE` 约束继续保证其唯一性，但它们不叫主键。易错点：主键强制非空，而普通 `UNIQUE` 约束在多数实现里允许一个（或多个，各实现不同）NULL——这是主键与「唯一约束」的一个实务差别（NULL 细节归 03-2.5）。

### 03-1.2.4 外键（foreign key）与参照完整性约束：跨表的引用不能悬空

**外键** 是一个关系（引用方 / referencing）里的一组属性，它的取值被要求必须出现在另一个关系（被引用方 / referenced）的候选键（通常是主键）中。**参照完整性约束（referential integrity）** 就是这条要求：外键的每个值要么在被引用关系里找得到对应的主键值，要么整个为空（NULL，若允许）。形式上，设 R 的外键属性集 α 参照 S 的主键，则约束要求

πα(r) ⊆ π_{主键}(s)

即引用方外键列的取值集合，被包含在被引用方主键列的取值集合里。DBSC 7e §2.3 与 CMU 15-445 L1 定义一致。

直觉是「不许指向一个不存在的东西」。比如 `takes(学号, 课程号)` 里的「学号」是外键，参照 `student` 表的主键——它保证选课记录里的每个学号都真有这么个学生，不会出现「一条选课记录挂在一个查无此人的学号上」的悬空引用。这解释了为什么增删改会被数据库拦下：想删掉一个还被选课记录引用着的学生，数据库会报参照完整性冲突（除非配置了级联删除等策略）；想插入一条引用不存在学号的选课记录，也会被拒。初学者两个常见困惑：其一，外键指向的必须是被引用表的**候选键/主键**，不能随便指向普通列；其二，外键约束是**有方向**的（`takes` 引用 `student`，不是反过来），删除、更新时受限的是「被引用的一方」和「悬空的一方」，搞反方向就会误判该拦谁。

## 03-1.3 关系代数基本运算：σ、π、∪、−、×、ρ

### 03-1.3.1 关系代数总览：封闭的「表进表出」算子系统

**关系代数（relational algebra）** 是一套作用在关系上的运算，每个运算取一个或两个关系为输入、产出一个新关系为输出。因为输入输出都是关系，运算可以任意嵌套组合，这个性质叫**封闭性（closure）**，是关系代数能当「查询语言」的根本。DBSC 7e §2.6 把运算分成**基本（fundamental）运算**和可由基本运算导出的扩展运算；基本运算共六个：选择 σ、投影 π、并 ∪、集合差 −、笛卡尔积 ×、改名 ρ。

关系代数是**过程式（procedural）** 的——它描述「先做什么再做什么」这条计算路径，和后面 03-1.5 的关系演算（声明式，只说「要满足什么」）形成对照。给初学者的定位：关系代数既是理解 SQL 语义的「底层字节码」（SQL 查询大体可翻译成一串代数算子），也是查询优化器做等价变换的操作对象（03-8 会重写这些代数表达式）。这里先记住六个基本算子，扩展算子（连接、交、除等）在 03-1.4 都能用这六个拼出来。以下算子的形式定义与记号以 DBSC 7e §2.6 为准，CMU 15-445 L1 记号一致。

### 03-1.3.2 选择 σ（selection）：按条件挑行

**选择运算 σ** 从一个关系里挑出满足给定谓词的那些元组（挑行），记作

σ_P(r) = { t | t ∈ r 且 P(t) 为真 }

其中 P 是选择谓词，可含比较（=、≠、<、≤、>、≥）与逻辑连接（∧ 与、∨ 或、¬ 非）。例如从教师表挑出物理系的：

σ_{dept_name = "Physics"}(instructor)

直觉就是 SQL 的 `WHERE` 子句。要点有二。其一，σ **只减少行、不改变列**——输出关系和输入有完全相同的属性（模式不变）。其二，谓词里比较的可以是「属性与常量」（`salary > 90000`）或「属性与属性」（`A = B`）。初学者易错点：别把 σ（挑行，selection）和 π（挑列，projection）记混——中文里「选择」听起来像挑列，但 σ 挑的是**行**。

### 03-1.3.3 投影 π（projection）：按属性挑列并（理论上）去重

**投影运算 π** 从关系里保留指定的若干属性、丢掉其余属性（挑列），记作

π_{A₁, A₂, …, Aₖ}(r)

例如只要教师的姓名和薪水：

π_{name, salary}(instructor)

投影是「竖着切」——只减少列、行数可能因去重而减少。因为结果仍是**集合**，投影掉某些列后若出现重复元组，理论上会**自动去重**。这正是理论与 SQL 的又一处分歧：SQL 的 `SELECT 列名`（不带 `DISTINCT`）保留重复（多集语义，见 03-1.1.4），要模拟关系代数的投影需写 `SELECT DISTINCT`。初学者记：**纸上的 π 会去重，SQL 的投影默认不去重**。此外还有一种**广义投影**允许在投影时做算术（如 `salary/12`），归 03-1.4.6。

### 03-1.3.4 并 ∪ 与集合差 −（union / set difference）：要求两表「同型」

**并运算 ∪** 把两个关系的元组合到一起（并按集合去重），**集合差 −** 从第一个关系里去掉那些也出现在第二个关系里的元组：

r ∪ s = { t | t ∈ r 或 t ∈ s }

r − s = { t | t ∈ r 且 t ∉ s }

这两个运算（以及导出的交 ∩）要求两个输入关系**相容（union-compatible / 同型）**：属性个数相同，且对应属性的域相同。例如「所有授过课的教师 ID」并上「所有选过课的学生 ID」——只有当两边都是「单个 ID 列且域相同」时才合法。

直觉是中学集合的并与差，只不过元素换成了「整条元组」。关键约束是「同型」：你不能把「(姓名)」和「(姓名, 年龄)」求并，因为一个是一元、一个是二元，元组结构对不上。初学者易错点：集合差**无交换律**，r − s 与 s − r 一般不等（前者是「在 r 不在 s」，后者反过来）。对应到 SQL 分别是 `UNION`（去重）/`UNION ALL`（保留重复）与 `EXCEPT`（标准）；本机 SQLite 实证中 `EXCEPT` 按集合语义去重、`UNION ALL` 保留重复，与理论/多集分歧一致（见 03-1.1.4 输出）。

### 03-1.3.5 笛卡尔积 ×（Cartesian product）：两表逐行两两配对

**笛卡尔积 ×** 把两个关系的每一个元组两两拼接，产出所有可能的组合：

r × s = { t q | t ∈ r 且 q ∈ s }

其中 t q 表示把元组 t 和 q 首尾相接。结果关系的属性是两边属性的合并，元组数是两边元组数之积，即

|r × s| = |r| × |s|

例如 `instructor × teaches`，若 instructor 有 12 行、teaches 有 20 行，积就有 240 行。

直觉是「把两张表所有行的组合全列出来」。它本身很少单独用（组合往往无意义，且规模爆炸），但它是**连接（join）的原料**：θ 连接、自然连接都定义成「先做笛卡尔积、再用 σ 挑出有意义的组合」（见 03-1.4）。本机 SQLite 实证 `SELECT COUNT(*) FROM R,S`（R 4 行、S 3 行）返回 12，正是 4×3，印证 |r×s|=|r||s|。初学者两个坑：其一，若两表有同名属性，积之后要靠「关系名.属性名」限定来消歧（这也是 ρ 改名存在的一个理由）；其二，笛卡尔积规模是乘积、极易爆炸——写 SQL 时 `FROM A, B` 忘了写连接条件，就会不慎产生全笛卡尔积（俗称「笛卡尔积炸弹」）。

### 03-1.3.6 改名 ρ（rename）：给关系或属性换名字

**改名运算 ρ** 给关系（或其属性）重新命名，好处是能在表达式里引用中间结果、消除同名冲突、以及做「自连接」。记法有几种，给整个关系改名：

ρ_x(E)

把表达式 E 的结果命名为 x；也可同时给属性改名：

ρ_{x(A₁, A₂, …, Aₙ)}(E)

改名唯一的作用是「换标签」，不改任何数据。它为什么必要？最典型的是**自连接**：要在同一张 `instructor` 表里找「和某人同系的其他人」，得把这张表当成两份来用，否则「工资 > 另一个人工资」里的「另一个人」无从指代。这时用 ρ 把表复制成两个不同名字（如 i 和 j），才能写出 `i.dept = j.dept ∧ i.ID ≠ j.ID` 这样的条件。对应 SQL 就是 `FROM instructor AS i, instructor AS j` 里的别名。初学者只要记住：ρ 是「起别名」，纯粹解决「指代」问题，不产生新数据。

## 03-1.4 扩展运算：连接（自然/θ/外）、交、除、赋值、广义投影

### 03-1.4.1 交 ∩（intersection）：可由差导出的「共同元组」

**交运算 ∩** 取两个（同型）关系里都出现的元组：

r ∩ s = { t | t ∈ r 且 t ∈ s }

它不是基本运算，因为可以用两次集合差拼出来：

r ∩ s = r − (r − s)

直觉是集合的交，和 ∪、− 一样要求两表相容（同型）。之所以把它归为「扩展」而非「基本」，是因为关系代数追求一个**极小的基本算子集**——凡能用现有算子拼出来的，就不列为基本。初学者不必纠结「为什么交明明这么常用却不算基本」：常用与否和「是否原语」是两回事，交是为了方便而定义的语法糖。对应 SQL 是 `INTERSECT`。

### 03-1.4.2 自然连接 ⋈（natural join）：按同名属性自动配对并合并

**自然连接 ⋈** 是最常用的连接：它对两个关系做笛卡尔积，只保留在**所有同名属性上取值都相等**的组合，并把重复的同名列合并成一份。设 r、s 的公共属性集为 R∩S，则

r ⋈ s = π_{R∪S}( σ_{r.A₁=s.A₁ ∧ … ∧ r.Aₖ=s.Aₖ}(r × s) )

其中 A₁…Aₖ 是全部公共属性。例如 `instructor ⋈ teaches`，会按两表共有的 `ID` 列自动匹配，把「教师信息」和「他教的课」拼到一行。

直觉是「按公共列对齐、把相关的两行缝成一行」，这几乎就是日常查询里「把两张表关联起来」的默认动作。三个要点。其一，「按哪些列连接」是**自动**由同名属性决定的——这是「自然」二字的由来，也是它的坑：如果两表恰好有个语义无关但同名的列（比如都叫 `note`），自然连接会把它也当连接条件，产生错误结果，所以工程上更常用显式指定条件的连接。其二，合并后同名列**只留一份**（这是它区别于 θ 连接的地方）。其三，自然连接满足交换律和结合律，多表自然连接可以按任意顺序做（这正是 03-8 连接顺序优化的理论基础）。本机 SQLite 实证 `R JOIN S ON R.a=S.a`（R 有两条 a=2 的行）返回 a=2 的两条配对 + a=3 一条，印证「匹配上的两两配对」。

### 03-1.4.3 θ 连接与等值连接（theta join / equi-join）：连接条件可自定义

**θ 连接 ⋈_θ** 是带任意谓词 θ 的连接，定义为「笛卡尔积后用 θ 做选择」：

r ⋈_θ s = σ_θ(r × s)

θ 可以是任意比较谓词（`<`、`>`、`≠` 等）。当 θ 只由等值比较（`=`）组成时，特称为**等值连接（equi-join）**。θ 连接与自然连接的关键区别：θ 连接**不自动合并同名列、也不要求按同名列连**，连接条件完全由你写的 θ 决定。

直觉是「自定义配对规则的连接」。什么时候需要它而非自然连接？当连接条件不是「相等」时——比如「找出工资高于其经理的员工」，条件是 `员工.工资 > 经理.工资`，这是不等号，自然连接做不到，θ 连接可以。等值连接与自然连接很像但有别：等值连接保留两个相等的列（各留一份、共两列），自然连接把它们合并成一列。对应 SQL 就是 `JOIN ... ON <任意条件>`：`ON a=b` 是等值连接，`ON a>b` 是一般 θ 连接。初学者记住优先级链：自然连接（同名等值、合并列）⊂ 等值连接（指定等值、不合并）⊂ θ 连接（任意谓词）。

### 03-1.4.4 外连接（outer join）：保留「没配上对」的行，缺的补 NULL

**外连接** 是连接的扩展，用来**保留在另一张表里找不到匹配的元组**，并给缺失的属性填 NULL。有三种：**左外连接 ⟕** 保留左表全部行、**右外连接 ⟖** 保留右表全部行、**全外连接 ⟗** 两边都保留。以左外连接为例，它 = 内连接的结果，再并上左表中「没配上任何右表行」的那些行（右表属性补 NULL）。

r ⟕ s

直觉：内连接（自然/θ 连接）会**丢掉配不上对的行**——一个从没教过课的教师，在 `instructor ⋈ teaches` 里会消失。但很多查询恰恰要「列出所有教师，包括没课的」，这时用左外连接保住他，课程列填 NULL 表示「无」。三种外连接的记忆法：「左/右/全」指**哪一侧的孤儿行被保留**。这里绕不开 NULL 的三值逻辑（NULL 参与比较得 unknown），细节归 03-2.5；本篇只需建立「外连接靠 NULL 占位来保留无匹配行」的图景。对应 SQL 是 `LEFT/RIGHT/FULL OUTER JOIN`（注意 SQLite 早期只支持 `LEFT JOIN`，`RIGHT/FULL` 在 3.39+ 才加入——实现差异，标为交叉参考）。

### 03-1.4.5 除 ÷（division）：表达「对所有……都成立」的查询

**除运算 ÷** 用来回答「找出与某集合中**每一个**元素都有关联的实体」这类「for all」查询。设关系 r 的属性为 R、s 的属性为 S 且 S ⊆ R，令差集属性 R−S 记为 R\S，则 r ÷ s 定义为：R\S 上的那些元组 t，使得 s 中**每一个**元组与 t 拼起来都能在 r 中找到。等价刻画为

t ∈ (r ÷ s) ⟺ 对所有 u ∈ s，都有 (t 拼 u) ∈ r

经典例子：`r = 选课(学号, 课程号)`，`s = 必修课(课程号)`，则 `r ÷ s` = 「选了**全部**必修课的学生学号」。

直觉是「除法是笛卡尔积的逆」——正如整数里 `(a×b)÷b = a`，关系里 (T × s) ÷ s = T。它专门对付自然语言里的「所有、每一个」：找选了所有必修课的学生、找供应了所有零件的供应商。除法是唯一直接对应「全称量词 ∀」的代数算子，这也是它能用其它算子（π、×、−）间接拼出来、但拼法繁琐的原因。初学者不必背它的组合展开式，只要能识别「题目里出现『所有/每一个』时，往除法上想」。注意 SQL **没有**直接的除法运算符，实现时通常靠「双重否定（NOT EXISTS ... NOT EXISTS ...）」或「计数比较（`GROUP BY` 后 `HAVING COUNT = 必修课总数`）」间接表达，归 03-2.4。

### 03-1.4.6 赋值 ← 与广义投影（assignment / generalized projection）

**赋值运算 ←** 把一个关系代数表达式的结果**存进一个临时关系变量**，好把复杂查询拆成几步写：

temp ← σ_{dept_name="Physics"}(instructor)

result ← π_{name}(temp)

它纯粹是「起中间变量」的便利，不增加表达能力（等价于把 temp 处处内联展开），对应 SQL 的 `WITH`（CTE，归 03-2.4）或临时表。

**广义投影（generalized projection）** 扩展了普通投影 π：允许在投影列表里写**算术/函数表达式**，而不只是属性名，记作

π_{F₁, F₂, …, Fₙ}(E)

其中每个 Fᵢ 可以是涉及属性与常量的表达式。例如把年薪换算成月薪输出：

π_{ID, name, salary/12}(instructor)

直觉是「投影时顺手做点计算」，对应 SQL `SELECT` 列表里写 `salary/12 AS monthly`。初学者把这两个算子理解为「工程便利」即可：赋值让长查询可读（分步），广义投影让输出列能派生新值——它们都不改变关系代数的根本表达能力。（另一个常并入扩展运算讲的是**聚合** γ / 𝒢，做 count/sum/avg 等分组统计；DBSC 在 ch2 一并介绍，但它严格说超出「纯关系代数」，本篇点到为止，聚合的 SQL 用法归 03-2.3。）

## 03-1.5 表达能力等价：关系代数 ↔ 关系演算（安全性）

### 03-1.5.1 元组关系演算 TRC：声明式地「描述想要的元组」

**元组关系演算（tuple relational calculus, TRC）** 是一种**声明式（非过程式）** 查询语言：你不写「怎么算」，只写「结果元组要满足什么条件」。一个 TRC 查询形如

{ t | P(t) }

读作「所有使谓词 P(t) 为真的元组 t 构成的集合」。P 是一阶逻辑公式，可用比较、逻辑连接（∧、∨、¬）和量词（∃ 存在、∀ 任意），还能用 `t ∈ r` 表示「t 属于关系 r」、`t[A]` 表示 t 在属性 A 上的值。例如「工资高于 80000 的教师姓名」：

{ t | ∃ s ∈ instructor (s[salary] > 80000 ∧ t[name] = s[name]) }

直觉对比：关系代数像「菜谱」（先选后投影再连接，一步步操作），关系演算像「点菜」（只说「我要一份满足这些条件的结果」，怎么做交给系统）。SQL 在风格上更接近关系演算——`SELECT name FROM instructor WHERE salary > 80000` 就是在「描述条件」而非「指定算子顺序」。这解释了为什么说关系代数是 SQL 的执行层、关系演算是 SQL 的思维层。初学者只需抓住「代数=过程式、演算=声明式」这条对照。

### 03-1.5.2 域关系演算 DRC：把变量绑到「值」而不是「整行」

**域关系演算（domain relational calculus, DRC）** 与 TRC 表达力相同，区别在变量的粒度：TRC 的变量代表**整个元组**，DRC 的变量代表**单个属性值（域上的值）**。DRC 查询形如

{ <x₁, x₂, …, xₙ> | P(x₁, x₂, …, xₙ) }

尖括号里是一串域变量，每个绑到结果的一个属性位置。同样的「工资 > 80000 的教师姓名」在 DRC 里写成：

{ <n> | ∃ i, s, d ( <i, n, d, s> ∈ instructor ∧ s > 80000 ) }

DRC 在历史上是查询语言 QBE（Query-by-Example）的理论基础。给初学者的落点：TRC 和 DRC 是「同一个声明式思想的两种记法」——一个以行为单位、一个以值为单位，能表达的查询集合完全一样，学会其一即可，另一记法照猫画虎。

### 03-1.5.3 安全性（safety）：为什么演算表达式必须「结果有限」

关系演算有一个代数没有的隐患：能写出**结果为无穷、或依赖于「域里全部可能值」** 的表达式。例如 `{ t | ¬(t ∈ r) }`「所有不在 r 里的元组」——如果域是无限的（如全体整数字符串），这个结果就是无穷集合，无法计算和存储。为排除这类病态查询，引入**安全性（safety）** 限制：一个演算表达式是**安全的**，当且仅当它的结果只包含出现在「表达式所涉及关系里实际出现过的值（active domain，活动域）」之上的元组，从而保证结果**有限**。

直觉是「答案里的每个值，都必须能在数据库里真实找到出处，不能凭空从无限的域里蹦出来」。为什么要专门管这件事？因为声明式的自由带来了「说得出、算不出」的风险——`¬` 和 `∀` 很容易不小心引用整个无限论域。安全性就是给演算套的一道「结果必须落在活动域内」的护栏。初学者不用死抠安全性的形式定义，记住结论即可：**只有安全的演算表达式才对应得上关系代数**；不安全的（如上面的无穷补集）被排除在外。这也是为什么 SQL 里没有「取一个表的绝对补集」这种操作——它天然不安全。

### 03-1.5.4 Codd 定理：三者表达能力等价（关系完备）

**Codd 定理** 断言：**关系代数、（安全的）元组关系演算、（安全的）域关系演算三者表达能力完全相同**——任何一种能表达的查询，另两种也能表达，且存在互相转换的算法。一种查询语言若其表达能力至少等于关系代数（等价地，等于安全的关系演算），就称为**关系完备（relationally complete）** 的。

这条等价是关系模型的理论压舱石，意义有三。其一，它给了「关系查询到底能表达什么」一个精确的边界——三种形式互为标尺。其二，它让「声明式」与「过程式」两个世界可以自由翻译：你用接近人类思维的演算/SQL 描述需求，系统能机械地转成可执行的代数算子序列，这正是查询处理器（03-7）和优化器（03-8）工作的合法性来源。其三，它定义了衡量查询语言的标准——SQL 的核心（SELECT-FROM-WHERE 那部分）是关系完备的，因而「不比关系代数弱」。初学者要建立的最终图景：**关系代数（怎么算）↔ 关系演算/SQL（要什么），经安全性约束后表达力相等，这就是关系模型「既能严格推理、又能高效执行」的根本保证。** 需要点明的边界：这条等价说的是**基础关系代数**的表达力；SQL 实际还包含聚合、分组、排序、递归 CTE 等，这些**超出**了经典关系代数/演算的表达范围（例如「传递闭包」用基础关系代数表达不了，需递归），不在 Codd 定理的等价范围内。
