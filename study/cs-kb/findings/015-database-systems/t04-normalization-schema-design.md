## 03-4.1 函数依赖：FD 定义、Armstrong 公理、属性闭包、候选键推导

### 03-4.1.1 函数依赖（functional dependency, FD）的定义

函数依赖是关系模式上的一种约束，写作 α → β（读作「α 函数决定 β」），其中 α、β 都是属性集合。它的含义是：在该模式的**任何**合法实例里，只要两个元组在 α 上取值相同，它们在 β 上取值也必然相同。形式化地，对关系 r 的任意两元组 t₁、t₂：

若 t₁[α] = t₂[α]，则 t₁[β] = t₂[β]

DBSC 7e §7.4.1 与 R&G §19.3 给的是同一条定义。它是「键」概念的推广——一个属性集 K 是超键，当且仅当 K → R（K 函数决定全部属性）成立。

给初学者的直觉是把 α → β 读成「查表函数」：以 α 的值为输入，β 的值就被唯一确定，像 `f(α)=β` 一样。例如学生表里 `ID → name`（一个学号只对应一个姓名），系表里 `dept_name → building`（一个系只在一栋楼）。三个易错点要先钉住。其一，FD 是对「所有合法实例」的断言，**不能靠看一张当前表碰巧没冲突就断定 FD 成立**——当前数据不违反只是必要条件，FD 是不是真规则要由业务语义（或设计者）决定。其二，方向有意义，`ID → name` 成立不代表 `name → ID` 成立（同名的人可以有不同学号）。其三，FD 谈的是「值定值」的确定性，与这一列具体存了什么无关。

### 03-4.1.2 平凡函数依赖与 FD 集合 F 的作用

如果 β ⊆ α，那么 α → β 一定成立（因为两元组在 α 上相同，自然在 α 的子集上也相同），这样的 FD 叫**平凡函数依赖（trivial FD）**，例如：

{A, B} → A

它不携带任何约束信息，永远为真。反之 β 不是 α 的子集时叫**非平凡 FD**；β 与 α 完全无交时叫**完全非平凡**。设计时我们只关心非平凡 FD。一个模式上设计者声明的那组 FD 记作 F，它把「哪些是同一个事实」这件事讲清楚，后面所有范式判定、分解算法都以 F 为输入。

初学者容易忽略平凡 FD 的意义——它看似废话，但在写范式定义时是重要的「豁免项」：范式定义里几乎都有一句「或者该 FD 是平凡的」，就是为了把这类恒真依赖排除在「违反范式」之外，否则任何表都通不过。可以把 F 理解成这张表的「业务规则说明书」，规则写得对不对直接决定后面拆表拆得对不对，这也是为什么 FD 要从需求/E-R 设计而非从样例数据里得来。

### 03-4.1.3 Armstrong 公理与 FD 闭包 F⁺

给定 F，有些 FD 虽没直接写出来但被 F **逻辑蕴含**（在满足 F 的每个实例里都成立）。所有被 F 蕴含的 FD 的集合叫 F 的闭包，记作 F⁺。求 F⁺ 靠 **Armstrong 公理**这三条推理规则，它对函数依赖是**可靠的（soundness，推出来的都对）且完备的（completeness，对的都推得出）**：

自反律（reflexivity）：若 β ⊆ α，则 α → β

增广律（augmentation）：若 α → β，则 γα → γβ

传递律（transitivity）：若 α → β 且 β → γ，则 α → γ

由这三条可导出三条常用的派生规则，用起来更顺手：

合并律（union）：若 α → β 且 α → γ，则 α → βγ

分解律（decomposition）：若 α → βγ，则 α → β 且 α → γ

伪传递律（pseudotransitivity）：若 α → β 且 γβ → δ，则 γα → δ

DBSC 7e §7.4.2 与 R&G §19.3.2 对三条公理与三条派生规则的表述一致，Armstrong 1974 原论文即证明了其可靠完备。给初学者的落点：Armstrong 公理就是 FD 版的「逻辑推理规则」，作用是让你从写下的少数几条规则，机械地推出所有隐含规则。合并/分解律合起来说明一件方便事——**α → βγ 与「α → β 且 α → γ」完全等价**，所以总可以把 FD 右边拆成单属性来处理（后面求最小覆盖会用到）。易错点：分解律只能拆右边，**左边不能拆**，`AB → C` 绝不蕴含 `A → C` 或 `B → C`。直接枚举 F⁺ 会指数爆炸，所以实践中从不真去算 F⁺，而是用下面的属性闭包按需判断某条 FD 在不在 F⁺ 里。

### 03-4.1.4 属性闭包 α⁺ 及其算法

属性集 α 关于 F 的闭包 α⁺ 定义为「所有能被 α 函数决定的属性」的集合：

α⁺ = { A ｜ α → A 可由 F 用 Armstrong 公理推出 }

它是判断一切 FD 问题的主力工具，因为有等价命题：**α → β 成立（∈ F⁺）当且仅当 β ⊆ α⁺**。算法是一个不动点迭代（DBSC 7e §7.4.3、R&G §19.3.1）：初始令 result = α；反复扫描 F，只要有一条 γ → δ 满足 γ ⊆ result，就把 δ 并入 result；直到某一轮 result 不再变大为止。

初学者可以把它想成「传染」：手里先握着 α 这些属性的值，凡是「左边属性我全知道」的规则，就把它右边的属性也收进手里，收到的新属性又可能触发别的规则，滚雪球直到收不动。它的三大用途一次记牢——(1) 判断某条 FD 是否成立（看 β 在不在 α⁺）；(2) 判断 α 是不是超键（看 α⁺ 是否等于全体属性）；(3) 作为求候选键、判范式的基础零件。

本机 Python 实证（基线 Py3.11.15 @2026-07-29，纯标准库，脚本见 03-4.1.5 说明）在 R(A,B,C,D)、F = {A→B, B→C, C→D} 上求得：

Ex1 A+ = ['A', 'B', 'C', 'D']

即 A⁺ 为全体属性，印证 A→B→C→D 的传递链，也说明 A 是超键。

### 03-4.1.5 候选键的推导

候选键是「极小的超键」：K 是候选键，当且仅当 K⁺ = R（是超键）且它的任何真子集都不是超键（极小性）。推导思路借助属性闭包：先用「只出现在某些 FD 左边、从不出现在任何 FD 右边」的属性缩小搜索——这类属性**必然属于每一个候选键**（没有别的属性能决定它们，只能靠自己）；再从小到大枚举属性子集，对每个子集求闭包看是否等于 R，并剔除已含候选键的超集以保证极小。

本机 Python 实证（基线 Py3.11.15 @2026-07-29，标准库 `itertools`，闭包+穷举求全部候选键）给出两个例子的真实输出：

在 R(A,B,C,D)、F = {AB→C, C→D, D→A} 上：

Ex2 AB+ = ['A', 'B', 'C', 'D']
Ex2 candidate keys = [['A', 'B'], ['B', 'C'], ['B', 'D']]

在 R(A,B,C,D,E)、F = {A→BC, CD→E, B→D, E→A} 上：

Ex3 candidate keys = [['A'], ['E'], ['B', 'C'], ['C', 'D']]

Ex2 说明候选键可以不止一个，且 B 出现在每个候选键里——正因为 B 从不出现在任一 FD 右边，任何键都少不了它，这与上一段的「必属键」判据吻合。给初学者两个易错提醒：其一，超键和候选键不是一回事，`ABCD` 是超键但含真子集超键故不是候选键；其二，**候选键之外的属性叫非素属性、属于某个候选键的属性叫素属性（prime attribute）**，这对术语是 2NF/3NF 判定的关键，下文反复用到。（脚本仅在 scratchpad 运行取证，未入库；上述为真实输出。）

### 03-4.1.6 正则覆盖 / 最小覆盖（canonical / minimal cover）

最小覆盖 Fc 是与 F **等价**（F⁺ = Fc⁺）但「最精简」的 FD 集合，满足三条：每条 FD 右边只有单个属性（或整体无冗余）；没有**外来属性（extraneous attribute）**——即左边或右边删掉某属性后依赖集仍等价的那种多余属性；没有一条 FD 是多余的（删掉它闭包不变）。求法（DBSC 7e §7.4.4）：先用合并律把同左边的 FD 合并，再逐条检查并去掉外来属性，反复到稳定。

最小覆盖是 3NF 合成算法（03-4.4.3）的输入，「一条 FD 生成一张表」时用最小覆盖能避免造出一堆冗余小表。直觉上它就是把业务规则说明书「去水分」——删掉能从别的规则推出来的重复条款、删掉每条规则里多写的属性，但保证说明书表达的约束一字不差（等价）。易错点：最小覆盖**不唯一**，检查外来属性的顺序不同可能得到不同（但都合法）的 Fc；另外去外来属性时要用「删除后的依赖集」判断等价，一步步来，不能一次删多个。

## 03-4.2 分解目标：无损连接分解、依赖保持

### 03-4.2.1 为什么要分解：更新、插入、删除异常

一个「大而全」的表若含冗余（同一事实被存多份），会产生三类**异常（anomalies）**，这是整套范式理论要解决的病根。设想把「教师-系-楼」塞进一张表 `(instructor, dept, building)`，每个教师一行、系与楼重复填。**更新异常**：某系换楼，要改动该系所有教师所在的每一行，漏改一行就自相矛盾。**插入异常**：想登记一个还没有教师的新系，却因为没有教师行而无处安放系信息（或被迫填 NULL）。**删除异常**：删掉某系最后一位教师，该系「在哪栋楼」的信息也随之丢失。

这三种异常的共同祸根是「一张表混装了两个本应独立的事实（教师归属 + 系的楼），且把后者重复存储」。修法就是**分解（decomposition）**——把大表拆成几张小表，让每个事实只存一处。但拆表不能乱拆，得同时满足下面两个目标，否则拆坏了。可以记一句话：范式是「诊断标准」，无损连接与依赖保持是「手术必须遵守的两条安全线」。

### 03-4.2.2 无损连接分解（lossless-join decomposition）

把 R 分解成 R₁、R₂ 两个子模式，若对 R 的任何合法实例 r，把两个投影再自然连接回去能**恰好**还原 r（不多不少），就叫无损连接分解：

π_{R₁}(r) ⋈ π_{R₂}(r) = r

判定条件（对二元分解，DBSC 7e §7.5.4、R&G §19.5.1）：R₁、R₂ 的**公共属性必须是其中至少一个子模式的超键**，即下面两条 FD 至少有一条在 F⁺ 里：

(R₁ ∩ R₂) → R₁

(R₁ ∩ R₂) → R₂

初学者最需要绕清楚的是「无损」的反面——**有损（lossy）分解连接回来会多出原来没有的假元组**，信息不是变少而是「变脏、变模糊」。举个反例：把 `(name, street, city)` 拆成 `(name, city)` 和 `(street, city)`，公共属性是 `city`，而 `city` 既不能唯一决定 `name` 也不能决定 `street`，连接时同城的不同人会被张冠李戴地配上错误街道，凭空造出假行。判定口诀：**看两张小表的「粘合列」是不是其中一张的键**——是，就粘得回去且不出错。注意「无损」指的是不丢信息也不造假信息，与元组数量多少无关，别被字面「损」误导成「行变少」。

### 03-4.2.3 依赖保持（dependency preservation）

分解成 R₁,…,Rₙ 后，把原 FD 集 F **限制**到每个子模式上（Fᵢ = F⁺ 中左右属性都落在 Rᵢ 内的那些 FD），若这些局部依赖合起来仍与 F 等价，就叫保持依赖：

(F₁ ∪ F₂ ∪ … ∪ Fₙ)⁺ = F⁺

保依赖的好处是**每条原始约束都能在单张表内用一个键/唯一约束检查，不必每次更新都跨表连接来验证**，代价小得多。

把业务规则拆到各小表后，如果有一条规则「横跨」了两张表（它涉及的属性被分到了不同表里），那么每次改数据都要先把两表连起来才能查这条规则有没有被违反，既慢又易漏——依赖保持就是要避免这种「规则被拆散」。经典的不保依赖场景见 03-4.4.2 的 BCNF 反例。易错点：判断保依赖要在 **F⁺** 层面比较（用属性闭包检验合并后的依赖集能否推回每条原 FD），不能只对着最初写下的 F 逐条看是否「原样落在某表内」——有的依赖是靠几张表的局部依赖传递地蕴含出来的。

### 03-4.2.4 两个目标的关系与「好分解」的标准

一个理想的分解应当同时做到三件事：无损连接（不丢不造信息，**这条是底线，任何分解都必须满足**）、依赖保持（约束好维护）、以及消除冗余（达到目标范式）。关键的现实是**这三者不总能同时满足**——具体说，分解到 BCNF 时「无损 + 消冗余」总能达成，但「依赖保持」有时达不到；分解到 3NF 则「无损 + 依赖保持」总能达成，代价是可能留一点冗余。这正是 03-4.4.4 要展开的 BCNF/3NF 取舍。

**无损是不可谈判的（否则分解就是错的），范式高低和依赖保持之间才是要权衡的地方**。把这三条目标记牢，后面所有算法都是在这三条约束下的具体操作。

## 03-4.3 1NF / 2NF / 3NF 定义与判定

### 03-4.3.1 第一范式（1NF）：属性域必须原子

一个关系模式属于 1NF，当且仅当所有属性的域都是**原子的（atomic）**——即每个属性值不可再分、不含内部结构，也不存在「一格里塞多个值」的重复组。DBSC 7e §7.1 指出，关系模型本身默认就要求 1NF（这也是为什么它常被当作「起点」而非需要努力达到的目标）。

初学者要抓的关键是「原子」的语境依赖性。一个字段是否原子，取决于应用是否需要看它的内部：把电话号码整体当一个字符串用，它就是原子的；但若应用要按区号分组统计，把「区号+号码」塞一格就破坏了原子性，应拆成两列。典型的 1NF 违例：一格里存 `"数学,物理,化学"` 这样的多值列表、或设计出 `hobby1, hobby2, hobby3` 这类重复组。修法是把多值拆成多行（新开一张关联表）或多列（若个数固定且有语义）。注意这与后续范式不同——1NF 谈的是「值的形状」（原子不原子），2NF 及以上谈的是「值之间的依赖」（谁决定谁），两者层面不同。

### 03-4.3.2 判定用语：素属性、非素属性、部分依赖、传递依赖

在给 2NF/3NF 下定义前，先钉住四个判定术语。**素属性（prime attribute）** 是至少属于某一个候选键的属性；反之为**非素属性（non-prime）**。**部分依赖（partial dependency）** 指某个非素属性依赖于候选键的一个**真子集**（而非整个键），形如候选键是 `{A,B}` 却有 `A → C`（C 非素）。**传递依赖（transitive dependency）** 指非素属性通过一条「中转」间接依赖候选键，形如 `键 → X` 且 `X → C`，而 X 不是超键、C 非素。

2NF 就是「消灭部分依赖」，3NF 是「进一步消灭传递依赖」，所以先分清这两种「坏依赖」长什么样，范式定义自然就顺了。判定这些依赖，前置动作永远是**先把候选键全求出来**（用 03-4.1.5 的方法），因为「素/非素」「部分/传递」全都相对候选键而言。这是初学者最常栽的地方——不先定候选键就套范式定义，必然判错。

### 03-4.3.3 第二范式（2NF）：消除非素属性对候选键的部分依赖

一个模式属于 2NF，当且仅当它在 1NF 基础上，**没有任何非素属性部分依赖于某个候选键**（即每个非素属性都完全依赖于每个候选键的整体，而非其真子集）。当候选键都是单属性时，不可能有「真子集依赖」，此时 2NF 自动满足；只有存在复合候选键时 2NF 才可能被违反。

`(学号, 课号, 成绩, 姓名)`，候选键 `{学号, 课号}`，但 `学号 → 姓名`——姓名（非素）只依赖键的一部分「学号」，这是部分依赖，违反 2NF，导致同一学生每选一门课姓名就重存一遍。修法是把部分依赖拎出去单独成表 `(学号, 姓名)`，原表留 `(学号, 课号, 成绩)`。给初学者的提示：2NF 在现代教材（含 DBSC 7e）里更多作为「通向 3NF 的历史台阶」被提及，实践中直接奔 3NF/BCNF；但它把「部分依赖」这个概念讲清楚了，是理解 3NF 的必要铺垫，所以不能跳过。

### 03-4.3.4 第三范式（3NF）：定义与三条件判定

一个模式 R（带 FD 集 F）属于 3NF，当且仅当对 F⁺ 中的**每一条**非平凡函数依赖 α → β，下面三个条件**至少满足一个**（DBSC 7e §7.3.2）：

(1) α → β 是平凡的（β ⊆ α）

(2) α 是 R 的超键

(3) β − α 中的每个属性都是素属性（属于 R 的某个候选键）

等价地，2NF 之外再排除「非素属性对候选键的传递依赖」即得 3NF。判定时对每条 FD 走这三条：只要每条都能命中至少一条，就是 3NF。

条件 (2) 说「决定方靠自己就是键，那它决定谁都天经地义，不算冗余」；条件 (3) 是 3NF 相对 BCNF 特有的「网开一面」——**哪怕决定方 α 不是超键，只要被决定的属性 β 本身是候选键的一部分（素属性），也放行**。正是这条 (3) 让 3NF 比 BCNF 宽松，也正是它让 3NF 可能残留冗余（下节详述）。经典 3NF 违例（只违 3NF，同时也讲清传递依赖）：`(学号, 系名, 系楼)`，键 `学号`，有 `学号 → 系名`、`系名 → 系楼`——`系名` 不是超键、`系楼` 非素，故 `系名 → 系楼` 三条件全不中，违反 3NF，系楼随学生数重复。易错点：三条件是「或」不是「且」，逐条 FD 判、命中一条即过；且必须先求全候选键才能判素/非素与超键。

- DBSC 7e ch7 §7.1「Features of Good Relational Designs」、§7.2「... First Normal Form」、§7.3.2「Third Normal Form」（核实 2026-07-29，章级已核，节级待核）：1NF 原子域、3NF 三条件定义、传递依赖。DBSC 7e 对 2NF 着墨少，仅作历史提及。
- R&G 3e ch19 §19.6「Normal Forms」（1NF/2NF/3NF/BCNF）：2NF 的部分依赖定义、3NF 定义与 DBSC 一致；R&G 明确给出 2NF 定义可补 DBSC 之简（交叉核对通过）。
- Codd, E.F. 1971/1972「Further Normalization of the Data Base Relational Model」：2NF、3NF 的原始提出（一手，佐证定义源头）。

## 03-4.4 BCNF 与 3NF 分解算法及二者取舍

### 03-4.4.1 Boyce-Codd 范式（BCNF）的定义

一个模式 R（带 F）属于 BCNF，当且仅当对 F⁺ 中**每一条**非平凡函数依赖 α → β，α 都是 R 的**超键**（DBSC 7e §7.3.1）。等价地说，BCNF 就是把 3NF 三条件里的第 (3) 条「网开一面」删掉，只留 (1) 平凡 或 (2) 决定方是超键：

对每个非平凡 α → β ∈ F⁺：α 是超键

因此每个 BCNF 模式都是 3NF，反之不一定——BCNF 严格强于 3NF。

**BCNF 要求「凡是能决定别人的（非平凡地），都必须是键」**，没有例外。它比 3NF 干净，理论上能消除所有由函数依赖引起的冗余。回看 03-4.3.4 的 `(学号, 系名, 系楼)`：`系名 → 系楼` 里 `系名` 不是超键，直接违反 BCNF（3NF 里它也违，因为系楼非素，两范式此例都判违）。而下一节的 `(J,K,L)` 反例则是「违 BCNF 但满足 3NF」的典型，用来体会两者的缝隙。

### 03-4.4.2 BCNF 分解算法（无损，但可能不保依赖）

算法（DBSC 7e §7.5.1）：只要 R 里存在一条违反 BCNF 的非平凡依赖 α → β（α 不是超键），就把 R 换成两张表——一张是 (α ∪ β)，另一张是 (R − (β − α))；对得到的每张表递归重复，直到全部满足 BCNF。这样得到的分解**保证无损连接**（因为拆点的公共属性 α 是新表 (α∪β) 的键，满足 03-4.2.2 的超键判据），但**不保证依赖保持**。

经典反例（DBSC 7e 与 R&G 均用同型例子）：R(J, K, L)，F = {JK → L, L → K}。候选键是 `JK` 和 `JL`，故 J、K、L 全是素属性——按 3NF 条件 (3)，`L → K` 中 K 是素属性，放行，**该表满足 3NF**。但 `L → K` 里 L 不是超键，**违反 BCNF**。按算法用 `L → K` 分解得 (L, K) 与 (J, L)。分解后 `JK → L` 这条依赖被拆散——它的属性 J、K、L 不再同处一表，任何单表都查不动它，需连接两表才能验证，**依赖丢失**。

BCNF 分解的「无损」有算法保证、可放心；但要警惕它可能拆散某条 FD，让原本一处可查的约束变成必须跨表连接才能维护。是否接受这种代价，就是下面 BCNF vs 3NF 的取舍。易错点：算法每一步都要针对**当前子表**重新算它自己的候选键与违反依赖，不能拿最初整表的键去套子表。

### 03-4.4.3 3NF 合成算法（保依赖 + 无损）

与 BCNF 的「自顶向下拆」不同，3NF 用**合成（synthesis）**自底向上造表（DBSC 7e §7.5.2）：先求 F 的最小覆盖 Fc；对 Fc 中每条 FD α → β 生成一张表 (α ∪ β)（同左边的可合并成 (α ∪ β₁ ∪ β₂…)）；若生成的所有表里没有一张包含 R 的某个候选键，就再补一张仅含某个候选键的表；最后删掉是别的表子集的冗余表。该算法产出的分解**同时保证无损连接、依赖保持、且每张表都在 3NF**。

BCNF 分解像「发现毛病就切一刀」，可能切断某条规则；3NF 合成像「按规则说明书一条一条建表」，每条规则天然落在某张表里（故必然保依赖），最后补键表保证能拼回（无损）。这是 3NF 分解总能兼得无损与保依赖的根本原因。易错点：一定要先求**最小覆盖**再合成，否则会造出一堆冗余小表；补候选键那一步不能忘，它是无损性的保证。

### 03-4.4.4 BCNF vs 3NF 的取舍（可达性结论）

核心结论，两条要交叉核对记牢：**(A) 任何模式都存在一个无损连接的 BCNF 分解，但不一定存在既无损又保依赖的 BCNF 分解；(B) 任何模式都存在一个既无损连接又保依赖的 3NF 分解**（DBSC 7e §7.3.3、§7.5，R&G §19.6–19.7 同此结论）。换句话说：

分解到 BCNF 可保无损、能最彻底消除函数依赖引起的冗余，但依赖保持有时做不到。

分解到 3NF 可保无损、且依赖保持总能做到，代价是可能残留一点冗余。

若一条被 BCNF 拆散的依赖很重要、需要高频廉价地维护，就退一步用 3NF、容忍少量冗余；若冗余带来的更新异常风险更痛、且那条依赖可以靠应用层或异步检查兜底，就上 BCNF。DBSC 7e 的实务建议是**多数情况以 3NF 为默认、追求 BCNF 但允许在会牺牲依赖保持时停在 3NF**。

把它记成一个「二选一」——**BCNF 更干净但可能丢规则，3NF 保规则但可能留点冗余；无损两者都保。** 之所以 3NF 能「既无损又保依赖」而 BCNF 不能，就是因为 3NF 的第 (3) 条豁免（素属性放行）恰好放过了像 `L → K`（K 素）这类「拆了才违 BCNF、不拆则违依赖保持」的依赖，从而绕开了矛盾。这条豁免既是 3NF 残留冗余的来源，也是它总能保依赖的原因，一体两面。

## 03-4.5 多值依赖与 4NF（PJNF/5NF 点到）

### 03-4.5.1 多值依赖（multivalued dependency, MVD）

BCNF 消除了函数依赖引起的冗余，但有一类冗余 FD 根本描述不了，需要**多值依赖**。α ↠ β（读「α 多值决定 β」）成立，指对任意在 α 上取值相同的两个元组，交换它们的 β 值后得到的元组仍在关系中——直观说就是 β 这组属性与其余属性（R − α − β）在给定 α 时**相互独立**。形式化（DBSC 7e §7.7.1）：对 r 中满足 t₁[α]=t₂[α] 的任意 t₁,t₂，存在 t₃,t₄ 使得

t₃[α]=t₄[α]=t₁[α]，t₃[β]=t₁[β]，t₃[R−β]=t₂[R−β]，t₄[β]=t₂[β]，t₄[R−β]=t₁[R−β]

每个 FD 都是 MVD（α → β 蕴含 α ↠ β），故 MVD 是 FD 的推广。

一张 `(教师, 技能, 语言)` 表，某教师会的技能与会的语言彼此无关。若某教师会 2 项技能、3 种语言，为把「独立的两组」凑在一张表里，就得存 2×3=6 行的笛卡尔组合，且每加一项技能要为每种语言各补一行——这种「组合爆炸式冗余」FD 描述不了，正是 MVD 要刻画的：`教师 ↠ 技能`（且 `教师 ↠ 语言`）。直觉记法：**FD 是「一个值定一个值」，MVD 是「一个值定一组彼此无关的值」**。易错点：MVD 总是成对出现，α ↠ β 当且仅当 α ↠ (R−α−β)（互补律）。

### 03-4.5.2 第四范式（4NF）：消除非平凡多值依赖

一个模式属于 4NF，当且仅当对其上（依赖集闭包 D⁺ 里）**每一条非平凡多值依赖 α ↠ β，α 都是超键**（DBSC 7e §7.7.2）。它与 BCNF 形状完全平行，只是把 FD 换成 MVD。因为每个 FD 是 MVD，**4NF 蕴含 BCNF**（4NF 严格强于 BCNF）。分解方法也与 BCNF 类似：找违反的 α ↠ β，把 R 拆成 (α ∪ β) 与 (α ∪ (R−β))，此分解无损。

回到上例，`(教师, 技能, 语言)` 有非平凡 MVD `教师 ↠ 技能` 而 `教师` 不是超键，违反 4NF；拆成 `(教师, 技能)` 与 `(教师, 语言)` 后，各表只存各自独立的事实，6 行冗余降为 2+3 行，且连接可无损还原。给初学者的落点：**遇到「一张表里两组多值属性彼此无关、被迫做笛卡尔组合」的信号，就该想到 MVD 和 4NF，把它们拆到各自的表。** 判断 MVD 是否被蕴含、分解是否无损，理论上用**追逐法（chase algorithm）**，本课点到为止、不展开。

### 03-4.5.3 连接依赖与 5NF/PJNF、DKNF（点到）

比 4NF 更高的是**投影-连接范式（PJNF），即第五范式（5NF）**，它处理比 MVD 更一般的**连接依赖（join dependency）**——某些关系无法二元无损分解，却能三元及以上无损分解，5NF 要求每个连接依赖都由候选键蕴含（Fagin 1979）。再往上还有**域-键范式（DKNF）**，要求每个约束都是域约束与键约束的逻辑后果（Fagin 1981）。

这些范式在实践中**极少需要专门处理**——现实里能触发 5NF 违例（即存在「必须三表才能无损拆」的连接依赖）的场景很罕见，DKNF 更是多为理论上的「终极目标」而非可操作规程。本课按锚点要求「点到为止」：知道范式序列是 **1NF ⊂ 2NF ⊂ 3NF ⊂ BCNF ⊂ 4NF ⊂ 5NF(PJNF) ⊂ DKNF**（右者更严）、知道 4NF 之上还有以连接依赖为对象的层级即可，具体判定与 chase 留作进阶。易错点：不要把「范式越高越好」当教条——多数生产库停在 3NF/BCNF，过度追高范式徒增连接开销，见下一节反范式。

## 03-4.6 反范式与工程权衡

### 03-4.6.1 反范式（denormalization）是什么、为什么反着来

反范式指**在一个已规范化的设计上，有意重新引入冗余**（如把常一起查的列合并回一张表、复制冗余列、预存聚合值），以减少查询时的连接与计算、换取读性能。它的前提是「先规范化、再有针对性地退化」，而不是「一开始就不做规范化」。

范式的目标是**写得干净**（每个事实一处、无更新异常），而查询往往要把拆散的表连回来，连接是有代价的操作，读多写少的场景下这代价可能成为瓶颈。反范式就是**用「写时的冗余与维护负担」去换「读时的速度」**——本质是一次针对具体负载的权衡，不是「范式错了」。这属于经验性的**工程权衡**，不像范式定义那样有唯一正确答案；DBSC/R&G 都将其列为设计实践建议而非定理，来源层级低于前面的理论结论，应据具体负载判断。

### 03-4.6.2 常见反范式手法

主要有几类。**预连接（合并表）**：把频繁一起查询、几乎总要 join 的两张表合并，省掉连接。**冗余列**：把另一张表的某列拷贝一份过来（如订单表里冗余存客户名），避免为显示一个名字去 join 客户表。**派生/预聚合列**：预先算好并存储聚合结果（如账户表里存 `订单总额`），避免每次 `SUM` 扫明细。**重复组/数组列**：在支持的引擎里用数组/JSON 列把小的一对多塞进一行，减少子表。

这几招都在**制造受控的冗余**，共同代价是——冗余数据要靠额外机制保持同步（触发器、应用代码、或定时刷新），一旦同步逻辑有漏洞就回到了 03-4.2.1 的更新异常。所以每用一处反范式，都要问「这份冗余由谁、何时、如何保证与源一致」。易错点：把反范式当「偷懒不建表」的借口——真正的反范式是**明知代价、为特定读负载有意为之**，且通常配套一致性维护方案。

### 03-4.6.3 代价、物化视图作为受控替代、何时决策

反范式的代价清单：更新变复杂且变慢（要同时改多处冗余）、更新异常风险回归、存储变大、约束更难用数据库原生机制保证。因此更受控的替代常是**物化视图（materialized view）**——把规范化基表上的一个连接/聚合查询的结果预先算好、物化存储，由数据库负责刷新，既保留规范化基表的写入干净、又提供反范式般的读性能，把「冗余的一致性维护」交给引擎而非手写代码。

决策指引（经验层级，非定理）：默认先做到 3NF/BCNF 的规范化设计；仅当**实测**证明某读路径的连接/聚合是瓶颈、且该表读远多于写时，才对那一处针对性反范式或改用物化视图；反范式后必须落实冗余同步方案并接受写放大。给初学者的落点一句话收尾：**范式是默认、是安全网；反范式是例外、是在测得的瓶颈处用一致性维护成本去买读性能——先规范化、再按需、按测量退化，而非反过来。** 这也呼应本大主题的整条主线：理论告诉你怎样最干净，工程告诉你何时、为何值得偏离。
