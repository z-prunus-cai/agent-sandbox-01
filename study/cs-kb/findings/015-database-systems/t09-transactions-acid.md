## 03-9.1 事务概念、ACID 语义与事务状态机

### 03-9.1.1 事务是什么：并发与故障之下的「正确性单位」

一个**事务（transaction）**是把若干数据库操作（读、写）打包成的一个**逻辑工作单元**，数据库对它整体负责，而不是对其中每一条语句单独负责。最经典的例子是转账：从账户 A 扣 50、给账户 B 加 50，这两步必须被当成不可分割的一件事——只做了扣、没做加，钱就凭空消失了。事务就是让这「一件事」在数据库看来是一个原子的、要么整体生效要么整体作废的单位。

初学者要抓住的关键是「事务解决的是两类捣乱」：一类是**并发**——多个用户同时读写同一批数据，操作交织在一起可能互相踩踏；另一类是**故障**——事务做到一半时程序出错、连接断开、机器崩溃、断电。没有事务机制，这两类情况都会把数据库留在一个「半成品」的错误状态（A 扣了钱 B 没加、或者两个人同时取款把余额取成负数）。事务的四条承诺 ACID（下一节）正是分别针对这两类捣乱：原子性 + 持久性对付故障，隔离性对付并发，一致性是它们共同要守住的目标。DBSC ch17 与 CMU 15-445 都以转账例子开场，正是要先建立「事务 = 面对并发和崩溃仍要正确」这个动机。

### 03-9.1.2 ACID 四性质

ACID 是事务的四条承诺，取自四个英文首字母：**原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）**。逐条讲：

**原子性（Atomicity）**：事务的所有操作要么全部反映到数据库、要么一个都不反映——「all or nothing」。转账事务若在扣款后、加款前崩溃，系统必须把已扣的款「撤销（undo）」回去，仿佛这个事务从未发生。原子性由数据库的**恢复系统**保障，手段是日志（03-11）：改动之前先记下「旧值」，崩溃后按日志把没提交的改动全部回滚。

**一致性（Consistency）**：事务若单独、完整地执行，必须让数据库从一个合法状态转到另一个合法状态——「合法」指满足所有完整性约束（主键、外键、`CHECK`、以及应用层不变式如「转账不改变总额」）。这一条和其它三条不同：它部分是**程序员的责任**（事务本身写得对，不能写一个「只扣不加」的转账），数据库负责的是「在保证隔离性和原子性的前提下，让每个正确的事务的效果得以正确落地」。

**隔离性（Isolation）**：多个事务并发执行时，每个事务感觉不到别的事务正在同时运行；并发执行的最终效果，要等价于这些事务以**某个串行次序**一个接一个执行的效果。这是本大主题的核心，03-9.2 会把「等价于某个串行次序」精确化为「可串行化」。隔离性由**并发控制**保障（锁、时间戳、MVCC，全在 03-10）。

**持久性（Durability）**：一旦事务成功提交（commit），它对数据库的改动就是永久的，即使随后立刻断电或崩溃也不会丢失。手段仍是日志——提交时先把日志刷到非易失存储（WAL：write-ahead logging），保证「提交」这个承诺有据可查、崩溃后能重做（redo，03-11）。

给初学者的落点是记住「谁保谁」：**原子性 + 持久性 = 恢复系统 / 日志（03-11）管；隔离性 = 并发控制（03-10）管；一致性 = 前三者 + 程序员共同守住的目标。** 一个常见易错点是把一致性（Consistency）与 CAP 定理里的 C、或与副本间一致性混为一谈——ACID 的 C 指「单库满足完整性约束」，与分布式的「一致性」是完全不同的词，后者留 L6-09 §09-9，本报告不涉及。

### 03-9.1.3 事务状态机：一个事务的一生

一个事务在执行过程中会经过若干**状态**，DBSC ch17 给出的状态图有五个状态：

活动（active）：初始状态，事务正在执行读写操作。

部分提交（partially committed）：最后一条语句执行完、但改动可能还在内存缓冲、尚未确保落盘。

失败（failed）：发现无法正常继续（约束违反、死锁被选中回滚、系统错误）。

中止（aborted）：事务已被回滚、数据库恢复到事务开始前的状态。

提交（committed）：成功完成，改动已确保持久。

状态之间的合法迁移是：

active → partially committed → committed （一切顺利）

active → failed → aborted （中途出错，回滚）

partially committed → failed → aborted （最后关头写盘/提交失败，也回滚）

初学者要理解「部分提交」这个中间态为什么存在：事务把最后一条语句跑完，逻辑上「做完了」，但它的改动可能还在内存里没真正写到持久存储；只有当日志确保落盘、系统正式承认，它才从「部分提交」跨到「提交」。这一步之前崩溃，事务仍会被当作失败回滚——所以「跑完最后一句」不等于「提交成功」。另一个要点是**进入 aborted 后的两条出路**（DBSC ch17）：若中止是因为系统性原因（如死锁牺牲品、临时故障），事务可以**重启（restart）**当作全新事务再来一遍；若是因为事务内部的逻辑错误（如输入数据本身非法），则应**杀掉（kill）**、由应用层处理，重试也没用。

### 03-9.1.4 SQL 里的事务边界：BEGIN / COMMIT / ROLLBACK / SAVEPOINT

在 SQL 里，事务的边界由三条语句划定。开始一个事务：

BEGIN;   -- 标准 SQL 也写作 START TRANSACTION

成功结束、让改动永久生效：

COMMIT;

放弃、把本事务的所有改动撤销：

ROLLBACK;

还有**保存点（savepoint）**，允许在一个事务内部设锚点、部分回滚而不放弃整个事务：

SAVEPOINT sp1;

ROLLBACK TO SAVEPOINT sp1;   -- 只回滚到 sp1，事务本身继续

初学者最需要澄清的是**自动提交（autocommit）**：大多数客户端（psql、大多数驱动）默认「每条独立语句就是一个自动提交的事务」，你不写 `BEGIN` 时，一条 `UPDATE` 跑完就自动 commit 了。只有显式 `BEGIN` 后，多条语句才会被归到同一个事务里、共命运。这解释了为什么初学者「写了一半 UPDATE 觉得能 rollback」却发现改动已经生效——因为处在自动提交模式下，每句都当场提交了。规范与实现的一个小分账：标准 SQL 里事务是隐式开始的（第一条语句就开启事务、直到显式 COMMIT/ROLLBACK），而 PostgreSQL、MySQL 等默认走 autocommit、需 `BEGIN` 显式开启多语句事务——行为可配置，用前先确认所用客户端的默认模式。

## 03-9.2 可串行化：冲突可串行化、视图可串行化、优先图判定

### 03-9.2.1 调度（schedule）与串行调度

要精确谈「隔离到位」，先要有语言描述「多个事务的操作是怎么交织的」。一个**调度（schedule）**就是若干并发事务的所有读写操作（以及提交/中止）按时间先后排成的一个总序列。记号上，用 `r_i(X)` 表示事务 T_i 读数据项 X、`w_i(X)` 表示 T_i 写 X。例如两个事务交织的一个调度可写成：

r₁(A) w₁(A) r₂(A) w₂(A) r₁(B) w₁(B) r₂(B) w₂(B)

**串行调度（serial schedule）**是一种特殊调度：每个事务的所有操作连续排在一起、事务之间不交织——就是「T_i 全做完再做 T_j」。n 个事务有 n! 种串行调度，每一种都天然正确（因为没有并发，谈不上互相干扰）。

初学者的落点是：串行调度一定正确但性能差（完全不并发），并发调度性能好但可能出错。**可串行化（serializability）**就是那个「既并发又正确」的判据——一个并发调度若其效果等价于某个串行调度，它就是可串行化的、可以放心执行。问题只剩下：怎么定义「等价」、怎么判定？这就引出下面两种可串行化。

### 03-9.2.2 冲突可串行化（conflict serializability）

先定义**冲突（conflict）**：调度里两个操作「冲突」，当且仅当它们来自**不同事务、访问同一数据项、且至少一个是写**。于是有三类冲突——写后读（w-r）、读后写（r-w）、写后写（w-w）；两个读操作不冲突。

**冲突等价（conflict equivalent）**：若一个调度能通过反复交换**相邻的、不冲突的**两个操作变成另一个调度，则两者冲突等价。直觉是「交换两个互不干扰的操作不改变结果」。

一个调度若**冲突等价于某个串行调度**，就称它**冲突可串行化（conflict serializable）**。这是可串行化最常用、最易判定的充分条件。

初学者要理解为什么「交换不冲突操作」保结果不变：两个操作若不访问同一数据、或都是读，那么谁先谁后对最终数据库状态毫无影响，交换它们只是改写记录、不改变语义。反过来，冲突的操作对（比如 T₁ 写 A、T₂ 读 A）交换顺序会改变 T₂ 读到的值，所以不能随便换。冲突可串行化的判定不必真去尝试各种交换——有一个图论工具直接判，就是下面的优先图。

### 03-9.2.3 优先图（precedence graph）判定

**优先图（precedence graph，也叫串行化图 serialization graph）**是判定冲突可串行化的标准算法。构造规则：

节点：调度中的每个事务 T_i 各一个节点。

边：若存在一对冲突操作，T_i 的操作在时间上**先于**且冲突于 T_j 的操作，则画一条有向边

T_i → T_j

具体地，三种冲突各生成一条边：T_i 写 X 而 T_j 随后读 X（w-r）、T_i 读 X 而 T_j 随后写 X（r-w）、T_i 写 X 而 T_j 随后写 X（w-w），都画 T_i → T_j。

判定定理是：

调度是冲突可串行化的 ⟺ 它的优先图无环（acyclic）

且当无环时，对该图做**拓扑排序**得到的任一线性次序，就是一个与原调度冲突等价的串行调度次序。

初学者最好用最小例子体会：调度 `r₁(A) w₂(A) r₂(B) w₁(B)`——T₁ 读 A 在 T₂ 写 A 之前（r-w 冲突，边 T₁→T₂），T₂ 读 B 写在 T₁ 写 B 之前，w₁(B) 在后，故 T₂ 读 B、T₁ 写 B 是 r-w 冲突、边 T₂→T₁。两条边 T₁→T₂ 和 T₂→T₁ 构成环，图有环 ⟹ 不可串行化。这个调度确实排不出等价串行序：它既要求「T₁ 在 T₂ 前」又要求「T₂ 在 T₁ 前」，自相矛盾。反之若图无环，拓扑排序给出的次序就是「假装它们其实是这样排队跑的」那个串行序。这是 03-10 并发控制里各种协议（尤其 SSI 检测 r/w 依赖成环）背后的理论依据。

### 03-9.2.4 视图可串行化（view serializability）

**视图可串行化**是比冲突可串行化更宽松的判据，基于「读到的是谁写的值」而非「操作能否交换」。两个调度**视图等价（view equivalent）**需同时满足三条：(1) 每个数据项的**初始读**由同一事务发出（谁读到最初值一致）；(2) 每个「读」操作**读到的值来自同一个写**（read-from 关系一致）；(3) 每个数据项的**最终写**由同一事务发出。一个调度视图等价于某个串行调度，就叫**视图可串行化**。

关系是：**每个冲突可串行化的调度都是视图可串行化的，反之不然。** 那些「视图可串行化但非冲突可串行化」的调度，一定含有**盲写（blind write）**——某事务不读某数据项就直接写它。

初学者的落点：视图可串行化能「原谅」一些冲突图有环、但因为盲写而实际结果仍等价于串行的调度，所以它接受的调度更多、理论上更优。但它有个致命的实用缺陷——**判定一个调度是否视图可串行化是 NP 完全问题**，没有像优先图那样的高效算法。因此现实数据库的并发控制**几乎都以冲突可串行化为目标**（可用优先图/锁高效保证），视图可串行化主要停留在理论层面，用来说明「冲突可串行化不是可串行化的全部、只是可高效判定的那一大部分」。

## 03-9.3 可恢复性与无级联调度

### 03-9.3.1 可恢复调度（recoverable schedule）

可串行化只管「并发正确」，还有一个正交的维度被它忽略了——**当某事务中途中止（abort）时，会不会连累已经根据它的数据做完并提交的其它事务**。这就是**可恢复性**要管的事。

一个调度是**可恢复的（recoverable）**，当且仅当：若事务 T_j 读了 T_i 写的某个数据项，那么 T_i 的提交必须**排在** T_j 的提交**之前**。形式化：

若 T_j read-from T_i，则 commit_i 先于 commit_j

为什么必须如此：假设 T_j 读了 T_i 写的值、T_j 先提交了，然后 T_i 却中止（要回滚它写的值）——此时 T_j 已经基于一个「本不该存在」的值提交且永久生效了，数据库无法把 T_j 也撤销（它已提交、持久性承诺不能反悔）。这就是**不可恢复**的调度，是绝对要禁止的。初学者记一句话即可：**你读了谁未提交的数据，就不能比它先提交**——否则它一翻脸，你就成了无法收拾的错误。

### 03-9.3.2 级联回滚与无级联调度（cascadeless）

即便调度可恢复，还可能出现**级联回滚（cascading rollback）**：T₁ 中止 → 凡是读过 T₁ 未提交数据的 T₂ 必须跟着中止 → 读过 T₂ 数据的 T₃ 也得中止……一个事务的失败像多米诺骨牌一样连累一长串事务全部回滚，代价巨大且浪费。

**无级联调度（cascadeless schedule，也叫 avoids cascading aborts / ACA）**通过一条更严的规则杜绝它：**事务 T_j 只能读 T_i 写的数据项在 T_i 已经提交之后**。形式化：

若 T_j read-from T_i，则 commit_i 先于 T_j 的这次 read

也就是「只读已提交的数据」。这样一来任何事务中止时，都不会有别的事务已经读了它的脏数据，级联便无从发生。

初学者要看清可恢复与无级联的区别：**可恢复**只要求「读了未提交数据的事务，提交要晚于被读者」——它**允许**你先读别人未提交的值（只是你得等对方先提交你才能提交）；**无级联**更进一步，干脆**不许**你读任何未提交的值。所以无级联比可恢复严格：无级联 ⟹ 可恢复，反之不成立。

### 03-9.3.3 严格调度（strict schedule）与三者的包含关系

**严格调度（strict schedule）**是最严的一档：**任何事务都不能读或写某数据项 X，直到最后写 X 的那个事务已经提交或中止为止**。它不仅像无级联那样禁止「读」未提交数据，还禁止「覆盖写」未提交数据——这让崩溃恢复时的 undo 变得极简单（直接把日志里记的「前像 before-image」写回即可，不会把别人的合法值也覆盖掉）。严格调度是实现（如严格两阶段锁 strict 2PL，03-10）实际采用的目标。

三档的包含关系是（DBSC ch17）：

严格调度 ⊂ 无级联调度 ⊂ 可恢复调度

即越往左越严格、能通过的调度越少、恢复越省事；越往右越宽松、并发度越高、但恢复越麻烦。

给初学者的整体图景：**可串行化（03-9.2）和可恢复性（本节）是两个正交的正确性维度**——前者管「并发结果对不对」，后者管「有人中途翻脸时收不收得了场」。一个理想的调度应同时是**可冲突串行化**且**无级联（或严格）**的。现实中严格两阶段锁（strict 2PL）一举同时保证了冲突可串行化 + 严格调度，所以它成了经典默认方案（细节 03-10）。这里只要建立「两个维度都得管、且实现常用 strict 一档同时搞定」这个认识即可。

- CMU 15-445 Spring 2026 并发控制部分（recoverable / cascadeless / strict 调度分类，与 strict 2PL 的对应）核实 2026-07-29。

## 03-9.4 隔离级别谱：READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE

### 03-9.4.1 为什么要有隔离级别：拿正确性换性能

完全的可串行化（等价于 SERIALIZABLE 隔离）是最强的隔离，但代价是并发度低——严格保证它要么大量加锁、要么频繁因冲突中止重试。现实中很多业务并不需要那么强的保证（比如「统计一下大致有多少订单」并不在乎期间有没有新订单插进来）。于是 SQL 标准提供了一把**旋钮**：让应用**按事务**选择一个**隔离级别（isolation level）**，用「容忍某些并发异常」换取更高的并发和吞吐。

初学者要建立的核心认识是：**隔离级别是「正确性 vs 性能」的分级折中，不是「开/关」。** 级别越高越接近可串行化、越慢；越低越快、但会放进特定的并发错误（下一小主题 03-9.5 逐一讲）。选级别的本质是问「我的业务能容忍哪些错」。而且——这是本大主题最重要的坑——**SQL 标准的四个级别是用「禁止哪些异常现象」定义的，各数据库的真实实现常常偏离标准**，下面把标准和实现分开记账。

### 03-9.4.2 SQL 标准的四个级别（ISO/IEC 9075 规范定义）

SQL 标准**不按实现机制**定义隔离级别，而是按「允许 / 禁止**三种现象**」定义。三种现象是脏读（dirty read, P1）、不可重复读（non-repeatable read, P2）、幻读（phantom, P3）（现象本身 03-9.5 详解）。四个级别与三种现象的对应就是标准的全部内容：

| 隔离级别 | 脏读 P1 | 不可重复读 P2 | 幻读 P3 |
|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不可能 | 可能 | 可能 |
| REPEATABLE READ | 不可能 | 不可能 | 可能 |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 |

读法：从上到下越来越严，每下一级多禁止一种现象。READ UNCOMMITTED 什么都不禁（最快最脏）；SERIALIZABLE 三种全禁（最慢最正确）。

初学者要牢牢记住两点。第一，**标准只规定「至少要禁止什么」，不规定「怎么实现」也不规定「只能禁止这些」**——一个实现在某级别下多禁止一些现象是合规的（PostgreSQL 的 REPEATABLE READ 就顺带禁了幻读，见下）。第二，**标准的三种现象并不能穷尽所有并发异常**——比如「写偏斜 write skew」和「丢失更新 lost update」就不在这张表里，这正是 1995 年那篇著名 Critique 论文批评标准的地方（03-9.5.6）。所以「SERIALIZABLE 禁止表里三种现象」不等于「SERIALIZABLE 一定真可串行化」——取决于实现是否真做到，别把标准表当成实现保证。

### 03-9.4.3 设置隔离级别的 SQL 语法

标准语法是按事务设置，独占一条语句：

SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

在 PostgreSQL 里既可以在 `BEGIN` 时一并指定，也可以事务开头单设：

BEGIN ISOLATION LEVEL REPEATABLE READ;

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

初学者常见易错点：`SET TRANSACTION ...` 必须在事务的**第一条数据操作语句之前**执行，事务跑到一半再改隔离级别是不允许的（会报错或被忽略）。另外 SQL 标准的**默认级别是 SERIALIZABLE**，但**几乎没有主流数据库真的默认 SERIALIZABLE**——PostgreSQL、Oracle、SQL Server、MySQL/InnoDB 默认都是较弱的级别（下节列）。这个「标准默认 vs 实现默认」的落差本身就是最常见的踩坑点。

### 03-9.4.4 规范 vs 实现：PostgreSQL 的真实行为（本大主题重点）

PostgreSQL（本机实证版本 PostgreSQL 16.13）语法上接受全部四个级别，但**内部只有三种不同的实现行为**，且实现基于**多版本快照（MVCC/快照隔离）**而非标准设想的加锁，因此与标准表有明显偏离：

READ UNCOMMITTED：PostgreSQL **不提供真正的读未提交**，它被**当作 READ COMMITTED** 处理——即 PostgreSQL 从不产生脏读，哪怕你要求 READ UNCOMMITTED。本机实证（03-9.5.7 DEMO C）证实：设 READ UNCOMMITTED 后读一个别的事务未提交的改动，读到的仍是旧值、不是脏值。

READ COMMITTED（PostgreSQL 默认级别，本机 `show default_transaction_isolation` 返回 `read committed`）：每条语句看到「该语句开始那一刻已提交」的快照；禁止脏读，但允许不可重复读和幻读。

REPEATABLE READ：PostgreSQL 用**快照隔离（snapshot isolation, SI）**实现——整个事务看到「事务开始那一刻」的同一份快照。这带来一个**超出标准要求**的效果：它**连幻读也一并禁止了**（标准只要求 RR 禁脏读和不可重复读、允许幻读）。本机实证（DEMO D）证实：RR 下重复统计同一谓词，别的事务插入的新行不会出现。但快照隔离**不能防写偏斜**（write skew），这正是 SI 特有的异常。

SERIALIZABLE：PostgreSQL 9.1 起用 **SSI（Serializable Snapshot Isolation，可串行化快照隔离）** 实现——在快照隔离基础上跟踪事务间的读写依赖，一旦检测到可能破坏可串行化的**依赖环**，就中止其中一个事务并报错

ERROR: could not serialize access due to read/write dependencies among transactions

（SQLSTATE `40001`，serialization_failure）。本机实证（DEMO E）证实：只有 SERIALIZABLE 能挡住写偏斜，代价是应用**必须准备好在收到 40001 时重试事务**。

一句话总结 PostgreSQL 的偏离：**它比标准更强（RR 顺带防幻读），但 RR 仍放行写偏斜；真正的可串行化只有 SERIALIZABLE(SSI) 能给，且以「可能中止 + 重试」为代价。** 初学者用 PostgreSQL 时要特别记住「READ UNCOMMITTED 等于 READ COMMITTED」和「REPEATABLE READ ≠ 标准 RR、其实是快照隔离」这两条实现事实。

### 03-9.4.5 规范 vs 实现：SQLite 与其它引擎的差异

**SQLite**（本机 Python 内置 sqlite3 引擎版本 3.45.1）的隔离模型与上面完全不同：它本质上是**串行化（SERIALIZABLE）**的，靠**数据库级/文件级锁**实现，而不是四级隔离旋钮。传统的 rollback-journal 模式下，写事务要拿**排他锁**，同一时刻只允许一个写者、且写时排斥读者，因此天然不会有脏读/不可重复读/幻读。SQLite 官方文档明确写「事务是 serializable 的」。它**没有** `SET TRANSACTION ISOLATION LEVEL` 那套语法；唯一相关的是 `PRAGMA read_uncommitted`，且只在**共享缓存（shared-cache）**模式下才允许读未提交——属于边角特性，普通用法用不到。WAL 模式（`PRAGMA journal_mode=WAL`）下读者看到一个快照、可与单个写者并发，但仍不放松到产生上述异常（WAL/日志细节留 03-11）。

对照一下其它主流引擎的默认级别（作为「实现默认普遍偏离标准默认」的佐证，具体行为以各自官方文档为准）：**Oracle** 默认 READ COMMITTED（且不支持 READ UNCOMMITTED、其 SERIALIZABLE 实为快照隔离）；**MySQL/InnoDB** 默认 REPEATABLE READ（用 MVCC + 间隙锁，能防大部分幻读）；**Microsoft SQL Server** 默认 READ COMMITTED（基于锁，另可选基于快照的 RCSI/SI）。这些默认值与实现机制随版本演进，标为「以各引擎当前官方文档为准，核实 2026-07-29」。

给初学者的落点：**「隔离级别」这个概念是 SQL 标准给的统一词汇表，但每个引擎把这几个词映射到自己的机制上、映射方式各不相同**。所以跨库迁移时，同一句 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` 在 PostgreSQL 和 MySQL 上的实际行为可能不一样——判断某引擎某级别到底防什么，必须查该引擎的官方文档，不能只背标准表。

## 03-9.5 异常现象：脏读 / 不可重复读 / 幻读 / 写偏斜（现象↔级别映射）

### 03-9.5.1 脏读（dirty read, P1）

**脏读**指一个事务读到了另一个事务**尚未提交**的改动。若那个事务随后回滚，读到的就是一个「从未真正存在过」的值——读到了「脏数据」。示意：

T₂: w₂(X=999)   -- 未提交
T₁: r₁(X)       -- 读到 999（脏）
T₂: ROLLBACK    -- X 其实回到旧值，T₁ 白读了个幻影

脏读只在 READ UNCOMMITTED 级别（标准）才可能发生；READ COMMITTED 及以上都禁止它。初学者要理解脏读的危害不只是「读到会被撤销的值」，更在于基于脏值做的后续决策（下单、扣款）会全盘错误。前面 03-9.3 讲的「无级联调度」正是从写者角度杜绝脏读的另一说法——「只读已提交数据」。实现上，防脏读要么写者加排他锁挡住读者（锁方案），要么读者永远读已提交快照（MVCC 方案，PostgreSQL 即此，所以它连 RU 都不会脏读）。

### 03-9.5.2 不可重复读（non-repeatable read / fuzzy read, P2）

**不可重复读**指一个事务在其执行期间**两次读同一行**，因为**另一个事务在两次读之间修改（或删除）了该行并提交**，导致两次读到的值不一样。示意：

T₁: r₁(X)=100
T₂: w₂(X=500); COMMIT
T₁: r₁(X)=500   -- 同一行，同一事务内，前后读到不同值

不可重复读在 READ COMMITTED 级别可能发生（因为 RC 是「每条语句读该语句时刻的最新已提交快照」，两条语句之间别人提交的改动会被看见）；REPEATABLE READ 及以上禁止它（顾名思义「可重复读」——事务内重复读同一行结果稳定）。本机实证 DEMO A 与 DEMO B 正是这一对的对照。

初学者要抓住脏读与不可重复读的区别：**脏读读的是「未提交」的值（对方可能反悔），不可重复读读的是「已提交」的值（对方确实改了并生效）**——后者读到的每个值都合法，问题只在于「同一事务内两次读不一致」，破坏了事务看到一个稳定世界的假象。

### 03-9.5.3 幻读（phantom read, P3）

**幻读**与不可重复读类似，但针对的是**一组满足某谓词条件的行**而非单个已存在的行：一个事务两次执行同一个带 `WHERE` 条件的查询，因为另一个事务在两次之间**插入（或删除）了满足该条件的新行**并提交，导致第二次查询多出（或少了）一些「幽灵」行。示意：

T₁: SELECT count(*) FROM acct WHERE bal>=100  -- 得 2
T₂: INSERT INTO acct VALUES(3,300); COMMIT     -- 插入满足条件的新行
T₁: SELECT count(*) FROM acct WHERE bal>=100  -- 得 3，多出一个「幻影行」

幻读与不可重复读的关键差别是**幻读关乎「行的存在与否」（谓词范围内的成员变化），不可重复读关乎「已存在行的值变化」**。这个区别很重要，因为防它们需要不同手段：防不可重复读只需锁住/快照住已读的那几行，防幻读还要锁住「未来可能插进这个范围的位置」——即**谓词锁 / 间隙锁 / 快照**（03-10）。标准把幻读单列一档，正因为它比不可重复读更难防、需要额外机制。

按 SQL 标准，幻读在 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 都可能，只有 SERIALIZABLE 才禁止。但如前述，PostgreSQL 的 REPEATABLE READ（快照隔离）**顺带禁了幻读**（DEMO D 证实），这是它优于标准 RR 之处。

### 03-9.5.4 现象↔级别映射（标准 vs PostgreSQL 实现对照）

把标准定义和 PostgreSQL 实测放在一起对照，是理解本大主题「规范 vs 实现」的关键一表（√=可能发生，×=被禁止）：

| 级别 | 脏读（标准/PG） | 不可重复读（标准/PG） | 幻读（标准/PG） | 写偏斜（标准未列/PG） |
|---|---|---|---|---|
| READ UNCOMMITTED | √ / ×（PG当作RC） | √ / √ | √ / √ | — / √ |
| READ COMMITTED | × / × | √ / √ | √ / √ | — / √ |
| REPEATABLE READ | × / × | × / × | √ / **×**（PG快照防幻读） | — / √（SI放行写偏斜） |
| SERIALIZABLE | × / × | × / × | × / × | — / ×（SSI防写偏斜） |

表里最值得注意的两处偏离：PostgreSQL 的 RR 那一格幻读是 **×**（标准是 √）；写偏斜整列是标准根本没定义的异常，而 PostgreSQL 只有 SERIALIZABLE 能防。这张对照表可以当作 PostgreSQL 使用者的选级速查。

### 03-9.5.5 写偏斜（write skew）与丢失更新（lost update）：标准之外的异常

**写偏斜（write skew）**是快照隔离（SI）特有、且**不在 SQL 标准三现象之列**的异常：两个事务各自读了**重叠的一批数据**，然后**各自修改不同的行**，每个事务单看都维持了某个约束、但两者合起来却破坏了这个约束。经典例子是「医院要求至少一名医生在岗」：两名值班医生同时各开一个事务，各自读到「现在有 2 人在岗、我下班后还剩 1 人、满足约束」，于是各自把自己设为下班；两个事务写的是**不同的行**（互不冲突），在 SI 下都能提交——结果 0 人在岗，约束被破坏。

本机 DEMO E 用「两账户总额至少 100」的约束复现了它：两事务各读到总额 200、各自把自己那个账户清零，在 REPEATABLE READ（SI）下双双提交、总额变成 0（约束破坏）；切到 SERIALIZABLE（SSI）后，其中一个事务被中止报 40001、总额守住 100。

**丢失更新（lost update）**是另一个常被单列的异常：两个事务都读同一行、各自基于读到的值算出新值再写回，后写的覆盖了先写的，先写的更新「丢失」了（典型：两人同时给同一计数器 +1，结果只加了 1）。SI 下同一行的并发写通常会被「first-committer-wins」规则挡住一个（PostgreSQL 的 RR 下第二个写者会收到序列化失败），但若两事务写的是不同行、通过读来的值间接耦合，就退化成写偏斜。

初学者的落点：**SQL 标准的三种现象不是并发异常的全集**。写偏斜、丢失更新、读偏斜（read skew）等都是标准表覆盖不到、却真实存在的坑；防它们通常需要真正的可串行化（PostgreSQL 的 SERIALIZABLE/SSI），或应用层显式加锁（`SELECT ... FOR UPDATE`）。这也是下一节那篇 Critique 论文的核心贡献——指出标准的不完备。

### 03-9.5.6 标准定义的模糊性：ANSI SQL Isolation Levels 之批评

1995 年 Berenson、Bernstein、Gray、Melton、O'Neil、O'Neil 的论文「A Critique of ANSI SQL Isolation Levels」是理解本大主题的关键次级来源。它指出 SQL 标准（ANSI SQL-92）用自然语言描述三种现象时**存在歧义**——每种现象可作「严格解释（strict）」或「宽松解释（broad）」，两种解释挡住的调度范围不同；标准的表述在两者之间摇摆，导致不同实现「都自称合规」却行为不一。论文还指出标准隐含假设「用加锁实现」，因而**没能描述基于多版本/快照的系统**，并正式定义了**快照隔离（Snapshot Isolation）**这一实际被广泛采用、却「塞不进」标准四级谱系的级别，以及它特有的**写偏斜（A5B）**与读偏斜（A5A）异常。

给初学者的意义：**不要把「SQL 标准隔离级别」当成一套精确、可实现照搬的规范**——它是一个有名的、但定义粗糙且以锁为隐含前提的历史约定。真实系统（尤其 MVCC 系统如 PostgreSQL/Oracle）的隔离行为，必须回到各自官方文档去确认，而不能仅凭标准表推断。这篇论文正是「规范 vs 实现分账」这条纪律的学术源头。

### 03-9.5.7 本机实证：PostgreSQL 16.13 双会话复现四种现象

以下为本机真实运行结果，环境串 `基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25`，引擎 `PostgreSQL 16.13 (Ubuntu 16.13-0ubuntu0.24.04.1)`，临时集群跑在 5433 端口、实证后已销毁（`show default_transaction_isolation` 返回 `read committed`，确认默认级别）。两会话用 `pg_sleep` 交错时序，测试表 `acct(id int primary key, bal int)` 初值 `(1,100),(2,100)`。

DEMO A（READ COMMITTED 出现不可重复读）——会话 B 在 RC 下前后读同一行，中间会话 A 改 `id=1` 的 bal 为 500 并提交：

[SESS-B RC] B read#1 bal=100
[SESS-B RC] B read#2 bal=500

两次读不同 ⟹ 不可重复读复现。

DEMO B（REPEATABLE READ 阻止不可重复读）——同样时序，会话 B 改用 RR：

[SESS-B RR] B read#1 bal=100
[SESS-B RR] B read#2 bal=100

两次读一致 ⟹ RR 的快照挡住了不可重复读。

DEMO C（READ UNCOMMITTED 无脏读，证 PG 把 RU 当 RC）——会话 A 把 bal 改成 999 但**不提交**（最终 ROLLBACK），会话 B 在 READ UNCOMMITTED 下读：

[SESS-B RU] read uncommitted        -- current_setting 回显请求的级别标签
[SESS-B RU] B reads bal=100         -- 但读到的是已提交旧值，非脏值 999

级别标签虽显示 read uncommitted，实际读不到未提交数据 ⟹ PostgreSQL 无真正 READ UNCOMMITTED。

DEMO D（幻读：RC 出现、RR 不出现）——读者两次 `SELECT count(*) WHERE bal>=100`，中间另一会话插入满足条件的新行 `(3,300)` 并提交：

reader RC:  count#1=2  count#2=3     -- 幻影行出现
reader RR:  count#1=2  count#2=2     -- 快照隔离挡住幻读

证实标准 RR「允许幻读」，但 PostgreSQL 的 RR（快照隔离）**超标准**地禁止了幻读。

DEMO E（写偏斜：RR 放行、SERIALIZABLE 拦截）——约束「两账户总额 ≥100」，T1、T2 各读总额 200 后各自清零一个账户：

both RR:          T1 COMMIT  T2 COMMIT  ⟹ final sum(bal)=0     -- 写偏斜，约束破坏
both SERIALIZABLE: T2 COMMIT
                   T1 ERROR: could not serialize access due to read/write dependencies among transactions
                   T1 ROLLBACK           ⟹ final sum(bal)=100   -- SSI 拦下，约束守住

证实 SI（PostgreSQL RR）无法防写偏斜，只有 SERIALIZABLE(SSI) 能防、代价是一方被中止需重试（SQLSTATE 40001）。

这一组实证同时坐实了 03-9.4.4 的所有断言：PG 的 RU=RC、RR=快照隔离且防幻读、SERIALIZABLE=SSI 防写偏斜。SQLite 侧因本机无 `sqlite3` CLI、且 SQLite 是库级锁的 serializable 模型、无隔离级别旋钮可复现「脏读/不可重复读」，故未做双会话实证（如实标注：SQLite 隔离实证未取）。
