## 03-5.1 存储层次与介质：磁盘、SSD、RAID 与访问代价模型

### 03-5.1.1 存储层次（memory hierarchy）：越快越贵越小，越慢越便宜越大

计算机的存储设备排成一个金字塔，自上而下依次是 CPU 寄存器、多级 cache、主存（RAM）、闪存 SSD、机械磁盘（HDD）、磁带/云冷存储。越靠上访问越快、单位容量越贵、总容量越小；越靠下越慢越便宜越大。一个粗略但够用的量级感是：主存访问以纳秒（ns）计，SSD 随机读以几十微秒（μs）计，机械磁盘一次随机 I/O 以毫秒（ms）计——磁盘比内存慢大约五到六个数量级。存储还分**易失（volatile）**与**非易失（non-volatile）**两类：寄存器/cache/RAM 断电即失，SSD/HDD/磁带断电保留。数据库要保证数据「持久」，就必须最终把它写到非易失介质上。

初学者要抓住的直觉是「为什么数据库这门课要专门讲硬件」。因为数据库处理的数据量通常远大于内存，主角是那两层非易失介质，而它们慢得离谱——慢到一次访问的成本压倒了几乎所有 CPU 计算。于是数据库的性能几乎完全由「挨了多少次慢速 I/O」决定，后面所有机制（缓冲、页、索引、连接算法）本质上都是在省 I/O。DBSC ch12 与 CMU 15-445 L3 都以「the DBMS assumes the database is stored on non-volatile disk」这一前提开场，正是这个原因。另一个易混点：这里说的「块设备」指磁盘/SSD 以固定大小的块为单位读写，不能像内存那样按字节随机寻址——这直接决定了数据库以「页」为搬运单位。

### 03-5.1.2 机械磁盘（HDD）：一次访问的三段时间

机械硬盘由若干旋转的盘片（platter）和在其上移动的读写磁头组成；盘面被划成同心的**磁道（track）**，磁道再切成**扇区（sector，通常 512B 或 4KB）**，不同盘面同半径的磁道合称**柱面（cylinder）**。读写一块数据的耗时由三段相加：

访问时间 = 寻道时间（seek time） + 旋转延迟（rotational latency） + 传输时间（transfer time）

其中**寻道时间**是磁头移动到目标磁道所需时间（典型几毫秒），**旋转延迟**是等目标扇区转到磁头下所需时间（平均约等于半圈时间，7200rpm 盘约 4.17ms），**传输时间**是数据实际读出的时间。前两段是「找到位置」的固定开销，与数据量几乎无关。

这三段时间的构成解释了数据库世界一条铁律：**顺序访问远快于随机访问**。若要读的数据在磁盘上物理连续，磁头寻道一次、几乎不用反复等旋转，就能一路读下去，传输时间摊薄了固定开销；若数据散落各处，每读一块都要重新寻道 + 等旋转，固定开销被反复付出。一个初学者常见的错误直觉是「读 100 块就是读 1 块的 100 倍时间」——错，随机读 100 块可能是顺序读 100 块的几十倍，因为随机读把寻道和旋转延迟付了 100 次。数据库把表尽量顺序存放、把小 I/O 攒成大 I/O，都是为了把「随机」变「顺序」。

### 03-5.1.3 固态盘（SSD）：没有机械臂，但仍非匀速

SSD 用闪存芯片存数据，没有旋转盘片和移动磁头，因此**没有寻道时间和旋转延迟**，随机读性能比 HDD 高几个数量级。但 SSD 有自己的脾气：读写以**页（page，闪存页，典型 4KB–16KB）**为单位，而擦除必须以更大的**块（block，若干页）**为单位，且闪存单元「先擦后写」——不能原地覆盖，改一个页往往要读出整块、擦除、再写回（写放大）。因此 SSD 的**写比读慢、随机写尤其贵**，还有**寿命**问题（每个单元可擦写次数有限），控制器用**磨损均衡（wear leveling）**把写分散开。

给初学者的落点是：SSD 大幅缩小了「随机 vs 顺序」的差距，但没有抹平——尤其写侧，顺序写仍明显优于随机小写。所以即便在全 SSD 的现代部署里，数据库「按页搬运、攒批顺序写、减少小随机写」的设计依然成立。DBSC ch12 与 CMU 15-445 L3 都强调 SSD 改变的是常数量级、而非「减少 I/O」这个总方向。注意区分两个「页/块」：数据库的逻辑页（下面各节讲的 4KB/8KB）与 SSD 内部的闪存页/擦除块是不同层次的概念，别混为一谈。

### 03-5.1.4 访问代价模型：数一数「块传输」和「寻道」

因为一次磁盘 I/O 的成本压倒 CPU，数据库分析算法代价时通常**只数磁盘块的传输次数和寻道次数**，忽略内存里的 CPU 工作。DBSC ch12 给出的估算式是：设一次操作需传输 b 个块、发起 S 次寻道（随机定位），块传输时间为 t_T、块访问/寻道时间为 t_S，则总时间约为

估算时间 ≈ b × t_T + S × t_S

顺序访问时 S 很小（一次定位读一长串），随机访问时几乎每块都要一次寻道，S ≈ b。

这个模型是后面 03-7 查询处理、03-8 查询优化里所有「代价估计」的地基，务必吃透其精神：**衡量数据库算法快慢，第一位看它读写多少块、其中多少是随机定位，而不是看它做多少次比较或加法。** 一个最小例子：全表扫描一张连续存放的表，是一次寻道 + 顺序读 b 块，代价约 t_S + b×t_T；而通过一个「未聚簇」的索引逐条回表取 b 行，最坏是 b 次随机 I/O，代价约 b×(t_S+t_T)——后者可能慢几十倍，这正是优化器有时宁可全表扫描也不走索引的原因（细节留 03-6/03-8）。易错点：这是**估算模型**，真实系统还有缓冲命中、预读、并发等因素，模型给的是数量级直觉而非精确秒数。

### 03-5.1.5 RAID：用多块盘换可靠性和/或吞吐

RAID（Redundant Array of Independent Disks）把多块物理盘组织成一个逻辑卷，用两种基本手法达成可靠性和性能：**条带化（striping）**把数据打散到多块盘上并行读写以提吞吐；**冗余**（镜像 mirroring 或校验 parity）用额外副本/校验信息，让坏一块盘时数据不丢。常见级别（DBSC ch12）：

RAID 0：纯条带化，无冗余——吞吐最高，任一盘坏则数据全失，不提供可靠性。

RAID 1：镜像，数据在两块盘各存一份——可靠、读可并行，但容量利用率仅 50%。

RAID 5：块级条带化 + 分布式奇偶校验（1 份校验散布各盘）——容错 1 块盘，容量利用率高，但「小写」需读改写校验（write penalty）。

RAID 6：双重分布式校验——容错 2 块盘同时坏，写代价更高。

RAID 10（1+0）：先镜像再条带化——兼顾可靠与性能，容量利用率 50%，是数据库常见选择。

初学者要把握的是 RAID 在解决两个不同问题：**磁盘会坏**（用冗余对抗）和**单盘不够快**（用并行对抗），不同级别是这两个目标间的不同折中。一个关键澄清：**RAID 不是备份**——它防的是「硬件坏一两块盘」，防不了「误删表」「勒索软件」「机房失火」，这些仍需独立备份和 03-11 的日志恢复机制。另一个易错点：RAID 5/6 的「小写惩罚」使其对写密集的 OLTP 未必友好，写多的场景常选 RAID 10。RAID 级别的数字**不表示优劣或高低**，只是不同方案编号。

## 03-5.2 缓冲区管理：buffer pool、pin/dirty、替换策略、steal/force

### 03-5.2.1 缓冲池（buffer pool）：内存里的页缓存

主存装不下整个数据库，DBMS 在内存里划出一大块固定区域叫**缓冲池（buffer pool）**，切成许多与磁盘页等大的**帧（frame）**。需要某页时，**缓冲管理器（buffer manager）**先查一张**页表（page table，或叫 buffer table）**看它是否已在某个帧里：命中就直接用；未命中就挑一个空帧（或按替换策略腾一个），把该页从磁盘读进来、登记进页表，再返回。上层代码只管「给我第 N 页」，搬运和缓存对它透明。

这是整个存储层的性能枢纽，初学者要理解它「像 CPU cache 之于内存，缓冲池之于磁盘」——都是「用一小块快存储缓存一大块慢存储里最近/最常用的部分」。关键收益：一页读进来后，接下来对它的多次访问全在内存完成，把昂贵的磁盘 I/O 摊薄。一个重要澄清（DBSC ch13 / CMU 15-445 L6 都强调）：**数据库通常自己管缓冲池，而不完全信任操作系统的文件缓存**，因为 DBMS 更懂自己的访问模式（哪页是索引根、哪个是顺序扫描的一次性页），能做出比 OS 通用 LRU 更聪明的替换与预读、并精确控制写回时机以配合恢复（见 03-5.2.5–03-5.2.6）。

### 03-5.2.2 pin 计数与脏位（dirty bit）：这页现在能不能被换出

每个帧带两个关键元数据。**pin 计数（pin count / 引用计数）**记录当前有多少个上层操作正在使用这页；pin 计数大于 0 的页**不能被换出**，否则正在读它的操作会拿到无效内存。用完必须 unpin。**脏位（dirty bit）**标记这页自读入后是否被修改过：脏页在被换出前**必须先写回磁盘**，干净页可直接丢弃（磁盘上还有一模一样的副本）。

给初学者的直觉：pin 是「租借中，别动」，dirty 是「改过了，扔之前记得存盘」。最常见的 bug 心智模型是——若替换策略换出了一个还被 pin 的页，等于把别人正用的桌子搬走；若换出脏页却忘了写回，改动就凭空丢失。所以任何替换策略在选「牺牲页」时，第一道硬约束永远是「只在 pin 计数为 0 的页里选」，其次才比较冷热。脏页写回还牵扯「什么时候写才安全」的问题，那属于 steal/force 与日志，见 03-5.2.6 并延伸 03-11。

### 03-5.2.3 替换策略之 LRU：淘汰最久没用的

当缓冲池满、又要读入新页时，必须挑一个帧腾出来，这就是**页替换策略（replacement policy）**。最经典的是 **LRU（Least Recently Used）**：淘汰「最久未被访问」的页，直觉是最近用过的近期还会再用（时间局部性）。实现上可用一个按访问时间排序的链表/队列：每次访问把该页移到「最新」一端，淘汰时取「最旧」一端。

初学者要理解 LRU 赌的是「局部性」——数据访问往往扎堆，刚碰过的页大概率马上又碰。它在很多负载上确实好用，是操作系统和数据库的默认直觉。但严格维护「访问顺序」代价不低（每次命中都要动链表、在高并发下还要加锁抢这条链表），所以真实系统常用更廉价的近似——见下一项的 Clock。另外 LRU 在某些数据库典型负载下会严重失灵，见 03-5.2.5。

### 03-5.2.4 替换策略之 Clock（第二次机会）：LRU 的廉价近似

**Clock（时钟 / second-chance）算法**用一个环形排列的帧和一根「表针」近似 LRU，代价远低。每帧一个**引用位（reference bit）**：访问该页时置 1。需要淘汰时，表针沿环前进，遇到引用位为 1 的帧就把它清 0 并跳过（给「第二次机会」），遇到引用位为 0 且未被 pin 的帧就选它淘汰，表针停在下一个位置备用。

理解要点：Clock 不精确记录「谁最久没用」，只用一个 bit 粗略区分「最近碰过 / 没碰过」，省掉了 LRU 每次命中都要重排链表的开销，在高并发下更友好——这正是它被广泛采用的原因。初学者可以把表针想成钟表指针扫一圈，引用位是「最近亮过灯」的标记，指针扫到亮灯的就熄灯放过、扫到不亮的就淘汰。它是「用极小的记账换接近 LRU 的效果」的典型工程折中。PostgreSQL 的缓冲区置换用的正是 Clock 的变体（clock-sweep，带使用计数），此处为交叉印证、非承重结论。

### 03-5.2.5 为什么 DBMS 不总用 LRU：顺序泛滥与领域知识

LRU/Clock 假设「最近用过的将再用」，但数据库有一类负载专门打脸：**顺序泛滥（sequential flooding）**。一次全表扫描把一大批只读一次的页灌进缓冲池，按 LRU 它们会占据「最近使用」端、把真正的热页（如常驻的索引上层）挤出去，而这些扫描页读完再也不用——命中率反而暴跌。这类场景下 **MRU（淘汰最近使用的）** 反而更优。

这就是「DBMS 要自管缓冲、而非照搬 OS 通用 LRU」的核心论据（DBSC ch13 / CMU 15-445 L6）：数据库知道「这是一次性的顺序扫描页」「那是索引根页要钉住」，能据此做区别对待——给顺序扫描单独的小缓冲环、给索引页更高优先级、显式 pin 关键页等。初学者的落点是：**没有一种替换策略在所有负载上最优**，通用近似（LRU/Clock）是默认，但数据库的价值恰在于用领域知识对特定访问模式做定向优化。这里只讲到入门直觉，具体引擎的多池/优先级实现属工程细节，不展开。

### 03-5.2.6 steal / no-steal 与 force / no-force：脏页何时能/必须落盘

缓冲管理还要和事务的原子性、持久性协调，由两条正交策略刻画。**steal vs no-steal**：允许把「未提交事务改过的脏页」换出并写到磁盘吗？允许叫 **steal**，不允许叫 **no-steal**。**force vs no-force**：事务提交时必须把它改过的所有页立刻强制写回磁盘吗？必须叫 **force**，不必须叫 **no-force**。四象限里，**no-steal + force** 最省恢复逻辑（未提交的改动从不上盘、已提交的一定在盘上），但性能差、大事务放不下缓冲；主流系统选 **steal + no-force**，性能最好，代价是崩溃后既可能有「未提交的改动已上盘」（需 **undo** 撤销）也可能有「已提交的改动还没上盘」（需 **redo** 重做）。

初学者先记住这张对应表，它是连接「缓冲管理」与「日志恢复」的桥：

steal ⟹ 崩溃恢复需要 undo（回滚已落盘的未提交改动）

no-force ⟹ 崩溃恢复需要 redo（重放已提交但未落盘的改动）

正因为选了 steal + no-force，才必须有**预写日志（WAL）**——先写日志再写数据页，用日志在崩溃后重建正确状态。为什么主流都这么选？因为 force 会把大量随机写塞进提交路径、no-steal 会限制事务大小，二者都严重伤性能；而 WAL 是顺序写、代价可控。这里点到即止，WAL、检查点、ARIES 三趟恢复的完整机制留 **03-11 日志与恢复**。易错点：steal/force 是关于「数据页」何时落盘的策略，别和「日志」何时落盘混淆——WAL 恰恰要求日志先于数据页落盘。

## 03-5.3 记录组织：定长记录、变长记录、slotted page、大对象

### 03-5.3.1 定长记录：字段挨着放，按偏移直接定位

一条**记录（record）**就是一个元组在页里的字节表示。若所有字段类型定长（如 `INTEGER`、`CHAR(n)`），整条记录长度固定，做法最简单：把各字段按 schema 顺序紧挨排列，记录 i 从字节偏移 i × 记录长度 开始。定位第 k 个字段只需加一个编译期已知的偏移量，无需扫描。

定长记录的好处是「随机访问快、页内排布简单」——像数组一样按下标算地址。初学者的落点：定长布局把「找第几条记录 / 第几个字段」变成纯算术，没有任何搜索。但它有两个代价：其一，`CHAR(n)` 这类定长字符串要按最大长度补白（padding），短值浪费空间；其二，删除记录会在页中间留「洞」，要么用空闲链表串起这些洞复用、要么把后面记录搬上来压紧（搬移代价高）。真实数据里变长字段（`VARCHAR`、`TEXT`）极普遍，所以纯定长布局远不够用，引出下面的变长记录。

### 03-5.3.2 变长记录：null 位图 + 变长字段的偏移-长度表

当记录含变长字段（`VARCHAR`/`TEXT`/`BLOB`）或可空字段时，记录长度不再固定。通行做法是把记录分成两段：前段是**定长部分**——所有定长字段的值，加上一个 **null 位图（null bitmap）** 标记哪些字段为 NULL，再加上每个变长字段的 **(偏移, 长度)** 二元组指针；后段是**变长部分**——把各变长字段的实际字节依次堆在记录尾部，由前段的 (偏移,长度) 指向。

这样布局的巧思在于：**定长部分本身又变回了定长**，于是「记录头 + 定长字段 + 变长字段的指针」这一段可以像定长记录一样按偏移直接读取，只有真正的变长数据放在后面、通过指针间接访问。初学者要抓住两个设计点：一是 **null 位图**用每字段 1 bit 表示是否为 NULL，NULL 值本身不占数据空间（省掉存储且区分「空串」与「NULL」）；二是变长字段用「指针 + 数据分离」避免了「一个字段变长导致后面所有字段偏移都要重算」。易错点：不同引擎的记录头字段（版本/事务可见性信息、null 位图位置）细节各异——例如 PostgreSQL 每条堆元组有 23 字节的 `HeapTupleHeader`（含 xmin/xmax 等 MVCC 信息）——这些属实现细节，原理层记住「定长头 + null 位图 + 变长指针 + 变长数据」即可。

### 03-5.3.3 slotted page：页内用一张 slot 目录间接指向每条记录

一个页里要放多条变长记录、还要支持增删，直接紧挨排布会因删除留洞、因变长难以定位。业界标准解法是 **slotted page（槽式页 / 分槽页）**：页头之后是一个**槽目录（slot array / line pointer array）**，每个槽存一条记录的 **(页内偏移, 长度)**；实际记录数据从**页的尾部往前**堆放。查一条记录先读它的槽拿到偏移，再按偏移取数据。

这个结构是页内组织的「事实标准」，初学者务必吃透它解决的三个问题。第一，**变长记录定位**：外部只需记「第几号槽」，不必知道记录的物理字节位置。第二，**记录可在页内自由移动**：整理碎片（compaction）时把记录搬来搬去压紧空闲空间，只需更新槽里的偏移，**槽号不变**——所以指向记录的外部引用（记录 ID，见 03-5.4.4）能保持稳定。第三，**删除留洞可回收**：删记录标记其槽为空、数据留洞，之后整理时回收。一个精确的记账细节：槽目录从页头**向后（向下）生长**，记录数据从页尾**向前（向上）生长**，两者相向而行，中间是空闲空间，当它们相遇即页满。这个「两端相向生长、中间空闲」的布局在 03-5.4.2 会用 PostgreSQL 的真实页头字段（pd_lower/pd_upper）再看一遍。

### 03-5.3.4 大对象：一页放不下的字段怎么办（规范 vs 实现，两边都记）

一个字段可能大到远超一页（几 KB 甚至几 MB 的文本、图片、JSON）。因为记录通常要求「整条落在一页内」，超大字段必须**移到主页之外单独存**，主记录里只留一个指向它的引用。这是本大主题「规范 vs 实现」分歧最明显处，两大主流引擎机制不同，两边都记、点明、不和稀泥。

**PostgreSQL —— TOAST（The Oversized-Attribute Storage Technique）**。当一行的总宽度超过阈值 `TOAST_TUPLE_THRESHOLD`（默认约 2 kB，即 2048 字节；PostgreSQL 默认页 `BLCKSZ` 为 8 kB = 8192 字节）时触发：先尝试**行内压缩**，仍放不下就把大字段**移到该表专属的 TOAST 附表**、切成每块至多 `TOAST_MAX_CHUNK_SIZE`（默认约 2000 字节，使 4 块正好填满一页）的**分块（chunk）**存储，主行里只留一个指针（TOAST pointer）。每个 TOAST 化字段有四种存储策略：

PLAIN：既不压缩也不移出行（不可 TOAST 的类型只能用它）。

EXTENDED：可压缩、可移出行——大多数可 TOAST 类型的**默认**策略（先压缩、不够再移出）。

EXTERNAL：可移出行、不压缩——牺牲空间换 `text`/`bytea` 的子串操作速度。

MAIN：可压缩、尽量不移出行（迫不得已才移出）。

**SQLite —— 溢出页（overflow page）**。SQLite 把每行存进 B-tree 的 cell，一个 cell 若装不下整行 payload（页放不下），就把超出部分链到一串**溢出页（overflow pages）**上，主 cell 里存前一部分 + 指向溢出页链表的指针，溢出页之间用 4 字节前置指针串成链。SQLite 默认页大小自 **3.12.0（2016-03-29）起为 4096 字节**（此前为 1024 字节）。SQLite **没有 TOAST 式的按列压缩策略**，也没有独立附表，就是朴素的「装不下就往溢出页链上接」。

分歧点讲清楚给初学者：**都是「大字段移出主页、主页留指针」的思路，但实现路子不同**——PostgreSQL 用一张独立 TOAST 附表 + 可选压缩 + 四种可调策略，粒度是「列」；SQLite 用行内 cell 溢出到页链，无压缩策略，粒度是「整行 payload 的溢出部分」。本机 SQLite 3.45.1 实证坐实了溢出页机制（内存/文件库，基线 Py3.11.15 @2026-07-29）：建 `r(a INTEGER PRIMARY KEY, b TEXT)`，插入一条 5000 字节的 `b`（超过 4096 页），查系统虚表 `dbstat`：

SELECT name, pageno, pagetype, ncell, payload FROM dbstat WHERE name='r';

真实输出：

('r', 2, 'leaf', 2, 917)

('r', 3, 'overflow', 0, 4092)

即该表占了一个 `leaf` 页和一个 `overflow` 页——5000 字节的大字段确实溢出到了独立的溢出页（pagetype='overflow'），与文档描述一致。默认 `PRAGMA page_size` 实测为 4096，印证 3.12.0 后的默认值。易错点：PostgreSQL 的 2 kB 是**行触发阈值**、SQLite 的溢出触发点由**页大小**决定，二者不可混谈；具体阈值/块大小请以对应版本官方文档为准（本报告数值取自 PostgreSQL 17 与 SQLite 3.45 官方文档，已注版本）。

## 03-5.4 页与文件组织：heap file、页内布局、空闲空间管理

### 03-5.4.1 文件组织：一张表怎么由许多页组成

一张表（关系）在物理上是一个或多个**文件**，文件是许多等大页的序列。页里如何安放记录、页与页如何组织，有几种典型的**文件组织（file organization）**：**堆文件（heap file）**——记录无序，新记录塞进任何有空闲空间的页，最通用、插入快，但按某条件查找需扫描；**顺序文件（sequential file）**——记录按某个搜索键排序存放，范围查询与顺序读友好，但插入要维护有序（常配溢出块）；**散列文件（hashing）**——按键的散列值决定落在哪个桶/页，等值查找快。DBSC ch13 还讲**多表聚簇**（把相关多表的记录存在同一页以省连接 I/O）。

初学者先建立「表 = 一摞页，页里放记录，页外有个组织方式」的分层图景。**堆文件是绝大多数关系型引擎的默认表组织**（如 PostgreSQL 的表就是 heap，故其存储文件层文档称 heap），因为它插入简单、对任意查询都能配合索引工作——「怎么快速找」的活儿交给索引（03-6），表本身保持无序堆。要点澄清：**「文件组织」（表本身怎么排）与「索引」（另建的查找结构）是两回事**——一张堆表可以额外挂多个 B+树索引；也有引擎让主键索引直接把整表数据聚簇进 B+树叶子（如 InnoDB 聚簇索引），那是 03-6 的话题。本节聚焦最基础的堆文件 + 页内布局。

### 03-5.4.2 页内布局：页头 + 槽目录 + 空闲空间 + 记录（PostgreSQL 实例）

一个页从头到尾通常分四段：**页头（page header）**（存元数据：空闲空间边界指针、校验和、LSN 等）、**槽目录 / 行指针数组**（从页头向后生长）、**空闲空间**（中间）、**记录数据**（从页尾向前生长）。这正是 03-5.3.3 slotted page 的完整形态。PostgreSQL 17 的堆页布局是一个精确可查的真实例子：页头 `PageHeaderData` 占 24 字节，其后是每项 4 字节的**行指针数组（ItemIdData，即 line pointer）**，每项存一条元组的 (偏移, 长度)；行指针从页头**向后**生长，实际元组从页尾**向前**填充，中间空闲。页头里两个关键指针刻画边界：

pd_lower：指向空闲空间的起点（= 行指针数组的末端，新增行指针从这里往后长）

pd_upper：指向空闲空间的终点（= 已放元组区的起点，新元组从这里往前放）

当 pd_lower 与 pd_upper 相遇，页即放满。页尾还有一段 `special space`，普通表为空、索引页用来放 B+树兄弟指针等（`pd_special` 指向它）。

给初学者的落点：**把抽象的 slotted page 对到一个真系统的字段上，机制就落地了**——「槽目录向下长、记录向上长、中间空闲」对应「pd_lower 向下移、pd_upper 向上移、中间是 free space」。行指针一旦分配就**不再移动**（这样 CTID 引用稳定），元组本身可在页内搬移压缩碎片。易错点：24 字节页头、4 字节行指针、8 kB 页是 PostgreSQL 的实现值，别当成所有数据库的通用常数；SQLite 的页头结构（B-tree page header 8 或 12 字节 + cell 指针数组）又不一样。原理通用、字节数因实现而异。

### 03-5.4.3 空闲空间管理：怎么快速找到「有地方插」的页

堆文件插入新记录时要找一个「还装得下」的页，逐页扫描太慢，于是需要**空闲空间记账**。常见做法：**空闲空间图（Free Space Map, FSM）**——单独用一小组页记录每个数据页大约还剩多少空闲，插入时先查 FSM 直接跳到够用的页；或**空闲页链表 / page directory**——把有空闲的页用链表或目录串起来。页内部则用 03-5.3.3 的槽机制回收删除留下的洞。

理解动机：没有空闲空间记账，一次插入最坏要扫遍全表找空位；有了 FSM/目录，插入近似 O(1) 定位。PostgreSQL 为每个表维护一个 `_fsm` 分支文件（Free Space Map）正是此机制的真实实现（交叉印证，非承重）。初学者要注意「两级空闲管理」：**页间**（哪一页有空——FSM/目录负责）与**页内**（页里哪段字节空——槽目录 + 整理负责），二者配合才能高效复用删除/更新腾出的空间。易错点：更新一条变长记录若变长了、当前页放不下，可能要「删旧插新」搬到别的页（PostgreSQL 的非 HOT 更新即如此），这会牵动空闲空间管理和索引——细节属 MVCC/更新路径，留 L6-04 §04-9，本节只点到。

### 03-5.4.4 记录 ID（RID/TID/CTID/rowid）：指向一条记录的稳定地址

外部（尤其索引）要指向表里某条具体记录，用的是**记录标识符**，通常是一个 **(页号, 槽号)** 二元组：页号定位到哪一页，槽号在该页的槽目录里定位到具体记录。PostgreSQL 叫 **CTID = (block number, line pointer index)**，SQLite 的表有隐藏的整型 `rowid` 作主行标识。因为定位走的是「槽号」而非物理字节偏移，记录在页内被整理搬移时地址保持不变（03-5.3.3 已铺垫）。

这个概念是连接本大主题与索引（03-6）的关键接口：**索引的叶子里存的往往就是记录 ID**，查到键后凭记录 ID「回表」到堆里取整行。初学者记住「(页号, 槽号) = 一条记录的门牌号」即可。一个重要澄清与易错点：记录 ID 的稳定性是**页内**的（整理不变它），但记录若因更新变大被迁到**别的页**，其 CTID 会变——PostgreSQL 用「行指针重定向」等手段处理，InnoDB 的二级索引干脆存主键而非物理地址来回避这问题。这些取舍属聚簇/二级索引与 MVCC 话题，分别留 03-6 与 L6-04，本节只确立「记录 ID = (页,槽)、是索引回表的落点」这一入门概念。

## 03-5.5 元组存储模型：行存（NSM）默认布局

### 03-5.5.1 NSM（N-ary Storage Model）：一整行的所有列挨着放

**元组存储模型**指「同一页里，多条元组的各列在字节上如何摆放」。最传统、也是 OLTP 引擎默认的是 **NSM（N-ary Storage Model，行存 / row store）**：一条元组的所有列**连续存在一起**，一条接一条填进页（配合 03-5.3–03-5.4 的变长记录 + slotted page）。取一整行只需读它所在的那一小段连续字节，一次到位。

初学者抓住一句话：**行存 = 「以行为单位打包」**，想象电子表格里一行的所有单元格被装进一个信封、信封一个个码进页。它的强项正对 OLTP 的胃口——事务型负载多是「按主键取/改整行」「插入整行」，行存下这些操作只碰一个页里的一小段连续数据，读写都高效。PostgreSQL、SQLite、MySQL/InnoDB 等 OLTP 主力默认都是行存。这也解释了为什么前面几节（变长记录、slotted page、TOAST/overflow）讲的都天然是行存布局——它们本就是行存的组织手段。

### 03-5.5.2 行存的代价与边界：为什么还要有列存（下沉 L6-04 §04-2）

行存的弱点在**分析型查询**：像「对一亿行只求某一列的平均值」这种，行存被迫把每行的**所有列**都从磁盘读进来、再从每行里挑出那一列——白读了大量无关列的字节，浪费 I/O 和缓存带宽，且同列的值散在各行、难以用压缩和 SIMD 批量算。针对 OLAP，业界用**列存（DSM，列式存储）**——把同一列的值连续存在一起——和 **PAX** 等行列混合布局来解决，配合按列压缩编码大幅省 I/O。

这正是本报告的显式边界：**列存（DSM）、PAX 混合布局、字典/RLE/位图等轻量压缩编码，属于分析型引擎的存储优化，全部下沉到 L6-04 §04-2「列存布局与压缩编码」**，本报告不展开，只在此点明「行存不是唯一选择、OLAP 场景常用列存，二者是面向不同负载（OLTP vs OLAP）的存储模型分工」。给初学者的收束直觉：**存储布局的选择本质是「一次 I/O 该带回哪些字节最划算」——OLTP 要整行，故行存；OLAP 要整列，故列存。** 记住这条对立，就能理解为什么同一份逻辑数据会有两种截然不同的物理摆法，以及为什么现代系统（HTAP）想同时要两者（亦留 L6-04）。
