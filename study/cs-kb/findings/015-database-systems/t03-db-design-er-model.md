E-R 模型解决的是数据库设计里最靠前的一步：在写任何一行 SQL 之前，先把「现实世界里有哪些东西、它们有什么性质、彼此怎么关联」用一张图描述清楚。这张图（E-R 图）只有三种基本积木——**实体**（现实中可区分的对象，如一个学生、一门课）、**属性**（对象的性质，如学号、姓名）、**联系**（对象之间的关联，如「学生选课」）——加上一层约束（一个学生能选几门课、每门课必须有老师吗）。E-R 图不依赖任何具体数据库产品，是「概念层」的设计；画好之后，有一套固定的转换规则能把它机械地变成关系模式（一堆表），这才进入 03-1/03-2 的关系世界。

本报告有一条贯穿的心智模型，**E-R 建模是「先画图后建表」：图上的每个实体集大体对应一张表，每条联系要么并进已有的表、要么单独成一张表，映射基数与参与约束决定外键放哪、能不能为空。** 因此把 03-3.1（三种积木）和 03-3.2（约束）想清楚，03-3.4（转换成表）几乎是水到渠成的机械操作；03-3.3 是三种进阶积木（弱实体、泛化、聚集），03-3.5 则是「同一个需求可以画成好几种图，怎么选」的经验判断。

## 03-3.1 E-R 基本构件：实体集、属性（简单/复合/多值/派生）、联系集

### 03-3.1.1 E-R 模型在设计流程中的位置：概念建模

E-R 模型（Entity-Relationship model）是一种**概念数据模型**，用来在数据库设计的早期阶段，把现实世界的信息需求刻画成一张由实体、属性、联系构成的图。DBSC 7e 把整个设计流程分成几个阶段：先做**需求分析**（搞清用户要存什么、查什么），再做**概念设计**（用 E-R 图把需求画出来，本大主题的核心），然后做**逻辑设计**（把 E-R 图转成具体数据模型下的模式，对关系数据库就是一堆关系模式，即 03-3.4），最后做**物理设计**（索引、存储布局，归 03-5/03-6）。E-R 图是概念设计阶段的主要产物。

初学者最该建立的定位是「E-R 图是给人看的、关系模式是给机器建表用的」。概念设计之所以要单独拉出来先做，是因为它**不牵扯任何数据库产品的细节**——不管你最后用 MySQL、PostgreSQL 还是别的，先把「业务里有学生、有课、学生选课、每门课有先修课」这类事实画清楚，是与实现无关的一步。这一步做错（比如漏了一个实体、把两个不同的东西混成一个），后面建表、写查询、加约束全会跟着错，且越往后改代价越大。所以 E-R 阶段的目标是「把需求想对、想全」，而不是追求画得多花哨。E-R 是**概念建模**，没有单一标准实现——不同教材、不同工具的记号和转换细节都略有出入，这一点贯穿全篇。

### 03-3.1.2 实体与实体集：现实中「可区分的对象」及其同类集合

**实体（entity）** 是现实世界中一个可以和其它对象区分开的「东西」，可以是具体的（某个学生、某本书），也可以是抽象的（一次贷款、一门课程）。**实体集（entity set）** 是具有相同属性（相同性质结构）的一批实体构成的集合，例如「所有学生」构成实体集 `student`，「所有教师」构成 `instructor`。实体集是 E-R 图的一级公民，实体本身通常不单独画，画的是实体集。

初学者最容易混的是「实体」与「实体集」这对词，它们的关系正好对应 03-1 里「元组」与「关系」、也对应编程里「对象」与「类」：实体集是模板（学生这一类），实体是模板的一个具体化身（学号 202301 的那个张三）。所以说「实体集 student 有三个属性」是对的（说的是结构），说「实体 张三 是一个实体集」就是错的（张三是一个实体，不是一集）。另一个要点是「可区分」：实体集里两个不同实体必须能被区分开——这就要求实体集像关系一样有能唯一标识每个实体的属性组（键，见 03-3.2.4）。在 DBSC 7e 记号里，实体集画成一个**矩形**，矩形内分两栏，上栏写实体集名、下栏列出它的属性。

### 03-3.1.3 属性与域：实体集的每个属性映射到一个取值域

**属性（attribute）** 是实体集的一个描述性性质，实体集里每个实体都为每个属性取一个值。每个属性关联一个**域（domain / value set）**，即该属性允许取的值的集合（如 `age` 的域是非负整数）。形式上，一个属性可看作从实体集到其域的一个函数：给定一个实体，返回它在该属性上的取值。例如 `student` 实体集可能有属性

student = (ID, name, dept_name, tot_cred)

每个学生在 `ID` 上取一个学号、在 `name` 上取一个姓名，以此类推。

这里的「属性/域」与 03-1 关系模型里的「属性/域」是同一套概念，只是这里是画在图上的概念层版本，转换成表后就变成表的列（03-3.4.1）。初学者要注意「属性是实体集的性质，不是实体的性质」这个说法的分寸：属性定义在实体集层面（学生这一类都有姓名这个属性），取值发生在实体层面（张三这个学生的姓名取「张三」）。域的作用是划定合法取值范围，落到表里会体现为列的数据类型和 `CHECK` 约束（归 03-2.1）。E-R 阶段一般只需说清「有哪些属性、大致什么类型」，精确的类型/约束留到逻辑与物理设计。

### 03-3.1.4 简单属性 vs 复合属性：属性能不能再拆成更小的部件

**简单属性（simple / atomic attribute）** 是不可再分的属性（如 `age`、`ID`）。**复合属性（composite attribute）** 是可以进一步拆成若干子部件的属性，每个子部件本身又是一个属性。典型例子是 `name` 拆成 `first_name / middle_name / last_name`，或 `address` 拆成 `street / city / state / zip`，其中 `street` 还能再拆成 `street_number / street_name / apt_number`（复合属性可以嵌套）。在 DBSC 7e 记号里，复合属性画成把子属性缩进列在父属性名下面。

复合属性的意义是「让设计者选择粒度」：如果业务只会整体使用一个地址、从不单独查「城市」，那把 `address` 当简单属性（一个字符串）就够；但如果要「按城市统计用户」，就该把它建成复合属性、拆出 `city` 子属性，将来才好单独查询。初学者的落点是——复合属性是**设计时的分组表达**，它在转换成关系模式时会被「摊平」：只保留叶子层的简单子属性作为表的列，父属性名本身不建列（03-3.4.2）。也就是说 `name(first, last)` 最终变成表里的 `first_name` 和 `last_name` 两列，没有单独的 `name` 列。

### 03-3.1.5 单值属性 vs 多值属性：一个实体在该属性上能取几个值

**单值属性（single-valued attribute）** 对每个实体只取一个值（如一个学生只有一个 `ID`）。**多值属性（multivalued attribute）** 允许一个实体在该属性上同时取多个值，典型如一个人的 `phone_number`（可能有手机、家庭、办公多个号码）或 `email`。在 DBSC 7e 记号里，多值属性用花括号包住属性名表示：

{phone_number}

多值属性是初学者最容易埋雷的地方，因为它**在关系模型里没有直接对应物**——关系要求每个属性位置只放一个原子值（第一范式，归 03-4.3），不能在一个单元格里塞多个电话号。所以多值属性在转换时必须「拆出去」：为它单独建一张表，表里每个电话号占一行，通过外键指回原实体（03-3.4.2）。这也解释了为什么 E-R 阶段允许多值属性、而关系阶段不允许——概念层可以更贴近人的直觉（一个人本来就可能有多个电话），逻辑层再用规范化的表结构去实现它。判断依据是「同一时刻这个性质会不会有多个值」：会，就是多值。

### 03-3.1.6 派生属性：值可由别的属性算出来，不必存

**派生属性（derived attribute）** 是其值可以从其它相关属性或实体计算得到、因而不必真正存储的属性。经典例子是 `age`（年龄），它可以由 `date_of_birth`（出生日期）和当前日期算出；再如「一个教师带的学生数」可由联系算出。与之相对，`date_of_birth` 这种必须实际存下来的叫**基属性（base / stored attribute）**。在 DBSC 7e 记号里，派生属性在属性名后加一对圆括号表示：

age ( )

派生属性的核心权衡是「存还是算」：存下来（物化）读得快但会随时间过期（今天算对的年龄明天就错了，得维护），每次现算不会过期但要花计算。派生属性在概念图上明确标出来，是提醒设计者「这个值别真存，或存了要负责更新」。初学者要把它和「多值」「复合」区分开：这三者是**属性的三个正交维度**——一个属性可以同时是「复合的、多值的」（比如一个人有多个地址，每个地址又是复合的），派生只是说它的值来源是「算」而非「存」。转换成关系模式时，派生属性通常**不建列**，改由视图或查询时计算给出（03-3.4.2）。

### 03-3.1.7 联系与联系集：实体之间的关联及其「度」

**联系（relationship）** 是若干实体之间的一个关联，**联系集（relationship set）** 是同类联系的集合。例如「教师 12345 指导学生 98765」是一个联系，所有这样的「指导」联系构成联系集 `advisor`。形式上，一个联系集是若干实体集上的一个数学关系：

advisor ⊆ { (i, s) | i ∈ instructor, s ∈ student }

即联系集的每个成员是一个由各参与实体各取一个凑成的元组。参与一个联系集的实体集**个数**叫这个联系的**度（degree）**：两个实体集之间的是**二元联系（binary）**，三个的是**三元（ternary）**，一般 n 个的是 **n 元（n-ary）**。在 DBSC 7e 记号里，联系集画成一个**菱形（diamond）**，用线连到它所关联的各实体集矩形。

初学者要抓住「联系是动词、实体是名词」这个直觉：`student`（学生）、`course`（课）是名词/实体，`takes`（选修）是把它们关联起来的动词/联系。绝大多数现实联系是二元的（两方之间），这也是为什么后面约束、转换的讨论都以二元为主。三元及以上联系存在但较少、也更难想清楚（一个「医生-病人-药品」的开药联系是真三元，还是能拆成几个二元？这属于 03-3.5.3 的设计取舍）。另一个关键点是**同一个实体集可以在一个联系里出现多次并扮演不同角色**（递归联系，见 03-3.3.5），例如「课程」和「课程」之间的「先修」联系。

### 03-3.1.8 联系集的描述性属性：属性也可以挂在联系上

联系集本身也可以带**描述性属性（descriptive attribute）**——描述的不是某一方实体、而是「这段关联」本身的性质。经典例子：`takes`（学生选课）这个联系集可以带属性 `grade`（成绩）——成绩既不属于学生本身、也不属于课程本身，而属于「某学生选了某课」这一具体关联。再如 `works_on`（员工参与项目）可带 `hours`（投入工时）。在 DBSC 7e 记号里，联系的属性画成挂在菱形上的属性框。

理解「描述性属性该挂在哪」是 E-R 建模的一个核心判断（详见 03-3.5.4）。判据是「这个值由谁唯一决定」：`grade` 不能只由学生决定（同一学生不同课成绩不同），也不能只由课程决定（同一课不同学生成绩不同），它由「学生+课程」这对组合共同决定，所以它属于联系而非任何单个实体。初学者易犯的错是把这类属性硬塞进某一方实体（比如给 `student` 加个 `grade` 列），结果一个学生选多门课时就存不下多个成绩了。一个重要限制：**在二元的一对多/一对一联系里，联系属性可以搬到「多」的那一端实体上**（因为那一端每个实体最多参与一次联系，值不会冲突），但在多对多联系里必须留在联系上——这条规则直接决定了 03-3.4.4 的联系表能否被消除。

### 03-3.1.9 E-R 图记号：DBSC 7e 画法与 Chen / UML / crow's-foot 对比

E-R 图**没有统一的国际标准记号**，主流有四套并存的画法，语义相通但符号差别很大，读图时必须先弄清用的是哪一套。**DBSC 7e 记号**（本报告采用）：实体集是**矩形**（分两栏，上名下属性，主键属性加下划线）；联系集是**菱形**；属性直接列在实体矩形内（复合属性缩进、多值属性加花括号 `{ }`、派生属性加圆括号 `( )`）；映射基数用**有向线（箭头 →）表示「一」、无向线表示「多」**；全部参与用**双线**。**Chen 1976 原始记号**：实体是矩形、联系是菱形（这点与 DBSC 一致），但**属性画成椭圆（oval）用线连到实体/联系**（多值属性双椭圆、派生属性虚线椭圆），基数在联系两侧的线上标 `1` / `N` / `M` 等数字。**Crow's-foot（乌鸦脚）记号**：实体是矩形（属性列在内），联系直接用**连线**表示、线的端点用「乌鸦脚」符号（三叉）表示「多」、竖杠表示「一」、圆圈表示「可选（零）」，非常紧凑，在工程/工具（如 dbdiagram、ERwin）里最常见。**UML 类图**：实体集≈类（class 矩形，属性列在框内），联系≈类之间的**关联（association）线**，基数用 `1`、`0..1`、`*`、`1..*` 等**多重性（multiplicity）** 标注写在线的两端。

给初学者的落点是「别背符号，先认语义」。四套记号表达的是同一批概念（实体、属性、联系、基数、参与），差别只在「用椭圆还是直接列属性」「用箭头还是数字还是乌鸦脚表示基数」。最容易踩的坑是**基数标注的位置约定相反**：DBSC/Chen 系里把基数标在「靠近对应实体那一侧」，而 UML/crow's-foot 里多重性写在「线的另一端」，同一张关系图用两套记号画出来，`1` 和 `N` 的位置看起来会像调换了——所以拿到一张 E-R 图，第一件事是确认它的记号体系。本课以 DBSC 记号为准，但工作中遇到 crow's-foot 和 UML 的概率同样很高，认得出即可。

## 03-3.2 约束：映射基数（1:1/1:N/M:N）、参与约束、键约束

### 03-3.2.1 映射基数总述：一方实体能关联到对方几个实体

**映射基数（mapping cardinality / cardinality ratio）** 描述一个二元联系集中，一方的一个实体最多能与另一方的多少个实体发生联系。对实体集 A、B 之间的联系，有四种：**一对一（1:1）**——A 的一个实体最多关联 B 的一个、且反之亦然；**一对多（1:N）**——A 的一个实体可关联 B 的多个，但 B 的一个只关联 A 的一个；**多对一（N:1）**——1:N 的镜像；**多对多（M:N）**——两边都可关联对方多个。

映射基数是 E-R 图上信息量最大的约束，因为它直接决定后面「联系怎么转成表、外键放哪、能不能合表」（03-3.4.4）。初学者建立直觉最好的办法是各举一例：一个国家一个首都、一个首都属一个国家，是 **1:1**；一个系有多名教师、一名教师属一个系，是 **1:N**（系对教师）；一个学生选多门课、一门课被多个学生选，是 **M:N**。要点是「基数是对**这个联系**说的，不是对实体本身说的」——同样是学生和课程，「选修」联系是 M:N，但假如再加一个「课代表」联系（一门课一个课代表、一个学生只当一门课的课代表）那就是 1:1。所以先说清「哪个联系」，再判基数。

### 03-3.2.2 各基数的含义与画法：箭头表「一」

在 DBSC 7e 记号里，映射基数靠联系菱形连到实体的**线上有没有箭头**来表达：**有向线（箭头 →）指向某实体集，表示「对方的每个实体最多关联这一侧的一个实体」**（即这一侧是「一」）；**无向线（普通线 —）表示「多」**。于是四种基数画法是：

1:1 —— 两条连线都带箭头（两侧都是「一」）

1:N（A 一、B 多）—— 指向 A 的线带箭头、指向 B 的线不带

M:N —— 两条连线都不带箭头（两侧都是「多」）

例如学生与导师的 `advisor` 联系，若「一个学生最多一个导师、一个导师带多个学生」，则从菱形到 `instructor` 的线带箭头（instructor 侧为「一」）、到 `student` 的线不带。

初学者要牢记 DBSC 这套是「**箭头 = 一（at most one）**」，方向指向被限制成「至多一个」的那一侧——这与直觉上「箭头指向多」正好相反，是最常见的读图错误来源。而且这套与 Chen 记号（在线上直接标 `1`/`N` 数字）、crow's-foot（乌鸦脚三叉表示多）画法完全不同（见 03-3.1.9），换记号就换读法。判断基数时的实用问法是两句：「A 的一个能连几个 B？」和「B 的一个能连几个 A？」——各自答「一个」或「多个」，组合起来就是基数。

### 03-3.2.3 参与约束：全部参与 vs 部分参与

**参与约束（participation constraint）** 描述一个实体集里的实体是否**必须**参与某个联系。**全部参与（total participation）**：实体集中的每个实体都至少参与该联系一次（该实体集「不能有孤儿」）。**部分参与（partial participation）**：实体集中允许有实体不参与该联系。在 DBSC 7e 记号里，全部参与用实体集到联系菱形之间的**双线**表示，部分参与用单线。

参与约束和映射基数是两个**正交**的维度，初学者极易把它们混为一谈：映射基数管「参与的话最多连几个」，参与约束管「必不必须参与」。举例：`student` 与 `advisor`——「一个学生必须有导师吗？」若规定每个学生都必须有导师，则 `student` 全部参与（双线）；「一个教师必须带学生吗？」若允许有教师暂时不带学生，则 `instructor` 部分参与（单线）。这两条合起来才完整描述一端的约束（既说「最多几个」又说「至少几个」），也直接决定转换成表后**外键列能不能为 NULL**（全部参与 → 外键非空，见 03-3.4.4）。更一般地，有些记号（如 UML/crow's-foot、以及 DBSC 提到的「基数区间」写法）用 `l..h`（下界..上界，如 `1..*` 表示「至少一个、至多多个」）把参与和基数一次写全，`0` 下界即部分参与、`1` 下界即全部参与。

### 03-3.2.4 键约束：实体集的主键与联系集主键的构成

**键（key）** 的概念从 03-1 关系模型平移到 E-R：实体集也有超键、候选键、主键——一组能唯一标识实体集中每个实体的属性。实体集的主键在 E-R 图里用**给主键属性加下划线**表示。联系集的键更微妙：一个（二元）联系集的候选键，由其**参与实体集的主键的并集**决定，具体取哪些取决于映射基数：

- M:N 联系：主键 = 两端实体集主键的**并集**（要两个才能唯一定位一条联系）。
- 1:N 联系（N 侧为 many）：主键 = **「多」侧实体集的主键**（因为多侧每个实体最多参与一次，用它就能定位）。
- 1:1 联系：任一端实体集的主键都可作候选键。

以 `takes(student, course)` 为 M:N 例，一条选课联系要靠「学号 + 课程号」才能唯一确定，所以联系主键是二者并集；而 `advisor` 若是「学生:导师 = N:1」，则用学号就能唯一定位一条 advisor 联系，联系主键就是学号。

初学者要抓住「联系的键由基数决定」这个规律，它是 03-3.4.3/03-3.4.4「联系表主键怎么取、能不能被消除」的直接依据：正因为 1:N 联系的键只是多侧主键，这条联系才可以不单独建表、而把外键塞进多侧实体表里（合表）。反过来 M:N 联系的键需要两端主键，无法塞进任何单方，必须单独成表。另一个易错点：联系集本身**不能凭空引入新的键属性**（联系没有自己的「身份证」），它的身份完全由参与实体的主键拼出来（描述性属性如 `grade` 不参与构成键）。

## 03-3.3 高级建模：弱实体集、泛化/特化/聚集、角色

### 03-3.3.1 弱实体集：靠「主人」才能被唯一标识的实体

**弱实体集（weak entity set）** 是自身没有足够属性构成主键、必须依附于另一个（强）实体集才能被唯一标识的实体集。它依附的那个实体集叫**标识实体集 / 属主（identifying / owner entity set）**，连接二者的联系叫**标识联系（identifying relationship）**。弱实体集自己有一个**判别式 / 部分键（discriminator / partial key）**——只能在同一属主下区分不同弱实体、但全局不唯一的属性。弱实体集的完整主键 = 属主的主键 + 自己的判别式。在 DBSC 7e 记号里，判别式用**虚线下划线**标注。

经典例子：`section`（某门课的某个开课班次，如「数据库-2026春-01班」）。班次号 `sec_id`（01、02……）只在**同一门课内部**能区分不同班次，光看「01班」不知道是哪门课的 01 班——所以 `section` 是弱实体集，依附于强实体集 `course`，`sec_id` 是判别式，`section` 的主键要写成「课程号 + sec_id」。初学者判断弱实体集的信号是「这东西的编号是相对某个上级从头数的」——发票的行号（相对发票）、订单的明细项（相对订单）、大楼的房间号（相对大楼）都是典型弱实体。要点有二：其一，弱实体集**总是全部参与**标识联系（弱实体离了属主没法存在，双线），且它对标识联系的基数总是「多」对「一」（多个弱实体属于一个属主）；其二，别把弱实体和「有外键的普通实体」混了——区别在于弱实体**连自己的主键都凑不齐**，必须借属主的主键来拼，而普通实体有自己独立的主键、外键只是额外引用。

### 03-3.3.2 泛化与特化：ISA 层次与属性继承

**特化（specialization）** 是自顶向下地把一个实体集划分成若干**子实体集（subclass）**，每个子集有超集所没有的额外属性；**泛化（generalization）** 是自底向上的反向过程——把几个有共性的实体集抽象成一个**超实体集（superclass）**。二者是同一层次关系的两个方向，这种「A 是一种 B」的关系叫 **ISA 联系**（读作「is-a」）。核心机制是**属性继承（attribute inheritance）**：子实体集自动拥有超实体集的全部属性，以及它参与的联系。在 DBSC 7e 记号里，ISA 用一个标注 `ISA` 的三角形连接超类与子类。

举个例子，超类 `person`（有 ID、name、address），特化出子类 `student`（额外有 tot_cred）和 `employee`（额外有 salary）——学生和员工都「是一种」人，自动继承 name/address，各自再加自己的属性。这和面向对象里的继承几乎是同一个直觉，初学者可以直接借用「父类/子类」的心智模型。它解决的建模问题是「一批实体大部分性质相同、但有几种分别带各自特有性质」——不用为每种从头列全部属性（会大量重复），也不用把所有可能属性堆进一个实体（会大量空值）。泛化/特化的转换到关系模式有好几种方案且各有取舍，是 03-3.4.6 的内容。

### 03-3.3.3 特化的约束：不相交 vs 可重叠、全部 vs 部分

泛化/特化层次上可以加两类**正交的约束**。第一类按「一个超类实体能否同时属于多个子类」分：**不相交（disjoint）**——每个超类实体最多属于一个子类（如账户要么是储蓄账户要么是支票账户，不能既是又是）；**可重叠（overlapping）**——一个超类实体可同时属于多个子类（如一个 `person` 可以既是 `student` 又是 `employee`，即在读研究生助教）。第二类按「超类实体是否必须落进某个子类」分：**全部特化（total）**——每个超类实体都必须属于至少一个子类；**部分特化（partial）**——允许超类实体不属于任何子类。

这两类约束又是正交的，可以任意组合（不相交+全部、可重叠+部分等四种）。初学者要看清它们各管一件事：disjoint/overlapping 管「能不能脚踏多条船」，total/partial 管「能不能一条船都不上」。举例辨析：银行账户特化成储蓄/支票，通常是**不相交且全部**（每个账户恰好是其中一种）；人特化成学生/员工，可能是**可重叠且部分**（有人既学又工、也有人两者都不是只是个访客）。这两类约束会实打实影响转换方案的选择（比如全部+不相交时，用「只为子类建表」的方案才不丢信息也不冗余，见 03-3.4.6），所以不是可有可无的装饰。

### 03-3.3.4 聚集：把「一整个联系」当成一个实体来再参与联系

**聚集（aggregation）** 是一种抽象，允许把「一个联系集连同它所关联的实体」整体看作一个高层实体，从而让这个「联系」再去参与另一个更高层的联系。它解决的是 E-R 模型的一条硬限制——**联系之间不能直接发生联系、联系上也不能直接挂另一个联系**。在 DBSC 7e 记号里，聚集用一个**方框把要被当作整体的那部分（实体们 + 它们之间的联系）圈起来**，再从这个框连线到外层联系。

经典例子：`instructor`、`student`、`project` 三者有个 `proj_guide`（导师带某学生做某项目）的联系；现在想再记录「这次带做项目用到了哪些设备 `equipment`」——「用设备」这件事关联的不是单个学生或单个项目，而是「(导师,学生,项目) 这一次具体的带做」整体。这时把 `proj_guide` 连同三方聚集成一个整体，再让它与 `equipment` 建 `uses` 联系。初学者的落点是「聚集 = 把一段关系打包成一个可被引用的对象」——它和三元联系容易搞混，区别在于：如果新联系确实是对「原联系这一整件事」发生的，用聚集才对；如果只是四方之间的一个新关联，可能该建四元联系或另想模型（这属 03-3.5 的取舍）。聚集是四个高级构件里最少用、也最抽象的一个，认得出、知道它为什么存在即可。

### 03-3.3.5 角色与递归联系：同一实体集在一个联系里出现多次

**角色（role）** 指实体集在联系集中所扮演的功能。通常角色是隐含的（联系连到哪个实体集，那个实体集就扮演对应角色），但当**同一个实体集在同一个联系集里出现不止一次**时，就必须用角色名把它们区分开——这种联系叫**递归联系（recursive relationship set）**。在 E-R 图上，这体现为从一个联系菱形画出两条线都连回同一个实体集矩形，两条线上各标一个角色名。

经典例子：`course`（课程）之间的 `prereq`（先修）联系——一门课是另一门课的「先修课」，另一门课是它的「后续课」。这里 `course` 在 `prereq` 里出现两次，一次扮演 `prereq_id`（先修）角色、一次扮演 `course_id`（后续）角色，必须靠角色名区分，否则无法表达方向。再如 `employee` 之间的 `manages`（管理）联系，一个员工扮演「经理」、另一个扮演「下属」。初学者的落点是「角色名是给自我关联消歧用的标签」——它和 03-1.3.6 里关系代数的改名 ρ 解决的是同一类问题（自连接时怎么指代「同一张表的两个副本」）。转换成关系模式时，递归联系表会有两个外键列都指向同一张表，靠列名（角色名）区分（如 `prereq(course_id, prereq_id)` 两列都引用 `course.course_id`）。

## 03-3.4 E-R 图 → 关系模式的转换规则

### 03-3.4.1 强实体集 → 一张表

一个只含简单单值属性的**强实体集**，直接转成一张同名关系模式：实体集的每个属性成为表的一列，实体集的主键成为表的主键。设强实体集 E 的属性为 `a₁, …, aₙ`、主键为某子集，则

E(a₁, a₂, …, aₙ)

例如强实体集 `student(ID, name, dept_name, tot_cred)`（主键 ID）直接变成关系模式 `student(ID, name, dept_name, tot_cred)`，主键 ID。

这是最直白的一条规则，初学者只要记住「一个强实体集 = 一张表、属性 = 列、E-R 主键 = 表主键」即可。它是所有转换的起点：先把每个实体集都落成表，再处理属性的特殊形态（下条）和联系（03-3.4.3 起）。需要注意的是这条只适用于「简单单值属性」的干净情形，复合、多值、派生属性要按下一条特殊处理，不能直接当普通列。

### 03-3.4.2 复合 / 多值 / 派生属性的转换

三种特殊属性各有转换规则。**复合属性**：不为父属性建列，只为它的**叶子层简单子属性**各建一列。例如复合属性 `name(first_name, last_name)` 在表里变成 `first_name`、`last_name` 两列，没有 `name` 列。**多值属性**：**单独建一张新表**，表的列 = 该多值属性 + 原实体集的主键，主键为二者的组合（原主键 + 属性值），并以原主键为外键指回原表。例如 `instructor` 的多值属性 `phone_number` 变成新表

inst_phone(ID, phone_number)

其中 ID 是外键指向 `instructor`，主键是 `(ID, phone_number)`——每个电话号占一行。**派生属性**：通常**不建列**，其值在查询时或用视图现算。

这三条里初学者最需要吃透多值属性的拆表，因为它是「E-R 允许、关系不允许」的直接后果（见 03-3.1.5）：关系第一范式要求每个单元格是单一原子值，塞不下多个电话，只能一号一行拆到副表。复合属性摊平相对好懂——「把地址拆成城市、街道分列存」。派生属性不建列的道理是「能算就别存冗余」（存了要维护、会过期）。这三条合起来体现了转换的一个总原则：**关系模式必须扁平且原子**，凡 E-R 里「不扁平、不原子」的构造，转换时都要想办法摊平或拆出去。

### 03-3.4.3 联系集 → 一张表：主键构成依基数而定

一个联系集转成一张关系模式，其列 = **所有参与实体集的主键（作为外键）** + 联系自身的描述性属性；这张表的主键，就是 03-3.2.4 里按基数确定的那个联系候选键。对二元联系 R 连接实体集 A、B（主键分别记 `A_pk`、`B_pk`），带描述属性 `d`：

R(A_pk, B_pk, d)

其主键按基数取：M:N 取 `(A_pk, B_pk)`；1:N（B 侧为多）取 `B_pk`；1:1 取任一端主键。例如 M:N 的 `takes`（学生选课，带成绩 grade）：

takes(student_ID, course_id, grade)

主键 `(student_ID, course_id)`，两列分别外键指向 `student` 和 `course`。

初学者要把这条和「实体集转表」区分开：实体表的主键来自实体自己的属性，联系表的主键**借来自参与实体的主键**（联系没有自己的身份证，见 03-3.2.4）。这条规则给出的是「联系单独成表」的通用做法——它对 M:N 联系是唯一选择（下条会说 M:N 表不能消除），但对 1:1 和 1:N 联系，这张单独的联系表往往可以被「合并」掉、省一张表，见下条。

### 03-3.4.4 联系表的消除：1:1 与 1:N 联系合并进实体表

对**一对多（1:N）和一对一（1:1）** 联系，通常**不单独建联系表**，而是把联系「合并」进某一端的实体表以省一张表、少一次连接。规则：**1:N 联系**——把「多」侧实体表加上指向「一」侧主键的外键列（外加联系的描述属性）；因为多侧每个实体最多参与一次联系，这些列不会有冲突。**1:1 联系**——可把外键加到任一端（通常选全部参与的那一端，让外键非空）。例如 `advisor` 若是「学生:导师 = N:1」（一个学生一个导师），不建 `advisor` 表，而在 `student` 表里加一列 `advisor_ID` 作外键指向 `instructor`：

student(ID, name, dept_name, tot_cred, advisor_ID)

`advisor_ID` 外键指向 `instructor.ID`。

这里参与约束决定外键**能否为空**：若 `student` **全部参与** `advisor`（每个学生都必须有导师），则 `advisor_ID` 声明为 `NOT NULL`；若部分参与（允许有学生暂无导师），则允许 NULL。这正是 03-3.2.3 参与约束落到实处的地方。初学者要抓住合表的前提——「多侧每个实体最多参与一次」，所以把联系信息塞进多侧那一行不会冲突；而 **M:N 联系两侧都可能参与多次，塞进任何一方都会冲突，因此必须保留独立的联系表**（回到 03-3.4.3）。这条「1:N/1:1 可合表、M:N 不可」是整个转换里最实用的一条，直接对应现实中「什么时候用外键列、什么时候用中间关联表」的判断。一个提醒：DBSC 也指出，若「一」侧那一端是**部分参与**、合表会引入较多 NULL，此时保留独立联系表有时更干净——是否合表在边界情形上属工程取舍，教材给的是默认规则。

### 03-3.4.5 弱实体集的转换

**弱实体集**转成一张表，其列 = 弱实体自己的属性（含判别式）+ **属主实体集的主键**（作为外键）；表的主键 = 判别式 + 属主主键（即 03-3.3.1 说的「弱实体完整主键」）。此外，因为属主主键已经进了弱实体表、且弱实体全部参与标识联系，**标识联系本身不再单独建表**（它的信息已被弱实体表吸收）。例如弱实体集 `section`（判别式 sec_id、还有 semester、year），属主 `course`（主键 course_id）：

section(course_id, sec_id, semester, year)

主键 `(course_id, sec_id)`，其中 `course_id` 外键指向 `course`。

初学者要点有二。其一，弱实体表**天然带着属主的外键**，因为它连主键都要靠属主拼——这与普通实体转表（03-3.4.1，主键全来自自己）不同。其二，标识联系「白转」——不建表，省了一张——这是弱实体建模的一个附带好处，本质是「1:N 联系合表规则（03-3.4.4）」在弱实体上的特例（弱实体多侧、属主一侧，且全部参与）。识别弱实体、正确合成它的复合主键，是转换里比较容易出错的一环，务必把判别式和属主主键都放进主键。

### 03-3.4.6 泛化 / 特化与聚集的转换

**泛化/特化（ISA 层次）** 转换有两大方案，各有取舍。**方案一（超类+子类都建表）**：为超类建一张含公共属性的表，再为每个子类建一张表，子类表含「子类特有属性 + 超类主键（作外键兼主键）」。例如 `person(ID, name)` 一张、`student(ID, tot_cred)` 一张、`employee(ID, salary)` 一张，子类表 ID 外键指向 person。优点是无冗余、对可重叠/部分特化都适用；缺点是查一个完整的学生要连接两张表。**方案二（只为子类建表）**：不建超类表，把超类属性下放到每个子类表里各存一份。例如 `student(ID, name, tot_cred)`、`employee(ID, name, salary)` 各含 name。优点是查单个子类不用连接；缺点是——若特化是**部分的**（有实体不属任何子类），这些实体无处存放会丢失；若是**可重叠的**（一个实体属多个子类），公共属性会在多张表里重复存储、产生冗余。因此方案二一般只在特化**既全部又不相交**时才安全。

**聚集**的转换相对简单：被聚集的那部分（实体+联系）已各自转成表，聚集之上的外层联系（如 `uses`）转表时，其外键取「被聚集联系的主键」加上外层另一端实体的主键。例如 `uses` 连接聚集后的 `proj_guide`（其主键设为参与三方主键的组合）与 `equipment`，`uses` 表就含这两部分主键作外键。

给初学者的落点是「ISA 转换是在『省连接』和『省冗余/防丢失』之间选」：方案一节省存储、语义最干净，是默认推荐；方案二用冗余换查询速度，只在约束允许（全部+不相交）时才不会出问题。这条取舍与后面 03-4 范式（用规范化消冗余）和 03-3.5.5 的反范式思路一脉相承——**是否容忍冗余，取决于读写模式和约束**。聚集转换记住「把被打包的联系当成一个有主键的整体去参与外层联系」即可，实际很少考。

## 03-3.5 建模陷阱与设计取舍：实体 vs 属性 vs 联系的选择

（round3b 将本细目标为「待核」。已据一手 DBSC 7e ch6「E-R Design Issues」一节及官方 slides ch6 核实其覆盖的四类设计取舍与常见陷阱，据此撰写；核实 2026-07-29。）

### 03-3.5.1 实体 vs 属性：这个东西该建成独立实体，还是当某实体的属性

同一个概念常常既能建成**独立实体集**、也能当成某实体的**属性**，选哪个是 E-R 设计的头号取舍。DBSC 7e 给的判据核心是：**当这个概念本身还需要描述自己的性质、或需要独立地被别的东西关联时，把它建成实体；只是一个单一的、附属的取值时，当属性。** 经典例子是「电话」：如果系统只把电话当一串号码存、不关心它别的信息，`phone_number` 就是 `instructor` 的一个（可能多值的）属性；但如果要记录每部电话的位置、类型（手机/座机）、是否共用，那「电话」就该升格为独立实体集 `phone`，与 `instructor` 建联系。

初学者的实用信号有几个：这东西**会有自己的属性**吗？会**被多个实体共享/引用**吗？将来**会不会单独增删查**？任一个「是」就倾向建实体。另一个强信号是**多值**——一个属性如果天然是多值的（一个人多个电话、一个产品多张图片），把它升格为实体往往比硬做多值属性更清晰（且转换时反正也要拆表，见 03-3.4.2）。反过来，若一个概念永远只是「某实体的一个从属取值、无需再描述」，建成实体会平白多出一张表和一次连接，属过度设计。这个取舍没有唯一正确答案，取决于业务对该概念的关注程度——这正是 E-R 设计需要经验的地方。

### 03-3.5.2 实体 vs 联系：这个概念是「一个东西」还是「东西之间的关联」

第二类取舍是把一个概念建成**实体集**还是**联系集**。DBSC 7e 的经验法则是：**当一个概念描述的是若干实体之间发生的一个「动作/关联」时，用联系；当它本身是一个有独立存在性、需要被其它东西再关联的对象时，用实体。** 判断的一个可操作信号是「它需不需要再和第三方发生关联」——联系（在纯 E-R 里）不能再直接连别的联系（那要用聚集，03-3.3.4），所以如果「贷款」既连客户又连账户、将来还要连「还款记录」，把 `loan` 建成实体集比建成联系更灵活。

一个典型辨析是「贷款 loan」：早期设计常把它当客户与支行之间的**联系**（`borrower`）；但若一笔贷款要有自己的贷款号、金额，还要被多次还款引用，它就更该是**实体集** `loan`，再分别与 `customer`、`branch` 建联系。初学者容易踩的坑是把明明是独立对象的东西（订单、贷款、预约）建成联系，结果发现「联系上挂不了太多东西、也没法被再引用」而被迫返工。反过来，把纯粹的关联（选课、参与）硬建成实体，又会多出没有实际身份的「壳实体」。经验落点：**名词性、有独立生命周期、要被反复引用的 → 实体；动词性、纯粹连接两方、身份完全由两端决定的 → 联系。**

### 03-3.5.3 二元 vs n 元联系：三方关联该用一个三元联系还是拆成多个二元

现实里三方或多方的关联，既能建成一个 **n 元（如三元）联系**，也常能**拆成多个二元联系**，二者不总等价，选择要小心。DBSC 7e 指出：任何非二元联系原则上都能用一组二元联系（有时需引入一个「联系实体」）替代，但**替代未必保持原来的语义约束**——三元联系能表达「三方必须同时凑齐才构成一条事实」，而拆成三个独立二元联系后，就可能允许「只两两成对、第三方缺席」的非法组合。

经典例子：`proj_guide(instructor, student, project)` 表示「某导师指导某学生做某项目」这一整件事。如果拆成 `instructor-student`、`student-project`、`instructor-project` 三个二元联系，就无法保证三者「配套」——数据里可能出现「导师A带学生S、学生S做项目P、但项目P其实是导师B分配的」这种拆开看各自成立、合起来却不是同一件事的错乱。初学者的落点是：**当三方是「一荣俱荣、必须同时确定」的一条事实时，保留 n 元联系（或引入一个代表这件事的联系实体）；只有当三方关联确实能干净地分解成互不牵扯的两两关系时，才拆成二元。** 多数数据库工具和教材偏好二元联系（更好画、好转换），但不能为了图省事而丢掉 n 元联系承载的「同时性」约束。

### 03-3.5.4 属性放实体上还是放联系上：由「谁唯一决定这个值」判定

一个描述性属性该挂在**某个实体**上、还是挂在**联系**上，是 03-3.1.8 提过、也是最常出错的取舍。判据是：**看这个属性的值由谁唯一决定。** 只由单个实体决定的（学生的姓名由学生本人决定），放实体；由两端组合才能决定的（成绩由「哪个学生+哪门课」共同决定），放联系。

反复用成绩 `grade` 举例最清楚：它放不进 `student`（一个学生多门课多个成绩，一列存不下）、也放不进 `course`（一门课多个学生多个成绩），只能放在 `takes` 联系上——因为「一个成绩」恰好对应「一个学生+一门课」这对组合。初学者的检验方法是问「固定住一端、这个值会不会还变？」：固定学生，成绩随课不同而不同 → 说明它不只由学生决定 → 不该放学生。还有一条来自 03-3.1.8 的实用规则：**在 1:N/1:1 联系里，联系属性可以搬到「多/任一」侧实体上**（那一侧每个实体最多参与一次，不冲突），且这样搬之后联系表往往能被消除（03-3.4.4）；但在 **M:N 联系里属性必须留在联系上**（搬到任一侧都会冲突）。把这条和转换规则连起来看，就明白「属性放哪」和「要不要建联系表」其实是同一个判断的两面。

### 03-3.5.5 其它常见陷阱：冗余联系、over/under-modeling 与「用泛化还是多实体」

除上述四类主取舍外，E-R 设计还有几个常见陷阱。**冗余联系（redundant relationship）**：同一份关联被画了不止一次，或某条联系的信息其实能从别的联系推出来，造成图上冗余和数据不一致风险（例如已有 `student-section` 和 `section-course`，再直接画 `student-course` 往往是冗余的）。**过度建模（over-modeling）**：把本可当属性的简单取值统统升格成实体，图变得庞杂、查询到处要连接。**建模不足（under-modeling）**：把本该拆开的多个概念塞进一个实体（一张 `person` 表硬塞学生、教师、供应商所有字段），造成大量空值和语义混乱——这与 03-4 范式要治的问题相通。**「泛化 vs 多个独立实体」**：几个实体若共性很大、且需要被同一个联系统一引用，用泛化（03-3.3.2）比并列几个独立实体更好；若它们几乎没有共性、也从不被统一对待，强行泛化反而绕。

初学者不必把这些陷阱当规则死记，而应记住它们背后统一的判断轴：**E-R 设计是在「表达完整、无冗余、贴合读写模式」三者间找平衡。** 冗余联系违反「无冗余」，过度/不足建模违反「贴合需求」，泛化取舍则是在「共性抽取的收益」与「层次带来的连接开销」间权衡。E-R 阶段的这些取舍会一路影响到范式（03-4，用函数依赖把冗余判定形式化）与反范式（03-4.6，反过来为读性能故意引入冗余）——所以这一节可看作后续「模式设计」大主题的经验入口：先靠直觉在概念图上把结构摆对，再到 03-4 用理论工具把它验证和精修。
