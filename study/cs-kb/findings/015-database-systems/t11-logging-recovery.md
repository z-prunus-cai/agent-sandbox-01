本报告的一句话心智模型是，**恢复的全部要义是「先把打算做的改动写进一份只追加的日志，再去改真正的数据页」——这样无论在哪一刻断电，重启后都能靠这份日志把「已提交但还没落盘的改动补做（redo）」、把「没提交却已落盘的改动撤销（undo）」，最终让数据库恰好停在「所有已提交事务都在、所有未提交事务都不在」的正确状态。** ARIES 就是这套思想的工业标准实现：它先扫一遍日志弄清崩溃瞬间谁在飞、哪些页是脏的（analysis），然后**不加判断地把历史重演一遍**（redo，repeating history），再回头把未提交事务逐条撤销、且把撤销动作本身也记进日志（undo + CLR）。全篇的两个关键直觉是：**日志是唯一可信的真相来源**（数据页可能落盘了一半、可能没落盘，但日志的写入顺序被 WAL 规则严格保证）；以及**重放必须幂等**（同一条 redo 做一遍和做十遍结果一样，否则「恢复到一半再崩溃」就无法收拾）。

## 03-11.1 故障模型与恢复需求

### 03-11.1.1 三类故障：事务故障、系统崩溃、介质故障

恢复系统首先要说清「防的是什么」。DBSC 7e ch19 把故障分成三类。**事务故障（transaction failure）**指单个事务无法正常完成而中止：要么是**逻辑错误**（违反约束、坏输入、除零），要么是**系统性错误**（被死锁检测选为牺牲品而 abort）——此时数据库还好好运行着，只需把这一个事务的改动撤销。**系统崩溃（system crash）**指整个 DBMS 进程或机器挂掉——断电、内核 panic、软件 bug——**内存（易失存储）里的一切全部丢失**，包括缓冲区里还没写回磁盘的脏页和日志缓冲；但磁盘上已经落盘的内容假定完好。**介质故障（media failure / disk failure）**指磁盘本身损坏，连落盘的数据都读不出来——这类要靠**备份 + 归档日志（archival dump）**或副本来恢复，不属于本篇日志算法的主战场。

给初学者的落点是：本大主题（以及 ARIES）主要对付的是**系统崩溃**这一类。为什么它最棘手？因为崩溃发生在「不确定的时刻」——你不知道哪些事务提交了、哪些页写盘了、哪些日志刷盘了。事务故障相对简单（数据库还在跑，直接回滚一个事务即可，是崩溃恢复里 undo 逻辑的一个特例）；介质故障超出单纯日志的能力（日志和数据在同一块坏盘上就都没了，所以生产系统会把日志归档到别处）。把三类分清，是为了明白「WAL + 检查点 + ARIES」这套机器精确地服务于哪一类问题。

### 03-11.1.2 存储层次与稳定存储假设

恢复算法建立在一个关于存储的分层假设之上。**易失存储（volatile storage）**指内存/缓存，断电即失。**非易失存储（nonvolatile storage）**指磁盘/SSD，断电后内容保留，但仍可能因磁盘损坏而失效。**稳定存储（stable storage）**是一个**理想化抽象**：假想一种「信息永不丢失」的存储，工程上用「把同一份数据写到多块独立磁盘 / 多个地点」来逼近它（如 RAID、多副本）。

初学者要抓住的关键是「恢复算法的正确性依赖于一条底线假设：日志一旦被认为写入了稳定存储，它就一定还在」。为什么要专门造「稳定存储」这个概念？因为整个恢复逻辑的信任根就是日志——如果日志本身可能丢，那什么都保证不了。所以工业实现里，「事务提交」的物理动作就是「把该事务的 commit 日志记录**确实刷到磁盘（`fsync`）**」；只有这一步完成，数据库才敢对客户端说「提交成功」。这也解释了一个常见困惑：为什么提交有时会「慢」——因为它要等一次真实的磁盘刷写，而不能只写进内存缓冲。

### 03-11.1.3 恢复要兑现的两条承诺：原子性与持久性

恢复系统存在的唯一目的，是在故障之下兑现 ACID 里的两条运行时承诺：**原子性（Atomicity）**——未提交事务的改动必须「仿佛从未发生」，即崩溃后要能把它们**撤销（undo）**干净；**持久性（Durability）**——已提交事务的改动必须「一定还在」，即崩溃后即便这些改动还没写回数据页，也要能**补做（redo）**回来。

用一句判据把恢复的目标钉死会很有帮助：

崩溃恢复完成后，数据库状态 = 恰好包含所有已提交事务的效果、且不含任何未提交事务的效果

初学者常把 redo 和 undo 的分工弄反，一个稳固的记法是：**「提交了但可能没落盘」→ redo（补做）；「落盘了但没提交」→ undo（撤销）。** 为什么这两种「错位」都会发生？因为出于性能，数据库既允许**把未提交事务的脏页提前写回磁盘**（steal 策略，见 03-11.2.4），又允许**提交时数据页还留在内存没写回**（no-force 策略）——正是这两个性能优化制造了「已落盘≠已提交」和「已提交≠已落盘」的双向错位，于是既需要 undo 又需要 redo。一致性（C）和隔离性（I）不归恢复系统直接管（分别是程序员 + 约束、以及并发控制 03-10 的职责），这条边界要记清。

## 03-11.2 WAL 与日志记录：redo/undo、steal/force 与日志的关系

### 03-11.2.1 日志与日志记录的格式

**日志（log）**是一个**只追加（append-only）**的记录序列，写在稳定存储上，忠实记录数据库发生的每一次「有意义的事件」。最核心的是**更新日志记录（update log record）**，它至少要能回答「哪个事务、改了哪个数据项、旧值是什么、新值是什么」，经典记法（DBSC 7e ch19）为：

<Ti, Xj, V_old, V_new>

其中 Ti 是事务标识、Xj 是数据项、V_old 是改动前的旧值（undo 用）、V_new 是改动后的新值（redo 用）。此外还有几类特殊记录：

<Ti, start>          事务 Ti 开始

<Ti, commit>         事务 Ti 提交

<Ti, abort>          事务 Ti 中止

<checkpoint ...>     检查点（见 03-11.3）

初学者要理解「为什么日志里旧值、新值都要记」：因为恢复时两个方向都可能用到——撤销一个未提交事务要靠旧值（undo，把 Xj 写回 V_old），补做一个已提交事务要靠新值（redo，把 Xj 写成 V_new）。一条同时含旧值和新值的记录，就同时支持 undo 和 redo，这叫**undo-redo 日志**（也是 ARIES 采用的形态）。相对地，只记新值的是 redo-only 日志、只记旧值的是 undo-only 日志——它们对缓冲策略有更强的约束（下面 03-11.2.4 会看到）。另一个要点：真实引擎记的往往不是「整个值」而是**物理/逻辑的字节级改动**（如「第 100 页偏移 40 处，把这 8 字节从 A 改成 B」），但教材用 (旧值, 新值) 这一抽象足以讲清原理。

### 03-11.2.2 WAL 规则：先写日志，再改数据

**预写式日志（Write-Ahead Logging, WAL）**是整套恢复的基石规则，一句话概括就是「**在把某个数据改动写回磁盘上的数据页之前，必须先把描述这个改动的日志记录写到稳定存储上**」。更精确地，WAL 含两条子规则：

规则一（undo 用）：对某数据页的改动写回磁盘前，该改动对应的（含旧值的）日志记录必须已在稳定存储上。

规则二（redo 用）：事务的 commit 日志记录写到稳定存储之后，才能认为该事务已提交。

为什么这条「先日志后数据」的顺序是命根子？设想没有它：如果数据页先写盘、日志还没写盘，此刻崩溃，磁盘上留下了一个「已改动的页」，但日志里没有任何记录说明这是谁改的、旧值是什么——于是既不知道要不要撤销、也无从撤销，原子性彻底破产。反过来，只要日志先落盘，那么无论数据页写没写、崩溃发生在哪，日志里都有据可查：未提交的能靠旧值撤销，已提交的能靠新值补做。这就是「**日志是唯一可信的真相来源**」这句直觉的技术根据——WAL 规则用「强制的写入顺序」把这个信任建立起来。工程上这条顺序靠「刷日志缓冲的 `fsync` 必须先于刷数据页的 `fsync`」来落实。

### 03-11.2.3 redo 与 undo 的语义

**redo(Ti)** 是把事务 Ti 的所有改动按日志中的新值**重新应用**一遍——把每个被 Ti 改过的数据项设成日志记录里的 V_new。**undo(Ti)** 是把 Ti 的所有改动**反向撤销**——按日志逆序把每个数据项写回 V_old，并（在 ARIES 中）为每步撤销写一条**补偿日志记录（CLR，见 03-11.4）**，最后写一条 <Ti, abort>。

初学者要建立的核心直觉是这两个操作的**幂等性**（idempotence，03-11.5 详展）：redo 一个改动做一次和做多次，结果都是「数据项等于 V_new」，因为它是**赋值**而非「增量」（不是「+50」而是「设为新值」）——这正是恢复敢于「无脑重放」的前提。哪些事务需要 redo、哪些需要 undo？判据来自日志：日志里**既有 <Ti, start> 又有 <Ti, commit>** 的，是已提交事务，需要 redo（保证持久性）；**只有 <Ti, start> 没有 <Ti, commit>** 的，是崩溃时还在飞的事务，需要 undo（保证原子性）。ARIES 的做法更进一步——redo 阶段**对所有事务无差别重放**（包括未提交的），再在 undo 阶段把未提交的撤掉，这个反直觉的设计（repeating history）留 03-11.4 讲。

### 03-11.2.4 缓冲策略 steal/force 与 redo/undo 需求的对应

数据库把数据页缓存在内存缓冲池里，改动先落在内存页上，何时写回磁盘由两个策略维度决定，它们**直接决定了恢复时需不需要 undo、需不需要 redo**。**steal vs no-steal**：是否允许把**未提交事务**的脏页写回磁盘？允许 = steal，不允许 = no-steal。**force vs no-force**：事务提交时，是否**强制**把它改过的所有脏页立刻写回磁盘？强制 = force，不强制 = no-force。四种组合与恢复需求的对应关系是恢复理论里最经典的一张表：

| 缓冲策略 | 是否需要 UNDO | 是否需要 REDO |
|---|---|---|
| No-Steal + Force | 否 | 否 |
| No-Steal + No-Force | 否 | 是 |
| Steal + Force | 是 | 否 |
| Steal + No-Force | 是 | 是 |

推导这张表的逻辑很直接，值得初学者自己走一遍。**需要 undo ⇔ 采用 steal**：只有当未提交事务的脏页可能已经溜到磁盘上（steal），崩溃后才会有「已落盘但没提交」的改动要撤销；no-steal 则未提交改动绝不上盘，无需 undo。**需要 redo ⇔ 采用 no-force**：只有当提交时不强制刷盘（no-force），才会有「已提交但没落盘」的改动崩溃后要补做；force 则提交即落盘，无需 redo。

那为什么主流引擎（以及 ARIES）几乎都选**最麻烦的 steal + no-force**？因为它性能最好：steal 让缓冲池不被未提交事务的脏页占死、可自由换出，no-force 让提交不必等一堆随机写盘（只需顺序追加一条 commit 日志）。代价就是恢复时 undo、redo 都得做——而这正是 WAL 日志能低成本兜住的（顺序写日志远比随机写数据页便宜）。这张表也解释了「为什么需要日志」的最深层动机：是缓冲池的性能优化制造了双向错位，日志用来把错位在崩溃后补平。

### 03-11.2.5 规范 vs 实现：SQLite 的 rollback journal 与 WAL 模式、PostgreSQL 的 WAL

「WAL」作为**通用原理**（先写日志再改数据）与某个引擎叫「WAL」的**具体模式**要分开记账，否则极易混淆。

SQLite 有两大类原子提交实现，本机（sqlite lib 3.45.1，见下方实证）可直接观察。默认的 **rollback journal 模式**（`PRAGMA journal_mode=DELETE`）其实是**undo 式**日志：改数据页前，先把**旧页**整页拷贝到一个单独的 `-journal` 回滚日志文件，然后直接就地改数据库主文件；提交时删掉回滚日志、崩溃时用回滚日志把旧页写回（undo）——注意这与「预写新值再改」的方向相反，是「预写旧值」。SQLite 的 **WAL 模式**（`PRAGMA journal_mode=WAL`）才是 redo 式：改动**不就地改主文件**，而是把新页追加写到一个 `-wal` 文件，读者按需合并；提交只需把 WAL 记录落盘，之后由 checkpoint 把 WAL 里的页合并回主文件。这更接近「预写新值」的经典 WAL 思想，且允许「读不阻塞写、写不阻塞读」。所以同一个「WAL」词，在 SQLite 语境下特指后一种模式，而它的默认 rollback journal 反而是 undo 日志——这是最常见的术语陷阱。

PostgreSQL 16 则是**单一的、始终开启的 WAL**（预写式日志，写在 `pg_wal/` 目录下的段文件里，redo 语义为主，记录带 LSN），提交即刷 WAL；可用 `pg_waldump` 反查 WAL 段文件里的记录内容（本报告未取 PostgreSQL 实机，如实标注）。规范层面两家都遵循「先日志后数据」的 WAL 原理，实现层面 SQLite 用「主文件 + 单独 journal/wal 文件」、PostgreSQL 用「集中式 WAL 段 + LSN」，粒度和布局不同。

本机实证（sqlite 库版本 3.45.1，通过 Python 3.11.15 `sqlite3` 模块，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25；系统未装 `sqlite3` CLI，改用标准库）：

```
# 默认模式
>>> PRAGMA journal_mode            → delete
# 一个事务提交后，目录里只有主库文件（回滚日志已在提交时删除）
del.db 提交后目录: ['del.db']

# 切到 WAL 模式
>>> PRAGMA journal_mode=WAL        → wal   （返回 'wal' 表示切换成功）
# 建表 + 两次 INSERT 提交后
wal.db 提交后目录: ['wal.db', 'wal.db-shm', 'wal.db-wal']
# 重新查询，模式持久保留
>>> PRAGMA journal_mode            → wal
```

这条真实输出印证了两点：默认是 `delete`（rollback journal）模式、提交后回滚日志被删；WAL 模式落盘后会稳定出现 `-wal`（预写日志本体）与 `-shm`（共享内存索引）两个 sidecar 文件，且 WAL 模式一经设置会持久化到数据库（下次打开仍是 WAL）。这正对应上面「rollback journal = undo 式、WAL = redo 式」的规范/实现分账。

## 03-11.3 检查点：普通检查点与模糊检查点

### 03-11.3.1 为什么需要检查点

没有检查点，崩溃后恢复就必须**从日志最开头扫到末尾**——数据库跑了几个月，日志几个 TB，重放全部历史既慢到不可接受、又毫无必要（早已提交且早已落盘的改动根本不用再 redo）。**检查点（checkpoint）**就是周期性地在日志里打一个「进度桩」，使恢复时**只需从最近一个检查点附近开始**，把要处理的日志量压到有限。

给初学者的直觉是：检查点像游戏的「存档点」。它周期性地做两件事——把内存里的脏页（部分或全部）刷回磁盘、并在日志里写一条 <checkpoint> 记录标明「到此为止，之前的已提交改动都已安全落盘」。有了它，恢复只需关心「检查点之后发生的事」加上「检查点时还没结束的那几个事务」。检查点的核心权衡是**频率**：太频繁则平时刷盘开销大、拖慢正常事务；太稀疏则崩溃后要重放的日志多、恢复慢。这是一个「平时的持续成本」换「崩溃后的一次性恢复成本」的取舍。

### 03-11.3.2 普通检查点（静止 / quiescent checkpoint）

最简单的**普通检查点**（也叫静止检查点）流程是：

1. 暂停接受新的更新（让系统静止下来）；

2. 把日志缓冲里的所有日志记录刷到稳定存储；

3. 把缓冲池里所有脏页刷回磁盘；

4. 在日志里写一条 <checkpoint L> 记录（L 为检查点时刻仍活跃的事务列表），并把它刷到稳定存储；

5. 恢复接受更新。

它的好处是恢复逻辑极简：崩溃后从最后一条 <checkpoint> 出发，检查点之前的改动因为脏页都刷过盘、无需 redo；只需处理检查点时活跃的事务（L 列表）加上检查点之后新开的事务。它的致命缺点是第 1、3 步——**为了打检查点要让整个数据库停摆**，把所有脏页一次性刷完，期间新事务全部卡住。对一个要求高吞吐、低延迟的 OLTP 系统，这种「world-stop」是不可接受的。这就催生了模糊检查点。

### 03-11.3.3 模糊检查点（fuzzy checkpoint）

**模糊检查点（fuzzy checkpoint）**的目标是「打检查点时几乎不打断正常事务」。它的关键改动是：**不在检查点里同步刷完所有脏页**，而是先快速写下检查点记录（记下此刻的活跃事务、以及此刻哪些页是脏的），让系统立刻恢复运行，脏页在后台**慢慢异步刷回**。

因为脏页是「模糊地、逐渐地」刷的，检查点记录写下那一刻，磁盘上的数据其实处在一个不一致的中间态——这正是「fuzzy（模糊）」一词的由来。代价是恢复时不能简单假设「检查点之前的都落盘了」，于是需要一个额外机制来精确追踪「到底哪些改动确实落盘了、redo 该从哪里起步」——这正是 ARIES 的**脏页表（DPT）与 recLSN** 要解决的（见 03-11.4）。一个常见实现细节：模糊检查点会记录一个 `last_checkpoint` 指针，指向「本检查点开始时，最早那个尚未刷盘的脏页对应的日志位置」，恢复的 redo 就从这个位置起步，而不是从检查点记录本身起步——因为检查点开始时那些脏页可能到检查点结束都还没刷完。ARIES 用的正是这种模糊检查点思想。

## 03-11.4 ARIES：analysis / redo / undo 三趟，LSN、CLR、脏页表 / 事务表

### 03-11.4.1 ARIES 是什么、为什么它是工业标准

**ARIES**（Algorithm for Recovery and Isolation Exploiting Semantics，Mohan et al. 1992）是 IBM 提出的崩溃恢复算法，采用 **steal + no-force + WAL**，是今天几乎所有主流 OLTP 引擎（DB2、SQL Server、以及思想上被 PostgreSQL/InnoDB 广泛借鉴）恢复模块的蓝本。它的整个恢复过程分**三趟扫描日志**：**analysis（分析）→ redo（重做）→ undo（撤销）**。

初学者可以先记住 ARIES 的三条设计原则，它们统领全部细节：**（1）Write-Ahead Logging**——先日志后数据（前面已讲）；**（2）Repeating History During Redo（重做时重演历史）**——重启后，ARIES 先「把崩溃前发生过的一切原样重演一遍」，把数据库带回到崩溃瞬间的精确状态，**然后**再撤销未提交事务；这听起来多此一举（未提交的也重演，再撤掉），但它让恢复逻辑极其统一、能正确处理各种复杂交织的情形；**（3）Logging Changes During Undo（撤销时也记日志）**——撤销动作本身写成补偿日志记录（CLR），使得「恢复到一半又崩溃」时不会重复撤销、可从断点续做。这三条是理解 ARIES 的钥匙。

### 03-11.4.2 LSN：日志序列号

**LSN（Log Sequence Number，日志序列号）**是每条日志记录的**全局单调递增编号**——写得越晚，LSN 越大。它是 ARIES 一切精确定位的坐标系。

LSN 有几个关键用法，初学者要逐个建立：每条日志记录有自己的 LSN；每个数据页头里存一个 **pageLSN**，记录「最后一次修改这个页的那条日志记录的 LSN」；每个事务在事务表里存 **lastLSN**，指向它最近写的那条日志。为什么 pageLSN 这么重要？因为它让 ARIES 能一眼判断「某条日志记录的改动到底应不应用到某个页上」：如果日志记录的 LSN ≤ 该页的 pageLSN，说明这条改动**早已应用并落盘**在这个页上了，redo 时就该**跳过**（这正是幂等重放的机制，03-11.5）。可以把 LSN 想成「时间戳 + 版本号」的合体——它既定义了日志的顺序，又通过 pageLSN 记录了「每个页当前推进到了哪个版本」。

### 03-11.4.3 两张表：脏页表（DPT）与事务表（TT）

ARIES 在正常运行时维护两张内存表，它们是恢复的两个「路标」。**事务表（Transaction Table, TT）**记录当前所有活跃事务，每项含事务的状态和它的 **lastLSN**（最后一条日志的 LSN）。**脏页表（Dirty Page Table, DPT）**记录当前缓冲池里所有脏页（改过但还没刷回磁盘的页），每项的关键字段是 **recLSN（recovery LSN）**——「使这个页**第一次变脏**（自上次刷盘以来）的那条日志记录的 LSN」。

recLSN 是 ARIES 里最需要细品的字段，它精确回答了「redo 该从哪儿起步」。直觉是：一个页的 recLSN 表示「从这条日志开始，对这个页的改动可能还没落盘」——所以所有脏页的 recLSN 里的**最小值**，就是「整个数据库可能有改动没落盘的最早时刻」，redo 必须从这里开始，往后的都要检查、之前的一定已落盘。这两张表在检查点时会被写进日志（作为模糊检查点的一部分），崩溃后 analysis 趟据此重建。给初学者的记法：**TT 回答「谁在飞（要 undo 谁）」，DPT 回答「从哪开始重放（redo 起点）」。**

### 03-11.4.4 第一趟：Analysis（分析）

**Analysis 趟**从「最近一个检查点」开始正向扫描日志到末尾，目的有三：重建崩溃瞬间的**事务表**（弄清哪些事务在崩溃时仍活跃、因此需要 undo）、重建**脏页表**（弄清哪些页可能脏、以确定 redo 起点）、以及确定 **redo 的起始 LSN**（= 脏页表中所有 recLSN 的最小值）。

具体做法：从检查点记录里的 TT、DPT 快照出发，往后扫每条日志——遇到某事务的记录且它不在 TT 里就加进去（并随记录更新其 lastLSN 与状态）、遇到 commit/abort 就相应更新或移除、遇到「修改某页」的记录且该页不在 DPT 里就加进 DPT（recLSN = 当前这条记录的 LSN）。扫完，TT 里剩下的「未提交」事务就是 undo 的目标清单，DPT 里 recLSN 的最小值就是 redo 的起点。初学者要理解 analysis 为什么是**只读扫描、不改任何数据**：它只是「侦察」，把崩溃现场的两张路标图重建出来，供后面两趟使用。

### 03-11.4.5 第二趟：Redo（重做，重演历史）

**Redo 趟**从 analysis 定出的起始 LSN（= min recLSN）开始正向扫描到日志末尾，对每一条**可重做的记录**（更新记录和 CLR），**无差别地重放**——不管这条记录属于已提交还是未提交的事务，全部重做。这就是「repeating history（重演历史）」。

关键在于它并非真的把每条都重做一遍，而是带三个**跳过条件**，任一满足就跳过这条 redo：（1）这条记录影响的页**不在脏页表**里（说明它早已落盘）；（2）在脏页表里但该记录的 **LSN < 该页的 recLSN**（说明这条改动早于「本页可能未落盘的最早点」，已落盘）；（3）把页从盘上读进来后，发现页头的 **pageLSN ≥ 这条记录的 LSN**（说明这条改动已经写进这个页并落盘了）。只有都不满足才真正重做，并把该页 pageLSN 更新为这条记录的 LSN。为什么要连未提交事务也重做？因为「先无脑重演到崩溃瞬间的精确状态、再统一撤销」比「边重做边判断该不该做」简单得多、也更不易出错——这就是 ARIES「repeating history」哲学的实用价值。第（3）条正是**幂等重放**的直接体现：靠 pageLSN 与记录 LSN 的比较，同一条 redo 无论恢复重启几次都不会被重复应用。

### 03-11.4.6 第三趟：Undo（撤销）与 CLR（补偿日志记录）

**Undo 趟**从日志末尾**反向**扫描，把 analysis 认定为「未提交」（loser）的那些事务的所有改动逐条撤销，写回旧值。撤销每一步时，ARIES **不是简单地改回去就完**，而是为这次撤销写一条**补偿日志记录（Compensation Log Record, CLR）**。

CLR 是 ARIES 的点睛之笔，两个特性要抓住。其一，**CLR 是 redo-only 记录**——它只记「撤销动作的新值（即旧值写回后的结果）」，本身不需要再被撤销（你不会去「撤销一个撤销」）。其二，每条 CLR 带一个 **UndoNextLSN（也叫 UndoNxtLSN）**字段，指向「这个事务**下一个还需要撤销**的日志记录的 LSN」（即被撤销那条记录的 prevLSN）。这个指针链的意义在 03-11.5 会讲透：它让「撤销到一半又崩溃」时，重启后能顺着 UndoNextLSN **跳过已经撤销过的部分、从断点继续**，绝不重复撤销。为帮助初学者建立画面：正常记录靠 prevLSN 把一个事务的所有日志串成一条反向链表，undo 就是沿这条链往回走、每走一步写一条 CLR、CLR 的 UndoNextLSN 记下「下一个要走到哪」。撤销完一个事务的全部记录后，写一条 <Ti, abort>（或 end）记录收尾。

### 03-11.4.7 三趟的顺序与整体图景

把三趟的因果顺序钉死：**必须先 analysis（否则不知道 redo 从哪起、要 undo 谁）→ 再 redo（把数据库精确恢复到崩溃瞬间，让所有页都「补齐」到该有的状态）→ 最后 undo（在已经一致的状态上，干净地剥离未提交事务）**。顺序不能乱：若不先 redo 就 undo，未提交事务的某些改动可能还没被「补做」上来，undo 就会撤销一个「其实还没生效」的改动，破坏正确性；ARIES「先重演历史再撤销」恰恰保证 undo 面对的是一个「历史已完整重演、状态确定」的数据库。

给初学者一句总括：**analysis 是侦察、redo 是把历史原样播放到崩溃那一帧、undo 是把这一帧里没提交的角色一个个删掉，并把删除动作也录进日志（CLR）以防再崩溃。** 三趟走完，数据库恰好停在「所有已提交事务在、所有未提交事务不在」的正确状态——正是 03-11.1.3 那条判据。

## 03-11.5 崩溃恢复流程与幂等重放

### 03-11.5.1 端到端把整条流程串起来

把前四节合成一条完整的时间线，是本报告的收束。**正常运行时**：每个改动先写 WAL 日志（含 LSN、旧值、新值），再改内存页并更新页的 pageLSN；后台维护事务表（谁在飞）和脏页表（哪些页脏、各自 recLSN）；周期性打模糊检查点，把两张表快照写进日志、异步刷脏页。**崩溃发生**：内存全失，磁盘上留下的是「一份完整到某个 LSN 的日志」+「一批状态参差不齐的数据页（有的改动落了盘、有的没落）」。**重启恢复**：analysis 从最近检查点扫到日志尾、重建两张表并定出 redo 起点（min recLSN）与 undo 目标（TT 里未提交者）；redo 从起点重演历史、靠 pageLSN 跳过已落盘的、把每个页补齐到崩溃瞬间；undo 反向撤销未提交事务、每步写 CLR。三趟走完，数据库 = 恰好含所有已提交事务、不含任何未提交事务。

给初学者的整合直觉：**日志记下了「本该发生的完整剧本」，数据页则是「实际演到一半的舞台」；恢复就是拿剧本把舞台先补演到崩溃那一刻（redo），再把没签约的演员（未提交事务）请下台（undo）。** 剧本（日志）由 WAL 规则保证「一定比舞台先写好」，所以永远可信。

### 03-11.5.2 幂等重放：为什么重放可以放心地重复做

**幂等（idempotent）**指「一个操作做一次和做多次，效果完全相同」。恢复的重放**必须**幂等，这是整套机制能承受「恢复中再崩溃」的根本。ARIES 用两个机制分别保证 redo 和 undo 的幂等。

redo 的幂等靠 **pageLSN 比较**：重做一条 LSN=k 的记录前，先看目标页的 pageLSN；若 pageLSN ≥ k，说明这条改动已经应用并落盘、**跳过**。于是同一条 redo 无论被恢复流程执行几次，第二次起都会被跳过——做十遍等于做一遍。这也解释了为什么 redo 记的必须是「新值（赋值）」而非「增量」：赋值 x:=5 天然幂等，而 x:=x+5 做两遍就错了。undo 的幂等靠 **CLR + UndoNextLSN**：每撤销一步就写一条 CLR 记下「已撤到这里、下一个要撤 UndoNextLSN」；若恢复过程中再次崩溃、又要重来，重启后顺着 CLR 的 UndoNextLSN 直接跳到「还没撤的位置」继续，已经撤过的绝不重撤。

初学者最该记住的一句是：**因为重放幂等，恢复过程本身可以被任意次中断和重启，最终结果都一样。** 这把「恢复」从一个「必须一气呵成、不能被打断」的脆弱过程，变成一个「随便崩、随便重来、总能收敛到正确状态」的健壮过程——这正是生产级数据库敢在真实的、随时可能再断电的环境里跑恢复的底气。

### 03-11.5.3 恢复过程中再次崩溃

恢复本身也可能被新的崩溃打断（恢复 redo 到一半又断电）。得益于三趟都基于「只读日志 + 幂等写」，重启后**只需从头再来一遍三趟**即可：analysis 重新扫日志（含恢复期间写的 CLR）重建现场；redo 靠 pageLSN 跳过所有已应用的（包括上一次恢复已经补做的）；undo 靠 CLR 的 UndoNextLSN 跳过上次已经撤销的、从断点续撤。

这里有个初学者常忽略的精妙点：**恢复期间写的 CLR 本身是 redo-only 的日志记录，会被下一次恢复的 redo 趟当作普通改动重放**——正因如此，上一次 undo 已经撤销的动作（体现为 CLR 里的新值）会在重启后的 redo 里被「重演」回来，避免了「重复撤销」。也就是说，CLR 既是「撤销的记录」，又在再次崩溃时充当「撤销结果的 redo 凭据」，一石二鸟。这三层嵌套（正常改动、undo 的 CLR、再崩溃后对 CLR 的 redo）听起来绕，但只要抓住「一切写入都进日志、一切重放都幂等」这两条铁律，就能理解为什么 ARIES 能在任意崩溃序列下始终收敛到唯一正确的状态。
