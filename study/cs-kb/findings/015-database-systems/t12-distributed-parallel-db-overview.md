## 03-12.1 数据库系统架构：集中式 / 客户-服务器 / 并行 / 分布式取向对比

### 03-12.1.1 为什么要走出单机：数据量与算力墙

到这一章之前，本课讲的都是**单机、单进程**的数据库——一台机器上一个 DBMS，管着本地磁盘上的数据。这套模型在数据量不大、并发不高时非常够用，也是理解一切的地基。但现实里有两堵墙会把单机逼到极限：一堵是**数据量**（一张表几十上百 TB，单机的磁盘装不下、内存缓存不住），另一堵是**性能要求**（每秒几十万笔交易，或一条分析查询要扫上亿行还要秒级返回，单机的 CPU 和 I/O 带宽跟不上）。

面对这两堵墙，思路只有一个：**用更多的硬件**。而「更多硬件」有两种组织方式，正是本小主题要对比的四种架构里的后两种——**并行数据库**（多个处理器、多块磁盘装在一台或紧耦合的机器里，共同服务一份数据，目标是「同样的活儿做得更快 / 同时的活儿做得更多」）和**分布式数据库**（数据分散在多台通过网络连接、可能地理上相隔很远的独立机器上，目标除了扩容还包括「离用户更近」「一台挂了别的还能顶上」）。初学者先记住这条动机链：**单机不够 → 加硬件 → 加在一起（并行）还是摊出去（分布式）**，本小主题剩下的内容都是在回答「怎么加、加了怎么衡量收益、加的方式有哪几类」。

### 03-12.1.2 集中式系统与客户-服务器系统

**集中式数据库系统（centralized）**指整个数据库跑在**单台计算机**上，不与其他系统交互。它可以是给单用户用的小系统（如个人电脑上的嵌入式库），也可以是给多用户用的高性能服务器。要点是「就一台机器、一份数据、一个 DBMS 实例」——本课前 11 个大主题默认的就是这个模型。现代的集中式机器本身可能已经是**多核**的（几个到几十个 CPU 核共享内存），所以「集中式」不等于「单处理器」，但它仍在一台机器的边界内。

**客户-服务器系统（client-server）**把功能拆成两层：**服务器端**跑数据库引擎（真正管数据、执行查询、处理事务），**客户端**是发起请求的应用程序（可能在别的机器上，通过网络连到服务器）。这是今天绝大多数数据库的部署形态——你的应用（客户端）用 SQL 连接（如 JDBC / 一个 psql 会话）连到数据库服务器，服务器算完把结果发回来。初学者要注意：**客户-服务器只是「谁发请求、谁干活」的职责划分，数据本身仍集中在服务器一侧**，所以它本质上还属于「集中式数据」的范畴，和下面真正把数据摊开的并行 / 分布式是两回事。DBSC ch20 还区分了「事务服务器」（客户端发 SQL、服务器执行，最常见）与「数据服务器」（服务器发数据页给客户端、客户端本地算，用于某些对象数据库），初学者了解前者即可。

### 03-12.1.3 衡量并行收益的两把尺子：speedup 与 scaleup

加了硬件，收益怎么量？DBSC ch20 给了两个正交的指标。**加速比（speedup）**衡量「**同一个任务**，硬件翻 N 倍后快了多少」：

speedup = （小系统上的执行时间）/（大系统上的执行时间）

理想情况是**线性加速比（linear speedup）**：硬件变 N 倍，时间变成 1/N，speedup = N。**扩展比（scaleup）**衡量的是另一回事——「硬件翻 N 倍的同时，把**问题规模也翻 N 倍**，还能不能保持同样的响应时间」：

scaleup = （小问题在小系统上的时间）/（N 倍大问题在 N 倍大系统上的时间）

理想是**线性扩展比（linear scaleup）**：两者的时间相等，scaleup = 1（有的教材写作「大系统跑大问题的时间 = 小系统跑小问题的时间」）。

初学者要抓住这两把尺子的区别：**speedup 问「花钱能不能把同一件事做得更快」（固定问题、加机器）；scaleup 问「业务长大后加同比例的机器能不能扛住」（问题和机器一起长）。** 一个直观例子：一条要扫 10 亿行的报表查询，机器从 1 台变 10 台后从 100 秒降到 11 秒，speedup ≈ 9（接近线性但没到 10）；而如果数据从 10 亿涨到 100 亿、机器也从 1 台加到 10 台，查询仍是 100 秒左右，那就是接近线性的 scaleup。现实中永远达不到完美线性，原因是**启动开销**（协调 N 个进程要花固定成本）、**干扰**（多个进程抢共享资源如总线 / 锁）、和**数据倾斜**（活儿没能均匀分到每台机器上，见 03-12.2.4）——这三点是并行系统一切性能损失的根源，记住它们比记公式更重要。DBSC 还把 scaleup 细分为「批量扩展比（batch scaleup，单个大任务变大）」与「事务扩展比（transaction scaleup，任务数变多，典型 OLTP）」，了解有此二分即可。

### 03-12.1.4 三种并行架构：shared-memory / shared-disk / shared-nothing（及分层式）

并行机器里，多个处理器怎么共享资源？DBSC ch20 按「共享什么」分成三类，这是本小主题最该记牢的一张分类图。

**共享内存（shared memory）**：所有处理器共享同一片主内存和磁盘，通过内存总线通信。优点是处理器间通信极快（读写同一块内存即可）、编程简单；缺点是**扩展性差**——内存总线会成为瓶颈，处理器多到几十个以上时大家抢总线，加机器不再变快。今天一台**多核服务器**就是典型的共享内存架构，它是「机器内并行」的主力，但撑不起成百上千个处理器。

**共享磁盘（shared disk）**：每个处理器有自己私有的内存，但所有处理器共享同一组磁盘（通过高速互连或存储网络访问）。好处是任一处理器都能读到全部数据、单个磁盘故障不致命（配合冗余）；瓶颈从内存总线换成了**互连网络到磁盘的带宽**，且多机改同一份数据需要跨机器的缓存一致性 / 锁协调，仍难扩到很大规模。存储区域网络（SAN）和一些「存算分离」的云数据库在思想上接近这一类。

**无共享（shared nothing）**：每个节点有**自己私有的处理器、内存和磁盘**，节点之间只通过网络收发消息通信，谁的数据在谁的盘上、就由谁来算（把计算推到数据所在处）。这是**扩展性最好**的架构，能扩到成百上千甚至更多节点，是大规模并行 / 分布式数据库（以及大数据系统）的主流选择；代价是编程和查询处理更复杂——数据要事先分区（03-12.2）、跨节点的操作要显式在网络上搬数据。

**分层式（hierarchical）**：现实的大系统往往是上面几种的组合——比如无共享的集群里，每个节点内部又是一台多核的共享内存机器。初学者记住一句话即可：**shared-memory 通信最快但最难扩、shared-nothing 最难写但最能扩、shared-disk 居中；真实大系统是它们的分层组合。** 这条谱系（从紧耦合到松耦合）也解释了后面为什么分布式数据库几乎都建立在无共享之上——把数据分区到各节点私有磁盘，正是无共享架构对「数据怎么放」的必然要求。

### 03-12.1.5 并行数据库 vs 分布式数据库：一字之差，动机不同

前面的架构分类偏「硬件怎么连」，这一节从「系统取向」上把**并行数据库**和**分布式数据库**这对常被混用的词分清。二者都用多台 / 多处理器、也常都建在无共享之上，区别在**动机和假设**。

**并行数据库**假设机器之间**距离近、网络快、同构、由一个机构统一管理**，它的唯一目标是**性能**——用并行把大查询做快、把高并发扛住（speedup / scaleup）。**分布式数据库**则假设各站点**地理上可能分散、网络较慢且可能断、站点相对自治**，它除了性能，还追求：**数据本地性**（把数据放在离用户近的站点，降延迟）、**可用性 / 容错**（一个站点挂了，别的站点还能服务）、以及**组织自治 / 数据主权**（不同部门 / 地区各管各的数据，按需共享）。分布式系统还会区分**同构（homogeneous，各站点用同一种 DBMS、协同一致）**与**异构（heterogeneous，各站点软件不同，需要中间层调和）**。

**并行 = 「为了快，把一份活儿在近处摊开」；分布式 = 「为了大 / 近 / 抗故障，把数据在远处摊开，还得容忍网络会断、机器会挂」。** 正因为分布式多了「网络不可靠、部分失败」这层假设，它才引出了本报告最后一节的分布式事务难题；而这些难题的深入处理（复制、共识、一致性）都超出本边界课，分别下沉 L6-09 与 L5-01。

### 03-12.1.6 一句话：云数据库与存算分离（下沉指引）

DBSC 7e 的 ch20 相比旧版新增了**云端数据库服务（cloud-based services）**一节，反映了今天数据库的主流部署已从「自己机房里的服务器」转向「云上按需租用」。云数据库常见的一个关键取向是**存算分离**——把「存储」（放在便宜、近乎无限、高可用的对象存储上）与「计算」（可弹性伸缩的无状态计算节点）解耦，从而能按负载独立扩容两者。

这一取向本报告只点名、不展开：**存算分离与云原生 OLAP 架构的机制与选型，下沉 L6-05 分布式云系统 / L6-04 §04-1（现代分析型 DBMS 架构）**。初学者此处只需知道「并行 / 分布式的思想在云上以『存算分离 + 弹性计算』的新形态延续」这一句即可。

## 03-12.2 并行存储：数据分区（范围 / 散列 / 轮转）入门

### 03-12.2.1 为什么要分区：把 I/O 并行起来

一旦走到无共享架构（每个节点只有自己的私有磁盘），第一个问题就是：**一张大表的数据怎么摊到 N 个节点 / N 块磁盘上？** 这就是**数据分区（partitioning，也叫 declustering / 分片 sharding）**——把一个关系（表）的元组按某种规则拆成若干份，每份放到一个节点 / 磁盘上。

分区的根本收益是**I/O 并行**：一张表被切到 10 块盘上，一次全表扫描就能同时从 10 块盘读，聚合带宽近 10 倍；而且后续的并行查询处理（03-12.3）也建立在「数据已经分好区、各节点可以并行地处理自己那份」之上。初学者要建立的因果是：**分区是并行存储和并行查询的前提——不先把数据摊开，就无从并行。** 分区依据的那个（组）属性叫**分区键 / 分区属性（partitioning attribute）**，选哪个属性、用哪种切法，直接决定了后面查询快不快、负载均不均，这正是下面两节的主题。

### 03-12.2.2 三种基本分区策略：轮转 / 散列 / 范围

DBSC ch21 给出三种基本的水平分区（按行切）策略，假设有 n 个磁盘 D₀…D₍ₙ₋₁₎。

**轮转分区（round-robin）**：把关系里第 i 个元组发到第 (i mod n) 个磁盘，像发牌一样一人一张轮流发。它的最大优点是**数据分布最均匀**（每块盘元组数几乎相等），适合需要**顺序扫描全表**的场景；缺点是**完全打乱了数据与位置的关系**——想找某个特定值的元组，不知道它在哪块盘，任何点查 / 范围查都得**扫所有盘**。

**散列分区（hash partitioning）**：选定分区属性，对其值套一个散列函数，函数值决定去哪块盘（如 h(值) mod n）。相同的分区键值一定落到同一块盘，所以**点查（等值查询，如 `WHERE id = 100`）只需查一块盘**，非常高效；同时若散列函数好，数据也大致均匀。缺点是**范围查询（如 `WHERE age BETWEEN 20 AND 30`）帮不上忙**——连续的范围被散列打散到各盘，仍得扫所有盘。

**范围分区（range partitioning）**：把分区属性的值域切成连续的区间，每个区间一块盘（如 age 0–20 去 D₀、21–40 去 D₁……），靠一张**分区向量（partition vector）**记录边界。它对**范围查询和点查都友好**——按值能直接定位到少数几块盘，只查它们即可（这叫**范围查询的磁盘局部性**）；代价是若数据在某些区间特别密集，就会**倾斜**（见下节），且热点范围可能造成**执行倾斜**（大家都查同一段，压力全压在一块盘上）。

**轮转→只利于全表顺序扫、分布最均；散列→利于点查、分布较均、范围查无力；范围→点查和范围查都利、但最易倾斜。** 选哪种，取决于这张表主要被怎么访问。

### 03-12.2.3 分区策略与访问类型的匹配

把上一节的三种策略对着三类典型访问再过一遍，是理解「为什么要有三种切法」的关键。三类访问是：**扫描整个关系**、**点查（定位某个具体值的元组）**、**范围查（定位某个值区间的元组）**。

对**扫描整个关系**：三种分区都能并行地各盘同扫，都受益，其中轮转分布最均、并行度利用最充分。对**点查**：散列分区最优（一次散列直接命中一块盘），范围分区也能定位到一块盘，而轮转分区只能扫全部盘——最差。对**范围查**：范围分区最优（连续区间落在少数相邻盘上，只查它们），而散列和轮转都把连续值打散了，只能扫全部盘。

初学者要从这里悟出一条工程直觉：**没有「最好的分区策略」，只有「最匹配主要访问模式的分区策略」。** 一张主要按主键点查的 OLTP 表适合散列分区；一张主要按时间范围做分析扫描的表适合范围分区（按日期分区）；一张主要被整表批处理的表用轮转也无妨。这也解释了为什么真实系统里同一个库的不同表会用不同的分区方式。更细的「二级索引怎么分区」「分区数变化时怎么再平衡」「请求怎么路由到正确分区」都属于架构选型，下沉 **L6-09 §09-6**，本篇不展开。

### 03-12.2.4 头号敌人：数据倾斜（skew）

并行的理想是「活儿均匀分到每台机器、大家同时干完」；一旦某台机器分到的活儿明显多，它就成了**拖后腿的那一个**——整个并行操作的完成时间由**最慢的那台**决定，其他机器早早干完只能干等。这种「分配不均」就是**倾斜（skew）**，是并行数据库性能达不到线性加速比的头号原因。DBSC ch21 区分几类：

**属性值倾斜（attribute-value skew）**：某些分区键值本身出现得特别频繁（如「国籍 = 中国」的行远多于别的国籍），导致这些值所在的分区特别大。**分区倾斜（partition skew）**：即便属性值分布均匀，分区函数没设计好（如范围分区的边界切得不均、或散列函数不够散），也会让某些分区分到过多元组——它又可细分为数据本身放得不均（数据分布倾斜）和执行时请求集中在某几个分区（**执行倾斜 execution skew**，如大家都在查最近一天的数据）。

初学者要抓住两点。其一，**倾斜为什么致命**：并行的收益来自「同时完工」，最慢节点定义了总时间，所以哪怕只有一个节点超载，加再多别的节点也白搭——这是理解「为什么现实达不到线性加速比」的核心。其二，**怎么缓解**：常见手段是用**基于直方图 / 采样的分区向量**让范围分区的每段元组数尽量相等（均衡分区）、用**更好的散列函数**打散热点值、或对已知的热点值做特殊处理（如把超热的值单独再切细）。这些是入门层面的直觉，具体机制与再平衡策略下沉 L6-09 §09-6。

### 03-12.2.5 一句话：并行存储里的复制（下沉指引）

DBSC ch21 除了分区，还讲**复制（replication）**——把同一份数据在多个节点各存一份副本。它的动机是**可用性**（一个节点挂了，副本还能读）和**读性能 / 本地性**（就近读副本）。分区回答「数据怎么摊开以扩容」，复制回答「数据怎么冗余以抗故障和加速读」，二者常配合使用（先分区、每个分区再各存几份副本）。

复制的机制（单主 / 多主 / 无主、同步 / 异步、复制延迟与读一致性、写冲突解决）都是架构选型的重头，本边界课一律不展开，**下沉 L6-09 §09-5 复制**。初学者此处只需记住「并行 / 分布式存储 = 分区（摊开）+ 复制（冗余）两件事」这一句即可。

## 03-12.3 并行查询处理入门：分区并行与流水线并行

### 03-12.3.1 两层粒度：查询间并行 vs 查询内并行

数据分好区后，查询怎么并行地算？DBSC ch22 先按「并行的是不同查询、还是一条查询内部」分两层。

**查询间并行（interquery parallelism）**：多条**不同的查询 / 事务**同时在不同处理器上跑。它**不会让单条查询变快**，但能提升**整体吞吐量**（单位时间处理的查询数），是 **OLTP（大量短小事务）** 的主要并行形态。在共享内存架构上实现最简单（各处理器共享同一份缓冲池和锁表即可）；在无共享 / 共享磁盘上要处理跨节点的缓存一致性和锁协调，复杂得多。

**查询内并行（intraquery parallelism）**：把**单独一条查询**拆开、在多个处理器上并行执行，目标是缩短**这一条查询的响应时间**。它主要服务 **OLAP（长时间的大分析查询，如扫上亿行的聚合）**——把一条要跑几分钟的查询并行到几秒。

**查询间并行提「吞吐」、服务 OLTP（多而短）；查询内并行提「单条延迟」、服务 OLAP（少而长）。** 本小主题剩下的内容都在拆解「查询内并行」——因为它才是并行数据库技术上真正有讲头的部分。

### 03-12.3.2 查询内并行的两条腿：操作内并行 vs 操作间并行

一条查询在执行时是一棵**算子树**（如：先各表 scan、再 join、再 aggregate）。要把这棵树并行起来，有两条正交的路子。

**操作内并行（intraoperation parallelism）**：把**单个算子**并行化——让同一个操作（如一次 join、一次 sort）同时处理数据的不同分区。因为数据本来就分了区（03-12.2），一个 scan 可以让 N 个节点各扫自己那份、一个 sort 可以各节点各排自己那份再归并。这种「同一算子、多份数据并行」也叫**分区并行 / 数据并行（partitioned / data parallelism）**，是并行数据库**扩展性的主力**，见 03-12.3.3。

**操作间并行（interoperation parallelism）**：让**算子树里不同的算子**并行地跑。它又分两种形态——**流水线并行（pipelined）**：一个算子刚产出的元组立刻喂给树中的下一个算子，两者同时在跑（见 03-12.3.4）；**独立并行（independent）**：算子树里彼此没有依赖关系的分支（如 join 的左右两个输入子树）可以完全独立地同时算。

**查询内并行 = 操作内（把一个算子摊到多份数据上，=分区并行，最能扩）+ 操作间（让不同算子同时跑，含流水线并行和独立并行）。** 现实中一条大查询往往两者同时用：既把每个算子分区并行，又让上下游算子流水线起来。

### 03-12.3.3 分区并行（partitioned parallelism）：扩展性的主力

分区并行的思想极其朴素：**数据已经分成 N 份放在 N 个节点上，那就让 N 个节点各自对自己那份数据独立地跑同一个算子，最后把结果汇总。** 因为各节点干的是同一件事、各管一摊、几乎不需要互相通信，所以它能随节点数近乎线性地扩展——这正是无共享架构追求的目标。

举两个例子。**并行扫描 / 选择**：`SELECT * FROM orders WHERE amount > 1000`，让每个节点扫自己分区里的 orders、各自过滤，结果并起来即可，天然并行、无需通信。**并行连接（partitioned join）**：要 join 两张表，先把两张表都按**连接键**重新分区（用同一个散列函数），使「连接键相同的行一定落到同一个节点」，然后每个节点在本地对自己那份数据做普通的连接、最后并起来——一次全局 join 就被拆成了 N 个可并行的本地 join。这一步「按连接键重分区」的通信，正是分区并行里的主要网络代价。

初学者要理解的关键是**为什么分区并行能扩得好**：各节点几乎独立作业，加节点就加算力、通信开销相对小（主要在重分区那一下）；而它能不能真达到线性，回到 03-12.2.4 那条铁律——**取决于数据分得均不均，一旦倾斜，最慢节点拖垮全局。** 并行连接 / 并行排序 / 并行聚合的具体算法（radix-partitioned hash join、并行外部排序、两阶段聚合）都属于内核实现，下沉 **L6-04 §04-6 / §04-8**，本篇只讲「按键重分区后各节点本地算」这个入门骨架。

### 03-12.3.4 流水线并行（pipelined parallelism）：概念、好处与局限

**流水线并行**属于操作间并行：把算子树上下游的算子接成一条**流水线**，上游算子每产出一批元组，就立刻传给下游算子接着算，二者**同时在运转**，而不是等上游把结果全部算完、物化成中间表后下游才开始。类比工厂流水线——第一个工位刚装好一个零件就传给第二个工位，两个工位同时忙，而不是第一个工位把所有零件都装完再交班。

它的好处是**省掉中间结果的物化**（不用把上游的完整输出写到磁盘 / 大块内存再读回）、并让上下游算子的时间重叠，从而降延迟。但它有两条硬性局限，初学者务必记住。其一，**扩展性有限**：流水线的并行度顶多等于**流水线的长度（算子链的级数）**——一条查询的算子链就那么几级，最多也就几路并行，无法像分区并行那样靠加节点无限扩。其二，**「阻塞型」算子会打断流水线**：像**排序、聚合、（经典的）散列连接建表阶段**这类算子，必须**读完全部输入才能产出第一个结果**，下游只能干等——流水线在这里断掉。

因此现实系统里，**流水线并行是分区并行的补充而非替代**：真正扛扩展性的是分区并行（数据越多加节点越有效），流水线并行则在算子链内部省物化、降延迟。初学者的落点：**分区并行「横向」把数据摊开、能随节点数扩；流水线并行「纵向」把算子接起来、受限于链长且怕阻塞算子——两者配合，但扩展性靠前者。**

## 03-12.4 分布式事务入门：两阶段提交（2PC）点到为止

### 03-12.4.1 为什么分布式事务难：跨站点的原子性

先回忆 03-9 里的单机情形。单机事务的原子性（要么全成、要么全不成）靠一份**本地日志**兜底——提交时把日志刷盘、崩溃后按日志重做 / 回滚，一台机器上一份日志说了算。现在事务要**同时改动多个站点**的数据（如从 A 银行的库转账到 B 银行的库，两个库在两台机器上），麻烦来了：**每个站点各有各的本地日志，没有一份「全局日志」能一锤定音。**

站点 1 已经把自己那部分改动提交了，站点 2 却在提交前崩溃 / 网络断了没提交——于是转账「扣了没加」，原子性被破坏，而且各站点已经各自「说了不同的话」，事后很难收拾。分布式事务要解决的核心，就是让参与同一事务的**所有站点对「提交还是中止」达成一致的、原子的决定**：要么所有站点都提交，要么所有站点都中止，绝不允许有的提交有的中止。达成这个「原子提交」的经典协议，就是**两阶段提交（two-phase commit, 2PC）**。

### 03-12.4.2 两阶段提交（2PC）的骨架

2PC 里有一个**协调者（coordinator，通常是发起事务的那个站点）**和若干**参与者（participants，事务touch到的其他站点）**。当事务想提交时，协调者主持两个阶段。整个协议的骨架如下（记号独占块级）：

```
阶段一（准备 / 投票，Prepare / Voting phase）
  协调者 → 所有参与者：  发送 "prepare T"（问：你准备好提交了吗？）
  每个参与者：
    若本地能提交 → 把 <ready T> 强制写入本地日志（force write），回复 "ready T"（投赞成票）
    若本地不能提交 → 回复 "abort T"（投反对票）

阶段二（提交 / 决定，Commit / Decision phase）
  协调者收齐所有投票：
    若全部为 "ready"  → 写 <commit T> 到日志，向所有参与者发 "commit T"
    若有任一 "abort"（或超时未回） → 写 <abort T> 到日志，向所有参与者发 "abort T"
  每个参与者：按收到的决定在本地提交或中止，写日志，回 ack（确认）
```

要抓住的三个要点。其一，**「谁说了算」在阶段二第一步就定了**：协调者一旦把 `<commit T>`（或 `<abort T>`）写进自己的日志，全局决定就此**不可翻悔**，之后就是把这个决定通知到每个参与者、直到都确认为止。其二，**参与者投了 "ready" 就进入「准备好 / in-doubt」状态**——它承诺「我随时能提交也能中止」，必须**锁住相关数据、等协调者的最终指令**，这期间不能自作主张。其三，**任何一方投反对或超时，结果就是全体中止**——2PC 是「一票否决」的。初学者把它理解成结婚仪式的类比：阶段一是主持人分别问双方「你愿意吗」（都得答愿意），阶段二是收到都愿意后宣布「现在正式结为夫妻」——问的阶段任一方说不，婚就结不成。

### 03-12.4.3 2PC 的软肋：阻塞（blocking）问题

2PC 能保证原子性，但有一个著名的致命弱点——**阻塞（blocking）**。设想这个时序：所有参与者都投了 "ready"、进入 in-doubt 状态、锁住了数据，正等协调者的最终决定；**偏偏这时协调者崩溃了**，而且迟迟不恢复。参与者的处境是：它已经投了 ready、不能自己决定提交或中止（万一别的参与者收到了相反的指令就不一致了），只能**一直等协调者活过来**——在此期间它锁住的数据谁都动不了。这就是阻塞：**一个节点（协调者）的故障，能让一批参与者无限期卡住、握着锁不放**。

初学者要理解阻塞**为什么难以根除**：参与者之所以不敢自作决定，是因为它不知道协调者到底写没写下、以及别的参与者收到的是什么——信息不全时任何自作主张都可能造成不一致。为缓解，人们提出了**三阶段提交（3PC）**，通过多加一个阶段让参与者在协调者失联时有据可依、在某些假设（如无网络分区）下不阻塞，但 3PC 更复杂、假设也强，实践中不常用。**更现代的做法是把「提交决定」交给一个基于共识（如 Paxos / Raft）的多数派来做**——只要多数派节点还在，决定就能推进、不必死等某一个协调者，从而避免单点阻塞。DBSC ch23 正是沿「2PC → 其阻塞问题 → 3PC → 基于共识的容错提交」这条线讲的。

本节到此为止，全部深挖显式下沉：**2PC 的完整状态机、恢复时的重启协议、3PC 细节，以及 Percolator / Calvin / Spanner 等工业协议下沉 L6-04 §04-10；共识算法本身（Paxos / Raft 的正确性与流程）下沉 L5-01 分布式系统；「线性一致性 / CAP / 2PC 的阻塞代价在架构选型中的位置」下沉 L6-09 §09-9。** 初学者在本边界课记住「2PC 靠两阶段达成跨站点原子提交、但协调者单点故障会造成阻塞」这一句核心，即达到本篇目标。

### 03-12.4.4 一句话：分布式并发控制与一致性（下沉指引）

除了「提交要原子」（2PC 解决的），分布式事务还有另外两个大问题，本篇同样只点名。其一，**分布式并发控制**——多个分布式事务并发时怎么还保住可串行化（03-10 讲的锁 / 时间戳 / MVCC 要扩展到多站点，如分布式锁、分布式时间戳、跨站点死锁检测）。其二，**副本一致性**——同一份数据有多个副本时，读到的是不是最新的、多个副本间怎么保持一致（这引出线性一致性、CAP 定理、共识）。

这两块都远超边界课范围：**分布式并发控制的引擎侧实现下沉 L6-04 §04-10；副本一致性 / 共识 / CAP 下沉 L6-09 §09-9 与 L5-01 分布式系统。** 至此本课从单机数据库到「多核 / 多机」世界的边界概览收尾——读者应带走的整幅地图是：**数据摊开靠分区（+ 复制），查询加速靠并行（分区并行为主、流水线为辅），跨机原子性靠 2PC（但要提防阻塞），而更深的复制 / 一致性 / 共识 / 云原生，是后续 L5-01 / L6-04 / L6-05 / L6-09 的疆域。**
