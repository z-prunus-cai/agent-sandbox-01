## 03-8.1 等价变换规则：关系代数表达式重写

### 03-8.1.1 优化器在流水线中的位置与「等价变换」的含义

一条 SQL 进入 DBMS 后依次经过解析（parse，查语法）、翻译（translate，转成一棵关系代数表达式树）、优化（optimize）、执行（execute）四步；查询优化就是中间那一步，输入是一棵初始的关系代数表达式树，输出是一棵带了具体算法标注的、被判定为代价最低的执行计划树。优化的核心工具是**等价规则（equivalence rule）**：如果两个关系代数表达式对任意合法的数据库实例都产生相同的结果集，就称它们等价，可以互相替换。优化器就是用这些规则，从初始表达式出发生成大量等价的候选表达式。

初学者要先建立的直觉是「为什么改写能省钱而结果不变」。举一个最小例子：查「学生表和选课表连接后，只留姓张的学生」，朴素写法是先把两张大表连接成一张更大的中间表、再从里面挑出姓张的；但如果先在学生表里挑出姓张的（可能只剩几十行）、再拿这几十行去连接选课表，结果完全一样，中间结果却小了几个数量级，连接的代价随之暴跌。两种写法结果集相同（等价），代价天差地别——这就是优化的全部意义。等价规则保证「怎么改都不改结果」，代价模型（03-8.2）负责判断「哪种改写更便宜」，两者配合缺一不可。

### 03-8.1.2 选择的下推（谓词下推）与选择相关的等价规则

选择运算 σ 相关的等价规则是优化里最重要、收益最大的一类，统称**谓词下推（predicate pushdown）**——把过滤条件尽量往表达式树的底部（靠近基表处）推，让它尽早执行、尽早缩小数据量。DBSC ch16 列出的几条基础规则（记 θ、θ₁、θ₂ 为谓词，E、E₁、E₂ 为表达式）：

合取选择可拆成级联的单条件选择（deconjunction）：

σ_{θ₁ ∧ θ₂}(E) ≡ σ_{θ₁}(σ_{θ₂}(E))

选择可交换（commutativity）：

σ_{θ₁}(σ_{θ₂}(E)) ≡ σ_{θ₂}(σ_{θ₁}(E))

选择可穿过连接下推到只涉及其属性的那一侧：

σ_{θ}(E₁ ⋈ E₂) ≡ (σ_{θ}(E₁)) ⋈ E₂ ，当 θ 只涉及 E₁ 的属性时

选择也可穿过并、交、差等集合运算下推到两侧。

下推之所以几乎总是好事，是因为**过滤是「减法」，越早做，后面每一步要处理的数据就越少**；而连接、排序这些贵操作的代价随输入规模超线性增长，所以把减法提前、把贵操作的输入变小，收益巨大。易错点：下推有前提——谓词必须只引用被推入那一侧的属性；若一个谓词横跨连接两侧（如 `R.a > S.b`），它就不能单独推给任何一侧，只能留在连接处（这类谓词往往正好成为连接条件）。另外「可交换」这条看似废话，其实是给优化器自由：可以把选择率最低（过滤最狠）的条件排到最前面先做。

### 03-8.1.3 投影下推

投影运算 π 相关的规则叫**投影下推（projection pushdown）**：把「只保留哪些列」这件事也尽量往下推，让中间结果不仅行数少、列数也少，从而每页装下更多元组、减少 I/O 和内存占用。DBSC ch16 的规则大意是，投影可以穿过连接下推，但下推时**必须保留连接会用到的属性**，否则连接没法做；连接完成后再补一个投影去掉那些只为连接而临时保留、最终不需要的列。

初学者容易忽视投影的价值，觉得「不就是少几列吗」。但在按行存储、以页为 I/O 单位的系统里（03-5），一行越窄、一页装的行越多、扫同样多行读的页就越少；在需要把中间结果写盘或塞进内存哈希表的算子里（排序、hash join），列数直接决定了内存/磁盘用量。所以投影下推和谓词下推是一对——一个砍行、一个砍列，共同把流经每个算子的数据量压到最小。这也是列存引擎（L6-04 §04-2）天然占优的地方：它只读需要的列，等于投影下推做到了极致。

### 03-8.1.4 连接的交换律与结合律

连接运算 ⋈ 满足交换律和结合律，这两条规则是「连接顺序枚举」（03-8.4）的全部合法性来源：

连接可交换（commutativity）：

E₁ ⋈ E₂ ≡ E₂ ⋈ E₁

连接可结合（associativity）：

(E₁ ⋈ E₂) ⋈ E₃ ≡ E₁ ⋈ (E₂ ⋈ E₃)

θ-连接也满足对应的交换律，结合律在谓词能相应重组时同样成立。

初学者要理解这两条为什么是「优化的富矿」。三张表连接，结果集是唯一的（连接满足交换/结合，最终结果与顺序无关），但**中间结果的大小极度依赖顺序**：先连接两张连出来很小的表、再连第三张，和先连出一个巨大笛卡尔式中间结果、再去连第三张，代价可能差几个数量级。所以优化器要在所有合法的连接顺序里挑中间结果最小、总代价最低的那个。易错点：交换律里「结果集相同」指的是元组集合相同，不含顺序——连接不保证输出顺序，若最终要求有序需另加排序（这正好牵出 03-8.4.4 的「有趣的序」）。另一个常见困惑：这里说的「顺序」是**连接的先后配对顺序**（join order），不是行的排列顺序，别混淆。

### 03-8.1.5 启发式重写阶段与基于代价的优化的分工

优化器通常分两段工作。第一段是**启发式重写（heuristic / rule-based rewrite）**：无条件应用那些「几乎总是有益」的规则，主要就是谓词下推和投影下推——它们极少让计划变差，所以不必逐一算代价，直接改。第二段是**基于代价的优化（cost-based optimization）**：对那些「不一定谁更好」的选择——最关键的是连接顺序（03-8.4）和每个连接/扫描用哪种算法——枚举候选、逐一估代价（03-8.2、03-8.3）、挑最优。

给初学者的心智模型是「先做稳赚不赔的，再对拿不准的精打细算」。为什么不把所有事都交给代价模型？因为代价模型本身是有成本的（要枚举、要估算），而下推这类改写好处稳定、不值得再花代价去比较，直接做更划算；反过来，连接顺序的好坏高度依赖数据分布，没有统计信息就是瞎猜，必须走代价评估。DBSC ch16 与 CMU 15-445 L15 都按这个「rewrite 阶段 + cost-based 阶段」的两段式来讲。一个澄清：真实工业优化器（如 PostgreSQL）里这两段的边界没有教材这么泾渭分明，很多改写也会参与代价比较；教材的两段式是帮你理解「哪些是无脑好、哪些要算账」的教学抽象。

## 03-8.2 代价模型基础：I/O 与 CPU 代价、中间结果规模估计

### 03-8.2.1 代价度量：以磁盘 I/O 为主、CPU 为辅

代价模型（cost model）给每个候选计划算出一个数值化的预估代价，供优化器比较。沿用 03-5 的结论，磁盘 I/O 的成本压倒 CPU，所以代价的主体是**磁盘块传输次数和寻道次数**；DBSC ch16 沿用 ch12 的记法，一个操作的代价主要按

代价 ≈ b × t_T + S × t_S

估算，其中 b 是传输块数、S 是寻道次数、t_T 是单块传输时间、t_S 是单次寻道时间。除 I/O 外，现代代价模型也计入 **CPU 代价**（比较、哈希、函数求值等）和内存缓冲的影响，但教材级模型以 I/O 为第一位。

初学者要抓住的是「代价是相对量，不是真实秒数」。优化器不需要知道某计划到底跑几秒，它只需要一个能**正确排序**候选计划的数（谁比谁便宜），因此代价常用「等效块 I/O 数」这种抽象单位表达。这也解释了为什么两个不同 DBMS 报出的 EXPLAIN 代价数字没有可比性——各家单位和权重不同。一个易错点：代价模型是**估算**，它基于统计信息和一堆简化假设（下节的独立性假设等），真实执行可能与估算相差很远；优化器选「估算最优」不等于「实际最优」，这是所有慢查询排查的根源之一。

### 03-8.2.2 为什么「中间结果规模估计」是代价模型的心脏

一个多算子计划的总代价，是各算子代价之和；而**每个算子的代价几乎都由它的输入规模决定**，上一个算子的输出（中间结果）就是下一个算子的输入。于是整条计划的代价评估，归结为一件事：**准确估计每一步中间结果有多少行、多宽。** 这就是为什么基数估计（03-8.3）被称为优化器里最难、最要命的部分——它不是代价模型的一个配件，而是代价模型的地基。

把计划想成一条流水线，水（元组）从底部基表流上来，每经过一个算子（过滤、连接、聚合）水量就变化。代价模型要给整条流水线报价，就必须先知道每一段管子里流多少水。如果最底下那段就估错了（比如以为过滤后剩 100 行、实际剩 100 万行），错误会沿流水线一路放大——上层的连接算法选择、内存分配全部基于错的输入规模，最终计划可能糟糕到离谱。这种「误差逐层放大」是实际系统里坏计划的头号成因，也是 03-8.5「统计过时」危害巨大的原因。

### 03-8.2.3 计划整体代价：算子代价累加与流水线/物化的影响

优化器对一个完整计划估代价，是自底向上把每个算子的代价加起来。这里有一个初学者常忽略的细节：算子之间是**流水线（pipelining）**还是**物化（materialization）**会显著改变代价（这两个概念 03-7 已讲）。流水线执行下，下层算子产出一个元组就交给上层处理，中间结果不落盘，省掉写读一遍中间结果的 I/O；物化执行下，下层先把全部中间结果写到临时空间、上层再读，多付一次写+读的 I/O，但某些算子（如排序、需要多趟扫描的连接）必须物化。

初学者要理解优化器不只是选「算法」，还在隐含地选「中间结果要不要落盘」。同样是排序归并连接，如果它的输入恰好已经有序（来自某个索引或上一步排序），就能省掉排序这一大笔物化代价——这正是 03-8.4.4「有趣的序」要利用的机会。所以看 EXPLAIN 时，除了看每个节点用什么算法，还要注意哪些节点会 `Materialize`、哪些是流式的：物化节点往往是内存/磁盘压力和代价的集中点。这一节承接 03-7 的执行模型，不再重复各算子内部代价公式。

### 03-8.2.4 实现侧：PostgreSQL 的代价参数（规范 vs 实现）

教材给的是抽象代价模型；具体引擎会把它落成一组**可调的代价常数**。以 PostgreSQL 18 为例，`seq_page_cost`（顺序读一页的代价，基准值 1.0）、`random_page_cost`（随机读一页，默认 4.0，即认为随机 I/O 约为顺序的 4 倍）、`cpu_tuple_cost`（处理一行的 CPU 代价，默认 0.01）、`cpu_index_tuple_cost`、`cpu_operator_cost` 等，共同把一个计划折算成一个无量纲的代价数。EXPLAIN 输出里每个节点的 `cost=启动代价..总代价` 就是用这组常数算出来的。

给初学者的落点是「教材的 b×t_T+S×t_S 在真实系统里长这样」。`random_page_cost=4` 就是把「随机 I/O 比顺序贵」这条铁律量化成一个比值——正是这个比值让优化器在「全表顺序扫」和「走二级索引逐条随机回表」之间权衡（03-5.1.4 已埋下伏笔）。实机上，如果数据大多命中缓存或跑在 SSD 上，把 `random_page_cost` 从 4 调低（如 1.1）常能让优化器更愿意用索引——这是「调代价常数」这种非 hint 式的计划干预手段（详见 03-8.5.3）。注意：这些是 PostgreSQL 的实现选择，数值和参数名是引擎特定的，不是 SQL 标准，别当成通用常量记。

## 03-8.3 统计信息与基数估计：直方图、选择率、相关性假设

### 03-8.3.1 优化器依赖的基础统计量

优化器要估中间结果规模，靠的是预先采集、存在系统目录（catalog）里的统计信息。DBSC ch16 列的基础量有：n_r（关系 r 的元组数）、b_r（r 占的块数）、l_r（一条元组的字节数）、f_r（一块能装的元组数，blocking factor），以及最关键的 **V(A, r)——属性 A 在 r 中的不同取值个数（number of distinct values）**。这些量在 `ANALYZE` 一类命令运行时被统计并落盘（03-8.5）。

初学者要理解「优化器不看数据本身，只看这几个概括数」。它做决策时不会去扫全表数一遍到底有多少行满足条件——那样太贵，等于把查询先跑一遍。它只拿这几个统计量做**估算**。所以统计量准不准，直接决定估算准不准。其中 V(A,r)（distinct 值个数）尤其重要，因为等值查询和连接的规模估计都直接除以它（见下）。一个易错点：这些统计是**近似**的、且有采样误差（尤其 V(A,r) 这种 distinct 计数，采样估计天生难准），不是精确值——这为后面的误估埋下种子。

### 03-8.3.2 选择率与选择运算的规模估计

**选择率（selectivity）**指一个谓词筛选后留下的元组比例，取值 0~1；规模估计 = n_r × 选择率。DBSC ch16 给出各类谓词的估计公式：

等值谓词 σ_{A=v}(r)，估计满足的元组数为：

n_r / V(A, r)

（假设 A 的各取值均匀分布；若 A 是键，则结果为 1。）

范围谓词 σ_{A ≤ v}(r)，若知 A 的最小最大值，估计为：

n_r × (v − min(A, r)) / (max(A, r) − min(A, r))

（若 v 未知或无 min/max 信息，教材退化用 n_r / 2 或 n_r / 3 作粗估。）

合取 σ_{θ₁ ∧ θ₂}(r)，在**各条件独立**假设下，选择率相乘：

n_r × (s₁ / n_r) × (s₂ / n_r)

（s_i 是单条件 θ_i 的估计满足数。）

析取 σ_{θ₁ ∨ θ₂}(r)，用容斥（同样假设独立）：

n_r × (1 − (1 − s₁/n_r) × (1 − s₂/n_r))

否定 σ_{¬θ}(r) 估为 n_r − size(σ_θ(r))。

等值公式 n_r/V(A,r) 就是「把 n_r 行平均分到 V 个不同值上，每个值分到这么多行」——这是**均匀分布假设**的直接产物。这也暴露了它的软肋：如果某个值特别热门（数据倾斜，如「国家=中国」占了 80%），均匀假设会严重低估该值、高估其它值。直方图（下节）和 MCV（最常见值）就是来补救这个软肋的。合取公式相乘则来自**独立性假设**，同样常常失真（下节 03-8.3.5 详述）。易错点：这些公式全是「若…均匀/独立…则」的条件估计，条件不成立时误差可能很大——理解公式的**假设**比记住公式本身更重要。

### 03-8.3.3 直方图：给分布画一张概貌

为了摆脱「均匀分布」的粗糙假设，DBMS 为高价值列维护**直方图（histogram）**：把列的取值范围切成若干桶（bucket），记录每个桶里有多少元组，从而近似刻画真实分布。两种常见切法：**等宽直方图（equi-width）**每个桶的取值区间等宽；**等深/等频直方图（equi-depth / equi-height）**每个桶装的元组数大致相等（因此热门区间的桶更窄、更精细）。有了直方图，范围查询的选择率就按落在区间内的桶来累加，比单一 min/max 线性插值准得多。

初学者要理解直方图解决的是「数据不均匀」这个核心痛点。等深直方图通常比等宽更受青睐，因为它把桶的边界自动加密到数据密集处——热门值附近划分更细，正好是估计最容易出错、也最值得算准的地方。配合直方图，系统还常单独记录一张 **MCV（Most Common Values，最常见值）列表**及其频率，把那几个极热的值精确点名、不塞进桶里靠平均——这样倾斜的热门值不再污染其它值的估计。一个落点：直方图和 MCV 是「用一点存储和维护成本，换基数估计精度」的经典权衡，列越重要（常出现在 WHERE/JOIN 里）越值得为它多留几个桶。

### 03-8.3.4 连接规模估计

连接结果的规模估计是最关键也最容易大错的一类。DBSC ch16 对自然连接 r ⋈ s（设公共属性为 A）给出的估计式为：

估计元组数 = (n_r × n_s) / max(V(A, r), V(A, s))

若两侧公共属性无公共取值，结果为 0；若 A 是 s 的键，则 r 的每行至多匹配 s 一行，结果不超过 n_r（对称亦然）。笛卡尔积（无连接条件）则是 n_r × n_s。

分子 n_r×n_s 是「若毫无约束，每行配每行」的笛卡尔上限；分母 max(V(A,r),V(A,s)) 是连接条件带来的「收缩因子」——公共属性的不同取值越多，两边能对上的行就越少、结果越小。这个公式同样建立在均匀分布 + 值域包含假设上，一旦数据倾斜或两侧取值分布不匹配就会失真。为什么连接估计「最要命」？因为多表连接是**层层嵌套**的：第一个连接的估计喂给第二个连接，误差沿连接链**指数级放大**——底部一个连接估错 10 倍，四五个连接叠下来可能错几万倍，最终选出灾难性的连接顺序。这正是 03-8.4 连接顺序搜索建立在 03-8.3 基数估计之上、且对估计误差极度敏感的原因。

### 03-8.3.5 相关性假设及其失效

上面几乎每个公式都偷偷用了两个假设：**属性值均匀分布**、**不同谓词/不同列之间相互独立**。合取选择率相乘（03-8.3.2）就是独立性假设的直接体现。现实中列与列往往**强相关**：经典例子是 `WHERE city = '杭州' AND province = '浙江'`——城市几乎决定了省份，两条件高度相关，真实满足数约等于单条件「city=杭州」的数量；但优化器按独立假设把两个选择率相乘，会把结果严重低估（乘了一个本不该乘的省份选择率）。这类误估在教材里叫违反 **AVI（Attribute Value Independence）假设**。

给初学者的落点是「优化器的世界观默认列之间互不相干，而真实数据里它们经常手拉手」。低估中间结果的后果很实在：优化器以为某步只出几行，于是给它配了适合小数据的 nested-loop join、只分了很小的内存，实际却涌出几百万行，计划瞬间崩盘。补救手段是**多列（扩展）统计**：让系统专门为一组相关列采集联合统计，从而知道它们不独立。实现侧，PostgreSQL 提供 `CREATE STATISTICS`（多列相关性/n-distinct/MCV 扩展统计，PostgreSQL 10+）显式声明相关列组；这是把「相关性」这个教材痛点落成引擎功能的例子。易错点：扩展统计要手动为已知相关的列组创建，优化器默认不会自己发现相关性——它默认独立，直到你告诉它别这么假设。

## 03-8.4 连接顺序枚举：System R 动态规划、左深树、搜索空间

### 03-8.4.1 搜索空间：连接顺序的组合爆炸与树形

「n 张表连接」这一件事的候选方案随 n 组合爆炸，来源有二：一是**连接顺序**（先连谁后连谁），二是**连接树的形状**。按形状分两类：**左深树（left-deep tree）**——每个连接的右操作数都是一张基表，连接像滚雪球一样一张接一张往上叠；**浓密树/丛生树（bushy tree）**——允许「两个中间结果互相连接」，形状可任意分叉。左深树是浓密树的一个子集。

对 n 张表而言，左深树的不同排列有 n! 种，把所有形状（浓密）都算上则更多——DBSC ch16 给出所有完整连接树的数目为

(2(n − 1))! / (n − 1)!

n=5 时左深有 5!=120 种、含形状的完整树有 1680 种；n=10 时左深就有 362 万种，全形状更是天文数字。挨个生成并估代价显然不可行。这就是为什么需要动态规划（下节），以及为什么表一多就要退而求其次用启发式（03-8.4.5）。一个易错点：连接顺序影响的是**代价**不是**结果**——不管什么顺序，最终结果集都一样（连接满足交换/结合律，03-8.1.4），优化器纯粹是在这堆等价方案里挑最便宜的。为什么工业界偏爱左深树？因为左深树天然适合流水线执行、且右侧总是基表便于用索引做 index-nested-loop，搜索空间也小得多——用少得多的搜索代价换到接近最优的计划。

### 03-8.4.2 System R 动态规划算法（Selinger 1979）

System R 优化器（Selinger et al. 1979）提出的**自底向上动态规划（bottom-up DP）**是所有传统优化器连接枚举的鼻祖。核心是**最优子结构 + Bellman 最优性原理**：一个包含关系集合 S 的最优连接计划，一定由「S 的某个子集 (S − a) 的最优计划」再连上单张关系 a 构成。于是算法按子集大小从小到大迭代：先算出每张单表的最佳访问路径，再算所有两表子集的最优计划（复用单表结果），再三表、四表……每一层都建立在下一层已算好的最优子计划之上。用公式表达，对关系集合 S：

optplan(S) = min over a∈S of [ optplan(S − {a}) 连接 a 的代价 ]

关键在于**每个子集只保留它的最优计划**并缓存复用，而不是保留该子集的所有可能计划——这就把 n! 的枚举压成了对 2ⁿ 个子集的一趟计算。

DP 的精髓是「不重复算子问题」。朴素枚举里，「{A,B,C} 按 A→B→C 连」和「按 B→A→C 连」都要从头把 {A,B} 连一遍——DP 发现「先把 {A,B} 连成最优、结果记下来」这个子问题被无数顺序共享，算一次存起来给所有用到 {A,B} 的顺序复用。这是典型的 DP「重叠子问题 + 最优子结构」套路（与 005/008 算法课的 DP 同源）。一个澄清：System R 只搜**左深树**（右操作数限定为基表），这既缩小了搜索空间，又契合当时的执行引擎；浓密树的 DP 是后来的扩展。

### 03-8.4.3 动态规划的复杂度

DP 把阶乘级枚举降到指数级，这仍是指数、但基数小得多、常数表几乎能装下中等 n。标准结论：

只搜左深树时，需为 2ⁿ 个子集各求解，总时间约

O(n · 2ⁿ)

若搜索所有浓密树（每个子集还要枚举它的两种非空子集切分方式），时间升到

O(3ⁿ)

两者的空间都是 O(2ⁿ)（缓存每个子集的最优子计划）。

从 n!（左深朴素枚举）降到 n·2ⁿ（左深 DP）是巨大的胜利——n=12 时 12! ≈ 4.8 亿，而 12·2¹² ≈ 4.9 万，差约四个数量级。但 2ⁿ 本身照样在 n 增大时失控：n=20 时 2²⁰≈100 万还能算，n=30 时 2³⁰≈10 亿就吃不消了，何况实际每个子集内部还要枚举物理算法和「有趣的序」，常数不小。这正是几乎每个引擎都设一个**表数阈值**、超过就切换到启发式或随机化搜索的原因（03-8.4.5）——PostgreSQL 的 `geqo_threshold` 默认 12 就是这样一条线。易错点：O(3ⁿ) 里的 3 不是笔误——它来自「对每个子集 S，要遍历把 S 拆成非空两半的所有方式」，Σ over subsets 的 2^|S| 求和恰为 3ⁿ（二项式展开），这是浓密树比左深树贵的根源。

### 03-8.4.4 有趣的序（interesting orders）

Selinger 1979 的一个精妙贡献是**有趣的序（interesting orders）**。纯 DP 的前提是「每个子集只留一个最优计划」，但这在有排序需求时会失效：一个子集的次优计划，如果它的输出**恰好按某个有用的顺序排好了**（比如正好是后续 sort-merge join 需要的连接键顺序、或正好是查询 ORDER BY 要的顺序），那它可能让后续步骤省下一大笔排序代价，从而全局更优。于是 System R 放宽规则：每个子集不再只留一个最优计划，而是**为每一种「有趣的排序」各留一个该序下的最优计划**，外加一个「无序」的最优计划。

给初学者的直觉是「便宜不便宜要连着下一步一起看」。孤立地看，A⋈B 有个更快的哈希方案（输出无序）和一个稍慢的排序归并方案（输出按连接键有序）；若只按本步代价 DP 会丢掉后者。但如果紧接着要 (A⋈B)⋈C 且用 sort-merge、或最终 ORDER BY 就是这个键，那个「有序但稍贵」的中间结果反而让整体更省——因为省掉了重新排序。所以「有趣」指的是**对后续步骤有用**的序。这解释了 03-8.2.3 说的「输入已有序能省物化排序」的机会是怎么被优化器系统性地抓住的。一个易错点：这打破了教科书式 DP「每子问题一个最优解」的纯粹性——它是「按物理属性（这里是排序）分组，每组一个最优」，是后来 Cascades 优化器「物理属性/interesting properties」概念的雏形（实现留 L6-04 §04-7）。

### 03-8.4.5 大查询的应对：启发式与随机化搜索

当表数超过 DP 能承受的规模，优化器改用不保证最优、但能在合理时间出结果的方法：贪心启发式（每步选当前最便宜的连接）、遗传/随机化搜索等。实现侧，PostgreSQL 用**GEQO（Genetic Query Optimizer，遗传查询优化器）**：当参与连接的表数达到 `geqo_threshold`（默认 12）就启用遗传算法做近似搜索，低于阈值才用穷尽式 DP。此外 PostgreSQL 还有 `from_collapse_limit` 和 `join_collapse_limit`（默认都是 8）：它们限制优化器把子查询/显式 JOIN 拉平重排的规模，超过就不再自由重排，等于人为限定搜索空间以控制优化耗时。

这是一个「优化本身也要花时间」的元权衡——查询越大、找最优越贵，贵到一定程度就不值得，宁可要一个「几毫秒内出的够好计划」也不要「花几秒才算出的最优计划」。GEQO 用遗传算法（把连接顺序编码成「基因」，交叉变异择优）在大搜索空间里碰运气找近似解，结果可能每次略有不同、不保证最优。易错点：`join_collapse_limit` 常被误解——它不直接决定用不用 GEQO，而是决定优化器**把多少个 JOIN 合并进一个可自由重排的组**；把它调高能让优化器考虑更多顺序（可能找到更好计划），但优化耗时上升。这些都是引擎特定的旋钮，SQL 标准不涉及。

> 边界重申：本节讲的是**自底向上（System R 式）DP** 这一经典范式。工业优化器另有**自顶向下的 Cascades/Volcano** 框架、memo 结构与等价类、变换规则驱动的搜索——这些实现内幕属 L6-04 §04-7，本报告不展开，只指明存在与分工。

## 03-8.5 统计维护对计划的影响：ANALYZE、过时统计、优化器提示

### 03-8.5.1 统计信息的采集与更新：ANALYZE

03-8.3 用到的所有统计（n_r、V(A,r)、直方图、MCV 等）不是实时的，而是由专门命令**采样扫描**表后算出、存进系统目录，供优化器反复查用。PostgreSQL 里这个命令是 `ANALYZE`（也可随 `VACUUM ANALYZE` 一起做），它对表做**抽样**（不是全表精算，为的是快），据样本估出各列统计写入 `pg_statistic`（对外经 `pg_stats` 视图查看）。日常由 **autovacuum** 后台进程在表被改动足够多后自动触发 `ANALYZE`，无需人工。SQLite 里对应命令也叫 `ANALYZE`，把统计写进 `sqlite_stat1`（及可选的 `sqlite_stat4`）表。

采样的粒度可调：PostgreSQL 的 `default_statistics_target`（默认 **100**）控制直方图桶数和 MCV 列表长度、以及采样行数（约为 target×300 行）——调高更准但 ANALYZE 更慢、目录更大；可用 `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS n` 给单列单独设。

初学者要建立的因果链是「优化器的每个决策，最终都追溯到某次 ANALYZE 采的那批样本」。优化器不看当前真实数据，只看上一次 ANALYZE 留下的快照式统计。这带来两个推论：一是刚导入大量数据、还没 ANALYZE 时，优化器可能拿着「空表」或旧统计做决策，计划会很差（下节）；二是采样有误差，`default_statistics_target` 就是在「统计精度」和「采集/存储成本」间的旋钮。易错点：ANALYZE 只更新统计、不改数据也不重建索引，它是「让优化器看清现状」，别和 VACUUM（回收死元组空间）或 REINDEX 混为一谈——虽然 `VACUUM ANALYZE` 常一起做。

### 03-8.5.2 过时统计的后果

统计信息是某个时间点的快照，数据在变、统计不自动跟着变（要等下一次 ANALYZE）。当数据分布已经大幅漂移、而统计还停在旧值，就是**过时统计（stale statistics）**：优化器基于错误的规模估计做决策，选出的计划可能灾难性地差。典型场景——刚往一张原本空的表批量灌了千万行、还没 ANALYZE，优化器以为表几乎是空的，于是对它用 nested-loop join、给极小内存，实际却要处理千万行，查询从毫秒级劣化到分钟级。

这是「按过期地图开车」——路已经改了，导航还照旧图规划，越自信错得越离谱。过时统计是生产环境慢查询排查里最常见、也最容易修复的一类：先看 `pg_stats` 或 EXPLAIN 里的估计行数（`rows=`）和 `EXPLAIN ANALYZE` 的实际行数（`actual rows=`）差多少，若差几个数量级，八成是统计过时或相关性误估——手动 `ANALYZE` 一下往往立竿见影。易错点：autovacuum 有触发阈值（改动比例达到一定值才 ANALYZE），批量操作后可能还没到阈值，此时**手动 ANALYZE** 是标准做法；别以为「有 autovacuum 就永远不用管」。

### 03-8.5.3 优化器提示：规范 vs 实现的显著分歧

当优化器选出坏计划、又一时改不好统计时，能不能「命令」它按你的意思走？这里各引擎分歧巨大，是本大主题「规范 vs 实现」的重点。**SQL 标准不定义任何优化器提示（hint）**——提示纯属各家实现的扩展。

PostgreSQL 的立场很鲜明：**官方不提供查询 hint**（如 Oracle 那种 `/*+ ... */` 注释式指令），文档明确称调参数是「影响计划的粗糙手段、临时方案」。它给的替代是一组 `enable_*` 开关（`enable_seqscan`、`enable_hashjoin`、`enable_nestloop`、`enable_indexscan` 等，默认全 on，设 off 是「强烈不建议但不完全禁止」用某算法）、调代价常数（如降 `random_page_cost` 鼓励用索引）、调 `default_statistics_target`、调 `join_collapse_limit`。真正的 hint 需第三方扩展 `pg_hint_plan`。而 **Oracle、MySQL、SQL Server 等都提供官方 hint 语法**（如 Oracle 的 `/*+ INDEX(...) */`、MySQL 的 `USE INDEX`/`FORCE INDEX`），可在语句级直接指定索引、连接算法、连接顺序。

给初学者的落点是「同一个需求（我想干预计划），不同引擎给的手段完全不同」。PostgreSQL 的哲学是「优化器应该自己变聪明，人为钉死计划会掩盖真问题、且随数据变化会失效」，所以它宁可给你调统计和成本模型的钝器，也不给精确的 hint 刀。这不是能力缺陷而是设计取向。易错点：`enable_seqscan=off` 之类不是「禁止」而是给该方式加一个巨大代价惩罚，优化器实在没别的路时仍会用它；它主要用于排查（「强行不让走顺序扫，看看走索引会不会更快」）而非生产环境长期设置。跨引擎迁移 SQL 时，hint 是最不可移植的部分之一，要特别当心。

### 03-8.5.4 实现侧对比：PostgreSQL 与 SQLite 的统计维护

两个引擎的统计维护机制值得并排看，凸显「同一教材概念，实现各异」。PostgreSQL：`ANALYZE` 采样统计写 `pg_statistic`（`pg_stats` 视图可见 n_distinct/most_common_vals/histogram_bounds/correlation），autovacuum 自动触发，支持 `CREATE STATISTICS` 多列扩展统计，`default_statistics_target` 默认 100。SQLite：`ANALYZE` 把统计写进 `sqlite_stat1`（每索引一行的粗粒度信息）和可选的 `sqlite_stat4`（更细的样本，需编译选项开启）；SQLite **没有 autovacuum-analyze 式的自动统计更新**——统计要么手动 `ANALYZE`、要么开 `PRAGMA optimize`（在连接关闭时按需更新），否则一直是旧的。

SQLite 作为嵌入式库，设计上更「静态」——很多部署下建库时 ANALYZE 一次就不怎么变了，它甚至提供**查询计划稳定性保证（Query Planner Stability Guarantee）**：承诺在给定相同 schema、相同统计的前提下，同一 SQLite 版本对同一查询总选同一计划，方便嵌入式场景做可预测的测试。这与 PostgreSQL「统计随数据持续自动演进、计划可能随之变化」的服务器取向形成鲜明对比。易错点：SQLite 里如果建完索引不 ANALYZE，优化器可能不知道索引的选择性、从而不用它——嵌入式场景「加了索引没提速」常常就是没 ANALYZE。

### 03-8.5.5 计划回归与统计调优的日常

统计维护还牵出一个运维现实：**计划回归（plan regression）**——数据或统计一变，优化器换了个新计划，结果反而更慢。因为优化器是「按当前统计选当前最优」，它不承诺跨时间的计划稳定性（PostgreSQL 尤其如此）。调优的日常手段就是前面各节的组合：保持统计新鲜（该手动 ANALYZE 就做）、给倾斜/相关的重要列提高 `SET STATISTICS` 或建扩展统计、用 `EXPLAIN (ANALYZE, BUFFERS)` 对比估计行数与实际行数定位误估、必要时用成本参数或 `enable_*` 开关临时纠偏。

给初学者的心智模型是「优化器是个每次重新做题的学生，不是背答案的」——同一道查询，喂给它的统计变了，它就可能给出不同答卷。这带来灵活（数据变了能自适应）也带来风险（可能变差）。所以生产系统里，关键查询的计划需要**监控**：留意 EXPLAIN 的估计与实际的偏差、留意执行时间的突变。这一节把 03-8 全章收束回一个实践闭环——等价变换给出候选（03-8.1），代价模型给候选定价（03-8.2），基数估计是定价的地基（03-8.3），连接枚举在候选里搜索（03-8.4），而这一切的输入质量，全系于统计是否新鲜准确（03-8.5）。统计一旦失守，前面四步再精巧也是空中楼阁。
