## 03-6.1 索引基本概念：稠密/稀疏、有序索引 vs 散列、聚簇顺序

### 03-6.1.1 索引、搜索键与两类查询

索引（index）是建立在表的某个或某几个属性上的辅助数据结构，被索引的那组属性叫**搜索键（search key）**。索引里的每个条目（index entry）形如「搜索键值 → 指向含该值记录的定位符」，定位符（record locator）在不同引擎里可能是行的物理地址、页号+页内槽位，或另一个索引的键值。索引的唯一目的是加速按搜索键的检索，把「逐行扫描整张表」换成「在结构里直接定位」。

索引要服务两类查询，这决定了该选哪种结构。第一类是**等值查询（point query）**，如 `WHERE id = 42`；第二类是**范围查询（range query）**，如 `WHERE age BETWEEN 20 AND 30` 或需要 `ORDER BY age`。给初学者的落点是：搜索键与「候选键/主键」是两个概念——搜索键只是「你打算按它来找」的那组列，可以不唯一（比如给 `city` 建索引，很多行同一个城市）；而且同一张表可以建多个索引（按 `id` 一个、按 `city` 一个），各服务不同查询。索引不是免费的：它要占额外存储，且每次 `INSERT/UPDATE/DELETE` 都要同步更新所有相关索引，所以「无脑给每列建索引」会拖慢写入——这正是 03-6.6 优化器要做取舍的根源。

### 03-6.1.2 稠密索引与稀疏索引

按「是否为每个搜索键值都建条目」，有序索引分为两类。稠密索引（dense index）为**文件中出现的每一个搜索键值**都建一个索引条目；稀疏索引（sparse index）只为**部分**搜索键值建条目（典型是每个数据块的第一个键值建一条），查找时先在索引里找到「不大于目标值的最大键值」对应的块，再进块内顺序扫描（DBSC 7e §14.2.1）。

有一条约束必须钉死——**稀疏索引只能建在聚簇（顺序）字段上**——因为它靠「记录已按搜索键物理有序」才能从一个块头的键值推断整块的范围；如果记录乱序，稀疏条目就无法定位。所以**二级索引必须是稠密的**（见 03-6.1.4、03-6.3）。给初学者的直觉：稠密像「书里每个词都进索引」，查得准但索引大；稀疏像「每页只记页首第一个词」，索引小、省空间，但只能用在内容本身已按该词排好序的书上，且找到页后还得在页内扫几行。DBSC 与 R&G 对这组定义一致；R&G §10 用「primary/clustered index 可稀疏，secondary index 必稠密」表述同一结论。

### 03-6.1.3 有序索引 vs 散列索引

按底层组织方式，索引分两大技术路线。**有序索引（ordered index）**把搜索键值按序组织（教材里从「有序索引文件」讲起，实践中就是 B+树），键之间保持顺序，因此**同时支持等值查询和范围查询**，也能直接支撑 `ORDER BY`／`MIN`／`MAX`。**散列索引（hash index）**用散列函数把键值打散到桶里，等值查找期望 O(1)，但**天然不支持范围查询与有序遍历**（散列打乱了顺序）。

这条分野是后面所有取舍的总纲：绝大多数关系引擎默认索引是 B+树（有序），因为它一种结构就覆盖等值 + 范围 + 排序三种需求，通用性压倒散列那一点点等值优势；散列索引只在「只做等值、且量很大」的窄场景才划算（详见 03-6.5）。给初学者的类比：有序索引像按拼音排好的字典，能查单字也能查「拼音在 A–C 之间的所有字」；散列索引像把每个字扔进按首字母哈希的抽屉，查单字快，但让你「按顺序列出所有字」它就抓瞎。CMU 15-445 与 DBSC 都把「是否支持范围」列为选结构的第一判据。

### 03-6.1.4 聚簇顺序：聚簇（主）索引 vs 非聚簇（二级）索引

聚簇索引（clustering index，DBSC 也叫 primary index）指**其搜索键的顺序与记录在文件中的物理存放顺序一致**的索引；一张表至多只能有一个聚簇索引，因为记录只能按一种顺序物理排列。非聚簇索引（nonclustering index，即 secondary index / 二级索引）的搜索键顺序**与物理存放顺序不同**，一张表可以有多个（DBSC 7e §14.1）。

聚簇与否直接决定范围查询的 I/O 形态。聚簇索引下，键相邻的记录物理上也相邻，范围扫描是**顺序 I/O**、很快；二级索引下，键相邻的记录物理上四散，逐个取记录是**随机 I/O**、慢得多，这正是 03-6.3 回表代价的来源。给初学者的直觉：聚簇顺序就像图书馆按索书号上架，「取 QA76.1 到 QA76.9 的所有书」沿架一路顺手拿；二级索引像「按作者名做的卡片盒」，卡片按作者排好，但书还在按索书号的架上，你查到 10 位作者就得在馆里跑 10 个不相干的位置。注意这里只是把聚簇/二级的概念立起来，各引擎「表到底有没有天然聚簇」分歧很大（InnoDB 主键聚簇 vs PostgreSQL heap 无天然聚簇），留到 03-6.3.1 做规范 vs 实现分账。

### 03-6.1.5 多级索引：从「一层索引」到 B+树的动机

当索引本身大到放不进内存、一层索引也要占很多块时，「在索引上再建索引」就形成多级索引（multilevel index）：外层稀疏索引指向内层索引块，内层再指向数据。这样查找一次只需读 log 级数量的块，而不是线性扫索引。B+树正是把「多级 + 自动维护平衡」这件事做到极致、且在增删时自动保持各级平衡的结构。

落到设计动机上，单层稀疏索引省了扫全表，但索引一大又出现「扫全索引」的新瓶颈，于是递归地对索引再建索引；手工维护多级索引在插入删除时很难保持平衡，B+树（03-6.2）用「节点分裂/合并 + 全部数据落在等深叶子」自动解决了平衡问题，所以现代系统直接用 B+树，不再手搓多级稀疏索引。这一节是承上启下：它解释了为什么 03-6.2 的 B+树是主角。

## 03-6.2 B+树结构与操作：查找/插入/删除、分裂合并、fanout 与树高

### 03-6.2.1 B+树的整体结构

B+树是一棵**平衡的多路查找树**：从根到任意叶子的路径长度都相同（等深），所有实际的搜索键值和数据定位符都存在**叶子层**，内部节点只存「路标键」用于导航。叶子节点之间用指针串成一个**有序双向/单向链表**，因此范围查询可以先定位区间左端、再沿叶链顺序读下去（DBSC 7e §14.3）。

对初学者最好的入门直觉，是把 B+树想成一本超大字典的「跳转目录树」。内部节点是各级目录页，上面只印「A 开头看这册、K 开头看那册」这类分界字，本身不含词条；真正的词条全在最底层，且最底层还首尾相连成一条链，方便你「从『apple』一路顺读到『azure』」。三个初学者易混点：其一，内部节点里的键只是**分隔用的路标**，不代表数据一定在那儿，同一个键值真正的记录一定在叶子；其二，B+树是「扁而宽」的（每个节点几十到几百个孩子），不是二叉树，所以哪怕上亿行也只有三四层高；其三，「B+」的加号意味着数据全在叶子（对比 B 树把数据也放内部节点，见 03-6.2.7）。

### 03-6.2.2 节点的占用约束（最少/最多）

设 n 为一个节点能容纳的**最大指针数（即扇出 fanout 的上限）**，则一个节点最多存 n−1 个键。为保持平衡与空间利用，DBSC 7e §14.3.1 规定各类节点的占用下界：

内部（非根）节点的孩子指针数介于 ⌈n/2⌉ 与 n 之间

叶子节点的键值数介于 ⌈(n−1)/2⌉ 与 n−1 之间

根节点若不是叶子，至少有 2 个孩子指针

这组「至少半满」的约束是 B+树保持浅高的保证：因为每个节点都不许低于半满，树不会退化成瘦长链。给初学者的提醒：不同教材记法不同——R&G 用「阶 d」表述，规定每个节点（除根）有 d 到 2d 个条目，这与 DBSC 的「n 个指针、⌈n/2⌉ 下界」是**同一件事的两种写法**，不是冲突；读到别处公式时先确认它定义的是「指针数」还是「键数」、是「最大」还是「阶」。根节点被特殊豁免（可以只有 2 个孩子甚至在整棵树很小时直接是叶子），否则一棵只有几行的表无法建树。

### 03-6.2.3 查找操作

查找一个键 k 时，从根开始：在当前内部节点里找到「使 k 落入的那个区间」的孩子指针（键是有序的，可二分），顺指针下降一层，重复到叶子；在叶子里按 k 精确匹配即得定位符（或判定不存在）。等值查找读的块数 = 树高 + 1（叶子），范围查找则先定位区间左端叶子、再沿叶链顺序读到右端。

直觉上，每下降一层就把候选范围缩小到「几百分之一」，所以三四层就能从上亿行里锁定目标。易错点：内部节点命中某个路标键**不等于**查找结束——B+树里数据只在叶子，必须一路走到叶子才算数（这是与 B 树的一处关键区别）；范围查询之所以高效，正是因为叶子被串成有序链表，定位一次后就变成顺序读，不必每个键都从根重走。

### 03-6.2.4 插入与节点分裂

插入键 k 时先按查找路径找到应放入的叶子。若叶子未满（键数 < n−1），直接有序插入即可。若叶子已满，触发**分裂（split）**：把（原有键 + 新键）平均分成左右两个叶子，右叶子挂进叶链，并把「右叶子的第一个键」**复制（copy up）**到父节点作为新路标；若父节点也满，则父节点按内部节点规则继续分裂，把中间键**上移（push up）**到祖父——分裂可能一路向上传播，最坏到根；根分裂时树才**长高一层**（DBSC 7e §14.3.3）。

有两个关键区别要记牢——叶子分裂是**复制**分界键上去（因为数据必须留在叶子一份），内部节点分裂是**上移**中间键（内部节点本就不存数据，键上去后本层不再保留）。直觉上，B+树是**从叶子往根长高**的——这保证了任何时刻所有叶子仍等深、树仍然平衡。这也解释了为什么 B+树增删自动维持平衡，不需要像手工多级索引那样周期性重建。

### 03-6.2.5 删除、合并与重分布

删除键后，若叶子仍满足下界（≥ ⌈(n−1)/2⌉ 个键）就结束。若下溢（underflow），有两种修复：向相邻兄弟**借（重分布 redistribution）**——若兄弟有富余键，挪一个过来并更新父节点路标；否则**合并（coalesce/merge）**——把本节点与兄弟并成一个，删除父节点中对应的分隔键，删除动作可能向上传播，甚至使根收缩、树变矮（DBSC 7e §14.3.4）。

这里有一处重要的**规范 vs 实现分账**。教材算法要求删除时积极重分布/合并以维持「至少半满」；但真实引擎常为省锁、省 I/O 而**放宽**：

- PostgreSQL 的 B+树（nbtree）**不做下溢合并**——只有当一个页变得**完全为空**时才会被删除并回收，半空页会一直留着（PostgreSQL 16 文档「Index Locking」/ nbtree README「B-tree deletion」）。所以频繁删改后 PG 索引可能膨胀，需 `REINDEX`。
- InnoDB 在页填充率跌破 `MERGE_THRESHOLD`（默认 50%）时才尝试与相邻页合并（MySQL 8.0 文档「Configuring the Merge Threshold for Index Pages」）。

删除的核心不变量是「下溢就借或并」，但工程实现普遍把「合并」做成惰性或阈值触发，因为立即合并要额外加锁、写盘，得不偿失；代价是索引可能暂时不那么紧凑。理解这一点就明白了为什么生产库要定期 `REINDEX`/`OPTIMIZE TABLE`。

### 03-6.2.6 扇出（fanout）与树高公式

扇出（fanout）是一个内部节点的孩子指针数，约等于「节点能塞下多少个（键 + 指针）对」。设一个磁盘块/页大小为 B，一对（搜索键, 指针）约占 s 字节，则扇出上限约为：

n ≈ ⌊B / s⌋

含 N 个搜索键值、扇出为 n 的 B+树，其高度（根到叶的层数）满足上界（DBSC 7e §14.3.1，用最小占用 ⌈n/2⌉ 估最坏情形）：

h ≤ ⌈log_{⌈n/2⌉}(N)⌉

举一个说明性的算例（数字为教学假设，非某引擎实测）：设页 8 KB、一对约 24 字节，则扇出约 8192/24 ≈ 340。取扇出 300、树高 4，可索引约 300⁴ ≈ 8.1×10⁹（约 80 亿）个键，而任何一次等值查找只需读 4 个页，且顶部一两层几乎常驻缓冲池，实际磁盘 I/O 往往只有一两次。

B+树快的根本原因是「扇出极大 → 树极浅」。二叉树查一亿行要约 27 层，B+树因每层分叉几百，只要三四层。所以调优时想让树更浅，就要让扇出更大——键越短扇出越大，这也是「别拿超长字符串当索引键」的底层原因。文档化的页大小可作参照：PostgreSQL 默认块 8 KB（编译期 `BLCKSZ`）、InnoDB 默认页 16 KB（`innodb_page_size`）、SQLite 默认页 4096 B（自 3.12.0，2016 起，`PRAGMA page_size`）——这些是各官方文档给的默认值，实际扇出随键长而变。

### 03-6.2.7 B 树 vs B+树

B 树（B-tree）与 B+树的差别在于「数据放哪」：B 树在**内部节点也存数据定位符**（键出现一次即带数据），B+树把数据**全放叶子**、内部节点只当路标（键会在内部和叶子各出现一次）。B 树看似省了叶子的重复键、偶尔能在内部节点就命中而更快，但内部节点因携带数据而变「重」、扇出更小、树更高，且没有整齐的叶子链表，范围扫描要中序遍历、很别扭。

结论对初学者也不复杂，几乎所有主流关系引擎（PostgreSQL、InnoDB、SQLite、SQL Server 等）的默认树索引都是 **B+树**，正是因为它扇出大、树浅、且叶链让范围查询和顺序遍历极其顺手；DBSC/R&G/CMU 15-445 也都以 B+树为讲授主体。日常口语里说的「B 树索引」在数据库语境下基本都指 B+树，这是初学者常见的名词混淆点。

## 03-6.3 聚簇 vs 二级索引、覆盖索引/包含列、回表

### 03-6.3.1 聚簇索引：规范 vs 实现的最大分歧点

聚簇索引把**表数据本身按索引键的顺序组织**——极端做法是「表就是一棵以聚簇键为序的 B+树，行数据直接存在叶子里」。这样按聚簇键的等值/范围查询到叶子即拿到整行，无需再跳转。但一张表只能有一个聚簇顺序，且是否存在天然聚簇因引擎而异，这是本大主题分歧最大的地方，必须分账：

- **InnoDB（MySQL）**：表**总是**按主键组织成聚簇索引——「表即主键 B+树」，行数据存在主键索引的叶子上。若没显式主键，InnoDB 取第一个 `NOT NULL` 唯一索引，否则生成一个隐藏的 6 字节 `row_id` 作聚簇键（MySQL 8.0「Clustered and Secondary Indexes」）。
- **PostgreSQL**：表是**无序 heap**，**没有天然聚簇索引**——包括主键在内的所有索引都是二级索引，索引叶子存的是指向堆的 TID（`ctid` = 块号+行偏移）。`CLUSTER` 命令能按某索引把堆**一次性**物理重排，但**不维持**：后续插入/更新的行不再保证有序，需要再次 `CLUSTER`（PostgreSQL 16「CLUSTER」）。
- **SQLite**：默认 `rowid` 表以隐含的 `rowid` 为聚簇键（类似 InnoDB）；`WITHOUT ROWID` 表则以声明的主键作聚簇键（SQLite「Clustered Indexes and the WITHOUT ROWID Optimization」）。

对初学者，要点在于同一句「主键索引」在 InnoDB 里意味着「表按它聚簇、查主键直达整行」，在 PostgreSQL 里只是「又一个指向堆的二级索引」，性能画像完全不同。理解这条分歧，才解释得了为什么「InnoDB 里主键查最快、二级索引查要回表两次」而「PostgreSQL 里主键和普通索引查法本质一样」。

### 03-6.3.2 二级索引与回表

二级索引的叶子存的不是整行，而是「搜索键值 + 指向行的定位符」。于是按二级索引查询分两步：先在二级索引里定位到匹配条目，再拿定位符去取整行——这第二步叫**回表**（bookmark lookup / heap fetch / 二次查找）。定位符形态因引擎而异：InnoDB 二级索引叶子存的是**主键值**，回表是拿主键值再走一遍聚簇索引（等于查两棵 B+树）；PostgreSQL/SQLite 存的是行的物理定位（TID/rowid），回表是按物理地址取堆行。

回表的代价是每一个匹配行一次**随机 I/O**，这正是优化器可能放弃索引改走全表扫描的核心原因（见 03-6.6）：若 `WHERE` 命中的行占全表比例较大（选择率低），成百上千次随机回表往往比一次顺序全表扫描还慢。给初学者的直觉：二级索引像卡片盒，卡片查得飞快，但每张卡片指向的书散在馆里各处，要查的书一多，满馆乱跑就不如从头到尾把书架扫一遍。这也说明为什么「选择性高」（命中行很少）的列才适合建二级索引。

### 03-6.3.3 覆盖索引与索引只扫描

如果一条查询**需要的所有列都在索引里**（无论作搜索键还是随附），引擎就能只读索引、跳过回表——这叫**覆盖索引（covering index）**，对应的执行方式叫**索引只扫描（index-only scan）**。它把「查索引 + N 次随机回表」压成「只查索引」，是消除回表代价最直接的手段。各引擎的叫法与判读点不同：

- **PostgreSQL**：计划节点显示为 `Index Only Scan`。但有 MVCC 特有的陷阱——PG 还要确认目标页在**可见性映射（visibility map）**里标记为「全可见」，否则仍需回堆核对行版本可见性；`EXPLAIN (ANALYZE)` 里的 `Heap Fetches:` 非零就表示并未真正省掉回表（PostgreSQL 16「Index-Only Scans and Covering Indexes」）。所以刚大量更新、还没 `VACUUM` 的表，索引只扫描可能名不副实。
- **SQLite**：`EXPLAIN QUERY PLAN` 直接显示 `USING COVERING INDEX`（本报告 03-6.6 有实测输出）。
- **MySQL/InnoDB**：`EXPLAIN` 的 `Extra` 列显示 `Using index` 表示覆盖；由于 InnoDB 二级索引叶子天然带主键值，「二级索引列 + 主键」的查询常常自动被覆盖。

覆盖索引对初学者的直觉，就是「目录本身已经印上了你要的全部信息，连正文都不用翻」。判断能否覆盖，看的是查询用到的列（`SELECT` 的列 + `WHERE`/`ORDER BY` 用到的列）是否都被这个索引装下。这也提示了一个常见调优手法——把高频查询要读的少数几列一并放进索引，用一点存储换掉大量回表。

### 03-6.3.4 包含列（INCLUDE）：只为覆盖而带的载荷列

为覆盖而把列加进索引有两种做法。一是直接把列加成搜索键的一部分（如 `(a, b)`），但这样这些列会参与排序/占据内部节点、增大键长、降低扇出。二是把列作为**纯载荷（payload）只放进叶子、不参与排序与查找**——这就是**包含列（included columns）**，用 `INCLUDE` 子句声明。这里也有实现分歧：

- **PostgreSQL**（自 11 版，2018）支持 `CREATE INDEX ... INCLUDE (...)`：`INCLUDE` 里的列只存于 B+树叶子、不建立顺序，专为凑成覆盖索引而设，还能让唯一索引带上非唯一的附加列（PostgreSQL 16「CREATE INDEX」`INCLUDE`）。示例：

```sql
CREATE INDEX idx_orders_cust ON orders (customer_id) INCLUDE (amount, status);
```

- **SQLite**：**没有 `INCLUDE` 语法**。要凑覆盖只能把列并进索引键，如 `CREATE INDEX ... ON orders(customer_id, amount, status)`；对不需要参与排序的列，这会有轻微的键变长代价，但 SQLite 无更精细的手段（SQLite「CREATE INDEX」文档无 INCLUDE 关键字）。

落到用法上，`INCLUDE` 的意义是「我要覆盖、但不想让这些列拖累树的搜索/排序结构」，所以它只落在叶子当资料、不进内部路标。若引擎没有 `INCLUDE`（如 SQLite），退而求其次把列塞进键也能覆盖，只是不如 `INCLUDE` 精细。是否值得，仍回到「省下的回表 I/O vs 更大索引的写入/存储成本」这一权衡。

- 聚簇实现分账：MySQL 8.0「Clustered and Secondary Indexes」（表即主键 B+树、无主键取唯一或生成 row_id）；PostgreSQL 16「CLUSTER」（一次性物理重排、不维持）+ heap/TID 存储模型；SQLite「Clustered Indexes and the WITHOUT ROWID Optimization」。三方文档 @各自当前稳定版，核实 2026-07-29。冲突显式：InnoDB 主键聚簇 vs PostgreSQL heap 无天然聚簇 vs SQLite rowid/WITHOUT ROWID——三种模型并存，已分别定位。

## 03-6.4 复合/多属性索引、部分索引、表达式索引、前缀匹配

### 03-6.4.1 复合索引与字典序

复合索引（composite / multi-column index）建在多个列上，如 `(a, b, c)`。它把这几列拼成一个组合键，按**字典序（lexicographic order）**排序：先按 a 排，a 相同再按 b，再按 c。这决定了它能高效服务哪些查询——只要谓词构成组合键的一个**有序前缀**即可命中：`a=?`、`a=? AND b=?`、`a=? AND b=? AND c=?`，以及在最后一个用到的列上加范围（如 `a=? AND b>?`）。

复合索引对初学者的直觉，像「先按省、再按市、再按区」排好的通讯录。你能高效地查「某省」「某省某市」；但想只按「市」查（跳过省）就用不上这个排序——因为同名的市散落在各省之间，不是连续一段。这就引出最左前缀规则。易错点：`(a,b)` 与 `(b,a)` 是两个不同的索引，服务的查询不同；列的先后顺序要按查询模式设计，通常把「最常用作等值过滤、选择性高」的列放前面。

### 03-6.4.2 最左前缀规则与 skip-scan 例外

**最左前缀规则（leftmost prefix rule）**：复合索引 `(a,b,c)` 只能被「从最左列开始、连续」的谓词有效利用；跳过最左列直接查 `b` 一般用不上该索引的有序性（MySQL 8.0「Multiple-Column Indexes」明确表述此规则）。原因就是 03-6.4.1 的字典序——不定住 a，b 的值在整棵树里不是连续的。

但这条规则有工程例外——当被跳过的前导列**基数很低（distinct 值很少）**时，一些引擎用 **skip scan（跳跃扫描）**：对前导列的每个可能取值分别做一次索引查找，等效地「补上」缺失的前缀。本报告用 SQLite 实测到了这一行为——对 `(a,b)` 索引查 `WHERE b=3`，SQLite 并未全表扫描，而是用了 skip-scan：

```
>>> SELECT a FROM t WHERE b=3
    'SEARCH t USING COVERING INDEX idx_ab (ANY(a) AND b=?)'
```

其中 `ANY(a) AND b=?` 就是 skip-scan 的标志（对 a 的每个值枚举、再定 b）。给初学者的落点：默认按最左前缀规则设计索引最稳妥；skip-scan 只是低基数前导列时的救济，不是可依赖的通则，且不同引擎支持不一——SQLite 有（实测），MySQL 8.0 有「Skip Scan Range Access」，PostgreSQL 传统上没有 B+树 skip scan（是否在某新版引入需按版本另核，标「待核」）。别因为「反正有 skip scan」就随意颠倒列序。

### 03-6.4.3 部分索引（partial index）

部分索引是**只对满足某谓词的行**建立的索引，用 `WHERE` 子句声明。它的价值在于：只索引「查询真正关心、或值得索引」的那部分行，索引更小、维护更省，尤其适合「大量行取某个常见值、只需快速定位少数特殊行」的场景。

- **PostgreSQL** 长期支持：`CREATE INDEX ... WHERE <条件>`（PostgreSQL 16「Partial Indexes」）。例如只给未完成订单建索引：

```sql
CREATE INDEX idx_open_orders ON orders (created_at) WHERE status = 'open';
```

- **SQLite** 自 3.8.0（2013）支持相同形式的部分索引（SQLite「Partial Indexes」）。
- **MySQL/InnoDB** **不支持**按谓词的部分索引——注意 MySQL 文档里的「prefix index」是另一回事（见 03-6.4.5），别混。

部分索引对初学者的直觉，像「只给 VIP 顾客建的小档案柜」，其余顾客不进柜。查询要命中它，`WHERE` 条件必须蕴含索引的谓词（如上例查询也得带 `status='open'`），否则优化器不敢用这个不完整的索引。这是「用更小索引换取更低维护成本」的典型手段，也是 PG/SQLite 与 MySQL 的一处能力分歧。

### 03-6.4.4 表达式索引 / 函数索引

普通索引存的是列的原值，若查询里对列套了函数（如 `WHERE lower(name)='amy'`），原值索引就用不上——因为索引按 `name` 原值排序，不是按 `lower(name)`。**表达式索引（expression index / functional index）**直接对一个表达式的计算结果建索引，从而让这类查询也能走索引。

- **PostgreSQL** 长期支持 `CREATE INDEX ON t (lower(name))`（要求表达式是不可变/`IMMUTABLE` 的函数，PostgreSQL 16「Indexes on Expressions」）。
- **SQLite** 自 3.9.0（2015）支持表达式索引（要求表达式确定性，SQLite「Indexes On Expressions」）。
- **MySQL** 自 8.0.13（2018）支持「functional key parts」，如 `CREATE INDEX ... ((lower(name)))`。

表达式索引的铁律是**查询里的表达式要与建索引时的表达式一字不差**，优化器才认得出可用；`lower(name)` 的索引救不了 `upper(name)` 的查询。它常用来支持「大小写不敏感查找」「按 `date(ts)` 按日聚合」等场景，本质是「把常用的计算结果预先排好序存下来」。

### 03-6.4.5 「前缀」的三重含义辨析

「前缀（prefix）」在索引语境下有三个完全不同的意思，是初学者的高频混淆点，特此辨析：

其一，**最左前缀（leftmost prefix）**——指复合索引 `(a,b,c)` 能被谓词的有序列前缀利用（03-6.4.2），谈的是「多列索引里列的前缀」。

其二，**前缀索引（prefix index）**——MySQL 特有，指只对**字符串列的前 N 个字符**建索引，如 `CREATE INDEX ... ON t (col(10))`，用来给长文本列省索引空间（MySQL 8.0「Column Indexes / index prefixes」）；PostgreSQL/SQLite 无此语法，但可用表达式索引 `left(col,10)` 近似。

其三，**字符串前缀匹配（prefix search）**——指 `LIKE 'abc%'` 这类「以某串开头」的查询能用上 B+树（因为有序，`abc` 开头的键是连续一段），而 `LIKE '%abc'`（前导通配）用不上索引。注意 PostgreSQL 里 `LIKE 'abc%'` 走索引通常还要求索引用 `text_pattern_ops` 操作符类或数据库为 C locale（PostgreSQL 16「Operator Classes」）。

读到「prefix」时先分清是在说「多列索引的列前缀」「字符串列取前 N 字符建索引」还是「LIKE 前缀匹配查询」——三者机制、语法、可移植性都不同，混为一谈会写错索引也读错文档。

- 最左前缀 + skip scan：MySQL 8.0「Multiple-Column Indexes」（最左前缀规则）+「Skip Scan Range Access」；SQLite skip-scan 官方文档 + 本报告实测（`ANY(a) AND b=?`）；PostgreSQL B+树 skip scan 是否支持随版本，标「待核」。核实 2026-07-29。

## 03-6.5 散列索引与静态/动态散列（可扩展/线性散列）

### 03-6.5.1 静态散列与溢出链

散列索引用一个散列函数 h 把搜索键值映射到固定数量的**桶（bucket）**里，每个桶通常是一个页；查等值键时算 h(key) 直接定位到桶、在桶内找。静态散列（static hashing）预先固定桶数 B，是最朴素的形式。当某个桶装满，新记录进**溢出桶**并用链表串起来，形成**溢出链（overflow chain）**（DBSC 7e §14.6 静态散列；R&G ch11.1）。

静态散列的致命弱点是**桶数固定**：数据持续增长后溢出链越来越长，查一个键退化成扫一条长链，等值查找的 O(1) 优势荡然无存；数据缩小则大量空桶浪费空间。给初学者的直觉：静态散列像固定了抽屉数的柜子，东西一多每个抽屉都塞不下、外挂一串小盒子，找东西又变成翻盒子链。这就是为什么需要「桶数能随数据量自动增减」的动态散列。

### 03-6.5.2 可扩展散列（extendible hashing）

可扩展散列（extendible hashing，Fagin 1979）在桶之上加一层**目录（directory）**：目录有 2^d 个指针（d 叫**全局深度 global depth**），用散列值的**前 d 位**索引目录、指向桶；每个桶另有一个**局部深度（local depth）**，表示该桶实际是靠散列值前几位区分的（DBSC 7e 动态散列；R&G §11.2）。桶满时**分裂该桶**：若桶局部深度 < 全局深度，只需分裂桶、局部深度加 1、更新目录指针；若局部深度 == 全局深度，则**目录翻倍**（全局深度加 1）再分裂。

这层目录对初学者的直觉，像一张「按散列前缀查该去哪个桶」的路由表，桶满了就按多一位散列前缀把它劈成两个，只有当劈到「前缀位数不够用」时才把整张路由表加长一倍。好处是几乎没有溢出链、查找稳定在「查目录 + 读一个桶」；代价是目录本身会随数据增长、可能占不小空间，且目录翻倍是突发的大动作。这是「用一层可伸缩目录换掉溢出链」的思路。

### 03-6.5.3 线性散列（linear hashing）

线性散列（linear hashing，Litwin 1980）不用目录，靠一个**分裂指针（split pointer）**和一族散列函数 h_i、h_{i+1} 实现渐进扩容：当整体负载超过阈值（如填充率）时，就分裂**当前分裂指针指向的那个桶**（注意：不一定是刚溢出的那个），把它按更高一位散列重分布到原桶和新追加的桶，然后分裂指针前移；一轮走完（所有旧桶都分裂过）就进入下一轮、启用下一级散列函数（DBSC 7e 动态散列；R&G §11.3）。查找时按分裂指针位置决定用 h_i 还是 h_{i+1}。

线性散列对初学者的直觉，像「排队轮流扩建抽屉」——不管哪个抽屉先爆，都从队首那个开始一个一个地劈、按顺序往后推，桶是**一次加一个、平滑增长**的，因此不需要可扩展散列那样会突然翻倍的目录，空间增长更平缓。代价是「爆的桶」和「正在分裂的桶」可能不是同一个，所以爆的桶仍可能临时挂溢出链。它与可扩展散列是动态散列的两条主流路线，各有取舍：可扩展散列查找更稳但有目录，线性散列无目录但可能有短溢出链。

### 03-6.5.4 真实引擎里的散列索引：实现分账

教材里的散列结构在主流关系引擎里落地情况差异很大，务必分账：

- **PostgreSQL**：提供用户可建的 `hash` 索引类型（`CREATE INDEX ... USING hash`），底层是类似线性散列的动态方案，**只支持等值 `=`**、不支持范围/排序。关键版本事实：hash 索引在 **PostgreSQL 10（2017）起才 WAL 记录、崩溃安全**，此前不写 WAL、不建议在生产用（PostgreSQL 16「Hash」索引文档）。
- **MySQL/InnoDB**：InnoDB 没有用户可建的磁盘散列索引；它有**自适应散列索引（Adaptive Hash Index, AHI）**——引擎在内存里对热点 B+树页**自动**建散列以加速等值查找，用户不能显式创建、只能开关（MySQL 8.0「Adaptive Hash Index」）。此外 `MEMORY` 存储引擎支持显式 `HASH` 索引。
- **SQLite**：**完全没有散列索引类型**，所有索引都是 B 树/B+树（SQLite 官方文档索引章节无 hash 类型）。

别把「教材讲了散列索引」误当成「到处都能建散列索引」。生产中散列索引用得远比 B+树少，原因见下一节。

### 03-6.5.5 何时用散列、何时别用

散列索引的唯一优势是**等值查找的期望 O(1)**，在超大表的纯等值场景可能略快于 B+树的 O(log N)。但它有硬伤：**不支持范围查询、不支持 `ORDER BY`/`MIN`/`MAX`、不支持最左前缀式的多列部分匹配、也不能用于 `LIKE 'abc%'`**——凡是需要「有序」的操作它一概无能为力。

结论是，正因为 B+树一种结构就同时覆盖等值 + 范围 + 排序，而散列只赢等值那一点、还输掉全部有序操作，所以工程默认几乎总是 B+树，散列索引只在「确定只做等值、且量极大」的窄场景才考虑。这与 03-6.1.3「有序 vs 散列」的总纲首尾呼应。至于 B+树 vs LSM 树在写放大/空间放大上的权衡，属于内核与选型层面，留 L6-04 / L6-09，本报告不展开。

## 03-6.6 读执行计划：EXPLAIN 中索引扫描 vs 全表扫描的判读

### 03-6.6.1 SQLite：EXPLAIN QUERY PLAN 的判读（含本机实测）

SQLite 用 `EXPLAIN QUERY PLAN`（简称 EQP）给出一棵人类可读的计划树，判读只看几个关键词：`SCAN t` 表示**全表扫描**（逐行读整张表）；`SEARCH t USING INDEX <名>` 表示**走了某个索引**；`USING COVERING INDEX` 表示**覆盖索引/只扫描**（不回表）；`USING INTEGER PRIMARY KEY (rowid=?)` 表示按 rowid（聚簇键）直达。本报告在本机实测（`基线 Py3.11.15 @2026-07-29`，Python 内置 `sqlite3` 模块，SQLite 3.45.1，5000 行内存表，建 `idx_a(a)`、`idx_ab(a,b)` 并 `ANALYZE`）：

```
>>> SELECT * FROM t WHERE c='xxxxxxxxxx'   -- 无可用索引
    'SCAN t'
>>> SELECT * FROM t WHERE a=5              -- 用单列索引
    'SEARCH t USING INDEX idx_a (a=?)'
>>> SELECT a,b FROM t WHERE a=5            -- 所需列都在 idx_ab 里
    'SEARCH t USING COVERING INDEX idx_ab (a=?)'
>>> SELECT * FROM t WHERE id=42            -- 按聚簇键直达
    'SEARCH t USING INTEGER PRIMARY KEY (rowid=?)'
>>> SELECT * FROM t ORDER BY a             -- 用索引避免排序
    'SCAN t USING INDEX idx_a'
```

这五行几乎覆盖了判读的全部要点——没索引就 `SCAN`（全表）；命中索引是 `SEARCH ... USING INDEX`；`COVERING` 意味着连回表都省了；`ORDER BY a` 那条虽是 `SCAN`（读了整段），但 `USING INDEX idx_a` 说明它靠索引拿到了有序性、免掉了单独排序。一个易踩的坑：SQLite 里**光写 `EXPLAIN`（不带 `QUERY PLAN`）会输出 VDBE 字节码**，那是给引擎开发者看的低层指令，不是执行计划——判读索引一定用 `EXPLAIN QUERY PLAN`。

### 03-6.6.2 PostgreSQL：EXPLAIN 的判读

PostgreSQL 的 `EXPLAIN` 给出**带代价估算**的计划树，核心节点类型：`Seq Scan`（全表顺序扫描）、`Index Scan`（走索引并回堆取行）、`Index Only Scan`（覆盖索引、尽量不回堆）、`Bitmap Index Scan` + `Bitmap Heap Scan`（先用索引攒一张位图再批量按物理序回堆，适合命中中等量行、把随机 I/O 变得较有序）。`EXPLAIN (ANALYZE, BUFFERS)` 会**真正执行**并给出实际行数、时间与缓冲命中/读盘。判读时重点看几处：

```
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
   -- Seq Scan on t  (cost=... rows=... )   全表扫描
   -- Index Scan using idx on t             走索引 + 回堆
   -- Index Only Scan using idx on t        覆盖，注意下一行
   --   Heap Fetches: 0                     0 才是真正省了回表
   -- Rows Removed by Filter: N             索引/扫描后又被过滤掉的行
```

`Seq Scan` 未必是坏事——当谓词命中占比高（选择率低）时它常比索引 + 大量随机回表更快，优化器按代价选它是理性的。三个判读要点：其一，`Index Only Scan` 下若 `Heap Fetches` 非零，说明可见性映射没标全可见（刚更新未 `VACUUM`），并未真省回表（呼应 03-6.3.3）；其二，估算 `rows` 与实际 `rows` 差很多，通常是统计过时，`ANALYZE` 一下再看（详见大主题 03-8）；其三，`Bitmap Scan` 出现说明命中量介于「少量→Index Scan」与「大量→Seq Scan」之间，是 PG 的中间挡位。

### 03-6.6.3 MySQL：EXPLAIN 的判读（简表）

MySQL 的 `EXPLAIN` 以表格给出，判读看三列：`type`（访问方式，从好到差大致 `const` / `eq_ref` / `ref` / `range` / `index` / `ALL`，其中 `ALL` 就是全表扫描）、`key`（实际用了哪个索引，为 `NULL` 表示没用索引）、`Extra`（`Using index` = 覆盖、`Using where` = 取回后再过滤、`Using filesort` = 需额外排序、`Using index condition` = 索引条件下推 ICP）。MySQL 8.0 还支持 `EXPLAIN FORMAT=TREE` 和 `EXPLAIN ANALYZE` 给树形与实测。

MySQL 判读时第一眼看 `type` 是不是 `ALL`（是则全表扫描、可能缺索引）和 `key` 有没有用上预期索引；`Extra` 里出现 `Using filesort` 或 `Using temporary` 往往是可优化信号。三家对照记一句话即可——**SQLite 看关键词、PostgreSQL 看节点类型 + 代价、MySQL 看 type/key/Extra 三列**。

### 03-6.6.4 优化器为什么会放弃索引改走全表扫描

即使有可用索引，优化器也可能选全表扫描，核心变量是**选择率（selectivity）**——谓词命中行占全表的比例。走二级索引要为每个命中行做一次随机回表（03-6.3.2），当命中行很多时，「查索引 + 大量随机 I/O」的总代价会超过「一次顺序扫全表」。所以优化器基于统计估出命中行数，按代价模型二选一。经验直觉：命中比例很小（高选择性）→ 索引划算；命中比例较大 → 全表扫描反而快。

落到常见坑上，其一，**小表**上优化器常直接全表扫描——几页就读完了，建索引反而多此一举，别看到 `Seq Scan`/`SCAN` 就慌。其二，**统计过时**会让估算的命中行数失真、选错计划，这时该 `ANALYZE`（PG/SQLite）或 `ANALYZE TABLE`（MySQL）刷新统计。其三，谓词写法会让索引失效——对列套了函数（`WHERE lower(x)=...` 而没建表达式索引）、隐式类型转换、`LIKE '%abc'` 前导通配，都会逼出全表扫描。这些「为什么该用的索引没被用」的判读，正是 `EXPLAIN` 的日常价值。至于优化器代价模型与统计估算的原理本身，属大主题 03-8，本报告只讲到「据代价二选一」为止。

### 03-6.6.5 三家 EXPLAIN 的规范 vs 实现分账（小结）

`EXPLAIN` 并无跨引擎统一格式，判读前先认清在读哪家：**SQLite** 的 `EXPLAIN QUERY PLAN` 是粗粒度可读树（而裸 `EXPLAIN` 是 VDBE 字节码，另一回事）；**PostgreSQL** 的 `EXPLAIN` 是带代价估算的计划树，`ANALYZE` 才真跑、`BUFFERS` 看 I/O；**MySQL** 的 `EXPLAIN` 是表格（`type/key/Extra`），`FORMAT=TREE`/`EXPLAIN ANALYZE` 才给树与实测。

同一个概念在三家里叫法都不同——「全表扫描」在 SQLite 是 `SCAN`、PG 是 `Seq Scan`、MySQL 是 `type: ALL`；「覆盖索引」在 SQLite 是 `USING COVERING INDEX`、PG 是 `Index Only Scan`、MySQL 是 `Extra: Using index`。跨库排查性能时，先把这张「词表」对齐，再看命中行估算与实际是否吻合，就能快速定位「该走的索引为什么没走」。
