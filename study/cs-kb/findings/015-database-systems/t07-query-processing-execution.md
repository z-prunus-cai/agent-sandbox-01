## 03-7.1 查询处理流水线与代价度量单位

### 03-7.1.1 查询处理的三大阶段：解析与翻译、优化、执行

一条 SQL 查询在数据库内部要依次经过三个阶段。第一阶段**解析与翻译（parsing and translation）**：解析器（parser）先做词法/语法分析，把查询文本变成一棵语法树，并做语义检查（表名/列名是否存在、类型是否匹配、权限是否够），然后把它翻译成一个**关系代数表达式**（或等价的内部算子树）。第二阶段**优化（optimization）**：因为同一个关系代数表达式往往有很多等价写法、每个算子又有多种实现算法，优化器要在这些可能的**执行计划（execution plan / query plan）**里挑一个预计代价最低的。第三阶段**执行（evaluation / execution）**：执行引擎按选定的物理计划实际跑，产出结果元组。

DBSC 7e §15.1 与 R&G §12.1 给的是同一套三阶段划分（DBSC 把「翻译」并入解析阶段一起讲）。给初学者的直觉：可以类比编译器——解析像前端把源码变 AST，优化像编译优化选最快的指令序列，执行像 CPU 真正跑。关键区别是数据库的「优化」不是可选的锦上添花，而是**必需**的：同一个查询不同计划的代价可能差几个数量级（比如大表连接用错算法），所以数据库一定要先估代价再决定怎么跑。本报告聚焦第三阶段「执行」——假设优化器已经把计划定好了（怎么定是 03-8 的事），只问每个算子怎么跑、花多少 I/O。

### 03-7.1.2 逻辑算子 vs 物理算子；执行计划是一棵算子树

优化阶段之所以有的选，是因为要把**逻辑算子（logical operator）**（关系代数层面的「做什么」，如「连接 R 和 S」）落实成**物理算子（physical operator）**（「用哪种算法做」，如「用 hash join 连接 R 和 S」）。一个查询的执行计划就是一棵**物理算子树**：叶子是对基表的访问（顺序扫描 / 索引扫描），内部结点是选择、投影、连接、排序、聚合等算子，数据从叶子往根流动，根结点输出最终结果。

给初学者的落点：同一句 `SELECT ... FROM R JOIN S WHERE ...` 对应唯一的逻辑意义，但物理计划千变万化——连接可以是 nested-loop / merge / hash，基表可以全扫或走索引，先做选择还是先做连接顺序也不同。这就是为什么后面 03-7.2~03-7.5 要为每个算子列出「一个逻辑算子对应哪几种物理算法、各自代价多少」，因为这正是优化器和读 `EXPLAIN` 的人要面对的选择空间。一个易错点：`EXPLAIN` 打印出来的就是这棵物理算子树（缩进表示父子/数据流关系），读懂它就是读懂「这句查询到底会怎么跑」。

### 03-7.1.3 代价度量单位：块传输 + 寻道（DBSC 7e 模型）

执行算法的代价主要由**磁盘 I/O** 决定，因为磁盘访问比内存和 CPU 慢几个数量级。DBSC 7e §15.1.1 采用的代价模型把 I/O 拆成两个可分别计量的量：**块传输次数（block transfers）**和**寻道次数（seeks）**。设一次块传输耗时 t_T、一次寻道耗时 t_S，一个操作若需要 b 次块传输和 S 次寻道，其估计代价为：

代价 = b × t_T + S × t_S

区分这两项的原因是：寻道（磁头移动/随机定位）比顺序读一个块贵得多，所以「随机读 100 个分散的块」远比「顺序读 100 个相邻的块」慢——前者是 100 次寻道 + 100 次传输，后者是 1 次寻道 + 100 次传输。

给初学者的直觉与几个约定要先钉住。其一，DBSC 的代价**只算 I/O，通常忽略 CPU 时间**（作为简化；现代内存充裕、列存/向量化引擎里 CPU 反而是瓶颈，那属 L6-04）。其二，DBSC 通常**不把最终结果写回磁盘的代价算进去**（因为各算法都一样、且结果常直接流给上层），也常忽略读索引块本身省下的一点点。其三，早期教材和很多课程（含 CMU 15-445）用更简化的模型：**代价 = 读写的磁盘页（page/block）数**，不单独区分寻道——两种模型结论方向一致，只是 DBSC 更细。本报告的公式以 DBSC 的「块传输 + 寻道」为准，但为便于初学者把握主干，重点看「块传输」项（它决定量级），寻道项作为修正。

### 03-7.1.4 关键符号约定（贯穿全章代价公式）

后面所有代价公式都用同一套记号，先集中列清楚。对关系 r：b_r 表示存放 r 的元组所占的**磁盘块数**；n_r 表示 r 的**元组数**；V(A, r) 表示 r 中属性 A 的**不同取值个数**（distinct values，用于估选择/连接结果大小）。M 表示**可用内存缓冲区的块数**（buffer pages）。做连接 r ⋈ s 时，习惯把 r 叫**外表（outer）**、s 叫**内表（inner）**。索引方面：h_i 表示 B+树索引的**高度（层数）**。

给初学者的提醒：这些符号里最要分清的是 b_r（块数）和 n_r（元组数），二者差一个「每块能放几条元组」的因子（叫 blocking factor，一块通常能放几十到几百条元组）。代价公式基本都以**块数 b** 为单位（因为 I/O 以块为最小单位），只有像基本 nested-loop 这类「按元组循环」的算法才会出现 n_r。M（内存块数）是排序和连接算法代价的关键旋钮——内存越大，能一次装下越多数据，趟数越少、代价越低，这个直觉在 03-7.3 和 03-7.4 反复出现。

## 03-7.2 选择运算的实现

### 03-7.2.1 线性扫描（A1）：最朴素、最通用

**线性扫描（linear scan / full table scan）**逐块读入关系的每一个块、对每条元组测试选择条件，是最基本的选择算法。它的代价（DBSC §15.3.1 算法 A1）为：

代价 = b_r × t_T + 1 × t_S

即读 b_r 个块共 b_r 次块传输，加 1 次寻道（假设关系连续存放，一次定位后顺序读完）。若选择条件是「等于码属性（key）」，找到即可停，平均只需扫一半，块传输约为 b_r / 2。

给初学者的直觉与要点：线性扫描的最大优点是**无条件可用**——不管有没有索引、条件是什么形式（等值、范围、复杂表达式）它都能跑，所以它是所有选择算法的「保底方案」。它的代价与选择条件的选择性（选出多少行）**无关**，永远扫全表。易错点：初学者常以为「有索引就一定比全扫快」，其实当选出的行占比很大（比如要选出 80% 的行），走索引反而因为大量随机回表而更慢，优化器这时会主动选线性扫描——这正是 03-7.2.4 要讲的权衡。

### 03-7.2.2 索引扫描：等值查找（A2/A4）

当选择属性上有索引时，可用**索引扫描**。DBSC 分几种情况。A2「主索引（primary index，即数据按该索引排序聚簇）+ 等值 + 码属性」：沿 B+树从根走到叶再取那一条记录，代价为：

代价 = (h_i + 1) × (t_T + t_S)

h_i 是树高，每层一次块传输 + 一次寻道（随机跳），最后 +1 取数据块。A4「二级索引（secondary index）+ 等值 + 码属性」代价同样是 (h_i + 1) × (t_T + t_S)，因为码属性最多命中一条记录。

给初学者的直觉：B+树等值查找的代价基本等于「树高」，而 B+树因为 fanout 很大（一个内部结点能指向几百个孩子），树高通常只有 3~4 层（先修 03-6），所以等值查找是「几次 I/O 就命中」，这正是索引的威力。要点：这里每层都算一次寻道，是因为 B+树的结点在磁盘上不一定相邻，逐层下降是随机跳转。

### 03-7.2.3 索引扫描：非码等值与范围查找（A3/A5/A6）

若等值条件的属性**不是码**（一个值可能对应多条记录），代价取决于用哪种索引。A3「主索引 + 等值 + 非码」：匹配的记录因为聚簇而**连续存放**，设它们占 b 个块，代价为：

代价 = h_i × (t_T + t_S) + t_S + b × t_T

即下降树高 h_i 层（随机），再一次寻道定位到第一个匹配块，然后顺序读 b 个匹配块。A5「二级索引 + 等值 + 非码」最坏：n 条匹配记录可能散落在 n 个不同块上，每条都要一次随机 I/O：

代价 = (h_i + n) × (t_T + t_S)

范围查询（`>`, `<`, `BETWEEN`）类似：主索引（A6）先定位区间下界再顺序扫（连续，便宜）；二级索引范围扫要对每条命中记录做一次随机回表（可能很贵）。

给初学者的关键落点：**A5 是「二级索引未必比全扫快」的典型**——如果 n 很大（命中很多行），(h_i + n) 次随机 I/O 会远超线性扫描的 b_r 次顺序 I/O。这就是聚簇索引（数据按索引物理有序）与二级索引（索引与数据物理分离、需回表）代价差异的根源（先修 03-6.3「回表」）。所以「非码 + 命中多」时优化器往往弃用二级索引。

### 03-7.2.4 选择性、位图/组合与算法选择

选出行数占总行数的比例叫**选择性（selectivity）**。优化器为一个选择挑算法，本质是比较「线性扫描的固定代价 b_r」与「索引扫描随命中数增长的代价」，命中越少索引越划算、命中越多越倾向全扫。当条件是多个属性上条件的 AND/OR，可用**合取选择**（用一个最挑剔的索引先筛、余下条件在内存里逐条测）或对多个二级索引结果做**位图/指针的交并**（bitmap index scan，先在内存里把各索引命中的记录指针做 AND/OR，再按物理顺序一次性回表，避免重复随机跳）。

给初学者的直觉：位图扫描是「先把要读哪些块算清楚、排好序，再顺序去读」，把二级索引的随机回表尽量转成顺序 I/O，是 PostgreSQL 里 `Bitmap Heap Scan` 的思路。要点：这里已经能看到「优化器要估命中行数才能选算法」，而估得准不准依赖统计信息——那是 03-8.3 的基数估计。本节只需记住结论：**选择算法之争 = 线性扫描 vs 索引扫描，胜负由选择性（命中多少行）决定，二级索引在命中多时会输。**

## 03-7.3 排序：外部归并排序

### 03-7.3.1 为什么需要外部排序

排序在数据库里无处不在：`ORDER BY`、`GROUP BY`、`DISTINCT`、sort-merge join、建索引都要排序。问题是待排数据往往**放不进内存**（b_r 远大于 M），内存里的快排/归并排序（内部排序）用不了，必须用**外部排序（external sorting）**——只能一次装 M 个块进内存、其余留在磁盘、通过多趟读写磁盘完成排序。经典算法是**外部归并排序（external merge sort）**（DBSC §15.4、R&G §13.1、CMU 15-445 L11）。

给初学者的直觉：外部排序的核心矛盾是「内存太小、数据太大」，解决思路和外面世界整理一大堆文件一样——先把能一次拿上手的一小叠整理好（生成有序小段），再把这些整理好的小段两两/多路合并成更大的有序段，直到并成一整段。所以它天然分成「生成初始归并段」和「多路归并」两个阶段。

### 03-7.3.2 阶段一：生成初始归并段（run generation）

第一阶段反复做：读入 M 个块的数据到内存 → 用内部排序把它们排好 → 作为一个**归并段（run）**写回磁盘。重复直到全部数据都变成有序段。初始归并段的个数为：

初始归并段数 = ⌈b_r / M⌉

给初学者的要点：每个初始段的大小是 M 个块（最后一段可能不足），段内已完全有序，但段与段之间还没合并。内存越大（M 越大），初始段越大、段数越少，后面要合并的趟数就越少——这是「内存换趟数」的第一处体现。

### 03-7.3.3 阶段二：(M−1) 路归并与趟数

第二阶段做**多路归并**：用 M 个内存块里的 M−1 个各作为一个输入段的读缓冲、留 1 个作输出缓冲，一次可把 **M−1 个有序段合并成一个更大的有序段**。若一趟合不完（段数 > M−1），就一趟趟做，每趟把段数缩小为原来的 1/(M−1)，直到只剩一个段。所需的**归并趟数**为：

归并趟数 = ⌈log_{M−1}(⌈b_r / M⌉)⌉

即以初始段数 ⌈b_r/M⌉ 为起点、每趟除以 (M−1)、直到 1 所需的趟数。这就是任务 prompt 里所指的「外部归并趟数 ⌈log_{b−1}(N/b)⌉」型公式（这里底数是 M−1、真数是初始段数）。

给初学者的直觉与易错点。为什么留 1 块作输出、只能 M−1 路？因为归并时要同时打开 M−1 个输入段各读一块、还要一块攒输出，共 M 块正好占满内存。易错点一：底数是 **M−1** 不是 M（漏了输出缓冲那 1 块）。易错点二：真数是**初始段数 ⌈b_r/M⌉**，不是 b_r 本身（run generation 已经把数据压成了 ⌈b_r/M⌉ 个段）。一个数值感受：M=11、b_r=1000 时，初始段数 ⌈1000/11⌉=91，趟数 ⌈log₁₀(91)⌉=2——一千个块只要两趟归并就排完，可见外部排序趟数增长极慢（对数级）。

### 03-7.3.4 总 I/O 代价公式

把两阶段的读写加起来，外部归并排序的**总块传输次数**（DBSC 7e §15.4，已用 WebSearch 对一手表述二次核实 2026-07-29）为：

总块传输 = b_r × (2 × ⌈log_{M−1}(b_r / M)⌉ + 1)

推导给初学者讲清：run generation 阶段读全部 b_r、写全部 b_r，是 2b_r；此后每一趟归并都要把全部数据读一遍、写一遍，也是 2b_r，共 ⌈log_{M−1}(b_r/M)⌉ 趟；但**最后一趟的输出直接流给上层算子、不写回磁盘**，省下 b_r。合起来 2b_r（run gen）+ 2b_r×趟数 − b_r（省最后写）= b_r×(2×趟数 + 1)，正是上式。若还要计寻道，DBSC 给出寻道次数约为 2⌈b_r/M⌉ +（每趟的段定位次数），此处从略。

给初学者的落点：记住主干「**总 I/O ≈ 2 × b_r × 趟数**」就够用——每趟把所有数据搬进搬出一次（2b_r），趟数是对数级（M 越大越少）。这解释了为什么数据库给排序分配的 `work_mem`（PostgreSQL）/内存越大，大排序越快：M 变大直接压低趟数。

## 03-7.4 连接算法

### 03-7.4.1 连接算法总览与记号

连接 r ⋈ s 是执行层代价最高、算法最多的算子，经典有五种：嵌套循环（nested-loop）、块嵌套循环（block nested-loop）、索引嵌套循环（indexed nested-loop）、归并连接（sort-merge join）、散列连接（hash join）。约定 r 为外表、s 为内表，b_r/b_s 为块数、n_r/n_s 为元组数，M 为内存块数。以下公式主要以**块传输**为主线（DBSC §15.5），寻道作次要修正。核心心智模型：连接就是「为外表每一行找内表里能配上的行」，五种算法只是**用不同方式减少『为找配对而反复读内表』的 I/O**。

### 03-7.4.2 （元组级）嵌套循环连接

最朴素的**嵌套循环连接（nested-loop join）**是双重循环：外层遍历 r 的每条元组 t_r，内层为每个 t_r 遍历 s 的全部、测连接条件。它无需索引、无需排序、支持任意连接条件（包括非等值 θ 连接）。最坏情况（内存只够放两个块，一读 r 一读 s）的块传输为：

代价 = n_r × b_s + b_r

因为外层每读一条 r 元组，内层就要把 s 整个扫一遍（b_s 块），共 n_r 遍，加上读 r 自己的 b_r。若把**较小的关系整个装进内存**（b_s ≤ M−2），内层只需读一次 s：

代价 = b_r + b_s

给初学者的关键：n_r × b_s 这一项是灾难——**用元组数 n_r 去乘块数 b_s**，因为内层循环重读 s 的次数等于 r 的元组数而非块数。所以除非小表能全进内存，元组级嵌套循环几乎不用，实践中总是升级成下面的「块」版本。易错点：谁当外表谁当内表影响代价，通常**把较小的关系当外表**更省（也可减少内层重读次数），但更根本的改进是块嵌套循环。

### 03-7.4.3 块嵌套循环连接

**块嵌套循环连接（block nested-loop join）**把循环的粒度从「元组」提到「块」：外层每读入 r 的**一个块**，就对内层 s 的每个块、把这一对块里所有元组两两配对。最坏情况块传输为：

代价 = b_r × b_s + b_r

关键改进是内层重读 s 的次数从 n_r 降到 b_r（块数远小于元组数）。进一步，若有 M 个内存块，可让外表一次读入 M−2 块（1 块给 s 输入、1 块给输出），内层 s 只需为「每 M−2 块外表」重扫一次：

代价 = ⌈b_r / (M − 2)⌉ × b_s + b_r

给初学者的落点：对比元组级的 n_r×b_s，块级是 b_r×b_s，两者差一个「每块元组数」的大因子，这就是「块」优化的全部价值——**尽量少重读内表**。而给外表分配 M−2 块的做法，本质是「内存越大、外表一口气吞得越多、内表重扫越少」，又一次体现「内存换 I/O」。这是没有索引、没排序时的通用兜底连接，且同样支持任意 θ 条件。

### 03-7.4.4 索引嵌套循环连接

若连接是**等值连接**且内表 s 在连接属性上**有索引**，可用**索引嵌套循环连接（indexed nested-loop join）**：外层遍历 r 的每条元组 t_r，不再扫全 s，而是用 t_r 的连接属性值去 s 的索引里**查**匹配元组。代价为：

代价 = b_r + n_r × c

其中 c 是「用索引在 s 上做一次选择」的代价（如等值命中码属性时 c = (h_i+1)×(t_T+t_S)，见 03-7.2.2）。

给初学者的直觉：它把内层的「扫全表 b_s」换成了「查索引 c」，当 s 很大而索引让单次查找只要几次 I/O 时非常划算。要点与易错点：代价里是 **n_r × c**（外表每条元组查一次索引），所以**外表越小越好**——优化器会倾向把小表放外层、在大表的索引上探查。它只适用于等值/可用索引的连接条件；且若 r 也大，n_r 次索引查找累积起来也可能不划算，这时 hash/merge join 更好。这是 OLTP 里点查连接的主力算法。

### 03-7.4.5 归并连接（sort-merge join）

**归并连接（merge join / sort-merge join）**用于**等值连接**：先把 r 和 s 都按连接属性**排好序**，再像归并两个有序表一样，用两个指针齐头并进、匹配相等的值。若两表已按连接属性有序，只需各扫一遍：

代价 = b_r + b_s

若未排序，要加上外部排序的代价（03-7.3），总代价 = 排序代价 + (b_r + b_s)。

给初学者的直觉：因为两边都有序，指针只需单向前进、每个块各读一次即可，非常省 I/O。要点：连接属性有重复值时，一边的一段相等值要和另一边对应的一整段做笛卡尔配对，指针要回退重扫那一段（DBSC §15.5.3 详述）。它的甜点场景是**数据本就有序**（比如上游是已排序的索引扫描、或结果还要 `ORDER BY` 同一列），这时排序代价为零、b_r+b_s 极省——优化器很看重这种「interesting order」（03-8 会讲）。相比 hash join，merge join 不怕数据倾斜、且能顺带产出有序结果。

### 03-7.4.6 散列连接（hash join）

**散列连接（hash join）**用于**等值连接**，分两阶段。**划分（partition/build 前）阶段**：用同一个哈希函数 h 作用在连接属性上，把 r 和 s 各自划分成 n 个分区（partition），使得「能连接上的元组必然落到编号相同的分区对」。**探查（probe）阶段**：对每一对同号分区，把较小一方（build 输入，通常是 s 的分区）在内存里建哈希表，再用另一方（probe 输入 r 的分区）逐条探查匹配。若每个 build 分区都能装进内存（即 build 表经一趟划分后每分区 ≤ M），块传输约为：

代价 = 3 × (b_r + b_s)

即划分阶段读写各一遍（2×(b_r+b_s)）、探查阶段再读一遍（(b_r+b_s)），共 3 倍。若较小表太大、一趟划分后分区仍装不下内存，需**递归划分**，代价上升（DBSC 给出含 ⌈log_{M−1}(b_s)−1⌉ 因子的递归公式）。**混合散列连接（hybrid hash join）**在内存足够时把第一个分区直接留在内存、省去它的读写往返。

给初学者的直觉：hash join 的精髓是「用哈希把大连接切成许多互不相干的小连接」——只有落进同号分区的元组才可能配对，于是每个小连接的 build 侧能塞进内存、探查是 O(1) 哈希查找。它是**大表等值连接的默认主力**（尤其 OLAP），因为 3×(b_r+b_s) 与表大小成线性、且不要求排序。易错点/前提：只支持**等值连接**（哈希按值分桶，θ 连接不适用）；对**数据倾斜**敏感（某个哈希值巨多会导致对应分区放不下、退化）；build 侧要选**较小**的表。它与 merge join 的分工是数据库执行的经典对照：hash join 快但无序、要内存；merge join 需有序输入但产出有序、抗倾斜。

### 03-7.4.7 规范 vs 实现：SQLite 与 PostgreSQL 的连接算法

不同引擎实现的连接算法集合差别很大，这是「教材讲全五种、实现各取子集」的典型分歧，必须分账。**SQLite**（3.4x，2026）执行层主要只用**嵌套循环连接**（配合内表索引即索引嵌套循环）——它没有独立的 hash join 或 merge join 算子，靠给内表建/选索引来加速；其查询计划由 `EXPLAIN QUERY PLAN` 查看，输出是 `SCAN`（全表扫）/`SEARCH ... USING INDEX`（索引探查）这类文字。**PostgreSQL**（16/17）三种连接算法俱全——`Nested Loop`、`Merge Join`、`Hash Join`，由代价优化器自动选，并提供会话级开关强制关闭某种以做对比：`SET enable_hashjoin = off;`、`SET enable_mergejoin = off;`、`SET enable_nestloop = off;`；计划由 `EXPLAIN` / `EXPLAIN (ANALYZE, BUFFERS)` 查看。

给初学者的落点：所以「数据库怎么连接两张大表」这个问题的答案**依引擎而异**——在 SQLite 上大表等值连接可能因为只有 nested-loop 而慢（除非有合适索引），在 PostgreSQL 上则通常自动走 hash join。想在 PostgreSQL 上验证「不同表规模下算法切换」，可对小表/大表分别 `EXPLAIN`、并用 `SET enable_hashjoin=off` 前后对比计划——本报告因无运行中的 PG 服务**未实机取证**，此处仅据官方文档陈述。

## 03-7.5 其它运算的实现：去重、投影、聚合、集合运算

### 03-7.5.1 投影（projection）

**投影 π** 是取出指定的列。若投影**不要求去重**（SQL 里 `SELECT` 不带 `DISTINCT`，遵循多重集语义），实现极简单——扫一遍关系、每条元组丢掉不要的列直接输出，几乎不增加代价，且能**流水线**完成（来一条处理一条，见 03-7.6）。若投影后要**去重**（`SELECT DISTINCT`），则要额外做一次去重（见 03-7.5.2），代价才上去。

给初学者的要点：关系代数的投影 π 按集合语义**默认去重**，而 SQL 的投影**默认保留重复**（多重集语义）——这是关系代数与 SQL 的一处经典差异（先修 03-1）。所以「投影贵不贵」几乎等于「要不要去重」：不去重时投影是白菜价、可流水线；去重时它退化成 03-7.5.2 的排序/散列问题。

### 03-7.5.2 去重（duplicate elimination）

**去重**把重复元组合并成一个，有两条实现路线，与排序/连接同源。**排序去重**：把关系按全部输出列排序（外部归并排序，03-7.3），排完后重复元组必然相邻，扫一遍相邻比较即可剔重。**散列去重**：用哈希把元组分区，同一元组必落同区，每区在内存里用哈希表判重。两者代价都主要是那次排序或散列划分的代价（≈ 一次外部排序 / 一次哈希扫描）。

给初学者的直觉：去重的本质是「让相同的元组聚到一起才好比」，排序（让相同的挨着）和散列（让相同的进同桶）是把「相同的聚到一起」的两种通用手段——这个「sort 或 hash」的二选一模式在去重、分组聚合、集合运算里反复出现，记住它就抓住了本小主题的主线。要点：去重不能流水线做完（要看过足够多元组才知一条是不是重复），所以它是**阻塞（blocking）**算子，需要先把数据攒起来。

### 03-7.5.3 聚合与分组（aggregation / GROUP BY）

聚合（`COUNT/SUM/AVG/MIN/MAX`）配合 `GROUP BY` 分组，实现同样是 **sort 或 hash 二选一**。**排序聚合**：按分组列排序，使同组元组相邻，扫一遍对每组累积聚合值。**散列聚合（hash aggregation）**：用分组列做哈希，在内存哈希表里为每个组维护一个累加器，扫一遍边扫边累加。像 `SUM/COUNT/AVG` 这类可增量累加的聚合，散列聚合无需先排序、一趟即可，通常更快；`AVG` 实现上是同时累加 sum 和 count 最后相除。

给初学者的直觉与易错点：分组聚合就是「把同组的行聚到一起、每组算一个汇总值」，同样靠 sort（同组相邻）或 hash（同组同桶）实现。易错点：`AVG` 不能靠「对各分块的平均再平均」得到（除非等权），要累加 sum 与 count 再相除——所以聚合状态是 (sum,count) 而非单个 avg。`MIN/MAX` 只需维护当前极值。散列聚合是现代数据库分组的默认选择，但组数极多、哈希表放不下内存时要溢出到磁盘（分区后分批），代价上升。

### 03-7.5.4 集合运算（UNION / INTERSECT / EXCEPT）

集合运算把两个关系按集合语义并（`UNION`）、交（`INTERSECT`）、差（`EXCEPT`）。实现仍是 **sort 或 hash 二选一**：**排序法**把两关系分别排序后归并——并集输出两边所有（去重），交集只输出两边都有的，差集输出左有右无的。**散列法**先对一个关系建哈希表，再用另一个关系探查决定取舍。带 `ALL`（`UNION ALL` 等）的版本保留重复、无需去重，因而便宜得多、且 `UNION ALL` 可近乎流水线（直接把两路输出拼起来）。

给初学者的落点：`UNION`（去重）与 `UNION ALL`（不去重）的代价天差地别——前者要做一次全量去重（排序或散列），后者只是把两个输入流首尾相接。SQL 里集合运算符**默认去重**（与投影相反的约定），要重复得显式写 `ALL`。这再次落回「去重贵、sort/hash 二选一」的主线。

## 03-7.6 执行模型：火山（迭代器）模型、物化 vs 流水线

### 03-7.6.1 火山（迭代器）模型：open / next / close

把一棵物理算子树「跑起来」的经典方式是**火山模型（Volcano model）**，又叫**迭代器模型（iterator model）**或 pull-based 模型。每个算子都实现统一的三个方法：`open()`（初始化）、`next()`（返回下一条结果元组，没有则返回结束标志）、`close()`（清理）。执行时从**根算子**反复调 `next()`，根算子在自己的 `next()` 里调用**孩子算子**的 `next()` 拿输入、加工后返回一条——如此层层向下递归拉取，数据像被「从树根一条条抽上来」。

给初学者的直觉：火山模型是「按需拉取（pull）」——上层要一条、才向下层要一条，不主动多算。它的最大优点是**统一优雅**：任意算子只要实现 open/next/close 就能任意拼装成树，代码高度模块化，这也是它自 1990 年（Graefe 的 Volcano 系统）以来统治了几十年、PostgreSQL 执行器（`ExecProcNode`）至今仍是这套结构的原因。要点：`next()` 一次返回**一条元组**，这叫 tuple-at-a-time（一次一元组）。

### 03-7.6.2 物化（materialization）vs 流水线（pipelining）

算子间传数据有两种方式。**物化（materialization）**：一个算子把它的**全部**输出结果先完整算出来、写到一个临时结果（内存或磁盘），下一个算子再从这个完整中间结果读——中间结果被「落地」了。**流水线（pipelining）**：一个算子每产出一条（或一批）元组就**立即**交给上层算子处理，不落地整个中间结果，多个算子像流水线一样同时在跑不同的元组。火山模型天然就是流水线式的（`next()` 逐条上传）。

给初学者的直觉与权衡：流水线省掉了写/读中间结果的 I/O、还能尽早吐出第一条结果（低延迟，利于 `LIMIT`），是首选。但**有些算子无法流水线**——它们必须看过全部输入才能产出第一条输出，叫**阻塞算子（blocking / pipeline breaker）**，典型是排序（要看完所有元组才知最小的是谁）、聚合、去重、hash join 的 build 阶段。遇到阻塞算子，其输入侧就必须物化（攒齐）。所以真实计划是「流水线段被阻塞算子切成几截」的混合体。易错点：流水线不是「更并行」而是「不落地中间结果、边产边用」；阻塞算子处必然打断流水线、常伴随临时文件（大排序/大聚合溢出磁盘就是这么来的）。

### 03-7.6.3 规范 vs 实现：PostgreSQL 迭代器 vs SQLite 字节码

执行模型的实现也分账。**PostgreSQL**（16/17）执行器是标准的火山/迭代器风格：计划树的每个 plan node 通过 `ExecProcNode` 被逐层拉取，pull-based、一次一元组（近年也引入部分批处理，但主干仍是迭代器）。**SQLite**（3.4x）走的是**不同的路子**：它把查询计划**编译成字节码程序**，由内部的虚拟机 **VDBE（Virtual DataBase Engine）**逐条执行字节码指令（可用 `EXPLAIN` 看字节码、`EXPLAIN QUERY PLAN` 看高层计划）——这不是教科书式的算子树递归调用，而更像「把计划翻译成一段小程序去跑」。两者最终都实现了一次一元组的流式语义，但机制不同。

给初学者的落点：火山迭代器是**最经典、最主流**的教学与实现模型（PostgreSQL 是活教材），但它不是唯一实现——SQLite 的字节码 VM 是另一种工业实现，说明「怎么把计划跑起来」有多种工程选择。

### 03-7.6.4 边界：火山模型的开销与后续演进（点到为止）

火山模型每处理一条元组都要一串虚函数/`next()` 调用，当数据量巨大（OLAP 扫几亿行）时，这种**一次一元组的函数调用开销**会成为瓶颈（CPU 时间占比高）。现代分析型引擎因此发展出**向量化执行**（一次 `next()` 传一批约上千行、摊薄调用开销）和**查询编译/JIT 代码生成**（把算子树直接编译成机器码、消除解释开销），以及**多核/分区并行执行**（morsel-driven 等）。

给初学者的边界申明：这些是本报告的**下沉边界**——向量化、JIT、并行执行属内核级主题，留 **L6-04**（§04-4 向量化、§04-5 查询编译、§04-8 调度与多核并行）。本报告到「火山模型有 per-tuple 开销、故有向量化/编译/并行的后续动机」为止，不展开其实现。初学者只需记住：火山迭代器是理解一切执行模型的**起点和基线**，后续所有优化都是在「怎么减少一次一元组的开销」上做文章。
