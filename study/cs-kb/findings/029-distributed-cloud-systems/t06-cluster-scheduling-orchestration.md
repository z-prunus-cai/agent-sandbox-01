一台机器装不下的活，几千上万台机器一起干，就需要一层软件替所有作业决定"哪个任务跑在哪台机器上、抢谁的资源、失败了怎么补"。这一层就是集群调度器（cluster scheduler / cluster manager）。本主题从 Google 的 Borg 讲清一个成熟集群管理器长什么样，再把调度问题抽象成"在线装箱"，然后横向对比单体 / 两级 / 共享状态三种调度器架构，最后延伸到两类更"细"或更"薄"的执行模型：serverless 函数与 Ray 的 task/actor 调度。

本主题只讲"调度算法与资源管理"这条线。容器运行时（namespaces/cgroups）与 Kubernetes 的"编排落地"细节属于另一门系统课的范围，这里仅在架构谱系里提到 Kubernetes 作为演进结果，不展开其对象模型与控制器机制。

## 6.1 集群管理与 Borg 架构

### 6.1.1 集群管理器要解决的问题

一个集群管理器接受用户提交的"作业"，把作业拆成一批要跑的进程，然后在一大堆异构机器上决定放置位置、启动进程、监控存活、失败重启、并在资源紧张时按优先级腾挪。它把"一堆机器"抽象成"一台大计算机"，让用户只描述"我要什么"（多少 CPU、多少内存、几个副本），而不用关心"在哪台机器上"。

对初学者，最直观的类比是操作系统的进程调度器：单机 OS 把 CPU 时间片分给进程，集群管理器把整片数据中心的机器分给作业。区别在于规模和失败常态化——单台机器崩溃在集群里是每天都发生的正常事件，所以集群管理器天生要把"机器会坏、任务会挂"当默认假设，而不是异常。Borg 是这类系统的开山标杆，Google 自 2005 年起用它管理生产集群，Kubernetes 是它的思想后裔。

### 6.1.2 Borgmaster 与 Borglet 架构

Borg 把一个数据中心（或其一部分）划成若干 cell，每个 cell 由一个逻辑上集中的控制器 Borgmaster 管理，cell 内每台机器上跑一个 agent 进程 Borglet。Borgmaster 负责接收作业、做调度决策、维护整个 cell 的状态；Borglet 负责在本机启停任务、按需重启、调节本机内核资源设置，并周期性把本机状态汇报回 Borgmaster。

```
        用户 / 命令行 / 配置
                │  提交作业
                ▼
     ┌────────────────────────┐
     │  Borgmaster（5 副本）    │  ← Paxos 复制状态，选主
     │  ├─ 主进程：状态/RPC     │
     │  └─ 调度器（独立进程）    │  ← 挑机器放任务
     └────────────────────────┘
        │ RPC（下发/心跳）  ▲ 汇报本机状态
        ▼                  │
   ┌─────────┐  ┌─────────┐  ┌─────────┐
   │ Borglet │  │ Borglet │  │ Borglet │   … 一 cell 约上万台
   │ task…   │  │ task…   │  │ task…   │
   └─────────┘  └─────────┘  └─────────┘
```

Borgmaster 本身不是单点：它是五路复制的，用 Paxos 维护一份复制状态并选出主副本，主副本挂了其余副本能接管。这里正好回收先修课的共识知识——集中式控制器要高可用，就把它的状态做成复制状态机。论文给出的量级参考是一个中位 cell 约 1 万台机器，均由这一套逻辑集中的 Borgmaster 服务；调度逻辑被拆成一个独立的调度器进程，与主进程解耦，避免调度慢拖累整体状态管理。一个易错点是把 Borglet 当成"从调度器"——它不做调度决策，只是执行 Borgmaster 下发的指令并做本机管理，真正的放置决策集中在 Borgmaster 的调度器里。

### 6.1.3 作业-任务模型与 alloc

用户提交的单位是作业（job），一个 job 由若干同构的任务（task）组成，每个 task 最终是某台机器上的一个（或一组）Linux 进程。job 描述"要跑什么、跑几份、每份要多少资源"，task 是被实际调度和放置的最小单位。此外 Borg 有 alloc（allocation 的缩写）概念：一块在机器上预留出来、可容纳一到多个 task 的资源"保留位"，用于把相关任务捆在同一台机器上（例如主进程和它的日志搬运边车）。

理解这个三层模型的关键是"声明式副本"：你说"给我 10 个副本、每个 2 核 4 GB"，系统负责找 10 个位置并维持这个数目，某个 task 挂了就再拉一个补上。这跟手动 ssh 到机器上起进程是两种世界——你管的是期望状态，系统管的是让现实收敛到期望状态。alloc 则解决"我这几个任务必须共处一机、共享本地磁盘/端口"的放置约束，把它们当成一个整体来预留和调度。初学者常混淆 job 和 task：job 是逻辑上的一组，真正落到某台机器、会被抢占、会重启的是单个 task。

### 6.1.4 优先级、优先级带与配额

Borg 给每个 job 一个优先级（priority，一个小正整数）和一份配额（quota）。优先级决定资源紧张时谁让谁：高优先级 task 可以通过抢占（杀掉）低优先级 task 来获得资源。优先级被归为几个带（band），按优先级从高到低是 Monitoring、Production、Batch、Best-effort（测试/免费）。配额则是准入控制（admission control）手段，表示"某优先级下、某段时间内、允许申请的资源向量上限"，在作业提交时就检查，防止用户申请超过其获批的容量。

```
优先级带（高 → 低）：
  Monitoring     监控类，最高
  Production     生产/在线服务   ← 同带内互不抢占（避免级联）
  Batch          批处理
  Best-effort    测试 / 免费额度  ← 最先被抢占
```

生产带内部的 task 彼此不抢占，这是为了避免"抢占级联"——A 抢了 B，B 被踢回队列又去抢 C……如果生产服务之间可以互抢，就会引发连锁反应把在线服务打崩。配额和优先级要分开理解：优先级是运行期"谁赢"的规则，配额是提交期"你有没有资格申请这么多"的规则；配额通常和物理容量规划、内部计费挂钩，按月度粒度分配，本身不在 Borg 运行期路径上决定放置。初学者别把"高优先级"等同于"一定拿得到资源"——你还得先有配额、且集群里确实存在可抢占的低优先级资源。

### 6.1.5 高利用率与混部

Borg 追求高机器利用率的核心手段是混部（co-location）：把对延迟敏感的在线生产任务和可被压缩、可被抢占的批处理任务放在同一批机器上。在线任务通常按峰值申请资源却长期用不满，把批处理塞进这些空隙，就能显著抬高整体利用率，而不必为批处理单独买机器。

这解释了为什么优先级和抢占机制如此重要：混部要成立，就必须保证在线任务需要资源时能立刻把批处理踢开，否则混部反而会拖垮在线服务。Borg 用优先级带 + 抢占 + 资源回收（对非生产任务按实际用量而非申请量估算可行性）来实现"批处理蹭空隙、在线随时优先"。这一思路是后续所有集群调度器的共同底色，也是"云省钱"的物理来源之一：同一台机器同时服务多个租户/多类负载，靠调度器动态腾挪来隔离与超卖。

## 6.2 调度算法与装箱

### 6.2.1 调度问题即在线装箱

把"任务需要一个资源向量（CPU、内存、磁盘…），机器有一个资源容量向量"这件事抽象出来，调度就是多维在线装箱（online bin-packing）：不断到来的物品（任务）要塞进容量有限的箱子（机器），目标是用尽量少的箱子、尽量少的碎片装下尽量多的物品。"在线"指任务是陆续到达的，做决定时不知道未来还会来什么。

```
机器容量：[CPU=16, MEM=64GB]
待放任务：t1[4,8]  t2[2,16]  t3[8,8] …
放置即：为每个任务找一台"放得下"（各维都够）的机器
碎片：某台机器 CPU 还剩很多但内存已满 → 剩的 CPU 浪费
```

初学者最容易忽略"多维"这个词的分量：单维装箱（只看一种资源）已经够难，现实中至少要同时满足 CPU 和内存两维，还常有磁盘、网络带宽、GPU、端口等约束。一个任务在某台机器上"可行"意味着每一维都放得下，缺一维都不行。多维还带来"碎片"问题：一台机器可能 CPU 有余但内存耗尽，剩余 CPU 就成了谁都用不上的碎片。调度器的好坏，很大程度上就是它制造多少碎片、能不能装下大任务。

### 6.2.2 可行性检查 + 打分两阶段

Borg 的调度算法分两步：先做可行性检查（feasibility checking），筛出所有"这台机器能放下这个任务"的候选机器；再做打分（scoring），在可行机器里挑一台最好的。可行性看的是硬约束（资源够不够、约束满不满足），打分看的是软目标（放哪台最优）。

对生产任务，可行性按 job 声明的资源上限（limit）来算；对非生产任务，则按对已有任务实际用量的预留估算来算——这正是混部超卖的技术实现：非生产任务的可行性不按它申请的量、而按它大概率会用的量来判断，于是能塞进更多。这个两阶段结构几乎被所有后来的调度器沿用（包括 Kubernetes 的 Predicates/Filter 再 Priorities/Score）。一个常见误解是以为调度器会全局最优地一次性安排所有任务——实际是逐个任务贪心放置的在线过程，先到先安排，不回头重排。

### 6.2.3 best-fit 与 E-PVM 的取舍

打分该偏向哪台机器？两种极端策略：best-fit（最佳适应）优先选"放下这个任务后剩余最少"的机器，把任务尽量挤在一起，减少碎片、留出整机给大任务，但热点集中、没给突发留头寸；E-PVM（Enhanced-PVM）则反过来把负载摊到尽量多的机器上，为负载尖峰留头寸、更稳，但会加剧碎片、让大任务难以找到整机。

Borg 的打分是两者的混合（hybrid），既想减碎片又想留头寸。论文明确提到：Borg 早期纯用 E-PVM，结果任务分布很均匀但碎片严重、大 job 难以塞下，于是转向混合策略。这组对立是调度器设计的永恒张力，初学者可以用旅馆开房间类比：best-fit 是"尽量把客人塞满几间房、空出整间大套房"，E-PVM 是"每间房都住一点、谁都别太挤"。前者利于接大团，后者利于抗突发。没有免费午餐，实际系统都在两端之间调。

### 6.2.4 优先级抢占与抢占级联

当高优先级任务找不到足够空闲资源时，调度器会抢占（preempt，即杀掉）选中机器上的低优先级任务来腾空间，被抢占的任务被放回待调度队列，稍后另寻位置重跑。这让集群能保证在线服务随时拿到资源，同时用低优先级批处理填满平时的空隙。

抢占必须防"级联"：如果任务 A 抢了 B，B 被踢回队列后又去抢 C，C 再抢 D……就会引发连锁踢人，在线服务反复被中断。Borg 的对策是同一生产优先级带内部互不抢占——只有更高带能抢更低带，同带之间和平共处。写玩具调度器时这是最容易踩的坑：一旦允许同级互抢，很容易造出震荡（两个任务反复互相踢出、谁都跑不完）。另一个易错点是忘了被抢占任务要"可重跑"——批处理任务通常无状态或有检查点才适合被抢，有状态的在线服务被随意杀会丢数据，这也是为什么优先级带和任务类型要对应起来。

### 6.2.5 装箱的困难本质与启发式

多维装箱是 NP-hard 的：没有已知的多项式时间算法能对任意输入求出最优放置，所以现实调度器全都用启发式（heuristic）——feasibility + scoring、best-fit/E-PVM 混合都是启发式，追求"够好且够快"，不追求最优。集群成千上万台机器、每秒大量调度请求，算法必须在毫秒级出结果，根本没有时间求最优解。

理解"NP-hard 所以用启发式"能解释很多现象：为什么调度结果不是全局最优、为什么会有碎片、为什么不同调度器策略差异这么大——因为大家都在同一个难问题上用不同的近似取舍。可以在本机用 Python 写个几十行的多维贪心装箱 + 优先级抢占玩具来体会：随机生成任务流，对比 best-fit 与"分散"两种打分下的机器数与碎片率，很快就能看出两种策略在利用率和抗突发上的此消彼长。这类小实验能加固直觉，但不替代对原始论文的比对。

## 6.3 两级 / 共享状态调度

### 6.3.1 单体调度器与其局限

最朴素的架构是单体调度器（monolithic）：一个中央调度进程掌握全部集群状态，所有作业的放置都由它串行决定。Borg 本质上是精心工程化的单体调度器（调度逻辑集中在 Borgmaster 的调度器进程里）。它的优点是全局视野完整、决策一致；缺点是这一个进程既是性能瓶颈也是可扩展与可演进的瓶颈——想给机器学习作业加一套特殊调度逻辑，就得改这份共用代码，各类负载的调度策略互相纠缠。

理解这个局限是理解后面两级/共享状态两条演进路线的前提：它们都是为了"让多种框架/多种调度逻辑并存，而不必挤进同一个中央调度器"而生。初学者可以把单体调度器想成"全公司只有一个排班主管"——他视野最全，但所有排班都得等他一个人批，且他脑子里只有一套排班规则。规模大了之后，要么把权力下放（两级），要么让多个主管并行看同一张班表、冲突了再重试（共享状态）。

### 6.3.2 两级调度与 Mesos 的 resource offer

Mesos 采用两级调度：底层一个中央资源管理器（Mesos master）不直接决定任务放哪，而是把空闲资源以 offer（要约）的形式主动推给上层各个框架（framework，如 Spark、Hadoop），由框架自己决定接受哪些 offer、在拿到的资源上放什么任务。放置决策被下放到框架，master 只管把资源公平地分发给各框架。

```
两级（Mesos）：master 发 offer，framework 自己挑
   ┌──────────── Mesos master ────────────┐
   │  资源池：机器A[..] 机器B[..] …          │
   │  按 DRF 决定"这轮把哪些资源 offer 给谁" │
   └───┬───────────────────────┬───────────┘
   offer│(一次只给一个框架)      │offer
        ▼                       ▼
   ┌─────────┐             ┌─────────┐
   │Spark 框架│             │Hadoop框架│  各自决定接不接、放什么
   └─────────┘             └─────────┘
```

关键机制是"悲观锁"式的冲突避免：master 一次只把某份资源 offer 给一个框架，在该框架考虑期间别人看不到这份资源，等于对它加了锁。这样天然不会有两个框架抢同一份资源，但代价是并发度低——一个慢框架捏着 offer 迟迟不决定，会拖住这份资源不让别人用；而且框架只能看到被 offer 给自己的那一小块，看不到全局，难做需要全局视野的决策（如"抢占别人的任务"）。这正是 Omega 后来批评 Mesos 的点。初学者要抓住："两级 = 放置权下放到框架 + master 靠独占 offer 避免冲突"。

### 6.3.3 DRF 主导资源公平

Mesos 用什么标准决定"这轮把资源 offer 给哪个框架"？答案是 DRF（Dominant Resource Fairness，主导资源公平）。当每个框架对不同资源的需求比例不同时（一个吃 CPU、一个吃内存），单看某一种资源无法公平；DRF 把每个用户的"主导资源"（其占集群比例最高的那种资源）拉平，作为多资源下 max-min 公平的推广。

DRF 的可贵在于它同时满足几条理想性质：激励共享（合并资源池不会让谁吃亏）、防策略（strategy-proof，谎报需求占不到便宜）、无嫉妒（envy-free，没人愿意换成别人的分配）、帕累托高效。它由 Ghodsi 等人在与 Mesos 同届的 NSDI 2011 论文提出，并实现在 Mesos 里。举个最小例子：集群有 9 CPU、18 GB 内存，框架 A 每任务需 ⟨1 CPU, 4 GB⟩（主导资源是内存），框架 B 每任务需 ⟨3 CPU, 1 GB⟩（主导资源是 CPU），DRF 会调整两者任务数，使 A 的内存占比等于 B 的 CPU 占比，从而在"各自最紧的那一维"上公平。初学者别把 DRF 当成"平均分 CPU"——它公平的是每个用户各自的主导资源份额，不是某一种具体资源。

### 6.3.4 YARN 架构

YARN（Yet Another Resource Negotiator）是 Hadoop 的资源管理层：一个全局的 ResourceManager 负责集群资源分配，每个作业有一个 ApplicationMaster 负责该作业内部的任务管理（申请容器、监控、重试），但 ApplicationMaster 本身不做集群级调度——它向全局 ResourceManager 发资源请求，由后者统一分配。

尽管 YARN 有"每作业一个 AM"看着像下放，但由于所有资源分配决策仍集中在单一的 ResourceManager 调度器里，学术界通常把 YARN 归为单体架构（monolithic），而非真正的两级。这是初学者容易误判的点：ApplicationMaster 提供的是作业管理服务，不是调度；真正决定"哪台机器给谁"的还是那个中央调度器。YARN 与 Mesos 的核心分歧就在这："offer 模型"把放置权真正推给框架，YARN 的"request 模型"仍由中央决定放哪，AM 只是代作业提要求。两种模型各有拥趸，也各自演化出了后来的混合调度器。

### 6.3.5 Omega 共享状态与乐观并发

Omega 是 Google 在 Borg 之后探索的调度架构，走第三条路：共享状态（shared state）+ 乐观并发控制（optimistic concurrency）。集群状态放在一份中央的、基于 Paxos 的事务型存储里，多个调度器各自持有这份状态的一个副本，并行、独立地做放置决策，然后以事务方式把决策提交回中央存储；如果两个调度器碰巧选了同一份资源，提交时检测到冲突，落败者回滚、拿新状态重试。

```
共享状态（Omega）：多调度器并行看同一张全局状态，冲突再重试
   ┌──────── 中央状态存储（Paxos 事务）────────┐
   │        全局资源与任务状态（唯一真相）        │
   └──▲───────────▲───────────▲──────────────┘
      │提交(可能冲突)          │
  ┌───┴────┐  ┌───┴────┐  ┌───┴────┐
  │调度器1  │  │调度器2  │  │调度器3  │  各自持状态副本，乐观放置
  └────────┘  └────────┘  └────────┘
   冲突 → 落败者回滚，取最新状态重试
```

与 Mesos 的悲观独占 offer 相反，Omega 是乐观的：先假设不冲突、大家并行干，真撞上了再重试。这跟先修课里数据库的乐观并发控制（OCC）是同一思想。它的好处是每个调度器都能看到全局状态、并发度高、可为不同负载写不同调度器；代价是高冲突场景下重试增多、可能浪费工作。Omega 论文正是用这一点批评 Mesos：Mesos 的独占 offer 在冲突少时够用，但缺乏并行 offer 与冲突解决机制，一个慢框架会拖累全局利用率。可以用 Python 写个小实验对拍两种策略：模拟多个调度器/框架抢有限资源，统计 Mesos 式串行 offer 的等待 vs Omega 式并行提交的冲突重试率，直观感受"悲观 vs 乐观"的适用边界。

### 6.3.6 三种架构对比与演进

把三条线并排：单体（Borg/YARN）——一个中央调度器，视野全、易一致，但是瓶颈且难演进；两级（Mesos）——放置权下放框架、master 靠独占 offer 避冲突，框架看不到全局、慢框架拖累他人；共享状态（Omega）——多调度器并行看全局、乐观提交冲突重试，并发高、可插多种调度逻辑，但高冲突时重试浪费。

```
架构          放置决策在哪   看到的状态    冲突处理        代表
单体          中央唯一调度器  全局(中央)   天然无并发冲突   Borg, YARN
两级(offer)   下放到框架     只见被 offer  master 独占避免  Mesos
共享状态      多个并行调度器  全局(各持副本) 乐观提交+重试    Omega
```

时效提醒（⚙演进快·随时变，核实 2026-08-01）：这场架构之争的现实结局是行业向 Kubernetes 收敛。Apache Mesos 于 2025-08 退役、2025-10 完成迁入 Apache Attic，转为只读、不再发布版本或安全补丁，官方与二手报道均把原因归结为社区活跃度不足、行业统一到 Kubernetes。Kubernetes 的调度器在血缘上承接 Borg（同一批作者、两阶段 Filter/Score），并借鉴了共享状态思想。要点：论文层面的三种架构分类仍是理解调度器的经典框架，但具体产品的存续状态变化快——引用时应锚定"哪年"的现实，Mesos 已成历史项目而非在用系统。

## 6.4 Serverless / Lambda 执行模型

### 6.4.1 事件驱动与无状态函数

Serverless（以 AWS Lambda 为代表的 FaaS，Function as a Service）把执行单位缩到"一个函数"：你只上传一段函数代码并声明它由什么事件触发（HTTP 请求、消息到达、文件上传等），平台负责在事件到来时分配环境、运行函数、结束后回收，你不管理任何服务器。计费按实际执行时间和内存计，没有请求时不花钱。

对初学者，和前面所有系统的关键区别是抽象层级："你不再申请机器或容器，只交一个函数"。"无状态"是核心约束：函数两次调用之间不保证共享内存或本地磁盘状态，任何需要持久的东西都得写到外部存储（对象存储、数据库）。这带来极致弹性——同一函数可以瞬间被拉起成千个并行实例应对流量高峰，闲下来全部回收——但也逼你把状态外置、把逻辑写成短小、幂等、无本地依赖的片段。"serverless"不是真没服务器，是服务器被平台完全隐藏、按需瞬时供给。

### 6.4.2 执行环境生命周期与冷启动

Lambda 用"执行环境"（一个隔离的微沙箱）来跑函数。生命周期分三阶段：Init（创建环境、下载代码、启动运行时、跑函数模块级初始化代码）、Invoke（执行处理函数）、Shutdown（回收）。当一次调用能复用已存在的热环境时，跳过 Init，叫热启动；当没有可复用环境、必须新建时，要付完整的 Init 成本，这就是冷启动（cold start）。

```
冷启动：新建环境全流程
  [事件到达] → 分配环境 → 下载代码 → 启动运行时 → 跑 init 代码 → 执行 handler → 返回
              └──────────── 冷启动额外延迟 ────────────┘

热启动：复用已有环境
  [事件到达] → 直接执行 handler → 返回     (跳过上面一大段)
```

冷启动是 serverless 最著名的性能陷阱：第一次调用（或扩容出新实例、或环境闲置被回收后再来）会明显更慢。初学者常见误区是把所有慢都归咎冷启动——实际冷启动只影响一小部分调用（通常远低于总量的 1%），且可通过"把重初始化放模块级、让热环境复用"来缓解。另一个易错点是误以为热环境会永远留着：平台会在空闲一段时间后回收环境，所以间歇性流量更容易反复冷启动。init 阶段还有独立的时间预算约束（与函数超时分开计），初始化过久本身也会失败。

### 6.4.3 冷启动缓解手段

⚙演进快·锚 AWS Lambda @2026-08-01：主流缓解手段有三类。预置并发（Provisioned Concurrency）预先初始化并常驻一批热环境，让被路由到它们的调用以两位数毫秒响应，代价是常驻要额外付费；SnapStart 在部署时对初始化完成的环境拍快照，调用时从快照恢复而非从零 Init，把大部分初始化延迟省掉；再就是代码层优化（精简依赖、用 arm64/Graviton、把可复用对象放模块级）。

需要按事实分账的一点是 SnapStart 的语言覆盖会变：截至核实日期，官方资料显示 SnapStart 已对 Java、Python、.NET 通用可用，而 Node.js 通常不在 SnapStart 覆盖内、靠预置并发等其他手段。这类"哪个运行时支持哪个特性"随云厂商发布节奏频繁变动，本节所有具体覆盖面/延迟数字都锚定 2026-08-01 并标"随时变"，落地前务必以当时的官方文档为准，不要把此处数字当长期常量。给初学者的选择直觉：偶发流量能忍冷启动就不用管；对延迟敏感且流量可预测用预置并发；想省常驻成本又要压初始化就看运行时是否支持 SnapStart。

### 6.4.4 并发与自动伸缩模型

Lambda 的伸缩单位是并发（concurrency）：每个正在处理请求的环境占一个并发，平台按需要自动增减环境数，同一函数可同时有大量实例并行跑不同请求。没有"实例数"要你手动设——你设的是并发上限（含账户级配额与函数级预留），平台在上限内自动扩缩到零。

这跟传统"起 N 个副本、放负载均衡后"的模型是两种心智：serverless 里你不预置容量，请求来了才有实例、请求走了缩回去（可到零），因此天然适配尖峰和长尾流量。易错点是忽视并发配额——突发流量可能撞上账户并发上限而被限流，且冷启动会在快速扩容时集中出现（一批新环境同时 Init）。理解"并发 = 计费与伸缩的基本单位"能解释很多现象：为什么按调用次数×时长×内存计费、为什么突发时冷启动扎堆、为什么要给关键函数留预置或预留并发。

### 6.4.5 限制与适用边界

⚙演进快·锚 AWS Lambda @2026-08-01：Lambda 有一组硬/软限制，最常被引用的是单次执行超时上限 15 分钟（900 秒）、单函数内存上限约 10 GB，且 CPU 能力随内存线性增长（约 1769 MB 分到 1 个完整 vCPU）。这些数字决定了 serverless 的适用边界：适合短、突发、无状态、可并行的工作，不适合长时间批处理、需要大量本地状态或超长运行的任务。

想跑一个跑几小时的训练任务，Lambda 的 15 分钟上限直接排除它；想要更快的 CPU，往往要调高内存（因为 CPU 随内存走），于是"内存"这个旋钮其实同时在调性能与成本。这些数值是随平台演进的，此处全部标"待以官方文档为准、随时变"，核实 2026-08-01；引用时务必回查当时的服务配额页，不要凭记忆填新数字。与前面 Borg/Ray 的对比也点明了 serverless 的定位：它是把调度/放置/扩缩全部藏进平台、只暴露"函数 + 事件"的最薄执行模型，用极致运维简化换取对执行环境的控制权与时长/状态的限制。

#### 来源与时效
- 一手：AWS Lambda 官方文档——execution environment lifecycle（Init/Invoke/Shutdown 三阶段与冷启动）、function scaling / concurrency（并发为伸缩与计费单位）、SnapStart 文档、服务配额（超时 900s、内存至 10 GB、CPU 随内存、约 1769 MB≈1 vCPU）。核实日期 2026-08-01。

## 6.5 数据流 / actor 调度（Ray）

### 6.5.1 统一 task 与 actor 编程模型

Ray 是面向新兴 AI/强化学习等负载的分布式框架，它在一套引擎里统一表达两种计算：无状态的 task（远程函数调用，一次性、可并行、天然幂等）和有状态的 actor（把一个对象的方法调用序列化地路由到同一个远端实例上，保有跨调用的内部状态）。同一个动态执行引擎既调度细粒度的短 task，也管理长寿命的 actor。

对初学者，task vs actor 的分野对应"无状态函数 vs 有状态对象"：训练里每步的独立计算适合做 task（并行、失败重跑即可），而需要维持模型参数或环境状态的组件适合做 actor（状态留在那个实例里，方法调用按序打到它）。Ray 的野心是让这两类在同一框架里混用、且调度得非常快——AI 负载常有海量细粒度、亚毫秒级、动态生成的任务，传统集群调度器（Borg/Mesos 那种粗粒度、秒级放置）扛不住这种量级和粒度，这正是 Ray 要解决的问题。

### 6.5.2 全局控制存储 GCS

Ray 把系统的控制状态（task/actor 的元数据、对象位置等）集中放进一个全局控制存储（GCS，Global Control Store）——一个分片的、可容错的元数据存储（原始设计默认由 Redis 支撑）。把控制状态从调度逻辑里剥离出来、集中存到 GCS，是 Ray 架构的关键决定：调度器和其他组件变成近乎无状态，状态都在 GCS 里，于是任何组件都能横向扩展或重启后从 GCS 恢复。

这跟 Borg 把状态放进 Paxos 复制的 Borgmaster 是同一类思路（控制平面状态要可靠、可恢复），但 Ray 把它做成一个独立、分片、可被各组件共享读写的存储，以支撑极高的任务吞吐。初学者可以这样理解：GCS 是整个集群的"共享记事本"，谁做了什么、对象在哪、actor 在哪台机器，都记在这上面；组件本身不囤私有状态，坏了重启读记事本即可续上。这也是 Ray 能把调度做"分布式"而不怕组件失忆的前提。

### 6.5.3 自底向上的分布式调度

Ray 的原始调度是自底向上（bottom-up）的两层结构：每台机器有本地调度器，任务默认先尝试在本地机器调度——如果本地有跑该任务所需的对象且资源够，就地跑，省去跨机数据搬运；只有本地无法满足时，才上交给全局调度器另找机器。

```
自底向上（Ray 原始设计）：
  task 产生 → 本地调度器：本地能跑吗？
                 │是 → 本地直接跑（数据在本地，最快）
                 │否 → 上交全局调度器 → 挑一台合适机器
```

这套设计的动机是数据局部性 + 吞吐：AI 任务产生快、依赖的对象常就在产出它的那台机器上，本地优先能避免搬数据、也避免每个任务都去挤中央调度器这个瓶颈。与 Borg 的集中式放置相反，Ray 把大多数调度决策留在本地、只把兜不住的往上交，从而支撑每秒百万级任务的目标吞吐。初学者的直觉：与其所有任务排队等中央大脑发落，不如"能就地解决就地解决，实在不行才上报"，用分层把中央压力摊薄。

### 6.5.4 血统容错与分布式对象存储

Ray 用血统（lineage）做容错：每个对象都记录它是由哪个 task、吃了哪些输入算出来的（这份依赖图存在 GCS 里），某个对象因机器故障丢了，就按血统重新执行产生它的 task 把它重算出来，而不必对每个中间结果都做昂贵的复制或落盘。这和先修课批处理里 Spark RDD 的血统重算是同一思想。

配套的是一个分布式对象存储（各机器上的共享内存对象存储，任务的输入输出以不可变对象形式存放并在节点间按需传输）。把这两件事连起来看：不可变对象 + 记录血统 = 丢了能重算，于是容错很轻量。易错点是血统重算对有状态 actor 不像对无状态 task 那么直接——重跑一个纯函数 task 总能得到同样结果，但重建一个丢失的 actor 要恢复它的内部状态，需要额外机制（如从检查点恢复）。这也呼应了 6.5.1 的 task/actor 分野：无状态的那半靠血统天然可重算，有状态的那半要额外托底。

### 6.5.5 现代 Ray 的调度演进

⚙演进快·锚 Ray 原始论文 OSDI 2018 @2026-08-01：上面描述的"Redis 支撑的 GCS + 严格自底向上、依赖全局调度器兜底"是 2018 年原始论文的架构。此后 Ray 作为活跃开源项目持续重构了控制平面与调度路径——例如降低对外部 Redis 的强依赖、调整调度决策的分布方式等。这些实现细节按版本演进，随时变。

把 OSDI 2018 论文当作"理解 Ray 设计思想"的稳定锚（统一 task/actor、控制状态外置到 GCS、数据局部性优先的分布式调度、血统容错这几条心智模型是稳的），但涉及"当前 Ray 用不用 Redis、调度器具体怎么分层、某参数默认值"这类实现事实，一律以你所用的 Ray 版本官方文档为准，不要拿论文里的细节当今天的实现。本节只锚定论文层的架构思想，具体版本行为标"待核·随版本变"，核实 2026-08-01。
