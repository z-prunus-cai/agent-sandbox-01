批处理框架要回答一个工程问题：当输入是「一堆存在分布式文件系统里的大文件、总量到 TB/PB」而机器随时可能宕机时，怎么把一段计算跑遍全部数据、又不让程序员亲手处理并行、容错、数据搬运这些脏活。本大主题沿两条历史主线展开：先是 MapReduce（Google，2004）——用两个纯函数把「怎么算」和「怎么并行/容错」彻底分开；再是 Spark RDD（Berkeley，2012）——用不可变数据集加血统把中间结果留在内存、把容错从「复制/重跑整个作业」变成「按需重算丢掉的那一块」，从而让迭代类作业快一个数量级。本课只讲编程模型与集群执行机制；把它们放进数据密集型系统全景的综述叙事不在此列。

## 4.1 MapReduce 编程模型

### 4.1.1 map 与 reduce 两个用户函数

MapReduce 让程序员只写两个函数。map 接收一条输入记录（一个键值对），产出零到多个中间键值对；reduce 接收某个中间键以及该键下所有中间值的集合，产出零到多个输出值。框架负责其余一切——把输入切开并行喂给多个 map、把相同中间键的值收拢到一起、把 reduce 的输出写回文件系统。

两个函数的类型签名（键值域用不同下标表示 map 前后类型可以不同）：

```
map    : (k1, v1)          ->  list(k2, v2)
reduce : (k2, list(v2))    ->  list(v2)
```

初学者最容易的入门例子是词频统计（word count）。map 读入一行文本，对行里每个单词 w 产出一个 `(w, 1)`；shuffle 阶段把同一个单词的所有 `1` 聚到一起；reduce 收到 `(w, [1,1,1,...])`，把列表求和，产出 `(w, 总次数)`。整个程序员要写的核心逻辑就这么几行，而它能不加修改地跑在几台或几千台机器上。

关键直觉是「计算的形状被固定成两拍」：第一拍（map）是对每条记录独立、无依赖的变换，天然可并行；第二拍（reduce）是按键的聚合。因为 map 之间互不依赖、reduce 之间也按键互不依赖，框架才敢随意地把任务切碎、分发、失败重跑。这种「用受限的编程模型换来自动并行与容错」是 MapReduce 的核心交易，也是它的表达力边界（见 4.1.7）。

### 4.1.2 shuffle：按键分组与分区函数

map 的输出和 reduce 的输入之间那一层「把相同键的记录搬到同一个 reduce 上」的数据重排，叫 shuffle。它是 map 侧和 reduce 侧协作完成的：每个 map 把自己的中间输出按目标 reduce 分成 R 份写到本地磁盘；每个 reduce 再去所有 map 那里拉取属于自己的那一份，然后按键排序、分组。

「一条中间记录该去哪个 reduce」由分区函数决定。默认分区函数是对键求哈希再取模：

```
partition(key) = hash(key) mod R
```

其中 R 是 reduce 任务数。用户可自定义分区函数（例如让同一 URL 的所有记录落到同一 reduce）。

初学者要理解 shuffle 是整个作业里最贵的一步，也是唯一需要机器间大量传数据的一步：map 阶段计算尽量在数据本地做（见 4.1.5），reduce 阶段的输出写回分布式文件系统，唯独中间的 shuffle 必须把数据横跨网络重新分布。一个易错点是把 shuffle 当成「框架自动、无成本」——实际上它涉及本地磁盘落盘、网络拉取、按键排序，作业慢往往慢在这里。另一个易混点是排序：经典 MapReduce 在 reduce 侧对到达的中间键做排序，所以同一 reduce 内的键是有序处理的，这是「排序」类作业几乎免费的原因。

### 4.1.3 整体数据流与 M/R 任务划分

一次 MapReduce 作业的数据流是：输入文件被切成 M 个分片 → M 个 map 任务并行处理，各自产出 R 份中间文件（本地磁盘）→ R 个 reduce 任务各自拉取全部 map 的对应那一份、排序聚合 → 产出 R 个输出文件（分布式文件系统）。

```
输入(GFS)              中间(map 本地磁盘)            输出(GFS)
 split 0 ─ map 0 ─┬─▶ 区0 区1 ... 区R-1
 split 1 ─ map 1 ─┼─▶ 区0 区1 ... 区R-1     shuffle    ┌─ reduce 0 ─▶ out-0
   ...      ...    │        ...          ══════════▶ │    ...
 split M-1─map M-1─┴─▶ 区0 区1 ... 区R-1              └─ reduce R-1 ─▶ out-(R-1)
                        每个 map 产出 R 份            每个 reduce 收 M 份
```

任务数 M 和 R 通常远大于机器数：论文里给的实践值是 M、R 都取到几千（例如 M=200000、R=5000，机器 2000 台的量级），这样每台机器同时跑很多小任务。这么做的好处有二：一是负载均衡更细，快机器能多领任务；二是某台机器挂掉时，它未完成的那些小任务可以被分散重跑到很多机器上，恢复更快。

初学者常见误解是「M 就等于机器数、R 就等于 1」。实际上把任务切得比机器多是刻意设计。R 决定了最终输出文件的个数（每个 reduce 一个），也常常由下游作业的需求决定。M 一般由输入分片大小自然决定（见 4.1.5）。

### 4.1.4 master/worker 执行架构

MapReduce 运行时是一个中心 master 加许多 worker 的架构。master 是协调者：它掌握每个 map/reduce 任务的状态（空闲 idle / 进行中 in-progress / 完成 completed）、把任务指派给空闲 worker、并记录每个已完成 map 产出的 R 个中间文件区域的位置和大小，好把这些位置转发给 reduce worker。worker 是干活的：领到 map 任务就读输入、跑用户 map 函数、把中间结果按区写本地盘并把区位置报告给 master；领到 reduce 任务就按 master 给的位置拉数据、排序、跑用户 reduce 函数、写输出。

```
                 ┌──────────┐
     指派任务 ◀──│  master  │──▶ 记录任务状态 + 中间文件位置
    /    |    \  └──────────┘
 map0  map1  ...          reduce0  reduce1 ...
 (读输入,写本地区)         (拉区,排序,写输出)
```

这个架构的一个要点是 master 是单点协调者但不经手数据本身——所有大流量（读输入、shuffle、写输出）都在 worker 之间或 worker 与文件系统之间直接流动，master 只传控制信息和文件位置这类小元数据。这跟 GFS 里「单 master 管元数据、chunkserver 走大数据」是同一种设计哲学，也是同一时代 Google 系统的共同套路：把元数据集中以简化一致性，把数据平面分散以扩展吞吐。

### 4.1.5 输入分片与数据本地性

输入被切成 M 个分片，每片是一段字节范围。论文里典型分片大小是 16–64 MB，可由用户参数调整；这个尺寸不是随意取的，而是刻意对齐底层分布式文件系统的块大小（GFS 块为 64 MB），好让「一个分片正好是一个存储块」。

对齐块大小是为了数据本地性优化。master 在指派 map 任务时，知道每个输入块的副本分布在哪几台机器上，于是尽量把处理某块的 map 任务派到已经存有该块副本的机器上；退而求其次，派到同一机架内的机器。这样绝大多数输入数据是从本地磁盘读的，不占用网络带宽。论文强调这一点在当年网络带宽稀缺的环境下是关键优化。

「把计算搬到数据旁边，而不是把数据搬到计算旁边」。这是大数据处理的一条通用直觉——PB 级数据搬不动，但几 KB 的代码可以随便调度。易错点是以为分片就是按行或按记录数均分；实际是按字节范围切，切点可能落在一条记录中间，所以读取库要处理「跨分片的记录边界」（通常约定一条记录归包含其起始位置的那个分片）。

### 4.1.6 Combiner 局部聚合

Combiner 是一个可选的用户函数，在 map 侧对该 map 自己产出的中间结果先做一次局部聚合，再写出去参与 shuffle。它的目的是减少 shuffle 阶段跨网络传输的数据量。

以词频统计为例：一个 map 处理的文本里 "the" 可能出现上千次，不用 combiner 就要写出上千条 `(the, 1)` 参与 shuffle；配上 combiner（逻辑和 reduce 一样是求和），这上千条在本地就被合成一条 `(the, 1000)`，网络上只传一条。

Combiner 能安全使用的前提是 reduce 操作满足结合律和交换律（如求和、求最大值），这样「先局部合一部分、再全局合」和「全部一起合」结果相同。一个易错点是对不满足这个前提的操作（如求平均值、求中位数）直接把 reduce 当 combiner 用会算错——求平均需要改造成传 `(和, 计数)` 对才能局部聚合。DDIA 里把这类「可局部预聚合」的性质单独强调，因为它决定了一个聚合能不能被高效分布式化。

### 4.1.7 编程模型的表达力与局限

MapReduce 用「两拍固定形状」换来了自动并行与容错，代价是表达力受限：很多计算不是天然的一趟 map+reduce。复杂逻辑要拆成多个 MapReduce 作业串成流水线，前一个作业的输出（写回文件系统）当后一个的输入。

这带来两个初学者该知道的痛点。其一，作业之间的中间结果必须落到分布式文件系统并按副本数复制，既慢又占存储——而这些中间结果往往用完即弃。其二，迭代类算法（机器学习的梯度下降、图算法的 PageRank）要在同一份数据上反复跑几十上百轮，每轮都是一个 MapReduce 作业、每轮都把数据从磁盘读进来又写回去，磁盘 I/O 成了主要开销。

正是这两个痛点直接催生了 Spark：把中间结果留在内存、把「一串作业」表达成一张可以整体优化调度的图（DAG）。所以 4.3 和 4.4 不是另起炉灶，而是针对 MapReduce 这两处短板的回应。理解这一点，就理解了批处理框架这十年演进的主线。

## 4.2 MapReduce 容错与落后者

### 4.2.1 worker 失效与任务重执行

MapReduce 靠「重新执行任务」来容错。master 周期性 ping 每个 worker，一段时间没回应就判定该 worker 失效。失效 worker 上的任务按状态分别处理，而 map 和 reduce 的处理方式关键地不同。

已完成的 map 任务在 worker 失效时也要重跑；已完成的 reduce 任务则不必。原因在于中间结果和最终结果存放位置不同：map 的输出写在执行它的 worker 的本地磁盘上，worker 一挂这份中间数据就没了，所以凡是在这台机器上完成过的 map 都得在别处重跑；reduce 的输出写在分布式文件系统里（有副本、独立于任何单台 worker），所以已完成的 reduce 不受某台 worker 失效影响。

```
worker 挂掉
  ├─ 其上「进行中」的 map/reduce 任务      → 重置为 idle，另派机器重跑
  ├─ 其上「已完成」的 map 任务            → 也要重跑（本地中间数据随机器丢失）
  └─ 其上「已完成」的 reduce 任务          → 不重跑（输出已在 GFS，有副本)
```

当一个 map 被重跑时，master 要通知所有还没读完该 map 中间数据的 reduce 任务「去新位置拉」。初学者记住这条不对称：中间数据放本地是为了快（不走复制、不占文件系统），代价就是 map 结果不持久、机器一挂就得重算。这是一个典型的性能与容错的权衡。

### 4.2.2 master 失效

master 是单点。原论文的处理很朴素：master 定期把自己的数据结构做检查点（checkpoint）写盘，若 master 挂掉，可从最近检查点重启一个新 master 继续；但在原论文的实现里，实际策略是——由于只有一个 master，它失效的概率低，实现选择直接让整个作业失败、由客户端重试，而不是自动切换。

初学者要把这理解成一个务实的工程取舍，而不是理论上的最优。单 master 简化了整个系统的一致性推理（任务分派、状态跟踪都有唯一权威），代价是它成为可用性上的单点。因为一次作业时长有限、master 又只有一个进程、硬件失效概率可算，Google 判断「作业失败重跑」的期望成本低于「为 master 做高可用」的复杂度成本。这与后来把协调者本身做成共识组（如 Spanner 里 Paxos 组当参与者）形成对照——不同系统在不同约束下对同一问题给了不同答案。

### 4.2.3 落后者 straggler 问题

落后者（straggler）指一台机器把某个 map 或 reduce 任务跑得异常慢，拖长整个作业的完成时间。因为一次 MapReduce 作业要等所有任务都完成才算完成，哪怕只剩最后一两个慢任务，整个作业都得干等。

落后者的成因是多样且往往不可预测的：磁盘出现坏道导致读写反复重试而降速、机器上被调度了其它任务抢占了 CPU/内存/带宽、甚至是机器代码里某个缓存被意外关闭。这些都不是「失败」——任务还在跑、还会正确完成，只是慢。所以单纯的失效检测（心跳超时）抓不住落后者，需要专门机制。

初学者要区分「失败」和「落后」：失败是任务停了要重跑，落后是任务在跑但太慢。分布式系统里落后者常常比彻底失败更棘手，因为它不触发任何错误、悄悄地拖垮尾延迟。

### 4.2.4 backup task 备份任务

MapReduce 对落后者的解法是备份任务（backup task）：当一次作业接近尾声（大部分任务已完成、只剩少量在进行中）时，master 为这些仍在进行中的任务额外调度一份备份执行。同一个任务此时有两个副本在两台机器上并行跑，谁先完成就算它完成，另一份被取消。

这个机制能奏效，是因为任务是幂等且确定性的（见 4.2.5）：跑两遍结果一样，所以随便用哪份都对。它把「等一个慢任务」变成「等两台机器里快的那台」，大幅压缩尾延迟。论文给了一个坐实的数据：在一个 TB 级排序基准里，开启备份任务的作业约 891 秒完成；关闭备份任务后，同样的作业约 1283 秒完成，慢了约 44%。

一个易错点是以为备份任务从头就开一堆冗余副本——那会浪费一倍资源。实际是只在作业尾部、只对少量仍未完成的任务开备份，冗余开销很小（论文称一般增加几个百分点的计算资源）却显著改善完成时间。这个「投机执行」的思想被后来的 Hadoop、Spark 都继承（术语叫 speculative execution，见 4.4.5）。

### 4.2.5 语义保证与输出的确定性

MapReduce 保证：当用户的 map 和 reduce 都是确定性函数（相同输入产生相同输出）时，整个分布式作业的输出与「用某种不出错的顺序串行执行整个程序」的输出相同。这让程序员可以用顺序程序的直觉去理解一个大规模并行作业的结果。

做到这一点靠的是任务输出的原子提交。每个 reduce 任务先把输出写到一个私有的临时文件，完成时通过文件系统的原子改名（atomic rename）把临时文件变成最终输出文件。若同一 reduce 任务因重跑或备份而完成了多次，多次改名指向同一个最终文件名，文件系统保证只有一个「胜出」、结果一致。map 任务的重复完成则由 master 忽略后到的完成报告来去重。

初学者的易错点是把「exactly-once 语义」误解为「任务只执行一次」。恰恰相反——任务可能因重跑、备份被执行很多次；框架保证的是「效果只算一次」，靠的是幂等 + 原子提交，而不是靠不重复执行。这与消息系统里 exactly-once 的实现思路一脉相承（去重 + 幂等），也是理解 4.3 之后 exactly-once 流处理的基础。对非确定性的 map/reduce（比如函数里用了随机数），论文明确只给较弱的保证。

### 4.2.6 掉队记录与坏记录跳过

生产环境里偶尔有个别输入记录会稳定触发用户代码崩溃（比如第三方库对某种畸形输入抛异常）。若一条坏记录每次都让处理它的任务崩溃、任务崩溃就重跑、重跑又崩溃，作业会卡死在这条记录上永远完不成。

MapReduce 的应对是坏记录跳过（skipping bad records）：worker 在处理每条记录前，先把当前记录的序号报给 master；若某条记录导致进程连续崩溃若干次，master 记下这个「毒记录」的序号，在下次重跑该任务时通知 worker 直接跳过它。牺牲极少量记录换整个作业能完成。

初学者可以把它理解成一种务实的降级：在处理海量数据时，个别记录出错是常态而非例外，与其让一条脏数据搞垮整个 PB 级作业，不如允许「尽力而为、丢弃极少数」。这体现了大数据批处理的一个价值取向——统计意义上的完整性优先于逐条严格。这属于工程上的补充特性，教材里常被略过，但它解释了为什么真实批处理系统在脏数据面前依然健壮。

## 4.3 Spark RDD 与血统

### 4.3.1 RDD：不可变的分区数据集

RDD（Resilient Distributed Dataset，弹性分布式数据集）是 Spark 的核心抽象：一个只读（不可变）、被切成多个分区、分布在集群多台机器上的记录集合。你不能就地修改一个 RDD 里的元素；你只能对一个 RDD 施加变换，得到一个新的 RDD。

RDD 通过两种方式创建：从稳定存储（如分布式文件系统里的文件）读入，或对已有的 RDD 施加一个变换（如 map、filter、join）。每个 RDD 都记着自己是「从哪些父 RDD、经由什么变换」得来的——这份出身信息就是它的血统（lineage，见 4.3.3）。

初学者最需要扭转的直觉是「数据不可变还怎么算」。答案是：算的结果永远是一个新数据集，旧的保持不动。这看似浪费，实则是容错和优化的基石——因为每个 RDD 的内容完全由「父 RDD + 确定性变换」决定，丢了随时能重算，且框架能自由地重排、合并、延后这些变换而不担心副作用。不可变性在这里不是约束，而是让分布式容错变简单的前提。

### 4.3.2 转换与动作：惰性求值

RDD 上的操作分两类。转换（transformation，如 map、filter、groupByKey、join）从一个 RDD 产生新 RDD；动作（action，如 count、collect、save、reduce）触发实际计算并把结果返回给驱动程序或写到存储。

关键机制是惰性求值（lazy evaluation）：转换不会立即执行，只是被记录下来（在血统图里加一条边）；只有当一个动作被调用时，Spark 才回溯这个 RDD 所依赖的整条变换链、构造执行计划、真正开始算。

```
rdd1 = read(file)          # 记下来，不算
rdd2 = rdd1.filter(...)    # 记下来，不算
rdd3 = rdd2.map(...)       # 记下来，不算
rdd3.count()               # 动作！此刻才回溯 rdd1->rdd2->rdd3 一起算
```

惰性的好处是框架能看到「从读入到动作」的全貌，从而整体优化：把连续的窄变换（filter 后紧跟 map）融合成一趟流水线处理、不为中间的 rdd2 单独物化存储。这正是对 MapReduce「每步中间结果都落盘」的直接改进。初学者的易错点是写了一串转换却发现「什么都没发生」——没触发动作，Spark 就一直在攒计划、不干活；也因此调试时报错常常在动作那一行才抛出，而不是在真正出问题的那个转换行。

### 4.3.3 血统与重算式容错

Spark 不靠复制数据来容错，而靠血统重算。因为每个 RDD 分区都记得自己是「由哪些父分区经什么确定性变换算出来的」，当某个分区因机器宕机丢失时，Spark 顺着血统只重算丢掉的那个分区（以及它依赖的、同样丢失的祖先分区），不需要重跑整个作业，也不需要事先把每份数据复制多份。

这是 Spark 相对 MapReduce（乃至相对「靠复制容错」的存储系统）的核心创新：把容错的成本从「持续付出的存储/带宽复制开销」转成「只在真的丢了东西时才付出的重算开销」。平时不出错，就一分冗余都不用付。

MapReduce 的中间结果丢了要重跑产生它的整个 map 任务；Spark 的血统是细粒度到「分区 + 变换」的，能精确定位并只重算最小必要的部分。但重算成本高低取决于依赖类型——窄依赖重算便宜，宽依赖重算可能牵连很广，这就引出了 4.3.4 的区分，以及 4.3.6 用检查点来给长血统兜底。

### 4.3.4 窄依赖 vs 宽依赖

RDD 之间的依赖分两种，这个区分决定了执行能否流水线化、以及容错重算的代价。窄依赖（narrow dependency）指父 RDD 的每个分区最多被子 RDD 的一个分区使用，如 map、filter、union。宽依赖（wide dependency，又称 shuffle 依赖）指父 RDD 的一个分区被子 RDD 的多个分区使用，如 groupByKey、reduceByKey、join（未预分区时），这类操作需要跨节点 shuffle 数据。

```
窄依赖 (map/filter)              宽依赖 (groupByKey/join，需 shuffle)
 父P0 ──▶ 子P0                    父P0 ─┬─▶ 子P0
 父P1 ──▶ 子P1                    父P1 ─┼─▶ 子P1
 父P2 ──▶ 子P2                    父P2 ─┴─▶ 子P2
 (一对一，可就地流水线)            (多对多，数据要重新分布)
```

这个区分有两层后果。执行上，一连串窄依赖可以在同一台机器、同一个分区上流水线连算（读一条、map、filter、再算，不落中间盘），而宽依赖处必须先把上游算完、shuffle 落盘，再开始下游——所以宽依赖是划分执行阶段（stage）的天然边界（见 4.4.1）。容错上，窄依赖丢分区只需重算对应的一个父分区，代价小；宽依赖丢分区则可能要重算多个父 RDD 的所有分区，代价大，因此长链宽依赖是检查点的重点保护对象。

窄依赖是「一对一，能连着算」，宽依赖是「多对多，要洗牌」。作业慢、重算贵，多半都跟宽依赖有关。

### 4.3.5 持久化与缓存

默认情况下，Spark 每次对一个 RDD 触发动作都会顺着血统从头重算——如果同一个 RDD 要被多次使用（典型是迭代算法里反复用同一份数据集），重复重算就是巨大浪费。persist（或其别名 cache）让用户显式要求把某个 RDD 的分区在首次算出后留在内存里，后续复用直接读内存，不再重算。

Spark 提供多个存储级别（storage level）来权衡内存与容错：只存内存（MEMORY_ONLY，装不下的分区下次用时重算）、内存放不下就溢写磁盘（MEMORY_AND_DISK）、序列化后存以省内存、以及带副本的级别等。⚙演进快·锚版本——具体存储级别的名字、默认级别、以及 `cache()` 等价于哪个级别，随 Spark 版本可能调整；以你所用版本官方文档为准，此处的级别语义锚定 RDD 论文（NSDI 2012）所述的内存/磁盘/序列化维度，具体默认值标「待核」。

初学者最该记住的收益场景是迭代计算：机器学习训练要在同一份训练数据上跑几十轮，把这份数据 cache 在内存里，第一轮从磁盘读入并缓存，之后每轮都从内存拿——这正是 Spark 相对 MapReduce 在迭代作业上快一个数量级的直接原因（见 4.4.4）。易错点：cache 不是免费的，缓存占内存，缓存了却只用一次反而白搭；且 cache 本身也是惰性的，要等下一个动作触发才真正把数据放进内存。

### 4.3.6 检查点：截断长血统

对于血统很长、或含大量宽依赖的 RDD，纯靠重算容错会有问题：血统链越长，一旦丢分区要回溯重算的祖先越多；含宽依赖的重算还可能牵连多个父 RDD 的全部分区，代价高到不可接受。检查点（checkpointing）把某个 RDD 的内容物化写到可靠存储（如分布式文件系统），并把它的血统在此处截断——之后若这个 RDD 的分区丢失，直接从可靠存储读回，不再往上重算。

这本质是在「重算容错」和「复制容错」之间做权衡：检查点付出一次写可靠存储的开销，换来把「潜在的昂贵重算」封顶。缓存（4.3.5）和检查点容易混淆但目的不同——缓存是为了复用加速、存在内存里、机器挂了缓存也没了（还得靠血统重算）；检查点是为了容错兜底、存在可靠存储、机器挂了也还在。

短血统、窄依赖为主 → 靠血统重算就够；长血统、宽依赖密集（如迭代很多轮后）→ 该打检查点了。这也解释了为什么迭代作业既要 cache（加速）又常要周期性 checkpoint（防血统失控），二者配合使用。

### 4.3.7 与 MapReduce 的定位对比

RDD 可以看成对 MapReduce 的一次抽象升级，而非彻底替代。MapReduce 表达力是「一趟 map+reduce，多趟靠串作业、中间落分布式文件系统」；RDD 提供一组更丰富的算子（map、filter、join、groupBy 等），并把「多步计算」表达成一张内存中的血统图，让连续窄变换不落盘、让容错细粒度化。

在容错思路上，两者其实同源：都要求变换/任务是确定性的，都靠「重新执行」而非同步复制来恢复丢失的计算——区别只在粒度（MapReduce 重跑整个任务，Spark 重算丢失的分区）和中间数据去处（MapReduce 落分布式文件系统，Spark 优先留内存）。

初学者不必把它们对立起来记：Spark 是站在 MapReduce 肩膀上，专门解决「迭代/交互式作业里中间结果反复落盘」这个具体痛点。对于就一趟、数据量巨大到内存放不下的纯批处理，MapReduce 式的落盘执行反而稳；对于要反复迭代、中间结果放得进内存的作业，Spark 快得多。选型取决于工作负载，而非「谁淘汰谁」。

## 4.4 DAG 调度与内存迭代

### 4.4.1 DAG 调度器与阶段划分

当一个动作被触发时，Spark 的 DAG 调度器把该 RDD 的整条血统图翻译成一个由阶段（stage）组成的有向无环图（DAG），再交给底层调度器分任务执行。阶段划分的规则很简洁：在宽依赖（shuffle）处切一刀。每个阶段内部全是窄依赖，可以流水线连算；阶段与阶段之间隔着一次 shuffle。

```
血统:  read ─▶ map ─▶ filter ─┃shuffle┃─▶ reduceByKey ─▶ map ─▶ save
                                切一刀
划分:  └────── Stage 1 ──────┘        └──────── Stage 2 ────────┘
       (窄依赖，流水线执行)             (窄依赖，流水线执行)
```

每个阶段会被展开成一批任务（task），一个任务对应处理一个分区。上游阶段全部任务完成、shuffle 数据落好后，下游阶段才能开始。初学者可以把 stage 类比成 MapReduce 里的一趟 map 或一趟 reduce——shuffle 依赖就是 map 和 reduce 之间那道坎；不同的是 Spark 能把多个连续的窄变换塞进一个 stage 一起流水线跑，而不像 MapReduce 那样每步都要一趟完整作业。

### 4.4.2 阶段内的流水线执行

一个阶段内部因为全是窄依赖（一对一），Spark 能对一个分区把连续的多个变换串起来、一条记录一条记录地连着算，中间结果不物化落盘。比如 `read → map → filter → map` 若都是窄依赖、同属一个 stage，则对每条输入记录一路算到底，不为中间的每一步单独生成一个完整数据集。

这就是对 MapReduce「每个作业的中间结果都要写分布式文件系统」的根本改进。省掉中间物化，既省了磁盘 I/O，也省了跨作业的调度启动开销。

窄依赖像流水线上的连续工位，一个零件依次通过每个工位，不用在工位之间入库出库；宽依赖像换车间，必须先把上一车间所有产品汇总重新分拣，才能进下一车间。流水线只能在「不换车间」（同一 stage 内）的范围内连续跑。

### 4.4.3 shuffle 的物化与读取

在阶段边界（宽依赖处），上游阶段的每个任务把自己的输出按下游分区写成本地的 shuffle 文件（shuffle write）；下游阶段的每个任务再从所有上游任务那里拉取属于自己分区的数据（shuffle read）。这与 MapReduce 的 shuffle 机制是一回事——中间数据落本地磁盘、下游按分区拉取。

因此，尽管 Spark 以「内存计算」著称，shuffle 处的中间数据通常仍要落本地磁盘（不是分布式文件系统，是执行节点本地盘）。这既是为了容错（下游还没拉走前上游任务就完成退出，数据得先存住），也是因为 shuffle 数据量可能超过内存。

初学者的常见误解是「Spark 全程在内存、从不落盘」。准确说法是：Spark 避免的是「跨作业把中间结果写到有副本的分布式文件系统」，而阶段边界的 shuffle 数据仍会写执行节点本地磁盘。这也是为什么宽依赖（shuffle）既贵在网络传输、又贵在磁盘 I/O，是 Spark 作业调优的重点。

### 4.4.4 内存迭代计算加速

Spark 最突出的场景是迭代计算：把要反复使用的数据集 cache 在内存里，之后每一轮迭代都直接从内存读，省掉了 MapReduce 每轮都从磁盘读入、算完又写回磁盘的往返开销。

以逻辑回归、K-means 这类机器学习训练为例：训练数据固定不变，算法在其上迭代几十上百轮不断更新模型参数。MapReduce 实现每轮是一个独立作业，每轮都要把整个训练集从分布式文件系统读一遍；Spark 把训练集 cache 后，只有第一轮从磁盘读，之后各轮都命中内存。RDD 论文报告在这类迭代机器学习工作负载上，Spark 相对 Hadoop 可快达约 20 倍。

初学者要抓住加速的本质来源：不是「内存比磁盘快」这么笼统，而是「消除了每轮迭代之间不必要的磁盘往返和作业启动」。也要知道边界——若数据集大到内存放不下、或只跑一趟不迭代，Spark 的内存优势就用不上，此时它相对 MapReduce 的优势会明显收窄。这个约 20 倍是特定迭代负载下的实测上界，不是普适倍数。

### 4.4.5 任务调度、数据本地性与推测执行

DAG 调度器把 stage 展成任务后，交给任务调度器分发到 executor 上执行。分发时同样讲究数据本地性：优先把处理某分区的任务派到已缓存该分区、或存有其输入数据的节点上，本地拿不到再退到同机架、跨机架——这与 MapReduce「把计算搬到数据旁」一脉相承。

Spark 也继承了 MapReduce 的落后者应对：推测执行（speculative execution）。当发现某任务明显慢于同批其它任务时，调度器在别的节点起一个副本并行跑，谁先完成用谁——正是 4.2.4 备份任务思想的延续。⚙演进快·锚版本——推测执行默认是否开启、触发阈值等参数随 Spark 版本与配置而异，具体默认值标「待核」，以所用版本官方文档为准。

初学者可把这一层理解成「MapReduce 那套调度智慧（本地性 + 投机执行）被 Spark 完整继承并做在了更细的 DAG/分区粒度上」。两代框架在容错和调度的核心思想高度连续，变的是抽象粒度和中间数据的去处。

### 4.4.6 性能对比与适用边界

把两代框架放到一起，可以给初学者一张选型直觉图。Spark 快在：迭代/交互式作业（数据可缓存内存、复用多次）、多步流水线（连续窄变换免中间落盘）、更丰富算子（少写胶水作业）。MapReduce（或落盘式执行）稳在：单趟、超大规模、内存装不下的纯批处理，以及对内存资源紧张的环境。

Spark 的优势高度依赖「中间数据/复用数据放得进内存」。当作业没有复用、或数据规模远超内存时，Spark 也要大量落盘 shuffle，其相对 MapReduce 的领先幅度会大幅缩小；论文里那种约 20 倍的加速是迭代负载的最好情形，不能当成任意批处理都能拿到的普适数字。

初学者最终应带走的心智模型：批处理框架的演进主线，是不断降低「表达复杂计算」与「高效执行、可靠容错」之间的摩擦——MapReduce 用极简两函数模型开了先河，Spark 用不可变数据集 + 血统 + 内存 + DAG 把迭代和多步作业的效率提上来，两者共享「确定性 + 重执行容错 + 计算贴近数据」的同一套底层哲学。
