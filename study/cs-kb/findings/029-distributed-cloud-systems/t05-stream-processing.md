## 5.1 流处理模型与消息日志

### 5.1.1 无界数据集与流处理的定位

批处理处理的是有界数据集：输入在计算开始前就已知、大小固定，作业跑完即结束。流处理处理的是无界数据集：事件源源不断地到来，没有"输入结束"这个时刻，计算必须持续运行、边到边算。

这个区别决定了后面所有机制。因为流永不结束，你不能"等数据到齐再算平均值"，只能在时间维度上切出一段一段有界的片段来聚合（这就是窗口，5.3）；因为事件是陆续到达的、还可能乱序，你需要一套时间语义来判断"某段时间的数据是不是到齐了"（这就是水位线，5.2）；因为作业要长期运行、中途一定会遇到机器故障，你需要一套不丢不重的容错机制（这就是检查点与精确一次，5.4）。初学者可以先记住一句话：批是流的特例（有界流），流处理是更一般的模型。

### 5.1.2 事件、流与生产者/消费者

一个事件是某个时刻发生的一件事的不可变记录，通常是一个小的自包含对象，带一个时间戳和一些字段（例如"用户 U 在 12:03:01 点击了商品 P"）。相关事件按时间先后组成的序列就是一个流。产生事件的一方叫生产者（producer，也叫 publisher），把事件写入某个中间系统；处理事件的一方叫消费者（consumer，也叫 subscriber），从中间系统读取并处理。

直接让生产者调用消费者（同步 RPC）会把两者紧耦合：消费者宕了生产者就阻塞，消费者慢了生产者被拖垮，加一个新消费者要改生产者代码。所以现实系统几乎都在中间放一个消息系统（message broker / event streaming platform）做缓冲和解耦：生产者只管往里写，消费者按自己的节奏读，两边互不感知对方的存在与速度。这就是发布/订阅（pub/sub）模式。

### 5.1.3 日志式消息与 Kafka 心智模型

日志式消息系统的核心数据结构是一个仅追加（append-only）的、持久化到磁盘的有序日志。生产者写入就是往日志尾部追加一条记录；消费者读取就是从某个位置开始顺序往后扫。Kafka 是这个范式的代表实现。

一个仅追加日志的结构大致是：

```
partition（一个分区 = 一条有序日志）
 offset:   0    1    2    3    4    5    6   ← 单调递增的位置编号
 record:  [e0] [e1] [e2] [e3] [e4] [e5] [e6] ...→ 尾部持续追加
                      ↑                   ↑
              consumer A 读到 2      producer 正在写入 6
```

关键特性有几点。日志只追加、不原地修改，因此写入是顺序磁盘 I/O，非常快。每条记录在分区内有一个单调递增的偏移量（offset），它既是记录的地址，也是排序依据。消费者读过的数据不会被立刻删除，而是按保留策略（时间或大小）保留一段时间，因此多个消费者可以各自独立地、以不同进度重复读同一份日志，甚至可以把 offset 倒回去重放历史（replay）——这是日志式相对于传统队列的杀手锏，也是后面 Kappa 架构（5.5.2）能成立的前提。初学者常见误解是把 Kafka 当成"读完就没了"的队列，其实它更像一个可被多方反复回放的持久提交日志。

本机可用一个 Python 玩具坐实这个心智：用一个 list 当 append-only 日志，生产者 `log.append(record)`，每个消费者各自维护一个整数 `offset` 从 0 往上读，读到 `len(log)` 就等待。删除记录不发生，重放只需把 offset 归零。

### 5.1.4 分区、偏移量与顺序保证

为了扩展吞吐，一个主题（topic，逻辑上的一个流）会被切成多个分区（partition），每个分区是一条独立的日志，可以放在不同机器上并行读写。生产者按某个 key 的哈希（或轮询）决定一条记录进哪个分区。

顺序保证只在单个分区内成立：同一分区里的记录严格按 offset 有序，消费者也按序读到。跨分区没有全局顺序。这是一个初学者极易踩的坑：如果你需要"同一个用户的事件严格有序"，就必须让该用户的所有事件用同一个 key、落到同一个分区；如果为了并行把它们打散到多个分区，就放弃了它们之间的相对顺序。offset 的提交（consumer 记录自己读到哪了）也是按分区独立进行的。在 Kafka 中，消费进度被提交到一个内部主题 `__consumer_offsets`，作为"哪些记录已成功处理"的检查点。

### 5.1.5 两种消息代理范式：JMS/AMQP 式 vs 日志式

传统消息队列（JMS、AMQP，如 RabbitMQ 的经典用法）和日志式（Kafka）是两种不同的心智。传统队列里，一条消息被某个消费者取走并确认（ack）后通常就从队列删除；消息是"待办任务"，多个消费者从同一队列取件是负载分摊，谁取到算谁的，消息之间的顺序在多消费者并行确认下容易被打乱。日志式里，消息是持久的日志记录，消费不删除，靠 offset 追踪进度，天然支持多方独立重复消费与重放。

需要精细的单条消息路由、优先级、按条 ack/重投、且消息量不特别大时，传统队列的模型更贴切；需要高吞吐、多消费者独立消费、可重放历史、并把消息流当作"事实的权威记录"时，日志式更合适。DDIA 明确把这组对比作为理解流处理系统的起点。二者并非谁淘汰谁，Kafka 也在演进中引入了更像队列的能力（见下一节 KIP-932）。

### 5.1.6 消费者组与重平衡

同一份数据往往需要既被多方独立消费，又在每一方内部并行处理。消费者组（consumer group）解决这个：同一个组内的多个消费者实例分摊该主题的所有分区（一个分区在同一时刻只被组内一个实例消费，保证组内不重复），不同的组各自独立地消费全量数据（互不影响进度）。

当组内实例增减（扩容、宕机）或分区数变化时，会触发重平衡（rebalance），即重新把分区分配给存活的实例。重平衡期间消费通常会短暂暂停，是运维中需要关注的抖动来源。Kafka 4.x 引入了新的重平衡协议以降低这种停顿（⚙演进快·锚 Kafka 4.x·随时变）。此外 Kafka 4.x 通过 KIP-932 引入了共享组（share groups）消费模型，让 Kafka 也能表现得更像传统消息队列（多个消费者从同一分区取件、按条 ack），是对上一节两种范式的融合尝试（⚙演进快·锚 Kafka 4.x·随时变）。

### 5.1.7 日志保留与日志压缩

无界流写进磁盘不可能永远留着，所以日志有保留策略。基于时间/大小的保留把超过阈值的旧段（segment）整段删除。日志压缩（log compaction）是另一种策略：对同一个 key 只保留最新一条记录，把老版本清掉，从而把日志变成一份"每个 key 的最新值"的紧凑快照，同时仍保持是一个可重放的日志。

压缩型日志非常适合承载"状态"类数据（例如每个用户的当前资料）：新消费者从头重放一遍压缩日志，就能重建出全量最新状态，之后再跟增量。这也是把日志当作数据库变更流（CDC，change data capture）来用的基础——数据库的每次写入作为一条事件进日志，下游系统重放日志即可得到与源库最终一致的物化视图。初学者要注意压缩不是"顺序压缩算法（gzip）"，而是"按 key 去重保留最新"的语义压缩。

## 5.2 事件时间 vs 处理时间与水位线

### 5.2.1 三种时间

流处理里有三个不同的时间概念，务必分清。事件时间（event time）是事件在真实世界中实际发生的时刻，通常由数据源在产生事件时打进记录里。摄入时间（ingestion time）是事件被流处理系统接收（进入第一个算子）的时刻。处理时间（processing time）是执行算子的机器在处理这条事件时的本地墙钟时刻。

一个手机 App 在用户 12:00:00 点击时记录了事件（事件时间 = 12:00:00），但手机当时离线，直到 12:05:00 联网才把事件发出，系统 12:05:03 收到（摄入时间 ≈ 12:05:03），某个算子 12:05:10 才处理到它（处理时间 = 12:05:10）。同一条事件的三个时间可以差很远。做分析时我们几乎总是想按事件时间分组（"12:00 那一分钟真正发生了多少点击"），而不是按处理时间（那只反映系统忙不忙）。

### 5.2.2 为什么处理时间不够：乱序与延迟

如果按处理时间开窗（"过去一分钟系统处理了多少事件"），结果简单、确定、无需等待，但它不反映业务真相：一次网络抖动或补传，会把本属于 12:00 的一批事件算进 12:05 的窗口，统计出来的曲线是系统状态而非世界状态。

按事件时间开窗才反映真相，但代价是事件会乱序到达（out-of-order）和延迟到达（late）：offset 相邻的两条记录，事件时间可能一大一小；某条属于 12:00 窗口的事件可能 12:05 才到。于是产生一个根本难题——处理到 12:04 的数据时，我怎么知道属于 12:00 那个窗口的事件是不是都到齐了、能不能安全地输出这个窗口的结果？无界流上没有"输入结束"信号来告诉你"齐了"。水位线就是为回答这个问题而生。

### 5.2.3 水位线的定义与语义

水位线（watermark）是插在事件流里的一种特殊标记，携带一个时间戳 W，其含义是系统断言：事件时间 ≤ W 的事件应该都已经到达了（之后基本不会再来更早的）。换句话说，水位线 W 是对"事件时间进展到哪了"的一个估计，是系统认为的、事件时间意义上的"现在"。

它的作用是给窗口一个触发信号：当水位线越过某个窗口的结束时间时，系统就认为该窗口的数据到齐了，可以计算并输出结果、随后释放该窗口的状态。一条乱序流 + 水位线推进大致长这样（横轴是事件时间戳）：

```
到达顺序 →   事件(事件时间):  4  2  3  7  5  W(7)  6*  9  8  W(11) ...
                                              ↑          ↑
水位线含义:                          "≤7 都到齐了"  "≤11 都到齐了"
窗口[0,5) 在 W≥5 时触发；窗口[5,10) 在 W≥10 时触发
6* 是在 W(7) 之后才到的、事件时间=6 的记录 → 相对 [5,10) 窗口尚可，
   但若晚于 W(超过其边界)则成为"迟到数据"（见 5.2.5）
```

设得越靠后（越保守、留越多等待余量），越少漏掉迟到事件、结果越准，但延迟越高、状态留存越久；设得越靠前（越激进），结果出得越快，但越容易漏算迟到事件。这是流处理里"完整性 vs 延迟"的核心张力。

### 5.2.4 水位线如何生成

水位线不是天上掉下来的，得由系统或用户根据数据特征估计。最常见的启发式是"最大已见事件时间减去一个固定的允许乱序量"：

```
watermark = (到目前为止见过的最大事件时间) − maxOutOfOrderness
```

例如假定乱序不超过 5 秒，就让水位线永远比见过的最大事件时间落后 5 秒。这个 `maxOutOfOrderness` 由工程师根据经验设定，是个纯启发式的赌注：赌绝大多数事件的延迟不超过它。此外还需处理"某个分区/数据源长时间没有新数据导致水位线卡住不前进"的空闲源（idle source）问题，通常给一个超时后强制推进水位线的机制。多个上游合并时，下游水位线取各上游水位线的最小值（木桶效应：最慢的上游决定整体进展）。这些都是 ⚙演进快 的框架实现细节（锚 Flink 2.x / Beam），默认参数因版本而异，具体数值待核。

### 5.2.5 迟到数据与允许延迟

即使水位线已经越过窗口边界、窗口结果已输出，仍可能有事件时间早于水位线的事件姗姗来迟，这就是迟到数据（late data / late arrivals）。默认策略通常是直接丢弃迟到事件（因为对应窗口的状态可能已被释放）。

如果不能接受丢弃，系统提供允许延迟（allowed lateness）：让窗口在触发输出后，仍额外保留一段时间的状态，在这段宽限期内每来一条迟到事件就重新计算并发出一个更新后的结果，宽限期过后才真正释放状态。还有一种做法是把迟到数据分流到侧输出（side output）单独处理。初学者要理解这背后是三方权衡：结果准确性、结果延迟、状态存储成本——想接更多迟到数据，就得留更久的状态、承受更晚或反复修正的结果。

### 5.2.6 触发器与结果修正

水位线越过窗口边界是最自然的触发时机，但不是唯一的。触发器（trigger）决定"窗口在什么时候发出（一次或多次）结果"。除了水位线触发，还可以有基于处理时间的定期触发（例如每 10 秒先发一个不完整的早期结果）、基于记录数的触发等，甚至组合起来：先给快速的近似早期结果，水位线到齐时给准确结果，之后每来迟到数据再给修正结果。

Dataflow 模型把这套思路系统化为四个正交的问题：算什么（What，做何种聚合）、在事件时间的哪里切（Where，窗口）、在处理时间的什么时候触发（When，触发器与水位线）、以及后续修正如何与之前结果发生关系（How，累积/丢弃/累积并撤回）。这个框架是理解现代流处理（Beam、Flink、Dataflow）时间语义的公认参照系。初学者不必记全，但要建立一个观念：在事件时间上"数据在哪个窗口"和在处理时间上"何时把这个窗口算出来"是两件独立的事，前者靠窗口，后者靠水位线与触发器。

## 5.3 窗口

### 5.3.1 窗口：无界流上的有界聚合

窗口把无界的流按时间（或其他维度）切成一段一段有界的桶，以便做聚合（求和、计数、平均、Top-N 等）。没有窗口，"这条流的总和"永远算不完；有了窗口，"每一分钟的总和"就是一个个可以输出的有界结果。窗口是流处理做聚合分析的基本单位。

窗口通常还叠加一个分组键：不是"全流每分钟计数"，而是"每个用户每分钟计数"。此时每个 (key, window) 组合各自维护一份聚合状态。下面几节讲最常见的窗口类型，它们的区别只在于"如何把事件时间轴切成桶"。

### 5.3.2 滚动窗口（tumbling）

滚动窗口把时间轴切成固定长度、首尾相接、互不重叠的段。每条事件恰好落进一个窗口。例如窗口长度 1 分钟：[12:00,12:01)、[12:01,12:02)、[12:02,12:03) ……

```
事件时间轴 →
|<-- 1min -->|<-- 1min -->|<-- 1min -->|
[12:00,12:01)[12:01,12:02)[12:02,12:03)   ← 不重叠，每事件属唯一窗口
```

它最简单、最省状态，适合"每分钟/每小时的固定周期统计"这类需求。初学者可先从它入手：一个事件的窗口归属就是 `floor(事件时间 / 窗口长度)`。本机用 Python 对一串 (时间戳, 值) 按整除分桶累加，即可复现滚动窗口聚合。

### 5.3.3 滑动窗口（sliding / hopping）

滑动窗口有一个窗口长度和一个更小的滑动步长，窗口按步长不断向前挪，因此相邻窗口会重叠，一条事件会同时落进多个窗口。例如窗口长 1 分钟、步长 10 秒："过去 1 分钟的计数，每 10 秒更新一次"。

```
事件时间轴 →
[----- 1min -----]
      [----- 1min -----]
            [----- 1min -----]     ← 每隔 10s 起一个新窗口，彼此重叠
step=10s
```

它适合"滑动平均、最近 N 分钟趋势"这种需要平滑、连续更新的指标。代价是重叠导致一条事件被复制进 长度/步长 个窗口，状态与计算量随之放大（上例每条事件进 6 个窗口）。易错点：把滑动窗口的步长误当成窗口长度，会让统计口径完全错位。

### 5.3.4 会话窗口（session）

会话窗口不是固定长度，而是由活动的间隙来划分：同一个 key 的事件，只要相邻两条的时间间隔小于一个设定的会话超时（gap），就归入同一个会话；一旦出现超过 gap 的静默，会话就结束，下一条事件开启新会话。

```
某用户事件（点表示一次活动，间隔看时间）：
 · · ·      · ·          · · · ·
[会话1 ]   [会话2]      [  会话3  ]
       ↑gap>timeout↑ 静默超过阈值 → 切分
```

它天然贴合"用户一次访问/一段连续操作"的语义，窗口长度随用户行为动态伸缩。实现上比前两种复杂：新事件可能延长已有会话，甚至两条迟到事件可能把原先分开的两个会话合并成一个，因此系统需要支持会话的动态合并。初学者理解到"按空档切、长度不定、可合并"即可。

### 5.3.5 全局窗口与自定义窗口

全局窗口（global window）把某个 key 的所有事件放进同一个永不自动结束的窗口，完全依赖自定义触发器来决定何时输出（例如每满 100 条触发一次）。它适合按计数而非按时间聚合的场景。除此之外多数框架允许用户自定义窗口分配逻辑，滚动/滑动/会话本质上都是内置的常见特例。

这一节的意义是让初学者知道窗口机制是可扩展的：时间只是最常用的切分维度，"何时开窗、何时闭窗、何时触发"是三个可分别配置的旋钮。绝大多数业务需求用前三种内置窗口就能覆盖。

### 5.3.6 窗口何时真正计算：与水位线/触发器的关系

窗口本身只回答"一条事件属于哪个桶"（事件时间维度的划分），它不回答"这个桶什么时候算出来"。后者由 5.2 的水位线与触发器决定：默认是水位线越过窗口结束时间时触发一次计算并输出，再叠加 allowed lateness 决定要不要为迟到数据保留状态、追加修正。

把两件事分开是初学者最需要建立的关键认知。同一组窗口（比如每分钟滚动窗口），配不同的触发策略，可以是"每分钟结束时出一个准确结果"，也可以是"每 5 秒先出一个近似早期结果、分钟结束时出准确结果、之后迟到数据再修正"。窗口定义"切在哪"，水位线/触发器定义"何时发、发几次"。

### 5.3.7 流上的连接（补位）

流处理里做连接（join）也和窗口/时间强相关，常见三类。流-流连接（例如"点击"流与"曝光"流按同一广告 ID 关联）必须限定在一个时间范围内匹配（窗口连接或区间连接），否则两条流都无界、状态会无限膨胀。流-表连接是用流里的事件去查一个会随时间变化的维表（例如按用户 ID 补充用户资料），需要注意用哪个时间点的表快照。表-表连接则维护两个变更流物化出的视图并持续同步。

这里点到为止，目的是让初学者知道：一旦连接涉及无界流，就绕不开"用时间/窗口来给状态设界"这个约束，否则系统迟早因状态无限增长而崩。连接的时间语义同样区分事件时间与处理时间，坑与前面一致。

## 5.4 exactly-once 与检查点容错

### 5.4.1 交付语义谱系

长期运行的流作业一定会遇到故障与重试，于是"一条事件对结果的影响到底算几次"有三档语义。至多一次（at-most-once）：故障时可能丢事件，绝不重复，最弱但最简单。至少一次（at-least-once）：绝不丢，但故障重放可能让同一事件被处理多次（计数偏大）。精确一次（exactly-once）：既不丢也不重，等价于每条事件对结果恰好生效一次。

要理解为什么 exactly-once 难：网络与进程随时可能故障，"处理事件"和"记录已处理"两个动作无法瞬间原子完成，中间崩溃就会产生"处理了没记下"（重放会重复）或"记下了没真正处理"（会丢）的缝隙。这正是 L5-01 里可靠 RPC 语义难题在流场景的延续。下面几节讲流处理系统怎么逼近 exactly-once。

### 5.4.2 状态与有状态流处理

很多流计算是有状态的：窗口聚合要累积中间和，去重要记住见过的 key，连接要缓存待匹配的记录。这些跨事件保留下来的中间数据就是状态（state）。状态通常存在每个算子实例本地（内存 + 本地磁盘，如 RocksDB 后端），才能高吞吐低延迟地读写。

有了本地状态，容错就变成一个分布式问题：机器宕了，它内存里的状态没了，重启后必须恢复到"和没宕过一样"的状态，且不能把已经反映进结果的事件重复算一遍。要恢复，就得定期把分散在各算子的状态一致地保存下来——这就是检查点。exactly-once 的核心其实是"状态的精确一次更新"。

### 5.4.3 检查点与分布式快照（Chandy-Lamport）

检查点（checkpoint）是给整个流作业的所有算子状态，周期性地拍一张全局一致的快照，持久化到可靠存储（如对象存储）。故障后，把所有算子回滚到最近一次成功的检查点，并把数据源的读取位置（如 Kafka offset）也回退到那一刻，从检查点之后重新消费，就能不丢不重地恢复。

难点在于"全局一致"：各算子分布在不同机器、处理进度不一，不能让它们停下来同时拍照。Flink 采用的是 Chandy-Lamport 分布式快照算法的变体——异步屏障快照（asynchronous barrier snapshotting）。数据源周期性地往数据流里插入一种特殊标记叫屏障（barrier），屏障随数据一起向下游流动；每个算子一旦收到屏障，就把自己当前的状态异步存盘，然后把屏障转发给下游。当屏障流过整个拓扑，一次全局一致的快照就完成了，全程不需要停止处理。

```
source ──[data...]──[barrier n]──[data...]──▶ opA ──▶ opB ──▶ sink
   每个算子收到 barrier n 时：
     1) 快照自身状态到持久存储（异步）
     2) 把 barrier n 转发给下游
   barrier n 流过整个拓扑 ⇒ 得到编号 n 的全局一致快照
   故障时：所有算子回滚到快照 n，source 从快照 n 记录的 offset 重放
```

屏障把连续的流切成"这次快照之前 / 之后"两段；快照是异步的（不停流）；恢复 = 状态回滚 + 数据源重放。

### 5.4.4 屏障对齐与非对齐检查点

当一个算子有多个上游输入时，各输入的屏障不会同时到。为保证快照严格对应"屏障 n 之前的所有事件恰好都已反映、之后的都没反映"，算子要做屏障对齐（barrier alignment）：先收到某路屏障后，暂时缓冲该路后续数据，等所有输入的屏障 n 都到齐，才拍快照并放行。这保证了 exactly-once 的一致性，但在反压（下游处理不过来）时，对齐等待会拖慢甚至卡住检查点。

Flink 为此提供非对齐检查点（unaligned checkpoint）：不再等待对齐，而是把"已越过屏障、在途缓冲区里的数据"也一并纳入快照，从而在反压下大幅缩短检查点时间。它只用于 exactly-once 模式且并发检查点为 1（⚙演进快·锚 Flink 2.x·随时变）。如果只需要至少一次语义，则根本不用对齐（允许屏障之后的少量数据被重复计入），换取更低延迟。这里体现了老规律：一致性越强，协调代价越高。

### 5.4.5 端到端 exactly-once 与两阶段提交 sink

检查点只保证流处理系统内部状态的精确一次。但作业还要把结果写到外部系统（数据库、另一个 Kafka 主题），如果写出去了、紧接着崩溃并回滚重放，外部就会看到重复写——内部 exactly-once 不等于端到端 exactly-once。

要做到端到端，数据源和数据汇都得配合。源必须可重放（能回退到检查点对应的位置，如 Kafka offset）。汇要么是幂等写（同样的写重复执行结果不变，例如按主键 upsert），要么参与两阶段提交（2PC）：汇在每次检查点时把本周期结果作为一个事务"预提交（pre-commit）",等这次检查点全局成功后再"提交（commit）"，检查点失败则整个事务回滚丢弃。这样"结果对外可见"与"检查点成功"被绑成原子的一步。

```
每个检查点周期：
  算子快照状态  +  sink 预提交事务(数据写入但对外不可见)
        └──────── 检查点全局成功? ────────┐
                     是 → sink 提交事务(结果对外生效，恰好一次)
                     否 → sink 回滚事务(丢弃本周期写，随重放重来)
```

初学者要记住这条链的木桶效应：端到端 exactly-once 要求"可重放的源 + 有检查点的处理 + 幂等或事务性的汇"三者齐备，缺一环就退化成至少一次。Kafka 事务、Flink 的 `TwoPhaseCommitSink` 就是为这条链服务的。

### 5.4.6 "有效一次"的辨析

严格意义上，你不可能保证每条事件的副作用（比如触发一次外部支付）物理上只发生一次——网络故障下无法区分"没收到回复"是没做还是做了没回。业界因此更愿意说有效一次（effectively-once）：从最终状态/结果看等价于恰好一次，靠的是重放 + 幂等/事务把重复的影响抵消掉，而不是物理上从不重复执行。

这是一个重要且常被营销话术模糊的点。当系统宣称 exactly-once 时，读者应理解为"对状态和最终结果而言等效于一次"，其成立前提是上面那条链完整、且外部副作用是幂等或事务性的；对不可抵消的外部副作用（发一封邮件、扣一次款），仍需业务层用幂等键等手段去重。DDIA 明确讨论了这一辨析。

### 5.4.7 savepoint 与 checkpoint 的区别

检查点由系统自动、周期性地触发，服务于故障自动恢复，通常轻量、会被自动清理，格式偏向内部优化。保存点（savepoint）则由用户手动触发，是一次有意的、持久保留的全局快照，用于有计划的运维：升级作业代码、扩缩容改并行度、集群迁移、版本升级时从保存点恢复。

两者机制同源（都是全局一致快照），差别在用途与生命周期。初学者只需分清：checkpoint 是给机器用的"自动存档以防崩溃"，savepoint 是给人用的"手动存档以便有计划地改动作业"。这两个术语与具体细节都属 ⚙演进快·锚 Flink 2.x·随时变。

## 5.5 批流统一与 lambda/kappa

### 5.5.1 Lambda 架构

Lambda 架构是早期为兼顾"准确"与"低延迟"提出的方案：同一份输入数据同时喂给两条并行链路。批处理层（batch layer）在全量历史数据上定期重算，结果准确但有延迟；速度层（speed layer）用流处理对最近的数据做实时近似计算，结果快但可能不够精确；查询时把两层结果合并（serving layer），用批层结果覆盖/校正速度层的近似。

```
             ┌──▶ 批处理层（全量重算，准确，慢） ──┐
输入数据 ──┤                                         ├──▶ 合并查询
             └──▶ 速度层（实时流，近似，快）    ──┘
```

它的价值在于承认了"批准而慢、流快而糙"的现实并同时利用两者，批层还能定期把速度层的误差抹平。但代价很重：同一套业务逻辑要用批和流两种不同的框架各实现一遍，两边要保持语义一致、长期同步维护，运维和心智负担都大。这个"逻辑写两遍"的痛点直接催生了 Kappa。

### 5.5.2 Kappa 架构

Kappa 架构（Jay Kreps 2014 提出）主张：去掉批处理层，只保留一条流处理链路。它把一切数据都看作日志式消息流（5.1.3），因为日志可以持久保留并重放，所以"重新计算历史"不再需要单独的批系统——只要用新版本的流程序从日志起点重放一遍即可。既有实时结果，又能通过重放做全量重算，一套代码、一种框架。

```
输入 ──▶ 持久可重放日志（Kafka…） ──▶ 流处理 ──▶ 结果
                    └── 需要重算历史时：新程序从头重放同一份日志 ──┘
```

它的前提正是 5.1 讲的可重放持久日志与 5.4 讲的精确一次容错——没有这两样，"只靠流搞定批"不成立。Kappa 显著降低了架构与维护复杂度，是当代实时数据平台的主流思路。局限是：对超大规模历史的一次性重算，纯流重放未必比批处理经济；且要求日志保留足够长的历史。

### 5.5.3 批流统一的编程模型

Lambda 的根本痛点是"两套代码"，解决方向除了 Kappa（只用流）之外，还有批流统一的编程模型：让开发者用同一套 API 描述计算，底层既能以批模式（有界输入、一次性跑完）执行，也能以流模式（无界输入、持续跑）执行。Apache Beam（源自 Google Dataflow，5.2/5.3 的时间与窗口语义即出自其模型）是这条路的代表：一份 Beam 管道可以跑在不同的执行引擎（runner）上，也可切换批/流执行。

对初学者，这里的核心洞见来自 Dataflow 论文的那句立场：批与流不是两种范式，而是同一模型在"输入是否有界"这一参数上的两个取值。一旦时间、窗口、触发、累积这些语义被统一定义好，批就成了流的一个特例（有界流），不必再为它单独发明一套 API。

### 5.5.4 有界流即批：统一执行引擎

在编程模型统一之上，执行引擎也在统一。现代引擎（如 Flink）把批处理实现为"有界流"：同一个运行时，输入有界时可以采用更省资源的批式调度与执行优化（例如无需一直维护水位线、可按阶段落盘），输入无界时则走持续流式执行。对用户是同一套算子与语义，对系统是根据有界/无界自动选择更优的执行策略。

这就把 5.1.1 开头那句"批是流的特例"从概念落到了工程：不再需要维护两套引擎，一套引擎两种执行模式即可。需要注意这是 ⚙演进快 的领域，各引擎批流统一的成熟度、性能与 API 覆盖度差异较大且持续演进（锚 Flink 2.x / Beam），具体能力边界待核，选型时应以当时官方文档为准。

### 5.5.5 取舍与选型

三种思路可以这样理解其递进关系。Lambda 用"批 + 流双链路"换准确与实时兼得，代价是双份实现与维护，如今多被视为过渡形态。Kappa 用"可重放日志 + 单流链路"消除双份代码，是当前主流，前提是持久日志与精确一次容错到位、且历史重算成本可接受。批流统一的编程/执行模型是更底层的统一，让批与流共享一套语义与引擎，从根上化解"两遍逻辑"。

选型没有唯一答案，取决于对延迟的要求、历史重算的规模与频率、团队已有技术栈、以及能接受的运维复杂度。初学者应把握主线：整个演进的方向是从"批流分立、逻辑写两遍"走向"批流统一、一套逻辑"，Lambda→Kappa→统一模型正是这条主线的三个台阶。DDIA 与 Kreps 的论述在这个大方向上一致，分歧只在具体权衡与适用边界。
