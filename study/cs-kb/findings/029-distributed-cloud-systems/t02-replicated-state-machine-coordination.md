## 2.1 日志压缩与快照

### 2.1.1 共识日志为什么必须被压缩

复制状态机的核心是一条只追加（append-only）的操作日志：每个副本把相同顺序的相同操作重放一遍，就得到相同的状态。问题在于这条日志只增不减，系统跑得越久日志越长，最终会撑爆磁盘，而且节点重启后要从头重放整条日志才能恢复状态，恢复时间随运行时间线性增长。日志压缩（log compaction）就是解决「日志不能无限长」的工程手段，其中最主流的一种叫快照（snapshot）。

理解这里的关键，是分清「日志」和「状态」两样东西。日志记录的是「发生过哪些操作」（例如 `SET x=1`、`SET x=5`、`DEL y`），状态记录的是「现在的结果长什么样」（例如 `x=5`）。对一个键值存储来说，`x` 被改了一百次，日志里就有一百条记录，但状态里 `x` 只有最后一个值。既然前面九十九次修改的效果已经完全体现在当前状态里，只要我们把「当前状态」整体存下来，前面那些日志条目就再也不需要了。快照就是「把某个日志位置为止的状态机完整状态，序列化存成一个文件」。

### 2.1.2 快照的构成与元数据

一份 Raft 风格的快照不只包含状态机数据本身，还必须记录两个关键元数据：这份快照覆盖到日志的哪个位置（lastIncludedIndex，最后一条被并入快照的日志条目下标）和那条日志条目的任期（lastIncludedTerm）。日志与快照的关系可以画成这样：

```
压缩前的日志：
  [1] [2] [3] [4] [5] [6] [7]   ← 全部条目都在
   x=1 x=2 y=9 x=5 z=3 x=8 w=1

压缩后（对 index<=5 做快照）：
  快照{ lastIncludedIndex=5, lastIncludedTerm=T, state={x=5,y=9,z=3} }
  剩余日志： [6] [7]
             x=8 w=1
```

lastIncludedIndex 和 lastIncludedTerm 之所以不能省，是因为共识协议在做日志一致性检查（AppendEntries 里比对前一条日志的 index/term）时，需要知道快照「顶端」那条虚拟条目的坐标。快照把前面的日志吃掉了，但被吃掉的最后一条的 index/term 必须以元数据形式保留，否则新来的日志条目就无法与本地日志对齐。这是初学者写快照时最容易漏掉的一环——只存了 KV 数据，忘了存这两个坐标，结果快照之后集群再也对不上日志。

### 2.1.3 日志截断与垃圾回收

有了快照，就可以安全地丢弃 lastIncludedIndex 及之前的所有日志条目，这一步叫日志截断（log truncation）或日志 GC。截断之后磁盘占用大幅下降，重启恢复时先加载快照直接得到状态、再只重放快照之后的少量日志即可，恢复时间不再随总运行时长增长。

需要小心的是「什么时候截断才安全」。原则是：只截断已经被并入快照、并且该快照已经持久化落盘的部分。如果先删日志、再存快照，中间崩溃就会既没日志又没快照，状态永久丢失。所以正确顺序是先把快照写到稳定存储、确认落盘，再删对应日志前缀。另外多数实现不是每追加一条就快照一次（那样开销巨大），而是设一个阈值——例如日志字节数或条目数超过某个界限才触发一次快照。这个阈值是典型的工程参数，具体默认值随实现而异（标「待核」，不同共识库取值不同），核心权衡是：阈值越小快照越频繁、单次快照越小但总开销高，阈值越大日志越长、恢复越慢。

### 2.1.4 InstallSnapshot：让落后太多的节点靠快照追赶

正常情况下，领导者用逐条追加日志（AppendEntries）的方式让落后的跟随者追上进度。但如果某个跟随者掉线太久，它需要的那些日志条目已经被领导者快照并截断掉了，领导者手上根本没有那些条目可发。此时领导者改用 InstallSnapshot RPC，直接把整份快照发给这个落后节点，让它一步到位跳到快照对应的状态，再从快照之后继续追日志。

这个机制回答了「日志都被压缩了，落后节点还怎么追」这个自然的疑问。可以把它理解成：平时用「增量」（一条条日志）同步，增量对不上了就退化成「全量」（整份快照）同步。一个容易忽略的细节是，跟随者收到快照后要用快照内容整体替换自己的状态机和日志，而不是简单往后拼接——因为快照代表的是一个自洽的完整状态点。Raft 扩展版论文第 7 节专门描述了这套快照 + InstallSnapshot 机制，MIT 6.5840 的 LEC 7 与 Lab 3 也据此实现。

### 2.1.5 快照与运行中状态机：写时复制避免长时间阻塞

生成快照需要把状态机的全部内容序列化下来，如果状态很大，这个过程可能耗时较长；如果在序列化期间把整个状态机锁住、停止服务，就会造成明显的可用性抖动。工程上常用写时复制（copy-on-write）或多版本手段解决：快照开始时冻结一个逻辑快照点，后台线程慢慢序列化这个点的内容，同时前台仍可继续处理新请求，新写入落在新版本上，不影响正在被序列化的旧版本。

对初学者，这里的直觉是「拍照片时不能让所有人停下不动」——你需要一种机制，让你能拍下「某一瞬间」的完整状态，同时世界继续运转。像 LSM-Tree 那种本身就不可变、分层的存储结构天然适合做这件事，因为旧层本来就是只读的，直接引用即可。这也解释了为什么共识层的快照常和底层存储引擎的结构耦合设计。

### 2.1.6 快照之外的压缩形式

快照不是唯一的日志压缩方式。Ongaro 的博士论文（Raft 扩展讨论）区分了几类：基于内存状态整体转储的快照（适合状态能放进内存的系统，如多数协调服务的 KV），以及增量式压缩——例如 log-structured merge（LSM）或 log cleaning，它们不一次性转储全部状态，而是渐进地清理陈旧条目，适合状态量大、不适合频繁全量转储的场景。还有一种是领导者主导 vs 各副本各自独立做快照的区别：各副本独立快照更省网络（不用传快照），但每个副本都要承担序列化开销。

「日志压缩」是一个问题类别，快照只是其中最直观、最常被教学采用的一种解法；真实系统会根据状态规模和存储引擎选择不同压缩策略。多数教学与主流共识库（如常见的 Raft 实现）默认走「全量内存状态快照」这条路，因为协调服务的状态通常不大。

## 2.2 集群成员变更

### 2.2.1 为什么在线改成员是危险的

集群运行中难免要增删节点（换掉坏机器、扩容、缩容）。天真的做法是「让每台机器直接把配置从旧集合改成新集合」，但由于各节点不可能在同一瞬间切换，就会出现一个致命窗口：一部分节点还认为集群是旧配置、另一部分已认为是新配置。在这个窗口里，可能同时存在两个互不相交的多数派——旧配置的多数派选出一个领导者，新配置的多数派选出另一个领导者，两个领导者都自认为合法，各自提交冲突的操作。这就是脑裂（split-brain），直接违反共识的安全性。

用一个最小例子看清楚。集群从 3 台 {A,B,C} 扩到 5 台 {A,B,C,D,E}。若 A、B 先切到新配置、C、D、E 还没切（或反过来），在切换的重叠期：旧视角下 {A,B} 是不是多数？旧配置 3 台里多数是 2，{A,B} 恰好是旧多数；新视角下 {C,D,E} 是 5 台里的 3，也是新多数。于是 {A,B} 和 {C,D,E} 各自能选出领导者——两个领导者并存。成员变更协议存在的全部意义，就是杜绝「新旧两个多数派同时成立」这一刻。

### 2.2.2 联合共识（joint consensus）

Raft 论文给出的通用方案是联合共识。它不让集群从旧配置 C_old 直接跳到新配置 C_new，而是先经过一个过渡配置 C_old,new（联合配置）。在联合配置期间，任何决策——选举领导者、提交日志——都要求同时得到旧配置的多数派和新配置的多数派两边的同意。切换过程分成两阶段：

```
阶段一：领导者把 C_old,new 作为一条日志条目复制、提交
        此期间：任何多数派判定 = 旧多数派 且 新多数派（两边都要过）
        → 因为要求"两边都过"，不可能出现新旧各自独立成派

阶段二：C_old,new 提交后，领导者再把 C_new 作为日志条目复制、提交
        C_new 提交后，旧配置节点可安全下线，切换完成
```

联合配置这个「双多数派」要求，正是防脑裂的关键：在 C_old,new 生效期间，无论旧派还是新派都无法单独凑齐一个能拍板的多数，任何决定都必须旧派新派共同点头，于是根本不存在「两个独立多数派」的可能。等到过渡稳定、再进入纯 C_new，就安全了。一个要点是：配置变更本身是作为普通日志条目走复制流程的，一旦某条配置条目进了节点的日志，该节点立即按新配置行事（不等它被提交）——这保证了配置切换和日志复制用的是同一套已被证明正确的机制。

### 2.2.3 单节点变更：更简单的替代方案

联合共识实现较繁琐。Ongaro 的博士论文提出并被许多实现采用的一个简化：限制每次只增加或删除一个节点。为什么一次只动一个就能免掉联合配置？因为当集群规模变化 1 时，旧多数派和新多数派必然重叠（有公共成员）。

```
3 台 → 4 台：旧多数=2，新多数=3；任意"旧的2"与"新的3"必有交集
4 台 → 5 台：旧多数=3，新多数=3；两组各3从至多5台里选，必然相交
```

有了这个重叠，就不可能出现旧新两个不相交的多数派，也就不会脑裂，于是不需要联合配置那套双多数派机制，直接把新配置作为一条日志条目提交即可。代价是每次只能动一个节点：要把集群从 3 台换成另外 3 台，得一台一台地加/减，做多轮。这是「实现简单」和「变更灵活」之间的取舍。DDIA 与多数生产级 Raft 实现倾向单节点变更这条路，因为它更不容易写错。这里存在来源侧重差异：Raft 原论文主推联合共识、把单节点变更作为附带提及；后续实践（含 Ongaro 论文与主流共识库）更强调单节点变更，两者都正确，只是适用工程复杂度不同。

### 2.2.4 成员变更中的可用性与干扰细节

除了防脑裂，成员变更还有几个易被忽略的工程点。其一，新加入的节点日志是空的，如果立刻把它算进多数派，会拖慢甚至阻塞提交（要等它追完日志才能凑齐多数）。解法是让新节点先以「无投票权学习者（learner / non-voting）」身份追日志，追得差不多了再正式纳入投票成员。其二，被移除的节点如果没意识到自己被移除，仍会因为收不到心跳而发起选举、用更高任期去打扰在任领导者。解法之一是节点在确信当前领导者健在（最近收到过心跳）时拒绝理会新的投票请求。其三，如果被移除的恰好是当前领导者，它要在 C_new 提交后再退位。

这些细节共同说明：成员变更的难点不止在「安全」（不脑裂），还在「不影响可用性」（不因加入空节点而卡住、不因移除节点而被反复骚扰选举）。初学者往往只关注前者，实现时却被后者绊倒。

## 2.3 线性一致读

### 2.3.1 为什么读也可能读到陈旧值

写操作走共识、经多数派确认才提交，这是稳的。但读操作如果图快、直接让某个节点返回它本地的值，就可能读到过时数据。最典型的场景：一个旧领导者已经在网络分区中被隔离、集群已经在另一边选出了新领导者并提交了新写入，而这个旧领导者自己还不知道，仍以为自己是领导者，继续用本地状态回答读请求——它返回的就是分区之前的陈旧值。要让读也满足线性一致（读到的一定是「读发起那一刻之前已提交的最新值」），必须有机制确认「我读的时候，我确实还是那个掌握最新已提交数据的领导者」。

这条是本小主题的核心痛点。初学者常以为「读嘛，直接读领导者本地不就行了」，恰恰在领导者失去领导权而不自知的窗口里，本地读会破坏线性一致性。承接上一门课：这里追求的「线性一致」正是最强的单对象一致性，实时序 + 原子生效。

### 2.3.2 ReadIndex：不写日志也能保证读线性一致

最保守的做法是把读也当成一条空操作日志走一遍共识，但那样每次读都要写一轮日志、开销大。ReadIndex 是一种更省的做法，它不真的往日志里写东西，只做两步确认：

```
ReadIndex 读流程：
  1. 领导者记下当前的 commitIndex，记为 readIndex
  2. 领导者向多数派发一轮心跳（heartbeat），确认自己仍是合法领导者
     （多数派回应 = 没有更高任期的新领导者存在）
  3. 等本地状态机 apply 到 readIndex（保证本地已应用到那个点）
  4. 用本地状态机回答读请求
```

第 2 步是精髓：通过一轮心跳拿到多数派确认，就能断定「在这一刻没有别的领导者能提交比我更新的数据」，因此我此刻已提交的 readIndex 就是全局最新的已提交点。读请求返回的值满足线性一致，代价只是一轮心跳的往返延迟，比写一条日志便宜得多（不落盘、不复制数据）。还有一个补充细节：新当选的领导者必须先提交一条自己任期内的（空）条目、确认已 apply 上一任期的所有已提交条目后，才能安全服务 ReadIndex 读，否则可能漏掉上一任期尾部的已提交数据。

### 2.3.3 租约读（lease read）：连心跳都省掉

ReadIndex 每次读都要一轮心跳往返，还能更快吗？租约读进一步优化：领导者在一次成功的心跳后，认为自己在「一个租约期」内稳坐领导位，这个租约期通常取得比选举超时略短。在租约有效期内，领导者直接用本地状态回答读，连那轮确认心跳都不发，读延迟接近本地读。

租约读的正确性依赖一个假设：各节点的时钟漂移有界。因为它是靠「时间还没到租约期满」来推断「我还是领导者」，而不是靠一轮实际的多数派确认。如果某节点时钟跑得异常快或异常慢，租约的时间推断就可能失效，出现旧领导者在自以为租约未满时错误地服务了陈旧读。所以租约读比 ReadIndex 快，但多了一条对时钟假设的依赖——这正是它与下一门课会讲的 TrueTime 类方案在「用时间做正确性论证」上的相通与风险之处。工程上常把租约期设为「选举超时 − 一个时钟漂移余量」来留安全裕度。

### 2.3.4 跟随者读与本地读的取舍

为了分摊读压力，有些系统允许跟随者也服务读（follower read）。但跟随者本地可能落后于领导者，直接读会陈旧。让跟随者读也线性一致的办法是：跟随者先向领导者索要当前的 readIndex，等自己 apply 到该 index 后再用本地数据回答。这样读吞吐可以横向扩展到多个节点，代价是每次跟随者读多一次「问领导者要 readIndex」的往返。

这里体现了一条贯穿分布式读优化的主线：一致性强度、读延迟、读吞吐三者互相拉扯。要最强一致又要最低延迟，就难扩吞吐（都压在领导者身上）；要扩吞吐让跟随者也读，就得付额外协调（问 readIndex）或放松一致性（接受陈旧）。没有免费的午餐，工程上按业务能容忍的一致性级别来选点。

### 2.3.5 与「读走共识」及协调服务同步读的对照

把上面几种放到一条谱系上对比：最强最贵的是「读也写一条日志走完整共识」，正确但每读一次都要复制落盘；ReadIndex 去掉了落盘和数据复制、只留一轮心跳确认；租约读连心跳也省、换来对时钟的依赖；跟随者读牺牲了「只在一个点读」以换吞吐。它们都是在「不牺牲线性一致」的前提下逐步压低读成本。作为对照，下一小主题的 ZooKeeper 走的是另一条路——默认允许本地陈旧读、只保证写线性一致，需要强读时用一个显式的 `sync` 操作把本地追到最新再读；这与 Raft 侧「默认就想让读也线性一致」的取向不同，是两种设计哲学，无所谓对错，取决于系统想给用户什么默认保证。

## 2.4 ZooKeeper/Chubby 协调服务

### 2.4.1 协调服务是什么，为什么不自己写共识

前面把共识核心加固成了能长期运行、能变更成员、能高效读的复制状态机。协调服务（coordination service）就是把这套东西封装成一个通用组件对外提供，让各种分布式应用不必各自重造共识轮子，而是把「谁是主」「集群里有哪些活节点」「这把分布式锁归谁」这类需要强一致的小块元数据，托管给它。ZooKeeper（Yahoo!，ATC 2010）和 Chubby（Google，OSDI 2006）是这一类最经典的两个系统。

理解定位很重要：协调服务不是用来存海量业务数据的通用数据库，它存的是少量、关键、要强一致的协调用元数据（配置、成员、锁、领导者身份）。它的价值在于「把最难写对的那部分（共识 + 会话 + 通知）做对一次，供所有人复用」。DDIA 里把这类系统归为「把线性一致性和全序广播打包出售」的基础设施。

### 2.4.2 数据模型：znode 与节点类型

ZooKeeper 对外呈现的是一个类似文件系统的层级命名空间，每个节点叫 znode，可以带一小块数据，也可以有子节点：

```
/
├── /config              (持久 znode，存全局配置)
├── /election
│   ├── /election/n_0000001   (临时+顺序 znode)
│   ├── /election/n_0000002
│   └── /election/n_0000003
└── /locks
    └── /locks/resourceA      (临时 znode，谁建谁持锁)
```

znode 有几种关键类型，它们组合出协调原语的基础。持久（persistent）znode 一直存在，直到被显式删除；临时（ephemeral）znode 与创建它的客户端会话绑定，会话一断（客户端崩溃或超时），这个 znode 自动消失——这是实现「故障自动释放锁 / 自动摘除死节点」的核心。顺序（sequential）znode 在创建时由服务端自动追加一个单调递增的序号后缀，多个客户端并发创建时天然得到一个全局有序的编号——这是实现锁排队和选主的核心。临时和顺序可以叠加（临时顺序 znode）。初学者要抓住的直觉是：ZooKeeper 没有直接提供「锁」这个 API，而是提供 znode 这几种性质，让你用它们拼出锁、选主等原语。

### 2.4.3 watch：一次性的变更通知

客户端可以在读某个 znode 时挂一个 watch（监视点），当这个 znode 之后发生变化（数据被改、被删、子节点增删）时，服务端给客户端发一个通知。这让客户端不用轮询就能感知变化。关键特性是 watch 是一次性触发（one-shot）：触发一次后就失效，客户端若还想继续监视，必须在处理通知时重新注册。

以为注册一次就能一直收到通知，结果错过了后续变化。正确模式是「收到通知 → 重新读取当前状态并重新挂 watch」。此外 watch 通知只告诉你「变了」，不告诉你「变成了什么」，所以拿到通知后要回读。watch 与 ZooKeeper 的顺序保证配合，能保证客户端看到的事件顺序与实际发生顺序一致，这是它能用来做可靠通知的基础。

### 2.4.4 会话与心跳

客户端连到 ZooKeeper 集群会建立一个会话（session），会话有超时时间，客户端靠定期心跳维持会话存活。会话是临时 znode「生死」的判据：只要会话活着，该客户端创建的临时 znode 就在；心跳超时会话过期，所有该会话的临时 znode 被服务端自动删除，挂在其上的 watch 触发，其它客户端因此得知这个节点死了。

会话把「进程活着没有」这个分布式系统里出了名难判定的问题，收敛成了一个由协调服务统一裁决的判断。它的意义在于给上层一个可靠的「故障探测 + 自动清理」原语。要注意会话超时是有代价的取舍：设太短，网络抖动就误判客户端死亡、误删临时节点、误释放锁；设太长，真死了也要等很久才被发现。这个超时值是协调服务里最需要按环境调的参数之一（具体默认区间随版本，标「待核」）。

### 2.4.5 Zab：ZooKeeper 的原子广播

ZooKeeper 底层用一个叫 Zab（ZooKeeper Atomic Broadcast）的协议，把所有写请求（状态变更）通过一个领导者按全序广播给所有副本，保证每个副本以相同顺序应用相同的写，从而各副本状态收敛一致。Zab 与 Paxos/Raft 同属「靠领导者做全序复制」这一大类，但它是为「主备复制 + 崩溃恢复」这一具体场景专门设计的，强调恢复后已提交事务不丢、且顺序不乱。

对初学者，可以把 Zab 理解成「ZooKeeper 版的 Raft 类协议」——它们要解决的核心问题（选一个领导者、让它把操作按序复制到多数派、崩溃后能一致恢复）是相通的。历史上 Zab 与 Paxos 的关系有过讨论：Zab 保证的「主变更后前一个主的已提交更新不被后一个主推翻，且保持顺序」比经典单值 Paxos 关注点更贴近日志复制。Chubby 走的则是另一条：直接基于 Paxos 实现其复制日志。这体现了同一目标下不同系统的协议选择差异。

### 2.4.6 一致性保证：写线性一致、读可陈旧、sync 补强

ZooKeeper 给出的保证要精确记住，因为它是一个「非对称」的一致性模型。所有写操作是线性一致的（经领导者全序、多数派确认）。但读操作默认由客户端连接的那台服务器本地应答，为了快，该服务器可能还没应用到最新的写，因此读可能返回陈旧数据。同时它保证同一个客户端看到的操作是 FIFO 客户端序（该客户端自己发出的请求按序生效、且读能看到自己之前写的结果，即读己写）。如果客户端需要读到「全局最新」，要先调用 `sync` 操作，它促使该服务器先把日志追到当前提交点，随后的读才保证不陈旧。

这套「写强、读默认弱、按需 sync」的设计是 ZooKeeper 高读吞吐的来源：绝大多数读不打扰领导者、直接本地返回，因此读可以随副本数线性扩展。代价是把「要不要强一致读」的决定权交给了应用开发者，用错（该 sync 没 sync）就会读到旧值。这与上一小主题 Raft 侧「默认就让读线性一致」是相反的默认取向，理解这个差异是用好协调服务的关键。

### 2.4.7 协调原语：锁、选主、成员、配置、屏障

有了 znode 类型、watch、会话这几样基础，就能拼出常用协调原语。分布式锁：各客户端在锁路径下创建临时顺序 znode，序号最小者持锁，其余各自 watch 前一个序号的 znode（而非都 watch 最小的那个，避免「惊群」——一个释放全体被唤醒），前驱消失时轮到自己。领导者选举：与锁几乎同构，序号最小者当选领导者，其余监视前驱等待接班；用临时节点保证领导者崩溃后自动让位。成员管理 / 故障探测：每个成员进程创建一个临时 znode，靠临时节点随会话消失来自动反映谁活着；其它进程 watch 这个目录感知加入/退出。配置管理：把配置放在持久 znode，客户端读并挂 watch，配置一改所有客户端被通知后重读。屏障（barrier）/ 双屏障：用某个 znode 的存在与否、或子节点数量达到阈值来同步一批进程的开始/结束。

这些原语共同印证了 2.4.2 的直觉：ZooKeeper 卖的不是「锁 API」而是「拼锁的零件」。理解「临时+顺序 znode + watch 前驱 + 会话自动清理」这个组合，就掌握了绝大多数协调模式的通用套路。这里有一个反复出现的易错点——惊群效应：如果所有等待者都监视同一个 znode，持有者一释放会同时唤醒所有等待者、造成一次风暴；正确做法是让每个等待者只监视排在自己前一位的那个 znode，形成一条唤醒链。

### 2.4.8 Chubby 对照

Chubby 是 Google 更早的协调服务（OSDI 2006），设计取向与 ZooKeeper 有共性也有差异。共性：都提供一个类文件系统的小命名空间、都用会话 + KeepAlive（心跳）判活、都用底层共识（Chubby 用 Paxos）做副本一致、都被用于分布式锁与主选举、且都强调「粗粒度锁」（锁一般持有较久，如「谁是主」，而不是高频短锁）。差异：Chubby 明确面向「粗粒度锁 + 少量元数据」并直接把「提供锁」作为主要卖点和接口（客户端拿锁、锁带序列号防止过期持有者误操作），而 ZooKeeper 更倾向提供底层原语让用户自己组装、并强调无等待（wait-free）的读写 API 与高读吞吐。

放在一起看，两者证明了「协调服务」是一个成熟的系统类别：把共识 + 会话 + 通知 + 少量强一致元数据打包，供上层复用。选型上，开源生态多用 ZooKeeper（及理念相近的 etcd 等），Chubby 是 Google 内部系统。它们的接口、默认参数会随版本演进（⚙演进快），但「用临时/顺序节点 + watch/通知 + 会话判活拼协调原语」这一核心心智是稳定的。

## 2.5 链式复制

### 2.5.1 拓扑与读写路径

链式复制（chain replication，van Renesse & Schneider, OSDI 2004）是与「基于多数派 quorum 的共识复制」并列的另一条强一致复制路线。它把所有副本排成一条链，写和读走不同的端：

```
写请求 ──▶ [ HEAD ] ──▶ [ 中间节点 ] ──▶ ... ──▶ [ TAIL ] ──▶ 读请求
             (头)                                      (尾)
          所有写从头进入                          所有读从尾返回
          沿链单向传播到尾                      写到达尾才算提交、才回复客户端
```

写请求只从链头（head）进入，沿着链一个接一个往下传，直到链尾（tail）；写传播到尾之后，由尾节点向客户端确认提交。读请求只由链尾（tail）应答。这个「写从头进、读从尾出」的分工是链式复制的全部机巧所在。

### 2.5.2 为什么能保证强一致

强一致的关键在于「提交点」被定义在链尾。一个写只有传播到了尾节点，才被认为已提交并向客户端确认。而所有读都从尾节点取值，尾节点的状态恰好就是「已经走完整条链、已提交」的那些写。因此读永远只能读到已提交的数据，绝不会读到「还在链中间、尚未到达尾部」的未提交写。这就自然得到了线性一致：读总是反映所有已确认的写，且顺序由链的单向传播唯一确定。

可以和多数派 quorum 复制对比着理解直觉。quorum 复制里，正确性靠「读写集合必然相交」这个数学性质来保证读到最新写；链式复制则靠「结构」——强制写单向流、把读点固定在流的终点——来保证同样的强一致。前者是「集合交集」式的论证，后者是「管道终点」式的论证，殊途同归。

### 2.5.3 与主从/quorum 复制的吞吐延迟对比

链式复制的吸引力在吞吐。在主从复制里，主节点既要处理所有写、又要把写扇出（fan-out）复制给所有从节点，主节点的出向网络成为瓶颈。链式复制把复制的传播分摊到链上每个节点——每个节点只需把写发给它的后继一个节点，出向压力均摊，因此在写密集场景下总吞吐可以更高。读则全压在尾节点，尾节点的读吞吐是一个上限。

代价是写延迟。写要从头依次流到尾，延迟随链长（副本数）线性增长，而 quorum 复制只要多数派响应即可、不必等最慢/最远的那个。所以链式复制在「高吞吐、副本数不太多、能接受略高写延迟」的场景占优；quorum 共识在「要低写延迟、要容忍部分慢副本」的场景占优。这是一组清晰的工程取舍，没有普适最优。

### 2.5.4 故障处理与配置管理

链上任一节点故障都要能修复而不破坏一致性，处理方式按位置分三种。链头故障：让链头的后继升为新头，之前只到过旧头、还没往下传的写会丢失（但那些写本来也没被确认给客户端，安全）。链尾故障：让链尾的前驱升为新尾；因为链是单向传播、前驱的状态一定不落后于旧尾（是旧尾状态的超集或相等），所以新尾能无缝接管读、不会丢已提交数据。中间节点故障：把它从链中摘掉、让它的前驱直接连到它的后继，并补发可能漏传的写。

这些重配置由一个独立的、可靠的配置管理者（master / configuration manager）来协调——它监控各节点存活、决定新的链拓扑、并把新配置告知相关节点。这里有一个重要的分账：配置管理者本身必须是强一致、高可用的，通常正是用一个共识服务或协调服务（如 ZooKeeper 类系统）来实现。也就是说，链式复制负责「数据面的高吞吐强一致复制」，但「谁在链上、链长什么样」这个控制面元数据，仍然托管给一个基于共识的协调服务。二者是配合关系，不是替代关系。

### 2.5.5 CRAQ：让读也能扩展

原始链式复制把读全压在尾节点，尾节点成了读吞吐上限。CRAQ（Chain Replication with Apportioned Queries，NSDI 2009）扩展了它，让链上每个节点都能服务读，从而读吞吐随副本数扩展。做法是每个对象在节点上可以有多个版本，并标记为「干净」（clean，已知是已提交的最新值）或「脏」（dirty，有更新的写正在链中传播、尚未提交）。节点收到读请求时，如果本地版本是干净的，直接返回；如果是脏的，就去问链尾「当前已提交的版本号是多少」，再返回对应版本。

CRAQ 的巧思是：绝大多数时候对象是干净的，读能被任意节点本地满足、无需打扰尾节点，于是读吞吐随节点数线性扩展；只有在某对象正被写、处于脏状态时，读它才需要一次「问尾节点要版本号」的轻量往返。它既保住了链式复制的强一致（脏时以尾节点为准），又解除了「读只能走尾」的吞吐瓶颈。这是「读多写少」负载下的一个漂亮优化。

### 2.5.6 链式复制与共识复制的关系定位

最后厘清链式复制在整张图里的位置。它和 Raft/Paxos 这类 quorum 共识都能提供强一致复制，但走的是不同结构：共识靠多数派交集，链式靠单向管道 + 尾部读点。它们不是谁淘汰谁——链式复制常被用在需要极高吞吐的存储层，而它赖以运转的成员/配置管理又反过来依赖一个共识型协调服务。理解这一点能纠正一个常见误解：以为「强一致复制 = 一定要跑 Paxos/Raft」。事实是强一致有多条实现路线，quorum 共识和链式复制是其中两条主要的，各有吞吐/延迟/容错侧写，真实系统按负载选用，甚至组合使用（链做数据面、共识做控制面）。
