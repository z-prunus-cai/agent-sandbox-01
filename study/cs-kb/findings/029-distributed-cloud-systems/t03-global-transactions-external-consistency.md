## 3.1 TrueTime 与有界时钟不确定性

### 3.1.1 为什么全球数据库需要"可信的时间"

分布式系统里给事件排全局顺序，本来有两条路：逻辑时钟（Lamport/向量时钟，只记因果，不记真实时间）和物理时钟（真实的墙上时间，但每台机器都有偏差）。全球数据库想用**物理时间戳**给事务排序，因为这样才能实现"跨会话、跨客户端"的外部序——用户 A 提交后打电话让用户 B 去读，B 必须读到 A 的写。逻辑时钟看不见这种"系统外的因果"，物理时间戳才行。

问题在于物理时钟不可信。机器晶振有漂移，NTP 校时有网络延迟和抖动，两台机器读出的"现在"可能差几毫秒到几十毫秒。如果你天真地拿本地时钟当全局序：机器 X 上事务 T1 用它的时钟盖了时间戳 100，机器 Y 上后发生的 T2 用它偏慢的时钟盖了 98，那么按时间戳排序 T2 反而"先于"T1，全局序就错了。传统做法要么放弃全局物理序（只保证单分片有序），要么用一个中心化时间戳服务器（成为瓶颈与单点）。TrueTime 的思路是第三条：**不消除时钟误差，而是把误差的上界老实测出来、显式暴露给上层，让上层主动绕开它**。这就是"有界时钟不确定性"的含义——误差不是被假装成零，而是被量化成一个已知的界 ε。

### 3.1.2 TrueTime API：返回时间区间而非时间点

TrueTime 是一套 API，核心方法 TT.now() **不返回一个时间点，而返回一个区间** [earliest, latest]，并保证"调用发生的那个绝对真实时刻 t_abs 一定落在这个区间内"。区间宽度就是 2ε（ε 是当前时刻的不确定半径）。

API 的三个方法：

```
TT.now()      → 返回 TTinterval:[earliest, latest]，保证 earliest ≤ t_abs ≤ latest
TT.after(t)   → 返回 true 当且仅当 t 一定已经过去了（即 t < now.earliest）
TT.before(t)  → 返回 true 当且仅当 t 一定还没到（即 t > now.latest）
```

理解 TrueTime 的关键是把"时钟"从"一个骗你说很准的数"改成"一个诚实交代自己不确定的区间"。打个比方：普通手表告诉你"现在 12:00:00"，但它可能快了或慢了几秒你却不知道；TrueTime 手表告诉你"现在真实时间在 11:59:59.996 到 12:00:00.004 之间"——它不假装精确，但它给出的区间一定罩住真值。有了这个诚实的区间，上层就能做两件笃定的判断：TT.after(t) 为真时，可以百分百确信时刻 t 已经过去（因为连区间下界都超过 t 了）；TT.before(t) 为真时，可以确信 t 还没到。后面的 commit-wait 就建立在 TT.after 这个"一定过去了"的笃定之上。易错点：TT.now() 两次调用返回的区间会因为时间流逝和重新校时而变化，ε 不是常数。

### 3.1.3 时钟源：GPS + 原子钟的双保险

TrueTime 的时间由每个数据中心的一组**时间主机（time masters）**提供，主机的时钟来自两类物理源：**GPS 接收机**和**原子钟**。每台机器上跑一个 **timeslave daemon**，定期（论文中约每 30 秒一次 poll）向多个时间主机校时，并用 Marzullo 算法式的手段剔除说谎的主机、合成出本地的时间区间。

用两类时钟源而不是一类，是为了让它们的**失效模式相互独立**。GPS 便宜、精度高，但有系统性失效风险：天线故障、GPS 信号被干扰/欺骗、闰秒 bug、无线电频率干扰——这些可能让一批 GPS 主机同时给出错误但"看起来一致"的时间。原子钟（铯钟/铷钟）不依赖外部信号，失效方式完全不同：它会**缓慢漂移**（drift），而不是突然跳变，且不同原子钟的漂移彼此独立。于是当 GPS 集体出问题时，原子钟能兜底；原子钟漂移时，GPS 能把它拉回。论文强调"两种时钟源的失效原因不相关"正是可靠性的来源。这是一个典型的"用异构冗余对抗共因失效"的系统设计思路，初学者可以记：单一高精度源不如两个失效方式互不相关的源。

### 3.1.4 不确定性 ε 从哪来、有多大

ε（epsilon，不确定半径）主要由两部分累积：其一是**本地时钟在两次校时之间的漂移**——daemon 保守地按一个最坏漂移率给本地时钟"记账"，Spanner 论文取的应用漂移率约 **200 μs/s**（每秒最多漂 200 微秒）；其二是**校时本身的不确定**——到时间主机的通信延迟、主机自身的不确定。

在两次 poll 之间，ε 呈**锯齿形（sawtooth）**变化：刚校完时 ε 最小，随时间线性增大（因为漂移在累积），到下次 poll 又被拉回。论文报告的典型区间是 ε 在每个 poll 周期内**从约 1 ms 变化到约 7 ms**（poll 周期约 30 秒；30 s × 200 μs/s = 6 ms 的漂移增量，加上基础项约得到这个上界）。论文 Figure 6 显示生产环境 ε 的分布，90 分位大致在数毫秒量级。

要点是 ε 越小越好，因为后面 commit-wait 平均要等约 2ε，ε 直接决定写事务的延迟代价。所以 Spanner 花力气把 ε 压到毫秒级：足够密的时间主机、足够短的 poll 间隔、快的网络。易错点/时效：这些具体数值来自 2012 年论文的生产环境，⚙演进快·锚 OSDI2012——如今商用 Cloud Spanner 的实际 ε 与时钟基础设施细节 Google 未逐版公开，具体现值「待核」，不应把 1–7 ms 当作当前商用保证。若某个数据中心 GPS/原子钟大面积故障导致 ε 飙升，Spanner 宁可让 ε 变大（写变慢甚至暂停），也不会缩小区间冒破坏正确性的险——正确性优先于可用性。

### 3.1.5 commit-wait：主动"等过"不确定性

commit-wait 是把 TrueTime 的诚实区间转化为正确性的关键动作：一个读写事务在协调者算好提交时间戳 s 之后，**并不立刻对外生效，而是先阻塞等待，直到 TT.after(s) 为真**——也就是等到"现在的时间区间下界都已经超过 s"，从而确信绝对真实时间已经越过了 s。等待时长平均约 2ε。

```
提交时间线（commit wait）：
  t0: 协调者收到 commit 请求
  t1: 令 s = TT.now().latest        ← 时间戳取"区间上界"，保证 s ≥ 任何已发生事件的真实时刻
      （同时被 2PL 的锁、2PC 的 prepare 约束，见 §3.3）
  t2 .. : 反复检查 TT.after(s)？
          即等待直到 TT.now().earliest > s
          ────── commit wait，长度 ≈ 2ε ──────
  t3: TT.after(s) 为真 → 释放锁、对客户端返回 commit 成功
```

时间戳 s 取区间**上界**（latest），保证 s 不小于此刻任何已经发生的真实时刻；提交前又等到 s 落进"确定的过去"（earliest 都超过 s），保证 s 不大于此刻的真实时刻。两头一夹，s 就被牢牢钉在事务真实存续的那段时间之内，且当客户端拿到"提交成功"时，绝对真实时间一定已经 ≥ s。这就使得"后开始的事务"看到的 TT.now() 一定给出更大的时间戳，从而时间戳顺序与真实时间顺序一致——正是 §3.2 外部一致性的机械保证。易错点：commit-wait 等的是"时间过去"，不是"等别的节点"，它是纯粹的本地等待；ε 越大等得越久，这解释了为什么 TrueTime 要拼命压小 ε。初学者常误以为"等 2ε 是在等网络"——不是，是在等物理时间流过不确定区间。

## 3.2 外部一致性

### 3.2.1 什么是外部一致性

外部一致性（external consistency）是 Spanner 提供的一致性保证，可以一句话概括：**如果事务 T1 的提交在真实时间上先于事务 T2 的开始，那么系统分配的时间戳满足 timestamp(T1) < timestamp(T2)，并且所有观察者看到的事务全局顺序都与这个真实时间顺序一致**。它等价于"事务粒度的线性一致性"，也常被称为 strict serializability（严格可串行化）——既是可串行化（等价于某个串行执行），又要求那个串行顺序尊重真实时间先后。

它强在哪？普通可串行化只保证"存在某个串行顺序"，但那个顺序可以违背真实时间——比如你先提交了 T1、朋友随后提交 T2，可串行化允许数据库把它俩排成 "T2 在前 T1 在后"。外部一致性堵死了这种反直觉：只要一个事务在墙上时钟意义上确实完成在另一个之前，它们的顺序就板上钉钉。最经典的例子：老板在系统里提交"你被解雇了"，然后当面告诉你"去看邮件"，你打开邮件（这是一个 read-only 事务），外部一致性保证你一定看得到那条解雇记录——因为你的读在老板的写完成之后才开始。逻辑时钟系统给不了这个保证，因为"老板打电话"这条因果通道在系统外部，系统看不见；只有真实物理时间戳能罩住它。

### 3.2.2 时间戳分配的两条不变式

外部一致性靠给每个读写事务分配一个提交时间戳 s，并让 s 满足两条不变式（论文称 start 与 commit wait）：

```
不变式 Start：       s ≥ TT.now().latest   （在收到 commit 请求后计算，取当时区间上界）
不变式 Commit Wait： 提交对外可见前，必须等到 TT.after(s) 为真（即 s < TT.now().earliest）
```

Start 不变式保证时间戳"不太小"：s 取自区间上界，所以 s 不会小于此刻任何已经发生完的事情的真实时刻。Commit Wait 不变式保证时间戳"不太大且已成过去"：等到 s 确定落入过去，才让事务生效。这两条合起来把 s 精确地锚在事务真实存续期内，并保证"提交完成"这个事件的真实时刻 ≥ s。这里没有任何新机制，就是 §3.1.5 那套动作的形式化——但把它写成不变式，是为了下一节能机械地证明外部序。

### 3.2.3 为什么 commit-wait 就能保证外部序（直觉论证）

要证的目标：若 T1 在真实时间先于 T2 开始（记 T1 提交完成的真实时刻 = e1_commit，T2 开始的真实时刻 = e2_start，前提是 e1_commit < e2_start），则 s1 < s2。

链条是这样走的（每一步都由不变式或 TrueTime 保证支撑）：

```
s1  ≤  e1_commit         ── 由 Commit Wait：提交完成时真实时间已 ≥ s1
    <  e2_start          ── 前提：T1 提交完成先于 T2 开始（真实时间）
    ≤  s2                ── 由 Start：T2 的 s2 = 收到请求时的 TT.now().latest ≥ 那一刻真实时间 ≥ e2_start
所以 s1 < s2。
```

commit-wait 逼着 T1 "把它的时间戳 s1 熬成板上钉钉的过去"才敢对外说提交成功；而 T2 后开始时，它取的时间戳 s2 一定不小于它开始那一刻的真实时间，而那一刻又晚于 T1 提交完成。于是 s1 被压在过去、s2 被顶在更晚的现在，中间还隔着"T1 提交完成→T2 开始"这段真实时间，两者不可能相等或颠倒。关键领悟：如果没有 commit-wait，T1 可能盖了个偏大的时间戳就立刻返回，而 T2 恰好盖了个偏小的时间戳，顺序就乱了——commit-wait 花掉的那 2ε 等待，买的正是"时间戳顺序 = 真实时间顺序"这个保证。这也解释了为什么强一致要付延迟代价：外部一致性不是免费的，代价就是每个写事务多等约 2ε。

### 3.2.4 只读事务与快照读

Spanner 的只读事务（read-only transaction）是**无锁**的，不参与 2PC、不阻塞写事务，代价极低。做法是给整个只读事务分配一个读时间戳 s_read，然后在该时间戳对应的**快照**上读——所有分片都返回"截至 s_read 时刻已提交"的版本。因为数据是多版本（MVCC）存储的，读某个时间戳的快照不会与并发写冲突。

快照读之所以能既强一致又高效，靠的是 §3.2.1–3.2.3 建立的时间戳全局有序：既然所有读写事务的提交时间戳都尊重真实时间序，那么"读时间戳 s_read 的快照"就是一个定义良好、全局一致的截面。对一个只想读当前一致状态的只读事务，Spanner 可取 s_read = TT.now().latest，保证读到"此刻之前所有已提交事务"的效果；若客户端能容忍稍旧的数据，也可指定一个更小的 s_read 来读历史快照（bounded-staleness / exact-staleness 读），换取更低延迟和更多可服务副本。易错点：只读事务不加锁不等于"弱一致"——它依然满足外部一致性，因为读时间戳被同一套 TrueTime 定序规则约束。初学者常混淆"无锁 = 脏读"，这里恰相反：无锁靠的是多版本 + 全局有序时间戳，读到的是干净的一致快照。

### 3.2.5 safe time：副本何时能安全服务某时间戳的读

一个只读/快照读可以由 Paxos 组里**任意一个足够新的副本**来服务，不必去找 leader。判据是每个副本维护的 **safe time t_safe**：副本能安全地服务时间戳 t 的读，当且仅当 t ≤ t_safe，意思是"截至 t 时刻的所有写，这个副本都已经确定地拿到、不会再有更小时间戳的写插进来"。

```
t_safe = min( t_safe_Paxos , t_safe_TM )
  t_safe_Paxos：该副本已应用的最高 Paxos 写的时间戳（这之前的写都定稿了）
  t_safe_TM   ：受未决 2PC 事务约束——存在 prepared 但未 commit 的分布式事务时，
                 其可能的提交时间戳会把 t_safe 往回压，避免读到"将要提交但时间戳更小"的写
```

safe time 的意义是把"强一致读"从 leader 卸载到副本，从而**就近读、抗单点、提吞吐**——用户在东京，就让东京的副本服务读，只要该副本的 t_safe 追上了请求的读时间戳。直觉：副本要敢说"时间戳 t 的快照我这儿是完整的"，就必须确信 t 之前不会再冒出新的写；t_safe 就是这个"保证不再有更早的写插入"的水位线。t_safe_TM 那一项容易被忽略却很关键——一个分布式事务 prepare 了但还没 commit 时，它未来会盖一个提交时间戳，如果副本贸然服务一个更大的读时间戳，就可能漏掉这个即将提交的写，所以未决 2PC 会把 safe time 压住，等它 commit/abort 才放行。这体现了 2PC 与快照读的耦合。

### 3.2.6 外部一致性 vs 线性一致/可串行化的关系

三个概念要分清。**可串行化**是隔离性概念，只要求并发事务的结果等价于某个串行顺序，不管这个顺序是否尊重真实时间。**线性一致**是一致性概念，针对单对象操作，要求操作看起来在其调用与返回之间的某一刻原子发生，且尊重真实时间先后。**外部一致性（= strict serializability）** 是二者的合体：既可串行化（事务级隔离），又要求那个串行顺序尊重真实时间（像线性一致那样）。

可串行化管"像串行"，线性一致管"尊重实时且单对象原子"，外部一致性 = 可串行化 + 尊重实时（事务级）。为什么 Spanner 要追到这么强？因为跨会话的因果（老板打电话那种系统外通道）只有"尊重真实时间"才能覆盖，而普通可串行化会被这类外部因果打脸。分账提醒：线性一致的完整定义与证明归 L5-01 大主题5，本报告只借它说明外部一致性的"尊重实时"这一面来自哪里；可串行化/隔离级别的谱系归数据库课与 L5-01 大主题7。冲突/措辞差异：不同文献对 "external consistency" 与 "strict serializability" 是否完全等同偶有细微措辞差别（Spanner 论文用 external consistency 并自述等价于 linearizability 的事务推广；学界多用 strict serializability），语义实质一致，本报告按论文口径记为等价，差异点在此标注。

## 3.3 2PC over Paxos

### 3.3.1 分层组合：Paxos 组做参与者、2PC 做跨组

Spanner 把数据切成很多分片，每个分片由一个 **Paxos 组**（一组分布在不同地域的副本）复制维护，组内用 Paxos 选出 leader、复制写日志。当一个读写事务只落在单个分片上时，走组内 Paxos 即可；当事务**跨多个分片（跨多个 Paxos 组）** 时，Spanner 在这些 Paxos 组之上再叠一层**两阶段提交（2PC）**来保证跨组原子性。

```
跨组事务的分层结构：

        ┌─────────── 2PC（跨组原子提交）───────────┐
        │                                          │
   [Paxos 组 A]        [Paxos 组 B]        [Paxos 组 C]
   leader=参与者      leader=参与者      leader=协调者+参与者
   ↕ Paxos 复制        ↕ Paxos 复制        ↕ Paxos 复制
   副本 副本 副本       副本 副本 副本       副本 副本 副本
   (跨地域)            (跨地域)            (跨地域)
```

关键在"2PC 的每个参与者不是一台机器，而是一个 Paxos 组的 leader"。传统教科书 2PC 的参与者是单机，单机崩了这个参与者就没了、协调者也可能崩得整个事务卡死。Spanner 把每个角色都换成 Paxos 组：参与者的状态（是否已 prepare、锁、日志）通过组内 Paxos 复制到多个副本，协调者的决定（commit/abort）也写进它所在 Paxos 组的复制日志。初学者可以这样搭积木理解：下层 Paxos 解决"单个分片如何高可用地存一份写"，上层 2PC 解决"多个分片如何原子地一起提交"，两层正交组合。

### 3.3.2 为什么这样能缓解 2PC 的阻塞问题

传统 2PC 的死穴（详见 L5-01 大主题7）：协调者在参与者已投 Yes（进入 prepared/in-doubt 状态）之后、还没广播最终决定之前崩溃，参与者就卡在"不敢提交也不敢中止"的锁持有状态，直到协调者恢复——这就是阻塞。Spanner 缓解它的办法不是改 2PC 协议本身，而是**让协调者和参与者都不再是会永久消失的单点**。

因为协调者的 commit/abort 决定一旦写进它的 Paxos 组日志、被多数派确认，就是持久且高可用的：即使原 leader 崩了，Paxos 组会选出新 leader，新 leader 从复制日志里读到"这个事务已决定 commit"，继续把决定推给参与者。同理参与者 leader 崩了，新 leader 从日志恢复出"我已 prepared、持有这些锁"，接着响应协调者。于是原来"单机崩溃→永久卡死"退化成"leader 崩溃→秒级重选→接着干"。要点/分账：这**缓解**而非"消灭"了原子提交的阻塞语义——2PC 仍要求所有参与组都回应，若某个 Paxos 组整组失去多数派（比如同时挂掉过半副本），该参与者依旧不可用、事务仍会等待；Spanner 换来的是"单点故障不再致命"，而不是"任意故障都不阻塞"。原子提交问题的理论下界（为什么无法完全非阻塞）归 L5-01 大主题7，本报告不重证。

### 3.3.3 读写事务的完整生命周期

把 2PL（隔离）、2PC（跨组原子）、commit-wait（外部一致）三者串起来，一个跨组读写事务的时间线如下：

```
读写事务生命周期（客户端驱动，buffer 写到提交时才下发）：

1. 事务开始，客户端向各相关 Paxos 组 leader 发读请求
   → 读走 2PL：读操作在各参与组 leader 上加读锁，读最新已提交数据
   → 写操作先在客户端本地缓冲（buffered），期间对外不可见
2. 客户端发起提交：选一个参与组 leader 作为【协调者】，其余为【参与者】
3. Prepare 阶段（2PC 第一阶段）：
   - 客户端把缓冲的写发给各参与者 leader
   - 每个参与者 leader：加写锁 → 选一个 prepare 时间戳 → 把 prepare 记录经 Paxos 复制到本组多数派 → 回 Yes/No 给协调者
4. 协调者定时间戳 s：
   - s ≥ 所有参与者的 prepare 时间戳
   - s ≥ 协调者收到 commit 请求时的 TT.now().latest   （Start 不变式）
   - s ≥ 该协调者已分配过的任何时间戳
5. Commit 阶段（2PC 第二阶段）：协调者把"commit @ s"经 Paxos 复制到本组日志（决定持久）
6. Commit Wait：协调者等待 TT.after(s) 为真（≈ 2ε）      ← 外部一致性在此买单
7. 协调者向客户端回成功，并通知各参与者 apply commit @ s、释放锁
   参与者把 commit @ s 经各自 Paxos 复制生效
```

这条时间线把全篇拼齐了：第 1、3 步的锁是隔离性（2PL）；第 3–5、7 步的 prepare/commit + Paxos 复制是跨组原子性 + 高可用（2PC over Paxos）；第 4、6 步的时间戳规则与等待是外部一致性（TrueTime + commit-wait）。易错点：commit-wait（第 6 步）发生在协调者已经把决定复制持久之后、回客户端之前——它不影响原子性，只服务外部序；即使跳过它，事务照样原子提交，但会丢外部一致性。另一个易错点：写在提交前一直缓冲在客户端，所以 prepare 阶段才真正把写下发加锁，这是理解"为什么读写事务的写锁在提交时才集中获取"的关键。

### 3.3.4 参与者领导者与协调者领导者的角色

在一次跨组事务里，每个参与 Paxos 组的 **leader 副本**担当该组的"参与者"角色；客户端从这些 leader 里挑一个兼任"协调者"。协调者既是它自己那组的参与者，又额外负责驱动 2PC 全流程、汇总投票、定提交时间戳、广播决定。

之所以让 leader 而不是任意副本充当这些角色，是因为 leader 是 Paxos 组里唯一有权发起写复制、持有锁状态的副本——把 2PC 的读写与加锁落在 leader 上，才能和组内 Paxos 复制无缝衔接。协调者与参与者的状态都不是它私有的内存态，而是各自 Paxos 组的复制状态：协调者把"事务已决定 commit @ s"写进自己组的日志，参与者把"我已 prepared"写进自己组的日志——这正是 §3.3.2 抗单点的物质基础。初学者容易把"协调者"想成一台独立的中央服务器，实际它就是众多参与组之一的 leader，多戴了一顶帽子，且这顶帽子的关键状态是被复制的。

### 3.3.5 与单机/理论 2PC 的分账

本节明确边界，避免与 L5-01 重复。**理论层面**——2PC 的两阶段协议逻辑、prepared/in-doubt 状态、原子提交问题不变式（AC-1 一致、AC-2 一票否决、AC-3 中止有效、AC-4 弱终止）、为什么 2PC 会阻塞、3PC 为何实践不用——这些归 L5-01 大主题7，本报告只引用不重证。**工程组合层面**——把参与者从单机换成 Paxos 组、把协调者决定 Paxos 复制以抗单点、与 2PL/commit-wait/TrueTime 如何拼装成完整事务——这是本课 C3 的落点。

L5-01 回答"2PC 为什么对、为什么会卡"；本报告回答"怎么把会卡的 2PC 做得基本不卡、且能跑在全球规模上"。这也解释了为什么现代系统很少抛弃 2PC 另起炉灶——2PC 的原子提交语义是需要的，需要修的只是它的单点脆弱性，而"把角色换成共识复制组"恰好补上这一刀。

## 3.4 分片、目录与数据放置

### 3.4.1 数据模型：半关系表与 INTERLEAVE 层次

Spanner 对上层暴露的是**半关系（semi-relational）数据模型**：类似关系数据库的有模式（schematized）表，行有主键，支持一种类 SQL 的查询语言；但它要求每张表必须声明主键，并允许用 **INTERLEAVE IN** 把子表的行按主键前缀**物理地穿插存放在父表行附近**，形成表间层次（hierarchy）。

这个层次不是花样，而是数据放置的抓手。举例：Users 表以 uid 为主键，Albums 表声明 INTERLEAVE IN PARENT Users，主键是 (uid, album_id)——于是某个用户的所有相册行会和该用户行**存在一起**。好处是同一用户的相关数据落在同一分片、同一 Paxos 组，读"这个用户及其相册"不用跨组、不触发 2PC，性能和一致性都更好。初学者可以把 INTERLEAVE 理解为"预先把经常一起访问的父子行绑在一块存"，本质是用数据布局换取"多数事务落单组"。这也和 §3.3 呼应：跨组才需要 2PC over Paxos 的昂贵路径，把相关数据 interleave 到一起就是尽量避免走那条路径。

### 3.4.2 directory：数据放置的最小单元

Spanner 里**数据放置的基本单元叫 directory（目录，也称 bucket）**：一个 directory 是一组**共享同一主键前缀**的连续行的集合（正是由 INTERLEAVE 层次界定的那种"一族相关行"）。directory 是 Spanner 中**能被独立指定地理放置、并作为数据迁移最小单位**的东西——同一个 directory 的所有数据一定在同一个 Paxos 组里。

要抓住的层级关系：行 → directory（一族共前缀的行）→ Paxos 组（承载若干 directory）。为什么放置单元是 directory 而不是单行或整张表？单行太细、迁移和管理开销大；整张表太粗、无法按用户/地域细粒度放置。directory 这个粒度刚好：它天然对应"一族经常一起访问、且往往属于同一用户/租户"的数据，既是局部性单元又是放置单元。应用因此能表达"把欧洲用户的 directory 放欧洲、把美洲用户的放美洲"这类需求。易错点：Spanner 的 directory 不是文件系统目录，只是一个借来的名字，指"一组共主键前缀的行"；也不要把它和 tablet 混为一谈（见下条）。

### 3.4.3 tablet 与 spanserver

物理上，每台服务器进程叫 **spanserver**，它管理一批 **tablet**（借自 Bigtable 的术语）；tablet 是数据在磁盘/Colossus 上的存储容器，其上跑一个 Paxos 状态机来复制。**与 Bigtable 不同的是，Spanner 的一个 tablet 可以装多个 directory（一袋 directory 片段），而不要求 tablet 内的行按主键连续**——这正是为了让"按 directory 放置数据"更灵活。

层级再补齐：spanserver（进程/机器）→ 管多个 tablet（存储容器 + Paxos）→ 每个 tablet 承载多个 directory → directory 由共前缀的行组成。Paxos 组是在 tablet 这一层组织复制的（一个 tablet 的多个副本组成一个 Paxos 组，分布在不同地域）。初学者只需记住两条链：**放置/迁移看 directory，存储/复制看 tablet**。为什么要允许一个 tablet 装多个 directory？因为若强制 tablet=连续主键区间（像 Bigtable），就没法把"分散在主键空间各处、但都属于欧洲用户"的 directory 灵活地凑到同一组去，放置自由度会受限。

### 3.4.4 movedir：在 Paxos 组间搬迁目录

Spanner 有一个后台任务 **movedir**，负责在 Paxos 组之间**搬迁 directory**——用于两类目的：给 Paxos 组减负均衡负载，或把某个 directory 移到离频繁访问它的用户更近的组。movedir 不是一个事务，而是一个**后台的、可与前台读写并发**的过程：它先在后台把 directory 的大部分数据搬到目标组，最后用一个小事务原子地切换这批数据的归属并搬迁剩余的少量增量。

设计要点是"搬迁必须不阻塞正常读写"。如果搬一个大 directory 要锁住它整段时间，用户就会感到长时间卡顿；所以 movedir 把工作拆成"大批量后台拷贝（可并发）+ 尾部小事务切换（短暂原子）"两段。直觉类比：搬家时先把绝大多数箱子慢慢运到新居（旧居照常住），最后只用极短时间把最后几件和钥匙一起交接。这样放置策略（§3.4.5）能在系统运行中动态生效——用户迁移地域、负载热点变化时，数据能跟着走，而这一切对上层事务基本透明。时效/分账：movedir 属实现机制，具体触发策略与实现随内部版本演进（论文为 2012 口径），不作定论。

### 3.4.5 就近放置与副本配置

Spanner 让应用通过对 directory 打**放置标签 / 配置副本策略**来控制两件事：**副本放在哪些数据中心（地域）** 以及**用多少个副本、什么类型**（如投票副本 vs 只读副本），从而在延迟、吞吐、可用性、成本之间做权衡。放置以 directory 为粒度，配合 movedir 可在运行时调整。

为什么放置这么重要？因为地理距离直接决定延迟：把副本放得离用户近，读写往返就短；把投票副本分散到多个独立故障域，能扛数据中心级故障。典型权衡：副本铺得越广、越分散，可用性和就近读越好，但写要跨更远的 Paxos 多数派、延迟越高；副本集中，写快但抗灾差。外部一致性 + 就近读（§3.2.5 的 safe time 让副本能服务快照读）合起来，才使"全球用户都能低延迟读到强一致数据"成为可能——读可以就近由本地副本服务，写付出跨地域共识 + commit-wait 的代价。初学者串起全篇：TrueTime 给全局序、2PC-over-Paxos 给跨分片原子高可用、directory/放置给地理局部性，三者合起来就是"全球规模的强一致数据库"。时效：具体可选放置策略/副本类型（如 Cloud Spanner 的多区域配置）⚙演进快，随商用产品演进，具体现行选项「待核」，勿据 2012 论文当当前产品规格。
