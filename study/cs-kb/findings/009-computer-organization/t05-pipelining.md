## 5.1 五级流水与段寄存器

### 5.1.1 为什么要流水线：从单周期到吞吐

流水线（pipelining）是一种实现技术：把一条指令的执行切成若干阶段，让多条指令的不同阶段在同一时刻重叠进行，就像工厂流水线上多件产品同时处在不同工位。它不缩短单条指令走完全程的时间（延迟 latency 不变，甚至略增），而是提高单位时间完成的指令数（吞吐率 throughput）。

单周期实现里，时钟周期必须等于最慢那条指令走完全程的时间（大主题4 §4.5 的结论），大量硬件在每个周期里大部分时间闲着。流水线把这条长路切成 5 段，让 5 条指令各占一段并行推进，理想情况下每个时钟周期就能"完工"一条指令。

一个经典直觉是"洗衣店类比"（P&H COD 用它开篇）：洗一批衣服要经过洗、烘、叠、收四道工序。非流水做法是洗完一批全部四道再开始下一批；流水做法是第一批进烘干机时，第二批就进洗衣机。四道工序、四批衣服重叠起来，总时间大幅缩短——但每一批衣服自己走完四道的时间没变。这就是流水线的本质：**用重叠换吞吐，不是让单件更快**。

初学者常以为"流水线让每条指令更快了"。恰恰相反，单条指令的延迟通常还略微变长（多了段寄存器的锁存开销、且周期要按最慢段而非最快段取整）。变快的是"程序整体"，因为大量指令重叠执行，平均每条指令占用的时间接近一个（短）时钟周期。这正对应八大伟大思想里的"借流水线提升性能"。

### 5.1.2 RISC-V 五级划分 IF / ID / EX / MEM / WB

P&H《COD》把 RISC-V 指令执行切成五个阶段，每段大致对应单周期数据通路的一段硬件：

```
IF  取指  Instruction Fetch     ：按 PC 从指令存储器取指令，PC ← PC+4
ID  译码  Instruction Decode    ：译码指令、读寄存器堆、生成立即数
EX  执行  Execute               ：ALU 运算；对访存指令算有效地址；对分支算目标/比较
MEM 访存  Memory access         ：load 从数据存储器读、store 写；其余指令空过
WB  写回  Write Back            ：把结果写回寄存器堆
```

这五段的划分让"取指令的硬件、算数的 ALU、访存的存储器、写寄存器的端口"各自独立，从而能在同一时刻分别服务处在不同阶段的五条指令。RISC-V 之所以能切得这么整齐，是因为它是精简（load-store）指令集：指令定长、格式规整、只有 load/store 访存，天生适合切段。

为什么恰好是 5 段而不是 3 段或 10 段？这是"关键路径切分"与"开销/收益"的折中——段越多，每段越短、时钟越快，但段寄存器开销、冒险惩罚、分支代价都随之上升。5 级是经典教学模型（也是早期 MIPS/RISC 商用流水的实际选择）。现代高性能 CPU 流水级数可达十几到二十级，但那属于 L5-05 的范畴，本报告只讲 5 级。

多来源一致性：H&H《DDCA》ch7 的五段命名为 Fetch / Decode / Execute / Memory / Writeback，H&P《QA》附录 C 命名为 IF / ID / EX / MEM / WB，与 COD 完全一致，只是英文全称写法略有出入，无实质分歧。

### 5.1.3 流水线寄存器（段寄存器）

要让五条指令的信息互不串台，必须在每两段之间插一排寄存器，把上一段算出的结果、以及这条指令后续还要用到的控制信号，整拍锁存下来传给下一段。这些寄存器叫流水线寄存器（pipeline register）或段间寄存器（segment register），在 COD 中按其分隔的两段命名：

```
IF/ID   ｜   ID/EX   ｜   EX/MEM   ｜   MEM/WB
```

段寄存器是流水线能成立的物理基础。每个时钟上升沿，所有段寄存器同时把本段结果锁存、送入下一段——于是"一条指令在流水线里前进一格"这件事，物理上就是"它的信息从一个段寄存器搬到下一个段寄存器"。凡是这条指令后面阶段还要用的东西（数据、目的寄存器号、控制信号），都必须一路随段寄存器往下带。

以 `add x5, x6, x7` 为例，它在 ID 段读出 x6、x7 的值，这两个值经 ID/EX 寄存器带到 EX 段做加法；加法结果和"目的寄存器号 x5"经 EX/MEM、MEM/WB 一路带到 WB 段，才知道该把结果写回哪里。如果不带目的寄存器号，等到 WB 段就"忘了"要写谁了。

段寄存器不是给程序员用的通用寄存器（x0–x31），程序员完全看不见它们；它们是微架构内部的隐藏锁存器，属于"实现"而非"ISA"。易错点二：PC 也可视为流水线最前的寄存器，但它较特殊（要支持顺序 +4 与分支改流），入门时先记住"每段之间都夹一排看不见的寄存器"即可。

### 5.1.4 时序图、吞吐与加速比（含本机实证）

流水线的执行常画成"时空图"（space-time diagram）：横轴时钟周期、纵轴指令，每条指令的 5 段沿对角线排开：

```
指令\周期     1    2    3    4    5    6    7    8    9
i1(add)      IF   ID   EX  MEM   WB
i2(sub)           IF   ID   EX  MEM   WB
i3(or)                 IF   ID   EX  MEM   WB
i4(and)                     IF   ID   EX  MEM   WB
i5(xor)                          IF   ID   EX  MEM   WB
```

第 5 拍起进入"稳态"：每拍都有一条指令在 WB 段完工。理想情况下（各段耗时相等、无冒险、无填充损耗），流水线相对单周期的加速比等于流水级数：

```
理想加速比 = 流水级数（本例 = 5）
```

更精确地，考虑"填充/排空"开销：执行 n 条指令、k 级流水、每级 1 拍，则总拍数为

```
总周期数 = n + (k − 1)
```

其中 (k − 1) 是流水线灌满前（第一条指令走到 WB 之前）的启动开销。当 n 远大于 k 时，(k − 1) 可忽略，平均每条指令趋近 1 拍，有效 CPI → 1。

流水线不改变单条指令的 CPI 走完全程仍是 5 拍，但让稳态吞吐达到"每拍 1 条"，即有效 CPI 逼近 1（这正是大主题4 §4.5 提出流水化时许下的目标）。冒险会让有效 CPI 略大于 1，后续 5.2–5.5 逐一处理。

本机实证（Python 逐拍模拟，纯逻辑模型，不需 RISC-V 硬件）：验证 5 条独立指令灌满流水线的时空图与 n+(k−1) 公式。环境串见抬头（Linux 6.18.5 x86_64，Python 3.11.15）。可复现脚本核心逻辑与真实输出如下：

```
$ python3 pipe_sim.py    # 段序 IF ID EX MEM WB；段进入周期 = IF周期 + 段序号
Case A: 5 independent instrs (fill the pipe, forwarding not needed)
cyc:         1   2   3   4   5   6   7   8   9
add x5,x6,x7   IF  ID  EX MEM  WB
sub x8,x9,x10       IF  ID  EX MEM  WB
or  x11,x12,x13           IF  ID  EX MEM  WB
and x14,x15,x16               IF  ID  EX MEM  WB
xor x17,x18,x19                   IF  ID  EX MEM  WB
instructions            = 5
total cycles            = 9
ideal (no stall) cycles = 9
bubbles injected        = 0
```

实测 total cycles = 9 = n + (k−1) = 5 + (5−1)，与公式一致，0 气泡，坐实 §5.1.4 的稳态吞吐结论。（脚本仅在仓库外 scratchpad 运行，不入库；完整脚本逻辑见 5.4.3 复用同一模拟器。）

## 5.2 结构冒险

### 5.2.1 什么是结构冒险

把指令重叠起来后，会出现三类"冒险"（hazard）——即"下一拍无法按计划推进下一条指令"的情形。第一类是结构冒险（structural hazard）：两条处在不同阶段的指令，在同一拍要用同一个硬件资源，而该资源只有一份，抢不过来。

结构冒险是"资源不够分"造成的。它不来自指令间的数据关系，纯粹是硬件配置问题——同一拍里，多个阶段争用唯一的一份部件。

回到洗衣店类比，如果整个店只有一台"洗+烘"二合一机器，那么第二批衣服想洗时，第一批还占着这台机器烘干，就冲突了。硬件也一样：一份资源在一拍里只能服务一个阶段。

### 5.2.2 两个典型场景与消除办法

单端口统一存储器。若指令和数据放在同一块只有一个访问端口的存储器里，那么每拍 IF 段要取指令、同一拍可能有一条更早的 load/store 在 MEM 段访问数据——两者同时访存，一个端口服务不过来。

```
同一拍冲突：  i1: … MEM(访数据)
             i4: IF (取指令)     ← 两者都要访存储器，单端口冲突
```

核心消除办法：把指令存储器和数据存储器分开（各自独立端口），即哈佛结构（Harvard architecture）思路；在真实机器上体现为一级缓存拆成独立的指令缓存（I-cache）和数据缓存（D-cache）。这样 IF 走 I-cache、MEM 走 D-cache，互不争用。P&H 的教学流水线正是默认"指令与数据存储器分离"，从而在设计上直接消除了这个结构冒险。

寄存器堆同拍读写。同一拍里，一条较早的指令在 WB 段要写寄存器堆，一条较晚的指令在 ID 段要读寄存器堆。若寄存器堆读写抢端口也会冲突。

核心消除办法：让寄存器堆"前半拍写、后半拍读"（write in first half, read in second half of the clock cycle）。COD 用这个约定使同一拍的写和读错开，既消除了这个结构冒险，又顺带让"上一指令刚写的值本拍就能被读到"——这对后面数据冒险的处理是有利的副产品。

结构冒险在设计良好的定长精简 ISA 五级流水里，通常靠"多配一份资源/分离存储器/读写错峰"在设计阶段就消灭了，运行时一般看不到它——这也是 RISC 相较复杂变长指令的优势之一。易错点：别把结构冒险和数据冒险混淆——结构冒险是"资源不够"（和指令算什么无关），数据冒险（5.3）是"数据还没算好"（和指令间的依赖有关）。两者成因不同、解法不同。

多来源分歧（显式记录）：H&P《QA》附录 C 讨论的经典流水线里，若刻意用单存储器端口或单写端口，会保留结构冒险并用停顿解决，作为"资源受限"的教学案例；而 P&H《COD》的教学数据通路默认分离指令/数据存储器、寄存器堆读写错峰，从设计上不引入这些结构冒险。两者不矛盾：是"是否愿意为消除结构冒险多花硬件"的设计选择差异，QA 展示"省硬件则需停顿"，COD 展示"多花硬件则无冒险"。

#### 来源与时效
- 锚点：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.5（Hazards 之 Structural Hazards：分离指令/数据存储器）与 §4.7（寄存器堆前半拍写、后半拍读的约定）；核实 2026-07-26。
- 佐证：H&P《QA》6th ed, 2017, 附录 C（单端口资源导致的结构冒险与停顿）；H&H《DDCA》RISC-V ed, 2021, ch7；Berkeley CS61C。

## 5.3 数据冒险与转发

### 5.3.1 数据相关与 RAW 冒险

数据冒险（data hazard）：一条指令需要用到前一条（或前几条）指令的计算结果，但那个结果还没写回寄存器堆，导致它读到旧值。最常见的是写后读（Read After Write, RAW）相关——真数据相关（true dependence）。

在顺序 5 级流水里，结果要到 WB 段（第 5 拍）才写进寄存器堆，而后一条指令在 ID 段（早于前者 WB）就要读寄存器——时间对不上，就会读到过时的旧值。最小例子（COD 经典）：

```
指令\周期     1    2    3    4    5    6
sub x2,x1,x3  IF   ID   EX  MEM   WB          ← x2 到第5拍WB才写入
and x12,x2,x5      IF   ID*  EX  MEM   WB     ← 第3拍就想读x2，但x2尚未写回
```

`and` 在第 3 拍的 ID 想读 x2，而 `sub` 要到第 5 拍才把 x2 写回——若不处理，`and` 会读到 x2 的旧值，结果算错。

这里为什么只提 RAW？在这种"按序读（ID 段）、按序写（WB 段）"的顺序流水里，写后写（WAW）和读后写（WAR）这两类"名字相关"不会引发冒险——因为所有指令都在 WB 按原顺序写、在 ID 按原顺序读，先后关系天然保持。WAR/WAW 只有在乱序执行时才成为问题，那归 L5-05。入门阶段：顺序 5 级流水只需对付 RAW。

### 5.3.2 转发（旁路）：不等写回，直接抄近路

核心解法叫转发（forwarding）或旁路（bypassing）：注意到 `sub` 的结果其实在第 3 拍末（EX 段算完）就已经存在于 EX/MEM 段寄存器里了，只是还没"正式写回寄存器堆"。既然值已经算出来，就用一条额外的数据通路，把它直接从段寄存器"抄近路"送到需要它的那条指令的 EX 段输入端，不必干等到 WB。

转发把"结果产生"到"结果可用"的等待时间压缩掉。对 ALU→ALU 这类相关，转发能完全消除停顿——结果在生产者的 EX 末就绪，正好赶上消费者下一拍的 EX 使用。加上寄存器堆"前半拍写后半拍读"的约定，隔两拍的相关甚至能直接靠寄存器堆读到，无需专门转发。

想象生产者刚把零件做好放在传送带尽头（EX/MEM 寄存器），消费者不用等它入库（WB 写回寄存器堆）再领用，直接从传送带上取走。转发就是这条"传送带旁路"。

### 5.3.3 转发路径与转发条件

转发单元（forwarding unit）比较正在 EX 段执行的指令要读的源寄存器，与"已经算完、正待写回"的前面两条指令的目的寄存器，若匹配就把结果旁路过来。COD 给出两条转发路径：

```
EX/MEM → EX   ：前一条指令（距离1）的EX结果，转发给当前指令的EX输入
MEM/WB → EX   ：前两条指令（距离2）的结果（或前一条load的MEM数据），转发给当前EX输入
```

转发条件（以转发给 EX 段 ALU 的某个源操作数为例，简化表述）：

```
若 EX/MEM.RegWrite 且 EX/MEM.rd ≠ x0 且 EX/MEM.rd == ID/EX.rs  → 从 EX/MEM 转发
否则若 MEM/WB.RegWrite 且 MEM/WB.rd ≠ x0 且 MEM/WB.rd == ID/EX.rs → 从 MEM/WB 转发
```

优先选"最近"的那条（EX/MEM 距离 1 优先于 MEM/WB 距离 2），因为最近的才是最新值；且要排除写 x0 的情况（x0 恒为 0，不是真写）。满足条件时，ALU 的输入多路选择器就选转发来的值而非从寄存器堆读来的旧值。

本机实证（同一模拟器 Case B）：三条指令连续依赖 `sub` 写的 x2，全部靠 ALU→ALU 转发覆盖，0 气泡：

```
Case B: RAW deps, ALU->ALU forwarding covers them (0 bubbles)
cyc:         1   2   3   4   5   6   7   8
sub x2,x1,x3   IF  ID  EX MEM  WB
and x12,x2,x5       IF  ID  EX MEM  WB
or  x13,x6,x2           IF  ID  EX MEM  WB
add x14,x2,x2               IF  ID  EX MEM  WB
bubbles injected        = 0
```

实测 0 气泡，坐实"ALU 类 RAW 相关可由转发完全消除、不必停顿"。

转发不是万能的——它只能把"已经算出来的值"提前送达；如果需要的值这一拍还根本没算出来（如 load 的数据要到 MEM 段末才就绪，却被紧邻的下一条指令在 EX 段初就要用），转发就"来不及"，必须停顿一拍。这正是 5.4 的 load-use 冒险。

多来源一致性：COD §4.7、H&H《DDCA》ch7、H&P《QA》附录 C 都给出 EX/MEM→EX 与 MEM/WB→EX 两条转发路径，命名与逻辑一致（QA 称之为 bypassing/forwarding，路径同）。三源无冲突。

#### 来源与时效
- 锚点：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.7 *Data Hazards: Forwarding versus Stalling*（RAW 相关、EX/MEM 与 MEM/WB 转发路径、转发条件、写 x0 排除、寄存器堆前写后读）；核实 2026-07-26。
- 佐证：H&H《DDCA》RISC-V ed, 2021, ch7（forwarding/bypass 路径）；H&P《QA》6th ed, 2017, 附录 C（data hazards、bypassing、RAW/WAR/WAW 分类，WAR/WAW 仅乱序才成冒险）；Berkeley CS61C。
- 一致性：三源转发路径（EX/MEM→EX、MEM/WB→EX）与条件一致；"顺序流水只需对付 RAW"为共识，无冲突。
- 本机实证：Python 逐拍模拟 Case B 实测连续 RAW 依赖 0 气泡（scratchpad/pipe_sim.py，Py3.11.15）。
- 待核：转发条件的完整布尔式（含"MEM 阶段亦可转发给后续"的边角情形）本报告只给核心式，未穷举；确切小节号依 COD ch4 编排。

## 5.4 load-use 停顿

### 5.4.1 为什么转发覆盖不了 load-use

load-use 数据冒险（load-use hazard）：一条 load 指令刚从内存取回数据，紧接着的下一条指令就要用这个数据。这是转发唯一覆盖不了的数据冒险。

load 的数据要到 MEM 段末（第 4 拍）才就绪，而紧邻的下一条指令在它的 EX 段初（也是第 4 拍）就要用这个值——生产时刻不早于消费时刻，转发"抄近路"也来不及，因为值这一拍还没生产出来。必须让消费指令停顿（stall）一拍，等 load 的数据出炉，再靠 MEM/WB→EX 转发补上。时序（COD 经典例）：

```
指令\周期     1    2    3    4    5    6    7
ld  x2,20(x1) IF   ID   EX  MEM   WB              ← x2 数据到第4拍MEM末才就绪
and x4,x2,x5       IF   ID  (气泡) EX  MEM   WB    ← 停顿1拍，EX推迟到第5拍，再从MEM/WB转发x2
```

`and` 若不停顿，会在第 4 拍 EX 用 x2，但 x2 此刻正在 load 的 MEM 段"路上"，尚未就绪；停顿一拍后，`and` 的 EX 挪到第 5 拍，此时 x2 已在 MEM/WB 段寄存器里，靠转发送达，恰好赶上。

ALU→ALU 相关中，生产者在 EX 末（第 3 拍）就出结果，消费者第 4 拍 EX 用，生产早于消费一拍，转发够用；而 load→use 中，生产者要晚一段（MEM 末）才出结果，正好和消费者的 EX 撞在同一拍，差这一拍，只能停。

### 5.4.2 冒险检测单元与气泡（bubble）

停顿由冒险检测单元（hazard detection unit）在 ID 段完成。它检测"上一条是 load、且其目的寄存器正是本条要读的源寄存器"这一模式：

```
若 ID/EX.MemRead 且 ( ID/EX.rd == IF/ID.rs1 或 ID/EX.rd == IF/ID.rs2 )
   → 停顿一拍（冻结 PC 与 IF/ID 寄存器，向 ID/EX 注入一个 nop 气泡）
```

停顿的物理实现是"冻结前端 + 注入气泡"——让 PC 和 IF/ID 寄存器这一拍不更新（消费指令原地等一拍），同时把 ID/EX 的控制信号全清零（塞进一个什么都不做的 nop，即气泡 bubble），使流水线后段这一拍空转一格。一次 load-use 冒险恰好插入一个气泡，等效于让有效 CPI 略微升高。

气泡到底是什么？它就是一条"人造 nop 指令"占着一个流水槽向下走，它不写任何寄存器、不访存，纯粹用来"垫一拍"。你可以把它想成流水线里一个空的托盘：占着位置、往下传，但上面没放东西。

### 5.4.3 编译器调度缓解 + 本机实证

load-use 的一拍停顿可由编译器通过指令调度（instruction scheduling）尽量避免——把一条与该 load 无关的有用指令挪到 load 和 use 之间填进那个"延迟槽"，让停顿拍改做有用功。若找不到可挪的独立指令，才退化为真正的气泡。这体现"软硬协同"：硬件保证正确（检测到就停），编译器负责性能（尽量不让它停）。

load-use 停顿在真实程序里相当常见（访存密集代码尤甚），所以"减少 load-use 停顿"是编译器调度和程序优化的重要着力点。易错点一：注意停顿只需 1 拍——因为差的只是"MEM 末 vs EX 初"这一拍；不要误记成停 2 拍或 3 拍。易错点二：只有紧邻 load 的下一条（距离 1）才需停顿；隔一条的（距离 2）已能靠 MEM/WB→EX 转发覆盖，无需停顿。

本机实证（Python 逐拍模拟 Case C，含冒险检测单元逻辑）：模拟器实现了上面 §5.4.2 的 load-use 检测（ID/EX.MemRead 且目的寄存器命中下一条的源），对 COD 经典序列 `ld x2,20(x1); and x4,x2,x5; …` 注入恰好一个气泡。可复现命令与真实输出：

```
$ python3 pipe_sim.py
Case C: load-use hazard (forwarding cannot cover) -> 1 bubble
cyc:         1   2   3   4   5   6   7   8   9
ld  x2,20(x1)   IF  ID  EX MEM  WB
and x4,x2,x5           IF  ID  EX MEM  WB
or  x8,x2,x6               IF  ID  EX MEM  WB
add x9,x4,x2                   IF  ID  EX MEM  WB
  note: 'and x4,x2,x5' -> load-use stall (1 bubble)
instructions            = 4
total cycles            = 9
ideal (no stall) cycles = 8
bubbles injected        = 1
```

实测：紧邻 load 且读 x2 的 `and` 触发停顿，总周期由无停顿的 8 拍升为 9 拍，恰好多 1 个气泡；而隔一条的 `or x8,x2,x6`（距离 2）未触发停顿——与 §5.4 结论、COD 经典例完全吻合。模拟器核心逻辑（供自足复现，仅在 scratchpad 运行、不入库）：

```python
# 5 段流水，段进入周期 = IF周期 + 段序号(IF=0..WB=4)
# load-use 检测：前一条是 load 且其 rd 被本条读到 -> IF 周期后移 1 拍(=1个气泡)
cur = 1
for i, ins in enumerate(prog):
    if_cycle[i] = cur
    cur += 1
    nxt = prog[i+1] if i+1 < len(prog) else None
    if nxt and ins.kind == 'load' and ins.rd not in (None,'x0') and ins.rd in nxt.reads():
        cur += 1   # 注入 1 气泡
# 总周期 = max_i(if_cycle[i] + 4)
```

（说明：本模型以"消费指令 IF 后移一拍"等效表达 1 个气泡的净时序效果——总拍数与气泡数正确；真实硬件是冻结 PC/IF-ID 并向 ID/EX 注 nop，视觉上表现为消费指令的 ID 多停一拍，二者净时序等价。）

#### 来源与时效
- 锚点：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.7（load-use hazard、冒险检测单元 ID/EX.MemRead 条件、注入气泡停顿一拍、编译器调度填延迟）；核实 2026-07-26。
- 佐证：H&H《DDCA》RISC-V ed, 2021, ch7（lw/load use 一拍停顿、stall/bubble）；H&P《QA》6th ed, 2017, 附录 C（load delay/load-use、pipeline stall）；Berkeley CS61C。
- 一致性：三源均给"load-use 恰停 1 拍、由冒险检测单元注气泡、编译器调度缓解"，停顿拍数一致（1 拍），无冲突。
- 本机实证：Python 逐拍模拟 Case C 实测 COD 经典序列注入 1 气泡、总周期 8→9，距离2不停顿（scratchpad/pipe_sim.py，Py3.11.15）。
- 待核：冒险检测单元的完整信号式（含与转发单元的协同边角）本报告给核心条件；确切小节号依 COD ch4 编排。

## 5.5 控制冒险与分支预测入门

### 5.5.1 控制冒险与分支延迟

第三类冒险是控制冒险（control hazard）或分支冒险（branch hazard）：取指是流水线最前一段，每拍都要按 PC 取下一条指令；但遇到条件分支时，"下一条到底该取哪儿"要等分支条件算出来才知道——而这时后面几条指令可能已经被顺序取进流水线了。

分支的方向（taken/not-taken）与目标地址要到流水线中段才确定，但流水线不能停下等它，只能"先猜着继续取指"。若猜错，那些已经进入流水线的错误路径指令必须作废。这就是控制冒险：控制流的不确定性与"每拍都要取指"之间的矛盾。

流水线像一条不能停的传送带，取指段每拍都得往上放一件"下一条指令"。分支就像岔路口，但要走哪条岔路的信号灯要过几拍才亮——传送带不能空等，只能先赌一条路放上去，等信号灯亮了发现赌错，就把错放的几件拿下来重放。

### 5.5.2 冲刷（flush）与分支惩罚

若分支预测错误，已进入流水线的错误指令必须被冲刷（flush）——把它们变成气泡（清零其控制信号），使其不改变任何寄存器/内存状态，如同没执行过。冲刷掉的拍数就是分支惩罚（branch penalty）。

分支惩罚 = 从取指到分支解决之间已错误取入的指令数。惩罚拍数取决于"分支在第几段被解决"：

```
分支在 MEM 段解决（朴素实现）：惩罚约 3 拍
分支提前到 ID 段解决（COD 优化：ID 段加比较器与专用加法器）：惩罚降为 1 拍
```

核心结论（COD 的做法）：P&H 教学流水线专门把分支的比较与目标地址计算硬件前移到 ID 段，使分支在第 2 拍就解决，预测错误只需冲刷 1 条指令（惩罚 1 拍）。这是"多花一点硬件（ID 段加比较器/加法器）换更小分支惩罚"的典型权衡。

冲刷和 load-use 的气泡机制相通——都是把某些流水槽清成 nop。区别在于：load-use 是"预防性停顿"（还没错，先等），控制冒险的冲刷是"纠错性作废"（已经错取，事后清掉）。

### 5.5.3 静态预测与延迟槽（ISA 相关差异）

最简单的应对是静态分支预测（static prediction）：编译期/设计期固定一种猜法，运行时不变。最常见的是预测不跳转（predict not-taken / predict untaken）——假设分支不成立，继续顺序取指；若最终真的不跳，零惩罚；若跳了，冲刷已取的错误指令。

静态预测简单、无需硬件历史表，但准确率受限于程序行为（循环回边这类"几乎总跳"的分支上，"预测不跳"会频繁猜错）。改进方向有二：更聪明的静态猜法（如"后向分支预测跳转、前向预测不跳"，契合循环）和动态预测（5.5.4）。

多来源分歧（显式记录，重要）：分支延迟槽（branch delay slot）——一种老式静态方案，让 ISA 规定"分支后面固定 1 条（或几条）指令无论分支是否跳转都照常执行"，由编译器往里填有用指令来吸收惩罚。**经典 MIPS 有 1 个分支延迟槽**（早期 P&H MIPS 版教材、H&P《QA》经典 MIPS 流水均以此讲解）；**RISC-V 则取消了架构级分支延迟槽**（P&H《COD》RISC-V 2nd ed 明确指出 RISC-V 无延迟槽，改用分支预测），因为深流水下 1 个延迟槽远不够吸收惩罚、反而成为 ISA 包袱。这是"教学载体从 MIPS 换成 RISC-V"带来的实打实差异，不是笔误——读旧版（MIPS）教材会看到延迟槽，读 RISC-V 版不会，两边都记、点明成因。

### 5.5.4 动态 1-bit 与 2-bit 预测入门

动态分支预测（dynamic prediction）用一张分支预测缓冲（branch prediction buffer / branch history table）记录每个分支近期的实际行为，据历史猜下一次。最简单的是 1-bit 预测器：每个分支存 1 位，记"上次跳没跳"，下次就照上次猜。

1-bit 预测器的致命弱点是循环的两端各错一次。设想一个执行很多次的内层循环，其回边分支绝大多数次都"跳转"（继续循环），只有最后一次"不跳"（退出）：

```
进入循环第一次：上次记录停留在"退出时的不跳" → 猜不跳 → 错1次
循环最后一次退出：历史是"跳" → 猜跳 → 错1次
```

于是每趟循环至少错 2 次（进入、退出各一次），即便循环体内 100% 规律。改进是 2-bit 预测器（2-bit saturating counter，四状态：强/弱 跳、强/弱 不跳）：需要连续错两次才翻转预测方向，因而循环退出那一次的偶发"不跳"不会立刻毁掉"跳"的预测，把每趟循环的错判从 2 次降到约 1 次。

入门只需掌握"1-bit 每趟循环错 2 次、2-bit 加一层迟滞把它降到约 1 次"这个直觉。易错点：动态预测不改变正确性——预测只影响性能（猜错就冲刷重来，结果始终正确）；它是"用历史赌未来"的性能优化，不是逻辑保证。更强的预测器（相关预测、gshare、竞赛、TAGE）与 BTB/RAS 属 L5-05 AA-4.5 的纵深，本报告不展开。

#### 来源与时效
- 锚点：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.8 *Control Hazards*（分支冒险、冲刷、分支解决前移到 ID 段使惩罚=1、predict-not-taken 静态预测、RISC-V 无延迟槽、1-bit 与 2-bit 动态预测、分支预测缓冲）；核实 2026-07-26。
- 佐证：H&P《QA》6th ed, 2017, 附录 C（control hazards、branch penalty、经典 MIPS 分支延迟槽、静态/动态预测、2-bit 预测器）；H&H《DDCA》RISC-V ed, 2021, ch7（branch misprediction/flush、prediction）；Berkeley CS61C。
- 冲突项（重要）：**分支延迟槽**——经典 MIPS（旧版 P&H MIPS 教材、QA 经典 MIPS 流水）有 1 个架构级延迟槽；**RISC-V（COD RISC-V 2nd ed）取消延迟槽、改用预测**。两边都记：这是 ISA 差异（教学载体 MIPS→RISC-V），非矛盾。读旧版教材见延迟槽属正常。
- ⚙相对稳定：1-bit/2-bit 预测器行为为经典结论，稳定；分支惩罚具体拍数取决于"分支在哪段解决"，COD 优化实现为 ID 段解决→1 拍，朴素实现或深流水会更多，锚定 COD 教学流水线。
- 待核：不同实现的确切分支惩罚拍数随微架构而异，本报告以 COD 教学流水（ID 段解决，惩罚 1）为准并标明前提；确切小节号依 COD ch4 编排。

## 5.6 异常与中断

### 5.6.1 异常与中断的区分

异常（exception）与中断（interrupt）是打断正常指令流的两类"意外事件"，需要处理器暂停当前程序、转去执行处理程序。二者的核心区别在来源：

```
异常 exception ：来自处理器内部、由某条指令引发（如未定义指令、算术溢出、缺页、系统调用/环境调用）
中断 interrupt ：来自处理器外部、与当前指令无关（如 I/O 设备就绪、定时器）
```

异常是"同步"的（由具体某条指令在其执行时触发，可精确对应到那条指令），中断是"异步"的（外部随时到来，与正在执行哪条指令无必然关系）。P&H 也指出不同教材/厂商对这两个词的用法并不统一——有的把二者统称 exception，有的统称 interrupt；关键是理解"内部指令引发 vs 外部异步到来"这条区分，而非纠结名词。

异常像"你做题时自己算出一个非法操作（除以零）"——由你这一步引发、能定位到哪一步；中断像"你做题时门铃响了"——和你做到第几题无关、随时可能响。

### 5.6.2 流水线中处理异常的困难

在单周期里异常好办：一拍一条指令，出事就停。但流水线里同时有 5 条指令在飞，麻烦随之而来。

异常可能由流水线中段的某条指令引发（如 EX 段算术溢出、MEM 段访存缺页），而此时：它前面的指令可能已快完成、它后面的指令已经进入流水线开始执行。要正确处理，必须能准确回答"是哪条指令出的事"，并保证"它前面的指令效果全部生效、它自己及它后面的指令效果全部不生效"。若处理不当，会把不该执行的后续指令的副作用留下，或漏掉前面该完成的指令，导致无法正确恢复。

还有一个棘手情形——同一拍可能有多条指令各自触发异常（不同段各出一档事），需要按程序顺序确定"最早那条"优先处理。RISC-V/COD 约定按指令的程序序（最老的优先）来裁决。

### 5.6.3 精确异常

流水线追求的目标叫精确异常（precise exception）：从软件看，异常发生时的机器状态，就好像"程序严格按顺序执行到出事那条指令为止、之后一条未动"。

精确异常要求满足——出错指令之前的所有指令都已完整改变状态（提交），出错指令本身及其之后的所有指令都未改变任何程序可见状态。实现手段与控制冒险的冲刷同源：检测到异常时，冲刷（flush）出错指令及其后面已进入流水线的指令（清成气泡，撤销其未提交的效果），把出错指令的 PC 存入专用寄存器，再跳转到异常处理程序入口。RISC-V 用以下机制（COD ch4 §4.9）：

```
SEPC   ：保存出错指令的 PC（Supervisor Exception Program Counter），供处理后返回
SCAUSE ：记录异常原因（Supervisor Cause），供处理程序判别事件类型
```

核心结论（为什么顺序流水相对好办）：正因为顺序 5 级流水是"按序取指、按序写回"，指令天然按程序序完成，要做到精确异常，只需在检测点冲刷后续指令即可，代价可控。真正困难的是乱序/超标量处理器——指令乱序完成，要靠重排序缓冲（ROB）等机制在"退休"时才按序提交，才能维持精确异常的假象，那属 L5-05 AA-4.4 的纵深，本报告不展开。

精确异常之所以是硬指标，是因为操作系统要靠它来正确处理缺页（补页后从出错指令原地重试）、调试、以及信号处理——若异常不精确，OS 拿到的现场就是一团"半执行"的乱麻，无法安全恢复。易错点：别把"冲刷"理解成"丢弃结果不管"——被冲刷的指令是"尚未提交状态"的，撤销它们不会破坏正确性；而出错指令之前"已提交"的指令效果必须保留。精确异常的精髓正是这条"提交边界"的干净切割。
