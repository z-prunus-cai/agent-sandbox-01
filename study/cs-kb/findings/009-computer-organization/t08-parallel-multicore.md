## 8.1 Flynn 分类：SISD / SIMD / MISD / MIMD

### 8.1.1 分类的坐标轴：指令流数 × 数据流数

Flynn 分类（Michael J. Flynn, 1966）用两个维度给所有计算机的并行性建坐标系：同一时刻在跑的**指令流（instruction stream）有几条**、被处理的**数据流（data stream）有几条**。两维各取"单/多"，交叉出四类：

    数据流 →        单数据流(SD)        多数据流(MD)
    单指令流(SI)     SISD                SIMD
    多指令流(MI)     MISD                MIMD

- **SISD**（单指令单数据）：经典单核顺序处理器，一次取一条指令、处理一份数据。是没有显式并行的基线；但注意它内部仍可有流水线/超标量这类"隐式"指令级并行——Flynn 分类看的是"程序员/指令层面"的流数，不是微架构内部。
- **SIMD**（单指令多数据）：一条指令同时对多份数据做同样的操作。向量处理器、CPU 的 SSE/AVX 向量扩展、GPU 的核心执行模型都属此类。适合"对一大片数据做同一种运算"的**数据级并行（DLP）**。
- **MISD**（多指令单数据）：多条不同指令作用于同一份数据流。现实中几乎没有通用商用机属于此类，P&H 明确指出没有这种商用多处理器；偶尔被用来勉强归类某些容错冗余或流水线特例，属"占位格"。
- **MIMD**（多指令多数据）：多个处理器各自跑各自的指令、处理各自的数据。多核 CPU、多处理器服务器、集群都是 MIMD。适合"多个任务或多个数据分区各干各的"**线程级/任务级并行（TLP）**。

理解这张表的关键是分清"省什么"：SIMD 省的是**取指与控制**——一条指令控制 N 个数据通道，硬件里控制逻辑只有一份，省下的晶体管全给了数据通路，所以吞吐高、但只能做整齐划一的活。MIMD 每个核都有完整的取指译码控制，灵活到能同时跑毫不相关的程序，代价是控制硬件成 N 份、还得解决核间通信与同步。初学者常见误解是把"多核"和"SIMD"对立——其实今天的机器是**分层混合**：一台 MIMD 多核机，每个核内部又带 SIMD 向量单元，GPU 更是"MIMD 的多个 SIMD 引擎"。

### 8.1.2 SPMD 编程模型：MIMD 硬件上的常见写法

实践中很少真让每个核跑完全不同的程序。最常见的写法是 **SPMD（Single Program, Multiple Data，单程序多数据）**：所有处理器跑**同一份程序代码**，但各自用线程号/进程号（如 rank、thread id）算出"我该处理哪一块数据"，于是走不同的分支、访问不同的数据。

SPMD 是**编程模型**，不是 Flynn 的第五类硬件——它跑在 MIMD 硬件上。之所以要单独记住它，是因为它解释了一个初学者的困惑："既然是 MIMD（多指令流），为什么我写并行程序时只写了一份代码？"答案就是 SPMD：一份代码 + 按 id 分工 = 在 MIMD 硬件上表现出"多指令流"（不同核此刻可能停在代码的不同行）。MPI、OpenMP、CUDA 的 kernel 都是 SPMD 风格。

易错点：SIMD 是**硬件层面**一条指令锁步驱动多通道（通道之间不能各走各的分支，除非用掩码）；SPMD 是**软件层面**多个独立线程恰好跑同一份源码，它们**可以**各自自由分支。两者名字像、层次不同，别混。

## 8.2 多核共享内存：共享地址空间与片上多核组织

### 8.2.1 共享地址空间：靠读写同一片内存来通信

**共享内存多处理器（shared memory multiprocessor, SMP）** 指多个处理器共享**单一物理地址空间**：任何一个核对地址 A 的读写，和别的核对地址 A 的读写指的是同一个内存位置。于是核间通信不需要显式发消息，而是**通过读写共享变量隐式完成**——一个核写内存，另一个核读同一地址就"收到"了。

这是与另一条路线**消息传递（message passing）** 的根本分野：消息传递里每个处理器有自己私有的地址空间，通信必须显式 send/receive（集群、超算多用此路线）。共享内存的好处是**编程直观**——串行程序里怎么用变量，并行里还怎么用，只是多了个"谁在什么时候读写"的协调问题；代价是硬件要维护"所有核看到一致内存"的假象（这就引出 8.4 的一致性）。

初学者最小例子：两个线程都执行 `counter = counter + 1`。共享内存模型下它们操作的是内存里同一个 `counter`；如果不加同步，两个"读—加—写"可能交错导致丢更新。这正说明共享内存"好写"的同时把**同步与一致性**推到了台前——这两件事分别归 L4-05 并发（锁/原子）和本报告 8.4（硬件一致性）。

### 8.2.2 UMA 与 NUMA：访存延迟均匀不均匀

按"每个核访问内存的延迟是否一样"，共享内存机分两类，公式化地看单次访存延迟：

    UMA：latency(core_i → 任意内存) ≈ 常数（对所有 i 相同）
    NUMA：latency(core_i → 本地内存) < latency(core_i → 远端内存)

- **UMA（Uniform Memory Access，统一访存）**：所有核到主存的延迟相同，典型是通过共享总线/交叉开关连到一块集中式主存。也叫对称多处理（SMP，此处 S 取 symmetric）。规模小时简单，但核多了共享通道成瓶颈。
- **NUMA（Non-Uniform Memory Access，非统一访存）**：内存分块挂在不同核/节点旁，访问"本地"内存快、访问"别人旁边"的内存慢。大规模多核/多路服务器普遍是 NUMA。好处是带宽随节点数扩展，代价是程序员/OS 要关心"数据放在哪、谁访问它"（数据放置与亲和性）。

深挖（互连拓扑、目录一致性对 NUMA 的支持）归 L5-05 AA-6，本报告只需记住"UMA 延迟均匀、NUMA 延迟看远近"这一入门区分。本机 `lscpu` 显示 `NUMA node(s): 1`，即单 NUMA 域——从访存延迟角度这台 4 核机对软件呈现 UMA 式的均匀视图。

### 8.2.3 片上多核组织：私有 L1/L2 + 共享 LLC

**多核（multicore）** 就是把多个处理器核做在**同一块芯片（die）**上。今天主流的片上组织是**分层 cache**：每个核有自己**私有的 L1**（常再加私有 L2），所有核**共享最后一级 cache（LLC，通常是 L3）** 与片外主存；核之间通过片上互连（总线/环/网格）相连。

为什么这样切？私有小 cache 离核近、延迟低、各核互不干扰；共享大 LLC 让核间共享的数据只存一份、且是核间快速交换数据的汇合点。这个"私有近 + 共享远"结构直接决定了一致性问题的作用面——**私有 cache 里的副本**才是 8.4 要协调的对象。

本机佐证：`lscpu` 报 `L1d 192 KiB (4 instances)`、`L1i 128 KiB (4 instances)`、`L2 8 MiB (4 instances)`、`L3 260 MiB (1 instance)`——正是"L1/L2 各核一份（4 instances）、L3 全芯片一份（1 instance）"的私有+共享分层，与教材描述吻合。区分多核与"多路（multi-socket）"：多核是一块芯片内多核；多路是多块芯片插在主板上，后者通常构成 NUMA。

## 8.3 GPU 概览：众核 SIMT 结构与吞吐导向

### 8.3.1 吞吐导向 vs 延迟导向：GPU 与 CPU 的根本取向差异

GPU（图形处理单元，现广用于通用计算 GPGPU）是**吞吐导向（throughput-oriented）** 的众核处理器：它不追求让单个线程尽快完成（那是 CPU 的**延迟导向**目标），而是追求**单位时间内完成的总工作量最大**。做法是把海量简单核堆在一起、同时驱动成千上万个线程，当某些线程因访存等待时，硬件立刻切到别的就绪线程，用"线程多到填满一切空隙"来隐藏延迟。

一句话对比：CPU 用**大 cache + 复杂乱序控制**让少数线程跑得快（省延迟）；GPU 用**大量线程 + 简单核**让总吞吐高（多线程隐藏延迟，把省下的晶体管给算术单元）。这解释了为什么 GPU 适合数据并行的规则计算（图形、矩阵、深度学习），而不适合分支复杂、线程少的串行逻辑。

### 8.3.2 SIMT 执行模型：一条指令驱动一组线程

NVIDIA 把 GPU 的执行模型称为 **SIMT（Single Instruction, Multiple Threads，单指令多线程）**：程序员按"每个线程处理一个数据元素"来写代码（看起来像很多独立线程），但硬件把线程**按组打包**，一组内的线程**共享一条指令、锁步执行**（这一组 NVIDIA 称 warp）。所以 SIMT 本质是"披着多线程外衣的 SIMD"——对程序员是多线程视角，对硬件是一条指令喂多个数据通道。

    SIMD：软件显式操作向量（一条指令写明"对这 N 个元素做加法"）
    SIMT：软件写单线程标量代码，硬件把一组线程锁步成 SIMD 执行

SIMT 相对纯 SIMD 的入门要点：当一组内的线程遇到**数据相关的分支**（有的线程走 if、有的走 else）时，硬件只能**串行地分别执行两条路径**、用掩码关掉不该执行的线程——这叫**分支发散（branch divergence）**，是 GPU 性能损失的典型来源。发散惩罚、占用率（occupancy）、warp 调度、线程块/网格层级等深挖明确归 **L5-05 AA-5**，本报告只需记住"SIMT = 多线程写法 + SIMD 锁步执行 + 分支发散是代价"。

初学者关联：把 8.1 的坐标系套上来——GPU 整体是"MIMD 地组织了很多个 SIMD 引擎"，每个引擎内部 SIMT 锁步、引擎之间各自独立，正是分层混合并行的典型。

## 8.4 缓存一致性入门：一致性问题的提出与嗅探基本思想

### 8.4.1 一致性问题从何而来：共享内存 + 私有 cache = 旧副本

在共享内存多核里，每个核有**私有 cache**（8.2.3）。当多个核读了同一个内存块，各自的私有 cache 里就有了该块的**多份副本**。此时若某个核**写**了这个块，它改的是自己 cache 里的副本；**别的核 cache 里的副本仍是旧值**——于是不同核读同一地址会读到不同结果。这就是**缓存一致性问题（cache coherence problem）**。

最小例子（P&H 经典场景）：核 A、核 B 都把变量 X（初值 0）读进各自 cache。核 A 执行 `X = 1`（只更新了 A 的 cache 副本）。此刻核 B 再读 X，如果没有一致性机制，B 从自己 cache 读到的仍是 0——两个核对"同一个 X"看到了不一致的值。程序就错了。

一致性要保证的直觉性质（P&H 表述）：（1）**写后能读到新值**——某核写 X 后，若无其他写介入，其他核最终的读能返回该新值；（2）**同一地址的写被所有核看到相同的先后顺序（写串行化）**。注意区分两个易混概念：**一致性（coherence）** 管"对**同一个地址**，多核看到的值/写序是否协调"；**内存一致性模型（consistency）** 管"对**不同地址**的读写，在多核间呈现的先后顺序约束"。后者（x86-TSO/弱序等）深挖归 L5-05 AA-6 与 L4-05 并发，本报告不展开。

### 8.4.2 嗅探（snooping）的基本思想：监听广播、写时使别人失效

解决一致性最主流的入门方案是**嗅探协议（snooping protocol）**：让所有 cache 都**监听（snoop）** 一个共享的广播介质（经典模型是共享总线）。每个 cache 控制器时刻盯着总线上出现的内存事务，一旦发现"别人要写一个我也缓存着的块"，就对**自己的副本**采取行动。两种基本策略：

    写失效（write-invalidate）：某核要写块 B 前，先在总线广播"我要写 B"，
                               其他持有 B 副本的 cache 收到后把自己的副本标记为无效。
                               此后它们再访问 B 会 miss、重新取到新值。（最常用）
    写更新（write-update/broadcast）：某核写 B 时，把新值广播出去，
                               其他 cache 直接更新自己的副本。（占用带宽大，少用）

**写失效**是绝大多数商用系统的选择：写之前"作废别人的旧副本"，保证任一时刻对某块最多只有一个核持有"可写的最新副本"，别人要用时自然会 miss 并取到新值。写失效的直觉是"要改之前先把别人手里的过期传单全收走"，比"每改一次就给所有人重发传单"（写更新）省带宽得多，尤其当一个核连续多次写同一块时。

嗅探依赖"所有 cache 能看到同一串广播事务"，因此天然适合总线式的中小规模多核；核数很多、总线成瓶颈时改用**目录协议（directory-based）**（用一张目录记录哪个块被谁缓存，点对点通知，不靠广播）。具体的 MESI/MOESI 状态机、目录协议、写传播与事务串行化的实现细节明确归 **L5-05 AA-6**，本报告只讲到"问题是什么 + 嗅探/写失效的基本思想"。

初学者易错点：一致性**不等于**"任何时刻所有 cache 值都完全相同"——它允许短暂的不一致，只要保证"写最终能被看到、且同地址写序一致"。真正要求"所有核对所有地址读写顺序"的是内存一致性模型，别把两者混为一谈。

## 8.5 硬件多线程：细粒度 / 粗粒度 / 同时多线程 SMT

### 8.5.1 硬件多线程的动机：用别的线程填一个核的空闲

**硬件多线程（hardware multithreading）** 让**单个处理器核**保存多个线程的状态（各自的寄存器、PC），并能在这些线程间**快速切换**，从而在某个线程停顿（如 cache miss、长延迟指令）时，让核转去执行另一个线程，**不让功能部件闲着**。它和多核是正交的两件事：多核是**复制整颗核**换并行；硬件多线程是在**一颗核内部**用别的线程填自己的执行空隙，提高这颗核的利用率。

前提是切换必须**极快**（硬件级、几乎零开销）——所以每个线程的上下文（寄存器堆、PC 等）在硬件里各存一份，切换只是改用哪一组，而不像 OS 线程切换那样保存/恢复到内存。按"多久切一次、怎么切"分三种粒度。

### 8.5.2 细粒度 vs 粗粒度多线程

- **细粒度多线程（fine-grained）**：**每个时钟周期都可能切线程**，通常在多个就绪线程间轮转（round-robin），跳过当前停顿的线程。好处是既能隐藏**长停顿**也能隐藏**短停顿**，功能部件几乎不空转；代价是**拖慢单个线程**——因为就算某线程完全就绪，也要和别人轮流用核，它的独占执行被稀释了。
- **粗粒度多线程（coarse-grained）**：**只在遇到代价高的停顿时才切**（如 L2/末级 cache miss 这种长延迟事件），平时让一个线程独占核连续跑。好处是**不拖慢单线程**（没停顿时它独享核）；代价是**短停顿隐藏不了**，而且切换时流水线要**排空并重新填充**（新线程的指令得从头灌满流水线），这段填充开销使它对短停顿收益差。

一句话对照：

    细粒度：拍拍都可切、轮转 → 隐藏长/短停顿，但单线程变慢
    粗粒度：只在长停顿才切 → 不拖慢单线程，但短停顿隐藏不了、切换有流水线重填开销

### 8.5.3 同时多线程 SMT：一拍内同时发射多个线程的指令

**同时多线程（Simultaneous Multithreading, SMT）** 是硬件多线程与**超标量（superscalar，一拍能发射多条指令）** 的结合：在同一个时钟周期里，处理器可以**同时发射来自多个线程的指令**去填满多个发射槽。前两种（细/粗粒度）在**任一时刻**执行槽里都只属于**一个**线程；SMT 则允许**同一拍**里 A 线程和 B 线程的指令**并肩占用**不同的功能部件。

为什么 SMT 有效？现代超标量核每拍有多个发射槽，但单个线程的**指令级并行（ILP）** 常填不满这些槽（存在相关、停顿，留下空槽）。SMT 借另一个线程的独立指令来填这些**水平方向的空槽**——它同时挖掘 ILP（一个线程内）和 TLP（线程之间）。对操作系统而言，一个 SMT 物理核会呈现为**多个逻辑处理器**。Intel 的商用实现叫 **Hyper-Threading（超线程）**，一核常暴露 2 个逻辑线程。

    细/粗粒度：每一拍的所有发射槽只服务一个线程（不同拍可换线程）
    SMT：      同一拍的多个发射槽可同时服务多个线程（水平共享）

易错点与本机说明：SMT 的两个逻辑线程**共享**同一颗物理核的执行单元、cache 等资源，所以两个逻辑线程的总性能通常**远小于**两颗真核——它是"填空隙"的增益，不是翻倍。本容器 `lscpu` 显示 `Thread(s) per core: 1`、`siblings` 与 `cpu cores` 均为 4，说明**本机未暴露 SMT**（每核仅 1 线程），因此无法在本机现跑"开/关超线程"对照；SMT 的行为在此以两部一手教材 + CS61C 交叉坐实，未做本机实证（如实留白，非结论）。
