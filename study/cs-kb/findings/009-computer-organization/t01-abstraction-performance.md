## 1.1 抽象层次与设计思想

### 1.1.1 从程序到硬件的抽象栈

计算机是一座"抽象的塔"：上层不必知道下层怎么实现，只需知道下层承诺提供什么。一个用高级语言写的程序，要真正在电路上跑起来，会自上而下穿过若干层：

```
应用软件（你写的程序）
  ↓ 高级语言 High-Level Language（C / Python …）
系统软件（编译器 Compiler、汇编器 Assembler、操作系统 OS）
  ↓ 汇编语言 Assembly Language（人可读的指令助记符）
  ↓ 机器语言 Machine Language（二进制 0/1 指令）
硬件（数据通路 + 控制 + 存储，最终是逻辑门与晶体管）
```

每一层只通过一个"约定好的界面"和相邻层打交道。编译器把高级语言翻成汇编，汇编器把汇编翻成二进制机器码，硬件直接执行这些 0/1。操作系统则夹在应用与硬件之间，管理输入输出、内存分配、任务调度这些底层杂务。

为什么要这么分层？因为复杂度大到一个人脑子装不下。设计 CPU 的人不需要懂浏览器怎么写，写浏览器的人也不需要懂晶体管怎么排布——两边只要都遵守中间那层界面即可。这正是"用抽象简化设计"（见 1.1.3 第 2 条伟大思想）的最典型体现。

容易以为"汇编语言"和"机器语言"是一回事。它们是同一层的两副面孔——汇编是给人看的助记符（如 `add x5, x6, x7`），机器语言是同一条指令的二进制编码（一串 0/1）；汇编器负责一一对应地翻译。另一个常见误解是把编译器和操作系统混为一谈：编译器在程序"运行前"把源码翻成机器码，操作系统在程序"运行时"提供服务，两者职责与时机都不同。

### 1.1.2 指令集体系结构（ISA）作为硬件/软件界面

在上面这摞抽象里，有一层界面地位特殊，叫指令集体系结构（Instruction Set Architecture, ISA）。它是"最低层软件所看到的硬件抽象"——即硬件对软件的完整承诺：有哪些指令、有哪些寄存器、内存怎么编址、指令怎么编码成二进制。软件只要照 ISA 写，就不必关心硬件内部到底怎么造。

ISA 是硬件与软件的分界契约。ISA 之上是软件世界（编译器只需面向 ISA 生成代码），ISA 之下是硬件世界（芯片厂商可以用完全不同的电路实现同一套 ISA）。RISC-V、x86-64、ARM 都是不同的 ISA。

一个关键的配套概念是应用二进制接口（Application Binary Interface, ABI）：

```
ABI = ISA 的用户可见部分  +  操作系统的接口约定（系统调用、寄存器使用/传参约定等）
```

ISA 让"同一个二进制程序能在不同厂商、不同年代但 ISA 相同的芯片上跑"成为可能——正因为界面稳定，Intel 和 AMD 的芯片能跑同一份 x86-64 程序。这也解释了为什么 ISA 一旦确立就极难改动：改 ISA 等于毁约，会让海量既有软件失效。

ISA ≠ 微架构（microarchitecture）。ISA 是"对外承诺"（做什么），微架构是"内部实现"（怎么做）。同一 ISA 可以有几十种微架构实现，快慢、功耗天差地别，但对软件呈现同一副面孔。这条"ISA 与微架构分账"的线，在本课大主题 2（ISA）和 L5-05（高级体系结构）会反复用到。

### 1.1.3 八大伟大思想（Eight Great Ideas）

P&H《COD》把贯穿整个计算机体系结构的通用设计原则提炼为"八大伟大思想"，用作全书的主线路标：

```
1. 面向摩尔定律设计   Design for Moore's Law
2. 用抽象简化设计     Use Abstraction to Simplify Design
3. 加速常见情形       Make the Common Case Fast
4. 借并行提升性能     Performance via Parallelism
5. 借流水线提升性能   Performance via Pipelining
6. 借预测提升性能     Performance via Prediction
7. 存储层次           Hierarchy of Memories
8. 借冗余保证可靠     Dependability via Redundancy
```

这八条不是零散口号，而是本课后续每个大主题的"为什么"来源——流水线（大主题 5）是第 5 条，缓存（大主题 6）是第 7 条，RAID/纠错（大主题 7）是第 8 条，多核（大主题 8）是第 4 条。先记住它们，后面学到具体机制时就能对号入座。

- 面向摩尔定律设计：晶体管数量约每 18–24 个月翻倍，芯片设计要提前几年动工，所以要"照着项目做完时的工艺"设计，而非当下工艺。（摩尔定律近年已明显放缓，属⚙演进项，见 1.4/1.5。）
- 加速常见情形：与其让罕见操作变快，不如让最频繁的操作变快，收益更大——这正是 Amdahl 定律（1.3）的实践指南。
- 借流水线/预测/并行提升性能：三种"用更多硬件换更高吞吐"的手段，是从大主题 4 到大主题 8 的技术脊梁。
- 存储层次：把小而快和大而慢的存储分层堆叠，制造"又大又快"的错觉（大主题 6）。

多来源分歧（显式记录，不和稀泥）：Berkeley CS61C 课程把类似原则总结为"Six Great Ideas in Computer Architecture"（六大，条目组织与措辞与 COD 不同，通常含抽象、摩尔定律、局部性/存储层次、并行、性能度量、冗余可靠）。二者不是矛盾而是"同一套智慧的不同切分粒度"：COD 数为 8、CS61C 数为 6。学习时以你所用教材/课程的清单为准即可，不必纠结条数。

#### 来源与时效

## 1.2 性能公式

### 1.2.1 性能与执行时间的定义

"性能好"这句话在体系结构里有精确含义。对单个程序，性能（performance）定义为执行时间（execution time，又称响应时间 response time）的倒数：

```
性能 = 1 / 执行时间
```

于是"X 比 Y 快 n 倍"意味着：

```
性能_X / 性能_Y = 执行时间_Y / 执行时间_X = n
```

谈"快慢"必须先说清用哪种时间。这里的执行时间通常指 CPU 执行时间（CPU execution time）——CPU 真正为该程序算数的时间，不含等磁盘、等网络、等其他程序的时间。它又分用户 CPU 时间和系统 CPU 时间。

为什么用执行时间而不用"每秒指令数"之类？因为最终用户关心的是"我的任务多久跑完"。吞吐率（throughput，单位时间完成的任务数）是另一个视角，服务器更关心它，但对单任务快慢，执行时间才是本源指标。易错点：MIPS（每秒百万条指令）这类指标会误导——不同指令干的活不一样多，指令数高不等于任务完成得快，COD ch1 专门把"用 MIPS 比性能"列为经典谬误。

### 1.2.2 CPU 时间的三因子分解（经典性能公式）

把 CPU 执行时间拆开，得到本大主题（乃至整门体系结构）最核心的一条公式，常被称为"性能的铁律"（iron law of performance）：

```
CPU 时间 = 指令数(IC) × 每指令周期数(CPI) × 时钟周期
```

其中时钟周期（clock cycle time）与时钟频率（clock rate）互为倒数，所以等价地：

```
CPU 时间 = (指令数 × CPI) / 时钟频率
```


```
CPU 时钟周期总数 = 指令数(IC) × CPI
CPU 时间 = CPU 时钟周期总数 × 时钟周期 = CPU 时钟周期总数 / 时钟频率
```

一个程序跑多久，由且仅由这三个因子的乘积决定：
- IC（Instruction Count，指令数）：这个程序一共执行了多少条指令。
- CPI（Cycles Per Instruction，每指令平均周期数）：平均每条指令花几个时钟周期。
- 时钟周期（Clock cycle time）：一个时钟周期有多长（如 0.5 ns 对应 2 GHz）。

这条公式的威力在于"分账"——它把"快慢"这个模糊问题拆成三个互相独立、可分别优化的旋钮。想让程序更快，只有三条路：减少指令数、降低 CPI、或提高频率（缩短周期）。

一个最小算例（纯示意性算术，用于理解量纲，非本机测量）：设某程序 IC = 10 亿条指令，平均 CPI = 1.5，时钟频率 2 GHz（时钟周期 = 0.5 ns），则

```
CPU 时间 = 1e9 × 1.5 × 0.5 ns = 0.75 s
```

CPI 是"平均值"。不同指令 CPI 不同（乘除法慢、简单算术快、访存可能因缓存失效很慢），整体 CPI 是按指令频率加权的平均。更精确地：

```
CPU 时钟周期总数 = Σ_i (CPI_i × IC_i)   （对每类指令 i 求和）
```

三因子并不互相独立地"免费"。提高频率往往抬高功耗（见 1.4）并可能被存储墙拖累 CPI；用更精简的指令可能减小 CPI 却增大 IC。真正的设计是三者的联合权衡，不能只盯一个。

### 1.2.3 三因子分别被哪一层影响（分账）

理解这条公式的关键，是知道每个因子由谁决定——这决定了"优化该找谁"：

```
IC（指令数）   ← 由 算法、编程语言、编译器、ISA 共同决定
CPI            ← 由 微架构（流水线/缓存/乱序等）与 ISA、指令组合决定
时钟周期/频率  ← 由 微架构关键路径 与 制造工艺 决定
```

算法和编译器主要动 IC；处理器微架构主要动 CPI 和频率；ISA 则同时影响 IC 与 CPI（这也是 RISC vs CISC 之争的战场，见大主题 2 §2.6）。

这张"分账表"是全课的导航图。学流水线（大主题 5）时，你其实在学"如何在几乎不增加频率的前提下把有效 CPI 逼近 1"；学缓存（大主题 6）时，在学"如何降低访存指令带来的 CPI 惩罚"；学编译优化（L3-03 及后续）时，在学"如何减少 IC 或换成更便宜的指令"。全部都能回挂到这三个因子上。

不能跨机器直接比 IC 或 CPI。不同 ISA 的一条指令干的活不同，"指令数少"不代表更快；同理 CPI 只在同一 ISA、可比指令组合下才有横向比较意义。唯一可跨机器公平比较的，永远是最终的执行时间（或其倒数性能）。

## 1.3 Amdahl 定律

### 1.3.1 局部改进对整体的作用

Amdahl 定律（Amdahl's Law）回答一个极其实用的问题：只把程序的一部分加速，整体到底能快多少？直觉上"把某段代码提速 10 倍"听起来很爽，但如果那段只占总时间的一小块，整体几乎纹丝不动。

用执行时间写出来：

```
改进后执行时间 = (受影响部分的时间 / 加速倍数) + 不受影响部分的时间
```

整体加速被"没被优化的那部分"死死拖住。你只能加速你动过的那块，剩下的原封不动，于是剩下那块就成了新的瓶颈。

辅助直觉（最小例子）：某程序总耗时 100 s，其中 80 s 是可优化的计算、20 s 是无法优化的 I/O。哪怕把计算加速到无穷快（80 s → 0），总时间也只降到 20 s，整体最多快 5 倍——那 20 s 是天花板。

### 1.3.2 加速比公式与上界

把它写成加速比（speedup）形式更常用。设 f 为可被加速部分占原执行时间的比例（fraction enhanced），s 为该部分的加速倍数，则整体加速比：

```
加速比 = 1 / ( (1 − f) + f / s )
```

当把那部分加速到极限（s → ∞）时，得到整体加速比的上界：

```
加速比上界 = 1 / (1 − f)
```

整体加速比的天花板只由"不可加速比例 (1 − f)"决定，与你把可加速部分优化得多猛无关。前面 80/20 的例子里 f = 0.8，上界 = 1/(1−0.8) = 5，与"加速无穷倍"算出的 5 倍一致。

这就是"加速常见情形"（八大思想第 3 条）的数学根据——要投资就投在占比最大的那部分（f 大），因为它决定了天花板有多高。反过来，一个只占 5% 时间的函数，就算优化到消失，整体也最多快约 5.3%（1/(1−0.05) ≈ 1.053），不值得投入。

### 1.3.3 常见误用与直觉陷阱

Amdahl 定律最常被"忘记还有不可加速部分"这件事坑到。工程师容易报告"我把热点函数提速了 20 倍"，却不提该函数只占 30% 时间——此时整体加速比 = 1/((1−0.3) + 0.3/20) ≈ 1.39，只快约 39%，远不如"20 倍"给人的印象。

- 递减收益：随着 s 增大，加速比迅速逼近上界后就几乎不动了，继续加大 s 是浪费。
- 它是"加速常见情形"的双刃：既告诉你该优化占比大的部分，也警告你占比小的部分优化了也白搭。
- 与多核直接相关（见 1.5）：当"加速手段"是并行到 p 个核时，f 是可并行比例，则加速比 = 1/((1−f) + f/p)，上界仍是 1/(1−f)。这解释了为什么"核越堆越多"边际收益急剧下降——串行部分成为硬天花板。这一并行版本常被称作 Amdahl 定律在并行计算中的推论。

f 是"按时间"算的比例，不是"按代码行数"或"按指令数"。一个只有几行的循环可能占了 90% 的时间。判断该优化谁，要看时间画像（profiling），不能凭代码长短拍脑袋。

- 佐证：H&P《QA》6th ed, 2017, ch1 §1.9（Amdahl's Law 完整量化推导与上界 1/(1−f)）；Berkeley CS61C。

## 1.4 功耗墙

### 1.4.1 动态功耗公式

几十年来 CPU 靠"堆晶体管 + 提频率"变快，直到撞上功耗墙（power wall）。要理解这堵墙，先看 CMOS 电路的动态功耗（dynamic power）——晶体管开关翻转时消耗的功率：

```
动态功耗 ∝ 1/2 × 电容负载(C) × 电压(V)² × 开关频率(f)
```

动态功耗随电压的平方、随频率的一次方增长。电压这一项是平方关系，所以它对功耗的影响最猛——这正是后面故事的关键。

每次一个晶体管从 0 翻到 1（或反过来），要给它的等效电容充/放电，一次翻转耗能约 1/2·C·V²；每秒翻 f 次，功率就是能量乘频率。所以想省功耗，降电压最划算（平方效应），其次降频率或减电容。易错点：这里的 f 是"翻转/开关频率"，与时钟频率相关但不完全等同（不是每个时钟每个门都翻转）；入门阶段把它理解为"活动越频繁、频率越高，功耗越大"即可。

### 1.4.2 Dennard 缩放及其终结

Dennard 缩放（Dennard scaling，1974 年 Robert Dennard 提出）是过去提频而功耗不失控的理论支柱：当晶体管尺寸按比例缩小，电压和电流也同比例下降，结果是单位面积的功率密度（power density）保持大致恒定。于是每代工艺既能塞进更多、更快的晶体管，又不至于把芯片烧穿——"免费的提频午餐"。

Dennard 缩放约在 **2004–2006 年前后终结**（属⚙演进项，各家给的拐点年份略有出入）。原因是电压不能再随尺寸继续往下降了——电压太低，晶体管的漏电流（leakage current）带来的静态功耗急剧上升，且阈值电压受物理限制。电压这一项（平方效应）降不动，再提频率就会让功耗和发热失控。

晶体管还能继续变小、变多（摩尔定律在此拐点后又延续了若干代，虽也在放缓），但"变小就自动省电、就能提频"这件事不再成立。这就是"晶体管数还在涨、时钟频率却卡在几个 GHz 上不去"这一著名现象的根源。

### 1.4.3 静态功耗与功耗墙的后果

除了开关时的动态功耗，现代芯片还有静态功耗（static power）——晶体管即使不翻转，也因漏电而持续耗电。工艺越先进（晶体管越小、电压越低），漏电占比越显著，静态功耗成了不可忽视的一块。

核心结论——功耗墙：芯片能散掉的热量有物理上限（受封装、散热限制，商用芯片大致在百瓦量级）。当"提频→功耗按大于线性增长→发热超过散热能力"时，单纯提频的路就走死了。这就是功耗墙：不是不能造更高频的电路，而是造出来散不掉热。

功耗墙是全书的转折点——它直接逼出了 1.5 的"多核转向"。既然单核提频此路不通，那就用同样的功耗预算摆多个较低频的核，靠并行（八大思想第 4 条）而非提频来换性能。易错点：功耗墙不是"晶体管不够用了"（那是摩尔定律的事），而是"电用不起、热散不掉"；两个限制不同，别混为一谈。

## 1.5 多核转向与基准

### 1.5.1 从单核提频到多核的转向

功耗墙撞上后，整个行业发生了一次 P&H 称为"沧海桑田式转变"（the sea change）的方向调整：约 **2006 年前后**，主流处理器从"单核不断提频"转向"单芯片集成多个核（multicore）"。

既然靠提高单核频率来提性能已被功耗墙堵死，厂商改为在同一功耗预算内摆放多个较低频、较高能效的核心，用线程级并行（thread-level parallelism）换取吞吐。从此"性能提升"从硬件白送变成了需要程序员/编译器显式并行才能兑现。

这是本课后半程（大主题 8 并行处理器）和 L4-05 并发、L5-05 高级体系结构的共同起点。它也带来一个负担转移：单核时代，程序不改也能随新芯片自动变快（"免费午餐"）；多核时代，不写并行代码，多出来的核就闲着，程序不会自动更快。本机即是一例——`lscpu` 显示 4 核、每核 1 线程（未开 SMT/超线程），要用满这 4 核必须靠并行程序。

### 1.5.2 SPEC 基准与相对性能

要公平比较不同机器，不能只跑一个自选程序（容易挑对自己有利的）。业界用标准基准套件（benchmark suite）——一组有代表性的真实程序。最主流的是 SPEC（Standard Performance Evaluation Corporation）的 CPU 基准，分整数（SPECint）与浮点（SPECfp）两类。

SPEC CPU 用一台参考机（reference machine）作基准，某机在某程序上的相对性能记为 SPECratio：

```
SPECratio_i = 参考机执行时间_i / 被测机执行时间_i
```

SPECratio 越大表示越快（比参考机快多少倍）。整套基准的总分再由各程序 SPECratio 汇总（见 1.5.3）。此外还有专门度量能效的 SPECpower 基准，反映"每瓦性能"，呼应功耗墙时代对能效的重视。

SPEC CPU 有明确的版本代际——历史上广泛使用的是 SPEC CPU2006，当前在售版本是 **SPEC CPU2017**（2017 年发布，属⚙演进项）。P&H《COD》ch1 用 SPEC CPU 基准作性能度量的范例（其 2nd ed 具体印的是 CPU2006 还是 CPU2017，本报告未逐页核对，标「待核」）。要点在方法（用标准套件 + SPECratio + 几何平均），而非记住某个版本的具体分数——那些分数会随硬件迭代过时。

### 1.5.3 几何平均与 SPECratio 的汇总

多个程序的 SPECratio 怎么合成一个总分？SPEC 用几何平均（geometric mean），而非算术平均：

```
几何平均 = ( SPECratio_1 × SPECratio_2 × … × SPECratio_n ) ^ (1/n)
```

对"比值型"指标（如相对性能倍数），几何平均才是恰当的汇总方式——它有一个关键好处：结果与所选参考机无关。换参考机会让每个 SPECratio 同比例缩放，但几何平均的比值关系不变，因而不同报告可比。

算术平均对比值不公平——一个程序快 100 倍、另一个快 1 倍，算术平均给出 50.5 倍，被极端值主导，具误导性；几何平均给出 √(100×1) = 10 倍，更能反映"综合快约 10 倍"的均衡感。易错点：几何平均用于"比率/加速比"的汇总；若要汇总的是"总执行时间"这类可直接相加的量，则应回到"总时间 = Σ 各时间"，别错用几何平均。

### 1.5.4 多核时代 Amdahl 定律的回响

多核转向让 1.3 的 Amdahl 定律重新变成头等约束。当"加速手段"是并行到 p 个核时：

```
并行加速比 = 1 / ( (1 − f) + f / p )
```

其中 f 是程序可并行部分的时间占比。上界仍是 1/(1 − f)：哪怕核数 p 无穷多，串行部分 (1 − f) 也会把整体加速比钉死在天花板上。

这解释了为什么"堆核"不是万能药——若一个程序 10% 的时间是无法并行的串行部分（f = 0.9），那么核数再多，整体加速比也超不过 1/(1−0.9) = 10 倍。所以多核时代的性能工程，重心从"提频"转向"尽可能减小串行比例、把 f 逼近 1"。这条线在 L5-05 会以更量化的方式深化，本报告点到为止。
