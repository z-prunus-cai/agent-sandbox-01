## 7.1 I/O 编址：内存映射 I/O vs 独立端口 I/O

### 7.1.1 内存映射 I/O（Memory-Mapped I/O, MMIO）

内存映射 I/O 是把外设内部的控制/状态/数据寄存器**分配到 CPU 的物理地址空间**里，让它们像普通内存单元一样占据一段地址；于是 CPU 用**普通的 load/store 指令**读写这些地址，就等于读写了外设寄存器，无需任何专门的 I/O 指令。RISC-V、ARM 等现代精简指令集架构**只有**这一种 I/O 编址方式。

举个最小例子：假设某串口的"发送数据寄存器"被映射到物理地址 0x1000_0000，那么 RISC-V 里一条

    sb  t0, 0(t1)     # t1 = 0x10000000，把 t0 低字节写进串口发送寄存器

就把一个字节送去发送——从指令角度看，这和往内存写一个字节毫无区别。为什么 RISC-V 敢只用 MMIO？因为它省事：不必为 I/O 单独设计指令、不必在 CPU 上留专门的 I/O 引脚，所有寻址方式（基址+偏移等）和所有访存指令都能直接用在外设上，硬件和编译器都不用特殊照顾。代价是**外设要占掉一部分地址空间**（在 32 位机上曾经是稀缺资源，64 位下已不成问题）。初学者最该记住的关联点在 7.1.3：正因为外设寄存器混在地址空间里，这段地址**绝不能被 cache 缓存**，否则 CPU 会读到 cache 里的旧值而不是外设的当前状态。

### 7.1.2 独立端口 I/O（Port-Mapped I/O, PMIO / Isolated I/O）

独立端口 I/O 给外设开辟一个**与内存完全分开的 I/O 地址空间**，用**专门的 I/O 指令**去访问，靠一根控制线（或指令本身）告诉总线"这次访问的是 I/O 空间而不是内存"。最典型的是 x86：它有独立的 `IN`/`OUT` 指令，I/O 端口地址是 16 位（共 65536 个端口，0x0000–0xFFFF）。

    ; x86 端口 I/O 示例（AT&T 风格意思：从 0x60 号端口读一个字节到 al）
    in   al, 0x60      ; 0x60 是传统键盘控制器端口

为什么会有这种"两套地址空间"的设计？历史原因是早期内存地址位数紧张，把 I/O 单独隔出去可以**不占用宝贵的内存地址空间**，也让"这是内存访问还是外设访问"在硬件上一眼可辨（靠一根 M/IO# 之类的信号线区分）。代价正好和 MMIO 相反：需要额外的指令、额外的控制引脚，而且 `IN`/`OUT` 通常只支持很有限的寻址方式，用起来不如普通 load/store 灵活。要点澄清：x86 **两种方式都有**——低速传统设备（键盘、老式定时器）常用端口 I/O，高带宽设备（显卡显存、PCIe 设备的 BAR 区）几乎都用 MMIO。所以"MMIO vs 端口 I/O"不是"哪种架构用哪种"的二选一，而是"同一台 x86 里两种并存、按设备取舍"。

### 7.1.3 两种编址的对比、可缓存性与访问顺序陷阱

把两者并排看，取舍就清楚了：

    维度            内存映射 I/O (MMIO)          独立端口 I/O (PMIO)
    指令            普通 load/store              专门的 IN/OUT
    地址空间        与内存共用，占内存地址        独立 I/O 空间，不占内存
    寻址灵活性      全部寻址方式可用              受限
    额外硬件        无需专门 I/O 引脚/指令        需要 I/O 控制线与指令
    代表架构        RISC-V、ARM（仅此一种）      x86（与 MMIO 并存）

除了这张表，MMIO 有两个初学者极易踩的实战陷阱，必须讲透：

第一，**可缓存性**。外设寄存器的值会被外设自己改变（比如"数据就绪"位由硬件置位），如果这段 MMIO 地址被 CPU 的 cache 缓存了，CPU 读到的可能是几个周期前的缓存副本，而不是外设此刻的真实状态；写也一样，写进 cache 迟迟不落到外设就会丢命令。所以 MMIO 区域必须被标记为**不可缓存（uncacheable）**——这是操作系统在页表/内存类型寄存器里设置的属性。

第二，**访问顺序**。编译器和乱序 CPU 都可能为了性能重排、合并甚至删掉它们"以为无副作用"的内存读写；但对外设寄存器，读写的**先后顺序本身就是语义**（比如必须"先写命令寄存器、再写触发寄存器"）。C 语言里用 `volatile` 阻止编译器优化掉或重排这些访问，硬件层面还需要**内存屏障指令**（RISC-V 的 `fence`、x86 的 `mfence` 等）保证真正的访存顺序。一句话：MMIO 让访问外设"看起来像访存"，但它绝不是普通访存，可缓存性与顺序这两层保护不能省。

## 7.2 数据传送方式：轮询 / 中断驱动 / DMA

### 7.2.1 轮询 / 程序控制 I/O（Polling / Programmed I/O）

轮询是最朴素的传送方式：CPU 反复读外设的**状态寄存器**，在一个循环里"忙等（busy-wait）"，直到状态位显示"设备就绪 / 数据到了"，才去读写数据寄存器完成一次传送。整个过程 CPU 全程参与、寸步不离。

    轮询骨架（伪代码）：
    do {
        status = load(STATUS_REG);   // 反复读状态寄存器
    } while ((status & READY) == 0); // 忙等到就绪位置起
    data   = load(DATA_REG);         // 就绪后才真正传数据

轮询的优点是**逻辑极简、无中断硬件依赖、延迟可控**：数据一就绪 CPU 立刻知道，没有中断进入/退出的额外开销。缺点是**极度浪费 CPU**——外设通常比 CPU 慢成千上万倍，CPU 把海量周期耗在空转读状态位上，什么正事都干不了。所以轮询只在两种场景划算：一是设备**又快又频繁**（比如高性能网卡在极高负载下，反而故意关中断改用轮询以省下中断开销，这是 Linux NAPI 的思路）；二是**极简嵌入式系统**里没有多任务、CPU 本来也没别的事干。理解了轮询的浪费，就理解了中断"为什么必须出现"。

### 7.2.2 中断驱动 I/O（Interrupt-Driven I/O）

中断驱动 I/O 把"盯着设备"的活儿从 CPU 转交给设备自己：CPU 发起 I/O 后就**去干别的事**，当外设就绪时**主动拉一根中断线**通知 CPU；CPU 收到中断后暂停当前程序、跳去执行对应的**中断服务程序（ISR / 中断处理程序）**完成这次传送，处理完再返回原程序继续。核心收益是**让 CPU 的计算与外设的等待重叠**，不再空转。

这里可以用本机的一个真实观测坐实"中断确实是设备主动发起的、且按设备分类计数"（Linux 6.18.5，命令 `head /proc/interrupts`，核实 2026-07-26）：

    24:  IO-APIC   5-edge      ACPI:Ged
    26:  IO-APIC   4-edge      ttyS0                 # 串口设备的中断（已触发 87 次）
    32:  PCI-MSIX-0000:00:01.0  3-edge  virtio0-stats
    35:  PCI-MSIX-0000:00:0a.0  1-edge  virtio9-input

每一行是一个中断号，最右是发起它的设备名，中间的计数列记录该设备触发了多少次中断——串口 `ttyS0` 每来一个字符就可能触发一次它的中断。这正是"设备就绪→喊 CPU"的物理证据。

中断的代价是**每次中断都有固定开销**：保存现场、跳进内核、执行 ISR、恢复现场、返回。如果设备**每传一个字节就中断一次**，而数据量很大（比如磁盘读一兆字节），中断次数会多到开销压垮收益——CPU 虽然不再空转，却被海量中断和"每次只搬一个字节"的琐碎传送淹没。这个痛点直接催生了 DMA。易错点：中断"异步、不可预测何时到来"，ISR 必须短小且注意与主程序共享数据的并发保护（深入归 L4-01 OS / L4-05 并发，本处不展开）。

### 7.2.3 直接存储器访问（Direct Memory Access, DMA）

DMA 引入一个专门的硬件——**DMA 控制器（DMAC）**——替 CPU 在**外设与主存之间直接搬运整块数据**。CPU 只需在开头做三件事：告诉 DMAC 源地址、目的地址、传输字节数，然后就完全撒手去干别的；DMAC 接管总线（成为"总线主设备 / bus master"）把整块数据搬完，**只在整块传完时才产生一次中断**通知 CPU。于是一兆字节的传输从"几十万次中断/逐字节搬"变成"一次启动 + 一次完成中断"，CPU 几乎不参与。

上面 `/proc/interrupts` 里的 `virtio0`、`virtio9` 这类 PCI 设备正是走 DMA 搬数据、用 MSI-X 中断报告完成的现代设备（本机为虚拟化 virtio 设备）。

DMA 带来一个必须点明的经典陷阱——**cache 一致性**。DMAC 直接读写的是**主存**，而 CPU 手里可能握着这块内存的 cache 副本：设备 DMA 写入主存后，CPU 若从 cache 读会读到旧数据；CPU 若有脏 cache 行还没写回主存，DMAC 从主存读又会读到旧数据。解决办法要么由硬件保证 DMA 与 cache 一致（cache-coherent DMA），要么由软件在 DMA 前后**刷新/失效相应 cache 行**。这与 7.1.3 的 MMIO 可缓存性问题同源：只要"CPU 之外的东西也能改内存/寄存器"，cache 这层就必须额外照顾。

### 7.2.4 三者权衡：为什么按"轮询→中断→DMA"依次出现

把三种方式并排，就能看清它们不是互相取代、而是各占一段"设备速度 × 数据量"的地形：

    方式      CPU 参与度              每次传送开销        最适场景
    轮询      全程忙等，最高          最低（无中断）      设备极快且频繁 / 极简系统
    中断驱动  仅就绪时被打断          中（中断进出开销）  设备慢或事件稀疏、CPU 有别的事做
    DMA       仅启动+完成两点         最低（整块一次中断）大块数据传输（磁盘/网络/显卡）

一条主线记住全部：**外设远慢于 CPU，而 CPU 每一次参与都要花代价**，所以历史沿着"减少 CPU 参与"演进——轮询让 CPU 全程空转（浪费最大），中断把 CPU 从"空转等待"里解放（但每字节一次中断在大数据量下又太碎），DMA 把 CPU 从"逐字节搬运"里彻底解放（只管头尾）。这就是三者"为什么依次出现"的直觉。易错点：DMA 并非永远最优——传输量很小时，启动 DMA 的开销可能比 CPU 直接搬几个字节还大，所以小传输仍常用 CPU 直接搬（programmed I/O）。三者在真实系统里长期并存、按场景取舍。

## 7.3 总线特性：带宽/延迟、同步/异步、仲裁

### 7.3.1 总线基本概念与"共享并行 → 点对点串行"的转变

总线（bus）是连接 CPU、内存、I/O 设备的**一组共享通信线路**，传统上分三类信号：**地址线**（说访问哪里）、**数据线**（搬运数据本身）、**控制线**（读/写、时钟、就绪、中断、仲裁等信号）。经典教科书里的总线是"一条大家共用的并行公路"，所有设备挂在同一组线上分时使用。

但要立刻建立一个时效认知：**现代高速互连已基本抛弃"共享并行总线"，转向点对点串行链路**。原因是并行总线在高频下受**时钟偏斜（skew）**和信号串扰限制——几十根线要同时到达、彼此干扰，频率越高越难做宽。串行链路（如 PCI Express）改用少数几对差分线、极高频率、点对点连接，再用多条独立"lane"并联扩带宽，绕开了并行总线的物理瓶颈。所以"总线"这个词今天更多是逻辑概念（PCIe 拓扑仍叫"PCI bus"编号），物理实现已是串行点对点。初学者读老教材的"共享总线仲裁"时要知道：那套模型对理解原理仍有效，但当代实现多是交换式点对点。

### 7.3.2 带宽与延迟

评价一条互连的两个基本指标是**带宽（bandwidth，单位时间搬多少数据）**和**延迟（latency，一次传输从发起到完成的时间）**。对一条并行同步总线，理论峰值带宽是宽度乘以传输速率：

    总线带宽 = 总线宽度（字节/次） × 传输速率（次/秒）

举例：一条 8 字节宽、每秒 10 亿次传输（1 GT/s）的总线，峰值带宽为

    8 字节 × 1×10⁹ 次/秒 = 8 GB/s（此处 1 GB = 10⁹ 字节）

对现代串行链路 PCIe，带宽换算要计入**编码开销**。以 PCIe 5.0 为例，每 lane 原始速率 32 GT/s，采用 128b/130b 编码（每 130 位里 128 位是有效数据），单 lane 单向有效带宽约：

    32 × 10⁹ 次/秒 × (128/130) ÷ 8 ≈ 3.94 GB/s ≈ 4 GB/s 每 lane

    x16（16 lane）单向 ≈ 16 × 3.94 ≈ 63 GB/s

（PCIe 数值演进快，此处锚 PCIe 5.0 / 核实 2026-07-26；不同代际每 lane 速率翻倍：4.0 为 16 GT/s、5.0 为 32 GT/s、6.0 为 64 GT/s。）延迟与带宽是**两个独立维度**，初学者常混：带宽是"公路多宽"（吞吐），延迟是"跑一趟多久"（响应）。大文件传输在意带宽，小而频繁的控制访问在意延迟——DMA 大块传输优化的是带宽利用率，而访问 MMIO 控制寄存器在意的是延迟。

### 7.3.3 同步总线 vs 异步总线

按"用不用公共时钟"，总线分两类。**同步总线**上所有设备共享一根**总线时钟**，所有事件在时钟边沿发生，协议简单、速度快，但因为要求全体设备在同一时钟节拍内响应，**总线不能太长、挂的设备速度差异不能太大**（慢设备会拖累时钟频率）。**异步总线**没有公共时钟，改用**握手协议（handshake）**：主设备发出请求信号，从设备准备好后回一个应答信号，双方靠"请求—应答"你来我往推进。异步总线能兼容**速度差异极大的设备**、可以做得更长，代价是握手往返带来额外延迟、协议更复杂、通常更慢。

一个最小的四步握手直觉（异步读）：

    1. 主设备放好地址，拉高 ReadReq（请求）
    2. 从设备看到请求，取好数据放上数据线，拉高 Ack（应答）
    3. 主设备看到 Ack，取走数据，撤销 ReadReq
    4. 从设备看到请求撤销，撤销 Ack —— 一次传输完成

为什么需要两种？同步适合**短距离、同构、高速**的场合（如 CPU 到内存的处理器总线）；异步适合**要挂各种快慢不一设备**的场合（传统 I/O 总线）。易错点：不要把"同步"理解成"更先进"——它只是在设备同构、距离短时更快；面对异构慢设备，异步的灵活兼容才是刚需。现代高速串行链路则用**嵌入式时钟**（时钟信息编码进数据流，接收端时钟恢复），兼取两者之长，已超出经典"同步/异步"二分。

### 7.3.4 总线仲裁

当**多个设备都想当主设备（bus master）占用总线**时（例如多个 DMA 控制器、多个 CPU），必须有**仲裁（arbitration）**机制决定"谁先用"，避免多方同时驱动总线造成冲突。仲裁要在两个目标间平衡：**优先级**（让紧急/高速设备优先）和**公平性**（别让低优先级设备被永远饿死 starvation）。

常见方案分两大类：

    集中式仲裁（有一个总线仲裁器）：
      - 菊花链（daisy chain）：授权信号串行地一级级往下传，靠物理位置定优先级；
        线最少、最简单，但离仲裁器越远优先级越低、且可能饿死远端设备。
      - 集中并行仲裁：每个设备有独立的请求线和授权线，仲裁器统一裁决；
        快、灵活，但线数随设备数增长。
    分布式仲裁（无单一仲裁器）：
      - 各设备按约定协议（如自比较标识符）自行协商谁获胜；无单点瓶颈，扩展性好。

理解仲裁的关键是记住它只在**"总线是共享资源、有多个潜在主设备"时才需要**。这也说明为什么它在经典共享总线时代是核心话题，而在点对点串行链路（每条链路只连两端、由交换机集中调度）时代，传统的总线仲裁被交换式的流控/调度取代，重要性下降。菊花链的"越远越吃亏且可能饿死"是最爱考的易错点：它用最少的线换来了最不公平的优先级。

## 7.4 存储可靠性：RAID 级别、纠错与冗余

### 7.4.1 可靠性度量：MTTF / MTTR / MTBF 与可用性

在谈冗余之前先要有度量。**MTTF（Mean Time To Failure，平均无故障时间）**是一个部件从开始工作到发生故障的平均时长；**MTTR（Mean Time To Repair，平均修复时间）**是故障后修好的平均时长；两者相加是**MTBF（Mean Time Between Failures，平均故障间隔时间）**：

    MTBF = MTTF + MTTR

而系统**可用性（availability）**——长期看有多大比例的时间在正常服务——为：

    可用性 = MTTF ÷ (MTTF + MTTR)

这几个量给"可靠性"一个可算的抓手。直觉例子：一块盘 MTTF 是 100 万小时（约 114 年），听起来固若金汤；但数据中心里放 1000 块盘，整个盘阵的"平均多久坏一块"约为 100 万 ÷ 1000 = 1000 小时（约 42 天）——**规模一大，故障就从"罕见"变成"日常"**。这正是为什么大规模存储必须假设"盘一定会坏"，进而用冗余（RAID）来保证坏盘时不丢数据、并缩短 MTTR（快速重建）以拉高可用性。可用性常用"几个 9"表示：99.9%（三个 9）约等于每年停机 8.76 小时。

### 7.4.2 纠错与冗余的基础：奇偶校验与 ECC（Hamming SEC-DED）

在整盘冗余（RAID）之外，更细粒度的可靠性手段是**纠错码（ECC, Error-Correcting Code）**，主要用于内存和存储介质，靠"多存一点冗余位"来发现甚至纠正位翻转。最简单的是**奇偶校验位（parity）**：给一组数据位加 1 个校验位，使总的 1 的个数为偶（或奇）——它能**检出 1 位错误**（single-error detection），但既不能定位也不能纠正，2 位错误还会漏检。

更强的是**汉明码（Hamming code）**，通过多个校验位覆盖不同的数据位子集，使校验结果（syndrome）能**定位**出错位并翻转纠正。要纠正单比特错，校验位数 p 与数据位数 d 需满足：

    2^p ≥ p + d + 1

内存里常用的是**SEC-DED（Single Error Correct, Double Error Detect）**：在汉明码基础上再加一个总校验位，做到**纠 1 位、检 2 位**。这就是服务器"ECC 内存"的核心。直觉：奇偶校验像"只告诉你这行字里有个错别字但不知在哪"，汉明码像"告诉你第几个字错了、直接改对"，SEC-DED 再加一层"两个错别字时至少能报警别装作没事"。要点：ECC 保护的是**位级**随机翻转（宇宙射线、电噪声等），而 RAID 保护的是**整块盘**级失效，两者层级不同、互补使用。

### 7.4.3 RAID 级别：0 / 1 / 5 / 6 / 10

**RAID（Redundant Array of Independent/Inexpensive Disks，独立磁盘冗余阵列）**用多块普通盘组成一个逻辑卷，通过**条带化（striping，把数据切片分散到多盘以提性能）**和**冗余（镜像或校验，以容错）**的不同组合，得到不同的性能/容量/容错权衡。设阵列共 n 块等容量盘，常见级别如下（容量与最少盘数为比对通过的公认定义）：

    级别    机制                    最少盘   可用容量      容错能力
    RAID 0  纯条带、无冗余          2       n（100%）     0（坏任一块即全丢）
    RAID 1  镜像（每份存两块）      2       n/2（50%）    可坏到只剩 1 块镜像
    RAID 5  条带 + 单份分布式校验   3       n−1          可坏 1 块
    RAID 6  条带 + 双份分布式校验   4       n−2          可坏 2 块
    RAID 10 先镜像再条带（1+0）     4       n/2（50%）    每个镜像对各可坏 1 块

逐条直觉：**RAID 0** 只为速度和容量，把数据摊到多盘并行读写，毫无保护——一块坏全完，严格说它不算"冗余"阵列。**RAID 1** 最简单粗暴的冗余：数据同时写两块，坏一块另一块顶上，代价是一半容量拿去做镜像。**RAID 5** 是经典折中：n 块盘里数据 + 1 块盘容量的**校验（用异或算出）**分散存在各盘上，坏任意 1 块可由其余盘异或重算恢复，容量利用率 (n−1)/n 比镜像高得多。**RAID 6** 在 RAID 5 基础上再加一份独立校验，能扛**同时坏 2 块**。**RAID 10** 把 RAID 1 和 RAID 0 叠加——先两两镜像再条带化，兼得镜像的高容错/快重建与条带的高性能，代价同样是 50% 容量。历史锚点：1988 年 Patterson/Gibson/Katz 的原始论文定义了 **RAID 1–5**；RAID 0（无冗余条带）和 RAID 6（双校验）是后来业界补充/形式化的，原论文并未包含——这点常被误传，需注意。

### 7.4.4 RAID 的权衡与陷阱：写惩罚与重建窗口

RAID 不是"越高级越好"，有两个必须讲透的实战陷阱。

第一，**校验 RAID 的写惩罚（write penalty）**。RAID 5 每改一小块数据，为维持校验正确，通常要"读旧数据 + 读旧校验 + 写新数据 + 写新校验"——一次逻辑小写变成多次物理读写，随机小写性能显著下降；RAID 6 有两份校验，写惩罚更重。这就是为什么随机写密集的负载（如数据库）有时宁可用 RAID 10（写只需同时更新镜像两块，无校验计算）。

第二，**重建窗口与"第二块盘"风险**。RAID 5 坏一块后进入"降级（degraded）"状态，此时必须读**其余所有盘**来重算恢复坏盘数据，大容量盘重建可能耗时数小时到数天；在这段**重建窗口**里，只要**再坏第二块盘**，数据就彻底丢失。盘容量越大、重建越久，窗口内二次故障概率越高——这正是 RAID 6（可扛 2 块）在大容量盘时代取代 RAID 5 的直接动因。核心澄清（最爱考的误区）：**RAID 不是备份**。它防的是"硬件盘失效"，但对误删、勒索软件、文件系统损坏这类**逻辑错误**毫无保护——错误会同步写进所有冗余副本。可靠存储既要 RAID（防硬件坏），也要独立备份（防逻辑错）。
