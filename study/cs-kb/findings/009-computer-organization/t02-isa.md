## 2.1 寄存器模型与操作数

### 2.1.1 32 个通用寄存器与位宽

RISC-V 的整数寄存器堆有 **32 个通用寄存器**，命名为 x0–x31，每个寄存器宽 XLEN 位；RV32 中 XLEN = 32（RV64 中为 64）。程序里所有整数算术直接对这些寄存器操作，寄存器堆是 CPU 内部速度最快、离 ALU 最近的一小块存储。

初学者可以把这 32 个寄存器想成"CPU 手边的 32 个抽屉"：内存像仓库，容量大但取用慢；寄存器像手边抽屉，只有 32 个，但取用几乎不花时间。程序运行时最活跃的那几个变量就被编译器放进这些抽屉里反复用。

为什么偏偏是 32 个、而不是 8 个或 128 个？这是一个折中：寄存器越多，能同时"摊在手边"的变量越多、越少往内存跑；但寄存器编号要写进指令，32 个正好用 5 位二进制编号（2^5 = 32），这个 5 位字段在下面每种指令格式里都固定占同样的位置，译码简单。抽屉再多，编号字段就要变宽，指令里留给其它信息的位就变少。

### 2.1.2 x0 恒零寄存器

x0 是一个特殊寄存器：它**永远读出 0**，任何对它的写入都被丢弃。它不是"初始值为 0"，而是硬连线（hardwired）为 0，无法改变。

这个设计看似浪费了一个抽屉，实则极其划算，因为它让一条指令能顶多条用。举例：

```
把 x5 清零：      addi x5, x0, 0     （x0 + 0 → x5）
把常数搬进寄存器： addi x5, x0, 42    （x0 + 42 → x5）
无条件跳转：      beq  x0, x0, 标号   （x0 == x0 恒真）
丢弃返回地址的跳转：jal  x0, 标号      （返回地址写进 x0 即丢弃）
```

也就是说，RISC-V 没有专门的"清零指令""传送常数指令""无条件分支指令"，全靠 x0 这一个恒零寄存器和现有指令组合出来——这正是精简指令集"少造专用指令、多做正交组合"的典型手法（见 2.6）。

易错点：x0 不能当普通变量用，写进去的值立刻蒸发；初学者若把中间结果暂存到 x0，会发现值永远是 0。

### 2.1.3 寄存器的 ABI 名与角色约定

除了 x0–x31 这套硬件编号，RISC-V 还有一套按**用途**取的助记名（ABI 名，Application Binary Interface）。硬件只认编号；ABI 名是软件层面的约定，让汇编可读、并规定每个寄存器在函数调用里扮演什么角色。核心对应关系：

```
x0        zero    恒零
x1        ra      返回地址（return address）
x2        sp      栈指针（stack pointer）
x3        gp      全局指针      x4  tp  线程指针
x5–x7     t0–t2   临时寄存器（调用者保存）
x8        s0/fp   保存寄存器 / 帧指针（被调用者保存）
x9        s1      保存寄存器（被调用者保存）
x10–x11   a0–a1   参数 / 返回值
x12–x17   a2–a7   参数
x18–x27   s2–s11  保存寄存器（被调用者保存）
x28–x31   t3–t6   临时寄存器（调用者保存）
```

初学者常疑惑"同一个物理寄存器为什么要两个名字"。硬件编号（x10）是机器码里真正写的东西；ABI 名（a0）是给人和编译器看的角色标签。二者一一对应，`a0` 和 `x10` 指的是同一个寄存器。这套角色划分（谁负责在调用前后保住谁）是过程调用约定的地基，具体规则见 2.4；这里先建立"寄存器不只是编号、还带约定角色"的意识。

时效提醒：上表的 ABI 名与角色来自 RISC-V psABI/调用约定规范，与 COD ch2 一致；它是**软件约定**而非硬件强制——硬件层面 x1 和 x5 没有区别，是约定让 x1 当返回地址。

### 2.1.4 load-store 架构与操作数约束

RISC-V 是**load-store（访存-运算分离）架构**：算术/逻辑指令的操作数只能是**寄存器或指令内立即数**，**不能直接是内存**；内存数据必须先用 load 指令搬进寄存器、算完再用 store 指令写回。典型算术指令是三操作数形式：

```
add  rd, rs1, rs2     # rd ← rs1 + rs2   （两源寄存器，一目标寄存器）
addi rd, rs1, 立即数   # rd ← rs1 + 立即数
```

直觉上这像"必须先把仓库里的货搬到工作台，才能加工"。为什么不允许"直接加工仓库里的货"（即算术指令带内存操作数，CISC 常这么做）？因为访存慢且时延不定，把访存和运算强行分开，能让每条运算指令的执行时间整齐可预测，硬件流水线好切分（为大主题5 流水线埋线）；代价是同样一段逻辑要多用几条 load/store 指令，指令条数（IC）偏多——这正是 RISC 的核心取舍（见 2.6）。

易错点：初学者常写出"把内存里两个数直接相加"这种一步到位的指令，在 RISC-V 里不存在；必须 `lw` 两次、`add` 一次、`sw` 一次。另外 `add` 与 `addi` 是两条不同指令：前者第二个源是寄存器，后者是立即数，编码格式都不同（见 2.2）。

## 2.2 指令格式编码

### 2.2.1 定长 32 位与固定字段位置

RV32I 基础指令一律是**定长 32 位**、按 4 字节对齐存放。译码时最关键的字段——**寄存器号（rd/rs1/rs2）永远落在同一批位置**，无论哪种格式。整条指令的通用位段划分（以位 31 为最高位、位 0 为最低位）：

```
位:   31        25 24   20 19   15 14  12 11    7 6      0
     [  funct7  ][ rs2 ][ rs1 ][funct3][  rd  ][opcode ]
       7 位       5 位    5 位   3 位    5 位     7 位
```

关键约定：**opcode 固定在最低 7 位 [6:0]**；**rd 固定在 [11:7]**；**funct3 固定在 [14:12]**；**rs1 固定在 [19:15]**；**rs2 固定在 [24:20]**；**funct7 固定在 [31:25]**。

为什么把寄存器号钉死在固定位置？因为"读寄存器堆"往往在关键路径上——CPU 想尽早知道要读哪两个寄存器。若寄存器号在不同格式里到处跑，硬件就得先判断格式、再挑位置，白白拖慢；钉死位置后，硬件可以在还没完全译码时就抢先把 rs1/rs2 送去读寄存器堆。代价是**立即数字段被迫让路、拆得七零八落**（见 2.2.3），但立即数不在最紧的关键路径上，这个代价划算。

易错点：opcode 只有 7 位、看似只能区分 128 类指令，但 RISC-V 用 opcode + funct3 + funct7 三级配合来区分具体操作（见 2.2.4），实际可编码的指令远多于 128 条。

### 2.2.2 六型格式：R / I / S / B / U / J

RV32I 的指令按操作数来源分成**六种格式**。前四种（R/I/S/U）是核心格式，B、J 是为分支/跳转立即数专门变体（见 2.2.3）。各格式的字段布局：

```
位:    31        25 24  20 19  15 14 12 11   7 6    0
R型:  [ funct7   ][ rs2 ][ rs1 ][f3][   rd   ][opcode]   寄存器-寄存器运算(add/sub/and…)
I型:  [   imm[11:0]     ][ rs1 ][f3][   rd   ][opcode]   立即数运算/加载/jalr(addi/lw/jalr)
S型:  [imm[11:5]][ rs2 ][ rs1 ][f3][imm[4:0]][opcode]   存储(sw/sh/sb)
B型:  [imm12|imm10:5][rs2][rs1][f3][imm4:1|11][opcode]   条件分支(beq/bne…)
U型:  [        imm[31:12]      ][   rd   ][opcode]        高位立即数(lui/auipc)
J型:  [ imm[20|10:1|11|19:12] ][   rd   ][opcode]        跳转(jal)
```

怎么记住哪种格式对应哪类指令？按"操作数里有几个寄存器、要不要立即数"来记：

- R 型：两个源寄存器 + 一个目标，无立即数——纯寄存器运算（`add x5, x6, x7`）。
- I 型：一个源寄存器 + 一个 12 位立即数 + 目标——立即数运算（`addi`）、加载（`lw`，地址 = 基址寄存器 + 立即偏移）、`jalr`。
- S 型：两个源寄存器（要存的值 + 基址）+ 立即偏移，无目标寄存器——存储（`sw`）。因为要存的数据也在寄存器里，且没有结果写回寄存器，所以立即数被拆成两段给 rd 的位置让路。
- B 型：像 S 型但立即数当分支偏移用（见 2.5）。
- U 型：一个 20 位大立即数 + 目标——`lui`（把 20 位立即数放到高位）。
- J 型：像 U 型但立即数当跳转偏移用——`jal`。

易错点：S 型和 B 型"没有 rd"是初学者常忽略的点——存储和分支都不往寄存器写结果，所以那 5 位 [11:7] 被拿去放立即数了。这也解释了为什么它们的立即数看起来被"劈成两半"。

### 2.2.3 立即数为何被打散：sign bit 恒在 inst[31]

I/S/B/U/J 五种带立即数的格式里，**立即数在指令里的排布是被打散、甚至次序颠倒的**。规范用 Figure 2.4 精确规定了"指令的第几位产生立即数的第几位"（下表 inst[y] 表示指令第 y 位，产生的立即数按 imm 下标对齐）：

```
产生立即数位:  31   30:20    19:12   11    10:5     4:1    0
I-立即数:     inst31 ←31复制→          inst30:25  inst24:21 inst20
S-立即数:     inst31 ←31复制→          inst30:25  inst11:8  inst7
B-立即数:     inst31 ←31复制→   inst7  inst30:25  inst11:8   0
U-立即数:     inst31 inst30:20 inst19:12          ← 低12位全 0 →
J-立即数:     inst31 ←31复制→   inst19:12 inst20 inst30:25 inst24:21 0
```

两条贯穿全表的规律最值得记：

第一，**所有立即数的符号位永远取自指令的第 31 位（inst[31]）**，且高位由它符号扩展。这样硬件一拿到 32 位指令，不必等译码完就能启动符号扩展电路——符号扩展与译码并行进行，省时间。

第二，**中间那些立即数位在不同格式里尽量保持在同一指令位置**（比如 imm[10:5] 几乎都来自 inst[30:25]）。这样"从指令里抽立即数"的接线在各格式间大量复用，硬件的多路选择器和信号扇出成本几乎减半。

代价就是 B 型、J 型的立即数看起来是"乱序拼装"的（imm 的高位、低位分散在指令各处，还整体左移 1 位表示"偏移是 2 的倍数"，见 2.5）。这对编译器是一次性的静态拼装、几乎不增加成本；对读机器码的人则是一道坎——**手工重组 B/J 立即数是本主题最易出错处**，务必按上表逐位对齐，别凭直觉顺读。

### 2.2.4 opcode / funct3 / funct7 三级译码

一条指令"到底做什么"由三个字段逐级细分决定：**opcode（[6:0]）**定大类，**funct3（[14:12]）**在大类里分小类，**funct7（[31:25]）**在 R 型里再区分同一 funct3 下的不同操作。RV32I 部分实际取值（来自规范 opcode 映射表）：

```
LUI    opcode 0110111
AUIPC  opcode 0010111
JAL    opcode 1101111
JALR   opcode 1100111  funct3 000
分支   opcode 1100011  funct3: 000 BEQ / 001 BNE / 100 BLT / 101 BGE / 110 BLTU / 111 BGEU
加载   opcode 0000011  funct3: 000 LB / 001 LH / 010 LW / 100 LBU / 101 LHU
存储   opcode 0100011  funct3: 000 SB / 001 SH / 010 SW
立即运算 opcode 0010011 funct3: 000 ADDI / 010 SLTI / 100 XORI / 110 ORI / 111 ANDI …
寄存器运算 opcode 0110011 funct3 000: funct7 0000000=ADD / 0100000=SUB
```

直觉：这像图书馆的三级索引——opcode 是"哪个书架"（运算类 / 加载类 / 分支类），funct3 是"这一架的第几层"（是加法还是异或、是相等分支还是小于分支），funct7 是"同一层里的哪本书"（同为 funct3=000 的寄存器运算，靠 funct7 区分 ADD 与 SUB）。

一个关键例子：**ADD 与 SUB 的 opcode 和 funct3 完全相同（0110011 / 000），只差 funct7 的一位**（ADD 是 0000000，SUB 是 0100000，即 inst[30] 那位）。这也是为什么加减法在硬件上能共用一个加法器，靠一个控制位切换是否对第二操作数取补——ISA 编码上就把它们摆在了"只差一位"的相邻位置。

易错点：不要把 opcode 单独当成"指令名"；同一个 opcode（如 0110011）下藏着 ADD/SUB/AND/OR/XOR/SLL/SLT… 一大批指令，必须连 funct3、funct7 一起看才能确定是哪条。

### 2.2.5 手工编码一个例子

把上面的字段表用一次，就能把一条汇编指令拼成 32 位机器码。以 `addi x15, x1, 12`（把 x1 加 12 写入 x15）为例。它是 I 型：imm[11:0]=12、rs1=x1、funct3=000、rd=x15、opcode=0010011。逐字段填入 I 型布局：

```
imm[11:0]      rs1    funct3  rd     opcode
000000001100   00001  000     01111  0010011
= 0000 0000 1100 0000 1000 0111 1001 0011
= 0x00C08793
```

再看一条 R 型 `add x5, x6, x7`：funct7=0000000、rs2=x7、rs1=x6、funct3=000、rd=x5、opcode=0110011：

```
0000000 00111 00110 000 00101 0110011  =  0x007302B3
```

这两个十六进制值由字段表按位拼出、并在本机 Python 上做过"二进制串→十六进制"的算术核对（确定性换算，非反汇编器输出）。它的意义是让你亲手体会：**机器码不神秘，它就是把"操作 + 寄存器号 + 立即数"按固定位段拼起来的一串 0/1**。分支/跳转的立即数因为要重组、更麻烦，单独放到 2.5 讲。

易错点：填 rd/rs1 时要填**寄存器编号的 5 位二进制**（x15 → 01111，x1 → 00001），不是十进制数字本身；立即数要按补码填满 12 位（正数高位补 0，负数补 1）。

## 2.3 寻址与内存访问

### 2.3.1 寻址模式：立即 / 寄存器 / 基址+偏移 / PC 相对

RISC-V 只用极少的几种寻址方式取操作数，教材通常归纳为：**立即数寻址**（操作数就在指令的立即数字段里）、**寄存器寻址**（操作数在寄存器里）、**基址+偏移寻址**（内存地址 = 某寄存器的值 + 指令里的立即偏移，用于 load/store）、**PC 相对寻址**（分支/跳转目标 = PC + 立即偏移，见 2.5）。访存地址的计算式：

```
有效地址 = 基址寄存器(rs1) 的值 + 符号扩展(12 位立即偏移)
```

初学者可以把"基址+偏移"想成"门牌号 = 这条街的起点（基址寄存器）+ 往前第几户（偏移）"。这套方式天然适配数组和结构体：基址寄存器存数组首地址，偏移取常量就能访问第 i 个元素或结构体的某个成员。

为什么 RISC-V 的寻址方式这么少（相比 x86 动辄十几种）？还是精简取向：寻址方式越少，译码和地址计算硬件越简单、越快；复杂的访问模式交给编译器用几条简单指令拼出来。这与 load-store 架构（2.1.4）是一套设计哲学。

### 2.3.2 load / store 指令与数据尺寸

内存与寄存器之间搬数据只靠两类指令：**load（内存→寄存器）**和 **store（寄存器→内存）**。按搬运的数据宽度还分字节/半字/字：

```
加载(I 型): lb/lbu(1 字节) lh/lhu(2 字节) lw(4 字节)     RV64 另有 ld(8 字节)
存储(S 型): sb(1 字节)     sh(2 字节)     sw(4 字节)      RV64 另有 sd
写法:  lw x5, 8(x6)     # x5 ← 内存[x6 + 8]
       sw x5, 8(x6)     # 内存[x6 + 8] ← x5
```

后缀 `b/h/w` 是宽度（byte/halfword/word）；加载里带 `u` 的（lbu/lhu）做**零扩展**、不带 `u` 的（lb/lh）做**符号扩展**——因为从内存取出的窄数据要填满整个寄存器，得决定高位补 0 还是补符号位。存储没有 u 变体，因为存储是把寄存器低位写进内存、不涉及扩展。

易错点：`lw x5, 8(x6)` 里的 8 是**字节偏移**不是元素下标；访问 `int` 数组第 2 个元素（每个 4 字节）偏移是 8 而不是 2。另外 load 是 I 型、store 是 S 型（2.2.2），因为 store 要同时给出"存哪个寄存器的值"和"基址寄存器"两个源、且无结果写回，所以立即数被劈成两段。

### 2.3.3 字节序：大端与小端

一个多字节数据（如 4 字节的字）在内存里按地址从低到高怎么摆放，叫**字节序（endianness）**。两种约定：

```
以 32 位值 0x01234567 存到地址 A 起：
小端(little-endian): 地址A=0x67 A+1=0x45 A+2=0x23 A+3=0x01  （低位字节在低地址）
大端(big-endian):    地址A=0x01 A+1=0x23 A+2=0x45 A+3=0x67  （高位字节在低地址）
```

RISC-V 基础 ISA **默认小端**（本机 x86-64 也是小端）。记忆窍门：小端 = "小的（低位字节）住小地址"。

字节序只在"把多字节对象当成一串字节来看"（比如网络传输、`memcpy`、类型双关）时才暴露出来；日常用 `lw` 整字读写时你感觉不到它。规范与实现分账：RISC-V 后续版本也定义了大端/双端变体，但教学与主流实现用小端；本报告按小端讲。易错点是跨机器传二进制数据时两端字节序不同会读出乱序值，网络协议因此约定统一用大端（"网络字节序"）。

### 2.3.4 对齐

**对齐（alignment）**指访问一个 N 字节数据时，其地址最好是 N 的整数倍（4 字节的字放在地址能被 4 整除处，2 字节半字放在偶地址）。自然对齐的访问，硬件一次就能取到，且规范保证其原子性。

RISC-V 规范对**数据访问**是否允许非对齐，采取"规范允许、实现可选"的态度：基础 ISA 在语义上支持非对齐 load/store，但**具体实现可以选择不支持而触发异常、或支持但很慢**——这是典型的规范 vs 实现分账，写可移植代码时不能假设非对齐访问一定又快又合法。而**指令本身**必须 4 字节对齐（RV32I），跳转到非 4 字节对齐的目标会触发取指非对齐异常。

初学者直觉：把数据想成必须整格摆进方格纸——4 字节的数据横跨两个"4 字节格"时，硬件可能要取两次再拼起来，慢且未必被支持。所以编译器默认把 `int` 放在 4 字节对齐处、结构体成员之间插入填充（padding）来维持对齐。易错点：手工强制把结构体"压紧"（去掉 padding）在某些平台上会导致非对齐访问变慢甚至崩溃。

## 2.4 过程调用约定

### 2.4.1 jal / jalr 与返回地址

函数调用要解决两件事：跳到被调函数、并记住"回来的地方"。RISC-V 用两条指令：

```
jal  rd, 标号     # 跳转并链接：rd ← 返回地址(下一条指令地址 PC+4)，PC ← PC + 偏移
jalr rd, rs1, 立即 # 跳转并链接寄存器：rd ← PC+4，PC ← (rs1 + 立即) 且末位清 0
```

约定用 **ra（x1）**装返回地址：`jal ra, 函数` 调用函数，被调函数干完用 `jalr x0, ra, 0`（常写作伪指令 `ret`）跳回 ra 存的地址。注意目标寄存器 rd 写成 x0 时返回地址被丢弃（2.1.2），用于纯粹的无条件跳转。

初学者直觉：`jal` 像"出发时在门口贴张便利贴写好回家的地址（存进 ra），然后出发"；`ret` 就是照便利贴回家。为什么需要 `jalr`（用寄存器给目标）？因为有些跳转目标要到运行时才知道——函数指针、返回、跳转表都用 `jalr`。而 `jal` 的目标是编译期已知的固定偏移。

易错点：如果被调函数内部又调别的函数，第二次 `jal ra, …` 会**覆盖 ra**，第一层的返回地址就丢了。所以非叶函数必须先把 ra 存到栈上（见 2.4.4），这是初学者写递归汇编最常见的崩溃原因。

### 2.4.2 参数与返回值寄存器

调用约定规定参数和返回值走哪些寄存器：**前 8 个整型参数用 a0–a7（x10–x17）**，超出的参数压栈传递；**返回值用 a0（需要两个字时用 a0、a1）**。

直觉：a0–a7 是调用双方约好的"传话窗口"——调用者把参数摆进 a0、a1…，被调者就知道去这些寄存器取；算完把结果摆回 a0，调用者去 a0 取。之所以用寄存器而非栈传前几个参数，是因为寄存器快、且多数函数参数不多，能全放进寄存器就省去访存。

易错点：只有前 8 个整型参数走寄存器，第 9 个起要压栈；浮点参数走另一组浮点寄存器（属浮点扩展，不在本报告 RV32I 范围内）。返回多于两个字的结构体时另有规则（通过隐藏指针），入门先掌握"参数 a0–a7、返回 a0/a1"即可。

### 2.4.3 调用者保存 vs 被调用者保存

一次调用会用到很多寄存器，双方必须约好"谁负责保住谁的值"，否则被调函数可能踩坏调用者还要用的数据。RISC-V 把寄存器分两类：

```
调用者保存(caller-saved, 又称 temporary): t0–t6, a0–a7, ra
  —— 被调函数可随意改写；调用者若在调用后还要用它们，得自己在调用前存好
被调用者保存(callee-saved, 又称 saved):   s0–s11, sp
  —— 被调函数若要用它们，必须先存、返回前恢复原值；调用者可放心它们跨调用不变
```

用一个比喻：借用别人的房间（调用一个函数）。**callee-saved（s 寄存器）**像"房主要求：你可以用这些抽屉，但离开时必须原样放回"——所以调用者不必操心，跨调用后 s 寄存器还是原值。**caller-saved（t / a 寄存器）**像"这些抽屉随便用、不保证归位"——所以调用者如果调用后还要用里面的东西，得自己在调用前抄一份走。

这套划分的意义是**减少不必要的保存**：如果一个值在调用后就不再用，放 t 寄存器里，谁都不用存它；如果要跨很多次调用长期存活，放 s 寄存器里存一次就够。编译器据此分配寄存器以尽量少往栈上倒腾。易错点：初学者常忘记——非叶函数里若用了 s 寄存器，必须在序言里存、尾声里恢复（下条）；ra 属 caller-saved，非叶函数也必须自己存 ra。

### 2.4.4 栈帧与序言 / 尾声

**栈（stack）**是内存里一块专门存放函数局部数据的区域，由 **sp（x2）**指向栈顶。RISC-V 约定**栈向低地址方向增长**：压栈时 sp 减小，出栈时 sp 增大。每次函数调用为自己分配的一块栈空间叫**栈帧（stack frame）**，存放：要保存的 ra、被用到的 s 寄存器、放不进寄存器的局部变量、以及第 9 个起的参数。

一个非叶函数的典型骨架：

```
序言(prologue):  addi sp, sp, -16     # 开辟 16 字节栈帧（sp 下移）
                 sw   ra, 12(sp)      # 保存返回地址
                 sw   s0, 8(sp)       # 保存要用的 callee-saved 寄存器
   ……函数体（可再调用别的函数，此时 ra 已安全存于栈上）……
尾声(epilogue):  lw   s0, 8(sp)       # 恢复 s0
                 lw   ra, 12(sp)      # 恢复返回地址
                 addi sp, sp, 16      # 释放栈帧（sp 回到原处）
                 jalr x0, ra, 0       # ret：跳回 ra
```

直觉：栈帧像"每层调用各拿一张便签纸，摞成一叠（栈）"——第 n 层调用摞上去、返回时揭掉最上面那张，恰好后进先出。递归之所以能工作，就是每次递归调用都摞一张新便签（新栈帧），各层的局部变量、返回地址互不干扰。

易错点：(1) 序言里 sp 减多少、尾声必须加回同样多，否则栈"漏了"，返回后调用者的栈被错位；(2) 叶函数（不再调别人）若不改 s 寄存器、不需要保存，可以不建栈帧，直接 `ret`；(3) sp 在调用点通常还要满足对齐要求（psABI 规定 16 字节对齐），入门先理解"存 ra + 平衡 sp"这条主线。

## 2.5 分支与跳转编码

### 2.5.1 PC 相对寻址

分支和跳转的目标地址不是绝对地址，而是**相对当前 PC（程序计数器）的偏移**：目标 = PC + 符号扩展偏移。条件分支（B 型）和 `jal`（J 型）都用这种 PC 相对寻址。

```
分支目标地址 = 当前指令 PC + 符号扩展(立即偏移)
```

为什么用相对而非绝对地址？两个原因。其一，**位置无关**：整段代码被加载到内存哪个位置，内部的相对跳转都不用改，便于共享库和重定位。其二，**省编码位**：绝对地址要 32 位，而绝大多数分支目标离当前指令很近（循环、if 就在附近），用一个十几位的有符号偏移就够，省下的位留给别的字段。

直觉：相对寻址像"往前走 20 步"而非"去 3 号大街 100 号"——不管你现在站哪，"往前 20 步"都成立。易错点：偏移是从**当前分支指令的 PC**算起（RISC-V 如此定义），不是从下一条指令算；手工算目标地址时基准要选对。

### 2.5.2 条件分支：比较即分支，无条件码

RISC-V 的条件分支**把"比较"和"跳转"合并在一条指令里**，直接比较两个寄存器再决定跳不跳，不依赖单独的条件码/标志寄存器。六条 B 型分支：

```
beq  rs1, rs2, 标号   # 相等则跳    bne  不等则跳
blt  rs1, rs2, 标号   # 有符号 <    bge  有符号 ≥
bltu rs1, rs2, 标号   # 无符号 <    bgeu 无符号 ≥
```

这与 x86 那种"先 `cmp` 设置标志位、再 `jl`/`je` 读标志位跳转"的两步风格不同。RISC-V 一步到位：`blt x5, x6, L` 直接就是"若 x5 < x6 跳到 L"。

为什么不用条件码？条件码是一个隐藏的全局状态，会在指令间制造隐式依赖（一条算术指令悄悄改了标志，后面的分支依赖它），给流水线和乱序执行添麻烦；把比较并进分支指令，依赖关系全都显式写在指令的操作数里，更干净。代价是"比较结果没法复用"——若要基于同一个比较跳好几次，得比较好几次；但这种情况少。

易错点：注意区分有符号（blt/bge）与无符号（bltu/bgeu）比较——比较 `-1` 和 `1` 时，有符号下 -1 < 1，无符号下 -1（即 0xFFFFFFFF）> 1，用错会导致边界判断反掉。没有"大于"指令，`a > b` 靠交换操作数写成 `blt b, a`。

### 2.5.3 B 型立即数重组

B 型分支的立即数是本主题最"绕"的编码。分支偏移总是 2 字节的倍数（指令至少 2 字节对齐），所以最低位 imm[0] 恒为 0、不需存储；有效的是 imm[12:1] 共 12 位，它们被打散进指令。B 型字段与立即数重组规则：

```
B 型:  [imm[12]][imm[10:5]][rs2][rs1][funct3][imm[4:1]][imm[11]][opcode]
        inst31   inst30:25              inst11:8  inst7

重组:  imm[12]  = inst[31]        （符号位）
       imm[11]  = inst[7]
       imm[10:5]= inst[30:25]
       imm[4:1] = inst[11:8]
       imm[0]   = 0（恒定）
最终偏移 = 符号扩展{ inst31, inst7, inst30:25, inst11:8, 0 }
```

举个手工例子：`beq x5, x6, +8`（向前跳 8 字节）。偏移 8 的二进制（13 位，含恒 0 的 imm[0]）是 `0 0000 0000 1000`，即 imm[12]=0、imm[11]=0、imm[10:5]=000000、imm[4:1]=0100、imm[0]=0。填进 B 型布局（rs2=x6=00110, rs1=x5=00101, funct3=000, opcode=1100011）：

```
imm12 imm10:5 rs2   rs1   f3  imm4:1 imm11 opcode
 0    000000  00110 00101 000 0100   0     1100011
= 0000 0000 0110 0010 1000 0100 0110 0011
= 0x00628463
```

（该十六进制值由字段表按位拼装 + 本机 Python 算术核对，非反汇编器输出；本机无 RISC-V 工具链，见 2.2 抬头。）

为什么设计得这么"乱"？回到 2.2.3 的两条规律：符号位钉在 inst[31]（好符号扩展），中间位尽量与 S 型对齐（好复用接线）。S 型和 B 型唯一的差别就是 S 型 inst[7] 那位在 B 型里被挪去当 imm[11]、整体表达"偏移是 2 的倍数"。代价是人读起来费劲。易错点：**千万别把指令 [31:25] 和 [11:7] 顺着读当成立即数**——必须按上面的映射逐位归位，这是初学者算分支目标最常错的地方。

### 2.5.4 无条件跳转：jal（J 型）与 jalr（I 型）

`jal`（J 型）用于目标在编译期已知的无条件跳转/调用，其 20 位立即数同样被打散重组，且表示 2 字节倍数的偏移，范围约 ±1 MiB：

```
J 型:  [imm[20|10:1|11|19:12]][rd][opcode]
重组:  imm[20]=inst[31], imm[19:12]=inst[19:12], imm[11]=inst[20], imm[10:1]=inst[30:21], imm[0]=0
目标 = PC + 符号扩展(该 20 位偏移)
```

`jalr`（I 型）用于目标要到运行时才确定的间接跳转（函数返回、函数指针、跳转表）：目标 = (rs1 + 12 位立即) 且强制末位清 0。它用的是普通 I 型 12 位立即数、不需重组，好懂。

直觉分工：`jal` = "跳到我编译时就写死的那个标号"，偏移大（±1 MiB）足够覆盖绝大多数函数调用；`jalr` = "跳到寄存器里存的那个地址"，用于目标不定的场合。两者配合 x0/ra 就能表达"调用（jal ra,…）/ 返回（jalr x0,ra,0）/ 无条件跳（jal x0,…）"全套控制转移。若目标超出 `jal` 范围，编译器用 `auipc + jalr` 两条拼出 32 位相对跳转。

易错点：`jal` 的立即数重组规则和 B 型不同（见上），别混用；`jalr` 末位清 0 是为保证跳转目标对齐，手算目标时别忘了这步。

## 2.6 RISC vs CISC、分账

### 2.6.1 RISC 与 CISC 的核心区别

**RISC（精简指令集）**与 **CISC（复杂指令集）**是两种 ISA 设计哲学。RISC（如 RISC-V、ARM、MIPS）的特征：定长或少数几种规整指令格式、load-store 架构（只有 load/store 访存）、寻址方式少、指令数量少而正交、几乎每条指令都能在硬件流水线里高效执行。CISC（典型 x86）的特征：变长指令、算术指令可直接带内存操作数、寻址方式丰富、指令多且有"一条顶一段"的复杂指令。

一句话对照：**RISC 用"很多条简单、整齐的指令"，CISC 用"较少条复杂、参差的指令"来完成同一件事。**

初学者可用这个类比：RISC 像乐高——积木种类少、都规整，靠拼装造复杂结构；CISC 像一套形状各异的专用零件——单个能干复杂活，但种类繁多、尺寸不一。前者制造（硬件译码）简单、组装（编译器）灵活；后者单件强、但硬件要认识各式各样的零件。

### 2.6.2 权衡：指令条数 vs 每条复杂度

用大主题1 的性能公式看这场取舍最清楚：

```
CPU 时间 = 指令数(IC) × 每指令周期数(CPI) × 时钟周期
```

RISC 倾向**增大 IC**（同一逻辑要更多条简单指令，尤其 load-store 拆分访存），但换来**更低、更整齐的 CPI 和更短的时钟周期**（指令简单、流水线好切、译码快）。CISC 倾向**减小 IC**（复杂指令一条顶多条），代价是**单条指令译码/执行更复杂**，早期实现里 CPI 高、时钟难提。

关键洞察：性能不由"指令条数"单独决定，而是三个因子的乘积。RISC 的赌注是"简单换频率和流水线效率，总账更划算"，这一赌注在追求高主频、深流水、低功耗的时代（尤其移动/嵌入式）被广泛验证。此外定长规整编码还带来编译器优化、功耗、芯片面积上的好处。易错点：不要简单认为"指令越少越快"或"RISC 一定比 CISC 快"——要放进 IC×CPI×周期 的乘积和具体实现里看。

### 2.6.3 ISA 与微架构分账：现代实现的融合

必须分清两个层次：**ISA（指令集架构）**是"程序员/编译器看到的接口"——有哪些指令、寄存器、编码；**微架构（microarchitecture）**是"这套接口在芯片里怎么实现"——流水线多深、是否乱序、有几个执行单元。**同一个 ISA 可以有天差地别的微架构实现**。

现代高性能处理器让 RISC/CISC 的界线在微架构层大大模糊：典型 x86（CISC 的 ISA）在芯片内部会把复杂的变长 x86 指令**译码成类似 RISC 的定长内部微操作（micro-ops / μops）**，再送进一条 RISC 风格的乱序流水线执行。也就是说，对外它讲 CISC 的"语言"（保持指令集向后兼容），对内它按 RISC 的方式"干活"。

这解释了一个常见困惑："既然 RISC 更好，为什么 x86 还统治桌面/服务器？"——因为 ISA 的价值很大程度在**软件生态与向后兼容**（几十年的二进制程序不能重编），而性能差距可以靠微架构（内部 μop + 乱序）追平。反过来，RISC ISA（ARM、RISC-V）凭编码规整、许可开放（RISC-V）、功耗优势在移动和新兴领域扩张。分账的意义在于：**评判快慢要落到"某 ISA 的某个具体实现"，而不是"RISC vs CISC"这种标签之争**；ISA 之争的胜负更多取决于生态、授权模式与能效定位。深挖（乱序、超标量、寄存器重命名）属高级体系结构主题，本报告只做入门分账，不展开。
