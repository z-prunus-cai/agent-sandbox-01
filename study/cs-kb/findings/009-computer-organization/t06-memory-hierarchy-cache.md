## 6.1 局部性原理

### 6.1.1 时间局部性与空间局部性

局部性（locality）是指程序访问内存并非均匀随机，而是高度集中、可预测的经验规律，分两种。时间局部性（temporal locality）：一个刚被访问的地址，很可能在不久之后再次被访问。空间局部性（spatial locality）：一个地址被访问后，与它相邻的地址很可能紧接着被访问。这条规律是整个内存层次得以奏效的物理前提。

为什么程序会有局部性？看两个最小例子就懂。循环里的计数器 `i` 和累加器 `sum` 在每次迭代都被读写——这是时间局部性（同一变量反复用）。而遍历数组 `a[0], a[1], a[2], …` 时地址一个接一个连续增长——这是空间局部性（挨着的数据接着被用）。指令的取指同样有强局部性：代码大多是顺序执行（空间）加循环体反复执行（时间）。

初学者易错点：局部性是"统计上的倾向"，不是硬性保证。写得差的程序（比如按列遍历行主序存储的大矩阵、或到处追随机指针）局部性很差，缓存会频繁失效。理解这点就能理解"为什么同样算法、换个循环嵌套顺序，速度能差好几倍"——这正是 L5-05 与高性能计算课要深挖的。

### 6.1.2 存储层次为何存在：速度、容量、成本的三角权衡

存储器有一个铁律：越快的存储越贵、单位容量越小；越大越便宜的存储越慢。没有任何一种介质能同时做到又快又大又便宜。存储层次（memory hierarchy）就是把多种介质叠成一个金字塔，让 CPU 在绝大多数时候都能从最快的那层拿到数据，从而"用少量快存储 + 大量慢存储，逼近'又快又大'的假象"。

典型层次从快到慢、从小到大：CPU 寄存器 → L1/L2/L3 高速缓存（SRAM 制成）→ 主存（DRAM 制成）→ 固态盘/磁盘。相邻两层是"包含式或近似包含式"的关系：上层是下层的一个高速小副本。当 CPU 要的数据在上层找到，叫命中（hit）；找不到、要向下层取，叫失效/缺失（miss）。

直觉模型（图书馆）：你在书桌上放几本正在用的书（寄存器/L1），手边书架放这学期的书（L2/L3），去总馆借架上大量藏书（主存），冷门书在异地库房（磁盘）。因为你"这阵子"总在看那几本（局部性），桌上那几本就够应付大多数查阅，偶尔才要跑一趟书架或总馆。

为什么 SRAM 快但小、DRAM 慢但大？SRAM 一个存储位要用约 6 个晶体管、无需刷新，快但占面积、贵；DRAM 一个位只用 1 个晶体管 + 1 个电容，密度高、便宜，但电容会漏电需定期刷新且访问慢（这层电路细节在 L2-02 数字逻辑 DL-7.3 讲）。正是这个物理差异撑起了整个金字塔。

## 6.2 直接映射 cache

### 6.2.1 缓存块与地址的三段拆分：tag | index | offset

缓存以块（block，又称行 line）为搬运单位，不是逐字节而是一整块一起从下层搬来（这样才吃到空间局部性）。要判断某个字节地址是否在 cache、在哪一行，硬件把这个物理地址从低位到高位切成三段：块内偏移（block offset）、索引（index）、标记（tag）。

设地址共 m 位，块大小 B = 2^b 字节，组数 S = 2^s 组，则：

块内偏移位数 b = log2(B)

索引位数 s = log2(S)

标记位数 t = m − s − b

其中偏移选中"块内第几个字节"，索引选中"该去哪一组/哪一行找"，标记则是"这一行到底存的是哪个块"的身份证。直接映射（direct-mapped）是最简单的情形：每一组只有一行，所以"组数 = 行数 = cache容量 / 块大小"，一个内存块只能落到唯一确定的一行。

为什么低位当偏移、中间位当索引？因为相邻地址（空间局部性）低位在变、要落进同一块或相邻块；用中间位做索引能把连续的块尽量散开到不同组，减少互相踢出。这是"按位切地址"而非"按大小取模再除"——但两者等价：index 正是 `(块号) mod (组数)`，因为组数是 2 的幂，取模就等于取低若干位。

初学者最容易错的三点：(1) offset 的位数由**块大小**定，不是由字长定；块 64 B 就是 6 位偏移。(2) index 是块级别的，不含 offset 那几位——先把地址右移掉 offset，再取低 s 位。(3) tag 要连**valid 位**一起看：cache 刚上电时全是垃圾，每行有一个有效位（valid bit）标记"这行是否装了真数据"，无效行即使 tag 碰巧相等也算失效。

### 6.2.2 命中判定的最小例子

命中判定三步：用 index 选中那一行 → 读出该行的 valid 位和存储的 tag → 若 valid=1 且存储 tag == 地址的 tag 段，则命中，用 offset 从块里取出目标字节；否则失效。

走一个具体小例子（教材通式，非本机）。设 32 位地址、块大小 16 B、cache 总容量 1 KiB、直接映射：

```
块大小 16 B  → offset = log2(16) = 4 位
行数 = 1024 / 16 = 64 行  → index = log2(64) = 6 位
tag = 32 − 6 − 4 = 22 位
地址布局：[ tag:31..10 ][ index:9..4 ][ offset:3..0 ]
```

访问地址 `0x00001834`（二进制 …0001 1000 0011 0100）：offset = `0100` = 第 4 字节；index = `000011` = 第 3 组；tag = 高 22 位。硬件跳到第 3 行，比对 tag 与 valid，相等即命中取第 4 字节。若下一次访问 `0x00001835`（同块、offset 变 5），必然命中——这就是空间局部性被块结构吃到的地方。

本机实证（sysfs，核实 2026-07-26）：本机 L1 数据 cache 行大小 `coherency_line_size = 64` B，故 offset = 6 位；这印证了"块 = 64 B"是当代 x86 的实际值，与教材常用的 16/32/64 B 例子同构。注意本机 L1 是 12 路组相联而非直接映射（见 6.3），所以 index 用的是"组数 64"而非"行数"——`number_of_sets = 64` → index = 6 位。

易错点：不要把"cache 容量"直接拿去算 index。直接映射下 index 位数由**行数**定；组相联下由**组数**定（组数 = 容量 /（块大小 × 相联路数））。混淆这点会把地址拆错。

## 6.3 相联与替换

### 6.3.1 从直接映射到组相联、全相联

直接映射的痛点：两个常用块若 index 相同，就会反复把对方从那唯一的行里踢出去（冲突失效），哪怕 cache 整体还很空。组相联（set-associative）缓解这点——把 cache 分成若干组，每组有 n 行（称 n 路，n-way），一个块按 index 落到唯一的组，但组内 n 行任选其一存放。全相联（fully associative）是极端：整个 cache 只有一组，任何块可放任何行。

三者是同一根轴的三个点：

```
直接映射     = 每组 1 行（n=1）：定位快、冲突多
n 路组相联   = 每组 n 行：折中（当代主流）
全相联       = 只有 1 组、共 L 行：冲突最少、比较最贵
```

相联度越高，冲突失效越少，但代价是命中时要在组内 n 行里**并行比较 n 个 tag**（要 n 个比较器），硬件更贵、命中时间可能更长。这是"降失效率"与"控命中时间/成本"之间的权衡。

本机实证印证主流选择是组相联：本机 L1d 为 12 路、L2 为 16 路、L3 为 20 路组相联（sysfs, 2026-07-26），没有一层是直接映射或全相联——因为组相联在失效率和硬件成本间最划算。全相联通常只用在项数很少的结构（如 TLB，见 6.6）。

### 6.3.2 三类失效（3C 模型）

缺失可按成因分三类（Three C's），帮你判断"该往哪个方向优化"。强制失效（compulsory / cold miss）：某块第一次被访问，cache 里必然没有，无法避免（可靠预取或加大块缓解）。容量失效（capacity miss）：工作集比整个 cache 还大，装不下导致的失效（加大 cache 缓解）。冲突失效（conflict miss）：cache 没满，但多个块争同一组把彼此挤出（提高相联度缓解，全相联下此项为 0）。

这个分类的用处是把"命中率上不去"翻译成可执行动作：冲突多就加相联度，容量不足就加容量或改算法缩小工作集，强制失效多就靠更大的块或预取。它也解释了 6.3.1 那句"直接映射冲突多"——直接映射的冲突失效项天然偏高。

### 6.3.3 替换策略：LRU、随机、FIFO

组相联/全相联下，组满了还要装新块，就得挑一行牺牲——这由替换策略（replacement policy）决定。最近最少使用（LRU, Least Recently Used）：替换掉组内最久没被访问的那行，最贴合时间局部性，但要为每组维护访问时序，路数大时硬件开销高。随机（random）：随机挑一行，几乎零维护成本，命中率通常只比 LRU 略差。先进先出（FIFO）：按装入顺序替换最早进来的，介于两者之间。直接映射不需要替换策略——每个块只有唯一落点，没得选。

为什么真实硬件多用"近似 LRU"而非精确 LRU？精确 LRU 在高相联度下要记录完整访问顺序，代价随路数急剧上升，所以实现常用伪 LRU（pseudo-LRU，如树状位）来近似，用很少的位逼近 LRU 效果。教材入门层通常只讲"LRU 概念 + 随机对比"，精确的硬件近似算法留给 L5-05。

易错点：LRU 是"最久未被**使用**"，不是"最早**放进来**"——后者是 FIFO。两者在有重复访问的负载下会给出不同的牺牲者，别混。

## 6.4 写策略

### 6.4.1 写命中：写直达 vs 写回

读只是取副本、不改变数据，但写会让 cache 里的副本和下层内存不一致，必须约定怎么把写传下去。写命中（要写的块在 cache 里）有两种策略。写直达（write-through）：每次写同时更新 cache 和下层内存，二者始终一致，实现简单，但每次写都碰慢速下层、写流量大。写回（write-back，又称 write-back/copy-back）：只写 cache，给该行置一个脏位（dirty bit）标记"改过了"；直到这行被替换出去时才把整块写回下层。写回大幅减少写流量、吃到写的时间局部性，但实现更复杂、且替换时要多一次写回。

为什么写回更主流？因为程序常对同一块反复写（时间局部性），写直达会把每次写都无谓地灌到主存，而写回把 N 次写合并成"替换时一次写回"。代价是一致性管理更麻烦——多核下这个"脏副本何时对别人可见"正是缓存一致性问题（大主题8 CO-8.4 与 L5-05 AA-6 深挖）。本机 L1/L2/L3 均为写回式（当代 x86 主流），但 sysfs 不直接暴露该字段，故此处标本机具体策略为「未直接实测，依教材通式」。

### 6.4.2 写失效：写分配 vs 非写分配

写失效（要写的块不在 cache 里）也有两种应对。写分配（write-allocate，又称 fetch-on-write）：先把整块从下层读进 cache，再在 cache 里写——赌"这块接下来还会被访问"。非写分配（no-write-allocate / write-around）：绕过 cache，直接写下层，不把块调进来。

两者通常这样搭配：写回 + 写分配（既然要长期在 cache 里改，就先拉进来）；写直达 + 非写分配（反正每次都写下层，不占用 cache 行）。这不是硬性规定，而是最自然的组合。判断依据仍是局部性：若写完很快会再读/写这块，写分配划算；若是一次性大批量写（如清零大数组）不再回头，非写分配避免污染 cache 更好。

### 6.4.3 写缓冲

写直达每次都写慢速下层，CPU 岂不是每次写都要干等？写缓冲（write buffer）解决这点：写请求先塞进一个小队列（缓冲），CPU 立刻继续执行，由缓冲在后台慢慢把数据写到下层。只要写不是太密集、缓冲不写满，就把写的延迟对 CPU 隐藏掉了。写回式同样可用类似的缓冲区暂存被替换出的脏块（victim/write-back buffer），让"取新块"先于"写回旧块"完成，避免读等写。

易错点：写直达 ≠ 慢。加了写缓冲后，写直达的 CPU 停顿主要发生在"缓冲写满"时，平时并不阻塞；写直达真正的代价是对下层的写带宽占用，而不是每次写都让 CPU 卡住。

## 6.5 AMAT 与多级 cache

### 6.5.1 平均访存时间 AMAT

平均访存时间（AMAT, Average Memory Access Time）把"命中很快、失效很慢"两种情况按发生概率加权，得到一次访存平均要花多久，是评价 cache 好坏的核心指标：

AMAT = 命中时间 + 失效率 × 失效代价

其中命中时间（hit time）是命中时取到数据的时间（含判定 tag 的时间），失效率（miss rate）= 失效次数 / 访存次数，失效代价（miss penalty）是失效后从下层取来一整块所需的额外时间。三者任意一项都能成为瓶颈，优化方向也就分三路：降命中时间、降失效率、降失效代价。

一个最小例子（教材通式）：命中时间 1 个周期，失效率 2%，失效代价 100 个周期，则

AMAT = 1 + 0.02 × 100 = 3 个周期

即别看命中率高达 98%，那 2% 的失效仍把平均访存从 1 拖到 3 个周期——因为失效代价比命中时间大两个数量级。这就是"为什么降低失效率如此值钱"的量化理由。

易错点：失效代价通常**不含**命中时间那一份被重复计（COD 的写法里命中时间对命中/失效都要付，失效再额外付 miss penalty），所以公式是"命中时间 + 失效率×失效代价"而非"命中率×命中时间 + 失效率×失效时间"；后者展开后与前者在"失效时间 = 命中时间 + 失效代价"的约定下等价，别把两种记法的项重复相加。

### 6.5.2 多级 cache 与全局/局部失效率

单靠一级 cache 没法同时做到"命中时间短"和"失效率低"——要快就得小（否则命中判定慢），要低失效率就得大。多级 cache（multilevel cache）用分工破解：L1 做得小而快（低命中时间），它一旦失效就找更大更慢的 L2，L2 再失效找 L3，最后才到主存。每一级都在削减"传到下一级"的失效代价。

两级 cache 的 AMAT 递归展开：

AMAT = 命中时间_L1 + 失效率_L1 × (命中时间_L2 + 失效率_L2 × 失效代价_L2)

这里要区分两种失效率。局部失效率（local miss rate）= 本级失效数 / 到达本级的访问数（如 L2 局部失效率的分母是"L1 漏下来的那些访问"）。全局失效率（global miss rate）= 本级失效数 / CPU 发出的总访问数。评价 L2 对整机的贡献要看全局失效率（= 失效率_L1 × 局部失效率_L2），因为 L2 只处理 L1 漏下来的一小部分，用局部失效率会高估它的实际负担。

本机层次印证这套分工（sysfs, 2026-07-26）：L1d 48 KiB（小、快）→ L2 2 MiB → L3 260 MiB（大、共享、慢）；容量逐级放大约 40 倍再 130 倍，相联度也从 12 路升到 20 路——正是"上层保命中时间、下层保命中率"的实物。

本机实证（工作集延迟扫描，仅作方向性说明，非精确延迟）：用 Python 对随机置换的指针链做逐行追逐（每 64 B 一跳），随工作集从 16 KiB 增大到 64 MiB，单次访问耗时从约 26 ns 升到约 50 ns，呈单调上升的台阶趋势——工作集越过某级 cache 容量后延迟抬升，定性符合"越出上层 cache 就掉进更慢的下层"。⚠注意：Python 解释器每次迭代自身开销约 20–30 ns，已淹没真实的 L1 vs DRAM 硬件延迟差（真实差约 1 ns vs 数十 ns），故上述绝对数值**不是**真实访存延迟，只能读出"随工作集增大而变慢"的方向；精确 rdtscp 步长扫描留给 L5-05 AA-2.1。

### 6.5.3 三条优化路线与含义

对着 AMAT 三项，缓存优化天然分三路：降命中时间（更小的 L1、更简单的映射、路预测）、降失效率（更大容量、更高相联度、更大块、预取）、降失效代价（多级 cache、关键字优先返回、非阻塞 cache）。入门层知道"每条优化对应削 AMAT 的哪一项"即可，六类具体技术（含预取、非阻塞、牺牲 cache 等）是 L5-05 AA-2.1 的内容，本报告不深挖。

一个入门层必须澄清的张力：加大块能吃更多空间局部性、降失效率，但块过大反而抬高失效代价（每次搬更多字节）且减少总行数、可能增加冲突失效——所以块大小有个甜点，当代普遍收敛到 64 B（本机 L1/L2/L3 均为 64 B，sysfs 实测）。这说明"某一项优化推到极端会伤到另一项"，AMAT 三项要整体平衡。

## 6.6 虚拟内存与 TLB

### 6.6.1 分页与地址转换

虚拟内存（virtual memory）把 6.1 的层次思想放大一层：让主存（DRAM）充当磁盘的 cache，同时给每个进程一套独立的、连续的虚拟地址空间。它把地址空间切成固定大小的页（page），下层磁盘上对应的块叫页帧/物理页（page frame）。CPU 用的是虚拟地址（virtual address），必须先翻译成物理地址（physical address）才能访问真正的 DRAM——这个翻译由硬件 MMU 配合页表完成。

虚拟地址同样按位拆分，规则与 cache 的 offset/index 同构：低位是页内偏移（page offset），高位是虚拟页号（VPN, Virtual Page Number）。翻译只换页号、不动偏移：

页内偏移位数 = log2(页大小)

物理地址 = 物理页号(PPN) 拼接 页内偏移

本机页大小 4096 B（`getconf PAGE_SIZE`，2026-07-26）→ 页内偏移 = 12 位；翻译时把 VPN 换成 PPN，低 12 位偏移原样保留。为什么偏移不用翻译？因为页是整块映射的，同一页内的相对位置在虚拟和物理里一致，只有"这一页搬到了哪个物理帧"需要查表。

初学者直觉：虚拟内存像给每个进程发一本"私人地址簿"，程序以为自己独占从 0 开始的一大片连续内存，实际这些虚拟页被 OS 分散映射到物理内存各处、甚至暂存到磁盘。这既隔离了进程（各自地址互不干扰、提供保护），又让物理内存不足时能把冷页换出到磁盘（换页）。

### 6.6.2 页表

页表（page table）是"虚拟页号 → 物理页号"的查找表，每个进程一张，存在主存里，由 OS 维护、硬件（MMU）读取。表项（PTE, Page Table Entry）除了 PPN，还带若干控制位：有效位（该页是否在物理内存里，无效则触发缺页）、权限位（读/写/执行）、脏位、访问位等。

缺页（page fault）：CPU 要访问的虚拟页当前不在物理内存（有效位=0，数据在磁盘或尚未分配），MMU 触发异常交给 OS，OS 从磁盘把该页调入物理内存（必要时先换出一个旧页），更新页表后重新执行那条指令。缺页代价极高（涉及磁盘，是百万级周期），所以设计目标是让缺页极罕见——靠的正是局部性（6.1）。

为什么页表放主存而不是放进 CPU？因为它太大：本机 4 KiB 页、若 48 位虚拟地址，单级线性页表会有天文数字的表项，根本塞不进芯片。真实系统用多级页表（层级化、只为用到的地址建表项）压缩空间——多级页表的结构细节属 L4-01 操作系统 / L5-05 AA-2.4，本报告只到"页表在主存、按需建"这一层。

### 6.6.3 TLB：给地址翻译加一层 cache

页表放在主存带来一个致命问题：每次访存都要先查一次页表（也在主存），等于每次真正访存前多一次主存访问，速度腰斩。TLB（Translation Lookaside Buffer，地址转换后备缓冲）就是专门缓存"最近用过的页表项"的小而快的 cache，通常做成全相联或高相联、几十到上千项，命中时一两个周期就拿到 PPN，完全避开查主存页表。

TLB 靠的仍是局部性：程序在一段时间内只用到少数几页（一个循环、一个数组多半落在同页或相邻几页），这少数几个翻译缓存在 TLB 里就能覆盖绝大多数访存。TLB 命中→直接得 PPN；TLB 失效→去查页表（可能由硬件 page walker 或 OS 完成），把结果填回 TLB。

一次访存的完整流程串起本报告：CPU 出虚拟地址 → 查 TLB 得物理地址（失效则走页表，页表缺页则从磁盘调页）→ 用物理地址查 L1/L2/L3 cache（6.2–6.5）→ 都失效才访问 DRAM。TLB 和 cache 是两层不同的加速：TLB 缓存的是"地址翻译"，cache 缓存的是"数据本身"，别混为一谈。

本机实证（可选，`/proc/self/maps`）：Linux 下 `cat /proc/self/maps` 可看到当前进程的虚拟地址区间映射（代码段/数据段/堆/栈/共享库各自的虚拟地址范围与权限 r/w/x），直观印证"进程看到的是自己的一套虚拟地址空间、分段映射"。本报告未逐行贴输出（属实证可选项），映射存在性已由该文件可读性坐实。易错点：`/proc/self/maps` 展示的是虚拟地址布局，不是物理地址；物理映射对用户态不可见。
