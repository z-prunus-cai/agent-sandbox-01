## 6.8.1 trunk-based development（主干开发）

### 6.8.1.1 什么是 trunk-based development

trunk-based development（TBD，主干开发）是一种源码分支模型：所有开发者在**同一条主分支**（称为 trunk，即 git 里通常的 `main`）上协作，并**刻意抵制创建其它长命名开发分支**。trunkbaseddevelopment.com（Paul Hammant 维护的业界站点，⚠非规范）给的定义是「开发者在单一分支 trunk 上协作，并通过一套成文技术抵制创建任何其它长命名开发分支的压力」。它的对立面正是下一节 GitFlow 那种「develop/release 等多条分支常年并存」的模型。

对初学者，先建立这个画面：TBD 不是「禁止一切分支」，而是「不允许分支**长命**」。改动可以在一条活不过一两天的短命名分支上做，但必须尽快合回 trunk。核心诉求是**让每个人手里的代码离主干都不远**——因为两份代码分开得越久、各自改得越多，合并时冲突就越大、越难查。TBD 用「频繁合回」把这种发散控制在最小。

### 6.8.1.2 两种落地形态：直接提交主干 vs 短命名分支加 PR

TBD 在实践中有两种粒度，取决于团队大小。trunkbaseddevelopment.com 区分了「小团队 TBD」与「规模化 TBD（scaled）」：很小的团队可以让开发者**直接向 trunk 提交**；团队一大，则改用**短命名分支（short-lived feature branch）+ Pull Request**——分支只为「过一遍代码评审和 CI 构建」而存在，通过后立刻合并、删除。

```
# 规模化 TBD 的典型一次循环（示意，非实证输出）
git switch -c fix-login main   # 从 trunk 切一条短命名分支
# ... 小改动、写测试 ...
git push -u origin fix-login   # 开 PR，触发 CI 与评审
# 评审 + CI 绿 → 合并回 main，随即删除该分支（存活 < 1~2 天）
```

区分这两种形态对初学者很重要：常见误解是「TBD = 谁都往 main 上乱提交」。其实规模化 TBD 依然走 PR 和评审门禁（见大主题06-7），只是把「分支的寿命」压到极短。它和 GitHub Flow（见 6.8.4.2）在操作上几乎一样，差别是侧重点——TBD 强调「分支要短、要频繁集成」，GitHub Flow 强调「分支要可评审、可部署」。

### 6.8.1.3 频繁集成：TBD 与 CI 是一体两面

TBD 的灵魂是**频繁集成**。trunkbaseddevelopment.com 提出的经验规则是：开发者应**至少每 24 小时把工作合回 trunk 一次**，以满足持续集成（continuous integration，见大主题06-12）的要求。Martin Fowler 站点（⚠业界）也把「每人每天至少集成一次到主线」列为 CI 的核心纪律——从这个角度看，「持续集成」这个名字本身就预设了主干开发：你没法对一堆常年不合并的分支「持续集成」。

这里要点破一个初学者容易混淆的因果：不是「先有 TBD 再谈 CI」，而是二者**互为前提**。频繁合回 trunk，才让 CI 每次都在「接近最终状态」的代码上跑；反过来，只有 CI 门禁足够强（自动化测试 + 静态检查能拦住坏提交），团队才敢让大家频繁往同一条 trunk 上合。缺了任一半，另一半都立不住——这也是为什么 TBD 在没有成熟自动化的团队里推不动。

### 6.8.1.4 规模化 TBD 里的 release 分支：从 trunk 切，只挑修复

大团队做 TBD 并非完全没有其它分支——但它们的用法和 GitFlow 相反。trunkbaseddevelopment.com 描述的 release 分支是：**从 trunk 上某个点切出、之后只往里 cherry-pick 必要的修复**，绝不在 release 分支上做新功能，也**不把 release 分支合回 trunk**（修复是先进 trunk 再挑到 release，或反向 cherry-pick，方向由团队定）。

对初学者，关键对比是「分支的信息流方向」。GitFlow 里 develop/release 是**功能汇聚**的地方（改动往里合）；TBD 的 release 分支只是**主干某一刻的快照 + 少量热修**，是「发射后基本冻结」的一次性产物。这样做的好处是主干永远是唯一的「功能真相来源」，避免了「一个改动到底在哪条分支上、合没合过去」的账难算。

### 6.8.1.5 经验证据与争议（⚠经验主张·锚版本）

支持 TBD 的最常被引用的经验证据来自 **DORA / 《Accelerate》**（Forsgren、Humble、Kim，2018；DORA 研究项目，⚠业界研究、非规范）。其结论是：软件交付高绩效团队更倾向于采用 trunk-based development，具体量化的**操作化定义**为「代码库中**同时活跃的分支少于 3 条**」「分支/fork 在合并回主线前**寿命很短（不超过一天）**」「几乎没有因合并冲突/代码冻结/稳定化阶段导致的锁定期」。DORA 并称高绩效与「三条或更少活跃分支」正相关。

必须给初学者交代清楚这类证据的分量与边界：DORA 是**大样本问卷的相关性研究**，它说的是「高绩效团队**倾向于**这么做」，是相关不是因果，也不构成「你照做就一定更好」的规范。反对/保留意见也存在——批评者指出 TBD 对自动化测试覆盖率、feature flag 基建、团队纪律要求很高，基建不到位时强推反而制造事故。所以本报告只把 TBD 记为「有较强经验证据支撑、但依赖前置条件」的一种主张，**不作「TBD 一定优于 GitFlow」的绝对定论**（核实 2026-07-30）。

#### 来源与时效（本小主题末集中列）

- 一手（承重·仅到工作流大类）：Pro Git 2nd ed §3.4 Branching Workflows（https://git-scm.com/book/en/v2/Git-Branching-Branching-Workflows）——把「主题分支（topic branch）」定义为「为单一功能创建、常常一天内多次创建/合并/删除的短命名分支」，这是 TBD「短命名分支」做法在一手文献里能找到的最接近的背书；但 Pro Git **未使用 "trunk-based development" 一词**，不为其具体主张背书。核实 2026-07-30。
- ⚠业界（**⚙演进快·锚版本·随时变·不承重·仅指路**）：trunkbaseddevelopment.com（Paul Hammant，定义/短命名分支/24 小时集成/scaled TBD 与 release 分支）；Martin Fowler 站点 ContinuousIntegration 词条（每人每天至少集成一次）；DORA/《Accelerate》(2018) 与 dora.dev「Trunk-based development」能力页（<3 活跃分支、分支寿命<1 天 的操作化定义，经验相关性主张）。核实 2026-07-30。
- 冲突/分歧：TBD 是否「更优」为**经验主张**，DORA 给相关性证据、批评者强调前置条件，本报告不下定论。

## 6.8.2 GitFlow 与长命名分支模型

### 6.8.2.1 GitFlow 的起源与五类分支

GitFlow 是 Vincent Driessen 在博文《A successful Git branching model》（nvie.com，**发布于 2010-01-05**，⚠业界、非规范）中提出的分支模型。它定义了**两条长命名主分支**加**三类支撑分支**：

- `master`（主分支）——只存**已发布的生产代码**，每个提交对应一个正式版本（打 tag）。
- `develop`（开发分支）——**集成分支**，汇聚下一个发布的所有已完成功能，是「最新的开发态」。
- `feature/*`（功能分支）——从 `develop` 切出、完成后合回 `develop`，承载单个功能。
- `release/*`（发布分支）——发布前从 `develop` 切出做收尾（改 bug、调版本号），完成后**同时合回 `master` 和 `develop`**。
- `hotfix/*`（热修分支）——生产出事时从 `master` 切出紧急修复，完成后**同时合回 `master` 和 `develop`**。

对初学者，抓住两个「常年存在」的分支（`master`、`develop`）和三个「用完即弃」的分支就够了。它的设计目标是**有明确版本、需要并行支持多个已发布版本**的软件（例如要给客户维护 1.x 又同时开发 2.x 的桌面/库软件）。

### 6.8.2.2 分支流转与它的开销

GitFlow 的流转是「功能在 `develop` 汇聚 → 发布时切 `release` 收尾 → 发布后 `release` 合进 `master` 打 tag、并回流 `develop` → 生产急事走 `hotfix` 双向合回」。它的价值是**结构清晰、每条分支职责单一、天然支持发布收尾期和多版本维护**。

代价也正来自这套结构。要向初学者讲清 GitFlow 被诟病的「开销」，核心是两点。其一是**合并成本**：功能分支常常在 `develop` 上待较久，离主干越漂越远，合并时冲突越多（前面说的 merge hell）——这与 TBD「频繁小步集成」的哲学正相反。其二是**流程重**：一次改动要在多条分支间来回合并（`feature→develop→release→master` 且 `release/hotfix` 还要回流 `develop`），对「一天发布很多次」的团队是沉重负担。这两点是下一节争议的根源。

### 6.8.2.3 原作者 2020 年的注记（争议核心·⚙锚版本）

GitFlow 最重要的时效信息是：**原作者本人在 2020-03-05 于原文顶部加了一条注记**，明确说明它不适合所有场景。原话（nvie.com，核实 2026-07-30）大意是——「Web 应用通常是持续交付的、不需要回滚、也不必支持多个在野版本运行，这不是我十年前写这篇文章时设想的那类软件。**如果你的团队在做持续交付，我建议采用更简单的工作流（比如 GitHub flow），而不是硬把 git-flow 塞给团队**。」作者同时强调，对于**需要显式版本化、要支持多版本并行**的软件，GitFlow 仍然适用。

这条注记对初学者是关键的「防误用」提醒：**不要把「连原作者都说要看场景」误读成「GitFlow 已死/一无是处」**——两种极端解读在网上都很常见，都是过度简化。准确的表述是：GitFlow 适配「按版本发布、需多版本维护」的软件；对「持续交付的 Web 应用」，原作者自己推荐更轻的工作流。这正是本报告「两边都记、不作绝对定论」纪律的典型例子。

### 6.8.2.4 与 Pro Git「长命名分支」大类的关系，及 GitHub Flow 作为轻量替代

回到唯一的一手承重点：Pro Git §3.4 把工作流分成「**长命名分支（long-running branches）**」与「**主题分支（topic branches）**」两大类。GitFlow 正是「长命名分支」大类的一个**具体且偏重**的实例——它把 Pro Git 举例的 `master`/`develop`/`proposed` 这种「稳定度递进的多条长命名分支」思想，细化成了带 feature/release/hotfix 的完整流程。**Pro Git 只为「长命名分支这个大类存在且有用」背书，并不为 GitFlow 的具体规程背书**——这条界线要守住。

与之对照，原作者推荐的替代 **GitHub Flow**（GitHub 官方文档，⚠平台侧、演进快）是个「轻量、基于分支」的工作流：只有一条长命名分支（默认分支），其余都是从它切出的短命名分支，经 PR 评审后合回并部署，随即删除。它本质上属于 Pro Git 的「主题分支」大类，也非常接近规模化 TBD。对初学者，可以把这三者排成一条谱系：**GitFlow（多长命名分支，最重）→ GitHub Flow（一条长命名 + 短命名分支）→ trunk-based（尽量直接在 trunk 上、分支寿命最短）**，从重到轻。

#### 来源与时效（本小主题末集中列）

- 一手（承重·仅到工作流大类）：Pro Git 2nd ed §3.4 Branching Workflows——「长命名分支」与「主题分支」两大类的划分及 `master`/`develop`/`proposed(pu)` 稳定度递进示例。GitFlow 是「长命名分支」大类的具体实例，Pro Git 不为其规程背书。核实 2026-07-30。
- ⚠业界（**⚙演进快·锚版本·随时变·不承重·仅指路**）：Vincent Driessen《A successful Git branching model》(nvie.com，正文 2010-01-05，**顶部注记 2020-03-05**)——五类分支定义 + 原作者「持续交付团队建议改用 GitHub flow」的注记；GitHub 官方文档 "GitHub flow"（docs.github.com，平台侧、随产品演进）——轻量分支工作流的步骤。核实 2026-07-30。
- 冲突/分歧：GitFlow 是否仍推荐——**原作者 2020 注记**给出「分场景」的权威口径（版本化软件仍适用；持续交付 Web 应用改用更轻工作流），网络上「已死」与「万能」两种极端说法均为过度简化，本报告采原作者分场景口径。

## 6.8.3 feature flag 与发布解耦

### 6.8.3.1 部署（deploy）与发布（release）的区分，以及开关如何解耦二者

feature flag（特性开关，又称 feature toggle）是一种在**运行时用配置控制某段代码是否对用户生效**的技术。它的核心价值是把两件平时被混为一谈的事**解耦**开来：

```
部署（deployment）：把新代码送上生产服务器（代码"在那儿运行"了）
发布（release）：让某个功能真正对用户可见/生效（用户"用得到"了）
```

Martin Fowler 站点（Pete Hodgson《Feature Toggles (aka Feature Flags)》，martinfowler.com，⚠业界）指出：feature flag 让团队可以**把代码部署到生产、同时对用户隐藏未完成的功能**，从而把「部署」与「发布」解耦。这样就能在主线上持续集成，而不必等一个功能全做完才敢合进去。

对初学者，这是理解 TBD 为何可行的关键钥匙。TBD 要求「半成品也要频繁合回 trunk」，但半成品直接暴露给用户会出事——feature flag 正好补上这一环：代码合进去、部署上线，但**开关默认关着**，用户看不到；等功能做完、验证过，再打开开关「发布」。于是「部署」变成低风险的日常动作，「发布」变成一个独立的、可随时开关的决策。

### 6.8.3.2 开关的分类

Pete Hodgson 的文章按「变化速度 + 存活时长」把开关分为四类（⚠业界，锚该文版本）：

- **release toggles（发布开关）**——开发期用来藏起未完成功能，让半成品能安全进主干；**应短命**，功能稳定后即拆。
- **experiment toggles（实验开关）**——做 A/B 测试，按用户分流不同代码路径以比较效果；存活到实验出结论。
- **ops toggles（运维开关）**——运维用的控制阀，例如流量高时临时关掉某个耗资源的功能（俗称 kill switch）；可能长期保留。
- **permissioning toggles（权限开关）**——按用户群控制功能可见性，例如只对内测用户或付费用户开放；可能长期存在。

对初学者，分类的意义不在死记名字，而在于理解「**开关不是一种东西**」：发布开关是临时脚手架、用完要拆；权限/运维开关是产品长期能力、本就该留。把二者混为一谈，是后面「开关债务」误区的根源。

### 6.8.3.3 与 trunk-based 的协同：允许主干存在半成品

feature flag 与 trunk-based 是**天生一对**。前面说 TBD 要求频繁把工作合回 trunk，但一个大功能往往几天甚至几周才做完——难道要憋着不合、退回长命名分支吗？feature flag 给出的答案是：**把大功能拆成一系列小改动，每个小改动都藏在同一个关闭的开关后面，随做随合进 trunk**。主干里因此可以坦然存在「已合入但未发布」的半成品代码。

这解决了初学者最容易问的矛盾：「主干开发不是要求主干始终可发布吗？半成品在里面怎么可发布？」答案是——**可发布 ≠ 每个功能都完成，而是「主干任一时刻都能安全地部署上线」**。半成品因为被关着的开关挡住，部署上去也不会对用户产生任何效果，因此不破坏「可发布」。开关就是让「主干里有半成品」与「主干随时可发布」这两件看似矛盾的事同时成立的机关。

### 6.8.3.4 开关债务与退役（易错点·⚙锚版本）

feature flag 最大的坑是**开关债务（toggle debt）**。Fowler 站点反复强调：**发布开关一旦对应的功能在生产上稳定下来，就必须及时退役（retire）**。每个开关都在代码里制造一个分叉（`if flag then A else B`），开关越堆越多，代码路径组合爆炸、测试和维护都变成噩梦。

对初学者，务必把这条当硬纪律记住：**开关是脚手架，不是永久建筑**。常见错误是「功能上线了，但开关代码一直没人删」，几年后代码里躺着几十个早已恒为 true 的开关，谁也不敢动。实践上团队会给发布开关设「到期日」或建清单跟踪，功能稳定后主动提 PR 删除开关及其挡住的旧分支。注意这只针对**发布开关**——权限/运维开关是长期产品能力，不在「必须退役」之列（呼应 6.8.3.2 的分类）。

### 6.8.3.5 Fowler 的「开关是最后手段」层级

一个常被忽略但重要的时效性观点：Fowler 站点把 feature flag 定位为**最后手段**，而非首选。更优先的做法是——先看能不能**把功能拆成更小的、可独立发布的完整片段**；或用 **Keystone Interface（拱心石）** 手法，即先把后端代码整合进去、只把用户能看见的那一小块 UI 留到最后接上，用「不接 UI」天然地隐藏功能，从而**不需要开关**。

不要一看到「主干半成品」就无脑加开关。开关有真实成本（债务、测试路径爆炸）。能靠「小步切分」或「留最后一块 UI 不接」解决的，就别引入开关；开关留给「确实无法拆小、又必须提前合并」的情形。这也说明「TBD 必须配 feature flag」是简化说法——更准确的是「TBD 需要某种隐藏半成品的手段，feature flag 是其中一种、且非首选」。

#### 来源与时效（本小主题末集中列）

- ⚠业界（**⚙演进快·锚版本·随时变·不承重·仅指路**）：Martin Fowler 站点，Pete Hodgson《Feature Toggles (aka Feature Flags)》（martinfowler.com/articles/feature-toggles.html）——部署 vs 发布解耦、四类开关（release/experiment/ops/permissioning）、开关债务与退役、「最小 toggle point」、「开关是最后手段 / Keystone Interface / 小步切分优先」。核实 2026-07-30。
- 交叉：trunkbaseddevelopment.com——feature flag 作为「让半成品能进 trunk」的配套手段，佐证 6.8.3.3 的协同关系。核实 2026-07-30。
- 说明：feature flag 全为业界方法学，无规范一手；本节所有主张均 ⚠、仅指路。

## 6.8.4 策略选型

### 6.8.4.1 选型的几个维度

分支策略没有「正确答案」，选型是按团队现实**匹配**的过程。综合前三节的业界主张，常被用来做取舍的维度有（⚠均为经验维度）：

- **发布节奏**：一天发布多次（持续交付/部署）强烈倾向 TBD/GitHub Flow；按版本、按批次发布则 GitFlow 的收尾期设计更贴合。
- **是否需支持多版本并行**：要同时维护 1.x 和 2.x（桌面软件、SDK、给客户私有部署的产品）时，GitFlow 的 `master` 多版本 + `hotfix` 设计有价值；只有一个「线上唯一版本」的 Web 应用则不需要这套。
- **团队规模与提交频率**：影响 TBD 落地形态——很小团队可直接提交 trunk，团队大则用短命名分支 + PR（scaled TBD）。
- **自动化与评审文化的成熟度**：TBD 依赖强 CI 门禁和 feature flag 基建；基建不足时贸然上 TBD 风险高，反而是较重的分支流程能提供缓冲。

对初学者，最该记住的是**别按「流行度」选，要按「约束」选**。先问自己团队：多久发一次？要不要养多个已发布版本？CI 和测试到不到位？答案基本就决定了该往谱系的哪一端靠。

### 6.8.4.2 主流策略谱系对比

把常见策略按「长命名分支的多少 / 集成频率」排成一条谱系，便于对照（⚠各条均为业界主张，非规范；命名与细节随来源略有出入）：

```
重  ←────────────────────────────────────────────→  轻
GitFlow            GitLab Flow           GitHub Flow          Trunk-Based
master+develop     一条主分支 +          一条默认分支 +        尽量直接在 trunk；
+feature/release   环境/发布分支          短命名分支+PR         分支寿命 <1~2 天；
/hotfix            （production/          →评审→合并→部署       半成品靠 feature
多长命名分支        pre-prod 等）                              flag 隐藏
```

- **GitFlow**：多条长命名分支，适配版本化、多版本维护；重、合并成本高（详见 6.8.2）。
- **GitLab Flow**（GitLab 文档，⚠平台侧）：介于两者之间——保留一条主分支，再按「环境」（如 `production`、`pre-production`）或「发布版本」加少量长命名分支，用 upstream-first 规则约束改动流向，比 GitFlow 轻、比纯 TBD 多一点结构。
- **GitHub Flow**：一条长命名默认分支 + 短命名分支 + PR，轻量、面向持续部署（详见 6.8.2.4）。
- **Trunk-Based**：谱系最轻端，强调短命名分支/直接主干 + 频繁集成 + feature flag（详见 6.8.1）。

现实里大多数团队并不「纯粹」采用某一种，而是落在谱系的某处、按需微调。理解两个极端（GitFlow ↔ TBD）和中间过渡（GitLab/GitHub Flow），比死记某一套流程更有用。

### 6.8.4.3 争议与「不作绝对定论」

选型话题上来源**互相打架**是常态，必须对初学者讲明白，避免被单一来源带偏：

其一，**GitFlow 之争**——原作者 2020 注记（6.8.2.3）给的是「分场景」口径：版本化软件仍适用、持续交付 Web 应用改用更轻工作流。网络上「GitFlow 已死」与「GitFlow 是标准」两派都在过度简化。

其二，**TBD 的证据分量**——DORA/《Accelerate》给的是**相关性**证据（高绩效团队倾向 <3 活跃分支、分支寿命 <1 天），不是「照做必更好」的因果保证；且 TBD 明确依赖强自动化前置条件。

其三，**没有统一命名**——GitHub Flow、GitLab Flow、TBD 在不同来源里的边界和步骤定义并不完全一致，甚至相互重叠（scaled TBD 与 GitHub Flow 操作上几乎相同）。因此本报告**不为任何一种下「最优」定论**，只给「维度—谱系—场景匹配」的框架（核实 2026-07-30）。

### 6.8.4.4 常见误用与迁移方向

几个业界反复提到的实践提醒（⚠经验主张）：

一是**别把重流程套到快节奏团队上**——这正是 GitFlow 原作者亲自劝阻的：持续交付团队硬塞 GitFlow，会被多分支间的来回合并拖垮。二是**别在基建不足时硬上 TBD**——没有可靠的自动化测试和 feature flag，频繁往 trunk 合半成品只会把主干搞坏，反噬「主干始终可发布」这条底线。三是**迁移通常是「由重变轻」的渐进过程**——很多团队从 GitFlow 起步，随着 CI/CD 成熟、发布变频，逐步砍掉 `develop`、缩短分支寿命、引入 feature flag，向 GitHub Flow / TBD 靠拢；反向（由轻变重）较少见，多发生在「开始需要维护多个已发布版本」时。

对初学者，把这三条当「选型体检表」：先看**约束**（发布节奏、多版本需求、基建成熟度），再选**谱系位置**，最后小步调整——而不是一上来就抄某个大厂的流程。策略是为团队服务的工具，不是需要膜拜的教条。

- ⚠业界（**⚙演进快·锚版本·随时变·不承重·仅指路**）：DORA/《Accelerate》(2018) 与 dora.dev（TBD 相关性证据、<3 活跃分支）；Vincent Driessen nvie.com 2020 注记（GitFlow 分场景口径）；GitHub 官方文档 GitHub flow、GitLab 官方文档 GitLab flow（谱系中间/轻端，平台侧随产品演进）；Martin Fowler 站点（feature flag 作为 TBD 前置基建）。核实 2026-07-30。
