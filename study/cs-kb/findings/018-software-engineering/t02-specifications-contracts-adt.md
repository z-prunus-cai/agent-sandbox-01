## 6.2.1 方法规约：前置/后置条件

### 6.2.1.1 规约即契约：把实现与客户端解耦

一个方法的**规约（specification）**是它对外承诺的**契约（contract）**，由两部分组成：**前置条件（precondition）**用 `requires` 子句写，是对**客户端（调用者）**的约束；**后置条件（postcondition）**用 `effects` 子句写，是对**实现者**的承诺。契约的含义是一句双向承诺：

```
只要客户端在调用时满足 requires，实现者就保证返回后满足 effects。
```

MIT 6.031 Reading 6 把它称为"团队协作的关键（linchpin）"：没有规约就无法把一个函数的实现责任委托出去——客户端需要一份可依赖的承诺，实现者需要一份明确的责任边界。规约正是这份边界。

对初学者，最容易的进入点是把它类比成买卖合同：`requires` 是"买家要先付够钱"（客户端的义务），`effects` 是"卖家保证交货"（实现者的义务）。买家没付钱（违反 requires），卖家就不受"交货"约束；买家付了钱，卖家就必须交货。关键在于：合同之外的东西双方都不许依赖——客户端不能依赖实现的内部细节，实现者也不能依赖客户端怎么用它。这种"只认契约、互不窥探"就是后面反复出现的"解耦（decoupling）"。

### 6.2.1.2 requires（前置条件）：加在客户端身上的义务

`requires` 描述方法被调用时**输入与状态必须满足的条件**。它可以收窄参数（比如"参数类型系统只能表达 number，但这里要求它是非负整数"）、可以规定参数之间的关系（比如"数组 a 已按升序排好"），也可以规定对象所处的状态。

```
requires: 对调用时刻状态的约束，是客户端的义务
```

初学者常问"为什么不干脆在方法里检查、非法就报错？"——规约层面区分两种写法：把某条件写进 `requires`，意思是"客户端保证不会违反，实现者可以**不检查**、直接假定成立"；反之，若希望方法自己检查非法输入并抛异常，那这条就该写进 `effects`（"当输入非法时抛某异常"），而不是 `requires`。二者是不同的契约。把条件放进 `requires` 的好处见 06-2.1.4：它给了实现者"跳过昂贵检查、用更快实现"的自由。

### 6.2.1.3 effects（后置条件）：加在实现者身上的承诺

`effects` 描述方法返回后**保证成立的一切**：返回值与输入的关系、会抛哪些异常及何时抛、是否以及如何改动（mutate）了对象。类型系统能静态检查的部分（如返回类型）是 effects 的一部分，但 effects 通常还包含类型系统表达不了的语义。

```
effects: 对返回值 / 抛出异常 / 对象改动的承诺，是实现者的义务
```

**"什么都不说"等于"什么都可能发生"**。如果规约没提"是否改动输入对象"，那么实现者**可以**改动它，客户端不能抱怨。所以一个只读的方法要显式承诺"不改动输入"，一个纯函数要显式说"无副作用"。规约的沉默不是"保证不做"，而是"不做承诺"。这条纪律和 06-2.1.4 的"前置条件被违反"是同一枚硬币的两面：契约没覆盖的地方，都是实现者的自由区。

### 6.2.1.4 前置条件被违反：行为完全未定义

契约的一条硬规则：**如果调用时 requires 不成立，实现者就完全不受 effects 约束**。MIT 6.031 的原话是它"可以做任何事，包括永不返回、抛出规约里没提到的异常、返回任意结果、做任意改动等等"。

这条常让初学者觉得"太不负责任了"，但它恰恰是规约**给实现者自由**的来源。因为不必为非法输入负责，实现者可以省掉一次昂贵的合法性检查，换来更快的实现；也可以在将来自由改写实现，只要仍满足"合法输入 → 承诺的输出"。要点是：`requires` 越强（要求越多），实现者的负担越轻、自由越大——这正是 06-2.2 "更强前置 = 更弱规约"的直觉起点。

把前置条件写得太强（要求客户端保证很多），会把出错的风险推给客户端，且一旦客户端违反，程序会以不可预测的方式崩坏、难以调试。所以实践中常见的折中是"要么写进 requires 让实现者假定、要么写进 effects 让实现者 fail-fast 抛异常"，二选一并写清楚，而不是留白。

### 6.2.1.5 契约作为防火墙：双向屏蔽

规约在客户端与实现者之间竖起一道**防火墙（firewall）**：它对客户端屏蔽实现的内部工作细节（客户端不必读实现代码，照规约用即可），同时对实现者屏蔽客户端的具体用法（实现者不必知道谁怎么调它）。结果就是**解耦**——只要改动仍尊重规约，模块的代码和客户端的代码就能各自独立地改。

对初学者，这就是"为什么要写规约"的终极答案：它让大型程序可以分工。你实现的排序函数被一百个地方调用，你不可能去读那一百处代码；那一百个作者也不该来读你的实现。大家只对着中间那份 `requires`/`effects` 契约编程，就能各改各的、互不打架。这也直接呼应了 06-1 的"ready for change（面向变更）"——规约是让代码"可安全改动"的最基本单位。

## 6.2.2 规约的强弱与安全替换

### 6.2.2.1 强弱定义：弱前置 + 强后置 = 更强规约

比较两份规约谁"更强"，MIT 6.031 Reading 7 给出精确判据：

```
规约 S2 强于或等于 S1  ⟺  S2 的前置条件弱于或等于 S1 的，且 S2 的后置条件强于或等于 S1 的。
```

也就是两条同时成立：S2 对输入**要求更少**（前置更弱），S2 对输出**承诺更多**（后置更强）。一份"更强的规约"意味着它对客户端更慷慨（更容易满足调用条件）、对实现者要求更高（必须兑现更多承诺）。

初学者可以把"强规约"理解成"对客户更好用的规约"：能接受更多输入、又保证更多结果。反直觉的地方在于"前置条件更弱反而使规约更强"——见下一节的拆解。

### 6.2.2.2 为什么"更强前置 = 更弱规约"（易记反的方向）

这是本主题**最容易记反**的一点，prompt 特意点名。把它想清楚的钥匙是：规约的强弱是站在**客户端能依赖多少**的角度衡量的。

前置条件是客户端要满足的**门槛**。门槛越高（前置越强、要求越多），能走进门、享受到承诺的客户端就越少——所以对整体而言，这份规约能保证的场景更少、更"弱"。反过来，门槛越低（前置越弱），越多调用都能享受到 effects 承诺，规约越"强"。后置条件方向相反且符合直觉：承诺越多（后置越强），规约越强。合成一句：

```
前置越弱 → 规约越强；   后置越强 → 规约越强。
（故：前置越强 → 规约越弱；后置越弱 → 规约越弱。）
```

一个最小例子。规约 A：`requires: 输入非空`，`effects: 返回最大元素`。规约 B：`requires: 无`，`effects: 输入非空时返回最大元素，为空时抛异常`。B 的前置更弱（不要求非空），承诺覆盖了更多情形，所以 B 强于 A。任何满足 B 的实现都能顶替 A 用（见下节），反之不行。

### 6.2.2.3 规约空间的图景：强规约 = 更小的实现区域

Reading 7 用一张"所有可能实现构成的空间"来直观化：一份规约在这个空间里圈出一块**区域**——所有满足它的实现都落在区域内。**规约越强，圈出的区域越小；越弱，区域越大**。当 S2 强于 S1 时，S2 的区域**被包含在** S1 的区域里（S2 的每个实现都同时满足 S1）。互不可比的两份规约，区域可能相交或不相交。

这张图给初学者两个好用的心像。其一，"强"意味着"挑剔"——满足它的实现更少（区域小）。其二，也是安全替换的几何本质：S2⊆S1 时，站在 S1 的位置上换用任何一个 S2 实现，都还落在 S1 允许的范围内，绝不越界。这就是下一节"安全替换"的图形版本。

### 6.2.2.4 安全替换与 Liskov 替换原则（LSP）

Reading 7 的结论：当 S2 强于或等于 S1，**满足 S2 的实现可以拿来当 S1 用**，在程序里把 S1 替换成 S2 是安全的。这就是"用强规约替换弱规约总是安全"。

把同一原则搬到面向对象的**子类型**上，就是 **Liskov 替换原则（LSP）**：凡是用父类型的地方都应能用子类型顶替而不破坏程序正确性。翻成契约语言，子类型的方法必须满足一份**至少和父类型一样强**的规约，也就是：

```
子类型方法：前置条件不能更强（只能更弱或相等）——逆变（contravariant），可接受更宽的输入；
            后置条件不能更弱（只能更强或相等）——协变（covariant），返回更具体的结果。
```

Liskov & Wing 1994 在此之上还加了一条**历史约束（history constraint）**：子类型不得引入"改动父类型视为不可变的状态"的新方法——即子类型不能偷偷放宽父类型承诺的不变性。

LSP 的方向和规约强弱**完全一致**——"子类型 = 更强（或相等）的规约"。所以只要记住 06-2.2.1 那条判据，LSP 的"前置只能放宽、后置只能收紧"就是它的直接推论，不必单独背。经典反例是"正方形继承长方形"：若长方形的 `setWidth` 承诺"只改宽、不改高"，正方形为保持边长相等偷偷也改了高，就削弱了后置承诺，违反 LSP，用正方形顶替长方形的代码会出错。

### 6.2.2.5 易错点小结与来源分歧

三个高频易错点集中提醒。其一，方向：**弱前置 + 强后置 = 强规约**，别把"前置更强"当成"更强规约"。其二，LSP 的"逆变/协变"：参数逆变（可更宽）、返回协变（可更窄），和契约强弱一一对应，不要记成反向。其三，"更强规约"不等于"更好的规约"——过强的规约（尤其过弱的前置逼实现者处理一切输入）可能难以实现或效率低；工程上要的是**恰当**强度，而非一味求强（这点在 Reading 7 "Designing good specifications" 里作为设计权衡讨论，本报告不深入）。

来源口径的一处细微差异值得记：MIT 6.031 用"前置/后置强弱"直接讲替换，不点 LSP 之名（Reading 7 全文未出现 "Liskov Substitution Principle" 字样）；LSP 的"逆变/协变 + 历史约束"表述来自 Liskov & Wing 1994 及后续 OOP 文献。两者结论方向一致、层次不同（6.031 停在规约层，LSP 明确到子类型层），本报告据一手逐句核对后合并陈述，未发现方向冲突。

## 6.2.3 ADT 操作分类

### 6.2.3.1 抽象数据类型：以操作而非表示定义类型

**抽象数据类型（abstract data type, ADT）**的核心思想是：**一个类型由它的操作定义，而不是由它的内部数据表示定义**。MIT 6.031 Reading 10 的原则句是"An abstract data type is defined by its operations"——操作及其规约完整刻画了这个类型的含义；对客户端，抽象值是**不透明（opaque）**的，只能通过被允许的操作去创建、观察、改动，不能直接窥探内部字段。

初学者可以对比"具体数据类型"来理解：说"用一个 `int[]` 表示集合"，这是在描述**表示**；而集合这个 ADT 真正是什么，取决于你提供了 `add`/`contains`/`size` 这些操作以及它们承诺的行为。同一个"集合 ADT"底下换成哈希表、位图或链表都行——因为客户端只认操作。这就是纵向抽象屏障：屏障之上是操作定义的抽象类型，屏障之下是可替换的表示（06-2.4 会给对齐两者的 AF/RI）。

Reading 10 把 ADT 的操作分成四类，用统一的抽象签名记法给出（`T` = 该抽象类型，`t` = 其它类型，`*` = 零个或多个，`+` = 一个或多个）。下面四节逐类讲。

### 6.2.3.2 creator（创建者）

**creator** 从"非本类型的输入"造出一个本类型的新对象。抽象签名：

```
creator:  t* → T
```

它的输入里**没有** T（`t*` 表示零或多个其它类型的参数），输出是一个全新的 T。常见实现形式是构造函数（如 `new Date()`），也可以是静态工厂方法（如 `Array.of()`）。

creator 是"无中生有"——你手上还没有这个类型的对象，用 creator 造第一个出来。区分它和 producer 的关键就在输入端有没有 T：creator 不吃 T，producer 吃 T。

### 6.2.3.3 producer（生产者）

**producer** 从"已有的本类型对象"造出"新的本类型对象"。抽象签名：

```
producer:  T+, t* → T
```

输入至少含一个 T（`T+`），可能还有其它参数，输出是一个**新的** T，而**不改动**输入对象。典型例子是 `String.concat`：吃两个字符串、产出一个表示其拼接的新字符串，原字符串不变。

初学者要抓的对比是 producer vs mutator：两者都"作用在已有对象上"，但 producer **产新对象、不改旧的**（函数式风格），mutator **原地改旧对象**（见 06-2.3.5）。不可变类型（如 String）只有 creator/producer/observer，没有 mutator——这也预告了 06-2.5"不可变性天然免疫表示暴露"。

### 6.2.3.4 observer（观察者）

**observer** 接收本类型对象，返回**其它类型**的值。抽象签名：

```
observer:  T+, t* → t
```

输入含至少一个 T，输出是别的类型 `t`（不是 T）。例子是数组的 `length`：吃一个数组、返回一个 number。observer 是客户端"看进"抽象值的唯一合法途径——因为表示不透明，客户端只能靠 observer 问出关于对象的信息。

初学者易混"observer 返回 T 的情况"：注意签名里 observer 的输出是 `t`（其它类型），一旦输出是 T，那通常就归到 producer 或 mutator 了。判类型时先看输出：输出非 T 且不改对象 → observer。

### 6.2.3.5 mutator（改变者）

**mutator** 原地**改动**本类型对象的状态。抽象签名：

```
mutator:  T+, t* → void | t | T
```

它作用在已有的 T 上并改变它，返回值可以是 `void`、某个 `t`（如被删掉的元素）或 T。例子是数组的 `push`：在数组末尾原地加一个元素，改动了这个数组本身。

先看"改不改输入对象"——改 → mutator；不改再看输出——输出 T 且输入有 T → producer，输出非 T → observer，输入无 T → creator。mutator 是不变量最容易被破坏的地方（它会改表示），所以 06-2.4 要求"每个 creator/producer/mutator 末尾都调用 checkRep"。

### 6.2.3.6 好 ADT 的四条品质与表示独立

Reading 10 给出评价 ADT 设计的四条品质。前三条关于操作集合：**简单（simple）**——宁可要"少而能强力组合的操作"，不要一堆特例；**连贯（coherent）**——每个操作有明确单一的目的、行为一致而非充满特殊情况；**充分（adequate）**——操作集合要够用，客户端想做的计算都能用现有操作组合完成。第四条是最重要的**表示独立（representation independence）**：

```
表示独立：抽象类型的使用独立于它的表示，改动表示不影响该类型之外的任何代码。
```

对初学者，"表示独立"是 ADT 一切好处的兑现点：正因为客户端只依赖操作、不依赖 `int[]` 还是哈希表，你才能在不惊动任何客户端的前提下把慢的表示换成快的。它也是 06-2.5 的直接动机——**表示暴露（rep exposure）会击穿表示独立**，让内部表示泄露给客户端，改表示就会连累外部代码。测试 ADT 时也要注意：应把 creator/producer/observer/mutator **放在同一批测试里配合使用**（因为不透明，得靠 observer 才能验证 creator/mutator 的效果），而不是孤立测每个操作。

## 6.2.4 表示不变量 RI 与抽象函数 AF

### 6.2.4.1 两个空间：表示空间 R 与抽象空间 A

实现一个 ADT 时存在两个世界：**表示空间 R（rep space）**——所有可能的内部数据取值（比如某类里那些字段的所有组合）；**抽象空间 A（abstract space）**——客户端心里的数学值（比如"一个整数集合""一个有理数"）。AF 与 RI 是把这两个空间对齐的一对工具，也是 06-2.3 那道纵向抽象屏障的精确刻画。

初学者可以把 R 想成"仓库里怎么摆货"，A 想成"顾客眼里买到的是什么"。同一件商品（抽象值）可以有多种摆法（多个 rep），而有些摆法根本是乱摆、不对应任何合法商品。AF 负责"这堆摆法代表哪件商品"，RI 负责"哪些摆法才算合法"。

### 6.2.4.2 抽象函数 AF：把表示映射到抽象值

**抽象函数（abstraction function, AF）**把表示值映射到它所表示的抽象值：

```
AF : R → A
```

**从表示 R 指向抽象 A**（不是反过来）。AF 通常是**满射（surjective / onto）**（每个抽象值都至少有一个 rep 表示它）、**不一定单射**（多个不同 rep 可以表示同一个抽象值，如 `-1/-2` 与 `1/2` 都表示有理数 ½）、因而**不一定双射**，而且**常常是偏函数（partial）**——因为 R 里有些取值根本不合法，AF 在它们上面没有定义。那"哪些 rep 才是合法的、AF 有定义的"，正是 RI 回答的。

AF 的方向。记法上是 `AF(rep) = 抽象值`，喂进去内部数据、吐出客户端看到的数学值。"一个抽象值可对应多个 rep"是常态（正因如此才需要 06-2.5 的防御——若把某个 rep 泄露出去被改，抽象值就变了）。

### 6.2.4.3 表示不变量 RI：界定合法表示

**表示不变量（representation invariant, RI）**把每个表示值映射到布尔，判定它是否"良构（well-formed）"：

```
RI : R → boolean
```

`RI(r)` 为真，当且仅当 r 是 AF 有定义的合法表示。换句话说，**RI 就是 R 中"AF 有定义"的那个子集**——它把 R 切成"合法 rep"与"非法 rep"两块，AF 只在合法那块上有定义。

用一个 `int` 列表表示"1..31 的天数集合"，RI 可以是"每个元素在 1..31、无重复、升序"。列表 `[1,3]` 满足 RI（合法），`[1,3,99]` 违反 RI（99 越界，非法）。RI 的作用是把"什么样的内部状态才算数"写死，任何创建或改动表示的操作都必须维持它。初学者要记住：RI 必须**精确**——"所有字段都合法"这种含糊话不算 RI，要写成可判定的数学条件。

### 6.2.4.4 checkRep：运行期守护不变量

`checkRep()` 是一个把 RI 用断言写出来、在运行期检查"当前表示是否仍满足 RI"的方法。Reading 11 的纪律：**在每个创建或改动表示的操作末尾都调用它**——也就是 creator、producer、mutator 结束时都 `checkRep()`；observer 一般不需要，但作为防御性习惯调用也无妨。

它的价值是**尽早抓 bug（fail-fast）**：一旦某段代码把表示改成非法状态，checkRep 会在那一刻当场断言失败，而不是等到很久以后抽象值出错、再回头苦苦调试。这直接呼应 06-3 "避免调试 = 让错误尽早、就地暴露"的纪律。初学者常见误区是"生产环境应该关掉断言、省性能"——checkRep 的定位恰恰是开发/测试期的安全网，它把"表示被谁悄悄改坏"这类最难查的 bug 变成一声立即的响铃。06-2.5 的实证就是用 checkRep 当场逮住一次表示暴露。

### 6.2.4.5 文档化 AF、RI 与安全论证

Reading 11 要求把 AF 与 RI **写成注释、就放在私有字段声明旁边**，且必须**精确**（数学化陈述，不能是"所有字段有效"这类空话）。典型格式：

```
class CharSet {
    private s: string;
    // Rep invariant:
    //   [精确的数学陈述]
    // Abstraction function:
    //   AF(s) = [把表示解释成抽象值的精确陈述]
}
```

此外还应写一段**表示暴露安全论证（rep exposure safety argument）**：逐个检查 rep 的每个部分、看处理它的代码（特别是参数进入和返回值离开的地方，因为暴露就发生在那里），论证为什么这段代码不会泄露表示。这段论证是 06-2.5 的书面形式——把"我为什么没暴露表示"讲清楚，而不是碰运气。对初学者，AF/RI/安全论证这三段注释合起来就是一个 ADT 实现的"设计说明书"：读代码的人（包括半年后的你）靠它一眼看懂内部表示的含义与约束。

## 6.2.5 表示暴露与防御拷贝

### 6.2.5.1 表示暴露的机理：泄露引用击穿抽象屏障

**表示暴露（representation exposure）**指的是"类之外的代码能直接改动内部表示"。Reading 11 明确它的双重危害：不仅**破坏表示不变量（RI）**，还**破坏表示独立**。最常见的成因是一句话：**返回一个指向可变内部对象的引用**——observer 把内部的可变 list / 数组 / 对象直接 `return` 出去，客户端拿到的是同一个对象的别名（alias），一改就改到了类的肚子里。构造函数把传入的可变参数直接存为字段，也是同一类漏洞（客户端手里还留着那个引用）。

你把保险柜里的原件（内部表示）直接递给访客看，还告诉他"随便改"。他一改，柜里的原件就变了，而且可能改成一个非法状态（违反 RI），也可能让"改表示不影响外部"这一承诺彻底失效（因为外部现在和内部共享同一个对象）。关键词是**别名（aliasing）**：暴露的本质是内外共享了同一个可变对象。

### 6.2.5.2 防御拷贝：进出边界都复制

针对可变类型，堵漏的标准手法是**防御拷贝（defensive copying）**：在两个方向都切断别名。**输入方向**——构造函数/mutator 收到可变参数时，存一份**拷贝**而不是原引用；**输出方向**——observer 要返回内部可变对象时，返回一份**拷贝**而不是本体。这样内外各持各的对象，客户端怎么改自己那份都不会碰到内部表示。

```
输入：this.field = copy(param)      // 别存客户端给的引用
输出：return copy(this.field)       // 别把内部引用交出去
```

初学者常问"到处拷贝不会很慢吗？"——会有成本，所以它是**可变类型**才需要的税。对不可变类型（下节）这税是零。工程上也有折中（返回不可修改视图、只在真有别名风险的边界拷贝），但入门阶段先把"可变对象过边界就拷贝"这条铁律记牢，比过早优化重要。

### 6.2.5.3 不可变性：从根上免疫表示暴露

更彻底的办法是让表示**不可变（immutable）**：如果内部对象根本不能被改，那么把它的引用交出去也无所谓——客户端拿到也改不动。这就是为什么不可变类型（如 Java 的 String、只含 final 不可变字段的类）**天然免疫表示暴露**，连防御拷贝都可以省。

这条把 06-2.3 的"不可变类型只有 creator/producer/observer、没有 mutator"和 06-2.5 接了起来：没有 mutator、字段不可变，就没有"被改坏"的可能，RI 一旦在创建时建立就永远成立。对初学者这是一个强有力的设计默认值：**能不可变就不可变**——它同时买到了线程安全（跨 L4-05 并发）、免防御拷贝、易推理三样好处。这也是 06-3「用不可变性作防御」将展开的主线，本报告点到为止。

### 6.2.5.4 表示暴露安全论证：把"没暴露"写下来

如 06-2.4.5 所述，Reading 11 要求为每个 ADT 写一段 **rep exposure safety argument**：逐一检查 rep 的每个可变部分，考察所有"客户端引用可能进入或离开"的点（构造函数参数、observer 返回值、mutator 参数），逐点论证为何不会造成别名共享。

对初学者，这段论证的价值在于把"我觉得应该没问题"变成"我逐点检查过、这里存的是拷贝、那里返回的是不可变对象、所以安全"。它是一种防御性思维的固化：表示暴露几乎总发生在"引用跨越类边界"的那几行，把这几行逐一盯过一遍，就能系统地堵住这类最隐蔽也最常见的 bug。

### 6.2.5.5 本机最小实证：checkRep 当场逮住一次表示暴露

按 prompt「本机实证可选」，下面用一个带 checkRep 的最小 ADT 坐实两件事：经由泄露引用的 observer 从外部改坏内部表示、checkRep 当场断言失败；改用防御拷贝后内部完好。基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25。

脚本（表示为 int 列表，RI = 元素∈1..31、无重复、升序；AF = 该天数集合）：

```
class MonthDays:
    def __init__(self, days):
        self._days = sorted(set(days))
        self._checkRep()
    def _checkRep(self):
        assert all(1 <= d <= 31 for d in self._days), f"RI broken: {self._days}"
        assert self._days == sorted(self._days)
        assert len(self._days) == len(set(self._days)), "RI broken: dup"
    def days_bad(self):   # observer：泄露内部可变 list 引用 —— rep exposure
        return self._days
    def days_safe(self):  # observer：返回防御拷贝，安全
        return list(self._days)
```

```
初始： MonthDays([1, 3])
经 days_bad() 泄露后被外部改写： MonthDays([1, 3, 99])
checkRep 捕获 RI 破坏： RI broken: [1, 3, 99]
经 days_safe() 拷贝被外部改写后，内部仍完好： MonthDays([2, 5])
checkRep 通过（防御拷贝有效）
```

输出直接坐实：`days_bad()` 把内部 list 引用交出去后，外部 `append(99)` 改到了内部表示，把它推入违反 RI 的非法状态（99 越界），`checkRep` 立刻断言失败并指出坏掉的表示；改用 `days_safe()` 返回拷贝，外部对拷贝的改动不影响内部，`checkRep` 通过。这就是 06-2.4（checkRep 守护 RI）与 06-2.5（防御拷贝堵表示暴露）合起来的最小闭环。（脚本在仓库外 scratchpad 运行，已清理，不入库。）
