## 06-11.1 红-绿-重构循环

### 06-11.1.1 三个阶段：red → green → refactor 的节奏

TDD（Test-Driven Development，测试驱动开发）的核心是一个不断重复的短循环：**先写一个当前会失败的测试（红），再写刚好让它通过的最小实现（绿），最后在测试保持通过的前提下清理代码结构（重构）**，然后进入下一圈。Kent Beck 在《Test-Driven Development: By Example》(2002) 里把这个节奏概括为两条规则：只在一个自动化测试失败时才写新的生产代码；消除重复。红-绿-重构就是这两条规则展开出来的操作步骤。

传统写法是"先把功能写完，再补几个测试看看对不对"——测试是**事后验收**。TDD 把顺序倒过来：**测试先行、由测试来"拉动"实现**。每一圈只前进一小步（一个小行为），所以你几乎永远处在"离上一个绿灯只有几分钟"的状态，出错时回退的代价极小。这三个颜色的说法来自测试运行器的惯例——失败的测试显示**红色**、通过显示**绿色**；"重构"阶段则要求全程保持绿色。

红-绿-重构是**一套开发做法（discipline），不是语言特性、也不是规范标准**。它没有"官方版本号"，不同作者的表述（Beck、Robert C. Martin、各测试框架文档）在措辞和步长建议上都有出入——这也是本篇多处打 ⚙演进快·锚版本 的原因。

### 06-11.1.2 red：先写一个会失败的测试，并且**亲眼看它失败**

循环的第一步是为"下一个想要的、最小的行为"写一个测试，此时生产代码还不能让它通过，所以运行必然失败（红）。关键纪律是：**你要真的运行它、亲眼确认它以你预期的原因失败**，而不是想当然地认为它会失败。

本机用 pytest 9.1.1 真跑一遍（罗马数字转换的例子，实现体故意留空）：

```python
# roman.py
def to_roman(n):
    pass

# test_roman.py
from roman import to_roman
def test_1():
    assert to_roman(1) == "I"
```

```
$ python3 -m pytest -q test_roman.py
>       assert to_roman(1) == "I"
E       AssertionError: assert None == 'I'
E        +  where None = to_roman(1)
FAILED test_roman.py::test_1 - AssertionError: assert None == 'I'
1 failed in 0.01s
```

为什么非要先看它失败？因为一个**从没红过的测试是不可信的**——如果它在实现还没写时就"通过"了，说明这个测试根本没在检查你以为它检查的东西（比如断言写反了、或根本没调用到目标代码）。红这一步同时验证了**两件事**：测试能被正确执行、并且它确实对"还不存在的行为"敏感。上面输出里 `assert None == 'I'` 精确地告诉你失败原因是"函数返回了 None"，这正是预期——测试可信，可以进入绿灯。

### 06-11.1.3 green：用**最小**实现让测试通过（fake it 与三角测量）

红灯之后，目标是**用最快、最少的代码让这个测试变绿**，哪怕实现"很傻"也没关系——此刻唯一的任务是让红变绿，正确的设计留到重构阶段。Beck 给了三种让测试变绿的策略：**Fake It**（先直接返回一个常量硬凑答案）、**Triangulation**（三角测量：再加一两个例子，逼你把硬编码泛化成真算法）、**Obvious Implementation**（如果正确实现一眼可见就直接写）。

本机演示 Fake It——先直接返回常量把第一个测试凑绿：

```python
# roman.py —— 故意"作弊"的最小实现
def to_roman(n):
    return "I"
```

```
$ python3 -m pytest -q test_roman.py
1 passed in 0.00s
```

`return "I"` 显然不是真的转换，但它让当前唯一的测试通过了——这是合法的一步。接着用**三角测量**逼它泛化：加入更多例子后，"作弊实现"立刻被打回红灯：

```
$ python3 -m pytest -q test_roman.py    # 参数化加入 2,4,9,40,90,2024 等例子
FAILED test_roman.py::test_to_roman[90-XC] - AssertionError: assert 'I' == 'XC'
7 failed, 1 passed in 0.02s
```

这时你别无选择、只能写出真正的算法，再次变绿：

```python
# roman.py —— 被多个例子逼出来的真实现
def to_roman(n):
    result = []
    for value, symbol in [(1000,"M"),(900,"CM"),(500,"D"),(400,"CD"),
                          (100,"C"),(90,"XC"),(50,"L"),(40,"XL"),
                          (10,"X"),(9,"IX"),(5,"V"),(4,"IV"),(1,"I")]:
        while n >= value:
            result.append(symbol)
            n -= value
    return "".join(result)
```

```
$ python3 -m pytest -q test_roman.py
8 passed in 0.01s
```

初学者最容易困惑的点是"先写作弊实现有什么意义"。意义在于**把步子切到足够小**：每一步只做"让下一个测试变绿"这一件事，你永远清楚自己在干什么、失败时问题范围极小。Fake It 和三角测量是"步子太大时"的减速手段——不确定怎么写才对时，先用常量凑绿，再靠多加例子一点点把它逼成通用算法。

### 06-11.1.4 refactor：在绿灯保护下清理设计

第三步是重构（refactor）：**在所有测试保持通过（绿）的前提下，改进代码的内部结构而不改变它的外部行为**——去掉重复、改好命名、抽出函数、理顺依赖。这是循环里"设计"真正发生的地方：绿灯阶段你只求通过、允许写得丑；重构阶段才把它收拾干净。每改一小步就重跑测试，一旦变红立即退回上一步。

一个初学者常犯的错误是把"绿了就进入下一个测试"当成循环的全部，**跳过重构**。后果是代码里的重复和坏结构越积越多（技术债），最终每加一个新测试都要在一堆乱麻里动手。Beck 反复强调"消除重复"是重构阶段的主线索——很多设计改进（抽公共方法、引入参数、提取类）本质上都是在回应"这里出现了重复"。因为此刻有测试兜底，你可以放心大胆地改，这正是下一小节 06-11.3"安全网"要展开的主题。

### 06-11.1.5 "三定律" vs Beck 原始表述（谁说的要分清）

社区里流传很广的"TDD 三定律（Three Laws of TDD）"——大意是：不写一个失败的测试就不许写生产代码；只写刚好够让它失败的测试；只写刚好够让当前失败测试通过的生产代码——**出自 Robert C. Martin（"Uncle Bob"），不是 Kent Beck 的原书**。Beck 原书的规范表述是前面 06-11.1.1 引的两条规则（"只在测试失败时写代码"+"消除重复"）加上红-绿-重构的操作循环。

之所以要分清出处，是因为这两种表述在**步长**上口味不同：Martin 的三定律把粒度压到"逐行、以秒/分计"的极小步，是一种更严格的纪律化叙述；Beck 原书更强调"根据你对问题的把握灵活调整步长"。初学者不必纠结哪个"正确"——两者是同一套做法的不同严格程度的表达，记住"谁说的"能帮你在读到不同教材时不被措辞差异绕晕。这类表述随社区演进、无权威版本，故标 ⚙演进快·锚版本。

### 06-11.1.6 步长控制：baby steps，以及何时可以放大步子

TDD 的一个隐含参数是**步长（step size）**——每一圈往前推多少。Beck 的建议不是"永远用最小步"，而是**根据把握动态调整**：对某个功能很有把握时可以直接用 Obvious Implementation 大步走；一旦遇到不确定、或刚吃了个红灯搞不清原因，就把步子切小（fake it + 三角测量），把不确定性关进一个几分钟就能验证的小循环里。

像走独木桥，脚下踏实时可以正常步幅，风大或桥窄时就改成一小步一停、每步都确认站稳。判断"步子是否该变小"的信号很直接——**如果你已经红灯超过几分钟还没弄绿、或者一次改动打红了一堆测试，就是步子太大了**，退回去、切小。这条经验在自动机/算法等其它课里没有对应物，是 TDD 特有的操作手感，值得初学者刻意练习。

## 06-11.2 测试先行作设计压力

### 06-11.2.1 可测性是一个设计反馈信号（"测试写得痛"往往是设计的坏味道）

本小主题的核心命题：**因为测试要先写，代码就必须从一开始就"容易被测试"，而"容易被测试"这个约束会反过来把代码推向更松耦合、依赖更清晰的结构。** 换句话说，可测性（testability）不是写完代码之后额外操心的属性，而是被 TDD 提前变成了一种**设计压力**——一段代码如果很难写测试，通常不是测试的错，而是这段代码把太多东西纠缠在了一起。

想给一个函数写单元测试时，你会本能地问"我怎么把输入喂给它、怎么把输出取出来检查"。如果发现"要测它必须先连上真实数据库 / 必须等到真实时钟到了下午 / 必须先启动整个 web 服务器"，那说明这个函数**把业务逻辑和外部依赖焊死在了一起**。这种"测起来很痛"的感觉（test pain）是一个信号——它指向的坏味道通常是**紧耦合**和**隐藏依赖**。TDD 让你在写实现之前就撞上这个信号，于是你会在设计成型前就把依赖解开。需要诚实标注的是：**"可测性倒逼出更好设计"本身也带有经验主张成分**（见 06-11.2.5），此处讲的是这套做法产生压力的机制，不是"结果一定更好"的断言。

### 06-11.2.2 依赖注入：把硬编码的依赖变成一个参数

回应上面那种"测起来很痛"最常见、最直接的手法就是**依赖注入（Dependency Injection, DI）**——不让一段代码**自己去创建/获取**它的依赖，而是让依赖**从外部作为参数传进来**。这样测试时就能传入一个受控的替身（stub/fake/mock，回指 06-10），生产时传入真实对象。

本机对照演示（pytest 9.1.1 真跑）。先看一个**把依赖焊死**的版本——它自己去读真实时钟，于是无法确定性地测试：

```python
# greet.py —— 依赖焊死：函数自己伸手去拿真实的墙上时钟
from datetime import datetime
def greeting_hardwired():
    hour = datetime.now().hour
    return "Good morning" if hour < 12 else "Good afternoon"
```

这个版本几乎没法为"下午分支"写一个可靠的测试——测试结果取决于你**什么时候**运行它（本机此刻 `datetime.now().hour` 真跑出来是 `0`，也就是说现在只能测到 morning 分支，afternoon 分支要等到中午以后才碰得到）。现在把"当前时间"**注入**为参数：

```python
# greet.py —— 依赖注入：把 now 变成参数，调用方掌控它
def greeting(now):
    return "Good morning" if now.hour < 12 else "Good afternoon"

# test_greet.py —— 两个分支都能确定性地测
from datetime import datetime
from greet import greeting
def test_morning():
    assert greeting(datetime(2026,7,30,9,0)) == "Good morning"
def test_afternoon():
    assert greeting(datetime(2026,7,30,15,0)) == "Good afternoon"
```

```
$ python3 -m pytest -q test_greet.py
2 passed in 0.01s
```

**为了让测试能控制"现在几点"，我们被迫把 `datetime.now()` 这个隐藏依赖从函数体里挤了出来、变成显式参数。** 这一步纯粹是被"可测性"逼出来的，但它顺带把函数变成了**纯函数**（同样输入永远同样输出）、去掉了对全局时钟的隐藏耦合——测试压力和好设计在这里指向了同一个方向。这就是"测试先行作设计压力"最典型的一次落地。

### 06-11.2.3 接缝（seam）：能替换依赖的那个"缝"

要能注入替身，代码里就得存在一个可以"从外面插手"的位置——Michael Feathers 在《Working Effectively with Legacy Code》(2004) 里把这种位置叫**接缝（seam）**：一个能在**不改动那段代码本身**的前提下、改变其行为的地方。函数参数是最简单的接缝（像上面的 `now`），构造函数参数、可覆写的方法、可替换的对象字段都是接缝。

06-10 讲的 stub/mock/fake 是**替身**（要塞进去的假东西），而 seam 是**塞它们进去的那个洞**。没有 seam 就没地方放替身、测试就得连真实依赖跑（慢、脆、不确定）。TDD 因为测试先写，会**天然地在代码里凿出这些洞**——你为了让测试能控制某个依赖，就得先留一个能注入它的接缝。反过来，给一段没留接缝的**遗留代码**补测试之所以难，正是因为要先想办法凿缝，这把我们引向 06-11.3.3 的遗留代码困境。

### 06-11.2.4 与"规约先行"的关系：先想清楚 spec，再写实现

TDD 的"先写测试"和 06-2 讲的"先写规约（前置/后置条件）"是同一种思维习惯的两个层面——都要求**在动手实现之前，先把"这段代码对外承诺什么"想清楚**。写一个测试，本质上就是在用一个具体例子**固定住一条规约**：`greeting(9点) == "Good morning"` 就是把"上午问早安"这条 spec 用可执行的形式钉下来。

MIT 6.031 的口径是把"先写规约"和"先写测试"并列为控制复杂度的手段：规约用自然语言/契约描述**意图**，测试用具体例子描述**可验证的行为**，两者都逼你在实现前先回答"我到底要做什么"。给初学者的提醒：TDD 的测试**不能替代规约**——测试只覆盖你想到的那些具体例子，规约才描述所有合法输入上的普遍承诺；成熟做法是先有 spec 的意图、再用测试把其中一批关键例子可执行化。这也是本篇把 06-2 列为先修的原因。

### 06-11.2.5 争议：测试驱动"改善设计"是经验主张，不是定论

必须诚实标注：**"TDD 能带来更好的设计 / 更少的缺陷 / 更高的生产力"这类效益断言，是长期存在争议的经验命题，业界至今没有一致结论。** 2014 年 David Heinemeier Hansson（DHH，Rails 作者）发表博文《TDD is dead. Long live testing.》，批评把 TDD 教条化会导致"测试诱导的设计损害（test-induced design damage）"——为了可测性过度拆分、过度使用 mock，反而把设计搞复杂、搞脆。随后 Kent Beck、Martin Fowler、DHH 三人做了系列对谈《Is TDD Dead?》（2014），公开辩论 TDD 的边界，Fowler 事后撰文总结。这场论战是本领域"两边都记、不作定论"的经典案例。

- **支持方（Beck 等）** 主张：测试先行提供快速反馈与信心、倒逼松耦合、让重构安全——这些是**经验主张**，在很多团队被报告为有效。
- **批评方（DHH 等）** 主张：严格 TDD 不是万灵药，过度追求单元可测性会造成过度 mock 与设计损害，在某些场景（如以数据库/框架为中心的 web 应用）成本高于收益。
- **实证研究** 结论**混杂、不一致**：多年来有多项对照/案例研究，方向不一（有的报告缺陷下降但开发时间上升，有的发现"红-绿-重构的严格顺序"本身影响不大、真正起作用的是"小步、均匀节奏"）。**这些研究的具体数字本报告不凭记忆填，一律标「待核」**——若要引用请回溯原始论文（如 Nagappan 等的工业案例、Fucci 等的对照实验）核实其条件与量级。

结论层面：把红-绿-重构当作一套**可选的、在很多情况下有用的开发做法**来学，而不是"不这么做就错了"的铁律；效益取决于团队、领域和执行方式。

## 06-11.3 重构安全网

### 06-11.3.1 重构的定义：改内部结构、不改可观察行为

**重构（refactoring）指的是在"不改变软件对外可观察行为"的前提下，改进其内部结构，使其更易理解、更易修改。** 这是 Martin Fowler《Refactoring》一书的定义。关键限定是"**不改变可观察行为**"——重命名变量、抽取函数、消除重复、调整类的职责都算重构；而修 bug、加功能、改接口语义**都不是**重构（因为它们改变了行为）。

日常口语里"我重构了一下"经常被用来泛指"我大改了一通代码"，但在工程语境里，**重构是一种有严格边界的操作——行为必须保持不变**。之所以要卡这么死，是因为只有"行为不变"这个约束成立，你才可能用"测试仍然全绿"来客观判断你的改动是安全的。这就直接引出安全网。

### 06-11.3.2 回归测试作安全网：让"改结构"这件事变得敢做

**回归测试（regression tests）** 是一组固定住"当前正确行为"的自动化测试；重构时，它们充当**安全网（safety net）**——你改完代码结构后重跑整个测试套件，**只要全绿，就说明可观察行为没被你改动破坏**；一旦变红，就精确指出你哪一步不小心改变了行为。有了这张网，"改结构"从一件提心吊胆的事变成一件可以频繁、大胆去做的事。

本机演示这张网怎么"接住"一次坏重构（pytest 9.1.1 真跑，仍用罗马数字例子）。先故意做一次**破坏行为**的改写：

```
$ python3 -m pytest -q test_roman.py     # 改坏了 to_roman 的实现
FAILED test_roman.py::test_to_roman[2024-MMXXIV] - AssertionError: assert '' ...
8 failed in 0.03s
```

网立刻变红、接住了错误。再做一次**保持行为**的正当重构（用 `divmod` + 常量表重写，逻辑等价）：

```python
# roman.py —— behavior-preserving 重构：抽出常量表、用 divmod
NUMERALS = [(1000,"M"),(900,"CM"),(500,"D"),(400,"CD"),(100,"C"),
            (90,"XC"),(50,"L"),(40,"XL"),(10,"X"),(9,"IX"),(5,"V"),(4,"IV"),(1,"I")]
def to_roman(n):
    out = ""
    for value, symbol in NUMERALS:
        count, n = divmod(n, value)
        out += symbol * count
    return out
```

```
$ python3 -m pytest -q test_roman.py
8 passed in 0.01s
```

同一套测试：坏重构 → 8 failed（被接住），好重构 → 8 passed（放行）。**这就是"安全网"三个字的全部含义**——它不替你重构，但它让你能立刻、客观地区分"我这次改动安不安全"，从而敢于持续清理设计。这也解释了为什么红-绿-重构循环里的"重构"阶段一定要**在绿灯下进行**：绿灯就是网已张开的证据。

### 06-11.3.3 先有覆盖，才能安全重构：遗留代码的困境

安全网有一个前提常被初学者忽略：**这张网必须先存在。** 对 TDD 从头写的新代码，测试是先于实现写的，网天然就在；但对一大坨**没有测试的遗留代码（legacy code）**，你想重构却发现"改了也不知道有没有改坏"——Feathers《Working Effectively with Legacy Code》(2004) 干脆把"legacy code"定义为**没有测试的代码**，并指出它的两难：**要安全改就得先有测试，但要给它加测试往往又得先改它（凿接缝）**。

给初学者的化解思路（Feathers 的核心手法，点到即止）：先找/凿出**接缝**（06-11.2.3），围绕你要改的那一小块补上**表征测试（characterization tests）**——不是去验证"正确行为应该是什么"，而是先**把它当前的实际行为原样记录下来**当作基准，然后在这层薄网的保护下小步重构。这条路径把 06-11.2（接缝/可测性）和 06-11.3（安全网）接了起来：可测性是能不能张网的前提，安全网是重构敢不敢下手的保障。

### 06-11.3.4 安全网的边界：它接不住什么

必须清醒：回归测试这张网**有洞**，不能盲信。至少三处边界要交代给初学者。

其一，**网只覆盖它测到的行为**——测试没覆盖到的路径、边界、输入组合上，重构即使把行为改坏了也不会变红（回指 06-10.3"高覆盖率≠高质量"、以及覆盖率盲区）。全绿只意味着"我测的那些例子行为没变"，不等于"所有行为都没变"。

其二，**测试自身可能是错的**——如果一条测试本身断言了错误的期望，它给你的"绿"是假的安全感；坏测试还可能在重构时"陪着一起对"，把错误一路放行。

其三，**脆弱测试（fragile / brittle tests）会误报**——如果测试过度绑定了实现细节（比如断言了内部调用顺序、私有结构，典型是过度 mock，回指 06-10.2 行为验证的代价），那么一次**纯粹的重构（行为没变）也会把它打红**。这时红灯不是"你改坏了行为"，而是"测试写得太贴实现"，反而拖累重构——这恰好又回到 06-11.2.5 里 DHH 批评的"测试诱导的设计损害"。好的安全网应当**验证行为、而非实现**，这样它才能在你重构时保持绿、只在行为真的变了时才响。
