## 06-3.1 静态 vs 动态检查

### 06-3.1.1 三档检查：静态检查、动态检查、不检查

一个错误在什么时候被发现，MIT 6.031 Static Checking 分成三档，原文的定义是：**静态检查（static checking）**——"the bug is found automatically before the program even runs"（程序还没跑就被自动发现）；**动态检查（dynamic checking）**——"the bug is found automatically when the code is executed"（代码执行时被自动发现）；**不检查（no checking）**——"the language doesn't help you find the error at all"（语言完全不帮你，得自己盯，否则拿到错误答案）。三档有明确的优先序，原文直接下结论：

```
Needless to say, catching a bug statically is better than catching it
dynamically, and catching it dynamically is better than not catching it at all.
```

初学者最容易混的是"静态/动态"跟"编译/运行"到底谁对应谁。抓一句话就够：**静态 = 编译期 = 还没运行；动态 = 运行期 = 正在运行**。"静"是因为程序是静止的一堆源代码文本，编译器只读文本就能判定；"动"是因为程序动起来了、有了真实的值在流动，才判得出。第三档"不检查"最危险——它不报错、不崩溃，只是默默给你一个错的结果，得靠你自己或测试才能发现。

一个贯穿本节的最小例子：把字符串传给只接收整数的函数。静态类型语言（下节展开）在编译期就拒绝它；动态类型语言要等真的执行到那一行、拿到那个字符串值，才可能抛错；而某些"不检查"的情形（比如下溢、整数截断）连运行时都不吭声，直接算出个错数。

### 06-3.1.2 静态检查捕获哪类错误：与具体值无关的错误

静态检查擅长抓的是**不依赖运行时具体值、只看程序结构与类型就能判定**的错误。MIT 6.031 列的典型静态可捕获类别是：语法错误（syntax errors）、拼错的名字（misspelled/未声明的名字）、参数个数不对（wrong argument counts）、参数类型不对（wrong argument types）、返回类型不对（wrong return types）。这些错误的共同点是：无论那个变量运行时到底等于几，错都是错——所以编译器不用运行程序就能定它的罪。

给初学者的直觉：静态检查大体上"关于类型"，回答的是"这个操作对这类东西合法吗"，而不问"这个具体的值是多少"。比如 `"abc" + 3`（把字符串和数字相加）在类型层面就可判——不管 `"abc"` 具体是什么字符串，这个操作要么被禁、要么按语言规则确定结果类型；编译器看类型即可裁决，不必真去拼这两个值。

本机可硬实证这一点。给一段有类型错误的 Python 交给 mypy（静态类型检查器），它在**不运行程序**的前提下就报错并以非零退出：

```
$ cat bad.py
def add(a: int, b: int) -> int:
    return a + b
result: int = add("hello", 3)   # 把 str 传给了 int 形参

$ python3 -m mypy bad.py         # 本机 mypy 2.3.0
bad.py:4: error: Argument 1 to "add" has incompatible type "str"; expected "int"  [arg-type]
Found 1 error in 1 file (checked 1 source file)          # 退出码 1，程序一次都没跑
```

这里 mypy 只读源码和类型注解就下了结论，`bad.py` 里的业务逻辑一行都没执行——这正是"静态"的含义。

### 06-3.1.3 动态检查捕获哪类错误：依赖运行时值的错误

动态检查抓的是**必须有了真实运行时值才判得出**的错误。MIT 6.031 列的典型动态可捕获类别是：非法的参数值（如除以零 divide-by-zero）、非法的类型转换、越界的下标（out-of-range indices）、对 null/undefined 的引用。它们的共同点是：合不合法取决于那个具体的值——`a / b` 本身完全合法，只有当 `b` 运行时恰好等于 0 才出错；`arr[i]` 本身合法，只有 `i` 运行时恰好越界才出错。编译器光看类型判不出来，得等值真的出现。

给初学者的直觉：动态检查大体上"关于值"。一句好记的对照——静态检查问"你这操作对这**类**东西讲得通吗"，动态检查问"你这个**具体的值**在这一刻合法吗"。因为要等到运行，动态检查发现 bug 的时机更晚、代价更高（下节 06-3.1.5），而且只有真的执行到那条路径、喂进那个坏值，才会触发——没被测到的路径上的坏值会漏网。

需要"规范 vs 实现"分账的地方：**同一类错误在不同语言里落在不同档**。数组越界在 Java/Python 是动态检查（抛异常），在 C 里却是"不检查"（未定义行为，可能读到垃圾、也可能段错误）；整数除零在多数语言是动态抛错，浮点除零在 IEEE-754 下却给 `Infinity`（不检查、返回特殊值）。所以"某类错误属于哪一档"不是绝对的，要落到具体语言/运行时来看。

### 06-3.1.4 "不检查"这一档与静默错误

第三档"不检查"意味着语言**既不在编译期拦、也不在运行期报**，程序照跑，只是给出错误结果或未定义行为。MIT 6.031 明确点出 TypeScript 之下的 JavaScript 运行时对某些情形就是 no checking——例如数组下标越界不抛错而是返回 `undefined`，除以零返回特殊值而非报错。这类错误最阴险，因为没有任何红灯，只能靠人工审查、测试或断言（06-3.3）去逮。

给初学者的直觉：前两档至少会"喊一声"（编译失败或运行时抛异常），而"不检查"是**闷声给你个错数**。C 语言里读越界内存、有符号整数溢出都属此列——程序不崩，跑出来一个看似正常其实错的值，可能几个月后才在生产暴雷。

这一档正是后面"类型安全 + 不可变 + 断言 + 静态分析工具"要合力堵的缺口：既然语言默认不帮忙，就靠设计（把非法状态设成不可表示，06-3.2）、靠 fail-fast 断言（06-3.3）、靠额外的静态分析器（06-3.4）把它从"不检查"往"静态/动态检查"这两档搬。

### 06-3.1.5 越早发现越省：检查时机的成本梯度

三档的排序本质上是一条**成本梯度**：bug 被发现得越早、离它被引入的时刻越近，定位与修复越便宜。MIT 6.031 Avoiding Debugging 把这条原则表述为 fail-fast 的依据——"The earlier a problem is observed (the closer to its cause), the easier it is to fix."（问题被观察到得越早、越靠近它的起因，就越好修）。静态 > 动态 > 不检查，正是"编译期 < 运行期 < 生产事故"这条时间线上越靠后越贵的直接推论。

给初学者的直觉：编译器报的错，行号就指着出错那一行，几秒钟就改掉；运行时的错，得先复现、看栈回溯、往回倒查是哪来的坏值；而"不检查"漏到生产的错，可能是用户投诉后才发现，还要在海量代码里反查根因。同一个 bug，在这三个阶段被抓，修复成本可能差几个数量级。

这条"越晚越贵"的量化曲线在业界常被追溯到 Boehm 的软件工程成本研究（"缺陷修复成本随阶段指数上升"），但**具体倍数因研究/年代/项目差异很大、且属经验主张**，此处标 `⚠经验主张·数值待核`，不引用具体倍数。教学上只需接受定性结论：能静态查掉就别留到运行时。

本机可对照演示"编译期拦下 vs 运行期才炸"。给 C 代码开不同的编译标志：

```
$ cat warn.c
#include <stdio.h>
int main(void) { int x; if (x == 5) printf("five\n"); return 0; }  /* x 未初始化 */

$ gcc -std=c11 warn.c -o a            # 无警告标志：静默编过，缺陷留到运行期
（无输出，退出码 0）

$ gcc -std=c11 -Wall -Wextra warn.c -o b   # 本机 gcc 13.3.0
warn.c:4:8: warning: 'x' is used uninitialized [-Wuninitialized]
```

同一份代码，开了 `-Wall -Wextra` 就把"用了未初始化变量"这个潜在缺陷提前到编译期暴露；不开，就得赌运行时的随机值恰好触发问题——这正是把 bug 从"晚"往"早"搬。

### 06-3.1.6 静态类型语言 vs 动态类型语言

一门语言把类型检查放在哪一档，决定了它是**静态类型（statically-typed）**还是**动态类型（dynamically-typed）**语言。MIT 6.031 原文：TypeScript 是静态类型语言，类型检查在编译期完成；"JavaScript and Python … are dynamically-typed languages, because this kind of checking is deferred until runtime."（JS、Python 是动态类型语言，因为这种检查被推迟到了运行时）。前者在你运行前就核对类型，后者要等值流到那一步才核对。

给初学者的直觉：静态类型 = 进门先查证件（编译期人人都得过安检），动态类型 = 出事再查（运行到哪查到哪）。静态类型的好处是整类类型错误跑之前就拦下、且对读代码的人是一份强制文档；代价是要写类型注解、有时和灵活性冲突。动态类型开发起步快、灵活，但把类型错误的发现推迟到了运行期甚至线上。

两个易错点要分清。其一，**静态类型 ≠ 强类型**：静态/动态说的是"何时检查"，强/弱说的是"允不允许隐式乱转"，是两个维度（06-3.2.5 展开）。其二，像 mypy（Python）、TypeScript 是给本是动态类型的语言**外挂**一层静态类型检查，叫**渐进类型（gradual typing）**——你可以只给部分代码加注解、逐步覆盖；没注解的部分退回动态行为。这属工具/语言特性，标 `⚙演进快·锚版本`（本机 mypy 2.3.0）。

## 06-3.2 类型安全与不可变性作防御

### 06-3.2.1 类型安全是什么：well-typed 的程序不会"卡住"

**类型安全（type safety / type soundness）**的工程直觉是：只要程序通过了类型检查（well-typed），运行时就不会发生"类型层面无意义"的操作——不会把一个整数当函数去调用、不会对字符串做只有数字才有的运算、不会因类型错配而进入未定义状态。换句话说，类型系统承诺"通过检查 ⇒ 这类错误运行时不会发生"。

给初学者的直觉：类型检查器像一个提前跑过所有类型组合的守门人，它证明的不是"你的程序算得对"，而是"你的程序不会因为把苹果当橙子用而在中途卡死"。它挡掉的是 06-3.1 里那一整类"参数类型不对、返回类型不对"的错误，而且是对**所有**输入一次性证明，不像测试只能覆盖跑到的用例。

边界要点（本报告不纵深，指向 L5-06）：类型安全"为什么成立"要靠 **progress（well-typed 程序要么是值、要么能继续算一步，不会卡住）+ preservation（算一步后类型不变）** 两条定理来证明，这属类型系统理论。本篇只用其结论：把更多约束编码进类型，就把更多错误挪进"静态可查"这一档。另需分账：类型安全是关于"类型层面不卡住"，**不**保证逻辑正确——类型对了照样能算错答案（那是规约与测试的职责，06-2/06-9）。

### 06-3.2.2 用类型把非法状态设计成"不可表示"

类型作防御的最强用法，是**让非法状态根本无法被表示（make illegal states unrepresentable）**——不是运行时检查"这个状态合不合法"，而是设计类型使非法状态压根构造不出来，于是那一整类 bug 被静态消除。这与 06-1 的"safe from bugs"、06-3.3 的"让 bug 不可能"是同一思想在类型层面的落地。

看一个最小例子，一个"要么成功带数据、要么失败带错误"的结果，若用两个可空字段 `{data?: T, error?: string}` 表示，就存在"两个都有"或"两个都没有"这种非法组合，得靠运行时判。改用**联合类型（tagged/discriminated union）**：

```typescript
type Result<T> =
  | { ok: true;  value: T }
  | { ok: false; error: string };
```

现在"既 ok 又带 error"这种状态在类型上就不存在，编译器还会强制你在用 `value` 前先判 `ok`——一整类"忘了判错就取值"的 bug 被设计掉了。

给初学者的直觉：与其事后拿断言检查"这个对象是不是处于合法状态"，不如一开始就不给它留出"非法状态"的位置。枚举替代裸字符串、非空类型替代可空、带单位的类型（`Meters` vs `Feet`）替代裸数字，都是这个套路。它把"记得检查"从程序员的自觉变成了编译器的强制。

### 06-3.2.3 不可变性作防御：不可重绑 vs 不可变对象

**不可变性（immutability）**是 MIT 6.031 明确点名的一条主要设计原则——原文："Immutability – intentionally forbidding certain things from change at runtime – will be a major design principle in this course."（不可变性，即刻意禁止某些东西在运行时改变，将是本课的一条主要设计原则）。它有**必须分清的两层**：一层是**引用不可重绑**（变量不能再指向别的对象），一层是**对象本身不可变**（对象内部状态不能被改）。

TypeScript 里 `const` 只给你第一层。MIT 6.031 原文："To make a reference unreassignable, declare it with the keyword `const` instead of `let`." —— `const` 让变量不能被重新赋值，但它指向的对象内部照样能改：

```typescript
const arr = [1, 2, 3];
arr = [4];        // 编译错误：不能重绑 const
arr.push(4);      // 合法！对象内部被改了——const 管不着
```

要第二层（对象不可变），得用 `readonly` 修饰或 `ReadonlyArray<T>`、Java 的 `final` 字段 + 不可变类、Python 的 `frozenset`/`tuple` 等。

给初学者最要命的易错点就是把 `const`（Java `final`）当成"这东西彻底冻住了"。它冻的只是"这个名字指向谁"，不是"被指向的对象长什么样"。想真正防住内部被改，必须在类型/对象层面另做不可变设计。C 语言的 `const` 又是另一套语义（承诺不通过该指针写），同样只是一层承诺、可被绕过——属"规范 vs 实现"要分账处。

### 06-3.2.4 不可变性消除的整类 bug：别名、共享可变状态、并发

不可变对象为什么是强力防御？因为它一次性关掉了好几类 bug 的来源。其一，**别名 bug（aliasing）**：两处引用指向同一个可变对象，一处改了另一处莫名其妙跟着变——若对象不可变，改不了，问题消失（这与 06-2.5 表示暴露、防御拷贝同源）。其二，**表示暴露**：不可变类型可以安全地把内部引用交出去而不怕客户端篡改，省掉防御拷贝。其三，**并发数据竞争**：多个线程读同一个不可变对象天然安全，无需加锁（呼应 017-concurrency 组：不可变即无竞争）。

给初学者的直觉：可变状态就像一块很多人都能涂改的白板，出了错很难说清是谁改的、什么时候改的；不可变对象像一张打印出来的纸，谁想要"改"只能另印一张新的，原件永远不变——于是"谁偷偷改了我的数据"这类最难调的 bug 从根上没了。

代价也要讲清（不是万能）：不可变意味着"改"要靠**造新对象**（producer 操作，见 06-2.3），频繁小改会有分配开销。工程上的取舍是"默认不可变、需要时才可变、可变范围尽量小"——这与 06-3.3.5 的最小化作用域是同一精神。

### 06-3.2.5 强类型 vs 弱类型、类型擦除（规范 vs 实现分账）

**强类型 / 弱类型**说的是语言**允不允许隐式的、不安全的类型转换**，跟静态/动态（何时检查）是**正交**的两个维度。Python 是动态但相对强类型（`"a" + 1` 直接抛错，不偷偷转）；C 是静态但相对弱类型（`int` 与指针、隐式窄化转换很多都放行）。所以"静态类型"不等于"类型安全"——C 是静态类型语言，却因弱类型和"不检查"留了大量漏洞。

给初学者的分辨法：静态/动态问"**什么时候**查类型"，强/弱问"查的时候**多严**、肯不肯睁只眼放过隐式转换"。四个象限都存在：静态强（TS 较严、Rust）、静态弱（C）、动态强（Python）、动态弱（早期 JS 的 `"5" - 1 === 4` 之类隐式转换）。

一个必须分账的实现细节：**类型擦除**。TypeScript 的类型检查纯发生在编译期，编译成 JavaScript 后**类型信息被完全抹掉**，运行时没有任何 TS 类型检查——也就是说 TS 的类型安全是"编译期承诺"，一旦有 `any`、外部 JSON 或 `as` 强制断言绕过检查，运行时不会兜底。这正是"规范（类型系统承诺）vs 实现（运行时其实不带类型）"的分账：类型检查器帮你，前提是你没在编译期把它骗过去。此项标 `⚙演进快·锚版本`（TS/mypy 的检查严格度随版本演进，如 `strict` 模式默认项时有调整，具体默认值待核所锚版本）。

- 锚点（一手承重）：MIT 6.031 sp22 Reading 08 Mutability & Immutability（https://web.mit.edu/6.031/www/sp22/classes/08-immutability/ ）与 Reading 01 Static Checking（同站 classes/01-static-checking/ ），`const` 不可重绑原句、"immutability 是主要设计原则"原句均核实自本站，2026-07-30。
- 交叉印证：不可变消除别名/表示暴露与 06-2.5（防御拷贝）同源，本组内部一致；并发安全性与 017-concurrency 组"不可变即无数据竞争"一致。
- 规范 vs 实现分账：`const`（TS/JS）只管引用不重绑 vs `readonly`/`final`/不可变类才管对象内部；C `const` 是"不通过此指针写"的可绕过承诺——正文两边记。TypeScript 类型擦除 ⇒ 运行时无类型检查，属编译期承诺，标 `⚙演进快·锚版本`。

## 06-3.3 「避免调试」纪律

### 06-3.3.1 两道防线：让 bug 不可能，其次局部化 bug

MIT 6.031 Avoiding Debugging 的中心论点是——"the best defense against bugs is to make them impossible by design."（对付 bug 最好的办法是靠设计让它们不可能发生）。整套纪律排成两道防线：**第一道，让 bug 不可能（make bugs impossible）**——用静态检查、不可变性、消除不可达代码等，从根上不给某类 bug 留位置；**第二道，局部化 bug（localize bugs）**——"If we can't prevent bugs, we can try to localize them to a small part of the program"（若挡不住，就把它们困在程序的一小块里，好让我们不必满世界找根因）。

给初学者的直觉：这一节把前两小节升华成日常习惯。"最好的调试是不调试"——因为调试（复现、下断点、看栈、二分定位）是整个开发里最耗时、最不可预测的活。与其练更强的调试术，不如从一开始就让 bug 更难产生、就算产生也被关在小笼子里。这也直接对应 06-1 的第一目标 safe from bugs。

第一道防线在前面已铺满：静态检查（06-3.1）、类型安全与不可变（06-3.2）都属"让 bug 不可能"。本节接下来讲第二道防线的具体手段：fail-fast、断言、增量开发、模块化封装与最小化作用域。

### 06-3.3.2 fail fast：越早暴露越靠近原因

**fail fast（快速失败）**指让程序在**第一时间、离错误起因最近的地方**就报错终止，而不是带着坏状态继续跑、在很远的地方才崩。MIT 6.031 的依据前面已引："The earlier a problem is observed (the closer to its cause), the easier it is to fix." 越晚失败，坏值流经的代码越多，最终崩溃点离真正的起因越远，反查越难。

给初学者的直觉：一个坏参数如果进函数就被立刻挡下，栈回溯直接指着调用它的那一行；如果不挡，让它一路传下去、写进某个字段、几百行后才因它算出个非法值崩溃，你面对的就是一个"案发现场离凶手十万八千里"的谜案。fail fast 就是把案发现场钉死在犯罪现场旁边。

这也解释了为什么 06-3.1 的"静态 > 动态 > 不检查"排序成立——静态检查是最极致的 fail fast（还没跑就失败），而"不检查"是最坏的 fail slow（带着错跑到底）。实践上，fail fast 的常见落地就是下面的断言与前置条件检查。

### 06-3.3.3 断言：断言什么、不断言什么、生产环境开关

**断言（assertion）**是在代码里写一句"此处我认定某条件必为真"，若运行时不真就立即终止——它是把规约（06-2 的 requires/effects）变成运行时自检的 fail-fast 手段。关键是知道**该断言什么、不该断言什么**。MIT 6.031 的指引：该断言的是"方法参数要求（argument requirements）"和"返回值要求（return value requirements）"，并且**边写代码边写断言**、而不是事后补；**不该**断言的是（a）测试编译器可靠性的琐碎断言（trivial assertions），（b）程序**外部**的条件——原文："Assertions test the internal state of your program"（断言检验的是程序的内部状态），像"文件存在""网络可达"这类外部条件不能用断言，得用正常错误处理。

给初学者的直觉：断言检查的是"我自己的代码逻辑有没有违反我对它的假设"（内部不变量、前后置条件），是给开发者看的自检；而"用户输入合法吗""文件在不在"是**预期会发生**的外部情况，属正常控制流，必须优雅处理、不能让断言把程序崩掉。判据：如果这个条件为假意味着"我的代码有 bug"，就断言；如果意味着"外部环境不如意"，就正常处理。

一个必须分账的实现细节：**很多语言在发布版里关掉断言**以省性能——原文提到"Many languages disable assertions in released code for performance"，并特别注明 **Node 的 assertions 总是运行**（不被关）。这带来一个经典大坑：**绝不能把有副作用的表达式写进断言**（比如 `assert(list.remove(x))`），否则生产环境断言被关，那次 remove 就没执行了。此项属"规范 vs 实现"分账（不同语言默认是否关断言不同，标 `待核·锚具体语言`）。

### 06-3.3.4 增量开发：一次只造一小块并彻底测试

**增量开发（incremental development）**指——原文："Build only a bit of your program at a time, and test that bit thoroughly before you move on."（一次只造程序的一小块，把这一小块彻底测好再往下走）。它是 fail-fast 在开发流程层面的体现：把系统一小块一小块地建、每块建完立即测，一旦出错，可疑范围就被限定在"刚写的那一小块"里。

给初学者的直觉：如果你把整个系统一口气写完再第一次运行，冒出来的 bug 可能藏在几千行的任何角落，无从下手；如果你每写几十行就测一次，新冒出来的 bug 几乎必然在你刚碰过的那几十行里。这就是把"搜索空间"从"整个程序"压到"最近一次改动"——本质仍是局部化。

它和两种支撑手段天然咬合：一是单元测试（06-9）——每块的"彻底测好"靠单测保障；二是版本控制的小步提交（06-4~06-6 的 Git）——每个能工作的小增量提交一次，出错时 `git bisect`/回退能进一步把 bug 定位到某一次提交。增量越小，回归定位越快。

### 06-3.3.5 模块化、封装与最小化变量作用域

局部化 bug 的结构性手段是**模块化（modularity）**与**封装（encapsulation）**，再加**最小化变量作用域（minimize scope）**。MIT 6.031：模块化指"dividing up a system into components … each … can be … reasoned about … separately"（把系统拆成组件，每个都能被单独理解、单独推理），一个模块出问题不至于牵连全局；封装则给模块筑墙，隐藏内部、只暴露受控接口，外部改不到内部状态。原文还点出："Minimizing the scope of variables is a powerful practice for bug localization."（最小化变量作用域是 bug 局部化的一个强力实践）。

给初学者的直觉：一个只在三行内可见的局部变量，能被谁改、在哪被改一目了然；一个全局变量，全程序任何地方都可能动它，出了错嫌疑人是整个代码库。作用域越小，一个变量的"可疑改动点"越少，反查越快。常见落地：变量用时才声明、循环变量声明在循环内、能局部就不全局、能私有就不公有、能不可变（06-3.2）就不可变。

这几条与本组前后一脉相承：封装/隐藏内部呼应 06-2.4 的 RI 守护与 06-2.5 的表示不封装之害；最小化作用域 + 不可变共同压缩"谁能改这块状态"的范围，是把第一道防线（让 bug 不可能）与第二道防线（局部化）拧在一起的抓手。

#### 来源与时效（本小主题）
- 锚点（一手承重）：MIT 6.031 sp22 Reading 09 Avoiding Debugging（https://web.mit.edu/6.031/www/sp22/classes/09-avoiding-debugging/ ，逐句核实 2026-07-30）——"靠设计让 bug 不可能"中心论点、两道防线、fail-fast、断言该/不该断言什么与"断言检验内部状态"、"发布版关断言 / Node 断言总运行"、增量开发、模块化/封装、最小化作用域原句均取自本页。
- 交叉印证：断言即 requires/effects 的运行时自检，与 06-2.1 方法规约一致；封装/隐藏内部与 06-2.4~06-2.5（RI 守护、防表示暴露）一致；增量开发 + 小步提交与 06-4~06-6（Git、bisect）一致。
- 规范 vs 实现分账：断言在发布版是否被关随语言而异（Node 总运行；Java `-ea` 默认关；Python `-O` 关），标 `待核·锚具体语言`；"绝不在断言里放副作用"为通用告诫。
- 待核：无独立数值型断言，无编造。

## 06-3.4 linter 与静态分析工具链

> 本小主题为 ⚠工具生态，整节标 `⚙演进快·锚版本·随时变`。具体工具的默认规则集、开关、版本行为随发布频繁变动，下文只锚本机实测版本（gcc 13.3.0、mypy 2.3.0）与一般定位，不承重、不编造具体默认规则；跨语言时"某工具具体行为"与"一般原则"分账。

### 06-3.4.1 编译器警告：最早、最零成本的一道静态防御

**编译器警告（compiler warnings）**是随手就有、零额外依赖的第一层静态分析——编译器在翻译代码时顺带指出"合法但很可能是 bug"的可疑写法。C/C++ 的 gcc/clang 默认为兼容历史只报少量警告，工程上应主动开 `-Wall`（一大批常见警告）、`-Wextra`（更多），并常配 `-Werror` 把警告升级为**硬错误**，让有警告的代码根本编不过——这就把警告变成了不可绕过的门禁。

给初学者的直觉：警告是编译器在说"这行语法没错，但你八成不是想这样"。默认不开等于把这些提示丢掉。`-Wall` 打开一大类经验证明"高度可疑"的模式，`-Werror` 则把"提示"变成"必须处理"，逼你要么修、要么显式标注这是有意为之。

本机实证（同一份未初始化变量的 C 代码，标志逐级收紧）：

```
$ gcc -std=c11 warn.c -o a                    # 无标志：静默编过（退出 0）
$ gcc -std=c11 -Wall -Wextra warn.c -o b      # 报 warning: 'x' is used uninitialized
$ gcc -std=c11 -Wall -Werror warn.c -o c      # 同一处升级为 error，退出码 1，编译失败
warn.c:4:8: error: 'x' is used uninitialized [-Werror=uninitialized]
cc1: all warnings being treated as errors
```

第三条命令展示了门禁的本质：`-Werror` 让"用了未初始化变量"直接挡下构建（本机 gcc 13.3.0 @2026-07-30 实测）。易错点：编译器警告本质是启发式，有漏报也有误报，`-Wall` 并非"所有警告"（名字有误导），更严的检查要继续加 `-Wextra` 及具体 `-W...` 项——具体项集合随 gcc 版本演进，标 `⚙演进快·锚版本`。

### 06-3.4.2 类型检查器：给动态语言外挂的静态类型门

**类型检查器（type checker）**是把 06-3.1/06-3.2 的静态类型检查独立成一个工具，尤其用来给本是动态类型的语言外挂静态检查：Python 的 **mypy**、JavaScript 的 **TypeScript（tsc）**、Python 的 pyright 等。它们做**渐进类型（gradual typing）**——你给代码加类型注解，工具据注解在不运行程序的前提下查类型错误；没注解的部分退回动态。

给初学者的直觉：这类工具让你在保留动态语言灵活性的同时，逐步买到静态类型的安全网——先给关键模块加注解、让 CI 跑类型检查挡住类型错误，其余部分照旧。它抓的正是 06-3.1.2 那一整类"参数/返回类型不对"的错误。

本机 mypy 2.3.0 对未运行代码的类型错误直接报错并以退出码 1 结束（命令与输出见 06-3.1.2），可作 CI 门禁的一关。分账要点：类型检查器的严格度靠开关调（如 mypy 的 `--strict`、tsc 的 `strict`），默认放过很多情形；且 TypeScript 类型编译后被擦除、运行时无兜底（06-3.2.5）。这些默认项/严格项随版本变，标 `⚙演进快·锚版本`，具体默认值 `待核·锚所用版本`。

### 06-3.4.3 linter：风格与"可疑模式"检查

**linter** 是专查**代码风格与可疑（但合法）模式**的静态工具——命名规范、未使用变量、可疑的相等比较、易错惯用法等。典型有 JS/TS 的 **ESLint**、Python 的 **Ruff/Flake8/Pylint**、C/C++ 的 **clang-tidy**、shell 的 shellcheck。它和编译器警告、类型检查器有重叠，但更偏"团队约定 + 经验坑位"的可配置规则集。

给初学者的直觉：编译器/类型检查器管"对不对（会不会出类型错）"，linter 更多管"好不好、像不像坑"——它标出的很多东西编译能过、也不一定是 bug，但按经验很可能是隐患或坏味道。规则通常可逐条开关、可 per-project 配置，所以团队间口径差异大。

这里的要点与易错在于，linter 规则集是**约定不是规范**，不同项目/版本差异极大，且以**误报**换"多提醒"，需要团队校准（关掉噪声规则、把重要规则设为 error）。工具与规则演进极快，标 `⚙演进快·锚版本·随时变`，本文不列具体默认规则以免编造。

### 06-3.4.4 静态分析 / SAST：跨函数的数据流与缺陷模式挖掘

更深的一层是**静态分析器（static analyzer）**，它不只看单行可疑模式，而是做**跨函数的数据流/控制流分析**，去挖空指针解引用、资源泄漏、越界、并发缺陷、安全漏洞（污点分析）等。代表有 clang static analyzer、Coverity、Java 的 SpotBugs（前身 FindBugs）、Infer，以及面向安全的 **SAST（Static Application Security Testing）**工具。它们把 06-3.1.4"不检查"那一档里的隐蔽 bug 尽量往"静态可查"搬。

给初学者的直觉：linter 像"逐句挑语病"，静态分析器像"顺着变量的来龙去脉推演，判断某条执行路径上会不会解引用一个可能为 null 的指针"。它能发现单看一行看不出、要跨多个函数才暴露的问题，代价是分析更重、更慢。

一个初学者必须建立的核心权衡是 **soundness（不漏报）vs completeness（不误报）** 的取舍：静态分析理论上无法既不漏报也不误报（可判定性所限）。实践中的工具都在两端做取舍——偏"少漏报"就会多误报（噪声大），偏"少误报"就可能漏真 bug。所以静态分析的产出需要人去分诊（triage），把误报标记掉、真问题修掉。此权衡的理论根在 L4-04/L5-06/026 程序分析，本篇只取工程结论。

### 06-3.4.5 在门禁里的定位：把静态检查前移进 CI

这些工具的工程价值，最终体现在**把它们装进持续集成的门禁（gate）**：每次提交/PR 自动跑编译器警告（`-Werror`）、类型检查（mypy/tsc）、linter、静态分析，任一不过就挡住合并——于是"静态可查"的错误在代码进主干**之前**被拦下，落实 06-3.1.5 的"越早越省"。这条正是本组 06-12（CI 与门禁）的一个组成阶段，本篇只点定位、机制细节留 06-12。

给初学者的直觉：一个人本地跑不跑这些检查全凭自觉，靠不住；把它们设成"不过就不能合并"的门禁，就把纪律从个人习惯变成团队的机器强制——这与 `-Werror` 把警告升级为错误是同一招（把"建议"变"强制"），只是搬到了团队协作层。

落地的现实取舍要讲清：门禁不是越多越严越好——误报太多会让人习惯性忽视（狼来了），慢的分析会拖垮反馈速度。常见做法是分层：快而准的（编译警告、类型检查、lint）设为**阻断式**门禁跑在每次提交；慢而全的（重型静态分析/SAST）设为**非阻断**或定时跑，产出交由人分诊。具体平台/工具与配置属 ⚠工具生态，标 `⚙演进快·锚版本·随时变`。
