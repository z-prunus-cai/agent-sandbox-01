## 6.13.1 delivery vs deployment 分账

### 6.13.1.1 持续交付（continuous delivery）的定义

持续交付是一种软件开发**纪律**：你以某种方式构建软件，使得软件**在任何时刻都能够被发布到生产环境**。Fowler 站点给的原话是「Continuous Delivery is a software development discipline where you build software in such a way that the software can be released to production at any time」，并列出可操作的判据：软件在整个生命周期里始终「deployable」、团队把「保持软件可部署」置于「开发新功能」之上、任何人在任何改动后都能对系统的「生产就绪度」拿到快速自动反馈、可以「push-button」地把**任意版本**部署到**任意环境**。这与 Humble-Farley《Continuous Delivery》(2010) 的核心表述一致——让软件**始终处于可发布状态（always in a releasable state）**。

对初学者，抓住一个词：持续交付强调的是一种**状态/能力**，不是一个动作。它不承诺「你每天真的发很多次版」，只承诺「你**随时想发就能发**，而且是低风险、按钮式地发」。为什么这很难？因为要做到「随时可发」，就得让每次改动都自动经过构建、测试、验证、且随时能部署到任一环境——这正是它要求「优先保持可部署，而不是优先堆功能」的原因。它是大主题06-12「CI 保证主干始终可构建可发布」这条纪律向「一路到生产」的自然延伸。

### 6.13.1.2 持续部署（continuous deployment）的定义

持续部署把持续交付再往前推一步：**每一次通过流水线的变更都自动被送进生产**，于是一天里会发生很多次生产部署。Fowler 的原话是「Continuous Deployment means that every change goes through the pipeline and automatically gets put into production, resulting in many production deployments every day」。它与持续交付的关系被 Fowler 点得很死——

```
持续部署 ⊃ 持续交付            （做持续部署，必然已经在做持续交付）
持续部署 = 持续交付 − 那道"人工放行"的门
```

Fowler 明说：「In order to do Continuous Deployment you must be doing Continuous Delivery.」

对初学者，最省事的记法是：**持续交付是「能自动发，但发不发由人决定」；持续部署是「连『发』这个决定也自动化了」**。两者共用同一条流水线、同一套自动化测试与门禁，唯一差别在流水线末端那一步——持续交付在「进生产」前留了一道人工放行闸（有人点一下「上线」），持续部署把这道闸也拆了，测试全绿就直接进生产。所以持续部署一定是持续交付的**超集**：你不可能在「还不能随时安全发布」的前提下让机器天天自动发布。

### 6.13.1.3 界线的本质：技术能力 vs 业务决策

两者真正的分界，不在技术强弱，而在「**谁来决定发布**」。持续交付把系统做到「技术上随时可发」，但**是否发、何时发，是一个业务/产品决策**，由人来拍板（比如要配合市场活动、要避开高峰、要等合规签字）。持续部署则是团队**主动选择**把这个决策也交给流水线——只要质量门禁通过就发。

持续部署**不是**「更高级、人人都该追求的终点」，持续交付**也不是**「没做完的持续部署」。很多成熟团队**刻意停在持续交付**——因为它们的业务就是需要人来控制发布时机（金融、医疗、面向企业客户的私有部署等）。选持续交付还是持续部署，是看「你愿不愿意、能不能把发布决策完全托付给自动化」，而不是技术段位高低。这条业务/技术分账，是本小主题最该记住的一句。

### 6.13.1.4 术语混用与「CD」二义（易错点·必读）

「continuous delivery」和「continuous deployment」在业界**长期被混用**，很多文章、工具文档把二者当同义词，缩写「CD」本身也**二义**（在「CI/CD」里既可能指 delivery 也可能指 deployment）。这是本领域最常见的沟通事故来源。

对初学者，处理办法是：看到「CD」先别默认它指哪个，**按 Humble-Farley/Fowler 的原定义去对齐**——关键就问一句「**末端那步进生产，是人点的还是自动的？**」人点的=持续交付，自动的=持续部署。本报告采原定义、两边都记：delivery = 具备随时发布的能力（发不发由人）；deployment = 每次变更自动进生产。遇到别人用「CD」时，确认对方指的是哪一个，比争论定义更有用。

### 6.13.1.5 与 CI、feature flag 的衔接（部署 ≠ 发布）

CD 不是凭空长出来的：它**站在 CI（大主题06-12）的肩膀上**。CI 保证「每次改动合进主干后主干仍可构建、测试仍绿」，CD 接着把这个「随时可用的好主干」一路推向生产。没有可靠的 CI 与自动化测试，CD 无从谈起——因为「随时可发」的前提是「随时确信它是好的」。

这里还要接上大主题06-8.3 已经讲过的一个关键区分：**部署（deployment）≠ 发布（release）**。部署是「把新代码送上生产服务器」，发布是「让某功能真正对用户生效」。feature flag（特性开关）能把二者解耦——代码可以先部署上线但用开关关着，用户看不到；等想发布时再打开开关。这一解耦对持续部署尤其重要：它让「把代码自动送进生产」变成低风险的日常动作（半成品被开关挡着），而「让用户真正看到新功能」成为一个独立、可控、可随时开关的决策。换句话说，feature flag 让「频繁自动部署」与「谨慎控制发布」可以同时成立。

## 6.13.2 环境晋级流水线

### 6.13.2.1 部署流水线（deployment pipeline）是什么

「部署流水线」是 Humble-Farley《Continuous Delivery》(2010) 的核心概念：把**从「一次提交」到「发布进生产」的全过程**建模成一条**自动化的、分阶段的传送带**，每次变更都要走同一条管线，在每个阶段接受越来越严格的验证，任一阶段失败就停下、不再往前。Fowler 也把「extensive automation … usually using a DeploymentPipeline」列为持续交付的必备机制。

```
提交 → [提交阶段]        编译 + 单元测试 + 静态检查（几分钟，快反馈）
     → [验收阶段]        自动化验收/集成测试（较慢）
     → [部署到 staging]  在类生产环境验证
     → [人工/自动放行]   ← 持续交付在这里等人点；持续部署这步自动
     → [部署到 prod]     进生产
（示意，非实证输出；阶段命名随团队/工具不同）
```

对初学者，把它想成「一道道逐渐变严的关卡」。越靠前的关卡越快、越便宜（几分钟就能告诉你「编译过没过、单测绿不绿」），越靠后越慢、越接近真实（在类生产环境跑完整验收）。这样设计的用意是**快速淘汰坏改动**：能在第一关几分钟内发现的问题，绝不拖到最后一关几十分钟才发现。这与大主题06-12 讲的「CI 门禁阶段（构建→单测→静态检查）」是同一思想的延续——CD 的流水线就是把 CI 的门禁**一路延长到了生产**。

### 6.13.2.2 dev → staging → prod 逐级门禁晋级

流水线在空间上体现为一串**环境**：典型是 dev（开发）→ staging（预生产/类生产）→ prod（生产），改动必须**逐级晋级（promote）**，每级之间设**门禁（gate）**，只有通过本级验证的制品才能晋级到下一级。

对初学者，关键直觉是「**离用户越近，关卡越严**」。dev 环境随便挂、随便改，影响面小；staging 要尽量像生产、跑完整验收，是「进生产前最后一次彩排」；prod 直接面向真实用户，任何问题都会被用户看到。逐级晋级的意义就是：让每个改动在「越来越像生产、代价越来越高」的环境里被反复检验，等它爬到 prod 门口时，你对它的信心已经很足了。这也解释了为什么不能「dev 测完直接上 prod」——中间少了 staging 这层「像生产但不影响用户」的验证，风险陡增。

### 6.13.2.3 构建一次、四处部署（build once, deploy many）与配置外置

一条重要且容易被初学者忽略的纪律：**同一个制品（artifact）从头晋级到尾，不在每个环境重新构建**。Humble-Farley 的原则是「build binaries once」——在提交阶段构建出唯一的制品（jar/镜像/包），之后 dev/staging/prod 部署的都是**同一个二进制**，各环境的差异只通过**外部配置**（环境变量、配置文件、密钥）注入。

```
构建一次 →  artifact:v42  ── 部署 → dev
                          ── 部署 → staging   （同一 v42，只换配置）
                          ── 部署 → prod       （同一 v42，只换配置）
（示意）
```

对初学者，这条为什么重要？因为如果每个环境**各自重新构建**，你在 staging 测过的东西和最终进 prod 的东西**可能不是同一个二进制**（依赖版本漂移、构建机差异都会让它们悄悄不一致），那 staging 的验证就白做了——你测的是 A，上线的是 A′。「构建一次、四处部署」保证「测的就是发的」。配套地，配置必须和代码**分离、外置**（回指 L5-13 ConfigMap/Secret 的同类思想），否则「同一制品跑各环境」无从实现。这也让回滚变得干净（见 6.13.4.4）：回滚就是重新部署那个已知good的旧制品。

### 6.13.2.4 门禁：自动门 vs 人工审批门

每级之间的门禁分两种。**自动门**由流水线机器判断——测试全绿、覆盖率达标、静态检查无阻断问题就自动放行；**人工审批门（manual approval / manual gate）**需要人点一下才放行，常用于「进生产」这最后一步，或需要合规/变更管理签字的场景。持续交付通常在「进 prod」处保留人工门；持续部署则把它也改成自动门。

对初学者，别把「人工门」理解成「不够自动化、落后」。人工门是**主动的业务控制点**，不是技术缺陷——它让人来决定「现在这个时机适不适合发」（要不要避开促销高峰、等不等合规批准）。判断一个团队是持续交付还是持续部署，最直接就是看「进生产这道门是人工的还是自动的」（呼应 6.13.1.3）。工具侧（GitHub Actions 的 environment protection rules、GitLab 的 manual jobs / protected environments 等）都提供「人工审批」配置，但**具体字段/默认值随产品演进**，属 ⚠二手、仅指路、待核。

### 6.13.2.5 环境奇偶性（environment parity）及其局限

「环境奇偶性」指让 staging 尽量**与 prod 一致**——同样的操作系统、依赖版本、数据规模、网络拓扑、配置形态——这样「在 staging 通过」才能有效预测「在 prod 也没问题」。这是逐级晋级能给出可信信号的前提。

对初学者要同时讲清它的**局限**，避免过度信任 staging：staging 永远**不可能**和 prod 完全一致——真实用户流量的规模与形态、真实数据的脏乱、真实的并发与长尾负载、第三方系统的真实行为，都很难在 staging 复刻。所以「staging 全绿」只降低风险、**不消灭风险**，总有一类问题只在生产真实条件下才暴露。这恰恰是下一节「部署策略」（尤其金丝雀）存在的理由：既然无法在上线前测尽一切，那就在**生产里**用小流量、可回退的方式谨慎地把新版本接进去。

## 6.13.3 部署策略

### 6.13.3.1 为什么需要部署策略（总纲与下沉边界）

「部署策略」回答的问题是：**怎么把新版本接进正在服务用户的生产系统，而不造成停机、又能控制风险**。最朴素的做法是「大爆炸式替换」——停掉旧版本、全量换上新版本——但它有两个致命问题：切换期间**服务中断（停机）**，且一旦新版本有问题就是**全体用户同时受影响**。蓝绿、滚动、金丝雀就是为规避这两点而生的几种「换挡手法」。

**蓝绿**=准备一整套新环境、一刀切过去（切换快、可秒回，但要双份资源）；**滚动**=一批一批地换实例（省资源、无需双份，但切换过程中新旧混跑）；**金丝雀**=先给一小撮用户尝新、看指标好再逐步放量（风险最小、最谨慎，但机制最复杂）。**本报告只讲到这层入门直觉与机制轮廓**；再往下的两件事明确下沉、不在此展开：**「靠什么指标/错误预算决定金丝雀继不继续放量」= 发布决策**，见 **L5-12 §12-10**；**「用 K8s Deployment / Argo Rollouts / Flagger 等怎么把这些策略编排落地」= 编排实现**，见 **L5-13**。

### 6.13.3.2 蓝绿部署（blue-green deployment）

蓝绿部署准备**两套尽可能一致的生产环境**，任一时刻只有一套对外服务（比如「蓝」在线），新版本先部署到**另一套闲置环境（「绿」）**，在绿环境做最后验证，确认无误后**切换路由器/负载均衡器，把所有进来的请求一次性导向绿环境**；出问题就把路由切回蓝环境。Fowler 原话：确认绿环境工作正常后「switch the router so that all incoming requests go to the green environment」，「if anything goes wrong you switch the router back to your blue environment」。两套环境随后循环轮换角色（这次的旧版蓝，下次就作为新版的待命环境）。

对初学者，画面是「两条一模一样的跑道，用一个道闸决定车流走哪条」。它最大的优点是**切换和回滚都极快**（就是拨一下路由开关，接近瞬时），且切换前能在完整的绿环境里从容验证。代价是**要维持两份生产资源**（成本高），以及 Fowler 点出的两个真实难点：一是切换瞬间「in-flight」的**在途事务/丢失事务**如何处理；二是**数据库**——两套环境通常共享数据库，schema 变更不能想切就切。Fowler 的建议是「**把 schema 变更与应用升级分开部署**」：先做一次让**新旧两个版本都能用**的数据库重构、部署它、确认好了（这样有回滚点），再部署新版本应用。这条「数据库要同时兼容新旧」的约束会在 6.13.3.5 与 6.13.4.3 再出现，是所有部署策略共同的隐形难点。

### 6.13.3.3 滚动部署（rolling deployment）

滚动部署**不另起一整套环境**，而是把新版本**一批一批地替换**掉现有实例：先下掉一小批旧实例、换上新版本、确认健康，再下一批，如此逐批推进，直到全部实例都是新版本。整个过程服务一直在线（总有实例在服务），不需要蓝绿那样的双份资源。

对初学者，这是云原生里最常见的默认策略（K8s 的 Deployment 默认更新方式即为 RollingUpdate；**其可调参数如 maxSurge/maxUnavailable 的具体默认值属 L5-13 与工具文档、⚙演进快·待核，本报告不给具体数值**）。要讲清它的一个内在特性与代价：滚动过程中**新旧版本会同时在线并存**一段时间——这带来两个初学者必须知道的约束。其一，新旧版本必须能**共存**（比如都能读写同一数据库、API 向后兼容），否则混跑期间会出乱子。其二，回滚不像蓝绿那样「一拨开关瞬间回去」，而是要**再滚一轮**把实例逐批换回旧版本，所以回滚也是渐进的、需要时间（见 6.13.4.2）。它与金丝雀的界线有时模糊——可以把金丝雀看成「带指标观察与放量决策的、更谨慎的滚动」。

### 6.13.3.4 金丝雀发布（canary release）

金丝雀发布通过**先把新版本只放给一小撮用户**、观察无恙后再逐步扩大，来降低「新版本引入生产」的风险。Fowler 原话：「slowly rolling out the change to a small subset of users before rolling it out to the entire infrastructure」。做法上，新版本先部署但不接流量，然后「start routing a few selected users to it」（可随机抽样、可先给内部员工、可按人群划分），随信心增长「releasing it to more servers … and routing more users to it」，直到全部用户迁移完；一旦发现问题，「the rollback strategy is simply to reroute users back to the old version」。它的一个额外好处是能在真实生产条件下对新版本做**容量/性能观测**，无需单独的容量测试环境。

对初学者，名字来自「矿井里的金丝雀」——用一小撮先行者去探测危险，代价可控。它和滚动部署的关键差别在于**有没有「看指标再决定放不放量」这一步**：滚动只是机械地逐批替换，金丝雀在每次扩大流量前会**对比新旧版本的关键指标**（错误率、延迟等），指标坏就停、就撤。**但「用哪些指标、阈值多少、错误预算耗尽就冻结发布」这套发布决策逻辑，是本报告的下沉边界——纵深见 L5-12 §12-10（发布工程与金丝雀发布、错误预算驱动发布决策）**；「用 Argo Rollouts / Flagger 等如何自动跑金丝雀分析与放量」的编排落地见 **L5-13**。本报告到「小流量灰度 + 看指标 + 逐步放量 + 出事撤流量」这层直觉为止。

### 6.13.3.5 数据库与向后兼容：所有策略共同的横切约束

三种策略有一个共同的隐形前提：**部署/切换期间，新旧版本几乎总要短暂并存**（滚动在混跑、蓝绿共享库、金丝雀新旧同时在线），因此**数据库 schema 与 API 必须同时兼容新旧两个版本**，否则一切换就崩。业界把这套手法叫 **expand-contract（又称 parallel change，扩展—收缩）**：先「扩展」——加出既容纳旧版又容纳新版的兼容 schema（如新增列而非改列），让新旧都能跑；等旧版本彻底退役后，再「收缩」——清掉只服务旧版的残留。这正是 Fowler 在蓝绿词条里建议「先做兼容新旧的数据库重构、再升级应用」的一般化。

对初学者，记住一句：**代码可以秒切秒回，数据不能**。数据库迁移往往是「不可逆或很难逆」的——你把一列删了、把数据改了格式，想切回旧代码时旧代码可能已经读不了新数据。所以「向后兼容的、分两阶段的数据库变更」是让蓝绿/滚动/金丝雀的「快速回滚」承诺**真正成立**的前提。忽视这一点，是初学者做部署时最容易踩、且后果最重的坑——它直接决定了下一节「可回退性」是不是纸上谈兵。

### 6.13.3.6 三种策略速览对比

```
策略      是否需双份资源   切换粒度        回滚方式             机制复杂度
蓝绿      需要（两套环境）  一次性全切      拨路由切回旧环境(快)  低~中
滚动      不需要           逐批替换实例    再滚一轮回旧版(渐进)  中
金丝雀    通常不需要       小流量→逐步放量  撤回流量到旧版        高(需指标分析)
（示意·非规范；各条细节随工具/团队不同，⚙演进快·待核）
```

对初学者，这张表不是让你背，而是给一个「按约束选型」的直觉：极看重「秒级回滚、切换前充分验证」且资源不紧张，偏蓝绿；资源紧张、能接受新旧混跑、想要云原生默认省心，偏滚动；风险极高、想用真实小流量探路并靠指标把关，偏金丝雀。现实中三者常组合（如「金丝雀 + 滚动放量」）。再次强调：**选哪种、怎么定放量与回滚的触发指标，其决策纵深在 L5-12 §12-10，编排落地在 L5-13**，本报告不展开。

## 6.13.4 回滚与可回退性

### 6.13.4.1 回滚作为发布安全网：可回退性比不出错更现实

无论流水线多严、部署策略多谨慎，生产事故**无法完全避免**（6.13.2.5 已说明 staging 测不尽一切）。因此成熟的交付实践把重心从「保证永不出错」转向「**出错了能极快恢复**」——**快速回滚（rollback）作为发布安全网**。核心目标是把「新版本上线到发现问题、再恢复到好状态」的时间压到最短。

对初学者，这里有一个心态转变要讲透：**「可回退性（能不能快速退回上一个好状态）」本身，应当被当成发布方案的一等设计目标，而不是事后补丁**。一个「一旦上线就退不回去」的部署，无论测得多充分都是危险的；一个「随时能秒退」的部署，即使出点小问题也不致命。所以设计部署时先问「**出事怎么退**」，往往比问「怎么保证不出事」更实际、更省命。这也是为什么前面反复强调「同一制品晋级」（6.13.2.3）和「数据库向后兼容」（6.13.3.5）——它们正是「退得回去」的前提。

### 6.13.4.2 各部署策略对应的回滚机制

回滚不是一种统一动作，它**取决于你用的部署策略**——这把 6.13.3 的三种策略在「反向」再串一遍：

```
蓝绿：  把路由从绿(新)切回蓝(旧)          —— 接近瞬时、最干脆
滚动：  再滚一轮，把实例逐批换回旧版制品   —— 渐进、需要时间
金丝雀：把导向新版的那部分流量撤回旧版     —— 快，且爆炸半径本就小
（示意）
```

对初学者，从这张对照能看出各策略「回滚友好度」的差异：蓝绿因为旧环境还完整在线，回滚就是拨回路由，最快；金丝雀因为大多数用户本来就还在旧版，撤流量即可，且出问题时受影响的只是那一小撮金丝雀用户（爆炸半径小）；滚动最不利，因为旧实例已被逐批销毁，回滚要**再走一遍滚动流程**把旧版滚回来，是渐进的、有耗时的。这也反过来印证了「同一制品晋级」的价值——回滚时你只要重新部署那个**留档的、已知good的旧制品**即可（见 6.13.4.4）。

### 6.13.4.3 可回退性的前提：向后兼容与不可逆迁移的陷阱

「快速回滚」是一句有**前提**的承诺，最大的绊脚石又是**数据**。若新版本已经对数据库做了**不可逆或不向后兼容**的迁移（删列、改数据格式、写入了只有新版能理解的数据），那么即使你把代码秒切回旧版，旧代码也可能**读不懂已经被改过的数据**——代码回滚了，数据回滚不了，系统照样崩。Fowler 在蓝绿词条里点的「missed transactions（切换期在途/丢失的事务）」是同一类问题的一个侧面。

对初学者，务必把这条当硬约束记牢：**代码可回滚 ≠ 系统可回滚，数据往往是那个退不回去的部分**。破解办法就是 6.13.3.5 的 expand-contract——**先让数据库同时兼容新旧版本再升级应用**，这样回滚时数据依旧能被旧代码读写。忽略它，前面所有「秒级回滚」的说法都会在真实事故里变成空头支票。这是把「可回退性」从口号落到实处的关键工程约束。

### 6.13.4.4 不可变制品与「回滚 = 重新部署已知good版本」

在「构建一次、四处部署」（6.13.2.3）之上，回滚有一个非常干净的实现：**每个版本都是不可变、可按版本寻址的制品**（打了唯一版本号/内容摘要的二进制或镜像，留档不改），于是**回滚就等于「把上一个已知good的制品版本重新部署一遍」**——不是去改代码、打补丁，而是重放一个你确信没问题的旧版本。

```
回滚(rollback) ≈ 重新部署(redeploy) 一个留档的、已知good的旧制品版本
（不是热修当前版本，而是切回一个确定性的旧状态）
```

对初学者，这一点把很多概念串成了闭环：因为制品**不可变**（呼应 L5-13 不可变镜像、大主题06-4 Git 内容寻址的「内容定身份」思想），「v41」永远是那个 v41，回滚到它就得到一个**确定的、可预测的**旧状态，不会有「以为回到旧版其实混进了别的改动」的意外。这也是为什么 CD 强烈倾向**不可变部署**而非「原地打补丁」：可预测的回滚，本身就是可回退性的技术基石。

### 6.13.4.5 roll back 还是 roll forward，与 MTTR 的权衡

回滚不总是唯一或最优选择。另一条路是 **roll forward（前滚）**——不退回旧版，而是**快速做一个修复、往前再发一版**把问题盖掉。何时前滚更好？典型是当「回滚代价更大或不可行」时：比如数据库已发生不可逆迁移（退不回去，见 6.13.4.3），或问题很小、一个 hotfix 比整套回滚更快更稳。持续部署那种「一天发很多次、每次改动很小」的团队，往往更偏向前滚——因为再发一版本来就是几分钟的日常动作。

对初学者，判断标准可以落到一个词：**MTTR（平均恢复时间，mean time to recovery）——哪条路让系统更快回到健康，就走哪条**。回滚不是目的、恢复才是；roll back 与 roll forward 都是达成「快速恢复」的手段，按具体情形择优。这里再次触及下沉边界：**把恢复速度当成核心可靠性指标来度量与优化（MTTR、以及渐进式交付中的自动回滚触发），其纵深属可观测性/SRE，见 L5-12（§12-9 响应指标 MTTD/MTTR、§12-10 渐进式交付与自动回滚）**，本报告点到为止。
