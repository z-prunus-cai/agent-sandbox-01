## T7.1 类型变量与代换

### T7.1.1 类型重建问题：从"照标注核对"到"解方程"

**类型重建**（type reconstruction，又称 type inference，TAPL Ch.22 引言）指：给定一个**去掉了全部或部分类型标注**的项，判定是否存在一种标注方式使它良类型，并在存在时算出这些类型。TAPL 把它形式化为——给一个未标注项 t，问是否存在代换 σ 和类型 T，使得 σ 作用后 t 在 STLC 里能推出类型 T（§22.1 开头）。与 T3 的类型检查（type checking，标注齐全、只核对）相对，重建是"标注缺失、需反解"。

直观上，这正好是"正问题 vs 反问题"。T3 的检查像"给了完整答案，验算对不对"；重建像"题目留了空，你要填出所有空并保证整道题自洽"。填空的技巧是先给每个未知位置放一个**占位符**（类型变量），再根据程序里"这里被当函数调用了""这两个分支类型必须相等"等线索列出方程，最后解方程。整章的技术就是把"列方程 + 解方程"讲精确。

这里真正的要点是，Curry 风格（无标注）不是给语言加功能，而是**把标注的负担从程序员转给算法**。ML、Haskell 的"你几乎不用写类型"体验，底层就是本章这台机器在替你把类型解出来。

### T7.1.2 类型代换 σ 及其组合

**类型代换**（type substitution，§22.1）是从类型变量到类型的有限映射，写作

```
σ = [X₁ ↦ T₁, …, Xₙ ↦ Tₙ]
```

它作用在一个类型上时，把其中出现的每个 Xᵢ 同时替换成对应的 Tᵢ；作用在类型环境 Γ 上则逐个作用于 Γ 中每个类型。两个代换可以**复合**：先作用 σ 再作用 γ，记为 γ∘σ，定义为

```
(γ∘σ)(X) = γ(σ(X))
```

直观上，代换就是"给占位符赋值"。如果把类型变量 X 想成方程里的未知数 x，那么代换 `[X ↦ Bool]` 就是"令 x = Bool"这一步赋值。复合 γ∘σ 表示"先按 σ 赋一批值，再在结果上按 γ 赋另一批值"——注意顺序：先算 σ，再把 γ 盖上去，这和函数复合 g(f(x)) 的读法一致，初学者最常把顺序记反。

设 σ = [X ↦ Y→Y]，则 σ 作用在类型 X→Bool 上得到

```
σ(X → Bool) = (Y → Y) → Bool
```

代换只动类型变量，不动 Bool、Nat 这些具体（基）类型，也不动 → 这个构造子的形状——它只往"空位"里填东西。这一点是后面合一算法的地基。

### T7.1.3 类型方程、约束集与约束生成

把"程序里的类型线索"写成方程，就得到一个**约束集**（constraint set，§22.3）：一组形如 `S = T` 的类型等式，

```
C = { S₁ = T₁, S₂ = T₂, …, Sₙ = Tₙ }
```

含义是"存在某个代换 σ，使每条等式两边在 σ 作用后完全相等"。TAPL §22.3 给出**约束生成**（constraint-based typing）的规则：遍历项 t，为每个子项引入新的类型变量并收集约束。关键三条（去标注 STLC 的核心）直觉如下——

```
变量 x：从环境取出它的类型，不产生新约束。

抽象 λx.t：给参数一个新变量 X 作其类型，
          在 Γ,x:X 下递归求 t 的类型 T，
          整体类型为 X→T。

应用 t₁ t₂：分别求出 t₁:T₁、t₂:T₂，取新变量 X 作结果类型，
          追加一条约束  T₁ = (T₂ → X) ，整体类型为 X。
```

直观上，约束都来自"某处被当函数用了"。应用 `t₁ t₂` 里，t₁ 站在函数位置、t₂ 站在参数位置，于是"t₁ 的类型必须是一个以 t₂ 类型为定义域的箭头类型"，这就逼出等式 `T₁ = T₂ → X`。抽象则相反——它只是**引入**一个待定的参数类型 X，先不约束它，把决定权留给后面 X 在哪里被使用。

对 `λf. λx. f x`，给 f 类型变量 A、x 类型变量 B，则 `f x` 触发约束 `A = B → C`（C 为新变量，作 `f x` 的结果），整项类型为 `A → B → C`，附带约束集 `{A = B → C}`。这一步只是"列出方程"，还没解；解方程是 T7.2 合一的活。要避免的误解是：约束生成阶段**不做**任何判断对错，它只忠实地把结构线索翻译成等式，可满足性留给合一裁决。

## T7.2 约束式类型与合一

### T7.2.1 约束式定型关系与"解"的定义

TAPL §22.3 把约束生成写成一个判断

```
Γ ⊢ t : T |ᵪ C
```

读作"在环境 Γ 下，项 t 有类型 T，生成约束集 C，其中 χ 记录本次用掉的新类型变量"。这个判断的**解**（solution）定义为：一个代换 σ 满足 C（即 σ 令 C 中每条等式两边相等），此时 σT 就是 t 在该解下的一个具体类型。于是"t 是否可定型"化归为"C 是否有解"，而**如何求解、以及有没有'最好'的解**，正是合一算法要回答的（§22.4 承接 §22.3）。

直观上，把 T7.1.3 生成的方程组交出去，这里定义"什么叫解出来了"。一个解就是一套给所有类型变量的赋值，使每条等式成立。可能有很多解（比如 `X = Y→Y` 里 Y 还能取任意类型），也可能一个都没有（比如 `Bool = Nat→X` 无解）。判定"有没有解"并给出"最省的那个解"是下一步。

还值得建立的一层联系是，约束式定型把 T3 的类型检查和"解方程"焊在一起——生成阶段（T7.1）纯语法制导地扫一遍产出 C，求解阶段（本节）纯代数地解 C，两阶段解耦是 HM 好实现、好证明的关键。

### T7.2.2 合一问题与最一般合一子（mgu）

**合一**（unification）问题：给定约束集 C，求一个代换使 C 中所有等式成立，这样的代换称 C 的一个**合一子**（unifier）。若 C 有合一子，则存在一个**最一般合一子**（most general unifier, mgu）σ，使得 C 的**任何**合一子 γ 都能写成 δ∘σ 的形式（σ 后面再补一个代换 δ）。用"更一般"的序表述：

```
σ 是 C 的 mgu  ⟺  σ 合一 C，且对 C 的任意合一子 γ，存在 δ 使 γ = δ∘σ
```

直观上，mgu 是"填得最少、最不武断"的那个解。它只把方程**逼着你填**的部分填掉，其余一律保留为变量，好让后续还能自由实例化。例如合一 `{X = Y→Y}` 的 mgu 是 `[X ↦ Y→Y]`，它没有多此一举地把 Y 也定死成 Bool；而 `[X ↦ Bool→Bool, Y ↦ Bool]` 也是合一子，但填过头了，只是 mgu 的一个特例（在 mgu 后再补 `[Y ↦ Bool]`）。mgu 的唯一性（差一个变量改名）是"主类型存在"的算法根源，直接喂给 T7.3。

mgu 不是"最短的代换"，而是"最弱的、信息量最少的"解——所有别的解都是它的加强版。

### T7.2.3 Robinson 合一算法与 occurs check

Robinson（1965）给出的合一算法按类型结构递归，是把约束集逐条化简的过程（TAPL §22.4 的 `unify`）：

```
unify(∅) = 恒等代换 []

unify({S = T} ∪ C'):
  ① S 与 T 同为同一变量 X：丢弃此式，unify(C')
  ② S 是变量 X 且 X 不出现在 T 中（occurs check 通过）：
       令 σ = [X ↦ T]，返回 unify(σ C') ∘ σ
  ③ T 是变量、S 不是：对称处理，同 ②
  ④ S = S₁→S₂ 且 T = T₁→T₂：
       用 {S₁ = T₁, S₂ = T₂} 替换此式，继续
  ⑤ S、T 都是（相同）基类型：丢弃此式，unify(C')
  ⑥ 其余情形（如 Bool = Nat，或结构对不上）：失败，无解
```

其中 ② 里的 **occurs check**（出现检查）是正确性与终止性的命门：若变量 X 出现在 T 内部（如 `X = X→X`），则不存在有限类型满足它，必须判失败，否则会造出无限类型、算法不终止。

直观上，合一就是"把两棵类型树叠在一起对齐"。箭头对箭头就分别对齐定义域、值域（规则 ④）；碰到一边是变量就把它赋成另一边（规则 ②③）；碰到 Bool 对 Nat 这种对不上就宣告矛盾（规则 ⑥）。occurs check 是在赋值前先问一句"我要赋给 X 的东西里是不是又含 X？"——含就是 `X = X→X` 这种自指方程，几何上是"要把一棵树塞进它自己的一根枝丫里"，永远塞不完。这个检查在 T7.4 会再次出场，用来解释为什么 `(λid. id id)(λx.x)` 被拒。

本篇做了一次可选的本机实证（加固算法步骤用）——用 Python 3.11.15 实现上述 `unify`（含 occurs check）与基于它的 HM 推断，对四个项给出类型或拒绝。命令 `python3 hm.py`，真实输出——

```
lambda x. x: (a0 -> a0)
let id=\x.x in id id: (a3 -> a3)
(\id. id id)(\x.x)  [no let-gen]: REJECTED (occurs check: a5 in (a5 -> a6))
let id=\x.x in id: (a8 -> a8)
```

第三行正是 occurs check 触发失败的实机复现（详见 T7.4）。基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25，实证机 @2026-07-30；此为加固补充，不替代多来源比对。

## T7.3 principal type 与 Algorithm W

### T7.3.1 principal type：最一般的类型

一个（去标注）项 t 的**主类型**（principal type，TAPL §22.5）是这样一个类型 T：t 可被赋予 T，且 t 能被赋予的**任何**类型都是 T 的一个代换实例。换言之，主类型是"最一般、涵盖其余一切类型"的那一个。TAPL §22.5 的**主类型定理**（对本章的约束式 STLC）说：

```
若约束集 C 有解，则它有一个主解（mgu）；
从而每个可定型的项都有一个主类型（把 mgu 作用到生成阶段算出的类型上即得）。
```

直观上，主类型就是恒等函数 `λx.x` 的那个 `∀X. X→X` 的"未量化骨架" `X→X`——它能特化成 `Bool→Bool`、`Nat→Nat`、`(A→A)→(A→A)`……所有这些具体类型都是把 X 填成某物得到的。主类型之所以存在，直接来自 T7.2 的 mgu 存在且唯一：生成阶段给出带变量的类型和约束集，合一给出最一般的赋值，两者一拼就是最一般的类型。

说到底，主类型是 HM 好用的根本原因——编译器不必在众多可能类型里挑，算出主类型这一个就够了，用到的地方各自实例化。这台"算主类型"的机器有名字，叫 Algorithm W。

### T7.3.2 Algorithm W：把主类型算法写成可执行程序

**Algorithm W**（Milner 1978；正确性由 Damas & Milner 1982 证明）是计算主类型的经典算法。它以"边走边串代换"的形式给出——输入环境 Γ 与项 e，输出一个代换 S 和一个类型 τ，使 `S Γ ⊢ e : τ` 且这是主的：

```
W(Γ, x)        = (∅, instantiate(Γ(x)))
W(Γ, λx.e)     : 取新变量 β；(S, τ) = W(Γ,x:β ; e)；返回 (S, Sβ → τ)
W(Γ, e₁ e₂)    : (S₁,τ₁) = W(Γ, e₁)
                 (S₂,τ₂) = W(S₁Γ, e₂)
                 取新变量 β；S₃ = unify(S₂τ₁, τ₂ → β)
                 返回 (S₃∘S₂∘S₁, S₃β)
W(Γ, let x=e₁ in e₂):
                 (S₁,τ₁) = W(Γ, e₁)
                 σ = generalize(S₁Γ, τ₁)          -- 见 T7.4
                 (S₂,τ₂) = W(S₁Γ, x:σ ; e₂)
                 返回 (S₂∘S₁, τ₂)
```

直观上，Algorithm W 把 T7.1 的约束生成和 T7.2 的合一**交织**成一趟递归——不再是"先全部列方程、再统一解"，而是"走到应用就地合一一次，把解出来的代换往后传"。返回值里的代换 S 就是"到目前为止解出来的那批赋值"，`τ` 是"在这批赋值下当前子项的类型"。应用那一步的 `unify(S₂τ₁, τ₂→β)` 正是 T7.1.3 的约束 `T₁ = T₂→X` 就地被解掉。

这台算法喂给两个下游（点名不展开）：**L4-04 编译原理 C5** 语义分析里"无标注/局部推断"的实现原型；**L5-14 Rust 与内存安全 R6** 的局部类型推导（Rust 用的是 HM 思想的受限、非全程版本，且叠加 trait 约束求解）。

### T7.3.3 各家表述分歧：约束式 vs W vs J，及复杂度

同一个 HM 推断，文献有几种**表述不同但等价**的写法，初学者容易在跨书阅读时混淆，这里两边都记：

TAPL Ch.22 走**约束式**（constraint-based）——先生成约束集、再统一合一，两阶段解耦，Pierce 明言这比经典 Algorithm W 更模块化、更易扩展；而 Milner 1978 / Damas-Milner 1982 的经典 **Algorithm W** 是**代换穿线**（substitution-threading）式，边推边合一、把代换 S 一路复合传递（即 T7.3.2 的形态）。此外常见的 **Algorithm J** 是 W 的一个用**可变引用/union-find 就地更新**替代显式代换传递的实现变体，效率更高但少了 W 那种"每步都有清晰代换语义"的可证明性；三者算出的主类型相同。

复杂度上有个反直觉的经典结论：ML/HM 的可定型性判定是 **DEXPTIME-完全**（deterministic exponential time complete），由 Mairson（POPL '90，"Deciding ML typability is complete for deterministic exponential time"）与 Kfoury-Tiuryn-Urzyczyn（CAAP '90，LNCS 431，pp.206–220，"ML typability is DEXPTIME-complete"）独立证明。指数爆炸只在**病态**输入上出现（嵌套 let 层层泛化，类型规模翻倍）；真实程序里 let 嵌套深度有界，实际几乎线性。

这里有一层直觉、也有一个易错点。不要因为"HM 是 DEXPTIME-完全"就以为编译器很慢——那是最坏情况的理论上界，实践中因 let 嵌套浅而基本线性。也不要把 W、J、约束式当成不同的类型系统：它们是同一 HM 系统的三种算法呈现，结论（主类型）一致，差别只在实现策略与可证明性。

## T7.4 let-多态

### T7.4.1 类型模式（type scheme）、泛化与实例化

**let-多态**（let-polymorphism，TAPL §22.7；即 Hindley-Milner 多态）的核心是引入**类型模式**（type scheme）——把类型里的一些变量用 ∀ 显式量化起来：

```
σ ::= ∀X₁ … ∀Xₙ. T        （n 可为 0，此时退化为普通类型）
```

配套两个互逆操作。**实例化**（instantiation）把量化变量换成新鲜变量（或任意类型），得到该模式的一个具体实例：

```
inst(∀X. X→X)  ⇒  Y→Y      （每次用到都取一个全新的 Y）
```

**泛化**（generalization）在 let 处把 e₁ 的类型里、**不出现在环境 Γ 中**的自由类型变量全部量化起来：

```
generalize(Γ, T) = ∀X̄. T ，其中 X̄ = FTV(T) \ FTV(Γ)
```

直观上，类型模式就是"可复用的类型模板"。`∀X. X→X` 是"恒等函数的模板"，每处调用各自实例化出独立的 `Y→Y`、`Z→Z`，互不牵连，于是同一个 `id` 能既用在布尔上又用在整数上。泛化的那条边界条件 `X̄ = FTV(T) \ FTV(Γ)` 是全篇最易错处：**只能量化"自己独有"的变量，不能量化"还被环境里别的东西牵着"的变量**——若某变量在 Γ 里已被别处约束，把它泛化就等于谎称"它对一切类型都成立"，会导致不可靠。

在空环境下 `λx.x` 的类型是 `X→X`，X 不被环境牵制，泛化得 `∀X. X→X`；但若在 `Γ = {y : X}` 下遇到同一个 `X`，则 X ∈ FTV(Γ)，**不可**泛化。

### T7.4.2 为什么在 let 绑定处放多态：let ≠ (λx. e₂) e₁

let-多态的关键抉择是：**只在 let 绑定处做泛化，λ 参数处不泛化**。这带来一个初学者必须理解的反直觉事实——在 HM 里

```
let x = e₁ in e₂      并不等价于      (λx. e₂) e₁
```

尽管两者在无类型 λ 演算里求值结果相同。原因：let 会对 e₁ 的类型**泛化**，使 x 在 e₂ 里获得多态类型模式、每次使用各自实例化；而 λ 参数 x 的类型是一个**单态**类型变量，在函数体内所有出现必须是同一个类型，不能泛化（§22.7）。TAPL 由此把 let 作为**原生构造**给出专门的类型规则，而非把它当作应用的语法糖。

下面是一个经典判别例（本篇实证坐实）——

```
let id = λx.x in id id          -- 良类型，主类型  X→X
(λid. id id) (λx.x)             -- 在 HM 里被拒
```

第一式里 `id : ∀X. X→X`，两处 `id` 各实例化：外层 `id` 取 `(A→A)→(A→A)`、内层 `id` 取 `A→A`，拼起来成立。第二式里 `id` 是 λ 参数、类型是单态变量 β，则 `id id` 要求 `β = β→γ`——**occurs check 失败**（T7.2.3），无解，故被拒。

同一份可选实证也覆盖了这一对——Python 3.11.15 HM 推断（let 分支做 generalize、λ 分支不做），真实输出——

```
let id=\x.x in id id: (a3 -> a3)
(\id. id id)(\x.x)  [no let-gen]: REJECTED (occurs check: a5 in (a5 -> a6))
```

两行恰好实机分出了"let 泛化则可定型"与"λ 参数不泛化则 occurs check 失败被拒"，正是 let ≠ 应用的可执行证据。基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25，实证机 @2026-07-30；加固补充，不替代多来源比对。

### T7.4.3 let-多态的边界：value restriction 与可变引用

let-多态有一个必须知道的**不可靠陷阱**：一旦语言加入**可变引用**（mutable references，参见 T4.4），无限制地在 let 处泛化就**不可靠**（能造出运行时类型错误）。经典反例的骨架是"泛化一个存放多态引用的 cell，先当存字符串的引用写入、再当存整数的引用读出"，绕过类型系统。现代 ML（SML '97 起）的标准修补是 **value restriction**（值限制，Wright 1995 "Simple Imperative Polymorphism"）：

```
只有当 let 右侧 e₁ 是一个语法值（value，如变量、λ 抽象、常量）时，才对它泛化；
若 e₁ 是可能有副作用的应用/求值表达式，则不泛化（保持单态）。
```

直观上，泛化等于宣称"这个值对一切类型都好使"，但一个**可变**的东西不能对一切类型都好使——你按某个类型写进去、又按另一个类型读出来就会崩。value restriction 用一条纯语法的保守判据（"是不是一眼可见的值"）把危险情形一律挡在泛化之外，宁可少推出一些多态、也不放过不安全的泛化。这解释了为什么在 ML 里 `let r = ref [] ...` 有时推不出你期望的多态类型——不是 bug，是 value restriction 在保平安。

这里要分开记两笔账（规范 vs 实现）。纯 HM（本篇 T7.1–T7.4.2，无引用的 λ 演算）里 let-多态是完全可靠的，无需 value restriction；value restriction 是**引入可变状态后**的实现层修补，属 ML 语言家族的工程约定，不是纯 HM 理论的一部分。TAPL 主线在纯函数式设定下讲 let-多态，可变引用与其相互作用属扩展话题。
