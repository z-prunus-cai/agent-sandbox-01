## T5.1 子类型关系与 subsumption

### T5.1.1 subsumption 规则：子类型为什么有用

子类型机制的入口是一条叫 **subsumption（包容）** 的类型规则（TAPL §15.1，规则 T-Sub）

Γ ⊢ t : S　　S <: T ⟹ Γ ⊢ t : T

它说的是，如果项 t 有类型 S，而 S 是 T 的子类型（S <: T），那么 t 也可以当作类型 T 来用。这一条把"子类型关系 <:"接进了类型系统——有了它，一个 S 类型的值在任何期待 T 的位置都合法。

理解要点是"subsumption 让类型系统变得更宽容、但不失安全"。没有子类型的 STLC 里，函数

f : {x:Nat} → Nat

只能接受**恰好**是 {x:Nat} 类型的记录；可现实中我们希望能把一个信息更全的 {x:Nat, y:Nat} 也传进去（它至少有 f 需要的 x 字段）。subsumption + 记录子类型（下面 T5.1.3）正是让这件事合法：先由 {x:Nat, y:Nat} <: {x:Nat} 推出实参也具有类型 {x:Nat}，再正常应用 f。初学者要抓住的方向感：**subsumption 是"向上转型/遗忘信息"——把一个更专门的类型看成一个更宽泛的类型，总是安全的**；反过来（把宽泛的当专门的用）不安全，需要运行时检查（见 T5.5 的 cast）。

### T5.1.2 子类型关系是预序：自反与传递

子类型关系 <: 由一组推导规则归纳定义，其中两条最基础的是自反与传递（TAPL §15.2，规则 S-Refl、S-Trans）

S <: S　　(S-Refl)

S <: U　　U <: T ⟹ S <: T　　(S-Trans)

自反说"每个类型是自己的子类型"，传递说"子类型关系可以串联"。这两条加上后面各构造的规则，使 <: 成为类型上的一个**预序**（preorder，自反且传递）。

理解要点在于，自反保证了"不改变类型也是合法替换"（S 当然能顶替 S），传递保证了"多级替换能一步到位"（S <: U 且 U <: T，则 S 直接能当 T 用）。为什么是预序而不是偏序（partial order）？因为可能存在 S <: T 且 T <: S 却 S 与 T 不是同一个类型（例如记录字段顺序不同的 {x:Nat,y:Nat} 与 {y:Nat,x:Nat}，见 T5.1.3 的置换规则，二者互为子类型）。初学者在这里先记住这两条是"骨架规则"，本身不涉及任何具体类型构造；真正让子类型"有内容"的是下面记录、函数的规则。一个重要伏笔：S-Refl 和 S-Trans 在算法化时会被证明是**可省的（admissible）**（T5.2），因为它们不是语法制导的、会让子类型检查无从下手。

### T5.1.3 记录子类型：宽度、深度、置换

记录类型的子类型有三条规则（TAPL §15.2，规则 S-RcdWidth、S-RcdDepth、S-RcdPerm）。**宽度子类型**（width subtyping）：字段更多的记录是字段更少的记录的子类型

{lᵢ:Tᵢ  (i∈1..n+k)} <: {lᵢ:Tᵢ  (i∈1..n)}　　(S-RcdWidth)

**深度子类型**（depth subtyping）：逐字段允许各自变成子类型

对每个 i 有 Sᵢ <: Tᵢ ⟹ {lᵢ:Sᵢ  (i∈1..n)} <: {lᵢ:Tᵢ  (i∈1..n)}　　(S-RcdDepth)

**置换**（permutation）：字段顺序无关紧要

{kⱼ:Sⱼ  (j∈1..n)} 是 {lᵢ:Tᵢ  (i∈1..n)} 的一个重排 ⟹ {kⱼ:Sⱼ} <: {lᵢ:Tᵢ}　　(S-RcdPerm)

理解宽度规则的方向是初学者头号易错点：**字段更多的是子类型（更小），字段更少的是超类型（更大）**。直觉是"字段多 = 信息多 = 更专门 = 能顶替信息少的用"——一个 {name, age} 的人事记录能当作只要求 {name} 的地方使用（多出来的 age 无害），反之不行（缺 age）。很多人凭"子集/包含"的错觉以为字段少的才是子类型，恰好反了：这里"子类型"讲的是**值集合的包含**（{x:Nat,y:Nat} 的值集是 {x:Nat} 值集的子集，因为前者约束更强），不是字段集合的包含。

深度规则让子类型能"钻进字段内部"：若 T 的某字段类型可以被替换成子类型，整个记录也随之成为子类型。置换规则则声明记录本质是"带标签的无序集合"，`{x:Nat,y:Bool}` 与 `{y:Bool,x:Nat}` 互为子类型（故 <: 只是预序）。三条规则常配合 S-Trans 联用：先置换对齐字段、再宽度丢字段、再深度调各字段，组合出复杂的记录子类型判断。

### T5.1.4 函数子类型：参数逆变、结果协变

函数类型的子类型规则是变型（variance）的核心，也是最反直觉的一条（TAPL §15.2，规则 S-Arrow）

T₁ <: S₁　　S₂ <: T₂ ⟹ S₁ → S₂ <: T₁ → T₂

注意两个前提方向**相反**：参数位置是 T₁ <: S₁（反着来，叫**逆变** contravariant），结果位置是 S₂ <: T₂（顺着来，叫**协变** covariant）。也就是说，"一个函数要当作另一个函数用，它必须**接受更宽的参数、返回更窄的结果**"。

理解逆变为什么"反"是本节关键。把"S₁→S₂ <: T₁→T₂"读成"一个 S₁→S₂ 的函数能顶替一个 T₁→T₂ 的函数"。顶替它的场合会：(1) 喂给它一个 T₁ 类型的实参——所以我这个函数必须能接受 T₁，即它的参数类型 S₁ 要**比 T₁ 更宽**（T₁ <: S₁，接受得更多才安全）；(2) 把它的返回值当作 T₂ 使用——所以我返回的 S₂ 必须**能当 T₂ 用**（S₂ <: T₂，返回得更专门才安全）。一句口诀：**"要用它的地方对参数更挑剔（给的更具体，函数要求得更宽松）、对结果更宽松（函数给的要更具体）"**。

看一个最小例子，设 {x:Nat,y:Nat} <: {x:Nat}，则

{x:Nat} → {x:Nat,y:Nat}　<:　{x:Nat,y:Nat} → {x:Nat}

左边这个函数"接受更少要求（只需 x）、返回更多信息（给 x 和 y）"，所以它能安全顶替右边那个"要求更多、给得更少"的函数。初学者最常犯的错是把参数也当协变（以为参数越具体越好）——那是**不安全**的：若允许 {x:Nat}→R <: {x:Nat,y:Nat}→R，调用方会拿一个只有 x 的记录喂进来，而函数体可能去访问它并不存在的 y，崩溃。记住参数**逆变**、结果**协变**，是写对任何带子类型语言（Java、Scala、TypeScript 的函数型）的地基。

### T5.1.5 Top 与 Bottom

子类型格上常加两个极端元素（TAPL §15.2 引入 Top，§15.4 讨论 Bottom）。**Top**（写作 Top 或 ⊤）是所有类型的超类型

S <: Top　　(S-Top)

**Bottom**（写作 Bot 或 ⊥）是所有类型的子类型

Bot <: T　　(S-Bot)

Top 是"最大类型"（最宽泛，任何值都算 Top，类似 Java 的 Object、Scala 的 Any、TypeScript 的 unknown）。Bot 是"最小类型"（最专门，没有任何值属于它，Bot 类型的项一定不会正常返回，类似 Scala 的 Nothing）。

理解要点在于，Top 给"我不关心具体类型、什么都能放"提供了一个类型（如异质容器的元素类型）。Bot 更微妙——它**没有闭值**（no closed values inhabit it），所以一个类型为 Bot 的项要么发散、要么抛异常/报错，永远不会真的产出一个 Bot 值；正因如此它可以子类型于任何 T（"从不返回的东西"放在期待任何类型的位置都不会出错）。Bot 的典型用途是给 error/raise 这类"不正常返回"的构造一个类型：

error : Bot

于是 error 能用在任何期待类型 T 的上下文里。初学者要注意：TAPL 正文的很多小节只加 Top、暂不引入 Bot（Bot 会给算法化和 join/meet 带来额外复杂度，见 T5.2）；两者是否同时存在取决于所讨论的具体系统，读规则时先看清该系统装了哪个。

## T5.2 元理论与算法子类型

### T5.2.1 加入子类型后类型安全依然成立

引入 subsumption 与 <: 后，STLC 的类型安全（Safety = Progress + Preservation，承 T3.3）仍然成立，但证明需要一些新引理（TAPL §15.3）。保型性（Preservation）陈述不变

若 Γ ⊢ t : T 且 t → t′，则 Γ ⊢ t′ : T。

进展性（Progress）陈述也不变

若 t 是良类型的闭项，则 t 是值，或存在 t′ 使 t → t′。

关键的新工具是**求逆引理**（inversion lemmas），例如"若 Γ ⊢ λx:S₁.t : T₁→T₂，则 T₁ <: S₁ 且 …"。

理解要点在于"为什么加了 subsumption 证明会变麻烦"。没有子类型时，一个项的类型由其语法形状唯一决定（syntax-directed）；有了 T-Sub，**同一个项可以有很多类型**（S 及其所有超类型），类型不再唯一。这破坏了原来"看语法就知道类型"的性质，于是 Preservation 证明里"从 t 的类型反推子项类型"的那一步不能再直接做，必须先用求逆引理"剥掉"外面可能套着的若干层 subsumption。初学者只需记住结论与直觉：**子类型不破坏安全性，但让"类型唯一"这一好性质消失，证明与算法都要为此付出代价**（下面几条正是这个代价的展开）。本节为纯元理论命题，未做本机实证（保型/进展是对推导做归纳的证明论结果，Python 不足以佐证，如实标注）。

### T5.2.2 声明式子类型 vs 算法式子类型

前面 T5.1 给的规则是**声明式（declarative）**系统：它规定"哪些子类型关系成立"，但不是**语法制导（syntax-directed）**的——遇到目标 S <: T 时，S-Refl、S-Trans 随时都能用，机器不知道该先试哪条、S-Trans 中间的 U 又从哪来（TAPL §16.1）。**算法式（algorithmic）子类型**把它改写成一个每步由类型形状唯一决定下一条规则的系统，从而可以直接实现成一个判定函数。

理解要点是"声明式说的是'是什么'，算法式说的是'怎么查'"。声明式系统方便证明性质、贴近直觉，但不能直接跑：S-Trans 有个"凭空出现"的中间类型 U，算法搜索时无从枚举；S-Refl 又和别的规则重叠。算法式系统的思路是：**把 S-Refl 和 S-Trans 删掉，只保留由类型构造子形状驱动的规则**（如两边都是箭头就用 S-Arrow、都是记录就用记录规则、右边是 Top 就用 S-Top），并证明删掉的两条是**可省的（admissible）**——即它们能被其余规则推出，删了不损失任何可推的子类型关系。初学者要抓住这个"声明式↔算法式"的分工模式：它在类型系统研究里反复出现（子类型、类型检查都这么做），本质是"先给一个好懂但不可执行的规范，再给一个可执行且被证明与规范等价的算法"。

### T5.2.3 算法式子类型规则与判定过程

算法式子类型关系 ⊢ S <: T 由一组语法制导规则给出，核心是（TAPL §16.1，Fig 16-1）

⊢ S <: Top　　(SA-Top)

⊢ T₁ <: S₁　　⊢ S₂ <: T₂ ⟹ ⊢ S₁→S₂ <: T₁→T₂　　(SA-Arrow)

{lᵢ} ⊇ {kⱼ} 且对每个共有标签 ⊢ Sᵢ <: Tⱼ ⟹ ⊢ {lᵢ:Sᵢ} <: {kⱼ:Tⱼ}　　(SA-Rcd)

其中 SA-Rcd 把 T5.1 的宽度、深度、置换三条**合并成一条**：右边记录的每个字段都要在左边找到同名字段、且左字段类型是右字段类型的子类型。

理解要点在于，这三条规则合起来是**语法制导**的——给定 S、T，只看它们最外层的构造子就知道用哪条（右边 Top 用 SA-Top、两边箭头用 SA-Arrow、两边记录用 SA-Rcd、否则失败），递归地把大问题拆成子问题，一定终止（子问题的类型都更小）。这样就得到一个必停的判定算法。本机 Python 实证：按上述三条规则实现子类型判定函数 `subtype(S, T)`，在若干测试上与手算一致——`{x:Nat,y:Nat} <: {x:Nat}` 返回 True、`{x:Nat} <: {x:Nat,y:Nat}` 返回 False、`(Top→Nat) <: (Nat→Top)` 返回 True（参数逆变 Nat<:Top、结果协变 Nat<:Top）、反向 `(Nat→Top) <: (Top→Nat)` 返回 False，均符合 SA-Arrow。初学者要注意 SA-Arrow 里参数位仍是**逆变**（递归调用时 T₁ 和 S₁ 交换了位置）——算法实现时最容易在这里把两个参数写反，正好对应 T5.1.4 的方向陷阱。

### T5.2.4 算法式类型检查：最小类型与消去 subsumption

不仅子类型要算法化，整个类型检查也要（TAPL §16.2）。问题同样出在 T-Sub：它可以插在推导树的任何位置，不是语法制导的。算法式类型系统把 T-Sub **删掉**，改为让它"内联"进真正需要子类型的地方——主要是函数应用规则

Γ ⊢ t₁ : T₁₁→T₁₂　　Γ ⊢ t₂ : T₂　　⊢ T₂ <: T₁₁ ⟹ Γ ⊢ t₁ t₂ : T₁₂　　(应用，算法版)

即"实参的类型只要是形参类型的子类型即可"，子类型检查被就地嵌进应用规则。算法式系统给每个项算出的是它的**最小类型**（minimal type，也叫 principal type for subtyping）。

理解要点在于，声明式系统里 subsumption 到处能用，一个项有一族类型；算法式系统只算那个**最专门的（最小的）**类型，其余超类型可由子类型关系随时得到，不必显式推导。为什么应用规则能"吸收"subsumption？因为函数应用是唯一真正要求"实参得匹配形参"的地方，把子类型检查放这里就够了；if-then-else 也需要（两分支类型可能不同，见下）。本机 Python 佐证同上：判定函数嵌进"应用要求 argType <: paramType"后，能正确接受 `f({x:Nat,y:Nat})`（f 期待 {x:Nat}）并拒绝 `f({y:Nat})`。初学者要建立的总图景是：**算法式类型检查 = 算每个子项的最小类型，然后只在应用（和条件）这些"汇合点"检查子类型是否成立**。

### T5.2.5 join 与 meet：条件表达式的类型

有了子类型，if-then-else 两个分支的类型可以不同，那整个表达式该是什么类型？答案是两分支类型的**最小上界**（least upper bound，也叫 **join**，记 S∨T）（TAPL §16.3）。对偶地，函数应用等场合可能需要**最大下界**（greatest lower bound，**meet**，记 S∧T）。TAPL 证明：在其带 Top 的记录+函数子类型系统里，任意两类型的 join 一定存在；meet 则是**部分的**（只有当两类型"相容"时才存在）。

if b then t₂ else t₃ 的类型 = (t₂ 的类型) ∨ (t₃ 的类型)

理解要点在于，条件表达式运行时会取两分支之一，所以结果类型必须是"同时能容纳两种可能"的最小类型——正是 join。例子：`if b then {x:Nat,y:Nat} else {x:Nat,z:Bool}` 的类型是两者的 join `{x:Nat}`（它们唯一共有的、且类型一致的字段）。为什么 meet 只是部分的？因为两个类型可能**没有公共子类型**（如 Nat 和 {x:Nat}，没有哪个类型既是数字又是记录），此时 meet 不存在；而加了 Bot 后 meet 才总存在（Bot 兜底）。初学者可把 join/meet 类比集合的并/交在子类型格上的对应：join 往"更宽泛"方向找最紧的公共超类型，meet 往"更专门"方向找最松的公共子类型。这解释了为什么很多带子类型的语言里，`if` 或三目运算的类型有时会"意外地"变宽——编译器在算 join。本节 join/meet 存在性为证明论命题，未做本机实证（标注）。

#### 来源与时效（本小主题）

- 冲突项：无实质分歧。TAPL 明确 join 全存在、meet 仅部分存在（除非加 Bot）；这一点各处一致。定理/图编号随印次微调，以命题内容为准。

## T5.3 引用/数组的变型

### T5.3.1 可变引用是不变的（invariant）

可变引用类型 Ref T 的子类型规则要求两个方向同时成立，即它是**不变的**（invariant，既非协变也非逆变）（TAPL §15.5）

T₁ <: T₂　　T₂ <: T₁ ⟹ Ref T₁ <: Ref T₂　　(S-Ref)

因为前提要求 T₁ <: T₂ 且 T₂ <: T₁（互为子类型），实际上只有当 T₁ 与 T₂ 本质相同时 Ref T₁ <: Ref T₂ 才成立。

理解为什么引用必须不变，是本节的核心。一个 Ref T 的单元格既能**读**（读出来是个 T，希望协变：读 Ref S 当 Ref T 用时要 S<:T）、又能**写**（写进去一个 T，希望逆变：写 Ref S 当 Ref T 用时要 T<:S）。读要协变、写要逆变，两个要求**打架**，唯一同时满足的办法就是不允许类型变化——即不变。最小反例：设 Ref {x:Nat,y:Nat} 能协变成 Ref {x:Nat}（若错误地允许）。拿着这个"看起来是 Ref {x:Nat}"的引用，我合法地往里写一个只有 x 的记录 {x:5}；可它底层其实指向一个要求 {x,y} 的单元格，之后有人从原引用读出来当作 {x:Nat,y:Nat} 去访问 .y，就读到了并不存在的字段——类型系统被击穿。所以可变单元格的类型不能变。初学者要牢记：**只读容器可以协变、只写容器可以逆变、可读可写容器必须不变**，这是所有语言泛型/引用变型规则的总原理。

### T5.3.2 协变数组之坑（Java 的 ArrayStoreException）

数组本质是可变引用的集合，本应不变；但 Java（以及早期 C#）出于历史原因让数组**协变**（TAPL §15.5 明确点名此为不安全设计；JLS §10.10、§4.10.3）

若 S <: T，则 Java 中 S[] <: T[]（协变，但不安全）

为弥补这个漏洞，Java 在**每次数组写入时插入一个运行时类型检查**，写入类型不符就抛 `ArrayStoreException`（JLS §10.10）。

理解要点在于，Java 允许 `Integer[]` 当 `Object[]` 用（协变），于是能写出

Object[] a = new Integer[3];　　a[0] = "hello";　// 编译通过，运行时抛 ArrayStoreException

编译期通过是因为 `String` 是 `Object`、而 a 的静态类型是 `Object[]`，看起来合法；但 a 运行时实际指向 `Integer[]`，把字符串塞进整型数组会破坏内存安全，于是 JVM 在存储时动态检查元素类型、发现不符即抛异常。这正是 T5.3.1 那个反例的真实语言版：协变数组把本该编译期拒绝的错误，推迟成了运行时异常。初学者要记住这是一个**被广泛承认的语言设计缺陷**——它用运行时检查换取了当年泛型缺失下的灵活性，代价是牺牲了"类型正确就不会有此类运行时错误"的保证。现代设计（如 Java 泛型 `List<E>`、C# 的 `IList<T>`）默认**不变**，正是吸取了这个教训；Java 泛型另用通配符 `? extends`/`? super` 显式表达协变/逆变（use-site variance）。

### T5.3.3 拆分读写：Source 与 Sink 恢复变型

引用不变虽安全却损失灵活性。TAPL 给出一个优雅的补救：把 Ref T 拆成两个"能力更窄"的类型——只读的 **Source T** 和只写的 **Sink T**（TAPL §15.5）。只读引用可以**协变**、只写引用可以**逆变**

T₁ <: T₂ ⟹ Source T₁ <: Source T₂　　(S-Source，协变)

T₂ <: T₁ ⟹ Sink T₁ <: Sink T₂　　(S-Sink，逆变)

且 Ref T 同时是二者的子类型

Ref T <: Source T　　Ref T <: Sink T

理解要点在于，T5.3.1 说引用必须不变，是因为读写两种能力捆在一起、要求互相冲突。一旦把能力**拆开**，冲突就消失了——只有读能力时，协变安全（读出来的更专门的值当更宽泛的用，没问题）；只有写能力时，逆变安全（往里写更宽泛类型的值，之后无论谁读都读到至少满足更专门类型的值）。一个 Ref T 既能读又能写，所以能"降级"成只读的 Source T 或只写的 Sink T（丢弃一半能力）。初学者可以把它类比现实的接口拆分：一个可读写文件句柄可以传给只需要"读接口"的函数（此时按读接口协变）或只需要"写接口"的函数（此时按写接口逆变）。这个 Source/Sink 思想正是 C# 的 `IEnumerable<out T>`（协变只读）与 `Action<in T>`（逆变只写）、以及 Scala 变型标注 `+T`/`-T` 的理论原型。

- 一手：TAPL Ch.15 §15.5（Subtyping and Other Features：Ref 不变 S-Ref、数组协变之不安全、Source/Sink 及其协变/逆变规则、Ref<:Source、Ref<:Sink），2002 版，核实 2026-07-30。
- 交叉一手：Java Language Specification, Java SE 21 (2023) §10.10（数组存储时的运行时检查与 ArrayStoreException）、§4.10.3（数组类型间的子类型为协变）——作为"真实语言里协变数组不安全"的独立一手佐证，与 TAPL 结论一致。
- 冲突项：无分歧——TAPL（理论）与 JLS（实现）在"可变引用/数组协变不安全、Java 用运行时检查兜底"上完全吻合，恰是"规范与实现分账后结论一致"的范例。

## T5.4 命令式对象与 OO 编码

### T5.4.1 对象即"方法记录"：用 λ 编码对象

面向对象里的"对象"可以直接在带记录、引用与子类型的 λ 演算里编码出来（TAPL Ch.18）。最基本的编码是**把对象表示成一个方法的记录**（a record of functions）。一个计数器对象

Counter = {get : Unit→Nat, inc : Unit→Unit}

一个具体计数器对象就是一个这样的记录，其字段是闭包，闭包捕获了共享的内部状态。

理解要点在于，OO 的"对象 = 状态 + 一组操作该状态的方法"这一直觉，在 λ 里被拆成"一个记录，字段是一批共享同一份（引用型）状态的函数"。方法之所以能操作同一份状态，是因为它们都是在同一个作用域里创建的闭包，捕获了同一个 Ref。这就把"对象"这个看似原生的语言概念，还原成了已有的更基础的构造（记录 + 闭包 + 引用），说明 OO 并非必须内建、可由类型论积木搭出。初学者要抓住这条"祛魅"主线：**对象没有魔法，它就是"打包了共享状态的一束函数"**。子类型在这里自然登场——方法更多的对象类型是方法更少的对象类型的子类型（记录宽度子类型 T5.1.3），这正对应 OO 里"子类对象能当父类对象用"。

### T5.4.2 实例变量与状态：把状态分组

带可变状态的对象，其编码要把实例变量（instance variables）单独分组、再让方法共享（TAPL §18.6 前后的"grouping instance variables / a representation type"）。一个带内部计数的对象大致形如

newCounter = λ_. let r = ref {x = 1} in {get = λ_. !(r).x, inc = λ_. r := {x = succ((!r).x)}}

即先建一个存实例变量的引用 r（这里状态记录 {x:Nat}），再返回一个方法记录，各方法闭包共享 r。

理解要点在于，`newCounter` 是一个**对象生成器**（object generator）——每调用一次就 `ref` 出一份全新状态、产出一个新对象，对应 OO 里的 `new`。方法通过读写共享的 r 来实现"有记忆的行为"：`get` 读 r 的 x，`inc` 把 r 的 x 更新为后继。这里 T5.3 的引用变型开始起作用：状态被藏在 Ref 后面，而 Ref 不变，正好保证了对象内部状态不会被子类型误替换击穿。初学者容易混的一点：**对象类型（方法记录的类型，可子类型化、可宽度变化）与内部状态类型（藏在 Ref 里、不变）是两层不同的东西**——外层灵活、内层刚性，各司其职。

### T5.4.3 类、self 与开放递归

在对象编码之上，**类**（class）被编码成"对象生成器的模板"，而方法要相互调用（一个方法调用同对象的另一个方法）则需要 **self**（this），其形式化是**开放递归**（open recursion，TAPL §18.9–§18.12 讨论 self、super、开放递归）。核心思想是把对象定义写成一个以自身为参数的函数，再用不动点把 self 绑回去

对象体 = λself. {方法们……可调用 self.其它方法}，真正的对象 = fix(对象体)

理解要点在于，类相比对象多了两件事——**可复用生成逻辑**（一份代码造无数对象）和**方法间互调 + 继承覆盖**。方法互调需要每个方法能引用"最终的、可能被子类覆盖过的"自己，这就是 self 的语义；用不动点组合子（承 T2.3.5 的 fix）把"尚未确定的 self"延迟绑定，正是**晚绑定/动态分派**（late binding / dynamic dispatch）的类型论根源——子类覆盖一个方法后，父类方法通过 self 调它时会调到覆盖后的版本。super 则是绑定到"覆盖前"的父类方法记录。本小主题按 prompt 只作"对象在 λ 中如何编码"的点名，OO 的完整语言机制（继承、多态、封装的工程设计）交由 **L3-04 面向对象范式**展开，此处不深入。初学者先记住一句：**"类 = 生成对象的函数 + 用不动点把 self 绑进方法，从而支持覆盖与晚绑定"**，细节留给 OO 专题。

#### 来源与时效（本小主题）
- 一手：TAPL Ch.18（Case Study: Imperative Objects：对象为方法记录、对象生成器、实例变量分组、简单类、子类型、self 与开放递归、super），2002 版，核实 2026-07-30。
- 交叉一手：Harper《PFPL》2nd ed. 2016 关于"对象/类作为存在类型/递归记录的编码"与动态分派的处理，可作独立佐证——两者都把 OO 还原为更基础的类型构造（记录/引用/递归/存在类型）而非原生概念。
- 冲突项：无实质分歧；编码方案有多种（TAPL 的方法记录 + 引用 vs 存在类型封装状态），属"同一目标的不同编码手段"，本节以 TAPL 的命令式对象编码为主线，其余仅点名。

## T5.5 Featherweight Java

### T5.5.1 FJ 是什么：Java 的极简核心演算

**Featherweight Java（FJ）** 是把 Java 砍到只剩最核心特性的一个极小演算，用来精确地陈述并证明 Java 类型系统的性质（TAPL Ch.19；原始文献 Igarashi, Pierce & Wadler, TOPLAS 2001）。它只保留：类声明、字段、方法、方法调用、对象创建 `new`、字段访问、类型转换 `cast`、以及 `this`；**砍掉**赋值（对象一旦创建不可变）、接口、重载、内部类、并发等一切"非本质"特性。

理解要点是"FJ 是给 Java 做的最小可推理模型"——就像 T2.1 那个玩具算术语言之于完整语言。它小到整套语法、归约、类型规则能印在一两页纸上、能手工完成可靠性证明，又保留了 Java 类型系统最想研究的东西：**基于继承的名义子类型（nominal subtyping）**和**类型转换（cast）**。为什么要砍掉赋值？因为 FJ 的设计目标是研究类与继承的类型行为，去掉可变状态能让演算变成纯函数式、大幅简化元理论，同时不影响对"继承/子类型/cast"的刻画。初学者要理解 FJ 与 T5.4 的对照：T5.4 是把对象**编码进** λ（结构化、structural），FJ 则是直接把 Java 的**名义（nominal）**类机制形式化——两条路线对应 OO 语言里"结构子类型 vs 名义子类型"的两大流派。

### T5.5.2 FJ 的核心：类表、名义子类型、方法查找

FJ 程序是一张**类表**（class table，一组类声明）加一个表达式。每个类形如

class C extends D { 字段声明; 构造器; 方法定义 }

FJ 的**子类型关系直接由 extends 的自反传递闭包给出**（名义子类型，TAPL §19.2–§19.3）

C <: C（自反）；　C extends D ⟹ C <: D；　C <: D 且 D <: E ⟹ C <: E（传递）

字段与方法通过在类表里沿继承链**查找**（fields(C)、mtype(m,C)、mbody(m,C) 等辅助函数）解析。

理解要点在于**名义（nominal）子类型和结构（structural）子类型的根本区别**。T5.1 的记录子类型是结构的——两个类型只要"形状匹配"（字段满足宽度/深度规则）就自动成为子类型，不管叫什么名字。FJ/Java 是名义的——`C <: D` **当且仅当**程序员显式写了 `class C extends D`（或经传递）；即使两个类字段方法完全一样，没写 extends 就不是子类型。名义子类型的好处是意图明确、可控（不会"意外"成为子类型），且天然支持递归类型与运行时类型标签（cast 靠它）；代价是灵活性差、要显式声明。初学者要把这条记牢：**Java/C#/C++ 是名义子类型，Go 接口/TypeScript/OCaml 对象是结构子类型**；FJ 形式化的是前者。方法查找沿 extends 链向上找，正是继承"子类没有就用父类的"的形式化。

### T5.5.3 FJ 的类型安全与 cast 的运行时角色

FJ 满足类型安全，其表述仍是 Progress + Preservation，但因为有 cast，多出一类"卡住"情形需要特别处理（TAPL §19.4；IPW 2001）。保型与进展的联合结论大致是

良类型的 FJ 项，要么是值（一个 `new C(...)`），要么能求值一步，要么**卡在一个必然失败的向下转型（stupid cast / downcast 失败）上**。

即 cast 是唯一可能让良类型项"合法地卡住"的地方，对应 Java 运行时的 `ClassCastException`。

理解要点在于，cast 把一个类型"向下"看成它的子类型（如把 Object 转成 String），这是**subsumption 的反方向**——T5.1.1 说过向上转型总安全、向下转型不安全。FJ 的类型规则允许写 cast（否则没法建模 Java 的强制转型），但类型系统无法在编译期保证转型一定成功，于是把检查留到运行时：`(C) new D(...)` 当 D <: C 时成功（**up-cast**，其实多余但安全）、当 C <: D 时是需要运行时验证的 **down-cast**、当 C 与 D 无子类型关系时是**stupid cast**（编译期就能判定必失败、Java 直接报编译错，FJ 里标为无法归约的错误项）。FJ 的可靠性定理精确刻画了"良类型 Java 程序运行时的类型错误只可能是 cast 失败（ClassCastException），不会有别的类型崩溃"。初学者要把 FJ 看成 T3.3 类型安全定理在真实语言上的落地范例：**它证明了 Java 核心是类型安全的，且把"哪些错误逃到运行时"（只有向下 cast）说得一清二楚**——这也是 GJ（带泛型的 Java，即后来的 Java 泛型）设计与证明的基础。本小主题为形式化元理论，未做本机实证（FJ 可靠性属证明论结果；如需可跑 Java 复现 ClassCastException，属可选，未取，标注）。

- 交叉一手：Igarashi, Pierce & Wadler《Featherweight Java: A Minimal Core Calculus for Java and GJ》ACM TOPLAS 23(3):396–450, 2001（会议版 OOPSLA'99）——FJ 的原始一手定义，TAPL Ch.19 即基于此；两者在语法、子类型定义、cast 分类（up/down/stupid）、可靠性陈述上一致。Java SE 21 JLS §5.5（cast 转换）与 §15.9（class instance creation）为"cast 运行时 ClassCastException、名义继承"的语言侧佐证。
