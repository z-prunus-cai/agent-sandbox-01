**高阶系统就是"把 λ 演算那一套（抽象、应用、β 归约、类型检查）原样复制到类型层，再让类型也需要被'定型'"**。前面几大主题里，类型一直是"扁平"的名字或简单构造（Bool、Nat、T₁→T₂、∀X.T）；从本篇起，类型自己也可以是**函数**——例如 `List` 不是一个类型，而是"吃一个类型、吐一个类型"的算子。一旦类型能当函数用，就必须有一层判断式来回答"这个类型表达式合不合法、它是普通类型还是算子"，这层判断式就是**种类判断（kinding）** Γ ⊢ T :: K。System F 让项在类型上抽象（多态），λω 让类型在类型上抽象（算子），两者合流即 Fω；再叠上子类型即 Fω<:。

这也正是 Barendregt λ-cube 的三条坐标轴：项依赖类型（多态，→ System F）、类型依赖类型（算子，→ λω），以及本篇末尾只点名的第三轴——类型依赖项（依赖类型，→ λP 直至演算构造 CoC，即 Coq 的内核，交 L6-02 V11）。

## T10.1 类型算子与 kinding

### T10.1.1 从"类型"到"类型算子"：为什么需要类型级函数

**类型算子**（type operator，又称 type constructor / 构造子，TAPL Ch.29 引言）是一个从类型到类型的函数，例如"给我元素类型 X、还你列表类型 List X"。在 STLC 与 System F 里，像 `List Nat`、`Pair Bool Nat` 这种写法只是**具体类型的缩写**，语言本身并没有把 `List`、`Pair` 当成可以独立存在、可以传递和抽象的对象。Ch.29 的目标是把这种"参数化的类型"提升为**一等的类型级函数**：允许写出

```
List = λX. ∀R. R → (X → List X → R) → R
Pair = λX. λY. ∀R. (X → Y → R) → R
```

这样的类型级 λ 抽象，并允许 `List Nat` 是真正的"把算子 List 应用到实参 Nat"。

这一步和当年"把函数变成一等公民"完全平行，只是搬到了类型层。在项层，`λx. x+1` 是一个可以到处传的值；在类型层，`λX. X→X` 就是一个可以到处传的类型算子。没有类型算子时，你只能一个一个手写 `ListNat`、`ListBool`、`ListListNat`，全是彼此无关的名字；有了类型算子，`List` 是一个东西，`List Nat`、`List Bool` 都是它的应用结果，"列表"这个概念在语言里第一次有了统一的形式对应物。

类型算子本身**不是类型**。`List` 不能拿来标注一个项（你不能写 `x : List`，只能写 `x : List Nat`），因为它还"缺一个参数"。正是这个"缺不缺参数、缺几个"的区别，逼出了下一节的种类系统——需要一层判断式来区分"完工的类型"和"半成品算子"。

### T10.1.2 种类 kind：类型的类型

**种类**（kind，TAPL §29.1）是"类型层的类型"，用来对类型表达式做分类。种类的语法只有两条：

```
K ::= *              （proper types，可用来classify项的"真正类型"的种类）
    | K ⇒ K          （type operators，从种类到种类的算子的种类）
```

`*`（读作 "type" 或 "star"）是所有"能标注项的普通类型"的种类，如 `Bool :: *`、`Nat→Nat :: *`。`K₁ ⇒ K₂` 是类型算子的种类：`List` 吃一个 `*` 类型、还一个 `*` 类型，所以

```
List :: * ⇒ *
Pair :: * ⇒ * ⇒ *
```

把种类系统看成"类型系统的类型系统"，层级完全同构。项被类型分类（`3 : Nat`），类型被种类分类（`Nat :: *`）。`*` 对应"基本已完工的类型"，`⇒` 对应"类型层的箭头"，和项层的 `→` 长得一模一样——这不是巧合，λω 就是把 STLC 整套原样搬到类型层：种类 `*` 扮演 STLC 里"唯一的基类型"的角色，`⇒` 扮演 `→` 的角色，类型算子 `λX::K.T` 扮演 `λx:T.t` 的角色。

`* ⇒ *` 这种种类只描述"元数与形状"，不描述算子内部行为。`List` 和 `λX. X→X` 种类都是 `* ⇒ *`，但显然是不同的算子——种类只保证"你给它一个真类型、它会还你一个真类型"，不保证还的是什么。这与项层"两个不同函数可以有同一个类型 Nat→Nat"完全对应。

### T10.1.3 λω 系统：类型级抽象与应用

**λω**（TAPL Ch.29 的系统名；Barendregt λ-cube 中"类型依赖类型"那一条轴的顶点）就是 STLC 加上类型算子后得到的系统。它在类型语法里新增了类型级 λ 抽象与类型级应用：

```
T ::= X                 （类型变量）
    | T → T             （箭头类型）
    | λX::K. T          （类型算子 / 类型级抽象）
    | T T               （类型级应用）
```

于是 `List Nat` 不再是缩写，而是真正的类型级应用项——`List` 是 `λX. …`，把它应用到 `Nat` 上，按类型级 β 归约算出结果类型。

你已经在 T2/T3 里学过项层的 λ 抽象与应用、α 等价、β 归约；λω 说的是"类型层也有这一整套"。类型层的 `λX::K.T` 引入一个类型变量 X（并声明它的种类 K），`T₁ T₂` 把算子 T₁ 应用到实参 T₂。唯一的新东西是每个类型变量抽象时要写上它的种类 `::K`，因为类型层现在也有"高低阶"之分，需要种类来把关。

`(λX::*. X→X) Bool` 是一个类型级应用，它会归约到 `Bool→Bool`。注意这发生在**类型检查阶段**，编译器在核对项的类型时会把类型表达式先算一算——这就引出了 T10.1.5 的"类型等价"。λω 本身**还没有多态**（没有 ∀）；它只是"带类型算子的 STLC"。把 λω 与 System F 合起来才是 Fω，这是 T10.2 的事。

### T10.1.4 kinding 判断式 Γ ⊢ T :: K 与 kinding 规则

**kinding**（种类判定，TAPL §29.1 Fig 29-1）是回答"类型表达式 T 是否良构、其种类为何"的判断式，写作

```
Γ ⊢ T :: K
```

其中环境 Γ 现在除了记录"项变量 : 类型"，还记录"类型变量 :: 种类"（形如 `X::K`）。核心规则与 STLC 的类型规则严格平行：

```
                     X::K ∈ Γ
（K-Var）           ─────────────
                    Γ ⊢ X :: K


                  Γ, X::K₁ ⊢ T₂ :: K₂
（K-Abs）        ──────────────────────────
                 Γ ⊢ λX::K₁.T₂ :: K₁ ⇒ K₂


              Γ ⊢ T₁ :: K₁₁ ⇒ K₁₂      Γ ⊢ T₂ :: K₁₁
（K-App）     ───────────────────────────────────────────
                        Γ ⊢ T₁ T₂ :: K₁₂


                 Γ ⊢ T₁ :: *      Γ ⊢ T₂ :: *
（K-Arrow）     ────────────────────────────────
                       Γ ⊢ T₁ → T₂ :: *
```

把这四条规则和 STLC 的 T-Var/T-Abs/T-App 对照着读，会发现它们逐字对应——K-Abs 就是 T-Abs 把 `:T` 换成 `::K`、把 `→` 换成 `⇒`；K-App 就是 T-App 的翻版。K-Arrow 是新加的把关：一个箭头类型 `T₁→T₂` 只有当左右两边都是**真类型**（种类 `*`）时才合法，你不能写 `List→Nat`（左边 `List :: *⇒*` 不是 `*`），因为"一个还缺参数的算子"不能直接当类型用。

这条 K-Arrow 正是种类系统的价值所在：它在类型检查更早的一层拦掉 `x : List` 这种错误——`List` 种类是 `*⇒*` 而标注位置要求种类 `*`，kinding 直接判不通过。要点是：kinding 是**判定性**的（对良构输入总能算出唯一种类或报错），它是 Fω 类型检查器"检查类型标注本身是否合法"的那一遍。

### T10.1.5 类型等价（定义相等）与类型级 β 归约

引入类型算子后，"两个类型表达式何时算同一个类型"不再是"字面相同"，而要模掉**类型级 β 归约**。TAPL §29.2 定义**类型等价**（type equivalence，记 `≡`，又称 definitional equality / 定义相等），其核心一条是类型层的 β：

```
（Q-AppAbs）      (λX::K₁.T₁₂) T₂  ≡  [X ↦ T₂] T₁₂
```

再加上自反、对称、传递与各构造子上的**同余**（congruence，即"子部件等价则整体等价"）。类型检查器据此把类型算成范式再比较。为把类型等价接回项的类型系统，需要一条新的类型规则：

```
                 Γ ⊢ t : S      S ≡ T      Γ ⊢ T :: *
（T-Eq）         ────────────────────────────────────────
                              Γ ⊢ t : T
```

Q-AppAbs 说的是"`(λX. X→X) Bool` 和 `Bool→Bool` 是同一个类型"，只不过一个没算、一个算完了。T-Eq 则允许类型检查器在核对时"随时把类型化简一下再比"：如果一个项能推出类型 `(λX.X→X) Bool`，而你要它匹配 `Bool→Bool`，T-Eq 通过类型等价把这道缝抹平。没有 T-Eq，类型检查就会因为"长得不一样"而误报，即使两者本质是同一类型。

一个易错点是把类型等价和子类型混为一谈：等价 `≡` 是**双向**的（`S≡T` 意味着可以互相替换），而子类型 `<:` 是**单向**的（`S<:T` 只允许 S 出现在需要 T 的地方）。本节的 `≡` 只处理"算不算得到同一个类型"，与大小无关；子类型要到 T10.3 才登场。另一个关键事实：λω/Fω 的类型层是**强正规化**（strongly normalizing）的，任何良种类的类型表达式化简都终止且范式唯一，所以类型等价是**可判定**的——这保证了 Fω 的类型检查算法能真正跑完，是整套系统能落地的基石。

## T10.2 高阶多态 Fω

### T10.2.1 Fω = System F + 类型算子：三系统合流

**System Fω**（读作 "F-omega"，TAPL Ch.30）是把 **System F 的多态**与 **λω 的类型算子**合并到一个系统里的结果。用一句话概括三者关系：

```
STLC（λ→）        ：项在项上抽象
System F（λ2）    ：项在类型上抽象（多态）      = STLC + ∀
λω               ：类型在类型上抽象（算子）    = STLC + 类型算子/种类
System Fω        ：两者兼有                    = System F + λω
```

Fω 的语法同时拥有项层的 `ΛX::K.t` / `t[T]`（类型抽象/应用，来自 F）和类型层的 `λX::K.T` / `T T`（类型算子/应用，来自 λω），并统一在 Γ ⊢ T :: K 的种类系统下管理。

这两条能力是"正交"的，合并后不打架，只是叠加。System F 让你写"对任意类型 X 都成立的函数"（多态恒等式 `ΛX. λx:X. x : ∀X.X→X`）；λω 让你写"参数化的类型"（`List :: *⇒*`）。Fω 让你两样一起用，比如写一个"对任意元素类型都能用的、作用在任意容器算子上的"高阶多态函数——这正是 Haskell 里 `fmap :: (a -> b) -> f a -> f b` 那种"对容器 f 也多态"的能力的理论根。

Fω 里**类型抽象**（Λ，项对类型多态）和**类型算子**（λ 在类型层，类型对类型抽象）是两个不同层次的东西，初学者极易混淆。前者产生的是 `∀X.T` 这种类型、作用于项的类型检查；后者产生的是 `*⇒*` 这种算子、作用于类型的 kinding。记法上 F 的类型抽象常写大写 `Λ`、类型层抽象写小写 `λ`，就是为了在视觉上把两层分开。

### T10.2.2 kinded 量化 ∀X::K.T 与 K-All 规则

在 System F 里全称类型写作 `∀X.T`；到了 Fω，被量化的类型变量 X 可能不是普通类型而是任意种类的算子，所以量化必须**带种类标注**：

```
T ::= … | ∀X::K. T
```

其良种类由新规则给出：

```
                 Γ, X::K₁ ⊢ T₂ :: *
（K-All）        ──────────────────────────
                 Γ ⊢ ∀X::K₁.T₂ :: *
```

对应地，项层的类型抽象与类型应用规则也带上种类与 kinding 前提：

```
              Γ, X::K₁ ⊢ t₂ : T₂
（T-TAbs）    ──────────────────────────────
              Γ ⊢ ΛX::K₁.t₂ : ∀X::K₁.T₂


              Γ ⊢ t₁ : ∀X::K₁₁.T₁₂      Γ ⊢ T₂ :: K₁₁
（T-TApp）    ───────────────────────────────────────────
                    Γ ⊢ t₁ [T₂] : [X ↦ T₂]T₁₂
```

F 里的 `∀X.T` 默认 X 是普通类型（种类 `*`）；Fω 把这个隐含前提显式化成 `∀X::K.T`，于是你能量化"对所有一元类型算子 f"这种更高阶的东西，例如 `∀F::*⇒*. …`。K-All 规则说：无论 X 量化的是什么种类的东西，整个 `∀X::K.T` 只要 body 是真类型（`*`），它自己就是一个真类型（`*`）——因为 `∀X::K.T` 是可以拿来标注项的完工类型。

一个易错点在 T-TApp：类型应用 `t₁[T₂]` 现在多了一条前提 `Γ ⊢ T₂ :: K₁₁`，即"你代入的实参类型 T₂ 的种类，必须和量词声明的种类 K₁₁ 对上"。在 F 里这条前提是平凡的（都是 `*`）；在 Fω 里你若把一个算子（`*⇒*`）代进只接受普通类型（`*`）的量词位置，kinding 会当场拒绝。这体现了"种类系统在类型应用处也把关"。

### T10.2.3 Fω 中的编码：高阶类型与容器多态

Fω 的表达力足以把"对容器结构多态"的程序直接写成类型。一个典范是多态的 `map`／`fmap`——它不仅对元素类型多态，还允许被作用的类型算子出现在量词里。以列表算子 `List :: *⇒*` 为例，一个"对任意元素类型的 map"的类型是

```
map : ∀X::*. ∀Y::*. (X → Y) → List X → List Y
```

这里 `List X`、`List Y` 都是类型级应用（K-App 保证它们种类为 `*`）。更进一步，Fω 能量化算子本身：

```
∀F::*⇒*. ∀X::*. ∀Y::*. (X → Y) → F X → F Y
```

这就是"对任意一元容器 F 的 map 的类型"。

这正是"从 List 特供的 map，升级到对任何容器都通用的 fmap"这一步在类型上长什么样。前一个类型把 `List` 写死；后一个把容器抽象成量化的算子 `F`，于是 map 的类型描述了"任何满足 `*⇒*` 形状的容器都能被逐元素映射"这一通用契约。Haskell 的 `Functor` 类型类、`fmap :: Functor f => (a->b) -> f a -> f b`，其"对 f 多态"的本质就落在这条 Fω 类型上（Haskell 的 higher-kinded types 是 Fω 高阶量化的工程化）。

Fω 让你**在类型里谈论类型算子**，但它仍然是"多态 + 算子"的组合，并**没有**让类型依赖具体的项值——`F X` 里的 X 永远是类型，不可能是某个运行时数字。这条边界把 Fω 和依赖类型（T10.4）划清：容器对"元素类型"多态是 Fω，容器对"元素个数这个值"依赖才是依赖类型。

### T10.2.4 Barendregt λ-cube 中的定位

把已学的几个系统摆进 **Barendregt λ-cube**（λ 立方体，Barendregt 1991/1992）能一眼看清 Fω 的坐标。立方体从 STLC（λ→）出发，沿三条互相正交的轴增加"依赖关系"：

```
轴①  项依赖类型（多态）        λ→ → λ2（System F）
轴②  类型依赖类型（类型算子）  λ→ → λω
轴③  类型依赖项（依赖类型）    λ→ → λP（LF）
```

Fω（λ2ω）= 同时打开轴①与轴②，即"多态 + 类型算子"；八个顶点里同时打开全部三轴的顶端是 **λC = 演算构造（Calculus of Constructions, CoC）**。

三条轴回答"谁能依赖谁"。普通函数是"项依赖项"（λ→，STLC 已有，不算轴）；多态是"项能对类型抽象"（轴①）；类型算子是"类型能对类型抽象"（轴②）；依赖类型是"类型能对具体的项值抽象"（轴③，本篇只点名）。Fω 恰好是"前两轴都开、第三轴不开"的那个顶点——它把类型层玩到极致（类型可以是任意高阶算子、可以被多态量化），但类型仍然只依赖类型、绝不依赖运行时的值。

这幅图的价值在于给出一张"下一步能往哪走"的地图：从 Fω 沿第三条轴继续走，就到依赖类型、到 CoC、到 Coq 的内核（交 L6-02 V11）。一个易错点是把 λ-cube 的顶点数记错——是 2³ = 8 个顶点（每轴开/关），Fω 与 CoC 是其中两个特定顶点，不是同一个。

### T10.2.5 Fω 元理论要点：正规化、可判定性

Fω 保留了 System F 与 λω 的良好元理论。关键事实（TAPL §30.3 与相关文献）：Fω 的项层与类型层都**强正规化**（strongly normalizing，Girard 1972 用可归约候选/reducibility candidates 技术证明 F 与 Fω 的正规化）；因此类型等价（模类型级 β）**可判定**，进而 Fω 的**类型检查可判定**。作为对照，System F 的**类型重建（type reconstruction，无标注推断）不可判定**（承 T8.3；Wells 1994 证明二阶合一/F 类型推断不可判定），Fω 亦然。

这两个"可判定"缺一不可。Fω 类型检查要不断地把类型算一算再比（T-Eq），如果类型级归约可能不终止，检查器就可能卡死；强正规化保证"算类型这件事一定停"，于是可判定。但"检查一个**带全标注**的程序"可判定，不等于"**不写标注**让编译器自己推"可判定——后者是类型重建，在 F/Fω 层面已被证不可判定。这解释了为什么 Haskell、OCaml 这类工程语言在触及高阶多态时，往往要求程序员在关键处写类型标注（如 Haskell 的 `RankNTypes`、显式 `forall`），而不敢全自动推断。

要点是把"可靠性/正规化"（理论保证程序不出错、类型化简会停）与"可判定性/可推断性"（工具层面检查会停、推断能不能全自动）分层看待。Fω 的定位是：类型检查判定性有、全自动类型推断没有（需标注辅助）。

## T10.3 高阶子类型 Fω<:

### T10.3.1 动机：把子类型抬到类型算子层

**System Fω<:**（TAPL Ch.31）是把 T5/T9 的子类型关系与 Fω 的类型算子合并的系统。核心问题是：既然类型现在可以是算子（如 `List :: *⇒*`），那"一个算子是不是另一个算子的子类型"该怎么定义？例如若 `Nat <: Int`，是否应有 `List Nat <: List Int`？Fω<: 就是要为"算子之间、以及不同种类的类型之间"给出一致的子类型规则，并把有界量化（F<:）也抬到高阶。

前面三个能力现在要三合一——多态（F）、有界量化（F<:）、类型算子（λω）。单独看子类型你已经在 T5 见过（记录/函数变型、Top/Bot），单独看有界量化在 T9 见过（`∀X<:T.…`）。Fω<: 的新意在于"子类型不再只发生在种类 `*` 的普通类型之间，还要发生在 `*⇒*` 这类算子之间"，于是子类型判断式本身也得带上种类。

这是 Part VI 里机制最密、最容易绕晕的一节。抓住主线——"把 T5 学的每条子类型规则，逐点（pointwise）提升到算子层"——就不会迷路。TAPL 也坦言 Fω<: 的元理论显著更复杂，本篇按教辅定位只讲到"规则形态与关键结论"，不做完整证明纵深。

### T10.3.2 kinded 子类型判断式 Γ ⊢ S <: T :: K

Fω<: 的子类型判断式在 T5 的 `Γ ⊢ S <: T` 上增加了种类信息，写作

```
Γ ⊢ S <: T :: K
```

读作"在环境 Γ 下，S 是 T 的子类型，且二者共同的种类为 K"。只有**同种类**的两个类型/算子之间才谈得上子类型——比较 `List <: Maybe` 只在两者都是 `*⇒*` 时有意义，跨种类比较无定义。环境 Γ 里的类型变量声明也升级为**带界带种类**的形式 `X<:T::K`（有界量化的界 T 与被声明变量同种类）。

种类在这里扮演"类型对齐"的角色，就像项的子类型里你不会去比较一个函数和一个记录一样，算子层也只在"形状（种类）相同"的东西之间比大小。`:: K` 这个后缀是全篇技术负担的来源——每条子类型规则都要在推导子类型的同时维护种类一致，规则数量和前提都随之膨胀。

不要把 `S <: T :: K` 读成"S 是 T 的子类型，而 T 的种类是 K"这种偏心的读法；正确读法是"S 与 T **同为**种类 K，且在该种类上 S <: T"。种类是双方共有的对齐条件，不是单属于某一边。

### T10.3.3 算子的逐点子类型与提升（promotion）

Fω<: 把子类型沿算子结构**逐点**（pointwise）扩展。直觉规则是：两个算子若"对每个输入都给出成子类型关系的输出"，则算子间成子类型；再配合应用处保持子类型：

```
              Γ, X::K₁ ⊢ S₂ <: T₂ :: K₂
（S-Abs 型）  ──────────────────────────────────────
              Γ ⊢ λX::K₁.S₂ <: λX::K₁.T₂ :: K₁⇒K₂


              Γ ⊢ S <: T :: K₁⇒K₂      Γ ⊢ U :: K₁
（S-App 型）  ──────────────────────────────────────
                    Γ ⊢ S U <: T U :: K₂
```

此外，有界类型变量在需要时可**提升**（promotion，记 `Γ ⊢ S ⇑ T`）到它的界，用于把一个变量替换成其上界以推进子类型判定；这套算法式处理承 T9 F<: 的思路，抬到高阶。

逐点扩展就是"算子的大小由它逐个输出的大小决定"。若对每个元素类型 X 都有 `S₂ <: T₂`，那么把 X 抽象掉后算子 `λX.S₂` 就整体 `<:` 算子 `λX.T₂`；S-App 则说"把同一个实参 U 喂给成子类型关系的两个算子，结果仍保持子类型"。这与 T5 里"函数子类型：参数逆变、结果协变"的精神一脉相承，只是搬到了类型层的算子上。

逐点扩展默认对算子的"输出"是协变的，但具体算子（如可变引用 `Ref`）在其参数上可能是不变或逆变的，是否安全取决于该算子的具体定义（承 T5.3 协变数组之坑）。种类系统只保证"形状对齐"，不自动赋予安全的变型——变型标注/约束是更精细的话题，本篇点到为止。

### T10.3.4 kernel vs full 的延续、元理论与复杂度

Fω<: 继承了 T9 F<: 的 **kernel vs full** 之分。kernel 版对量词的子类型要求"两个 `∀X<:U.…` 的界 U 完全相同"，full 版允许界之间也成（逆变的）子类型。TAPL 指出：full 版在一阶已使 **Full F<: 子类型判定不可判定**（承 T9.3，Pierce 1994 的构造），这一不可判定性在高阶的 Full Fω<: 依旧存在；实用系统（及 TAPL 的可靠性发展）多采用 **kernel Fω<:**，其子类型与类型检查具良好性质。Fω<: 的元理论（子类型下的可靠性、算法化子类型的完备性、类型等价与子类型的相互作用）显著比前面各系统繁复。

kernel 是"保守但可判定"的选择——量词的界必须逐字相同，规则简单、算法会停；full 是"更灵活但危险"的选择——连界都允许有子类型关系，表达力更强，但 T9.3 已给出一个让子类型判定永不终止的构造，抬到高阶也救不回来。工程与教材因此普遍站 kernel 一边：宁可少一点灵活，也要类型检查器能保证跑完。

这条把 T9 的"Full F<: 不可判定"结论一路带到了高阶系统的最外层，是"子类型 + 有界量化"这条线的终点风险提示。它也解释了为何现实语言（Java/Scala 的泛型子类型、Rust 的 trait bound，交 L5-14 R6.3）在设计上都对"界之间再比子类型"这类特性高度克制或加以限制——理论上的不可判定在工程上会表现为编译器可能卡死或需要人为标注辅助。Fω<: 的完整元理论展开超出本篇教辅深度，只给结论与风险定位。

## T10.4 案例与依赖类型一瞥

### T10.4.1 案例研究：纯函数式对象（TAPL Ch.32）

TAPL Part VI 的收尾案例是用高阶系统**把面向对象编程编码进 Fω<:**，即**纯函数式对象**（purely functional objects，Ch.32）。与 T5.4 的命令式对象（用引用存可变状态）不同，这里用**存在类型 ∃X.…**（承 T8.4）封装对象内部状态、用**记录**存方法、用**有界量化与类型算子**处理 self 类型与继承，得到一个不依赖可变引用、纯函数式的对象模型：对象是"把内部状态类型藏起来（存在量化）、只暴露一组方法记录"的包，方法通过返回"新对象"而非修改原对象来表达状态更新。

这一章的意义是"验收"——把前面攒的所有零件（存在类型做数据抽象、记录与子类型做接口与继承、类型算子做参数化、有界量化做 self 类型的界）拼成一个能表达真实 OO 特性（封装、子类型、继承、self）的系统，证明 Fω<: 的表达力确实够用。"纯函数式"是说对象没有内部可变格：调用 `counter.inc()` 不是就地加一，而是返回一个"计数加一后的新 counter"，一切靠值的传递，符合函数式无副作用的风格。

这与 T5.4/T5.5（命令式对象、Featherweight Java）互为对照——同一个"对象"概念，可以用可变引用的命令式方式编码，也可以用存在类型 + 高阶的纯函数式方式编码，体现"OO 不是原生魔法，而是更基础类型构造的组合"。完整机制展开交 L3-04 OOP；本篇按教辅定位只给编码思路的骨架，不逐规则展开。

### T10.4.2 高阶系统在真实语言中的投影

Fω 及其子类型扩展不是纸上系统，主流函数式/多范式语言的类型系统大多是它的受限工程化。几个对应关系：Haskell 的 **higher-kinded types**（`Functor f`、`Monad m` 中对种类 `*⇒*` 的类型构造子 f/m 抽象）几乎是 Fω 高阶量化的直接落地；ML/OCaml 的 **functor（函子，参数化模块）** 是"模块层的类型算子"，把"依赖一个模块、产出一个模块"形式化；Scala 的高阶类型参数（`F[_]`）、以及 Rust 逐步引入的 **GAT（generic associated types，泛型关联类型）** 也在向高阶靠拢（Rust 侧交 L5-14 R6，具体特性版本以本机 rustc 现查为准，不凭记忆）。

当你在 Haskell 写 `class Functor f where fmap :: (a->b) -> f a -> f b`，那个"对容器 f 也抽象"的能力，教科书里的名字就是 Fω 的高阶多态（T10.2.3 那条 `∀F::*⇒*.…` 类型）。语言之所以要求这些特性往往伴随更多类型标注、或对推断有限制，正是因为高阶多态触及了 Fω 层"类型重建不可判定"的边界（T10.2.5）——理论上的不可推断在工程上表现为"编译器需要你多写点类型信息"。

要点是把"理论系统 ↔ 语言特性"这条映射建立起来：λω/Fω/Fω<: 不是屠龙之技，而是解释"为什么 Haskell 有 higher-kinded types、为什么 ML 有 functor、为什么这些特性对推断不友好"的底层语法。凡涉及具体语言的版本/特性名（如 Rust GAT 是否稳定、Scala 版本），均标注以现查为准，不在本报告写死版本号。

### T10.4.3 通向依赖类型：λ-cube 的第四条轴

沿 Barendregt λ-cube（T10.2.4）的**第三条轴——类型依赖项（types depend on terms）**继续走，就离开 Fω、进入**依赖类型**（dependent types）的领地。其最小顶点是 **λP（LF，Edinburgh Logical Framework）**，把三条轴全部打开的顶端是 **λC = 演算构造（Calculus of Constructions, CoC，Coquand & Huet 1988）**——它正是 **Coq 证明助手内核**（CIC，Calculus of Inductive Constructions 的基础）的理论根。依赖类型的核心新意是：类型里可以出现具体的项值，例如"长度为 n 的向量"

```
Vec : Nat → * → *          （种类里出现了 Nat 这个"值的类型"）
Vec 3 Bool                 （类型依赖具体的值 3）
```

这在 Fω 里是做不到的——Fω 的 `F X` 里 X 只能是类型，绝不能是运行时的数 `3`。

Fω 让"类型依赖类型"（`List` 吃类型），依赖类型让"类型依赖值"（`Vec 3` 吃数值）。一旦类型能谈论具体的值，类型就强到可以直接表达数学命题——"这个函数返回的向量长度恰为输入长度"这种规格可以写进类型，类型检查即证明检查。这正是 **Curry-Howard 同构的深化**（承 T3.4"命题即类型、证明即程序"）：命题是依赖类型、证明是该类型的项、类型检查器就是证明检查器（接 L6-02 V11.2"依赖类型即命题"）。

本篇对依赖类型**只作一瞥、点名不展开**：完整机制（依赖函数类型 Π、依赖对类型 Σ、归纳类型、tactic 证明、可信基 TCB、机械化元理论）属 **L6-02 程序分析与形式验证 V11 交互式定理证明** 的内容，以 Coq/Software Foundations 为一手锚点在那里展开。这里给出的定位是：Fω 是"类型系统能玩到的、仍不依赖运行时值"的高点，跨过第三轴即进入依赖类型与证明助手的世界，四门课（L5-06 类型理论 ↔ L6-02 验证）在此汇合。
