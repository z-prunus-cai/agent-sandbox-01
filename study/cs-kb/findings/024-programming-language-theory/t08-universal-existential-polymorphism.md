T`，多态从此可以出现在任何位置、任意嵌套。它的对偶 `∃X. T`（存在类型）则反过来把类型**藏起来**，成为抽象数据类型与模块的理论根。

## T8.1 System F：类型抽象/应用、全称类型 ∀

### T8.1.1 从 STLC 到 System F：为什么要对类型抽象

System F（又称二阶 λ 演算、多态 λ 演算、polymorphic lambda-calculus）由 Girard（1972，逻辑视角）与 Reynolds（1974，编程语言视角）独立发现，是在 STLC 上增加"对类型的抽象与应用"得到的类型系统（TAPL Ch.23）。STLC 里恒等函数必须为每种类型各写一份——`λx:Bool. x`、`λx:Nat. x`……彼此毫无关系；System F 让你只写一份"对所有类型都成立"的版本，其语法在 STLC 的基础上多出两条类型构造与两条项构造：

```
类型  T ::= X | T→T | ∀X. T
项    t ::= x | λx:T. t | t t | ΛX. t | t [T]
```

其中 `∀X. T` 是**全称类型**（universal type），`ΛX. t` 是**类型抽象**（type abstraction），`t [T]` 是**类型应用**（type application）。

给初学者的直觉：把"类型"当成一种新的参数就懂了。普通函数 `λx:Nat. t` 说"给我一个 Nat 值 x，我算出 t"；类型抽象 `ΛX. t` 说"给我一个类型 X，我算出 t"。两者形状完全平行，只是一个收值、一个收类型。恒等函数在 System F 里写成"先收一个类型 X，再收一个 X 类型的值 x，把 x 还回去"：

```
id  =  ΛX. λx:X. x        :   ∀X. X→X
```

要用它时先喂类型、再喂值：`id [Nat] 5` 先把 X 定成 Nat，得到 `λx:Nat. x`，再作用到 5。这就是"一份代码、按需特化到各种类型"的通用多态。

一个易混点：`∀X. T` 里的 ∀ 不是逻辑里"对所有元素"，而是"对所有**类型**"。`∀X. X→X` 读作"对任意类型 X，都是一个从 X 到 X 的函数"——它描述的正是恒等函数这一族的共同类型。

### T8.1.2 类型抽象 Λ 与类型应用的求值

类型抽象与类型应用的运行时行为，和普通抽象/应用完全对称。类型应用碰到类型抽象时发生**类型层面的 β 归约**：把实参类型代入体内的类型变量。

```
(ΛX. t) [S]   ⟶   [X ↦ S] t
```

其中 `[X ↦ S] t` 表示把 t 里所有自由出现的类型变量 X 换成 S（对项里的类型标注和内部的类型应用都要换）。

给初学者的直觉：这跟普通函数 `(λx:T. t) v ⟶ [x↦v] t` 是一个模子——只不过代入的是"类型"而不是"值"。一个最小走查：

```
id [Nat]  =  (ΛX. λx:X. x) [Nat]  ⟶  λx:Nat. x
```

先把 X 代成 Nat，`λx:X. x` 里的标注 `X` 变成 `Nat`，得到 STLC 的整数恒等函数，然后它才能吃一个整数。

要点在于：类型抽象 `ΛX. t` 本身也是一个**值**（在纯 System F 里，Λ 抽象和 λ 抽象都是不再求值的值），所以 `id` 单独摆着不会算，必须先做类型应用把 X 定下来才进一步归约。初学者常把 `id [Nat]` 误当成"传了一个叫 Nat 的普通参数"——不是，方括号 `[ ]` 是语法上专门区分"喂类型"和"喂值"的记号，喂进去的 Nat 是类型不是值。

### T8.1.3 类型规则：T-TAbs 与 T-TApp

System F 在 STLC 三条规则（T-Var/T-Abs/T-App）之外，为类型抽象与类型应用各加一条（TAPL Ch.23，Figure 23-1）。类型环境 Γ 现在既记"值变量的类型"（`x:T`），也记"在作用域里的类型变量"（`X`）。

类型抽象规则 T-TAbs：在把 X 加入环境后，体 t 若有类型 T，则整个 Λ 抽象有全称类型。

```
        Γ, X ⊢ t : T
   ──────────────────────────   (T-TAbs)
   Γ ⊢ ΛX. t : ∀X. T
```

类型应用规则 T-TApp：若 t 有全称类型 `∀X. T₁`，则喂进类型 T₂ 后，结果类型是把 T₁ 里的 X 换成 T₂。

```
   Γ ⊢ t : ∀X. T₁
   ────────────────────────────────   (T-TApp)
   Γ ⊢ t [T₂] : [X ↦ T₂] T₁
```

给初学者的直觉：这两条和 STLC 的 T-Abs/T-App 一一对应。T-TAbs 像"函数把参数类型记进签名"——它把"体在 X 在场时成立"打包成"∀X. …"。T-TApp 像"应用消去箭头得到结果类型"——它把 ∀ 消去、同时把量化变量替换成你喂的具体类型。以恒等函数为例：

```
id : ∀X. X→X            由 T-TAbs 得
id [Nat] : Nat→Nat      由 T-TApp，把 X 换成 Nat
```

一个关键易错点是**作用域**：T-TAbs 要求 X 是"新引入、之前不在 Γ 里"的类型变量，且体里用到的所有自由类型变量都必须已经在环境中。若写 `λx:X. x` 而 X 没被任何外层 `ΛX` 或环境绑定，它是**非良构类型**（ill-formed），类型检查必须拒绝。这一点在本篇实证里会具体撞到。

### T8.1.4 谓词性 vs 非谓词性：System F 的表达力与代价

System F 是**非谓词的**（impredicative，TAPL Ch.23）：`∀X. T` 里的 X 可以被实例化成**任何**类型，**包括含 ∀ 的多态类型乃至该全称类型自身**。也就是说 `id [∀Y. Y→Y]` 是合法的——你可以把"恒等函数的类型"本身喂给恒等函数。作为对照，T7 的 Hindley-Milner 是**谓词的**（predicative）且限定"前束/秩-1"形式（量词只能出现在最外层），量化变量只能实例化成不含 ∀ 的单态类型。

```
id [∀Y. Y→Y]  :  (∀Y. Y→Y) → (∀Y. Y→Y)        -- System F 允许（非谓词）
```

给初学者的直觉：非谓词性是"自我引用式"的强大——"对所有类型成立"这句话里的"所有类型"把"对所有类型成立的类型"也算进去了，像集合论里"包含自己的集合"那种自指。它换来的是巨大的表达力：System F 里可以纯用 ∀ 编码出布尔、自然数（Church 数）、积、和、乃至存在类型（见 T8.4），完全不需要额外的内置类型。代价是这份表达力让类型推断彻底崩掉——正是 T8.3 要讲的"类型重建不可判定"的根源之一。

本机实证（可选·已做）：用 Python 3.11.15 实现一个显式类型（Church 风格）的 System F 类型检查器（类型代换 + T-TAbs/T-TApp + 类型良构性检查），对若干项给出类型或拒绝。命令 `python3 systemf.py`，真实输出——

```
id = LX. lx:X. x: (All X. (X -> X))
id [All Y.Y->Y]: ((All Y. (Y -> Y)) -> (All Y. (Y -> Y)))
double = LX. lf:X->X. la:X. f(f a): (All X. ((X -> X) -> (X -> X)))
(lx:X.x) [X]  (bad): REJECTED (free type var X not in scope)
lx:X. x  with X free (bad): REJECTED (free type var X not in scope)
```

第二行实机坐实了非谓词性——恒等函数被实例化到"多态类型" `∀Y. Y→Y` 上仍良类型；末两行坐实了 T8.1.3 的作用域约束（自由类型变量 X 不在作用域即拒）。基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25，实证机 @2026-07-30；此为加固补充，不替代多来源比对。

## T8.2 参数性：parametricity、免费定理

### T8.2.1 参数化多态 vs 特设多态

**参数化多态**（parametric polymorphism）指一个函数对它所抽象的类型参数"一视同仁"——它不能窥探、也不能因具体类型不同而改变行为，只能对所有类型跑同一套逻辑（Reynolds IFIP '83；术语 parametric vs ad-hoc 上溯 Strachey 1967）。System F 的多态正是参数化的。与之相对的**特设多态**（ad-hoc polymorphism，如函数重载、Java/C++ 的运行时类型判断）则允许"按类型分情况处理"。

给初学者的直觉：参数化多态的函数是"戴着眼罩干活"——它拿到一个类型 X 的值，但看不见 X 到底是 Nat 还是 Bool，只能把这个值当作一个不透明的黑盒传来传去。正因为它什么都不能"偷看"，它能做的事就被类型死死框住了。比如

```
f : ∀X. X → X
```

这样的 f，无论内部怎么写，**唯一**能做的就是把输入原样返回（在纯 System F、不含副作用/异常的设定下）——它拿到的 x 是个黑盒，它造不出别的 X 类型的值，也不能凭空变一个，只能还回去。这就是参数性带来的"类型即规约"的威力。

一个易错点：不要把参数化多态和"泛型语法"划等号。Java 泛型里可以 `instanceof` 偷看类型、可以对 `Object` 调方法，那已经破坏了参数性；真正的参数化多态要求"类型信息在运行时被彻底擦除、行为完全不依赖具体类型"。

### T8.2.2 参数性与 Reynolds 抽象定理

**参数性**（parametricity）是把"参数化多态"这个直觉数学化的定理。Reynolds（IFIP '83，"Types, Abstraction and Parametric Polymorphism"）给出 System F 类型的**关系解释**（relational interpretation）：不再把类型解释成"值的集合"，而是解释成"关系"——类型变量 X 解释成任意一个关系 R，箭头类型和 ∀ 类型按固定方式从子关系构造出来。**抽象定理**（abstraction theorem，又称参数性定理）说：

```
每个良类型的项，都与它自身处在"由其类型诱导出的那个关系"之中。
```

给初学者的直觉：这句话翻译成人话是"类型相同的两个（可能不同的）实现，在任何'兼容的关系'下都给出关系对应的结果"。它精确地刻画了"参数化多态函数不能依赖具体类型"这件事——因为它对任意关系 R 都要成立，而 R 可以任意刁钻，函数就没有余地去"偷看"类型的内部结构。Reynolds 提出它最初是为了刻画"数据抽象"：一个模块换一种内部表示（比如栈用数组实现换成用链表实现），只要两种表示之间存在一个恰当的关系，外部观察者就分辨不出差别。这条定理是 T8.4 存在类型/数据抽象在语义上"表示无关"的根据。

要点在于：抽象定理对**每个**良类型项自动成立，无需逐个证明——类型一旦定了，性质就免费附送。这正是下一节"免费定理"的来源。

### T8.2.3 免费定理（free theorems）

Wadler（FPCA '89，"Theorems for free!"）观察到：把 Reynolds 抽象定理用在一个**没有自由变量的多态类型**上，就能"仅从类型签名"读出该类型所有函数都必然满足的一条定理——不看实现、不写证明，定理白送。经典例子：任何类型为"对列表的多态变换"的函数

```
r : ∀X. List X → List X
```

都必然满足：对任意类型 A、B、任意函数 `f : A→B` 和任意列表 `xs : List A`，

```
map f (r xs)  =  r (map f xs)
```

给初学者的直觉：这条等式说"先重排/删减再逐元素映射"和"先逐元素映射再重排/删减"结果一样。为什么白送？因为 r 戴着眼罩（T8.2.1）——它看不见列表元素是什么类型，只能对元素做"搬运、复制、丢弃、重排"这类**与元素类型无关**的操作，绝不可能凭元素的具体值来决定怎么处理。既然它对元素的身份完全无感，那么"先换一层皮（map f）"和"后换一层皮"当然可交换。类型 `∀X. List X → List X` 的每一个居民——reverse、tail、take 3、去偶数位——都自动满足它。

再看两个免费结论帮助建立感觉：类型为 `∀X. X→X` 的函数必是恒等（T8.2.1 已述）；类型为 `∀X. X→X→X` 的函数必是"取第一个或取第二个参数"二者之一（因为它只能返回两个黑盒输入里的一个，别无选择）。

一个易错点：免费定理成立的前提是**纯粹**的参数化多态。一旦语言允许副作用、异常、`seq`（强制求值）、运行时类型反射，眼罩就被摘掉，免费定理会被削弱甚至失效——例如 Haskell 里因为存在 `⊥`（发散/未定义）和 `seq`，`∀X. X→X` 除恒等外还多出"永远发散"这个居民，标准免费定理需要附加条件。这属规范（纯 System F）vs 实现（真实惰性语言）的分账，Wadler 原文即讨论了这一点。

## T8.3 System F 元理论与实现：类型重建不可判定

### T8.3.1 强正规化与逻辑一致性

System F 的头号元理论结论是**强正规化**（strong normalization，Girard 1972）：每个良类型的项，无论按什么顺序归约，都在有限步内到达范式（不存在无限归约序列）。Girard 用**可归约候选**（candidats de réductibilité / reducibility candidates）技术证明了这一点。

给初学者的直觉与推论：强正规化等于说"System F 里写不出死循环"——每个良类型程序都必然停机。这有个立刻的代价：**通用递归/不动点算子 `fix` 在 System F 里是不可类型化的**（否则就能造出不停机的项），T4.3 的 `fix` 在这里没有位置。经由 Curry-Howard 同构（T3.4），System F 对应二阶直觉主义命题逻辑，强正规化对应该逻辑的**一致性**（不能证出假命题）——一个不停机的项会对应一个"假的证明"，正规化保证了这种事不发生。

一个反直觉点：既然写不出死循环、连 `fix` 都没有，System F 到底还能算什么？答案是它的表达力其实极强——所有在二阶算术里可证明为全函数的可计算函数它都能表达（远超原始递归），只是**不能**表达"可能不停机"的一般递归。实用语言（如带 `fix` 或递归定义的 ML/Haskell）为了图灵完备会主动放弃强正规化。

### T8.3.2 类型检查易、类型重建不可判定

这里必须把两个问题分清，否则会得出自相矛盾的印象。

Church 风格（显式类型，即 TAPL Ch.23 和本篇 T8.1 实证所用的形式）的 System F，**类型检查是可判定的、而且直截了当**——所有类型抽象和类型应用都写明了，检查器只需按 T-TAbs/T-TApp 照着核对、做类型代换即可（本篇实证正是这样一个可终止的检查器）。

真正不可判定的是 Curry 风格（隐式类型）的**类型重建**（type reconstruction / full type inference）：给一个**擦掉了所有 Λ 和 [T] 标注**的项，问能否补回标注使它在 System F 里良类型。这个问题由 **Wells（LICS '94；期刊全文 APAL 98, 1999）** 证明**不可判定**，且他证明了 System F 的 **typability（可定型性）与 type checking（Curry 风格类型检查）二者等价且都不可判定**。

```
Church 风格 System F 类型检查        —— 可判定（容易）
Curry 风格 System F 类型重建/可定型  —— 不可判定（Wells 1994）
```

给初学者的直觉：区别在于"标注在不在"。显式版本里编译器只是核对你写好的类型证书，当然能算完；隐式版本要编译器**凭空反推**出所有该在哪里插入类型抽象、每个类型应用该喂什么类型——而"该喂什么类型"可以是任意复杂的多态类型（非谓词性，T8.1.4），搜索空间无界。Wells 的证明把它归约到**半合一**（semi-unification，一阶合一 + 一阶匹配的组合）这个已知不可判定的问题上：类型检查 ← 半合一，可定型 ← 类型检查。

要点与易错点：不要把"System F 类型重建不可判定"误读成"System F 没法用"。实用语言的做法是**要求程序员写少量类型标注**（比如 Haskell 里高秩多态要显式 `forall`），把不可判定的全推断降级为可判定的检查；这正是显式版本容易的那一面在工程上的兑现。

### T8.3.3 与 Hindley-Milner 的分工：可判定的受限片段

System F 不可推断，而 T7 的 Hindley-Milner 完全可推断，二者关系是"同一光谱的两端"。HM 恰好是 System F 的一个**受限片段**：**谓词的**（量化变量只实例化成单态类型）、**前束/秩-1 的**（∀ 只能出现在类型最外层，`∀X̄. τ` 里 τ 不含 ∀）。正是这两条限制把搜索空间收窄到合一可解，换回了可判定的类型推断和主类型（T7.3）。

给初学者的直觉：这是一笔清清楚楚的交易——放弃 System F 的"任意位置、任意嵌套、非谓词"的多态自由，换取"编译器全自动推断、程序员一个标注都不用写"的便利。ML/早期 Haskell 选了 HM 这端（几乎不用标注，但写不出内层 ∀）；需要高秩/非谓词多态时（如某些库设计），语言就得让程序员补标注、退回到"检查而非推断"的 System F 那端。

要点在于把 T7 与 T8 的关系钉死：**T7 = 可推断但受限的多态，T8 = 通用但不可推断的多态**；HM ⊂ System F。理解了这一层，就明白为什么现代语言（Rust 泛型、Haskell 的 `RankNTypes`）总是"默认自动推断、局部要求标注"——它们在这条光谱上按需滑动。

- 锚点（一手承重）：TAPL Ch.23（强正规化的陈述与 Notes、System F 类型重建不可判定的讨论指向 Wells；HM 作为 System F 可判定片段的定位）。MIT Press 2002，核实 2026-07-30。
- 交叉印证（一手）：强正规化——Girard 1972（reducibility candidates 原始技术）。类型重建不可判定——Wells《Typability and Type Checking in System F are Equivalent and Undecidable》LICS '94、期刊全文 Annals of Pure and Applied Logic 98(1–3):111–156 (1999)，经 Web 检索（IEEE Xplore、ScienceDirect、PhilPapers 收录一致）核实 2026-07-30：type checking 经半合一 semi-unification 归约得不可判定，typability 经归约到 type checking 得不可判定，二者等价。

## T8.4 存在类型与数据抽象：∃、ADT/模块、pack/open

### T8.4.1 存在类型 ∃ 的直觉与语义

**存在类型**（existential type）`{∃X, T}`（TAPL Ch.24 记法；也常写 `∃X. T`）是全称类型 ∀ 的对偶。若 `∀X. T` 是"**对所有**类型 X 都能给出一个 T"（生产者视角，被调方承诺通用），那么 `{∃X, T}` 是"**存在某个**类型 X，配上一个 T 类型的东西，但这个 X 具体是谁被藏起来了"（打包一个隐藏了内部表示的包裹）。

给初学者的直觉：存在类型就是"把实现类型封进黑箱"。一个 `{∃X, {a:X, f:X→Nat}}` 类型的值，对外说的是"我内部有某个类型 X，我给你一个 X 类型的初值 a 和一个能把 X 变成 Nat 的函数 f，但**我不告诉你 X 到底是什么**"。使用者只能通过 f 这套接口操作那个 a，永远拿不到、也不能假设 X 的真身。这正是"信息隐藏 / 数据抽象"的类型化身——∀ 让**调用者**自由选类型，∃ 让**实现者**把类型藏起来、只暴露接口。

一个建立联系的要点：∃ 在纯 System F 里其实不必内置，可用 ∀ 编码（TAPL §24.3 的 Church 编码）：

```
{∃X, T}  ≜  ∀Y. (∀X. T → Y) → Y
```

直觉是"要用这个包裹里的东西，你得给我一个'对任意 X 都能处理 T 得出 Y'的续延（continuation），我把藏起来的 X 和内容喂给你的续延"——续延对 X 是全称量化的，所以它同样看不见 X 真身。这条编码把 ∃ 归约到 ∀，说明存在多态并未超出 System F 的表达力，只是换个记法更好用。

### T8.4.2 pack（引入）与 open（消去）

存在类型配两个操作：**pack** 打包（引入 ∃）、**open**（又称 unpack/let）拆包使用（消去 ∃）。

引入规则 T-Pack：把一个具体的"见证类型（witness）S 和一个 `[X↦S]T` 类型的实现"打包，对外冒充成隐藏了 X 的存在类型。TAPL 记法 `pack {*S, t} as {∃X, T}`：

```
   Γ ⊢ t : [X ↦ S] T
   ────────────────────────────────────────   (T-Pack)
   Γ ⊢ pack {*S, t} as {∃X, T} : {∃X, T}
```

消去规则 T-Unpack（open/let）：拆开一个存在包裹，在包内给隐藏类型一个**新的、不透明的**局部名字 X 和内容一个名字 x，然后在这个作用域里用它们算出结果 t₂。TAPL 记法 `let {X, x} = t₁ in t₂`：

```
   Γ ⊢ t₁ : {∃X, T₁}      Γ, X, x:T₁ ⊢ t₂ : T₂
   ──────────────────────────────────────────────   (T-Unpack，要求 X 不自由出现于 T₂)
   Γ ⊢ let {X, x} = t₁ in t₂ : T₂
```

给初学者的直觉：pack 是"装箱并贴上抽象标签"——你心里知道内部用的是 S（比如 Nat），但对外只声明"某个 X"。open 是"拆箱使用"——拆开后你拿到内容 x，但内部类型只以一个**陌生的抽象名 X** 出现，你无从知道它是 Nat，只能用包裹里附带的接口操作它。

那条**副条件"X 不自由出现于结果类型 T₂"**是全节最关键、也最易错的地方：它保证隐藏的类型**不会泄漏到包外**。如果允许 X 出现在 T₂ 里，那么拆包的结果类型就会提到那个本该保密的 X，抽象就漏了。用最小例子体会：你可以在 open 的体内把内部计数器加一、读出一个 Nat 返回（结果类型 Nat，不含 X，合法）；但你**不能**直接把内部那个 X 类型的值 return 出去（结果类型会是 X，违反副条件，被拒），否则外界就拿到了本该封装的表示。

### T8.4.3 存在类型即抽象数据类型（Mitchell-Plotkin）

"存在类型正是抽象数据类型（ADT）/模块的类型"这一等式由 **Mitchell & Plotkin（TOPLAS 10(3):470–502, 1988，"Abstract Types Have Existential Type"；会议版 POPL '85）** 正式建立。一个 ADT 声明"有一个隐藏的表示类型 + 一组作用在其上的操作"，恰好就是一个 `{∃X, {ops…}}` 类型的 pack 值；`open` 对应"打开模块、在其作用域里用它的操作"。

给初学者的直觉与一个模块例子：一个"计数器 ADT"暴露 `{new: X, inc: X→X, get: X→Nat}`，隐藏表示 X。用 Nat 实现时 pack 成

```
counter = pack {*Nat, {new=0, inc=λc:Nat.c+1, get=λc:Nat.c}} as {∃X, {new:X, inc:X→X, get:X→Nat}}
```

换成用记录 `{n:Nat}` 实现，pack 出来的类型**一模一样**——外界代码经 open 只能 `new`、`inc`、`get`，根本分辨不出内部换了表示。这就是数据抽象"表示可替换"的类型级保证，其语义正当性回到 T8.2.2 的参数性/抽象定理（两种表示间存在恰当关系，观察者无法区分）。

要点与关联：这条等式是**模块系统的理论根**——ML 的 module/functor、面向对象里对象封装内部状态、Rust 的 `pub`/私有字段做信息隐藏，追根溯源都是存在类型这一套。要区分它与 ∀：`∀X. X→X` 是"你（调用者）挑类型，我对你挑的都成立"；`{∃X, …}` 是"我（实现者）挑并藏起类型，你只能隔着接口用"。一个是通用性、一个是抽象性，方向恰好相反。

#### 来源与时效（本小主题）
- 锚点（一手承重）：TAPL Ch.24 "Existential Types"：`{∃X,T}` 语法、T-Pack `pack {*S,t} as {∃X,T}`、T-Unpack `let {X,x}=t₁ in t₂`（含"X 不自由于 T₂"副条件）、§24.3 用 ∀ 编码 ∃、存在类型作 ADT。MIT Press 2002，核实 2026-07-30。
- 交叉印证（一手）：Mitchell & Plotkin《Abstract Types Have Existential Type》TOPLAS 10(3):470–502 (1988)，会议版 POPL '85——"具体表示是存在类型的元素、存在类型是数据抽象/信息隐藏的基础"，经 Web 检索（ACM DOI 10.1145/44501.45065、Stanford theory 站原文 PDF、PLS-Lab ADT/Existential 词条）核实 2026-07-30，与 TAPL Ch.24 Notes 一致。
- 冲突/待核：记法差异——TAPL 用 `{∃X,T}`、`pack {*S,t}`、`let {X,x}=…`，Mitchell-Plotkin 原文用二阶演算 SOL 的 `abstype`/`rep` 风格；语义一致，仅记号不同，正文按 TAPL 记法陈述。无实质矛盾。

## T8.5 F 的实现：工程实现要点

### T8.5.1 类型与项的表示：de Bruijn 与代换

TAPL Ch.25（"An ML Implementation of System F"）把前四节的规则落成一个真实类型检查器，头号工程问题是**变量表示**。System F 里现在有**两类**绑定变量——项变量（被 λ 绑定）和类型变量（被 Λ、∀、∃ 绑定），实现时对**两类**都用 **de Bruijn 索引**（无名表示，承 T2.5）以彻底回避 α 换名与捕获问题。

给初学者的直觉：de Bruijn 索引就是"不给变量起名字，只记它指向第几层外的绑定子"。这样 `ΛX. λx:X. x` 和 `ΛY. λy:Y. y` 会有**完全相同**的内部表示，判两个类型是否相等直接结构比较即可，不必先对齐名字。代价是每当把一个类型/项移进或移出一个绑定作用域，就得对里面的索引做**移位**（shifting）以保持它们指对层数——这是 Ch.25 里最琐碎、也最容易写错的部分。类型应用 `(ΛX. t)[S]` 的执行就是"把 S 代入 t 的类型层、同时对跨越绑定的索引移位"。

要点在于：T-TApp 的核心动作 `[X↦T₂]T₁`（类型代换）在实现里就是"类型层的 de Bruijn 代换 + 移位"，与 T7 值层代换同构但作用在类型上。实现一个 System F 检查器，大半工作量在把这套移位/代换写对。

### T8.5.2 类型擦除、无类型语义与 impredicativity 的实现代价

System F 的类型抽象/应用在**运行时不做任何计算**——`ΛX. t` 和 `t [T]` 只是类型检查期的脚手架。因此实现里普遍做**类型擦除**（type erasure）：类型检查通过后，把所有 Λ 和 [T] 抹掉，剩下一个无类型 λ 项去求值。这与参数性（T8.2）互为表里——正因为多态函数不能依赖具体类型，类型信息才可以在运行时安全丢弃。

给初学者的直觉与关联：类型擦除解释了两种真实工程路线的分野。Java/OCaml 走类型擦除路线（泛型在运行时无痕，一份代码跑所有类型，省空间但运行时拿不到类型信息）；而 **Rust/C++ 的单态化（monomorphization）** 走另一条路——为每个实际用到的类型实例各生成一份专用代码（喂 L5-14 R6.1），拿到具体类型、可内联优化，代价是代码膨胀。两者都合法：擦除对应"参数性保证行为与类型无关，故可共用一份"，单态化对应"既然共用合法，那也可以为性能各展开一份"。

一个实现上的坑：非谓词性（T8.1.4）虽不增加运行时开销（擦除后都一样），却让**类型检查**变复杂——因为 ∀X 可实例化成含 ∀ 的类型，类型相等/替换必须能处理任意嵌套的量词。这也是为什么真实语言要么限制到谓词/前束片段（HM，T8.3.3），要么要求显式标注（Haskell `RankNTypes`）。

### T8.5.3 局限与走向：通往 T9 / T10

纯 System F 作为理论内核完备而优雅，但直接当编程语言用有几处不足，恰好各引出后续大主题。它没有**子类型**——无法表达"任何'带某字段的记录'都能用在这"，这催生 **T9 有界量化 F<:**（把 `∀X` 加上界 `∀X<:T`，喂 L5-14 trait bound，点名不展开）。它的量化只作用在"类型"上、不能对"类型到类型的函数（类型算子）"抽象，这催生 **T10 高阶系统 Fω**（引入 kind、类型级函数，点名不展开）。它不可推断（T8.3.2），实用语言要么退回 HM 片段、要么补标注。

给初学者的直觉：把 System F 看成"多态的原子内核"——它把"对类型抽象"这一件事做到极致纯粹，后续系统都是在它上面叠加正交的维度（子类型、类型算子、有界量化），而不是推翻它。理解了 T8 的 ∀/∃/参数性/不可判定这四块，T9、T10 就只是"在同一个内核上再加一层量化的限定词或提升一阶"。

要点与关联收束：本篇是 Part V（多态）承上启下的枢纽——上承 T7 的 HM（可推断片段），本篇给出通用但不可推断的 System F，下启 T9（有界量化）、T10（高阶）；工程上则是 Rust/Haskell/OCaml 泛型与模块系统的共同理论祖型。
