## T1.1 类型系统的作用与本书方法

### T1.1.1 类型系统的定义

TAPL §1.1 给出全书的定纲定义，逐字是：

```
A type system is a tractable syntactic method for proving the absence
of certain program behaviors by classifying phrases according to the
kinds of values they compute.
（类型系统是一种可行的、语法层面的方法，通过按"短语会算出哪一类值"给短语分类，
来证明某些程序行为不会发生。）
```

这句话每个词都承重，拆开看：**语法层面（syntactic）**——只看程序文本结构、不运行程序；**证明不会发生（proving the absence）**——它给的是"这类坏事一定不发生"的保证，而不是"这类好事会发生"；**某些行为（certain behaviors）**——只覆盖一部分错误，不是全部；**可行（tractable）**——判定过程能自动、高效地跑完（通常要求可判定且高效）。

直观地看，类型检查器像一个只读源码就能下结论的门卫，它不关心你程序算得对不对，只保证"你不会把一个整数当函数去调用""不会对字符串做只有数字才有的减法"这类**类型层面无意义**的操作在运行时发生。抓住"语法方法 + 证明坏行为的缺席 + 按值的种类分类"这三点，就抓住了 Pierce 给类型系统下的全部定义。

这里的"证明缺席"是对**所有**可能输入一次性成立的（因为是对程序结构做的证明），这跟测试只能覆盖跑到的用例有本质区别——这也是类型系统作为"轻量形式方法"价值的来源（下一节）。

### T1.1.2 类型即轻量形式方法

TAPL 反复强调的一个定位是，类型系统是**轻量级的形式方法（lightweight formal methods）**。"形式方法"指用严格数学去证明程序性质；"轻量"指它不像完整程序验证那样要人写规约、手写证明，而是**自动、无需程序员额外证明**就能给出保证——你只要写下类型注解（有时连注解都能推断掉），编译器就替你把证明做了。

直观地看，把"程序正确性保证"想成一条光谱。一端是"什么都不证"（纯动态语言，错了运行时才知道），另一端是"用 Coq/Isabelle 手工证明程序完全正确"（L6-02 V11，极重、极强）。类型系统落在靠自动化的这一端——它给的保证比"什么都不证"强得多、又比全验证便宜得多（几乎零人工成本、每次编译自动重跑），这就是"轻量"的含金量。正因为轻量、能天天用，它成了业界唯一被大规模采用的形式方法。

代价就是它只能证"某些"性质（T1.1.4 的保守性）：换来自动化和低成本，就得放弃"证明任意复杂的正确性"。这条取舍是理解类型系统一切设计的总纲。

### T1.1.3 静态检查带来的好处

TAPL §1.1 列了类型系统在工程上的几项主要收益，可归纳为：**尽早发现错误（error detection）**——很多 bug 在编译期就被逮住，不必等运行；**抽象与接口（abstraction）**——类型是模块间的契约，是划分接口、支撑大型程序结构的语言；**文档作用（documentation）**——类型注解是永远不会过期的、机器校验过的文档；**语言安全（safety）**——配合运行时，类型帮助排除会破坏抽象的非法操作；**效率（efficiency）**——早期类型系统正是为让编译器生成高效代码（省去运行时标签检查）而生。

直观地看，这几条里最该先记住的是"尽早发现"。同一个 bug，编译期被类型检查器指着行号拦下，几秒就改；漏到运行时要复现、看栈、倒查坏值；漏到线上可能是用户投诉才暴露，修复成本差几个数量级。类型系统的核心价值就是把一整类错误从"运行时才炸"提前到"编译期就拦"。

"文档"这一条对初学者也很实在：函数签名 `f : Int -> Bool` 本身就说明了怎么用它，而且编译器保证这份说明和实现一致——普通注释会写错、会过时，类型不会。这条与 L4-06 工程质量观里"静态检查 + 类型作强制文档"是同一件事在理论侧的根。

### T1.1.4 保守性与限度：只证坏行为的缺席

类型系统是**保守的（conservative）**——它宁可错杀也不放过：有些运行起来其实完全没问题的程序，会因为通不过类型检查而被拒绝。原因回到 T1.1.1 的定义，类型检查只看语法结构、且要可行（可判定高效），而"这段程序运行时会不会真的出错"在图灵完备语言里是不可判定的（Rice 定理，见 L6-02 V1）。既然无法精确判定，又要求"绝不漏报坏程序"，就只能牺牲一部分好程序。


```
if <一个运行时恒为 true 的复杂条件> then 5 else (true + 1)
```

人能看出 else 分支永远不会执行、程序其实安全，但类型检查器判不出那个条件恒真，只能看到 `true + 1` 这个类型错误的子式，于是拒绝整个程序。这就是"错杀好程序"的典型。

由此引出必须分清的两句话。其一，类型系统证明的是**坏行为的缺席**，不是好行为的存在——它保证"不会把整数当函数调"，但**不**保证"你的排序函数真的排对了"（那是规约与测试、乃至全验证的职责）。其二，著名的口号 **"well-typed programs cannot go wrong"** 出自 **Milner 1978**（不是 Pierce 原创，Pierce 引用它），其中 "go wrong" 有精确含义——指程序求值到一个**卡住的状态（stuck）**，即不是最终值、又没有任何求值规则能继续（T1.4.2 展开）。类型安全定理保证的正是"良类型 ⇒ 永不卡住"，而非"永不报错""结果正确"。

这里要给初学者提个醒，不要把"类型检查通过"理解成"程序没 bug"。它只排除了类型层面的一类错误；逻辑错、死循环、算错答案，类型系统一概不管。理解了保守性和"只证缺席"，才不会对类型系统抱过高或过低的期待。

### T1.1.5 本书方法：操作语义 + 归纳证明

TAPL 研究每个类型系统的固定套路是三步走：先用**归纳定义**写下语言的语法（term 的文法）；再用**操作语义**（一组求值规则，T1.4）定义程序怎么一步步算；最后陈述并用**归纳法**（T1.3）证明该类型系统的**类型安全（type safety / soundness）**，而安全性被拆成两条定理：

```
Safety = Progress + Preservation
（安全性 = 进展 + 保持）
```

进展（Progress）说"良类型的项要么已是值、要么还能再算一步"（即不会卡住），保持（Preservation）说"良类型的项算一步后类型不变"。两条合起来就得到"良类型的项永远不会卡住"。

那么，为什么全书选操作语义而不用指称/公理语义？Pierce 的理由是操作语义**数学包袱最轻、又能覆盖到复杂语言特性**（不需要指称语义那套域理论 domain theory）。对初学者这也最友好——操作语义就是"照着规则一步步算"，几乎可以直接翻译成一个解释器（本报告 T1.4 附了可跑的 Python 求值器）。

后面 T2–T10 每引入一个新语言特性，都会重走"语法→求值规则→重证 Progress/Preservation"这条路。Progress+Preservation 的具体陈述与证明骨架属大主题 T3，此处点名不展开；它也是 L5-14 RustBelt 机器化类型安全证明的祖型。

## T1.2 数学预备

### T1.2.1 集合、关系与函数

TAPL Ch.2 先把讨论要用的最基本对象定死。**集合**用朴素（naive）集合论即可，元素、子集、幂集、笛卡尔积照常用。**关系**是笛卡尔积的子集：一个 A 与 B 之间的二元关系 R 就是

```
R ⊆ A × B
```

写 `a R b` 或 `(a, b) ∈ R` 表示 a 与 b 有关系。**函数** f 是一种特殊关系（每个输入至多对一个输出），A→B 记全函数（每个输入都有像），偏函数（partial function）允许有些输入无定义。

直观地看，本课里"求值"和"定型"这两件核心的事，最后都被建模成**关系**，而不是普通函数。为什么不是函数？因为求值可能"卡住"（无输出）或在非确定语义下"多个结果"，定型关系 `Γ ⊢ t : T` 也是一个三者之间的关系。先接受"关系比函数更基本、更宽松"这一点，后面看到 `t → t'`（求值一步）和 `t : T`（t 有类型 T）时才不会别扭。

还有个容易踩的坑，关系不要求"每个输入都有像"，也不要求"至多一个像"。求值关系 `→` 恰恰在值上没有像（值不能再算），在卡住项上也没有像——这正是我们要用类型系统去排除的情形。

### T1.2.2 关系的性质与闭包

关系上几个性质要能张口就来：**自反（reflexive）** `∀a. a R a`、**对称（symmetric）** `a R b ⇒ b R a`、**传递（transitive）** `a R b ∧ b R c ⇒ a R c`。由一个关系可以"补全"成满足某性质的最小关系，叫**闭包（closure）**。全书最常用的是求值关系的**自反传递闭包**，记作 `→*`：

```
→*  =  满足「自反 + 传递」且包含 → 的最小关系
```

于是 `t →* t'` 读作"t 经零步或多步求值到 t'"。

直观地看，单步关系 `→` 只描述"算一步"，但我们真正关心的是"算很多步直到停"，这就要把 `→` 的传递自反闭包取出来。"最小"很关键——闭包是"恰好为了满足该性质而补进去的那些对，一个不多"，比如自反传递闭包里 `t →* t` 永远成立（自反补的），`t →* t''`（若 `t → t' → t''`）也成立（传递补的），但不会平白多出无关的对。

本机可实证"取传递闭包"这件事。用 Python 对一个小关系反复合成直到不再增长（Warshall 式）：

```
$ python3 - <<'PY'      # 基线 Py3.11.15 @2026-07-30
R = {(1,2),(2,3),(3,4)}                 # 单步关系
def trans_closure(R):
    C = set(R); changed = True
    while changed:
        changed = False
        new = {(a,d) for (a,b) in C for (c,d) in C if b==c} - C
        if new: C |= new; changed = True
    return C
def refl_trans_closure(R, dom):
    return trans_closure(R) | {(x,x) for x in dom}
print("→*  =", sorted(refl_trans_closure(R, {1,2,3,4})))
PY
→*  = [(1, 1), (1, 2), (1, 3), (1, 4), (2, 2), (2, 3), (2, 4), (3, 3), (3, 4), (4, 4)]
```

输出里 `(1,4)` 是传递补进来的（1→2→3→4），`(4,4)` 等是自反补进来的——这正是 `→*` 的含义：把"零步或多步可达"全部显式列出。

### T1.2.3 归纳定义与推理规则

本课几乎所有对象（项的集合、求值关系、定型关系）都是**归纳定义（inductive definition）**的——用一组**推理规则（inference rules）**给出：若干条**公理**（无前提，直接断言某元素在集合里）加若干条**推导规则**（前提成立则结论成立），被定义的集合是"满足所有规则的**最小**集合"。推理规则的标准写法是一条横线，上前提下结论：

```
（公理，无前提）                    前提1   前提2   …
------------                      ----------------------
   结论                                   结论
```

以布尔+算术项集合 T 为例（TAPL §3.2），它是被下面这组规则封闭的最小集合：

```
true ∈ T          false ∈ T          0 ∈ T

   t1 ∈ T                    t1 ∈ T
------------            ---------------
succ t1 ∈ T             iszero t1 ∈ T

  t1 ∈ T   t2 ∈ T   t3 ∈ T
------------------------------
 if t1 then t2 else t3 ∈ T
```

直观地看，"最小集合"是这里最容易忽略却最关键的词。它意味着 T 里**只有**能由这些规则一步步搭出来的东西，没有别的（比如无穷大的项、凭空冒出来的项都不在 T 里）。正因为"只有搭出来的"，我们才能用归纳法证明"T 里所有元素都具有性质 P"——只要证每条规则都保持 P（T1.3）。归纳定义与归纳证明是一枚硬币的两面：这样定义的集合，天生配一个对应的归纳原理。

公理和推导规则怎么区分？看横线上有没有前提——没有前提（横线上空）的是公理（如 `true ∈ T`），是搭积木的"地基块"；有前提的是推导规则（如由 `t1 ∈ T` 得 `succ t1 ∈ T`），是"往上垒"的规则。任何一个项都对应一棵由这些规则拼成的**推导树（derivation）**，这棵树正是 T1.3.3 规则归纳要归纳的对象。

## T1.3 归纳法

### T1.3.1 自然数归纳与良基归纳

最熟悉的**数学归纳法**是对自然数的：要证 `∀n. P(n)`，证基例 `P(0)` 和归纳步 `P(k) ⇒ P(k+1)`（或强归纳：`(∀m<n. P(m)) ⇒ P(n)`）。TAPL Ch.2 把它推广成最一般的形式——**良基归纳（well-founded induction）**：在任何**良基关系**（well-founded relation，即不存在无穷下降链 `… ≺ a2 ≺ a1 ≺ a0` 的关系 `≺`）上都能做归纳。要证性质 P 对论域中所有元素成立，只需证：

```
对每个 a：  ( 对所有 b ≺ a 都有 P(b) )  ⇒  P(a)
```

一旦如此，则 `∀a. P(a)`。

直观地看，良基归纳是"所有归纳法的母版"，自然数归纳、结构归纳、规则归纳都是它的特例——只是把 `≺` 分别取成"小于""是子项""是子推导"。它成立的直觉理由是"没有无穷下降"：假如有个 a 使 P(a) 假，就能从它不断找到更小的反例，无穷降下去，与良基矛盾。所以只要论域没有"无底洞"，把每个元素都还原到比它小的元素上去证，就能覆盖全体。

这里有个初学者常绊倒的点，归纳步里那个假设"对所有 b ≺ a 都有 P(b)"叫**归纳假设（IH）**，它假设的是"所有更小的"而不只是"前一个"——这正是强归纳/良基归纳比朴素归纳更好用的地方（证 P(a) 时可以随便调用任何更小对象的 P）。另外，良基是关键前提：在实数或整数的 `<` 上做不了归纳（能无穷下降），所以要挑对关系。

### T1.3.2 结构归纳

**结构归纳（structural induction）**是良基归纳在"归纳定义的数据结构"上的特例，`≺` 取成"是直接子项"。要证归纳定义的项集合上性质 P 对所有项成立，就**按语法构造分情形**：对每条构造规则，假设 P 对各直接子项成立（IH），证 P 对由它们构造出的项也成立。对布尔+算术项：

```
证 P(true)、P(false)、P(0)                       （基例，对应公理）
设 P(t1) 证 P(succ t1)、P(iszero t1)              （归纳步）
设 P(t1)、P(t2)、P(t3) 证 P(if t1 then t2 else t3) （归纳步）
```

覆盖所有构造情形后即得 `∀t∈T. P(t)`。

直观地看，结构归纳就是"顺着你当初造这个数据的方式反过来证"。因为项都是从公理块出发、用规则一层层搭起来的（T1.2.3），你只要保证"地基块满足 P"且"每种搭法都保持 P"，那么无论怎么搭出来的项都满足 P。它和程序里对递归数据类型写递归函数是同构的——递归函数的每个分支，正对应归纳证明的每种情形。

看一个最小例子，证"每个项里 `true`/`false`/`0` 这类常量的个数 ≥ 1"。基例 3 个常量各含 1 个，成立；归纳步如 `succ t1`，其常量数 = t1 的常量数 ≥ 1（由 IH），仍成立。整套证明就是照着语法规则走一遍。要当心的是，分情形必须**穷尽所有构造规则**，漏一种（比如忘了 `if`）证明就不成立。

### T1.3.3 规则归纳与对推导的归纳

当被归纳的对象不是"项"而是"一条推导/一个关系的成员"时，用的是**规则归纳（rule induction）**，TAPL 里称之为**对推导的归纳（induction on derivations）**。求值关系 `t → t'`、定型关系 `Γ ⊢ t : T` 都是用推理规则归纳定义的（T1.2.3），要证"凡满足该关系的都具有性质 P"，就对**推出它的那条规则**分情形，并对每条规则的**前提对应的子推导**用归纳假设。骨架是：

```
对定义该关系的每条规则
      J1  …  Jn
     ------------  (规则名)
          J
证：( P 对每个前提 J1…Jn 成立 )  ⇒  P 对结论 J 成立
```

对所有规则都证毕，即得 P 对该关系的所有成员成立。

直观地看，结构归纳归纳的是"项这棵语法树"，规则归纳归纳的是"推导这棵证明树"——两者形状很像，但归纳的对象不同。凡结论形如"如果 `t → t'`（或 `t : T`），那么……"的命题，几乎都用规则归纳：因为 `t → t'` 这个事实本身是靠某条求值规则得出的，你就对"最后用的是哪条规则"分情形。TAPL 后面证 Preservation（若 `Γ⊢t:T` 且 `t→t'` 则 `Γ⊢t':T`）用的正是对求值推导的规则归纳。

一个必须显式标注的术语分歧：**"规则归纳"这个名字来自 Winskel**（其书把它作为一等的命名原理系统讲），而 **Pierce/TAPL 更常说"对推导的归纳（induction on derivations）"**，Harper PFPL 则统一叫 **rule induction**。三者**指的是同一件事**——都是"对生成该关系成员的推导做良基归纳"，只是叫法不同，初学者遇到任一名字都应认得。区分它与结构归纳的判据：看你归纳的是数据（项）还是判断（derivation/关系成员）。

## T1.4 三种语义风格

### T1.4.1 三种语义风格总览

要说清"一个程序是什么意思"，TAPL §3.4 列出三条主流路线：**操作语义（operational）**——把语言的意义定义成一台**抽象机**的行为，项的意义就是这台机器从它出发算到的最终状态；**指称语义（denotational）**——把每个项**翻译（映射）成一个数学对象**（如一个数、一个函数），项的意义就是这个"denotation"；**公理语义（axiomatic）**——直接把关于程序的**逻辑断言/定律本身**当作语言的定义，项的意义就是"关于它能证明出什么"。

直观地看，同一个程序 `1+2`，三种风格分别这样回答"它是什么意思"。操作语义说"它是一个会一步步算成 `3` 的过程"（关注**怎么算**）；指称语义说"它就是数学里的那个数 3"（关注**是什么数学对象**）；公理语义说"它是一个满足'算完后结果等于 3'这条性质的东西"（关注**能断言什么**）。三者不是对错之分，而是三种视角，各有擅长的场合。

Pierce 明确表态并全书贯彻：**操作语义为主**。理由是它数学包袱最轻、又能扩展到很复杂的语言特性（并发、异常、可变状态等），而指称语义要背上域理论、公理语义在复杂特性上不易铺开。所以下面 T1.4.2–T1.4.3 把操作语义讲细，T1.4.4–T1.4.5 对另两种作定位介绍。

### T1.4.2 小步操作语义

**小步操作语义（small-step / structural operational semantics, SOS）**用一个**单步求值关系** `t → t'` 描述"项 t 一次原子计算后变成 t'"，程序的运行就是反复走单步直到停下：`t →* t'`（`→*` 是单步的自反传递闭包，T1.2.2）。它由一组推理规则定义。以布尔条件为例（TAPL Ch.3）：

```
if true  then t2 else t3  →  t2                         (E-IfTrue)

if false then t2 else t3  →  t3                         (E-IfFalse)

            t1 → t1'
--------------------------------------------            (E-If)
if t1 then t2 else t3  →  if t1' then t2 else t3
```

前两条是"计算规则"（真正干活），第三条是"同余/一致性规则"（指定先算哪个子式，这里是先把条件 t1 算出真假）。

配套要建立几个关键概念。**值（value）** 是"算完了、不能再走单步"的合法结果（如 `true`、`false`、数值 `0`/`succ 0`/…）。**范式（normal form）** 指任何"没有单步可走"的项。**卡住（stuck）** 指一个项**既不是值、又是范式**——它停下来了却不是个合法结果，对应运行时类型错误。三者关系是：

```
值 ⊆ 范式；  卡住项 = 范式 \ 值（即：是范式但不是值）
```

直观地看，小步语义就是把"程序运行"拆成一格一格的慢动作，每次只推进最小的一步，好处是能精确刻画"中间过程"——尤其对并发、异常这种"半路发生的事"必不可少。"卡住"是本课的灵魂概念：`succ true`（对布尔取后继）就是卡住项——它不是值，又没有任何求值规则能处理它，于是运行到这就"死"在半路。类型系统的全部目标（T1.1.5 的 Progress）就是保证良类型的项**永不卡住**。

本机可跑一个忠实实现上述规则的小步求值器（含 succ/pred/iszero/if），观察正常项算到值、非法项卡住：

```
$ python3 eval.py       # 基线 Py3.11.15 @2026-07-30；规则同 TAPL Ch.3
t1 small: ('value', '0')          | big: 0
t2 small: ('stuck', 'true')       | big: ('STUCK', ('succ', 'true'))
t3 small: ('stuck', '0')          | big: ('STUCK', ('if', '0', 'true', 'false'))
# t1 = if iszero(pred(succ 0)) then 0 else succ 0   → 值 0（良行为）
# t2 = succ true                                     → 卡在 true（succ 施于非数值）
# t3 = if 0 then true else false                     → 卡在 0（条件非布尔）
```

t2、t3 停下来却不是值，这就是"卡住"的实机形态；它们正是类型检查该拒绝的项。

### T1.4.3 大步操作语义

**大步操作语义（big-step / natural semantics）**换一种记法，用**求值到值**的关系 `t ⇓ v` 直接说"项 t 最终算出值 v"，不描述中间每一步。它同样由推理规则定义，但每条规则的前提是"各子式各自算到自己的值"，结论是"整个式子算到最终值"。条件式的大步规则：

```
   t1 ⇓ true      t2 ⇓ v2
-----------------------------           (B-IfTrue)
 if t1 then t2 else t3  ⇓  v2

   t1 ⇓ false     t3 ⇓ v3
-----------------------------           (B-IfFalse)
 if t1 then t2 else t3  ⇓  v3
```

直观地看，小步像"逐格慢放整段计算过程"，大步像"直接给出输入到最终结果的对应关系"。大步更贴近怎么写一个递归解释器——"求值 if：先求条件的值，再据真假求相应分支的值"几乎是照着 `B-IfTrue/B-IfFalse` 直译。所以写解释器、讲"程序最终算成啥"时大步更省事。

两者各有短板，要分场合。大步的软肋是**分不清"卡住"和"死循环"**：这两种情况在大步里都表现为"推不出任何 `t ⇓ v`"（没有值），无法区分"停下但非法"与"永不停"；小步能区分（卡住 = 停在非值范式，死循环 = 永远还能走一步）。这正是 TAPL 讲类型安全（要精确刻画"卡住"）时选小步的原因。上一节的 Python 输出里，同样的 t2/t3，小步报 `stuck`（明确指出停在哪个非值项），大步只能报 `STUCK`（推不出值），直观展示了这一差别。

不要以为大步、小步是两种"不同的语义"给出不同答案。在良好定义的确定性语言里，对能正常终止的项两者**结果一致**（可证 `t ⇓ v ⟺ t →* v` 且 v 是值）；它们只是同一套意义的两种描述粒度。

### T1.4.4 指称语义

**指称语义（denotational semantics）**给语言配一族**语义域（semantic domains）**（数学对象的集合，如整数集、从域到域的连续函数空间），再定义一个**解释函数 ⟦·⟧** 把每个项映射到域中一个元素，这个元素就是项的"意义（denotation）"。它的招牌性质是**组合性（compositionality）**——复合式的意义只由其子式的意义决定：

```
⟦ t1 op t2 ⟧  =  F( ⟦t1⟧ , ⟦t2⟧ )      （某个只依赖子式意义的语义函数 F）
```

直观地看，指称语义追求"程序 = 一个不依赖任何机器、任何执行过程的纯数学对象"。比如把命令式程序 `while` 循环解释成"状态到状态的一个（偏）函数"。它的强项是**支持等式推理**：两段代码只要 denotation 相同就可互相替换（这对编译器优化、程序等价性证明很有力），且组合性让"整体意义由局部意义拼出"。

一旦语言里有递归/循环/自引用，denotation 就不能天真地当普通集合函数，要靠**域理论（domain theory）**——完全偏序、最小不动点、连续函数那一套（Scott-Strachey 传统）来给"递归定义的意义"一个良定的数学解。这层机械较重，正是 TAPL 为保持"轻量"而**不采用**它、只在 §3.4 提及的原因。初学者此处知道"它把程序看成数学对象、讲究组合性、处理递归要域理论"即可，不必深入。

### T1.4.5 公理语义（通向 Hoare 逻辑的桥）

**公理语义（axiomatic semantics）**不另造抽象机也不映射到数学域，而是**把对程序成立的逻辑断言（及其推理规则）直接当作语言的定义**——一个程序的意义，就是"关于它能证明出哪些性质"。其载体是 **Hoare 三元组**：

```
{ P }  C  { Q }
（前条件 P 成立时执行命令 C，若 C 终止，则终止后后条件 Q 成立）
```

配一组随语法结构给出的推理规则（赋值、序列、条件、循环、consequence），程序验证就是用这些规则推出想要的三元组。

直观地看，前三种问"程序**算出什么**"，公理语义问"程序**保证什么性质**"。它天生是为"证明程序正确"服务的——你先写下想要的规约（前/后条件），再用规则一步步证明程序满足它。上面的三元组是**部分正确性（partial correctness）**：只承诺"若终止则后条件成立"，不保证一定终止；要额外证终止（循环变式 / ranking function）才升级为**全部正确性（total correctness）**。

这一节按大主题定位**点到即止**：公理语义 = Hoare 逻辑，是**通向 L6-02 程序分析与形式验证（V9 演绎验证：Hoare 逻辑与最弱前条件 WP）的桥**。此处只需记住三件事——它以断言/规则为语义、载体是 `{P} C {Q}`、分部分/全部正确性；规则细节（赋值公理、循环不变式、WP 演算）留到 L6-02。

### T1.4.6 三种风格对比

三种风格回答的是同一问题的不同切面，横向对照如下：

```
风格        意义是什么             招牌工具/概念         最擅长
操作语义    抽象机的执行行为       求值关系 →、⇓        实现解释器、证类型安全、复杂特性(并发/异常)
指称语义    映射到的数学对象       解释函数 ⟦·⟧、域理论  程序等价、组合性推理、编译优化正确性
公理语义    能证明出的逻辑断言     Hoare 三元组 {P}C{Q}  程序验证、规约驱动的正确性证明
```

直观地看，不必纠结"哪个才对"——它们是同一意义的三种镜子，理想情况下应彼此**一致（等价）**（例如可证某语言的操作语义与其指称语义给出相同的程序等价关系，这类结果叫 adequacy/full abstraction）。选哪面镜子看目的：要写解释器、要证"不卡住"就用操作；要做等式化简、证两段代码等价就用指称；要证"程序满足规约"就用公理。

TAPL 因"轻、可扩展、贴近实现"而全程用操作语义（且以小步为主来精确刻画卡住），这解释了为什么从 T2 起你看到的每个语言都是先给一堆 `→` 求值规则。指称/公理在本课基本只在这里露一面——指称是理论工具箱里的另一大件，公理则在 L6-02 作为验证半场的主角重新登场。
