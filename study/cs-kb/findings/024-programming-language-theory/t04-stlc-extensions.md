## T4.1 基本扩展与派生形式

### T4.1.1 基本类型与"外部/内部语言"的派生形式思想

TAPL 扩展 STLC 的第一步是引入若干**基本类型**（base types，§11.1）——如 Bool、Nat，或干脆一个不加解释的原子类型 A——它们没有自己的引入/消去规则，只作为"给函数类型当零件"的最小材料。真正贯穿本章的方法论是**派生形式**（derived form，又称语法糖 syntactic sugar）：把一个新构造定义成"已有构造的缩写"，于是它不需要自己的类型规则和求值规则，安全性自动继承。

TAPL 把这套做法讲成"外部语言 → 内部语言"的翻译（§11.3）。程序员写在**外部语言**里的糖，在进入类型检查/求值前先被一个**脱糖**（desugaring）函数 e 机械地翻译成**内部语言**里的核心项。举例来说，序列化 t₁;t₂（先算 t₁、丢弃结果、再算 t₂）根本不必新增语义，只要定义

t₁ ; t₂　　≝　　(λx : Unit. t₂) t₁　　（其中 x 不在 t₂ 中自由出现）

初学者要抓住的直觉是"糖不改变语言的表达力，只改变书写的舒适度"。既然 t₁;t₂ 展开后就是一个普通的应用，它的类型、它怎么求值、它安不安全，全都由已经证过的应用规则决定——这就是派生形式最大的好处：**加特性不加证明负担**。一个常见误解是把所有扩展都当成糖；下面会看到，积、和、引用、异常大多是**真扩展**（要自己的规则），只有序列化、通配符、（可选地）ascription 和 let 能做成纯粹的糖。判据很简单：如果新构造能被"已有构造 + 已有规则"忠实模拟，它就是糖；否则就得老老实实加规则、补证明。

### T4.1.2 Unit 类型

**Unit 类型**（§11.2）是只有唯一一个值 unit 的类型，写作 Unit，其唯一居民（inhabitant）是常量 unit。类型规则平凡

Γ ⊢ unit : Unit　　(T-Unit)

它没有消去规则（拿到一个 Unit 值也问不出任何信息，因为它只有一种取值）。

Unit 的用处不在"算什么"，而在"占位"。它对应 C 里的 void、ML 里的 unit、Rust 里的 ()：当一个表达式是为了**副作用**而算、其返回值无意义时，就让它返回 Unit。序列化 t₁;t₂ 正是要求 t₁ 的类型必须是 Unit（"你既然被丢弃，就不该带有意义的结果"），这既是类型上的自然约束，也是脱糖式 (λx:Unit.t₂)t₁ 能成立的前提。初学者容易把 Unit 和空类型（没有任何值的类型，后面 T4.5 的 error 会触及）搞混：Unit 恰有一个值，空类型一个值都没有——一个是"信息量为零"，一个是"根本到不了"。

### T4.1.3 序列化与通配符

**序列化**（sequencing）t₁;t₂ 表示"先求值 t₁（其类型须为 Unit），丢弃它，再求值 t₂，整体取 t₂ 的值和类型"。**通配符**（wildcard）_ 是"我不打算用这个绑定的变量"的记法，λ_:T.t₂ 意为"接受一个 T 类型的参数但不用它"。TAPL 把两者都作为派生形式给出（§11.3）

t₁ ; t₂　　≝　　(λx : Unit. t₂) t₁　　（x 不在 t₂ 中自由）

λ _ : T. t　　≝　　λx : T. t　　（x 不在 t 中自由）

也就是说，序列化和通配符都不是新语义，只是"不起名字的 λ 抽象"的两种便利写法。

理解要点是：序列化之所以能用应用来编码，靠的正是**求值顺序**——在值调用（call-by-value）语义里，要先把实参 t₁ 求成值才能做 β 归约，这就"顺手"实现了"t₁ 先算完"。如果换成惰性求值，这个脱糖就不对了。这里也顺带回答了初学者常问的"为什么序列化要求左边是 Unit"：不是语法洁癖，而是脱糖后 x 的类型标注只能填一个类型，填 Unit 最自然，同时也表达了"左边只为副作用"的设计意图。TAPL 也提醒：把糖直接展开会让类型错误信息变得难懂（错误指向脱糖后的 λ 而非源码的 ;），所以真实编译器往往仍把糖当"准原生"来报错——这是"规范上是糖、实现上给特殊待遇"的典型分账。

### T4.1.4 Ascription（类型标注）

**Ascription**（§11.4）写作 t as T，含义是"断言 t 的类型是 T"。类型规则要求 t 确实能定型为 T，求值时标注在值上直接脱落

Γ ⊢ t₁ : T　　⟹　　Γ ⊢ (t₁ as T) : T　　(T-Ascribe)

v₁ as T → v₁　　(E-Ascribe)

TAPL 指出它也能写成派生形式 (t as T) ≝ (λx:T. x) t。

Ascription 的三个实际用途值得初学者记住：一是**文档化**，在复杂表达式旁写明"我认为这里是 T"，让读者和类型检查器都受益；二是**约束推断**，当一个项本可有多种类型（例如后面 T4.2 的 inl、T4.5 的 error）时，用 as 把它钉死到想要的那个；三是**抽象**，把一个类型"看窄"（在有子类型的系统里，t as T 可把 t 向上转成超类型，见本课 T5）。易错点：as 只做**静态检查 + 运行时脱落**，它不是类型转换（cast），不会在运行时改变值的表示，更不会做任何检查性的强转——"as 通过"纯粹意味着"编译器同意这个类型"。

### T4.1.5 Let 绑定

**Let 绑定**（§11.5）let x = t₁ in t₂ 表示"把 t₁ 的值绑定到 x，然后在 t₂ 里用 x"。类型规则和求值规则为

Γ ⊢ t₁ : T₁　　Γ, x : T₁ ⊢ t₂ : T₂　　⟹　　Γ ⊢ (let x = t₁ in t₂) : T₂　　(T-Let)

let x = v₁ in t₂ → [x ↦ v₁] t₂　　(E-LetV)

t₁ → t₁′　　⟹　　let x = t₁ in t₂ → let x = t₁′ in t₂　　(E-Let)

即先把 t₁ 求成值 v₁，再把 v₁ 代入 t₂。

let 看起来又能写成糖 (let x=t₁ in t₂) ≝ (λx:T₁. t₂) t₁，但这里藏着一个本课后续（T7 类型重建）会正面处理的**真实分歧**：脱糖式需要在 λ 上写出 x 的类型标注 T₁，而在支持**类型推断**的系统（如 Hindley-Milner）里，t₁ 的类型本应由系统推出、不该要求人写。更关键的是，HM 的 **let-多态** 让 let 具有 λ 应用不具备的泛化能力（同一个 x 在 t₂ 里可用于多个不同类型），此时 let 就**不能**再当作 (λx.t₂)t₁ 的糖，必须原生。所以 TAPL 在纯 STLC 语境下说"let 可作派生形式"，而 PFPL 直接把 let（定义/绑定）当原生构造给规则——这不是矛盾，而是"在哪个系统里谈"的口径差异，正文两边都记，落点见 T7。初学者先记住结论：**在本大主题（无推断、无多态）里 let 是糖；一旦进入 T7 的 let-多态，它就变成原生构造**。

### T4.1.6 积类型与序对

**积类型**（product type）T₁ × T₂ 是"一对值"的类型，其引入是序对 {t₁, t₂}，消去是两个投影 t.1、t.2（§11.6）。规则为

Γ ⊢ t₁ : T₁　　Γ ⊢ t₂ : T₂　　⟹　　Γ ⊢ {t₁, t₂} : T₁ × T₂　　(T-Pair)

Γ ⊢ t : T₁ × T₂　　⟹　　Γ ⊢ t.1 : T₁　　(T-Proj1)

Γ ⊢ t : T₁ × T₂　　⟹　　Γ ⊢ t.2 : T₂　　(T-Proj2)

求值规则让投影落到序对上时取出对应分量

{v₁, v₂}.1 → v₁　　(E-PairBeta1)

{v₁, v₂}.2 → v₂　　(E-PairBeta2)

外加把求值钻进序对分量与投影对象的同余规则（E-Pair1/E-Pair2/E-Proj）。

积类型是初学者最好上手的扩展，因为它就是数学上的笛卡尔积、编程里的"结构体/元组"。要抓住的机制模式是**引入-消去配对**：{·,·} 把两个值"打包"进积类型（引入），t.i 把它们"拆开"（消去），而 E-PairBeta 规则正是"消去作用在引入结果上时该化简成什么"——这是所有类型构造子都遵循的统一节奏（函数是 λ 引入、应用消去；后面和类型是 inl/inr 引入、case 消去）。看穿这个模式，本章后面的条目就都是"同一个套路换个构造子"。易错点：投影 t.1 里的下标 1 是**语法的一部分**（第一投影这个操作），不是一个可计算的数——不能写 t.n 让 n 在运行时变。

### T4.1.7 元组

**元组**（tuple，§11.7）是积类型从"二元"到"n 元"的直接推广：类型 {T_i \| i ∈ 1..n}，值 {t_i \| i ∈ 1..n}，投影 t.i 取第 i 个分量。规则是积类型规则的"带下标版本"

Γ ⊢ t.i : T_i　　（当 t : {T_j \| j∈1..n} 且 1 ≤ i ≤ n）　　(T-Proj)

{v_i \| i∈1..n}.j → v_j　　(E-ProjTuple)

元组就是"任意长度的序对"，对应大多数语言里的定长元组（Python 的 tuple、Rust 的 (a, b, c)）。它和序对不是两种独立机制——二元元组 {t₁, t₂} 就是序对；TAPL 先讲序对是为了把引入-消去的模式讲清楚，再用元组说明"同样的规则套一层下标就推广到 n 元"。初学者要注意元组的**下标从 1 开始**（TAPL 约定），且元组的分量靠**位置**区分——第 3 个分量是什么，只能靠"数到第三个"。这正是下一条记录要改进的地方：用名字代替位置。

### T4.1.8 记录

**记录**（record，§11.8）给积的每个分量配一个**标签**（label）：类型 {l_i : T_i \| i∈1..n}，值 {l_i = t_i \| i∈1..n}，用标签而非位置来投影 t.l。规则为

Γ ⊢ t.l_j : T_j　　（当 t : {l_i : T_i \| i∈1..n}）　　(T-Proj)

{l_i = v_i \| i∈1..n}.l_j → v_j　　(E-ProjRcd)

记录就是"带字段名的结构体"，对应 C 的 struct、ML 的 record、Rust 的具名字段结构体。它相对元组的进步在于**可读性与稳健性**：按名字 point 比按位置数更不易错，字段加减也不会像元组那样打乱所有下标。要点是记录仍是**积**（每个字段都在、都要提供），这和下一小节的和类型（几选一）形成对照。一个在本课后续（T5 子类型）会放大的伏笔：记录之间有天然的子类型关系（字段多的记录可当字段少的用，即宽度子类型），但**本大主题不涉及子类型**，这里的记录类型要求标签集完全一致才同类型——把"记录能否相互替换"留到 T5，此处点名不展开。另一个易错点：TAPL 的记录字段是否**有序**取决于表述；作宽度/深度子类型时通常视为无序集合，纯 STLC 里按定义给定的标签集匹配即可。

## T4.2 和类型与变体

### T4.2.1 和类型

**和类型**（sum type）T₁ + T₂ 表示"要么是个 T₁、要么是个 T₂"（二选一），与积（两个都要）对偶（§11.9）。引入是两个标记构造子 inl、inr，消去是 case 分情况处理

Γ ⊢ t₁ : T₁　　⟹　　Γ ⊢ inl t₁ as T₁ + T₂ : T₁ + T₂　　(T-Inl)

Γ ⊢ t₁ : T₂　　⟹　　Γ ⊢ inr t₁ as T₁ + T₂ : T₁ + T₂　　(T-Inr)

Γ ⊢ t₀ : T₁ + T₂　　Γ, x₁ : T₁ ⊢ t₁ : T　　Γ, x₂ : T₂ ⊢ t₂ : T
⟹　Γ ⊢ (case t₀ of inl x₁ ⇒ t₁ \| inr x₂ ⇒ t₂) : T　　(T-Case)

求值时 case 落到已标记的值上，选对应分支并把携带的值绑给分支变量

case (inl v₀ as T) of inl x₁ ⇒ t₁ \| inr x₂ ⇒ t₂ → [x₁ ↦ v₀] t₁　　(E-CaseInl)

case (inr v₀ as T) of inl x₁ ⇒ t₁ \| inr x₂ ⇒ t₂ → [x₂ ↦ v₀] t₂　　(E-CaseInr)

和类型的直觉是"带标签的联合"：inl（left injection）和 inr（right injection）像两张不同颜色的信封，把一个值装进去并记住它来自左边还是右边；case 就是"拆信按颜色分流"。这对建模"多种可能之一"极其常用——错误处理（成功值 + 错误值）、可选值（有 + 无）、语法树的多种结点，都是和类型。

TAPL 在这里遇到一个初学者必须理解的**唯一定型（uniqueness of typing）问题**：单看 inl 5，它是 Nat + Bool？还是 Nat + Nat？光凭 inl 5 无法确定右半边是什么类型。TAPL 的解法是要求写成 inl t as T₁+T₂（用 T4.1.4 的 ascription 把整体类型钉死），于是每个项仍恰有一个类型，算法化类型检查得以进行。这解释了为什么 inl/inr 规则里带 as：不是啰嗦，是为了保住"每个良型项类型唯一"这条对实现至关重要的性质。到了本课 T5（子类型）会有别的办法（最小上界），此处不展开。易错点：case 的两个分支**必须返回同一类型 T**——否则整个 case 表达式的类型无法确定；这也是初学者写 match/case 时最常撞的类型错误。

### T4.2.2 变体

**变体**（variant，§11.10）是和类型的"带标签、可多路"推广，正如记录是积的带标签推广：类型 <l_i : T_i \| i∈1..n>，值 <l_j = t_j> as <l_i : T_i \|...>，消去用带标签的 case。规则形如

Γ ⊢ t_j : T_j　　⟹　　Γ ⊢ (<l_j = t_j> as <l_i:T_i \| i∈1..n>) : <l_i:T_i \| i∈1..n>　　(T-Variant)

Γ ⊢ t₀ : <l_i:T_i>　　（对每个 i）Γ, x_i:T_i ⊢ t_i : T
⟹　Γ ⊢ (case t₀ of <l_i = x_i> ⇒ t_i) : T　　(T-Case)

case (<l_j = v_j> as T) of <l_i = x_i> ⇒ t_i → [x_j ↦ v_j] t_j　　(E-CaseVariant)

变体就是"带名字的多路和类型"，直接对应 ML 的 datatype、Haskell 的 data、Rust 的 enum、TypeScript 的可辨识联合（discriminated union）。它相对裸和类型的好处和记录相对元组一样：**用有意义的标签代替左右/位置**。TAPL 用变体给出两个经典编码，初学者应记住：

Bool 可编码为　<true : Unit, false : Unit>

Option T（"可有可无的 T"）可编码为　<none : Unit, some : T>

前者说明枚举就是"所有分支都携带 Unit 的变体"，后者是空值安全的基石——把"可能没有"显式编码进类型，逼迫使用者用 case 处理 none 分支，从根上消灭空指针。这正是工程上 Rust 的 Option/enum、Swift 的 optional 的理论原型（对应本课体系里 L5-14 R5 的 enum，点名不展开）。易错点同和类型：变体值也需 as 标注来保唯一定型；且 case 必须**穷尽**所有标签、各分支返回同一类型。

- 一手：TAPL Ch.11 §11.9 Sums、§11.10 Variants，2002 版；含 inl/inr 需 ascription 以保唯一定型、Option = <none:Unit, some:T> 编码；页码 132–142，核实 2026-07-30。
- 交叉一手：Harper《PFPL》2nd ed. 2016「Sum Types」章（二元和 + 有限和 finite sum、injection/case）。两书引入-消去与对偶于积的叙述一致；PFPL 从一开始就用带标签的有限和（更接近 TAPL 的 variant），TAPL 则先讲二元裸和再推广到 variant——呈现次序差异，非定义分歧。
- 冲突项：**唯一定型的处理**——TAPL 用 as 标注钉死和/变体类型以保每项类型唯一（算法化前提）；PFPL 在其表述里同样需要类型信息定位 injection 的目标类型。核心一致：裸 injection 类型不唯一、需外部类型信息；两书手段等价，正文已点明。
- 实证：case 的分支选择动态以元层 case 函数模拟并实跑（见 T4.3 实证脚注中 `case ("inl",3)` 的真实输出 103 / `("inr",3)` 输出 2），加固 E-CaseInl/E-CaseInr 的"按标签分流并代入"语义。

## T4.3 一般递归与列表

### T4.3.1 一般递归与 fix 算子

**一般递归**（general recursion，§11.11）通过 **fix 算子** 引入。纯 STLC 是**强正规化**的（每个良型项都会停机，见 TAPL Ch.12 正规化，本大主题不展开），所以它连"死循环"都写不出来，也就无法表达一般的递归函数——必须显式加一个不动点构造。规则为

Γ ⊢ t₁ : T₁ → T₁　　⟹　　Γ ⊢ fix t₁ : T₁　　(T-Fix)

fix (λx : T₁. t₂) → [x ↦ (fix (λx : T₁. t₂))] t₂　　(E-FixBeta)

外加把求值钻进 fix 参数的同余规则（E-Fix）。直观上 fix f 求解方程 x = f x：E-FixBeta 每被触发一次，就把"整个 fix 表达式自己"代回函数体里的递归位置，从而"按需展开一层"。

TAPL 在此之上把带类型的递归绑定 letrec 定义成 fix 的糖

letrec x : T₁ = t₁ in t₂　　≝　　let x = fix (λx : T₁. t₁) in t₂

初学者要接住的关键对照是它与本课 T2.3 的 Y 组合子：在**无类型** λ 演算里，递归靠 Y = λf.(λx.f (x x))(λx.f (x x)) 这类不动点组合子实现，无需任何原生支持。但 Y 里的自应用 x x **在 STLC 中无法定型**（x 既要当函数又要当它自己的参数，类型方程 T = T→? 无有限解），所以类型系统一收紧，Y 就写不出来了——这正是为什么必须把 fix 作为**原生构造**加进来。一句话总结这条脉络：**无类型世界用 Y 组合子换来递归，代价是同时放进了不停机；STLC 用类型挡掉了不停机，于是必须再用 fix 把递归"有节制地"请回来**。易错点：fix 的参数类型必须是 T→T（自己映到自己），因为不动点方程 x=f x 要求 f 的输入输出同类型；写成别的会定型失败。加了 fix 后 STLC 不再强正规化（可写死循环），但 Progress + Preservation 仍成立——类型安全只承诺"不卡在无意义状态"，从不承诺停机。

### T4.3.2 类型化列表

**列表**（list，§11.12）给出元素同类型的有限序列，类型 List T，配一组构造/析构原语

nil[T] : List T　　（空表）

cons[T] : T → List T → List T　　（表头 :: 表尾）

isnil[T] : List T → Bool　　（判空）

head[T] : List T → T　　（取首元）

tail[T] : List T → List T　　（去首元）

对应的关键求值规则为

isnil[S] (nil[T]) → true　　(E-IsnilNil)

isnil[S] (cons[T] v₁ v₂) → false　　(E-IsnilCons)

head[S] (cons[T] v₁ v₂) → v₁　　(E-HeadCons)

tail[S] (cons[T] v₁ v₂) → v₂　　(E-TailCons)

注意 nil、cons 等都带一个**类型注记** [T]，标明列表元素类型；这和 T4.2 的 inl as 是同一动机——保证 nil 这类"空壳"仍有唯一类型。

列表的直觉就是"归纳定义的链条"：一个 List T 要么是 nil（空），要么是 cons v vs（一个头 v 接一条更短的尾巴 vs）。这与 T4.2 的和类型、T4.1 的积暗合——列表本质上是"和（空 或 非空）套着积（头 与 尾）"的递归组合，正是本课 T6 递归类型要正面形式化的对象（List T ≈ μX. <nil:Unit, cons:{T, X}>，此处点名不展开）。易错点：head (nil) 和 tail (nil) 在这个系统里是**卡住项**（stuck，无规则可走），也就是运行时错误——纯 STLC 扩展并不用类型排除它（要靠 T4.5 的异常或依赖类型才能优雅处理空表取头）。这也是初学者理解"类型安全 ≠ 无运行时错误"的好例子：head nil 不是"类型错误"，而是一个良型但会卡住的项，正好动机出下一小节的异常机制。

#### 来源与时效（本小主题）
- 一手：TAPL Ch.11 §11.11 General Recursion（fix、T-Fix、E-FixBeta、letrec 糖）、§11.12 Lists（nil/cons/isnil/head/tail、List T），2002 版；页码 142–150，核实 2026-07-30。STLC 强正规化（fix 之所以必要）见 TAPL Ch.12。
- 交叉一手：Harper《PFPL》2nd ed. 2016「System PCF of Recursive Functions」章（一般递归 fix / fixed point、部分性 partiality 的引入）；列表作为归纳类型见其归纳类型相关章。两书 fix 的不动点语义一致；PFPL 强调 fix 使语言从全函数（total）变为部分函数（partial），与 TAPL "加 fix 后失去强正规化"是同一事实的两种说法。
- 冲突项：**Y 组合子 vs 原生 fix**——TAPL/PFPL 均以原生 fix 处理类型化递归，因经典 Y 的自应用在简单类型下不可定型（承本课 T2.3）。这不是两书分歧，而是"无类型 λ（Y 可写）"与"STLC（Y 不可定型、须原生 fix）"两个系统的区别，正文已点明。
- 实证：fix 的 call-by-value 不动点语义以元层 `fix(f)=f(lambda x: fix(f)(x))` 实现并实跑 `fact 5 = 120`（Python 3.11.15 @2026-07-30），加固 E-FixBeta 的"把自身代回递归位置"；head/tail 对 nil 的卡住性质为文本比对结论，未单独实证（标注）。

## T4.4 引用与存储

### T4.4.1 可变引用的语法与类型

**引用**（reference，Ch.13）把**可变状态**引入语言：ref t 分配一个新的、初值为 t 的**引用单元**（reference cell），!t 读取（解引用 dereference）单元当前内容，t₁ := t₂ 把 t₂ 的值写进 t₁ 指向的单元。引用单元的类型是 Ref T（"指向一个存 T 的可变单元"）。类型规则为

Γ ⊢ t₁ : T₁　　⟹　　Γ ⊢ ref t₁ : Ref T₁　　(T-Ref)

Γ ⊢ t₁ : Ref T₁　　⟹　　Γ ⊢ !t₁ : T₁　　(T-Deref)

Γ ⊢ t₁ : Ref T₁　　Γ ⊢ t₂ : T₁　　⟹　　Γ ⊢ (t₁ := t₂) : Unit　　(T-Assign)

赋值返回 Unit（它是为副作用而算，承 T4.1.2），且要求写入值的类型 T₁ 与单元声明的元素类型**严格一致**——这是保证读出来的东西类型不变的关键。

引用的直觉就是"一个盒子"：ref 造盒子并放进初值、返回盒子的把手（引用），! 打开盒子看里面、:= 换掉里面的东西，而把手本身（Ref T 值）可以到处传递、复制。这对应 ML 的 ref/!/:=、也解释了 C 指针、Java 对象引用背后的类型观念。初学者最该建立的区分是**引用 vs 内容**：一个 Ref T 类型的变量存的是"盒子的地址"，不是盒子里的值；把引用赋给另一个变量（r2 = r）复制的是**把手**，两者从此指向**同一个盒子**——这就是别名（见 T4.4.4）。

### T4.4.2 位置与存储

要给引用一个精确语义，必须把"内存"显式建模。TAPL 引入两个概念：**位置**（location，记作 l）是引用单元的抽象地址；**存储**（store，记作 μ）是从位置到值的有限映射，即"当前内存快照"。于是求值不再是 t → t′，而是在**配置**（configuration）t | μ 上进行——项和存储一起演进（§13.3）。核心求值规则为

ref v₁ | μ　→　l | (μ, l ↦ v₁)　　（l ∉ dom(μ)）　　(E-RefV)

!l | μ　→　μ(l) | μ　　(E-DerefLoc)

l := v₂ | μ　→　unit | [l ↦ v₂]μ　　(E-Assign)

E-RefV 挑一个新鲜位置 l、把它加进存储并返回 l；E-DerefLoc 从存储读 l 的当前值；E-Assign 更新存储中 l 的绑定、项本身变成 unit。

这里初学者要接住一个微妙但重要的点：**位置 l 是运行时才出现的项**，源程序里写不出 l——你写 ref 0，求值一步后它才变成某个具体的 l。所以 l 是"求值的中间产物"，需要一并进语法（作为值）和类型系统（下条的 store typing）。另一个直觉：把 store μ 显式拎出来当求值状态的一部分，是处理一切副作用的通用手法——同样的技巧也用于建模输入输出、随机数等。存储是"外部可变世界"，项在其中演进；纯函数式扩展（T4.1–T4.3）不需要它，正是因为那些构造不改变任何外部状态。

### T4.4.3 存储类型

给带引用的语言证类型安全，会撞上一个循环：要判断"位置 l 的类型"，天真的想法是"去 store μ 里查 μ(l) 的值、给它定型"，但 μ 里的值可能自己又含有指回 l 的引用（环状结构），于是定型永远绕不出来。TAPL 的解法是引入**存储类型**（store typing，记作 Σ，§13.4）：一个从位置到类型的映射，"每个单元该存什么类型"由 Σ 一次性声明，定型时查 Σ 而不去 store 里递归。类型判断因此扩展为带 Σ 的形式

Σ(l) = T₁　　⟹　　Γ \| Σ ⊢ l : Ref T₁　　(T-Loc)

（T-Ref/T-Deref/T-Assign 也相应带上 Σ，形如 Γ \| Σ ⊢ ...）

核心思路是：**Σ 把"位置的类型"从"值的类型"里解耦出来**，用一个独立的、不递归的映射来记录，从而斩断环状引用带来的定型循环。

初学者可以这样理解 Σ 与 μ 的分工：μ 是"内存里现在装着什么值"（运行时数据），Σ 是"每个内存格子被设计来装什么类型"（静态契约）。给 l 定型时问的是契约 Σ 而非当前内容 μ，所以哪怕 μ 里有指来指去的环，定型也一步到位。这也解释了为什么类型规则要多背一个 Σ——它是为了让"含环的可变堆"也能被静态定型而付出的必要代价。这是 TAPL 里第一次出现"类型判断需要一个描述运行时结构的辅助上下文"，同样的模式在更复杂的系统（对象、模块）里反复出现。

### T4.4.4 存储下的类型安全

有了 Σ，就能重述 Progress + Preservation。关键新概念是**良类型存储**（well-typed store）Γ | Σ ⊨ μ：存储 μ 中每个位置 l 存的值，其类型都符合 Σ(l)。两定理相应改写为在配置上陈述（§13.5）

保型（Preservation）陈述为，若 Γ \| Σ ⊢ t : T、且 Γ \| Σ ⊨ μ、且 t \| μ → t′ \| μ′，则存在某个扩展 Σ′ ⊇ Σ，使 Γ \| Σ′ ⊢ t′ : T 且 Γ \| Σ′ ⊨ μ′。

前进（Progress）陈述为，若 t 是（相对 Σ）闭合良型项，则 t 要么是值，要么对任何满足 Γ \| Σ ⊨ μ 的 μ，配置 t \| μ 都能再走一步。

Preservation 里那句"存在扩展 Σ′ ⊇ Σ"是精髓：ref 会分配新位置，让存储类型**变长**，所以保型定理必须允许 Σ 在求值中增长——类型不变，但"已知位置集合"单调扩大。

初学者要抓两个直觉。其一，为什么加了可变状态还能保持安全？因为 T-Assign 强制"写进单元的值类型 = 单元声明类型"，所以任何时刻从单元读出的东西类型都如契约所料，别名再多也不会读出类型错乱的值——**别名不破坏类型安全，因为所有别名共享同一个 Σ(l) 契约**。其二，这套演算里 ref 只分配、**从不释放**（没有 free / 没有 GC），所以不会出现悬垂引用（dangling pointer）——位置一旦分配就永远有效，安全性因此免费得到；真实语言要回收内存，才需要额外的机制（GC 或 Rust 的所有权/借用，见 L5-14）来在"允许释放"的前提下仍防悬垂。这条对照点出了本大主题引用模型的"理论洁净、工程简化"边界：它证明了"可变状态可以类型安全"，但把内存管理的难题搁置了。别名的实机观感见本节实证。

- 一手：TAPL Ch.13 §13.1 引言（ref/!/:=、别名、counter 例）、§13.2 Typing（T-Ref/T-Deref/T-Assign）、§13.3 Evaluation（配置 t\|μ、位置 l、E-RefV/E-DerefLoc/E-Assign）、§13.4 Store Typings（Σ、T-Loc、解循环）、§13.5 Safety（良类型存储、含 Σ′⊇Σ 的 Preservation、Progress），2002 版，页码 153–170，核实 2026-07-30。

## T4.5 异常

### T4.5.1 抛出异常：error 项

**异常**（exception，Ch.14）为"非局部地中止当前计算"提供机制。TAPL 分三步引入，第一步是最简的不可恢复错误项 **error**（§14.1）：一遇到 error，就丢弃周围一切待算的上下文、直接把 error 冒泡到顶层。它的类型规则和求值（传播）规则为

Γ ⊢ error : T　　（对任意类型 T）　　(T-Error)

error t₂ → error　　(E-AppErr1)

v₁ error → error　　(E-AppErr2)

也就是 error 像"计算里的黑洞"，出现在应用的函数位或参数位都会把整个应用一口吞成 error（并继续向外吞）。

T-Error 里那句"对任意类型 T"值得初学者停一下：error 可以有**任何**类型。这很自然——一个永不返回正常值的项，放在期待任何类型的位置都不会"读出错类型的值"，所以给它全部类型是安全的。但它带来一个实现难题：**唯一定型被打破**（error 不再恰有一个类型）。TAPL 说明这会让算法化类型检查变复杂，干净的处理要么等本课 T5 的子类型（给 error 一个"最小类型" Bot，让 error : Bot 再向上包容到任何类型），要么在算法里特殊照顾 error。这里点名不展开，只需记住结论：**error 破坏唯一定型，是后续引入 Bot / 子类型的动机之一**。另一个要点：加了 error 后 Progress 定理要**改写**——良型闭合项现在的结局是"值 或 error 或 能再走一步"，把 error 作为一个合法的最终结果承认下来，否则"冒到顶层的 error"会被误判为卡住。

### T4.5.2 处理异常：try/with

第二步给异常加上**捕获**能力（§14.2）：try t₁ with t₂ 先算 t₁，若 t₁ 正常求值就用它的结果、忽略 t₂；若 t₁ 抛出 error，就转而求值**处理器** t₂。规则为

try v₁ with t₂ → v₁　　(E-TryV)

try error with t₂ → t₂　　(E-TryError)

t₁ → t₁′　　⟹　　try t₁ with t₂ → try t₁′ with t₂　　(E-Try)

类型上要求两条路（t₁ 正常返回 与 t₂ 兜底返回）给出同一类型

Γ ⊢ t₁ : T　　Γ ⊢ t₂ : T　　⟹　　Γ ⊢ (try t₁ with t₂) : T　　(T-Try)

try 的直觉就是"设一道防线"：正常情况下防线不起作用（E-TryV 直接放行结果）；一旦里面炸了（error），防线拦住冒泡、改跑备用方案 t₂（E-TryError）。这正是各语言 try/catch、ML 的 handle 的核心语义。要点是 E-TryError 拦下的是"恰好冒到这层的 error"——try 是唯一能**阻断** error 传播的构造，其余上下文（应用、投影等）都只会放行传播（承 E-AppErr1/2）。易错点：try 的两个分支必须同类型（T-Try），道理和 case 一样——整个表达式无论走哪条路都得有确定的类型。至此 error 从"必然冒到顶层"升级为"可被局部捕获恢复"，这才是真正可用的异常。

### T4.5.3 携带值的异常

第三步让异常**携带数据**（§14.3），从而处理器能知道"出了什么错"。把无参的 error 换成带参的 raise t（抛出并携带值 t），把处理器换成一个**函数**（接收被携带的值）。设异常携带值的类型为固定的 T_exn，规则为

Γ ⊢ t₁ : T_exn　　⟹　　Γ ⊢ raise t₁ : T　　（对任意 T）　　(T-Exn / T-Raise)

Γ ⊢ t₁ : T　　Γ ⊢ t₂ : T_exn → T　　⟹　　Γ ⊢ (try t₁ with t₂) : T　　(T-Try)

try v₁ with t₂ → v₁　　(E-TryV)

try (raise v₁₁) with t₂ → t₂ v₁₁　　(E-TryRaise)

raise 仍像 error 那样有任意结果类型 T（它不正常返回），但多背一个"携带值类型 T_exn"；捕获时 E-TryRaise 把携带的值 v₁₁ **喂给处理器函数** t₂，于是处理器能按错误内容分情况处置。

初学者要理解 T_exn 这个"异常类型"的作用：它是全语言约定的"异常能携带什么"的统一类型。在真实语言里 T_exn 往往是一个**可扩展的变体/类"**——各处代码把自己的错误注册成 T_exn 的一个新标签（如 <divByZero:Unit, fileNotFound:String, ...>），处理器再用 T4.2 的 case 按标签分流。这就把本大主题的多个零件串了起来：异常携带值（本节）+ 变体（T4.2）= 现代语言"按错误种类分别 catch"的能力。要点与前两节一贯：raise/error 破坏唯一定型（任意结果类型），且 Progress 需把 raise 到顶层作为合法结局。TAPL 也明确 error / 异常与本课 T4.4 引用属于"正交扩展"——各自独立地挂在 STLC 上、各自补几个 case 重证安全，这正回扣本报告主线"类型系统可增量扩展"。

#### 来源与时效（本小主题）

- 交叉一手：Harper《PFPL》2nd ed. 2016 异常相关章（异常作为一种控制效果、固定的异常值类型、handle 语义），与控制栈 / continuation 章相邻。两书 try/handle 语义一致；PFPL 从"控制效果"视角组织，TAPL 从"给 STLC 加特性并重证安全"视角组织——视角差异，非定义分歧。
- 冲突项：**error 的类型 error : T（任意 T）与唯一定型**——TAPL 承认这会破坏唯一定型，并把干净处理（Bot / 子类型）推迟到 Ch.15（本课 T5）；这是 TAPL 内部的一处"暂缓"，非两书矛盾。真实语言 T_exn 通常实现为可扩展变体（如 ML 的 exn），本报告按 TAPL 取固定 T_exn 表述，并点明工程上多为可扩展变体，两种口径都记。
