## T6.1 递归类型示例

### T6.1.1 μ 记法与递归类型的引入

**递归类型**（recursive type）是允许在类型定义中引用自身的类型，用 **μ 记法**（mu-notation）写出（TAPL §20.1；PFPL 同名概念）

μX.T

其中 X 是**类型变量**，T 是可能含有 X 的类型表达式，μX 把 X **绑定**在 T 内（类比 λx 绑定项里的 x）。μX.T 直观读作"满足方程 X = T 的那个类型"。

理解这一节要抓住"类型层面的自指"这一件事。普通类型如 Nat、Bool→Nat 都是有穷写死的；但"自然数列表"这种类型天然是自指的——一个列表要么空、要么是"一个数配上另一个列表"，定义里又冒出了"列表"自己。μ 就是给这种自指一个精确写法：把要自指的地方换成变量 X，再用 μX 把它"扎住"。一个易错点是 μX.T 里的 X **不是一个真实存在的独立类型**，它只是个占位记号，表示"此处再放一份整个 μX.T"；真正的含义要靠下一小主题的"展开"来给。另一个初学者常混的点是 μ（类型层的递归绑定子）和 λ（项层的函数绑定子）虽然形似，但一个在类型上、一个在项上，作用对象完全不同。

### T6.1.2 列表作为 μ 类型

最经典的例子是**自然数列表**（TAPL §20.1）

NatList = μX. <nil:Unit, cons:{Nat, X}>

即"一个 NatList 是一个变体（variant，见 T4.2）：要么是携带 Unit 的 nil 标签，要么是携带一个 {Nat, X} 序对的 cons 标签"，而里面那个 X 又代表整个 NatList。构造与析构操作（同构递归表述，fold/unfold 见 T6.2）为

nil = fold [NatList] (<nil = unit> as <nil:Unit, cons:{Nat,NatList}>)

cons = λn:Nat. λl:NatList. fold [NatList] <cons = {n, l}> as …

理解要点是，这正是 ML 里 `type natlist = Nil | Cons of int * natlist` 的形式化。和类型/变体（T4.2）负责"要么空要么非空"的**选择**，μ 负责"非空分支里又出现列表自己"的**自指**——两者合起来才拼出列表这个数据结构。初学者要看清 μ 的作用：如果没有 μ、把 X 换成一个具体类型，那这个类型就"封顶"了、只能表示定长的东西；正因为 X 指回整个类型，它才能表示任意长的列表。一个易错点：`{Nat, X}` 里用序对（积类型）把"头元素"和"尾列表"绑在一起，头是 Nat、尾是 X（即又一个 NatList），别把 X 误当成 Nat。

### T6.1.3 流作为 μ 类型

递归类型不止能表达"有限但任意长"，还能表达**无限数据**。**流**（stream）是一个"每次索要就吐出一个数、外加剩下的流"的对象（TAPL §20.1）

Stream = μA. Unit → {Nat, A}

即一个 Stream 是个函数：喂给它 unit，它返回一个序对 {当前的数, 剩下的流}。取头、取尾为

hd = λs:Stream. (unfold[Stream] s unit).1

tl = λs:Stream. (unfold[Stream] s unit).2

理解要点是，和列表不同，流**没有 nil 分支**——它永远有下一个元素，是真正无穷的。为什么要用一个 `Unit→…` 的函数包一层？因为如果直接写 `μA.{Nat,A}`，构造它就得当场把无穷多个数全算出来（不可能）；包成函数后，"下一个数"只有在你真正调用时才被计算，这就是**惰性/按需产生**。初学者可以把流理解成"一台按一下出一个数、并把自己复位成新流的机器"。这也预告了 T6.3 的直觉分野：有限的列表用**归纳**理解（从 nil 往上建），无限的流用**余归纳**理解（永远能再观察一步）。本节 hd/tl 里出现的 unfold 是把 Stream 当函数用前必须做的"揭开一层"动作，详见 T6.2。

### T6.1.4 对象作为 μ 类型

面向对象里"方法返回一个新的自己"也是递归类型。TAPL 用**计数器对象**示范（TAPL §20.1；Abadi–Cardelli 对象论同一思想）

Counter = μC. {get:Nat, inc:Unit→C}

一个 Counter 是个记录：字段 get 给出当前值（Nat），字段 inc 是个函数，调用后返回一个**新的 Counter**（值加一后的对象）。返回类型里又出现 C，故必须用 μ。

理解要点是，这解释了对象为什么"天生递归"——只要有一个方法返回 `Self` / 同类对象（如 Java 里返回 `this` 或链式调用返回自身类型），类型定义就自指了。用函数式的"返回新对象"而非"原地改字段"来建模，是为了先在没有可变状态的纯 λ 里把对象的**类型结构**讲清楚（可变版本要配 T4.4 的引用）。初学者要抓住的关联：对象 = 记录（T4.1，把若干方法/字段捆一起）+ 递归（μ，让方法能提到对象自己）；把这两块拼起来就得到了对象最朴素的类型刻画。TAPL Ch.18（子类型部分）与 Abadi–Cardelli 专著在此基础上发展出完整的对象演算，本报告按 v3 点到即止。

### T6.1.5 递归类型带来一般递归与不停机

一个深刻且易被忽视的事实：**给简单类型 λ 演算（STLC）加上递归类型，就足以写出不动点组合子、从而获得一般递归与不停机**，即使语言本身没有内建 fix（TAPL §20.1；PFPL「System FPC」同一结论）。关键在于用递归类型把"危险的自应用"重新定型。定义

D = μX. X → X

则原本在 STLC 里非法的自应用 `x x`，在把 x 当作 D 类型后可以合法地打上类型（借助 fold/unfold 在 D 与 D→D 间转换）。由此可构造出良类型的不动点组合子，进而

fix_T : (T → T) → T

回忆 T2.3 的发散项 Ω=(λx.x x)(λx.x x) 和 T3——STLC 之所以强可终止（一定停机），正是因为它**禁掉了 `x x` 这种自应用**（x 若是函数 S→T，就不能又当 S 用）。递归类型恰好把这道门重新打开：D=μX.X→X 说"X 既是函数又是它自己的参数类型"，于是 `x x` 合法了，Ω 和 fix 也就回来了。结论是**递归类型让类型系统重新变得图灵完备**——"良类型程序不会卡住"（类型安全）仍然成立，但"良类型程序一定停机"（强规范化）**被牺牲掉了**。相关的还有"永远饥饿的函数" Hungry = μA. Nat→A（吃一个数、返回又一个还要吃数的函数，可无限喂下去），以及用 μX.X→X 直接把整个无类型 λ 演算嵌进带类型的世界。初学者记住这条取舍即可：**表达力（一般递归、无限数据、对象）与强可终止性不可兼得，递归类型选了前者。**

## T6.2 等递归 vs 同构递归

### T6.2.1 核心问题：μX.T 与其展开的关系

递归类型元理论的全部分岔，起于一个问题：μX.T 和把它"展开一层"得到的类型是什么关系（TAPL §20.2）。**展开**（unfolding）指把 T 里的 X 替换成整个 μX.T

[X ↦ μX.T] T

例如 NatList = μX.<nil:Unit, cons:{Nat,X}> 展开一层得

<nil:Unit, cons:{Nat, NatList}>

问题在于，这个展开式和 NatList **是同一个类型（相等）**，还是**两个不同但可来回转换的类型（同构）**？两种回答给出两套系统。

理解要点是，这一步是本小主题的"总开关"，务必先建立直觉。"展开"就是把递归定义按一次它自己的定义"抄"进去——List 的定义里有 List，抄一次就得到"空 | 数×List"。直觉上展开式和原类型"描述的是同一堆数据"，所以自然想说它们相等（等递归）；但相等会让类型检查器面对"无限展开"的麻烦，于是另一条路要求程序员显式标记每一次展开/折叠（同构递归）。初学者先记住这对术语的字面含义：**等递归 = equi-recursive（equal，相等）**，**同构递归 = iso-recursive（isomorphic，同构）**——名字本身就点明了两者对上面那个问题的不同回答。

### T6.2.2 等递归表述

**等递归**（equi-recursive）表述规定：递归类型与它的任意步展开**就是同一个类型**，在所有类型上下文里可以自由互换（TAPL §20.2）

μX.T  =  [X ↦ μX.T] T

程序员无需写任何标记，`nil`、`cons` 得到的东西直接就是 NatList，编译器自己在"折叠形态"和"展开形态"间无缝切换。

理解要点是，等递归对**程序员最友好**——代码里看不到任何额外的转换算子，写起来就像类型自然地相等。代价全压在**类型系统的元理论**上：既然 μX.T 可以无限展开，判断"两个类型是否相等""一个是否是另一个的子类型"就得在**无限展开的树**上做（见 T6.3），类型等价与子类型的算法明显更复杂，可靠性证明也更繁琐。一个易错点：等递归**不是**说"任何自指都合法"——像 μX.X 这种没有实质结构、纯粹指向自己的类型通常要被排除（否则语义无意义），实用系统会要求 μ 下的 X 出现在某个类型构造子内部（"contractive/guarded"）。OCaml 加 `-rectypes` 开关后的对象类型、多态变体就是等递归的现实例子。

### T6.2.3 同构递归表述

**同构递归**（iso-recursive）表述规定：μX.T 与其展开 [X↦μX.T]T **不相等，但同构**——存在一对互逆的内建函数在两者间转换（TAPL §20.2）。这对函数是 **fold** 与 **unfold**

fold[μX.T]   : [X ↦ μX.T] T  →  μX.T

unfold[μX.T] : μX.T  →  [X ↦ μX.T] T

fold 把"展开形态"的值打包成递归类型（"折起来"），unfold 把递归类型拆回展开形态（"摊开来"）；程序员必须在代码里显式写出它们。

理解要点是，同构递归把负担从"编译器"移到"程序员"——你每次要把一个 `<nil:Unit,cons:{Nat,NatList}>` 形状的值当 NatList 用，就得写个 fold；每次要拆开一个 NatList 看它内部结构，就得写个 unfold。换来的好处是**类型系统极其简单**：μX.T 和别的类型比是否相等/子类型时，它就是个普通的、不会自动展开的类型，完全不必处理无限树。这就是为什么"绝大多数实际语言选同构递归"（TAPL §20.2 明确指出）。初学者最该建立的关联在下一节：ML/Haskell 里你其实**天天在写 fold/unfold**，只是它们被藏在了数据构造子和模式匹配里。

### T6.2.4 fold/unfold 的类型规则与求值

同构递归下 fold/unfold 作为项层构造，其**类型规则**为（TAPL §20.2，记 U = μX.T）

Γ ⊢ t₁ : [X ↦ U] T  ⟹  Γ ⊢ fold[U] t₁ : U　　(T-Fold)

Γ ⊢ t₁ : U  ⟹  Γ ⊢ unfold[U] t₁ : [X ↦ U] T　　(T-Unfold)

fold 后的项是值（fold[U] v 为 value），二者互逆由**求值规则**保证

unfold[S] (fold[T] v₁)  →  v₁　　(E-UnfldFld)

即"先折再拆"回到原值，运行时 fold/unfold 相遇就抵消。

理解要点是，T-Fold 读作"如果 t₁ 已经是展开形态（[X↦U]T）的值，就能 fold 成递归类型 U"；T-Unfold 反过来。E-UnfldFld 是全套机制的核心——它说明 fold 和 unfold 确实是一对逆运算，运行期不留下任何真实计算，纯粹是给类型检查器看的"形态标记"。一个关键澄清（初学者易误解）：fold/unfold **只影响类型、不改变运行时数据**，一个 NatList 的值折叠前后在内存里是同一个东西，fold/unfold 是"零成本"的类型层记号（这也呼应了它为何能被编译器完全擦除）。把它和 ML 对照：`Cons(3, l)` 里的构造子 `Cons` 干的就是 fold 的活（把展开形态包成 natlist），而 `match l with Cons(h,t) -> …` 里的模式匹配干的就是 unfold 的活（把 natlist 拆回展开形态供你取 h、t）。

### T6.2.5 两种表述的取舍与现实对应

把两条路并排看（TAPL §20.2；PFPL 采同构递归为主）。等递归让**程序无标记、类型系统复杂**；同构递归让**类型系统简单、程序需显式 fold/unfold**。表达力上两者本质等价（都能表达同一批递归类型），差别在"负担放哪"和"元理论难易"。

现实语言的落点是初学者最该记住的关联。ML、Haskell 等的 **datatype/data 声明本质是同构递归**：每个数据构造子隐式携带一个 fold，每次模式匹配隐式携带一个 unfold——程序员不必手写 fold/unfold 字样，是因为构造子/模式匹配把它们自动插好了。这也解释了为什么 ML 里"结构相同但名字不同的两个 datatype 不可互换"（名义式、iso 味道）。相反，需要"结构相等即可互换"的场景（如 OCaml 对象类型、多态变体）走等递归。一个易错点：不要把"同构递归需要 fold/unfold"误读成"实际编程很啰嗦"——在有 datatype 语法糖的语言里你几乎感觉不到它们的存在，fold/unfold 是形式系统层面的显式算子，语言表层用构造子/匹配把它包了起来。

## T6.3 递归类型的元理论

### T6.3.1 类型作为树：有限与无限

要精确谈论递归类型的相等与子类型，先把类型看成**树**（TAPL §21.2）。普通类型（Nat、T→U 等）是**有限树**（finite tree types）——叶子是基类型、内节点是 →/×/+ 等构造子。递归类型 μX.T 对应把它**无限展开**得到的**无限树**：每遇到 X 就再长出一整棵 μX.T 的树，永不终止。

例如 μX.(Nat→X) 展开成无限右伸的树 Nat→(Nat→(Nat→…))。

理解要点是，这是等递归元理论的地基。既然 μX.T 与其无限展开"相等"，判断两个递归类型是否相等/子类型，本质就是比较两棵**无限树**——不能靠有限步的结构归纳硬走到底。关键补充：μ 类型展开出的无限树不是任意无限树，而是**正则树**（regular tree），即只含**有限多种不同子树**的无限树（TAPL §21.7 及 §21.8）。正是"有限多种子树"这一点让无限对象仍可被有限算法处理——比较两棵正则树时，状态数有限，算法能终止。初学者先抓直觉：**递归类型 = 有规律地无限重复的树；正因为规律有限，才能用有限手段判定它的性质。**

### T6.3.2 归纳与余归纳

比较无限树需要一套与结构归纳对偶的工具：**余归纳**（coinduction）。TAPL §21.1 把归纳与余归纳统一在不动点框架下。给定全集 U 与一个**单调生成函数** F（把集合映到集合），称 X 是 F-闭的若 F(X)⊆X、是 F-一致的若 X⊆F(X)。由 Knaster–Tarski 定理，F 有**最小不动点** μF 与**最大不动点** νF

μF = 所有 F-闭集之交（最小 F-闭集）

νF = 所有 F-一致集之并（最大 F-一致集）

对应两条证明原理

若 F(X) ⊆ X，则 μF ⊆ X　　（归纳原理）

若 X ⊆ F(X)，则 X ⊆ νF　　（余归纳原理）

理解要点是，归纳"从底向上有穷地构造"（自然数、有限列表、有限树都是某个 μF），证明用结构/规则归纳；余归纳"从顶向下允许无穷"（流、无限树都是某个 νF），证明用余归纳原理。余归纳原理的用法极实用：**要证某关系里的一对对象满足某个"无限性质"，只需找到一个包含它、且对生成函数"自洽（X⊆F(X)）"的集合即可**——不必真的走完无限步。初学者可把两条原理记成一句对偶口诀：归纳是"闭集夹住最小不动点"，余归纳是"一致集被最大不动点罩住"。本报告按 prompt 要求，余归纳只讲这层直觉，不铺完整格论证明。

### T6.3.3 递归类型上的子类型

递归类型的**子类型关系**用**余归纳**（最大不动点）定义（TAPL §21.3；Amadio–Cardelli 1993 为一手出处）。直觉上 S <: T 成立，当"把它们各展开一层后对应部分的子类型要求"能一直自洽地成立下去——因为展开无穷，取**最大**满足这组要求的关系（即最大不动点 νF），而非最小。对同构递归的实用系统，常用 Amber 语言（Cardelli）传下来的 **Amber 规则**在假设下比较两个 μ 类型

Σ, X<:Y ⊢ S <: T  ⟹  Σ ⊢ μX.S <: μY.T　　(S-Rec, Amber 规则)

即"先假设 X<:Y（两递归变量对应），若能推出体 S<:T，则 μX.S <: μY.T"。

为什么子类型要用余归纳而不是归纳？因为递归类型无限展开，若用"从底建起"的归纳，永远建不到底、无法开始；改用余归纳，等于说"只要找不到反证（找不到某处违反子类型要求），就认定成立"——这对无限对象是唯一说得通的定义方式。Amber 规则的精髓是那个**假设 X<:Y**：处理 μ 时把"两个递归变量互为子类型"当成前提记进上下文，从而在遇到内部再次出现的 X、Y 时可直接引用假设、不必无限展开，这正是余归纳"自洽即成立"在算法上的体现。初学者易错点：递归类型子类型的方向仍受各构造子变型规则支配（函数参数逆变、结果协变，见 T5），μ 本身不改变型方向，只是把"无限"这层用余归纳兜住。

### T6.3.4 子类型的传递性与判定算法

TAPL §21.4 特意用一节讨论**传递性**（transitivity）这个坑，值得单列。用余归纳直接定义出的子类型关系，其**传递性（S<:U 且 U<:T 推出 S<:T）不是显然的**，需要单独论证——这与有限类型下传递性可由归纳轻松得到形成对照。相应地，判定 S<:T 是否成立用**求最大不动点的成员检查算法**（TAPL §21.5–§21.6）

从待判定的一对 (S,T) 出发，反复用生成函数展开、把新产生的子目标对加入待验证集合，若过程中从未碰到"明确违反"且因正则性（有限种子树）最终不再产生新目标对，则判定 S<:T 成立。

理解要点是，这套算法之所以能终止，全靠 T6.3.1 的正则树性质——子树种类有限，展开中出现的 (S,T) 对也只有有限种，算法记住已访问过的对（类似图搜索的 visited 集），碰到重复就当作"已自洽"停下。这与 T6.3.3 Amber 规则"假设 X<:Y"是同一件事的两种表述：一个是声明式的推理规则、一个是过程式的判定算法。初学者要接住的关联：这正是 T5.2"算法子类型"在递归类型上的延伸——普通类型的子类型判定是有限递归下降，递归类型的判定则是"带 visited 集、靠正则性保证终止"的余归纳式搜索。TAPL §21.4 的传递性讨论提醒一个易错点：**别默认余归纳定义出来的关系自动具备传递性/自反性这些"看起来理所当然"的性质，它们要一条条证。**

### T6.3.5 余归纳直觉小结与关联

收束本大主题的元理论视角（TAPL §21.1–§21.2；PFPL 归纳/余归纳类型章）。**归纳类型**（列表、有限树）是"有穷构造、最小不动点 μF"，配"构造子建、结构归纳证"；**余归纳类型**（流、无限对象）是"无穷观察、最大不动点 νF"，配"观测子拆、余归纳证"。递归类型 μX.T 在等递归视角下天然对应无限（正则）树，故其相等与子类型都落在余归纳一侧。

理解要点（本节按 prompt 只给直觉、不展开完整理论）：把"归纳 vs 余归纳"记成"建 vs 拆""有限 vs 无限""最小 vs 最大不动点"三组对偶即可。为什么这对初学者重要？因为它把 T6.1 埋下的两个例子收了口——列表（T6.1.2）是归纳的（总能从 nil 有穷地建起、可结构归纳），流（T6.1.3）是余归纳的（永远只能再观察一步、要余归纳推理）；而 T6.2 的等递归之所以元理论难，正是因为它把递归类型当无限树、逼着相等与子类型都走余归纳。一个常见误解需澄清：余归纳**不是**"反着做归纳"或某种玄学，它就是"取最大不动点 + 用一致集(X⊆F(X))作证据"这一套精确机制，只是服务于无限对象而已。此处点到即止，深入的余代数/双模拟理论超出本课范围（TAPL 亦不展开）。
