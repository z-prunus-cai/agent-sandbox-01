> 本报告一条主线心智模型：**有界量化 = "带上界的泛型"**。纯 System F 的 ∀X 说"对任意类型都成立"，太宽，函数体里对 X 什么也不能做；纯子类型 + subsumption 能约束参数却会把"实参其实是更全的类型"这件事忘掉。有界量化 ∀X<:T 取两者之长：类型参数 X 被限制为 T 的某个子类型（所以函数体可以安全使用 T 提供的一切操作），同时 X 仍是一个类型变量（所以调用点传进来的具体类型不会在结果里被抹平）。一句话——"参数必须至少是个 T，但到底是哪个 T 的子类型，由调用方决定并被完整记住"。

> 本大主题以文本多来源比对为主，本机实证机会少（F<: 的核心命题——安全性、kernel 可判定、Full 不可判定——都是证明论/可判定性命题，无法靠一次运行"证明"）。本报告未做本机实证，如实标注；所有规则与结论以 TAPL 一手 + 上述交叉一手比对为准。

## T9.1 有界量化 F<:

### T9.1.1 动机：子类型多态会"丢信息"

有界量化要解决的问题，是纯子类型加纯多态各自都办不好的一件事——写一个"对任何至少含某些字段的记录都适用、且不丢失其原始类型"的函数（TAPL §26.1）。先看纯子类型的做法。恒等函数

f = λx:{a:Nat}. x

的类型是 {a:Nat} → {a:Nat}。把一个更全的记录 r = {a=0, b=true}（类型 {a:Nat, b:Bool}）传进去：由记录宽度子类型 {a:Nat, b:Bool} <: {a:Nat} 与 subsumption，r 被当作 {a:Nat} 接受，于是

f r : {a:Nat}

——注意结果类型里 b 字段**消失了**。子类型让调用合法，代价是把"实参其实还带着 b"这条信息在结果类型上抹掉了。

有界量化用一个带上界的类型抽象修好它

f = λX<:{a:Nat}. λx:X. x

它的类型是

∀X<:{a:Nat}. X → X

调用时先传具体类型、再传值

f [{a:Nat, b:Bool}] r : {a:Nat, b:Bool}

结果类型完整保留了 {a:Nat, b:Bool}。

理解这里的取舍是本大主题的起点。纯 System F 的 ∀X. X→X 也能保留类型（多态恒等），但那样的话 X 完全无约束，函数体里对 x 除了原样返回什么也做不了——因为"任意类型"意味着不能假设它有 a 字段。纯子类型能保证 x 有 a 字段（可以写 x.a），却会丢类型。有界量化 ∀X<:{a:Nat} 同时拿到两件事：界 {a:Nat} 保证 X 一定有 a 字段（函数体里 x.a 合法），而 X 仍是变量，保证结果类型随调用点的具体类型而定、不被抹平。初学者可以记成一句口诀——"**界管‘能对它做什么’，变量管‘它到底是谁、别忘了’**"。

### T9.1.2 F<: 的语法：类型抽象、类型应用、有界全称类型

F<: 在 STLC + 子类型之上，把 System F 的三样东西各加一个"界"（TAPL §26.2，Figure 26-1）。项这一层新增两个构造

λX<:T. t　　（有界类型抽象）

t [T]　　（类型应用）

类型这一层新增有界全称类型

∀X<:T₁. T₂

而上下文 Γ 里除了 x:T 这种项变量绑定，还多了类型变量绑定

X <: T

意思是"类型变量 X 已声明、其上界是 T"。

要点在于"处处都比 System F 多带一个界"。System F 的类型抽象是 λX. t（引入一个无约束的类型变量），有界版 λX<:T. t 引入的类型变量自带上界 T；System F 的全称类型 ∀X. T₂ 在 F<: 里写成 ∀X<:T₁. T₂。上下文里之所以要记 X<:T，是因为进入一个 λX<:T 的函数体后，后续所有子类型/类型判断都要知道"当前这个抽象类型变量能当什么用"——正是靠 Γ 里的 X<:T 这条记录，函数体才敢对 X 类型的值使用 T 的操作。初学者容易忽略上下文的这一变化：F<: 的类型环境不再只装"变量的类型"，还装"类型变量的界"，两类绑定共用一个 Γ、按出现顺序排列（后面的可以引用前面声明的类型变量）。

### T9.1.3 界、子类型规则与类型规则

F<: 的子类型关系 <: 在 Γ 下定义（TAPL §26.2，Figure 26-1）。除沿用 T5 的 S-Refl、S-Trans、S-Arrow 外，有界量化带来三条关键规则。类型变量的界本身就是一条子类型事实

X <: T ∈ Γ ⟹ Γ ⊢ X <: T　　(S-TVar)

任何类型都是 Top 的子类型

Γ ⊢ S <: Top　　(S-Top)

以及量化类型之间的子类型规则 S-All（下一节详述 kernel/full 两版）。

类型规则方面，有界类型抽象与类型应用各配一条

Γ, X<:T₁ ⊢ t₂ : T₂ ⟹ Γ ⊢ (λX<:T₁. t₂) : (∀X<:T₁. T₂)　　(T-TAbs)

Γ ⊢ t₁ : (∀X<:T₁₁. T₁₂)　　Γ ⊢ T₂ <: T₁₁ ⟹ Γ ⊢ t₁ [T₂] : [X↦T₂] T₁₂　　(T-TApp)

再加上从 T5 继承的包容规则

Γ ⊢ t : S　　S <: T ⟹ Γ ⊢ t : T　　(T-Sub)

理解 S-TVar 是抓住"界怎么起作用"的钥匙。它说：一个抽象类型变量 X，唯一已知的子类型事实就是"X 是它上界的子类型"。于是在 λX<:{a:Nat} 的函数体里，X <: {a:Nat} 成立，配合 subsumption，一个 X 类型的值 x 可当作 {a:Nat} 使用，从而 x.a 合法——这正是 T9.1.1 里"界保证能取 a 字段"的规则级来源。

T-TApp 的第二个前提 Γ ⊢ T₂ <: T₁₁ 是初学者最该盯住的地方：给 ∀X<:T₁₁ 的函数做类型应用 t₁ [T₂] 时，传入的具体类型 T₂ **必须满足界**（是 T₁₁ 的子类型），否则不合法。这与函数应用要求实参类型匹配是一回事，只不过发生在类型层：界就是对"能传哪些类型"的约束。传进去之后，结果类型把函数体类型里的 X 全替换成 T₂（即 [X↦T₂] T₁₂），这一步替换正是"类型信息不被抹平"的机制——结果里留下的是调用方给的真实类型 T₂，而非界 T₁₁。

### T9.1.4 kernel F<: 与 full F<:：量化类型之间的子类型

F<: 有两个版本，差别**只在一条规则**——两个有界全称类型之间何时构成子类型（TAPL §26.2，规则 S-All）。kernel F<: 要求两边的界**完全相同**，只比较量化体

Γ, X<:U₁ ⊢ S₂ <: T₂ ⟹ Γ ⊢ (∀X<:U₁. S₂) <: (∀X<:U₁. T₂)　　(S-All, kernel)

Full F<: 放宽为界可以**逆变**（子类型的界更宽、超类型的界更窄），量化体在更严的界下比较

Γ ⊢ T₁ <: S₁　　Γ, X<:T₁ ⊢ S₂ <: T₂ ⟹ Γ ⊢ (∀X<:S₁. S₂) <: (∀X<:T₁. T₂)　　(S-All, full)

理解两条规则的分野，可类比函数子类型的逆变（T5.1.4）。一个 ∀X<:S₁. S₂ 的多态值要"顶替"一个 ∀X<:T₁. T₂ 来用时，别人会拿一个满足界 T₁ 的类型来实例化它，所以它自己的界 S₁ 必须**更宽松**（T₁ <: S₁，接受得更多才安全）——这就是 Full 版参数位（界）逆变的由来，和函数参数逆变同源。kernel 版则干脆规定"界必须一字不差相同"，回避了比较界的问题。

为什么要保留更弱的 kernel 版？因为表达力换来了可判定性。Full F<: 明显更能表达"界也能变宽"的子类型关系，但正是这条逆变界规则让子类型判定变得不可终止乃至不可判定（T9.3 详述）；kernel 版牺牲这点表达力，换来子类型判定必然终止（T9.2.4）。一个能一眼看出差别的例子：无界量化 ∀X. T 在 F<: 里是 ∀X<:Top. T 的缩写，那么在 Full F<: 中 ∀X<:Top. T 可以是任何 ∀X<:S. T（同体）的子类型（因为 S <: Top 恒成立，界逆变允许把界从 Top 收窄到 S）；而在 kernel F<: 中，∀X<:Top. T 只能与另一个界同为 Top 的量化类型比较，不能自动成为界更窄者的子类型。初学者记住一句：**kernel = 界必须相等；full = 界可逆变、更强但会失去可判定性**。名字来源也有帮助——"kernel"（内核）取自 Cardelli & Wegner 1985 的语言 Fun 的"kernel"子集，是历史上最早、最保守的定义；Full 版的逆变界规则由 Curien 与 Ghelli 提出。

### T9.1.5 无界量化是缩写；与 Rust trait bound / F-bounded 的关联

有界量化把 System F 的普通全称类型**吸收为特例**：无界量化就是"上界为 Top 的有界量化"

∀X. T　　≜　　∀X<:Top. T

因为一切类型都 <: Top，界为 Top 等于"不加约束"，于是纯 System F 可视为 F<: 里所有界都取 Top 的退化情形。

这一点让 F<: 成为把"约束式多态"讲清楚的理论母体，直接对应工程语言里的**有界泛型 / trait bound**。Rust 的 `fn f<T: Ord>(x: T)`、Java 的 `<T extends Comparable>`、Scala 的 `[T <: Ordered[T]]`，本质都是"给类型参数 T 加一个上界/约束，函数体内即可使用该约束提供的操作"——正是 ∀X<:界 的工程化身。需要点明一个**易错的口径差异**（点名不展开，工程细节见 L5-14 R6.3 trait bound）：F<: 的界是**子类型上界**（X 是某个具体类型 T 的子类型），而 Rust 的 `T: Trait` 是**约束/谓词界**（T 实现了某 trait），二者是近亲但不完全等同——Rust 没有 Java/F<: 意义上的名义子类型 `<:`，它用 trait 约束表达"T 具备哪些能力"。此外，真实 OO/泛型里常见的自指界如 `<T extends Comparable<T>>`（界里出现被约束的 T 本身），属于 F<: 的一个扩展叫 **F-bounded quantification**（∀X<:F[X]，Canning 等 1989），本课的 F<: 是不含自指的基本版；点名以备将来对齐，不在此展开。

## T9.2 F<: 元理论与算法

### T9.2.1 类型安全：Progress + Preservation

F<:（kernel 与 full 皆然）是**类型安全**的：满足进展（Progress）与保型（Preservation）两定理（TAPL §26.4）。

进展：良类型的封闭项要么是值、要么能再走一步求值

若 ⊢ t : T，则 t 是值 或 存在 t′ 使 t → t′

保型：求值一步不改变（准确说不扩大）类型

若 Γ ⊢ t : T 且 t → t′，则 Γ ⊢ t′ : T

理解这两条与 T3（STLC 安全性）、T8（System F）是同一套路的延续：安全性 = 进展 + 保型，合起来说"良类型程序不会卡住（不会到达既非值又无法求值的‘出错’状态）"。有界量化没有改变这个大结论，它带来的新求值规则只是 System F 那两条的有界版——类型应用遇到类型抽象时做类型层的 β 归约

(λX<:T₁₁. t₁₂) [T₂] → [X↦T₂] t₁₂　　(E-TappTabs)

**加了子类型和界之后，安全性证明变难了但结论不变**。变难的地方在于证明保型时要处理 T-Sub（包容规则可以插在推导任意处），需要"反演（inversion）引理"把 subsumption 剥掉、看清底层真正的类型规则；这套技巧在 T5.2 处理子类型时已出现，F<: 只是把它扩展到类型抽象/应用上。安全性对 kernel 还是 full 都成立——kernel/full 的分野只影响子类型判定的可判定性（T9.3），不影响"程序不出错"这件事本身。

### T9.2.2 类型代换下子类型与类型保持

支撑 F<: 保型证明的核心引理，是"用一个满足界的类型去替换类型变量，子类型关系与类型判断都保持"（TAPL §26.4，type substitution lemmas）。子类型版本

若 Γ, X<:Q, Δ ⊢ S <: T 且 Γ ⊢ P <: Q，则 Γ, [X↦P]Δ ⊢ [X↦P]S <: [X↦P]T

配套的类型版本

若 Γ, X<:Q, Δ ⊢ t : T 且 Γ ⊢ P <: Q，则 Γ, [X↦P]Δ ⊢ [X↦P]t : [X↦P]T

T-TApp 做类型应用时，把函数体里的类型变量 X 全部替换成实参类型 T₂，并要求 T₂ <: T₁₁（满足界）。要证明"替换后仍良类型"（保型的关键一步），就得有一条引理保证——只要拿来替换的 P 满足原界 Q（P <: Q），那么原先在"X<:Q 假设下"成立的一切子类型/类型判断，替换后依然成立。直觉上这很自然："我原来只假设 X 是 Q 的某个子类型就能推出的结论，现在换成一个货真价实的 Q 的子类型 P，结论当然照样成立。" 这条引理是有界量化区别于无界 System F 的技术核心：无界版替换任意类型都行，有界版必须带着"P <: Q"这个前提，替换才安全。初学者不必记证明细节，记住它的角色即可——它是 T-TApp 这条规则"名正言顺"的保证书。

### T9.2.3 exposure 与 minimal typing

要把 F<: 的类型检查变成算法（可执行的判定过程），需要两个概念：暴露（exposure）与最小类型（minimal typing）（TAPL §28.1–§28.2）。暴露是"把一个类型里最外层的类型变量顺着它的界一路提升（promote），直到最外层不再是变量"

expose(Γ, X) = expose(Γ, Γ(X))　　（X 是变量，Γ(X) 是它的界）

expose(Γ, T) = T　　（T 最外层不是变量）

最小类型定理则说：F<: 里每个可定型的项都有一个**最小类型**（在 <: 意义下最小），算法只要算出这个最小类型即可。

理解这两者要连着 T5.2 的"算法式类型"来看。声明式类型系统里 T-Sub 可以插在任何位置，导致同一个项有无穷多类型、无法机械判定；解决办法是构造一个"语法制导"的算法式系统，让每个项算出唯一的最小类型，需要放宽处再显式检查子类型。exposure 在这里解决一个具体障碍：做函数应用 t₁ t₂ 的算法式类型检查时，要拿 t₁ 的类型的"箭头结构"（形如 T₁→T₂）出来，可 t₁ 的类型算出来可能是个类型变量 X（比如在多态函数体内）——这时就 expose 它：顺着 X 的界往上提，X 提到 Γ(X)，若还是变量继续提，直到露出真正的箭头类型为止。一句话：**exposure = "顺着界把变量翻译成它到底长什么形状"，是算法式类型检查在多态/有界场景下必备的一步**。初学者可把它类比成"查字典"——遇到不认识的抽象类型变量，就顺着它的界这条线索查到它至少是个什么结构。

### T9.2.4 kernel F<: 的算法式子类型：可判定

kernel F<: 的子类型关系可以改写成一套**语法制导、且保证终止**的算法式规则，因而**可判定**（TAPL §28.3）。与 T5.2 一样，先证明 S-Refl 与 S-Trans 在算法式系统里"可省（admissible）"，再给出如下按类型结构分派的规则

Γ ⊢ S <: Top　　(SA-Top)

Γ ⊢ X <: X　　(SA-Refl-TVar)

Γ ⊢ Γ(X) <: T ⟹ Γ ⊢ X <: T　　(SA-TVar，把变量提升到界再继续)

Γ ⊢ T₁ <: S₁　　Γ ⊢ S₂ <: T₂ ⟹ Γ ⊢ S₁→S₂ <: T₁→T₂　　(SA-Arrow)

Γ, X<:U₁ ⊢ S₂ <: T₂ ⟹ Γ ⊢ (∀X<:U₁. S₂) <: (∀X<:U₁. T₂)　　(SA-All，kernel，界相同)

理解"为什么可判定"的关键是终止性论证。算法读入一对类型 (S, T)，按 S 或 T 的形状唯一地选一条规则递归。除 SA-TVar 外，每条规则的子目标里类型都**严格变小**（比较箭头就比较更小的分量，比较量化类型就比较更小的体）；SA-TVar 把变量 X 换成它的界 Γ(X)，虽然界可能更大，但由于上下文有限、界的嵌套不能无限深，这一步只会发生有限次。综合起来递归必然终止 → 判定过程一定给出 yes/no → 可判定。这里最能体现 kernel 的价值：注意 SA-All 里两边界都是同一个 U₁，比较时只递归比较更小的体 S₂ 与 T₂，不产生任何"比较界"的新子目标——正是这一点保证了终止。对照下一节 Full 版就会看到，一旦允许界逆变、递归里冒出"比较界"的子目标，终止性立刻崩塌。初学者记住结论：**kernel F<: 的子类型和类型检查都可判定，是实现可用的系统。**

### T9.2.5 join 与 meet

kernel F<: 里，任意两个类型的**上确界（join，最小公共超类型）总存在**，而**下确界（meet，最大公共子类型）只部分存在**（TAPL §28.6）。

理解它为什么重要、以及为什么 join 全而 meet 缺，可类比 T5.2 记录子类型的同一现象。join 用在类型检查条件表达式这类"多分支要合成一个类型"的地方：`if b then t₁ else t₂` 的类型取 t₁、t₂ 两类型的 join。join 总存在的直觉是——最坏情况两个类型毫无共性，它们的公共超类型还有 Top 兜底，所以永远能往上找到一个最小公共超类型。meet（往下找最大公共子类型）则不然：两个没有公共子类型的类型，若语言里没有 Bot（最小类型），就根本不存在下确界，故只"部分存在"。§28.8 进一步讨论：给 F<: 加上 Bottom 类型后，meet 也能变得处处存在（Bot 兜底，正如 Top 兜住 join）。初学者抓一句即可：**join（合并分支类型用）总有，meet（求公共子类型用）要靠 Bot 才齐全**——这与 T5 子类型里的结论一脉相承，有界量化没有推翻它。

## T9.3 Full F<: 子类型不可判定性

### T9.3.1 Full 规则为何危险：界逆变让子目标"长回来"

Full F<: 不可判定的根子，是它那条允许界逆变的算法式量化子类型规则（TAPL §28.4）。把 T9.2.4 的 kernel SA-All 换成 full 版

Γ ⊢ T₁ <: S₁　　Γ, X<:T₁ ⊢ S₂ <: T₂ ⟹ Γ ⊢ (∀X<:S₁. S₂) <: (∀X<:T₁. T₂)　　(SA-All, full)

理解危险在哪：kernel 版比较两个量化类型时只递归比较更小的体（S₂ 与 T₂），子目标严格变小、必然见底；full 版却**多出一个子目标 T₁ <: S₁**——要比较两边的界，而且界的方向是反的。问题就出在这个"比较界"的子目标不保证变小：它把原来处在"界"位置的类型拽到"被比较类型"的位置上重新比较，配合替换，完全可能生成一个**不小于甚至大于原问题**的新子目标。递归不再单调下降，终止性论证（kernel 靠的那条）当场失效。这是"多一条前提、判定性全塌"的经典案例：规则表达力增强了，代价是算法可能永远转下去。

初学者可以先只抓这一层直觉：**kernel 递归只往‘体’里钻、越钻越小所以停得下来；full 还要回头比‘界’，而比界这一步能把问题重新养大，于是可能停不下来。**

### T9.3.2 发散的子类型查询（思路）

比"效率差"更强的第一个坏消息是：存在具体的上下文 Γ 与具体的一对类型，使 Full F<: 的**算法式子类型判定过程无限展开、永不返回**（TAPL §28.4 给出这样一个发散例；此类发散判断由 Ghelli 系统性构造）。

理解这个"发散例"的思路（按本课要求只讲思路、不铺完整构造）：精心挑选一个类型变量 X，让它的界本身是一个量化类型，且这个界的体里又用到 X。于是判定 X 的某个子类型问题时，SA-TVar 把 X 提升到它的界（一个量化类型），随即触发 SA-All（full）去比较界——而比较界又逆变地生成一个"结构和原问题同型、但把 X 换成了一个更复杂类型"的新子目标；新子目标重复同样的展开，产生又一个同型而更复杂的子目标……如此自我再生，算法在一串永不重复、越来越大的子目标之间无限循环。关键点只有一个：**逆变界规则让子问题能‘变形成自己的一个更大版本’，于是递归自我繁殖、不收敛。** 这一步只在 Full 出现，kernel 因界必须相同、根本没有"比较界"的子目标而绝不会发生。

初学者不必看懂具体类型，抓住机制即可：发散不是实现写得烂，而是规则本身允许问题自我放大。

### T9.3.3 不可判定性定理与归约思路

比"某个查询发散"更强的最终结论是：Full F<: 的子类型关系是**不可判定的**——不存在任何算法能对所有 Full F<: 子类型判断都正确地给出 yes/no（TAPL §28.5；原始证明见 Pierce《Bounded Quantification Is Undecidable》，POPL'92，期刊版 Information and Computation 112(1):131–165, 1994）。

理解"发散"与"不可判定"的区别很重要，是本节要点。上一节说的是"某个特定算法在某些输入上不停"——这本身还不排除"换个更聪明的算法就能判定"。不可判定性是更强的断言：**任何**算法都不行。证明的思路（只讲骨架）是把一个已知不可判定的问题**归约**到 Full F<: 子类型判定上——Pierce 的做法是把一类图灵完备的机器（两计数器机 / 一个等价的重写系统）的停机问题编码成 Full F<: 的子类型判断，使得"某台机器停机"当且仅当"对应的子类型判断成立"。既然停机问题不可判定，能判定 Full F<: 子类型就能判定停机问题，矛盾——故 Full F<: 子类型不可判定。

kernel 可判定且高效（T9.2.4）→ Full 的朴素算法在某些输入上发散（T9.3.2）→ Full 从根本上不可判定，没有任何算法能救（本节）。历史注记：这条不可判定性由 Pierce 1992/1994 证明，是类型系统设计史上一个著名的"表达力 vs 可判定性"反例。

### T9.3.4 工程后果与各系统的取舍

不可判定性不是纯理论玩具，它直接决定了真实类型系统该选哪一版（TAPL §26.6 Notes、§28.5）。因为编译器的类型检查器**必须终止**，任何以 F<: 为理论基础的语言都不能照搬 Full F<: 的完整子类型规则。常见做法有三种取舍：采用 kernel F<:（界相等，牺牲一点表达力换可判定）；采用某个可判定的受限变体；或在实现里对量化类型的子类型比较施加保守的近似/深度限制（宁可偶尔拒绝一个理论上成立的子类型，也不冒死循环的风险）。

理解这层的意义在于把 T9 收束回工程。它解释了为什么工业语言的泛型子类型规则往往看着"不够强"——不是设计者想不到更强的规则，而是更强的规则会让编译器可能不终止。这也回接 T9.1.5 的 Rust/Java 类比：这些语言的有界泛型在处理量化/高阶约束时都要做可判定性上的妥协。初学者带走一句总纲即可：**理论上更强的类型规则不一定能用；‘类型检查必须停机’是一条硬约束，Full F<: 的不可判定性就是它最有名的一次现身。**

## T9.4 有界存在与应用

### T9.4.1 有界存在类型 ∃X<:T

把 System F 的存在类型 ∃X.T（T8.4）也加上界，就得到**有界存在类型**（TAPL §26.5，§28.7）

{∃X<:T₁, T₂}

它打包一个"被隐藏的表示类型 X"和一个类型为 T₂（可提及 X）的值，但额外声明"这个隐藏类型 X 一定是 T₁ 的子类型"。配套的打包（pack）与解包（open/unpack）规则为

Γ ⊢ S <: T₁　　Γ ⊢ t₂ : [X↦S] T₂ ⟹ Γ ⊢ {*S, t₂} as {∃X<:T₁, T₂} : {∃X<:T₁, T₂}　　(T-Pack)

Γ ⊢ t₁ : {∃X<:T₁₁, T₁₂}　　Γ, X<:T₁₁, x:T₁₂ ⊢ t₂ : T₂ ⟹ Γ ⊢ (let {X,x}=t₁ in t₂) : T₂　　(T-Unpack)

理解它与普通存在类型的差别，全在解包时"客户端知道多少"。普通 ∃X.T 打包后，使用方 open 出来只知道"X 是某个类型"，对 X 一无所知（全隐藏）。有界 {∃X<:T₁, T₂} 解包后，使用方多知道一条 X <: T₁——虽然仍不知道 X 到底是哪个类型，但知道它至少是 T₁ 的子类型，因此可以对 X 类型的值使用 T₁ 提供的操作。对照 T-Pack：打包方必须证明它私藏的具体表示类型 S 确实满足界（S <: T₁），这条承诺才对使用方成立。初学者可以把它想成"带保证书的黑箱"——普通存在类型是"里面是什么完全不告诉你"，有界存在类型是"不告诉你具体是什么，但保证它至少支持 T₁ 这套接口"。

### T9.4.2 部分数据抽象 vs 全数据抽象

有界存在类型给出的是**部分数据抽象**，介于"完全暴露"和"完全隐藏"之间（TAPL §26.5；对照 Ch.24 普通存在类型的全数据抽象）。

理解这条谱系是 T9.4 的核心。回忆 T8.4：普通存在类型 ∃X.T 实现的是**全数据抽象**——模块把表示类型 X 彻底藏死，客户端只能通过模块导出的操作集与之打交道，连"X 大概长什么样"都不知道。这提供了最强的封装，但有时太严：客户端明明可以安全地对表示做一些通用操作，却因为完全不知道 X 是什么而被挡住。有界存在类型放开一道口子：声明 X <: T₁，客户端于是获得"对 X 用 T₁ 接口"的权利，同时表示的确切身份仍然保密。举例，一个"某种可比较元素的集合"模块可以导出 {∃X<:Comparable, ...}，客户端既不知道元素的具体类型、又能确定元素都可比较（可以排序）——这正是部分抽象的用武之地。初学者记住这条三段谱系即可：**完全暴露（具体类型）→ 部分抽象（有界存在：知道是某接口的子类型）→ 完全抽象（普通存在：什么都不知道）。** 界越松（越接近 Top）越接近全抽象，界越紧信息暴露越多。

### T9.4.3 有界存在可编码为有界全称

与普通存在类型能编码进全称类型（T8.4，Ch.24）一样，**有界存在类型也可编码进有界全称类型**，因此它不是必须新增的原语，而是可由 F<: 已有构造派生的（TAPL §26.5、§28.7）。编码沿用存在类型的 CPS 式思路

{∃X<:T₁, T₂}　≜　∀Y. (∀X<:T₁. T₂ → Y) → Y

一个有界存在包，本质等价于"一个只肯把内部（隐藏类型 X 及其上的值）交给‘任意结果类型 Y 的、能接受 X<:T₁ 的续延函数’去用的东西"。使用方想用这个包，就得提供一个对所有满足界 X<:T₁ 的 X 都成立的处理函数——这恰好把"表示类型隐藏、但保证 X<:T₁"翻译成了有界全称量化的语言。§28.7 从元理论上确认有界存在的性质（安全性、子类型）可由此编码继承，不必单独重证一套。初学者不必吃透编码细节，带走结论即可：**有界存在是有界全称的‘对偶包装’，理论上可互相翻译，工程上单列出来是为了写模块/抽象类型更顺手。**

### T9.4.4 案例：命令式对象 Redux 与部分抽象

有界量化最重要的一处应用，是给面向对象的对象/类系统一个更精确的类型（TAPL Ch.27「Case Study: Imperative Objects, Redux」）。它在 T5 的命令式对象编码（Ch.18）基础上，用有界量化（与有界存在）重做对象模型，主要为了处理**"self 类型"与继承下的类型保持**这类纯子类型办不好的场景。

理解它解决的痛点，正是 T9.1.1 那个"丢信息"问题在 OO 里的化身。当一个方法要返回"和自己同类型的对象"（self 类型，例如 `clone`、返回 self 以支持链式调用），纯子类型会把返回类型抹平成基类接口，子类调用后拿不回子类类型。用有界量化把对象/类的类型写成"对所有 X<:某接口"的形式，就能让"返回 self 类型"随实际子类被完整保留——这与 T9.1.1 用 ∀X<:{a:Nat}. X→X 保留记录全类型是同一招，只是搬到了对象上。Ch.27 同时用到有界存在做对象内部状态的部分抽象（隐藏实例变量的具体类型、只暴露其接口）。初学者抓住一条即可：**有界量化在 OO 里的杀手级用途，是让"方法返回与接收者同类型"这件事在子类型/继承下仍然类型正确**；这也正是 T9.1.5 提到的 F-bounded quantification（`<T extends Comparable<T>>` 那种自指界）在工程语言里流行的根本原因——OO 的 self 类型天然需要"界里提到自己"。对象完整机制交 L3-04 OOP，本节点名不展开。
