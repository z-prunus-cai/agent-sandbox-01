**N3（数据平面）讲"包到了路由器，查表往哪个口送"；N4（控制平面）讲"那张转发表是怎么被算出来、并在拓扑变化时被更新的"。** 数据面是每个包都要经历的快速动作（纳秒级、查表转发）；控制面是相对慢速的"后台大脑"，它跑路由算法、和别的路由器交换信息，把结果写进数据面的转发表。本篇先把路由抽象成图上的最短路问题（4.1），再讲两大类分布式路由算法——链路状态（4.2，OSPF）与距离向量（4.3，RIP，含著名的无穷计数陷阱）；然后升到跨自治系统的域间路由 BGP（4.4）；最后讲把控制面从每台设备里抽出来集中化的 SDN（4.5）与广播/多播路由（4.6）。

**路由要解决的是"求可达性、求最短路"，它和分布式共识（求多个节点对同一个值达成一致，属 L5-01）不是一回事，本篇绝不混谈。** 路由协议里"各节点最终算出一致的路由表"是收敛的副产物，靠的是重复交换局部信息而非投票达成单一决议；OSPF/RIP/BGP 都没有"多数派表决某个值"这一步。

本容器可用 Python 做算法侧的最小佐证（Dijkstra/Bellman-Ford 手写对拍），`ip route` 可看本机路由表；但容器内无真实多路由器拓扑，故 LS 泛洪、DV 收敛、BGP 邻居等**协议行为的实机验证未取**，相关结论以 Kurose 8E ch5 与对应 RFC 的多来源比对为承重，实机部分如实标注为可选/未取。

## 4.1 路由问题抽象与最短路

### 4.1.1 把路由抽象成带权图上的最小代价路径问题

路由的核心问题可以干净地抽象成一个图论问题：**把网络画成一张图，路由器（和网络）是节点，直连链路是边，每条边有一个代价（权重）；路由就是为每一对源-目的节点，找出一条总代价最小的路径。** 这是 Kurose 8E ch5 开篇给路由算法下的统一定义，也是 OSPF、RIP 等协议底下真正在算的东西。

用图记号说，网络是图

G = (N, E)

其中 N 是节点集合、E 是边集合；每条边 (x, y) ∈ E 有代价 c(x, y)。一条从源到目的的路径的代价是路径上所有边代价之和，路由算法要找的就是**最小代价路径（least-cost path）**；当所有边代价都取 1 时，最小代价路径就退化成**最短路径（跳数最少）**。

对初学者要点明"代价"到底是什么：它是**人为配置或按规则算出的一个数**，不是物理定律。常见取法有「每跳记 1」（于是最小代价=最少跳数，RIP 就这么干）、按链路带宽反比取值（带宽越大代价越小，OSPF 默认这么干）、或按时延/负载取值。谁来设这些代价、代价设得好不好，直接决定路由走哪条路——这也是为什么同一张物理网络换一套代价配置，流量走向就完全不同。记住这层"代价是可调旋钮"的性质，后面 BGP 的"策略路由"（4.4）本质上就是把"最短"换成了"最合我方利益"。

### 4.1.2 两种经典最短路算法：Dijkstra 与 Bellman-Ford

图上的最小代价路径有两个教科书级算法，它们恰好对应网络里两大类路由协议，所以必须先认清。

第一个是 **Dijkstra 算法**，它是一个**全局（global）算法**：要求算的人手里有整张图的完整信息（所有节点、所有边、所有代价），然后从源点出发、每轮"敲定"一个当前已知最近的节点，逐步把最短路树长满。它对应**链路状态（Link-State）路由**（4.2）——每个路由器先设法拿到全网拓扑，再本地跑 Dijkstra。Dijkstra 的核心是一步"松弛"更新，对每个尚未敲定的邻居 v：

D(v) = min( D(v), D(w) + c(w, v) )

其中 w 是本轮刚敲定的节点、D(v) 是源到 v 当前已知的最小代价。

第二个是 **Bellman-Ford 算法**，它是一个**分散式（decentralized / distributed）算法**：不需要谁掌握全图，每个节点只和**直接邻居**交换"我到各目的地的当前估计代价"，反复迭代直到不再变化。它对应**距离向量（Distance-Vector）路由**（4.3）——RIP 就是它的工程化。Bellman-Ford 的分布式形式是这条递推（Kurose 称之为距离向量的 Bellman-Ford 方程）：

d_x(y) = min_v { c(x, v) + d_v(y) }

x 到 y 的最小代价，等于"遍历 x 的每个直连邻居 v，取（x 到 v 的直连代价 + v 声称的它到 y 的最小代价）之和"里最小的那个。

初学者最该抓住的对比是"信息掌握程度"这条轴：**Dijkstra 要先知道全局才能算，Bellman-Ford 只靠邻里传话就能算。** 这不是谁更聪明，而是两种工程取舍——全局算法算得准、收敛干脆，但要先把全网拓扑散播到每个节点（泛洪，见 4.2）；分散式算法省去泛洪、天然适合"没人有全局视角"的大网，但迭代式传话在拓扑变坏时会闹出"无穷计数"这类毛病（见 4.3）。这条对比是理解 4.2 与 4.3 全部差异的总纲。

### 4.1.3 静态 vs 动态、全局 vs 分散：给路由算法分类

除了 4.1.2 的"全局 vs 分散"，路由算法还常按"是否随网络状态自动变"分为两类：**静态路由**由管理员手工配死，除非人去改否则不动；**动态路由**由协议根据拓扑/代价变化自动重算（OSPF/RIP/BGP 都是动态的）。还有一条次要轴是"是否负载敏感"：多数现代协议是**负载不敏感**的（链路代价不随实时流量抖动，以免路由震荡），Kurose 8E 明确指出今日 Internet 路由协议（RIP/OSPF/BGP）基本都是负载不敏感的。

对初学者，这里最容易和 N3 混的一点要再强调：**"路由（routing）"和"转发（forwarding）"是两件事。** 转发是数据面的局部动作——包到了，查转发表，从某个输出口送走，只关心"这一台设备这一步往哪送"；路由是控制面的全局过程——通过算法算出"整条路怎么走"，其产物才是那张转发表。一个比喻：转发是"到了路口看路牌右转"，路由是"出发前规划整条行车路线并把每个路口该怎么拐都算好"。本篇 4.2 起讲的全是"怎么规划"这一半。

再点一句防重：**这里的"各路由器最终算出彼此一致的路由表"是收敛，不是共识。** 收敛靠的是所有节点看到同一份拓扑/距离信息后各自独立算出同样结果，没有"表决某个提议值"的环节；共识（Paxos/Raft，L5-01）要在可能失败、可能冲突的提案里选定唯一值，问题结构完全不同。别把路由收敛套进 CAP 或共识框架去谈。

#### 来源与时效
- Kurose & Ross 8E ch5 §5.2「Routing Algorithms」：把路由定义为图 G=(N,E) 上的最小代价路径问题；给出全局(LS)/分散(DV)、静态/动态、负载敏感/不敏感的分类，以及 Dijkstra 与分布式 Bellman-Ford 方程。核实 2026-07-29。
- CLRS《算法导论》单源最短路章（Dijkstra、Bellman-Ford）：作为算法正确性/复杂度的第二独立来源，交叉核对松弛式与 Bellman-Ford 递推形式。核实 2026-07-29。
- 本机可选实证（Python 手写 Dijkstra/Bellman-Ford 对拍同一带权图，验证两算法给出相同最短路代价）：环境具备，属加固算法侧结论；协议侧行为无关，未逐项跑。
- 分账/防重：路由=求最短路/可达性 ≠ 分布式共识（L5-01）；路由(控制面) ≠ 转发(数据面 N3)。

## 4.2 链路状态路由（OSPF）

### 4.2.1 链路状态算法：全网泛洪拓扑 + 各自本地跑 Dijkstra

**链路状态（Link-State, LS）路由**的思路是"先让每个节点都拿到整张地图，再各自算路"。具体分两步：第一步，每个路由器测出自己到各直连邻居的链路代价，打包成一条**链路状态通告（Link-State Advertisement, LSA）**，通过**泛洪（flooding）**发给网络里所有其它路由器；第二步，每个路由器收齐全网的 LSA、拼出一张完全相同的**链路状态数据库（LSDB，即全网拓扑图）**，然后各自本地跑 **Dijkstra 算法**算出以自己为根的最短路树，据此填转发表。

**因为所有路由器最终持有同一份全网拓扑，它们各自独立跑 Dijkstra 会得到彼此一致的路由结果。** 这就是 LS 的"全局算法"本色——把全局信息复制到每个节点，从而把一个全局问题变成每个节点的本地计算。

对初学者，用"发地图"的比喻最直观：每个路由器只知道自己周边一小块（我连了谁、每条边多贵），它把这一小块广播出去；全网互相广播后，每个人手里都拼出了同一张完整地图；有了完整地图，各自用 Dijkstra 规划从自己出发的最优路线即可。这里"泛洪"是 LS 的命脉也是代价——它保证信息扩散到每个角落，但也意味着拓扑一变就要重新泛洪、全网重算。

### 4.2.2 泛洪、LSDB 同步与收敛

泛洪的可靠性由协议保证：每条 LSA 带序号和寿命（age），路由器收到新 LSA 就转发给除来源外的所有邻居、并存进 LSDB；收到旧的或重复的就丢弃。这样一条 LSA 能可靠、无环地铺满全网，让所有 LSDB 收敛到一致。当某条链路 up/down 或代价改变，相关路由器发出新 LSA 触发**增量泛洪**，各节点更新 LSDB 后重跑 Dijkstra——这一过程叫**重新收敛（re-convergence）**。

LS 也有它的烦恼，最典型的是**路由震荡（oscillation）**：如果链路代价被设成随流量负载变化（负载敏感），那么大家算出最优路后一起涌上去，反而让原本便宜的链路变贵、下一轮又一起逃离，路由来回抖。这正是 4.1.3 说"现代协议倾向负载不敏感"的原因之一。另一个开销点是：LSDB 要存全网拓扑、泛洪有通信开销、Dijkstra 有计算开销，网络越大越吃紧——OSPF 用"分区域"来缓解（见 4.2.3）。

### 4.2.3 OSPF：链路状态路由的工程实现

**OSPF（Open Shortest Path First）** 是 Internet 域内（一个自治系统内部）最主流的链路状态路由协议，一手规范是 **RFC 2328「OSPF Version 2」(J. Moy, 1998-04)**（用于 IPv4）；IPv6 版本是 **OSPFv3，RFC 5340**。"Open"指它是开放标准（相对于早年 Cisco 私有的 IGRP/EIGRP），"SPF"即 Dijkstra 最短路优先。OSPF 就是把 4.2.1–4.2.2 的 LS 机制标准化：路由器间泛洪 LSA、维护 LSDB、跑 Dijkstra。

OSPF 有几个必知的工程特性。其一，**分层/分区域（areas）**：一个大的 OSPF 域可切成多个区域，区域内做完整 LS、区域间只交换汇总信息，这样把"全网泛洪+全网 Dijkstra"的规模压到区域内，是它能扩展到大型企业网的关键；所有区域都要连到编号 0 的**骨干区域（backbone area, area 0）**。其二，**支持带认证的消息**，防止伪造 LSA 污染路由。其三，OSPF 直接跑在 IP 之上（协议号 89），不经 TCP/UDP。OSPF 属于**内部网关协议（IGP）**——用于 AS 内部；AS 之间的路由交给 BGP（4.4）。

对初学者，把 OSPF 记成"LS 算法 + 分区域扩展 + 认证 + 直接跑在 IP 上的一套标准打包"即可。教学上不必背 LSA 的具体字段，重点是理解它和 4.3 的 RIP 是两条完全不同的技术路线：OSPF 靠"每人拿全图各自算"，RIP 靠"只跟邻居传距离"。

#### 来源与时效
- Kurose & Ross 8E ch5 §5.3「Intra-AS Routing in the Internet: OSPF」：LS 算法（泛洪+Dijkstra）、路由震荡、OSPF 作为 IGP、区域/骨干区域、认证、直接跑在 IP 上等特性。核实 2026-07-29。
- RFC 2328「OSPF Version 2」(J. Moy, 1998-04)：OSPFv2 的权威规范（LSA 泛洪、LSDB、区域）。RFC 5340 为 OSPFv3（IPv6）。核实 2026-07-29（RFC Editor 与 IETF Datatracker 二源交叉，编号与标题一致）。
- 冲突/口径：OSPFv2(RFC 2328) 用于 IPv4、OSPFv3(RFC 5340) 用于 IPv6，分账清楚；本节 LS 通用机制以 Kurose 为教材锚、协议编号以 RFC 为一手锚。
- 实机说明：容器无多路由器拓扑，OSPF 泛洪/收敛未实机验证（未取），结论以教材+RFC 承重。

## 4.3 距离向量路由（RIP）与无穷计数

### 4.3.1 距离向量算法：只跟邻居交换"我到各处多远"

**距离向量（Distance-Vector, DV）路由**与 LS 相反，是彻底的分散式算法：**没有任何节点掌握全网拓扑，每个节点只维护一张"到各目的地的最小代价估计"表（即距离向量），并周期性地把这张表发给它的直连邻居；收到邻居的向量后，用 Bellman-Ford 方程更新自己的向量，如此反复直到收敛。** 它是 4.1.2 那条分布式 Bellman-Ford 方程

d_x(y) = min_v { c(x, v) + d_v(y) }

的直接工程化：节点 x 对每个目的地 y，把"到邻居 v 的直连代价 + 邻居 v 报来的它到 y 的代价"逐个邻居算一遍取最小，并记下取到最小值的那个邻居作为**下一跳**。

DV 的迭代是"异步、分布、自终止"的：每个节点在自己的向量变化时才需要通知邻居，一有更新就可能触发邻居再更新，像涟漪一样扩散；当没有节点的向量再变时，全网收敛。

对初学者，用"传口信"比喻：没人有地图，每个村子只对邻村喊"我到城里要走 5 里""我到码头要走 3 里"；邻村听到后加上"我到你村的距离"，更新自己到城里/码头的估计，再喊给它的邻村。消息一圈圈传开，最终每个村子都算出了到各地的最短距离和"该往哪个邻村走"。这套机制省掉了泛洪全图，但它的软肋也正埋在"只信邻居的转述、看不到全局"里——见 4.3.2。

### 4.3.2 无穷计数问题：好消息传得快，坏消息传得慢

DV 的著名毛病是**无穷计数（count-to-infinity）**：当某条链路断掉、某目的地变得更远或不可达时，坏消息会在节点间**极其缓慢地、一次加一点点地**传播，代价估计一路缓慢爬升，需要很多轮才能爬到"无穷"（表示不可达）才停。Kurose 把这总结成一句口诀：**"good news travels fast, bad news travels slow"（好消息传得快，坏消息传得慢）。**

根因是 DV 节点看不到全局、无法分辨"邻居报来的路是不是绕经了我自己"。设直线拓扑 A—B—C，各链路代价 1，目的地是 C：

```
正常时：  B 到 C = 1（直连）；A 到 C = 2（经 B）
链路 B—C 断：
  B 发现直连 C 没了，但 A 还在报 "我到 C = 2"
  B 误信 A，算出 "我到 C = 1 + 2 = 3"（其实 A 的那条路是 A→B→C，已经断了！）
  B 报给 A："我到 C = 3" → A 更新 "我到 C = 1 + 3 = 4"
  A 报给 B → B 变 5 → A 变 6 …… 两人你加一我加一，缓慢爬向无穷
```

这就是"互相踢皮球"：A 和 B 各自以为对方有一条通往 C 的好路，实际那条路正是经过自己、且已经断了。它们看不到这个环，只能靠代价一点点涨到约定的"无穷"值才明白 C 不可达。

### 4.3.3 缓解手段：水平分裂与毒性逆转

为压制无穷计数，DV 协议用两招启发式。**水平分裂（split horizon）**：一个节点**不把"某目的地的路由"再发回给它用来到达该目的地的那个下一跳邻居**——既然我到 C 是经过你 B 的，我就不该回头告诉你"我也能到 C"，免得你误以为我有独立的路。**毒性逆转（poison reverse）** 是加强版：不仅不回传，而是**主动回传一个"无穷"**告诉那个邻居"从我这儿到 C 是不可达的（别经我）"，把误解直接毒杀。

用记号表示毒性逆转：若 A 经 B 到达 C，则 A 向 B 通告

d_A(C) = ∞

（而向其它邻居仍如实通告真实距离）。

对初学者要老实说清一个易错点：**这两招治标不治本。** 它们能解决上面那种"两个节点互踢"的简单环路，但对**三个或更多节点构成的环路**无能为力——坏消息仍可能绕着大环慢慢爬。这也是 DV 相对 LS 的结构性劣势：LS 靠全局拓扑天然不会产生这种"看不见的环",而 DV 只能用启发式打补丁。所以现代大型域内网络多用 OSPF（LS），RIP（DV）主要留在小型或教学场景。

### 4.3.4 RIP：距离向量路由的工程实现

**RIP（Routing Information Protocol）** 是最老牌的 DV 路由协议，一手规范是 **RFC 2453「RIP Version 2」(G. Malkin, 1998-11)**（RIPv2，加了子网掩码/CIDR 支持；RIPv1 是 RFC 1058）。RIP 的几个数字要点：**代价就是跳数（hop count，每跳记 1）**；**最大有效跳数 15，跳数 16 即表示"无穷/不可达"**——这个刻意设得很小的"无穷"正是为了让无穷计数尽快触顶收敛（它变相限制了 RIP 只能用于直径不超过 15 跳的网络）。RIP 路由器**默认每 30 秒**向邻居广播一次自己的距离向量（RIPv2 承载在 UDP 端口 520 上）；若一段时间（默认 180 秒）没收到某邻居的更新，就认为该邻居/路由失效。

RIP = "跳数当代价 + 16=无穷 + 每 30 秒传一次向量 + 水平分裂/毒性逆转防环"的一套 DV 打包。它简单、易配、适合小网；缺点是收敛慢、有无穷计数隐患、且"16 跳封顶"限制了网络规模。把它和 OSPF 摆一起，就是 DV 与 LS 两条路线在真实协议里的化身。这里"16=无穷""30 秒周期"等数值取自 RFC 2453 与 Kurose 对齐，非凭记忆填。

### 4.3.5 链路状态 vs 距离向量：一张对照

把 4.2 与 4.3 收束成一组对照，便于初学者建立总图：

```
维度            链路状态 LS (OSPF)          距离向量 DV (RIP)
掌握的信息      全网拓扑(LSDB)             仅自己到各目的地的距离+邻居转述
交换什么        LSA(本地链路状态)泛洪全网  整张距离向量,只发给直连邻居
算法            本地 Dijkstra              分布式 Bellman-Ford 迭代
收敛速度        快、干脆                   慢,有无穷计数
坏消息          天然无隐藏环               "传得慢",需水平分裂/毒性逆转补
消息量/存储     泛洪开销大,存全图          只与邻居交换,存 O(邻居×目的)
健壮性          一个坏 LSA 影响有限         错误距离会沿链传播扩散
典型规模        大型域内(分区域扩展)       小型网络
```

这两条路线没有绝对优劣，是不同权衡：LS 用"泛洪换全局视野、换快速无环收敛"，DV 用"只和邻居传话换低开销，代价是慢收敛和环路隐患"。理解这组权衡，比记住任何单个协议字段都重要。

#### 来源与时效
- Kurose & Ross 8E ch5 §5.2.2「The Distance-Vector (DV) Routing Algorithm」与 §5.3.1「RIP」：分布式 Bellman-Ford、无穷计数、"good news fast / bad news slow"、水平分裂/毒性逆转（及其对三节点环无效）、RIP 跳数/16=无穷/30 秒周期。核实 2026-07-29。
- RFC 2453「RIP Version 2」(G. Malkin, 1998-11)：RIP 权威规范（跳数度量、infinity=16、定时器、UDP/520）；RFC 1058 为 RIPv1。核实 2026-07-29（RFC Editor 与 IETF Datatracker 二源交叉编号/标题）。
- 冲突/待核：水平分裂与毒性逆转能否完全消除环路——教材立场一致（不能，仅解简单两节点环），无冲突。RIP 各定时器默认值以 RFC 2453/Kurose 为准。
- 本机可选实证（Python 模拟 A—B—C 断链后的 DV 迭代，复现代价缓慢爬升）：算法侧可跑加固，属可选，未逐项落稿；协议实机（真实 RIP 收敛）未取。

## 4.4 域间路由 BGP

### 4.4.1 自治系统与"域内/域间"分账

真实的 Internet 不是一张扁平大图，而是**上万个自治系统（Autonomous System, AS）** 拼起来的"网络的网络"。一个 AS 是**同一行政/技术管辖下的一组路由器**（一家 ISP、一所大学、一个大公司），有唯一的 **AS 号（ASN）**。路由因此分成两层：**AS 内部**用**内部网关协议（IGP）**，如 OSPF（4.2）或 RIP（4.3）；**AS 之间**用唯一的**外部网关协议——BGP（Border Gateway Protocol）**，一手规范 **RFC 4271「A Border Gateway Protocol 4 (BGP-4)」(2006-01)**，人称"把整个 Internet 粘在一起的胶水"。

为什么域间不能沿用 OSPF/RIP？两个根本原因。**规模**：让全 Internet 每台路由器都持有全球拓扑跑 Dijkstra（LS）或传全球距离向量（DV）都不现实。**策略（policy）**：AS 之间是有商业关系的（谁给谁付费转接、谁和谁对等免费互换流量），一个 AS 想控制"我的流量走谁家、我愿意帮谁转发"——这不是"最短路"能表达的，需要**基于策略而非纯代价**的路由。这两点决定了域间路由是另一套逻辑。

### 4.4.2 BGP 是路径向量协议：AS-PATH 与无环

BGP 属于**路径向量（path-vector）协议**——它是距离向量的变体，但传的不只是"距离"，而是**到达某个目的前缀所要经过的完整 AS 序列（AS-PATH）**。一条 BGP 路由通告大致是"目的前缀 + AS-PATH + 下一跳 + 其它属性"。

带上完整 AS-PATH 有两大好处。其一，**天然防环**：一个 AS 收到一条通告，若发现自己的 ASN 已经出现在 AS-PATH 里，就知道这是绕回来的、直接丢弃——这一招干净地根除了 4.3.2 那种 DV 无穷计数问题（DV 只传数字看不见路径，BGP 传出了完整路径就能识别环）。其二，**AS-PATH 长度可作粗略的"距离"参考**（经过的 AS 越少通常越好），同时它承载了策略判断所需的路径信息。

把 BGP 想成"传的是路线清单而不是只报里程数"。DV 只说"我到那儿要 5 里"（看不出这 5 里绕没绕经过你），BGP 说"我到那儿的路线是 经过 AS3→AS7→AS9"——一看清单就知道有没有把自己绕进去，也能按清单里的 AS 是敌是友做取舍。

### 4.4.3 eBGP 与 iBGP

BGP 会话分两种。**eBGP（external BGP）** 跑在**不同 AS 的边界路由器之间**，用来学习"从别的 AS 能到达哪些前缀"。**iBGP（internal BGP）** 跑在**同一个 AS 内部的路由器之间**，用来把 eBGP 学到的外部路由信息**散播到本 AS 内部所有路由器**，让 AS 内部对"去往外部某前缀该从哪个边界出去"达成一致。

初学者常把 iBGP 和 IGP（OSPF/RIP）搞混，要分清：**IGP 负责"AS 内部各路由器之间怎么互相到达"（内部拓扑最短路）；iBGP 负责"把外部（域间）路由信息在 AS 内部传开"。** 两者并存、各管一段——一个包要出 AS，先靠 iBGP 知道"该去哪个边界路由器出境"，再靠 IGP 知道"到那个边界路由器在内部怎么走"。BGP 会话本身承载在 **TCP（端口 179）** 上，靠 TCP 保证可靠有序传递路由更新。

### 4.4.4 策略路由与路径属性

BGP 选路的灵魂是**策略**，不是最短。每条 BGP 路由带一组**属性**，路由器按一套优先级规则从多条候选路由里选一条装进转发表。教学层面要认识几个关键属性（字段细节不必背）：**AS-PATH**（经过的 AS 序列，防环+粗略距离）；**NEXT-HOP**（下一跳 IP）；**LOCAL-PREF（本地优先级）**——AS 内部策略偏好，值越高越优先，是表达"我更想走哪条"的主力旋钮；**MED（多出口判别）**——建议邻居 AS"进我这儿请走哪个入口"。

BGP 路由选择的简化流程是：**先比 LOCAL-PREF（策略优先），再比 AS-PATH 长度（短者优），再按其它属性打破平局。** 注意 LOCAL-PREF 排在 AS-PATH 之前——这正说明 **BGP 首先服从策略/商业意图，其次才考虑"路径短"**，和域内"一切为最短路"的取向截然不同。

对初学者，用商业直觉理解就通了：一个 ISP 宁愿让流量走"付费更少或有对等协议"的邻居，哪怕那条路 AS 跳数多一点——省钱/守约比省一跳更重要。所以域间路由的"最优"是**经济与政策意义上的最优**，不是图论最短路。这也是为什么 Internet 上两点间的实际路径常常不是地理或跳数最短的。

#### 来源与时效
- Kurose & Ross 8E ch5 §5.4「Routing Among the ISPs: BGP」：AS 概念、eBGP/iBGP、路径向量与 AS-PATH 防环、NEXT-HOP/LOCAL-PREF/MED 属性、"策略优先于最短路"的选路流程、BGP 跑在 TCP/179。核实 2026-07-29。
- RFC 4271「A Border Gateway Protocol 4 (BGP-4)」(Rekhter/Li/Hares, 2006-01)：BGP-4 权威规范（路径属性、AS-PATH、基于 TCP 的会话）。核实 2026-07-29（RFC Editor 与 IETF Datatracker 二源交叉编号/标题）。
- 分账/防重：BGP 用路径向量+AS-PATH 根除 DV 无穷计数环路；iBGP(散播外部路由) ≠ IGP(内部拓扑最短路)，二者并存。BGP 选路属"策略优化"非"最短路优化"。

## 4.5 SDN 与控制/数据面分离

### 4.5.1 传统路由器的控制面与数据面耦合，SDN 把它们拆开

传统路由器是**控制面与数据面捆在同一台设备里**：每台路由器既跑路由算法（OSPF/BGP 等控制面逻辑），又用算出的转发表做转发（数据面）；全网的"路由智能"分散在成千上万台自治设备中，靠协议互相协调。**软件定义网络（SDN, Software-Defined Networking）** 的核心思想是**把控制面从每台设备里抽出来、集中到一个（逻辑上）中央的软件控制器**，交换机/路由器退化成"只管按下发的规则转发"的哑数据面设备。

这就是"**控制面与数据面分离（control-data plane separation）**"：数据面（交换机）负责快速的 match-action 转发，控制面（控制器）负责"算规则、下发规则"。控制器有全网视野、用通用服务器上的软件实现路由逻辑，通过一个标准协议把转发规则装进各交换机。

传统网络像"每个路口都有一个自己拿主意的交警，交警之间靠对讲机协调"；SDN 像"所有路口的信号灯统一接到一个中央调度室，调度室根据全局路况直接给每个路口下指令，路口设备只管执行"。集中化带来的好处是**全局视野下更灵活、可编程的流量工程**，坏处是控制器的可扩展性与可靠性成了新焦点（通常做成逻辑集中、物理上多副本）。

### 4.5.2 OpenFlow 与 match-action 流表

控制器与交换机之间"下发转发规则"的经典协议是 **OpenFlow**（由 Open Networking Foundation, ONF 标准化）。交换机里维护一张或多张**流表（flow table）**，每条流表项是一组"**匹配-动作（match-action）**"规则：

```
流表项 = 匹配字段(match) → 动作(action) [+ 计数器]
  匹配可跨多层：入端口、源/目的 MAC、以太类型、VLAN、
                源/目的 IP、IP 协议、TCP/UDP 端口 …
  动作：转发到某端口 / 泛洪 / 送控制器 / 丢弃 / 改写头部字段 …
```

一个包进交换机，按流表规则匹配、执行对应动作；匹配不到的包可以"送控制器"由控制器决定并可能下发新流表项。这套 match-action 抽象比传统"只按目的 IP 最长前缀匹配"强大得多——它能**跨层匹配（二层 MAC、三层 IP、四层端口一起看）**，因此同一台 OpenFlow 交换机可以被编程成路由器、交换机、防火墙或负载均衡器。Kurose 8E 称之为"**通用转发（generalized forwarding）**"，是相对 N3 传统"基于目的地转发"的推广。

### 4.5.3 成熟度与状态（⚙演进快）

SDN/OpenFlow 属演进较快、生态变动明显的领域，成熟度要如实标：**OpenFlow 协议最新版本为 1.5.1**（ONF 规范）；**ONF（Open Networking Foundation）已于 2023-12 并入 Linux Foundation**，OpenFlow 规范仍在 Linux Foundation/ONF 名下维护可获取。这些是版本/组织事实，标注锚版本与核实日期，随时可能变。

SDN 是**真实且已大规模落地**的技术（大型数据中心、云骨干网内部广泛使用集中式控制来做流量工程），但"OpenFlow 一统天下"并未发生——业界还有 P4（可编程数据面语言）、各家私有控制器/协议、以及基于 BGP 的传统方案并存。所以本节把 SDN 当作"控制面集中化"这一**架构思想**来学最稳妥，具体协议（OpenFlow 版本、控制器实现）当作会变的实现细节看待。这里的版本/组织信息取自 ONF 规范页与相关条目的二源交叉，非凭记忆。

## 4.6 广播与多播路由（可选）

### 4.6.1 广播路由：从"送给所有节点"到受控泛洪

前面 4.1–4.5 都在解决**单播（unicast）**——一个源到一个目的。**广播路由**要解决"把一个包送给网络里**所有**节点"，**多播路由**解决"送给**一组**感兴趣的节点"。本节为查全补位，作概念性覆盖。

广播最朴素的做法是**泛洪（flooding）**：每收到一个包就往除来路外的所有口复制转发——但天真泛洪在有环拓扑里会导致包无限增殖（广播风暴）。工程上用两招控制：**序号控制泛洪**（节点记住已转发过的包序号，重复的丢弃）与**反向路径转发（Reverse Path Forwarding, RPF）**——只有当包**从"本节点通往源的最短路径上的那个上游接口"进来**时才转发，否则丢弃，从而避免重复与环路。更省的是构造一棵覆盖所有节点的**生成树（spanning tree）**，广播只沿树边走，每个节点恰好收到一份。

### 4.6.2 多播：组地址与分发树

多播的关键抽象是**多播组（multicast group）**：用一个**组地址**（IPv4 里是 D 类地址 224.0.0.0/4）标识一组接收者，源把包发给这个组地址，网络负责复制并送达所有当前加入该组的成员——**源不需要知道有谁、有多少接收者**。这天然适合"一对多"场景（直播、软件分发、路由协议自身的组播通告）。

多播路由的核心是构造**分发树（distribution tree）**，让包沿树被复制、每条链路最多传一份。两大类树：**基于源的树（source-based tree）**——为每个源单独建一棵以它为根、通往所有组成员的最短路树（常用 RPF 构造），送达快但每源一棵、状态多；**共享树（shared/group-shared tree）**——全组共用一棵以某"汇聚点（rendezvous point）"为根的树，所有源都先把包送到汇聚点再沿树散发，状态省但路径未必最优。这是"每源建树的低时延"与"共享树的低状态"之间的经典权衡。

### 4.6.3 IGMP 与多播路由协议

多播分两段协作。**IGMP（Internet Group Management Protocol）** 管**主机与它直连的路由器之间**——主机用 IGMP 告诉本地路由器"我要加入/退出某多播组"，路由器据此知道自己下面挂着哪些组的成员（IGMPv3 = RFC 3376，IGMPv2 = RFC 2236）。**多播路由协议**管**路由器与路由器之间**——在网络内部构造并维护 4.6.2 的分发树，代表性协议是 **PIM（Protocol Independent Multicast）**，分 PIM-SM（稀疏模式，用共享树+汇聚点）与 PIM-DM（密集模式，用基于源的树），早期还有 DVMRP。

把这两段记成"**IGMP 是主机对本地路由器喊'我要看这个频道'，多播路由协议是路由器之间商量'怎么把这个频道的信号沿树送到有观众的地方'。**" IGMP 只在最后一跳（主机↔接入路由器）起作用，网络内部的树由 PIM 等负责。多播在教学上是"广度覆盖"项，理解"组地址 + 分发树 + IGMP 管加入退出"三件套即可，具体协议模式（SM/DM）与 RPF 细节不必深挖。这里的 RFC 编号（IGMPv3=3376）为常见一手编号，标注核实日期；PIM-SM 现行规范为 RFC 7761。
