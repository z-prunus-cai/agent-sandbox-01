## N9.1 安全目标与威胁模型

### N9.1.1 四个安全目标：机密性、完整性、认证、可用性

网络安全通常围绕四个核心目标展开。**机密性（confidentiality）**指报文内容只有预期的收发双方能读懂，中途窃听者拿到的只是密文；**完整性（integrity）/消息完整性**指报文在途中若被篡改（哪怕改一个比特），接收方能检测出来并拒收；**端点认证（authentication）**指通信一方能确认对面确实是它声称的那个实体，而不是冒充者；**可用性（availability）**指服务在遭受攻击（如拒绝服务）时仍能正常提供。Kurose-Ross ch8 把前三项加上"运营安全（operational security，即防火墙/IDS 保护内网）"列为网络安全的四大"合意属性"，与经典的 CIA 三元组（Confidentiality/Integrity/Availability）在措辞上略有出入但内核一致。

对初学者，最容易混的是**机密性 ≠ 完整性 ≠ 认证**，它们各防一类事，且缺一不可。举个最小例子：你给银行转账，若只有机密性、没有完整性，攻击者虽读不懂密文，却可能盲改密文让"转 100 元"变成"转 900 元"（对某些不带认证的加密确实做得到）；若只有机密性和完整性、没有认证，你可能正在和一个假冒银行的钓鱼服务器安全地通信——加密得再好也没用，因为对面根本不是银行。所以一条真正的安全信道必须**同时**提供这三者，TLS 正是把三者打包交付。可用性则是另一维度：加密解决不了"服务器被海量请求打垮"，那要靠防火墙、限流等手段（见 N9.5）。

另有一项常被单列的目标是**非否认性（non-repudiation）**——事后无法抵赖曾发过某消息，通常靠数字签名实现。TLS 握手中的 `CertificateVerify` 用到签名，但 TLS 的会话数据用的是对称 AEAD、双方共享同一密钥，因此 **TLS 本身不为应用数据提供非否认**（谁都能造出对方能验证的 MAC），需要非否认要在应用层用签名单独做。

### N9.1.2 被动攻击与主动攻击

按攻击者"是否改变了系统中的数据流"，攻击分两大类。**被动攻击（passive）**指攻击者只窃听、不改动，典型是**嗅探/窃听（eavesdropping/sniffing）**——搭在链路上抄走经过的报文，以及**流量分析（traffic analysis）**——即便读不懂密文，也从"谁在和谁通信、报文多大多频繁"推断信息。被动攻击的特点是**难以察觉**（数据没被动过），只能靠加密来"预防"而非"检测"。

**主动攻击（active）**指攻击者会篡改、注入、重放或伪造数据流，典型包括：**篡改（modification）**改报文内容；**重放（replay）**把先前截获的合法报文原样再发一遍（如重放一条转账指令）；**伪造/假冒（spoofing/masquerade）**冒充某个 IP 或身份；**中间人攻击（man-in-the-middle, MITM）**同时冒充通信双方、坐在中间转发并可窜改；以及**拒绝服务（DoS/DDoS）**——不偷不改，只用洪水般的请求耗尽对方资源、破坏可用性。主动攻击一般**可检测**（数据被动过会留痕），防御思路是"检测 + 拒收 + 认证"。

初学者可用一句话记住二者的应对分工：**机密性对付被动窃听，完整性 + 认证对付主动篡改与假冒，可用性（限流/过滤）对付 DoS**。TLS 的加密挡住被动窃听，AEAD 认证标签挡住篡改与重放（序号纳入认证），证书链挡住假冒与 MITM；但 TLS 挡不住 DoS——那是防火墙和网络基础设施的活。

### N9.1.3 威胁模型：攻击者能力假设

谈"安全"必须先说清"防谁、对手能做什么"，这就是**威胁模型（threat model）**。网络安全普遍采用一个很强的攻击者假设（学界常称 **Dolev-Yao 模型**）：攻击者**完全控制网络**——能看到、拦截、丢弃、修改、重放、注入任何经过网络的报文，且掌握所有公开算法；但攻击者**不能破解密码学原语本身**（除非拿到密钥），也算不出私钥。Kurose-Ross 用 Alice（发送方）、Bob（接收方）、Trudy（intruder，入侵者）三个人物把这套假设讲得很直观：Trudy 能对信道为所欲为，唯独打不开正确加密的密文、伪造不了正确的签名/MAC。

**安全协议的"安全"永远是相对于某个假设成立的**，脱离假设谈安全没有意义。例如 TLS 假设"攻击者控制网络但没有服务器私钥、且客户端的信任根（CA 列表）没被污染"——如果这两个前提被打破（私钥泄露、或攻击者往你系统里塞了个恶意根 CA），TLS 的保证就随之失效。这也解释了为什么 N9.4 的 PKI（谁来背书公钥可信）和私钥保护如此关键：密码算法再强，信任的根基被撬动，整座大厦就塌了。

### N9.1.4 安全信道要交付什么，以及"前向保密"这一进阶目标

把上面几点合起来，一条**安全信道（secure channel）**要向应用交付三件事：加密（机密性）、消息认证码或 AEAD 标签（完整性 + 抗篡改）、以及握手期的身份认证（认证 + 抗 MITM），再加上通过序号把重放挡在门外。TLS 就是把这套打包成一个可复用的"安全传输层"，让上层的 HTTP、SMTP、IMAP 等无需各自造轮子。

一个值得初学者提前建立的进阶目标是**前向保密（forward secrecy，又称 perfect forward secrecy, PFS）**：即便服务器的长期私钥**未来某天泄露**，攻击者也**无法**用它解密**此前**录下的历史会话。做到这一点的关键是"每次会话用一对临时（ephemeral）密钥协商会话密钥，会话结束即销毁，长期私钥只用于签名认证、不用于加密密钥本身"。TLS 1.3 把前向保密变成了**默认且强制**（见 N9.3.3），这正是它相较旧版本最重要的安全升级之一——旧的 RSA 密钥传输模式没有前向保密，私钥一旦泄露，多年录下的流量可被批量解密。

- 术语分歧（如实标注）：Kurose 列"机密性/完整性/端点认证/运营安全"四属性，经典教材（CIA 三元组）列"机密性/完整性/可用性"、把认证与非否认另列；两者内核一致，本报告合并陈述并点明差异。Dolev-Yao 模型名出自密码协议分析文献（Dolev & Yao 1983），Kurose 未用此名但其攻击者假设等价。

## N9.2 TLS 记录层与握手协议分层

### N9.2.1 TLS 在协议栈中的位置

TLS 是一层"**夹在应用层与传输层之间**"的协议：它建在 TCP（一条可靠、有序的字节流）之上，向上给应用层（如 HTTP）提供一条同样是字节流、但已加密并认证的"安全 socket"。所以 HTTPS 就是"HTTP 报文原封不动地灌进 TLS 信道"，浏览器和服务器的 HTTP 代码几乎不用改，只是底下的 socket 换成了 TLS socket。

对初学者，关键是理解 TLS **依赖 TCP 已经解决了可靠传输**——TLS 自己不管重传、排序、丢包，它假设下面递上来的字节流是完整有序的，因此可以专注于"加密 + 认证"。这也解释了一个常见困惑：为什么 TLS 不能直接跑在 UDP 上？答案是不能直接跑，需要 UDP 上的变体 **DTLS**（Datagram TLS）来处理乱序丢包；而 QUIC/HTTP3（本课大主题N8）则干脆把 TLS 1.3 的握手与密钥体系**内嵌进自己的传输层**、不再作为独立一层——这是 TLS 1.3 设计上被复用的一个重要方向。

### N9.2.2 记录协议（record protocol）：承载与保护

**记录协议**是 TLS 的底层"搬运工 + 保安"。它把上层交来的数据流切成一个个**记录（record）**（TLS 明文记录负载上限为 2^14 = 16384 字节），给每个记录加一个短头部（内容类型、版本、长度），握手完成后再用协商好的密钥对记录负载做 **AEAD**（认证加密）保护，最后交给 TCP 发送。接收端反向操作：从 TCP 收字节、按记录边界切分、AEAD 解密并**校验认证标签**（标签不对就报致命告警并断连），再把明文交回上层。

记录层负责的正是"数据面"的机密性与完整性：**每条记录都被加密并带一个认证标签，任何篡改都会让标签校验失败**。初学者要抓住记录协议做的三件事——分片（fragment）、（历史版本有可选压缩，TLS 1.3 已移除）、加密+认证——以及一个关键点：记录的**序号**被纳入 AEAD 的计算（作为 nonce/附加数据的一部分），所以攻击者既不能篡改单条记录，也不能删除、重排或重放记录而不被发现。

### N9.2.3 握手协议与其余子协议

握手完成前，记录层承载的是**握手协议（handshake protocol）**的消息——这是 TLS 的"控制面"，负责协商协议版本与密码套件、通过（EC）DHE 交换临时公钥算出共享密钥、用证书完成身份认证、并最终用 `Finished` 消息校验整场握手没被篡改。除握手协议外，TLS 记录层历史上还承载另外三类子协议：**告警协议（alert）**传递警告与致命错误（如证书过期、解密失败）；**变更密码规格协议（change_cipher_spec, CCS）**在旧版本用于"从此刻起启用刚协商的密钥"；以及**应用数据协议（application_data）**，即真正的用户数据。

这四类由记录头部的**内容类型（ContentType）**字段区分（RFC 8446 §5.1，取自规范）：

```
change_cipher_spec = 20   alert = 21   handshake = 22   application_data = 23   invalid = 0
```

初学者要知道 TLS 1.3 对这套做了简化：**`change_cipher_spec` 在 1.3 里已失去实际功能，仅为"中间设备兼容模式（middlebox compatibility）"保留**——因为网络中大量老旧中间设备会看 TLS 记录流的样子，若样子和旧版本差太多就会误拦，所以 1.3 故意发几个假的 CCS 记录让流量"看起来像 TLS 1.2"。这是一个"为了穿过僵化的网络而做的向后兼容妥协"的经典例子。

### N9.2.4 TLS 1.3 记录格式与"内容类型隐藏"

TLS 1.3 的记录保护有个精巧设计：握手完成后，**所有加密记录的外层内容类型一律填成 `application_data`(23)**，真正的内容类型被藏在加密负载内部（RFC 8446 定义的 `TLSInnerPlaintext` 结构：明文 ‖ 真实 ContentType ‖ 可选的零填充）。也就是说，从网线上看，握手后的每条记录外表都长一个样，观察者无法从内容类型区分"这是握手消息、告警还是用户数据"。

AEAD 保护可写成一个"密封"操作（概念式，非某具体算法）：

```
ciphertext = AEAD-Seal(key, nonce, additional_data = record_header, plaintext = TLSInnerPlaintext)
```

其中 nonce 由每条记录递增的序号与一个静态 IV 异或得到，`record_header` 作为附加认证数据参与校验但不加密。对初学者，这里要建立的直觉是：**AEAD（如 AES-GCM、ChaCha20-Poly1305）一步同时给出机密性和完整性**——它输出密文外还输出一个认证标签，解密时标签一旦对不上就整条拒绝。TLS 1.3 强制只用 AEAD 类密码套件，彻底告别了旧版本"先 MAC 再加密 / CBC 分组"那些被反复攻破（如 BEAST、Lucky13、POODLE）的组合，可选的记录填充（padding）还能一定程度上掩盖真实报文长度、削弱流量分析。

### N9.2.5 两层分工小结

把 N9.2 收束成一句可背的分工：**握手协议"谈密钥、验身份"（控制面，只在连接开头跑一次，用非对称密码 + 证书），记录协议"运数据、保安全"（数据面，握手后一直跑，用对称 AEAD）**。这个"非对称谈密钥、对称传数据"的两段式，正是几乎所有安全传输协议的通用骨架——非对称密码慢但能在陌生人之间安全地商定密钥，对称密码快、适合海量数据，两者取长补短。

## N9.3 TLS 1.3 握手（1-RTT / 0-RTT / 前向保密）

### N9.3.1 1-RTT 握手时序

TLS 1.3 最重要的改进之一是把常规握手压缩到 **1-RTT（一个往返）**：客户端在第一个飞行（flight）里就把临时公钥（`key_share`）一起发出，服务器一个来回就把密钥定下并开始发数据。完整时序如下（`{}` 表示已用**握手流量密钥**加密，`[]` 表示已用**应用流量密钥**加密；`*` 表示可选/按需；取自 RFC 8446 §2.1 Figure 1）：

```
Client                                             Server

ClientHello
  + supported_versions        (声明支持 TLS 1.3)
  + key_share                 (客户端临时 (EC)DHE 公钥)
  + signature_algorithms
  + [psk / pre_shared_key*]          -------->
                                                ServerHello
                                                  + key_share      (服务器临时公钥)
                                                  + [supported_versions]
                                        {EncryptedExtensions}
                                        {CertificateRequest*}   (要求客户端证书时)
                                        {Certificate*}          (服务器证书链)
                                        {CertificateVerify*}    (对握手记录的签名)
                                        {Finished}              (握手完整性 MAC)
                                <--------  [Application Data*]   (服务器可立即发数据)
{Certificate*}
{CertificateVerify*}
{Finished}                      -------->
[Application Data]              <------->  [Application Data]
```

对初学者，读这张图抓三点。其一，**ClientHello 一发出就带上了 `key_share`**——客户端"赌"服务器支持它猜的那个组（如 X25519），赌中就省一个来回；赌不中服务器回一个 `HelloRetryRequest` 让客户端换组重来（退化为 2-RTT）。其二，**从 `ServerHello` 之后的所有握手消息都已经是加密的**（用双方刚算出的握手密钥），这是相较 TLS 1.2"证书明文可见"的又一隐私改进。其三，**服务器在发完自己的 `Finished` 后就能立刻发应用数据**，不必等客户端的 `Finished`，这正是"1-RTT"的由来。

### N9.3.2 密钥交换：仅 (EC)DHE + PSK，临时密钥

TLS 1.3 **只保留两种密钥建立方式**：基于 (EC)DHE 的临时 Diffie-Hellman 交换，以及基于 PSK（预共享密钥，多用于会话恢复）的模式，二者也可结合（PSK + (EC)DHE）。**它彻底删除了 TLS 1.2 里的静态 RSA 密钥传输和静态 DH**。在 (EC)DHE 交换中，双方各自生成一对**临时（ephemeral）**密钥对，把公钥放进 `key_share` 交换，各自用"自己的私钥 + 对方的公钥"算出同一个共享秘密（DH 的核心性质），再经密钥派生（HKDF）生成一系列流量密钥。

对初学者，(EC)DHE 里那个 **E（ephemeral，临时）** 是理解前向保密的钥匙：这对密钥**只为这一次握手而生、握手完就丢**。DH 交换本身"为什么让窃听者算不出共享秘密"属于密码学原语（离散对数/椭圆曲线难题，归 g11），本课只用其结论——**双方能在公开信道上、当着窃听者的面，算出一个只有他俩知道的共享秘密**。注意 DH 交换本身**不认证身份**（它防窃听不防 MITM），所以必须叠加 N9.3.4 的证书签名来确认"和我做 DH 的这个公钥确实来自真服务器"。

### N9.3.3 前向保密：为何 TLS 1.3 默认就有

前向保密在 TLS 1.3 是**默认且不可关闭**的，直接后果就是上面"只用临时 (EC)DHE、删掉静态 RSA"这个设计。机制上：会话密钥由**临时**私钥参与派生，握手结束后临时私钥被销毁；服务器的**长期私钥只用来对握手做签名**（`CertificateVerify`，证明身份），**从不用于加密或派生会话密钥**。因此长期私钥即便日后泄露，攻击者也拿不到早已销毁的临时私钥，无法重算出历史会话密钥、也就解不开此前录下的流量。

用一个对比讲透为什么这是大进步。TLS 1.2 的老式"RSA 密钥传输"模式里，客户端用**服务器的长期 RSA 公钥**加密一个随机数（pre-master secret）发过去，会话密钥全从它派生——这意味着"谁有服务器长期私钥，谁就能解这条会话"。攻击者只要长期潜伏、把加密流量全录下来，等哪天（通过入侵、法律强制、心脏出血漏洞等）拿到那把长期私钥，就能**批量、事后**解密多年积累的历史流量。前向保密正是斩断这条"一把钥匙开所有历史锁"的链路——这也是为什么现代部署即便在 TLS 1.2 也强烈推荐只用 ECDHE 套件。

### N9.3.4 认证：Certificate、CertificateVerify 与 Finished

TLS 1.3 里服务器（以及可选的客户端）身份认证由三条消息协作完成。`Certificate` 携带证书链（服务器的叶证书 + 中间 CA 证书，见 N9.4）。`CertificateVerify` 是**用证书对应的私钥、对到此为止的整个握手记录（transcript）做的一个数字签名**——这一步至关重要：它证明发证书的这一方**真的持有该证书对应的私钥**，而不是拿别人的证书来冒充（光有一张公开的证书证明不了身份，能对当前握手签名才行）。`Finished` 则是**用握手密钥算出的一个 MAC，覆盖整场握手的转录哈希**，双方互发并校验，用来确认"从头到尾没有任何一条握手消息被中间人篡改过"（比如被偷偷降级或改了密码套件）。

初学者要理清这三者防的是不同的攻击：`Certificate` 提供"公钥 + 谁背书"，`CertificateVerify` 用签名把"这场 DH 握手"和"证书身份"**绑定**（防 MITM 把自己的 DH 公钥塞进来），`Finished` 提供**整场握手的完整性**（防降级/篡改）。三者缺一，MITM 就有机可乘。一个易错点：**TLS 默认只认证服务器、不认证客户端**（网页浏览典型场景）；需要双向认证（mTLS）时服务器才发 `CertificateRequest`、客户端才回自己的证书与 `CertificateVerify`，常见于企业内网、API 网关与服务间调用。

### N9.3.5 密码套件命名：TLS 1.3 vs 1.2（附实机对比）

TLS 1.3 重新定义了密码套件的命名，只描述**AEAD 算法 + 哈希**，而把密钥交换和签名算法**移出套件名、单独协商**。RFC 8446 §B.4 定义的五个套件为：

```
TLS_AES_128_GCM_SHA256   TLS_AES_256_GCM_SHA384   TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_CCM_SHA256   TLS_AES_128_CCM_8_SHA256
```

对比 TLS 1.2 的套件名（如 `ECDHE-RSA-AES256-GCM-SHA384`）——它把"密钥交换(ECDHE) + 认证(RSA) + 加密(AES256-GCM) + PRF哈希(SHA384)"四件事全塞进一个名字。TLS 1.3 的名字里**看不到密钥交换和签名算法**，因为 1.3 已把密钥交换固定为 (EC)DHE/PSK、由 `supported_groups`/`key_share` 协商，签名算法由 `signature_algorithms` 协商，套件名只剩"用哪种 AEAD + 哪种哈希做密钥派生"。

本机实机坐实这一命名差异（`openssl` 3.0.13，@2026-07-29，Linux 6.18.5，经会话出站代理；**注意该会话被 egress 网关终结重签，仅用于坐实"版本/套件命名规则"这类端点无关事实**）：

```
# openssl s_client ... -tls1_3 :  New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
# openssl s_client ... -tls1_2 :  New, TLSv1.2, Cipher is ECDHE-RSA-AES256-GCM-SHA384
```

这段真实输出清楚显示，强制 1.3 时协商出的套件名是 `TLS_AES_256_GCM_SHA384`（无密钥交换/签名段），强制 1.2 时是 `ECDHE-RSA-AES256-GCM-SHA384`（四段俱全），与 RFC 8446 的命名规则一致。

### N9.3.6 0-RTT / 早期数据与重放风险

TLS 1.3 还支持 **0-RTT（zero round-trip time）** 恢复：如果客户端此前连过该服务器、手里有服务器给的 PSK（会话票据），它可以在**第一个 ClientHello 里就带上加密的应用数据（early data）**，服务器在完成握手前就能读到并处理——省掉了等握手的那一个来回，对延迟敏感的场景（如重复访问的网页）很有吸引力。

但 0-RTT 有两个**必须硬记的安全短板**（RFC 8446 §2.3、§8、附录 E.5 反复警示）。其一，**0-RTT 数据没有前向保密**——它由 PSK 派生保护，而 PSK 是先前会话留下的、寿命较长。其二，也是更棘手的，**0-RTT 数据可被重放（replay）**：因为它在服务器确立"新鲜性"之前就发出了，攻击者可把截获的 early data 原样重发多次，服务器可能重复处理。所以规范要求 **0-RTT 只能用于"可安全重复执行"的操作**（幂等的、无副作用的，如 GET 一个页面），**绝不能**用于会改变状态的请求（如下单、转账）。初学者应把 0-RTT 理解为"一个用安全性换延迟的可选加速档，默认关，开了要严格限定用途"。

### N9.3.7 会话恢复与 NewSessionTicket

握手成功后，服务器可发 `NewSessionTicket` 消息，给客户端一张（或多张）**会话票据**，其中封装了一个 PSK。下次连接时客户端用 `pre_shared_key` 扩展带上票据，双方就能跳过完整的证书验证与部分协商、用 PSK 快速恢复会话（可选叠加一次新的 (EC)DHE 以获得前向保密）。这取代了 TLS 1.2 里的 Session ID / Session Ticket 两套旧机制，统一到"PSK 恢复"这一条路径上。

对初学者，会话恢复的价值是**省掉昂贵的非对称运算与证书验证**——首次握手要做 DH、验证书链、验签名，代价不小；恢复时凭一张票据就能重建安全信道，显著降低延迟与 CPU 开销，也正是 0-RTT 得以实现的前提（0-RTT 必须基于恢复用的 PSK）。

### N9.3.8 与 TLS 1.2 的删减对比与降级保护

TLS 1.3 相对 1.2 是一次"大扫除"，删掉了一批被反复证明危险或冗余的东西：静态 RSA 密钥传输与静态 DH（→换来前向保密默认化）、所有非 AEAD 的分组密码模式（CBC 等，→堵住 BEAST/Lucky13/POODLE 一类攻击）、TLS 层压缩（→堵住 CRIME 攻击）、RC4、MD5/SHA-1、可协商的自定义 DH 群、以及重协商（renegotiation）。这套删减是"通过减少可选项来减少攻击面"的教科书式安全设计。

删旧引出一个新问题——攻击者能否强迫双方"降级"到有漏洞的旧版本？TLS 1.3 用**降级保护（downgrade protection）**应对——若服务器实际支持 1.3 却因某种原因协商到了 1.2 或更低，它会在 `ServerHello.random` 的最后 8 字节填入一个**特定的哨兵值**（RFC 8446 §4.1.3 规定的 `DOWNGRD` 标记），支持 1.3 的客户端一旦看到这个哨兵值却发现自己被降级了，就知道"这大概是中间人在搞降级攻击"从而中止连接。初学者只需记住结论：**TLS 1.3 内建了"我本可以用更安全的版本却被降级"的检测机制**。此外 RFC 8996（2021）已正式**废止 TLS 1.0/1.1**，现代部署最低应为 TLS 1.2。

### N9.3.9 后量子密钥交换迁移（⚙演进快·锚版本 @2026-07）

一个正在快速演进、初学者应当知道方向的前沿：**后量子（post-quantum）迁移**。未来的大型量子计算机可用 Shor 算法破解今天 TLS 依赖的椭圆曲线/RSA 密钥交换，威胁模型里出现了"**先录下今天的流量、等量子机成熟再解密（harvest-now-decrypt-later）**"这种针对**密钥交换**的现实担忧（对没有前向保密的更甚）。业界的应对是在 TLS 1.3 里引入**混合密钥交换（hybrid key exchange）**：把传统的 X25519 与后量子 KEM **ML-KEM**（即 NIST FIPS 203，2024-08 标准化，前身为 Kyber）组合，任一算法被破也仍安全。

这一方向必须硬标 ⚙演进快·锚版本、随时变。截至 **2026-07**，以 `X25519MLKEM768`（早期部署曾用 `X25519Kyber768Draft00`）为代表的混合密钥交换已在主流浏览器与大型 CDN（Chrome、Cloudflare 等）**默认或大规模启用**；而后量子**签名/证书**（ML-DSA=FIPS 204、SLH-DSA=FIPS 205）的 PKI 迁移仍处更早阶段。具体命名、代码点与默认开关随版本快速变动，此处仅登记方向与锚版本、**不作为稳定结论**，精确参数请以当时的 IETF TLS 工作组文档与 NIST FIPS 为准。密码原语（ML-KEM 的格困难假设、为何抗量子）归 g11，本课只讲其作为 TLS 密钥交换组件的**接入机制**。

#### 来源与时效
- 锚点：RFC 8446 §2（握手概览与 1-RTT/0-RTT 图）、§2.2（会话恢复与 PSK）、§2.3（0-RTT 及其重放警示）、§4.1.3（`ServerHello.random` 降级哨兵）、§4.2.8/§4.2.9（key_share/psk_key_exchange_modes）、§4.4（CertificateVerify/Finished）、§B.4（五个密码套件）、§8/附录 E（前向保密与 0-RTT 安全考量）；Kurose-Ross 8E §8.6（TLS 握手与会话密钥、以 TLS 1.2 视角讲原理）；RFC 8996（废止 TLS 1.0/1.1，2021-03）。@核实 2026-07-29。
- 实机：`openssl` 3.0.13 s_client 取得 TLS 1.3 套件 `TLS_AES_256_GCM_SHA384` 与 TLS 1.2 套件 `ECDHE-RSA-AES256-GCM-SHA384`（真实输出，会话被 egress 网关重签，仅坐实命名规则）。
- 冲突/时效（如实标注）：Kurose-Ross 8E 的 TLS 章以 TLS 1.2 的四步握手为主线讲原理，与 RFC 8446 的 1-RTT 精简握手在**消息数与流程**上不同；本报告握手时序、消息名、密码套件以 **RFC 8446 一手为准**，教材仅用于原理层交叉印证。**⚙演进快**：N9.3.9 后量子混合密钥交换命名/默认开关锚 2026-07、随时变，非稳定结论；ML-KEM/ML-DSA/SLH-DSA 对应 NIST FIPS 203/204/205（2024-08）。

## N9.4 证书链与 PKI 信任

### N9.4.1 X.509 v3 证书结构（附实机解码）

TLS 用**数字证书**把"一个公钥"和"一个身份（域名）"绑在一起，格式是 **X.509 v3**（RFC 5280）。一张证书本质是一份被**颁发它的 CA 用私钥签名**的结构化文档，核心字段包括：版本（version，现代都是 v3）、序列号（serial number，CA 内唯一）、签名算法、**颁发者（issuer，签发此证书的 CA）**、**有效期（validity：notBefore / notAfter）**、**主体（subject，证书归谁）**、**主体公钥信息（subjectPublicKeyInfo，即被绑定的公钥及其算法）**、一组 **v3 扩展（extensions）**，最后是 **CA 对以上内容的签名**。

本机 `openssl x509 -text` 解码一张实机证书的字段布局（**该证书由沙箱 egress 网关签发、非真实端点证书**，仅用于展示 X.509 v3 的字段结构；真实输出，@2026-07-29）：

```
Version: 3 (0x2)
Serial Number: ...
Signature Algorithm: sha256WithRSAEncryption
Issuer:  O = Anthropic, CN = Egress Gateway SDS Issuing CA (production)
Validity
    Not Before: Jul 27 18:18:27 2026 GMT
    Not After : Aug 26 18:19:27 2026 GMT
Subject: CN = *.cloudflare.com
Subject Public Key Info
    Public Key Algorithm: rsaEncryption
        Public-Key: (2048 bit)
X509v3 extensions:
    X509v3 Key Usage: critical
    X509v3 Extended Key Usage
    X509v3 Authority Key Identifier
    X509v3 Subject Alternative Name:  DNS:www.cloudflare.com
```

对初学者，这张解码把抽象概念坐实了：`Issuer`（谁签的）与 `Subject`（签给谁）成对出现——正是它俩把证书**串成链**（下一节）；`Validity` 是"这张证书哪天到哪天有效"（过期即失效）；`Subject Public Key Info` 就是"要被背书的那把公钥"；`Subject Alternative Name` 里的 `DNS:...` 才是现代浏览器**真正拿来匹配域名**的字段（见 N9.4.5）。

### N9.4.2 关键 v3 扩展

X.509 v3 的威力在于**扩展（extensions）**，几个对 TLS 最关键的：**BasicConstraints** 标明"这是不是一张 CA 证书（CA:TRUE/FALSE）"以及路径长度限制——**叶子（服务器）证书必须 CA:FALSE，否则任何网站证书都能再去签发别的证书，信任体系就崩了**；**KeyUsage** 限定这把密钥能用来干什么（如数字签名、密钥协商）；**ExtendedKeyUsage（EKU）** 进一步限定用途，服务器证书须含 `serverAuth`、客户端证书须含 `clientAuth`；**SubjectAltName（SAN）** 列出该证书覆盖的所有域名/IP；**AuthorityKeyIdentifier / SubjectKeyIdentifier** 帮助在建链时快速定位"用哪张上级证书来验签"；**CRLDistributionPoints / AuthorityInfoAccess(AIA)** 分别给出吊销列表地址与 OCSP 响应者地址（见 N9.4.6）。

初学者最该记住的是 **BasicConstraints 的 CA 标志**：它是 PKI 安全的一道关键闸门。历史上（如 2011 年前的某些实现）曾因不检查这个标志而出过大漏洞——攻击者用一张普通的叶证书去给别的域名签发证书竟被接受。所以链验证时**每一级都要检查 CA 标志与路径长度**，确保只有真正的 CA 才能出现在链的中间节点。

### N9.4.3 CA 信任链与信任锚

单张证书只是"某 CA 说这把公钥属于这个域名"，凭什么信这个 CA？答案是**信任链（chain of trust）**：叶证书由中间 CA 签，中间 CA 的证书又由（更上级 CA 或）**根 CA** 签，根 CA 自签（self-signed）。链的终点是**信任锚（trust anchor）**——操作系统/浏览器预装的**根证书存储（root store）**里那些被"无条件信任"的根 CA 公钥。验证时把叶证书一路往上串到某个信任锚，就完成了信任传递。

```
叶证书 (www.example.com)  —签发者→  中间 CA 证书  —签发者→  根 CA 证书（信任锚，预装在系统/浏览器）
   由中间 CA 签名               由根 CA 签名           自签名、天生被信任
```

对初学者，关键直觉是**信任是"传递"来的、根是"预置"的**：你并没有逐一认识全世界的 CA，你的浏览器/操作系统厂商替你预置了一份被审计过的根 CA 名单，凡能追溯到这份名单里某个根的证书就被接受。中间 CA 的存在是为了让根 CA 的私钥可以离线深锁（少用少暴露），日常签发交给中间 CA。这也解释了 N9.1.3 里那个前提"信任根没被污染"为何致命——**谁能往你的 root store 里塞一个恶意根，谁就能给任意网站签出你会信任的假证书**，实现无痕 MITM。

### N9.4.4 链验证步骤

给定服务器发来的证书链，客户端大致做这几步验证：**建链**——从叶证书出发，用 issuer/AKI 找到上级证书，一路拼到某个信任锚（拼不到就失败）；**逐级验签**——用每张上级证书里的公钥验证下级证书的 CA 签名；**查有效期**——每张证书的当前时间须落在 notBefore/notAfter 之间；**查约束**——检查每级 BasicConstraints 的 CA 标志与路径长度、KeyUsage/EKU 是否允许当前用途、以及名称约束（NameConstraints）；**查吊销**——通过 CRL/OCSP 确认没被提前作废（见 N9.4.6）；**查主机名**——叶证书的 SAN 是否匹配你要访问的域名（见 N9.4.5）。任何一步失败都应中止连接。

初学者要把这理解成一条"**层层过关，一关不过全盘否决**"的流水线，而不是"看一眼证书好像有就行"。一个常见误解是"有 HTTPS 小锁就绝对安全"——小锁只表示"到某个证书能验通的服务器的信道是加密的"，若用户点了"忽略证书错误"、或系统被装了恶意根、或钓鱼域名申请了自己的合法证书（域名确实归攻击者），锁照样是绿的。**证书验证保证的是"你连到的是这个域名的真正持有者"，不保证"这个域名不是坏人的"**。

### N9.4.5 主机名校验：SAN 取代 CN

验完链只说明"这张证书是可信 CA 签的、没过期没吊销"，还差最后一步：**这张证书是不是签给我正在访问的这个域名的**？现代做法是比对 **SubjectAltName(SAN)** 扩展里的 `DNS:` 条目（RFC 6125、以及 CA/Browser Forum 基线要求），**而不是**看老式的 Subject CN 字段。上面 N9.4.1 的实机解码里 `Subject Alternative Name: DNS:www.cloudflare.com` 正是浏览器实际拿来匹配的字段。

初学者要记住这条已经落地的演进：**CN 用于主机名校验已被弃用，一律以 SAN 为准**——主流浏览器（Chrome 自 2017 起）对不含 SAN 的证书直接判为无效。原因是 CN 是个自由文本字段、语义含混（还可能同时含组织名等），而 SAN 是结构化、可含多个域名/通配符/IP 的专用字段。匹配还要处理通配符（`*.example.com` 只匹配一层子域，不匹配 `a.b.example.com` 也不匹配裸 `example.com`）。这一步失败的典型症状就是浏览器报"证书对该域名无效（NET::ERR_CERT_COMMON_NAME_INVALID / 域名不匹配）"。

### N9.4.6 吊销：CRL、OCSP、OCSP stapling 与短期证书

证书可能在到期前就需要作废（私钥泄露、信息有误、域名易主），这需要**吊销（revocation）**机制。经典有两条路：**CRL（Certificate Revocation List，RFC 5280）**——CA 定期发布一份"已吊销证书序列号"的黑名单，客户端下载比对，缺点是列表大、更新有延迟；**OCSP（Online Certificate Status Protocol，RFC 6960）**——客户端就单张证书**在线**问 CA 的响应者"这张还有效吗"，实时性好但带来延迟与隐私问题（等于把你访问了哪些站点告诉了 CA）。

工程上更常用的是 **OCSP stapling（RFC 6066 的 `status_request` 扩展）**：由**服务器**定期向 CA 取得一份带 CA 签名、带时间戳的 OCSP 响应，在 TLS 握手时**随证书一起"钉（staple）"给客户端**——客户端无需再自己去问 CA，既省一次往返又保护了隐私。近年更受青睐的方向是**签发寿命很短的证书**（如几天到几十天，让"到期"本身承担大部分吊销职责，浏览器也在推动缩短最长有效期），以及浏览器侧的聚合吊销机制（如 CRLite 一类）。初学者只需掌握三层：**吊销就是"到期前提前作废"，CRL 是批量黑名单，OCSP 是逐张在线问、stapling 让服务器代问代传**。

### N9.4.7 证书透明度（CT，补充）

**证书透明度（Certificate Transparency，RFC 6962）**是给 PKI 加的一层"公开审计"：CA 签发的每张证书都要提交到公开、只可追加的 **CT 日志**，任何人都能监视"有没有 CA 给我的域名签发了我没申请过的证书"。主流浏览器已要求公网服务器证书必须带 CT 证明（SCT），否则不予信任。

对初学者，CT 解决的是 PKI 的一个软肋：**根 CA 名单里任何一个 CA 出了问题（被黑、被骗、作恶），就能给任意域名签假证书**，而受害域名此前无从知晓。CT 让签发行为"晒在阳光下"，把"事前无法阻止"变成"事后一定能发现并追责"，多起 CA 误签/违规正是靠 CT 日志曝光的。它不加密、不改握手，是纯粹的**可审计性**增强。

- 锚点：RFC 5280（X.509 v3 字段、扩展 BasicConstraints/KeyUsage/EKU/SAN/AKI、CRL、路径验证算法 §6）；RFC 6125（用 SAN 做服务身份校验、CN 弃用）；RFC 6960（OCSP）；RFC 6066 §8（status_request / OCSP stapling）；RFC 6962（Certificate Transparency）；Kurose-Ross 8E §8.3（数字证书与 CA 的角色）。@核实 2026-07-29。

- 无实质冲突。教材以概念讲 CA/证书，RFC 5280/6125 为字段与校验规则一手；"CN 已弃用、以 SAN 为准""浏览器要求 CT"为已落地的行业实践（CA/Browser Forum 基线），非草案。

## N9.5 防火墙 / IDS / IPsec 概念

### N9.5.1 防火墙：包过滤、状态检测与应用网关

**防火墙（firewall）**是置于内网与外网之间的过滤设备，按预设策略决定放行或丢弃流量，属于 N9.1.1 里的"运营安全"。它有三个层次：**无状态包过滤（stateless packet filter）**——逐包看 IP/端口/协议/标志位对照规则表（如"只放行到 443 的入站、其余丢弃"），不记连接上下文，简单快但表达力弱；**有状态过滤（stateful filter）**——维护一张连接跟踪表，能识别"这个入站包是不是某条已建立出站连接的回包"，从而只放行属于合法会话的流量，是现代防火墙的主流；**应用网关/代理（application gateway/proxy）**——工作在应用层，能看懂 HTTP/SMTP 等内容并按应用语义过滤（如只允许特定用户外发邮件），最强也最重。

对初学者，三层的取舍就是"**看得越深、控制越细，但越慢越复杂**"：包过滤只看到网络/传输层头部，状态过滤加了会话记忆，应用网关能读懂业务内容。要点是防火墙防的是"谁能连进/连出"，它**不解密也读不懂 TLS 加密内容**（除非做 TLS 拦截代理，那本身就是一种受控 MITM，仅在企业内可控环境用），所以防火墙与 TLS 是互补的两道防线，不能相互替代。

### N9.5.2 入侵检测（IDS）与入侵防御（IPS）

**入侵检测系统（IDS, Intrusion Detection System）**比防火墙看得更深——它对流量做**深度包检测（DPI）**，寻找攻击特征（端口扫描、已知漏洞利用、异常流量模式）并**告警**；**入侵防御系统（IPS, Intrusion Prevention System）**则更进一步，**串接在流量路径上、能实时阻断**可疑流量，而不只是报警。两者的检测方法分两类：**基于签名（signature-based）**——匹配已知攻击的特征库（如 Snort 规则），准但只能识别已知攻击；**基于异常（anomaly-based）**——先学习"正常"基线，偏离太多就告警，能发现未知攻击但误报率高。

初学者可用一句话区分 IDS/IPS 与防火墙：**防火墙按"规则"决定放行（主要看包头），IDS/IPS 按"攻击特征/异常"检测并（IPS）阻断（要看包的内容）**。IDS 通常旁路部署（镜像流量、只观察不挡路，故障也不影响业务），IPS 在线部署（能挡但成为单点、且误判会误伤正常流量）。同样地，面对 TLS 加密流量，纯内容检测的 IDS/IPS 大多失效（看不到明文），这也是"端到端加密普及"与"网络侧内容审查"之间的长期张力。

### N9.5.3 IPsec 架构：AH、ESP 与安全关联

**IPsec（IP Security，RFC 4301）**在**网络层（IP 层）**提供安全，与 TLS 在传输层之上不同——它保护的是 **IP 数据报**，对上层应用完全透明（应用无需改造就能获得保护），是 **VPN** 的主流底层技术。IPsec 有两个保护协议：**AH（Authentication Header，RFC 4302）**只提供完整性与来源认证、**不加密**（现已少用）；**ESP（Encapsulating Security Payload，RFC 4303）**同时提供机密性 + 完整性 + 认证，是实际部署的主力。

IPsec 的核心抽象是**安全关联（SA, Security Association）**：一条 SA 是"两端就用什么算法、什么密钥保护某个方向流量"达成的单向约定，由一个 **SPI（Security Parameter Index）** 加目的地址标识；因为 SA 是**单向**的，一条双向受保护通信需要**两条** SA（一来一回各一）。初学者抓两点：其一，**IPsec 保护在 IP 层，故对应用透明、且能保护任意上层协议（含 UDP、ICMP，不像 TLS 只护一条 TCP 流）**；其二，**ESP 用（对称）加密 + 认证，密码原语本身（AES-GCM 等）归 g11，本课只讲 IPsec 如何用 SA/SPI 把它组织成网络层安全通道**。

### N9.5.4 传输模式与隧道模式

IPsec（AH/ESP）都有两种封装模式。**传输模式（transport mode）**只保护 IP 数据报的**负载**（上层数据），保留原 IP 头，用于**主机到主机**的端到端保护。**隧道模式（tunnel mode）**把**整个原始 IP 包**（含原 IP 头）加密封装进一个**新的 IP 包**，用于**网关到网关**——这正是站点到站点 VPN 的做法：两个分支机构的安全网关之间建一条隧道，内网主机的流量到网关处被整包封装、加密后穿越公网、到对端网关拆封再送入对方内网。

```
传输模式:  [原IP头 | {ESP保护: 上层负载}]                 主机↔主机
隧道模式:  [新IP头 | {ESP保护: 原IP头 | 上层负载}]         网关↔网关（VPN 典型）
```

对初学者，两模式的差别就是"**保不保护原始 IP 头**"：隧道模式连原 IP 头都藏进密文，所以在公网上看不到内网真实源/目的地址（只看到两端网关地址），这正是 VPN"把内网延伸过公网"的关键。传输模式开销小但暴露原地址，多用于两台主机直接安全通信。

### N9.5.5 IKE：IPsec 的密钥管理

IPsec 的 SA（用哪套算法、哪把密钥）不是手工配的（那不可扩展），而由 **IKE（Internet Key Exchange，当前版本 IKEv2 = RFC 7296）** 自动协商：IKE 先自己做一次认证过的 Diffie-Hellman，建立一条受保护的 IKE SA，再在其保护下协商出用于 ESP/AH 的一对 IPsec SA 及其密钥，并负责定期重协商（rekey）。IKE 的身份认证可用预共享密钥（PSK）或证书。

初学者可把 IKE 类比成 TLS 里的"握手协议"、把 ESP 类比成"记录协议"——**IKE 谈密钥与身份（控制面），ESP 用谈好的密钥保护实际 IP 流量（数据面）**，又是那个"非对称谈密钥、对称传数据"的通用骨架（见 N9.2.5）。区别只在层次：TLS 在 TCP 之上护一条应用连接，IPsec 在 IP 层护主机/网关之间的所有数据报。

### N9.5.6 边界防御的局限与纵深防御

最后一个应建立的全局观：防火墙/IDS/IPsec 都属于**边界/网络层防御**，它们各有天花板——防火墙只按包头/会话过滤、读不懂加密内容；IDS/IPS 对未知攻击与加密流量力有不逮、且误报是长期难题；IPsec/VPN 只保护"在途"的数据、进了内网就不再保护。任何单点防御都可能被绕过，所以现实安全采取**纵深防御（defense in depth）**——多层叠加（边界防火墙 + 网段隔离 + 主机加固 + 传输层 TLS + 应用层鉴权 + 监控告警），一层失守还有下一层。

对初学者，这解释了为什么"有了 HTTPS/TLS 就不需要防火墙"或反之都是错的：**TLS 保护"数据在两端点间传输的机密与完整"，防火墙/IDS 保护"网络边界与可用性"，IPsec 保护"IP 层与站点互联"——它们防的是不同位置、不同类型的威胁，是叠加而非替代关系**。这也呼应了 N9.1 的分工：没有任何一种机制能同时解决机密、完整、认证、可用四个目标，安全永远是多种机制在不同层次的组合。
