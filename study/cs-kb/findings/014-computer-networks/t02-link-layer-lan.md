## N2.1 链路层服务与成帧

### N2.1.1 链路层的位置与「节点/链路」术语

链路层（link layer，又称第二层 / L2）位于物理层之上、网络层之下，它的任务是**在一条通信链路上，把一个数据报（datagram）从一个节点搬运到相邻的下一个节点**。Kurose-Ross 用两个术语框定这一层：任何运行链路层协议的设备（主机、路由器、交换机、WiFi 接入点）都叫**节点（node）**；把相邻节点连起来的通信信道叫**链路（link）**；链路层把网络层的数据报封装进的 PDU 叫**帧（frame）**。

初学者最该建立的区分是「一跳 vs 端到端」。一个数据报从北京的主机发往纽约的主机，网络层（IP）负责规划并维持这条端到端路径的完整旅程；但数据报实际是被一段段链路接力送过去的——先经过家里的 WiFi 这一跳，再经过运营商的以太网/光纤若干跳……**每一跳都是一次独立的链路层传输，且相邻两跳可能用完全不同的链路技术**。所以同一个 IP 数据报在旅途中会被反复地「封进一个帧 → 送过一跳 → 剥出来 → 再封进下一种帧」。这也解释了为什么链路层协议五花八门（以太网、WiFi、PPP），而网络层的 IP 却要保持统一——统一的 IP 是黏合各种异构链路的「细腰」。

### N2.1.2 链路层可能提供的服务

链路层协议可以提供一组服务，但**并非每种链路层协议都全部提供**，具体取决于技术。Kurose-Ross 列出的主要服务包括：成帧（framing，把数据报装进帧、加上帧头帧尾）；链路接入（link access，当链路被多个节点共享时，由 MAC 协议规定谁何时能发，见 N2.3）；可靠交付（reliable delivery，在链路层就用确认/重传保证无误，多见于易出错的无线链路，有线链路常省略）；差错检测与纠正（error detection/correction，见 N2.2）；以及流量控制、半双工/全双工协调等。

理解的关键是「服务是可选菜单，不是套餐」。为什么可靠交付在 WiFi 上常做、在以太网上常不做？因为差错率高的链路上，就地重传比让远方的传输层（TCP）发现丢包再重传要快得多、代价小得多；而低差错率的有线链路上，链路层再加一层可靠性属于重复劳动，不如把这活儿留给端到端的传输层。这正是 N1「端到端原则」在链路层的一个具体体现：不是每层都要保证可靠，而是按链路特性权衡。

### N2.1.3 成帧：如何在比特流里划出帧的边界

**成帧（framing）** 指发送方把网络层数据报用帧头（header）和帧尾（trailer）包起来、接收方能在连续到达的比特流中准确识别出「一个帧从哪里开始、到哪里结束」。核心难题是**帧定界（framing / delimiting）**：物理层送上来的只是一串 0/1，接收方必须知道边界才能正确切分。

常见的定界手段有几类。一是**特殊定界符 + 填充**：用一个特定的字节/比特序列（flag）标记帧首尾，若数据里恰好出现了这个序列，就用**字节填充（byte stuffing）** 或**位填充（bit stuffing）** 插入转义字符/额外比特，接收方再脱去（HDLC、PPP 用这类做法）。二是**长度字段**：帧头写明后续长度，接收方数够字节即为一帧。三是**物理层前导码 + 编码**：以太网靠帧前的前导码（preamble）做时钟同步与起点标定，并规定最小/最大帧长来辅助定界。初学者可以把成帧类比成「把一段没有标点的文字断句」——你需要某种约定（空格、标点、或事先说好每句多少字）才能把连续符号切成有意义的单元，否则接收方无从下手。

### N2.1.4 链路层在哪里实现：网络适配器（NIC）

链路层的主体实现在**网络适配器（network adapter / network interface card, NIC）** 里，也就是网卡。它是软硬件结合体：成帧、MAC 寻址、差错检测（CRC 计算/校验）这些对时延敏感、计算规整的活儿由网卡上的**硬件**（专用芯片）完成；而组装数据报、响应差错、给操作系统上报等则由主机上的软件（驱动 + 协议栈）配合。

这解释了一个初学者常有的疑惑：为什么 CRC-32、MAC 地址填写这些看起来很「软件」的逻辑，其实几乎不消耗 CPU？因为它们被下沉到了网卡硬件里，线速（wire-speed）完成。发送时，主机把数据报交给网卡，网卡负责封帧、算 CRC、按 MAC 协议择时发出；接收时，网卡校验 CRC、剥掉帧头、把数据报交回主机。链路层因此是**唯一一个大部分实现在硬件里的协议层**，这也是它与更靠上、纯软件实现的网络层/传输层的显著差别。

## N2.2 差错检测：奇偶校验 / 校验和 / CRC

### N2.2.1 差错检测的总体框架

**差错检测（error detection）** 指发送方在数据 D 之外附加若干**差错检测比特（EDC, error-detection-and-correction bits）**，接收方据此判断传输中是否发生了比特翻转。基本布局是：发送 D 与 EDC 共 d + r 比特（d 为数据位、r 为冗余位），接收方对收到的 D′、EDC′ 重新计算并比对。

要先厘清两个边界。第一，**检测 ≠ 纠正**：多数链路层方案只做「检测」（发现有错就丢弃该帧），少数做**前向纠错（FEC, forward error correction）**（不仅发现还能定位并翻转回来）。第二，**差错检测不是万能的**：任何检错码都存在**未检出错误（undetected errors）** 的可能——某些特定的比特翻转组合恰好使 EDC 仍然「对得上」。所以差错检测是概率性的保障，衡量一个方案好坏，就是看它能以多小的冗余开销，把漏检概率压到多低、能保证检出哪些错误模式（如所有单比特错、所有奇数个错、所有长度 ≤ r 的突发错）。

### N2.2.2 奇偶校验与二维奇偶校验

最简单的方案是**单比特奇偶校验（single parity bit）**：在 d 个数据位后加 1 位，使整体「1」的个数为偶数（偶校验）或奇数（奇校验）。它能检出**任意奇数个**比特翻转，但**偶数个翻转会漏检**（两位同时翻，奇偶性不变）。

**二维奇偶校验（two-dimensional parity）** 把数据排成 i 行 j 列的矩阵，对每行、每列各算一个奇偶位。这样不仅能**检出**任意单比特错，还能**定位**它——出错比特所在的行校验和列校验会同时报错，交叉点即错误位置，接收方可直接翻转纠正。这是一种最朴素的 FEC。初学者可借它建立直觉：一维校验只知道「有错」，加一个维度的冗余就换来了「错在哪」的定位能力——冗余换纠错能力，这是所有纠错码的共同逻辑。二维奇偶实践中很少单用，价值在于把「检测→定位→纠正」这条链讲清楚。

### N2.2.3 Internet 校验和（RFC 1071）

**Internet 校验和（Internet checksum）** 是 IP、TCP、UDP 头部使用的差错检测方法，算法为**16 位反码（一的补码）求和**：把数据切成 16 位的字，做端回卷进位（end-around carry）的加法，再对结果取反码，得到校验和；接收方把数据连同校验和一起求和，若无误则结果为全 1（0xFFFF）。

发送方计算（S 为各 16 位字的反码和）：

checksum = ~( Σ_i word_i  带端回卷进位 )

接收方验证（把校验和也计入求和）：

Σ_i word_i + checksum  =  0xFFFF  （无差错）

本机 Python 复现 RFC 1071 §3 的示例字节 `00 01 f2 03 f4 f5 f6 f7`，得校验和 `0x220d`，且接收方把校验和一并求和得 `0xffff`，与 RFC 一致：

```
RFC1071 example checksum = 0x220d (expect 0x220d)
receiver sum incl checksum = 0xffff (expect 0xffff)
```

（环境串 基线 Py3.11.15 @2026-07-29；纯 Python 实现，无第三方依赖。）

初学者要注意两点。其一，它**为什么用在软件层（传输/网络层）而不是链路层**：反码求和实现极简、纯软件几条指令就能算，适合主机 CPU 逐包做；但它检错能力弱于 CRC（例如对某些位置对调、成对翻转不敏感）。其二，**它与 CRC 是分工不同的两道防线**：链路层用强壮的 CRC 挡住线路上的突发错，端到端再用弱一些但便宜的校验和兜底软件/内存层面的错——正是 N1 端到端原则的又一体现，「链路层查过一遍，端到端仍要自己再查一遍」。

### N2.2.4 循环冗余校验（CRC）

**循环冗余校验（CRC, cyclic redundancy check）** 是链路层（以太网、WiFi 等）广泛采用的强检错码，基于**多项式的模 2 除法**。把 d 位数据 D 看成一个二进制多项式，收发双方约定一个 r+1 位的**生成多项式（generator）G**；发送方求出 r 位余数 R，使得

D · 2^r  XOR  R  能被 G 整除（模 2 运算，即无进位的 XOR 加减）

具体地，R 就是 D·2^r 除以 G 的模 2 余数：

R = remainder( D · 2^r  /  G )

发送方把 R 附在 D 后面发出（D·2^r + R 恰好被 G 整除）；接收方把收到的整体再除以 G，**余数为 0 判为无错，非 0 判为有错**。这里的除法是「无进位」的 XOR 长除法，不是普通十进制除法——这是初学者最容易算错的点。

CRC 的威力在于生成多项式选得好时能给出确定性保证：能检出所有单比特错、所有奇数个比特错、所有长度 ≤ r 的**突发差错（burst error）**，以及绝大部分更长的突发。以太网 / IEEE 802.3 用的是 **CRC-32**，生成多项式为 `0x04C11DB7`（初值 0xFFFFFFFF、结果取反）；软件里常用的按位实现采用其反射形式 `0xEDB88320`。本机 Python 用反射多项式手写 CRC-32，对标准测试串 `"123456789"` 得 `0xcbf43926`，与 `zlib.crc32` 一致：

```
zlib.crc32('123456789')  = 0xcbf43926 (expect 0xcbf43926)
manual crc32('123456789') = 0xcbf43926
match zlib: True
```

（环境串 基线 Py3.11.15 @2026-07-29；`zlib` 为标准库，其 CRC-32 即 IEEE 802.3 多项式。）以太帧尾部那 4 字节的 **FCS（frame check sequence）** 装的就是这个 CRC-32。

### N2.2.5 三种方法的对比与选型

三者是**冗余开销、检错强度、实现代价**的不同折中。奇偶校验开销最小（1 位）、能力最弱（漏检偶数个错），基本只在教学和极简场景出现；Internet 校验和开销 16 位、能力中等、纯软件极易算，用于 IP/TCP/UDP 等**软件处理的上层**；CRC 开销数十位、能力最强（保证检出突发错）、适合硬件流水线，用于**链路层帧尾**。

一句话记忆：**越靠近物理线路、越用硬件、错误越以突发形式出现的地方，越用 CRC；越靠软件、越要便宜实现的地方，越用校验和。** 另需强调，三者都只是「检错」——真正的可靠交付要靠上层的确认/重传（链路层 ARQ 或传输层 TCP），检错码本身只负责「发现并丢弃坏帧」。

## N2.3 多路访问协议

### N2.3.1 多路访问问题与三类协议

当一条链路被**多个节点共享**（如早期以太网的同轴总线、WiFi 的无线电频段）时，若两个节点同时发送，信号会在介质上叠加而互相破坏，称为**冲突（collision）**。**多路访问协议（multiple access protocol）**，即媒体访问控制（MAC）协议，就是规定「谁在什么时候可以发」的规则，目标是在没有中央调度者的前提下高效、公平地共享信道。

Kurose-Ross 把 MAC 协议分为三大类：**信道划分协议（channelization）** 把信道按时间/频率/编码切成片各占各的；**随机接入协议（random access）** 让节点想发就发、冲突了再退避重试；**轮流协议（taking-turns）** 让节点有序地轮流使用信道。理解的钥匙是「有无冲突、有无浪费」这对权衡：信道划分无冲突但轻载时浪费（分给你的时隙你不用也空着），随机接入轻载时高效但重载时冲突频发，轮流协议试图折中。

### N2.3.2 信道划分：TDMA / FDMA / CDMA

**信道划分**把共享信道静态地分给各节点。**TDMA（时分多址）** 把时间切成周期性的时隙，第 i 个节点固定用第 i 个时隙；**FDMA（频分多址）** 把频段切成子频带各占一条；**CDMA（码分多址）** 给每个节点分配不同的正交编码，多个节点可同时同频发送，接收方靠编码把它们分离。

直觉上，TDMA 像「一间会议室按钟点轮流分给各部门开会」，FDMA 像「同一时间不同部门用不同的会议室」，CDMA 则像「一屋子人同时说不同的语言，你只听得懂说你那门语言的人」。它们的共性优点是**无冲突、带宽/时延有保证**；共性缺点是**静态分配下利用率低**——分给某节点的时隙/频带即便闲置，别人也不能用。所以它们适合流量稳定、连接数固定的场景（如蜂窝语音），不适合突发性强的数据网。

### N2.3.3 随机接入与 ALOHA

**随机接入协议**让节点在有数据时就以完整速率发送，不预先协调；一旦冲突，各冲突节点各自等待一段**随机**时间再重发（随机化是为了避免它们重试时又撞在一起）。最早的随机接入协议是 **ALOHA**。**纯 ALOHA（pure ALOHA）** 想发就发，理论最大信道利用率约 **1/(2e) ≈ 18%**；**时隙 ALOHA（slotted ALOHA）** 要求只能在时隙起点开始发，把「危险窗口」减半，最大利用率翻倍到约 **1/e ≈ 37%**。

初学者要抓住随机接入的核心矛盾：**没有预约、靠碰运气**。轻载时几乎不冲突、时延极低（想发就发，不用等时隙）；但节点一多、流量一大，冲突就急剧增加，大量信道时间浪费在被撞坏的传输上，利用率随之崩塌。ALOHA 本身效率不高，其价值是引出「先侦听再发、边发边听」的改进——也就是以太网的 CSMA/CD。

### N2.3.4 CSMA/CD：载波侦听 + 冲突检测

**CSMA/CD（Carrier Sense Multiple Access with Collision Detection，带冲突检测的载波侦听多路访问）** 是经典（共享介质）以太网的 MAC 协议，在 ALOHA 上加了两条规则。**载波侦听（carrier sense）**：发送前先听信道，若有人正在发就等它发完（「说话前先听有没有人在说」）。**冲突检测（collision detection）**：发送中持续监听，一旦发现自己的信号被别人的信号破坏（冲突），立即停发、发一段拥塞信号（jam）通知各方，然后退避重试——不必把整个坏帧发完，省下带宽。

冲突后的等待用**二进制指数退避（binary exponential backoff）**：第 n 次连续冲突后，节点从 {0, 1, 2, …, 2^m − 1}（其中 m = min(n, 10)）中**均匀随机**取一个数 K，等待

等待时间 = K × 512 比特时间

再重试（512 比特时间即发送 512 位所需的时长，为 10 Mbps 以太网的一个关键时间单位）。碰撞越多，随机范围越大，节点「主动错开」的力度越强，从而降低再次相撞的概率。初学者需理解两个「为什么」：为什么要**先听**（减少明显可避免的冲突）、为什么退避要**指数增长且随机**（拥塞时拉大间隔、随机化避免同步重撞）。此外 CSMA/CD 依赖能「边发边听、及时发现冲突」，这要求帧不能太短（最小帧长 64 字节即由此而来，保证发送时间足够长到能在最坏传播时延内察觉冲突）——这也是为什么它**只适用于有线共享介质，不适用于无线**（无线难以边发边听，见 N2.3.5）。

### N2.3.5 CSMA/CA：为何无线要「避让」而非「检测」

**CSMA/CA（… with Collision Avoidance，带冲突避免）** 是 WiFi（IEEE 802.11）用的 MAC 协议：同样先侦听信道，但**发送中不做冲突检测，而是事先尽量避免冲突**——发送前等一个随机退避时间，并可用 RTS/CTS 握手预约信道。

关键是理解**为什么无线不能照搬 CSMA/CD**。其一，无线网卡收发同频时，自己发出的强信号会淹没远处传来的弱信号，**难以「边发边听」检测到冲突**。其二，存在**隐藏终端（hidden terminal）** 问题：A 和 C 都能与中间的 B 通信，但 A、C 互相听不到，于是各自「侦听到信道空闲」而同时向 B 发，在 B 处冲突却谁都没察觉。既然检测不到冲突，无线只能改为**主动避免**（随机退避 + 预约 + 收到才回 ACK 确认）。本篇只作对照，无线接入的细节（隐藏/暴露终端、RTS/CTS、802.11 帧）见大主题 N10。

### N2.3.6 轮流协议：轮询与令牌传递

**轮流协议（taking-turns）** 试图兼得信道划分「无冲突」与随机接入「按需分配」的优点。两种代表：**轮询（polling）** 由一个主节点依次询问各从节点「你要发吗」，有数据就让它发（如蓝牙、某些下行网络）；**令牌传递（token passing）** 让一个特殊的小帧「令牌」在节点间按固定顺序传递，持有令牌者才能发送、发完把令牌交给下一个（如令牌环 Token Ring、FDDI）。

它们无冲突、能给出时延上界（适合实时/工业场景），代价是引入**单点与开销**：轮询依赖主节点（主节点故障则全网瘫）、有轮询时延；令牌传递中若令牌丢失需复杂的恢复机制，且轻载时也要等令牌转一圈。历史上令牌环曾与以太网竞争局域网，最终因以太网（尤其交换式以太网）更简单、更便宜、可平滑升速而胜出——今天局域网几乎清一色是交换式以太网，轮流协议主要作为原理性对照与特定领域（如工业现场总线）存在。

- 冲突项：无实质冲突。ALOHA 效率为教材公认理论值；退避「truncated binary exponential backoff」封顶 m=10 各来源一致。CSMA/CA 细节留 N10，本篇只作对照，未纵深。

## N2.4 MAC 编址与以太网帧

### N2.4.1 MAC 地址的语义

**MAC 地址（MAC address，又称物理地址 / LAN 地址 / 硬件地址）** 是链路层用来标识网络适配器的地址，长 **48 比特（6 字节）**，通常写成 6 组十六进制如 `02:fc:00:00:00:05`。它由 IEEE 统一管理分配以保证**全球唯一**：前 24 位是厂商标识 **OUI（Organizationally Unique Identifier）**，后 24 位由厂商自行分配。地址第一字节的两个低位有特殊含义——**I/G 位**区分单播（0）与组播/广播（1），**U/L 位**区分全球管理（0）还是本地管理（1）地址；全 1 地址 `FF:FF:FF:FF:FF:FF` 是**广播地址**。

初学者最该建立的是 **MAC 地址与 IP 地址的对比**。MAC 地址是**扁平（flat）、不含位置信息**的——它随网卡出厂固化，无论这块网卡插在世界哪个网络里都不变，类似「身份证号」；IP 地址是**层级（hierarchical）、随接入位置变化**的，类似「当前住址」，用于跨网路由。为什么两套地址都需要？因为它们服务不同层：IP 地址让数据报能被路由到正确的目的**网络**（跨网、可聚合），MAC 地址让帧能在**本地链路**上送到正确的网卡（一跳、就近）。一个数据报旅途中源/目的 IP 通常不变，而源/目的 MAC **每过一跳都改写**成本跳两端的网卡地址。

### N2.4.2 以太网帧格式

以太网帧（Ethernet II / DIX 格式）的字段与字节数如下（不含物理层前导）：

```
+----------+-----+----------+----------+-----------+---------------+-----+
| Preamble | SFD | Dest MAC | Src MAC  | Type/Len  |    Payload    | FCS |
|  7 字节  |1字节|  6 字节  |  6 字节  |  2 字节   |  46–1500 字节 |4字节|
+----------+-----+----------+----------+-----------+---------------+-----+
   物理层前导(8)              ├──────────── 帧本体，参与 CRC ──────────┤
```

各字段作用：**前导码（Preamble）7 字节 + 帧起始定界符（SFD）1 字节**用于收发时钟同步并标出帧的起点（属物理层，不计入帧长、不参与 CRC）；**目的 MAC / 源 MAC** 各 6 字节；**类型/长度（Type/Length）** 2 字节（见 N2.4.3）；**数据（Payload）** 承载上层数据报，46–1500 字节；**FCS** 4 字节，即 N2.2.4 的 CRC-32。

由此可算出帧长边界（不含 8 字节前导/SFD）：**最小帧 64 字节**（6+6+2+**46**+4；载荷不足 46 字节要填充 pad 补齐，最小帧长由 CSMA/CD 冲突检测需求决定，见 N2.3.4），**最大帧 1518 字节**（6+6+2+**1500**+4；1500 即以太网标准 **MTU**）。帧间还要求至少 **96 比特时间（12 字节）的帧间隔（interframe gap）** 空闲。初学者常把 MTU（1500，指载荷上限）与最大帧长（1518）混淆——MTU 说的是能装多少「乘客」，帧长还要加上「车头车尾」。

### N2.4.3 类型 vs 长度：DIX 与 802.3 的历史分账

那 2 字节的 Type/Length 字段有两种解读，这是初学者极易踩的坑。**Ethernet II（DIX）** 把它当**类型（EtherType）**，指示载荷是什么上层协议（如 `0x0800`=IPv4、`0x0806`=ARP、`0x86DD`=IPv6）；**原始 IEEE 802.3** 把它当**长度（Length）**，写载荷字节数。二者靠数值区分：

字段值 ≤ 1500 (0x05DC)  ⇒  解释为长度（IEEE 802.3）
字段值 ≥ 1536 (0x0600)  ⇒  解释为类型（EtherType / Ethernet II）

因为以太网最大载荷 1500，长度字段永远 ≤ 1500，而所有已分配的 EtherType 都 ≥ 1536，二者数值区间不重叠，网卡据此无歧义地判断。今天实际网络中**绝大多数帧是 Ethernet II（用 EtherType）**；这是历史上 DEC/Intel/Xerox 联盟版本与 IEEE 标准版本融合后遗留的兼容设计。理解这段分账，才不会在抓包看到 `0x0800` 时误以为是「长度 2048」。

### N2.4.4 以太网的演进

以太网从 1970 年代的 **10 Mbps 共享总线**（多台机器挂在一根同轴电缆上、靠 CSMA/CD 争用）一路演进到 **100 Mbps（快速以太网）、1 Gbps、10/40/100 Gbps 乃至更高**，物理介质从同轴电缆变为双绞线和光纤，拓扑从「共享总线」变为「以交换机为中心的星型」。贯穿这几十年演进的关键，是**帧格式基本不变**——今天的万兆以太网帧和当年的帧结构一脉相承，这种向后兼容是以太网能长盛不衰的核心原因。

一个重要的观念更新：**现代以太网几乎都是「交换式」的，CSMA/CD 已基本退出历史舞台。** 在交换式以太网里，每台主机通过独占的全双工链路连到交换机端口，收发各走一对线、不再共享介质、**不会发生冲突**，因此 CSMA/CD 与最小帧长这些为「共享总线」设计的机制在现代部署中不再实际触发（标准仍保留以向后兼容）。初学者要把「以太网 = CSMA/CD」这个旧等式更新为「共享式以太网才用 CSMA/CD；现代交换式以太网无冲突」——CSMA/CD 更多是理解 MAC 协议演进的历史锚点（详见 N2.5 交换机）。

## N2.5 交换机自学习与 ARP

### N2.5.1 链路层交换机：即插即用、对主机透明

**链路层交换机（switch）** 是现代局域网的核心设备，工作在第二层，任务是**接收入帧、并根据目的 MAC 地址有选择地转发到某个（或某些）出端口**。它有两个关键特性：**过滤（filtering）**（决定一个帧该不该转发，还是就地丢弃）与**转发（forwarding）**（决定转到哪个端口）。交换机对主机是**透明的**——主机以为自己在直接跟目的主机通信，感知不到中间交换机的存在；交换机也是**即插即用（plug-and-play）、自学习**的，无需任何配置就能工作。

初学者要建立的对比是「交换机 vs 集线器」。早期的**集线器（hub）** 是第一层设备，把从任一端口收到的比特**无脑广播到所有其他端口**，所有主机仍共享一个冲突域，必须靠 CSMA/CD 争用。而交换机**按 MAC 地址定向转发**，每个端口是独立的冲突域（配合全双工则根本无冲突），因此能同时进行多对通信、吞吐大增。这就是 N2.4.4 说的「现代以太网无冲突」的实现基础——是交换机让 CSMA/CD 退居幕后。

### N2.5.2 交换机自学习：MAC 地址表如何自动建立

交换机靠**自学习（self-learning）** 建立一张 **交换表 / MAC 地址表**，把「MAC 地址 → 出端口」的映射记下来。规则很简洁：每当一个帧到达某端口，交换机就记下它的**源 MAC** 与**入端口**（「地址 X 在这个方向」），并附一个时间戳；转发时查表——若目的 MAC 在表中且对应端口就是入端口，则**过滤**（同侧，无需转发）；若在表中对应别的端口，则**定向转发**到该端口；**若不在表中（或是广播地址），则泛洪（flooding）**——转发到除入端口外的所有端口。表项超过一定**老化时间（aging time）** 无更新就删除，以适应主机移动。

理解这套机制的巧妙在于：交换机**从流量中被动学习**，不需要任何人配置、也不需要主机配合。可以把它想成一个前台，一开始不知道谁坐哪，来一封信就看寄件人地址、记下「这个人从东门进来」；下次有信要送给这个人，就往东门送，不用再向全楼广播。「第一次未知就泛洪、之后定向」正是自学习的核心节奏——网络刚启动时泛洪较多，随着各主机陆续发过帧、表被填满，泛洪迅速减少、转发趋于精准。

### N2.5.3 ARP：从 IP 地址解析出 MAC 地址

主机要发送数据报时，网络层给的是目的**IP 地址**，但链路层封帧需要目的**MAC 地址**——**ARP（Address Resolution Protocol，地址解析协议）** 就负责在**同一子网内**把一个 IP 地址翻译成对应的 MAC 地址。每台主机维护一张 **ARP 表（ARP cache）**，缓存近期用过的「IP → MAC」映射及其 TTL。

解析流程是一次**广播请求 + 单播应答**：若目的 IP 不在 ARP 表里，源主机构造一个 **ARP 请求**帧，目的 MAC 填广播地址 `FF:FF:FF:FF:FF:FF`，内容大意是「谁的 IP 是 X？请把你的 MAC 告诉我」，泛洪到整个子网；持有该 IP 的主机（只有它）用**单播 ARP 应答**回复自己的 MAC，源主机收下并存入 ARP 表。本机 `/proc/net/arp` 里就能看到这类缓存表项，例如观察到：

```
IP address   HW type  Flags  HW address           Device
192.0.2.1    0x1      0x2    02:fc:00:00:00:05    eth0
```

其中 HW type `0x1` 表示以太网、Flags `0x2`（ATF_COM）表示该表项已完成解析、HW address 即解析出的 MAC。（本机 `cat /proc/net/arp` 实测 @2026-07-29；容器无 `ip`/`arp`/`tcpdump` 命令，故未能实抓 ARP 请求-应答报文，仅取到已完成的缓存表项。）

初学者常把 ARP 与 DNS 混淆——两者都是「解析/翻译」，但 **DNS 把主机名翻译成任意主机的 IP（跨全网）**，**ARP 把 IP 翻译成 MAC 且只在同一子网内**。ARP 是「即插即用」的：无需配置，缓存超时后自动重新解析。

### N2.5.4 同子网寻址 vs 跨子网寻址

一个常见困惑是：既然 ARP 只解析本子网内的 IP，那要发给**外网**主机时，目的 MAC 填谁的？答案是**填默认网关（路由器）的 MAC**，而不是最终目的主机的 MAC。判断逻辑：源主机用**子网掩码**比对目的 IP 是否与自己同一子网——同子网则 ARP 解析目的主机的 MAC、直接交付；不同子网则把帧发给**默认网关**（对网关的 IP 做 ARP、拿到网关 MAC），由路由器接力。

这正好收束了本篇与网络层的分工：**IP 地址决定「最终去哪个网络/主机」（端到端不变），MAC 地址决定「这一跳交给谁」（每跳改写）。** 发往外网时，帧的目的 MAC 是网关的、但数据报里的目的 IP 仍是远方主机的；路由器收到后剥掉旧帧头、根据 IP 查路由、对下一跳重新做 ARP、封上新的帧头再发。把「目的 MAC = 下一跳、目的 IP = 最终目的」这组对照记牢，链路层与网络层的接力关系就通了。

## N2.6 VLAN 与数据中心链路层（可选）

### N2.6.1 VLAN：在一台交换机上切出多个逻辑局域网

**VLAN（Virtual Local Area Network，虚拟局域网）** 允许在同一套物理交换机上划分出多个相互**隔离的逻辑局域网（广播域）**。例如把一台 16 口交换机的端口 1–8 划给「工程部 VLAN」、9–16 划给「财务部 VLAN」，两组端口之间的广播（如 ARP 请求）互不可见、二层不可直达，如同两台物理上分开的交换机——尽管它们其实共用一台设备。VLAN 间要通信必须经过三层设备（路由器 / 三层交换机）。

对初学者，VLAN 解决的痛点是「**不用重新布线就能重划网络边界**」。传统上要隔离两个部门得买两台交换机、拉两套线；有了 VLAN，改配置即可，一个人换部门只需把其端口划到另一个 VLAN。隔离带来两个直接好处：**限制广播风暴的范围**（广播只在本 VLAN 内泛洪，规模可控）与**安全隔离**（不同 VLAN 默认二层不可达）。

### N2.6.2 802.1Q 帧标记与 Trunk

当一个 VLAN 跨越多台交换机时，交换机之间的**干道链路（trunk）** 上会同时跑多个 VLAN 的帧，需要给每个帧打标签标明它属于哪个 VLAN——这就是 **IEEE 802.1Q** 定义的 VLAN 标记（tag）。它是插在源 MAC 与 Type/Length 之间的 **4 字节**字段：

```
+----------+----------+========================+----------+---------+-----+
| Dest MAC | Src MAC  | 802.1Q Tag (4 字节)    | Type/Len | Payload | FCS |
+----------+----------+========================+----------+---------+-----+
                        │ TPID(16) │ PCP(3) │ DEI(1) │ VID(12) │
                        │ =0x8100  │优先级  │丢弃标记│VLAN 号  │
```

各字段的含义如下。**TPID** 16 位固定为 `0x8100`（标识这是 802.1Q 标记帧）；**PCP** 3 位是优先级（802.1p CoS，用于 QoS）；**DEI** 1 位丢弃资格标记（旧称 CFI）；**VID** 12 位是 VLAN 号，有效范围 **1–4094**（0 表示「仅优先级、无 VLAN」，4095 保留），故最多约 4094 个 VLAN。打了 tag 后以太网**最大帧从 1518 增至 1522 字节**。发送方交换机在帧进入 trunk 时插入 tag、接收方交换机在帧离开 trunk 送往目的端口前去掉 tag，对终端主机透明。

初学者记住一条主线即可：**VID 这 12 位就是「这个帧属于哪个 VLAN」的编号**，trunk 靠它在一条物理线上区分并复用多个 VLAN 的流量；4094 这个上限正是 12 位可用编号的结果，也是传统 VLAN 在超大规模数据中心里不够用、催生 VXLAN 等 overlay 技术的原因。

### N2.6.3 数据中心链路层拓扑（概念）

数据中心内部有海量服务器，其链路层网络与办公室局域网的最大不同是**追求高对分带宽（bisection bandwidth）与多路径**。典型采用**分层的胖树 / Clos 拓扑**（接入层 ToR 交换机 → 汇聚层 → 核心层），任意两台服务器之间存在**多条等价路径**，靠多路径负载均衡（如 ECMP）把流量摊开，避免单点成为瓶颈，也提供冗余容错。

对本篇而言，只需建立「数据中心为了扛住东西向（服务器间）巨量流量，链路层拓扑被设计成富含冗余路径的多层结构」这一图景即可。其纵深（Clos/胖树的严格构造、流量工程、拥塞控制）超出本大主题范围，本节按 prompt 定位为「查全补位/可选」，仅作概念覆盖，不做展开。
