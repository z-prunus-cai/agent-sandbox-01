## 8.1 赋值与局部状态的代价

### 8.1.1 局部状态变量与赋值的引入

在此之前（大主题7 的函数式风格里），一个过程的输出只由它的输入决定，程序像一组数学函数的组合。**赋值**（Scheme 的 `set!`、Python 的 `=` 对已有名字的重新绑定）打破了这一点：它允许一个变量随时间被改写，于是过程可以携带**局部状态**——同样的调用，因内部状态不同而给出不同结果。

SICP §3.1.1 的经典例子是"带余额的取款器"。每次调用同一个 `withdraw`，余额都在变：

```python
def make_withdraw(balance):
    def withdraw(amount):
        nonlocal balance      # 声明修改的是外层帧里的 balance，而非新建局部名
        balance -= amount
        return balance
    return withdraw

w = make_withdraw(100)
print(w(25), w(25))
# => 75 50
```

这里 `balance` 就是一个**局部状态变量**：它被 `make_withdraw` 创建、被返回的 `withdraw` 独占并反复修改，外界无法直接访问。这正是"对象=状态+行为"（大主题3）在函数式外壳下的最小实现——一个闭包 + 一处可变绑定，就构成了一个有记忆的对象。

初学者要抓住的关键动作是 `nonlocal`：没有它，`balance -= amount` 会被 Python 当成"在 `withdraw` 内新建一个叫 `balance` 的局部变量再读它"，从而报 `UnboundLocalError`。`nonlocal` 告诉解释器"我要改的是外层那个已存在的绑定"——这一步就是"赋值引入局部状态"的字面兑现，也预告了 8.2 环境模型要解释的"到底改的是哪一帧里的哪个绑定"。

### 8.1.2 引用透明性被破坏

一个表达式若**引用透明**（referential transparency），意味着可以用它的值就地替换它而不改变程序含义——这是大主题7 纯函数的核心性质。一旦某过程内部有可变状态，同一个调用在不同时刻会返回不同的值，替换就不再安全：表达式不再"等于"某个固定的值。

```python
counter_state = {'n': 0}
def impure():
    counter_state['n'] += 1
    return counter_state['n']
print(impure(), impure(), impure())
# => 1 2 3       同一个无参调用，三次结果不同 —— 不再引用透明

def pure(n):
    return n + 1
print(pure(5), pure(5), pure(5))
# => 6 6 6       同一调用永远同值 —— 引用透明
```

数学里 `f(5)` 就是一个确定的数，你可以把它抄写、缓存、重排、并行计算，含义都不变。`impure()` 却不能——它的"值"取决于"这是第几次调用"。于是许多在函数式世界里理所当然的推理（代入化简、公共子表达式提取、缓存、乱序求值）在有状态代码里统统失效。

一个更隐蔽的后果是求值顺序开始变得要紧。纯表达式里 `a + b` 先算 `a` 还是先算 `b` 无所谓；但若 `a`、`b` 是两个都会改动同一状态的调用，顺序就决定结果。这就是把"何时、以何顺序求值"从无关紧要提升为程序正确性的一部分——8.2 的环境模型正是用来精确回答这类问题的工具。

### 8.1.3 代价：sameness 与 change 的哲学难题

SICP §3.1.3 把这一节直接命名为"引入赋值的代价"。核心论点是：一旦对象可变，"两个东西是否相同"就变成了一个棘手问题。

考虑两个初始余额都是 100 的账户 `a` 和 `b`。它们此刻"看起来一样"，但它们不是同一个对象——改 `a` 不影响 `b`。反过来，同一个账户在两个时刻余额不同，它却仍是"同一个账户"。于是"相同"分裂成两种含义：**值相等**（此刻内容一样）与**身份相同**（是同一个可变对象，改一个另一个跟着变）。Python 用两个运算符把它们分开：

```python
a = [1, 2, 3]
b = a            # b 与 a 是同一个对象（别名）
c = [1, 2, 3]    # c 是内容相同的另一个对象
print(a == c, a is c)   # => True False   值相等，但不是同一个
print(a == b, a is b)   # => True True    值相等，且是同一个
b.append(4)
print(a)                # => [1, 2, 3, 4]  改 b 就是改 a
```

在纯不可变世界里根本不需要区分这两者——不可变对象没有"改一个另一个变"的问题，值相等就够了。是赋值/可变性逼出了 `==` 与 `is` 之分。

这也是为什么函数式风格反复强调不可变：放弃可变状态，就换回了引用透明、可自由代入、可无脑并行、无需担心别名的推理简单性。代价则是有些东西（计数器、账户、缓存、I/O）天然是有状态的，硬用不可变表达会绕远。大主题8 的整条主线就是在权衡这笔账：状态给了我们贴近现实的建模能力，同时拿走了函数式的推理简单性，8.2–8.4 分别处理"如何精确解释它""它会怎么咬人""如何用延迟求值缓解"。

## 8.2 环境模型的求值

### 8.2.1 为什么需要环境模型

大主题7 之前用的是**替换模型**（substitution model）：调用过程就是把参数值代入过程体、再化简。它简单，但一遇到赋值就崩——8.1 已说明，有了可变状态，一个变量不再"等于"一个固定值，你没法把它"代入"。SICP §3.2 因此引入**环境模型**：不再谈"代入什么值"，而是谈"变量在什么环境里绑定到什么"。

环境模型把"变量"理解为"某个帧里的一条绑定"，把"求一个表达式"理解为"在某个环境里查绑定、并可能新建帧"。替换模型问"这个符号代表哪个值"，环境模型问"这个符号在当前环境链上绑定到哪个位置"——后者才装得下"位置里的值会变"这件事。

### 8.2.2 帧、绑定与环境链

一个**帧**（frame）是一张"名字→值"的绑定表。一个**环境**（environment）是一串帧构成的链条：每个帧有一个指向**外层帧**（enclosing environment）的指针，链的尽头是全局帧。变量的值，就定义为"在当前帧里找该名字；找不到就沿指针到外层帧继续找；直到全局帧"。

```python
x = 10                 # 绑定进全局帧
def outer():
    x = 20             # outer 被调用时的帧里新建绑定 x=20
    def inner():
        return x       # inner 帧里没有 x，沿链到 outer 帧找到 20
    return inner()
print(outer(), x)
# => 20 10
```

`inner` 返回 20 而不是 10，正是"沿环境链**由内向外**逐帧查找、就近命中"的结果——它先撞上 `outer` 帧的 `x=20`，就不再往全局走了。这条链就是 L1-01 讲的 **LEGB**（Local → Enclosing → Global → Built-in）规则的机制本体：LEGB 的四层，就是环境链上从内到外的四种帧。

初学者常把"作用域"当成一块静态的文本区域，环境模型给出更准的图像：作用域是**运行时真实存在的一串帧**，查名字就是在这串帧上走指针。谁是谁的外层，由代码**书写时的嵌套位置**决定（词法作用域），而不是由"谁调用了谁"决定——这点在 8.2.4 展开。

### 8.2.3 过程的求值规则：过程是"体 + 定义环境"

环境模型下，一个过程对象不只是一段代码，而是一对东西：**过程体**加上**它被定义时所处的那个环境**（Python 里就是函数对象的 `__closure__` 抓住的外层帧）。这一点是理解闭包和局部状态的关键。

调用一个过程时的规则（SICP §3.2.1）分两步：

```text
1. 新建一帧，把形参绑定到实参值；
   这一帧的外层指针，指向【过程被定义时所在的环境】（不是调用它的地方）。
2. 在这个新环境里求过程体。
```

第 1 步末句是全部微妙之处所在："新帧的外层 = 过程的定义处"。这就是为什么 8.1 的 `make_withdraw` 能工作：每次调用 `make_withdraw(100)` 都新建一帧、把 `balance` 绑成 100，返回的 `withdraw` 记住的正是这一帧；此后每次调用 `withdraw`，它新建的帧的外层指针都指回那一帧，于是 `nonlocal balance -= amount` 改的始终是同一处绑定——局部状态就这样在帧里存活下来。

### 8.2.4 变量查找是词法的，赋值只动当前帧

环境模型精确回答两件初学者最容易混的事：查找沿"定义时的嵌套链"（词法/静态作用域），而普通赋值只在**当前帧**新建或改写绑定，不会穿透到外层。

```python
def f():
    y = 1
    def g():
        y = 100      # 在 g 自己的帧里新建 y，与 f 的 y 无关
        return y
    r = g()
    return (r, y)
print(f())
# => (100, 1)        g 改的是自己帧里的 y，f 的 y 仍是 1
```

`g` 里的 `y = 100` 没有影响 `f` 的 `y`，因为一条普通赋值语句的语义是"在**当前帧**里绑定这个名字"。想改外层帧的绑定，必须显式用 `nonlocal`（改最近的外层函数帧）或 `global`（改全局帧）——这正对应 8.1.1 里 `nonlocal balance` 的必要性。

词法作用域的含义是：`inner` 能看见哪些外层变量，只看**代码写在哪里**，与"从哪里调用它"无关。把 `inner` 传到别处再调用，它查名字仍沿定义时的链走。这与"动态作用域"（按调用链查找）相对，绝大多数现代语言（含 Scheme、Python）用词法作用域，因为它让"一段代码引用的变量"在阅读时就能静态确定，可推理性强得多。

## 8.3 可变数据与共享风险

### 8.3.1 可变数据对象与就地修改

可变数据结构允许**就地修改**已有对象的内容而不新建对象。SICP §3.3 用 `set-car!`/`set-cdr!` 改 pair 的字段；Python 里 `list.append`、`d[k]=v`、`obj.attr=x` 都是就地修改。它是 8.1 局部状态的自然延伸——不只是"一个变量能改"，而是"一个复合对象的内部能被原地改写"。

就地修改带来效率与建模便利（无需每次复制整个结构），但也带来本小主题的主题：一旦多个名字指向同一个可变对象，透过任何一个名字的修改，对其余名字**全部可见**。这在纯不可变数据里根本不会发生。

### 8.3.2 别名与身份

**别名**（aliasing）指两个或多个名字绑定到**同一个**对象。8.1.3 已用 `is` 与 `==` 区分过"同一个"与"内容相同"；这里强调它的危险面：别名下的修改是"远程生效"的。

```python
a = [1, 2, 3]
b = a            # b 是 a 的别名，指向同一个 list
b.append(4)
print(a, a is b)
# => [1, 2, 3, 4] True     改 b 就改了 a
```

初学者常带着"变量是盒子、赋值是拷贝"的错误直觉。Python 的真相是"变量是贴在对象上的标签"，`b = a` 只是给同一个对象多贴一张标签，没有复制。判断某处修改会不会"波及别处"，就看有没有别名、以及改的是不是可变对象——这是 8.1.2"求值顺序变得要紧""缓存不再安全"在数据层面的具体体现。

把可变对象作为参数传进函数，函数内的就地修改会改到调用方的对象（L1-01 3.2 的"可变实参被改"）。想要"传进去一份不受影响的副本"，需显式浅拷贝 `list(x)`/`x[:]` 或深拷贝 `copy.deepcopy(x)`；浅拷贝只复制最外层，嵌套的可变子对象仍是共享的，这是别名问题的二阶陷阱。

### 8.3.3 可变默认参数陷阱

这是 Python 里最著名的别名/可变性坑，源于一条常被忽视的语义：函数的**默认参数值在函数定义时只求值一次**，此后所有未显式传参的调用**共享同一个**默认对象。若这个默认值是可变的（如 `[]`），它就成了一个跨调用累积的隐藏状态。

```python
def add_item(x, bag=[]):     # bag 的 [] 只在 def 执行时建一次
    bag.append(x)
    return bag
print(add_item(1), add_item(2), add_item(3))
# => [1, 2, 3] [1, 2, 3] [1, 2, 3]   三次调用共用同一个 list，越积越多
```

预期里三次应各得 `[1]`、`[2]`、`[3]`；实际三次操作的是同一个列表对象。这正是 8.2.3 的规则在起作用：默认值绑定在函数对象上（定义环境里那一处绑定），不随每次调用重建。

惯用的修法是用 `None` 哨兵，在函数体内每次新建：

```python
def add_item(x, bag=None):
    if bag is None:
        bag = []             # 每次调用都新建，互不共享
    bag.append(x)
    return bag
print(add_item(1), add_item(2))
# => [1] [2]
```

"默认参数用不可变值（`None`/数字/字符串/元组）是安全的；用可变值（`list`/`dict`/`set`）几乎总是 bug。"根因不是 Python 设计失误，而是"默认值也是一处只求值一次的绑定"这一环境模型事实，与可变性相撞的结果。

### 8.3.4 共享状态的意外修改与防御

把别名、可变实参、可变默认值合起来看，共同的失败模式是：**某处修改在另一处以非预期方式显现**，因为它们暗中共享同一个可变对象。这类 bug 难查，正因为"改的地方"和"出问题的地方"在代码上离得很远。

防御手段有三条主线，按代价递增：一是**尽量用不可变类型**（`tuple`/`frozenset`/具名元组），从根上消除"能被改"；二是在**边界处复制**，凡把可变对象交出去或收进来就 `copy`/`deepcopy` 一份，切断别名；三是**约定所有权与不修改契约**（谁负责修改这个对象、其余只读），用文档与代码审查兜住。

这也解释了为什么大主题7 反复推不可变、为什么函数式风格在并发场景格外吃香：没有可变共享，就没有"意外修改"这一整类 bug。把这条线推到多线程/多进程真正并行修改同一状态时，就升级为数据竞争与内存可见性问题——那属于并发的深挖，本报告按边界显式归 L4-05，此处只到"单线程内共享可变对象已足够危险"为止。

## 8.4 流与惰性求值（引申）

### 8.4.1 流的思想：把求值延后

**流**（stream）是 SICP §3.5 给出的一种数据结构，直觉上是"元素按需才计算的序列"。它靠**延迟求值**（delayed evaluation）实现：构造流时并不立刻算出后续元素，而是把"如何算出下一段"打包成一个待触发的过程（Scheme 里用 `delay` 造、用 `force` 触发；`(delay expr)` 大致等价于 `(lambda () expr)`，`force` 就是调用它）。

```text
delay(expr)  ~  记住"以后要算 expr"，现在不算
force(p)     ~  真正去算，得到值
```

这套机制的意义在于 SICP §3.5 开篇的论点：流让我们能用**函数式的、看似整体处理序列**的写法，去描述本质上随时间演化的过程，从而**不引入显式赋值和局部状态**也能建模"随时间变化的量"。换句话说，流是 8.1–8.3 那条"状态的代价"的一个对冲方案——把"变化"重新表达为"一个（可能无穷的）不可变序列上的映射"，把可变性从代码里挤出去。

Python 没有内建 `delay`/`force`，但**生成器**（generator）提供了等价的按需求值：函数里出现 `yield`，调用它只返回一个生成器对象、函数体一行都没跑，直到被 `next()`/迭代逐步驱动才算出下一个值。

### 8.4.2 无穷流与生成器

延迟求值最亮眼的用途是**无穷序列**：因为元素按需才算，你可以定义"所有自然数""所有素数"这样永不终止的流，只要消费方只取有限个，就永远算不到尽头、也不会耗尽内存。

```python
def integers_from(n):
    while True:          # 表面是死循环
        yield n
        n += 1

def take(k, it):
    return [next(it) for _ in range(k)]

print(take(5, integers_from(1)))
# => [1, 2, 3, 4, 5]

squares = (x * x for x in integers_from(1))   # 无穷流上再叠一层惰性映射
print(take(5, squares))
# => [1, 4, 9, 16, 25]
```

`integers_from` 的 `while True` 若在普通函数里会挂死，但作为生成器它只在被 `next` 驱动时才走一圈、产出一个数就"暂停"在 `yield` 处等下次。`squares` 展示了流的组合性：在无穷流上再套一个惰性变换，仍是无穷流、仍不立刻计算——这正对应 SICP 用流做筛法（如埃拉托斯特尼素数筛）的写法。

把生成器想成一条"拉一下动一步"的传送带，而不是"一次造好一整箱"的容器。列表是"急切"的（一次算全、占全部内存），生成器/流是"惰性"的（要一个算一个、内存恒定）。

### 8.4.3 惰性的收益：按需计算与记忆化

惰性求值的两大收益，一是**只算用得到的部分**（上面无穷流即是极端例），二是可与**记忆化**（memoization）结合，让已经算过的元素不重复算。

SICP §3.5 特别强调：Scheme 版流的 `delay` 用一个 `memo-proc` 包装，使得同一个延迟对象被 `force` 多次时**只真正计算一次**、之后返回缓存值。这对流的性能是本质的——否则递归定义的流（如斐波那契流）会指数级重算。这与大主题7/4.3 讲的"朴素斐波那契指数爆炸"是同一个问题的两面：记忆化把重叠子问题的重复计算消掉。

需要分账的一处**规范 vs 实现差异**：SICP 的流默认带记忆化；而 Python 生成器**不自动缓存**——它是一次性的前向游标，每个值只产出一次、消费即弃。要"重复取用同一个流的元素"，得自己 `itertools.tee` 或落地成 `list`；要函数级记忆化则用 `functools.lru_cache`/`cache`。这一点初学者极易误以为"生成器能像列表一样反复遍历"。

### 8.4.4 陷阱：一次性耗尽与副作用时机

惰性带来的两个高频陷阱，都是"计算被推迟"这件事的副作用。

第一是**一次性耗尽**：生成器被迭代完就空了，再迭代什么都没有。

```python
g = integers_from(10)
print(next(g), next(g))
# => 10 11     游标前进后不回头；已产出的值不会再来
```

第二是**副作用的时机被推迟**：如果生成器体内有 `print`/写文件/改状态等副作用，它们**不在创建时发生，而在被消费到那一步时才发生**。

```python
def noisy():
    for i in range(3):
        print("  producing", i)
        yield i

gen = noisy()          # 此刻不打印任何东西
for v in gen:          # 消费时才逐步触发副作用
    print("  got", v)
# =>   producing 0
# =>   got 0
# =>   producing 1
# =>   got 1
# =>   producing 2
# =>   got 2
```

创建 `noisy()` 时一行都没跑；直到 `for` 逐个拉取，`producing i` 才与 `got i` 交错出现。这与 8.1.2"求值顺序变得要紧"呼应，但更棘手——惰性把"这段代码到底何时执行"从书写顺序里剥离了。若生成器里读的是一个会变化的外部状态，等到消费时状态可能已经变了，产出的就不是你以为的值。经验法则："把副作用留在急切代码里，让惰性流只做纯计算"——这又回到了大主题7 的"纯核心、薄壳"。
