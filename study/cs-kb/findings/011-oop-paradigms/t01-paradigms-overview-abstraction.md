## 1.1 命令式/过程式范式 — 语句序列 + 状态变更

### 1.1.1 命令式范式是什么

命令式（imperative）编程把程序看成一串**依次执行的语句**，每条语句通过**修改状态**（给变量赋值、改写内存/数据结构）来一步步逼近结果。它回答的是「怎么一步步做（how to）」这个问题：先做什么、再做什么、循环到什么条件为止。SICP 在 §1.1.7 把这种「描述怎么做」的知识叫做**命令性知识（imperative knowledge）**，与数学里「描述是什么」的**声明性知识（declarative knowledge）**相对：

描述性（declarative, what is）：y 是使 y² = x 成立的那个非负数

命令性（imperative, how to）：从猜测 g 出发，反复令 g ← (g + x/g)/2 直到 g² 足够接近 x

上面第二行才是一个可执行的、靠反复改写 `g` 的值来推进的命令式过程。

命令式是 L1-01 里「默认写法」的正式名字：你在入门时写的 `for` 循环累加、`if` 分支、给变量重新赋值，那一整套就是命令式风格。本大主题把它"升华"为一个有名字、有对立面的范式，好让你之后能有意识地在它和别的范式之间切换。

### 1.1.2 赋值与可变状态是命令式的核心机制

命令式风格的灵魂是**赋值（assignment）**——同一个名字在不同时刻可以绑定不同的值，程序的意义依赖于「执行到这一行时状态是什么」。这也意味着语句的**顺序至关重要**：交换两条赋值语句往往会改变结果。

初学者的直觉抓手是「照菜谱做菜」：菜谱是一串按顺序执行的动作（切、炒、加盐），每个动作都在改变锅里的状态，顺序错了菜就毁了。命令式程序就是给机器的菜谱。

一个最小例子说明"顺序即语义"：

```python
x = 1
x = x + 1   # 现在 x 是 2
x = x * 10  # 现在 x 是 20
```

把后两行对调，结果就从 20 变成 11。这正是命令式与后面函数式最本质的区别——函数式里表达式的值不依赖"执行到哪一步了"。

### 1.1.3 过程式是命令式加上过程抽象

过程式（procedural）编程是命令式的一个子风格：在"语句序列 + 状态变更"之上，用**过程/函数（procedure）** 把语句序列打包、命名、复用。C、早期 Pascal 是典型过程式语言。二者关系可以记成：所有过程式程序都是命令式的，但过程式额外强调"把命令式代码组织成可调用的过程"。

区分它俩不必太较真——很多文献把 imperative 和 procedural 近乎混用。要点是：命令式描述的是"靠改状态推进"这一大类风格，过程式强调其中"用过程做模块化"的组织手段。SICP 全书的第一层抽象（§1.1 的 procedure）正是过程抽象，它让你不必每次都重写那串语句，只需调用一个名字。

### 1.1.4 三范式对照中的过程式版本

用同一个问题——「求列表中所有偶数的平方和」——贯穿本报告的四个范式，最能看清差异。命令式/过程式版本靠一个不断被改写的累加器变量推进：

```python
def sum_even_squares_imperative(data):
    total = 0                 # 可变状态
    for x in data:            # 语句序列
        if x % 2 == 0:
            total += x * x    # 状态变更
    return total
```

它读起来就是一份菜谱：备一个 `total`，逐个看元素，是偶数就把它的平方加进去。对 `[1,2,3,4,5]` 结果是 20（2²+4²）。

### 1.1.5 命令式的代价与易错点

命令式最大的隐患是**共享可变状态带来的推理困难**：当多处代码可以改同一个变量/对象，你必须在脑中追踪"执行到此刻它到底是什么"，程序越大越难。这也是引入赋值的代价——SICP §3.1.3 专门讲"赋值的代价"，它会破坏"同样输入必得同样输出"这一性质（见 1.3 引用透明）。初学者常见的坑是循环里忘了重置累加器、或两个变量意外指向同一个可变对象（别名），这些都是"状态被谁改了"追踪失败的表现（详见本课大主题 8）。

## 1.2 面向对象范式概览 — 对象 + 消息

### 1.2.1 面向对象范式是什么

面向对象（object-oriented, OO）编程把程序组织成一堆**对象**，每个对象把**局部状态（数据）** 和**作用在该状态上的行为（过程）** 捆在一起，对象之间通过**发消息（调用方法）** 相互协作。SICP §3.1 开篇给出这一范式的世界观：

> 我们通常把世界看成由一个个独立的对象组成，每个对象都有随时间变化的状态。

一个对象"有状态"的判据是：它的行为受自身历史影响。SICP 的经典例子是银行账户——能不能取款取决于此前存过取过多少，所以账户是个有状态的对象。

### 1.2.2 SICP 用消息传递刻画对象

SICP 不预设"类"这个语法，而是用**闭包 + 消息分派**从零构造对象：`make-account` 返回一个 `dispatch` 过程，它「接收一个『消息』作为输入，返回对应的局部过程」。SICP 明确说这正是 §2.4.3 见过的**消息传递（message-passing）** 风格，只不过这里叠加了"修改局部变量"的能力。

它说明**对象不是语言天生的魔法**，而是"把状态藏在局部、只暴露一组按名字选择的操作"这一模式的产物。"给对象发消息 `withdraw`"和"调用对象的 `withdraw` 方法"是同一件事的两种说法。

### 1.2.3 三范式对照中的 OO 版本

同一个「偶数平方和」问题，OO 版本把累加器包成一个带局部状态的对象，通过发消息 `add` 来推进：

```python
class EvenSquareAccumulator:
    def __init__(self):
        self._total = 0          # 局部状态，藏在对象里

    def add(self, x):            # 行为：一条消息
        if x % 2 == 0:
            self._total += x * x
        return self._total

    @property
    def total(self):
        return self._total

acc = EvenSquareAccumulator()
for x in [1, 2, 3, 4, 5]:
    acc.add(x)
# acc.total == 20
```

对比 1.1.4 的过程式版本，能看出 OO 只是把"可变的 `total`"从散落的局部变量，收进了一个负责看管它的对象里——**OO 本质上是被有纪律地组织起来的命令式**：状态仍在变，但谁能改、怎么改被对象的接口约束住了。

### 1.2.4 常见误解与关联

初学者常把"面向对象"等同于"用了 `class` 关键字"。更准确的判据是：程序的组织单位是不是"状态 + 行为捆在一起、靠消息协作的对象"。你完全可以用 `class` 写出一堆没有封装、纯过程式的代码；也可以像 SICP 那样不用 `class`、仅靠闭包实现对象。OO 的三支柱（封装/继承/多态）、方法查找与派发机制是本课大主题 3、4 的主题，这里只立"对象 + 消息"这个总观。

## 1.3 函数式范式概览 — 表达式 + 无副作用

### 1.3.1 函数式范式是什么

函数式（functional）编程把计算看成**表达式的求值**：程序主要由"输入到输出的纯函数"组合而成，尽量**不做副作用**（不改变量、不改外部状态、不做 I/O）。SICP §1.3 把重心放在**高阶过程（higher-order procedures）**——能接收函数作参数、能返回函数的过程——它是函数式组合能力的来源。

与命令式最尖锐的对立在于：函数式里一个表达式的值**不依赖"执行到第几步"**，因此语句顺序不再是语义的一部分。你可以像做数学代数一样，把 `f(3)` 直接替换成它的值来推理。

### 1.3.2 引用透明与纯函数

函数式的关键性质叫**引用透明（referential transparency）**：一个表达式总可以被它的值替换而不改变程序意义。等价地，对纯函数 f 与相同输入 x：

f(x) 恒等于 f(x)，且求值 f(x) 不改变任何外部状态

满足"相同输入必得相同输出、且无副作用"的函数就叫**纯函数（pure function）**。SICP §3.1.3 反过来点明：一旦引入赋值，"同一过程用同样参数求值两次会得到同样结果"这一性质就不再成立——这正是函数式刻意回避赋值的原因。

初学者的抓手是"数学函数 vs 现实动作"：`sin(30°)` 永远是 0.5，问一百次都一样、也不会改变世界；而"往账户存 100 元"每次都改变余额、结果依赖历史。函数式追求把程序尽量写成前者。

### 1.3.3 三范式对照中的函数式版本

同一个「偶数平方和」，函数式版本用 `filter`/`map`/`reduce` 把数据流"变换"出来，全程不出现被改写的变量：

```python
from functools import reduce

def sum_even_squares_functional(data):
    evens    = filter(lambda x: x % 2 == 0, data)
    squares  = map(lambda x: x * x, evens)
    return reduce(lambda a, b: a + b, squares, 0)
# sum_even_squares_functional([1,2,3,4,5]) == 20
```

没有 `total = 0` 再 `total += ...` 这种状态改写，只有"筛出偶数→各自平方→加总"三步纯变换的**组合**。这些高阶序列操作（map/filter/reduce）是本课大主题 7 的正题，这里只作范式定位。

### 1.3.4 边界与易错点

函数式不等于"绝不碰状态"——真实程序总要做 I/O，务实的做法是把副作用**隔离到程序边缘**、让核心保持纯（本课大主题 7.5）。初学者易踩的坑是闭包的**晚绑定**、以及把可变对象当默认参数（归大主题 7、8）。另一个常见误会是"用了 lambda 就是函数式"：判据不是语法糖，而是"是否靠无副作用的表达式求值来组织计算"。

## 1.4 声明式/逻辑式范式概览 — 描述「是什么」

### 1.4.1 声明式范式是什么

声明式（declarative）编程让你**描述「想要什么结果（what is）」，而把「怎么算出来（how to）」交给系统**。SICP §1.1.7 的那对概念在这里是总纲：

声明性知识：说明结果应满足什么性质（what is）

命令性知识：给出得到结果的步骤（how to）

命令式/OO/函数式都偏向"给步骤"，而声明式把重心挪到"给规格、给关系"。SQL（说清要哪些行，不说怎么扫表）、正则、逻辑编程都属这一大类。函数式常被看作声明式的一支，因为它也强调"表达式描述的是什么值"而非"怎么一步步改状态"。

### 1.4.2 逻辑式：用关系而非函数，"一个 what 解多个问题"

逻辑式（logic）编程是声明式的一个突出分支：你陈述**事实与规则（关系）**，系统靠**合一（unification）** 和搜索去求解。SICP §4.4 的核心洞察是——传统语言算的是"单向、单值的函数"，而逻辑编程里"表达式可以有多个值，计算处理的是关系而非单值函数"。

最漂亮的例子是 `append`：只写一条"两个表如何拼接"的声明性规则，就能反过来用——既能算"A 接 B 得什么"，也能问"什么表接上 A 能得到某结果"，甚至枚举"哪些表对能拼出某结果"。SICP 原话是：一条"是什么"的事实，可以解决若干个各自需要不同"怎么做"成分的问题。这就是声明式相对命令式的杠杆：一次描述、多向使用。

### 1.4.3 三范式/声明式对照中的 Python 写法

Python 不是逻辑式语言，但**列表/生成器推导**带有明显的声明式味道——你描述"要满足什么条件的哪些元素"，而不写累加循环：

```python
def sum_even_squares_declarative(data):
    return sum(x * x for x in data if x % 2 == 0)
# sum_even_squares_declarative([1,2,3,4,5]) == 20
```

读法是"把每个满足 `x % 2 == 0` 的 `x` 取平方再求和"——一句"是什么"的描述，循环与累加的"怎么做"被 `sum` 和推导语法接管了。这只是声明式风味的类比，真正的逻辑式（Prolog / SICP 的查询系统）还有合一与回溯，不是 Python 原生能力。

### 1.4.4 边界：此处仅广度，深挖归 L5-06

声明式/逻辑式的机制深挖——合一算法、回溯搜索、非确定性求值、元循环求值器——显式归 L5-06（编程语言理论）与本课大主题 9（选修广度）。本节只需建立"存在一类范式：你说想要什么、不说怎么做"这个总观，以及"逻辑式=用关系描述、可多向求解"这个直觉，不展开求解引擎。初学者别把"声明式"误当成"高级/更好"——它只是把控制权让给了系统，代价是可控性和性能可预测性下降。

## 1.5 抽象作为复杂度管理 — 范式=风格而非语言、多范式融合

### 1.5.1 三大抽象机制：所有范式共享的地基

无论哪种范式，"抽象"都是它们共同的复杂度管理工具。SICP §1.1 开篇给出任何强大语言都具备的三种机制：

- 基本表达式（primitive expressions）：语言直接关心的最简单实体；
- 组合手段（means of combination）：由简单元素构造复合元素；
- 抽象手段（means of abstraction）：给复合元素命名、当作整体来操纵。

抽象的作用是**竖起屏障、隐藏细节**：给一段复杂东西起个名字，之后就能"当作一个整体来用"，不必每次都想它内部。命令式用过程抽象，OO 用对象/类抽象状态，函数式用高阶函数抽象控制模式，声明式用关系/规则抽象求解过程——**范式的差异在于"用什么当抽象单位"，而抽象本身是共同的复杂度管理手段**。

### 1.5.2 范式是风格/方法论，不是语言

"范式（paradigm）"这个词进入编程，公认源自 Robert Floyd 1978 年图灵奖演讲《The Paradigms of Programming》。Floyd 借用 Kuhn 的科学范式概念，把范式理解为**解决问题的方法论**（如结构化编程、分治、状态机），它由语言"支持"，但并不被某一门语言"独占"。

Peter Van Roy（2009）进一步点明：**语言极多，范式少得多**；每个范式由一组编程概念定义，可归约到一个"核语言（kernel language）"。这给初学者一个关键更正——

范式 ≠ 语言

你可以在 Python 里写纯命令式，也能写相当函数式的代码；C 主要过程式但能手写对象；Lisp 家族一门语言横跨函数式/命令式/OO。判断"这是什么范式"要看**代码的组织风格**（靠改状态推进？靠对象发消息？靠纯表达式组合？靠声明关系？），而不是看用了哪门语言或哪个关键字。

### 1.5.3 多范式融合

现代主流语言几乎都是**多范式（multi-paradigm）** 的：同一份程序里，不同部分用最合适的范式。Van Roy 明确主张多范式——"解决一个问题需要选对概念，而不同部分往往需要不同概念集合"。Python 就是活例：`for` 循环是命令式，`class` 是 OO，`map`/推导/`functools` 是函数式，SQL/正则调用是声明式，它们在一个工程里共存。

务实心态是"按问题选范式"而非"信仰某一种"：需要建模有身份、随时间变化的实体（账户、连接）时 OO 顺手；做数据变换管线时函数式清爽；查询/规则匹配时声明式省心；贴近硬件、性能敏感的热点循环命令式最直接。范式是工具箱，不是阵营。

### 1.5.4 同一问题的四范式对照（真实运行输出）

把 1.1–1.4 的四个版本放在一起跑，同一问题、同一答案、四种风格。以下为基线环境（Py3.11.15, Linux 6.18.5 x86_64）下的真实输出：

```python
data = [1, 2, 3, 4, 5]
print("imperative :", sum_even_squares_imperative(data))
print("oo         :", EvenSquareAccumulator_run(data))   # 见 1.2.3
print("functional :", sum_even_squares_functional(data))
print("declarative:", sum_even_squares_declarative(data))
```

```text
imperative : 20
oo         : 20
functional : 20
declarative: 20
```

四者答案都是 20（即 2²+4²）。差别不在结果，而在**思路的组织方式**：命令式改一个累加器，OO 把累加器藏进对象靠消息推进，函数式把它写成筛-映射-归约的纯变换组合，声明式只描述"要偶数的平方之和"。这张对照表就是本大主题的落点——同一件事，可以用不同抽象单位去表达，选择哪种取决于问题与可读性，而非语言的强制。

### 1.5.5 抽象屏障与复杂度管理的意义

抽象之所以是"复杂度管理"，是因为它把系统切成**可以独立理解、独立替换的层**：屏障之上的人只需知道"这层承诺做什么"，无需知道"内部怎么做"；屏障之下的人只需守住承诺，可以随意重写实现。这一思想在数据抽象（大主题 2 的抽象屏障）、OO 封装（大主题 3）、接口/协议（大主题 5）里反复出现，本节先立总纲：范式各异，但都靠"命名 + 隐藏细节"这一抽象动作来对抗规模带来的复杂度。
