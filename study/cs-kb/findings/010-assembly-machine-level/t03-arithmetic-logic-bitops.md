## 3.1 整数算术指令

### 3.1.1 add 与 sub：一条指令一次加减

`add S, D` 把源操作数 S 加到目的 D 上（`D ← D + S`），`sub S, D` 从 D 中减去 S（`D ← D − S`）；结果写回 D，同时按结果隐式设置条件码。AT&T 语法里源在前、目的在后，尺寸后缀 b/w/l/q 指明操作宽度。它们不区分有符号与无符号——补码加减法在两种解释下用的是同一套位级运算（见 L3-02 CO-3.1），区别只体现在事后看哪个标志位（无符号看 CF、有符号看 OF）。

最直观的 O0 反汇编（`long f_add/f_sub(long,long)`，参数在 rdi/rsi，返回值在 rax）：

```
f_add:  addq  %rdx, %rax        # rax = rax + rdx
f_sub:  subq  -16(%rbp), %rax   # rax = rax - [内存操作数]
```

对初学者，先建立"目的操作数被就地更新"这个心智模型：`addq %rsi, %rax` 读作"rax 加上 rsi，结果留在 rax"，rsi 不变。这与 C 的 `a += b` 一一对应。一个常见困惑是 AT&T 的操作数顺序：`sub S, D` 算的是 `D − S` 而不是 `S − D`，顺序上"减号左边的数写在右边"，看惯 Intel 语法（`sub D, S`，同样是 `D − S` 但两操作数位置相反）的读者尤其要留意。另一个易错点是这两条指令一次只碰两个操作数，x86 是"二地址"指令集，没有"三个寄存器相加得第四个"的 RISC 式写法；要算 `a+b+c` 必须两条 add 接力。

### 3.1.2 imul：截断乘法与全宽乘法两种形态

`imul` 是有符号整数乘法，x86-64 提供三种操作数形式，教材与规范都强调要分清两类用途。**两操作数 / 三操作数形式**（`imul S, D` 或 `imul $imm, S, D`）产生"截断到操作数宽度"的乘积，是编译器实现 C 里 `a*b` 的常规选择：

```
f_imul:  imulq  %rsi, %rax      # rax = (rax * rsi) 的低 64 位
```

**单操作数形式**（`imul S`）产生"全宽"乘积：两个 n 位数相乘得 2n 位结果，高半部分放 rdx、低半部分放 rax（详见 3.5.3）。C 层面写不出直接的全宽乘，通常经 `__int128` 或"取高位"意图触发。

为什么要分两类？因为两个 64 位数相乘的完整结果最多有 128 位，普通 `a*b` 只要低 64 位（与 C 的模 2^64 语义一致），所以用截断形式、结果就在一个寄存器里；只有当你真的关心"溢出的高位"时才需要单操作数的全宽形式。这里有一个只影响进阶读者的规范细节，先知道即可：截断形式的 imul 会按"结果是否放得下"设置 CF/OF，但 SF/ZF/AF/PF 在两/三操作数形式下被规范列为 undefined（Intel SDM Vol.2 `IMUL`），所以编译器不会拿截断 imul 之后的 ZF 去判零。还要区分 `imul`（有符号）与 `mul`（无符号，只有单操作数形式）——低位截断乘积两者相同，但全宽乘的高位不同，因为符号扩展方式不同。

### 3.1.3 neg：补码取负

`neg D` 把 D 替换为它的补码相反数（`D ← −D`，等价于 `0 − D`），是一元指令。

```
f_neg:  negq  %rax             # rax = -rax
```

直觉上 neg 就是"取反加一"（`~D + 1`）的一步到位版本，与 L3-02 CO-3.1 讲的补码取负完全一致。初学者要记住两个点：其一，它对 CF 的设置很特别——操作数为 0 时 CF 清 0，非 0 时 CF 置 1（Intel SDM Vol.2 `NEG`），这与它等价于 `0 − D` 时借位的行为吻合；OF/SF/ZF/AF/PF 则按结果正常设置。其二，最小负数取负会溢出、结果仍是自己（如 8 位下 `−(−128)=−128`），此时 OF 被置位，这是补码不对称的老问题。不要把 `neg`（算术取负，改标志）和 `not`（按位取反，不改标志，见 3.3.1）混为一谈。

### 3.1.4 inc / dec 与"为什么编译器偏爱 add/sub"

`inc D` 与 `dec D` 分别把 D 加 1、减 1，是最古老的加一/减一指令。但一个反直觉的实测事实是：现代 gcc 默认几乎不生成它们，`a++` 在 O0 下也是编译成加立即数 1：

```
f_inc:  addl  $1, -4(%rbp)     # a++  ->  加立即数 1，而非 inc
f_dec:  subl  $1, -4(%rbp)     # a--  ->  减立即数 1，而非 dec
```

核心原因是 inc/dec 有一个与众不同的语义：**它们更新 SF/ZF/AF/PF/OF，但刻意保留 CF 不变**（Intel SDM Vol.2 `INC`/`DEC`）。这个"部分更新标志位"的特性在乱序流水线上会造成对旧 CF 的假依赖（partial-flags stall），所以主流编译器在优化与代码生成时倾向于用会全量更新标志的 `add $1`/`sub $1` 代替。对初学者，这里要带走的结论是：inc/dec 在语义上正确且指令编码更短，但"更短的指令不一定更快"，微架构上的标志位依赖让编译器选择了看似更长的 add/sub——读反汇编时看到加减 1 用 add/sub 而非 inc/dec，不必惊讶。inc/dec 不影响 CF 这一点本身也是有意为之：早期设计让循环计数器自增时不破坏进位标志，便于多字节大数运算跨迭代保留进位。

- 锚点：Intel SDM Vol.2，`ADD`/`SUB`/`IMUL`/`MUL`/`NEG`/`INC`/`DEC` 逐条（语义与 Affected Flags）｜核实 2026-07-26。
- 实证：本机 `gcc -std=c11 -O0/-O1 -S` + `objdump -d`（gcc 13.3.0 / objdump 2.42），确认 inc/dec 被 add/sub 取代、imul 用两操作数截断形式。
- 冲突/分歧：无实质冲突。CSAPP 表把 imul 简记为"乘法"，Intel SDM 进一步区分单/两/三操作数形式与各自的标志位影响（尤其两/三操作数形式 SF/ZF/AF/PF undefined），以 SDM 为准；inc/dec 不改 CF 属 SDM 明文规定，CSAPP 未强调。

## 3.2 移位指令

### 3.2.1 sal / shl：左移，且是同一条指令

`sal`（算术左移）与 `shl`（逻辑左移）把操作数的位向高位移动、低位补 0，左移 k 位等于乘以 2^k（在模 2^n 意义下）。关键事实：**左移没有"算术"与"逻辑"之分，`sal` 与 `shl` 是同一条机器指令的两个助记符**。本机汇编器实测两者产生完全相同的字节：

```
d1 e0    sal $1,%eax     # 汇编后
d1 e0    shl $1,%eax     # 与上一行字节完全相同；objdump 一律反汇编成 shl
```

对初学者：左移补 0，所以不管把这些位当有符号还是无符号看，"低位补 0、整体乘 2"的效果都一样，自然不需要两条指令。CSAPP 与 Intel SDM 都把 SAL 列为 SHL 的同义词。你在别人代码里看到 `sal`、在自己反汇编里看到 `shl`，指的是同一操作。易错点：左移会把高位挤出去丢弃，`x<<k` 若 k 太大或结果超出类型范围就会丢高位（对有符号数在 C 里是未定义/实现定义行为），指令本身只是照移不报错。

### 3.2.2 sar：算术右移，符号位填充

`sar`（算术右移）把位向低位移动，高位用**原符号位**填充，从而对有符号补码数实现"向下取整的除以 2^k"。C 里对有符号整数用 `>>` 通常编译成 sar：

```
sar_c:  sarl  $3, %eax          # int x >> 3  ->  算术右移
```

从直觉上看，右移丢掉低位相当于除以 2^k，但为了让负数右移后仍是负数、且数值上等于向负无穷取整的商，必须复制符号位而不是补 0。例子：`−8 >> 1` 补符号得 `−4`（正确），若补 0 会得到一个大正数（错误）。一个易错点是 sar 实现的是**向下取整**（floor）除法，而 C 的有符号 `/` 是**向零取整**（truncation）：`−7/2` 在 C 里是 `−3`，但 `−7 >> 1` 是 `−4`。所以编译器把"有符号除以 2 的幂"翻译成除法时，会在 sar 前后加偏置修正，而不是裸用一条 sar——这也是为什么 `a/2` 和 `a>>1` 对负数不等价。

### 3.2.3 shr：逻辑右移，零填充

`shr`（逻辑右移）把位向低位移动、高位一律补 0，对应无符号数的除以 2^k。C 里对无符号整数用 `>>` 编译成 shr：

```
shr_c:  shrl  $3, %eax          # unsigned x >> 3  ->  逻辑右移
```

shr 与 sar 是右移的"逻辑 vs 算术"这一对，也是右移唯一需要区分两条指令的原因：右移会暴露被移入的高位是什么，无符号数希望补 0（shr），有符号数希望补符号（sar），二者不能共用。初学者判断用哪条的最简规则：看被移的操作数在 C 里是有符号还是无符号——`unsigned` 走 shr，`signed`（含普通 `int`）走 sar。这也解释了为什么 C 里"右移一个负的有符号数"的行为历史上是实现定义的，而无符号右移永远是清晰的逻辑移位。

### 3.2.4 移位量来源与计数掩码

移位量（shift amount）只有两种合法来源：**一个立即数**，或**寄存器 %cl**（cx 的低 8 位）——x86 规定变量移位量必须放在 cl 里，不能用别的寄存器。实测变量移位：

```
shl_var:  movl  %esi, %ecx      # 把移位量 k 搬进 ecx
          sall  %cl, %eax       # 用 cl 做移位量
```

为什么偏偏是 cl？这是 x86 沿袭下来的硬性约定（Intel SDM Vol.2 移位指令的操作数形式里，变量计数只接受 CL），编译器因此常常为一次变量移位专门把计数值挪进 rcx。还有一个初学者极易踩的规范细节：**实际移位量会被掩码**——处理器只取计数值的低几位，32 位及以下操作数取低 5 位（`count & 0x1F`，范围 0–31），64 位操作数取低 6 位（`count & 0x3F`，范围 0–63）（Intel SDM Vol.2 "Description"）。这与 C 语言的规定不同：C 里"移位量 ≥ 类型位宽"是未定义行为，编译器不保证按硬件掩码走。所以 `x << 64`（x 为 32 位）在硬件上等于 `x << 0`（掩码后为 0，原值不变），但在 C 源码里它是 UB，绝不能依赖这个硬件行为写代码——规范语义（C 标准 UB）与实现行为（x86 掩码）在此分账。

#### 来源与时效
- 锚点：CSAPP 3rd ed（2016）§3.5.2 Figure 3.10（移位操作：SAL/SHL/SAR/SHR，及"移位量为立即数或 %cl"的说明）｜核实 2026-07-26。
- 锚点：Intel SDM Vol.2，`SAL/SAR/SHL/SHR` 单条（SAL≡SHL、count 掩码 5/6 位、变量计数走 CL、CF 取末位移出、OF 仅对 1 位移位有定义）｜核实 2026-07-26。
- 实证：本机 `gcc -O1 -S`（gcc 13.3.0）确认 signed `>>`→sar、unsigned `>>`→shr、变量移位经 %cl；`as`+`objdump -d`（binutils 2.42）确认 `sal`/`shl` 助记符编码完全相同（`d1 e0`）。
- 冲突/分歧：**规范 vs 实现分账**——x86 硬件对超范围移位量做掩码（低 5/6 位），而 ISO C 把"移位量 ≥ 位宽"定为未定义行为；两边都记，教学以"C 里勿依赖硬件掩码"为安全结论。CSAPP 提到掩码到 w−1，与 SDM 的 5/6 位掩码一致。

## 3.3 位逻辑指令

### 3.3.1 and / or / xor / not：逐位布尔运算

`and`/`or`/`xor` 是二元按位逻辑指令（`D ← D & S`、`D ← D | S`、`D ← D ^ S`），`not` 是一元按位取反（`D ← ~D`）；它们对操作数的每一位独立做布尔运算，与算术进位无关。

```
and_c:  andl  $15, %eax        # x & 0xF
or_c:   orl   $15, %eax        # x | 0xF
xor_c:  xorl  $15, %eax        # x ^ 0xF
not_c:  notl  %eax             # ~x
```

对初学者，先分清"位逻辑"和"逻辑运算"：这里的 and/or/xor 是逐位的（bitwise，对应 C 的 `&`/`|`/`^`），不是短路布尔（`&&`/`||`）。标志位方面有一条实用规律：**and/or/xor 会把 CF 和 OF 都清 0**，并按结果设置 SF/ZF/PF（AF 未定义）——因为按位逻辑不产生进位或溢出的概念（Intel SDM Vol.2 `AND`/`OR`/`XOR`）。而 **`not` 是个例外：它不影响任何标志位**（Intel SDM Vol.2 `NOT`）。这条差异在读反汇编时有用：看到 `xor`/`and`/`or` 后面紧跟一个条件跳转，说明它顺带用结果设了 ZF/SF；而 not 之后的条件跳转看的一定是更早的指令留下的标志。别把 `not`（按位取反、不改标志）和 `neg`（算术取负、改标志）搞混，二者只差一个"加一"和"是否动标志位"。

### 3.3.2 编译器位技巧：xor 清零、test 判零、and 做掩码

编译器把位逻辑指令当成一批高效小工具，几个惯用法值得初学者一眼认出。**`xor reg, reg` 清零**：任何数与自身异或得 0，且这条指令编码短、无输入依赖，是把寄存器置 0 的标准手法（比 `mov $0` 更受青睐；本机在需要短依赖链时可见）。**`test`/`and reg, reg` 判零**：`test %rax,%rax` 做一次"丢弃结果的 and"，只为按 rax 是否为 0 设置 ZF，随后配合 `je`/`jne` 判空指针或判零，比 `cmp $0` 更省。**`and` 做掩码、`or` 置位、xor 翻位**：`x & 0xF` 取低 4 位、`x | 0xF` 把低 4 位强制置 1、`x ^ mask` 翻转 mask 指定的位——这些都是位操作的日常。

为什么这些技巧成立、又为什么编译器爱用？根子在于位逻辑指令快、编码紧凑、且能顺带设置标志位省掉一条比较指令。以判零为例，`test %rax,%rax` 一条就把"取值 + 设 ZF"合并，避免了单独的 `cmp $0,%rax`；实测里 `(a+b)==0` 甚至连 test 都省了——因为前面的 `add` 已经按结果设了 ZF，直接 `sete` 读标志即可（见 3.5.1）。初学者只需记住：反汇编里看到寄存器和自己做 xor 就是"清零"，和自己做 test/and 就是"判零"，这是模式识别而非真的在算异或。

#### 来源与时效
- 锚点：CSAPP 3rd ed（2016）§3.5.1 Figure 3.10（AND/OR/XOR/NOT 二元与一元逻辑操作）；§3.6.1 提到 `test`/`xor` 惯用法｜核实 2026-07-26。
- 锚点：Intel SDM Vol.2，`AND`/`OR`/`XOR`（CF=OF=0，SF/ZF/PF 按结果，AF undefined）、`NOT`（不影响任何标志）、`TEST`（如 AND 但不写回）｜核实 2026-07-26。
- 实证：本机 `gcc -O1 -S`（gcc 13.3.0）确认 `x&0xF`→andl、`x^x`→`mov $0`（此上下文下编译器选 mov 清零）、位逻辑各指令直译。

## 3.4 lea 做算术

### 3.4.1 lea 的双重身份：算地址，也算数

`lea D_addr, reg`（load effective address，取有效地址）本职是把内存操作数 `disp(base,index,scale)` 的**地址值**算出来放进寄存器，而**不访问内存**。正因为它内部就是一个能算 `disp + base + index*scale` 的加法/移位单元，编译器把它"挪用"来做纯算术：任何形如"若干寄存器按 1/2/4/8 缩放再加常量"的整数表达式都能一条 lea 搞定。

```
poly:  leaq  1(%rdi,%rsi,2), %rax   # rax = rdi + rsi*2 + 1  （纯算术，不碰内存）
```

初学者最容易被 lea 绊住的一点：**它和 mov 长得像但完全相反**。`movq (%rdi), %rax` 是"到 rdi 指向的内存里取值"，`leaq (%rdi), %rax` 是"把 rdi 这个地址本身算出来给 rax"（等价于 `mov %rdi,%rax`）。记法：lea 只算括号里那套地址公式的值，绝不解引用。第二个要点：**lea 不影响任何条件码**（Intel SDM Vol.2 `LEA`：不影响标志位），这既是它区别于 add 的关键，也是编译器有时选它的理由之一——想算个中间值又不想破坏当前标志位时，lea 比 add 安全。

### 3.4.2 用 lea 实现乘常量与乘加

lea 的 scale 只能取 1/2/4/8，base 与 index 各一个寄存器，所以它能一步算的乘法系数有限，但配合"base 与 index 用同一个寄存器"可以变出 2/3/4/5/8/9 等常见小系数；更大的常数乘法则用 lea 加移位组合。本机实测：

```
m5:   leaq  (%rdi,%rdi,4), %rax      # x*5  = x + x*4
m3:   leaq  (%rdi,%rdi,2), %rax      # x*3  = x + x*2
m12:  leaq  (%rdi,%rdi,2), %rax      # 先 x*3
      salq  $2, %rax                 # 再 <<2，合成 x*12
```

为什么编译器绕这么大弯不直接用 imul？因为整数乘法指令延迟较高，而 lea 与移位是最廉价的操作之一；把"乘一个小常量"拆成一两条 lea/shift，往往比一条 imul 更快，这是编译器在 O1/O2 下的常规强度削减（strength reduction）。初学者读到 `lea (%rdi,%rdi,4)` 不要按"取地址"去理解，看到目的是普通整数变量（不是指针）就知道这是在算 `x*5`。易错点：这套技巧只对能由 `2^a * base + 2^b * base` 凑出的系数成立，凑不出的（如乘 7、乘 11 且不划算时）编译器仍会退回 imul——所以看到 imul 也别意外，是编译器权衡后的选择。

#### 来源与时效
- 锚点：CSAPP 3rd ed（2016）§3.5.1（lea 作为加载有效地址指令、被用于紧凑算术，Figure 3.10 前后正文与练习 3.5.x）｜核实 2026-07-26。
- 锚点：Intel SDM Vol.2，`LEA`（计算有效地址、写入通用寄存器、不访问内存、不影响标志位）｜核实 2026-07-26。
- 实证：本机 `gcc -O1 -S`（gcc 13.3.0）确认 `x*5`→`lea (%rdi,%rdi,4)`、`x*3`→`lea (%rdi,%rdi,2)`、`x*12`→lea+`salq $2`、`a+2*b+1`→`lea 1(%rdi,%rsi,2)`。
- 冲突/分歧：无。CSAPP 与 SDM 对 lea "不解引用、不改标志"的口径一致。

## 3.5 条件码副作用与特殊算术

### 3.5.1 算术/逻辑指令对 CF/ZF/SF/OF 的隐式设置

x86-64 里绝大多数算术与逻辑指令**在算出结果的同时，隐式更新一组条件码（标志位）**，最常用的四个是：

```
CF (Carry Flag)     无符号运算的进位/借位（结果超出无符号范围）
ZF (Zero Flag)      结果是否为 0
SF (Sign Flag)      结果最高位（有符号看作负号）
OF (Overflow Flag)  有符号补码运算是否溢出
```

这套"副作用"是 x86 条件分支的基础：一条 add/sub/and 先把标志设好，后面的 `setCC`/`jCC`/`cmovCC` 再来读（详见 AS-4）。本机实测两个典型：

```
add_ovf:     addl  %esi, %edi     # 加法顺带设置 OF
             seto  %al            # seto 直接读刚才那次加法的 OF
is_zero_sum: addq  %rsi, %rdi     # 加法顺带设置 ZF
             sete  %al            # 直接读 ZF，无需另加 cmp/test
```

对初学者，最重要的心智模型是：**标志位不是单独一条"比较"才产生的，普通算术指令就在持续更新它们**。上面 `is_zero_sum` 里没有任何 cmp——因为 `a+b` 这条 add 已经按结果设了 ZF，编译器直接用 `sete` 读即可。这正是 3.3.2 里"test/位逻辑能省掉比较"的同一个道理。四个标志各看一面：判无符号进位看 CF，判等/判零看 ZF，判正负看 SF，判有符号溢出看 OF——例子 `add_ovf` 用 `seto` 把 OF 落到一个布尔值，正是 `__builtin_add_overflow` 检测溢出的机器实现。

### 3.5.2 哪些指令不设标志：lea / mov / 以及 inc-dec 的 CF 例外

不是所有指令都动标志位，读反汇编时分清这点能避免误判分支依据。**`lea` 与 `mov` 完全不影响任何条件码**（Intel SDM Vol.2）——所以编译器可以拿 lea 算中间地址、拿 mov 搬数据，而不破坏之前算术指令留下的、马上要被条件跳转用到的标志。**`inc`/`dec` 更新除 CF 外的标志、独独保留 CF**（见 3.1.4），这是它们与 add/sub 最本质的语义差异。

为什么要记这些例外？设想一段代码"先做减法设好标志、再算一个地址、然后条件跳转"：如果算地址用的是 add（改标志），跳转依据就被冲掉了；用 lea（不改标志）才安全。这解释了编译器的指令选择不只看"算得对不对"，还看"会不会踩坏标志位"。初学者的实用规则：mov 和 lea 是"标志位安全"的，算术（add/sub/neg/imul）和位逻辑（and/or/xor，注意 not 除外）会改标志，inc/dec 是"改标志但不碰 CF"的特殊户。

### 3.5.3 特殊算术：全宽乘法的高低位（mul / imul 单操作数）

普通 `a*b` 只要低位截断结果（3.1.2），但"两个 64 位数相乘得 128 位完整积"需要单操作数的 `mul`（无符号）或 `imul`（有符号）：被乘数隐式取自 rax，结果的**高 64 位放 rdx、低 64 位放 rax**（记作 rdx:rax）。本机用 `unsigned __int128` 触发取高位：

```
umulhi:  movq  %rdi, %rax     # 被乘数放 rax
         mulq  %rsi           # rdx:rax = rdi(隐式rax) * rsi  的 128 位积
         movq  %rdx, %rax     # 取高 64 位（rdx）作为返回值
```

对初学者，关键是记住这条"隐式寄存器"约定：单操作数乘法的一个乘数必须在 rax，结果强制铺到 rdx:rax 这对寄存器上，指令里看不到 rdx 却被写了。为什么用两个寄存器？因为 n 位乘 n 位最多 2n 位，一个寄存器装不下完整积，所以规定高低位分家。这也是"取乘法高位"（如实现定点数、大数乘法、编译器算除法魔数）的硬件基础。`mul` 与 `imul` 单操作数形式的低位相同、高位因符号扩展方式不同而不同，所以有符号取高位（`smulhi`）的反汇编会额外出现符号修正的 sar/imul 序列，比无符号版复杂。

### 3.5.4 特殊算术：除法的 rdx:rax 与被除数扩展

除法 `div`（无符号）/`idiv`（有符号）也是单操作数、隐式用 rdx:rax：把 **128 位被除数 rdx:rax 除以操作数**，**商放 rax、余数放 rdx**。关键陷阱是——除法前必须先把 rdx 正确地设好，否则被除数高 64 位是垃圾。本机实测两种设法：

```
udiv:  movq  %rdi, %rax
       movl  $0, %edx          # 无符号：rdx 清 0（被除数高位补 0）
       divq  %rsi              # 商->rax
umod:  ...    divq  %rsi
       movq  %rdx, %rax        # 取余数（rdx）
sdiv:  movq  %rdi, %rax
       cqto                    # 有符号：把 rax 符号扩展进 rdx:rax
       idivq  %rsi             # 商->rax，余数->rdx
```

初学者要抓住两点。其一，商和余数一次算出、分放两个寄存器：`a/b` 取 rax，`a%b` 取 rdx——这解释了为什么 C 里 `/` 和 `%` 常被编译成同一条除法指令，取哪个结果而已。其二，除法前的"被除数扩展"必须与符号性匹配：无符号除法把高位 rdx 清 0（`mov $0,%edx`），有符号除法用 `cqto`（也写作 `cqo`，convert quad to octuple）把 rax 的符号位铺满 rdx，形成正确的 128 位有符号被除数。忘了这一步或用错扩展方式会算出完全错误的商。另外除法是所有整数指令里最慢的，且除以 0（或有符号最小值除以 −1 溢出）会触发 `#DE` 硬件异常而非静默出错——这也是编译器对"除以常量"极力改用乘魔数+移位来规避真实 div 的原因。

- 锚点：CSAPP 3rd ed（2016）§3.5.5 *Special Arithmetic Operations*（单操作数 mul/imul 全宽积 R[rdx]:R[rax]、div/idiv 商 rax 余 rdx、`cqto` 符号扩展）；§3.6.1 条件码｜核实 2026-07-26。
- 锚点：Intel SDM Vol.2，`MUL`/`IMUL`/`DIV`/`IDIV`（隐式 rdx:rax、被除数扩展、`#DE` 除零/溢出异常）、`MOV`/`LEA`（不影响标志）、状态标志 CF/ZF/SF/OF 定义（Vol.1 §3.4.3 EFLAGS）｜核实 2026-07-26。
- 实证：本机 `gcc -O1 -S`（gcc 13.3.0）确认：`add`+`seto` 读 OF、`add`+`sete` 读 ZF（无独立 cmp）；无符号乘用 `mulq` 取 rdx；无符号除 `mov $0,%edx`+`divq`、有符号除 `cqto`+`idivq`；`a%b` 取 rdx。
- 冲突/分歧：无实质冲突。CSAPP 用 `cqto` 助记符，等价于 Intel/AT&T 的 `cqo`（AT&T 常写 `cqto`），仅助记符差异，语义一致；两/三操作数 imul 的 SF/ZF/AF/PF undefined 以 Intel SDM 为准（CSAPP 未细列）。
