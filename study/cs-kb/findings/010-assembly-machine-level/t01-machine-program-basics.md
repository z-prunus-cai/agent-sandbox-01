## 1.1 编译流水线：从 C 到可执行文件的全链路产物

### 1.1.1 四个阶段与四种产物

从一份 `.c` 源文件到一个能运行的可执行文件，`gcc` 在幕后依次驱动四个工具，产生四种不同形态的中间/最终产物：

```
预处理 (cpp)      hello.c  ──►  hello.i     纯文本 C（宏已展开、头文件已插入）
编译   (cc1)      hello.i  ──►  hello.s     纯文本汇编（本课主角）
汇编   (as)       hello.s  ──►  hello.o     二进制·可重定位目标文件（ELF）
链接   (ld)       hello.o  ──►  hello       二进制·可执行文件（ELF）
```

你手上拿到的每一份东西——`gcc -S` 出来的汇编、`objdump -d` 反汇编出来的清单、`gdb` 里单步的指令——都是这条链上某一站的产物。搞清"这是哪一站的东西"，才不会把汇编器的输入（`.s` 文本）和它的输出（`.o` 里的机器码字节）混为一谈。

初学者最容易误解的是把"编译"当成一步。实际上日常说的"编译"通常指整条链；而严格意义上"编译"只是第二步（把 C 翻译成汇编文本），真正把汇编文本变成机器码字节的是第三步"汇编"，把多个目标文件和库拼成能跑的程序的是第四步"链接"。四步各有独立工具、独立产物，可以分别停下来观察。

### 1.1.2 预处理（gcc -E）：还是 C，但宏和头文件都摊开了

预处理器 `cpp` 处理所有以 `#` 开头的指示：`#include` 被替换成对应头文件的完整内容，`#define` 宏被展开，`#if`/`#ifdef` 条件编译被裁剪，注释被删除。产物 `.i` **仍然是 C 语言文本**，只是"自包含"了——不再依赖任何头文件。

```
$ gcc -std=c11 -E sum.c | tail -3
    long t = a + b;
    return t;
}
```

（环境串：gcc 13.3.0 @Linux 6.18.5 x86-64。`-E` 让 gcc 只跑到预处理就停。）

直觉上这一步是"文本层面的复制粘贴"：它不懂 C 的语义，只做符号替换。这解释了很多初学者踩的坑，比如宏 `#define SQR(x) x*x` 展开 `SQR(a+b)` 会变成 `a+b*a+b`（没有语义、纯替换，所以不会自动加括号）。预处理产物很少直接看，但当"某个宏到底展开成了什么"搞不清时，`gcc -E` 是最直接的排查手段。

### 1.1.3 编译到汇编（gcc -S）：本课真正的主角

编译阶段把预处理后的 C 翻译成**汇编文本** `.s`。这是本课几乎所有内容的入口——汇编是"人还能读、又几乎一一对应机器指令"的层次。`-S` 让 gcc 跑到这一步停下，产出 `.s` 文本文件。


```c
long sum(long a, long b) { long t = a + b; return t; }
```

```
$ gcc -std=c11 -S -O0 -fno-asynchronous-unwind-tables sum.c -o sum.s
$ cat sum.s        # 只看函数体，省略 .file/.ident/.note 等汇编器指示
sum:
	endbr64
	pushq	%rbp
	movq	%rsp, %rbp
	movq	%rdi, -24(%rbp)
	movq	%rsi, -32(%rbp)
	movq	-24(%rbp), %rdx
	movq	-32(%rbp), %rax
	addq	%rdx, %rax
	movq	%rax, -8(%rbp)
	movq	-8(%rbp), %rax
	popq	%rbp
	ret
```

（环境串：gcc 13.3.0 @Linux 6.18.5 x86-64。`-fno-asynchronous-unwind-tables` 只是去掉 `.cfi_*` 调试展开指示让输出更干净，不改指令。）

`.s` 文本里除了指令，还有很多以 `.` 开头的**汇编器指示（directive）**，如 `.text`（代码段）、`.globl sum`（把 sum 导出为全局符号）、`.type`、`.size`。它们不是 CPU 指令，是给下一步的汇编器 `as` 看的说明。初学者读汇编时先聚焦冒号结尾的标号（如 `sum:`）和缩进的指令行，`.` 开头的先跳过，能大幅降低阅读噪声。此处第一条 `endbr64` 是 CET 控制流保护的落点标记（见大主题7），入门可先当"函数入口的一个固定开头"。

### 1.1.4 汇编（as / gcc -c）：文本变成机器码字节

汇编器 `as` 把 `.s` 汇编文本逐条翻译成**二进制机器码**，打包进一个**可重定位目标文件**（relocatable object）`.o`。`gcc -c` 驱动这一步。产物 `.o` 已经是二进制 ELF，不能再当文本读，但可以用 `objdump -d` 反汇编回来看：

```
$ gcc -std=c11 -c -O0 -fno-asynchronous-unwind-tables sum.c -o sum.o
$ file sum.o
sum.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
$ objdump -d sum.o        # 左列是机器码字节，右列是反汇编还原的指令
0000000000000000 <sum>:
   0:	f3 0f 1e fa          	endbr64
   4:	55                   	push   %rbp
   5:	48 89 e5             	mov    %rsp,%rbp
   8:	48 89 7d e8          	mov    %rdi,-0x18(%rbp)
   c:	48 89 75 e0          	mov    %rsi,-0x20(%rbp)
  10:	48 8b 55 e8          	mov    -0x18(%rbp),%rdx
  14:	48 8b 45 e0          	mov    -0x20(%rbp),%rax
  18:	48 01 d0             	add    %rdx,%rax
  1b:	48 89 45 f8          	mov    %rax,-0x8(%rbp)
  1f:	48 8b 45 f8          	mov    -0x8(%rbp),%rax
  23:	5d                   	pop    %rbp
  24:	c3                   	ret
```

（环境串：gcc 13.3.0 / objdump 2.42 @Linux 6.18.5 x86-64。）

这里有几个初学者的关键认识。其一，`.s`（汇编文本）和 `.o`（机器码字节）是**输入与输出**的关系，别混：`gcc -S` 给你前者，`gcc -c` 给你后者。其二，反汇编输出左列 `f3 0f 1e fa`、`55`、`48 89 e5` 才是 CPU 真正执行的字节，右列 `endbr64`、`push %rbp` 是 `objdump` 为方便人读还原出来的助记符——同一段字节，机器执行的是字节，人读的是助记符。其三，注意函数地址从 `0` 起（`0000000000000000 <sum>`），因为这是"可重定位"文件，真实运行地址还没定，要等链接。

### 1.1.5 链接（ld / gcc）：拼合符号、定地址，产出可执行文件

链接器 `ld` 把一个或多个 `.o` 以及需要的库拼成一个**可执行文件**：它做两件核心事——**符号解析**（把每处对 `printf`、对别的 `.o` 里函数的引用，对应到真正的定义）和**重定位**（给各段和符号分配最终运行地址，回填所有引用处的地址）。`gcc`（不加 `-c/-S/-E`）默认一路驱动到链接，直接给你可执行文件。

为什么需要单独的链接步？因为大型程序被拆成多个 `.c` 分别编译成 `.o`，改一个文件只需重编那一个再链接，不必重编全部；标准库（如 `printf`）也早已编译好，链接时接进来即可。这就是"分离编译"，链接是把这些独立编译的碎片缝合成一个整体的那一步。上一节里 `sum` 的地址是 0，正是因为还没链接、地址未定；链接后（尤其在 PIE 可执行文件里，见大主题2的 rip 相对寻址与大主题7的 PIE/ASLR）符号才拿到真正的运行期地址。

### 1.1.6 gcc 是"驱动器"，一条命令跑完整条链

平时敲的 `gcc hello.c -o hello` 之所以一步到位，是因为 `gcc` 本身不是编译器，而是一个**驱动程序（driver）**：它按需依次调用 `cpp`（预处理）→ `cc1`（编译，这才是真正的 C 编译器）→ `as`（汇编）→ `ld`（链接），中间产物默认放临时目录、跑完即删。前面用的 `-E`/`-S`/`-c` 就是叫驱动器"跑到某一站就停、把该站产物留下来"的开关。

```
gcc -E   ► 停在预处理，出 .i
gcc -S   ► 停在编译，  出 .s
gcc -c   ► 停在汇编，  出 .o
gcc      ► 一路到链接， 出可执行文件
```

记住这张开关表，就能随时在流水线任意一站"截停"取证，这是读机器级程序最常用的基本功。易错点：`as` 是 GNU 汇编器（binutils 的一部分），`cc1` 才是 C 编译器本体，二者不是一回事；`gcc` 只是把它们串起来的指挥。

### 1.1.7 静态视角的反汇编入口：objdump 与产物观察

除了从源码正向编译，逆向看产物的第一工具是 `objdump`：`objdump -d` 反汇编代码段（如 1.1.4 所示），`objdump -s` 看某段的原始字节（看 `.rodata` 里的跳转表、字符串常量常用，见大主题4），`file` 快速判断一个文件是 `.o`（relocatable）还是可执行（executable）。这些是"手上拿到一份编译产物、想看它到底是什么"的入门取证手段。

机器级程序的东西大多**可直接观测**，不必靠记忆猜。想知道某段 C 编成什么样，`gcc -S` 或 `gcc -c` + `objdump -d` 当场就能看到真实字节与指令；本课后续所有结论都应以这种"当场跑一下"的证据为准，而不是背下来的印象。

## 1.2 汇编语法：AT&T（本课主）vs Intel

### 1.2.1 两套语法是同一份机器码的两种记法

x86-64 汇编有两大记法：**AT&T 语法**（Unix/GNU 世界默认，CSAPP 与本课主用，`gcc -S`、`objdump -d` 默认输出）和 **Intel 语法**（Intel SDM、Windows/MASM、NASM 世界主用）。关键认识：它们描述的是**完全相同的机器码字节和相同的指令**，只是把同一条指令写成不同的文本样子。语法之争不涉及 CPU 行为，只涉及人怎么读写。

最能说明"同一字节、两种记法"的证据是：对同一个 `.o`，让 `objdump` 分别用两种语法反汇编，左列机器码字节一模一样，只有右列文字不同：

```
源码：int get(int *a, long i) { return a[i]; }

$ objdump -d mem.o                 # AT&T（默认）
   4:	8b 04 b7             	mov    (%rdi,%rsi,4),%eax
$ objdump -d -M intel mem.o        # Intel
   4:	8b 04 b7             	mov    eax,DWORD PTR [rdi+rsi*4]
```

（环境串：gcc 13.3.0 / objdump 2.42 @Linux 6.18.5 x86-64。字节 `8b 04 b7` 两侧完全相同。）

语法不改变程序，选一种能读顺即可。本课跟 CSAPP 走 AT&T，但读 Intel 手册时要能对照过来。下面逐项列出四个最主要差异。

### 1.2.2 差异一：操作数顺序（源在前 vs 目的在前）

AT&T 是"**源, 目的**"（source, destination）；Intel 反过来是"**目的, 源**"（destination, source）。这是最容易翻车的差异。

```
AT&T ： add    %rdx, %rax        含义： rax ← rax + rdx   （右边是目的）
Intel： add    rax,  rdx         含义： rax ← rax + rdx   （左边是目的）
```

同一句 `mov`：

```
AT&T ： mov    %rsp, %rbp        含义： rbp ← rsp
Intel： mov    rbp,  rsp         含义： rbp ← rsp
```

AT&T 读作"从…到…"（from src to dst，箭头向右），和赋值方向相反；Intel 读作"dst = src"（像高级语言赋值，左边被赋值）。初学者在两种语法间切换时，`mov a, b` 的搬运方向正好相反，是头号 bug 来源——务必先确认自己在读哪套语法。

### 1.2.3 差异二：寄存器与立即数的前缀符号

AT&T 给寄存器名加 `%` 前缀、给立即数加 `$` 前缀；Intel 两者都不加前缀，寄存器和数字直接写。

```
AT&T ： movq   $0, -16(%rbp)      # $0 是立即数 0，%rbp 是寄存器
Intel： mov    QWORD PTR -16[rbp], 0
```

这套前缀在 AT&T 里其实是"消歧义"的好处：一眼能区分 `%rax`（寄存器）、`$42`（立即数常量）、`42`（内存地址/位移）。初学者看到 `$` 就读"这是个字面常量值"，看到 `%` 就读"这是个寄存器"，不会把常量 42 和地址 42 搞混。Intel 语法没有前缀，靠上下文和 `PTR` 关键字区分，写起来简洁但需要更多上下文判断。

### 1.2.4 差异三：内存寻址写法

内存操作数的通用有效地址是 `位移 + 基址 + 变址×比例`（disp + base + index×scale，详见大主题2 AS-2.3）。两套语法写法差别很大：

```
AT&T 通式 ：  disp(base, index, scale)
Intel 通式：  [base + index*scale + disp]
```

同一个"取 a[i]（int 数组，元素 4 字节）"的地址计算：

```
AT&T ： (%rdi,%rsi,4)             # base=rdi, index=rsi, scale=4, disp=0
Intel： [rdi+rsi*4]
```

带位移的例子（栈上局部变量）：

```
AT&T ： -8(%rbp)                  # 地址 = rbp + (-8)
Intel： QWORD PTR -8[rbp]         （gcc 输出形式；NASM 写作 [rbp-8]）
```

AT&T 用圆括号 `()` 包住寄存器、逗号分隔四要素、比例因子放最后；Intel 用方括号 `[]` 并用 `+`/`*` 明写算式，更接近数学表达式。初学者读 AT&T 的 `disp(base,index,scale)` 时，在心里翻译成 `disp + base + index*scale` 即可；scale 只能是 1/2/4/8（对应 1/2/4/8 字节元素），省略时默认相关项为 0 或 1。

### 1.2.5 差异四：操作数大小的表达（AT&T 尺寸后缀 vs Intel PTR 关键字）

指令要知道操作几个字节。AT&T 把大小编进**指令助记符的后缀** `b/w/l/q`（1/2/4/8 字节，详见大主题2 AS-2.1）；Intel 保持助记符干净，用 `BYTE/WORD/DWORD/QWORD PTR` 关键字标注内存操作数大小。

```
AT&T ： movq   %rsp, %rbp        # q 后缀 = 8 字节（quad word）
        movl   $0, %eax          # l 后缀 = 4 字节（long word）
Intel： mov    rbp, rsp          # 由 64 位寄存器名 rbp/rsp 自明大小
        mov    QWORD PTR [rbp-8], rax    # 内存操作数用 QWORD PTR 标 8 字节
```

当操作数里有寄存器时，大小其实由寄存器名就能定（`%rax`=8 字节、`%eax`=4 字节），后缀/PTR 是冗余或省略的；只有当操作数**全是内存和立即数、没有寄存器"定尺寸"**时，大小才必须显式标出——AT&T 靠后缀（`movq $0, (%rax)`），Intel 靠 `QWORD PTR`。这解释了初学者常见的困惑："为什么有的 mov 带 q 后缀有的不带"——带不带取决于大小能否从别处推出。

### 1.2.6 如何切换语法

想在两套语法间切换，记住三个开关即可：

```
gcc -S               # 默认输出 AT&T 汇编
gcc -S -masm=intel   # 让 gcc 输出 Intel 语法汇编
objdump -d           # 默认 AT&T 反汇编
objdump -d -M intel  # Intel 语法反汇编
.att_syntax / .intel_syntax noprefix   # 在 .s 文件内切换汇编器解析模式
```

（前两组本机实证：`gcc -S -O0 sum.c` 与 `gcc -S -O0 -masm=intel sum.c` 对同一函数分别产出 AT&T/Intel 两版函数体，指令一一对应；objdump 两版见 1.2.1。）

读 CSAPP、读 Linux 内核/GNU 生态汇编，用 AT&T；查 Intel SDM 指令语义、读 Windows 或很多 CTF/逆向资料，会碰到 Intel。两种都能读、清楚自己此刻在读哪种，比强记哪种"更好"重要得多。

## 1.3 优化级别 diff：-O0 vs -O2 与阅读技巧

### 1.3.1 优化级别谱系

gcc 用 `-O` 系列开关控制优化强度，是"编译速度/可调试性"与"运行速度/代码体积"之间的档位：

```
-O0   不优化（默认）：直译，最好调试、最慢、最长
-O1   基础优化
-O2   常用发布级：开大量优化，一般不显著增大代码
-O3   在 -O2 上再加激进优化（更多内联、向量化等）
-Os   为体积优化（size）
-Og   为"可调试地优化"：优化但尽量保住调试体验
```

对读汇编的人，最重要的对照是 **-O0 vs -O2**：前者是"C 的逐句直译"，几乎能和源码逐行对上，适合入门理解；后者是"实际发布代码长的样子"，读它需要技巧。初学者应先在 -O0 上把每条指令和源码对应起来，再去看 -O2 感受编译器做了什么。

### 1.3.2 -O0 的特征：变量落栈、逐句直译

`-O0` 下编译器几乎不做重排或消除：每个局部变量都在栈上有一个格子，每次用到都从栈读进寄存器、算完写回栈。指令冗长但和源码严格对应，便于调试和教学。回看 1.1.3 的 `sum`（`-O0`）：

```
movq	%rdi, -24(%rbp)     # 参数 a 存到栈
movq	%rsi, -32(%rbp)     # 参数 b 存到栈
movq	-24(%rbp), %rdx     # 从栈读回 a
movq	-32(%rbp), %rax     # 从栈读回 b
addq	%rdx, %rax          # a + b
movq	%rax, -8(%rbp)      # 结果 t 存回栈
movq	-8(%rbp), %rax       # 再从栈读 t 作返回值
```

明明 `a+b` 一步就能算完，`-O0` 却把参数先存栈、又立刻读回来，还给中间变量 `t` 单独在栈上留格子存了再读。这种"存了马上读"的冗余正是 -O0 的典型面貌：它老老实实按"每个变量住在内存里"的模型直译，不做省略。好处是每个 C 变量在栈上有确定位置，`gdb` 里随时能查、能改，调试直观。

### 1.3.3 -O2 的特征：寄存器化、常量折叠、消除冗余

`-O2` 下编译器做大量变换：把热变量常驻寄存器（不再来回落栈）、常量在编译期算好（常量折叠）、删除算不出用处的冗余读写、把小函数内联、把循环展开甚至向量化。同一个 `sum`，`-O2` 塌缩成两条指令：

```
$ gcc -std=c11 -S -O2 -fno-asynchronous-unwind-tables sum.c
sum:
	endbr64
	leaq	(%rdi,%rsi), %rax     # rax = rdi + rsi，一步算完
	ret
```

（环境串：gcc 13.3.0 @Linux 6.18.5 x86-64。）

`-O0` 的 11 条指令（含栈读写）被压成一条 `leaq` 加返回——参数直接在寄存器 `%rdi`、`%rsi` 里相加，用 `lea` 借地址计算单元做纯加法（`lea` 做算术见大主题3 AS-3.4），中间变量 `t`、栈帧全部消失。这就是"发布代码"的样子：和源码不再逐行对应，但语义等价、快得多。

一个稍复杂的循环 `for(i=0;i<n;i++) s+=i;` 在 `-O2` 下会被进一步展开（一次迭代处理 2 个 i）并用 `lea` 合并计算，本机实测 `-O2` 版本出现 `leaq 1(%rdx,%rax,2), %rdx` 这类"一条指令干多件事"的形态。初学者不必看懂每条，只需建立直觉：**优化后指令数、结构都可能与源码大相径庭**，读它要靠推理数据流而非逐行对照。

### 1.3.4 阅读优化汇编的抓手

读 -O2 汇编时，几个实用抓手：

```
1) 认调用约定：参数在 rdi/rsi/rdx/rcx/r8/r9，返回值在 rax（见大主题5）——
   函数开头看这些寄存器怎么被用，就知道哪个是哪个参数。
2) 顺着数据流走：盯住某个值从哪个寄存器来、到哪去，别指望和 C 逐行对齐。
3) 抓循环骨架：向后的条件跳转（jl/jne 跳回上方标号）标出循环体边界。
4) lea 常是算术：优化后 lea 多半在算 base+index*scale+disp 这类乘加常量，不是取址。
5) 先 -O0 对照：拿不准时同一份 C 编一份 -O0，逐句读懂语义，再回看 -O2 找对应。
```

核心心法是"读优化汇编靠推理数据流、不靠逐行映射"。-O0 是学语义的脚手架，-O2 是练推理的实战；两份对照着看，是本课最高效的自学法。

### 1.3.5 调试与优化的张力

优化和调试有天然矛盾：优化把变量塞进寄存器、删掉中间步骤、重排指令后，`gdb` 里常出现"变量被优化掉（value optimized out）""单步乱跳、和源码行对不上"。所以调试通常用 `-O0 -g`（`-g` 加调试信息）。当你又想优化、又想调试时，gcc 提供 `-Og`：它开一部分不太破坏调试体验的优化，是"边优化边调试"的折中。

"为什么 gdb 里我的变量看不到值了？"多半是因为编在了 `-O2`——变量只活在某个寄存器的某段时间里，没有固定内存位置。学习和调试阶段用 `-O0 -g`，看"真实发布代码长啥样"时才切 `-O2`。

## 1.4 机器状态模型：程序员可见的机器状态

### 1.4.1 程序员可见状态：四件套

机器级程序执行时，CPU 的"程序员可见状态（program-visible state，也叫架构状态 architectural state）"是指令能直接读写、且 ISA 规范承诺其行为的那部分状态。x86-64 下核心是四类：

```
1) 程序计数器 PC —— 即 %rip，存"下一条要执行的指令地址"
2) 整数通用寄存器组 —— 16 个 64 位寄存器（rax…r15）
3) 条件码（标志）—— RFLAGS 中的 CF/ZF/SF/OF 等，记录最近算术/逻辑结果的性质
4) 内存 —— 按字节编址的巨大数组，存代码、数据、栈、堆
```

"程序员可见"这个限定很重要：CPU 内部还有大量状态（流水线寄存器、缓存、分支预测器、乱序执行的物理寄存器……）都**不属于**架构状态——它们影响速度不影响结果，指令看不到也不能直接操纵它们（微架构层归 L5-05）。本课讲的机器级程序，操纵的正是这四件套。理解一条指令，本质就是理解它读了/改了这四件套里的哪些。

初学者可以把机器级程序想成一台状态机：内存和寄存器是"当前状态"，`%rip` 指着"下一步要执行谁"，每条指令读入部分状态、产生新状态、并把 `%rip` 推进到下一条。整个程序就是从初始状态出发、一条条指令驱动的状态演化。

### 1.4.2 PC：程序计数器 %rip

x86-64 的程序计数器叫 **`%rip`**（instruction pointer，64 位）。它始终保存**下一条**将要执行的指令的地址；CPU 取出当前指令后，`%rip` 就前进指向紧随其后的指令，遇到跳转/调用/返回则被改写成目标地址（见大主题4、5）。程序的控制流本质上就是"`%rip` 依次取什么值"的历史。

本机 `gdb` 在函数 `add` 内断下时观察到：

```
$ gdb -q -batch -ex 'break add' -ex run -ex 'info registers rip' prog
rip            0x401146            0x401146 <add+16>
```

（环境串：gcc 13.3.0 / gdb 15.1 @Linux 6.18.5，`prog` 用 `-no-pie` 编译使地址固定便于展示。）

`0x401146 <add+16>` 表示当前 `%rip` 指向 `add` 函数入口往后第 16 字节处的那条指令。易错点：`%rip` 指的是"下一条"而非"正在执行的这条"，且程序员一般不直接 `mov` 写 `%rip`——它由 `jmp`/`jCC`/`call`/`ret` 这类控制转移指令间接改写。x86-64 里 `%rip` 还参与"rip 相对寻址"来访问全局数据（见大主题2 AS-2.5）。

### 1.4.3 整数通用寄存器组：16 个 64 位寄存器

x86-64 有 **16 个 64 位整数通用寄存器**：`%rax %rbx %rcx %rdx %rsi %rdi %rbp %rsp` 和 `%r8`–`%r15`。它们是 CPU 手边最快的存储，几乎所有整数运算的操作数都取自或写入它们。每个还能按 32/16/8 位的子寄存器名访问（如 `%eax`/`%ax`/`%al`，见大主题2 AS-2.2）。

`gdb` 在 `add(3,4)` 断点处一次性读出：

```
$ gdb ... -ex 'info registers rax rdi rsi rsp rbp'
rax   0x401153   ...
rdi   0x3        3           # 第 1 个参数 a = 3
rsi   0x4        4           # 第 2 个参数 b = 4
rsp   0x7fffffffce00  ...    # 栈指针
rbp   0x7fffffffce00  ...    # 帧基址指针
```

（环境串：gdb 15.1 @Linux 6.18.5 x86-64。可见 `rdi=3`、`rsi=4` 正是按 System V 调用约定传入的前两个参数。）

这些寄存器叫"通用"是相对浮点/向量寄存器而言，但其中几个在**调用约定**里被赋予固定角色——`%rsp` 是栈指针（永远指向栈顶）、`%rdi`/`%rsi`/… 传参、`%rax` 放返回值（详见大主题5）。所以看到 `%rdi=3` 就能推断它多半是第一个参数。此外 x86-64 还另有 16 个用于浮点/SIMD 的 `%xmm0`–`%xmm15`（大主题7 AS-7.1），以及内核态才用的段/控制寄存器，本课整数部分聚焦这 16 个。

### 1.4.4 条件码（标志）：CF / ZF / SF / OF

条件码是一组**单比特标志**，存在标志寄存器（32 位视图 `%eflags`、64 位 `RFLAGS`）里，记录**最近一条**算术/逻辑指令结果的性质。四个最常用：

```
CF (Carry Flag)     进位/借位标志 —— 无符号运算溢出（进位或借位）
ZF (Zero Flag)      零标志       —— 结果为 0
SF (Sign Flag)      符号标志     —— 结果最高位为 1（按有符号看为负）
OF (Overflow Flag)  溢出标志     —— 有符号运算溢出
```

它们由算术/逻辑/比较指令**隐式设置**（如 `cmp`/`test`/`add`），再由条件跳转 `jCC`、条件传送 `cmov`、`setCC` 读取，是实现 `if`/循环/比较的桥梁（详见大主题3、大主题4）。本机用两次 `cmp` 直接观测标志变化：

```
# rax = 7
cmpq $7, %rax   →  eflags = 0x246 = [ PF ZF IF ]     # 7-7=0，ZF 置位
cmpq $9, %rax   →  eflags = 0x293 = [ CF AF SF IF ]  # 7-9 借位为负，CF/SF 置位、ZF 清零
```

（环境串：gdb 15.1 @Linux 6.18.5 x86-64，`cmp` 做减法但只设标志、不存结果。）

这段证据把条件码"属于程序员可见状态"讲实了：`cmp` 比较相等时 `ZF=1`，不相等且被减数较小时 `CF/SF=1、ZF=0`——后面 `je`（相等则跳，看 ZF）、`jl`（小于则跳，看 SF、OF）就是读这些位来决定分支。初学者要建立的直觉：**比较/算术指令不直接"返回真假"，而是在标志位里留下痕迹，跳转指令再来看这些痕迹**。输出里的 `IF` 是中断使能标志、`PF/AF` 是奇偶/辅助进位，本课不重点用。

### 1.4.5 内存：按字节编址的虚拟地址空间

第四类可见状态是**内存**——从程序视角看，它是一个巨大的、按字节编址的数组（x86-64 下地址是 64 位，实际用其中较低位）。程序的代码、全局数据、运行栈、堆都住在这个统一的虚拟地址空间里，指令通过内存操作数（`disp(base,index,scale)`，见大主题2）读写它。

上一节 `%rsp = 0x7fffffffce00` 这个很大的地址就是**栈**所在的高地址区；代码（如 `%rip=0x401146`）在低地址区。初学者要建立三点认识：其一，寄存器只有 16 个、极小极快，内存极大但慢，程序不断在两者间搬数据（load/store）；其二，每个进程看到的是自己独立的虚拟地址空间（背后由 OS 分页映射到物理内存，属 L4-01 操作系统），所以不同次运行、不同进程的同一变量地址可以不同（尤其开了 ASLR/PIE，见大主题7）；其三，字节序为**小端**（多字节对象低字节存低地址，见大主题6 AS-6.5），这会影响你在 `gdb` 里逐字节看内存时的读法。

### 1.4.6 用 gdb 观察机器状态

把上述四件套一次性观测出来的入门工具是 `gdb`：`info registers`（或 `i r`）看全部寄存器（含 `rip`、`eflags`），`info registers rax rdi`（选看），`p/x $eflags` 看标志的十六进制，`x/…` 系列检查内存，`stepi`/`si` 单步一条机器指令。本机 `info registers` 列出的寄存器名恰好印证了状态模型：

```
rax rbx rcx rdx rsi rdi rbp rsp r8 r9 r10 r11 r12 r13 r14 r15   # 16 个整数通用寄存器
rip                                                              # 程序计数器
eflags                                                           # 条件码/标志
cs ss ds es fs gs  k0..k7  fs_base gs_base                       # 段寄存器/掩码寄存器等（本课非重点）
```

（环境串：gdb 15.1 @Linux 6.18.5 x86-64。）

这正是本课的"实证心态"落地：机器状态不是抽象概念，用 `gdb` 断点 + `info registers` + 单步，就能亲眼看到每条指令如何改写 `%rip`、寄存器、条件码与内存。建议初学者拿一个 `-O0 -g` 编的小程序，反复用 `si` 单步、每步看寄存器变化，机器级程序的状态机模型会迅速变得具体。
