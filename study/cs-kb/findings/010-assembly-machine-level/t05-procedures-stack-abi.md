## 5.1 call/ret 机制：返回地址的压栈与弹栈

### 5.1.1 call 一条指令做两件事

`call` 指令实现"调用"：它把**返回地址**（`call` 的下一条指令的地址）压入栈，然后把 `rip` 改成被调用函数的入口地址，从而把控制流转移过去。用伪代码写这两步是：

```
push  下一条指令地址      ; 即 call 执行完本应回到的地方
jmp   目标函数入口
```

返回地址就是"函数干完活该回到哪里"的书签。CPU 没有别的地方记这个书签，所以它被放在栈顶——`call` 把 `rsp` 减 8、把 8 字节的返回地址写进去。这解释了为什么函数调用天然要用到栈：每嵌套调用一层，就多压一个返回地址。`call` 有直接形式（`call 目标标号`，目标是立即数偏移）和间接形式（`call *%rax`、`call *(%rbx)`，目标从寄存器或内存取，用于函数指针、虚函数表）。

### 5.1.2 ret 一条指令做一件事

`ret` 实现"返回"：它把栈顶的 8 字节弹出到 `rip`，控制流就回到了 `call` 之后。伪代码：

```
pop   rip                ; 取回 call 当初压入的返回地址
```

`ret` 正是 `call` 的逆操作——`call` 压什么，配对的 `ret` 就弹什么。初学者最该记住的一点是：`ret` 不认识"哪个函数调的我"，它只无条件地把**当前栈顶**当成返回地址弹进 `rip`。所以只要栈顶在函数执行期间被写坏（例如局部数组越界覆盖了返回地址），`ret` 就会跳到一个错误甚至被攻击者控制的地址——这就是栈溢出攻击的机理（详见大主题7）。函数的序言/尾声之所以要小心维护 `rsp`，根本目的就是保证 `ret` 执行时栈顶恰好是当初 `call` 压入的那个返回地址。

### 5.1.3 gdb 单步实证：call 前后 rsp 与栈顶

在本机对 `int main(){ return (int)add6(1,2,3,4,5,6); }` 单步，断在 `add6` 的**第一条指令**（尚未执行 `endbr64`/`push rbp`），观察刚被 `call` 转移进来的瞬间：

```
$ gcc -std=c11 -O0 -g -fno-asynchronous-unwind-tables -fno-stack-protector drv.c -o drv
$ gdb -q -batch -x cmds ./drv
Breakpoint 1, add6 (...) at drv.c:1
ENTRY(after call, before endbr64): rsp=0x7fffffffce48 rip=0x555555555129  rsp_mod16=8
top-of-stack (return addr) = 0x7fffffffce48:  0x000055555555519f
```

（环境串：gcc 13.3.0 / gdb 15.1 @Linux 6.18.5 x86-64。`0x...519f` 是 `main` 里 `call add6` 的下一条指令地址，即返回地址；此刻它正躺在 `rsp` 指向的栈顶。）

这段输出把 5.1.1 讲的抽象坐实成了三个可看见的事实：控制流已经跳进 `add6`（`rip=0x...129`，正是 `add6` 入口）；栈顶 `0x...ce48` 存着返回地址 `0x...519f`；`rsp` 相对进入 `main` 前下降了 8 字节（就是那次 `push` 返回地址）。等 `add6` 执行到 `ret`，CPU 会把 `0x...519f` 弹回 `rip`，控制流精确回到 `main`。`rsp_mod16=8` 这个细节留到 5.5 讲对齐。

### 5.1.4 push/pop 与栈的生长方向

x86-64 的栈**向低地址生长**：`push` 先把 `rsp` 减去操作数宽度（压 8 字节则 `rsp -= 8`）再写入，`pop` 先读出再把 `rsp` 加回去。`call`/`ret` 内部就复用了这套 `push`/`pop` 语义来搬运返回地址。

理解方向是读所有栈帧图的前提：地址数值越大的在"栈底"方向（更早压入、更靠近程序启动时的高地址），越小的在"栈顶"方向（`rsp` 当前所指，最新压入）。所以栈帧图里习惯把**高地址画在上方、低地址画在下方**，`rsp` 指向图的最下面。一个常见的初学者困惑是"栈明明在'长大'，地址却在'变小'"——记住 x86-64 的栈是"往下长"的即可，后面所有 `sub $N, %rsp`（分配局部空间）都是在把栈顶继续往低地址推。

#### 来源与时效

- 锚点：Intel SDM Vol.2「CALL」「RET」「PUSH」「POP」指令定义（返回地址压/弹、`rsp` 增减语义）；CSAPP 3rd ed §3.7.1–3.7.2（图 3.25 运行时栈、图 3.27 call/ret）；核实 2026-07-26。
- 本机实证：`gdb` 单步断在 `*add6` 入口，`rsp=0x7fffffffce48`、栈顶存返回地址 `0x000055555555519f`（gcc 13.3.0 / gdb 15.1 @Linux 6.18.5，scratchpad 真跑）。
- 三来源（SDM 语义 + CSAPP 图示 + 本机反汇编/单步）一致，无冲突。

## 5.2 整型参数传递：前 6 个走寄存器，第 7+ 入栈

### 5.2.1 前六个整型/指针参数的固定寄存器顺序

x86-64 System V 约定：函数的前 6 个 INTEGER 类参数（整数、字符、枚举、指针等能放进通用寄存器的类型）依次通过以下 6 个寄存器传递，顺序固定：

```
参数序号:   1     2     3     4     5     6
寄存器:    %rdi  %rsi  %rdx  %rcx  %r8   %r9
```

这个顺序是 ABI 硬性规定的、必须背下来的核心表。它是"函数间通信的公共协议"：调用方按这个顺序把实参放进寄存器，被调用方就按同样顺序去这些寄存器里取形参，双方不用商量也能对上。之所以优先用寄存器而非栈，是因为寄存器访问远快于内存——把最常见的"参数不多"情形优化到零内存访问。参数宽度小于 64 位时用对应的子寄存器名（如 32 位 `int` 用 `%edi`、`%esi`…，见大主题2 的子寄存器别名），但占的仍是同一个物理寄存器的槽位。

### 5.2.2 第 7 个及以后的参数通过栈传递

超过 6 个的参数放到栈上，由调用方在 `call` 之前压入；ABI 规定它们**从右到左**压栈（即最后一个参数先压、第 7 个参数最后压，于是第 7 个参数落在最靠近栈顶、最低地址处）。被调用方通过正偏移（相对帧指针 `rbp` 或 `rsp`）来读取这些栈上参数。

### 5.2.3 实证：6 参数全走寄存器 vs 8 参数溢出到栈

对两个函数各反汇编，先看 6 参数的调用方 `caller`：

```
$ gcc -std=c11 -O0 -fno-asynchronous-unwind-tables -c callret.c -o callret.o
$ objdump -d -M att callret.o
0000000000000049 <caller>:
  51:  mov    $0x6,%r9d        ; 第6参数 -> r9
  57:  mov    $0x5,%r8d        ; 第5参数 -> r8
  5d:  mov    $0x4,%ecx        ; 第4参数 -> rcx
  62:  mov    $0x3,%edx        ; 第3参数 -> rdx
  67:  mov    $0x2,%esi        ; 第2参数 -> rsi
  6c:  mov    $0x1,%edi        ; 第1参数 -> rdi
  71:  call   ...  <add6>
```

（环境串：gcc 13.3.0 / objdump 2.42 @Linux 6.18.5 x86-64。6 个实参恰好填满 `rdi/rsi/rdx/rcx/r8/r9`，零次压栈；注意编译器倒着填是无关紧要的实现顺序，关键是每个值进了约定的寄存器。）

再看 8 参数的调用方 `caller8`——多出的第 7、第 8 个参数改用 `push` 压栈：

```
$ objdump -d -M att args8.o
0000000000000057 <caller8>:
  5f:  push   $0x8              ; 第8参数先压（更高地址）
  61:  push   $0x7              ; 第7参数后压（更低地址=更靠栈顶）
  63:  mov    $0x6,%r9d         ; 第1~6参数仍走寄存器
  ...
  7e:  mov    $0x1,%edi
  83:  call   ...  <add8>
  88:  add    $0x10,%rsp        ; 调用后回收这 16 字节栈参数
```

对应地，被调用方 `add8` 用**正偏移**读这两个栈上参数（前 6 个仍从寄存器读）：

```
0000000000000000 <add8>:
  47:  mov    0x10(%rbp),%rax   ; 第7参数
  4e:  mov    0x18(%rbp),%rax   ; 第8参数
```

（环境串：同上。`0x10(%rbp)`/`0x18(%rbp)` 是正偏移，落在返回地址与保存的旧 `rbp` 之上方，正是调用方压入的栈参数区；调用返回后 `add $0x10,%rsp` 把两个 8 字节参数一次回收。）

### 5.2.4 分类维度：INTEGER 走这 6 个，浮点走 XMM

上面 6 寄存器顺序只适用于 **INTEGER 类**参数。浮点参数（`float`/`double`）走另一组寄存器 `%xmm0`–`%xmm7`（最多 8 个），与整型参数各走各的、独立计数。聚合类型（结构体/联合）由 ABI 的分类算法按大小和字段类型拆成 INTEGER/SSE 片段分别塞进这两组寄存器，超出则整体走栈。

初学者只需先记住"整型/指针一条队、浮点另一条队，互不占位"。举例来说 `f(int a, double x, int b)` 里 `a` 进 `rdi`、`b` 进 `rsi`（整型队第 1、2 位），而 `x` 进 `xmm0`（浮点队第 1 位）——两条队各自从头排。浮点寄存器与聚合分类的细节归大主题7 与大主题6，本处只做分账提示，避免把"第 7 个参数才入栈"误当成"第 7 个整型参数才入栈"。

#### 来源与时效

- 一手/规范级：x86-64 psABI §3.2.3「Parameter Passing」——INTEGER 序列 `rdi, rsi, rdx, rcx, r8, r9`，SSE 序列 `xmm0–xmm7`，溢出走栈（从右到左）。核实 2026-07-26。ABI 精确提交哈希本会话未取（见抬头待核）。
- 佐证：CSAPP 3rd ed §3.7.3 图 3.28（参数寄存器 6 个的同一顺序表）。
- 本机实证：`caller` 6 参数全填寄存器零压栈；`caller8` 第 7/8 参数 `push`、被调用方 `0x10(%rbp)`/`0x18(%rbp)` 读取（gcc 13.3.0 / objdump 2.42，scratchpad 真跑）。
- 三来源一致（顺序、溢出方向、整/浮分账均吻合），无冲突。R2 §3-A 曾确认前 6 参数顺序，本轮本机反汇编再次坐实。

## 5.3 返回值与寄存器保存：rax 返回、caller/callee-saved 划分

### 5.3.1 返回值放在 rax

函数的整型/指针返回值通过 `%rax` 传回调用方（宽度不足 64 位时用其子寄存器 `%eax`/`%ax`/`%al`）。需要 128 位整型返回值时用 `%rax:%rdx`（`rdx` 放高 64 位）；浮点返回值走 `%xmm0`（次要用 `%xmm1`）。

`rax` 是"函数的出口"。前面 5.2 说参数是"进口"（走 rdi… ），这里返回值是"出口"（走 rax）。所以读任何一段函数汇编，尾声之前把结果算进 `%rax` 几乎是标配——`ret` 之后调用方就直接从 `rax` 取结果。5.1.3 的 `main` 里 `return (int)add6(...)` 就是把 `add6` 留在 `eax` 的返回值直接当作 `main` 的结果。

### 5.3.2 谁负责保存寄存器：调用者保存 vs 被调用者保存

寄存器只有一组，调用方和被调用方都想用，于是 ABI 把 16 个通用寄存器划成两类，明确"跨越一次调用后谁保证它的值还在"：

```
callee-saved（被调用者保存，调用前后保持不变）:
    %rbx  %rbp  %r12  %r13  %r14  %r15   （外加栈指针 %rsp）

caller-saved（调用者保存，可能被被调用方随意覆写）:
    %rax  %rcx  %rdx  %rsi  %rdi  %r8  %r9  %r10  %r11
```

这套划分是一份"责任合同"，解决同一个矛盾：函数 A 调用函数 B 时，A 正在用的寄存器会不会被 B 弄脏？合同规定——若 A 的值放在 **callee-saved** 寄存器里，A 可以放心，因为 B 若要用这些寄存器，B 有义务在序言里先 `push` 保存、在尾声里 `pop` 恢复，还回来时原封不动；若 A 的值放在 **caller-saved** 寄存器里，A 不能指望它，B 可以任意覆写，A 若还想要就得在 `call` 之前自己存好。这样双方各担一半，既不必每次调用都保存全部 16 个寄存器，又保证了正确性。

### 5.3.3 实证：被调用方保存 callee-saved 寄存器

写一个必须用到 `rbx`（callee-saved）的函数，观察它序言里 `push %rbx`、尾声里 `pop %rbx`：

```
$ cat use_rbx.c
long use_rbx(long x){ long acc=0; for(long i=0;i<x;i++) acc+=g(i); return acc; }
$ gcc -std=c11 -O1 -fno-asynchronous-unwind-tables -S use_rbx.c
use_rbx:
        endbr64
        push    %rbp            ; 保存三个 callee-saved 寄存器
        push    %rbx            ;   （本函数要跨 call 使用它们）
        ...
        pop     %rbx            ; 尾声按逆序恢复
        pop     %rbp
        ret
```

（环境串：gcc 13.3.0 @Linux 6.18.5 x86-64，`-O1`。函数要在循环里跨 `call g` 保存累加值与循环变量，就把它们放进 callee-saved 的 `rbx`/`rbp`，并在两端配对 `push`/`pop`——这正是"被调用者负责保存"合同的执行现场。）

### 5.3.4 易错点：r10/r11 与 rsp 的归属

初学者常把 `r10`、`r11` 误记成 callee-saved——它们是 **caller-saved**（临时寄存器，`r11` 常被用作 scratch，`r10` 在传静态链指针等场景用），跨调用不保证保留。另一个易混点是 `%rsp`：它由序言/尾声的配对操作隐式维持"调用前后一致"，通常单列为"被调用者维护"而非普通的 callee-saved 数据寄存器。CSAPP 图 3.34 与 ABI §3.2.1 的寄存器角色表在这套划分上完全一致，可交叉互证。

#### 来源与时效

- 一手/规范级：x86-64 psABI §3.2.1「Registers and the Stack Frame」图/表——callee-saved：`rbx, rbp, r12–r15`（及 `rsp`）；其余通用寄存器 caller-saved；返回值 `rax`(:`rdx`)、`xmm0`(:`xmm1`)。核实 2026-07-26。
- 佐证：CSAPP 3rd ed §3.7.5 图 3.34（caller-saved/callee-saved 划分，与 ABI 一致）。
- 本机实证：`use_rbx` 序言 `push %rbx`/`push %rbp`、尾声配对 `pop`，坐实被调用者保存义务（gcc 13.3.0，scratchpad 真跑）。
- 两来源（ABI + CSAPP）划分一致，无冲突。

## 5.4 栈帧序言与尾声：搭建与拆除本次调用的骨架

### 5.4.1 序言（prologue）：保存旧帧、分配本帧

被调用函数开头的几条固定指令称为**序言**，它把当前调用需要的栈帧建立起来。典型的带帧指针序言是：

```
push   %rbp            ; 1) 保存调用者的帧指针（callee-saved）
mov    %rsp, %rbp      ; 2) 把 rbp 设为本帧基准（帧指针）
sub    $N, %rsp        ; 3) 向下挪 rsp，为局部变量分配 N 字节
```

第 1 步把上一层的 `rbp` 存到栈上（因为 `rbp` 是 callee-saved，用之前必须先保存）；第 2 步让 `rbp` 指向一个本次调用固定不动的锚点；第 3 步一次性把栈顶下压 N 字节，腾出本函数所有局部变量、寄存器溢出、栈参数暂存区的空间。有了固定的 `rbp`，函数体内所有局部变量都能用相对 `rbp` 的固定负偏移访问（如 5.1.3 里的 `-0x8(%rbp)`），不受 `rsp` 后续变化影响。并非每个函数都有第 3 步——不需要局部栈空间的函数会省略 `sub`。

### 5.4.2 尾声（epilogue）：拆除本帧、恢复旧帧、返回

函数结尾把栈帧还原到进入前的样子，再 `ret`。带帧指针时最常见的是用一条 `leave` 抵两步：

```
leave                  ; 等价于 mov %rbp,%rsp ; pop %rbp
ret                    ; 弹返回地址回 rip
```

`leave` 先把 `rsp` 拉回 `rbp`（一步回收所有局部空间，抵消序言的 `sub`），再 `pop %rbp` 恢复调用者的帧指针（抵消序言的 `push %rbp`）。此后栈顶恰好是返回地址，`ret` 就能正确返回。5.1.3 与递归例子里反汇编尾部出现的 `leave; ret` 或 `pop %rbp; ret` 就是这个模式。要点是尾声必须严格抵消序言对 `rsp` 的所有改动，否则 `ret` 会弹错栈顶。

### 5.4.3 帧指针 rbp 与省略帧指针

`rbp`（帧指针/base pointer）在整个函数执行期间固定指向本帧一个基准位置，让局部变量、参数用稳定偏移寻址，也让调试器能沿 `rbp` 链回溯调用栈；`rsp`（栈指针）则随 `push`/`pop`/`call` 时刻变动，永远指向栈顶。

编译器在优化时常"省略帧指针"（`-fomit-frame-pointer`，在 `-O1` 及以上默认开启），此时不 `push %rbp`/`mov %rsp,%rbp`，而是全程用相对 `rsp` 的偏移访问局部变量，把 `rbp` 释放成一个额外的通用寄存器用。这解释了为什么 `-O0` 的汇编几乎都有整齐的 `push %rbp; mov %rsp,%rbp` 序言、而 `-O2` 的常常看不到——不是没有栈帧，而是不再用 `rbp` 当帧指针了。初学者读优化后的代码时，把"帧基准"从 `rbp` 换成 `rsp` 来理解即可。

### 5.4.4 一次调用后的栈帧全图

把上面各件拼起来，一个带帧指针、且向被调用者传了栈参数的完整栈帧长这样（高地址在上、`rsp` 在最下）：

```
        高地址（栈底方向）
   ┌────────────────────────┐
   │  ... 调用者的栈帧 ...     │
   ├────────────────────────┤
   │  第 8 个参数            │  ← 调用者压入的栈参数
   │  第 7 个参数            │     被调用方用 +偏移(%rbp) 读
   ├────────────────────────┤
   │  返回地址 (call 压入)    │  ← ret 会弹走它
   ├────────────────────────┤
   │  保存的旧 %rbp          │  ← push %rbp 存入；%rbp 现指向这里
   ├────────────────────────┤  ◄── %rbp
   │  保存的 callee-saved    │     （如 push %rbx）
   │  局部变量 / 溢出区       │  ← 用 -偏移(%rbp) 访问
   │  （由 sub $N,%rsp 分配） │
   ├────────────────────────┤  ◄── %rsp（当前栈顶）
   │  ↓ 红区 128B（叶函数用）  │
        低地址（栈顶方向）
```

这张图是本大主题的总纲：5.1 的返回地址、5.2 的栈参数、5.3 的 callee-saved 保存区、5.4 的旧 rbp 与局部变量区、5.5 的红区，全部各就各位。读任何函数的反汇编时，对照这张图先定位序言（建帧）与尾声（拆帧），中间的指令就都能落到"访问哪一格"上。

#### 来源与时效

- 一手/规范级：x86-64 psABI §3.2.2「The Stack Frame」（帧布局、rbp 用途）；Intel SDM Vol.2「LEAVE」「ENTER」（`leave` = `mov %rbp,%rsp; pop %rbp`）。核实 2026-07-26。
- 佐证：CSAPP 3rd ed §3.7.1 图 3.25（通用栈帧结构，参数构造区/保存寄存器/局部变量分层）。
- 本机实证：`-O0` 反汇编普遍 `push %rbp; mov %rsp,%rbp [; sub $N,%rsp]` 序言，尾声 `leave; ret` 或 `pop %rbp; ret`；`caller8` 调用后 `add $0x10,%rsp` 回收栈参数（gcc 13.3.0 / objdump 2.42，scratchpad 真跑）。
- 三来源一致；栈帧图各格由 5.1/5.2/5.3 各例逐格坐实，无冲突。

## 5.5 红区与栈对齐：两条必须满足的硬约束

### 5.5.1 16 字节栈对齐要求

ABI 规定：在执行 `call` 指令的那一刻，`%rsp` 必须是 16 的倍数（即 `%rsp % 16 == 0`）。等价的官方表述是——控制转移到函数入口时，`(%rsp + 8)` 是 16 的倍数。写成关系式：

```
call 时刻:            %rsp % 16 == 0
函数入口（call 压入返回地址后）:  (%rsp + 8) % 16 == 0   ⇔   %rsp % 16 == 8
```

这条约束存在是因为某些指令（尤其 SSE/AVX 的对齐访存 `movaps`/`movdqa` 等）要求操作数 16 字节对齐，编译器需要一个稳定的对齐基准才能安全地把 16 字节的向量数据放上栈。它是"每个函数都要遵守、才能互相信任对方入口是对齐的"公共前提。初学者常忽略它，直到手写汇编调用 `printf` 时因为栈没对齐而在浮点相关代码里莫名崩溃——原因就是违反了这条 16 字节对齐约束。

### 5.5.2 实证：入口 rsp%16==8，push rbp 后归零

5.1.3 那次 `gdb` 单步已经把这条规则拍在明面上——断在 `add6` 入口（`call` 刚压完返回地址）时：

```
ENTRY(after call, before endbr64): rsp=0x7fffffffce48  rsp_mod16=8
...（单步执行 endbr64 -> push %rbp -> mov %rsp,%rbp 之后）...
after push rbp+mov rsp,rbp: rsp=0x7fffffffce40  rbp=0x7fffffffce40  rsp_mod16=0
```

（环境串：gcc 13.3.0 / gdb 15.1 @Linux 6.18.5 x86-64，scratchpad 真跑。）

这正好验证了 5.5.1 的关系式：入口处 `rsp = 0x...ce48`，`rsp % 16 == 8`（因为 `call` 刚压了 8 字节返回地址，把原本对齐的 `rsp` 挪了 8）；再执行序言的 `push %rbp` 又压 8 字节，`rsp` 变成 `0x...ce40`，`rsp % 16` 回到 0——栈重新对齐。可见"入口余 8、押一次 rbp 复位"是这条对齐约束在序言里的自然结果。若函数体内还要 `sub $N,%rsp`，编译器会把 N 取成能维持 16 字节对齐的值。

### 5.5.3 红区（red zone）：叶函数栈顶下方的 128 字节

ABI 允许函数使用 `%rsp` **下方（更低地址）128 字节**的区域而无需先用 `sub` 分配，这块区域叫红区（red zone）。形式化说：

```
可用红区范围: [%rsp - 128, %rsp)
前提: 该区域内容不被信号处理器/中断破坏（Linux 内核遵守此约定）
```

红区是给**叶函数**（不再调用任何其它函数的函数）的一个提速优化：它需要的少量局部变量可以直接写到 `rsp` 下方，省掉序言里的 `sub $N,%rsp` 和尾声里对应的回收，指令更少更快。之所以只有叶函数敢用，是因为一旦本函数再 `call` 别人，那次 `call` 会把返回地址压到 `rsp` 处，紧接着被调用方的执行会继续往下压栈，直接覆盖掉 `rsp` 下方的红区——所以非叶函数不能依赖红区，必须老实 `sub` 出正式空间。

### 5.5.4 实证：叶函数用红区、不 sub rsp

对一个只做算术、不调用别人的叶函数，`-O0` 下也能看到它把局部值写到 `rbp` 下方却**没有** `sub $N,%rsp`：

```
$ gcc -std=c11 -O0 -fno-asynchronous-unwind-tables -fno-stack-protector -S redzone.c
leafrz:
        endbr64
        pushq   %rbp
        movq    %rsp, %rbp          ; 注意：这之后没有 sub $N,%rsp
        movq    %rdi, -24(%rbp)     ; 局部量直接写到 rsp/rbp 下方
        movq    -24(%rbp), %rax
        addq    $1, %rax
        movq    %rax, -8(%rbp)      ; -8、-16、-24 都在 rsp 下 128B 红区内
        movq    -24(%rbp), %rax
        addq    $2, %rax
        movq    %rax, -16(%rbp)
        movq    -8(%rbp), %rax
        imulq   -16(%rbp), %rax
        popq    %rbp
        ret
```

（环境串：gcc 13.3.0 @Linux 6.18.5 x86-64，`-O0 -fno-stack-protector`。`mov %rsp,%rbp` 后 `rbp==rsp`，随后 `-8/-16/-24(%rbp)` 全部落在 `rsp` 下方，都在红区 128 字节内，所以编译器安全地省掉了 `sub`。对比 5.6 里的非叶 `fact` 就有 `sub $0x10,%rsp`。）

红区可用 `-mno-red-zone` 关闭（内核代码、或会在 `rsp` 下方触发异步事件的场景必须关，否则红区会被中断帧破坏）。这也是内核态 x86-64 代码普遍带 `-mno-red-zone` 的原因。

#### 来源与时效

- 一手/规范级：x86-64 psABI §3.2.2——16 字节栈对齐（`(%rsp+8)` 在入口为 16 倍数）；红区定义为 `%rsp` 下 128 字节、叶函数可用、不被信号破坏。核实 2026-07-26。ABI 精确提交哈希本会话未取（见抬头待核）。
- 佐证：CSAPP 3rd ed §3.7.1（栈对齐要求）；关于红区 CSAPP 提及较简，以 ABI 为主承重。
- 本机实证：`gdb` 观测入口 `rsp%16==8`、序言后 `rsp%16==0`；叶函数 `leafrz` 无 `sub $N,%rsp` 而用 `-8/-16/-24(%rbp)`（红区）；非叶 `fact` 有 `sub $0x10,%rsp`（gcc 13.3.0 / gdb 15.1 / objdump 2.42，scratchpad 真跑）。
- 数值 128 字节、16 字节对齐由 ABI 一手规定并经本机 gdb/反汇编坐实，无冲突。

## 5.6 递归与局部变量：帧内布局与逐层堆叠

### 5.6.1 局部变量在栈帧内的布局

函数的局部变量（凡是不能常驻寄存器的，如取了地址的变量、数组、结构体，或寄存器不够时溢出的标量）存放在本函数栈帧里，通过相对帧基准的固定偏移访问。`-O0` 下每个局部变量几乎都有一个确定的栈槽：

```
$ objdump -d -M att misc.o        # 函数 fact，-O0
0000000000000000 <fact>:
   4:  push   %rbp
   5:  mov    %rsp,%rbp
   8:  sub    $0x10,%rsp          ; 为局部/参数备份分配 16 字节
   c:  mov    %rdi,-0x8(%rbp)     ; 把参数 n 备份到局部栈槽 -8(%rbp)
  10:  cmpq   $0x1,-0x8(%rbp)     ; if (n <= 1)
```

（环境串：gcc 13.3.0 / objdump 2.42 @Linux 6.18.5 x86-64，`-O0`。`-O0` 为了可调试，会把寄存器传入的参数 `n` 也先落到栈槽 `-0x8(%rbp)` 再用；`-O2` 则倾向全程留在寄存器、不落栈。）

局部变量落在栈里而非固定全局地址，正是"每次调用有自己一份"的机制基础——每进一次函数，序言 `sub` 出一块新空间，局部变量就住在这次调用专属的帧里，与其它调用互不干扰。这一点在递归里最关键。

### 5.6.2 递归：每一层调用一个独立栈帧

递归函数每调用自己一次，就执行一次序言、在栈上叠一个新帧；每个帧有自己独立的参数备份和局部变量，所以不同层的同名变量（如 `fact` 各层的 `n`）互不覆盖。到达基例后逐层 `ret`，栈帧逆序一个个弹出、拆除。

递归之所以"能记住每一层的状态"，靠的就是栈：调用去程一路压帧（越来越深、地址越来越低），回程一路弹帧（`ret` 依次返回）。这也解释了递归太深会**栈溢出**（stack overflow）——每层帧都占一段栈空间，层数 × 每帧大小超过线程栈上限（Linux 默认通常 8 MiB，`ulimit -s` 可查）就撞栈边界崩溃。

### 5.6.3 实证：fact(5) 的栈帧逐层堆叠

对 `int main(){ return (int)fact(5); }`，在递归最深处（`n==1`）用 `gdb` 回溯，能直接看到 5 个 `fact` 帧叠在 `main` 之上：

```
$ gcc -std=c11 -O0 -g -fno-asynchronous-unwind-tables -fno-stack-protector rec.c -o rec
$ gdb -q -batch -x cmds ./rec      # break fact if n==1; run; bt
#0  fact (n=1) at rec.c:1
#1  0x0000555555555157 in fact (n=2) at rec.c:1
#2  0x0000555555555157 in fact (n=3) at rec.c:1
#3  0x0000555555555157 in fact (n=4) at rec.c:1
#4  0x0000555555555157 in fact (n=5) at rec.c:1
#5  0x0000555555555170 in main () at rec.c:2
```

（环境串：gcc 13.3.0 / gdb 15.1 @Linux 6.18.5 x86-64，scratchpad 真跑。）

这份回溯把 5.6.2 讲的"每层一帧、各存各的 n"变成看得见的事实：栈上同时存在 5 个 `fact` 帧，各自的 `n` 是 1、2、3、4、5，互不覆盖；第 #1–#4 帧的返回地址都是同一个 `0x...5157`（即 `fact` 内 `call fact` 的下一条指令），因为它们都是从 `fact` 自身的同一处递归调用点进来的；最外层 #5 的返回地址 `0x...5170` 才指回 `main`。回程时 5 个帧按 `ret` 逐个弹出，把 `1*2*3*4*5` 一层层乘回去。`gdb` 正是靠 `rbp` 链（或调试信息）把这些帧一节节走出来的。

### 5.6.4 尾声：从栈帧看局部变量的生命周期

一个局部变量的"生命"精确等于它所在栈帧的存在期间——序言分配、尾声（`leave`/`add $N,%rsp`）回收。函数一返回，帧被拆，其局部变量的栈空间立刻可被后续调用重用。

这直接解释了一条经典 C 陷阱：不能返回指向局部变量的指针。函数返回后该局部变量所在的帧已被拆除，那段栈空间随时会被下一次调用覆写，返回的指针于是变成悬垂指针，读它是未定义行为。把 5.1–5.6 连起来看，一次函数调用的完整生命周期就是——`call` 压返回地址并转移（5.1）、按约定收参数（5.2）、序言建帧并保存 callee-saved（5.3/5.4）、在满足对齐与红区约束下（5.5）使用局部变量、（递归则再叠帧，5.6）、把结果放进 `rax`、尾声拆帧、`ret` 弹返回地址回到调用方。

#### 来源与时效

- 一手/规范级：x86-64 psABI §3.2.2（栈帧与局部变量区）；CSAPP 3rd ed §3.7.4（递归过程，图 3.35 递归栈帧）。核实 2026-07-26。
- 佐证：Intel SDM Vol.2（`CALL`/`RET` 语义支撑逐层压弹）。
- 本机实证：`fact` `-O0` 用 `sub $0x10,%rsp` + `-0x8(%rbp)` 存 `n`；`gdb` 回溯 `fact(5)` 见 5 层独立帧、返回地址链 `0x...5157`(层间)/`0x...5170`(回 main)（gcc 13.3.0 / gdb 15.1 / objdump 2.42，scratchpad 真跑）。
- 两来源（ABI + CSAPP §3.7.4）一致，无冲突。栈上限数值（Linux 默认约 8 MiB）为环境相关、以 `ulimit -s` 为准，非 ABI 规定。
