# L5-10·大主题2 专业操守与责任（ACM Code 2018）

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01 ｜先修：L5-10·大主题1 规范性伦理框架（后果论/义务论/德性论/正义论） ｜一手锚点：ACM Code of Ethics and Professional Conduct（2018 版，四节结构）；CS2023 SEP KA（结构锚） ｜成熟度：稳定（GA），现行为 2018 版，为 1992 版之后二十六年来首次全面修订

本大主题以 ACM Code of Ethics and Professional Conduct 2018 版为职业腿一手承重。本课属社会伦理职业，无可跑源码、无可数值验证的对象：源码腿与本机实证腿缺失，全部断言以"援引 ACM Code 具体条款做可核对陈述"支撑，另用 CS2023 SEP 知识领域做结构锚，不伪造任何代码实证。条款编号与标题均取自官方 2018 版文本并经独立镜像交叉核对。

ACM Code 2018 的整体架构是四节：第 1 节一般伦理原则（1.1–1.7，人人适用）、第 2 节职业责任（2.1–2.9，计算从业者适用）、第 3 节职业领导责任（3.1–3.7，对带团队/定政策者的加码要求）、第 4 节遵守准则（4.1–4.2）。前三节层层收窄适用人群，第四节收口于"如何对待这套准则本身"。每条正文都由一个祈使句标题加一段阐释组成，本报告逐条讲清标题含义与初学者常见误解。

## 2.1 一般伦理原则（§1）

第 1 节的七条对"每一个从事计算工作的人"都成立，是整部准则的道德底座，后面第 2、3 节的职业要求都要回头受这七条约束。这一节混合了义务论（"应当/不得"式的规则与义务）与德性论（诚实、公平这类品格），是理解 ACM Code 为什么被称作"义务论+德性论混合腿"的地方。

### 2.1.1 公共利益优先（1.1）

第 1 节开篇一条要求把公众与人类福祉放在首位，并明确"所有人都是计算的利益相关者"。

> 1.1 Contribute to society and to human well-being, acknowledging that all people are stakeholders in computing.（为社会与人类福祉做贡献，承认所有人都是计算的利益相关者。）

这条是整部准则的"首要原则（primary obligation）"，官方措辞里它凌驾于其他条款之上：当职业利益、雇主要求与公共福祉发生冲突时，公共福祉优先。"所有人都是利益相关者"这半句是 2018 版新加的重点——它把受影响者从"直接用户/客户"扩展到被系统间接波及的每一个人，包括没用你产品但被你产品影响的人（例如被推荐算法塑造舆论的旁观者）。

初学者容易把这条读成一句空泛口号。它的实际抓手是"识别谁被影响"：动手前先列出全部利益相关者（用户、非用户、弱势群体、后代、环境），再评估你的技术选择对他们各自意味着什么。它和后果论的"总效用最大化"形似，但落点在"义务"——你有义务主动考虑公共利益，而不只是事后算一笔总账。这条也是第 3 节领导责任 3.1 的源头。

### 2.1.2 避免伤害（1.2）

第二条要求不制造伤害，这里的"伤害"指对他人的负面后果，尤其是重大或不可逆的。

> 1.2 Avoid harm.（避免伤害。）

标题只有两个词，但官方阐释把"harm"定义得很宽：身体、心理、财产、名誉、环境乃至社会性伤害都算，且包含"不作为造成的伤害"。它引入了一个关键限定——只有在有充分正当理由、且伤害无法避免时，经过深思熟虑才可造成必要伤害，而且要设法把伤害降到最小、并对受害者负责。

这条最容易被误读为"绝对不能有任何负面后果"，那不现实（任何真实系统都有代价）。准确理解是"最小化并正当化"：当伤害不可避免时，你要能说清为什么、向谁负责、如何补救。它和 1.1 的关系是——1.1 说要主动做好事，1.2 说至少别做坏事，二者一正一反。对初学者常见的抓手是"负责任地披露漏洞"：发现安全缺陷后，不声张地私下利用会造成伤害，因此本条要求走负责任披露流程。这条与 2.5（评估风险）、2.9（安全）在工程上直接咬合。

### 2.1.3 诚实可信（1.3）

第三条要求诚实、可信，不欺骗。

> 1.3 Be honest and trustworthy.（诚实且值得信赖。）

这条覆盖对系统能力、局限、成本、设计的如实陈述：不夸大产品能力、不隐瞒已知缺陷、不做误导性声明、如实披露相关的利益冲突。它既是义务（不撒谎的规则），也是德性（"值得信赖"是一种品格）。

对初学者，最直观的例子是不要"demo 造假"或谎报测试通过率；进一步，隐瞒"这个模型在少数群体上准确率低"这类已知局限也违反本条，因为沉默同样构成误导。它和第 2 节的 2.7（促进公众正确理解）连成一条线：诚实不只是不说假话，还包括不制造错误印象。常见误区是把"商业保密"当成撒谎的挡箭牌——保密（见 1.7）允许你不说，但不允许你说假话。

### 2.1.4 公平且不歧视（1.4）

第四条要求公平对待，并主动采取行动防止歧视。

> 1.4 Be fair and take action not to discriminate.（做到公平，并采取行动避免歧视。）

标题里的"take action"是要点：这不是"别主观歧视就行"的消极义务，而是要求主动排查与纠正不公，包括系统性、隐性的歧视。官方阐释点名了基于年龄、肤色、残障、族裔、家庭状况、性别认同、工会身份、军人身份、国籍、种族、宗教信仰、性别、性取向等的歧视都属违反。

在计算语境下，这条正是"算法公平/偏见"议题的规范源头：训练数据里潜藏的历史偏见、模型对不同群体的差异化表现，即便无人主观恶意，也可能落入本条禁止的"歧视性后果"，而"take action"要求你去检测并缓解它。初学者易混的一点是——公平不等于"对所有人一模一样"：有时对处境不同的群体一视同仁反而加剧不公，因此本条也支持合理的可及性照顾。公平度量的技术细节与"公平不可能性定理"属负责任 AI 张力主题，本条只承"规范上要求公平"这一诉求。

### 2.1.5 尊重创造性工作（1.5）

第五条要求尊重产生新思想、发明、创作与计算产物所付出的劳动。

> 1.5 Respect the work required to produce new ideas, inventions, creative works, and computing artifacts.（尊重为产生新思想、发明、创作及计算产物所付出的劳动。）

这条是知识产权与署名伦理的道德根基：尊重版权、专利、商业秘密、许可协议，恰当署名与致谢他人贡献，不剽窃。它同时点出"知识共享同样有价值"——即公共领域与开源共享是被尊重、鼓励的，本条并不要求一切都私有化。

对初学者，最贴近的例子是遵守开源许可证（用了 GPL 代码却闭源分发就违反本条），以及在论文/项目里如实署名与引用。常见误区是把"能拿到就等于能用"——能下载不代表许可你随意使用，许可证条款才是边界。知识产权、许可证类型（copyleft/permissive）与 AI 训练数据版权争议的展开属隐私与知识产权主题，本条只承"尊重他人劳动"的原则。

### 2.1.6 尊重隐私（1.6）

第六条要求尊重隐私。

> 1.6 Respect privacy.（尊重隐私。）

官方阐释把它落到具体动作：只以合法且正当目的收集个人信息，采集最小必要数据，明确告知收集与使用方式，保障数据准确、安全并有留存/销毁政策，尊重当事人的知情同意。它明确"技术使个人信息的收集与交换空前容易，因此从业者负有特别责任"。

这条是隐私工程与数据保护（如数据最小化、知情同意）的伦理源头，也与 GDPR 一类法规的原则同频。对初学者，最小可懂的抓手是"数据最小化"：不为"以后也许有用"而超量收集，因为你多存一份数据就多担一份泄露与滥用风险。常见误区是把"用户点了同意"当万能免责——同意必须是知情且针对特定目的的，笼统的一揽子授权不满足本条精神。隐私保护的技术手段（如差分隐私）与法规细节属隐私专题，本条只承"为何要保护隐私"。

### 2.1.7 守信保密（1.7）

第七条要求信守保密义务。

> 1.7 Honor confidentiality.（信守保密。）

保密指对因职务而获知的、被明示或默示要求保密的信息负有守护义务，例如商业秘密、客户数据、未公开的业务信息。本条设有一个重要例外：当保守秘密会违反法律、违反准则本身、或掩盖对公众的严重伤害时，保密义务让位——这正是举报（whistleblowing）在准则内的合法性来源。

初学者常把 1.6 隐私和 1.7 保密弄混：隐私保护的是"个人对自身信息的控制"，保密保护的是"因特定关系（雇佣、合同）而托付给你的信息"，两者常重叠但出发点不同。理解本条的关键是那个例外——保密不是无条件的，它不能被用来掩盖对公众的重大危害，这一点直接连到第 4 节与 2.5 责任归属主题的举报讨论。

## 2.2 职业责任（§2）

第 2 节从"人人适用"收窄到"计算从业者适用"，共九条，讲的是把工作做好、做扎实、守规矩、可被检验。它对应大主题1 里的"专业德性论"——胜任、尽责、诚实评审是从业者的职业品格。这九条也是 ACM Code 里与软件工程实践最直接咬合的一节。

### 2.2.1 高质量工作（2.1）

第一条要求在过程与产品两方面都追求高质量。

> 2.1 Strive to achieve high quality in both the processes and products of professional work.（在专业工作的过程与产品两方面都力求高质量。）

要点是"过程"与"产品"并列：不能只看最终交付物漂亮，开发流程本身（评审、测试、文档、可维护性）也是质量的一部分。官方阐释强调高质量的工作应尊重并维护用户及受影响者的尊严。

对初学者，这条落地为"别只让 demo 能跑"：能跑的代码和高质量的系统之间隔着测试覆盖、错误处理、可维护性、文档。它和后面 2.5（评估影响与风险）、2.9（安全）互补——质量不只是功能正确，还包括可靠、安全、对人负责。

### 2.2.2 专业胜任与操守（2.2）

第二条要求持续保持高水准的专业能力、行为与伦理实践。

> 2.2 Maintain high standards of professional competence, conduct, and ethical practice.（保持高水准的专业胜任力、职业行为与伦理实践。）

它把"能力"和"操守"绑在一起：技术能力要靠持续学习维持（领域变化快，吃老本会掉队），同时行为与伦理标准也要一贯。官方阐释鼓励从业者在有条件时参与并支持提升这些标准的活动。

初学者要抓住"持续（maintain）"这个动词——胜任不是一次性拿到的证书，而是需要不断更新的状态。它和 2.6（只在胜任领域工作）是一对：2.2 说要把能力养起来，2.6 说没养起来的领域别硬接。

### 2.2.3 遵守既有规范（2.3）

第三条要求知晓并尊重与专业工作相关的既有规则。

> 2.3 Know and respect existing rules pertaining to professional work.（了解并尊重与专业工作相关的既有规则。）

"规则"包括法律法规、组织规章、专业标准。但本条有一个关键平衡：当规则本身不道德、或有充分伦理理由时，可以质疑、可以违反，但要为后果负责，且违规前应先穷尽合法途径去改变规则。

初学者常把这条读成"无条件服从一切规定"，那是误读——ACM Code 明确允许在规则不义时经深思熟虑地不服从，前提是承担责任并优先走正当渠道。这条正是"合法义务"与"道德义务"冲突时的处理框架，和 2.3 之上的公共利益优先（1.1）配合使用。

### 2.2.4 接受并提供专业评审（2.4）

第四条要求既接受他人对自己工作的评审，也为他人提供评审。

> 2.4 Accept and provide appropriate professional review.（接受并提供恰当的专业评审。）

它把评审当成双向义务：你要愿意让别人检查你的工作（代码评审、同行评议、设计审查），也要认真地去评审别人的。官方阐释指出高质量的专业工作依赖于各阶段的评审与批评。

对初学者，最贴近的例子就是代码评审（code review）——本条从伦理层面说明为什么它不是可有可无的形式，而是职业责任。常见误区是把评审当成挑刺或走过场；本条要求的是"恰当（appropriate）"且建设性的评审，目的在提升质量而非表演。

### 2.2.5 全面评估系统及其影响与风险（2.5）

第五条要求对计算机系统及其影响做全面、彻底的评估，包括分析可能的风险。

> 2.5 Give comprehensive and thorough evaluations of computer systems and their impacts, including analysis of possible risks.（对计算机系统及其影响做全面彻底的评估，含对可能风险的分析。）

要点在"impacts"和"risks"：评估不止功能是否正确，还要评估系统对人、对社会的影响与潜在风险。官方阐释要求从业者在有能力做专业评估时如实、客观地给出，且对夸大或掩盖风险负责。

这条是风险评估、影响评估（含算法影响评估）的伦理源头，也直接支撑负责任 AI 里的问责诉求。对初学者，抓手是"上线前问一句：这系统可能怎样出错、会伤到谁"。它与 1.2（避免伤害）、2.9（安全）联动：识别风险（2.5）→ 最小化伤害（1.2）→ 做稳健安全（2.9）。

### 2.2.6 只在胜任领域工作（2.6）

第六条要求只承接自己有能力胜任的工作。

> 2.6 Perform work only in areas of competence.（只在自己胜任的领域从事工作。）

它要求对自己能力有诚实判断：接活前评估自己是否真的能做好，超出能力范围时应寻求资质更高者的意见或明确告知客户局限。这与 1.3 诚实相通——高估自己的能力本身就是一种不诚实。

初学者容易把它误解为"永远不能挑战新领域"。准确理解是"不隐瞒能力缺口"：可以学、可以接有挑战的活，但要如实沟通不确定性、寻求帮助或补足能力，而不是硬撑装懂。它是 2.2（维持胜任）的孪生条款。

### 2.2.7 促进公众理解（2.7）

第七条要求促进公众对计算及其相关技术与后果的认识与理解。

> 2.7 Foster public awareness and understanding of computing, related technologies, and their consequences.（培育公众对计算、相关技术及其后果的认知与理解。）

它把从业者置于"公众教育者"的位置：因为你懂技术，你有义务帮公众看清技术能做什么、不能做什么、有什么后果，反制误导性宣传与技术神话。

对初学者，这条延伸自 1.3 诚实——不仅自己不说假话，还要主动帮公众建立正确认知，例如向非专业受众如实解释 AI 系统的能力边界，纠正"AI 无所不能"或"AI 必然客观中立"这类误解。它是"负责任 AI 透明度诉求"在个人从业者层面的一个落点。

### 2.2.8 仅在授权下访问资源（2.8）

第八条要求只在获得授权、或因公共利益被迫时，才访问计算与通信资源。

> 2.8 Access computing and communication resources only when authorized or when compelled by the public good.（仅在获授权、或因公共利益而不得不为时，才访问计算与通信资源。）

这条是"未授权访问即不当"的伦理表述：不擅自侵入系统、不越权读取数据、不占用不属于你的资源。它给了一个狭窄例外——当访问是为阻止对公众的紧迫重大伤害且别无他法时（例如紧急制止正在进行的攻击），可被正当化，但门槛很高。

初学者要把它和"黑客好奇心"划清界限：即便你能进入某系统、即便你没恶意，未经授权本身就违反本条。这条是计算机犯罪、渗透测试伦理的规范源头——合法渗透测试的关键正是"事先获得授权"。

### 2.2.9 稳健且可用的安全（2.9）

第九条要求设计与实现"稳健且可用地安全"的系统，这是 2018 版新增的一条。

> 2.9 Design and implement systems that are robustly and usably secure.（设计并实现稳健且可用地安全的系统。）

两个形容词都是重点。"robustly"指安全要经得起意外与恶意的考验，且系统部署后威胁会演变，因此要持续做监控、打补丁、漏洞上报。"usably"是本条的点睛之笔：安全功能如果难用到用户绕开它，就等于没有——所以可用性必须作为安全设计的首要需求之一。

这是 2018 版为回应普适计算、物联网带来的新攻击面而专门加入的条款，把"安全"从可选项提升为职业责任。对初学者，最好记的例子是密码策略：强制到极端复杂又频繁更换的密码，反而逼用户写在便利贴上——这违反"usably secure"。本条与 1.2、2.5 串成安全责任链：评估风险、避免伤害、把安全做得既稳健又能被真正用起来。

#### 来源与时效
- 一手锚点：ACM Code of Ethics and Professional Conduct（2018 版）§2 职业责任 2.1–2.9，条款标题与阐释（核实 2026-08-01）。
- 交叉核对：2.1–2.9 全部条款编号与标题经 SFU CMPT 276 课程镜像逐条核对一致；2.9「Design and implement systems that are robustly and usably secure」及其"usability as a priority design requirement""monitoring, patching, and vulnerability reporting"阐释另经 Communications of the ACM 独立核对；2.9 为 2018 版新增条款（多来源一致）。
- 版本时效：2018 版稳定；结构无「⚙演进快」。
- 冲突项：无。

## 2.3 职业领导责任（§3）

第 3 节再收窄一层，只对"以领导身份行事者"生效——不论职衔高低，凡是能定政策、带团队、管资源、对系统方向拍板的人都算领导。它在第 1、2 节之上加码：领导者不仅要自己守规，还要为让整个组织守规、为组织行为的社会后果负责。共七条。

### 2.3.1 公共利益为核心（3.1）

第一条要求领导者确保公共利益在一切专业计算工作中处于核心位置。

> 3.1 Ensure that the public good is the central concern during all professional computing work.（确保在所有专业计算工作中，公共利益都是核心关切。）

这是把 1.1（人人应贡献公共利益）在领导层放大：领导者要保证团队做出的东西、定下的方向，整体上服务而非损害公众。官方阐释把"公共利益"称为领导角色应始终关注的中心。

对初学者，理解要点是"个人守则"与"组织守则"的区别：一个普通工程师做好本分即可，而领导者要对"这个项目整体是否有益于公众"负责——哪怕每个下属都合规，方向错了仍是领导的责任。这条是第 3 节的总纲。

### 2.3.2 组织社会责任的落实（3.2）

第二条要求领导者清晰表达、鼓励接受，并评估组织成员对社会责任的履行。

> 3.2 Articulate, encourage acceptance of, and evaluate fulfillment of social responsibilities by members of the organization or group.（阐明、鼓励接受并评估组织或团队成员对社会责任的履行。）

三个动词是一条闭环：先把社会责任讲清楚（articulate）、再营造让大家愿意接受的氛围（encourage）、最后检查是否真的做到了（evaluate）。它要求领导者别把伦理当口号，而要建成可落实、可检查的机制。

对初学者，这条落地为"伦理不能只写在墙上"：领导者要把它变成流程（如伦理评审关卡）和考核。它与 4.1（拥护并推广准则）相通，只是站在组织建设的角度。

### 2.3.3 提升工作生活质量（3.3）

第三条要求领导者管理人员与资源，以提升工作生活质量。

> 3.3 Manage personnel and resources to enhance the quality of working life.（管理人员与资源，以提升工作生活的质量。）

它把"对人负责"扩展到自己团队内部：合理配置资源、避免过劳、营造尊重与安全的工作环境。官方阐释关注工作场所的政策与条件应尊重从业者的尊严。

对初学者，这条提醒"伦理不只朝外（对用户/公众），也朝内（对同事/下属）"。它常被在讨论"996"式过劳文化、有毒工作环境时援引——领导者放任这些即违反本条。

### 2.3.4 政策流程反映准则（3.4）

第四条要求领导者制定、应用并支持能体现本准则原则的政策与流程。

> 3.4 Articulate, apply, and support policies and processes that reflect the principles of the Code.（阐明、应用并支持体现本准则原则的政策与流程。）

它要求把这部准则"制度化"：不是靠个人自觉，而是把准则精神写进公司政策、开发流程、决策机制里，让守则成为默认路径。官方阐释还要求领导者让成员知晓这些政策与其背后的合规程序。

对初学者，这条与 3.2 的差别在于对象：3.2 针对"人"的责任履行，3.4 针对"制度"的设计——把伦理固化到流程里，就算换了人也不走样。它是"隐私设计（privacy by design）""安全默认（secure by default）"这类"把规范内建进流程"思路的组织层依据。

### 2.3.5 创造专业成长机会（3.5）

第五条要求领导者为组织或团队成员创造成长为专业人士的机会。

> 3.5 Create opportunities for members of the organization or group to grow as professionals.（为组织或团队成员创造作为专业人士成长的机会。）

它把 2.2（个人维持胜任）在领导层做了对偶：既然每个从业者有义务保持胜任，领导者就有义务提供让他们能保持胜任的条件——培训、导师、成长路径。

对初学者，这条说明专业发展不只是个人的事，也是组织责任。它常与 3.3 一起被视为"善待团队"的两面：3.3 管当下的工作质量，3.5 管长期的成长空间。

### 2.3.6 系统修改/退役的审慎（3.6）

第六条要求在修改或退役系统时保持审慎。

> 3.6 Use care when modifying or retiring systems.（在修改或退役系统时审慎行事。）

要点是"系统的整个生命周期都要负责"，尤其是变更与下线这两个高风险节点。官方阐释要求充分告知受影响的用户、为迁移/替代/淘汰提供合理支持，注意变更对既有依赖者的冲击。

对初学者，最贴近的例子是"接口停用（deprecation）"：一个被很多人依赖的 API 说关就关会造成连锁伤害，本条要求提前通知、给迁移期、提供替代方案。它是 1.2（避免伤害）在系统生命周期末端的具体化，也和下一条 3.7 衔接。

### 2.3.7 对社会基础设施系统的特别关照（3.7）

第七条要求识别并特别关照那些已嵌入社会基础设施的系统。

> 3.7 Recognize and take special care of systems that become integrated into the infrastructure of society.（识别并特别关照那些已融入社会基础设施的系统。）

它指出：有些系统一旦被社会广泛依赖（支付、电力调度、通信、医疗、政务），其失效或滥用的后果远超普通软件，因此对它们要施加更高的可靠性、安全与连续性标准。官方阐释还提醒即便系统当初不是为关键用途设计的，也可能随时间变成基础设施，领导者要对这种"漂移"保持警觉。

对初学者，这条说明"责任与影响力成正比"：一个玩具 App 崩了没人受伤，但一个被数百万人依赖的系统崩了就是社会事件。它是 2018 版对"关键基础设施"日益软件化这一现实的回应，与 3.6 一起构成对高影响系统的加码要求。

#### 来源与时效
- 一手锚点：ACM Code of Ethics and Professional Conduct（2018 版）§3 职业领导责任 3.1–3.7，条款标题与阐释（核实 2026-08-01）。官方说明"leadership"不限于正式职衔，凡有领导性影响者皆适用。
- 交叉核对：3.1–3.7 全部条款编号与标题经 SFU CMPT 276 课程镜像逐条核对一致。
- 版本时效：2018 版稳定；§3 在 2018 版由旧版"Organizational Leadership Imperatives"重构而来（多来源一致其为现行结构），无「⚙演进快」。
- 冲突项：无。

## 2.4 遵守准则（§4）

第 4 节最短，只有两条，处理"如何对待这部准则本身"。它把前面所有原则从"建议"提升为"成员承诺"：签下 ACM 会员，就意味着承诺遵守并推广这套准则，违反它有会员资格上的后果。

### 2.4.1 拥护、推广并尊重准则（4.1）

第一条要求拥护、推广并尊重本准则的各项原则。

> 4.1 Uphold, promote, and respect the principles of the Code.（拥护、推广并尊重本准则的各项原则。）

三个动词递进：不仅自己遵守（uphold），还要向外推广（promote，鼓励同行也遵守），并尊重准则的精神而非只抠字面。官方阐释指出从业者的行为会影响整个职业的声誉，因此每个人都对准则的公信力负有一份责任。

对初学者，这条说明伦理准则不是"个人私事"：当你看到同行违反、或参与制定可能违反准则的方案时，本条要求你不袖手旁观。它是把个人守则变成职业共同体规范的关键一环，也为 2.5 责任归属主题里的"举报"提供了积极义务的一面。

### 2.4.2 违反准则与 ACM 会员资格（4.2）

第二条声明：违反本准则被视为与 ACM 会员身份不相容。

> 4.2 Treat violations of the Code as inconsistent with membership in the ACM.（将违反本准则视为与 ACM 会员资格不相容。）

这条给准则装上了"牙齿"：它不再只是道德倡议，而是会员制度的一部分——严重或持续违反可导致会员资格受影响。它把遵守从"自愿"锚定为"成员资格的条件"。

初学者要注意本条的现实边界：ACM 是专业协会而非执照发放机构，它的处分是会员层面的（不像医生/律师有吊销执照的国家强制力），因此这套准则的强制力主要来自职业声誉与共同体压力，而非法律。理解这一点很重要——ACM Code 是"专业自律准则"，与"法律"分属两个层面（对应 2.3 里"合法义务 vs 道德义务"的分账）。

#### 来源与时效
- 一手锚点：ACM Code of Ethics and Professional Conduct（2018 版）§4 Compliance with the Code 4.1–4.2，条款标题与阐释（核实 2026-08-01）。
- 交叉核对：4.1「Uphold, promote, and respect the principles of the Code」、4.2「Treat violations of the Code as inconsistent with membership in the ACM」经 SFU CMPT 276 课程镜像核对一致。
- 版本时效：2018 版稳定。ACM 作为专业协会（非执照机构）的强制力性质属职业伦理常识，无「⚙演进快」。
- 冲突项：无。

## 2.5 责任归属与工程落点

本小主题不是 ACM Code 的第五节，而是把前四节的规范"落到工程现场"的接口：准则说了"应当怎样"，本节讲这些义务在真实软件工程动作（发布决策、事件响应、举报）里落在哪、以及责任如何归属。按本库编排的分工，工程实现细节指回软件工程课与相应元课程，此处只承"规范要求什么、落点在哪"，不重复深挖工程流程本身。

### 2.5.1 责任归属：不可推卸的个人责任

ACM Code 的一个贯穿性预设是：从业者对自己参与的工作负有个人责任，不能用"我只是执行命令""这是团队决定"来完全推卸。

这一点散落在多条里——1.2 要求对造成的必要伤害负责、2.5 要求对风险评估的诚实与否负责、2.3 允许在规则不义时违规但要承担后果。把它们合起来看，准则拒绝"责任真空"：一个由多人、多环节、甚至算法参与的系统出了问题，不能因为"没有单一责任人"就无人负责。

对初学者，这正是负责任 AI 里"问责（accountability）"诉求的伦理根基——自动化决策不能成为逃避责任的挡箭牌，系统背后总要有可归责的人。常见误区是把"责任分散"当成"责任消失"；准则的立场恰恰相反：越是复杂协作的系统，越要事先把责任落实清楚。责任链、可审计性、human-in-the-loop 的具体机制属负责任 AI 张力主题，此处只承"个人责任不可推卸"这一原则。

### 2.5.2 发布决策与风险沟通

要不要发布、以什么条件发布一个系统，是把多条准则一次性激活的决策点。

它同时受 2.5（先做全面的影响与风险评估）、1.2（把伤害降到最小并正当化不可避免的伤害）、1.3 与 2.7（如实向用户/公众沟通已知局限，不夸大不隐瞒）约束。也就是说，"能发就发"不是默认，"评估—最小化—如实告知"才是准则要求的发布姿态。

对初学者，一个贴近的场景是发布一个已知在某些边缘场景会出错的模型：准则不必然禁止发布（伤害可被正当化、可被披露时可以发），但要求你先评估清楚、把风险降到合理范围、并对用户如实说明局限，而不是把缺陷藏起来。发布流程、发布门禁的工程实现指回软件工程课，本节只承"发布决策要过哪几条伦理关"。

### 2.5.3 事件响应

系统上线后出了安全事件或造成了伤害，如何响应也在准则的射程内。

2.9 明确要求把"部署后威胁会演变"纳入责任，包含监控、打补丁、漏洞上报；1.2 要求对已造成的伤害负责并设法补救；3.6 要求在系统变更时审慎并告知受影响者。合起来，准则要求的事件响应不是"悄悄修掉就好"，而是"及时缓解 + 对受影响者负责 + 如实沟通"。

对初学者，最好懂的对照是数据泄露：把泄露瞒下来（怕影响声誉）违反 1.2、1.3；准则要求的是及时缓解、通知受影响者、修补并复盘。事件响应的技术流程（on-call、postmortem 等）指回软件工程课，本节只承"响应中要守住哪几条义务"。

### 2.5.4 举报（whistleblowing）的规范落点

当组织内部出现违反准则、违法或危害公众的行为，而内部渠道无法纠正时，向外部披露（举报）在 ACM Code 内是有明确正当性来源的。

它由几条共同支撑：1.1 公共利益优先、1.2 避免（尤其对公众的）伤害、1.7 保密义务的那个例外（保密不能用来掩盖对公众的严重伤害）、以及 4.1 拥护并推广准则。准则同时要求审慎——2.3 提示应先穷尽合法/内部途径，举报前对指控的真实性有充分把握，避免造成不成比例的新伤害。

对初学者，这条要点是"举报不是背叛，掩盖才是"：当保密与公共安全冲突时，准则站在公共安全一边，但也不鼓励轻率、未经核实的揭发。举报的现实代价、法律保护差异很大，属超出本准则的社会/法律议题；此处只承"ACM Code 在何种条件下为举报提供伦理正当性"。

### 2.5.5 义务论与德性论的混合结构（与分析工具主题的接口）

回看整部 ACM Code，它在伦理学框架上是一个"义务论为骨、德性论为肉"的混合体，理解这一点能把前四节串成一条线。

第 1、2 节里大量"应当/不得/避免"式的祈使句是义务论的规则腿（1.2 避免伤害、2.8 未授权勿访问、2.3 遵守规则）；而"诚实可信（1.3）""胜任（2.2/2.6）""审慎（3.6）"这些指向行为者品格而非单条规则的要求，是德性论的品格腿。准则并不给一个可机械套用的算法，而是要求从业者在具体情境里用判断力去权衡这些原则——这本身就是德性论的姿态。

对初学者，这解释了为什么 ACM Code 读起来是一串原则而非一部"法条+罚则"：它假设你是一个有判断力的专业人，而非只会查表的执行器。它与规范性伦理框架主题（后果论/义务论/德性论/正义论）互为表里——那边讲分析工具，这边是这些工具在计算职业里的一次具体落地。准则并未采纳单一框架，因此遇到原则冲突时（如 1.6 隐私 vs 2.5 全面评估所需的数据），需要回到那套分析工具去权衡，本准则本身不替你裁决。

#### 来源与时效
- 一手锚点：ACM Code of Ethics and Professional Conduct（2018 版）跨条款综合——个人责任（1.2/2.5/2.3）、发布与风险沟通（2.5/1.2/1.3/2.7）、事件响应（2.9/1.2/3.6）、举报（1.1/1.2/1.7 例外/4.1）、义务论+德性论混合（§1–§2 整体结构）（核实 2026-08-01）。
- 结构锚：CS2023 SEP 知识领域将 ACM Code 定位为"专业实践/职业责任"的规范骨架，工程实现落点指回软件工程与相应元课程（https://csed.acm.org/society-ethics-and-professionalism/ ，核实 2026-08-01）。
- 交叉核对：ACM Code 具备"混合义务论与德性论"性质，为 ACM Code 官方导读文《ACM code of ethics: a guide for positive action》（dl.acm.org/doi/10.1145/3173016）与多份伦理学教辅一致的定性。本小主题为跨条款推演，各断言均可回指到上列具体条款编号。
- 演进/待核：本节不涉及快速演进的治理法规（AI 治理框架、EU AI Act 时效等属另一大主题）。举报的法律保护因司法辖区而异，超出 ACM Code 范围，本节不做法律断言，标为超范围。
- 冲突项：无准则内部条款冲突；准则不预设单一伦理框架，原则相互张力（如隐私 vs 全面评估）由使用者按分析工具权衡，此为设计使然而非文本矛盾。
