## 9.1 X.509 证书结构

### 9.1.1 证书是什么：用签名把公钥绑定到身份

一张 X.509 证书是一个结构化的数据文件，核心作用是把"一个公钥"和"一个身份（如域名 example.com）"绑在一起，并由一个证书颁发机构（CA）用自己的私钥对这个绑定关系做数字签名。任何人拿到这张证书，只要信任那个 CA、并用 CA 的公钥验签通过，就能确信"这个公钥确实属于这个身份，是 CA 背书过的"。

证书在逻辑上分成两大块。一块是待签名内容（RFC 5280 里叫 TBSCertificate，to-be-signed），装着身份、公钥、有效期等所有实质信息；另一块是 CA 对这块内容算出的签名值，外加"用了哪种签名算法"的标注。验证时的动作正是第八大主题学过的验签：对 TBSCertificate 部分重新计算，用 CA 公钥核对签名。

**证书本身不是秘密，它是公开的**。你访问任何 HTTPS 网站，服务器都会把它的证书明文发给你——里面只有公钥没有私钥，私钥始终留在服务器上从不外传。证书的价值不在于"藏起来"，而在于"没人能伪造出一张 CA 签名有效、却把攻击者公钥绑到 example.com 上的证书"，因为伪造签名需要 CA 的私钥。这就是为什么整套体系的安全最终压在"CA 私钥不泄露、CA 不乱签"这两件事上。

### 9.1.2 TBSCertificate：待签名主体的字段结构

证书的待签名主体（TBSCertificate）在 RFC 5280 §4.1 中定义为一组固定字段，主要有

version（版本号，现代证书均为 v3，编码值为 2）
serialNumber（序列号，同一 CA 下唯一的正整数）
signature（签名算法标识，须与外层算法一致）
issuer（签发者，即 CA 的可分辨名称 DN）
validity（有效期，含 notBefore 与 notAfter 两个时间点）
subject（主体，即证书持有者的 DN）
subjectPublicKeyInfo（主体的公钥及其算法标识）
extensions（v3 扩展，见 9.1.3–9.1.4）

其中 issuer 和 subject 都是"可分辨名称"（Distinguished Name, DN），由 CN（Common Name）、O（Organization）、C（Country）等一串属性拼成。一个关键关系：**下一级证书的 issuer 必须等于上一级证书的 subject**，这是把证书串成链的"接口"（见 9.2、9.3）。

初学者要抓住两个易错点。其一，序列号不是"第几张证书"这种小整数，而应是不可预测的大随机数——RFC 5280 与 CA/B Forum 都要求它含足够的熵（通常 ≥64 位随机），目的是防止一类利用哈希碰撞伪造证书的攻击（历史上 MD5 碰撞攻击正是靠可预测序列号得手）。其二，早年习惯把域名塞进 subject 的 CN 字段，但现代规则已明确：**验证域名要看 SAN 扩展（9.1.4），CN 中的域名被忽略**——这是初学者读老教程时最常踩的坑。

本机用 OpenSSL 解析教学叶证书，可直接看到这些字段的真实取值

```
serial=2C16B969C78D3B5F475F2A6BE6D5A560A361559F
subject=CN = example.test
issuer=CN = Demo Intermediate CA, O = KB
notBefore=Jul 30 02:37:35 2026 GMT
notAfter=Oct 28 02:37:35 2026 GMT
```

serial 是一个 160 位的大随机数；issuer（中间 CA）与 subject（叶）不同，正体现了"叶证书由中间 CA 签发"。

### 9.1.3 v3 扩展机制与 critical 标志

X.509 v3 引入了可扩展的 extensions 字段，让证书能携带标准之外的附加约束和信息。每个扩展由三部分组成：一个标识它类型的 OID、一个布尔的 critical（关键）标志、以及扩展的具体内容。RFC 5280 §4.2 规定了这一机制。

critical 标志决定了"验证方遇到一个它不认识的扩展时该怎么办"

如果 critical=TRUE 而验证方不认识该扩展，必须拒绝整张证书
如果 critical=FALSE 而验证方不认识，则可以安全地忽略它

这条规则是理解扩展的钥匙。它让标准可以往前演进（新扩展设为非关键，老客户端忽略即可继续工作），同时保证真正涉及安全的约束（如"这张证书不能当 CA 用"）被标为关键，任何合规验证方都不敢无视。初学者可以把 critical 类比成"这条规矩看不懂就必须停手"，而非关键扩展是"看不懂可以跳过的备注"。一个常见的安全陷阱是把本该关键的约束错标成非关键，导致老客户端把它当备注忽略掉，从而绕过限制。

### 9.1.4 关键扩展一览

RFC 5280 定义了一组标准扩展，实践中最要紧的几个是

basicConstraints 标明该证书是否为 CA（CA:TRUE/FALSE），若为 CA 还可带 pathLenConstraint 限制其下还能再套几层 CA
keyUsage 限定公钥的用途（如 digitalSignature、keyCertSign、cRLSign 等），CA 证书须含 keyCertSign
extendedKeyUsage（EKU）给出更细的用途（如 serverAuth 表示可用于 TLS 服务器认证、clientAuth 用于客户端认证）
subjectAltName（SAN）列出证书覆盖的身份，TLS 中放域名（DNS:）或 IP，**现代域名匹配只认这里**
authorityKeyIdentifier（AKI）与 subjectKeyIdentifier（SKI）分别标识"签我的那把 CA 公钥"和"我自己的公钥"，用来在一堆证书里快速找到父证书、加速路径构建
authorityInfoAccess（AIA）给出签发者证书的下载地址（caIssuers）和 OCSP 响应器地址
cRLDistributionPoints（CDP）给出该证书对应 CRL 的下载地址

其中 basicConstraints 与 keyUsage 是安全的承重扩展，务必设为 critical。一个反例能说明为什么：如果一张普通网站的叶证书没有把 basicConstraints 设为 CA:FALSE 并标关键，且客户端验证有缺陷，攻击者理论上就可能拿这张叶证书去反过来签发别的证书——把自己变成一个"影子 CA"。历史上著名的 2009 年 Moxie Marlinspike 攻击正是利用了老客户端不检查 basicConstraints 的缺陷。

本机教学叶证书的扩展解析真实输出为

```
X509v3 Basic Constraints: critical
    CA:FALSE
X509v3 Extended Key Usage:
    TLS Web Server Authentication
X509v3 Subject Alternative Name:
    DNS:example.test, DNS:www.example.test
```

CA:FALSE 且关键，表示它是纯叶证书不能签别的证书；EKU 限定只能用于 TLS 服务器认证；SAN 列出它覆盖的两个域名。

### 9.1.5 编码格式：ASN.1、DER 与 PEM

X.509 证书的内容用 ASN.1（抽象语法记法）描述结构，再用 DER（Distinguished Encoding Rules）序列化成一串确定的二进制字节。DER 的"确定性"很重要——同一份内容只有唯一一种合法字节编码，因为签名是对这串字节算的，若编码可变则签名无法复现验证。

日常见到的 `.pem` / `.crt` 文件多是 PEM 格式：把 DER 二进制做 Base64 编码，再用 `-----BEGIN CERTIFICATE-----` 和 `-----END CERTIFICATE-----` 包起来的纯文本。所以 PEM 只是 DER 的文本外壳，二者可无损互转。

初学者常被一堆后缀绕晕，记住两条即可。第一，`.pem`/`.crt`/`.cer` 通常是文本（PEM）或二进制（DER）的证书，`.key` 是私钥，`.csr` 是证书签名请求（见 9.3）；后缀名只是习惯，真正决定内容的是里面是文本还是二进制。第二，"证书链文件"往往是把叶证书和若干中间证书的 PEM 块**依次拼接**在一个文件里，顺序一般是"叶在前、CA 在后"——TLS 服务器就是这样把整条链一次发给客户端的。

## 9.2 CA 信任链与信任模型

### 9.2.1 信任锚与根 CA

信任锚（trust anchor）是验证一条证书链时"无需再向上验证、直接当作可信起点"的那把公钥，在 Web PKI 中它就是根 CA 的证书。根证书是自签名的——它的 issuer 等于 subject，签名由它自己的私钥做，所以对根证书验签只能证明"它没被篡改"，不能证明"它可信"。它的可信性完全来自它被**预装**进了操作系统或浏览器的信任库（见 9.5.1）。

这是初学者最需要转过弯的一点：**信任链的顶端不是靠密码学"证明"出来的，而是靠"预先约定"确立的**。你的电脑出厂时内置了一份根 CA 名单（几十到一两百个），这份名单就是你所有 HTTPS 信任的最终来源。密码学负责把"信任根"这一点扩散成"信任由它签出的成千上万张证书"，但"根本身可信"是一个人为的、行政层面的决定（由微软、苹果、谷歌、Mozilla 等运营各自的根计划来审核 CA 是否够格入库）。

### 9.2.2 中间 CA 与层级信任

现实中根 CA 几乎从不直接签发终端实体（网站）证书，而是先签出若干中间 CA（intermediate CA / subordinate CA），再由中间 CA 去签叶证书，形成"根 CA → 中间 CA →（可再多级）→ 叶证书"的层级结构。每一级都用自己的私钥签下一级的证书。

这样分层的核心动机是**保护根私钥**。根 CA 的私钥一旦泄露，整个信任体系崩塌且极难挽救（要把根从全球几十亿设备的信任库里换掉，周期以年计）。因此根私钥通常被离线保存在物理隔离的硬件安全模块里，平时根本不联网、极少动用；日常大量的签发工作交给可以在线、可以撤换的中间 CA。万一某个中间 CA 出事，只需吊销那一张中间证书，根安然无恙。

初学者可类比"公司公章"：董事长的总章（根）锁在保险柜里几乎不用，平时盖章由各部门的授权分章（中间 CA）负责；分章丢了换一个即可，总章不受影响。层级信任的本质就是"把稀有而致命的根信任，安全地下放成大量可日常使用、可随时收回的下级签发权"。

### 9.2.3 证书链如何串起来

一条证书链靠字段的首尾相接构成：**每张证书的 issuer 等于其父证书的 subject，且每张证书的签名可用父证书里的公钥验证通过**。链的形式是

叶证书（issuer = 中间CA）← 中间证书（subject = 中间CA，issuer = 根CA）← 根证书（自签名，subject = 根CA）

验证方从叶开始，逐级向上找到父证书、逐级验签，直到到达一个在本地信任库里的信任锚（根）为止。

初学者要理解"服务器发链、客户端补根"这个分工。TLS 握手时，服务器把**叶证书 + 中间证书**打包发给你（通常不发根，因为根你本地已经有了）；你的客户端在本地信任库里找到对应的根，把链补全并逐级验证。所以如果网站管理员**忘了配置中间证书**，很多客户端会因为"接不上到根的链"而报错——这是真实运维里最常见的证书故障之一，而不是证书本身无效。

用根 CA 签出中间 CA、再用中间 CA 签出叶证书后，把中间证书作为 `-untrusted` 传入即可验证成功

```
openssl verify -CAfile root.crt -untrusted int.crt leaf.crt
leaf.crt: OK
```

而如果不提供中间证书（模拟服务器漏配中间），链在叶这一层就断开

```
openssl verify -CAfile root.crt leaf.crt
error 20 at 0 depth lookup: unable to get local issuer certificate
error leaf.crt: verification failed
```

错误号 20（unable to get local issuer certificate）正是"找不到父证书、链断了"的典型症状。

### 9.2.4 信任模型对比：层级 vs 信任网 vs TOFU

Web PKI 采用的是**严格层级信任模型**（一小撮权威根往下分发信任）。作为对照，还有两种常见模型。一是 PGP/GPG 的**信任网**（web of trust）：没有中心 CA，用户之间互相签名彼此的公钥，信任靠"我信任的人信任他"这样的社交路径传递。二是 SSH 常用的 **TOFU**（Trust On First Use，首次使用即信任）：第一次连接时无条件接受对方公钥并记下来，之后若公钥变了就报警。

三者的权衡很直观。层级模型的优点是可扩展、可撤销、用户零配置（信任库出厂就有），缺点是把巨大权力集中在少数 CA 手里，任一 CA 失守都能危害全网（这正是 9.5 的 CT 要监督的问题）。信任网无单点、去中心，但对普通用户太难用、无法规模化，且撤销机制薄弱。TOFU 极简、无需任何基础设施，但对"第一次连接就被中间人"毫无防御。

**Web PKI 之所以选层级模型，是为了"规模化 + 用户零心智负担"**，代价是必须额外建一套机制来约束被集中授权的 CA（吊销 + CT），这也正是 9.4、9.5 存在的理由。

### 9.2.5 交叉签名与信任库过渡

一张 CA 证书可以被**不止一个**父级签名，这叫交叉签名（cross-signing）。同一个中间 CA 公钥，既被"已经广泛内置的老根"签一份、又被"较新的自家根"签一份，从而在新根还没普及到所有老设备时，仍能靠老根被老设备信任。

这是解决"信任库更新滞后"这一现实难题的关键手段。新根 CA 从被创建到进入全球绝大多数设备的信任库，往往要好几年（老手机、老系统可能永远不更新）。交叉签名让 CA 在过渡期"脚踏两条链"，客户端能沿任一条走通即可。初学者最熟悉的实例是 Let's Encrypt 早期靠 IdenTrust 老根交叉签名，才让它签的证书在推出初期就被海量老设备接受——这也解释了为什么"同一张服务器证书，在不同设备上验证出的链可能不一样"。

## 9.3 证书签发与验证

### 9.3.1 签发流程：CSR、域名验证与 ACME

申请一张证书的标准起点是证书签名请求（CSR, Certificate Signing Request）：申请者在本地生成密钥对，把**公钥**和身份信息打包成 CSR、再用自己的**私钥**对 CSR 自签一次（证明"我确实持有这个公钥对应的私钥"），然后把 CSR 发给 CA。私钥全程不出本地。

CA 在签发前必须做域名控制验证（Domain Control Validation, DCV），确认申请者真的控制它声称的域名。常见方式有：在网站特定路径放一个 CA 指定的文件（HTTP-01）、在 DNS 里加一条 CA 指定的 TXT 记录（DNS-01）等。验证通过后，CA 取 CSR 里的公钥、配上自己审核过的身份和有效期、加上各扩展，组成 TBSCertificate 并用 CA 私钥签名，签出的就是正式证书。这一整套流程如今高度自动化，主流协议是 **ACME**（RFC 8555），Let's Encrypt 等免费 CA 即基于它。

初学者要抓住两个要点。其一，**CA 从不接触你的私钥**——它只见公钥，这是 PKI 安全的基石。其二，绝大多数公开 TLS 证书只做了"域名控制"这一层验证（这类叫 DV，Domain Validated），它只证明"申请者控制了这个域名"，**不证明"这家网站背后的公司是谁"**；后者需要 OV/EV 那样更重的组织身份审核。所以看到 HTTPS 锁标只意味着"到该域名的连接被加密且域名被验证过"，不等于"这家公司可信"。

### 9.3.2 路径构建

验证一张证书前，客户端要先"构建路径"：从叶证书出发，反复寻找"其 subject 等于当前证书 issuer 且其公钥能验证当前证书签名"的父证书，直到抵达本地信任库里的某个信任锚。authorityKeyIdentifier / subjectKeyIdentifier 扩展（9.1.4）就是用来加速这个"找父亲"过程的索引。

路径构建之所以单独成为一步、且比想象中难，是因为现实中"父证书"可能不唯一：由于交叉签名（9.2.5）和 CA 换根，同一张证书可能存在**多条**通往不同信任锚的候选路径，客户端要在其中找出至少一条完全有效的。这也是为什么有的老旧客户端"路径构建能力弱"，明明存在一条有效链却找不到而报错。初学者只需知道：路径构建（找出候选链）和下面的路径验证（检查链是否合规）是两件事，前者是"搭桥"，后者是"验桥"。

### 9.3.3 路径验证的关键检查步骤

拿到一条候选链后，客户端按 RFC 5280 §6 从信任锚往叶逐级检查。教学层面的核心步骤是

1. 签名有效：每张证书的签名都能用其父证书的公钥验证通过
2. 有效期内：验证的当前时间落在每张证书的 notBefore 与 notAfter 之间
3. 未被吊销：每张证书都没有被吊销（查 CRL/OCSP，见 9.4）
4. 名称链合规：每张证书的 issuer 等于父证书的 subject
5. 基本约束成立：链上除叶以外的每张证书 basicConstraints 均为 CA:TRUE，且 pathLenConstraint 未被超出
6. 用途匹配：keyUsage / extendedKeyUsage 允许当前用途（如 TLS 服务器需 serverAuth）
7. 名称约束满足：链上任何 CA 的 nameConstraints 都未被下级违反（见 9.3.4）
8. 到达信任锚：链的顶端是本地信任库中的一个信任锚

以上任一步失败，整张证书即判定无效。注意"域名是否匹配你要访问的主机"（把 SAN 和 URL 里的主机名比对）严格说是 TLS 客户端在证书路径验证之外**额外**做的一步（属应用层的 endpoint identification），但对 Web PKI 同样必不可少。

初学者最容易忽略第 3、5、6、7 步，以为"签名对 + 没过期"就万事大吉。实际上正是这几步在拦截真实攻击：第 5 步拦"叶证书冒充 CA"，第 6 步拦"邮件证书被拿去认证网站"，第 7 步拦"某国 CA 越权签发别国域名"。把验证理解成"八道关卡缺一不可"，比理解成"验个签名"要准确得多。

### 9.3.4 名称约束（Name Constraints）

名称约束是放在 **CA 证书**上的一个扩展（nameConstraints），用来限定"这个 CA（及其下级）**只被允许**为哪些名字空间签发证书"，可用 permittedSubtrees（白名单）和 excludedSubtrees（黑名单）表达，例如"该中间 CA 只能签 `*.example.com` 的证书"。RFC 5280 §4.2.1.10 定义，且要求把它标为 critical。

它的价值在于**约束授权范围、把风险关进笼子**。设想一家企业想自建一个中间 CA 来签发内部服务器证书，理想做法是让上级 CA 在这张中间证书里加名称约束，限定它只能签 `*.corp.example.com`。这样即便该内部 CA 私钥被盗，攻击者也无法用它签出 `google.com` 的证书——验证时第 7 步会因违反名称约束而拒绝。

初学者易混"名称约束"和"叶证书的 SAN"：SAN 说的是"这张叶证书覆盖哪些域名"，是被授予的身份；名称约束说的是"这个 CA 有权签哪些域名"，是授权的边界。一个在链上层，一个在链底层，方向相反。遗憾的是历史上名称约束部署率偏低、且部分客户端支持不全，所以它是"很好但未被充分利用"的安全工具。

### 9.3.5 有效期 ⚙演进快·锚版本

证书的有效期由 validity 字段的 notBefore/notAfter 两个时间点界定。这是本大主题**演进最快**的数值，务必锚定版本与日期。当前（核实 2026-07-30）由 CA/Browser Forum Ballot **SC-081v3**（2025-04 通过）确立的公开 TLS 证书最大有效期缩短时间表为

2026-03-15 起：最长 200 天
2027-03-15 起：最长 100 天
2029-03-15 起：最长 47 天

（此前自 2020-09 起的上限是 398 天。）同一张票还同步把域名验证（DCV）的复用期一路压缩到 2029 年的 10 天。

有效期缩短的核心动机与 9.4 的吊销困境直接相关：**证书活得越短，"吊销"就越不重要**——一张只活 47 天的证书，就算私钥泄露，攻击窗口也顶多几十天，且它很快自然过期，不必依赖那套一直不太好使的实时吊销机制。代价是运维必须自动化：47 天有效期意味着一年要续期约 8 次、DCV 一年要重做约 35 次，手工换证已完全不现实，ACME 自动化几乎成为唯一可行方案。初学者应把"有效期缩短 + 吊销弱化 + 自动化续期"理解成同一场趋势的三个面：整个 Web PKI 正在从"长寿命证书 + 出事靠吊销"转向"短寿命证书 + 自然过期兜底"。这些具体天数会随后续投票继续变动，引用时务必带上锚版本 SC-081v3 与核实日期。

## 9.4 吊销机制

### 9.4.1 为什么需要吊销

证书在有效期内本应一直可信，但有时必须在到期前**提前作废**：私钥泄露、域名易主、证书信息填错、CA 发现自己误签发等。吊销机制就是让 CA 对外宣告"这张（尚未过期的）证书从现在起不再可信"的手段。

理解吊销的难点在于它天生别扭：证书是离线可验证的（拿到证书自己就能验签），但"它有没有被吊销"却是一个**需要实时查询 CA 才能知道的动态状态**。这就在"离线自足的证书"上强行加了一条"在线依赖"，而这条在线查询链路的可靠性、隐私性、性能，恰恰是过去二十年 Web PKI 反复折腾的痛点，也直接催生了 9.3.5 的"干脆用短寿命证书绕开吊销"的思路。

### 9.4.2 CRL（证书吊销列表）

证书吊销列表（Certificate Revocation List, CRL）是 CA 定期发布并签名的一份"已吊销证书序列号"清单，RFC 5280 §5 定义其结构。客户端下载对应 CRL（地址在证书的 cRLDistributionPoints 扩展里），若待验证证书的序列号在列，即判定已吊销。

CRL 的优点是简单、离线可缓存、由 CA 签名不可伪造；缺点是**大且不实时**。一个大 CA 可能有几十上百万张有效证书，其 CRL 可能达到很多 MB，浏览器每次访问都下载显然不现实；而且 CRL 有发布周期，"刚吊销的证书"要等到下次发布才体现，存在时间差。为缓解体积问题，SC-063（见 9.4.7）允许把 CRL 切成带独立 URL 的分片（sharding），客户端只取相关分片。初学者可把 CRL 理解成"作废支票黑名单的定期公告"——权威、可离线核对，但厚、更新慢。

### 9.4.3 OCSP（在线证书状态协议）

在线证书状态协议（Online Certificate Status Protocol, OCSP, RFC 6960）改成"按需单查"：客户端拿证书序列号去问 CA 运营的 OCSP 响应器"这一张现在还有效吗"，响应器返回一个 CA 签名的 good / revoked / unknown 状态。地址在证书的 authorityInfoAccess 扩展里。

OCSP 解决了 CRL"下载整份大清单"的体积问题，但引入两个新麻烦。一是**隐私**：客户端每访问一个 HTTPS 站点就要向该证书的 CA 查一次，等于把用户的浏览行踪实时暴露给 CA——这是 OCSP 后来被弃用的主因。二是**性能与可用性**：每次握手多一次外部往返，且若响应器宕机会拖慢甚至阻断连接，由此逼出了下面的"软失败"和"装订"两个补丁。初学者记住：CRL 是"下载整本黑名单自己查"，OCSP 是"逐张实时问 CA"，前者费带宽、后者泄隐私。

### 9.4.4 软失败问题

现实中浏览器面对"吊销查询失败"（响应器超时、网络不通）时，普遍采用**软失败**（soft-fail）策略：查不到就默认放行、当作没被吊销。因为若采用硬失败（查不到就拒绝连接），一旦 CA 的响应器宕机，全网用它的网站都会瞬间打不开，可用性代价无法接受。

软失败却几乎架空了吊销的安全价值：一个能实施中间人的攻击者，本来就有能力**顺手屏蔽掉受害者的吊销查询**，于是浏览器查不到、软失败放行，被吊销的证书照样被接受。这被业界称作吊销机制的"根本性困境"——安全上想硬失败，可用性上只能软失败。初学者要建立这个略反直觉的认知：**传统在线吊销检查在对抗真正的主动攻击者时基本是无效的**，这正是推动"短寿命证书 + OCSP stapling"的深层原因。

### 9.4.5 OCSP stapling 与 Must-Staple

OCSP stapling（装订，RFC 6961 支持多证书装订）把查询的活儿从客户端转移到服务器：由**服务器**自己定期向 OCSP 响应器取得一份带时间戳、CA 签名的状态响应，在 TLS 握手时随证书一起"装订"发给客户端。客户端无需再自己联系 CA。

这一招同时缓解了 OCSP 的三大痛点：隐私上，客户端不再直连 CA、CA 看不到用户访问了谁；性能上，省掉客户端的额外往返；可用性上，由服务器集中承担查询。配套的 Must-Staple（证书里的一个扩展）能进一步声明"本证书必须装订，客户端见不到有效装订就应拒绝"，从而把软失败变成"针对这张证书的硬失败"、堵上前述被绕过的漏洞。初学者可类比：不装订是"顾客每次进店都自己打电话问总部这张会员卡有没有作废"（慢且暴露行踪），装订是"店家提前拿到总部盖章的有效证明，贴在门口给所有顾客看"。不过 stapling 的部署率一直不算高，Must-Staple 更小众。

### 9.4.6 短寿命证书 ⚙演进快·锚版本

短寿命证书（short-lived certificates）是"用超短有效期从根本上绕开吊销"的思路：如果证书只活几天，那么私钥泄露的攻击窗口也就几天，且证书很快自然过期，**几乎不再需要吊销**。CA/Browser Forum 已为短寿命证书定义了单独门槛，且实践正快速推进——Let's Encrypt 于 2025 年推出了 6 天有效期的证书档位（经 ACME profiles 与 Certbot 4.0 支持）。

这项趋势与 9.3.5 的有效期缩短是一体两面，也是对 9.4.4 软失败困境的"结构性解法"：既然实时吊销对抗主动攻击者本就失效，不如让证书短到根本不依赖吊销。代价仍是对自动化的强依赖——几天一换证，只有 ACME 这类全自动机制才撑得住。初学者可把它理解成"把长期身份证换成随时过期的临时通行证"：临时证丢了也不怕，因为它本来就快作废了。具体天数与门槛属演进快项，引用须带核实日期（2026-07-30）与来源版本。

### 9.4.7 生态迁移 ⚙演进快·锚版本：OCSP 退场、CRL 回归

吊销机制的重心正在发生方向性迁移。CA/Browser Forum Ballot **SC-063v4**（生效 2024-03-15）把运行 OCSP 响应器改为**可选**、而发布 CRL 改为**强制**，并要求吊销信息 24 小时内进入 CRL。随后 Let's Encrypt 于 **2025-08-06 正式关停其 OCSP 服务**、改为提供 CRL——由于 Let's Encrypt 覆盖了极大比例的网站，这标志着 OCSP 在公共 Web PKI 中的实际退场。

这与前面几节是一条完整逻辑：OCSP 因隐私问题（9.4.3）被主动淘汰，CRL（配合分片提升效率）被重新扶正为标准吊销发布形式，而客户端侧的实时检查则越来越多地让位给"短寿命证书自然过期"。初学者要更新一个可能过时的认知——很多老教程把 OCSP 讲成"CRL 的现代替代品"，但截至 2026 年，趋势恰恰**反转**了：CRL 强制、OCSP 可选并正在关停。引用这些结论务必带锚版本（SC-063v4）与生效/关停日期，因为这一带仍在快速变动。

## 9.5 Web PKI 与证书透明度(CT)

### 9.5.1 浏览器与操作系统信任库

Web PKI 的信任起点是操作系统或浏览器内置的**根信任库**——一份被审核通过、允许充当信任锚的根 CA 证书名单。主流的有五套：Microsoft、Apple、Google（Chrome 自 2023 起用自有 Chrome Root Store）、Mozilla（Firefox，也被大量 Linux 发行版沿用），各自运营独立的"根计划"（root program）来审核、加入、移除 CA。

理解信任库要抓住两点。其一，**你信任的是这份名单，而不是"所有 CA"**——不在名单里的 CA 签的证书，你的浏览器一律不信。其二，根计划握有对 CA 的最终生杀权：CA 若违规（乱签发、审计不合格），根计划可以把它**从信任库移除**，这对 CA 是"商业死刑"，也是约束 CA 行为最有力的杠杆。初学者可把根计划理解成"给 CA 发牌照并能吊销牌照的监管机构"，它们运营的根库就是全世界 HTTPS 信任的实际锚点。企业内网也可以往信任库里手动加自己的私有根，从而让内部自签 CA 被内部设备信任——这就是公司能在内网做 HTTPS 拦截审计的原理。

### 9.5.2 证书透明度的动机与 Merkle 日志

证书透明度（Certificate Transparency, CT, RFC 9162）是一套让"所有被签发的证书都被公开记录、可被任何人审计"的机制。CA 在签发证书时（或之后）把证书提交到公开的 CT 日志（log），日志用**仅追加、密码学可验证**的结构保存所有提交，任何人都能监控这些日志、发现"不该被签出来的证书"。

CT 要解决的核心问题是 9.2 埋下的隐患：既然任何一个受信 CA 都能为**任意域名**签发证书，那么一个被攻陷或作恶的 CA 就能悄悄为 google.com 签发伪造证书而无人知晓。CT 把"签发"这件事从暗箱变成公开账本——你无法阻止 CA 签发，但能保证它**藏不住**：google 只要盯着 CT 日志，就能发现有人替它的域名签了它没申请的证书。日志底层是 **Merkle 哈希树**（G11-05 学过的结构），它让日志能高效地向外证明"某证书确实已被收录"且"日志只增不改、没偷偷删改历史"，从而无需信任日志运营者本身。

### 9.5.3 SCT 与递送方式

证书被提交到 CT 日志后，日志返回一个签名时间戳（Signed Certificate Timestamp, SCT），相当于日志出具的"我已收录此证书"的签名回执。浏览器要求 TLS 连接**出示足够的 SCT** 才认为该证书满足 CT 合规。SCT 有三种递送给客户端的方式

嵌入证书（CA 签发时把 SCT 直接放进证书扩展，最常用）
通过 TLS 扩展在握手时递送
通过 OCSP stapling 递送

其中"嵌入证书"用得最多，因为它对服务器零配置——证书里自带 SCT，服务器照常发证书即可。初学者要理解 SCT 的角色：它不是"证书有效性"的证明，而是"这张证书已经被公开记录、藏不住了"的证明。浏览器把"有没有足够 SCT"纳入验证，等于强制要求"任何要被信任的证书都必须先上公开账本"，从而让 CT 的监督能力真正有牙齿。

### 9.5.4 Chrome 的 CT 策略 ⚙演进快·锚版本

Chrome 是最早强制 CT 的浏览器（自 2018-04 起对所有新签发的公开信任证书强制）。其策略的核心是**要求来自不同日志运营者的多个 SCT**，以防单一日志作恶。当前（核实 2026-07-30）Chrome CT 策略的门槛为

有效期 ≤180 天的证书：至少 2 个来自不同运营者的 SCT
有效期 >180 天的证书：至少 3 个来自不同运营者的 SCT

要求"多个不同运营者"的原因是提高作恶门槛：要想悄悄让一张伪造证书通过 CT 检查而不留痕迹，攻击者不仅要控制一个作恶 CA，还得同时串通两个（或以上）独立的日志运营者一起造假，协同难度大幅上升。初学者记住：CT 不阻止误签发，但让误签发**一定会被公开记录并可被发现**；"多日志 SCT"则是防止连日志本身也被收买。这些数值属演进快项，Chrome 会调整，引用须带核实日期。

### 9.5.5 误签发案例

两个历史事件是理解 Web PKI 风险与 CT 由来的经典教材。其一是 **DigiNotar（2011）**：这家荷兰 CA 被入侵，攻击者签发了包括 `*.google.com` 在内的数百张伪造证书，被用于对伊朗用户的中间人攻击；因为当时没有公开记录，事件拖了数周才被发现，DigiNotar 随后被各大浏览器移出信任库并破产。其二是 **Symantec（2015 起陆续暴露）**：其体系被发现多次误签发（包括未经授权的 google.com 测试证书，正是 Google 通过 CT 日志监控发现的），最终导致浏览器在 2017–2018 年逐步不再信任 Symantec 旧体系签发的证书。

这两个案例分别印证了 CT 的必要性与有效性：DigiNotar 说明"没有透明度，一个 CA 失守能长期危害全网而无人知"；Symantec 说明"有了 CT，误签发能被及时抓出并追责"。初学者从中该得到的结论是：**Web PKI 的最大风险不是密码被破解，而是某个受信 CA 被攻陷或作恶**——因为任一 CA 都能为任意域名签发。整个吊销（9.4）与 CT（9.5）体系，本质都是在为"我们不得不信任几百个 CA、而其中任何一个都可能出事"这一结构性风险打补丁。

### 9.5.6 CAA 记录

CAA（Certification Authority Authorization, RFC 8659）是域名所有者在 **DNS** 里发布的一条记录，声明"只有我列出的这些 CA 才被授权为本域名签发证书"。CA 在签发前必须查询目标域名的 CAA 记录，若自己不在授权名单内则**必须拒绝签发**（CA/B Forum 强制要求）。

CAA 与前面机制的分工可这样区分：名称约束（9.3.4）是"上级 CA 限制下级 CA 能签哪些域名"，方向从 CA 端约束；CAA 则是"域名主人反过来限制哪些 CA 能签我"，方向从域名端约束。二者一个自上而下、一个自下而上，共同收窄"谁能为某域名签证书"的口子。初学者可把 CAA 理解成挂在域名上的一张告示："本域名只授权 XX 家 CA 发证，其余一律免谈"——它把 9.5.5 里"任一 CA 都能为任意域名签发"的默认开放，收敛为域名主人显式白名单。
