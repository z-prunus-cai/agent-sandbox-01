## 12.1 栈缓冲区溢出

### 12.1.1 x86-64 栈帧的布局

函数被调用时，会在栈上开辟一块"栈帧"（stack frame）存放它的局部变量、保存的寄存器和返回地址。x86-64 System V ABI 下，`call` 指令先把返回地址（调用点的下一条指令地址）压栈，被调函数序言再压入调用者的帧基址寄存器（saved rbp），然后为局部变量分配空间。关键事实是栈**从高地址向低地址增长**，而局部数组在帧内被放在较低地址，返回地址在较高地址。

一个典型帧从高地址到低地址依次是：

[更高地址] ... 调用者的帧

返回地址（saved return address / saved RIP）

保存的帧基址（saved rbp）

局部变量，例如 char buf[16]

[更低地址] rsp 指向的栈顶

对初学者，最反直觉的一点是：数组元素的下标从低地址往高地址排（`buf[0]` 在最低地址、`buf[15]` 更高），而返回地址在数组**上方**（更高地址）。所以一个"往数组里写太多"的操作，写着写着就会越过 `buf` 的末尾，先盖掉 saved rbp，再盖掉返回地址。数组写入方向和"覆盖返回地址"的方向是一致的，这正是栈溢出能得手的几何前提。

### 12.1.2 溢出如何发生：无边界检查的复制

栈缓冲区溢出的根因是往固定大小的栈数组里写入了超过其容量的数据，而 C 标准库里一批函数**不带目标长度参数**，天然不检查边界：

strcpy(dst, src)  // 一直复制到 src 的 '\0'，不管 dst 多大

gets(buf)         // 读一整行到 buf，无长度上限（C11 已彻底移除）

sprintf(buf, fmt, ...)  // 格式化结果可能远超 buf

memcpy(dst, src, n)     // 若 n 由攻击者控制且大于 dst

这类"越界写"在 MITRE 分类里是 CWE-787（Out-of-bounds Write），栈上专门一格是 CWE-121（Stack-based Buffer Overflow）。CWE-787 在 2025 CWE Top 25 里排第 5（2024 年曾排第 2，两年均在榜），说明越界写至今仍是最高频的严重缺陷之一。

初学者要建立的直觉：漏洞不在"数组"本身，而在"写入量由外部数据决定、却没有和容量做比较"。修复方式就是永远带上界——用 `strncpy`/`snprintf`/`fgets` 并显式传 `sizeof(buf)`，或改用会自动管理长度的类型（C++ `std::string`、Rust `String`）。

### 12.1.3 覆盖返回地址与控制转移

`ret` 指令的语义是"从栈顶弹出一个地址并跳过去执行"。函数正常返回时，弹出的正是序言阶段压入的那个返回地址。如果溢出已经把栈上那一格改写成攻击者选择的地址，那么 `ret` 就会跳到攻击者指定的位置——控制流被劫持。

从 `buf` 到返回地址的距离是可算的：局部数组大小 + 对齐填充 + saved rbp（8 字节）。攻击者构造的输入通常是：

[ 填充字节 × 到返回地址的偏移 ][ 目标地址（8 字节，小端序） ]

只要偏移算对、目标地址填对，`ret` 就把 RIP 设成目标地址。

这里初学者最常混淆两点。其一，覆盖返回地址本身**不会立刻**跳转，劫持发生在函数**返回的那一刻**（执行到 `ret`），中间若崩溃多半是盖坏了别的东西。其二，x86-64 地址要按**小端序**逐字节写（地址 0x401176 写成字节序列 76 11 40 00 00 00 00 00），初学者常按人读的顺序写反而失败。

### 12.1.4 跳转目标之一：注入 shellcode 与 NOP sled

最经典（也是 Aleph One 1996 年演示）的劫持目标，是把一段攻击者的机器码（shellcode，通常是拉起一个 shell 的 `execve("/bin/sh")`）直接放进那个被溢出的缓冲区里，再把返回地址改成指向缓冲区，让 CPU 回来执行自己的数据。

因为攻击者往往不能精确知道缓冲区的运行时地址，常在 shellcode 前垫一长串 `nop`（0x90，什么都不做）构成 NOP sled（滑板）：

[ NOP NOP NOP ... NOP ][ shellcode ][ 指向 sled 中部的返回地址 ]

只要返回地址落在滑板任意一处，CPU 就一路"滑"到 shellcode。

这种"数据被当代码执行"的玩法今天默认已被 NX/DEP（数据页不可执行）挡住——现代系统里栈不可执行，跳回栈上的数据会立即出错。所以本报告的实证要显式加 `-z execstack` 才能重现 1996 年的世界，而真实攻击早已转向"代码复用"（ROP，见大主题13）。这一层历史演进初学者必须记住：注入 shellcode 是理解原理的起点，不是当代主流手法。

### 12.1.5 本机实证：gcc/gdb 观察栈帧与返回地址覆盖

在本机 gcc 13.3.0 + gdb 15.1 上，用一个含 `strcpy` 溢出的玩具程序（仅教学，编译时关掉栈保护、关 PIE、开可执行栈）观察布局。核心源码：

void vuln(const char *s){ char buf[16]; strcpy(buf, s); ... }

编译命令：

gcc -std=c11 -g -fno-stack-protector -no-pie -z execstack -o ovf ovf.c

gdb 在 `vuln` 断点处的真实输出（节选）：

$1 = (char (*)[16]) 0x7fffffffcdd0      // &buf

$2 = (void *) 0x7fffffffcde0            // rbp（saved rbp 所在）

0x7fffffffcde0: 0x00007fffffffce00  0x000000000040121b   // [saved rbp][saved RIP=main 内地址]

distance buf->savedRIP = 24 bytes

这坐实了布局：`buf` 在 rbp−16，saved rbp 在 rbp，返回地址在 rbp+8，故从 `buf` 起点到返回地址正好 16 + 8 = 24 字节。喂入 40 字节全 'A' 时程序 `Segmentation fault`、退出码 139（= 128 + SIGSEGV(11)）；喂入"24 字节填充 + 8 字节标记"后 `ret` 目标变为非法地址，程序在 `ret` 处收到 SIGSEGV/SIGILL——即返回地址确实被我们的输入接管。（本机未演示成功拉起 shell，仅验证到"控制转移被输入控制"这一步，如实标注。）

## 12.2 堆溢出与堆管理

### 12.2.1 堆与分配器的组织

堆是 `malloc`/`free`（C++ `new`/`delete`）动态分配的内存区。分配器（Linux glibc 用 ptmalloc2）把堆切成一个个"块"（chunk），每个块除用户数据外还带**元数据头**，记录本块大小、前块是否在用等。glibc 的块头大致是：

[ prev_size ][ size | 低 3 位标志位 ][ ......用户数据...... ]

其中 size 字段低位复用为标志，PREV_INUSE（0x1）表示前一个物理相邻块是否被占用；被 `free` 的空闲块还会在用户数据区就地存放双向链表指针 fd/bk（把空闲块串进 bin/freelist）。

初学者要抓住的关键：**元数据和用户数据紧挨着、混在同一片连续内存里**。分配器信任这些元数据来决定合并、拆分和取块。因此如果用户数据能越界写到相邻块的元数据上，就等于篡改了分配器的"账本"。

### 12.2.2 堆溢出破坏相邻块元数据

堆缓冲区溢出（CWE-122，Heap-based Buffer Overflow，2025 Top 25 第 16）指越界写发生在堆块上。与栈溢出盖返回地址不同，堆上没有返回地址，攻击者盖的是**物理相邻的下一个块的元数据头**（size、标志位、以及若该块空闲则其 fd/bk 指针）。

被破坏的元数据会在后续 `malloc`/`free` 时被分配器当真使用，攻击者据此诱导分配器做出错误决策——例如把一个受控大小当成真实块大小，或把伪造的链表指针当成合法空闲块。

初学者常以为"堆没有返回地址就安全"，恰恰相反：堆利用的目标是先拿到一次**任意地址写**或"分配到攻击者选定地址"的能力，再用它去改写别处的代码指针（GOT 表项、C++ 虚表指针、函数指针）。也就是说堆溢出通常是"手段"，最终仍指向控制流劫持（见 12.6）。

### 12.2.3 unlink 攻击：经典的元数据破坏利用

历史上最经典的堆利用是 unlink 攻击。当两个相邻空闲块合并时，分配器要把其中一个从双向链表中摘下，早期的 unlink 宏做的是：

FD = P->fd; BK = P->bk;

FD->bk = BK;   BK->fd = FD;

如果攻击者能伪造 P->fd 和 P->bk，令 FD = 目标地址−offsetof(bk)、BK = 想写入的值，那么 `FD->bk = BK` 就等价于往任意地址写入任意值。

这是"用分配器的正常逻辑做坏事"的范例：没有一行代码越权，只是喂进去的元数据是伪造的。现代 glibc 已在 unlink 里加了完整性校验（如 `P->fd->bk == P` 与 `P->bk->fd == P`、size 一致性检查），朴素 unlink 攻击基本失效，但它是理解"元数据即攻击面"的必修课。

### 12.2.4 freelist / tcache 中毒

现代 glibc（2.26 起，2017 年）引入 tcache——每线程的小块空闲缓存，单链表，速度快但早期检查很少。tcache 中毒的核心是：若攻击者能改写某个空闲块里存的 next 指针（fd），就能让下一次 `malloc` 返回一个**攻击者指定的地址**，从而实现"在任意地址处分配"，进而任意写。

这类"改写空闲块链表指针 → 控制下次分配落点"的手法统称 freelist 中毒，fastbin 和 tcache 都适用，是当代堆利用的主力思路之一。

初学者需要区分"堆溢出"和"堆利用手法"：溢出/UAF 是拿到写空闲块指针的**入口**，而 tcache/fastbin 中毒是把这个入口放大成"任意地址分配"的**杠杆**。两者常组合出现。

### 12.2.5 现代分配器加固

glibc 近年针对堆利用加了多道检查，初学者应知其存在（细节属大主题13/专家纵深，此处只登记）：

tcache 双重释放检查：glibc 2.29（2019）给每个 tcache 块加了一个 key 字段，`free` 时若发现块已在 tcache 中就报 `free(): double free detected in tcache 2` 并中止。

Safe-Linking：glibc 2.32（2020）把 fastbin/tcache 的 next 指针与其所在地址做异或混淆，攻击者不知道堆地址就难以伪造出可用的 next 指针。

这些不改变"元数据即攻击面"的本质，只提高伪造成本；攻防持续演进，具体绕过与更多缓解见大主题13。相关版本号（2.26/2.29/2.32）随发行版打包差异可能不同，标为随实现演进。

## 12.3 释放后使用（UAF）

### 12.3.1 悬垂指针与 UAF 定义

释放后使用（Use After Free，CWE-416，2025 CWE Top 25 第 7）指：一块堆内存被 `free`（或 `delete`）后，程序仍持有并**继续使用**指向它的指针。那个指向已释放内存的指针叫悬垂指针（dangling pointer）。

典型代码形态：

p = malloc(n);

free(p);            // 内存归还分配器，p 未置空 → 悬垂

*p = ...;           // 释放后使用：读或写一块"名义上已不归我"的内存

问题的根源在于 `free(p)` 只把内存交还分配器，**并不会把 `p` 变量清零**；C/C++ 也不追踪"还有谁指向这块内存"。于是同一块物理内存可能已被重新分配给别的对象，而旧指针还在按旧类型读写它。

初学者的可靠习惯是 `free` 之后立刻 `p = NULL;`（解引用空指针会确定性崩溃，比静默踩踏别人的数据安全得多），并在有多个别名指针时理清所有权归属。

### 12.3.2 UAF 如何被利用：重新占位与类型混淆

UAF 之所以危险，是因为攻击者常能控制"释放后那块内存被什么占据"。经典节奏是：

1. 对象 A 被释放，其内存进入空闲链表；

2. 攻击者迅速申请一个同尺寸对象 B，分配器把**同一块内存**给了 B，攻击者可控 B 的内容；

3. 程序仍用悬垂指针按 A 的类型访问这块内存，实际读写的是攻击者布置的 B 数据。

在 C++ 里最致命的是：A 若是带虚函数的对象，其内存开头是虚表指针（vtable pointer）。攻击者用 B 覆盖成伪造的虚表指针，随后程序通过悬垂指针调用 A 的虚函数，就会跳到攻击者控制的地址——控制流劫持。这类"按错误的类型解释同一块内存"也叫类型混淆（CWE-843，与 UAF 常同时出现）。

初学者记住一句话：UAF 把"时间上的错误（用得太晚）"变成"空间上的越权（读写到别人的对象）"，而其危害等级取决于释放的对象里是否藏着代码指针。

### 12.3.3 双重释放

双重释放（Double Free，CWE-415）是 UAF 的近亲：对同一指针调用两次 `free`。第二次 `free` 会把一个已在空闲链表里的块**再次**插入链表，破坏链表结构，常可被引导成"同一块内存被分配两次给两个对象"，进而任意写（与 12.2.4 的 freelist 中毒衔接）。

根因同样是"`free` 后指针未失效、所有权不清"。常见诱因是错误处理路径重复释放、或两个指针别名同一块内存各自 `free` 一次。

如 12.2.5 所述，glibc 2.29 起 tcache 用 key 字段能检测出"块已在缓存中"的重复释放并中止（报 double free detected in tcache 2），但这只覆盖部分情形（fastbin/大块路径检查不同），也可被绕过；根本修复仍是所有权清晰 + 释放即置空。

### 12.3.4 缓解方向

针对 UAF 的系统级缓解初学者需知其名（细节属大主题13）：

隔离堆 / 延迟复用（如某些分配器让释放后的内存不立即重用）、地址消毒器（AddressSanitizer，编译期插桩，把释放的内存标为"中毒"，一旦访问立即报错，是开发期抓 UAF 的利器）、以及用具备所有权/借用检查的语言（Rust）在编译期消除悬垂指针（呼应大主题13.6）。

这些手段各有代价（性能、兼容性）；ASan 主要用于测试而非生产。攻防持续演进，标随生态演进。

## 12.4 格式化字符串

### 12.4.1 漏洞成因：把用户输入当格式串

格式化字符串漏洞（CWE-134，Use of Externally-Controlled Format String）源于把**用户可控的数据**直接当作 `printf` 家族的格式串参数：

printf(user_input);        // 危险：user_input 里的 % 会被当格式指令解析

正确写法本应是：

printf("%s", user_input);  // 安全：user_input 只当数据

差别在于：`printf` 遇到 `%` 会去读取"对应的可变参数"。但如果格式串里的转换说明（如 `%x`、`%s`、`%n`）数量超过实际传入的参数，`printf` 并不知道，它会按调用约定继续到栈上/寄存器溢出区去取"本不存在的参数"，从而读到或写到不该碰的内存。

初学者的直觉锚点：`printf` 的参数个数是由**格式串**告诉它的，而非编译器核对的。一旦格式串由攻击者写，攻击者就同时掌握了"要访问几个参数、怎么解释它们"——这等于把 `printf` 变成一个受控的内存读写原语。现代编译器用 `-Wformat -Wformat-security` 能对 `printf(non_literal)` 告警。

### 12.4.2 信息泄露：%x / %s 读取内存

只用读类转换就能泄露内存。连续的 `%x` 会把栈上相邻的字（本该是参数）逐个打印出来：

printf("%x %x %x %x");   // 打印栈上四个"参数"位置的原始值

而 `%s` 更狠：它把对应参数当**指针**、解引用打印其指向的字符串，可用来读任意地址的内容（若能控制那个指针）。

这类读原语的价值在于**泄露地址**——泄露出栈上残留的返回地址、libc 函数地址或栈/堆指针，就能反推出 ASLR 随机化后的真实基址，为后续精确劫持（12.6）铺路。初学者要意识到：一个"看起来只是打印乱码"的 bug，实质是击穿地址随机化的钥匙。

### 12.4.3 %n 任意写

格式化串里最危险的转换是 `%n`：它不打印任何东西，而是把"到目前为止已经打印的字符数"**写回**到对应参数所指的 `int*` 地址：

int cnt; printf("hello%n", &cnt);   // cnt 被写成 5（"hello" 5 个字符）

如果攻击者能控制那个指针（借助 12.4.2 的参数错位），并通过在格式串前段打印足量字符来精确控制"已打印字符数"这个被写入的值，`%n` 就成了一个**任意地址写任意值**的原语（写宽度可用 `%hn`/`%hhn` 按 2/1 字节拆分、配合宽度域 `%100c` 凑数控制数值）。

有了任意写，攻击者就能改写返回地址、GOT 表项、函数指针，把控制流引向自己的代码——这就是格式化串漏洞可以直接等价于"代码执行"的原因。初学者记住 `%n` 是"读多了会泄露、能写就能提权"里最锋利的一把。因其危险，很多现代 libc 默认在写保护/只读格式串场景限制 `%n`（如某些平台需显式开启），标随实现。

### 12.4.4 直接参数访问 %n$

实战中攻击者很少数一堆 `%x`，而用 POSIX 的"直接参数访问"语法一步定位到第 k 个参数：

printf("%7$x");    // 直接取第 7 个参数位并按十六进制打印

printf("%7$n");    // 直接向第 7 个参数所指地址写入

`n$` 让攻击者稳定地选中栈上他事先布置好的目标指针，无需靠数量凑位，是格式化串利用的标准工具。初学者只需理解：这只是"精确寻址第 k 个参数"的便捷写法，不改变 12.4.2/12.4.3 的读写本质。

#### 来源与时效（本小主题末集中列）
- 一手锚点：CS155 Control Hijacking（format string 攻击，%x 泄露 / %n 写）；`printf(3)` / POSIX 规范（转换说明 `%n`、宽度、`n$` 直接参数访问语义）；CS161 Fall 2025 Memory Safety（格式串误用）。核实 2026-07-30。
- 交叉源 / 编号：MITRE CWE-134 Use of Externally-Controlled Format String。核实 2026-07-30。
- 冲突项：`%n` 的默认可用性随平台/libc 加固不同（部分平台默认禁用只读段写），标规范 vs 实现分账；CWE-134 未进 2025 Top 25，仅登记编号。

## 12.5 整数溢出

### 12.5.1 有符号回绕与无符号回绕

整数溢出（CWE-190，Integer Overflow or Wraparound）指算术结果超出该整数类型能表示的范围。C/C++ 里两种情况语义不同，务必分清：

无符号整数溢出是**定义良好**的，按模 2^n 回绕：

UINT_MAX + 1 == 0        // 32 位无符号：0xFFFFFFFF + 1 回绕到 0

有符号整数溢出是**未定义行为（UB）**，编译器可假设它不发生并据此优化，实际表现不可依赖：

INT_MAX + 1              // 有符号溢出：C 标准未定义，勿依赖任何结果

初学者最关键的认知：无符号回绕是"合法但常出乎意料"的行为（bug 的温床），有符号溢出则是"标准都不保证会发生什么"的雷区（连"回绕成负数"都不能假设，因为优化器可能把 `x+1 > x` 直接当恒真删掉检查）。两者都能被攻击者用来让程序算出一个荒谬的小/负数值。

### 12.5.2 截断与符号转换

除了加减乘溢出，两类隐式转换同样常出问题：

截断（CWE-197）：把宽类型赋给窄类型丢高位，如把 `size_t`（64 位）赋给 `int`（32 位），大长度被砍成小数甚至负数。

符号转换（CWE-195 Signed to Unsigned / 相关 CWE-196）：一个负的有符号数被当成无符号数，会变成巨大的正数，例如

int len = -1;

memcpy(dst, src, (size_t)len);   // -1 变成 SIZE_MAX，复制天文数字字节

初学者要留意：这类 bug 常出现在"边界检查"和"实际使用"用了不同符号/宽度的类型——检查时看着没超，转换后却变成越界的巨值。

### 12.5.3 整数溢出如何变成内存越界

整数溢出本身不直接改写内存，它的危害是**把一个错误的大小/下标喂给后续的分配或访问**。最经典的是分配前的乘法溢出：

n = count * size;        // count、size 用户可控，乘积回绕成一个很小的数

p = malloc(n);           // 分配了远小于预期的缓冲区

memcpy(p, src, count*size_expected);  // 按"预期大小"写入 → 堆溢出

这里 `malloc` 按回绕后的小值分配，但程序后续仍按"本该有的大值"去写，于是越界——一个整数 bug 转化成了 12.2 的堆溢出。同理，一个回绕成负/巨值的下标或长度可导致越界读写（CWE-787/CWE-125）。CWE-190 在 2024 CWE Top 25 曾上榜（第 23），2025 版已跌出 Top 25，但它作为"越界的上游成因"依然常见，排名下降不等于消失。

初学者的心智模型：整数溢出很少是终点，它是"让后面那道内存操作拿到错误尺寸"的导火索——查这类 bug 要顺着"这个大小/下标是怎么算出来的"往回追。

### 12.5.4 防御：先验证再运算

防御的要点是在做分配/访问之前**检查算术是否会溢出**，而不是事后看结果：

用编译器内建的溢出检测做乘加：

if (__builtin_mul_overflow(count, size, &n)) { /* 拒绝 */ }

优先用会自己做溢出检查的接口，如 `calloc(count, size)`（标准要求它检测 count*size 溢出并失败返回 NULL）。

统一用无符号/足够宽的类型表示大小（`size_t`），避免有符号/窄类型参与长度计算；并在编译期开 `-fsanitize=undefined`（UBSan）在测试中捕获有符号溢出与非法转换。

初学者容易写成先算 `a*b` 再判断 `if (result < a)`——对有符号类型这是 UB、对无符号也未必覆盖所有情况，正确姿势是用专门的溢出检查原语或 `calloc`，把"会不会溢出"这件事交给标准保证的机制。

#### 来源与时效（本小主题末集中列）
- 一手锚点：ISO C11/C17 标准（无符号模 2^n 回绕 §6.2.5、有符号溢出为 UB §6.5）；CS161 Fall 2025 Memory Safety（整数溢出导致越界分配）；gcc 官方文档 `__builtin_mul_overflow`、UBSan（`-fsanitize=undefined`）。核实 2026-07-30。
- 交叉源 / 编号：MITRE CWE-190 Integer Overflow or Wraparound（2024 Top 25 第 23；2025 已跌出 Top 25，页面 last-updated 2025-12-15 核对）、CWE-197 Numeric Truncation、CWE-195 Signed to Unsigned Conversion Error。核实 2026-07-30。
- 冲突项：无。规范（无符号回绕定义良好 vs 有符号 UB）与实现（编译器据 UB 优化删检查）已分账标注。

## 12.6 越界读与控制劫持原理

### 12.6.1 越界读

越界读（CWE-125，Out-of-bounds Read，2025 CWE Top 25 第 8）指读取超出对象边界的内存。它不改写数据，却会**读出本不该暴露的字节**——相邻变量、栈上残留的指针、堆里别的对象、甚至跨请求的敏感数据。

最著名的实例是 OpenSSL 的 Heartbleed（CVE-2014-0160，2014）：TLS 心跳包里请求方自报一个长度字段，服务端未校验就按该长度从缓冲区回拷并返回，攻击者报一个远超实际载荷的长度，就能读回缓冲区后面**多达约 64KB 的进程内存**，其中可能含私钥、会话票据、其他用户的明文。它是"缺一个长度检查"就能持续泄密的教科书案例。

初学者要纠正一个偏见："只读的 bug 不严重"。越界读不改控制流，但它是**信息泄露**的主力，而信息泄露往往是精确劫持不可或缺的前置步骤（见下）。

### 12.6.2 信息泄露如何击穿 ASLR

现代系统用 ASLR（地址空间布局随机化）把代码段、库、栈、堆的基址随机化，攻击者事先不知道要跳到哪个地址，劫持难度大增（详见大主题13.2）。

越界读/格式化串读（12.4.2）的价值就在这里：只要泄露出任意一个已知函数或已知栈变量的运行时地址，攻击者就能反推出对应模块的随机化基址，从而算出所有目标地址。

泄露 libc 里某函数地址 → 推出 libc 基址 → 算出 system() 等地址

这解释了为什么当代利用几乎都是"两段式"：先用一个信息泄露漏洞（越界读/格式串/UAF 读）拿到地址，再用一个内存破坏漏洞（越界写/UAF 写）做精确劫持。初学者应把"泄露地址"和"改写指针"看成攻击链上分工明确的两环。

### 12.6.3 可被劫持的代码指针

控制流劫持的本质是改写一个"程序接下来会跳过去执行"的代码指针。栈返回地址只是其中最著名的一个，实际攻击面还包括：

返回地址（saved return address，`ret` 的目标，见 12.1）

函数指针（程序里显式的 `void (*fp)()` 被改写）

C++ 虚表指针 / 虚函数表项（vtable，通过对象调用虚函数时经过它，见 12.3.2）

GOT（全局偏移表）表项（动态链接下调用外部函数会间接经过 GOT，改写它可劫持库函数调用）

longjmp 的 jmp_buf、以及某些 C 库的析构/退出回调（如 __malloc_hook 历史上、atexit 处理器）

初学者的统一视角：凡是"程序会把某个内存里的值当地址跳过去执行"的地方，那个内存位置就是控制指针，就是劫持目标。前面五个小主题（栈溢出、堆溢出、UAF、格式串写、整数溢出导致的越界写）本质都是"取得改写这些指针之一的能力"的不同途径。

### 12.6.4 劫持之后：注入代码 vs 代码复用

拿到控制指针的改写能力后，攻击者要决定"跳到哪执行"，历史上有两条路：

注入并执行自己的 shellcode（12.1.4）——要求目标内存可写又可执行，已被 NX/DEP 广泛封杀。

代码复用（code reuse）——不注入新代码，而是把返回地址/指针指向**程序里已有的合法指令片段**，如 libc 里的函数（return-to-libc）或以 `ret` 结尾的小片段"gadget"，用一串精心排列的地址把这些片段串成任意逻辑，即 ROP（Return-Oriented Programming）。因为执行的都是本就可执行的现有代码，NX 挡不住它。

ROP/CFI 与更完整的缓解体系属于大主题13，本报告只把"劫持后去哪"的分岔点讲清：注入 shellcode 是原理起点，代码复用是当代主流，二者的胜负由防御（NX/ASLR/CFI）决定。

### 12.6.5 内存安全语言的对照

以上六类漏洞几乎都根植于 C/C++ "不检查边界、不追踪所有权、整数静默回绕"的设计。换一类语言，这些问题在**语言层面**就大多不存在：

带运行时边界检查的语言（Java、Python、Go 等）对数组越界抛异常/panic 而非静默踩踏，越界读写从"可利用漏洞"降级为"确定性崩溃"。

Rust 用所有权与借用检查在**编译期**消除悬垂指针、双重释放与数据竞争（安全子集内），并对数组越界做运行时检查——从类型系统根除 UAF 一类问题（呼应大主题13.6）。

初学者要有的分寸感：内存安全语言并非消灭所有 bug（逻辑漏洞、`unsafe` 块、FFI 边界、整数逻辑错误仍在），但它把本大主题这一整类"内存破坏 → 控制流劫持"的攻击面从根上收窄，这也是当下系统软件向 Rust 等迁移的核心动因。

#### 来源与时效（本小主题末集中列）
- 一手锚点：Stanford CS155 Control Hijacking Attacks（返回地址/函数指针/vtable/GOT 劫持目标、注入 vs 代码复用）；CS161 Fall 2025 Memory Safety（越界读、信息泄露与 ASLR 绕过）；OpenSSL 官方通告 CVE-2014-0160 Heartbleed（越界读泄露内存）。核实 2026-07-30。
- 交叉源 / 编号：MITRE CWE-125 Out-of-bounds Read（2025 Top 25 第 8；last-updated 2025-12-15）、CWE-476 NULL Pointer Dereference（2025 第 13，相关空悬垂）。核实 2026-07-30。
- 前沿/演进：注入 shellcode → 代码复用（ROP）的主流迁移由 NX/DEP、ASLR、CFI 推动，具体缓解见大主题13；标随防御演进。
- 冲突项：无实质冲突。各源对"信息泄露 + 内存破坏两段式劫持"的因果结构一致。
