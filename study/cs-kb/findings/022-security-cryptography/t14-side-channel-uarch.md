## 14.1 计时侧信道

### 14.1.1 侧信道与计时侧信道是什么

侧信道（side channel）指的是：一个系统在完成其功能时，除了它正式的输入/输出（"主信道"）之外，还会无意中泄露出**与内部状态相关的物理或可观测量**——执行时间、缓存占用、功耗、电磁辐射、声音、发热等。攻击者不去破解算法本身，而是测量这些"副产物"，反推出本应保密的数据（如密钥）。计时侧信道（timing side channel）是其中最基础、最易在纯软件层触发的一类：**当一段代码的运行时间依赖于秘密数据时，能测量时间的攻击者就能推断秘密。**

对初学者最关键的一步是接受这个反直觉的事实：一个数学上"证明安全"的密码算法，实现出来仍可能被轻易攻破，因为安全证明假设攻击者只看得到输入输出，而现实中攻击者还看得到"花了多久"。经典例子是登录口令的逐字符比较——如果程序一发现某个字符不对就立刻返回，那么"正确前缀越长、返回越慢"，攻击者反复试探、按响应时间逐字符爆破，就能把指数级的猜测变成线性级。侧信道攻击的威胁模型通常比想象的宽：攻击者甚至不需要在本机，网络计时攻击（远程测 TLS/Web 服务响应时间）也已被反复证明可行。

### 14.1.2 CWE-208 可观测的时序差异（Observable Timing Discrepancy）

CWE-208 是 MITRE 通用弱点枚举中对计时侧信道这一类缺陷的标准命名，定义为：产品中两个不同操作耗时不同，且这种差异对某个行为体（攻击者）可观测，从而泄露了与产品状态有关的安全敏感信息（例如某操作成功与否）。它在 CWE 层级中的位置（CWE 4.20，核实 2026-04-30）是：

父类 CWE-203《Observable Discrepancy》（可观测差异，涵盖时间/错误消息/行为等一切可观测泄露）

子类 CWE-1254《Incorrect Comparison Logic Granularity》（比较逻辑粒度不当，即"提前退出"式比较）

可导致（Can Precede）CWE-385《Covert Timing Channel》（隐蔽计时信道）与 CWE-327《使用有缺陷/风险的密码算法》

初学者可以把 CWE 理解为"漏洞的分类学名录"：给每一类实现缺陷一个稳定编号，方便漏洞报告、扫描器、教材统一指代。CWE-208 的编号是权威且不可自造的（本报告已核对 MITRE 官方页面）；它的父/子关系透露了一个有用直觉——计时泄露只是"可观测差异"这个大家族的一员，错误消息不同、返回码不同、内存用量不同都属同族，防御思路相通：让秘密相关的分支在**所有可观测维度**上都无差别。注意区分 CWE-208（无意泄露的时序差异）与 CWE-385（攻击者刻意构造的隐蔽通道）：前者是 bug，后者可以是恶意设计，两者机理相邻但意图不同。

### 14.1.3 数据依赖分支导致的时序泄露

时序泄露最常见的来源是**秘密数据依赖的分支**（secret-dependent branch）：`if (secret_bit) { A } else { B }`，若 A、B 两条路径耗时不同，则单次执行时间就编码了 `secret_bit`。密码实现里的重灾区是"平方-乘"（square-and-multiply）快速幂：模幂 `m^d mod n`（RSA 解密/签名）逐位扫描私钥指数 `d`，遇到 1 就多做一次乘法，遇到 0 就跳过——

for each bit b of secret exponent d:

    square  (总是执行)

    if b == 1: multiply  (仅当该位为 1)

于是总耗时正比于 `d` 中 1 的个数，更精细的测量还能定位每一位。这正是 Kocher 1996 年 CRYPTO 论文《Timing Attacks on Implementations of Diffie-Hellman, RSA, DSS, and Other Systems》的核心：他证明只要能较准确地测量私钥操作耗时，就能逐步恢复 RSA/DH/DSS 的私钥，且攻击"计算上廉价、常只需已知密文"。

对初学者，抓住两点。其一，"分支耗时不同"不一定是分支体本身长短不同，也可能来自分支预测器（预测失败要清流水线，见 14.3）、或分支体触发了不同的内存访问（见 14.1.4）。其二，防御方向是"消灭秘密相关分支"：把 `if bit` 改成"无论如何都做平方和乘法，再用无分支的方式选择要不要保留乘法结果"（常时化，见 14.5）。历史上 OpenSSL 的 RSA/DSA 都因这类问题打过多个 CVE，Kocher 论文之所以是里程碑，正因为它把"计时"从理论顾虑变成了可操作的密钥恢复攻击。

### 14.1.4 数据依赖内存访问导致的时序泄露

第二类来源是**秘密数据依赖的内存访问地址**（secret-dependent memory access）：`table[secret]` 这样的查表，访问哪一项由秘密决定。它本身没有分支，但访问的地址落在缓存的哪一行是秘密相关的，而"这一行在不在缓存里"直接影响访问耗时（命中约几个周期，未命中要上百周期访存）。经典受害者是用查找表（T-table）实现的 AES：加密时按明文和轮密钥异或的结果去查 256 项的 S 盒/T 表，攻击者通过观测"哪些表项被访问过"（用 14.2 的缓存攻击）反推密钥字节。

这一点把 14.1（计时）和 14.2（缓存）连了起来：数据依赖的内存访问之所以泄露，正是因为缓存把"访问过的地址"变成了可被计时探测的状态。初学者容易以为"没有 if 就安全"——不对，`arr[secret]` 同样危险，因为地址即秘密。防御同样是常时化：要么改用不查表的实现（如 AES 的 bitsliced 或硬件 AES-NI 指令），要么"每次都把整张表都读一遍"使访问模式与秘密无关（代价高但可行）。这也是为什么现代密码库尽量避免"用秘密做数组下标"和"用秘密做分支条件"这两件事。

### 14.1.5 教学级计时差异实证

为让"数据依赖分支→可测时间差"从概念落到可见的数字，本报告在仓库外 scratchpad 用纯 Python 对比了两种 32 字节比较：朴素的"提前退出"比较（首个不匹配字节即返回，属 CWE-1254）与标准库的常时比较 `hmac.compare_digest`。对每种实现分别测"在第 0 字节就不匹配"与"前 31 字节都匹配、仅最后一字节不同"两种输入，取多轮最小值以压噪。真实输出（本机 Linux 6.18.5 / Python 3.11.15）：

naive early-exit compare:  mismatch at byte 0 = 175.4 ns/call ；mismatch at byte 31 = 902.6 ns/call

hmac.compare_digest:       mismatch at byte 0 = 49.2 ns/call ；mismatch at byte 31 = 50.2 ns/call

朴素比较在"匹配前缀更长"时明显更慢（约 5 倍），时间直接编码了"猜对了几个字节"——攻击者据此可逐字节爆破 MAC/口令；而 `compare_digest` 两种情形几乎相等（49 vs 50 ns，差异落在噪声内），时间与秘密去相关。

必须诚实说明这只是**教学级**演示，不是严谨的泄露量测量：Python 解释器开销大、单机噪声高，此处 5 倍差异之所以清晰，部分是因为循环次数放大了效果；真实攻击面对的信号往往是纳秒级且淹没在噪声中，需要大量重复采样与统计处理才能提取（这正连向 14.4 的差分分析思想）。这里的价值在于坐实定性结论"数据依赖分支的耗时可测"，以及"标准库的常时比较确实把差异抹平了"。脚本与完整输出仅在 scratchpad，不入库。

## 14.2 缓存攻击

### 14.2.1 缓存为什么会变成侧信道

CPU 缓存用来缓和"CPU 极快、主存极慢"的落差：访问已在缓存的数据（命中）只需几个周期，未命中要访主存、上百周期。缓存对程序是"透明"的（程序不显式管理它），但它是**多个进程/线程共享的有状态资源**——尤其是最后一级缓存（LLC/L3，通常全核共享）。这两点合起来就造出侧信道：攻击者通过**测量自己访问某地址的快慢**，推断"受害者刚才是否访问过该地址"，因为受害者的访问会把对应缓存行调入（或挤出）缓存，改变攻击者后续访问的耗时。

初学者要建立的核心图景是"缓存是一块被大家共用、且能被计时探测的黑板"：受害者在黑板上留下的痕迹（哪些行被载入）本应无关紧要，但攻击者能通过"我读这块黑板快不快"把痕迹读出来。缓存攻击因此比 14.1 的纯软件计时更强：它能在**同一台机器的另一个进程/虚拟机**里，探测受害者的**内存访问模式**（结合 14.1.4，访问模式往往就编码了密钥）。所有缓存攻击的通用套路都是三拍：把缓存置于已知状态 → 让受害者运行 → 测量缓存状态变化。下面两种主流手法只是"置状态"和"测变化"的方式不同。

### 14.2.2 Flush+Reload

Flush+Reload 由 Yarom 与 Falkner 在 USENIX Security 2014 提出，前提是攻击者与受害者**共享物理内存页**（常见于共享库、内存去重 KSM、写时复制）。三步：

先 Flush —— 攻击者用 `clflush` 指令把目标共享地址从整个缓存层级中逐出（保证初始为未缓存）

再 Wait —— 让受害者执行一段时间（可能会访问该地址）

后 Reload —— 攻击者重新访问该地址并计时，若很快（命中）说明受害者在等待期访问过它、把它带回了缓存；若很慢（未命中）说明受害者没碰过

它精度高、噪声低，且因为作用在共享的 LLC 上，**攻击者与受害者不必在同一核**。原论文用它从跨核运行的 GnuPG 1.4.13 中恢复了 RSA 私钥。

对初学者，Flush+Reload 的精髓是"我先擦干净这一格，跑一会儿，再看它有没有被别人填上"。它探测的是**具体某个地址**是否被访问——因此攻击者需要知道要盯哪个地址（如某个 S 盒表项、某段代码），这依赖共享内存把攻击者和受害者的虚拟地址映射到同一物理行。防御上，关掉跨租户内存去重、避免敏感代码/数据落在可被共享的页、以及从根上做常时实现（不让访问地址依赖秘密），都能削弱它。`clflush` 是关键武器，所以有些防御会限制非特权代码使用刷新指令。

### 14.2.3 Prime+Probe

Prime+Probe（缓存竞争型，早于 Flush+Reload；Percival 2005 对 RSA、Osvik/Shamir/Tromer 2006 对 AES）**不要求共享内存**，因此适用面更广（跨 VM、云多租户）。它利用组相联缓存的"同一缓存组容量有限、会互相驱逐"这一点：

先 Prime —— 攻击者访问自己构造的一组地址（"驱逐集/eviction set"），填满目标缓存组，使该组全是自己的数据

再 Wait —— 让受害者运行，若受害者访问了映射到同一组的地址，就会驱逐掉攻击者的某条数据

后 Probe —— 攻击者重新访问自己那组地址并计时，某些访问变慢（未命中）说明对应的组被受害者用过了

于是攻击者得到的是"受害者用了哪些**缓存组**"，据此（结合已知的表在缓存中的布局）反推秘密相关的访问模式。

初学者可对比记忆：Flush+Reload 探测"某个**地址**在不在缓存"（需共享内存、精度高）；Prime+Probe 探测"某个**缓存组**被不被别人挤占"（不需共享内存、粒度粗一点、噪声更大但更通用）。构造有效的驱逐集是 Prime+Probe 的工程难点，尤其现代 CPU 的 LLC 用了复杂的、非公开的切片哈希把地址映射到 slice。防御思路包括缓存分区（如 Intel CAT 把不同安全域的缓存隔开）、限制超线程共享、以及同样的根治手段——常时、无数据依赖访问。

### 14.2.4 常见变体：Evict+Reload、Flush+Flush、Prime+Abort

围绕上面两种范式衍生了一串变体，广度上应知其名与差异（细节略）：

变体 Evict+Reload —— 像 Flush+Reload 但用"访问驱逐集把目标挤出"代替 `clflush`，用于无法使用刷新指令的场景（如某些 ARM/JavaScript 环境）

变体 Flush+Flush —— 只用 `clflush` 本身的耗时（刷新一条已缓存的行比刷新未缓存的行略慢）来判断命中，攻击者自己**不做访存**，因而更隐蔽、更难被性能计数器检测

变体 Prime+Abort —— 借助 Intel TSX 事务内存的中止事件来感知缓存驱逐，免去 Probe 阶段的计时

这些变体的存在说明一件对初学者重要的事：缓存侧信道不是单一 exploit，而是一整套"如何把缓存状态变化读出来"的技术家族，攻防持续演进。它们共用同一弱点根源（共享且有状态的缓存 + 秘密相关的访问），所以根治手段也共通——本报告把统一防御放在 14.5。这些变体多为学术论文提出，具体阈值/成功率随微架构而变，此处只登记不给数值。

### 14.2.5 前提条件与防御要点

缓存攻击并非无条件成立，理解其前提有助于评估现实风险：共享 LLC（多核共享或超线程同核共享 L1/L2）、攻击者能在受害者附近运行代码（同机进程、同宿主 VM）、能较精确计时（`rdtsc` 等高精度计时器）、以及（Flush+Reload 特有的）共享内存。相应缓解分几层：

关掉跨信任域的内存去重（KSM）、避免共享敏感页——削弱 Flush+Reload

缓存分区/着色、禁用不可信负载的超线程（SMT）——削弱 Prime+Probe

降低计时器精度或粒度（浏览器曾降低 `performance.now()` 精度）——提高测量门槛

根治手段 —— 常时实现，使访问地址与分支都不依赖秘密（见 14.5）

初学者要记住："降低计时精度"只是提高门槛、不是根治，攻击者可用放大重复、并发计数线程等手段恢复精度。真正稳妥的是从软件侧消除数据依赖访问，以及在硬件/OS 侧做隔离。这也是为什么密码库（OpenSSL、BoringSSL、libsodium）在 AES 上优先用硬件 AES-NI 指令（无查表、天然抗缓存计时）而非 T-table 软实现。

#### 来源与时效
- 锚点：Yuval Yarom, Katrina Falkner《FLUSH+RELOAD: A High Resolution, Low Noise, L3 Cache Side-Channel Attack》，USENIX Security 2014，pp.719–732，https://www.usenix.org/conference/usenixsecurity14/technical-sessions/presentation/yarom （核实 2026-07-30）。
- 锚点：D. A. Osvik, A. Shamir, E. Tromer《Cache Attacks and Countermeasures: the Case of AES》(CT-RSA 2006，Prime+Probe 对 AES)；C. Percival《Cache Missing for Fun and Profit》(2005，超线程缓存计时对 RSA)。
- 锚点：Stanford CS155《Hardware and micro-architectural security》，https://cs155.stanford.edu/syllabus.html 。
- 交叉核对一致：三来源对"缓存命中/未命中的耗时差 → 探测他人访问模式"机理一致；Flush+Reload 需共享内存、Prime+Probe 不需，两者分工在多篇综述中反复确认。
- 未复现：缓存攻击仅概念讲解，本机未做 PoC（如实标注）。变体阈值/成功率随微架构而变，未给数值。

## 14.3 瞬态执行攻击

### 14.3.1 推测执行与"瞬态指令"背景

现代高性能 CPU 为跑满流水线会**乱序执行**（out-of-order）和**推测执行**（speculative execution）：遇到分支时不等条件算完就先按预测方向执行；遇到可能出错的加载也可能先执行、稍后再检查权限。当预测错误或检查发现越权，CPU 会把这些指令的**架构状态**（寄存器、内存的正式结果）回滚，仿佛什么都没发生——这些被回滚的指令叫**瞬态指令**（transient instructions）。瞬态执行攻击的核心洞察是：**架构状态被回滚了，但微架构状态（尤其是缓存）没有回滚**。于是攻击者让瞬态指令"违规读到"秘密、并用秘密去访问一个数组把某缓存行调入，回滚后再用缓存攻击（14.2）把那一行读出来，秘密就泄了。

对初学者，关键是分清两个"世界"：架构世界（ISA 规定程序员能看到的状态，CPU 保证回滚后一致）与微架构世界（缓存、预测器等实现细节，ISA 不承诺其一致）。瞬态执行攻击就是"在微架构世界里偷偷做了违规操作、把结果编码进缓存，再从微架构世界读回来"。它于 2018 年 1 月公开，震动整个行业，因为它不是某个软件 bug，而是**高性能 CPU 设计范式本身**留下的漏洞，几乎影响所有乱序/推测执行的处理器（Intel、部分 AMD、部分 ARM）。这一整个家族仍在增补，硬标 ⚙演进快·锚 2026-07-30。

### 14.3.2 Meltdown（CVE-2017-5754，熔断）

Meltdown（Lipp 等，USENIX Security 2018）打破的是**用户态与内核态的内存隔离**：正常情况下用户程序读内核地址会触发权限异常，但在乱序执行的 CPU 上，那条越权加载可能**在异常真正抛出前**就已把内核数据取到寄存器，并被后续瞬态指令拿去当索引访问一个用户态探测数组。异常最终使架构结果回滚，但探测数组对应的缓存行已被载入，攻击者用 Flush+Reload 读出即得内核字节。概念流程：

推测地读取一个越权的内核地址，得到字节 `k`（异常尚未落地）

用 `k` 作索引访问 `probe[k * 4096]`，把某缓存行调入

CPU 抛异常、回滚架构状态（`k` 从寄存器消失）

攻击者遍历 `probe[]` 计时，命中最快的那一项的下标即 `k`

主要缓解是 KPTI/KAISER（内核页表隔离）：把内核地址从用户态页表里几乎完全移除，让越权加载连"推测地读到"都做不到。

初学者可记："Meltdown = 抢在权限检查生效前把内核内存偷读出来"。它之所以特别危险，是因为一个普通用户进程无需任何漏洞就能转储整个内核内存（含其他进程数据）。好消息是它相对容易缓解（KPTI），代价是系统调用变慢；且它主要影响特定 Intel（及少数其他）微架构。本机内核对 meltdown 报告 "Not affected"（见 14.3.6），说明所测 CPU 微码/型号不受此变体影响。

### 14.3.3 Spectre 变体 1：边界检查绕过（CVE-2017-5753）

Spectre（Kocher 等，IEEE S&P 2019）打破的是**同一地址空间内的软件隔离**（如沙箱、同进程内不同信任域），它不依赖越权异常，而是诱骗 CPU 的**分支预测器**。变体 1（Bounds Check Bypass）针对这样的常见代码：

if (x < array1_size) { y = array2[array1[x] * 4096]; }

攻击者先用合法的小 `x` 反复训练分支预测器"这个 if 通常为真"，再传入一个越界的大 `x`；此时 CPU 推测性地跳过边界检查、用越界的 `array1[x]`（可能是任意秘密）去索引 `array2`，把秘密相关的缓存行调入。边界检查随后算完、发现应为假、回滚架构结果，但缓存痕迹留下，Flush+Reload 读出秘密。

对初学者，Spectre v1 的要害是"**受害者自己的合法代码**在被诱导后替攻击者干了坏事"——攻击者只是训练了预测器并喂了越界输入。因此它极难根治：编译器插入 `lfence`（推测屏障）强制边界检查先完成，或用掩码把 `x` 钳制在合法范围（`x &= (size-1)`），但要逐处识别易受攻击的代码模式。本机对 spectre_v1 报告 "Mitigation: usercopy/swapgs barriers and __user pointer sanitization"（见 14.3.6），即内核在关键处做了指针净化与屏障。

### 14.3.4 Spectre 变体 2：分支目标注入（CVE-2017-5715）

变体 2（Branch Target Injection）更狠：攻击者训练**间接分支预测器**（负责预测 `jmp *reg`、函数指针、返回等跳到哪），把它"投毒"到攻击者选定的地址，诱导受害者在推测窗口内跳到一段"泄露小工具（gadget）"去执行，把秘密编码进缓存。它相当于把 Spectre 的"诱导受害者代码"升级成"诱导受害者跳到任意 gadget"，威力接近推测版的 ROP。缓解手段两条主线：

软件侧 retpoline —— 把间接跳转改写成一段用 `ret` 构造的"蹦床"，让推测走进一个无害的死循环而非攻击者目标

硬件+微码侧 IBRS/eIBRS/IBPB —— 间接分支限制推测、分支预测器屏障，隔离不同特权级/上下文的预测器状态

本机对 spectre_v2 报告 "Mitigation: Enhanced / Automatic IBRS; IBPB: conditional; PBRSB-eIBRS: SW sequence; BHI: Vulnerable"，即启用了 eIBRS 等硬件缓解，但对 BHI（Branch History Injection，v2 的后续变体）仍标 Vulnerable——这正是"⚙演进快"的现实注脚：老变体缓解了，新变体又冒出来。

### 14.3.5 后续变体谱系（广度登记）

Spectre/Meltdown 之后，瞬态执行攻击扩成一个大家族，广度上应知其名（细节与阈值随微架构变，此处只登记不作结论）：

Spectre-v4 / Speculative Store Bypass（SSB，CVE-2018-3639）—— 推测性地绕过"存储-加载依赖"读到旧值

Foreshadow / L1TF（L1 Terminal Fault，2018）—— 从 L1 缓存推测泄露，可击穿 SGX enclave 与虚拟机隔离

MDS 家族（RIDL/Fallout/ZombieLoad，2019）—— 从行填充缓冲、存储缓冲等微架构缓冲区采样他人数据

TAA（TSX Async Abort）、SRBDS、MMIO Stale Data、GDS（Gather Data Sampling，2023）—— 陆续发现的采样类变体

Retbleed（2022，CVE-2022-29900/29901）—— 绕过 retpoline，用 `ret` 指令做分支目标注入

BHI（Branch History Injection，2022，CVE-2022-0001）—— 绕过 eIBRS 的 v2 后续变体

初学者不必记全，只需把握两点：其一，这些变体各自利用不同的微架构结构（不同缓冲区、不同预测器、不同推测源），但套路一致——瞬态窗口内违规取数 + 用缓存/缓冲把结果编码出来；其二，缓解与攻击是持续拉锯，每个缓解常带性能损失，且新变体不断出现。因此 Linux 内核用 `/sys/devices/system/cpu/vulnerabilities/` 逐项报告每台机器对每个变体的状态，运维需据此评估——下一节读的就是本机的真实状态。

### 14.3.6 本机缓解状态实证

在本机（Intel Xeon @2.10GHz，Linux 6.18.5，4 vCPU）读取 `/sys/devices/system/cpu/vulnerabilities/` 得到各变体的真实内核报告（核实 2026-07-30，逐条 `cat`）：

meltdown = Not affected

spectre_v1 = Mitigation: usercopy/swapgs barriers and __user pointer sanitization

spectre_v2 = Mitigation: Enhanced / Automatic IBRS; IBPB: conditional; PBRSB-eIBRS: SW sequence; BHI: Vulnerable

spec_store_bypass = Mitigation: Speculative Store Bypass disabled via prctl

l1tf / mds / tsx_async_abort / srbds / mmio_stale_data / retbleed / gather_data_sampling / spec_rstack_overflow = Not affected

这条实证坐实了两件事：其一，缓解不是"全有或全无"，而是每个变体一条状态——有的靠硬件/微码天然"Not affected"，有的靠内核软件缓解（如 spectre_v1 的指针净化），有的可按需开关（SSB 通过 `prctl` 由进程选择）。其二，spectre_v2 行末的 "BHI: Vulnerable" 直观展示了"老洞补上、新变体仍开"的动态，正是本节硬标 ⚙演进快 的理由。

初学者可把这个目录当成"本机微架构漏洞体检表"：每个文件名是一个变体，内容要么 "Not affected"（该 CPU/微码不受影响），要么 "Mitigation: …"（已缓解及方式），要么 "Vulnerable"（暴露）。它是评估一台机器实际风险最直接的一手信号，比"这颗 CPU 理论上受不受影响"更可靠，因为它综合了 CPU 型号、微码版本、内核缓解开关的实际组合。注意此状态随内核版本、微码更新、启动参数（如 `mitigations=off`）而变，故必须锚版本与日期。

#### 来源与时效
- 锚点：M. Lipp 等《Meltdown: Reading Kernel Memory from User Space》，USENIX Security 2018（CVE-2017-5754）；官方站 https://meltdownattack.com/ 。
- 锚点：P. Kocher 等《Spectre Attacks: Exploiting Speculative Execution》，IEEE S&P 2019（v1 = CVE-2017-5753，v2 = CVE-2017-5715）；官方站 https://spectreattack.com/ 。
- 锚点：Linux 内核文档 `Documentation/admin-guide/hw-vuln/`（`/sys/.../vulnerabilities/` 各文件语义）；Intel/ARM 官方 Spectre/Meltdown 白皮书（CVE 编号与缓解 IBRS/retpoline 对齐）。
- 本机实证：`cat /sys/devices/system/cpu/vulnerabilities/*`，Linux 6.18.5 / Intel Xeon @2.10GHz，输出如上（核实 2026-07-30）。
- ⚙演进快·锚 2026-07-30：瞬态执行变体谱系持续增补（v4/L1TF/MDS/Retbleed/BHI/GDS…），缓解与新变体拉锯；本机 spectre_v2 "BHI: Vulnerable" 即例证。CVE 编号已核对官方站，未编造；变体成功率/阈值随微架构变，未给数值。
- 未复现：瞬态执行攻击仅概念讲解，未做 PoC（如实标注）。

## 14.4 功耗/电磁侧信道

### 14.4.1 物理侧信道概述

前三节的侧信道都能纯软件远程或同机触发；本节的**物理侧信道**则需攻击者能物理接近设备、测量其物理量：功耗（power）、电磁辐射（EM）、执行声音（acoustic）、发热等。原理同源——CMOS 电路的瞬时功耗依赖它此刻在算什么、翻转了哪些位，而这些又依赖被处理的数据（含密钥）。这类攻击主要威胁**嵌入式与智能卡**场景：智能卡、硬件钱包、TPM、IoT 芯片，攻击者拿到设备、接上示波器/探头即可测量。

对初学者，先建立"电路会说话"的直觉：一个门电路把 0 翻成 1 时要给电容充电、瞬间多耗电，翻转的位越多、耗电尖峰越大。所以一次加密运算的功耗曲线（power trace）其实是一段"运算过程的心电图"，里面藏着中间值和密钥的信息。物理侧信道的经典文献起点是 Kocher、Jaffe、Jun 于 CRYPTO'99 的《Differential Power Analysis》，它把功耗分析系统化为 SPA 与 DPA 两级（下两节）。这类攻击对纯软件系统（如云服务器）通常不适用（拿不到物理探头），但对任何"密钥装在攻击者手里的物理设备"里的场景是头号威胁。

### 14.4.2 简单功耗分析（SPA）

SPA（Simple Power Analysis）直接从**单条或少数几条**功耗曲线肉眼/直接读出秘密相关的操作序列。它奏效的前提是不同操作有肉眼可辨的功耗特征。最经典的例子仍是模幂的"平方-乘"（同 14.1.3）：在功耗曲线上，一次"平方"和一次"平方+乘"的形状/时长不同，于是曲线上的模式序列直接拼出指数的比特串——

曲线上看到 [方] 段 → 该位是 0

曲线上看到 [方][乘] 段 → 该位是 1

把整条曲线的模式读下来，私钥指数就出来了。

初学者可把 SPA 理解为"看波形认操作"：它不需要统计、不需要很多条曲线，只要操作序列本身泄露秘密就成立。因此 SPA 的防御是"让操作序列与秘密无关"——例如"总是做平方且总是做乘法"的常时模幂（如 Montgomery ladder），使曲线上每一位都长得一样。SPA 与 14.1 的计时攻击是近亲：计时看"总时长"，SPA 看"功耗波形里的操作序列"，两者都因秘密相关分支而泄露，防御也都是常时化。

### 14.4.3 差分功耗分析（DPA）

DPA（Differential Power Analysis）比 SPA 强得多：即使单条曲线看不出任何东西（信号淹没在噪声里），只要采集**大量**曲线并做统计，也能提取密钥。思路是"分而治之 + 假设检验"：攻击者对密钥的**一小块**（如 AES 的一个字节，256 种可能）逐一假设，用该假设和已知明文预测某个中间值的某一比特，据此把成千上万条曲线**分成两组**（预测该比特为 0 / 为 1），再比较两组功耗的**均值差**——

对每个密钥字节假设 k（0..255）：

    用 k 和已知明文预测中间比特 b

    按预测 b=0 / b=1 把所有 trace 分两堆

    算两堆功耗均值之差 Δ(k)

    正确的 k 会在 b 真正影响功耗的时刻出现显著尖峰

峰值最大的那个假设即正确密钥字节。逐字节做完，整把密钥恢复。

对初学者，DPA 的威力来自统计：单条曲线里密钥对功耗的影响是极微弱的信号 + 大量噪声，但把上万条曲线按"正确假设"分组求均值，真信号会累加、随机噪声会相互抵消，于是正确假设处冒出可辨的尖峰、错误假设处一片平坦。这正是 14.1.5 末尾提到的"重复采样 + 统计提取"的完整版。DPA（及其改进 CPA，相关功耗分析）是硬件密码模块认证（如 FIPS 140-3、Common Criteria）必须防御的核心威胁，防御见 14.4.5 与 14.5.3。

### 14.4.4 电磁与其他物理信道

功耗之外，同一"数据依赖的物理量"思想还延伸出多条物理信道，广度上应知其名：电磁辐射分析（EMA，用近场探头测芯片辐射，可局部化到某个电路区域、且无需接入电源线，常比功耗更精细）、声学攻击（测 CPU/电容发出的高频声，曾被用于远程提取 RSA 密钥）、光子/温度信道，以及**故障注入**（fault injection，用电压毛刺、时钟毛刺、激光诱导计算出错，属主动物理攻击，与被动的侧信道相邻但不同）。

初学者只需把握：这些都是"物理世界里数据依赖的可观测量"，机理与功耗分析同族，SPA/DPA 的分析框架大多可平移（如 EM 上做 DEMA）。它们的共同前提是物理接近，因此威胁集中在离线的、落入攻击者手中的设备。故障注入要单独记一笔，因为它是"主动改变计算"而非"被动观测"，防御手段（冗余计算、校验）也不同，但常与侧信道联合使用。此处只登记，不展开数值。

### 14.4.5 物理侧信道的防御方向

物理侧信道的防御分两大类，思想是"让功耗/辐射与秘密去相关"：

一是隐藏（hiding）—— 降低信噪比，加噪声、随机化功耗（随机插入哑操作/乱序执行）、用功耗平衡的逻辑（如双轨预充电逻辑，使翻转 0→1 与 1→0 功耗相同）、加屏蔽层

二是掩码（masking）—— 从算法层把每个中间值随机拆成若干"份额"（share），使任何单个可观测量都与真实秘密独立，攻击者要同时测多个点才可能复原（提高 DPA 阶数门槛），详见 14.5.3

三是常时化操作序列 —— 消灭 SPA 可见的秘密相关分支（如 Montgomery ladder 模幂）

初学者要理解一个重要区别：隐藏是"把信号埋进噪声"（提高攻击成本，但攻击者多采样仍可能突破），掩码是"从数学上让单点观测与秘密无关"（更根本，但实现难、有开销、且实现不当会因物理耦合而失效）。实践中高安全硬件（智能卡、安全芯片）往往多管齐下并接受严格的侧信道测评认证。这也是本报告把"掩码/盲化"统一放到 14.5 的原因——它们既防物理侧信道，也防微架构侧信道，是跨类的通用武器。

- 锚点：P. Kocher, J. Jaffe, B. Jun《Differential Power Analysis》，CRYPTO'99，LNCS 1666，pp.388–397（DOI 10.1007/3-540-48405-1_25）——SPA/DPA 的奠基文献。
- 锚点：Stanford CS155《Hardware and micro-architectural security》（物理侧信道概述）；FIPS 140-3 / Common Criteria 对侧信道防御的合规要求（硬件密码模块场景）。
- 交叉核对一致：Kocher 等原论文对 SPA（看单条曲线读操作序列）与 DPA（多曲线统计分组求均值差）的两级划分，与后续教材/综述表述一致。
- 未复现：物理侧信道需示波器/探头，本机无法复现（如实标注）；EMA/声学/故障注入仅登记，未给数值。

## 14.5 常时实现与防御

### 14.5.1 常时编程的三条铁律

常时（constant-time）实现是抵御 14.1–14.2（及部分 14.4 的 SPA）的软件根治手段，核心目标是让程序的**可观测行为（时间、访存地址、指令选择）与秘密数据无关**。落到代码上是三条铁律：

不用秘密做分支条件（no secret-dependent branches）——否则时间/功耗泄露走的哪条路

不用秘密做内存访问地址/数组下标（no secret-dependent memory access）——否则缓存状态泄露访问了哪里

不用秘密做变长指令的操作数（no secret-dependent variable-latency ops）——某些指令（早期的整数除法、乘法、浮点）耗时依赖操作数值

对初学者，前两条正对应 14.1.3（分支）和 14.1.4（访存）两类泄露源，第三条是补充：即使没有显式分支，个别 CPU 指令本身就"看数据快慢"。判断一段密码代码是否常时，就逐行问这三个问题。要警惕的是这些泄露常藏在"无辜"的高层代码里——一个 `if (key[i])`、一个 `table[secret_nibble]`、一个 `if (a == b) return`——都可能是漏洞。因此密码库要么手写常时代码、要么用经过审计的常时原语，绝不依赖"编译器/CPU 应该会优化好"。

### 14.5.2 常时选择与常时比较

替代秘密相关分支的标准手法是**无分支的常时选择**：用位运算构造一个全 0 或全 1 的掩码，再用掩码做条件选择，两条"路径"都执行、只是结果被掩码挑选。常时选择（在条件 c 为真时取 a，否则取 b）：

mask = 0 - c            // c 为 1 得全 1（0xFFFF…），c 为 0 得全 0

result = (a & mask) | (b & ~mask)

常时比较（判断两段秘密是否相等，替代提前退出的 CWE-1254）——不提前返回，把所有字节的差异**累积**后一次判断：

diff = 0

for i in range(len(a)):

    diff |= a[i] ^ b[i]      // 有任何一字节不同，diff 就非 0

return diff == 0             // 无论在哪不同，都走完全程再判

这正是 14.1.5 里 `hmac.compare_digest` 做的事，其两种输入耗时相等（49 vs 50 ns）即因走完全程、无早退。

初学者要掌握的直觉是"用算术/位运算把 if 消掉"：与其"如果条件成立就做 A"，不如"A 和 B 都算，再用无分支的掩码选一个留下"。这看似浪费（两条都算），但换来的是时间与秘密无关。写常时代码有个大坑：**编译器可能把你的无分支代码又优化回带分支的**（比如把 `|` 累积识别成"提前退出"），所以关键常时原语常需用内联汇编、`volatile`、或专门屏障保护，并用工具（见 14.5.5）验证编译产物确实常时。切勿用 `==`、`memcmp`、`if` 直接比较 MAC/口令哈希/密钥。

### 14.5.3 掩码（masking）

掩码是抵御 DPA（14.4.3）等统计型侧信道的核心算法级防御：把每个秘密中间值 `s` 随机拆成若干**份额（share）**，运算全程只在份额上进行，任何单个份额（以及它引起的单点功耗/时序）都与真实秘密**统计独立**。最简单的一阶布尔掩码：

取随机数 r

把秘密 s 拆成两份份额 (s ⊕ r, r)

之后所有运算在这两份上分别/联合进行，绝不显式重构 s

攻击者只测到一个点时看到的是 `s⊕r` 或 `r`，因 r 随机而与 s 无关；要复原 s 必须**同时**获取两份的信息（二阶攻击），门槛陡增。

初学者可类比"秘密分享"：把一句秘密拆成两张纸条，各自看任一张都是乱码，合起来才有意义；掩码就是让电路在整个运算里只处理"纸条"，不处理原文。掩码的阶数 d（拆成 d+1 份）越高、攻击所需曲线数越呈指数增长，但实现开销和随机数消耗也随之上升，且**实现不当会失效**：若两份份额在硬件里物理耦合（glitch、寄存器复用）而同时泄露，掩码就被击穿——这是硬件掩码工程的主要难点，需要专门的门级验证。掩码与常时化正交：常时化管"时间/访存不泄露"，掩码管"即便功耗泄露也与秘密去相关"。

### 14.5.4 盲化（blinding）

盲化是掩码思想在**公钥运算**上的具体应用：在做秘密相关运算前，用随机数把输入/密钥随机化，运算后再去除随机化，使每次运算的中间值都不同、与固定秘密去相关，从而挫败依赖"多次运算复用同一秘密"的计时/DPA 攻击。RSA 的经典盲化（防对私钥指数的计时/功耗攻击，解密密文 c）：

取随机 r，计算 c' = c · r^e mod n     // e 是公钥指数

对盲化后的 c' 做私钥运算，得 m' = (c')^d mod n

再去盲还原 m = m' · r^(-1) mod n       // 因 (r^e)^d = r，故 r 被约掉

这样每次解密实际处理的底数都被随机的 r 打乱，攻击者无法跨多次运算累积同一秘密的信息。

对初学者，盲化的精髓是"每次都换一层随机外衣，算完再脱掉"：数学上结果不变（`r` 被精心构造成能约掉），但攻击者观测到的每次运算都作用在不同的、随机的数据上，统计攻击失去可累积的固定目标。常见还有**指数盲化**（把私钥 d 改成 d + k·φ(n)，模 φ(n) 同余不改结果但改变位模式）和 ECDSA 的**标量盲化 / nonce 随机化**。盲化专治"秘密固定、可多次触发运算"的场景（正是 Kocher 1996 计时攻击和 DPA 的前提），是 RSA/ECC 库的标准防御；它与常时模幂（14.4.2）常配合使用。

### 14.5.5 编译陷阱与验证工具

常时/掩码实现最反直觉的一点：**写对了不等于编译对了**。优化编译器可能把无分支的常时代码"优化"回带秘密分支的形式（如把掩码选择识别成条件跳转、把累积比较改成提前退出），或引入秘密相关的 `cmov`→分支降级。因此常时保证必须在**最终机器码**上验证，常用手段/工具（广度登记）：

用 `volatile`、编译屏障、或内联汇编（如 `cmov`）固定关键选择，阻止编译器还原分支

工具 dudect 做黑盒统计检测——对固定输入与随机输入测大量时间样本，做统计检验判断是否常时

ct-verif / ctgrind（基于 Valgrind，把秘密标为"未初始化"追踪其是否影响分支/地址）等静态/动态分析

优先用硬件指令消除查表分支，如 AES 用 AES-NI、通用平台用 bitslicing

初学者要记住的结论是：常时安全是"实现 + 编译 + 验证"三环的整体属性，任一环失守都前功尽弃，所以密码工程强调"不要自己造常时轮子，用经审计的库（libsodium、BoringSSL 等）并保留其验证流程"。这也呼应全报告的主线——侧信道防御不是加一层就完事，而是要在软件语义、编译产物、微架构行为、乃至物理层逐层保证"可观测行为与秘密无关"。
