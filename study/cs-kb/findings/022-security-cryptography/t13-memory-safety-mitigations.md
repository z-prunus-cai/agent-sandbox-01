**内存安全缓解不是"堵住漏洞"，而是层层抬高利用门槛的纵深防御**。C/C++ 的内存漏洞（G11-12）短期消灭不完，于是防御方在编译器、操作系统、CPU、语言四个层次各设一道关卡——每一道都能被绕过，但叠在一起让"从一个溢出到拿到 shell"的代价越来越高。理解本主题的关键是记住每道防御针对的是攻击链的哪一环，以及它被绕过的典型手法，这样才明白为什么现代系统要"全都开"。

## 13.1 栈金丝雀（canary）

### 13.1.1 canary 是什么、怎么检测返回地址破坏

栈金丝雀（stack canary，又称 stack cookie）是编译器在每个函数的栈帧里、局部缓冲区与保存的返回地址之间插入的一个随机哨兵值。函数进入时把这个值写到栈上，函数返回前再检查它是否被改动；由于连续的栈缓冲区溢出要覆盖返回地址就必须先"踩过"canary，一旦 canary 变了就说明返回地址很可能已被破坏，程序立即中止（在 Linux/glibc 上调用 `__stack_chk_fail` 打印 `*** stack smashing detected ***` 并 abort）。

栈帧从低地址到高地址的关键排布是

```
[ 局部缓冲区 buf ] [ canary ] [ 保存的 rbp ] [ 返回地址 ret ]
```

一次典型的 `strcpy(buf, attacker_input)` 向高地址溢出，要覆盖 `ret` 就必然先覆盖 `canary`。

名字取自"矿井里的金丝雀"——毒气来临时金丝雀先死，矿工据此逃生；这里 canary 先"死"（被改写），程序据此在跳转到被污染的返回地址之前先崩溃。要抓住它的定位：canary 是一道**检测**机制而非**阻止**机制，它不阻止溢出发生，只在"坏事将要生效的那一刻"（函数返回前）拦一道，把"控制流劫持"降级为"程序崩溃/拒绝服务"。它也只保护栈上"缓冲区之后、返回地址之前"这一段的连续溢出，对堆溢出、越界读、格式化字符串、非连续的任意地址写一概无能为力。

### 13.1.2 canary 的三种取值：终止符、随机、随机异或

历史上 canary 有三类取值，防御强度递增。终止符 canary（terminator canary）取字符串终止字符的组合（如 NULL、CR、LF、0xFF），思路是让依赖这些字符停止的字符串函数（`strcpy`/`gets`）无法把 canary 原样写过去。随机 canary（random canary）在进程启动时由内核提供的随机源（Linux 上是 auxiliary vector 的 `AT_RANDOM`）生成一个不可预测的值；glibc 通常把最低字节设为 `0x00`，既保留一个字符串终止符防泄露、又让高位保持随机。随机异或 canary（random XOR canary / terminator-and-random）再把随机值与栈帧的控制数据（如保存的 rbp 或返回地址）异或，使得攻击者即便想同时改 canary 和返回地址也难以让校验通过。

终止符防的是"字符串函数照抄"，随机防的是"直接猜值"，异或防的是"连返回地址一起改还想蒙混过关"。现代 Linux/glibc 的实现属于"随机值 + 最低字节置 0"这一路——最低字节的 0（NULL）是一个字符串终止符，也解释了一个初学者常见现象：用 `%s` 泄露栈内容时 canary 往往被那个 NULL 字节截断而"看起来"以 00 开头。整个进程内所有线程共享同一个主 canary（存放在线程控制块 TLS 里，x86-64 上经 `%fs:0x28` 访问），这一点在 13.1.4 的绕过里很关键。

### 13.1.3 GCC/Clang 如何决定给哪些函数插 canary

canary 不是所有函数都插，而是由编译选项按启发式决定，覆盖面与性能开销折中。`-fstack-protector` 只给"含大于阈值的字符数组"的函数插桩，GCC/Clang 的默认阈值是 **8 字节**（由 `--param ssp-buffer-size` 控制）。`-fstack-protector-strong` 放宽到更多情形：函数含任意大小/类型的局部数组、取了局部变量地址、或使用 register-local 变量时都插桩，是覆盖面与开销的较好折中，也是当代主流发行版（含 Ubuntu）的默认。`-fstack-protector-all` 给所有函数插桩（开销最大），`-fno-stack-protector` 关闭。

对初学者，关键是理解"为什么不是全开"：每个被保护的函数在入口/出口都多几条读写与比较指令，全开会拖慢热点函数，所以编译器只给"看起来可能被栈溢出踩到"的函数（有本地数组的）加保护。这也留下一个盲点——如果一个可溢出的缓冲区不是数组形态、或函数没触发启发式，就可能没有 canary。本机可用

```
gcc -fstack-protector-strong prog.c -o prog   # 开
gcc -fno-stack-protector      prog.c -o prog   # 关
```

编译两版，再用 `checksec --file=prog`（或 readelf 看是否引用 `__stack_chk_fail`）对照观察保护位（教学级、仓库外）。

### 13.1.4 canary 的绕过

canary 不是终点，常见绕过有四类。信息泄露（leak）：先用一个独立的越界读/格式化字符串漏洞把 canary 的值读出来，再在溢出 payload 里把正确的 canary 原样写回去，校验就通过了——这是最主流的绕过，也解释了为什么 canary 必须与 ASLR、防信息泄露配合。逐字节爆破（byte-by-byte brute force）：在 fork 型服务器里，子进程从父进程继承**同一个** canary 且崩溃不改变它，攻击者可以一次猜一个字节、根据"崩溃/不崩溃"判断对错，把 8 字节的暴力从 2^64 降到约 256×8 次尝试。绕过而非破坏：如果漏洞是任意地址写（write-what-where）、堆溢出、或覆盖的是函数指针/C++ 虚表而非返回地址，根本不经过 canary。覆盖异常处理相关结构（如 Windows 上的 SEH、或 `__stack_chk_fail` 之前就能触发的路径）也可绕过检测时机。

初学者要从这些绕过里读出一个通用规律：**单一缓解几乎总能被"另一个漏洞"或"信息泄露"打穿**，所以 canary 从来不是单独部署，而是和 ASLR（让泄露更难、让爆破无从复用）、NX（让即便劫持也难执行注入代码）一起构成纵深。fork-server 爆破这一条尤其反直觉——"随机 + 保密"的前提是攻击者不能反复试错且崩溃会重置秘密，而 fork 子进程恰好破坏了这个前提。

## 13.2 ASLR：地址空间布局随机化

### 13.2.1 ASLR 是什么、随机化了哪些区域

ASLR（Address Space Layout Randomization，地址空间布局随机化）在每次程序加载时随机化各内存区域的基址，使攻击者无法预先知道栈、堆、共享库、以及（配合 PIE 时）可执行文件本身的绝对地址。它针对的攻击链是"攻击者需要一个确定的地址去跳转/返回"——注入 shellcode 要知道 shellcode 在哪、ROP 要知道 gadget 在哪、覆盖返回地址要填一个有效目标；ASLR 把这些地址变成每次运行都不同的随机值，攻击者只能猜。

Linux 上随机化的典型区域包括栈基址、mmap 区域基址（共享库/`mmap` 分配落在这里）、堆（brk）基址，以及主可执行文件的加载基址——但**最后一项只有把程序编译成 PIE（Position Independent Executable，位置无关可执行文件）时才随机化**；非 PIE 的可执行文件总是加载到固定地址（历史上如 0x400000），其代码段完全可预测。

要点是把 ASLR 理解成"给攻击者的地址知识加噪声"，而不是"消灭漏洞"。它和 NX 是天然搭档：NX 逼攻击者放弃注入代码、改用已有代码（ROP，见 13.3/13.4），而 ROP 需要知道那些代码的地址——ASLR 正好把这些地址藏起来。初学者常忽略的一点是 PIE 的必要性：只开 ASLR 但程序非 PIE，攻击者仍可从固定地址的主程序里找 gadget，所以现代发行版把"编译为 PIE + 开 ASLR"绑定使用。

### 13.2.2 熵：随机化到底有多少位

ASLR 的强度用熵（entropy，随机位数）衡量——熵越高，攻击者盲猜命中的概率越低，猜测期望次数约为

```
E[尝试次数] ≈ 2^(熵位数 - 1)
```

32 位系统上可随机化的地址空间小，熵通常只有约 8–16 位，意味着几万次尝试内就可能猜中，历史上被 fork-server 爆破打穿。64 位系统地址空间大得多，熵显著更高：Linux 上 mmap 区域的随机位数由 sysctl `vm.mmap_rnd_bits` 控制，x86-64 的最大值为 **32 位**（发行版默认常为 28 位），栈随机化另有若干位（受 `STACK_RND_MASK` 约束，x86-64 约 22 位掩码、按页对齐后有效熵略低）。

初学者要建立的直觉是"位数每多 1，攻击者期望工作量翻倍"：8 位约 128 次期望尝试（几乎无防护），28–32 位则是上亿次量级——对"崩溃即失败、且每次崩溃地址重掷"的场景足够安全。但两个前提破坏它：其一是 32 位地址空间根本没有足够熵（这也是"迁移到 64 位"本身即安全收益的原因之一）；其二是任何**信息泄露**都能一次性抹掉全部熵——因为同一进程内各区域是整体偏移，泄露任一库函数的运行时地址，减去它的已知偏移就得到库基址，全部 gadget 地址随之确定（见 13.2.3）。这里给出的具体位数属"内核版本相关、⚙演进快"，本报告标锚 2026-07-30，未在基线本机逐项 readelf/`/proc` 核对处如实留待核。

### 13.2.3 ASLR 的绕过：信息泄露与其他

ASLR 的头号克星是信息泄露（information disclosure）。攻击者利用一个格式化字符串、越界读、或未初始化内存漏洞，读出某个位于随机化区域的运行时指针（如栈上保存的某库函数返回地址，或 GOT 表项），再减去该符号在库内的固定偏移，即可算出整个库/区域的基址；由于区域内部布局固定、只是整体被随机平移，一个泄露就解开全部地址。其余绕过包括：熵不足时的暴力猜测（尤其 32 位或 fork-server 场景，配合 13.1.4 的爆破）；部分覆盖（partial overwrite）——只改写地址的低字节，因页内低位常不被随机化，可在小范围内可靠地重定向；以及针对非 PIE 主程序的"从固定代码段取 gadget"。

把这几条连起来看，ASLR 的安全模型有一个脆弱假设："攻击者对地址一无所知"。现实里内存安全漏洞往往同时提供"读"和"写"两种能力，读能力就足以打掉 ASLR。这解释了为什么单靠 ASLR 不够，也解释了业界为什么持续投入"防信息泄露"（如指针加密、更细的隔离）与"控制流完整性"（13.4，即便地址泄露也限制能跳去哪）。一个常被初学者忽视的细节是 ASLR 的粒度：它随机化的是**区域基址**，不是区域内每个对象——所以库内两个函数的相对距离恒定，这正是"一次泄露、全盘皆知"的根源。

## 13.3 DEP/NX 与 W^X

### 13.3.1 不可执行数据页：DEP/NX 是什么

DEP（Data Execution Prevention，数据执行保护，Windows 术语）/ NX（No-eXecute，硬件的"不可执行"页标志，AMD 称 NX bit、Intel 称 XD bit）把内存页标记为"可写但不可执行"，使 CPU 拒绝从数据区域（栈、堆、全局数据段）取指执行。它直接封杀最经典的攻击——把 shellcode 注入到栈缓冲区、再让返回地址跳到栈上执行；有了 NX，CPU 在从栈取指的那一刻就触发异常（段错误），注入的字节即便被跳转到也跑不起来。

硬件基础是页表项里的一个 NX 位；在 x86-64 长模式下由页表项的最高位（bit 63）标记不可执行，需 CPU 与操作系统协同开启。相对地，historically 32 位 x86 没有独立 NX 位，只能靠段限制粗略模拟，所以 NX 的普及也与 64 位化同步。

要抓住定位：NX 针对的是"注入的数据被当作代码执行"这一步，把它彻底切断。但它不阻止溢出、不阻止控制流被劫持——攻击者仍能改写返回地址，只是不能再跳到自己注入的字节去执行。这个"堵死注入、逼出复用"的结果，正是下一步 return-to-libc / ROP 攻击（13.3.3、13.4）诞生的直接动因。

### 13.3.2 W^X 原则

W^X（Write XOR eXecute，"可写"与"可执行"互斥）是 NX 背后的通用安全原则：任一内存页在任一时刻要么可写、要么可执行，绝不同时（异或语义）。代码页应为"可执行、只读"，数据页应为"可写、不可执行"；这样既防止把数据当代码跑（NX 方向），也防止攻击者篡改已有代码（写方向）。OpenBSD 最早系统性推行 W^X，如今是主流 OS 的默认内存策略。

```
W ^ X == true   ⇔   一个页不可能既 W 又 X
```

初学者需要注意 W^X 与"合法的运行时代码生成"之间的张力：JIT 编译器（JavaScript 引擎、JVM）本质上要"生成新代码并执行"，天然违反 W^X。合规做法是分两步——先把生成的机器码写入一个可写页（W，不可执行），再用 `mprotect` 把该页切换为可执行只读（X，去掉写权限），全程不让同一页同时 W 且 X。这也留下一个被利用点：如果程序里存在能调用 `mprotect`/`VirtualProtect` 把数据页改成可执行的路径，ROP 链就能"先解开 W^X、再执行注入代码"，这是 NX 的一种绕过思路（见 13.3.3）。

### 13.3.3 NX 导向代码复用攻击

NX 封死了"注入并执行自己的代码"，攻击者的自然应对是**代码复用**（code reuse）——不注入新代码，转而拼接程序里**已有的、本就可执行的**代码片段。最早的形态是 return-to-libc（ret2libc）：把返回地址改成 libc 里 `system` 函数的地址，并在栈上摆好参数（如指向字符串 `"/bin/sh"` 的指针），函数返回时就"返回进" `system("/bin/sh")`，全程只执行合法的 libc 代码，NX 完全不触发。

由此演进出更通用的 ROP（Return-Oriented Programming，返回导向编程，见 13.4），把攻击者代码"用现成指令片段拼出来"，彻底绕过 NX 的"不能执行数据"限制。

这里的核心教学点是"缓解会改变攻击形态而非消灭攻击"：NX 把攻击从"注入 shellcode"推向"复用已有代码"，代价是攻击者需要知道那些代码的地址——于是 NX 的有效性又依赖 ASLR（13.2）把 libc/gadget 地址藏起来。三者的耦合关系可以这样连：canary 检测栈上的连续覆盖 → NX 让注入代码跑不起来、逼出 ROP → ROP 需要地址、ASLR 把地址藏起来 → 攻击者靠信息泄露打穿 ASLR → 于是还需要 CFI（13.4）从"能跳去哪"这个维度再设一道关。本机可用 `checksec` 观察 `NX enabled`、用

```
gcc -z execstack prog.c -o prog   # 关闭 NX（栈可执行，用于教学对照）
```

制造对照样本（教学级、仓库外）。

## 13.4 ROP 与 CFI

### 13.4.1 ROP：返回导向编程

ROP（Return-Oriented Programming，返回导向编程）是绕过 NX 的通用技术：攻击者不注入代码，而是在程序及其库的现有可执行内存里搜集大量以 `ret` 指令结尾的短指令序列——称为 gadget（小配件），再通过精心构造的栈内容把这些 gadget 像积木一样串起来，拼出任意计算（图灵完备）。

其运转机制的关键是 `ret` 指令的语义——它做的是

```
ret  ≡  pop rip   （从栈顶取一个地址，跳过去执行）
```

所以只要攻击者控制了栈内容（栈溢出即可做到），就能在栈上摆一串 gadget 地址；每个 gadget 执行到末尾的 `ret` 时，就自动从栈上取下一个 gadget 地址继续，形成"gadget 链"。一个典型的 ROP 链栈布局像这样：

```
[ gadget1 地址 ] [ gadget1 用的数据 ] [ gadget2 地址 ] [ gadget2 用的数据 ] ... [ system 地址 ] [ "/bin/sh" 指针 ]
```

初学者最容易卡在"为什么这些片段能凑出任意功能"。因为可执行代码里 `ret`（0xC3）字节极多，从任意偏移解码 x86 变长指令还能"错位"解出更多意外 gadget，实践中总能找到"往寄存器里放常数""内存读写""系统调用"等基本操作的 gadget，组合起来即图灵完备。ROP 的两大前提是 (1) 能控制栈内容（栈溢出/任意写）(2) 知道 gadget 的绝对地址——第二点正是 ASLR（13.2）要破坏的，所以实战 ROP 往往先靠信息泄露拿到库基址。变体包括 JOP（Jump-Oriented Programming，用间接跳转 gadget，不依赖 `ret`）与 ret2libc（退化为直接调用整函数）。

### 13.4.2 CFI：控制流完整性

CFI（Control-Flow Integrity，控制流完整性）从根上对付 ROP/JOP：它在编译期为程序算出一张合法的控制流图（CFG），运行时在每个**间接**转移（间接调用、间接跳转、函数返回）前检查目标是否落在该图允许的集合里，不合法就中止。ROP/JOP 的本质是把控制流劫持到"程序本不会跳去"的 gadget 位置，CFI 恰好把这类越界跳转拦下。

CFI 分粗粒度与细粒度。粗粒度 CFI 只要求间接目标是"某个合法入口"（如任意函数开头、任意标记的落地点），实现便宜但攻击者仍有较大腾挪空间。细粒度 CFI 进一步约束——例如按函数签名匹配（间接调用点的参数/返回类型必须与被调函数一致），大幅缩小可跳集合。前向边（forward edge，间接调用/跳转）与后向边（backward edge，函数返回）常分别防护：前向边多用"类型/标签检查"，后向边最强的手段是影子栈（shadow stack）。

要理解 CFI 的定位：canary/NX/ASLR 都是"间接抬高门槛"，而 CFI 直接约束"控制流能去哪"，是针对代码复用攻击最对症的一类防御。局限也要讲清——CFI 只约束控制流转移的**目标合法性**，不保证转移的**上下文正确**；只要攻击者选的目标仍在允许集合内，就可能发起"符合 CFG 但语义错误"的攻击（如面向数据的攻击、或在粗粒度下的 gadget 复用）。所以 CFI 强度高度依赖粒度与后向边是否有影子栈。

### 13.4.3 CFI 的落地：软件 CFI 与硬件辅助 ⚙演进快

CFI 有软件与硬件两条实现路线，当前（锚 2026-07-30）均在快速演进。软件 CFI 以 Clang/LLVM 的 `-fsanitize=cfi` 为代表，编译期做基于类型的前向边检查（间接调用目标必须与调用点的函数类型一致，属细粒度），需全程序/LTO 配合；GCC/内核另有 kCFI 用于内核。硬件辅助 CFI 主要有三套：

```
Intel CET —— Shadow Stack（后向边：硬件维护只读影子栈，ret 目标须与影子栈匹配）+ IBT（前向边：间接分支目标须为 endbr64 落地指令）
Arm       —— PAC（Pointer Authentication，用指针高位存放认证码 PAC，返回前校验，防返回地址篡改）+ BTI（Branch Target Identification，前向边落地点，类似 IBT）
```

Intel CET 的 IBT 是一种粗粒度前向边防护（只认"是不是 endbr64 落地点"），业界有 FineIBT 等提案在其上叠加细粒度检查。

对初学者，把这些对号入座即可：影子栈/PAC 管"函数返回不被劫持"（后向边，直击 ROP 的 `ret`），IBT/BTI 管"间接调用/跳转只能落到合法落地点"（前向边，直击 JOP 与间接调用劫持）。影子栈是一块受硬件写保护的独立栈，每次 `call` 同时把返回地址压入影子栈、`ret` 时比对两栈是否一致——攻击者改了普通栈上的返回地址但改不了影子栈，比对失败即中止，这是对 ROP 最干净的后向边防御。这一小节的具体特性/默认开启状态属"⚙演进快、随硬件与内核版本变"，本报告锚 2026-07-30，未在基线本机（是否具备 CET 硬件、内核是否启用 `user_shstk`）逐项实证，如实标待核。

## 13.5 沙箱与隔离

### 13.5.1 隔离的思路：把爆炸半径关进盒子

沙箱（sandbox）与隔离（isolation）是一类不同于 13.1–13.4 的防御——前面几节假设漏洞存在、想让"利用"更难，隔离则假设"利用可能成功"，退一步把被攻破组件能触及的资源（系统调用、文件、内存、网络）压到最小，使攻破一个组件不等于攻破整个系统。这体现最小权限原则（principle of least privilege）：每个组件只拿到完成其工作绝对必要的权限。

渲染引擎要解析来自任意网站的不可信 HTML/JS，是漏洞高发区，于是把它放进一个几乎没有权限的沙箱进程，即便渲染器被攻破，攻击者也拿不到磁盘、无法直接发起危险系统调用，还得再打穿一层才能提权。

要建立的心智模型是"纵深防御的最后一层"：canary/ASLR/NX/CFI 是"防止被攻破"，沙箱是"假设已被攻破，限制损失"。二者互补——正因为前面几层总可能被绕过，隔离才不可或缺。初学者要注意隔离的代价是设计复杂度（进程间通信、权限中介 broker）和性能，所以只把"处理不可信输入的高风险组件"关进沙箱，而非整个程序。

### 13.5.2 进程与权限隔离

最基础的隔离单位是操作系统进程——每个进程有独立虚拟地址空间，硬件页表与内核保证一个进程默认读不到、写不到另一个进程的内存，这本身就是一道内存隔离墙。在此之上叠加权限隔离手段：特权分离（privilege separation）把程序拆成"高权限的小 broker"和"低权限的大 worker"，worker 干脏活、需要特权操作时通过 IPC 请求 broker 代办；降权（drop privileges）在完成必须的特权初始化（如绑定 <1024 端口）后调用 `setuid`/`setgid` 放弃 root；Linux 的 capabilities 把单一的 root 权限切成细粒度能力（如仅 `CAP_NET_BIND_SERVICE`）按需授予；命名空间（namespaces）与 cgroups 隔离进程可见的资源视图（PID、网络、挂载、用户）并限量，是容器（container）的底层机制；chroot/pivot_root 限制文件系统视图。

理解这些的钥匙是"信任边界"——把系统画成若干区域，明确哪块信任哪块、跨界必须经过受控接口。特权分离的经典例子是 OpenSSH：把处理网络输入的部分降权隔离，即便这部分被攻破也不是 root。初学者常混淆"隔离"和"缓解"：进程隔离不修复漏洞，它保证的是"漏洞被利用后，攻击者困在低权限盒子里"。另一个易错点是隔离并非绝对——共享内核是所有这些隔离的公共攻击面，一个内核提权漏洞可以打穿几乎所有用户态隔离，这也是下一节 seccomp（缩小内核攻击面）与虚拟化/更强隔离存在的理由。

### 13.5.3 seccomp：系统调用过滤

seccomp（secure computing mode）是 Linux 内核提供的系统调用过滤机制，让进程主动声明"我只会用这些系统调用"，之后内核拒绝（或杀死/报错/追踪）其余调用，从而大幅缩小该进程能触达的内核攻击面。最初的 seccomp（2005 年引入）只允许极少数调用（`read`/`write`/`exit`/`sigreturn`）；现代实际使用的是 seccomp-BPF（Will Drewry 为 Chrome 沙箱开发），用一段 BPF（Berkeley Packet Filter）程序作为策略，对每次系统调用检查其编号与参数，返回允许/拒绝等动作。

其工作流可以按步骤记：

```
1. 进程构造一段 BPF 过滤程序（对 seccomp_data：系统调用号 + 参数 + 架构 做判定）
2. prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog)  安装过滤器（一经安装不可撤销、且被子进程继承）
3. 之后每次 syscall，内核运行该 BPF，按返回值 ALLOW / ERRNO / KILL / TRAP / TRACE 处理
```

要抓住 seccomp 的独特价值：进程隔离限制"能碰谁的内存/资源"，seccomp 限制"能向内核请求什么"，直接压缩共享内核这个最危险的攻击面。它是允许清单（allowlist，默认拒绝、只放行明确需要的）思路最有效，Chrome、Firefox、systemd、容器运行时（Docker 有默认 seccomp profile）都在用。一个初学者常见误区是"过滤系统调用号就够了"——不然，很多攻击藏在参数里（如 `open` 一个敏感路径、`ioctl` 危险命令），所以 seccomp-BPF 支持对参数做检查（但注意它只能检查寄存器里的标量参数，无法安全解引用指针参数，这是其已知局限）。安装不可撤销的设计是刻意的：防止被攻破的代码把过滤器关掉。

### 13.5.4 软件故障隔离（SFI）

软件故障隔离（SFI，Software Fault Isolation）是一种在**同一地址空间内**用软件手段把不可信模块关进"沙盒"的技术：通过编译期/加载期给不可信代码的每一条内存访问和跳转插入检查（或掩码），强制它只能访问分配给它的一段内存、只能跳转到自身代码内，从而无需独立进程/硬件页表就实现隔离。经典实现是 Google Native Client（NaCl），让浏览器能在同一进程里较安全地跑原生机器码；思想的现代延续是 WebAssembly 的内存模型（线性内存 + 边界约束）。

SFI 的核心手法是对访问做"掩码或检查"，例如把地址强制限制在沙盒段内：

```
addr &= sandbox_mask   （掩码，把高位清零/置为沙盒基址，越界访问被折回段内而非逃逸）
```

跳转目标同样对齐到合法指令边界并限制在沙盒内。

理解 SFI 要对比它和进程隔离的取舍：进程隔离靠硬件（页表 + 特权级）隔离、跨界要昂贵的上下文切换/IPC；SFI 在**同进程内**用软件插桩隔离，跨界调用便宜得多，代价是每次内存访问/跳转都多几条检查指令（运行时开销）且正确性依赖插桩不被绕过（工具链必须可信、代码不可被改写）。初学者可把 SFI 理解为"用软件模拟出一堵墙"，适合"想在自己进程里安全地跑一段不可信插件/字节码、又不愿付进程切换代价"的场景——这正是 WebAssembly 在浏览器与边缘计算里流行的原因。

- 锚点：Stanford CS155「Isolation & Sandboxing」（最小权限、进程/特权隔离、seccomp、SFI/NaCl）+ UC Berkeley CS161 相关讲，核实 2026-07-30。
- 锚点：Linux 内核 `Documentation/userspace-api/seccomp_filter`（seccomp-BPF 机制、`prctl` 安装、不可撤销、参数检查局限）+ Chromium「Linux Sandboxing」文档，核实 2026-07-30。

## 13.6 Rust 所有权对照

### 13.6.1 从"缓解漏洞"到"消灭漏洞类别"

前五节都在"漏洞会存在"的前提下抬高利用门槛，Rust 走的是另一条路——用类型系统在**编译期**静态排除内存错误的整类来源，让空悬指针、越界、释放后使用（UAF）、双重释放、数据竞争在安全代码里根本无法编译通过，从而无需运行时缓解就消灭这些漏洞（呼应 N-12「Rust 内存安全」）。它做到内存安全的同时不依赖垃圾回收（GC），运行时开销接近 C/C++。

核心机制是所有权（ownership）系统，三条规则：

```
1. 每个值有且仅有一个所有者（owner）
2. 同一时刻只能有一个所有者
3. 所有者离开作用域时，值被自动释放（drop）
```

对初学者，关键是理解这三条如何一举消灭多个 bug 类别：因为"唯一所有者 + 离开作用域即释放"，释放时机由编译器根据作用域静态确定，不会漏放（内存泄漏减少）、不会重复释放（无 double-free）、释放后原所有者也不再有效（无 UAF），全部在编译期定死，没有运行时 GC 也没有手动 `free` 的出错空间。这正是 Rust 与 C（手动、易错）和 Java/Go（GC、有运行时开销）之间的第三条路。

### 13.6.2 借用与借用检查器

值不必每次都转移所有权，可以"借用"（borrow）——通过引用临时访问而不夺走所有权。借用受一条黄金规则约束，由编译期的借用检查器（borrow checker）强制：

```
在任一时刻，对某个值，要么存在任意多个不可变引用（&T，共享只读），
要么存在恰好一个可变引用（&mut T，独占可写），二者不可兼得。
```

这条"多读 XOR 一写"（aliasing XOR mutability，别名与可变互斥）规则，静态排除了数据竞争与迭代器失效一类问题。

要把这条规则和内存安全连起来：绝大多数内存破坏（包括数据竞争、迭代中修改容器导致的悬垂）本质是"一个地方在写，另一个别名同时在读/写"。Rust 直接在类型层面禁止"可变别名"——要么大家都只读（安全），要么独此一份可写（无竞争）。借用检查器还引入生命周期（lifetime）标注，静态验证任何引用都不会比它指向的数据活得更久，从而杜绝悬垂引用（dangling reference）——这是 C 里 UAF 的编译期对应物被直接拒绝。初学者常觉得"和编译器搏斗"很痛苦，但那正是把运行时崩溃提前成了编译期报错。

### 13.6.3 unsafe、边界检查与"对照"的边界

Rust 的内存安全保证覆盖**安全**子集；某些底层操作（解引用裸指针、调用 C FFI、实现底层数据结构）无法被借用检查器证明安全，需显式写在 `unsafe` 块里，此时程序员向编译器承诺"我保证这里的不变式成立"。此外，Rust 对数组/切片的索引访问在运行时做边界检查（越界即 panic 而非越界读写），这是运行时而非纯编译期的保护。

理解这一节要点在于把 Rust 摆到正确位置，而非神话它。安全 Rust 静态消灭的是空悬/UAF/double-free/越界/数据竞争这些**空间与时间内存错误**；它不消灭逻辑错误、也不消灭 `unsafe` 块内或错误 FFI 引入的问题——`unsafe` 是"信任程序员"的逃生舱，Rust 的安全性依赖 `unsafe` 用得少且被严格审计。相对本报告前几节：canary/ASLR/NX/CFI/沙箱是"C/C++ 已经写好、漏洞难免，运行时兜底"的事后缓解；Rust 是"从语言设计上让整类漏洞写不出来"的事前预防。二者不互斥——现实系统常两者叠加（Rust 组件仍跑在开了 NX/ASLR/沙箱的进程里），因为 `unsafe`、FFI 与逻辑漏洞的存在意味着纵深防御依然必要。这也解释了为什么 Android、Windows、Linux 内核等都在把新代码/高风险组件逐步迁往 Rust，同时保留传统缓解。
