## 11.1 量子威胁

### 11.1.1 量子计算对密码的两类冲击（总览）

量子计算机不会"一键破解一切密码"，它对密码学的冲击分成截然不同的两类。第一类是**致命的**：Shor 算法能在多项式时间内解大整数分解和离散对数，这两个问题正是 RSA、（有限域）Diffie–Hellman、椭圆曲线 ECDH/ECDSA 的全部安全根基，因此这些公钥算法在足够大的量子计算机面前**完全失效**，无论把密钥加到多长都救不回来。第二类是**可控的**：Grover 算法只能给"无结构搜索"提供平方根级加速，它把对称加密（AES）和哈希（SHA-2/SHA-3）的穷举强度打了对折，应对办法是**把密钥/摘要长度翻倍**（例如从 AES-128 升到 AES-256）即可，不必换算法。

初学者先把这张"分账表"记牢，它是整个 PQC 领域的地图：公钥密码（非对称）受 Shor 冲击、要**换**；对称密码与哈希受 Grover 冲击、只要**加长**。这也解释了为什么 NIST 的后量子标准（11.3–11.4）全都是公钥算法（密钥封装与签名），而没有"后量子 AES"——AES-256 本身就被认为足够抗量子。一个常见误解是"量子计算机让所有加密都失效"，这是不准确的；准确的说法是"它摧毁了当前的公钥密码，并把对称密码的有效强度减半"。

### 11.1.2 Shor 算法：破分解与离散对数

Shor 算法（Peter Shor, 1994）在理想的大规模容错量子计算机上，能以多项式时间（约输入位数的立方级）分解大整数并计算离散对数。它的核心是用量子傅里叶变换高效地找出模幂函数的**周期**，而一旦拿到周期，分解和离散对数就迎刃而解。这直接击穿了三大经典困难假设：

大整数分解（RSA 的根基）

离散对数问题 DLP（有限域 DH、DSA、El Gamal 的根基）

椭圆曲线离散对数问题 ECDLP（ECDH、ECDSA、EdDSA 的根基）

因此 RSA、DH、ECDH、DSA、ECDSA、EdDSA、El Gamal 在足够强的量子机面前**全线崩塌**。

对初学者，关键是理解"多项式时间"意味着什么。经典计算机分解 2048 位 RSA 模数需要的时间随位数指数级增长，天文数字般不可行；Shor 算法把这个代价压到多项式级，等于把"永远算不完"变成"很快算完"。要注意的是，这需要一台**大规模、容错**的量子计算机（需要成千上万稳定逻辑比特），而 2026 年现实中的量子机还远达不到破 RSA-2048 的规模——所以经典公钥密码**今天仍安全**。PQC 的紧迫性不在"明天就被破"，而在于两点：一是大机器可能十几年后出现，二是"先收割后解密"的威胁（见 11.1.4），使得今天加密的长效机密数据已经有风险。椭圆曲线常被误以为"更抗量子"，其实相反——ECDLP 在 Shor 面前和普通离散对数一样脆，且因密钥短，破解所需的量子资源反而更少。

### 11.1.3 Grover 算法：对称/哈希的平方根冲击

Grover 算法（Lov Grover, 1996）为"在 N 个候选里找出满足条件的那一个"这类无结构搜索提供平方根加速：经典要试约 N 次，量子只需约 √N 次。对一个 n 位密钥的对称加密，穷举空间是

N = 2ⁿ

Grover 把穷举代价从 2ⁿ 降到

√(2ⁿ) = 2^(n/2)

也就是把**有效安全强度砍半**：AES-128 对 Grover 只剩约 64 位强度，AES-256 只剩约 128 位。应对极简单——用 AES-256，它在量子下仍有约 128 位强度，足够安全。

初学者要抓住 Shor 与 Grover 的**量级差别**：Shor 是指数→多项式的"降维打击"，直接判死刑；Grover 只是平方根加速，是"打折"，加长密钥就能补回来。哈希函数同理：找原像（preimage）的量子代价从 2ⁿ 降到 2^(n/2)，所以想要 128 位抗量子原像强度就用 SHA-256（n=256）。抗碰撞则更微妙——生日攻击本就把经典碰撞代价压到 2^(n/2)，量子理论上能进一步到约 2^(n/3)，但需要巨量量子存储，普遍认为不实用，因此实践中 SHA-256 的抗碰撞仍视作约 2^128。还有一个重要的现实限制：Grover 的加速极难并行化——用 M 台机器只能得到 √M 的额外加速，这让它在工程上比理论更弱，也是不少专家认为"Grover 威胁被高估"的原因。

### 11.1.4 HNDL（先收割后解密）与迁移紧迫性

"先收割后解密"（Harvest Now, Decrypt Later，HNDL）是驱动 PQC 迁移紧迫性的核心逻辑：攻击者**现在**就可以把截获的加密流量整批存下来，等未来量子计算机成熟后**再回头解密**。这意味着一条数据的"保密寿命"若跨越量子机成熟的时点，它今天用 RSA/ECDH 加密就已经不安全了——哪怕破解发生在十年后。

对初学者，这解释了一个看似矛盾的现象：既然能破 RSA 的量子机还不存在，为什么 2024–2026 年浏览器、云厂商就急着上 PQC？答案就是 HNDL——对于"需要保密很多年"的数据（国家机密、医疗记录、长期身份凭证），迁移窗口 = 数据保密寿命 + 迁移改造时间，往前倒推，现在动手已经不算早。这也解释了迁移的**优先级顺序**（见 11.5）：密钥交换/加密（KEM）最紧急，因为它直接暴露在 HNDL 下；数字签名相对不急，因为签名是当下验真、事后伪造一份旧签名没有"回溯收割"价值，只要在量子机成熟前换掉即可。

## 11.2 格基困难问题

### 11.2.1 格与最短向量问题(SVP/CVP)直觉

格（lattice）是 n 维空间里由一组基向量的所有整数线性组合张成的、无限延伸的规则点阵。围绕它有两个被广泛相信"经典和量子都难解"的问题：最短向量问题 SVP（在格里找出离原点最近的非零点）和最近向量问题 CVP（给定空间中任一目标点，找出离它最近的格点）。这些问题在维度很高（几百上千维）时，即使用最好的算法也只能做到指数级代价，是后量子公钥密码的地基。

对初学者，可以用一个二维直觉起步：给你两个基向量，它们的整数组合铺出一片斜网格点阵；SVP 就是"哪个格点离原点最近"。在二维你一眼能看出来，但格密码用的是几百维的格——此时"一眼看出最近点"变得极其困难，因为好的（接近正交的）基能让你轻松找点，而攻击者拿到的往往是一组"又长又歪、几乎平行"的坏基，从坏基里找最短向量就是难题。一个关键点：与分解/离散对数不同，**目前没有任何已知量子算法能显著加速一般格问题**，这正是 NIST 把格作为后量子首选地基的信心来源。

### 11.2.2 LWE 问题

带误差学习问题（Learning With Errors，LWE，Regev 2005）是格密码最常用的困难问题形式。取一个模数 q、一个秘密向量 s，攻击者看到许多"随机矩阵 A 乘以 s 再加一点小随机噪声 e"的样本：

b = A · s + e  (mod q)

搜索型 LWE 要求从 (A, b) 恢复秘密 s；判定型 LWE 要求区分 (A, b) 与"完全均匀随机的 (A, 均匀 b)"。关键在那个**小噪声 e**：没有它，b = A·s (mod q) 就是一个普通线性方程组，高斯消元瞬间解出 s；加了噪声后，每个方程都"差一点点对不上"，高斯消元会把噪声不断放大到彻底淹没信号，于是求解变回困难的格问题。

对初学者，LWE 可以类比成"带橡皮擦痕迹的方程组"：正常的线性方程组是送分题；但如果每个等式右边都被人偷偷加减了一个小随机数，你就再也不能靠代数消元干净地解出未知数了。噪声的大小要拿捏得恰到好处——太小则接近无噪声、容易被攻破；太大则连合法用户自己解密都会出错（见 11.3.4 解密失败）。这种"用噪声把好解的问题变难"的思想，是所有格基加密的共同引擎。

### 11.2.3 Module-LWE 与 Ring-LWE

朴素 LWE 用的是普通整数矩阵和向量，安全但**又大又慢**（矩阵 A 巨大）。为提效，密码学家把标量换成多项式：在多项式环上做 LWE，就得到 Ring-LWE（环）和介于两者之间的 Module-LWE（模）。ML-KEM 和 ML-DSA 都建在 Module-LWE 上，工作在多项式环

R_q = Z_q[X] / (X²⁵⁶ + 1)，  q = 3329

秘密和公钥变成"由这种多项式组成的小向量/小矩阵"，用维度参数 k（模的秩）来调节安全等级。

对初学者，理解这三者是一条"结构 vs 效率"的光谱：朴素 LWE 结构最少、最保守、也最笨重；Ring-LWE 把整个系统塞进一个多项式环，效率最高但引入了最多的额外代数结构（理论上给攻击者更多可乘之机）；Module-LWE 是折中——把问题拆成 k 个小环再拼起来，既比朴素 LWE 快得多，又比 Ring-LWE 保守。NIST 选 Module 版正是看中这份平衡：改 k 就能在同一套代码里切换安全等级（ML-KEM 的 512/768/1024 就对应 k=2/3/4），工程上非常干净。

### 11.2.4 为什么相信格抗量子：最坏情形到平均情形规约

格密码除了"目前无量子加速算法"这一经验信心外，还有一层更强的理论支撑——最坏情形到平均情形的规约（worst-case to average-case reduction，Regev）。它证明：如果你能解开**随机**（平均情形）的 LWE 实例，就能用它解开**任意最坏情形**的格问题（如近似 SVP）。因此"随手生成一个 LWE 密钥恰好落在弱实例上"这种运气问题不存在——破随机密钥和破最难的格问题一样难。

对初学者，这条规约的价值在于把安全性"锚"在最坚固的地方。很多密码方案的困难假设是"平均而言难"，但你无法排除某些倒霉的密钥特别弱；LWE 的规约保证了**没有弱密钥**——随机采样出的密钥其安全强度有下界托底，不靠运气。需要澄清的是：这条规约是"抗量子信心"的重要理论支柱，但并非绝对证明，NIST 参数选择仍主要依据对已知最好格攻击算法（如 BKZ 格基约减）的具体代价估计；因此格的抗量子性属"强烈相信但未被数学证明"，这一点在 11.5 讨论 HQC 备份算法时会再呼应。

## 11.3 ML-KEM (FIPS 203)

### 11.3.1 KEM 抽象接口（KeyGen / Encaps / Decaps）

ML-KEM 是一个密钥封装机制（Key-Encapsulation Mechanism，KEM），不是"直接加密任意消息"的公钥加密。KEM 的任务是让双方安全地商定一段**随机共享密钥**（32 字节），再用它去喂对称加密（这就是 G11-06 讲过的 KEM/DEM 混合范式）。它由三个算法组成：

KeyGen() → (ek, dk)  生成封装密钥 ek（公钥）与解封装密钥 dk（私钥）

Encaps(ek) → (K, c)  用对方公钥产出一段共享密钥 K 和密文（封装）c

Decaps(dk, c) → K  用自己私钥从 c 还原出同一段 K

发送方把 c 传给接收方，双方就都持有了相同的 K，全程 K 本身从不上网。

对初学者，KEM 和"公钥加密"的区别是常见困惑点。公钥加密是"我选一条消息 m，用你的公钥加密它"；KEM 是"我不选消息，让算法**随机生成**一段密钥 K 并连同密文一起给你"——因为大多数场景（如 TLS 握手）真正需要的就是一段双方共享的随机密钥，而不是加密某条特定明文。把 ML-KEM 想成"抗量子版的 ECDH"：ECDH 也是双方各出一份、算出共享密钥；ML-KEM 达到同样目的，只是底层换成了格问题。ek/dk 这套新命名（encapsulation/decapsulation key）是 FIPS 203 的正式术语，取代了旧论文里的 public/secret key 叫法。

### 11.3.2 从 Kyber 到 ML-KEM：底层 K-PKE 与环参数

ML-KEM 的前身是 NIST PQC 竞赛胜出的 CRYSTALS-Kyber，2024 年定型为 FIPS 203 时改名 ML-KEM（Module-Lattice-based KEM）并做了细节调整，两者**不完全等同、不可混用测试向量**。它内部先构造一个只满足弱安全（IND-CPA）的公钥加密 K-PKE，其安全性直接来自 Module-LWE（见 11.2）：公钥本质是一组 LWE 样本 (A, b=A·s+e)，加密就是再叠一层小噪声把消息藏进去。工作环固定为

R_q = Z_q[X] / (X²⁵⁶ + 1)，  q = 3329，  n = 256

再用 FO 变换（见 11.3.4）把 K-PKE 升级成抗强攻击（IND-CCA2）的完整 KEM。

对初学者，记住"两层结构"就够了：内层 K-PKE 是"格加密的毛坯"，只扛得住被动窃听；外层 FO 变换是"加固层"，让它扛得住主动攻击者反复投喂恶意密文。命名上要特别当心——文献、旧库、区块链项目里仍大量写"Kyber"，而合规实现必须用 FIPS 203 的 ML-KEM；面试或工程中把两者当成同一个东西直接套参数/测试向量会出错。q=3329 是个精心选的小素数（让快速多项式乘法 NTT 能用），X²⁵⁶+1 则让环具备好的代数性质，这些是效率工程细节，初学者知道"参数是固定且精心挑选的"即可。

### 11.3.3 参数集与尺寸对照

FIPS 203 定义三个参数集，用 Module 的秩 k 调节强度，对应 NIST 的三档安全类别（类别 1/3/5 分别对标穷举 AES-128/192/256 的代价）。核实数值（NIST FIPS 203，2024-08-13）：

ML-KEM-512（k=2，类别 1）：封装密钥 ek 800 字节，密文 c 768 字节

ML-KEM-768（k=3，类别 3）：封装密钥 ek 1184 字节，密文 c 1088 字节

ML-KEM-1024（k=4，类别 5）：封装密钥 ek 1568 字节，密文 c 1568 字节

三档共享密钥 K 均为 32 字节。

对初学者，先建立"数量级直觉"：ML-KEM-768 的公钥约 1.2 KB、密文约 1.1 KB，比 ECDH 的 32 字节公钥大了几十倍——这正是后量子密码的普遍代价（密钥/密文尺寸显著变大），也是迁移时要关心带宽和握手包大小的原因（见 11.5.2）。选型上，ML-KEM-768 是业界事实上的默认与推荐主力（Chrome/Firefox 的混合方案就用它），因为它在安全余量和尺寸间平衡最好；ML-KEM-512 用于极度受限场景，ML-KEM-1024 用于要求最高长效保密的场景。注意"512/768/1024"是参数集编号（约等于底层格维度 k×256），不是"密钥比特数"，别和 AES-128/256 那种"直接是位数"的命名混淆。

### 11.3.4 FO 变换、IND-CCA2 与解密失败

内层 K-PKE 只有 IND-CPA 安全（能抗被动窃听，但抗不住主动喂恶意密文的攻击者）。ML-KEM 用 Fujisaki–Okamoto（FO）变换把它升级到 IND-CCA2（能抗自适应选择密文攻击）。FO 的核心机制是**重加密校验**：Decaps 先解出候选消息，再用它**重新加密一遍**，把重算出的密文和收到的密文逐位比对——只有完全一致才接受。ML-KEM 采用**隐式拒绝**：一旦比对失败，不报"解密错误"，而是返回一个由私钥和密文伪随机派生出的、看起来正常的假密钥。

由于 LWE 天生带噪声，还存在极小概率的**解密失败**（合法密文也偶尔解错），FIPS 203 的参数把这个失败概率压到密码学上可忽略（约 2⁻¹³⁰ 量级或更低，属精心设计的参数目标）。

对初学者，这里有两个反直觉但关键的设计。其一，为什么失败要"假装成功返回假密钥"而不是报错？因为报错本身会泄露信息——攻击者能靠"这条密文是否被拒"这个 1 比特反馈，反复试探逐步逼近私钥（这正是选择密文攻击的套路）；隐式拒绝让"合法失败"和"恶意密文"在攻击者眼里长得一模一样，堵死了这条信息侧信道。其二，重加密校验的直觉是"你要么老老实实按协议封装、要么就别想让我接受"——攻击者篡改过的密文重加密后必然对不上，于是被无声丢弃。这套 FO 变换是几乎所有格基 KEM 的通用加固手段，QROM（量子随机预言模型）下的安全证明是 NIST 选它的重要依据。

#### 来源与时效（本小主题末集中列，不逐项脚注）
- 锚点：NIST FIPS 203（Module-Lattice-Based Key-Encapsulation Mechanism Standard，2024-08-13 定型 GA）——KEM 三算法（KeyGen/Encaps/Decaps）、ek/dk 术语、K-PKE 内层、参数集与尺寸、FO 变换与隐式拒绝 https://csrc.nist.gov/pubs/fips/203/final ，核实 2026-07-30。
- 锚点：Katz & Lindell 3rd ed. Ch14（KEM 抽象、Kyber/Module-LWE 加密构造、CPA→CCA 的 FO 提升直觉），核实 2026-07-30。
- 交叉核对：参数集尺寸（512: ek 800/ct 768；768: ek 1184/ct 1088；1024: ek 1568/ct 1568；K=32B）取自 FIPS 203 正文，并与多份二手技术综述（Encryption Consulting、Cloudflare 等）交叉一致，无冲突。安全类别 1/3/5 对标 AES-128/192/256 两来源一致。
- 冲突/分账：文献中"Kyber"与"ML-KEM"常混用——本报告按 FIPS 203 分账：ML-KEM 为标准算法、与原始 Kyber 有细节差异、测试向量不通用，属"标准 vs 前身"分账而非矛盾。
- 前沿性：主流库对 ML-KEM 的标准化实现仍在推进，**⚙演进快·锚版本·随时变**；解密失败概率数量级为参数设计目标，具体精确值以 FIPS 203 正文为准。

## 11.4 ML-DSA / SLH-DSA (FIPS 204/205)

### 11.4.1 ML-DSA (FIPS 204)：格基 Fiat–Shamir-with-aborts 签名

ML-DSA（Module-Lattice-based Digital Signature Algorithm，FIPS 204，前身 CRYSTALS-Dilithium）是 NIST 推荐的**主力后量子签名**，建立在 Module-LWE 与 Module-SIS（短整数解）困难问题上。它用"带中止的 Fiat–Shamir"（Fiat–Shamir with aborts）范式：签名时先承诺一个带噪声的随机量，用哈希（把消息和承诺压成挑战）做 Fiat–Shamir 变换生成响应，但若响应会泄露私钥信息就**拒绝重来**（rejection sampling），直到采到一个安全的签名为止。

对初学者，Fiat–Shamir 的思想在 G11-08（Schnorr 签名）已见过——把"交互式身份证明"用哈希塞掉交互、变成非交互签名。ML-DSA 的新意在那个"aborts（中止重采样）"：格签名的每个响应都可能像投影一样泄露一丝私钥方向，攻击者攒够多条就能反推私钥；解决办法是签名者自我审查，只保留那些"落在安全区间内、不泄露信息"的响应，落在危险区就丢掉重签。所以 ML-DSA 签名耗时是**不固定**的（偶尔要重试几次），这是它的正常特征而非 bug。它和 ML-KEM 共享同一套 Module-LWE 数学地基和 NTT 快速多项式乘法，是"格基双子星"。

### 11.4.2 ML-DSA 参数集与尺寸

FIPS 204 定义三个参数集，对应 NIST 安全类别 2/3/5。核实数值（NIST FIPS 204，2024-08-13）：

ML-DSA-44（类别 2）：公钥 1312 字节，签名 2420 字节

ML-DSA-65（类别 3）：公钥 1952 字节，签名 3309 字节

ML-DSA-87（类别 5）：公钥 2592 字节，签名 4627 字节

对初学者，先看数量级：ML-DSA 签名约 2.4–4.6 KB、公钥约 1.3–2.6 KB，比 ECDSA/Ed25519 的 64 字节签名、32 字节公钥大了几十倍。这在证书链、固件签名等要塞很多签名的场景会明显增加体积，是选型时的核心权衡。命名里的"44/65/87"是内部矩阵维度参数（不是安全位数），对应类别 2/3/5——注意这里最低档是**类别 2**（对标略高于 AES-128），没有类别 1，这是 ML-DSA 与 ML-KEM 命名对应关系上一个容易记错的小差异。业界常用 ML-DSA-65 作平衡默认。

### 11.4.3 SLH-DSA (FIPS 205)：无状态哈希基签名

SLH-DSA（Stateless Hash-based Digital Signature Algorithm，FIPS 205，前身 SPHINCS+）是一条**完全不依赖格、只依赖哈希函数安全性**的备选签名路线。它的全部安全性仅建立在底层哈希（SHA-2 或 SHAKE）抗原像/抗碰撞之上——而哈希只受 Grover 的温和冲击（加长即可，见 11.1.3）。它把一次性哈希签名（每把密钥只能安全签一次）用 Merkle 树和"少数几次签名"方案层层组织成一棵巨大的超树（hypertree），从而能用一把密钥签很多次，且**无需维护状态**（这正是相对早期有状态哈希签名 XMSS/LMS 的关键改进——不必记住"哪些一次性密钥已用过"）。

对初学者，SLH-DSA 的定位是"最保守的保险丝"。它不碰任何新数学假设（格可能哪天被攻破，但"哈希是安全的"是密码学几十年最稳的信念之一），所以是抵御"万一格出事"的兜底选择。代价是**慢且大**：签名可达几 KB 到几十 KB、签名速度也远慢于 ML-DSA。"无状态"这三个字很重要——有状态签名一旦重用某个一次性密钥就彻底泄露私钥，而运维中要可靠地跨机器/备份记住"用过哪些"极易出错；SLH-DSA 用随机化和超树设计消除了这个致命运维陷阱，代价是尺寸更大。选型建议：日常用 ML-DSA，对"抗未知格攻击"有极高长期要求（如根 CA、固件信任根）时考虑 SLH-DSA 或两者并用。

### 11.4.4 SLH-DSA 参数命名（s/f、SHA2/SHAKE）与保守性权衡

FIPS 205 批准 **12** 个参数集，命名由三个维度组合而成：哈希族（SHA2 或 SHAKE）× 安全强度（128/192/256）× 优化取向（s = small 签名更小但签名更慢，f = fast 签名更快但签名更大）。例如 SLH-DSA-SHA2-128s、SLH-DSA-SHAKE-256f 等，共 2×3×2 = 12 个。

对初学者，重点理解那个 **s/f 取舍**：同一安全级下，"s"版把签名压小（但生成慢），"f"版把生成加快（但签名更大），这是一个纯工程权衡——签得多、传得多就选 s 省带宽；签得少、要快就选 f。SHA2 与 SHAKE 只是底层哈希族不同（SHAKE 来自 SHA-3/Keccak），选哪个通常看平台已有哪种哈希加速。数字 128/192/256 才是安全强度位。把这套"哈希族×强度×s/f"记成三个旋钮，就能看懂任何一个 SLH-DSA 参数名。

### 11.4.5 FN-DSA (FIPS 206 / Falcon)：草案状态（前沿硬标）

**⚙演进快·锚版本·随时变**——除已定型的 ML-DSA、SLH-DSA 外，NIST 还在标准化第三个签名 FN-DSA（Fast-Fourier lattice-based DSA，前身 Falcon），编号 FIPS 206。截至核实日 2026-07-30，FIPS 206 **仍为草案、尚未定型**：NIST 于 2025-08-28 将草案提交审批，初始公开草案（IPD）流程进行中，最终版预计 2026 年底至 2027 年初。因此本报告**不把 FN-DSA 作为可用结论**，只登记其状态。

对初学者，FN-DSA 的卖点是**签名和公钥都非常紧凑**（比 ML-DSA 小得多），适合带宽/存储极受限又要塞很多签名的场景（如某些证书、区块链）。它标准化最慢的原因很有教学意义：FN-DSA 签名依赖浮点高斯采样，而"在恒定时间内安全地做浮点运算"极难实现——稍有不慎就会引入计时侧信道泄露私钥（呼应 G11-14 侧信道）。这说明一个算法"数学上优秀"不等于"工程上易安全落地"，NIST 宁可让它多等也要把实现安全性打磨好。三个签名的分工可记为：ML-DSA = 主力（平衡）；SLH-DSA = 保守兜底（只靠哈希）；FN-DSA = 紧凑但尚未定型（谨慎观望）。

#### 来源与时效（本小主题末集中列，不逐项脚注）
- 锚点：NIST FIPS 204（Module-Lattice-Based Digital Signature Standard / ML-DSA，2024-08-13 定型 GA）——Fiat–Shamir-with-aborts、Module-LWE/SIS、参数集与尺寸 https://csrc.nist.gov/pubs/fips/204/final ，核实 2026-07-30。
- 锚点：NIST FIPS 205（Stateless Hash-Based Digital Signature Standard / SLH-DSA，2024-08-13 定型 GA）——无状态哈希签名、超树、12 个参数集（SHA2/SHAKE × 128/192/256 × s/f）https://csrc.nist.gov/pubs/fips/205/final ，核实 2026-07-30。
- 锚点：Katz & Lindell 3rd ed. Ch14（哈希基签名、一次性签名/Merkle 树、格签名与 Fiat–Shamir 直觉），核实 2026-07-30。
- 锚点（前沿状态）：NIST CSRC "FIPS 206: FN-DSA (Falcon)" 状态更新（草案提交审批 2025-08-28，未定型）https://csrc.nist.gov/projects/post-quantum-cryptography ，核实 2026-07-30。
- 交叉核对：ML-DSA 尺寸（44: pk1312/sig2420；65: pk1952/sig3309；87: pk2592/sig4627）取自 FIPS 204，并与二手综述交叉一致；SLH-DSA 12 参数集命名取自 FIPS 205 正文。安全类别 ML-DSA 为 2/3/5（无类别 1）两来源一致，无冲突。
- 前沿性：FIPS 206/FN-DSA **未定型**，硬标状态、不作可用结论；最终发布时间为估计，**⚙随时变**。

## 11.5 混合部署与迁移

### 11.5.1 混合(hybrid)的动机与构造

混合部署（hybrid）指在同一次密钥交换里**同时**跑一个经典算法（如 X25519/ECDH）和一个后量子算法（如 ML-KEM），把两者各自产出的共享密钥**拼接**后一起喂给密钥派生函数（KDF），得到最终会话密钥。安全性是"二者取其强"：只要经典与 PQC 中**至少一个**没被攻破，最终密钥就安全。

拼接的直觉可写成

最终密钥 = KDF( 经典共享密钥 ‖ PQC 共享密钥 )

对初学者，混合是过渡期的"双保险/安全带加背带"策略，动机有二。其一，PQC 算法（尤其 ML-KEM）相对年轻，虽有强证据但可能存在尚未发现的实现或数学缺陷（回想 11.2.4 格抗量子"相信但未证明"）——万一 PQC 翻车，经典 ECDH 还能顶住今天的经典攻击者。其二，经典 ECDH 面对未来量子机会倒，但今天仍是久经考验的成熟算法——万一新 PQC 实现有 bug，经典这条腿保底。两条腿一起，才在"当下经典攻击者"和"未来量子攻击者"两个方向都安全。注意拼接顺序和格式由具体协议规范固定，不能随意拼（否则会引入攻击面），这是 draft-ietf-tls-ecdhe-mlkem 等文档要精确规定的原因。

### 11.5.2 TLS 1.3 的 X25519MLKEM768

**⚙演进快·锚版本·随时变**——当前 Web 上事实标准的混合密钥交换是 **X25519MLKEM768**：把经典 X25519（ECDH）与后量子 ML-KEM-768 组合。截至 2026 年，它已在主流浏览器**默认启用**：Chrome（约 131+）、Firefox（约 132+，QUIC/HTTP-3 约 135+）、Edge、Brave、Opera 等。其 IETF 规范 draft-ietf-tls-ecdhe-mlkem 截至核实日**仍是草案、尚未成为正式 RFC**（注意：RFC 9370 是 IKEv2 的，不是 TLS 的，勿混淆）。

握手中客户端在 ClientHello 里发一个合并的 key share：ML-KEM-768 封装密钥 1184 字节 + X25519 临时公钥 32 字节 = 1216 字节；最终共享密钥 64 字节（两段各 32 拼接）。

对初学者，这是 PQC 迄今最大规模的真实落地——你今天打开支持的网站，浏览器已经在悄悄用抗量子密钥交换了。选 ML-KEM-768（类别 3）而非更高档，是尺寸与安全的平衡（见 11.3.3）。为什么先迁**密钥交换**而不是签名？因为 KEM 直接暴露在 HNDL（11.1.4）下、最紧急；TLS 里的服务器证书签名（认证）是当下验真、量子机成熟前换掉即可，所以证书链的 PQC 签名（用 ML-DSA）落地比密钥交换晚一拍。要注意握手包因此变大（多了约 1 KB+），极少数老旧中间盒可能因不认识大 ClientHello 而出问题，这是部署时的现实摩擦点。

### 11.5.3 迁移时间线（NIST IR 8547：2030 弃用 / 2035 禁用）

**⚙演进快·锚版本·随时变**——NIST 在 NIST IR 8547（《向后量子密码标准过渡》，2024-11 发布初始公开草案，截至核实日仍为草案状态）里给出迁移时间锚点：量子易损的公钥算法（RSA、ECDSA、ECDH、有限域 DH）在 **2030 年后弃用（deprecated）**、**2035 年后禁用（disallowed）**。关键例外：**混合模式（经典＋已批准 PQC）不受 2035 禁用限制**，正是为支持平滑分阶段迁移。

对初学者，"弃用"和"禁用"是两个严格分级：弃用 = 不再用于新部署但存量可延用；禁用 = 到期后彻底不许再用于其保护目的。把 2030/2035 当成"倒计时锚"——从今天到 2035 只有约十年，而大型机构的密码迁移（盘点资产、换库、换协议、换证书、验证兼容）往往要好几年，所以"现在就动手"并不夸张。这套日期通过美国行政令 EO 14412 与 OMB M-26-15 等对联邦系统构成合规压力（联邦高价值资产以 2030 为准、2035 为全面迁移终点）。务必注意：这些是**美国联邦**的时间线与草案状态，具体日期仍可能随 IR 8547 定稿调整，属演进项，不当作全球硬性法律结论。

### 11.5.4 HQC 备份 KEM 与算法多样性

**⚙演进快·锚版本·随时变**——NIST 于 2025-03 宣布选中 **HQC**（Hamming Quasi-Cyclic）作为 ML-KEM 之外的**备份密钥封装算法**，它是第五个入选的 PQC 算法、也是第四轮评估的唯一胜出者。HQC 基于**纠错码**（code-based）困难问题，而非格——这正是选它的核心动机：**算法多样性**。其正式标准（编号待定）截至核实日**仍在起草、尚未定型**。

对初学者，HQC 的意义在"不把鸡蛋放一个篮子"。ML-KEM 和 ML-DSA 都建在格上，万一未来有人找到破格的通用（甚至量子）算法，整条格基防线会同时失守；HQC 的数学基础完全不同（编码理论），能在"格翻车"的极端情形下接棒，做加密侧的兜底——功能上类比 SLH-DSA 在签名侧的兜底角色（11.4.3）。代价是 HQC 的密钥/密文比 ML-KEM 更大、效率更低，所以它是"备份"而非"主力"：日常仍用 ML-KEM，HQC 作为多样性储备。

### 11.5.5 加密先行、签名滞后与密码敏捷性(crypto-agility)

迁移的总策略可提炼成两条。其一是**优先级排序**：密钥交换/加密（KEM）最先迁，因为受 HNDL（11.1.4）直接威胁；数字签名次之，因为它当下验真、只需在量子机成熟前换掉。其二是**密码敏捷性（crypto-agility）**：把系统设计成"算法可插拔"，让未来再换算法（无论是升级 PQC 参数，还是万一要切到 HQC）时不必重写整个系统。

对初学者，密码敏捷性是这轮迁移留下的最重要工程教训。过去很多系统把某个算法（如 RSA-2048）**硬编码**进协议和代码，一旦要换就伤筋动骨；PQC 迁移正好暴露了这种脆弱，也逼着大家把"算法标识符 + 可协商 + 可替换"做进架构。这样即使 PQC 本身还年轻、未来可能再调整（参数变、备份算法上位、甚至发现新缺陷），系统也能低成本跟进。把这条记成一句话：迁移不是"一次性换个算法"，而是"建立随时能再换算法的能力"。

### 11.5.6 基线环境的 PQC 支持现状（坐实、不作结论）

**⚙演进快·锚版本·随时变**——就本知识库基线（Python 3.11.15）而言：Python **标准库**（`hashlib`、`ssl`、`secrets`、`hmac` 等）**不提供任何 PQC 原语 API**——没有 ML-KEM/ML-DSA/SLH-DSA 的密钥生成、封装或签名接口，标准库只覆盖经典算法（RSA、ECDH、ECDSA、AES、SHA 等）。这是可坐实的**状态陈述、不作结论**：并非"Python 永远不支持 PQC"，而是"基线标准库当前无标准 PQC 接口"。

要获得 PQC 能力，需依赖标准库之外：底层可经 OpenSSL 3.5（2025 年引入原生 ML-KEM/ML-DSA/SLH-DSA）暴露，或用第三方库（如 liboqs / python-oqs、pqcrypto 等）。**基线 Python 3.11.15 所链接的 OpenSSL 是否已达 3.5+、是否暴露 PQC 接口，以及第三方库的具体可用版本——均标「待核」**（本次未做实机验证；且 brief 已注明 `pip install` 的包不随容器持久化，第三方库需现装现用）。

对初学者，这一节的价值是给出一个**诚实的现实锚**：标准已经定型（FIPS 203/204/205 GA，这是硬结论），但"你手边这套基线环境能不能直接 import 一个 PQC 就用"是另一回事，答案是标准库层面不行、需外部依赖，且具体支持随库版本快速变化。把"标准定型"与"生态落地"分开看，是理解一切前沿密码技术的通用姿势——标准先行，工具链和运行时支持往往滞后并持续演进。
