## 16.1 认证与授权（authN vs authZ）

### 16.1.1 认证（authentication）与授权（authorization）的定义与区分

认证（authentication，常缩写 authN）是**核实"你是不是你声称的那个主体"**的过程；授权（authorization，常缩写 authZ）是**在已知主体身份后，判定"这个主体能否对某资源做某操作"**的过程。二者顺序固定：先认证、后授权——系统必须先确定请求者是谁，才能查它有没有权限。

进公司大楼，前台核对你的工牌照片是不是你本人，这是认证；工牌能刷开哪几层楼的门禁，这是授权。同一个人（认证结果相同）在不同系统里权限可以完全不同（授权结果不同），所以两者不能合并。最常见的初学者误区是"登录成功 = 有权限"：登录只完成了认证，之后每一次访问资源都还要再做一次授权检查。反过来，很多严重漏洞（越权访问，IDOR）正是"认证做了、授权忘了"——用户 A 登录后把 URL 里的 `id=A` 改成 `id=B` 就读到了 B 的数据，因为服务端只认证了"你是某个登录用户"，却没授权"你能不能看 B 的记录"。

### 16.1.2 识别、认证、授权三步与认证的三类因素

在认证之前还有一步识别（identification）：主体先"声称"自己是谁（给出用户名/账号），认证再"验证"这个声称。因此完整链条是识别 → 认证 → 授权。认证所依据的证据传统上分三类因素：

```
知道的东西（something you know）：口令、PIN、密保问题
拥有的东西（something you have）：手机、硬件密钥、TOTP 生成器
本身的特征（something you are）：指纹、人脸、虹膜等生物特征
```

多因素认证（16.5）要求证据来自**不同类别**才算"多因素"，两个口令不算多因素。初学者容易把"识别"和"认证"混为一谈——输入用户名是识别（声称），输入口令并被核对才是认证（验证）；这也是为什么"用户名是否存在"不该在登录失败时泄露，否则等于把识别环节的信息白送给攻击者去做账号枚举。

### 16.1.3 认证失败作为一类漏洞（OWASP Top 10:2025 A07）

OWASP Top 10:2025 把认证相关缺陷归为 A07「Authentication Failures」（2021 版名为「Identification and Authentication Failures」，2025 版精简了名字），位列第 7。它覆盖约 36 个 CWE，典型包括：允许凭据填充（credential stuffing，用别处泄露的账号口令批量试登）与暴力破解、缺失或可绕过的多因素认证、弱口令策略、明文/弱哈希存储口令、以及会话管理缺陷（如登录后不更换会话 ID，见 16.4 的 CWE-384）。

对初学者，这一节的价值是把后面五节"串起来"：16.3（口令存储）、16.4（会话）、16.5（MFA）都是 A07 的具体防线。要记住 A07 的排名多年来是**下降**的——不是因为攻击变少，而是因为标准化认证框架（OAuth/OIDC、WebAuthn）和 MFA 的普及让开发者少造轮子、少犯错；这恰好说明"别自己发明认证，用成熟标准"本身就是最有效的缓解。

## 16.2 访问控制模型

### 16.2.1 访问控制矩阵与引用监视器

授权的抽象底座是访问控制矩阵（access control matrix，Lampson 1971）：一张以主体（subject，行）为行、客体（object，列）为列的大表，每个格子写明"该主体对该客体允许的操作"（读/写/执行等）。所有具体的访问控制模型都可看成这张矩阵的某种压缩存法或某种填表规则。

```
             file1        file2       process_p
  Alice      {read,write}  {read}      {}
  Bob        {read}        {}          {own}
```

真正在运行时拦截每次访问、对照矩阵放行或拒绝的组件叫引用监视器（reference monitor），它须满足三性质：不可绕过（每次访问都经过它）、防篡改（自身不能被改）、可验证（小到能被审计）。给初学者的直觉是：矩阵是"规则数据"，引用监视器是"执法者"；后面 DAC/MAC/RBAC/ABAC 的差别，本质是"谁来填这张表、按什么规则填"。这张矩阵直接存会极其稀疏且巨大，所以现实里要么按列存（ACL）、要么按行存（capability），见 16.2.6。

### 16.2.2 自主访问控制（DAC）

自主访问控制（Discretionary Access Control, DAC）指资源的**属主（owner）自行决定**把哪些权限授予哪些主体，权限可由属主自主转授。Unix 文件权限（属主/组/其他 × 读/写/执行）与多数数据库的 `GRANT` 是典型 DAC。

DAC 的"自主"是关键词也是软肋：因为普通用户能自己改自己文件的权限、甚至转授给别人，所以一旦某个账号被攻陷或被社工，权限就会不受控地扩散——木马以你的身份运行时，它拥有你能自主授予的一切权限。初学者可把 DAC 理解为"我的东西我做主"，灵活、符合直觉，但不适合需要强制统一策略的高安全场景（那要用 MAC）。

### 16.2.3 强制访问控制（MAC）

强制访问控制（Mandatory Access Control, MAC）指权限由**系统/管理员按全局策略强制决定，属主无权更改**。经典形态是给主体和客体都打上安全标签（如"绝密/机密/公开"），由内核按固定规则裁决，个人不能自主放权。军政系统与 SELinux/AppArmor 是代表。

理解 MAC 要抓住它和 DAC 相反的那一点：DAC 是"属主说了算"，MAC 是"策略说了算，属主也不能破例"。一个常被引用的具体规则族是 Bell–LaPadula 模型（面向机密性）：**不能向上读（no read up）**——低密级主体读不了高密级文件；**不能向下写（no write down）**——高密级主体不能把机密内容写进低密级文件，防止信息泄漏下沉。初学者只需记住 MAC 用"标签 + 硬规则"换取"个人无法绕过"，代价是灵活性差、配置繁琐。

### 16.2.4 基于角色的访问控制（RBAC）

基于角色的访问控制（Role-Based Access Control, RBAC，NIST/INCITS 359 标准化）在主体和权限之间插入一层"角色"：权限先分配给角色，用户再被赋予角色，用户的有效权限 = 其所有角色的权限之并。它把"给每个人单独配权限"变成"给岗位配权限、给人配岗位"。

```
用户 ── 被赋予 ──> 角色 ── 被授予 ──> 权限（对客体的操作）
```

RBAC 之所以成为企业主流，是因为它贴合组织结构、便于管理：新人入职只需分配"财务""客服"等角色，离职收回角色即可，无需逐条改权限；还能表达职责分离（同一人不能同时持有"发起付款"和"审批付款"两个冲突角色）。初学者要注意 RBAC 的边界：它按"你是什么角色"决策，无法直接表达"上班时间才能访问""只能改自己部门的单据"这类依赖上下文/属性的规则——那要靠 ABAC。

### 16.2.5 基于属性的访问控制（ABAC）

基于属性的访问控制（Attribute-Based Access Control, ABAC，NIST SP 800-162）用一组布尔规则对**主体属性、客体属性、操作、环境属性**求值来决定放行，是四者中表达力最强的。它能写出这样的策略：

```
IF 主体.部门 == 客体.部门 AND 主体.级别 >= 客体.密级
   AND 环境.时间 ∈ 工作时间 AND 环境.来源IP ∈ 公司网段
THEN 允许 读
```

ABAC 的强大来自"任意属性任意组合"，因此能表达 RBAC 表达不了的细粒度、上下文相关策略（时间、地点、设备、数据敏感度）。代价是复杂：策略多了难以推理"某人到底能访问什么"、难以审计、易出现规则冲突。给初学者的定位：RBAC 是 ABAC 的一个特例（把"角色"当成一个属性即可），实践中常 RBAC 打底、ABAC 处理例外，两者混用。

### 16.2.6 ACL 与能力（capability）

ACL（Access Control List）和能力（capability）是把 16.2.1 那张访问控制矩阵落地存储的两种对偶方式。ACL 按**客体（列）**存：每个资源挂一张"谁能对我做什么"的列表（Unix 文件的权限位、云资源的资源策略）。能力按**主体（行）**存：每个主体持有一串"我能对哪些资源做什么"的不可伪造令牌（capability），出示令牌即获得对应访问（如带签名的 URL、OAuth 的 bearer token、Unix 文件描述符）。

```
ACL：      资源 R 记录 { Alice:读写, Bob:读 }          —— 按客体聚合
capability：Alice 持有 { R:读写, S:读 } 这串令牌         —— 按主体聚合
```

两者的取舍很对称，初学者可按几个维度记：回答"谁能访问 R"时 ACL 天然容易（直接看 R 的列表）、capability 难（要扫所有主体）；撤销权限时 ACL 容易（从列表删一行）、capability 难（令牌已散出去，要么加过期时间、要么维护吊销表）；委托/转授时 capability 天然容易（把令牌递给别人即可）、ACL 需改列表。ACL 依赖"每次访问先认证主体身份再查表"，capability 则是"持有即证明"，所以 capability 的令牌一旦泄露就等于权限泄露——这正是 16.6 里 bearer token 必须走 HTTPS、设短有效期的原因。

## 16.3 口令存储：加盐、慢哈希、抗彩虹表

### 16.3.1 为什么不能明文存、也不能只做一次普通哈希

口令绝不能明文存：数据库一旦泄露（这几乎是常态假设），所有账号立刻沦陷，且用户常跨站复用同一口令，泄露会外溢到别的网站。直觉上想到"存哈希值"，但只做一次快速哈希（如单次 SHA-256）也不够——因为口令空间小、人类口令可预测，攻击者能用极快的 GPU 每秒算几十亿次哈希去逐个试（离线暴力/字典攻击），快速哈希等于给攻击者送算力。

所以现代口令存储要同时满足两点：**加盐**让预计算失效（16.3.2），**慢/内存硬**让每次尝试都昂贵（16.3.3）。初学者要建立的核心认知是：口令哈希的目标和普通哈希相反——普通哈希越快越好，口令哈希要**故意慢**，慢到攻击者离线爆破不划算，而单个用户登录时的一次计算延迟（几十到几百毫秒）可以接受。

### 16.3.2 加盐（salt）与抗彩虹表

盐（salt）是给每个口令**各自随机生成的、唯一的**一段值，和口令拼接后再哈希，盐本身明文存在数据库里（它不是密钥，无需保密）。存储形如：

```
salt = random_bytes(≥16)
stored = salt , H(salt ‖ password)     # 盐与哈希一并存
```

盐的作用是击穿"预计算"这条捷径。彩虹表（rainbow table）是攻击者事先为海量常见口令算好哈希、以时间换空间压缩存储的大表，拿到泄露哈希后直接查表反查口令；还有更简单的"哈希-口令"字典。加了唯一盐后，同一个口令在每个用户处的哈希都不同，攻击者预先算好的表全部作废——他必须针对每个盐、每个用户单独重算，预计算优势归零。初学者常见两个误区：一是"全站用同一个盐"——那又能被预计算（针对这一个盐建表），盐必须**每口令唯一**；二是"盐要保密"——不必，盐防的是预计算/批量摊薄，不是防知道盐的人，它明文存无妨。（想额外防"知道盐也难算"的，是 pepper，见 16.3.4。）

### 16.3.3 慢哈希与内存硬函数：bcrypt / scrypt / Argon2

加盐挡住预计算后，还要让**每一次**尝试都昂贵，这就是慢哈希/口令哈希函数（password hashing function）。它们内建盐、内建可调"代价参数"，让攻击者的离线爆破成本随参数线性/指数上升。OWASP Password Storage Cheat Sheet（核实 2026-07-30）的现行推荐与参数：

```
Argon2id（首选）：m=19 MiB, t=2, p=1（最低）；或 m=47 MiB, t=1, p=1 等价档
scrypt（次选）：  N=2^17, r=8, p=1（最低）；内存 128 MiB
bcrypt（仅遗留）：work factor（cost）≥ 10；输入上限 72 字节
```

三者的分工可以这样直观地记。bcrypt（基于 Blowfish）只可调 CPU 代价（cost 每 +1 迭代翻倍），出现最早、最成熟，但**不是内存硬**，对拥有大量并行 GPU/ASIC 的攻击者防御力弱，且有 72 字节截断这个坑（超过 72 字节的部分被忽略）。scrypt 引入"内存硬"——强制占用大量内存，让攻击者没法靠堆便宜的并行核来摊薄，因为内存又贵又难并行。Argon2（2015 年口令哈希竞赛冠军）是当代首选，其 `Argon2id` 变体同时抗 GPU（内存硬）和抗侧信道，三个参数分别调内存 `m`、迭代 `t`、并行 `p`。初学者选型只需记："新系统用 Argon2id，其次 scrypt，只有维护老系统才用 bcrypt，纯 PBKDF2 仅在需要 FIPS 合规时用"（见 16.3.5）。参数不是越大越好——要在"登录延迟用户可接受"和"攻击者爆破足够贵"之间调，OWASP 给的是**最低**基线，硬件变强时应上调，属 ⚙演进快项。

### 16.3.4 pepper（胡椒）

pepper 是在盐之外再加的一段**全站共享、且不存进数据库**的秘密（存在应用配置/环境变量/HSM/密钥库里）。它通常以带密钥的方式混入，例如对口令哈希再做一层 HMAC：

```
stored = salt , HMAC(pepper_key, H(salt ‖ password))     # pepper 单独保管，不入库
```

pepper 与 salt 的关键区别：salt 唯一且明文入库，防的是预计算；pepper 全站共享且**独立于数据库保管**，防的是"只泄露了数据库、没拿到应用密钥"的场景——此时攻击者拿到全部盐和哈希也算不动，因为缺 pepper。初学者要注意 pepper 是"纵深防御的加分项"而非替代品：它只在"数据库和 pepper 分开存、且攻击者只拿到其一"时有价值；若服务器被整体攻陷（pepper 也泄），它就失效。因此顺序是先把盐 + Argon2id 做对，再考虑 pepper。

### 16.3.5 PBKDF2 与合规场景

PBKDF2（Password-Based Key Derivation Function 2，RFC 8018）通过把底层 HMAC 迭代成千上万次来拉长计算时间，是最老牌的慢哈希。它**只调 CPU 迭代次数、不是内存硬**，因此抗 GPU 能力最弱，但因为只依赖标准 HMAC，是 FIPS-140 认可的算法，在需要合规的场景仍在用。OWASP 现行迭代数（核实 2026-07-30）：

```
PBKDF2-HMAC-SHA256：600,000 次
PBKDF2-HMAC-SHA512：210,000 次
PBKDF2-HMAC-SHA1：  1,300,000 次（仅遗留）
```

PBKDF2 也是本报告的教学级实证载体，因为它在基线 Python 内置库里就有（`hashlib.pbkdf2_hmac`），无需第三方包：

```
import hashlib, os
salt = os.urandom(16)
dk = hashlib.pbkdf2_hmac("sha256", b"correct horse", salt, 600_000)
# 每次登录用相同 salt 与迭代数重算，比对 dk 是否相等；迭代数越大越慢越贵
```

初学者应把 PBKDF2 与 Argon2 的关系记成"同一目标、不同代价维度"：PBKDF2 只堆 CPU 时间，Argon2/scrypt 还堆内存，而内存是抵抗专用硬件的关键，所以非合规场景优先内存硬函数。

### 16.3.6 口令策略：NIST SP 800-63B-4（⚙演进快·锚 2026-07-30）

现代口令**策略**（对用户提什么要求）在 NIST SP 800-63B-4（2025 年定稿）里有一次方向性转变，与旧观念相反，属演进快项。要点（核实 2026-07-30）：

```
最短长度：用户自选口令 ≥ 8 字符（推荐更长）；验证方须支持 ≥ 64 字符与空格、可打印字符
不强制组合复杂度：不再要求"必须含大小写+数字+符号"
不定期强制改密：不再要求周期性改密，仅在有泄露证据时才强制
必查泄露口令：新设/改密时比对"已知常见/已泄露口令"黑名单并拒绝
```

强制复杂度和频繁改密看似更安全，实则逼用户造出 `P@ssw0rd1!` 这类可预测变体、并把密码写便签或在各站复用，反而更弱；NIST 转而鼓励长口令/口令短语 + 泄露检查 + 支持口令管理器。这条是"策略随研究演进"的典型，务必标 ⚙演进快·锚 2026-07-30——它是 800-63 的第 4 版（-4），与广为流传的旧版（要求复杂度/定期改密）结论相反，引用时要认版本。

### 16.3.7 离线攻击谱系：字典 / 暴力 / 彩虹表 / 凭据填充

把针对口令的攻击摆在一起才好理解上面各道防御各挡什么。字典攻击试常见口令与其变体；暴力攻击穷举字符组合；彩虹表用预计算的哈希表反查（被盐挡住）；凭据填充（credential stuffing）用**别处泄露的真实账号-口令对**批量试登你的站，赌用户跨站复用。

对应关系可这样记：加盐（16.3.2）废掉彩虹表/预计算；慢哈希（16.3.3）把字典/暴力的单次成本抬高到不划算；而凭据填充**绕过**了口令存储强度——因为攻击者用的是明文正确口令，此时唯一有效防线是限速/风控 + 多因素认证（16.5）+ 检查泄露口令（16.3.6）。这解释了为什么"口令存得再好也不够"，必须叠加 MFA。

## 16.4 会话管理：会话固定（CWE-384）与令牌管理

### 16.4.1 会话与会话令牌为何存在

HTTP 本身无状态，每个请求互不相识；但登录是"一次认证、多次访问"的，所以服务端在认证成功后创建一个会话（session），发给客户端一个会话令牌（session token / session ID），此后客户端每个请求都带上它，服务端据此认出"这是刚才登录的那个人"，无需每次重新输口令。这枚令牌通常放在 cookie 里。

**会话令牌在有效期内等价于口令**——谁持有它谁就是那个已登录用户（它就是 16.2.6 的 capability/bearer token）。因此保护它的三个基本 cookie 属性要记牢：

```
HttpOnly：禁止 JavaScript 读取该 cookie，降低 XSS 偷令牌的危害
Secure：  仅经 HTTPS 发送，防明文网络被嗅探
SameSite：限制跨站携带该 cookie，缓解 CSRF（Lax/Strict/None）
```

### 16.4.2 会话固定攻击（session fixation, CWE-384）与防御

会话固定（session fixation, CWE-384）是这样一种攻击：攻击者先取得一个合法的会话 ID，设法让**受害者用这个已知的 ID 去登录**；由于很多系统登录后不更换会话 ID，受害者认证成功后，这个"攻击者早就知道的 ID"就变成了一个已认证会话，攻击者拿着同一个 ID 即可冒充受害者。攻击流程分行看清：

```
1. 攻击者从站点获取一个有效但未认证的 session ID = S
2. 攻击者诱导受害者带着 S 去登录（如发含 S 的链接、或注入 cookie）
3. 受害者输入口令认证成功，服务端把 S "升级"为已认证会话（未更换 ID）
4. 攻击者用他早已知道的 S 直接访问，即为已登录的受害者
```

**在权限边界跨越时（尤其登录成功那一刻）重新生成一个全新的会话 ID，并作废旧的**。这样即使攻击者预置了旧 ID，登录后它立刻失效，攻击者手里的 ID 变成废票。初学者要理解会话固定与会话劫持的区别：劫持是"事后偷到你的令牌"，固定是"事先塞给你一个我知道的令牌"；前者防在"别让令牌泄露"（16.4.1 的属性 + HTTPS），后者防在"登录后换 ID"。CWE-384 被明确收录在 OWASP Top 10:2025 A07 里。

### 16.4.3 会话令牌的生成与保管

会话令牌必须**不可预测**：由密码学安全随机数生成、足够长（一般 ≥ 128 位熵），否则攻击者能猜测或枚举有效会话（这也是一种 A07 缺陷）。绝不能用可预测的东西当会话 ID（如自增数字、用户名 + 时间戳）。服务端侧应能随时使某个会话失效（登出、异常时踢下线）。

对初学者来说，会话 ID 的安全**全靠随机性**——它没有口令那样的"慢哈希"保护，因为它是随机的高熵串，天然无法字典攻击，但一旦可预测就等于门户大开。所以两条底线：用 CSPRNG（而非普通 `rand()`）、长度足够。令牌在数据库侧存储时也宜只存其哈希，避免"读库即得所有活会话令牌"。

### 16.4.4 会话生命周期：超时、登出与失效

一个会话应有明确的生命周期以缩小被盗后的暴露窗口：空闲超时（idle timeout，一段时间无操作即失效）、绝对超时（absolute timeout，无论活跃与否到期即失效）、以及可靠的登出（服务端真正销毁会话，而非只删客户端 cookie）。敏感操作（改密、转账）宜要求重新认证（step-up）。

初学者常见错误是"登出只在前端删了 cookie，服务端会话还活着"——若令牌之前已泄露，攻击者仍能用它访问。正确做法是登出时服务端主动作废会话记录。超时的取舍是安全 vs 体验：银行几分钟就登出，社交应用可能几周，取决于资产敏感度。这些机制共同把"令牌泄露"的后果从"永久沦陷"压缩为"一个有限窗口"。

#### 来源与时效（本小主题末集中列，不逐项脚注）
- 锚点：OWASP Session Management Cheat Sheet（会话 ID 熵 ≥128 位、CSPRNG、HttpOnly/Secure/SameSite、登录后 renew ID 防固定、空闲/绝对超时、服务端登出），核实 2026-07-30。
- 锚点：MITRE CWE-384「Session Fixation」（定义、攻击流程、登录后重生成会话 ID 的缓解），https://cwe.mitre.org/data/definitions/384.html ；OWASP Top 10:2025 A07（会话复用/固定纳入），核实 2026-07-30。
- 交叉核对：CWE-384 的攻击步骤与"登录时更换会话 ID"防御在 MITRE、OWASP Session Management Cheat Sheet、CS155 三处一致；SameSite 缓解 CSRF 的定位与 15 章 Web 报告一致，无冲突。

## 16.5 多因素认证：MFA、TOTP、FIDO/WebAuthn

### 16.5.1 MFA 的概念与"抗钓鱼"分级

多因素认证（Multi-Factor Authentication, MFA）要求用户出示来自**两类或更多不同因素**（16.1.2 的知道/拥有/是）的证据，使得攻破单一因素（如口令泄露）不足以登录。它是抵御凭据填充/口令泄露（16.3.7）的关键第二道防线。

但初学者最该记住的新认知是"MFA 分强弱、并非都抗钓鱼"：

```
弱（可被钓鱼/中继）：短信 OTP、邮件 OTP、TOTP 验证码、推送批准
强（抗钓鱼）：      FIDO2/WebAuthn（passkey）、绑定源域的公钥认证
```

之所以有强弱之分：TOTP/短信这类"把一串码输进网页"的方式，攻击者可以搭一个假站做中间人，把用户输入的实时验证码转发给真站（实时钓鱼/中继），MFA 照样被绕过。而 WebAuthn（16.5.4）把"当前站点的域名"绑进签名里，假站拿到的响应对真站无效，从原理上抗钓鱼。这也是 NIST 与业界推 passkey 取代 OTP 的原因。

### 16.5.2 HOTP 与 TOTP：一次性口令的构造

一次性口令（OTP）用一个只有用户设备和服务器共享的密钥，配合一个"计数器"生成短暂有效的验证码。HOTP（RFC 4226）用**递增事件计数器**，TOTP（RFC 6238）把计数器换成**当前时间除以时间步长**，于是验证码每隔固定时间（通常 30 秒）自动翻新。核心公式分行：

```
HOTP(K, C) = Truncate( HMAC-SHA1(K, C) )         # C 为 8 字节计数器
TOTP(K)    = HOTP( K, floor((T - T0) / X) )       # T=当前 Unix 时间, T0=0, X=30s
```

Truncate 是"动态截断"：取 HMAC 输出最后一字节的低 4 位作偏移，从该偏移取 4 字节、清最高位得一个 31 位整数，再对 `10^digits` 取模得到 6 或 8 位数字码。RFC 6238 Appendix B 给了测试向量，本报告用基线 Python 内置 `hmac`/`hashlib` 自实现并跑通（仓库外 scratchpad），得到与 RFC 完全一致的真实输出：

```
seed(SHA1) = ASCII "12345678901234567890"（20 字节）, X=30, digits=8
T=59         -> 94287082
T=1111111109 -> 07081804
T=1234567890 -> 89005924
T=2000000000 -> 69279037   （四条均与 RFC 6238 Appendix B 一致）
```

初学者要理解 TOTP 的两个工程细节：服务器校验时通常允许前后一两个时间步的"漂移"以容忍时钟不同步；因为码短、有效期短，TOTP 抗"离线爆破"靠的是"过期就作废"而非哈希强度。它比短信 OTP 好在验证码不经网络传输（本地生成），但仍属可被实时钓鱼中继的"弱 MFA"（16.5.1）。

### 16.5.3 短信 OTP 的固有弱点

把 OTP 用短信下发（SMS OTP）是最普及但最弱的一档 MFA。它的弱点是结构性的：短信可被 SIM 交换（攻击者社工运营商把你号码转到他卡上）、SS7 电信信令攻击拦截、以及和 TOTP 一样的实时钓鱼中继；NIST 800-63 早期版本就已"限制/不推荐"把短信作为受限的带外认证方式。

短信 OTP 聊胜于无（好过只有口令），但只要能用 TOTP 就别用短信，能用 WebAuthn/passkey 就别用 TOTP。这是一条清晰的强度阶梯。

### 16.5.4 FIDO2 / WebAuthn / CTAP：抗钓鱼的公钥认证

FIDO2 是抗钓鱼 MFA 的现代标准，由两部分组成：W3C 的 WebAuthn（浏览器/网站侧 JS API）+ FIDO 联盟的 CTAP（Client to Authenticator Protocol，浏览器与硬件密钥/手机等认证器之间的协议）。它用**公钥密码**取代共享口令：注册时认证器为该网站生成一对密钥，公钥交给网站、私钥永不离开认证器；登录时网站发随机挑战，认证器用私钥签名。登录流程分行：

```
1. 服务器（依赖方 RP）发送随机 challenge
2. 浏览器把 challenge + 当前站点来源(origin/RP ID) 交给认证器
3. 用户本地授权（触摸密钥/指纹/PIN），认证器用该站私钥对 (challenge, origin, ...) 签名
4. 服务器用注册时存的公钥验签，并核对签名里的 origin 是否为本站
```

抗钓鱼的关键就在第 3、4 步把"当前站点来源"绑进签名：假冒站 `evil.com` 拿到的签名带的是 `evil.com` 的 origin，真站 `bank.com` 验签时 origin 不符即拒——所以即便用户被骗到假站，凭据也无法被中继到真站。这与 TOTP 的"把码抄进任意站都能用"形成鲜明对比。初学者要记住三点：私钥不出设备（泄库也偷不到私钥）、每站独立密钥对（不可跨站关联/追踪）、来源绑定带来抗钓鱼；这三条是 WebAuthn 优于口令 + OTP 的根本。WebAuthn Level 2 已是 W3C Recommendation；Level 3 截至 2026-07-30 处于 Candidate Recommendation（草案推进中），属 ⚙演进快。

### 16.5.5 passkey：同步式与设备绑定式（⚙演进快·锚 2026-07-30）

passkey（通行密钥）是 FIDO2/WebAuthn 凭据面向大众的品牌化叫法，即上节那对"网站专属公私钥"。它分两类：设备绑定式（device-bound，私钥锁死在单个硬件如安全密钥/TPM，不可导出）和同步式（synced，私钥经平台的端到端加密钥匙串在用户设备间同步，如 Apple/Google/Microsoft 账户），后者解决了"设备丢了就登不进"的账号恢复痛点，是当前推广主流。

passkey 的目标是**彻底取代口令**（无口令登录），而不只是当第二因素——它天生抗钓鱼、无共享秘密可泄、无需用户记忆。同步式与设备绑定式的权衡是"便利/可恢复" vs "私钥集中于云端账户的风险"，两者的账号恢复与钓鱼考量不同，WebAuthn L3 专门为同步凭据补了语义。整个 passkey 生态（平台支持、恢复流程、企业策略）2026 年仍在快速演进，务必标 ⚙演进快·锚 2026-07-30，具体平台默认行为引用时需认当时版本。

#### 来源与时效（本小主题末集中列，不逐项脚注）
- 锚点：IETF RFC 6238 (TOTP) 含 Appendix B 测试向量；RFC 4226 (HOTP) 动态截断与公式，核实 2026-07-30。
- 锚点：W3C「Web Authentication (WebAuthn)」Level 2 (Recommendation) 与 Level 3 (Candidate Recommendation, 2026)；FIDO Alliance CTAP 与 passkey 文档（公钥挑战-响应、origin/RP ID 绑定抗钓鱼、同步 vs 设备绑定），https://www.w3.org/TR/webauthn-3/ ，核实 2026-07-30，⚙演进快。
- 锚点：NIST SP 800-63B-4（认证器强度、限制短信 OTP、抗钓鱼认证器）；OWASP Authentication Cheat Sheet（MFA 分级、TOTP/WebAuthn），核实 2026-07-30。
- 本机实证：基线 Python 3.11.15 内置 `hmac`+`hashlib` 自实现 TOTP，四条时间点输出（94287082/07081804/89005924/69279037）与 RFC 6238 Appendix B（SHA-1 列）逐一吻合（仓库外 scratchpad，跑完即清）。
- 交叉核对：TOTP 公式与测试向量以 RFC 6238 一手为准并经本机实证坐实；"短信 OTP 弱/WebAuthn 抗钓鱼"结论在 NIST 800-63B-4、CS155、FIDO 官方三处一致，无冲突。WebAuthn L3 状态为草案(CR)，硬标 ⚙演进快，不当作已定标准引用。

## 16.6 联合身份与令牌：OAuth2/OIDC、JWT 及其陷阱

### 16.6.1 联合身份与单点登录的动机

联合身份（federated identity）指用户不必在每个应用各建账号，而是由一个受信任的身份提供方（IdP）统一认证，各应用（依赖方）信任 IdP 的结果，从而实现单点登录（SSO，一次登录访问多个应用）与"用 Google/Apple 账号登录"。它把认证这件最容易做错的事集中给专业方，呼应 16.1.3"别自己造认证轮子"。

初学者要先分清两个目标经常被同一套协议承载但本质不同：授权委托（我授权某第三方应用**代表我**访问我在另一处的数据，如授权某 App 读我的相册）用 OAuth 2.0；身份认证（我向某应用**证明我是谁**）用 OIDC。混淆这两者正是本节陷阱的根源（16.6.3）。

### 16.6.2 OAuth 2.0 的角色与授权码 + PKCE 流程

OAuth 2.0（RFC 6749）是**授权委托**框架，核心角色：资源所有者（用户）、客户端（想访问数据的第三方 App）、授权服务器（发令牌）、资源服务器（持有数据的 API）。主流且推荐的是授权码流程（Authorization Code）配 PKCE，步骤分行：

```
1. 客户端把用户重定向到授权服务器，附带 state 与 PKCE 的 code_challenge
2. 用户在授权服务器登录并同意授权
3. 授权服务器回跳客户端，带回一个一次性 authorization code
4. 客户端拿 code + code_verifier（PKCE）向授权服务器换取 access token
5. 客户端持 access token 访问资源服务器的 API
```

几个参数的作用要讲清：`access token` 是访问 API 的 bearer 令牌（16.2.6 的能力令牌，持有即权限，故须走 HTTPS、设短期）；`state` 用于把回跳与本次请求绑定，防 CSRF；PKCE（`code_challenge`/`code_verifier`）确保"拿到 code 的必须是发起请求的同一客户端"，防授权码被截获后冒用。初学者要记住授权码流程为何比"直接发令牌"安全：令牌不经浏览器地址栏/前端暴露，而是后台用一次性 code 交换，PKCE 又堵上了 code 泄露的缺口。

### 16.6.3 OAuth 不是认证协议；OIDC 才是

一个高频且危险的误解是"能用 OAuth 登录 = OAuth 做了认证"。其实 OAuth 只发"访问某资源的令牌"，并**不告诉客户端"用户是谁"**，也不保证这个 access token 是**发给当前这个客户端**的。历史上"用 OAuth 自造登录"的应用因此被攻破（如把别的 App 拿到的 access token 拿来冒充登录，token 替换/混淆）。

OpenID Connect（OIDC）是架在 OAuth 2.0 之上的**认证**层：它在返回里加一个 ID Token（一个 JWT），里面有标准化的身份声明（`sub` 用户唯一标识、`iss` 签发者、`aud` 受众/目标客户端、`exp` 过期、`nonce` 防重放）。客户端必须**验证 ID Token 的签名并核对 `aud` 是不是自己、`iss` 是否可信、`nonce` 是否匹配**，才能安全地断定"用户是谁"。初学者结论：要做登录用 OIDC（看 ID Token），要做"代表用户访问 API"用 OAuth 的 access token；不要拿 access token 当身份凭证。

### 16.6.4 JWT 的结构与验证

JWT（JSON Web Token, RFC 7519）是一种自包含的令牌格式，广泛用作 ID Token 和 API 令牌。它由三段 Base64URL 编码、用点连接：

```
header . payload . signature
header  = {"alg":"RS256","typ":"JWT"}      # 签名算法
payload = {"sub":..., "iss":..., "aud":..., "exp":...}   # 声明(claims)
signature = Sign(header ‖ "." ‖ payload, key)            # 对前两段签名
```

它的价值是"自包含 + 可验证"：接收方无需查数据库，验签通过即可信任 payload 里的声明，适合无状态、跨服务传递身份。但初学者要牢记两点：payload 只是 Base64 编码、**不是加密**，任何人都能解开看内容，别往里放敏感数据；令牌的可信**完全依赖签名验证**——不验签或验错，JWT 就是一张任人涂改的明信片。验证必须包含：验签名、核 `exp`（未过期）、核 `aud`（是发给我的）、核 `iss`（可信签发者）。

### 16.6.5 JWT 的常见陷阱

JWT 的坑几乎都出在"验证环节偷懒或被诱导用错密钥"，分行列出：

```
alg:none —— 攻击者把 header 的 alg 改成 "none" 并删掉签名，早期库误当"无需验签"直接放行
算法混淆(RS256→HS256) —— 攻击者把非对称 RS256 改成对称 HS256，
   诱使服务端用"公开的 RSA 公钥"当 HMAC 密钥来验签，而公钥是公开的 => 可伪造令牌
不校验 exp/aud/iss —— 用过期令牌、把发给别的客户端的令牌拿来用、信任任意签发者
把敏感数据放进 payload —— 误以为 JWT 加密了（实为明文可解）
无法即时吊销 —— 自包含令牌在过期前一直有效，泄露后难提前作废（需短期 + 刷新令牌/黑名单）
```

服务端必须**固定并强制预期的签名算法**（不接受 `none`、不让 header 决定用对称还是非对称）、按预期密钥类型验签、严格校验 `exp/aud/iss`（OIDC 还要 `nonce`）、令牌设短有效期并用刷新令牌轮换。`alg:none` 与算法混淆之所以经典，是因为它们把"信任"错误地交给了**攻击者可控的 header**——凡是"让不可信输入决定如何验证它自己"的设计都危险。

### 16.6.6 OAuth 2.1 与安全最佳实践（RFC 9700，⚙演进快·锚 2026-07-30）

OAuth 生态在收敛：OAuth 2.0 Security Best Current Practice（RFC 9700，2025 年发布）与整合中的 OAuth 2.1 草案把多年经验固化为强制项——**弃用隐式流程（Implicit grant）和资源所有者口令凭据流程（ROPC）**，即使单页应用也一律用授权码 + PKCE；强制精确重定向 URI 匹配、强制 PKCE 等。

老教程里的"Implicit 流程直接在 URL 片段返回 access token"已被判定不安全（令牌暴露在浏览器历史/引荐来源），现代一律授权码 + PKCE。OAuth 2.1 尚为草案（截至 2026-07-30 未成正式 RFC），故标 ⚙演进快·锚 2026-07-30；但其收敛的安全实践（RFC 9700）已是当前应遵循的 BCP。

#### 来源与时效（本小主题末集中列，不逐项脚注）
- 锚点：IETF RFC 6749 (OAuth 2.0 角色/授权码流程)；RFC 7636 (PKCE)；RFC 7519 (JWT 结构与声明)；RFC 9700 (OAuth 2.0 Security BCP, 2025，弃 Implicit/ROPC、强制 PKCE)，核实 2026-07-30。
- 锚点：OpenID Connect Core 1.0（ID Token、`sub/iss/aud/exp/nonce`、OAuth 是授权非认证），https://openid.net/specs/openid-connect-core-1_0.html ；OWASP JWT / OAuth2 Cheat Sheet（alg:none、算法混淆、校验 exp/aud/iss、payload 非加密），核实 2026-07-30。
- 锚点：OAuth 2.1 draft（授权码+PKCE 统一、精确重定向匹配），⚙演进快·草案未定型，核实 2026-07-30。
- 交叉核对：alg:none 与 RS256→HS256 算法混淆攻击在 OWASP、多篇安全研究与 JWT 官方最佳实践三处一致；"OAuth 授权 vs OIDC 认证"的区分在 RFC 6749/OIDC Core 一手与 CS155 一致；"弃 Implicit 用授权码+PKCE"在 RFC 9700 与 OAuth 2.1 draft 一致，无冲突。JWT 无法即时吊销为设计取舍（非漏洞），单独记。
