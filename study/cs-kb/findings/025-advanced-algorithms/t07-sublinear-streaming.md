> 流式模型（data stream model）设定：输入是一个长度 n 的序列 a₁, a₂, …, aₙ，逐个到达；算法只能**顺序读一遍**（或极少数遍），可用的工作内存 S 远小于 n（目标是 S = polylog(n) 或 O(1/ε·polylog) 量级），每个元素处理时间要小。因为存不下全部数据，精确回答（如「恰好多少个不同元素」）在这种内存下被证明不可能，所以流式算法几乎都是**随机化 + 近似**：以高概率给出相对误差受控的估计。下文每个算法都要盯住三个量——用了多少空间、单遍还是多遍、误差保证是什么形式。

## 7.1 蓄水池抽样

### 7.1.1 问题设定：单遍、未知长度、等概率

蓄水池抽样（reservoir sampling）解决的问题是：一个长度 n **事先未知**的流逐个流过，只能读一遍，要从中随机抽出 k 个元素，使得最终每个元素被选中的概率都恰好是 k/n，且只用 O(k) 的内存。难点在于「n 未知」——如果 n 已知，直接给每个元素独立以概率 k/n 决定去留即可；但流式场景下你在读到某元素时并不知道后面还有多少，无法预先算出 k/n。

朴素想法「先把整条流存下来再随机抽 k 个」需要 O(n) 内存，当 n 是十亿级日志时根本存不下——这正是流式模型要回避的。蓄水池抽样的巧妙之处是维护一个大小固定为 k 的「蓄水池」，边流边以精心设计的概率替换池中元素，保证**任意时刻**池内都是「到目前为止所见元素的一个均匀 k-子样本」，因此流何时结束都对——这叫算法对流长度的**任意时刻正确（anytime）**性质。

### 7.1.2 Algorithm R（Vitter 1985）与伪代码

经典算法称 Algorithm R。先把前 k 个元素直接放入蓄水池；此后对第 i 个元素（i > k），以概率 k/i 决定「接纳它」，若接纳则从池中**等概率随机挑一个**踢出、换成它。

对 k = 1 的最简形式（抽 1 个元素），规则化为：读到第 i 个元素时，以概率 1/i 用它替换当前保存的元素。伪代码

```
reservoir_sample(stream, k):
    R ← first k items of stream        # 装满蓄水池
    i ← k
    for each next item x in stream:
        i ← i + 1
        j ← uniform random integer in [1, i]
        if j ≤ k:
            R[j] ← x                    # 以概率 k/i 接纳，踢掉第 j 个
    return R
```

关键的一步是替换概率**随 i 增大而减小**（k/i 越来越小），这正是为了补偿「后来的元素本应和先来的元素机会均等，但先来的已经在池里待了更久、被后续踢出的机会也更多」这两股力量，最终让所有元素打平到 k/n。初学者容易写错成「每个新元素都以固定概率替换」——那样越靠后的元素留存概率越高，分布不均匀。

### 7.1.3 等概率性质的归纳证明

要证的命题是，流结束（长度 n）时，前面任一元素 aᵢ 留在蓄水池中的概率为 k/n。用对流长度的归纳。以 k = 1 为例最清楚：读完 t 个元素时，任一元素被保存的概率是 1/t。归纳步——读第 t+1 个元素时，新元素以概率 1/(t+1) 被选中；而某个旧元素继续留存，需要「它原本被保存（概率 1/t）」且「新元素没有替换它（概率 1 − 1/(t+1) = t/(t+1)）」，两者相乘

P(旧元素 t+1 步后仍留存) = (1/t) · (t/(t+1)) = 1/(t+1)

于是所有 t+1 个元素留存概率都是 1/(t+1)，归纳成立。一般 k 的证明同理，只是把「被替换」拆成「本次接纳（概率 k/(t+1)）且恰好挑中它（概率 1/k）」，乘出来仍是 1/(t+1) 的踢出概率，留存概率保持 k/(t+1)。

这条证明的美感在于它是纯组合的、不依赖任何分布假设，且**每一步都保持不变式**「池是当前所见的均匀样本」。可选实测：k = 1、n = 8、20 万次重复，八个位置的经验留存频率均为 0.124–0.126（理论 0.125），均匀性成立。

### 7.1.4 变体：加权抽样与分布式合并

现实里常要**加权**版本（每个元素有权重 wᵢ，希望被选概率正比于权重）。Efraimidis–Spirakis（2006）的算法 A-Res 给每个元素生成一个键 uᵢ^(1/wᵢ)（uᵢ 为 [0,1] 均匀随机数），保留键最大的 k 个，即为按权无放回抽样；它同样单遍、O(k) 内存。另一个实用变体是可**合并（mergeable）**的蓄水池：并行处理多个分片、各自维护带随机键的样本，最后按键归并，天然适配分布式聚合（下游 L6-05）。

初学者只需记住主线不变：无论加权与否，套路都是「给每个元素一个随机优先级、只保留 top-k、优先级设计使留存概率符合目标分布」。等概率版是权重全相等的特例。这些变体是广度点名，工程取舍归下游。

## 7.2 Morris 近似计数

### 7.2.1 动机：用 loglog 位数计到 n

Morris 近似计数（approximate counting，Morris 1978）解决的是：在只有极少位的寄存器里，对一个可能非常大的事件数 n 做近似计数。精确计到 n 需要 ⌈log₂ n⌉ 位；Morris 的技巧是**只存计数器的「量级」而非计数本身**，让寄存器里存的值 C 大约是 log₂(计数)，于是只需约 log₂(log₂ n) 位——loglog 级，这是它相对精确计数的指数级空间节省。

背后的直觉是，与其一个一个数，不如维护一个数量级。当已经数到「大约 2^C」时，再来一个事件对量级的贡献越来越小，所以让计数器**越大越难增长**——增长概率随当前值指数衰减。这样 C 就以对数速度追踪真实计数，用很少的位表示很大的数。代价是估计有随机误差，这是空间换精度的典型交易。

### 7.2.2 算法与估计量

维护一个整数计数器 C，初值 C = 0。每来一个事件，以概率 2^(−C) 把 C 加一（否则不动）。查询时，真实计数的估计为

n̂ = 2^C − 1

因为 C 大约等于 log₂(真实计数)，所以 2^C 还原出量级，减 1 是使其无偏（下条证明）。存的是 C 而非 n̂，故寄存器只需容纳 C ≈ log₂ n，即 O(log log n) 位。

举个最小例子，数到 3 时 C 期望在 2 附近（2² − 1 = 3）。这里增量是**随机**的——同一条长度 n 的流跑两次，得到的 C 可能不同，n̂ 是一个随机变量；单次运行的估计可能偏大或偏小，靠期望无偏和多份平均来控制（7.2.4）。一个常见易错点是把增量概率记错——它是 2^(−C)（当前计数器值），不是 2^(−n) 或固定值。

### 7.2.3 期望无偏：E[2^C] = n + 1

设 Cₙ 为 n 个事件后的计数器值，令 Xₙ = 2^(Cₙ)。核心引理是

E[2^(Cₙ)] = n + 1

于是 E[n̂] = E[2^(Cₙ) − 1] = n，估计量无偏。证明只需一步条件期望：给定 Cₙ，下一个事件让 C 加一的概率是 2^(−Cₙ)，故

E[X_{n+1} | Cₙ] = 2^(−Cₙ)·2^(Cₙ+1) + (1 − 2^(−Cₙ))·2^(Cₙ) = 2^(Cₙ) + 1

两边取期望得递推 E[X_{n+1}] = E[Xₙ] + 1，配合 E[X₀] = 2⁰ = 1，归纳出 E[Xₙ] = n + 1。

这里的漂亮之处在于「增长概率 2^(−C)」被精确设计成让每一步期望恰好增加常数 1——这正是选这个概率而非别的值的原因。可选实测：n = 10000、4000 次重复，平均估计 9933（理论 10000），无偏性成立。

### 7.2.4 方差、相对误差与改进（Morris+）

无偏不等于准。基础 Morris 计数器的方差约为 Var[2^(Cₙ)] ≈ n²/2，故相对标准误约

rel-SE ≈ 1/√2 ≈ 0.707

即单个计数器的估计典型有约 ±70% 的相对波动——太粗。两种正交的改进：其一，跑 s 个独立计数器取平均，方差降为 1/s，相对误差降到约 1/√(2s)；其二，改用底数 a 的推广（Morris+/Morris++）——以概率 a^(−C) 增量、估计 (a^C − 1)/(a − 1)，a 越接近 1 增长越平滑、方差越小，但寄存器位数增加，是精度与空间的旋钮。

初学者抓住两点。第一，无偏（期望对）与低方差（单次准）是两件事，Morris 天然有前者、要靠平均或调 a 换后者。第二，即便用了改进，寄存器仍是 O(log log n + log(1/ε)) 量级，相对精确计数的 O(log n) 仍是指数节省——这就是为何它在需要海量并行小计数器的场景（如概率数据结构、某些 sketch 的内部计数）仍有价值。可选实测：单计数器 rel-SE 实测 0.713，与 1/√2 = 0.707 吻合。

- 锚点：Morris《Counting Large Numbers of Events in Small Registers》CACM 21(10), 1978（原始算法）；Flajolet《Approximate counting: a detailed analysis》(BIT 25, 1985)（方差与无偏的严格分析，给出 E[2^C]=n+1 与方差 ≈ n²/2）；核实 2026-07-30。二源在无偏性与方差量级上一致。

## 7.3 Count-Min Sketch

### 7.3.1 数据结构：d × w 计数器阵与 d 个哈希

Count-Min Sketch（CM sketch，Cormode–Muthukrishnan 2005）估计流中每个元素的**频数**（某键出现了多少次），只用亚线性空间。结构是一张 d 行 w 列的整数计数器表，初值全 0，配 d 个**两两独立**的哈希函数 h₁,…,h_d，每个把键映到 {1,…,w} 的一列。参数取

w = ⌈e/ε⌉，d = ⌈ln(1/δ)⌉

其中 ε 是相对误差参数、δ 是失败概率，总空间 O((1/ε)·ln(1/δ)) 个计数器——与不同键的数量无关，这是它相对「精确哈希表存每个键计数」的关键节省。

直觉上，每一行都是一个「有冲突的计数表」——不同键可能哈希到同一列、共享计数器，导致高估；用 d 个独立行、查询取最小，把「所有行都撞车」的概率压到 δ 以下。可以类比 Bloom filter（也是多哈希多位）但存的是计数而非存在位，且回答的是「多少次」而非「在不在」。

### 7.3.2 更新与点查询（取行最小值）

更新时，键 x 到达（或频数增加 c），就对每一行 j 把第 j 行第 hⱼ(x) 列的计数器加 c。查询键 x 的频数时，取**所有行对应计数器的最小值**

f̂(x) = min_{j=1..d} CM[j][hⱼ(x)]

取最小而非平均或求和，是因为每个计数器只会因冲突被**别的键加高**、绝不会被减低，所以每一行给的都是「真值 + 非负冲突噪声」，其中最小的那个噪声最少、最接近真值。

举个最小例子，两个键 x、y 在第 1 行撞到同一列，则该列计数器 = f(x)+f(y)，查 x 时这一行高估了 f(y)；但只要还有某一行 x 和 y 没撞车，那一行就给出无噪声的 f(x)，取 min 就命中它。一个易错点是 CM sketch 只适用于**非负**更新（计数只增）的基本版；带删除（负更新）时 min 不再是上界，要改用 Count-Sketch（见 7.3.4）。

### 7.3.3 单侧高估误差界

CM sketch 的估计**永不低估**，且高估量以高概率受控。核心保证可写成，对任意键 x，

f̂(x) ≥ f(x)   （恒成立，单侧高估）

且

P[ f̂(x) ≤ f(x) + ε·‖f‖₁ ] ≥ 1 − δ

其中 ‖f‖₁ = Σ_y f(y) 是所有频数之和（即流的总长度 n）。也就是说估计的绝对误差以概率 1−δ 不超过 ε·n。

证明骨架很短，用得上先修的 Markov。单行看，键 x 那个计数器等于 f(x) 加上「所有哈希到同列的其他键的频数和」，后者的期望是 ‖f‖₁/w = ε·‖f‖₁/e（因为 w = e/ε）。由 Markov，单行噪声超过 ε·‖f‖₁ 的概率 ≤ 1/e。d 行独立，取 min 要全部超标才失败，概率 ≤ (1/e)^d = e^(−d) ≤ δ（因 d = ln(1/δ)）。初学者关键领会：误差是**加性**的、正比于流总量 ‖f‖₁ 而非该键自身频数——所以 CM 对**高频键（heavy hitters）估得准**（ε·n 相对它们小），对稀有键的相对误差可能很大。

### 7.3.4 与 Count-Sketch、Bloom filter 的辨析及应用

同族的 Count-Sketch（Charikar–Chen–Farach-Colton 2002）在更新时额外乘一个 ±1 的哈希符号、查询取**中位数**，得到的是**无偏、双侧**误差（可正可负），界与 ‖f‖₂ 相关而非 ‖f‖₁，且天然支持负更新（可删除）。对比记忆：CM = 取 min、单侧高估、界随 ‖f‖₁、只增；Count-Sketch = 取 median、双侧无偏、界随 ‖f‖₂、可增可减。Bloom filter 则只答「在/不在」，是频数=0/>0 的退化情形。

典型应用是**找 heavy hitters**（频数超过 φ·n 的键）与流式频数直方图：因为 CM 对高频键估得准且空间与键数无关，配一个候选堆就能单遍找出频繁项，广泛用于网络流量监控、数据库查询计数（下游 L6-04）。初学者只需记住选型主线：只增计数、能容忍单侧高估、想省空间 → CM；需要删除或要无偏估计 → Count-Sketch。

## 7.4 HyperLogLog

### 7.4.1 问题：单遍估基数（去重计数）

HyperLogLog（HLL，Flajolet 等 2007）估计流中**不同元素的个数**（基数 cardinality，即 COUNT DISTINCT），用极小内存。精确去重要存所有见过的键，内存正比于基数；HLL 只需约 O(m) 个小寄存器（每个几位），就能估到十亿级基数、相对误差百分之几，内存以 KB 计。这是它在 Redis、Presto、BigQuery 等广泛部署的原因。

直觉源头是一个概率观察：把每个元素哈希成一串均匀随机比特，看其二进制前导零的最大个数。如果见过很多不同元素，就更可能出现「很长的前导零串」——前导零达到 ρ 的概率是 2^(−ρ)，所以观测到的最大前导零长度 R 大致是 log₂(不同元素数)，于是 2^R 反推基数。这与 Morris「用量级代替计数」同源，但这里量级来自**哈希值的极端统计**，且对重复元素天然免疫（同一元素哈希值相同，不改变最大前导零），故估的是去重数而非总数。

### 7.4.2 算法：分桶 + 前导零

HLL 用 m = 2^b 个寄存器。每个元素哈希成比特串后，取**前 b 位作为桶号**选一个寄存器，剩余位里数**前导零个数 + 1**记作 ρ，用它更新该桶

M[bucket] ← max( M[bucket], ρ )

即每个桶只保留「落进本桶的元素中，最大的前导零长度」。用 m 个桶而非单个观测量，是为了对 m 个独立估计做平均、把方差降下来——这叫**随机平均（stochastic averaging）**，只哈希一次却得到 m 份观测。

举个最小例子，b = 4 时 m = 16 个桶；哈希值 0001011… 的前 4 位 0001 选中 1 号桶，其余位 011… 的前导零为 1、故 ρ = 2，若大于原值则更新。关键在于每个寄存器只存一个小整数（ρ 最多约 log₂(基数/m)，几位足够），这是空间省到 O(m) 小寄存器的原因。重复元素哈希值相同、ρ 相同，max 不变，故去重自动完成。

### 7.4.3 调和均值估计公式与 α_m

朴素地用 2^(平均 ρ) 会因少数大 ρ 桶造成严重高估（算术均值对离群值敏感）。HLL 的关键改进是用**调和均值**综合各桶，估计式

E = α_m · m² · ( Σ_{j=1}^{m} 2^(−M[j]) )^(−1)

其中 Σ 2^(−M[j]) 的倒数正是调和均值的核心，它压制了大 ρ 离群桶的影响；α_m 是修正系数，纠正调和均值估计的系统偏差。常用取值

α₁₆ = 0.673，α₃₂ = 0.697，α₆₄ = 0.709，α_m = 0.7213 / (1 + 1.079/m)（m ≥ 128）

初学者领会两点：其一，「调和均值 + m² 缩放」是 HLL 相对前身 LogLog（用几何均值、误差 1.30/√m）把误差降到 1.04/√m 的技术核心；其二，α_m 是为消偏而拟合出的常数，不是随手取的，直接照抄论文值即可、不要自行编造。

### 7.4.4 标准误 1.04/√m 与空间

HLL 的相对标准误（relative standard error，估计的相对波动）为

rel-SE ≈ 1.04 / √m

即桶数 m 翻 4 倍，误差减半。这个 1.04 来自方差分析里的常数 β_∞ = √(2·ln 2 − 1) = 1.03896…，是载重数值、锚定 Flajolet 2007。例如 m = 2048（b = 11）时 rel-SE ≈ 1.04/√2048 ≈ 2.3%；每个寄存器约 5–6 位，总空间约 1.5 KB 就能估到远超十亿的基数。

空间与精度的关系一目了然：要相对误差 ε，需 m ≈ (1.04/ε)² 个桶，空间 O((1/ε²)·log log N)（N 为基数上界，log log 来自每个寄存器存 ρ 所需位数）。一个易错点是把 1.04/√m 当成最坏界——它其实是**标准误（一个标准差）**，单次估计有可能偏离更多，是概率意义上的典型误差。可选实测：m = 1024，真实基数 5 万，30 次重复的相对误差标准差实测 0.036，与预测 1.04/√1024 = 0.0325 同量级（实测哈希非理想且重复数少，略偏大，趋势吻合）。

### 7.4.5 小基数与大基数修正

基础估计式在**基数很小**（相对 m）时偏差大：许多桶还是空的（M = 0），此时改用**线性计数（linear counting）**——设空桶数为 V，估计 m·ln(m/V)，在小基数区更准；论文给出经验阈值（约 5m/2）以下切换。在**极大基数**接近哈希空间上限（原论文用 32 位哈希，约 2³²）时，会出现哈希碰撞导致的饱和，需做 2³² 相关的上端修正。Google 的 HyperLogLog++（2013）进一步改用 64 位哈希消除上端修正、并用经验偏差表改良小基数区，是工业主流实现。

初学者只需记住：教科书的核心估计式在「中间量程」准，两端要打补丁；这些补丁是让 HLL 在全量程都可用的工程必需，但不改变 1.04/√m 这个主精度结论。HLL++ 属演进版，细节归下游 L6-04（数据库基数估计）。
