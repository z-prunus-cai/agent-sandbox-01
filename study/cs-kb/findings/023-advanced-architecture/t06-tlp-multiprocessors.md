## 6.1 共享内存结构

### 6.1.1 线程级并行与共享内存多处理器

线程级并行（TLP, Thread-Level Parallelism）指把一个程序拆成多个可同时执行的线程，交给多个处理器核并行推进，从而在指令级并行（ILP）已被榨干、单核提频受功耗墙限制之后继续提升吞吐。本大主题研究的主流载体是**共享内存多处理器**（shared-memory multiprocessor）：多个核共享同一个物理地址空间，任何核用普通 load/store 就能读写同一块内存，线程间通信隐式地通过"写内存—读内存"完成，而不必显式发消息。按 Flynn 分类（CO-8.1）这属于 MIMD（多指令流多数据流）。

对初学者，先把三类并行的分工记清：ILP 是同一条指令流内部找可并行的指令（大主题3/4），DLP 是一条指令作用于一批数据（大主题5 的向量/SIMD/GPU），TLP 是多条独立指令流同时跑。共享内存的关键便利在于"通信免编排"——线程 A 把结果写进变量 x，线程 B 直接读 x 就拿到了，程序员不用写 send/recv。但便利的代价正是本大主题后半段的全部内容：一旦每个核都有自己的私有 cache，同一个 x 可能同时有多份副本，谁看到谁的值、按什么次序看到，就需要硬件（一致性协议、一致性模型）和软件（同步原语）合力保证。

共享内存不是唯一路线。与之对立的是**消息传递**（message passing）：每个节点有私有地址空间，通信靠显式 send/recv（如 MPI，归 L6-06 HPC）。共享内存编程门槛低但扩展到成百上千节点时硬件维护一致性的代价陡增，消息传递反之。本大主题只讲共享内存这一支。

### 6.1.2 集中式共享内存 SMP / UMA

集中式共享内存多处理器，即对称多处理器（SMP, Symmetric Multiprocessor），把所有核接到一条共享互连（经典是共享总线，现代是片上环/网格），共用一块集中式主存。因为每个核到主存的路径对称、访问任一内存地址的延迟都相同，这类结构又称 UMA（Uniform Memory Access，均匀存储访问）。核仍各有私有 L1/L2 cache，靠一致性协议维护副本一致；末级 cache 可能共享。

直觉上 SMP 像"几个人围着一张公共办公桌，谁都伸手就能拿桌上任意文件，拿任何一份文件的距离都一样"。这种对称性让操作系统调度极简单——任何线程放到任何核上，内存性能都一样，不用操心数据在哪。这也是笔记本/手机里的多核（本机 4 个逻辑 CPU、单 NUMA 节点，见 6.1.3 实测）以及中小服务器的主流形态。

SMP 的天花板是那条共享互连的带宽：核越多，争抢同一条总线/内存控制器越激烈，带宽成为瓶颈，一致性流量也随核数上升。所以 UMA 通常只扩展到"单芯片/单插槽的几十核"这个量级；再往上，就得让内存也分散化，进入下面的 NUMA。

### 6.1.3 分布式共享内存 DSM / NUMA

分布式共享内存（DSM, Distributed Shared Memory）把主存拆成多块，各挂在不同的节点（通常一个 CPU 插槽/一个 die 一块），节点间用高速互连相连。地址空间仍是**单一共享的**——任何核仍能用普通 load/store 访问全地址空间——但访问"挂在自己节点上的本地内存"快，访问"挂在别人节点上的远程内存"要走互连、慢。这种延迟随地址所在节点而异的特性叫 NUMA（Non-Uniform Memory Access，非均匀存储访问）。

用办公桌比喻：现在每个人面前有自己的抽屉（本地内存），也能去够别人的抽屉（远程内存），够自己的快、够别人的慢。软件要想跑得快，就得尽量让线程访问自己节点上的数据（NUMA 亲和性 / first-touch 分配策略）。这就是为什么大内存服务器上"线程和它的数据要绑在同一个 NUMA 节点"是性能调优的常识——把工作放错节点，可能凭空慢一大截。

远程访问相对本地访问的额外代价可粗略刻画为

远程延迟 / 本地延迟 = NUMA 比率（NUMA ratio，典型 1.5x～3x，⚙随平台代际变·随时变，具体数值须以厂商手册或实测为准，此处不作现状结论）

本机为受限虚拟机，实测只有单个 NUMA 节点，NUMA 效应无法在此复现：

```
$ lscpu | grep -i numa

NUMA node0 CPU(s):   0-3
```

### 6.1.4 缓存一致性问题的提出

只要每个核有私有 cache，同一内存块就可能同时缓存在多个核里；某核改了自己副本，别的核若还读旧副本，就读到了过时值——这就是**缓存一致性问题**（cache coherence problem）。它不是共享内存的可选烦恼，而是"私有 cache + 共享地址空间"的必然产物：cache 的存在本是为了让每个核就近命中，但也天然制造了副本分歧的风险。

最小例子：核 0 和核 1 都读了变量 x（初值 0），各自 cache 里存了一份 x=0。核 0 执行 `x=1`，只改了自己 cache 里的副本。若无一致性机制，核 1 之后读 x 仍命中自己 cache 的旧值 0，两个核对同一个 x 看法不一致。硬件必须介入：要么在核 0 写时让核 1 的副本失效（写-作废），要么把新值推给核 1（写-更新）——这正是 6.2 嗅探协议要做的事。

一致性要保证的性质可精确表述为两条（本报告 6.2.1 展开）：写传播（一个核的写最终能被别的核看到）+ 写串行化（所有核看到"对同一地址的多个写"的先后次序一致）。初学者此刻只需记住：一致性协议管的永远是"**同一个地址**的多个 cache 副本"这件事，跨不同地址的次序问题是 6.4 的一致性模型，别混。

### 6.1.5 SMP 与 NUMA 的选择与扩展性

集中式（SMP/UMA）与分布式（DSM/NUMA）的选择本质是"编程简单/一致性代价"对"内存带宽/可扩展性"的权衡。核数少时 SMP 用共享总线嗅探即可，简单高效；核数多、跨多插槽时，共享总线扛不住，必须走 NUMA + 目录一致性（6.3）以让一致性流量点对点、可扩展。

可扩展性的量化尺子仍是 Amdahl 定律（大主题1）：并行部分占比 p、处理器数 N 时

加速比 = 1 / ((1 − p) + p / N)

它说明串行部分 (1−p) 会封顶加速比，N→∞ 时加速比上界为 1/(1−p)。对多处理器还要额外扣通信/同步/一致性开销——核越多，远程访问与一致性流量越可能吃掉并行收益。这解释了为什么"堆核"不是免费的：组织形态（SMP vs NUMA）、一致性方案（嗅探 vs 目录）、以及程序的数据布局（NUMA 亲和、避免伪共享）共同决定实际能跑出多少加速比。

## 6.2 嗅探一致性

### 6.2.1 缓存一致性的两条性质

一个存储系统"一致"（coherent），H&P 给出可操作的定义，核心是两条性质。其一是**写传播**（write propagation）：某处理器对地址 X 的写，若之后没有别的写覆盖，最终会被其他处理器的读看到。其二是**写串行化**（write serialization）：所有处理器观察到的"对同一地址 X 的多个写"的先后次序是同一个次序（不会 P1 看到"先 a 后 b"而 P2 看到"先 b 后 a"）。

直觉上，第一条保证"改动传得出去"，第二条保证"大家对这个地址的历史故事讲法一致"。少了写传播，别人永远读不到你的更新（等于没通信）；少了写串行化，两个核会对同一个变量的演变史各执一词，无法推理。注意这两条只约束**单个地址**——它们完全不管"对 X 的写"和"对 Y 的写"之间谁先谁后被看到，那是一致性模型（6.4）的职责。这条边界是初学者最容易越界的地方，务必钉死。

一个隐含前提是读也要及时：在合理时间内，写要传播到其他核（不能无限延迟）。真实协议靠"写时使别人失效/更新"来同时满足写传播与写串行化——串行化通常由一个全局序点（总线的仲裁次序，或目录 home 节点的处理次序）来担保。

### 6.2.2 总线嗅探与两种写策略

在共享总线的 SMP 里，一致性的经典实现是**嗅探**（snooping）：每个核的 cache 控制器都监听（snoop）共享总线上的所有内存事务，看到与自己缓存的块相关的事务就做出反应。总线天然是一个**全序广播**媒介——所有事务串成一条总线次序，这条次序就充当了写串行化的全局序点，这是嗅探协议成立的关键。

写传播有两种策略。写-作废（write-invalidate）：核要写某块前，先在总线上广播一个"作废"（invalidate）信号，令所有其他副本失效，之后本核独占改；别人再读时 miss、重新取到新值。写-更新/写-广播（write-update/write-broadcast）：核每次写都把新值广播到总线，其他持有副本的 cache 就地更新。

```
写-作废：写前令他人副本失效 → 之后本核独占写 → 他人读 miss 再取新值
写-更新：每次写都把新数据广播 → 他人副本就地更新，不失效
```

绝大多数真实系统用**写-作废**，原因是它对总线更省：一段连续写同一块只需第一次作废一次（之后本核已独占，后续写不再上总线），而写-更新每次写都要占总线广播。写-更新只有在"一写多读且读者紧接着就要用"时才可能划算，实际很少用。初学者记住"现代 CPU 一致性 = 写作废嗅探/目录"即可。

### 6.2.3 MSI 基础三态

最小的写作废嗅探协议用三个状态描述每个 cache 块（MSI）：M（Modified，已修改，本核独占且是唯一最新副本，主存过时）、S（Shared，共享，可能多核持有相同的干净副本，与主存一致）、I（Invalid，无效，本副本不可用）。核对块的读写请求 + 从总线嗅探到的他核请求，共同驱动状态转移。

```
本核读 miss  → 发总线读(BusRd)，取块，进 S（若他核在 M 则先写回并降为 S）
本核写       → 若在 S：发作废(BusRdX/Upgrade)使他人失效，升 M；若 miss：发 BusRdX 取块并作废他人，进 M
嗅到他核 BusRd  ：自己在 M → 写回主存并降为 S；在 S → 留 S
嗅到他核 BusRdX ：自己在 M/S → 作废，降为 I（对方要独占写）
```

理解 MSI 的钥匙是"M 意味着独占且脏、S 意味着可共享且干净、I 意味着没有"。写操作必须先取得独占（把所有别的副本打成 I）才能改，这就是写作废的核心动作；读操作可以多核共享（都在 S）。M 与 S 的分野同时兼顾了写串行化（写必先独占，写被总线串成一序）与写传播（他核读到 M 块会触发写回/降级，拿到新值）。MSI 的浪费在下一节修正。

### 6.2.4 MESI 状态机（增 Exclusive）

MSI 有个常见浪费：一个核读入一块、随后想改它（典型的"读后写"，如 `x++`），在 MSI 里即使当时没有别的核持有该块，本核也处在 S，写时仍要发一次总线作废才能升 M——一次其实无人需要的总线事务。MESI 增加 **E（Exclusive，独占且干净）** 状态解决它：当一个核读 miss 且嗅探发现无其他核持有该块时，直接进 E（独占但与主存一致）；此后本核要写，可从 E **静默升到 M，无需任何总线事务**。

```
MESI 四态：
M 已修改  独占、脏（主存过时）、唯一副本
E 独占    独占、干净（与主存一致）、唯一副本
S 共享    可能多核持有、干净
I 无效

关键新增转移：
读 miss 且无他核持有 → E（而非 S）
E 状态本核写 → 静默升 M（无总线事务，这是 E 的全部价值）
E 状态嗅到他核 BusRd → 降 S（出现第二个读者）
```

E 的价值就是省掉"读进来又马上独写"这一极常见模式里的那次多余作废。判断"无他核持有"靠总线上的一根共享信号线（他核嗅到 BusRd 且自己有副本就拉高）。MESI 是 Intel/AMD/ARM 现代 CPU 的一致性基座（各家有增强变体）。初学者只需抓住 E 相对 MSI 的唯一增益：把"独占但干净"从"共享"里分出来，让后续本地写免上总线。

### 6.2.5 MOESI（增 Owned）

MOESI 再加 **O（Owned，被拥有）** 状态，解决 MESI 里另一种浪费：MESI 中一个 M（脏）块若被别的核读，必须先写回主存再降 S（好让主存与共享副本一致）。O 状态允许"块是脏的、但可被多核共享，由某一个核负责持有权威副本并直接供数给其他核，暂不写回主存"。于是脏数据可以核到核直接转发（cache-to-cache），推迟甚至省去写回主存。

```
MOESI 五态 = MESI + O
O 被拥有  脏（主存过时）、但可共享；持有者负责应答他核读请求（直接供数），负责最终写回
M 块被他核读 → 持有者转 O（继续持脏、供数给读者），读者进 S，不立即写回主存
```

O 的收益是在"一写、多核随后读"的共享模式下，省掉每次都写回主存的带宽，让脏块在片上核间直接流转。AMD 处理器用 MOESI，ARM 也有类似的 owner 语义；Intel 传统用 MESI 的增强版（如 MESIF，增 F=Forward 指定一个共享者负责转发）。这里体现一个共性思路：状态越细分，越能省"其实不必要"的总线/主存事务，代价是协议更复杂、状态位更多。初学者掌握 MESI 即够用，MOESI/MESIF 是"谁来供数、要不要立刻写回"这一维度上的进一步优化。

MESI 与 MOESI/MESIF 的差异属实现选择而非语义冲突：它们都满足 6.2.1 的写传播 + 写串行化两条性质，只是在"脏块共享/供数/写回时机"上各有取舍——不是对错之争，是不同厂商的工程权衡，须分账记录。

### 6.2.6 嗅探的扩展性极限

嗅探成立的前提是"存在一个所有核都能监听、且事务全序的广播媒介"。共享总线正是如此，但总线带宽固定，核数一多，一致性事务（每次作废/读 miss 都要上总线且被所有核嗅探）就把带宽吃满，还带来嗅探本身的功耗与 cache 标签端口压力。这使纯总线嗅探难以扩展到很多核。

现代做法有几层缓解：用**分裂事务总线**（split-transaction bus）把"请求"和"响应"解耦以提高并发；用片上**环/网格互连**替代单条总线但仍维持一个全序点；用**嗅探过滤器**（snoop filter，记录哪些块可能被哪些核持有）避免每个核都去查自己 cache 标签。但这些都治标——当规模跨越单芯片/多插槽、需要成百上千核时，广播式嗅探的根本瓶颈无法回避，一致性就得改用**点对点、不广播**的目录协议（6.3）。这条"总线扩展不动 → 转目录"的因果，是理解下一小主题的动机。

#### 来源与时效

- 佐证：P&H《COD》RISC-V 2nd ed, 2020, ch6 §6.5（嗅探一致性、写作废协议、MSI 状态机）；MOESI/MESIF 的厂商归属交叉核对 AMD64 架构手册（MOESI）与 Intel QPI/MESIF 公开描述（此二为厂商实现，标「实现选择」）。
- 一致性：QA 与 COD 对嗅探、写作废、MSI/MESI 表述一致；MOESI vs MESIF 属不同厂商实现选择，非语义冲突，两边都记（AMD=MOESI，Intel=MESI/MESIF）。

## 6.3 目录一致性

### 6.3.1 目录协议的动机

目录协议（directory-based coherence）为大规模、分布式共享内存（NUMA）系统而生。嗅探靠广播 + 总线全序（6.2.6），核多了扛不住；目录把"谁持有某块"的信息**集中记录在一张目录里**，写块时只需查目录、**点对点**通知确实持有该块的那几个核，而不是广播给所有核。通信量从"随核数线性广播"降为"随实际共享者数量"，从而可扩展。

打个比方：嗅探像开会时"任何人要改一份文件就朝全场大喊一声让相关的人作废"，人多了全靠吼会瘫痪；目录像有一个登记册，记着每份文件现在被谁借走了，要改时只私信通知那几个借阅人，与在场总人数无关。这就是目录能扩展而嗅探不能的根本原因。

代价是多一次"查目录"的间接：写请求要先到该块的归属节点（home node）查目录，再由它转发给共享者，延迟比总线直接广播长一跳。所以目录用于"核多到嗅探扛不住"的规模，小规模仍是嗅探更省事。

### 6.3.2 目录结构与块状态

每块内存有一个**归属节点**（home node，通常是该块物理内存所在的 NUMA 节点），其目录项记录这块的全局状态 + 共享者信息。最直接的编码是**全映射目录**（full-map / full bit-vector）：每块配一个 P 位的位向量（presence bits），第 i 位为 1 表示核 i 持有该块副本，外加一个状态位。

块在目录里的全局状态通常三类：

```
U (Uncached)     无人缓存，主存是最新（有的记法叫 Invalid）
S (Shared)       一个或多个核持干净副本，主存最新；位向量标出共享者
M/E (Modified/Exclusive)  恰好一个核独占且脏；位向量标出那唯一的属主(owner)
```

注意这里的状态是"从目录/整块的全局视角"看的，与 6.2 里每个 cache 私有副本的 MESI 状态是两套视角：目录状态说"这块整体上被谁怎么持有"，cache 行状态说"我这一份副本现在能不能读/写"。二者协同：目录是权威登记册，各 cache 行状态是各自的凭证。初学者别把"目录里的 S/M"和"cache 行的 S/M"当成同一个东西——它们描述同一件事的不同侧面。

### 6.3.3 目录协议消息流

目录协议靠节点间点对点消息驱动。以读 miss 与写 miss 两条主线为例（Local=发起核，Home=归属节点，Remote/Owner=远端持有者）：

```
读 miss（Local 要读块 X）：
  Local --Read Req--> Home
  若 X 在 U/S：Home 供数据，Home 把 Local 记入共享者位向量，X 转/留 S
  若 X 在 M（属主是 Owner）：
      Home --Fetch--> Owner
      Owner --回数据--> Home（并降为 S）
      Home --Data--> Local，X 转 S，位向量含 Owner 与 Local

写 miss（Local 要写块 X，需独占）：
  Local --Write Req(RdX)--> Home
  若 X 在 S（若干共享者）：
      Home --Invalidate--> 每个共享者
      共享者 --Ack--> Home（或直接 --> Local）
      收齐 Ack 后 Home --Data+独占权--> Local，X 转 M，属主=Local
  若 X 在 M（旧属主 Owner）：
      Home --Fetch/Invalidate--> Owner
      Owner --回数据+降 I--> Home/Local
      Home --Data--> Local，属主改为 Local
```

关键点：写必须**收齐所有共享者的作废确认**（Ack）才算独占成功——这保证了写传播与写串行化（Home 处理请求的次序充当序点，取代了总线的全序广播）。相比嗅探"一次广播搞定"，目录多了"逐个点对点通知 + 等 Ack"的往返，延迟更长但只涉及真正的共享者，故可扩展。初学者抓住主线即可：读 miss 去 home 要数据（脏则回源属主取），写 miss 去 home 请独占（home 替你逐个作废共享者并等确认）。

### 6.3.4 目录存储开销与优化

全映射目录的软肋是存储：每块内存都要挂一个 P 位向量，开销随核数 P 与内存总量增长。位向量占内存的比例约为

目录开销比例 ≈ P / (块大小(字节) × 8)

例如 P=64 核、块 64 字节时，每块 64 位向量 / (64×8=512 位数据) ≈ 12.5%；核数越多、块越小，这个比例越大，成千上万核时全映射变得不可接受。

几种优化按思路分：**有限指针目录**（limited pointer）——不存 P 位向量，只存少量（如 i 个）指针记"最近的几个共享者"，超出就回退到广播或逐出，赌"实际共享者通常很少"；**稀疏目录**（sparse / cache-like directory）——不给每块都留目录项，只给"当前真被缓存的块"留项，用类似 cache 的结构索引，因为任一时刻被缓存的块远少于内存总块数；**分层/多级目录**——大系统里把目录也做成层次结构。它们共同的赌注都是"共享是稀疏的"：绝大多数块要么没被缓存、要么只被很少几个核共享，为最坏情况（所有核都共享每一块）预留全位向量是浪费。这与 cache 本身"赌局部性"的思路一脉相承。

### 6.3.5 嗅探与目录的对比

两族协议解同一个问题（维护 6.2.1 的写传播 + 写串行化），差别在"如何找到并通知副本持有者"以及"由谁充当写串行化的全局序点"。

```
             嗅探(snooping)            目录(directory)
序点/广播    共享总线全序广播          归属节点(home)串行处理，点对点
通信量       随总核数（人人嗅探）      随实际共享者数
延迟         短（一次广播）            长（查目录+转发+等Ack，多跳）
扩展性       小规模/单芯片/单总线      大规模/多插槽/NUMA
存储开销     低（无集中目录）          高（目录项，需优化）
```

选型逻辑一句话：核少、有共享总线 → 嗅探（简单、低延迟）；核多、分布式 NUMA、无法广播 → 目录（可扩展，代价是延迟与目录存储）。现实大型系统常是**混合/层次**的：插槽内用嗅探，跨插槽用目录（如把每个插槽当一个嗅探域，插槽间挂目录）。二者不是对错而是规模适配，须并置记录，别把"目录一定更好"当结论——小规模上目录反而更慢更费。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch5 §5.4（分布式共享内存的目录一致性：home 节点、目录状态 U/S/M、presence 位向量、读/写 miss 的点对点消息流与 Invalidate/Ack、目录存储开销、有限指针/稀疏目录优化）+ 附录 I（大规模多处理器）；核实 2026-07-30。
- 佐证：P&H《COD》RISC-V 2nd ed, 2020, ch6（目录一致性对大规模系统的必要性，与 QA 一致）；目录开销比例公式由位向量定义直接推得（P 位 / 每块 8×块字节），与教材数量级一致。
- 一致性：两教材对"嗅探不可扩展 → 目录点对点可扩展"的动机、目录状态与消息流表述一致，无冲突。
- 待核：目录消息名（Read Req/Fetch/Invalidate/Ack 等）与状态记法（U/S/M vs 别名）为教材通用抽象，不同实现命名各异，此处采 QA 通用记法，未锁定某具体商用一致性引擎的实际报文格式。

## 6.4 内存一致性模型

### 6.4.1 缓存一致性 vs 存储一致性模型（术语辨析）

这是本大主题最易混的一对术语，必须先钉死。**缓存一致性**（cache coherence，6.2/6.3）管的是"**单个地址**"：保证对同一个变量 X 的多份 cache 副本最终看到一致的值与一致的写次序。**存储一致性模型**（memory consistency model，本节）管的是"**多个地址之间**"：规定一个核对不同变量（X、Y、…）的读写，在别的核看来能以什么先后次序出现，即"内存操作的可见次序"规则。

一句话对照：一致性回答"对同一个 X，大家看到的值和写序一致吗"；一致性模型回答"我先写 X 再写 Y，别的核会不会看到 Y 的新值却还看到 X 的旧值"。二者正交——即使每个地址都完美一致（coherent），跨地址的次序仍可能被硬件重排，需要一致性模型来界定"允许怎么重排"。

最小例子（Dekker/store-buffer 例，两核初值 x=y=0）：

```
核0: x = 1;  r1 = y;
核1: y = 1;  r2 = x;
```

这段代码能否出现 r1==0 且 r2==0？在直觉的"顺序一致"下不能（总得有一个写先发生）；但在允许"store→load 重排"的真实 x86（TSO）上，**可以**出现 r1==r2==0——两个核的 store 都先卡在各自 store buffer 里、还没对对方可见时，两个 load 就都读到了旧值 0。这个结果与缓存一致性毫不矛盾（x 和 y 各自都一致），它纯是一致性模型（跨地址次序）的事。理解这个例子，就抓住了两术语的分界。

### 6.4.2 顺序一致性 SC

顺序一致性（SC, Sequential Consistency，Lamport 1979）是最强、最符合直觉的模型：所有核的所有内存操作存在一个**全局单一次序**，且这个全序里每个核自己的操作保持其程序顺序（program order）。等价说法是"就好像所有核的指令被交错（interleave）成一条串行序列，谁都不许把自己的 load/store 相对程序顺序重排"。

直觉上 SC 就是"多核像一群人轮流操作同一块内存、每人内部不许乱序"。上一节的 store-buffer 例在 SC 下**不可能**出现 r1==r2==0：若真存在这样一个全序，两个 store 里必有一个排在前面，那个先发生的写就会被对应的 load 看到。SC 好推理，但它禁止了许多能提升性能的硬件优化（store buffer、load 提前、写合并等都可能违反 SC），所以**几乎没有现实主流 CPU 提供 SC**——它是理论基准与推理标尺，不是硬件默认。这点初学者常误解：SC 是"理想模型"，不是"x86 的行为"。

### 6.4.3 x86-TSO（总存储序）

x86（Intel/AMD）实际提供的是 **TSO（Total Store Order，总存储序）**，比 SC 略弱。TSO 的唯一放松是引入每核**存储缓冲**（store buffer）：核的 store 先进本核 store buffer 再异步刷入 cache/内存，于是**本核后续的 load 可以越过（bypass）前面尚未刷出的 store**（对不同地址而言），即允许 **store→load 重排**。除此之外，store→store、load→load、load→store 都**不**重排；且所有 store 对所有核以一个全局总序变得可见（这也是"Total Store Order"名字的由来）。

x86-TSO 允许 / 禁止的重排（Sewell et al. 形式化，Intel SDM 同）：

```
允许：  W(x) 之后的 R(y) 可提前到该 W(x) 之前可见   —— store→load 重排（store buffer 造成）
禁止：  W→W（两个写不换序）
禁止：  R→R（两个读不换序）
禁止：  R→W（读不越过其后的写）
额外：  一个核能通过 store-forwarding 提前读到自己 store buffer 里自己的写（不算违规）
```

所以 6.4.1 的 store-buffer 例在 x86 上确实可能 r1==r2==0——正是唯一被允许的 store→load 重排。要禁止它，需在两条指令间插入全屏障（`mfence`，或带 `lock` 前缀的原子指令，见 6.5）。TSO 的实践意义：x86 程序员大多数时候不用操心重排（只有 store→load 这一种、且跨不同地址），这让 x86 上的并发代码相对"好写"；但"相对好写"不等于"不用同步"——需要 store 后立刻对别核可见并读回时，仍必须显式屏障。

### 6.4.4 弱序模型

ARM、Power、RISC-V 等采用**弱序/宽松一致性**（weak / relaxed consistency）：默认几乎所有的读写重排都被允许（store→load、store→store、load→load、load→store 都可能乱序），只要不违反单核自身的数据依赖与缓存一致性。程序员必须用显式**屏障/栅栏指令**（barrier/fence）或带获取-释放语义（acquire/release）的内存操作，在需要的地方**手动**建立次序。

对比 TSO，弱序把"默认不重排、少数例外要屏障"翻转成"默认可重排、要次序处处得屏障"。这么设计是为了给硬件最大的重排自由（更容易做乱序、写合并、非阻塞 cache），从而在移动/服务器 SoC 上省功耗、提吞吐。代价是编程更难、更易踩内存序 bug。一个常见弱序原语是**获取-释放**（acquire/release）：release 写保证它之前的所有内存操作都已完成并可见，acquire 读保证它之后的操作不会提前——二者配对就能在生产者/消费者间建立"发布-订阅"的可见性，而不必用最重的全屏障。

模型强弱谱系（从强到弱）：

```
SC（最强，理论基准，几乎无硬件） > TSO（x86/SPARC-TSO） > 弱序/release consistency（ARM/Power/RISC-V）
```

一个直接后果：同一段"看似正确"的无锁代码，在 x86（TSO）上可能碰巧能跑，移植到 ARM（弱序）上就因缺屏障而出错。这正是"不能靠某个架构的实测行为当作可移植保证"的原因，必须按语言内存模型（6.4.5）写、让编译器为目标架构插入正确屏障。

### 6.4.5 与 L4-05 并发的分账（硬件内存序 vs 语言内存模型）

本节到此讲的都是**硬件内存序**：CPU 允许/禁止哪些重排、`mfence`/屏障指令的机器语义、TSO/弱序是处理器 ISA 层面的性质。而 L4-05 并发讲的是**语言级并发**：`std::atomic`/`std::mutex`、Java `volatile`/`synchronized`、语言内存模型（C++11、Java JMM）定义的抽象规则（`memory_order_relaxed/acquire/release/seq_cst`、happens-before、数据竞争 UB 等），以及互斥量、条件变量等运行时同步设施。两者是分层的：

```
语言内存模型（C++11/Java JMM，L4-05）  —— 抽象、可移植的规则；程序员写 acquire/release/seq_cst
        ↓ 编译器按目标 ISA 翻译/插屏障
硬件内存序（TSO/弱序，本大主题）        —— 具体 CPU 的重排规则与 mfence/dmb 等屏障指令
```

分账要点有三。其一，语言内存模型是**抽象契约**，硬件内存序是**具体实现**：C++ 的 `seq_cst` 在 x86 上编译器可能只需在 store 处用 `xchg`/在必要处加 `mfence`（因 TSO 已很强），在 ARM 上则要插更多 `dmb` 屏障——同一份可移植代码，落到不同硬件内存序上编译出的屏障不同。其二，正确性判据在语言层是"数据竞争自由（DRF, Data-Race-Free）"：只要程序无数据竞争（共享变量的并发访问都由同步或原子操作保护），语言模型就保证它表现得如同 SC，程序员**无须直接面对 TSO/弱序的重排细节**——这正是语言内存模型的价值。其三，本大主题只负责讲清"硬件提供什么"（原子指令、屏障指令、TSO/弱序），语言如何在其上建模、`std::atomic` 各 memory_order 的精确语义、happens-before 推理，归 L4-05，不在此下沉。初学者记住这条链：写代码用语言原语（L4-05）→ 编译器按本节的硬件内存序插屏障 → CPU 按 TSO/弱序执行。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch5 §5.6（存储一致性模型入门：一致性 vs 一致性模型的区分、顺序一致性 SC、宽松一致性模型与同步的必要性）；核实 2026-07-30。
- 佐证：x86-TSO 形式化模型 —— Sewell, Sarkar, Owens, Nardelli, Myreen, "x86-TSO: A Rigorous and Usable Programmer's Model for x86 Multiprocessors", *CACM* 53(7), 2010（store-buffer 例、允许 store→load、禁止其余三类重排）；Intel SDM Vol.3 §8 内存序（与 TSO 一致）；SC 原始定义 Lamport 1979 "How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs"。
- 一致性：QA 给出 SC 与宽松模型的概念框架，x86-TSO 论文/Intel SDM 给出 x86 的精确重排规则，二者互补无冲突；SC 是理论基准而非主流硬件默认，各源一致。
- 分账：硬件内存序（本节，TSO/弱序/mfence 机器语义）vs 语言内存模型（L4-05，C++11/Java JMM、std::atomic memory_order、DRF-SC 保证）显式分层，见 6.4.5，不混讲。

## 6.5 同步与屏障

### 6.5.1 原子读改写指令

多核要协作，光靠普通 load/store 不够：`x++` 这种"读-改-写"若两个核同时做，可能都读到旧值、各自加一、都写回，丢一次更新（竞态）。硬件因此提供**原子读改写**（atomic read-modify-write, RMW）指令，把"读+改+写"打包成一个不可被打断、对其他核表现为瞬时完成的操作，作为一切锁与无锁结构的地基。常见几族：

```
Test-and-Set (TAS)      原子读出旧值并置 1；旧值告诉你之前是否已被占
Compare-and-Swap (CAS)  若内存等于期望值则换成新值，返回是否成功；无锁结构基石
Fetch-and-Add (FAA)     原子取回旧值并加上增量；用于计数器、ticket 锁
Exchange (XCHG)         原子交换寄存器与内存
LL/SC (Load-Linked/Store-Conditional)  RISC/ARM/Power 路线：LL 读并记地址，SC 仅当期间无人写才成功
```

x86 走"指令带 `lock` 前缀"路线：加了 `lock` 的 RMW 指令原子完成。本机反汇编坐实（gcc 13.3.0 -O2，`stdatomic.h`）：

```
atomic_fetch_add(&cnt,1)            → lock addl $0x1,0x0(%rip)
__sync_val_compare_and_swap(p,e,d)  → mov %esi,%eax ; lock cmpxchg %edx,(%rdi)
```

可见 `atomic_fetch_add` 编译成 `lock addl`、CAS 编译成 `lock cmpxchg`——`lock` 前缀就是硬件原子性的来源（历史上锁总线，现代通过缓存一致性锁定该 cache 行）。ARM/RISC-V 无 `lock` 前缀，改用 LL/SC 一对指令：SC 若发现 LL 之后该地址被别人动过就失败，让软件重试。初学者只需记住：原子 RMW 是同步的物理基础，CAS 尤其通用（几乎任何无锁结构都能用 CAS 循环搭出来）。

### 6.5.2 锁的实现

互斥锁（mutex/lock）保证同一时刻只有一个线程进临界区，最底层用原子 RMW 搭。最朴素的是**自旋锁**（spinlock）：反复用 TAS/CAS 抢一个标志，抢到进临界区、放锁时清标志。朴素自旋锁的问题是每次 TAS 都是写操作、都要抢 cache 行独占，多核狂抢时一致性流量爆炸。改进层层递进：

```
TAS 自旋锁       循环 test-and-set 抢锁 —— 争用时一致性流量大
TTAS(测试后测试再设)  先只读自旋(while lock busy)，看似空闲了才 TAS —— 减少写风暴
Ticket 锁        取号(fetch-and-add)排队，轮到自己的号才进 —— 公平、先到先得
MCS / CLH 队列锁  每线程在自己本地变量上自旋 —— 争用可扩展，避免全体抢同一行
```

递进的主线是"减少多核抢同一个 cache 行"：TTAS 让等待者大多数时间只读（读可多核共享 S 态，不抢独占）；ticket 锁给出公平顺序、避免饿死；MCS 锁让每个等待者在各自私有的节点上自旋，彻底消除"一放锁全体一起抢"的惊群与一致性风暴，因此在高并发下最可扩展。初学者理解到"自旋锁能用但争用重时很费、真实系统用排队锁或退避+让出"即可。自旋锁只适合临界区极短、持锁时间远小于一次上下文切换的场景；否则该用阻塞锁（睡眠等待，归 L4-05/OS）。

### 6.5.3 内存屏障与 fence 语义

原子性还不够，还要管**可见次序**（承接 6.4）。**内存屏障/栅栏**（memory barrier/fence）是一条限制内存操作重排的指令。x86 提供三条：

```
mfence  全屏障：屏障前的所有 load/store 都完成可见后，之后的才可开始 —— 唯一能挡住 store→load 重排的
sfence  写屏障：只对 store 排序（配合非临时/写合并内存使用）
lfence  读屏障：只对 load 排序（并作为投机执行的序列化点）
```

获取-释放语义（acquire/release）是更细粒度的表达：**release** 屏障保证它**之前**的内存写在此点前全部完成可见（"发布"），**acquire** 屏障保证它**之后**的读不被提前到此点前（"订阅"）。一对 release-store / acquire-load 就能在两线程间建立"我发布的数据你订阅时一定看得见"的因果，而不必用最重的全屏障。

因为 x86 是 TSO（6.4.3），本机 gcc -O2 编译 `stdatomic.h` 的产物很省——很多序反正 TSO 已保证：

```
atomic_store(seq_cst)               → xchg %esi,(%rdi)        # xchg 隐含 lock，兼作全屏障，故不再单发 mfence
atomic_store(release)               → mov  %esi,(%rdi)        # release 存在 TSO 下就是普通 mov（store 不会前移）
atomic_thread_fence(seq_cst)        → lock orq $0x0,(%rsp)    # 现代 gcc 用 lock 空操作作全屏障，比 mfence 更快
```

这三行是关键教学点。其一，seq_cst 的 store 被编成 `xchg`（自带锁语义即全屏障），而 release 的 store 只是普通 `mov`——因为 TSO 下 store 天然不会被后移到别的 store 之后，release 语义"免费"，无需任何屏障指令。其二，seq_cst 全屏障 gcc 选择 `lock orq $0,(%rsp)`（对栈顶做一次带 lock 的无副作用操作）而非教科书常提的 `mfence`——现代 x86 上 `lock` 空操作通常比 `mfence` 更快，二者都提供全屏障效果，这是"规范语义（全屏障）vs 实现选择（用哪条指令实现）"的一个鲜活分账：语义相同、指令不同。这也解释了为什么"同样的 C++ 原子代码，x86 生成的屏障很少，ARM 要插一堆 dmb"（弱序下 release/acquire 都得真发屏障）。

### 6.5.4 lock 前缀、原子性与一致性的协同

`lock` 前缀（及 `xchg`、LL/SC）之所以能既保证原子性又提供屏障，是因为它与缓存一致性协议协同：带 lock 的 RMW 会先把目标 cache 行拿到独占（M/E，作废别核副本），在此期间该行的读改写对别核表现为不可分割，完成后新值经一致性协议传播。所以"原子指令"其实是"一致性协议 + 排序约束"的合体——它同时压住了 6.2 的一致性（独占该行）与 6.4 的次序（带全屏障语义）。

这解释了为什么原子操作比普通访存贵得多：它要独占 cache 行（可能触发跨核作废与数据迁移）、还要排空 store buffer 保证屏障。争用越重（多核抢同一行），代价越高——这正好通向下一节的伪共享：即便逻辑上各写各的变量，只要它们落在同一 cache 行，硬件也会当成"抢同一行"来回迁移，白白付出这份代价。初学者把握一句：同步不是免费的，它的成本来自缓存一致性的 cache 行迁移 + 屏障对流水线/store buffer 的约束。

### 6.5.5 无锁与 ABA 问题（广度补充）

除了用锁，还可用原子 RMW 直接搭**无锁**（lock-free）数据结构，典型是"CAS 循环"：读当前值→算新值→CAS 尝试写回，失败（说明期间被别人改过）就重读重试。无锁结构避免了锁带来的阻塞/优先级反转，但更难写对。

一个经典陷阱是 **ABA 问题**：线程读到值 A，准备 CAS(A→C)；其间别的线程把它从 A 改成 B 再改回 A。CAS 只比较"值等于 A 吗"，看到还是 A 就成功了，却没察觉中间发生过变化——对指针/栈这类结构可能导致结构被破坏。常见对策是给值附带一个版本号/标签一起 CAS（双字 CAS，如 x86 的 `lock cmpxchg16b`），或用 LL/SC（SC 检测的是"期间有无写"而非"值是否相同"，天然免疫 ABA）。初学者只需知道无锁不等于简单，ABA 是它的招牌坑，深入实现归 L4-05/高级算法。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch5 §5.5（同步：原子交换/test-and-set/fetch-and-increment、LL/SC、自旋锁、争用下的一致性流量、屏障与同步对存储一致性模型的依赖）；核实 2026-07-30。
- 佐证：本机 gcc 13.3.0 -O2 反汇编 `stdatomic.h`（`atomic_fetch_add`→`lock addl`；CAS→`lock cmpxchg`；seq_cst store→`xchg`；release store→`mov`；seq_cst fence→`lock orq $0x0,(%rsp)`），实测坐实原子指令与屏障的真实编码；Intel SDM Vol.3（`lock` 前缀原子性、`mfence`/`sfence`/`lfence` 语义）。
- 一致性：QA 讲同步机制与原子原语，Intel SDM 给 x86 具体指令语义，本机反汇编坐实实际选择的指令，三者互补；`mfence` vs `lock or` 属实现选择（语义均为全屏障），非冲突，两边都记。
- 分账：硬件同步指令语义（本节）vs 语言级锁/条件变量/std::atomic memory_order 语义（L4-05）分层；MCS/CLH 锁与无锁/ABA 深入实现留 L4-05/高级算法，此处仅广度点名。

## 6.6 伪共享

### 6.6.1 伪共享的定义与成因

伪共享（false sharing）指两个（或更多）核各自读写**逻辑上互不相干的变量**，但这些变量恰好落在**同一条 cache 行**（本机 64 字节，`getconf LEVEL1_DCACHE_LINESIZE` = 64）上，于是缓存一致性协议以 cache 行为最小粒度工作，把这条行在各核间反复作废、来回搬运，造成本不该有的争用和串行化——尽管程序逻辑上根本没有共享。

成因的关键是"一致性的粒度是 cache 行，不是变量"。核 0 写变量 a、核 1 写变量 b，只要 a、b 同行：核 0 写 a 要独占该行（作废核 1 的副本），核 1 写 b 又要独占同一行（作废核 0 的副本），两核轮流把整行抢来抢去（cache line ping-pong），每次写都变成一次跨核 miss。逻辑上零冲突的代码，被硬件当成了对同一资源的激烈争用——因为硬件看的是行地址，不是你以为的变量边界。这是"隐形串行化"：源码里看不出任何共享，性能却像加了锁。

最典型的触发场景是"每线程一个计数器放进连续数组" `long counter[NTHREADS]`：8 字节的 long，8 个连成 64 字节正好挤在一到两条行里，多线程各更新自己那个元素，全在互相作废。

### 6.6.2 检测与消除

消除伪共享的核心手段是让"被不同核频繁写的变量各占独立 cache 行"，即**填充/对齐**（padding / alignment）：

```
易伪共享：  struct { long v; } arr[N];              // 每个 8B，多个挤一行
已消除：    struct { long v; char pad[64-8]; } arr[N]; // 每个撑满 64B，独占一行
或用对齐：  alignas(64) / __attribute__((aligned(64)))  让每元素起始于行边界
C++17：     std::hardware_destructive_interference_size 给出建议对齐（通常 64）
```

其他手段：把频繁写的共享结构里"各线程各写的字段"拆开、别塞进同一行；线程本地累加（thread-local）到最后再汇总，避免全程写共享行；用性能计数器（perf 的 cache miss / HITM 事件、Intel `c2c` 工具）定位到底哪条行在跨核弹跳。易错点：填充是空间换时间，别无脑给所有结构填充（浪费 cache 容量、伤局部性），只对"确实被多核高频写、且相邻"的字段做。判断依据是"这两个字段会不会被不同核同时高频写"——只读共享或单核访问的数据不需要填充。

### 6.6.3 本机实测

用 4 线程各自狂增一个计数器，对比"计数器挤在一起（8 字节 long 连续数组）"与"每个计数器填充到 64 字节独占 cache 行"两种布局（gcc 13.3.0 -O2 -pthread，各 5000 万次自增）：

```
sizeof shared = 8   (未填充，4 个 long 挤进 1 条 64B 行 → 最大伪共享)
sizeof padded = 64  (每个独占一条行)
false-shared: 0.142 s
padded:       0.119 s
ratio: 1.19x
```

方向与理论一致：未填充（伪共享）确实更慢，填充后更快。不过本机比值只有约 1.19x，明显低于文献常见的 3x–10x；原因是本机为受限虚拟机、单 NUMA 节点、仅 4 个逻辑 CPU（见 6.1.3），核间一致性往返代价被大幅压低——伪共享的惩罚在真实多插槽/多物理核、跨 NUMA 节点的机器上会显著放大。所以这里的 1.19x 只作"方向坐实"，**不作现状结论的绝对数值**；真实生产环境下伪共享可能是数倍的性能杀手，值得用 padding 消除。这也再次印证 6.5.4 的成本来源：伪共享贵，贵在缓存一致性把整条行在核间反复迁移。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch5 §5.2（一致性以 cache 行/块为粒度；块大小与一致性 miss——含伪共享作为一致性 miss 的一种，在 miss 分类讨论中）；核实 2026-07-30。
- 佐证：本机 pthread 实测（4 线程各 5e7 次自增，未填充 0.142s vs 填充 64B 0.119s，比值 1.19x；`getconf LEVEL1_DCACHE_LINESIZE`=64）；C++17 标准 `<new>` 的 `std::hardware_destructive_interference_size`（伪共享对齐建议，标准化了"用行大小填充"这一做法）。
- 一致性：教材（一致性以行为粒度 → 伪共享是必然副作用）与本机实测（填充后更快）方向一致，无冲突。
- 待核：本机实测比值 1.19x 远低于文献常见 3x–10x，因单 NUMA 节点/4 逻辑核的受限 VM 压低了核间一致性代价，标「实测方向坐实、绝对数值不作现状结论·真实多核机器惩罚更大」，不以此 VM 数值当普适结论。
