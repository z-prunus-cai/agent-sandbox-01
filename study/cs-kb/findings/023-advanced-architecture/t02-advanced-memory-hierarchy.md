## 2.1 Cache 优化技术

### 2.1.1 AMAT 框架与优化的三个抓手

平均访存时间（Average Memory Access Time, AMAT）是衡量内存层次好坏的核心量，它把一次访存的期望耗时拆成"命中时就付的固定代价"加"偶尔失效时额外多付的代价"：

AMAT = 命中时间 + 失效率 × 失效代价

（Hit time + Miss rate × Miss penalty）

一切 cache 优化技术，本质上都是在压这三项中的某一项（或用并行把某项的等待藏起来）。QA ch2 正是按"降命中时间 / 增带宽 / 降失效代价 / 降失效率 / 用并行掩盖"这几个抓手把十来种高级优化归类的；教辅口径可收敛成三大类：降命中时间、降失效率、降失效代价，外加"增带宽 + 并行"这条横向手段。

为什么要盯着这个公式而不是只看失效率？因为三项会互相拉扯：把 cache 做大能降失效率，但更大的阵列查找更慢、命中时间反而涨；提高相联度也降失效率却让命中路径更长。优化不是单点最优，而是让 AMAT 这个乘加式整体最小。初学者最容易只记"失效率越低越好"，却忽略命中时间是每一次访问都要付的（失效只是偶尔），所以哪怕失效率只降一点点、只要命中时间涨了，也可能得不偿失——这正是"为什么 L1 要小而简单"的根本原因。

还有一个要点，AMAT 是把访存耗时换算成"时间"，但它不直接等于程序变慢多少。真正影响性能的是"每条指令的访存停顿周期数"，还要看这些停顿能否被乱序执行、非阻塞 cache 等机制重叠掉（见 2.3）。所以 AMAT 是分析工具，不是最终性能，QA 特意提醒不要把二者划等号。

### 2.1.2 3C 失效模型

要"降失效率"，先得知道失效从哪来。经典的 3C 模型把 cache 失效按成因分成三类：强制失效（compulsory，又称冷启动失效）——数据第一次被访问，cache 里根本没有，谁也躲不掉；容量失效（capacity）——工作集比整个 cache 还大，块被挤出去后又要用，属于"装不下"；冲突失效（conflict，又称碰撞失效）——cache 明明还有空位，但因为映射规则（组相联度不够）把本可共存的块映到了同一组、互相踢出。

这个分类的用处在于它把每种优化对准了明确的靶子。加大块能减少强制失效（一次多搬点，吃空间局部性）；加大 cache 能减少容量失效；提高相联度能减少冲突失效（全相联时冲突失效为零，只剩强制与容量）。

初学者要抓的直觉是"如果换成一个无穷大的全相联 cache，还会失效吗？会——那就是强制失效；如果换成同样大小的全相联就不失效了、直接映射却失效，那多出来的就是冲突失效；剩下的是容量失效"。这三个"如果"正是 3C 的操作性定义。易错点：3C 不是互斥可精确切分的物理量，而是一种归因框架，QA 也指出多核环境下还要加第 4 个 C——一致性失效（coherence miss，因别的核写了同一块使本地副本失效），这条留 AA-6 讲。

### 2.1.3 降命中时间：小而简单的一级 cache 与路预测

命中时间是每次访问都要付的成本，也常常落在处理器的关键时序路径上（它可能直接决定时钟周期或 L1 的流水级数），所以第一类优化就是把 L1 做得又小又简单。小 cache 阵列的地址译码和数据读出更快、功耗更低；低相联度让"读标记 + 比较 + 选数据"的链路更短。这就是为什么现代 L1d 常年停在 32 KiB 上下（本机每核 L1d 恰为 32 KiB），而不是一味做大——大 L1 会拖慢每一次命中。

路预测（way prediction）是在组相联 cache 上省时间的技巧：组相联每次命中前要比较组里所有"路"的标记再选数据，慢且费电。路预测先用一个小预测器猜"这次多半命中第几路"，提前把那一路的数据取出来，猜对就快、猜错再回退按正常流程走一遍。

打个比方，小而简单的 L1 像你桌上只放三五本最常用的书，伸手就拿到；做成一整墙书架（大而高相联）虽然能装更多、少跑图书馆，但每次找书要扫一排书脊，反而慢。路预测则像你对"常用书放在书架第二格"形成了肌肉记忆，先往那格伸手，多数时候一把拿对。易错点：这些手段降的是命中时间，通常会略微抬高失效率（cache 更小），是拿 AMAT 里一项换另一项，符合 2.1.1 说的整体权衡。

### 2.1.4 降失效率：块大小、容量、相联度与编译器优化

对着 3C，降失效率有四个直接旋钮。加大块（block size）能吃更多空间局部性、压强制失效，但块太大在固定容量下块数变少，反而抬高冲突/容量失效，还加大失效代价（每次要搬更多字节），所以存在一个最优块大小，多数通用 cache 落在 64 B（本机行大小即 64 B）。加大 cache 容量直接压容量失效，代价是命中时间和功耗上升、成本更高。提高相联度压冲突失效，有个经验法则值得记：

容量为 N 的直接映射 cache，其失效率约等于容量为 N/2 的两路组相联 cache

（QA/附录 B 给出的经验规律，非精确等式，不同工作负载会偏移，标「经验法则·非定值」）

第四个旋钮不在硬件而在编译器：通过循环交换（loop interchange，把按列扫的坏顺序改成按行扫，顺着内存布局走）、分块/瓦片化（blocking / tiling，把大矩阵切成能塞进 cache 的小块反复复用）等变换，在不改硬件的前提下大幅改善访问的局部性、压低失效率。

为什么把编译器优化也算进 cache 优化？因为失效率是"程序访问模式"和"cache 结构"共同决定的，改程序和改硬件是同一枚硬币的两面。最小例子：一个 N×N 矩阵按 `a[j][i]`（列序）访问行主序存储的数组，每次都跳一整行的距离、几乎每访必失效；改成 `a[i][j]`（行序）后连续命中同一 cache 行——同样的算法、同样的硬件，只因访问顺序不同，失效率能差一个数量级。这正是 2.1.2 里"局部性差的程序 cache 很差"的具体化，也是高性能计算课分块算法的地基。

### 2.1.5 降失效代价：多级 cache、读优先、关键字优先与合并写缓冲

失效代价是"失效后向下层取数据要等多久"，也有多招可压。最重要的是多级 cache（multilevel cache）：在 L1 和主存之间插 L2、L3，把一级失效的代价从"访问主存"降为"访问下一级 cache"。多级下 AMAT 要递归展开：

AMAT = 命中时间_L1 + 失效率_L1 × (命中时间_L2 + 失效率_L2 × 失效代价_L2)

局部失效率（local miss rate，本级失效数 ÷ 到达本级的访问数）与全局失效率（global miss rate，本级失效数 ÷ CPU 发出的总访问数）。评估 L2 对整体的贡献要用全局失效率，因为很多访问已被 L1 挡下、根本没到 L2；只看 L2 的局部失效率会高得吓人却不代表它没用。这是初学者最容易搞混的一处，QA 特意强调。

其余几招各有巧思。读优先于写（read miss 优先，让写先进写缓冲区、读失效先行处理），因为读常在关键路径上、CPU 等着它继续算。关键字优先/尽早重启（critical word first / early restart）：一个块有很多字，但 CPU 当下只要其中一个字，就先把那个字取回来交给 CPU 继续跑，块的其余部分后台补齐，不必等整块到齐。合并写缓冲（merging write buffer）：多个写同一 cache 行时在写缓冲里合并成一次写回，减少与下层的往返。

把这几招串起来看，它们都是"能不等就不等、能少搬就少搬"。关键字优先像你点外卖只等你要先吃的那份先送到，别的菜后到不挡你开吃；合并写缓冲像攒够一车快递再发，而不是一件一趟。它们不改失效率，只把每次失效的痛感压小。

### 2.1.6 增带宽与用并行掩盖：流水化、多 bank、非阻塞与预取

前面几类是缩短单次访问的时间，还有一类横向手段是提高吞吐、用并行把延迟藏起来，这类在带宽紧张的现代处理器上越来越重要。流水化 cache 访问（pipelined cache access）把一次命中拆成多个流水级，允许多个访问在 cache 里首尾相接地流动，提高访问频率（代价是命中延迟占的时钟拍数变多，分支等对延迟敏感的路径要小心）。多 bank cache（multibanked cache）把 cache 切成若干独立体，不同 bank 可同时服务不同地址的访问，用地址交叉（如按低位地址轮流分派到各 bank）提高并发。

另外两支重要到需要单独成节：非阻塞 cache 让一次失效未完成时 cache 仍能服务后续命中甚至后续失效（见 2.3），硬件/软件预取在数据被用之前就提前搬进来（见 2.2）。它们不减少单次失效代价，而是让多次访存在时间上重叠、把等待摊薄——这正是 2.1.1 说"AMAT 不等于性能"的原因：能被重叠掉的停顿不完全计入实际变慢。

初学者可以把这一类理解为"多开几条流水/多设几个窗口同时办事"。前面几类优化是让每个顾客办得更快，这一类是让多个顾客同时被服务；两者叠加才是现代 cache 的真实样貌。这里也点出本大主题的结构：2.2 与 2.3 就是把这条"并行掩盖延迟"的线拆开细讲。

## 2.2 预取

### 2.2.1 预取的动机、分类与三个评价维度

预取（prefetching）是在处理器真正需要某数据之前，就预测性地把它从下层搬进 cache（或专门的预取缓冲），从而把强制失效/容量失效的等待藏在计算背后。它对付的是 AMAT 里"失效代价"和"失效率"——理想情况下数据在被用时已经就位，那次访问从失效变成命中。预取分两大类：硬件预取（由硬件观察访问流自动发起）和软件预取（由编译器或程序员插入预取指令显式发起）。

评价一个预取好不好有三把尺子，初学者务必记住，因为预取是把双刃剑。准确率（accuracy）——预取来的东西有多少真的被用上；覆盖率（coverage）——本来会失效的访问里有多少被预取提前挡下了；及时性（timeliness）——预取得太晚（数据还没到就被用了，白等）或太早（还没用就被别的数据挤出 cache）都不行，要恰好在使用前不久到位。

为什么需要这三把尺子一起看？因为只追一个会翻车：只追覆盖率就会疯狂预取、把没用的数据也搬进来污染 cache、挤掉有用数据还白耗带宽（准确率崩）；只追准确率就只敢预取十拿九稳的、覆盖率低、省不下多少失效。好的预取是三者的平衡。这也是预取"看起来稳赚、实则容易帮倒忙"的原因，下面 2.2.4 专门讲它的代价。

### 2.2.2 硬件流预取与步长预取

硬件预取由 cache 控制器旁的一个小引擎自动干，程序无感。最简单的是下一行预取（next-line）：取了第 N 行就顺手把第 N+1 行也拿来，直接吃空间局部性。进阶的是流预取（stream prefetcher）/步长预取（stride prefetcher）：引擎观察最近的访问地址，若发现它们以固定步长（stride）递增/递减（比如每次 +64 B、+512 B），就判定这是一条"流"，沿该步长提前多取若干行。经典实现里还会配流缓冲（stream buffer）——一个独立的小队列专门存预取来的连续块，不立即污染主 cache，命中了再提上来。

为什么步长检测有用？因为数组遍历、矩阵按行扫、结构体数组顺序访问，这些最常见的访问模式在地址上就是一条等差数列。硬件只要认出"步长稳定"就能高置信地往前铺路。最小例子：`for (i=0;i<N;i++) sum+=a[i];` 地址每次涨一个元素大小，步长预取器几拍内就锁定这条流，之后 CPU 每要一个新块，块基本已在 cache 里等着了。

这里要建立的边界感是，硬件预取擅长规则的、可外推的模式（连续、定步长），对不规则模式（追随机指针的链表/图遍历、哈希表跳跃访问）基本无能为力甚至帮倒忙——这类模式的地址序列没有可学的规律。现代预取器有更复杂的变种（如基于地址相关性的预取），属前沿且实现各异，标「⚙实现相关」，本报告不深挖。

### 2.2.3 编译器控制的软件预取

当访问模式硬件猜不到、但编译器/程序员在代码里看得出来时，就用软件预取：在真正用到数据之前若干次迭代，插入一条专门的预取指令（x86 的 `prefetcht0/t1/t2/nta` 系列，GCC 内建 `__builtin_prefetch`），把目标地址的 cache 行提前拉进来。关键是预取距离（prefetch distance）——要提前多少次迭代发预取，才能让数据在被用前恰好到位：

预取距离（迭代数）≈ ⌈内存访问延迟 / 每次迭代的计算时间⌉

（QA 给出的估算原则：预取要覆盖住内存延迟；具体值随平台/循环体变，属需实测量，标「经验估算」）

一个关键性质是这类预取多为非绑定/非阻塞（nonbinding）且不产生异常：预取指令即使地址无效或缺页也不会真的触发缺页/异常，只是当作提示、失败就悄悄放弃。这保证插错预取不会改变程序语义或崩溃，只影响性能。

打个比方，软件预取像做饭时"我知道下一步要用葱，先从冰箱拿出来放案板"——因为你（程序员/编译器）懂食谱（访问模式），比只会看你手上动作的硬件（硬件预取器）更早知道。易错点有二：距离算错则前功尽弃（太近数据没到、太远被挤出）；软件预取会占用指令发射带宽和寄存器，插太多反而拖慢循环。所以它主要用在硬件预取失灵、又能静态看出地址的场景，二者互补而非替代。

### 2.2.4 预取的代价与陷阱

预取不是免费的加速开关，它至少有三笔账。带宽占用——预取和正常访存抢同一条内存总线，在带宽已经吃紧的程序里，预取抢了带宽反而让真正的访问更慢。cache 污染（cache pollution）——预取错的、用不上的数据进了 cache，会挤走正在用的有用数据，把命中变失效。指令/资源开销——软件预取额外占发射槽和 MSHR（见 2.3）等资源。

这就是为什么 2.2.1 要强调三把尺子：一个准确率低的激进预取器，很可能净负收益。QA 也指出预取的收益强烈依赖工作负载与平台，不能一概而论。

一句话结论，预取是"用带宽和一点复杂度换延迟"，只在延迟是瓶颈、带宽有余、且模式可预测时才划算；带宽受限或模式随机时，关掉预取有时反而更快。这与 2.1.1"整体权衡"一脉相承——预取压的是失效等待，但可能抬高带宽压力和有效失效率，账要合起来算。

#### 来源与时效（本小主题）

## 2.3 非阻塞 cache

### 2.3.1 阻塞 vs 非阻塞：hit-under-miss 与 miss-under-miss

普通（阻塞式）cache 在一次失效未完成时会锁死：从它失效那一刻起，直到数据从下层取回，后续所有访存都得排队干等，哪怕后面那些访问其实是命中、本可以立刻返回。非阻塞 cache（nonblocking / lockup-free cache）打破这个锁：失效正在处理时，cache 仍能继续服务后续请求。它有两个层级——hit-under-miss（一次失效待处理时，后续命中照常返回）和 miss-under-miss / 多重失效（多次失效可同时在途，各自并行向下层取数）。

为什么这对乱序超标量处理器几乎是必需的？因为乱序核心在等一次 load 失效时，往往还有大量互不依赖的后续指令可以继续发射执行，其中就有别的访存。如果 cache 一失效就全锁死，乱序执行的意义大打折扣——它好不容易找出的并行指令又被内存挡回串行。非阻塞 cache 让"一个 load 卡住、其余照跑"成为可能。

打个比方，阻塞 cache 像单窗口银行，前一个客户在办复杂业务（失效去下层取数），后面所有人——哪怕只是查个余额（命中）——都得干等。非阻塞 cache 像开了叫号和多柜台，复杂业务在后台办，简单业务继续叫号办理，甚至几笔复杂业务并行推进。易错点：非阻塞不减少单次失效的绝对延迟，它减少的是"因为一次失效而白白停摆的其他访问"，靠重叠把总停顿摊薄。

### 2.3.2 MSHR：失效状态处理寄存器

要同时追踪多笔在途失效，硬件需要记账簿，这就是 MSHR（Miss Status Handling Register，失效状态处理寄存器，也叫 miss status/information holding register）。每当发生一次新的、地址不同的失效，就占用一个 MSHR 条目，记下：失效的是哪个块地址、数据回来后要送到哪里（哪个寄存器/哪条指令）、以及是否有多条指令在等同一个块。数据从下层返回时，cache 按 MSHR 记录把数据分发给所有等待者，然后释放该条目。

MSHR 的数量直接决定 cache 能同时容忍多少笔在途失效——有 M 个 MSHR，最多 M 笔失效可并行在途，第 M+1 笔失效就得等到有条目空出（这才是非阻塞 cache 真正的"阻塞点"）。一个巧妙之处是同块合并：若多条指令失效于同一个 cache 块，它们共用一个 MSHR 条目（只需向下层取一次），这叫二级失效合并，省带宽。

打个比方，MSHR 就是"正在下单、还没到货"的订单列表。列表有几行，就最多能有几笔货同时在路上；同一件商品有多人要，合并成一个订单发出、到货了分给大家。易错点：常有人以为非阻塞 cache 能无限并发失效——不能，MSHR 数目是硬上限，它和下面讲的 MLP 直接挂钩。

### 2.3.3 内存级并行 MLP

内存级并行（Memory-Level Parallelism, MLP）指同一时刻能有多少笔独立的内存访问在途并行处理。非阻塞 cache + 多个 MSHR 正是把 MLP 变现的硬件基础：能同时在途的失效越多，多次内存延迟就越能相互重叠，等效的人均延迟被摊薄。用 Little 定律的视角看，稳态下：

在途访问数 = 有效内存带宽 × 内存延迟

要在长延迟下喂饱高带宽的内存系统，就必须维持足够多的在途访问（足够的 MLP），否则带宽用不满、延迟藏不住。

为什么 MLP 是现代内存墙下的关键？主存延迟几十年几乎没怎么降（见 2.5.3），但带宽一直在涨。既然单笔访问的延迟压不下去，就靠"同时多发几笔、让它们的延迟叠在一起"来提高有效吞吐。乱序执行负责找出互相独立的访问，非阻塞 cache 和 MSHR 负责让它们真的并行发出去，预取（2.2）则是主动制造更多在途访问。

把全景串起来看，2.3 和 2.2 是 2.1.6"用并行掩盖延迟"那条线的两个支柱——预取是"提前发"，非阻塞+MLP 是"同时发"。二者共用 MSHR 这类资源（预取也要占 MSHR），也共同解释了为什么"AMAT 不等于实际变慢"：能重叠掉的停顿不完全计入性能损失。这条线会在 AA-4（动态调度/乱序）和 AA-5（GPU 靠海量线程隐藏延迟）继续放大。

- 一手：Hennessy & Patterson《QA》6th ed, 2017, §2.2（优化 4 非阻塞 cache：hit-under-miss / hit-under-multiple-miss；与乱序执行、MLP 的关系）+ §2.1 内存墙背景。核实 2026-07-30。

## 2.4 虚拟内存加速

### 2.4.1 地址转换与页表回顾

虚拟内存（virtual memory）让每个进程看到一段连续的私有虚拟地址空间，硬件（MMU）配合操作系统把虚拟地址（VA）按页（page，通常 4 KiB，本机 `getconf PAGE_SIZE` = 4096）翻译成物理地址（PA）。翻译规则存在页表（page table）里，逻辑上是"虚拟页号 → 物理页帧号"的映射表，页内偏移直接透传。这层间接换来了进程隔离、按需分页、内存超额分配等能力，代价是每次访存前都要先做一次地址转换——这一步一旦慢，就拖垮所有访存。本小主题的所有技术都是围绕"把这次转换做快"。

作为地基要先记住，虚拟地址被切成"虚拟页号 + 页内偏移"两段，页大小是 2 的幂（4 KiB → 低 12 位是偏移）。转换只换页号那部分、偏移原样保留。这和 CO-6 的 tag|index|offset 是两套不同的切分（一套服务地址转换、一套服务 cache 定位），初学者极易混淆——务必分开记：分页切的是 VA→PA，cache 切的是"物理地址落哪一行"。

### 2.4.2 多级页表

问题在于，64 位地址空间巨大，若用一张平坦页表，光表本身就大到装不下（48 位有效虚拟地址、4 KiB 页 → 2^36 个页表项，不可能全建）。解法是多级页表（multilevel / hierarchical page table，又称基数树 radix tree）：把虚拟页号再切成几段，逐级索引——上一级表项指向下一级表的物理地址，一层层走下去，最后一级才给出物理页帧号。它的妙处是稀疏：进程没用到的虚拟地址区域，对应的下级表根本不必建立，省下海量空间。

x86-64 长期用 4 级页表（页目录逐级：PML4 → PDPT → PD → PT），覆盖 48 位虚拟地址；较新平台支持 5 级页表（加一级 PML5）把虚拟地址扩到 57 位。走一遍完整的多级页表叫页表遍历（page table walk），4 级就意味着一次转换最坏要额外访存 4 次——这正是需要 TLB（2.4.3）的原因。

打个比方，多级页表像国家 → 省 → 市 → 街道的分级地址簿，你不必为每一个可能的门牌号预先印一整本，只为真正有住户的街道建下级册子。易错点：多级页表省的是空间、花的是时间（多几次访存），所以它必须和 TLB 搭配才实用；单独的多级页表反而更慢。

### 2.4.3 TLB 与地址转换加速

TLB（Translation Lookaside Buffer，转换后备缓冲/快表）是一个专门缓存"虚拟页号 → 物理页帧号"最近转换结果的小型高速 cache。有了它，绝大多数访存的地址转换只需查一次 TLB（一拍左右命中），不必每次都走多级页表遍历。TLB 命中率通常很高（局部性使得程序反复访问少数几个页），只有 TLB 失效时才触发页表遍历，把结果填回 TLB。

TLB 失效的处理分两种实现：硬件管理 TLB（如 x86，MMU 自动遍历页表并回填，软件无感）和软件管理 TLB（如部分 RISC/MIPS，TLB 失效触发异常、由 OS 的处理程序遍历并回填）——这是"规范/实现分账"的典型点，两种都对，只是分工不同。现代还常有多级 TLB（L1 TLB 小而快、L2 TLB 大些），并区分指令 TLB 与数据 TLB。

一个关键直觉是，TLB 是"页表的 cache"，而不是"数据的 cache"——它缓存的是转换（地址映射），数据本身还在普通 L1/L2/L3 里。这两者独立并存、各司其职，最容易被初学者合并成一个东西。易错点：TLB 覆盖的地址范围 = TLB 项数 × 页大小，叫 TLB 覆盖范围（reach）；若程序工作集横跨的页数超过 TLB 项数，就会频繁 TLB 失效——这正是下面大页要解决的问题。

### 2.4.4 大页

大页（huge / large page）用比标准 4 KiB 更大的页（本机支持 2 MiB，CPU flag `pdpe1gb` 表明还支持 1 GiB 页）。它主要不是为了省数据 cache，而是为了扩大 TLB 覆盖范围并缩短页表遍历：同样项数的 TLB，页越大覆盖的内存越多——

TLB 覆盖范围 = TLB 项数 × 页大小

用 2 MiB 页替代 4 KiB 页，同一个 TLB 覆盖的地址范围直接放大 512 倍，大工作集程序的 TLB 失效率骤降；此外大页少一级页表层级（2 MiB 页在 x86-64 上省掉最后一级 PT），页表遍历更短。

为什么不干脆全用大页？因为大页的代价是内部碎片（只用几 KB 也要占整整 2 MiB）和管理不灵活（换页、拷贝、写时复制粒度都变粗）。所以大页适合大而密集访问的场景（大矩阵、数据库缓冲池、大堆的 JVM/运行时），Linux 通过 HugeTLB 显式预留或透明大页（THP）自动合并来提供。本机 `/proc/meminfo` 显示 `HugePages_Total: 0`（默认未预留显式大页）、`Hugepagesize: 2048 kB`。

一句话结论，大页是拿"内存利用率/灵活性"换"更少 TLB 失效 + 更短页表遍历"，是典型的空间/性能权衡。易错点：大页解决的是地址转换开销，不改变数据 cache 的命中率；把大页当成"让程序数据更快"的通用开关是误解——只有 TLB 是瓶颈时才有效。

### 2.4.5 转换与 cache 访问的重叠：VIPT

地址转换在访存关键路径上，若"先查 TLB 得到物理地址、再用物理地址查 L1"完全串行，会拉长 L1 命中时间。经典优化是虚拟索引物理标记（Virtually Indexed, Physically Tagged, VIPT）cache：用虚拟地址里的页内偏移那几位（这几位转换前后不变）去索引 L1、同时并行查 TLB，等 TLB 给出物理页号时正好用它来比对标记。这样转换和 cache 索引重叠进行，L1 命中路径不被转换拖慢。

为什么用页内偏移位做索引就安全？因为页内偏移在 VA→PA 转换中原样不变，用它选组不依赖尚未完成的转换。约束是 cache 的"索引 + 块内偏移"位数不能超过页偏移位数（否则索引会用到会被转换改变的位，产生别名问题），这就把"单路容量 ≤ 页大小"绑成了设计约束——也是 L1 常做成小容量高相联（如本机每核 32 KiB）的另一个原因（配合 2.1.3）。

打个比方，VIPT 是"一边查地址簿、一边已经按门牌低位去对应的信箱格翻找"，两件事并行、省时间。纯物理索引物理标记（PIPT，须先转换再查 cache，简单无别名但慢）和纯虚拟索引虚拟标记（VIVT，最快但有同义/别名难题）是两个极端，VIPT 是工程上常见的折中。这个点偏进阶，初学者知道"L1 为什么要小、为什么转换能和 cache 查找重叠"即可，不必深挖别名细节。

## 2.5 主存技术

### 2.5.1 DRAM 基础：单元、刷新与 bank

主存今天几乎都用 DRAM（Dynamic RAM，动态随机存取存储器）。它的存储单元极简：一个晶体管 + 一个电容（1T1C），用电容有没有电荷表示 0/1。这换来了极高密度和低成本（对比 SRAM 每位约 6 晶体管），但电容会漏电，所以必须周期性刷新（refresh）——定期把每一行读出再写回，否则数据流失，"Dynamic"即得名于此。DRAM 阵列按行（row）和列（column）组织，访问要先用行地址选通（RAS，激活整行到行缓冲/sense amplifier），再用列地址选通（CAS）读出具体列；多个阵列组成 bank，多个 bank 可交错并行以提高吞吐。

为什么这套结构决定了 DRAM"又慢又便宜"的性格？激活一整行（RAS）耗时长，是延迟的主要来源；但一旦行被激活到行缓冲，同一行内的多次列访问（行命中/page hit）就很快。所以 DRAM 的性能强烈依赖访问的行局部性——连续访问同一行快，频繁跨行（行冲突，要先关旧行再开新行）慢。

打个比方，DRAM 像一个巨大的储物柜矩阵，取东西要先把一整排柜门拉开（RAS，慢），然后从这排里逐个格子拿（CAS，快），要换排就得先关上这排再拉开另一排。刷新则像管理员必须定期巡查每一排、把快掉电的东西重新充电。易错点：刷新期间对应区域不能访问，会带来少量额外延迟；随容量增大刷新开销上升，是大容量 DRAM 的隐性成本。

### 2.5.2 SDRAM 与 DDR 代际

现代 DRAM 是同步 DRAM（SDRAM，用时钟同步接口）。主流是双倍数据率（DDR，Double Data Rate）——在时钟的上升沿和下降沿都传数据，故同频下吞吐翻倍。DDR 一代代提升的主要是数据率（每引脚每秒传输次数 MT/s）和总线频率，同时降工作电压省功耗。各代大致数据率区间如下（JEDEC 标准区间，超频产品更高；主存代际前沿易变，标「⚙演进快·锚 JEDEC 规范」）：

| 代际 | JEDEC 数据率(MT/s) 约 | 定型/标准 | 备注 |
|------|----------------------|-----------|------|
| DDR (DDR1) | 200–400 | 2000 前后 | 2.5 V |
| DDR2 | 400–1066 | 2003 | 1.8 V |
| DDR3 | 800–2133 | 2007 | 1.5 V |
| DDR4 | 1600–3200 | 2014 | 1.2 V；QA 6th ed 主力代际 |
| DDR5 | 3200–6400（更高持续上探） | JESD79-5, 2020 | ⚙演进快·教材后定型 |

QA 6th ed（2017）以 DDR3/DDR4 为主，DDR5（2020 定型）在书之后，故其数据以 JEDEC JESD79-5 规范为准、且实际市场产品数据率持续上探，本报告只锚区间不作"当前最高"结论。

直观地说，DDR 的"双倍"是在同一个时钟周期里搭两班车（上沿一班、下沿一班），所以业界用 MT/s（每秒百万次传输）而非 MHz 来标称，避免把"传输率"和"时钟频率"搞混——这是最常见的误读。要注意"数据率高"主要提升的是带宽，单次访问的延迟（见 2.5.3）并没有同比例改善。

### 2.5.3 带宽 vs 延迟：内存墙

内存技术几十年演进的一个残酷事实是带宽和延迟严重不对称：带宽（单位时间能搬多少字节）随 DDR 代际大幅增长，但访问延迟（发出请求到拿到第一个数据的时间，主要由 DRAM 行激活决定）改善极慢，几十年只降了个位数倍、甚至基本停滞。单通道峰值带宽可粗算为：

峰值带宽 = 数据率(MT/s) × 总线宽度(字节)

例如 64 位（8 字节）通道、DDR4-3200：3200 × 8 ≈ 25.6 GB/s（单通道理论峰值，实际受行冲突/刷新/时序打折）。

这个"带宽涨、延迟停"的鸿沟就是著名的内存墙（memory wall）：处理器速度长期快过内存，导致访存延迟以 CPU 周期计越来越贵。它解释了本报告几乎所有技术的存在理由——多级 cache、预取、非阻塞 cache/MLP、大页，全都是在"延迟压不下去"的前提下，靠缓存、提前搬、并行重叠来"绕过"或"藏住"延迟，而不是消灭它。

打个比方，带宽像马路有多少车道（可以拓宽），延迟像从北京到上海开一趟要多久（很难缩短）。加宽车道能让更多车同时上路（更高吞吐），但每辆车的行程时间没变。所以现代内存系统的思路是"多发车、让行程重叠"（MLP、预取），而不是指望单程变快。易错点：把"内存变快了"简单等同于"延迟低了"是错的——变快的主要是带宽。

### 2.5.4 HBM：堆叠高带宽内存

HBM（High Bandwidth Memory，高带宽内存）是为极端带宽需求（GPU、AI 加速器、高端网络芯片）设计的 DRAM 封装技术：把多片 DRAM 裸片垂直堆叠，用硅通孔（TSV, Through-Silicon Via）在片间做竖直连线，再通过硅中介层（interposer）与处理器近距离并排封装，提供极宽的总线（每堆栈上千位宽），从而以相对适中的频率拿到远超传统 DIMM 的带宽。代价是工艺复杂、成本高、容量相对受限、且通常焊死不可插拔。

QA 6th ed（2017）已把 HBM 列为扩展内存层次的方向（当时以 HBM/HBM2 为背景），但 HBM2E/HBM3/HBM3E 等更高代际在书之后陆续定型，单堆栈带宽逐代大幅攀升。具体代际带宽数字随 JEDEC 规范修订与厂商产品快速变动，本报告统一标「⚙演进快·锚版本·随时变」，不给"当前最高带宽"定值（属待核·随时变），只讲机制。

打个比方，传统 DIMM 是把内存芯片平铺在主板上、用有限引脚的长走线连到 CPU（车道有限、路又长）；HBM 是把芯片叠成塔、贴着处理器用海量极短的竖直线连接（车道极多、路极短），所以带宽暴涨。它对付的正是 2.5.3 的带宽需求侧——用极宽总线在延迟没大改善的情况下把吞吐推上去，配合 GPU 的海量线程隐藏延迟（AA-5）。

### 2.5.5 闪存与非易失存储

闪存（flash，NAND 型为主）是非易失（断电不丢数据）的固态存储，用浮栅/电荷俘获晶体管存储电荷表示数据，密度高、无机械部件，是 SSD 的核心介质，在内存层次里位于 DRAM 主存之下、机械磁盘之上（或替代之）。它的性格与 DRAM 迥异：读较快、写慢且必须先擦后写（以大块 block 为擦除单位、以 page 为读写单位），且每个单元的擦写次数有限（写磨损 wear），需要磨损均衡（wear leveling）和 FTL（闪存转换层）管理。

多层单元技术（SLC/MLC/TLC/QLC，每单元存 1/2/3/4 位）用降低每单元位数的可靠性换更高密度与更低单位成本，这条密度演进前沿且随工艺快速变动，标「⚙演进快」。3D NAND（把单元层垂直堆叠）是当代提升密度的主路线。

为什么闪存进了"内存层次"讨论？因为它模糊了"内存 vs 存储"的界线：作为快速持久层，它承接了 DRAM 装不下、又不能全丢给慢磁盘的数据；持久内存（如曾经的 Optane/3D XPoint，介于 DRAM 与闪存之间，注意该产品线已停产，标「已退役·历史锚点」）等技术也曾试图填补 DRAM 与闪存间的空档。要划清的边界是，闪存不是用来替代 DRAM 做主存的——它太慢、有写磨损、且非字节级随机写友好；它替代的是磁盘那一层。易错点：SSD 快是相对磁盘而言，比 DRAM 仍慢几个数量级，别把"SSD 很快"误当成"接近内存速度"。
