## 3.1 流水线复习（附录 C）

### 3.1.1 流水线 CPI 方程与停顿来源

流水线的性能不能只看"理想每拍完工一条"，真实流水线会因冒险（hazard）插入停顿。附录 C 把每条指令的平均时钟周期数（CPI, Cycles Per Instruction）拆成一个可加的方程，让性能损失有账可算：

流水线 CPI = 理想流水线 CPI + 结构停顿 + 数据冒险停顿 + 控制停顿

其中理想流水线 CPI 在单发射顺序流水里等于 1（稳态每拍完工一条），后面三项分别对应三类冒险带来的额外停顿拍数（按每条指令平摊）。这个方程是整个 ch3 的记分牌：循环展开、静态调度、多发射的作用，本质都是在压低右边某一项。

为什么要把 CPI 拆成加法项？因为它把"性能从哪儿丢的"变成可定位、可分别优化的独立账目。想减少数据冒险停顿就去做转发和调度；想减少控制停顿就去做分支预测；想把理想 CPI 压到 1 以下（即 IPC 大于 1）就得多发射。初学者只要记住：任何 ILP 技术，最终都落到"减小这四项之一"。

回顾大主题1 的性能公式，CPU 时间 = 指令数 × CPI × 时钟周期，流水线主要作用在 CPI 与时钟周期这两个因子上——切段缩短时钟周期，压停顿降低 CPI。易错点：流水化不减少指令数（IC 不变），也不缩短单条指令延迟，它提高的是吞吐。

### 3.1.2 三类冒险与旁路（转发）回顾

附录 C 把冒险分为三类，与 CO-5 一致，但用于后续量化：结构冒险（structural hazard，资源不够同拍争用）、数据冒险（data hazard，后条指令要用还没写回的结果）、控制冒险（control hazard，分支未决时不知道取哪条）。数据冒险中最常见的是写后读（RAW, Read After Write）真相关。

旁路/转发（forwarding / bypassing）是数据冒险的主解法：结果在功能单元算完的当拍就存在于流水寄存器里，用一条专用通路把它直接送到需要它的指令输入端，不必干等写回寄存器堆。对整数 ALU→ALU 相关，转发能完全消除停顿。

```
EX/MEM → EX ：前一条指令（距离1）刚算出的结果，旁路给当前指令的 EX 输入
MEM/WB → EX ：前两条指令（距离2）或 load 的访存数据，旁路给当前 EX 输入
```

转发覆盖不了的典型是 load-use：load 的数据要到 MEM 段末才就绪，紧邻的下一条在 EX 段初就要用，差一拍，必须停顿一拍。这一拍恰恰是编译器调度（3.4）要设法填掉的"延迟槽"。初学者需要把"相关（dependence）"与"冒险（hazard）"分清：相关是程序里固有的指令间关系，冒险是相关在某个具体流水线组织下真的引发了停顿——同一段相关，换个流水线/加了转发，可能就不再是冒险。这条区分是 3.5 讨论 ILP 极限的基础。

### 3.1.3 多周期操作与浮点流水

真实流水线里不是每条指令都能一拍算完。浮点乘除、浮点加这类操作要花好几拍，附录 C 把流水线扩展成"整数段照旧、另设若干可流水或不可流水的多周期功能单元"。这带来两个新问题：功能单元延迟拉长使相关指令要等更久，且多周期操作可能乱序完成，反而制造出顺序 5 级流水里见不到的写后写（WAW）冒险。

教材为讲解循环展开与调度，给这些操作设定了一组示例延迟（QA ch3 的设定，指"产出结果的指令"到"使用该结果的指令"之间必须间隔的拍数）：

```
浮点 ALU 运算 → 另一条浮点 ALU 运算 ：3 拍
浮点 ALU 运算 → 浮点 store        ：2 拍
浮点 load     → 浮点 ALU 运算      ：1 拍
浮点 load     → 浮点 store        ：0 拍
```

这组数字是教材为示例假定的（教材示例设定，锚 QA ch3 §3.2 的延迟表），不是任何具体现实 CPU 的实测值；它的意义是"若消费指令紧跟生产指令而间隔不够这么多拍，就得插停顿"。为什么 load→store 延迟为 0？因为 store 只是把 load 来的值原样写回，转发路径能直接对接，不需要额外等待；而浮点 ALU→ALU 要等满 3 拍，是因为浮点执行单元本身流水深、结果就绪晚。理解这组延迟，才看得懂 3.2 为什么"不展开的循环里到处是停顿"。

多周期操作乱序完成会引发 WAW（写后写）冒险与精确异常难题：一条慢的浮点指令可能比后发的快指令更晚写回，若两者写同一寄存器，顺序就乱了。顺序流水靠"写回端口仲裁 + 检测 WAW"处理，而彻底的解法（乱序完成仍精确）要到 AA-4 的 ROB。此处只需知道：延迟一拉长，名字相关（WAR/WAW）就开始咬人，这正是 3.5 的伏笔。

## 3.2 循环变换

### 3.2.1 循环展开的原理与收益

循环展开（loop unrolling）是把循环体复制若干份、相应减少迭代次数的编译变换。展开因子为 k，就把 k 次迭代的循环体拼进一个大循环体，循环控制（计数、比较、回跳分支）从每元素一次降到每 k 个元素一次。它是编译期暴露 ILP（Instruction-Level Parallelism，指令级并行）最基础的手段。

以经典向量加法（教材用 `for (i=…) x[i] = x[i] + s;` 这类 SAXPY 式循环）为例，未展开时每次迭代只有一条浮点加，前后还夹着 load、store、地址自增、循环分支；由于 3.1.3 的浮点延迟，紧挨的相关指令之间会插入停顿，一次迭代里大量拍数浪费在等待和循环开销上。展开成 4 份后，一个大循环体里有 4 条互不相关的浮点加，它们可以填进彼此的延迟空隙，且循环开销被 4 个元素分摊。

展开带来两类收益，务必分清。其一是摊薄循环开销（amortize loop overhead）：计数与分支指令变少。其二、也是更关键的一条，是暴露独立指令供调度（3.4）填空隙：展开前一个循环体内可重排的独立指令太少，展开后 4 份迭代的指令混在一起可自由调度，长延迟操作就能被别的迭代的有用指令盖住。教材的经典结论是，对该示例循环 4 倍展开并调度后，可从每元素好几拍降到约 3.5 拍/元素（QA ch3 §3.2 的worked example，具体拍数依 3.1.3 的示例延迟设定而定，标「教材示例设定」）。

### 3.2.2 展开必须配合寄存器重命名消除名字相关

如果 4 份迭代都用同一个寄存器存中间结果，它们之间会产生写后写（WAW）和读后写（WAR）名字相关（name dependence），把本可并行的 4 条加法又串成一串。所以循环展开必须给每份迭代分配不同的寄存器——这一步叫（编译期的）寄存器重命名（register renaming），是展开能真正暴露并行的前提。

名字相关不是真的数据流动，只是"恰好复用了同一个名字（寄存器）"造成的假依赖；换个名字就能解除。这与 3.5 要讲的"名字相关 vs 真数据相关"是同一回事——重命名只对名字相关有效，对真正的数据传递（RAW）无能为力。

本机实证（gcc 13.3.0 @Linux 6.18.5 x86_64）直观坐实这一点。对同一段浮点加循环，`-O2`（不展开）每次迭代只有一条 `addss`，而 `-O3 -funroll-loops`（关掉自动向量化以便看清标量展开）把循环体展开、且给每份迭代分配了不同的 XMM 寄存器：

```
$ gcc -O2 -std=c11 -fno-tree-vectorize -S saxpy.c    # 循环体：1 条 addss
.L3:
    movss  (%rdi), %xmm1
    addss  %xmm0, %xmm1        # s 在 xmm0；每迭代复用 xmm1
    movss  %xmm1, -4(%rdi)
    ...
    jne    .L3

$ gcc -O3 -std=c11 -funroll-loops -fno-tree-vectorize -S saxpy.c   # 展开体：多条 addss，不同寄存器
    addss  %xmm0, %xmm2
    addss  %xmm0, %xmm3
    addss  %xmm0, %xmm4
    addss  %xmm0, %xmm5
    addss  %xmm0, %xmm6
    addss  %xmm0, %xmm7
    addss  %xmm0, %xmm8
    addss  %xmm0, %xmm9        # 8 份迭代各用独立 xmm2..xmm9
```

展开后主体的 8 条加法分别落在 xmm2..xmm9 八个互不相同的寄存器上——这正是"展开 + 寄存器重命名消除名字相关"的真实产物：若都复用 xmm1，这 8 条会因 WAW/WAR 串成一条链；换成不同寄存器后它们彼此独立，可被乱序/多发射硬件或后续调度并行推进。（脚本仅在仓库外 scratchpad 运行，不入库。）

### 3.2.3 展开的代价与残余迭代

循环展开不是免费的。代价主要有三：代码膨胀（code size 增大，可能挤爆指令 cache 反而变慢）、寄存器压力（register pressure，见 3.4，重命名要吃更多寄存器，用光就得溢出到内存）、以及迭代数不能被展开因子整除时的残余处理。

当循环次数 n 不是展开因子 k 的整数倍时，必须补一个"收尾循环"（余数循环）逐个处理剩下的 n mod k 次迭代；n 是运行时变量时，编译器还要生成判断逻辑决定走展开体还是收尾体。这套"主展开体 + 收尾"的划分俗称条带挖掘（strip mining）的近亲——把 n 次迭代切成"若干整段 + 一个余段"。上面 gcc 的 8 倍展开产物里除了 8 条一组的主体，就伴随着这样的收尾代码。

展开因子越大越好是错的。展开收益随因子递减（循环开销摊薄很快见顶），代价（代码尺寸、寄存器压力）却持续上升，存在一个最优点。编译器（如 -O3）会用启发式选择因子，而非无限展开。

### 3.2.4 软件流水（软件流水线）

软件流水（software pipelining，又称 symbolic loop unrolling）是另一种循环变换：它不复制循环体，而是重组循环，让每个新迭代由"来自不同原始迭代的指令"拼成——取第 i 迭代的 load、第 i-1 迭代的运算、第 i-2 迭代的 store 放进同一个新循环体。这样每个新迭代内部的指令天然互不相关（分属不同原迭代），流水线各段被填满，长延迟被跨迭代盖住。

它和循环展开的目标相同（暴露 ILP、隐藏延迟），路径不同：展开靠"堆多份迭代 + 重命名 + 调度"，代码会膨胀；软件流水靠"错位重排跨迭代指令"，稳态循环体大小基本不变，代码膨胀小，但需要额外的"填充（prologue）"与"排空（epilogue）"代码来启动和收尾这条软件流水，且实现更复杂。

把连续迭代的 load/compute/store 想成流水线三段，软件流水就是"让循环体在稳态时同时干着三个不同迭代的三个阶段"，正如硬件流水线稳态时段内同时住着多条指令。教材指出软件流水与循环展开常配合使用（先展开再软件流水），因为展开给软件流水提供更多可错位的独立指令。二者都是 VLIW/静态调度处理器（3.3）的关键使能技术。

### 3.2.5 全局调度：迹调度与超块

前述变换多在单个循环/基本块内。要跨越分支挖并行，需要全局代码调度（global code scheduling）。迹调度（trace scheduling）先选出程序中最可能执行的一条"迹（trace，一串跨越多个基本块的高频路径）"，把它当作一个大块整体调度以最大化并行，再为"猜错这条迹"的情形插入补偿代码（compensation code）。超块（superblock）是其变体，限制迹只有单一入口、多出口，简化补偿代码的生成。

真实程序被分支切得很碎，单个基本块内指令太少、可挖并行有限；只有跨基本块把高频路径连成长段，才有足够指令供 VLIW 打包。代价是猜错高频路径时要执行补偿代码，且实现复杂、可能显著增大代码。初学者只需记住：全局调度 = "赌一条高频路径、按它排、赌错了补救"，它是编译器为静态多发射硬件喂饱指令的高级手段，深挖留给编译器课（L4-04）。

## 3.3 静态多发射 / VLIW

### 3.3.1 多发射的两条路线：超标量 vs VLIW

要让 CPI 降到 1 以下（每拍完工多于一条，即 IPC > 1），必须多发射（multiple issue）——每拍取/发射多条指令。多发射有两大流派，按"由谁决定哪几条指令能同拍发射、发到哪个单元"来分：

```
超标量 superscalar ：每拍发射可变条数（1~n），谁能同发由硬件在运行时判定
   ├ 静态调度超标量：硬件按序检查相关，能并行才并行（顺序发射）
   └ 动态调度超标量：硬件乱序调度（Tomasulo 等）——归 AA-4，不在本大主题
VLIW（超长指令字）：每拍发射固定条数，哪几条能同发由编译器在编译期定好、打包进一个长指令
```

本大主题只讲**静态**路线：静态调度超标量与 VLIW，二者的并行决策都主要交给编译器。核心分工差异是：超标量把"检查这几条能否同发"的负担放在硬件（运行时），VLIW 把它放在编译器（编译期），硬件只管照单执行。初学者记住这条"决策放在编译期还是运行时"的分水岭，就抓住了静态 ILP 与动态 ILP（AA-4）的本质区别。

### 3.3.2 VLIW / LIW 的工作原理

VLIW（Very Long Instruction Word，超长指令字）把多个相互独立的操作打包进一条很宽的指令，每个操作对应一个固定的发射槽（issue slot），每个槽绑定一类功能单元（如两个整数、两个访存、一个浮点、一个分支）。编译器负责保证同一条 VLIW 里的各操作确实互不相关、可安全并行执行；硬件不再做相关检查，只把每个槽的操作送进对应单元。

```
一条 VLIW =  [ 整数op | 整数op | 访存op | 浮点op | 分支op ]   ← 编译器保证槽间互不相关
             ↓        ↓        ↓        ↓        ↓
           固定绑定各自的功能单元，同拍并行执行
```

当某个槽这一拍无独立操作可填时，编译器必须塞一个空操作（NOP）占位——这是 VLIW 代码膨胀的直接来源。为什么要固定槽位、去掉硬件相关检查？因为这样硬件极简、时钟可以更快、面积/功耗更省，把复杂度整体转嫁给编译器。这正是 VLIW 的赌注：相信编译器能在编译期挖出足够并行，从而省掉动态调度的昂贵硬件。3.2 的循环展开与软件流水，正是给 VLIW 喂饱各发射槽的关键前置变换。

### 3.3.3 VLIW 的局限

VLIW 的编译期赌注也带来一串固有局限：代码膨胀（NOP 填充 + 展开）、二进制兼容性差（发射槽数/延迟一变，旧二进制就要重编，因为并行信息硬编码进了指令），以及最致命的——无法应对编译期不可知的动态事件。

最典型的是 cache miss：编译器按"命中延迟"排好的静态调度，一旦某次 load 真的 miss，延迟远超预期，整条 VLIW（乃至锁步推进的相邻指令）只能一起停顿等待，因为静态调度没有运行时重排的能力去找别的活干。相比之下，动态调度超标量（AA-4）能在 miss 期间乱序执行别的独立指令，把延迟藏起来。

初学者需要理解这条根本张力：静态调度的信息优势是"能看全整个程序、慢慢优化"，劣势是"看不见运行时才发生的事（miss、分支实际走向、依赖内存地址的别名）"；动态调度正相反。VLIW 把宝全押在编译期，因此在访存行为不可预测的通用代码上吃亏，而在延迟可预测、并行规整的信号处理/DSP、以及后来的部分加速器上仍有市场。

### 3.3.4 谓词执行与静态投机支持

为了让编译器能跨越分支挖更多并行，一些 ISA 提供硬件支持消除或推迟分支。谓词执行（predication，又称条件执行）给指令挂一个布尔谓词寄存器，谓词为真才生效、为假则等同 NOP——这样可把小的 if-then 用无分支的谓词指令替代，消灭该分支及其控制相关（把控制相关转成数据相关，见 3.5）。

编译期投机（compiler speculation）则让编译器把一条指令提前到它所依赖的分支之前执行（如把可能要用的 load 提前），以隐藏延迟；但提前执行可能引发本不该发生的异常（如提前的 load 越界）。硬件为此提供支持：投机 load 用"毒位（poison bit）"标记异常而不立即抛出，等到真正确认该指令该执行时才决定是否兑现异常；配合还有专门的检查指令。这样编译器就能安全地把长延迟操作提到分支上游。

这两类机制是"软硬协同"的典型：编译器想跨分支挖并行，硬件补上"猜错也不破坏正确性"的安全网。初学者只需把握动机——分支是 ILP 的大敌（3.5），谓词把小分支直接铲平，投机支持让编译器敢把指令提前，二者都是为静态调度松绑。它们在 EPIC（3.3.5）里被系统化，深挖留给 AA-4（动态投机）与安全课（投机侧信道）。

### 3.3.5 EPIC / Itanium 案例（⚙历史）

EPIC（Explicitly Parallel Instruction Computing，显式并行指令计算）是 Intel 与 HP 基于 VLIW 思想、加上谓词执行与投机支持的商用体系结构，落地为 IA-64 指令集与 Itanium 处理器（约 2001 年首发）。它把并行信息显式编码进指令束（bundle），试图用编译器智能替代乱序硬件。

Itanium 是理解 VLIW 局限的最佳现实教材：它在编译器技术、二进制兼容（对既有 x86 生态）、以及"静态调度斗不过 cache miss 等动态事件"上遭遇的困难，使其商业上未能取代乱序超标量的 x86；Intel 已于近年正式停止 Itanium 生产（属退役产品线，标⚙历史·随时间已定型）。它的技术遗产（谓词、显式并行、投机支持）则被吸收进后续架构与编译器研究。

对初学者的教益不是记住产品型号，而是记住这条判断：把并行完全押在编译期（静态）在通用负载上难以战胜"编译期挖并行 + 运行时动态调度"的组合。这正解释了为什么主流高性能通用 CPU 走了动态调度超标量（AA-4）而非纯 VLIW，而 VLIW/静态调度的思想在 DSP、GPU 着色器、AI 加速器等延迟规整场景中延续。教材出版于 2017，Itanium 后续退役等产品动态属⚙演进项，以"押注编译期 vs 运行时"的原理为准，不以具体型号作现状结论。

## 3.4 编译器指令调度

### 3.4.1 静态指令调度的目标：重排指令隐藏延迟

指令调度（instruction scheduling）是编译器在不改变程序语义（保持真数据相关顺序）的前提下，重排指令次序，让相关指令之间隔开足够拍数，把长延迟操作的等待期填上无关的有用指令，从而消除或减少停顿。它是 3.2（循环展开/软件流水）与 3.3（VLIW 打包）能真正兑现并行的执行环节。

回到 3.1.3 的延迟：一条浮点 load 后紧跟用它的浮点加会停 1 拍，一条浮点加后紧跟另一条相关浮点加会停几拍。调度器就是把这些"空隙"用别处搬来的独立指令填掉。最小例子：把 `load; use(load); 无关指令A; 无关指令B` 重排成 `load; A; B; use(load)`——use 被推后，load 的延迟被 A、B 盖住，停顿消失。语义不变（A、B 与 load 无关），性能变好。

调度只能重排相互独立的指令；真数据相关（RAW）的先后次序绝不能颠倒，否则算错。所以"有多少独立指令可供填空隙"直接决定调度效果——这就是为什么要先循环展开（制造更多独立指令）再调度。调度与展开是配套拳。

### 3.4.2 基本块调度、数据相关图与列表调度

调度的基本单位常是基本块（basic block，一段无分支进入、无分支离开的直线代码）。编译器先为块内指令建数据相关图（DDG, Data Dependence Graph）：结点是指令，有向边表示"必须先算完才能算"的相关，边上标注延迟。调度问题就变成"在满足所有相关边与延迟约束下，给每条指令排一个尽量紧凑的发射拍"。

列表调度（list scheduling）是最常用的启发式：维护一个"就绪列表"（所有前驱已排且延迟已满足的指令），每拍从中按优先级（如关键路径长度——离出口越远、越该早排）挑指令填入可用发射槽，排一条就更新就绪列表，直到排完。它不保证最优（最优调度是 NP 难），但快且效果好。

为什么用图和启发式？因为块内指令的相关关系是偏序（不是全序），合法排法有很多，要在其中找停顿最少的一个。DDG 把约束显式化，列表调度用"关键路径优先"的贪心快速逼近好解。初学者不必掌握算法细节，只需理解：调度器眼里的程序是一张相关图，它在图的约束下重排以填满流水线——基本块太小则可挖有限，故需 3.2.5 的全局调度扩大调度范围。

### 3.4.3 寄存器压力与调度—分配的相位冲突

指令调度与寄存器分配（register allocation）之间存在根本张力。调度为隐藏延迟，倾向把生产者和消费者拉开、让更多值同时"在飞"，这会同时活跃的值变多，即寄存器压力（register pressure）升高；而物理寄存器有限，压力过大就得把值溢出（spill）到内存（多出 store/load），反而制造新的访存延迟，得不偿失。

这是经典的相位顺序（phase-ordering）难题：先调度后分配，调度器可能排出寄存器分配器满足不了的方案（被迫溢出）；先分配后调度，分配器复用寄存器引入的名字相关（WAR/WAW）又会束缚调度器（3.2.2）。二者互相牵制，没有普遍最优的先后。

循环展开 8 份能暴露 8 路并行，但若要 8 个中间值同时活跃却只有 4 个空闲浮点寄存器，就会溢出 4 个，展开收益被溢出开销吃掉——这就是 3.2.3 说的"展开因子不是越大越好"的深层原因之一。初学者记住：调度追求"多值在飞以隐藏延迟"，分配约束"同时在飞的值不能超过寄存器数"，好编译器要在两者间平衡，这也是纯静态方案的一个天花板（动态硬件有更多物理寄存器做重命名，见 AA-4.3）。

### 3.4.4 静态调度与动态调度的分工

静态调度把重排放在编译期，一次编译、多次运行，能看全整个程序、花大成本优化，且不占运行时硬件；但看不见运行时才知道的事——某次 load 是否 cache miss、分支实际走向、两个指针是否别名（内存消歧, memory disambiguation）——只能按最坏或最常见情形保守排。动态调度（AA-4）把重排放在硬件运行时，信息实时但硬件昂贵、窗口有限。

现代高性能 CPU 是二者合力：编译器做静态调度与循环变换喂饱前端，硬件做动态调度容忍 miss、乱序挖并行。它们不是替代关系而是互补——静态调度降低对硬件窗口的压力，动态调度兜住静态看不见的运行时事件。

静态调度信息全但不知运行时，动态调度知运行时但窗口小、硬件贵。VLIW（3.3）是"全押静态"的极端，纯顺序标量是"完全不调度"的另一端，主流通用 CPU 落在中间偏动态。理解这条谱系，就能顺理成章过渡到大主题4 的动态调度、Tomasulo 与乱序超标量。

- 锚点：H&P《QA》6th ed, 2017, ch3 §3.2（静态指令调度重排隐藏延迟、填 load-use/FP 延迟槽、调度需独立指令、与循环展开配套）与 ch3 关于静态调度与寄存器压力/内存消歧的讨论；核实 2026-07-30。
- 佐证：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.7 结尾（编译器调度填 load-use 延迟槽）；编译原理通识（数据相关图、列表调度、相位顺序难题——L4-04 编译器课范畴，此处只作静态 ILP 视角的浅层引用）。
- 一致性：两源对"编译器重排隐藏延迟、保持真相关、需足够独立指令"一致；寄存器压力/相位顺序为编译器领域共识。

## 3.5 ILP 极限

### 3.5.1 三类相关：数据、名字、控制

程序能挖出多少 ILP，根本上受相关（dependence）约束。QA ch3 把相关分为三类，这是整章的理论骨架：

```
数据相关 data dependence（真相关 true dep）：指令 j 用到指令 i 产出的值（RAW）——数据真的从 i 流向 j
名字相关 name dependence：i 与 j 用了同一个名字（寄存器/内存位置）但无数据流动
   ├ 反相关 antidependence（WAR）：j 要写的名字，i 还要先读
   └ 输出相关 output dependence（WAW）：i 与 j 写同一名字，先后不能乱
控制相关 control dependence：指令是否执行取决于某分支的结果
```

真数据相关是"硬约束"——数据必须先产出才能用，无法靠改名消除，只能靠更快算或投机绕过。名字相关是"软约束"——只是复用了名字造成的假依赖，换个名字（寄存器重命名）即可解除。控制相关约束指令能否被搬到分支之前。理解这三类的可解除程度不同，是理解 ILP 上限的钥匙。

为什么区分真相关和名字相关如此重要？因为它决定了"重命名"这一核心技术的作用边界：重命名（无论编译期还是硬件 AA-4.3）能消除所有名字相关，却对真数据相关无能为力。程序里真数据相关的长链，才是 ILP 不可逾越的下界。

### 3.5.2 相关、冒险与可挖并行度

相关是程序固有属性，是否变成冒险（停顿）取决于流水线组织与是否投机（回到 3.1.2 的区分）。一段相关链决定了指令间必须的先后与最小间隔；把无相关的指令尽量并行、把名字相关重命名掉、把控制相关用投机绕过，剩下的真数据相关关键路径长度就设定了理想执行时间的下界。

把程序画成相关图，最长的真数据相关路径（关键路径）有多长，程序理论上最快就要多少"串行步"，其余指令都能在其间并行铺开。可挖并行度大致是

ILP 可挖上限 ≈ 总指令数 / 关键路径长度

关键路径越短、旁支越宽，可挖并行越多。

不要以为"没有数据相关就能无限并行"。还有名字相关（需足够寄存器去重命名）、控制相关（需准确分支预测/投机去跨越）、内存别名不确定（需内存消歧）三重现实约束，任何一重不满足，实际可挖并行都会远低于理论上界。这正是下面极限研究要量化的事。

### 3.5.3 循环携带相关

循环级并行的关键判据是循环携带相关（loop-carried dependence）：一次迭代用到前面某次迭代产出的值。若循环无循环携带相关，各迭代完全独立，可任意并行（3.2 的展开/软件流水收益最大，也是向量化/DLP 的前提）；若存在循环携带相关，迭代间被串起来，可挖并行受限。

对照两例。`x[i] = x[i] + s;`（各元素独立）无循环携带相关，展开的各份迭代互不依赖，能并行。而 `x[i] = x[i-1] + s;`（本次用上次结果）有循环携带相关，第 i 次必须等第 i-1 次算完，展开也串成一条链，无法并行。编译器靠相关分析（dependence analysis，如对数组下标做 GCD 测试等）判定是否存在循环携带相关。

判断一个循环能否并行/向量化，第一步就是看有没有循环携带相关——有则受限，无则大有可为。这条判据把 3.2 的循环变换、3.5 的 ILP 极限、以及后续 DLP（大主题5 向量/SIMD）串到了一起：向量化本质就是利用"无循环携带相关"的循环把多次迭代同拍执行。

### 3.5.4 控制相关及其放松

控制相关规定"分支之后的指令，只有在分支走对应方向时才该执行"。它约束了指令能否被提前搬到分支之前。但控制相关在保证两条性质的前提下可以放松：不改变异常行为（不能因提前执行而多抛/漏抛异常）、不改变数据流（提前执行不能污染分支另一方向要用的值）。

放松控制相关的手段就是投机（speculation）：赌分支方向、把后续指令提前执行，赌对了赚到并行，赌错了作废（squash）。静态投机（3.3.4，编译器提前指令 + poison bit 安全网）与动态投机（AA-4.6，硬件预测 + ROB 回滚）都是在"安全地违反控制相关"。谓词执行（3.3.4）则更彻底，把控制相关直接转成数据相关（指令总执行，靠谓词决定是否生效）。

控制相关像"红灯前不许过路口"，投机就是"赌它要变绿、先冲过去，真红了再当没发生过"。之所以敢这么做，是因为分支很频繁（每几条指令一个），若严格遵守控制相关就几乎挖不到跨分支的并行。投机是突破单基本块并行天花板的必需品，但它把正确性责任转嫁给"猜错能干净回滚"的机制——这也是投机侧信道（Spectre/Meltdown，归安全课 L5-04）的物理根源，此处只点接缝，不深挖。

### 3.5.5 ILP 的理想极限研究

QA ch3 §3.10 做了一项经典的极限研究：假设一个"理想处理器"——无限发射宽度、完美分支预测、完美寄存器重命名（无限物理寄存器，消除一切名字相关）、完美内存消歧、单拍完成——去测 SPEC 类基准里到底藏着多少 ILP。结论是理想条件下可挖并行极大（远超任何现实机器），但每放松一个假设（有限窗口、真实分支预测、有限寄存器），可挖并行都会急剧塌缩到个位数附近的量级。

这项研究的意义是给"堆硬件挖 ILP"划了天花板：单靠拓宽发射、加大窗口，收益迅速递减，因为真数据相关的关键路径、有限的分支预测准确率、内存别名不确定这些现实约束是绕不过的。这直接解释了体系结构从"死磕单线程 ILP"转向多核（TLP，大主题6）与数据级并行（DLP，大主题5）的历史拐点，也呼应大主题1 的 Amdahl 定律——串行部分（此处即真相关关键路径）设定了加速上限。

具体的 IPC 数字随基准、随各理想假设的放松组合而大幅变化（教材研究结论，锚 QA §3.10；具体数值依基准与模型设定，不作单一现状结论，标「教材研究·数值随设定」）。初学者只需带走三条：其一，理想 ILP 很大但现实约束把它压得很低；其二，压制它的是真相关关键路径 + 有限预测 + 有限重命名 + 内存别名；其三，正因单线程 ILP 见顶，产业才转向多核与向量并行。这就把静态 ILP 这一大主题收束到"为什么并行要往 DLP/TLP 走"的下一步。
