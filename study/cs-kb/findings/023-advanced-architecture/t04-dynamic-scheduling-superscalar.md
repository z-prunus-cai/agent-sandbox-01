## 4.1 动态调度动机

### 4.1.1 动态调度是什么

动态调度（dynamic scheduling）指由硬件在运行期重排指令的执行顺序，让不相关的后续指令越过正在等待操作数的指令先执行，而不是像顺序流水线那样一遇停顿就全线卡住。它的核心是把"发射（issue，把指令送进执行部件）"与"按程序序推进"解耦：指令仍**按序取指、按序发射进队列**，但一旦操作数就绪就可以**乱序执行（out-of-order execution）**。

顺序流水线的痛点在于停顿会向后传染：若第一条指令在等一个慢结果（比如 cache miss 的 load 或长延迟浮点），紧跟其后、哪怕跟它毫无关系的指令也只能干等。动态调度让硬件在这段等待里去执行后面已经就绪的指令，把空闲的执行槽填满。

这里的关键直觉是"静态 vs 动态"分工：大主题3 里编译器在编译期靠循环展开、指令调度来暴露并行，但编译器看不到运行期才知道的信息（比如某次访存到底命中还是 miss、某个间接跳转到底去哪）。动态调度把调度权交给运行期的硬件，因此能处理编译期无法预知的动态延迟；代价是硬件复杂度和功耗大增。二者不是替代而是叠加：现代乱序核既吃编译器调度好的代码，又在运行期再动态重排一次。

### 4.1.2 顺序发射、乱序执行、乱序完成

要精确描述动态调度，需要把流水线的三个"顺序性"分开看：发射顺序（指令进入执行阶段的顺序）、执行完成顺序、写回/退休顺序。顺序流水线三者都严格按程序序；动态调度则允许执行与完成乱序，但通常保持取指与发射按序（便于检测相关），退休是否按序则要看有没有 ROB（见 4.4）。

用一句话概括各代方案的差别：

```
顺序流水线      ：按序发射、按序执行、按序完成
记分板/Tomasulo：按序发射、乱序执行、乱序完成（无 ROB 时不保证精确异常）
Tomasulo + ROB ：按序发射、乱序执行、乱序完成、按序退休（恢复精确异常）
```

为什么"乱序完成"是个麻烦而不是纯收益？因为一旦指令能乱序写结果，两条写同一寄存器的指令的先后就可能颠倒（WAW 冒险），异常也可能在程序序靠后的指令上先抛出（破坏精确异常）。整个大主题4 的机制，本质都在解决"要乱序执行的性能，又要顺序程序的语义正确"这对矛盾——重命名解名字相关，ROB 解乱序完成的语义问题。

### 4.1.3 记分板

记分板（scoreboard）是最早的动态调度硬件，源自 CDC 6600（1960 年代中期）。它是一张集中式的状态表，跟踪每条在飞指令处于哪一步、每个功能单元忙不忙、每个寄存器将由哪个功能单元写。指令按序发射，只要目标功能单元空闲且不产生 WAW 冲突就能发射进去，之后各指令在功能单元里独立推进，靠记分板检查相关、决定何时能读操作数、何时能写回。

记分板把每条指令分成四步推进：发射（issue，检查结构冒险与 WAW）、读操作数（read operands，等 RAW 真相关的源就绪）、执行（execution）、写回（write result，检查 WAR 冒险后才允许写）。

```
记分板四步：Issue → Read Operands → Execution → Write Result
每步都由记分板集中检查对应的冒险，不满足就在该步停住
```

记分板的关键局限正是它不做寄存器重命名：它靠"在发射处停顿来避 WAW、在写回处停顿来避 WAR"，也就是用停顿硬扛名字相关（WAR/WAW），而不是消除它们。因此当名字相关频繁时记分板会频繁卡住。此外它是集中式结构、且功能单元之间没有结果转发（要经寄存器堆中转），并发上限受限。理解记分板的意义在于：它点出了动态调度要解决的全部难题（相关检测、结构冲突、乱序），而 Tomasulo（4.2）正是针对"用停顿扛名字相关"这一短板给出的更优解。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch3 §3.4 前言与动态调度导入（顺序发射/乱序执行/乱序完成的划分、记分板作为 CDC 6600 的历史方案、四步流程与靠停顿处理 WAR/WAW 的局限）；核实 2026-07-30。
- 佐证：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.10 *Parallelism via Instructions*（乱序执行动机、in-order issue / out-of-order execution / in-order commit 的分层，与 QA 划分一致）。
- 一致性：两源对"发射按序、执行可乱序、完成/退休的顺序性决定语义正确性"表述一致。记分板细节 QA 讲得更全，COD 以概念带过，无冲突。
- 待核：记分板的四步命名依 QA ch3 编排；CDC 6600 年代作历史背景，不作精确年份结论。

## 4.2 Tomasulo 算法

### 4.2.1 Tomasulo 算法总览

Tomasulo 算法由 Robert Tomasulo 为 IBM System/360 Model 91 的浮点单元设计（1960 年代后期），是动态调度的奠基方案。相比记分板，它的两大进步是：用**保留站（reservation station）**做分布式的指令缓冲与操作数追踪，用**寄存器重命名**（通过保留站编号做标签）**消除**而非停顿式回避名字相关（WAR/WAW）。它让指令一发射就带着"操作数值或将来提供该值的来源标签"进保留站，之后完全由数据就绪驱动执行。

Tomasulo 把每条指令分成三步：发射（issue）、执行（execute）、写结果（write result）。

```
Tomasulo 三步：
  Issue         从指令队列取队首指令，若有空闲保留站则发射进去；
                源操作数已就绪则取值填入，未就绪则记下"由哪个保留站/来源会产出它"的标签
  Execute       保留站的两个源操作数都就绪后，指令进功能单元执行（可乱序）
  Write Result  结果算出后，连同本保留站的标签一起广播到公共数据总线 CDB
```

初学者最容易卡在"标签"这一层。核心心智模型是：寄存器堆里存的不再总是"值"，也可能是"一张欠条"——写着"这个值将来由某号保留站给出"。任何等这个值的指令，就在自己的保留站里记下这张欠条的编号；等那号保留站在 CDB 上广播结果时，所有记着这个编号的指令同时抓取，把欠条换成真值。这套"欠条 + 广播"机制就是隐式重命名的全部秘密。

### 4.2.2 保留站

保留站是挂在每个功能单元前的一组缓冲条目，每条保留站记录一条已发射但尚未执行完的指令所需的全部信息。它把指令从寄存器堆"解绑"：指令一旦发射进保留站，就不再回头读寄存器堆，之后要么用已抓到的值、要么等 CDB 广播，功能单元的调度只看保留站里的就绪位。

每个保留站条目通常含这些字段：

```
Op        该指令要做的操作（如加、乘）
Vj, Vk    两个源操作数的值（若已就绪）
Qj, Qk    两个源操作数的来源标签（若未就绪，记"将产出该值的保留站编号"；为 0 表示对应的 V 已就绪）
A         load/store 用于保存地址/偏移
Busy      本保留站是否被占用
```

理解 Qj/Qk 与 Vj/Vk 的互斥关系是关键：对每个源操作数，要么 V 里有值（Q 为 0），要么 Q 里有个等待的标签（V 无效）。发射时若寄存器状态表说"该源寄存器正被某保留站写"，就把那个保留站编号填进 Q；否则直接从寄存器堆读值填进 V。当两个 Q 都为 0（两源都就绪），这条保留站的指令才可以进功能单元。保留站数量多，就等于能同时"挂起"更多在等操作数的指令，从而挖出更多并行——这也是超标量核不断加大保留站/调度窗口的原因。

### 4.2.3 公共数据总线 CDB

公共数据总线（CDB, Common Data Bus）是 Tomasulo 的中枢广播通道。任何功能单元算出结果后，不是先写回寄存器堆再让别人去读，而是把"结果值 + 本保留站标签"一起放上 CDB，一拍之内广播给全机：所有保留站、寄存器堆、store 缓冲同时侦听。

CDB 广播的匹配逻辑是这样运作的：

```
功能单元产出结果 →  在 CDB 上广播 (标签 = 产出它的保留站号, 值 = 结果)
                    ↓（同一拍，所有侦听者比对）
每个保留站：若 Qj == 广播标签 → Vj ← 值, Qj ← 0 （该源就绪）
            若 Qk == 广播标签 → Vk ← 值, Qk ← 0
寄存器堆：  若该寄存器的等待标签 == 广播标签 → 写入值, 清除等待
```

CDB 是 Tomasulo 又快又省停顿的物理原因：结果直达所有消费者（相当于全局转发），不必经寄存器堆中转，省掉一次写回—读出的往返。但它也是硬件瓶颈——单条 CDB 每拍只能广播一个结果，若同拍多个功能单元完成就得仲裁或增设多条 CDB，而多条 CDB 上的标签比较器数量随保留站数与 CDB 数相乘增长，是超标量核里出了名的耗电大户。初学者只需记住：CDB = "谁算完了就冲全场喊一嗓子，等这个结果的都来抓"。

### 4.2.4 隐式寄存器重命名

Tomasulo 的重命名是"隐式"的：它没有一个显式的物理寄存器名字空间，而是用**保留站编号**充当临时的值容器名。当一条指令发射，它的结果目的地在寄存器状态表里被登记为"由第 N 号保留站产出"，于是后续读该寄存器的指令拿到的是标签 N 而非旧值；这就自动把同名寄存器的不同写入区分成了不同的保留站编号，WAR 与 WAW 名字相关随之消失。

举最小例子看 WAR 如何被消除：设序列

```
I1: F0 ← F2 + F4     （慢，F2 还没就绪）
I2: F4 ← F6 + F8     （要写 F4，与 I1 读 F4 构成 WAR）
```

顺序机里 I2 必须等 I1 读完 F4 才能写 F4。而 Tomasulo 中 I1 发射时已经把 F4 的当前值（或其来源标签）抓进自己的保留站 Vk/Qk，之后 I2 无论何时写 F4 都只改寄存器状态表和后续读者，动不到 I1 保留站里已抓好的那份——I2 完全不必等 I1，WAR 消失。WAW 同理：两条写 F0 的指令各自占不同保留站，最后谁的结果留在寄存器由发射顺序在状态表里覆盖决定，不会互相阻塞执行。

这解释了 4.3 为什么要把"重命名"单独拎出来讲：Tomasulo 用保留站做了重命名，但保留站数量有限、且值散在各处不便管理精确状态；现代乱序核改用**独立的物理寄存器堆**做显式重命名，思想同源、实现更规整。理解 Tomasulo 的隐式重命名，是理解显式重命名的最好台阶。

### 4.2.5 Tomasulo 与记分板对比

把两者并排看，能看清动态调度的进步方向。记分板集中式、无转发、靠停顿避 WAR/WAW；Tomasulo 分布式（保留站）、有 CDB 全局转发、靠重命名消除 WAR/WAW。

```
维度          记分板(CDC 6600)        Tomasulo(IBM 360/91)
结构          集中式记分板             分布式保留站
名字相关      靠停顿回避(发射/写回卡)   靠隐式重命名消除
结果传递      经寄存器堆中转           CDB 直接广播(全局转发)
WAR/WAW       会造成停顿               不停顿
```

核心结论是：Tomasulo 用"保留站 + CDB + 隐式重命名"把记分板的两大短板（无转发、名字相关靠停顿）一并解决，因此能挖出更高并行。它的思想直接活在今天每一颗乱序 CPU 里——保留站演化为发射队列/调度器，CDB 演化为结果转发网络，隐式重命名演化为显式物理寄存器重命名。二者都还缺一样东西：乱序完成时的精确异常，这要等 4.4 的 ROB 补上。

- 锚点：H&P《QA》6th ed, 2017, ch3 §3.5 *Overcoming Data Hazards with Dynamic Scheduling*（Tomasulo 三步 issue/execute/write result、保留站字段 Op/Vj/Vk/Qj/Qk/A/Busy、CDB 广播匹配、隐式寄存器重命名消除 WAR/WAW、IBM 360/91 背景）与 §3.4（与记分板对比）；核实 2026-07-30。

## 4.3 寄存器重命名

### 4.3.1 名字相关与为什么要重命名

名字相关（name dependence）指两条指令用了同一个寄存器名，但并没有真正的数据流动——分反相关（WAR, Write After Read）与输出相关（WAW, Write After Write）两种。它们不是真相关（RAW），纯粹是"寄存器名字不够用、被复用"造成的假冲突，因此原则上可以通过换个名字彻底消除。寄存器重命名（register renaming）就是硬件在运行期把每次写入映射到一个新的物理寄存器，从而让同一架构寄存器名的不同写入互不干扰。

区分真相关与名字相关是理解重命名的前提。真相关 RAW（读后写，指令要用前一条真正算出的值）是程序固有的数据流，无法消除，只能靠转发/调度缩短等待；而 WAR、WAW 只是名字撞车。举例：

```
I1: R1 ← R2 + R3
I2: R4 ← R1 × R5     （RAW：真的要 I1 的 R1，不可消除）
I3: R1 ← R6 + R7     （WAR：I3 写 R1 与 I2 读 R1 撞名；WAW：I3 写 R1 与 I1 写 R1 撞名）
```

I3 与前面并没有数据要传递，只是又想用 R1 这个名字。重命名把 I3 的 R1 换成一个全新的物理寄存器（比如 P37），I3 就能立刻和 I1/I2 并行，假冲突消失。为什么架构寄存器名"不够用"？因为 ISA 只给了有限个（如 32 个）程序员可见寄存器，而乱序核里同时在飞的指令远多于此，必须用一个大得多的物理寄存器池去承接。

### 4.3.2 物理寄存器堆式重命名

现代乱序核主流采用显式的物理寄存器堆（physical register file）方案：设一个远大于架构寄存器数的物理寄存器池，配一张**重命名映射表（register alias table, RAT）**记录每个架构寄存器当前映射到哪个物理寄存器。每遇到一条会写寄存器的指令，就从空闲链表（free list）取一个新物理寄存器分配给它的目的，并更新映射表；读源寄存器时则查映射表拿到当前物理寄存器号。

重命名阶段每条指令做的动作可归纳为：

```
读源：  对每个源架构寄存器，查 RAT → 得到当前物理寄存器号（作为源）
分配目的：从 free list 取一个空闲物理寄存器 Pnew
更新：  RAT[目的架构寄存器] ← Pnew（后续读者将看到 Pnew）
记录：  旧映射（被覆盖的物理寄存器号）存入 ROB，供退休时回收
```

这样一来，同一架构寄存器的每次写都落到不同物理寄存器，WAR/WAW 从根上不存在了，剩下的指令间关系只有 RAW 真相关（表现为"源物理寄存器还没被写"）。这套显式方案相比 Tomasulo 隐式重命名的好处是：值集中存在物理寄存器堆里便于管理、精确状态更好维护（配合 ROB）、可支持更大的重命名深度。初学者可以把 RAT 理解成"架构名 → 物理名"的实时翻译词典，每写一次就给这个架构名换一个全新的物理名。

### 4.3.3 物理寄存器的回收

物理寄存器是有限资源，必须回收，否则很快耗尽。回收的时机很讲究：一个物理寄存器只有在"再没有任何在飞指令会读它"之后才能放回空闲链表。常用判据是——当一条更新了同一架构寄存器的**后继指令退休**时，它所覆盖的那个**旧物理寄存器**就可以回收（因为此后所有读该架构名的指令都已改读新物理寄存器）。

这就是为什么 4.3.2 里重命名时要把"旧映射"记进 ROB：退休（4.4）时才拿出来把旧物理寄存器还给 free list。

理解回收时机的易错点在于：不能在指令一执行完就回收它写的物理寄存器，因为可能还有更早发射、更晚执行的指令要读它；也不能在被覆盖时立刻回收旧值，因为投机路径上的指令、以及尚未退休的读者可能还需要它。把回收绑定到"覆盖它的指令退休"这一按序事件上，既安全又简单。物理寄存器数量因此直接限制了乱序窗口能开多大——池子越大，能同时在飞、能投机越深的指令越多。

### 4.3.4 重命名与保留站/ROB 的分工

重命名解决的是"名字相关"，它与保留站（调度就绪指令）、ROB（保证按序退休与精确异常）是三件分工不同、协作运行的事，初学者极易混为一谈。重命名在发射前的重命名阶段一次性完成名字→物理名的翻译；保留站/发射队列负责在操作数就绪后把指令派给功能单元（做乱序调度）；ROB 负责让所有指令的结果**按程序序对外生效**。

两种主流微架构组织方式值得点明：一种把值存进保留站（Tomasulo 式，值随指令流动），一种把值集中存进物理寄存器堆、保留站只存物理寄存器号（现代主流，值不流动、只传号）。后者省掉了在保留站与 ROB 间反复搬运数据的开销，是当代乱序核的通行做法。

核心结论：名字相关由重命名消除，真相关由调度/转发处理，乱序完成的语义正确由 ROB 兜底——三者各司其职，缺一不可。把这条分工记牢，再看任何一款乱序核的框图都不会晕。

- 锚点：H&P《QA》6th ed, 2017, ch3 §3.5（隐式重命名消除 WAR/WAW 的原理）与 §3.6（结合 ROB 的重命名与物理寄存器管理、旧映射保存与退休回收）；核实 2026-07-30。
- 佐证：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.10（重命名 + 物理寄存器 + 提交的乱序执行模型）；与大主题3（AA-3.5）名字相关分类互为印证——静态视角指出名字相关可由重命名消除，此处给出硬件实现。

## 4.4 ROB 与精确异常

### 4.4.1 精确异常问题

精确异常（precise exception）指当异常（如缺页、除零、非法指令）发生时，处理器能呈现一个干净的架构状态：异常指令之前的所有指令都已完成、它之后的一条都未生效，就好像程序严格顺序执行到该点被打断。乱序执行天然破坏这一点——后发的指令可能已经算完并改了寄存器，而前面某条才抛异常，架构状态成了"乱序完成"的中间态，无法精确定位断点。

为什么精确异常非要不可？因为操作系统要靠它做缺页处理后重新执行、调试器要靠它单步、异常处理程序要靠它拿到一致的现场。没有精确异常，虚拟内存、可靠调试、可恢复的浮点异常都无从谈起。

这就是纯 Tomasulo/记分板（乱序完成、无 ROB）的致命缺口：它们性能好但不保证精确异常，因此 IBM 360/91 当年的浮点异常就是不精确的。4.4 的 ROB 正是为在保留乱序执行性能的同时恢复精确异常而生。

### 4.4.2 重排序缓冲 ROB

重排序缓冲（ROB, Reorder Buffer）是一个按程序序管理所有在飞指令的循环队列（FIFO）。指令在发射时按序进入 ROB 队尾，执行可以乱序完成、结果先写进对应 ROB 条目（或物理寄存器）打上"就绪"标记，但只有当一条指令走到 ROB 队头且已就绪时，才允许**退休/提交（commit/retire）**——即把结果真正写入架构可见状态（架构寄存器堆或内存）。这样"对外生效"这一步被强制拉回程序序。

加入 ROB 后，指令生命周期扩成四步：

```
Issue        → 按序发射、分配 ROB 条目（占队尾）、重命名
Execute      → 操作数就绪后乱序执行
Write Result → 结果写入 ROB 条目/物理寄存器，标记就绪（此时对外仍不可见）
Commit       → 指令到达 ROB 队头且就绪，按序提交：写架构状态；有异常则此刻处理
```

每个 ROB 条目通常记录：指令类型、目的寄存器（或内存地址）、结果值或其物理寄存器号、就绪位、以及是否发生异常的标记。关键点在于"执行完成 ≠ 生效"：结果早早算出来了，但被 ROB 扣在手里，直到轮到它按序提交才放行。这一层缓冲就是让"乱序执行的性能"与"按序生效的语义"共存的机关。

### 4.4.3 按序退休与投机回滚

ROB 让所有对架构状态的修改都在提交阶段按程序序发生，于是异常处理变得干净：把异常标记挂在 ROB 条目上，一路带到队头，等这条指令要提交时才真正抛出异常，此刻它之前的指令都已提交、之后的都还没提交且尚在 ROB 里，一律作废（flush）即可——架构状态恰好停在异常指令之前，精确异常达成。

同一套机制天然支持分支投机的回滚。分支预测（4.5）让处理器在分支结果未知时就沿预测方向继续取指执行，这些都是投机指令、进 ROB 但暂不提交；当分支在队头附近被判定预测错误，就把 ROB 里该分支之后的所有条目清空、恢复重命名映射、从正确目标重新取指。

```
分支预测错误恢复：
  1. 检测到误预测（分支执行完，实际方向 ≠ 预测方向）
  2. 清空 ROB 中该分支之后的所有条目（丢弃投机结果）
  3. 恢复 RAT 映射与 free list 到分支点的状态
  4. 从正确的分支目标重新取指
```

初学者可以把 ROB 想成"结果的候车厅"：谁先算完都能进来坐着，但必须按买票（程序）顺序检票出站；异常/误预测就是"取消这一站之后所有人的票"。正因为提交是按序的、且只有提交才动架构状态，回滚才能做到只丢投机部分、不伤已确认部分。这也正是投机执行敢大胆猜的底气所在（4.6）。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch3 §3.6 *Hardware-Based Speculation*（ROB 四步 issue/execute/write result/commit、按序提交恢复精确异常、投机指令进 ROB 暂不提交、误预测/异常时 flush 与恢复）；核实 2026-07-30。
- 佐证：P&H《COD》RISC-V 2nd ed, 2020, ch4 §4.10 与 §4.9（乱序 commit 阶段、精确异常与流水线冲刷）；精确异常概念上承 L3-02 CO-5.6（顺序流水线的精确异常）。
- 一致性：两源一致：ROB 提供按序提交点，异常/误预测在提交时处理以保精确异常与投机回滚，无冲突。
- 待核：ROB 条目字段与容量为实现相关；IBM 360/91 浮点异常不精确作历史背景陈述。

## 4.5 分支预测

### 4.5.1 为什么要分支预测

分支预测（branch prediction）在分支指令的方向（taken/not-taken）和目标地址尚未算出时，就预测它并据此继续取指、投机执行后续指令，以填满流水线、避免控制相关造成的空转。深流水、宽发射的处理器里分支约每几条指令就出现一个，若每遇分支都等它算完（可能十几拍后）再取下一条，流水线大半时间在冒泡，ILP 无从谈起，因此分支预测是超标量投机核的命门。

预测错误的代价随流水线加深、发射加宽而放大：误预测要清空整条流水线里所有投机指令、从正确目标重灌，惩罚可达十几到几十拍。所以预测准确率的每一点提升都极其值钱，这也是分支预测器结构不断演进、越做越复杂的根本动力。

分支预测分两个子问题，别混淆：预测**方向**（这个条件分支跳不跳）与预测**目标**（若跳，跳到哪个地址）。4.5.2–4.5.5 讲方向预测器的演进，4.5.6 讲目标预测（BTB/RAS）。

### 4.5.2 1-bit 与 2-bit 饱和计数器

最简单的动态方向预测用一张分支历史表（BHT, Branch History Table），按分支地址低位索引，每项存 1 或 2 个比特记录该分支近来的行为。1-bit 预测器只记"上次跳没跳"、下次照抄，缺点是每次行为翻转都错、循环边界会连错两次。2-bit 饱和计数器（2-bit saturating counter）用四个状态给预测加"惯性"，要连续错两次才改变预测方向，对偶尔翻转的分支（如循环回边）鲁棒得多。

2-bit 计数器的四个状态与转移：

```
状态：  00 强不跳   01 弱不跳   10 弱跳   11 强跳
预测：  00/01 预测不跳 ，10/11 预测跳
更新：  实际跳 → 计数 +1（饱和于 11）；实际不跳 → 计数 -1（饱和于 00）
```

为什么 2-bit 比 1-bit 好？拿一个跑很多次的内层循环回边分支举例：它绝大多数迭代都"跳"（回到循环开头），只有最后一次退出时"不跳"。1-bit 预测器会在退出那次错一次、下次进入循环又错一次（因为它把退出记成了新习惯），一个循环错两次；2-bit 有惯性，退出那一次错了但状态只从"强跳"退到"弱跳"仍预测跳，下次进入循环立刻对，一个循环只错一次。这就是"加一个比特换来的惯性"。

### 4.5.3 相关预测器与 gshare

2-bit 计数器只看单个分支自己的历史，抓不住"分支之间相互关联"的规律（比如 if (a) 与 if (a && b) 的方向高度相关）。相关预测器（correlating predictor，又称二级预测器 two-level predictor）引入**全局历史寄存器（GHR, Global History Register）**——一个移位寄存器，记录最近若干个分支的实际方向；用"分支地址 + 全局历史"共同索引计数器表，从而让预测依赖上下文。

gshare 是 McFarling（1993）提出的经典相关预测器，用分支地址与全局历史的**异或**来索引 2-bit 计数器表：

```
索引 = (分支地址低位) XOR (全局历史寄存器 GHR)
用该索引查 2-bit 计数器表 → 得到方向预测
```

用异或而非拼接的巧妙之处在于：拼接会浪费表项（地址与历史各占一段位、组合稀疏），异或把两者揉进同一段位、让表项利用更充分，在相同硬件预算下往往更准。gshare 是"用全局历史抓分支间相关"这一思想最简洁有效的实现，长期是教科书基准。初学者记住一条主线：预测器演进的核心就是"喂给它越来越丰富的上下文"——从只看自己（2-bit）到看全局历史（gshare）到看多种历史长度（TAGE）。

### 4.5.4 竞赛/混合预测器

没有单一预测器对所有分支都最优：有的分支靠局部历史（自己的行为规律）准，有的靠全局历史（与别人的关联）准。竞赛预测器（tournament predictor，又称混合预测器 hybrid predictor）同时跑两个（或多个）子预测器，再用一个"选择器"表（本身也是一组 2-bit 计数器，按分支索引，学习"对这个分支哪个子预测器近来更准"）动态挑选采信哪个的输出。

竞赛预测器的意义是把"选局部还是选全局"这件事也交给硬件学习，而不是设计时一刀切。它在 1990 年代末—2000 年代的高性能处理器（如 Alpha 21264）里成为标配，是 gshare 到 TAGE 之间的过渡形态。理解它只需一句：多养几个"预测顾问"，再养一个"HR"按业绩动态决定听谁的。

### 4.5.5 TAGE

TAGE（TAgged GEometric history length predictor，Seznec & Michaud, 2006）是当代准确率最高的一类方向预测器，也是近年学术竞赛（如 CBP 分支预测锦标赛）冠军方案的基础。它用**多张**打了标签的预测表，各表分别以**几何递增**的不同全局历史长度做索引（如历史长度按 0、2、4、8、16、…几何级数增长）；预测时取"命中且使用最长历史"的那张表的结果，短历史表作为兜底。

TAGE 的核心思想可归纳为：

```
多张表，各表用不同长度的全局历史 + 分支地址计算索引与标签
历史长度呈几何级数：L(i) ≈ α^i 递增（覆盖从很短到很长的关联）
预测 = 命中的表中"使用历史最长"者的结果；都不命中则用基础 2-bit 表兜底
```

为什么"几何递增的多历史长度"是关键突破？因为不同分支的可预测性依赖的历史跨度差异极大——有的只跟上一个分支相关（短历史就够），有的要看几十个分支之前的模式（需长历史）。单一固定历史长度（如 gshare）无法同时照顾两端；TAGE 用一排从短到长的历史表覆盖全谱，再让"最长命中优先"自动为每个分支选中最合适的历史长度，因而显著更准。

⚙演进快·锚论文：TAGE 属活跃演进的前沿方向，具体变体（TAGE-SC-L 加统计校正器与循环预测器等）与准确率随实现与基准而变，本节只给原理，不作具体数值/名次的现状结论。QA 6th ed ch3 对方向预测器的讲解主要到相关/竞赛预测器层面并提及带标签的混合思路；gshare 与 TAGE 的细节以其原始论文（McFarling 1993；Seznec-Michaud 2006）为一手来源，与教材分账。

### 4.5.6 BTB 与 RAS

方向预测只解决"跳不跳"，还要知道"跳到哪"。分支目标缓冲（BTB, Branch Target Buffer）是一张按分支地址索引的缓存，存最近跳转的目标地址，让处理器在取指阶段（还没译码出这是分支、更没算出目标之前）就能拿到预测目标继续取指，避免为等目标而停顿。返回地址栈（RAS, Return Address Stack）则专门预测函数返回（ret）的目标：调用（call）时把返回地址压入这个小硬件栈，返回时弹出栈顶作为预测目标，因为函数返回的目标高度符合后进先出规律，用普通 BTB 反而不准。

```
BTB：按分支 PC 索引 → 预测目标地址（用于普通跳转/分支）
RAS：call 压栈返回地址，ret 弹栈作为返回目标预测（后进先出，专治函数返回）
```

初学者要把"方向预测器（BHT/gshare/TAGE）"与"目标预测器（BTB/RAS）"分开：前者预测条件分支跳不跳，后者预测跳到哪，二者协同才能在取指阶段完全不停顿地沿投机路径推进。易错点是间接跳转（如虚函数、switch 跳转表）的目标预测最难——目标不固定，单一 BTB 项常预测错，需要更复杂的间接分支预测器，这也是现代核持续投入的方向（⚙演进快）。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch3 §3.3 *Reducing Branch Costs with Advanced Branch Prediction*（1-bit/2-bit 饱和计数器与四状态、相关/二级预测器与全局历史、竞赛/混合预测器、带标签混合预测思路、BTB 与返回地址栈）；核实 2026-07-30。

- 一致性：教材与论文对"喂入更丰富上下文（局部→全局→多历史长度）以提升准确率"的演进主线一致；2-bit 四状态、gshare 异或索引、TAGE 几何历史三点在各自一手来源内自洽。

## 4.6 投机与内存级并行

### 4.6.1 硬件投机

硬件投机（hardware-based speculation）把动态调度、分支预测、ROB 三者合体：用分支预测猜出执行路径，沿该路径乱序执行后续指令，但所有结果先扣在 ROB 里按序提交，一旦预测错误就把投机部分全部作废。它让处理器能越过分支边界挖并行——不再被"每个基本块只有几条指令"的控制相关天花板卡死。

投机执行的正确性完全建立在"能干净回滚"之上，而这正是 4.4 的 ROB 提供的：投机指令允许乱序执行、允许把结果写进 ROB/物理寄存器，但**绝不允许在提交前修改架构可见状态**（架构寄存器、内存）。只要投机结果没提交，撤销它就只是清 ROB 条目、恢复重命名映射，代价可控。

三大机制的分工到此闭环：分支预测提供"猜哪条路"，重命名 + 保留站提供"乱序执行的引擎"，ROB 提供"猜错能反悔"的安全网。这就是现代乱序超标量处理器的完整骨架。

### 4.6.2 多发射与超标量

超标量（superscalar）指每个时钟周期能取指、发射、提交**多条**指令（发射宽度 > 1），从而把 IPC（每周期指令数, Instructions Per Cycle）推到 1 以上。它与动态调度是两个正交维度：超标量讲"每拍处理几条"，动态调度讲"是否乱序"；现代高性能核是"多发射 + 乱序 + 投机"三者叠加。理想 CPI 与 IPC 互为倒数：

```
IPC = 1 / CPI理想   （单发射顺序机 IPC ≤ 1；n 路超标量理想 IPC 上界为 n）
```

要真正兑现多发射的潜力，必须同时拓宽整条流水线：每拍取多条指令、并行重命名多条、保留站/调度器每拍唤醒并派发多条、多个功能单元、多条 CDB/多写端口、ROB 每拍提交多条。任何一环成为窄口都会拖垮实际 IPC。这也是为什么发射宽度不能无限加大——唤醒/选择逻辑、重命名端口、旁路网络的复杂度大致随宽度平方增长，功耗与时序迅速吃不消（呼应大主题3 的 ILP 极限：硬件挖并行收益递减）。

初学者别把"超标量"与"乱序"划等号：存在顺序超标量（每拍多发但不乱序，如早期某些设计）与乱序超标量（主流）。也别把发射宽度当成实测 IPC——真实 IPC 受相关、cache miss、误预测拖累，通常远低于宽度上界。具体宽度是⚙演进快的微架构参数，随代际变化，不作单一现状数值结论。

### 4.6.3 内存级并行

内存级并行（MLP, Memory-Level Parallelism）指同时容忍多个未完成的内存访问（尤其多个并行的 cache miss），用后面的访问延迟去重叠前面的，而不是一个 miss 就停到底。乱序 + 投机核靠此把长内存延迟藏起来：借助非阻塞 cache 与 MSHR（miss status holding register，见 AA-2.3）挂起多个在飞 miss，配合乱序访存让独立的 load 提前发出。

乱序访存需要专门的**加载/存储队列（load/store queue）**与**内存消歧（memory disambiguation）**来保证正确性：store 的地址可能要到较晚才算出，硬件必须判断一个较晚的 load 是否与某个较早、地址未知的 store 指向同一地址（有则必须等、否则可提前执行）。

```
内存消歧：较晚的 load 想提前执行时，须确认它不与任何较早的未决 store 同地址
  - 保守：等所有较早 store 地址已知再放行 load（安全但慢）
  - 投机：赌不冲突、提前放行 load；若事后发现同地址（store-load 别名）则回滚重执
```

为什么 MLP 对性能如此关键？因为内存延迟（尤其 DRAM）动辄上百拍，若串行等待，再宽的乱序核也会被内存墙卡死；能同时发起多个独立 miss、让它们的延迟重叠，等效于把内存带宽用起来、把延迟摊薄。这把 4.6 与内存层次（大主题2）扣在一起：乱序投机核之所以要非阻塞 cache 与深访存队列，正是为了榨取 MLP。

### 4.6.4 投机侧信道接缝

投机执行虽然架构上"猜错能干净回滚"（不改架构状态），但它在回滚前已经改变了**微架构状态**——最典型是把某些数据带进了 cache。投机侧信道攻击（如 Spectre、Meltdown，2018 年公开）正是利用这一点：诱导处理器投机地访问了本不该访问的数据，虽然结果被作废，但它在 cache 等微架构结构里留下的痕迹可被计时旁路探测出来，从而泄露秘密。

这暴露了"架构正确 ≠ 微架构无泄露"这一深刻裂缝：ROB 保证了架构状态的精确回滚，却没人保证投机路径不在 cache/预测器/端口占用上留下可观测残迹。

本报告只点这条接缝，攻击原理、变体分类与缓解措施（如 retpoline、投机屏障、微码更新等）归 L5-04 信息安全课，不在此深挖（遵循 prompt 的分账要求）。初学者带走一句即可：投机执行是性能利器，但"猜错回滚"只回滚了架构状态、回滚不了它在硬件上留下的时间/占用痕迹，这正是一整类硬件安全问题的物理根源。
