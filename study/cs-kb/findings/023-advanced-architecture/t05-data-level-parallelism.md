## 5.1 向量处理器（AA-5.1）

### 5.1.1 数据级并行与向量处理器的基本思想

数据级并行（DLP, Data-Level Parallelism）指的是同一个操作要施加到大量彼此独立的数据元素上——例如把一个数组的每个元素都乘以常数。向量处理器（vector processor）就是为这种模式定制的机器：它用**一条**向量指令表达"对一整排数据做同一操作"，硬件再用若干条并行的执行车道把这排数据一起算掉。这属于 Flynn 分类里的 SIMD（Single Instruction, Multiple Data，单指令多数据）。

它和普通标量处理器（一条指令算一个数）最本质的区别，是把并行性显式写进了指令语义。为什么这样划算？因为对 N 个元素，标量代码要取 N 条加法指令、译码 N 次、判 N 次循环边界；向量代码只取一条向量加法，指令数与相关的取指/译码/分支开销一下子降到 1/N 量级。省下的不只是执行部件的钱，更是前端（取指译码）与控制（循环分支）的开销——这正是 DLP 相对 ILP 的效率优势：并行度是"声明"出来的，不用硬件费力去动态挖掘。

初学者容易把"向量处理器"和"多核"混淆。多核（TLP，线程级并行）是多个独立的指令流各干各的；向量是**一个**指令流、一条指令铺开处理多份数据。也不要把它和超标量（ILP）混淆：超标量是一拍发射多条**不同**指令，向量是一条指令覆盖多份**相同**操作的数据。记住这条主线：DLP 用"数据多、操作同"换掉了大量重复的控制开销，后面 5.2 的 SIMD、5.3 的 GPU 都是这同一思想的不同封装。

### 5.1.2 向量寄存器与向量指令（RV64V 教学模型）

向量处理器的核心存储是**向量寄存器（vector register）**：一个寄存器不再存一个标量，而是存一整排元素（例如 32 个 64 位元素）。H&P 6th ed 用 RISC-V 向量扩展的教学版 RV64V 举例，典型配置为 8 个向量寄存器 v0–v7，每个能容纳一批元素；配套的向量 load/store 指令负责在内存与向量寄存器之间成批搬运，向量算术指令（如向量加、向量乘）则对两个向量寄存器逐元素运算写回第三个。

一段最小的向量代码大致长这样（把标量 s 乘进向量 x 再加上向量 y，即 SAXPY）：

```
vld   v0, x        ; 把数组 x 的一批元素装入向量寄存器 v0
vld   v1, y        ; 把数组 y 的一批元素装入 v1
vmul  v0, v0, s    ; v0 的每个元素乘以标量 s
vadd  v0, v0, v1   ; v0 += v1（逐元素）
vst   v0, x        ; 写回
```

这五条向量指令，替代了标量版里以元素个数为倍数的一长串指令 + 循环。为什么向量寄存器比"一堆标量寄存器"强？因为向量 load 一次发起就搬一整排，能把内存访问组织成规整的顺序流、喂满内存带宽；而且逐元素操作之间天然无相关，硬件可以放心并行或流水，不必逐条检查冒险。初学者需要建立的直觉：向量寄存器是"批处理的容器"，向量指令是"对整个容器做一件事"，元素之间的独立性是编译器/程序员保证的、写进指令语义的，这就是它不需要复杂乱序硬件也能高吞吐的原因。

### 5.1.3 Lane（车道）与向量执行的数据流

**车道（lane）**是向量处理器里并行工作的执行单元切片。一条向量指令要处理的所有元素，被均匀分配到若干条 lane 上；每条 lane 有自己的一份功能单元和向量寄存器分片，负责其中一部分元素。若有 4 条 lane、要算 32 个元素，则每条 lane 顺次处理 8 个元素，四条同时干活，整体吞吐约为单 lane 的 4 倍。

一条向量加法在 4 条 lane 上的执行大致是这样铺开的：

```
向量寄存器按元素下标切成 4 片，分别驻留在 lane0..lane3
lane0: 元素 0,4,8,...    →  各自的加法器  →  写回本片
lane1: 元素 1,5,9,...    →  各自的加法器  →  写回本片
lane2: 元素 2,6,10,...   →  各自的加法器  →  写回本片
lane3: 元素 3,7,11,...   →  各自的加法器  →  写回本片
（同一条 vadd 指令，四条 lane 并行推进；每条 lane 内部还可流水化连续元素）
```

要分清两个维度的并行。一是 lane 的**空间并行**：多条 lane 同拍处理不同元素。二是每条 lane 内的**流水线并行**：同一条 lane 把它负责的连续元素像流水线一样一个接一个喂进功能单元。为什么这样设计而不是给每个元素配一个功能单元？因为那样太贵；lane 数是成本与吞吐的折中，加 lane 就近似线性加吞吐，是向量机最直接的扩展旋钮。易错点：lane 数变了不改变程序语义，只改变一条向量指令要花几拍——这与后面 5.3 GPU 用固定 warp 宽度 + 时间复用的做法形成对照。

### 5.1.4 向量链接（chaining）

**链接（chaining）**是向量流水线的关键优化：当一条向量指令的结果要作为下一条向量指令的输入时，不必等整个结果向量全部算完写回，而是每算出一个元素就立即转发给下一条指令开始处理。这相当于把向量层面的转发/旁路做到了元素粒度，让相关的两条向量指令在时间上大幅重叠。

举例 `vmul` 之后紧跟 `vadd`（乘的结果要被加用到）。没有链接时，必须等 `vmul` 把整排元素都算完、写回向量寄存器，`vadd` 才能开始，两条指令的时间几乎串行相加。有链接时，`vmul` 产出第 0 个元素的当拍，`vadd` 就能拿它开工；两条指令像瓦片一样叠起来跑，总时间约等于"一条指令的时间 + 少量启动延迟"，而不是两条相加。

初学者可以把链接类比成工厂流水线：上一道工序做完一个零件立刻传给下一道，而不是攒齐一整批再传。为什么这对向量机特别重要？因为向量寄存器很长（元素多），"等整排算完"的代价被放得很大，链接把这段等待几乎完全消掉。链接是向量机能把多条相关向量指令跑出接近峰值吞吐的核心手段，理解它才能看懂为什么向量代码即使有依赖也不像标量那样处处停顿。

### 5.1.5 条带挖掘（strip mining）与向量长度

现实中要处理的数组长度 n 是任意的，而向量寄存器一次只能装固定的最大元素数（记为 MVL, Maximum Vector Length，或在 RV64V 里由可设置的向量长度寄存器 vl 控制）。**条带挖掘（strip mining）**就是把长度为 n 的循环切成若干"条带"：每条处理 MVL 个元素，最后剩下不满一整批的尾巴单独处理一次。它是把任意长循环映射到定长向量硬件的标准手法。

其迭代结构可以写成：

```
处理批数 = ⌈n / MVL⌉
第 0 批：处理 n mod MVL 个元素（把不整齐的尾巴先清掉，令后续都是整批）
其余每批：处理 MVL 个元素，共 ⌊n / MVL⌋ 批
（RV64V 用 setvl 指令按剩余元素数动态设置 vl，硬件自动收尾，无需程序员手写尾循环）
```

为什么需要它？因为不做条带挖掘，程序就得假设 n 恰好是 MVL 的整数倍，这在真实数据上几乎不成立。RV64V 这类"向量长度可编程"的设计（vector-length agnostic）相比早期固定长度 SIMD 的一大进步，正是让同一份二进制不改代码就能在不同 MVL 的硬件上跑——尾部由 vl 自动处理。初学者要点：条带挖掘不是算法优化，而是"把任意长度塞进定长硬件"的必备胶水；它引入的少量开销（每批一次的循环控制、可能的一次不满批）正是向量化收益需要摊薄的对象，短数组上向量化不划算多半就栽在这里。

### 5.1.6 跨步/聚散访问与向量掩码

真实数据不总是连续排列，向量机因此提供两类特殊访存。**跨步访问（strided access）**按固定间隔取元素（如取矩阵的一列，每隔一行距离取一个），用一条带步长的向量 load 表达。**聚集/散射（gather/scatter）**按一个下标向量做间接寻址（如 `x[index[i]]`），把稀疏或不规则分布的元素凑成一个向量、或写回去，是向量机处理稀疏矩阵、查表的手段。

此外**向量掩码寄存器（vector mask register）**给每个元素配一位开关：置 0 的元素本次运算被跳过（不写结果）。这让向量机能表达"条件执行"——把 `if (a[i]>0) ...` 编译成"先算出比较结果做掩码，再在掩码下做后续运算"，而不必对每个元素真的分支。

初学者要理解这几个机制解决的是"数据不规整"和"有条件"两个麻烦。跨步/聚散的代价是访存不再连续、带宽利用率下降（聚散尤其可能每元素一次独立访存），所以能用连续访问就别用聚散——这是性能上的大坑。掩码则是把控制流转成数据流的关键：它避免了向量内部的分支，但被掩掉的 lane 仍然占着时间在空转（算了不写），所以掩码只是"正确地跳过写回"，并不省下那部分执行时间。这一点正是 5.4 GPU 分支发散惩罚的同源现象，二者本质相同。

## 5.2 SIMD 扩展（AA-5.2）

### 5.2.1 多媒体 SIMD 扩展与"真"向量机的区别

SIMD 多媒体扩展（SIMD multimedia extension）是把向量思想以有限、固定宽度的形式塞进通用 CPU 指令集的产物，例如 x86 的 SSE/AVX、ARM 的 NEON。它给通用寄存器堆之外加一组宽寄存器（如 128/256/512 位），一条 SIMD 指令把这个宽寄存器切成若干个同样大小的"通道"（如 512 位切成 16 个 32 位 float）同时运算——这叫**打包（packed）**运算。

它与 5.1 的"真"向量机有三点关键区别，务必分清。其一，宽度**固定且较窄**且写死在指令编码里（早期 SSE 就是 128 位），不像向量机有可编程的向量长度寄存器；宽度升级要靠新增指令集（SSE→AVX→AVX-512），旧二进制吃不到新宽度。其二，早期缺少条带挖掘/gather-scatter/掩码等完整机制，处理不规整数据和收尾很笨拙（AVX-512 才补上掩码与聚散）。其三，它是通用 CPU 上的"附加"部件，与标量代码混跑，而非独立的向量协处理器。

SIMD 扩展是"简化版、固定宽度、长在 CPU 里的向量机"。它换来的好处是不需要单独的向量处理器、复用现有流水线，代价是宽度受限、每次加宽都要动 ISA。为什么厂商还是走这条路？因为多媒体、科学计算、现在的 AI 推理都有大量规整 DLP，在通用核里加宽 SIMD 是"花小钱办大事"。理解了这层，就懂了 5.2.2 为什么 x86 的 SIMD 宽度是一路加倍演进上来的。

### 5.2.2 x86 SIMD 的演进（⚙演进快·锚版本）

x86 的 SIMD 扩展沿"寄存器不断加宽 + 功能不断补齐"演进，是典型的**演进快、需锚版本**的对象：

```
MMX(1997)        64 位，整数打包，复用 x87 浮点寄存器
SSE(1999)        128 位 XMM 寄存器，单精度浮点打包
SSE2(2001)       128 位扩到双精度浮点与整数
AVX(2011)        256 位 YMM，三操作数非破坏性编码（VEX）
AVX2(2013)       256 位整数全面化 + FMA（融合乘加）+ gather
AVX-512(2016–)   512 位 ZMM，掩码寄存器 k0–k7，聚散/压缩，分多个子集
```

必须强调 AVX-512 不是单一整体，而是一族子集（如 AVX512F 基础、AVX512BW 字节/字、AVX512CD 冲突检测、AVX512DQ、AVX512VL 让 512 位能力用于 128/256 位寄存器……），不同 CPU 支持的子集不同，写代码前要按目标机的实际标志判定。本机（核实 2026-07-30，`/proc/cpuinfo`）确认支持 `avx512f avx512bw avx512cd avx512dq avx512vl` 等子集。

一是**宽度**从 64→128→256→512 位一路翻倍，同一条指令能打包的元素数随之翻倍；二是**编码与功能**在补课——AVX 引入三操作数（结果不再覆盖源操作数）、AVX2 补上 FMA（乘加一条指令、一拍出结果，既省指令又提精度）、AVX-512 才终于补齐掩码与聚散，逼近"真"向量机的表达力。易错点：H&P 6th ed（2017）正文主要讨论到 AVX/AVX2（256 位）时代，对 AVX-512 只是新兴提及；AVX-512 的确切子集、频率降档行为（早期实现开满 512 位会降频）等属厂商实现细节，必须以 Intel SDM/Intrinsics Guide 的对应版本为准，不以教材为现状结论——这正是本节硬标 ⚙演进快 的原因。

### 5.2.3 AVX-512：ZMM 寄存器与掩码寄存器

AVX-512 提供 32 个 512 位向量寄存器 ZMM0–ZMM31（其低 256/128 位分别别名为 YMM/XMM，向后兼容），一个 ZMM 可打包 16 个 32 位 float、或 8 个 64 位 double、或更多窄整数。配套新增 8 个**掩码寄存器（mask/opmask register）k0–k7**：每条 AVX-512 指令可挂一个掩码，按位控制哪些通道写回结果（其中 k0 常作"无掩码"的特殊约定）。

掩码有两种作用模式。**merge-masking**：被掩掉的通道保留目的寄存器原值。**zero-masking**：被掩掉的通道写 0。这让 `if` 型条件运算在向量内无分支地表达出来——先用比较指令生成掩码，再在掩码下做算术。

初学者对照 5.1.6 就能秒懂：AVX-512 的掩码寄存器就是"真"向量机的向量掩码寄存器搬到了 x86 上，它把控制流转成数据流。为什么这是 AVX-512 相对旧 SSE/AVX 的质变？因为旧扩展要模拟条件写回得靠 blend（先都算、再按条件混合）很别扭，掩码把它变成一等公民，还顺带支持了聚散、压缩/展开这些不规整访问。要牢记的坑：掩码只决定"写不写回"，被掩掉的通道**仍占用执行时隙**，并不加速——省的是结果的正确性维护，不是时间。

### 5.2.4 打包运算、FMA 与标量的区别

同一批 SIMD 硬件可以跑三类操作，初学者常混。**打包（packed）**：一条指令处理宽寄存器里的全部通道（如 `vaddps` 加 16 个 float），这是 SIMD 的常态用法。**标量（scalar）**：同样用 SIMD 寄存器，但只操作最低一个通道（如 `vaddss` 只加 1 个 float），现代 x86 的普通浮点运算其实就走这条标量 SIMD 路径。**FMA（fused multiply-add，融合乘加）**：`a*b+c` 用一条指令、一次舍入完成。

FMA 值得单列，因为它同时影响性能和数值。一条 FMA 顶两次浮点运算（1 乘 1 加 = 2 FLOP），却只占一条指令、一个执行端口；且"融合"意味着中间乘积不先舍入，精度略优于分开的乘再加。峰值算力的常见算法就建立在此：

峰值 FLOP/s ≈ 核数 × 频率 × (每周期 FMA 条数) × (每条 FMA 通道数) × 2

其中末尾的 ×2 正是因为一条 FMA 记作 2 FLOP。举例：若一个核每周期发 2 条 FMA、每条 FMA 处理 16 个 float（AVX-512 单精度），则每核每周期 2×16×2 = 64 单精度 FLOP。

初学者由此能看穿 5.5 Roofline 的"峰值算力"从哪来：它不是玄学，就是上式几个因子相乘。易错点：这是**理论**峰值，真实代码几乎达不到（受相关、访存、频率降档制约）；而且宽 SIMD 只在能"打包"的规整循环里生效，一旦退化成标量 SIMD（每指令只算 1 个通道），宽寄存器的通道就大量浪费。

### 5.2.5 自动向量化与本机实证

让 SIMD 生效有两条路：编译器**自动向量化**（`gcc -O3 -march=native`，编译器自己把循环变成打包指令），或程序员写 intrinsics/内联汇编手动控制。硬件机制是本报告主题，编程细节留 L6-06/N-16；此处只用本机一个可选实测坐实"向量化收益到底由什么决定"。

本机（gcc 13.3.0，AVX-512，核实 2026-07-30）对同一个 SAXPY 循环 `a[i]=s*a[i]+b[i]`（数组约 4M 元素，远超 cache）三档编译实测，每次 SAXPY 平均耗时：

```
标量（-O2 -fno-tree-vectorize -mno-avx -mno-sse2）：约 705 µs
SSE 默认（-O2）                                    ：约 289 µs
AVX-512（-O3 -march=native -mprefer-vector-width=512）：约 306 µs
（objdump 确认 AVX-512 版确实用了 zmm 寄存器）
```

从标量到 SSE 提速约 2.4 倍（向量化确实有效），但从 SSE 再到 AVX-512 **几乎没有额外收益**（306 µs 甚至略慢于 289 µs）。原因不是 AVX-512 没生效（zmm 确实在用），而是 SAXPY 是**受内存带宽限制**的核（每算 2 个 FLOP 要搬 12 字节，算术强度很低），瓶颈在把数据从内存搬进来，加宽计算通道对搬运毫无帮助——这正是 5.5 Roofline 的核心教训的一次实证预演。

作为对照，把核换成计算密集、数据常驻 L1 的多项式核（每元素 16 次 FMA、数组仅 4096 元素），同机实测标量约 800 ms、AVX-512 约 20 ms，约 40 倍。初学者据此要建立的判断：宽 SIMD 只在**计算受限**时兑现宽度红利；**带宽受限**时再宽也白搭。这条判断的形式化工具就是下面 5.5 的 Roofline。

## 5.3 GPU / SIMT（AA-5.3）

### 5.3.1 GPU 作为吞吐导向处理器

图形处理单元（GPU, Graphics Processing Unit）在通用计算里被当作**吞吐导向（throughput-oriented）**处理器：与 CPU 用大 cache、乱序、分支预测去压低**单个**线程的延迟不同，GPU 用海量简单核心和成千上万个线程去最大化**总吞吐**，并用"线程一多，总有活干"来掩盖单个操作的长延迟。它本质是把 SIMD 推向极致再叠加大规模硬件多线程。

CPU 是"少数快车道 + 大 cache，怕延迟"；GPU 是"极多慢车道 + 高带宽显存 + 超多线程，靠并行摊延迟"。所以 GPU 擅长规整、数据并行度极高的负载（矩阵乘、图像、神经网络），不擅长强串行、分支多、延迟敏感的负载。

初学者要摆脱"GPU 就是更快的 CPU"这一错觉。GPU 单个线程往往比 CPU 线程慢，它赢在**同时跑的线程数**和**内存带宽**。理解这条，才明白后面 occupancy（占用率）为什么是 GPU 的核心效率指标——因为 GPU 的整套设计前提就是"用线程数量换延迟容忍度"。

### 5.3.2 SIMT 执行模型与 warp

GPU 的执行模型叫 **SIMT（Single Instruction, Multiple Thread，单指令多线程）**。硬件把一组线程（NVIDIA 称 **warp**，固定 32 个线程；AMD 传统称 wavefront，为 64 或在较新架构上 32）绑在一起，同一 warp 的所有线程**共用一个程序计数器、同拍执行同一条指令**，只是各自作用在自己的数据与寄存器上。也就是说，SIMT 在硬件层其实是 SIMD（一条指令驱动 32 条通道），但在**编程模型层**伪装成"很多个独立的标量线程"。

一条指令在一个 warp 上的数据流大致是：

```
一个 warp = 32 个线程（thread 0..31），共享 1 个 PC
取指一次 → 译码一次 → 32 条通道并行执行同一操作
   thread0: 用自己的寄存器/数据
   thread1: 用自己的寄存器/数据
   ...
   thread31: 用自己的寄存器/数据
（对程序员：像 32 个独立线程；对硬件：一条 SIMD 指令铺 32 通道）
```

SIMT 相对显式 SIMD 的妙处，是把"把循环切成向量宽度、处理掩码与收尾"这些苦活藏进了编程模型：程序员只写"一个线程做什么"，硬件自动按 warp 打包。初学者关键区分：warp 内 32 个线程**不是真正独立**，它们步调一致；一旦它们想走不同分支，就出 5.4 的发散问题。这也是"SIMT 是伪装成 MIMD 的 SIMD"这句话的确切含义——理解它是看懂整个 GPU 效率模型的钥匙。

### 5.3.3 线程层级与流多处理器

CUDA 编程模型把线程组织成层级：若干线程组成一个**线程块（thread block）**，若干块组成一个**网格（grid）**；块内线程可通过片上**共享内存（shared memory）**协作并用屏障同步。硬件侧，一个 GPU 由多个**流多处理器（SM, Streaming Multiprocessor；AMD 称 CU, Compute Unit）**组成，每个线程块被整体调度到某个 SM 上，SM 再把块内线程切成 warp 逐个（或几个 warp 调度器并行）发射。

H&P 6th ed 特意给出一张"教材描述性术语 ↔ NVIDIA CUDA 术语"的对照，因为 GPU 术语厂商味极重、极易混。粗略对应：

```
教材（descriptive）        NVIDIA CUDA            大致含义
向量化循环 Grid            Grid                   整个数据并行任务
SIMD 线程块 Thread Block   Thread Block           一批协作线程，调度到一个 SM
SIMD 线程 / warp           Warp                   32 个同步执行的线程
多线程 SIMD 处理器          SM (Streaming Multiproc.) 承载并调度多个 warp 的硬件核
```

初学者不必背全，但要抓住嵌套关系：grid ⊃ block ⊃ warp ⊃ thread，软件写的是 thread/block/grid，硬件真正一起动的最小单位是 warp。为什么要有 block 这一层？因为它是"能共享片上内存 + 能屏障同步 + 被整体放到一个 SM"的协作单位，是数据局部性和同步的边界。易错点：不同架构每个 SM 能同时驻留的 warp 数/块数/寄存器/共享内存都不同，这些硬件上限直接决定 5.4 的占用率——所以术语和层级要先理清。

### 5.3.4 硬件多线程与延迟隐藏

GPU 的每个 SM 同时驻留**多个 warp**，并用零开销的硬件线程切换在它们之间轮转：某个 warp 因为等访存（几百拍的显存延迟）而卡住时，SM 立刻切去执行另一个就绪的 warp，让执行单元不空转。这就是 GPU 的**延迟隐藏（latency hiding）**——它不像 CPU 那样想办法**降低**延迟，而是用足够多的并行 warp 把延迟**盖住**。

```
需要的并行 warp 数 ≈ 要隐藏的延迟（拍） / 每 warp 每次能持续发射的拍数
（并行 warp 越多，越能填满长访存延迟造成的空档）
```

初学者对照 CPU 就懂了：CPU 靠大 cache + 乱序 + 预取来**缩短/绕开**延迟，代价是复杂硬件、线程数少；GPU 干脆承认延迟很大，转而堆足够多 warp 来**遮住**它，代价是需要程序提供巨量并行、且单线程慢。这解释了为什么 GPU 需要成千上万线程才跑得满——不是因为有那么多活必须那么多线程，而是需要足够多的"备胎 warp"来填延迟空档。这个"用并行度换延迟容忍"的思想，直接引出 5.4 的占用率指标。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch4 §4.4 *Graphics Processing Units*（GPU 吞吐导向定位、SIMT、warp=SIMD 线程、Grid/Thread Block/SM 层级、教材术语↔CUDA 术语对照表、硬件多线程延迟隐藏）；核实 2026-07-30。
- 佐证：NVIDIA《CUDA C++ Programming Guide》（SIMT 架构、warp=32 线程、thread/block/grid、SM 与 shared memory、occupancy），核实 2026-07-30，标 ⚙演进快·锚 CUDA 现行文档；AMD《ROCm/HIP》文档（wavefront 64 或 32、CU）作跨厂商佐证。

## 5.4 分支发散与占用率（AA-5.4）

### 5.4.1 分支发散（warp divergence）与惩罚

**分支发散（branch/warp divergence）**指同一个 warp 里的 32 个线程在遇到 `if`/循环时想走**不同**的路径。由于 warp 共用一个 PC、只能同拍执行同一条指令，硬件的处理办法是**串行化**：先让走 then 分支的线程执行（其余线程被掩码屏蔽、空转），再让走 else 分支的线程执行（前一批被屏蔽）。两条路径接连跑完，warp 才继续。

```
发散执行时间 ≈ Σ(每条被走到的路径的时间)
最坏情况：warp 内出现 k 条互不相同的路径 → 时间约为无发散时的 k 倍
（32 个线程各走一条极端路径时，退化到近乎串行）
```

GPU 上的 `if` 不像 CPU 那样"只跑该跑的那条便宜分支"。只要一个 warp 内部产生了分歧，两条路径都要跑，被屏蔽的线程只是**不写结果但仍占时间**——这与 5.1.6 / 5.2.3 的向量掩码是同一现象。所以 GPU 编程的黄金律是"让同一 warp 的线程尽量走同一条路"，例如按 warp 边界对齐分支条件。跨越不同 warp 的分支不发散（不同 warp 本就各有 PC、独立调度），发散只发生在 warp**内部**——这条边界是理解发散惩罚的关键。

### 5.4.2 掩码执行、重汇聚与独立线程调度（⚙演进快）

发散在硬件上靠**掩码/谓词执行（predication）**实现：每个线程带一个活跃位，被屏蔽的线程照样过流水线但不提交结果。走完一条分支路径后，硬件要在汇合点做**重汇聚（reconvergence）**，把分道的线程重新拉回同步执行，以恢复满 warp 效率。经典实现用一个重汇聚栈（immediate post-dominator 处汇合）。

需硬标 ⚙演进快：NVIDIA 自 Volta（2017）起引入**独立线程调度（Independent Thread Scheduling）**，给每个线程独立的 PC/栈，放宽了"warp 内必须锁步"的旧模型，让发散路径能交错前进、也让 warp 内线程间的细粒度同步成为可能。这改变了发散的一些行为细节与旧代码的隐式假设，属架构代际差异，须以对应架构的 NVIDIA 文档为准，不能用旧 warp 锁步模型一概而论。

初学者只需把握两点。其一，掩码执行 = 让不该动的线程"空跑不写"，重汇聚 = 分歧结束后重新拉齐以免长期只用半个 warp。其二，"warp 内是否严格锁步"是随架构演进的（Pascal 及以前锁步、Volta 起独立线程调度），所以任何依赖"warp 内隐式同步"的老写法在新架构上可能不成立——这正是本节硬标演进快的原因。

### 5.4.3 占用率（occupancy）

**占用率（occupancy）**是衡量 SM 被 warp 填满程度的指标，定义为：

occupancy = 每 SM 实际驻留的活跃 warp 数 / 该 SM 硬件支持的最大 warp 数

它之所以重要，是因为 5.3.4 说过 GPU 靠"足够多的并行 warp"来隐藏延迟；占用率太低意味着可切换的备胎 warp 不够，访存延迟盖不住，执行单元就闲置。

限制占用率的通常不是线程写得不够多，而是**每个线程/块消耗的硬件资源**：每线程用的寄存器越多、每块用的共享内存越多，一个 SM 能同时塞下的 warp/块就越少。三者是此消彼长的预算分配问题：

```
可驻留 warp 数 ≤ min( 寄存器上限/每线程寄存器数, 共享内存上限/每块共享内存, 硬件 warp/块 上限 )
```

初学者的常见误区是"占用率越高越快"。并非如此：占用率只要**高到足以隐藏延迟**即可，之后再高收益递减；有时故意降低占用率、换给每线程更多寄存器（减少寄存器溢出到显存）反而更快。正确理解是：占用率是"延迟隐藏能力"的代理指标，目标是"够用",不是"最大化"。它把 5.3.4 的定性"要够多 warp"变成了可测量、可调的量。

### 5.4.4 访存合并与带宽利用

除了发散与占用率，GPU 数据并行的第三个效率命门是**访存合并（memory coalescing）**：当一个 warp 的 32 个线程同拍访问显存时，若它们的地址落在连续、对齐的一段里，硬件能把这 32 次访问合并成少数几个宽内存事务，充分利用显存带宽；若地址分散（如大跨步或随机 gather），则退化成大量小事务，带宽利用率暴跌。

初学者对照 5.1.6 的跨步/聚散就懂了：这是同一个"访存是否规整"的问题在 GPU 上的版本。为什么它和占用率并列重要？因为 GPU 的杀手锏是高显存带宽，而合并访问是把这条带宽真正用满的前提；不合并的访存模式会让 GPU 明明有巨大带宽却跑不出来。实践中"让相邻线程访问相邻数据"（如按行让线程沿连续列走）就是为了合并。这条与占用率、少发散一起，构成 GPU 上把硬件潜力兑现为实际性能的三要素，也自然过渡到 5.5 用 Roofline 统一判断"到底卡在算力还是带宽"。

#### 来源与时效
- 锚点：H&P《QA》6th ed, 2017, ch4 §4.4（分支发散与掩码/谓词执行、SIMD 通道被屏蔽仍占时隙、多线程与 warp 调度隐藏延迟；占用率与访存合并作为 GPU 效率要素在 ch4 GPU 与交叉议题中讨论）；核实 2026-07-30。
- 佐证：NVIDIA《CUDA C++ Programming Guide》与《CUDA Best Practices Guide》（warp divergence、occupancy 定义 = 活跃 warp/最大 warp、寄存器与共享内存对占用率的约束、memory coalescing；Volta 起 Independent Thread Scheduling），核实 2026-07-30，标 ⚙演进快·锚 CUDA 现行文档。
- 冲突/分账：warp 内是否严格锁步随架构演进（Pascal 及以前锁步 vs Volta 起独立线程调度），两代模型都记、按架构分账；"占用率越高越好"是常见误解，NVIDIA 文档明确其为够用即可、有寄存器权衡，从严采信一手。

## 5.5 Roofline 模型（AA-5.5）

### 5.5.1 算术强度（arithmetic intensity）

**算术强度（arithmetic intensity）**，也叫操作强度（operational intensity），衡量一段计算"每从内存搬一个字节数据、能做多少次浮点运算"，定义为：

I = 浮点运算次数（FLOPs） / 从主存搬运的字节数（Bytes）

单位是 FLOP/Byte。它是把一个核归类为"受算力限制"还是"受带宽限制"的核心量：I 大说明数据搬来后被反复计算、访存不是瓶颈；I 小说明算一点就要搬一堆数据、瓶颈在内存带宽。

初学者用 SAXPY `a[i]=s*a[i]+b[i]` 算一遍就懂：每个元素做 2 个 FLOP（1 乘 1 加），要从内存读 a、读 b、写 a 共 3 个 float = 12 字节，所以

I_SAXPY = 2 FLOP / 12 Byte ≈ 0.17 FLOP/Byte

这是个很低的算术强度，注定受带宽限制——正好解释了 5.2.5 里 AVX-512 相对 SSE 毫无收益。反例是稠密矩阵乘：O(n³) 次运算却只需搬 O(n²) 数据，算术强度随 n 增大，属受算力限制。易错点：分母通常指"搬到/搬出**主存（DRAM）**的字节"，被 cache 命中挡下的访问不计——所以同一算法在 cache 里放得下与放不下，有效算术强度可以差很多，这也是为什么优化局部性（提高数据复用）能把一个核从带宽受限推向算力受限。

### 5.5.2 Roofline 公式与两道屋顶

**Roofline 模型**（Williams, Waterman & Patterson, 2009）用一张对数-对数图，把一个处理器能达到的性能上界画成"屋顶"：横轴是算术强度 I，纵轴是可达性能（FLOP/s）。核心公式是一个取小：

可达性能(I) = min( 峰值算力, 峰值内存带宽 × I )

这条上界由两段拼成。当 I 小，`峰值带宽 × I` 更小，性能被这条**斜线**（带宽屋顶）压住——受内存带宽限制；当 I 大，`峰值算力` 更小，性能被这条**水平线**（算力屋顶）压住——受算力限制。

```
性能(log)
  ^
  |            ______________  ← 峰值算力（水平屋顶，算力受限区）
  |           /
  |          /  ← 斜率 = 峰值带宽（带宽屋顶，带宽受限区）
  |         /
  +--------+---------------------> 算术强度 I(log)
        脊点 (ridge point)
```

把你的核算出算术强度 I，在横轴找到它，屋顶的高度就是这台机器上该核性能的**理论上界**；再把实测性能点标上去，点离屋顶多远，就说明还有多少优化空间。为什么用 min（取两者较小）？因为性能同时受制于"搬得进来多少数据"和"算得多快"，木桶效应取短板。这一个模型把向量机、SIMD CPU、GPU 全部统一到同一张图上比较，是它最大的价值。

### 5.5.3 脊点（ridge point）

两道屋顶的交界点叫**脊点（ridge point）**，它对应的算术强度是：

I_ridge = 峰值算力 / 峰值内存带宽

脊点把横轴分成两半：I < I_ridge 的核落在斜线下，受带宽限制；I > I_ridge 的核落在水平线下，受算力限制。脊点因此是"这台机器上，一个核要多高的算术强度才配触到峰值算力"的门槛。

脊点还刻画了机器的性格。脊点**靠左**（算力/带宽比值小，即带宽相对充裕）的机器，大多数核都落在算力受限区、容易跑满算力，对程序员友好；脊点**靠右**（算力远大于带宽，如很多现代 GPU/加速器）的机器，只有算术强度很高的核才吃得到峰值算力，低强度核会被带宽死死压住。初学者由此能理解一个趋势：随着算力增长快过带宽增长，脊点逐年右移，"内存墙"越来越突出——这也是 5.4.4 访存合并、5.5.1 提高数据复用为何如此关键的深层原因。

### 5.5.4 用 Roofline 诊断与优化

Roofline 的实用价值是**指方向**：把实测点画到图上，看它被哪道屋顶挡住，就知道该优化什么。若点贴着斜线（带宽受限），加宽 SIMD、提高算力都没用，该做的是提高算术强度（增加数据复用、改善局部性让访问落在 cache）或提升有效带宽（访存合并、对齐、预取）。若点贴着水平线（算力受限），才轮到用 FMA、向量化、提高发射宽度去榨算力。若点离两道屋顶都远，说明存在其他瓶颈（如延迟未隐藏、并行度不足、发散）。

模型还常叠加多道"次级屋顶"：不带 FMA 的算力线、无向量化的算力线、无 NUMA 优化的带宽线等，形成阶梯，指示"启用某项优化最多还能抬多高"。

初学者要记住 Roofline 的定位：它是**上界与诊断**工具，不是精确性能预测器；它告诉你"天花板在哪、你离它多远、该往哪使劲"，而不是"你一定能到多少"。它的最大好处是防止南辕北辙——例如对一个带宽受限的核拼命做指令级优化（如 5.2.5 的 SAXPY 换 AVX-512）是白费力气，Roofline 一眼就能拦住这类误判。

### 5.5.5 本机算术强度点定位（可选实证）

用 5.2.5 的两个本机核在 Roofline 语义下定位（可选补充，核实 2026-07-30）。SAXPY 核算术强度 I ≈ 0.17 FLOP/Byte，属**低强度、带宽受限**：实测标量→SSE 提速约 2.4 倍（此前访存尚未打满、向量化减少了指令开销），但 SSE→AVX-512 无额外收益（306 µs vs 289 µs）——因为它已贴近带宽斜线，加宽计算通道碰不到那道屋顶。

作为算力受限的对照，计算密集多项式核（每元素 16 次 FMA、数据常驻 L1，算术强度高）实测标量约 800 ms、AVX-512 约 20 ms，约 40 倍——它落在水平屋顶下，加宽 SIMD 直接兑现。

这组对照正是 Roofline 的实物教具：同一台机器、同一套 AVX-512 硬件，一个核几乎吃不到向量化红利、一个核吃得满满，差别只在算术强度落在脊点的哪一侧。初学者据此应形成的工作习惯：优化前先估算术强度、判断在斜线还是水平屋顶下，再决定动带宽还是动算力——本机数字只是示意（未换算绝对 GFLOP/s 与实测 STREAM 带宽，故不定量标注屋顶高度，标未取），但"带宽受限时宽 SIMD 无用"这一定性结论已被坐实。
