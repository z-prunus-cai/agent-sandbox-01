# L5-11·大主题1 需求与非功能目标定义

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01｜先修：分布式系统基本概念（一致性/可用性口径回指 L5-01）、后续容量估算方法（大主题2）｜一手锚点：DDIA 2nd ed「Defining Nonfunctional Requirements」章（准一手教材，早期发布版，对应 1st ed ch1 材料）、Google SRE Book ch4「Service Level Objectives」｜成熟度：GA（工程方法学，概念稳定；具体业务影响数值随年代/公司变，逐条标注）

系统设计的第一步不是画框图，而是把"这个系统要满足什么"说清楚。这一大主题讲的就是需求侧的功课：先把"做什么"和"做得多好"分开，再把"多好"翻成能被检验的数字，估清数据与流量的量级和增长，最后把这些数字反推成"必须采用哪些架构手段"。它是后面所有容量估算、选型、折衷的输入；跳过它，后面的设计就没有评判标准。

## 1.1 功能 vs 非功能需求分离

### 1.1.1 功能需求（做什么）

功能需求描述系统必须提供的行为与能力：它接收什么输入、执行什么操作、产生什么输出。比如"用户能发一条推文""能按时间线拉取关注者的推文""能删除已发内容"——这些都是可以逐条列成用例、能被"做到了/没做到"二值判定的能力。

对初学者最直观的判别法是问一句"少了它，这个产品还是它自己吗？"。如果答案是否定的（一个不能发推文的推文应用根本不成立），那多半是功能需求。功能需求通常来自产品经理、用户故事、接口契约，它回答"系统是什么"。它的特点是相对离散、可清点、通过就是通过，一般不带"多少"这个维度。

### 1.1.2 非功能需求（多快 / 多可靠 / 多省）

非功能需求不改变"系统做什么"，而是约束"系统把这件事做得多好"：多快响应、能扛多大流量、多久不宕机、出错时怎么表现、花多少钱、以后好不好维护和演进。同一个"发推文"功能，要求它在 100 毫秒内返回、支撑每秒十万次写入、全年停机不超过一小时——这三个"要求"就是非功能需求。

它们也常被叫作质量属性（quality attributes）。初学者最容易踩的坑是把非功能需求当成"锦上添花、以后再说"。恰恰相反：一个系统的架构形态（要不要分片、要不要多副本、要不要缓存）几乎完全由非功能需求决定，而不是由功能需求决定。两个功能一模一样的系统，一个要撑 100 用户、一个要撑 1 亿用户，架构会天差地别——差异全在非功能需求里。所以在系统设计里，非功能需求才是驱动架构的主力。

非功能需求的另一个关键特征是"带刻度"：它天然要用数字表达（多快、多少、多久），这就把它和 1.2 的量化直接连起来了——一个说不出数字的非功能需求，等于没提。

### 1.1.3 可靠性 / 可扩展性 / 可维护性（DDIA 的三大非功能关注）

DDIA 把海量的非功能关注收敛为三个统摄性维度。可靠性（reliability）指系统在出现硬件故障、软件缺陷、人为误操作等"错误"时仍能正确工作，也就是"容错"；可扩展性（scalability）指系统有合理手段应对负载增长；可维护性（maintainability）指系统在整个生命周期里对运维、演进、排障都友好。

这三个词是初学者组织思路的好脚手架：拿到一个模糊的"要健壮一点""要能扛住""要好改"的诉求时，可以先归到这三类，再在每类下追问"具体多少"。要注意 DDIA 对术语的精确区分——它强调 fault（组件层面的偏差，如一块盘坏了）和 failure（系统层面对用户不可用）不是一回事，容错的目标是"让 fault 不升级成 failure"。这个区分在后面讲复制、容错模式时会反复用到。

可维护性偏软性、不易量化，但它同样是非功能需求，只是通常不用一个数字而用"运维负担、变更成本、可演进性"来描述。本大主题的量化重点放在可靠性和可扩展性上（它们能落到延迟、吞吐、可用性等硬指标），可维护性更多在后续工程与交付、可观测性主题里展开。

### 1.1.4 分离的价值与做法

把功能与非功能分开列，好处是让"对不对"和"够不够好"两套判据各归各位：功能需求用验收测试判"做没做到"，非功能需求用度量指标判"达没达标"。混在一起时最典型的失败是——团队实现了全部功能、演示一切正常，一上线真实流量就崩，因为从没人把"要扛多少 QPS、p99 要多低"写下来当验收线。

具体做法是对每条需求追问一句"这是行为，还是对行为的质量约束？"。"支持导出报表"是功能；"导出十万行报表要在 5 秒内完成"是挂在这条功能上的非功能约束。二者常成对出现：非功能需求往往依附于某个功能之上，量化时要说清"哪个操作、在什么规模下、达到什么指标"。分离不是把它们割裂，而是让每条功能都带上它该满足的质量刻度，从而使整份需求可被检验。

## 1.2 SLA / 延迟 / 吞吐 / 成本目标量化

### 1.2.1 响应时间、延迟、吞吐的概念区分

这三个词日常常被混用，但在系统设计里含义不同，务必分清。响应时间（response time）是客户端视角的端到端耗时：从发出请求到收到完整响应，包含服务实际处理时间、网络往返、以及在队列里排队等待的时间。延迟（latency）严格说指请求"尚未被处理、在等待"的那部分时间。吞吐（throughput）是单位时间能处理的请求数或数据量，常用 QPS（每秒查询数）、RPS、TPS 或 MB/s 表示。

响应时间关心"单个请求等了多久"，吞吐关心"单位时间能干多少活"，二者是一个系统的两个正交侧面。一个系统可以吞吐很高但单请求响应时间也很长（批量流水线就是如此），也可以响应快但总吞吐有限。DDIA 特别提醒：response time 与 latency 在很多资料里被当同义词，但它把 latency 收窄为"等待被服务"的时长，而 response time 是用户真正感受到的总时长——写目标时应以用户可感的 response time 为准。这里的分歧只是术语口径，写需求时点明你用的是哪种口径即可，不必纠结谁"正确"。

### 1.2.2 用百分位而非平均值描述延迟

描述延迟目标要用百分位（percentile），不要用平均值。p50（中位数）表示一半请求比它快；p95 表示 95% 的请求比它快、最慢的 5% 比它慢；p99、p999（即 99.9 百分位）同理。一个典型的延迟目标写法是"p50 < 50ms，p99 < 200ms，p999 < 1s"。

为什么不用平均值？因为平均值会被少数极端值拉动、又掩盖极端值，无法回答"最糟的用户体验有多糟"。而恰恰是慢请求最伤体验：DDIA 引用 Amazon 的经验，其内部对响应时间的要求用 99.9 百分位来描述，理由是响应最慢的那批客户往往是数据最多、最有价值的老客户。高百分位（p99、p999）代表的是尾部体验（tail latency，尾延迟），它比平均值重要得多，因为一次访问常要发很多请求，用户感受到的是其中最慢的那一个。

其一，百分位不能跨机器简单平均——把两台机器各自的 p99 取算术平均得不到整体 p99，正确做法是合并原始分布或用专门的近似算法（这属度量学细节，展开归可观测性主题）。其二，测量端很关键——要在客户端而非服务端测量响应时间，否则会漏掉排队和网络的时间。

### 1.2.3 尾延迟放大（tail latency amplification）

当一个用户请求需要在后端并行地扇出（fan-out）成多个子请求、并等所有子请求都返回后才能响应时，只要有一个子请求慢，整个请求就慢。结果是：后端单个服务的高百分位延迟，会被"取最大值"的聚合方式放大到前端——这就是尾延迟放大。

举个最小例子。假设一次页面渲染要并行调用 100 个后端服务，每个后端有 1% 的概率响应超过 1 秒（即各自 p99=1s）。那么"至少一个后端慢"的概率是

P(整体慢) = 1 − (1 − 0.01)^100 ≈ 0.63

也就是约 63% 的页面请求会遇到至少一个慢子请求。于是后端看起来只有 1% 慢，前端却有六成的请求慢。这就是为什么大规模系统里，即使单机 p99 很好，端到端 p99 仍可能很差。这个现象由 Dean 与 Barroso 在《The Tail at Scale》中系统阐述。它的工程含义是：扇出越宽，越要压住每个后端的尾延迟，或采用对冲请求（hedged requests）等手段——具体手法属容错与性能工程，此处只需建立"尾延迟会被扇出放大"这个意识。

### 1.2.4 可用性与"几个 9"

可用性（availability）指系统在给定时间窗口内正常提供服务的时间占比，常用"几个 9"表达。它和停机预算是一体两面：

不可用度 = 1 − 可用性

把不可用度乘以时间窗口，就得到该窗口允许的停机时长（停机预算 / error budget 的雏形）。下表按一年 365.25 天、一个月 30 天换算（本机 Python 演算，2026-08-01）：

| 可用性 | 每年停机 | 每月停机 | 每周停机 |
|--------|----------|----------|----------|
| 99%      | 87.66 h  | 432.0 min | 100.8 min |
| 99.9%    | 8.77 h   | 43.2 min  | 10.08 min |
| 99.95%   | 4.38 h   | 21.6 min  | 5.04 min  |
| 99.99%   | 52.6 min | 4.32 min  | 1.01 min  |
| 99.999%  | 5.26 min | 0.43 min  | 0.10 min  |

初学者要建立的直觉是"每多一个 9，允许的停机时间就缩到十分之一"，代价（冗余、多区、自动化）却往往指数上升——所以可用性目标不是越高越好，而要匹配业务价值。要注意换算口径会造成小差异：一年按 365 还是 365.25 天、一个月按 30 天还是按实际天数，会让表格数值略有出入（例如 99.99% 常被写成"每年约 52.6 分钟"也有写"约 52.56 分钟"），引用时说明口径即可。SRE 领域进一步用这套预算做"错误预算驱动的发布决策"，那属可观测性/SRE 主题的度量学，此处只到"把可用性目标翻成可量化的停机预算"为止。

### 1.2.5 SLI / SLO / SLA 三者区分

把非功能目标落成可度量、可承诺的东西，业界用三个术语。SLI（Service Level Indicator，服务水平指标）是被测量的量本身，比如"成功请求占比""p99 延迟"。SLO（Service Level Objective，服务水平目标）是给 SLI 设的目标值和窗口，比如"过去 30 天成功率 ≥ 99.9%"，它是对内的目标。SLA（Service Level Agreement，服务水平协议）是与客户的正式合约，写明达不到目标时的后果（退款、赔偿），它对外、带罚则。

三者的关系可以记成一条链：SLI 是"测什么"，SLO 是"对内要达到多少"，SLA 是"对外承诺多少、违约怎么赔"。一个常见且重要的经验法则是：对外 SLA 通常设得比对内 SLO 宽松（比如内部盯 99.9%，对外只承诺 99.5%），留出缓冲，避免刚破内部目标就触发对客户的赔偿。

这里存在一处术语分歧要点明：Google SRE Book 严格三分 SLI/SLO/SLA；而 DDIA 等资料里 SLA 一词有时被宽泛地用来泛指"响应时间/可用性目标"，不强调"对外合约+罚则"这层。写文档时应以 SRE 的严格口径为准，并明确自己指的是对内目标还是对外合约。SLI/SLO 具体怎么定义好指标、怎么选窗口、怎么做燃烧率告警，属度量学细节，归可观测性/SRE 主题（L5-12）；本大主题只到"把业务约束翻译成可度量的目标"这一步。

### 1.2.6 成本目标量化

成本是一等非功能约束，不是事后账单。可量化的成本目标包括单位成本（每请求成本、每用户每月成本、每 GB 存储/传输成本）和总拥有成本 TCO（含机器、带宽、存储、人力运维）。把成本写成"每百万请求不超过 X 元""毛利要求下每用户基础设施成本 ≤ Y"这类目标，才能在选型时做取舍。

初学者容易忽略成本，或把它当成"能省则省"的模糊愿望。但成本目标会实打实地反推架构：它决定你能不能上多副本、能不能全内存、能不能多区部署。延迟、可用性、成本三者常互相拉扯——要更低延迟和更高可用往往要花更多钱，量化成本目标就是给这场拉扯定一条底线，让"值不值得"变成可计算的问题。

### 1.2.7 把业务约束翻成可度量目标的方法

前面几项合起来给出一套可操作的翻译流程：拿到一句业务话（"页面要秒开""不能老是崩""别太烧钱"），逐句改写成"指标 + 目标值 + 测量窗口 + 测量点"四要素俱全的可度量目标。"秒开"→"首屏 p95 响应时间 < 1s，客户端测量"；"不能老是崩"→"过去 30 天可用性 ≥ 99.9%（对应每月停机预算 43.2 分钟）"；"别太烧钱"→"每百万请求基础设施成本 ≤ X 元"。

判断一个目标是否合格，就看它能不能被"通过/未通过"地检验。凡是说不清用什么指标、目标多少、在多大规模、多长窗口、在哪里测的，都还只是愿望，不是目标。这一步做扎实，后面的容量估算和选型才有可校验的靶子；做不扎实，架构评审就会沦为口味之争。

## 1.3 数据规模与增长假设

### 1.3.1 当前量级作为设计输入

设计任何系统前，要先把当前的规模量级摸清并写下来：数据总量（多少 TB）、实体数量（多少用户、多少条记录）、请求速率（平均/峰值 QPS）、单条记录大小。这些数字是后续一切容量估算的起点，也是判断"哪些操作常见、哪些罕见"的依据。

初学者的直觉误区是"先把功能做出来，规模以后再说"。但规模决定形态：一个百万级数据的系统单机数据库就能搞定，十亿级则几乎必然要分片。DDIA 强调，一个系统的可扩展性总是围绕"哪些操作会频繁发生"这一组假设来构建的——脱离规模谈架构没有意义。所以规模不是背景信息，而是和功能同等重要的设计输入，必须显式估出量级（哪怕是数量级的粗估）。

### 1.3.2 增长率与设计时间跨度

只看当前量级不够，还要假设增长：用户和数据是线性增长还是指数增长，未来 6 个月、1 年、3 年会到多大。一个常用的粗略表达是

未来规模 ≈ 当前规模 × (1 + 月增长率)^月数

比如当前 100 万用户、月增 20%，一年后约为

100万 × 1.2^12 ≈ 100万 × 8.9 ≈ 890万

设计时通常按"要撑住未来某个时间点的规模"来定容量，常见做法是留出一定倍数的余量（headroom），而不是刚好卡着当前值。易错点在两端：低估增长导致上线不久就要推倒重来（迁移、重分片代价极高）；高估增长则过度设计、白烧钱。合理做法是明确写出"本设计针对 N 倍于当前的规模，超过则需重新评估"，把假设摆到台面上，而不是让它隐含在某个人脑子里。

### 1.3.3 用负载参数描述负载

要描述"负载有多大"，不能只说一个笼统的数字，而要用一组负载参数（load parameters）——挑选最能刻画本系统压力来源的几个量。DDIA 用 Twitter 的时间线为例：真正决定架构的负载参数不是"每秒发多少推文"，而是"每个用户有多少关注者"带来的扇出写入量，因为这决定了每发一条推文要往多少个时间线里写。

对初学者，关键领悟是"负载参数是与业务相关的、需要挑选的"：不同系统的压力来源不同，选错参数就会低估或高估压力。常见候选包括请求速率、并发连接数、数据库读写比、缓存命中率、单请求扇出度、消息队列积压量等。定义负载时先问"什么东西一多，这个系统就吃紧？"，把那个量作为主负载参数，是估算和压测的正确起点。

### 1.3.4 读写比、访问分布与峰均比

同样的总请求量，读多写少还是写多读少，架构完全不同——读多可以靠副本和缓存扩展，写多则要面对分片和写放大。所以要估读写比（如读:写 = 100:1）。此外还要看访问分布：是均匀访问，还是少数热点数据被反复访问（幂律/长尾分布）——热点决定了缓存能不能救你、会不会出现热分区。

还有峰均比：真实流量不是恒定的，白天高夜里低、有促销尖峰。峰值 QPS 往往是平均 QPS 的数倍甚至数十倍，容量必须按峰值（再留余量）来备，而不是按平均。初学者若只按日均请求数除以 86400 秒来估 QPS，会严重低估峰值需求。这三个量（读写比、访问分布、峰均比）把"总量"细化成"结构"，是把规模假设转成容量数字（大主题2 的容量估算）时的必备输入。

### 1.3.5 数据保留期与生命周期

要估存储容量，除了"每天新增多少数据"，还必须定"数据留多久"。保留期（retention）× 日增量 ≈ 需要的存储规模。日志留 7 天还是留 1 年、用户数据永久保存还是定期归档，会让存储需求差出几个数量级，也牵动合规（如个人数据的删除义务）。

初学者常只算"当前数据多大"而忘了它会随时间累积。明确写出"热数据留 X 天在线、冷数据归档到廉价存储、超过 Y 后删除"这样的生命周期策略，既是容量估算的输入，也是成本控制的手段。分层存储（热/温/冷）本身就是由"不同数据的访问频率随时间衰减"这一假设驱动的架构决策。

## 1.4 约束 → 架构驱动因子映射

### 1.4.1 什么是架构驱动因子

不是所有需求对架构的影响都一样大。那些真正决定架构形态、迫使你采用某类机制的需求，叫架构驱动因子（也称架构上重要的需求，architecturally significant requirements）。它们几乎都来自非功能目标和规模假设——"要撑十亿数据""p99 要 10ms""要 99.99% 可用"这类目标，才是驱动因子；而"按钮是蓝色的"不是。

映射的核心方法论是：对每一个量化目标，反问"要达到它，架构上必须具备什么？"，从而把目标翻译成必需的机制。这一步让架构决策变得可追溯——每个组件的存在都能回指到某条需求，而不是凭喜好堆砌。下面几项就是最常见的几条映射规则，可当查检清单用。

### 1.4.2 高吞吐 / 读多 → 复制 + 缓存

当目标是高读吞吐、低读延迟时，典型的架构驱动是加读副本（replication）和加缓存。副本让读请求分摊到多台机器，缓存让热点读不必每次都打到后端存储。二者都是"用空间/冗余换读性能"。

其代价与边界要一并交代：副本带来复制滞后，缓存带来一致性窗口，都会让"读到旧数据"成为可能——这是否可接受，回到 1.2 的一致性目标去判断。这里只做"读压力大→往复制/缓存方向想"的映射；复制的具体拓扑（单主/多主/无主）与缓存的读写模式属后续大主题的展开。

### 1.4.3 大数据集 / 写扩展 → 分片 sharding

当单机装不下全部数据、或单机写吞吐扛不住时，架构驱动是分片（sharding / partitioning）：把数据按某种键切成多块，分散到多台机器，从而线性地扩容量和写吞吐。判据很直接——数据量或写速率超过单机上限，就得考虑分片。

分片的代价是复杂度陡增：要选分片键、要处理跨分片查询与事务、要应对热点分区和再平衡。所以映射规则的完整表述是"仅当规模确实超过单机能力时才分片"，不要为不存在的规模提前分片。分区键怎么选、范围分区还是哈希分区、如何再平衡，属数据分片大主题；此处只到"大到装不下/写不动→分片"这一步。

### 1.4.4 高可用 → 冗余 / 多副本 / 多区

可用性目标越高（越多的 9），越要靠冗余来消除单点故障：多副本、跨可用区甚至跨地域部署、自动故障切换。因为可用性本质上是"任何单一组件坏了，系统整体还能服务"，而这只能靠"有备份可顶上"来实现。

映射时要把 1.2.4 的停机预算和成本挂钩：目标从 99.9% 提到 99.99%，往往意味着从单区多副本升级到多区容灾，成本和复杂度大幅上升。所以高可用不是无脑堆冗余，而是"目标的 9 数"反推出"需要几层冗余、跨不跨区"。冗余带来的一致性/延迟代价，又回到 CAP 类折衷去权衡。

### 1.4.5 低延迟 → 就近 / CDN / 边缘 / 缓存

当延迟目标很严（尤其面向全球用户）时，物理距离成为硬约束——光速决定了跨洲往返就有几十到上百毫秒，再优化代码也绕不过。于是架构驱动是"把数据/计算搬到离用户更近的地方"：CDN 缓存静态内容、边缘节点、多地域部署、以及各层缓存减少往返。

初学者要建立的直觉是"延迟目标 + 用户地理分布"共同决定要不要走就近部署。如果用户全在一个城市，单区就够；如果全球分布且要求低延迟，几乎必然要多地域 + CDN。这条映射把"p99 要多低"和"用户在哪"两个输入，翻成"要不要边缘/多区"的决策。

### 1.4.6 强一致 vs 高可用 → CAP 类折衷

有些目标彼此冲突，无法同时最大化，映射时必须显式做取舍而非假装都要。最经典的是一致性与可用性：在网络分区发生时，系统只能二选一——要么拒绝服务以保证不返回不一致数据（偏一致），要么继续服务但可能返回旧数据（偏可用）。这就是 CAP 折衷的工程含义。

对需求定义而言，关键动作是问业务："能容忍偶尔读到旧数据吗？还是宁可这次不可用也不能出错？"银行余额可能选前者的反面（宁缺毋滥），社交点赞数则可容忍短暂不一致。把这个容忍度写进需求，才能在 AP / CP 之间选边。这里只做"目标冲突要显式选边"的映射；CAP 定理的形式化定义与证明、线性一致性的严格定义属分布式理论（回指 L5-01），本主题不展开证明，只用其工程结论。

### 1.4.7 映射方法总纲：从目标反推，不堆砌

把上面几条串起来，就是一套需求到架构的推导纪律：逐条拿量化目标（吞吐、延迟、可用性、数据规模、成本、一致性要求），问"达到它必须有什么机制"，把答案汇成架构驱动因子清单；再检查这些机制之间有没有冲突（如高可用 vs 强一致、低延迟 vs 低成本），对冲突显式做取舍并记录理由。

这样得到的架构，每个决策都能回指到一条需求，评审时可以逐条质询"这个分片/多区/缓存是为满足哪条目标"。反面教材是"简历驱动设计"——因为想用某个时髦组件而引入它，却对应不上任何需求。初学者记住一句话即可：需求量化在前，架构机制在后；机制是目标的推论，不是起点。
