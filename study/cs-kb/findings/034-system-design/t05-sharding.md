# L5-11·大主题5 数据分片 sharding

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01 ｜先修：L5-01 分布式系统（分区/一致性哈希理论）、L4-03 数据库（索引与存储局部性）｜一手锚点：DDIA 2nd ed「Partitioning」章（Kleppmann & Riccomini，martin.kleppmann.com 2026-03-24 公告版）｜成熟度：GA（分片模式本身成熟；具体组件的默认分片数/token 数 ⚙演进快·随版本变）

分片（sharding，DDIA 与多数学术文献称 partitioning）指把一个大数据集按某种规则切成多块，每块（partition/shard）放到不同节点上，使数据量与读写负载能横向摊到多台机器。本报告只做工程装配层面的选型、容量与折衷；分区方案的分布式理论正确性（如一致性哈希的均衡性证明、再平衡期间的一致性保证）回指 L5-01。

一个贯穿全篇的前提：分片几乎总是和复制（大主题6）叠加使用——每个分片自身再复制成多副本。本报告只谈"怎么切"，"切完每块怎么复制"归大主题6。

## 5.1 范围分区（range partitioning）

### 5.1.1 范围分区是什么

范围分区按 key 的排序区间划分：给每个分区分配一段连续的 key 区间（如 A–C 一个分区、D–F 下一个），落在哪段区间的 key 就进哪个分区。分区之间边界有序，分区内部通常也按 key 有序存储。

直觉上就像一套纸质百科全书：第 1 卷 A–B、第 2 卷 C–D……你想查某个词，看首字母就知道去哪一卷，而且同一卷内词条也是排好序的。区间不必等宽——如果 A 开头的词特别多，可以让 A 单独一卷、X–Z 合成一卷，让每卷厚度大致相当。数据库里这些区间边界既可以管理员手动设定，也可以由系统随数据分布自动调整。

### 5.1.2 有序带来的范围查询优势

范围分区最大的好处是保留了 key 的顺序，因此范围扫描（range scan）很高效：查询"key 在 X 到 Y 之间的所有记录"时，只需定位到覆盖该区间的少数几个相邻分区，顺序读出即可，不必碰其他分区。

传感器数据以时间戳为 key，"取昨天 0 点到 24 点的全部读数"这类查询，在范围分区下只落在保存那一天的分区上，一次连续扫描就取全。这是范围分区相对哈希分区的决定性优势——哈希分区会把相邻时间戳打散到所有节点，同样的范围查询就得访问每一个分区。HBase、MongoDB 的 range sharding、以及 RDBMS 的 range partition 都属此类。

### 5.1.3 热点与倾斜（skew / hot spot）

范围分区的代价是容易产生热点（hot spot）：如果访问集中在某个连续 key 区间，承载该区间的那一个分区就会被打爆，而其他分区闲置。负载在分区间的这种不均衡称为倾斜（skew），被压垮的那个分区叫热点。

最经典的反面例子仍是"用时间戳做 key"：所有新写入的时间戳都递增，永远落在"最新"那个分区上，于是写入热点始终跟着"当前时间"这一个分区跑，其余分区都是历史冷数据。DDIA 给出的缓解办法是给 key 加前缀（如把传感器名放在时间戳前面，key 变成 `sensorA_2026-08-01T...`），让写入先按传感器散开、每个传感器内部再按时间有序——代价是想按时间范围查所有传感器时，得对每个前缀各做一次范围查询再合并。这说明热点治理常常是把"范围性"和"打散"之间的矛盾局部转移，而非消除。

### 5.1.4 分区边界的选择与自动分裂

范围分区的区间边界不能拍脑袋等分 key 空间（例如按字母表把 26 个字母均分），因为真实数据分布往往极不均匀（以 A、S、T 开头的英文词远多于 X、Z）。边界应当贴合实际数据分布，让每个分区的数据量大致相当。

实践中系统多用自动分裂：当某分区数据量或负载超过阈值，就把它从中间切成两个分区，其中一半迁到别的节点（详见 5.2.5 动态分区）。这样区间边界随数据生长自动细化，无需人工预估。易错点：初始只有一个分区时，若不主动预分裂（pre-splitting），所有写入会先挤在这唯一分区上，直到它够大才分裂——冷启动阶段无法利用集群并行，这是范围分区上线初期的常见坑。

## 5.2 哈希分区与一致性哈希

### 5.2.1 哈希分区是什么（打散热点）

哈希分区先对 key 算一个哈希值，再按哈希值决定分区归属。因为好的哈希函数会把即便相邻的 key 也均匀散开，哈希分区能把负载和数据量较均匀地摊到所有分区，从根本上避免了范围分区那种"连续热点"。

范围分区是"按姓氏首字母分档案柜"，同姓的人全挤一格；哈希分区是"给每个人算一个随机工号、按工号分柜"，同姓的人被打散到各柜，谁也不会被挤爆。代价对称地出现——哈希打散了顺序，范围查询（"查工号相邻的一批人"）就失效了，必须扫所有分区。因此哈希分区适合点查（按精确 key 取单条）为主、几乎不做范围扫描的负载。注意 DDIA 强调：哈希只需"分布均匀"，不需要密码学强度，很多数据库用的是 MD5、Fowler–Noll–Vo 等快速哈希而非加密哈希。

### 5.2.2 hash mod N 的再平衡陷阱

一个诱人但错误的做法是"分区号 = hash(key) mod N"（N 为节点数）。它在节点数固定时确实均匀，但一旦增删节点（N 变化），几乎所有 key 的归属都会改变，触发全量数据迁移。

设 N 台变 N+1 台，一个 key 留在原节点的条件是 `hash mod N == hash mod (N+1)`，满足的 key 极少。需要迁移的数据比例约为：

需迁移比例 ≈ N / (N+1)

也就是说从 10 台扩到 11 台，约 10/11 ≈ 91% 的数据都要搬。这在生产上是灾难。这条陷阱正是"一致性哈希"和"固定分区数"两种方案要解决的核心问题：把再平衡的迁移量从"接近全量"压到"仅约 1/N"。易错点：初学者常把 `mod N` 当成哈希分区的标准实现，其实它只是反面教材，真实系统都避开对节点数直接取模。

### 5.2.3 一致性哈希（Karger）与哈希环

一致性哈希（consistent hashing，Karger 等 1997）把哈希输出空间首尾相接看成一个环（0 到最大哈希值再回到 0）。每个节点也被哈希到环上若干个点；一个 key 哈希到环上某点后，沿环顺时针找到的第一个节点就负责它。

增删节点时，只有该节点在环上那段弧对应的 key 需要重新归属，其余 key 不动。理论上增删一个节点平均只迁移约 `1/N` 的数据：

单节点增删迁移比例 ≈ 1 / (N+1)

为避免"每个节点在环上只占一段、导致负载不均"，实践中给每个物理节点分配多个虚拟节点（virtual node / vnode，Cassandra 里叫 token），把它散布到环上多处，使各物理节点承担的弧长之和趋于均衡；虚拟节点越多越均衡，但元数据也越多。示意（一个 4 段环、节点各持 2 个 vnode）：

环: [n1 · n3 · n2 · n1 · n4 · n2 · n3 · n4] → 顺时针命中第一个节点负责该弧

### 5.2.4 固定分区数（fixed number of partitions）

一种被 DDIA 推荐、工程上最常用的再平衡方案：一开始就创建远多于节点数的固定数量分区（例如 10 个节点建 1000 个分区），每个节点分到若干分区。分区总数和"key→分区"的映射永不变，变的只是"分区→节点"的分配。

加入新节点时，它从每个现有节点"偷"走几个完整分区，直到分配重新均衡；删除节点则反向把它的分区分给其余节点。整个过程只搬动整块分区、不重算 key 归属，迁移量约为总量的 `1/(新节点总数)`。Riak、Elasticsearch、Couchbase 等采用此法。难点在于分区数是建库时定死的、后期改动昂贵：定太少则单分区随数据增长过大、限制未来扩容上限；定太多则每个分区太小、管理与再平衡开销上升。⚙演进快·锚版本：Elasticsearch 在 7.0（2019）把每索引默认主分片数从 5 改为 1，正是因为"默认分区偏多"在小索引上得不偿失——这类默认值随版本变，用时以当前版本文档为准。

### 5.2.5 动态分区（dynamic partitioning）

动态分区让分区数随数据量自适应：当某分区超过配置的大小上限就分裂成两个（其中一半迁到别的节点），低于下限则与相邻分区合并。这样小数据集只需少量分区、大数据集自动细分，无需预估分区数。

这正是范围分区数据库（HBase、MongoDB、RethinkDB）常用的再平衡方式，也可用于哈希分区。优点是分区大小自我调节、避免"固定分区数定太死"的两难。代价与 5.1.4 一致：初始只有一个分区，冷启动阶段所有写入挤在一处，直到第一次分裂才用上集群并行——所以这类系统通常支持预分裂（pre-splitting）来预热。

### 5.2.6 按节点比例分区（partitioning proportionally to nodes）

第三种方案：让分区数正比于节点数，即每个节点固定持有约定数量的分区（如每节点 256 个），于是分区总数 = 节点数 × 每节点分区数。数据量增长靠加节点吸收，单分区大小则大致稳定。

新节点加入时，随机选若干现有分区分裂，取走每个被选分区的一半。Cassandra、Ketama 属此类。"随机选分裂点"会带来短期不公平的分裂，但用足够多虚拟节点可摊平。⚙演进快·锚版本：Cassandra 4.0（2021）起把默认 `num_tokens`（每节点虚拟节点数）从 256 下调到 16，以减小重平衡与修复开销——具体默认值随版本演进，用时以当前版本文档为准（待核你所用版本的确切默认）。

### 5.2.7 扩缩迁移量直觉（估算式）

把上面几种方案的核心差异落到"扩容一台需搬多少数据"这一个数上，便于选型时快速估算。设当前 N 台、总数据量 D：

hash mod N（反面教材）：搬约 (N/(N+1))·D

一致性哈希 / 固定分区数 / 比例分区：搬约 (1/(N+1))·D

例：N=9、D=900 GB，扩到第 10 台。mod N 约搬 810 GB（≈9/10），而后三种约搬 90 GB（≈1/10）。数量级差异说明：只要用了"分区数与节点数解耦"或"哈希环"，再平衡代价就从 O(全量) 降到 O(1/N)，这是所有现代分片系统的共同底线。这些系数是模型化的期望值、假设哈希均匀且分区等重，真实迁移量还受虚拟节点数、数据倾斜影响，工程估算够用即可。

### 5.2.8 术语陷阱：DDIA 对 "consistent hashing" 一词的告诫

DDIA 特别提醒：数据库语境下"consistent hashing"一词常被误用。Karger 原始的一致性哈希（随机放置节点到环上、按环划边界）在数据库里其实很少直接照搬，因为纯随机放置会导致负载不均；很多号称"一致性哈希"的数据库（如 Cassandra）实际用的是虚拟节点 + 固定/比例分区的变体。

因此看到"某数据库用一致性哈希"时，别默认它就是教科书里的 Karger 环——要落到该库文档确认它到底怎么放置节点、怎么再平衡。这也是本报告把"固定分区数""比例分区"和"一致性哈希"并列而非混为一谈的原因：它们解决的是同一个问题（避免 mod N 的全量迁移），但机制与均衡性质不同。冲突点见下方来源。

## 5.3 二级索引分区

### 5.3.1 为什么二级索引难分区

分区是按主 key（primary key）切的，但应用常要按非主 key 的字段查询（如"颜色=红的所有车"），这类字段上的索引叫二级索引（secondary index）。难点在于：二级索引的值和主 key 的分区归属天然对不齐——同样"红色"的记录，其主 key 可能散落在所有分区上，索引到底该放哪、查询该问谁，就成了问题。

主 key 分区像"按身份证号分档案室"，而二级索引查询是"找出所有姓张的人"——姓张的人身份证号五花八门，分布在每个档案室里。于是有两种建索引的思路：要么每个档案室各自维护"我室内姓张的人"的小名册（本地索引），要么另建一套"全公司姓张的人"的总名册并按姓氏分区（全局索引）。这就是下面两小节。

### 5.3.2 本地索引（document-partitioned）与 scatter-gather

本地二级索引（document-partitioned，DDIA 称按文档分区的索引）让每个分区只为自己存的记录维护索引。写入简单：一条记录写进某分区，就在同分区内更新它的二级索引，一次分区内操作即可，无跨分区写。

代价在读：按二级索引查询时，因为符合条件的记录可能落在任意分区，必须把查询发给所有分区、各自返回本地命中、再在协调节点合并，这一模式叫 scatter-gather（分散-聚合）。它的问题是尾延迟放大——整个查询要等最慢的那个分区返回，分区越多、命中长尾的概率越大，p99 越难看。MongoDB、Cassandra、Elasticsearch、Riak 的二级索引多为此类。示意：

查询 → [P1 本地查][P2 本地查]…[Pn 本地查] → 协调节点合并 → 结果

### 5.3.3 全局索引（term-partitioned）

全局二级索引（term-partitioned，DDIA 称按词条分区的索引）不按记录所在分区、而按被索引的值（term）本身来分区。例如"颜色"索引：所有 color=red 的条目集中放在负责 "red" 的那个索引分区上，与这些记录的主 key 在哪无关。

好处是读高效：按二级索引查"红色的车"只需问持有 "red" 的那一个索引分区，不必 scatter-gather，避免尾延迟放大。代价是写变复杂：写入一条记录可能同时影响多个索引分区（一条车记录含颜色、品牌等多个被索引字段，各字段的 term 分布在不同索引分区上），一次写要更新多处索引，落在不同节点上。

### 5.3.4 取舍与异步维护

二级索引分区的本质是"读便宜/写便宜"二选一：本地索引写便宜（分区内写）但读贵（scatter-gather）；全局索引读便宜（点查一个索引分区）但写贵（一次写扇出到多个索引分区，理论上需跨分区事务才能保证一致）。

为回避昂贵的分布式事务，全局索引在实践中几乎总是异步维护：写主记录后，索引更新稍后才追上，因此存在一个索引陈旧窗口（读到的索引可能还没反映最新写入）。DynamoDB 的全局二级索引（GSI）即最终一致，就是这个原因。选型直觉：读多写少、且常按某固定字段过滤 → 倾向全局索引；写多、或查询字段多变 → 本地索引 + scatter-gather 更省心。易错点：以为"全局索引=强一致的实时索引"，实际它通常最终一致，业务若依赖"写完立刻按索引查到"会踩坑。

## 5.4 再平衡与热点治理

### 5.4.1 再平衡的目标与成本

再平衡（rebalancing）指在增删节点、或负载/数据分布变化时，把分区在节点间重新分配，使各节点数据量与负载重新趋于均衡。它的三条基本要求（DDIA）：再平衡后负载应公平分摊；再平衡期间数据库应继续可读写；只搬必要的数据、把网络与磁盘 I/O 开销降到最低。

成本主要是迁移开销：搬分区要占用网络带宽和磁盘 I/O，可能挤占正常请求的资源、抬高延迟。这正是 5.2 各方案追求"迁移量约 1/N 而非全量"的原因。易错点：再平衡不是免费的后台动作——大规模迁移若不限速，可能把集群拖入"越迁越慢、请求超时又触发更多问题"的境地，因此生产系统通常对再平衡带宽做节流。

### 5.4.2 自动 vs 手动再平衡

再平衡可以全自动（系统探测到不均衡就自行迁移）、全手动（管理员显式指定分区分配）、或半自动（系统建议、人工确认执行）。DDIA 明确倾向"至少让人参与其中"。

原因是全自动再平衡与自动故障检测叠加时很危险：若某节点只是短暂慢/网络抖动被误判为宕机，自动再平衡会启动大规模迁移去"补偿"，迁移本身又加重集群负载、让更多节点显得"慢"，从而触发更多迁移——形成级联雪崩。所以许多系统（如 Couchbase、部分 Elasticsearch 操作）把再平衡设计成需人工点击确认。这与大主题9容错模式里"自动化要防止把小故障放大成大故障"的直觉一致。

### 5.4.3 请求路由（routing / service discovery）

分区分布在多节点、且会因再平衡而变动，于是产生一个问题：客户端想读写某 key，怎么知道该连哪个节点？这就是请求路由 / 服务发现。DDIA 归纳三种做法：

方式一，客户端连任意节点，若该节点不持有目标分区，就把请求转发给正确节点（如 Cassandra、Riak 的 gossip 传播路由信息）。方式二，客户端先问一个独立的路由层（routing tier / 代理），由它转发（如通过代理）。方式三，客户端自己保有分区映射、直连正确节点。

许多系统用一个独立协调组件（如 ZooKeeper）保存"分区→节点"的权威映射，节点向它注册、路由层向它订阅变更，从而在再平衡后所有人都能拿到最新映射。核心难点是共识：所有参与方必须对"分区现在归谁"达成一致，否则请求会发错节点——这一致性问题的正确性回指 L5-01。

### 5.4.4 热点治理：key 加盐与拆分

即便用了哈希分区，仍可能出现单 key 热点（single hot key）：某一个 key 被极端频繁访问（如一条爆款微博、一位顶流明星的账户），哈希只能把不同 key 打散，对"同一个 key 被亿万次读"无能为力——它永远落在同一个分区。

工程上的缓解是给热点 key 人为加"盐"（salting）：在 key 后拼一个小随机数或分桶号，把一个逻辑热点 key 拆成 N 个物理 key（如 `celebrityX_00`…`celebrityX_09`），分散到不同分区，读时对 N 个变体并发查再合并。代价是读写都要多做 N 份工作、逻辑变复杂，且通常只对少数已识别的热点 key 手动施加、不能无差别全上。DDIA 指出目前多数系统不自动补偿单 key 倾斜，需应用层自己处理。

### 5.4.5 热点分裂与倾斜工作负载

对"某个分区整体（而非单 key）过热"的情况，治理手段是热点分裂：把过热分区从中间切开、其中一半迁走（即 5.2.5 动态分区的按需触发），让原本挤在一个分区的负载分到两个节点。

要点是"分裂"缓解的是分区级倾斜（分区内有很多不同的热 key），而"加盐"缓解的是单 key 倾斜（就一个 key 特别热）——两者对症不同，别混用。判断依据：若热点分区里是成千上万个中等热度的 key，分裂有效；若热点几乎全来自一两个超级 key，分裂后这一两个 key 仍在同一子分区里、白搬一场，得靠加盐。真实倾斜工作负载常两者并用。热点识别本身（怎么发现哪个 key/分区热）依赖监控与度量，度量学归 L5-12。
