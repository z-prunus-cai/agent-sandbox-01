负载均衡（load balancer，LB）是把大量客户端请求分摊到多台后端实例上的组件。它解决的是"单机吞吐撑不住、单机故障即全站挂"这两个问题：让流量在一组等价后端间分发，从而把容量做成"加机器就能涨"，把可用性做成"挂几台不致命"。本大主题只讲工程装配层——怎么在传输层还是应用层做转发、用什么算法分、怎么探活剔除坏后端、怎么把服务改造成能随意加减实例。一致性哈希的分布式理论正确性归 L5-01；K8s 里 Service/Ingress 这些对象的落地机制归 L5-13，本章只到"工程装配到这一层"为止。

## 3.1 L4 vs L7 负载均衡

### 3.1.1 L4 负载均衡（传输层转发）

L4 负载均衡工作在 OSI 传输层，依据 IP 四元组（源 IP、源端口、目的 IP、目的端口）和协议来决定把一条 TCP/UDP 连接转发给哪台后端，全程不解析连接里承载的应用数据。它看到的只是"一条连接要去某个端口"，据此选一台后端，然后把这条连接的所有数据包都转发到那台后端。

对初学者最关键的直觉是"L4 不拆信封"：它只看信封上的地址（IP+端口），不拆开看信里写了什么（HTTP 路径、Host 头、Cookie）。因为不解析应用层，L4 转发极快、CPU 开销低、能扛极高的连接数与吞吐，也天然支持任意基于 TCP/UDP 的协议（不限于 HTTP）。代价是"看不懂内容"：它无法按 URL 路径分流，无法读 Cookie 做会话保持（只能靠源 IP 哈希这种粗粒度手段），也做不了应用层的重试或改写。一个常见误区是以为 L4 一定不终结 TLS——L4 通常直接透传加密流量给后端由后端解密，但这不是"不能"，而是"不需要看内容就不看"。

### 3.1.2 L7 负载均衡（应用层路由）

L7 负载均衡工作在应用层，会真正解析 HTTP/gRPC 等协议：读取请求行、Host 头、路径、方法、Cookie 等，据此做路由决策。因此它能实现"把 /api 的请求发到 API 集群、把 /static 的请求发到静态资源集群"这类基于内容的分流，也能做 TLS 终结、请求头改写、按响应重试、限流、灰度等应用层能力。

直觉上 L7 是"拆信封读信再决定送谁"。它比 L4 多做了协议解析和（通常的）TLS 解密，所以单请求开销更高、吞吐上限更低，但换来了远强的表达力：现代 API 网关、Ingress、服务网格的 sidecar（如 Envoy）本质都是 L7 代理。一个关键区别是连接语义：L7 代理通常在客户端和后端之间维持两段独立连接（客户端↔代理、代理↔后端），可以复用到后端的连接池，也因此能在应用层做连接级的负载均衡（对 gRPC 这种长连接多路复用的协议尤其重要——L4 只能把一整条长连接钉在一台后端，L7 能把连接里的每个请求分散开）。易错点：不要把"L7 一定比 L4 好"当结论，二者是不同层的工具，超高吞吐的四层入口常用 L4，需要内容路由的业务层用 L7，大型架构往往 L4 在前、L7 在后串联。

### 3.1.3 转发拓扑与 NAT/DSR 数据路径

L4 转发在数据路径上有两种典型做法。一种是 NAT 模式：LB 改写目的地址把包转给后端，后端的回包也必须经过 LB 改写回来，所以进出流量都过 LB。另一种是 DSR（Direct Server Return，直接服务器返回）：请求经 LB 到后端，但后端的响应绕过 LB 直接回客户端，LB 只处理入向流量。

下面是三种拓扑的数据路径对比（独占块级示意）：

```
L4 NAT：      client → LB → backend
              client ← LB ← backend        （回程也过 LB）

L4 DSR：      client → LB → backend
              client ←──────── backend      （回程绕过 LB）

L7 代理：     client ⇄ LB ⇄ backend        （两段独立连接，进出都过 LB）
```

初学者需要的直觉是"为什么要有 DSR"：Web 流量通常下行（响应）远大于上行（请求），如果响应也走 LB，LB 的带宽会先成为瓶颈；DSR 让 LB 只扛入向小流量，出向大流量由后端各自直接吐给客户端，极大提高 LB 的可扩展性。代价是 DSR 部署更复杂（后端要配置能以 LB 的虚拟 IP 应答、通常要求同二层网络），且 LB 看不到回程也就更难做精细统计。L7 代理因为要读写应用层内容，进出都必须过代理，无法做 DSR，这也是 L7 吞吐天花板更低的一个结构性原因。

## 3.2 均衡算法

### 3.2.1 轮询与加权轮询（round-robin / weighted round-robin）

轮询是最基础的算法：把请求按顺序依次发给后端列表里的每一台，发完一圈再从头开始。加权轮询给每台后端一个权重，权重高的在一圈里被选中的次数更多，用来照顾"有的机器配置强、有的弱"的异构集群。Nginx 的 upstream 默认就是加权轮询，无需任何指令。

轮询的直觉是"发牌"：把请求像发扑克一样一张一张轮流发出去。它简单、无需维护后端状态、在后端同构且每个请求耗时相近时分布很均匀。易错点在于它只看"发了几个"，不看"每个请求多重"：如果请求耗时差异大（有的查询 1ms、有的 5s），轮询会把慢请求和快请求平均地撒到各机器，可能出现某台恰好连续接到几个慢请求而积压，而它下一轮还是照发不误。所以轮询适合请求开销均匀的场景，不适合请求耗时高度不均的场景。

### 3.2.2 最少连接 / 最少请求与"二选一"（least-conn / least-request / P2C）

最少连接（Nginx `least_conn`）把新请求发给当前活跃连接数最少的后端，也考虑权重。它的直觉是"谁最闲发给谁"：活跃连接数是后端当前负载的近似信号，慢后端会积压更多未完成连接，于是自动少分给它，比纯轮询更能自适应请求耗时不均的情况。

Envoy 的对应策略叫加权最少请求（weighted least request），默认并不扫描全部后端，而是用"二选一的力量"（Power of Two Choices，P2C）：随机挑 2 台（Envoy 默认 `choice_count = 2`），比较这 2 台的活跃请求数，把请求发给较少的那台。

```
P2C：随机取 2 台 → 比较活跃请求数 → 选更少的那台
```

为什么是"随机二选一"而不是"全局选最少"？全局扫描选最少在分布式多 LB 场景有个著名陷阱——"羊群效应"：多个 LB 同时看到同一台最闲，就会同时把请求都砸向它，反而把它压垮。P2C 用极小的随机性（只比 2 台）就能把最坏负载从"随机分配的 O(log n)"降到"O(log log n)"量级，既避免羊群、又几乎和全局最优一样均衡，是现代 LB 的常用默认。易错点：least-conn/least-request 依赖"连接/请求数能反映负载"这个前提，对 keep-alive 长连接或 gRPC 多路复用（一条连接上跑很多请求）时，"连接数"就不再等于"负载"，需要用"请求数"口径而非"连接数"口径。

### 3.2.3 哈希与会话粘性（hash / ip_hash / 粘性会话）

哈希类算法用请求里某个键（客户端 IP、某个 header、Cookie、URL）算哈希，映射到固定的一台后端，保证"同一个键总落到同一台"。Nginx 提供 `ip_hash`（按客户端 IP，IPv4 取前三个八位组作键）和更通用的 `hash key`（可用任意变量作键）。这类算法用来实现会话粘性（session affinity / sticky session）：让同一用户的连续请求打到同一台后端，从而用得上后端本地缓存或本地会话状态。

粘性有两种典型实现：一种是 LB 基于请求特征哈希（如 ip_hash）；另一种是 L7 基于 Cookie——LB 在响应里种一个标识后端的 Cookie，客户端后续带回来，LB 据此路由到同一台。直觉上粘性是"认人"：让熟客总找同一个柜台，柜台就记得他。但粘性有明显易错点：一是分布不均，大客户或 NAT 后一大片用户共用一个出口 IP 时，`ip_hash` 会把他们全钉到一台造成热点；二是弹性差，后端一旦增减，普通取模哈希会让大量键重新映射（见下一项），粘的会话集体失效；三是它和"无状态化"（见 3.4）是对立取向——粘性是"把状态留在某台"的权宜，真正可扩展的做法是把状态外置、让任意台都能服务任意用户。

### 3.2.4 一致性哈希（consistent hashing：ring hash / ketama / maglev）

一致性哈希是为"后端数量会变"设计的哈希方案。普通哈希用"键 mod N"（N=后端数）定位，一旦 N 变（加/减一台），几乎所有键的归属都变，缓存全部失效、粘性全部丢失。一致性哈希把后端和键都映射到同一个环形哈希空间（0 到 2^k−1 首尾相接），键顺时针找到的第一台后端就是它的归属；增减一台时，只有环上相邻一段的键需要迁移，其余不动。

```
        [0]
     n3      n1
   .    环     .        键 k 顺时针找到的第一个节点 = 归属
     n2      k
        ...
   删除 n1 → 只有本该落 n1 的键改落顺时针下一个节点，其余键不动
```

它的核心价值是"最小化重映射"：理论上增减一台只影响约 1/N 的键。为解决"少量节点在环上分布不均"的问题，实现会给每台后端放很多"虚拟节点"（Nginx `hash ... consistent` 与 Envoy `ring_hash` 都用 ketama 算法，即每台后端在环上撒多个点），让分布更平滑。Envoy 还提供 `maglev`（一个固定大小、默认 65537 项的查找表），比环形哈希的表构建和查找都快，代价是节点变动时稳定性略差（更多键会移动）。

初学者要抓住两个点。其一，一致性哈希不是"负载最均衡"的算法，它是"变动时扰动最小"的算法——追求均衡该用 least-request，追求缓存亲和/粘性稳定才用一致性哈希。其二，它有个源头：这套思想出自 Karger 等人 1997 年的论文（STOC'97），最初就是为 Web 缓存去热点而提出，后来成为分布式缓存、分片、粘性 LB 的通用基石。它的分布式正确性证明归 L5-01，本章只用它的工程性质。

## 3.3 健康检查与故障剔除

### 3.3.1 主动健康检查（active health check）

主动健康检查是 LB 周期性地主动向每台后端发探测请求（如定时打一个 `/healthz`、或建一次 TCP 连接），根据响应状态和延迟判断后端是否健康，不健康就从可用列表里摘掉、恢复了再加回来。它的直觉是"定期点名"：不管有没有真实流量，LB 都主动问一句"你还活着吗"。

主动探测的好处是能在真实用户请求打到坏后端之前就发现问题（探测先于流量），也能探测"进程活着但依赖已坏"这类深层故障（只要健康检查端点检查了下游依赖）。关键参数一般包括探测间隔、超时、连续成功/失败阈值（连续 N 次失败才判定不健康，连续 M 次成功才判定恢复——用阈值而非单次结果是为了抗抖动）。易错点有二：一是探测太频繁会给后端和 LB 都加负担，太稀疏又发现得慢，要权衡；二是健康检查端点的设计——如果 `/healthz` 只返回 200 而不真正检查关键依赖，会出现"探测通过但实际不能服务"的假健康。实现差异要注意：Nginx 开源版不含主动健康检查，`health_check` 指令与 `ngx_http_upstream_hc_module` 属于商业版 Nginx Plus；Envoy 开源即内置主动健康检查。

### 3.3.2 被动健康检查 / 离群点检测（passive health check / outlier detection）

被动健康检查不额外发探测，而是观察真实流量的结果：如果发给某台后端的真实请求连续失败（如连续多个 5xx、连接超时），就把它判为坏并暂时剔除。Nginx 开源版用 `max_fails`（默认 1）和 `fail_timeout`（默认 10 秒）实现被动剔除——在 `fail_timeout` 时间窗内失败次数达到 `max_fails` 就把该后端标记不可用并在该时长内不再向它发请求。Envoy 把这套机制叫离群点检测（outlier detection），依据连续 5xx、连续网关错误、成功率偏离、故障百分比等维度动态踢出表现异常的后端。

被动检查的直觉是"用真实流量当探针"：不专门去问，而是从"发给它的请求老是失败"直接推断它坏了。好处是零额外探测开销、且反映的是真实服务能力（而非一个可能造假的 /healthz）；代价是"得先有用户请求失败才发现"，即用户先当了小白鼠。所以主动与被动通常一起用、互补：被动兜住"探测通过但实际在坏"的漏网之鱼，主动兜住"当前无流量所以被动看不到"的空窗。易错点：`max_fails` 默认 1 意味着单次失败即剔除，对偶发抖动可能过于敏感，生产中常调大；另外被动检查判定的是"这台相对别人差"，在整片后端都在返错时（比如下游共同依赖挂了）不该继续踢——这正是下一项 panic 阈值要处理的。

### 3.3.3 故障剔除、恢复与惩罚性退避（ejection / recovery / backoff）

后端被判坏后不是永久删除，而是"剔除一段时间再试探性放回"。典型做法是剔除后过一个冷却期把它当作候选重新放回一小部分流量，若又立刻失败则再次剔除，且每次剔除时长按指数增长（Envoy 的离群点检测即采用剔除时长随重复失败指数增长、直到上限的策略）。恢复侧还常配合"慢启动"（slow start）：刚恢复或新加入的后端先只给少量流量、逐步爬坡到满负载，避免冷实例（缓存空、连接未预热）一上来被打满又倒下。

直觉是"给犯错的后端罚站，屡犯罚更久，改好了先试岗再转正"。指数退避的意义在于：一台反复失败的后端很可能是真坏（而非偶发），越试越浪费用户请求，所以拉长间隔；而一旦真的恢复，试探性放回又能让它自动归队，无需人工干预。易错点：恢复时若不做慢启动而直接满流量灌给刚回来的实例，很容易因缓存/连接未预热造成"恢复即再挂"的震荡；剔除阈值设得太激进则会在网络抖动时频繁踢来踢去（flapping），反而降低可用容量。

### 3.3.4 panic 阈值与"宁可全发也不发空"（panic threshold）

当被判为健康的后端比例低于某个阈值时，继续按"只发给健康后端"的逻辑会把全部流量挤到寥寥几台上、瞬间压垮它们，形成雪崩。为此 LB 设有恐慌阈值（Envoy 默认健康后端比例低于 50% 进入 panic 模式）：一旦健康比例过低，LB 干脆忽略健康状态、把流量分散给所有后端（包括被标记不健康的），赌"部分坏后端也许还能处理一些请求"，好过"把仅存的健康后端也压垮"。

直觉是"当好人不够多时，不如大家一起扛"。这个设计承认一个现实：大面积不健康往往不是后端真都坏了，而是健康检查本身或共同依赖出了问题（比如全网抖动导致探测集体失败），此时"信任健康检查、只发少数几台"是灾难性的。所以 panic 模式本质是对健康检查判断的一个安全阀。易错点：初学者容易觉得"发给不健康后端不是雪上加霜吗"——关键在于比较对象是"把全部流量压到极少数台直接打挂"，两害相权取其轻；这也提醒健康检查阈值不能设得过于敏感，否则容易误触 panic。Envoy 的 50% 为默认值，可配置，⚙锚 latest。

#### 来源与时效

- 锚点：Nginx 官方文档 ngx_http_upstream_module（nginx.org/en/docs，核实 2026-08-01）——被动检查 `max_fails`（默认 1）、`fail_timeout`（默认 10s）；主动健康检查 `health_check` / `ngx_http_upstream_hc_module` 仅 Nginx Plus（商业版）。
- 锚点：Envoy 官方文档 outlier detection（envoyproxy.io/docs/…/upstream/outlier，latest，核实 2026-08-01）——被动=离群点检测（consecutive 5xx / 成功率 / 故障率），剔除时长指数增长至上限；主动与被动可独立或同时启用；panic 场景下不再按健康状态过滤。Envoy 健康检查（active）文档为主动探测一手。⚙演进快·锚 latest·随时变。
- 待核：Envoy panic 阈值默认值（业界与文档常述为 50%），以当前 latest 的 Cluster/health checking 文档为准；本文按 50% 表述并标待核·可配置。
- 冲突项：主动/被动"health check"术语跨厂商命名不一（Envoy 称被动侧为 outlier detection，Nginx 用 max_fails/fail_timeout 表达被动，未单独命名），本文已按"主动探测 vs 观察真实流量"的机制口径统一，并点明命名差异。

## 3.4 横向扩展与无状态化

### 3.4.1 横向扩展 vs 纵向扩展（scale out vs scale up）

纵向扩展（scale up）是把单台机器换成更强的（更多 CPU/内存）；横向扩展（scale out）是加更多台同等机器、用 LB 把流量摊到它们上。负载均衡是横向扩展的前提——有了它，"提升容量"才等于"往后端池里加实例"。

纵向扩展像"把一个收银员换成手更快的收银员"，横向扩展像"多开几个收银台"。纵向扩展简单（应用无需改造）但有硬上限（单机再强也有天花板，且高端硬件价格非线性上涨）、且单点故障风险不变（还是一台）。横向扩展理论上可近乎无限加机器、天然带冗余（挂几台不致命），是大规模系统的主路径，代价是应用必须能"多实例并行跑同一份逻辑"——这就要求服务无状态（见下一项）。易错点：横向扩展不是免费午餐，它把复杂度从"买更大的机器"转移到"让多实例协同"（数据一致性、会话、分布式协调），本大主题的分片/复制/一致性折衷等其他主题正是为解决这些代价而存在。

### 3.4.2 无状态服务（stateless service）

无状态服务指处理请求所需的状态不保存在处理它的那台实例的本地内存/本地磁盘里，任何一台实例都能处理任何一个请求、结果不因"落到哪台"而不同。这是横向扩展和随意增减实例的根本前提：只有无状态，LB 才能把请求随便发给任意实例，扩容才能"新实例即插即用"，故障才能"挂了直接换一台不丢会话"。

直觉是"每个收银台都一样，你排哪个队都行，柜台不需要记得你是谁"。反例是把用户登录会话存在某台实例的本地内存里——那这个用户就只能被这台服务，这台一挂会话就没了，也没法把他的请求分给别的实例，于是被迫用粘性会话（3.2.3）把他钉死在这台，弹性和容错双输。无状态不等于"系统没有状态"，而是"把状态从应用实例里挪出去"（见下一项）。易错点：一些看似无害的本地状态会悄悄破坏无状态性——本地文件上传暂存、进程内缓存、本地生成的自增序号、写死到本地的 WebSocket 连接，都会让某些请求只能由特定实例处理，是横向扩展时的隐藏地雷。

### 3.4.3 会话外置与状态存储（session externalization）

会话外置是把原本放在实例本地的会话/状态搬到所有实例共享的外部存储（如 Redis、数据库），或干脆放到客户端（如带签名的 JWT/Cookie）。这样每台实例都能从共享处读到同一份状态，实例就变成了可互换的无状态处理单元。

直觉是"把柜台的记事本挪到大家共用的中央档案室"：无论你这次被分到哪个柜台，柜台都去同一个档案室查你的资料，于是哪个柜台服务你都一样。两条常见路线：一是服务端集中存（Redis/DB 存 session，实例只存请求期临时数据），好处是服务端可随时使会话失效、状态量不受 Cookie 大小限制；二是客户端存（签名/加密的 token 放 Cookie），好处是服务端完全无状态、无需查存储，代价是难以主动撤销、且每次请求都要传输 token。易错点：会话外置只是把状态问题从"钉在某台"变成"依赖一个共享存储"——这个共享存储自己就成了新的扩展与可用性瓶颈和单点，需要它自身也能分片/复制（跨本大主题的分片、复制主题）；此外用 JWT 这类客户端状态时，"如何主动登出/吊销"是经典难点，不能想当然。

### 3.4.4 弹性扩缩与连接优雅摘除（elastic scaling / connection draining）

服务无状态化之后就能弹性扩缩：负载高时自动加实例并注册进 LB，负载低时自动减实例。但"减实例"不能粗暴地直接杀进程——那会把该实例上正在处理的请求全部打断。正确做法是连接优雅摘除（connection draining / graceful shutdown）：先把该实例从 LB 的可用列表里摘掉（停止给它发新请求），等它把手头已接的请求处理完（或到超时上限）再真正下线。

直觉是"要关的收银台先挂'本台不再接新顾客'的牌子，把正在结账的这几位服务完再关灯"。这样扩缩容和滚动发布才不会造成用户可见的错误。它和健康检查配合：摘除时 LB 通过健康检查/主动注销把该实例移出池，新请求自然流向其余实例。易错点：优雅摘除需要"下线信号 → 停止接新 → 排空存量 → 退出"这一整套配合，若应用收到终止信号立刻退出、或 LB 摘除与进程退出之间存在时间差，都会漏掉在途请求造成偶发 5xx；这类"扩缩容/发布期间的瞬时错误"往往就出在优雅摘除没做对。具体到编排平台（如 K8s 的 preStop 钩子与终止宽限期）的落地机制归 L5-13，本章只到"工程上必须做优雅摘除"这一层。
