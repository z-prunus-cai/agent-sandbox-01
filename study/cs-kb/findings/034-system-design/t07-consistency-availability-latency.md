## 7.1 CAP 工程解读

### 7.1.1 CAP 三要素在工程语境里各指什么

CAP 是对一个"会复制数据、跨多台机器"的系统提出的三个属性：一致性（Consistency）、可用性（Availability）、分区容忍（Partition tolerance）。CAP 定理的工程结论是：当网络发生分区时，一个系统无法同时保住"一致"和"可用"两者，只能保住其一。

这三个词在 CAP 里有**专门的、比日常用法更窄的含义**，初学者最容易在这里翻车。

CAP 的 C 指**线性一致性（linearizability）**，也就是最强的那种一致性：任何一次读，都能读到"在它之前已经完成的那次写"的最新值，整个系统看起来像只有一份数据、所有操作排成一条全局时间线。它不是数据库里 ACID 那个 C（那个 C 指"事务不破坏完整性约束"，是另一回事，见 7.1.4）。

CAP 的 A 指**每一个发到"没有宕机的节点"的请求，都必须在有限时间内返回一个非错误的响应**。注意它不要求"低延迟"，只要求"最终返回且不是错误"。一个节点只要没死，就不能用"我等分区恢复了再答复你"来搪塞——那样就算不可用。

CAP 的 P 指**系统在网络分区（节点之间消息丢失或严重延迟，网络被切成互不相通的几块）发生时仍能继续运行**。

理解这三个定义的宽窄，是读懂后面一切折衷的前提。很多"CAP 悖论"其实是把这三个词按日常含义理解造成的假矛盾。比如有人说"我的系统又一致又可用啊"，多半是因为他把 C 理解成了弱得多的"最终会一致"，或者他根本没在分区状态下测过。

### 7.1.2 分区不是可选项：真正的选择是"分区来了，舍 C 还是舍 A"

CAP 常被写成"三个里挑两个"，但工程上更准确的表述是：**P（分区）不是你能选择放弃的东西，它是客观世界强加给你的**。只要系统跨多台机器、走网络通信，网络就有可能故障、丢包、延迟飙升，分区迟早会发生。你不能"选择不要分区容忍"——你只能选择分区真的发生时系统怎么反应。

所以真正的、唯一的选择发生在分区期间：

分区发生时，一个被切开、联系不上其它副本的节点，收到一个写请求，它只有两条路。要么**接受这次写**（保住可用性 A），但因为它联系不上其它副本，其它副本读到的还是旧值，全局不再线性一致，于是舍弃了 C。要么**拒绝服务或阻塞**（保住一致性 C），宁可不返回也不返回一个可能过时/冲突的结果，于是舍弃了 A。

这就是把系统称为 **CP**（分区时保 C 舍 A）或 **AP**（分区时保 A 舍 C）的由来。

两个数据中心 DC1、DC2 各存一份账户余额副本，中间光缆被挖断（分区）。用户在 DC1 发起取款。CP 系统会说"我联系不上 DC2，无法确认没有并发操作，本次拒绝"（一致但当下不可用）；AP 系统会说"先让你取，等网络恢复再对账"（可用但可能两边都取了、余额出负，不一致）。选哪个，取决于这是银行账户还是社交点赞。

以为"分区容忍"是一个可以像开关一样关掉的功能。单机数据库确实不涉及 CAP，因为它没有网络分区问题——但那是因为它没有跨机器复制，而不是因为它"选择了 CA"。一旦你为了扩展或容灾而复制到多台机器，P 就自动上桌，你只剩 C/A 之选。所谓"CA 系统"在跨网络复制的语境里基本是个不存在的选项。

### 7.1.3 "三选二"通俗说法的误导与纠正

流传最广的 CAP 讲法是"一致性、可用性、分区容忍，三个只能选两个"。这句话作为记忆口诀没错，但按字面理解会误导，业界一手作者对此有明确纠正。

第一个误导：它暗示三者地位对等、可以任意组合，包括"CA"。但如上一节所说，分区是客观现实不是选项，"CA"在分布式复制场景里没有实际意义。

第二个误导：它暗示这是一个"系统级、一刀切、永久"的属性——好像一个系统天生就是 CP 或 AP，一辈子如此。实际上，C 和 A 的取舍**只在分区期间才需要做**；分区没发生时，一个设计良好的系统可以同时给你强一致和高可用，此时 CAP 什么都没说（这正是 PACELC 要补的洞，见 7.2）。而且很多系统的一致性级别是**可调的**（如 Cassandra 的 tunable consistency、DDB 的可选强一致读），甚至可以在同一系统里对不同操作选不同的边（见 7.4.4）。

Kleppmann 在其广为引用的短文里主张"别再简单地把数据库叫 CP 或 AP"，理由正是：一个系统的行为取决于它面对的具体故障类型、它的配置、乃至具体是哪个操作，用单个标签盖章会掩盖这些差别。DDIA 2nd ed 也强调 CAP 定义狭窄（C 特指线性一致、A 有专门定义、只考虑网络分区一种故障），实用价值有限，不宜当成系统设计的主要框架。

工程上正确的用法：把 CAP 当成一个**提问的起点**——"分区来的时候我这个操作要保一致还是保可用？"——而不是给系统贴标签的分类学。两个来源在这一点上一致（DDIA 与 Kleppmann 短文），冲突之处见本节末。

### 7.1.4 CAP 的 C 不是 ACID 的 C（同名不同物）

CAP 里的 C 和数据库事务 ACID 里的 C 是两个**完全不同**的概念，只是碰巧都叫 Consistency，是系统设计里头号同名陷阱。

CAP 的 C = 线性一致性，讲的是**多副本之间**看到的数据是否像单一最新副本，是一个关于"复制/分布"的属性。

ACID 的 C = Consistency，讲的是**一个事务执行前后，数据库都满足预先声明的完整性约束**（外键、唯一约束、余额非负等不变量），是一个关于"事务不破坏应用层规则"的属性，而且这个"一致"很大程度上要靠应用自己写对事务来保证，数据库只是不让你违反显式约束。

初学者读到"CAP 说分区时要牺牲 C"，很容易恐慌地以为"那我的数据库约束、我的事务原子性都保不住了"。不是的。CAP 牺牲的是"跨副本读到最新值"这层；单节点上的 ACID 约束、事务原子性是另一套机制（WAL、锁、MVCC），跟 CAP 的取舍不在一个维度。DDIA 明确指出 CAP 的 C 与 ACID 的 C 无关，建议不要混用这个词。

## 7.2 PACELC

### 7.2.1 PACELC 的动机：CAP 只讲了分区那一半

CAP 有一个大盲区：它**只描述了网络分区发生时**该怎么办，对"绝大多数时间里网络是好的"这个常态只字未提。可现实中分区是罕见事件，系统 99.9% 的时间都运行在没有分区的正常状态下。在这个常态里，系统仍然要做一个天天都在做的重要折衷——它却不在 CAP 的视野里。

这个被 CAP 忽略的常态折衷是：**延迟 vs 一致性**。当你有多个副本，一次写要不要等所有（或多数）副本都确认了才算成功？等——延迟高但一致性强；不等——延迟低但可能读到还没同步过去的旧值。这个取舍每秒都在发生，跟有没有分区无关。

PACELC 由 Daniel Abadi 提出，就是为了把这两半拼全：分区时的 C/A 折衷（CAP 那一半）**加上**常态下的延迟/一致性折衷（CAP 漏掉的那一半）。

### 7.2.2 PACELC 决策式与四种组合

PACELC 是一个把系统的两次折衷都表达出来的助记式，读作 "P-A-C-E-L-C"：

```
if (Partition)   then choose Availability or Consistency   // 分区时：A 还是 C
else (Else,常态) then choose Latency     or Consistency    // 无分区时：L 还是 C
```

字母 P 是 "if Partitioned"，其后 A/C 表示分区时选可用还是选一致；字母 E 是 "Else"（即没有分区的正常状态），其后 L/C 表示常态下选低延迟还是选强一致。

因此一个系统可以用形如 **PA/EL、PC/EC、PA/EC、PC/EL** 的两段标签描述：

```
PA/EL：分区时保可用，常态下保低延迟（两头都偏向"快而软"）——典型 Dynamo 风格
PC/EC：分区时保一致，常态下也保强一致（两头都偏向"慢而硬"）——典型强一致数据库
PA/EC：分区时保可用，但常态下仍要强一致
PC/EL：分区时保一致，但常态下宁可低延迟（较少见）
```

相比 CAP 的单标签，PACELC 的价值在于它逼你分别回答两个场景，避免用"AP/CP"一个词盖住系统在正常运行时的行为。

### 7.2.3 常见系统的 PACELC 归类（配置相关，随版本变）⚙演进快·随时变

Abadi 原论文给出的经典归类：Dynamo 及其风格的系统（Cassandra、Riak 早期）是 **PA/EL**——分区时可用、常态下为低延迟不强求一致；完全 ACID 的强一致系统（如 VoltDB/H-Store、传统单主强一致配置）是 **PC/EC**；Abadi 把 MongoDB 归为 **PC/EC**（更常被后续文献讨论的是其随默认写关注变化的行为）。

**这些归类高度依赖版本和配置，不能当成系统的永久属性**。

Cassandra 是"可调一致性"（tunable consistency）：同一个集群，读写时指定 `ONE` 就偏 AP/EL，指定 `QUORUM`/`ALL` 就偏 EC，甚至能满足 `R+W>N`（回指大主题6 无主/quorum）逼近强一致。所以说 Cassandra "是 PA/EL" 只对它的默认/常见用法成立。

MongoDB 的默认写关注（write concern）在其历史上从 `w:1` 演进到了 `w:majority`（此变更随主版本发生，具体版本号本机无法核实，标「待核」），默认读关注、是否走 majority 读也影响它落在 PACELC 的哪一格。因此不同年代的资料给 MongoDB 贴的标签会打架——这不是资料错，是系统本身变了。

结论：**用 PACELC 描述一个系统时，务必带上"在什么配置下"**。凡本报告给出的具体系统归类，都以"原论文口径 + 配置相关"看待，具体默认值以你所用版本的官方文档为准，标 ⚙演进快·随时变，核实日期 2026-08-01。

### 7.2.4 延迟与一致性为何天生对立

PACELC 的 "EL vs EC" 不是人为规定，而是物理决定的。理解这一点就理解了为什么强一致系统在跨地域时几乎必然更慢。

要让一次写对后续的读**立刻可见且一致**，这次写必须在返回"成功"之前，先让足够多的副本都记下它。如果副本分布在不同城市甚至不同大洲，一次"等多数副本确认"就至少要付一个**跨地域网络往返（RTT）**的时间。跨大洲 RTT 通常在几十到上百毫秒量级（具体数值取决于地理与线路，属大主题2 的量级基准，此处不展开数值）。

反过来，如果允许写只在本地副本落地就返回、异步再慢慢同步给远端（回指大主题6 异步复制），那么写延迟可以低到本地磁盘/内存量级，但代价是远端副本在同步完成前读到的是旧值——一致性被牺牲。


```
强一致 = 写要等（多数）副本确认 = 至少一个跨副本往返的延迟
低延迟 = 写不等远端确认 = 远端会有一段时间读到旧值
```

所以延迟和一致性像跷跷板，你压低一头另一头必然翘起，这与分区无关，是常态下就存在的成本。这也解释了为什么很多全球化产品在"写自己的数据要不要立刻全球可见"上会做妥协——为了让用户感觉快。

## 7.3 一致性谱系工程含义

### 7.3.1 一致性谱系概览：从强到弱是一条连续带

"一致性"不是"有/没有"的开关，而是一条从强到弱的**谱系**。工程上常用的几档，从强到弱大致是：

```
线性一致性（强一致，linearizable）
   ↓ 放松
顺序一致性（sequential）
   ↓ 放松
因果一致性（causal）+ 各种会话保证
   ↓ 放松
最终一致性（eventual）
```

越往上：应用看到的行为越接近"只有一份数据、按真实时间顺序操作"，写代码越省心，但延迟越高、分区时越可能不可用。越往下：越快、分区时越可用，但应用要自己面对"读到旧值""看到乱序""并发写冲突"等异常。

工程选型的核心问题不是"要不要一致"，而是"**我这个业务能接受放松到哪一档**"。谱系的形式化定义、各档之间的严格强弱证明属 L5-01，本报告只讲每一档对应用代码意味着什么可见行为。

下面逐档讲工程含义。

### 7.3.2 线性一致性（强一致）对应用意味着什么

线性一致性给应用的承诺是：**系统表现得就像只有一份数据**。一旦某次写返回成功，此后任何客户端的任何读都必定读到这个新值（或更新的值），绝不会读回旧值；所有客户端看到的操作顺序是同一条、且符合真实发生的先后。

对应用开发者，这是最省心的模型——你可以像在单机上一样推理："我刚写进去了，那我（和别人）马上读一定读得到"。不需要考虑副本、不需要考虑同步延迟。

代价在 7.2.4 已说：写要等多数副本确认，延迟高；分区时若凑不齐多数副本，为保线性一致只能拒绝服务（CP 行为）。

分布式锁与 leader 选举（两个节点同时以为自己拿到锁会出灾难）、唯一性约束（同一个用户名不能被两人同时注册成功）、账务/库存的"不能超卖/不能透支"。这些地方读到旧值会直接导致业务错误，值得为强一致付延迟和可用性的代价。

线性一致性只保证"看起来像单份最新数据"，它**不等于事务隔离级别里的可串行化（serializability）**。可串行化讲的是"多个事务的交错等价于某个串行执行"，是关于事务的；线性一致讲的是"单个对象/寄存器的读写实时可见"，是关于单个数据项的。二者可以独立存在，合起来（strict serializability）才是最强的。这一区分的严格定义在 L5-01。

### 7.3.3 因果一致性与会话保证

因果一致性是一个非常实用的中间档：它**只保证"有因果关系的操作，大家看到的顺序一致"，而对没有因果关系的并发操作不强求全局统一顺序**。

如果操作 B "看到了" A 的结果（B 依赖 A），那 A 就是 B 的"因"。最经典的例子是评论区——先有帖子 P，再有回复 R（R 是对 P 的回复，因果上 R 依赖 P）。因果一致保证：任何人只要看到了回复 R，就一定也能看到它所回复的帖子 P，绝不会出现"看到一条孤零零的回复，却看不到它在回复啥"这种诡异现象。但对两条互不相关的帖子谁先谁后，因果一致不管，允许不同用户看到不同顺序。

因果一致之所以重要，是因为它是**在保持"分区时仍可用"的前提下能达到的最强一致性**（这个"最强"的结论是理论成果，归 L5-01；这里只用其工程含义）。也就是说，想要 AP 又不想让用户看到太离谱的乱序，因果一致是甜点区。

与因果一致密切相关的是一组**会话保证（session guarantees）**，它们是从单个用户会话角度看的、更细粒度的弱一致保证。常见四条：

读己之写（read-your-writes / read-your-own-writes）：你自己写的东西，你自己随后一定读得到。缺了它，用户改完资料刷新一下发现改动"没了"（其实是读到了还没同步的旧副本），体验极差。

单调读（monotonic reads）：你连续读，时间上不会"倒退"——不会第一次读到新值、刷新一下反而读回旧值。缺了它，用户会看到数据"闪回"过去。

单调写（monotonic writes）：你自己的多次写，会按你发出的顺序被应用，不会乱序。

写后读（writes-follow-reads / 也叫 read-your-writes 的对偶）：如果你基于读到的某个值再去写，那么你的写一定排在你读到的那个写之后。

这些会话保证很多可以用相对便宜的手段实现（比如把某用户的读写都路由到同一副本、或用版本号/时间戳带在会话里），是工程上性价比很高的"局部一致性",能消除最刺眼的用户可见异常，而不必上全局强一致。

各家资料对这几条会话保证的命名和边界略有出入（DDIA 与不同论文用词不完全一致），冲突见本节末；但四条的**直觉**是一致的，记直觉即可。

### 7.3.4 最终一致性与收敛、冲突

最终一致性是谱系里最弱的常用档：它只承诺"**如果停止写入、给足够时间，所有副本最终会收敛到相同的值**"，但对"多久"以及"收敛前你会读到什么"几乎不给保证。

这个"最终"是它的软肋——可能是几毫秒，也可能在分区/高负载下拖到很久；收敛前不同副本可能给出不同的旧值，客户端要有心理准备。DDIA 曾把 eventual consistency 戏称为"convergence"（收敛）更贴切，因为重点是"终会收敛"而非"某种一致"。

最终一致的核心工程挑战是**并发写冲突**：既然允许多个副本各自接受写（AP），就可能出现两个副本对同一数据写了不同的值，收敛时必须决定"听谁的"。常见冲突解决策略：

最后写入者胜（LWW, last-write-wins）：用时间戳，谁的时间戳大留谁。实现简单，但会**静默丢数据**（时间戳小的那次写直接没了），且依赖时钟，时钟不准就出错。

版本向量 / 因果追踪：记录每次写的因果关系，能区分"真并发冲突"和"一个是另一个的更新"；真并发的留给应用或 CRDT 处理。

CRDT（无冲突复制数据类型）：设计成数学上**天然可合并**的数据结构（如计数器、集合），任意副本任意顺序合并都收敛到同一结果，从根上避免冲突判定。适合购物车、协同编辑、点赞计数等。

选择哪种取决于业务能接受怎样的"合并语义"。购物车用"并集"（宁可多留商品也别丢）就很合理；而账务绝不能用 LWW 静默丢一笔。

## 7.4 AP/CP 选型后果

### 7.4.1 选边的根本判据：业务对"陈旧"和"不可用"哪个更不能忍

AP/CP 的选型，剥到最里层，就是回答一个业务问题：**当分区或故障发生、鱼与熊掌不可兼得时，我的业务是更受不了"读到/写入了过时或冲突的数据"（那就选 CP，宁可停），还是更受不了"服务直接不可用、拒绝请求"（那就选 AP，宁可脏）？**

这是个业务决策，不是技术决策。同样的技术，装在不同业务上答案相反：

社交媒体的点赞数、时间线、"最近浏览"——晚几秒一致、偶尔数字跳一下，没人受得了损失，但如果分区时直接刷不出来、发不了帖，用户立刻流失。这类**强烈倾向 AP**：可用压倒一致。

银行转账、库存扣减、订票选座、分布式锁——读到旧余额可能透支、旧库存可能超卖、旧锁状态可能两人同时下单同一个座位，这些是真金白银或安全问题。这类**强烈倾向 CP**：宁可这次操作失败/等待，也不能给出错误结果。

所以选型的第一步永远是问业务："这个操作，读到 5 秒前的旧值会怎样？完全拒绝服务 30 秒又会怎样？"两害相权取其轻。

### 7.4.2 选 AP 的后果：可用，但要吞下陈旧读和冲突处理

选 AP，得到的是"分区/故障时仍然能读能写"的高可用，但你必须在应用层承担一串后果，很多初学者只看到"高可用"的好处而低估了这些成本：

会读到陈旧数据（stale read）。用户可能看到别人已经改过、但还没同步到这个副本的旧值。UI 要能容忍、最好能提示"数据可能有延迟"。

会产生并发写冲突，必须有冲突解决策略（7.3.4 的 LWW/版本向量/CRDT）。这是 AP 系统里最容易被忽略、又最容易出数据错误的地方——"能写"不等于"写对了"，两个副本都接受了写之后，谁对谁错要你来收拾。

需要"读己之写"等会话保证来兜住最刺眼的体验问题（7.3.3），否则用户会遇到"我明明改了怎么没了"。

业务逻辑要设计成**可容忍暂时不一致并能事后对账/补偿**。比如先让用户下单，后台异步校验库存，真超卖了再取消并道歉——把强一致的检查从"下单同步路径"挪到"事后异步补偿"。

AP 把复杂度从"基础设施的可用性"转移到了"应用层的一致性处理"。你省下的是停机，付出的是代码里到处要处理旧值和冲突。

### 7.4.3 选 CP 的后果：一致，但分区/故障时会拒绝服务、且更慢

选 CP，得到的是"永远不会读到旧值/不会算错"的强保证，代价同样具体：

分区或副本不足时会**主动不可用**。为了不给出可能错误的结果，CP 系统在联系不上足够多副本（如凑不齐 quorum 多数）时会拒绝或阻塞请求。也就是说，网络一抖、某几台机器一挂，用户就可能收到错误或超时。可用性的账要认。

常态下延迟更高。如 7.2.4 所述，强一致要等多数副本确认，跨地域尤其明显。CP 系统往往在"写"和"强一致读"上更慢。

故障切换期间有空窗。单主 CP 系统主挂了要选新主（回指大主题6 故障切换），选主期间通常不可写，这段空窗要么拒绝写、要么排队等待。

对"读多写少但要求绝对正确"的场景（如库存、账务、配置中心），CP 的这些代价通常是划算的——偶尔的短暂不可用远比一次超卖/透支便宜。但对"必须永远在线"的前台展示，CP 的不可用窗口可能不可接受。

不要以为选了 CP 就"高枕无忧永远正确"。CP 只在**它的一致性协议覆盖的范围内**保证一致；跨系统（比如数据库 CP 但缓存 AP）、跨操作的组合仍可能出现不一致。一致性是端到端的，单个组件是 CP 不代表整条链路是 CP。

### 7.4.4 不必全局一刀切：按操作/按数据分别选边

一个常见误区是把 AP/CP 当成"整个系统必须统一选一个"。实际工程里，**同一个系统完全可以对不同的操作、不同的数据选不同的边**，这往往才是最优解。

同一个电商系统里：库存扣减和支付走 CP（不能超卖不能重复扣款），而商品浏览、评价展示、推荐走 AP（旧几秒无所谓，但要永远打得开）。把强一致的成本只花在真正需要的那一小撮操作上，其余全部享受 AP 的高可用和低延迟。

很多现代数据库支持这种"按操作调一致性"：如前述 Cassandra 的 tunable consistency（每次读写指定一致性级别）、DynamoDB 提供"最终一致读（便宜快）"与"强一致读（贵慢）"两种读、Spanner/Cosmos DB 等提供多档一致性级别供 API 选择（具体档位与命名随产品版本变，标 ⚙演进快·随时变，以官方文档为准，核实 2026-08-01）。

设计方法：把系统的每类操作列出来，逐一问 7.4.1 的两个问题（"读到旧值会怎样/拒绝服务会怎样"），据此给每类操作单独定 AP 或 CP，再选能满足这些需求的存储与一致性配置。这比"整个系统一刀切 CP（太慢太脆）或一刀切 AP（账都要算错）"都好。

把整章串起来的选型清单，可以浓缩成一条从业务到技术的推导链：

```
业务问题："这个操作读到旧值会怎样？拒绝服务会怎样？"
   ↓ 逐操作回答，两害取其轻
定每个操作的边：CP（不能错） / AP（不能停）
   ↓
定常态折衷（PACELC 的 E 段）：这个操作能否忍受强一致带来的延迟？
   ↓
定一致性档位：强一致 / 因果+会话保证 / 最终一致（+冲突解决策略）
   ↓
选/配置存储：用可调一致性数据库按操作分别配置
```
