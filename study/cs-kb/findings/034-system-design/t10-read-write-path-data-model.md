## 10.1 访问模式驱动选型

### 10.1.1 什么是访问模式

访问模式（access pattern）指一个系统实际会怎样读和写数据：读多还是写多、每次读是按主键取单条（点查）还是取一段区间（范围查）还是要跨大量行做聚合、查询是否需要跨实体连接、写是追加为主还是频繁原地更新、数据被访问的时间局部性如何。系统设计里的存储选型不是先挑一个"最好"的数据库，而是先把访问模式列清楚，再挑一个让这些模式跑得又快又省的存储。

初学者常把"选数据库"当成一场技术品牌之争（MySQL vs MongoDB vs 某某），其实真正决定成败的是访问模式与存储引擎特性的匹配度。一个直觉例子：如果你的系统 99% 的操作是"按用户 ID 取这个用户的完整资料"，那把用户资料存成一个自包含的文档、一次读取就拿全，会比拆成十张关系表每次 join 十次要快得多；反过来，如果你要频繁问"所有在 2020 年后注册、且购买过 A 类商品的用户"，这种跨维度、多条件的查询在关系模型里用索引和 join 很自然，硬塞进按单一主键组织的键值/文档存储反而别扭。

一个常见误区是"先建模再想查询"。在关系数据库里可以先按范式建好表、之后再想怎么查（关系模型的查询灵活性高）；但在多数 NoSQL（键值、宽列、文档）里，数据的物理组织必须迁就查询，业界公认的做法是"query-first / access-pattern-first design"——先枚举全部查询，再据此设计表和键。选错顺序会导致上线后发现某个高频查询在选定存储上根本没有高效路径，只能全表扫描或事后补一层派生存储。

### 10.1.2 读放大与写放大的取舍

任何存储设计本质上是在读代价和写代价之间做分配。读放大（read amplification）指一次逻辑读实际触碰了多少数据或做了多少工作（例如要 join 五张表、要扫描并聚合十万行）；写放大（write amplification）指一次逻辑写实际引发了多少物理写（例如更新一行要同步更新它的三个索引和两个物化视图）。降低读代价的手段（加索引、反范式冗余、预计算物化视图、加缓存）几乎都会抬高写代价与存储占用；反过来，写优化的设计（只追加、不维护额外索引）会把代价推到读时。

理解这一点能解释本大主题后面几乎所有技术的动机。索引让读快、让写慢（每次写要维护索引）。反范式（把常一起读的数据冗余到一起）让读少 join、让写要更新多份副本并承担不一致风险。物化视图和 CQRS 读模型是把"读时的计算"提前到"写时"做，用写放大和一致性窗口换读性能。没有免费的午餐——选型就是决定"把成本放在读侧还是写侧"，依据是你的系统读写比和延迟要求。

初学者容易无脑加索引、加缓存来提读性能，忽视了写侧被拖垮。一张被十个索引覆盖的表，写入吞吐可能只有无索引时的零头；一个命中率不高的缓存，反而在读路径上多了一跳和一致性维护负担。加任何读优化前先量化它对写路径的代价。

### 10.1.3 OLTP 与 OLAP 的工作负载分野

按访问模式，工作负载大致分两类。OLTP（在线事务处理）是面向用户的日常操作：每次读写只碰少量记录、按主键或索引定位、要求低延迟高并发，典型如"下单""查我的订单""改个人资料"。OLAP（在线分析处理）是面向分析的：每次查询扫描海量行、做聚合（sum/count/group by）、并发低但单查询重，典型如"上季度各地区销售额趋势"。两者访问模式差异巨大，因此长期演化出不同的存储组织：OLTP 多用行式存储（一行数据物理相邻，利于取整行、频繁更新），OLAP 多用列式存储（同一列数据相邻，利于只读几列却扫全表的聚合，且压缩率高）。

这个分野是数据模型选型的第一个大分岔。把 OLAP 查询直接压在生产 OLTP 库上，会因为全表扫描拖垮面向用户的低延迟请求；业界通行做法是把数据从 OLTP 库抽取（ETL/CDC）到独立的分析系统（数据仓库、列存），让两类负载物理隔离。这也正是"读写路径"这一大主题的核心思想之一：不同访问模式走不同的数据路径和不同的存储。

行存 vs 列存的存储引擎内部机制属 L4-03/L6-04 深度，本报告只到"按 OLTP/OLAP 访问模式选不同存储"这一装配层结论，不深入列压缩编码等内核。

### 10.1.4 以访问模式反推存储的选型方法

把前面串起来就是一套可操作的选型方法：先枚举系统的主要读查询和写操作，标注每个的频率（QPS 量级）、延迟要求、数据量、查询形态（点/范围/聚合/连接）；再据此判断读写比、判断属 OLTP 还是 OLAP、判断需不需要跨实体连接或多跳关系；最后把这些需求映射到存储特性上——需要强事务和复杂 join 指向关系库，需要按主键高速读写自包含对象指向文档/键值库，需要多跳关系遍历指向图库，需要重聚合分析指向列存/数仓。

存储是为访问模式服务的，不是反过来。一个真实系统常常不是"选一个数据库"，而是按不同访问模式装配多个存储（这叫 polyglot persistence，多语言持久化）——例如主数据放关系库、会话放 Redis、全文搜索放 Elasticsearch、分析放数仓，各司其职。选型的产物往往是一张"访问模式→存储"的映射表，而不是单一答案。

映射的骨架可以写成：

访问模式（读写比·查询形态·数据量·延迟目标）→ 存储特性需求 → 候选存储 → 读写路径装配

## 10.2 关系 vs 文档 vs 图

### 10.2.1 关系模型

关系模型把数据组织成表（关系），每行是一条记录，行之间、表之间的关联靠外键和 join（连接）在查询时动态建立，用 SQL 声明"要什么"而非"怎么取"。它的核心强项是对多对一（many-to-one）和多对多（many-to-many）关系的天然支持：同一份被引用的数据只存一份（范式化），谁需要就 join 过去，改一处即全局生效。

关系模型像一堆规整的电子表格加上"按需拼接"的能力。比如"用户"表和"订单"表分开存，一个用户有多个订单，查"某用户的所有订单"就用 user_id 把两表 join 起来。它的好处是没有数据冗余、一致性好维护、查询极其灵活（任意维度组合都能用 SQL 表达）；代价是高频、深层的 join 在大数据量下开销大，且对象与表之间存在阻抗失配（见 10.2.2）。关系库是 OLTP 的默认选择，成熟、事务强（ACID）、生态完整，"没有明确理由就先选关系库"是稳妥的工程默认。

### 10.2.2 文档模型

文档模型把一个逻辑实体连同它的从属数据存成一个自包含的文档（通常是 JSON/BSON），例如把一个用户的资料、地址列表、偏好设置全嵌套在一个用户文档里。它的两个核心卖点是局部性和阻抗失配的缓解：一次读取就能把整个对象拿全（局部性好，不用 join 多表），且文档结构天然贴近应用代码里的对象/嵌套结构，省去了对象与关系表之间来回翻译的胶水层（object-relational impedance mismatch，阻抗失配）。

一份简历（有多段工作经历、多项技能）作为一个文档整存整取，比拆成 person/job/skill 三张表再 join 更顺手，也更快。文档模型尤其适合一对多（one-to-many）的树状结构、以及"整个对象一起读写"的访问模式。

文档模型不擅长多对多和跨文档 join。若数据高度互联（一个实体被很多其他实体引用），文档模型要么冗余存多份（更新时要改多处、易不一致），要么在应用层手动做 join（把本该数据库做的活搬到代码里）。DDIA 明确指出：关系模型对 join 和多对多的支持更好，文档模型对高度互联数据"awkward（别扭）"。还有一个反直觉点——嵌套过深的文档更新局部字段可能要重写整个文档，且很多文档库对单文档大小有上限。所以"文档模型 = 更现代更好"是误读；它只是对特定访问模式（自包含对象、一对多）更优。

### 10.2.3 图模型

图模型把数据组织成顶点（vertex，实体）和边（edge，关系），关系是一等公民、可带属性。它为高度互联数据、以及需要沿关系做多跳遍历的查询而生，典型如社交网络（朋友的朋友）、推荐（买了 A 的人还买了什么）、知识图谱、欺诈检测中的关联分析、路网寻路。查询语言如 Cypher（Neo4j）、Gremlin、以及 SQL/PGQ 让"沿边走 N 跳"这类遍历表达简洁、执行高效。

问"我的朋友的朋友的朋友里有谁在 A 公司"，在关系库里要 self-join 三次、随深度指数级变重且 SQL 越写越长；在图库里就是"从我出发沿 friend 边走三跳再筛 works_at"，既好写又能用图遍历索引高效执行。DDIA 的结论顺序很清楚：数据越互联，文档模型越别扭、关系模型尚可、图模型最自然；当应用里多对多关系非常多时，就该考虑图模型。

图模型在多跳关系查询上强，但在需要扫描聚合大量数据的分析型负载、或简单的按主键取整对象场景上，并不比关系/文档库有优势，反而更重。它是"关系密集"这一特定访问模式的专用工具，不是通用替代品。此外"图数据库"内部也分属性图（property graph）和三元组/RDF 两大范式，选型时需区分（本报告不深入两者语言差异）。

### 10.2.4 连接代价与局部性——三选一的判据

把三种模型放到同一把尺子上比，关键就两个维度：连接代价和局部性。局部性指"常一起访问的数据在物理上是否也在一起"——文档模型局部性最好（整对象一处存），关系模型靠 join 在查询时拼、局部性差但灵活。连接代价指"建立跨实体关联有多贵"——关系模型把 join 做成数据库内置能力（有优化器和索引支撑），文档模型把 join 推给应用层或靠冗余规避，图模型把多跳遍历做成核心能力。

一个可操作的判据：数据主要是自包含的一对多树、且总整对象读写 → 文档模型（吃局部性红利）；数据有大量多对多、需灵活跨维度查询、要强事务 → 关系模型；数据高度互联、核心查询是沿关系多跳遍历 → 图模型。DDIA 把这条判据讲得很直白，多数工程二手资料（含本次交叉核对的社区解读）与之一致。

现实中绝大多数业务从关系库起步是安全的，因为它最灵活、事务最强、最不容易一开始就把自己锁死在错误的物理模型上；只有当某个访问模式（整对象读写、或多跳关系遍历）被证明是瓶颈、且关系库确实吃力时，才引入文档或图存储来专门服务那个模式。

### 10.2.5 schema-on-write 与 schema-on-read

关系模型是写时模式（schema-on-write）：表结构预先定义，写入必须符合，数据库强制校验；改结构要 migration。文档模型常是读时模式（schema-on-read）：文档不强制统一结构，写入什么都行，结构约束在读取、由应用解释——本质是"弱模式/隐式模式"而非"无模式"。

写时模式像静态类型语言（编译期就卡住不合规数据），读时模式像动态类型语言（运行时才发现结构不符）。读时模式的好处是演进灵活——加个字段不用停机改表、天然容纳异构记录（不同文档字段可不同），适合结构频繁变或本就不规整的数据；代价是数据质量约束和一致性要靠应用自己扛，读代码里到处是"这个字段可能不存在"的防御。易错点：schema-on-read 不等于没有 schema，只是 schema 从数据库转移到了应用代码里，责任没消失只是换了地方。选型时这决定了"结构约束由谁保证"。

### 10.2.6 模型趋同——关系库的 JSON 与文档库的关系能力

一个重要的现实是三种模型正在互相借能力，"关系 vs 文档"的对立在收窄。主流关系库（PostgreSQL 的 jsonb、MySQL 的 JSON 类型）已原生支持存储和索引 JSON 文档，能在一张表里同时享受强事务/join 与文档的灵活嵌套；不少文档库也加入了跨文档 join、事务、二级索引等原本关系库的能力。因此"要文档灵活性就必须放弃关系库"越来越不成立。

选型不必被"关系派 vs NoSQL 派"的口号绑架。很多场景用一个支持 jsonb 的 PostgreSQL 就能同时覆盖结构化主数据（关系表）和半结构化附属数据（JSON 列），既拿到事务和 join，又拿到局部灵活性，省去引入第二种数据库的运维成本。这也是"没有明确理由先选关系库"这条默认建议在今天依然稳妥的原因。此项属能力快速演进区间，具体某版本支持到什么程度需查该库当版文档。

## 10.3 读写分离与物化视图

### 10.3.1 主从读写分离

读写分离指把写请求发往主库（primary/leader）、把读请求分散到多个只读副本（read replica/follower）上，用复制把主库的写同步到副本。它的动机是：绝大多数 OLTP 系统读远多于写（读写比常在 10:1 甚至更高），单机写能力够用但读扛不住，于是通过增加只读副本水平扩展读吞吐。

一个主库负责所有写、保证数据权威，若干副本各自复制一份数据专门伺候读，读流量被摊薄到多台机器。这是复制（大主题6）在读扩展场景的直接应用，装配层只需在应用或代理层做"写走主、读走从"的路由。

关键易错点是复制滞后（replication lag）带来的一致性异常：写到主库后立刻从副本读，可能读到旧值（因为写还没同步过去）。最典型是"读己之写"违背——用户改了资料立刻刷新却看到旧资料。补救手段包括：对"写后立刻读"的请求强制读主库、按会话把该用户短时间内的读钉在主库、或用单调读保证。所以读写分离不是免费扩读——它把系统推入最终一致，应用要显式处理陈旧读。一致性异常的严格定义与协议正确性归 L5-01/大主题6，本处只到"装配时要为复制滞后兜底"。

### 10.3.2 物化视图

普通视图（view）是一段被命名的查询，每次访问时实时执行、不存结果；物化视图（materialized view）则把查询结果预先计算并物理存下来，读时直接取现成结果，不再实时跑那段昂贵查询。它是"用写侧代价换读侧速度"的典型：把复杂 join/聚合的计算从"每次读时做"提前到"写时或定时做一次"。

仪表盘要显示"各地区今日销售总额"，若每次打开都实时扫描订单表聚合，既慢又压库；把它做成物化视图、每隔几分钟刷新一次，打开仪表盘就是一次点查，飞快。适用场景是读频繁、查询昂贵、且能容忍结果有一点点延迟的聚合/报表类访问模式。

物化视图占额外存储、且需要刷新——刷新期间或两次刷新之间，视图数据是陈旧的（存在一致性窗口）。刷新方式分全量重算和增量更新，成本差别大；刷新太频繁抬高写放大、太稀疏则数据太旧。它本质是一份派生数据（derived data），底表才是真相来源，物化视图必须能从底表重建。把物化视图当权威数据源、或忘了它有刷新延迟，是常见错误。

### 10.3.3 物化视图 vs 普通视图 vs 缓存

三者容易混淆但定位不同。普通视图不存数据、每次实时算，只是查询的复用/封装，不改变性能特征。物化视图存了预计算结果、由数据库管理其刷新，是数据库内的持久派生数据。缓存也是存了结果换读速度，但它通常在数据库之外（如 Redis）、由应用管理失效、命中不命中不确定（miss 时要回源）。

要不要占额外存储、由谁负责保持它与源数据一致、访问它是否保证命中——普通视图（不占/实时/必命中源查询）、物化视图（占/数据库刷新/必命中已存结果）、缓存（占/应用失效/可能 miss 回源）。三者都可用于降低读代价，选哪个取决于容忍多陈旧、愿不愿多引一层依赖、以及数据是否适合被数据库自己管理。它们和大主题4的缓存策略是同一思想（预存换读速）在不同层的体现。

### 10.3.4 派生数据、刷新与一致性窗口

读写分离的副本、物化视图、缓存、二级索引、搜索索引，本质上都是同一份真相数据的派生数据（derived data）——它们都能从权威源（主库/底表）重新生成，都通过某种"从源到派生"的更新管道保持（近似）同步，也都因此存在一致性窗口：源已更新、派生还没跟上的那段时间里读派生会读到旧值。这是理解本大主题读写路径的统一视角。

把系统想成"一个权威写入点 + 若干为不同读访问模式服务的派生视图"。写只改权威源，各派生视图按自己的节奏（同步/异步、实时/定时）跟上。设计读写路径的核心决策就变成：每条读走哪个派生视图、那个视图能落后多久（一致性窗口多大可接受）、更新管道用推还是拉、失败了怎么补。

初学者容易把每个派生存储当成独立的"另一个数据库"各自维护，导致多份数据互相打架、无法收敛。正确心智是确立单一真相来源（source of truth），其余全是可重建的派生数据、允许最终一致、并保证有办法从源重放/重建。这一视角直接引出 10.4 的 CQRS 与事件溯源——它们正是把"权威写入 + 多个派生读视图"这套思想推到极致的架构模式。

## 10.4 CQRS 与事件溯源直觉

### 10.4.1 CQRS：读写模型分离

CQRS（Command Query Responsibility Segregation，命令查询职责分离）指用一套模型处理更新（命令，改状态）、用另一套独立的模型处理读取（查询，返回值），两套模型分开设计、分别存储、彼此不共享同一个对象结构。它把 10.3 的"读写分离"从"同一模型分主从"升级为"读和写用根本不同的数据模型"——写侧按业务规则和一致性组织，读侧按查询形态组织（甚至用不同的存储技术），两侧通过某种同步机制（常是异步）连接。

写侧和读侧对同一份业务数据有截然不同的诉求。写侧关心"这笔操作合不合法、状态怎么正确变迁"，适合规范化、强约束的模型；读侧关心"某个页面要展示的数据怎么一次取全、取得快"，适合为具体查询预拼好的反范式视图。CQRS 承认这种矛盾无法用一个模型同时优雅满足，干脆拆开。Fowler 的定义强调两个模型"conceptually not linked（概念上不关联）"，Greg Young 的原始定义把它追溯到"命令改状态、查询返回值"的方法级区分再放大到架构级。

重要边界（这是本项的多来源冲突焦点）：CQRS 不是默认架构，而是有明确适用边界的模式。Fowler 本人在 bliki 中警告：CQRS 增加显著复杂度，只在"单一模型确实同时服务读写变得笨重"的复杂 bounded context 里才值得；对简单 CRUD、低数据量、无特殊读写差异的场景用 CQRS 是过度设计、得不偿失。它常被误当成"高级架构就该上"，实际是把复杂度和最终一致性引入系统，需要充分理由。

### 10.4.2 事件溯源：以事件为真相来源

事件溯源（Event Sourcing）指不把"当前状态"当作权威存储，而是把导致状态变化的每一个事件按发生顺序追加进一个不可变的、只追加（append-only）的事件日志，这个日志才是真相来源（source of truth）；任意时刻的当前状态都是把事件从头重放（replay）折叠出来的结果。对比传统做法——传统是存"账户余额=100"并原地覆盖更新；事件溯源是存"开户""存入 100""取出 30"这一串事件，余额靠重放这些事件算出。

会计账本从不涂改已记的条目，只不断追加新分录，任何时点的余额都由历史分录累加得出。事件溯源的红利也正在此：完整的历史审计（每次变更都留痕、可追溯"为什么变成这样"）、可回到任意历史时点重建状态（时间旅行）、可用同一份事件流生成多种不同的读视图（不同读模型订阅同一事件流各自投影）。它天然和 CQRS 搭档——事件流是写侧真相，读侧的各种查询视图由消费事件流投影（project）而来。

事件 schema 会演进，几年后重放旧事件要处理历史版本兼容（schema evolution）——这是事件溯源最大的长期负担。重放全量事件重建状态可能很慢，需要快照（snapshot）优化。且事件一旦写入不可变，"删除/更正"要靠追加补偿事件而非物理删，与 GDPR 式"被遗忘权"存在张力。事件溯源不是简单的"多存点日志"，它是一套需要认真对待其演进与运维成本的架构承诺。

### 10.4.3 两者关系与"过度神化"辨析

CQRS 和事件溯源是两个独立的模式，常一起出现但不互相依赖：可以只做 CQRS 不做事件溯源（读写分模型，但写侧仍存当前状态）；也可以只做事件溯源不做严格 CQRS。它们搭配好，是因为事件溯源天然提供一个"写侧事件流"，而 CQRS 需要一个机制把写侧变化传播去更新读模型——事件流正好充当这个传播通道。

这两个模式是被过度神化的重灾区，务必点明适用边界（本项多来源均强调这点）。误读一：把 CQRS/事件溯源当成"现代/正确"的默认架构，凡系统都上——实际它们只在复杂领域、有强审计/多读视图/读写模型严重矛盾的场景才回本。误读二：以为它们能"顺便解决"一致性问题——恰恰相反，读写分离 + 异步投影意味着读模型相对写侧是最终一致的，系统必须显式处理"写了之后读模型还没更新"的窗口。误读三：把事件溯源等同于"用了 Kafka/消息队列"——事件流技术选型和"事件日志是不是真相来源"是两码事。event-driven.io、Fowler、Greg Young 三方一致的口径是：这些是强大但成本高、有明确适用边界的模式，不是银弹。

只有当你确实需要完整审计历史、需要从同一份写入派生出多个差异巨大的读视图、或读写模型的诉求确实无法用一个模型同时满足时，才考虑 CQRS/事件溯源；否则一个关系库 + 必要的读副本/物化视图就够了，别为"架构显得高级"付这笔复杂度税。

### 10.4.4 读写路径全景与代价账

把本大主题收束成一张读写路径图：写请求进入写侧（命令），写侧按业务规则改变权威状态（传统 CQRS 存当前状态、事件溯源存事件流）；写侧的变化通过（通常异步的）投影/更新管道，同步到一个或多个为不同查询形态优化的读模型；读请求（查询）直接命中这些预拼好的读模型，快速返回。

写侧（命令）：校验+改权威状态（当前状态 或 append-only 事件日志）
        │  （异步投影 / 更新管道；存在一致性窗口）
        ▼
读侧（查询）：一个或多个按查询优化的读模型（反范式视图 / 物化视图 / 搜索索引）

这张图和 10.3.4 的"权威写入 + 多派生读视图"是同一件事的两种说法，CQRS/事件溯源只是把它显式化、模式化到极致。理解到这一层，本大主题的所有技术就统一了：读写分离、物化视图、CQRS 读模型，都是"把读从写的路径上分离出去、用专门优化的派生视图服务读"，代价统一是写放大 + 最终一致 + 运维复杂度。

最后的代价账要记牢：这套架构买到的是读性能、读写各自独立演进与扩展、审计与多视图能力；付出的是最终一致（读可能读到尚未更新的视图）、更多运维组件（投影管道、事件存储、快照）、更高的认知与调试成本。选型的落点永远是"我的访问模式与业务约束，值不值得付这笔账"——回到 10.1 的第一性原则：让存储与读写路径服务于真实的访问模式，而不是追逐架构时髦。
