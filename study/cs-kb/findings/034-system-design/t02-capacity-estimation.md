# L5-11·大主题2 容量估算方法学（back-of-envelope）

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01 ｜先修：L5-11·大主题1 需求与非功能目标定义（把业务约束翻成可度量目标）｜一手锚点：Google SRE Workbook ch12「Non-Abstract Large System Design (NALSD)」(sre.google/workbook/non-abstract-design)；Jeff Dean「Latency Numbers Every Programmer Should Know」(社区流传表，jboner gist / Colin Scott interactive 版) ｜成熟度：方法学 GA；其中"延迟/带宽基准数"⚙演进快·随硬件世代变

容量估算（capacity estimation，又叫 back-of-envelope estimation，信封背面估算）是系统设计里"动笔画架构前先算一遍数量级"的能力。它不追求精确，只追求**量级正确**：这个系统是每秒几千次请求还是几百万次？要存几个 GB 还是几个 PB？一台机器够不够，还是要一千台？答对量级，就能在方案评审的头五分钟排除掉大部分行不通的设计。本报告分四节：先建立"数量级基准数"直觉，再讲从用户量反推 QPS、从数据推存储与带宽、最后从单机吞吐反推实例数。

## 2.1 数量级基准数（延迟/带宽/字节大小的量级直觉）

### 2.1.1 延迟数量级阶梯（latency numbers）

不同操作的耗时相差许多个数量级，把这条"阶梯"记进肌肉记忆，是一切估算的地基。下面是社区流传最广的一份基准表（源自 Jeff Dean/Peter Norvig，jboner gist 版，约 2012 年硬件世代）：

```
L1 缓存引用 ...................................... 0.5 ns
分支预测失败 ..................................... 5   ns
L2 缓存引用 ...................................... 7   ns
互斥锁 加/解锁 ................................... 25  ns
主存（RAM）引用 ................................. 100 ns
用 Zippy 压缩 1 KB .............................. 3,000 ns    (3 µs)
经 1 Gbps 网络发送 1 KB ......................... 10,000 ns   (10 µs)
从 SSD 随机读 4 KB .............................. 150,000 ns  (150 µs)
从内存顺序读 1 MB ............................... 250,000 ns  (250 µs)
同数据中心内一次往返 ............................ 500,000 ns  (500 µs)
从 SSD 顺序读 1 MB .............................. 1,000,000 ns  (1 ms)
磁盘寻道（HDD seek） ............................ 10,000,000 ns  (10 ms)
从磁盘顺序读 1 MB ............................... 20,000,000 ns  (20 ms)
一个包 加州→荷兰→加州往返 ....................... 150,000,000 ns  (150 ms)
```

要记住的不是这十四个精确数字，而是它们之间的**倍率台阶**：内存比 L1 慢约 200 倍；SSD 随机读比内存慢约 1000 倍；跨大陆网络往返比同机房往返又慢约 300 倍。一个常用的心智技巧是"把纳秒乘十亿当成秒来体感"：这样 L1 引用是 0.5 秒，主存引用是 100 秒（一分半），同机房往返变成约 6 天，跨洲往返变成约 5 年。这套放大让"缓存命中和一次跨洲调用的差距有多离谱"变得可感知，从而在设计时本能地避免热路径上的远程往返。

初学者最容易犯的错误，是把这些数字当成"当前精确值"背下来去做精算。它们只用于**判断量级和相对关系**：一次请求如果要走十次磁盘寻道（10 ms 一次），那它至少 100 ms，这个结论量级上永远成立，而具体是 8 ms 还是 12 ms 一次并不影响设计决策。另一个易错点是混淆"延迟"与"吞吐"——延迟是单次操作等多久，吞吐是单位时间能做多少次，二者不能互相换算（低延迟不等于高吞吐，反之亦然）。

### 2.1.2 数字随硬件世代漂移（⚙演进快·锚年份·随时变）

上表是约 2012 年的世代值，必须硬标"会随硬件演进而变"⚙演进快（核实 2026-08-01）。变化最大的是存储与网络两行：SSD/NVMe 让随机读从 150 µs 一路降到几十微秒级，10/25/100 Gbps 网卡让"发送 1 KB"和大块传输的带宽项显著下降；相对稳定的是 CPU 缓存和主存那几行（L1≈0.5–1 ns、主存≈100 ns 十余年基本没动，因为受物理和光速约束）。

Colin Scott 做了一个可交互版本（colin-scott.github.io，年份滑块 1990–2020），按年份外推每一行的值；例如到 2020 年 SSD 随机读、磁盘容量、网络带宽都比 2012 版有量级改善。多来源在此处存在系统性分歧：jboner 2012 版、Colin Scott 逐年版、以及各博客转载版给出的具体数值互不相同，分歧根源正是**硬件年代不同**——所以引用时务必连年代一起写（"L1≈0.5 ns @2012 世代"），不写年代的单一数字不可承重。设计评审里只依赖不随年代翻转的**相对量级关系**（内存≫SSD≫本地磁盘≫跨洲网络），这部分十年稳定。

### 2.1.3 字节大小基准

估算存储与带宽前，要先有"一条数据大概多少字节"的直觉。常用锚点：1 个 ASCII 字符 = 1 字节；一个 Unicode 字符在 UTF-8 下 1–4 字节；32 位整数 4 字节、64 位整数/时间戳/ID 8 字节；一条短文本消息（如一条推文正文）约 100–300 字节；一张缩略图约几十 KB、一张高清照片约几 MB、一分钟压缩音频约 1 MB、一分钟标清视频约几 MB 到几十 MB（编码相关，属"待核·随编码格式变"）。

容量单位换算是本节的另一半地基：

```
1 KB = 10^3 字节 ≈ 2^10  = 1,024
1 MB = 10^6 字节 ≈ 2^20
1 GB = 10^9 字节 ≈ 2^30
1 TB = 10^12 字节 ≈ 2^40
1 PB = 10^15 字节 ≈ 2^50
```

初学者常在这里栽两个跟头。其一是 bit 与 byte 混淆：网络带宽几乎总用 bit/s 计（1 Gbps = 10^9 比特/秒），而存储用 byte 计，二者差 8 倍，估带宽时漏乘 8 会让结果错一个量级。其二是十进制 KB（10^3）与二进制 KiB（2^10=1024）的差别：在信封估算里两者近似相等、可以互换以简化心算，但真要对账磁盘标称容量与操作系统显示容量时，这约 2.4%（每级累积）的差距就是"1 TB 硬盘为什么只显示 931 GB"的来源。

### 2.1.4 吞吐与带宽基准

除了延迟，还要记几个"通道有多粗"的基准：单块机械硬盘顺序读约 100–200 MB/s、随机 IOPS 约 100（受寻道限制）；单块 SATA SSD 顺序读约 500 MB/s、NVMe SSD 可达数 GB/s，随机 IOPS 上万到几十万；网络单条链路常见 1/10/25/100 Gbps（换成字节即 ÷8：1 Gbps ≈ 125 MB/s）。这些都属⚙演进快·随代际变，用于量级判断而非精算。

这几个数字的用途是"识别瓶颈通道"。举例：要在 1 Gbps（≈125 MB/s）链路上传 100 GB，至少需要

```
100 GB ÷ 125 MB/s = 100,000 MB ÷ 125 MB/s = 800 秒 ≈ 13 分钟
```

不管上层代码多快，这条链路就是下限。易错点是忘了"顺序 vs 随机"的巨大差异：同一块盘顺序吞吐可能是随机吞吐的几十上百倍，设计时把随机小 IO 攒成顺序大 IO（如日志追加、批量写）往往是数量级的优化。

## 2.2 QPS 反推（从 DAU/请求率推峰值 QPS）

### 2.2.1 从用户量到平均请求率

QPS（Queries Per Second，每秒查询数，写侧常叫 TPS/写 QPS）是容量估算的起点数字。最常见的反推链路是从**日活用户数**（DAU，Daily Active Users）出发：

```
平均 QPS = DAU × 人均每日请求次数 ÷ 一天的秒数
一天的秒数 = 86,400 ≈ 10^5（信封估算常直接用 86,400 或近似 10^5）
```

1 亿 DAU、人均每天写 2 条内容，则平均写 QPS ≈

```
100,000,000 × 2 ÷ 86,400 ≈ 2,315 QPS
```

直觉上，"一天约十万秒"是个值得记死的锚点：DAU 除以 10^5 大致就是"如果每人每天来一次、且流量完全均匀"的每秒请求数。1 亿 DAU 均匀摊开约是 1,000 QPS 量级，这个换算能让你在听到用户规模的瞬间就报出 QPS 量级。

易错点是混淆 DAU 与 MAU（月活）与注册用户数：注册用户里可能只有一小部分是日活，日活里又只有一部分在任一时刻在线。反推时要明确用的是哪个口径，并且"人均每日请求次数"这个假设必须显式写出来、可被评审质疑——它往往是整个估算里最不确定、最该标"待核/假设值"的一环。

### 2.2.2 峰均比（peak-to-average ratio）

平均 QPS 会严重低估真实压力，因为流量从不均匀：白天高夜里低、饭点和晚高峰有尖峰。所以要乘一个**峰均比**把平均值放大到峰值：

```
峰值 QPS = 平均 QPS × 峰均比
```

峰均比取多少没有权威定值，属工程经验假设，常见做法是取 2× 到 10×（社交/新闻类日内波动，常用 2–3×；有明确档期/秒杀/直播的场景可达数十倍甚至更高）。这是个必须显式声明并标"待核·业务相关"的系数，不能默认。承接上例：平均写 2,315 QPS，取峰均比 2×，则峰值写 ≈ 4,630 QPS。

初学者容易只算平均值就去定容量，结果一到高峰就过载。反过来，把峰均比取得过大又会长期浪费机器。正确姿势是：用峰值定"必须扛得住的容量下限"，用平均值定"长期成本"，两者都报。更极端的尖峰（如整点秒杀）往往不靠堆机器硬扛，而是用队列削峰（见本课"消息队列"大主题）——识别出"峰均比高到堆机器不划算"本身就是估算的产出。

### 2.2.3 读写比（read/write ratio）

大多数系统读远多于写，读写比（read:write）决定了读、写两条路径各自的 QPS，进而决定架构重心。常见量级：社交 feed、内容站往往 100:1 甚至更高（读极重）；而写重的场景（日志采集、监控指标写入）可能反过来。读写比同样是需显式声明的假设值。

写平均 2,315 QPS，若读写比 100:1，则读平均 ≈ 231,500 QPS，峰值（×2）≈ 463,000 QPS。可见读路径压力比写高两个量级——这直接推出"读侧要加缓存、加只读副本，写侧才是持久化与一致性的重点"这一架构结论。

易错点是把总 QPS 笼统当成一个数去设计。读和写的代价、扩展手段完全不同：读可以靠缓存和复制近乎无限水平扩展，写受一致性和持久化约束扩展难得多。所以估算必须把 QPS 拆成读、写两股分别推。

### 2.2.4 完整反推链路（worked example）

把上面几步串起来是本节的核心技能。下面是一条从 DAU 到峰值读写 QPS 的完整信封演算（本机 Python 数量级演算实证，环境串：基线 Py3.11.15 @2026-08-01）：

```
输入假设：DAU=1亿；人均日写 2 条；读写比 100:1；峰均比 2×
平均写 QPS = 1e8 × 2 ÷ 86,400            ≈ 2,315
平均读 QPS = 2,315 × 100                  ≈ 231,481
峰值写 QPS = 2,315 × 2                     ≈ 4,630
峰值读 QPS = 231,481 × 2                   ≈ 462,963
数量级 sanity: 写峰值在 10^3~10^4、读峰值在 10^5~10^6 ✓
```

上述数字由本机脚本跑出并用 `assert 1e3 <= 写峰值 <= 1e5` 与 `assert 1e5 <= 读峰值 <= 1e6` 做量级自检通过。这一步的价值不在于精确到个位，而在于**用 assert 卡住量级区间**：如果算出来读峰值是 10^8，那多半是某个假设（DAU 或读写比）填错了一个量级，assert 会立刻暴露。信封估算最该防的就是"错一个零"，而数量级自检正是防它的护栏。

初学者要习惯把每个假设（DAU、人均次数、读写比、峰均比）都写成一行明确的输入，而不是揉进心算。这样评审时任何人都能替换其中一个假设重算，估算才有可讨论性；把假设藏起来的"拍脑袋 QPS"是不可复核的。

## 2.3 存储与带宽估算（记录大小×量×保留期→容量）

### 2.3.1 存储容量公式

存储估算的主公式是"单条大小 × 每日条数 × 保留天数"，再乘放大系数：

```
每日新增存储 = 单条记录字节数 × 每日新增条数
总存储 = 每日新增存储 × 保留期天数 × 放大系数
```

承接 2.2 的例子（1 亿 DAU、人均日写 2 条 = 每日 2 亿条）、每条按 300 字节、保留 5 年：

```
每日新增 = 300 字节 × 2亿 = 6 × 10^10 字节 = 60 GB/天
5 年总量 = 60 GB/天 × 365 × 5 ≈ 109 TB（未计放大）
```

60 GB/天意味着大约每 17 天累积 1 TB，五年到百 TB 量级。得到"百 TB"这个量级后，立刻能推出后续决策——单机放不下（一般单机磁盘几 TB 到几十 TB），必须分片（sharding）；冷热数据要分层（近期热数据放 SSD、历史冷数据放廉价对象存储）。这就是估算驱动架构的典型闭环。

### 2.3.2 放大系数（replication / index / overhead）

上面 109 TB 是"裸数据"，真实占用要乘几个放大系数，漏掉任何一个都会低估：复制副本（常见 3 副本 → ×3）、索引（二级索引、倒排索引可能再占原数据的几成到数倍）、元数据与存储引擎开销、以及为压缩节省的负系数（文本常可压到 1/3～1/5）。

```
实际存储 ≈ 裸数据 × 副本数 × (1 + 索引占比) × 引擎开销系数 × 压缩系数
```

例如 109 TB 裸数据、3 副本、索引占 20%、压缩到 1/3，则

```
109 TB × 3 × 1.2 × (1/3) ≈ 131 TB
```

易错点是只算裸数据就报容量。副本这一项影响最大（×3 直接翻三倍），几乎总要算进去；压缩和索引方向相反，能不能相互抵消取决于数据形态。信封估算里这些系数取"量级合理的整数"即可（副本 3、索引 +20%～+100%、压缩 1/3～1/5），关键是**把每一项显式列出来**，让评审看到你没漏算复制。

### 2.3.3 带宽估算（QPS × payload）

带宽（bandwidth）估算是"请求率 × 单次数据量"，读写两侧分开算，并牢记网络用 bit/s：

```
写入带宽 = 写 QPS × 单次写字节数 × 8   (bit/s)
读出带宽 = 读 QPS × 单次响应字节数 × 8 (bit/s)
```

承接例子，读峰值 462,963 QPS、每次响应 300 字节：

```
读峰值带宽 = 462,963 × 300 × 8 ≈ 1.1 × 10^9 bit/s ≈ 1.1 Gbps
```

这告诉你出口带宽要 Gbps 量级，单条 1 Gbps 链路刚好吃满、需要多机分摊或更粗的管道。易错点前面强调过：漏乘 8（bit vs byte）会把结论说小 8 倍。另一个易错点是只算应用层 payload、忽略协议开销（TCP/IP、TLS、HTTP 头），小响应场景下头部开销可能与正文同量级——信封估算通常给 payload 乘 1.2～2 的头部系数，或直接在结论上留出余量。

### 2.3.4 十的幂与二的幂近似心算

信封估算全靠心算，掌握几个近似能大幅提速。核心近似是

```
2^10 = 1,024 ≈ 10^3
```

由此 2^20 ≈ 10^6、2^30 ≈ 10^9，即"每 10 个 2 的幂约等于 3 个 10 的幂"。做乘法时把所有数写成"系数 × 10 的幂"，指数相加、系数相乘，最后归一：例如 2 亿条 × 300 字节 = (2×10^8) × (3×10^2) = 6×10^10。一天 ≈ 10^5 秒、一年 ≈ 3×10^7 秒也是常用锚点。

初学者的最大障碍是心算时数错零的个数——这正是全部估算里最致命的错误（错一个零就是十倍偏差）。对策是全程用科学计数法只操作指数，绝不写一长串零；并在关键结果处做量级 sanity（"这个数应该在 GB 还是 TB？"）。把 2^10≈10^3 这条记牢，就能在内存/磁盘容量（常按 2 的幂标）与业务数量（常按 10 的幂给）之间自由换算而不必掏计算器。

## 2.4 实例数/资源反推（单机吞吐→所需实例数×冗余系数）

### 2.4.1 从单机吞吐到实例数

拿到峰值 QPS 或总数据量后，用"单机能力"去除，得到实例数下限：

```
计算型（QPS 驱动）：实例数 = 峰值 QPS ÷ 单机可承 QPS
存储型（容量驱动）：实例数 = 总存储 ÷ 单机可用容量
```

承接前例，读峰值 462,963 QPS、假设单机可稳定承 8,000 QPS：

```
实例数（裸） = 462,963 ÷ 8,000 ≈ 58 台
```

一个系统往往同时受多种资源约束（CPU、内存、磁盘容量、磁盘 IOPS、网络带宽），要**分别按每种资源算一遍机器数，取最大值**——那个最大值对应的资源就是瓶颈。比如按 QPS 算要 58 台、按存储算要 130 台，则存储是瓶颈、按 130 台起步。SRE Workbook 的 AdWords 示例正是这样：先发现"仅为把数据放进内存就需要约 1,563 台机器"（100 TB ÷ 64 GB/台），从而暴露单机方案不可行、必须重新设计。

### 2.4.2 冗余与余量系数（redundancy / headroom）

上面算出的是"刚好够用"的理论下限，直接照此部署必挂。要乘几个安全系数：容错冗余（N+1 或 N+2：多备 1～2 台以容忍单机故障；跨可用区部署时按 AZ 冗余更多）；利用率余量（绝不能把机器跑到 100%）；以及为增长预留的前瞻系数。

```
部署实例数 = 理论下限 ÷ 目标利用率 + 冗余台数
```

例如理论 58 台、目标利用率 65%、再加 N+2：58 ÷ 0.65 ≈ 90，加 2 ≈ 92 台。为什么不能跑满？因为**排队论**：当资源利用率逼近 100% 时，排队延迟会急剧（非线性）爆炸——利用率从 80% 升到 95%，等待时间可能翻几倍。所以生产系统通常把目标利用率压在 50%～70% 一档，用容量换可预测的低延迟。这条"逼近满载延迟爆炸、必须留余量"是 SRE 的核心直觉之一（详细排队论直觉归 L5-12 过载处理，本章只到"反推时要乘余量系数"）。

一是按理论下限报机器数（没留冗余，单机一挂就雪崩）；二是把余量系数拍得过大导致成本失控。合理做法是把"容错冗余"和"利用率余量"作为两个显式系数分别声明，评审时可分别调整。

### 2.4.3 NALSD 迭代四问

Google SRE Workbook 把容量估算收进一套叫 NALSD（Non-Abstract Large System Design，非抽象大型系统设计）的迭代方法，核心是对每一版设计反复问四个问题：

```
1. 可能吗（Is it possible）？        —— 不计资源约束，方案原理上能work吗
2. 能更好吗（Can we do better）？    —— 更快/更省/更简单的改法
3. 可行吗（Is it feasible）？        —— 在预算与硬件约束内能落地吗（← 容量估算在此发力）
4. 有韧性吗（Is it resilient）？     —— 能否优雅承受组件故障
```

方法的名字点破了它的信条——"non-abstract"（非抽象）：任何设计最终都要跑在真实机房的真实机器和真实网络上，所以必须用具体数字把抽象方案"落地"成机器数、带宽、成本。四问是迭代的：往往第一版"可能"但"不可行"（如前述 1,563 台放内存），于是改设计再算，直到四问全过。这把容量估算从"一次性算数"升格为"驱动设计演进的引擎"。

初学者容易把估算当成设计完成后的"验算"，NALSD 的要点恰相反：估算是**贯穿设计过程的**，每改一版方案就重算一遍资源，用数字淘汰不可行分支。这也是为什么信封估算要快——因为要在一次评审里反复算很多遍。

### 2.4.4 从资源到成本与瓶颈识别

反推的终点常常不只是机器数，而是**成本**与**瓶颈资源**。把机器数乘单机价、带宽乘单位流量价、存储乘单位容量价，就得到量级成本，用于判断方案经济上是否成立（"这个功能一年要烧几百万，值不值"）。同时，2.4.1 里"取各资源所需机器数的最大值"这一步识别出的瓶颈资源，指明了优化方向：若瓶颈是内存，就想办法压缩或分片降内存；若瓶颈是网络，就想办法减少跨机传输。

加机器不一定能解决瓶颈。若瓶颈是单条链路带宽、或是某个无法分片的中心组件（如单主数据库的写），横向加机器无济于事，必须改架构（分片、加缓存、异步化）。所以反推的产物不该止于"要 N 台机器"，而应是"瓶颈在哪、要不要重新设计"。这正好接回 NALSD 的第 2、3 问，形成"估算→发现瓶颈→改设计→再估算"的闭环，也把本大主题与本课其余大主题（负载均衡、缓存、分片、复制、消息队列）串成一条设计主线。
