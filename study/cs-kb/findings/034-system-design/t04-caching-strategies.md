缓存（cache）是把"取一次很贵、但会被反复取"的数据，临时存到一个"取起来很便宜"的地方，从而让后续请求走近路、少打后端。它解决的是两件事：把读延迟从"访问慢速数据源（磁盘、数据库、远端服务）"降到"访问快速副本（内存、就近边缘）"，以及把后端的读负载挡在缓存层之外，让数据库不至于被读流量压垮。本大主题只讲缓存层的工程装配——分几层缓、用什么读写模式、怎么让缓存里的旧数据及时失效、命中率不足时会出哪些病理故障以及怎么防。数据库索引与访问局部性的存储内核机制归 L4-03，本章只到"缓存层怎么装配"为止，不深入索引内部。

缓存能省事的根本前提是"局部性"：数据访问不是均匀随机的，少数热点数据被反复访问（时间局部性），最近访问过的很可能马上又被访问。缓存押的就是这个宝——把热点留在快的地方。若访问完全随机、每条数据只被读一次，缓存就毫无价值（命中率趋近于零，还白搭一层）。全篇请带着这个直觉读。

## 4.1 多层缓存拓扑

### 4.1.1 缓存的分层与命中递进

一次读请求从用户到数据源，中间可以布好几层缓存：客户端本地 → CDN 边缘 → 应用层缓存 → 数据库自身缓存，最后才是磁盘上的数据源。每一层都先看"我这有没有"，命中就直接返回、请求就地掉头，未命中才把请求往下一层传。越靠近用户的层，命中时延迟越低、为后端挡掉的流量越多。

这套逐层下探的过程叫命中递进：请求像剥洋葱一样一层层往里问，任意一层命中就返回，只有全都未命中的请求才会真正打到数据源。

```
用户请求
  → 客户端/浏览器缓存   命中→直接用（0 网络）
  → CDN / 边缘缓存      命中→就近返回（不回源）
  → 应用层缓存(Redis…)  命中→免查库
  → DB 内部缓存(buffer pool) 命中→免读磁盘
  → 磁盘数据源          （全部未命中才到这）
```

对初学者最关键的直觉是"漏斗"：假设每层各自能挡住 90% 的请求，那么到达数据源的流量就是 0.1×0.1×0.1×0.1 = 0.0001，即万分之一。多层缓存的威力是逐层相乘、层层衰减，而不是某一层单打独斗。这也解释了为什么大型系统要多层缓存而非把宝全押在一层：每一层各挡一部分，前面的层还能在后面的层故障时兜底。

一个常见误区是"层越多越好"。每加一层都引入一份可能变旧的数据副本，多层意味着"同一份数据在多个地方各有一个可能过期的拷贝"，一致性问题被放大（更新时要考虑失效哪几层、各层一致性窗口叠加）。所以分层是拿"更低延迟 + 更强抗压"去换"更复杂的失效与一致性"，不是免费的。

### 4.1.2 客户端与浏览器缓存

客户端缓存把数据存在离用户最近的地方——浏览器本地、移动 App 的本地存储、进程内。命中时连网络请求都不用发，是延迟最低、最省后端的一层。对 Web 而言，它主要由 HTTP 缓存语义驱动：服务器用 `Cache-Control`（如 `max-age=3600`）告诉浏览器"这份资源多少秒内可直接用本地副本"，用 `ETag`/`Last-Modified` 支持"条件请求"（浏览器带上 `If-None-Match`，服务器若没变就回 `304 Not Modified`，省掉重传响应体）。

直觉是"自己家的抽屉"：需要的东西上次拿过就放在抽屉里，这次直接开抽屉，根本不用出门。它的独特价值是能省掉整个网络往返，这是其他任何层都做不到的。易错点有两个。其一是失效难：一旦浏览器缓存了一份带长 `max-age` 的旧资源，服务器很难主动通知它更新——这正是前端"改了代码用户却还看到旧版本"的经典坑，业界标准解法是给静态文件名加内容哈希（如 `app.9f3c.js`），内容一变文件名就变，等于换了新 URL 绕过旧缓存（cache busting）。其二是它不受服务端控制、无法保证用户拿到的是最新，所以强一致要求高的数据（余额、库存）不该只靠客户端缓存。

### 4.1.3 CDN 与边缘缓存

CDN（Content Delivery Network，内容分发网络）是分布在全球各地的一批边缘服务器，把内容缓存到离用户地理上更近的节点。用户请求先落到最近的边缘节点，边缘有缓存（cache hit）就直接就近返回、不回源站；没有（cache miss）才回源站取一次、缓存下来再返回，后续同地区用户就能命中边缘。

直觉是"连锁便利店"：与其让所有人都跑到总仓库拿货，不如在每个小区门口开个便利店，把畅销货铺到店里，大多数人就近买到。它主要解决两件事：一是把物理距离带来的网络延迟砍掉（光速有限，跨洲往返几十上百毫秒是硬约束），二是把海量静态流量（图片、视频、JS/CSS）挡在源站之外。传统上 CDN 擅长静态内容，现代 CDN 也能缓存部分动态内容并在边缘跑计算（edge compute）。

命中与否常见于响应头（如 CDN 会返回类似 `HIT`/`MISS` 的缓存状态标识，具体头名各厂商不同）；缓存键默认多以 URL 为主，若资源随查询参数、Cookie、语言而变，需正确配置缓存键，否则会"把 A 用户的个性化内容缓存了返给 B 用户"，这是 CDN 缓存最危险的坑之一（缓存投毒/串号）。更新已缓存内容要靠主动清除（purge/invalidation），但边缘节点众多、清除有传播延迟，所以"改了源站，全球边缘立刻全更新"做不到，仍有一致性窗口（见 4.3）；同样地，带用户隐私的响应必须标为不可共享缓存（`Cache-Control: private`/`no-store`），否则会被边缘错误地缓存并泄露。

### 4.1.4 应用层缓存：本地缓存 vs 分布式缓存

应用层缓存是应用自己维护的一层缓存，用来存"算一次很贵、要反复用"的结果（查询结果、会话、渲染片段）。它分两类。本地缓存（进程内，如一个内存里的 Map、Guava/Caffeine 之类的库）存在应用进程自己的内存里，取起来最快（纳秒级、无网络），但每个实例各存一份、互不相通，且随进程重启就没了。分布式缓存（如 Redis、Memcached）是独立的缓存服务，所有应用实例通过网络共享同一份缓存数据。

本地缓存像"自己桌上的便签"，拿起来最快，但别人看不到你的便签，你换个工位（重启/换实例）便签就丢了；分布式缓存像"全组共用的白板"，谁都能读能写、看到的是同一份，代价是要走到白板前（一次网络往返，通常亚毫秒到几毫秒）。

本地缓存适合"读极热、每实例都需要、允许各实例短暂不一致"的小数据；分布式缓存适合"要跨实例共享、数据较大、需要统一失效"的场景（这也和大主题3的无状态化呼应——会话外置到 Redis 就是把状态从实例本地挪到共享缓存）。易错点：本地缓存在多实例下会出现"各实例缓存不一致"——你在实例 A 更新并清了 A 的本地缓存，实例 B 的本地副本还是旧的，因为没人通知 B。所以本地缓存要么只用于可容忍短暂陈旧的数据 + 短 TTL，要么配一套跨实例的失效广播机制。另外，Redis 与 Memcached 常被拿来对比：Memcached 是纯粹的多线程内存 KV 缓存，Redis 支持丰富数据结构、持久化、复制等，功能更广（选型细节 ⚙演进快，具体能力以各自官方文档当前版本为准）。

### 4.1.5 数据库自身的缓存

数据库自己内部也有缓存层，最典型的是缓冲池（buffer pool，如 InnoDB Buffer Pool、PostgreSQL 的 shared_buffers），它把最近访问的数据页/索引页缓存在内存里，让重复访问的数据免于每次都读磁盘。这是数据库为自身读性能做的、对应用透明的一层缓存，命中递进的最内层。

直觉是"数据库也有自己的抽屉"：即使请求穿透了前面所有应用缓存打到数据库，数据库也未必真去读磁盘——它先看缓冲池里有没有这一页，热数据其实常年待在内存里。这解释了一个初学者常困惑的现象：为什么同一条查询第一次慢、之后就快了很多——第一次把页从磁盘读进缓冲池，之后都命中内存。

过去 MySQL 有一个应用可见的"查询缓存"（query cache，缓存整条 SQL 的结果集），因命中条件苛刻、失效开销大、并发下反成瓶颈，已在 MySQL 8.0 被移除——这提醒"缓存整条查询结果"这类做法在写频繁场景常弊大于利，业界如今更多把这类缓存放到应用层（如 Redis）自己控制。缓冲池的调优、页面替换、预读等存储引擎内核机制归 L4-03，本章只需知道"DB 内部有缓冲池、它是命中递进的最后一层内存缓存"。

## 4.2 读写模式

### 4.2.1 旁路缓存（cache-aside / lazy loading）

旁路缓存是最常用的模式，缓存的读写完全由应用代码控制、缓存本身不直接连数据库。读流程是：应用先查缓存，命中就直接返回；未命中（miss）则应用去数据库读，把结果写回缓存，再返回。写流程通常是：应用更新数据库，然后使缓存里对应的键失效（删除）。因为数据是"用到时才被加载进缓存"，它也叫惰性加载（lazy loading）。

```
读：  app → cache 命中? ── 是 → 返回
                      └ 否 → 读 DB → 写回 cache → 返回
写：  app → 更新 DB → 删除 cache 中该键
```

直觉是"缓存是个便签本，用到才记、由你亲手记和擦"。它的好处是简单、缓存里只存真正被读过的热数据（惰性加载不会预先塞一堆没人读的），且缓存挂了系统仍能直接读库（降级容易）。这是绝大多数"Redis + 关系库"组合的默认玩法。

初学者要吃透两个易错点。其一，为什么写时是"删缓存"而不是"更新缓存"？删除更简单且更安全——直接改缓存要保证"改缓存"和"改库"两步一致，并发下容易把旧值写进缓存；删掉则让下次读自然回源加载最新值，出错空间小。其二，冷启动与缓存击穿风险：因为是"用到才加载"，缓存刚启动或某热点键刚失效时，会有一批请求同时未命中、同时涌向数据库（见 4.4.3）。另外它天然存在一个并发竞态窗口：读线程未命中读到旧库值、还没写回缓存，写线程更新了库并删了缓存，随后读线程把旧值写回缓存——旧值就残留在缓存里，直到下次失效。这类竞态是 cache-aside 一致性讨论的核心（见 4.3）。

### 4.2.2 读穿透（read-through）

读穿透和 cache-aside 的读路径目标一样（未命中就回源加载），区别在于"谁去回源"：cache-aside 是应用代码自己查库、写回缓存；read-through 把这件事交给缓存层（或缓存库/中间件），应用只对缓存发"给我这个键"，未命中时由缓存自己去数据源加载、填充、返回，对应用透明。

直觉是"图书管理员帮你取书"：cache-aside 是你自己发现书架上没有、自己跑去仓库取回来再放上架；read-through 是你只管跟管理员要书，架上没有他自己去仓库取、上架、递给你，你全程不用管仓库在哪。

它的好处是把回源逻辑收敛到缓存层、应用代码更干净、多个应用共用同一套加载逻辑不会各写一遍。代价是需要缓存层支持这种"回源加载器"（通常靠缓存框架/库实现，纯 Redis 需要自己包一层），且缓存层与数据源耦合更紧。易错点：read-through 只是把 cache-aside 的读逻辑换了个执行者，未命中时的"惊群/击穿"问题依然存在（甚至因为对应用透明而更容易被忽视），仍需配合下文的防护。

### 4.2.3 写穿透（write-through）

写穿透是写的时候同步写两处：应用（或缓存层）在写数据库的同时也写缓存，两者都成功才算写成功。它常和 read-through 搭配：写时把最新值同步进缓存，读时缓存总是最新的。

```
写： app → 同步写 cache + 同步写 DB（都成功才算成功）
```

直觉是"记账时账本和便签同时写"：一笔账既记进正式账本（DB），也立刻抄到便签（cache），于是便签永远和账本对得上。它的好处是缓存与数据库的数据始终一致（写完即一致，读永远读到最新），没有 cache-aside 那种"删了缓存下次才加载"的空窗。代价有两个：一是写延迟变高（每次写都要写两处）；二是"写了但没人读"的数据也被塞进缓存，浪费缓存空间（与 lazy loading 的惰性相反，它是"写时即加载"）。

write-through 常被误当成"绝对强一致"。它保证的是"缓存与库的值一致"，但"同步写两处"本身不是一个原子事务——若写完库、写缓存前进程崩了，两者仍会短暂不一致，需要考虑写顺序与失败补偿。此外因为它把所有写的数据都缓存，若写多读少，缓存里会堆满没人读的冷数据，此时常改用 write-around（写只更新库、不写缓存，让数据靠后续读按 cache-aside 惰性加载），避免缓存被写流量污染。

### 4.2.4 写回 / 写behind（write-back / write-behind）

写回是写的时候只先写缓存就立即返回成功，再由缓存异步、批量地把数据刷回数据库。写操作在缓存里就"完成"了，落库是后台稍后的事。

```
写： app → 写 cache 即返回成功
          （后台）cache → 异步/批量刷入 DB
```

直觉是"先记便签，攒一批再誊进账本"：每笔都立刻只写便签（快），过一会儿把便签上的一堆一起誊到账本，还能把"同一个数被改了 10 次"合并成"只写最后一次"（写合并），大幅减少落库次数。它的最大优势是写延迟极低、写吞吐极高，适合写非常密集、能容忍少量数据丢失的场景（如计数器、指标、日志聚合）。

这是四种模式里最危险的一个，易错点必须讲透：数据在被刷回数据库之前只存在于缓存（内存）里，一旦缓存节点在刷回前崩溃，这段未落库的数据就永久丢失——这是拿持久性换性能的明确取舍。所以强一致、不容丢数据的业务（支付、订单）不该用写回。它还会造成"库里的数据滞后于缓存"，任何绕过缓存直接读库的旁路都会读到旧值。CPU 的多级缓存正是用 write-back 策略（脏行延迟写回内存），是这个模式最经典的硬件类比（跨 L1-09 组成原理）。

### 4.2.5 四种模式的取舍总览

cache-aside 与 read-through 处理的是"读怎么填充缓存"，write-through、write-back（以及 write-around）处理的是"写怎么对待缓存"，读写模式常两两组合（如 read-through + write-through、cache-aside + write-around）。选型的核心变量是三条：读写比、对一致性/新鲜度的要求、对丢数据的容忍度。

读多写少、要简单又好降级 → cache-aside（最常见默认）；想让读逻辑集中、应用无感 → read-through；要求读总是最新、写延迟可接受 → write-through；写极密集、能容忍丢一点数据换极致写性能 → write-back；写的数据很少马上被读、怕缓存被写污染 → write-around。

没有"最好"的模式，只有"最匹配当前读写比与一致性要求"的模式；且它们不是互斥的教条，真实系统常按数据种类混用（热点用 cache-aside，指标用 write-back）。还要记住所有引入缓存的模式都用"可能读到旧数据"换"更快、更抗压"，选型时必须先问业务能容忍多旧（这正是 4.3 一致性窗口要量化的东西）。

#### 来源与时效

- 锚点：AWS 白皮书「Database Caching Strategies Using Redis」（docs.aws.amazon.com，核实 2026-08-01）——cache-aside(lazy loading)/write-through 的定义、优缺点与"write-through 缓存冷/热数据"取舍；Redis 官方文档（redis.io/docs，latest）——作为 cache-aside 缓存后端的常用实践。
- 锚点：Hazelcast Docs / Oracle Coherence 等分布式缓存官方文档（read-through / write-through / write-behind 为其内建缓存加载/存储模式的一手命名来源，核实 2026-08-01）——read-through、write-through、write-behind 的"由缓存层负责回源/落库"语义。⚙演进快·锚 latest。
- ⚠二手（仅指路不承重）：多篇缓存模式综述（含 write-around 命名）——用于交叉命名，不作结论承重。
- 冲突项：write-back 与 write-behind 在多数来源视为同义（本文按同义处理并两名并列）；个别来源把 write-behind 特指"带批量/写合并的异步落库"，本文已在正文点明其批量/写合并特征。read-through/write-through 是否"必须由缓存中间件实现"各来源口径略有出入（有的把应用自封装的同步双写也叫 write-through），本文按"由缓存层负责"的经典口径表述并注明与 cache-aside 的执行者差异。

## 4.3 失效与 TTL

### 4.3.1 TTL 与过期（time-to-live / expiration）

TTL（time-to-live，存活时间）是给缓存项设一个"保质期"：写入时设定它能活多久（如 300 秒），到期后这份缓存自动失效，下次访问视为未命中、触发回源加载最新值。它是最基础、最省心的失效手段——不需要在数据变更时主动去通知缓存，靠"到期自动过期"来兜底保证缓存不会无限期地陈旧下去。

直觉是"牛奶的保质期"：不用每天去检查牛奶坏没坏，到期就扔、重新买一瓶新的。TTL 的本质是拿"可接受多旧"换"实现简单"：你愿意容忍数据最多旧 TTL 那么久，就能省掉一整套"数据一变就精确失效缓存"的复杂机制。

过期在实现上分两种执行方式，惰性过期（lazy/passive，访问到某键时才检查是否过期、过期则删）和主动过期（active，后台周期性抽样清理过期键）。Redis 两者都用——它默认不会在 TTL 到点的瞬间就删除键，而是"访问到时删 + 后台定期抽样删"，所以一个已过期但一直没人访问、也没被抽样到的键，可能在内存里多待一会儿（这解释了"设了 TTL 内存却没立刻降下来"的现象）。TTL 选值是核心权衡：太长→数据陈旧、一致性窗口大；太短→命中率下降、回源压力大，且大量键同一时刻集中过期会引发雪崩（见 4.4.4），故常给 TTL 加随机抖动打散过期时刻。

### 4.3.2 主动失效（explicit invalidation）

主动失效是在数据发生变更时，由写入方立即去缓存里删除（或更新）对应的键，让缓存不必等到 TTL 到期就反映最新状态。它和 TTL 是互补的两条路线：TTL 是"被动等它自己过期"，主动失效是"一变就主动踢掉"。生产中常两者并用——主动失效负责及时性、TTL 负责兜底（防止主动失效因消息丢失/漏删而让某个键永远旧下去）。

直觉是"文件一改就撕掉旧的备忘录"：不等备忘录自己过期，改动发生的那一刻就把贴在墙上的旧备忘撕了，逼着下次去看最新的。它把一致性窗口从"一个 TTL"压缩到"从数据变更到失效完成的那一小段"，新鲜度好得多。

易错点是删缓存这一步并不总可靠。写库和删缓存是两个独立操作，任一失败就会残留旧缓存："先更新库再删缓存"若删缓存失败，旧值会一直留到 TTL 兜底；"先删缓存再更新库"则有并发读把旧值重新加载回缓存的竞态窗口（见 4.3.4）。此外分布式下要失效多层/多副本（本地缓存 + Redis + CDN），需要一套失效传播（如发布订阅广播失效消息），任何一层漏收都会残留旧值。所以"主动失效"实践上很难做到 100% 精确，TTL 兜底几乎是必配。

### 4.3.3 一致性窗口（consistency window / staleness）

一致性窗口是指"数据源已经变了，但缓存里还是旧值、会把旧值返给读者"的那段时间。缓存本质上是异步于数据源的副本，只要副本更新不是和数据源变更瞬时同步，就必然存在这样一段可能读到陈旧数据的窗口。它的大小直接由失效策略决定。

对纯 TTL 策略，最坏情况下一份数据可能陈旧接近一整个 TTL——如果它刚被缓存后数据源就变了，那么直到这份缓存过期前，读者一直读到旧值：

```
纯 TTL 下最坏陈旧时间 ≈ TTL
（数据源在该键刚缓存后立即变更 → 直到过期都读旧值）
```

对"主动失效 + TTL 兜底"，正常情况下窗口被压缩到"数据变更 → 失效生效"的很短一段（毫秒到秒级，取决于失效传播延迟）；只有当主动失效失败时，才退化到由 TTL 兜底的最坏情况。

用缓存就等于接受最终一致性（读到的可能不是此刻最新）。所以设计缓存前必须先问业务"能容忍多旧"——商品详情旧几分钟无所谓（TTL 可长），账户余额/库存则几乎不能旧（要么不缓存、要么强主动失效 + 极短 TTL、要么读时旁路直查）。易错点是把缓存当成和数据库一样的强一致数据源来用，在需要读到绝对最新值的地方（如下单前的库存校验）直接读缓存，导致超卖等一致性事故。缓存是"读优化的可陈旧副本"，不是"权威数据源"。

### 4.3.4 双写一致性与竞态（cache-DB consistency）

当数据同时存在于数据库和缓存时，一次数据变更就要动两处（更新库 + 处理缓存），这两步不是原子的，并发下会产生把旧值残留进缓存的竞态。这是缓存工程里最经典、最容易出错的一块。主流做法是 cache-aside 的"更新数据库 + 删除缓存"，且业界普遍推荐"先更新库、再删缓存"，并配 TTL 兜底。

一个典型的竞态（"先删缓存再更新库"路线下）：

```
时刻1  写线程：删除缓存 key
时刻2  读线程：未命中 → 从 DB 读到【旧值】
时刻3  写线程：更新 DB 为【新值】
时刻4  读线程：把【旧值】写回缓存   ← 旧值残留，直到 TTL 到期
```

"先更新库再删缓存"能规避上面这个窗口，但也存在更罕见的竞态（读线程在写线程删缓存之前恰好把旧值写回），业界为此提出"延迟双删"（更新库后删一次缓存，过一小段时间再删一次，用第二次删掉可能被并发读写回的旧值）等补救。这些做法都在缩小竞态窗口，但都不能把它变成绝对强一致——真正要强一致，只能不用缓存或用读时直查权威源。

只要"缓存"和"库"是两份异步的副本、更新它们的动作不能捆成一个原子操作，就永远存在"某种并发时序让旧值留在缓存"的可能，工程手段（删而非改、先库后缓存、延迟双删、加短 TTL 兜底、必要时用变更数据捕获 CDC 订阅库的 binlog 来驱动失效）只是把这个概率和窗口压到业务可接受，而非消灭它。易错点：不要在缓存与库一致性上追求"零窗口"的完美方案而过度设计；先明确业务能容忍的窗口，再选够用的策略即可。

### 4.3.5 淘汰策略（eviction）与 TTL 的区别

淘汰（eviction）是缓存内存满了之后，为了给新数据腾地方而主动踢掉一些已有键；它和过期（expiration）是两回事——过期是"到期了该删"（基于时间），淘汰是"内存不够了必须删谁"（基于空间压力）。缓存容量有限，装不下全部数据，就必须有个策略决定"内存满时牺牲哪些键"，最常见的是 LRU（Least Recently Used，踢掉最久没被访问的）和 LFU（Least Frequently Used，踢掉访问频率最低的）。

以 Redis 为例，行为由 `maxmemory`（内存上限）和 `maxmemory-policy`（淘汰策略）两个配置决定。Redis 的默认 `maxmemory-policy` 是 `noeviction`——即内存达到上限后不淘汰任何键，而是对写命令直接返回错误（读仍可）；默认 `maxmemory` 为 0，表示不限内存（此时永不因容量触发淘汰，但可能吃光机器内存）。可选策略包括 `allkeys-lru`/`allkeys-lfu`/`allkeys-random`（在所有键里淘汰）和 `volatile-lru`/`volatile-lfu`/`volatile-random`/`volatile-ttl`（只在设了 TTL 的键里淘汰）。

TTL 回答"这条数据什么时候不新鲜了"，淘汰回答"地方不够时先扔谁"。一个键可能因为 TTL 到了而过期，也可能因为内存满、按 LRU 被淘汰（哪怕它还没过期）。易错点很要命：若把 Redis 当纯缓存用却保留默认的 `noeviction`，内存一满写入就开始报错、缓存无法接纳新热点——纯缓存场景通常应显式设为 `allkeys-lru` 或 `allkeys-lfu`。另一个易错点是 `volatile-*` 策略只淘汰有 TTL 的键，若一批键没设 TTL，内存满时这些键淘汰不掉，可能同样触发写失败。此外 Redis 的 LRU/LFU 是近似算法（采样若干键挑最差，非全局精确），追求精确淘汰会误解其行为。

#### 来源与时效

- 锚点：Redis 官方文档「Key eviction」（redis.io/docs/latest/develop/reference/eviction/，核实 2026-08-01）——默认 `maxmemory-policy=noeviction`、默认 `maxmemory=0`（不限）、八种策略列表、LRU/LFU 为近似采样算法。⚙演进快·锚 Redis latest（7.x/8.x）·随时变。
- 锚点：Redis 官方文档 EXPIRE / 过期实现说明（redis.io/docs）——惰性（访问时）+ 主动（后台抽样）双重过期，过期键非到点即删。
- 锚点：AWS 白皮书「Database Caching Strategies Using Redis」——TTL 作为缓存一致性兜底、cache-aside 下"更新库 + 失效缓存"的实践与陈旧窗口讨论（docs.aws.amazon.com，核实 2026-08-01）。
- ⚠二手（仅指路不承重）：中文社区广泛讨论的"先删缓存/先更新库、延迟双删、CDC 驱动失效"——用于交叉命名与列举，具体方案有效性以并发时序分析为准，不作数值承重。
- 冲突项：双写一致性没有业界公认唯一最优方案，"先删缓存再更新库" vs "先更新库再删缓存" vs "延迟双删"各有竞态窗口，本文两边都记并给出各自竞态时序，不和稀泥给"标准答案"；淘汰(eviction)与过期(expiration)在口语中常被混用，本文按 Redis 官方口径严格区分。

## 4.4 命中率与病理

### 4.4.1 命中率（hit rate / hit ratio）

命中率是缓存的核心健康指标，指请求在缓存中命中的比例：命中数 ÷ 总请求数。它直接决定缓存到底省了多少事——命中率越高，被挡在缓存层、不用打后端的请求就越多，平均延迟越低。

```
命中率 = 命中数 / (命中数 + 未命中数)
未命中率 = 1 − 命中率
平均读延迟 ≈ 命中率 × 缓存延迟 + 未命中率 × 回源延迟
```

假设缓存命中 1ms、回源 50ms，命中率 95% 时平均延迟 ≈ 0.95×1 + 0.05×50 = 3.45ms；命中率掉到 80% 时 ≈ 0.8×1 + 0.2×50 = 10.8ms。可见命中率每掉几个百分点，因为未命中要付昂贵的回源代价，平均延迟会显著恶化——这就是为什么监控命中率如此重要。

命中率不是越高越一定好，也要看它是怎么来的。为了刷高命中率把 TTL 设得极长，会牺牲新鲜度、加大一致性窗口。命中率低的常见原因包括 TTL 太短、缓存容量太小导致频繁淘汰热点、缓存键设计太细（每个键都独一无二、无复用，比如把用户 ID 拼进本可共享的键）、或访问模式本身就缺乏局部性（此时缓存本就不该用）。另外要区分"冷启动期命中率低"（刚上线缓存是空的，属正常，会随流量升温）和"稳态命中率低"（说明缓存设计有问题）。

### 4.4.2 缓存穿透（cache penetration）

缓存穿透指请求查询一个数据库里根本不存在的数据。因为数据不存在，缓存里永远不会有（每次都未命中），于是每次请求都穿过缓存直接打到数据库。若被恶意利用（大量请求查不存在的 key，如乱造 ID），会让缓存完全失效、数据库被读垮。

缓存只挡得住"存在且被缓存过"的数据；查一个压根不存在的东西，缓存永远说"我没有"，请求就一路捅到底。这类攻击的可怕之处在于每个请求都天然未命中，缓存形同虚设。

两种主流防护。其一，缓存空值：数据库查不到时，也在缓存里为这个 key 写一个"空/不存在"标记（配一个较短 TTL），后续同 key 请求直接被缓存挡回，不再打库；缺点是攻击者用海量不同的不存在 key 会撑爆缓存空间（故空值 TTL 要短）。其二，布隆过滤器（Bloom filter）：用一个极省内存的概率数据结构预先记录"所有存在的 key 集合"，请求先问布隆过滤器"这个 key 可能存在吗"，回答"一定不存在"就直接拒掉、根本不查缓存和库。布隆过滤器有假阳性（可能把不存在误判为可能存在，放行少量穿透）但无假阴性（说不存在就一定不存在），正好卡住恶意的不存在查询。易错点：穿透的关键特征是"数据本就不存在"，这与下面击穿/雪崩（数据存在、只是缓存里暂时没有）本质不同，别把三者混为一谈。

### 4.4.3 缓存击穿（hotkey miss / "dog-piling"）

缓存击穿（中文社区常用词，也叫热点失效）指某个热点 key 恰好在某一刻失效（过期或被淘汰），而此刻大量并发请求都在读它，于是这批请求同时未命中、同时涌向数据库去回源加载同一个 key，瞬间把数据库打出一个尖峰。它对应英文里的 cache stampede / dog-piling / thundering herd（惊群）。

一个超热的 key（如首页配置、爆款商品）平时全靠缓存扛，它一失效的那一瞬间，成千上万个请求发现"缓存没了"，一窝蜂全去查库加载——本该由缓存挡住的洪流，在这个失效瞬间集中砸向数据库。注意它和穿透的区别：击穿的数据是存在的、平时也命中良好，只是"失效瞬间的并发回源"出了问题。

主流防护。其一，互斥锁/单飞（mutex / singleflight）：未命中时只允许第一个请求去回源加载并写回缓存，其余并发请求等待或短暂重试，加载完大家一起命中新缓存——把 N 次并发回源压成 1 次。其二，逻辑过期/后台刷新：热点 key 不设真实过期或设很长 TTL，用一个存在值里的"逻辑过期时间"判断该刷新了，由后台异步续期而非让前台请求承担回源，读永远命中（可能拿到刚过期一瞬的旧值，换来不打库）。易错点：击穿是"单个热点 key + 失效瞬间并发"，防护重点是"回源去重/避免同一 key 被并发重复加载"；这与雪崩（大量 key 同时失效）的防护侧重点不同。

### 4.4.4 缓存雪崩（cache avalanche）

缓存雪崩指大面积缓存在同一时间集体失效（或缓存服务整体宕机），导致海量请求在同一时刻全部未命中、一起打到数据库，数据库瞬间被压垮甚至连锁拖垮整个系统。它和击穿的区别在规模：击穿是"一个热点 key"，雪崩是"一大批 key 同时没了"。

直觉两种成因。一是"集体到期"：如果系统启动时把大量 key 用同一个 TTL 一次性灌进缓存，它们就会在同一时刻集体过期，制造一个未命中洪峰。二是"缓存整体挂了"：Redis 集群宕机，所有请求瞬间全部回源，等于缓存层凭空消失、全部流量直击数据库。

主流防护。其一，TTL 加随机抖动：给每个 key 的 TTL 加一个随机偏移（如基础 300 秒 ± 随机 60 秒），把过期时刻打散，避免集体同时到期——这是防"集体到期型雪崩"最简单有效的手段。其二，缓存高可用：给缓存做主从复制 + 故障转移（如 Redis Sentinel/Cluster），避免单点宕机造成整层消失。其三，配合后端保护：即使雪崩发生，也要靠限流、熔断、降级（见大主题9容错模式）在数据库前挡一道，让部分请求快速失败而不是把库彻底压死、进而级联拖垮全站。易错点：初学者常只想着"怎么让缓存别失效"，但雪崩防护的另一半是"假设缓存真的没了，后端还能不能扛住"——把缓存当作性能优化而非依赖底线，给数据库留出即使缓存全失效也不至于崩的余量与保护，才是稳健设计。

### 4.4.5 三大病理的命名分歧与统一辨析

穿透、击穿、雪崩这三个词是中文技术社区高度约定俗成的划分，但英文文献并没有一一对应的固定术语，跨语言/跨厂商沟通时极易混淆，必须点明。粗略的对应关系是：穿透 ≈ 查询不存在的数据（英文常描述为 querying non-existent keys，无统一专名）；击穿 ≈ cache stampede / dog-piling / thundering herd（单热点失效瞬间并发回源）；雪崩 ≈ 有时也被英文笼统归入 cache stampede 或 mass expiration（大面积同时失效）。

直觉上用一条主线把三者串起来最不容易记混：三者都是"未命中的请求打到了数据库"这一件事的不同触发方式——穿透是"数据本就不存在，压根缓存不了"，击穿是"一个热点数据的缓存瞬间没了、并发回源"，雪崩是"一大批数据的缓存同时没了、洪峰回源"。区别在于"不存在 vs 存在""单个 vs 大量"两个维度。

不要背死名词而忽略机制。面试或跨团队沟通里，同一个词（尤其"击穿"和"雪崩"）不同人理解可能不同，甚至有资料把击穿与雪崩定义互换；稳妥做法是描述机制（是不存在的 key？是单热点并发？还是大批同时失效？）而非只甩术语。英文语境下更要直接说 cache stampede / querying non-existent keys，而不是直译中文词。

#### 来源与时效

- 锚点：Redis 官方文档 develop/reference/eviction 与相关最佳实践（redis.io/docs/latest，核实 2026-08-01）——命中率、淘汰对命中率的影响；缓存作为可失效副本的定位。
- 锚点：AWS 白皮书「Database Caching Strategies Using Redis」及 AWS/云厂商缓存最佳实践文档（docs.aws.amazon.com，核实 2026-08-01）——缓存空值防不存在查询、TTL 抖动防集体过期、缓存高可用等防护实践的一手佐证。
- 锚点：布隆过滤器（Bloom, 1970,「Space/Time Trade-offs in Hash Coding with Allowable Errors」CACM）——无假阴性、有假阳性的概率结构性质，用于穿透防护的原理承重。cache stampede / thundering herd 为英文标准术语（操作系统/缓存文献通用）。
- ⚠二手（仅指路不承重）：中文技术社区对"穿透/击穿/雪崩"的划分与"互斥锁/逻辑过期/延迟双删"等防护方案——用于列举与命名，机制正确性以并发分析与一手为准。
- 冲突项：穿透/击穿/雪崩三词中英与跨资料定义不一致（尤击穿与雪崩偶被互换，英文无一一对应专名），本文已按"不存在/单热点/大面积"机制维度统一辨析，并列出中英命名分歧、点明沟通应描述机制而非仅用术语；命中率是否含冷启动期各来源口径不同，本文区分"冷启动低"与"稳态低"。
