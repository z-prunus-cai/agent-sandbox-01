# L5-11·大主题6 复制 replication

复制（replication）是把同一份数据保存在多台机器（副本，replica）上的技术。它要解决三件事：把数据放到离用户更近的地方以降延迟、在部分机器故障时仍能服务以提高可用性、把只读流量摊到多台副本上以扩展读吞吐。本大主题只讲工程装配层——什么时候选单主、多主还是无主，各自的可用性/读扩展/一致性折衷怎么权衡，以及复制滞后会让应用看到哪些反直觉的异常。复制协议本身的正确性证明（共识、线性一致性的形式化定义与 FLP 等结论）归 L5-01，本章只用这些协议的工程性质、不做证明。DDIA 深入复制协议的内部机制，本章停在"选型 + 折衷"这一层，DDIA 作准一手佐证。

复制难在"数据会变"：如果数据只写一次永不修改，复制就只是把文件拷 N 份那么简单。真正的困难全部来自"写入之后如何让每个副本都跟上这次改动"，本章的三种架构（单主/多主/无主）本质就是"由谁来接受写、改动如何传播到其他副本"这一个问题的三种答案。

## 6.1 单主复制（single-leader / leader-based replication）

### 6.1.1 单主复制的基本模型

单主复制指定一个副本为主（leader，也叫 master/primary），所有写请求必须先发给它；主把每次数据改动记进一个复制日志（replication log），并把日志按顺序发送给其余的从副本（follower，也叫 read replica/secondary），从按同样顺序应用这些改动，从而追上主的状态。客户端的读可以打到主，也可以打到任意从。

对初学者最关键的直觉是"写只有一个入口，读有很多出口"。为什么写要集中到一台？因为如果允许任意副本都能接受写，同一条数据被两台同时改成不同值时就没人能裁决谁对；把写集中到唯一的主，就等于让主来给所有写定一个全局顺序，从而天然避免了写冲突。这也是单主复制最大的优点：应用几乎不用考虑冲突，语义简单。代价是主成了写入的单点——主挂了就写不了（要等故障切换），主的写吞吐也成了整个系统写能力的天花板。绝大多数关系数据库（PostgreSQL、MySQL 的默认主从、SQL Server）和不少分布式存储的默认模式都是单主复制。

### 6.1.2 复制日志的实现方式

主把改动传给从，有四种典型的日志实现。一是基于语句（statement-based）：主把它执行的每条写 SQL 原样发给从重放；二是传输预写日志（WAL shipping / physical replication）：主把存储引擎底层的物理日志（记录哪个磁盘块的哪些字节变了）发给从；三是基于行的逻辑日志（logical / row-based）：主发送"哪一行被插入/更新/删除成了什么值"这种与存储格式无关的逻辑记录；四是基于触发器（trigger-based）：用数据库触发器把改动写进一张表由应用层搬运，灵活但开销大、易出错。

理解它们的差别，抓住"发的东西离物理存储有多近"这条线。基于语句最省带宽，但对不确定性函数会翻车——比如 `NOW()`、`RAND()`、自增序号，主执行时和从重放时可能得到不同结果，导致副本悄悄发散，所以现代 MySQL 默认已改用行级（binlog 的 ROW 格式）。WAL shipping 传的是物理块变更，效率高，但因为它和存储引擎的磁盘格式紧耦合，主从往往必须跑同一个数据库大版本，做不了"主升级到新版、从还在旧版"的滚动升级。行级逻辑日志把物理格式解耦，主从可以跑不同版本甚至把改动喂给外部系统（这正是变更数据捕获 CDC 的基础），代价是日志体积通常更大。易错点：很多人以为"复制日志"就是那条 SQL，其实生产系统主流是物理或行级日志，statement-based 因为不确定性坑太多已非默认。

### 6.1.3 读扩展与读写分离

因为从副本保存着数据的完整拷贝，可以把只读查询打到从上，把写集中在主上，这叫读写分离（read/write splitting）。对读多写少的负载（大多数 Web 应用都是），这能极大扩展读吞吐——想扛更多读，加从副本即可。

直觉是"一个记账员负责写账本，很多复印件供大家查阅"。这是单主复制在实践中最常被用到的价值，甚至超过它的容错价值。但有一个初学者极易踩的坑：从副本上的数据可能比主旧（因为改动是异步传过去的，见 6.4），于是"写完立刻去读却读不到自己刚写的东西"这类异常几乎必然出现（读己之写问题，见 6.4.3）。所以读写分离不是无脑把所有读都甩给从——对"写后马上要读且必须读到最新"的场景（如用户改完资料立即查看），要么把这类读路由回主，要么用后面讲的一致性技巧兜住。另一个易错点是从副本数量不能无限加：每个从都要从主拉日志，从太多时主的复制分发本身会成为负担，超大规模下会改用级联复制（从再带从）来分摊。

### 6.1.4 故障切换 failover

主一旦故障，系统必须把某个从提升为新主、让其余从改从新主拉日志、并把客户端的写重新导向新主，这个过程叫故障切换（failover）。它可以人工触发，也可以自动：自动切换通常靠超时判定主已死（一段时间收不到心跳就认为它挂了），再选一个数据最新的从当新主。

故障切换听起来简单，实则是分布式系统里事故的高发区，初学者要知道它有一串经典陷阱。其一，异步复制下新主可能落后于旧主——旧主还没来得及把最后几条写传给从就挂了，这些写在新主上就丢了；如果这期间那条数据的主键又被别的写用掉，还可能违反外键等约束，酿成数据损坏。其二是脑裂（split brain）：判定主已死其实只是"联系不上"，若旧主并没真死（只是网络抖动），而系统又选了新主，就会同时存在两个都认为自己是主的节点各自接受写，数据彻底冲突；为此系统需要一种"确保只有一个主"的机制（如让旧主检测到有新主就自杀，即 STONITH），而这背后正是共识问题，其正确性归 L5-01。其三是超时阈值的两难：设得太短，一次网络抖动或短暂高负载就会误判触发不必要的切换（切换本身有代价、还可能把过载的系统推入雪崩）；设得太长，故障后不可用的时间就更久。正因这些坑，很多团队宁可选择人工故障切换以求可控。

## 6.2 多主复制与冲突（multi-leader replication）

### 6.2.1 多主复制的模型与适用场景

多主复制允许多个节点都能接受写（每个都是主），各主把自己收到的写复制给其他所有主。它本质是单主复制的扩展：把"唯一写入口"放宽成"多个写入口"，换取写入侧的可用性和低延迟。

单主已经能满足大多数场景，什么时候才需要多主？初学者记住三类典型场景就够。一是多数据中心部署：每个数据中心放一个主，本地写走本地主（延迟低），跨数据中心异步复制；即使数据中心间网络断了，各中心仍能独立接受写。二是离线客户端：手机日历这类应用，每台设备就是一个"主"，离线时也能改，联网后再同步——这本质就是多主。三是协同编辑：多人同时编辑一个文档，每个人的本地副本相当于一个主。它们的共同点是"写方必须能在与其他主失联时独立继续写"。代价极其明确、也是它的最大难点：两个主可能同时改同一条数据成不同值，产生写冲突（见下一项）。DDIA 的建议很直白——多主复制的坑很深，能不用就不用，只在确有上述需求时才用。

### 6.2.2 写冲突的产生

当两个不同的主几乎同时修改同一条记录时，各自都先在本地成功写入，等改动异步复制到对方时才发现两边值不一样，这就是写冲突。它和单主复制的根本区别在于冲突被检测到的时机是异步、事后的——写入当下不会失败，冲突要等复制到达时才暴露，而那时两个主可能都已经把"成功"告诉了各自的用户。

直觉上想象两个人在断网的两台电脑上把同一个标题分别改成了 A 和 B，联网那一刻系统必须决定这条数据到底是 A 还是 B（或别的）。为什么这个问题在单主下不存在？因为单主让所有写排成一条队，第二个写会看到第一个写的结果（要么覆盖、要么基于它），永远不会"两个写都以为自己是基于同一个旧值"。多主打破了这条队，冲突就成了必须正面处理的一等问题。易错点：不要以为"写的时间戳分个先后就行"——不同机器的时钟不可靠、且并发写往往在物理上无法定义谁先谁后，靠墙上时钟裁决会静默丢数据。

### 6.2.3 冲突避免与收敛

处理冲突有两条路：避免和解决。避免是让特定记录的所有写都路由到同一个主（比如按用户 ID 把某用户的写永远导向某个数据中心），从根上不产生冲突——这是最简单可靠的办法，但一旦要切换主（如数据中心故障）就又会冒出冲突。解决则需要一种让所有副本最终收敛到同一个值的规则，常见几种：最后写入胜（LWW，last write wins，给每个写打时间戳/ID、取最大者，实现简单但会静默丢弃"落败"的那次写）；记录合并（把冲突的多个值都保留、拼在一起或交给应用/用户解决）；以及用无冲突数据类型让结构本身保证收敛。

初学者要抓住"收敛"（convergence）这个核心目标：不管改动以什么顺序到达各副本，所有副本最终必须得到同一个结果，否则副本永久发散就等于数据损坏。为此需要能识别"并发"的机制——版本向量（version vectors）能判断两个写是"一个基于另一个"（有先后、可安全覆盖）还是"互不知晓"（真并发、才是冲突），这比单一时间戳可靠得多。更进一步，CRDT（无冲突复制数据类型，Conflict-free Replicated Data Types）把数据设计成"任意顺序合并都得同一结果"的结构（如只增计数器、集合的特定合并规则），从数据类型层面消除冲突解决逻辑，是协同编辑等场景的现代方案（⚙该领域仍在演进，具体库/算法随版本变）。易错点：LWW 简单但"胜出"意味着"另一次写被无声丢弃"，凡是不能接受丢写的业务都不该用 LWW。

### 6.2.4 复制拓扑（replication topology）

多主之间怎么互传改动，有几种拓扑：全联通（all-to-all，每个主把写发给所有其他主）、环形（circular，写沿环一站站传）、星形（star，一个中心节点转发给其余）。

拓扑决定了改动传播的路径与容错性，直觉上"连得越密越不怕断一条线，但也越容易乱序到达"。环形和星形有单点问题：链路上某个节点挂了，改动就传不过去（除非能绕路），且改动要经过多跳、延迟叠加。全联通更健壮（一条链路断了还有别的路），但带来因果乱序的坑：同一条数据的两次相关改动，可能因为走了不同延迟的链路而在某个副本上后发先至（比如"插入一行"还没到，"更新这行"先到了），造成应用逻辑错乱。要正确处理这种因果关系需要版本向量之类的机制，而不能靠时间戳。易错点：初学者容易只关注"用哪种拓扑"，实际上更该警惕的是"全联通下改动的因果顺序无法靠到达顺序保证"这个隐患——这也是为什么多主系统难做对。

## 6.3 无主复制与 quorum（leaderless replication）

### 6.3.1 无主复制的基本模型

无主复制没有主的概念，客户端把写直接发给多个副本（或经一个协调节点转发给多个副本），也从多个副本读。它不依赖某台节点来定序或做故障切换——由客户端"同时问多台、按多数意见办"来达成一致。亚马逊的 Dynamo 论文让这种风格流行，Cassandra、Riak、Voldemort 是代表，因此也叫 Dynamo 风格复制。

直觉是"不设组长，凡事投票、少数服从多数"。它最大的好处是对节点故障极其宽容：单主复制里主挂了要走故障切换（有停写窗口），而无主复制里任何副本挂了都无所谓——写只要写到足够多的副本、读只要从足够多的副本读，就能照常工作，没有"切换"这个动作。代价是把复杂度推给了读写路径：因为没有主来保证顺序，副本之间会不一致，客户端读时可能从不同副本拿到不同版本的值，必须自己处理"哪个是最新"以及"如何让落后的副本追上"（见下两项）。易错点：无主不等于"没有一致性保证"，它是用"读写都碰足够多副本"这个数量条件来换取一致性的，条件不满足就可能读到旧值。

### 6.3.2 读修复与反熵（read repair / anti-entropy）

无主复制里，落后的副本靠两种机制追上。读修复：客户端并行读多个副本时若发现某副本返回的是旧值，就顺手把新值写回那个落后的副本；反熵过程：后台有个进程持续比对各副本的数据差异并补齐，与是否有读请求无关。

直觉是"顺路纠错 + 定期对账"。读修复的巧妙在于"读的时候免费修"——反正已经从多个副本读了、已经知道谁新谁旧，就顺手把落后的补上，不额外发请求。但它有个致命短板：只有被读到的数据才会被修，冷门数据（很少被读）可能长期停在旧值，甚至永远修不到。所以必须配一个不依赖读流量的反熵后台进程来兜底，保证所有数据（包括没人读的）最终都能收敛。易错点：只靠读修复而不做反熵，是无主系统里"某些副本上的冷数据永久陈旧/丢失"这类隐蔽故障的根源。

### 6.3.3 quorum 条件 R + W > N

无主复制用一个数量条件来保证"读能读到最新写"：设总副本数为 N，每次写要成功写入至少 W 个副本才算成功，每次读要从至少 R 个副本读取。只要满足下面这个条件，读取的 R 个副本里就一定至少有一个是"参与过最近一次写"的，从而能读到最新值：

R + W > N

这被称为法定人数（quorum）读写。抽屉原理是它的直觉：N 个副本里有 W 个被最新的写覆盖过，你读 R 个，只要 R + W > N，读的集合和写的集合就必然重叠（至少交出一个），那个重叠的副本就带着最新值——再配合"读多个副本时取版本最新的那个"，就能读到最新写。

N=3、W=2、R=2，则 R+W=4>3，重叠至少 1 个，成立。常见配置是 N 取奇数、W=R=(N+1)/2（多数派）。灵活之处在于可以按负载调 W 和 R：想让写更快更可用就调小 W（但读要相应调大以维持不等式），读多写少就可以让 W 大、R 小。易错点一：R+W>N 只保证"读集合与最近一次成功写的集合相交"，它不保证线性一致性，也不定义并发写的胜负——那些更强的正确性归 L5-01。易错点二：把 W 或 R 设得让 R+W≤N（比如为了低延迟两个都调很小），就等于放弃了这个重叠保证，读到旧值将成为常态而非偶发。

### 6.3.4 quorum 的局限：宽松 quorum 与仍可能读到陈旧值

即使配置满足 R+W>N，也不能想当然认为"读一定最新"。因为存在几种边界情况：并发写没有明确先后，两个写都满足 quorum 却互相不知道对方（并发冲突，仍需版本向量/LWW 收敛）；写只成功了一部分（写了 W 中的几个就失败）时，后续读到的可能是旧值也可能是新值、且不会回滚；采用宽松 quorum（sloppy quorum）时，当本该负责的 W 个"home"节点不够用，写会被临时接收到其他能连上的节点上（暂存移交，hinted handoff，等原节点恢复再转交回去），此时"写到了 W 个节点"里可能没有一个是真正该存这份数据的节点，读的重叠保证就被打破了。

直觉是"投票机制在边界上会漏":宽松 quorum 是为了在很多节点临时不可达时仍能接受写（提升写可用性），代价就是牺牲了 R+W>N 的读最新保证——它是"先把写收下、事后再送到对的地方"。初学者要建立的正确认知是：quorum 是一个概率性/条件性的一致性手段，不是强一致性开关。DDIA 明确指出，即便 R+W>N，在存在并发写、部分失败、宽松 quorum、时钟偏移等情况下，你仍可能读到陈旧值；需要"写后必读到自己写的"这类保证时，要用 6.4 的一致性技巧或回到单主/共识方案。这也是本章与 L5-01 的分账线：要严格的正确性定义与证明，去 L5-01。

## 6.4 同步 vs 异步与复制滞后（synchronous/asynchronous & replication lag）

### 6.4.1 同步、异步与半同步复制

复制可以同步或异步。同步复制指主要等某个（些）从确认收到并写入这次改动后，才向客户端返回写成功；异步复制指主写完自己就立刻返回成功，改动之后才慢慢传给从。半同步（semi-synchronous）是折中：只要求至少一个从同步确认、其余从异步。

这一项的核心是持久性与延迟/可用性的对立，初学者务必吃透。同步的好处是"从上一定有这份数据"，主即使立刻爆炸数据也不丢（那个同步从有）；坏处是写延迟被最慢的那个同步从拖累，且只要那个从卡住或挂掉，主就无法完成写（可用性下降）。异步反过来：写延迟低、主不受从拖累、可用性好，但主返回成功后、改动传到从之前若主崩溃，这些"已告诉用户成功"的写就永久丢失。所以纯全同步几乎没人用（一个从卡住全局停写），实践中常见是半同步（保一个从有备份，兼顾可用）或纯异步（追求性能、接受少量丢写风险）。这里有一个块级折衷对照：

```
同步  ：写延迟高 · 不丢已确认的写 · 从故障会阻塞写（可用性↓）
半同步：≥1 从同步、其余异步（持久性与可用性折中）
异步  ：写延迟低 · 主崩溃可能丢已确认的写 · 从故障不阻塞写（可用性↑）
```

不要把"复制成功"等同于"数据落盘持久"——即便同步复制，若从只是收到内存里还没落盘、或只同步了一个而它也随后挂了，仍可能丢；持久性是概率的叠加，不是布尔开关。

### 6.4.2 复制滞后（replication lag）

复制滞后是从副本落后于主的时间/进度差。异步复制下它总是存在，正常时是毫秒级，但在从繁忙、网络拥塞、主写入激增或从刚重启追赶时可能拉大到秒甚至分钟级。滞后本身不是 bug，但它让"从上的数据是过去某一刻的主"，从而引出一系列反直觉的读异常。

直觉是"复印件永远比原件慢半拍，平时慢一点没事，忙起来能慢很多"。为什么要专门讲它？因为读写分离（6.1.3）几乎必然引入滞后，而滞后导致的异常（下面三项）是初学者做分布式系统最常被现实教育的地方——功能测试时滞后近乎为零、一切正常，上了生产负载滞后变大，"我明明改了怎么没变"的诡异 bug 就冒出来了。这类"最终一致性"（eventual consistency，只保证"停止写入后副本最终会收敛"，但不保证多久）的异常，正是 6.4.3–6.4.5 要逐一命名和解决的。

### 6.4.3 读己之写（read-your-writes / read-after-write consistency）

读己之写保证：一个用户提交了写之后，他自己后续的读一定能看到这次写（但不保证看到别人的写）。缺了它，用户改完资料刷新却看到旧数据，会以为自己没保存成功。

这是复制滞后引发的最直接、最影响体验的异常。为什么会发生？用户的写落在主上，但他随后的读被负载均衡分到了一个还没追上的从，于是读不到刚写的。直觉修法有几种：对"用户自己可能刚改过"的数据（如个人资料）总是读主；或记住用户最后一次写的时间戳，读时只选滞后小于该时间戳的从（保证读到的从已包含那次写）；或客户端记住自己最近写的版本，读时要求副本至少达到这个版本。易错点：读己之写只管"自己的写"，不保证读到别人的最新写；也要注意跨设备场景——用户在手机上写、在电脑上读，就需要跨设备的读己之写，实现更难（不能只靠单设备记时间戳）。

### 6.4.4 单调读（monotonic reads）

单调读保证：如果一个用户先后做多次读，他不会看到"时间倒流"——即读到较新的数据之后，不会在下一次读里又读到更旧的数据。它比强一致弱、比完全不保证强。

这个异常的画面感很强：用户连刷两次页面，第一次读到的从比较新（看到了某条新评论），第二次读被分到一个更落后的从，那条评论又消失了——数据仿佛倒退了。直觉修法是让同一个用户的所有读都落到同一个副本上（比如按用户 ID 哈希选副本），这样他看到的进度只会前进不会后退。易错点：单调读只保证"不倒退"，不保证"读到最新"——同一个从可能一直落后，用户看到的始终是稍旧但单调前进的数据；另外"固定到同一副本"要处理该副本故障时如何重新选副本、又不破坏单调性的问题。

### 6.4.5 一致前缀读（consistent prefix reads）

一致前缀读保证：如果一系列写有因果先后（先问后答），那么任何人读到时也会按这个先后顺序读到，不会先看到"答"再看到"问"。它主要在分区（分片）系统里成为问题，因为不同分区的复制进度各自独立。

A 问"你能看多远？"，B 答"大约 100 公里"。若这两句被存在不同分区、复制进度不同，第三个观察者可能先读到 B 的答"大约 100 公里"、再读到 A 的问，变成答非所问、因果颠倒。为什么单机数据库没这问题？因为单机写有全局顺序；一旦数据被分片到多个独立复制的分区，跨分区就没有天然的全局顺序了。修法需要让有因果关系的写落到能保序的地方，或显式追踪因果依赖（版本/因果序机制，深入正确性归 L5-01）。易错点：这是三种异常里最容易被忽略的，因为它只在"有因果关系的写被分散到不同分区/独立复制流"时才暴露，测试环境往往碰不到。
