## 04-3.1 结构组件：memtable、WAL、SSTable 与不可变分层

### 04-3.1.1 LSM 树的基本思想：把随机写变成顺序写

LSM 树（Log-Structured Merge-Tree）是一种为**写密集**负载设计的存储结构。它的核心手法是：所有写入先在内存里累积成有序批次，再整块顺序写入磁盘形成不可变文件，磁盘上从不做"找到那一页、原地改掉"的随机写。名字里的三个词分别对应三件事——Log（一切先追加进日志）、Structured（数据始终保持有序）、Merge（靠后台归并把小文件合成大文件）。

对初学者，最好的进入点是先看它要解决什么问题。传统 B+树（先修 03-6）更新一个 key 时，要把对应的磁盘页读进来、改掉、再写回原位，这在机械盘上是一次随机 I/O，即使在 SSD 上也会放大到"整页重写"。当写入速率很高（日志、时序、消息、KV 缓存持久化等场景），随机写会成为瓶颈。LSM 的赌注是：把每一次写都变成"往内存里插一条 + 往日志尾部追加一条"，等内存攒够一大批再顺序刷盘。顺序写比随机写快一到两个数量级，代价则推迟到读路径和后台合并去承担——后面几节讲的全是这笔"推迟的账"怎么还。

### 04-3.1.2 memtable：内存中的有序写缓冲

memtable 是 LSM 引擎在内存里维护的**有序**写缓冲区。每一条写入（put/delete）先插入 memtable，使得内存里始终保存着"最近写入的、已排好序的一批数据"。它必须支持高效的有序插入和范围扫描，因此实现上常用跳表（skip list）或平衡树。

跳表之所以是常见选择（例如 RocksDB 的默认 memtable 就是跳表实现），是因为它插入是对数复杂度、天然有序、且相对容易做成并发友好（多个写线程可无锁或低锁并发插入）。这里初学者容易混淆两点：其一，memtable"有序"不是指按插入时间，而是按 key 排序——这样它满了之后可以整块顺序刷成一个已排序的磁盘文件，无需再排序；其二，同一个 key 被反复写时，memtable 里既可能只保留最新值（视实现而定）、也可能靠更上层的多版本/序号区分，但对读来说"内存里这份永远是最新的候选"，所以读一定先查 memtable。

### 04-3.1.3 WAL（预写日志）：崩溃时的持久性保障

memtable 在内存里，一旦进程崩溃或断电就会丢失。为保证已确认的写入不丢（ACID 里的 D，持久性），每条写入在进入 memtable 的同时（通常在其之前）先**顺序追加**到磁盘上的预写日志（Write-Ahead Log，WAL）。崩溃重启后，引擎重放 WAL 就能把丢失的 memtable 重建出来。

这正好呼应先修 03-5/03-11 里的 WAL 思想：先写日志、再改数据。区别在于 LSM 里 WAL 保护的是"还没刷盘的 memtable"，一旦 memtable 成功刷成 SSTable（04-3.1.4），对应那段 WAL 就可以安全丢弃。初学者常问"写两次（WAL + memtable）不是更慢吗"——关键在于 WAL 是**顺序**追加、且 memtable 只是内存操作，二者都很便宜；真正省下的是 B+树那种"每次改都随机写数据页"的开销。另一个常见调优点是 WAL 的刷盘策略：每条写都 `fsync`（最安全、最慢）还是攒一批再 `fsync`（更快、崩溃可能丢最后一小段），这是耐久性和吞吐之间的旋钮，具体默认值随引擎与版本而异（⚙演进快·待核）。

### 04-3.1.4 immutable memtable 与 flush（刷盘）

当 memtable 增长到阈值（例如达到某个字节大小），它会被冻结为**不可变（immutable）memtable**，同时新建一个空的可写 memtable 继续接收写入。冻结的那份随后由后台线程整块写成一个磁盘上的 SSTable，这个动作叫 flush（刷盘）。

设计的巧妙处在于"冻结 + 新建"这一步：它让**刷盘和继续写入互不阻塞**——前台写线程往新 memtable 写，后台线程慢慢把旧的那份落盘。初学者要注意一个边界情况：如果写入太快、刷盘跟不上，immutable memtable 会积压，内存吃紧，此时引擎通常会主动限速甚至短暂阻塞写入（write stall），这是后面 04-3.2.6 会再提到的"写停顿"来源之一。刷出来的 SSTable 进入磁盘分层的最顶层（LevelDB/RocksDB 里称 L0），成为不可变分层结构的第一层。

### 04-3.1.5 SSTable：不可变的有序键值文件

SSTable（Sorted String Table）是 LSM 落到磁盘上的基本文件单位：一个**按 key 排好序、写完即不可修改**的键值文件。"排好序"使得文件内可用二分/索引快速定位，也使得多个 SSTable 之间可以高效归并；"不可变"意味着任何更新都不会回头改它，只会在更新的地方写新数据。

SSTable 这个术语来自 Google 的 Bigtable 论文（2006），后被 LevelDB、RocksDB、Cassandra、HBase 等广泛采用，是理解现代 LSM 实现的关键词。一个 SSTable 文件内部通常不是一整块，而是切成若干**数据块（block）**，再配一个**索引块**记录"每个块的起始 key / 偏移"，外加可选的**过滤块**（Bloom filter，见 04-3.4）——这个内部布局是 04-3.4.4 的主题。初学者需要牢牢记住"不可变"这三个字带来的两个后果：一是并发读极其友好（文件永不变，读时无需加锁、可随意缓存），二是空间不会自动回收（旧值和被删的 key 直到 compaction 才真正消失），后者正是空间放大（04-3.3.4）的根源。

### 04-3.1.6 删除与更新：tombstone 与多版本共存

因为 SSTable 不可变，LSM 无法"就地删掉"或"就地改掉"一个 key。删除的实现方式是写入一条特殊标记——**墓碑（tombstone）**，表示"这个 key 从此逻辑上不存在"；更新则直接写入新值。于是同一个 key 可能在不同层的多个文件里留下多个版本（旧值、更旧值、墓碑……），读取时以"最新的那条"为准。

理解这点是理解整个 LSM 读路径的钥匙：读一个 key 不能读到第一处就停，而要保证读到的是**最新版本**。实现上靠"从新到旧"的顺序扫描——先查 memtable，再查 L0 的新文件，逐层向下，一旦命中该 key 的最新一条（可能是值、也可能是墓碑）即为答案；若命中墓碑，则对客户端返回"不存在"。初学者常见的两个坑：其一，删除一个 key 反而**先增加**了数据量（多写了一条墓碑），空间要等 compaction 才降下来；其二，墓碑本身也必须活到"比它旧的所有该 key 版本都被合并掉"之后才能丢弃，否则被覆盖的旧值会"复活"——这让墓碑的清理比想象中微妙，是 compaction 正确性的一个必守约束。

### 04-3.1.7 原始 LSM 论文的 C0/C1 分层 vs 现代 memtable/SSTable（来源分歧）

需要显式区分"教科书里的 LSM 原型"和"今天工业界的 LSM 实现"，两者术语和结构并不完全一致。O'Neil 等 1996 年的原始论文里，LSM 树是由**多个组件** C0、C1、…、Ck 构成：C0 常驻内存（原文用类 AVL/2-3 树等有序内存结构），C1…Ck 在磁盘（原文用类 B 树的结构），组件间靠一种叫 **rolling merge（滚动归并）** 的持续过程把数据从 C0 逐级推向更大的磁盘组件。原论文里并没有"SSTable""memtable""WAL"这些名字，也没有 LevelDB 式的"每层一堆有序文件"的具体形态。

今天大家说的 LSM（LevelDB/RocksDB 谱系）是原思想的一个**具体工程化**：C0 对应 memtable（+ WAL 补上原论文没强调的崩溃恢复），C1…Ck 对应磁盘上分层堆放的一批批不可变 SSTable，rolling merge 具体化为 compaction。对初学者，结论是：**读原论文时按 C0/C1/rolling merge 理解，读 RocksDB 文档时按 memtable/SSTable/compaction 理解，二者是同一思想的两代表述，不要把某一方的细节当成 LSM 的唯一定义**。这也是本主题多来源比对时最容易踩的分歧点——凡引用"LSM 就是……"的断言，都要先分清它站在哪一代的语境。

## 04-3.2 compaction 策略：leveled vs tiered、触发条件与代价

### 04-3.2.1 为什么需要 compaction

compaction（压实/合并）是 LSM 的后台维护过程：把若干个 SSTable 读进来、按 key 归并排序、丢弃过期版本与墓碑、写出新的 SSTable，再删掉旧的。没有它，LSM 会因为"只追加不清理"而迅速退化——磁盘文件越堆越多、旧版本永不消失。

它同时解决三个问题，初学者可以一次记住：其一，**回收空间**——同一 key 的旧值和已删除 key 的墓碑在合并时被真正丢掉（04-3.3.4 空间放大）；其二，**控制读放大**——文件数越少，读一个 key 要检查的地方越少（04-3.3.3 读放大）；其三，**维持有序性**——把重叠的、零散的小文件合并成 key 范围不重叠的大文件，让读能更快定位。代价是 compaction 本身要读写大量数据，产生额外 I/O（04-3.3.2 写放大），并可能和前台读写抢资源。所以"用什么策略、多激进地 compaction"就是 LSM 调优的核心旋钮——下面两种主流策略正好站在这个权衡的两端。

### 04-3.2.2 leveled compaction（分层合并）

leveled 策略把磁盘组织成一串层级 L1、L2、…、Ln，每层有一个**目标容量**且逐层按固定倍数放大（这个倍数常称 fanout，LevelDB/RocksDB 里典型取 10，即每层约是上一层的 10 倍）。关键约束是：**除 L0 外，同一层内所有 SSTable 的 key 范围互不重叠**，合起来恰好覆盖该层的全部 key 一次。当某层超出目标容量，就从中挑一个（或几个）SSTable，与**下一层里 key 范围重叠的那些**文件归并，产出的新文件放进下一层。

层内不重叠这条约束带来 leveled 的招牌特性：**读一个 key，在 L1 及以下每层至多只需检查一个文件**（因为该层 key 不重叠，二分即可定位到唯一可能含它的文件）——读放大低。空间放大也低：每个 key 在每层最多一份，旧版本很快被逐层合并挤掉，稳态下磁盘约等于逻辑数据大小（常引一个 ~1.1 的经验值，属经验估计非硬保证）。代价是写放大高：一个 key 从上层落到下层，每经过一层就要参与一次"读下层重叠文件 + 重写"的归并，被反复重写多次（04-3.3.2 会给数量级）。LevelDB 用的就是这种策略，RocksDB 也以 leveled 为常用/默认形态之一。

```
leveled 磁盘布局（key 范围示意，"|abc|" 表一个 SSTable 覆盖的 key 区间）

  L0 :  |a..m|  |c..z|  |b..p|      ← 刚从 memtable flush 来，彼此 key 范围可重叠
  L1 :  |a..f| |g..n| |o..z|        ← 层内互不重叠，合起来覆盖全域一次；容量 = T^1 · base
  L2 :  |a..c||d..f||g..i|...|x..z|  ← 层内互不重叠；容量 = T^2 · base（T≈10）
  ...
  Ln :  ................            ← 最大层，存绝大部分数据
```

### 04-3.2.3 tiered（size-tiered / universal）compaction（分级合并）

tiered 策略不追求"层内不重叠"，而是让相似大小的 SSTable**先攒着**，攒够一批（例如 4 个大小相近的文件）就把它们整批归并成一个更大的文件；大文件再和其它大文件攒够一批、合成更大的……如此形成一个个"体量级别（tier）"。它不保证任一层内 key 不重叠，因此同一个 key 可能同时存在于同一体量级别的多个文件里。

和 leveled 正好相反，tiered 的取向是**省写、费读、费空间**：因为合并次数少、每次合并的数据"更值当"，同一个 key 被重写的次数少，写放大低；但读一个 key 可能要检查多个彼此重叠的文件，读放大高；旧版本也会在多个待合并文件里滞留更久，空间放大高（合并瞬间还要额外准备一份等量空间放输出）。Cassandra 的 Size-Tiered Compaction Strategy（STCS）、以及 RocksDB 的 Universal Compaction 都属这一族。初学者可以记一句对照：**leveled 是"勤打扫、屋子干净但一直在拖地"，tiered 是"攒一堆再一次性清、平时省力但屋里堆得满、找东西要翻好几处"**。

### 04-3.2.4 L0 的特殊性与 compaction 触发条件

L0（第 0 层）在 leveled 里是个例外：它直接接收 memtable 刷盘的结果，因此 **L0 内的 SSTable 彼此 key 范围可以重叠**（每个都是某个时间点的全量最近写入）。正因为重叠，读 L0 时要检查其中的每一个文件——这也是为什么 L0 的文件数要被严格限制。

触发 compaction 的常见条件有几类，初学者了解即可：其一，**L0 文件数超阈值**（RocksDB 的 `level0_file_num_compaction_trigger`，常见默认值 4，⚙演进快·随版本，具体值待核）——文件太多读会变慢，于是触发 L0→L1 合并；其二，**某层总大小超过其目标容量**——触发该层向下一层合并；其三，一些引擎还有基于"墓碑过多""文件太旧"等的额外触发。要点是这些都是**后台异步**发生的：前台写入不必等 compaction 完成，除非积压严重到触发写限速（write stall）。

### 04-3.2.5 术语分歧：tiered vs universal、leveled 的不同实现

这是本主题多来源比对最需要显式点破的分歧：**同一类策略在不同系统里名字不同，同一个名字在不同系统里含义也不完全相同**。"分级/攒批合并"这一族，Cassandra 叫 Size-Tiered（STCS），RocksDB 叫 Universal Compaction，学术论文常统称 tiering——读文档时要意识到它们是同一思想。"分层不重叠合并"这一族，LevelDB 就叫 leveled，RocksDB 也叫 Leveled Compaction，Cassandra 叫 Leveled Compaction Strategy（LCS），这一侧命名较统一。

更细的差异还有：RocksDB 的 leveled 并非教科书纯 leveled——它的 L0 是 tiered 式（重叠、攒够再合），L1 及以下才是 leveled，属于**混合**形态；学术界（如 Dostoevsky、Lethe 等 LSM 调优论文）还提出介于两者之间的"lazy leveling""hybrid"等策略。初学者不必记全，但要建立一个判断习惯：**看到"leveled/tiered"先问"是哪个系统、哪个版本的定义"**，不要把某一实现的细节当成通用定义——这正是章节末"冲突两边都记"要落到的地方。

### 04-3.2.6 compaction 的代价与副作用（写放大、突发 I/O、写停顿）

compaction 不是免费的后台魔法，它有三类现实代价。其一是**写放大**：合并要把旧数据读出来再写回去，实际写盘量远大于用户写入量，直接决定 SSD 寿命和 I/O 带宽占用（量化见 04-3.3.2）。其二是**突发 I/O 与资源争抢**：一次大 compaction 会短时间占用大量磁盘读写和 CPU，可能挤压前台查询，导致**尾延迟（p99/p999）抖动**——这是 LSM 在延迟敏感场景最常被诟病的点。其三是**写停顿（write stall）**：当 flush 或 compaction 跟不上写入速度，L0 文件积压或待合并数据过多，引擎会主动给前台写入限速甚至短暂阻塞，以免读性能和空间失控。

对初学者，这解释了一个反直觉现象：LSM 号称"写快"，但在持续高压写入下反而可能出现**周期性卡顿**——平时顺序写很快，一旦后台合并追不上就被限速。调优 LSM 很大程度上就是在调"compaction 的激进程度、并发度、限速阈值"，让后台整理的节奏跟得上前台写入，同时不至于抢光资源。具体的默认并发数、限速阈值随引擎与版本变化很大（⚙演进快·待核）。

## 04-3.3 写/读/空间放大三角与调优权衡

### 04-3.3.1 三种放大的定义

评估一个存储引擎的开销，有三个互相拉扯的指标，合称"放大三角"。它们各自度量"为了服务用户的逻辑操作，系统实际付出了多少倍"：

```
写放大 (Write Amplification, WA) = 实际写入磁盘的字节数 / 用户请求写入的字节数
读放大 (Read Amplification, RA) = 服务一次查询实际读取的字节(或 I/O)数 / 查询逻辑所需的字节数
空间放大 (Space Amplification, SA) = 磁盘上实际占用的空间 / 逻辑数据的真实大小
```

对初学者，关键认知是这三者**不能同时都好**——这是 LSM（乃至所有存储结构）设计权衡的根本。降低一个往往抬高另外一个或两个：合并得越勤，读放大和空间放大越低，但写放大越高；合并得越懒，写放大越低，但读和空间放大越高。后面三节分别拆开每一项，最后一节讲三者怎么围成一个必须取舍的三角。这个"三者不可兼得"的框架在学界被 Athanassoulis 等人（2016）提炼为 **RUM 猜想**（Read / Update / Memory 三者优化不可兼得），是理解本节的高层背景。

### 04-3.3.2 写放大

写放大衡量"用户写 1 字节，磁盘上到底被写了几字节"。在 LSM 里，一个 key 的字节除了写 WAL、写 memtable 刷盘外，还会在每一次 compaction 里被读出重写。leveled 策略下，一个 key 从上层被逐层合并到底层，每经过一层就被重写一次，且每次合并还要连带重写下层重叠部分，因此写放大在数量级上正比于"层数 × 每层扇出"：

```
leveled 写放大 ~ O(T · L)      （T = 相邻层容量倍数/fanout，L = 层数）
tiered  写放大 ~ O(L)          （攒批合并，每 key 被重写次数随体量级别数增长，明显低于 leveled）
```

（上式给的是**数量级直觉**，具体常数因实现、数据分布、key 更新频率而异，精确系数待核，不同论文/文档给的经验值也不同。）

初学者要抓住两点。其一，写放大直接关系到 **SSD 寿命**（闪存有擦写次数上限）和**写吞吐上限**（磁盘带宽被 compaction 吃掉一部分）——这是生产环境选 tiered 换低写放大的主要动机。其二，"LSM 写快"和"LSM 写放大高"并不矛盾：**前台**看到的是顺序写、很快；**后台**的 compaction 才是写放大的来源，它把成本从"前台随机写"挪到了"后台顺序重写"。B+树则相反，写放大主要来自"每次改动都要写整页 + WAL"（04-3.5.1）。

### 04-3.3.3 读放大

读放大衡量"读一个 key，实际要检查/读取多少地方"。LSM 的读必须保证拿到最新版本，所以要按"新→旧"检查：memtable → L0 的每个文件 → L1…Ln 各层。最坏情况下，一次点查（point lookup）可能要触及内存加多层磁盘文件；范围扫描（range scan）更要在所有可能含该范围的文件间做多路归并。

```
点查读放大 ~ 需检查的位置数 ≈ (memtable) + (L0 文件数) + (leveled: 每层 1 个 × 层数)
                                            ↑ tiered 下每个体量级别可能多个重叠文件，更高
```

**读放大是 LSM 相对 B+树的主要弱点**，也是 04-3.4 一整节存在的理由。B+树读一个 key 只需一次自根到叶的遍历（O(树高) 次页访问，且通常缓存命中率高）；LSM 却可能要问好几个文件"你有没有这个 key"。缓解手段正是下一节的 Bloom filter（快速排除"肯定没有"的文件）、block cache（缓存热块）、以及 leveled 的"层内不重叠"（每层只查一个文件）。此外，**未命中查询（key 不存在）**是最吃读放大的——没有 Bloom filter 时它得把每层都问一遍才敢说"不存在"。

### 04-3.3.4 空间放大

空间放大衡量"磁盘实际占用是逻辑数据的几倍"。LSM 因为不可变 + 只追加，磁盘上会同时存在同一 key 的多个旧版本、以及已删除 key 的墓碑，它们要等 compaction 才被清理；compaction 进行时还要临时占一份输出空间。这些都让实际占用大于逻辑数据量。

leveled 的空间放大低（旧版本被勤快地逐层挤掉，稳态常引 ~1.1 的经验值，即约 10% 冗余；此为经验估计，随负载而变、非硬保证）。tiered 的空间放大高（旧版本在待合并文件里滞留更久，最坏情况下合并前可能接近 2 倍甚至更高，且合并瞬间要额外准备等量空间）。初学者容易忽略的一点：**删除操作短期内反而增加空间**（多写了墓碑），空间只有在墓碑及其覆盖的所有旧版本都被合并后才真正下降——这在大量删除的场景（如 TTL 过期）里会造成"删了却不见磁盘变小"的困惑。

### 04-3.3.5 三者的权衡：leveled vs tiered 与 RUM 猜想

把三项放在一起，就得到 LSM 调优的全局图景：**leveled 牺牲写放大，换低读放大 + 低空间放大**；**tiered 牺牲读放大 + 空间放大，换低写放大**。没有一种设置能三项全优——这就是"放大三角"这个名字的由来，也是 RUM 猜想（读、更新、内存三者优化不可兼得，Athanassoulis et al. 2016）在 LSM 语境下的具体体现。

```
                写放大(WA)
                   /\
                  /  \
                 /    \
     leveled →  /      \  ← tiered 在此侧代价大（读/空间）
               /        \
    读放大(RA) ‾‾‾‾‾‾‾‾‾‾ 空间放大(SA)
   （降低任一角，通常抬高其余角；三者不可同时最优）
```

对初学者，实践含义很直接：**写多读少、看重写吞吐和 SSD 寿命** → 偏 tiered；**读多、对延迟和磁盘占用敏感** → 偏 leveled；很多引擎允许按列族/表分别配置，甚至用混合策略（04-3.2.5）在三角内部找折中点。Bloom filter 等读路径优化（04-3.4）则相当于"在不改变 compaction 策略的前提下，单独把读放大这一角往回拉一点"，是三角之外的额外救济。需要强调：这里只讲机制上的取舍，**具体到某负载该怎么选**属 L6-09·09-3 的选型叙事，本报告不展开。

## 04-3.4 读路径加速：Bloom filter、block cache、index/filter block

### 04-3.4.1 读路径全貌：LSM 读为什么需要专门加速

一次 LSM 点查的完整路径是：查 memtable → 查 L0 各文件 → 逐层查 L1…Ln，直到命中该 key 的最新版本（或全部落空判定不存在）。因为 key 可能散落多处、且未命中查询要问遍所有层，读放大天然高于 B+树（04-3.3.3）。本节的三件工具就是专门用来把"要检查几处"和"每处检查多贵"这两笔成本压下来。

初学者可以把它们对应到三个不同的省法：Bloom filter 省的是"**根本不用打开**那些肯定没有该 key 的文件"（减少无谓的磁盘 I/O）；block cache 省的是"**已经读过的块不用再读盘**"（把热数据留在内存）；index block 省的是"打开一个文件后，**不用扫全文件**就能定位到正确的块"（文件内快速寻址）。三者叠加，才让 LSM 的读在实践中可用。

### 04-3.4.2 Bloom filter（布隆过滤器）

Bloom filter 是一种**概率型集合成员判断**结构：给它一个 key，它能极快地回答"这个 key **一定不在**集合里"或"**可能在**集合里"。它有假阳性（说"可能在"其实不在）但**绝无假阴性**（说"一定不在"就绝对不在）。LSM 给每个 SSTable 配一个 Bloom filter，读一个 key 时先问 filter：若答"一定不在"，就**直接跳过这个文件、不读盘**；只有答"可能在"才去真读。

这对 LSM 读放大是决定性的优化，尤其救的是**未命中查询**——没有 filter 时判定"key 不存在"要读遍每层文件，有了 filter 绝大多数文件被瞬间排除。它的工作原理是：一个位数组 + 若干哈希函数，插入 key 时把它哈希到的几个位置一，查询时若这些位置有任一为 0 则"一定不在"，全为 1 则"可能在"。假阳性率由每个 key 分配的位数 m/n 和哈希函数个数 k 决定：

```
假阳性率 FPR ≈ (1 − e^(−k·n/m))^k

其中 n = key 数，m = 位数组总位数，k = 哈希函数个数；
最优 k ≈ (m/n)·ln 2。
每 key 位数 m/n 越大，FPR 越低，但占用内存越多——这又是一个空间/读放大权衡。
```

Bloom filter 只能加速**点查**（判断"某个具体 key 在不在"），对**范围扫描**基本无能为力（范围里的 key 事先不知道，没法逐个问 filter）。RocksDB 里每 key 位数常见配置约 10 bits（对应 FPR 约 1%），但这是可配项且随版本/配置变化（⚙演进快·具体默认待核）。Monkey（SIGMOD 2017）的洞见是：不该给所有层平均分配 filter 内存，越靠底层（数据越多、被查中概率相对低）应分更多位——这属进阶调优，了解即可。

### 04-3.4.3 block cache（块缓存）

block cache 是内存里的一块缓存区，存放最近从 SSTable 读出的**数据块**，使得对热点数据的重复读不必反复访问磁盘。它和先修 03-5 的 buffer pool 是同一思想在 LSM 里的体现，只不过缓存的单位是"SSTable 的不可变块"而非"可变的数据页"。

因为 SSTable 不可变，block cache 有个天然优势：**缓存的块永远不会脏、无需回写、无需处理一致性**——读进来就一直有效，直到被淘汰或所属文件被 compaction 删除。淘汰策略常见 LRU（RocksDB 也提供 Clock 等实现，具体默认待核）。初学者要区分两层缓存：操作系统的页缓存（page cache）也会缓存 SSTable 文件内容，很多引擎的 block cache 是在其之上再加一层"解压后/结构化"的缓存，两者可能并存、也可能配置成绕过 page cache（direct I/O）——这属部署调优。要点是：block cache 命中率直接决定 LSM 读的真实延迟，热数据放得下内存时，读放大在"实际 I/O"层面被大幅抵消。

### 04-3.4.4 index block 与 filter block（SSTable 内部布局）

一个 SSTable 文件内部不是一整块，而是被切成若干**数据块（data block）**，末尾附上**索引块（index block）**和**过滤块（filter block）**，再加一个**footer** 指向这些元数据块的位置。索引块记录"每个数据块的最后一个 key 及其在文件中的偏移"，于是读一个 key 时可以先二分索引块、定位到唯一可能含它的数据块，只读那一个块，而不必扫全文件。过滤块存的就是 04-3.4.2 的 Bloom filter。

```
SSTable 文件内部布局（LevelDB/RocksDB 谱系，示意）

  ┌────────────┬────────────┬─────┬────────────┬─────────────┬──────────────┬────────┐
  │ data block │ data block │ ... │ data block │ filter block│ index block  │ footer │
  │  (KV 有序) │            │     │            │(Bloom filter)│(块→偏移映射) │(指针)  │
  └────────────┴────────────┴─────┴────────────┴─────────────┴──────────────┴────────┘
     读一个 key：footer → 载 index/filter → filter 判"可能在" → index 二分定位块 → 只读该块
```

初学者要建立的心智是"**分层过滤、逐步收窄**"：filter 先把整个文件排除掉（若"一定不在"）；进不了这一步才用 index 把范围收窄到一个块；最后只把那一个块读进内存（还可能命中 block cache）。这样读一个 key 的磁盘代价从"读整个文件"降到"读一个块"甚至"零磁盘 I/O"。RocksDB 还支持把 index/filter 也做成分块（partitioned index/filter）以减少大文件下的内存驻留——属进阶实现，随版本演进（⚙演进快·待核）。

### 04-3.4.5 其它读路径优化（前缀 Bloom、分区过滤、compaction 的间接帮助）

除三件主力外，还有若干常见加速手段，初学者了解名字与用途即可。**前缀 Bloom filter**：为 key 的某个前缀建 filter，让"以某前缀开头的范围扫描"也能借 filter 跳过整个文件（部分弥补 filter 对范围查询的无力）。**分区 index/filter（partitioned）**：把大 SSTable 的索引/过滤元数据切块、按需加载，避免一次把整份元数据钉在内存。**读时合并的短路**：leveled 因层内不重叠，读到某层命中即可停，不必再下探更旧的层。

还有一个容易被忽略的间接效应：**compaction 本身就是最根本的读加速**——它减少文件数、合并重叠、清掉旧版本和墓碑，直接把读放大的"分母"做小。所以读性能不佳时，除了加 filter/cache，另一条路是让 compaction 更激进（代价是写放大上升，又回到 04-3.3 的三角）。这再次印证本主题的主线：**每一处加速都要放回放大三角里看它借走了哪一角**。

## 04-3.5 B+树 vs LSM 权衡（选型叙事只点到）

### 04-3.5.1 B+树的写路径与写放大

B+树（先修 03-6）是**原地更新（update-in-place）**结构：更新一个 key 要找到它所在的叶页、把值改掉、写回**原来的位置**。为保证崩溃一致性，通常还要先写 WAL（有些实现如 InnoDB 还有 doublewrite buffer 再多写一份），所以一次逻辑写至少落两处盘，且改一个 key 往往要重写**整页**（页内其它未改的 key 也被连带写回）。

这带来 B+树的写放大特征：来自"整页重写 + WAL（+ 可能的 doublewrite）"，且更新是**随机**落在磁盘各处的页上。对初学者，核心对比是：B+树把成本花在**前台的随机写**，LSM 把成本花在**后台的顺序重写**（compaction）。在机械盘时代随机写极贵，这是 LSM 兴起的直接动因；在 SSD 上随机写代价下降，但写放大对 SSD 寿命的影响让这笔账依然重要——两种结构各有其甜区。

### 04-3.5.2 LSM 的对照优势与代价

与 B+树并排，LSM 的优势是：写入是顺序追加（高写吞吐）、SSTable 不可变且紧密排列（**压缩率通常更好**，因为整块有序数据利于压缩、且无需为原地更新预留页内空闲空间）、并发读友好（不可变文件无需读锁）。代价是：读放大较高（要查多处，靠 04-3.4 的手段缓解）、空间放大和写放大来自后台 compaction、以及 compaction 引起的**尾延迟抖动与写停顿**（04-3.2.6）。

B+树的对照优势则是：**读路径短而可预测**（一次自根到叶的遍历，延迟稳定）、无后台合并带来的突发 I/O、范围扫描沿叶链顺序读很自然。初学者可把两者的性格总结成一句：**B+树是"写时多花点、读时省心、延迟平稳"；LSM 是"写时极快、读时多绕几处、延迟偶有抖动、但写吞吐和压缩占优"**。二者没有绝对优劣，只有匹配不匹配负载。

### 04-3.5.3 选型维度速览（点到为止，主叙事另处）

把机制差异收敛成几条可对照的维度，供快速定位（**注意：这里只列维度、不下选型结论**）：写吞吐/写放大（LSM 顺序写占优，B+树原地写随机）、读延迟与可预测性（B+树短而稳，LSM 需 filter/cache 且有尾延迟风险）、空间/压缩（LSM 压缩率通常更好，但有临时空间放大与旧版本滞留）、后台开销（LSM 有 compaction 的 CPU/I/O 与写停顿，B+树没有等价后台合并）、以及可调性（LSM 可在放大三角内按负载调 compaction 策略与 filter 内存）。

对初学者，结论只需记住一句：**LSM 偏"写多、可容忍读放大、看重写吞吐与磁盘占用"，B+树偏"读多、要低且稳定的读延迟"**。至于面对一个具体系统的读写比、延迟 SLA、数据规模到底怎么权衡决策——那属本track L6-09·09-3「存储与检索引擎（选型视角）」的完整叙事，本报告在此止步，只把两种结构的机制账摆清，供选型时调用。
