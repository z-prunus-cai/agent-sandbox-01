## 04-11.1 HTAP 架构：行列混合 / 双引擎 / delta store 设计

### 04-11.1.1 HTAP 是什么：一套系统同时扛交易与分析

HTAP（Hybrid Transactional/Analytical Processing，混合事务分析处理）指用一套系统在同一份（或强一致的）数据上同时服务 OLTP 写事务与 OLAP 分析查询，避免"交易库 →（ETL/CDC 抽取）→ 数仓"这条传统两库分离链路。这个术语由 Gartner 于 2014 年提出，Forrester 用的近义词是 translytical（易混，指同一回事）。

传统架构里，交易跑在行存 OLTP 库、分析跑在列存数仓，中间靠一条 ETL（抽取-转换-加载）管道定期把数据从前者搬到后者。这条管道带来两个痛点，正是 HTAP 想消掉的。一是新鲜度滞后：分析看到的是几分钟到几小时前的数据，做不了"实时"决策（欺诈检测、实时大盘、个性化推荐都吃这个亏）。二是运维复杂度与成本：两套系统、两份数据副本、一条易碎的管道要维护。HTAP 的卖点就是"一份新鲜数据、一套系统、交易刚写完分析立刻可见"。要注意 HTAP 不是"把 OLTP 和 OLAP 引擎简单塞进一个进程"就行——真正的难点在于这两种负载对存储与执行的要求几乎相反（下一节），如何在一套系统里同时讨好它们才是全部技术含量所在。

### 04-11.1.2 核心张力：一份数据同时满足两种相反的负载

HTAP 的根本困难在于 OLTP 与 OLAP 对存储布局、并发、新鲜度的要求几乎处处相反，任何 HTAP 设计本质都是在这组张力里选一个折中点。

```
              OLTP（交易）              OLAP（分析）
访问模式      点查/点改，少量行         全表扫描，大量行少量列
理想布局      行存（一行连续、写快）    列存（一列连续、扫描/压缩好）
新鲜度        必须读到自己刚写的        可容忍稍旧（秒级/分钟级）
并发          高并发短事务              少量长查询、吃 CPU/内存
```

三条主要张力初学者要抓住。第一是布局之争：交易要行存（改一整行、写放大小），分析要列存（只读需要的列、压缩率高、向量化友好），同一份数据没法同时是行又是列，于是必须"存两种布局"或"存一种再临时转"。第二是隔离与新鲜度之争：让分析读到最新已提交数据需要同步开销，而放宽到"读稍旧的一致快照"能让分析几乎不打扰交易——survey 把这点概括为快照隔离带来更强一致但更高延迟、放宽一致性可换更快 OLAP。第三是干扰之争：长分析查询会抢走交易需要的 CPU、内存、缓存，做不好会让交易延迟抖动，所以很多设计刻意把两种负载的资源/副本隔开。理解了这三条，后面所有 HTAP 流派其实都是"在这三个旋钮上拧出不同组合"。

### 04-11.1.3 设计分类：单副本 vs 双副本、统一存储 vs 分离存储

HTAP 系统按"数据存几份布局、行列是否共享一份存储"大致分两大流派：单副本（single-copy，一份统一存储服务两种负载）与双副本（dual-copy，行存 + 列存两份，常见"主行存 + 从列存"）。

单副本流派只维护一份数据，冗余最小、天然新鲜（没有副本要追），但一份布局要同时被点写和大扫描访问，必须在存储上做精细优化，且长分析容易干扰交易。双副本流派把行存与列存拆成两份，各自为负载调到最优、互不干扰，代价是要维护两份数据的同步、以及列存副本相对行存有一点延迟（新鲜度打折）。这条"一份还是两份"的分界是理解 HTAP 最有用的一把尺子。

再叠加一个正交维度：统一存储（unified/single storage，行列在同一存储引擎里，如 SAP HANA 一个引擎同时管行列格式）vs 分离存储（separated storage，行存与列存是不同引擎/不同副本，如 TiDB 的 TiKV + TiFlash）。同一系统可以是"双副本 + 分离存储"（TiDB），也可以是"单引擎里维护主 + delta"（HANA 更接近统一存储 + delta 结构）。要提醒初学者：不同来源对这些标签的切法略有出入（survey 把 HyPer、MemSQL/SingleStore 归为"主行 + 次列"的 dual-copy，把 HANA 归为统一存储自适应），记住"看它到底存几份、行列共不共享引擎"这两个问题，比死记分类名更靠谱。

### 04-11.1.4 delta store + main store：写优化区 + 读优化区的合流设计

delta store（增量存储）+ main store（主存储）是列存系 HTAP 的经典单副本设计：新写入先落进小而写优化的 delta 区（常为行式或轻压缩），主区是大而读优化的列存（重压缩、排序字典），后台周期性把 delta 合并进 main（delta merge），查询时同时读 main + delta 取得完整结果。

```
写入 ─▶ [delta store]  行式/轻压缩，写快，体量小
                │  delta merge（阈值/定时触发，后台）
                ▼
        [main store]   列式/重压缩，读快，体量大
查询 ─▶ 同时扫 main + delta，合并出完整、最新的结果
```

这个设计其实是 LSM 思想在"行列混合"上的翻版：直接往重压缩、排序好的列存里插一行代价极高（要解压、挪位、重建字典），于是先把新数据缓冲在便宜可写的 delta 里，攒够了再批量合并——用"合并的批量代价"换"单次写的低代价"，和 04-3 的 memtable→SSTable compaction 是同一招。SAP HANA 是典型：它把列存分三层，L1-delta 行式（写最快）、L2-delta 列式但字典未排序、Main 列式且字典排序压缩最狠，数据随合并从 L1 逐级流向 Main。易错点有两个：一是别忘了查询必须同时读 delta 和 main 才能看到最新数据，delta 越大分析越慢，所以 merge 频率是个要调的旋钮；二是 delta merge 是资源密集的后台活，触发阈值（delta 大小/变更数/时间，具体默认值随版本变，待核）没调好会和前台负载抢资源。

### 04-11.1.5 双引擎 + 复制：以 TiDB 的 TiKV + TiFlash 为例

双引擎流派把行存引擎与列存引擎做成两套，靠日志复制保持两边数据一致——TiDB 是有代表性的一手案例：行存 TiKV（基于 RocksDB/LSM）扛 OLTP，列存 TiFlash 扛 OLAP，靠扩展 Raft 的"Learner（学习者）"角色把行存的 Raft 日志异步复制给列存副本，由列存侧把行格式转成列格式落地。

```
        写事务
          │
     ┌────▼─────┐  Raft 日志（同步，多数派提交）
     │  TiKV    │  行存，OLTP，Leader/Follower
     │ (row/LSM)│
     └────┬─────┘
          │ Raft Learner：异步收日志（不投票、不选主）
     ┌────▼─────┐
     │ TiFlash  │  收到日志后 行→列 转换后落列存
     │ (column) │  OLAP 扫描走这里
     └──────────┘
```

这里的关键巧思是 Learner 角色：普通 Raft 副本要参与投票和选主，会拖慢主链路；Learner 只异步接收日志、不投票不选主，所以给行存加一个列存副本几乎不增加交易开销。TiDB 论文强调这样做既能让分析读到"实时且一致"的数据（列存副本追上日志后与行存一致，查询可从任一侧读到一致快照），又把两种负载的资源隔在不同副本上、互不干扰——正好对上 04-11.1.2 的"干扰之争"。要注意 TiFlash 落列存用的是类 Parquet 的行组 + 列块结构、并用 B+ 树式结构（DeltaTree）合并 Raft 更新（而非 LSM）——这是它区别于 TiKV 的实现选择。双引擎的代价是列存副本有复制延迟（虽小），以及要多存一份列格式数据。SingleStore 走的是另一条更偏单存储的路（universal storage / 通用存储，把行存与列存能力统一到一套可寻列存段上，见下节），说明"双引擎复制"只是双副本流派里的一种落法，不是唯一解。

### 04-11.1.6 快照 / 写时复制：以 HyPer 的 fork 为例

还有一种更轻的 HTAP 思路：不额外维护列存副本，而是让 OLAP 在 OLTP 数据的一份一致快照上跑，用操作系统的写时复制（copy-on-write, CoW）几乎零成本地"冻结"一份快照——HyPer（慕尼黑工大研究原型，ICDE 2011）是奠基案例。

HyPer 把数据全放内存，OLTP 事务在主进程里串行/短事务地跑；要跑 OLAP 时，它 `fork()` 出一个子进程，子进程继承父进程的内存页映射，此后父进程（OLTP）继续改数据时，被改的页由 OS 触发写时复制复制一份新页，子进程手里仍是 fork 那一刻的旧页——于是子进程看到的是一个一致、不变、不打扰 OLTP 的内存快照，在其上跑分析。妙处在于快照几乎免费：没有物理拷贝整份数据，只有被写到的页才真正复制，且隔离靠硬件页表 + OS 缺页机制天然做到。初学者易误解成"复制了整个数据库"——恰恰相反，未被 OLTP 改动的页父子共享，改动越少快照越省。局限也在此：它假设数据能放进内存、且依赖 fork/CoW 这套内存机制，长 OLAP 期间若 OLTP 写得多，被复制的页会增多、内存压力上升。这条路证明了 HTAP 未必要"两份布局"，用一致快照 + 隔离也能达成。

### 04-11.1.7 代表系统坐标（细目随版本演进，逐点标核实日期）

把主流 HTAP/兼具能力的系统按"存几份、行列关系、耦合方式"摆个粗坐标，方便初学者建立地图；⚙演进快·锚版本·随时变，以下均按 2026-08-01 公开资料，具体版本能力请以官方文档为准，标注处存疑即"待核"。

SAP HANA：内存列存为主，单引擎同时管行列 + delta merge，偏统一存储的 HTAP 老牌代表。TiDB：TiKV 行存 + TiFlash 列存双引擎，Raft Learner 异步复制，偏分离存储双副本。SingleStore（原 MemSQL）：universal storage / 通用存储，行存 + 列存能力向一套可寻（seekable）列存收敛，官方主打 HTAP/OLTP+分析。HyPer / Umbra（学术谱系，部分并入 Tableau/Salesforce 技术栈，细目待核）：内存 + 快照 CoW。Oracle Database In-Memory：在行存主库旁维护一份内存列存（dual-format，双格式），事务改行存、分析走内存列存，是"主行 + 次列"的商用代表。SQL Server：靠列存索引（columnstore index）+ 内存 OLTP（Hekaton）在一套引擎里兼顾两侧。云上还有一批把 OLTP 主库与列存/湖分析耦合的新品（如 Postgres 生态的分析加速产品线），命名与能力变动频繁，逐个以官方文档核实，不在此下定论（待核）。要给初学者的提醒：这些系统在各自市场话术里都自称"HTAP/实时分析"，但落到 04-11.1.3 的"存几份、耦合多紧、新鲜度多高"三问上差异很大，看架构而非看标语。

### 04-11.1.8 "HTAP 已死 / LTAP"之争：一个正在发生的命名之辩

⚙演进快·随时变（截至 2026-08-01）：近一两年业界对"HTAP 是不是一个真类别"有明显争论。一方（含湖仓阵营）提出把交易直接跑在湖仓开放列存之上的新说法（如"LTAP"，Lake Transactional/Analytical Processing 之类），另一方（含 CMU 的 Andy Pavlo、SingleStore 的技术负责人等）指出"物理规律没变"，认为这更多是把列表示下推到共享对象存储、每种负载各配一个引擎，究竟算新范式还是"工程做得好的 HTAP"，本质是命名之争。

不必站队，但要读懂争论背后的真问题。经典 HTAP 把行表示与列表示放进同一个引擎；而近年的湖仓/存算分离思路是把列表示下推进共享对象存储、行/列各配独立引擎，变化的是"这份列副本归谁所有、两种负载隔离到什么程度、分析格式是否开放（Parquet/Iceberg 这类）"。所以这波争论其实是 04-11.1.3 那把"单副本/双副本、统一/分离存储"尺子在云原生存算分离时代的再一次摆位——底层张力（布局/新鲜度/干扰）一个都没消失，只是折中点挪了位置。凡此类术语与产品动向变化极快，本报告只记录"争论存在、分歧点在哪"，不下"谁对"的结论。

## 04-11.2 内存数据库与 NVM / 持久内存引擎

### 04-11.2.1 内存数据库：把内存当主存储改变了什么

内存数据库（in-memory database, IMDB / main-memory DBMS）指把工作数据集常驻内存、以内存为主存储（而非把磁盘当主存储、内存只做缓存）的引擎。这个前提一变，传统"为磁盘慢而生"的一整套机制就被重构。

要让初学者体会差别，看几处被"取消"的老设计。传统磁盘库的核心是缓冲池（buffer pool）：数据以页为单位在磁盘与内存间换进换出，每次访问一行要先定位页、可能触发磁盘 I/O、经过缓冲管理器的间接层。内存库里数据本来就全在内存，于是缓冲池、页级 I/O、以及"访问前先 pin 住页"这套间接层可以整个去掉，数据结构直接用内存指针相连，访问就是解引用。瓶颈也随之转移：磁盘库的瓶颈是磁盘 I/O，内存库的瓶颈变成 CPU 缓存未命中、指令数、锁竞争——所以内存库特别讲究缓存友好布局、无锁/乐观并发、减少解释开销（这也是它和 04-4 向量化、04-5 编译天然亲和的原因）。一个常见误解是"内存库就是把数据 load 进内存的普通数据库"——不是，真正的内存库是围绕"内存是主存储"重写并发、恢复、索引的，只是"加大 buffer pool"达不到同等效果。持久性仍要靠日志/快照落到持久介质（内存断电即失），这点没变，见后文 NVM 正是想改这一点。

### 04-11.2.2 代表内存引擎：串行分区、无锁 MVCC、快照三条路

内存库在并发/恢复上分化出几条有代表性的路线，各自解决"内存里怎么高效又正确地并发"这个问题。

H-Store / VoltDB（Stonebraker 谱系）：把数据按分区切开，每个分区单线程串行执行事务——既然内存里事务极快，干脆不用锁，用"一个分区一个线程排队跑"消除并发控制开销，代价是跨分区事务变贵。Microsoft Hekaton（SQL Server 内存 OLTP 引擎）：走无锁 + 乐观 MVCC，用为内存优化的索引（如 Bw-tree）和多版本避免加锁阻塞，深度集成进 SQL Server。HyPer：内存 + 前述 fork/CoW 快照兼顾 OLTP/OLAP。此外 Redis 等把内存 KV 做到极致（虽常被当缓存，但也是内存数据管理的一支）。给初学者的归纳：这些系统的共同点是"承认内存快，于是把并发控制/恢复的开销当成新的头号敌人来砍"，砍的手法不同（串行 vs 无锁 MVCC vs 快照），但目标一致。这也解释了为什么内存库常和 HTAP 绑在一起讲——数据全在内存、又想少干扰，天然适合上快照/多版本这类 HTAP 手法。

### 04-11.2.3 NVM / 持久内存：介于 DRAM 与 SSD 之间的一层

NVM（Non-Volatile Memory，非易失内存）/ 持久内存（Persistent Memory, PMem）指一类同时具备"字节可寻址、接近 DRAM 的低延迟"与"断电不丢（持久）"的存储介质，性能与价格介于 DRAM 和 SSD/闪存之间，最有名的实现是 Intel/Micron 的 3D XPoint（Intel 品牌名 Optane）。

```
        快、贵、易失                              慢、便宜、持久
  CPU 缓存 ── DRAM ──[ NVM / 持久内存 ]── SSD/闪存 ── 磁盘
                        字节可寻址 + 持久
                     （填补 DRAM 与 SSD 之间的空档）
```

传统上"快的（DRAM）会丢、不丢的（磁盘）很慢"，数据库为此发明了 WAL、检查点、缓冲池等一大堆机制来在两者间搭桥。NVM 承诺"又快又不丢、还能像内存一样按字节读写"，理论上可以简化甚至取消这些机制——比如日志可以直接写进 NVM、恢复几乎瞬时、内存里的数据结构本身就是持久的。要提醒初学者：NVM 不等于"更快的 SSD"也不等于"不丢的 DRAM"，它有自己的脾气——写比读慢、有耐久度限制、且"持久"这件事在 CPU 缓存层面并不自动（数据可能还卡在 CPU 缓存里没落到持久域，见下节），这正是编程它的难点所在。

### 04-11.2.4 编程 NVM 的难点：持久域、刷缓存与故障原子性

在 NVM 上写正确的持久数据结构比想象中难，核心难点是：CPU 写出的数据默认停在易失的 CPU 缓存里，只有显式刷到"持久域"才算真落，且崩溃可能发生在任意一步，必须保证故障原子性（要么改动完整可见、要么当没发生）。

程序员需要显式控制持久顺序：用 `CLWB`/`CLFLUSHOPT`（回写/刷出缓存行）把缓存行推向持久域，再用 `SFENCE`（存储屏障）保证顺序，才能确保"我以为写下去了"的数据在断电后真的还在。故障原子性要额外机制保障：现代 CPU 通常只保证 8 字节对齐写是原子的，更大的结构更新要靠 redo/undo 日志、影子拷贝等软件手段做成"全有或全无"，否则崩在半路会留下坏了一半的结构。Intel 为此提供了 PMDK（Persistent Memory Development Kit，pmem.io）这套库封装上述细节。给初学者的直觉：NVM 编程的头号陷阱是"看起来写了、其实还在缓存里没持久"，以及"改到一半崩了"——这两点让人们意识到，NVM 的好处不是白拿的，要重构数据结构和恢复逻辑才能兑现。

### 04-11.2.5 NVM 数据库引擎设计：单级存储、反缓存、写后日志

围绕 NVM 特性，数据库研究提出了几种引擎设计取向，帮初学者建立"NVM 能改变哪些老设计"的直觉。单级存储（single-level store）：既然 NVM 又快又持久，就取消"内存工作副本 + 磁盘持久副本"的双层结构，数据结构直接建在 NVM 上、原地持久，省掉序列化/反序列化与刷盘。反缓存（anti-caching）思路的变体：把冷数据放 NVM、热数据放 DRAM，做冷热分层。写后日志（write-behind logging, WBL）：传统 WAL 是"先写日志再改数据"，在 NVM 上可反过来利用其字节持久 + 快速随机写，减小日志量、加速恢复。

这些设计的共同逻辑是：WAL、检查点、缓冲池这些机制的存在前提是"持久介质慢且块寻址"，一旦介质变成"快 + 字节持久"，就有机会把它们简化或替换。但要给初学者一个诚实的括注：这些多为研究原型或论文方案，是否在生产系统落地、落地到什么程度，取决于硬件是否可得——而硬件这一环恰恰出了大问题，见下节。所以本节的正确读法是"这是 NVM 若普及会带来的设计空间"，而非"现在的数据库都这么做了"。

### 04-11.2.6 现实校准：Optane 已退场，方向转向 CXL

⚙演进快·锚版本（截至 2026-08-01）：必须给初学者一个反预期但重要的事实——最主流的持久内存产品线已经退场。Intel 于 2022 年 7 月宣布逐步关停 Optane 业务，3D XPoint 作为商用 NVM 产品到 2022 年 7 月为止；Optane 持久内存 300 系列于 2023 年 1 月 31 日取消，Intel 不再开发后续 Optane 产品（100/200 系列仅继续既有支持）。连带影响到数据库产品：例如 Oracle 因 Optane 硬件停产，将其 Persistent Memory Database 特性在新版本中标为弃用（deprecated，具体版本以 Oracle 官方为准，此处版本名待核）。

这件事给初学者两个教训。第一是硬件假设会落空：一整批"围绕 NVM 重构引擎"的研究与产品，其硬件底座在几年内消失了，这正是本主题反复强调"前沿硬标、不下定论"的活教材——押注某个新硬件，要考虑它可能不普及甚至退市。第二是方向并未死、而是转移：字节可寻址、可扩展、可池化的内存需求没消失，业界正把这份期待转向 CXL（见 04-11.3.4）承载的内存扩展/内存池，以及 DRAM 与 SSD 之间的软件内存分层。所以正确的心态不是"NVM 白学了"——它教给我们的"持久域、故障原子性、单级存储"这套思维，会在下一代互连/介质上复用；变的是具体产品，不变的是"内存层次正在被重排"这个大趋势。本机基线（普通服务器/容器，无 Optane、无 CXL 内存）上这些均不可得，相关能力标"基线上不可用"，不作实测结论。

## 04-11.3 新硬件适配：GPU / FPGA / RDMA / CXL

### 04-11.3.1 GPU 数据库：海量并行扫描，卡在传输与容量

GPU 数据库用图形处理器的成千上万个核做数据并行的分析计算（扫描、过滤、聚合、连接），在能装进显存、以扫描为主的 OLAP 负载上可比纯 CPU 快很多——HeavyDB（谱系为 MapD → OmniSci → HeavyDB）是代表：它是列存引擎，把查询计划经 LLVM 编译成 GPU/CPU 内核执行（正是 04-5 codegen 思想搬到 GPU）。

GPU 擅长这活的原因是"同一操作施加到大量数据"（SIMD/SIMT）的模式和列存扫描天然契合——一列几百万个值做同一个过滤/求和，正好喂满 GPU 的众核。但有两个绕不开的瓶颈初学者必须记住。第一是数据传输：数据通常先在 CPU 主存/磁盘，要经 PCIe 总线搬进显存才能算，这条总线带宽有限，很多查询"搬数据的时间比算的时间还长"，收益被吃掉——HeavyDB 的对策是把热数据常驻显存、跨查询复用以摊薄搬运。第二是显存容量：显存比主存小得多，数据集一旦超过显存就要分批换入换出或退回 CPU，优势打折。所以 GPU 数据库的甜区是"数据(半)常驻显存 + 扫描密集"的实时分析/可视化。⚙演进快（截至 2026-08-01）：据数据库百科（dbdb.io）等公开资料，HEAVY.AI 于 2025 年被 Nvidia 收购、其开源项目随之搁置——这条为二手口径，具体后续以官方为准（待核）；GPU 数据库这一品类整体仍在演进，别把单一产品动向当成品类结论。本机基线通常无独显/无 CUDA 环境，标"基线上不可用"。

### 04-11.3.2 FPGA 加速：可重构近数据计算，卡在开发与重配

FPGA（Field-Programmable Gate Array，现场可编程门阵列）是一种可编程硬件，能把特定算子（扫描、过滤、解压、聚合）"烧"成定制电路直接跑，常部署在靠近存储的位置做近数据处理（把计算下推到数据所在处，减少往 CPU 搬数据）。

代表案例有两类。一是 Amazon Redshift 的 AQUA（Advanced Query Accelerator）：用 FPGA 在存储层加速扫描、过滤、聚合，把计算推到数据附近，官方称可显著加速特定查询（其配置方式后来改为由 Redshift 自动决定，见官方文档）。二是 Swarm64：一套让 PostgreSQL 借助 FPGA 协处理器并行加速的软件（该团队/技术后被 SingleStore 收购，年份待核）。FPGA 的吸引力在于灵活 + 能效：既能像硬件一样快，又能重新编程改算法，且近数据处理省下总线搬运。但瓶颈在开发与运维：把算子写成硬件电路（用 HDL/HLS）远比写软件难、周期长；重配 FPGA（换一套电路）有开销；且它同样受总线/接口带宽约束。给初学者的落点：FPGA 在"固定、热、可硬化的算子 + 近存储"场景有价值，但通用查询的灵活性/开发成本让它多以"专用加速器"而非"通用引擎"出现。⚙演进快·锚版本（2026-08-01）：AQUA/Swarm64 等产品形态与是否续存随厂商策略变动，此处只记设计取向，现状以官方为准（部分待核）。本机基线无 FPGA，标"基线上不可用"。

### 04-11.3.3 RDMA 与快网络：一端直读远端内存，重画分布式边界

RDMA（Remote Direct Memory Access，远程直接内存访问）让一台机器的网卡直接读写另一台机器的内存，绕过对方 CPU 与操作系统内核，配合 InfiniBand/RoCE 等高速网络把网络延迟压到微秒级——这改变了"分布式数据库里网络必然是瓶颈"的老假设。

要抓的关键概念是单边（one-sided）操作：普通网络通信是双边的（收方 CPU 要参与收包、处理），而 RDMA 的单边 READ/WRITE 由发起方网卡直接操作远端内存、远端 CPU 全程不介入，省下大量 CPU 周期，扩展性因此更好。这催生了新的架构范式 NAM（Network-Attached Memory，网络附着内存）：把集群显式拆成"计算服务器"与"内存服务器"两类，计算侧尽量用单边 RDMA 去内存侧取数据（存算分离的一种硬件级实现）——NAM-DB 论文（Zamanian et al.「The End of a Myth: Distributed Transactions Can Scale」VLDB 2017）展示了用 RDMA + 快照隔离让分布式事务线性扩展，反驳了"分布式事务扩不动"的旧论断（这也和 04-10 分布式事务、04-1 存算分离呼应）。给初学者的直觉：网络快到接近本地内存后，"数据在本机还是远端"的界限变模糊，很多"因为网络慢才那么设计"的老决定（比如尽量避免跨机通信）需要重估。易错点：RDMA 不是"免费加速"——单边操作绕开远端 CPU 的同时也拿不到远端的并发控制协助，在其上做正确的同步/一致性反而更烧脑（有专门研究单边 RDMA 同步陷阱的工作）。本机基线无 RDMA 网卡，标"基线上不可用"。

### 04-11.3.4 CXL：缓存一致互连，把内存扩展 / 池化 / 共享

CXL（Compute Express Link，计算快速链接）是构建在 PCIe 物理层之上的缓存一致（cache-coherent）互连标准，让 CPU 能以接近本地内存的语义访问挂在 CXL 上的设备内存，主打三件事：内存扩展（给单机加挂更多内存）、内存池化（多台主机共享一个内存池、按需分配）、内存共享（多主机一致地访问同一块内存）。它被广泛视为 Optane 退场后"可扩展、可池化字节级内存"这条需求的接棒者。

```
   CPU ──缓存一致──┬── 本地 DRAM
                   └── CXL 链接 ──┬── CXL 内存扩展（加内存）
                                  ├── CXL 内存池（多机共享分配）
                                  └── 其它一致设备
```

数据库长期受"单机内存容量固定、多机内存无法共享"所限（要么数据放不下、要么各机内存各用各的、利用率低）。CXL 的池化/共享让"内存"变成可像存储一样解耦、按需分配的资源，天然契合存算分离（04-1）与内存库（04-11.2）——本可弥补 Optane 留下的空档。关键取舍是延迟层级：CXL 挂载的内存比本地 DRAM 慢一档（要走链接），于是引擎需要做内存分层（热数据放本地 DRAM、温数据放 CXL），这和 04-11.2 的冷热分层思路一脉相承。⚙演进快·锚版本·随时变（2026-08-01，多为较新动向，部分数值待核）：CXL 规范已迭代到较高版本（业界报道有 CXL 3.0 已定稿、并有 CXL 4.0 规范于 2025 年底发布、带宽再翻倍等说法，具体以 computeexpresslink.org 官方规范为准）；云厂商开始提供 CXL 相关实例（有报道称微软于 2025 年底推出业界首批 CXL 云实例）——这些均属快速演进的行业动态，本报告记录方向与趋势，不锁定具体数值/时间点，存疑处标待核。数据库对 CXL 的利用目前多在研究/早期阶段，成熟度总体为"预览/早期"，本机基线无 CXL 内存，标"基线上不可用"，不作实测结论。

### 04-11.3.5 贯穿主线：数据搬运成为主敌，内存层次正在被重排

把 GPU/FPGA/RDMA/CXL 摆在一起，会浮现一条贯穿主线：随着计算越来越快、介质与互连越来越多样，数据搬运（在缓存/内存/显存/远端/持久介质之间挪数据）取代"算得慢"成为主要成本，于是新硬件时代的引擎设计核心，是围绕"数据放哪、计算去就数据、尽量少搬"来重排。

这条主线把本主题串了起来。列存 + 向量化 + 编译（04-2/04-4/04-5）是"让 CPU 少浪费、缓存友好"；GPU/FPGA 是"把计算搬到能大规模并行/近数据的地方"；RDMA/CXL 是"让远端内存/池化内存近得像本地"；NVM 是"让快介质也能持久"。它们回答的都是同一个问题：数据和计算怎么摆才最省搬运。给初学者的收束：不必记住每个硬件的每个参数（它们变得太快，本主题因此全程硬标演进、留白待核），但要带走这个判断框架——遇到任何"新硬件 + 数据库"的说法，先问它改变了内存层次的哪一层、把数据搬运省在了哪、代价（成熟度/可得性/新的复杂度）是什么。这也正是本主题作为内核前沿收尾的意义：机制会更替，"为数据搬运而设计"的思路会长期有效。
