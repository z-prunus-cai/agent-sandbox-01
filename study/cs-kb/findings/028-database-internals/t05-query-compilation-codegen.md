这份报告讲加速查询执行的第二条路线：不逐条元组去"解释"一棵算子树，而是把这棵树先编译成机器码、再一次性跑掉，从根上抹掉解释开销。它和 04-4 的向量化是并列的两条路——向量化靠"一批一批处理摊薄每条元组的固定开销"，编译靠"干脆不解释、直接把这条查询变成一段专用程序"。全篇从"解释到底慢在哪"出发，讲清 HyPer 提出的数据中心化 produce/consume 模型、几类 codegen 后端的取舍，最后落到"编译要花时间，短查询划不划算"这笔账以及业界的自适应/分层解法。编译的核心思想在 2011 年前后定型、跨实现口径一致，可放心作定论；只有具体的 LLVM 后端、各引擎实现细节和默认阈值仍在演进，凡涉及具体数值处一律锚定来源版本或标「待核」。

## 04-5.1 解释执行的开销来源：虚函数分派、解释循环

### 04-5.1.1 火山迭代器模型与逐元组解释开销

传统查询执行用火山（Volcano）迭代器模型：每个算子实现一个统一的 `next()` 接口，父算子调一次 `next()` 就从子算子拉回一条元组，整棵算子树靠一层层 `next()` 调用驱动，一条元组从叶子被"拉"到根。这套模型优雅、可组合、内存占用小，是教科书里的标准执行框架。

它的代价在于"每条元组都要走一遍整棵树的调用链"。一个查询要处理上亿条元组，就意味着上亿次 `next()` 往返；真正有用的计算（比如一次整数加法、一次比较）在每次往返里只占极小一部分，其余全是函数调用、循环控制、状态检查这类固定开销。数据量一大，这些"每条元组都重复付一遍"的固定开销就累加成执行时间的主体。这正是编译和向量化共同要打击的靶子：向量化把它摊到一批元组上，编译把它整个消掉。

初学者容易误以为"慢"是因为算法不好或磁盘慢。这里讨论的是另一个层次的慢——当数据已经在内存里、算法也没问题时，纯粹由"逐条解释"这一执行范式带来的 CPU 开销。现代分析型引擎数据大多在内存/快存里，这层开销就浮到了台面上。

### 04-5.1.2 虚函数分派与间接跳转的代价

火山模型里的 `next()` 通常是虚函数（或函数指针）调用：父算子不知道子算子的具体类型，只能通过虚表/指针间接跳转。这类"间接调用"对现代 CPU 很不友好，是解释开销里被反复点名的一项。

代价来自几处叠加。间接跳转的目标地址在运行时才定，CPU 的分支预测器难以预测，一旦预测失败就要冲刷流水线、白跑十几个周期；调用点跨越函数边界，编译器无法把子算子的逻辑内联进父算子，也就无法做跨算子的常量传播、循环优化等；每次调用还有压栈/跳转/返回的固定成本。把这些乘以"每条元组一次"，量级就很可观。

解释执行像每加工一个零件都要重新查一遍工序手册、走一遍全套交接流程；而下面要讲的编译执行，相当于先按这批零件的具体规格订做一条专用流水线，之后零件径直流过、不再查手册。易错点是把"虚函数慢"绝对化——单次虚调用并不贵，贵的是"每条元组都来一次、且挡住了编译器优化"，是频次和优化屏障放大了它。

### 04-5.1.3 属性访问与元组解释的开销

除了算子间的调用，解释执行在"读取一条元组的某个字段"上也有隐藏开销。存储里的元组是一段字节，要取出第 k 个字段，得根据 schema 在运行时算偏移、判类型、处理变长字段和 NULL 位图，这个"把字节解释成有类型的值"的过程（常称 tuple deforming）在解释器里对每条元组、每个字段都要重做一遍。

表达式求值同理。一个 `a * 2 + b > c` 的谓词，在解释器里通常被表示成一棵表达式树，求值时递归遍历这棵树、每个节点判断自己是加法还是比较、再取操作数——大量时间花在"遍历树、判断节点类型"上，真正的算术只是叶子上的一瞬。类型在编译期本可确定，解释器却在运行期反复判断，这是纯浪费。

这解释了为什么很多引擎即使不编译整条查询，也会优先编译"表达式求值"和"元组解形"这两块热点（见 04-5.3.5 的 PostgreSQL 表达式 JIT）——因为 schema 和表达式结构在计划确定时就已知道，把它们特化成一段直算的代码，收益最直接、风险最小。

### 04-5.1.4 两条破解路线：编译与向量化（划界）

消除逐元组解释开销有两条主流路线，本大主题（编译）与 04-4（向量化）各讲一条，此处只点明分野。向量化保留解释器式的执行框架，但把接口从"一次一条元组"改成"一次一批（如约千行）列值"，让固定开销被一整批摊薄，且批内是紧凑循环、对 SIMD 与 cache 友好。编译则改变执行范式本身：为这条具体查询生成专用机器码，把 `next()` 调用链、类型判断、表达式树遍历统统在生成代码时消解掉，运行时只剩必要的计算。

两者不是互斥的敌人。业界后来发现它们各有胜场（编译在计算密集、分支少的查询上强，向量化在内存访问密集、便于运行时自适应上强），也出现了融合方案（见 04-5.4.4）。初学者先记住这条主线即可：向量化"摊薄"开销，编译"消除"开销；本报告接下来只沿编译这条路走。

## 04-5.2 数据中心化编译：HyPer produce/consume 模型

### 04-5.2.1 从算子中心到数据中心的转向

Neumann 在 2011 年提出的核心转向是：把执行从"算子中心"（operator-centric）改为"数据中心"（data-centric）。算子中心即火山模型——以算子为主角，算子主动去拉数据、控制流在算子间往返。数据中心反过来以数据为主角：让一条（或一段）数据尽量长时间地停在 CPU 寄存器里，被连续施加一串操作，直到不得不落地为止，控制流围绕"数据往哪走"来组织。

这个转向的目标是数据局部性：迭代器模型下，一条元组每被一个算子处理一次就可能进出内存/缓存一次；数据中心模型追求"数据一旦进了寄存器，就把能在它身上做的操作一口气全做完再说"。为此代码不再按算子边界切分，而是按"数据能连续停留的区段"切分——这个区段就是下面要讲的 pipeline。

不要让算子去追数据（拉模型），而是让数据推着往前走、沿途被加工（推模型），并尽量不把它从寄存器里放下来。这既是 2011 论文的思想，也是 HyPer 引擎的实现基础。

### 04-5.2.2 pipeline 与 pipeline breaker：数据在哪里必须落地

数据中心执行的关键概念是 pipeline（流水线）和 pipeline breaker（流水线断点）。一段可以让元组"始终停在寄存器、连续流过"的算子链就是一个 pipeline；而某些算子必须先把它的全部输入物化下来、之后才能产出结果，这类算子就切断了流水线，称为 pipeline breaker。

典型的 pipeline breaker 有：哈希连接的构建侧（要先把整个构建表灌进哈希表，才能开始探测）、排序（要看到全部输入才能出第一个有序元组）、以及需要看全量数据的聚合。相对地，过滤、投影、哈希连接的探测侧这些"来一条处理一条、不必囤积"的操作则不打断流水线。

```
SELECT ... FROM R JOIN S ON R.k=S.k WHERE R.x>5

pipeline 1 (breaker=build hashtable on S):
   扫 S ──▶ 建哈希表(HT)          ← S 的元组流到"建表"这里落地，pipeline 断
pipeline 2 (breaker=最终输出/聚合):
   扫 R ──▶ 过滤 x>5 ──▶ 探测 HT ──▶ 输出
            └───── 一条 R 元组全程停在寄存器，连续走完这几步 ─────┘
```

理解 pipeline breaker 是理解整个模型的钥匙：编译器就是以 pipeline 为单位生成一段紧凑循环——循环体内，一条元组从被扫出来到被过滤、被探测、被写出，全程尽量待在寄存器，没有 `next()` 往返、没有中间物化。只有到 breaker 处（数据非落地不可），才把结果写进哈希表/排序区，然后开启下一个 pipeline 的循环。初学者可以把一个 pipeline 想成"编译后的一个 for 循环"，breaker 就是循环之间的分界。

### 04-5.2.3 produce/consume 代码生成机制

Neumann 用两个方法把上面的思想落成可实现的代码生成框架：每个算子实现 `produce()` 和 `consume()`。`produce()` 让一个算子"生成产出结果所需的代码"，它会先递归要求其子算子去 produce；`consume()` 则由子算子在自己生成的代码里回调父算子，意为"我这里有一条元组了，请你（父算子）生成继续处理它的代码"。两者配合，沿算子树把一段紧凑的循环代码"拼"出来。

```
根.produce()
  └─ 子.produce()
       └─ 扫描算子.produce():
            生成: for 每条元组 t in 表:
                     子.consume(t 的代码位置)   ← 回调父算子，把处理代码接上
                        父(过滤).consume(): 生成 if(谓词) { 祖父.consume(...) }
                            祖父(输出).consume(): 生成 emit(t)
最终拼出的一段代码 ≈
  for t in 表:
     if (谓词) emit(t)      ← 一个 pipeline 编译成一个紧凑循环，无虚调用
```

produce/consume 是"生成代码的控制流"，不是"运行时的数据流"。它们在编译期跑一遍，把整个 pipeline 展开成一段没有算子边界、没有虚函数、类型全部特化的代码；运行期只跑这段代码，不再有算子对象互相调用。这就把 04-5.1 里所有解释开销（虚调用、类型判断、表达式树遍历）都消解在了代码生成阶段。

易错点是把 produce/consume 和 push/pull 混为一谈——它们是不同层面的东西，下一项澄清。

### 04-5.2.4 与 push/pull 执行模型的关系（划界）

produce/consume 生成出的代码在运行时表现为推（push）模型：数据从扫描算子出发，被主动"推"给上层算子处理，而不是上层用 `next()` 去拉。这与 04-4.5 讨论的 push vs pull 是同一枚硬币——数据中心编译天然落到 push 形态，因为"让数据一路推着走完一个 pipeline"正好对应"数据停在寄存器连续加工"。

push/pull 描述的是"数据在算子间流动的方向"，是一个可以脱离编译单独讨论的执行模型维度（向量化引擎也能选 push 或 pull）；而 produce/consume 是"编译期如何生成这段 push 代码"的具体机制。换句话说，push 是结果的形状，produce/consume 是把这个形状造出来的模具。本报告只讲后者；push/pull 本身的权衡（如 push 对多输出/DAG 计划更自然、pull 对提前终止 LIMIT 更自然）留在 04-4.5。

编译（数据中心）→ 生成推式代码 → 一个 pipeline 一个紧凑循环。这条链把 04-4 和 04-5 两个大主题在"push"这个点上接了起来。

## 04-5.3 codegen 后端：LLVM IR vs 直接机器码 vs 模板/表达式展开

### 04-5.3.1 源到源转译（transpilation）

最朴素的 codegen 后端是把查询计划翻译成一门高级语言的源代码（C/C++/Java/Scala），再调用现成编译器把它编成可执行代码或字节码。数据库不必自己实现代码生成的底层细节，直接复用成熟编译器的全部优化。

```
查询计划 ──生成──▶ C++/Java 源码 ──调用 g++/javac/Janino──▶ 机器码/字节码 ──执行
```

代表实现：Amazon Redshift 生成 C++ 再编译；Apache Spark SQL 的 whole-stage code generation 生成 Java 代码、用 Janino 在运行时编成 JVM 字节码；早期研究系统 HIQUE 生成 C 代码。优点是实现简单、能白嫖顶级编译器优化、生成的源码可读便于调试。缺点是把一整个重型编译器搬进了查询路径——调用 g++/javac 编译一段代码的启动与编译时间往往到几百毫秒量级，对短查询完全不划算（具体耗时依代码规模与编译器而异，待核）。这也是 Neumann 明确避开源到源、转而用 LLVM 的直接原因。

### 04-5.3.2 生成 LLVM IR 再 JIT

Neumann 在 HyPer 里选择生成 LLVM IR（一种介于源码和机器码之间的中间表示），再用 LLVM 的即时编译（JIT）把 IR 编成本机机器码。相比源到源，直接生成 IR 跳过了"解析高级语言源码"这一大块前端开销，编译更快，同时仍享有 LLVM 后端的寄存器分配、指令选择等优化。

HyPer 的一个务实设计是混合模式：不是把所有东西都生成成 IR。复杂但非热点的逻辑（如复杂算子的管理代码、数据结构操作）用预编译好的 C++ 实现，只有真正的 per-tuple 热路径（pipeline 循环体）才生成 LLVM IR 并与 C++ 部分链接调用。这样既保住热路径的极致性能，又不必用 IR 去表达繁琐的非热点逻辑。

```
非热点/复杂逻辑: 预编译 C++ 函数(现成)
热路径 pipeline: 生成 LLVM IR ──JIT──▶ 机器码，内联调用上面的 C++ 函数
```

LLVM 是活跃演进的外部依赖（版本升级会改 IR、改 API、改编译时延），凡涉及 LLVM 版本与其编译耗时的具体数值都属 ⚙演进快·锚版本·随时变，本篇不写死。

### 04-5.3.3 直接生成机器码 / 自定义轻量 IR

第三条路是不依赖 LLVM，自己直接吐机器码，或设计一套比 LLVM 更轻量的自定义中间表示。动机是 LLVM 的优化管线本身耗时不小——对追求"编译要极快"的场景（尤其想低延迟启动的系统），LLVM 的编译时延反而成了瓶颈。

代表是 HyPer 的后继系统 Umbra：它引入自定义的轻量 IR 与自研的快速后端，可以极快地生成机器码用于"先跑起来"，需要时再交给 LLVM 做重优化（与下节自适应执行配合）。直接生成机器码的极端好处是编译近乎零延迟，代价是要自己负担寄存器分配、指令选择等本可交给 LLVM 的活，工程量大、可移植性差、优化质量通常不及 LLVM。

这条路线的实现细节高度依赖具体系统与版本（Umbra 等仍在学术/工程演进中），属 ⚙演进快·锚版本·随时变；本篇只讲清动机与取舍主线，不引具体编译时延数值（待核）。

### 04-5.3.4 模板扩展与表达式编译

模板/微特化。不为每条查询从零生成代码，而是预先写好一批带"洞"的代码模板（如各种算子的骨架），运行时把具体的类型、常量、列偏移等填进洞里，拼装出特化代码。它介于"纯解释"和"全量编译"之间，编译成本低、覆盖有限。

与之相关的是"编译的粒度"选择：可以编译整条查询（whole-query），也可以只编译最热的表达式求值这一小块（expression compilation）。只编译表达式的好处是改动局部、风险小、编译量小，却已能吃掉表达式树遍历这块大头开销；缺点是算子间的 `next()` 往返仍在，摘不掉那部分开销。

初学者可把这四类后端排成一条"编译投入 vs 性能上限"的谱：模板/表达式编译（投入小、上限中）→ LLVM IR（投入中、上限高）→ 直接机器码/自定义 IR（投入大、编译最快、上限高）→ 源到源（实现最省事但编译最慢）。没有绝对最优，取决于系统对启动延迟和吞吐的偏好。

### 04-5.3.5 只编译表达式的工程范例：PostgreSQL 表达式 JIT

PostgreSQL 是"只编译表达式而非整条查询"这条务实路线的典型。自 11 版起（2018），PostgreSQL 用 LLVM 对表达式求值和元组解形（tuple deforming）做 JIT——即把 WHERE/投影里的表达式和"从字节里取字段"这两块热点特化成机器码，而算子仍走原有的火山执行器。它没有采用 HyPer 式的整查询数据中心编译，是一种低风险、增量式的编译落地。

PostgreSQL 用代价阈值决定"这条查询值不值得付编译成本"：`jit`（总开关，PostgreSQL 12 起默认 on）、`jit_above_cost`（计划估计代价超过它才启用 JIT，文档默认 100000）、`jit_optimize_above_cost`（默认 500000，超过才做 LLVM 优化）、`jit_inline_above_cost`（默认 500000，超过才做内联）。这几个默认值是"编译开销 vs 收益权衡"（见 04-5.4）在真实系统里的直接体现——用估计代价当"这条查询够不够大、够大才值得编译"的判据。

```
计划估计代价 c:
  c < jit_above_cost(默认1e5)          → 不 JIT，纯解释执行
  jit_above_cost ≤ c                   → JIT 表达式与元组解形
  c ≥ jit_optimize_above_cost(默认5e5) → 额外做 LLVM 优化
  c ≥ jit_inline_above_cost(默认5e5)   → 额外做函数内联
```

这些默认值随 PostgreSQL 版本可能调整，且是否开启 JIT 在不同发行版/版本上有过反复（⚙演进快·锚版本）；上文默认值以 PostgreSQL 官方文档口径记录、核实 2026-08-01，落地到具体大版本时应以该版本文档为准。易错点：JIT 并非总是净收益——对代价被高估、实际数据量小的查询，编译时间可能反噬，因此这些阈值和开关允许按负载调。

## 04-5.4 编译开销 vs 执行收益权衡、自适应/分层执行

### 04-5.4.1 编译开销的来源与收益折线

编译不是免费加速：在查询真正开始处理数据之前，得先花一段时间把计划变成代码（生成 IR/源码、跑优化、JIT 成机器码），这段"编译时延"是纯前置成本。之后每处理一条元组，编译版比解释版省下固定开销，处理的数据越多、省得越多。于是"编译总耗时"和"解释总耗时"随数据量画成两条线，存在一个交叉点。

```
耗时
 ▲
 │        解释执行(斜率大：每条元组开销高)
 │       /
 │      /        编译执行(有前置编译成本c0，但斜率小)
 │     /     ___/
 │    /  ___/
 │   /__/    ← c0 编译时延(起点抬高)
 │  /│
 │ / │交叉点
 └───┴───────────────────────▶ 处理的数据量/查询运行时间
```

用一条粗略的心智不等式表达"编译值不值得"：

编译总耗时 ≈ 编译时延 + 数据量 × 每元组低开销

解释总耗时 ≈ 数据量 × 每元组高开销

只有当"数据量大到 × 省下的每元组开销 > 编译时延"时，编译才净赚。这就是所有编译型引擎必须回答的问题：这条查询够不够大，大到能把编译的前置成本赚回来。

### 04-5.4.2 何时不该编译：短查询与低延迟场景

上面的折线直接推出一个结论：数据量小、运行时间短的查询不该编译——还没等省下的开销累积到覆盖编译时延，查询就跑完了，结果是编译版比解释版更慢。OLTP 式的点查、只返回几行的查询、以及要求极低启动延迟的交互场景，都落在交叉点左侧。

这带来一个真实痛点：编译时延本身可能是几十到几百毫秒量级（依后端与查询复杂度而异，待核），对一条本该毫秒级返回的短查询是无法接受的固定税。这也是为什么纯"总是全量编译"的引擎在混合负载下会吃亏——它把 OLAP 的加速优势，赔在了 OLTP 短查询的编译延迟上。

工程上的第一道防线就是 04-5.3.5 里 PostgreSQL 那样的代价阈值：用优化器估的计划代价当"这条查询够不够大"的判据，低于阈值直接不编译。但代价估计会错（高估/低估都可能），只靠静态阈值不够稳，于是有了下面更聪明的自适应执行。

### 04-5.4.3 自适应/分层执行：解释起步 + 后台编译热切换

自适应（分层）执行是对"编不编译"这道选择题的高级答法：不预先赌，而是先用一个可以立刻开跑的低延迟模式启动查询，同时在后台把它编译成高性能机器码；一旦编译完成，就在运行途中无缝切换到机器码继续跑。短查询在编译完成前就结束了，只付了低延迟模式的成本；长查询则在跑的过程中"升级",享受到编译的加速。

Kohn、Leis、Neumann 在 2018 年为 HyPer 提出的方案是典型代表：查询先由一个轻量字节码解释器"起飞"（论文称 flying start，几乎零编译延迟即可开始产出结果），编译在后台并行进行，好了就切到 LLVM 优化后的机器码。Umbra 进一步把这套多档位（自研快速后端出低质快码 → LLVM 出高质慢码）做成常态。这直接对应指令集/JVM 世界里"分层编译"（先解释、后 JIT、再重优化）的思路。

```
t=0  ┌───────────── 字节码解释(立刻开跑，低延迟) ─────────────┐
     │ 同时后台: 生成机器码/LLVM 优化 ...(耗时 c0)             │
t=c0 └──── 编译完成 ──▶ 途中热切换到机器码 ──▶ 高吞吐跑完剩余数据
短查询: 在 c0 之前就结束 → 只付解释成本，零编译延迟税
长查询: c0 后切换 → 前段解释 + 后段机器码，总体接近全量编译
```

这套设计几乎抹平了"要不要编译"的两难：它不再需要精确预测查询大小，用"边跑边编、好了就换"取代了"跑前赌一把"。初学者记住这条主线即可：低延迟模式保短查询，后台编译保长查询，运行时切换把两者的好处都拿到。具体的档位数、切换时机、各档编译时延是实现与版本细节，⚙演进快·锚版本，本篇不写死（待核）。

### 04-5.4.4 编译 vs 向量化的比较与融合

编译和向量化（04-4）长期被当成竞争的两条路线，Kersten 等人 2018 年做了系统对比，结论是二者性能相近、各有胜场，不存在一边碾压。大致规律：编译在计算密集、表达式复杂、分支少的查询上更强（生成的紧凑代码把计算压到极致）；向量化在数据访问密集、以及需要运行时自适应（如按数据分布动态选实现）的场景上更灵活，且实现和调试比编译简单。

因此近年趋势是融合而非二选一：在编译出的 pipeline 里，仍以向量/批为单位处理数据，兼收"无解释开销"和"SIMD/批处理友好"两方面好处。代表工作有 Menon、Pavlo、Mowry 的 Relaxed Operator Fusion（ROF，VLDB 2017），它在编译的流水线中引入向量化的物化点，让两种技术协同。

```
纯编译:     一条元组连续走完 pipeline(无解释开销)
纯向量化:   一批列值走一个算子、再走下一个(有框架开销但批处理/SIMD)
融合(ROF等): 编译出的 pipeline 内部按批/向量处理 → 既无虚调用又能 SIMD
```

04-4 和 04-5 是打击"逐元组解释开销"的两把锤子，一把靠摊薄、一把靠消除；它们不是对手，现代高性能引擎往往两把一起抡。选哪条、怎么融合，取决于负载、硬件和工程成本，没有放之四海的最优解。相关比较与融合方案仍在活跃研究，具体加速比数值依查询/数据/硬件而异，本篇不给（待核）。
