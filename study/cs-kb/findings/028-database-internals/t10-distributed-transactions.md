本主题只讲"数据被切成多份、分散在多台机器上时，一个事务怎么在这些机器之间原子地提交"这一个问题——即引擎侧的分布式提交协议实现。它承接单机事务（ACID、隔离级别、MVCC 快照）：单机上一条 `COMMIT` 只需把本地日志刷盘就万事俱备，因为只有一台机器要点头；一旦数据跨了机器，就出现了"要么所有机器都提交、要么所有机器都回滚"的协调难题，而且任何一台机器或它们之间的网络都可能在协调途中挂掉。四节分别讲四种应对：经典的两阶段提交（2PC）及其致命的阻塞问题、Percolator 把 2PC 搬到客户端做快照隔离、Calvin 用"先定序、再确定性执行"绕开 2PC、Spanner 用 TrueTime 时钟给出全局一致的提交时间戳。

划界说明：共识算法本身（Paxos/Raft 如何在多副本间就一个值达成一致）不在本主题展开，留作独立主题；分布式数据库的架构选型（该选哪种一致性、哪套系统）也另有主题。这里只把共识当作被协议调用的一块积木，聚焦"提交协议怎么写"。全篇凡涉及具体数值（如 TrueTime 的不确定度 ε）一律引用论文原值并标核实日期，不凭记忆填。

## 04-10.1 2PC 协议、阻塞问题与 3PC 局限

### 04-10.1.1 两阶段提交协议的基本流程

两阶段提交（Two-Phase Commit，2PC）是让多台机器就"一起提交还是一起回滚"达成一致的经典协议。参与方分两种角色：一个协调者（coordinator，通常是发起事务的那个节点）和若干参与者（participant，各自持有部分数据的机器）。顾名思义它分两个阶段完成一次提交。

第一阶段是投票/准备阶段：

```
阶段1（准备/投票）
  协调者 ──PREPARE──▶ 参与者A、B、C
  每个参与者：
    - 检查自己能否提交（无冲突、约束满足）
    - 若能：把 undo/redo 写入本地日志并刷盘（进入"已准备"态，锁不释放）
    - 回复 YES（我保证：之后无论你让我提交还是回滚，我都做得到）
    - 若不能：回复 NO
```

第二阶段是提交/完成阶段：

```
阶段2（提交/完成）
  协调者收齐投票：
    - 全部 YES → 把 COMMIT 决定写入自己的日志并刷盘 → 向所有参与者发 COMMIT
    - 有一个 NO（或超时）→ 决定 ABORT → 向所有参与者发 ABORT
  参与者收到决定后：应用（提交或回滚）→ 释放锁 → 回 ACK
```

参与者投出 YES 的那一刻，就交出了"单方面反悔"的权利。投 YES 之前，参与者随时可以自己决定放弃；投 YES 之后，它必须把结果写进持久日志、并且承诺"哪怕现在我崩溃重启，恢复后我仍然能按协调者的最终决定提交或回滚"。这个"不可撤回的承诺"正是 2PC 能保证原子性的支点——所有参与者都点头之后，协调者才敢做出全局决定，此时已经没有任何一方能翻盘。另一个要点是决定的唯一权威在协调者：全局的 COMMIT/ABORT 由协调者写日志的那一瞬间确定，其余节点只是执行这个决定。

### 04-10.1.2 阻塞问题：2PC 的致命弱点

2PC 的致命弱点是阻塞（blocking）：如果协调者在参与者们都投了 YES、但决定还没送达的窗口内崩溃，参与者就会卡死——它已经承诺提交、锁还攥在手里，却不知道最终是 COMMIT 还是 ABORT，而它无权自己拍板，只能一直等协调者恢复。

理解这个窗口为什么无解，可以设身处地想一个投了 YES 的参与者：它此刻既不能提交（万一别的参与者投了 NO、全局其实要 ABORT，它提交就破坏了原子性），也不能回滚（万一全局其实是 COMMIT，它回滚同样破坏原子性）。它唯一知道决定的途径就是协调者，而协调者恰恰失联了。更糟的是，问其他参与者也未必有用：如果其他参与者也都停在"已投 YES、未收决定"，谁都不知道答案。在这段时间里，被这个事务锁住的数据对所有其他事务都不可用，故障就从一台机器传染成了整个系统的停摆。这就是为什么常说 2PC 不是容错的原子提交协议——它在无故障时正确，却扛不住协调者这个单点在错误时机崩溃。协调者恢复后从日志读回决定继续推进，能最终解阻塞，但"恢复前一直卡着"这段是逃不掉的。

### 04-10.1.3 协调者日志与恢复：presumed abort/commit

2PC 靠持久化日志在崩溃后恢复。协调者在做出全局决定时必须先把决定写日志再发消息，参与者在投 YES 前必须先把"已准备"状态写日志。崩溃重启后，各方读日志接着把协议推进完（协调者重发决定，参与者按日志里的决定或"已准备待查"状态处理）。

为减少日志写入和恢复期查询开销，工业实现常用两类优化，初学者了解其取向即可。一类是 presumed abort（推定中止）：如果恢复时查不到某事务的任何提交记录，就默认它是 ABORT，于是 ABORT 决定可以不强制记日志、参与者的询问也能省掉——代价偏向"提交要多记一点、中止省事"。另一类是 presumed commit（推定提交），默认取向相反，适合提交远多于中止的负载。它们只改变"没有记录时默认怎么猜"，不改变协议的正确性骨架。这里点到为止，因为不同数据库（以及 XA 这类分布式事务标准）在细节上各有取舍，属于实现层而非协议核心。

### 04-10.1.4 3PC 及其局限：为什么工业界基本不用

三阶段提交（Three-Phase Commit，3PC）是为消除 2PC 阻塞而设计的变体：它在投票和提交之间插入一个"预提交"（pre-commit）阶段，把提交决定的传播分成两步，让参与者在协调者失联时也能通过彼此的状态推断出安全的默认行为，从而在特定故障模型下做到非阻塞。

3PC 的局限在于它的非阻塞性依赖一个很强的假设：网络同步、消息延迟有上界、且不发生网络分区（只允许节点崩溃这类 fail-stop 故障）。现实的分布式系统恰恰做不到——网络会分区、会任意延迟。在网络分区下，3PC 反而可能让被分开的两部分各自做出不一致的决定（一边提交、一边中止），破坏原子性，这比 2PC 的"卡住但不出错"更危险。加上 3PC 多一轮消息、延迟更高，所以工业界基本不用它。真正扛住协调者故障的正路，是把提交决定本身交给一个容错的共识协议来定（例如让一组副本用 Paxos 就"提交还是中止"达成一致，即 Gray 与 Lamport 的 Paxos Commit 思路，也是 Spanner 的做法，见 04-10.4）。这也是为什么现代系统里 2PC 很少单独出现，而总是"2PC 骨架 + 每个角色由一组共识副本担任"。

## 04-10.2 Percolator：Bigtable 上的快照隔离 + 2PC（客户端协调）

### 04-10.2.1 Percolator 的定位与快照隔离

Percolator 是 Google 为增量建立网页索引而做的系统，它在原本只支持单行事务的 Bigtable 之上，加出了跨行、跨机器的多行事务，隔离级别是快照隔离（snapshot isolation，SI）。它没有独立的事务管理器，而是把 2PC 的协调逻辑放进客户端库里，靠一个全局的时间戳服务（timestamp oracle）发号。

快照隔离的含义是：每个事务在开始时拿一个 start_ts（开始时间戳），它读到的是"所有 commit_ts ≤ start_ts 的已提交版本"构成的一致快照，看不到在它之后提交的任何改动；提交时再拿一个 commit_ts。这正好架在 MVCC 之上（见 04-9）：数据带版本，读按时间戳挑版本。初学者可以把 Percolator 理解成"在一个只会存带时间戳的键值对的仓库（Bigtable）上，用客户端代码手写了一套 MVCC + 2PC"。它的巧妙之处在于：所有跨机器的协调状态，都被编码成 Bigtable 里的普通数据列，从而复用了 Bigtable 已有的单行原子性和多副本可靠性，自己不用再造存储。

### 04-10.2.2 三列模型：data / lock / write

Percolator 给每个逻辑列在 Bigtable 里维护三个物理列，这是理解它的钥匙：

```
c:data   —— 存实际数据值，键上带 start_ts（这个版本是哪个事务写的）
c:lock   —— 存"未提交的锁"，标记此 cell 正被某事务 prewrite、尚未提交
c:write  —— 存"提交指针"，键上带 commit_ts，值指向对应 data 的 start_ts
```

这三列合起来编码了一个 cell 的完整状态。读一个 cell 的最新已提交值时，流程是：在 `c:write` 里找 commit_ts ≤ start_ts 的最新一条提交记录，它的值告诉你数据在 `c:data` 里的哪个 start_ts 版本，再去 `c:data` 取出真正的值。

初学者常困惑"为什么要分三列、不能一列搞定"。关键在于把"数据""这行正被谁占用""这行哪个版本算已提交"三件事拆开：`c:write` 的存在与否决定一个版本是否对外可见（提交的原子开关就是往 `c:write` 写那一条），`c:lock` 的存在标记"有事务正在两阶段提交的中途"，`c:data` 只是原始值仓库。这种拆分让"提交"变成一次对 `c:write` 的写、"加锁"变成一次对 `c:lock` 的写，每一步都是 Bigtable 的单行原子操作，从而把复杂的多行协议拆成一串单行原子步骤。

### 04-10.2.3 Prewrite 阶段与冲突检测

Percolator 事务的第一阶段叫 prewrite，对应 2PC 的准备阶段。客户端在所有要写的 cell 上尝试加锁并写入数据（写到 `c:data` 的 start_ts 版本、写到 `c:lock`），其中挑一个 cell 作为主锁（primary lock），其余为次锁（secondary），次锁的值里记着指向主锁的引用。

prewrite 每写一个 cell 都要做两项冲突检测，任一失败则整个事务中止：

```
冲突检测（对每个待写 cell）
  1. 写-写冲突：若 c:write 里存在 commit_ts ≥ 本事务 start_ts 的提交
              → 说明有更晚的事务已经提交过它 → 中止（保 SI 的首提交者胜）
  2. 锁冲突：  若 c:lock 里已存在别的事务的锁
              → 说明有并发事务正占用 → 中止（或尝试清理陈旧锁，见 04-10.2.5）
```

第 1 条对应快照隔离的"首个提交者胜"（first-committer-wins）规则：如果在我读快照之后、别人已经改并提交了同一 cell，我就不能再提交，否则会丢更新。第 2 条保证同一 cell 上不会有两个事务同时进行两阶段提交。初学者要注意主锁/次锁的区分不是修辞——它是下一节原子提交的核心机制：整个多行事务的"生死"被绑定到主锁这一个 cell 上。

### 04-10.2.4 Commit 阶段与主锁的原子性

第二阶段是 commit。客户端先向 timestamp oracle 取一个 commit_ts，然后先提交主锁：把主锁那个 cell 的 `c:lock` 删除，同时在 `c:write` 写入一条 commit_ts→start_ts 的提交记录——这一步是 Bigtable 的单行原子操作。主锁一旦提交成功，整个事务就在逻辑上"已提交"，无法回头；之后再逐个提交各个次锁（同样删 `c:lock`、写 `c:write`）。

这里是 Percolator 全部原子性的收敛点：多行事务的原子提交，被归约成"主锁那一行的单行原子提交"。想清楚这一点就懂了它为什么正确——

```
主锁提交前崩溃：主锁的 c:lock 还在、c:write 没记录 → 事务视为未提交 → 可回滚
主锁提交后崩溃：主锁的 c:write 已有提交记录         → 事务视为已提交 → 可前滚
```

也就是说，无论客户端（协调者）在提交次锁的过程中任何时刻崩溃，事务的最终结果都已由"主锁那一行是否已写入 `c:write`"这一个原子事实唯一确定，不存在"一半提交一半没提交"的模糊态。次锁还没来得及提交也没关系——它们会被后续访问者根据主锁的状态清理并推进（见下一节）。

### 04-10.2.5 崩溃恢复与惰性清理

Percolator 没有专门的协调者进程去善后崩溃事务，而是采用惰性清理（lazy cleanup）：当后来的事务撞见一个残留的锁时，由它顺手根据主锁状态把陈旧事务清理掉。

具体地，某事务读或写时若遇到 `c:lock` 里有别人的锁，它会先判断这个锁是不是"孤儿"（持锁事务可能已崩溃）。判断办法是去看那个锁指向的主锁：若主锁的 `c:write` 已有提交记录，说明原事务其实已提交成功，就把这个次锁"前滚"（补写它的提交记录）；若主锁仍是未提交的锁且已超过存活判定（原文用 Chubby 锁服务维护 worker 存活/锁的 TTL 判定），就认定原事务已死，把它"回滚"（清掉锁）。这样系统不需要一个中心化的故障检测与恢复模块，正确性靠"主锁是唯一真相源 + 任何访问者都能据此推进"来保证。代价是延迟：Percolator 为每次跨行事务付出多轮 Bigtable RPC 和向 oracle 取时间戳的往返，吞吐可扩展但单事务延迟偏高，这也符合它"面向批量增量索引、不追求低延迟 OLTP"的初衷。落地方面，TiKV/TiDB 的事务模型基于 Percolator（主锁/次锁、prewrite/commit 两阶段、时间戳 oracle 由 PD 提供）⚙演进快·锚 TiKV 当前文档·随时变｜核实 2026-08-01；CockroachDB 用相关但不同的"写意图（write intent）"模型，非严格 Percolator，细节待核。

## 04-10.3 Calvin：确定性事务与定序层消除 2PC

### 04-10.3.1 确定性执行的核心思想

Calvin 的核心思想是：先让所有节点就"事务以什么顺序执行"达成一致，之后各节点按这个统一顺序确定性地（deterministically）执行，就不再需要 2PC 来协调提交。因为一旦执行顺序和输入都定死了，每个节点算出的结果必然相同，也必然对"提交还是中止"得出一致结论，无需运行时再互相询问。

初学者可以把它类比成"发牌前先公示牌序"。传统做法是事务们各自到达、边跑边协调谁先谁后、最后用 2PC 确认大家步调一致；Calvin 则把顺序问题提到最前面一次性解决——有一个定序层（sequencing layer）把所有到来的事务排成一个全局输入序列，广播给所有副本，之后每个副本像照着同一份乐谱演奏一样独立执行。既然乐谱相同、演奏又是确定性的，各副本自然收敛到同一状态，"跨节点提交是否一致"这个问题在执行开始前就已经被"大家跑的是同一个定死的序列"给消解了。这也顺带让副本容错变简单：一个副本挂了，另一个副本因为有同一份输入日志，重放即可，不会阻塞。

### 04-10.3.2 定序层与批处理（epoch）

定序层负责把并发到来的事务收集、定序、并复制这份顺序。为摊薄开销，它按时间片批量处理：把一小段时间窗口（epoch，论文用 10ms 量级）内收到的事务打成一批，对这一批的全局顺序用复制协议（如 Paxos，或异步复制）在各副本间敲定，然后把这批"已定序的输入"交给执行层。

按 epoch 批处理是 Calvin 的关键工程取舍。逐个事务去跑共识定序，网络往返开销会压垮吞吐；把 10ms 内的成百上千个事务打成一批一起定序，就把"每事务一次共识"摊薄成"每批一次共识"，吞吐大增，代价是每个事务多等最多一个 epoch 的定序延迟。定序层与执行层的解耦也是要点：定序层只管"排出顺序并可靠复制这个顺序"，不碰数据；执行层只管"照顺序把数据算出来"。这条分界线让 Calvin 把"就顺序达成一致"这唯一一次协调集中到前端，后端执行完全本地化、无跨节点提交协商。

### 04-10.3.3 确定性锁与消除 2PC

在执行层，Calvin 用一种确定性的加锁调度：每个节点严格按定序层给出的事务顺序去申请锁（锁必须按事务在全局序列中的次序被授予），从而所有节点对"谁先拿到锁、谁等谁"得出完全一致的结论。因为调度是确定的、输入是相同的，各节点无需在提交时再跑 2PC 去对齐——它们本就不可能产生分歧。

要看清 2PC 为什么被消掉，对比一下它存在的理由：2PC 的准备阶段是为了让协调者确认"每个参与者都能提交"，因为在传统系统里，某个参与者可能因本地冲突或故障而单方面中止，别人事先不知道。Calvin 里这种"运行时才冒出来的单方面中止"被设计排除了：事务的执行是确定性的，任何会导致中止的情况（如显式的应用级 abort）在所有副本上都会以相同方式、相同结果发生，不存在"这台想提交那台想中止"的分裂。既然全体的提交/中止结论天然一致，就没有什么需要用 2PC 去投票协调，跨节点提交这一轮网络往返被整个省掉。节点故障也不再阻塞事务：由于有确定性的输入日志，健康副本继续按序执行即可。

### 04-10.3.4 读写集预声明与依赖事务（reconnaissance）

Calvin 要能确定性调度，必须在事务开始前就知道它要读写哪些数据项（读写集，read/write set）——这样才能预先安排锁顺序、把事务路由到相关节点。对读写集已知的事务这没问题；但有些事务的访问集取决于数据内容（例如"更新余额最高的账户"，要先读才知道改谁），这类依赖型事务需要额外处理。

Calvin 用一个称为 OLLP（Optimistic Lock Location Prediction，乐观锁位置预测）的侦察（reconnaissance）机制应对：先跑一个只读的"侦察查询"去探明这个事务实际会碰哪些数据项，据此推测出读写集，再把真正的事务连同这个预测的读写集提交定序；执行时如果发现数据变了、预测的读写集不再准确，就中止并重试。这解释了 Calvin 的适用边界与权衡：它对"读写集可预先确定或可低成本侦察"的事务（典型 OLTP、存储过程式事务）效率极高；对高度交互式、随用户输入分多次往返、读写集难以预知的事务则不友好，且一个很长的事务会拖住确定性流水线（因为后面的事务要按序等）。这是它用"预先定序换取消 2PC"所付的代价。

## 04-10.4 Spanner：TrueTime 与外部一致性（commit-wait）

### 04-10.4.1 TrueTime API 与时钟不确定度 ε

Spanner 的独特之处是它不假装机器时钟是精确的，而是把时钟的不确定性显式暴露出来。TrueTime API 的 `TT.now()` 不返回一个时间点，而返回一个区间 `[earliest, latest]`，并保证真实的绝对时间一定落在这个区间内。区间半宽记作 ε（epsilon），代表当前的时钟不确定度。

```
TT.now() = [t_earliest, t_latest]，真实时间 t_abs 满足 t_earliest ≤ t_abs ≤ t_latest
区间宽度 ≈ 2ε，即 ε 越小，时钟越"确信"
```

这套 API 背后是每个数据中心部署的时间主机（time masters），它们用 GPS 接收机和原子钟两类互不相关的时间源互校，把误差控制得很小并把不确定度算准。初学者要理解的关键跃迁是：普通系统"假设时钟准，出错就出错"；Spanner"承认时钟不准，但把不准的程度量化成 ε 并据此等待"，从而把不可靠的物理时钟变成可用于全局排序的工具。ε 越小，下面 commit-wait 要等的时间越短，所以 Spanner 花大力气把 ε 压低。论文报告的 ε 数值：在其生产部署中 ε 通常是个位数毫秒，随后台时间同步的锯齿周期在约 1 到 7 毫秒间波动、平均约 4 毫秒（Spanner OSDI 2012 论文原值，核实 2026-08-01）；这是论文当时的实测值，后续硬件改进会变，属 ⚙演进快·锚论文版本·随时变。

### 04-10.4.2 外部一致性（线性一致的事务序）

Spanner 提供的正确性保证叫外部一致性（external consistency），等价于事务级的线性一致性（linearizability）：如果事务 T1 在 T2 开始之前就已提交完成（在真实时间上先后发生），那么系统给它们分配的提交时间戳一定满足 s1 < s2。也就是说，时间戳的先后与真实世界里的先后一致，绝不倒挂。

不同客户端、不同机器上看到的事务顺序，和真实发生的顺序一致，没有"我明明后转的账却显示在先"这种反直觉现象。要实现它，难点全在"给每个事务分配一个既全局唯一又能反映真实先后的提交时间戳"。单机上用一个本地计数器就行；跨越全球多个数据中心、机器时钟又各有漂移时，天真地"取本地时钟当时间戳"会因时钟误差导致后发生的事务拿到更小的时间戳，破坏外部一致性。Spanner 用 TrueTime 的 ε 加上下一节的 commit-wait 来堵住这个漏洞。

### 04-10.4.3 Commit-wait：等掉时钟不确定度

Commit-wait 是 Spanner 保证外部一致性的核心动作：给一个写事务分配提交时间戳 s 之后，协调者不立刻让写入生效、释放锁，而是主动等待，直到 TrueTime 能确认 s 已经绝对地成为过去，才提交可见。判据是等到 `TT.after(s)` 为真，即等到当前 `TT.now().earliest > s`。

```
提交时间戳 s = TT.now().latest      （取区间上界，保证 s 不早于真实时间）
commit-wait：自旋等待直到 TT.now().earliest > s
            （即等到真实时间必定已越过 s，至多等 ≈ 2ε）
之后：应用写入、释放锁、对外可见
```

取 s 为区间上界 latest，保证 s 不小于分配时刻的真实时间；再等到 earliest 超过 s，保证等待结束时的真实时间必定已经大于 s。于是"s 这个时间点"在写入真正可见之前就已经确凿地过去了。这样一来，任何在本事务提交可见之后才开始的事务，它取到的时间戳必然更大，先后关系不会倒挂——外部一致性得证。代价直接就是延迟：每个读写事务要多等约 2ε（论文里个位数毫秒量级）。这解释了 Spanner 为什么拼命压低 ε——ε 就是它为全局一致性支付的时间税。一个常被忽略的巧思是：commit-wait 常常可以和 2PC 的其他步骤（如把决定复制到 Paxos 组）重叠进行，把等待藏在本来就要花的时间里，摊薄实际开销。

### 04-10.4.4 Spanner 的提交栈：Paxos 组之上的容错 2PC

Spanner 并没有抛弃 2PC，而是把它架在容错的复制之上，从而绕开了 04-10.1 里 2PC 的阻塞死穴。数据按 tablet 分片，每个分片由一个 Paxos 组（跨多数据中心的一组副本）复制维护；对于跨多个分片的读写事务，Spanner 在这些 Paxos 组之间跑 2PC，其中一个组当协调者、其余当参与者。

经典 2PC 里每个角色是单机，协调者一崩就阻塞；Spanner 里每个角色是一个 Paxos 组，单台机器崩溃时组内换个副本顶上、日志已复制，协调者/参与者的角色本身是高可用的，于是"协调者单点崩溃导致长期阻塞"这一 2PC 顽疾被复制层化解。这正是 04-10.1.4 说的正路——2PC 骨架 + 每个角色由共识副本担任。要点是分清两层：Paxos 解决的是"一个分片内部多副本就每条日志达成一致"（复制/共识层，本主题不展开），2PC 解决的是"多个分片就一次跨分片事务的提交与否达成一致"（提交协议层）；Spanner 把两者叠起来，加上 TrueTime 给时间戳和 commit-wait，才凑齐了"全球分布 + 外部一致 + 可容错提交"。此外，Spanner 的只读事务可以完全无锁：给定一个读时间戳，直接在各分片按快照读对应版本即可（MVCC），不参与 2PC、也不必 commit-wait，这让占多数的只读负载几乎不付一致性开销。落地上 Spanner 是 Google 内部/Cloud Spanner 产品，其 ε、部署规模等随时间演进 ⚙演进快·锚论文与产品版本·随时变；开源界 CockroachDB、YugabyteDB 采用类似思路但用软件时钟/混合逻辑时钟（HLC）而非 TrueTime 硬件，机制细节不同，待核。
