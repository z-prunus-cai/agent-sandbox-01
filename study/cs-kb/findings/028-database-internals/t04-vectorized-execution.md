# L6-04·大主题04-4 向量化查询执行

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01 ｜先修：L4-03·03-7 查询执行（火山/迭代器模型、算子 open/next/close）｜一手锚点：CMU 15-721 Fall 2025 L04–L06（https://www.cs.cmu.edu/~15721-f25/）＋ MonetDB/X100「Hyper-Pipelining Query Execution」（CIDR 2005）＋ DuckDB 官方内核文档（Vector / Execution）｜成熟度：向量化执行的核心机制 GA（2005 前后由 X100 定型、跨实现口径一致）；具体引擎的 vector 大小默认值、SIMD 宽度、push/pull 实现细节 ⚙演进快·锚版本·随时变

本主题承接火山模型（迭代器执行），只讲"向量化怎么把火山模型的每元组开销摊薄掉"。火山模型每处理一行就要跨一次算子边界（一次虚函数调用、一趟解释逻辑），行数一大，这层"手续费"就吃掉了大部分 CPU。向量化的答案是：不再一次传一行，而是一次传"一列的一小块"（一个 vector，约上千个值），算子在这一块上跑一个紧凑的列内循环。这样固定手续费被上千行分摊，循环体又对编译器自动向量化（SIMD）友好。向量化与查询编译（04-5）是内核消除解释开销的两条并列路线：向量化保留解释器但让每次解释干很多活，编译则直接把计划变成机器码。全篇凡涉及具体数值（vector 行数、SIMD 宽度、每元组周期数）都锚定到来源或标「待核」，因为这些随引擎版本与硬件平台变化。

## 04-4.1 批列处理模型：vector/batch 与列内循环

### 04-4.1.1 向量化执行是什么

向量化执行（vectorized execution）指算子之间传递的不是单行元组，而是"一列的一个小批"——一个连续存放的定长值数组，通常叫 vector（X100 术语）或 batch/chunk。算子对这一整块数据跑一个循环，一次调用就处理成百上千个值，然后把结果块交给上层算子。

初学者可以把它想成"从零售改批发"。火山模型是零售：上层每要一行，下层就现取一行、过一遍所有算子，每行都重复一整套调用开销。向量化是批发：下层一次备好一整箱（一个 vector）同类型的值，上层的算子对着这一箱做一趟流水线加工。批发省的不是"加工每件商品的力气"，而是"每次开单、跑腿、交接的固定手续"——这正是火山模型的瓶颈所在。关键前提是列存布局：只有同一列的值连续摆放，才能把它们当成一个数组喂给一个紧凑循环；因此向量化几乎总是和列式（或 PAX）布局搭配出现（见 04-2）。

### 04-4.1.2 vector/batch 大小与 cache 驻留

vector 的大小（一块多少行）是向量化最核心的调参：它要足够大，让每次算子调用的固定开销被充分摊薄；又要足够小，让"参与本次运算的所有 vector 加起来"能装进 CPU cache，从而每个值都在 cache 里被就地加工，主存只当 I/O 缓冲。X100 论文把 vector 定义为"小的（例如 1000 个值）、cache 驻留的垂直数据块"，并给出默认大小 1024。

X100 论文用 TPC-H Query 1 实测了 vector 大小对性能的影响，结论是一条"中间有甜点、两端变差"的曲线：

```
vector 太小(=1 行)   → 退化为逐行处理，解释/调用开销主导，最慢
vector 适中(≈1000)   → 甜点：开销已摊薄，且所有中间 vector 仍驻留 cache
vector 过大(→4M 行)  → 中间结果溢出 cache，退回主存物化，性能回落到
                       接近逐行/列代数(MonetDB/MIL)的水平
```

论文原话给出的可用区间是：最优约 1000，但 128 到 8K 之间都工作良好；一旦中间结果放不进任何一级 cache，性能开始恶化，到极端的 4M 行时行为退化到接近"整列物化"的老式列代数。这解释了为什么各引擎的默认 vector 大小都落在千级而非百万级——不是越大越好，而是"够摊薄开销 + 不溢出 cache"的折中。工程上这个默认值因引擎而异且会变：DuckDB 的 `STANDARD_VECTOR_SIZE` 默认 2048 行（⚙演进快·锚 DuckDB 官方内核文档 @核实 2026-08-01），X100 是 1024；常说的"约 1024 行"是量级口径而非某个固定常数，切勿当成通用默认。

### 04-4.1.3 列内紧循环与每元组开销的消除

拿到一个 vector 后，向量化算子对它跑一个"列内紧循环"（tight loop over one column）：循环体只做一件简单的、类型确定的运算（比如"把这一列的每个值加上常数"），没有分支去判断类型、没有跨算子调用。这种循环体小、无数据依赖、访问连续，是编译器和 CPU 最喜欢的形态。

紧循环之所以快，有两层原因。第一层是把"每元组的固定手续"从循环里踢出去：类型分派、算子调度、边界检查只在进入循环前做一次，循环体里全是纯计算。第二层是这种规整循环极易被编译器自动向量化成 SIMD 指令（见 04-4.2），并让 CPU 的流水线、预取、分支预测都跑满。X100 论文报告其高效原语的代价可低到每元组少于 2 个 CPU 周期，而传统逐行解释执行往往是每元组几十到上百周期——这一两个数量级的差距，主线就来自"紧循环 + 开销摊薄"。初学者要抓住的因果链是：列存布局 → 同列值成数组 → 能写紧循环 → 编译器能 SIMD 化 → 每元组周期数掉到个位数。

### 04-4.1.4 选择向量与向量的物理格式

在一个 vector 里，并非每个位置的值都"有效"——上游的 filter 可能只选中了其中一部分行。为避免每过一个算子就把选中的值搬到新数组（物化代价高），向量化引擎普遍用一个选择向量（selection vector）：一个存"哪些下标有效"的整数小数组，附在 vector 上，算子只对被选中的下标做运算。这样过滤只改选择向量、不搬数据。

除了"值数组 + 选择向量"，成熟引擎还给 vector 设计了多种物理格式以省内存和计算。以 DuckDB 官方内核文档为例（⚙锚 DuckDB @核实 2026-08-01），它区分：flat（普通未压缩数组）、constant（整块只有一个常量值，只存一份）、dictionary（子向量 + 索引，对应字典压缩）、sequence（只存起点和步长，表示等差序列如 row id），并用一个 unified（统一）视图让算子无需为每种格式各写一份代码。这些格式让"在压缩/特殊形态上直接算"成为可能：例如一整块常量值，算子认出 constant 格式后只算一次而非一千次。初学者容易忽略选择向量这一层，误以为向量化就是"简单地一次算一批"；实际上选择向量与向量格式是让"过滤后仍不搬数据、编码态上仍能算"的关键工程支架，直接决定向量化能省多少。

## 04-4.2 SIMD 与数据并行原语

### 04-4.2.1 SIMD 数据并行

SIMD（Single Instruction Multiple Data，单指令多数据）是 CPU 的一类指令：一条指令同时对一个宽寄存器里并排的多个值做同一种运算。比如一条 SIMD 加法能把 8 个 32 位整数和另外 8 个一次加完，而不是发 8 条标量加法。向量化的紧循环天然契合 SIMD——循环体对一列同类型值做同一运算，正是"单指令多数据"。

理解 SIMD 的关键是把它和前面的"vector 批处理"分清层次。vector 是软件层的批（一次传上千行）；SIMD 是硬件层的批（一条指令并行算几个到几十个值）。二者叠加：一个上千行的 vector，在紧循环里被 CPU 每次吞下一个 SIMD 宽度的小片。一次 SIMD 能并行几个值，取决于寄存器宽度除以数据类型宽度——例如 256 位寄存器处理 32 位整数一次是 8 个。具体的 SIMD 宽度（128/256/512 位）与可用指令集因 CPU 平台而异，不是固定常数（本机基线为 x86-64，具体指令集支持随 CPU 型号而定，此处不写死宽度，标「因平台而异」）。

### 04-4.2.2 掩码：把比较结果变成可并行的选择

SIMD 里没有"对某几个值执行、跳过另几个"的分支——一条指令要么对整片都算。处理"条件"的办法是掩码（mask）：比较运算（如 `>`）不产生跳转，而是对片内每个值产出一个"真/假"位或字节，拼成一个掩码。后续用掩码做按位选择（真的取新值、假的保留旧值），或把掩码压缩成选择向量供下游只处理选中行。

掩码是 SIMD 处理分支的核心手段，也是初学者最反直觉的一点：向量化里"if 条件"往往被改写成"无分支的比较 + 掩码"，因为在数据并行硬件上，分支既不能对片内不同值分头走，还会引入分支预测失败的代价。举例，`WHERE amount > 100` 在标量代码里是每行一个 if；在向量化里是"对整个 amount vector 做一条 SIMD 比较得到掩码"，再据掩码更新选择向量。这也是为什么向量化 filter 输出的是"选择向量"而非搬移后的新数组（呼应 04-4.1.4）——掩码到选择向量是同一条链路。

### 04-4.2.3 gather 与 scatter

gather（收集）和 scatter（散布）是 SIMD 的两条"带下标的批量访存"原语。gather 按一片下标从内存里一次取回多个不连续位置的值（如按一组 row id 去某列取值）；scatter 反过来，按一片下标把多个值一次写到不连续位置。它们让"随机访问"也能在向量化里成批做。

向量化最爱连续访问，但很多算子绕不开随机访问——hash join 探测要按哈希值跳到散列表不同桶，字典解码要按码去字典表取原值，这些都是"按一批下标取一批值"。没有 gather/scatter 就得退回一个个标量地取，破坏批处理。要提醒初学者的是，gather/scatter 虽是一条指令，但底层仍是多次不连续访存，cache 不友好时可能很慢，并不是"和连续访问一样快的银弹"；它是"让随机访问也能纳入向量化流水线"的手段，而非零成本。硬件对 gather/scatter 的支持强弱、是否高效随指令集与代际变化（⚙因平台/代际而异，具体加速比标「待核」，不编造）。

### 04-4.2.4 SIMD 与向量化的关系：自动向量化 vs 手写原语

向量化执行拿到 SIMD 收益有两条途径。一是靠编译器自动向量化（auto-vectorization）：把算子写成规整的紧循环，编译器识别后自动生成 SIMD 指令——这也是 X100 强调"写 cache 友好、无依赖的紧循环"的原因，让编译器有机会做这件事。二是手写 SIMD 原语（intrinsics）：针对关键算子直接用平台指令写，掌控更强但不可移植、维护成本高。

向量化（软件批处理模型）不等于 SIMD（硬件指令），前者不必依赖后者也已经能大幅提速——因为它主要消除的是"每元组的解释/调用开销"，这一层收益在没有任何 SIMD 的标量紧循环上就已兑现（X100 的主线收益就来自开销摊薄，SIMD 是叠加项）。SIMD 是在开销摊薄之上"再把循环体本身并行提速"的第二层红利。初学者常把两者混为一谈，误以为"向量化 = 用 SIMD"；正确的心智模型是：向量化先靠批处理消灭手续费，再顺势让规整循环吃到 SIMD。到底吃到多少 SIMD，取决于数据类型、算子形态、编译器与目标 CPU 指令集，因平台而异，不宜给死数字。

## 04-4.3 火山模型 per-tuple 开销的摊薄机制

### 04-4.3.1 火山模型的每元组开销来自哪里

火山模型（Volcano / 迭代器模型）里每个算子实现一个 `next()` 接口，上层每调一次 `next()` 就向下拉取一行（先修 L4-03·03-7）。它的优点是算子可任意组合、内存占用小；代价是每产出一行就要跨一次算子边界，而这一次跨越带着固定开销：一次虚函数（或函数指针）调用、进出算子的状态维护、按行判断类型的解释逻辑、以及打断 CPU 流水线的间接跳转。

这些开销的要害在于它们是"每元组一份"，与真正的计算量无关。当一列有上千万行时，光是"调用 + 分派 + 解释"这层手续费就可能占到 CPU 时间的大头，真正的算术反而是零头。这就是为什么逐行火山模型在分析型大扫描上慢得不成比例——不是算得慢，是手续办得太频繁。初学者可把 `next()` 想成"每取一件货都要重新排一次队、验一次单"，货一多，排队验单本身成了瓶颈。

### 04-4.3.2 摊薄的定量刻画

向量化不改变火山"算子组合"的骨架，而是把 `next()` 的粒度从"一行"改成"一个 vector"：一次调用返回一整块，固定开销由这一块里的 N 行共同分摊。设每次算子调用的固定开销为 C_fixed（分派、状态、类型判断），每个值真正的计算成本为 C_work，vector 大小为 N，则平均每元组成本为

cost_per_tuple = C_fixed / N + C_work

逐行执行相当于 N = 1，每元组都要付满一份 C_fixed；向量化把 N 提到上千，C_fixed / N 这一项被压到近乎可忽略，每元组成本逼近纯计算 C_work。

这个简单式子解释了三件事。其一，为什么 vector 不必很大：C_fixed / N 随 N 增大迅速衰减，N 到几百上千时这项已很小，再大收益递减——正好呼应 04-4.1.2 里"128 到 8K 都工作良好"。其二，为什么还有上界：N 太大时中间结果溢出 cache，C_work 那项因访存变贵而回升，总成本反弹。其三，摊薄的是 C_fixed 不是 C_work：向量化不会让"加一个数"这件事本身变快（那是 SIMD 和编译的活），它消灭的是重复缴纳的手续费。X100 报告高效原语可达每元组少于 2 周期，正是 C_fixed/N 被压没、C_work 又被 SIMED 化后的综合结果。

### 04-4.3.3 摊薄之外的次级收益

除了直接的开销分摊，批处理还捎带来几项 CPU 微架构层面的红利。紧循环的循环体固定、分支少，分支预测器命中率高；指令序列在循环里高度复用，指令 cache 命中好；连续访存让硬件预取器有效工作，隐藏内存延迟；无数据依赖的规整循环让 CPU 的多发射流水线并行度拉满（X100 标题"Hyper-Pipelining"正指此）。

这些收益单看每项都不大，合起来却能把"每元组周期数"再压一截，是逐行模型永远拿不到的——逐行执行里频繁的间接调用不断清空流水线、污染指令 cache，硬件的这些加速机制根本使不上劲。初学者理解到这一层就够了：向量化的总收益 = 开销摊薄（主线）+ SIMD 数据并行 + 微架构友好（流水线/预取/预测），三者都建立在"一次处理一整块规整数据"这个共同前提上。

### 04-4.3.4 向量化与查询编译的划界

消除逐行解释开销有两条路线，向量化是其一，查询编译（04-5）是其二。向量化保留解释器，但让每次解释干一整块的活，用"批"摊掉手续费；编译则把查询计划直接生成机器码，让整条流水线融成一个循环，从根上取消解释与算子边界。

两条路线目标相同（干掉 per-tuple 开销）、手段不同，各有取舍：向量化实现相对简单、无编译时延、易于调试与做自适应，但算子间仍要把中间 vector 写来读去（物化开销）；编译能把多个算子融进一个循环、避免中间物化，理论峰值更高，但有编译时延、实现与调试更复杂。二者并非互斥，工业界也有"向量化 + 局部编译"的混合。本节只做划界，编译路线的机制主叙事留 04-5。初学者只需记住：这是内核为同一个病（火山模型每元组太贵）开出的两张不同药方。

## 04-4.4 向量化算子实现：filter / hash / aggregate 的批处理形态

### 04-4.4.1 向量化 filter

向量化的选择（filter）算子对输入 vector 的谓词列跑一趟 SIMD 比较，得到掩码，再把掩码转成（或更新）选择向量，输出"哪些下标通过了条件"，而不搬移数据本身。下游算子据这个选择向量只处理被选中的行。

它把标量代码里"每行一个 if 分支"换成"整块一条无分支比较 + 掩码"，既摊掉了每元组开销，又避开了分支预测失败（呼应 04-4.2.2）。关键设计是不物化：filter 不生成一个"只含通过行"的新数组，只更新一个下标列表，因为立即搬数据在多级过滤链里代价高。这直接把话题引向延迟物化（见 04-2.4）——尽量晚地、必要时才把选中的行真正取齐。初学者要记住向量化 filter 的产物是"选择向量"这个下标集合，不是过滤后的紧凑数据。

### 04-4.4.2 向量化 hash join

hash join 分建表（build）与探测（probe）两阶段，向量化让两阶段都批处理。build：对建表侧一个 vector 的连接键批量算哈希、批量插入散列表。probe：对探测侧一个 vector 的键批量算哈希，用 gather 按哈希批量定位到桶，成批比较键、成批产出匹配。

难点在于哈希探测本质是随机访问散列表，与向量化偏爱的连续访问相冲突——这正是 gather/scatter（04-4.2.3）的用武之地：把"按一批哈希值跳到一批桶"做成批量访存。工程上还常把探测拆成"算哈希→取桶→比键→取载荷"几个各自规整的小步骤，每步对整块做，避免一行走到底的长依赖链。要提醒的是，散列表探测的 cache 未命中往往是 hash join 的真实瓶颈，向量化能把控制流开销摊掉，但填不平随机访存的延迟；这也是 04-6 里 radix 分区、缓存感知 hash join 要解决的问题。此处只讲"算子的批处理形态"，高性能实现细节留 04-6。

### 04-4.4.3 向量化聚合

向量化聚合（如 `GROUP BY ... SUM`）对输入 vector 批量计算分组键的哈希、用 gather/scatter 批量定位到每组的聚合状态（累加器），再对整块做累加。无分组的全局聚合更简单：对整块做一次 SIMD 归约（如把一片值水平相加）即可。

它与 hash join 的探测同构——都靠哈希把值散布到一张表的不同槽再更新，因此同样重度依赖 gather/scatter，也同样受随机访存制约。一个初学者常忽略的细节是聚合状态的更新有写冲突风险：同一块里若多行落到同一组，scatter 式并行更新需处理"同组多次累加"的正确性，实现上或串行化同组更新、或分片后合并。并行/两阶段聚合、溢出（spill）等把这套做到高性能的手段属 04-6，此处只需理解"聚合 = 批量哈希定位 + 批量更新累加器"这个向量化形态。

### 04-4.4.4 表达式求值的向量化

算子内部的表达式（如 `a * 2 + b`）也按向量化方式求值：把表达式树自底向上、对整块逐个子运算地算——先对整个 a 列乘 2 得一个中间 vector，再和整个 b 列相加得结果 vector。每个子运算都是一趟紧循环原语。

这种"一次算一整块的一个子运算、产出中间 vector"是向量化的标志性形态，也暴露它的代价：中间 vector 要写出再读入，多级表达式会产生多趟内存往返，这正是编译执行（04-5）想用"把整棵表达式融进一个循环、不落中间结果"来省掉的部分。X100 之所以强调所有中间 vector 都要驻留 cache，就是为了让这些往返都发生在 cache 内、代价可控。初学者可把它对照 04-4.3.4 的划界：向量化用"分步、每步一整块"的方式跑表达式，简单通用但有中间物化；编译用"一趟到底"换取更高峰值但更复杂。

## 04-4.5 push vs pull 执行模型对比

### 04-4.5.1 pull 模型（需求驱动）

pull（拉取 / demand-driven）模型就是经典火山模型：控制权在顶端，最上层算子调 `next()` 向下要数据，需求沿算子树一路往下传，叶子（扫描）产出后再层层返回。数据是被上层"拉"上来的，谁要谁开口。

pull 的好处是控制流直观、算子接口统一、天然惰性（上层不要就不算，`LIMIT` 很省），这也是它几十年成为默认的原因。向量化可以直接嫁接到 pull 上——只要把 `next()` 的返回粒度从一行改成一个 vector，就得到"向量化的 pull 模型"，X100 本身就是 Volcano 式的向量化 pull。初学者要分清：pull 是"谁驱动数据流动"的问题，向量化是"一次流动多少"的问题，两者正交。

### 04-4.5.2 push 模型（数据驱动）

push（推送 / data-driven）模型反转控制方向：由数据源（扫描）主动把产出的一块数据"推"给下游算子，下游算子处理完再推给它的下游，数据沿算子链自底向上被推着走，直到汇入结果或某个需要攒齐数据的算子。

push 的关键优势在于对复杂计划和并行更友好。以流水线为单位组织执行时，一条流水线从一个数据源推到一个"流水线断点"（pipeline breaker，如 hash join 的 build 端、聚合），中间的算子被融成连续处理，减少了 pull 里每个算子各自调用、各自维护迭代状态的开销，也更容易把不同流水线、不同数据分片交给多线程并行（morsel-driven，见 04-8）。对 UNION、OUTER JOIN 这类一个算子有多个输入/输出的结构，push 的数据流也比 pull 的"从哪个孩子拉"更自然。

### 04-4.5.3 两模型的对比与取舍

把两者摆在一起看，差异集中在控制方向与并行组织：

```
维度          pull(需求驱动/Volcano)      push(数据驱动)
控制方向      上层调 next() 向下拉        源头产出后向上推
惰性          天然惰性(LIMIT 友好)        需额外机制表达"够了、停止"
多输入算子    需选择从哪个孩子拉,稍别扭   数据自然汇入,较自然
并行/流水线   迭代状态分散,较难融合       以流水线为单位,易并行/融合
实现直观度    接口统一,历史默认,易理解    控制流反转,初看较绕
```

没有绝对优劣：pull 惰性好、概念简单，push 在多核并行与复杂计划上更顺手，这也是不少现代 OLAP 引擎从 pull 转向 push 的动因。要强调的是它与向量化正交——两种模型都能是向量化的（一次推/拉一个 vector），也都能是逐行的。初学者常把"向量化"和"push"捆在一起，其实是两个独立的设计维度：一个决定批的大小，一个决定谁驱动数据流。

### 04-4.5.4 工程现状与演进

工程上 push 模型近年明显走强，尤其在为多核并行重造执行引擎时。一个有据可查的例子：DuckDB 早期是 pull 式的向量化 Volcano，后来切换到 push-based 执行模型（DuckDB PR #2393「Switch to Push-Based Execution Model」，⚙演进快·锚该 PR @核实 2026-08-01），理由正是 push 更好地支持事件式调度、复杂计划与 morsel 并行；Meta 的 Velox 等新引擎也采用 push 风格。

这属于快速演进区：各引擎的具体选择、混合形态与版本时间线随迭代变化，不宜当成稳定结论。稳定的是概念划界本身（pull=需求驱动、push=数据驱动，与向量化正交），以及"为并行友好而倾向 push"这一趋势方向。具体到某引擎某版本用哪种、何时切换的时间点，凡无法从一手来源坐实的一律标「待核」，不据传闻编造。多核并行调度（morsel-driven、work-stealing、背压）的主叙事在 04-8 展开，此处只把 push/pull 作为向量化的执行骨架讲清。
