## 04-7.1 优化器架构：自底向上（System R）vs top-down/Cascades

### 04-7.1.1 优化器在整机里的位置：从逻辑计划到物理计划

查询优化器是 SQL 引擎里"解析/绑定"之后、"执行"之前的一层。它的输入是一棵**逻辑计划**（一棵关系代数表达式树：哪些表、做什么选择/投影/连接/聚合），输出是一棵**物理计划**（每个逻辑算子换成一个具体执行算法，并定好次序：这个 join 用 hash join、那张表走索引扫描、先连 A 和 B 再连 C）。它不改变查询的语义结果，只改变"用哪种方式算出同一个结果"。

对初学者，关键是分清"逻辑等价"和"物理选择"两件事叠在一起。逻辑层面，关系代数有大量等价律（选择可以下推、join 可交换可结合），同一个结果对应无数棵等价的逻辑树；物理层面，每个逻辑算子又有多种实现算法（join 有 nested-loop / hash / merge，扫描有全表 / 索引）。两者相乘，可能的执行方式数量随表数量指数增长——这就是为什么"优化"本质是"在一个指数大的空间里搜索最便宜的一个"，而不是套一个公式算出来。

### 04-7.1.2 为什么 join order 是搜索的核心难点

在整个计划空间里，**连接顺序（join order）**是组合爆炸的主要来源，也是优化器最花力气的地方。n 张表做连接，仅"连接顺序 + 树形状"这一个维度，可能的方案数量就随 n 超指数增长，再叠上每个 join 的算法选择、每张表的访问路径选择，空间大到无法穷举列出。

三张表 A、B、C 做连接，可以先连 A⋈B 再连 C，也可以先连 B⋈C 再连 A，也可以先连 A⋈C……每种顺序产生的**中间结果大小**可能天差地别——如果 A⋈B 只剩几行、而 A⋈C 会炸出上亿行，那么选错顺序会让后续每一步都背着一个巨大的中间结果跑，代价可能相差几个数量级。所以优化器把主要预算花在 join order 上是有道理的：这里选错，后面算法选得再好也救不回来。这也解释了 04-7.4 为什么如此重要——判断"哪个中间结果小"要靠基数估计，估不准，join order 就选歪。

### 04-7.1.3 System R：自底向上的动态规划

System R 优化器（Selinger 等 1979）确立了沿用至今的经典做法：**自底向上的动态规划（bottom-up dynamic programming）**。它先为每张单表求出最优访问计划，再枚举所有两表连接的最优计划，再由两表最优拼三表……逐级向上，直到覆盖全部表。每一层都利用"最优子结构"：一个 k 表连接的最优计划，一定由某个 (k−1) 表子集的最优计划再连一张表得到，于是下层算过的最优子计划被上层反复复用，避免重复求解。

对初学者，把它类比成"先算好所有小零件的最省做法，再用小零件拼大零件"。动态规划相对暴力枚举的省法在于：它把"所有 {A,B} 的连接方式"归约成"只保留 {A,B} 这个集合的那个最优计划"（这里先忽略一个例外，见 04-7.3.3 的 interesting orders），下一层要用到 {A,B,C} 时，只需在少数几个最优子计划上接一张表，而不是从头重排。代价是仍要遍历所有表子集，复杂度量级约为

O(2^n)

（n 为参与连接的表数）——所以它只在表数不太多时可行，表一多就要退路（04-7.1.7）。

### 04-7.1.4 join 树形状：left-deep vs bushy，System R 的限制

连接可以拼成不同"树形"。**left-deep（左深树）**是一根"藤"：每次都拿"已经连好的一大坨中间结果"去连"一张新的基表"，新基表永远在右边当内表。**bushy（浓密树）**则允许"两个中间结果互相连"（比如 (A⋈B) ⋈ (C⋈D)）。System R 的经典优化器**只搜索 left-deep 树**，把 bushy 排除在搜索空间外。

限制成 left-deep 有两个初学者能理解的好处。其一，搜索空间小很多：只考虑左深树能把候选数量从"全体二叉树形状"砍到一个可管理的量级。其二，执行上顺手：左深树里内表总是一张原始基表，适合"拿外表的每一行去探一个建在基表/索引上的哈希表或索引"这种流水线式执行，中间结果不必整块物化下来。代价是可能漏掉某些 bushy 才最优的形状——星型/雪花模式下多个维表分别连事实表时，bushy 有时更好。所以现代优化器（尤其分析型引擎）大多**放开到 bushy**，用后面讲的 memo + 剪枝来压住随之变大的空间，而不是靠限制树形。

### 04-7.1.5 Volcano / Cascades：自顶向下的目标驱动搜索

Graefe 的 Volcano（1993）与其后继 Cascades（1995）确立了另一条路线：**自顶向下（top-down）、目标驱动（goal-driven）**的搜索。它不从单表往上拼，而是从"我要整棵查询的结果"这个总目标出发，把它分解成子目标（"我要 A、B、C 的连接结果"），再递归分解（"那我需要 A⋈B 的结果，且需要 C"），一路向下按需展开；展开过程中用记忆化（memo，04-7.2）把已经解过的子目标缓存起来，避免重复。

对初学者，最好的对比是"自底向上像先把所有小积木都拼好备用，自顶向下像从要盖的房子倒推需要哪些零件、要哪个才去做哪个"。top-down 的一个实际优势是**天然支持剪枝**：既然是带着"目标"往下钻，就可以给每个子目标带一个"代价上限"，一旦某条展开路径的下界已经超过当前已知最好计划的代价，就整枝砍掉不再深入（branch-and-bound，见 04-7.2.6）——这在自底向上里不那么自然，因为它是"先全算再挑"。另一大优势是它把优化逻辑组织成一套**可扩展的规则系统**（04-7.2.7），加一种新算子或新变换只需注册规则，不用改搜索主循环。

### 04-7.1.6 两条路线的对比与分歧点

自底向上 DP 和自顶向下 Cascades 并不是"谁绝对更好"，而是同一个搜索问题的两种组织方式，工业界两派都有大量落地，取舍点值得点清而不和稀泥。

自底向上（System R 系）的代表是 PostgreSQL 的核心 join 搜索：实现直接、对"表数不多"的 OLTP 查询极快，且天然只走 left-deep（Postgres 也支持部分 bushy，但主线是 DP over 子集）。它的短板是搜索空间形状被写死在算法里，想加"新的等价变换"要动主循环，扩展性差。自顶向下（Volcano/Cascades 系）的代表是 SQL Server、Greenplum/Cloudberry 的 Orca、CockroachDB 优化器；Apache Calcite 的 `VolcanoPlanner` 也是这一族的 top-down/memo 变体（Calcite 名字里就带 Volcano）。它扩展性强、剪枝自然、易支持 bushy 与丰富规则，代价是框架复杂、实现门槛高、规则集调不好时搜索会失控。一个常被误解的点：**"Cascades 一定比 DP 快"是错的**——两者都在同一个指数空间里搜，剪枝和记忆化决定实际开销，框架选择更多是关于**可扩展性与工程组织**，不是关于"谁枚举得少"。

### 04-7.1.7 表数爆炸时的退路：启发式与遗传搜索

无论哪种精确搜索，表数一多（几十张表连接）都会因

O(2^n)

量级而超时，于是引擎需要**次优但可控**的退路。常见两类：一是**启发式/贪心**（按某种规则一步步选"当前看起来最好"的下一个连接，不回溯，牺牲最优性换线性时间）；二是**随机/遗传搜索**，PostgreSQL 的 GEQO（Genetic Query Optimization）即属此类。

PostgreSQL 的具体做法对初学者是很好的落地样本：当 `FROM` 里参与连接的表数达到 `geqo_threshold`（默认 **12**，核实 2026-08-01，⚙随版本可调）时，Postgres 放弃穷举 DP，改用遗传算法在 join order 空间里随机搜索一个"够好"的解。要点是理解这是一个**明确的时间/质量折中**：表少时穷举能保证在其搜索空间内最优、也不慢，就用 DP；表多到穷举会爆时，宁可要一个"可能不是最优、但几秒内能出"的计划，也不能让优化本身跑到天荒地老。分析型引擎面对大 join 图时也各有类似的空间裁剪与启发式（如限制 bushy 的形态、超时降级），思路一致：**用最优性换可预期的优化时间**。

## 04-7.2 变换规则、memo 结构与等价类分组

### 04-7.2.1 memo：把指数级空间压成共享子结构的图

memo 是 Cascades 类优化器的核心数据结构：一张**记忆化（memoization）表**，用来紧凑地存下"搜索过程中见过的所有等价子表达式"，让指数级的计划空间以多项式规模的共享图形式驻留内存。没有它，自顶向下搜索会对同一个子问题（比如"A⋈B 的结果"）反复重算，退化成暴力枚举。

对初学者，把 memo 想成一个"带去重的计划仓库"。当搜索走到"我需要 A⋈B 的结果"时，先查 memo：这个子问题以前解过吗？解过就直接复用它记录的最优子计划，没解过才展开、算完把结果登记进去。关键洞察是：无数棵完整计划树之间**大量共享子树**——很多不同的整体计划都用到"A⋈B"这块。memo 不去存每一棵完整树，而是存"子表达式"以及它们之间的引用关系，于是指数级的树集合被折叠成一张远小得多的图。这正是 top-down 搜索能在大空间里跑起来的根本原因。

### 04-7.2.2 group（等价类）与 group expression

memo 内部按**group（组）**组织，一个 group 就是一个**逻辑等价类**：所有能算出"同一份结果集"的表达式归到同一个 group。例如 "A⋈B" 和 "B⋈A" 逻辑等价，属同一个 group；"A⋈B⋈C" 是另一个 group。group 里装的是一条条 **group expression（组表达式）**，每条组表达式是"一个算子 + 若干指向其它 group 的输入引用"（比如一条 `Join` 组表达式，它的两个孩子不是具体子树，而是"某某 group"的指针）。

理解 group 与 group expression 的分工是读懂 memo 的钥匙。group 代表"要算出的那份结果"（是什么），group expression 代表"算出它的一种方式"（怎么算，且它的输入用 group 间接引用而非嵌完整子树）。这个"用 group 引用代替嵌套子树"的间接层，正是共享得以发生的机制：`(A⋈B)⋈C` 和 `(A⋈C)⋈B` 里如果都要用到 group{A,B}，它们各自的 `Join` 组表达式都指向同一个 group{A,B}，不必各存一份。一个 group 通常同时含**逻辑组表达式**（如 `Join`）和后续生成的**物理组表达式**（如 `HashJoin`、`MergeJoin`），见下一条。结构示意（一个组内多种等价表达式，输入以 group 编号间接引用）：

```
Group 7  ≡  { A ⋈ B ⋈ C }      ← 等价类：算出这份结果的所有方式
  ├─ [logical]  Join( Group5 , Group3 )     Group5 = {A,B}, Group3 = {C}
  ├─ [logical]  Join( Group6 , Group2 )     Group6 = {A,C}, Group2 = {B}
  ├─ [physical] HashJoin( Group5 , Group3 )
  └─ [physical] MergeJoin( Group5 , Group3 )   （需 Group5、Group3 按 join key 有序）
```

### 04-7.2.3 逻辑变换规则 vs 物理实现规则

搜索靠**规则（rule）**驱动地往 memo 里填新表达式，规则分两类。**变换规则（transformation rule，逻辑→逻辑）**把一个逻辑表达式改写成另一个逻辑等价的表达式，产物落在**同一个 group**里（因为逻辑等价），例如 join 交换律 `A⋈B → B⋈A`、结合律、谓词下推。**实现规则（implementation rule，逻辑→物理）**把一个逻辑算子替换成一个具体物理算法，例如 `Join → HashJoin`、`Join → MergeJoin`、`Scan → IndexScan`。

对初学者，一句话记牢分工：**变换规则扩大"有哪些等价算法"（探索逻辑空间），实现规则回答"每种算法怎么落地执行"（映到物理算子）**。变换规则的产物仍是逻辑表达式、留在原 group（还没决定怎么执行），实现规则的产物是物理表达式（带了执行算法、可以估代价）。这种"逻辑探索"和"物理实现"分成两类规则的干净切分，是 Cascades 可扩展性的来源：想让优化器认识一种新的等价变换，写一条变换规则注册进去即可；想支持一种新的执行算法，写一条实现规则即可，都不用改搜索主循环。

### 04-7.2.4 规则应用中的去重与记忆化

规则不停产生新表达式，其中很多是重复的——比如对 `A⋈B` 用交换律得 `B⋈A`，再对 `B⋈A` 用交换律又得回 `A⋈B`。memo 必须**检测并合并重复**：每生成一个新表达式，先做规范化/哈希，查它是否已存在于某个 group，存在就丢弃（或合并 group），不存在才真正插入并可能触发进一步的规则应用。

这一步对初学者容易被忽略，但它是 memo 不退化成暴力枚举的另一半保障（前一半是 group 的共享引用）。如果不去重，交换律、结合律这类"能来回变"的规则会让表达式无限繁殖。实现上还有一个微妙情形：两个原以为不同的 group，经变换后发现其实等价（算出同一结果），此时要把它们**合并（group merging）**成一个，并修正所有指向它们的引用——这是 memo 实现里最容易出 bug 的地方之一。初学者只需记住结论：memo 的正确性建立在"逻辑等价的东西必须落进同一个 group、且不重复存"这条不变量上。

### 04-7.2.5 任务驱动的搜索：Cascades 的 task 组织

Cascades 把搜索过程本身也结构化成一组相互调用的**任务（task）**，用一个任务栈驱动，而不是一个写死的多层循环。典型任务有：优化一个 group（求它在某组需求属性下的最优计划）、优化一条组表达式、探索一个 group（对它应用变换规则以生成更多逻辑等价式）、对一条表达式应用某条规则等。任务之间互相压栈调用，形成自顶向下的按需展开。

对初学者，这层设计的价值在于"**按需、可中断、可定序**"。因为是任务栈而非固定循环，优化器可以只展开真正被目标需要的那部分空间（目标驱动），可以在预算耗尽时停下返回当前最好计划（超时降级），也可以调整任务优先级来引导搜索先看更有希望的方向。这与自底向上 DP"必须把每一层子集都算齐"形成对比——后者结构简单但没法"只算需要的"。这一条属实现内幕，初学者理解到"搜索被拆成可组合的任务、支持按需与剪枝"即可，不必背具体任务清单。

### 04-7.2.6 branch-and-bound 剪枝：用代价上限砍枝

top-down 搜索的一大实惠是天然支持**分支限界（branch-and-bound）剪枝**：优化一个 group 时带上一个"代价上界"（当前已知最好的完整计划代价），一旦某条展开路径累积的代价下界已经超过这个上界，就不再深入这条枝——因为它不可能产出更优的整体计划。

这对初学者是"为什么 top-down 常被认为剪枝更自然"的具体答案。举例：正在优化 `A⋈B⋈C`，已经找到一个代价 100 的完整计划；接着尝试另一种连接顺序，刚展开到子步骤代价就已累计到 120，那么无论后面怎么接都 ≥120 > 100，整条枝直接砍掉，省下其下所有子问题的求解。要点是上界越早收紧、剪得越狠，所以实现上常先用启发式快速求一个"还不错"的初始计划把上界压低，再让精确搜索在这个上界下剪枝。这与自底向上 DP 的差别在于：DP 是"先把各层最优都算出来再组合"，剪枝要额外设计；top-down 因为带着目标和上界往下钻，剪枝顺理成章。

### 04-7.2.7 优化器生成器：规则化框架的初衷

Volcano 论文标题里的 "Optimizer **Generator**" 点明了这套框架的原始动机：不是造一个特定数据库的优化器，而是造一个"**能生成优化器的工具**"——把搜索引擎做成通用内核，让不同系统只需提供各自的**规则集、算子、代价模型、属性定义**，就能得到一个定制优化器。Cascades 延续并精炼了这个思想。

对初学者，这解释了为什么现代优化器爱用 Cascades 风格：它把"通用的搜索机制"和"某数据库特有的知识（有哪些算子、哪些等价变换、代价怎么算）"彻底解耦。前者写一次、复用；后者以声明式规则注入。落地证据是这套框架被反复复用：Apache Calcite 作为一个**可嵌入的优化器框架**被众多系统（如 Trino 早期、Flink SQL、Hive 等生态）采用，正是"优化器生成器"理念的当代体现；SQL Server、Orca、CockroachDB 各自的 Cascades 变体也都遵循"通用内核 + 声明式规则"的组织。结论：Cascades 的持久生命力，一半来自搜索效率，另一半来自它作为**可扩展框架**的工程价值。

## 04-7.3 代价模型实现与物理属性推导（interesting orders / 分布）

### 04-7.3.1 代价模型：给每个物理计划打一个可比的分

代价模型是优化器的"打分尺"：给每个候选**物理计划**估算一个代价数值，供搜索比较取小。经典代价由两部分构成——**I/O 代价**（读写多少页/块）和 **CPU 代价**（处理多少元组、算多少表达式）——加权求和。System R 的原始公式把这笔账写成页面读取次数加上一个权重乘以 CPU 调用次数：

COST = PAGE_FETCHES + w × RSI_CALLS

（PAGE_FETCHES 是 I/O 页数，RSI_CALLS 是访问单元组的调用次数即 CPU 侧工作量，w 是把二者换算到同一尺度的权重系数。核实 2026-08-01，Selinger 1979 §代价公式。）

对初学者，两个要点。其一，代价是**估计**不是实测：优化器还没执行就要打分，所以每一项都依赖统计与基数估计（04-7.4）给出的"预计要处理多少行"，估不准分就打歪。其二，权重 w 的存在是因为 I/O 和 CPU 单位不同、快慢比例又随硬件变化——机械盘时代 I/O 是绝对瓶颈，w 很小（CPU 几乎白送）；SSD/内存数据库时代 CPU 占比上升，权重结构随之调整。现代引擎的代价模型远比这条原始公式复杂（含内存、网络、并行度等项），但"多个资源维度加权求和、每项由估计的数据量驱动"这个骨架没变。

### 04-7.3.2 物理属性：sort order 与 distribution

**物理属性（physical property）**是物理计划输出所附带的、影响后续算子代价的"物理特征"，两个最重要的是**排序序（sort order）**——输出是否按某组列有序——和**分布/分区（distribution / partitioning）**——数据在并行/分布式执行里如何散布到各节点。物理属性不改变结果集内容，但深刻影响下游能用什么算法、要不要额外操作。

理解物理属性的意义要从"下游算法有前置要求"入手。merge join 要求两个输入都按 join key 有序；如果某个子计划恰好已经有序（比如它走了一个有序索引扫描），下游 merge join 就能白捡这个有序、省掉排序；反之则要插一个排序算子补上。分布属性同理：并行 hash join 常要求两侧按 join key **同样分区**（co-partition），否则要先做一次数据重分布（shuffle/exchange），这在分布式里是昂贵的网络操作。所以优化器不能只比"算子本身多少钱"，还要连带考虑"为了满足下游对物理属性的要求，要额外花多少钱"——这正是下一条 interesting orders 的动机。

### 04-7.3.3 interesting orders：为什么不能只留"最便宜"的子计划

这是 System R 的一个关键洞见，也是初学者最常忽略的细节。前面 04-7.1.3 说动态规划"每个子集只保留最优计划"，其实有个例外：如果某个子计划虽然**本身**更贵，但它的输出**恰好有序**，而这个序能被下游（ORDER BY、GROUP BY，或某个 merge join）利用从而省下后续排序，那它可能让**整体**更便宜。这种"可能被下游利用的排序序"叫 **interesting order（有趣序）**。优化器因此不为每个子集只留一个最优计划，而是**为每一种 interesting order 各留一个最优计划**，外加一个无序的最优计划。

一个具体例子让初学者抓住要害：查询要 `... ORDER BY x`，中途还要按 x 做一次 merge join。子计划甲用全表扫描 + hash join，本身最便宜但输出无序，最后得单独排一次序；子计划乙走 x 上的有序索引，本身贵一点但输出天然按 x 有序，merge join 和最后的 ORDER BY 都白捡这个序、都省了排序。若只按"本身代价"淘汰，乙早被砍掉，优化器就永远看不到这个整体更优的方案。所以 interesting order 的实质是：**代价比较必须带上"输出物理属性"这个上下文，一个子计划的价值不能脱离它能为下游省下什么来判断**。在 Cascades 里，这一思想被推广为"每个 group 针对不同的 required physical properties 分别求最优"（04-7.3.5）。哪些序算"interesting"？——出现在 ORDER BY / GROUP BY / join 谓词里、可能被利用的那些列序。

### 04-7.3.4 required vs derived 属性与 enforcer

Cascades 把物理属性推导做成一对方向相反的传播：**required property（需求属性）**自顶向下传——父算子/查询顶层向下要求"我需要你的输出按 x 有序"；**derived property（导出属性）**自底向上传——一个物理算子根据它的输入和自身语义，报告"我的输出实际是什么属性"（如 sort-merge join 输出按 join key 有序，hash join 输出无序）。搜索时把二者对上：如果某算子导出的属性已满足父亲的需求，皆大欢喜；如果不满足，就插入一个 **enforcer（强制算子）**去补上——补排序就插一个 Sort 算子，补分布就插一个 Exchange/Shuffle 算子。

对初学者，enforcer 是把"物理属性不匹配"这件事**显式变成一个带代价的算子**的机制，从而纳入统一的代价比较。这样"要不要为满足下游而多排一次序"就不再是特判，而是"插 enforcer 的那条计划"和"某个子计划本就满足属性、不插 enforcer 的那条计划"之间的正常代价 PK。理解这一点，就理解了物理属性推导为什么能干净地融进搜索：需求向下要、能力向上报、对不上就插一个 enforcer 顶上，全程只是往 memo 里多几条带代价的物理表达式而已。

### 04-7.3.5 winner：每个 group 按需求属性各存一个最优

综合前几条，Cascades 里一个 group 的"最优计划"不是唯一的，而是**"给定一组 required physical properties 下的最优"**——同一个 group{A,B,C}，"要求按 x 有序"时的最优计划，和"无排序要求"时的最优计划，可能是完全不同的两棵物理子树。优化器为每个 (group, required properties) 组合缓存一个 **winner（赢家/最优物理计划）**，供上层复用。

这正是 04-7.3.3 的 interesting order 思想在 Cascades 框架下的推广形态：System R 用"为每个 interesting order 各留一个最优子计划"来处理这件事，Cascades 用"为每个 required property 各求一个 winner"来处理，二者是同一洞见的两代表述——**代价最优必须相对于'输出属性需求'来定义，脱离需求谈最优是不完整的**。初学者记住这条对应关系，就把两派在"排序/属性"上的做法打通了。

### 04-7.3.6 代价常数从哪来：可校准且随硬件演进

代价公式里除了"预计处理多少行"（来自统计），还有一批**单位代价常数**：读一个顺序页多贵、读一个随机页多贵、处理一行 CPU 多贵、算一个表达式多贵。这些常数把不同资源换算到同一把尺子上，其取值依赖硬件，且各引擎给的默认值不同、可调、随版本演进。

以 PostgreSQL 为具体样本（⚙演进快·锚版本·随时变，具体数值随版本调整，此处仅示意其**结构**，精确默认值随版本以官方文档为准、未逐版亲测者标「待核」）：它暴露一组可配置代价参数，如顺序页读、随机页读、每元组 CPU、每算子 CPU、每索引项 CPU 等，优化器把"预计页数 × 页代价 + 预计行数 × 行代价 + …"加起来作为计划代价。对初学者的两个提醒：其一，这些常数是**相对比值**才有意义（随机读相对顺序读贵多少倍，比绝对值更关键），机械盘上随机远贵于顺序、全内存/SSD 上二者差距大幅缩小，所以在新硬件上常需重新校准，否则优化器会基于过时的比值选错计划。其二，**代价数字不是时间**，是一套内部无量纲评分，只用于计划间相对比较，不要拿去当"预计运行秒数"读。

## 04-7.4 统计维护与基数估计实现：采样、sketch、多列相关

### 04-7.4.1 基数估计：优化器最不准也最要命的一环

**基数估计（cardinality estimation）**是估算"每个算子的输入/输出有多少行"。它是代价模型的头号输入——04-7.1.2 说过 join order 的好坏取决于中间结果大小，而中间结果大小正是靠基数估计预测的。基数估计错了，代价就错，计划就选歪，且错误会沿着计划树**逐层放大**（04-7.4.7）。业界公认它是优化器里最脆弱的部分，"优化器选了个烂计划"十有八九根子在这里。

对初学者，先建立一个反直觉认知：优化器**大部分时间不是在算代价公式，而是在猜数据长什么样**。它没有真去跑查询，只能靠事先采集的**统计信息**（每列有多少不同值、值怎么分布、有没有极端热点）加一套**假设**（各谓词独立、数据均匀等）去推断"满足这个条件的大概有多少行"。这些统计是近似的、假设常常不成立，所以估计天然有误差；后面几条讲的就是"用什么统计、怎么采、怎么在假设失效时补救"。

### 04-7.4.2 选择率因子与 Selinger 的默认魔数

**选择率（selectivity factor）F** 是一个 0~1 的分数，表示某谓词能筛过多少比例的行——`满足谓词的行数 ≈ F × 总行数`。在没有更细统计时，System R 给出了一套沿用至今、被戏称为"魔数（magic numbers）"的**默认选择率**（Selinger 1979，核实 2026-08-01）：

```
column = value   （列上有索引）:  F = 1 / ICARD        （ICARD = 该列不同值个数）
column = value   （无索引）    :  F = 1 / 10
column > value / 范围（可算）  :  F = (high − value) / (high − low)
column > value / 范围（不可算）:  F = 1 / 3
col1 = col2  （join，两侧有索引）: F = 1 / MAX(ICARD1, ICARD2)
col1 = col2  （join，无索引）    : F = 1 / 10
p1 AND p2                       :  F = F(p1) × F(p2)      （独立假设）
p1 OR  p2                       :  F = F(p1)+F(p2) − F(p1)×F(p2)
```

对初学者，这些魔数最重要的不是记住数字，而是理解它们代表**"什么都不知道时的兜底猜测"**。等值谓词有索引时用 `1/ICARD` 是合理的——如果该列有 100 个不同值且假设均匀，等于某个值就命中 1/100；没索引连 ICARD 都不知道，就退到 `1/10` 这个纯拍脑袋的常数。范围谓词能拿到列的最大最小值时按线性比例算，拿不到就用 `1/3`。`AND` 直接把选择率相乘，背后是**属性独立假设**——这也是 04-7.4.6 要专门补救的头号误差来源（现实中列常相关，相乘会严重低估或高估）。现代引擎在有直方图/采样时会用更准的估计取代这些魔数，但当统计缺失或过期时，仍会退回到这类默认值兜底。

### 04-7.4.3 直方图：把值分布记下来，equi-width vs equi-depth

**直方图（histogram）**是比"单个平均选择率"精细得多的统计：它把一列的取值域切成若干桶，记下每个桶里大约有多少行，从而能回答"值落在某区间大概多少行"，尤其能处理**分布不均**（有热点值、有稀疏区）的列。两种经典切法：**等宽（equi-width）**——每个桶覆盖同样大的值区间（如 0-10、10-20…），桶间行数不等；**等深/等高（equi-depth / equi-height）**——每个桶覆盖同样多的行数，桶的值区间宽窄不等。

对初学者，等深直方图为什么更常用值得讲透。等宽直方图在数据倾斜时很糟：如果 90% 的行都挤在某个窄区间，那个桶会奇高、其余桶几乎空，估计精度在热点区反而差。等深直方图反过来——它让每个桶装等量的行，于是热点区会被切成很多个窄桶（精度高），稀疏区用一个宽桶带过（那里本来行少、不需精细），把统计"分辨率"自动分配到数据密集处。这也是 PostgreSQL 等主流引擎采用等深直方图的原因。实践中直方图常与一张**MCV（Most Common Values，最常见值）列表**配合：把少数超高频的热点值单独拎出来精确记其频率，剩下的"普通值"才交给直方图描述——这样热点值不会污染直方图桶、也能被精确估计。

### 04-7.4.4 采样：ANALYZE 如何"抽样看一眼"全表

统计不是把全表扫一遍精确统计（那太贵），而是**采样（sampling）**：随机抽一小部分行，从样本推断全表分布。触发方式通常是显式 `ANALYZE`（或自动统计收集）。样本大小决定统计精度与采集开销的折中——样本太小估不准，太大又慢。

PostgreSQL 是很好的落地样本（核实 2026-08-01，⚙版本相关）：它的采样目标由 `default_statistics_target` 控制，**默认 100**；采样行数约为

sample_rows ≈ 300 × statistics_target

即默认约 **30000 行**（300×100）。这个 `300×target` 的系数不是随手定的，其理论依据来自基于"要把直方图每个桶估到给定误差界所需的样本量"的分析（Chaudhuri–Motwani–Narasayya 1998 给出的样本量界）。对初学者的要点：其一，采样意味着统计**天生是近似**，且抽样有随机性——两次 ANALYZE 可能给出略有出入的直方图；其二，`statistics_target` 是**精度旋钮**——调大它，直方图桶数和 MCV 条数都增加、采样行数也增加，估计更准但 ANALYZE 更慢、优化器用的统计更占内存，是典型的"准确度换开销"。这个具体系数与默认值随版本可调，未逐版亲测者以官方文档为准（标「待核」）。

### 04-7.4.5 distinct 值估计与 sketch：HyperLogLog、Count-Min

"一列有多少个不同值（NDV，number of distinct values / n_distinct）"是估计里出了名难的量——它直接决定等值谓词的选择率 `1/NDV`，但从小样本外推全表 NDV 极易失准（样本里见到 k 个不同值，全表远不止 k 个，外推公式众多且都不完美）。为此工程上引入**概率性数据结构 sketch**：用很小的固定内存，对海量数据流给出高精度的近似统计。

两个初学者该认识的 sketch。**HyperLogLog（HLL）**估计**基数（不同值个数）**：靠观察哈希值的"前导零最大长度"等特征，用几 KB 内存就能把上亿量级的不同值个数估到个位数百分比的误差内，且可合并（各分片各算一个 HLL，合起来得全局 NDV）——非常适合分布式统计汇总。**Count-Min sketch** 估计**频率**（某个值大约出现多少次），用一个小的二维计数数组 + 多个哈希函数，代价是可能高估（永不低估）。对初学者，sketch 的共同卖点是"**用可控的小内存和一点可量化的误差，换在超大数据上也能算的统计**"。它们越来越多地被用在需要增量/分布式维护统计的场景（数据不断流入，不可能每次重扫全表）。这类实现细节属⚙演进快，各引擎是否用、用哪种 sketch 差异较大，具体以对应引擎文档为准。

### 04-7.4.6 属性独立假设与多列相关：优化器翻车重灾区

04-7.4.2 里 `AND` 的选择率直接相乘，背后是**属性独立假设（attribute value independence）**——假设不同列的取值互不相关。现实里这个假设经常严重失效，导致基数估计大错。经典反例：`WHERE city = 'Beijing' AND country = 'China'`——城市和国家高度相关（北京必在中国），真实选择率约等于单个 `city='Beijing'` 的选择率；但独立假设会把两个选择率相乘，得到一个**严重偏小**的估计，进而可能选出一个为"以为只有几行"而设计、实则要处理很多行的烂计划。

补救办法是**多列/扩展统计（multi-column / extended statistics）**：不再假设独立，而是显式采集列组合的相关信息。PostgreSQL 的 `CREATE STATISTICS`（⚙演进快·锚版本）提供三类：**函数依赖（functional dependencies）**——记录"一列的值能决定另一列"（如 city→country），从而修正 `AND` 相乘；**多列 n-distinct**——记录列组合的联合不同值个数（`(city,country)` 一起有多少种，而非各自相乘）；**多列 MCV**——记录列组合的最常见值及频率。对初学者，核心认知是：**独立假设是优化器为了省事做的强假设，它一旦不成立就是基数估计最大的系统性误差来源**；扩展统计是"人工/自动告诉优化器某些列其实相关"的补丁，但默认不开、要显式建，且只覆盖被显式声明的列组合。这也是实践中"某查询计划突然变烂"排查时的高频根因。

### 04-7.4.7 误差传播：估计错误如何沿计划树放大

单个谓词的选择率即便略有误差，一旦进入多层 join，误差会**逐层复合放大**。因为上层算子的输入基数是下层输出基数，下层估小了 2 倍、再 join 一层可能变成估小 4 倍、8 倍……到计划树高层可能偏差几个数量级，而 join order 的选择恰恰最依赖这些高层基数。这就是为什么"优化器越到复杂多表查询越容易翻车"。

对初学者，这条把前面所有统计努力的意义收口：直方图、采样、sketch、扩展统计，本质都是在**压低每一层的估计误差**，因为误差会在 join 链上指数式累积，源头省一点、终点省很多。也正因误差传播不可根除，现代引擎越来越多引入**执行期反馈/自适应**手段——运行时实测到某算子实际行数远超估计，就动态调整后续计划或下次优化时修正统计（如自适应执行、learned cardinality、执行反馈回灌统计）。这些属⚙演进快·随时变的前沿方向，成熟度与各引擎支持程度差异大，本报告只点到"存在这条'用真实执行数据补估计不准'的补救路线"，不下定论。

### 04-7.4.8 统计的维护：何时刷新、过期的代价

统计是**快照**——它反映 ANALYZE 那一刻的数据，之后数据不断增删改，统计会**过期（stale）**，优化器基于过期统计做的估计随之失真。所以统计需要**维护**：定期或按数据变化量重新采集。PostgreSQL 靠 autovacuum 的 auto-analyze，在表被修改的行数超过一定比例阈值时自动触发 ANALYZE（阈值参数化、⚙版本相关、具体默认值以官方文档为准，标「待核」）。

对初学者，几个实践要点。其一，**大批量导入/删除后统计往往严重过期**——刚灌进千万行、统计还停留在"空表"，优化器会以为表很小而选错计划，所以批量操作后手动 `ANALYZE` 是常识。其二，**统计维护本身有开销**（采样要读数据、占 CPU/IO），所以自动触发用阈值控制频率，不是每次写入都重算，这又是一个"新鲜度换开销"的折中。其三，规范与实现分账：这些触发阈值、采样系数、扩展统计能力都是**具体引擎的实现选择**且随版本演进（⚙演进快），Selinger 1979 定的是"用选择率+统计估基数"这个**原理框架**，而"每列存等深直方图+MCV、autovacuum 按阈值刷新、CREATE STATISTICS 补多列相关"这些是 PostgreSQL 一路演化出来的**实现**，读文档时要分清哪些是通用原理、哪些是本引擎特有。
