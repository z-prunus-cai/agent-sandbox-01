## 4.1 OLAP 与 OLTP 的引擎取向对比

### 4.1.1 OLTP 与 OLAP 是两类负载，不是两种产品

OLTP（On-Line Transaction Processing，联机事务处理）指业务系统里高频、短小的读写，比如"给账户 A 转 100 元给账户 B"——每条操作只碰极少数几行，但并发量巨大、要求低延迟和强事务保证。OLAP（On-Line Analytical Processing，联机分析处理）指从既有数据里"挖新信息"的分析查询，比如"过去三年每个大区每月的销售额同比"——单条查询要扫过海量行、做大量聚合，但并发数低、可以容忍秒级甚至分钟级延迟。

这两类负载对引擎的要求几乎处处相反，所以历史上逐渐分化出两套引擎设计，而不是一个产品两个模式。初学者最容易误解的是把 OLAP 当成"OLTP 数据库上跑复杂 SQL"——早期确实这么干（在业务库上直接跑报表），但分析查询会长时间占用资源、拖垮在线业务，于是才有了专门的分析型系统。理解本大主题的起点就是："分析引擎的每一个设计选择，都是为了服务'扫得多、算得狠、但可以慢一点、不用高并发'这种负载画像。"

### 4.1.2 三个对比维度：吞吐、延迟、数据规模

把两类负载放到三个维度上量化，取向差异就清楚了。

延迟维度：OLTP 追求单条事务的**低延迟**（毫秒级），OLAP 追求单条查询的**高扫描吞吐**（每秒处理多少 GB / 多少亿行），单条查询本身允许慢。

并发/吞吐维度：OLTP 是**高并发、每事务小**（每秒成千上万条短事务）；OLAP 是**低并发、每查询大**（同时可能只有几十条查询，但每条都很重）。

数据规模与访问模式维度：OLTP 每次只读写少量行、且几乎总是"整行"一起用，天然适合**行存**；OLAP 一次扫过大量行但只用其中少数几列（如只要 sales 和 region 两列做聚合），天然适合**列存**——只读需要的列，跳过其余，极大减少 I/O。


    OLTP = 少行 × 多列 × 高并发 × 低延迟 × 读写混合
    OLAP = 多行 × 少列 × 低并发 × 高吞吐 × 读为主

要注意这是"取向"而非"红线"。现代系统里两者边界在模糊：HTAP（混合事务分析）试图一套系统兼顾两者（留 04-11 讲）；很多分析引擎也支持一定的更新。但作为设计出发点，"OLAP 引擎为扫描吞吐而生、OLTP 引擎为事务延迟而生"这条心智模型贯穿后面所有大主题——列存、向量化、压缩编码都是 OLAP 侧的产物。

### 4.1.3 分析型系统的历史四代：从数据立方到湖仓

分析型系统的形态随硬件与云的演进走过四代，理解这条线能解释"为什么今天的架构长这样"。

1990 年代是**数据立方（Data Cube）**：在既有的面向行的业务库上，预先算好多维聚合的物化视图，定期刷新；维度要管理员提前指定，查询快但僵硬。2000 年代是**数据仓库（Data Warehouse）**：为 OLAP 专门造的单体系统，采用 shared-nothing 架构 + 列存，很多是 Postgres 的分支加上专有的编码/格式，靠 ETL（抽取-转换-加载）从业务库把数据搬进来。2010 年代是**shared-disk 引擎**：不再自建存储管理器，而是把数据放到第三方分布式存储（对象存储）上，存储和计算开始解耦。2020 年代是**湖仓（Lakehouse）**：给数据湖加上一层中间件，提供更好的 schema 管理/版本和事务性 CRUD——改动先写成面向行的日志结构文件，再定期压实成只读的列式文件。

湖仓这一代背后有三个观察值得记住：人们想在数据上跑的不只是 SQL，还有更过程化的代码（如机器学习）；把数据存储和 DBMS 解耦能降低数据进出的门槛；现实中大量数据是非结构化/半结构化的（图片、视频）。这四代不是简单替代，而是层层叠加的设计压力，正是它们把"存算分离 + 开放列式格式"推成了今天的主流骨架（详见 4.3）。

## 4.2 引擎分层设计空间：存储 / 执行 / 优化器各层的选择维度

### 4.2.1 一个 OLAP 引擎的组件拆解

现代分析引擎的一个核心观念是：**各层组件正在被拆成独立的服务与库**。一个引擎大致由这些可复用组件构成——系统目录（catalog）、中间表示（intermediate representation, IR）、查询优化器、文件格式、数据访问库、执行引擎。让这些组件既能互通又都高性能，本身就是一大工程挑战。

对初学者，先建立"引擎 = 一条从 SQL 文本到结果的流水线，流水线上每一段都是一个可替换的模块"的图景。把它们当成可拆装的积木，才能理解为什么今天会出现 DuckDB 用 Apache Arrow 做交换格式、多个引擎共用 Parquet 文件格式这种"组件跨系统复用"的现象——这正是"可组合数据管理系统（composable data management）"的思路：不再每家从头造整机，而是复用彼此的格式、IR 和执行库。

### 4.2.2 端到端流水线：前端 → 规划器 → 调度器 → 执行引擎 → I/O

把组件按数据流串起来，就是一条标准流水线，记住这条链是读懂后续所有大主题的骨架。

    用户 SQL
      → 前端 Front-end（语言解析器把 SQL 解析成中间表示 IR）
      → 规划器 Planner（binder 绑定 + rewriter 改写 + 优化器 optimizer + 代价模型 → 查询计划）
      → 调度器 Scheduler（把计划拆成 plan fragment，组织 worker 节点、安排执行）
      → 执行引擎 Execution Engine（执行各个 plan fragment）
      → I/O Service（向对象存储发块请求、取回数据）

贯穿全程的还有**目录 Catalog**：它记录数据位置和元数据，和除前端外的所有组件通信。

理解这条链时，抓住每一段的输入输出契约：前端只管"文本→IR"，规划器只管"IR→物理计划"，调度器只管"计划→可并行的碎片 + 派活"，执行引擎只管"跑碎片"。后面的大主题正是逐段深挖：04-2 是 I/O/存储层的列存格式，04-4/04-5 是执行引擎的两条加速路线（向量化 vs 编译），04-6 是执行引擎里的连接/聚合算子，04-7 是规划器里的优化器，04-8 是调度器的多核并行。本节给的就是把它们挂回去的那张总图。

### 4.2.3 存储层的选择维度：布局、格式、位置

存储层要回答三组正交的问题。**数据布局**：行存（NSM，整行连续）还是列存（DSM，同列连续）还是混合（PAX，块内按列、跨块分块）——OLAP 默认列式或 PAX。**文件格式**：自管的专有格式，还是开放格式（Parquet/ORC），后者能被多个引擎共读。**存储位置**：DBMS 自管的本地存储，还是外部对象存储（S3/Azure Blob/GCS）。

对初学者，关键是看出这三个维度是**可自由组合**的，不是绑死的一条路。比如"列式 + 开放 Parquet 格式 + 放对象存储"是典型云数仓组合；"列式 + 专有格式 + 本地盘"是经典单体数仓组合。一个反直觉但重要的点（来自 L01）：即使数据放进对象存储，单个文件内部通常仍用 **PAX** 布局——一个元组的所有列存在同一个文件里、但文件内按列分块，文件头/尾记录各列的偏移、压缩方案、索引和 zone map（区间统计）。引擎先读头/尾元数据，算出只需拉取哪段字节范围，从而在对象存储上也能做"只读需要的列 + 跳过无关数据块"。布局与编码的实现细节留 04-2，这里只需记住"存储层 = 布局 × 格式 × 位置三选一组合"。

### 4.2.4 执行层的选择维度：解释 vs 编译、逐元组 vs 批列、push vs pull

执行层决定"计划怎么被跑"，有三个关键分岔。第一是**解释执行 vs 编译执行**：解释器逐个算子解释计划（经典火山模型），或把计划编译成机器码消除解释开销——这是 04-4（向量化）与 04-5（编译）两大主题的分野。第二是**处理粒度**：一次一元组（火山模型 per-tuple），还是一次一批列（向量化，典型一批约上千行），后者把每元组的固定开销摊薄到一批上。第三是执行的**驱动方向**：pull（火山模型，上层算子向下"要"数据）还是 push（下层算子把数据"推"给上层）。

初学者不必在此纠缠机制，只要建立"同一份查询计划，可以用截然不同的执行策略去跑，性能差几倍到几十倍"的认识。这里也埋着分布式执行的一个取向对子：**push query to data**（把查询/部分查询送到数据所在节点，就地过滤再传结果）vs **pull data to query**（把数据搬到执行查询的节点）——前者省网络但要求数据端有算力，后者在"数据端无计算资源"（如纯对象存储）时是必需的。这个对子在 4.3 存算分离里会再次登场。

### 4.2.5 优化器层的选择维度：搜索框架与代价模型

优化器负责把逻辑计划变成"预计代价最低"的物理计划，它的两大设计维度是**搜索框架**和**代价模型**。搜索框架经典有两派：自底向上的动态规划（System R 风格，从小的连接子树逐步拼大）与自顶向下的规则驱动（Volcano/Cascades 风格，用变换规则在 memo 结构上探索等价计划）。代价模型则靠统计信息（基数估计、数据分布）给每个候选计划打分。

对初学者，优化器可以先理解成"一个在庞大计划空间里搜最优解的搜索引擎，代价模型是它的评分函数"。它为什么难、Cascades/memo 怎么实现、统计怎么维护，都是 04-7 的深水区，本节只需把它定位成流水线里"规划器"那一段的大脑，并记住"搜索框架 × 代价模型"是它的两个正交设计轴。分布式场景还会多一层：查询计划本质是**物理算子的有向无环图（DAG）**，每个算子都要决定输入从哪来、输出往哪送，数据分成"持久数据"（表，是记录源，现代系统假设文件不可变、要改就重写）和"中间数据"（算子间短命的临时产物，其量与读入的持久数据量或执行时长没有必然相关）。

## 4.3 存算分离与云原生 OLAP 架构

### 4.3.1 shared-nothing 与 shared-disk：两种系统架构的取向

一个分布式 DBMS 架构首先要定的是"持久数据文件放在哪、节点之间怎么协调"，历史上有两大范式。**Shared-Nothing（无共享）**：每个节点自带 CPU、内存和本地盘，数据被切成互不相交的子集分散到各节点，节点间只通过网络通信。因为数据在本地，可用 POSIX 文件 API 直接访问，天然支持 push-to-data、性能潜力高；但加新节点要在节点间**物理搬数据**，扩缩容重、慢。**Shared-Disk（共享磁盘）**：所有节点通过互连访问同一份逻辑存储（可各自另有私有内存和临时存储），节点仍需互相通信以了解彼此状态，访问存储走用户态 API 而非 POSIX。

shared-nothing 把"数据和算力绑在一起"，扩缩容要搬数据；shared-disk 把"数据和算力解耦"，两层能独立伸缩、空闲算力可随时关掉省钱。这正是云时代天平倒向 shared-disk 的根本原因——弹性。代价是 shared-disk 常常要先把数据从存储"拉"到计算侧才能过滤（不过并非绝对，配合下推可缓解）。L01 明确点出："shared-disk 是现代重点关注的架构。"

### 4.3.2 对象存储成为存储底座

shared-disk 的存储层早期是本地机房的 NAS（如 Oracle Exadata），如今主流已换成**云对象存储**（Amazon S3、Azure Blob、Google Cloud Storage），原因是近乎无限的可扩展性。数据组织方式是：把表切成大的**不可变文件**存进对象存储，文件内按 PAX 列式布局，头/尾放列偏移、压缩方案、索引、zone map 等元数据；每家云厂商用各自专有 API（GET / PUT / DELETE）访问。

要理解为什么对象存储适合当分析底座，抓住它的几个特性与代价的匹配：容量近乎无限且按量付费、持久性极高、多个计算集群能同时读同一份数据（天然的"shared-data"）。它的短板是**高延迟、只能整对象读写（不能原地改一行）**——但这恰好和 OLAP"大扫描、读为主、数据不可变、要改就重写整个文件"的画像吻合。文件不可变这个约束不是缺陷而是设计前提：它让缓存、并发读、版本/时间旅行都变简单。这也解释了 4.1.3 里"改动先写日志结构文件再压实成只读列文件"的湖仓做法——都是在绕开对象存储不能原地改写这一约束。

### 4.3.3 存算分离：把 shared-disk 推到极致的云原生架构

**存算分离（storage-compute separation / disaggregation）**是把 shared-disk 思想在云上做到底：持久数据只放在共享的对象存储层，计算完全无状态、按需拉起和关闭，两层各自独立伸缩、独立计费。这是当代云数仓的标志性架构。Snowflake 的 SIGMOD 2016 论文是这条路线的奠基性一手来源，它提出的架构常被概括为**多集群共享数据（multi-cluster, shared-data）**：一个共享存储层之上，跑多个互相隔离的计算集群（Snowflake 称"虚拟仓库 virtual warehouse"），它们读同一份数据但资源互不干扰。

为什么这件事重要，用一个初学者能懂的场景：白天报表和夜间 ETL 是两拨负载，存算分离下可以给它们各开一个虚拟仓库，互不抢资源；忙时给某个仓库临时扩容、闲时缩到零，只为存储和实际用掉的计算付费。Snowflake 论文给出的核心论断是——**真正的弹性要求存储与计算分离，shared-nothing 架构在云上无法优雅地扩容和升级**（因为它绑定了数据与算力，扩容要搬数据）。这句话点破了从 shared-nothing 数仓向存算分离云数仓迁移的根本动因。实践中这套架构常被分成三层理解：无状态的计算层（虚拟仓库）、共享的持久存储层（对象存储）、以及处理元数据/事务/优化/鉴权的云服务层。⚙演进快·锚版本：具体云数仓的分层命名与能力边界各家不同、迭代很快，本节只锚 Snowflake 2016 论文给出的原始架构骨架，现状细节以各系统官方文档为准（核实 2026-08-01）。

### 4.3.4 存算分离的取舍与"数据下推"的回归

存算分离不是免费的：把数据和算力拆开，意味着每次查询都可能要通过网络从对象存储把数据拉到计算层，网络和对象存储延迟成了新瓶颈。于是 4.2.4 的 **push vs pull** 对子在云架构里以新形式回归——纯对象存储没有算力，只能 pull data to query；为缓解，系统在计算侧加**本地 SSD/内存缓存**热数据，并在存储访问层做**谓词/投影下推**（只取需要的列、用 zone map 跳过无关数据块），尽量少拉数据。

初学者需要建立的权衡直觉是：存算分离换来了弹性和成本灵活性，代价是引入了"远程存储访问"这条慢路径，而整个云数仓工程的很大一部分，就是在用缓存、下推、文件内元数据（zone map / min-max 统计）去把这条慢路径的伤害压到最小。这也把本大主题和后面的列存/编码（04-2，让下推更有效）、向量化执行（04-4，让拉回来的数据算得快）串成了一条完整因果链：云架构选择存算分离 → 产生远程 I/O 瓶颈 → 逼出列式+下推+向量化这套组合拳。

## 4.4 代表系统的设计坐标定位

> 本节各系统的版本号、当前定位随生态快速演进，逐点标注核实日期并硬标 ⚙演进快·锚版本·随时变；未逐一实测的版本细目按来源如实标注、不编造。系统取向定位取自各自一手论文/官方口径，属稳定判断；具体版本号属易变项。

### 4.4.1 用几条设计轴给系统定位

在把具体系统钉到坐标上之前，先明确坐标轴——它们正是前三章的设计维度：部署形态（进程内嵌入 vs 客户端-服务器 vs 云托管服务）、系统架构（单机 vs shared-nothing vs 存算分离 shared-disk）、存储布局（行/列/PAX）、执行策略（解释/向量化/编译）、存储位置（本地 vs 对象存储）。

对初学者，这一步的价值在于把"系统名"翻译成"取向组合"。当你说得出"DuckDB = 进程内 + 单机 + 列式 + 向量化 + 本地文件"、"Snowflake = 云托管 + 存算分离 + 列式 + 对象存储"时，你就不再是在记品牌，而是在读架构。下面三个系统覆盖了设计空间里差异最大的三个角落：极简单机嵌入、开源 shared-nothing 高吞吐、云原生存算分离。

### 4.4.2 DuckDB：进程内嵌入式单机分析引擎

DuckDB 是一个**进程内（in-process）嵌入式** OLAP 引擎——它不是独立服务器，而是像 SQLite 那样作为库嵌进宿主应用（Python、R 等）同进程运行，省掉了客户端-服务器的进程间通信开销。设计取向是：列式存储 + 向量化执行（一次处理一批值、摊薄解释开销、吃 CPU 缓存和 SIMD），自带为批量优化的 MVCC 提供 ACID，数据可存成单文件；并原生支持 Apache Arrow 做数据交换、能直接读写 Parquet。它的一手论文是 Raasveldt & Mühleisen「DuckDB: an Embeddable Analytical Database」SIGMOD 2019。

DuckDB 占据的是"单机、嵌入、零运维"这个角落——它不追求分布式和弹性，而是把"在你的笔记本/一个进程里，对本地或远端文件跑快分析"做到极致，被称为"分析界的 SQLite"。它验证了 4.2/4.3 讲的组件复用趋势：用 Arrow 当交换格式、直接消费 Parquet，正是"可组合"理念的活样本。⚙演进快·锚版本：DuckDB 于 2024 年发布 1.0 稳定版；二手来源（生态月报/教程，核实 2026-08-01）称当前稳定线在 1.3.x（如 1.3.2），确切最新版本号属易变项、标「待核」，以官方 https://duckdb.org 发布页为准。

### 4.4.3 ClickHouse：开源 shared-nothing 高吞吐列存引擎

ClickHouse 是面向"万亿行、数百列"表的开源列式 OLAP 数据库，取向是高吞吐、高摄入、低延迟的实时分析。核心架构要素：列式存储（每列独立成文件、独立压缩，查询只读涉及的列）、**MergeTree** 系列表引擎（按主键排序数据、用稀疏主索引的"marks"在读盘前就跳过大块数据）、向量化执行引擎并可选**运行时代码编译**。它起家于 2009 年 Yandex 内部做 web 日志的过滤聚合算子，2016 年开源，一手论文是 Schulze et al.「ClickHouse - Lightning Fast Analytics for Everyone」PVLDB 17(12):3731-3744, 2024。

ClickHouse 站在"开源、可自托管、单集群 shared-nothing、为高吞吐摄入+扫描而生"这个角落，和 DuckDB 的"单机嵌入"、Snowflake 的"云托管弹性"形成三角。它的 MergeTree + 稀疏索引是"用文件内/块级统计做数据跳过"这一思想（4.3.4 的下推）的典型实现。论文里一个值得记的交叉结论：在其基准里，研究型系统 Umbra 拿到最好的热运行时，而 ClickHouse 在生产级系统中热/冷运行时都领先——注意这是论文自报基准、随版本和负载而变，不作绝对排名。⚙演进快·锚版本：ClickHouse 按日历号版本（形如 YY.M）高频发布，具体版本能力随时变，核实 2026-08-01，以官方 https://clickhouse.com/docs 为准。ClickHouse 亦在向存算分离/云形态演进（ClickHouse Cloud），该部分尤其 ⚙演进快·待核。

### 4.4.4 Snowflake：云原生存算分离数仓的范式样本

Snowflake 是**云托管**的分析型数仓服务，其架构是存算分离的教科书样本（4.3.3 已述）：共享的对象存储持久层 + 多个互相隔离的无状态计算集群（虚拟仓库）+ 处理元数据/事务/优化/鉴权的云服务层，即"多集群共享数据"。它提供 MVCC/快照隔离、时间旅行（time travel）、半结构化 SQL、数据跳过（pruning）、端到端安全、多可用区可用性等特性。一手来源是 Dageville et al. SIGMOD 2016 论文。

Snowflake 占据"云原生、极致弹性、按需付费、零运维"这个角落，是把 4.3 整章思想产品化的代表——用户看不到节点，只调虚拟仓库的档位；忙时扩、闲时缩，存储与计算分开计费。它和 DuckDB（单机嵌入）、ClickHouse（自托管 shared-nothing）三者放在一起，恰好把本大主题的三条主轴——部署形态、系统架构、弹性模型——的极端取向各占一角，构成一张可迁移到其它系统（Redshift、BigQuery、Databricks、StarRocks、Doris 等）的定位底图。⚙演进快·锚版本：Snowflake 是持续演进的托管服务、无传统版本号，本节只锚其 2016 论文确立的架构骨架，具体能力以官方文档为准，核实 2026-08-01。其它同类系统的坐标（细目）本库编排清单已标为待核，本报告仅给方法论与三个已一手锚定的样本，不对未逐一核实的系统编造取向。
