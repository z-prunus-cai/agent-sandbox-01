## C4.1 语法制导定义(SDD)

### C4.1.1 属性文法：给文法符号挂属性与语义规则

**语法制导定义（syntax-directed definition, SDD）**是在一个上下文无关文法之上做的扩充：给每个文法符号（终结符与非终结符）关联一组**属性（attribute）**，并给每条产生式关联一组**语义规则（semantic rule）**，规则说明如何用产生式中其它符号的属性算出某个符号的属性。带属性和语义规则的文法也叫**属性文法（attribute grammar）**。

属性是一个"名字 + 值"的信息槽，值可以是数、字符串、类型、内存位置、寄存器、指向某段代码或某棵子树的指针——凡是翻译过程需要沿树携带的信息都行。记号 `X.a` 表示符号 X 的属性 a。语义规则一般形如

X.a = f(⋯其它符号的属性⋯)

其中 f 是不含副作用的函数（纯 SDD 的理想形态）。

初学者可以这样理解"语法制导"四个字：翻译的每一步都被语法结构牵着走——不是另写一个独立程序去遍历源码，而是把"遇到这条产生式该算什么"直接钉在产生式旁边，分析器每认出一次这条产生式，对应的语义规则就该被触发一次。最小直觉例子：文法里

digit → 0 | 1 | ⋯ | 9

给 digit 挂一个属性 value，产生式 `digit → 7` 配语义规则 `digit.value = 7`，这样"7 这个字符"就带上了"数值 7"这个属性。整棵树的语义，就是无数这种小规则协同算出来的结果。要点是 SDD 只**声明**了"属性之间的等式关系"，并没有规定"先算谁后算谁"——求值顺序是 C4.3 要解决的问题。

### C4.1.2 综合属性：值自底向上流

**综合属性（synthesized attribute）**是这样一种属性：在分析树的节点 N 上，它的值由 **N 的子节点的属性**（以及 N 自身的属性）算出。也就是说综合属性的值沿着树**往上传**——从子节点汇聚到父节点。对产生式

A → X₁ X₂ ⋯ Xₙ

若给头部 A 定义综合属性，其语义规则形如

A.a = f(X₁.a₁, X₂.a₂, ⋯, Xₙ.aₙ)

综合属性是最自然、最常用的一类。直觉例子：算术表达式求值，`E → E₁ + T` 配规则

E.val = E₁.val + T.val

叶子（数字）的值由词法分析器给出，然后每个 `+`、`*` 节点把两个孩子的值加/乘起来往上报，根节点 E 的 val 就是整个表达式的值——信息像水一样从叶子往树根汇。为什么综合属性这么重要？因为它天然匹配"自底向上"的求值：只要先算完所有孩子，就能算父亲，而这正是 LR 分析器归约（reduce）的顺序（C4.2 会接上）。初学者记住一句话：**综合属性 = 孩子喂给父亲**。

### C4.1.3 继承属性：值自顶向下 / 自左向右流

**继承属性（inherited attribute）**是与综合属性方向相反的一类：在节点 N 上，它的值由 **N 的父节点、N 的兄弟节点、以及 N 自身**的属性算出。也就是信息**往下、往旁边传**——从父节点或左边的兄弟流到当前节点。对产生式

A → X₁ X₂ ⋯ Xₙ

给某个体部符号 Xₖ 定义继承属性，其语义规则形如

Xₖ.a = f(A 的属性, X₁ 的属性, ⋯, Xₖ₋₁ 的属性, ⋯)

继承属性用来把"上下文信息"送到树的更深处。经典例子是变量声明 `int x, y, z`：类型 `int` 出现在最左边，但它要"发"给右边每一个被声明的变量。龙书用的文法是

D → T L
T → int | float
L → L₁ , id | id

规则把 T 算出的类型作为**继承属性** L.inh 往下传给 L，再传给每个 id，于是 x、y、z 都拿到类型 int：

L.inh = T.type
（L → L₁ , id 时）L₁.inh = L.inh，并 addtype(id.entry, L.inh)

初学者的关键区分点：综合属性问"我的孩子们算出了什么，我汇总"；继承属性问"我的父亲/左邻居告诉了我什么上下文，我据此确定自己"。一个常见困惑是"为什么不都用综合属性"——因为有些信息（如声明的类型、外层的作用域、目标标签）天生在结构的"上方或左方"产生、却要在"下方"使用，逆着综合的方向，只能靠继承属性送过去。继承属性更强大，但也更难求值（不能简单地一趟自底向上做完），这正是下一节要区分 S-属性和 L-属性的动机。

### C4.1.4 注解分析树：把属性值填回树上

给定一棵分析树，把树上每个节点该有的属性都算出并标注上去，得到的树叫**注解分析树（annotated parse tree）**（或"带属性的分析树"）。它是 SDD 的"运行结果"的可视化：每个节点旁边写着它各个属性的具体值。

直觉上，SDD 是"规则模板"，注解分析树是"把某棵具体的树按模板填满数字"。比如对输入 `3 * 5 + 4`，先由语法分析得到分析树骨架，再按求值 SDD 把每个 E、T、F 节点的 val 填上，根节点标注 val = 19——这棵填满值的树就是注解分析树。

初学者要抓住的是：注解分析树只是**概念工具**，用来说明"属性应当满足哪些等式"。真实编译器几乎从不真的构造出完整的分析树再慢慢标注（太占内存、也没必要），而是像 C4.3.4 讲的那样"边分析边算属性"。但入门时先在纸上画注解分析树，是理解属性如何流动、依赖关系长什么样的最好办法。要注意注解分析树里的属性值是否"填得出来"、以什么顺序填，取决于属性间的依赖关系有没有环——这就引出 C4.3 的依赖图。

- 龙书 2nd ed. 2006 Ch.5 §5.1「Syntax-Directed Definitions」（章节级已核）：SDD 定义、属性、综合属性（§5.1.1，值取自子节点）、继承属性（§5.1.2，值取自父/兄弟/自身）、注解分析树（§5.1.2）、`digit`/声明 `D→TL` 传类型的继承属性例子。
- Stanford CS143 SDT 讲义（Handout 16 Summer 2012 / Handout 13 Summer 2008「Syntax Directed Translation」，https://web.stanford.edu/class/cs143/ ，PDF 正文核实 2026-07-25）：属性文法定义、`X.a` 记号、synthesized「passed up a parse tree，左侧属性由右侧算出」与 inherited「passed down a parse tree」定义、`digit`/`int` 与 Pascal 声明 `P→DS…` 传变量列表的例子——与龙书表述一致。

## C4.2 S-属性与 L-属性文法

### C4.2.1 S-属性 SDD：只有综合属性

一个 SDD 若它的**每一个属性都是综合属性**，就称为 **S-属性定义（S-attributed SDD）**（S 取 Synthesized）。这类 SDD 的属性值只往上传，不存在往下或往旁边的信息流。

S-属性 SDD 的巨大好处是**求值顺序极其简单**：只需对注解分析树做一次**自底向上的后序遍历（postorder）**——先算完所有孩子，再算父亲——所有属性就都能被算出，绝不会出现"算父亲时孩子还没算好"的窘境。表达式求值、计数、汇总这类"信息从叶子往根汇聚"的翻译，几乎都能写成 S-属性 SDD。

初学者的直觉：S-属性 = "纯汇总"。因为没有任何属性需要上下文往下送，整棵树可以像堆积木一样从底往上一层层算稳。它的意义在下一节会更清楚——后序遍历恰好就是 LR 分析器归约的顺序，所以 S-属性 SDD 能被 LR 分析器"顺便"在归约时求值，无需真的建出整棵树。易错点：不要以为"只有终结符有值、非终结符靠孩子"就一定是 S-属性——只要出现哪怕一个继承属性，就不再是 S-属性了。

### C4.2.2 L-属性 SDD：综合属性 + "受限的"继承属性

一个 SDD 称为 **L-属性定义（L-attributed SDD）**（L 取 Left），如果它的每个属性要么是综合属性，要么是**满足如下限制的继承属性**：对每条产生式

A → X₁ X₂ ⋯ Xₙ

体部符号 Xᵢ 的**继承属性**，其语义规则只允许使用以下这些属性：

（1）头部 A 的继承属性；
（2）位于 Xᵢ **左边**的符号 X₁, X₂, ⋯, Xᵢ₋₁ 的属性；
（3）Xᵢ **自身**的属性——但需不造成 Xᵢ 各属性之间的循环。

换句话说：继承属性只能依赖"来自上方（父的继承属性）"和"来自左方（左边兄弟）"的信息，**绝不能依赖右边兄弟**。综合属性不受此限（照常从孩子取）。

L-属性是介于"最好用但受限"的 S-属性 和"最一般但难求值"的任意 SDD 之间的一个甜点。为什么卡"只能往左看"这条线？因为这样一来，属性就能在**沿树深度优先、从左到右**遍历的一趟中被算出：走到 Xᵢ 时，它左边的兄弟都已经处理过、父亲的继承属性也早已备好，正好够算 Xᵢ 的继承属性。所有 S-属性 SDD 都自动是 L-属性的（因为它根本没有继承属性）。易错点：判断 L-属性时，逐条产生式检查每个继承属性的规则右边"有没有引用到它右边的符号"——只要引用了右边兄弟，就破坏了 L-属性。C4.1.3 那个传类型的声明例子（类型从左往右发）正是 L-属性的典型。

### C4.2.3 与 LR / LL 分析配合的求值序

这两类 SDD 之所以被单独拎出来，是因为它们能**贴着真实分析器一趟求值**，不必先建整棵树。

S-属性 SDD 天然配合**自底向上（LR）分析**。LR 分析器在**归约**一条产生式时，其体部符号的属性都已备好（它们对应的子树已被识别），此时执行该产生式的语义规则、把综合属性算好压回分析栈即可。求值顺序 = 归约顺序 = 后序。工程上这就是 Yacc/Bison 里"动作写在产生式末尾、用 `$$` 表头部属性、`$1 $2 …` 表体部属性"的模型。

L-属性 SDD 天然配合**自顶向下（LL / 递归下降）分析**。递归下降沿着树做深度优先、从左到右的遍历：进入一个非终结符对应的函数时，把它的继承属性作为**函数参数**传进去（对应"来自上方/左方"的依赖），返回时把综合属性作为**返回值**送出去。因为 L-属性保证继承属性只依赖左边已处理过的部分，这趟遍历刚好能把一切算出。

初学者可用一句话记住配对：**S-属性 ↔ LR ↔ 归约时求值（动作在末尾）；L-属性 ↔ LL ↔ 递归下降传参/返回。** 一个重要的进阶事实（此处只指路、不纵深）：L-属性 SDD 也能改造后在 LR 分析中求值（借助"标记非终结符"在产生式中间插入动作），但受限较多；而任意含"往右看"的继承属性的 SDD 一般**无法**边分析边求值，只能先建树、再按依赖图找顺序（见 C4.3）。这解释了为什么实际语言的语义规约总是尽量写成 L-属性甚至 S-属性——为的就是能和分析器合成一趟、省掉建整棵树的开销。

#### 来源与时效

- 龙书 2nd ed. 2006 Ch.5 §5.1.1「S-Attributed Definitions」：S-属性=全综合属性，可由自底向上后序遍历求值。§5.2.4「L-Attributed Definitions」：L-属性的三条限制（依赖父的继承属性 / 左侧兄弟 / 自身且不成环）。§5.4「Syntax-Directed Translation Schemes」与 §5.5：S-属性配 LR、L-属性配 LL/递归下降的求值实现。
- Stanford CS143 SDT 讲义（同上，核实 2026-07-25）：明确 S-attributed「every attribute is synthesized，可由单趟 bottom-up (postorder) 遍历求值」、L-attributed「每个属性要么综合、要么继承自 parent 或 from the left」；并给出 top-down（递归下降传参）与 bottom-up 两种 SDT 实现方式，与龙书一致。
- 冲突项：无。两源对 S-/L-属性定义与"S↔LR、L↔LL"的配合关系表述一致。

## C4.3 语义规则求值序

### C4.3.1 依赖图：属性之间"谁依赖谁"的图

对一棵具体的分析树，把树上每一个**属性实例**画成一个节点，若某条语义规则用属性 b 去算属性 c（即 c 的规则里出现了 b），就画一条**有向边 b → c**（读作"c 依赖 b，b 必须先算"）。这张图叫**依赖图（dependency graph）**。

依赖图把 SDD 那些"声明式的等式"翻译成了"计算的先后约束"。综合属性的边从子节点属性指向父节点属性（自底向上）；继承属性的边从父/左兄弟属性指向当前节点属性。举例：对 `E → E₁ + T { E.val = E₁.val + T.val }`，依赖图里有两条边

E₁.val → E.val
T.val   → E.val

表示"E.val 要等 E₁.val 和 T.val 都算好"。

初学者要抓住的是：依赖图是"对某棵具体分析树"画的，不是对文法画的——同一个 SDD，输入不同、树不同，依赖图也不同。它的作用是把"求值顺序"这个问题，转化成一个纯粹的图论问题：任何合法的求值顺序，必须让每条边的起点先于终点被算。

### C4.3.2 拓扑序：任何合法求值顺序都是依赖图的拓扑排序

给定依赖图，一个**合法的属性求值顺序**必须满足"沿每条边，源属性先于目标属性求值"。满足这个条件的节点线性排列，正是图论里的**拓扑排序（topological sort）**。因此：SDD 在某棵树上的求值顺序 = 该树依赖图的一个拓扑序。

直觉：拓扑序就是"把有先后依赖的一堆任务排成不违反任何一条依赖的队列"。做菜要先切菜再下锅，依赖图记录了所有这类"先…才能…"，拓扑排序给出一条能把菜做出来的完整步骤。对属性而言，只要按某个拓扑序逐个套用语义规则，每算一个属性时它依赖的属性都已就绪。

初学者常见疑问："拓扑序不唯一，选哪个？"——任意一个合法拓扑序都能得到正确结果（因为规则是纯函数，先后无关紧要，只要满足依赖）。S-属性 SDD 的后序遍历、L-属性 SDD 的深度优先从左到右遍历，本质上都是"预先知道一定合法的一种固定拓扑序"，所以它们不用真的去跑拓扑排序算法。

### C4.3.3 无环是可求值的前提：循环依赖 = 无解

拓扑序存在，当且仅当依赖图是**有向无环图（DAG）**。如果依赖图里出现了**环（cycle）**，就意味着一组属性互相循环依赖（a 要先有 b、b 又要先有 a），没有任何求值顺序能满足，这个 SDD 在该输入上**无法求值**。

直觉上环就是"死锁"：切菜要先洗菜、洗菜又要先切菜，永远开不了工。所以一个良定义的翻译，其 SDD 必须保证对任何输入树，依赖图都无环。

初学者需要知道两点实用结论。其一，"给定任意 SDD，判断它是否对所有可能输入都无环"这个一般性问题是**指数级代价**的（龙书指出判定 SDD 是否循环需要指数时间），所以实践中不去做这种一般判定。其二，正因为一般判定太贵，人们改用**充分条件**来省事：只要把 SDD 写成 S-属性或 L-属性，就**保证**任何输入的依赖图都无环、且有现成的固定求值顺序（后序 / 深度优先从左到右）。这就是 C4.2 那两个受限类别的根本价值——用"限制表达力"换来"无需检查环、直接一趟求值"。

### C4.3.4 边分析边翻译 vs 先建树后遍历

求值属性有两种落地策略。**先建树后遍历**：语法分析先构造出完整的（分析树或 AST），再对这棵树按某个拓扑序（可能真的跑一次拓扑排序，或对 S-/L-属性用固定遍历）算属性。这种方式最通用，能处理任意无环 SDD。**边分析边翻译（on-the-fly / 与分析交织）**：不单独建整棵树，而是在分析器识别结构的同时就地执行语义动作、算属性——S-属性搭 LR 在归约时算、L-属性搭 LL 在递归下降中传参/返回时算（见 C4.2.3）。

初学者的取舍直觉：边分析边翻译**省内存、少一趟**，但只适用于 S-属性 / L-属性这类能与分析顺序对齐的 SDD；一旦语义计算需要"往右看"或需要多趟（比如先收集全局信息再回头生成代码），就只能先建树、多次遍历。真实的工业编译器（如 clang）通常**先建 AST**，再在 AST 上做多趟语义分析和代码生成——因为类型检查、优化等需要反复、全局地访问这棵树，一趟到底的边分析边翻译不够用。所以"边翻译"多见于教学小译器和简单场景，"先建 AST 再多趟"是现代编译器的主流工程选择。这也顺势引出 C4.4：那棵被反复利用的树，通常不是臃肿的分析树，而是精炼的 AST。

## C4.4 AST 构建与翻译方案(SDT)

### C4.4.1 AST vs 分析树：抽象语法树是分析树的"精简版"

**分析树（parse tree，又称具体语法树 concrete syntax tree）**忠实记录了推导的每一步：每个内部节点是一个非终结符，孩子是产生式体部的每一个符号，连为消解优先级/结合性而引入的辅助非终结符（如 E、T、F）和标点都在树上。**抽象语法树（abstract syntax tree, AST）**则是它的精简形态：**运算符和关键字成为内部节点**，它们的**操作数成为孩子**，那些只为语法而存在的中间非终结符、括号、分号等一律省去。

对比 `3 * 5 + 4`：分析树里会有一长串 E→E+T、T→T*F、F→digit 的层层嵌套节点；而它的 AST 只有三个"实质"节点——一个 `+`，左孩子是 `3*5` 对应的 `*` 节点，右孩子是 `4`：

```
    (+)
   /   \
 (*)    4
 / \
3   5
```

初学者要抓住"抽象"二字的含义：AST 丢掉的是"怎么按文法一步步推出来的"这类语法细节，保留的是"程序到底表达了什么结构"这类语义要点。为什么编译器后端要用 AST 而不是分析树？因为分析树里 E/T/F 这类节点纯粹是为了在文法层面表达优先级，语义分析、类型检查、代码生成根本不关心它们——AST 把它们压掉后，树更小、遍历更快、结构更贴近语义。易错点：AST 里**不需要**靠额外节点表达优先级，优先级已经"固化"在树的形状里了（上面 `*` 是 `+` 的孩子，就代表乘法先算）。

### C4.4.2 用 SDD 构建 AST：给每个节点造一个树节点

构造 AST 本身就是一个用 SDD 完成的经典翻译：给每个文法符号一个**综合属性 node**（指向它对应的 AST 子树的根），语义规则调用两个构造函数——`new Node(op, c₁, c₂, …)` 造一个带运算符 op 和若干孩子的内部节点、`new Leaf(op, val)` 造一个叶子节点——把孩子的 node 拼成父亲的 node。表达式文法的核心规则形如

E → E₁ + T   { E.node = new Node('+', E₁.node, T.node) }
E → T        { E.node = T.node }
T → ( E )    { T.node = E.node }
F → id       { F.node = new Leaf(id, id.entry) }
F → num      { F.node = new Leaf(num, num.val) }

注意 `T → ( E )` 的规则是 `T.node = E.node`——括号本身**不建节点**，只是把里面表达式的树原样传上来，这正是 AST"丢弃纯语法符号"的体现。

初学者可以把这套规则想成"自底向上拼积木"：每个叶子先造好自己的小节点，每条运算符产生式把已经造好的两棵子树接到一个新运算符节点下，一路往上拼，根节点的 node 就是整棵 AST 的根。因为 node 全是综合属性（只从孩子取），这是个 **S-属性 SDD**，可以在 LR 分析器归约时顺手建出来——这就是为什么用 Bison 写编译器时，产生式动作里最常见的就是 `$$ = mknode(...)` 这类建 AST 节点的代码。

### C4.4.3 翻译方案(SDT)：把语义动作直接嵌进产生式体

**语法制导翻译方案（syntax-directed translation scheme, SDT）**是 SDD 的一种**过程式实现**：把语义动作（一段程序片段，用花括号 `{ }` 括起）直接**写进产生式的体部**，位置可以在体部的任意位置（末尾、中间、开头）。动作在分析器"扫描到它所处的那个位置"时被执行。

SDD 与 SDT 的区别在于抽象层次：SDD 是**声明式**的——只说"属性之间满足什么等式"，不说何时算；SDT 是**命令式**的——明确规定"分析到这里，就执行这段代码"。可以把 SDT 看作"给 SDD 定了一个具体的求值时机与顺序"。例如把中缀转后缀的翻译写成 SDT：

expr → expr₁ + term { print('+') }
expr → expr₁ - term { print('-') }
term → 0            { print('0') }

分析器每归约一条产生式就执行相应的 print，输出的就是后缀式。

初学者的关键认识：SDT 是编译器实际"跑"的东西。SDD 帮你想清楚"语义规则该是什么"，SDT 帮你落实"这些规则在分析过程中的哪一刻触发"。Yacc/Bison 的 `.y` 文件本质上就是 SDT——产生式加花括号动作。易错点：SDT 里动作的**位置至关重要**——同一段动作放在体部末尾还是中间，执行时机完全不同，会影响它能看到哪些属性是否已算好，下一节专门讲放置规则。

### C4.4.4 动作放置：后缀 SDT 与 L-属性 SDT 两种安全套路

动作往哪儿放不是随意的，要保证动作执行时它用到的属性都已备妥。两个"一定安全"的套路对应 C4.2 的两类 SDD：

**后缀翻译方案（postfix SDT）**——把所有动作放在产生式**体部的最末尾**。这适用于 **S-属性 SDD**：因为综合属性要等孩子都算完，把动作放最后、在归约整条产生式时执行，正好孩子都就绪。后缀 SDT 能直接在 LR 分析器归约时执行，最省事。

**L-属性 SDT**——把动作放在产生式体部的**恰当中间位置**。这适用于 **L-属性 SDD**：计算某符号继承属性的动作，要放在**该符号出现之前**（这样轮到分析这个符号时，它的继承属性已算好、可作参数传入）；计算综合属性的动作放在相关符号之后。这套 SDT 能在递归下降 / LL 分析中一趟执行。

一个动作放错位置的经典翻车：若某动作要用符号 X 的属性，却被放在了 X **前面**，那么执行到这个动作时 X 还没被分析、它的属性还不存在——动作拿到的是垃圾值。所以放置规则的核心就一句：**动作用到的属性，必须在动作执行之前就已经被算出。** 初学者只要守住"S-属性就把动作全放末尾（后缀）、L-属性就把算继承属性的动作放对应符号之前"这两条安全线，绝大多数翻译方案就不会因时机错乱而出错。在 LR 分析器里，在产生式**中间**插入动作还会带来额外复杂性（需引入标记非终结符，可能引入冲突），这也是工程上偏好后缀 SDT / S-属性的又一原因。

### C4.4.5 实证：clang -ast-dump 看一棵真实 AST

用本机 clang/LLVM 18.1.3 打印一段 C 代码的真实 AST，直观印证 C4.4.1 的"AST 结构固化了优先级、丢弃纯语法节点"。源文件（基线 @2026-07-25）：

```c
int f(int a, int b) {
  return a + b * 2;
}
```

命令 `clang -Xclang -ast-dump -fsyntax-only foo.c`，摘录 `f` 函数体部分真实输出：

```
`-FunctionDecl <foo.c:1:1, line:3:1> line:1:5 f 'int (int, int)'
  |-ParmVarDecl <col:7, col:11> col:11 used a 'int'
  |-ParmVarDecl <col:14, col:18> col:18 used b 'int'
  `-CompoundStmt <col:21, line:3:1>
    `-ReturnStmt <line:2:3, col:18>
      `-BinaryOperator <col:10, col:18> 'int' '+'
        |-ImplicitCastExpr <col:10> 'int' <LValueToRValue>
        | `-DeclRefExpr <col:10> 'int' lvalue ParmVar 'a' 'int'
        `-BinaryOperator <col:14, col:18> 'int' '*'
          |-ImplicitCastExpr <col:14> 'int' <LValueToRValue>
          | `-DeclRefExpr <col:14> 'int' lvalue ParmVar 'b' 'int'
          `-IntegerLiteral <col:18> 'int' 2
```

看三点。其一，`a + b * 2` 的 AST 里，`+`（外层 `BinaryOperator '+'`）的右孩子是 `*`（内层 `BinaryOperator '*'`）——乘法节点嵌在加法节点下面，**优先级被固化成了树的形状**，没有任何 E/T/F 之类纯语法节点，正是 C4.4.1 说的"AST 丢弃辅助非终结符、用结构表达优先级"。其二，节点上已挂了属性：每个 `BinaryOperator`/`DeclRefExpr` 都标了类型 `'int'`——这正是语义分析往 AST 上填的综合/继承属性（类型信息），呼应 C4.1 的"属性挂在节点上"。其三，clang 甚至已插入了 `ImplicitCastExpr <LValueToRValue>` 这种隐式转换节点——说明真实编译器是"先建 AST、再在其上多趟加注/变形"（C4.3.4 的主流策略），而非边分析边一次算完。

这条实证给初学者的校准：教材里手画的三节点小 AST，和工业编译器的 AST 是同一回事，只是后者节点类型更细（区分声明、语句、表达式、隐式转换等）、且每个节点挂满了类型等属性。AST + 属性，正是 C4 整章机制在真实编译器里的落地形态。
