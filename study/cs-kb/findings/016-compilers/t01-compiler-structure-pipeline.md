本报告有一条贯穿始终的心智模型，**编译器是一条把「源程序文本」逐级变形、最终产出「等价目标代码」的流水线；每个阶段吃上一阶段的输出、吐一个更接近机器的中间形式，越往后离人类语言越远、离机器越近。** 前半程（分析/前端）只关心「读懂源程序说了什么」，把文本嚼成一个结构化的中间表示；后半程（综合/后端）只关心「用目标机的话把这份意思复述出来」。这条流水线之所以能被切成一段段，是因为每一段的职责边界清晰、接口（上一段的输出格式）明确——正是这种模块化让编译器可编写、可测试、可换后端。整个大主题就是先讲清这条流水线的六个逻辑阶段与前后端分界（C1.1），再讲「逻辑阶段」与工程上真实跑几趟（物理趟）的分离、以及贯穿全程的两个「竖向」构件（C1.2），接着用龙书 Ch.2 那个「中缀→后缀」小译器把词法+分析+翻译一次性走一遍缩影（C1.3），最后跳出单个编译器、看它嵌在预处理器/汇编器/链接器/加载器构成的语言处理系统里，以及编译器 vs 解释器 vs JIT 的定位（C1.4）。

## C1.1 分析-综合模型与阶段划分

### C1.1.1 分析（前端）与综合（后端）：编译的两个半场

龙书把编译过程分成两大部分。**分析（analysis）部分**读入源程序，检查它在词法、语法、语义上是否合法，并把它拆解、组织成一个结构化的**中间表示（intermediate representation, IR）**，同时把收集到的名字信息填进符号表；分析部分若发现源程序不合法（拼写错、括号不配对、类型不匹配），就在这里报错。**综合（synthesis）部分**接过这份中间表示和符号表，据此构造出目标程序。工程上习惯把分析部分叫**前端（front end）**、综合部分叫**后端（back end）**。

分析与综合的分界，直觉上就是「先读懂，再复述」。前端只关心源语言——它把「一段 C 文本」理解成一棵结构化的语法/语义树，这个过程完全不需要知道目标机是 x86 还是 ARM。后端只关心目标机——它拿着那份与源语言无关的中间表示，翻译成具体机器的指令，这个过程也基本不用回头看源代码长什么样。这种「以 IR 为腰、前后端各管一头」的设计带来一个巨大的工程红利，叫**可移植性/可重用性**：m 种源语言 + n 种目标机，理论上只需要 m 个前端 + n 个后端（都对接同一份 IR），而不是 m×n 个完整编译器——这正是 GCC、LLVM 能支持大量语言与架构组合的结构性原因。初学者要抓住的分界线是「前端依赖源语言、后端依赖目标机，IR 是二者之间与两头都解耦的中间语言」。

### C1.1.2 六个阶段：词法→语法→语义→中间代码→优化→目标代码

龙书 §1.2 把编译器进一步细分为一串**阶段（phase）**，每个阶段把源程序的一种表示转换成另一种表示。经典的六个阶段依次是：

词法分析 → 语法分析 → 语义分析 → 中间代码生成 → 机器无关优化 → 目标代码生成

它们的职责边界如下。**词法分析（lexical analysis / scanning）**把字符流切成一个个**记号（token）**，如把 `position = initial + rate * 60` 切成标识符、赋值号、加号、数字等记号，并丢弃空白与注释。**语法分析（syntax analysis / parsing）**按文法把记号流组织成一棵反映语法结构的**语法树/分析树**。**语义分析（semantic analysis）**检查语法树是否符合语言的语义规则（类型是否匹配、变量是否声明、数组下标是否为整数等），并做必要的类型转换标注。**中间代码生成（intermediate code generation）**把语法树翻译成一种独立于机器、便于优化的低级中间表示（如三地址码）。**机器无关代码优化（machine-independent optimization）**在中间表示上做等价变换，让代码更快/更小（如删冗余计算）。**目标代码生成（code generation）**把优化后的中间表示翻译成目标机的汇编或机器码，并做寄存器分配等。

初学者可以顺着一句话 `position = initial + rate * 60` 想象这条流水线：词法阶段把它变成一串记号（相当于把句子切成单词）；语法阶段把这些记号搭成一棵「赋值语句」的树（相当于分析句子的主谓宾结构）；语义阶段发现 `60` 是整数、而 `rate` 是浮点，于是插入一个「整数转浮点」的动作（相当于检查这句话逻辑上讲不讲得通）；中间代码阶段把树压平成几条「一次只做一个运算」的三地址指令；优化阶段把 `rate * 60` 这类能提前算或能简化的地方处理掉；目标代码阶段最后把这些指令变成真正的机器指令并分配寄存器。前三个阶段属于前端（分析），后面属于后端（综合），中间代码生成是二者的接缝。要点是**这六个是「逻辑阶段」，不等于程序真跑几趟**——真实编译器可能把相邻阶段合在一趟里做，见 C1.2。

### C1.1.3 阶段之间流动的数据：从字符流到目标码的表示逐级下降

把六个阶段串起来看，真正在流水线上流动、逐级变形的是「源程序的一系列表示」。字符流经词法阶段变成**记号流**；记号流经语法阶段变成**语法树**；语法树经语义阶段变成**带注解的语法树**（挂上类型等信息）；再经中间代码阶段变成**中间表示**（如三地址码）；优化阶段产出**优化后的中间表示**；目标代码阶段产出**目标机代码**。每一步的输出就是下一步的输入，抽象层次单调下降——越往后，信息越贴近机器、越远离源文本。

初学者理解这条链的关键是「每个阶段只认得自己的输入格式，不必知道更早的文本长什么样」。比如目标代码生成器面对的是三地址码，它根本不需要回头看源程序里的空格和注释——那些早在词法阶段就被丢掉了。这种「表示逐级下降、接口固定」正是流水线能拆分的前提：只要接口（记号流、语法树、IR 的格式）说定了，各阶段就能独立开发和替换。一个常见误解是以为「优化」是可有可无的旁支——其实它是流水线上正规的一环（吃 IR、吐 IR），只是它是**可选强度**的（`-O0` 基本跳过、`-O2/-O3` 做得多），下节 C1.1.4 会点明它在真实编译器里的位置。

### C1.1.4 实证：编译流水线在 gcc/clang 里的真实阶段

龙书的六阶段是**逻辑模型**；真实编译器驱动（driver）看到的阶段更贴近工程分工。本机 clang/LLVM 18.1.3 用 `clang -ccc-print-phases` 打印它对一个 C 文件规划的阶段（源文件 `foo.c` 仅含一个 `add` 函数，基线 @2026-07-25）：

```
0: input, "foo.c", c
1: preprocessor, {0}, cpp-output
2: compiler, {1}, ir
3: backend, {2}, assembler
4: assembler, {3}, object
```

可以看到 clang 把工作分成：预处理（preprocessor）→ 编译到 IR（compiler，产出 LLVM IR，对应龙书的词法+语法+语义+中间代码生成）→ 后端（backend，IR→汇编，对应优化+目标代码生成）→ 汇编（assembler，汇编→目标文件）。龙书六阶段里的「优化」并不单列成一个 driver 阶段，而是折叠在 compiler/backend 内部按 `-O` 等级开关。

这条实证给初学者两点校准。其一，**逻辑阶段 ≠ 驱动阶段 ≠ 物理趟**：龙书讲的是概念上的六个转换，clang 的 driver 报的是它调度的可执行子任务，二者是同一件事的不同粒度视角，别指望一一对应。其二，真实编译从来不是「compiler 一个程序干完所有事」——预处理、汇编、（下一步的）链接往往是分开的子程序。至于「机器无关优化」这一环在这里被吸收进 compiler/backend、不单独露头，正说明龙书的阶段是教学用的逻辑切分。

## C1.2 遍数与逻辑阶段 vs 物理趟

### C1.2.1 阶段（phase）与趟（pass）的分离：逻辑职责 vs 物理扫描次数

**阶段（phase）**是按职责划分的逻辑步骤（词法、语法、语义……）；**趟（pass）**是工程上对程序表示的一次完整读入-处理-输出。二者不必一一对应：一趟可以完成多个阶段，一个阶段有时也可能跨多趟。龙书 §1.2 明确指出，若干阶段可以被组合进一趟里实现；把哪些阶段放进同一趟，是实现者的工程选择。

初学者最容易犯的错，就是把「六个阶段」直接理解成「程序要从头到尾扫六遍」。其实「阶段」讲的是**做哪几件事**（逻辑分工），「趟」讲的是**把源程序（或其某种表示）完整过几遍**（物理扫描）。一个直观类比：批改一叠试卷，「阶段」是「先核对姓名、再判选择题、再判大题」这三种工作；「趟」是「我把整叠卷子翻几遍」——你完全可以一遍就把三件事同时干完（一趟多阶段），也可以为了省心分三遍各干一件（多趟）。所以「几个阶段」和「几趟」是两个独立的问题。

### C1.2.2 单遍与多遍编译器：一次读完 vs 反复扫描

**单遍（single-pass / one-pass）编译器**只把源程序完整扫描一遍，边扫边分析边生成代码，中途不回头。**多遍（multi-pass）编译器**把编译分成若干趟，每趟读入上一趟产出的某种中间表示、做一部分工作、再写出给下一趟。经典的教学例子是 Pascal 被设计成便于单遍编译（要求「先声明后使用」正是为此），而现代优化编译器几乎都是多遍的。

两者的取舍很直白。单遍**快、省内存**（不用把整个程序的中间结构都存下来），但**能力受限**：它在读到某处时，还没见过后面的代码，做不了需要「全局视野」的事——比如引用一个定义在文件更后面的函数或变量、或做跨越整个函数的优化。多遍则相反：把整个程序读进内存、构造出完整的语法树/IR，就能自由地前后查看、反复变换，因而能做复杂优化和处理前向引用，代价是更慢、更耗内存。初学者记住这条因果链：**要做全局分析/优化、要支持前向引用，就得多遍；只求快速一次性翻译，可用单遍。** 一个常见误解是「单遍就是只有一个阶段」——不对，单遍编译器照样有词法/语法/语义/生成这些逻辑阶段，只是把它们揉进同一次扫描里流水地做。

### C1.2.3 符号表：贯穿所有阶段的「名字账本」

**符号表（symbol table）**是一个把程序里的**名字（标识符）**映射到它们的**属性**（类型、作用域、存储位置、参数信息等）的数据结构。它不属于某一个阶段，而是被几乎所有阶段共同读写的**贯穿件（cross-cutting component）**：词法/语法阶段在遇到声明时把名字记进去，语义阶段查它做类型检查，中间代码与目标代码阶段查它确定变量的类型和地址。龙书把符号表和错误处理一起画在流水线**侧面**，用双向箭头连到每个阶段，以强调它「竖着穿过整条流水线」的地位。

初学者可以把符号表想成编译器随身带的一个「名字账本」：每当程序里声明一个变量或函数，就在账本上记一行「这个名字是什么类型、在哪个作用域、占几个字节、放在哪」；后面任何阶段用到这个名字，都翻账本查它的信息。为什么它不能塞进某一个阶段？因为「同一个名字」的信息在不同阶段被反复需要——声明时登记（前端）、用到时核对类型（语义）、生成代码时算地址（后端），这些跨越了多个阶段，只有一个共享的账本才能把它们串起来。理解这一点，就明白了为什么「阶段」的线性流水图不足以描述编译器——符号表是横在流水线之上的一根轴。（符号表的具体组织、嵌套作用域实现归大主题 C5，本篇只定位它「贯穿全程」的角色。）

### C1.2.4 错误处理：同样贯穿全程的报错与恢复

**错误处理（error handling / error recovery）**和符号表一样是贯穿件：每个阶段都可能发现错误并需要报告，且理想情况下不应一遇到第一个错误就崩溃退出，而应尽量**恢复**、继续处理以便一次编译尽可能多地报出错误。不同阶段发现的是不同层次的错误——词法阶段报非法字符/记号，语法阶段报括号不配对/语句结构错，语义阶段报类型不匹配/未声明变量，等等。

直觉上，错误处理之所以必须贯穿全程，是因为「哪种错在哪个阶段才看得出来」是天然分层的：字符层面的错，词法阶段就撞上；而「把字符串加到整数上」这种错，要到语义阶段做类型检查时才暴露。所以没有哪一个阶段能独揽报错。对初学者更实在的一点是理解「错误恢复」的价值：如果编译器碰到第一个语法错就停，你改一个错编译一次、再撞下一个错，效率极低；好的编译器会「跳过出错的片段、猜一个合理的续点，继续往下分析」，从而一次报出一批错误（代价是可能产生一些「假错」级联）。这解释了为什么同一段错代码，不同编译器报出的错误条数和措辞会差别很大——错误恢复策略不同。（具体恢复策略如 panic-mode 归大主题 C3，本篇只定位它是贯穿件。）

## C1.3 语法制导翻译器缩影（龙书 Ch.2 中缀→后缀小译器）

### C1.3.1 麻雀虽小的完整译器：一次走完词法+分析+翻译

龙书 Ch.2 用一个「把中缀算术表达式翻译成后缀表达式」的小程序，把前端的完整流程浓缩演示一遍。**中缀（infix）**是运算符写在两个操作数中间的日常写法，**后缀（postfix，又称逆波兰）**是运算符写在操作数之后的写法。这个小译器读入一个中缀表达式、输出等价的后缀表达式，麻雀虽小地包含了「词法分析（切记号）+ 语法分析（按文法识别结构）+ 语法制导翻译（边分析边生成输出）」这三件事，是理解整条前端流水线的最短样例。

举一个最小例子，输入与输出的对应是：

9 - 5 + 2   （中缀）  →   9 5 - 2 +   （后缀）

给初学者的定位是：**这一章不是讲某个孤立技术，而是把「一个编译器前端从头到尾长什么样」缩到一页纸让你先建立整体感**，后面的 C2/C3/C4 再把其中的词法、语法、翻译分别放大讲透。之所以选「中缀→后缀」，是因为它足够小（不涉及类型、优化、目标机），又足够典型（有记号、有文法、有翻译动作），学完能一眼看清「文本进、结构化输出出」的骨架。后缀表达式的好处顺带也预告了后续内容——它无需括号就能无歧义地表示运算顺序，天然适合用栈来求值，这正是它常被当作中间形式的原因。

### C1.3.2 语法制导翻译（SDT）：把翻译动作挂在文法规则上

**语法制导翻译（syntax-directed translation, SDT）**是这个小译器的核心思想：先用一个**上下文无关文法**描述输入的语法结构，再给文法的每条**产生式**附上一段**语义动作（semantic action）**，规定「当分析器按这条规则识别出一段结构时，该做什么（比如输出一个记号）」。翻译就随着语法分析的进程被「制导」着一并完成——分析走到哪、动作就触发到哪。

对「表达式加减」的部分，可以用带动作的产生式表达（花括号里是识别到该结构时执行的动作）：

expr → expr₁ + term   { print('+') }

expr → expr₁ - term   { print('-') }

expr → term

term → 0 | 1 | ... | 9   { print(该数字) }

直觉是「文法负责认结构，动作负责顺手干活」。以 `9 - 5` 为例：分析器先识别出 `9` 是一个 term，触发 `print(9)` 输出 `9`；再识别出 `5` 是 term，输出 `5`；最后识别出整体是 `expr - term`，触发 `print('-')` 输出 `-`——拼起来正是后缀 `9 5 -`。关键在于**动作的执行顺序由分析顺序决定**：数字在被归约成 term 时就先输出，而运算符要等两个操作数所在的更大结构被识别后才输出，于是自然得到「操作数在前、运算符在后」的后缀顺序。这就是「语法制导」四个字的含义——翻译被语法分析的节奏牵着走。初学者不必此刻深究 SDT 的形式理论（那是大主题 C4），只要先建立「文法 + 挂在规则上的动作 = 边分析边翻译」这个直觉即可。

### C1.3.3 小译器里的词法分析器：把字符流切成记号

小译器的**词法分析器（lexical analyzer）**负责把输入的字符流转成一串记号，供语法分析器消费。它逐字符读入，跳过空白，把连续的数字识别成一个「数字记号」，把 `+ - * /` 等识别成运算符记号，并（在龙书 Ch.2 的扩展版本里）为多位数、标识符等赋予记号种类和属性值。它是流水线的第一道，把「无结构的字符」升级成「有种类的记号」。

给初学者的落点是理解「为什么要先有词法这一层，而不让语法分析器直接读字符」。因为让语法分析直接面对字符会非常繁琐——它得反复处理空白、拼多位数、区分是运算符还是数字的一部分。词法分析器先把这些琐碎的、只需局部就能判断的事处理掉，把干净的记号流交给语法分析器，让后者专注于「结构」这件更难的事。这是一种典型的**关注点分离**：词法管「单词」，语法管「句子结构」。在这个小译器里你能亲眼看到这条分工——词法器一次吐一个记号，语法器按文法一个个消费它们。（词法分析的完整机制——正则、NFA/DFA、最长匹配——归大主题 C2，此处只用其最简形态。）

### C1.3.4 缩影的意义：从这一章看到整本书的地图

这个小译器的价值不在译器本身，而在它**预演了整条编译流水线的骨架**：字符流经词法器变记号流、记号流经语法分析被识别成结构、结构被语法制导的动作翻译成输出。龙书 Ch.2 之后的每一章，本质上都是把这里某个被简化的环节放大做深——Ch.3 把词法分析做成正则/自动机的系统方法，Ch.4 把语法分析做成 LL/LR 的系统方法，Ch.5 把语法制导翻译做成属性文法与 AST 构建，Ch.6 及以后进入中间代码、优化、目标代码。

对初学者，这一章是整本书最该先读懂的「地图」。它的作用是：在你还没学会任何一个阶段的正规算法之前，先让你握住「输入怎样一步步变成输出」的全局脉络，这样后面学每个孤立技术时，你都知道它嵌在流水线的哪一节、上游给它什么、它该交给下游什么。缺了这张地图，后续章节容易学成一堆互不相干的算法碎片。记住这条对应关系——**Ch.2 的小译器 = 整个前端的迷你原型**，就抓住了本小主题的全部意图。

## C1.4 语言处理系统与工具

### C1.4.1 语言处理系统全景：预处理器→编译器→汇编器→链接器→加载器

一个能真正跑起来的程序，通常不是「编译器一个工具」造出来的，而是一条**语言处理系统（language-processing system）**流水线协作的结果。龙书 §1.1 给出的经典链条是：

源程序 → 预处理器 → 编译器 → 汇编器 → 链接器 → 加载器 → 内存中运行的程序

各工具职责如下。**预处理器（preprocessor）**在编译前做文本级处理，如展开宏、处理 `#include` 把头文件内容插进来、处理条件编译。**编译器（compiler）**把（预处理后的）源程序翻译成目标机的**汇编代码**（或直接机器码）。**汇编器（assembler）**把汇编代码翻译成**可重定位机器代码（relocatable object file）**。**链接器（linker）**把多个可重定位目标文件以及库文件合并、解析彼此的符号引用（把「调用某函数」的地方连到该函数的真实定义），产出一个完整的可执行文件。**加载器（loader）**在运行时把可执行文件读入内存、做地址重定位、启动执行。

初学者可以顺着 C 程序从 `.c` 到能跑的过程对上号：预处理器把 `#include <stdio.h>` 和宏展开掉，编译器把展开后的 C 变成汇编 `.s`，汇编器把 `.s` 变成 `.o`（目标文件），链接器把你的 `.o` 和 C 标准库连成一个可执行文件（比如 `a.out`），加载器（操作系统的一部分）在你敲下运行命令时把它搬进内存开跑。关键的认知升级是：**「编译」在日常口语里常指这一整条链，但严格说编译器只是其中一环**——它前面有预处理、后面有汇编和链接。理解这条链，才明白为什么会遇到「编译通过但链接报错（undefined reference）」这类现象：那是链接器阶段找不到某个函数定义，和编译器阶段的语法/类型错误完全是两回事。

### C1.4.2 链接与加载的分工：为什么要把「合并」单独拆出来

**链接器**存在的根本原因是**分离编译（separate compilation）**：大程序被拆成多个源文件分别编译成各自的目标文件，还会用到预先编译好的库；每个目标文件里都可能引用别的文件里定义的函数或全局变量，这些跨文件的引用在单独编译时是「悬空」的（只知道名字、不知道地址）。链接器的工作就是把这些目标文件和库拼在一起、把每一处外部引用**解析（resolve）**到对应的定义、并做**重定位（relocation）**（因为多个模块合并后各自的地址要重新安排）。**加载器**则负责运行期把最终镜像放进内存、设好运行地址。

直觉上，链接器像「把几份分开写的稿子装订成一本书，并把每处『见第几页』的交叉引用都填上正确页码」。为什么非要单独拆出链接这一步？因为分离编译能带来巨大好处：改动一个源文件只需重编它自己、再重新链接，不必重编整个项目；公共库可以编译一次、被无数程序共享。代价就是需要一个专门的工具来「事后把碎片拼起来并接好线」——这就是链接器。初学者常把「编译错误」和「链接错误」混为一谈，其实前者发生在单个文件被编译时（语法/类型问题），后者发生在多个文件被合并时（找不到定义、重复定义），分属流水线不同环节。（链接器/加载器的地址空间与重定位细节承 L3-03 汇编与机器级，本篇只讲编译器视角的定位。）

### C1.4.3 实证：gcc 驱动如何调度各阶段子程序

`gcc` 命令本身是一个**驱动程序（driver）**，它按需依次调用真正干活的子程序。本机 gcc 13.3.0 用 `gcc -v` 观察对一个 C 文件从源码到可执行的驱动调用（基线 @2026-07-25），关键子程序依次是：

cc1  （编译器本体：C 源 → 汇编 .s）

as   （汇编器：汇编 .s → 目标文件 .o）

collect2 → ld  （链接器：.o + 库 → 可执行文件）

即 `gcc` 先调用 `/usr/libexec/gcc/.../cc1` 把 C 编译成汇编，再调用 `as` 汇编成目标文件，最后调用 `collect2`（它进一步调用 `ld`）完成链接。（预处理在 gcc 中默认由 cc1 集成完成，不再单独 fork 一个 `cpp` 进程；本机实证的 `-c` 只编译不链接时确实只见到 cc1 与 as，加上链接目标时才出现 collect2→ld。）

这条实证给初学者的落点，是把 C1.4.1 那条抽象链条落到了真实命令上：你敲的 `gcc foo.c`，背后 gcc 这个「包工头」把活分包给了 cc1（编译）、as（汇编）、ld（链接）这几个「工人」。这解释了几个平时的现象——`gcc -E` 只做预处理、`gcc -S` 停在汇编（只调 cc1）、`gcc -c` 停在目标文件（调 cc1+as、不调 ld）、不带这些开关才走完到链接。看懂 driver 的分包，也就看懂了为什么 undefined reference 之类的错来自 `ld` 而非 cc1。

### C1.4.4 编译器 vs 解释器 vs JIT：三种执行源程序的方式

处理源程序有三条不同路线。**编译器（compiler）**把整个源程序**提前**翻译成目标机代码，之后运行的是这份目标代码，源程序本身运行时不再参与；典型是 C/C++/Rust。**解释器（interpreter）**不产出独立的目标程序，而是**直接逐条读源程序（或其字节码）并当场执行**，边读边算；典型是早期 Python/Shell 的纯解释模式。**JIT（just-in-time，即时编译）**是混合路线：程序先被编译成一种中间字节码，运行时由虚拟机解释执行，同时把**热点（频繁执行）**的代码段在运行期动态编译成本地机器码以提速；典型是 Java 的 JVM（HotSpot）、JavaScript 的 V8。

龙书用一个对比点出编译与解释的取舍：**编译器产出的目标程序通常运行更快，解释器则通常能给出更好的错误诊断（因为它逐句执行，出错时对源程序的位置信息更精确）**。直觉上，编译像「先把外文书整本翻译成中文再读」——翻译一次、之后读得快；解释像「找个同声传译边听边译」——不用等整本翻完就能开始，但每句都要现场译、整体慢。JIT 则像「先大致同传，遇到反复出现的段落就临时把它精翻下来贴着用」——兼顾启动快与热点快。初学者需要破除的两个误解：其一，「编译型/解释型」不是语言的固有属性而是**实现方式**——同一门语言可以有编译器也可以有解释器（如 C 也有解释器、Python 也有编译到机器码的实现）。其二，JIT 不是「第三种孤立东西」，而是编译与解释的**结合**：用解释保证快速启动和可移植，用运行期编译换取热点性能，这正是现代托管语言（Java/C#/JavaScript）主流的执行模型。
