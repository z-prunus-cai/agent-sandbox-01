## C8.1 目标机模型与设计问题

### C8.1.1 代码生成器的任务与三个核心子问题

目标代码生成器（code generator）是编译器后端的最后一环：输入是（已优化的）中间表示加上符号表信息，输出是目标机器的代码。龙书把它的核心难点拆成三个必须解决且相互影响的子问题——**指令选择（instruction selection）**、**寄存器分配（register allocation）**、**指令排序/调度（instruction ordering / scheduling）**。代码生成器还必须满足两条硬约束：产出的代码必须**正确**（语义等价于源程序），并且尽量**高质量**（快、短）。正确性因为约束多而不可让步，质量则是一个在合理时间内尽量逼近的目标。

对初学者，最重要的直觉是"为什么这一步这么难、值得单独讲"。前面几阶段（词法、语法、语义、中间代码）本质上是把源程序**逐层规整**成越来越干净的结构；到了目标代码生成，问题的性质变了——它要在一个资源受限（寄存器只有十几个）、指令种类繁多（同一个加法可能有七八种编码）、且各种选择互相打架的空间里做**组合优化**。理论上求全局最优是 NP 难的，所以真实编译器用的是一套启发式：把大问题切成"选指令 / 分寄存器 / 排次序"三块分别用较成熟的算法攻克。记住这三块的名字，就抓住了整个 C8 的骨架。

### C8.1.2 目标机模型：一台用来教学的简化机器

要讨论代码生成就得先固定"往哪台机器上生成"。龙书用一台简化的**三地址、面向寄存器的 RISC 风格机器**做讲解载体：有 n 个通用寄存器 R0, R1, …，指令大体是"运算类"（形如 `op dst, src1, src2`）、"访存类"（LD 载入 / ST 存储）与"跳转类"。一条典型的加法指令形如

ADD R1, R2, R3    // R1 = R2 + R3

而访存分开成显式的 LD/ST，这正是 RISC 的"load/store 架构"特征。

为什么要用一台"假机器"而不是直接讲 x86？因为真实指令集（尤其 x86-64 这种 CISC）编码繁杂、特例极多，会把"代码生成的原理"淹没在细节里。龙书的简化机器保留了所有本质要素——寄存器有限、访存要显式指令、每条指令有代价——却剥掉了噪声，让指令选择、寄存器分配的算法能讲清楚。学的时候把它当成"最小可用 CPU"即可；等原理懂了，套到 x86-64 或 ARM 上只是把指令表换一换。本篇的实证部分用真实的 x86-64（System V ABI）来印证这些原理确实体现在 gcc 产物里。

### C8.1.3 寻址方式：操作数可以从哪里来

**寻址方式（addressing mode）**描述一条指令的操作数如何定位。龙书的教学机器给出一组典型寻址方式：寄存器寻址（操作数在寄存器里，如 `R2`）、立即数（常量本身，如 `#100`）、直接/绝对（内存变量名，如 `x`）、变址（`a(R)`，地址 = a 的值 + R 中的偏移，用于数组）、间接（`*R`、`*100(R)`，寄存器或内存里存的是地址）。不同寻址方式对应不同的机器代价，这是 C8.1.4 代价模型的基础。

寻址方式之所以关键，是因为它决定了"访问一个值要花多少代价"，从而直接影响指令选择和寄存器分配的收益。直觉例子：数组元素 `a[i]`，如果机器支持变址寻址，一条

LD R, a(Ri)    // R = contents(a + contents(Ri))

就能取到；若不支持，就得先算地址再间接取，多花指令。x86-64 把这一切做到极致——它的一条内存操作数可以写成 `disp(base, index, scale)`（如 `(%rdi,%rsi,4)` 表示 base+index×4），一条 `mov`/`add` 就内联了地址计算。本篇实证里 `lea (%rdi,%rsi,4),%rdx` 正是这种复合寻址：编译器用它把"基址 + 下标 × 元素宽度"折进一条指令，省掉单独的乘加。初学者容易忽视寻址方式，但它是"为什么某些 IR 能被一条指令实现、某些要两三条"的根源。

### C8.1.4 指令代价模型：给每条指令打分

代码生成器要在众多等价的指令序列里挑一个，就需要一把"标尺"。龙书用的**代价模型**是：一条指令的代价 = 1（取指令本身的固定开销）加上其**源操作数与目标操作数寻址方式带来的附加代价**。规则大致是——用寄存器或立即数作操作数附加代价为 0，凡是要访问内存（直接、变址、间接）附加代价为 1。于是一条指令的总代价写成

cost(instr) = 1 + (源操作数附加代价) + (目标操作数附加代价)

例如 `ADD R0, R0, R1`（全寄存器）代价为 1，而 `ADD R0, R0, M`（一个内存操作数）代价为 2，`MOV *R1, *R2`（两个间接）代价为 3。

这个代价模型是"教学用的粗略近似"，务必分账看待：它把指令代价简化成"长度/访存次数"，方便讲清"为什么把值留在寄存器里划算"（寄存器操作数不加钱，内存操作数每次 +1）。但真实机器上，一条指令的实际开销由流水线、缓存命中、乱序执行等因素决定，和这个静态代价差得很远——这正是 C8.4 指令调度要处理的另一个维度。初学者应把它理解为"衡量代码生成质量的一把简化尺子"，用来在指令选择/寄存器分配里做局部比较，而不是精确的时间预测。龙书对此有明确说明：找"代价最小"的代码本身是不可判定/NP 难的，代价模型只是让启发式有个可比较的目标。

### C8.1.5 其他设计问题：输入形式、目标程序形式与相位耦合

除了三大子问题，龙书还列出代码生成器面对的若干设计选择。**输入的形式**：中间代码可能是三地址码、树/DAG、或字节码，本篇假定输入是已做完机器无关优化的三地址码 + 符号表。**目标程序的形式**：可以是绝对机器码（直接可执行，位置固定）、可重定位机器码（可分模块编译再由链接器拼装，主流做法）、或汇编文本（再交汇编器，便于教学与调试，`gcc -S` 产的就是它）。此外还要处理运行时存储的映射——把变量名绑定到寄存器或活动记录中的栈偏移（承 C7）。

最需要初学者记住的一个"设计问题"是**相位耦合 / 相位排序（phase ordering / phase coupling）**：指令选择、寄存器分配、指令调度三者互相影响，谁先做都会限制后做者的选择空间。例如——先做寄存器分配再调度，分配器引入的复用会制造假依赖、限制调度自由度；反过来先调度再分配，又可能因为拉长了值的活跃区间而加剧寄存器压力。理论上三者应联合求解，但那是 NP 难的，所以真实编译器只能定一个顺序、分阶段做，并接受由此损失的一点最优性。理解这一点，就理解了为什么 C8 的三节看似独立、实则是一个被人为切开的整体，也为 C8.4 末尾的讨论埋下伏笔。

## C8.2 指令选择与树覆盖

### C8.2.1 指令选择是什么：从"朴素逐条翻译"说起

**指令选择（instruction selection）**是把中间表示里的每个操作映射到一条或一组目标机指令的过程。最朴素的做法是给每种三地址指令固定一个"代码模板"，逐条翻译。例如三地址码 `a = b + c` 用模板

LD  R1, b
LD  R2, c
ADD R1, R1, R2
ST  a, R1

逐条套。这种"模板拼接"实现简单、正确，但生成的代码往往冗长低效。

为什么朴素法不好，是理解指令选择价值的关键。逐条翻译看不到"相邻指令之间的机会"：上一条刚把 b 载入 R1，下一条又把它 ST 回内存、再 LD 出来，白白多了访存；也用不上机器提供的"一条顶多条"的复合指令（如变址寻址一次完成地址计算，或一条乘加指令）。直觉上，指令选择的目标是**用尽量少、尽量便宜的机器指令覆盖 IR 表达的计算**，而这要求算法能"往上看一小片 IR、匹配一条能吃掉这一片的指令"。这就引出了树覆盖。

### C8.2.2 树重写与树覆盖：用指令模式去"铺瓷砖"

一种系统化的指令选择方法是把 IR（尤其表达式）表示成**树**，把每条机器指令表示成一个**树模式（tree pattern / tile，瓷砖）**，指令选择就变成"用一组瓷砖把整棵 IR 树无重叠地盖满"——即**树覆盖 / 树铺砖（tree tiling）**，也叫**树重写（tree rewriting）**。每盖上一块瓷砖，就等于选定了一条指令；盖满全树，就得到实现这棵树的一串指令。

举个直觉：IR 树 `+(a, *(4, i))`（表示 `a + 4*i`）。如果机器有一条变址访存瓷砖能匹配"基址 + 下标×常数"这一整块子树，就能用一块瓷砖盖住 `*(4,i)` 连同上面的 `+`，对应一条变址指令；否则只能用"乘法瓷砖 + 加法瓷砖"两块分开盖，多一条指令。**每一种铺法都对应一个合法但代价不同的指令序列**，指令选择的任务就是从所有铺法里挑代价最小的那种。初学者可以把它想成拼图/贴瓷砖游戏：瓷砖的形状 = 指令能匹配的模式，铺法唯一确定一段代码，目标是用最省的瓷砖铺满。这个视角的好处是把"选指令"变成了一个有清晰结构、可用算法求解的问题。

### C8.2.3 基于代价的最优树覆盖：动态规划

当每块瓷砖（指令）带一个代价时，"铺满全树且总代价最小"这个问题在**树**上可以用**动态规划（dynamic programming）**在线性时间内求出最优解。思路是自底向上地为每个树节点计算"把以该节点为根的子树、且结果放到某类寄存器里，所需的最小代价"，父节点的最优代价由孩子的最优代价加上覆盖它的瓷砖代价组合得到。龙书给出的最优代码生成算法正是基于这种在树上的动态规划。

这里要点明一个重要的分账（也是常见的来源"看似冲突"处）：**在树上**，最优指令选择有多项式（DP）算法；但一旦 IR 是**DAG**（有公共子表达式、值被多处复用）或考虑寄存器数量约束，最优代码生成就变成 **NP 难**。所以"指令选择可最优"这句话只在"表达式树 + 无限寄存器"的理想设定下成立。初学者不必掌握 DP 的递推细节，但要记住这条边界：树能最优、DAG 一般不能，这也解释了为什么下一节要专门处理 DAG。DP 之所以在树上奏效，直觉是"子树之间不共享、互不影响"，最优子结构成立；DAG 里子表达式共享，一处的选择会牵动另一处，最优子结构被破坏。

### C8.2.4 用 DAG 表示基本块：暴露并复用公共子表达式

一个**基本块（basic block）**内的计算可以表示成**有向无环图（DAG）**：每个内部节点是一个运算，叶子是初始变量/常量值，同一个子表达式只画一个节点、被多处指向。DAG 把基本块里的**公共子表达式（common subexpression）**天然合并了——`a = b + c; d = b + c;` 里的 `b + c` 在 DAG 里只有一个节点，两次赋值共用它。指令选择/代码生成从 DAG 出发，就能复用已算出的值、少算一遍。

DAG 是连接指令选择与局部优化的枢纽。它的价值在于"看见复用"：树会把 `b+c` 画两遍、生成两次加法，DAG 只画一次、只生成一次加法，把结果留在寄存器供两处用。构造 DAG 时，对每个三地址指令查一张表——若相同运算 + 相同操作数节点已存在就复用，否则新建——这就顺手完成了公共子表达式消除（属 C9 局部优化，此处只用其结果）。代价是前面说的：从 DAG 生成最优代码是 NP 难的（尤其"以什么顺序求值各节点、如何最少用寄存器"），所以实际用启发式（如龙书的 DAG 重排启发式，C8.4 会接上）。初学者记住：树→易最优但看不见复用；DAG→看得见复用但最优化变难，这是一个典型的"表示能力换算法复杂度"的权衡。

### C8.2.5 指令选择的生成器化：BURS / 模式匹配工具一瞥

手写树覆盖的模式匹配又繁又易错，于是有了**指令选择生成器**：像 lex/yacc 之于词法/语法那样，用一套"树文法 + 每条规则的代价"来描述目标机指令，由工具自动生成做最优树覆盖的匹配器。这类技术统称 **BURS（Bottom-Up Rewrite System）**，代表工具有 BURG/iburg 等，它们在编译期用动态规划做最小代价铺砖。真实编译器（如 LLVM 后端）里的指令选择也是这一思想的工程化——LLVM 的 SelectionDAG 把 IR 降成 DAG 再做模式匹配选指令（⚙ 具体 pass 名与实现随 LLVM 版本演进，本机 LLVM 18.1.3，细节以官方后端文档为准，未逐一实证，标「待核」）。

对初学者，这一节的意义是"别以为指令选择要一台机器一台机器手写"。它和词法/语法分析一样走了"声明式描述 + 生成器"的路：你写一份"这台机器有哪些指令、各匹配什么树形状、各花多少钱"的规格，工具替你生成最优铺砖器。这也呼应 C8.1 的代价模型——正是因为每块瓷砖有明确代价，DP 才能在生成器内部自动选最省的铺法。把这条线记住即可，无需深入 BURS 的形式化。

## C8.3 寄存器分配（图着色）

### C8.3.1 寄存器分配问题与活跃性

**寄存器分配（register allocation）**要决定：程序里众多的值（临时变量、局部变量）如何分配到机器上数量有限的通用寄存器里；放不下的必须**溢出（spill）**到内存。它常被拆成两步——**寄存器分配（allocation）**决定哪些值在某时刻应驻留寄存器，**寄存器指派（assignment）**决定具体用哪个物理寄存器。核心前提是**活跃性分析（liveness）**：一个变量在某点"活跃"意味着它当前的值将来还会被用到；只有同时活跃的值才会争抢寄存器。

活跃性是理解寄存器分配的钥匙。直觉：如果两个变量的"活跃区间"不重叠——一个用完了另一个才开始用——它们完全可以共用同一个寄存器，就像两个人错峰用同一间会议室。反之，两个变量若在某一点同时活跃，就绝不能放进同一个寄存器（否则一个会覆盖另一个）。所以寄存器分配的本质是"在有限的房间里给一堆错峰/撞车的活跃区间排座位"。活跃性由数据流分析（活跃变量分析，属 C9 / L6-02）算出，这里直接拿来用：它告诉我们"哪两个值在打架"。

### C8.3.2 干扰图：把冲突关系画成图

把"哪两个值不能共享寄存器"这层关系画出来，就是**干扰图（interference graph）**：每个待分配的值（变量/临时/虚拟寄存器）是一个**节点**，若两个值在程序某点**同时活跃**（互相干扰、不能同寄存器），就在它们之间连一条**边**。于是"给值分配寄存器且互相冲突者不同寄存器"这个问题，精确地等价于"给图的节点着色、相邻节点不同色"——即经典的**图着色（graph coloring）**问题，颜色数 = 可用寄存器数 k。

这一步的美妙在于把工程问题化归成了一个纯图论问题，初学者可借地图/课表着色类比：干扰图的节点像国家，边像"接壤"，k 种颜色像 k 个寄存器，要求接壤国家不同色——这正是四色定理那类问题。构造干扰图的方法：沿基本块逆向扫描维护活跃集合，在每个定值点，把被定值的变量与当时所有其他活跃变量两两连边。最小例子：若变量 x、y、z 中 x 与 y 同时活跃、y 与 z 同时活跃、但 x 与 z 从不同时活跃，则图是一条路径 x—y—z，用 2 色（2 个寄存器）即可：x、z 同色，y 另一色。记住这个化归，C8.3.3 的算法就有了对象。

### C8.3.3 图着色分配：Kempe 化简启发式（Chaitin 与 Briggs）

图 k 着色本身是 NP 完全的，所以实际用**启发式**。经典的是 Chaitin 系列基于 **Kempe 化简（simplify）** 的方法：反复找一个**度数 < k**（邻居少于寄存器数）的节点，把它从图里移除并压入一个栈——因为度数 < k 意味着无论邻居怎么涂，总还剩一种颜色留给它。全部能移的都移完后，再从栈里逐个弹出节点、放回图中并**分配一个与当前邻居都不冲突的颜色（select）**。若化简过程中所有剩余节点度数都 ≥ k，就选一个节点标记为**潜在溢出（spill）**并移除，继续化简。

k 表示可用物理寄存器数，算法主循环可概括为

while 图非空:
    if 存在度数 < k 的节点 n:  simplify(n)   // 移除并压栈
    else:                      spill(m)      // 选一节点标记溢出并移除
然后依次 select（弹栈着色）

Chaitin（1981）与后来的 **Briggs 乐观着色（1994）** 有一处需分账的差别：Chaitin 在化简阶段一旦某节点度数 ≥ k 就将其**实际溢出**；Briggs 则**乐观地**先把它照样压栈，等到 select 弹栈时再看——很多时候它的邻居实际用到的颜色数 < k，仍能着上色，从而避免了一次不必要的溢出。也就是说 Chaitin 是"度数 ≥ k 即溢出"，Briggs 是"先压栈、着不上色时才真溢出"，后者通常生成更少溢出、更好的代码。初学者不必背两套流程，只需记住核心启发式（度数 < k 的点总能着色，故先移走留到最后处理）与"乐观压栈可少溢出"这一改进方向即可。

### C8.3.4 溢出：寄存器不够时把值赶回内存

当图无法用 k 色着色（着色阶段某节点找不到可用颜色），就必须**溢出（spilling）**：把某个值不常驻寄存器，而是放在栈帧的内存槽里，用到时临时 LD 进寄存器、改完 ST 回内存。生成的这些额外访存指令就是**溢出代码（spill code）**。溢出降低了寄存器压力（把一个节点从干扰图里"拆散"成多个短小区间），但代价是多了访存、程序变慢，所以选谁溢出很关键——通常挑"活跃区间长、使用次数少、或干扰度高"的值，即溢出收益/代价比最好的那个。

理解溢出，就理解了寄存器分配的现实约束。直觉：寄存器是一间只有 k 个座位的教室，学生（值）比座位多时，只能让一部分学生"每次要发言（使用）时才进来坐一下、发言完就出去"——进出就是 LD/ST 溢出代码。这解释了为什么优化编译器如此在意寄存器压力：每一次溢出都是实打实的内存往返。溢出后干扰图变了（被溢出的值不再整段占座），需要重建干扰图再着色，如此迭代直到成功着色——这就是 Chaitin 分配器"化简—溢出—重建—再着色"的迭代结构。初学者记住溢出是"塞不下时的兜底"，不是失败而是必要机制。

### C8.3.5 局部分配与实机对比：-O0 全溢出 vs -O2 常驻寄存器

图着色是**全局**（跨基本块、按函数）寄存器分配。作为对照，龙书也讲了一种**局部**的简单分配法——在单个基本块内，按"下次使用（next-use）"信息用一个 `getreg` 函数临时挑寄存器，够用则复用、不够则就近溢出。局部法实现简单但看不到跨块复用，质量不如全局图着色，是理解"为什么需要全局分配"的对照物。这里用真实 x86-64 产物把"分配 vs 不分配"的差异摆出来。

对下面这个求和函数（gcc 13.3.0，`-std=c11`，x86-64 System V ABI）

int sum(int *a, int n){ int s=0; for(int i=0;i<n;i++) s+=a[i]; return s; }

`gcc -O0 -S` 基本不做寄存器分配，几乎每个变量都住在栈上（内存），循环体每轮都要往返访存

movl	-4(%rbp), %eax     # 从栈载入 i
...
addl	%eax, -8(%rbp)     # s(在栈上) += a[i]
addl	$1, -4(%rbp)       # i(在栈上) += 1

而 `gcc -O2 -S` 做了全局分配，把累加器 s 常驻 `%eax`、遍历指针常驻 `%rdi`，循环体内**零访存于局部变量**（只剩对数组元素的必要读取），甚至连归纳变量 i 都被优化掉、改用指针比较

.L3:
	addl	(%rdi), %eax       # s(在 %eax) += *p
	addq	$4, %rdi           # p(在 %rdi) 前进一个 int
	cmpq	%rdx, %rdi
	jne	.L3

对照 `-O0` 每轮多条 LD/ST、`-O2` 把热变量钉在寄存器里，正是寄存器分配价值的实机印证——本机 gcc 13.3.0 实测（objdump 反汇编亦确认循环体仅 `add (%rdi),%eax` / `add $0x4,%rdi` / `cmp` / `jne` 四条）。初学者可自行 `gcc -O0 -S x.c` 与 `gcc -O2 -S x.c` 对比感受。注意这里 `-O2` 的提速是寄存器分配 + 归纳变量优化 + 强度削减共同作用，寄存器分配是其中把"局部变量搬离内存"的那一份。

## C8.4 指令调度与窥孔优化

### C8.4.1 表达式 DAG 与求值次序：先算哪棵子树省寄存器

在从表达式 DAG/树生成代码时，**求值次序（order of evaluation）**会影响需要多少寄存器与临时值。同一棵表达式树，先算左子树还是右子树、先算哪个操作数，会得到寄存器用量不同的指令序列。经典结果是 **Ershov 数（labeling / Sethi–Ullman 算法）**：给树的每个节点标一个数，表示"用最少寄存器求这棵子树所需的寄存器数"，叶子标 1，内部节点若两个孩子标号相等则标号 +1、否则取较大者；据此**先求标号大的那棵子树**，可使整棵表达式用最少寄存器求值。

这条规则背后的直觉是先啃"更费寄存器的那半边"，因为算它时另一半还没占用寄存器、手头宽裕；反过来先算简单的一边、把它的结果占着一个寄存器不放，再去算复杂的一边，就等于自缚手脚。最小例子：`(a+b) + (c+d)` 两个子树对称、各需 1 个寄存器算出中间值，按 Sethi–Ullman 标号根节点需 2 个寄存器；若表达式是 `a + ((b+c)+(d+e))`，右子树更"重"，先算右子树能省寄存器。对 DAG（有共享节点）而言，最优求值排序是 NP 难的，故用启发式重排（龙书 §8.4 的 DAG 重排）。初学者记住一句话：**先算复杂的子树**，能少用寄存器、少溢出。

### C8.4.2 指令调度：为流水线重排指令

**指令调度（instruction scheduling）**是在不改变程序语义的前提下，重排指令次序，让它们更好地喂饱现代 CPU 的**流水线**、减少因数据/资源冲突造成的停顿（stall）。典型算法是**表调度（list scheduling）**：在一个基本块内，先根据指令间的数据依赖建一个**依赖 DAG**（若指令 B 用了 A 产生的值，则 B 依赖 A，必须排在 A 后且要等 A 结果就绪），然后在满足依赖的前提下，按某种优先级（如关键路径长度）逐条挑选"就绪且最紧要"的指令排入，把互不依赖的指令错开、填补长延迟指令（如 load、除法）后的空档。

调度是"机器无关生成"与"机器相关性能"的交界，需分账并指路。它之所以有用，是因为现代 CPU 一条指令的结果往往不是下一拍就能用（load 要等缓存、乘除有多拍延迟），若紧跟着用就得停顿等待；调度器把不相关的指令塞进这些等待窗口，让流水线不空转。最小直觉：`x = load(p); y = x + 1; z = load(q); w = z + 1;` 若照原序，`y=x+1` 要等第一个 load，`w=z+1` 要等第二个 load，两次停顿；调度成 `load p; load q; y=x+1; w=z+1;` 让两个 load 先发、它们的延迟互相重叠，停顿更少。调度的具体收益强依赖目标微架构（流水线深度、发射宽度、乱序能力），深入的流水线/ILP 机制交 **L5-05 体系结构**，本篇只讲编译器"如何按依赖 DAG 重排"这一层。本机 `objdump -d` 里 gcc 在循环前插入的 `nopl` 是对齐/调度相关的填充，间接可见编译器对指令布局的干预。

### C8.4.3 窥孔优化：在小滑动窗口里就地打磨

**窥孔优化（peephole optimization）**是在已生成的目标（或中间）代码上，用一个小的**滑动窗口（peephole，通常几条相邻指令）**扫过去，把窗口内匹配到的低效模式替换成等价的更优模式的局部优化。它简单、快、效果显著，是代码生成的收尾打磨。龙书列出的经典窥孔变换有几类，逐一给例。

**冗余加载/存储消除**：刚 ST 到某地址、紧接着又 LD 回来的，第二条可省。本机实证——`int f(int*p){*p=5; return *p;}` 经 `gcc -O2 -S` 得

movl	$5, (%rdi)     # 存 5 到 *p
movl	$5, %eax       # 直接用常量 5 作返回值，未从 *p 重新载入

编译器认出"刚存进去的就是 5"，返回时不再从内存 reload，而是复用常量。

**代数化简与强度削减（strength reduction）**：把昂贵运算换成便宜的，如乘 2 的幂换成移位/LEA。实证——`int m(int x){return x*8;}` 经 `gcc -O2 -S` 得

leal	0(,%rdi,8),%eax    # 用 LEA 的比例寻址实现 ×8，避免乘法指令

**不可达/无用指令消除**：删掉跳转后永不执行的代码、删掉 `MOV R, R` 这类恒等指令。**控制流优化**：把"跳到一条跳转指令"的链路（jump-to-jump）拉直、把跳过一条无条件跳转的条件跳转反转合并。

窥孔优化对初学者最好上手，因为它就是"模式 → 替换"的查表替换，不需要全局分析，看几个例子就懂。要点是**窗口内的等价性**：每条替换规则必须在任何上下文下都语义等价（如冗余 load 消除的前提是两条指令间那个地址没被别人改过）。它常需要**反复多趟**：一次替换可能暴露新的可优化模式（如删掉一条指令后，另两条变得相邻可合并），所以窥孔器通常扫到不动点为止。它与 C9 的全局优化互补——全局优化管跨块的大账，窥孔管眼皮底下的小账。

### C8.4.4 基本块局部优化与相位耦合的收尾

把 C8 收束一下：目标代码生成里的"局部优化"主要发生在基本块 / DAG 层面——公共子表达式复用（DAG）、死代码剔除、求值重排（Sethi–Ullman）、指令调度、窥孔替换，都是在不跨越控制流边界的小范围里把代码打磨得更紧凑高效。它们与 C9 的全局（跨基本块、基于数据流）优化分工明确：局部优化便宜、见效快、是生成阶段的标配；全局优化更强大但更贵。

最后回扣 C8.1.5 的**相位耦合**：指令选择、寄存器分配、指令调度三者收益互相牵制，且各自都以"局部/启发式"求近似最优——这解释了为什么真实编译器要反复迭代、要在固定相位顺序里做取舍，也解释了为什么同一段 C 代码在 `-O0` 和 `-O2` 下产物差异如此之大（本篇 C8.3.5 已实测）。初学者到这里应形成一个完整闭环：中间代码进来 → 选指令（树/DAG 覆盖）→ 分寄存器（图着色，不够则溢出）→ 排次序并窥孔打磨（调度 + peephole）→ 汇编/可重定位目标码出去，全程被 C8.1 的代价模型与目标机模型这把标尺牵引。至此 C8"目标代码生成"的骨架完整。
