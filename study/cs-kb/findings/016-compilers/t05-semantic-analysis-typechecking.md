本报告有一条贯穿的心智模型，**语法分析证明了"这串记号在语法上排得对"，语义分析要进一步证明"这串记号在意义上讲得通"。** 讲不通的典型是：用了没声明的变量、把指针加到浮点数上、给只接收 3 个参数的函数传了 4 个、在需要布尔值的循环条件里写了个字符串。这些错误语法层面完全合法，必须靠语义分析在生成代码前抓出来。语义分析的两大支柱就是**符号表**（回答"这个名字是什么、在哪儿可见"）和**类型检查**（回答"这个操作对这些类型合法吗、结果是什么类型"）。

一处重要的边界（本报告显式指路、不纵深）：类型系统"**为什么可靠**"（well-typed 的程序不会在运行时卡住，即 progress + preservation 定理）以及 Hindley-Milner 类型**推导算法**（Algorithm W）的完整机制，根在 L5-06 编程语言理论 T3、T7。本篇只讲编译器工程上"**怎么查**"，不展开可靠性证明。

## C5.1 符号表与作用域

### C5.1.1 符号表：从名字到声明信息的映射

**符号表（symbol table）**是编译器维护的一张数据结构，把源程序里出现的每一个**名字（标识符）**映射到它的**声明信息**——类型、作用域、存储位置、是否可赋值、（对函数）参数个数与类型等。它是语义分析乃至整个编译过程的中枢：分析器一遇到声明就往表里"记一笔"，之后每用到这个名字，就回表里"查一笔"来核对用法是否合法。

符号表是贯穿编译器多个阶段的"贯穿件"（承 C1.2）——词法/语法阶段建条目，语义阶段填类型、查用法，代码生成阶段取存储位置。可以把它想成程序里所有名字的"户口本"：谁叫什么、是什么类型、住在哪个作用域、能不能被改写，全登记在案。最小直觉例子：读到 `int x = 3;` 时，编译器在符号表里新建一条 `x → {类型: int, 作用域: 当前块, 可赋值}`；之后读到 `x + 1` 就查表确认 x 已声明且是 int，读到 `y = ...` 而 y 不在表里就报"未声明"。

初学者要抓住的关键是，符号表回答的不是"这个名字长什么样"（那是词法的事），而是"这个名字**指代什么、在这里能不能用**"。为查得快，实现上通常用**哈希表**做名字到条目的映射。易错点：符号表里存的是"声明"而非"值"——它记录 x 的类型是 int、住在栈上第几个槽，但不记录 x 运行时到底等于几（那是运行期的事，编译期通常不知道）。

### C5.1.2 作用域与嵌套作用域：当前、开放与关闭作用域

**作用域（scope）**是源程序里由程序定界符（C 的 `{}`、Pascal 的 `begin-end`）括起的一段文本，一个名字的声明只在它所属的作用域（及其内部）里"可见"。很多语言允许**嵌套作用域（nested scope）**——作用域套作用域。由最内层单元定义的作用域叫**当前作用域（current scope）**；当前作用域及一切包住它的外层作用域叫**开放作用域（open scope）**；其余都是**关闭作用域（closed scope）**。

作用域的意义在于"名字复用"和"局部隔离"：不同函数里都能叫 `i` 而互不干扰，因为各自的 `i` 活在不同作用域里。判断"某处能否访问某名字"这件事叫**作用域检查（scope checking）**——只有声明在**当前作用域和包住它的开放作用域**里的名字才可访问；去访问另一个函数的局部变量（那是关闭作用域）应当报错。

初学者可以把开放作用域想成"此刻我站在最里层的房间，能看见的东西 = 本房间里的 + 一路往外每一层房间里的；隔壁那些没包住我的房间（关闭作用域）里的东西我看不见"。易错点：作用域是**静态的文本嵌套结构**（谁的花括号套在谁里面），跟程序运行时谁调用谁是两回事——后者引出 C5.1.6 的静态 vs 动态作用域之分。

### C5.1.3 名字解析与遮蔽：最近嵌套声明胜出

当同一个名字在多个开放作用域里都有声明时，**名字解析（name resolution）**采用**最近嵌套规则**：引用点看到的是**离它最近的那层**（最内层）声明，外层的同名声明被**遮蔽（shadowing）**。CS143 讲义的例子：

```
int a;
void Binky(int a) {
  int a;
  a = 2;
}
```

这里有三个 a（全局变量、参数、局部变量），`a = 2` 赋给的是最内层的局部变量，另外两个 a 被它遮蔽、在函数内无法访问。

直觉上遮蔽就是"近的挡住远的"：站在最里层房间，若本房间和外层房间都有一件叫 a 的东西，你伸手拿到的永远是本房间那件。名字解析就是编译器"顺着开放作用域从内往外找，找到的第一个就用"。

初学者要抓住的是，遮蔽是**特性不是 bug**——它让程序员在内层随意复用名字而不必担心撞上外层。但它也是常见的困惑与告警来源（很多编译器有 `-Wshadow` 提醒你内层变量遮蔽了外层）。易错点：遮蔽只是"外层名字暂时看不见"，不是"外层名字被销毁"——离开内层作用域后，外层同名声明重新可见。

### C5.1.4 组织方式一：作用域栈（每个作用域一张表）

第一种实现是**给每个作用域配一张独立的符号表**，把这些表组织成一个**作用域栈（scope stack）**：每进入一个新作用域就 new 一张表压栈，栈顶永远是当前作用域，往下依次是各外层开放作用域；离开作用域就把栈顶那张表弹出。查名字时**从栈顶往栈底逐层找**，第一个命中的就是最近嵌套声明；找到栈底还没有就报"未声明"。

这种组织天然实现了 C5.1.3 的最近嵌套规则——从栈顶往下找，第一个命中的必然来自最内层的开放作用域，遮蔽关系自动成立。它的一大优点（CS143 讲义指出）是每张表一旦建好就**不再变动**（immutable），程序更健壮。

初学者可以把作用域栈想成一摞卡片盒，每进一层房间就往上叠一个新盒子，查东西从最上面的盒子往下翻。易错点/代价：全局变量总在栈底，一个深层嵌套里频繁访问全局名字的程序，每次都要翻到栈底，查找会偏慢；且每作用域一张表也有内存开销。

### C5.1.5 组织方式二：单一全局表 + 作用域号

第二种实现是**只用一张全局符号表**，给每个作用域编一个**作用域号（scope number）**：进入新作用域时把计数器 +1，该作用域里声明的名字都打上这个号。同一个名字可以在表里出现多次，只要作用域号不同。用哈希表时，**新名字总是插到冲突链的表头**，于是同名多次声明时，链上第一个命中的就是最内层的那个（自动满足最近嵌套规则）。作用域关闭时，把带该作用域号的所有条目**删掉**，被遮蔽的外层名字随即重新可见。

这种组织省掉了"每作用域一张表"的开销，查找命中通常更直接。它和方式一的取舍正好相反：方式一"关闭作用域"很便宜（弹栈），但可能有多表开销与深层查全局慢的问题；方式二插入/查找快，但"关闭作用域"可能要扫描整张表删条目，偏贵。

初学者只要记住两种组织都在实现同一件事——**让名字解析遵守最近嵌套规则**，区别只在"用一摞小表"还是"用一张带标号的大表"、以及各自把开销花在了进作用域还是出作用域上。易错点：方式二里"新条目插到链表头"这个细节是最近嵌套规则能自动成立的关键，插错位置（插到链尾）就会解析到外层的旧声明。

### C5.1.6 静态作用域 vs 动态作用域

块结构语言有两种作用域规则。**静态作用域（static / lexical scoping）**：一个名字的非局部引用，按它在**源代码文本里的词法嵌套结构**去外层找——函数在"定义它的环境"里求名字。**动态作用域（dynamic scoping）**：按**运行时的调用栈**去找——函数在"调用它的环境"里求名字，即沿调用链往上找最近的同名变量。

静态作用域看"代码写在哪儿"（编译期就能定），动态作用域看"运行时谁调用了我"（要到运行时才定）。对 C、Decaf 这类**函数不能嵌套**的语言，这个区分意义不大（非局部名字只能是全局的）；但 Pascal（可嵌套函数）、早期 LISP 等允许非局部访问的语言就必须明确采用哪种。

初学者要抓住的是，几乎所有现代主流语言都用**静态作用域**——因为"看代码就能确定一个名字指谁"极大方便了阅读、优化和排错；动态作用域会让同一段代码在不同调用路径下引用到不同变量，难以推理。这也呼应 C5.1.2 强调的"作用域是静态文本结构"：那句话本身就是静态作用域的立场。（非局部数据在运行时靠什么访问——访问链/display——是运行时环境的话题，归 C7.2，本篇不展开。）

## C5.2 类型表达式与类型系统实现

### C5.2.1 类型是什么，与类型的三大类

一个**类型（type）**是"**一组值 + 作用在这些值上的一组操作**"。CS143 把语言里的类型分三类：**基本类型（base type）**——int、float、double、char、bool 等硬件直接提供的原子类型；**复合类型（compound type）**——数组、指针、记录/结构体、联合、类等由基本类型聚合而成的类型；**复杂类型/抽象数据类型（complex type / ADT）**——列表、栈、队列、树等更高层抽象（语言可有可无内建支持）。

"类型 = 值集 + 操作集"这个定义是理解一切类型规则的根。说 `int` 和 `bool` 不同，本质是它们的值集不同（整数 vs 真假）、能做的操作不同（int 能做算术、bool 能做逻辑与或）；说"不能把指针加到浮点数上"，本质是 `+` 这个操作没定义在"指针×浮点"这对值上。

初学者要抓住的是，类型检查归根结底是在核对"**这个操作是否定义在这些操作数的类型上、结果落在哪个类型**"。基本类型的等价很好判（int 只等价 int），难点在复合/递归类型的等价（C5.2.4–C5.2.5）和不完全匹配时的转换（C5.4）。

### C5.2.2 类型表达式与类型构造子

编译器内部把类型表示成**类型表达式（type expression）**：基本类型（int、char……）和类型名是类型表达式；在类型表达式上施加**类型构造子（type constructor）**得到更复杂的类型表达式。龙书给的主要构造子有：

```
array(I, T)      —— 下标集为 I、元素类型为 T 的数组
T1 × T2          —— 笛卡尔积（用于记录字段、参数列表）
record((n1×T1) × (n2×T2) × …)  —— 带字段名的记录/结构体
pointer(T)       —— 指向类型 T 的指针
s → t            —— 定义域类型 s、值域类型 t 的函数类型
```

类型表达式就是"用小积木搭出任意复杂类型"的语法。例如 C 里 `int (*)[5]`（指向"5 个 int 的数组"的指针）对应的类型表达式是

pointer(array(5, int))

函数 `int f(char, char)` 对应

char × char → int

初学者要抓住的是，把类型写成这种**有结构的表达式**（而不是一个不透明的字符串），才让"两个类型是否相同"变成一个可以机械递归比较的问题（下一节的类型树/图就是它的数据结构落地）。易错点：`s → t` 这个箭头记法在类型理论里到处出现（L5-06 会大量用），此处先当作"函数类型"的写法记住即可。

### C5.2.3 用类型树/类型图表示类型

类型表达式在编译器里通常存成**类型树（type tree）**或**类型图（type graph / DAG）**：叶子是基本类型，内部节点是构造子。CS143 给的建树规则：

```
数组   —— 两棵子树：一棵表元素个数，一棵表基类型
结构体 —— 每个字段一棵子树
指针   —— 一棵子树：所指向的类型
```

例如 `int nums[5]` 存成一棵 `array` 节点，两个孩子分别是 `5` 和 `int`。

用树/图表示的好处是：判断两个类型是否等价，就变成"**递归地同步遍历两棵树、逐节点比较**"这样一个干净的树操作。用**图（共享子树）**而非纯树还能让相同的子类型只存一份，节省空间、加速比较（同一指针即同一类型，见下节 `tree1==tree2` 的快速返回）。

初学者可以把类型树想成"把 `pointer(array(5,int))` 这个表达式画成语法树"。它的价值在 C5.2.4/C5.2.5 会兑现——结构等价判定、递归类型判定，全靠在这棵树/图上做递归。

### C5.2.4 结构等价 vs 名字等价

两个类型何时算"相同"，有两种定义。**名字等价（name equivalence）**：两个类型相同当且仅当它们**由同一个类型名指代**（或按语言规定同源）。**结构等价（structural equivalence）**：把类型名替换成其定义、递归展开后，**两棵类型树逐节点完全匹配**即算相同。CS143 的 Pascal 例子：

```
type
  little = array[1..5] of integer;
  small  = array[1..5] of integer;
var
  a, b: array[1..5] of integer;
  d, e: little;
  f, g: small;
```

名字等价下：d、e 同类型（都叫 little），f、g 同类型（都叫 small），但 d 与 f 不等价（名字不同），d 与 a 也不等价。结构等价下：a、b、d、e、f、g **全部等价**（展开后都是"5 个整数的数组"）。

**名字等价问"叫得一样吗"，结构等价问"长得一样吗"。** 结构等价用一个递归比较函数即可实现（CS143 给的 `AreEquivalent`）：

```
bool AreEquivalent(t1, t2) {
  if (t1 == t2) return true;              // 同一指针，必等价
  if (t1->kind != t2->kind) return false; // 构造子不同，不等价
  switch (t1->kind) {
    case BASE:  return true;                          // 同基本类型
    case PTR:   return AreEquivalent(t1->c[0], t2->c[0]);
    case ARRAY: return AreEquivalent(t1->c[0], t2->c[0])
                    && AreEquivalent(t1->c[1], t2->c[1]);
  }
}
```

名字等价**更快更严**（只比名字），但可能把"其实一样的东西"判成不同；结构等价**更宽更慢**（要递归展开比较），但更贴近"类型真正代表什么"。两者都是**合法的语言设计选择**，选哪种是语言定义的一部分，直接影响类型检查器实现难度。历史注脚（CS143）：第一个支持复合/递归类型表达式的 Algol 68 用的就是结构等价。

### C5.2.5 递归类型的等价判定：环与标记节点

上面的 `AreEquivalent` 有个坑：如果类型是**递归的**（如"记录里含一个指向同类型记录的指针"，典型如链表节点），朴素递归比较会**无限循环**下去。解决办法有二：在遍历时给**已访问节点做标记**以检测环（发现回到已访问节点就停），或干脆规定**指针类型只按名字等价**（不展开指针所指的类型），从而截断递归。

递归类型是真实语言的常态——链表、树、"含 next 指针的结构体"全是递归类型。CS143 明确点出这个终止性问题："这函数看着简单，但保证终止吗？如果比较的是一个含指向自身指针的记录呢？" 直觉上，纯结构展开会像两面对着的镜子无限反射，必须靠"标记走过的节点"来打破无限。

初学者要抓住的是，"标记节点检测环"是处理一切递归数据结构（不只类型树，也包括后续的图算法）的通用招数。易错点：很多语言正是为了绕开递归类型结构等价的复杂性，在涉及指针/递归时**退回名字等价**——这也解释了为什么 C 的结构体用名字（标签）等价而非结构等价（两个字段完全一样但 tag 不同的 struct 不算同类型）。

### C5.2.6 类型兼容与子类型

类型系统除了定义"等价"，还定义**类型兼容（type compatibility）**——很多语言构造并不严格要求等价，而允许**可强制转换（coercible）或兼容**的类型替换。**子类型（subtype）**是一种"可自由替换"的兼容关系：若类型 S 拥有类型 T 的全部行为、可在任何期待 T 的位置替换 T，就说 S 是 T 的子类型，S 的值可以用在期待 T 的地方。

兼容比等价宽：一个接收 `double` 参数的函数常允许传 `int` 实参（int 能无损转成 double）；C 的 `enum` 是 int 的子类型（期待 int 处可放 enum）；面向对象语言里，子类实例可替换父类实例（"is-a" 关系）。类型检查器因此不只判等价，还要"知道哪些类型可以替换哪些"。

初学者要抓住的是，**等价 ⊂ 兼容**——等价的一定兼容，兼容的不一定等价（int 兼容于 double 但不等价）。这条"可替换"直觉（子类型 S 能用在需要 T 的地方）就是子类型的核心，即里氏替换原则的雏形；它的完整理论（子类型规则、协变逆变、subsumption）根在 L5-06 T5，本篇只用不证。易错点：兼容/子类型的方向性——"int 可当 double 用"不等于"double 可当 int 用"（后者要窄化、可能丢精度），替换关系是单向的。

## C5.3 类型检查规则的实现

### C5.3.1 类型检查是什么，静态 vs 动态，强类型

**类型检查（type checking）**是核对程序中每一个操作都遵守语言类型系统的过程——即"任何表达式里的操作数类型与个数都恰当"。检查可发生在**编译期**（**静态类型检查 static type checking**，信息取自声明、存进符号表）、**运行期**（**动态类型检查 dynamic type checking**，每个数据带类型标签、操作前先验标签），或两者分担。一个语言若**每一个类型错误都在编译期被查出**，称为**强类型（strongly typed）**。

静态检查在"跑之前"靠声明信息查（快、能提前拦错，但有些错查不出）；动态检查在"跑的时候"靠运行时类型标签查（能查出静态查不出的错，如数组越界、除零溢出，但有运行时开销）。LISP 是典型动态类型检查语言（不要求声明类型）。CS143 坦言：连 Pascal 这样声明严格的语言也做不到完全强类型——`a*b` 溢出、整数除零这类错误编译期通常测不出；C 的强类型检查更"敷衍"（无数组边界检查、typecast 直接挂起类型检查）。

初学者要抓住的是，"静态/动态"讲的是**何时查**，"强/弱"讲的是**查得严不严（是否所有类型错都被拦）**——两者正交。易错点：静态类型检查 ≠ 强类型；很多静态检查语言（如 C）因为有转型、无边界检查等漏洞，达不到严格强类型的定义。

### C5.3.2 类型综合 vs 类型推断

龙书把类型检查的算法分两种风格。**类型综合（type synthesis）**：从**子表达式已知的类型**自底向上"综合"出整个表达式的类型——要求名字先声明后使用（这样叶子类型已知）。**类型推断（type inference）**：从一个构造**被使用的方式**反推出它（及相关变量）的类型——即使名字没显式声明也能定型。函数应用的综合规则典型形如：

```
若 f 的类型是 s → t，且 x 的类型是 s，
则 f(x) 的类型是 t。
```

抓住区别：综合是"**孩子的类型已知 → 算父亲的类型**"（大多数带声明的语言如 C/Java 走这条路，天然对应 C4 的综合属性，值自底向上流）；推断是"**从用法倒推类型**"（ML/Haskell 这类不强制声明的语言走这条，如 CS143 例 `fun mult x = x*10` 里 ML 从"x 乘了个整数"推断出 x 是 int）。

初学者要抓住的是，日常见到的 C/Java 类型检查基本都是**类型综合**——因为你必须先 `int x;` 声明，叶子类型才已知，才谈得上往上综合。类型推断更强大（能省声明）但更复杂。指路：完整的类型推断算法（Hindley-Milner、合一、Algorithm W、let-多态）根在 L5-06 T7，本篇只点到"综合 vs 推断"的分野，不展开推导算法。

### C5.3.3 表达式的类型检查规则

表达式的类型综合就是给每条产生式配一条**语义规则**，用子表达式的 `type` 属性算出本表达式的 `type` 属性（这正是 C4 的综合属性）。龙书的算术加法规则形如：

```
E → E1 + E2   { E.type = if (E1.type == integer and E2.type == integer)
                          then integer
                          else if (数值且可转换) then ...（见 C5.4 coercion）
                          else type_error }
```

数组下标、函数调用同理：

```
E → E1 [ E2 ]   { if (E2.type == integer and E1.type == array(s, t))
                     then E.type = t else type_error }
E → E1 ( E2 )   { if (E1.type == (s → t) and E2.type == s)
                     then E.type = t else type_error }
```

写成更贴近类型理论的**推断式（premise/conclusion）**记法，加法规则是：

```
   E1 : int      E2 : int
   ------------------------
        E1 + E2 : int
```

读作"横线上方的前提都成立时，横线下方的结论成立"。

初学者要抓住的是，类型检查器的骨架就是**在 AST 上做一趟（后序）遍历，对每个节点套用对应的类型规则**：先算出两个孩子的类型，再按规则核对是否合法、并给本节点定型；不合法就报类型错。CS143 的 Decaf 例子——`Expr → Expr + Expr` 时"检查两操作数必须同为 int 或同为 double"——正是这套规则的具体化。易错点：类型检查是自底向上综合类型的同时**顺便查错**，两件事在同一趟遍历里完成；类型规则的"前提"就是要核对的合法性条件，前提不满足就是类型错。

### C5.3.4 语句的类型检查

语句本身通常没有"值的类型"，但语句里嵌着表达式，其类型检查规则约束这些表达式的类型，并常约定语句的检查结果是一个特殊类型 `void`（或"检查通过/type_error"）。龙书的典型规则：

```
S → id = E        { if (id.type == E.type) then S.type = void else type_error }
S → if E then S1  { if (E.type == boolean) then S.type = S1.type else type_error }
S → while E do S1 { if (E.type == boolean) then S.type = S1.type else type_error }
```

抓住共性：**赋值**要求左值类型与右值类型匹配（或右值可转成左值类型），**条件/循环**要求测试表达式是布尔型。CS143 的 Decaf 语义规则也是同一套——"循环测试表达式必须是 bool 类型""数组下标必须是整型""逻辑 && 两操作数须为 bool、结果为 bool""函数调用实参类型须与形参兼容"。

初学者要抓住的是，语句层的类型检查主要是"**把语句里各表达式的类型算出来，核对它们符合该语句的要求**"。一个特别常见、语法层拦不住而必须靠语义检查抓的错，就是"在 `if`/`while` 的条件里放了个非布尔表达式"——在 C 里这甚至只是告警（int 当条件），在强类型语言里就是硬错误。这也印证了 C1/CS143 的定位：语义分析专门收拾"语法合法但意义不通"的问题。

### C5.3.5 设计一个类型检查器：三步法与实证

CS143 给的类型检查器设计三步：(1) 列出语言里有哪些**类型**；(2) 列出哪些**语言构造**带类型（常量、变量、函数、表达式，以及内含表达式的 if/while/赋值等）；(3) 列出语言的**语义规则**。这三样（类型 + 构造 + 规则）合起来定义了一个语言的**类型系统**，据此就能把类型检查器实现为语义分析的一部分。

实现骨架就是：语法分析建出 AST 与符号表 → 对 AST 做遍历，进入声明时往符号表登记类型（C5.1）、进入表达式/语句时套用类型规则（C5.3.3/C5.3.4）核对并综合类型 → 有错就报诊断。

用本机 clang/LLVM 18.1.3 实证语义诊断（基线 @2026-07-25），把 C5.1/C5.3 的检查落到真实编译器输出。源文件 `sem.c`：

```c
int main(void) {
  int x = 3;
  y = x + 1;     /* 用了未声明的 y */
  int *p = x;    /* 把 int 赋给 int* */
  return p;      /* 拿 int* 当 int 返回 */
}
```

命令 `clang -fsyntax-only sem.c`（`-fsyntax-only` 只做到语义检查、不生成代码），真实输出摘录：

```
sem.c:3:3: error: use of undeclared identifier 'y'
sem.c:4:8: error: incompatible integer to pointer conversion initializing 'int *' with an expression of type 'int'
sem.c:5:10: error: incompatible pointer to integer conversion returning 'int *' from a function with result type 'int'
3 errors generated.
```

三条错误精确对应本章机制：第一条是**符号表查找失败**（y 不在任何开放作用域的符号表里，C5.1.3 名字解析报未声明）；第二条是**类型不兼容**（int 与 int* 既不等价也不可隐式转换，C5.2.6 兼容判定失败）；第三条是**返回类型检查**（返回值类型 int* 与函数声明的返回类型 int 不匹配，C5.3.4 语句规则）。

这条实证给初学者的校准是，教材里抽象的"套类型规则报 type_error"，在工业编译器里就是这些你天天见到的编译报错——它们全部产生在语义分析阶段，且带着精确的行列号（这正来自 C4 里 AST 节点上携带的源位置属性）。

## C5.4 类型转换与重载消解

### C5.4.1 隐式转换（coercion）vs 显式转换（cast）

当一个操作的操作数类型与所需类型不严格匹配、但"可以设法对上"时，就发生**类型转换**。**隐式转换（implicit conversion / coercion，强制转换）**由编译器**自动**插入——发现类型不匹配时，编译器搜索一个合适的转换操作补进代码里；只有找不到任何转换才报类型错。**显式转换（explicit conversion / cast，强制类型转换）**由程序员用语法（如 C 的 `(double)x`）**手动**要求。

coercion 是"编译器悄悄帮你转"，cast 是"你明说要转"。经典 coercion 例子（龙书）：`rate * 60`，`rate` 是浮点、`60` 是整数，编译器自动把整数 60 转成浮点再相乘。CS143 点出：C 里几乎任何算术类型错，编译器都会先找转换来补救；而 C++ 里可能的自动转换空间巨大，会拖慢编译、有时给出意外结果。

初学者要抓住的是，coercion 让代码简洁（不必到处手写转换）但会**掩盖潜在错误**——本该报错的地方被自动"和稀泥"转过去了。CS143 的 PL/I 反面教材：`DECLARE (A,B,C) CHAR(3); B="123"; C="456"; A=B+C;` PL/I 自动把字符串转成数 123、456，相加得 579，转回字符串用默认宽度 8 变成 `"     579"`，再塞进只有 3 字符的 A，静默截断成 `"   "`——完全不是本意。这说明过度隐式转换的危险。Ada、Pascal 则几乎不做自动转换，逼你显式转。

### C5.4.2 拓宽（widening）vs 窄化（narrowing）

隐式转换分两种方向。**拓宽转换（widening）**：从"小"类型转到能容纳它的"大"类型，通常**无损**（如 int → double、char → int）。**窄化转换（narrowing）**：从"大"类型转到"小"类型，**可能丢失信息**（如 double → int 截断小数、int → char 溢出）。龙书用两个偏序层次图规定：拓宽沿层次"向上"走（安全、可自动做），窄化"向下"走（危险）。

拓宽像把水从小杯倒进大杯，一滴不洒；窄化像把大杯往小杯倒，会溢出去。所以多数语言**自动做拓宽、但不自动做窄化**——窄化要么禁止、要么必须显式 cast。龙书给的转换辅助函数形如

widen(a, t, w)   —— 把类型为 t 的值 a 拓宽到目标类型 w

在生成代码时把该插的转换指令插进去。

初学者要抓住的是，"能不能自动转"背后的原则就是"**安不安全（会不会丢信息）**"：安全的拓宽随便自动做，危险的窄化要程序员签字（显式 cast）画押。易错点：C 比较宽松，`int n = 3.9;` 会自动窄化（截断成 3）只给告警；Java 则要求 `(int)` 显式转型才允许这种截断——同一操作，语言的严格度不同（本机实证见 C5.4.5）。widening/narrowing 的**具体类型层次**是语言定义的一部分，不同语言不同，不凭记忆套用。

### C5.4.3 左值（l-value）vs 右值（r-value）

同一个表达式出现在赋值号两边，含义不同：出现在**左边**要的是一个**可写的存储位置**，叫**左值（l-value）**；出现在**右边**要的是一个**值**，叫**右值（r-value）**。语义分析要核对：赋值号左边必须是**可作左值**的东西（有地址、可赋值的变量、数组元素、结构体字段等），不能是常量或临时结果。

`x = y` 里，左边 `x` 要"往哪儿存"（位置），右边 `y` 要"存什么进去"（值）；一个变量在右值语境里会被"求值成它当前的值"，在左值语境里则代表"它的存储位置"。所以 `3 = x` 非法（3 是常量，没有可写位置，不能作左值），`x + 1 = y` 也非法（`x+1` 是临时值，非左值）。

初学者要抓住的是，l-value/r-value 是"**表达式在此处是被当作位置还是当作值**"的语境区分。这也解释了 C4.4.5 clang AST 里那个 `ImplicitCastExpr <LValueToRValue>`——当一个变量出现在右值语境，编译器插入一个"取出它存储位置里的值"的隐式转换。易错点：l-value/r-value 是**编译期的表达式分类**（能否作赋值目标），不是运行期的值本身；"可作左值"是语义检查赋值合法性的关键条件之一。

### C5.4.4 重载与重载消解

**重载（overloading）**指同一个名字（运算符或函数）对应**多个不同类型签名**的定义——如 `+` 既能加整数也能加浮点、C++ 里可为不同参数类型定义多个同名函数。**重载消解（overload resolution）**是语义分析根据**实参的类型（有时还有上下文期待的返回类型）**从这些候选里挑出**唯一**该用的那个定义的过程。

重载是"一名多义"，消解就是"根据上下文断定此处到底用哪个义"。CS143 的 ML 例子 `fun sqr x = x*x` 会报错——因为 `*` 对实数和整数是两个不同的重载操作，ML 无法确定用哪个，得靠 `fun sqr x:int = x*x` 显式标注才能消解。消解一般按"实参类型与哪个候选签名匹配"来选；若有多个候选都能通过隐式转换匹配，就要按语言规定的"最佳匹配"规则挑（否则报"有歧义"）。

初学者要抓住的是，重载消解是"**按类型选定唯一目标**"，它和 coercion 常纠缠在一起——因为一个候选可能需要对实参做隐式转换才匹配，于是"选哪个重载"要连带考虑"要不要转、转的代价"。易错点：重载（overloading，编译期按静态类型选，同名不同签名）与**覆盖/多态（overriding，运行期按动态类型选）**是两回事；本节讲的是前者。重载消解在 C++ 这类语言里规则复杂（候选集、转换序列排序、最佳可行函数），此处只讲"是什么、怎么定位唯一目标"，不纵深展开各语言的消解细则。

### C5.4.5 实证：clang -Wconversion 看隐式转换告警

用本机 clang/LLVM 18.1.3 实证隐式转换与拓宽/窄化（基线 @2026-07-25）。源文件 `conv.c`：

```c
int f(int x) { return x; }
int main(void) {
  double d = 3.9;
  int n = d;        /* double -> int 窄化，截断 */
  char c = 300;     /* int -> char 窄化，溢出 */
  unsigned u = -1;  /* 有符号 -> 无符号，变号 */
  return f(d);      /* 实参 double -> 形参 int */
}
```

命令 `clang -Wconversion -Wall -fsyntax-only conv.c`，真实告警摘录：

```
conv.c:4:11: warning: implicit conversion turns floating-point number into integer: 'double' to 'int' [-Wfloat-conversion]
conv.c:5:12: warning: implicit conversion from 'int' to 'char' changes value from 300 to 44 [-Wconstant-conversion]
conv.c:6:16: warning: implicit conversion changes signedness: 'int' to 'unsigned int' [-Wsign-conversion]
conv.c:7:12: warning: implicit conversion turns floating-point number into integer: 'double' to 'int' [-Wfloat-conversion]
```

四条告警精确印证本章机制：`double→int`（第 4、7 行）和 `int→char`（第 5 行，clang 连"300 截断成 44"这个丢信息的结果都算出来了）都是 C5.4.2 的**窄化**——C 会自动做但发告警提示风险；`int→unsigned`（第 6 行）是变号转换。第 7 行 `f(d)` 是**函数实参的隐式转换**（double 实参转成 int 形参），呼应 C5.4.1 编译器自动补转换。

C 属于"宽松放行 + 发告警"的策略——这些窄化默认不是硬错误（不加 `-Wconversion` 甚至完全静默），编译照过；而更严格的语言（如 Java）会把其中一些直接判为编译错误、逼你显式 cast。同一段"看似无害"的代码，在不同语言/不同 `-W` 等级下从"静默"到"告警"到"报错"，正说明类型转换策略是**语言与编译器共同的设计选择**，不是绝对真理。
