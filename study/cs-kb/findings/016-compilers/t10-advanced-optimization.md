## C10.1 指令级并行与软件流水

### C10.1.1 指令级并行（ILP）与代码调度的目标

**指令级并行（Instruction-Level Parallelism, ILP）**指的是：在一段看似顺序的指令流里，其实有许多指令彼此不依赖，硬件可以在同一时刻发射/执行多条。现代处理器靠流水线（pipelining）、多发射（superscalar）、乱序执行等手段挖掘 ILP。编译器这一侧的任务叫**代码调度（code scheduling / instruction scheduling）**：在**不改变程序语义**的前提下重排指令次序，让相邻指令尽量互不依赖、让长延迟指令（load、乘除、浮点）的等待窗口被别的有用指令填满，从而减少流水线**停顿（stall）**。

对初学者，关键直觉是"硬件早就不是一次一条了"。你写的 `a=...; b=...; c=...;` 在真实 CPU 上可能几条同时在流水线的不同阶段跑；但如果 `b` 用了 `a` 刚算出、还没就绪的结果，硬件就得插入气泡（等待）。编译器调度做的事，就是把不相关的指令挪到这些等待窗口里去，让流水线别空转。注意分工：ILP 的**硬件机制**（流水线深度、发射宽度、乱序窗口、分支预测）属体系结构，交 **L5-05**；本篇只讲**编译器如何按指令间的依赖关系重排**这一层。龙书 Ch.10 正是把 C8 里"基本块内的调度"提升为系统的 ILP 优化专题。

### C10.1.2 数据依赖：真依赖、反依赖与输出依赖

要重排而不改变语义，必须先知道"哪两条指令的先后不能动"。这由**数据依赖（data dependence）**刻画，分三种：**真依赖 / 流依赖（true / flow dependence，RAW，写后读）**——后一条读了前一条写的值，是本质的、不可消除的；**反依赖（anti-dependence，WAR，读后写）**——后一条写了前一条要读的位置；**输出依赖（output dependence，WAW，写后写）**——两条写同一位置，先后决定最终值。把指令当节点、依赖当有向边，就得到**数据依赖图（data dependence graph, DDG）**，调度必须保持这张图上所有边的先后。

三种依赖里只有**真依赖是"真的"**，这一点对初学者极重要。反依赖和输出依赖是因为**复用了同一个名字/寄存器/内存位置**才产生的"假依赖"——把其中一个换成新名字（重命名，renaming）就能打断它。最小例子

t = a + b     // (1)
a = c + d     // (2) 与(1)是反依赖：(1)读a,(2)写a

若把 (2) 的 `a` 改名成 `a2`，(1)(2) 就再无约束、可以互换或并行。这正是 SSA 形式（C6.4）和硬件寄存器重命名的价值所在：消掉假依赖、暴露更多 ILP。真依赖则无法用改名消除——你必须等值算出来才能用它。记住"真依赖是硬约束、反/输出依赖可用重命名打破"，就抓住了调度自由度的来源。

### C10.1.3 基本块内的表调度（list scheduling）

在单个基本块内，最常用的调度算法是**表调度（list scheduling）**。它先根据指令间依赖建好 DDG，并给每条指令标注一个**延迟（latency，结果几拍后可用）**；然后维护一个**就绪表（ready list）**——所有前驱都已调度、且结果将就绪的指令；每个周期从就绪表里按某种**优先级**挑一条（或多条，若机器可多发射）排入，最常用的优先级是**关键路径长度（critical-path / 到出口的最长延迟）**，优先排"下游还很长"的指令。机器每种功能部件的占用由**资源预约表（resource reservation table）**记账，避免超发。

表调度是"贪心 + 拓扑序"的结合，初学者可以这样理解：DDG 决定了哪些指令"现在合法可排"（就绪表），优先级决定"其中先排哪条最划算"（先排关键路径上的，别让它拖住整体）。最小直觉

x = load(p)   // load 有较长延迟
y = x + 1     // 真依赖 x，必须等 load
z = w * 2     // 与上面无关

照原序 `y=x+1` 要停顿等 load；表调度把无关的 `z=w*2` 提到 load 之后、`y` 之前，用它填住 load 的延迟窗口。要点是最优基本块调度本身是 NP 难的，故表调度是启发式；且它只在**基本块内**重排，跨块的机会要靠下面的全局调度。

### C10.1.4 全局调度一瞥：trace / superblock 调度与推测

基本块通常很短（几条指令），块内可挖的 ILP 有限。**全局调度（global scheduling）**跨越基本块边界找并行，代表技术有**踪迹调度（trace scheduling）**和**超块调度（superblock scheduling）**：先用剖析信息（profiling）找出最常走的一条路径（trace / superblock），把它当成一个大"直线块"来调度，允许指令跨越原来的分支边界上下移动；为保持语义，需要在其他分支出口补上**补偿代码（compensation / bookkeeping code）**。当把一条指令提到它原本所属分支之前执行时，就是**推测执行（speculation）**——先算了再说，猜错了丢弃。

对初学者，这一节的意义是理解"为什么现代编译器敢把指令挪那么远"。块内调度太局促，于是编译器赌"热路径"（最常执行的路径）值得优化，把热路径拉直成大块、跨分支重排，代价是给冷路径补偿代码。这依赖两样东西：剖析数据（知道哪条路径热）和推测（提前执行可能白算的指令）。龙书 Ch.10 把这些归为全局调度技术；它们大量用于早期 VLIW/超长指令字机器和 EPIC（如 Itanium），在编译器需要静态挖掘 ILP、硬件不做乱序时尤其关键。深入的硬件推测/乱序机制交 L5-05，本篇只需记住"热路径拉直 + 补偿代码 + 推测"这条思路。

### C10.1.5 软件流水与模调度（modulo scheduling / SMS）

**软件流水（software pipelining）**是针对**循环**的调度技术：不再一轮迭代完整跑完再跑下一轮，而是让**不同迭代的指令重叠执行**——当第 i 轮还在做后段时，第 i+1 轮的前段已经开始，像硬件流水线那样在"软件层面"把循环各阶段错开填满。最主流的实现是**模调度（modulo scheduling）**：找一个尽量小的**启动间隔（Initiation Interval, II，相邻两轮迭代启动相隔的周期数）**，构造一个长度为 II 的稳态循环体（kernel），使每 II 个周期就能启动一轮新迭代；循环前后各加一段**填充/排空代码（prologue / epilogue）**来启动和收尾流水。II 的下界由两方面决定

II ≥ max( ResII , RecII )

其中 ResII 是资源约束下界（某功能部件被占满决定），RecII 是循环携带依赖（recurrence）形成的环路延迟下界。

直觉上，普通调度只能在一轮迭代内部找并行，一旦一轮里指令太少或依赖链太长就没得可排；软件流水把"下一轮的独立指令"提前拉进来填空，等于把循环体在时间轴上斜着切、让多轮同时在跑。最小画面：一轮迭代分 A→B→C 三段有依赖，单轮时 A 等不到东西填、C 后面空着；软件流水后稳态每拍在做 `C(i) B(i+1) A(i+2)`——三轮的三段并行推进。GCC 用 **SMS（Swing Modulo Scheduling，摆动模调度）**实现，由 `-fmodulo-sched` 开启（本机 gcc 13.3.0 `gcc -O2 -fmodulo-sched -fdump-rtl-sms` 确实产生 `*.sms` RTL dump，2026-07-25 实测；SMS 默认不在 `-O2/-O3` 打开，需显式加标志）。软件流水与展开（C10.1.6）互补：展开是"把几轮摊平在一起再块内调度"，软件流水是"稳态重叠、代码不膨胀那么多"。

### C10.1.6 循环展开与自动向量化：暴露 ILP / 数据级并行

**循环展开（loop unrolling）**把循环体复制若干份、迭代步长相应放大，用来减少分支/归纳变量开销，更重要的是**把多轮迭代的独立指令摊到一个大基本块里，给块内调度和寄存器分配更多并行素材**。**自动向量化（auto-vectorization）**更进一步：若各轮迭代互不依赖，就把它们打包成一条 **SIMD（单指令多数据）**指令一次算多个元素，这是**数据级并行（DLP）**。二者都需要先确认"迭代间没有会被破坏的依赖"——这套依赖分析属 C10.2，此处只用其结果。

对下面的 SAXPY 循环（gcc 13.3.0，`-std=c11`，x86-64 System V ABI，用 `restrict` 断言无别名）

void saxpy(float *restrict y, const float *restrict x, float a, int n){
  for(int i=0;i<n;i++) y[i] = a*x[i] + y[i];
}

`gcc -O3 -S` 把标量循环向量化成 SSE 打包运算，稳态循环体一次处理 4 个 float

movups (%rsi,%rax), %xmm1
mulps  %xmm2, %xmm1      # 4 个 x[i] 同时乘 a
addps  %xmm3, %xmm1      # 再同时加 4 个 y[i]
movups %xmm1, (%rcx,%rax)

`gcc -O3 -fopt-info-vec` 报告 `loop vectorized using 16 byte vectors`（本机 2026-07-25 实测）。版本时效要点：本机 gcc 13.3 中循环向量化 `-ftree-loop-vectorize` 与基本块向量化 `-ftree-slp-vectorize` **在 `-O2` 与 `-O3` 均默认开启**（`gcc -Q -O2 --help=optimizers` 显示二者 `[enabled]`；GCC 自 12 起在 `-O2` 用保守成本模型开向量化），而循环展开 `-funroll-loops`、循环交换 `-floop-interchange`、`-funroll-and-jam`、`-fpredictive-commoning` 属 `-O3` 级默认（`-Q -O3` 实测 `[enabled]`）。初学者需知：`restrict`（或 C++ 里编译器能证明的无别名）常是向量化能否发生的关键——若编译器无法排除 `x`、`y` 重叠，它必须保守假设有依赖、放弃向量化。SIMD/向量的硬件宽度与吞吐交 L5-05，本篇只讲编译器如何生成。

## C10.2 并行与局部性优化

### C10.2.1 目标：并行性与数据局部性，以及仿射框架总览

龙书 Ch.11 的主题是把**循环嵌套**变换得既能**并行执行**（多个迭代同时跑在多核/向量单元上）、又有好的**数据局部性**（访存尽量命中缓存）。这两个目标常常一起追求，因为都取决于同一件事——**迭代之间到底有没有依赖、访存落在哪里**。该章的统一工具是**仿射（affine）框架**：当循环边界和数组下标都是循环变量的**线性/仿射函数**时，迭代集合与访存模式可以用整数线性代数（多面体、线性不等式组）精确刻画，从而系统地判定依赖、推导合法变换。

对初学者，先建立一个大局观：C9 的循环优化（LICM、归纳变量、强度削减）是"不改变循环结构、把循环里的冗余抠掉"；C10.2 则**改变循环的结构本身**——交换内外层、把两个循环合成一个、把大循环切成小块。为什么值得这么做？因为并行硬件和缓存对"访存的顺序与形状"极其敏感：同样的计算，换个循环次序可能就从"每次都 cache miss"变成"连续命中"，或从"每轮依赖上一轮、只能串行"变成"各轮独立、可并行"。而要保证变换后结果不变，就得先精确回答"哪些迭代之间有依赖"——这就是为什么要引入仿射/多面体这套数学。

### C10.2.2 迭代空间与仿射数组访问

一个 d 层循环嵌套的所有迭代，可以看成 d 维整数空间里的一组点，叫**迭代空间（iteration space）**；每个点是一个迭代向量（如二重循环的 `(i,j)`）。当循环上下界是外层循环变量的仿射函数时，迭代空间是一个被一组线性不等式围成的**多面体（polytope）**。数组访问的下标若也是循环变量的仿射函数（如 `A[i+1][2*j]`），则每次访问的地址可写成

访问地址 ≈ F·**i** + **f**

其中 **i** 是迭代向量、F 是整数矩阵、**f** 是常向量。

直觉上，"仿射"就是"只用循环变量的加法和常数倍，不出现 `i*j`、`A[B[i]]` 这种非线性/间接下标"。为什么盯着仿射？因为一旦访存写成 `F·i+f` 的线性形式，"两个迭代 i1、i2 是否访问同一内存"就变成解一个**整数线性方程/不等式组**的问题，可以用成熟算法判定。这是整章的地基：仿射 = 可用线性代数精确分析；一旦下标非仿射（间接寻址、指针追逐），这套方法失效，编译器只能保守假设"可能有依赖"、放弃变换。初学者记住这条适用边界，就明白了为什么科学计算/稠密数组循环最受益于这类优化，而指针满天飞的代码往往无能为力。

### C10.2.3 数据依赖分析：距离/方向向量与 GCD、Banerjee 测试

**循环携带依赖（loop-carried dependence）**指不同迭代之间的依赖：迭代 i1 写了某数组元素、迭代 i2（i2 在 i1 之后）读/写同一元素。是否存在这种依赖，等价于问"下标方程 `F·i1+f = F·i2+f` 在迭代空间内有没有整数解"。分析结果用**距离向量（distance vector，i2−i1 的差）**或更粗的**方向向量（direction vector，各分量取 <、=、>）**表示。求解常用两个经典测试：**GCD 测试**——依赖有整数解的**必要条件**是下标系数的最大公约数整除常数差，

若 gcd(系数们) ∤ (常数差)，则无依赖（安全）

不整除就一定无依赖、可放心变换；能整除只是"可能有"，需更强的测试。**Banerjee 测试**在循环边界范围内用不等式判断解是否落在迭代空间内，比 GCD 更精确但仍是保守近似。

这里要给初学者点明两个测试的定位与"看似冲突"的正确读法。GCD 测试**快但松**：它只能证明"没有依赖"，不能证明"有依赖"（能整除时它给不出结论）；Banerjee 测试**更精确但仍近似**：它进一步利用循环边界排除范围外的解，但为了可判定/高效仍是保守的——即"报告有依赖"可能是假警报，但"报告无依赖"一定可靠。这正是静态分析的一贯品性：**宁可错报有依赖（放弃一次优化），绝不漏报（导致错误变换）**（可靠性 vs 精度的权衡，其分析语义与 over-approximation 框架交 L6-02 V1/V2）。两测试不矛盾，是"快粗筛 + 精细筛"的层次关系，实际编译器串联使用。最小例子：`for i: A[2*i]=A[2*i+1]`，下标差为常数 1，`gcd(2)=2` 不整除 1，GCD 测试直接判定无循环携带依赖，各轮可并行。

### C10.2.4 循环变换目录：交换、融合、分裂、倾斜、分块、并行化

在依赖分析给出"哪些迭代序不能颠倒"之后，编译器可施加一系列**循环变换**，每一种都有明确的**合法性条件（不违反任何依赖）**：**循环交换（interchange）**换内外层次序，改善局部性或暴露并行；**循环融合（fusion）**把两个相邻循环并成一个，增加局部性与指令并行；**循环分裂/分布（fission / distribution）**反过来把一个循环拆成多个，隔离依赖或便于向量化；**循环倾斜（skewing）**对迭代空间做斜切，配合交换让原本有依赖的循环暴露出并行维度；**循环分块（tiling / blocking）**把大循环切成小块以适配缓存（见 C10.2.5）；以及**DoAll 并行化**——若某层循环无任何循环携带依赖，该层所有迭代相互独立、可直接分给多核/向量单元。

合法性是这些变换的灵魂，初学者务必抓住"变换必须保持依赖方向"这条铁律。举例：矩阵乘 `for i: for j: for k: C[i][j]+=A[i][k]*B[k][j]`，把 `j`、`k` 两层**交换**通常能让内层对 `B` 的访问变成按行连续（改善局部性），但只有当交换不违反依赖时才合法。再如**融合**两个都遍历数组 `a` 的循环，能让 `a[i]` 一次载入缓存就被两处用到（局部性↑）——前提是第二个循环不依赖第一个循环尚未算完的元素。反例意识同样重要：若盲目交换/融合破坏了某个真依赖，结果就错了。所以真实编译器（如 gcc 的 `-floop-interchange`、`-ftree-loop-distribute-patterns`，`-O3` 默认；实测见 C10.2.6）都先跑依赖分析、只在合法时施加。

### C10.2.5 循环分块（tiling / blocking）与数据局部性

**循环分块（loop tiling，又称 blocking）**是局部性优化里最重要的一招：把一个遍历大数组的循环，按小块（tile / block）重新组织迭代次序，使得一小块数据被载入缓存后、在被换出之前尽量多地被复用。经典对象是矩阵乘和模板计算：原始三重循环里，内层每次扫过整个 `B` 矩阵的一列/一行，数据量远超缓存，等下次要用时早被挤出去了（**容量失效**）；分块后先只处理 `B` 的一个 `tile×tile` 小块、把它算干净再换下一块，让每块数据的多次复用都发生在缓存命中期内。

对初学者，分块的价值可以用一句话概括：**把"数据的复用距离"缩短到缓存能装下**。缓存有限（比如 L1 只有几十 KB），一次装不下整个大数组，但装得下一个小块；分块就是重排循环让"用完还要再用"的数据在小块内集中发生，而不是隔着整趟遍历才回头用。它是 C10.2.1 说的"并行与局部性"里局部性的主力，收益常常是数量级的（尤其在数值计算里）。要点：分块本身是循环变换的组合（strip-mining + interchange），合法性同样由依赖决定；块大小（tile size）要匹配缓存容量，是个需要调参/由成本模型决定的量（具体缓存层级与容量属 L5-05，本篇不给固定数值，标「随目标机而定」）。

### C10.2.6 仿射变换统一框架与多面体模型（Graphite / Polly）

龙书 Ch.11 的理论高潮是把上面各种循环变换**统一**成对迭代空间施加**仿射变换（affine transformation，用一个整数矩阵重新映射迭代向量）**：交换、倾斜、分块等都成了选取不同变换矩阵的特例，编译器的任务变为"在保持所有依赖的约束下，求一个能最大化并行性/局部性的仿射调度"。这套思想的工程化就是**多面体模型（polyhedral model）**：把循环嵌套抽成多面体、用整数线性规划求最优变换、再生成代码。代表实现是 GCC 的 **Graphite**（`-fgraphite` / `-floop-nest-optimize`，基于 **isl** 库与 **Pluto** 调度算法）和 LLVM 的 **Polly**（基于整数多面体，做 tiling/fusion 并暴露 SIMD/OpenMP 并行）。

对初学者，"统一框架"要传达的是：前面那一串循环变换看着零散，其实都是"对迭代空间坐标做一次线性变换"的不同姿态；把它们统一到矩阵语言后，编译器不必逐个试探，而能把"找最优变换"当成一个数学优化问题来解。时效与成熟度务必分账：这类多面体优化**思想成熟、工程实现仍属实验性且演进快**（⚙）——GCC 官方文档明确 `-floop-nest-optimize` 是"experimental"、需 `--with-isl` 配置构建、基于 Pluto 算法；LLVM Polly 默认不启用、按发行版打包（本机常规 `-O3` 流水线未走多面体路径，向量化/交换/分块由 gcc 的 tree 层 loop passes 完成）。本机 `gcc -O3 -fopt-info-optimized -ftree-loop-distribute-patterns` 可观察 tree 层循环变换发生；深入多面体调度不做纵深，标锚版本：gcc 13.3 / LLVM 18.1.3 @2026-07-25，随版本变。

## C10.3 过程间分析

### C10.3.1 为什么需要过程间分析，以及它与内联的关系

前面所有分析（数据流、循环优化）都默认在**单个函数内（过程内，intraprocedural）**进行——遇到函数调用就只能保守：假设被调函数可能改任何全局、返回任何值。**过程间分析（interprocedural analysis, IPA）**打破这个边界，跨越函数调用来传播信息，例如"这个参数在所有调用点都是常量 3""这个函数不修改任何全局（pure/const）""这个指针参数不与那个别名"。有了这些，编译器能做过程内做不到的优化：跨函数常量传播、把只读参数特化、消除冗余调用等。

对初学者，最直接的入口是"过程间分析和**内联（inlining）**是什么关系"。内联（把被调函数体直接展开到调用点）是最"暴力"的过程间优化——一旦内联，跨函数的问题就退化成了函数内问题，所有过程内优化自动生效。但内联不能无限做（代码膨胀、递归、间接调用挡路），所以还需要**不内联也能跨函数传播信息**的分析，这才是狭义的 IPA。本机演示：把一个 `static int scale(int x){return x*3;}` 在循环里累加，`gcc -O2 -S`（`-std=c11`）的产物里**既无 `call scale` 也无乘法指令**，整段 `for(i=0;i<5;i++) r+=scale(i)` 被内联并常量折叠为字面量

movl $30, %edx     # 循环结果 30 = 3*(0+1+2+3+4) 直接作为 printf 参数
movl $30, %eax     # 返回值也是常量 30

（本机 2026-07-25 实测）——这是内联 + 过程间常量传播合力的直观证据。

### C10.3.2 调用图（call graph）与间接调用的难点

**调用图（call graph）**是过程间分析的骨架：节点是程序里的函数/过程，有向边 `f→g` 表示 f 可能调用 g。有了调用图才能定义"信息如何沿调用/返回传播"。对**直接调用**（调用点写死了函数名），建图是平凡的。真正的难点是**间接调用**——通过函数指针、C++ 虚函数、或高阶函数调用时，调用点并不知道具体调哪个函数，调用图的边必须靠分析来推断。对面向对象语言常用**类层次分析（Class Hierarchy Analysis, CHA）**：根据变量的静态类型与类继承关系，缩小虚调用可能的目标集合。

这里的初学者要点是"调用图往往不是现成的，而是分析的产物、且互相依赖"。间接调用要确定目标，需要知道函数指针/对象可能指向谁——这恰恰是指针/别名分析（C10.3.4）要回答的；而指针分析又常常需要调用图来跨函数传播……于是调用图构建与指针分析**互相依赖**，实际中要么迭代到不动点、要么用保守近似（如"函数指针可能指向任何地址匹配的函数"）。CHA 是缩小虚调用目标的经典手段，直觉是"一个声明为 `Animal*` 的指针，虚调用 `speak()` 只可能落到 `Animal` 及其子类里重写了 `speak` 的那些实现，而非程序里所有同名函数"。记住"调用图对间接调用是近似的、且与指针分析纠缠"，就理解了 IPA 为何比过程内分析难得多。

### C10.3.3 上下文敏感度：调用串与克隆

过程间分析的一大分野是**上下文敏感度（context sensitivity）**。**上下文不敏感（context-insensitive）**分析把一个函数的所有调用点混在一起分析——简单、快，但会把不同调用点的信息**串味**：调用点 A 传了参数 1、调用点 B 传了参数 2，不敏感分析只会得出"参数是 1 或 2"，丢失了"A 处必是 1"的精度。**上下文敏感（context-sensitive）**分析区分不同调用上下文，主要两种实现：**调用串（call-string）**——用调用点序列（最近 k 层，k-CFA）标识上下文；**克隆 / 基于克隆（cloning-based）**——为不同上下文复制出函数的多个分析副本分别分析。

对初学者，上下文敏感度的直觉是"同一个函数被不同人以不同参数调用，要不要分开记账"。不敏感 = 一本流水账、所有调用混记，省事但模糊；敏感 = 给每个调用上下文单开一本账，精确但账本数量可能爆炸（调用链一深、克隆指数增长）。这是典型的**精度换开销**权衡。最小画面：`id(x){return x;}` 被 `id(1)` 和 `id("s")` 调用，不敏感分析认为 `id` 的返回"可能是整数或字符串"，敏感分析则分别得出两处各自的精确类型。龙书 Ch.12 主要以基于克隆/调用串的上下文敏感 Datalog 表述来讲；这套上下文敏感数据流的**分析理论与 k-CFA** 与 L6-02 的 V2.5（过程间数据流）、V3.4（k-CFA）同源，本篇只讲"编译器为优化而做"这一面，验证语义交 L6-02。

### C10.3.4 指针 / 别名分析：Andersen vs Steensgaard

**别名分析（alias analysis）/ 指针分析（points-to analysis）**回答"两个指针/表达式是否可能指向同一内存"，是几乎所有过程间优化的前提（不知道别名关系，就不敢重排访存、不敢跨调用传播）。两个奠基性的算法代表两种精度/开销取舍：**Andersen 分析（包含式 / inclusion-based，1994）**——把赋值 `p = q` 建模为集合包含约束 `pts(q) ⊆ pts(p)`，求解约束图的传递闭包，精度高但复杂度约 O(n³)；**Steensgaard 分析（统一式 / unification-based，1996）**——把 `p = q` 建模为 `pts(p)` 与 `pts(q)` **合并成同一等价类**，用并查集近乎线性时间求解，极快但精度低（合并是双向的、会把本不相关的指向混到一起）。

初学者可以这样把握两者差异：Andersen 是"单向箭头"——`p=q` 只让 q 的指向流进 p，方向准、但要反复传播（慢）；Steensgaard 是"焊在一起"——`p=q` 直接把 p、q 的指向集焊成一个，一步到位（快）但从此二者指向永远相同（粗）。这是全课反复出现的**精度 vs 可扩展性**主题的又一实例：编译器对小程序可用 Andersen 求精度、对大程序退回 Steensgaard 求速度。另两个正交维度：**流敏感（flow-sensitive）**是否考虑语句执行顺序（考虑则更准更贵，Andersen/Steensgaard 经典版都是流不敏感的）、**上下文敏感**如 C10.3.3。龙书 Ch.12 用 **Datalog（逻辑规则/关系）**统一表述指针分析与上下文敏感，是理解现代指针分析（如 bddbddb、以及后续工具）的钥匙。分账提示：龙书 Ch.12 正文以**包含式（Andersen 风格）+ Datalog + 基于克隆的上下文敏感**为主线展开；Steensgaard 的统一式方法是文献中并列的另一支（更快更粗），二者不冲突、是同一问题的两种权衡，本篇按标准指针分析文献并列列出。别名分析的可靠性证明与抽象解释框架交 L6-02（V1/V4）。

### C10.3.5 过程间优化的工程实践：LTO 与 IPA passes

真实编译器把过程间分析落地为一组具体优化。GCC 的 `-fipa-*` 系列即是：`-fipa-cp`（过程间常量传播）、`-fipa-cp-clone`（为常量参数克隆特化版本）、`-fipa-pure-const`（识别无副作用的 pure/const 函数）、`-fipa-icf`（合并语义相同的函数/变量）、`-fipa-pta`（过程间指向分析）、`-fipa-modref`（跨函数的读写副作用摘要）等（本机 `gcc --help=optimizers` 可列全，2026-07-25 实测存在）。但单个编译单元（.c 文件）里 IPA 只能看到本文件的函数；要跨文件（整个程序）做过程间优化，需要**链接时优化（Link-Time Optimization, LTO，`-flto`）**——它把各编译单元的中间表示（GIMPLE）保留到链接阶段，在看到全程序后统一做内联、跨模块常量传播、死函数消除等。

对初学者，这一节把前面的理论接回工具地面：过程间分析不是黑板概念，而是 `-O2/-O3` 下天天在跑的一堆 `ipa-*` pass（本机 `-O2` 就已把 static 函数内联+常量传播，见 C10.3.1 实测），而 LTO 是"把整个程序当一个大编译单元"从而让过程间优化跨越 `.c`/`.o` 文件边界的机制。要点与边界：LTO 的收益（尤其跨文件内联）常很可观，代价是链接更慢、更吃内存；间接调用/函数指针仍是 IPA 的老大难（受限于指针分析精度，见 C10.3.2/4）。具体 pass 的开关档位与实现细节随 gcc 版本演进，标锚版本 gcc 13.3 @2026-07-25。深入的过程间数据流/指针分析的**可靠性语义**交 L6-02，本篇止于"编译器为生成快代码而做"这一层。
