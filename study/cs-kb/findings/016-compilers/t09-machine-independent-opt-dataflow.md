## C9.1 流图与基本块

### C9.1.1 基本块：一条要么全跑要么全不跑的直线代码

**基本块（basic block）**是一段最大化的连续三地址指令序列，控制流只能从它的**第一条**指令进入、只能从它的**最后一条**指令离开——中间没有任何跳入点，也没有任何跳出（除最后一条外）。换句话说，只要执行到了块首，块内所有指令就会按顺序一条不落地全部执行。

对初学者，最好的直觉是"把程序切成不会半路拐弯的直线段"。为什么要切？因为直线代码没有分支，分析和优化都简单得多：块内每个变量的值怎么流动是完全确定的，可以直接顺着读。龙书给出机械的切分法——先找出所有**首领（leader）**指令，每个首领就是一个基本块的开头，块一直延伸到下一个首领之前。首领的判定规则只有三条：

(1) 程序的第一条指令是首领；

(2) 任何跳转（条件或无条件）的**目标**指令是首领；

(3) 紧跟在任何跳转之后的指令是首领。

把这三条应用一遍，程序就唯一地被切成了基本块。易错点是忘了规则 (3)：跳转指令的**下一条**也必须另起一块，因为控制流可能不走到它（被前面的跳转带走了）。

### C9.1.2 控制流图（CFG）：把基本块连成图

把每个基本块当作一个节点，块 B 末尾若能把控制转交给块 C（B 以跳到 C 结尾，或 B 顺次落到紧邻的 C），就画一条有向边 B → C，得到的有向图就是**控制流图（control-flow graph, CFG）**。通常再加两个虚拟节点：唯一的**入口（entry）**指向第一个基本块，所有会离开函数的块指向唯一的**出口（exit）**，方便分析统一起止。

初学者可以把 CFG 理解成"程序所有可能执行路线的地图"。它是本大主题后面一切全局分析的底座：数据流信息就是沿着 CFG 的边传播的，循环就是 CFG 里的环。一个术语要记牢——**前驱（predecessor）**和**后继（successor）**：B → C 时 B 是 C 的前驱、C 是 B 的后继。前向分析沿后继方向传播、后向分析沿前驱方向传播（见 C9.2）。CFG 只表达"控制可能怎么走"，不表达"数据怎么算"，所以它对每个分支都保守地认为两条路都可能走——这是编译器"宁可少优化也不能优化错"的安全底线。

本篇实证用 LLVM 观察真实 CFG：`clang -S -emit-llvm f.c` 产出的 IR 里，每个以标签开头、以 `br`/`ret` 结尾的段落就是一个基本块，`br` 的目标标签就是 CFG 的边；`opt -passes='dot-cfg'`（或旧式 `-view-cfg`）能把它导成 Graphviz 图。

### C9.1.3 局部优化：只在一个基本块内做的改写

**局部优化（local optimization）**是只看单个基本块、不跨块的优化。因为块内是直线代码，很多改写不需要任何全局信息就能安全做，是性价比最高的一档。典型的局部优化包括：局部公共子表达式消除、局部死代码消除、代数化简与常量折叠、以及把独立指令重排以利后续调度。

龙书给出的经典载体是**基本块的 DAG（有向无环图）表示**：为块内每个值建一个节点，同一个表达式重复出现时**复用**已有节点而不新建，这样一眼就能看出哪些计算是重复的（同一节点被多次引用 = 公共子表达式）、哪些计算的结果没人用（没有出边/不对应活跃变量 = 死代码）。举个最小例子，块内

a = b + c

b = a - d

c = b + c

d = a - d

第二条和第四条右边都是 `a - d`，建 DAG 时第四条直接复用第二条算出的节点，于是 `d` 可写成 `d = b`（`b` 此时正持有 `a-d` 的值）——这就是局部公共子表达式消除。要注意"局部"的边界：一旦离开这个块，`b` 可能被别的路径改写，块内推出的等式就不再成立，所以局部优化不能跨块外推，跨块的版本要靠 C9.4 的全局分析撑腰。

## C9.2 数据流分析框架

### C9.2.1 数据流分析要解决的问题：每个程序点上什么为真

**数据流分析（data-flow analysis）**是一套在不实际运行程序的前提下，静态推算"在每个程序点，某类信息取什么值"的通用方法。每个程序点关联两个数据流值——进入该点前的 IN 和离开后的 OUT；分析的产物就是给流图上每个点算出一个 IN/OUT。

初学者要抓住的核心矛盾是：程序有分支和循环，一个点可能从多条路径到达，你无法枚举所有实际执行路径（可能无穷），只能保守地**综合所有可能路径**给出一个"对每条路径都成立"或"至少一条路径上成立"的答案。数据流分析的天才之处在于：它不枚举路径，而是把"每个点的信息"当未知数，列一组方程，然后迭代解出来。C9.2 讲的就是这组方程长什么样、为什么解得出、解出来的是什么。它和 L6-02 V2 是同一套数学，区别只在目的——那边为证明程序安全，这边为生成快代码。

### C9.2.2 数据流方程：传递函数 + 汇合运算

一个数据流分析由两类方程刻画。**传递函数（transfer function）**描述一个基本块 B 如何把入口信息变成出口信息，写作

OUT[B] = f_B(IN[B])       （前向分析）

或对后向分析

IN[B] = f_B(OUT[B])

**汇合运算（meet / confluence operator，记作 ∧）**描述多条边在一点汇合时信息如何合并，前向分析里一个块的入口信息是所有前驱出口的汇合：

IN[B] = ∧ over P in pred(B) of OUT[P]

后向分析则对称地对后继取汇合。汇合运算通常是集合的**并（∪）**或**交（∩）**——用并还是用交，正是一个分析"保守方向"的体现（见 C9.3）。

直觉上，传递函数回答"走过这个块，信息怎么变"，汇合运算回答"几条路汇到一起，该信任哪些"。一个最常见的传递函数形式是 **gen/kill** 形式：

f_B(x) = gen_B ∪ (x − kill_B)

意思是"块 B 新产生的信息 gen_B，加上入口信息里没被 B 消灭（kill_B）的那部分"。四大经典分析（C9.3）都能套进这个 gen/kill 模子，只是各自的 gen/kill 定义不同。

### C9.2.3 格与偏序：数据流值住在什么结构里

所有可能的数据流值构成一个**格（lattice）**——一个带偏序 ≤ 的集合，任意两个元素都有唯一的最大下界（交/meet，∧）和最小上界（并/join）。数据流分析只用到半格即可（有 meet 就够）。格有一个**顶元素 ⊤（top）**和**底元素 ⊥（bottom）**。以活跃变量分析为例，格就是"变量集合的幂集"，偏序是子集包含 ⊆，meet 是并 ∪。

为什么非要把数据流值组织成格？因为格给了两样保证迭代能收敛、结果有意义的东西：一是**偏序**给了"信息更精确/更保守"的方向感（顺着 ≤ 走信息单调变化），二是**高度有限**（满足升链条件：不存在无限严格上升的链）保证迭代不会永远升下去。初学者不用被抽象代数吓到——把格想成"一把有刻度的尺子，数据流值只能沿刻度一格格移动，且尺子有头有尾"，迭代就是让每个点的值沿这把尺子单调滑到不能再滑，那个稳定位置就是答案。

### C9.2.4 单调性与迭代不动点算法

传递函数必须是**单调的（monotone）**：

x ≤ y  ⟹  f(x) ≤ f(y)

单调性 + 格的有限高度，是**迭代算法必然终止**的数学保证。迭代算法本身极简单：先把所有 IN/OUT 初始化成边界值（前向分析里 entry 给定、其余置 ⊤），然后反复扫过所有块、用方程重算每个 IN/OUT，直到某一整轮下来没有任何值再变——这个稳定状态就是**不动点（fixed point）**。

伪代码骨架（前向、gen/kill）：

```
OUT[entry] = boundary; 其余 OUT[B] = ⊤
while (有变化) {
    for each block B (逆后序):
        IN[B]  = ∧ over P in pred(B): OUT[P]
        OUT[B] = gen_B ∪ (IN[B] − kill_B)
}
```

单调性的直觉：信息只会朝一个方向"越变越保守"，绝不来回震荡，加上尺子有底，滑到底就停。真实实现常用**工作表算法（worklist algorithm）**优化——不每轮盲扫全部块，而是只把"入口信息变了的块的后继"放进待办表重算，把无谓重算省掉（详见 L6-02 V6.1）。本篇 C9.3 的实证里，一个五块含分支的流图跑活跃变量分析，迭代 2 轮即达不动点，正是"有限高度 + 单调 ⟹ 快速收敛"的体现。

### C9.2.5 MFP 与 MOP：迭代解和理想解的关系

迭代算法算出的解叫 **MFP（Maximum Fixed Point，最大不动点解）**。而理论上"最精确"的答案是 **MOP（Meet Over all Paths，全路径汇合解）**——对到达某点的**每一条**实际路径分别算传递函数、再把所有路径的结果汇合。两者的关系是编译原理里一个关键结论：

MFP ≤ MOP        （MFP 总是安全，可能更保守）

且当所有传递函数满足更强的**分配律（distributivity）**

f(x ∧ y) = f(x) ∧ f(y)

时，两者**相等**：MFP = MOP。

为什么迭代解可能不如全路径解精确？因为迭代算法在汇合点**先合并再传播**（把几条路的信息 meet 到一起再过传递函数），而 MOP 是**先各自传播到底再合并**——如果传递函数只单调不分配，"先合并"会丢掉一点信息，得到偏保守（但绝对安全）的答案。好消息是 gen/kill 形式的传递函数天然满足分配律，所以四大经典分析的迭代解就是最精确解；只有像常量传播这种传递函数不分配的分析，MFP 才会严格劣于 MOP（C9.3.4 会点到）。初学者记住一句话即可：迭代算得快且永远安全，绝大多数经典分析里它还恰好等于理想解；不分配的分析里它保守一点，但仍然可用。

## C9.3 经典数据流问题

### C9.3.1 到达定值分析（前向 / may / 并）

**到达定值（reaching definitions）**分析：对每个程序点，求出有哪些"定值"（对某变量的赋值语句）能够**不被重新覆盖地**流到该点。它是前向分析，汇合运算用并（∪），属于 **may（可能）**分析——只要**存在一条**路径让定值 d 流到该点，d 就算"到达"。传递函数是标准 gen/kill：

OUT[B] = gen_B ∪ (IN[B] − kill_B)

其中 gen_B 是 B 内产生且未被 B 内后续赋值覆盖的定值，kill_B 是被 B 内赋值所覆盖的、对同一变量的其他所有定值。

初学者可以把它理解成"这个值是从哪儿来的"的追踪。它的直接用途是常量传播和复制传播（C9.4）：要判断"此处用到的 x 是不是常量 5"，就看能到达这里的 x 定值是不是全都把 x 赋成了 5。用并、用 may 的原因是**安全方向**——如果漏算了一个能到达的定值，后续优化就会基于错误前提改代码（把不是常量的当常量），所以宁可多算（把可能到达的都算上）也不能少算。这就是 may 分析普遍用并的道理。

### C9.3.2 活跃变量分析（后向 / may / 并）

**活跃变量（live variables）**分析：对每个程序点，求出有哪些变量的当前值在将来**还可能被使用**（在被重新赋值之前）。它是**后向**分析（沿前驱方向、从出口往入口传播），汇合用并（∪），也是 may 分析。方程为

IN[B] = use_B ∪ (OUT[B] − def_B)

OUT[B] = ∪ over S in succ(B): IN[S]

其中 use_B 是 B 内"先使用后（未）定值"的变量，def_B 是 B 内被赋值的变量。

它是死代码消除和寄存器分配（C8.3）的地基：如果一个赋值 `x = ...` 之后 x 不再活跃，这个赋值就是死代码可删；寄存器分配则靠"两个变量是否在同一点同时活跃"来建干扰图。为什么后向？因为"将来会不会被用"这个问题的答案在**后面**，得从使用点往回倒推。下面是本篇的实证：一个含分支的五块流图，Python 手写后向迭代，**2 轮达不动点**——

```
fixpoint after 2 sweeps
B1: in=[]        out=['a','b']
B2: in=['a','b'] out=['a','c']
B3: in=['c']     out=['d']
B4: in=['a','c'] out=['d']
B5: in=['d']     out=[]
```

注意 B2 的 out 含 `a`：因为分支后继之一 B4 用到了 a，而 B3 没用——may 分析取并，只要**一条**后继路径还要 a，a 就在 B2 出口保持活跃。这直观演示了"后向 + 并"如何保守地跨分支保住一个变量。

### C9.3.3 可用表达式分析（前向 / must / 交）

**可用表达式（available expressions）**分析：对每个程序点，求出有哪些表达式（如 `x+y`）在到达该点的**每一条**路径上都已经被计算过、且其操作数此后都没被改动——即"这里再算一遍是白算，可以直接复用之前的结果"。它是前向分析，但汇合用**交（∩）**，属于 **must（必然）**分析——必须**所有**路径都算过才算可用。传递函数为

OUT[B] = e_gen_B ∪ (IN[B] − e_kill_B)

e_gen_B 是 B 内算出且其后未被 B 内改动操作数的表达式，e_kill_B 是操作数被 B 内赋值改动、因而失效的表达式。

它是全局公共子表达式消除（C9.4.2）的依据。与到达定值/活跃变量的关键对照是**用交不用并、must 不 may**：这里删一个"重复计算"必须百分百确定它真的重复（每条路都算过），漏删只是少优化（不出错），错删（某条路其实没算过、复用了脏值）就是灾难——所以安全方向反过来，取交、初始化成全集。把这三个分析的"方向 × 汇合"对照记住，是理解数据流分析设计的关键：may 分析用并求最小安全上界，must 分析用交求最大安全下界。

### C9.3.4 常量传播（前向 / 半格更复杂 / 传递函数不分配）

**常量传播（constant propagation）**分析：对每个变量在每个程序点，判断它是否恒为某个编译期已知常量，若是则值是多少。它是前向分析，但和前三个不同——它的数据流值不是简单的集合，而是给每个变量标一个格值，取自三层格：

⊤（尚不知） >  常量 c  >  ⊥（非常量 / 值冲突）

汇合运算：两条路给同一变量的常量若相同则保留、不同则降为 ⊥（不是常量）。

它是 C9.4.1 常量折叠/传播优化的分析支撑。要给初学者点明的关键差异是：**常量传播的传递函数只单调、不满足分配律**，所以（承 C9.2.5）它的迭代解 MFP 可能严格保守于理想解 MOP。经典反例是分支两侧 `x=2,y=3` 与 `x=3,y=2`，汇合后各自变 ⊥，于是 `x+y` 被判为非常量；但两条路径上 `x+y` 其实都等于 5，MOP 能发现这个常量而 MFP 发现不了。这不是 bug 而是"先合并后传播"的固有代价——编译器接受这点保守，换取算法的高效与终止性。记住：不是所有数据流分析都像 gen/kill 那样"迭代即最优"，常量传播就是最常被点名的例外。

## C9.4 局部与全局代码改进

### C9.4.1 常量折叠与常量传播

**常量折叠（constant folding）**是把编译期就能算出的常量表达式直接算掉，如把 `3 + 4` 换成 `7`；**常量传播（constant propagation）**是把"已知为常量的变量"在其使用处替换成该常量，如已知 `y == 3` 则把 `z = y + 4` 里的 y 换成 3。两者常联手迭代：传播暴露出更多可折叠的常量表达式，折叠又产生新常量供继续传播。

它依赖 C9.3.4 的常量传播分析提供"某点某变量是否常量"的结论。本篇 gcc 实证直观展示了这条链——源码

int f(int x){ int y = 3; int z = y + 4; int dead = x * 99; return z + x; }

经 `gcc -O1 -fdump-tree-optimized` 后优化 IR 为

```
int f (int x) {
  _2 = x_1(D) + 7;
  return _2;
}
```

`y=3` 折叠传播进 `z=y+4` 得 `z=7`，`dead=x*99` 被删（见 C9.4.3），最终 `z+x` 化为 `x+7`——常量折叠、传播、死代码消除三者协同的完整缩影。易错点：只有编译器能**证明**恒为常量才能替换，运行时才确定的值不行；且要小心溢出/浮点舍入语义，折叠必须严格复现目标机的算术结果，否则改变程序含义。

### C9.4.2 公共子表达式消除（CSE）

**公共子表达式消除（common subexpression elimination, CSE）**：若表达式 `a+b` 在某点已经被计算过、且其操作数 a、b 此后未被修改，则该点再次出现的 `a+b` 无需重算，直接复用先前的结果。局部 CSE 只在基本块内做（C9.1.3 的 DAG），**全局 CSE** 跨基本块，靠 C9.3.3 的可用表达式分析判定"此处 a+b 是否在所有到达路径上都可用"。

直觉是"别重复算同一件事"。最小例子：

t = a + b

...（a、b 未变）...

x = a + b   →   x = t

全局 CSE 的收益比局部大，但也更危险——必须由可用表达式分析（must/交）担保**每一条**路径都算过且操作数未变，否则复用到脏值就错了。这正是 C9.3.3 用交而非并的现实理由。一个常见配套是引入临时变量保存首次结果，但这会增加寄存器压力，和 C8.3 的寄存器分配存在张力（相位耦合的又一例）。

### C9.4.3 死代码消除（DCE）

**死代码消除（dead-code elimination, DCE）**：删除那些计算结果永远不会被使用的指令。一个赋值 `x = e` 是死的，当且仅当 x 在该点之后**不活跃**（且 e 无副作用）。它直接由 C9.3.2 的活跃变量分析驱动。相关但不同的是**不可达代码消除（unreachable-code elimination）**——删的是控制流永远到不了的整块代码，靠 CFG 可达性判定，不是数据流。

上面 C9.4.1 的实证里 `int dead = x * 99;` 就是死代码：它算出后从没被 return 用到，活跃变量分析判 `dead` 在其定值后不活跃，于是整条指令连同乘法一起被删。易错点有二：一是**副作用**，`x = f()` 即便 x 不活跃，若 f() 有副作用（改全局、I/O）也不能删；二是死代码常常是**其他优化的产物**——常量传播、复制传播替换掉变量使用后，原来的定值就"变死"了，所以 DCE 通常放在优化流水线较后、反复穿插着跑。

### C9.4.4 复制传播

**复制传播（copy propagation）**：遇到复制语句 `x = y` 之后，在能保证"此处 x 仍等于 y"（x、y 到该点都未被重新赋值）的使用点，把用到 x 的地方直接换成 y。它本身几乎不加速代码，但能**打通后续优化**——替换后原来的 `x = y` 往往变成死代码可删，也可能让两个表达式在文本上变得相同从而被 CSE 抓到。

直觉是"消灭无谓的中间人变量"。最小例子：

x = y

z = x + 1   →   z = y + 1   （随后 x=y 若无其他使用即成死代码，删）

它需要一个类似到达定值/可用复制的分析来担保替换安全：只有当到达使用点的 x 定值**唯一且就是 `x = y`**、且 y 一路未被改动时才能换。复制传播 + 常量传播 + DCE 三者反复迭代，是现代编译器"清理"阶段的标准组合，也是为什么优化 pass 要跑很多遍、彼此喂料的原因。

## C9.5 循环优化

### C9.5.1 支配关系：谁是谁的必经之路

节点 d **支配（dominates）**节点 n（记 d dom n），当且仅当从流图入口到 n 的**每一条**路径都必经过 d。每个节点支配自己；离 n 最近的严格支配者叫**直接支配者（immediate dominator）**，把所有节点连到其直接支配者得到**支配树（dominator tree）**。

支配关系本身也是一个数据流问题（前向、交），但它更重要的角色是**定义循环**的工具。直觉："要进 n，就绕不开 d"——比如循环头支配整个循环体。初学者常把支配和"前驱可达"搞混：B 能到 n 不等于 B 支配 n，支配要求**所有**路径都过 B，只要有一条绕过就不成立。支配树是循环识别、SSA 构造（C6.4 的 φ 放置）等一大批分析的公共基础设施。

### C9.5.2 自然循环与回边

**回边（back edge）**是一条 n → d 的边，其中 d 支配 n（即跳回一个必经的、更靠前的节点）。由一条回边 n → d 确定的**自然循环（natural loop）**是：循环头 d，加上所有"不经过 d 就能到达 n"的节点集合。自然循环有唯一入口（循环头 d），且是识别循环、施加循环优化的标准单位。

为什么不直接用"图里的环"而要用支配+回边这套定义？因为任意 CFG 里的环可能盘根错节、多入口，无法安全优化；自然循环靠"单入口 + 头支配全体"的良好结构，保证了"循环不变代码外提"等变换有明确、安全的落脚点（把代码搬到循环头前的**前置头 preheader**）。一个可优化的循环几乎总是自然循环；多入口的不规则环（irreducible）在结构化语言里罕见，编译器通常回避或先做节点分裂。记住这条链：支配 → 回边 → 自然循环 → 前置头，是所有循环优化的入场券。

### C9.5.3 循环不变代码外提（LICM）

**循环不变代码外提（loop-invariant code motion, LICM）**：如果循环体内某条计算的操作数在整个循环执行期间都不改变，它每轮算出的结果都一样，就把它**提到循环外**（前置头）只算一次。判定"循环不变"要靠到达定值：一个运算是不变的，若其每个操作数要么是常量、要么其所有到达定值都在循环外、要么本身已被判为循环不变（递归判定）。

这是收益最大的循环优化之一，因为循环体每少一条指令就乘以迭代次数的节省。本篇 LLVM 实证直接看到它：源码内层循环含 `a[i] * (m + 5)`，`clang -O1 -S -emit-llvm` 后 `m + 5` 被提到循环前置头——

```
5:                          ; 循环前置头(preheader)
  %6 = add nsw i32 %2, 5    ; m + 5 只算一次
  br label %10
10:                         ; 循环体
  %14 = load i32, ptr %13
  %15 = mul nsw i32 %14, %6 ; 复用外提结果
  ...
```

`m+5`（`%6`）搬到了块 `5:`（前置头）里只算一次，循环体 `10:` 只剩必要的 load/mul/add。易错点：外提必须保证**安全**——若该计算可能抛异常或有副作用、或循环可能一次都不执行（那就不该在循环外无条件执行它），编译器要么证明循环至少执行一次、要么用前置头（只在进入循环时才走）来避免改变语义。LLVM 的这个 pass 就叫 `licm`，可用 `opt -passes=licm` 单独触发。

### C9.5.4 归纳变量

**归纳变量（induction variable）**是每轮循环按固定量增减的变量。最基本的是循环计数器 i（如每轮 `i = i + 1`），称**基本归纳变量**；凡是能写成"基本归纳变量的线性函数" j = c·i + d 形式的变量（如 `j = 4*i + a`）称**派生归纳变量**，是识别强度削减机会的关键。

循环里大量地址计算和下标运算本质上都是归纳变量——访问 `a[i]` 的地址是 `base + 4*i`，随 i 线性变化。编译器先做**归纳变量识别**，把每个派生归纳变量表示成三元组 (基本变量, 系数 c, 偏移 d)，为后面的强度削减和归纳变量消除铺路。最小例子：循环里 i 从 0 每轮 +1，`t = 4*i` 就是派生归纳变量 (i, 4, 0)——它虽然写着乘法，实际每轮只是在上一次基础上 +4。看穿这一点，就能把乘法换成加法（C9.5.5）。

### C9.5.5 强度削减与归纳变量消除

**强度削减（strength reduction）**：把循环里代价高的运算换成等价的廉价运算，最经典的是把归纳变量里的**乘法换成加法**。对派生归纳变量 `t = c*i`，与其每轮重算乘法，不如引入一个变量随 i 同步递增：i 每 +1，t 就 += c。**归纳变量消除（induction-variable elimination）**更进一步：若一个基本归纳变量除了维持自己递增外别无他用（比如 i 只用于算 `4*i` 做地址），干脆删掉它、直接对派生变量做循环控制和终止判断。

最小例子，强度削减把

for (i=0; i<n; i++)  t = 4*i;  // 每轮一次乘法

改写成

t = 0;  for (i=0; i<n; i++) { ...; t = t + 4; }  // 每轮一次加法

在老式机器上乘法远贵于加法，这是实打实的加速；即便现代 CPU 乘法已不那么慢，强度削减仍能减少指令、简化地址计算、配合归纳变量消除删掉冗余计数器。易错点：改写必须严格保持数值等价（注意有符号/无符号溢出、循环边界的首末值），且这类变换通常要求循环已被识别为规范的自然循环、归纳变量已被正确分类——所以它排在 C9.5.1–C9.5.4 全部就绪之后。
