## C6.1 中间表示形态谱系

### C6.1.1 中间表示的定位与 m+n 论证

**中间表示（intermediate representation, IR）**是编译器在源程序与目标程序之间使用的内部程序表示。前端把源语言分析、翻译成 IR，后端把 IR 综合成目标代码，两者只通过 IR 接口耦合。引入 IR 的核心理由是把编译器从"每种源语言 × 每种目标机各写一个专用编译器"的 m×n 工作量，降为"m 个前端 + n 个后端"的 m+n 工作量——只要大家都翻译到／自同一种 IR。

这就是所谓的 **"m+n 论证"** 或"编译器脖子（narrow waist）"：IR 是那个细腰，前端各异、后端各异，中间收束到一处。

对初学者，最直观的类比是"翻译中转语言"：要把 5 种语言互译成 5 种语言，直接两两对译要写 5×5=25 本词典；若先都译成一种中间语（比如世界语），只需 5 本"源语→中间语"加 5 本"中间语→目标语"，共 10 本。编译器同理：GCC/LLVM 之所以能支持大量语言 × 大量芯片，正是因为它们各有一个稳定的公共 IR（GCC 的 GIMPLE/RTL、LLVM 的 LLVM IR）。第二个关键收益是**优化只写一遍**：机器无关优化（常量折叠、死代码消除等）写在 IR 层，所有前端、所有后端共享，不必为每种语言或每种机器重写。要点是 IR 不必只有一层——真实编译器常有**高、中、低多层 IR**（见 C6.1.2），越靠后越接近机器。

### C6.1.2 抽象层次谱系：高层、中层、低层 IR

IR 按"离源语言近还是离机器近"分为一个连续谱系。**高层 IR**（如 AST、带语义注解的语法树）保留源程序结构——循环、数组访问、类型仍是聚合形态，适合做与源结构相关的分析（依赖分析、源级变换）。**低层 IR**（如三地址码、LLVM IR、机器相关的 RTL）已经把控制结构拆成跳转、把数组访问拆成地址算术，适合做机器无关优化和指令选择。**中层 IR** 居于两者之间。

**越高层越像源码、越低层越像汇编；中间代码生成就是从高层 IR（AST）下降到低层 IR（三地址码/LLVM IR）的那一步**。

初学者容易以为"IR 只有一种"。实际是同一个编译器内部往往逐层下降（lowering）：AST → 高层 IR → 三地址码/SSA → 机器相关 IR → 汇编。每下降一层，源语言的某种抽象就被"摊开"成更原始的操作。比如 `for` 循环这个高层结构，到三地址码层就只剩下"初值赋值 + 条件跳转 + 递增 + 回跳"四段（C6.3 会看到真实产物）。选在哪一层做某项优化，取决于该优化需要哪些信息还没被摊掉——这是 Cooper & Torczon 反复强调的"IR 选择即工程权衡"。

### C6.1.3 语法树与 DAG

**语法树（syntax tree / AST）**是表达式和语句的树形 IR，每个内部节点是一个运算符、子节点是其运算对象。**DAG（directed acyclic graph，有向无环图）**是语法树的压缩形式：它把语法上不同但**值相同的公共子表达式合并成同一个节点**，因此一个节点可以有多个父亲。DAG 是识别公共子表达式的天然结构。

对表达式

a + a * (b - c) + (b - c) * d

对应的 DAG 里，`b - c` 只有一个节点，被 `a * (b-c)` 和 `(b-c) * d` 两处共享；而普通语法树会画出两棵独立的 `b - c` 子树。

为什么要 DAG？因为它一眼暴露**公共子表达式（common subexpression）**：图上一个有多个引用的节点，就是一处可以只算一次、结果复用的计算。构造 DAG 的办法是在建树时对每个"运算符+运算对象"组合先查表——若已存在相同节点则复用，否则新建（value numbering 的雏形）。初学者要注意 DAG 的"无环"前提：它表达的是一次求值内表达式的共享结构，不表达循环（循环由控制流图承载，见 C6.1.5）。DAG 主要用于基本块内的局部优化，是三地址码与优化之间的一座常用桥。

### C6.1.4 三地址码作为线性 IR

**三地址码（three-address code, TAC）**是一种线性 IR：每条指令最多含一个运算符和最多三个"地址"（两个运算对象、一个结果），因此一般形如

x = y op z

其中 x、y、z 是名字、常量或编译器生成的**临时变量（temporary）**。复杂的嵌套表达式被拆成一串这样的简单指令，每步的中间结果存进一个新临时变量。

对源表达式

x = a + b * c

三地址码把它拆成

t1 = b * c
t2 = a + t1
x = t2

三地址码的"三地址"直觉：一条指令最多摸三个数据位置，正好对应大多数机器"两源一目的"的算术指令，所以它离目标机很近、又不绑定具体机器。它是把树"拍平成一行行"的结果——每个原本的树内部节点对应一条指令、引入一个临时变量。为什么要拍平？因为优化和代码生成在线性指令序列上比在树上好做（顺序、跳转、活跃区间都显式了）。三地址码还包含赋值、跳转、条件跳转、函数调用、数组存取、指针存取等指令类型（完整清单见 C6.2.1）。它是龙书 Ch.6 的主力 IR，也是理解 SSA 和 LLVM IR 的基础形态。

### C6.1.5 图 IR：控制流图

**控制流图（control-flow graph, CFG）**是把三地址码按**基本块**组织起来的图 IR：节点是基本块（basic block，一段只能从头进入、从尾离开的、无内部跳转的最长指令序列），边表示块之间可能的控制转移（跳转/条件跳转/顺序流入）。CFG 是"线性三地址码 + 显式控制结构"的合体。

基本块的划分规则是先找**领导者（leader）**：程序第一条指令、任何跳转的目标、任何跳转指令的下一条，都是领导者；每个领导者到下一个领导者之前的所有指令构成一个基本块。

初学者可把 CFG 理解为"把一长条三地址码剪成若干段，再用箭头连回它们之间的跳转关系"。一段直线代码（无分支无跳转目标）就是一个基本块，块内指令必然从头执行到尾，不会中途跳走或跳入——这个性质让块内优化极其干净（顺序确定、无意外入口）。块之间的箭头则承载了 `if`/`while`/`goto` 的全部控制逻辑。CFG 是几乎所有全局数据流分析和优化（C9）的工作底盘，也是 SSA 定义 φ 函数位置（C6.4）的舞台。本机 clang 的 LLVM IR 就是天然的"CFG of 基本块"形态——C6.5 里每个 `label:` 段就是一个基本块，`br` 是块间边。

## C6.2 三地址码与地址翻译

### C6.2.1 三地址码的指令类型

**三地址码不止 `x = y op z` 一种形式**，龙书给出一组完整的指令类型，覆盖赋值、控制流、过程调用与内存访问。主要类型如下（每条独占一行）：

x = y op z      （双目运算赋值）
x = op y        （单目运算赋值，如取负、类型转换）
x = y           （复制）
goto L          （无条件跳转）
if x goto L / ifFalse x goto L      （条件跳转）
if x relop y goto L                 （关系条件跳转）
param x; call p, n; y = call p, n   （过程调用与参数）
x = y[i] / x[i] = y                 （数组存取，i 为字节偏移）
x = &y / x = *y / *x = y            （地址与指针）

这里 `op` 是任意二元/一元运算符，`relop` 是关系运算符（`<`、`==` 等），`L` 是指令标号。

初学者要抓住"每条指令都简单到能几乎一对一映射成一条机器指令"这个设计目标——这正是三地址码作为"接近机器又机器无关"IR 的意义。标号 `L` 让控制流显式：结构化的 `if`/`while` 在这里全部化成 `goto`/条件跳转（C6.3 详述）。数组和指针指令里的下标 `i` 通常已是**字节偏移量**而非元素序号（地址翻译的结果，见 C6.2.5）。这组指令类型就是后面四元式/三元式要"存储"的对象。

### C6.2.2 四元式（quadruples）

**四元式（quadruple）**是三地址码最常见的实现方式：把每条指令存成一个四字段记录

(op, arg1, arg2, result)

即"运算符、运算对象1、运算对象2、结果"。指令 `x = y op z` 存为 `(op, y, z, x)`；单目 `x = -y` 存为 `(minus, y, _, x)`（arg2 空）；复制 `x = y` 存为 `(=, y, _, x)`。

对

a = b * -c + b * -c

四元式序列（临时变量 t1…t4）为

| # | op    | arg1 | arg2 | result |
|---|-------|------|------|--------|
| 0 | minus | c    |      | t1     |
| 1 | *     | b    | t1   | t2     |
| 2 | minus | c    |      | t3     |
| 3 | *     | b    | t3   | t4     |
| 4 | +     | t2   | t4   | t5     |
| 5 | =     | t5   |      | a      |

四元式的关键优点是**结果字段显式命名了每个临时变量**，因此指令可以自由重排、移动而不破坏引用关系——优化器最爱这一点，因为搬动一条四元式不影响别人怎么找到它的结果。代价是临时变量多、占空间。初学者记住：四元式 = "一行四格的表格"，`result` 那格就是这条指令产出的名字，别人靠这个名字来引用它。

### C6.2.3 三元式与间接三元式

**三元式（triple）**省掉 result 字段，只存 `(op, arg1, arg2)`，用**指令自身的位置（编号）**来指代它的结果——即"第 i 条三元式的结果"就写作 `(i)`。这样省了临时变量的显式命名。**间接三元式（indirect triple）**在三元式数组之外再加一张**指令指针列表**，程序的执行顺序由这张列表给出，三元式本体只按创建顺序存放。

上例 `a = b * -c + b * -c` 的三元式为

| # | op    | arg1 | arg2 |
|---|-------|------|------|
| 0 | minus | c    |      |
| 1 | *     | b    | (0)  |
| 2 | minus | c    |      |
| 3 | *     | b    | (2)  |
| 4 | +     | (1)  | (3)  |
| 5 | =     | a    | (4)  |

三元式省空间，但有个致命弱点：**结果用"位置号"指代，一旦优化器移动某条指令，所有指向它的位置号都得改**——重排代价高。间接三元式正是为解决这点：三元式本体不动（位置号稳定），要重排只改那张指令指针列表的顺序即可。所以三种实现的权衡是——四元式最利于优化（显式临时名，随便搬），三元式最省空间但难搬，间接三元式在省空间的同时恢复了可重排性。初学者不必记死细节，抓住"result 显式命名 vs 用位置隐式指代"这条主轴即可。现代工业编译器（如 LLVM）实质走的是四元式思路的升级版——每条指令是一个带唯一名字的 SSA 值（C6.5）。

### C6.2.4 表达式翻译：用 SDT 生成三地址码

**表达式到三地址码的翻译**用语法制导翻译方案（SDT，承 C4）实现：给非终结符 `E` 配一个综合属性 `E.addr`（存放"该表达式的值放在哪个名字/临时里"）和 `E.code`（生成的三地址码串），在产生式的语义动作里边归约边生成指令、边申请新临时。核心产生式的语义规则（`gen` 表示"发射一条三地址码"，`newtemp` 申请新临时）：

E → E₁ + E₂    { E.addr = newtemp(); gen(E.addr '=' E₁.addr '+' E₂.addr) }
E → ( E₁ )     { E.addr = E₁.addr }
E → id         { E.addr = id.lexeme 对应的符号表条目 }

翻译 `a + b * c` 时，先递归归约出 `b * c` 生成 `t1 = b * c`（`E.addr = t1`），再归约 `a + (b*c)` 生成 `t2 = a + t1`。

这里的直觉是"每归约一个运算符节点，就发射一条指令、造一个新临时来接住它的结果"——临时变量的个数正好等于表达式里运算符的个数。`E.addr` 是综合属性（值自底向上流，承 C4.1.2），因此这套翻译能挂在自底向上（LR）分析器上一趟做完：归约的顺序恰好是"先算里层子表达式、再算外层"的正确求值顺序。初学者做题时常见错误是忘记"复制/括号不产生新指令"——`( E₁ )` 只是把地址透传，不 `gen` 任何东西。C6.5 会用 clang 的 LLVM IR 印证：一个 `a + b * c` 确实变成两条带唯一名字的指令。

### C6.2.5 数组引用的地址翻译

**数组引用 `a[i]` 要翻译成地址算术**，因为机器只认线性内存地址。对一维数组，若 `a` 的基地址为 `base`、每个元素宽 `w` 字节、下标从 0 起，则 `a[i]` 的地址为

addr(a[i]) = base + i * w

对二维数组 `a[i][j]`（行主序，行数无关、每行 n₂ 个元素、元素宽 w）：

addr(a[i][j]) = base + (i * n₂ + j) * w

翻译 `x = a[i]` 生成的三地址码（`t` 为临时）：

t1 = i * w
t2 = a[t1]     （或 t2 = base[t1]，取决于 base 表示）
x = t2

对初学者，关键是理解"下标 i 不是地址，i×元素宽才是字节偏移"。数组访问在源码里是一个漂亮的 `a[i]`，到 IR 层就被摊成"乘宽度求偏移 + 基址加偏移 + 取内存"这几步——这正是 C6.1.2 说的"下降时抽象被摊开"。多维数组按行主序（C/龙书）还是列主序（Fortran）会改变公式里下标的组合顺序，是一处**语言相关**细节：龙书默认行主序，公式 `((i₁×n₂+i₂)×n₃+i₃…)` 是逐维展开的 Horner 形式。C6.5 会看到 LLVM 用一条 `getelementptr` 指令专门干这件事，并且它把"下标 × 元素宽"的乘法隐含在类型信息里，比手写三地址码更类型安全。

### C6.2.6 类型、宽度与临时变量

**翻译时必须知道每个名字的类型**，因为地址算术中的"元素宽度 w"和数值运算的机器操作都由类型决定（`int` 加法与 `float` 加法是不同指令，`int[]` 与 `double[]` 的 w 不同）。翻译器一边翻译一边查**符号表**（承 C5.1）取类型与宽度；`newtemp` 生成临时变量时也要给它标类型，登记进符号表。

比如 `float x; int i;` 下翻译 `x = a[i]`，元素宽 w 取 `float` 的宽度（常见 4）；而 `a[i]` 若要参与 `x` 的浮点运算，还可能需要插入类型转换指令。

初学者容易忽略"临时变量也是有类型的变量"——它不是凭空的记号，编译器给它分配类型、宽度，后端才能给它选寄存器或栈槽。宽度信息还驱动**内存布局**：结构体成员偏移、数组步长、对齐都靠类型宽度算出。这一节把 C5（类型/符号表）和 C6（生成 IR）接上：语义分析算好的类型，正是中间代码生成做地址算术、选运算指令、造临时时的输入。若类型信息缺失或错误，地址翻译就会算错偏移——这是"规范与实现分账"的一处：源语言类型语义（C5）决定 w 的值，具体后端 ABI（L3-03）决定该类型在本机的实际字节宽。

## C6.3 控制流与布尔表达式翻译

### C6.3.1 布尔表达式的两种角色

**布尔表达式（如 `a < b`、`x && y`）在翻译时有两种可能角色**：一是当**数值**用（把真/假算成 1/0 存进某个名字，例如 `bool flag = a < b;`），二是当**控制流**用（决定跳到哪里，例如 `if (a < b) …`）。翻译方式随角色不同：数值角色生成算出 0/1 的指令，控制流角色生成**跳转代码（jumping code）**——用条件跳转直接实现分支，不物化出 0/1。

同一个 `a < b` 在

if (a < b) S

里被翻译成"若 `a < b` 为假就跳过 S"的跳转，而不是先算出一个布尔值再判断。

初学者常默认"布尔表达式一定先算出 true/false 再用"，但在 `if`/`while` 条件位置，编译器几乎总是走跳转代码——因为机器的条件跳转指令本就直接吃比较结果，中间物化一个 0/1 再测试它反而多余。判断走哪条路，看布尔表达式出现在**什么上下文**：赋值右侧走数值，控制流条件走跳转。C6.5 的 `cond.c`/`bool.c` 实证里能看到 clang 对条件位置的布尔表达式一律生成 `icmp` + `br`（跳转），只有需要一个布尔值时才用 `phi` 收敛出 0/1。

### C6.3.2 短路求值与跳转代码

**短路求值（short-circuit / lazy evaluation）**指 `&&`、`||` 按从左到右、能定则定的规则求值：`b1 && b2` 中若 `b1` 为假，则整体为假、**不再求值 `b2`**；`b1 || b2` 中若 `b1` 为真，则整体为真、不再求值 `b2`。翻译成跳转代码时，短路语义天然对应"提前跳转"。翻译方案给布尔表达式 `B` 配两个继承属性 `B.true`（为真时跳去的标号）、`B.false`（为假时跳去的标号）：

B → B₁ && B₂   { B₁.true = newlabel(); B₁.false = B.false;
                  B₂.true = B.true;    B₂.false = B.false; }

即 `B₁` 为真才落到 `B₂`（新标号），`B₁` 为假直接跳 `B.false`（短路，跳过 `B₂`）。

短路不仅是效率优化，更是**语义**：`p != NULL && p->x > 0` 依赖短路来避免空指针解引用——若 `p` 为空，`&&` 右侧根本不能执行。所以翻译必须忠实实现"左假即整体假、右侧不碰"。跳转代码把这一点做得很自然：`p != NULL` 为假的那条边直接跳到 `false` 出口，物理上就不会走到 `p->x`。C6.5 的 `bool.c` 实证会看到 `a < b && b < c`：clang 生成的第一条 `icmp slt`（`a<b`）的假分支直接 `br` 到最终 fall-through 块，跳过第二个 `icmp`——短路在 IR 上一目了然。

### C6.3.3 控制流语句的翻译

**结构化控制语句（`if`、`if-else`、`while`）翻译成"条件跳转 + 标号 + 无条件跳转"的组合**。给语句 `S` 配继承属性 `S.next`（S 执行完后应跳去的标号）。三个骨架：

if (B) S₁：
   B.true = newlabel(); B.false = S.next;
   S₁.next = S.next
   → B 的跳转代码; label B.true; S₁ 的代码

if (B) S₁ else S₂：
   B.true, B.false = 两个新标号; S₁.next = S₂.next = S.next
   → B 代码; label B.true; S₁; goto S.next; label B.false; S₂

while (B) S₁：
   begin = newlabel(); B.true = newlabel(); B.false = S.next; S₁.next = begin
   → label begin; B 代码; label B.true; S₁; goto begin

`while` 的产物就是"顶部判条件，真则执行体、跳回顶部，假则跳出"。

初学者把这三个骨架和 C6.5 的实证 IR 对上就通了：`sum.c` 的 `for` 循环（等价于 while）在 LLVM IR 里正是"一个条件判断块 `br i1 ... label ... label`、一个循环体块末尾 `br` 回判断块、一个出口块"。结构化语句在源码里是缩进和花括号，到 IR 层全部变成标号和跳转——**控制结构被"摊平"成 goto 网**。这也解释了为什么 CFG（C6.1.5）是三地址码的自然组织：翻译完的跳转代码天然就是一张基本块之间的图。

### C6.3.4 回填（backpatching）

**回填（backpatching）是一遍（one-pass）生成跳转代码的技术**：翻译到跳转指令时，其目标标号往往还没生成（例如 `if (B) …`，`B` 为真该跳去的位置在 `B` 翻译完时尚不知道），于是先发射一条"目标待定"的跳转，把它的地址记进一张列表；等目标标号确定后，再回头把列表里所有跳转的目标字段填上——这就是"回填"。

三个辅助操作：`makelist(i)` 造一个只含指令 i 的待填列表；`merge(p1, p2)` 合并两张列表；`backpatch(list, L)` 把 list 里所有指令的跳转目标填为 L。布尔表达式 `B` 改用两个综合属性 `B.truelist`、`B.falselist`（存"待填真/假出口"的指令列表），产生式动作：

B → B₁ && M B₂  { backpatch(B₁.truelist, M.quad);
                   B.truelist = B₂.truelist;
                   B.falselist = merge(B₁.falselist, B₂.falselist) }

其中标记非终结符 `M → ε { M.quad = nextquad }` 记下"下一条指令的位置"。

回填要解决的痛点是"向前跳转（forward jump）的目标在生成跳转时还不知道"。若不回填，就得两遍：第一遍生成、第二遍填目标。回填让编译器**边分析边生成、只走一遍**——发射跳转时目标留空并挂进列表，等分析器归约到目标位置时立刻 `backpatch`。初学者可类比写信时"地址栏先空着，等收信人确定了再统一填一批信封"。`nextquad` 是"下一条将生成的四元式序号"，`M` 这个空产生式的唯一作用就是在恰当时机把它记下来。回填是龙书 §6.7 的重点，也是一遍编译器（如早期 C 编译器）能高效生成跳转代码的关键工艺。

#### 来源与时效（本小主题末集中列）
- 锚点：龙书 2nd ed. 2006 §6.6（布尔表达式的两种角色、短路跳转代码、控制流语句翻译、`B.true`/`B.false`/`S.next` 继承属性）、§6.7（回填 backpatching、`truelist`/`falselist`/`makelist`/`merge`/`backpatch`、标记非终结符 M）；核实 2026-07-25。

## C6.4 SSA 形式

### C6.4.1 SSA 定义与动机

**静态单赋值形式（static single assignment, SSA）**是一种 IR 约束：程序中**每个变量在文本上只被赋值一次**（"静态单赋值"——指程序文本里每个名字只有一处定义，不是运行时只赋一次）。要满足这一约束，每次对源变量的重新赋值都改写成对一个**新版本名字**的赋值，例如源码里两次赋值 `x`，SSA 里写成 `x1 = …` 与 `x2 = …`，后续使用按位置引用对应的版本。

源代码

x = 1;
x = x + 1;

在 SSA 里变成

x1 = 1
x2 = x1 + 1

SSA 的核心动机是**让"定义-使用"关系一目了然**：既然每个名字只定义一次，那么"这个使用点用的是哪个定义"就没有歧义——名字本身就唯一标识了它的定义。这极大简化了后续的数据流分析与优化（常量传播、死代码消除、值编号等），因为分析器不必再费力追踪"某变量此刻的值来自哪次赋值"。SSA 是 1991 年 Cytron/Ferrante/Rosen/Wegman/Zadeck 系统化的，如今几乎所有工业编译器（LLVM、GCC 的 GIMPLE、V8、HotSpot）的核心 IR 都是 SSA 或其变体。初学者记住一句：**SSA = 给每次赋值发一个新名字，从此"名字"和"定义"一一对应**。

### C6.4.2 φ 函数

**φ 函数（phi function）解决"控制流汇合处该用哪个版本"的问题**。当两条（或多条）控制流路径在某个基本块汇合，而它们各自带来了同一源变量的不同 SSA 版本时，在汇合块开头插入一条

xₙ = φ(x_i, x_j, …)

表示"若从产生 x_i 的那条前驱边进来就取 x_i，从产生 x_j 的边进来就取 x_j"——φ 按"控制从哪条前驱边到达本块"来选值，结果绑定给新版本 xₙ。

对 `if (c) x = 1; else x = 2; use(x);`，两个分支分别定义 `x1 = 1`、`x2 = 2`，汇合块里需要

x3 = φ(x1, x2)

之后 `use(x3)`。

φ 函数是 SSA 唯一"不寻常"的构造，初学者最容易卡在这。关键直觉：单赋值约束在直线代码里好满足，但控制流一汇合，"用哪个版本"就取决于运行时走了哪条路——静态时无法确定，于是用 φ 这个"按来路选值"的伪指令占位。φ 不是真实机器指令，它在最终 lowering 到机器码时会被**消解**成在各前驱块末尾插入拷贝（out-of-SSA / phi elimination）。φ 必须放在基本块**最开头**、且并行语义（同一块的多个 φ 同时取值，互不影响）。C6.5 的 `cond.c`、`sum.c` 实证会看到真实的 `phi i32 [ %5, %4 ], [ %7, %6 ]`——正是"来自 %4 块取 %5、来自 %6 块取 %7"。

### C6.4.3 SSA 构造：φ 放置与变量重命名（指路 C9）

**把普通 IR 转成 SSA 分两步**：一是决定在哪些基本块开头插 φ 函数，二是给所有定义和使用重命名版本号。φ 的放置由**支配边界（dominance frontier）**决定——直观说，一个变量在块 B 定义后，凡是"B 支配不到、但控制流能从 B 也能从别处到达"的汇合点，就需要 φ。经典高效算法（Cytron et al. 1991）先算支配树与支配边界，在每个定义的支配边界上放 φ，再沿支配树重命名。

一个块 D **支配** 块 N，指从入口到 N 的每条路径都必经 D；B 的支配边界大致是"刚好不再被 B 独占支配的第一批汇合块"，那里正是不同版本可能碰头、需要 φ 的地方。

初学者不必掌握支配边界的完整算法（那属于 C9/数据流的纵深），只需理解"φ 不是到处乱插，而是精确插在控制流汇合、且确实有多个版本竞争的点上"。放太多 φ 浪费、放漏 φ 会错——支配边界给出的是恰好够用的最小集（minimal SSA 的一种）。本报告按 prompt 显式指路：**支配关系、支配边界的构造属于 L4-04 C9（机器无关优化/数据流）与 L6-02 的内容，此处只交代 SSA 为何需要它、不展开算法**。本机可用 `opt -passes=mem2reg`（见 C6.5.4）一键把 alloca 形式的 IR 提升为带 φ 的 SSA，无需手算支配边界即可观察产物。

### C6.4.4 SSA 与数据流分析的关系（喂 C9）

**SSA 之所以是现代 IR 的基石，是因为它让许多数据流分析从"迭代求解"退化为"顺着 def-use 链走一遍"**。在非 SSA 形式里，"某变量在某点的可能定义集合"要靠到达定值分析（reaching definitions）迭代计算；在 SSA 里，每个使用点的定义唯一（就是那个版本名的那一处定义，或一条 φ），def-use 链是现成的稀疏图，稀疏常量传播（SCCP）、全局值编号、死代码消除都因此更快更准。

例如常量传播：SSA 下 `x1 = 3; y1 = x1 + 1;` 里 `x1` 只有一个定义 `3`，直接代入即知 `y1 = 4`，无需数据流迭代确认"x 到这里一定是 3"。

初学者可以把 SSA 理解为"预先把数据流分析最费力的那部分（谁的值来自谁）编码进了名字本身"。这正是 prompt 所说的"SSA 构造动机——喂 C9 数据流"：SSA 是中间代码生成阶段就把 IR 整理成便于后续优化的形态，优化（C9）在 SSA 上做事半功倍。按 prompt 指路，**具体的到达定值/活跃变量/常量传播等数据流分析算法归 L4-04 C9 与 L6-02，本篇不展开**——这里只钉住"为什么生成 IR 时值得费力转成 SSA"这个动机。

- 锚点：Cooper & Torczon 2nd ed. 2011 §5.4.2 + §9.3（SSA 构造、φ 放置、支配边界、重命名），比龙书详尽——两书交叉核对 φ 语义、单赋值定义一致。

## C6.5 LLVM IR 一手实物

> 本节全部片段来自本机 clang/LLVM 18.1.3 真实产物。环境串：基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25（本组 clang/LLVM 18.1.3）。复现命令随各项给出；源文件（sum.c/cond.c/arr.c/bool.c）与命令均在仓库外 scratchpad，跑完即清。

### C6.5.1 LLVM IR 的三种形态与模块结构

**LLVM IR 有三种等价形态**：内存中的数据结构（编译器内部用）、人类可读的文本汇编（`.ll` 文件）、紧凑的二进制位码（`.bc` 文件）。教学与调试用文本形态，由 `clang -S -emit-llvm foo.c` 生成。一个 `.ll` 模块（module）顶层含目标数据布局、目标三元组、函数定义、全局变量、类型定义与元数据。本机 `sum.c` 产物的模块头（复现：`clang -S -emit-llvm -O0 sum.c`）：

```
; ModuleID = 'sum.c'
source_filename = "sum.c"
target datalayout = "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128"
target triple = "x86_64-pc-linux-gnu"
```

`target datalayout` 编码字节序（`e`=小端）、各类型的对齐与指针宽度；`target triple` 是"架构-厂商-系统"三元组，本机为 `x86_64-pc-linux-gnu`。

初学者把 `.ll` 文本当成"带类型、带无限寄存器的高级汇编"来读即可。`;` 起头是注释。模块 = 一个编译单元的全部 IR。这三种形态可互转（`llvm-as`/`llvm-dis`），语义完全等价——文本形态只是给人看的皮肤。datalayout/triple 的存在提醒我们：LLVM IR **并非完全机器无关**，它携带了目标机的字宽/字节序/对齐信息（这属于"规范与实现分账"里偏实现的一侧），但指令层面仍是机器无关的。

### C6.5.2 类型系统

**LLVM IR 是强类型的**：每个值都有显式类型。基本类型有任意位宽整数 `iN`（`i1` 是布尔、`i8` 字节、`i32` 常规 int、`i64` 长整型）、浮点 `float`/`double`、指针 `ptr`（LLVM 15+ 为**不透明指针 opaque pointer**，不再带指向类型，本机 18.1.3 已默认如此）、数组 `[N x T]`、结构体 `{T1, T2, …}`、向量 `<N x T>`、函数类型 `T (args)`。

`sum.c` 的函数签名（复现同上）：

```
define dso_local i32 @sum(i32 noundef %0) #0 {
```

`i32 @sum(i32 …)` 表示"接收一个 i32、返回 i32"；`@sum` 是全局符号（`@` 前缀），`%0` 是局部值（`%` 前缀）。

类型显式是 LLVM 相对龙书三地址码的一大加强——三地址码的临时变量类型隐含在符号表里，LLVM 直接写在每条指令上，验证器（`opt`/`llvm-verifier`）能静态查出类型错误。初学者要注意本机版本的一个演进点：**不透明指针**。老教程里指针写作 `i32*`、`%struct.Foo*`，而 LLVM 18 里一律是 `ptr`——指针不再携带被指类型，被指类型改由 `load`/`store`/`getelementptr` 指令显式标注（见 C6.5.5）。这是⚙演进项，凡看到 `i32*` 风格的旧 IR 需按版本折算。`i1` 是布尔（布尔表达式的数值角色产物就是 `i1`），`iN` 的任意位宽是 LLVM 的特色。

### C6.5.3 SSA、虚拟寄存器与 φ 指令

**LLVM IR 天生是 SSA**：`%` 开头的局部值是**虚拟寄存器**（无限多个），每个只被定义一次，正是 C6.4 的 SSA 落到实物。`sum.c` 经 `opt -passes=mem2reg` 后的 SSA 形态（复现：`clang -S -emit-llvm -O0 -Xclang -disable-O0-optnone sum.c | opt -passes=mem2reg -S`）：

```
define dso_local i32 @sum(i32 noundef %0) #0 {
  br label %2

2:                                                ; preds = %6, %1
  %.01 = phi i32 [ 0, %1 ], [ %5, %6 ]
  %.0 = phi i32 [ 0, %1 ], [ %7, %6 ]
  %3 = icmp slt i32 %.0, %0
  br i1 %3, label %4, label %8

4:                                                ; preds = %2
  %5 = add nsw i32 %.01, %.0
  br label %6

6:                                                ; preds = %4
  %7 = add nsw i32 %.0, 1
  br label %2, !llvm.loop !6

8:                                                ; preds = %2
  ret i32 %.01
}
```

`%.0`（循环变量 i）与 `%.01`（累加器 s）在循环头块 `2:` 各有一条 φ——`phi i32 [ 0, %1 ], [ %7, %6 ]` 意为"从入口块 %1 进来取 0，从循环体块 %6 回来取 %7"。

这段 IR 是本报告前四节的活教材：每个 `label:` 段是一个**基本块**（C6.1.5），`preds =` 注释列出前驱块（现成的 CFG 边）；`br label %2` 是无条件跳转、`br i1 %3, label %4, label %8` 是条件跳转（C6.3.3 的 while 骨架——判断块 `2:`、循环体 `4:`/`6:`、出口 `8:`）；两条 φ 精确对应 C6.4.2 讲的"循环变量在回边处的版本汇合"。`icmp slt` 是有符号小于比较（signed less-than），`add nsw` 是"无有符号回绕（no signed wrap）"标记的加法。初学者对着这段把"三地址码 + CFG + SSA + φ"一次性对齐，比读十页文字都清楚。

### C6.5.4 内存模型：alloca / load / store 与 mem2reg

**clang 在 `-O0` 下并不直接生成 SSA，而是先把每个局部变量放进栈内存（`alloca`），用 `load`/`store` 读写**——这样每个变量始终是一个内存位置、天然满足"单赋值"（赋值即 `store`），回避了直接建 φ 的难题。`sum.c` 的 `-O0` 未优化产物（复现：`clang -S -emit-llvm -O0 sum.c`）片段：

```
  %3 = alloca i32, align 4
  %4 = alloca i32, align 4
  store i32 0, ptr %3, align 4     ; s = 0
  store i32 0, ptr %4, align 4     ; i = 0
  ...
  %10 = load i32, ptr %3, align 4  ; 读 s
  %11 = load i32, ptr %4, align 4  ; 读 i
  %12 = add nsw i32 %10, %11        ; s + i
  store i32 %12, ptr %3, align 4   ; s = s + i
```

`mem2reg` pass 再把这些"栈上变量"提升（promote）为虚拟寄存器、按需插入 φ，得到 C6.5.3 那段干净 SSA。

这是 LLVM 工程上的关键分工，初学者务必理解：前端只管"无脑地"把每个变量落成 `alloca` + `load`/`store`（简单、不会错），把"提升为 SSA、插 φ"这件难事交给一个专门的、久经考验的 pass（`mem2reg`）统一做。命令 `opt -passes=mem2reg` 就是单独跑这个提升。对比 C6.5.3 与本段：同一个 `sum`，未优化版满是 `alloca/load/store`（对应 C6.2.1 的指针存取指令），mem2reg 后局部变量全变成 SSA 虚拟寄存器、循环变量凝成两条 φ——这就是"SSA 构造"（C6.4.3）在本机的一键实物。`align 4` 是对齐要求。

对 `cond.c`（`if (a>b) x=a+1; else x=b-1; return x*2;`）经 mem2reg 后，汇合处的 φ 尤其干净（复现：`clang -S -emit-llvm -O0 -Xclang -disable-O0-optnone cond.c | opt -passes=mem2reg -S`）：

```
4:                                                ; preds = %2
  %5 = add nsw i32 %0, 1        ; then: a+1
  br label %8
6:                                                ; preds = %2
  %7 = sub nsw i32 %1, 1        ; else: b-1
  br label %8
8:                                                ; preds = %6, %4
  %.0 = phi i32 [ %5, %4 ], [ %7, %6 ]   ; x = φ(then 版, else 版)
  %9 = mul nsw i32 %.0, 2
```

这正是 C6.4.2 的 `x3 = φ(x1, x2)` 教科书图景的真实对应——两分支各定义一版 `x`，汇合块 `8:` 用 φ 按来路选值。

### C6.5.5 getelementptr：地址计算指令

**`getelementptr`（GEP）是 LLVM 专门做地址算术的指令**，对应 C6.2.5 的数组/结构体地址翻译，但它把"下标 × 元素宽度"的乘法隐含在类型里、比手写三地址码更安全。`arr.c`（`return a[i] + a[j];`）在 `-O1` 的产物（复现：`clang -S -emit-llvm -O1 arr.c`）：

```
  %4 = sext i32 %1 to i64
  %5 = getelementptr inbounds i32, ptr %0, i64 %4
  %6 = load i32, ptr %5, align 4
  %7 = sext i32 %2 to i64
  %8 = getelementptr inbounds i32, ptr %0, i64 %7
  %9 = load i32, ptr %8, align 4
  %10 = add nsw i32 %9, %6
  ret i32 %10
```

`getelementptr inbounds i32, ptr %0, i64 %4` 意为"从基指针 %0 出发，按元素类型 `i32` 偏移 %4 个元素"——元素宽度（i32=4 字节）由类型 `i32` 自动决定，不必像三地址码那样显式写 `i * w`。

对照 C6.2.5 的手写三地址码 `t1 = i * w; t2 = a[t1]`：LLVM 把 `i*w` 折进 GEP 的类型语义，只留下"基址 + 下标（按类型步进）"。`sext i32 %1 to i64` 是把 32 位下标符号扩展到 64 位（指针宽度），这是本机 64 位目标的地址计算细节。`inbounds` 是一个优化提示，声明访问不越界（否则行为未定义），让优化器更激进。初学者抓住一句：**GEP 只算地址、不访问内存；真正的读写是随后的 `load`/`store`**——`%5 = getelementptr …` 算出 `a[i]` 的地址，`%6 = load i32, ptr %5` 才把值取出来。这与 C6.2.1"地址算术与内存访问分离"的三地址码设计一脉相承。

### C6.5.6 短路布尔的控制流实证

**布尔短路（C6.3.2）在 LLVM IR 里表现为"提前跳转、跳过右操作数"**。`bool.c`（`if (a<b && b<c) return 1; return 0;`）经 mem2reg 的产物（复现：`clang -S -emit-llvm -O0 -Xclang -disable-O0-optnone bool.c | opt -passes=mem2reg -S`）：

```
  %4 = icmp slt i32 %0, %1        ; a < b
  br i1 %4, label %5, label %8    ; a<b 假 → 直接跳 %8（短路，跳过 b<c）
5:                                                ; preds = %3
  %6 = icmp slt i32 %1, %2        ; b < c （仅当 a<b 为真才到达）
  br i1 %6, label %7, label %8
7:
  br label %9
8:                                                ; preds = %5, %3
  br label %9
9:
  %.0 = phi i32 [ 1, %7 ], [ 0, %8 ]   ; 结果 1/0 由来路决定
  ret i32 %.0
```

第一条 `icmp slt`（`a<b`）的**假分支直接 `br` 到 %8**，根本不进入算 `b<c` 的块 %5——短路语义在控制流上被忠实实现。

这段把 C6.3 整节坐实：布尔表达式在条件位置走**跳转代码**（`icmp` + `br`），`&&` 的短路 = "左假即跳出、不碰右侧"（%4 假直接到 %8），最终若需要一个布尔数值（这里 `return` 的 1/0）才用 `phi` 在汇合块 %9 收出。初学者把这段与 C6.3.2 的翻译方案（`B₁.false = B.false` 让左操作数假时直跳整体假出口）对照，就能看到教科书的继承属性方案与工业编译器产物是同一件事。注意 clang 未优化路径里 %7/%8 各先 `br` 到 %9 再由 φ 汇合，是 `-O0`+mem2reg 的朴素形态，更高优化级会进一步简化。
