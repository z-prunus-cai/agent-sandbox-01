本报告有一条贯穿始终的心智模型，**语法分析（parsing）就是拿词法阶段吐出的记号流，去核对「这串记号能不能由文法一步步推导出来」，能则顺手搭出一棵反映语法结构的树，不能则报语法错。** 一切分析器本质上都在回答同一个问题——「给定文法 G 和输入串 w，w ∈ L(G) 吗？若是，它的结构是什么？」——只是走的方向不同：自顶向下从开始符号出发、试着往下推导去凑出输入（像做完形填空，先猜整体框架再填细节）；自底向上从输入记号出发、往上归约回开始符号（像拼图，先把小块拼成大块直到拼出全图）。两族各有能处理的文法类别（LL 系 vs LR 系），能力谱系和工程取舍不同，但都建立在同一套 CFG/推导/分析树的形式底座上。整个大主题的路线是：先打底座并把文法「整形」成分析器吃得下的形状（C3.1 CFG 与推导、二义性/左递归/左公因子）；再讲自顶向下一族（C3.2 FIRST/FOLLOW、LL(1) 预测表、递归下降）；转入自底向上一族的地基（C3.3 移进-归约、句柄、LR(0) 项集与自动机）；铺开自底向上的三种实用表构造与能力谱系及冲突（C3.4 SLR/LR(1)/LALR）；最后落到真实生成器与错误恢复（C3.5 Yacc/Bison、优先级消解二义、panic-mode）。

## C3.1 CFG 与推导/分析树

### C3.1.1 上下文无关文法(CFG)：语法分析的规约语言

上下文无关文法是描述编程语言语法的标准工具，形式上是一个四元组

G = (V, T, P, S)

其中 T 是**终结符**集合（就是词法阶段产出的记号，如 `id`、`+`、`(`），V 是**非终结符**集合（代表语法构造，如「表达式」「语句」），S ∈ V 是**开始符号**，P 是一组**产生式**，每条形如

A → α

左部 A 是单个非终结符、右部 α 是终结符与非终结符组成的串（可为空 ε）。语言 L(G) 就是从 S 出发、反复用产生式替换非终结符，最终能得到的所有终结符串的集合。

「上下文无关」这个名字的关键在于产生式左部**只有一个非终结符**——替换 A 时不看它左右的上下文，任何出现 A 的地方都能用 A 的任一产生式替换。这比正则表达式强（能表达括号配对、嵌套结构这类需要「记住配对深度」的语法，正则做不到），又比一般文法弱（左部只能是单个非终结符，可判定、可高效分析），恰好卡在描述编程语言语法的甜区。初学者最容易混的是「文法层次」：词法用正则（C2），语法用 CFG（本章），因为语言的嵌套结构（表达式里套表达式、块里套块）本质上需要 CFG 这一级的表达力。一个常用记法约定：小写字母/记号是终结符，大写字母是非终结符，希腊字母 α、β 表示任意文法符号串——本报告沿用这套龙书记法。

### C3.1.2 推导：最左推导与最右推导

**推导（derivation）**是「用产生式右部替换左部非终结符」的一步步展开。记

αAβ ⇒ αγβ    （当 A → γ 是一条产生式）

⇒ 读作「一步推导出」，⇒* 表示「零步或多步推导出」。若每一步都替换当前句型里**最左**的那个非终结符，叫**最左推导（leftmost derivation）**，记 ⇒lm；每步都替换**最右**非终结符，叫**最右推导（rightmost derivation）**，记 ⇒rm。最右推导也叫**规范推导（canonical derivation）**。

为什么要区分最左/最右？因为它直接对应两大分析族。自顶向下分析（LL）产出的正是**最左推导**——它从开始符号出发，总是先展开最左边的非终结符去匹配下一个输入记号。自底向上分析（LR）产出的是**最右推导的逆序**——它归约时，等价于把最右推导倒着走。理解这层对应，后面「为什么 LL 叫从左、LR 的 R 指最右推导」就顺理成章了（LR 里 L 表示从左到右扫描输入，R 表示构造最右推导）。举个最小例子，对文法

E → E + E | id

推导 `id + id`，最左推导是 E ⇒ E + E ⇒ id + E ⇒ id + id，最右推导是 E ⇒ E + E ⇒ E + id ⇒ id + id——同一棵树，展开顺序不同。

### C3.1.3 分析树与句型：推导的结构化表示

**分析树（parse tree）**是把推导「画成树」：根是开始符号，内部结点是非终结符，某结点 A 的子结点从左到右拼起来正好是某条产生式 A → X₁X₂…Xₙ 的右部，叶子从左到右拼起来就是被分析的串。一次推导对应一棵分析树；但同一棵分析树可能对应多条推导（最左、最右等），因为它只记录「谁是谁的儿子」的结构、不记录展开先后。分析器的最终产物就是这棵树（或它的精简版 AST，见 C4）。

初学者要抓住「分析树抹掉了推导顺序、只保留结构」这一点：最左推导和最右推导若产出同一棵树，说明它们描述的是**同一个语法结构**，只是叙述次序不同。这也是判断二义性的关键工具（下一节）——二义不看「有几条推导」，而看「有几棵不同的分析树」。补充一个术语：推导过程中出现的中间串（含非终结符的）叫**句型（sentential form）**；全部由终结符组成的句型叫**句子（sentence）**，也就是 L(G) 的成员。

### C3.1.4 二义性及其消除

若某个句子存在**两棵或以上不同的分析树**（等价地：存在两个不同的最左推导，或两个不同的最右推导），该文法就是**二义的（ambiguous）**。二义文法对编译器是麻烦，因为一个程序会有多种合法结构解释、语义不唯一。典型例子是表达式文法

E → E + E | E * E | ( E ) | id

对 `id + id * id`，既能先归 `+` 再归 `*`（解释成 `(id+id)*id`），也能先归 `*`（解释成 `id+(id*id)`），两棵树、两种算法优先级，二义。

消除二义有两条路。其一，**改写文法**引入优先级/结合性层次，把二义文法等价改成无二义文法。经典改法是给每个优先级一层非终结符：

E → E + T | T

T → T * F | F

F → ( E ) | id

这里 `*` 被塞进更「深」的 T 层，天然比 `+` 先归约，`+` 因左递归而左结合——`id + id * id` 只剩一棵树。其二，**保留二义文法 + 外加消解规则**（优先级/结合性声明），让生成器在冲突处按规则选一条——这是 Yacc/Bison 的实用做法，见 C3.5。另一个必讲的二义例子是**悬空 else（dangling else）**：

stmt → if expr then stmt

stmt → if expr then stmt else stmt

stmt → other

`if e1 then if e2 then s1 else s2` 里的 else 该配哪个 if 有歧义，通行规则是「else 配最近的未匹配 if」，落到分析器上就是「遇 else 优先移进」（C3.5.3）。初学者要记住：二义是**文法的性质**、不是语言的性质——同一门语言常有二义与无二义两套文法，编译器要的是后者（或前者+消解规则）。判定「一个 CFG 是否二义」在一般情况下是**不可判定**的，所以实践中靠已知模式（表达式分层、悬空 else 就近匹配）而非通用算法处理。

### C3.1.5 消除左递归

若非终结符 A 存在推导 A ⇒⁺ Aα（右部以自己打头），称文法含**左递归**。直接左递归形如 A → Aα。左递归会让自顶向下分析器（尤其递归下降）**无限递归**——要展开 A 就先展开 A，永远沉不到底，所以 LL 一族必须先消除左递归。对一组产生式

A → Aα | β

（β 不以 A 打头）可等价改写为

A → β A'

A' → α A' | ε

引入新非终结符 A' 把「左递归」翻成「右递归」，语言不变但不再左循环。上例表达式文法消左递归后变成

E → T E'

E' → + T E' | ε

T → F T'

T' → * F T' | ε

F → ( E ) | id

这套无左递归形式正是后面 LL(1)/递归下降的标准输入。直觉上，左递归 `A → Aα` 生成的是 `βαα…α`（β 后面跟一串 α），改写后用 `A' → αA' | ε` 把「跟一串 α」显式表达成右递归，机器就能靠「看下一个记号决定还要不要再来一个 α」来驱动，不必先无脑递归。易错点：这只处理**直接**左递归；**间接**左递归（A ⇒ Bα ⇒ Aαβ 绕一圈回到 A）需龙书 §4.3.3 的通用算法（先给非终结符定序、逐个代入消除）先化为直接左递归再消。另需注意，消左递归会改变分析树形状（引入 E' 等辅助结点），语义动作要相应调整——但它**不改变所定义的语言**。

### C3.1.6 提取左公因子

**左公因子（left factoring）**处理「两条产生式右部有相同前缀」的情形，它让自顶向下分析器在只看有限个（LL(1) 是 1 个）记号时无法决定选哪条。对

A → αβ₁ | αβ₂

公共前缀 α 使得看到 α 时分不清走 β₁ 还是 β₂。提左因子改写为

A → α A'

A' → β₁ | β₂

把「选择点」推迟到 α 之后——先无条件吃掉公因子 α，等看到能区分 β₁/β₂ 的记号再分叉。经典场景还是悬空 else 或

stmt → if expr then stmt | if expr then stmt else stmt

两条都以 `if expr then stmt` 打头，提左因子后

stmt → if expr then stmt rest

rest → else stmt | ε

这样看到 `if` 时不必立刻决定有没有 else。左因子与左递归是自顶向下分析的**两道预处理关卡**：左递归让分析器沉不下去，左公因子让分析器在分叉点看不清路，二者都会破坏 LL(1)「用 1 个前看记号唯一定路」的前提，所以 C3.2 的 LL(1) 建表前默认文法已消左递归、已提左因子。要点：提左因子和消左递归一样是**保语言的等价变换**，只是把文法整形成「前看 1 个记号即可决策」的形状；有些文法做完这两步仍非 LL(1)（比如本质二义），那就得换 LR 一族或加消解规则。

## C3.2 自顶向下分析

### C3.2.1 自顶向下分析与递归下降总览

**自顶向下分析（top-down parsing）**从开始符号出发，尝试构造一个**最左推导**去逐记号匹配输入——每步为「当前最左非终结符」挑一条产生式展开，展开后新露出的最左符号若是终结符就跟输入比对、是非终结符就继续展开。最朴素的实现是**递归下降（recursive descent）**：给每个非终结符写一个函数，函数体按产生式右部依次「匹配终结符 / 调用对应非终结符的函数」。若挑产生式时可能挑错、需退回重试，叫**带回溯的递归下降**；若能靠前看 1 个记号唯一确定挑哪条、永不回溯，就是**预测分析（predictive parsing）**，对应 LL(1) 文法。

直觉上自顶向下像「按语法规则做完形填空」：先假设整个输入是一个 `E`，展开 E 的规则、看看第一个记号符不符合期望，符合就继续往下细化。递归下降之所以受欢迎，是因为它**代码结构直接映射文法**——一个非终结符一个函数、产生式右部就是函数体，手写清晰、易加语义动作和好的报错信息（很多工业编译器如 GCC 的 C++ 前端、Clang 都用手写递归下降）。回溯版本通用但可能指数级慢且难加语义动作（撤销副作用麻烦），所以实用的自顶向下几乎都是**无回溯的预测分析**，代价是文法必须满足 LL(1)（先做 C3.1 的消左递归、提左因子，再看 FIRST/FOLLOW 是否满足条件）。LL 的两个 L：第一个 L 指从左到右（Left-to-right）扫描输入，第二个 L 指产出最左推导（Leftmost derivation），括号里的 1 指前看 1 个记号。

### C3.2.2 FIRST 集

FIRST(α) 是「从文法符号串 α 出发，能推导出的所有串的**第一个终结符**」的集合；若 α 能推出空串 ε，则 ε 也放进 FIRST(α)。它回答自顶向下分析最核心的问题：面对若干候选产生式，看到下一个记号 a，该走哪条？——走那条右部 FIRST 里含 a 的。计算规则（对文法符号 X）：

若 X 是终结符，则 FIRST(X) = { X }。

若 X → ε 是产生式，则把 ε 加入 FIRST(X)。

若 X → Y₁Y₂…Yₖ，则把 FIRST(Y₁)\{ε} 加入 FIRST(X)；若 ε ∈ FIRST(Y₁) 再看 Y₂……若 Y₁…Yₖ 全都能推出 ε，则把 ε 也加入 FIRST(X)。

对 C3.1.5 那套无左递归表达式文法，标准结果是

FIRST(E) = FIRST(T) = FIRST(F) = { ( , id }

FIRST(E') = { + , ε }

FIRST(T') = { * , ε }

直觉是「一个构造能以哪些记号打头」。易错点集中在 ε 的处理：只有当一个符号**可能整个消失**（推出 ε）时，才继续看它后面的符号能打头什么——因为它一消失，后面的符号就顶到最前面了。这正是 ε ∈ FIRST(Y₁) 时要「顺延看 Y₂」的原因。FIRST 是纯粹关于「右部能打头什么」的信息，还不涉及「这个非终结符后面能跟什么」——那是 FOLLOW 的活。

### C3.2.3 FOLLOW 集

FOLLOW(A) 是「在某个句型中，可能**紧跟在非终结符 A 右边**的终结符」的集合；输入结束标记 $ 也算（表示 A 后面可能就是输入结尾）。计算规则：

把 $ 加入 FOLLOW(S)（S 为开始符号）。

若有产生式 A → αBβ，则把 FIRST(β)\{ε} 加入 FOLLOW(B)。

若有 A → αB，或 A → αBβ 且 ε ∈ FIRST(β)，则把 FOLLOW(A) 加入 FOLLOW(B)。

对无左递归表达式文法，标准结果是

FOLLOW(E) = FOLLOW(E') = { ) , $ }

FOLLOW(T) = FOLLOW(T') = { + , ) , $ }

FOLLOW(F) = { + , * , ) , $ }

FOLLOW 的用途是处理「一条产生式能推出 ε」的情形：当某产生式 A → α 里 α 可能整个变没（FIRST(α) 含 ε），分析器看到的下一个记号其实是「A 后面的东西」，此时该不该选 A → α？——看这个记号在不在 FOLLOW(A) 里。直觉例子：`E' → +TE' | ε`，若下一个记号是 `)`（在 FOLLOW(E') 里），就选 E' → ε 让 E' 空掉、把 `)` 留给外层。易错点有二：其一，ε **永远不进 FOLLOW 集**（FOLLOW 只装真实终结符和 $）；其二，第三条规则里「把 FOLLOW(A) 加入 FOLLOW(B)」经常需要反复迭代到不动点——因为 FOLLOW 之间互相依赖，得一轮轮加直到没有新元素。

### C3.2.4 LL(1) 文法与预测分析表

一个文法是 **LL(1)** 的，当且仅当对每个非终结符 A 的任意两条不同产生式 A → α 和 A → β，都满足：

FIRST(α) ∩ FIRST(β) = ∅

且若 ε ∈ FIRST(α)，则 FIRST(β) ∩ FOLLOW(A) = ∅（对称地反之亦然，且 α、β 中至多一个能推出 ε）。

满足这条就能建**预测分析表** M[A, a]（行是非终结符、列是终结符/$），规则是：对每条产生式 A → α，对每个 a ∈ FIRST(α)，令 M[A, a] = A → α；若 ε ∈ FIRST(α)，则对每个 b ∈ FOLLOW(A)（含 $，若 $ ∈ FOLLOW(A)），令 M[A, b] = A → α。若建表时**某格被填入两条产生式**，说明文法非 LL(1)。

LL(1) 条件的本质是「前看 1 个记号就能唯一定路，绝不含糊」：两条产生式能打头的记号集不许重叠（否则看到重叠记号不知走哪条）；若一条可能空掉，那它的「跟随集」也不能撞上另一条的打头集（否则不知该空掉当前非终结符还是走另一条）。初学者最该内化的是「LL(1) 是文法的可判定性质」——给定文法，算完 FIRST/FOLLOW、建完表看有没有冲突，就知道是不是 LL(1)，不必猜。易错点：很多自然写法的文法（含左递归、含左公因子、或本质二义）非 LL(1)，得先做 C3.1 的整形；整形后仍冲突的（如需要看多个记号才能决策），要么换 LL(k)/换 LR 族，要么手工消解。

### C3.2.5 表驱动的非递归预测分析

有了预测分析表就能写一个**不用递归、只用一个显式栈**的分析器。栈初始放 `$` 和开始符号 S，输入串末尾加 `$`。主循环看栈顶 X 和当前输入记号 a：

若 X = a（都是终结符且匹配），弹栈、读下一个输入记号（匹配成功）。

若 X 是非终结符，查 M[X, a]：得到产生式 X → Y₁…Yₖ 就弹出 X、把 Y₁…Yₖ **逆序压栈**（使 Y₁ 在栈顶）；查到空格则报语法错误。

若 X = a = $，分析成功接受。

这套流程和递归下降是**同一个算法的两种外衣**——递归下降用程序调用栈隐式记录「待展开的符号」，表驱动用显式数据栈记录同样的东西，还多一张表来「查该走哪条产生式」。为什么右部要**逆序**压栈？因为栈后进先出，想让最左符号 Y₁ 最先被处理（放栈顶），压栈时就得从 Yₖ 压到 Y₁。表驱动版本的好处是不受宿主语言递归深度限制、便于用生成器自动产出；递归下降版本的好处是可读、易插语义动作与定制报错。两者都要求文法 LL(1)、都产出最左推导。

### C3.2.6 实证：递归下降如何被左递归卡死、无左递归文法如何被前看驱动

用本机 Python 3.11.15 就能直观看到「左递归让递归下降沉不下去、无左递归文法靠前看记号驱动」这件事（脚本仅演示原理，不入库）。对左递归 `E → E + T | T`，递归下降函数 `parseE()` 第一件事就是调用 `parseE()`，栈无限增长直到 `RecursionError`——这正是 C3.1.5 必须先消左递归的运行时证据。改成无左递归形式后，`parseE'` 靠「下一个记号是不是 `+`」决定走 `+TE'` 还是走 ε（即 `+ ∈ FIRST(E')` 则展开、否则当前记号应 ∈ FOLLOW(E') 才收手），全程前看 1 个记号、无回溯，正好印证 LL(1) 的「1 个前看记号唯一定路」。

这条实证给初学者的校准在于，LL(1) 不是抽象约束，而是「能不能写出不递归爆栈、不回溯的下降分析器」的直接判据。FIRST 决定「该不该展开某条产生式」，FOLLOW 决定「该不该让某个非终结符空掉」，两者合起来就是那张预测表的全部内容。（本条为原理级实证，未附完整脚本；表驱动/递归下降等价性以龙书 §4.4 为准。）

## C3.3 自底向上分析基础

### C3.3.1 移进-归约分析模型

**自底向上分析（bottom-up parsing）**从输入记号出发，反复把「若干符号」替换回某条产生式的左部（归约），一路往上直到只剩开始符号——它构造的是**最右推导的逆序**。主流实现是**移进-归约（shift-reduce）**分析器：用一个栈存「已看过、尚未归约完的符号」，对输入做两类主要动作：

移进（shift）动作把下一个输入记号压入栈。

归约（reduce）动作在栈顶若干符号恰好匹配某产生式 A → β 的右部 β 时触发，把 β 弹出、压入左部 A。

此外还有接受（accept，栈中恰为开始符号且输入耗尽）与报错（error）两类动作。分析器就是一串 shift/reduce 决策，栈顶的活跃部分随之伸缩。

直觉上移进-归约像「拼图」：不断从输入拿小块（移进），一旦手里的几块能拼成一个更大的语法构造就拼起来（归约），直到拼出整张图（开始符号）。它比自顶向下强在——归约发生在「已经看到整个右部之后」，决策时信息更充分，所以能处理的文法类更大（LR 族严格包含 LL 族），且**天然容纳左递归**（不像 LL 必须先消）。核心难点只有一个：**每一步到底该移进还是归约、归约时用哪条产生式**？——回答这个问题需要「句柄」概念（C3.3.2）和一台自动机（C3.3.3–4）来指路。LR 命名里 L 指从左到右扫描输入、R 指产出最右推导（的逆）。

### C3.3.2 句柄与句柄剪枝

**句柄（handle）**是移进-归约分析的核心概念：在一个最右句型中，句柄是「一个与某产生式右部匹配、且**归约它就等于把最右推导倒退一步**」的子串（连同它在句型中的位置）。自底向上分析的本质就是**句柄剪枝（handle pruning）**——反复找到当前句型的句柄、归约掉，直到回到开始符号。形式化地，若

S ⇒*rm αAw ⇒rm αβw

则 A → β 是句型 αβw 的一个句柄，且句柄右边的 w 全是终结符。

为什么强调「归约句柄」而不是「归约任何匹配右部的子串」？因为随便找一个匹配某产生式右部的子串归约，可能**归错**、走进死胡同（归约出的句型再也回不到开始符号）。句柄是「正确的那一次归约」——它保证每一步都对应最右推导的一步逆行。初学者可这样体会：对 `id + id * id`（用表达式文法），第一步句柄是最左那个 `id`（归约成 F），而不是能匹配的别的东西；句柄总在「已扫描部分的末尾附近」，其右边一定是尚未移进的终结符。难点在于**如何在扫描中即时认出句柄**——手工找句柄靠经验，机器则把「所有可能的句柄前缀」编码进一台 DFA，这就是下一节 LR(0) 自动机要干的事。「栈顶恰好是一个句柄」正是 shift-reduce 分析器决定「该归约」的时机。

### C3.3.3 LR(0) 项与项集的闭包、GOTO

要让机器认出句柄，先引入 **LR(0) 项（item）**：一条产生式加一个「点」标记分析进度，如

A → α · β

表示「A 的这条产生式，α 部分已在栈上、β 部分还期待在输入中看到」。点在最右（A → γ·）叫**归约项**（该归约了）；点后面是终结符叫可**移进项**。分析前先把文法**增广**：加一条 S' → S，使接受状态唯一。

两个运算把项组织成状态。**闭包 CLOSURE(I)**：若项集 I 含 A → α·Bβ（点后是非终结符 B），就把 B 的所有产生式的初始项 B → ·γ 也加进来，反复到不动点——直觉是「既然期待看到一个 B，就同时期待看到任何能开启 B 的东西」。**转移 GOTO(I, X)**：把 I 中所有形如 A → α·Xβ 的项的点右移一格（变 A → αX·β），再取闭包——表示「在状态 I 上读入文法符号 X 后到达的新状态」。

初学者最容易卡在「点」的含义：它不是文法的一部分，而是**分析进度的书签**，标记「这条产生式我看到哪儿了」。闭包的作用是「展开所有当下可能刚开始的产生式」，所以一个状态里往往塞着好几条产生式的项——它们是「此刻所有可能正在进行的归约」的并集。GOTO 就是这台自动机的状态转移函数。举例，增广表达式文法的初始状态

I₀ = CLOSURE({ E' → ·E })

闭包后含

E' → ·E

E → ·E + T

E → ·T

T → ·T * F

T → ·F

F → ·( E )

F → ·id

因为期待 E 就连带期待 T、F 乃至 `(`、`id`。

### C3.3.4 LR(0) 自动机（规范 LR(0) 项集族）

把 I₀ 反复施加 GOTO，得到全部可达项集，就构成**规范 LR(0) 项集族（canonical collection）**，它们就是一台 DFA 的状态，GOTO 是转移边——这台 **LR(0) 自动机**识别的是文法的**可行前缀（viable prefix）**，即「可能出现在移进-归约分析栈上的、尚不越过句柄右端的符号串」。分析时，栈上符号串驱动这台 DFA 走，走到的状态就告诉分析器「此刻栈顶是不是一个句柄、或还该继续移进」。对增广表达式文法，GOTO(I₀, ·) 展开出的部分状态：

GOTO(I₀, T) = { E → T· , T → T·* F }

GOTO(I₀, F) = { T → F· }

GOTO(I₀, id) = { F → id· }

GOTO(I₀, ( ) = CLOSURE({ F → ( · E ) }) = 又是一大坨初始项

完整族对这个文法共 12 个状态（龙书 Fig 4.31）。

这里有一个贯穿 LR 的心智模型，**LR 分析就是用一台 DFA 追踪「栈顶离某个句柄还差多远」**。走到含归约项 A → γ· 的状态，意味着「栈顶那段 γ 可能就是句柄，该归约成 A 了」；走到只含可移进项的状态，就继续移进。LR(0) 的「0」表示做归约/移进决策时**不看前看记号**——只凭当前状态决定。这带来 LR(0) 的局限：若某状态既含归约项又含可移进项（或含两个归约项），LR(0) 无从抉择，就是冲突。解决办法是在归约时引入前看信息——用 FOLLOW（SLR）或把前看编进项本身（LR(1)/LALR），正是 C3.4 的主题。初学者不必手推全 12 个状态，抓住「项集=状态、闭包=展开期待、GOTO=读符号转移、归约项=可能该归约」即可。

### C3.3.5 LR 分析表与栈式分析引擎

所有 LR 分析器（SLR/LR(1)/LALR 皆然）共享同一套**表驱动引擎**：一张 **ACTION 表**（行=状态、列=终结符/$，值 ∈ {shift j, reduce A→β, accept, error}）加一张 **GOTO 表**（行=状态、列=非终结符，值=状态号）。分析栈交替存「状态、符号」。主循环看栈顶状态 s 和当前输入 a，查 ACTION[s, a]：

遇 shift j 就把 a 和状态 j 压栈，读下一个输入。

遇 reduce A → β 就从栈弹出 2·|β| 个元素（β 有几个符号就弹几对），设弹后栈顶状态为 t，把 A 压栈并压入 GOTO[t, A]。

遇 accept 分析成功，遇 error 报语法错。

三种 LR 表的差别**只在如何填 reduce 动作**（用什么前看信息、以及状态是否合并），移进和 GOTO 的填法完全一样，引擎更是同一个。这解释了为什么学会一种 LR 就学会全部——差异被隔离在「reduce 该填在哪些列」这一点上。初学者要把「状态号」和「文法符号」分开看：栈上真正驱动决策的是**状态**（编码了「见过的可行前缀走到哪」），符号只是陪着记录。reduce 时弹 2·|β| 个元素是因为每个符号在栈上占「符号+状态」两格。这套引擎的高效（线性时间、无回溯）正是 LR 相对回溯式自顶向下的核心优势。

## C3.4 SLR / LR(1) / LALR

### C3.4.1 SLR(1)：用 FOLLOW 集决定归约

**SLR(1)（Simple LR）**是给 LR(0) 打的最省事的补丁：LR(0) 自动机不变，只在填 reduce 动作时**加一道前看过滤**——状态 Iᵢ 含归约项 A → α·（A ≠ S'），不再对所有输入都归约，而是**只对 a ∈ FOLLOW(A) 的列**填 reduce A → α。移进和 GOTO 照旧。构造规则：

若 Iᵢ 含 A → α·β 且 GOTO(Iᵢ, a) = Iⱼ（a 为终结符），则 ACTION[i, a] = shift j。

若 Iᵢ 含 A → α·（A ≠ S'），则对每个 a ∈ FOLLOW(A)，ACTION[i, a] = reduce A → α。

若 Iᵢ 含 S' → S·，则 ACTION[i, $] = accept。

同格出现两条动作即冲突，文法非 SLR(1)。

SLR 的直觉是「都走到 A → α· 这个归约项了，那归约成 A 之后，紧跟的记号必然是 A 能被跟随的东西（∈ FOLLOW(A)）；若当前记号不在 FOLLOW(A) 里，这次归约必然是错的，别归」。它极其廉价（复用 LR(0) 自动机 + 已算好的 FOLLOW），能处理大量实用文法。局限在于 FOLLOW 是**全局**信息、太粗：FOLLOW(A) 收集的是「A 在整个文法里所有可能的跟随记号」，但在**某个具体状态**下，A 的合法跟随集可能只是它的子集——SLR 用全局集去判局部，偶尔会「不该归时误判成能归」而产生冲突，这类冲突 LR(1)/LALR 能靠更精确的前看化解。初学者记：SLR = LR(0) 骨架 + FOLLOW 做归约前看。

### C3.4.2 LR(1)：把前看记号编进项

**规范 LR(1)** 把前看信息做进项本身。LR(1) 项形如

[ A → α·β , a ]

多带一个**前看终结符 a**，含义「用这条产生式归约时，只有当下一个输入是 a（对归约项而言）才归约」。闭包规则相应变精细：对 [A → α·Bβ, a]，为 B 的每条产生式加入 [B → ·γ, b]，其中

b ∈ FIRST(βa)

即「B 归约后紧跟的记号，来自 β 打头能有的记号；若 β 可空则顺延到 a」。GOTO 定义同 LR(0)（点右移 + 闭包，前看随之携带）。填表时归约项 [A → α·, a] 只在**列 a** 填 reduce，其余同 SLR。

LR(1) 的强在「前看是**每个状态各自算出来的**、局部精确」，不像 SLR 用一个全局 FOLLOW 一刀切——所以凡 SLR 能分析的文法 LR(1) 都能，且 LR(1) 能多分析一批 SLR 卡壳的文法。代价是**状态数暴涨**：同一个 LR(0) 核心，配不同前看就分裂成多个 LR(1) 状态，实际文法的 LR(1) 自动机常有成千上万状态，表太大不实用。这正是 LALR 要解决的问题。初学者抓住：LR(1) = 把「归约时该看什么记号」从全局 FOLLOW 升级成「按状态精算的局部前看」，更准但更胖。

### C3.4.3 LALR(1)：合并同心项集

**LALR(1)（Look-Ahead LR）**是 LR(1) 的瘦身版，也是 Yacc/Bison 的默认算法。做法：先（概念上）造规范 LR(1) 项集族，再把所有**同心（same core）**的状态——即忽略前看后 LR(0) 项完全相同的状态——**合并成一个**，合并时把各自的前看集**求并**。结果状态数**回落到与 LR(0)/SLR 相同**（因为核心就那么多），但前看比 SLR 精确（是精算过再合并的，不是全局 FOLLOW）。

LALR 卡在 LR(1) 的精度和 SLR 的体积之间，性价比极高，是工业生成器的事实标准。关键的、必须讲清的副作用：合并同心状态**可能引入新的归约-归约冲突**，但**绝不会引入新的移进-归约冲突**。直觉是——移进动作只由核心（LR(0) 项）决定、与前看无关，合并不动核心故不新增 shift/reduce 冲突；但两个原本前看不同、各自无冲突的归约项，合并后前看集求并，可能在某个记号上撞车，制造出 reduce/reduce 冲突。所以「LALR 文法」比「LR(1) 文法」略窄。初学者记这条能力次序里 LALR 的位置：它用 SLR 的状态数换到接近 LR(1) 的精度，唯一的税是偶发的 R/R 冲突。

### C3.4.4 能力谱系：LR(0) ⊂ SLR ⊂ LALR ⊂ LR(1)，与 LL 的关系

四种自底向上文法类严格递增：

LR(0)-文法 ⊊ SLR(1)-文法 ⊊ LALR(1)-文法 ⊊ LR(1)-文法

即每种都严格包含前一种能处理的文法集。同时 LR(1) 是「用 1 个前看记号做移进-归约分析」的**能力上界**——凡确定性上下文无关语言都有 LR(1) 文法。与自顶向下族的关系是

LL(1)-文法 ⊊ LR(1)-文法

自底向上族严格更强（LR 容左递归、决策时已看到整个右部；LL 须消左递归、只看到右部开头）。

这张谱系是选分析技术的地图。实践取舍：SLR 最易手算、够用于教学与简单文法；LALR 是生成器默认（体积小、精度够），绝大多数编程语言文法都能写成 LALR；规范 LR(1) 理论最强但表太大，除少数场景（如某些 GLR/精确诊断需求）少用。初学者常见误解是「LR 一定比 LL 好」——能力上 LR 确实更广，但 LL/递归下降在**可读性、错误信息质量、手写可控性**上常胜出，所以工业界两条路线都活跃（Clang 手写递归下降；GCC 早期用 Bison、后改手写）。另一易错点：「LR(0) ⊂ SLR」不等于「LR(0) 自动机 ≠ SLR 自动机」——SLR 用的正是 LR(0) 自动机，差别只在填表时加了 FOLLOW 过滤，是「同一台自动机、更聪明地填 reduce」。

### C3.4.5 移进-归约冲突与归约-归约冲突（Bison 实证）

当分析表某格要填两个动作，就是**冲突**。两类：**移进-归约冲突（shift/reduce）**——同一状态同一记号既可移进又可归约；**归约-归约冲突（reduce/reduce）**——同一状态同一记号可用两条不同产生式归约。冲突意味着文法在该 LR 变体下不成立（常因二义或超出该变体能力）。用本机 GNU Bison 3.8.2 对二义表达式文法实测（基线 @2026-07-25）：

```
%token ID
%%
E : E '+' E | E '*' E | '(' E ')' | ID ;
```

`bison -v` 报告：

```
expr.y: warning: 4 shift/reduce conflicts [-Wconflicts-sr]
State 9 conflicts: 2 shift/reduce
State 10 conflicts: 2 shift/reduce
```

`.output` 里 State 9 的项与动作是

```
State 9
    1 E: E . '+' E
    1  | E '+' E .
    2  | E . '*' E
    '+'  shift, and go to state 6
    '*'  shift, and go to state 7
    '+'       [reduce using rule 1 (E)]
    '*'       [reduce using rule 1 (E)]
```

State 9 里既有归约项 `E → E '+' E ·`（可归约 rule 1）又有可移进项 `E → E · '+' E` 和 `E → E · '*' E`，所以在看到 `+` 或 `*` 时移进还是归约无法确定——方括号里的 reduce 是被默认规则**抑制掉**的动作（Bison 默认在 shift/reduce 冲突时选 shift）。再看归约-归约：

```
%%
S : A | B ;  A : ID ;  B : ID ;
```

Bison 报 `1 reduce/reduce conflict`，因为看到 `ID` 归约后既能是 A 又能是 B；Bison 默认取**文法中先声明的那条规则**（保留 `A : ID`，`B : ID` 被标 `rule useless in parser due to conflicts`）。

给初学者的校准在于，冲突不是「Bison 出 bug」，而是**文法在该 LR 变体下确实有歧义**的信号。移进-归约冲突常来自二义（表达式无优先级、悬空 else），多能靠优先级/结合性声明干净消解（C3.5.2），是「可接受的良性冲突」；归约-归约冲突通常是**文法设计有实质问题**（两条规则在同一上下文产同一串），默认消解（选先声明的）往往不是你要的语义，应当改文法而非依赖默认。看懂 `bison -v` 的 `.output`（状态、项、被方括号抑制的动作）是调试真实文法冲突的基本功。

## C3.5 生成器与错误恢复

### C3.5.1 Yacc / Bison：从文法规格到 LALR(1) 分析器

**Yacc（Yet Another Compiler-Compiler）**是 Unix 上的经典分析器生成器，**GNU Bison** 是它的兼容再实现（本机 3.8.2）。你写一份 `.y` 规格文件——分声明段、规则段（产生式 + 内嵌 C 语义动作 `{ ... }`）、C 代码段——Bison 据此**自动构造 LALR(1) 分析表**并生成一个 C 语言的表驱动分析器（默认函数 `yyparse()`），分析器调用你提供的词法函数 `yylex()` 取记号，在归约时执行对应产生式的语义动作。产生式记法直接对应 CFG：

```
expr : expr '+' term   { $$ = $1 + $3; }
     | term            { $$ = $1; }
     ;
```

`$$` 是左部的属性值、`$1 $3` 是右部第 1、3 个符号的属性值。

这套「声明式写文法 + 生成器造表」的价值在于：把 C3.3–3.4 那套繁琐易错的项集/表构造**全自动化**，你只管把文法和语义动作写对。默认算法是 **LALR(1)**（状态少、精度够，见 C3.4.3），Bison 也支持 `%glr-parser`（GLR，能处理二义/非 LALR 文法，代价是运行时分叉）等模式。初学者要建立的连接：Bison 生成的分析器**就是** C3.3.5 那台栈式 LR 引擎，`.output`（由 `bison -v` 产出）里的 State/项/动作正是 C3.3–3.4 的项集族与 ACTION/GOTO 表的真实呈现——把教材概念和 `bison -v` 输出对上，是理解 LR 的最快路径。易错点：Bison 是 LALR 而非 SLR，所以偶有 SLR 不冲突但……（实际相反：LALR 比 SLR 强，SLR 不冲突的 LALR 一定不冲突）——正确说法是 LALR 能处理比 SLR 更多的文法。

### C3.5.2 用优先级与结合性消解二义文法

生成器提供一条实用捷径——**保留二义文法**（如无分层的表达式文法），再用**优先级/结合性声明**告诉生成器在移进-归约冲突处怎么选，从而免去 C3.1.4 那种引入 T/F 层的改写。Bison 用 `%left`、`%right`、`%nonassoc` 声明结合性，**声明的先后顺序表示优先级从低到高**。对 C3.4.5 那个报 4 个冲突的二义文法，加两行声明：

```
%left '+'
%left '*'
%%
E : E '+' E | E '*' E | '(' E ')' | ID ;
```

本机 `bison -v`（基线 @2026-07-25）此时报 **0 冲突**，`.output` 中原冲突的 State 9 变为

```
State 9
    1 E: E '+' E .
    '*'  shift, and go to state 7
    $default  reduce using rule 1 (E)
```

看到 `*` 时移进（`*` 优先级更高，先算乘），看到 `+` 时按 `$default` 归约 rule 1（`+` 左结合，同级左边先归）——正好是「乘先于加、加左结合」的算术语义。

机制上，Bison 比较「待移进记号的优先级」与「拟归约产生式的优先级」（产生式优先级默认取其最右终结符）：记号优先级高就移进、产生式优先级高就归约、相等则看结合性（`%left` 归约、`%right` 移进、`%nonassoc` 报错）。这条路的好处是文法保持简短直观、优先级集中可调；风险是它**掩盖**冲突而非消除歧义——若声明没覆盖到某个冲突，Bison 仍按默认（shift）静默消解，可能不是你要的语义。初学者准则：优先级/结合性声明适合**表达式**这类有清晰优先级语义的二义，且务必用 `bison -v` 确认「冲突数归零」而非「冲突被默默压掉」。

### C3.5.3 冲突的默认消解规则

生成器对未被显式声明消解的冲突有**默认规则**，必须知道以免被静默坑到。Bison（与 Yacc）的默认是：**移进-归约冲突 → 选移进（shift）**；**归约-归约冲突 → 选文法中先声明（行号靠前）的那条产生式**。C3.4.5 的实测印证了两者——二义表达式的 S/R 冲突默认走 shift，`A:ID`/`B:ID` 的 R/R 冲突默认保留先声明的 `A:ID`。

「S/R 默认移进」这条恰好把**悬空 else** 处理对：`if e then if e then s . else …` 在看到 `else` 时移进（把 else 配给最近的、还没闭合的内层 if），正是通行的「就近匹配」语义——所以很多语言干脆留着悬空 else 的二义文法、靠这条默认吃下。但两类默认的「可信度」天差地别：S/R 默认移进常常正中下怀（尤其配合优先级声明），是**可接受**的；R/R 默认取先声明规则则**几乎总是**掩盖了文法设计缺陷，产出的行为往往非你所愿，应当去改文法而不是依赖它。初学者要养成的习惯：`bison -v` 报任何冲突都当作**警告去审查**，确认每个冲突要么被优先级声明正确消解、要么其默认行为确实正确——绝不放任 `.output` 里一堆未审查的冲突。Bison 还提供 `%expect N` 声明「我预期恰好 N 个 S/R 冲突」，数目不符即报错，用于把「已知良性冲突」钉住、防新冲突混入。

### C3.5.4 错误恢复：panic-mode、短语级与 error 记号

真实编译器遇语法错不能一遇错就停——要**错误恢复**，尽量跳过错误、继续分析以在一次编译中报出多个错。龙书讲四种策略：**panic-mode（恐慌模式）恢复**——遇错后丢弃输入记号直到碰见某个「同步记号（synchronizing token，常是 `;`、`}`、`end` 等语句/块边界）」，再从一个安全状态继续；**短语级（phrase-level）恢复**——就地做局部修补（插入/删除/替换少量记号，如补一个缺失的 `;`）；**错误产生式（error productions）**——在文法里预先写进常见错误模式的产生式，命中就报专门错误；**全局纠正**——理论上找「改动最少即合法」的修正，代价高、实用少。

panic-mode 最简单也最常用，因为它保证**不会死循环**（每步至少消耗一个输入记号）、实现廉价，代价是会跳过错误点到同步记号之间的内容（可能漏报其间的错）。生成器层面，Yacc/Bison 提供内建的特殊记号 **`error`**：你在产生式里写它，如

```
stmt : error ';'   { yyerrok; }
```

含义「若分析 stmt 时出错，就丢弃记号直到能匹配 `error ';'`（即找到下一个 `;`）再恢复」——这正是 panic-mode 的生成器实现，`;` 就是同步记号。初学者要理解错误恢复的**目标是「让编译器一次多报几个真错、且不误报级联假错」**：恢复得好，能在跳过一处错后干净地继续；恢复得差（同步点选得不好），会在错误点后吐一串因分析器状态错乱而生的**级联假错**。好的错误信息与恢复策略是工业编译器体验的重要一环，也是手写递归下降相较生成器常被认为更有优势的地方（更易定制精准报错）。
