## C7.1 存储组织与活动记录

### C7.1.1 运行时存储的逻辑分区：代码 / 静态 / 堆 / 栈

编译器把目标程序运行时可用的内存，按数据的**生命周期与分配方式**划成几个逻辑区域。龙书 Ch.7 §7.1 给出的经典划分是四类：**代码区（code）**放编译好的目标指令，大小编译期已知、固定；**静态区（static）**放全局变量和编译期就能定地址、生命周期贯穿整个程序的数据；**堆区（heap）**放运行时动态申请、生命周期不随任何函数进退的数据；**栈区（stack / run-time stack）**放随过程调用而生、随过程返回而灭的数据（局部变量、参数、返回地址等）。

一张典型的地址布局图（龙书 Fig. 7.1 的思路）：代码与静态区在地址低端、大小固定；堆和栈各占一端、朝对方生长、中间是空闲内存，谁用得多谁就往中间挤。

```
低地址  ┌──────────┐
        │  Code    │  固定大小，编译期确定
        ├──────────┤
        │  Static  │  全局/静态数据，固定地址
        ├──────────┤
        │  Heap    │  动态分配 → 向高地址生长
        ├──────────┤
        │  (free)  │  空闲内存，两端共享
        ├──────────┤
        │  Stack   │  过程调用 → 向低地址生长
高地址  └──────────┘
```

初学者最该抓住的是"为什么要分区"：不同数据的**生命周期规律不同**，规律不同就该用不同的管理策略。全局变量活得和程序一样久，那就编译期钉死一个固定地址（静态分配），零运行时开销。函数的局部变量遵循严格的"后调用的先返回"——完美的后进先出（LIFO），那就用一根栈，压进弹出都是常数时间、天然嵌套。而像 C 里 `malloc` 出来的对象、Java 里 `new` 出来的对象，它的存活时间由程序逻辑决定、和调用栈的进退无关，栈管不了，就得放进堆、单独管理。

这里的"栈/堆"是**逻辑区域**，是编译器和运行时约定的用途划分，不等同于"数据结构里的栈/堆（heap 那个优先队列）"。运行时的 heap 只是"一大片可动态切分的自由内存"，和数据结构的堆无关。另外真实进程里的地址布局还受操作系统和 ASLR（地址随机化）影响，上图是教学抽象，方向与相对关系正确，绝对地址不必当真——精确布局属于 L3-03/OS 课。

### C7.1.2 活动记录（栈帧）：一次过程调用的私有存储

**活动记录（activation record）**，工程上更常叫**栈帧（stack frame）**，是运行时栈上为**某一次过程调用**分配的一段连续存储，专门存放这次调用私有的信息——它的参数、局部变量、返回地址、以及为管理调用关系而需要的链接指针等。每调用一个过程就压入一个新的活动记录，过程返回就弹出它。

要分清两个词：一个**过程（procedure）**是源码里写的那段函数定义（只有一份）；一次**活动（activation）**是这个过程被调用执行的一趟（可以有很多趟，递归时还同时存在多趟）。活动记录记的是"活动"，不是"过程"——所以递归调用 `fact(3)` 时，栈上会同时躺着 `fact(3)`、`fact(2)`、`fact(1)` 三个各自独立的活动记录，各有各的局部变量副本，这正是递归能工作的存储基础。

为什么活动记录天然适合放在栈上？因为过程调用/返回严格服从 LIFO：A 调用 B、B 调用 C，一定是 C 先返回、再 B、再 A——后进先出。栈正好刻画这种嵌套。程序运行中，从 main 到当前正在执行的过程，这一串还没返回的活动，其活动记录从栈底到栈顶依次排列，这串正是"调用链（call chain）"，也就是你在调试器里看到的**调用栈（call stack）/回溯（backtrace）**。初学者可以把栈帧理解成"每次进一个函数，系统就发给你一个专属抽屉，放你这趟用的东西；函数一返回，抽屉连同里面的局部变量一起被回收"——这也解释了为什么"返回局部变量的地址"是错的（抽屉已经被收走）。

### C7.1.3 栈帧的典型布局

一个活动记录内部大致分成哪些槽位，龙书 Fig. 7.5 给出一个教学用的通用布局（从高地址到低地址、或说从"先压入"到"后压入"）：

```
┌────────────────────────┐  （靠调用者一侧）
│ 实在参数 actual params  │
│ 返回值 returned value   │
├────────────────────────┤
│ 控制链 control link     │  → 指向调用者的活动记录（动态链）
│ 访问链 access link      │  → 指向外层作用域的活动记录（静态链，见 C7.2）
│ 保存的机器状态          │  返回地址、被保存的寄存器
├────────────────────────┤
│ 局部数据 local data     │
│ 临时变量 temporaries    │
└────────────────────────┘
```

**实在参数**是调用者传给被调用者的值；**返回值**放被调用者算出、要交回调用者的结果；**控制链（control link，又叫动态链 dynamic link）**指向调用者的活动记录，用于返回时恢复调用者的帧；**访问链（access link，又叫静态链 static link）**用于带嵌套作用域的语言访问非局部变量（C7.2 详述）；**保存的机器状态**含返回地址和调用前需要保护的寄存器值；**局部数据**和**临时变量**放本过程的局部变量与表达式求值的中间结果。

这里必须给初学者划清一条边界：上面是**抽象/教学布局**，说明"一个栈帧概念上需要装哪些东西、彼此顺序如何"。**真实机器上并不完全长这样**——在 x86-64 System V ABI（L3-03）里，前几个整型/指针参数根本不进栈，而是走寄存器（`rdi, rsi, rdx, rcx, r8, r9`）；返回值走 `rax`；返回地址由 `call` 指令自动压栈；很多简单函数连"控制链"都省了（用固定的帧指针或纯栈指针寻址）。所以"栈帧里到底放什么、放哪"是**抽象概念 + 具体 ABI**两层，编译器按目标平台的 ABI 决定真实布局。教材给通用骨架，ABI 给字节级现实，二者不冲突、是抽象与实现的关系。

### C7.1.4 静态 / 栈 / 堆分配的判定：什么数据放哪

编译器为每个名字（变量）决定它的存储分配策略，主要看它的**生命周期能否在编译期确定、是否服从调用嵌套**。**静态分配（static）**用于生命周期贯穿全程序、且不随调用变化的数据（C 的全局变量、`static` 变量），地址编译期定死。**栈分配（stack）**用于生命周期与某次过程活动一致的数据（普通局部变量、参数），随栈帧进退。**堆分配（heap）**用于生命周期由程序逻辑显式控制、可能超出创建它的过程的数据（`malloc`/`new` 出来的对象）。

判断的直觉是问一句"这块数据什么时候死"。如果答案是"程序结束才死"，静态分配最省——一次定址、零运行时管理。如果是"造它的那个函数返回就该死"，栈分配最省——跟着栈帧自动回收，压弹都是移动一下栈指针的常数开销。如果是"说不准，可能比造它的函数活得久，得由别的代码来决定何时死"，那栈管不了（函数返回栈帧就没了），只能放堆，代价是需要 C7.3/C7.4 那套堆管理或垃圾回收。

一个能一下子讲清区别的最小例子：函数里 `int x;` 是栈分配，`x` 随函数返回消失；`int *p = malloc(sizeof(int));` 里 `p` 这个指针变量本身是栈分配（随函数消失），但 `p` 指向的那 4 字节是堆分配（函数返回后依然存在，直到有人 `free`）。初学者最经典的错误正来自混淆这两层——`return &x;`（返回栈上局部变量地址，返回后失效）是错的，而 `return p;`（返回堆地址，仍有效）是对的。为什么早期语言（如 Fortran）不需要栈、也没有递归？因为它把所有局部变量都做静态分配，每个过程只有一份固定存储，自然也就不能同时有两趟活动——不支持递归正是这个存储决策的直接后果。

### C7.1.5 栈的生长方向与对齐（x86-64 一手佐证）

栈朝哪个方向生长、按多少字节对齐，属于具体 ABI 的规定。在 x86-64 System V ABI 上，栈**向低地址生长**（压栈时栈指针 `rsp` 减小），并要求调用点处栈按 16 字节对齐。这些是编译器生成栈帧代码时必须遵守的硬约束，本篇不展开字节细节（在 L3-03），仅用一段真实反汇编坐实"编译器确实按 ABI 布置了栈帧"。

用 gcc 13.3.0 编译一个最简单的 `int add(int a,int b){int c=a+b;return c;}`，`gcc -std=c11 -O0 -S`（x86-64，AT&T 语法，去掉了 unwind 伪指令）得到：

```
add:
    pushq   %rbp            # 保存调用者的帧指针
    movq    %rsp, %rbp      # 建立本帧的帧指针
    movl    %edi, -20(%rbp) # 参数 a（来自 rdi）存入本帧局部区
    movl    %esi, -24(%rbp) # 参数 b（来自 rsi）存入本帧局部区
    ...
    movl    %eax, -4(%rbp)  # 局部变量 c 存在 rbp 之下（低地址）
    popq    %rbp            # 恢复调用者帧指针
    ret
```

这段真实输出印证了本节的几件事：局部变量 `c` 存在 `-4(%rbp)`，即帧指针**下方**（更低地址），说明帧内局部区确实朝低地址延伸；参数 `a`、`b` 不在栈上传进来，而是先到寄存器 `edi`/`esi`（`rdi`/`rsi` 的低 32 位）再被存入本帧——正是 C7.1.3 说的"ABI 用寄存器传参、抽象布局用栈"的现实版；`pushq %rbp; movq %rsp,%rbp` / `popq %rbp` 就是下一节要讲的 prologue/epilogue。初学者只需带走一个结论：**栈帧不是虚的，编译器真的会逐条生成建帧/拆帧指令**，抽象布局与 ABI 在这里合流。

## C7.2 调用序列与非局部数据

### C7.2.1 调用序列与返回序列：调用双方的分工

一次过程调用要建立被调用者的活动记录、传参、保存状态、跳转过去；返回时要拆掉这个记录、传回返回值、恢复调用者状态、跳回来。为完成这一切而生成的一段固定代码，前半段叫**调用序列（calling sequence）**，后半段叫**返回序列（return sequence）**。关键在于：这些动作由**调用者（caller）**和**被调用者（callee）****分摊**执行——ABI 规定谁做哪一部分。

为什么要分摊、而不是一方全做？龙书 §7.2.3 给出的原则是：把动作尽量塞给"被调用者"这一侧能减小代码体积——因为一个过程可能被调用成百上千次，调用点（在调用者里）有很多份，而过程本身（被调用者里）只有一份；能放进被调用者做一次的，就不必在每个调用点重复。但有些信息只有调用者知道（比如实在参数的值、返回后该接着执行哪条指令），那就必须由调用者来放。所以典型分工是：调用者负责求值并放好参数、放好返回地址、跳转；被调用者负责保存需要保护的寄存器、开辟自己的局部空间（prologue），返回时再撤销（epilogue）。

初学者要抓住的直觉是"调用序列是一段礼节"：双方按 ABI 约定好"我进门前先把鞋放这、你进屋后自己搬椅子、走的时候各自把东西归位"，只要两边都守同一套礼节，分别编译的两个函数（甚至不同语言、不同编译器产的）就能正确对接。这正是 ABI 存在的意义——它是调用序列这套礼节的书面规范。一个易错点：调用序列里有些槽位（如参数、返回地址）位于调用者与被调用者两帧的"交界处"，到底算谁的帧、由谁压入，不同约定划法不同，读 ABI 时要以具体规范为准，别想当然。

### C7.2.2 prologue 与 epilogue：被调用者的建帧 / 拆帧

**prologue（序言/入口代码）**是被调用者函数体最开头、由编译器自动插入的几条指令，负责建立本次调用的栈帧（保存调用者帧指针、设置新帧指针、下移栈指针为局部变量腾地）。**epilogue（尾声/出口代码）**是函数返回前的几条指令，负责撤销栈帧、恢复调用者状态、跳回返回地址。它俩是返回序列/调用序列在被调用者一侧的具体落地。

x86-64 上最典型的 prologue/epilogue（gcc `-O0` 实测，见 C7.1.5）：

```
pushq %rbp        ; prologue: 压入调用者帧指针（存入"控制链"）
movq  %rsp, %rbp  ; prologue: 用当前栈顶作为本帧的帧指针基准
...               ; 函数体
popq  %rbp        ; epilogue: 恢复调用者帧指针
ret               ; epilogue: 弹出返回地址并跳回
```

这解释了帧指针 `rbp` 的作用：它在函数执行期间稳定指向本帧一个固定位置，于是局部变量和参数都能用"`rbp` 加减固定偏移"来寻址（如 `-4(%rbp)`），即使栈顶 `rsp` 因为压栈弹栈上下浮动也不受影响。初学者的一个常见疑问是"为什么开了优化就看不到这套 push rbp 了"——因为编译器在 `-O2` 等优化下常做**帧指针省略（frame pointer omission）**：如果一个函数不需要动态改变栈大小、也不需要 `rbp` 做基准，编译器就直接用 `rsp` 偏移寻址，把 `rbp` 省下来当普通寄存器用。gcc 实测：同一个 `add` 在 `-O2` 下被优化成 `leal (%rdi,%rsi),%eax; ret`，连栈帧都没建（参数在寄存器里算完直接返回）。这说明"栈帧/prologue 不是语言强制，而是编译器按需生成"，也提醒调试时优化级别会显著改变栈的样子。

### C7.2.3 参数传递方式

同样是"把实参传给形参"，语言层面对"传的是什么、被调用者改动形参是否影响实参"有不同规定，主要有四种。**传值（call-by-value）**：把实参的值复制一份给形参，被调用者改形参不影响调用者的实参（C 的默认方式，Java 基本类型也是）。**传引用（call-by-reference）**：把实参的地址（左值）传过去，被调用者通过它直接读写调用者的那个变量，改动可见（C++ 的 `&` 引用，Fortran 默认）。**传名（call-by-name）**：实参像宏一样被"整体代入"形参出现处、每次用到才求值，是 Algol 60 的历史机制，现代主流语言基本不用。**拷贝-恢复（copy-restore，又叫传值-结果 call-by-value-result）**：调用时把实参值拷进形参、返回时再把形参最终值拷回实参，是传值与传引用之间的一种折中。

初学者最该分清的是传值 vs 传引用，判据是"被调用者对形参的赋值，调用者看不看得见"。C 语言只有传值——所以 `swap(a,b)` 里直接改形参交换不了实参，必须传指针 `swap(&a,&b)`，但注意这仍是"传值"（传的是指针这个值的副本），只不过顺着这个地址值能改到调用者的变量。这正是初学者最大的困惑来源："C 传指针"经常被误说成"传引用"，严格讲 C 永远是传值，传引用是 C++ 引用那种编译器帮你隐式取地址/解引用的语法。传名和拷贝-恢复在多数场景下与传引用结果相同，但在有别名（aliasing，同一个变量被多个参数指向）或求值有副作用时会产生可观察的差异——这类微妙区别是龙书用来说明"参数传递语义必须精确定义"的经典例子，入门只需知道存在这四种、以及它们"改动是否回传"的核心区别即可。

### C7.2.4 非局部数据访问与访问链（静态作用域）

在允许**过程嵌套**（一个函数定义在另一个函数体内，如 Pascal、Python 的嵌套函数）的语言里，内层过程可以引用外层过程的局部变量——这种既不是自己局部、也不是全局的变量叫**非局部数据（nonlocal data）**。问题是：运行时内层过程的栈帧里没有这些变量，得去外层过程的栈帧里找，可栈上"物理上紧挨着我的那个帧"是**调用我的人（动态）**，未必是**在源码里包着我的那个外层过程（静态）**。**访问链（access link，静态链 static link）**就是为此设的指针：它从当前帧指向**源码上直接外层过程的最近活动记录**，顺着访问链走就能层层找到任意外层作用域的变量。

**控制链（动态链）**指向"谁调用了我"（运行时的调用者），用于返回；**访问链（静态链）**指向"我被定义在谁里面"（源码的词法外层），用于查非局部名字。二者常常不是同一个帧！举例：外层过程 `p` 里嵌套定义了 `q`，`p` 调用 `q`——此时 `q` 的控制链和访问链都指向 `p`；但若 `q` 又递归调用 `q`，第二个 `q` 的控制链指向第一个 `q`（调用者），访问链却仍指向 `p`（词法外层）——这时两链分道扬镳。

访问链怎么设？靠**嵌套深度（nesting depth）**：最外层过程深度记 1，每往里嵌一层加 1。若深度为 `n` 的过程调用深度为 `m` 的过程，编译器在调用序列里按 `n` 与 `m` 的关系设置被调用者的访问链（往里嵌一层就指向调用者、平级或往外调就顺调用者的访问链上溯若干步）。访问一个定义在深度 `d` 的非局部变量，就从当前帧沿访问链走 `(当前深度 − d)` 步。初学者不必记设置公式的每种情形，只要抓住核心："访问链把词法嵌套结构在运行时用指针还原出来，因为栈的物理相邻反映的是调用关系、不是嵌套关系。" 顺带一提：C 语言没有嵌套函数（函数不能定义在函数里），所以标准 C 根本不需要访问链——这个机制主要服务于 Pascal、Ada、以及带闭包/嵌套函数的现代语言。

### C7.2.5 display：用数组加速非局部访问

**display** 是访问链的一种优化替代：不再让每个帧存一个访问链指针、访问深层外层时逐级走链，而是维护一个全局数组 `d[]`，`d[i]` 直接指向**当前**嵌套深度为 `i` 的那个过程的最近活动记录。要访问深度为 `i` 的非局部变量，直接查 `d[i]` 一步到位，不用沿链走多步。

为什么需要它？沿访问链访问非局部变量的代价正比于"深度差"——嵌套很深、要访问很外层的变量时，得走很多步指针。display 把这变成一次数组索引（O(1)）。代价是每次过程进入/退出时要维护 `d[]`：进入深度 `i` 的过程时，把 `d[i]` 保存到本帧、再让 `d[i]` 指向本帧；退出时从本帧恢复旧的 `d[i]`。

```
访问链方案：访问深度 i 的变量 → 沿链走 (当前深度 − i) 步
display 方案：访问深度 i 的变量 → 直接取 d[i]，一步
```

初学者可以把 display 理解成"给每个嵌套层级设一个专用书签，随时指向该层级当前活着的那个帧"，于是查任意层级的变量都是翻到对应书签、不必从当前层一页页往回翻。它和访问链是**同一问题（非局部访问）的两种实现**、各有取舍：访问链省数组维护、访问慢；display 访问快、需维护数组且实现更绕。两者选哪个是编译器/运行时的工程决定。这个机制在现代主流语言实现里已不常见（很多语言干脆不支持深嵌套，或用闭包捕获替代），属于经典教材要点、了解即可。

### C7.2.6 帧指针 vs 栈指针寻址、caller-saved vs callee-saved（编译器视角）

编译器给帧内数据寻址有两种基准：用**帧指针（frame pointer，`rbp`）**加固定偏移，或直接用**栈指针（stack pointer，`rsp`）**加偏移。前者稳定（`rbp` 整个函数不动）、便于调试和处理动态大小的帧；后者省一个寄存器（`rbp` 可挪作它用），是优化后的常见选择（帧指针省略，见 C7.2.2）。这属于编译器如何利用 ABI 的决定。

寄存器由谁负责保存也是调用序列的一部分：ABI 把寄存器分成**调用者保存（caller-saved / volatile）**和**被调用者保存（callee-saved / non-volatile）**两类。若调用者有个值放在 caller-saved 寄存器里、还想在调用返回后接着用，它得在调用前自己存起来（因为被调用者可能覆盖它）；若被调用者要用某个 callee-saved 寄存器，它得在 prologue 里先存、epilogue 里恢复（因为调用者指望它不变）。

初学者只需理解这套划分的目的是**减少不必要的保存**：如果所有寄存器都由调用者保存，那被调用者用不到的寄存器也被白存了；如果都由被调用者保存同理。分成两类，让"谁真的要用、谁就负责保存"，把保存开销压到最小。具体哪些寄存器属于哪类、精确到寄存器名，是 x86-64 System V ABI（L3-03）的内容，本篇不列——编译器做寄存器分配（见 C8.3）时必须查这张表来决定跨调用点的值放哪、要不要额外保存。

## C7.3 堆管理与碎片

### C7.3.1 堆与动态分配：栈管不了的数据住这里

**堆（heap）**是运行时用来存放那些**生命周期不服从调用嵌套**的数据的内存区：它可能在创建它的过程返回后依然存活，直到程序显式释放或垃圾回收器回收它。管理这块内存的子系统叫**内存管理器（memory manager）**，它响应两类请求——**分配（allocation）**：给出一块足够大的连续空闲内存；**回收（deallocation）**：把用完的块还回去、供以后复用。C 里的接口是 `malloc`/`free`，C++ 是 `new`/`delete`，很多高级语言只有分配、回收交给 GC（C7.4）。

为什么非要有堆？回顾 C7.1.4：栈上的数据随栈帧自动回收，可有些对象的存活时间由程序逻辑决定、和调用栈无关——比如一个函数 `new` 出一个链表节点、把指针返回给调用者，这个节点得比该函数活得久，放栈上函数一返回就没了。堆就是为这种"生命周期灵活"的数据准备的：你显式说"给我一块",它就一直在，直到你（或 GC）说"可以收了"。

堆分配比栈分配**贵得多**。栈分配就是把栈指针挪一下（一条指令），堆分配却要在一堆大小不一、来来去去的空闲块里找一块合适的、还要维护记账信息、可能触发向操作系统要更多内存。所以"能用栈就别用堆"是常见的性能建议。内存管理器追求几个目标：**空间效率**（少浪费、少碎片）、**程序局部性**（相关对象靠在一起，对缓存友好）、**低分配开销**（分配/回收要快）——这几个目标常常互相拉扯，下面的碎片和放置策略就是在权衡它们。

### C7.3.2 内碎片与外碎片

**碎片（fragmentation）**指内存虽有空闲、却因为零散或分配粒度而用不上的浪费，分两种。**内碎片（internal fragmentation）**：分配器给出的块比实际请求的**大**，多出来的那部分在块内部被浪费——通常源于分配器只按固定档位（如 8 字节的倍数、2 的幂）给块，你要 13 字节它给你 16 字节，多的 3 字节谁也用不了。**外碎片（external fragmentation）**：空闲内存**总量够**，但被已分配的块切割成许多**不相邻的小块**，没有一块单独够大来满足一个较大的请求——空闲总量足够却"拼不到一起"。

内碎片像"买鞋只有整码，你穿 41.5 只能买 42，半码空着"；外碎片像"停车场总空位很多，但都是零散的单个车位，来一辆加长车却找不到连续两个空位"。二者的区分点是"浪费在块内还是块间"：内碎片浪费在**已分配块内部用不到的尾巴**，外碎片浪费在**块与块之间太小的空隙**。

初学者要知道两种碎片是**此消彼长**的设计权衡：为减少外碎片，分配器可以把内存切成统一大小的块（如伙伴系统的 2 的幂档位），这样回收的块更容易重新拼上——但代价是内碎片增加（请求 13 字节给 16 字节）。反过来，为减少内碎片做到"要多少给多少"，又会切出五花八门的尺寸、加剧外碎片。外碎片还能靠**紧致（compaction）/复制**来消除（把活对象搬到一起、腾出连续空闲），这正是 C7.4 里标记-压缩和复制式 GC 的一大好处；但搬移对象需要能更新所有指向它的指针，手动管理的 C 做不到（指针是裸地址），所以 C 的 `malloc` 只能靠合并相邻空闲块来缓解外碎片、不能搬移。

### C7.3.3 空闲块管理与放置策略

内存管理器用一个或多个**空闲块列表（free list）**记录当前可用的内存块。收到一个大小为 `s` 的分配请求时，要从空闲块里挑一块 `≥ s` 的来切给它，怎么挑就是**放置策略（placement policy）**，龙书 §7.4.2 给了三种经典策略：

```
first-fit （首次适配）：从头扫，用第一块够大的        —— 快，但小碎片易堆在链表前部
best-fit  （最佳适配）：选所有够大的里最小的那块      —— 省空间，但要扫全表、且留下极小碎屑
next-fit  （下次适配）：从上次停的位置接着找          —— 分散使用、改善局部性
```

分配是"切一块给你"，回收则要处理**合并（coalescing）**：一个块被释放后，若它相邻的块也空闲，就把它们并成一个更大的空闲块，以对抗外碎片。要快速判断相邻块是否空闲、并高效合并，经典技术是**边界标记（boundary tags）**——在每个块的头尾各放一个记账字（记大小和"空闲/占用"标志），这样从任一块都能 O(1) 找到物理相邻的前后块并检查其状态。另一类是**伙伴系统（buddy system）**，按 2 的幂管理块、合并时找"伙伴"块，合并快但内碎片偏高。

这是一个"如何切蛋糕又如何把切剩的拼回去"的问题。best-fit 听起来最省，但它专挑最贴合的块，反而容易到处留下"太小、谁都用不上"的碎屑，且每次都要扫整个链表；first-fit 快、实践中综合表现常常不比 best-fit 差，是很多分配器的默认思路。这里没有唯一正确答案——不同请求分布下各策略优劣不同，这也是"内存分配是启发式工程"的体现。一个易混点：放置策略（分配时怎么选块）和合并策略（回收时怎么并块）是两件事，一个管"切"、一个管"拼"，好的分配器两头都要做好。

### C7.3.4 局部性与内存层级

**局部性（locality）**指程序倾向于在一小段时间里反复访问相邻或相同的内存（时间局部性 + 空间局部性）。内存管理器的分配决策会影响局部性，进而影响性能——因为现代机器有多级缓存/虚拟内存（内存层级，L3-02），命中近层缓存比访问主存快几个数量级，把常一起访问的数据分配得**在地址上靠近**，能显著提升缓存命中率。

为什么分配器要操心这个？因为"逻辑上相关的对象若在物理内存上四散",访问它们就会频繁跨缓存行/跨页、命中率低、速度慢。反之若分配器让同一批相关对象落在相邻地址（甚至同一缓存行/同一页），一次缓存加载就能覆盖多个，程序跑得更快。这就是 C7.3.1 里"程序局部性"作为分配器目标之一的原因，也是碎片有害的另一面——外碎片不仅浪费空间，还把数据打散、损害局部性。

初学者把它和缓存联系起来即可：分配器不只是"找块空地"，好的分配器还尽量让"经常一起用的东西住得近"，因为硬件对"访问集中"这件事有巨大奖励。这也解释了为什么 C7.4 的复制式/压缩式 GC 除了消除碎片，还有一个副产品好处：把活对象搬到一起时顺便改善了它们的局部性。局部性的量化分析属于体系结构/性能课，本篇只需建立"分配布局影响缓存、缓存影响速度"这条因果链。

### C7.3.5 手动管理的典型错误：为什么要有 GC

在手动管理（`malloc`/`free`）下，"何时释放"由程序员负责，一旦判断错就产生几类经典 bug。**内存泄漏（memory leak）**：该释放的块一直不释放（丢了指向它的最后一个指针又没 `free`），内存被慢慢吃光。**悬垂指针（dangling pointer）**：块已经 `free` 了、却还有指针指着它并继续解引用，读到垃圾或踩到已被重新分配的数据。**重复释放（double free）**：同一块 `free` 两次，破坏分配器的记账结构。

这三类错误的共同根源是：对象的真实生命周期（"还有没有人用它"）和程序员手写的 `free` 时机之间容易脱节，尤其当一个对象被多处共享、"最后一个使用者是谁"很难静态看清时。悬垂指针和泄漏其实是一枚硬币的两面——释放早了（还有人用）成悬垂，释放晚了/忘了成泄漏，中间那条"恰好在最后一个使用者用完时释放"的线极难手工踩准。

正因为手动踩这条线又难又易错，才催生了**垃圾回收（C7.4）**——让运行时自动判断"还有没有人能用到这个对象"（可达性），不能用到了就回收，把"何时释放"从程序员手里接过去。代价是运行时开销和（某些算法的）停顿。C/C++ 选择手动管理换取控制力与可预测性，Java/Python/Go 等选择 GC 换取安全与省心，这是语言设计的根本取舍之一。C7.4 就讲运行时怎么自动做这件事。

## C7.4 垃圾回收

### C7.4.1 前提：可达性、根集与"垃圾"的定义

**垃圾回收（garbage collection, GC）**是运行时自动回收"程序再也用不到的堆对象"的机制。核心难点在于精确定义"用不到"——GC 用一个**可判定的保守近似**：**可达性（reachability）**。从一组**根（root set）**出发（根 = 程序能直接拿到的引用：全局变量、当前各栈帧里的局部变量与参数、寄存器里的引用），凡是顺着对象里的指针能一步步走到的对象都算**活（reachable）**；走不到的就是**垃圾（garbage）**，可以回收。

为什么用可达性而不是"真的还会被用到"？因为"程序将来是否真的会访问某对象"等价于停机问题，不可判定。可达性是它的**可靠近似**：不可达的对象**一定**用不到（没有引用就没法访问），回收它绝对安全；但可达的对象未必将来真会用到（可能有个引用挂着却再不访问——这叫"语义垃圾"，GC 收不掉，属于逻辑层面的泄漏）。所以 GC 消除的是"物理上够不着"的垃圾，不能消除"逻辑上不再需要但还挂着引用"的浪费。

初学者可以把堆对象想成一张有向图：根是入口，对象是节点，引用是边。GC 做的就是"从入口出发做一次图遍历，标记所有能到达的节点，剩下没被标记的就是孤岛、全部回收"。理解这个"根 + 可达图"模型，下面所有 GC 算法都是它的不同实现：引用计数是局部地维护"有多少条边指向我"，标记-清扫/复制是全局地做这次遍历。一个关键前提要点：GC 必须能**准确识别哪些字是指针、哪些是普通数据**（否则遍历会出错），这要求运行时有类型信息（**精确 GC**）；若无法准确识别、只能"看着像指针就当指针"，则是**保守 GC（conservative GC）**（如 C/C++ 上的 Boehm GC），可能误判、也不敢搬移对象。

### C7.4.2 引用计数

**引用计数（reference counting）**给每个堆对象附一个计数器，记录"当前有多少个引用指向它"。每当新增一个指向它的引用，计数加一；每当一个引用被覆盖或离开作用域，计数减一；计数**降到 0**的瞬间，说明没人再指向它，立即回收它，并把它内部指向的其它对象的计数各减一（可能引发连锁回收）。

它的优点是**增量、即时、停顿分散**：对象一变成垃圾（计数归零）就马上回收，不需要"停下整个程序做一次大扫描"，回收开销摊在每次指针赋值上。这也是它在 CPython（配合循环检测）、C++ 的 `shared_ptr`、Swift 里被采用的原因。

但它有两个硬伤，初学者必须记牢。其一，**开销分摊在每次指针赋值上**——每改一次引用都要维护计数（还要在多线程下加锁/原子操作），频繁的指针操作会拖慢程序。其二，也是最著名的，**回收不了循环引用（cycle）**：若对象 A 指向 B、B 又指向 A，即使外界再没有任何引用指向这对对象，它俩的计数也都停在 1（互相指着），永远归不了零，于是泄漏。

```
外界引用全部消失后：
  A.count = 1（被 B 指着）
  B.count = 1（被 A 指着）
→ 谁都不为 0 → 永远回收不掉 → 泄漏
```

正因为循环这个坑，纯引用计数很少单独用，通常要么配一个"循环检测器"兜底（CPython 的做法），要么在设计上用弱引用（weak reference，L5-14 R8.5 的 `Weak` 就是破环工具）打断环。这一点与追踪式 GC（下面几种）恰好互补：追踪式从根做可达性遍历，天然不受循环影响（环若整体不可达，遍历根本走不进去，自然当垃圾收掉）。

### C7.4.3 标记-清扫（mark-and-sweep）

**标记-清扫（mark-and-sweep）**是最基础的**追踪式（tracing）**GC，分两趟。**标记（mark）**趟：从根集出发遍历可达图（深度优先/广度优先），给每个到达的对象打上"活"标记。**清扫（sweep）**趟：线性扫过整个堆，凡是没被标记的对象就是垃圾、回收进空闲链表，同时把活对象的标记清掉（为下一轮 GC 复位）。

和引用计数相比，它的两大优势直接对应引用计数的两大痛点：**天然处理循环引用**（不可达的环在标记趟根本走不到，直接当垃圾清掉），且**不给每次指针赋值加开销**（平时程序全速跑，只在触发 GC 时才付出代价）。这使它成为追踪式 GC 的基石，后面的复制、压缩、分代都可看作对它的改良。

它的代价是初学者要理解的两点。其一，经典标记-清扫是**"停止世界"（stop-the-world）**的：GC 运行时通常要暂停程序（不然对象图边扫边变会出错），造成一次可感知的停顿。其二，它**不移动对象**，只把垃圾块还给空闲链表，所以**不消除外碎片**——回收后堆里活对象和空闲块交错，长期运行会碎片化。此外它的清扫趟要扫过**整个堆**（含垃圾），代价与堆大小相关。这两个缺点分别催生了下面的"压缩"（治碎片）和"分代"（减扫描量、缩停顿）。

### C7.4.4 标记-压缩（mark-compact）

**标记-压缩（mark-compact）**在标记趟之后，不做"就地清扫留出空洞"，而是把所有**活对象搬到堆的一端、紧挨着排列**，另一端就变成一整块连续空闲内存。它是标记-清扫的变体，用"移动对象"换来"消除外碎片"。

它的直接好处是彻底解决外碎片：回收后空闲区是连续的一大块，之后的分配可以像栈一样"挪一下指针（bump pointer）"就完成，分配极快；活对象紧凑排列也改善局部性。代价是压缩趟要移动对象、并**更新所有指向被移动对象的指针**（否则指针就指错了），这需要多趟扫描、开销比纯清扫大。

标记-清扫"留原地、收空洞、有碎片、不用改指针"；标记-压缩"搬到一起、无碎片、分配快、但必须能改指针"。"必须能改指针"正是移动式 GC（压缩、复制）的共同前提，也是它们只能用在**精确 GC**（运行时知道哪些字是指针，才敢改）语言里、而不能用于裸指针的 C 的根本原因。

### C7.4.5 复制回收（copying / semispace）

**复制式回收（copying collector）**把堆分成大小相等的两半——**from-space** 和 **to-space**。程序只在 from-space 里分配；GC 触发时，从根出发遍历，把每个**活对象复制到 to-space**并紧凑排列，复制完后两个半区**角色互换**（to 变 from），原来的 from-space（连同里面全部垃圾）整块作废、无需逐个清扫。经典实现是 **Cheney 算法**，用 to-space 自身当遍历队列、广度优先地边复制边扫描，无需额外栈。

**开销只与"活对象"成正比，与垃圾数量无关**——因为它只碰活对象（复制走），垃圾根本不被访问，直接随整个半区丢弃。这与标记-清扫（清扫趟要扫过含垃圾的整个堆）形成鲜明对比：当大多数对象是垃圾时（常见！），复制式非常划算。而且复制后 to-space 里活对象天然紧凑，**无外碎片、分配靠 bump pointer、局部性好**。

代价也很直白，初学者要记住：它**只能用一半内存**（另一半永远空着当 to-space 备用），空间利用率减半；且和压缩一样是移动式的，需要精确 GC、要更新指针。这个"用一半空间换取无碎片 + 只碰活对象"的取舍，使它特别适合"垃圾多、活对象少"的场景——这恰好描述了刚创建不久的年轻对象，于是它成为下面分代 GC 里回收年轻代的常用手段。

### C7.4.6 分代回收

**分代回收（generational GC）**基于一条经验规律——**弱分代假设（weak generational hypothesis）：绝大多数对象在创建后很快就死**（"most objects die young"）。据此把堆按对象年龄分成若干**代（generation）**，至少分**年轻代（young / nursery）**和**老年代（old）**：新对象都在年轻代分配，年轻代**频繁地小范围回收**（大部分很快变垃圾，回收收益高），少数活得够久的对象被**晋升（promote）**到老年代，老年代**较少地才做一次大回收**。

为什么这样能提速？因为每次 GC 只需扫一个小小的年轻代、而不是整个堆，单次停顿短、频率虽高但每次便宜；而占堆大头、又大多长寿的老年代难得才扫一次，避免了反复白扫长寿对象。年轻代对象垃圾比例极高，正好用复制式回收（只碰少量活对象）最划算。这套"大部分回收都廉价地限定在年轻代"的策略，是现代高性能 GC（Java HotSpot、Go、.NET 等）的主流骨架。

初学者要理解一个由此产生的关键机制——**跨代引用**问题：回收年轻代时，根不能只看全局/栈，还必须算上"老年代对象指向年轻代对象"的引用（否则会把仍被老对象引用的年轻对象误当垃圾）。为高效找出这些跨代引用，运行时用**写屏障（write barrier）**在每次"把年轻对象的引用写进老年代对象"时做记录，存进**记忆集（remembered set）**，回收年轻代时把记忆集也当作根的一部分。这就是分代 GC 的额外代价：写屏障给指针写入加了一点开销，换来"回收年轻代无需扫描整个老年代"。一个易错认识：分代不是一种新的回收算法，而是一个**组织策略**——每一代内部仍用复制/标记-清扫/压缩等基础算法来实际回收。

### C7.4.7 停顿、增量/并发与保守 vs 精确（简述）

真实 GC 还要面对**停顿（pause）**问题：经典 stop-the-world 会暂停程序，对交互式/实时系统不友好。为缩短停顿，工程上有**增量式（incremental）**（把一次大回收拆成许多小步、穿插在程序运行间）和**并发式（concurrent）**（GC 线程与程序线程同时跑）GC，代价是需要读/写屏障来协调"边回收边修改对象图"的一致性、实现复杂度显著上升。

另一条正交的分类是**精确 GC vs 保守 GC**：精确 GC 靠运行时类型信息准确知道每个字是不是指针，因此能安全地移动对象、更新指针（复制/压缩式都要求精确）；保守 GC（如 C/C++ 上的 Boehm-Demers-Weiser GC）在拿不到完整类型信息时，把"看起来像堆地址的字"一律当作可能的指针，宁可少收（把疑似引用指向的对象保守地当活）也不误删，代价是可能漏收一些真垃圾、且**不敢移动对象**（怕改错把整数误当指针的字）。

GC 的设计是在**吞吐量（总开销）、停顿时间、内存占用、实现复杂度**几个维度间权衡，没有全能最优解——引用计数停顿平滑但收不了环、标记-清扫简单但有碎片和停顿、复制无碎片但费一半内存、分代针对"对象早夭"规律做了工程优化、并发/增量拿复杂度换低停顿。语言与运行时按自己的目标（Java 重吞吐与低停顿、Python 用引用计数+循环检测图简单、C 干脆不用 GC 换可预测性）选择组合。这些高级工程细节（具体收集器如 G1/ZGC 的参数与阶段）属于运行时系统专门课，本篇讲到"每种基础算法解决什么问题、代价是什么"为止，不做专家纵深。
