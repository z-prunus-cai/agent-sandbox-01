## 1.1 ADT 概念 — 规范 vs 实现分离、接口契约

### 1.1.1 什么是抽象数据类型

抽象数据类型（abstract data type, ADT）是从「能存放哪些值、支持哪些操作、每个操作的语义是什么」这个角度对一类数据的描述，它只规定「做什么（what）」，完全不规定「怎么做（how）」。CS61B 把 List、Set、Map 这样的东西叫 ADT；Open Data Structures 用「接口（interface）」这个词表达同一件事——接口描述一个数据结构支持的操作集合，而数据结构才是这些操作的具体实现。

一个 ADT 通常由两部分构成：

- 一组值（这个类型能表示的数据，如「一个整数序列」）；
- 一组操作及其语义（如栈的 `push(x)`、`pop()`、`peek()`，并说明它们各自对状态的影响）。

初学者最容易混淆的是把 ADT 和它的实现绑死，比如一听到「栈」就想到「数组」。但「栈」这个 ADT 只承诺「后进先出（LIFO）」这条语义，至于底下用数组还是链表存，那是实现的自由。心智模型：ADT 是「合同」，实现是「按合同干活的承包商」——只要满足合同，换承包商不影响甲方（调用者）的代码。

### 1.1.2 接口契约：前置条件、后置条件与不变式

ADT 的每个操作都带一份契约（contract），用来精确说明调用者和实现者之间的责任划分。契约通常包含三类断言：

- 前置条件（precondition）：调用操作前必须成立的条件，由调用者负责保证（如「对非空栈才能 `pop`」）；
- 后置条件（postcondition）：操作正确执行后保证成立的结果，由实现者负责保证（如「`push(x)` 后 `peek()` 返回 `x`」）；
- 表示不变式（representation invariant）：实现内部始终维持为真的性质（如数组栈里「栈顶下标始终等于元素个数减一」）。

契约的价值在于把「正确性」变成可以分工核对的东西：调用者只需读接口契约就能正确使用一个结构，无需读实现源码；实现者只需保证后置条件成立，无需担心调用者怎么用。这正是「抽象」省心的来源——它在调用者面前竖起一道信息屏障，屏障两边可以独立推理、独立演化。

一个常见易错点是把前置条件的责任推给实现：初学者常写「反正 `pop` 空栈会抛异常，调用时不检查也行」。但抛异常属于实现对「违约」的处理策略，不等于允许违约；依赖未定义/异常行为写出的代码，一旦换实现就可能崩。

### 1.1.3 规范与实现分离：同一个 ADT 的多种实现

规范（specification，即接口契约）与实现（implementation）分离，意味着同一个 ADT 可以有多种实现，它们对外行为一致，但内部代价画像不同。CS61B 的 ADTs 讲次用 Java 的 `List` 接口举例：`ArrayList`（底层动态数组）和 `LinkedList`（底层链表）都实现同一个 `List` 接口，可以互换，但随机访问、头部插入的代价截然不同。

下面用 Python 展示同一个「栈」ADT 的两种实现对外完全一致：

```python
class ArrayStack:          # 用列表（动态数组）实现
    def __init__(self): self._a = []
    def push(self, x): self._a.append(x)
    def pop(self):     return self._a.pop()
    def peek(self):    return self._a[-1]
    def is_empty(self): return not self._a

class LinkedStack:         # 用单链表头部实现
    def __init__(self): self._head = None
    def push(self, x): self._head = (x, self._head)
    def pop(self):
        x, self._head = self._head
        return x
    def peek(self):    return self._head[0]
    def is_empty(self): return self._head is None
```

任何只依赖 `push/pop/peek/is_empty` 语义的代码（比如括号匹配、表达式求值），传入哪个实现都能跑对——这就是「面向接口编程」。分离带来的直接好处：可以先用最简单的实现把逻辑跑通，之后在不改调用方的前提下换成更快/更省内存的实现。

正确性由 ADT 契约保证，效率由实现选择决定，这两件事被刻意解耦。渐近分析（1.2 起）正是用来比较「同一个 ADT 的不同实现效率差异」的尺子。

### 1.1.4 ADT、数据结构与具体类型的辨析

三个词常被混用，务必分清：ADT 是「操作语义的规范」（如 Stack/List/Map）；数据结构（data structure）是「支持某组操作的具体组织方式」（如数组、链表、哈希表）；而语言里的具体类型（如 Python 的 `list`、`dict`）是「某种数据结构在某语言里的落地产物」。

它们是「规范 → 实现方式 → 具体产品」的三层关系。同一个 ADT 可由多个数据结构实现（Map 可用哈希表或平衡树实现）；同一个数据结构也可实现多个 ADT（动态数组既能实现 List，也能实现 Stack、Queue）。

Python 的 `list` 名字叫 list，但它是动态数组（连续内存 + 下标 O(1) 访问），不是链表；而 ADT 意义上的「表（List）」并不规定连续存储。名字与底层结构不一致是初学者踩坑的高发区，判断代价时要看底层数据结构，而不是看类型名。

## 1.2 渐近记号 — Big-O/Θ/Ω 的定义与关系

### 1.2.1 为什么用渐近：只看增长率，扔掉常数和低阶项

渐近分析（asymptotic analysis）关心的是：当输入规模 n 趋于无穷大时，算法代价随 n 增长的量级（order of growth），而刻意忽略常数因子和低阶项。之所以这么做，是因为常数因子依赖机器、编译器、语言，不可移植；而增长率反映算法本身的可扩展性，是跨平台可比的本质属性。

一个代价为

3n² + 100n + 500

的算法，当 n 很大时，n² 项主导一切——n=10⁶ 时 3n² 已是 3×10¹²，而 100n 才 10⁸，相差上万倍。所以我们说它是「n² 量级」，记作 Θ(n²)，把系数 3 和低阶的 100n+500 都扔掉。

渐近记号是一副「只看大局的望远镜」，它回答「输入翻倍/翻十倍时，代价大致怎么变」，而不回答「跑几毫秒」。因此两个都是 O(n²) 的算法在具体机器上可能快慢差几倍（常数不同），但当 n 足够大时，任何 O(n) 算法终将碾压任何 O(n²) 算法——这正是渐近比较的意义所在。

### 1.2.2 大 O：渐近上界

O(g(n)) 表示「增长不快于 g(n)」的函数集合。CLRS 的正式定义是：f(n) = O(g(n)) 当且仅当存在正常数 c 和 n₀，使得

0 ≤ f(n) ≤ c·g(n)，对所有 n ≥ n₀ 成立。

从某个规模 n₀ 起，只要把 g(n) 乘上一个足够大的常数 c，它就能永远压在 f(n) 上方。所以 O 给的是「最多不超过」的天花板。

2n + 3 = O(n)，取 c=3、n₀=3 即可验证（n≥3 时 2n+3 ≤ 3n）。同时 2n+3 也 = O(n²)、= O(n³)——因为 O 只要求「不快于」，一个宽松的上界照样合法。这引出初学者最常见的误解，见 1.2.5。

### 1.2.3 大 Ω：渐近下界

Ω(g(n)) 与 O 对称，表示「增长不慢于 g(n)」。CLRS 定义：f(n) = Ω(g(n)) 当且仅当存在正常数 c 和 n₀，使得

0 ≤ c·g(n) ≤ f(n)，对所有 n ≥ n₀ 成立。

从 n₀ 起，g(n) 乘上某个正常数后永远压在 f(n) 下方，所以 Ω 给的是「至少不低于」的地板。例：2n + 3 = Ω(n)，也 = Ω(1)、= Ω(√n)——同样，一个宽松的下界也合法。

Ω 常用来陈述「问题下界」，即「任何算法至少要花这么多」。例如「比较排序至少要 Ω(n log n) 次比较」（本课大主题 11 / L3-01 会证），这是对问题本身而非某个算法的断言。

### 1.2.4 大 Θ：渐近紧界，以及三者关系

Θ(g(n)) 表示「增长与 g(n) 同阶」，即同时被 g(n) 从上下夹住。CLRS 定义：f(n) = Θ(g(n)) 当且仅当存在正常数 c₁、c₂、n₀，使得

0 ≤ c₁·g(n) ≤ f(n) ≤ c₂·g(n)，对所有 n ≥ n₀ 成立。

三者的核心关系可以一句话概括：Θ 就是 O 与 Ω 的交集。CLRS 的定理 3.1 正式陈述了这点：

f(n) = Θ(g(n)) 当且仅当 f(n) = O(g(n)) 且 f(n) = Ω(g(n))。

O 是天花板、Ω 是地板，两者贴着同一个 g(n) 时，f 就被夹成「正好这个量级」，这是最精确的刻画。例：3n²+100n+500 = Θ(n²)，因为它既 = O(n²)（上界）又 = Ω(n²)（下界）。

O 像 ≤，Ω 像 ≥，Θ 像 =（都在「忽略常数」的意义下）。CS61B 因此把 Θ 作为首选记号，鼓励能给紧界时就给 Θ，而不是含糊地只写 O。

### 1.2.5 常见增长率阶梯与三个高频易错点

按增长由慢到快排列的常见量级阶梯（初学者应背下大小顺序）：

1 ≺ log n ≺ √n ≺ n ≺ n log n ≺ n² ≺ n³ ≺ 2ⁿ ≺ n!

其中「log n 比任何正次幂都慢」这一条最反直觉，可用极限坐实（sympy 实测）：

lim (n→∞) log(n) / n^0.001 = 0

即 log n 连 n^0.001 都追不上。


- 「O(n²) 就是最坏情况」——错。O/Ω/Θ 是关于函数增长的界，与最坏/平均/最好是两个正交的维度（见 1.3）。可以说「最坏情况是 Θ(n²)」，也可以说「最好情况是 Θ(n)」，情况先固定，再套记号。
- 「用 = 号就当等号」——记号 f(n) = O(g(n)) 里的「=」其实是「∈（属于集合）」的滥用写法，是单向的：能写 2n = O(n²)，不能写 O(n²) = 2n。CLRS 明确指出这个「=」不可对称解读。
- 「常数和底数无所谓到可以乱丢对数底」——log 的底在渐近里确实可丢（换底只差常数因子），但幂次和指数不能丢：n² 与 n³ 不同阶，2ⁿ 与 3ⁿ 也不同阶。

## 1.3 最坏/平均/最好情况分析 — 输入分布与代价刻画

### 1.3.1 三种情况的定义：在固定规模的不同输入之间取

对固定的输入规模 n，同一个算法在不同具体输入上代价可能不同。三种情况分析就是在「所有规模为 n 的输入」这个集合上，分别取代价的三种统计量：

- 最坏情况（worst case）：在规模 n 的所有输入里代价最大的那个，给出「上限保证」；
- 最好情况（best case）：代价最小的那个，通常意义有限；
- 平均情况（average case）：在某个输入概率分布下代价的期望值。

情况分析固定的是「n 已定、输入在变」这一层，回答「同样大小的输入里，运气最差/最好/平均能有多差」。这和渐近记号（回答「n 变大时增长多快」）是两个独立维度，把两者组合起来才是一句完整的代价陈述，例如「线性查找的最坏情况是 Θ(n)」。

最小例子——顺序查找（linear search）一个长度为 n 的数组找 key：最好情况是 key 恰在第一个位置，Θ(1)；最坏情况是 key 不存在或在最后，Θ(n)。同一个算法、同一个 n，两种情况差一个量级。

### 1.3.2 为什么默认分析最坏情况

实践中「最坏情况」是最常报告的，原因有三，CLRS §2.2 明确列出：

- 它给出运行时间的上界保证，即「无论输入多坏，都不会更慢」，这对有时限要求的系统是硬承诺；
- 对许多算法，最坏情况经常发生（如查找一个不存在的元素）；
- 平均情况往往和最坏情况同阶，且平均情况需要额外假设输入分布（见 1.3.3），最坏情况不需要。

最坏情况像「体检报告里的上限值」——它未必是你日常的样子，但它是你能对外做出的安全承诺。工程上说「这个操作是 O(log n)」，默认指的就是最坏情况上界，除非另行说明。

### 1.3.3 平均情况与输入分布假设

平均情况分析要先假定一个输入的概率分布，再算代价的期望。它的结论强度完全取决于这个分布假设是否贴合现实——分布假设变了，平均情况结论就变了，这是它比最坏情况「脆」的地方。

用期望的定义写，若规模 n 的输入 x 出现概率为 P(x)、代价为 T(x)，则平均情况代价为

E[T] = Σ_x P(x)·T(x)


- 顺序查找：若假设 key 等概率地位于 n 个位置之一，则平均需检查约 (n+1)/2 个元素，仍是 Θ(n)——此处平均与最坏同阶。
- 快速排序：在「输入随机排列」假设下平均是 Θ(n log n)，但最坏（每次划分极不均衡）是 Θ(n²)——此处平均远好于最坏，正是快排实践中好用的原因（L3-01 深挖）。

平均情况 ≠ 「最坏和最好的算术平均」。它是按输入分布的加权期望，两者通常不相等；脱离分布假设谈平均情况是没有意义的。

### 1.3.4 情况分析与渐近记号是正交的两件事

最坏/平均/最好是「在哪种输入上量」，O/Ω/Θ 是「用哪种界来表达这个量随 n 的增长」。二者正交，可以自由组合。

因此下面都是合法且互不矛盾的陈述：「插入排序最坏情况 Θ(n²)」「插入排序最好情况（已排序输入）Θ(n)」「顺序查找最坏情况 O(n)」。给出「Θ(n²)」时若不说是哪种情况，默认理解为最坏情况。

一个常见的错误说法是「插入排序是 O(n²) 所以永远慢」——忽略了它在近乎有序的输入上最好情况只有 Θ(n)，这正是它被用作小数组/近有序数组子程序的原因。把「情况」和「界」分清，才能读懂这类看似矛盾的效率描述。

## 1.4 均摊分析 — 聚合/记账/势能法框架（CLRS Ch16）

### 1.4.1 均摊的概念：一串操作平摊，不是平均情况

均摊分析（amortized analysis）求的是「一串操作的最坏总代价除以操作数」，即每个操作的均摊代价。它给出的是对任意操作序列都成立的确定性保证，因此和「平均情况分析」有本质区别——CLRS 明确指出均摊分析不涉及概率、不假设输入分布。

某些操作偶尔很贵（如动态数组扩容要搬全部元素），但贵操作之间隔着很多便宜操作，把总账摊到每次操作上，每次的均摊代价仍然很低。均摊关心「长期总账」，而不是「单次最坏」。

只看单次最坏，动态数组的一次 append 最坏是 O(n)（触发扩容搬迁）；但这会严重高估——因为 O(n) 的扩容不可能每次都发生。均摊分析给出更真实的界：n 次 append 总代价 O(n)，故每次均摊 O(1)。CLRS 给出三种做这笔账的方法，见下。

### 1.4.2 聚合法（aggregate method）

聚合法最朴素：直接算「n 个操作的最坏总代价 T(n)」，再令每个操作的均摊代价为 T(n)/n。它不区分不同操作类型，给所有操作同一个均摊值。

以动态数组的 n 次 append（按 2 倍扩容）为例：扩容只在容量为 1,2,4,8,…,2^k 时发生，各次搬迁代价之和为

1 + 2 + 4 + ⋯ + 2^k < 2·2^k ≤ 2n

加上 n 次写入本身的 n，总代价 < 3n = O(n)，故每次 append 均摊 O(1)。实测（Python 模拟 2 倍扩容累计代价）：

```
doubling total cost n=1000:   2023  ratio/n=2.023
doubling total cost n=100000: 231071 ratio/n=2.311
```

（环境：Python 3.11.15 / Linux 6.18.5 x86_64；代码为 scratchpad 内示意脚本，模拟「满则容量翻倍并搬迁」的计数模型。）比值稳定在小常数（≈2–3），实证了「总代价线性、每次均摊 O(1)」。

### 1.4.3 记账法（accounting method）

记账法给每种操作指定一个「均摊费用」（可高于或低于其实际代价），把多收的部分作为「存款（credit）」预存在数据结构的某些对象上，将来用于支付实际代价高于均摊费用的贵操作。只要保证账户余额永不为负，总均摊费用就是总实际代价的上界。

每次 append 收「3 元」——1 元付本次写入，另 2 元存起来。等到扩容需要搬迁时，被搬的每个元素身上正好攒够了搬迁自己的钱。于是每次 append 均摊 3 = O(1)，贵操作用「预存款」支付。

均摊费用是分析者自己设定的「记账口径」，可以任意设，唯一硬约束是余额（总预收 − 总实付）任何时刻 ≥ 0。设得好就能得到漂亮的常数均摊界。

### 1.4.4 势能法（potential method）

势能法是三者中最通用的。它给数据结构的每个状态 D_i 定义一个势能函数 Φ(D_i)（直觉：结构里「攒着的、将来能用来抵扣贵操作的能量」）。第 i 个操作的均摊代价定义为实际代价加上势能变化：

ĉ_i = c_i + Φ(D_i) − Φ(D_{i−1})

对 n 个操作求和，中间项望远镜式相消，得到：

Σ ĉ_i = Σ c_i + Φ(D_n) − Φ(D_0)

只要保证 Φ(D_n) ≥ Φ(D_0)（常令 Φ(D_0)=0 且 Φ 恒非负），均摊总代价就是实际总代价的上界。

势能像「水位」。便宜操作把水位抬高（存能量），贵操作把水位放低（花能量抵扣自己的高实际代价），使每步的均摊代价都平滑。势能法之所以最常用，是因为一旦找到合适的 Φ，逐步套公式即可，无需像记账法那样对每种操作单独编故事。（本课大主题 8 并查集的 α(n) 界、栈的 multipop 都用势能法分析。）

### 1.4.5 实现级旁证：CPython 动态数组的扩容因子

CPython 的 `list` 是动态数组，其 `list_resize()` 决定扩容策略。v3.11.15 的 `Objects/listobject.c` 中，新容量的核心计算与注释如下（逐字引自源码）：

```c
/* The growth pattern is:  0, 4, 8, 16, 24, 32, 40, 52, 64, 76, ... */
new_allocated = ((size_t)newsize + (newsize >> 3) + 6) & ~(size_t)3;
```

这里 `newsize >> 3` 就是 `newsize / 8`，故新容量 ≈

new_allocated ≈ newsize × (1 + 1/8) = 1.125 × newsize

即 CPython 用约 1.125 倍（9/8）的温和过量分配，而非教材惯用的 2 倍。实测复现该增长序列（Python 计算 `list_resize` 公式，环境 Python 3.11.15 / Linux 6.18.5）：

```
growth capacities: [0, 4, 8, 16, 24, 32, 40]
```

与源码注释的前缀完全吻合。

这里正好是一处一手源之间的口径分歧，须点明而非和稀泥：

- CLRS / Open Data Structures 的均摊论证用「2 倍扩容」（factor 2）作理想模型，便于教学（1+2+4+… 的等比和最漂亮）；
- CPython 实测用 ≈1.125 倍；Java 的 `ArrayList` 用 1.5 倍（`oldCapacity + (oldCapacity >> 1)`）。

分歧的实质并非矛盾：均摊 O(1) 只要求扩容因子是「大于 1 的常数倍」（几何增长），任何固定倍数 g>1 都给 O(1) 均摊——倍数越大越省搬迁次数但越费内存，越接近 1 越省内存但搬得更勤。教材取 2 是为讲清原理，实现取 1.125/1.5 是内存与拷贝的工程折中。反例警示：若改成「每次 +固定常数」（算术增长而非几何增长），均摊会退化到 O(n)，这正是几何扩容不可省的原因。

## 1.5 递归式与主定理入门 — 分治代价递推求解（CLRS Ch4）

### 1.5.1 递归式是什么：分治代价的自我引用

递归式（recurrence）是用「更小规模上的自身」来表达一个函数值的方程或不等式，天然刻画分治（divide-and-conquer）算法的代价：一个规模为 n 的问题被拆成若干规模更小的子问题，各自递归求解，再花一些代价合并。分治算法的运行时间通式为

T(n) = a·T(n/b) + f(n)

其中 a ≥ 1 是子问题个数，b > 1 是每个子问题规模缩小的倍数，f(n) 是「拆分 + 合并」的非递归代价（CLRS 4th ed 称 f(n) 为驱动函数 driving function）。

归并排序把数组分成 2 半（a=2, b=2），各自排序，再线性合并（f(n)=Θ(n)），于是

T(n) = 2·T(n/2) + Θ(n)

「求解递归式」就是把这种自我引用的式子解成一个不含递归的闭式增长量级（如 Θ(n log n)）。

### 1.5.2 求解递归式的三种入门方法

CLRS Ch4 给出三条路子，初学者按「够用优先」的顺序掌握：

- 代入法（substitution）：先猜一个界，再用数学归纳法验证。灵活但要先会猜。
- 递归树法（recursion tree）：把递归展开画成树，每层算出代价，逐层求和。最直观，常用来「猜界」再交给代入法证。
- 主定理（master theorem/master method）：针对 T(n)=a·T(n/b)+f(n) 这种规整形式，直接套公式出答案，无需归纳。最快，但只适用于该标准形式。

对归并排序，树共 log₂n 层，每层所有结点的合并代价合起来都是 Θ(n)，故总代价 ≈ 层数 × 每层代价 = Θ(n log n)。主定理本质上就是把「递归树逐层求和」的结果封装成了可直接查表的三种情形。

### 1.5.3 主定理的三种情况

主定理比较「驱动函数 f(n)」与「分水岭函数（watershed）」

n^(log_b a)

的大小——log_b a 是递归树叶子总数的指数。设 a≥1、b>1，则（CLRS 4th ed 定理 4.1）：

- 情况 1：若 f(n) = O(n^(log_b a − ε))，某常数 ε>0，即叶子代价占主导，则

  T(n) = Θ(n^(log_b a))

- 情况 2：若 f(n) = Θ(n^(log_b a)），即两者同阶（每层代价相当），则

  T(n) = Θ(n^(log_b a) · log n)

  （CLRS 4th ed 将此推广为：若 f(n)=Θ(n^(log_b a)·log^k n)，k≥0，则 T(n)=Θ(n^(log_b a)·log^(k+1) n)。）

- 情况 3：若 f(n) = Ω(n^(log_b a + ε))，某常数 ε>0，且满足正则条件 a·f(n/b) ≤ c·f(n)（某常数 c<1，大 n 成立），即根部代价占主导，则

  T(n) = Θ(f(n))

叶子重 → 看叶子（情况 1）；上下一样重 → 多乘一个 log（情况 2）；根重 → 看根（情况 3）。

### 1.5.4 最小例子与易错点

用主定理解归并排序 T(n)=2T(n/2)+Θ(n)：这里 a=2, b=2，分水岭指数

log_b a = log₂ 2 = 1

（sympy 实测 `log(2,2)=1`）。驱动函数 f(n)=Θ(n)=Θ(n¹)，与分水岭 n¹ 同阶，命中情况 2，故

T(n) = Θ(n^1 · log n) = Θ(n log n)

与「递归树 log n 层、每层 Θ(n)」的直觉一致。


- 情况 1/3 要求 f 与分水岭之间相差一个多项式因子 n^ε（ε>0 严格为正）。若只相差一个对数因子（如 f(n)=n log n 对 n），落在情况 1、2 之间的「缝隙（gap）」里，主定理不适用，需改用递归树或代入法（4th ed 的推广情况 2 能覆盖部分此类）。
- 情况 3 的正则条件（regularity）不可漏；工程题里几乎总满足，但形式上属于情况 3 成立的前提。
- 主定理只管 T(n)=a·T(n/b)+f(n) 这种「子问题等大、按倍缩小」的规整形式。像 T(n)=T(n−1)+n（减法型）或子问题不等大的递归式，不能套主定理，得另解。
