**线性表 = 把元素排成"一条线"、按位置访问的序列**。它有两种截然不同的物理实现——**数组**把元素挤在一段连续内存里（靠"下标算地址"直达任意元素，但增删要搬家、扩容要重分配）；**链表**把每个元素单独装进一个结点、用指针把结点串起来（增删只改指针不搬家，但找第 i 个元素得从头一个个走）。两者的取舍贯穿本主题：**连续 = 随机访问快、缓存友好，但中间插删贵**；**分散 = 端点插删快、天生可增长，但随机访问慢、缓存不友好**。选哪种，取决于你的操作以"按下标读"为主还是以"到处插删"为主。

## 2.1 静态数组与随机访问

### 2.1.1 连续内存布局：元素等宽、紧挨排列

静态数组（static / fixed-size array）是**同一类型的元素在内存里连续、紧挨排布**的一段区域，长度在创建时定死。因为每个元素类型相同、宽度相等（记作 `s = sizeof(元素)` 字节），第 `i` 个元素的位置完全可由起点算出，不必逐个去找。

把数组想成一排等间距的储物柜，柜子编号 0、1、2…，每个柜子一样大。只要知道第 0 号柜子在哪、每个柜子多宽，就能一步算出任意编号柜子的位置——不用从头数过去。这份"连续 + 等宽"正是数组一切好处（随机访问、缓存友好）的物理根源，也是它一切代价（定长、插删搬家）的根源。

数组"连续"是对**逻辑相邻的元素物理也相邻**的承诺。正因如此，数组能被 CPU 的缓存机制高效预取（见 2.5）；而链表没有这个承诺，结点可以散落在堆的任意角落。

### 2.1.2 O(1) 随机访问：下标寻址公式

"随机访问（random access）"指**访问任意下标的元素都花同样的常数时间**，与下标大小、数组长度无关。它靠一条简单的地址算术实现：

addr(a[i]) = base + i × sizeof(元素)

其中 `base` 是数组首元素地址、`sizeof(元素)` 是单个元素字节宽。给定 `i`，一次乘加就得到地址，随即一次访存取值——步数固定，故为

T_访问(i) = O(1)

它是数组区别于链表的**决定性优势**。链表要取第 `i` 个结点，必须从头沿指针走 `i` 步（O(n)）；数组则"一步到位"。这也解释了 L1-01 里 `a[i]` 与 `*(a+i)` 为何等价——`a+i` 正是上面这条指针算术（指针加法按元素宽自动缩放），`a[i]` 只是它的语法糖。

这条 O(1) 假设"一次访存 = 一个单位时间"，这是**渐近分析的理想模型**。真实硬件上，命中缓存和穿透到主存差几十倍（见 2.5），但在大 O 意义下都算 O(1)——模型与硬件的这条缝隙要心里有数。

### 2.1.3 静态数组的代价画像与硬限制

静态数组的完整代价画像：**按下标读/写 O(1)**（上一节）；但**长度固定不可增长**，**在中间插入或删除要移动其后所有元素**，故

T_插入/删除(位置 i) = O(n − i)  最坏 O(n)

因为要在下标 i 处腾出/填补一个空位，后面的元素得整体后移/前移一格。

往 `[10,20,30,40]` 的下标 1 处插入 `15`，必须把 `20,30,40` 各右移一格才能空出位置，得到 `[10,15,20,30,40]`——移动了 3 个元素。数组越长、插入点越靠前，搬得越多。删除同理。**只有在末尾追加/删除**（若还有空位）才是 O(1)，因为无需搬动别人。

其一，静态数组**长度是死的**——存不下就得另开一块更大的、把旧数据拷过去（这正是 2.2 动态数组要解决的问题）。其二，在 C 里**数组不做边界检查**（L1-01 大主题6），`a[n]` 越界是未定义行为；这属实现层安全问题，与本处的代价画像分开看。

## 2.2 动态数组与均摊扩容

### 2.2.1 动态数组是什么：容量与逻辑长度分离

动态数组（dynamic array / 可增长数组，Python 的 `list`、Java 的 `ArrayList`、C++ 的 `std::vector` 都是）在静态数组之上加了"能自动变长"的能力。它的关键设计是**把两个量分开**：

- **容量（capacity）**：底层实际分配的那块连续内存能装几个元素；
- **逻辑长度（size / length）**：当前真正存了几个元素。

始终满足

0 ≤ size ≤ capacity

动态数组内部藏着一块"可能比你看到的更大"的连续数组。追加元素时若还有空位（size < capacity），直接放进去、size 加一，O(1)；一旦装满（size == capacity），就**另分配一块更大的连续内存、把旧元素全拷过去、再放新元素**——这一步是 O(n) 的"搬家"。诀窍在于：只要搬家发生得足够稀疏，把它的代价"摊"到中间那许多次便宜的追加上，平均下来每次追加仍是常数。

**"看起来的长度" ≠ "实际占的内存"**。这正是 Python 里 `len(lst)`（逻辑长度）和 `sys.getsizeof(lst)`（含预留容量的字节数）常对不上的原因——下一节用实测坐实。

### 2.2.2 几何扩容 → O(1) 均摊 append（为什么必须"倍增"而非"加常数"）

**每次扩容按当前容量乘一个常数因子（几何/倍增增长），追加操作即得 O(1) 均摊代价**；若改成"每次只加固定几个位置"（算术增长），均摊代价会退化成 O(n)。

以最经典的"容量翻倍"（因子 2）分析：从空表追加 n 个元素，扩容发生在容量 1、2、4、8、…、n 处，每次扩容拷贝的元素数是 1+2+4+…+n，这是一个几何级数，其和

1 + 2 + 4 + ⋯ + n < 2n

即 n 次追加里所有搬家的**总拷贝次数是线性的 O(n)**，摊到每次追加就是

T_append(均摊) = O(n) / n = O(1)

反之若每次只"加常数 c 个位置"，则扩容发生 n/c 次、第 k 次要拷 ck 个元素，总拷贝是 c(1+2+…+n/c) ≈ n²/(2c)，即 O(n²)，摊到每次是 O(n)——直接退化。

**容量翻倍后，你"白赚"了和已有元素一样多的空位**，要再次触发搬家得先把这些空位填满，也就是要再追加 n 次才扩一次容——搬家的频率随规模指数级稀释，于是每个元素平均只被拷贝 O(1) 次。这是 L2-01 大主题1「均摊分析」（CLRS Ch16 动态表）最标准的应用例。

易错点/关键辨析：**"几何 vs 算术"是这里唯一真正要记住的道理**，因子取 2 还是 1.5 还是 1.125 只影响常数（时间-空间权衡：因子越大追加越少搬、但预留浪费越多），不影响"均摊 O(1)"这个量级——只要因子是大于 1 的常数即可。CS61B 专门强调初学者最常犯的错就是写成 `resize(size + 1)`（算术增长），导致看似能跑、实则 O(n²)。

### 2.2.3 CPython list 的实际扩容因子（读 listobject.c）

CPython 的 `list` 并不用"翻倍"，而用一个**更温和的约 9/8 ≈ 1.125 的几何因子**。直接取证 CPython 3.11.15 源码 `Objects/listobject.c` 的 `list_resize()`，其过量分配公式是：

new_allocated = (newsize + (newsize >> 3) + 6) & ~(size_t)3

`newsize >> 3` 就是 `newsize / 8`，故新容量 ≈ `newsize × 9/8 + 6`，最后 `& ~3` 把结果向下取整到 4 的倍数（对齐）。源码注释给出的容量增长序列是：

0, 4, 8, 16, 24, 32, 40, 52, 64, 76, …

注释原文说明其意图：过量分配"proportional to the list size…mild, but…enough to give linear-time amortized behavior over a long sequence of appends"（与规模成比例、幅度温和、但足以让长序列 append 得到线性均摊行为）。

本机实测坐实（基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25，用 `sys.getsizeof` 反推容量，每元素 8 字节指针、空表头 56 字节）——记录每次容量变化时的 `(逻辑长度, 容量槽数)`：

    empty list getsizeof = 56 bytes
    (len_at_growth, capacity_slots):
    [(1,4),(5,8),(9,16),(17,24),(25,32),(33,40),(41,52),(53,64),(65,76),(77,92),(93,108),(109,128),(129,148)]

容量序列 4, 8, 16, 24, 32, 40, 52, 64, 76, 92, 108, 128, 148 与源码注释的 `0,4,8,16,24,32,40,52,64,76,…` 完全吻合——**实测与一手源码互证**。

追加的均摊常数也实测（`timeit`，单次运行）：

    append    100000 items:    3.52 ms  (35.23 ns/append)
    append   1000000 items:   31.50 ms  (31.50 ns/append)

10⁵ 与 10⁶ 规模下每次追加稳定在约 31–35 ns（近似常数），印证 O(1) 均摊。（10⁷ 规模会因超出缓存/内存分配抖动而升到约 149 ns/次，那是硬件访存与分配器效应，不推翻均摊 O(1) 这个量级结论。）

### 2.2.4 均摊 ≠ 每次都便宜：单次最坏仍是 O(n)

**"O(1) 均摊"不等于"每一次追加都是 O(1)"**。触发扩容的那一次追加，要拷贝当前所有元素，单次代价是实打实的 O(n)；均摊只是保证"这种昂贵操作足够稀疏，平均下来是常数"。

在**实时/低延迟**场景里，你可能不能容忍某一次追加突然卡一下（那次要搬 100 万个元素）。这时"均摊 O(1) 但最坏 O(n) 单次"就不够，需要别的结构或预分配（`list` 无公开预分配接口，但可一次性 `[None]*n` 造好）。这也是"均摊 vs 最坏"两种分析口径的现实意义——量级相同不代表延迟画像相同。

与 2.1.3 对照：静态数组根本不能增长；动态数组用"偶尔搬一次大家"换来了"平均每次追加常数"的可增长能力——**用空间预留 + 稀疏的大搬家，买到了均摊常数的追加**。

## 2.3 单链表

### 2.3.1 结点与指针：用"指向下一个"把元素串起来

单链表（singly linked list）**不要求元素连续存储**：它把每个元素单独装进一个**结点（node）**，结点里除了存数据，还存一个**指向下一个结点的指针（next）**；最后一个结点的 next 指向空（C 里是 `NULL`，Python 里是 `None`）。整条链由一个指向首结点的**头指针（head）**引出。

    struct Node { int val; struct Node *next; };   // C：一个结点 = 数据 + 后继指针

数组是"一排挤在一起的柜子、靠编号定位"；链表是"一串用绳子（next 指针）系起来的珠子、每颗珠子只知道下一颗在哪"。珠子可以散落在内存的任何地方，全靠指针把它们逻辑上串成一条线。因此链表**天生可增长**（要加元素就新造个结点接上，无需预留连续空间、无需扩容搬家），代价是**失去了 O(1) 随机访问**——你手里只有头指针，想到第 i 颗珠子必须顺着绳子一颗颗数过去。

数组的"下一个元素"靠地址算术（`+size`）隐式得到；链表的"下一个元素"靠显式存的 next 指针得到。前者省了指针的空间但要连续内存，后者每个结点多花一个指针的空间但换来存储的自由。

### 2.3.2 头插 O(1)：从表头加元素最省事

在单链表**头部插入**一个新元素是 O(1) 的：新造一个结点，让它的 next 指向原来的头结点，再把头指针改指向这个新结点即可——只动了两个指针，与链表多长无关。

    new->next = head;   // 新结点接到原链头前面
    head = new;         // 头指针前移到新结点

T_头插 = O(1)      T_数组头插 = O(n)（要整体后移，见 2.1.3）

数组在**头部**插入最惨（后面全体右移 O(n)），而链表头插只改指针、O(1)。这也是"用链表实现栈/队列"很自然的原因（大主题3）。易错点：头插要**先让新结点指向旧头、再移动头指针**；顺序反了（先改 head 再接 next）会丢失对原链其余部分的引用，整条链断掉。

### 2.3.3 查找 O(n) 与按值删除（需要前驱）

单链表的**查找**（找某个值 / 找第 i 个）只能**从头沿 next 逐个走**，最坏要走到表尾：

T_查找 = O(n)

**删除**一个结点时有个单链表特有的麻烦：要把某结点摘下来，必须让它的**前驱结点**的 next 跨过它、指向它的后继。但单链表每个结点只知道"后继"、不知道"前驱"，所以删除时通常得**从头再走一遍、边走边记住前驱**，才能完成"改前驱的 next"：

    prev->next = target->next;   // 前驱跨过 target，target 被摘除

链 `A→B→C`，要删 B，需拿到 A（B 的前驱），令 `A.next = C`，得 `A→C`。若手里只有指向 B 的指针而没有 A，单链表就无法 O(1) 删除 B（这正是 2.4 双链表要解决的痛点之一）。

链表"增删 O(1)"这句常听到的话有**前提**——是"**已经站在操作位置（已持有相关指针）时**改指针 O(1)"。若还要先**定位**（找到第 i 个、或找前驱），定位本身是 O(n)。所以"链表增删快"是就"改接线"这一步而言；把定位算进去，任意位置的增删仍是 O(n)。这是初学者对链表最常见的过度乐观，务必分清"定位"与"接线"两笔账。

## 2.4 双链表与哨兵结点

### 2.4.1 双链表：每个结点同时记住前驱和后继

双链表（doubly linked list）在单链表的基础上，给每个结点**再加一个指向前驱的指针（prev）**，于是每个结点同时知道自己的前一个和后一个：

    struct Node { int val; struct Node *prev, *next; };

单链表的"绳子"是单向的（只能顺着走），双链表的是双向的（前后都能走）。多花一个指针的空间，换来两个好处：**能从任一结点向前或向后遍历**，以及——更实用的——**给定一个结点指针就能 O(1) 删除它**（因为它自己就知道 prev 和 next，不必再从头找前驱，直接解决 2.3.3 的痛点）。

    // O(1) 删除已知结点 x：让它的前后互相牵手、跳过 x
    x->prev->next = x->next;
    x->next->prev = x->prev;

双链表每个结点多一个指针（空间开销更大），且插删时要维护 prev、next **两套指针**、容易漏改一边——这是它相对单链表的主要负担。

### 2.4.2 哨兵/哑结点：用一个"假结点"消灭边界特判

**哨兵结点（sentinel / dummy node）**是一个**不存实际数据的占位结点**，永远待在链表的边界处（常做成一个把头尾接成环的 dummy）。它的唯一目的：**让"空表""表头""表尾"这些边界情形和中间情形长得一模一样**，从而消掉一大堆 `if (head == NULL)`、`if (prev == NULL)` 的特判。

没有哨兵时，在真正的头部插入要特判（得改 head 本身）、删除首结点要特判、空表要特判——每个特判都是一处潜在 bug。有了哨兵，"真正的第一个数据结点"永远有一个前驱（哨兵），"最后一个"永远有一个后继（哨兵），于是**任何插入/删除都变成"在两个已存在结点之间接线"这一种统一情形**，代码里再没有 `NULL` 判断的分叉。

一个带循环哨兵的空双链表，是 `dummy.next = dummy; dummy.prev = dummy;`（哨兵自己牵着自己）。往里加第一个元素、加中间元素、加末尾元素，走的是**完全相同**的四行接线代码——这就是"边界统一"的价值。CS61B 在 DLList 讲次里专门用"circular sentinel"来讲这个技巧，Morin 的 DLList 也用一个 dummy 结点。

哨兵结点**不计入逻辑长度**、不该被当作数据返回；遍历时的终止条件从"走到 NULL"变成"绕回哨兵"（`p != &dummy`）。初学者常忘了把哨兵排除，导致把占位结点当成真元素。

### 2.4.3 双链表的操作代价画像

综合起来，双链表的代价画像：**给定结点指针时，插入/删除该结点是 O(1)**（只改常数个指针，配合哨兵还无边界特判）；但**按下标/按值定位仍是 O(n)**（和单链表一样得逐个走，双向只是能选更近的方向起步，不改变量级）：

T_已知结点处插/删 = O(1)      T_定位第 i 个 = O(n)

与单链表的关键差异就集中在"删除已知结点"：单链表要 O(n) 找前驱，双链表因自带 prev 而 O(1)。代价是每结点多一个指针的空间、以及插删要维护双向指针。

再次强调 2.3.3 的账：双链表也不能把定位算进去还叫 O(1)——"O(1) 增删"始终是"已站在位置上、只改接线"的那一步。

- 一手锚点：CLRS 4th ed(2022) §10.2「Linked lists」（双链表 prev/next 域；带哨兵 `L.nil` 的循环双链表如何统一边界、`LIST-INSERT'`/`LIST-DELETE'` 因哨兵而无需边界特判、删除已知结点 O(1)）。Pat Morin《Open Data Structures》§3.2「DLList: A Doubly-Linked List」（dummy 结点、`addBefore`/`remove(Node)` O(1)、按位置访问 O(n) 但可从较近端出发）。Berkeley CS61B(Lists III: DLList，sentinel/circular sentinel、双向指针，核实 2026-07-25)。核实 2026-07-26。
- 比对结论一致：CLRS 的 `L.nil` 哨兵与 Morin/CS61B 的 dummy/sentinel 是同一技巧的不同命名，三家都确认「哨兵统一边界、双链表 O(1) 删除已知结点、定位仍 O(n)」。
- 冲突/易混点：无实质冲突；命名差异（CLRS `nil`/Morin `dummy`/CS61B `sentinel`）非分歧。易错点：哨兵不计长度、遍历终止条件改为"绕回哨兵"。

## 2.5 连续 vs 分散布局代价画像

### 2.5.1 缓存局部性：为什么连续布局遍历快得多

除了大 O 复杂度，数组和链表还有一个**渐近记号看不见、但真实性能上差几十倍**的差异：**缓存局部性（cache locality）**。现代 CPU 从主存读数据时，不是一个字节一个字节读，而是**一次搬一整条缓存行（cache line，通常 64 字节）进高速缓存**，并会**预取**紧邻的后续数据。数组元素物理连续，顺序遍历时"读一个就顺带把邻居装进了缓存"，后续访问几乎全部命中缓存；链表结点散落各处，每跳一个 next 都可能是一次缓存未命中、被迫穿透到慢速主存。

本机实测坐实这条差异（基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25，`gcc -std=c11 -O2`）——**完全相同的工作量**（都沿 `next` 数组做 2000 万次"跳到下一个"），唯一区别是访问顺序：一份 next 是顺序的（`next[i]=i+1`，模拟连续数组），一份 next 是一个随机大环（模拟结点散落堆各处的链表）：

    sequential  :     46.0 ms   (顺序/连续，缓存友好)
    scattered   :   2871.4 ms   (随机/分散，缓存敌对)

同样 2000 万次指针跳转，分散布局慢了约 **62 倍**——这个差距纯由缓存局部性造成，大 O 完全看不出来（两者都是"O(n) 次访存"）。这正是"数组遍历 vs 链表遍历"在真实机器上的核心差异。

**大 O 假设"每次访存花一个单位时间"，但真实内存有层级（缓存 vs 主存差几十倍）**。所以即便链表和数组的顺序遍历都是 O(n)，数组因连续布局在实践中通常快一个数量级。这也是为什么工业界的"链表"在性能敏感场景常被数组/动态数组取代（呼应 2.2 的 `list`/`vector`）。这属于"渐近模型 vs 硬件现实"的分层——两者都对，只是刻画的东西不同。

### 2.5.2 插入/删除代价对比：搬家 vs 改指针（但别忘了定位）

把两种布局的插删代价并排看：

- **数组（连续）**：在位置 i 插/删要移动其后所有元素，`O(n − i)`；但**定位到位置 i 是 O(1)**（下标寻址）。
- **链表（分散）**：改接线本身 `O(1)`（双链表已知结点）；但**定位到位置 i 是 O(n)**（逐结点走）。

于是"谁更快"取决于你**是否已经站在操作位置**：

- 若你**手里已持有该结点/迭代器**（如"删除当前遍历到的这个"）：链表 O(1) 胜，数组仍要 O(n) 搬移。
- 若你只知道**下标 i、要随机地插删**：数组是"O(1) 定位 + O(n) 搬移 = O(n)"，链表是"O(n) 定位 + O(1) 接线 = O(n)"——**量级相同**，但数组因缓存友好、搬移是连续 memmove，常数通常远小于链表的指针追逐定位。

这解释了一个反直觉的现实结论：**"中间频繁随机插删就该用链表"这句常见说法在现代硬件上往往是错的**——因为链表的 O(n) 定位是缓存敌对的指针追逐，而数组的 O(n) 搬移是缓存友好的连续拷贝，后者常数小得多。链表真正的甜点是"已持有位置、且不需要随机访问、且元素大/拷贝贵"的场景，以及需要 O(1) 拼接/搬迁整段的场景。

### 2.5.3 选型直觉小结

把本主题的代价画像收成一张对照（n 为元素数）：

| 操作 | 数组/动态数组（连续） | 链表（分散） |
|---|---|---|
| 按下标随机访问 a[i] | O(1) | O(n) |
| 顺序遍历 | O(n)，缓存友好（快常数） | O(n)，缓存敌对（慢常数） |
| 末尾追加 | O(1) 均摊（偶尔 O(n) 扩容） | O(1)（有 tail 指针时） |
| 头部插入 | O(n) | O(1) |
| 已知位置处插/删 | O(n) 搬移 | O(1) 改指针（双链表） |
| 额外空间 | 预留容量（浪费上限约与因子相关） | 每元素额外 1~2 个指针 |

**以"按下标读、顺序扫、末尾追加"为主 → 用（动态）数组**（随机访问 O(1)、缓存友好、`list`/`vector` 是默认选择）；**以"在已持有的位置频繁插删、且几乎不做随机访问、或需 O(1) 整段拼接"为主 → 用链表**。这也串起了本大主题的两条线：数组把"连续 + 等宽"用到极致换随机访问与缓存，链表把"指针 + 分散"用到极致换插删自由——没有免费的午餐，选型即在这两组代价间权衡。

- 比对结论一致：CLRS 与 Morin 对「数组 vs 链表复杂度对照」一致；CS61B 亦持相同代价画像。
- 冲突/分歧（显式）：**"渐近复杂度" vs "真实缓存性能"是两个不同刻画层**——按大 O，数组和链表的顺序遍历都是 O(n)（教材主线，把访存当单位代价）；按真实硬件，连续布局因缓存局部性常快一个数量级（本机实测约 62×）。这不是来源打架，而是模型层次不同：CLRS 的复杂度模型不建模缓存，故看不出此差异；须显式标注"O(1)/O(n) 是单位访存模型下的结论"，实际常数受布局与缓存主导。
