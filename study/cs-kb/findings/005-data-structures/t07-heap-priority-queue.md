## 7.1 完全二叉树与数组表示 — 父/子下标公式

### 7.1.1 完全二叉树：堆的形状约束

二叉堆（binary heap）首先是一棵**完全二叉树**（complete binary tree）：除了最底层，每一层都被结点填满，且最底层的结点从左到右**连续排列、不留空洞**。这是堆的「形状不变式」（shape property），与后面 7.2 的「堆序性质」是两条独立的约束，合起来才定义了堆。

为什么非要完全二叉树？因为「每层填满、最后一层靠左」这个约束保证了树高被压到最低：

h = ⌊lg n⌋

即 n 个结点的完全二叉树高度是 ⌊lg n⌋（以 2 为底的对数取下整）。CLRS 4th §6.1 明确给出这一高度界。树高直接决定了后面上浮/下沉操作的最坏代价——正因为树高是 Θ(log n)，插入和取极值才能做到 O(log n)。如果允许树长歪（像退化的 BST 那样成一条链），这个保证就没了。

初学者要区分「完全二叉树」和「满二叉树」（full/perfect，每层都填满、结点数恰为 2^k−1）：完全二叉树允许最后一层不满，但必须靠左连续。正是这个「连续无洞」的性质，让下一节的数组表示能不浪费任何空间。

### 7.1.2 数组表示与父/子下标公式

完全二叉树最漂亮的地方是：它可以**不用任何指针**，直接压进一个数组，用下标的算术关系来表达父子链接。做法是按**层序**（从上到下、每层从左到右）把结点依次放进数组。

用 0 起始下标（Python `heapq`、Open Data Structures 的约定），结点 i 的父、左孩子、右孩子分别是：

parent(i) = ⌊(i − 1) / 2⌋

left(i) = 2·i + 1

right(i) = 2·i + 2

若改用 1 起始下标（CLRS 4th §6.1 的约定，数组从 A[1] 开始），公式更简洁：

PARENT(i) = ⌊i / 2⌋，LEFT(i) = 2·i，RIGHT(i) = 2·i + 1

这两套公式描述的是**同一棵树**，只是数组起始偏移不同——这是初学者最容易搞混、把两套公式混用而算错下标的地方，务必先确认自己用的是 0 起始还是 1 起始。本机实测（0 起始）打印下标映射：

```
i=0: parent=- left=1 right=2
i=1: parent=0 left=3 right=4
i=2: parent=0 left=5 right=6
i=3: parent=1 left=7 right=8
```

为什么公式是「乘 2」这种形式？直觉是：完全二叉树按层序编号时，第 k 层的结点数恰是上一层的两倍且紧接排列，所以「往下一层」在数组下标上就体现为「大致乘 2」。这也解释了数组表示的两大好处：其一，**省掉了每个结点的两个孩子指针**（省空间、且缓存友好，因为父子在数组里下标接近）；其二，**找父/孩子是 O(1) 的下标算术**，不需要顺指针走。代价是它只对「完全二叉树」成立——一棵会长歪、留空洞的树（如普通 BST）就没法这样紧凑地压进数组，否则空洞位置会浪费大量空间。

CPython 的 `heapq` 正是用一个普通 Python `list` 当这棵树，其源码头部注释把不变式写成「a[k] <= a[2*k+1] and a[k] <= a[2*k+2] for all k, counting elements from 0」——`2*k+1` 与 `2*k+2` 就是上面的 left/right 公式，`heap[0]` 就是根（最小元）。

#### 来源与时效
- 锚点：CLRS 4th ed (2022) §6.1「Heaps」——数组表示、PARENT/LEFT/RIGHT（1 起始）、高度 ⌊lg n⌋、完全二叉树形状（核实 2026-07-26）。
- 锚点：Open Data Structures（Morin）§10.1 BinaryHeap——0 起始下标的 `left(i)=2i+1 / right(i)=2i+2 / parent(i)=(i−1)/2`、以数组隐式表示完全二叉树（核实 2026-07-26）。
- 锚点：CPython 源码 `Lib/heapq.py` @tag v3.11.15——头部注释「a[k] <= a[2*k+1] and a[k] <= a[2*k+2] ... counting elements from 0」、`heap[0]` 为最小元（核实 2026-07-26）。
- 冲突/分歧：**下标起始约定不同**——CLRS 用 1 起始（LEFT=2i），heapq / Open Data Structures 用 0 起始（left=2i+1）。二者是同一结构、仅数组偏移差异，公式已两套并列、分账说明；混用会算错下标，是主要陷阱。

## 7.2 维护堆性质 — 下沉 heapify、自底向上建堆 O(n)

### 7.2.1 堆序性质与下沉操作（sift-down / heapify）

堆的第二条不变式是**堆序性质**（heap-order / heap property）。以最小堆为例：

任意结点 i（非根）：A[parent(i)] ≤ A[i]

即**每个父结点都不大于它的孩子**，因此沿任一条根到叶的路径值是非降的，**根一定是全局最小值**（最大堆则反号，根是最大值）。注意堆序只约束「父子」，不约束「左右兄弟」，所以堆是**部分有序**（partially ordered），远弱于 BST 的全序——这也是建堆能比排序更便宜的根本原因。

「下沉」（CLRS 称 MAX-HEAPIFY，最小堆则称 min-heapify 或 sift-down）用来**修复单个结点违反堆序的局部破坏**：假设结点 i 的两棵子树都已是合法堆，但 i 自己可能比孩子大（最小堆情形），下沉就把 i 与它「更小的那个孩子」比较、若违反就交换，然后在被换下去的位置继续这个过程，直到 i 沉到合适位置或到达叶子。因为最多沿树高走一条路径：

下沉（heapify）单次代价 ： O(h) = O(lg n)

直觉心智模型：下沉像「一个不合格的经理被逐级下调」——只要手下有比他更够格（更小）的，就和最够格的那个换位，一路降到他真正胜任的层级为止。易错点：最小堆下沉时必须和**两个孩子中较小的**那个换，换错成较大的会破坏另一支的堆序。

### 7.2.2 自底向上建堆与 O(n) 紧界

给定一个乱序数组，把它整体变成堆有两种思路。朴素思路是「逐个 insert」，n 次每次 O(log n)，总代价 O(n log n)（见 7.3、7.2.3 实测）。更好的思路是**自底向上建堆**（BUILD-HEAP）：**从最后一个非叶结点开始、下标递减到根，对每个结点做一次下沉**。CLRS §6.3 的 BUILD-MAX-HEAP 循环是 `for i = ⌊n/2⌋ downto 1`；CPython `heapq.heapify` 的等价写法是：

```python
def heapify(x):
    n = len(x)
    for i in reversed(range(n//2)):
        _siftup(x, i)          # _siftup 即下沉，把 x[i] 沉到合适位置
```

为什么从 ⌊n/2⌋（0 起始时下标 n//2−1）开始？因为下标 ≥ n//2 的都是**叶子**，叶子本身就是合法的单结点堆、无需下沉。从倒数第二层往上逐个下沉，能保证「处理结点 i 时，它的两棵子树已经是合法堆」，正好满足下沉的前提。

关键且反直觉的结论是：**自底向上建堆是 O(n)，不是 O(n log n)**。虽然单次下沉最坏 O(log n)、共做约 n/2 次，粗估是 O(n log n)，但这个界不紧。真实代价要按「结点所在高度」加权求和——越靠近叶子的结点越多、但能下沉的高度越小：

T(n) = ∑_{h=0}^{⌊lg n⌋} ⌈n / 2^{h+1}⌉ · O(h) = O( n · ∑_{h=0}^{∞} h / 2^h ) = O(n)

其中级数 ∑ h/2^h 收敛到常数 2，所以总和是 O(n)。CLRS §6.3 给出的正是这个「按高度加权、级数收敛到常数」的紧界论证。直觉版：一半结点是叶子（下沉 0 步），四分之一在高度 1（至多沉 1 步）……真正要沉很远的根附近结点极少，加权平均后每个结点的均摊下沉步数是常数。

### 7.2.3 本机实测：建堆 O(n) vs 逐个插入 O(n log n)

用「比较次数」和「墙钟时间」两个角度验证 O(n) 紧界。先看比较次数（自定义计数比较器，最小堆，**降序输入**——这是逐个 push 的最坏输入）：

```
      n     build  push_desc     nlogn  push/n
   1000      1490       7987      9965    7.99
   2000      2989      17964     21931    8.98
   4000      5988      39917     47863    9.98
   8000     11987      87822    103726   10.98
  16000     23986     191631    223452   11.98
```

读数解读：`build`（heapify）的比较次数约等于 1.5n（23986/16000 ≈ 1.5），n 翻倍它就翻倍——**线性**；而 `push_desc`（逐个插入）的「每元素比较次数」`push/n` 从 7.99 一路涨到 11.98，每次 n 翻倍就增加约 1，正是 log₂n 的增长形态，总量贴着 n·log n 走。这直接坐实了「建堆 O(n) 严格快于逐个插入 O(n log n)」。

再看 heapify 的墙钟时间随规模的缩放：

```
n=  200000  heapify=    5.57 ms  ratio_vs_prev=  nan
n=  400000  heapify=   10.87 ms  ratio_vs_prev= 1.95
n=  800000  heapify=   21.44 ms  ratio_vs_prev= 1.97
n= 1600000  heapify=   43.79 ms  ratio_vs_prev= 2.04
```

读数解读：n 每翻一倍，heapify 时间也几乎恰好翻一倍（比值 ≈ 2.0），这是 O(n) 线性的典型指纹（若是 O(n log n)，比值会略大于 2 并随 n 缓慢上升）。两组实测互相印证 §6.3 的 O(n) 紧界结论。

#### 来源与时效
- 锚点：CLRS 4th ed (2022) §6.2 MAX-HEAPIFY——下沉伪码与 O(lg n) 界；§6.3 BUILD-MAX-HEAP——`for i=⌊n/2⌋ downto 1`、按高度加权求和得 O(n) 紧界与级数 ∑h/2^h=2（核实 2026-07-26）。
- 锚点：CPython 源码 `Lib/heapq.py` @tag v3.11.15——`heapify` 的 `for i in reversed(range(n//2)): _siftup(x,i)` 自底向上写法、头注「transforms list into a heap, in-place, in linear time」（核实 2026-07-26）。
- 锚点：Open Data Structures（Morin）§10.1——BinaryHeap 的 add/remove 与 O(log n) 调整（核实 2026-07-26）；CS61B sp24 Heaps & PQs 讲次给同样的 bottom-up build 直觉。

## 7.3 插入与上浮、取极值 — O(log n) 增删、O(1) 取顶

### 7.3.1 取顶（peek）：O(1)

取极值中「只看不删」的那一半——**取顶**（peek / find-min，最小堆取最小值；最大堆取最大值）——是最便宜的操作，因为根永远存在数组的第一个位置：

peek 单次代价 ： O(1)

在 0 起始表示里就是直接读 `heap[0]`（CPython `heapq` 的用法就是 `heap[0]`，注释写明「smallest item on the heap without popping it」）。这正是优先队列最常用的能力：反复问「当前优先级最高的是谁」而暂不取走。易错点：peek 前要判空，对空堆读根会越界。

### 7.3.2 插入与上浮（sift-up）：O(log n)

**插入**新元素分两步：先把它**追加到数组末尾**（也就是完全二叉树最后一层的下一个空位，这样自动维持了 7.1.1 的形状不变式），再让它**上浮**（sift-up / bubble-up）修复可能被破坏的堆序——把它与父结点比较，若比父更小（最小堆）就交换，一路向上直到不再违反堆序或到达根：

插入单次代价 ： O(log n)

因为上浮最多沿树高走一条路径，而树高是 ⌊lg n⌋。上浮是下沉的「反方向」孪生操作：下沉修复「结点比孩子大」，上浮修复「结点比父小」。心智模型：新来的员工先站到队伍最后，再凭本事逐级往上顶，顶到比他强的上级为止。

易错点：插入必须先追加到**末尾**再上浮，不能插到中间——插中间会破坏「完全二叉树连续无洞」的形状不变式，数组表示就失效了。

### 7.3.3 取极值（extract）：O(log n)

**取极值**（extract-min / extract-max，取走并返回根）是插入的逆操作，技巧在于如何在拿走根之后仍保持完全二叉树形状。标准做法三步：

1. 记下根（`heap[0]`，即要返回的极值）；
2. 把**数组最后一个元素**搬到根位置、并砍掉末尾（这一步维持了形状不变式——总是从最后一层最右端移除结点）；
3. 对新的根做一次**下沉**（7.2.1）修复堆序。

因为唯一耗时的第 3 步是一次下沉，故：

取极值单次代价 ： O(log n)

初学者常犯的错是「取走根后，把某个孩子直接提上来当根」——这会连锁破坏形状（在树中间留洞）。正确做法一定是「拿末尾元素补根、再下沉」，这样删除的物理位置永远是最后一层最右，形状天然保持。

本机实测（最小堆，`heapq`）验证「根是最小、反复取极值得到升序」：

```python
import heapq
data = [5,3,8,1,9,2,7]
h = data[:]; heapq.heapify(h)          # h[0] 是最小元
out = [heapq.heappop(h) for _ in range(len(h))]
```

```
input : [5, 3, 8, 1, 9, 2, 7]
heap  : [1, 3, 2, 5, 9, 8, 7]  top(min)= 1
popped: [1, 2, 3, 5, 7, 8, 9] sorted? True
```

读数解读：heapify 后 `heap[0]=1` 确为最小；反复 heappop 依次弹出 1,2,3,5,7,8,9，严格升序——这正是「每次取极值都拿到当前最小」的体现，也顺带说明了堆排序的原理（反复取极值 = 排好序，深挖归 L3-01）。注意中间数组 `[1,3,2,5,9,8,7]` 只是**部分有序**（满足堆序但整体不有序），别误以为 heapify 会把数组排好序。

综合 7.1–7.3，二叉堆的操作代价画像是：

peek = O(1)，insert = O(log n)，extract = O(log n)，build = O(n)

## 7.4 优先队列 ADT 与应用 — 改键/合并直觉

### 7.4.1 优先队列 ADT：接口与堆的关系

**优先队列**（priority queue，PQ）是一个抽象数据类型（ADT，见大主题1）：它维护一个「每个元素带有优先级键（key）」的集合，支持**插入元素**、**查询极值**（最高/最低优先级）、**取走极值**三个核心操作。CLRS §6.5 给出最大优先队列接口 INSERT / MAXIMUM / EXTRACT-MAX / INCREASE-KEY（最小优先队列对偶为 MINIMUM / EXTRACT-MIN / DECREASE-KEY）。

要分清「ADT」与「实现」：优先队列是**规范**（要什么操作、什么语义），二叉堆是它最常见的**实现**。用别的结构也能实现优先队列——无序数组（插入 O(1)、取极值 O(n)）、有序数组（插入 O(n)、取极值 O(1)）都行，但**二叉堆在插入和取极值之间取得了最好的平衡**（都 O(log n)），所以是默认选择。这也回应了大主题1「同一 ADT 多实现、各有代价画像」的主题。

它和普通队列（大主题3）的区别：普通队列按「到达顺序」FIFO 出队，优先队列按「优先级」出队——谁优先级最高谁先走，与到达先后无关。用最小堆时优先级值越小越先出，用最大堆时越大越先出。

### 7.4.2 改键（decrease-key / increase-key）直觉

**改键**是指修改队列中某个已有元素的优先级，并把堆修复到合法状态。方向决定用哪个修复操作：

- 最小堆里 **decrease-key**（把某键调小）——元素可能比父还小，用**上浮**修复；
- 最大堆里 **increase-key**（把某键调大）——同理用上浮修复；
- 反方向的改动（把键往「离根更远」的方向调）则用**下沉**修复。

改键单次代价 ： O(log n)（不含定位元素的开销）

改键是很多图算法的核心操作：Dijkstra 最短路和 Prim 最小生成树都在「找到某结点的更短距离/更小权重」时对它 decrease-key。易错点也在这里：**二叉堆本身不支持「按元素内容快速定位它在数组中的下标」**，若要 O(log n) 改键，必须**额外维护一张「元素 → 下标」的映射表**（handle / index map），否则光是找到那个元素就要 O(n)。CPython 的 `heapq` 就**不直接提供 decrease-key**；实践中常用的替身技巧是「懒删除」——把新优先级作为新条目 push 进去，弹出时跳过已失效的旧条目（这属应用层技巧，深挖归 L3-01）。

### 7.4.3 合并（meld / merge）直觉与堆的家族

**合并**是把两个优先队列并成一个。用普通二叉堆合并很笨——最直接的办法是把两堆元素倒进一个数组重新 build-heap，代价 O(n)：

二叉堆合并代价 ： O(n)

这催生了一族「可合并堆」（mergeable / meldable heaps）：**二项堆**（binomial heap，CLRS 旧版有专章）、**斐波那契堆**（Fibonacci heap）、**左偏堆/配对堆**等，它们通过更灵活的多树/指针结构，把合并做到 O(log n) 甚至更好。其中斐波那契堆更把 decrease-key 做到**均摊 O(1)**、把 Dijkstra/Prim 的理论复杂度进一步压低——但常数因子大、实现复杂，工程上二叉堆仍是默认。

初学者层面记住三点即可：其一，优先队列是 ADT、二叉堆是它的主力实现；其二，二叉堆的插入/取极值/改键都是 O(log n)、取顶 O(1)、建堆 O(n)，但**合并要 O(n)**；其三，当「频繁合并」或「海量 decrease-key」成为瓶颈时，才需要换成二项堆/斐波那契堆这类更高级的可合并堆。具体这些高级堆的机制与图算法应用属专家纵深，深挖归 L3-01 算法课，本报告只给到「有这么一族结构、解决什么问题」的直觉。
