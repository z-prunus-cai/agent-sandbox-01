## 4.1 哈希函数

### 4.1.1 哈希表要解决的问题与「直接寻址」的起点

哈希表（hash table）是一种用来实现字典 ADT（动态集合的 INSERT / SEARCH / DELETE）的数据结构，目标是让这三个操作的**平均**时间达到 O(1)。它的出发点是「直接寻址表」（direct-address table）：如果键都来自一个不太大的整数全集 U = {0, 1, …, m−1}，就开一个长度 m 的数组 T，把键 k 的数据直接放在 T[k]，查找就是一次下标访问，O(1)。

直接寻址的致命问题是空间：如果全集 U 很大（比如所有可能的字符串、所有 64 位整数），却只实际存储少量键，那么开 |U| 大的数组既浪费又不可能。哈希表的核心思想就是：不再用键本身当下标，而是用一个**哈希函数**把巨大的全集 U「压缩」到一个大小适中的槽数组（slot / bucket array）上。

### 4.1.2 哈希函数的定义与「均匀分散」的目标

哈希函数（hash function）是一个从键全集到槽下标的映射：

h : U → {0, 1, …, m−1}

其中 m 是槽的数量（表长）。键 k 被放到槽 h(k)。一个好的哈希函数应当把键**尽可能均匀地**散布到 m 个槽上，让每个槽平均只落到 n/m 个键。这个比值是全章反复出现的核心量，叫负载因子（load factor）：

α = n / m

其中 n 是已存元素数。直觉上，只要 h 把键摊得足够均匀，每个槽里的键数就接近 α，操作代价就接近常数。

初学者要建立的第一个直觉是：哈希函数必然「多对一」（|U| ≫ m），所以**不同的键映射到同一个槽是不可避免的**——这叫冲突（collision），是 4.2、4.3 两节要处理的核心难题，而不是可以靠「设计得好」完全消除的意外。哈希函数只能让冲突尽量少、尽量均匀，不能让它归零。

CLRS 4th ed 在此处特别强调它所依赖的理想假设叫**独立均匀哈希**（independent uniform hashing）：假想每个键被独立、等概率地散到 m 个槽之一。这是 4th 版相对旧版的一个术语与措辞调整（旧版惯用「简单均匀哈希 simple uniform hashing」）——含义相近但 4th 版把「哈希值相互独立」这一点讲得更明确，用于后续概率分析。真实哈希函数只能逼近这个假设，不能真正做到。

### 4.1.3 除留余数法（division method）

最简单的整数哈希函数是除留余数法，用键除以表长取余数：

h(k) = k mod m

它只需一次取模，非常快。关键的易错点在于 **m 的选取**：应避免取 m 为 2 的幂，因为 k mod 2^p 只等于 k 的最低 p 个二进制位，完全忽略了高位信息——如果输入键的低位有规律（例如都是偶数、或都以相同后缀结尾），就会严重扎堆。CLRS 的经验法则是取一个**离 2 的幂较远的质数**作为 m。

若键是 `1200, 1201, 1202, …`，取 m = 100 = 2²·5²（含 2 的幂因子且是 100 的倍数敏感），末两位直接决定槽，规律输入易扎堆；改取 m = 101（质数）就能把这些键打散到不同槽。

### 4.1.4 乘法法（multiplication method）

乘法法先用键乘以一个 0 到 1 之间的常数 A，取小数部分，再乘以 m 取整：

h(k) = ⌊ m · (k·A mod 1) ⌋

其中 `k·A mod 1` 表示 k·A 的小数部分。它的好处是**对 m 的取值不敏感**，因此 m 可以放心取 2 的幂（便于用位运算实现）。CLRS 沿用 Knuth 的建议，常取

A ≈ (√5 − 1) / 2 ≈ 0.6180339887…

（黄金比例的小数部分），经验上散布效果好。直觉是：乘以一个无理数般的常数再取小数部分，能把等差的键序列「旋转」到分布均匀的位置，避免除留余数法对低位规律的敏感。

### 4.1.5 全域哈希（universal hashing）

前两种方法都是**固定**的函数，因此对任何一个固定 h，总存在一批「坏输入」全部撞到同一个槽（4.5 会看到攻击者正是利用这一点）。全域哈希的思路是：不用固定函数，而是在运行时**从一族哈希函数中随机挑一个**，使得任意两个不同的键碰撞的概率不超过 1/m。满足这个条件的函数族称为「全域的」（universal）。

CLRS 给出的一个经典全域族基于取模运算：先选一个比全集还大的质数 p，再随机选 a、b：

h_{a,b}(k) = ((a·k + b) mod p) mod m

其中 a ∈ {1, 2, …, p−1}，b ∈ {0, 1, …, p−1} 都在建表时随机抽取。

随机性从**输入**移到了**算法**。攻击者即便知道用的是这个族，也不知道这次具体抽中的 a、b，因而无法预先构造必然扎堆的输入——碰撞概率对任意输入都有 ≤ 1/m 的保证。这正是抵御 4.5 中对抗性攻击的理论武器。CS61B 在工程层面表达同一诉求：要求 `hashCode` 把键「充分打散」并配合表长做二次混合，虽不叫全域哈希，但目标一致——让常见键分布不扎堆。

## 4.2 链地址法

### 4.2.1 用链表挂住每个槽里的所有键

链地址法（chaining，又译「拉链法 / 分离链接 separate chaining」）解决冲突的办法很直接：**每个槽不再只存一个元素，而是存一条链表**，所有哈希到该槽的键都挂在这条链表上。

- INSERT：算出 h(k)，把元素插到对应链表（通常头插，O(1)）；
- SEARCH：算出 h(k)，沿该槽的链表线性扫描；
- DELETE：找到后从链表中摘除。

于是「冲突」被就地化解为「同一条链表上的多个结点」，永远不会因为槽被占而放不下——只要内存够，链地址法能装下任意多元素（α 可以大于 1）。

### 4.2.2 为什么平均是 O(1)：负载因子决定链长

在独立均匀哈希假设下，每条链表的期望长度就是负载因子 α = n/m。查找一个键时，除了一次 O(1) 的哈希计算，还要扫描它所在的链表。CLRS 的结论是：链地址法下，查找（成功或不成功）的期望时间为

Θ(1 + α)

其中 1 是计算哈希 + 定位槽的固定成本，α 是扫描链表的期望长度。

这条式子是理解哈希表「为什么快」的钥匙：**只要让 α 保持为一个常数上界**（例如始终 α ≤ 某个常数，靠 4.4 的再散列维持），那么 Θ(1+α) 就是 Θ(1)，三种操作都是平均常数时间。反过来，如果放任 n 无限增长而不扩容，α 会线性增大，链表越来越长，操作退化到 O(n)（正是 4.5 的一种情形）。

初学者最常见的误解是把「哈希表 O(1)」当成无条件的铁律。正确的表述是：**平均 O(1) 是有前提的**——需要好的哈希函数（均匀）＋ 控制住负载因子（扩容）。二者缺一，O(1) 就不成立。

### 4.2.3 最小例子

设 m = 4，`h(k) = k mod 4`，依次插入 4、8、5、12：

```
槽0: 4 -> 8 -> 12     (4,8,12 都 mod 4 = 0，挂成一条链)
槽1: 5
槽2:
槽3:
```

查 12：算 h(12)=0，到槽 0 的链表从头扫 4→8→12，三步命中。可见链变长时查找变慢，这就是要控制 α 的直接原因。

链地址法的优点是实现简单、对 α 的容忍度高（α>1 仍能工作）、删除干净利落；代价是每个结点要额外存指针（空间开销），且链表结点分散在堆上，缓存不友好（呼应大主题2 的「分散布局代价」）。

- 锚点：Pat Morin《Open Data Structures》§5.1「ChainedHashTable」——每槽一链表、期望链长 α 的等价论述。核实 2026-07-26。

## 4.3 开放定址法

### 4.3.1 不用链表，冲突了就往后找空槽

开放定址法（open addressing，又称「闭散列 closed hashing」）走另一条路：**所有元素都直接存在槽数组里，不用任何链表指针**。冲突发生时，就按一个确定的「探测序列」（probe sequence）依次试探后续的槽，直到找到一个空槽放进去。

因为元素只能放在数组内部，所以必然有 n ≤ m，即负载因子 α = n/m < 1（表永远填不满还得留余量）。哈希函数因此扩展为带「探测次数 i」的双参数形式：

h(k, i) : U × {0, 1, …, m−1} → {0, 1, …, m−1}

对固定 k，序列 ⟨h(k,0), h(k,1), …, h(k,m−1)⟩ 应当是 {0,…,m−1} 的一个排列，保证探完所有槽。SEARCH 沿同一序列探测：命中键则成功，遇到空槽则判定不存在。

### 4.3.2 线性探测（linear probing）

最简单的探测方式是「撞了就看下一个槽」：

h(k, i) = (h′(k) + i) mod m

其中 h′ 是一个普通（辅助）哈希函数。实现极简单、缓存友好（连续访问相邻槽）。它的著名缺陷是**一次聚集（primary clustering）**：一旦形成一段连续的占用槽，任何哈希落进这段区间的新键都会加长它，聚集块越滚越大，探测越来越长。

### 4.3.3 二次探测（quadratic probing）

二次探测让探测步长随 i 二次增长，以打散连续聚集：

h(k, i) = (h′(k) + c₁·i + c₂·i²) mod m

其中 c₁、c₂ 是常数（需与 m 配合选取，才能让探测序列覆盖足够多的槽）。它缓解了一次聚集，但引入**二次聚集（secondary clustering）**：两个 h′(k) 相同的键，其整条探测序列完全一样，仍会互相绊住。

### 4.3.4 双重哈希（double hashing）

双重哈希用第二个哈希函数决定探测步长，是开放定址中散布最接近理想的方案：

h(k, i) = (h₁(k) + i · h₂(k)) mod m

关键点是 **h₂(k) 必须与 m 互质**（例如取 m 为质数、或 m 为 2 的幂而 h₂ 恒为奇数），才能保证 i 从 0 变到 m−1 时探遍所有槽。它的好处是不同键即便首槽相同，只要 h₂ 不同，探测序列就不同，从而同时避开一次和二次聚集。

### 4.3.5 探测代价、删除陷阱与复杂度界

在独立均匀哈希假设下（把每个键的探测序列理想化为 {0,…,m−1} 的均匀随机排列），CLRS 给出的界为：

不成功查找的期望探测次数 ≤ 1 / (1 − α)

成功查找的期望探测次数 ≤ (1/α) · ln( 1 / (1 − α) )

（对应 CLRS 4th ed 的 Theorem 11.6 与 Theorem 11.8。）直觉：α=0.5 时不成功查找约 2 次探测；α=0.9 时飙到约 10 次；α→1 时趋于无穷——这解释了为什么开放定址表必须在 α 远小于 1 时就扩容（4.4）。

一个初学者极易踩的坑是**删除**：开放定址下不能简单把槽清空，否则会切断某条探测链，让本应能找到的键被误判为「不存在」。标准做法是放一个特殊的「已删除（DELETED / tombstone 墓碑）」标记：查找时把它当作「占用、继续探测」，插入时把它当作「可覆盖的空位」。墓碑积累会拖慢查找，这也是再散列的动机之一。

省掉了所有链表指针，空间更紧凑、缓存更友好；但受限于 α<1、对哈希函数质量更敏感、删除更麻烦。

## 4.4 负载因子与再散列

### 4.4.1 负载因子是「该不该扩容」的仪表盘

负载因子 α = n/m 衡量表的拥挤程度。4.2、4.3 已表明操作代价随 α 上升而恶化（链地址 Θ(1+α)、开放定址随 1/(1−α) 爆炸）。因此哈希表的通用策略是：**监控 α，一旦超过某个阈值就扩容并重新哈希**，把 α 拉回低位。这个「换更大的表、把所有键重新算哈希搬过去」的过程叫再散列 / 重哈希（rehashing）。

再散列必须重算哈希、逐个搬迁，因为槽下标 h(k) 依赖表长 m，m 变了下标全部作废。一次再散列的代价是 O(n)（当前元素数），看似昂贵，但因为每次都把表**成倍**放大（类比大主题2 的动态数组倍增扩容），扩容频率呈几何下降，均摊到每次插入仍是 O(1)——这正是大主题1「均摊分析」在哈希表上的直接应用。

阈值的选择是空间与时间的权衡：阈值定得低（如 0.5），操作快但浪费空间；定得高（如 0.9），省空间但操作变慢。链地址法容忍更高的 α（可>1），开放定址法必须在 α 明显小于 1 时就扩容。

### 4.4.2 CPython 的紧凑 dict：实现层的一手取证

Python 的 `dict` 是开放定址哈希表，且自 3.6 起采用「紧凑字典」（compact dict）布局。关键实现常量取自 `Objects/dictobject.c`（v3.11.15 标签）：

```c
#define PyDict_MINSIZE 8                       /* 表的最小容量（槽数） */
#define USABLE_FRACTION(n) (((n) << 1)/3)      /* 可用槽 = 容量的 2/3 */
#define GROWTH_RATE(d) ((d)->ma_used*3)        /* 扩容目标 ≈ 已用数 x3 */
#define PERTURB_SHIFT 5                        /* 探测扰动位移 */
```

从这三行可读出 CPython 的负载因子政策：当已用槽数达到容量的 2/3（`USABLE_FRACTION` = 2n/3）时触发再散列；扩容时把新容量取为「能容纳 `已用数 × 3` 的最小 2 的幂」（`GROWTH_RATE` 配合 `calculate_log2_keysize` 向上取到 2 的幂）。源码注释明确说明这样做的效果是「无删除地增长时，字典大小翻倍；当删除与插入相当时留出更多余量」。表长恒为 2 的幂，因此 CPython 用**位与**取槽下标而非取模：

i = hash(k) & (m − 1)

冲突时用带扰动的探测序列（把哈希高位逐步搅进来，比纯线性探测更能打散聚集）：

perturb ← hash;  i ← (5·i + perturb + 1) mod m;  perturb ← perturb >> 5

### 4.4.3 紧凑 dict 的两层结构（规范通式 vs 实现细节的分歧点）

教材（CLRS §11.4）讲的开放定址通式是「一个槽数组，键直接住在槽里」。CPython 的紧凑 dict 与这个通式有一个显著的**实现层差异**，值得点明：它把表拆成**两部分**——一个只存「索引」的稀疏数组 `dk_indices`（开放定址真正发生在这里，存的是指向条目数组的下标，可按规模用 int8/int16/int32/int64 压缩），和一个**按插入顺序紧密排列**的条目数组 `dk_entries`（存实际的键值对）。

这层间接带来两个教材通式看不到的性质：其一，键值对连续存放，内存更省、遍历缓存友好；其二，**dict 从此保持插入顺序**（Python 3.7 起成为语言规范保证的行为）。所以「Python dict 有序」并不是哈希表的普遍性质，而是这套紧凑布局的副产品——初学者不要把它误当成所有哈希表都成立的通则。

本机观测（Python 3.11.15）逐个插入整数、记录 `sys.getsizeof(d)` 发生跳变的时机，可看到再散列点与容量约按 2 倍增长、触发点约在 2/3 负载处，与上面两个宏一致：

```
resize points (len_after_insert, sizeof_bytes):
[(1,224),(6,352),(11,632),(22,1168),(43,2264),(86,4688),(171,9304)]
```

## 4.5 最坏 O(n) 退化

### 4.5.1 平均 O(1) 的另一面：最坏仍是 O(n)

哈希表的「O(1)」永远是**平均 / 期望**意义下的；它的**最坏情况**始终是 O(n)。退化发生在所有键（或大量键）都哈希到同一个槽 / 同一条探测链时：链地址法退化成一条长度 n 的链表，开放定址法退化成一次次遍历几乎整张表。此时单次查找 O(n)，连续插入 n 个这样的键总代价 O(n²)。

这不是实现 bug，而是哈希表的固有性质：对任何**固定**的哈希函数 h，因为 |U|≫m，总存在至少 ⌈|U|/m⌉ 个键映射到同一个槽——攻击者只要知道 h，就能挑出全部撞到一起的键，把表打回线性。

### 4.5.2 对抗性输入与哈希洪水攻击

当哈希表用于处理**外部不可信输入**（如 Web 服务器把请求参数塞进字典），攻击者可故意构造大量碰撞键，使服务端在插入/查找上耗尽 CPU，这类拒绝服务称为「哈希洪水攻击」（hash-flooding / algorithmic complexity attack）。这是 4.1.5 全域哈希与「哈希随机化」存在的现实理由：把哈希函数在运行时随机化（Python 默认对 `str`/`bytes` 启用哈希随机化 `PYTHONHASHSEED`，每次进程用不同盐值），攻击者无法预知本次的哈希映射，也就无法离线构造必中碰撞的输入。

### 4.5.3 本机验证：制造碰撞看退化

用一个 `__hash__` 恒返回常数、`__eq__` 按真实值比较的类，强制所有键落进同一探测链，与正常键对比插入 n 个的耗时（Python 3.11.15）：

```
n= 1000  bad(all-collide)=   25.80ms  good=  0.196ms  ratio=   131.4x
n= 2000  bad(all-collide)=  103.65ms  good=  0.416ms  ratio=   249.1x
n= 4000  bad(all-collide)=  417.48ms  good=  0.902ms  ratio=   462.6x
```

现象与理论吻合：全碰撞情形下 n 翻倍、耗时约 ×4（∼O(n²) 累积，即单次 ∼O(n)），慢于正常情形的倍数随 n 线性拉大；正常键则近似线性、单次近似 O(1)。（复现脚本仅存 scratchpad，不入库。）

### 4.5.4 缓解手段与关联

要点归纳（都在前几节出现过，此处收束）：其一，用**好的、随机化的哈希函数**（全域哈希 / 运行时加盐），把「对固定 h 的坏输入」变成攻击者不可预测的目标；其二，**控制负载因子**（4.4 再散列），防止因过载而非碰撞导致的退化；其三，把桶内结构从链表升级为**平衡树**——这是工程上的常见加固（例如 Java 8 HashMap 在单桶超过阈值时把链表转红黑树，使单桶最坏从 O(n) 降到 O(log n)），把哈希表和大主题5/6 的搜索树联系起来。作为入门，记住结论即可：哈希表的 O(1) 是「好哈希 + 控负载」条件下的期望值，最坏情况 O(n) 永远存在，处理不可信输入时必须正视它。
