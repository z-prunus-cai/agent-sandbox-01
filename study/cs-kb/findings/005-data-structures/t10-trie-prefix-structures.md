## 10.1 前缀树结构 — 边标字符、结点表示与终止标记

### 10.1.1 核心思想：键写在「路径」上，而不是写在结点里

Trie（前缀树）是一种**用键的字符序列来组织的树**：从根出发，每往下走一条边就「消费」键里的一个字符，一条从根到某结点的路径**拼起来就是一个字符串**。因此一个键并不存在某个单一结点里，而是由「走到那里的整条路径」隐式表示的。这与 BST（大主题5）、哈希表（大主题4）把**整个键**塞进一个结点/桶里，是根本不同的组织方式。

它最关键的一条性质是**共享前缀**：所有拥有相同前缀的键，会**共用**从根开始的那一段路径。例如 `cat`、`car`、`card` 三个词共享 `c→a` 这一段，到 `a` 之后才分叉。这既省了重复存储，也让「找出所有以某前缀开头的键」变得天然高效——这正是 Trie 相对哈希表的独门优势（哈希表打散了键，无法回答前缀问题）。

心智模型：把 Trie 想成一本**字典的目录结构**——先翻到 c 开头那一叠，再翻 ca，再在 ca 底下分出 cat / car / card。每一层都是「按下一个字母再细分一次」。

### 10.1.2 结点表示：R 路数组 vs 映射（dict/链）

一个 Trie 结点要能「按下一个字符找到对应的孩子」。有两种主流表示：

其一是 **R 路 Trie（R-way trie）**：每个结点持有一个长度为 R 的**孩子指针数组**，下标直接用字符编码（如 `children['c'-'a']`）。查孩子是一次 O(1) 数组寻址，最快；代价是**每个结点都固定占 R 个指针槽**，绝大多数是空的，空间浪费大。Sedgewick §5.2 的 `TrieST` 用的就是这种 `Node[] next = new Node[R]`。

其二是**映射表示**：每个结点用一个哈希表/字典（Python 里就是 `dict`）或一条有序链表，只存**真正出现过的**孩子字符 → 孩子结点。空间随实际分叉数走、省得多；查孩子的常数因子略大（一次 dict 查找而非数组寻址）。CS61B 的 `TrieSet` 常用 `Map<Character, Node>` 表示，Python 教学里普遍用「dict-of-dict」。

用 dict-of-dict 表示，一个最小 Trie 长这样（`$` 是下面 10.1.3 要讲的终止标记）：

```python
# 插入 "cat","car","card" 后的结构（简化示意）
{'c': {'a': {'t': {'$': True},
             'r': {'$': True,
                   'd': {'$': True}}}}}
```

初学者易错点：**Trie 的高度只取决于最长键的长度 L，与键的个数 n 无关**。装 100 万个长度 ≤ 20 的英文词，Trie 也只有 ≤ 20 层高。这与 BST「n 个键至少 log n 层、退化时 n 层」完全不同——Trie 把「树高」从「键数量」解耦成了「键长度」，这是它所有 O(L) 复杂度的来源。

### 10.1.3 终止标记：为什么必须区分「是一个词」和「只是别人的前缀」

只靠「路径能走通」不足以判断一个字符串是不是被存进来的键，因为**一个键可能恰好是另一个键的前缀**。存了 `card` 之后，路径 `c→a→r` 一定能走通，但 `car` 到底存没存过？必须有额外信息。

解决办法是给每个结点加一个**布尔终止标记**（is-word / end-of-word flag，常记作结点的 `isKey` 字段，dict-of-dict 里用一个特殊键 `$` / `""` 表示）：**只有走到路径终点且该结点的终止标记为真，才算命中一个真正存过的键**。

存了 `card` 但没存 `car`：路径 c→a→r 走得通，但 r 结点终止标记为假 ⟹ search("car") 为假

这是初学者写 Trie 最容易漏的一点：忘了终止标记，就会把「任意前缀」误判成「已存的词」，`card` 一存进去，`c`、`ca`、`car` 全被错误地当成命中。终止标记就是用来把「这里是一个词的结尾」和「这里只是通往更长词的中转站」区分开。

## 10.2 插入/查找/前缀匹配 — 按字符逐层下降

### 10.2.1 查找（search）：逐字符下降 + 检查终止标记

**查找**一个键 w 的过程是：从根出发，按 w 的字符一个一个往下走——第 i 个字符对应一步「取当前结点标 `w[i]` 的那个孩子」。若中途某个字符没有对应孩子，立即返回「不存在」；若走完全部字符，再看终点结点的**终止标记**（10.1.3）是否为真。

查找单次代价 ： O(L)

其中 L 是被查键的长度。注意这个界**不含 n**（键的总数）——无论 Trie 里有 10 个还是 1000 万个键，查一个长度为 L 的词都只走 L 步。这正是 Trie 相对 BST（O(L·log n)，因为每层比较还要逐字符比字符串）的优势。用映射表示时每步是一次 dict 查找、R 路数组时是一次寻址，都摊到 O(1)，故总代价 O(L)。

### 10.2.2 插入（insert）：走到哪建到哪，末端置终止标记

**插入**键 w 与查找同构，区别在于「走不通时不是失败、而是新建结点」：沿 w 的字符逐层下降，缺哪个孩子就**新建**一个空结点接上去，走完最后一个字符后把终点结点的**终止标记置真**。

插入单次代价 ： O(L)

至多新建 L 个结点、走 L 步。共享前缀在这里自动发生：插 `card` 时若 `car` 的路径已在，前三步直接复用、只新建 `d` 一个结点。易错点：插入结束别忘了置终止标记，否则等于「铺了路却没声明这是一个词」，后续 search 会漏掉它。

### 10.2.3 前缀匹配（startsWith / prefix query）：Trie 的独门能力

**前缀匹配**问的是「有没有任何已存的键以 pfx 开头」，只需沿 pfx 逐字符下降、**走得通就返回真**——不看终止标记（因为我们要的是「有词以此为前缀」，而不是「pfx 自己是不是词」）。

前缀查询单次代价 ： O(L_pfx)

更进一步，「列出所有以 pfx 开头的键」= 先走到 pfx 对应的结点，再对它**子树做一次遍历（DFS/BFS，见大主题5、9）收集所有终止标记为真的路径**。这类「按前缀检索/自动补全」是 Trie 的杀手锏，哈希表根本做不到（哈希打散了键，无从枚举前缀邻居）。

本机实测（dict-of-dict Trie，插入 `cat/car/card/dog`）：

```
search cat  : True
search ca   : False
prefix ca   : True
prefix ba   : False
search card : True
```

读数解读：`search("ca")` 为 **False**——路径 c→a 走得通，但 `a` 结点终止标记为假，`ca` 从没作为词存过，正确地不命中；而 `prefix("ca")` 为 **True**——确实有词（cat/car/card）以 ca 开头。这一对结果精确演示了 10.1.3「终止标记区分词与前缀」在操作层面的体现：search 看终止标记，prefix 不看。`prefix("ba")` 为 False 是因为第一步 b 就没有孩子、当即失败。

初学者常见混淆：把 `search` 和 `startsWith` 写成同一个函数。二者的走法完全一样，唯一差别是**终点要不要检查终止标记**——search 要、startsWith 不要。分不清就会出现「`ca` 被判成已存的词」这类 bug。

## 10.3 基数思想与压缩 Trie — Radix/Patricia 合并单链路径

### 10.3.1 标准 Trie 的空间痛点与「压缩单链路径」的动机

标准 Trie 的软肋是**空间**：每个字符都占一个结点，键很长、分叉又少时会拉出一大串「只有一个孩子、自己也不是词尾」的**单链结点**，每个结点却只贡献一个字符的信息。一个孤零零的长词 `internationalization`（21 字符）在标准 Trie 里要占一整条 21 个结点的链，纯属浪费。

**压缩 Trie（compressed trie）** 也叫**基数树（radix tree）/ Patricia 树**（PATRICIA = Practical Algorithm To Retrieve Information Coded In Alphanumeric，Morrison 1968），核心优化只有一句话：**把「只有一个孩子且自身非词尾」的连续结点链合并成一条边，边上标一个字符串（而非单个字符）**。分叉点（有 ≥2 个孩子）和词尾结点保留，中间的单链塌缩掉。

这就是「基数（radix）思想」的一种体现：不再死板地「一次只看一个字符」，而是**一次跳过一整段没有分歧的公共子串**，只在真正需要做分支决策的地方才停下来建结点。

### 10.3.2 压缩前后结点数对比（本机实测）

对同一组键 `cat/car/card/dog` 分别数标准 Trie 与压缩 Trie 的结点数：

```
uncompressed nodes (incl root): 9
compressed nodes (hand-derived): 6
```

压缩后的结构（手工推演）是：

```
root
 ├─"ca"─┬─"t"·           (cat)
 │      └─"r"·─"d"·      (car 词尾; card)
 └─"dog"·                (dog)
```

读数解读：标准 Trie 的 9 个结点里，`c→a` 这段是纯单链（root 之后到分叉点前），被压成一条标 `"ca"` 的边，省下一个结点；`dog` 三个结点压成一条 `"dog"` 边，省两个——合计 9 降到 6。压缩幅度在「长键、少分叉」时最夸张：

```
single long word -> uncompressed nodes: 21  compressed nodes: 2
```

单个 21 字符的词，标准 Trie 要 21 个结点（root + 20 字符链），压缩 Trie 只需 2 个（root + 一条标着整词的边）。这直观说明了压缩为何值得——它把空间从「与总字符数成正比」降到「与**键数量和分叉数**成正比」。

关键点：压缩**不改变**查找/插入的时间复杂度量级——仍是 O(L)（沿边比对字符串时总字符数还是 L），省的是**结点数量（空间与指针跳转次数）**。这是初学者容易误解的地方：压缩 Trie 更快主要是因为**更少的指针跳转、更好的缓存局部性**，渐近时间界与标准 Trie 同阶。

### 10.3.3 变体谱系与和其它结构的辨析

沿「基数思想」这条线，有一族相关结构，初学者知道名字与定位即可：

- **Radix tree / 压缩 Trie**：上面讲的「合并单链、边标字符串」的通用版本。
- **Patricia trie**：Morrison 1968 的经典特例，最初定义在**二进制位**上（R=2），每个内部结点还额外记「下一个要检查的是第几位」以便跳过公共位。Open Data Structures §13.1 的 **BinaryTrie** 就是这条「位级 radix」路线的教学版。
- **Ternary Search Tree（TST，三向搜索树）**：Sedgewick §5.2 给出的另一条省空间路线——每个结点存一个字符和左/中/右三个孩子，用「BST 式的字符比较」代替「R 路数组」，在大字母表下比 R 路 Trie 省得多。

和已学结构的横向辨析（回应大主题4、5）：

- **vs 哈希表**：哈希表整键查找均摊 O(1)、但**不支持前缀/有序遍历**、且要算完整哈希（也是 O(L)）；Trie 保证最坏 O(L)、天然支持前缀查询与按字典序遍历，代价是空间和常数因子。
- **vs BST**：BST 每层比较一个**完整键**（字符串比较本身 O(L)），n 个键需 O(L·log n)；Trie 用路径共享把它降到与 n 无关的 O(L)。

初学者层面记住三点即可：其一，Trie 的时间复杂度由**键长 L**决定、与键数 n 解耦；其二，压缩（radix/Patricia）省的是**空间/结点数**、不改时间量级；其三，需要**前缀检索/自动补全/按字典序**时选 Trie，只需**整键精确查找**时哈希表通常更省。更纵深的字符串索引（后缀树/后缀数组、Aho-Corasick 多模式匹配）属专家纵深，深挖归算法课，本报告只给到「有这么一族结构、解决什么问题」的直觉。
