这一份是整个"容器与云原生"主题的地基：先把"容器到底是什么、和虚拟机差在哪、隔离到底靠什么"讲清楚，后面 namespaces、cgroups、镜像、运行时、Kubernetes 才有落点。核心的一句心智模型是：虚拟机是"在一台机器里再造一整台机器"，而容器只是"一个被限制了视野和资源配额的普通进程"。这里要反复点明一个机制根衔接——容器用来隔离的 namespaces 和 cgroups 并不是容器发明的，它们本就是 Linux 内核提供的资源隔离原语（属操作系统课 L4-01 的范畴），本课讲的是如何把这些内核原语工程化地组装成"容器"这个产品。

## 13-1.1 hypervisor 整机虚拟化 vs 共享内核

### 13-1.1.1 虚拟机与 hypervisor：在硬件之上再虚拟出整台机器

虚拟机（VM）是用软件模拟出的一整台计算机。它有自己的虚拟 CPU、虚拟内存、虚拟磁盘和虚拟网卡，并且在这套虚拟硬件之上安装并运行一个完整的、独立的操作系统内核（称为 guest OS，客户机操作系统）。负责创建和管理这些虚拟机、在多台虚拟机之间分配真实硬件资源的那层软件，叫 hypervisor（虚拟机监控器，也叫 VMM，Virtual Machine Monitor）。

要建立直觉，可以把物理服务器想象成一栋楼。虚拟机相当于在楼里隔出几套完全独立的公寓，每套公寓自带厨房、卫生间、水电表——对应每台 VM 自带一套完整的操作系统内核。hypervisor 就是物业，负责把整栋楼的水电（真实的 CPU、内存）按套分配下去，并保证一套公寓里发生的事不会直接影响另一套。

hypervisor 通常分两类，初学者知道这个二分即可：

Type 1（裸机型 / bare-metal）：直接跑在物理硬件之上，如 VMware ESXi、Microsoft Hyper-V、Xen；Linux 上的 KVM 是把内核本身变成 hypervisor 的内核模块，通常也归入这一类。

Type 2（宿主型 / hosted）：作为一个普通应用跑在已有操作系统之上，如 VirtualBox、VMware Workstation。

现代 VM 之所以性能可用，靠的是 CPU 的硬件辅助虚拟化（Intel VT-x、AMD-V）和内存的二级地址翻译（Intel EPT、AMD NPT），让 guest 内核的大部分指令能近乎原生地直接在物理 CPU 上跑，而不是逐条软件模拟。这也是为什么"整机虚拟化"如今开销可以做得不算大，但仍存在——每台 VM 都要为自己那份完整 guest 内核和虚拟硬件付出内存与启动时间成本。

### 13-1.1.2 容器：共享宿主内核的进程级隔离

容器走的是完全不同的路线：它不虚拟硬件、也不带自己的内核，而是让若干进程直接跑在宿主机（host）那一个内核之上，只不过内核给这些进程套上了"看不到别人、也用不了超额资源"的限制。换句话说，一台机器上无论跑多少个容器，内核只有一个，就是宿主机的内核，所有容器共享它。

如果说 VM 是"隔出独立公寓、各自装修水电"，那么容器更像是"同一间大开间里用屏风隔出几个工位"。每个工位的人看不到别的工位（视图隔离），也被规定了只能用多少电、多少桌面空间（资源隔离），但他们呼吸的是同一间屋子的空气、用的是同一套供电系统——这套共享的"空气和供电"就是那唯一的宿主内核。

这里是本课最重要的机制根衔接：容器实现"看不到别人"靠的是 Linux 的 namespaces（命名空间，做视图隔离），实现"用不了超额资源"靠的是 cgroups（control groups，做资源限额）。这两样都是操作系统内核（L4-01）早就提供的原语，并非容器技术专属；容器只是把它们和文件系统、进程创建组合起来用。因为共享同一个内核，容器省掉了整份 guest OS 的开销，所以启动快（毫秒级）、内存占用小、单机能塞下的数量远多于 VM——代价是隔离强度不如 VM，这个权衡是后面 13-1.3、13-1.4 的主线。

### 13-1.1.3 两条路线的直接对比

把两者放到同一张对照表里，初学者最该记住的差异集中在"有没有独立内核"这一条根因上，其余差异几乎都由它派生：

在虚拟机一侧，每台 VM 有一个独立 guest 内核，隔离边界由 hypervisor 加硬件强制，启动以秒计，每台要为完整 OS 付出百 MB 级以上内存，单机密度低（几台到几十台），并且可以跑与宿主不同的操作系统（如 Linux 宿主上跑 Windows guest）。

在容器一侧，所有容器共享宿主的那一个内核，隔离边界由内核的 namespaces/cgroups 提供，启动以毫秒计，开销接近裸进程，单机密度高（可上百上千），但只能跑与宿主同类内核的负载（Linux 容器需要 Linux 内核）。

那条"只能跑同类内核"的限制常被初学者忽略：Windows 容器需要 Windows 内核，Linux 容器需要 Linux 内核；在 macOS/Windows 上用 Docker 跑 Linux 容器，其实底层偷偷起了一台 Linux 轻量虚拟机来提供那个共享内核——这恰恰反证了"容器必须有一个和自己同类的内核可共享"。

## 13-1.2 容器三要素：进程 + namespaces + cgroups

### 13-1.2.1 一句话拆解：容器 = 受限视图 + 受限资源的进程

站在内核视角，一个"容器"并不是一种特殊的对象，它本质上仍是一个（或一组）普通进程。它之所以像个"独立的小机器"，是因为在创建这个进程时给它叠加了三样东西：它本身是一个进程（有 PID、有内存、能被调度，和你平时 `ps` 看到的进程没有本质区别）；用 namespaces 限制它"能看到什么"（视图隔离）；用 cgroups 限制它"能用多少"（资源隔离）。这三样组合起来，就构成了一个基本容器。


namespaces 管"看得见什么"，cgroups 管"用得了多少"。

前者决定这个进程眼里的世界有多大——它能看到哪些进程、哪些网络接口、哪些挂载点；后者决定这个进程能吃掉多少真实资源——多少 CPU 时间、多少内存、多少进程数。缺了 namespaces，进程能看到并干扰宿主上的一切；缺了 cgroups，一个进程能把整机 CPU 或内存吃光拖垮邻居。两者一起上，才既"隔开视野"又"隔开资源"。

### 13-1.2.2 第一要素：它终究是一个进程

强调"容器就是进程"这一点，是为了打破初学者最常见的误解——以为容器里"开机"了一个微型系统。实际上，当你启动一个容器，宿主内核只是像 fork/exec 任何普通程序那样创建了进程；容器里那个 PID 为 1 的进程，就是你指定的启动命令本身，而不是什么 init 系统必须存在的产物。

本机可以直接观察到这一点。用 unshare 创建一个新的 PID 命名空间并 fork 出子进程，在里面看到的进程视图被清空、启动的 shell 成了 1 号进程：

unshare --pid --mount --fork --mount-proc sh -c 'echo "in-ns PID: $$"; ps -e'

在本基线（Linux 6.18.5、util-linux 2.39.3）上真实输出为容器内 shell 的 `$$` 是 1，`ps -e` 只列出该 ns 内的 sh、ps、head 三个进程；而同一时刻宿主上 `ps -e | wc -l` 有 81 行。这说明容器内"只有自己"的错觉，纯粹是命名空间对进程视图做了裁剪，底下还是宿主内核在统一调度所有这些进程。

### 13-1.2.3 第二要素：namespaces 做视图隔离

namespaces 让不同进程对某类全局系统资源看到彼此独立的"实例"。Linux 目前提供八种命名空间，各管一类视图：pid（进程号视图）、net（网络栈：接口/路由/端口）、mnt（挂载点视图）、uts（主机名与域名）、ipc（System V IPC 与 POSIX 消息队列）、user（uid/gid 映射）、cgroup（cgroup 层级根视图）、time（部分时钟的偏移）。

理解它的关键在于"每种资源一把独立的刀"：你可以只隔离网络而共享其余，也可以八种全隔离。容器只是习惯性地把常用的几种一起隔离，让进程看起来像在独立主机里。本机 `ls /proc/self/ns/` 能真实列出这八类命名空间的链接（还额外有 pid_for_children、time_for_children 两个"给子进程用"的），印证了这套原语确实是内核内建、随时可查的。八种 namespace 的逐一展开属于本主题的姊妹报告，这里只需建立"namespaces = 一组按类别切分的视图隔离原语"这个总印象。

### 13-1.2.4 第三要素：cgroups 做资源限额

cgroups（control groups，控制组）把进程组织成层级，并对每一组施加资源上限与统计。常见的控制器有 cpu（CPU 时间的份额与配额）、memory（内存上限，超限触发回收或 OOM 杀进程）、pids（组内最大进程数）、io/blkio（块设备读写权重与上限）等。它回答的是"这一组进程最多能占用多少真实资源"。

直觉上，namespaces 解决"公平地看不见"，cgroups 解决"公平地分蛋糕"。没有 cgroups，一个容器里跑飞的进程可以疯狂 fork 或申请内存，把宿主拖垮，殃及同机所有其他容器（这类"吵闹的邻居"问题正是 cgroups 要治的）。cgroups 有两代——本机基线是 v1 hybrid（多个控制器各自挂载成独立层级），现代默认是 v2（单一统一层级）——这个 v1/v2 的分账是姊妹报告的重点，这里只需知道 cgroups 是容器"资源那一半"隔离的承重原语。

### 13-1.2.5 三要素之外：安全收窄与根文件系统（补充）

严格说，"进程 + namespaces + cgroups"是容器的最小骨架，但真实的容器运行时还会常规性地再叠加两类东西，初学者了解它们的存在即可，以免误以为容器隔离只有三样。

一类是安全收窄：capabilities（把 root 的全能权限拆成细粒度能力再削减）、seccomp（过滤容器能调用的系统调用）、以及 AppArmor/SELinux 这类 LSM（强制访问控制）。因为容器共享宿主内核，这些收窄用来缩小"万一进程作恶能碰到的内核面"，属于安全边界主题。

另一类是根文件系统隔离：容器要有自己独立的目录树，靠的是准备一个 rootfs 再用 pivot_root/chroot 切换根目录，配合镜像的分层文件系统（union/overlay）。这解释了为什么容器里 `ls /` 看到的是镜像内容而非宿主目录。把这两类补上，才是一个"生产级容器"，但它们都建立在三要素这个骨架之上。

- 锚点：Linux man page namespaces(7)（八种命名空间清单与语义）、cgroups(7)（控制器与层级模型）——强·一手，核实 2026-08-01。
- 本机实证（可复现，基线 Linux 6.18.5 / util-linux 2.39.3）：`ls /proc/self/ns/` 列出 cgroup/ipc/mnt/net/pid/time/user/uts 八类；`unshare --pid --mount --fork --mount-proc` 内 `$$`=1 且 `ps -e` 仅见 ns 内进程。

## 13-1.3 "容器不是轻量 VM"辨析

### 13-1.3.1 核心区别：容器没有自己的内核

"容器就是个更轻的虚拟机"是初学者最普遍、也最危险的误解。二者最根本的分界只有一条：VM 有自己独立的 guest 内核，容器没有。容器里的进程发起的每一个系统调用，最终都由宿主机那唯一的内核来执行；VM 里的进程发起的系统调用，则由该 VM 自己的 guest 内核处理，再由 hypervisor 把对硬件的访问中转给物理机。

为什么这条区别值得单独拎出来强调？因为它决定了"隔离边界画在哪里"。VM 的隔离边界是 hypervisor 加硬件虚拟化那一层，guest 里的坏进程要影响宿主或别的 VM，必须先攻破 guest 内核、再攻破 hypervisor，两道墙且第二道墙面（hypervisor 对外暴露的接口）相对很窄。容器的隔离边界就是那一个共享内核本身：容器里的进程和宿主进程面对的是同一套系统调用接口，只隔着 namespaces/cgroups 这层"内核内的权限与视图检查"。

### 13-1.3.2 攻击面差异：共享内核 = 更大的暴露面

顺着上一节，隔离边界的位置直接决定了攻击面大小。容器与宿主共享内核，意味着容器进程可以直接调用宿主内核暴露的整套系统调用（数百个），任何一个系统调用里的内核漏洞，都可能被容器内的进程利用来突破 namespaces/cgroups 的限制、拿到宿主权限——这类事件就叫"容器逃逸"（container escape）。也就是说，容器的攻击面约等于"整个宿主内核的系统调用接口"，非常大。

VM 则不同：guest 里的进程即便完全掌控了 guest 内核，它能触碰到的宿主侧接口只是 hypervisor 暴露的那一小组（虚拟设备、少量超级调用），面窄得多，因此"VM 逃逸"比"容器逃逸"要罕见且困难得多。一句话总结这条辨析：容器换来的轻量与高密度，代价正是把隔离从"硬件+hypervisor 的强边界"降级为"共享内核内部的软边界"。所以在多租户、跑不可信代码的场景里，"容器等于安全隔离"是错误预期，需要额外手段（见 13-1.4 的强隔离方案）。

### 13-1.3.3 常见误判与纠偏

有几个具体现象容易强化"容器像 VM"的错觉，逐一纠偏有助于建立正确心智。

容器里能看到独立的进程列表、独立的网络接口、独立的主机名、独立的根目录——这些"像一台独立机器"的表象，全部来自 namespaces 对视图的裁剪，底层仍是同一个内核在服务，并没有第二个内核存在。

容器里 `uname -r` 显示的内核版本，永远是宿主内核的版本，而不是镜像里那个发行版"应该"配的内核版本——因为镜像里根本没有内核，只有用户态的文件。这是判断"到底共享不共享内核"的一个极直接的观察点。

在 macOS/Windows 上"原生"跑 Linux 容器其实经过了一台隐藏的 Linux 虚拟机，这不是反例而是佐证：正因为容器必须共享一个同类内核，宿主内核不对路时，就得先用 VM 造出一个 Linux 内核来给容器共享。

- 锚点：Linux man page namespaces(7)、user_namespaces(7)（隔离由内核内检查实现，非独立内核）——强·一手，核实 2026-08-01。
- 交叉核对："容器共享宿主内核、攻击面为宿主系统调用接口、逃逸即突破内核"这一定性，由 Kubernetes 官方 Security 文档与 OCI 运行模型（无 guest 内核）双向印证，二来源一致，无冲突。

## 13-1.4 隔离谱系与用例

### 13-1.4.1 一条从弱到强的隔离连续谱

现实里并不是"只有容器和 VM 两个选项"，而是一条隔离强度递增、同时开销递增、密度递减的连续谱。从弱到强大致排列为：

裸进程（仅靠 OS 用户/权限隔离）→ 普通容器（namespaces + cgroups，共享内核）→ 用户态内核沙箱（如 gVisor）→ 微 VM（如 Kata Containers / Firecracker，每负载一个精简 guest 内核）→ 完整虚拟机（整机虚拟化）。

贯穿这条谱的规律是一个此消彼长的权衡：越往右，隔离越强、攻击面越小、越能安全地跑不可信代码，但启动越慢、单位负载内存开销越大、单机能跑的数量越少；越往左则相反。选型的本质就是在"我需要多强的隔离"与"我愿意付多少开销/牺牲多少密度"之间找平衡点，没有普适最优解。

### 13-1.4.2 普通进程与普通容器

最左端是普通进程：同一台机器上的进程之间只靠操作系统的用户/权限、文件权限做基本隔离，共享几乎一切（同一内核、同一网络、同一文件系统视图）。开销最小，隔离最弱，适合互相信任、本就属于同一应用的组件。

再往右是普通容器：在进程基础上加 namespaces 视图隔离与 cgroups 资源隔离，得到"看起来像独立主机、但共享宿主内核"的执行单元。它的甜点在于开销接近裸进程、启动毫秒级、密度极高，同时又有足够的隔离来打包依赖、限定资源、避免互相看见。因此绝大多数微服务、Web 应用、CI 任务都用普通容器——前提是这些负载大体可信，不把容器当作对抗恶意代码的安全边界。

### 13-1.4.3 用户态内核沙箱：gVisor

当普通容器的隔离不够、又不想付出完整 VM 的代价时，一类中间方案是用户态内核沙箱，代表是 gVisor。它的做法是在容器和宿主内核之间插一个"用 Go 写的用户态内核"（gVisor 的 Sentry 组件）：容器发出的系统调用被拦截，交给这个用户态内核用一套内存安全的重实现来处理，只有少量必要操作才真正落到宿主内核。这样，容器直接触达宿主内核的系统调用面被大幅收窄，攻击面随之缩小。

它的直觉是"给共享内核加一道用户态的过滤/代换层"，因此隔离强于普通容器、又不需要为每个负载起一台真 VM。代价是拦截与重实现带来运行时开销：系统调用密集、I/O 密集的负载会明显变慢，而计算密集、少 I/O 的负载（如批处理、部分推理）受影响小。gVisor 属快速演进的前沿项，具体性能开销随版本与负载差异很大，此处不引具体百分比。

### 13-1.4.4 微 VM：Kata Containers 与 Firecracker

再往强隔离走，是"给每个（或每组）容器包一台精简虚拟机"的微 VM 方案，代表是 Kata Containers（可搭配 Firecracker 或 QEMU 等轻量 VMM）。它让每个负载重新拥有自己独立的 guest 内核，隔离边界重新回到 hypervisor + 硬件那道强边界，从而获得接近 VM 的隔离强度；同时通过精简 guest、按需裁剪设备，把启动时间和内存开销压到远小于传统整机 VM，力求"VM 级隔离 + 接近容器的体验"。

关键辨析在于 gVisor 与 Kata 走的是两条不同的强隔离路线：gVisor 不引入 guest 内核，靠"用户态重实现系统调用"收窄面；Kata 引入独立 guest 内核，靠"真·硬件虚拟化边界"隔开。对抗性、跑不可信代码的场景通常认为微 VM 的隔离保证更硬。这两者及 Firecracker 都属 ⚙演进快·随时变的前沿生态，启动时延、内存与稳态性能开销随版本和配置显著波动，本报告不采信具体数值（待核）。

### 13-1.4.5 按用例选点：怎么落到谱系上

把选型落到实处，可给初学者一组粗线条判断。负载彼此可信、追求高密度与快启动（内部微服务、Web 后端、CI 构建）——普通容器即可，这是默认选择。需要比普通容器更强的隔离但不愿付 VM 代价、且负载偏计算密集——考虑 gVisor 一类用户态沙箱。跑不可信/多租户/对抗性代码（如公有 FaaS、在线运行他人提交的代码）——用微 VM（Kata/Firecracker）或干脆用完整 VM，把隔离边界压回硬件层。需要跑与宿主不同的操作系统、或要最强的整机级隔离——完整 VM。

这些不是互斥阵营，而是同一条谱上的取点，甚至可以混用（例如在 VM 里再跑容器，Kubernetes 也支持通过 RuntimeClass 让同一集群里不同 Pod 分别落到普通容器或沙箱运行时）。选点的依据始终是那个贯穿全谱的权衡——你要多强的隔离，愿意用多少开销和密度去换。

- 锚点：Linux man page namespaces(7)/cgroups(7)（普通容器隔离原语）、Kubernetes 官方文档 RuntimeClass 概念（v1.36，⚙演进快·锚版本）——核实 2026-08-01。
- 前沿（⚙演进快·随时变）：gVisor（用户态内核/Sentry 拦截系统调用）、Kata Containers、Firecracker 的机制定性取自各自官方文档与 CNCF 生态描述；隔离-开销的相对排序为多来源一致的定性结论，具体启动时延/内存/性能开销数值随版本剧烈变动，标「待核」，不引具体百分比。
- 二手指路（不承重）：2026 年多篇容器隔离对比文（gVisor vs Kata vs Firecracker）方向一致地把隔离强度排为 进程<容器<gVisor<微VM<VM，用作交叉印证，具体数字未采信。
- 冲突记录：关于 gVisor 与 Kata "谁隔离更强"，不同二手来源侧重不同（gVisor 收窄系统调用面 vs Kata 硬件边界+独立内核）；本报告按"引入独立 guest 内核者边界更硬"的一手机制差异陈述，不做量化裁决。
