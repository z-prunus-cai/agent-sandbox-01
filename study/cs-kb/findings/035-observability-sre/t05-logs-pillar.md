# L5-12·大主题5 logs 支柱

日志（log）是可观测性最古老、最普及的一种遥测数据：一条日志就是"某时刻发生了某事"的一条带时间戳的记录。本报告讲清日志从"怎么写"（结构化）、"写多少/写多重"（级别与采样）、"写到哪去"（聚合管道）到"规范如何收编它"（OTel Logs 与"三支柱"之辨）四条线。承重一手为 OTel Logs 规范与 RFC 5424；业界工具与"三支柱"综述打 ⚠，仅指路、不承重。

## 12-5.1 结构化 vs 非结构化日志

### 12-5.1.1 日志是什么

日志是应用或系统在运行时主动写出的、带时间戳的离散事件记录，每条描述"在某个时间点、某处发生了什么"。它与 metrics（数值时序聚合）、traces（跨服务的请求因果链）并列，但粒度最细：日志保留的是单条事件的原始上下文，而不是被预先聚合成的数字。

对初学者最直观的心智模型是：metrics 回答"系统现在健不健康、有多少量"，traces 回答"这一个请求在各服务间怎么流动、卡在哪"，而 logs 回答"具体那一刻到底发生了什么、带着什么细节"。三者都来自同一套运行中的程序，只是把信息压成了不同形状。OTel 的日志数据模型把一条日志抽象成一个 LogRecord，明确它可以来自应用日志文件、机器生成的事件、系统日志等多种来源，并能被无歧义地映射到统一模型——也就是说"日志"这个词覆盖的范围比 `print` 一行字要宽得多。

### 12-5.1.2 非结构化日志

非结构化日志是自由格式的纯文本行，人写给人看，机器要靠正则/模式匹配才能解析。经典形态如 `2026-08-01 12:00:03 ERROR user login failed for alice from 10.0.0.5`——信息都在，但字段边界只存在于人的脑子里。

它的优点是写起来零成本、肉眼直接可读，小规模排障时很顺手。缺点在规模上暴露：要在几十亿行里筛"某用户的失败登录"，就得写脆弱的正则去从文本里抠出 `user` 和 `status`，而只要有人改了一下日志措辞，解析规则就跟着崩。多个来源一致指出，非结构化日志"易写、难在规模上搜索与分析"，且高度依赖必须随日志文案变动而更新的模式匹配。半结构化格式（如 `logfmt` 的 `key=value` 串、Apache 访问日志的固定字段序）介于两者之间：有一定字段约定，但仍是文本、仍需按格式解析。

### 12-5.1.3 结构化日志（键值 / JSON）

结构化日志用统一的机器可读格式承载每条记录，典型是 JSON 或键值对，把"时间、级别、消息、用户、来源 IP、trace_id"等都放进具名字段，而不是拼进一句话里。上一条 5.1.2 的例子结构化后是：

```
{"ts":"2026-08-01T12:00:03Z","level":"ERROR","msg":"user login failed","user":"alice","src_ip":"10.0.0.5","trace_id":"4bf9..."}
```

好处是字段天然可被检索、过滤、聚合、关联，不再依赖正则；同一格式既能被人读，也能被采集器、索引引擎、告警系统直接消费。JSON 成为事实主流是因为它轻量、工具生态支持广、人机皆可读。写给初学者的关键直觉：结构化的本质不是"变成 JSON"，而是"把语义放进字段而不是放进散文"——这样查询从"文本搜索"升级成"按字段过滤+聚合"，也让日志能和 trace/metrics 用相同的属性（如同一个 `trace_id`）关联起来。易错点是把大段自由文本仍塞进一个 `msg` 字段却不拆字段，等于套了 JSON 壳的非结构化日志；另一个常见坑是字段命名不一致（`user` / `userId` / `uid` 混用），会让跨服务聚合失效——这正是后文 OTel 语义约定要解决的问题。

### 12-5.1.4 结构化 vs 非结构化的取舍与易错点

两者的取舍是"写入便利/人眼可读"对"规模化查询与自动化"的权衡：非结构化胜在即写即读、开发心智负担低；结构化胜在可搜索、可聚合、可跨源关联、维护成本低。现代可观测性实践普遍倒向结构化，把它视为"可观测性的基础"，因为下游的聚合管道和查询体验几乎完全建立在字段化数据之上。

初学者容易误以为"结构化=只对机器友好、对人不友好"，实际上成熟工具会把 JSON 渲染成人类可读视图，所以并不牺牲可读性。真正的成本在别处：结构化日志每条体积更大（键名重复占空间）、需要在代码里养成传字段的习惯、字段一旦爆炸（高基数字段如把完整 URL、用户 ID 当字段无限展开）会拖垮索引。因此实务上常见折中：入口/关键路径结构化并带 `trace_id`，边角调试信息可留文本，靠采集端再解析。这里存在来源分歧：安全/SIEM 视角（CrowdStrike 等）会把"半结构化"单列为一类并强调其解析成本，而多数可观测性文章只做"结构化 vs 非结构化"二分——两种切法都对，只是分类粒度不同，读者知道有"半结构化"这一档即可。

## 12-5.2 日志级别与采样 / 降级

### 12-5.2.1 日志级别语义

日志级别（log level / severity）标注一条日志的重要程度，供过滤与告警使用。这里存在多套并行标准，须分账。IETF RFC 5424（Syslog 协议）定义 8 个数字严重级，数字越小越紧急：

```
0 Emergency  1 Alert  2 Critical  3 Error  4 Warning  5 Notice  6 Informational  7 Debug
```

应用框架（log4j、Python logging、Go 等）则常用一套约 5–6 档的命名级别：TRACE / DEBUG / INFO / WARN(WARNING) / ERROR / FATAL(CRITICAL)。OpenTelemetry 为了统一各家，定义了 SeverityNumber（1–24，0 为未指定），把上面各家级别归并成 6 个区间：

```
1–4 TRACE   5–8 DEBUG   9–12 INFO   13–16 WARN   17–20 ERROR   21–24 FATAL
```

初学者要抓住的直觉是"级别是给日志分优先级的旋钮"：INFO 记录正常但值得留痕的事，WARN 是"有点不对但还没坏"，ERROR 是"这次操作失败了"，FATAL/Emergency 是"系统要挂/已挂"。三套标准的存在正是本节的关键分歧点：syslog 是 8 级且方向相反（0 最严重），应用框架是约 5–6 级、名字互不统一（有的用 WARN 有的用 WARNING、有的有 FATAL 有的叫 CRITICAL），OTel 用 SeverityNumber 区间+原始 SeverityText 两字段并存来吸收这种混乱——既存归一化数字（跨系统可比），又保留原始级别串（不丢原味）。易错点：不要假设"ERROR 在所有系统里是同一个数字"；RFC 5424 里 Error=3、OTel 里 ERROR=17–20，语义相近但编码不同，跨系统比较要走 SeverityNumber 这类归一化层。

### 12-5.2.2 级别作为运行时过滤与降级手段

日志级别的第一用途是设"最低输出阈值"：配置成 INFO 就丢弃 DEBUG/TRACE，只留 INFO 及以上。生产默认通常跑在 INFO 或 WARN，把昂贵的 DEBUG 关掉；OTel 也明说 TRACE 类"细粒度调试事件，默认配置下通常禁用"。

对初学者，这就是"音量旋钮"：平时调低（只听重要的），出问题时临时调高到 DEBUG 看细节。进阶做法是动态调级——不重启服务、在运行时把某个模块的级别临时提到 DEBUG，排完障再调回，避免长期开 DEBUG 把磁盘和成本打爆。这也是最朴素的一种"降级"：负载或成本压力大时，把日志阈值上抬（例如从 INFO 提到 WARN），用牺牲细节换吞吐与花费。易错点是把 DEBUG 长期留在生产：既拖性能又淹没真正重要的日志，还可能把敏感数据写进日志。

### 12-5.2.3 日志采样

日志采样是在高流量下只保留一部分日志，用抽样换取成本与查询速度，同时尽量不丢关键信息。常见策略有三类：概率/头部采样（按固定比例随机保留，且常按级别分层——高严重级少采或不采、低价值日志重采）、尾部采样（先缓冲，等知道结果再决定：出错了就全留，没出错就抽样或丢弃）、以及丢弃规则（对特定高频噪声模式直接整类丢掉）。

同一类"请求成功"日志每秒几万条，信息高度冗余，留 1% 足够看趋势；但"请求失败/异常"稀有且宝贵，要 100% 保留。按级别分层采样正是这个思路——ERROR 全留、INFO 抽样、DEBUG 基本不采。尾部采样更聪明但更贵：因为要"等结果再决定"，就必须先把日志缓冲住，实现和内存成本更高，好处是能精准保留"有错的那条链路的全部日志"。业界工具（Vector、Logstash、Filebeat 等）可在进入存储前就做采样。易错点：采样率不是拍脑袋定的常量，业界一致建议从保守（少丢）起步再按数据调低；以及采样后不能再拿日志"数个数"当精确指标用——计数类的事该交给 metrics，否则采样会让计数失真。

具体采样比例/默认值属实现相关，各工具不一，无单一标准默认值可引，须按所用工具文档为准（此处不设定值，避免编造）。

### 12-5.2.4 高流量下的降级与限速

除了采样，系统在过载时还会对日志本身做背压与限速：限制每秒写入的日志条数/字节数、对突发日志做速率限制（rate limiting）、在管道拥塞时优先丢弃低级别日志以保住高级别。这与本课"过载处理"主题一脉相承——日志子系统自己也可能成为过载源，必须能被"止血"。

想象一个 bug 导致某行 ERROR 每毫秒打一次，日志管道瞬间被这条"日志风暴"打满，反而把真正重要的其他日志挤掉、甚至拖垮应用。因此成熟框架会做"同类日志去重/限频"（例如"相同消息 1 秒内最多打 N 条，其余折叠为 '重复 M 次'"）。这里没有跨系统统一的默认阈值，属各库/各采集器实现自定，具体数值须查对应文档或标「待核」，不凭记忆填。核心心智：日志是"尽力而为"的遥测，过载时宁可有损（丢低价值日志）也不能让日志拖垮主业务。

## 12-5.3 日志聚合管道

### 12-5.3.1 为什么需要集中式聚合

日志聚合是把分散在众多主机/容器/服务上的日志集中收集到一处，做统一存储、检索与分析。在单机时代 `tail -f` 一个文件就够；但在分布式系统里，一次请求横跨几十个服务实例、容器还会随时被销毁重建，登录每台机器看日志既不可能也无意义，必须把日志"汇总到一个可搜索的地方"。

容器是"短命"的，Pod 一重启本地日志就没了；一次故障往往涉及多个服务，你需要把它们的日志按时间/按 `trace_id` 拼到一起看。集中式聚合解决的正是"日志随节点漂移、跨服务分散"这两个问题——先把日志运走、存到不随节点消亡的地方，再提供统一查询入口。

### 12-5.3.2 管道阶段：采集 → 传输 → 解析 → 索引存储 → 查询

一条典型日志聚合管道分若干阶段，链路是：采集（agent 从文件/stdout/syslog 抓取）→ 传输/缓冲（经网络送出，常加消息队列做削峰缓冲）→ 解析与富化（把非结构化行解析成字段、补上主机/环境/标签）→ 索引与存储（写入可搜索的存储引擎）→ 查询与可视化（UI 上搜索、聚合、建看板、配告警）。可写成：

```
采集(collect) → 传输/缓冲(ship/buffer) → 解析/富化(parse/enrich) → 索引/存储(index/store) → 查询/可视化(query/visualize)
```

把它想成一条流水线，日志像原料从源头产出，一站站被搬运、清洗、贴标签、入库、最后上架供查询。中间的"缓冲"环节（常用 Kafka/Redis/RabbitMQ）很关键——当日志洪峰超过下游索引能力时，队列先扛住，避免直接丢数据或压垮存储。易错点：解析放在哪一层是个工程选择（源头结构化最省，还是到管道里再用 Logstash/Vector 解析），越靠源头结构化，后面越省事、越不易因文案变动而解析失败。

### 12-5.3.3 典型实现：ELK/EFK 与 Loki

最主流的一手落地是 ELK/Elastic 栈：Beats/Filebeat 采集 → Logstash 解析富化（也可省略或替换）→ Elasticsearch 索引存储并提供全文检索与聚合 → Kibana 查询与可视化；把采集端换成 Fluentd/Fluent Bit 常记作 EFK。另一条路线是 Grafana Loki，它的设计哲学是"只索引标签、不做日志正文全文索引"，以此大幅降低索引成本，查询时靠标签快速缩小范围再扫描原文。

ELK 强在"任意全文检索+强聚合"，代价是索引开销大、存储贵；Loki 强在"便宜、和 Prometheus/Grafana 标签模型一致"，代价是不擅长任意全文搜索、更依赖你先用好标签。这不是谁更优，而是"索引一切"与"只索引标签"两种成本模型的取舍。此处工具链演进快（版本、组件、默认项常变），具体功能/默认须以对应版本官方文档为准（⚙演进快·锚版本·随时变，核实 2026-08-01；本报告不锚定某一工具版本号，避免过时）。

### 12-5.3.4 成本、基数与保留期陷阱

日志聚合最大的现实约束是成本：日志量随流量线性增长，索引与存储费用会失控，因此保留期（retention）、采样、字段基数都要被当作预算来管。高基数字段（把用户 ID、完整 URL、请求参数当索引字段无限展开）会让索引急剧膨胀，是成本爆炸的头号原因。

保留期就是"日志留多久"——热数据（近几天，随时查）放贵而快的索引，冷数据（几周前，偶尔查）转成便宜的对象存储归档甚至只留采样。基数（cardinality）指某字段可能取值的数量，越高越贵；这与 metrics 里"标签基数"的坑同源。易错点：默认把所有字段都索引、把保留期设很长、不采样——三者叠加就是账单灾难。务实做法是分级保留+按价值采样+控制索引字段。具体价格/压缩比/默认保留期随厂商与版本变动大，属「待核」，不在此设定数值。

## 12-5.4 OTel Logs 规范 vs "支柱"概念

### 12-5.4.1 "三支柱"是社区框架，须与规范分账

"可观测性三支柱=metrics、logs、traces"是一个流行的社区叙事，不是任何标准规范里的定义。它源于 2018 年 Peter Bourgon 一篇影响很大的博客，随后被广泛采用——一部分原因是它贴合工程师的日常，另一部分（被业界人士直言）是厂商恰好各有"指标产品、日志产品、追踪产品"可卖。

把这三者当"三根并列支柱"是一种便于沟通的心智模型，但它是二手框架、不承重。多位业界人物对它有明确批评——Ben Sigelman 论证"metrics、logs、traces 不过都是遥测（telemetry）的不同形状"，Charity Majors（Honeycomb）等则推动"observability 2.0"的说法，主张三者本质是同一批带上下文的事件数据的不同投影，而非三种割裂的东西。因此本报告用"logs 支柱"只是沿用通行说法定位主题，真正承重的定义与数据模型来自下面的 OTel 规范。

### 12-5.4.2 OTel Logs 数据模型（一手，GA）

OpenTelemetry 的 Logs Data Model 是本主题的承重一手规范，状态为 Stable（GA）。它定义了与物理格式无关的 LogRecord 逻辑模型，声称各类既有日志格式都能被无歧义地映射进来。LogRecord 的顶层具名字段包括：Timestamp（事件发生时间）、ObservedTimestamp（采集系统观测到的时间）、TraceId、SpanId、TraceFlags、SeverityText（原始级别串）、SeverityNumber（归一化数字，见 5.2.1）、Body（日志正文，可为字符串或结构化数据）、Resource（来源元数据）、InstrumentationScope、Attributes（事件级键值属性）、EventName。

这套模型把"人各写一套 JSON 字段"变成"大家往同一组具名字段里填"，于是不同语言、不同框架、不同来源的日志能被统一处理、跨源关联。尤其注意 Timestamp 与 ObservedTimestamp 分开——它承认"事件发生"和"系统收到"往往不同步，这对乱序/延迟日志的正确排序很重要。配合语义约定（semantic conventions，统一属性命名），它直接解决了 5.1.3 里"字段命名不一致导致聚合失效"的痛点。此规范随 OTel 演进（⚙演进快·锚版本·随时变）：本报告锚 spec v1.53.0、logs 数据模型状态 Stable，核实 2026-08-01；OTel 项目已于 CNCF 毕业（graduated, 2026-05）。

### 12-5.4.3 OTel Logs 的桥接式设计（与 traces/metrics 不同）

OTel 对日志采取了与 traces/metrics 明显不同的设计路线：traces 和 metrics 是"全新设计的用户级 API"，而 logs 走"桥接（bridge）"路线——不发明让应用开发者直接调用的新日志 API，而是提供 Log Bridge API，供日志库作者写"appender/桥接器"，把现有日志框架（log4j、logback、Python logging 等）的输出接入 OTel 数据模型与管道。

Log Bridge API 不是给业务代码直接调的。日志领域已有几十年的库和海量既有 `logger.info(...)` 调用，OTel 选择"收编而非取代"——应用开发者继续用熟悉的日志库照常写日志，只需在启动时配置一个 appender 和 SDK，日志就被自动桥接进 OTel 管道。这是它区别于 traces（通常要显式创建 span）的最大特点，也降低了迁移成本。易错点：初学者常以为"用 OTel 记日志要改写所有日志语句"，其实恰恰相反，桥接式设计就是为了不用改写。

### 12-5.4.4 日志与 trace 的关联（弱化"支柱"边界）

OTel Logs 模型内建 TraceId / SpanId / TraceFlags 字段，appender 可自动从当前活跃的 span 上下文抓取 trace_id、span_id 并贴到日志记录上。这样一条日志就能被精确归属到"哪一次请求、哪一个处理步骤"，从而在查询时把 logs 和 traces 直接串起来。

对初学者，这正是对"三支柱"叙事最有力的现实反驳：当每条日志都带着 trace_id、和 trace/metrics 共享同一套 Resource 与语义属性时，三者就不再是三根割裂的柱子，而是同一批带上下文事件数据的不同视图——这与 5.4.1 里 "observability 2.0"/"都只是遥测"的批评相互印证。落到实践的收益也很直接：排障时从一个慢 trace 一键跳到该请求产生的全部日志、或从一条 ERROR 日志跳回它所在的完整调用链，不用再手工按时间戳猜。这也是为什么现代实践强调"日志务必带 trace 关联字段"——它把日志从孤立文本升级成可与其它信号联查的结构化事件。
