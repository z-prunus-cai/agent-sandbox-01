## V3.1 控制流分析(CFA)

### V3.1.1 CFA 要回答的问题：在高阶语言里"谁调用谁"

控制流分析（Control Flow Analysis, CFA）是针对函数式/高阶语言的一种静态分析，目标是为程序里**每个调用点（函数应用 e1 e2）算出：被调用的函数体到底可能是哪几个 lambda 抽象**。等价地说，它要为每个子表达式求出"这个表达式求值后可能得到哪些函数值"。

对初学者，先看它和命令式语言的对比就懂了。在 C 这种一阶语言里，`f(x)` 直接写着调用的是名叫 `f` 的函数，控制流图（哪个基本块能跳到哪个）一眼可见，数据流分析（V2）可以直接在这张图上跑。但在函数式语言里函数是"一等公民"——可以存进变量、当参数传、从函数里返回。于是一个应用式

(g y)

到底调用的是哪个函数，取决于运行时 `g` 里装的是哪个 lambda，而这正是分析想算的东西。控制流依赖于数据流、数据流又依赖于控制流，二者纠缠在一起。CFA 就是为了打破这个循环：它同时逼近"每个表达式的可能函数值"和"每个调用点的可能目标"，一次算清。

一个具体直觉：CFA 之于函数式语言，相当于**调用图（call graph）构造**之于面向对象语言里的虚方法分派（`obj.m()` 到底调哪个重写版本）——都是"间接调用目标集合"的静态近似。算出这张"谁可能调谁"的图之后，才谈得上在其上做别的优化或验证。易错点是别把 CFA 误当成"求精确的调用目标"——它是 sound 的**过近似（over-approximation，见 V1.3）**：算出的目标集合只多不少，宁可多列几个不可能真的发生的目标，也绝不漏掉一个真会发生的，这样基于它的后续优化才安全。

### V3.1.2 分析对象：带标号的 Fun 语言

要精确地谈"每个子表达式的可能值"，得先给每个子表达式一个名字。PPA 用一门小函数式语言 **Fun**，并给每个子表达式打上唯一**标号（label）ℓ**，写作 t^ℓ（项 t 处在程序点 ℓ）。语法主干是

e ::= t^ℓ

t ::= c ｜ x ｜ fn x => e0 ｜ fun f x => e0 ｜ e1 e2 ｜ if e0 then e1 else e2 ｜ let x = e1 in e2 ｜ e1 op e2

其中 fn x => e0 是普通匿名函数、fun f x => e0 是可递归引用自身 f 的函数、e1 e2 是函数应用。

标号是理解 CFA 的关键脚手架，初学者务必抓住。它就像给源码里每个括号结点贴一个编号便签，让分析可以说"标号 5 这个位置可能求值出哪些函数"而不至于指代不清。比如把

((fn x => x^1)^2 (fn y => y^3)^4)^5

拆开来看，内层 x 在点 1、整个 fn x=>x 在点 2、内层 y 在点 3、整个 fn y=>y 在点 4、外层这个应用式在点 5。同一个 lambda 文本如果在源码里出现两次，会拿到两个不同标号，是两个不同的程序点——这点在后面区分"抽象值"（是哪个 lambda）和"程序点"（在哪里）时很重要。

### V3.1.3 CFA 的结果：抽象缓存 Ĉ 与抽象环境 ρ̂

一份 CFA 的分析结果是一对函数 (Ĉ, ρ̂)。**抽象缓存 Ĉ** 把每个标号 ℓ 映到一个"抽象值集合"，表示程序点 ℓ 可能求值出的东西；**抽象环境 ρ̂** 把每个变量名 x 映到一个抽象值集合，表示 x 在运行时可能绑定到的东西。这里的"抽象值"就是程序里出现的那些 lambda 抽象本身（fn/fun 项），抽象值的论域是它们的幂集：

Ĉ : Lab → P(Term)

ρ̂ : Var → P(Term)

其中 Term 是程序中全部 lambda 抽象构成的有限集合。

初学者可以把 Ĉ 想成"给每个程序点挂一块小白板，上面写着这里可能冒出哪些函数"，把 ρ̂ 想成"给每个变量名挂一块白板，写着它可能装哪些函数"。为什么值只记"是哪个 lambda"而丢掉整数、布尔等？因为 CFA 只关心控制流——它要回答"调用点会跳进哪个函数体"，常量对这个问题没贡献，于是被抽象掉、记为空集。

关键要分清两块白板的角色差异，这是最常见的混淆点。Ĉ 是按**程序点**（标号）索引的，同一个变量 x 出现在两个不同标号会查各自的 Ĉ；ρ̂ 是按**变量名**索引的，整个程序里所有叫 x 的地方共享同一块 ρ̂(x) 白板。正是"所有同名变量共享一块环境白板"这一点，使得基础版 CFA 是上下文不敏感的（下面 V3.4 会松开这个限制）。

## V3.2 抽象 0-CFA

### V3.2.1 0-CFA 是什么：最基础、上下文不敏感的 CFA

0-CFA（读作"零 CFA"）是 CFA 家族里最基础的一档：它为每个变量、每个程序点各维护**唯一一块**抽象值白板，完全不区分"这个函数是从哪个调用点进来的上下文"——名字里的 0 就指"记录 0 层调用上下文"。它算出的 (Ĉ, ρ̂) 是 sound 的过近似，且可在多项式时间内求出。

对初学者，"0" 的含义可以这样体会：设想一个函数 id = fn x => x 被在程序里两处分别用整数和用另一个函数调用。0-CFA 把这两次调用的实参**混在同一块 ρ̂(x) 白板上**，于是分析认为 x 可能是"整数或那个函数"，两处调用的信息互相污染。这种"不分上下文、全程序合并"的做法叫**单变量分析（monovariant）**——每个变量只有一个抽象版本。它精度不高，但简单、快、够很多用途，是理解一切更精细 CFA 的地基。

还有一个易错点，0-CFA 的"流不敏感"也体现在它不追踪语句执行顺序、不为每个程序点单独维护"到达此处时的环境"，ρ̂ 是全程序一份的。这与 V2 数据流分析里"每个程序点有各自的 IN/OUT"不同——那种逐点区分留给更强的分析，0-CFA 故意舍弃以换取简单与速度。

### V3.2.2 可接受性规范：用关系 (Ĉ, ρ̂) ⊨ e 定义"什么样的解是对的"

在写"怎么求解"之前，PPA 先用一个**可接受性关系（acceptability relation）** (Ĉ, ρ̂) ⊨ e 声明式地刻画"(Ĉ, ρ̂) 是 e 的一个合法 CFA 结果"需要满足哪些包含关系。它对语法逐条给出（核心几条）：

(Ĉ, ρ̂) ⊨ c^ℓ    恒成立（常量不产生函数值）

(Ĉ, ρ̂) ⊨ x^ℓ    当且仅当 ρ̂(x) ⊆ Ĉ(ℓ)

(Ĉ, ρ̂) ⊨ (fn x => e0)^ℓ    当且仅当 {fn x => e0} ⊆ Ĉ(ℓ) 且 (Ĉ, ρ̂) ⊨ e0

(Ĉ, ρ̂) ⊨ (t1^ℓ1 t2^ℓ2)^ℓ    当且仅当 (Ĉ, ρ̂) ⊨ t1^ℓ1 且 (Ĉ, ρ̂) ⊨ t2^ℓ2 且

对每个 (fn x => t0^ℓ0) ∈ Ĉ(ℓ1)：Ĉ(ℓ2) ⊆ ρ̂(x) 且 Ĉ(ℓ0) ⊆ Ĉ(ℓ)

（fun f x => e0 一条同理，另加 {fun f x => e0} ⊆ ρ̂(f)，使递归名 f 在函数体内可见。）

逐条读懂它就掌握了 0-CFA 的全部直觉。变量那条 ρ̂(x) ⊆ Ĉ(ℓ) 说："x 出现在点 ℓ，那么 x 可能绑定到的一切，都必须记进点 ℓ 的白板"。抽象那条说："fn x => e0 这个函数字面量出现在点 ℓ，那这个函数自己就是点 ℓ 的一个可能值（{它} ⊆ Ĉ(ℓ)），并且它的函数体也得合法"。最关键的是应用那条：把操作数点 ℓ1 上可能出现的**每一个**函数拉出来，对每一个都要求——实参（点 ℓ2 的值）流进该函数的形参 x（Ĉ(ℓ2) ⊆ ρ̂(x)），且该函数体的结果（点 ℓ0）流回到整个应用的结果点 ℓ（Ĉ(ℓ0) ⊆ Ĉ(ℓ)）。这就是"调用即：实参进形参、返回值出到调用点"的静态版本。

初学者常见困惑：为什么全是 ⊆ 而不是 =？因为分析是 sound 过近似，白板上"至少要包含真实可能发生的值"，多写无害、少写不安全，所以约束都是"下界"形式的包含。满足全部 ⊆ 的解通常有很多（把所有白板都填成全集也满足），我们要的是其中信息最少、最精确的那个——**最小解**（V3.3 讲怎么取到它）。

### V3.2.3 约束生成：把 ⊨ 规则改写成一组可求解的约束

可接受性关系是"检验一个解对不对"的判据；要**算出**解，把同一批条件重写成一组**约束**，再交给求解器。0-CFA 生成三类约束：

{t} ⊆ Ĉ(ℓ)         （lambda 字面量 t 在点 ℓ，无条件成立）

Ĉ(ℓ1) ⊆ Ĉ(ℓ2)  或  ρ̂(x) ⊆ Ĉ(ℓ)     （无条件的包含流）

{t} ⊆ Ĉ(ℓ1)  ⟹  Ĉ(ℓ2) ⊆ Ĉ(ℓ3)     （条件约束：仅当函数 t 真的可能出现在 ℓ1 时，右边的流才生效）

对应用式 (t1^ℓ1 t2^ℓ2)^ℓ，对程序里**每一个** lambda 抽象 (fn x => t0^ℓ0) 生成一对条件约束：

{fn x => t0} ⊆ Ĉ(ℓ1)  ⟹  Ĉ(ℓ2) ⊆ ρ̂(x)

{fn x => t0} ⊆ Ĉ(ℓ1)  ⟹  Ĉ(ℓ0) ⊆ Ĉ(ℓ)

条件约束是 0-CFA 的点睛之笔，也是它和普通数据流分析记法最大的不同，值得慢慢体会。前置条件 {t} ⊆ Ĉ(ℓ1) 是一道"闸门"：只有当分析过程中真的发现"函数 t 可能流到调用点的操作数位置 ℓ1"时，才打开闸门、让"实参流进 t 的形参 / t 的返回值流回调用点"这两股流生效。这精确地对应"只有可能被调用的函数，才需要把实参接进来"。用最小例子体会：

((fn x => x^1)^2 (fn y => y^3)^4)^5

生成的约束（挑关键几条）：

{fn x=>x} ⊆ Ĉ(2)，  {fn y=>y} ⊆ Ĉ(4)     （两个 lambda 字面量各就各位）

ρ̂(x) ⊆ Ĉ(1)，  ρ̂(y) ⊆ Ĉ(3)     （变量出现处）

{fn x=>x} ⊆ Ĉ(2) ⟹ Ĉ(4) ⊆ ρ̂(x)     （若 fn x=>x 可能是被调者，则实参 fn y=>y 流进 x）

{fn x=>x} ⊆ Ĉ(2) ⟹ Ĉ(1) ⊆ Ĉ(5)     （……则函数体 x 的结果流回应用点 5）

顺着解一遍：Ĉ(2) 里确有 {fn x=>x}，闸门打开 → Ĉ(4)⊆ρ̂(x) 使 ρ̂(x) 含 fn y=>y → 又 ρ̂(x)⊆Ĉ(1) 使 Ĉ(1) 含 fn y=>y → 再由 Ĉ(1)⊆Ĉ(5) 得 Ĉ(5) 含 fn y=>y。于是分析结论：整个表达式（点 5）可能求值出 fn y=>y——这与它真实的求值结果 fn y=>y 完全一致。这个例子也顺带演示了"约束生成"和"约束求解"确实是解耦的两步。

### V3.2.4 记法各家有别：需核对到出处

0-CFA 的这套规则各家教材/讲义记法差异不小，落笔前务必核对原书，别把不同体系的符号拼在一起。PPA 用 (Ĉ, ρ̂) 双函数 + 可接受性关系 ⊨ + 条件约束三件套；Shivers 的原始 k-CFA 则以抽象状态机（abstract interpretation of a CPS machine）呈现，用 contour/时间戳而非显式 ⊆ 约束；CMU 等课程讲义常写成 C(ℓ)、r(x) 或用不同的箭头方向。

对初学者，要记住的是这些只是同一件事的不同外衣：核心永远是"变量/程序点各配一个集合变量，函数应用生成'实参进形参、返回值出调用点'的（条件）包含约束，求最小解"。易错点是抄公式时把某本书的"操作数标号 ℓ2"与"结果标号 ℓ"记反，或把递归 fun 那条漏掉 {fun f x=>e0}⊆ρ̂(f)——递归名在体内必须可见，漏了会让递归调用分析不出目标。凡具体下标方向，以你实际采用的那一本（这里是 PPA §3.1–3.2）为准。

## V3.3 集合约束与求解

### V3.3.1 集合约束：把 CFA 归约为"集合上的包含不等式组"

上一节生成的每条约束，本质都是**集合约束（set constraint）**——变量取值是集合、约束形如"某集合包含于另一集合"。0-CFA 用到的只是集合约束的一个受限片段：右边是单个集合变量（Ĉ(ℓ) 或 ρ̂(x)），左边是常量集 {t}、另一个集合变量，或一条带前置守卫的**条件约束**。求 CFA 结果 = 求这组集合约束的**最小解（least solution）**。

初学者可以把它类比成一个只有 ⊆ 没有 = 的"不等式组"。普通代数解方程求的是精确等号解；这里因为分析要 sound 过近似，只要求"每块白板至少装下约束逼着它装的东西"，所以是不等式，且要的是把每块白板填得尽量小、恰好满足全部约束的那个解。为什么最小解一定存在且唯一？因为这些约束在集合的包含序（⊆）下都是**单调**的（往白板里加元素只会让更多闸门打开、只会要求加更多元素，不会反悔删元素），由不动点理论（承 V2 的完全格 + 单调函数 + Tarski 不动点）保证存在唯一最小不动点。这正是 V2 那套数学在这里的复用。

一句话点明与 V2 的关系：数据流方程也是一组单调约束、也求最小/最大不动点；约束式分析只是把"约束"显式地写成集合包含式、并允许**条件**约束（这是数据流框架里不常见的表达力），从而天然适配"控制流未知"的高阶场景。

### V3.3.2 图闭包求解：把约束画成图，沿边传播到稳定

求最小解的标准机械办法是**基于图的传递闭包（graph closure）**。构造一张有向图：

每个集合变量（Ĉ(ℓ)、ρ̂(x)）是一个**节点**，节点上挂一个当前已知元素的集合；

每条无条件约束 Ĉ(ℓ1) ⊆ Ĉ(ℓ2) 画一条边 ℓ1 → ℓ2（元素沿边从源流向目标）；

每条条件约束 {t} ⊆ Ĉ(ℓ1) ⟹ Ĉ(ℓ2) ⊆ Ĉ(ℓ3) 挂在节点 ℓ1 上作为"待激活边"：一旦 t 进入 ℓ1 的集合，就把边 ℓ2 → ℓ3 加入图并激活。

求解就是一个**worklist 传播**（呼应 V6 的通用求解器）：

1. 用无条件约束 {t}⊆Ĉ(ℓ) 给各节点填入初始元素，把"元素刚加入某节点"这类事件放进工作表；

2. 取出一个事件：把该元素沿所有出边传播给后继节点；若某节点因此新增元素，产生新事件入表；

3. 若新增的元素触发了挂在该节点上的条件约束（守卫 {t}⊆Ĉ(ℓ1) 满足），把对应的新边加入图并激活，可能再产生传播；

4. 工作表空时停止，此时各节点集合即为最小解。

初学者抓住"闸门 + 管道"的画面就懂了：普通约束是常开的管道，元素顺着流；条件约束是带阀门的管道，只有当上游流来了指定的那个函数 t，阀门才打开、下游管道才接通。整个过程只会往节点里"加"元素、只会"开"阀门，绝不回退，所以必然在有限步内稳定（论域 Term 有限，满足升链条件 ACC）。终止性和唯一最小解都来自这个单调性。

### V3.3.3 复杂度：0-CFA 是立方时间

0-CFA 的最小解可在**立方时间**求出：设程序规模为 n（标号数/子表达式数量级），则

时间复杂度 = O(n³)

这个 O(n³) 是 CFA 家族里"context-insensitive"一档的标志性界，也是它相对 k-CFA（V3.4）"便宜"的根本原因。

对初学者，立方界的来源可以粗略这样理解：约束/边的数量是 O(n²) 量级（每个应用点要对程序里每个 lambda 生成条件约束），而每条约束在传播中最多让 O(n) 个元素流过，合起来约 O(n³)。Nielson & Seidl 有专文《Control-Flow Analysis in Cubic Time》系统给出这一界。要注意 n³ 是最坏情形上界，实际程序远快；且"立方"依赖于把分析写成上面这种单调集合约束——若像 Henglein 观察的那样把包含约束 ⊆ 换成等式约束（用**合一 unification** 求解，相当于 Steensgaard 式而非 Andersen 式），可以做到近线性时间，但精度更低，是速度/精度的又一个权衡点。这里"约束求解算法与其复杂度"的通用引擎，正是 V6 的主题，本节点名不展开。

## V3.4 上下文敏感度

### V3.4.1 为什么要上下文敏感：0-CFA 的精度天花板

0-CFA 因为"每个变量只有一块白板"，会把一个函数在不同调用处的信息**合并**，导致精度损失。上下文敏感分析（context-sensitive）为同一个函数/变量在**不同调用上下文**下维护**多块**白板，从而区分开互不相干的调用——这类"一变量多版本"的分析叫**多变量分析（polyvariant）**。

用最经典的恒等函数例子体会 0-CFA 的天花板：

let id = fn x => x^1 in ((id^2 g^3)^4 ; (id^5 h^6)^7)

两处分别用函数 g、h 调用 id。0-CFA 只有一块 ρ̂(x)，于是它同时装下 g 和 h，进而认为**两处**调用的返回都可能是 {g, h}——第一处本该只返回 g，却被第二处的 h 污染。这种跨调用的串味就是单变量分析的固有缺陷。上下文敏感的修法是：给 id 的每次调用配一个不同的"上下文标记"，让 x 在"从点 4 调进来"和"从点 7 调进来"两种上下文下各有一块白板，互不干扰。

初学者要建立的直觉：上下文敏感 ≈ 对被调函数按调用来源做"分身"。分身越细，精度越高，但白板数量（状态空间）也越膨胀——这是下面 k 这个旋钮要平衡的东西。

### V3.4.2 k-CFA：用长度 k 的调用串做上下文

k-CFA 是 Shivers 提出的上下文敏感 CFA 家族，用**调用串（call string）**——即"最近 k 个调用点的序列"——作为区分上下文的标记，称为**contour（轮廓）**。抽象缓存/环境因此升级为按 (程序点/变量, 上下文) 两维索引：

Ĉ : (Lab × Δ) → P(Term × Δ)

ρ̂ : (Var × Δ) → P(Term × Δ)

其中 Δ 是长度 ≤ k 的调用串（contour）集合；k=0 时 Δ 退化为单点，k-CFA 就还原成 V3.2 的 0-CFA。

理解 k 这个旋钮最省事的图像：k 是"记忆多少层调用历史"。0-CFA 记 0 层（谁调的都一样对待）；1-CFA 记最近 1 个调用点（能区分"从点 4 调进来"还是"从点 7 调进来"，从而解决上面 id 的污染）；k-CFA 记最近 k 个调用点。k 越大，同一函数被切成越多分身、精度越高。PPA 讲的这一档（所有 contour 用统一长度 k 的调用串）通常称作 **uniform k-CFA**。

一个初学者极易误解的点：k-CFA 的 k 不是"精确到 k 层就没有近似了"。调用串一旦超过 k 就被截断（只保留最近 k 个），超过 k 层的历史仍被合并，所以 k-CFA 对任意 k 都仍是 sound 过近似、仍会有精度损失，只是损失随 k 增大而减小。另一处措辞差异：文献里 monovariant=0-CFA=上下文不敏感、polyvariant=k≥1=上下文敏感，"variance"指的是"同一程序实体是否有多个分析版本"，别和类型系统里协变/逆变（variance）混为一谈——同词不同义。

### V3.4.3 精度与代价：k-CFA 的复杂度爆炸

上下文敏感是有代价的：随 k 增大，contour 数量指数增长，分析代价迅速爆炸。0-CFA 是多项式（立方，V3.3）时间；而对任意 k ≥ 1，判定 k-CFA 结果被证明是 **EXPTIME-complete（确定性指数时间完全）**——不存在多项式算法。

这条复杂度界由 Van Horn & Mairson《Deciding kCFA is complete for EXPTIME》(ICFP 2008) 给出，是 k-CFA "精度贵得惊人"的形式化坐实。

对初学者，这里有个值得记住的反直觉现象，文献称"k-CFA 悖论"：在函数式语言里从 0-CFA 跨到 1-CFA，复杂度从多项式直接跳到指数；但在面向对象语言里，类似的 k-object-sensitive 上下文敏感指针分析却常有多项式实现。原因在于两种语境下"上下文"绑定的对象不同（函数闭包环境 vs 对象抽象），Might/Smaragdakis/Van Horn 有专文剖析（PLDI 2010）。实践中的结论很朴素：k=1 或 k=2 往往已能显著提精度，但 k 再大通常算不动，工程上极少用大 k；要更强的上下文敏感常改走别的建模（如对象敏感、类型敏感）而非一味加大 k。这一节点名即止，专家级机制不深挖。
