模型检验（model checking）回答一个非常具体的问题：**给定一个有限状态系统的模型 M 和一条用时序逻辑写的性质 φ，M 是否满足 φ？** 若不满足，工具还会吐出一条**反例**（counterexample）——一条真实展示"性质怎样被违反"的执行轨迹。它和本课前半场（数据流分析、抽象解释、符号执行）的根本区别在于：前者是"对程序做保守近似的静态分析"，模型检验则是**对一个有限状态空间做穷尽的、算法化的判定**——原则上能给出"是/否 + 反例"的确定答案，代价是系统必须（先被抽象成）有限状态，且状态数可能爆炸。

一条贯穿全大主题的心智模型：**模型检验 = 把系统画成一张"状态图"（Kripke 结构），把要求写成一条"随时间演化的逻辑公式"（时序逻辑），然后让算法在图上穷举/搜索，判断图里所有（或某条）路径是否都满足公式**。抓住"状态图 + 时序公式 + 穷尽搜索"这三件事，就抓住了模型检验的全部骨架；剩下的技术（显式 vs 符号、BDD vs SAT、抽象精化）都是为了对抗同一个敌人——**状态爆炸**。

## V8.1 时序逻辑 LTL/CTL

### V8.1.1 为什么要用时序逻辑规约性质

普通命题/谓词逻辑只能谈"某个状态此刻是否成立"，无法表达"**永远不会**死锁""请求后**最终一定**被响应"这类跨越时间的要求。时序逻辑（temporal logic）在命题逻辑之上加入**时序算子**，让公式的真值定义在一条（或一棵）**执行随时间展开的轨迹**上，从而能规约系统"随时间如何演化"的性质。模型检验里两大主流是**线性时序逻辑 LTL**（Linear Temporal Logic，Pnueli 1977）和**计算树逻辑 CTL**（Computation Tree Logic，Clarke & Emerson 1981）。

对初学者，先记住二者的世界观差异：**LTL 看"线"，CTL 看"树"**。LTL 的公式在**单条无限执行路径**上求值，一个系统满足 LTL 公式 φ 当且仅当它的**每一条**可能路径都满足 φ——时间被看成一条确定的线。CTL 则显式地谈"分叉"：从一个状态出发有多条未来路径，CTL 用**路径量词** A（沿所有路径）和 E（存在某条路径）去量化这些分叉，公式在**状态**（一棵计算树的根）上求值。这个"线 vs 树"的区别是后面表达力差异（V8.1.6）的根源。

### V8.1.2 LTL 语法与时序算子

LTL 公式在原子命题（atomic proposition，记作 p、q…，来自集合 AP）和布尔联结词（¬、∧、∨、→）之上，加入下列时序算子构成：

```
X φ      （Next：下一步 φ 成立）
F φ      （Future / Eventually：将来某一步 φ 成立）
G φ      （Globally / Always：从现在起每一步 φ 都成立）
φ U ψ    （Until：ψ 将来某步成立，且在那之前每一步 φ 都成立）
φ R ψ    （Release：ψ 一直成立，直到 φ 首次成立的那一步——φ "释放"了 ψ；R 是 U 的对偶）
φ W ψ    （Weak Until：像 U，但允许 ψ 永不成立、φ 一直成立）
```

其中 X、U 是**基本算子**，其余可由它们导出：

```
F φ  ≡  true U φ
G φ  ≡  ¬ F ¬φ  ≡  false R φ
φ R ψ  ≡  ¬(¬φ U ¬ψ)
```

初学者最该建立的直觉，是把一条执行路径想成时间轴上一串状态 s₀ s₁ s₂ …。X 是"把镜头右移一格"；F 是"未来至少一格为真"（存在量词）；G 是"未来每一格都为真"（全称量词）；U 是最强的原语——"ψ 迟早发生，且在此之前 φ 不许断"。一个高频记法陷阱：**很多教材（如 Baier-Katoen）用符号 ○=X、◇=F、□=G**（○ next、◇ diamond=eventually、□ box=always），Clarke 书与本报告用字母 X/F/G；同一算子两套写法，读原书时以该书的符号表为准（冲突见本章末）。另一个易错点：R（release）的方向——ψ 必须**从头一直真到** φ 首次为真的那一刻（含该刻），若 φ 永不为真则 ψ 必须永远真。

### V8.1.3 LTL 的语义（定义在无限路径上）

设 π = s₀ s₁ s₂ … 是一条无限路径，πⁱ 记从第 i 个状态起的后缀 sᵢ sᵢ₊₁ …。LTL 满足关系 ⊨ 的核心条款为：

```
π ⊨ p        当且仅当  p ∈ L(s₀)                （原子命题看首状态的标记）
π ⊨ X φ      当且仅当  π¹ ⊨ φ
π ⊨ F φ      当且仅当  存在 j ≥ 0，πʲ ⊨ φ
π ⊨ G φ      当且仅当  对所有 j ≥ 0，πʲ ⊨ φ
π ⊨ φ U ψ    当且仅当  存在 j ≥ 0，πʲ ⊨ ψ，且对所有 0 ≤ k < j，πᵏ ⊨ φ
```

系统 M（初始状态 s₀）满足 LTL 公式 φ，记

```
M ⊨ φ   当且仅当   从 s₀ 出发的每一条无限路径 π 都有 π ⊨ φ
```

要点在于，LTL 公式本身**不带路径量词**——量化"所有路径"是在 M ⊨ φ 这一层默认加上的（隐含全称）。所以 LTL 天然表达的是"所有执行都……"的性质。为什么路径要求是**无限**的？因为 G/F 这类性质要谈"永远/最终"，需要一条走不完的轨迹；有限系统里通过在终止状态加自环（或按 V8.2 的全关系约定）把有限执行补成无限。最小例子：`G ¬crash`（永不崩溃，安全性）要求每条路径每一格都 ¬crash；`G(req → F ack)`（每次请求最终被响应，响应性）是 U/F 嵌套的典型规约。

### V8.1.4 CTL 语法：路径量词 + 时序算子成对出现

CTL 的关键语法约束：**每个时序算子（X/F/G/U）前面必须紧跟一个路径量词（A 或 E）**，二者成对构成 CTL 的时序模态。八个组合是：

```
EX φ     存在一条后继路径，下一步 φ         AX φ     所有后继路径，下一步 φ
EF φ     存在一条路径，将来某步 φ           AF φ     所有路径，将来都会 φ
EG φ     存在一条路径，全程 φ               AG φ     所有路径，全程 φ
E[φ U ψ] 存在一条路径满足 φ U ψ             A[φ U ψ] 所有路径都满足 φ U ψ
```

其中一组**足够表达其余全部**（adequate set）。Clarke 书常用的一组基是 EX、EG、EU（其余由布尔运算与对偶导出）：

```
AX φ  ≡  ¬ EX ¬φ
EF φ  ≡  E[true U φ]
AG φ  ≡  ¬ EF ¬φ  ≡  ¬ E[true U ¬φ]
AF φ  ≡  ¬ EG ¬φ
A[φ U ψ]  ≡  ¬E[¬ψ U (¬φ ∧ ¬ψ)] ∧ ¬EG ¬ψ
```

初学者理解"成对出现"的意义：CTL 把"选哪条未来路径（A/E）"和"在那条路径上看什么时间性质（X/F/G/U）"打包成一个不可拆的模态。所以 `AG p` 读作"沿所有路径、每一格 p 都真"，`EF p` 读作"存在一条路径、将来能到 p 的状态"。一个高频的经典性质 `AG(EF restart)`——"从任何可达状态出发，总**存在**一条路回到 restart（可复位性）"——正好嵌套了 A…E…，这个式子后面会证明 LTL 写不出来。易错点：**不能写裸的 `F p` 或 `G(F p)` 当作 CTL 公式**——CTL 里 F/G 前必须有 A 或 E；`G F p` 这种"无量词嵌套"是 LTL（或 CTL*）的合法式，不是 CTL 的。

### V8.1.5 CTL 的语义（定义在 Kripke 结构的状态上）

CTL 公式在**状态**上求值（对比 LTL 在路径上）。设 M 为 Kripke 结构（见 V8.2），s 为状态，核心条款：

```
M, s ⊨ p          当且仅当  p ∈ L(s)
M, s ⊨ EX φ       当且仅当  存在 s 的后继 s'，M, s' ⊨ φ
M, s ⊨ AX φ       当且仅当  s 的所有后继 s' 都有 M, s' ⊨ φ
M, s ⊨ EG φ       当且仅当  存在一条从 s 出发的路径，其上每个状态都 ⊨ φ
M, s ⊨ AF φ       当且仅当  从 s 出发的每条路径上都存在某状态 ⊨ φ
M, s ⊨ E[φ U ψ]   当且仅当  存在一条从 s 出发的路径，其上 φ U ψ 成立
```

系统满足性定义为初始状态满足：M ⊨ φ 当且仅当对每个初始状态 s₀，M, s₀ ⊨ φ。

一个直觉锚点，是把从 s 展开的所有可能执行摊成一棵**计算树**（computation tree，s 为根、每个分叉是一次非确定选择）。E 是"树里存在一根这样的枝"，A 是"树里每一根枝"。这正是 CTL 名字（Computation Tree Logic）的由来，也解释了为什么它能谈"分叉可能性"而 LTL 不能——LTL 只盯单条枝。最小例子：`M, s ⊨ EF p` 当且仅当从 s 在状态图里**可达**某个标了 p 的状态（"存在路径到 p"）——这直接等价于图可达性，是 V8.4 里 EF 用最小不动点计算的原因。易错点：`AF p` 要求**每条路径都最终到 p**，包含"每条路径都不会永远绕开 p"；一条卡在 ¬p 自环里的路径就能证伪 AF p。

### V8.1.6 LTL 与 CTL 的表达力：互不包含，CTL* 统摄

一个反直觉但极重要的结论：**LTL 和 CTL 的表达力互不包含（incomparable）**——各有对方写不出的性质；把二者合并放松语法约束得到的 **CTL\*** 严格强于两者。两个标志性分界例子：

```
AG (EF p)   —— CTL 能写，LTL 写不出（"从任意可达状态都存在路径回到 p"，可复位性）
F G p       —— LTL 能写（"最终永远 p"），其自然 CTL 译文 AF AG p 与它不等价，且 FG p 无 CTL 等价式
```

初学者理解这一冲突的关键在于，`AG EF p` 谈的是"**存在某条未来路径**能到 p"这种分叉可能性，LTL 只谈单条线、无法量化"存在一条路"，所以写不出。反过来 `FG p` 谈的是"沿这条线，从某点起 p 永远真"——CTL 的 `AF AG p` 要求"每条路径都在某状态进入 AG p（即那点之后每条分叉都永远 p）"，这比 FG p 强，二者在含分叉的模型上会分道扬镳，可构造 Kripke 结构使一者成立另一者不成立。CTL\* 去掉"算子前必须紧跟量词"的限制，允许 `A(FG p)`、`E(GF p)` 这类量词后跟任意 LTL 式，于是同时涵盖 LTL（= 全部路径量词为 A 的 CTL\* 子集）与 CTL。这条表达力关系是选逻辑与选算法的现实依据：CTL 有线性时间检验算法（V8.3.2），LTL 检验是关于公式 PSPACE 完全（V8.3.3），工程上按性质形态取舍。

### V8.1.7 常见性质模式：安全性、活性、公平性

时序逻辑在实践中最常落到三类性质模式：

```
安全性 (safety)   ：G ¬bad  /  AG ¬bad        —— "坏事永不发生"；违反必有有限前缀见证
活性 (liveness)   ：G(req → F ack)  /  AG(req → AF ack) —— "好事最终发生"；违反是无限轨迹
公平性 (fairness) ：G F enabled → G F taken   —— "无限次使能则无限次执行"，用于排除病态调度
```

先看三者的分工。**安全性**说"never 某坏状态"，它的反例总是一条**有限**路径（走到坏状态即止，见 V8.5.2），因此最容易检验；**活性**说"eventually 某好事"，反例是一条**无限**路径（好事永不来，即绕圈躲开），需要 lasso 形式的反例。**公平性**不是被检验的目标性质，而是加在系统上的**假设**——用来排除"调度器永远饿死某进程"这类不现实的路径，否则很多活性性质会被病态路径伪证伪。一个关键落差：**LTL 能把公平性直接写进公式**（如 `(G F enabled) → (G F taken)`），而 **CTL 在逻辑内无法表达公平性**——必须改用"公平 CTL（fair CTL）"语义，把公平约束附在 Kripke 结构上、重新定义 A/E 只量化公平路径。这是 CTL 相对 LTL 的一个实务短板，也是很多工具同时支持"公平约束 + CTL"的原因。

## V8.2 Kripke 结构与状态空间

### V8.2.1 Kripke 结构的定义

模型检验里"被检验的系统"标准建模为 **Kripke 结构**（Kripke structure）——一个带状态标记的有向图。Clarke 书定义：给定原子命题集 AP，Kripke 结构是四元组

```
M = (S, S₀, R, L)
```

其中

```
S           有限状态集合
S₀ ⊆ S      初始状态集合
R ⊆ S × S   迁移关系，且要求是全关系（total）：每个状态至少有一个后继，∀s ∃s'. (s,s') ∈ R
L : S → 2^AP  标记函数，给每个状态标出在该状态成立的原子命题集合
```

初学者不妨把 Kripke 结构看成"一张状态图 + 每个圈里写着此刻为真的命题"。节点是系统的**全局状态**（所有变量取值的一个快照），边是"一步可能的迁移"，节点标签 L(s) 说明"在 s 这个状态，哪些原子命题成立"。时序逻辑公式就在这张图上求值：LTL 沿图中路径、CTL 在图中状态。一个必须记牢的约定：**R 是全关系**——Clarke 要求每个状态都有后继，好让每条路径都能无限延伸（LTL 的 G/F 需要无限路径）；对真实会终止的系统，做法是给终止状态加一条**自环** (s,s)，把"停在这"表达成"永远重复这个状态"。

### V8.2.2 迁移系统：Kripke 结构的近亲（记法分歧）

Baier & Katoen 用的基础模型叫**迁移系统**（transition system, TS），比 Kripke 结构多带**动作**（action）标签：

```
TS = (S, Act, →, I, AP, L)
```

其中 → ⊆ S × Act × S 是带动作的迁移关系，I 是初始状态集，其余同上。二者本质是同一类对象的两种写法：Kripke 结构把标记放在**状态**上、迁移无标签且要求全关系；Baier-Katoen 迁移系统把标签放在**动作/迁移**上、允许**终止状态**（无后继）。

关键在于，这不是两种不同的数学，只是侧重不同——**状态标记（Kripke）适合谈"系统处于什么状况"，动作标记（LTS/TS）适合谈"系统发生了什么事件"**。做 CTL/LTL 检验时用状态标记更顺（公式谈的是状态命题），所以 Clarke 传统用 Kripke 结构；过程代数与 SPIN/Promela 等更偏动作视角。二者可互相转换（把动作编码进状态、或反之）。初学者不必纠结选哪个，认清"节点=状态、边=迁移、标签=此刻成立的命题"这个核心即可。一个易错点在**全关系要求上的分歧**：Clarke 强制全关系（无终止），Baier-Katoen 允许终止状态并单独处理——比对两书时留意这条（冲突见章末）。

### V8.2.3 路径与计算树

在 Kripke 结构上，从状态 s 出发的**路径**（path）是一条无限状态序列

```
π = s₀ s₁ s₂ …   其中 s₀ = s 且对所有 i，(sᵢ, sᵢ₊₁) ∈ R
```

把从 s 出发的所有路径按分叉全部摊开，得到以 s 为根的**计算树**（computation tree）——LTL 在单条路径 π 上求值，CTL 在整棵树上（通过 A/E 量化枝）求值。

直观地说，路径是"系统一次具体的无限运行"，计算树是"从当前状态出发所有可能运行的总和"。全关系保证每条路径都能无限走下去（不会走到死胡同断掉），从而 G/F/U 这些"谈无限未来"的算子有良好定义。最小例子：若状态图是 s₀→s₁、s₀→s₂、s₁→s₁（自环）、s₂→s₂，则从 s₀ 出发有两条无限路径 s₀s₁s₁… 与 s₀s₂s₂…，计算树在 s₀ 处分两枝。`EF p`（存在路径到 p）只要有一枝碰到 p 即真；`AF p` 要两枝都碰到 p 才真。易错点：路径允许**重复状态**（有限图上的无限路径必然从某处开始循环，形成"lasso"，这是 V8.5 反例的形状）。

### V8.2.4 从程序/并发系统到 Kripke 结构的建模

真实系统（变量、并发进程）如何变成有限 Kripke 结构？标准做法：**全局状态 = 所有变量取值 + 各进程的程序计数器（PC）的一个组合；迁移 = 一步可执行的语句/动作**。原子命题就是关于变量/PC 的谓词，如 `pc₁ = critical`、`x > 0`。

初学者要抓的是**状态数的来源**：n 个布尔变量就有 2ⁿ 个变量组合；k 个并发进程各有若干局部状态，全局状态是它们的**笛卡尔积**，且并发带来**交错（interleaving）**——每一步可以是任一进程动作，路径数进一步暴涨。这正是"状态爆炸"（V8.3.5）的建模级根源。一个最小例子：两个进程各有 `idle/wait/crit` 三个局部状态，忽略变量则全局状态最多 3×3=9 个；一旦加一个共享布尔锁又 ×2。易错点：建模时若变量取值域无限（整数、堆、递归），Kripke 结构就**不是有限**的——此时必须先做**抽象**（V8.5.3）把它压成有限，否则模型检验（作为有限状态判定）根本不适用。这条把 V8 和本课前半场的抽象解释接上了：抽象是让模型检验落地的前置手术。

### V8.2.5 原子命题与标记函数的角色

原子命题集 AP 与标记 L 是**连接"系统"与"逻辑"的唯一接口**——时序逻辑公式只能谈 AP 里的命题，L(s) 决定每个状态里哪些命题为真，检验算法完全靠 L 判断"这个状态是否满足某原子命题"。

关键在于，**选什么进 AP，等于选择"从系统里能观察到什么"**。若你想检验"互斥"，AP 里就得有 `p₁_in_crit`、`p₂_in_crit`，性质写成 `AG ¬(p₁_in_crit ∧ p₂_in_crit)`；AP 里没有的信息，逻辑就谈不了。这也解释了标记函数为何是"状态→命题集合"而非"命题→真假"：一个状态可以同时使多个命题为真。易错点：AP 粒度取太粗会漏掉想检验的性质，取太细会放大状态标记开销与抽象难度——AP 的选择本身是建模决策的一部分。这一点与 V8.5 的抽象直接相关：谓词抽象（predicate abstraction）正是"用一组谓词当 AP、按谓词真值给状态分类"的手术。

#### 来源与时效
- Clarke/Grumberg/Peled《Model Checking》Ch.2「Modeling Systems」——Kripke 结构四元组 (S, S₀, R, L)、R 为全关系的要求、路径与计算树、由并发程序建模。核实 2026-07-30。
- Baier & Katoen《Principles of Model Checking》Ch.2「Modelling Concurrent Systems」——迁移系统 TS = (S, Act, →, I, AP, L)、动作标记、允许终止状态、交错语义与并发状态空间。第二独立一手。
- 原始论文：Kripke 1963（模态逻辑可能世界语义，Kripke 结构名称之源）；Clarke-Emerson-Sistla 1986（TOPLAS）给出模型检验语境下的结构化定义。
- 冲突/分歧：**全关系要求**——Clarke 要求 R 全关系（每状态有后继，终止用自环），Baier-Katoen 迁移系统允许终止状态并单独处理终止路径。**标记位置**——Kripke 结构标状态（state-labeled），LTS/迁移系统标动作/迁移（action-labeled）。二者可互转，本报告以状态标记的 Kripke 结构为主叙述。

## V8.3 显式状态检验与状态爆炸

### V8.3.1 显式状态检验的基本盘：把状态一个个建出来

**显式状态模型检验**（explicit-state model checking）逐个枚举可达状态、显式存进内存（哈希表），用 DFS/BFS 遍历状态图。可达性（reachability）本身就能回答最基本的安全性："坏状态可达吗？"——从初始状态搜，碰到坏状态即报违反并给出搜索路径作反例。

初学者对照 V8.4 的符号法理解"显式"：显式法**一次处理一个状态**，内存里存的是"状态的集合，每个状态是一条具体记录"；符号法一次处理"一批状态"（用公式/BDD 表示状态集合）。显式法直观、易做 on-the-fly、易生成具体反例，是 SPIN 的路线；缺点是状态数一大内存就爆（V8.3.5）。最小心智模型：显式安全性检验 ≈ 在状态图上做一次图搜索，`bad` 命中即停。

### V8.3.2 CTL 显式检验：自底向上的标记算法（线性时间）

CTL 的显式检验用**标记算法**（labeling / marking）：对公式 φ 的每个子公式，按语法结构**从最内层往外**，在每个状态上标注"该子公式在此状态是否成立"，最后看初始状态是否标上了 φ。关键子过程：

```
标 EX ψ  ：凡有一个后继已标 ψ 的状态，标 EX ψ            （一步回推）
标 E[ψ₁ U ψ₂] ：从已标 ψ₂ 的状态出发沿逆向边回推，途经状态若标 ψ₁ 则标之（最小不动点）
标 EG ψ  ：在"ψ 成立的子图"里找非平凡强连通分量(SCC)，能到达 SCC 的状态标 EG ψ（最大不动点）
```

整体复杂度是**线性**的：

```
O( |φ| · (|S| + |R|) )
```

即公式大小乘以状态图大小。理解为什么 CTL 检验这么便宜：CTL 公式在**状态**上求值，每个子公式对每个状态只需看它的直接后继（一步局部信息），配合不动点迭代/SCC 一遍图即可定死；不需要像 LTL 那样在"路径"这种指数多的对象上推理。这条线性结果（Clarke-Emerson-Sistla 1986）是 CTL 在工业界流行的核心原因。易错点：这里的"线性"是相对**状态图规模** |S|+|R| 而言，而状态图本身可能对系统描述是指数大的（状态爆炸）——两个"指数/线性"说的不是同一层，别混。

### V8.3.3 LTL 显式检验：自动机理论法（Vardi-Wolper）

LTL 检验走**自动机理论路线**（automata-theoretic approach，Vardi & Wolper 1986）。核心三步：

```
1. 把待检性质取反 ¬φ，构造一个接受"违反 φ 的无限字"的 Büchi 自动机 A_{¬φ}
2. 把系统 M（看成生成无限字的自动机）与 A_{¬φ} 做乘积 M × A_{¬φ}
3. 检查乘积自动机的语言是否为空：若非空（存在被接受的无限运行），该运行就是违反 φ 的反例；若为空，则 M ⊨ φ
```

语言非空 ⟺ 乘积图里存在一条**从初始状态可达、且经过某个接受状态无限多次**的路径——在有限图上等价于"存在一个含接受状态的可达环"（lasso）。复杂度：

```
O( |M| · 2^{O(|φ|)} )   —— 对系统线性，对公式指数（LTL 检验是关于公式 PSPACE 完全）
```

初学者不妨这样建立直觉——Büchi 自动机是"能接受无限长输入的有限自动机"，接受条件是"某接受状态被访问无限多次"——正好匹配 LTL 的 G/F（无限未来）语义。为什么取反 ¬φ？因为"M 满足 φ"⟺"M 没有任何违反 φ 的执行"⟺"M 与'违反 φ 的执行集合'的交为空"，把 φ 取反后交空检测就成了标准的自动机空性检查。这解释了 LTL 反例天然是 lasso（无限路径的有限表示，V8.5.2）。易错点：对公式的 2^|φ| 是因为 ¬φ 的 Büchi 自动机可能指数大；实务中公式短，这项常不成瓶颈，真正的敌人还是 |M|（状态爆炸）。

### V8.3.4 on-the-fly（边搜边建）与嵌套 DFS

**on-the-fly**（就地/惰性）检验：不预先把整个状态图/乘积自动机建完，而是**在搜索过程中按需生成**后继，一旦发现反例立刻停——常常不必展开整个状态空间就能报错。空性检查（找可达接受环）用**嵌套深度优先搜索**（nested DFS，Courcoubetis-Vardi-Wolper-Yannakakis 1992）：外层 DFS 找接受状态，对每个接受状态启动内层 DFS 看能否回到自己（成环）。

初学者理解 on-the-fly 的价值：**找 bug 时你只想尽快撞到反例，不想先花光内存把没用的状态全建出来**。若性质被违反，边搜边判往往在展开一小部分状态时就命中，这对"证伪"极友好（对"证明性质成立"则仍需走遍可达状态）。SPIN 就是 on-the-fly + 嵌套 DFS 的代表实现（工具本机未装，未验证）。嵌套 DFS 之所以要"嵌套"：判断"接受状态是否在环上"需要从它再搜一次看能否绕回自身，两层 DFS 用颜色标记避免重复、把内存压到与状态数同阶。易错点：嵌套 DFS 的正确性依赖外层 DFS 的后序访问次序，实现细节微妙——概念上记住"外层找接受态、内层验成环"即可。

### V8.3.5 状态爆炸问题（本大主题的头号敌人）

**状态爆炸**（state explosion）：系统的状态数随其描述规模（变量数、并发进程数）**指数增长**，显式枚举因此内存/时间双爆。两条主要来源：

```
数据爆炸 ：n 个布尔变量 → 2ⁿ 个状态（k 个进程各 m 状态 → 全局最多 mᵏ）
交错爆炸 ：并发进程的独立动作以任意先后交错 → 路径/状态组合数进一步指数放大
```

理解这是模型检验"能不能用"的生死线：一个含 30 个布尔变量的模块就有约 10⁹ 个状态，显式存储直接吃光内存。**整个后续技术栈（V8.4 符号法、偏序/对称归约、V8.5 抽象）都是为对抗它而生**。初学者常见误解："模型检验是穷举，所以只对玩具系统有用"——一半对：朴素显式穷举确实受限，但符号表示（BDD 能压缩 10²⁰ 状态，见 V8.4）、抽象与归约把可处理规模推高了许多个数量级。记住定位：状态爆炸不是被消灭了，而是被各种表示/归约技术**推后**了。

### V8.3.6 缓解显式爆炸：偏序归约、对称归约、位状态哈希

在不切换到符号表示的前提下，显式检验有几类经典缓解手段：

```
偏序归约 (partial order reduction) ：并发中独立动作的不同交错常等价，只探一个代表交错，剪掉冗余排列
对称归约 (symmetry reduction)      ：进程/组件对称时，把对称等价的状态归并成商结构，按等价类搜
位状态哈希 (bitstate hashing)       ：用位数组近似存"访问过的状态"，牺牲完备性换极低内存（可能漏状态）
```

初学者要抓的是每种手段的取舍。**偏序归约**利用"并发里 a 和 b 若互不影响，先 a 后 b 与先 b 后 a 到达同一状态"，只保留一种顺序——对存有大量独立交错的并发系统削减极大，且**保持**所检性质（对不涉及交错次序的性质是可靠的）。**对称归约**利用"把进程 1 和进程 2 互换，系统行为同构"，只需检一个代表——需要能自动/人工识别对称。**位状态哈希**（Holzmann，SPIN 的 supertrace）是"内存不够时的近似战术"：哈希冲突会把不同状态当成同一个而漏搜，因此它可能**漏报**（找不到本该报的反例），是拿完备性换覆盖率的赌注。易错点：前两者在其适用假设下**不损可靠性**，位状态哈希则**牺牲完备性**——用途完全不同，别混为一谈。

#### 来源与时效
- Clarke/Grumberg/Peled《Model Checking》Ch.4「CTL Model Checking」（标记算法、EX/EU/EG 的 SCC 与不动点、O(|φ|·(|S|+|R|)) 线性界）、Ch.9「Partial Order Reduction」、Ch.14「Symmetry」。核实 2026-07-30。
- Baier & Katoen《Principles of Model Checking》Ch.6.4（CTL 显式算法）、Ch.4.4 与 Ch.5.2（LTL 的 Büchi 自动机法、乘积与持久性/空性检查）、Ch.8「Partial Order Reduction」。第二独立一手。
- 原始论文：Vardi & Wolper 1986《An Automata-Theoretic Approach…》(LTL 自动机法一手)；Courcoubetis-Vardi-Wolper-Yannakakis 1992（嵌套 DFS/memory-efficient）；Clarke-Emerson-Sistla 1986（CTL 线性算法一手）；Sistla & Clarke 1985（LTL 检验 PSPACE 完全）；Peled 1994 / Godefroid（偏序归约）；Clarke-Filkorn-Jha 1993、Emerson-Sistla 1993（对称归约）；Holzmann（SPIN、bitstate hashing）。

## V8.4 符号模型检验

### V8.4.1 符号表示的动机：不再一个个存状态

**符号模型检验**（symbolic model checking，Burch-Clarke-McMillan-Dill-Hwang 1990；McMillan 1993 的 SMV）不再显式枚举单个状态，而是用**布尔公式**表示"状态集合"和"迁移关系"，用集合运算（而非逐状态遍历）完成检验。一组状态用其**特征函数**（characteristic function）表示——一个布尔函数，输入状态变量、输出该状态是否在集合中。

初学者要抓的核心转变在于，显式法内存里是"一堆具体状态记录"，符号法内存里是"一个描述集合的公式"。为什么这能对抗状态爆炸？因为**一个紧凑的公式可以描述天文数字的状态**——正如 `x > 0` 一句话描述了无穷多个正数，一个布尔公式能一次性代表 10²⁰ 个状态而不必逐个列出。BCM 那篇论文标题"10²⁰ States and Beyond"正是这个卖点。关键是：迁移关系 R(s, s')、初始集、以及"满足子公式的状态集"全部编码成布尔函数，检验就变成布尔函数的运算。

### V8.4.2 BDD / OBDD：布尔函数的紧凑规范表示

符号检验第一代的核心数据结构是**（有序）二叉决策图 OBDD**（Ordered Binary Decision Diagram，Bryant 1986）——把布尔函数表示成一张压缩的决策图。在**固定变量序**下、施加两条约简规则（合并同构子图、删去冗余判定节点）后，OBDD 是布尔函数的**规范形式**（canonical）：同一函数在同一变量序下有唯一的约简 OBDD。

关键在于，规范性带来两个红利——判断两个状态集是否相等（不动点是否到达）只需比较 BDD 是否同一，判断某集合是否为空只需看它是不是常量 0，都是 O(1)/近乎常数。集合的交并补、"存在量化"（用于计算前像/后像）都有标准 BDD 算法。最小直觉：BDD 像"共享子表达式的真值表"，把指数大的真值表折叠成常常是多项式大小的图。**致命易错点：BDD 的大小对变量序极其敏感**——好的序能把某函数压成线性，坏的序能让同一函数炸成指数；变量序选取（自动/启发式）是符号检验能否跑动的关键工程难题。此外某些函数（如乘法器的中间位）**任何变量序下 BDD 都是指数**，这是 BDD 法的固有天花板，也是后来 BMC 用 SAT 绕开 BDD 的动机。

### V8.4.3 符号 CTL 检验：不动点刻画 + BDD 迭代

符号 CTL 检验把 V8.3.2 的标记算法重写成**集合的不动点迭代**——每个 CTL 模态对应一个 μ（最小不动点）或 ν（最大不动点）方程，迭代过程全用 BDD 上的集合运算完成：

```
EX p   =  Pre∃(⟦p⟧)                       （p 集合的前像：能一步到 p 的状态）
EF p   =  μZ. ⟦p⟧ ∨ EX Z                   （最小不动点：不断把"能一步到已知集合"的状态并进来）
EG p   =  νZ. ⟦p⟧ ∧ EX Z                   （最大不动点：反复剔除"无法在 p 内续命"的状态）
E[p U q] = μZ. ⟦q⟧ ∨ (⟦p⟧ ∧ EX Z)
```

其中 ⟦·⟧ 表示"满足该子公式的状态集合"，Pre∃（前像）用迁移关系 R 的存在量化在 BDD 上算出。迭代从 ⊥（或 ⊤）起，反复套用直到集合不再变化（BDD 相等即到达不动点）。

初学者对接 V2/V4 的不动点：这正是本课反复出现的"单调函数在完全格上的不动点"（Knaster-Tarski），只不过格是"状态集合的幂集"、单调算子是 EX 相关的像运算。为什么 EF 是最小不动点、EG 是最大不动点？EF p 是"可达 p 的状态"，从 p 本身出发不断往回吸收前驱，取**最小**的封闭集合；EG p 是"存在一条永远待在 p 内的路径起点"，从全体 p 出发不断剔除"续不下去"的，取**最大**的封闭集合。易错点：不动点方向（μ vs ν）与算子对应关系是符号检验的核心，记反了结果就错——含"存在无限延续"意味的（EG）用 ν，含"有限步内达成"意味的（EF/EU）用 μ。

### V8.4.4 有界模型检验 BMC：把展开交给 SAT

**有界模型检验**（Bounded Model Checking, BMC；Biere-Cimatti-Clarke-Zhu 1999）绕开 BDD：把迁移关系**展开固定的 k 步**，编码成一条命题逻辑公式，问 **SAT 求解器**"在 k 步内是否存在违反性质的执行"。检验"安全性 G p 是否在 k 步内被违反"（即能否 k 步内到达 ¬p）的 BMC 公式是：

```
I(s₀)  ∧  ⋀_{i=0}^{k-1} R(sᵢ, sᵢ₊₁)  ∧  ⋁_{i=0}^{k} ¬p(sᵢ)
```

这条公式的含义是，s₀ 是初始状态、s₀…s_k 是一条合法的 k 步迁移、且其中某个 sᵢ 违反 p。把它交给 SAT：

```
SAT   → 求解器给出的赋值就是一条长度 ≤ k 的具体反例（一条违反执行）
UNSAT → k 步内无反例（但不排除更长的反例——除非 k 已达完备性阈值，见 V8.4.5）
```

初学者理解 BMC 的定位：**它天生是"找 bug"的利器，不是"证明正确"的**。给定 k，SAT 到反例就铁证违反；UNSAT 只说明"k 步以内没事"。为什么用 SAT 而非 BDD？因为现代 CDCL SAT 求解器（接 V10）极其高效、对 BDD 会爆的函数（如算术/乘法）也常能扛住，且不需要费心选变量序。工程流程通常是**从小 k 递增**：k=1,2,3,… 逐步加深，先抓浅 bug。一般 LTL（含 G/F 的活性）BMC 要额外加"loop 条件"把无限 lasso 反例编码进有界公式。易错点：BMC 的 UNSAT **不等于**性质成立——把 BMC 当完备证明用是常见错误（补救见下节）。

### V8.4.5 完备性阈值与 k-归纳：把 BMC 变成证明

要让 BMC 从"找 bug"升级为"证明性质成立"，需要一个**完备性阈值**（completeness threshold）——一个足够大的 k，使"k 步内无反例"能推出"永远无反例"。对安全性，这个阈值与状态图的**直径**（diameter，从初始状态到任意可达状态的最短路径的最大值）或 recurrence diameter 相关：只要 k ≥ 阈值且 BMC 得 UNSAT，即证明性质全局成立。另一条实用路线是 **k-归纳**（k-induction）：

```
基础步：I(s₀) ∧ … ∧ (k 步内 p 始终成立)                       —— 前 k 步无违反
归纳步：任意 k+1 长度路径上 p 连续成立 → 第 k+1 步之后 p 仍成立   —— 归纳保持
两步皆 UNSAT（无反例）⟹ G p 成立
```

初学者理解为什么需要这一步：BMC 天然是"有界"的，只查到第 k 步；要跨越"有界→无界"这道坎，要么找到"再深也不会有新状态/新反例"的保证（完备性阈值），要么用归纳把"局部保持"提升为"全局成立"（k-归纳）。k-归纳的直觉与数学归纳一致，只是"归纳假设"用连续 k 步而非单步，以增强归纳的强度（单步归纳常因不变式不够强而失败）。易错点：完备性阈值往往难以精确算出或过大，k-归纳的归纳步可能因缺少辅助不变式而"归纳不出来"（既非 SAT 也非能收敛）——所以实务中 BMC 更多用作高效 bug 猎手，完备证明常回到符号 BDD 检验或配合抽象（V8.5）。

### V8.4.6 SMV / NuSMV：符号检验的代表工具

**SMV**（Symbolic Model Verifier，McMillan 1993）是第一个把 BDD 符号 CTL 检验工程化的工具，其开源重写 **NuSMV**（及后继 **nuXmv**）同时支持 **BDD 引擎**（符号 CTL/LTL）与 **SAT/BMC 引擎**，用 SMV 语言描述有限状态机、写 CTLSPEC/LTLSPEC 性质。

从初学者视角定位，SMV 系工具把 V8.4.2–V8.4.5 的机制打包成可用产品——你写状态机 + 性质，它自动用 BDD 或 BMC 跑并给反例。它与 V8.3 的 SPIN 形成两条工程路线：**SPIN = 显式状态 + on-the-fly + LTL（偏并发协议）**；**NuSMV/nuXmv = 符号（BDD/SAT）+ CTL 与 LTL（偏硬件/同步系统）**。这两个名字与它们代表的技术路线值得记住。本机（@2026-07-30）NuSMV/nuXmv **均未安装**，故其具体命令、版本行为与输出**未做实机验证**；上述定性描述以 McMillan 一手与教材为准，工具细节需安装后复核。

## V8.5 反例与抽象精化

### V8.5.1 反例：模型检验最值钱的产物

模型检验相对其他验证手段的杀手锏是：当 M ⊭ φ 时，它不只答"不满足"，还给出一条**反例**（counterexample）——一条真实违反 φ 的执行轨迹，让工程师能直接沿轨迹定位并复现 bug。这也是模型检验在工业界（尤其硬件、协议）比"只给 yes/no"的方法更受欢迎的核心原因。

反例的价值，对比静态分析就清楚了。静态分析（本课前半场）报"可能有错"时常给不出具体触发路径，让人难以判断真假；模型检验的反例是**一条可回放的具体执行序列**（状态/动作序列），要么直接暴露真 bug、要么（在抽象场景下）暴露抽象太粗（V8.5.5）。反例把"验证失败"从抽象判断变成可操作的调试线索——这是它成为"debugging aid"而不仅是"verification verdict"的关键。

### V8.5.2 反例的形状：安全性=有限前缀，活性=lasso

反例的形状由被违反性质的类别决定：

```
安全性 (G ¬bad) 的反例  ：一条有限路径 s₀ s₁ … s_n，末状态 s_n 违反（到达 bad）——有限、可直接展示
活性 (F good / GF …) 的反例：一条无限路径，good 永不发生；有限图上必为 lasso 形——一段前缀 + 一个环
```

lasso（套索）即"前缀 + 循环"：

```
s₀ … s_i (s_i … s_j)ᵂ      —— 走到 s_i 后在 s_i…s_j 这个环里无限绕，环内始终 ¬good
```

初学者理解为什么两类形状不同：安全性是"坏事永不发生"，一旦坏事发生就**在有限步内**被抓到，反例自然有限。活性是"好事最终发生"，要证伪它必须展示一条"好事**永远**不来"的无限执行——但有限状态图上无限路径必然从某点起循环，于是无限反例被压缩成有限可表示的 lasso（前缀 + 可无限重复的环）。这直接呼应 V8.3.3 里"找可达接受环"的空性检查——那个环就是 lasso 的环部。易错点：别以为反例总是有限的；活性反例本质无限，工具给你的是它的 lasso 表示，读时要理解"括号部分无限重复"。

### V8.5.3 抽象：把无限/过大的系统压成可检验的模型

当系统状态无限（整数变量、堆）或过大时，先做**抽象**（abstraction）——按某种规则把具体状态归并成少量抽象状态，得到一个更小的抽象模型再检验。模型检验最常用**存在抽象**（existential abstraction，over-approximation）：抽象迁移只要具体世界里存在对应迁移就保留，于是抽象模型的行为**包含**具体行为（是过近似）。一种主流实例是**谓词抽象**（predicate abstraction，Graf & Saïdi 1997）：选一组谓词 p₁…p_m 当"观察镜片"，按每个具体状态使这些谓词真/假的组合，把状态划成至多 2ᵐ 个抽象状态。

要点与可靠性在于，**存在抽象保持"全称性质"（ACTL/LTL 的安全性）的可靠性**——若抽象模型上 `AG ¬bad` 成立，则具体系统也成立（因为抽象行为是具体行为的超集，抽象里没有的坏路具体里更没有）。这正是 V1.3"over-approximation ⟹ sound"在模型检验里的落点。反过来，抽象模型上出现的反例**未必是真的**（抽象引入了具体没有的假路径），这就引出 V8.5.5 的 spurious 问题。最小例子：把整数变量 x 抽象成谓词 `x > 0`，则"x=3→x=5"和"x=1→x=2"都归并成同一条"(x>0)→(x>0)"的抽象迁移。易错点：谓词选得太少会过粗（大量假反例），太多会退回状态爆炸——谓词的"够用又不多"正是 CEGAR 要自动求解的。

### V8.5.4 spurious 反例：抽象太粗的信号

在过近似的抽象模型上，检验可能报出一条抽象反例，但它在**具体系统里根本走不通**——这叫**虚假反例/伪反例**（spurious counterexample）。它是过近似的必然副产物：抽象合并状态时引入了具体世界不存在的迁移，抽象路径里可能藏着一段"具体无法衔接"的跳变。

初学者理解 spurious 的来龙去脉：抽象把多个具体状态揉成一个抽象状态后，抽象状态 A→B 的迁移只要"A 里某个具体状态能到 B 里某个具体状态"就成立；但一条抽象反例要求"沿途每一步的具体状态首尾相接成一条真路径"，揉并可能让相邻两步接不上。判断真伪的做法是**把抽象反例映射回具体系统、逐步检查可行性**（常交给 SMT 求解器判路径条件是否可满足，接 V10）：可行则是**真 bug**（连同具体反例一并报告）；不可行则是 spurious，说明抽象太粗、需要精化。易错点：spurious 反例不是工具的错误，而是抽象过程的固有代价——它恰恰是"该往哪里加精度"的宝贵提示，这正是 CEGAR 的燃料。

### V8.5.5 CEGAR 一瞥：反例引导的抽象精化闭环

**CEGAR**（Counterexample-Guided Abstraction Refinement，Clarke-Grumberg-Jha-Lu-Veith 2000）是把"抽象—检验—精化"串成自动闭环的框架，是让模型检验对付大/无限系统的主力方法之一：

```
1. 抽象   ：从初始（粗）抽象构造抽象模型 M̂
2. 检验   ：在 M̂ 上跑模型检验
              · 若 M̂ ⊨ φ         → 性质在具体系统也成立（存在抽象的可靠性），结束
              · 若得反例 ĉ        → 进入第 3 步
3. 验真   ：把 ĉ 映射回具体系统检查可行性
              · 可行             → ĉ 是真反例，报告真 bug，结束
              · 不可行(spurious) → 进入第 4 步
4. 精化   ：分析 ĉ 为何 spurious，加入新谓词/拆分抽象状态以排除这条假路径，回到第 1 步
```

初学者抓 CEGAR 的精髓：**从最省的抽象起步，只在被"假反例"逼问时才加精度，且精度恰好加在能排除这条假反例的地方**——这是一种"按需、由反例导航"的精度投放策略，避免一上来就把所有变量精确建模（那会立刻状态爆炸）。它把 V8.5.2–V8.5.4 的零件（反例、抽象、spurious 判定）组装成一个自我改进的循环：每轮要么给出确定答案（成立/真 bug），要么让抽象变得更聪明一点。这个框架是 SLAM（微软驱动验证）、BLAST 等软件模型检验器的骨架。按本大主题"CEGAR 只作一瞥"的定位，此处不深入精化算法（插值、最弱前条件等）与终止性讨论——记住"反例驱动、按需加谓词、闭环迭代"这三点即可。易错点：CEGAR 循环**不保证终止**（无限状态系统上抽象精化可能无限加谓词也收不敛），它是强大启发式而非判定过程。
