符号执行是这门课"验证半场"里最贴近测试实践的一种技术。它的一句话心智模型是：**不给程序喂具体输入（比如 x = 7），而是喂一个符号（x 就是"任意的 x"），让程序照常跑，只不过所有中间值都变成关于这些符号的公式；每遇到一个 if 分支就把执行"劈成两半"，各自记下"要走这条分支，输入必须满足什么条件"，这个不断累积的条件叫路径条件。** 跑到某个程序点时，只要它的路径条件是"可满足的"，就说明存在一组真实输入能走到这里——把这组输入解出来，就得到一个能精确触发该路径的测试用例。

King 1976 的原始洞察是：**一次符号执行覆盖的不是一条具体执行，而是一整类走同一条路径的执行**。这就是为什么符号执行能自动生成高覆盖测试、能证明某条危险路径不可达、能定位触发崩溃的确切输入。抓住两件事就抓住了全部内核：一是"符号状态 + 路径条件"如何随执行积累（V7.1），二是"路径条件可满足性"如何决定可达并生成输入（V7.4）；中间两节（V7.2、V7.3）都在解决同一个敌人——路径数量爆炸导致朴素做法跑不动。

> 本报告 V7.4 的路径条件可行性结论在如下环境实跑取证：Python 3.11.15 + z3-solver 5.0.0 @2026-07-30，代码仅存 scratchpad、不入库，正文贴真实输出。实证是多来源比对的**补充而非替代**；机制性命题（King 的符号执行语义、KLEE/DART 的算法）以一手论文比对为准，未实证处如实标注。

## V7.1 符号状态与路径条件

### V7.1.1 符号执行的基本思想

符号执行（symbolic execution）是 King 1976 提出的程序分析/测试技术：把程序的输入不当成具体数值，而当成**符号**（symbolic value），程序照常解释执行，只是每个变量存的不再是一个数，而是一个**关于输入符号的表达式**。凡是不依赖分支的普通语句（赋值、算术），符号执行和普通执行没区别，只是把"算出一个数"换成"拼出一个公式"。真正的难点和价值都在条件分支上——一个 `if (c)` 会让执行分裂成"c 成立"和"c 不成立"两条待探索的路径。

初学者可以把它想成"带占位符的心算"。普通执行是"输入 x = 3，算 y = x + 1 得 4"；符号执行是"输入 x = α，算 y = α + 1"，把 α 当成一个不确定的记号一路带下去。这样一次分析就不再绑死在 x = 3 这一个输入上，而是对"所有可能的 x"同时成立。King 在 EFFIGY 系统里实现了这套机制，用一种类 PL/I 的语言解释执行，输入符号取代具体数值，中间值是符号公式——这正是后来 DART、KLEE 等所有工具的共同祖型。

### V7.1.2 符号存储（符号状态）

符号执行在每个程序点维护一个**符号存储**（symbolic store，也叫符号状态），它是一个从程序变量到符号表达式的映射：

```
σ : Var → SymExpr        （每个变量当前"等于关于输入符号的哪个公式"）
```

初始时，每个输入变量 v 被映射到一个全新的符号 αv（即 σ(v) = αv）；此后每执行一条赋值 `x = e`，就把 e 里的变量按当前 σ 展开成符号公式，再更新 σ(x) 为这个公式。

举个最小例子。设输入为 a、b，初始 σ = {a ↦ α, b ↦ β}。依次执行：

```
x = a + b;      →  σ(x) = α + β
y = x * 2;      →  σ(y) = (α + β) * 2
x = y - a;      →  σ(x) = (α + β) * 2 − α
```

关键点在于符号存储只记"当前值是什么公式"，不记"曾经是什么"——第三步 x 被覆盖后，旧的 α+β 就没了，新值是用**更新前**的 σ(y) 和 σ(a) 拼出来的。初学者容易和路径条件混淆：符号存储回答"现在各变量等于什么"，是执行的**数据**部分；下一节的路径条件回答"要走到这里，输入得满足什么"，是执行的**控制**部分。两者都随执行推进而更新，但角色不同。

### V7.1.3 路径条件（path condition）

**路径条件**（path condition，简称 PC）是一个只关于输入符号的**布尔公式**，它是"沿当前这条路径走过的所有分支判定"的合取（逻辑与）。初始 PC = true（还没做过任何分支选择，什么都不约束）。每当执行到一个条件分支 `if (c)`，就把 c 按当前符号存储展开成一个关于输入符号的约束 φ，然后：走 then 分支的那份执行把 PC 更新为

```
PC_then = PC ∧ φ
```

走 else 分支的那份执行把 PC 更新为

```
PC_else = PC ∧ ¬φ
```

路径条件的意义是**这条路径的"入场券"**：任何一组具体输入，只要代入后使 PC 为真，就一定会沿这条路径执行；反过来，若 PC 不可满足（无论怎么取输入都为假），这条路径就是**不可行路径**（infeasible path），现实中根本走不到。这一点是符号执行区别于随机测试的根本——它不是"碰运气走到某条路径"，而是"解出走到某条路径所需的输入"。

初学者要抓住"合取只增不减"这个直觉：沿一条路径往深走，PC 只会不断 ∧ 上新的约束，条件越来越苛刻、能满足它的输入集合越来越小。这也预示了 V7.2 的麻烦——分支越多，路径越多，每条路径的 PC 各不相同。

### V7.1.4 分支处的分叉（forking）

遇到条件分支时符号执行会**分叉**（fork）：把当前执行状态复制成两份，一份带着 PC ∧ φ 去走 then、一份带着 PC ∧ ¬φ 去走 else，两份各自独立继续。所谓"执行状态"就是一整套上下文——符号存储 σ、路径条件 PC、程序计数器（下一条要执行的语句）三者打包。KLEE 把它实现成一个 `ExecutionState` 对象，fork 就是克隆这个对象。

一个重要且常被误解的优化是：**分叉前应当先问求解器"这个分支方向可行吗"**。如果 PC ∧ φ 已经不可满足（比如之前的约束已经蕴含 x > 10，现在分支要求 x < 0），那条 then 路径根本不必创建——它是不可行路径，探下去纯属浪费。反过来若两个方向都可满足，才真正分叉成两条。这就是为什么符号执行天然需要一个可满足性判定器（SMT 求解器）挂在每个分支上，也是 V7.4 的主题。

初学者可以把分叉想成"走到岔路口时，把自己复制一份，一个我走左边、一个我走右边，各自记下'我选了这条'"。分叉是路径爆炸的直接来源：n 个顺序排列的独立 if 会产生多达 2ⁿ 个执行状态。

### V7.1.5 一次完整的符号走查

把上面的机制串起来走一个最小例子。程序（伪码）：

```
f(a, b):
  if (a > 0):
    if (b == a + 10):
      ERROR        // 想知道：这行可达吗？触发它的输入是什么？
```

初始 σ = {a ↦ α, b ↦ β}，PC = true。执行第一个分支，得到两条路径：

```
路径①（走进 a>0）：   PC = (α > 0)
路径②（a>0 不成立）：  PC = ¬(α > 0)
```

在路径① 上继续执行第二个分支，走进 `b == a+10` 的那一支：

```
到达 ERROR 的路径条件：PC = (α > 0) ∧ (β = α + 10)
```

把这个 PC 交给求解器，它是可满足的，一组解是 α = 1、β = 11——于是 `f(1, 11)` 就是精确触发 ERROR 的测试用例。这正是符号执行"自动生成高覆盖/触发特定行为的输入"的完整链条：符号存储把 b == a+10 翻译成 β = α + 10，路径条件把沿途分支合取起来，求解器把它变回一组真实输入。（本例的 PC 可满足性与解在 V7.4.4 用 z3 真跑复核。）

### V7.1.6 符号执行的可靠性视角（under-approximation）

放回本课 V1 的坐标系里看：**经典符号执行本质上是一种 under-approximation（欠近似）分析**。它只推理"确实存在输入能走到"的真实路径，每条路径上的推理都是**精确的**（PC 精确刻画了这条路径的输入集合，不引入假设、不做抽象丢信息）。所以它报出的"这条路径可达 / 这个 bug 能触发"几乎没有假阳——给出的输入拿去真跑就能复现。

代价在另一头：它**做不到穷尽所有路径**（循环和大程序会让路径数无穷或爆炸），所以"没找到 bug"绝不等于"没有 bug"——存在没被探索到的路径。这与 V4 抽象解释的 over-approximation（过近似，宁可假阳不可假阴，能证"绝对没有某类 bug"）恰好互补：抽象解释适合**证明性质成立**，符号执行适合**找出违反性质的具体证据（反例/测试）**。初学者记住这句对照即可：抽象解释"往大处圆、能证无"，符号执行"逐路径精确、能造有"。

## V7.2 路径爆炸与剪枝

### V7.2.1 路径爆炸的根源

**路径爆炸**（path explosion）是符号执行的头号敌人：程序中的路径数量随分支数量**指数增长**。粗略地说，若一段代码里有 n 个顺序排列、互相独立的 if 分支，可能的执行路径就多达

```
2ⁿ
```

每条路径对应一个需要独立维护和求解的执行状态。几百行带循环和嵌套判断的真实代码，路径数就轻易突破天文数字，朴素的"把每条路径都探一遍"根本跑不完。

初学者要理解这不是"实现不够快"的问题，而是**问题本身的组合复杂度**。KLEE 论文里对 GNU Coreutils 89 个工具做符号执行时，核心工程挑战之一正是控制爆炸；它能拿到平均 90%+ 的行覆盖，靠的不是穷尽路径，而是聪明的路径选择与大量约束求解优化。后面几节讲的所有技术，都是在同一个目标下打转：**在有限时间和内存里，尽量多、尽量快地探到"有价值"的路径**。

### V7.2.2 循环与无界路径

分支之外，**循环**是路径爆炸的另一个（更凶的）来源。一个循环体里若含分支，循环每多转一圈就可能再翻倍路径数；若循环次数依赖于符号输入，理论上会产生**无穷多**条路径（转 0 次、1 次、2 次……各是一条）。这直接触到 V1 的不可判定性——一般而言无法自动决定要展开循环多少次。

工程上只能"截断"：设一个**循环展开上界**或**探索深度/时间预算**，超过就停。这带来一个初学者必须记住的直接后果——**符号执行通常是不完备的**：达不到的深度里可能藏着 bug，"跑完没报错"只说明"预算内探到的路径都没问题"。这也是为什么符号执行定位为"强力找 bug / 生成测试"，而不是"证明无 bug"（后者要靠 V4 抽象解释或 V9 演绎验证）。

### V7.2.3 搜索策略与路径选择启发式

由于探不完，**先探哪条路径**就成了核心工程决策，即**搜索策略 / 路径选择启发式**（search heuristic）。朴素的深度优先（DFS）会一头扎进某个循环出不来；广度优先（BFS）内存开销大。KLEE 给出两种更实用的策略并把它们**交替轮转**（round-robin）使用，以避免任何单一策略被卡死：

```
随机路径选择（random path selection）：沿状态二叉树从根随机下行选状态，天然偏向"分叉少、更浅"的子树，防止被某个疯狂分叉的循环吃光资源
覆盖优化搜索（coverage-optimized search）：给"更可能到达未覆盖代码"的状态更高权重（依据到最近未覆盖指令的距离、状态新近被执行的情况等）
```

初学者可以把搜索策略理解成"探索预算怎么花最划算"。目标通常是**最大化代码覆盖**或**尽快命中某个目标点/危险语句**，所以策略会奖励"能通向没走过的新代码"的路径、惩罚"在老地方原地打转"的路径。不同工具、不同任务（测试生成 vs 定向漏洞挖掘）会选不同启发式，这是符号执行调优的主战场之一。

### V7.2.4 状态合并（state merging）

**状态合并**（state merging）是对抗路径爆炸的关键剪枝思路：与其让两条路径各走各的，不如在它们**重新汇合**的程序点（比如 if-else 之后的第一条语句）把两个执行状态**合并成一个**。合并后，对某个在两支里取了不同符号值的变量，用一个带条件的表达式（ite，if-then-else）来统一表示：

```
合并前： 状态A 里 σ(x) = e₁，PC_A = P ∧ φ
         状态B 里 σ(x) = e₂，PC_B = P ∧ ¬φ
合并后： σ(x) = ite(φ, e₁, e₂)，PC = P
```

这样两条路径变回一条，状态数不再翻倍。这个思路在"静态符号执行 + 合并"的路线里发展成了 **veritesting**（Avgerinos et al., ICSE'14，MergePoint 工具）等技术。

代价要讲清楚，否则初学者会以为合并是"免费的午餐"：合并把分支约束从"路径条件"搬进了"符号表达式内部的 ite"，路径少了，但**每次求解的公式变复杂了**。也就是说合并是在"路径数量爆炸"和"单次约束求解变难"之间做权衡——分支后两支代码若差异大、后续各自还要大量求解，合并未必划算；若两支很快汇合、后续共享很多，合并收益就大。实践中常"选择性合并"（只在划算的汇合点合）。

### V7.2.5 不可行路径剪枝与冗余消除

除了合并，符号执行还有几类直接"砍路径"的剪枝手段。最基本的一类是**不可行路径剪枝**：在每个分支处先求解 PC ∧ φ 是否可满足，unsat 的那一支根本不创建（见 V7.1.4）——这是不需要任何额外分析、由求解器自然提供的剪枝。

进一步是**冗余/等价路径消除**。若两条路径在某点之后会以"完全相同的方式"影响程序的剩余行为（读写的内存集合一致、后续可达状态无区别），探其中一条就够了。Boonstoppel、Cadar、Engler 的 **RWset**（读写集分析，TACAS'08）就是靠比较路径在各程序点的读写集来剪掉冗余后继。另一类是**函数摘要 / 组合式符号执行**（compositional，如 Godefroid 的 SMART）：把一个函数符号执行一次、总结成"输入满足什么则输出/副作用如何"的摘要，之后调用处直接复用摘要，不再重复展开函数体。

初学者抓住三层剪枝的层次感即可：分支处砍**不可行**的（几乎免费）、汇合处**合并**等价的（省路径但公式变难）、跨函数**摘要复用**避免重复劳动。它们不互斥，工业工具通常叠加使用。

### V7.2.6 约束求解开销与优化

即便路径被控制住，符号执行绝大部分时间其实**花在约束求解上**——每个分支、每个可达性判断都要调一次 SMT 求解器。KLEE 报告里求解是主要瓶颈，为此它内建了几层针对性优化，这些优化是它能跑完 Coreutils 的关键：

```
约束独立性（constraint independence）：一次查询只把与目标约束"共享变量"的那些约束送给求解器，无关约束不掺和，大幅缩小公式
计数示例缓存（counterexample cache / cex-cache）：缓存历史查询的可满足结果及其解；新查询是旧查询的子集/超集时，往往能直接复用结论而无需再解
表达式改写（expression rewriting）：常量折叠、算术化简等把公式先化简再送求解器
```

符号执行的性能工程有两条战线——**减少路径数**（V7.2.3–V7.2.5）和**降低单次求解代价**（本节）。两条战线都做好，符号执行才能从"玩具程序"走向"真实系统代码"。这也解释了为什么 V7.4/V10 的 SMT 后端质量，直接决定符号执行工具的成败。

## V7.3 混合执行（concolic）

### V7.3.1 纯符号执行的困境与 concolic 的动机

经典（纯）符号执行有两个现实痛点。其一，**约束可能超出求解器能力**——非线性算术、复杂位运算、密码学哈希等，求解器要么解不动要么超时。其二，**遇到外部环境无能为力**——程序调了一个没有源码的库函数、系统调用、或返回值不可符号建模的操作，符号执行不知道该给它什么符号语义。这两种情况下纯符号执行会卡住或不得不放弃整条路径。

**混合执行**（concolic execution，"concolic" = **conc**rete + symb**olic**）就是为化解这两个痛点而生。它的核心思想是：**始终拿着一组具体输入真实地运行程序（具体执行），同时在旁边"影子式"地维护符号状态和路径条件（符号执行），两者并肩前进。** 有了随时可用的具体值兜底，遇到解不动的约束或黑盒环境时，就用当前的具体值把它"钉死"，绕过困境继续走。

初学者可以理解为"一边真跑、一边记账"：真跑保证程序永远能往下走、永远有一条真实路径和真实值；记账（符号）负责在旁边攒路径条件，好在事后指导"下次换什么输入能拐进没走过的分支"。

### V7.3.2 concolic 的基本机制

concolic 从一组**初始具体输入**开始（可以是随机的），真实运行程序一遍。运行途中在每个分支处，它既知道具体走了哪一支（因为在真跑），又记录下这一支对应的符号约束。跑完一条路径后，得到这条路径完整的符号路径条件：

```
PC = φ₁ ∧ φ₂ ∧ … ∧ φₖ    （沿本次具体执行，第 1…k 个分支各自的符号约束）
```

关键在于符号信息是"贴着一条真实执行"收集的，所以**永远至少有一条走得通的路径**，不会像纯符号执行那样在难约束处彻底卡死。

这带来一个初学者常忽略的性质：concolic 天然处理"混合可解性"。一个分支条件里若一部分变量能符号推理、另一部分来自不可解运算，concolic 可以对能推的部分保留符号约束、对不能推的部分代入其具体运行值。这就是下一节"具体化"的机制，也是 concolic 比纯符号执行**更鲁棒、更容易在真实程序上落地**的根本原因。

### V7.3.3 DART/CUTE 的路径否定式系统探索

concolic 靠一个漂亮的算法来**系统地**探索路径——由 DART（Godefroid et al., PLDI'05）提出、CUTE（Sen et al., FSE'05，"concolic"一词即出自此文）细化。跑完一条路径拿到 PC = φ₁ ∧ … ∧ φₖ 后，为了下一次走一条**不同**的路径，它取路径条件里**最后一个（或某个选定的）约束取反**，并保留其之前的所有约束：

```
本次路径条件：      φ₁ ∧ φ₂ ∧ … ∧ φₖ₋₁ ∧ φₖ
下次目标路径条件：  φ₁ ∧ φ₂ ∧ … ∧ φₖ₋₁ ∧ ¬φₖ
```

把这个新公式交给求解器求解，得到的解就是**一组新的具体输入**——它保证前 k−1 个分支走法不变，但在第 k 个分支拐向另一支，从而探到一条尚未走过的新路径。用这组新输入再跑一遍、再取反下一个未翻转的分支……如此反复，就能系统地覆盖越来越多路径。

初学者抓住"复用前缀 + 翻转一个分支"这个套路即可：它像在一棵路径树上做深度优先/广度优先遍历，每次只改变一个分支决定，靠求解器把"我想拐这个弯"翻译成"那得喂什么输入"。wikipedia 与 CUTE 讲义给的经典例子（要让 `if (x == 100000)` 成立，就把上次的 `x ≠ 100000` 取反成 `x = 100000` 再解）正是这个机制的最小演示。

### V7.3.4 具体化：用具体值绕过难约束与环境

concolic 处理"解不动的约束"和"黑盒环境"的统一手法叫**具体化**（concretization）：当符号推理遇到求解器搞不定的部分时，直接用该变量**当前这次具体运行的实际值**替换它，把公式简化到可解。wikipedia 的原话是——"Any time that such constraints arise, the symbolic execution may substitute the current concrete value of one of the variables to simplify the problem."

比如路径条件里出现 `hash(x) == y`，而 hash 是个不可反解的复杂函数。concolic 不会卡死，而是取本次运行中 x 的具体值代进去，把这个约束变成一个具体的相等判断继续走。代价是**牺牲了这部分的探索完备性**——被具体化的变量这一维不再被系统探索，可能漏掉一些路径。这正是 concolic 的核心权衡：用"少探一点"换"永远能往下走、能上真实大程序"。

初学者要理解这是一种诚实的工程取舍，而非缺陷。SAGE（Godefroid、Levin、Molnar，微软）就是把 concolic + 具体化用到 x86 二进制文件解析器上做安全模糊测试（whitebox fuzzing）的著名工业案例，据 CACM 2012 文章其影响覆盖了超过十亿台 Windows PC 的安全测试——靠的正是 concolic 对真实、庞大、含大量黑盒操作的程序的鲁棒性。

### V7.3.5 concolic 与经典符号执行的关系辨析

术语上要给初学者理清一处常见混乱。"经典符号执行"（King 式，也叫 static symbolic execution）在分支处**分叉**、同时维护多条路径的符号状态，不需要真实运行；"concolic / dynamic symbolic execution（DSE，动态符号执行）"则**贴着一次具体运行**收集约束、靠翻转约束驱动下一次运行。文献中 concolic 常按实现方式再分两类：

```
online（在线）：一次运行中在分支处 fork 出多个状态同时推进（KLEE 属此类）
offline / concolic（离线）：一次跑一条具体路径，翻转约束后重跑整个程序换下一条路径（DART/CUTE/SAGE 的经典形态）
```

这里存在一处需明示的**术语分歧**：部分文献（含 Baldoni 综述）把"concolic"专指 offline 的、贴具体执行翻约束重跑的做法；另一些文献把"concolic / DSE"当成"任何结合具体与符号执行"的统称，从而也把 online 的 KLEE 归入其中。两种用法都在流通，本报告采用"concolic 强调具体+符号并行、online/offline 是其实现细分"的口径，遇到具体论文时以该文定义为准。

**它们都在算符号状态和路径条件，区别在"要不要真跑一条具体执行来兜底、以及怎么在多路径间切换"**。concolic 用具体执行换来了对难约束和真实环境的鲁棒性，这正是符号执行在 2005 年后能真正走进工业界（DART→CUTE→SAGE→KLEE）的关键转折。

## V7.4 SMT 后端可达性

### V7.4.1 可达性 = 路径条件的可满足性

符号执行里判断"某个程序点/某条路径**是否可达**"，被精确归约为一个**可满足性问题**：把到达该点的路径条件 PC 交给一个 SMT 求解器（satisfiability modulo theories，见 V10），问它 PC 是否可满足：

```
solver.check(PC)
  = sat    →  可达；求解器给出的 model（一组输入符号取值）就是触发该路径的测试用例
  = unsat  →  不可达；这是一条不可行路径，可安全剪掉（见 V7.2.5）
```

这一步把"程序分析问题"彻底转成了"逻辑求解问题"——符号执行负责把程序翻译成路径条件公式，SMT 求解器负责判定公式并给出解。V7.1–V7.3 反复用到的"分支是否可走""路径是否可行""怎样输入能拐进某支"，本质上全是同一个 `check(PC)` 查询。

初学者抓住这条对应关系就够了：**可达 ⟺ 路径条件可满足；不可达 ⟺ 路径条件不可满足**。符号执行的"智能"很大程度上是借来的——借的正是 SMT 求解器判定可满足性的能力。

### V7.4.2 用到的理论与 model/unsat 的解读

路径条件不是纯命题公式，而是带"理论"的公式——变量是整数、位向量、数组等，约束是它们上的算术/关系运算，这正是 SMT（"modulo theories"）的用武之地。符号执行常用的理论（详见 V10）包括：

```
线性整数/实数算术（LIA/LRA）：x + 2*y ≤ 10 之类
位向量（bit-vectors, BV）：精确建模机器整数的定宽、溢出、位运算（对 C/二进制分析至关重要）
数组（arrays）：建模内存、数组读写（select/store）
未解释函数（UF）：建模不透明操作
```

求解器返回 **sat** 时会附带一个 **model**（模型）：给每个输入符号一个具体取值，代回去使 PC 为真——这就是可复现的测试用例。返回 **unsat** 时表示无解（路径不可达），还可给出 **unsat-core**（导致矛盾的最小约束子集），有助于理解为何不可行。初学者记住 model 是"符号执行生成测试用例的最终产物出口"即可——前面所有机制忙活半天，就是为了拼出一个可满足的 PC，好让求解器吐出这组具体输入。

### V7.4.3 位向量语义：一个必须警惕的易错点

一个初学者（乃至工程师）极易踩的坑：**把符号执行的整数当成数学上的无界整数**。真实程序里的 `int` 是**定宽、会溢出**的（32 位补码回绕）。若用数学整数（LIA）建模，符号执行会漏掉一切依赖整数溢出的行为/漏洞；只有用**位向量理论**如实建模机器整数的宽度与回绕，PC 的可满足性判断才与程序真实行为一致。

举个会让两种建模给出不同答案的约束：`a > 0 ∧ a + 1 < 0`。在数学整数下这永远 **unsat**（正数加一还是正数）；但在 32 位有符号位向量下它 **sat**，唯一解是 a = INT_MAX = 2147483647（加一回绕成负数）。这直接决定符号执行能否发现"整数溢出类"缺陷。这也呼应 brief 的"规范与实现分账"——数学语义和机器实现语义必须分开对待，V7.4.4 用 z3 把这个差异真跑出来。

### V7.4.4 用 z3 实证路径条件可行性

本节把 V7.1.5 的路径条件和 V7.4.3 的位向量差异用 z3-solver 5.0.0 真跑复核。脚本（仅存 scratchpad，不入库）核心如下：

```python
from z3 import *
x, y = Ints('x y')
s = Solver(); s.add(x > 0, y == x + 10)          # V7.1.5 到达 ERROR 的 PC
print("PC1:", s.check(), s.model() if s.check()==sat else "")
s2 = Solver(); s2.add(x > 5, x < 3)               # 明显矛盾的不可行路径
print("PC2:", s2.check())
a = BitVec('a', 32); s3 = Solver(); s3.add(a > 0, a + 1 < 0)   # 32位溢出
print("PC3:", s3.check(), s3.model() if s3.check()==sat else "")
```

本机真实输出（Python 3.11.15 + z3 5.0.0 @2026-07-30）：

```
PC1 (x>0 & y==x+10): sat
  model: [y = 11, x = 1]
PC2 (x>5 & x<3): unsat
PC3 bitvec (a>0 & a+1<0): sat
  model a = 2147483647 (= INT_MAX?) True
```

三行输出逐一坐实了本大主题的核心命题：PC1 可满足并解出 `f(1, 11)` 精确触发 V7.1.5 的 ERROR（与手推一致）；PC2 是不可行路径、求解器判 unsat 可安全剪枝（对应 V7.2.5）；PC3 在位向量语义下可满足且解恰为 INT_MAX，证明"整数溢出型"路径只有用位向量建模才判得对（对应 V7.4.3）。这就是"路径条件可达性判定"在真实 SMT 后端上的完整闭环。

### V7.4.5 SMT 后端的局限与接口（接 V10）

最后要如实标注局限，避免初学者高估符号执行。SMT 求解本身在一般情形下是**计算困难甚至不可判定**的：命题可满足性（SAT）是 NP 完全，加上非线性整数算术等理论后整体不可判定，实践中靠超时（timeout）兜底。因此每个 `check(PC)` 都可能**超时或返回 unknown**——这时符号执行既不能确认可达、也不能确认不可达，只能保守处理（通常按"可能可达"继续，或放弃该路径）。浮点、非线性、字符串等理论上求解器能力参差，也是符号执行"卡壳"的常见来源，正是 V7.3 具体化要绕开的对象。

关于 SMT 求解引擎本身——DPLL(T) 框架、各理论决策过程、Nelson-Oppen 理论组合、sat/unsat/model/unsat-core 的完整语义——是本课 **V10（SMT 求解引擎，锚 de Moura & Bjørner, Z3, TACAS'08）** 的主题，此处按 prompt 要求点名接入、不展开。初学者只需带走一句话：**符号执行是"翻译官"（程序→路径条件公式），SMT 求解器是"判官"（判可满足并给证据/给矛盾），两者合起来才是完整的符号执行系统。**
