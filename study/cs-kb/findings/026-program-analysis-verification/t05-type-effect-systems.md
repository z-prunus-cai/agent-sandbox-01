## V5.1 注解类型系统

### V5.1.1 总思想：把程序分析信息编码进类型

注解类型系统（annotated type system）的核心想法，是在一个已有的底层类型系统（underlying / original type system）之上，给类型**附加注解（annotation）**，用这些注解携带某种静态分析的信息，从而让"做分析"变成"做一种更精细的类型推导"。底层类型只说"这是个整数""这是个 int→int 的函数"；加了注解后，类型还能说"这个整数是编译期就知道的""这个函数可能是源码里第 3 号或第 7 号那两个 lambda 之一"。

对初学者，先建立"类型 = 对值的静态描述"这个基本认识，再看注解是怎么把描述加厚的。普通类型系统里，判断写成

Γ ⊢ e : τ

意思是"在类型环境 Γ（记录各自由变量的类型）下，表达式 e 具有类型 τ"。注解类型系统只是把 τ 换成一个**带注解的类型** τ̂，判断变成

Γ̂ ⊢ e : τ̂

而 τ̂ 里多出来的那些注解，恰好就是某个程序分析想算的东西。为什么值得这样做？因为类型系统是一套极其成熟、语法制导（syntax-directed，即"看着语法结构一条条往上推"）、且有现成推断算法的机械；把分析套进这个框架，就能白捡"多态、principal type、可判定性理论、模块化"等一整套工具，而不必从零造一个数据流框架。

一个贯穿全大主题的对照要先记住：注解类型系统与 V2/V3/V4 分析的是**同一批性质**（控制流、副作用、别名、区域……），只是"外衣"不同。V2 在 CFG 上传播、V3 解 ⊆ 约束、V4 在抽象域上求不动点，而本大主题把它们统统写成"带注解的类型规则"。这是《Principles of Program Analysis》把四大方法并列的用意：它们是**同一件事的四种技术呈现**，可以互相翻译。

### V5.1.2 底层类型系统：注解要挂在谁身上

要谈"给类型加注解"，得先有个"没加注解"的底层类型系统作参照。本大主题沿用一门最小函数式语言，表达式与类型为

e ::= c ｜ x ｜ fn x => e0 ｜ e1 e2 ｜ …

τ ::= int ｜ bool ｜ … ｜ τ1 → τ2

底层类型系统的判断 Γ ⊢UL e : τ（UL = underlying）由几条标准规则给出，其中函数抽象与应用两条是关键：

Γ[x ↦ τx] ⊢UL e0 : τ0    推出    Γ ⊢UL (fn x => e0) : τx → τ0

Γ ⊢UL e1 : τ2 → τ0    且    Γ ⊢UL e2 : τ2    推出    Γ ⊢UL (e1 e2) : τ0

这就是简单类型 λ 演算（L5-06 T3）的记法，读者应已熟悉：函数抽象把"形参类型 → 函数体类型"拼成箭头类型；函数应用要求实参类型与箭头左边匹配、结果取箭头右边。

对初学者，抓住"注解有两个可以附着的地方"这一点，后面两小节就顺理成章了。一处是**类型构造子（type constructor）**——比如函数箭头 →，可以在箭头上写注解（V5.1.3 的控制流分析就把注解写在箭头上）；另一处是**基类型（base type）**——比如 int、bool，可以给基类型本身写注解（V5.1.4 的绑定时间分析就写成 int^S、int^D）。两条路线不互斥，很多分析两处都注（比如既标基类型、又标箭头）。这里 fn x => e0 里那个上标 π（下节出现）是给这个函数抽象起的唯一名字/程序点标号，作用与 V3 里给子表达式打标号 ℓ 完全一样，是让分析能"指名道姓"的脚手架。

### V5.1.3 注解类型构造子：控制流分析作为注解类型系统

把注解挂在类型构造子上的典型例子，是把 V3 那套控制流分析（CFA）重新表述成一个注解类型系统。做法是给函数类型的箭头附一个注解 φ，φ 是一个**函数名的集合**，表示"这个箭头类型的值可能是哪几个 lambda 抽象"。带注解的类型与注解语法为

φ ::= {π} ｜ φ1 ∪ φ2 ｜ ∅

τ̂ ::= int ｜ bool ｜ … ｜ τ̂1 —φ→ τ̂2

其中 τ̂1 —φ→ τ̂2 读作"一个带注解 φ 的箭头类型"，φ 收集了所有可能求值到此处的函数抽象的名字。判断形式为 Γ̂ ⊢CFA e : τ̂，两条核心规则是

Γ̂[x ↦ τ̂x] ⊢CFA e0 : τ̂0    推出    Γ̂ ⊢CFA (fn x => e0)^π : τ̂x —{π}∪φ→ τ̂0

Γ̂ ⊢CFA e1 : τ̂2 —φ→ τ̂0    且    Γ̂ ⊢CFA e2 : τ̂2    推出    Γ̂ ⊢CFA (e1 e2) : τ̂0

上面第一条规则说的是，名叫 π 的函数抽象，它自己的名字 π 必须进入它所产生的箭头类型的注解集合（{π} ∪ φ）；第二条规则说的是，应用一个箭头类型的函数时，实参类型要和箭头左边一致、结果取箭头右边——和底层规则一模一样，只是类型带上了注解、被一路传递下去。

对初学者，把它和 V3 的约束式 CFA 并排看最有启发。V3 是"给每个程序点配一个集合变量，生成 ⊆ 约束，解最小解"；这里是"给每个箭头配一个注解集合，用类型规则把注解从定义处一路带到使用处"。两者算的是同一个东西——"哪个函数可能流到哪个调用点"——只是一个走约束求解、一个走类型推导。这印证了 V5.1.1 说的"同一件事的不同外衣"。易错点在下一节的"保守扩展"：为什么箭头注解写成 {π} ∪ φ 而不是干脆写 {π}？答案见 V5.1.5。

### V5.1.4 注解基类型：绑定时间分析

把注解挂在基类型上的典型例子，是绑定时间分析（binding-time analysis, BTA）——它区分每个数据是**静态的**（S，编译期就已知）还是**动态的**（D，要到运行期才知道），这是部分求值（partial evaluation）的基础，也可改造成区分"机密/公开"的安全信息流分析。注解与带注解类型为

φ ::= S ｜ D ｜ β

τ̂ ::= int^φ ｜ bool^φ ｜ … ｜ τ̂1 —φ→ τ̂2

这里 β 是**注解变量**（annotation variable），给有限的注解多态留出空间；S、D 上有一个偏序（见 V5.3.2）。注意基类型也带上标注解了：int^D 表示"一个动态整数"。一个作用于动态整数的静态函数，其类型形如

int^D —S→ int^D

因为基类型能带注解，就出现了"有没有意义"的问题：一个静态的（S）复合数据里不该藏着动态的（D）成分——否则整块数据其实要等到运行期才齐。于是引入一个**良构性（well-formedness）**判断 τ̂ ▷ φ，它抽出类型的顶层注解 φ 并要求各部件注解不低于它：

int^φ ▷ φ        bool^φ ▷ φ

τ̂1 ▷ φ1    且    τ̂2 ▷ φ2    且    φ ⊑ φ1    且    φ ⊑ φ2    推出    (τ̂1 —φ→ τ̂2) ▷ φ

直觉是"一个静态的东西可以operating on/包含动态的东西吗？"——良构性精确地卡住这类组合：静态函数可以作用于动态数据，反之不行。

对初学者，绑定时间分析是体会"注解基类型"最好的入口，因为 S/D 的含义特别具体（编译期知不知道）。与 V5.1.3 的 CFA 对照：CFA 的注解是集合（一堆函数名），BTA 的注解是一个来自小偏序的值（S 或 D）。这暗示注解的取值域可以很不一样——集合、小格、甚至任意完全格（呼应 V4 抽象域），只要它上面有个序、能谈"放大/合并"就行。BTA 还额外引入了良构性这个 CFA 没有的配件，原因就是"注解爬到了基类型上"，才有了"内外注解是否协调"的问题；CFA 只注箭头，不涉及此。

### V5.1.5 保守扩展：为什么注解要能"放大"

设计注解类型系统有一条隐形红线——它应当是底层类型系统的**保守扩展（conservative extension）**：凡在底层类型系统里能定型的程序，在注解版里也必须能定型（反之亦然，只是注解版更精细）。若不满足，就会出现"本来类型正确的程序，加了分析反而没法定型"的荒唐局面，分析就成了废物。V5.1.3 里箭头注解写成 {π} ∪ φ（而非仅 {π}）正是为此：

Γ̂ ⊢CFA (fn x => e0)^π : τ̂x —{π}∪φ→ τ̂0

对初学者，用条件分支就能看懂为什么非得留那个"∪ φ"的活口。设想

if b then (fn x => e1)^1 else (fn x => e2)^2

两个分支各是一个函数、名字分别是 1 和 2；if 要求两分支类型相同，可它们的箭头注解一个含 {1}、一个含 {2}，若规则死板地只准写 {π}，两边永远配不齐，整个 if 就无法定型——而它在底层类型系统里明明是合法的。留出 {π} ∪ φ 这个"可以往里多塞"的口子，就能把两个分支的注解都放大成 {1,2}，让类型对齐、if 通过。这种"把注解/效果往大了放以消解冲突"的机制，就是 V5.3 要正式讲的**子效果（subeffecting）**——CFA 本质上正是一个 subeffecting 分析。这里点到即止，机制在 V5.3.1 展开。

本小主题与 L5-06 的类型理论有明确交叠：注解类型系统直接复用 L5-06 T4（类型扩展：引用、异常）的语言构造、T5（子类型、协变/逆变）的 subsumption 思想、T7（合一、let-多态、principal type）的推断机械。按 round-prompt 要求，这些底层类型理论此处**作分析工具引用、点名不展开**，其完整机制归 L5-06 各主题；本大主题只讲"如何把它们当分析用"。两处记法一致（同用 Γ ⊢ e : τ 判断、同一套箭头/协变逆变约定），无实质冲突——差别仅在 PPA 侧把类型进一步注解化、并额外要求"保守扩展"这一分析特有的约束。

## V5.2 效果(effect)推断

### V5.2.1 核心判断形式 Γ ⊢ e : τ & φ

效果系统（effect system）是注解类型系统的一次升格：判断里除了类型，再显式带一个**效果（effect）**分量，专门描述"求值 e 的过程中会发生什么副作用/动作"。判断形式为

Γ ⊢ e : τ & φ

读作"在类型环境 Γ 下，表达式 e 具有类型 τ，且求值 e 时可能发生的效果由 φ 刻画"。φ 在形式上和 V5.1 的注解是同一类东西（通常是某种集合），但**概念上不同**：注解描述"值本身的一个性质"，而效果描述"求值这个过程会做出的动作"（读了哪块内存、抛了什么异常、往哪个信道发了消息）。

对初学者，用一句大白话抓住 τ 与 φ 的分工：τ 说"算完得到什么"，φ 说"算的过程中干了什么"。比如一个"读取全局计数器并返回其值"的表达式，τ 是 int（算完得到一个整数），φ 是 {读内存}（过程中读了内存）。为什么要把 φ 单拎出来而不是塞进 τ？因为效果是**过程性**的，它天然要在"求值发生的地方"累积、在"函数被调用的地方"释放，这套累积/释放的流动规律和类型的流动规律不完全一样，值得独立成一个分量来管（尤其是函数——见下节的潜在效果）。这也正是效果系统比"只注解类型"更有表达力的地方。

还有一处要点值得辨析。常量、变量这类"取一个已有的值、不做任何动作"的表达式，其效果是**空**（记作 ∅ 或 ε）：

Γ ⊢ c : τc & ∅        Γ ⊢ x : Γ(x) & ∅

它们只是把一个现成的值摆出来，没有可观察的副作用，所以账单是空的。这是所有效果推导的起点。

### V5.2.2 潜在效果：把函数体的效果挂到箭头上

效果系统最精巧的一处设计，是**潜在效果（latent effect）**：定义一个函数本身**不产生**效果（只是把代码摆在那儿），真正的效果要等到函数被**调用**时才发生；所以函数体的效果被"冻结"起来、**标注在函数类型的箭头上**，等应用时再"解冻"释放。函数抽象与应用两条规则精确表达了这一点：

Γ[x ↦ τ̂x] ⊢ e0 : τ̂0 & φ0    推出    Γ ⊢ (fn x => e0) : (τ̂x —φ0→ τ̂0) & ∅

Γ ⊢ e1 : (τ̂2 —φ0→ τ̂0) & φ1    且    Γ ⊢ e2 : τ̂2 & φ2    推出    Γ ⊢ (e1 e2) : τ̂0 & (φ1 ∪ φ2 ∪ φ0)

上面第一条规则里，函数体 e0 的效果是 φ0，但它被搬到箭头上作为**潜在效果**（τ̂x —φ0→ τ̂0），而定义这个函数本身的整体效果是 ∅——光定义不调用，什么也没发生。第二条规则里，调用时三股效果汇合——求值函数部分 e1 的效果 φ1、求值实参 e2 的效果 φ2、以及从箭头上解冻下来的函数体潜在效果 φ0，并起来就是整个应用的效果。

对初学者，用"信用卡账单"的比喻最直观：写下一个函数就像办了张卡但没刷（定义的效果 ∅），卡的额度/消费规则记在卡面上（箭头上的潜在效果 φ0）；只有真的刷卡（调用函数）时，卡面上的消费才计入你这个月的账单（应用处并入 φ0）。为什么潜在效果必须挂在箭头上、而不能在定义处就结账？因为同一个函数可能被调用零次、一次或多次，效果发生几次取决于调用、而非定义——把账挂在箭头上、随每次调用释放，才对得上真实语义。这是初学者最容易想错的一点：会误以为"定义了带副作用的函数，定义处就有副作用"。

### V5.2.3 副作用分析：区域与 read/write/alloc 效果

效果最经典的用途是**副作用分析（side-effect analysis）**：跟踪程序读了/写了/新建了哪些引用单元（可变内存）。语言先加上命令式构造（仿 Standard ML）：new x := e1 in e2 新建一个引用变量、!x 读取、x := e0 赋值。分析里，一个引用变量不再只记"它存什么类型"，还记它**可能在哪些程序点被创建**——这个创建点的集合叫**区域（region）** ρ。带注解类型与效果为

ρ ::= {π} ｜ ρ1 ∪ ρ2 ｜ ∅

φ ::= {!π} ｜ {π:=} ｜ {new π} ｜ φ1 ∪ φ2 ｜ ∅

τ̂ ::= … ｜ τ̂1 —φ→ τ̂2 ｜ τ̂ ref ρ

其中 τ̂ ref ρ 是"一个引用单元的类型，它持有 τ̂ 类型的值，且可能创建于区域 ρ 中的某个程序点"；效果 !π 表示"读了创建于 π 的单元"、π:= 表示"写了创建于 π 的单元"、new π 表示"在 π 新建了一个单元"。三条关键规则为

Γ ⊢ !x : τ̂ & {!π1, …, !πn}    若    Γ(x) = τ̂ ref {π1,…,πn}

Γ ⊢ e : τ̂ & φ    推出    Γ ⊢ (x := e) : τ̂ & (φ ∪ {π1:=, …, πn:=})    若    Γ(x) = τ̂ ref {π1,…,πn}

Γ ⊢ e1 : τ̂1 & φ1    且    Γ[x ↦ τ̂1 ref (ρ ∪ {π})] ⊢ e2 : τ̂2 & φ2    推出    Γ ⊢ (new x := e1 in e2)^π : τ̂2 & (φ1 ∪ φ2 ∪ {new π})

对初学者，"区域"这个词别被吓到——它就是"这个指针可能指向的对象是在哪几行 new 出来的"的集合，是对"到底是哪块内存"的一个保守近似（呼应 V1 的 over-approximation：宁可多列几个创建点，不可漏）。读 !x 时，因为 x 可能指向区域里任一个单元，所以效果把区域里每个创建点都记成一次读（{!π1,…,!πn}）。这套信息的用途很实在：编译器若知道"求值这段代码只读不写某块内存"，就能放心地重排、并行、缓存它——这正是 Gifford & Lucassen 当年提出效果系统的初衷（整合函数式与命令式、指导并行化）。区域信息再往前一步，就是 Tofte & Talpin 的**区域推断（region inference）**：把内存按区域组织成一个栈、编译期决定每块数据分配到哪个区域、区域何时整体释放，从而用"区域栈"替代运行期垃圾回收——Standard ML 的 MLKit 实现即基于此。

### V5.2.4 通信效果与行为：带因果结构的效果

效果不必是"扁平的集合"。当分析并发/通信程序（如 Concurrent ML）时，我们关心动作之间的**因果与时序**——谁先发生、是顺序还是选择、有没有循环。于是效果升级成有结构的**行为（behaviour）**，形如进程代数（process algebra）里的项。语言加上 channel（建信道）、spawn e0（派生进程）、send e1 on e2、receive e0 等构造，行为语法为

φ ::= ε ｜ β ｜ φ1 ; φ2 ｜ φ1 + φ2 ｜ rec β. φ ｜ τ̂ chan ρ ｜ spawn φ ｜ ρ!τ̂ ｜ ρ?τ̂

各构造的含义如下。ε 是无通信的原子动作（相当于"静默"）；φ1 ; φ2 表示 φ1 先于 φ2 发生（顺序）；φ1 + φ2 表示二者择一（选择）；rec β. φ 是递归行为；τ̂ chan ρ 表示在区域 ρ 新建了一条传 τ̂ 类型值的信道；spawn φ 表示派生了一个行为为 φ 的进程；ρ!τ̂ 表示往信道发送、ρ?τ̂ 表示从信道接收。函数应用的规则改用"顺序"来记录求值次序：

Γ ⊢ (e1 e2) : τ̂0 & (φ1 ; φ2 ; φ0)

对初学者，把行为读成"用正则表达式/进程代数描述这段程序会依次做出哪些通信动作"就对了：`;` 像正则里的连接、`+` 像或、`rec` 像 Kleene 星的循环。它比 V5.2.3 的集合效果强在**保留了顺序**——集合只说"读过也写过"，行为能说"先读后写"。这类信息可喂给模型检验（接 V8）去验证"这个控制程序永远不会在收到停止信号前继续动作"之类的安全性质，Nielson 等人确有用 CML 行为分析验证嵌入式控制程序的案例。易错点：行为不是运行时的真实执行轨迹，而仍是**静态过近似**——它可能包含实际永不发生的路径，`+` 覆盖了所有分支可能。

### V5.2.5 效果族巡览：副作用、异常、通信及其它

把前几节收拢一下：效果系统的"效果"论域可以承载许多不同的分析，文献里常见的效果族包括——被调用的函数集合（这正是 V5.1.3 的控制流分析，可视作最简单的效果）、求值中读/写/新建的存储单元（V5.2.3 副作用分析）、可能抛出的异常集合（exception analysis，φ 记"这段代码可能 raise 哪些异常"）、求值发生的区域（region，喂区域推断）、以及带因果结构的通信行为（V5.2.4）。它们共用同一套判断骨架 Γ ⊢ e : τ & φ，区别只在"φ 装的是什么、φ 上的代数长什么样"。

对初学者，异常分析是个好补充例子，因为它贴近日常：让 φ 装"可能抛出的异常名集合"，则 try e0 with … 之类构造的规则会把 e0 抛出的异常从效果里"消掉"（被 handler 捕获），而未被处理的就继续往上冒——这正是 Java 的 checked exception（`throws` 子句）在做的事，`throws` 子句本质就是一个写在方法签名上的效果注解。由此可见效果系统并非纯学术：类型化异常、Rust 的 `Result`/`?` 传播、乃至现代语言的效果处理器（effect handlers），都是这一思想在工程中的后代。本报告按 round-prompt 只讲经典骨架，不深入现代代数效果（algebraic effects）分支。

## V5.3 子效果与代数性质

### V5.3.1 子效果规则：把效果"放大"到刚好满足约束

**子效果（subeffecting）**是效果系统里最基础的"精度调节/兼容性"配件：它允许把一个表达式已推出的效果**放大**成一个更大的效果，只要新效果包含旧效果。规则为

Γ ⊢ e : τ̂ & φ    推出    Γ ⊢ e : τ̂ & φ'    若    φ ⊑ φ'

其中 φ ⊑ φ' 表示 φ 是 φ' 的"子效果"（对集合效果就是 φ ⊆ φ'）。它是保证效果系统成为底层类型系统**保守扩展**（V5.1.5）的关键，且在有条件分支时不可或缺。

对初学者，子效果的必要性和 V5.1.5 的 if 例子是同一回事，只是现在放在效果上。if 的两个分支各有自己的效果 φ1、φ2，而 if 规则通常要求两分支的类型与效果一致；没有子效果就永远对不齐。子效果给了个"往大了放"的活口：把 φ1、φ2 都放大成 φ1 ∪ φ2，两边就齐了。直觉上这是安全的——效果是过近似，账单多记几笔（声称"可能发生但实际没发生的动作"）只会让分析更保守、绝不会漏报真实动作。回头看 V5.1.3 的 CFA：它箭头注解写 {π}∪φ 而非 {π}，本质就是一个 subeffecting 分析。易错点：子效果只放大**效果分量**，不动类型结构；能连类型一起放大的是下面的子类型。

### V5.3.2 效果集合的代数：UCAI 与偏序

效果要能"比较大小、合并、放大"，就得在效果上定义代数结构。对最常见的**集合式效果**，合并用并集 ∪，其代数性质概括为缩写 **UCAI**——并集有单位元（Unit，∅ 是单位元）、可交换（Commutative）、可结合（Associative）、幂等（Idempotent）：

φ ∪ ∅ = φ        φ1 ∪ φ2 = φ2 ∪ φ1        (φ1 ∪ φ2) ∪ φ3 = φ1 ∪ (φ2 ∪ φ3)        φ ∪ φ = φ

在此之上，"子效果"偏序即由包含定义：

φ ⊑ φ'    当且仅当    φ ∪ φ' = φ'   （对集合即 φ ⊆ φ'）

对初学者，UCAI 这四条不是故弄玄虚——它们正是"一个集合并半格（join-semilattice）"的公理，等价于说效果集合在 ⊑ 下构成一个**格**（呼应 V2/V4 反复出现的格论）：任意两个效果有最小上界（就是它们的并）。这解释了效果系统与前几大主题的深层统一——V2 数据流、V4 抽象解释都在格上求不动点，效果系统的效果也活在一个格里，只是"合并"这一步藏在了 subeffecting 规则和推断算法（V5.4）里。绑定时间分析（V5.1.4）的注解偏序 S ⊑ D 是同一个故事的最小实例：一个只有两点、S 在下 D 在上的格。要记住 ⊑ 的方向：小的那个是"信息更精确/更少"，大的是"更保守/更放松"；放大（沿 ⊑ 往上）总是 sound 的。

### V5.3.3 子类型与协变/逆变

**子类型（subtyping）**比子效果更进一步：它不仅能放大效果，还能沿类型结构整体地放大带注解的类型。规则为

Γ ⊢ e : τ̂ & φ    推出    Γ ⊢ e : τ̂' & φ    若    τ̂ ⊑ τ̂'

带注解类型上的序 τ̂ ⊑ τ̂' 由注解的序结构地提升，其中**函数箭头是关键**：

τ̂1' ⊑ τ̂1    且    τ̂2 ⊑ τ̂2'    且    φ ⊑ φ'    推出    (τ̂1 —φ→ τ̂2) ⊑ (τ̂1' —φ'→ τ̂2')

也就是说，箭头类型在**参数位逆变（contravariant）**、在**效果位与结果位协变（covariant）**。引用类型 τ̂ ref ρ 则在区域 ρ 上协变、在所持值类型上**既协变又逆变（不变）**——因为引用既可读（协变）又可写（逆变）。

对初学者，协变/逆变是这里唯一的门槛，用"替换安全"来记最稳。一个函数 f' 要能安全顶替 f 使用，f' 必须**接受更宽的参数、返回更窄的结果**：参数能接受得更多（逆变，τ̂1' ⊑ τ̂1 里 τ̂1' 在下、更精确的需求 τ̂1 反而在上），结果给得更精确（协变）。效果位协变的道理同子效果：账单只能往大放。引用为什么在所持类型上"不变"（既协变又逆变）？因为你能通过它读（要求读出来的类型足够宽 → 协变）又能写（要求写进去的类型足够窄 → 逆变），两个方向都要满足只能相等——这正是 L5-06 T5.3"可变引用/数组必须不变、协变数组之坑"在效果语境的复刻。这套协变/逆变的正确使用是语义可靠性（subject reduction）成立的前提，方向搞反会让类型系统不健全。此处作分析工具引用，完整的子类型元理论归 L5-06 T5，不展开。

### V5.3.4 行为上的序：更丰富的代数

当效果是有结构的**行为**（V5.2.4）时，⊑ 就不再是简单的集合包含，而是一个尊重行为运算子的**预序（preorder）且是同余（congruence）**，其代数性质丰富得多。关键的几条为

φ1 ; (φ2 ; φ3) ⊑ (φ1 ; φ2) ; φ3    且    (φ1 ; φ2) ; φ3 ⊑ φ1 ; (φ2 ; φ3)   （顺序结合律）

ε ; φ ⊑ φ    且    φ ⊑ ε ; φ    且    φ ; ε ⊑ φ    且    φ ⊑ φ ; ε   （ε 是顺序的单位元）

φ1 ⊑ φ1 + φ2    且    φ2 ⊑ φ1 + φ2    且    φ + φ ⊑ φ   （选择：各分支被自身覆盖、幂等）

(φ1 + φ2) ; φ3 ⊑ (φ1 ; φ3) + (φ2 ; φ3)   （顺序对选择的分配律，反向亦成立）

rec β. φ ⊑ φ[β ↦ rec β. φ]    且    φ[β ↦ rec β. φ] ⊑ rec β. φ   （递归的展开/折叠）

对初学者，把它类比成正则表达式/进程代数的等式律最省力：`;` 像连接（结合、以 ε 为单位元）、`+` 像或（交换、幂等）、`;` 对 `+` 分配、`rec` 可展开一层。与 V5.3.2 的集合效果相比，行为多出了"顺序"和"递归"这两维结构，所以它的序是预序（可能 φ1 ⊑ φ2 与 φ2 ⊑ φ1 同时成立而 φ1、φ2 语法不等，即行为等价）而非集合上那种反对称偏序。"同余"意味着可以在任意上下文里用"更大"的行为替换"更小"的，替换后整体仍更大——这是让 subeffecting/subtyping 规则在有结构效果上仍成立的技术保证。这一节点名即止，进程代数的完整语义不深挖。

### V5.3.5 三个精度旋钮：subeffecting、subtyping、polymorphism

效果系统有三个层层加强的"放大/复用"机制，它们都在解决同一个矛盾——让一个效果/类型既足够宽以兼容各处需求，又足够窄以保留精度。**子效果**只在某一点把效果整体放大（最粗，但足以保证保守扩展）；**子类型**能在类型结构的深处、更晚的时机才放大（更细，能让子程序用上更精确的类型效果）；**多态（polymorphism）**则用类型/效果/区域**变量**加"泛化-实例化"，让同一个函数在不同调用处实例化出不同的效果（最灵活，直接复用 Hindley-Milner 那套）。多态的两条规则（泛化 Gen、实例化 Inst）为

Γ ⊢ e : τ̂ & φ    推出    Γ ⊢ e : ∀(ζ1,…,ζn). τ̂ & φ    若    ζ1,…,ζn 不自由出现于 Γ 与 φ

Γ ⊢ e : ∀(ζ1,…,ζn). τ̂ & φ    推出    Γ ⊢ e : (S τ̂) & φ    若    dom(S) ⊆ {ζ1,…,ζn}

其中 ζ 可以是类型变量、效果（注解）变量或区域变量，S 是把这些变量替换掉的代换。

对初学者，三者的关系可以这样排：subeffecting 是"就地把账单写大点"，subtyping 是"连同数据的形状描述一起、在更深的地方写大点"，polymorphism 是"根本不写死、留个空（变量），每次用的时候按当时情况填"。它们各有取舍、互相不可替代，实践中常组合使用。一个关键的可判定性警告在此埋下伏笔：泛化规则里"ζ 不自由出现于 Γ 与 φ"这个副条件（side condition）很微妙——效果 φ 里出现的变量不能被泛化，这限制了多态的范围，也正是 V5.4 里"效果如何影响能泛化哪些类型变量"这一算法难点的根源。另外，允许递归函数在**自己体内**也被多态使用（polymorphic recursion）会让类型系统变得**不可判定**（V5.4.5），所以多态的强度必须谨慎控制。

## V5.4 与推断算法的关系

### V5.4.1 方法论全景：从规则到能跑的算法

前面给的都是**声明式**的推导规则（"什么样的类型效果是合法的"），但要真正拿来做分析，还需要一个**算法**去自动算出类型和效果。PPA 把整套方法论拆成六步：为语言定语义 → 把分析写成类型与效果系统（V5.1–V5.3 做的）→ 证明相对语义可靠（subject reduction）→ 开发高效推断算法 → 证明算法**句法可靠且完备（syntactically sound and complete）**→ 用结果做优化/验证。本小主题聚焦第 4、5 步：算法怎么造、能造到什么程度。

对初学者，先分清两对"可靠"以免混淆。**语义可靠（semantic soundness / type soundness）**说的是"类型系统相对程序真实运行是对的"，标准手法是 subject reduction（若 e 有类型 τ 且 e 求值到 e'，则 e' 也有类型 τ），这与 L5-06 T3 的 Progress+Preservation 同宗。**句法可靠与完备（syntactic soundness & completeness）**说的是"算法相对声明式规则是对的"：句法可靠 = 算法算出的结果确是规则能推出的合法结论；句法完备 = 规则能推出的每个结论，算法都能（以最一般的形式）算到、即算法能求出 principal type（主类型/主效果）。principal type 的存在性与"算法完备"是一体两面——有了句法可靠且完备的算法，就自动有 principal type。这个 principal（最一般/最优）解的角色，恰对应 V2/V3 里"约束系统的最小解"，是 inference-based 与 flow-based 两条路线的又一汇合点。

### V5.4.2 两阶段算法：先类型后效果，Algorithm W 的扩展

当效果**不影响类型的形状**时（即效果只是挂在类型上的额外注解、不改变类型结构），可以用**两阶段（two-stage）**算法：第一阶段跑普通的 Hindley-Milner 类型推断（就是 L5-06 T7 的 **Algorithm W**）把底层类型定下来；第二阶段在已定型的程序上，把注解/效果变量摊出来、收集它们之间的约束再求解。扩展后的 W 形如

W(Γ, e) = (S, τ, φ, C)

其中 e 是待分析程序，Γ 是初始类型环境，返回：代换 S（对 Γ 的精化）、推出的类型 τ、整体效果 φ、以及一组约束 C（记录各效果/注解变量之间必须满足的 ⊑ 关系）。

对初学者，"两阶段"之所以可行且好用，关键在第一阶段把类型骨架先钉死，第二阶段就只剩"在固定骨架上填效果"这件相对简单的事。实现上有个核心技巧叫 **simple types**：强制让所有注解位置都只放**注解变量**（而非具体的效果集合），把具体值的约束统统外挂到约束集 C 里。这样类型项就落在一个**自由代数（free algebra）**上，普通的合一（unification，见下节）能原封不动地用——合一不需要懂"效果 ∪ 满足 UCAI"这些等式，那些都推给 C 里的约束求解去管。这正是能"白捡 HM 全套机械"的技术前提。回接 V5.3.5 埋的伏笔：泛化时"哪些变量能泛化"要参考 C（不能泛化那些被约束牵连到 Γ 或 φ 的变量），这是第二阶段的主要难点。

### V5.4.3 合一与约束求解：复用 T7 的技术

第一阶段的引擎是**合一（unification）**——Robinson 算法，给两个含类型变量的类型求一个使它们相等的最一般代换（most general unifier, mgu）。这正是 L5-06 T7.2 的内容，本大主题**直接复用、点名不展开**。第二阶段则把效果注解之间的关系收成约束集 C（形如一堆 β ⊑ β' 或 {…} ⊑ β），再解这组约束——对集合式效果，这就退化成 V3 见过的**⊆ 约束求最小解**（图闭包/worklist 传播，接 V6）。

对初学者，把两阶段对上前面学过的东西就通透了：第一阶段合一 = L5-06 T7 的 HM 推断（生成类型方程 → 合一求解）；第二阶段约束求解 = V3 的集合约束分析（生成 ⊆ 约束 → 求最小解）。所以"类型与效果推断"= "HM 类型推断"叠加"V3 式约束分析"，两块都是已学技术的组装，这就是 round-prompt 说的"与推断算法的关系：复用合一/约束求解"。为什么类型用合一（等式 =）、效果用约束（不等式 ⊑）？因为类型要求精确匹配（int 就是 int，箭头对箭头），是等式；而效果是过近似、只要"够大就行"，是包含不等式。这个"等式 vs 不等式"的分工，也解释了为什么第二阶段能沿用 V3 那套单调、有最小解、可 worklist 求解的框架。

### V5.4.4 一阶段算法：当类型与效果互相纠缠

若允许效果**反过来影响类型的形状**（例如 Standard ML 里为保证引用的类型安全，要禁止对"命令式类型变量"做泛化——效果信息决定了哪些类型变量可泛化，见下），两阶段就失效了，因为"定类型"和"定效果"互相依赖、没法分先后。这时需要**一阶段（one-stage）**算法：类型与效果一起推，在决定"泛化哪些变量"时必须**查约束集** C，算出一个比"直接出现在 Γ 和 φ 里的变量"更大的"禁止泛化"变量集（约束集下的向下闭包）。

对初学者，Standard ML 的可变引用是理解这个纠缠的经典坑。考虑

let r = new nil in ( r := cons(1, !r) ; r := cons(true, !r) )

若天真地给 r 一个多态类型 ∀α. (α list) ref，两次赋值都能过类型检查，但一次存 int list、一次存 bool list，类型系统就**不健全**了（ML 只允许同质列表）。修法正是用效果信息：副作用分析能识别出"被命令式地使用了的类型变量"，泛化规则就禁止对这些变量泛化——于是效果（怎么用的）决定了类型（能不能多态），二者纠缠，必须一阶段联合推断。这就是历史上著名的"多态引用"难题及其"命令式类型变量/值限制（value restriction）"系解法的由来。此处点名，工程细节归 L5-06 T4.4（引用与存储）与 Rust 侧 L5-14。

### V5.4.5 可判定性边界：多态递归、子类型与完备性的失守

这套方法论踩在**可判定与不可判定的边界**上，几处红线要记住。其一，**类型上的多态递归（polymorphic recursion over types）不可判定**——允许递归函数在自己体内也被多态使用，会让类型推断变成不可判定问题，因此没有既句法可靠又完备的终止算法；实用做法是只对**效果/区域变量**开放多态递归（如 Tofte-Talpin 区域推断），类型仍限制为单态递归。其二，**加子类型会急剧提升难度**——要处理 shape-conformant subtyping 且保持完备，一般必须把**约束显式放进推断系统**（而非像声明式规则那样藏起来），否则 principal type 可能根本无法表达；这也是为什么工业级带子类型的效果推断都是"约束式（constraint-based）"的。其三，对足够复杂的组合，**句法完备性可能失守或悬而未决**——区域推断的算法被证明句法可靠但**不完备**，而"既可靠又完备"对某些系统"超出当前技术水平（beyond state-of-the-art）"甚至不可能；好在**可靠性往往就足以让算法实用**（可靠 = 算出来的都对，只是可能不是最优/最一般）。

对初学者，把这三条红线读成"表达力越强、算法越难"的具体刻度即可：多态递归、子类型、类型效果互递归，每加一样，可判定性/完备性就退一步。这与 V1 的世界观完全一致——静态分析永远在"表达力 vs 可判定性"之间权衡，type-and-effect 路线只是把这条边界画在了"类型推断可判定性"这个特别经典的位置上（HM 主类型可判定，是这条路线的甜蜜点；越过它就步步惊心）。这也回答了"为什么不无脑追求最强系统"：够用、可靠、能跑，往往胜过理论最优却算不动。本节点名即止，各具体系统的完备性证明不深挖。
