## V1.1 Rice 定理与不可判定性

### V1.1.1 语法性质与语义性质的区分

理解 Rice 定理前必须先分清两类关于程序的性质。**语法性质**（syntactic property）只看程序的文本形状，例如"这段代码里含不含 `if` 语句""源码有没有超过 100 行""是否用到了变量 `x`"——这些扫一遍文本就能机械判定。**语义性质**（semantic property）关心的是程序**运行起来会做什么**（它计算出的那个"部分函数"是什么样），例如"这个程序对所有输入都停机吗""它算出的结果恒等于 0 吗""它会不会解引用空指针"。

给初学者的直觉与最小例子。判断"程序里有没有 `while`"是语法问题，`grep` 一下就有答案。判断"程序会不会死循环"是语义问题——它问的是运行行为，而运行行为可能要真跑无穷步才看得出来。关键的易错点是：语义性质说的是**程序所实现的函数/行为**，而不是"某一段具体代码"。两个写法完全不同的程序，只要输入输出行为一模一样，在语义性质上就必须被同等对待。正是这一点让语义性质极难判定——你不能靠"看它长什么样"来回答"它到底算什么"。

### V1.1.2 Rice 定理的陈述

Rice 定理（Rice 1953）用一句话概括就是：**图灵完备语言上，程序的一切非平凡语义性质都是不可判定的**。这里两个限定词都不可少。"语义性质"指只依赖程序所计算的部分函数（行为）、不依赖具体写法的性质。"非平凡"（non-trivial）指这个性质**既不是对所有程序都成立、也不是对所有程序都不成立**——也就是说，至少有一个程序具有该性质、至少有一个程序不具有。定理的形式陈述（以可计算函数编号 φₑ 表述）为：

```
设 F 是一个部分递归函数的集合（一个"语义性质"），
且 F 非平凡（F ≠ ∅ 且 F 不等于全部部分递归函数）。
令 A_F = { e | φₑ ∈ F }（具有该性质的程序编号之集合）。
则 A_F 不可判定（不存在总停机的算法对任意 e 判定 e ∈ A_F 是否成立）。
```

给初学者的直觉。"平凡"的性质有两个：恒真性质（"这是不是一个程序"——所有程序都算，废话）和恒假性质（"这个程序既停机又不停机"——没有程序满足，也是废话）。这两个当然可判定：直接输出"是"或"否"即可。Rice 定理说的是：**除了这两个废话性质，凡是你真正关心的语义问题——会不会停机、结果对不对、有没有越界、是不是常函数——统统没有万能判定算法。** 要提醒的常见误解：Rice 定理不是说"对某个具体程序也答不出来"。对一个具体程序，答案客观存在（要么有该性质要么没有），有时你甚至一眼看穿；定理否定的是"存在一个对**所有**程序都正确且总停机的通用判定器"。

### V1.1.3 为什么成立：归约自停机问题的直觉

Rice 定理是**停机问题不可判定性的推广**，本节只讲证明的直觉骨架，不铺完整构造（那属专家纵深）。核心手法是**归约**（reduction）：假设我们真有了一个能判定某非平凡语义性质 P 的万能算法，就用它去解停机问题；但停机问题已知不可判定，于是这个假设矛盾，P 的判定器不可能存在。

给初学者的直觉与最小例子。设想性质 P 是"这个程序算出的函数恒等于常数 0"（非平凡：`λx.0` 有，`λx.x+1` 没有）。要判定"任意程序 M 在输入 w 上是否停机"，我可以机械地造一个新程序：

```
构造 M_w(x) = 先忽略 x，模拟 M 在 w 上运行；
             若 M(w) 停机，则返回 0；（否则永远算下去、不返回）
```

于是 M_w 计算的函数"恒等于 0"当且仅当 M(w) 停机。若真有 P 的判定器，把它用在 M_w 上就等于解了停机问题——矛盾。这个"把待判定的语义问题偷偷编码进一个新程序的行为里"的套路，就是归约的精髓。要强调的关键点：这里用到的正是 V1.1.1 的语义视角——判定器只能看 M_w 的行为、看不出它内部藏着"模拟 M(w)"这件事，所以无从作弊。

### V1.1.4 世界观含义：为什么整门课都建立在"近似"上

Rice 定理是本课的**世界观钉子**：它一劳永逸地宣判了"写一个既总能终止、又永远精确回答某个有趣语义问题的程序分析器"是不可能的。所以任何真实可用的静态分析，必然在三件事里放弃至少一件——要么不保证终止、要么不保证精确（给近似答案）、要么只回答平凡问题。工程上的统一选择是：**保证终止 + 给出安全方向的近似答案**，这就直接引出 V1.3 的过/欠近似框架。

给初学者的意义与关联。这解释了为什么后面每一种技术（数据流分析、抽象解释、类型系统、模型检验……）都带着"可能误报""可能漏报""结果是保守估计"这类说法——不是它们做得不够好，而是 Rice 定理从根上禁止了"完美"。同时要澄清一个边界：Rice 定理限定在**图灵完备**语言上；如果你的语言故意不图灵完备（例如无循环、或循环有界的领域语言、总停机的类型系统片段），某些语义性质就可能重新变得可判定——这正是许多受限 DSL、终止性类型系统、有界模型检验之所以可行的根本原因。Rice 定理划的是"图灵完备"这条线，越过它才不可判定。

## V1.2 静态分析总览与 WHILE 语言

### V1.2.1 什么是静态程序分析

**静态程序分析**（static program analysis）指**不实际运行程序、仅从程序文本出发，计算关于其动态行为的可靠近似信息**的技术。PPA 开篇一句话定义即"computing reliable approximate information about the dynamic behaviour of programs"（关于程序动态行为的、可靠的、近似的信息）。三个词都是承重的：static（不跑，或不完整地跑）、reliable（可靠——结果在某个安全方向上不会骗你）、approximate（近似——由 V1.1 的 Rice 定理，精确不可能）。

给初学者的直觉与关联。把它和"动态分析"对照最清楚：动态分析（如测试、打印日志、profiler）真跑程序、看具体某几次执行；它精确但只覆盖跑到的那些路径，可能漏掉没触发的情形。静态分析反过来——不跑、一次性对**所有可能执行**下结论，代价是结论必须近似。典型应用有三类（PPA 引言列举）：编译器优化（据分析结果安全地改写代码）、软件校验（查错误/安全漏洞）、程序变换（在不同数据表示间转换）。要避免的误解是把静态分析等同于"编译器报的语法错误"——语法错误是语法性质（V1.1.1），而静态分析瞄准的是语义性质那一侧，难度本质不同。

### V1.2.2 WHILE 语言与标号

PPA 全书的**运行示例语言是 WHILE**——一个刻意做到最小的命令式语言：只有算术表达式、布尔表达式，以及赋值、`skip`、顺序 `;`、`if-then-else`、`while` 五种语句。它的语句语法（PPA Ch.1 记法）大致为：

```
a ::= x | n | a₁ op_a a₂                       （算术表达式）
b ::= true | false | not b | b₁ op_b b₂ | a₁ op_r a₂   （布尔表达式）
S ::= [x := a]ℓ | [skip]ℓ | S₁ ; S₂
    | if [b]ℓ then S₁ else S₂
    | while [b]ℓ do S
```

关键约定是给每个基本块（elementary block，即每个赋值、skip、判定）打一个唯一的**标号**（label）ℓ，写成 `[…]ℓ`。PPA Ch.1 用来贯穿全书的经典示例程序是求幂/阶乘式：

```
[y := x]¹ ; [z := 1]² ; while [y > 1]³ do ( [z := z * y]⁴ ; [y := y - 1]⁵ ) ; [y := 0]⁶
```

给初学者的直觉与为什么这样设计。选 WHILE 是因为它**图灵完备**（有 `while` 就能表达任意可计算函数，所以 Rice 定理照样适用、近似仍是必须的），同时又小到能把每种分析的规则完整写下来而不被语言细节淹没。标号的作用是给"程序里的位置"起名字：数据流分析要谈"在第 3 个点，哪些变量是活的""哪些定值到达了这里"，没有标号就没法精确指认"这里"。要提醒的易错点：标号标的是**程序中的静态位置**，不是运行时的执行次数——同一个 `[…]³` 在 while 循环里会被执行很多次，但它始终是同一个标号 ℓ=3，分析正是要对"这个位置的所有次执行"一并下结论。

PPA 的核心贡献是指出：看似五花八门的程序分析，其实归结为**四大方法**，Ch.1 先用 WHILE 例子把它们各演示一遍，Ch.2–Ch.6 再逐个展开。四大方法加上通用求解算法，恰好对应本课后续大主题：

给初学者的直觉与关联。这几种方法表面记法差别很大（数据流用格上的方程、约束式用集合包含约束、抽象解释用 Galois 连接、类型效果用推理规则），但 PPA 反复强调它们在做**同一件事**——对程序行为求安全近似——只是"数学外衣"不同，很多时候还能互相翻译。这就是为什么把 V1 当世界观钉子：先立起"不可判定 ⟹ 必须近似"这根柱子，后面四种方法都是同一根柱子上挂的不同工具。一个常见的初学者困惑是"到底该学哪个"——答案是它们不是竞品而是不同视角，抽象解释（V4）甚至提供了一个能把数据流分析统一涵盖进去的通用框架（回接 V4.4）。此处不展开各方法内部机制，仅作导览；细节归 V2–V6。

## V1.3 over-/under-approximation：sound vs complete、假阳/假阴

### V1.3.1 为什么必须近似，以及近似的两个方向

由 V1.1，精确回答语义问题不可判定，所以分析只能计算真实行为集合的一个**近似**。近似只有两个安全方向。设真实（但不可计算）的行为/状态集合为 C（concrete），分析计算出的可计算集合为 A（analysis result）：

```
过近似（over-approximation）：  A ⊇ C   （宁可多算，不漏真实行为）
欠近似（under-approximation）： A ⊆ C   （宁可少算，只保证算进来的都真会发生）
```

给初学者的直觉与最小例子。想象 C 是"程序运行时变量 x 真正可能取到的值的集合"，比如真实是 C = {2, 4}。过近似给出 A = {偶数}（把 x 可能取的值放大成一个更大的、好描述的集合，绝不遗漏 2 和 4）；欠近似给出 A = {2}（只保留能确证一定会出现的值，宁可漏掉 4）。要点是：**近似必须朝一个固定方向偏，才谈得上"可靠"**——一个既可能多算又可能少算、方向不定的估计是没有安全保证的，不能拿来下结论。选哪个方向，取决于你要回答的是"可能"型问题还是"一定"型问题（下面两节）。

### V1.3.2 sound（可靠）= 朝安全方向的近似

**sound（可靠/健全）** 的直觉口号是：**分析给出的保证，真实执行绝不违反**。对一个"某坏事**可能**发生吗（may）"型的问题（如"这里可能空指针解引用吗""这个指针可能指向哪些对象"），可靠性由**过近似**保证——把可能发生的坏事集合放大，只要放大后的集合里没有坏事，真实就一定没有：

```
用过近似证明安全性（may 性质）：
  若 over-approx 结果中不含任何"坏状态"，
  则真实执行也绝不进入坏状态（可靠：不漏报违规）。
```

给初学者的直觉与为什么。因为 A ⊇ C，A 里"干净"（无坏事）能推出 C 里也干净（子集当然干净）；反过来若 A 里出现坏事，可能只是那个坏事在放大部分里、C 中并不真发生。所以过近似分析**验证安全性时是可靠的、不会漏掉真违规**，代价是它可能对着"其实不会发生的坏事"虚报。要提醒的关键点：可靠性是"分析所声称的那种保证"意义上的——一个 may 分析的可靠性等于"它列出的可能性覆盖了全部真实可能性"，而不是"它列出的每一项都真会发生"。

### V1.3.3 complete（完备）= 反方向的近似，及"两者不可兼得"

**complete（完备）** 的直觉口号与可靠对偶：**真实成立的，分析都能报出来**——分析不遗漏任何真实情形，代价是它报的可能有假。对"某事**一定**发生吗（must）"型问题，或用分析做**找 bug**（只想报真 bug）时，用**欠近似**：

```
用欠近似只报真情形（must 性质 / 只报真 bug）：
  A ⊆ C ⟹ 凡分析报出的，真实一定成立（无虚报），
           但可能漏掉真实成立却没算进来的（不完备）。
```

由 V1.1 的 Rice 定理可推出一条铁律：**对任何非平凡语义性质，不存在既可靠、又完备、还保证终止的分析**——三者最多得其二。真实分析普遍**保留可靠、放弃完备**（即接受"虚报"以换取"绝不漏真违规"），这是静态验证的默认工程取向。

给初学者的直觉与关联。可靠 vs 完备就是"宁可错杀不可放过"（可靠：不放过真违规，代价错杀）与"宁可放过不可错杀"（完备：不错杀，代价放过）两种偏向，Rice 定理禁止你同时做到"既不错杀也不放过还总停机"。这也解释了两大用途的分野：编译器优化与安全验证要**可靠**（一次漏报可能酿成错误优化或漏掉真漏洞），所以容忍误报保守一点；某些 bug 猎手工具则偏向少误报（图开发者体验），于是主动牺牲可靠性只报高置信项。选择哪一半，取决于"漏报的代价"和"误报的代价"哪个更贵。

### V1.3.4 假阳 vs 假阴，以及"哪个是哪个"取决于框架（务必别写反）

**假阳性（false positive，假阳/误报）** 指分析**报了警、但实际不会发生**的那种坏事；**假阴性（false negative，假阴/漏报）** 指实际会发生、但分析**没报出来**的坏事。它们与 sound/complete、over/under 的对应，在"用分析证明安全（验证）"这一主流框架下为：

```
主流框架 = 用分析证明"程序安全/无 bug"（验证视角）：
  可靠 sound      ⟺ 无假阴（不漏掉真 bug）  ⟵ 由过近似 over-approx 保证
  完备 complete   ⟺ 无假阳（不误报假 bug）  ⟵ 由欠近似 under-approx 保证
  典型静态分析器：可靠但不完备 ⟹ 无漏报、但有误报（假阳）
```

给初学者最需要小心的易错点——**这套对应会因"你把分析当验证器还是当 bug 猎手"而整体翻转，是本领域最容易写反的地方**。上面是验证视角（PPA / 抽象解释的默认）：sound = 覆盖全部真实行为 = 不漏真违规 = 无假阴。但在动态分析/测试社区，"sound"常被用成相反含义——"每个报出的 bug 都是真的"（无假阳）。两种用法都合法，冲突点在于"分析声称保证的是哪一侧"。避免写反的可靠办法：**别背 "sound=无假阳还是无假阴" 这种死记，而是回到定义**——先问"这个分析对着什么集合做过近似还是欠近似"，再问"它声称的保证是哪一侧不出错"，对应关系就自然推出来，不会记反。一个自检小例：一个可靠的空指针分析报出 100 处"可能解引用空指针"，其中只有 3 处真会发生——那 97 处就是假阳（误报），而"可靠"恰恰保证了不存在第 101 处它没报却真会崩的（无假阴）。

### V1.3.5 精度（precision）与保守（conservative）

在"方向选定、可靠性保住"的前提下，衡量分析好坏的量是**精度**（precision）——它把近似做得多贴近真实、少产生多余的假阳。一个可靠但精度低的分析是安全的（不漏报）但没用（满屏误报）；提高精度是绝大多数分析技术（流敏感、上下文敏感、更精细的抽象域）的核心追求。与精度同义反复出现的词是**保守（conservative）**：一个保守的近似就是朝安全方向偏、宁可牺牲精度也不牺牲可靠性的近似。

给初学者的直觉与关联。可靠性是"对不对"（红线，不能破），精度是"有没有用"（好不好，可持续改进）。二者常此消彼长：分析想更精确，往往要付出更多计算代价（回接 V4.2 抽象域的"精度—代价权衡"、V2 的流敏感 vs 流不敏感）。要澄清的边界：精度再高也**不可能达到 100% 精确**——那就等于既可靠又完备，被 Rice 定理禁止；精度提升永远是在"可容忍的假阳率"上做文章，而非消灭假阳。

- 交叉印证（一手/权威）：Livshits, Sridharan, Smaragdakis et al.《In Defense of Soundiness: A Manifesto》, Communications of the ACM 58(2):44–46, 2015——明确"sound 静态分析 = 过近似真实行为""soundness 与 completeness 的取舍""无假阳与无假阴不可兼得"，与本节验证视角一致（https://yanniss.github.io/Soundiness-CACM.pdf ，核实 2026-07-30）。

## V1.4 分析的正确性论证

### V1.4.1 "正确"是相对语义而言的

一个静态分析给出的近似，凭什么敢说它"可靠"？答案是：**必须相对程序的语义来证明它可靠**。也就是先给 WHILE 语言一个精确的**语义**（通常是操作语义，规定每个程序真正会怎么一步步执行），再证明"分析算出的信息，被每一次真实执行所满足"。没有这一步，"分析结果可靠"只是口头承诺；有了它，可靠性成为一条被证明的数学定理。PPA 把这类结论称为分析的**语义正确性**（semantic correctness / soundness of the analysis）。

给初学者的直觉与为什么。语义在这里扮演"真相"的角色——它是那个不可计算但客观存在的 C（真实行为）。分析结果 A 是可计算的近似。"正确性论证"就是证明 A 与 C 之间那个安全方向的包含关系（A ⊇ C 或 A ⊆ C，见 V1.3）确实成立。要提醒的关键点：正确性是**分析设计者的义务**，不是使用者能事后检验的——正因为 C 不可计算，用户没法逐个程序去核对；所以分析框架必须一次性地、对所有程序证明可靠，这正是把分析建立在坚实语义之上的意义。

### V1.4.2 正确性关系与"保持性"证明骨架

标准做法是定义一个**正确性关系**（correctness relation，常记作类似 σ ⊨ A 或 R(σ, A)），刻画"一个真实运行时状态 σ 被分析信息 A 所正确描述/覆盖"是什么意思；然后证明这个关系在语义的每一步转移下**被保持**（preserved）。骨架为：

```
（1）初始相容：程序入口的初始状态 σ₀ 被分析入口信息所覆盖，R(σ₀, A_entry)。
（2）保持性：若 R(σ, A) 且语义允许一步 σ → σ'（从标号 ℓ 走到 ℓ'），
             则 R(σ', A') 仍成立（A' 是 ℓ' 处的分析信息）。
（3）归纳：由（1）（2）对执行步数归纳 ⟹ 每一次可达的真实状态都被分析覆盖，
             即分析对全部真实执行可靠。
```

给初学者的直觉与关联。这套"定义一个'覆盖/相容'关系 + 证明它在每步转移下不被打破 + 对步数归纳"的模板，和 L5-06 T3 里证明类型安全用的 **Progress + Preservation** 是同一个思想的两个化身——那里保持的是"良类型"，这里保持的是"被分析信息正确覆盖"；两者都靠"局部一步守恒 + 归纳推到整条执行"把一个关于无穷多次执行的全局命题证下来。一个最小的体会：对到达定值分析（V2），正确性关系大意是"若运行时变量 x 的当前值来自某次赋值，则该赋值的标号一定在分析算出的'到达此处的定值集合'里"；保持性要逐条检查每种语句（赋值把新定值加进去、把被覆盖的旧定值移除……）都不破坏这个关系。要避免的误解：正确性证明保证的是"可靠"（不漏），**不保证"精确"**——分析完全可以正确地覆盖了真实状态却同时覆盖了一堆假状态（那是精度问题，V1.3.5），这与它"正确"并不矛盾。

### V1.4.3 与后续框架的接口

不同方法把"正确性关系"具体化为不同数学对象，但都在做 V1.4.2 那件事，本节只点名不展开。数据流分析（V2）用"传递函数单调 + 格上最小不动点"承载，正确性即不动点解安全覆盖真实数据流。抽象解释（V4）把正确性关系精确化为**Galois 连接**（抽象化 α 与具体化 γ 的一对伴随），并要求抽象转移函数与具体转移函数满足可靠性条件——这是把"相对语义证明可靠"这件事做到最一般、最系统的框架，可反过来涵盖数据流分析（回接 V4.4）。演绎验证（V9）与模型检验（V8）则用逻辑蕴含/满足关系来承担"相对语义正确"的角色。

给初学者的意义与关联。V1.4 是把 V1.3 的"安全近似"从口号钉成方法论：任何一个自称可靠的分析，背后都欠着一份"相对语义的正确性证明"。理解了这份共同义务，再看 V2–V11 各家花样繁多的记法，就能一眼认出它们都在回答同一个问题——"我算出的近似，凭什么覆盖了全部真实行为？"这也回扣本大主题开头的世界观：Rice 定理逼我们近似（V1.1），近似分两个安全方向（V1.3），而"正确性论证"（V1.4）就是给近似盖上"确实安全"的合格印章。此处各框架细节全部归其对应大主题，不展开。
