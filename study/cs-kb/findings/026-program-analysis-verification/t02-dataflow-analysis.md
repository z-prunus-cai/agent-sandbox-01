## V2.1 四经典分析与方向

### V2.1.1 数据流分析要算的东西：每个程序点上的 IN 与 OUT

数据流分析在不实际运行程序的前提下，静态推算"在每个程序点，某一类信息取什么值"。做法是给控制流图上每个基本块（或每条语句）关联两个数据流值——进入前的 IN 和离开后的 OUT——然后列一组方程把它们联系起来，方程的解就是分析结果。

对初学者，核心矛盾是：程序有分支和循环，一个点可能从多条路径到达，实际路径可能无穷多，你没法逐条枚举。数据流分析的巧妙处在于不枚举路径，而是把"每个点的信息"当未知数，写出"这个点的信息 = 它前驱（或后继）传来的信息经过本块加工后的结果"这样的递归方程，再迭代解出来。一个分析由四件事完全确定——信息住在哪个格里（V2.2）、每块的传递函数怎么写（V2.3）、汇合时用 ⊔ 还是 ⊓（本节 may/must）、沿控制流往前还是往后传（本节方向）。把这四件事填不同的值，就得到不同的分析。

PPA 用同一个运行示例语言 WHILE（承 V1.2：赋值、序列、if、while 的极小命令式语言）来讲这四个分析，好处是四个分析共用一套程序、只换"信息"和"方向/汇合"，对照极其清晰。

### V2.1.2 到达定值分析（前向 / may / 并 ⊔=∪）

到达定值（reaching definitions）分析：对每个程序点，求出有哪些"定值"（对某变量的赋值出现点）能够**不被重新覆盖地**流到该点。它是前向分析，汇合用并（∪），属于 **may（可能）** 分析——只要**存在一条**路径让定值 d 流到该点，d 就算到达。传递函数是经典的 gen/kill 形式：

OUT[B] = gen_B ∪ (IN[B] − kill_B)

IN[B] = ⋃ over P ∈ pred(B) of OUT[P]

其中 gen_B 是 B 内产生且未被 B 内后续赋值覆盖的定值，kill_B 是被 B 内赋值覆盖掉的、对同一变量的其它所有定值。

初学者可把它理解成"这个变量的值是从哪几处赋来的"的追踪。用并、用 may 的原因是**安全方向**：后续优化（如判断某处 x 是否常量）要依赖"能到达这里的定值全集"，若漏算了一个能到达的定值就可能基于错误前提改错代码，所以宁可多算（把所有可能到达的都算上）也不能少算——多算只是让结论保守（可能到达其实没到达），不会出错。这就是 may 分析普遍取并的道理。用 PPA 的格定向说：信息装进 (P(Defs), ⊆)，⊔ = ∪，⊥ = ∅，least solution 就是"最小的、仍覆盖所有可能"的安全集合。

### V2.1.3 可用表达式分析（前向 / must / 交 ⊔=∩）

可用表达式（available expressions）分析：对每个程序点，求出有哪些表达式（如 `a+b`）在到达该点的**每一条**路径上都已被计算过、且其操作数此后都没被改动——即"这里再算一遍是白算，可直接复用"。它是前向分析，汇合用**交（∩）**，属于 **must（必然）** 分析——必须**所有**路径都算过才算可用。传递函数：

OUT[B] = e_gen_B ∪ (IN[B] − e_kill_B)

IN[B] = ⋂ over P ∈ pred(B) of OUT[P]

e_gen_B 是 B 内算出且其后未被 B 内改动操作数的表达式，e_kill_B 是操作数被 B 内赋值改动因而失效的表达式。

与到达定值的关键对照是**取交不取并、must 不 may**：删一个"重复计算"必须百分百确定它真的每条路都算过，漏删只是少优化（不出错），错删（某条路其实没算过、复用了脏值）就是灾难——所以安全方向反过来，取交、并把边界/入口初始化成**全集**（最保守地假设"一切都可用"，再靠交一步步删掉不满足的）。这里要点破一个初学者的常见误区：must 分析取交不代表"信息更少"，恰恰相反，它的初值是全集、迭代过程是不断**缩小**，安全侧在"交得到的下界"。PPA 的定向把它装进 (P(Exprs), ⊇)（把包含关系反过来），于是 ⊔ 在这个反序里正好实现 ∩，⊥ 是全集——这样四个分析就都能统一写成"⊔ + least solution"，代价是 must 分析的格要倒着看（这正是 V2.4 记法对账要处理的根源）。

### V2.1.4 活跃变量分析（后向 / may / 并 ⊔=∪）

活跃变量（live variables）分析：对每个程序点，求出有哪些变量的当前值在将来**还可能被使用**（在被重新赋值之前）。它是**后向**分析（从出口往入口、沿前驱方向传播），汇合用并（∪），是 may 分析。方程：

IN[B] = use_B ∪ (OUT[B] − def_B)

OUT[B] = ⋃ over S ∈ succ(B) of IN[S]

其中 use_B 是 B 内"先使用、（在本块内）未先被定值"的变量，def_B 是 B 内被赋值的变量。

它是死代码消除、寄存器分配的理论基础（那些应用在 L4-04 C9），本篇只关心它的结构。为什么后向？因为"将来会不会被用到"这个问题的答案在**后面**，必须从使用点往回倒推。这也是初学者最容易和到达定值搞反的地方——同是 may/并，但一个前向（信息随执行往前流）、一个后向（需求从末尾往回流）。

本篇做了一个小的可复现实证以坐实"有限高度 + 单调 ⟹ 快速收敛"（V2.2–V2.3）。对一个含分支的五块流图（B1: `a=b+c`；B2: `if a<0` 分叉到 B3/B4；B3: `c=a+1`；B4: `d=a+2`；B5: `x=c`）跑后向 may 迭代，**2 轮达不动点**：

```
live-variables MFP, sweeps to fixpoint = 2
  B1: IN=['b', 'c'] OUT=['a', 'c']
  B2: IN=['a', 'c'] OUT=['a', 'c']
  B3: IN=['a'] OUT=['c']
  B4: IN=['a', 'c'] OUT=['c']
  B5: IN=['c'] OUT=[]
```

注意 B2 的 OUT 含 `c`：分支后继之一 B3 用到 c、另一支 B4 不用，may 取并——只要**一条**后继路径还要 c，c 就在 B2 出口保持活跃。这直观展示了"后向 + 并"如何保守地跨分支保住一个变量。（脚本跑于 scratchpad，未入库；环境 Py3.11.15。）

### V2.1.5 极忙表达式分析（后向 / must / 交 ⊔=∩）

极忙表达式（very busy expressions，PPA 用此名；亦称 anticipated expressions 预期表达式）分析：对每个程序点，求出有哪些表达式在从该点出发的**每一条**路径上，都会在其任一操作数被改动之前先被计算。它是**后向 + must + 交**分析——四个经典分析里"方向 × 汇合"矩阵剩下的那一格。方程与可用表达式对称，只是沿后继取交：

IN[B] = e_gen_B ∪ (OUT[B] − e_kill_B)

OUT[B] = ⋂ over S ∈ succ(B) of IN[S]

它的用途是**代码提升（hoisting）**：一个表达式若在某点极忙，就说明无论之后走哪条分支它都要算，那不如把它提前到该点算一次，缩减代码体积（各分支不必各算一份）。

对初学者，极忙表达式最好的记法是"未来一定会用到的计算"——must 决定了它要求**所有**后继路径都用到（取交），backward 决定了它看的是**未来**。把它和另外三个放一起，四个经典分析恰好铺满一张 2×2 表（方向 × may/must），这张表是数据流分析设计的"骨架图"，见下一节。

### V2.1.6 方向与 may/must：两个正交维度

四个经典分析可由两个正交维度完全归类：**方向**（前向 forward / 后向 backward）与 **may/must**（是否只需一条路成立）。may 分析取**并**、求"至少一条路成立"的最小安全上界；must 分析取**交**、求"所有路都成立"的最大安全下界。列成表：

| 分析 | 方向 | may/must | 汇合（集合视角） | 初值/边界 |
|------|------|----------|------------------|-----------|
| 到达定值 Reaching Definitions | 前向 | may | 并 ∪ | ∅ |
| 可用表达式 Available Expressions | 前向 | must | 交 ∩ | 全集 |
| 活跃变量 Live Variables | 后向 | may | 并 ∪ | ∅ |
| 极忙表达式 Very Busy Expressions | 后向 | must | 交 ∩ | 全集 |

这张表要抓两条直觉。其一，**方向** = "信息的因果朝向"：到达定值/可用表达式问的是"过去发生了什么"（前向），活跃变量/极忙表达式问的是"未来会怎样"（后向）。其二，**may/must = 安全方向的选择**：想收集"可能性"（谁可能到达、谁可能还要用）就取并、宁多勿漏；想断言"确定性"（哪条计算铁定重复、铁定要用）就取交、宁缺勿滥。一个易错点是把 may↔并、must↔交 记成僵硬对应——它们的绑定其实来自"哪种错误是灾难性的"：may 分析里漏报是灾难，故取并把候选放大；must 分析里误报是灾难，故取交把断言收紧。理解了这层，就不用死记表格。

## V2.2 格论基础

### V2.2.1 偏序集：给"更精确/更保守"一个方向

一个**偏序（partial order）**是集合 L 配一个关系 ⊑，满足自反（l ⊑ l）、传递（l1 ⊑ l2 且 l2 ⊑ l3 ⟹ l1 ⊑ l3）、反对称（l1 ⊑ l2 且 l2 ⊑ l1 ⟹ l1 = l2）。"偏"的意思是允许有两个元素互不可比。

数据流分析里，数据流值就住在一个偏序集里，⊑ 编码"信息的近似方向"。在 PPA 定向下，l1 ⊑ l2 读作"l1 比 l2 更精确、l2 比 l1 更保守/更安全"。初学者要接受一点反直觉：分析的目标不是"求最精确"，而是"求最精确的**安全**近似"——安全近似住在 ⊑ 的较大一侧，所以很多分析求的是满足约束的**最小解**（least solution，在安全前提下尽量往精确压）。为什么允许"不可比"？因为两个数据流值可能各自在不同变量上更精确，没有全局的谁强谁弱——偏序而非全序正是为容纳这种情形。

### V2.2.2 格与完全格

在偏序 (L, ⊑) 中，若任意两个元素 l1, l2 都有唯一的**最小上界（least upper bound，join，记 l1 ⊔ l2）**和**最大下界（greatest lower bound，meet，记 l1 ⊓ l2）**，则 (L, ⊑, ⊔, ⊓) 是一个**格（lattice）**。若更强地，**任意子集** Y ⊆ L（含空集与无限子集）都有 ⊔Y 与 ⊓Y，则称**完全格（complete lattice）**。完全格必有唯一顶元素与底元素：

⊤ = ⊔L = ⊓∅

⊥ = ⊓L = ⊔∅

数据流分析要求信息住在**完全格**里。原因是分析要对"多条路径汇合"取 ⊔（或对整个可达路径集取上确界），若只保证两两有上界、无穷子集却没有上界，理论就不闭合。最贴身的例子是**幂集格**：给定有限集合 D（如程序里所有定值），(P(D), ⊆) 就是完全格，⊔ = ∪，⊓ = ∩，⊤ = D，⊥ = ∅——四大经典分析用的正是它。初学者可以把完全格想成"一把有头（⊤）有尾（⊥）的尺子，任意一堆刻度都能找到刚好压住它们的上确界和下确界"，数据流值只能在这把尺子上取位置，迭代就是让每个点的值在尺子上单向滑动到稳定。要留意 ⊔/⊓ 与 ∪/∩ 不是永远等同——它俩等于并/交只在"幂集 + 子集序"这个具体格里成立；换个格（如 V2.4 常量传播的三层格），⊔/⊓ 就是别的运算。

### V2.2.3 升链条件（ACC）：保证迭代会停

一个偏序满足**升链条件（Ascending Chain Condition, ACC）**，若不存在无限严格上升的链——即任何链

l1 ⊑ l2 ⊑ l3 ⊑ …

都会在有限步后稳定（∃n 使 l_n = l_{n+1} = …）。对称地有**降链条件（DCC）**。

ACC 是**迭代算法必然终止**的那条腿（另一条腿是传递函数单调，见 V2.3）。直觉：迭代过程中每个点的值只会沿 ⊑ 单调上升（信息越变越保守），若格里没有"无限往上爬的梯子"，就一定在有限轮内爬到顶不动为止。最省事的充分条件是格**有限高度**（最长链长度有限），有限幂集格自动满足。一个易错点：完全格不一定满足 ACC（实数区间 [0,1] 配 ≤ 是完全格但有无限上升链），所以"完全格"保证解**存在**（V2.3.5 的不动点定理），"ACC/有限高度"才保证解**算得完**——两者管的是不同的事，别混为一谈。正因区间等格不满 ACC，抽象解释才需要 widening 来强行截断（见 V4，本篇不展开）。

## V2.3 单调框架与传递函数

### V2.3.1 传递函数：一块代码怎么改动信息

**传递函数（transfer function）**f_B: L → L 描述基本块 B 如何把入口信息变成出口信息。前向分析写 OUT[B] = f_B(IN[B])，后向写 IN[B] = f_B(OUT[B])。四大经典分析的传递函数都是 **gen/kill（生成/杀死）** 形式：

f_B(l) = gen_B ∪ (l − kill_B)

读作"B 新产生的信息 gen_B，加上入口信息里没被 B 消灭（kill_B）的那部分"。

对初学者，传递函数就是"把一块代码的语义压缩成对信息集合的一次加减"。gen/kill 形式之所以处处出现，是因为绝大多数"位向量式"的信息（每个定值/表达式/变量是一个开关位）确实只被一块代码单调地开几位（gen）、关几位（kill），与入口信息里的其它位无关——这种"逐位独立"正是下面分配性的来源。

### V2.3.2 单调性：迭代收敛的另一条腿

传递函数必须**单调（monotone）**：

l1 ⊑ l2 ⟹ f(l1) ⊑ f(l2)

含义是"喂进更保守的信息，吐出的也不会更精确"——函数不会把 ⊑ 的方向拧反。

单调性 + ACC（V2.2.3）合起来，是迭代算法终止且解有意义的完整保证：单调保证迭代序列 ⊥ ⊑ f(⊥) ⊑ f(f(⊥)) ⊑ … 单调上升不回头，ACC 保证这条上升链有限步稳定。初学者常把单调性误当成"传递函数得连续/线性"——不需要，只要不逆转序即可；也别把它和分配性（V2.3.3）混淆：单调是**必需**的最低要求（否则迭代可能震荡不收敛），分配是**更强**的可选性质（决定迭代解精不精确，见 V2.4）。gen/kill 传递函数显然单调（往集合里加 gen、减固定的 kill，都保持 ⊆）。

### V2.3.3 单调框架与分配框架

一个 **单调框架（Monotone Framework）** 由一个满足 ACC 的完全格 L 和一族单调传递函数 F（含恒等、对复合封闭）构成，是数据流分析的通用抽象。更强的是 **分配框架（Distributive Framework）**：要求所有传递函数**分配于 ⊔**——

f(l1 ⊔ l2) = f(l1) ⊔ f(l2)

分配 ⟹ 单调（把 l2 换成 l1 ⊔ l2 即得），反之不然。

这两个框架的区别是本大主题最重要的分水岭：**单调**保证迭代**收敛且安全**；**分配**额外保证迭代解**恰好等于理想解**（V2.4）。gen/kill 形式的传递函数天然分配（本篇实证：对全集 {a,b,c,d} 上 f(x)=gen∪(x−kill) 穷举所有子集对 A,B，验证 f(A∪B)=f(A)∪f(B) 恒成立）——

```
gen/kill distributes over union (bit-vector framework): True
```

所以四大经典分析都在分配框架内，迭代即最优。PPA 把这类 gen/kill 的分配框架专称为**位向量框架（bit-vector framework）**。反例是常量传播：它的传递函数只单调、不分配（见 V2.4），是"单调但非分配"的标准代表。（穷举脚本跑于 scratchpad，未入库；Py3.11.15。）

### V2.3.4 不动点的存在与最小解（Knaster–Tarski）

数据流方程本质是求某个单调函数 F: L → L 的**不动点**，即满足 F(x) = x 的 x。**Knaster–Tarski 定理**保证：完全格上任一**单调**函数的不动点集合本身也构成完全格，因而必有**最小不动点（least fixed point, lfp）**与最大不动点。数据流分析取的是最小不动点（PPA 定向下 = 最精确的安全解），且它等于从 ⊥ 出发迭代的极限：

lfp(F) = ⊔ { F^n(⊥) : n ≥ 0 }

（当 L 满足 ACC 时这个上确界在有限步达到，即迭代必然停在 lfp）。

这条定理是"迭代为什么解得出、解出来的是不是唯一确定的东西"的最终答案。初学者只需记住因果链：**完全格**给了"不动点一定存在且有最小者"（Knaster–Tarski，靠单调）；**ACC/有限高度**给了"从 ⊥ 迭代有限步就到达那个最小不动点"（靠单调 + ACC）。把方程组的多个 IN/OUT 打包成一个大向量、整体看成一个 L^k 上的单调函数，同样的定理照用不误。一个易错点：不动点可能不止一个，分析选**最小**不动点是有意的——它对应"在安全前提下承诺得最少、最精确"的那个解；选最大不动点会得到平凡而无用的保守解。

## V2.4 MFP vs MOP

### V2.4.1 MOP：理想的"全路径汇合"解

**MOP（Meet Over all Paths，全路径汇合解）**是理论上最精确的安全答案：对到达某程序点 ℓ 的**每一条**路径 π，各自从入口沿 π 施加传递函数得 f_π(ι)，再把所有路径的结果汇合。PPA 定向（⊔）下写作：

MOP(ℓ) = ⊔ { f_π(ι) : π ∈ path(ℓ) }

其中 ι 是入口的初始信息，path(ℓ) 是从入口到 ℓ 的所有路径集合，f_π 是路径上各块传递函数的复合。

"MOP"这名字带 Meet 是历史遗留（早期文献用 meet 定向），PPA 虽用 ⊔ 仍沿用旧名，初学者别被字面误导——它的运算就是把各路径结果按格的汇合运算合起来。MOP 是"金标准"：它先让每条路各自算到底、最后才合并，没有任何过早的信息损失，因此是**在给定抽象下能达到的最精确安全解**。问题在于——路径集合通常无穷（有循环），MOP 一般**不可计算**（承 V1：这是把不可判定真相做近似时又冒出的一层不可计算性）。

### V2.4.2 MFP：可计算的迭代不动点解

**MFP（Maximum Fixed Point）**是 V2.3.4 那个迭代算法实际算出的解——把 IN/OUT 当未知数列方程组、从 ⊥ 迭代到不动点。它与 MOP 的根本差别在**合并时机**：MFP 在每个**汇合点先把各前驱信息 ⊔ 起来、再过传递函数**，而 MOP 是**各路径先各自过完传递函数、最后才 ⊔**。

MFP(ℓ) = 迭代求解方程组 { IN[ℓ] = ⊔ pred 的 OUT，OUT[ℓ] = f_ℓ(IN[ℓ]) } 的最小不动点

"MFP"里的 Maximum 同样是历史命名（旧 meet 定向下它是最大不动点）；在 PPA 的 ⊔/least-solution 定向下，它其实是方程组的最小解。名字别较真，抓住"它是那台可计算的迭代引擎的输出"即可。MFP 的最大优点是**永远可计算**（ACC 保证有限步停）且**永远安全**——代价是可能不如 MOP 精确，差在哪由分配性决定，见下。

### V2.4.3 MFP 与 MOP 的关系与相等条件

核心结论（Kildall；Kam–Ullman）：**迭代解 MFP 总落在"安全/保守"一侧，MOP 落在"最精确"一侧；当框架分配时二者相等。** 在 PPA 的 ⊔ 定向下写作：

MOP(ℓ) ⊑ MFP(ℓ)     （MFP 是 MOP 的安全上近似，可能更保守）

f 分配 ⟹ MOP(ℓ) = MFP(ℓ)     （分配框架里迭代解就是理想解）

为什么"先合并再传播"会丢精度？因为若 f 只单调不分配，f(l1 ⊔ l2) 可能严格大于（更保守）f(l1) ⊔ f(l2)——在汇合点提前把两路 ⊔ 到一起，再过传递函数，会引入两路"混合"出的、任何单条真实路径上都不成立的保守信息。分配性恰好是"合并与传播可交换"的代数条件，一旦满足，先合并后合并没区别，MFP=MOP。好消息是 gen/kill 位向量框架天然分配（V2.3.3），所以四大经典分析的迭代解就是最精确解、且 MOP 由此变得可算（否则 MOP 因路径无穷不可计算）。

记法对账（本大主题最易混点，两边都记）：龙书用相反格定向（汇合取 meet ⊓、求 maximum fixed point、"安全"对应"更小"），写作 **MFP ≤ MOP**（MFP 偏小、偏保守）。PPA 用 ⊔ 定向写作 **MOP ⊑ MFP**。**这不是矛盾，是同一命题在相反格定向下的两种写法**——两边都在说"迭代不动点解处于安全侧、MOP 处于精确侧、分配时相等"，只是"安全侧"在龙书是下界、在 PPA 是上界。判断某本书方向的口诀：看它的汇合运算是 ⊔ 还是 ⊓、求 least 还是 maximum，方向随之定。

### V2.4.4 一个 MFP 严格劣于 MOP 的实例（非分配框架）

当传递函数只单调、不分配时，MFP 会严格保守于 MOP。最常被点名的例子是**常量传播**（数据流值给每个变量一个格值，取自三层格）：

⊤（尚不知） ⊐ 具体常量 c ⊐ ⊥（非常量/值冲突）

分支两侧分别赋 `x=2,y=3` 与 `x=3,y=2`，问汇合后 `x+y` 是不是常量。本篇实证：

```
constant-prop MFP z = ('BOT',)  MOP z = 5  (MFP strictly coarser => not distributive)
```

MFP 在汇合点**先**把 x（2 与 3 汇合成"非常量"⊥）、y（同理 ⊥）合并，再算 x+y，得到 ⊥（判为非常量）；MOP 对两条路径**各自**算 x+y——路径一 2+3=5、路径二 3+2=5——再汇合，两个 5 汇合仍是 5，于是发现 x+y 恒为常量 5。MFP 发现不了这个常量，正是因为常量传播的加法传递函数不分配。这不是 bug 而是"先合并后传播"的固有代价：编译器接受这点保守，换算法的高效与终止。给初学者的收束：**不是所有数据流分析都像 gen/kill 那样"迭代即最优"**，常量传播是最经典的例外；分配与否，就是判断"迭代解够不够精确"的那把尺子。（脚本跑于 scratchpad，未入库；Py3.11.15。）

## V2.5 过程间数据流分析

### V2.5.1 无效路径问题：为什么不能把调用当跳转

**过程间（interprocedural）数据流分析**要跨越函数调用边界传播信息。最朴素的做法是把每个调用点当成一条到被调函数入口的跳转、返回当成跳回——但这会引入**无效路径（invalid / infeasible path）**：一个从调用点 c1 进入函数、却从函数返回到**另一个**调用点 c2 之后的路径，在真实执行里绝不会发生（谁调用谁就返回给谁），朴素分析却会沿它传播信息，导致结论被无关调用点"污染"、精度严重下降。

把每个 `call` 的进入和对应 `return` 的返回看成一对必须匹配的括号——`(` 与 `)`。真实执行的调用/返回序列一定是**括号正确匹配**的；无效路径就是"用 c1 的左括号配了 c2 的右括号"的错配路径。过程间分析的核心任务，就是只沿**匹配的（valid）** 路径传播、把错配路径排除掉。这也解释了它比过程内难的本质——合法路径集合是一个上下文无关（Dyck 括号）语言，比过程内的正则路径复杂了一个层级。

### V2.5.2 上下文敏感：call-string 与 functional 两条路线

要排除无效路径、区分"同一函数被不同调用点调用"的不同情形，需要**上下文敏感（context-sensitive）** 分析。PPA 给出两条经典路线。**call-string 方法**：给每个数据流值附上一段"调用栈快照"（最近 k 层调用点的序列，call string），用它标记信息来自哪条调用链，返回时只把标签匹配的信息送回对应调用点——k 层截断就是 k-CFA 式的上下文深度。**functional（函数式 / 假设-保证）方法**：不记调用历史，而是把每个函数分析成一个"入口信息 → 出口信息"的**汇总传递函数（summary）**，在调用点直接把这个 summary 套到实参信息上，返回值信息由 summary 算出——相当于给每个函数算一张输入输出表，调用处查表。

call-string 是"记住我从哪来"（按上下文分身传播），functional 是"把被调函数浓缩成一个可复用的黑盒函数"（一次分析、处处套用）。前者上下文越深越精确但代价指数级涨，后者用一个 summary 复用于所有调用点、通常更省但 summary 的构造更难。二者都能排除无效路径、达到上下文敏感，是过程间分析框架（Sharir–Pnueli，PPA §2.5 整理）的两大支柱。初学者不必深挖实现，记住"过程间的额外精度来自——要么给信息贴调用链标签、要么给函数造输入输出摘要"即可。

### V2.5.3 MVP：把理想解从 MOP 收窄到"有效路径"

过程间的"理想解"不再是全路径汇合 MOP，而是只在**有效（匹配）路径**上汇合的 **MVP（Meet / Merge over all Valid Paths，全有效路径汇合解）**：

MVP(ℓ) = ⊔ { f_π(ι) : π ∈ validpath(ℓ) }

其中 validpath(ℓ) 只含调用/返回正确匹配的路径，是 path(ℓ) 的子集。

这是过程内 MOP 概念的自然升级——把汇合的范围从"所有路径"缩到"所有有效路径"，从而在源头上就不让无效路径的信息进来。因为有效路径少于全路径，MVP 一般比把过程间当过程内硬算的 MOP **更精确**（后者被无效路径拖保守）。上下文敏感分析（V2.5.2）的目标，正是让可计算的迭代解逼近 MVP 而非被无效路径污染的 MOP。这里点到为止：过程间分析的工程侧——调用图构造、上下文敏感的具体层级、别名/指针分析——在 L4-04 C10.3 从编译优化角度展开，本篇按 prompt 要求**点名不展开**，只交代它与过程内框架的接口（无效路径、上下文、MVP）。
