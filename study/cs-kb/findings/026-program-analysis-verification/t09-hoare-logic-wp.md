演绎验证（deductive verification）是这门课"验证半场"里最接近"数学证明"的一支：它不像数据流分析（V2）或抽象解释（V4）那样自动地对所有程序给近似答案，而是要求人把"程序应当满足什么"写成一条**规约**，然后用一套**逻辑推理规则**证明程序确实满足它。这套逻辑的核心载体就是 Hoare 三元组，核心机制就是"沿程序结构把三元组拆成子目标"，而最弱前条件则是把这套拆解过程算法化的谓词转换器。

**Hoare 逻辑是"给程序写断言并逐条证明"的形式系统；最弱前条件是"从你想要的结果倒着算出最省力的前提"的机械方法。** 抓住三件事就抓住了全部内核：三元组 {P} C {Q} 说的到底是什么（V9.1），赋值规则为什么"往后代换"（V9.2、V9.4 是同一件事的两种包装），以及循环为什么必须靠人给不变式（V9.3）。V9.5 只是把前面的规则反过来当成"生成待证明义务"的引擎。

> 本报告 V9.5 的验证条件（VC）在如下环境实跑取证：Python 3.11.15 + z3-solver 5.0.0 @2026-07-30，代码仅存 scratchpad、不入库，正文贴真实输出。工具实证是多来源比对的**补充而非替代**；所有机制性命题（三元组语义、各推理规则、wp 演算）以 Software Foundations 与 Hoare 1969 / Dijkstra 1976 一手比对为准。

## V9.1 Hoare 三元组：{P} C {Q} 与部分/全部正确性

### V9.1.1 Hoare 三元组的形式与读法

Hoare 三元组（Hoare triple）是演绎验证的基本规约单位，写作

```
{P} C {Q}
```

其中 C 是一段程序（命令），P 是**前条件**（precondition）、Q 是**后条件**（postcondition），二者都是关于程序状态（变量取值）的逻辑断言。它的标准读法是：如果在满足 P 的状态下开始执行 C，**且 C 终止**，那么终止后的状态满足 Q。Software Foundations 把这条语义直接定义成一条 Coq 命题：

```
valid_hoare_triple P c Q  :=  ∀ st st', st =[ c ]=> st' → P st → Q st'
```

即"对任意起始状态 st 和终止状态 st'，若 c 能把 st 走到 st' 且 st 满足 P，则 st' 满足 Q"。

这里初学者最容易读错的是"终止"这个前提的位置。三元组默认表达的是**部分正确性**（见下一节），语义里"C 终止"是写在蕴含式的**假设**一侧的——只要 C 不终止（死循环），这条三元组就**自动为真**，因为"如果终止"的前提根本没被触发。换句话说，{P} C {Q} 从不承诺 C 会停下来，它只承诺"万一停下来，结果一定对"。

Hoare 1969 原论文用的记号与今天略有不同，他写成 P {C} R（把程序放在花括号里、断言在两侧），断言的是同一件事。今天教材与工具统一采用 {P} C {Q}（程序在中间、断言在两侧的花括号里），Software Foundations 用 `{{ P }} c {{ Q }}` 双花括号只是 Coq 记号法的需要。三种写法语义完全一致，读到旧文献不要被记号绊住。

### V9.1.2 部分正确性 vs 全部正确性

部分正确性（partial correctness）与全部正确性（total correctness，也译"完全正确性")的唯一区别在于**是否承诺终止**：

```
部分正确性  {P} C {Q}：若 P 成立且 C 终止，则终止态满足 Q。（不保证终止）
全部正确性  [P] C [Q]：若 P 成立，则 C 必定终止，且终止态满足 Q。（保证终止）
```

很多教材用不同的括号区分二者：部分正确性用 {P}C{Q}，全部正确性用 [P]C[Q]（也有用 ⟨P⟩C⟨Q⟩ 或语义判断 ⊨ₚ / ⊨ₜ 的）。记号不统一，读文献时以其定义为准。

直觉上，全部正确性 = 部分正确性 + 终止性证明。二者拆开是有工程理由的：证明"结果对"（部分正确性）用 Hoare 规则递归拆解即可，是相对机械的；而证明"一定停"（终止性）需要额外给出一个**变式/ranking function**（V9.3），本质是另一类论证。把它们分账，可以让"逻辑对不对"和"会不会停"两件事各自独立推进，也让 Software Foundations 这类教材先只讲部分正确性、把终止性作为进阶。

考虑程序 `while true do skip done`（永远空转）。对任意 Q，三元组

```
{True} while true do skip done {False}
```

在**部分正确性**下是**成立的**——因为它永不终止，"若终止则……"的前提永假，蕴含式为真；但在**全部正确性**下它是**假的**——因为它根本不终止，违背了"必定终止"的承诺。这个例子最能让初学者体会"部分正确性对不终止程序过于宽容"这一点。

### V9.1.3 断言语言与"状态谓词"的心智模型

前条件 P 和后条件 Q 不是程序代码，而是**断言**（assertion）——关于"某一时刻程序变量满足什么关系"的逻辑公式，比如 `x > 0`、`x = y + 1`、`∀i. 0≤i<n → a[i]≥0`。把断言理解成"状态的集合"最不容易出错：一个断言 P 就代表"所有让 P 为真的程序状态"这一集合，P 越强（约束越多），它代表的状态集合越小。

这个"断言即状态集合"的视角是理解后面所有规则的钥匙。"P 蕴含 P'"（P ⟹ P'）意思是 P 代表的状态集合被 P' 包含，也就是 P **比 P' 强**（更苛刻、集合更小）。V9.2 的 consequence 规则里"前条件可以换成更强的、后条件可以换成更弱的"，说的就是这个包含关系。初学者一定要先把"强/弱"和"集合大/小"对应清楚：**前条件越强越好证（假设更多），后条件越弱越好证（要求更少）**。

要留意断言语言通常比程序语言**表达力更强**：它允许量词 ∀/∃、允许引用"辅助变量/逻辑变量"（如用 x₀ 记住 x 的初值）。这是必要的——很多规约（比如"排序后是原数组的一个排列"）在纯程序表达式里根本写不出来。

## V9.2 Hoare 规则与推导

### V9.2.1 赋值规则（向后代换，最反直觉的一条）

赋值规则（也叫赋值公理，assignment axiom）是整个 Hoare 逻辑最核心也最反直觉的一条：

```
─────────────────────────  (hoare_asgn)
{ Q[E/x] } x := E { Q }
```

其中 `Q[E/x]`（Software Foundations 记作 `Q [X ⊢> a]`）表示把后条件 Q 里所有出现的变量 x 都**替换成表达式 E**。它是**从后条件倒推前条件**：给定你想在赋值之后成立的 Q，把 Q 里的 x 换成即将赋给它的 E，得到的就是赋值之前必须成立的前条件。

初学者几乎都会先猜成"正着走"的错误版本 `{P} x:=E {P[E/x]}`，这是**错的**。用最小例子体会为什么必须往后代换：想让赋值后 `x = 5` 成立，赋值语句是 `x := y`。按规则，前条件是 `(x=5)[y/x]`，即把 `x=5` 里的 x 换成 y，得到

```
{ y = 5 }  x := y  { x = 5 }
```

读起来完全对：赋值前 y 得等于 5，赋完 x:=y 后 x 自然等于 5。再看一个含 x 自身的例子：

```
{ x + 1 = 5 }  x := x + 1  { x = 5 }
```

把后条件 `x=5` 里的 x 换成 `x+1` 得 `x+1=5`（即 x=4）——赋值前 x 是 4，加 1 后恰好是 5。

为什么方向必须是"后→前"而不是"前→后"？因为赋值会**销毁** x 的旧值。若正着推，前条件里关于 x 的信息在赋值后已经失效，无法机械地转成后条件；而"把后条件里的 x 翻译回它被赋值前的样子（即 E）"总是有定义、总是对的。Hoare 1969 把这条列为公理 D0，并强调它其实是一个**公理模式**（axiom schema）——对每个具体的 Q、x、E 都是一条公理，共同遵循同一语法模式。这条"倒着走"的设计正是 V9.4 最弱前条件把整套验证算法化的种子。

代换是**语法替换**，且要防止变量捕获（若 E 里含有会被 Q 中量词绑定的变量需先改名）；在只有整型全局变量、Q 无量词的简单 WHILE 语言里可以不担心，但进入含数组/指针/量词的断言时要当心。

### V9.2.2 skip 规则

空命令 skip 什么都不做，所以任何断言穿过它都不变：

```
──────────────  (hoare_skip)
{ P } skip { P }
```

这条规则毫无玄机，但在把程序拆解到底时是必要的"叶子"。初学者只需记住 skip 是恒等变换：前后条件相同即可。它对应 V9.4 里 `wp(skip, Q) = Q`。

### V9.2.3 序列（组合）规则

顺序执行 `c1; c2` 的规则通过一个**中间断言** R 把两段接起来：

```
{ P } c1 { R }      { R } c2 { Q }
──────────────────────────────────  (hoare_seq)
{ P } c1 ; c2 { Q }
```

要证 `{P} c1;c2 {Q}`，就找一个中间状态描述 R，使得 c1 能从 P 走到 R、c2 能从 R 走到 Q。Hoare 1969 把它列为组合规则 D2。

关键难点在于 R 从哪来。人工推导时通常**从后往前**做：先由 c2 和 Q 用赋值/其他规则算出 c2 的前条件当作 R，再拿 R 当 c1 的后条件继续往前推。这正是"验证天然是倒着走的"的又一体现，也是 wp 演算（V9.4）之所以能把序列写成 `wp(c1;c2, Q) = wp(c1, wp(c2, Q))`（先算 c2 再算 c1）的原因。Software Foundations 里 `hoare_seq` 的两个前提在形式陈述中 c2 先于 c1 出现，正是配合这种反向推理流。

### V9.2.4 条件规则

分支 `if b then c1 else c2` 的规则要求两条分支**各自**在加上"守卫是否成立"的信息后都能达到 Q：

```
{ P ∧ b } c1 { Q }      { P ∧ ¬b } c2 { Q }
────────────────────────────────────────────  (hoare_if)
{ P } if b then c1 else c2 end { Q }
```

进入 then 分支时我们额外知道 b 为真，进入 else 分支时额外知道 b 为假；只要两个分支各自都能在这一额外信息下把 P 变成 Q，整个 if 就把 P 变成 Q。

初学者要抓住"分支把守卫信息注入前条件"这一点：证 then 分支时前条件是 `P ∧ b`（不是光 P），这多出来的 b 往往正是证明的关键。一个最小例子——取绝对值：

```
{ True }  if x < 0 then y := -x else y := x end  { y = |x| }
```

then 分支前条件 `True ∧ x<0` 给了我们 x<0，于是 y:=-x 后 y=-x=|x|；else 分支前条件 `True ∧ ¬(x<0)` 给了 x≥0，于是 y:=x 后 y=x=|x|。两支都到 Q，整体成立。

### V9.2.5 循环（迭代）规则

while 循环的规则围绕一个**循环不变式**（loop invariant）I 展开：

```
{ I ∧ b } c { I }
─────────────────────────────────  (hoare_while)
{ I } while b do c end { I ∧ ¬b }
```

它说：若 I 在"循环体执行且守卫成立"下被保持（前提），那么整个循环把 I 变成 `I ∧ ¬b`（循环退出时 I 仍成立、且守卫已为假）。Hoare 1969 把它列为迭代规则 D3。

这条规则的三个要点初学者必须记牢：第一，I 必须在**每次迭代前后都成立**（这是前提 `{I∧b} c {I}` 的含义）；第二，规则本身要求进入循环时 I 已成立、退出时得到 `I∧¬b`，若实际前条件/后条件不是这个形状，需要靠下一节的 consequence 规则把 P⟹I 和 `I∧¬b`⟹Q 补上；第三，这条规则**只管部分正确性，不保证循环终止**——终止性要另配变式（V9.3）。

不变式为什么是循环验证的灵魂？因为循环执行多少次事先不知道，无法像序列那样把每步展开。I 是"无论循环转了几圈都成立的那句话"，它把"无穷多种执行"压缩成一句可证的断言。找 I 是**创造性**的、无法完全机械化的一步（这与赋值/序列的机械推导形成鲜明对比），也是自动验证工具最需要人工标注或靠不变式推断技术补齐的地方。

### V9.2.6 后果规则（consequence）

后果规则（rule of consequence）是把上面各条"拼装"起来的胶水，允许**加强前条件、削弱后条件**：

```
P ⟹ P'      { P' } c { Q' }      Q' ⟹ Q
────────────────────────────────────────────  (hoare_consequence)
{ P } c { Q }
```

Software Foundations 把它拆成两条单侧规则分别用：

```
P ⟹ P'      { P' } c { Q }
────────────────────────────  (hoare_consequence_pre，加强前条件)
{ P } c { Q }

{ P } c { Q' }      Q' ⟹ Q
────────────────────────────  (hoare_consequence_post，削弱后条件)
{ P } c { Q }
```

为什么方向是"前条件可换强、后条件可换弱"？回到 V9.1.3 的"断言即状态集合"：前条件描述"允许的起始状态"，缩小它（换更强的 P，P⟹P'）只会让程序面对更少的输入，仍然安全；后条件描述"承诺的结果"，放宽它（换更弱的 Q，Q'⟹Q）只是承诺得更少，仍然兑现。反过来则不成立。这里的两个蕴含式 `P⟹P'` 和 `Q'⟹Q` 是纯逻辑命题（与程序无关），它们正是 V9.5 里最终交给 SMT 求解器的**验证条件**的来源。

初学者最常犯的错是把方向记反（以为可以削弱前条件或加强后条件），那会得到不可靠的证明。一个记忆法：consequence 让你"多假设、少承诺"——假设更强、承诺更弱，都是把事情变得更好证，且不会证出假的东西。

## V9.3 循环不变式与变式：终止性与 ranking function

### V9.3.1 循环不变式的三条职责

循环不变式（loop invariant）I 是一个断言，它要同时担起三件事，才能用 V9.2.5 的 while 规则加 consequence 完成一个循环的部分正确性证明：

```
初始化 (initialization)：  P ⟹ I            （进入循环前，前条件蕴含 I）
保持   (preservation)：     { I ∧ b } c { I }  （循环体在守卫成立下保持 I）
退出   (postcondition)：    I ∧ ¬b ⟹ Q        （退出时 I 与守卫假一起蕴含 Q）
```

这三条合起来才把"循环把 P 变成 Q"证完；单靠 while 规则只给出中间两步的骨架，首尾两个蕴含由 consequence 规则补。

初学者判断一个候选 I 好不好，就逐条对这三件事：进得去吗（P⟹I）？转一圈还成立吗（保持）？出来时够用吗（I∧¬b⟹Q）？三条缺一不可是最常见的坑——很多人给的 I 太弱（保持得住但退出时推不出 Q）或太强（退出够用但循环体保持不住）。找 I 的诀窍是让它"强到退出时能推出 Q，又弱到循环体能维持"，恰好卡在中间。

以整数除法（反复减法）为例：

```
{ a≥0 ∧ b>0 }
r := a; q := 0;
while r ≥ b do  r := r - b;  q := q + 1  done
{ a = b*q + r  ∧  0 ≤ r < b }
```

不变式取 `I : a = b*q + r ∧ r ≥ 0`。初始化：r:=a,q:=0 后 a=b*0+a 且 a≥0，成立；保持：每次减 b、q 加 1，a=b*q+r 的等式恒真且 r 减到 r-b≥0（因守卫 r≥b）；退出：`¬(r≥b)` 即 r<b，配合 I 得到 `a=b*q+r ∧ 0≤r<b`，正是 Q。这个 I 就是 V9.5 会自动生成 VC 的那个例子。

### V9.3.2 循环变式（variant / ranking function）与终止性

while 规则只证部分正确性；要升级到全部正确性（保证循环停），需要额外给一个**循环变式**（loop variant），也叫**ranking function**（秩函数）：一个从程序状态映到某个**良基集合**（well-founded set，通常取自然数 ℕ 或有序对的字典序）的表达式 V，要求

```
每次循环体执行都使 V 严格减小，且在守卫成立时 V 有下界（如 V ≥ 0）。
```

带变式的全部正确性 while 规则可写成（V₀ 记录进入循环体前 V 的值）：

```
I ∧ b ⟹ V > 0
{ I ∧ b ∧ V = V₀ } c { I ∧ V < V₀ }
─────────────────────────────────────────  (总正确性 while)
[ I ] while b do c end [ I ∧ ¬b ]
```

终止性的原理是"无穷下降不可能"：良基集合里不存在严格递减的无穷序列（自然数不能一直减下去还非负）。所以只要每转一圈 V 都严格变小又不能低于下界，循环就必然在有限步内停。上面的除法例子取变式 `V = r`：每次 r 减去 b>0 严格减小，且守卫 r≥b>0 保证 r>0 有下界，故循环终止。

初学者要分清不变式 I 和变式 V 的分工：**I 管"对不对"（值/关系正确），V 管"停不停"（终止）**，两者独立给出、独立验证。常见误区是选的"变式"不能保证有下界（比如整数无下界地减）或不严格减小（比如某次迭代不变），都会让终止性论证失效。变式不必是自然数——只要落在某个良基序（如二元组的字典序，用于嵌套/双计数循环）即可。这与 V8/模型检验里的"公平性/终止性"验证是同一个数学根子（良基关系），只是这里用演绎方式给出。

#### 来源与时效
- 一手（主锚点）：Software Foundations Vol.2 PLF「Hoare」「Hoare2」章，loop invariant 三职责（initialization/preservation + 首尾 consequence）与除法示例式的不变式推导。https://softwarefoundations.cis.upenn.edu/plf-current/Hoare2.html （核实 2026-07-30）
- 第二独立一手：Hoare 1969（D3 迭代规则，部分正确性、不含终止）；终止性/变式的经典表述见 Dijkstra 1976《A Discipline of Programming》（bound function）与 CMU 15-414/15-424 讲义（ranking function / well-founded、严格递减+有下界）。https://www.cs.cmu.edu/~15414/ （核实 2026-07-30）
- 交叉：Wikipedia "Loop variant"（loop variant 定义为对良基关系单调递减的状态函数，与讲义一致，作二手对照）。https://en.wikipedia.org/wiki/Loop_variant （核实 2026-07-30）
- 分歧点：术语 variant / bound function / ranking function 指同一对象（不同学派用词），语义一致，无实质冲突。

## V9.4 最弱前条件（WP）演算

### V9.4.1 wp 作为谓词转换器

最弱前条件（weakest precondition，wp）是 Dijkstra 提出的把 Hoare 逻辑"算法化"的机制。给定命令 C 和后条件 Q，

```
wp(C, Q)
```

定义为"能保证 C 终止且终止态满足 Q 的**所有**初始状态构成的最弱（最宽松）前条件"。所谓"最弱"就是**约束最少、代表状态集合最大**的那个前条件——它精确刻画了"起点在哪里才能安全到达 Q"，多一分嫌严、少一分不够。wp 是一个**谓词转换器**（predicate transformer）：吃进一个断言 Q，吐出另一个断言 wp(C,Q)。

wp 与 Hoare 三元组的桥梁是一条等价：

```
{P} C {Q}  成立   ⟺   P ⟹ wp(C, Q)
```

也就是说，验证一个三元组，等于先机械地算出 wp(C,Q)，再检查前条件 P 是否蕴含它——把"找证明"变成"算一个断言 + 证一个纯逻辑蕴含"。初学者要抓住"最弱=最省力"的直觉：wp 给的是"恰好够用"的前提，任何比它更强的 P 都能用（这正对应 consequence 的加强前条件），任何比它弱的 P 都不安全。

Dijkstra 原始的 wp 是**全部正确性**语义（内含终止），与之相对的"只管部分正确性、不含终止"的版本常记作 wlp（weakest liberal precondition，最弱自由前条件）。教材里 wp/wlp 的区别就在终止那一项，读文献时注意用的是哪一个。

### V9.4.2 wp 的逐条计算规则

wp 沿命令的语法结构递归定义，每条对应 V9.2 的一条 Hoare 规则（这正是它把验证机械化的原因）：

```
wp(skip, Q)          = Q
wp(x := E, Q)        = Q[E/x]
wp(c1 ; c2, Q)       = wp(c1, wp(c2, Q))
wp(if b then c1 else c2, Q)
                     = (b ⟹ wp(c1, Q)) ∧ (¬b ⟹ wp(c2, Q))
```

赋值那条 `Q[E/x]` 与 V9.2.1 的赋值公理是**同一件事**——向后代换；序列那条"先算 c2 再算 c1"正是 V9.2.3 反向推理的算法化。条件那条也可等价写成 `(b ∧ wp(c1,Q)) ∨ (¬b ∧ wp(c2,Q))`，两种写法在 b 为确定布尔值时等价。

用赋值 + 序列两条就能全自动处理无循环程序。最小例子——交换两数（无临时变量、用算术）：求 `wp(x:=x+y; y:=x-y; x:=x-y, x=b ∧ y=a)`。从后往前代：最后一句 `x:=x-y` 把 `x=b` 变成 `x-y=b`；`y:=x-y` 把 `y=a` 变成 `x-y=a` 并把上一步的 y 也换……一路机械代换即可得到前条件 `x=a ∧ y=b`。整个过程没有任何"灵感"，纯语法操作——这就是 wp 的威力。

### V9.4.3 循环的 wp：为什么这里机械化会卡壳

循环是 wp 唯一无法纯机械展开的地方。理论上

```
wp(while b do c, Q) = 最小不动点（把循环展开 0 次、1 次、2 次……的 wp 取极限）
```

但这个不动点一般没有有限闭式，无法像赋值那样"算出来"。所以实践中不直接算，而是要求用户**标注一个循环不变式 I**（V9.3），再用它把循环这一段的验证义务转成有限个可判定的蕴含式：

```
P ⟹ I                        （初始化）
I ∧ b ⟹ wp(c, I)             （保持：循环体保持不变式）
I ∧ ¬b ⟹ Q                   （退出：不变式加守卫假蕴含后条件）
```

（要全部正确性再加变式严格递减且有下界的条件，见 V9.3.2。）

**wp 把"除循环外的一切"变成纯机械计算，而循环把"创造性"隔离在"给一个不变式 I"这一步**。这解释了为什么现代验证器（Dafny、Why3、F* 等）都要求你为循环写 `invariant` 注解——不是工具偷懒，而是这一步在理论上就不可完全自动化（否则可判定停机）。给了 I 之后，剩下的三条蕴含就是 V9.5 要生成并交给求解器的验证条件。

#### 来源与时效
- 一手（主锚点）：Dijkstra, *A Discipline of Programming*, Prentice-Hall 1976，wp 作为 predicate transformer 的定义、`wp(skip)`、`wp(x:=E,Q)=Q[E/x]`、`wp(S1;S2,Q)=wp(S1,wp(S2,Q))` 与 if 的 wp（原书用 guarded commands 记法）。
- 第二独立一手/交叉：CMU 15-414 "Weakest Preconditions and Strongest Postconditions" 讲义，wp 条件式 `(B→wp(S1,Q))∧(¬B→wp(S2,Q))`、循环 wp 需不变式、wlp vs wp（终止项）区分。https://www.cs.cmu.edu/~15414/ （核实 2026-07-30）
- 交叉：Software Foundations PLF「Hoare」章的 `hoare_asgn` 与 wp 的 `Q[E/x]` 一致（wp 赋值规则=Hoare 赋值公理的算法化，两来源互证方向为向后代换）。
- 分歧/易错：wp（含终止，全部正确性）vs wlp（不含终止，部分正确性）——不同教材默认不同，本报告按 Dijkstra 原义 wp 含终止；循环 wp 无有限闭式、需人工不变式，两来源一致。

## V9.5 验证条件生成（VCGen）

### V9.5.1 从注解程序到验证条件

验证条件生成（Verification Condition Generation，VCGen）是把演绎验证真正落到工具上的一环。它的输入是一段**带注解的程序**（annotated program）——即在代码里嵌入前条件、后条件、以及每个循环的不变式（和变式）；输出是一组**验证条件**（Verification Conditions，VC）：一批**不含程序、只含逻辑的公式**，程序正确当且仅当这些 VC 全部有效（valid）。这些 VC 随后被交给 SMT 求解器（V10，如 Z3）自动判定。

```
带注解程序  ──VCGen──▶  { VC₁, VC₂, …, VCₙ }（纯逻辑公式）──SMT──▶  全部 valid?
```

核心思想就是 V9.4：VCGen 内部本质是沿程序结构跑 wp（或对偶的最强后条件 sp），把每处需要"逻辑蕴含成立"的地方（赋值经过的代换、consequence 的 P⟹P'、循环的三条不变式义务）收集成 VC。程序的控制结构在这一步被完全"编译掉"，只剩逻辑——这正是能交给通用求解器的原因。

"VCGen = 沿程序算 wp，把途中每个'必须成立的蕴含'掐下来攒成一张待证清单。"把验证拆成"生成 VC"（机械、由工具做）和"证 VC"（交给 SMT）两段，是所有现代演绎验证器（Dafny/Why3/F*/Frama-C 等）的共同架构。

### V9.5.2 循环处的 VC 与不变式的角色

VCGen 遇到循环时无法机械展开（V9.4.3），它依赖程序员标注的不变式 I，据此产出**恰好三条**（部分正确性）VC——就是 V9.3.1 那三条职责：

```
VC-init：  P ⟹ I
VC-pres：  I ∧ b ⟹ wp(body, I)
VC-post：  I ∧ ¬b ⟹ Q
```

要全部正确性再加一条变式递减 VC。这解释了工具的分工：**人负责"想出" I 和 V（创造性、不可自动化那一步），工具负责把 I/V 机械地摊成 VC，求解器负责判 VC 真假。** 若某条 VC 不成立，说明要么程序有 bug、要么不变式给错/给弱——工具会指出是哪条 VC 失败，帮助定位。

注解不足或不变式太弱时，VC-pres 或 VC-post 会判不成立，但这**未必**意味着程序错——很可能只是 I 没写够强。初学者要学会区分"程序真有 bug"和"不变式没标好"，后者靠加强 I 修复。

### V9.5.3 本机实证：用 Z3 判定除法示例的 VC

以 V9.3.1 的整数除法程序为例，取不变式 `I : a = b*q + r ∧ r ≥ 0`，VCGen 产出三条 VC。把它们的**否定**交给 Z3——若返回 `unsat`（否定不可满足），则原 VC **有效**（valid）。本机 z3-solver 5.0.0 真跑（Python 3.11.15 @2026-07-30）：

```
VC1 (init)  a≥0 ∧ b>0 ⟹ a=b·0+a ∧ a≥0                         -> unsat  (VC valid)
VC2 (pres)  a=b·q+r ∧ r≥0 ∧ r≥b ⟹ a=b·(q+1)+(r−b) ∧ r−b≥0    -> unsat  (VC valid)
VC3 (post)  a=b·q+r ∧ r≥0 ∧ ¬(r≥b) ∧ b>0 ⟹ a=b·q+r ∧ 0≤r<b   -> unsat  (VC valid)
```

三条 VC 的否定全部 `unsat`，即三条 VC 全部有效，故该除法程序对给定规约**部分正确**（终止性另由变式 V=r 论证，见 V9.3.2）。

`python3 vc.py`（脚本仅存 scratchpad、不入库；每条 VC 用 `Solver.add(Not(vc))` 后 `check()`，`unsat` 即 VC 有效）；环境 Py3.11.15 + z3-solver 5.0.0 @2026-07-30。这一步实证是对"VCGen→SMT"工程链条的**加固演示**，不替代前面各节的多来源比对；机制性结论仍以 Software Foundations 与 Hoare/Dijkstra 一手为准。

初学者从这个例子能看清整条链：人给规约 + 不变式 → VCGen 摊成三条纯逻辑蕴含 → Z3 秒判 → 全 valid 即证毕。这正是演绎验证"半自动"的真面目：创造性的不变式靠人，繁琐的逻辑判定靠机器。
