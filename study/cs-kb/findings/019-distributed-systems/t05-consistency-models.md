## 5.1 线性一致性

### 5.1.1 线性一致性：实时序 + 原子生效的最强单对象一致性

**线性一致性**（linearizability，也叫 atomic consistency）是对单个对象（一个寄存器、一个 KV 键、一个队列）能给出的**最强**一致性保证。它的核心承诺是：**每个操作看起来都在它的"调用（invocation）"与"返回（response）"之间的某一瞬间原子地、一次性地生效，且一旦某次写生效，之后（按真实物理时间）开始的任何读都必须看到该写或更新的值。** 直觉上，它让一个被多客户端并发访问、内部还多副本复制的对象，对外表现得就像**一台单机、单线程、瞬间完成每个操作的理想机器**。

Herlihy & Wing 1990 的原始表述是：存在一个把每个并发操作"收缩"到区间内某一点的**线性化点（linearization point）**，使得按这些点排出的顺序既满足对象的顺序规范（sequential specification，例如"读返回最近一次写入的值"），又**不违反操作之间的真实时间先后**。

判定一段历史是否线性一致，要能找到一个满足两条的全序：

```
设 H 为一段读写历史。H 线性一致 ⇔ 存在操作的全序 π 使得：
  (L1) 顺序合法：π 中每个操作满足对象的顺序规范
                （对寄存器：读返回 π 中它之前最近一次写的值）
  (L2) 实时序保持：若操作 op1 在真实时间上先返回、op2 才被调用（op1 <_rt op2），
                则 π 中 op1 必须排在 op2 之前
```

三个客户端操作一个初始为 0 的寄存器。

```
时间轴（水平=真实时间；每个操作占一个 [调用, 返回] 区间）：
  C1:  |--- write(x=1) ---|
  C2:            |--- read(x) → ? ---|          （与 write 部分重叠）
  C3:                          |-- read(x) → ? --|  （在 write 返回之后才调用）
```

C2 与写重叠，它读到 0 或 1 都**合法**（写还没被强制"生效"，两种线性化点都能安排）。但 C3 是在 `write(x=1)` **返回之后**才开始的，按 (L2) 写必须排在 C3 之前，所以 **C3 必须读到 1**；若 C3 读到 0，这段历史就不可线性化。这个"晚开始的读必须看到已完成的写"正是线性一致比后面几种模型都强的地方——它把**真实时间**钉进了合法性条件。

### 5.1.2 组合性（locality）：线性一致独有的"拼装即成立"性质

线性一致性有一个后面所有较弱模型都不具备的珍贵性质——**组合性 / 局部性（composability / locality）**：如果系统里**每一个对象各自**都是线性一致的，那么整个系统（把这些对象合起来看）**自动就是**线性一致的。

它意味着你可以**独立地**实现和验证每个线性一致对象（每个 KV 键、每个锁），然后放心地把它们拼在一起用，整体一致性无需再额外协调证明。Herlihy & Wing 在论文里专门证明了 linearizability is a local property，并指出这正是它相较顺序一致性（5.2 会看到顺序一致**不**组合）在模块化推理上的关键优势。

线性一致还是一个**非阻塞（non-blocking）**条件：一个待决（pending）的调用永远不会被迫等待另一个待决调用完成才能返回——这使它适合刻画并发数据结构的正确性，而不像加锁那样天然阻塞。初学者记住组合性这一点即可：**"每个部件线性一致 ⇒ 整机线性一致"，这是白送的模块化红利。**

### 5.1.3 易错点：线性一致 ≠ 串行化（serializability）

初学者最常混淆的是把 linearizability（线性一致）和 serializability（可串行化，事务隔离的黄金标准）当成一回事。两者是**正交的两个维度**：

```
线性一致 (linearizability)：单对象 + 单操作；约束的是「实时顺序」，是一致性/新鲜度保证
串行化   (serializability)：多对象 + 多操作事务；约束的是「事务等价于某个串行序」，是隔离性保证
两者合起来 = 严格可串行化 (strict serializability)：谱系最强点
```

线性一致只管"单个键的读写有没有按真实时间看到最新值"，它**不**跨多个键提供事务原子性；串行化保证一组事务像挨个串行执行，但**不**要求这个串行序符合真实时间（一个提交晚的事务可以被排到前面）。把两者叠加——事务像串行执行、且这个串行序还尊重真实提交时间——才是 strict serializable（Jepsen 谱系的最强点，Spanner 的外部一致性即属此类，归 L6-05）。

线性一致是**关于读写历史的合法性**，不是"用了强一致协议（如 Raft）就自动拿到"。Raft 保证日志复制的共识，但一个从 follower 直接读的实现可能读到陈旧值、破坏线性一致——所以才需要 ReadIndex/租约读等技巧（归 L6-05）。共识是手段，线性一致是目标，二者不等价。

## 5.2 顺序一致性

### 5.2.1 顺序一致性：存在一个保程序序的全序，但不绑真实时间

**顺序一致性**（sequential consistency）由 Lamport 1979 定义：一次执行的结果，等同于**把所有进程的所有操作排成某一个全序**去顺序执行的结果，且这个全序里**每个进程自己的操作保持它的程序序（program order）**。关键在于——它只要求存在这样一个全序，**不要求这个全序符合跨进程的真实物理时间**。

Lamport 的原始判据可写成：

```
一次执行是顺序一致的 ⇔ 存在所有操作的一个全序 S，使得：
  (S1) S 顺序合法：每个操作满足对象顺序规范（读返回 S 中之前最近一次写）
  (S2) 程序序保持：每个进程 P 的操作在 S 中的相对顺序 = P 发出它们的顺序
  （注意：没有实时序约束——不同进程之间的操作可被任意交错）
```

对比 5.1 的线性一致：线性一致 = 顺序一致 **(S1)+(S2)** 再**加**实时序约束 (L2)。所以：

```
线性一致 ⊂ 顺序一致    （线性一致更强；每个线性一致的历史都顺序一致，反之不然）
```

### 5.2.2 与线性一致的分界：丢掉实时序意味着什么

理解顺序一致的最好办法，是看它**允许而线性一致禁止**的那种历史。回到 5.1.1 的例子：C3 在 `write(x=1)` 返回之后才开始读。线性一致强制 C3 读到 1；**顺序一致却允许 C3 读到 0**——只要能排出一个全序，把 C3 的读安排在那个写"之前"，且不违反各进程自己的程序序即可。也就是说，顺序一致允许"整个系统的逻辑时钟停在过去某一刻"，只要大家一致地停在同一个过去。

一个最小例子是两个进程各写各的、再互读。

```
P1: write(x=1); read(y) → ?
P2: write(y=1); read(x) → ?
顺序一致下，允许出现 read(y)→0 且 read(x)→0 吗？
  —— 不允许两个都读到 0 时还满足两进程程序序 + 单一全序？其实要看模型细节；
     但顺序一致「允许」P1、P2 各自看到的全局顺序是「同一个」交错，
     不要求这个交错贴合真实时间（可以整体滞后）。
```

**线性一致 = 所有人共享同一个"实时挂钟"，晚发生的必须看到早发生的；顺序一致 = 所有人共享同一本"剧本（全序）"，但这本剧本可以整体比真实时间慢半拍。** 只要大家读的是同一本剧本、且各自台词顺序没乱，就合法。多处理器/多核内存模型里，顺序一致是"最符合程序员直觉"的基准（现实 CPU 因性能用了更弱的 TSO 等，需要内存屏障补齐——那属 L5-05/L4-05，不在此深入）。

### 5.2.3 顺序一致不组合：它比线性一致"贵在推理"的地方

顺序一致性**不具备组合性（not local）**：即使每个对象单独看都顺序一致，把它们合起来的系统也**未必**顺序一致。这正是 Herlihy & Wing 用来凸显线性一致优越性的对比点。

顺序一致允许每个对象各自"整体滞后"到不同程度，单看每个对象都能排出合法全序，但要给**所有对象的所有操作**排一个**统一**的全序（同时尊重每个进程跨对象的程序序）时，各对象之间滞后不一致就可能拼不出一个自洽的全序。这带来一个实际后果：用顺序一致的部件搭系统，你**不能**像线性一致那样"分部件验证完就拼装"，必须整体推理。初学者到此记住结论即可——**线性一致组合、顺序一致不组合**，这是选强一致时一个常被忽略但很实在的理由。

#### 来源与时效
- Lamport「How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs」IEEE Trans. Computers C-28(9):690–691, Sept 1979（一手原论文，核实 2026-07-30 经卷期页码）：顺序一致性原始定义（结果等同于某个保各进程程序序的全序顺序执行）。

- 交叉一致，无冲突。分账记录：Lamport 原文出自多处理器内存语境，本报告只取其分布式一致性语义，硬件内存模型（TSO/屏障）归 L5-05/L4-05。

## 5.3 因果一致性

### 5.3.1 因果一致性：尊重因果依赖，并发写允许分歧

**因果一致性**（causal consistency）只强制一件事：**有因果关系（happens-before，大主题2 的 →）的操作，必须被所有节点按同一因果顺序看到；而彼此并发（concurrent，无因果关系）的操作，允许不同节点看到不同顺序。** 它比顺序一致弱——顺序一致要求**所有**操作有一个统一全序，因果一致只要求**有因果关系的那些**保持序，放弃了对并发操作的全局统一定序。

合法性条件（沿用大主题2 的因果序 →）：

```
一次执行因果一致 ⇔ 每个进程看到的操作顺序，都与「因果序 →」的某个线性扩展一致：
  若 write A → write B（B 因果依赖 A，例如 B 是读到 A 后才写的），
     则任何读到 B 的进程，必须先看到 A（不能只看到 B 而漏掉 A）
  若 write A ‖ write B（A、B 并发，互不依赖），
     则允许进程 P1 看到顺序 A 后 B、进程 P2 看到 B 后 A（合法分歧）
```

### 5.3.2 为什么因果一致是"高可用下最强的甜点"

因果一致最重要的性质是：**它是（在收敛前提下）仍能保持高可用的最强一致模型**——粗略地说，一个要求"分区时也永远可响应、且副本最终收敛"的系统，能提供的一致性上限大约就到因果一致（Mahajan-Alvisi-Dahlin 2011、Attiya-Ellen-Morrison 2017 给出了"实时因果一致是永远可用+收敛系统的最强可实现语义"这一方向的结论）。顺序一致及更强的模型在分区下无法保持可用（见 5.5），而因果一致既能挡住绝大多数反直觉的乱序（因果乱序），又不需要跨副本的全局协调。

给初学者最经典的例子——**社交网络的"评论看不到原帖"问题**：

```
Alice: 发帖 P（"我通过考试了！"）        —— write P
Bob:   读到 P，回复评论 C（"恭喜！"）     —— read P; write C   ⇒  P → C（C 因果依赖 P）
Carol: 看到了 Bob 的评论 C，却看不到原帖 P  —— 因果乱序！（看到果，没看到因）
```

因果一致**禁止**这种情况：任何看到 C 的人必须先看到 P。而对**并发**的两条独立帖子（比如 Alice 和 Dave 同时各发一帖、互不引用），因果一致**允许** Bob 先看到 Alice 的、Carol 先看到 Dave 的——因为它们没有因果关系，谁先谁后不影响正确性。这就是"尊重因果、放任并发"的精确含义。

### 5.3.3 收敛与冲突处理：因果一致要配"并发写怎么合"

因果一致只约束**有依赖的**操作的可见顺序，它本身**不**告诉你**并发写**最终该收敛成什么值。所以实用的因果一致系统通常是 **causal+（causal + convergent conflict handling，Lloyd et al. COPS SOSP 2011）**——在因果一致之上再加一个"所有副本对同一组并发写用**同一个确定性规则**收敛"的要求，避免副本永久分歧。

**最后写赢（LWW，用时间戳/节点 ID 定序，简单但会丢写）**、**保留多值让应用解决（如 Dynamo 的向量时钟 + 兄弟版本）**、或 **CRDT（无冲突复制数据类型，设计成并发写天然可交换合并，如计数器、集合）**。初学者的关联记忆：大主题2 的**向量时钟**正是这里用来判定"两个写是因果先后还是并发"的工具——因果一致的实现离不开向量时钟这类因果元数据。

这里的易错点在于，因果一致**允许不同副本对并发写有不同的当前值**（只要因果序不被破坏），所以它**不**保证"任意时刻所有副本读到同一个值"。要"最终所有副本收敛到同一状态"，得靠 causal+ 里附加的收敛规则，而不是因果一致本身。

- Ahamad, Neiger, Burns, Kohli & Hutto「Causal Memory: Definitions, Implementation, and Programming」Distributed Computing 1995（一手，核实 2026-07-30 经书目）：因果一致（因果存储）的形式定义——尊重因果序、并发操作可不同序。
- Lloyd, Freedman, Kaminsky & Andersen「Don't Settle for Eventual: Scalable Causal Consistency for Wide-Area Storage with COPS」SOSP 2011（一手系统论文）：causal+（因果 + 收敛冲突处理）、用依赖元数据跟踪因果、"评论看不到原帖"类因果乱序的动机。
- Jepsen「Causal Consistency」（https://jepsen.io/consistency/models/causal ，交叉核对，核实 2026-07-30）：causal 弱于 sequential、强于 PRAM/会话保证；并发写允许分歧。

- 交叉一致。边界记录："因果一致是永远可用+收敛系统的最强可实现语义"是 Mahajan-Alvisi-Dahlin 2011 / Attiya et al. 2017 方向的结论，前提（是否要求实时因果、是否单值）会影响精确表述，本节给方向性结论与直觉，完整证明不在本课纵深内。

## 5.4 最终一致性与会话保证

### 5.4.1 最终一致性：只承诺"迟早收敛"，不承诺何时、也不管中间乱不乱

**最终一致性**（eventual consistency）是谱系里最弱的一档常用保证：**如果对某个对象停止写入，那么所有副本最终（eventually）会收敛到同一个值。** 它只是一个**活性（liveness）**承诺——"迟早一致"——对**中间过程几乎不设约束**：读可能读到旧值、可能读到比上次更旧的值（回退）、不同副本可能长时间给出不同答案。

它之所以流行，是因为它把可用性和性能推到极致：任何副本都能立即接受读写、无需等待其他副本，天然抗分区（分区期间照常服务，恢复后再收敛）。代价是**几乎所有一致性直觉都不成立**，把消解分歧的复杂性完全甩给应用。给初学者最扎心的易错点：**"最终一致"里的"最终"没有时间上界**——它只保证"不写了就会收敛"，不保证在任何有限时间内一致；而且它**连"读到自己刚写的值"都不保证**（下一节的会话保证正是为补这类窟窿而生）。

### 5.4.2 会话保证四条：给单个客户端会话补上最起码的直觉

**会话保证**（session guarantees，Terry et al. Bayou 1994）是在最终一致之上、**以单个客户端会话（session）为范围**提供的四条弱保证，目的是让一个客户端"看自己的操作是自洽的"，即使它在多个互不一致的副本间跳来跳去。四条是：

```
读己写 (Read Your Writes, RYW)：
    一个会话写过的值，它之后自己的读必须能看到（不会读丢自己刚提交的写）
单调读 (Monotonic Reads, MR)：
    一个会话读到过某个写，之后的读不会"倒退"到看不见该写的更旧状态
单调写 (Monotonic Writes, MW)：
    一个会话的多次写，按它发出的顺序被应用（不会后写先于先写生效）
读后写 (Writes Follow Reads, WFR)：
    一个会话读到某值后再写，这次写在全局上排在"产生被读值的那个写"之后
    （把因果关系跨会话传播出去）
```

**读己写**——你改了个人签名、刷新页面却还显示旧签名，就是违反 RYW；**单调读**——你看到一条新消息，切换标签页后它又消失了，就是违反 MR；**读后写**（WFR）本质是"把 5.3 的因果关系落到会话层"，保证"我基于看到的东西做出的写"在顺序上跟在它依赖的写后面。这四条各自独立、可按需组合，**都不要求跨客户端的全局一致**，因此能廉价地叠加在最终一致系统上。

### 5.4.3 会话保证的代价：从"到处可用"降到"粘住可用"

四条会话保证不是白拿的：要保证一个会话读到自己的写、读不倒退，客户端通常必须**"粘"在能看到它历史的副本上**（或携带因果元数据让副本等到追平才响应）。这带来一个精确的可用性归类差别：

```
最终一致（无会话保证）：可以「完全可用 (totally available)」——任意副本随时可读写
会话保证（RYW 及以上）：至多「粘性可用 (sticky available)」——只要客户端粘住同一（组）副本就可用；
                        换副本可能读到违反 RYW 的旧值，被迫等待或转移会话状态
```

这个"totally available vs sticky available"的区分（Bailis et al. HAT 2013 / Viotti-Vukolić 综述整理）是理解谱系的关键刻度：它说明**连很弱的会话保证也已经不是"零协调"了**——它需要"会话粘性"这一点点协调，换来客户端视角的自洽。5.5 会把这条刻度接到整条谱系与 CAP 上。

- Terry, Demers, Petersen, Spreitzer, Theimer & Welch「Session Guarantees for Weakly Consistent Replicated Data」PDIS 1994（一手原论文，核实 2026-07-30 经作者/会议）：四条会话保证（Read Your Writes / Monotonic Reads / Monotonic Writes / Writes Follow Reads）的定义与动机（Bayou，read-any/write-any 复制下给单会话自洽视图）。
- Bailis, Davidson, Fekete, Ghodsi, Hellerstein & Stoica「Highly Available Transactions: Virtues and Limitations」VLDB 2014 / Vogels「Eventually Consistent」CACM 2009（一手，交叉核对）：最终一致定义、totally available vs sticky available 的可用性归类。

## 5.5 一致性代价谱系

### 5.5.1 谱系全景：一条从"最像单机"到"最能扛分区"的轴

把 5.1–5.4 串起来，就是一条单对象一致性的**强度谱系**（强 → 弱）：

```
严格可串行化 ⊃ 线性一致 ⊃ 顺序一致 ⊃ 因果一致 ⊃ {读后写/PRAM} ⊃ {读己写, 单调读, 单调写} ⊃ 最终一致
（每个 ⊃ 表示「更强模型是更弱模型的真子集：满足强的历史一定满足弱的」）
```

**位置越靠左（越强），一个模型"允许发生的历史"越少、越接近一台理想单机、客户端越不需要动脑；越靠右（越弱），允许的历史越多、副本越能各自为政、把消解分歧的活儿推给应用。** 谱系不是"越强越好"——它是一张"你想要多少直觉、愿付多少协调代价"的价目表。Jepsen 的谱系图与 Viotti-Vukolić 的综述都用"包含关系（子集）"来组织这张图，本报告与之对齐。

### 5.5.2 越强越需协调：一致性强度 ↔ 可用性/延迟的权衡轴（对接 CAP）

这条谱系的经济学本质是一句话：**一致性越强，副本之间就越需要在每次操作时协调（等多数派、等实时序对齐），因此在网络分区时越难保持可用、在正常时延迟越高。** 具体到可用性，谱系被切成三段（Bailis et al. HAT 2014 / Jepsen 整理）：

```
顺序一致及更强（含线性一致、严格可串行化）：分区期间无法保持可用 —— 必须停服务或牺牲一致（对应 CAP 的 C↔A 二选一）
读己写 ~ 因果一致：至多「粘性可用 (sticky available)」—— 客户端粘住副本即可继续
最终一致 / PRAM / 单调读写：可「完全可用 (totally available)」—— 任意副本随时响应
```

这正是**对接大主题6 CAP** 的接口：Gilbert & Lynch 2002 证明的 CAP 定理里那个"C"，**精确地就是线性一致性**——分区期间，一个线性一致（C）的系统无法同时保持可用（A）。所以谱系左端（线性/顺序一致）天然是 CAP 意义下的"CP"候选，右端（因果/最终一致）才能做"AP"。PACELC 进一步补充：**即使没有分区（E, else），强一致也要用延迟 L 来换**——因为等待协调本身就是延迟。谱系 ↔ CAP ↔ PACELC 三者说的其实是同一件事的三种切法，大主题6 展开精确表述与误读辨析。

### 5.5.3 用谱系给系统选点：为什么"够用的最弱"往往是对的

工程上用这条谱系做决策的心法是：**先问业务能容忍的最弱语义是什么，选那一档，而不是无脑上最强。** 因为每往强的方向走一格，都要为分区期不可用、正常期高延迟、跨副本协调开销买单。

给初学者的落地判据（对接后续系统课的归类方法）：需要"读到就是全局最新、且能安全当锁用"选**线性一致**（代价：CP、协调贵）；只需"大家看到同一本剧本、不必贴实时"可退到**顺序一致**；社交/协作类只要"因果不乱、并发可分歧"用**因果一致**（甜点：高可用又挡住反直觉乱序）；纯计数/缓存/购物车类能自行收敛的，用**最终一致 + 会话保证**（读己写等）把最扎人的体验窟窿补上即可。具体系统（Dynamo/Cassandra 偏右、Spanner 偏最左）如何按 CAP/PACELC 精确归类，归大主题6 的分类方法与 L6-05 的实例，本节只给谱系轴与选点直觉。
