## 3.1 复制目标与架构

### 3.1.1 为什么要复制：容错、低延迟、读扩展

**复制**指在多个节点上各保存同一份数据（或运行同一个服务）的多个副本（replica）。做这件事图的是三件好处：**容错**——一台机器崩了，其它副本还能继续服务，这是分布式系统对抗"部分失败"（大主题1）的第一道防线；**低延迟**——把副本放到离用户近的机房，用户就近读，省掉跨洲往返；**读吞吐扩展**——读请求可以分散到多个副本上并行处理，突破单机读上限。

要先把复制和另外两个常被混淆的概念分清。**复制 ≠ 分区（partition/sharding）**：复制是"同一份数据存多份"（冗余，图容错与读扩展），分区是"把整份数据切成互不重叠的几块分别存"（图写扩展与容量）。真实系统通常两者叠用（每个分区再各复制几份），但它们解决的是不同问题。**复制也 ≠ 备份**：备份是某个时间点的静态快照、通常用于灾难恢复；复制是持续的、副本要跟着主数据一起实时演进。

复制真正的难点不在"复制"本身，而在"复制过程中数据一直在变"。如果数据只写一次、之后永不改，把它拷 N 份就完事了；难的是**写操作源源不断到来，如何保证 N 份副本对"发生了哪些写、以什么顺序发生"达成一致**——这就是后面三种拓扑和 RSM 模型要解决的核心。

### 3.1.2 主从复制（single-leader / 主备）

**主从复制**（single-leader，也叫 primary-backup、active-passive）指定一个副本为**主**（leader/primary），所有**写**只能发给主；主把每一次写变更（作为一条一条的变更记录/日志）按它接收的顺序转发给各个**从**（follower/replica），从按同样顺序重放这些变更。**读**可以走主，也可以走从（放宽一致性时）。

它是最主流、最好理解的方案，绝大多数关系数据库（PostgreSQL、MySQL 的默认复制）、以及 Raft/ZooKeeper 这类系统本质上都是主从。它天然解决了"写的顺序"问题：**因为只有主一个人接收写，写的全局顺序由主唯一确定**，从只要照抄这个顺序就不会乱——这正是 3.2 复制状态机模型的现实载体。

主从的代价与风险要点：写吞吐受限于单个主（写不能水平扩展，只能靠分区）；**主一旦崩溃就要做故障转移**（failover）——选一个从接任新主，这个"选主"恰恰需要共识（大主题4），而且如果旧主没死透只是网络分区，可能出现两个主同时自认为是主的**脑裂**（split-brain），这也是为什么严肃系统的选主要靠多数派而非拍脑袋。

### 3.1.3 多主复制（multi-leader / 主主）

**多主复制**（multi-leader，multi-master）允许**多个**副本同时接受写（通常一个数据中心一个主），每个主把自己的写异步同步给其它主。典型场景是**多数据中心部署**（每个机房本地写、跨机房再对齐）和**离线可写**的客户端（如日历 App 多设备各自编辑）。

它的好处是写不再被单点主卡住、且跨地域写延迟低（写本地主即可）。但它引入了主从没有的头号难题——**写冲突**（write conflict）：两个主可能在几乎同一时刻对同一份数据写了不同的值，等这两笔写异步传到对方时，谁都不知道该听谁的。因为没有单一的主来定序，**同一份数据在不同主上可能出现分歧的历史**，必须额外引入冲突解决策略（如"最后写入者胜 LWW"、版本向量、应用层合并、CRDT 等）才能最终收敛。

给初学者的关联：多主之所以难，正是因为它放弃了主从"单点定序"这个宝贵性质。3.2 会讲到，RSM 收敛的前提是各副本喂进**同一条有序日志**；多主天然没有这条唯一的全序日志，所以它换来的写可用性，代价是收敛性和一致性都被削弱（往往只能做到最终一致，大主题5）。

### 3.1.4 无主复制（leaderless / Dynamo 风格）

**无主复制**（leaderless）彻底取消"主"这个角色：客户端（或代它的协调者）把每一次写**直接并行发给多个副本**，也把每一次读**并行发给多个副本**，然后用"法定人数"（quorum）规则来判断写是否算成功、读该采信哪个值。代表是 Amazon Dynamo 及其血脉的 Cassandra、Riak、Voldemort。

它的核心思路是不再靠"谁是主"来保证一致，而是靠**读集合与写集合必然相交**这条算术事实（3.3 详解 W+R>N）：只要每次写让足够多副本确认、每次读问足够多副本，读集合里就一定包含至少一个"见过最新写"的副本。为了应对副本暂时落后，无主系统还配套**读修复**（read repair，读时发现某副本旧就顺手更新它）和**反熵**（anti-entropy，后台不断比对补齐差异）。

无主的取舍：牺牲了主从那种清晰的全局顺序和强一致，换来极高的写可用性（挂几台仍能读写）和无单点。它对写冲突同样敏感（多个客户端并发写同一键），一般用版本向量（大主题2）标记并发、再做冲突解决。初学者需记住的边界：**无主 + quorum 给的是"能读到最新写"的概率性/条件性保证，不是无条件的线性一致**，其边界在 3.3.4 专门讲。

## 3.2 复制状态机模型（RSM）

### 3.2.1 RSM 核心不变式：确定性状态机 + 相同有序日志 ⇒ 相同状态

**复制状态机**（Replicated State Machine, RSM）是让多个副本保持一致的经典模型：把服务建模成一个**确定性状态机**（同样的当前状态 + 同样的输入 ⇒ 必然产生同样的新状态和同样的输出），给每个副本一份**完全相同、顺序完全相同的操作日志**（log），让每个副本从相同初始状态出发、按相同顺序把日志里的操作逐条 apply 到自己的状态机上。核心不变式是：

相同初始状态 + 相同顺序的相同操作序列 + 每步转移确定 ⇒ 所有副本经过每一步后状态恒等

换句话说，只要把"让副本一致"这个难题，**归约成"让所有副本拿到同一份有序日志"这一个难题**，状态的一致就被确定性自动保证了。

给初学者的直觉：把每个副本想成一台一模一样的计算器，日志是一叠**编了号、必须按号执行**的指令卡（"+3""×2""-1"……）。只要两台计算器从 0 开始、严格按 1,2,3… 的号执行同一叠卡，它们任何时刻显示的数字必然相同——不需要它们互相看对方的屏幕，只需要保证"卡的内容和顺序一致"。这就是 RSM 把"同步状态"偷换成"同步日志"的精髓。

### 3.2.2 确定性为什么是硬前提

RSM 成立的**硬前提是状态机必须确定性**：给定当前状态和下一条操作，新状态与输出必须唯一确定，不能依赖任何副本各自不同的"隐藏输入"。一旦某步转移引入了各副本会不一样的东西——本地时钟读数（`now()`）、随机数、哈希表遍历顺序、未定序的并发线程调度、依赖到达时刻的逻辑——即便日志完全相同，副本也会**分叉**（diverge），不变式当场失效。

最小易错例子：

日志里有一条操作 "把字段 ts 设为当前时间 now()"

如果每个副本各自执行 `now()`，副本 A 记下 10:00:00.001、副本 B 记下 10:00:00.007，状态立刻不一致。正确做法是**把不确定性挪到日志外面**——由定序者（主/共识层）先把 `now()` 求好值、把"设 ts = 10:00:00.001"这个**已定值的操作**写进日志，各副本 apply 的是同一个确定值。这条"消除非确定性"的纪律，是把真实服务做成 RSM 时最常踩的坑，Raft/6.5840 的 lab 里反复强调。

另一个初学者常混的点：**RSM 不要求副本同步执行、也不要求实时一致**。副本可以有快有慢，落后的副本只是"日志 apply 到的位置靠前"，只要它继续按序 apply，迟早会追上并与其它副本经历完全相同的状态轨迹。RSM 保证的是"沿相同轨迹演进"，不是"任一瞬间完全同步"。

### 3.2.3 RSM 与共识的分工：复制是目标，共识是手段

RSM 把一致问题归约成了"所有副本拿到同一份有序日志"，那**这份日志的每一格里到底放哪条操作、由谁拍板**？——这一步，正是**共识**（consensus，大主题4）负责的。Paxos、Raft、Zab 这些共识算法，本质上就是在反复对"日志的第 i 格是什么"达成一致；一旦第 i 格被多数派确定下来（committed），各副本就能安全地 apply 它。

这就是本大主题反复强调的分账：

```
复制（RSM）  = 目标/模型：让多副本收敛到同一状态轨迹
共识（Paxos/Raft）= 手段：就"有序日志的每一格填什么"逐格达成一致
```

Schneider 1990 用的措辞是：RSM 需要满足 **Agreement**（每个正常副本收到相同的操作请求序列）与 **Order**（每个正常副本以相同顺序处理请求）两个条件——而共识/全序广播（大主题2、大主题4）正是用来落实这两个条件的机制。初学者只需记住：**看到"确定性状态机 + 有序日志"是复制模型，看到"Prepare/Accept、AppendEntries、选主、多数派投票"才是共识协议**；本报告讲前者，后者归大主题4。

## 3.3 读写 Quorum 与 W+R>N

### 3.3.1 quorum 交集不变式：W+R>N

在无主（或可调一致的）复制里，设总副本数为 N，规定：**每次写必须收到至少 W 个副本的确认才算成功，每次读必须从至少 R 个副本收集回应**。当满足

W + R > N

时，任意一个**读集合**（R 个副本）与任意一个**写集合**（W 个副本）必然**至少有一个副本重叠**——这个重叠副本既参与了最近那次写、又参与了本次读，于是本次读一定能"碰到"最新写过的那个副本。这就是**法定人数（quorum）交集**保证，是无主复制读到最新写的算术基石。

一个常配套的写侧不变式（防止两次写彼此不相交导致丢写）是：

2W > N

即两个写集合也必然相交，从而同一键的写有一个共同副本能看到彼此、便于定序或冲突检测。实践中最常用的对称配置是把 W、R 都取多数派：

W = R = ⌊N/2⌋ + 1

此时 W+R = N+2 > N 且 2W > N 同时满足，这也是 Paxos/Raft 用"多数派"（majority quorum）的原因。

### 3.3.2 为什么交集就能保证读到最新

这里的核心直觉是**鸽笼原理**：N 个副本里，写占了 W 个、读占了 R 个，如果 W+R>N，两拨加起来超过总数，就不可能"井水不犯河水"地各占一批不相交的副本——必然有至少一个副本被"两边都数到了"。

用最小例子（N=3, W=2, R=2，满足 2+2>3）：

副本编号 {1,2,3}
写 x=新值 → 落在某 2 个副本上，比如 {1,2}
读 x     → 问某 2 个副本，比如 {2,3}
交集 = {2} 非空 → 副本 2 既有新值、又被这次读问到 → 读得到新值

即便读的是 {3},{1} 之外最"错开"的组合，只要各取 2 个，就总有一个重叠。读到多个版本时，靠版本号/时间戳/版本向量（大主题2）挑出最新的那个即可。

这条不变式最漂亮的地方在于：它**不需要任何主、不需要任何副本实时同步**，纯靠"集合大小之和超过总数"这一算术事实，就把"读到最新写"从"依赖同步时机"变成了"依赖计数"。这也是无主复制敢于放弃主、仍宣称能强一致读的底气。

### 3.3.3 W/R 配置的调参谱系

W 和 R 在 W+R>N 约束下怎么分配，是一条**读延迟 ↔ 写延迟 ↔ 可用性**的调参轴：

```
W 大、R 小（如 W=N, R=1）：读快且读高可用（问一个副本即可），但写慢、写可用性差（要等所有副本）
W 小、R 大（如 W=1, R=N）：写快且写高可用，但读慢、读可用性差
W=R=多数派（约 N/2）    ：读写延迟与可用性均衡，最常用
```

要点是**能容忍多少故障由 W、R 各自决定**：写要等 W 个确认，就最多容忍 N−W 个副本不可用仍能写；读同理最多容忍 N−R 个不可用仍能读。取多数派（约 N/2）时，读写都能在少数副本故障下继续，且满足交集，故成为默认。

初学者易错点：**W+R>N 是"读能看到写"的充分条件之一，但把 W 或 R 调到不满足该式（如 W=R=1, N=3）并不是"配置错误"**——那是系统在**故意换取更低延迟/更高可用**，代价是只能保证最终一致、读可能拿到旧值。很多生产系统正是这样按业务容忍度调这两个旋钮，不是必须处处 W+R>N。

### 3.3.4 W+R>N 的边界：它保证不了什么

必须诚实地讲清 W+R>N 的**局限**，否则初学者会误以为它等于线性一致（大主题5）。至少有以下场景，即便 W+R>N 也可能读到旧值或产生分歧：

其一，**sloppy quorum（松散法定人数）**：当"本该负责这个键的那 N 个指定副本"里有些不可用时，Dynamo 风格系统允许把写临时接管到别的副本上（hinted handoff），于是这次写落在了指定 N 个之外——后续的读即便凑齐 R 个指定副本，也可能与这次写**没有交集**，W+R>N 的前提被打破。（sloppy quorum/hinted handoff 的机制细节归 L6-05。）

其二，**并发写**：多个客户端同时写同一键，各自都满足 W，但彼此的写集合内容不同，系统只能靠版本向量记录"这两笔是并发的"、再做冲突解决（LWW/合并），quorum 本身不消解并发冲突。

其三，**写失败的中间态**：一次写只成功了不到 W 个副本就返回失败，但那几个已写的副本并不会回滚——之后的读可能读到这笔"名义上失败"的写，也可能读不到，行为不确定。

其四，**时序/线性一致**：W+R>N 只保证"存在一个副本见过最新写值"，不保证读写之间满足实时序（一个刚完成的写，另一个客户端的后续读在没凑够交集或遇到读修复竞态时仍可能看到旧值）。**要真正的线性一致需要额外机制**（如经由共识的读、ReadIndex/租约读，属大主题5与 L6-05），单靠 quorum 计数不够。

记住一句话：**W+R>N 是"多数派相交"的算术保证，给的是一致性的一块拼图，不是线性一致本身。**

## 3.4 同步 vs 异步复制的张力

### 3.4.1 复制时机：写延迟与丢数据风险的对立

同步 vs 异步的分歧点，是一个非常具体的时机问题：**主（或写协调者）在把写转发给其它副本后，要不要等副本确认，才向客户端回复"写成功"？**

```
同步复制（synchronous） ：等到（指定的）副本都确认写入持久化后，才回客户端"成功"
异步复制（asynchronous）：主一写到本地就立刻回客户端"成功"，转发给副本在后台异步进行
```

这两个选择把"写延迟"和"丢数据风险"放在了天平的两端，**无法同时最优**：

```
同步 → 数据安全（回成功=多副本已有），但写延迟高、且任一副本慢/挂会拖住甚至卡死写
异步 → 写延迟低、写高可用（不被慢副本拖累），但主在"已回成功、副本还没收到"的窗口内崩溃，这笔已确认的写就丢了
```

### 3.4.2 半同步：现实系统的折中

纯同步（等所有副本）在实践中几乎不用——只要有一个副本慢或挂，写就得停摆，可用性太差。纯异步则有丢已确认数据的风险。所以真实系统普遍走**半同步**（semi-synchronous）：只要求**一部分**副本同步确认，其余异步跟进。

最典型的半同步就是 3.3 的 **quorum**：等 W 个副本确认（而非全部 N 个）就回成功。取 W=多数派时，既保证"回成功的写至少在多数副本上、故障转移选出的新主必含这笔写不会丢"，又不必等最慢的那些副本——**quorum 本质上就是一种把"等多少个"参数化的半同步复制**。MySQL 的 semi-sync、PostgreSQL 的 `synchronous_standby_names`（可配置等几个备库）也是同一思路的工程化。

给初学者的关联：这解释了为什么 3.3 的 W 旋钮同时是"一致性旋钮"和"延迟/可用性旋钮"——它决定的正是"回成功前要同步等几个副本"这个复制时机。W 越大越偏同步（安全、慢），越小越偏异步（快、易丢）。

### 3.4.3 与 RSM/共识提交的关联，及一个常见误解

把 3.4 接回 RSM（3.2）与共识：在 Raft 这类系统里，"一条日志何时算 **committed**（可安全 apply）"的规则，正是"被多数派副本持久化后"——这恰恰是一次半同步（多数派 quorum）复制。所以"复制时机"在共识语境下就是"提交规则"：**committed = 多数派已复制**，既不等全部（避免被慢副本拖死，保 liveness），又不只写主（避免主崩丢数据，保 safety）。

一个必须点破的误解：**异步复制不等于"最终一致就够了"或"数据不重要"**。异步复制在正常无故障时副本很快就追平，读起来往往和同步差不多；它的风险只在"主已回成功但副本尚未跟上时主恰好崩溃"这个窄窗口暴露。是否接受这个窗口，取决于业务对"丢掉最近几毫秒已确认写"的容忍度——金融账务多用同步/多数派，日志/指标/缓存类常用异步换吞吐。**同步与异步不是对错之分，是拿"这笔写多久能返回"去交换"这笔写崩溃时会不会丢"的定价选择。**
