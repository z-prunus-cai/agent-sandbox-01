## 2.1 物理时钟与时钟漂移

### 2.1.1 石英振荡器与时钟漂移（drift / skew）

计算机的本地时钟由一块**石英晶体振荡器**驱动：晶体以接近固定的频率振动，硬件数它振了多少次来推进时间。问题在于，任意两块晶体的实际频率都略有差别，而且会随温度、老化、电压波动，所以每台机器的时钟走得**快慢不一**。两个概念要分清：某一时刻两台时钟读数之差叫**偏移（clock skew / offset）**；单位真实时间里这个差的增长速率叫**漂移率（drift / clock drift）**。

普通计算机石英时钟的漂移率通常在**百万分之几十（数十 ppm）**这个量级；RFC 5905 更指出石英振荡器可有几百 ppm 的**系统性偏差**外加几 ppm 的随温度随机变化。给个直观换算：

```
若漂移率 = 50 ppm = 50 微秒/秒，则一天累计偏差 ≈ 50e-6 × 86400 s ≈ 4.3 秒
```

也就是说，一台不做任何校正的机器，一天就能和真实时间差出好几秒。这解释了两件事：为什么必须定期同步（§2.1.2），以及为什么"直接比两台机器此刻的时间戳"是不可靠的。

初学者容易以为"电脑时间是精确的"。其实本地时钟只是**自己数自己的拍子**，没有外部校正时它只保证"自己单调往前走"，绝不保证"和别人一致"。偏移是两台钟的差、漂移是这个差变大的速度——校正能把偏移拉回来，但只要不校正，漂移就会让偏移重新累积。

### 2.1.2 NTP 同步：能拉近，但留有残余误差

**NTP（Network Time Protocol）**是互联网上把机器时钟同步到参考时间源（最终追溯到原子钟/GPS）的标准协议，当前主版本 NTPv4 由 **RFC 5905（2010 年 6 月）**规范。它的核心是客户端与服务器交换带四个时间戳的报文，用往返测量估计**单向网络延迟**与**时钟偏移**，再平滑地把本地时钟"拉"向正确时间（disciplining），并持续估计本地漂移率来做前馈补偿。基本估计式（假设去/回程延迟对称）为：

```
offset θ = ((t1 − t0) + (t2 − t3)) / 2
delay  δ = (t3 − t0) − (t2 − t1)
```

其中 t0/t3 是客户端发送/接收时刻，t1/t2 是服务器接收/发送时刻。

关键在于同步**永远留有残余误差**。RFC 5905 给出的典型精度：广域网上 NTP 客户端相对服务器通常准到**几十毫秒**量级（poll 间隔可长达 36 小时）；在现代工作站 + 快速局域网上，改进的滤波/校准算法可把精度提到**几十微秒**量级。误差来源主要是网络往返延迟的**不对称与抖动**——上式假设去回程对称，一旦不对称，offset 估计就带偏。

NTP 让分歧从"每天几秒"缩到"几十毫秒到几十微秒"，这对看日志、算超时足够好，但**没有把偏差消到零**。所以你不能假设"两台 NTP 同步过的机器时间戳完全一致"。此外校正可能让时钟**回拨**（往回跳），于是同一台机器上后发生的事件也可能拿到更小的时间戳——单调性都不保证（这也是为什么很多系统区分"可回拨的墙上时钟"与"只增的单调时钟"）。⚙NTP 家族演进快：更高精度场景已有 PTP（IEEE 1588）等，此处不展开，锚 RFC 5905 版本为准。

### 2.1.3 为什么物理时间戳不能给分布式事件定序

综合 2.1.1–2.1.2：既然每台机器的时钟有漂移、同步后仍有**几十毫秒到几十微秒**的残余误差，那么当两个在不同机器上发生、时间间隔**小于这个误差**的事件出现时，比较它们的物理时间戳给出的先后**可能与真实先后相反**。更糟的是，即便物理先后判对了，物理"先"也**不等于**"有因果影响"。所以物理时钟无法可靠地回答分布式系统里最基本的问题——"哪个事件先发生 / 谁可能影响了谁"。


```
真实时间轴：机器 A 在 10.000s 发出请求 req；机器 B 在 10.005s 收到并处理，记事件 proc
若 A 的钟快 8ms、B 的钟慢 4ms：A 给 req 打戳 10.008s，B 给 proc 打戳 10.001s
按物理时间戳比较：proc(10.001) < req(10.008) —— 结论"处理发生在请求之前"，荒谬
```

这就是 Lamport 1978 的出发点，也是本大主题其余小节的动机：既然物理时间不可靠，就换一把尺子——不测"绝对时间"，只刻画"因果先后"。这把尺子就是 §2.2 的 happens-before 关系，以及实现它的逻辑时钟。

初学者不必背具体毫秒数，抓住这条逻辑即可：**误差存在 + 事件可能挨得比误差还近 ⇒ 物理时间戳定序会错**。分布式定序问题因此必须绕开物理时间，改用只依赖"消息实际传递了"这一事实的逻辑方法。

## 2.2 happens-before 与 Lamport 时钟

### 2.2.1 happens-before 偏序关系

Lamport 1978 定义了事件之间的**"先于发生"关系（happened-before，记 →）**，它完全不依赖物理时间，只由两类"确实可能传递影响"的先后构成，并对传递闭包封闭。三条定义（对应论文的三个条件）是：

```
(1) 同进程内：若 a、b 在同一进程且 a 排在 b 前面，则 a → b
(2) 消息：若 a 是某进程发送消息 m，b 是另一进程接收同一条 m，则 a → b
(3) 传递：若 a → b 且 b → c，则 a → c
```

满足这些的 → 是事件集合上的一个**偏序（partial order）**（严格偏序：不自反、传递）。

为什么只认这两类先后？因为分布式系统里，一个事件能"影响"另一个，**唯一**的途径要么是它们在同一进程里按程序顺序执行（本地能看到彼此），要么是通过发/收消息把信息从一处传到另一处。除此之外，两个分处不同机器、又没有消息把它们串起来的事件，谁也影响不了谁——凭什么说谁先谁后？Lamport 的洞见就是：**分布式系统真正需要的"先后"不是物理时间先后，而是这种"可能有因果影响"的先后**，而后者恰好只由程序顺序 + 消息传递决定，与不可靠的物理钟无关。

a → b 读作"a 可能影响到 b"或"a 是 b 的因果前驱"。它是**偏序**而非全序，意味着允许存在互不可比的事件对——这正是下一节"并发"的来源。

### 2.2.2 并发（concurrent）关系

如果两个事件 a、b 满足**既不 a → b、也不 b → a**，就称它们**并发（concurrent）**，记 a ∥ b。

```
a ∥ b   ⟺   ¬(a → b) ∧ ¬(b → a)
```

并发**不是**"物理上同时发生"的意思，而是"两者之间没有任何因果路径，谁也不可能影响谁"。它们在真实时间里谁先谁后完全无所谓，因为系统没有任何办法（也没有任何必要）去区分。

直觉上总觉得"任何两个事件总有个先后"。但在分布式世界里，"没有消息把它们联系起来"就意味着这个先后**没有可观测的意义**，强行给它们排序只会是武断的。happens-before 是偏序，正是因为它诚实地承认了"有些事件对之间就是没有先后可言"。§2.3 的向量时钟能力的关键，就在于它能**判定**出这个 ∥ 关系；而 §2.2.3 的标量时钟做不到（§2.2.4）。

### 2.2.3 Lamport 逻辑时钟与递增规则

**Lamport 逻辑时钟**给每个进程 Pi 一个整数计数器 Ci，给每个事件 a 赋一个时间戳 C(a)，目标是让时间戳满足**时钟条件（Clock Condition）**：

```
若 a → b，则 C(a) < C(b)
```

要满足它，论文给出两条实现规则（原文 IR1、IR2）：

```
IR1：每个进程 Pi 在它的任意两个相继事件之间把 Ci 加 1（本地事件也要 +1）
IR2a：进程 Pi 发送消息 m 时，把当前时间戳 Tm = Ci 附在 m 上一起发出
IR2b：进程 Pj 收到带戳 Tm 的 m 时，先令 Cj = max(Cj, Tm)，再 +1，然后给"接收"这个事件赋新的 Cj
```

直觉上，IR1 保证"同进程内后发生的时间戳更大"（覆盖 happens-before 的条件 1），IR2 里的 `max(Cj, Tm)+1` 保证"收消息事件的戳一定大于发消息事件的戳"（覆盖条件 2）；两者加传递性，就凑齐了时钟条件。

一个最小例子（也是 §2.2.4 脚本里的场景）：P0 本地事件 a 得 C=1，P0 发消息事件 b 得 C=2 并把 2 发给 P1；P1 收消息事件 c 令 C=max(0,2)+1=3；P1 本地事件 d 得 C=4。于是 a(1)→b(2)→c(3)→d(4)，时间戳沿因果链严格递增。

初学者要抓住 `max(...)+1` 这个动作的意义：它是"把别人的时间往自己身上并"——只要一条消息从高时钟的进程流到低时钟的进程，接收方就被"拉高"到不低于发送方，从此它的后续事件时间戳都盖过了那条因果链上游的一切。这就是逻辑时钟"追上因果"的机制。

### 2.2.4 只蕴含一个方向：因果 ⇒ 时间戳更小，但反之不成立

标量 Lamport 时钟只保证**单向**蕴含：

```
a → b  ⇒  C(a) < C(b)      （成立，即时钟条件）
C(a) < C(b)  ⇒  a → b      （不成立！反过来推不出因果）
```

也就是说，看到 C(a) < C(b) 你**不能**断定 a 因果地影响了 b——它们可能只是**并发**事件，却被时钟排出了一个先后。所以标量时钟能用来**构造**一个全序（§2.2.5），但**不能用来判定**两个事件到底是有因果关系还是并发（那要靠向量时钟，§2.3）。

已就地用 Python 验证（scratchpad，非入库）。场景：P0 本地 a、发 b→P1；P1 收 c、本地 d、发 f→P2；P2 本地 e、收 g。真实输出：

```
Lamport 时间戳 (proc, C): a=(0,1) b=(0,2) c=(1,3) d=(1,4) e=(2,1) f=(1,5) g=(2,6)
Clock-condition holds on hb pairs: True        # 所有 happens-before 对都满足 C(a)<C(b)
e,b scalar C: 1 2  -> 标量时钟给并发事件 e、b 排了 e<b 的先后（其实 e ∥ b）
```

e 是 P2 的本地事件、b 是 P0 的发送事件，二者之间没有任何消息路径，本应并发；但标量时钟给出 C(e)=1 < C(b)=2，凭空造了个"e 在 b 之前"。这就是"反向不成立"的活证据，也直接引出向量时钟的必要性。

初学者别把这当缺陷——它是**取舍**。标量时钟只用一个整数、开销极小，代价就是丢掉了"区分因果与并发"的信息；当你只需要一个说得过去的全序（比如做全序广播的打平局键，§2.4）时，它足够且划算。

### 2.2.5 用 Lamport 时间戳构造事件全序

happens-before 是偏序，但很多场景需要一个**全序**（所有事件排成一条唯一的队）。做法是拿 Lamport 时间戳当主键、进程编号当**打平局（tie-break）**的次键：

```
定义全序 ⇒：a ⇒ b  当且仅当  C(a) < C(b)，或 ( C(a) = C(b) 且 pid(a) < pid(b) )
```

因为进程编号两两不同，这个 ⇒ 是一个**全序**，且**扩展**了 happens-before（若 a → b 则必有 a ⇒ b）——即它与因果不矛盾，只是额外给并发事件也强行定了先后。

这一步初学者要理解它的"合法但武断"：全序里那些先后，凡是来自真实因果（→）的都靠谱，凡是靠 pid 打平局的都是人为约定。好在对很多应用（如让所有副本按同一顺序处理请求）来说，**只要大家用同一个约定、排出同一条序**就够了，序"对不对得上物理真相"并不重要。这正是 §2.4 全序广播 + 时间戳定序的思想内核；而这个全序**无法反推因果**，需要因果信息时仍得回到向量时钟。

## 2.3 向量时钟

### 2.3.1 向量时钟的结构与更新规则

**向量时钟（vector clock）**由 Fidge（1988）与 Mattern（1989）独立提出。它把标量时钟换成一个长度为 N（进程数）的整数**向量**：进程 Pi 维护 Vi[1..N]，Vi[k] 表示"就 Pi 目前所知，进程 Pk 已经发生了多少个事件"。更新规则与标量版平行，只是每格独立：

```
本地/发送事件：Pi 先把自己那格 +1，即 Vi[i] += 1
发送消息 m：附上当前整个向量 Vi 一起发出
接收消息 m（带向量 Vm）：先逐格取最大 Vi[k] = max(Vi[k], Vm[k]) for all k，再把自己那格 +1（Vi[i] += 1）
每个事件被赋予"更新后的整个向量"作为它的向量时间戳 V(e)
```

直觉上，标量时钟把"我知道多少"压成一个数会丢信息；向量时钟给每个进程留一格，于是一个事件的时间戳精确记下了"要产生我，各进程分别至少已经发生了多少个事件"——这恰好是它的**因果历史的计数摘要**。收消息时逐格取 max，就是把发送方的"见识"并进自己的向量。

### 2.3.2 向量的偏序比较：判 happens-before 与并发

向量时间戳之间定义逐格比较，据此**精确**判定因果关系（这是向量时钟相对标量时钟的核心增益）：

```
V ≤ W  ⟺  对所有 k，V[k] ≤ W[k]
V < W  ⟺  V ≤ W 且 V ≠ W
判定：a → b   ⟺   V(a) < V(b)
判定：a ∥ b   ⟺   ¬(V(a) ≤ V(b)) 且 ¬(V(b) ≤ V(a))   （两向量互不"支配"，即各有一格严格更大）
```

标量时钟只有 `a → b ⇒ C(a) < C(b)` 这**单向**蕴含（§2.2.4），而向量时钟做到了**双向等价** `a → b ⟺ V(a) < V(b)`，因此**既能判 happens-before、又能判并发**。

已就地用 Python 验证（同 §2.2.4 场景）。真实输出：

```
VC a=[1,0,0] b=[2,0,0] c=[2,1,0] d=[2,2,0] e=[0,0,1] f=[2,3,0] g=[2,3,2]
b<c (happens-before)? True          # V(b)=[2,0,0] < V(c)=[2,1,0]，判定 b→c 成立
e concurrent with b? True           # e=[0,0,1] 与 b=[2,0,0] 互不支配 ⇒ 判定并发（标量版曾误排 e<b）
e concurrent with d? True           # e 与 d=[2,2,0] 也并发
less(e,g)=True                      # e=[0,0,1] < g=[2,3,2]：e→g 成立（g 是 P2 收 m2 后的事件，程序序在 e 之后）
```

对照 §2.2.4：同样的 e 与 b，标量时钟错判成"e 在 b 之前"，向量时钟正确判为**并发**。这就是"捕获因果" vs "仅蕴含因果"的差别落到可运行代码上的样子。

`V(a) < V(b)` 要求 b 的向量在**每一格都不小于** a 且至少一格更大——直观意思是"要产生 b，必须已经历过产生 a 所需的一切，还多经历了点别的"，这正是"a 是 b 的因果前驱"。而"并发"就是两个向量**各有各的一格领先**，谁也不包含谁的全部历史。

### 2.3.3 向量时钟 vs 标量 Lamport 时钟

标量 Lamport 时钟只能保证"因果在前 ⇒ 时间戳更小"的**单向**蕴含，可用来造全序但**分不清并发与因果**；向量时钟以每进程一格的代价换来**双向等价**，能同时判定 happens-before 与并发，代价是时间戳大小随进程数增长。

```
标量 C：a → b ⇒ C(a) < C(b)（单向）；空间 O(1)；能造全序，判不了并发
向量 V：a → b ⇔ V(a) < V(b)（双向）；空间 O(N)；能判因果/并发，但不是全序（因为偏序会出现互不可比）
```

选择取决于需求：只要一个说得过去的**全序**（如全序广播打平局，§2.4）——标量足够；要**检测冲突/并发写**（如无主复制里判两个写是否并发、需冲突解决）——必须向量。二者不是谁替代谁，是两种粒度的工具。

初学者常见误解是"向量时钟更好，标量时钟被淘汰了"。恰恰相反：向量时钟的 O(N) 开销在进程多、动态变化时很贵，能用标量的场景没必要上向量。工具按需选，别一律用最强的。

### 2.3.4 代价与变体

向量时钟的主要代价是**时间戳大小与进程数 N 成正比（O(N)）**，且需要知道参与者集合；进程动态加入/退出、或 N 很大时，携带和存储整向量都昂贵。实践中因此出现若干变体：**版本向量（version vector）**用于复制系统里跟踪每个副本对某数据项的更新版本、检测并发写冲突（如 Dynamo）；**点分版本向量（dotted version vector）**更精确地处理"同一客户端多次写"；也有用压缩/裁剪（丢弃已被所有节点确认的历史）来控制大小的做法。

这些变体细节属于复制与存储系统的落地（部分见大主题3/5 与 L6-05），本节只需建立一个认识：向量时钟是"精确捕获因果"的理论工具，但它的 O(N) 开销让工程上常常要在"精确度"和"元数据大小"之间做裁剪与近似。

更精确地区分因果 = 更多的元数据。版本向量就是把"事件计数"换成"副本对某个 key 的更新计数"的同一思想的应用。

## 2.4 全序广播与时间戳定序

### 2.4.1 全序广播（total order / atomic broadcast）的定义

**全序广播（total order broadcast，又称 atomic broadcast）**是一种消息广播抽象：一组节点各自可以广播消息，系统保证所有正确节点最终以**完全相同的顺序**交付（deliver）所有消息。它通常要求两条核心性质：

```
可靠交付（reliable delivery）：没有消息丢失——若一条消息交付给某个正确节点，则交付给所有正确节点
全序交付（totally ordered delivery）：所有节点按同一个顺序交付消息——若节点交付了 m1 再 m2，则没有节点交付 m2 在 m1 之前
```

注意"顺序对所有人一致"是硬约束，且这个顺序一旦定下**不能反悔**（已交付的不能重排）。

为什么需要它？因为若能让所有副本收到**同一串、同一序**的命令，且每个副本都是确定性状态机，那么各副本必然演化出一致的状态——这就是复制状态机（§2.4.3）。全序广播把"让大家步调一致"这件难事收敛成一个干净的抽象。

初学者要区分它和 §2.2.5 那个"用时间戳排全序"：后者是**单机事后**给一堆已知事件排序的规则，前者是一个**在线的、容错的分发服务**，要在消息不断到来、节点可能故障的情况下，持续保证人人交付顺序一致——这难得多，也正因此它与共识等价（§2.4.4）。

### 2.4.2 用逻辑时钟 + 打平局构造一致事件序

把逻辑时钟接到定序上的经典构造（Lamport 1978 用它做分布式互斥的那套）是：每条消息带上发送者的 Lamport 时间戳，接收方按 `(时间戳, 进程号)` 这个**全序**（§2.2.5）把消息排进本地队列；只要能确认"不会再来时间戳更小的消息了"，就按序交付。因为所有节点用的是**同一个确定性的排序键** `(C, pid)`，它们排出的序必然一致。

```
排序键：msg 排在队列里的位置由 (C(msg), pid(发送者)) 的字典序决定（与 §2.2.5 的全序 ⇒ 同款）
交付条件：队首消息 m 可交付 ⟺ 已确知不会再收到 (C, pid) 更小的消息（例如已从每个进程都收到不小于 m 的时间戳）
```

关键的"能交付"判据（§2.4.4 展开）就是难点所在：本地队首看起来最小，不代表全局最小——可能有一条更小时间戳的消息还在路上。

初学者可以把它想成机场按"叫号"登机：号码就是 (C, pid)，谁号小谁先；但广播员不能一看手上号最小就放行，得**确认没有更小的号还没到窗口**才行。这个"确认收全"的要求，是把"排序键"变成"真能定序的服务"的关键，也是它和 §2.2.5 单机排序的本质差别。

### 2.4.3 与复制状态机（RSM）的关系

全序广播和**复制状态机（state machine replication）**是一枚硬币的两面：把每个副本建成**确定性状态机**（同样的输入序列必然产生同样的输出与状态），再用全序广播把客户端命令以同一顺序交付给所有副本，各副本就会**收敛到同一状态**。这个"确定性状态机 + 全序输入日志 ⇒ 副本一致"的模式由 Lamport 提出、Schneider 抽象为通用容错方法。

```
不变式：若所有副本从同一初态出发、按同一顺序 apply 同一串确定性命令，则任意时刻它们状态一致
```

这解释了为什么"造一个一致的事件序"是复制的核心引擎：状态一致问题被归约成了"让所有节点对命令顺序达成一致"。而"达成一致的顺序"正是共识（大主题4）要解决的——所以全序广播、复制状态机、共识三者紧密咬合。

确定性 + 相同输入序 ⇒ 相同状态。这里"确定性"是前提（含随机、含读本地时钟这类不确定操作都会破坏它），"相同输入序"由全序广播提供。RSM 的工程化（快照、成员变更、线性一致读）归大主题3 与 L6-05，本节只讲这条构造原理。

### 2.4.4 一个陷阱：全序何时才"定下来"

用逻辑时钟造全序有一个初学者极易踩的陷阱：**光有时间戳并不能立刻交付**。因为 Lamport 时钟只保证因果在前的时间戳更小，**不保证时间戳按到达顺序单调**——本地队首那条时间戳最小的消息，随时可能被一条时间戳更小、但还在网络里飞的消息插到前面。所以要安全交付，必须先**确认已经收全了所有可能更小的消息**。DDIA 把这点总结为：总序"只有在你收齐全部操作之后才真正定下来"。

其一，在异步、会故障的系统里，"确认收全"本身就需要节点间达成一致——因此**全序广播被证明与共识等价**（互相可归约），它的容错实现绕不开共识算法（Paxos/Raft/Zab，归大主题4）。其二，纯 Lamport 时间戳方案要"确认收全"，通常依赖"从每个进程都听到过更大的时间戳"这类假设，一旦某进程沉默或崩溃就会阻塞——这正是它需要故障检测/共识来兜底的地方。

**逻辑时钟给你一个确定性的排序键，但把这个键变成"人人一致、可容错的交付顺序"需要共识。** 排序键是便宜的，"就绪交付"才是难的。这道坎把本大主题（时间/因果）自然地交接给了大主题4（共识）。
