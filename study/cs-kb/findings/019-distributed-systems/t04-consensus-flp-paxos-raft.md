## 4.1 共识问题定义

### 4.1.1 共识的三条性质：agreement、validity、termination

共识问题（consensus）设定为：每个进程有一个**输入值**（提案），最终要各自**输出一个决定值**（decide），并满足三条性质。第一，**一致性 agreement**：任意两个（正确的）进程不会决定出不同的值。第二，**有效性 validity**：被决定的值必须是某个进程真正提出过的输入（不能凭空捏造一个没人提过的值）。第三，**终止性 termination**：每个正确进程最终都会做出决定（不会永远悬而不决）。

同一件事在不同教材里措辞略有差别，但骨架不变。这里给出对初学者最省心的三句话记法：

```
agreement   — 大家的答案必须一样（不能各说各话）
validity    — 答案得是真有人提过的（不能无中生有）
termination — 每个活着的进程最终都得给出答案（不能卡死）
```

要建立的第一个直觉是：**agreement 才是共识真正难的地方**。validity 通常靠"只提议合法输入"就自动满足；termination 在异步下是 FLP 攻击的靶心（4.2）；而 agreement 要求"哪怕节点崩溃、消息乱序、网络分区，也绝不出现两个进程各认一个值"，这是所有协议花最大力气去守的红线。一个只需要满足 validity+termination 的"假共识"很容易写（每个进程直接决定自己的输入即可），但那样必然违反 agreement——难点恰恰在三条**同时**成立。

一个常见的加强版本是 **uniform agreement（一致同意的一致性）**：不仅正确进程之间不能分歧，连"即将崩溃、但在崩溃前已经决定过"的进程，其决定也不能和别人矛盾。崩溃-恢复模型下这条更贴近现实（崩溃前写进磁盘的决定重启后还在）。初学阶段先记住基本版三条即可，知道有 uniform 强化版存在。

### 4.1.2 safety 与 liveness：把三条性质切成"两类保证"

把上面三条性质按"违反时长什么样"重新归类，就得到分布式系统里最重要的一组二分：**safety（安全性）** 与 **liveness（活性）**。

```
safety   —「坏事永远不发生」：agreement、validity 属此类
           违反 = 在某个有限时刻能指着说"看，这里出错了"
liveness —「好事最终会发生」：termination 属此类
           违反 = 永远等下去也等不到，没有任何单一时刻能判定它"已失败"
```

这个二分之所以关键，是因为它决定了**协议设计的优先级**：safety 绝不允许在任何情况下（哪怕网络烂到极点）被违反；liveness 则允许"暂时得不到，等条件变好再说"。Raft 论文明确表态——**Raft 在任何非拜占庭条件下（含网络延迟、分区、丢包、重复、乱序）都保证 safety，而 liveness 只在多数派存活且能互通时才保证**。这正是应对 FLP 的标准姿势（4.6）。

给初学者的落地记法：**safety 是"绝不说错话"，liveness 是"迟早会说话"**。一个死循环什么都不输出的进程，它 safety 完美（从没说错），但 liveness 全无（永远不说）。真实协议宁可暂时卡住（牺牲 liveness）也绝不给出矛盾决定（守住 safety），因为一个错误的 commit 会污染整个复制状态机，而暂时卡住只要网络恢复就能自愈。理解这一点，后面 FLP、Paxos 活锁、Raft 选举超时才不会读乱。

#### 来源与时效
- Lynch《Distributed Algorithms》(Morgan Kaufmann, 1996) 共识章（一手教材，核实 2026-07-30）：agreement/validity/termination 的形式定义；safety/liveness 二分的经典表述（liveness 违反无有限见证时刻）。
- Raft 论文（Ongaro & Ousterhout, USENIX ATC 2014）§2、§5，扩展版（一手）：明确"任何非拜占庭条件下保证 safety，多数派可互通时保证 liveness/availability"。
- MIT 6.5840 Spring 2026 schedule（一手，核实 2026-07-30）：LEC4/LEC6-7 把共识定位为 RSM 的核心手段，安全性优先于活性。
- 交叉一致，无冲突。uniform agreement 的强化版本各教材措辞不同，本节只取骨架，不逐字裁定。

## 4.2 FLP 不可能性

### 4.2.1 FLP 结论的精确表述

FLP（Fischer–Lynch–Paterson, 1985）证明的是：

```
在纯异步系统模型下，只要存在一个进程可能崩溃（崩溃-停止），
就不存在任何确定性算法能同时保证共识的 agreement、validity 与 termination。
```

要把这句话的每个限定词都咬准，否则极易误读。**纯异步**：消息延迟无上界、进程步速无上界、无同步时钟（大主题1）。**一个进程可能崩溃**：注意是"可能"，哪怕实际一个都没死，只要模型允许"有一个可能死"，结论就成立；且是最温和的崩溃-停止失败，不是拜占庭。**确定性**：算法不能掷骰子（无随机）。结论落在 termination 上——**agreement 和 validity 仍能保证，垮掉的是"一定终止"**。换句话说，异步确定性共识可以做到"永不出错，但可能永远得不出结果"。

对初学者最要紧的一句纠偏：**FLP 不是说"异步下共识做不了"，而是说"没有算法能在所有执行中都保证终止"**。它排除的是"确定性 + 保证终止"这个组合，而不是共识本身。这也正是为什么 Paxos/Raft 能在实践中天天跑——它们没有违反 FLP，只是把"保证终止"松成了"网络稳定时终止"（4.6）。

### 4.2.2 bivalency 论证的直觉

FLP 的证明核心是 **bivalency（双值性）论证**，这里只讲直觉，不做完整形式化。把系统在某一刻的整体状态叫**配置（configuration）**。按"从这个配置往后，最终可能决定出什么值"给配置分类：

```
0-valent  — 无论后续怎么调度，最终只会决定 0
1-valent  — 无论后续怎么调度，最终只会决定 1
bivalent  — 命运未定：存在能走向 0 的后续，也存在能走向 1 的后续
```

证明分两步。第一步：**一定存在一个 bivalent 的初始配置**（否则每个初始配置的命运都被输入唯一锁死，但通过翻转单个进程输入 + 利用"可能有一个进程崩溃"造成的不可分辨，能构造出命运可左可右的初始配置）。第二步（关键）：**从任何 bivalent 配置出发，总能选一条调度把系统带到"下一个仍然 bivalent 的配置"**——也就是说，总能让那个"决出命运"的关键消息被无限拖延，使系统永远停留在"未定"状态。

给初学者的直觉画面：把"命运已定的那一步"想象成一个开关。FLP 说，对手（调度器）永远能抢在开关被拨定之前，插入/延迟恰当的消息，让局面重新回到"两边都还有可能"。因为异步允许消息任意晚到，对手手里永远有这张"再拖一下"的牌。于是存在一条无限长的执行，系统永远 bivalent、永远不决定——termination 被打破。这里"存在一条"就够了：FLP 是对"保证"的否定，只需构造出一个反例执行。

### 4.2.3 常见误读辨析

第一个误读：**"FLP 说分布式共识不可能"**。错。它只针对"纯异步 + 确定性 + 保证终止"这个特定组合；换任一条件（加同步假设、加随机、松成"最终终止"），结论即不适用。

第二个误读：**"因为 FLP，Paxos/Raft 是错的或不可靠"**。错。Paxos/Raft 完全承认 FLP，选择永久保证 safety、只在部分同步（网络终将稳定）时保证 liveness，这与 FLP 毫无矛盾——FLP 恰恰给它们指明了唯一可行的设计路线。

第三个误读：**"FLP 里进程真的崩溃了才出问题"**。错。FLP 的杀伤力来自"活着的慢进程和崩溃进程在异步下不可分辨"（大主题1的"慢 vs 死无法区分"）——哪怕没有任何进程真崩溃，只要模型允许有一个可能崩溃，对手就能用"无限延迟一条消息"制造出与"崩溃"不可分辨的局面。真正的敌人是**无界延迟**，不是实际的崩溃。

## 4.3 Paxos 单值共识

### 4.3.1 角色、目标与"一旦选定永不改变"

Paxos（这里指对单个值达成共识的 **single-decree / Basic Paxos**）里有三种角色：**Proposer（提案者）** 发起提案、**Acceptor（接受者）** 投票并记忆、**Learner（学习者）** 得知最终选定值。同一物理节点常同时扮演多个角色。目标是让整个系统对"选定了哪个值"达成 agreement，并满足一条核心不变式：

```
一旦某个值 v 被"选定"（chosen，即被一个多数派 Acceptor 接受同一提案），
此后任何被选定的值都必须仍是 v。
```

这条不变式就是 Paxos safety 的全部：值只会被选定一次，选定后所有后续提案要么选出同一个 v、要么选不出，绝不会选出另一个值。理解 Paxos 的关键，就是理解它如何用两阶段协议把这条不变式变成数学上必然成立。

给初学者的背景：为什么需要这么绕？因为多个 Proposer 可能同时抢着提议不同的值（比如多个客户端同时想让系统认自己那个值），消息还会乱序、Proposer 会崩溃。Paxos 必须在这种混战里保证"要么没人被选定，要么大家认同一个"。它的办法是给每个提案编一个全局唯一且递增的**编号（proposal number / ballot）**，用编号大小来仲裁冲突。

### 4.3.2 两阶段协议：Prepare / Accept

Basic Paxos 是两个来回（two-phase）。每个提案带一个唯一且递增的编号 n。

```
阶段 1a  Prepare(n)：
    Proposer 选一个比自己见过的都大的编号 n，向多数派 Acceptor 发 Prepare(n)

阶段 1b  Promise(n, (n_accepted, v_accepted)?)：
    Acceptor 收到 Prepare(n)：
      若 n > 它承诺过的最大编号，则
        承诺（promise）今后不再接受编号 < n 的任何提案，
        并回带自己"已接受过的最高编号提案"(n_accepted, v_accepted)（若有）
      否则忽略（或回拒绝）

阶段 2a  Accept(n, v)：
    Proposer 收齐多数派的 Promise 后，选定要提议的值 v：
      若任何 Promise 回带了已接受值，取其中 n_accepted 最大的那个 v_accepted 作为 v
      否则 v 可自由取自己本来想提的值
    向多数派发 Accept(n, v)

阶段 2b  Accepted(n, v)：
    Acceptor 收到 Accept(n, v)：只要没承诺过更大的编号，就接受它，记下 (n, v)
    当一个值被多数派接受 ⇒ 该值被"选定"（chosen）
```

给初学者拆解这两阶段各自的职责。**阶段 1（Prepare/Promise）是"抢占 + 打探"**：Proposer 用大编号让多数派承诺封锁掉所有更小编号（抢占写权），同时打探"你们之前有没有已经接受过什么值"。**阶段 2（Accept）是"提交"**：真正让一个值被多数派接受。最反直觉、也最关键的一步是阶段 2a 里的"**如果打探到已有被接受的值，Proposer 必须放弃自己原本想提的值，改提那个已被接受的值**"——正是这条"抢占者必须尊重前人"的规则，锁死了 4.3.1 的不变式。

### 4.3.3 多数派 quorum 交集：safety 从何而来

Paxos 的 safety 建立在一个纯集合论事实上：

```
任意两个多数派（各含 > N/2 个 Acceptor）必有至少一个公共成员。
```

这就是 quorum 交集（大主题3.3 的 W+R>N 在共识里的化身）。它带来的连锁保证是：如果值 v 已被编号 n 的多数派 Q1 接受（即 v 被选定），那么任何更大编号 n' > n 的提案，其阶段 1 联系的多数派 Q2 必与 Q1 相交——那个公共 Acceptor 一定已接受过 (n, v)，会在 Promise 里把 (n, v) 回带给新 Proposer，逼它在阶段 2a 只能重提 v。层层递推：一旦 v 被选定，所有更高编号的提案都只会重提 v，别的值再也无法被选定。agreement 由此永久成立。

给初学者的直觉：**多数派交集 = "历史无法被抹掉"**。任何想推翻既定值的新提案，都必须先联系一个多数派，而这个多数派里必然"卧底"着一个记得旧值的人，它会把旧值告诉新提案者，新提案者被迫尊重历史。这就是为什么 Paxos 不需要任何同步时钟、不惧崩溃与乱序也能守住 safety——safety 完全建立在"两个多数派必相交"这个和时序无关的数学事实上，因此 FLP 打不到它（FLP 打的是 termination）。

### 4.3.4 活性问题：dueling proposers 与 FLP 的现身

Paxos 的 safety 铁打，但 **liveness 会出问题**：两个 Proposer 可能反复用越来越大的编号互相抢占——A 用 n1 完成 Prepare，B 用 n2>n1 完成 Prepare（作废了 A 的 Accept），A 再用 n3>n2 重来……如此往复，谁的 Accept 都永远无法在多数派上生效。这叫 **dueling proposers（决斗提案者）活锁**。

这正是 FLP 在 Paxos 身上的具体现身：异步下无法阻止这种病态调度，所以 Paxos **无法保证 termination**。Lamport 在「Paxos Made Simple」里明确指出解决办法是选出一个**唯一的（distinguished）Proposer/leader**：只让一个人发提案，就没人跟他抢编号，活锁消失。但"选出唯一 leader"本身又是一个共识/选举问题、在异步下同样不能保证成功——于是活性最终还是靠"网络终将稳定 + 一点超时/随机"来兜底（4.6）。Paxos 把这个 leader 选举留作实现细节，而 Raft 把它抬到协议正中央（4.4）。

## 4.4 Raft leader 选举

### 4.4.1 强领导者与任期（term）

Raft 用一个和 Paxos 不同的组织方式达成同一套 safety：**强领导者（strong leader）**。任何时刻集群最多有一个 leader，**所有客户端请求都经 leader、所有日志条目只从 leader 单向流向 follower**。这把共识拆成三个相对独立、各自好懂的子问题：**leader 选举、日志复制（4.5）、安全性（4.5.4）**。

时间被切成连续的**任期（term）**，每个任期是一个单调递增的整数编号。

```
term 是 Raft 的逻辑时钟：每次选举开启一个新 term，一个 term 最多一个 leader（也可能选不出，是空任期）
每条 RPC 都带发送者的 term；收到更大 term 的消息 ⇒ 自己立刻更新 term 并退回 follower
```

给初学者的直觉：**term 就是"第几届政府"**。编号大的一定比编号小的新，任何节点只要听说了更大的 term，就承认"改朝换代了"、自动下野。这一条"见大 term 即退位"的规则，配合"一个 term 至多一个 leader"，就把 Paxos 里靠 proposal number 仲裁的那套逻辑，收编进了 term 里——term 同时充当了 Paxos 的提案编号和 leader 的任命凭证。Raft 的三种角色是 **Leader / Follower / Candidate**，正常态下只有一个 Leader，其余都是 Follower。

### 4.4.2 选举过程与投票规则

Follower 在**选举超时（election timeout）**内没收到当前 leader 的心跳（空的 AppendEntries），就认为 leader 挂了，发起选举：

```
1. Follower 自增 currentTerm，转为 Candidate，先投自己一票
2. 并行向所有其他节点发 RequestVote(term, candidateId, lastLogIndex, lastLogTerm)
3. 每个节点在一个 term 内至多投一票，先到先得（且要满足日志新旧限制，见 4.5.4）
4. 三种结局：
     (a) 收到多数派选票 ⇒ 成为 leader，立刻发心跳压制其他候选人
     (b) 收到某个自称 leader 且 term ≥ 自己的 AppendEntries ⇒ 承认对方，退回 follower
     (c) 超时无人胜出（选票被瓜分）⇒ 开启新 term，重新选举
```

给初学者的两个要点。其一，**"多数派选票"复用了 quorum 交集**：因为每个 term 每人只投一票，两个候选人不可能在同一 term 各拿到多数派（多数派必相交，那个公共节点只投了一票），所以**一个 term 至多产生一个 leader**——这是 Raft election safety 的根。其二，结局 (c)"选票瓜分（split vote）"是 Raft 特有的活性隐患：多个 follower 几乎同时超时、同时变 candidate、把票分光，谁都不过半，只能重来——若每次都同时超时就会反复瓜分、迟迟选不出，这正是 FLP 式活性问题在 Raft 里的化身，解法见 4.4.3。

### 4.4.3 随机化选举超时：避免选票分裂

Raft 用一个极简的工程手段打破 split vote：**每个节点的选举超时从一个区间里随机取值**（论文建议的量级是 150–300ms，属实现参数、可调）。

```
election timeout ← random(T, 2T)   // 每个节点各自随机、每轮重掷
```

这样绝大多数情况下**总有一个 follower 明显最先超时**，它抢先发起选举、拿到多数票、发出心跳，把还没超时的其他节点重新压回 follower，选举一轮即成。即便偶尔撞车瓜分，下一轮各自重新随机，再次撞车的概率指数级下降。

给初学者的直觉与纠偏：**随机化不是为了 safety，而是为了 liveness**——它不影响"一个 term 至多一个 leader"（那是 quorum 保证的），只负责让"选出 leader"这件事大概率快速发生。这正是 4.6 要总结的"用随机化规避 FLP"的最干净例子：FLP 说确定性算法无法保证终止，Raft 就往超时里掺随机，把"保证终止"换成"以概率 1 终止 / 期望很快终止"，绕过 FLP 而不违反它。注意随机化超时是 Raft 的核心设计，而 Paxos 论文把类似问题留给"选 distinguished proposer"的实现——两者是同一问题的不同包装。

## 4.5 Raft 日志复制与提交

### 4.5.1 AppendEntries 与日志结构

Leader 接到客户端命令后，先追加到自己的日志，再通过 **AppendEntries RPC** 复制给 follower。每条日志条目记 **(index 位置, term 该条被创建时的任期, command 命令)**。心跳就是不带新条目的 AppendEntries。

```
AppendEntries(term, leaderId,
              prevLogIndex, prevLogTerm,   // 新条目前一条的位置与任期，用于一致性检查
              entries[],                    // 要复制的新条目（心跳时为空）
              leaderCommit)                 // leader 已提交到的位置

Follower 收到后：
  1. 若 term < currentTerm ⇒ 拒绝
  2. 一致性检查：若本地在 prevLogIndex 处没有一条 term == prevLogTerm 的条目 ⇒ 拒绝
  3. 检查通过：若已有条目与新条目在同一 index 冲突（term 不同），删掉它及其后所有，再追加新条目
  4. 若 leaderCommit > 本地 commitIndex ⇒ 推进本地 commitIndex
```

给初学者的直觉：**日志就是一排带编号的格子，leader 是唯一的"抄写员"，AppendEntries 是"把我第 i 格及其上下文抄给你"**。第 2 步的一致性检查是精髓——follower 不会盲目接受，它要求"你抄给我的新内容，其紧邻的前一格必须和我这里对得上"，对不上就拒绝，逼 leader 往前退一步再试，直到找到两者日志一致的分叉点，然后用 leader 的版本覆盖 follower 从分叉点之后的所有内容。

### 4.5.2 日志匹配性质（Log Matching Property）

一致性检查的归纳结果，是 Raft 的一条核心不变式 **Log Matching Property**：

```
若两份日志中某条目的 (index, term) 相同，则：
  (a) 它们存的 command 相同；且
  (b) 它们在此 index 之前的所有条目也完全相同。
```

(a) 成立是因为**给定 term 至多一个 leader，而 leader 在一个 index 上只创建一条条目且从不改写自己的日志**，所以 (index, term) 唯一确定一条 command。(b) 成立是因为 AppendEntries 的一致性检查（4.5.1 第 2 步）像归纳步：每次成功追加都先验证了"前一条对得上"，层层回溯即得"之前全部对得上"。

给初学者的意义：这条性质让 follower 与 leader 的日志"一旦某点对齐、则该点之前全对齐"，把"两份日志有多一致"这件复杂的事压缩成"只看最后一个匹配点"。它是后面提交规则与状态机收敛（大主题3.2 的 RSM：同一有序日志喂确定性状态机 ⇒ 副本同态）的地基。

### 4.5.3 提交规则与"只提交当前任期条目"的陷阱

一条日志条目何时算**已提交（committed，可安全交给状态机执行）**？基本规则：

```
leader 把某条目复制到多数派后，该条目即可提交；提交后其之前的所有条目也随之提交。
```

但 Raft 有一条极易被忽略、却关乎 safety 的附加限制：

```
Leader 只能通过"复制自己【当前任期】的条目到多数派"来提交条目；
不能仅凭"某条【旧任期】条目已存在于多数派"就判定它已提交。
```

给初学者讲清这条陷阱的来由：论文里著名的 Figure 8 场景显示，一条旧任期的条目哪怕一度被复制到了多数派，之后仍可能被另一个 leader 的日志覆盖掉——如果贸然按"已在多数派"就提交它，就可能提交一条后来被推翻的条目，违反 agreement（已提交条目必须永久存在于所有未来 leader）。解决办法是：leader 上任后，靠**复制一条自己当前任期的新条目**（哪怕是空操作）到多数派，凭这条新条目的提交，"顺带"把它前面的旧条目一并安全提交。记住这条"只用当前任期条目锚定提交"的规则，是理解 Raft 为什么安全的关键一环。

### 4.5.4 选举限制：保证 leader 拥有全部已提交条目

提交规则要成立，还需保证**新选出的 leader 一定包含所有已提交的条目**（否则新 leader 会用缺胳膊少腿的日志覆盖别人，抹掉已提交内容）。Raft 用一条**投票限制**做到这点：

```
Candidate 的日志必须"至少和投票者一样新（up-to-date）"，投票者才投票。
"谁更新"的比较：先比最后一条日志的 term，term 大者更新；term 相同则 index 大（更长）者更新。
```

给初学者的推理链：一条已提交的条目必然在某个多数派上。而当选需要另一个多数派的票。两个多数派必相交（quorum 交集又一次登场），那个公共节点持有该已提交条目；投票限制保证它只会投给"日志不比自己旧"的候选人——于是当选者的日志必然也含有该条目。层层保证下，**已提交条目永不丢失**，这就是 Raft 的 Leader Completeness / State Machine Safety。

把 4.5 串起来看：日志匹配（4.5.2）+ 只提交当前任期（4.5.3）+ 选举限制（4.5.4）三条环环相扣，共同保证"一旦一条命令被提交并应用到状态机，所有节点在同一 index 上应用的都是它、且永不反悔"——这正是复制状态机（大主题3）对共识层提出的全部要求。

## 4.6 规避 FLP 以保活性

### 4.6.1 FLP 不能被推翻，只能被"绕过"

先立一个总纲：**没有任何实用协议真的推翻了 FLP**。FLP 是数学定理，在其假设（纯异步 + 确定性 + 保证终止）下永远成立。实用协议做的是**改变假设**，让 FLP 的前提不再完全满足，从而在"新假设"下重新获得活性——这叫"规避（circumvent）"而非"打破（break）"。所有手段可归为三类：**加随机、加时序假设（故障检测/部分同步）、加稳定领导者**。它们都不碰 safety（safety 靠 quorum 交集，与时序无关，4.3.3/4.5.4），只用来把 termination 从"确定性保证"松成"概率/条件性保证"。

### 4.6.2 随机化：把"保证终止"换成"概率 1 终止"

第一条路是往算法里掺**随机**，破坏 FLP 对"确定性"的要求。FLP 只约束确定性算法；随机化算法（如 Ben-Or 共识，或 Raft 的随机化选举超时 4.4.3）可以做到"**以概率 1 终止**"——不再是"每条执行都终止"，而是"不终止的那些执行总概率为 0"。

给初学者的直觉：FLP 的对手靠"精准预测算法下一步、卡在关键消息前"制造无限拖延。一旦算法掷骰子，对手无法预测，也就无法始终卡在要害上；每一轮系统都有正的概率跳出僵局，无限轮下去几乎必然跳出。Raft 就是最轻量的例子：随机化选举超时让 split vote 每轮都有大概率被打破，期望极少轮内选出 leader。

### 4.6.3 故障检测器与部分同步：加回一点时序假设

第二条路是承认现实网络不是纯异步，而是**部分同步**（大主题1：延迟上界存在但未知，或存在全局稳定时间 GST 之后网络转好）。等价地，可给系统装一个**故障检测器**（大主题1.5：completeness + accuracy）。Chandra & Toueg 的经典结果指出：一个满足弱完备性 + 最终弱准确性的故障检测器（记作 ◇W），足以在崩溃-停止异步系统里解出共识——它恰好是解共识所需的最弱故障检测器。

给初学者的直觉与纠偏：**超时是穷人版故障检测器**。纯异步下超时什么也不能证明（慢 vs 死不可分辨，大主题1.1），但如果假设"网络最终会稳定下来、届时超时不再误判"，超时就能最终正确地识别崩溃节点，共识随之能推进。要点是这份准确性只需**最终（eventually）**成立——GST 之前爱怎么误判都行（只伤 liveness），GST 之后不再误判即可选出稳定 leader 并终止。这与 FLP 不矛盾：FLP 的世界里没有任何时序保证，而这里额外假设了"最终变好"。

### 4.6.4 稳定领导者：把活锁收敛到"选一个人说话"

第三条路是**选出并维持一个稳定的领导者**，由它独家发起提案/追加日志，从源头消灭竞争。Paxos 的 dueling proposers 活锁（4.3.4）、Raft 的 split vote（4.4.2），本质都是"多人抢着推进"导致的互相作废；只要"同一时刻只有一个人说话"，推进就一路畅通。

```
无 leader / 多 leader 竞争 ⇒ 互相抢占、活锁（liveness 差）
稳定单 leader（网络稳定期）⇒ 提案/复制一次成功，快速终止
```

给初学者的收束：这三条路在真实系统里是**叠加使用**的。Raft = 稳定领导者（4.6.4）+ 随机化超时快速选出并稳住这个领导者（4.6.2）+ 隐含部分同步假设（4.6.3，心跳/超时在网络稳定期才可靠）。Multi-Paxos 同理靠 distinguished proposer + 超时重选。它们共同的姿态始终是那句话——**safety 在任何网络下都不破（quorum 交集撑着），liveness 只在网络进入并保持稳定期时才保证**。这既是对 FLP 的尊重，也是它给出的唯一可行工程答案，把大主题4 的三套机制（不可能性 → Paxos → Raft）收拢成一条完整逻辑。
