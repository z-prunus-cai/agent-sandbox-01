## 6.1 CAP 定理精确表述

### 6.1.1 三个属性各自的精确定义

CAP 里的三个字母不是三个模糊的"好性质"，Gilbert & Lynch 2002 给了它们各自**可证明**的精确定义，读懂定理必须先钉死这三条。

一致性 C 指的是**原子一致（atomic）/ 线性一致（linearizable）**，即存在一个对所有操作的全序，使每个操作看起来都在某个单一瞬间完成——等价于"整个分布式共享内存表现得像跑在单个节点上、一次只处理一个操作"。

```
Consistency (atomic/linearizable)：存在对所有操作的全序，每个操作看似在单一时刻原子生效；系统行为等同于"单节点、一次一操作"
```

可用性 A 的定义是：**每个被非故障节点收到的请求都必须产生一个响应**——也就是算法必须最终终止。

```
Availability：every request received by a non-failing node must result in a response（每个到达非故障节点的请求都必须得到应答，即算法最终终止）
```

分区容忍 P 的定义是：**允许网络丢失从一个节点发往另一个节点的任意多条消息**；当网络被分区时，从一个分块发往另一个分块的所有消息全部丢失。

```
Partition tolerance：网络被允许丢失任意多条节点间消息；分区 = 两分块之间的消息全部丢失（任意消息丢失都可建模成一次瞬时分区）
```

这三条定义要一个字一个字读，因为后面所有误读（§6.2）都源自把它们读松了。给初学者的直觉：C 是"读永远看得到最新写、像只有一台机器"；A 是"只要机器没死，它一定回你话，哪怕回得慢"；P 是"网络会断，消息会全丢，系统得在这种前提下工作"。特别注意 A 的定义**很弱**——它不限定多快回，允许无限久的计算；但一旦叠加 P 的要求（消息可全丢也得回），它又变得**很强**：哪怕这个节点被单独隔离、和其他所有节点都断了，它收到请求也必须自己给出一个（原子的）响应。这个"被隔离也得独立应答"正是 §6.1.2 冲突的火药桶。

### 6.1.2 定理主结果与推论（异步网络模型）

在**异步网络模型**（没有时钟，节点只能靠收到的消息和本地计算做决定）下，Gilbert & Lynch 证明了 CAP 的核心不可能性——这就是 Theorem 1。

```
Theorem 1：在异步网络模型中，不可能实现一个读写数据对象，在所有公平执行（含消息丢失的执行）中同时保证：
  • Availability（可用）
  • Atomic consistency（原子一致）
```

注意定理的表述里**只出现了 A 和 C 两个属性**——P（消息可任意丢失）已经内建进了"在所有公平执行、包括消息丢失的执行中"这句限定里。换句话说，P 不是与 A、C 并列被"选"的第三项，而是"网络会丢消息"这个**既定前提**；在这个前提下，A 与 C 不能同时保证。这正是 §6.2.2 要澄清的关键。

它还有一个更强的推论，说明就算你只在"没有消息丢失时"要求一致，也做不到：

```
Corollary 1.1：异步模型中，不可能实现一个读写数据对象同时保证：
  • Availability，在所有公平执行中；
  • Atomic consistency，仅在"没有消息丢失"的公平执行中。
```

推论 1.1 的道理是：异步模型里节点**无法区分**"消息丢了"和"消息只是被延迟了"。所以如果存在一个算法能在"无丢包"执行里保证原子一致，它在"有丢包"执行里也没法察觉区别、只能照样应答，于是就把不一致带进来了——这会违反 Theorem 1。给初学者：Theorem 1 说"分区期间 A 和 C 不能兼得"，推论 1.1 进一步说"你甚至不能只在网络好的时候偷偷保一致、坏的时候放开"，因为异步节点根本分不清网络好没好。

### 6.1.3 证明直觉：分区两分块的不可区分性论证

Theorem 1 的证明只用一招——**不可区分性（indistinguishability）论证**，值得单独讲清，因为它就是 CAP 全部张力的来源。

把网络切成两个非空、不相交的分块 G1 和 G2，并假设 G1 与 G2 之间的消息全部丢失（即它们被分区）。构造过程如下：

```
α1：只在 G1 发生一次写（把值从初始 v0 改成别的），由 A 保证这次写完成并返回。
α2：只在 G2 发生一次读，由 A 保证这次读返回；因为 G2 没看到任何写，它只能返回初始值 v0。
α ：把 α1 接在 α2 前面拼成一个执行——写先完成、读后开始。
```

这里的关键是，对 G2 里的节点来说，α 和 α2 **完全无法区分**，因为 G1→G2 的消息全丢了，G2 根本不知道 G1 发生过那次写。所以在 α 里，那个"其实发生在写之后"的读，仍然只能返回 v0（旧值）。但按实时顺序，读明明在写完成**之后**才开始——读却没读到写，这就**违反了原子一致**。矛盾，故满足 A + P 的算法不可能同时满足 C。

一个直观的说法是，两块被隔离，G1 收了写、G2 一无所知。此刻有人去 G2 读——G2 面临二选一：要么诚实回一个它手上的旧值（保住了 A：它回话了；但破坏了 C：旧值不是最新的），要么拒绝回话等到能联系上 G1（保住了 C：不吐旧值；但破坏了 A：它不回话了）。它没有第三条路，因为它压根不知道 G1 那边发生了什么。**这个"被隔离的节点无从得知对面发生了什么、又必须马上决定"的窘境，就是 CAP 不可能性的全部内核。** Theorem 2（§6.1.4）用几乎一样的构造，只是在部分同步模型里插入一段"足够长的等待"来保证写先于读完成。

### 6.1.4 部分同步模型：结果仍成立，但留了一道缝

真实网络不是纯异步的——机器有时钟。Gilbert & Lynch 于是考察**部分同步模型**：每个节点都有一个时钟，所有时钟以相同速率前进（但彼此不同步、读数可不同，相当于本地计时器），且每条消息要么在已知时间 tmsg 内送达、要么就是丢了。

在这个更强的模型里，核心不可能性**依然成立**：

```
Theorem 2：在部分同步网络模型中，仍不可能实现一个读写数据对象，在所有执行（含消息丢失的执行）中同时保证 Availability 与 Atomic consistency。
```

但这里出现了和异步模型不同的一道缝：**推论 1.1 的类比在部分同步模型里不成立**。因为推论 1.1 的证明依赖"节点分不清消息丢了还是延迟了"，而现在节点有计时器——等超过 2·tmsg + tlocal 还没回应，它就能**判定消息丢了（超时）**。于是存在这样的算法：网络正常（所有消息按时送达、无分区）时返回原子一致的数据；一旦超时判定分区，就退而返回本地已知的最佳值（可能陈旧、可能违反一致），但至少保住了可用与终止。

落到实务上，这正是现实系统的活法。CAP 不是"你永远只能有两个字母"，而是"**当且仅当分区真的发生时**，你必须在 C 和 A 里选一个放弃"；平时网络好、没分区，C 和 A 可以同时拥有（§6.2.5）。部分同步模型 + 超时，就是把"放弃"精确地限制在"检测到分区那段时间"里的工程手段——这也是通往 §6.3 PACELC 的桥：既然平时能同时保 C 和 A，那平时到底还有没有别的取舍？有，就是延迟。

### 6.1.5 分区期间的取舍不变式

把前面几节压缩成一条可以随身带走的不变式：在一个必须容忍分区的分布式读写系统里，

```
分区期间不变式：Partition 发生 ⇒ (线性一致 C) 与 (可用 A) 至多得其一，不可兼得。
无分区时：C 与 A 可同时满足（此时 CAP 不构成约束）。
```

这条不变式是 §6.2 全部误读辨析的判据、也是 §6.4 归类方法的第一根轴（"分区时你选 A 还是 C"）。

请把 CAP 记成一句**条件句**而不是"三选二"——"IF 分区，THEN C 与 A 二选一"。它没说无分区时也要选，也没说 P 是你去选的东西。Brewer 本人在 2012 年（§6.2.1）特意回来纠正："2 of 3"这个流行说法从一开始就是误导。抓住这条条件句，下面每一条误读你都能自己判对错。

## 6.2 CAP 常见误读辨析

### 6.2.1 「三选二（2 of 3）」是被误导的通俗表述

流传最广的说法是"CAP 三者只能选两个（C+A、C+P、A+P 三选一）"。这句话被 CAP 提出者 **Eric Brewer 本人在 2012 年的 "CAP Twelve Years Later" 里明确称为误导**："'2 of 3' 这个表述一直是有误导性的（misleading）。"

它的误导之处在于，CAP 的真正命题是一句**条件句**——只有当分区发生时，才被迫在 C 与 A 之间二选一（§6.1.5）。分区在多数系统里是**罕见事件**，绝大部分时间根本没有分区，此时 C 和 A 可以同时拥有，谈"放弃其中一个"没有意义。把它讲成"你要在三个属性里永久划掉一个"，就把一个"分区期间的局部取舍"夸大成了"全局的架构判决"。

正确的一句话是"**分区时，C 与 A 二选一**"，不是"C、A、P 三选二"。后面 6.2.2–6.2.7 的每一条误读，本质上都是"三选二"这个错误框架派生出来的。记住 Brewer 自己都来纠正了，就别再背"三选二"。

### 6.2.2 「牺牲 P 换 C+A」不成立——P 不是可选项

"三选二"最有害的派生结论是"我可以牺牲 P、选择 C+A"。这在一个会发生网络分区的分布式系统里**不成立**。

原因在 §6.1.1 已埋下：在 Gilbert & Lynch 的定理里，P（网络可丢任意消息）不是一个与 A、C 并列、由你去"选"的属性，而是分布式网络的**客观现实前提**。网络分区是会真实发生的物理事件（网线断、交换机挂、机房间链路抖动），你不能通过"设计选择"让它不发生。你能选择的只是：当它发生时，你的系统表现成 CP（牺牲 A，拒绝服务/阻塞以保一致）还是 AP（牺牲 C，继续应答但可能返回陈旧/冲突数据）。

```
可选的是：分区发生时 → 表现为 CP（弃 A 保 C）或 AP（弃 C 保 A）
不可选的是：让分区不发生（P 是前提，不是旋钮）
```

一个易错点是，所谓"CA 系统"（声称同时要 C 和 A、不管 P）在一个真正可能分区的网络里是不存在的——一旦分区真的来了，它照样得在 C 和 A 里塌向一边。单机数据库或不跨网络的系统可以说"没有分区问题"，但那是因为它压根不是"必须容忍分区的分布式系统"，而不是它"选择了放弃 P"。把"CA"当成一个和 CP/AP 平起平坐的可选类别，是 §6.2.7 要专门收尾的误读。

### 6.2.3 C 特指线性一致，不是 ACID 的 C，也不是最终一致

CAP 里的 C 有非常窄的含义：**线性一致 / 原子一致**（§6.1.1）。初学者极易把它和另外两个"C"混淆。

它**不是** ACID 里的 C（Consistency）。ACID 的 C 指"事务不破坏数据库的完整性约束（如外键、余额非负）"，是关于事务对不变式的保持；CAP 的 C 是关于**单个对象的读写在多副本间表现得像单副本**，两者是完全不同的东西。Gilbert & Lynch 原文特意脚注澄清：CAP 的原子一致"包含了数据库里 Atomic 和 Consistent 两个概念，但含义不同于 ACID 的任何一个字母"。

它也**不是**最终一致（eventual consistency）。最终一致只承诺"如果停止写入，副本们最终会收敛到同一值"，它对"任一时刻读到的是不是最新写"不作保证——而线性一致恰恰要求每次读都反映此前已完成的写。所以最终一致是一种**弱一致**，是很多 AP 系统在分区时（甚至平时）退守的模型，而不是 CAP 里那个被迫放弃的 C。

看到 CAP 谈 C，脑子里要立刻替换成"线性一致——读永远看得到最新写、系统像一台机器"。如果一句话里"C"其实指的是"不违反业务约束"或"迟早会一致"，那它谈的就不是 CAP 的 C。这条误读辨析直接依赖大主题5 对一致性谱系的界定。

### 6.2.4 A 的精确含义：不是"看起来还能用"

CAP 的 A 也常被读松成"系统响应挺快""大部分请求能成功"。其精确定义（§6.1.1）是：**每个被非故障节点收到的请求都必须终止并返回响应**——注意它对"多快返回"没有任何限制，允许任意长的计算时间。

这带来两个初学者常踩的点。其一，A 是个"全有或全无"的形式化属性：只要存在某个非故障节点收了请求却不返回（比如为了等其他副本确认而无限阻塞），就算破坏了 A，哪怕系统整体看起来还挺忙。其二，反过来，"响应很慢"在 CAP 的字面定义里**不算**违反 A（只要最终返回）——但这恰恰暴露了 CAP 的粗糙：现实中一个要等 30 秒才返回的系统和挂了没区别。这个"CAP 只看返不返回、不看多快"的盲区，正是 §6.3 PACELC 要补的：把"延迟"作为一个独立维度拎出来。

简言之，CAP 的 A = "非故障节点收到请求就一定会回话（终止）"，是个理论上的终止性概念；它不度量延迟、不度量吞吐、也不等于"高可用 SLA"里那个百分比。别把工程上的"可用性 99.99%"直接等同于 CAP 的 A。

### 6.2.5 CAP 只在分区期间才逼你选择

再强调一遍这条最常被忽略的限定，因为它是把 CAP 从"架构判决"降回"局部取舍"的关键：**没有分区时，C 和 A 可以同时满足，CAP 不构成任何约束。**

Theorem 2 的部分同步解法（§6.1.4）已经证明了这点——网络正常、消息都按时送达时，一个中心化协议既能返回原子一致的数据、又能对每个请求终止应答。只有当超时判定"分区来了"，系统才被迫在"继续用本地陈旧值应答（AP）"和"拒绝应答等恢复（CP）"间选。Brewer 2012 把这讲成一个运行时的三步循环：检测到分区 → 进入显式的分区模式（限制某些操作）→ 分区恢复后做补偿/合并。

落到实务上，设计系统时你不是在开工那天"永久划掉 C 或 A"，而是在设计"**当分区发生的那几秒/几分钟里，这个操作该偏向一致还是偏向可用**"。同一个系统里不同操作甚至可以有不同选择（购物车加购偏 A、账户扣款偏 C）。把 CAP 当条件句用，才能做出这种细粒度决策；当成"三选二"就只能一刀切。

### 6.2.6 CAP 与可扩展性、与延迟无关

一个常见的越界误读是"CAP 教你怎么权衡扩展性/性能"。CAP 的定理本身**只谈网络分区这一种故障下 C 与 A 的取舍**，它不谈吞吐、不谈水平扩展、也不直接谈延迟。

把 CAP 当扩展性理论用是张冠李戴：分区是"消息全丢"这种故障场景，扩展性是"加机器能不能线性提升处理能力"，两者不是一个问题。至于延迟——CAP 的 A 定义压根不看响应快慢（§6.2.4），所以 CAP **无法**表达"为了强一致而牺牲了平时的延迟"这种极常见的现实取舍。这个空白正是 Abadi 提出 PACELC 的直接动机（§6.3）：他指出"一致性 vs 延迟"的取舍对真实分布式数据库的影响，其实比 CAP 描述的"一致性 vs 可用性"更日常、更持续。

一句话，CAP 回答的是"网断了怎么办"，不回答"怎么跑得更快、扩得更大"。看到有人用 CAP 论证 sharding 或性能调优，多半是把框架用错了地方。

### 6.2.7 「CA 系统」这一类别的问题

顺着 §6.2.2，专门收尾"CA"这个标签。在经典的"三选二"文氏图里，CA（要 C 和 A、不要 P）被画成和 CP、AP 并列的第三类，很多入门材料还把单机关系数据库归到这里。这个类别是有问题的。

问题在于，对一个**真正跨网络、可能分区**的分布式系统，"CA"是空类——分区一旦发生它必然塌向 CP 或 AP，不可能停在"既要 C 又要 A"。而那些被归为"CA"的例子（单机数据库、单机房内不考虑分区的系统），本质是"**这个系统不面对分区问题**"，也就不在 CAP 讨论的范畴内，而不是它"在 CAP 三者里选了 CA"。Brewer 2012 也指出，把 CA 与 CP 并列会误导人——因为无分区时 CA 和 CP 的行为完全一样（都能同时给 C 和 A），它们的区别**只在分区发生时才显现**，所以真正有意义的区分是"分区时选 A 还是选 C"，即 AP vs CP。

别把 CA 当成一个可选的架构类别。要么你的系统不跨会分区的网络（那就别用 CAP 谈它），要么它就得在分区时做 AP/CP 的选择。这也是 §6.4 归类方法里我们只沿"分区时 A 还是 C"这根轴分类、而不设"CA 档"的原因。

#### 来源与时效
- 锚点（承重）：Brewer, "CAP Twelve Years Later: How the 'Rules' Have Changed", IEEE Computer 45(2):23–29, 2012 —— "2 of 3 表述具误导性"、"分区罕见故只在分区期间才需二选一"、"CA 与 CP 只在分区时才有区别"、运行时"检测分区→分区模式→恢复补偿"三步（核实 2026-07-30）。
- 锚点（承重）：Gilbert & Lynch 2002 §2.3（P 是"网络被允许丢任意消息"这一前提，非并列可选项）与 §2.1 脚注（CAP 的 C 不同于 ACID 的 C）—— 支撑 §6.2.2、§6.2.3（核实 2026-07-30）。
- 交叉印证：DDIA 2E ch9（"CAP 常被误述为 pick 2 of 3、实则只在分区时 C/A 二选一"、"CA 不是有意义的类别"、CAP 的 C 特指线性一致、CAP 只覆盖网络分区一种故障且不谈延迟/扩展性）；Abadi 2012（CAP 忽略了无分区时的延迟取舍，支撑 §6.2.4/§6.2.6，详见 §6.3）。
- 冲突/分歧显式记：**通俗"三选二"表述 vs 学术精确表述**是本大主题最主要的分歧点——大量二手入门材料（含早期文氏图）沿用"C、A、P 三选二 / 可选 CA"的讲法；一手来源（Gilbert & Lynch 2002 的条件式定理、Brewer 2012 的本人纠正、DDIA 2E）一致否定该讲法，主张"P 是前提、仅分区期间 C 与 A 二选一、CA 非有意义类别"。本报告以一手为准，通俗表述仅作为"需要纠正的误读"记录，不采纳为结论。
- 分账：各具体系统在分区时到底表现 AP 还是 CP 的实例判定，归 §6.4 与 L6-05。

## 6.3 PACELC 补充维度

### 6.3.1 CAP 的盲区：无分区时也有取舍

CAP 只回答了"有分区时怎么办"，却对"没有分区时（也就是系统绝大部分运行时间）该怎样"保持沉默——好像平时就没有任何取舍似的。Abadi 2012 指出这是 CAP 的一大盲区，也是"CAP is only part of the story（CAP 只是故事的一部分）"这个副标题的由来。

盲区具体在哪，得从复制说起——为了容错，分布式数据库几乎都会**复制数据**（一份数据存多个副本）。一旦有多副本，每次写就面临一个平时就存在、与分区无关的选择——是**同步**等所有（或多数）副本都确认了才算写成功（读到的一定是最新值，强一致，但每次写都要跨网络等一圈，**延迟高**），还是**异步**地写完主副本就返回、后台再慢慢传给其他副本（**延迟低**，但此刻别的副本还是旧值，读可能读到过时数据，弱一致）。

简单说，这个"同步复制慢但一致 / 异步复制快但可能不一致"的取舍，在网络完全正常、根本没有分区时就天天在发生。CAP 因为 A 的定义不看延迟（§6.2.4），完全表达不了它。PACELC 就是来补这半张图的。

### 6.3.2 PACELC 的精确表述

Abadi 把 CAP 改写成一个更完整的框架 **PACELC**（读作 "pass-elk"）：

```
PACELC：if there is a partition (P), how does the system trade off availability and consistency (A and C);
        else (E), when the system is running normally in the absence of partitions,
        how does the system trade off latency (L) and consistency (C)?
```

翻成中文就是两句话——**如果发生分区（P），系统如何在可用性 A 与一致性 C 之间取舍；否则（E，else，即无分区正常运行时），系统如何在延迟 L 与一致性 C 之间取舍。**

它把"CAP 那半"原封不动收进了 P 段（分区时 A vs C，就是 §6.1 的结论），再补上了 CAP 缺的 E 段（无分区时 L vs C）。给初学者记忆法：PACELC 就是 "**P**→**A**/**C**，**E**（lse）→**L**/**C**"——分区时选 A 还是 C，平时选 L 还是 C。注意两段共用了 C，因为一致性在两种情形里都是那个被拿来交换的东西：分区时拿它换可用，平时拿它换低延迟。

### 6.3.3 EL/EC 的取舍来源：同步复制 vs 异步复制

E 段（无分区时）里 L 与 C 的取舍，其物理根源就是 §6.3.1 说的复制时机，落到 §大主题3 的 Quorum 框架上尤其清楚。

```
强一致（偏 EC）：写等到足够多副本确认（如 W + R > N 的 quorum 交集），读一定命中最新写 —— 每次操作多一轮跨节点往返，延迟↑
低延迟（偏 EL）：写完本地/主副本即返回，副本异步追平；读可能落在还没追平的副本上 —— 少等一圈，延迟↓，但可能读到陈旧值
```

举个最小例子，三副本、要求"写要 2 个副本确认、读要问 2 个副本"（W=2, R=2, N=3，W+R>N），那么读的 2 个里必然至少 1 个见过最新写——强一致，但每次读写都要等两个节点的网络往返（EC，延迟高）。若改成"写 1 个就返回、读只问最近的 1 个"（W=1, R=1），读写都快（EL，低延迟），但你问到的那个副本可能还没收到刚才的写，读到旧值。**同一套 quorum 旋钮，往一致拧就偏 EC、往延迟拧就偏 EL**——这就是 §6.4 归类时看的第二根轴。

### 6.3.4 为什么 ELC 只适用于复制数据的系统

Abadi 特别加了一句限定：**延迟/一致取舍（ELC，即 E 段）只适用于会复制数据的系统**；不复制数据的系统就没有这一段取舍。

道理很直接——L 与 C 的矛盾完全来自"多副本要不要等彼此同步"（§6.3.3）。如果数据只有一份、不复制，那读写都打到那一份上，不存在"等副本"的问题，也就无所谓"为低延迟牺牲一致"。当然，不复制的系统也就没有容错，通常不是分布式数据库会做的选择——所以现实里 E 段几乎总是适用的。

可以把这句限定记成"**没有副本，就没有 EL/EC 之分**"。它也提醒你 PACELC 的 E 段和 CAP 一样，本质是**复制**带来的代价——复制给了你容错和可用，但要么让你在分区时选边（P 段），要么让你平时为一致付延迟（E 段）。

### 6.3.5 PACELC 与 CAP 的关系

PACELC 不是推翻 CAP，而是**包含并扩展**了 CAP：它的 P 段（分区时 A vs C）就是 CAP 的严格重述，E 段是 CAP 完全没覆盖的新维度。

```
PACELC ⊃ CAP：
  P 段（有分区）= CAP 命题本身（分区时 A/C 二选一）
  E 段（无分区）= CAP 的盲区补全（平时 L/C 二选一，仅复制系统适用）
```

打个比方，CAP 是一张只画了"暴风雨天（分区）该怎么开车"的图，PACELC 补上了"晴天（无分区）也得在开快和开稳之间选"的另一半。因为分区是罕见事件、晴天才是常态，很多人会说**E 段的取舍其实比 P 段更影响日常体验**（Abadi 原话大意：一致性 vs 延迟的取舍对现实 DDBS 的影响比 CAP 描述的更直接）。这也是为什么给系统贴标签时，光说 AP/CP 不够，还要补上 EL/EC——正是 §6.4 的四象限。

#### 来源与时效
- 锚点（承重）：Abadi, "Consistency Tradeoffs in Modern Distributed Database System Design: CAP is Only Part of the Story", IEEE Computer 45(2):37–42, 2012 —— PACELC 精确表述（"if there is a partition (P)… else (E)… latency (L) and consistency (C)"逐字）、"ELC 仅适用于复制数据的系统"限定、"一致性/延迟取舍比 CAP 更直接影响现实 DDBS"的论点（核实 2026-07-30，DOI 10.1109/MC.2012.33；PACELC 原始表述亦见 Abadi 2010 博客 dbmsmusings，为期刊版前身）。
- 交叉印证：DDIA 2E ch9（同步 vs 异步复制的延迟/一致取舍、CAP 不谈延迟）；大主题3（读写 Quorum 与 W+R>N 交集原理，本节据其解释 EL/EC 的旋钮，不重讲）；HandWiki / 多来源 PACELC 条目（PA/EL、PC/EC 等标签口径，用于交叉印证表述一致性）。
- 分账：Quorum 交集的证明与 N/R/W 全部配置分析归大主题3；具体系统如何实现可调一致（Cassandra 的 tunable consistency、Dynamo 的 sloppy quorum）归 L6-05·C1，本节只把它当"L/C 旋钮"引用。
- 无冲突项：PACELC 的两段结构与"ELC 仅复制系统适用"在 Abadi 期刊版、其 2010 博客、DDIA 与各百科条目间表述一致。

## 6.4 系统按 CAP/PACELC 归类

### 6.4.1 归类方法：两个正交的问句

给一个具体分布式数据系统贴 CAP/PACELC 标签，方法就是分别回答**两个彼此正交的问句**——它们对应 §6.1.5 和 §6.3 提炼出的两根轴。

```
轴一（P 段，来自 CAP）：分区发生时，系统偏向可用还是一致？ → A（保可用、弃一致）或 C（保一致、弃可用）
轴二（E 段，来自 PACELC）：无分区正常运行时，系统偏向低延迟还是强一致？ → L（保延迟、弃一致）或 C（保一致、付延迟）
```

把两个答案拼起来就是这个系统的 PACELC 标签。给初学者：不要试图给系统贴"CA/CP/AP"这种单轴老标签（§6.2.7 已说明 CA 是空类），而是用 PACELC 的两问句各答一次，得到一个两段的标签，信息量更全。

### 6.4.2 四象限标签：PA/EL、PC/EC、PC/EL、PA/EC

两根轴各两个取值，组合出四类标签。Abadi 用它给系统的**默认配置**归类，示例如下（这里只用来演示分类方法，具体系统的内部机制归 L6-05，不展开）：

```
PA/EL：分区时保可用弃一致，平时为低延迟弃一致 —— 默认配置的 Dynamo、Cassandra、Riak（一致往两边都让）
PC/EC：分区时保一致弃可用，平时也为一致付延迟 —— 完全 ACID 的系统，如 VoltDB/H-Store、Megastore（两边都死保一致）
PC/EL：分区时保一致（弃可用），但平时为低延迟弃一致 —— PNUTS（两段选择不一致，最能体现两轴独立）
PA/EC：分区时保可用弃一致，平时却为一致付延迟 —— 少见，个别材料把某些配置的 MongoDB 归此（待核，随版本变）
```

读法上，标签前半（PA/PC）读"分区时"，后半（EL/EC）读"平时"。最值得玩味的是 **PC/EL 的 PNUTS**——它平时为了低延迟愿意读到稍旧的数据（EL），可一旦真分区了反而选择保一致、宁可牺牲可用（PC）。这个"平时松、分区时紧"的组合恰好证明了两根轴是**独立**的：不能从"平时选了 L"推出"分区时就选 A"。若两轴不独立，PACELC 就没必要写成两段了。

### 6.4.3 归类靠什么判断：默认配置与可调旋钮

判定一个系统的标签，看两处：它的**默认行为**，以及它暴露的**可调旋钮**。

很多系统的一致性是**可调的**（tunable）——通过调 §6.3.3 的 quorum 参数（W/R/N）或一致性级别，同一个系统能在 EL 和 EC 之间滑动。比如 Cassandra 默认偏 EL（低一致级别、低延迟），但把读写一致性级别调到 quorum 就能表现得更像 EC。所以严格说，PACELC 标签描述的是**某个配置下的倾向**，Abadi 归类时明确取的是"**default version（默认版本/配置）**"。

```
判定要点：
  · 分区时默认是拒绝服务/阻塞（→ PC）还是继续应答可能陈旧的数据（→ PA）
  · 平时默认是等 quorum/多数确认（→ EC，延迟换一致）还是本地/单副本即返回（→ EL，一致换延迟）
  · 记录旋钮范围：可调一致的系统给"默认标签 + 可滑动区间"，而非一个死标签
```

贴标签前先问一句"你说的是它哪个配置？"同一个数据库不同一致性级别可以落在不同象限，脱离配置谈标签容易吵架。

### 6.4.4 归类的陷阱：标签是倾向不是铁律，且随版本演进

用这套方法时有两个初学者高频陷阱。

其一，**标签是"默认倾向"而非"绝对属性"**。除了 §6.4.3 的可调一致，很多系统在不同操作、不同一致性级别下行为不同；把一个系统一句话钉死成"它就是 AP"往往过简。Brewer 2012 也强调，AP/CP 是运行时对**具体操作**的选择，同一系统可以对不同数据/操作做不同选择。

其二，**标签随实现版本演进（⚙演进快）**。系统的默认一致性、分区行为会随大版本改变（历史上 MongoDB 的默认写关注点、Cassandra 的默认一致性级别都调整过），所以任何"某系统 = 某标签"的断言都应**绑版本 + 核实日期**，不能当永久事实背。本报告对个别系统标签（尤其 §6.4.2 里 PA/EC 的 MongoDB 归属）标"待核、随版本变"，不作硬结论。

把 PACELC 标签当作"这个系统在这个版本、这个配置下的取舍**倾向**"来用，是很好的沟通和选型工具；当成"刻在石头上的分类"就会被现实打脸。

### 6.4.5 本课边界：给方法，实例机制落 L6-05

最后明确边界。本大主题交付的是**分类方法**（两根轴、两个问句、四象限、判定要点与陷阱），以及为演示方法而引用的轻量示例。至于每个系统**为什么这样选、内部怎么把这个选择实现出来**——Dynamo 如何用 sloppy quorum 与 hinted handoff 在分区时保可用、如何用向量时钟做冲突检测（L6-05·C1），Spanner 如何用 TrueTime + commit-wait 造外部一致从而在 PC/EC 象限里仍拿到可用性（L6-05·C3）——都属于系统落地专题，本报告不展开。

读完本节，你应该能拿起任意一个分布式数据库、用两个问句给它贴出 PACELC 标签、并知道要绑配置和版本；至于"它是怎么做到的"，那是 L6-05 讲"如何做得快且能扩展"时的内容。分类方法（本课）与系统机制（L6-05）分账，正是为了不在两处重复、也不越界。

#### 来源与时效
- 锚点（承重）：Abadi 2012 IEEE Computer 45(2) —— PACELC 四象限归类方法与"取 default version 归类"的口径；示例标签 PA/EL（Dynamo、Cassandra、Riak 默认）、PC/EC（VoltDB/H-Store、Megastore 等完全 ACID 系统）、PC/EL（PNUTS）均取自本文的归类论述（核实 2026-07-30）。
- 锚点（承重）：Brewer 2012 IEEE Computer 45(2) —— "AP/CP 是运行时对具体操作的选择、同一系统可对不同操作不同选择"支撑 §6.4.4 陷阱一（核实 2026-07-30）。
- 交叉印证：DDIA 2E ch9（可调一致 / quorum 与 CAP-PACELC 标签的关系）；大主题3（W/R/N quorum 旋钮，§6.4.3 判定要点据此）；多来源 PACELC 条目（HandWiki 等）用于交叉印证四象限标签口径。
- 演进/待核项：**⚙演进快** —— 具体系统的默认一致性与分区行为随大版本改变，任何"系统=标签"断言须绑版本+核实日期。§6.4.2 中 **PA/EC 的 MongoDB 归属标「待核·随版本变」**，二手材料口径不一，本报告不作硬结论，仅作演示第四象限存在性之用。
- 分账：各系统"为何这样选、机制如何实现"（Dynamo sloppy quorum/hinted handoff/向量时钟；Spanner TrueTime + commit-wait）归 L6-05·C1/C3，本节不展开。
- 冲突/分歧显式记：单轴老标签"CA/CP/AP"（尤其把系统归入 CA）与 PACELC 双轴标签并存于二手材料；本报告采 PACELC 双轴口径（与 Abadi/Brewer 一手一致），不设 CA 档（理由见 §6.2.7）。
