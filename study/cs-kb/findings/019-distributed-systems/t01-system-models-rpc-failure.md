## 1.1 同步 vs 异步系统模型

### 1.1.1 时序假设：一个模型的三个"表"

一个分布式系统模型，本质上是在回答三个"有没有上界"的问题。第一，**消息延迟**：从发出到送达，有没有一个已知的最大时间上界？第二，**处理速度**：节点执行一步（收消息、算、发消息）花的时间，有没有已知上界？第三，**时钟漂移**：各节点本地时钟相对真实时间的偏移速率，有没有已知上界？把这三者是否有界的不同组合，就得到不同强度的系统模型。

**同步模型**（synchronous model）对三者都假设**有已知上界**：消息在 δ 内必达、节点每步在 φ 内完成、时钟漂移率有界。**异步模型**（asynchronous model）对三者**都不做任何上界假设**：消息可以晚任意久（但最终会到，除非被显式建模为丢失）、节点可以慢任意久、时钟不可用于推断真实时间。两者之间还有一大片**部分同步**（partial synchrony）模型：上界存在但未知，或系统只在某些时段（GST，全局稳定时间之后）才表现同步。

**模型不是描述真实网络长什么样，而是描述"算法被允许假设什么"。** 真实的互联网当然大部分时候消息几毫秒就到，但如果你的算法的**正确性**依赖"消息一定在 100ms 内到"，那一次偶发的网络拥塞就能让它出错。异步模型的价值就在于：在它上面证明正确的算法，无论网络多糟都不会给出错误答案（尽管可能变慢）。

### 1.1.2 时序假设如何决定问题可解性

**同一个问题，在同步模型下可解，在异步模型下可能根本不可解。** 最著名的例子是共识（consensus）——异步模型下即使只有一个节点可能崩溃，也不存在既保证正确又保证一定终止的确定性共识算法（FLP 不可能性，大主题4细讲）；而在同步模型下，共识不但可解，还能容忍拜占庭失败（有节点数下界）。

为什么时序假设有这么大的威力？关键在**"慢"和"死"能不能区分**。

```
异步模型下，一个节点迟迟不回消息，有两种可能：
  (a) 它崩溃了（永远不会回）
  (b) 它只是很慢 / 消息在路上很慢（迟早会回）
异步模型下这两种情况从外部完全无法区分。
```

在同步模型里，因为延迟有已知上界 δ，你只要等超过 δ 还没收到，就能**确定**对方崩溃了——"死"变成可判定的。这一点判定能力，就是同步模型能解更多问题的根本来源。异步模型下你永远无法确定对方是死是活，任何"等够久就当它死了"的做法都可能误判一个只是暂时慢的活节点，而这种误判恰恰是不可能性结果的攻击点。

**同步 = 有闹钟且闹钟可信，超时即真相；异步 = 没有可信闹钟，超时什么也证明不了。** 现实系统（如 Raft、Paxos）几乎都跑在异步/部分同步假设上以保证 safety（永不给错答案），而把超时只用来触发重试/换主等**推进 liveness** 的动作，绝不用超时来下"数据正确性"的结论——这正是把 1.1 的教训用对地方。

### 1.1.3 部分同步：现实系统真正站的地方

**部分同步模型**（Dwork, Lynch & Stockmeyer 1988）是同步与异步之间的折中，两种常见形式：一是上界 δ、φ 确实存在但算法**不知道具体值**；二是系统大部分时间异步，但存在一个未知的**全局稳定时间 GST**，GST 之后消息延迟才被 δ 束住。

它之所以重要，是因为它精准刻画了真实系统的处境：网络平时很好但偶尔会抽风（分区、GC 停顿、拥塞）。在部分同步模型下，设计目标通常是——**无论系统是否处于同步期，safety 永远保持；只在系统进入并保持同步期（GST 之后）时，才保证 liveness（一定有进展）**。Raft、Paxos、PBFT 都是这个路数：坏网络下最多卡住不推进，但绝不给出矛盾的结果。

一个常见误区是把"异步模型"误解为"消息可以永远丢"。标准异步模型里消息**最终会送达**（fair-loss/可靠信道假设，见 1.3），"不可预测的只是延迟，不是是否送达"；真正的"可以永久丢失"是另一层信道假设。区分"延迟无界"与"允许永久丢失"是读懂后续所有结果的前提。

## 1.2 失败模型谱系

### 1.2.1 失败模型：从"最善良"到"最恶毒"的一条假设强度轴

**失败模型**（failure model）规定"一个出故障的节点被允许以什么方式偏离正常行为"。它构成一条按**假设强度递增**（等价于容错难度递增）排列的谱系，经典分类（Cristian、Schneider、Tanenbaum）大致如下：

```
崩溃-停止 (crash-stop / fail-stop)
    ⊂ 崩溃-恢复 (crash-recovery)
        ⊂ 遗漏失败 (omission)
            ⊂ 时序失败 (timing，仅同步模型有意义)
                ⊂ 拜占庭失败 (Byzantine / arbitrary)
```

越往下，故障节点被允许的"坏行为"越多，容错算法就越难写、需要的正常节点越多。这里"假设强度递增"要理解对方向：**能容忍拜占庭失败的算法，假设最弱（对故障节点几乎不做任何善意假设），因此最强壮但最贵**；只容忍崩溃-停止的算法，假设最强（相信节点要么完全正常要么干脆死透、绝不乱来），因此最便宜但最脆弱。

### 1.2.2 逐级看每种失败

**崩溃-停止**（crash-stop / fail-stop）：节点要么完全按协议正常运行，要么在某一刻**彻底停机、之后永不再动**，且（fail-stop 的严格版）停机可被他人检测到。它绝不发错消息、绝不"诈尸"。这是最善良的假设，也是 Paxos/Raft 等主流共识默认的模型。

**崩溃-恢复**（crash-recovery）：节点会崩溃，但**可能重启回来**继续参与。这比 crash-stop 难，因为重启后它可能"忘了"崩溃前的部分状态（除非写了持久化日志），一个刚回来的节点带着过时状态参与协议是很多 bug 的来源——这正是共识算法要求关键状态落盘（persistent state）的原因。

**遗漏失败**（omission）：节点没崩，但会**漏掉**某些动作——发送遗漏（该发的消息没发出/丢在自己网卡）、接收遗漏（该收的没收进来）。它介于崩溃和拜占庭之间：不会发错消息，但会"沉默"。

**时序失败**（timing failure）：仅在同步模型下才有意义，指节点响应太早或太晚、超出了模型承诺的时间界。异步模型里因为本就没有时间界，谈不上时序失败。

**拜占庭失败**（Byzantine / arbitrary failure）：故障节点可以做**任何事**——发送矛盾消息（对 A 说 X、对 B 说 Y）、伪造数据、串通合谋、精准挑最坏时机作恶。名字来自 Lamport, Shostak & Pease「The Byzantine Generals Problem」(1982)。它涵盖了硬件位翻转、软件 bug、乃至真正的恶意攻击（如区块链场景）。

### 1.2.3 假设强度换来的代价：容错下界

不同失败模型下，"要容忍 f 个故障节点，总共需要多少节点 n"的下界不同，这是失败模型最实在的后果：

```
崩溃失败（异步/部分同步共识）：n ≥ 2f + 1   （多数派存活即可，容 f 个崩溃）
拜占庭失败（同步或部分同步 BFT 共识）：n ≥ 3f + 1
```

`2f+1` 的直觉：只要故障节点是"沉默型"，让任意多数派（> n/2）能做决定，两个多数派必然交于至少一个诚实节点，保证一致。`3f+1` 的直觉：拜占庭节点会**主动撒谎**，你不仅要让诚实多数派能推进，还要保证"就算 f 个在说谎、另有 f 个恰好没参与，剩下的诚实节点仍占多数"——多扣一层 f 就来自"分不清谁在撒谎"。

第一个易错点在于，**失败模型是"允许什么"，不是"一定发生什么"。** 选 crash-stop 模型不代表你的机器不会中拜占庭式故障，而是你的算法**在拜占庭故障下不保证正确**——这是一个郑重的假设声明，不是对现实的预测。第二个易错点是把拜占庭等同于恶意，其实拜占庭 ≠ 恶意。位翻转、序列化 bug、配置错误导致节点发出"看似合法但内容错误"的消息，都落进拜占庭范畴，这也是为什么关键基础设施（如某些金融/航天系统）即使没有攻击者也上 BFT。

- Tanenbaum & Van Steen《Distributed Systems》3rd/4th ch8「Fault Tolerance」§8.1（一手教材，核实 2026-07-30 经章节结构）：失败分类（crash/omission/timing/arbitrary=Byzantine）、fail-stop vs fail-silent、故障容错术语。

## 1.3 消息传递语义

### 1.3.1 不可靠信道：丢失、乱序、重复三种"坏"

节点之间靠**信道**（channel）传消息，而底层网络信道天生不完美，主要有三类偏差：**丢失**（loss，消息发了对方没收到）、**乱序**（reorder，先发的后到）、**重复**（duplication，一条消息被送达多次）。分布式算法的第一步，就是明确它假设的信道**提供哪些保证、不提供哪些**，然后自己补上缺的那部分。

一个常用的信道抽象谱系（Cachin/Guerraoui/Rodrigues《Reliable and Secure Distributed Programming》的措辞）：

```
fair-loss links（公平丢失）：可能丢、可能重复，但"若不断重发则最终必有一条送达"，不会凭空捏造消息
    ⇒ 加"重发 + 去重" ⇒ stubborn links（固执链路，最终至少送达一次）
        ⇒ 加"序号 + 去重" ⇒ reliable links / perfect links（可靠链路：恰好一次、不丢不重）
```

**上层的"可靠"不是网络白给的，是用不可靠的底层一层层"造"出来的**——底层只承诺 fair-loss，靠"不停重发"把它抬成"至少一次"，再靠"序号去重"把"至少一次"抬成"恰好一次"。这也预告了 1.4 RPC 交付语义为什么正好是这几档。

### 1.3.2 为什么这三种"坏"必须分开对待

**这三种偏差要用不同手段治，不能一招通吃。**

治**丢失**靠"重发 + 确认（ACK）+ 超时"：发出后等 ACK，超时没等到就重发。但重发本身会引入**重复**（原消息其实到了，只是 ACK 丢了，于是你白重发一次）——所以治丢失的代价往往是制造重复。

治**重复**靠"唯一序号/请求 ID + 接收端去重表"：每条消息带唯一 ID，接收端记下已处理过的 ID，见到重复就丢弃（或返回缓存的旧结果）。

治**乱序**靠"序号 + 接收缓冲重排"：按序号把乱序到达的消息缓存起来、按序交付给上层（TCP 就是这么干的）。


```
客户端发 REQ(id=7, "转账100")
  → 网络丢了 REQ            （丢失）
客户端超时重发 REQ(id=7)     （因治丢失而重发）
  → 这次到了，服务器执行转账
服务器发 REPLY(id=7)
  → 网络又把 REPLY 送达两次   （重复）
客户端靠 id=7 去重，只认第一份
```

要小心别把"信道会丢消息"和"异步模型延迟无界"混为一谈。1.1 的异步模型说的是**延迟不可预测但消息终会到**；本节说的丢失是**消息可能永远不到**。真实系统两者都要面对，但它们是不同的假设维度，处理手段也不同（延迟无界靠"不用超时下正确性结论"应对，永久丢失靠"重发+去重"应对）。

#### 来源与时效
- Cachin, Guerraoui & Rodrigues《Reliable and Secure Distributed Programming》2nd (2011) ch2「Basic Abstractions」§2.4（一手教材）：fair-loss / stubborn / perfect (reliable) links 的抽象层级与实现（重发→去重）。
- Tanenbaum & Van Steen《Distributed Systems》ch4「Communication」+ ch8（一手教材，核实 2026-07-30）：不可靠信道下丢失/重复/乱序的处理（确认、超时重传、序号）。

## 1.4 RPC 与并发原语

### 1.4.1 RPC：把远程调用伪装成本地函数调用

**RPC**（Remote Procedure Call，远程过程调用）是一种通信抽象：让调用远端机器上的一个过程，**在代码上看起来和调用本地函数一样**——写 `y = server.Add(x)`，底层却是把参数打包（marshalling / 序列化）成消息、走网络发给服务器、服务器解包执行、把返回值打包发回、客户端解包得到 `y`。中间那层帮你收发和打包解包的代码叫**存根**（stub）。MIT 6.5840 L2 正是「RPC and Threads」，用 Go 的 RPC 讲这套。

RPC 的设计意图是"透明"——让分布式编程像本地编程一样简单。但这份透明是有裂缝的，这正是本节的重点：**本地调用要么成功返回、要么进程一起崩（不存在"调用了但不知道结果"）；远程调用却多了一种本地没有的失败模式——请求或回复丢在路上、或服务器执行完才崩，客户端拿不到回复，于是根本不知道"那次调用到底执行了没有"。** 这个"不知道执行没执行"的不确定性，就是 1.4.2 交付语义要处理的核心难题，也是 RPC 抽象无法完全掩盖底层网络（1.3）的地方。

### 1.4.2 三种交付语义：at-least-once / at-most-once / exactly-once

当客户端"发了请求但没等到回复"时，它面临一个两难：**重发**还是**不重发**？两种选择对应两种基本语义：

**at-least-once（至少一次）**：超时就重发，直到收到回复。后果是——如果原请求其实已被服务器执行、只是回复丢了，重发会让操作**被执行不止一次**。对**只读或幂等**（idempotent，做多次和做一次效果相同，如"把 x 置为 5"）的操作没问题；对**非幂等**操作（如"余额减 100""计数器加 1"）会出错（多扣钱）。

**at-most-once（至多一次）**：客户端给每个请求一个唯一 ID，服务器维护一张**已执行请求表**，见到重复 ID 就**不再执行**、直接返回上次缓存的结果。后果是——操作要么执行一次、要么因彻底失败而零次，**绝不重复执行**。代价是服务器要维护去重状态（这张表何时能安全清理是工程难点）。这是实用 RPC 系统（含 6.5840 的 KV lab）追求的默认目标。

**exactly-once（恰好一次）**：理想中"操作精确执行一次且客户端确知结果"。


```
在会崩溃、会丢消息的分布式系统里，端到端的 exactly-once 交付在一般情况下不可实现。
```

根本原因在于，客户端与服务器无法同时、原子地"既执行操作又确认对方知道"——总能构造一个时序（回复丢失 + 某方崩溃），让双方对"到底做没做"产生分歧。实践中所谓的 "exactly-once"（如某些消息系统宣传的）几乎都是 **at-least-once 传输 + 幂等/去重处理** 的组合效果（在应用层看起来像只发生一次），而非真的在网络层保证恰好一次投递。把这一点讲清，能帮初学者破除"exactly-once 是个可选开关"的误解。

### 1.4.3 幂等性：让 at-least-once 变安全的关键工具

**幂等操作**指执行一次和执行多次结果相同的操作。它是把便宜的 at-least-once 变得安全的核心手段：既然重复不可避免，那就让"重复也无害"。


```
非幂等：balance -= 100     （重发一次就多扣 100，错）
幂等  ：balance  = 400     （重发多少次结果都是 400，对）
幂等  ：set(key, val)      （天然幂等）
去重化：apply(reqID=7, "balance-=100")  （服务器按 reqID 去重，等效 at-most-once）
```

落到设计上有两条路：要么把操作本身设计成幂等（赋值式、集合式），要么给每个请求配唯一 ID + 服务器去重，把"至少一次的传输"在语义上收敛成"至多一次的执行"。这也解释了为什么 1.3 的"序号 + 去重"是贯穿始终的主线工具。

### 1.4.4 RPC 与并发：为什么 RPC 天然要配并发原语

RPC 几乎总和**线程/并发**绑在一起（6.5840 L2 把两者合讲不是偶然）。原因：一次 RPC 要跨网络往返，客户端若同步等待就会阻塞很久，因此常用**多线程**并发发起多个 RPC、或服务器**每请求一线程**并发处理；而一旦有多个线程共享状态（如那张去重表、KV 存储），就必须用**锁 / 条件变量 / channel** 等并发原语保护共享数据，防止竞态。

本课把 RPC 的"网络失败语义"（本节）和"共享状态并发控制"（互斥、锁——详见并发课 L4-05）放在一起，是因为一个正确的分布式服务必须**同时**处理两类问题——远端可能失败（要重试/去重）、本地多线程可能竞态（要加锁）。只解决一个而忽略另一个，都会出难以复现的 bug。本报告聚焦网络失败语义，并发原语的深入机制指路并发课，不在此纵深。

## 1.5 故障检测器

### 1.5.1 故障检测器：把"对方死没死"形式化成一个模块

**故障检测器**（failure detector）是一个抽象模块：每个节点上跑一个本地检测器，随时能被查询"你怀疑哪些节点已经崩溃了？"。它的典型实现是**心跳（heartbeat）+ 超时**——每个节点周期性发"我还活着"的心跳，若某节点在超时时间内没收到另一节点的心跳，就**怀疑**（suspect）它崩溃了。

为什么要把它单独抽象出来？因为 1.1 已经说清：纯异步模型下"死"和"慢"不可区分，共识不可解（FLP）。故障检测器的思想是——**把"判断谁死了"这件不可靠的事集中封装成一个模块，并诚实地刻画它到底能提供多可靠的判断**，让上层共识算法建立在这个明确的接口之上。Chandra & Toueg (JACM 1996) 正是用它证明了"给异步系统配一个足够好的故障检测器，共识就重新可解"——这是绕过 FLP 的经典路径（大主题4细讲）。

### 1.5.2 两个正交指标：完备性 (completeness) 与准确性 (accuracy)

一个故障检测器的质量由两个**正交**的性质刻画：

```
完备性 (Completeness)：崩溃的节点，最终会不会被（某些/所有）正常节点怀疑？
    —— 管"该抓的漏没漏"（不放过真崩溃的）
准确性 (Accuracy)：正常存活的节点，会不会被错误地怀疑？
    —— 管"抓的对不对"（不冤枉活着的）
```

Chandra & Toueg 把它们各分强弱，组合出一张分类表。完备性两档：

```
强完备性 (Strong Completeness)：每个崩溃节点最终被【所有】正常节点永久怀疑
弱完备性 (Weak Completeness)：每个崩溃节点最终被【某个】正常节点永久怀疑
```

准确性四档（强/弱 × 是否"最终"）：

```
强准确性 (Strong Accuracy)：正常节点【从不】被【任何】节点怀疑
弱准确性 (Weak Accuracy)：至少有一个正常节点【从不】被【任何】节点怀疑
最终强/弱准确性 (Eventual …)：上述性质只需在【某个时刻之后】成立（此前允许乱怀疑）
```

由此得到几个有名的检测器类，其中最关键的是 **◇W（Eventually Weak，最终弱）= 弱完备 + 最终弱准确**——Chandra、Hadzilacos & Toueg 证明它是**解共识所需的最弱故障检测器**。初学者不必记全表，记住"完备性=不漏、准确性=不冤，两者各有强弱，◇ 表示允许一段时间后才达标"即可。

### 1.5.3 核心权衡：完备性容易，准确性难，两者不可兼得（异步下）

本小主题的灵魂结论：**用心跳+超时实现的故障检测器，完备性和准确性存在根本张力，异步模型下无法同时做到"完美"。**


```
超时设得短  ⇒ 崩溃很快被发现（完备性好、反应快）
            但一个只是暂时慢的活节点极易被误判死掉（准确性差、误报多）
超时设得长  ⇒ 几乎不误判活节点（准确性好）
            但真崩溃了也要拖很久才发现（完备性达标慢、反应迟钝）
```

为什么异步下不能兼得"完美"？因为完美准确性（Perfect / P 类，从不误判活节点）等价于"能可靠区分慢与死"，而 1.1 已证异步模型下这不可能——任何有限超时都可能撞上一个"慢到超过该超时但其实还活着"的节点。所以异步系统里能造的**只有**"最终"准确的检测器（◇P、◇S、◇W）：它承认"一开始可能误判，但网络稳定下来后不再误判"。这与 1.1.3 的部分同步、GST 思想完全同构——**故障检测器把"系统迟早会安稳"这个假设，封装成"迟早会停止误判"的准确性承诺**。

这就是为什么真实系统（如 Raft）的选举超时要**随机化并取一个不算太小的值**——太小则频繁误判 leader 死亡、频繁无谓选举（准确性差）；配合随机化避免同时超时。心跳间隔、超时阈值的调参，本质就是在这条完备性↔准确性轴上选一个工程折中点。可选的 Python 实证（心跳+注入延迟看误判率随超时变化）未做，如实标注。
