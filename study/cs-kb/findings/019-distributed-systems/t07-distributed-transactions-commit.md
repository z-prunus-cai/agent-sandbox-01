## 7.1 分布式事务与 ACID 挑战

### 7.1.1 什么是分布式事务

分布式事务是指一个事务的读写操作涉及**多个独立节点**（不同机器、不同数据库分片、或不同服务），而这些节点各自管理自己的数据与本地事务，却要求整体仍满足事务的 ACID 语义——原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。典型例子是转账：从 A 银行账户扣 100 元、往 B 银行账户加 100 元，而 A、B 分别存在两台不同的数据库上。

给初学者的直觉：单机事务里，数据库有一个统一的日志和一把统一的锁管理器，"提交"就是往本地日志写一条 commit 记录、一瞬间生效，天然原子。分布式事务的麻烦在于**没有这样一个统一的裁决点**——扣钱那台机器提交了、加钱那台机器却崩了，钱就凭空消失了。所以分布式事务的核心不是"怎么执行读写"（各节点本地照常做），而是"**怎么让多个节点对最终提交与否达成一致、且这个决定对崩溃鲁棒**"。ACID 四个字母里，跨节点真正变难的主要是 A（原子性）和 I（隔离性），下面两节分别说。

### 7.1.2 跨节点原子性为什么难：部分失败

原子性要求"要么所有参与节点都提交、要么所有参与节点都中止，绝不出现一部分提交一部分中止"。跨节点做不到的根源是**部分失败（partial failure）**：单机崩溃是"全体一起停"，而分布式系统里某些节点在运行、某些节点崩了、某些消息在飞——系统处于一种"部分活着"的中间态，而且从外部无法可靠区分"节点崩了"和"节点只是慢/网络断了"。

给初学者：设想协调者对两个参与者喊"提交！"，第一条消息送达、参与者1 提交了；发第二条时网络断了，参与者2 没收到、超时后自作主张中止了——原子性就被破坏。你可能想"那让每个节点自己决定不就行了"，但各节点看到的局部信息不同（有的检测到约束冲突要中止、有的一切正常想提交），各自为政必然分裂。所以必须有一个协议，让所有节点**先交出"单方面提交"的自主权**、统一听一个决定，这正是 §7.2 两阶段提交要解决的。这里的失败模型是**崩溃-停止 + 崩溃-恢复**（节点可能崩溃，但崩溃后会重启并从持久化日志恢复），网络可丢消息、可延迟，这是理解后续所有协议的前提。

### 7.1.3 跨节点隔离为什么难

隔离性要求并发事务的效果等价于某种串行执行（可串行化）。单机上靠两阶段锁（2PL）或 MVCC 就能保证；跨节点难在：锁分散在各节点、无法用一把全局锁一锁到底，而**跨节点的锁等待会形成谁都察觉不到的全局死锁环**（§7.5），并且要判定"全局是否可串行化"需要把各节点的读写依赖拼成一张全局图，代价高。

给初学者：并发控制在单机已经是大话题，跨节点它同时叠加了两个新麻烦。其一，可见性——事务 T 在节点1 提交了、在节点2 还没提交，此时另一个事务在两个节点上读，会看到"半提交"的不一致状态，除非隔离机制跨节点协调可见时机。其二，死锁——T1 在节点A 持锁等节点B 的锁、T2 在节点B 持锁等节点A 的锁，两者互等成环，但没有任何单个节点能看到完整的环。本报告 §7.4 讲隔离机制（快照隔离），§7.5 讲跨节点死锁，都是这个"隔离跨节点变难"的展开。

### 7.1.4 原子提交问题（Atomic Commit）的精确定义

把 §7.1.2 的诉求形式化，就是**原子提交问题**：一组参与者各自对事务投一票（Yes=我能提交 / No=我要中止），要设计一个协议让所有参与者对最终结果（Commit / Abort）达成一致，且满足下面这组不变式。

```
AC-1 (一致 / Agreement)：所有做出决定的参与者，决定相同（不能有人 Commit 有人 Abort）
AC-2 (有效性 / Validity)：只有当所有参与者都投 Yes 时，结果才可能是 Commit
AC-3 (中止有效)：若有任一参与者投 No，或发生某类故障，结果必须是 Abort
AC-4 (终止 / Termination，弱形式)：不发生故障时，所有参与者最终都做出决定
```

给初学者：AC-2 是关键——**任何一个参与者说"不行"，整个事务就必须中止**，这叫"一票否决"。原因很实在：如果参与者2 因为余额不足（约束冲突）没法提交，而其他人都提交了，数据库就进入了违反业务约束的坏状态。所以原子提交本质是"全体一致同意才通过"的表决。注意 AC-4 是**弱终止**——它只保证"无故障时"能终结；一旦允许协调者崩溃，能否保证终止就成了 2PC 的死穴（§7.3）。这组不变式是判断"某协议对不对"的判据，后面每讲一个协议都回来对照它。

### 7.1.5 原子提交 vs 共识：像但不同

原子提交和共识（大主题4）长得很像——都是"让一组节点对某个值达成一致"，但**不是同一个问题**，混淆会导致对 2PC 的错误期待。

关键区别在有效性条件。共识只要求"最终选定的值是某个节点提出过的值"，允许在多个候选里挑一个、且**只需多数派存活**就能终结（Paxos/Raft 容 f 个故障需 2f+1 节点）。原子提交则要求**一票否决 + 全体参与**：只要有一个参与者说 No，或有一个参与者不可达，结果就倾向于 Abort（或阻塞等它），它对"每个参与者的意见"都敏感，不能靠多数派绕过某个沉默的参与者。

给初学者：一句话记——"共识是少数服从多数、能带伤前进；原子提交是全票通过、一人缺席就卡住或作罢"。这解释了为什么 2PC 不像 Raft 那样"多数派活着就能继续"：因为它必须听到**每一个**参与者的确认。也正因如此，现代做法（§7.3.5）不是抛弃 2PC，而是把 2PC 里那个脆弱的**协调者角色用共识组来实现**——让协调者的决定本身高可用，从而把两者的长处结合。这两者的界线是本大主题与大主题4 分账的落点。

## 7.2 两阶段提交（2PC）

### 7.2.1 角色、消息序列与状态机

两阶段提交是解决原子提交问题最经典的协议，由一个**协调者（coordinator，即事务管理器 TM）**驱动一组**参与者（participants，即资源管理器 RM）**。顾名思义分两个阶段：投票阶段（prepare/voting）与提交阶段（commit）。正常提交的完整消息序列如下。

```
阶段1 · 投票（prepare / voting phase）
  协调者 → 全体参与者：PREPARE（"准备好提交这个事务吗？"）
  每个参与者：本地做完事务、把 undo/redo 写进持久化日志、锁住数据
             → 若能提交，持久化写下 "prepared" 记录，回 VOTE-YES
             → 若不能（约束冲突/故障），回 VOTE-NO，本地中止

阶段2 · 提交（commit phase）
  若协调者收齐全体 VOTE-YES：
     协调者持久化写下 "commit" 决定（此刻决定生效，不可逆）
     协调者 → 全体参与者：COMMIT
     每个参与者：提交、释放锁，回 ACK
  若协调者收到任一 VOTE-NO 或投票超时：
     协调者持久化写下 "abort" 决定
     协调者 → 投过 YES 的参与者：ABORT
     每个参与者：回滚、释放锁，回 ACK
```

给初学者：两个阶段对应两个心智动作。阶段1 是"点名表决"——协调者挨个问"你到底行不行"，每个参与者此时要做一件极重要的事：**把"我承诺能提交"这件事写进磁盘日志**，之后哪怕自己崩溃重启，也必须认账、不能反悔（§7.2.2）。阶段2 是"公布结果"——只有全票 YES 协调者才敢宣布 COMMIT，并且**协调者写下 commit 决定的那一瞬间就是全局提交点（commit point）**，此后无论谁崩溃，最终结果都已注定是提交。最易错的理解是把"参与者投了 YES"当成"事务提交了"——不是，投 YES 只是**放弃了单方面中止的权利、进入待命**，真正提交要等阶段2 协调者的 COMMIT。

### 7.2.2 prepared 状态与预写日志：为什么参与者必须先落盘

2PC 正确性的物理基石是：参与者在回 VOTE-YES **之前**，必须把事务的 redo/undo 信息与"prepared"标记**持久化到日志（WAL）**。这样一来，即使它在投完 YES 后立刻崩溃，重启后也能从日志里看到"我处于 prepared 状态、还欠一个最终决定"，从而去询问协调者结果、并有能力执行提交或回滚。

给初学者：想象参与者投了 YES 却没落盘就断电了。重启后它对这个事务一无所知——若协调者随后广播 COMMIT，它却已经把改动丢了，原子性就碎了。所以"投 YES"这个承诺必须是**可持久兑现**的，这就要求先写日志。这也是 2PC 昂贵的原因之一：每个参与者一次事务至少要强制刷盘两次（prepared 一次、最终 commit/abort 一次），协调者也要刷盘写决定，都是同步 fsync，延迟高。术语上，投完 YES 但还没收到最终决定的参与者处于 **in-doubt（存疑）状态**——它手里锁着数据、进退不得，只能等协调者。这个 in-doubt 状态就是 §7.3 阻塞问题的主角。

### 7.2.3 中止路径与超时

2PC 里"中止"可以由两种情况触发：任一参与者投 VOTE-NO，或协调者在阶段1 等投票时超时（某参与者没及时回）。两种情况协调者都写下 abort 决定并广播 ABORT。

给初学者要分清一个关键的**时机不对称**：在协调者写下最终决定**之前**，任何一方超时都可以安全地中止——参与者若在投票前还没收到 PREPARE，或投了 YES 但迟迟等不到决定……（注意后者恰恰**不能**擅自中止，见下）。准确地说：（1）参与者在投票**前**超时，可单方面中止（反正还没承诺）；（2）协调者在收齐投票**前**超时，可决定中止（一票缺失视同否决）；（3）但参与者一旦投了 YES、进入 in-doubt，就**丧失了单方面中止的权利**，它超时后不能擅自中止也不能擅自提交，只能去问协调者——这正是阻塞的来源。把这三种超时的处置背下来，就抓住了 2PC 安全性的边界。

### 7.2.4 2PC 为何保证原子性

对照 §7.1.4 的 AC 不变式，2PC 的正确性来自一个**单一决定点**：全局结果完全由协调者写进日志的那条 commit/abort 记录决定，所有参与者最终都执行这条唯一决定。

```
原子性不变式：全局结果 = 协调者持久化的唯一决定（commit XOR abort）
  · COMMIT 只在收齐全体 VOTE-YES 后写下 ⇒ 满足 AC-2（全 Yes 才提交）
  · 任一 VOTE-NO / 投票超时 ⇒ 写 ABORT ⇒ 满足 AC-3（一票否决）
  · 所有参与者执行同一条决定 ⇒ 满足 AC-1（决定一致）
```

给初学者：2PC 之所以对，是因为它把"要不要提交"这个判断**收敛到协调者这一个点**，消除了各节点各自为政的可能。参与者投 YES 后就把命运交给协调者，绝不自作主张，于是决定天然一致。副作用也在这里：全局的一致性以"协调者是唯一裁决者"为代价，一旦这个唯一裁决者在关键时刻消失（阶段2 开始前后崩溃），系统就没人能补位——这就是 AC-4（终止）无法在故障下保证、2PC 会阻塞的根本原因，下一节展开。

### 7.2.5 常见优化：presumed abort / 只读优化

朴素 2PC 要求协调者记住每个事务、参与者最终都要 ACK，日志和消息开销大。经典优化 **presumed abort（推定中止）** 规定：协调者在提交决定持久化前**不必**为事务保留日志；崩溃恢复后若某参与者来问一个"查无记录"的事务，协调者一律回答 ABORT。这样中止路径就不需要写日志、不需要收 ACK，省掉大量开销（中止是常见情形）。对称地还有 presumed commit，但因需要额外记录参与者列表，实践中 presumed abort 更常用。

另一个优化是**只读参与者早退**：若某参与者本次事务只做了读、没有写，它在阶段1 可以回 "VOTE-READ-ONLY" 而非 YES，随即释放锁退出，不参与阶段2——因为一个只读参与者提交与否对数据无影响。

给初学者：这两条不改变 2PC 的正确性骨架，只是"约定俗成的默认值省日志"。presumed abort 的巧思是把"没有记录"这个廉价状态直接解释成"中止"，因为中止本就不需要任何人记得它（中止 = 什么都没发生）；只有提交这个"有后果"的决定才值得花代价持久记录。这解释了工业实现（XA、Gray & Reuter 描述的经典 TM）为何普遍采用 presumed abort 作为默认。

## 7.3 2PC 阻塞问题与 3PC

### 7.3.1 2PC 的致命伤：协调者崩溃导致参与者阻塞

2PC 最被诟病的是**阻塞（blocking）**：如果协调者在**收齐投票之后、把最终决定送达所有参与者之前**崩溃，那些已投 YES、进入 in-doubt 的参与者将无限期卡住——它们锁着数据、既不能提交也不能中止，只能等协调者恢复。

```
阻塞时刻：参与者已回 VOTE-YES（in-doubt），但尚未收到 COMMIT/ABORT，此时协调者崩溃且长时间不恢复
后果：该参与者不能擅自提交（万一协调者其实决定了 ABORT），也不能擅自中止（万一协调者其实决定了 COMMIT）
     ⇒ 持锁等待，阻塞其他访问同数据的事务
```

给初学者：为什么 in-doubt 参与者不能自己拿主意？因为它**无法知道协调者在崩溃前到底写没写、写了什么决定**。若它猜"提交"而协调者其实写了 abort，或反之，都会破坏 AC-1（决定一致）。安全的唯一选择就是"死等"。这就是 §7.2.4 说的代价兑现——把决定权收敛到协调者一个点，换来了一致，也换来了"这个点没了大家就集体瘫痪"。注意区分：参与者崩溃**不致命**（它重启后靠日志恢复、来问结果即可，协调者还能推进）；真正致命的是**协调者崩溃**，尤其在阶段2 临界点。

### 7.3.2 参与者互相询问也救不了

一个自然的补救是：in-doubt 的参与者去问其他参与者"你收到决定了吗"。这在某些情形有用（若有参与者已收到 COMMIT/ABORT，就能传播开），但**不能根治阻塞**。

给初学者：设想协调者刚写下决定、还**一条 COMMIT 都没发出去**就崩了。此刻所有参与者都处于 in-doubt、都投了 YES、谁都没收到决定——它们互相一问，答案全是"我也不知道"，信息量为零，照样集体卡死。更糟的是，它们也无法安全地"多数决"自行提交，因为协调者崩溃前写下的可能是 abort。根本原因是：**决定这个信息只存在于崩溃的协调者那里，没有在参与者间冗余**。这句话直接点出 3PC 的思路（把决定的"预兆"提前扩散到参与者），也点出现代方案（§7.3.5，把决定本身用共识复制到多数派）。

### 7.3.3 3PC 的思路：插入 pre-commit 阶段

三阶段提交（3PC，Skeen 1981）为消除阻塞，在 2PC 的投票和提交之间**插入一个 pre-commit（预提交）阶段**，把"决定即将提交"这个信息先扩散给所有参与者，再真正提交。

```
阶段1 · CanCommit：协调者问，参与者投 Yes/No（同 2PC 投票）
阶段2 · PreCommit：协调者收齐 Yes 后，先广播 PRE-COMMIT；参与者收到后进入 "prepared-to-commit" 状态并 ACK
                  （此阶段传达："大家都同意了，准备提交"，但还没真提交）
阶段3 · DoCommit：协调者广播 COMMIT，参与者真正提交
```

给初学者：3PC 的关键洞察是，2PC 里参与者从"in-doubt（完全不知道结果）"直接跳到"提交"，中间没有过渡；3PC 加的 PreCommit 阶段制造了一个中间状态——"我知道**全体都投了 YES**、结果一定是 COMMIT，只是还没执行"。有了这个共享信息，如果协调者在阶段3 崩溃，任何一个进入了 prepared-to-commit 的参与者都能推断"结果必是提交"并接管完成；而如果崩溃发生在还没有任何人进入 prepared-to-commit（即阶段2 之前），那说明还没人可能提交，可以安全地统一中止。这样就把"死等崩溃的协调者"变成了"存活参与者能自行推进"，即**非阻塞**。

### 7.3.4 3PC 为何在无分区下非阻塞——以及它的致命前提

Skeen 1981 证明了 3PC 在**同步网络 + 仅崩溃-停止故障 + 网络不分区**的模型下是非阻塞的：存活的参与者总能通过一个终止协议（termination protocol）在有限时间内一致地决定提交或中止，不必等崩溃节点恢复。

给初学者要牢牢记住这个前提，因为它就是 3PC 的阿喀琉斯之踵。3PC 的非阻塞性依赖两个理想假设：（1）**没有网络分区**；（2）网络是**同步的**（消息延迟有已知上界，故超时能可靠区分"崩溃"和"慢"）。现实网络两条都不满足。Skeen & Stonebraker 1983 进一步证明：**在允许网络分区的情况下，不存在任何非阻塞的原子提交协议**——这是一个不可能性结果，和 CAP、FLP 一脉相承。直觉上，分区会把参与者切成两组、各组都以为对方崩了，若都"非阻塞地"自行决定，两组可能得出相反结论，破坏一致。

### 7.3.5 3PC 实践不用；现代做法是把协调者做成共识组

尽管 3PC 理论上非阻塞，工业界**基本不用**它。原因：它多一轮消息（延迟更高）、依赖的同步假设在真实网络站不住、且面对网络分区照样不安全（§7.3.4）。真正解决 2PC 单点阻塞的主流思路是另一条路——**保留 2PC 的两阶段骨架，但把脆弱的协调者角色用共识（Paxos/Raft）复制成一个高可用组**。

```
2PC over 共识（心智）：协调者的每个关键决定（commit/abort）先经共识复制到多数派日志
  ⇒ 协调者单机崩溃后，新领导者从复制日志读出决定并接管推进
  ⇒ 2PC 的一致性骨架不变，但"决定"不再是单点、消除了 in-doubt 死等
```

给初学者：这就把 §7.3.2 点出的根因——"决定只存在崩溃的协调者一处"——直接治掉：让决定冗余存在于共识组的多数派里，任何幸存的多数派都能恢复决定并继续。这也呼应 §7.1.5："原子提交需要每个参与者，共识提供高可用的裁决"，两者组合而非二选一。**具体系统实现（Spanner 的 2PC over Paxos + TrueTime、各分布式数据库的做法）属 L6-05 C3，本报告只给到这层机制指路，不深挖。** 一句话收束：3PC 是"教科书里为理解非阻塞而存在"的协议，实战答案是共识化的协调者。

## 7.4 并发控制与快照隔离（理论）

### 7.4.1 并发控制目标与可串行化

并发控制的目标是让并发执行的多个事务**等价于某个串行执行**，即**可串行化（serializability）**——这是隔离性的黄金标准。可串行化保证：无论调度器如何交错各事务的读写，最终结果都和"把这些事务一个接一个跑完"的某个顺序一致，从而不产生任何并发异常。

给初学者：为什么以"串行"为标准？因为串行执行显然没有并发 bug（一次只跑一个事务，谁也干扰不了谁），所以"等价于串行"就成了正确性的天花板。实现可串行化的经典手段有两类：**基于锁的两阶段锁（2PL）**——事务先只加锁、到某点后只放锁，保证冲突操作串行；以及**多版本（MVCC）**方案。工程上完全的可串行化代价高（锁争用、读写互相阻塞），所以数据库提供了一系列**较弱的隔离级别**（读未提交、读已提交、可重复读、快照隔离），用"允许某些异常"换性能——理解这些级别各自漏什么异常，是本小主题的核心，下面从 MVCC 与快照隔离切入。

### 7.4.2 MVCC 多版本并发控制

多版本并发控制（MVCC）让每次写**不覆盖旧值、而是创建一个新版本**，每个版本带有创建它的事务的时间戳/版本号。读操作则按事务开始时的"快照"去读**在该时刻已提交的那个版本**，于是读永远读到一个一致的历史快照，不需要加读锁。

给初学者：MVCC 的核心红利是一句话——**读不阻塞写，写不阻塞读**。传统 2PL 里读要加共享锁、和写的排他锁互斥，读多写多时争用严重；MVCC 让读走旧版本快照、写造新版本，二者井水不犯河水，并发度大增。代价是要存多个版本、并需要后台垃圾回收（清理没人再读的旧版本，如 PostgreSQL 的 VACUUM）。MVCC 是快照隔离（§7.4.3）的实现基础，也是现代数据库（PostgreSQL、Oracle、MySQL InnoDB、几乎所有分布式数据库）的主流机制。要点：MVCC 是"机制"，快照隔离是这套机制提供的"隔离级别语义"，别把两者划等号。

### 7.4.3 快照隔离（Snapshot Isolation, SI）的定义

快照隔离由 Berenson et al. 1995 首次形式化。它规定：**每个事务读的是它开始那一刻的数据库一致快照**（看不到任何在它开始后才提交的事务的改动），并且用 **first-committer-wins（首个提交者胜）** 规则处理写冲突——两个并发事务若写了同一行，只有先提交的能成功，后者中止。

```
Snapshot Isolation：
  · 读：事务 T 读到的都是 T 启动时刻已提交的版本（一个固定的一致快照）
  · 写冲突：若 T1、T2 并发（时间区间重叠）且写了同一数据项，只有一个能提交（first-committer-wins / first-updater-wins）
```

给初学者：SI 的体验非常好——读永远看到一个干净的历史截面，绝不会读到中间态或不一致，也**杜绝了脏读、不可重复读、以及 ANSI 定义的幻读**。它靠 MVCC 实现：T 开始时记下一个快照时间戳，之后所有读都按这个时间戳取版本。first-committer-wins 则防止了"丢失更新"（两个事务同时改同一行、后者覆盖前者）。SI 曾长期被误当作"可串行化"（Oracle 的 SERIALIZABLE 级别实际就是 SI），但**它并不是可串行化**——它会漏出一种叫"写偏斜"的异常，这是下一节的重点，也是 Berenson et al. 论文最重要的发现。

### 7.4.4 写偏斜（write skew）：SI 不等于可串行化

**写偏斜**是快照隔离允许、但破坏可串行化的经典异常。它发生在两个并发事务**各自读了同一组数据、然后各自写了其中不同的数据项**，两者的写没有直接冲突（没写同一行，所以 first-committer-wins 拦不住），但合起来违反了一个跨行的约束。

```
写偏斜史（Berenson et al. 1995，A5B）：
  T1: read(x), read(y)          T2: read(x), read(y)
  T1: write(y)                  T2: write(x)
  T1: commit                    T2: commit
  两事务读同一快照、各写不同项、无写-写冲突 ⇒ SI 允许两者都提交，但非可串行化
```

给初学者用最经典的"医生值班"例子（DDIA）：约束是"任意时刻至少留 1 名医生值班"。当前 Alice、Bob 都在值班。两人同时想请假，各自的事务先读"当前值班人数=2 ≥ 1，OK"（读的是同一快照），然后 Alice 把自己改成休息、Bob 把自己改成休息——两个写落在不同的行（不同医生记录），first-committer-wins 不认为它们冲突，于是**两个事务都提交成功，结果值班人数=0，约束被破坏**。而任何串行执行都不会出这个问题（后跑的那个会读到人数=1、被拦下）。写偏斜的本质是：SI 的冲突检测只看"写-写是否同一行"，看不到"两个事务基于同一读集做了会相互抵消的决定"。这就是 SI 不可串行化的根源，也是初学者最容易忽视的隔离陷阱。

### 7.4.5 与"可重复读"的辨析及其他异常

快照隔离常被和 ANSI 的"可重复读（Repeatable Read）"混淆，但两者**互不包含**：Berenson et al. 指出，SI 禁止了 ANSI 定义的幻读（Phantom，因为读的是固定快照），而可重复读不禁止幻读；反过来，SI 允许写偏斜，而真正的可串行化不允许。它们各自漏的异常不同，不能简单说谁强谁弱。

给初学者还需知道 SI 相关的两个点。其一，**丢失更新（lost update）** 被 SI 的 first-committer-wins 挡住了（这是 SI 相对读已提交的一大改进）。其二，还有一种"**只读事务异常**"——在 SI 下即使一个事务只读，也可能观察到不可串行化的结果（Fekete et al. 后续研究指出），比写偏斜更隐蔽。这些都指向同一结论：**SI 是一个很实用但不可串行化的隔离级别**，用它就要在应用层用显式加锁（SELECT ... FOR UPDATE）或约束来堵写偏斜。命名混乱是易错点——PostgreSQL 的 REPEATABLE READ 实际提供的是 SI，Oracle 的 SERIALIZABLE 实际也是 SI；别被级别名字骗了。

### 7.4.6 可串行化快照隔离（SSI）：给 SI 打补丁

为了既保住 MVCC/SI 的高并发、又达到可串行化，Fekete、Cahill 等人（2008–2009）提出**可串行化快照隔离（Serializable Snapshot Isolation, SSI）**：在 SI 基础上运行时**追踪事务间的读写依赖**，检测出可能导致不可串行化的危险模式（尤其写偏斜特有的"两条 rw-依赖首尾相接"结构），发现就中止其中一个事务。

给初学者：SSI 是一种**乐观并发控制**——它不预先加锁阻塞，而是让事务乐观地跑，提交时检查有没有形成危险依赖环，有就回滚重试。它的代价是可能有额外的中止/重试，但保留了 SI"读不加锁"的高并发优势，比传统 2PL 的可串行化更快。PostgreSQL 从 9.1（2011）起的 SERIALIZABLE 级别就是 SSI 实现（Ports & Grittner）。要点：SSI 是"用检测+回滚，把 SI 提升到可串行化"的工程方案，它的存在恰恰反证了"SI 本身不可串行化"（§7.4.4）。⚙演进快：SSI 的具体实现与优化随数据库版本演进，锚 PostgreSQL 9.1+，随时可能有新做法。

- 冲突/易错标注：**命名冲突显式记录**——Oracle 的 "SERIALIZABLE" 与 PostgreSQL 9.0 及以前的 "SERIALIZABLE"/"REPEATABLE READ" 实际提供的是 SI 而非真可串行化；PostgreSQL 9.1+ 起 SERIALIZABLE 才是 SSI（真可串行化）。此为实现命名与标准语义的分账，非文献分歧。⚙SSI 实现演进快，锚 PostgreSQL 9.1+。

## 7.5 分布式死锁与提交时序

### 7.5.1 分布式死锁：跨节点的全局等待环

当并发控制用锁时，事务会因等待被别人持有的锁而阻塞；若这种等待关系形成环，就是死锁。在分布式场景，等待关系跨节点：事务 T1 在节点A 持锁、等待节点B 上被 T2 持有的锁，而 T2 又等待节点A 上被 T1 持有的锁——形成一个**跨节点的全局等待环（global wait-for graph, WFG）**。

```
分布式死锁：
  节点A：T1 持锁 a，T2 等待 a
  节点B：T2 持锁 b，T1 等待 b
  全局 WFG：T1 → T2 → T1（环） ⇒ 死锁，但任一单节点只看到半条边
```

给初学者：分布式死锁比单机死锁难在**没有谁能看到完整的环**。节点A 只知道"T2 在等 T1"，节点B 只知道"T1 在等 T2"，两条边分别在两台机器上，必须把各节点的局部 WFG **拼起来**才能发现环。这就带来两个新问题：如何在不集中所有信息的前提下检测环（§7.5.2），以及能不能干脆预防环的形成（§7.5.3）。此外还有"幻影死锁（phantom deadlock）"陷阱——由于各节点的 WFG 是异步收集的、可能不是同一时刻的快照，拼出来的"环"可能是已经不存在的过时状态，导致误杀无辜事务。

### 7.5.2 死锁检测：边追逐（edge-chasing，Chandy-Misra-Haas）

分布式死锁检测的经典算法是 Chandy-Misra-Haas 1983 的**边追逐（edge chasing）**：不集中构造全局 WFG，而是让**探测消息（probe）沿等待边在节点间传播**，若一个探测消息绕一圈回到发起者，就说明存在环、即死锁。

```
probe 三元组 (i, j, k)：进程 Pi 发起的探测，由 Pj 的站点发往 Pk 的站点（Pj 在等 Pk）
规则：被阻塞的进程收到 probe 后，沿它自己正在等待的边继续转发 probe
判定：若 Pi 发起的 probe 最终又回到 Pi ⇒ 检测到环 ⇒ Pi 参与了死锁
```

给初学者：边追逐的巧思是把"找环"这个需要全局视图的任务，变成"一个探测信号顺着等待链跑，看能否回到出发点"的分布式过程——完全不需要谁掌握全局 WFG。每个节点只需在收到 probe 时，按本地已知的"我在等谁"把 probe 转发下去。探测信号回到发起者，等价于等待链闭合成环。检测到死锁后要**打破它**：选一个牺牲者（victim）事务回滚、释放其锁，让环解开。选谁通常按代价最小（如已做工作最少、时间戳最新）来定。边追逐是"检测再解除"的代表；下一节的时间戳法则走"根本不让环形成"的预防路线。

### 7.5.3 死锁预防：wait-die 与 wound-wait（时间戳法）

与其事后检测，不如从源头预防死锁。Rosenkrantz, Stearns, Lewis 1978 提出两种基于**事务时间戳**（越老的事务时间戳越小、优先级越高）的预防策略，靠"只允许单向等待"来杜绝环。

```
设请求锁的事务为 Ti，持锁的事务为 Tj：
  wait-die（非抢占）：
     若 Ti 比 Tj 老（ts(Ti) < ts(Tj)） → Ti 等待
     否则（Ti 更年轻）             → Ti 中止（die），稍后用原时间戳重启
  wound-wait（抢占）：
     若 Ti 比 Tj 老（ts(Ti) < ts(Tj)） → 抢占：Tj 中止（被 wound），Ti 拿锁
     否则（Ti 更年轻）             → Ti 等待
```

给初学者：这两个方案的共同点是**让等待关系只朝一个时间方向走**，环就无法形成（环必然要求既有"老等新"又有"新等老"）。wait-die 里永远只有"老的等年轻的"，wound-wait 里永远只有"年轻的等老的"，都是单向。区别在处置：wait-die 是**非抢占**的（年轻事务自己 die，不去动持锁的老事务），wound-wait 是**抢占**的（老事务来了直接把持锁的年轻事务打断）。一个关键设计——中止重启的事务**保留原时间戳**，这样它会越来越"老"、优先级越来越高，最终必能推进，避免了饿死（starvation）。易错点：这两者是"死锁预防（prevention）"，用中止的代价换"绝不死锁"，与 §7.5.2 的"检测后解除"是两条不同的路线。实践中，超时法（§7.5.4）因简单也很常用。

### 7.5.4 超时法：实践中的务实选择

最简单的分布式死锁处理其实是**超时**：事务等锁超过某个阈值就假定"可能死锁了"，直接中止（并重试）。它不区分"真死锁"和"只是等得久"，是一种近似手段。

给初学者：超时法的魅力在于零协调开销——不需要传探测消息、不需要维护全局图、不需要时间戳，每个节点各自计时即可。代价是不精确：阈值太短会误杀本可成功的长事务（把非死锁当死锁），太长又会让真死锁的事务白等很久才被清理。很多工程系统（尤其分布式数据库）就直接用锁等待超时 + 中止重试来兜底死锁，用简单换掉了边追逐的复杂度。这也呼应了整门课的务实精神：理论上边追逐/时间戳更精确，但工程上"够用且简单"的超时常常胜出。

### 7.5.5 提交时序：为什么需要一致的提交定序

分布式事务不仅要原子提交（§7.2），还要让并发事务的**提交生效顺序**在所有节点上表现一致——否则不同节点会对"谁先谁后"产生分歧，破坏隔离性甚至线性一致。提交定序就是给事务分配一个全局一致的顺序（常用时间戳/逻辑时钟），并让各节点按此顺序让写生效。

给初学者：设想事务 T1、T2 都改了分布在多个节点的数据。若节点A 认为 T1 先于 T2、节点B 认为 T2 先于 T1，那么在 A 上读到的世界和在 B 上读到的世界互相矛盾，整个系统就不再"看起来像一台机器"。所以需要一个各节点公认的提交顺序。逻辑上，这与大主题2 的全序广播、大主题5 的线性一致是同一个诉求的不同面孔——都是"给分布式事件定一个大家都认的序"。**如何用真实时钟高效且正确地定这个序（Spanner 的 TrueTime + commit-wait 造外部一致），属 L6-05 C3，本报告只指出"提交必须定序、且序要对齐线性一致/外部一致"这层机制诉求，不深挖具体实现。** 这也把本大主题（理论机制）和 L6-05（系统落地）的分账点收在此处。
