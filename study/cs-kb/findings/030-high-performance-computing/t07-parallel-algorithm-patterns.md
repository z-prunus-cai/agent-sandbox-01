> 本报告一条主线心智模型：**"并行算法模式"是一小撮反复出现的计算骨架——把一堆数据"合成一个数"（归约）、"算出每个位置的累加前缀"（扫描）、"统计落桶数"（直方图）、"邻域加权"（卷积/模板）、"重排成序"（排序/归并）、"压缩存零并乘"（稀疏）、"一层层铺开走图"（BFS）。串行版你早就会写；并行的关键动作只有两个：把独立的活儿铺给很多线程同时做，再想办法把"不独立"的部分（累加、去重、写同一个桶）用树形结构 / 私有副本 / 前缀和 拆成可并行的形状。** 每个模式都要盯两个量：**总工作量 work（做了多少次基本运算）** 和 **步深 step/depth（关键路径上必须串行的轮数）**——好并行算法要么步深低（快），要么工作量不比串行多太多（不浪费），最好两者兼顾。

## H-07.1 Reduction（归约）与减分歧策略

### H-07.1.1 归约是什么：把一串数用一个可结合运算合成一个数

归约（reduction）指用一个满足结合律的二元运算 ⊕（如加、乘、max、min、逻辑与/或）把一个数组 `a[0..n)` 合成单个结果：

result = a[0] ⊕ a[1] ⊕ … ⊕ a[n-1]

串行做法是一个累加器从头扫到尾，做 n−1 次运算、步深也是 n−1（每一步依赖上一步的累加器）。归约之所以能并行，靠的是 **结合律**：加法可以任意加括号，`((a0+a1)+(a2+a3))` 和 `(((a0+a1)+a2)+a3)` 结果相同，于是可以把相邻元素两两一组同时相加，做成一棵二叉树。

树形（tree / pairwise）归约的两个量独占记：

work（总运算次数）= n − 1

step（步深 / 树高）= ⌈log₂ n⌉

对 8 个整数，线性累加得 267、numpy 的 `sum`（内部用 pairwise 归约）也得 267，两者一致；n=8 时树形只需 3 轮（log₂8），线性需 7 次加法。这正是并行归约的卖点——工作量和串行一样是 O(n)，但关键路径从 n−1 缩到 log n，用 n/2 个"加法器"并行时理论上从 O(n) 时间降到 O(log n) 时间。

初学者最容易在两点栽跟头。其一，**运算必须可结合才能重排**；浮点加法在数学上结合、在机器上不严格结合（舍入顺序不同结果会有微小差异），所以并行归约和串行归约对浮点求和可能给出略微不同的最后几位——这不是 bug，是浮点的本性（详见数值课）。其二，别把"归约"和"扫描"混了：归约只要最后那一个总和，扫描要的是**每个前缀的和**（下一节）。

### H-07.1.2 GPU 上的朴素归约与 warp 分歧问题

⚙演进快·锚 CUDA Toolkit 13.x（本机无 GPU·文档腿）｜核实 2026-08-01

在 GPU（SIMT）上实现块内归约时，一个自然但糟糕的写法是"隔一个加一个"的交错寻址：第 0 轮线程 0,2,4,… 活动，第 1 轮线程 0,4,8,… 活动，用 `if (threadIdx.x % (2*stride) == 0)` 挑活动线程。

问题在于 SIMT 是"一个 warp（PMPP/CUDA 文档记为 32 线程）齐步走"：同一 warp 内只要有线程走 if、有线程不走，两条路径会被串行化执行，这叫 **warp 分歧（divergence）**（机制归大主题6）。上面这种"按线程号取模挑活动线程"的写法会让活动线程稀疏地散布在各 warp 里，分歧严重且随轮数越来越浪费。

PMPP Ch10 给出的减分歧改法是**改用连续寻址**：让 stride 从大到小（`stride = blockDim.x/2; stride >>= 1`），每轮由**前一半连续的线程号**去加"自己 + 自己+stride"处的元素：

```
// 减分歧的块内归约（示意，连续活动线程）
for (stride = blockDim/2; stride > 0; stride >>= 1) {
    if (t < stride) shared[t] += shared[t + stride];
    __syncthreads();
}
```

这样活动线程始终是"前 stride 个"，在整块 warp 满载时前几个 warp 全活动、后几个 warp 全不活动——warp 内不分歧。核心结论：**并行归约的正确性与工作量不变，减分歧只改"哪些线程在哪一轮活动"的排布，把 SIMT 惩罚降下来。** 进一步的优化（线程粗化 thread coarsening：每个线程先串行加多个元素再进树、以及最后一个 warp 用 warp 级原语免同步）PMPP 也讲，属大主题6 性能篇，此处点到为止。具体分歧惩罚倍数与不同架构相关，本机无 GPU，标「待核·文档腿」。

#### 来源与时效
- 锚点：PMPP 4e Ch10 Reduction（树形归约 work=n−1/step=log n、交错 vs 连续寻址减分歧、线程粗化）@4th ed 2022｜核实 2026-08-01。
- 锚点：CS267（Spring 2024，Demmel）并行归约与树形合并讲义，作复杂度界交叉印证｜核实 2026-08-01。
- 本机实证：numpy 2.4.6 `sum`（pairwise）与线性累加对 8 整数一致（=267），树形 3 轮 vs 线性 7 加。
- ⚙演进快·锚 CUDA Toolkit 13.x：warp=32、分歧串行化为 GPU 专属机制，本机无设备→分歧惩罚倍数「待核·文档腿」。

## H-07.2 Scan / prefix-sum（扫描 / 前缀和）

### H-07.2.1 扫描是什么：包含式 vs 排他式前缀和

扫描（scan / prefix sum）把结合运算 ⊕ 作用到"每个前缀"上，输出和输入一样长。包含式（inclusive）扫描的第 i 项含 a[i] 自己：

out_inclusive[i] = a[0] ⊕ a[1] ⊕ … ⊕ a[i]

排他式（exclusive）扫描的第 i 项**不含** a[i]（是它前面所有元素的合成，第 0 项为单位元，加法取 0）：

out_exclusive[i] = a[0] ⊕ … ⊕ a[i-1]  ，  out_exclusive[0] = 0

对 `1..8`，包含式扫描 = `[1,3,6,10,15,21,28,36]`，与 `numpy.cumsum` 完全一致；排他式扫描 = `[0,1,3,6,10,15,21,28]`。

扫描看似"天生串行"（每一项要用前一项），却是并行编程里最重要的基石之一：**只要你需要"给每个元素分配一段连续的输出位置 / 偏移量"，答案几乎总是先做一次排他式扫描**。典型用途——把稀疏满足条件的元素紧凑打包（stream compaction）、给每个桶算写入起点（基数排序）、把不定长子结果拼接（每个线程产出的条数做扫描得到写入偏移）。初学者先建立这个直觉："扫描 = 算偏移"，比记公式更有用。

### H-07.2.2 Hillis-Steele（步高效，亦称 Kogge-Stone）

Hillis-Steele 扫描（PMPP 中作为 Kogge-Stone 扫描讲，二者是同一骨架的不同来源命名）以"步深最小"为目标。做法是每一轮把每个元素加上它左边距离 `d` 处的元素，`d` 从 1 开始翻倍：

```
d = 1
while d < n:
    for all i in parallel where i >= d:
        a[i] = a[i] + a[i-d]     # 需用上一轮的旧值，故要双缓冲
    d *= 2
```

务必注意"读旧值写新值"——同一轮里若就地覆盖会读到本轮刚改过的值，所以要双缓冲（两块 buffer 轮换）。本机用显式拷贝旧数组实现，`1..8` 一轮轮变为 `[1,3,5,7,9,11,13,15] → [1,3,6,10,14,18,22,26] → [1,3,6,10,15,21,28,36]`，3 轮（=log₂8）后得到正确包含式前缀和。

两个量独占记：

step = ⌈log₂ n⌉

work = O(n log n)  （每轮约 n 次加法，共 log n 轮）

它步深最小（log n 轮，最快），但工作量是 O(n log n)，比串行的 O(n) 多做了 log n 倍的加法——在处理器数量受限时这份多余工作会变成实打实的浪费。这就引出下一个"少干活"的版本。

### H-07.2.3 Blelloch（工作高效，上扫/下扫，亦称 Brent-Kung）

Blelloch 工作高效扫描（PMPP 中作为 Brent-Kung 扫描讲）以"总工作量最小"为目标，直接产出**排他式**扫描，分两趟走一棵二叉树：

上扫（up-sweep / reduce 阶段）：自底向上把每对元素合成，最终根处得到全体总和——这就是一次树形归约。

下扫（down-sweep 阶段）：把根置为单位元（加法取 0），自顶向下每个内部节点把"自己原值传给左孩子、自己与左孩子原值之和给右孩子"，铺下去后每个叶子恰好得到它的排他前缀。

```
# up-sweep：build sum tree
for d in [1,2,4,...,n/2]:
    for i in parallel step 2d: a[i+2d-1] += a[i+d-1]
a[n-1] = 0                      # 清根为单位元
# down-sweep：spread prefixes
for d in [n/2,...,4,2,1]:
    for i in parallel step 2d:
        t = a[i+d-1]; a[i+d-1] = a[i+2d-1]; a[i+2d-1] += t
```

两个量独占记：

step = 2·⌈log₂ n⌉  （上扫一趟 + 下扫一趟）

work = 2(n − 1) ≈ 2n  次加法（O(n)，与串行同阶）

对 `1..8` 跑上述上扫/下扫，得排他式 `[0,1,3,6,10,15,21,28]`，与参考排他前缀和完全一致；加法计数为 14 = 2(8−1)，印证 ≈2n 的工作量界。

**Hillis-Steele 步深低（log n）但费工（n log n）；Blelloch 工作省（2n）但步深翻倍（2 log n）。** 硬件核多、数据不大时用步高效版更快；核有限或数据大、怕浪费带宽时用工作高效版。真实 GPU 库（如 CUB/Thrust 的 scan）通常是"分块本地扫描 + 块间扫描 + 回加"的分层混合，且用装饰过的工作高效核，具体实现随版本演进，标 ⚙演进快·锚 CUDA 13.x（本机无 GPU·文档腿）。

#### 来源与时效
- 锚点：PMPP 4e Ch11 Prefix sum（Kogge-Stone=step-efficient、Brent-Kung=work-efficient、包含/排他、分段扫描）@4th ed 2022｜核实 2026-08-01。
- 锚点：Blelloch, "Prefix Sums and Their Applications"（CMU-CS-90-190, 1990）——work-efficient scan 与 up-sweep/down-sweep 一手来源，扫描作并行原语的经典论证｜核实 2026-08-01。
- 锚点：CS267（Spring 2024）scan/prefix-sum 讲义（Blelloch 树形扫描），交叉印证 work/step 界｜核实 2026-08-01。

## H-07.3 Histogram（直方图：原子操作与私有化）

### H-07.3.1 直方图为何难并行：多个线程写同一个桶

直方图统计每个元素落入哪个"桶"（bin）并计数，串行就是遍历数据、`hist[bin(x)]++`。并行化的困难不在读、在写：多个线程可能同时想给**同一个桶 +1**，这是一次"读-改-写"竞争——若不保护，两个 `++` 可能都读到旧值 5、各写回 6，丢掉一次计数（丢更新 lost update）。

对 20 个落在 4 个桶的整数，串行 `hist` = `[3,2,9,6]`，与 `numpy.bincount` 一致，作为并行版必须复现的正确基线。

最直接的并行修法是**原子操作**：把 `hist[b]++` 换成 `atomicAdd(&hist[b], 1)`，硬件保证读-改-写不可分割，绝不丢更新。正确性没问题，但当很多线程往少数几个热门桶猛加时，这些原子加会被硬件串行化，形成争用瓶颈——数据分布越偏、桶越少，越慢。原子操作的正确性根因（内存序、compare-and-swap）归 L4-05 并发，本报告只用其结论。

### H-07.3.2 私有化（privatization）与聚合（aggregation）

私有化是治直方图争用的主力手法：让**每个线程（或每个线程块）先各自维护一份私有的局部直方图**，各自随便加、互不争用；等各自算完，再把所有私有直方图**归约（相加）合并**成全局直方图。争用从"全体线程抢全局桶"降到"最后一次结构化合并"。

把 20 个数据切成两半，各自 `bincount` 得 `h1`、`h2`，`h1 + h2` = `[3,2,9,6]`，与全局直方图完全一致——这就是"私有累加 + 最后合并"的最小演示。

```
每线程/每块： local_hist[NBINS] = 0
遍历自己那份数据： local_hist[bin(x)]++      # 无争用
合并阶段： 对每个桶 b： atomicAdd(&global_hist[b], local_hist[b])   # 争用大幅减少
```

在 GPU 上，私有直方图放**共享内存**里（块内线程共享、访问快），块结束时才用原子加汇总到全局内存——把慢速全局原子的次数从"每个元素一次"降到"每个块每个桶一次"。当桶数太多、共享内存放不下私有副本时，退一步用少量副本或直接全局原子。另一个配套技巧是**聚合 / aggregation**：线程发现自己连续处理的元素落同一个桶时，先在寄存器里攒够计数再一次性原子加，减少原子次数（对高度局部化的数据尤其有效）。具体共享内存容量、原子吞吐随架构演进，标 ⚙演进快·锚 CUDA 13.x（本机无 GPU·文档腿·数值待核）。

## H-07.4 Convolution / Stencil（卷积 / 模板运算）

### H-07.4.1 卷积：邻域加权求和，天然数据并行

卷积用一个小滤波器（filter / kernel，此处 kernel 指卷积核，勿与 GPU kernel 混）在输入上滑动，每个输出点是"该点邻域元素乘以对应滤波器权重再求和"。一维形式：

out[i] = Σ_{k} in[i + k] · filter[k]

**每个输出点的计算彼此独立**，读若干输入、只写自己那一个输出，没有跨输出的写依赖——这是最"干净"的数据并行，直接一个线程算一个输出点即可。难点全在访存效率而非正确性。

对 5×5 随机图用 Laplacian 模板 `[[0,1,0],[1,-4,1],[0,1,0]]` 做 `scipy.signal.convolve2d`，内部点 (1,1) 的库结果与手算 `上+下+左+右−4·中` 在 1e-9 内吻合，确认邻域加权语义。

其一，**边界处理**——输出点在边缘时邻域越界，需选零填充（zero-pad）/ 复制边界 / 环绕，不同选择结果不同；其二，**卷积 vs 相关**——数学卷积要把滤波器翻转，很多深度学习"卷积"实际是不翻转的互相关，权重学出来就行、影响不大，但对照公式时要注意（本机 `convolve2d` 是翻转的真卷积）。

### H-07.4.2 滤波器复用、常量内存与分块（tiling）

卷积的性能核心是**数据复用**：相邻输出点的邻域大量重叠，同一个输入元素会被多个输出点读到（复用度约等于滤波器大小）。朴素实现让每个线程各自从全局内存反复读这些重叠元素，带宽浪费严重，算术强度低（回顾大主题2 Roofline：这类核常卡在访存带宽而非算力）。

PMPP Ch7 给的两招都在"减少重复的慢速全局访存"：其一，滤波器权重全体线程共用且只读、体积小，放 GPU 的**常量内存 constant memory**（有广播缓存，全 warp 读同一权重很快）；其二，**分块 tiling**——块内线程协作把"本块所有输出点用到的输入片"（含四周多出来的一圈 **halo / ghost cells 光环单元**）一次性搬进**共享内存**，之后邻域读都命中共享内存。tile 要比输出块大一圈（每边多 filter 半径个元素），这圈 halo 是分块卷积最容易写错的地方（边界索引、加载哪些光环）。

### H-07.4.3 Stencil（模板）：卷积的迭代近亲

模板运算（stencil）与卷积形状几乎一样——每个点由固定邻域模式加权更新——区别在语境：stencil 通常来自**偏微分方程的离散化**（如热方程、拉普拉斯方程），且往往**迭代很多轮**（时间步进），每轮用上一轮的整个网格算这一轮。上面那个 Laplacian 就是最常见的 2D 5 点模板。

并行结构与卷积同源（每点独立、分块进共享内存），但 stencil 多两个特点值得初学者知道。其一，**时间维依赖**：第 t+1 轮依赖第 t 轮，轮与轮之间要同步（一轮内并行、轮间串行），这正是大主题2 里 Amdahl 串行段的来源之一。其二，PMPP Ch8 强调 3D stencil 的**寄存器分块 / 线程粗化**——让每个线程沿一个维度串行推进、把该维相邻平面留在寄存器里复用，减少共享内存与全局访存。数据划分与光环交换在多机（MPI）上就是"通信-计算重叠"的经典战场（归大主题8）。GPU 具体收益数值本机无法测，标「文档腿·待核」。

- 锚点：PMPP 4e Ch7 Convolution（常量内存、tiling、halo/ghost cells、算术强度）与 Ch8 Stencil（3D、寄存器分块、迭代）@4th ed 2022｜核实 2026-08-01。
- 锚点：CS267（Spring 2024）结构化网格 / stencil 与 PDE 讲义，交叉印证迭代与光环交换｜核实 2026-08-01。
- 本机实证：scipy 1.17.1 `signal.convolve2d` Laplacian 模板内部点 = 手算 5 点差分（1e-9 内），确认邻域加权语义。
- ⚙演进快·锚 CUDA 13.x：常量内存/共享内存分块收益为 GPU 专属，本机无设备→「数值待核·文档腿」。

## H-07.5 Sorting（并行排序：基数与归并思想）

### H-07.5.1 并行基数排序：用扫描算出每个元素该去哪

基数排序（radix sort）不比较大小，而是**按位（或按几比特一组）分桶**，从最低位到最高位（LSD）逐轮稳定分配，扫完所有位就有序。串行每轮就是"数每个桶多少、算桶起点、把元素搬过去"。

玩具 LSD 十进制基数排序对 15 个 0–999 的整数，结果与 `sorted` 完全一致，确认逐位分桶的正确性。

它之所以是 GPU 排序的主力，关键在于**每一轮的并行化恰好用到扫描（H-07.2）**：对某一位，先算每个元素落哪个桶（比如 1 比特就是 0/1 桶），要把它们稳定地放到输出的正确位置，就需要知道"我前面有多少个和我同桶的元素"——这正是一次**排他式扫描**（对每个桶的标志位做前缀和）给出的写入偏移。于是"数桶 + 求偏移 + 散射写"整轮都能并行。

```
每一位（或几比特）一轮：
  1. 每个元素算出它的桶号（如取该位的值）
  2. 对每个桶做 exclusive scan → 得到每个元素的输出下标
  3. 按下标把元素稳定散射（scatter）到输出
  轮数 = 位数 / 每轮比特数（与数据规模 n 无关，是 O(k·n)）
```

其一，基数排序是 **O(k·n)**（k=位数/轮数），当 k 是常数时对整数近似线性，不受比较排序 O(n log n) 下界约束（因为它不做比较）；其二，**必须稳定**（同桶元素保持原相对序），否则低位排序会被高位轮打乱。

### H-07.5.2 并行归并排序：分块并行 + 归并组合

并行归并排序沿用分治骨架：把数组分成很多小段各自（并行地）排好，再两两归并、逐层合并成整体有序。它是"比较型"并行排序的代表，思想直观：底层大量小段可完全独立并行排序，越往上归并的段越大、可并行的归并对越少。

并行归并的真正难点在**单次归并如何并行**——把两个有序序列合成一个，串行是双指针 O(n)，但双指针本身是串行的（下一步依赖当前比较结果）。让多个线程分工去填输出的不同区段，就需要"每个线程能独立算出：我这段输出，分别对应 A、B 各自的哪一段"——这就是下一节的**协同秩 co-rank**。所以并行归并排序把问题归结到"并行单次归并"，而并行单次归并归结到 co-rank。GPU 与多核库里的高性能排序常是"基数（整数/定长键）+ 归并（通用/大数据分块合并）"的混合，随实现演进，标 ⚙演进快·锚 CUDA 13.x（本机无 GPU·文档腿）。

#### 来源与时效
- 锚点：PMPP 4e Ch13 Sorting（并行基数排序：用 scan 求散射偏移、稳定性、O(k·n)；归并排序与分块合并）@4th ed 2022｜核实 2026-08-01。
- 锚点：CS267（Spring 2024）并行排序讲义（基数 / 归并 / 采样），交叉印证"扫描算偏移"与比较下界｜核实 2026-08-01。
- 本机实证：Python/numpy 2.4.6 玩具 LSD 基数排序（15 个 0–999 整数）= `sorted`，确认逐位稳定分桶。
- ⚙演进快·锚 CUDA 13.x：库级混合排序实现随版本演进，本机无 GPU→「文档腿」。

## H-07.6 Merge（并行归并与协同秩 co-rank）

### H-07.6.1 单次归并的并行化困境

给两个已排序序列 A（长 m）、B（长 n），归并成一个长 m+n 的有序序列 C。串行双指针算法一步一比较、O(m+n)，但每一步的"取 A 还是取 B"依赖上一步——是一条串行链，步深 O(m+n)，无法直接并行。

手写双指针归并两个各 8 元素的有序数组，结果与 `numpy.sort(concatenate)` 完全一致，作为并行版必须复现的正确基线。

要并行，思路是**按输出切分**：把输出 C 均匀切成若干连续区段，让每个线程独立负责一段 `C[k0..k1)`。难点是——线程要填 `C[k0..k1)`，它得知道这段输出**分别来自 A 的哪一段、B 的哪一段**，而且不能靠"从头归并到 k0"（那又串行了）。答案是 co-rank 函数能 O(log) 地直接算出来。

### H-07.6.2 协同秩 co-rank：给定输出位置，反推 A/B 的分界

协同秩（co-rank）解决："输出 C 的第 k 个元素之前（C[0..k)），恰好用掉了 A 的前 i 个和 B 的前 j 个，问 i 是多少？"因为归并不增不减，必有：

i + j = k

且 i 是唯一使"A[0..i) 与 B[0..j) 归并后正好占满 C[0..k)"的分界，判据（元素互不越位）大致是：

A[i-1] ≤ B[j]   且   B[j-1] < A[i]

（边界处按空段处理）。给定 k，在 i 的可行区间上做**二分查找**即可 O(log) 求出 i，进而 j = k − i。于是每个线程拿到自己输出段的两端 k0、k1，各求一次 co-rank，就得到它要读的 `A[i0..i1)` 与 `B[j0..j1)`，然后**独立串行归并自己这一小段**，线程之间零依赖。

```
并行归并（每线程负责 C 的一段 [k0,k1)）：
  i0 = co_rank(k0, A, B);  j0 = k0 - i0
  i1 = co_rank(k1, A, B);  j1 = k1 - i1
  serial_merge(A[i0:i1], B[j0:j1]) -> C[k0:k1]      # 线程间互不依赖
```

**co-rank 把"串行的单次归并"变成"先 O(log) 定界、再各段独立并行归并"**，是并行归并排序（H-07.5.2）能扩展的关键零件。初学者别被判据吓到——记住直觉即可："输出走到第 k 步，一定是从 A、B 各拿了一部分，co-rank 就是二分找出那个分界点。" PMPP Ch12 还讲了分块版（tiled merge，把 co-rank 定界后的段搬进共享内存再归并），属性能篇。

#### 来源与时效
- 锚点：PMPP 4e Ch12 Merge（co-rank 函数定义、二分求分界、并行归并、tiled merge）@4th ed 2022｜核实 2026-08-01。
- 锚点：Siebert & Traff 等并行归并 co-rank 思想的通用表述，与 CS267 归并讲义交叉印证判据 `A[i-1]≤B[j] 且 B[j-1]<A[i]`｜核实 2026-08-01（判据不等式的"严格/非严格"取法各来源略有出入，取"稳定归并、A 优先"约定，边界以空段处理）。
- 本机实证：Python 双指针归并两个有序 8 元数组 = `numpy.sort(concatenate)`，作并行 co-rank 版的正确基线。

## H-07.7 Sparse matrix（稀疏矩阵：CSR 与 SpMV）

### H-07.7.1 稀疏存储与 CSR 格式

当矩阵绝大多数元素是 0（稀疏），存全部 n² 个数既浪费内存又浪费算力。稀疏格式只存非零元（nnz 个）及其位置。最常用的 **CSR（Compressed Sparse Row，按行压缩）** 用三个数组：

values：按行顺序排列的所有非零值（长 nnz）

col_index：每个非零值所在的列号（长 nnz）

row_ptr：长 (行数+1)，row_ptr[r] 是第 r 行第一个非零元在 values 里的下标；第 r 行的非零元就是 values[row_ptr[r] : row_ptr[r+1])

对 4×4 矩阵 `[[10,0,0,0],[0,20,0,0],[0,0,30,40],[50,0,0,60]]`，scipy 的 CSR 给出 `indptr=[0,1,2,4,6]`、`indices=[0,1,2,3,0,3]`、`data=[10,20,30,40,50,60]`、`nnz=6`——第 2 行（0 基）有两个非零（30 在列 2、40 在列 3），`indptr` 里 `4→6` 差 2 正好对上。

其一，**row_ptr 相邻两项之差 = 该行非零元个数**，这个"用前缀式指针数组定位每行数据"的套路本身就是排他扫描的产物；其二，CSR 适合"按行访问"，若要按列访问则用对应的 CSC（按列压缩），另有 COO（坐标三元组，好构造难计算）、ELL（每行补齐到等长，规整好并行但补零浪费）等格式，PMPP Ch14 会比较它们在 GPU 上的取舍。

### H-07.7.2 SpMV：稀疏矩阵-向量乘及其负载不均

⚙演进快·锚 CUDA Toolkit 13.x（GPU 部分本机无设备·文档腿）｜核实 2026-08-01

SpMV（Sparse Matrix-Vector multiply）算 y = A·x，是迭代解法（共轭梯度等，归 L1-03 线代）的内层热点。CSR 上每个输出 y[r] 只需该行的非零元与 x 对应分量的点积：

y[r] = Σ_{t = row_ptr[r]}^{row_ptr[r+1]-1} values[t] · x[col_index[t]]

对上面 CSR 矩阵与 `x=[1,2,3,4]`，`C @ x = [10,40,250,290]`，与稠密 `M @ x` 完全一致（第 2 行 `30·3+40·4=250`、第 3 行 `50·1+60·4=290`）。

最直接的并行是 **一线程一行（CSR scalar）**：线程 r 遍历自己行的非零元累加。正确、简单，但有两个 GPU 上的老大难。其一，**负载不均**：各行非零个数差异大（社交网络等幂律图尤甚），非零多的行拖慢整个 warp。其二，**访存不合并**：同一 warp 的相邻线程处理相邻行，它们同一时刻访问的 values 元素在内存里不相邻（各在自己行里推进），合并访问差。改法有 **一 warp 一行（CSR vector）**（一个 warp 协作点积一行、再 warp 内归约）、按行长分组、或改用 ELL/JDS/混合 ELL-COO 等更规整的格式来均衡与合并。哪种最优高度依赖矩阵的稀疏结构与硬件，PMPP Ch14 与库（cuSPARSE 等）随版本演进，标 ⚙演进快·锚 CUDA 13.x，本机无 GPU 的性能对比「待核·文档腿」。

#### 来源与时效
- 锚点：PMPP 4e Ch14 Sparse matrix computation（CSR/COO/ELL/JDS/混合、SpMV scalar vs vector、负载不均与合并访问）@4th ed 2022｜核实 2026-08-01。
- 锚点：CS267（Spring 2024）稀疏矩阵与 SpMV 讲义（格式取舍、迭代解法内核），交叉印证；↔ L1-03 线代（迭代解法收敛性另账）｜核实 2026-08-01。
- 本机实证：scipy 1.17.1 `csr_matrix`（indptr=[0,1,2,4,6]、nnz=6）SpMV = 稠密 `M@x` = `[10,40,250,290]`。
- ⚙演进快·锚 CUDA 13.x：scalar/vector/ELL 在具体架构的性能与库实现随版本变，本机无 GPU→「数值待核·文档腿」。

## H-07.8 Graph traversal（图遍历：并行 BFS）

### H-07.8.1 BFS 的并行结构：一层层铺开的前沿

广度优先搜索（BFS）从源点出发，先访问所有距离 1 的点、再距离 2 的、依此逐层扩展，可求各点到源的最短跳数。串行 BFS 用一个队列，但队列是串行结构。并行 BFS 改成**按层（frontier / 前沿）推进**：当前层是一批"上一轮刚发现的点"，同一层内所有点可**并行地**去看各自的邻居，把尚未访问的邻居收进"下一层前沿"，一层做完再做下一层。

对路径图 `0-1-2-3` 加一条 `0-4`，从 0 做分层 BFS，得各点层号 `{0:0, 1:1, 4:1, 2:2, 3:3}`——0 距离 0，1 和 4 距离 1，2 距离 2，3 距离 3，与手算最短跳数一致。

```
frontier = {source};  dist[source] = 0;  level = 0
while frontier not empty:
    next = {}                                  # 下一层
    for u in frontier   (并行):                 # 层内并行
        for w in neighbors(u):                  # 邻接常用 CSR 存
            if w 未访问:  dist[w] = level+1;  加入 next
    frontier = next;  level += 1                # 层间串行（隐式屏障）
```

图的邻接表在 GPU 上正是用 CSR 存（H-07.7）：`row_ptr` 定位每个点的邻居段，`col_index` 是邻居编号——图遍历和稀疏矩阵是同一副骨架的两种用法（BFS 一层 ≈ 一次"稀疏布尔矩阵 × 前沿向量"）。

### H-07.8.2 并行 BFS 的坑与方向优化

⚙演进快·锚 CUDA Toolkit 13.x（GPU 部分本机无设备·文档腿）｜核实 2026-08-01

并行 BFS 的正确性坑：多个当前层的点可能**同时发现同一个邻居**，若不保护会把它重复加进下一层、或重复标距离——需要用原子操作或"标记去重"（每个点用原子 compare-and-swap 抢占"我第一个发现它"）保证每点只入一次、距离只写一次。层间的隐式同步（一层全做完才进下一层）是并行 BFS 的串行瓶颈，图直径越大层数越多、越难加速。

性能上，PMPP Ch15 讲两种推进方向。**push（自顶向下 top-down）**：前沿里的点主动去更新邻居——前沿小的时候高效。**pull（自底向上 bottom-up）**：未访问的点反过来查"我的邻居里有没有在前沿的"，一旦找到一个即可停——当前沿很大（BFS 中段、大量点在同一层）时，pull 能避免海量重复检查而更快。**方向优化 BFS（direction-optimizing，Beamer 等）** 就是根据前沿大小在 push/pull 间自动切换，对社交网络这类小世界图提速显著。此外还有负载不均（度数差异大）问题，缓解手段与 SpMV 同源（按度分组等）。具体加速数值依赖图结构与硬件、库（如 nvGraph/cuGraph 后继）随版本演进，标 ⚙演进快·锚 CUDA 13.x，本机无 GPU 的性能「待核·文档腿」。

#### 来源与时效
- 锚点：PMPP 4e Ch15 Graph traversal（frontier-based BFS、CSR 邻接、push/pull 方向优化、去重与负载不均）@4th ed 2022｜核实 2026-08-01。
- 锚点：Beamer, Asanović, Patterson, "Direction-Optimizing Breadth-First Search"（SC 2012）——方向优化 BFS 一手；与 CS267 图算法讲义交叉印证 top-down/bottom-up 切换｜核实 2026-08-01。
- 本机实证：Python 分层 BFS（路径图 + 一分支）层号 = `{0:0,1:1,4:1,2:2,3:3}`，与手算最短跳数一致。
- ⚙演进快·锚 CUDA 13.x：GPU 去重原子、方向优化收益、图库实现随版本/图结构变，本机无 GPU→「数值待核·文档腿」。
