本主题讲的是同一件事的两面：GPU 有一套**分层的片上/片外内存**，越靠近计算单元越快但越小；而 GPU 的性能几乎完全取决于你**能不能喂饱**成千上万个并发线程。绝大多数 GPU 程序不是"算得慢"，而是"数据搬得慢"——它们是**访存受限（memory-bound）**的。因此这里的每一项优化，本质都在回答一个问题：怎样用更少、更规整的访存，换来更多的有效计算。

本机没有 GPU，下面涉及硬件行为的数值（延迟、带宽、事务大小、bank 数、warp 大小）全部来自官方文档与教材交叉核对，硬标"未验证·文档腿"；只有 tiling 与 privatization 的**思想**用 numpy 做了可复现的概念类比。

## 6.1 内存层级：global / shared / register / constant / local

### 6.1.1 五种内存空间与"越近越快越小"的层级

CUDA 把设备内存分成几种作用域和速度都不同的空间。按"离计算单元由远到近、由慢到快"大致排：**global（全局）** 和 **local（本地）** 在片外 DRAM，延迟最高、容量最大；**constant（常量）** 也在 DRAM 但有专门的只读缓存；**shared（共享）** 在片上、按线程块共享、延迟接近寄存器；**register（寄存器）** 最快、每个线程私有。CUDA C++ Programming Guide 明确给出这条延迟序：global/local/texture 延迟最大，其次 constant，再次 shared，最快是寄存器堆。

内存层级示意（作用域 / 位置 / 速度）：

```
register   ← 每线程私有，片上，最快最小（延迟 ~1 周期级）
shared     ← 每线程块共享，片上 SRAM，很快（软件管理的“缓存”）
constant   ← 所有线程只读，DRAM + 专用常量缓存
local      ← 每线程私有，但物理在片外 DRAM（寄存器放不下时的溢出地）
global     ← 所有线程可读写，片外 DRAM，容量最大、延迟最高
```

理解这套层级最好的类比是 CPU 的"寄存器 / L1 / L2 / 主存"，但有一个决定性区别：**shared memory 是"软件管理"的**。CPU 的 L1 缓存对程序员透明、硬件自动决定装什么；而 GPU 的 shared memory 要你**在 kernel 里显式声明、显式搬数据、显式同步**。这既是负担也是机会——正因为你能手动把热点数据钉在片上，才有了后面 6.3 的 tiling 优化。初学者常见的误解是把 shared memory 当成"自动加速的缓存"，其实不写 `__shared__` 声明和搬运代码，数据永远待在慢速 global memory 里。另一个易错点：register 和 local 都是"每线程私有"，名字上 local 听起来像"离得近"，其实它物理上在**片外 DRAM**，和 global 一样慢（见 6.1.5）。

### 6.1.2 全局内存 global memory

全局内存是 GPU 的"主存"：容量最大（现代卡从十几 GB 到上百 GB 量级，具体随卡型而定，待核到具体型号），所有线程都能读写，数据在整个 kernel 生命周期乃至跨多次 kernel 启动之间保持。它也是延迟最高的空间——一次访问要几百个时钟周期。host 端用 `cudaMalloc` 分配的、通过 `cudaMemcpy` 传进来的数据都住在这里。

因为容量大又是唯一能和 host 交换数据的地方，global memory 是几乎所有 kernel 的数据入口和出口，但它的高延迟正是性能瓶颈的根源。GPU 的对策不是"降低单次延迟"，而是**用海量并发线程把延迟藏起来**：当一个 warp 在等 global memory 返回时，调度器立刻切到另一个就绪的 warp 执行——这就是 6.4 占用率要保证"手上有足够多 warp 可切换"的原因。初学者要建立的核心直觉是：GPU 不怕访存慢，怕的是**没有别的活可干来掩盖这份慢**。因此对 global memory，两条优化主线贯穿本主题——(1) 让访问尽量**规整合并**（6.2），(2) 把反复用的数据**搬到片上**减少访问次数（6.3）。

### 6.1.3 共享内存 shared memory

共享内存是位于每个流多处理器（SM）片上的一小块高速 SRAM，**同一个线程块内的所有线程**都能访问它，生命周期与线程块相同。它的延迟比 global memory 低一两个数量级、带宽高得多，是 GPU 上做数据复用的关键工具。用 `__shared__` 关键字在 kernel 里声明，块内每个线程各搬一部分数据进来，再靠 `__syncthreads()` 保证"大家都搬完了"才开始用。

共享内存的价值在于它把"块内线程要反复读的公共数据"从慢速 global 提升到片上：一份数据搬进来一次，块内成百上千次读取都在片上完成。它是软件管理的暂存区（scratchpad），不是硬件缓存——你得自己规划放什么。容量很有限，每个 SM 的 shared memory 是几十 KB 到上百 KB 量级（随架构代际变，具体值待核到锚定架构），而且它和占用率相互挤占：一个块用的 shared memory 越多，SM 上能同时驻留的块就越少（见 6.4.2）。易错点有两个：一是忘了同步——搬数据和用数据之间不加 `__syncthreads()`，会读到别的线程还没写完的位置，结果随机错；二是把它当"全局共享"，其实它只在**块内**共享，不同块之间看不到彼此的 shared memory。

### 6.1.4 寄存器 register（及溢出到 local memory）

寄存器是最快的存储，每个线程**私有**一组寄存器，kernel 里普通的局部标量变量（`int i;` `float sum;`）默认就放在寄存器里，访问几乎零延迟。寄存器是 SM 上的稀缺资源：SM 有一个固定大小的寄存器堆，被同时驻留的所有线程瓜分。

寄存器的关键约束是"总量固定、按线程平分"。如果一个 kernel 每线程用很多寄存器，SM 上就放不下那么多线程，占用率下降（6.4.2 会展开这个权衡）。当线程需要的寄存器超过硬件所能给的，编译器会把一部分变量**溢出（spill）到 local memory**——而 local memory 物理上在片外 DRAM，于是"本该零延迟的局部变量"突然变成几百周期的慢访问，性能骤降。初学者常见的困惑是"我明明只用了几个变量为什么慢"——大数组、被取地址的变量、或寄存器压力过大触发的溢出，都会悄悄落到 local memory。诊断寄存器用量要靠编译器报告（如 `nvcc -Xptxas -v`），本机无 GPU 无法实测，此处仅陈述机制。

### 6.1.5 本地内存 local memory

"本地内存"这个名字有强烈误导性：它是**每线程私有**的没错，但物理位置在**片外 global DRAM**，因此速度和 global memory 一样慢，绝不是"离得近的快内存"。它用来存放放不进寄存器的每线程私有数据：寄存器溢出的变量、编译期无法用常量下标索引的私有数组、以及体积过大的自动变量。

理解 local memory 的要点就是记住"名字骗人、位置在远处"。它的存在是为了给寄存器兜底——寄存器不够时数据总得有地方放。所以优化上，凡是能避免 local memory 的就避免：减少每线程的私有数组、用编译期常量下标让小数组能进寄存器、控制寄存器压力别触发溢出。易错点正是被名字误导，以为把数据声明成线程"local"的就快了——恰恰相反，落到 local memory 往往是性能问题的信号。

### 6.1.6 常量内存 constant memory

常量内存是一块所有线程都能读、但**不能写**的空间，物理在 DRAM，但配有专门的**常量缓存**。它的性能特点很特殊：当一个 warp 里的**所有线程读同一个地址**时，这次访问会被广播（broadcast），一次就服务整个 warp，非常高效；但如果 warp 内线程读不同地址，访问会被串行化，反而变慢。常量内存容量小，典型上限 **64 KB**（用 `__constant__` 声明）。

它的最佳用武之地是"所有线程共享的、只读的、小的"参数——比如卷积核的权重、物理常数、查找表。PMPP 在卷积（Ch7）里就把滤波器系数放常量内存：卷积时同一位置的滤波器系数被大量线程同时读，正好命中"全 warp 读同一地址→广播"的甜区。初学者要抓住的判断标准是**访问模式一致性**：常量内存不是"只读就快"，而是"只读且大家读同一个值才快"；如果每个线程读常量数组里不同的元素，就享受不到广播优势，此时不如用别的方案。另一个易错点是 64 KB 的硬上限——大数据放不进常量内存。

## 6.2 访存合并（memory coalescing）

### 6.2.1 访存合并是什么

访存合并指的是：当一个 warp（32 个线程）同时访问 global memory 时，如果这 32 个线程的地址落在连续、对齐的一段，硬件能把它们**合并成尽量少的内存事务**一次性完成。CUDA Best Practices Guide 13.3 明确：对 compute capability 6.0 及以上的设备，一个 warp 的并发访问会合并成"服务该 warp 所有线程所需的 **32 字节事务**数目"。地址越集中，事务越少，有效带宽越高。

合并访问示意（一个 warp 的 32 个线程）：

```
合并（好）：  线程 0,1,2,...,31 依次访问 addr, addr+4, addr+8, ...
              → 地址连续对齐，一整段被少数几次 32 字节事务取走

不合并（差）： 线程 0,1,...,31 访问 addr, addr+128, addr+256, ...（大跨步）
              → 每个线程各触发一次事务，32 次访存只利用了每次事务的一小部分
```

理解合并的核心直觉是"内存按段搬运，不按字节搬运"。DRAM 每次读都是取一整段（如 32 字节），哪怕你只要其中 4 字节，剩下的也一起搬来了。如果一个 warp 的 32 个线程恰好把连续的一段全用上，这段搬运没有浪费；如果它们分散在很多段里，每段只用一点点，就要触发很多次事务、每次都浪费大半带宽。这就是为什么合并是 GPU 访存的头号优化。初学者最该记住的经验法则：**让相邻线程访问相邻内存**（线程 t 访问 `data[base + t]`），就能自然合并。

### 6.2.2 合并 vs 非合并访问模式

同样一段计算，索引方式不同，访存效率能差出好几倍。最常见的对比是"按行访问 vs 按列访问"二维数组，或"跨步（strided）访问"。合并的写法是让 warp 内连续 threadIdx 映射到连续的内存地址；非合并则是大跨步、错位、或每线程访问的地址间隔很大。

矩阵按 row-major 存储，`A[row][col]` 的内存地址随 col 连续。如果让线程索引 t 去访问 `A[t][fixed_col]`（按列走），相邻线程的地址相差一整行的宽度，完全不合并；反过来访问 `A[fixed_row][t]`（按行走），相邻线程地址连续，完美合并。易错点是把 CPU 的访存直觉照搬过来——在 CPU 单线程里"按行还是按列"影响的是**单个线程**的缓存局部性；在 GPU 里，关键是"**同一时刻一个 warp 的 32 个线程**的地址是否连续"，这是一个跨线程的空间维度，初学者最容易忽略。Best Practices Guide 还强调**对齐**：即使连续，如果起始地址没对齐到事务边界，也会多跨一个段、多一次事务，效率打折。

### 6.2.3 AoS vs SoA（数据布局对合并的影响）

数据结构的内存布局直接决定能否合并。**AoS（Array of Structures，结构体数组）** 把每个元素的各字段挨在一起存（如 `struct{float x,y,z;} p[N]`）；**SoA（Structure of Arrays，数组的结构体）** 把同名字段各自连续存（如 `float x[N], y[N], z[N]`）。


```
AoS:  x0 y0 z0 | x1 y1 z1 | x2 y2 z2 | ...   ← 一个元素的字段挨在一起
SoA:  x0 x1 x2 ... | y0 y1 y2 ... | z0 z1 z2 ...  ← 同一字段全部连续
```

差别在于"一个 warp 要用哪些数据"。GPU kernel 常是"每线程处理一个元素、且同一步只用某个字段"（比如都在更新 x 坐标）。SoA 下，32 个线程读 `x[0..31]` 地址连续→合并；AoS 下，32 个线程读各自结构体的 `x`，地址间隔一个结构体大小（还夹着用不到的 y、z）→跨步、不合并。所以 GPU 上普遍偏好 **SoA**。这和 CPU 面向对象编程"把一个对象的字段放一起"的习惯正好相反，是初学者从 CPU 转 GPU 最容易踩的布局坑。判断标准：看你的并行 kernel 在同一步里是否只用到部分字段——是，就用 SoA 让被用到的字段连续。

## 6.3 共享内存 tiling（分块）

### 6.3.1 tiling 的核心思想

Tiling（分块）是 GPU 上最重要的手写优化：把大数据切成能装进 shared memory 的小块（tile），由一个线程块协作**把一块数据从 global memory 搬进 shared memory 一次**，然后块内所有线程在片上高速地反复使用这块数据，用完再搬下一块。它把"每个线程各自反复读慢速 global"改成"大家合伙搬一次、片上共享读多次"，大幅减少 global memory 访问次数。

tiling 的动机可以从矩阵乘讲清。朴素矩阵乘里，计算 C 的每个元素要读 A 的一行和 B 的一列；相邻的输出元素会重复读大量相同的 A 行、B 列——同一份数据被从 global memory 反复取了很多次。tiling 的洞见是：一个线程块负责输出的一个子块（tile），这个子块用到的 A、B 数据是**共享**的，那就让块内线程协作把该 tile 需要的 A、B 小块一次性搬进 shared memory，之后子块内所有乘加都从片上读。数据复用度越高，省下的 global 访问越多。初学者要抓的直觉：tiling 不改变要做多少次乘加，它减少的是**同一份数据被从慢速内存搬运的次数**。

### 6.3.2 分块矩阵乘与 __syncthreads() 协作

分块矩阵乘是 PMPP 的经典范例。把 A、B、C 都切成 TILE×TILE 的块；线程块循环遍历 A 的一行 tile 和 B 的一列 tile，每一轮：块内线程协作把当前 A-tile、B-tile 搬进 shared memory，同步，然后每个线程用片上的这两块累加它负责的部分和，再同步，进入下一轮。

分块矩阵乘的骨架（示意）：

```
__shared__ float As[TILE][TILE], Bs[TILE][TILE];
float acc = 0;
for (each tile step along K dimension) {
    As[ty][tx] = A[...];      // 块内线程各搬一个元素进 shared
    Bs[ty][tx] = B[...];
    __syncthreads();          // 等全块搬完，再开始算
    for (k = 0; k < TILE; ++k)
        acc += As[ty][k] * Bs[k][tx];   // 全部从片上 shared 读
    __syncthreads();          // 等全块算完，再搬下一块
}
C[row][col] = acc;
```

两处 `__syncthreads()` 是正确性的命门：第一处保证"数据全搬完才开始算"，第二处保证"全算完才覆盖 shared memory 搬下一块"。漏掉任何一处都会读到脏数据或被提前覆盖，结果随机错。初学者第一次写 tiling，最常见的 bug 就是少一个同步、或把 tile 边界（当矩阵维度不是 TILE 整数倍时的越界）没处理好。TILE 大小的选择是权衡：越大复用越多，但占用的 shared memory 越多、能驻留的块越少（连到 6.4）。

### 6.3.3 tiling 为什么能加速：访存节省与算术强度

tiling 的收益可以量化为"每个从 global 搬来的数据被复用了几次"。朴素矩阵乘里每次乘加都伴随 global 访问，算术强度（每字节访存对应的运算量）很低，是典型访存受限。tiling 后，一块 TILE×TILE 数据搬进 shared 一次，被用于 TILE 次乘加，global 访问量近似降低为原来的 1/TILE，算术强度相应提高约 TILE 倍，程序从"访存受限"向"计算受限"移动。

用性能模型的语言说，tiling 把 Roofline 图上的工作点向右推（算术强度变大），从而能触到更高的性能上限。本机无 GPU，无法测 kernel 加速比；但 tiling 的**数学等价性**（重排访存顺序不改变计算结果）可以用 numpy 概念类比坐实——把 384×384 矩阵乘分成 64×64 的 tile 逐块累加，与整块矩阵乘结果完全一致：

```
tiling analog: max|tiled - ref| = 2.4e-13
tiling analog: results identical to full matmul: True
```

tiling 是**访存顺序的重排**，不是算法的近似，结果必须逐位（数值误差内）等于原始矩阵乘。易错点是误以为 tiling 会改变精度或结果——它不会；变的只有"数据在内存层级里被搬运的路径"。（本机 numpy 类比仅验证"分块不改结果"这一点，不代表 GPU 实测加速；GPU 加速幅度依赖具体架构与 TILE 选择，待核。）

## 6.4 占用率（occupancy）与 warp 分歧（divergence）

### 6.4.1 占用率的定义

占用率（occupancy）是一个 SM 上**活跃 warp 数**与该 SM **能支持的最大活跃 warp 数**之比。它衡量 SM 被"填满"的程度：

occupancy = 活跃 warp 数 / SM 支持的最大活跃 warp 数

占用率的意义要回到 6.1.2 说的"用并发掩盖延迟"。当一个 warp 因等待 global memory 而停顿时，SM 的调度器需要有**别的就绪 warp**可以马上切过去执行，才能把访存延迟藏住。占用率高，意味着 SM 上驻留的 warp 多、随时有活可切，延迟掩盖得好。占用率低（比如只有几个 warp），一旦它们都在等内存，SM 就只能空转。这就是为什么"提高占用率"常被列为首要优化方向之一。初学者要建立的直觉：占用率不是"CPU 利用率"，而是"SM 手上攒了多少可随时调度的 warp 来填延迟空隙"。

### 6.4.2 占用率的限制因素

一个 SM 能驻留多少 warp，受几种**资源**共同限制，取最紧的那个：(1) 每线程用的**寄存器**数——寄存器堆固定，每线程用得多，能驻留的线程/warp 就少；(2) 每块用的 **shared memory**——SM 的 shared memory 固定，每块用得多，能同时驻留的块就少；(3) **块大小与块数上限**——warp 大小是 32，块大小若不是 32 的倍数，最后一个 warp 会有线程被浪费；(4) SM 的**硬件上限**本身（最大驻留 warp/块数）。

这几个限制的相互挤占是 GPU 调优的核心张力。举例：一个 kernel 每线程用很多寄存器以减少重复计算，看似聪明，但寄存器压力可能把可驻留 warp 数压得很低、占用率崩掉，反而更慢；或者为了 tiling 用了很大的 shared memory tile，复用是提升了，但每 SM 只能放一两个块，warp 不够多、延迟藏不住。所以 tiling 的 TILE 大小、每线程寄存器、块大小是要联合调的，不能只顾一个。初学者的常见错误：只盯着"块开大一点线程多一点"，忽略了寄存器/shared memory 才是真正的天花板；以及块大小随手写成非 32 倍数（如 100），导致每块最后一个 warp 有线程空跑。具体的每 SM 最大 warp 数、寄存器数、shared memory 大小随 compute capability 变化（如某些架构每 SM 最多 64 驻留 warp / 2048 线程，随代际变），本报告不锚死具体数值，标待核·本机无 GPU 未验证。

### 6.4.3 warp 分歧（warp divergence）

由于 SIMT，一个 warp 的 32 个线程共用一个指令流、步调一致地执行同一条指令。当遇到依赖线程 ID 的分支（`if/else`、循环次数不同）导致同一 warp 内的线程要走**不同路径**时，就发生 warp 分歧：硬件只能**串行地**先执行走 if 的线程（其余暂时屏蔽），再执行走 else 的线程，两条路径的时间相加，warp 的有效并行度下降。

warp 分歧的直觉是"一个班一起上课，题目却因人而异"：老师（一个指令流）只能先讲 A 组的题、B 组干等，再讲 B 组的题、A 组干等，总时间是两组之和。所以分歧越严重，浪费越大——极端情况下 32 个线程走 32 条不同路径，几乎退化成串行。优化的方向是**让分支边界对齐到 warp**：尽量让"整个 warp 走同一条路径"，而不是 warp 内一半走一半不走。一个经典例子（PMPP Ch10 归约）：把"按线程 ID 奇偶分支"改成"按 warp 连续分段分支"，就能让前若干个 warp 整体活跃、后若干个 warp 整体空闲，而不是每个 warp 内都半死不活，从而减少分歧。初学者的易错点：以为"有 if 就一定慢"——不是，只要**同一 warp 内所有线程的分支判断结果一致**（比如分支条件按块或按 warp 粒度变化），就没有分歧代价；分歧只发生在 warp**内部**产生分叉时。

### 6.4.4 辨析：高占用率不等于高性能

一个重要的、反直觉的结论：占用率高**不保证**性能好，它只是"有能力掩盖延迟"的必要不充分条件。CUDA 官方与 CS267 都强调，过了某个"够用"的占用率阈值后，再往上提占用率往往没有额外收益；而且盲目追求高占用率（比如硬压寄存器用量）可能引入寄存器溢出到 local memory，反而变慢。

这里要破除的迷思是"占用率越高越快"。占用率的作用是**掩盖延迟**，一旦 SM 上的 warp 已经多到足够填满访存空隙，再多的 warp 也无事可做，收益饱和。真正决定性能的还是访存是否合并（6.2）、数据是否复用（6.3）、分歧是否受控（6.4.3）、以及算法本身的算术强度。初学者容易把占用率当成唯一的调优仪表盘，一味调到 100% 却发现没提速——正确的做法是把占用率提到"够用"，再回头解决真正的瓶颈（通常是访存）。所以占用率是"手段/指标"，不是"目标"。

## 6.5 原子操作（atomics）与 privatization

### 6.5.1 原子操作是什么

原子操作（atomic operation）是"读-改-写"三步作为一个**不可分割**的整体完成的操作，比如 `atomicAdd(&x, 1)`。当成千上万个线程可能同时更新同一个内存位置时，普通的"读出来、加一、写回去"会发生竞争——两个线程都读到旧值、各自加一、各自写回，结果只加了一次而不是两次。原子操作由硬件保证：一个线程完成整个读-改-写之前，别的线程对该位置的更新被排队，从而结果正确。

原子操作解决的是并行更新共享数据的**正确性**问题。最典型的场景是直方图（histogram）：很多线程扫描数据、都要给某个 bin 计数加一，多个线程可能命中同一个 bin，就必须用 `atomicAdd` 保证不丢计数。初学者要区分两件事：原子操作保证的是"这一次读改写不被打断"，它**不**保证多个原子操作之间的顺序，也不是"加锁整段代码"。用 numpy 串行类比可以看清直方图计数的正确目标（下面 6.5.3 会一并给出）。GPU 支持的原子操作有 add/sub/max/min/CAS 等，具体类型与支持的数据精度随架构演进（待核·本机无 GPU）。

### 6.5.2 原子操作的争用与串行化开销

原子操作正确，但**慢**——尤其在争用（contention）高时。如果很多线程同时对**同一个地址**做原子更新，硬件必须把这些更新排队、一个接一个地执行，这段就退化成串行，成为瓶颈。争用越集中（比如数据分布使大量线程都命中同一个 bin），串行化越严重。

理解这个开销的直觉是"一扇门只能一个人进"：原子操作把对某地址的并发更新变成了排队通行，门前排的人越多，等得越久。所以原子操作的性能强烈依赖**争用程度**：分散到很多不同地址的原子操作（每个地址争用低）代价小，全挤在少数几个地址上代价大。这直接引出下一节的优化——privatization，通过给每个线程/每个块一份私有副本，把"大家挤一个地址"拆成"各更新各的、最后再合并"，从根本上降低争用。初学者易错点：以为"用了原子操作就万事大吉"，忽略了它在高争用下会把并行程序拖成串行。

### 6.5.3 privatization（私有化）

Privatization（私有化）是降低原子争用的核心手段：不让所有线程去更新**同一份**全局数据，而是给每个线程（或每个线程块）一份**私有副本**，各自在私有副本上累加（争用极低甚至无争用），最后再把所有私有副本**归并**成全局结果。它把"高争用的全局原子"换成"低争用的局部累加 + 一次性合并"。

以直方图为例：不是让所有线程对全局的 8 个 bin 做 atomicAdd，而是把线程分组，每组维护自己的一份私有直方图，组内累加互不干扰，最后把各组私有直方图逐 bin 相加得到最终结果。本机用 numpy 串行类比坐实了"私有化后合并结果与直接累加完全一致"：

```
privatization analog: private-then-combine == serial ref: True
counts: [12576, 12543, 12552, 12508, 12524, 12477, 12329, 12491]
```

私有化不改变最终计数（合并后逐位等于全局累加），它改变的是"争用被分散了"。初学者要抓的直觉——把"很多人抢一个账本记账"改成"每人一个小本子各记各的、最后汇总"，汇总虽有额外一步，但记账阶段不再排队，整体快得多。易错点是忘了最后的合并步、或合并步本身又制造了新的高争用（合并也要设计成低争用/树形归并）。（numpy 类比仅验证"私有化不改结果"，GPU 上的实际加速幅度依赖争用程度与实现，待核·本机无 GPU。）

### 6.5.4 共享内存私有化与两级归约

在 GPU 上，privatization 常和 shared memory 结合成"两级"结构：先让**每个线程块**在自己的 shared memory 里维护一份私有直方图（块内线程用 shared memory 原子累加，比 global 原子快得多，且只在块内争用），块处理完后，再用少量 global 原子把每块的私有直方图**合并**进全局结果。这样绝大多数原子操作发生在快速的片上 shared memory 且争用范围仅限块内，只有最后合并少量地打到 global。

这套结构把 6.3（shared memory 复用）、6.4（占用率/块）、6.5（原子/私有化）串了起来，是 PMPP 直方图章节（Ch9）的核心优化路线，也是"访存优化 + 争用优化"协同的典范。它的收益来源有两层：一是把高延迟的 global 原子换成低延迟的 shared 原子，二是把全局争用缩小到块内争用。初学者需要注意的权衡：私有副本要占 shared memory，会挤占占用率（回到 6.4.2 的资源张力）；私有副本数（每块一份 vs 更细粒度）也要按争用和资源折中。这里没有唯一最优，取决于数据分布与硬件，具体调优结论待核·本机无 GPU 未验证。
