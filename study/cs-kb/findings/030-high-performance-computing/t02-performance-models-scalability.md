## 2.1 Amdahl 定律

### 2.1.1 加速比与 Amdahl 定律公式

Amdahl 定律回答一个问题：在**问题规模固定**的前提下，把程序中一部分工作并行化、再增加处理器，整体能快多少。设程序里可并行的工作占比为 p（那么串行、无法并行的占比是 1−p），用 N 个处理器执行，则相对单处理器的加速比为

S(N) = 1 / ((1 − p) + p / N)

分母的第一项 (1−p) 是永远串行的部分，不随 N 缩短；第二项 p/N 是可并行部分被 N 个处理器均摊后的时间。把 N 推到无穷大，p/N → 0，得到加速比的天花板

S(∞) = 1 / (1 − p)

这条上限是 Amdahl 定律最著名的结论：只要有一小段代码串行，无论堆多少处理器，加速比都被这段串行占比死死卡住。

对初学者，最好的直觉是"木桶效应"。把一次执行想成一段固定长度的路：可并行的路段可以让很多人分着跑、越跑越短，但串行路段只能一个人走、长度不变。人再多，总时间也不会短过"串行路段那一截"。举个数：可并行占比 p=0.95（已经很高了），代入公式，N=8 时 S≈5.93、N=∞ 时 S=20；p=0.99 时 N=∞ 才到 100。这说明"最后那 1% 串行"就把上限从无穷拉到了 100 倍。本机用 numpy 代入公式核对了这几个点（p=0.95：S(2)=1.905、S(8)=5.926、S(∞)=20.00；p=0.99：S(∞)=100.00），与手算一致。

一个常见误读是把 p 当成"CPU 使用率"或"跑得快的时间比例"——它不是，它是**工作量**（或串行执行时间）中可被并行化的那一份占比，要在单处理器基线上度量。另一个坑是忽略"1−p 里藏了什么"：初始化、I/O、进程间同步、无法拆分的依赖链都算串行开销，真实的 1−p 往往比直觉大。

### 2.1.2 串行瓶颈与"优化谁"的启示

Amdahl 定律的实践价值不在算加速比本身，而在它告诉你**该优化哪一段**。把公式换个角度看：当 N 很大时，总时间趋近于串行部分的时间，可并行部分再怎么加速对总时间的贡献都会饱和。所以当你已经投入很多处理器后，继续优化可并行部分收益递减，真正的瓶颈是那段串行代码——想再快就得设法缩小 1−p 本身。

这正是"收益递减律（law of diminishing returns）"在并行里的体现，Hennessy & Patterson 把 Amdahl 定律作为体系结构设计的一条根本原则来讲：改进只作用于一部分执行时间，整体收益受限于该部分的占比。一个最小例子：某程序 90% 可并行、10% 串行（p=0.9）。你花大力气把并行部分加速到理论极限（p/N→0），整体也只能到 1/(1−0.9)=10 倍；但如果转而把串行部分砍掉一半（串行占比从 10% 降到 5%，p 升到 0.95），上限立刻从 10 倍抬到 20 倍。同样的工程投入，用在串行瓶颈上翻倍见效。

初学者易踩的坑是"盲目加核"：看到程序慢就申请更多处理器，却没先量串行占比。Amdahl 定律给的纪律是——先测 1−p，它决定了你加核的天花板在哪，超过某个 N 之后加核几乎白费。

### 2.1.3 "固定问题规模"这个前提

Amdahl 定律有一个常被忽略却决定性的假设：**问题规模不变**。它问的是"同一个任务，用更多处理器能快多少"，因此它天然对应后面会讲的"强扩展（strong scaling）"场景——工作量固定、只加处理器。

理解这个前提很重要，因为它既是 Amdahl 定律的适用边界，也是它显得"悲观"的根源。现实中人们买更大的机器，往往不是为了把老问题跑得更快，而是为了在相同时间里解**更大**的问题（更细的网格、更多的粒子、更大的模型）。当问题规模可以随处理器增长时，Amdahl 的固定规模假设就不成立了——这正是下一节 Gustafson 定律要修正的地方。所以不要把"S(∞)=1/(1−p) 很小"直接读成"并行没前途"；它只说明"在这个固定问题上，靠加核提速有天花板"。

## 2.2 Gustafson 定律与强扩展 / 弱扩展

### 2.2.1 Gustafson 定律

Gustafson 定律（1988，又称 Gustafson–Barsis 定律）从与 Amdahl 相反的假设出发：不是固定问题规模，而是**固定执行时间、让问题规模随处理器数增长**。它的观察是——实践中大机器用来解大问题，可并行的工作量会随规模一起变大，而串行部分（初始化、加载等）大致恒定。设在并行系统上测得的执行里串行占比为 s、可并行占比为 p（s+p=1），用 N 个处理器，则相对"同样这份放大后的工作交给单处理器要花的时间"的加速比（scaled speedup）为

S(N) = s + p · N

等价地写成

S(N) = N − s · (N − 1)

这条式子是"乐观"的：加速比随 N 近似线性增长，斜率是可并行占比 p。本机代入 p=0.95（s=0.05）核对：N=2/4/8/16 时 S=1.95/3.85/7.65/15.25，确实接近线性，与公式吻合。

关键直觉在"你在哪测占比"。Amdahl 在**串行基线**上测 p 并固定总工作；Gustafson 在**并行执行**上测占比并让工作随 N 放大。同一个 5% 串行，在 Amdahl 里是"总工作的 5%、拖住无穷加速"，在 Gustafson 里是"每次运行固定花掉 5% 时间、其余 95% 时间处理越来越大的问题"，于是加速比能随 N 一路涨。两者不是谁对谁错，而是回答了两个不同的问题。初学者最容易混的就是把两式的 p 当成同一个量——它们的定义基准不同，不能直接互换。

### 2.2.2 强扩展 vs 弱扩展

这是并行性能里最重要的一对术语，直接对应上面两条定律。

强扩展（strong scaling）：**问题规模固定**，增加处理器数，看总时间怎么缩短。它衡量"同一个任务能不能靠加核跑得更快"，理论天花板由 Amdahl 定律给出。理想情况是 N 倍处理器带来 N 倍加速，但串行部分和并行开销会让它偏离理想，且 N 越大偏得越多。

弱扩展（weak scaling）：**每个处理器上的工作量固定**（即总问题规模随处理器数成比例放大），看总时间能不能保持大致不变。它衡量"处理器和问题一起变大 N 倍，是否还能在差不多的时间里算完"，对应 Gustafson 的视角。理想弱扩展是时间恒定（曲线水平）。

你关心"把手头这个固定任务加速"就看强扩展；你关心"用更大的机器解更大的问题"就看弱扩展。一个最小例子——2D 热传导模拟：强扩展是网格 1000×1000 固定，从 1 核加到 100 核，看一步迭代的时间；弱扩展是每核负责 100×100 子网格，1 核跑 100×100、100 核跑 1000×1000，看每步时间是否持平。易错点：报告"扩展性好"时不写清是强还是弱，会误导——很多问题弱扩展漂亮但强扩展很快饱和（因为固定规模下通信/串行占比随 N 上升）。CS267 在性能分析里明确要求区分并分别画曲线。

### 2.2.3 两条定律的分歧与调和

表面看 Amdahl 说"加速有硬上限"、Gustafson 说"加速能近线性增长"，像是矛盾。它们的分歧点只有一个：**问题规模是否随处理器增长**。Amdahl 固定规模（强扩展），得出上限 1/(1−p)；Gustafson 放大规模（弱扩展），得出 S≈N。二者其实描述同一物理现实的两种使用方式，用不同的实验协议就会看到不同的曲线，并不冲突。

调和的说法（多来源一致）：如果串行部分是**绝对时间恒定**、可并行部分随规模线性增长，那么随着问题变大，串行占比 1−p 会趋于 0，Amdahl 的上限本身就被推高——两条定律在"规模可增长"这一假设下是一致的。反过来，若串行部分也随规模增长，弱扩展同样会恶化。所以真正决定扩展性的不是"信哪条定律"，而是"你的串行/通信开销随问题规模和处理器数怎么变"。这也是为什么实践中要同时报强扩展和弱扩展两条曲线，而不是只引用一条定律下结论。

## 2.3 加速比、效率与可扩展性度量

### 2.3.1 加速比与效率

加速比（speedup）是并行性能的基本度量，定义为串行执行时间比上并行执行时间

S(N) = T(1) / T(N)

其中 T(1) 是单处理器时间、T(N) 是 N 个处理器时间。理想（线性）加速比是 S(N)=N。效率（efficiency）把加速比除以处理器数，衡量每个处理器被用得有多充分

E(N) = S(N) / N = T(1) / (N · T(N))

E=1（或 100%）表示完美线性加速、处理器零浪费；E 越低说明并行开销（通信、同步、负载不均、串行部分）吃掉的比例越大。

直觉上，加速比回答"快了几倍"，效率回答"这些处理器有没有被浪费"。两者要一起看：加速比可能随 N 一直涨，但效率往往随 N 下降——因为并行开销随处理器增多而累积。本机用 Amdahl p=0.95 代入核对了这种"涨速但掉效率"：N=2 时 S=1.905、E=0.952；N=4 时 S=3.478、E=0.870；N=8 时 S=5.926、E=0.741。加速比在涨，效率却从 95% 掉到 74%。易错点：只报加速比不报效率会掩盖浪费——16 核拿到 8 倍加速听着不错，但效率只有 50%，一半算力空转。

一个定义上的讲究：T(1) 该用"最快的串行算法"还是"并行算法退化到单核"？规范做法（CS267/教材）是用**最优串行算法**做基线，否则会高估加速比。用并行版跑单核当基线，会把并行版自带的开销也算进 T(1)，让加速比虚高。

### 2.3.2 可扩展性度量：强扩展效率、弱扩展效率与等效率

"可扩展性"不是单个数字，而是看这些度量随 N（和问题规模）如何变化的趋势，常用三种角度。

第一个角度是强扩展效率，它在问题规模固定时看 E(N)=T(1)/(N·T(N)) 随 N 的下降有多快。下降越慢、扩展性越好，理想是保持在 1 附近。

第二个角度是弱扩展效率，它让每核工作量固定、总规模随 N 放大，度量为

E_weak(N) = T(1) / T(N)

这里 T(1) 是单核跑单份工作、T(N) 是 N 核跑 N 份工作的时间；理想弱扩展下二者相等、E_weak=1（时间不随 N 增长）。注意弱扩展效率的公式和强扩展不同——分母没有 N，因为工作量已经随 N 放大了。

第三个角度是等效率（isoefficiency），它更进阶但很有用，回答"要维持某个固定效率，问题规模需要随处理器数增长多快"。如果只需缓慢增大问题规模就能保持效率，系统"可扩展性好"；如果规模必须爆炸式增长才能压住效率下滑，则可扩展性差。它把"效率"和"规模增长速度"绑在一起刻画，比单看一条曲线更能说明系统本质。

强扩展效率看"固定问题加核会不会浪费"，弱扩展效率看"问题和机器一起长大能不能保持时间"，等效率看"要不掉效率、问题得长多快"。

### 2.3.3 度量陷阱：超线性加速、基准选择与并行开销

有几个反直觉现象和常见误用，初学者要能识别。

先说超线性加速（superlinear speedup）。偶尔会测到 S(N)>N（效率>100%），这不违反物理，最常见的真实原因是**缓存/内存效应**——N 个处理器合起来的缓存更大，数据放得下缓存后每核访问更快，于是总时间比"线性预期"还短；搜索类问题里某进程提前找到解也能造成表观超线性。但更多"超线性"是度量错误：T(1) 基线选得太差（用了低效串行算法或让单核跑内存换页）。看到超线性，先怀疑基线。

再说基准选择。如 2.3.1 所述，T(1) 必须是合理的最优串行实现，否则加速比失去意义；跨机器、跨规模比较时还要固定问题规模定义和输入。

最后是并行开销。真实 T(N) 里含有通信、同步/屏障、负载不均、以及为并行付出的额外计算。这些开销通常随 N 增长，是效率随 N 下降的根本原因，也是 Amdahl"串行部分"在实测里的具体来源。报告扩展性时应说明测的是强还是弱扩展、基线是什么、跑了几次取什么统计量——否则数字不可比。

## 2.4 Roofline 模型与算术强度

### 2.4.1 算术强度（arithmetic intensity）

算术强度是刻画一段计算"访存密集还是计算密集"的核心量，定义为该计算执行的浮点运算数除以它从内存搬运的字节数

I = FLOPs / Bytes

单位是 FLOP/Byte。I 小意味着每搬一个字节只做很少运算——瓶颈在内存带宽（memory-bound）；I 大意味着每个字节被反复参与很多运算——瓶颈在算力（compute-bound）。

直觉是"数据搬一次能榨出多少计算"。以浮点向量加法 c=a+b（n 元）为例：读 a、b 各 n 个、写 c 共 3n 个数、做 n 次加法，若 fp64 每数 8 字节，I≈n/(3n·8)=1/24≈0.04 FLOP/Byte——极低，纯带宽受限。对比 n×n 矩阵乘：约 2n³ 次浮点运算，若数据只需最少地各进出一次，字节量约 3n²·8。本机对 n=1024 估算：FLOPs=2.147e9、最小字节=2.517e7、I_max≈85 FLOP/Byte——远高于向量加，理论上是计算受限。易错点：矩阵乘的算术强度**依赖实现**——朴素实现反复从内存读数据、有效 I 远低于这个理论上界；只有做了分块（tiling）让数据留在缓存/寄存器复用，实测 I 才接近上界。所以算术强度分"算法固有的上界"和"具体实现达到的值"，别把二者混为一谈。

### 2.4.2 Roofline 模型

Roofline 模型（Williams、Waterman、Patterson，2009）用一张对数-对数图，把"某内核在给定硬件上到底能跑多快"直观地框出来。横轴是算术强度 I（FLOP/Byte），纵轴是可达性能 P（FLOP/s）。硬件由两个上限刻画：峰值算力 π（FLOP/s）和峰值内存带宽 β（Byte/s）。某内核的可达性能上界是二者取小

P(I) = min(π, β · I)

画出来是一条"屋顶"折线：左半段是斜率为 β 的斜屋顶（带宽受限区，性能随 I 线性上升），右半段是高度为 π 的平屋顶（算力受限区，性能被峰值算力压平）。两段交点处的算术强度

I_ridge = π / β

称为脊点（ridge point）。内核的 I 落在脊点左边就是内存受限、落在右边就是计算受限。

可以把带宽想成"进料速度"、算力想成"加工速度"。如果每个字节要做的运算少（I 小），机器再能算也得等数据进来——被进料速度卡住（斜屋顶）；如果每个字节要做很多运算（I 大），进料够快、瓶颈变成加工速度（平屋顶）。Roofline 的价值是一眼看出"我这段代码离硬件上限还有多远、卡在带宽还是算力"。一个要记住的边界是，Roofline 给的是**上界**，实测点通常落在屋顶之下——差距来自没做到访存合并、缓存复用差、指令级并行不足等，模型本身不预测你一定能到屋顶。

### 2.4.3 用 Roofline 判断优化方向

Roofline 最实用的地方是把"我该优化什么"变成看图定位。把内核的实测性能点画在图上（横坐标是它的算术强度、纵坐标是实测 FLOP/s），位置就给出方向。

若点落在斜屋顶下方（内存受限区）：瓶颈是带宽，优化方向是**提高算术强度或改善访存**——分块复用数据、改数据布局提升缓存命中、减少冗余读写；单纯增加算力单元没用。若点落在平屋顶下方（计算受限区）：瓶颈是算力利用，优化方向是**提升计算效率**——用向量化/SIMD、更好的指令并行、更充分占用计算单元。若点已经贴着屋顶：这段代码在当前算法下已接近硬件极限，再抠收益有限，该考虑换算法（改变 I 本身）。

稠密矩阵乘朴素实现常落在内存受限区（有效 I 低），做共享内存/缓存分块把 I 抬上去，点会沿斜屋顶右移并上升，直到越过脊点进入计算受限区——这正是分块优化"从带宽墙走向算力墙"的可视化。

在 GPU 上 Roofline 同样适用，但硬件的 π、β 以及多级带宽（如显存带宽 vs 片上共享内存带宽）会画出多条屋顶线，且这些峰值数值随 GPU 代次和工具链更新变化。⚙演进快·锚版本：GPU Roofline 相关的峰值算力/带宽数值与分析工具（如随 CUDA Toolkit 13.x 提供的性能分析器）请以对应硬件白皮书与工具当次输出为准，本报告不引用具体 GPU 的峰值数值（本机无 GPU，属文档腿）；具体设备数值标「待核」，不凭记忆填。核实 2026-08-01。
