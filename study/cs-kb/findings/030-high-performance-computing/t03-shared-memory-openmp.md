## H-03.1 fork-join 模型与 parallel for

### H-03.1.1 共享内存并行的前提：一个进程、多个线程、一片共享地址空间

共享内存并行指的是：一个进程内启动多个执行线程，这些线程运行在同一个（对它们透明的）共享地址空间里，任何线程都能直接读写同一个全局变量、同一个数组，无需显式发送数据。OpenMP 就是为这种模型设计的一套"编译指示 + 运行时库 + 环境变量"标准：你在普通 C/C++/Fortran 串行代码上加 `#pragma omp ...` 指示，编译器（如 gcc `-fopenmp`）据此生成多线程代码。

这和分布式内存（MPI，本课大主题4）是两种根本不同的世界，初学者一开始就要分清。分布式内存里每个进程有自己独立的内存，想共享数据必须"发消息"显式拷贝；共享内存里数据天然可见、零拷贝，代价是"谁都能改同一个变量"带来的竞争风险。共享内存并行的天然适用场景是单台多核机器（本机 4 核就是一个共享内存节点）；一旦跨机器，内存不再共享，就得换成消息传递。可以先记一句对照：**共享内存省了拷贝、欠了同步；分布式内存省了同步、欠了拷贝。**

### H-03.1.2 fork-join 执行模型

OpenMP 的执行模型叫 fork-join。程序启动时只有一个线程在跑（规范称"initial thread / 初始线程"，也常叫主线程 / primary thread）。当执行流遇到一个并行构造时，主线程"分叉"（fork）出一队额外线程，与它一起组成一个线程团队（team），团队里每个线程都执行这个并行块的代码；到并行块末尾，所有线程在一个隐式屏障处"汇合"（join），除主线程外的其它线程停止，程序又回到单线程状态继续往下走。

示意（一次 fork-join 的形状）：

```
串行 ──▶ [遇到 #pragma omp parallel]
          ├─ 线程0(主) ─┐
   fork ──┼─ 线程1 ─────┤  各线程并行执行并行块
          ├─ 线程2 ─────┤
          └─ 线程3 ─────┘
          [隐式 barrier: 全部到齐] ── join ──▶ 只剩主线程 ──▶ 串行继续
```

这个模型的直觉是"张开-收拢"：串行段像一根单线，并行段像临时撑开的一把扇子，用完收回。一个程序可以有很多次 fork-join（每个并行块一次），并行块之间又回到串行——这正好对应大主题2 Amdahl 定律里"串行段 + 并行段"的结构：那些收拢回单线程的部分就是串行段，撑开扇子的部分才被多核加速。初学者最容易误以为"整个程序从头到尾都是多线程"，其实 OpenMP 默认只在你标注的并行块里才是多线程，块外仍是单线程。术语提醒：新版规范（5.1 起）把过去的 "master"（主线程/master 构造）改称 "primary"，master 仍保留但已废弃（deprecated），读老资料会看到 master 一词。

### H-03.1.3 parallel 构造与线程团队

创建团队、真正"分叉出线程"的是 `parallel` 构造，它是 OpenMP 里唯一开启并行的构造，其它并行特性（分循环、分任务）都必须在它内部才起作用。

```c
#pragma omp parallel num_threads(4)
{
    // 这段代码被团队里每个线程各执行一遍（默认 4 个线程 → 执行 4 遍）
    int id = omp_get_thread_num();   // 本线程编号 0..num-1，主线程恒为 0
    int n  = omp_get_num_threads();  // 团队线程数
}
```

光有 `#pragma omp parallel`，块里的代码是**每个线程都完整跑一遍**（这叫复制执行 / replicated），而不是"自动被分摊"。团队线程数由几层来源决定，优先级从高到低大致是：构造上的 `num_threads` 子句 > 运行时 `omp_set_num_threads()` > 环境变量 `OMP_NUM_THREADS` > 实现默认（通常取可用核数）。本机实测默认 `omp_get_max_threads()` 返回 4（等于 4 核，libgomp 默认拿满核数）。所以要真正"把一个循环的迭代分给不同线程去干"，需要下一节的 worksharing 构造，而不是只靠 `parallel`。

### H-03.1.4 worksharing-loop：parallel for 如何分配迭代

要把一个 for 循环的迭代分摊给团队里的线程，用 worksharing-loop 构造 `#pragma omp for`（它必须位于某个 `parallel` 区域内）。常把两者合写成组合构造 `parallel for`，一行同时开团队 + 分循环：

```c
#pragma omp parallel for
for (long i = 0; i < N; i++) {
    a[i] = b[i] + c[i];   // N 次迭代被切成若干段，分给不同线程并行执行
}
```

它的语义是：把 N 次迭代按某种调度策略（见 H-03.4.3）划分成若干块，分配给团队的各线程，每个线程只跑分到的那部分迭代——所以总迭代次数不变，只是被并行摊开。这要求循环是 OpenMP 认可的"规范形式"（迭代次数在进入循环时可确定、迭代之间没有会导致竞争的数据依赖），否则并行化会得错误结果。最常见的初学者错误就是把一个"后一次迭代依赖前一次结果"的循环（如 `a[i]=a[i-1]+...`）直接加 `parallel for`——迭代被打乱分到不同线程后依赖被破坏，结果错乱。判断能否直接并行化的第一问永远是：**各次迭代能不能任意乱序、并发地跑而互不影响？** 循环的迭代变量 `i` 默认是每个线程私有的（否则大家共用一个 `i` 立刻就乱），这是规范专门规定的默认私有项（见 H-03.2.2）。

### H-03.1.5 隐式屏障、nowait 与版本坐标

worksharing-loop 和 parallel 区域末尾默认都有一个**隐式屏障**（implicit barrier）：所有线程必须都跑到这里、彼此等齐，才一起往下走。它保证"循环全部算完，后面依赖结果的代码才开始"，是正确性的重要保障。可以用 `nowait` 子句去掉 worksharing 循环末尾的隐式屏障，让先算完的线程不必等别人、直接去干下一段——省掉等待开销，但只有在"后面那段确实不依赖本循环的全部结果"时才安全。

```c
#pragma omp parallel
{
    #pragma omp for nowait      // 去掉本循环末尾隐式 barrier
    for (int i=0;i<N;i++) x[i]=f(i);
    // 先算完的线程不等其它线程，直接进入下面（须确认无依赖才安全）
}
```

版本坐标（⚙演进快·锚 OpenMP 6.0，核实 2026-08-01）：OpenMP 主要版本节点为 3.0（2008，引入 task）、4.0（2013，引入 SIMD 与 `target` 设备卸载）、4.5（2015）、5.0（2018-11）、5.1（2020-11，master→primary 更名）、5.2（2021-11）、6.0（2024-11 定稿，当前正式版）。本报告所有语义锚定 6.0 官方规范 PDF；6.0 之后官方以技术报告（TR）形式给 6.1 的预览，编号与发布日期请以 openmp.org 为准（约 2025-11，待核）。fork-join、`parallel`、worksharing-loop、reduction 这些核心语义在 3.x 以来长期稳定，不随小版本漂移，初学者不必担心版本差异。

## H-03.2 数据竞争、共享/私有变量、归约子句

### H-03.2.1 数据竞争是什么，为什么共享内存并行天然有此风险

数据竞争（data race）指：两个或更多线程并发访问同一个内存位置、其中至少有一个是写，且没有任何同步来给这些访问定序。有数据竞争的程序其结果是不确定的（在 C/C++ 语言层面属未定义行为）——同样的代码同样的输入，这次对、下次错，取决于线程碰巧怎么交错。

为什么共享内存并行天生容易踩？因为线程共用一片内存，`sum += 1` 这种看着"一步"的操作，机器上其实是"读 sum → 加一 → 写回 sum"三步。两个线程同时做，可能都读到旧值 10、各自算成 11、都写回 11——本该 12 却成了 11，一次更新"丢了"。这就是经典的丢失更新（lost update）。

```
线程A: 读sum(=10) ──── 算11 ──── 写sum=11
线程B:        读sum(=10) ── 算11 ──────── 写sum=11   ← 两次+1只涨了1
```

**"并行跑出来的结果这次对"不代表代码对**——竞争是概率性的，可能跑一百次对九十九次，偏偏上生产环境那次错。所以对付竞争不能靠"多跑几次看着没错"，只能靠语言/OpenMP 提供的机制从根上消除共享写冲突（下面的私有化与 reduction，或 `atomic`/`critical` 同步）。本报告只把竞争讲到"为什么必须消除"这一层；无锁、内存序、happens-before 等正确性深层机制归 L4-05 并发。

### H-03.2.2 默认数据共享属性

在 OpenMP 里，进入并行区域后，每个变量要么是**共享的**（shared，所有线程看同一份、同一地址）要么是**私有的**（private，每个线程有自己独立的一份副本）。规范给了默认规则，初学者必须记牢，因为绝大多数竞争 bug 都源于"以为私有其实共享"：

- 在并行区域**之前就已声明**、以及具有静态存储期的变量 → 默认 **shared**。
- worksharing-loop 所关联循环的**迭代变量** → 默认 **private**（否则多个线程共用一个 `i` 立刻乱套）。
- 在并行区域**内部声明**的（自动存储期）局部变量 → **private**（每个线程自己栈上一份）。

一个强烈推荐的防错习惯是给 `parallel` 加 `default(none)` 子句：它强制你对每个变量显式声明是 shared 还是 private，编译器会把漏标的变量报错，逼你想清楚每个变量该怎么处理。最典型的坑是"在循环外声明的临时变量 `tmp`"——它默认 shared，于是所有线程往同一个 `tmp` 里乱写，结果错乱；正确做法是把它标成 `private(tmp)` 或干脆在循环体内声明。

### H-03.2.3 private / firstprivate / lastprivate / shared 子句

data-sharing 子句让你显式指定变量的共享属性，覆盖默认规则：

```c
#pragma omp parallel for \
        shared(a) private(tmp) firstprivate(base) lastprivate(last)
for (int i=0;i<N;i++){ tmp = a[i]+base; last = tmp; a[i]=tmp; }
```

- `shared(x)`：所有线程共用同一个 `x`（同一地址）。对它并发写就有竞争风险，需自己保证同步。
- `private(x)`：每个线程一份独立的 `x`，进入区域时**未初始化**（是全新的、不继承外面的值），退出后外面的原变量也不受影响。初学者常犯的错是以为 private 变量会自动等于外面的值——不会。
- `firstprivate(x)`：像 private，但每个线程的副本**进入时用区域外的原值初始化**。适合"需要以外部初值起步、但各线程各改各的"。
- `lastprivate(x)`：像 private，但退出时把"顺序意义上最后一次迭代"（相当于串行执行时的最后一次）算出的值**写回**外部原变量。适合"循环结束后还想拿到最后一轮的结果"。

这四个子句加上 reduction，基本覆盖了共享内存并行里"每个变量该怎么处理"的全部日常需求。记忆钩子：private 是"空白副本"、firstprivate 是"带初值的副本"、lastprivate 是"副本 + 把末轮值带回家"、shared 是"大家共用一份（当心竞争）"。

### H-03.2.4 reduction 子句：私有副本 + 合并

归约（reduction）是共享内存并行里出现频率最高的模式：把很多迭代的结果"累"成一个值（求和、求积、求最大最小、逻辑与或）。直接让所有线程往同一个 `sum` 上 `+=` 就是 H-03.2.1 的竞争。`reduction` 子句专门无竞争地解决它：

```c
double sum = 0.0;
#pragma omp parallel for reduction(+:sum)
for (long i=0;i<N;i++) sum += a[i];   // 无竞争、结果正确
```

它的机制分两步：第一步，给每个线程一份**私有副本**，初始化为该运算符的**标识元**（identity，让"加进去不改变结果"的那个值）；各线程只往自己的私有副本累加，彼此不碰同一内存，所以没有竞争。第二步，在区域末尾把所有线程的私有副本用同一个运算符**合并**回原始变量。

各运算符的标识元初值（取自 OpenMP 规范的 reduction 标识表）：

```
+   → 0        *   → 1        -   → 0
&   → ~0(全1)  |   → 0        ^   → 0
&&  → 1        ||  → 0
max → 该类型最小值   min → 该类型最大值
```

reduction 不是"给累加加锁"，而是"先各算各的、最后汇总一次"——把 N 次共享写压缩成"每线程本地累加 + 一次合并"，既消除了竞争、又避免了每次迭代都同步的巨大开销，所以既对又快。两个易错点：一是浮点求和的 reduction 因为合并顺序和串行不同，结果可能与串行有极小的舍入差异（浮点加法不满足结合律），这是正常现象不是 bug；二是 `min`/`max` 的标识元是"类型的极值"而非 0，若手写私有化累加时初始化错了会得错误结果——用 reduction 子句则由实现自动填对标识元。

### H-03.2.5 本机实证：竞争 vs 归约的正确性

用 gcc 13.3.0 `-fopenmp` 对照两种写法：4 个线程各把一个共享计数器加 500 万次（共享写、无同步，制造竞争）vs 用 `reduction(+:)`。本机实测（`-O2 -std=c11` @2026-08-01，多次运行）：

```
expected    = 20000000
race result = 15000000  (lost updates: 5000000)   ← 首次运行丢了整整一个线程的更新
reduction   = 20000000  (correct? yes)            ← 归约恒正确
--- 再次运行 ---
race result = 20000000  (lost updates: 0)          ← 这次又"碰巧对了"
reduction   = 20000000  (correct? yes)
```

这组输出把 H-03.2.1 讲的"竞争是概率性的"活生生演了出来：无同步的共享 `+=` 首次运行丢了 500 万次更新（恰好一个线程的量，典型的丢失更新），而再跑两次又"碰巧全对"——这正是数据竞争最危险的地方，**它不会每次都错，所以靠"跑几次看着对"永远发现不了它**。而 `reduction(+:)` 版本每次都精确等于 2000 万，因为各线程在私有副本上累加、末尾才合并一次，从根上没有共享写冲突。复现核心：`#pragma omp parallel num_threads(4)` 内让各线程对同一 `long shared` 做 `shared += 1`（竞争版）对比 `reduction(+:red)`（归约版）；`gcc -O2 -fopenmp -std=c11` 编译后多跑几次即可观察到竞争版的不确定结果。

#### 来源与时效
- OpenMP API Specification v6.0（核实 2026-08-01）：data-sharing 属性默认规则、`shared/private/firstprivate/lastprivate` 语义、`default(none)`、`reduction` 子句机制与标识元（identity）表——一手权威，标识元初值逐一比对规范表填写，未凭记忆。

- 交叉一致：默认共享/私有规则与 reduction 机制在规范、CS267、《Using OpenMP》三方一致，无冲突。

## H-03.3 伪共享与缓存行、缓存一致性开销

### H-03.3.1 缓存行与缓存一致性

CPU 缓存不是按单个字节搬运的，而是按固定大小的**缓存行**（cache line）为单位在内存与缓存之间移动、以及在多核之间同步。本机实测缓存行大小为 64 字节（`getconf LEVEL1_DCACHE_LINESIZE` 与 `/sys/.../coherency_line_size` 均为 64，x86-64 常见值）。也就是说，即便你只读写一个 8 字节的 `long`，硬件也是把它所在的整条 64 字节一起拉进缓存。

多核共享内存机器必须保证"各核缓存里同一份数据看起来一致"，这由缓存一致性协议（cache coherence protocol，典型是 MESI：Modified / Exclusive / Shared / Invalid 四状态，Intel 变体 MESIF、AMD 变体 MOESI）在硬件层完成。核心规则的直觉：一条缓存行可以被多个核**同时缓存着读**（Shared 状态），但当某个核要**写**它时，必须先让其它核上这条行的副本**失效**（invalidate），把行的所有权抢过来（独占）才能写。于是"一个核写、别的核缓存里有同一行"就会触发一次跨核的失效流量。这套机制对程序员通常是透明的，但它的开销正是下一节伪共享减速的根源。

### H-03.3.2 伪共享（false sharing）

伪共享指：多个线程各自读写**不同的变量**，本来毫无数据依赖、逻辑上不该互相影响，但这些变量**恰好落在同一条缓存行上**，于是每个线程的写都会让持有该行的其它核缓存失效，缓存行在核之间被反复"抢来抢去"（ping-pong / 弹跳），产生大量本可避免的一致性流量，把并行程序拖慢。

它叫"伪"共享，是因为线程之间**并没有真正共享数据**（各写各的变量），是硬件"按整条缓存行管理"这个粒度制造出来的假冲突。最典型的触发场景：给每个线程分一个数组元素当计数器 `count[tid]`，`count[0..3]` 四个 `long` 只占 32 字节、挤在同一条 64 字节行里——四个线程疯狂各写各的 `count[tid]`，这条行就在四个核之间狂弹。初学者最反直觉的一点：这段代码**逻辑完全正确、结果也对**，只是慢得莫名其妙，且加的线程越多可能越慢——因为它不是竞争（结果没错），而是纯粹的缓存一致性开销。这也点出本报告"讲性能"和 L4-05"讲正确性"的分工：伪共享是对而慢的性能问题，数据竞争是错的正确性问题。

### H-03.3.3 本机实证：伪共享减速

用 gcc `-fopenmp` 对照两种布局：4 个线程各把自己的计数器加 2 亿次。布局A（伪共享）：四个计数器是相邻的 `long`，挤在同一条 64B 缓存行里；布局B（填充）：每个计数器独占一条 64 字节缓存行（用 padding 隔开）。本机实测（`-O1 -fopenmp -std=c11` @2026-08-01）：

```
packed  (false share) : 0.166 s     ← 四计数器同一缓存行，行在核间弹跳
padded  (own line)    : 0.080 s     ← 每计数器独占缓存行，无伪共享
```

同样的计算量、同样正确的结果，仅仅因为内存布局不同，伪共享版慢了约 2 倍（本机 4 核；核数越多、弹跳越剧烈，减速通常越显著）。这就是缓存一致性开销的数值面孔：布局A 里那条被四个核争抢的缓存行，每次写都要把别的核的副本失效再抢回来，绝大部分时间耗在跨核同步而非计算上。复现核心：`#pragma omp parallel num_threads(4)` 内让线程 `id` 循环自增 `packed[id]`（四个相邻 `long`，伪共享）对比自增 `slot[id].v`（每个 `slot` 用 `long pad[7]` 填满到 64 字节，独占缓存行）；用 `-O1` 编译以防编译器把计数器整个提升进寄存器而消掉访存。

### H-03.3.4 缓解手段

对付伪共享的思路都是"让被并发写的变量彼此不落在同一条缓存行上"。常见手段：给每个线程的数据做**填充/对齐**（padding），使其独占一条缓存行（如 H-03.3.3 里用 `long pad[7]` 把结构体撑到 64 字节，或 C11 `alignas(64)` / `_Alignas`）；或者干脆**用私有变量本地累加、最后再合并**——这正是 reduction 子句在做的事：每个线程在自己的私有副本（各在各自栈上、天然不同缓存行）上累加，中途完全不碰共享内存，因此既无竞争也无伪共享，末尾才合并一次。

**能用 reduction / 私有化的地方就别用"每线程写共享数组一格"的写法**——后者极易踩伪共享。填充是不得已（比如确实需要保留每线程结果数组时）才手动做的补救，且要注意填充会增加内存占用、并非越大越好，通常对齐到一条缓存行（本机 64 字节）即可。判断"是不是伪共享在作怪"的信号：并行版结果正确但加速远低于预期、甚至加线程更慢，而各线程写的是同一个小数组的不同元素——高度可疑。

#### 来源与时效
- OpenMP API Specification v6.0（核实 2026-08-01）：reduction 作为避免共享写（从而顺带避免伪共享）的一等手段，语义见 H-03.2.4 来源。
- Hennessy & Patterson《Computer Architecture: A Quantitative Approach》缓存一致性 / MESI 章（核实 2026-08-01）：缓存行为一致性单位、写触发失效、false sharing 定义——体系结构一手权威。
- CS267 (Spring 2024) 共享内存性能章：伪共享与缓存行填充的教学表述，与体系结构教材交叉一致。
- 本机实测（gcc 13.3.0 / libgomp @2026-08-01）：缓存行 64 字节（`getconf` 与 sysfs 双确认）；伪共享版 0.166 s vs 填充版 0.080 s（约 2× 减速，4 核）。数值为本机具体结果，绝对时间随机器而异、仅示相对关系。

## H-03.4 NUMA 亲和与线程调度策略

### H-03.4.1 UMA vs NUMA 与 first-touch 分配

在共享内存机器里，内存对所有核"是否等距"分两种。UMA（Uniform Memory Access，一致内存访问）：所有核到所有内存的延迟/带宽都一样（典型是单插槽多核）。NUMA（Non-Uniform Memory Access，非一致内存访问）：机器由多个节点（node，常对应多个 CPU 插槽）组成，每个节点有自己的"本地内存"，核访问本节点本地内存快、访问别的节点的"远程内存"要走节点间互联、更慢。本机实测只有单个 NUMA 节点（`/sys/devices/system/node/` 下仅 `node0`），因此本机等价于 UMA，下面的 NUMA 性能结论为文档腿、本机无法实测。

理解 NUMA 的关键是 Linux 的 **first-touch（首次触碰）分配策略**：`malloc` 只是预留虚拟地址，物理页并不在分配时就落到某个节点；一个物理页实际被分配在"**第一个写它的线程所在节点**"的本地内存上。这条规则对性能影响巨大且极反直觉——如果你用单个主线程串行初始化整个大数组（`for(i) a[i]=0;`），所有物理页都落到主线程那个节点，之后即便多线程并行计算，别的节点上的线程每次访问都是慢的远程访问。正确做法是**让将来计算某段数据的线程，去负责初始化那段数据**（用与计算同样的 `parallel for` 并行初始化），使页面按 first-touch 分散落到各自节点、后续都是本地访问。这就是 NUMA 上"初始化方式决定性能"的著名坑。

### H-03.4.2 线程亲和：OMP_PROC_BIND 与 OMP_PLACES

线程亲和（affinity / binding）指把 OpenMP 线程"钉"在特定的硬件核（或核的集合）上，不让操作系统随意迁移它。为什么要钉？线程若被 OS 迁到别的核，它辛苦预热进本核缓存的数据全部作废（要重新从内存/远程节点拉），在 NUMA 上还可能迁到离它数据很远的节点——亲和就是防止这种"人走了、数据还在原地"的抖动。

OpenMP 用两个环境变量（也有对应子句/ICV）控制：`OMP_PROC_BIND` 决定"绑不绑、怎么绑分布"，`OMP_PLACES` 定义"可绑的位置集合"（如 `threads`=硬件线程、`cores`=物理核、`sockets`=插槽）。`OMP_PROC_BIND` 的取值语义（取自规范）：

```
OMP_PROC_BIND = false    不绑定，OS 自由调度
              = true     绑定（分布方式由实现定）
              = primary  所有线程绑到主线程所在的位置(旧称 master)
              = close    线程绑到彼此邻近的位置（依次紧挨主线程）
              = spread   线程尽量均匀铺开到各位置
```

初学者层面记住两种典型意图：`close` 让线程挤在一起（共享同一块缓存、线程间通信快，适合数据密集互相协作）；`spread` 把线程摊开到不同插槽/节点（每个线程独享更多缓存和内存带宽，适合带宽敏感、且配合 first-touch 让每线程用本地内存）。绑对了能显著改善缓存和 NUMA 局部性，绑错了（比如把该分散的活儿全挤到一个节点）反而更慢。本机单节点，亲和的 NUMA 收益无法实测，此处为规范语义 + 文档腿。

### H-03.4.3 循环调度策略：static / dynamic / guided / auto / runtime

`schedule` 子句决定 worksharing-loop 的迭代**怎么分给线程**，直接影响负载均衡与开销。规范定义的调度类型：

```c
#pragma omp parallel for schedule(dynamic, 100)
for (...) { ... }        // 每次抓 100 个迭代，干完再抓，直到没有
```

- `static[,chunk]`：进入循环时就把迭代按 `chunk` 大小静态地、轮转地分好（不指定 chunk 时每线程分到一块大致相等的连续迭代）。开销最低、无运行时分配成本，适合**每次迭代耗时均匀**的循环。
- `dynamic[,chunk]`：线程干完手上的块就来"抢"下一块（默认 chunk=1），先干完的多抢——能应对**各迭代耗时不均**（负载不均），代价是每次抓取都有运行时同步开销。
- `guided[,chunk]`：类似 dynamic，但块大小**从大到小递减**（开始给大块摊薄开销、临近结束给小块以便收尾均衡），块缩到 `chunk` 为下限。
- `auto`：把选择权完全交给编译器/运行时。
- `runtime`：由环境变量 `OMP_SCHEDULE`（或 `run-sched-var` ICV）在运行时决定，便于不改代码调参。

迭代耗时**整齐** → `static`（省开销）；耗时**参差不齐**（如三角矩阵、每行工作量不同、含 `if` 分支）→ `dynamic`/`guided`（换取负载均衡）。一个要规范与实现分账的点：**不写 `schedule` 子句时的默认调度是"实现定义"的**——OpenMP 规范说它由 `def-sched-var` ICV 决定、并未强制某种；具体到 GCC 的 libgomp，默认取 `static`。所以"OpenMP 默认是 static"这句话只对特定实现成立，规范层面应表述为"实现定义（GCC 为 static）"，不可当作普适保证。

### H-03.4.4 GPU 视角一句指路：OpenMP target offload

OpenMP 从 4.0 起加入 `target` 系列构造（`#pragma omp target`、`teams`、`distribute` 等），可以把一段计算"卸载"（offload）到 GPU 等加速设备上执行，让同一套 OpenMP 指示既能写多核 CPU 也能写 GPU，属于共享/异构并行框架谱系的一环。

```c
#pragma omp target teams distribute parallel for map(to:a[0:N]) map(from:c[0:N])
for (int i=0;i<N;i++) c[i]=a[i]*2;   // 卸载到设备执行；map 子句管数据搬运
```

这里只需知道 OpenMP 有这条"通向 GPU"的路径、它和 CUDA 是同一层次的不同选择即可。设备内存层级、`map` 数据传输、GPU 上的执行细节归本课大主题5/6（GPU 架构与 CUDA / 内存层级优化）深讲，本报告不展开——本机无 GPU，target offload 亦无法实测，标文档腿。
