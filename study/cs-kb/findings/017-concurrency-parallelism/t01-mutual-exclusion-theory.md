## CP-01.1 互斥的形式化：临界区与三条正确性性质

### CP-01.1.1 临界区与互斥性

把一段"访问共享数据、不能被别的线程插进来搅乱"的代码称为**临界区**（critical section）。互斥问题就是要设计一对 `lock()`/`unlock()` 操作，使得任何线程执行 `lock()`…临界区…`unlock()` 这个模式时，满足**互斥性**（mutual exclusion）：任意两个不同线程的临界区执行区间**在时间上不重叠**。

用 AMP 的记号，设 $CS_A^j$ 表示线程 A 第 j 次进入临界区的那段执行区间，则互斥性可写成：

对任意 A≠B、任意 j、k，

CS_A^j 与 CS_B^k 不重叠（一个整体在另一个之前，或反之）

这条性质是互斥的**底线**——做不到它，这段代码就根本不是"锁"。要抓住的直觉是：互斥不是"保护某个变量"，而是"保护一段代码所访问的那批数据不被并发穿插"。同一份数据被多处访问时，必须用**同一把**锁把这些地方都罩住，互斥才成立。另一个初学者易错点是把"互斥"当成唯一目标——只要互斥的话，一把"永远不让任何人进"的锁也满足互斥，却毫无用处；所以还必须配上下面两条"活性"（liveness）性质，保证系统真的往前走。

### CP-01.1.2 无死锁（deadlock-free）

**无死锁**是最弱的一条进展（活性）性质，它要求的是**系统整体**往前走：只要有线程想进临界区（调用了 `lock()`），那么**总有某个**线程能成功进入并最终离开。换句话说，不允许出现"大家都想进、却谁都进不去、永远卡死"的局面。

无死锁只保证**集体**有进展，**不保证每个个体**都有进展——某个特定线程完全可能被其他线程反复插队、永远抢不到锁而饿死，只要"总有人能进"就不违反无死锁。初学者常把它和"没有 bug 意义上的死锁"混淆：这里的 deadlock-free 是一条被精确定义的**算法性质**（"想进的人里总有人能进"），不是泛指"程序不卡"。它对应的反例很具体——见 CP-01.2 的 LockOne：两个线程可以同时卡在各自的等待循环里，谁都进不去，这就违反了无死锁。

### CP-01.1.3 无饥饿（starvation-free）

**无饥饿**（又叫 lockout-free，无锁死）比无死锁强：它要求**每一个**调用 `lock()` 的线程**最终都能**返回（进入临界区）。也就是不允许任何**个体**被无限期地饿着。

无饥饿 ⇒ 无死锁（个个都能进，系统当然整体有进展），反之不成立——一个无死锁但会让某些倒霉线程饿死的算法，就卡在这两者之间。这正是二者的分界，也是初学者最该记牢的层级关系：

无饥饿 ⟹ 无死锁（严格更强）

要注意无饥饿只承诺"**最终**能进"，但没说"要等多久"——等待步数可以是无界的（可能被后来者插队任意多次，只要不是无限次）。想进一步约束"最多被插队几次"，就要上升到 CP-01.5 的**有界等待**。三条性质合起来构成一条强度递增的阶梯：互斥性（安全性底线）< 无死锁（集体进展）< 无饥饿（个体进展）< 有界等待（个体进展且公平有界）。

## CP-01.2 两线程算法：LockOne / LockTwo / Peterson

### CP-01.2.1 LockOne：只用 flag，互斥但会死锁

LockOne 让每个线程用一个布尔标志 `flag[i]` 宣告"我想进"，然后等对方的标志变假：

```
// 线程 i（对方为 j）
flag[i] = true;
while (flag[j]) { }   // 对方也想进，就自旋等
// 临界区
flag[i] = false;
```

LockOne 满足**互斥性**，但**不满足无死锁**。互斥的道理：若两个线程都进了临界区，考察谁最后写自己的 `flag`、谁先读对方的 `flag`，会推出矛盾（AMP 的标准论证用"写 flag[i] 在读 flag[j] 之前"这个程序序，配合两线程的读写交错分析）。死锁的道理更直观：如果两线程几乎同时各自把 `flag[i]=true` 都设成真，然后都进入 `while`，就会**互相等对方变假**——可谁都不会先退让，双双卡死。这正是 CP-01.1.2 无死锁的反例。初学者要体会：LockOne 的问题不是"没互斥"，而是"太容易一起卡住"。

### CP-01.2.2 LockTwo：只用 victim，互斥但单独运行就卡

LockTwo 换一个思路：不看标志，而是设一个"谁是牺牲者"的变量 `victim`，谦让对方：

```
// 线程 i
victim = i;              // 我先声明"我当牺牲者，让你先"
while (victim == i) { }  // 只要还是我当牺牲者就等
// 临界区
```

LockTwo 也满足**互斥性**（`victim` 只能是一个值，最后写它的那个线程成为牺牲者、被挡在外面，另一个进去），但它连**单独运行都会卡死**：如果只有线程 i 在跑、线程 j 根本没来，i 把 `victim=i` 后就永远等 `victim` 变成 j——可没人来改它，i 永久阻塞。所以 LockTwo 也不满足无死锁，且失败模式和 LockOne 恰好互补：LockOne 死在"两个都来"，LockTwo 死在"只有一个来"。这个互补是下一步的关键伏笔。

### CP-01.2.3 Peterson：两者相加，互斥 + 无死锁 + 无饥饿

Peterson 算法（Gary Peterson, 1981）把 LockOne 的 `flag` 和 LockTwo 的 `victim` **叠加**起来，恰好让两者的失败模式互相抵消：

```
// 线程 i（对方为 j）
flag[i] = true;          // 我想进（来自 LockOne）
victim  = i;             // 但我谦让，先当牺牲者（来自 LockTwo）
while (flag[j] && victim == i) { }   // 只有"对方也想进 且 我是牺牲者"时才等
// 临界区
flag[i] = false;
```

Peterson 同时满足**互斥性、无死锁、无饥饿**，是两线程互斥的经典标准解。直觉：等待条件是"对方想进（`flag[j]`）**并且**我是牺牲者（`victim==i`）"两者同时成立才等。若两线程同时来，`victim` 只会保留**最后一次写入**的那个值，于是恰好只有一个线程满足 `victim==i` 被挡住、另一个放行——解决了 LockOne 的双卡；若只有我一个来，`flag[j]` 是假、`while` 条件立刻不成立、我直接进——解决了 LockTwo 的单卡。Peterson 论文的标题「Myths About the Mutual Exclusion Problem」意在戳破当时"两线程互斥必须很复杂"的迷思——它只用两个共享变量、几行代码就做到了。

一个对初学者极重要的时效性提醒：以上正确性论证**默认内存是顺序一致的**（每个线程的读写按程序序、且对其他线程即时可见）。在真实的 x86-64 / ARM 硬件上，`flag[i]=true` 这个写和随后读 `flag[j]` 之间可能被**重排**（x86 的 store→load 重排），导致裸写的 Peterson 偶发失效——必须插入内存屏障才成立。这属 CP-05「内存一致性模型」的主场，本课只把 Peterson 当作"顺序一致模型下的正确性范例"，不展开屏障细节。

## CP-01.3 N 线程算法：filter 锁与 bakery 算法

### CP-01.3.1 filter 锁：把 Peterson 推广到 n 个线程

filter（过滤器）锁把 Peterson 的思路推广到 n 个线程：设立 **n−1 个"级别"（level）**，线程必须逐级往上爬，每一级都像一次 Peterson 式的谦让，且**每一级最多淘汰一个、保证到最高级时只剩一个线程**能进临界区。它用两个数组：`level[i]` 记录线程 i 当前爬到第几级，`victim[ℓ]` 记录第 ℓ 级的牺牲者。

```
// 线程 i 想进：逐级 ℓ = 1 .. n-1 往上爬
for (ℓ = 1; ℓ <= n-1; ℓ++) {
    level[i]   = ℓ;
    victim[ℓ]  = i;
    // 只要"还有别的线程在 ℓ 级或更高" 且 "我是本级牺牲者"，就等
    while (∃ k≠i : level[k] >= ℓ  &&  victim[ℓ] == i) { }
}
// 爬满 n-1 级 → 进入临界区
level[i] = 0;   // 释放
```

filter 锁满足**互斥性、无死锁、无饥饿**，但**不满足先来先服务**（不公平，见 CP-01.5）。直觉是每一级都是一道"过滤门"：第 ℓ 级最多允许 n−ℓ 个线程停留在该级或以上，于是每升一级至少挡下一个，爬到第 n−1 级时最多只剩 1 个线程通过——这就把"n 个抢 1 个"层层收敛成"1 个胜出"。要点在于它是 Peterson 的自然递归推广：每一级的 `victim[ℓ]` 就是那一级的"我谦让你先"。它的短板是公平性——一个线程可能被后来者反复卡在某一级、等待次数无上界（虽然最终能进，满足无饥饿，但不满足有界等待）。

### CP-01.3.2 bakery 算法：先来先服务的"取号排队"

Lamport 的 bakery（面包店）算法（1974）用现实中"面包店取号排队"的比喻做到**先来先服务**（FCFS）。每个线程进店先**取一个号**（比现有最大号大 1），然后**按号从小到大**依次进入；号相同则按线程编号打破平局。它用两个数组：`flag[i]`（"我正在取号/我要排队"的门厅标志）和 `label[i]`（线程 i 拿到的号）。

```
// 取号（doorway，门厅阶段）
flag[i]  = true;
label[i] = 1 + max(label[0], ..., label[n-1]);
flag[i]  = false;
// 排队等待：等到"没有任何别的线程排在我前面"
for each k != i:
    while (flag[k]) { }                       // 等 k 取完号
    while (label[k] != 0 &&
           (label[k], k) <lex (label[i], i)) { }   // 号更小(或号同而编号更小)的先走
// 临界区
label[i] = 0;   // 释放：把号清零
```

关键是这条**字典序**比较（先比号、号相同再比线程编号），它给所有排队者定义了一个全序，从而实现严格排队：

(label[k], k) <lex (label[i], i)  ⟺  label[k] < label[i]，或 label[k] = label[i] 且 k < i

bakery 满足**互斥性、无死锁、无饥饿，且是先来先服务**——谁先取完号（先走完门厅阶段）谁就先进临界区，这是它最珍贵的性质。更深的意义（Lamport 论文强调）是：bakery **完全不依赖任何底层互斥或原子硬件操作**，即便"取号"这一步本身有并发、读到重叠写的中间值，算法依然正确——它是第一个用纯读写共享变量、不借硬件原子指令就实现 FCFS 互斥的算法。代价是每次取号要扫描所有 n 个线程的号（O(n) 工作）、且号会无界增长（理论上需要无界的整型；有界化是后续研究课题）。初学者可把 flag 阶段理解为"进门取号，取号时别人要等我取完"，label 阶段理解为"手里号小的先叫号"。

## CP-01.4 纯软件互斥的下界：为何要 Ω(N) 个内存位置、离不开硬件原语

### CP-01.4.1 空间下界定理：n 个线程至少需 n 个内存位置

只用普通**读/写共享变量**（不借硬件原子读改写指令）实现互斥，有一条硬性的**空间下界**：任何**无死锁**的 n 线程互斥算法，至少要用 **n 个不同的内存位置**（寄存器）。这条结果由 Burns 与 Lynch 证明（1993），也被 AMP 第 2 章作为定理收录。

任意仅用 read/write 寄存器的无死锁 n 线程互斥算法，所需不同内存位置数 ≥ n

这意味着 filter 和 bakery 那种"内存开销随线程数线性增长"不是实现得不够聪明，而是**理论上无法避免**——你不可能用固定的几个共享变量、只靠读写就给任意多线程做互斥。证明的核心直觉（AMP 给的"covering"论证）是：若位置数少于 n，总能构造一个执行，让若干线程各自"盖住"（准备写但还没写）某些位置，使得任一线程都无法从共享内存中分辨出别人是否正在临界区，于是要么破坏互斥、要么卡死。初学者不必掌握完整构造，记住结论即可：**纯读写的软件互斥，空间代价与线程数同阶，躲不掉。**

### CP-01.4.2 为何离不开硬件原语

空间线性增长只是问题的一面。另一面是这些纯软件算法都**默认顺序一致内存**，而真实多核硬件为性能会重排读写（CP-05），使裸算法失效、必须插屏障；再加上取号扫描 O(n)、忙等自旋等开销，纯软件互斥在实践中既不省空间也不高效。

出路是引入**硬件原子读改写原语**（read-modify-write）：test-and-set（TAS）、compare-and-swap（CAS）等把"读旧值 + 写新值"合并成一次不可分割的操作。有了它，一个**固定大小**（O(1) 个变量）的自旋锁就能给任意多线程做互斥——直接绕过了上面 Ω(n) 的读写下界，因为下界的前提是"只有读和写"。这就是为什么现代所有实用锁（内核 mutex、pthread、futex）底层都建立在硬件原子指令上，而 Peterson/bakery 主要作为**教学与理论对象**：它们回答的是"最弱能力下能做到什么、要付什么代价"，而工程实现则靠硬件把代价压到常数。硬件原语到底有多强、能做到什么（consensus number、CAS 为何"万能"）归 CP-04，本课只到"为何非要它不可"为止。

#### 来源与时效
- AMP 2nd/Revised ch2 §2.9「Lower Bounds on the Number of Locations」（核实 2026-07-25）：无死锁 n 线程读写互斥需 ≥ n 个位置的定理与 covering 论证；纯软件方案不实用、实用锁需硬件 RMW 的结论。
- Burns & Lynch「Bounds on Shared Memory for Mutual Exclusion」Information and Computation 107(2):171–184, 1993（经 ACM/Semantic Scholar 交叉核实出处与"n 个二元变量必要且充分"表述 2026-07-29）：空间下界原始出处。
- 分账指路：硬件原语的相对能力/共识数归 CP-04；裸算法所依赖的顺序一致性与真实弱内存模型的差距归 CP-05。
- 交叉一致，无冲突。两源均给"n 个位置"这一同阶下界，Burns-Lynch 原文精确到"n 个二元变量必要且充分"。

## CP-01.5 有界等待与公平：doorway 分解、时间与因果的参照系

### CP-01.5.1 doorway 分解：把 lock() 切成有界的"门厅"与无界的"等待"

要谈"公平"，先得解决一个定义上的难题：`lock()` 里的等待步数本来就可以是**无界**的（后来者可能合法地插很多次队），那"公平"该怎么量？AMP 的做法是把 `lock()` 拆成两段——前半段叫**门厅**（doorway），要求它**在有界步数内必然完成**（wait-free，不含循环等待）；后半段才是可能无界的**等待**（waiting）区。bakery 的"取号"就是典型的 doorway：取号本身几步就做完。有了这个切分，公平性就可以定义在"谁先走完门厅"这个**有界、可比较**的时刻上，而不是纠缠于无界的等待。

这个分解是理解一切公平性定义的钥匙。初学者要抓住：我们不能要求"先调用 lock() 的先进"（因为"调用"这个时刻在并发下难以良定义、且等待无界），而是退一步要求"**先走完门厅的先进**"——门厅是有界的，所以"先走完门厅"是一个干净的、类似实时先后的参照点。

### CP-01.5.2 有界等待（bounded waiting）与先来先服务（FCFS）

在 doorway 分解之上，**r-有界等待**（r-bounded waiting）定义为：如果线程 A 第 j 次走完门厅**早于**线程 B 第 k 次走完门厅，那么 A 的这次临界区不会比 B 的第 (k+r) 次更晚——即 A 最多被 B "反超" r 次。记 $D_A^j$ 为 A 第 j 次门厅完成、$CS$ 为对应临界区：

D_A^j → D_B^k  ⟹  CS_A^j → CS_B^{k+r}

其中 r = 0 的特例就是**先来先服务**（FCFS，first-come-first-served）：先走完门厅的严格先进临界区，一次都不被反超。

D_A^j → D_B^k  ⟹  CS_A^j → CS_B^k     （r = 0，即 FCFS）

bakery 算法满足 FCFS（r=0），这也是它区别于 filter 的关键——filter 只做到无饥饿（最终能进），却**不是**有界等待（可能被反超任意多次）。要点在于有界等待是比无饥饿更强的公平承诺：无饥饿只说"你最终能进"，有界等待还说"你最多被插队 r 次"，给出了量化的公平上界。这补全了 CP-01.1 的性质阶梯的最强一档。

### CP-01.5.3 公平只能相对某个序来定义：时间序与因果序

一个深一层但对初学者很重要的观念：**"公平"没有绝对标准，它总是相对某个"先后序"来定义的**。上面的有界等待用的是 doorway 完成的**先后**，这本质上是一种被限制到有界门厅上的"**实时先后序**"。为什么不直接用"真实物理时间"给所有事件排序来谈公平？因为在并发/分布式系统里，跨线程的事件往往没有全局同步的物理时钟，能可靠比较先后的只有**有因果关系**（一个操作的结果被另一个读到）的那些事件——这正是 Lamport 后来在「Time, Clocks」中形式化的**因果序**（happens-before）。

所以公平性定义面临一个根本约束：它只能架在**能被系统可靠观测到的序**之上。doorway 分解之所以聪明，正是因为它把"公平参照"钉在有界、可判定的门厅完成时刻上，绕开了"无界等待期间的先后无法良定义"和"没有全局时钟"两个坑。初学者记住这条即可：**谈公平，先问"相对什么序"**——本课用的是 doorway 实时先后；更一般的因果序、以及它与内存模型的关系，归 CP-02（顺序/线性一致性）和 CP-05（happens-before），本课不展开。

- AMP 2nd/Revised ch2 §2.6「Fairness」（核实 2026-07-25）：doorway/waiting 分解、doorway 为 wait-free（有界步完成）、r-bounded waiting 的形式定义 $D_A^j → D_B^k ⟹ CS_A^j → CS_B^{k+r}$、FCFS = r=0、bakery 满足 FCFS、filter 无饥饿但不 FCFS。
- Lamport「Time, Clocks, and the Ordering of Events in a Distributed System」CACM 21(7):558–565, 1978（因果序/happens-before 概念来源，交叉印证"公平需相对某个可观测序"，核实 2026-07-29）。
- 分账指路：因果序/happens-before 的完整定义归 CP-05；顺序/线性一致性归 CP-02；OS 层调度公平（时间片/优先级）归 L4-01·OS-05，与此处"算法层公平"分账。
