## CP-10.1 链表并发级别谱：coarse → fine → optimistic → lazy → lock-free

### CP-10.1.1 为什么拿"有序链表集合"当载体

AMP 第 9 章用一个最朴素的对象贯穿始终：一个**有序单链表实现的集合（set）**，支持 `add(x)`、`remove(x)`、`contains(x)` 三个操作，节点按 key 升序排列，头尾各放一个**哨兵节点**（sentinel，key 分别取 −∞ 和 +∞，永不删除）。所有并发级别都在这同一个数据结构上做，唯一的区别就是"访问共享节点时用多强的同步"。之所以选它，是因为链表的核心难点——"两个相邻节点要一起改（`pred.next` 和 `curr`）"——恰好是并发同步的最小又最典型的场景。

哨兵节点是初学者容易忽略但很关键的技巧：因为有序表的每个操作都要找到"前驱 `pred` 和当前 `curr`"这一对，如果表头/表尾也可能是操作目标，就会有大量"要改的节点是不是第一个/最后一个"的边界判断。放两个永不删除的哨兵后，任何真实 key 都严格落在 −∞ 和 +∞ 之间，`pred` 永远存在，边界判断被消掉，代码和正确性论证都干净很多。

### CP-10.1.2 粗粒度锁（coarse-grained）

粗粒度锁就是**整张表一把锁**：任何 `add/remove/contains` 一进来先 `lock()`，做完 `unlock()`。它显然正确（临界区互斥，等价于顺序执行），代码最简单，在低争用下甚至是最优选择——因为它没有任何额外开销。

它的问题只有一个但是致命：**完全不可扩展**。无论表多长、无论两个操作是不是碰同一个位置，所有线程都在抢那一把锁，n 个核最终排成一队串行执行，加核不提速。这是整条谱系的起点：后面每一级都在"放松同步的作用范围"，让互不相干的操作能真正并行。要记住的对照是——粗粒度锁牺牲并行度换正确性的简单，后面各级牺牲代码/论证的简单换并行度。

### CP-10.1.3 细粒度锁：交替上锁（fine-grained / hand-over-hand）

细粒度锁把"一把大锁"拆成**每个节点各一把锁**，遍历时像攀岩换手一样"交替上锁"（hand-over-hand locking，又叫 lock coupling）：先锁住 `pred`，再锁住 `curr`，确认这一对没问题后，才释放 `pred` 的锁、把手挪到下一对。任意时刻一个线程只锁住相邻两个节点，别的线程可以在表的其他部分同时干活。

为什么必须**同时**锁住相邻两个、不能锁一个放一个：假设只锁 `curr` 不锁 `pred`，另一个线程可能正好把 `pred` 删掉（改了 `pred.next`），你手里的 `pred` 就成了已被摘除的"孤儿"，你基于它做的链接全错。同时持有 `pred` 和 `curr` 两把锁，才能保证"这两个节点此刻确实相邻且都还在表里"。代价是每个节点访问都要真正加解锁（即使 `contains` 这种只读操作也得一路锁过去），锁开销随表长线性累积，且线程必须严格按 key 从小到大的顺序加锁——这正是防死锁的**锁序**（见 CP-10.6.2）。

### CP-10.1.4 乐观同步（optimistic）

乐观同步赌"冲突很少"：**先完全不加锁地遍历**到目标位置，找到 `pred` 和 `curr`；然后才锁住这两个节点；锁住之后做一次**验证（validate）**——确认 `pred` 确实还在表里、且 `pred.next` 确实还等于 `curr`（即这段时间没人插进来或删掉它们）。验证通过才真正改指针，验证失败就整个重来（放锁、重新遍历）。

它的收益是：遍历阶段完全无锁，只在真正要改的一小段加锁，`contains` 大部分时间无锁，扩展性远好于细粒度锁。关键的正确性点在验证怎么做——因为遍历时没锁，读到的 `pred/curr` 可能在你锁它们之前就已经被别人删了，所以**必须重新从头走一遍表**确认 `pred` 可达且仍指向 `curr`。这也是乐观法的代价：验证=再遍历一次，所以它适合"遍历便宜、冲突少"的场景；冲突一多，反复重试反而更慢。易错点是"锁了就万事大吉"——不，锁只保证从此刻起没人再动它们，锁之前发生的删除必须靠验证兜住。

### CP-10.1.5 惰性同步（lazy）

惰性同步在乐观法上再进一步，引入**逻辑删除**：每个节点加一个 `marked` 布尔位。`remove(x)` 分两步——先把目标节点的 `marked` 置 `true`（**逻辑删除**，此刻它在语义上已不在集合里），再改 `pred.next` 跳过它（**物理删除**，真正从链上摘走）。有了 `marked` 位，验证被大幅简化：不再需要重新遍历全表，只要检查 `pred` 和 `curr` **都没被标记**、且 `pred.next == curr` 即可。

最漂亮的收益是 **`contains` 变成完全 wait-free（无等待）**：它只需一路无锁遍历，找到 key 后看一眼该节点的 `marked` 位——没标记就在集合里、标记了就不在，不加任何锁、不重试、保证有限步返回。这对"读多写少"的集合是巨大优势。逻辑删除位为什么让验证变简单：一旦一个节点被标记，它就再也不会"复活"，所以只要你锁住的 `pred/curr` 都没被标记，就说明它们从你读到到你锁住之间没被删过，`pred.next==curr` 就足以保证它们此刻相邻——不必再走全表。这个"标记后不可逆"的单调性，是从惰性法通向下一节无锁链表的桥。

### CP-10.1.6 无锁（lock-free）

最后一级把锁彻底去掉：连 `add/remove` 也不加锁，全部用 CAS 完成。逻辑删除的 `marked` 位保留，但它必须和 `next` 指针**打包成一个可以一次 CAS 原子改动的整体**（见 CP-10.2.3）；物理删除、插入都由 CAS 尝试，失败就重读重试。这样任何线程停摆都不阻塞别人，得到 **lock-free 进展性**——系统整体保证有线程在前进（但不保证每个线程都前进，那是更强的 wait-free）。

要把这条谱系当成一个连续的放松过程来记：粗粒度=一把锁串行；细粒度=把锁切碎、能局部并行但仍处处加锁；乐观=遍历免锁、只锁改动点、靠再遍历验证；惰性=加逻辑删除位、验证不必再遍历、读操作 wait-free；无锁=连改动点也用 CAS、彻底无锁、单点停摆不拖累全局。每一步都在"减少被锁保护的范围"，代价是正确性论证越来越微妙。下面三节的进展性/正确性词汇（wait-free、lock-free、线性化点）都在 CP-10.6 统一收口。

## CP-10.2 lock-free 链表：逻辑删除标记 + CAS 物理摘除

### CP-10.2.1 为什么不能"一次 CAS 直接删除"

天真的无锁删除会想：删 `curr` 不就是 CAS 把 `pred.next` 从 `curr` 改成 `curr.next` 吗？问题出在**同时发生的插入**：设想线程 A 要删 `curr`，线程 B 要在 `curr` 之后插入新节点 `e`（即把 `curr.next` 从 `d` 改成 `e`，`e.next=d`）。两个 CAS 各自都成功——A 让 `pred.next` 跳过了 `curr`，B 让 `curr.next` 指向了 `e`——但结果是 `e` 被挂在了一个**已经被摘除的 `curr`** 后面，于是新插入的 `e` 神秘丢失，永远不在表里。

根子在于删除要同时保证两件事——`pred.next` 从 `curr` 改走，**并且**在这期间没有人往 `curr` 后面挂东西。单独一个 CAS 只能原子地管住 `pred.next` 这**一个**字，管不住"`curr` 在此期间不被别人当作有效前驱去修改它的 `next`"。这就是无锁链表比无锁栈/队列难的核心：删除牵扯**两个指针**的一致性。

### CP-10.2.2 两步删除：先逻辑标记，再物理摘除

解法沿用惰性法的逻辑删除，但把标记位赋予新的作用——**给 `curr.next` 指针本身"上封条"**。删除分两步：

第一步（逻辑删除），CAS 把 `curr` 的 `next` 指针**连同一个 mark 位一起**从 `(unmarked, curr.next)` 改成 `(marked, curr.next)`。

第二步（物理删除），CAS 把 `pred.next` 从 `curr` 改成 `curr.next`，把 `curr` 从链上摘走。

关键在第一步：一旦 `curr.next` 被打上 mark，任何试图"在 `curr` 后面插入"或"把 `curr` 当有效前驱去 CAS 它的 `next`"的操作都会**失败**——因为它们期望的旧值是 `(unmarked, ...)`，而现在是 `(marked, ...)`，CAS 比对不上。于是 CP-10.2.1 的丢失插入被堵死：`curr` 一被标记就等于宣告"我正在离场，别再往我身上挂东西"。第二步的物理摘除即使这次没做成也没关系（见 10.2.4 的帮忙机制），因为逻辑上它已经不在集合里了。

### CP-10.2.3 把 mark 位塞进指针：AtomicMarkableReference / 偷一个比特

第一步要"原子地一起改 next 和 mark"，前提是这俩能被打包进**一个可 CAS 的字**。AMP 的 Java 版用 `AtomicMarkableReference<Node>`，它把一个引用和一个布尔标记捆成一个可原子 CAS 的对象。在 C/C++ 层面对应两种落地：

一种是**偷指针的低位比特**（bit stealing）：因为节点按对齐分配（如 16 字节对齐），指针最低几位恒为 0，可以借最低 1 位当 mark 位，整体仍是一个普通 `uintptr_t`，用单字 CAS 即可。

另一种是把 `(指针, 标记)` 放进一个宽字用**双字 CAS**（x86-64 的 `cmpxchg16b`，gcc 需 `-mcx16`），但这更常用于带版本号计数的场景（见 CP-10.3.5）。

初学者要抓住的点是：mark 和 next 必须是"同一次 CAS 的原子对象"，否则"先标记、再有人插入、再改 next"之间会出现空隙，前功尽弃。偷比特之所以可行，全靠"对齐地址的低位一定是 0"这个免费的存储空间——这是无锁编程里极常见的手法。

### CP-10.2.4 遍历顺手清理与"帮忙"（helping）

无锁链表的遍历函数（AMP 里叫 `find`，返回一个 `(pred, curr)` 窗口）有个额外职责：**遇到被标记的节点就顺手把它 CAS 摘掉**。也就是说，物理删除不一定由发起删除的那个线程完成——任何后来经过这里的线程，只要看见 `curr.next` 是 marked 的，就替它把 `pred.next` CAS 过去。这叫**帮忙（helping）**。

帮忙机制是无锁算法保证 lock-free 进展性的关键：因为发起删除的线程可能在"第一步标记成功、第二步物理摘除还没做"时就被调度器换下甚至崩溃，如果没人帮忙，这个被标记的僵尸节点会永远挂在链上挡路。有了帮忙，任何活跃线程都会把挡路的标记节点清掉，从而"总有人在前进"。这也解释了为什么 `find` 不能简单地跳过标记节点——它必须真的把它们 CAS 摘除，否则后续 CAS 会因为期望值不匹配反复失败。易错点：帮忙的物理摘除 CAS 如果失败（说明别人已经摘了或链变了），就重读窗口重来，不能当错误。

### CP-10.2.5 add 与 remove 的 CAS 骨架

`add(x)`：用 `find` 定位窗口 `(pred, curr)`，若 `curr.key==x` 则已存在、返回 false；否则新建节点 `n`（`n.next = (unmarked, curr)`），CAS 把 `pred.next` 从 `(unmarked, curr)` 改成 `(unmarked, n)`。成功即插入完成，失败就重跑 `find` 重试。

`remove(x)`：`find` 定位到 `curr.key==x`，先 CAS 给 `curr.next` 打 mark（逻辑删除，这一步的成功就是删除的**线性化点**）；再 CAS 摘除 `pred.next`（物理删除，失败也无妨，交给帮忙）。

要点是每个操作都遵循同一个模式：**读快照（find 出窗口）→ 单次 CAS 提交 → 失败则重读重试**。这是所有无锁结构的通用节奏，链表只是因为"删除牵扯两个指针"才多出"标记 + 帮忙"这层。线性化点落在那次成功的 CAS 上——插入是改 `pred.next` 那次，删除是打 mark 那次（不是物理摘除那次！物理摘除只是清扫，逻辑删除已决定了语义）。这个"线性化点在哪次 CAS"是把无锁结构和 CP-02 线性一致性对接的抓手。

## CP-10.3 并发队列与 ABA：Michael-Scott 队列、ABA 问题成因

### CP-10.3.1 Michael-Scott 无锁队列的结构

Michael-Scott（MS）队列是无锁 FIFO 队列的标准实现，被 `java.util.concurrent.ConcurrentLinkedQueue` 等直接采用。结构是单链表加两个原子指针 `head` 和 `tail`，外加一个恒存在的**dummy（哑）节点**：`head` 永远指向 dummy（队首真正的元素是 `head.next`），`tail` 指向最后一个节点（或落后一格）。入队在尾部、出队在头部，两端各由自己的 CAS 管辖，因此入队和出队能真正并发。

dummy 节点的作用和链表哨兵类似：让空队列和非空队列的代码统一。空队列时 `head==tail` 且都指向 dummy，永远不会出现 `head`/`tail` 为 null 的边界。MS 队列的巧妙之处在于把"入队"这件本来要同时改 `tail` 和 `tail.next` 两个字的事，拆成两次独立 CAS，并用"帮忙"补上中间的不一致窗口。

### CP-10.3.2 入队的两步 CAS 与"帮忙推进 tail"

入队 `enqueue(x)` 逻辑上要做两件事：让当前最后节点的 `next` 指向新节点、再让 `tail` 指向新节点。这两件事无法用一个 CAS 原子完成，MS 队列的做法是：

第一步，CAS 把 `tail.next` 从 `null` 改成新节点 `n`（这一步成功就是入队的**线性化点**——元素此刻已在队列里）。

第二步，CAS 把 `tail` 从旧尾改成 `n`（把 `tail` 追上去）。

第二步失败或压根没来得及做都没关系：此时队列处于"`tail` 落后一格"的**中间态**（`tail.next != null`）。任何后来的线程只要发现 `tail.next != null`，就知道有人入队到一半、`tail` 落后了，于是它会**先帮忙**把 `tail` CAS 推进一格，再做自己的事。这个帮忙保证了没有哪个入队者能靠"卡在两步之间"阻塞整个队列——正是 lock-free 的体现。初学者要理解：中间态是合法且短暂的，读者必须先识别并修复它，而不是假设 `tail` 总是精确指向最后一个节点。

### CP-10.3.3 出队与空队列判定

出队 `dequeue()` 读 `head`、`tail`、`head.next`。若 `head==tail`：要么队列空（`head.next==null`，返回空/抛异常），要么正处于 10.3.2 的中间态（`head.next!=null`，说明 `tail` 落后，先帮忙推进 `tail` 再重试）。否则取出 `head.next` 里的值，CAS 把 `head` 从旧 dummy 改成 `head.next`（`head.next` 升格为新 dummy）——这次 CAS 成功是出队的线性化点。

这里再次出现"读快照 → 判断是否中间态 → 帮忙或提交 → 失败重试"的通用节奏。要注意出队返回的值是从 `head.next`（新首元素）里读的，而被 CAS 换掉的旧 dummy 节点此刻**逻辑上可以回收了**——但"逻辑上可回收"和"物理上能安全 free"之间，隔着 ABA 和安全内存回收两道坎，正是下面两节的内容。

### CP-10.3.4 ABA 问题的成因

ABA 是无锁 CAS 编程的头号陷阱：**一个位置的值从 A 变成 B 又变回 A，中间的变化被 CAS "看漏"了**。CAS 只比较"值等不等于我记的旧值"，它无法区分"这个 A 是我当初看到的那个 A"还是"一个被回收后又碰巧复用回同一地址/同一值的新 A"。

在手动内存管理的 MS 队列/Treiber 栈里，典型场景是：线程 T1 读到 `head` 指向节点 A、记下 `A.next==B`，准备 CAS `head: A→B`；T1 被换下。其间别的线程出队 A（A 被 free）、出队 B、又入队一个新节点，而内存分配器**把刚 free 的 A 的地址复用**给了新节点，于是 `head` 又指回地址 A。T1 恢复，CAS 发现 `head` 仍是 A、**成功**，把 `head` 设成 B——可 B 早已被 free/移出队列，队列结构就此损坏。根子是：CAS 的"值相等"被当成了"没被动过"，而在有内存复用时这两者不等价。

### CP-10.3.5 解决 ABA：带版本号的指针（tagged/versioned pointer）

最直接的解法是给指针**附一个单调递增的版本号（tag/stamp）**，CAS 时连指针带版本号一起比对、一起自增。这样即使地址转了一圈变回 A，版本号也已经不同，CAS 会失败并触发重试，ABA 被拦下。落地方式：把 `(指针, 计数)` 塞进一个双字用 `cmpxchg16b`（DWCAS），或在 64 位字里"指针 + 高位计数"打包（若地址位宽够用）。Java 的 `AtomicStampedReference` 就是这个思路的现成封装。

这里要强调一点，MS 队列原始论文 **1996** 正是用"指针 + 计数"的双字 CAS 来防 ABA 的，这是它区别于早期天真无锁队列的关键。版本号法便宜且局部，但它只是**回避了 ABA 的错误后果**，并没有解决"节点到底什么时候能物理 free"——如果地址被复用给别的对象仍可能有更深的悬垂访问。彻底的答案是下一节的安全内存回收（hazard pointer/epoch/RCU），它从"确保没人还在看这个节点"的角度根治，也顺带消除 ABA。带 GC 的语言（Java）天然没有"地址复用给新对象"的问题，但**仍可能有 ABA**（值层面的 A→B→A），所以 `AtomicStampedReference` 在 GC 语言里依然有用。

下面是本机对 ABA 成因的确定性实证（单线程手工编排交错，避免随机性，保证可复现）。用小整数当"节点地址"以便打包进一个字：

```c
// aba.c (节选)  基线 gcc 13.3 @2026-07-30，编译： gcc -std=c11 -O2 -Wall aba.c -o aba
// Case1 单字 CAS：只比对地址。T1 记 top==A，其间 A 被 pop/复用又变回 top==A。
uint32_t exp = 1;                 // T1 期望 top == A(1)
atomic_store(&top, 1);            // 别的线程折腾一圈后 top 又是 A(1)  <- 这就是 "A...A"
int ok = atomic_compare_exchange_strong(&top, &exp, 2);  // CAS top: A->B
// Case2 带标签 CAS：把 (tag,addr) 打包成 64 位一起比对。
uint64_t v_seen = PACK(0,1);      // T1 快照 (tag0, A)
atomic_store(&vtop, PACK(3,1));   // 别的线程 3 次成功 CAS 后是 (tag3, A)：地址同、tag 变
uint64_t vexp = v_seen;
int vok = atomic_compare_exchange_strong(&vtop, &vexp, PACK(1,2));  // 期望 tag0 -> 失败
```

本机真实输出：

```
Case1 plain CAS  : CAS(top: A->B) SUCCEEDED, top now = node2  <-- ABA: B was freed, stack corrupted
Case2 tagged CAS : CAS(tag0,A -> tag1,B) FAILED (found tag3,node1)  <-- tag changed, ABA detected, retry
is_lock_free: u32=1 u64=1
```

这坐实了两点：单字 CAS 在"值转回原值"时会**误判成功**（Case1，酿成结构损坏）；给指针附上单调 tag 后，同样的地址因 tag 变化而 CAS **正确失败**并触发重试（Case2），ABA 被拦下。末行 `is_lock_free` 显示本机 32/64 位原子均为无锁实现，故上述 CAS 都是真正的硬件无锁原语，非退化为内部加锁。

### CP-10.3.6 阻塞队列变体与两把锁队列

MS 1996 论文其实给了两个算法：上面讲的无锁版，以及一个**用两把锁**（head 锁 + tail 锁）的阻塞队列——入队只抢 tail 锁、出队只抢 head 锁，因为两端锁分离，入队与出队仍能并发，是"简单又实用"的折中。很多实际系统在不需要严格 lock-free 进展性时直接用这个两锁版。

提这一点是为了纠正一个常见误解：MS 队列不等于"那个无锁算法"，论文标题本就是 "Non-Blocking **and Blocking**"。选型上，无锁版抗线程停摆（某线程被抢占不拖累别人）、但代码复杂且要处理 ABA/回收；两锁版简单、低争用下够快，但持锁者被抢占会阻塞同端操作。这与 CP-10.6 的进展性权衡一脉相承。

#### 来源与时效
- AMP 2nd/Revised ch10「Concurrent Queues and the ABA Problem」（核实 2026-07-25）：MS 无锁队列结构（dummy 节点 + head/tail）、入队两步 CAS + 帮忙推进 tail、出队与中间态判定、ABA 成因与用版本号/回收解决。
- Michael & Scott 1996（PODC）原始论文（核实 2026-07-30）：无锁队列 + 两锁阻塞队列两个算法、用"指针+计数"双字 CAS 防 ABA。两源一致；AMP 是其教材化。
- 本机实证（aba.c，gcc 13.3 @2026-07-30）：确定性复现单字 CAS 的 ABA 误判与带标签 CAS 的拦截，真实输出见正文。
- 交叉一致，无冲突。澄清项：MS 队列含无锁与两锁两个变体，勿把 MS 队列等同于单一无锁算法。

## CP-10.4 无锁栈与消除：Treiber 栈、elimination backoff

### CP-10.4.1 Treiber 栈：一个 top 指针 + 两个 CAS

Treiber 栈（1986）是最早、最简单的无锁数据结构：一个链表，只有一个原子指针 `top` 指向栈顶。`push(x)`：新建节点 `n`，读当前 `top` 记为 `t`，令 `n.next=t`，CAS 把 `top` 从 `t` 改成 `n`，失败就重读 `top` 重试。`pop()`：读 `top` 记为 `t`（空则返回空），读 `t.next` 记为 `next`，CAS 把 `top` 从 `t` 改成 `next`，成功则返回 `t` 的值，失败重试。

它是"读快照 → 单次 CAS 提交 → 失败重试"模式最纯粹的样板：整个栈的状态就浓缩在 `top` 一个字里，push/pop 各自只需一次 CAS 就能原子地完成"读旧顶 + 写新顶"。线性化点就是那次成功的 CAS。因为没有锁，任何线程停摆都不拖累别人，是 lock-free 的。

### CP-10.4.2 Treiber 栈的两个软肋：热点争用与 ABA

Treiber 栈简单，但有两个问题。其一是**顺序瓶颈/热点**：所有 push 和 pop 都要 CAS 同一个 `top` 指针，高争用下大家的 CAS 互相失败重试，`top` 所在缓存行被反复争抢作废（呼应 CP-08 的失效风暴），吞吐无法随核数扩展——栈本质上是个**单点竞争**的结构。

其二是 **ABA**：pop 里"读 `top==t`、记 `t.next==next`、CAS `top: t→next`"这段，若 `t` 被 pop 后 free、又被复用重新 push 回栈顶，`top` 转一圈变回 `t`，CAS 误判成功，而 `next` 可能早已不是当前的第二个节点，栈损坏。要纠正一个流行误解：**Treiber 栈并非"天生免疫 ABA"**——在手动内存管理下它和 MS 队列一样需要版本号或安全回收；只是在带 GC 的语言里，节点只要还被某线程引用就不会被复用为新对象，才让 ABA 在实践中不发作。

### CP-10.4.3 消除（elimination）：让 push 和 pop 对冲

消除的洞见极漂亮：**一个 push 紧跟一个 pop，其净效果等于什么都没对栈做**——push 放进去的值直接被 pop 拿走即可，两者**根本不用碰 `top`**。于是可以在栈旁边放一个 **elimination array（消除数组）**，当线程在 `top` 上 CAS 失败（说明正撞车、争用高），它不急着重试，而是随机到消除数组的一个槽位去，看能不能和一个"方向相反"的操作（push 找 pop、pop 找 push）**配对交换**：配上了，push 把值交给 pop，两人各自返回，完全绕开 `top`。

这把"高争用"从灾难变成了机会：争用越高，撞车越多，找到反向伙伴对冲的概率也越高，`top` 的压力反而被卸掉。这类似 CP-10.3 的帮忙，但方向不同——帮忙是"替卡住的人干活"，消除是"两个互补的操作直接私下结清、不惊动公共结构"。配对交换本身用一个无锁的 **exchanger（交换器）** 实现（也是 CAS + 超时退避）。

### CP-10.4.4 Elimination-Backoff Stack：把消除当退避层

AMP 的 **EliminationBackoffStack** 把消除数组当成 Treiber 栈的"退避层"：正常先试 `top` 的 CAS；失败就退避到消除数组尝试配对；配对也超时失败，就回到 `top` 重试。低争用时几乎总走 `top` 快路径（消除很少用上，无额外开销）；高争用时大量操作在消除数组里对冲掉，`top` 争用被显著分散。

它仍然是**线性一致**的栈：配对成功的 push/pop 的线性化点可以安排在"交换发生的那一刻"，且 push 必须线性化在配对 pop 之前，符合"先进后出、且这一对没影响其余元素"的顺序语义——所以对外看起来和一个普通栈无异。要抓住的直觉是：栈天生是单点热点，无法像链表那样靠"操作分散在不同位置"来并行；消除是绕过这个物理瓶颈的巧计——不是让并发操作各改各的，而是让互补操作直接抵消、根本不进公共结构。这也解释了为什么消除对栈特别有效、对队列则要复杂得多（FIFO 语义下 enqueue/dequeue 的对冲要保序，条件苛刻）。

- AMP 2nd/Revised ch11「Concurrent Stacks and Elimination」（核实 2026-07-25）：Treiber 栈（LockFreeStack）、其 ABA 与热点问题、EliminationArray/Exchanger、EliminationBackoffStack 的结构与线性一致性论证。
- Treiber 1986「Systems Programming: Coping with Parallelism」IBM RJ5118（原始技术报告，无锁栈首创，核实 2026-07-30）。
- Hendler, Shavit & Yerushalmi 2004「A Scalable Lock-Free Stack Algorithm」（消除栈原始论文，交叉印证，核实 2026-07-30）。
- 交叉一致。澄清项：Treiber 栈**并非天生免疫 ABA**，只在 GC 语言里因无地址复用而实践上不发作；手动内存下需版本号/安全回收。

## CP-10.5 安全内存回收：hazard pointers / epoch / RCU 解决"何时能 free"

### CP-10.5.1 核心难题：并发下"什么时候能 free 一个节点"

前面所有无锁结构都把节点从结构里"摘除"，但摘除**不等于**能立刻 `free`：当一个线程 CAS 把节点 X 摘走时，可能有别的线程**手里还攥着指向 X 的指针**（它在自己的重试循环里读到过 X，正准备用），此刻 free 掉 X 就是 **use-after-free**，且往往还诱发 ABA（X 的地址被复用）。所以无锁编程真正最难的部分不是算法本身，而是"**确认没有任何线程还可能访问 X**，才敢回收它"。带 GC 的语言把这活儿甩给垃圾回收器，天然回避；C/C++ 等手动内存管理必须自己解决，这就是安全内存回收（Safe Memory Reclamation, SMR）。

要建立的直觉：摘除是"逻辑上不在结构里了"，回收是"物理内存还给分配器"。两者之间必须夹一个"宽限期"——等到确信所有可能持有旧指针的线程都已经放手。三大方案（hazard pointer / epoch / RCU）本质都是给这个"宽限期"下不同的判定标准。

### CP-10.5.2 Hazard Pointers（Michael 2004）：每线程公示"我正在看谁"

hazard pointer（危险指针）的思路：每个线程维护少量（通常 1–2 个）**公开可见的指针槽**，在真正解引用某节点前，先把该节点地址写进自己的 hazard 槽并公示出去，意思是"我正在看这个，谁都别 free 它"。当某线程摘除节点 X 后，不立即 free，而是把 X 放进一个本地"待回收列表"；积累到一定量时**扫描所有线程的 hazard 槽**——只有当 X 不在任何线程的 hazard 槽里时，才真正 free X。

它的优点是**回收上界确定**（每线程 hazard 指针数有限，最多延迟回收的节点数有界）、内存占用可控，对"某个线程卡住"鲁棒（卡住的线程若没公示 hazard，不会无限拖延回收）。代价是**每次解引用前都要写一次 hazard 槽并加一道 store-load 屏障**，读路径不是零开销。适用于对内存占用敏感、要求 lock-free 回收进展性的场景。C++26 已将其标准化为 `<hazard_pointer>`（`std::hazard_pointer`），标注：这是 2024 年定稿的 C++26 特性，编译器/库支持随时间演进，具体可用性随工具链**待核**。

### CP-10.5.3 Epoch-Based Reclamation（EBR）：全局纪元 + 宽限期

基于纪元的回收（EBR）用一个**全局纪元计数器**和每线程的"本地纪元 + 是否在临界区"标志。线程进入无锁操作前，把自己的本地纪元同步到全局纪元并标记"活跃"；退出时清标记。回收时，节点被打上"在哪个纪元被摘除"的标签，放进对应纪元的待回收桶；当系统确认**所有活跃线程都已推进到比该纪元更新的纪元**（意味着没人还停留在能看到旧节点的那个纪元里），该纪元的待回收桶就能整批 free。

EBR 的读路径**几乎零开销**（进/出临界区只是设一个本地标志、偶尔推进全局纪元），批量回收摊销后很高效，是 lock-free 库（如 crossbeam、folly）的常用默认。它的软肋是**一个卡住/长时间不退出临界区的线程会冻结全局纪元推进**，导致待回收内存无限堆积（unbounded）——所以 EBR 通常只保证 lock-free 而非 wait-free 的回收，且不耐"线程被长时间抢占/阻塞"。这正是它与 hazard pointer 的核心权衡：EBR 读更快但回收有界性差，hazard pointer 读稍贵但回收上界确定。

### CP-10.5.4 RCU（Read-Copy-Update）：读端零成本 + 写端等宽限期

RCU 是 EBR 的近亲，专为**读极多写极少**优化（呼应 L4-01·OS-06.5 的内核 RCU）。读者进入"读端临界区"几乎不花钱（内核里常常就是关抢占，无锁无屏障），且读者**从不阻塞**。写者更新时采用"复制—修改—原子替换指针"，把旧版本摘除后**不立即 free**，而是等一个**宽限期（grace period）**——即等到"所有在更新前就已进入读端临界区的读者都已退出"，此时确信没人再引用旧版本，才回收它。等待宽限期可以同步（`synchronize_rcu`）或异步回调（`call_rcu`）。

RCU 的极致在于把几乎所有代价都挪到写端，读端近乎免费，因此在读:写比极高（如路由表、配置、链表遍历）时无可匹敌。代价是写端要承担宽限期等待与复制开销，且它不适合写频繁或需要读者立即看到最新值的场景。要与 EBR 区分：EBR 是通用无锁库的回收机制，RCU 是一整套"读端免同步 + 写端延迟回收"的编程范式（内核里是核心设施）。C++26 也把 RCU 纳入标准库 `<rcu>`（`std::rcu_*`），标注：C++26 特性，工具链可用性**待核**。

### CP-10.5.5 三方案对比与选型直觉

把三者放一起对照最好记：

hazard pointer——读端有开销（每次解引用要公示 + 屏障），但**回收上界确定**、耐线程停摆，适合内存敏感 + 要 lock-free 保证。

epoch (EBR)——读端近乎零开销、批量回收高效，但**回收无界**、怕线程长期滞留临界区，适合无内核支持的通用用户态无锁库、线程行为良性。

RCU——读端零/极低开销且读者不阻塞，写端付宽限期代价，适合**读远多于写**、有系统/内核支持的场景。

一句话选型直觉：问自己"回收延迟能不能无界"和"读路径能不能付一点开销"。要有界回收就上 hazard pointer；读要极致快、能容忍回收滞后就用 EBR；读写严重不对称且能拿到宽限期机制就用 RCU。三者都同时**顺带解决了 ABA**——因为"确保没人还引用旧节点才 free"意味着该地址在有人可能看它时绝不会被复用，ABA 的土壤（地址复用）被铲除。

### CP-10.5.6 与语言/运行时的分账

带 GC 的托管语言（Java/C#/Go）里，这一整节的问题大部分被 GC 兜住：只要还有可达引用，对象就不会被回收，use-after-free 和"地址复用型 ABA"都不会发生（值层面的 ABA 仍需 `AtomicStampedReference` 类手段）。所以 AMP 用 Java 讲无锁结构时几乎不谈 SMR——不是不重要，是被运行时隐藏了。

C/C++/Rust 等手动或半自动内存管理里，SMR 是无锁工程的**主承重难点**，选错方案会导致内存爆掉或悬垂访问。Rust 生态用 `crossbeam-epoch`（EBR）、C++ 标准从 C++26 起提供 hazard pointer 与 RCU。初学者要记住的分账：**无锁算法的"逻辑正确性"和"内存安全回收"是两个相对独立的问题**，前者靠 mark+CAS+帮忙，后者靠 SMR；很多教材/示例只讲前者（假设有 GC），移植到无 GC 环境时必须补上后者。

## CP-10.6 死锁 / 活锁的算法层回避：锁序、无锁绕开四条件、活锁

### CP-10.6.1 分账：本节只讲算法层，四条件本身归 OS-07

死锁的四个必要条件（Coffman 条件：互斥、持有并等待、不可抢占、循环等待）的完整列举、死锁检测（资源分配图找环）、死锁避免（银行家算法/安全状态）属于**操作系统资源管理层**，归 L4-01·OS-07，本节不重复。本节只回答并发**算法**层的问题：写并发数据结构时，怎么在代码里主动回避死锁；无锁结构又是靠什么"结构上"就不可能死锁；以及无锁不是免费午餐——它把死锁换成了活锁。

先给一句锚定：死锁四条件是"要发生死锁必须四条全满足"，所以**破坏任意一条**就能防死锁。基于锁的算法主要破坏"循环等待"（靠锁序），无锁算法则直接釜底抽薪破坏"持有并等待/互斥"这一支。

### CP-10.6.2 锁序（lock ordering）：破坏循环等待

基于锁的并发结构里最实用的防死锁纪律是**给所有锁定义一个全局线性顺序，任何线程都必须按这个顺序加锁**。经典的死锁是两个线程 AB–BA：T1 持锁 A 求锁 B，T2 持锁 B 求锁 A，互等成环。若强制"编号小的锁先加"，两人都得先拿 A 再拿 B，就不可能形成 A→B 和 B→A 的环——循环等待条件被破坏。

CP-10.1.3 的细粒度链表交替上锁正是锁序的实例：因为链表有序、总是按 key 从小到大加锁，任意两个线程加锁的方向一致，永不成环。锁序的难点是工程性的——大型系统里锁很多、加锁点分散，维护一致的全局序很难，容易被后加的代码破坏（这类 bug 用 `-fsanitize=thread` 或 lockdep 类工具查）。要记住：锁序是"约定"，靠纪律和工具维持，不是结构自动保证的。

### CP-10.6.3 无锁如何"结构上"绕开四条件

无锁算法压根不持有锁，于是死锁四条件里的**"持有并等待"和"互斥（对锁的独占持有）"直接不成立**：没有哪个线程"占着一个别人要的资源不放"，大家只是各自 CAS、失败就重读重试，谁也不会因为等某个被别人占住的锁而永久阻塞。所以无锁结构**在设计上就不可能死锁**——这是它相对锁最本质的健壮性优势，尤其是能抵抗"持锁线程被抢占甚至崩溃"这种会拖垮全系统的情形。

这对应 CP-02 的进展性谱系：lock-free 保证**系统整体**总有线程在有限步内前进（某线程失败必因为另一线程成功了），wait-free 更强、保证**每个线程**都在有限步内前进，obstruction-free 最弱、只保证"在没有争用干扰时单线程能前进"。锁只能给到"deadlock-free / starvation-free"这类阻塞式进展性，一旦持锁者停摆全盘皆输；无锁的 lock-free 进展性不依赖任何线程持续运行，这就是它绕开死锁的根。

### CP-10.6.4 代价：无锁把死锁换成了活锁

无锁不是没有进展风险，它把死锁换成了**活锁（livelock）**：多个线程的 CAS 反复互相失败——你 CAS 到一半我改了、我 CAS 到一半你又改了——大家都在忙着重试却谁也提交不成功，CPU 满转但整体不前进。死锁是"都不动"，活锁是"都在动但都在原地打转"。注意：纯 lock-free 结构从定义上**不会永久活锁**（一个线程 CAS 失败必然是因为另一个成功了，系统整体仍在前进），但**单个线程可能被持续"饿死"**（老是它的 CAS 失败、别人一直成功），这就是 lock-free 不蕴含 wait-free 的现实体现。

活锁在带退避的自旋/消除里也会以另一种形式出现：两个线程反复"检测到冲突→同时退让→同时重试→再冲突"，像走廊里两人反复左右互让谁也过不去。要建立的对照：死锁需要破坏四条件之一来防；活锁的通用解药是**引入随机化/退避打破对称**——让重试时刻错开，见下节。

### CP-10.6.5 缓解活锁与饥饿：退避、随机化、helping

缓解活锁的主要手段有三。其一是**指数退避 + 随机化**（呼应 CP-08.2）：CAS 失败后随机等一小段再试，把多个线程的重试时刻错开，降低持续对撞的概率——这是对付活锁最常用的招。其二是**helping（帮忙）**：像 CP-10.2.4 链表清理、CP-10.3.2 推进 tail 那样，让后到的线程替卡住的操作完成剩余步骤，保证被"看到"的半成品操作一定能被推进，这是把 lock-free 提升到接近 wait-free 的关键技术。其三是消除（CP-10.4.3）：让互补操作直接对冲、根本不进公共竞争点，从源头减少 CAS 撞车。

收尾的心智模型：锁的世界里，正确性的敌人是死锁，武器是锁序（破坏循环等待）；无锁的世界里，结构上免疫死锁，但正确性的敌人变成了活锁/饥饿与内存回收，武器是退避随机化（打破对称）、helping（保证半成品被推进）、以及 CP-10.5 的安全回收。选无锁 vs 用锁，本质是在"抗停摆的强进展性 + 复杂的回收/活锁工程"和"简单的锁代码 + 怕持锁者停摆"之间权衡——这与 CP-10.3.6 的 MS 无锁版 vs 两锁版是同一个取舍在不同结构上的复现。
