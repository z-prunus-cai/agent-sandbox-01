## CP-14.1 共享内存 vs 消息传递：两大范式对立

### CP-14.1.1 两种协调并发实体的根本方式

并发实体（线程、进程、协程）之间要协作，本质上只有两种交换信息的方式。**共享内存**：多个实体能访问同一块内存，一方写、另一方读，就完成了"通信"；因为大家踩在同一块地上，必须用锁、原子操作、内存屏障来保证不会互相踩踏（这正是本课前面十几个大主题的全部内容）。**消息传递**：每个实体只拥有自己的私有内存，谁也看不见谁的内存，要交换信息就把数据打包成一条**消息**显式地发给对方、对方显式地收。

共享内存像一间合租房里公用的白板，室友们都能上去写、上去擦，方便但必须约好"谁在写时别人别动"（加锁），否则内容就乱了。消息传递像各自住独立房间、只能靠递纸条沟通——你永远碰不到我房间里的东西，想让我知道什么就写张纸条塞过来。递纸条要多花一道"抄写"的功夫（消息拷贝），但根本不存在"两人同时改同一处白板"的问题，因为压根没有共用的白板。这就是消息传递最大的卖点：**从结构上消灭了共享状态，也就从结构上消灭了数据竞争**——不是靠加锁把竞争"管住"，而是让竞争无从发生。

### CP-14.1.2 "Do not communicate by sharing memory; share memory by communicating"

这句 Go 社区的箴言是消息传递范式的总纲。反过来读最清楚：不要用"共享一块内存"的方式去通信（那要靠锁保护、容易错），而要用"通信"这个动作本身去传递数据的所有权——把数据从一个实体"发"给另一个，发出去之后自己就不再碰它。数据在任一时刻只被一个实体"拥有"，所有权随消息转移，于是天然不需要锁。

假设线程 A 算出一个结果要交给线程 B。共享内存写法是 A 把结果写进一个全局变量、B 去读，中间要用锁或原子操作+内存序保证 B 读到的是 A 写完的完整值（撕裂、可见性都是坑）。消息传递写法是 A 把结果通过一个 channel 发出去、B 从 channel 收——一旦 A 发出，就当作"这个数据现在归 B 了"，A 不再引用它；B 收到就是收到完整的值，不需要任何锁。要抓住的领悟是：这不是语法糖的差别，而是**心智模型的转向**——从"多方共同守护一块共享地"转向"数据像接力棒一样在实体间单向传递，任何时刻只有一人持棒"。理解了这句箴言，就理解了后面 CSP、actor、MPI 三种落地的共同灵魂。

### CP-14.1.3 两范式的权衡与"没有银弹"

消息传递不是免费的，两范式各有代价，选型要看场景。共享内存的**优点**是快——同机内读写共享内存是纳秒级，不用拷贝、不用序列化；**缺点**是难写对——锁、死锁、数据竞争、内存序，全是本课前十几章在治的病，且只能在同一地址空间内用。消息传递的**优点**是隔离带来的简单与可扩展——无共享状态就无数据竞争，且消息可以跨地址空间、跨进程、甚至跨机器（分布式天然是消息传递）；**缺点**是每条消息通常要拷贝或序列化（有开销），且要显式设计通信协议、处理消息顺序与背压。

数据量大、更新频繁、且都在同一进程内、对延迟极敏感——共享内存往往更划算（但你得会用锁/原子）。实体天然独立、要跨进程或跨机器、想要强隔离和容错、或团队更怕竞争 bug——消息传递更省心。现实中两者常常混用：一个进程内部用共享内存+锁跑得飞快，进程之间用消息传递做隔离与扩展。还有个常见误解要澄清：消息传递在**实现底层**往往仍然用共享内存（比如 Go channel 内部就是一段带锁的共享缓冲），但它把共享内存**封装在语言/库里**，对使用者暴露的是"发/收消息"的干净接口——你写代码时不再直接面对那块共享内存，竞争也就不再是你的负担。

- Go 官方文档「Effective Go」§Sharing / Go 官方博客「Share Memory By Communicating」（golang.org/doc，核实 2026-07-30）：箴言原文 "Do not communicate by sharing memory; instead, share memory by communicating."，及"数据所有权随通信转移、任一时刻只一个 goroutine 持有"的解释。

## CP-14.2 CSP / channel：Go 的 goroutine + channel 模型

### CP-14.2.1 CSP：Hoare 的"顺序进程靠通信协作"

CSP（Communicating Sequential Processes，通信顺序进程）是 Hoare 1978 年提出的并发模型。核心主张：一个并发系统由若干**各自顺序执行、互不共享变量**的进程组成，进程之间唯一的协作方式是**通过通道（channel）收发消息**。CSP 里的通信是**同步的**（rendezvous，会合）：发送方执行"输出"、接收方执行"输入"，两者必须**同时就绪**，消息才在那一刻传递，任一方先到就阻塞等对方——像两人击掌，必须同时伸手才拍得响。CSP 还从 Dijkstra 的"卫式命令"（guarded commands）借来选择结构，让一个进程能同时守候多个通信、哪个先就绪就走哪个。

CSP 把"并发"拆成"一堆各自跑得笔直的小程序 + 它们之间明确的通信线路"。你不用再想"这个变量会不会被别的线程同时改"（根本没有共享变量），只需想清楚"谁在哪条线路上、什么时候、发什么消息给谁"。同步会合的意义是：一条消息成功传递，就意味着收发双方在那个瞬间"对上了点"，这本身就是一次天然的同步——发送成功即知对方已收，不需要额外的锁或信号。CSP 是后来 occam 语言、Go channel 的直接思想源头。

### CP-14.2.2 goroutine 与 channel：Go 对 CSP 的落地

Go 把 CSP 落成两个语言构件。**goroutine** 是 CSP 里的"顺序进程"——用 `go f()` 启动一个极轻量的并发执行流（不是 OS 线程，由 Go 运行时以 M:N 方式多路复用到少量 OS 线程上，创建成千上万个也很便宜）。**channel** 是 CSP 里的通道，且在 Go 里是**一等值**（可以像普通变量一样传递、存进结构体），这点比 CSP 原版更灵活。声明与收发的基本形态各自独立成行：

ch := make(chan int)     // 无缓冲 channel

ch <- v                  // 发送：把 v 送入 ch

v := <-ch                // 接收：从 ch 取出一个值

**无缓冲 channel**（`make(chan int)`）就是 CSP 的同步会合：发送阻塞到有接收方就绪、接收阻塞到有发送方就绪，二者在同一瞬间交接。**有缓冲 channel**（`make(chan int, N)`，容量 N）放松成异步：缓冲没满时发送不阻塞、缓冲非空时接收不阻塞，只有满了才阻塞发送、空了才阻塞接收——这是 Go 对纯 CSP 的一个扩展。

goroutine 是"演员"，channel 是"传送带"。无缓冲传送带要求两头的人同时到位、手把手交货（同步）；有缓冲传送带上能先堆 N 件货，放货的人不必等取货的人（异步，直到堆满）。写 Go 并发的标准姿势就是"起一堆 goroutine，用 channel 把它们串起来"，而不是让它们去抢同一个共享变量。

### CP-14.2.3 select、close、range 与死锁检测（含本机实证）

Go 提供三个配套构件把 channel 用活。**`select`** 对应 CSP 的卫式选择：同时守候多个 channel 操作，哪个先就绪就执行哪个分支，多个同时就绪则随机选一个（避免饥饿）——常用于超时、多路复用、优雅退出。**`close(ch)`** 关闭 channel，表示"不会再有值了"；对已关闭 channel 接收会立即返回零值且第二返回值为 false。**`for v := range ch`** 持续接收直到 channel 关闭并取空——这是"生产者关闭、消费者自然收尾"的惯用法。

本机实证坐实工具链与语义（本库编排清单把 Go 标「待核」，此处坐实：**本机实装 go1.24.7，未列入基线但可用**）。基线 go1.24.7 @2026-07-30，4 核 x86-64：无缓冲 channel 会合、4-worker 池 fan-out/fan-in（1..9 的平方和 = 285）、`select` 多路，真实输出：

```
# go run chan.go
recv: 42
sum of squares 1..9: 285
select got: hello
```

Go 运行时还内建**死锁检测**：当所有 goroutine 都阻塞在 channel 上、无人能推进时，运行时直接报致命错误退出。对"无缓冲 channel 发送但无接收方"的最小死锁，本机实测触发：

```
# go run dead.go   (ch := make(chan int); ch <- 1  // 无接收方)
fatal error: all goroutines are asleep - deadlock!
goroutine 1 [chan send]:
main.main()
```

其一，channel 的收发天然提供**内存可见性保证**——Go 内存模型规定"一次 channel 发送 happens-before 对应的接收完成"，所以通过 channel 传过去的数据，接收方读到的一定是发送方写完的完整状态，不需要额外加锁（这正是它替代共享内存的底气，呼应本课大主题05/06 的 happens-before）。其二，**只由发送方 close、且 close 后不可再发**，向已关闭 channel 发送会 panic；range 一个永不关闭的 channel 会永远阻塞。其三，Go 的死锁检测只在"所有 goroutine 都睡死"时才报，部分死锁（还有 goroutine 在跑）它发现不了——别把它当完整的死锁分析器。

- 冲突/差异（显式标注）：**同步性**——CSP 原版通信全同步（rendezvous），Go 无缓冲 channel 与之一致，但 Go 额外提供**有缓冲 channel**做有限异步，是对纯 CSP 的扩展；**命名**——CSP 原版按进程名指定通信对端（`P!v` / `P?x`），Go 把 channel 做成一等值、按 channel 而非进程命名，更灵活。两点差异不矛盾，是"经典模型 vs 工程语言"的取舍，两源各自自洽。

## CP-14.3 actor 模型：Erlang 进程 / 邮箱、无共享状态

### CP-14.3.1 actor：以"响应消息"为唯一行为的并发单元

actor 模型由 Hewitt、Bishop、Steiger 于 1973 年提出。一个 **actor** 是一个并发计算单元，拥有自己的私有状态和一个**邮箱**（mailbox）。actor 之间**不共享任何状态**，唯一的交互是**异步发送消息**。收到一条消息时，一个 actor 只能做三件事：(1) 向它知道地址的其他 actor 发送有限条消息；(2) 创建有限个新 actor；(3) 指定"处理下一条消息时的行为"（即更新自己的内部状态）。除此之外别无他法——这三条就是 actor 全部的能力。

把每个 actor 想成一个只认信箱的独居者。你想让它做事，只能往它信箱里投信（发消息）；它什么时候拆信、怎么回应，完全由它自己决定，你管不着也看不见它屋里的东西（私有状态）。它读一封信，可能回你几封信、可能雇几个新帮手（创建 actor）、可能改变自己下次读信的心情（更新状态）。关键三点：消息是**异步**的（投进信箱就走，不等对方读）、状态是**完全私有**的（无共享 = 无锁 = 无数据竞争）、actor 靠**地址**互相寻址（我要给你发消息，得先知道你的信箱地址）。

### CP-14.3.2 Erlang 进程：actor 模型的经典落地

Erlang 是 actor 模型最有名的工业落地。Erlang 的"进程"是**语言级的轻量进程**（不是 OS 进程，由 BEAM 虚拟机调度，一个系统可轻松跑几十万个），每个进程有独立的堆和一个邮箱，进程间**不共享内存**。三个核心原语各自独立成行：

Pid = spawn(fun worker/0)    % 创建进程，返回它的地址 Pid

Pid ! Message                % 发送：把 Message 投入 Pid 的邮箱（异步）

receive Pattern -> Body end  % 接收：从邮箱按模式匹配取消息

`spawn` 创建 actor 并返回其进程标识 `Pid`（就是地址）；`!` 是发送运算符，把消息异步投进目标邮箱（发完立即返回，不等对方处理）；`receive` 从本进程邮箱里**按模式匹配**取出消息处理，匹配不上的消息暂留邮箱、下次再看。

Erlang 进程之间只有"发消息"这一条线，没有共享变量、没有锁——所以 Erlang 程序员几乎不写锁，也几乎不遇数据竞争，这是 actor 范式最直接的红利。Erlang 还有一套著名的容错哲学 **"let it crash"（让它崩）**：进程出错就让它崩掉，由"监督者"（supervisor）进程按预设策略把它重启到已知良好状态，而不是在每个进程里写一堆防御性错误处理。这依赖进程间的**隔离**（一个进程崩了不会带坏别人的内存，因为本就不共享）和**链接/监控**机制（一个进程能感知另一个的死亡）。这套"隔离进程 + 监督树"是 Erlang/OTP 做高可用电信系统的招牌。

### CP-14.3.3 actor 与 CSP 的分野

actor 和 CSP 都是消息传递、都无共享状态，但两处关键不同，初学者极易混。其一，**同步性**：CSP 通信默认**同步会合**（收发双方必须同时就位），actor 消息是**异步**的（发出即走、投进邮箱就不管了）。其二，**寻址对象**：CSP 里进程通过**命名的 channel**通信（消息发给通道，通道是通信的媒介），actor 直接通过**对端的地址（Pid）**通信（消息发给某个具体 actor，没有独立的"通道"实体）；因此 actor 的拓扑是动态的、以 actor 身份为中心，CSP 更以通道为中心。

CSP 像"两人对着一条固定的传送带手把手交货"（同步、以传送带/channel 为中心）；actor 像"给某个人的信箱投信"（异步、以收信人/地址为中心，投完就走）。Go 是 CSP 一系，Erlang 是 actor 一系；Akka（Scala/Java）、Elixir（跑在 BEAM 上）也是 actor 一系。两者没有绝对优劣：actor 的异步+地址寻址更贴近分布式与容错场景，CSP 的同步会合让"消息传递即同步点"的推理更直接。

#### 来源与时效
- Hewitt, Bishop, Steiger「A Universal Modular ACTOR Formalism for Artificial Intelligence」IJCAI 1973（核实 2026-07-30）：actor 三条基本能力（send/create/designate-behavior）、异步消息、无共享状态的一手定义。
- Erlang/OTP 官方文档：Erlang Reference Manual（Processes、`spawn`/`!`(send)/`receive`）、"Getting Started / Concurrent Programming"、OTP Design Principles（Supervisor、"let it crash"）（erlang.org/doc；语言原语自 Erlang 诞生即稳定，OTP 为现役框架，核实 2026-07-30；本机未装 `erl`，语义取自官方文档，未做实机验证）。
- 交叉一致与差异：Hewitt（异步、地址寻址、无共享）与 Erlang（`!` 异步发送到 Pid 邮箱、进程无共享内存）在核心上完全一致。与 CP-14.2 的 CSP 对比处（同步 vs 异步、channel 命名 vs 地址命名）为两模型的定义性差异，已在 14.3.3 显式标注，非来源冲突。

## CP-14.4 MPI：进程级显式消息与集合通信

### CP-14.4.1 MPI 是什么：分布式内存下的进程级消息传递标准

MPI（Message Passing Interface，消息传递接口）是高性能计算（HPC）领域**进程间消息传递的事实标准**——注意它是一份**标准/API 规范**，不是某个具体库；MPICH、Open MPI 等是它的实现。MPI 面向**分布式内存**模型：程序以 **SPMD**（Single Program Multiple Data，同一份程序被启动成多个进程）方式运行，每个进程有独立地址空间、互不共享内存，靠显式收发消息协作。每个进程在一个**通信域**（communicator，最基础的是 `MPI_COMM_WORLD`）里有唯一编号 **rank**（0..size−1），程序靠"我是几号进程、一共几个进程"来分工。

MPI 就是"把同一份程序在一堆机器/核上各开一份，每份靠自己的编号 rank 决定该干哪一块活，需要交换数据时就显式地 send/recv"。它和共享内存最大的不同在于**显式**二字——没有隐式共享的变量，谁要什么数据，必须有人明确地发、有人明确地收，通信是代码里看得见的一行调用。这也是它能跨成千上万台机器扩展的原因：机器之间本就没有共享内存，消息传递是唯一自然的协作方式。它和前两节（Go/Erlang 的语言内轻量进程）的区别是：MPI 的"进程"是**真正的 OS 进程、常跨物理机**，量级重得多，定位是集群级科学计算。

### CP-14.4.2 点对点通信：send / recv

MPI 最基本的通信是两个进程间的点对点收发。**阻塞式**的核心是一对：

MPI_Send(buf, count, datatype, dest, tag, comm)

MPI_Recv(buf, count, datatype, source, tag, comm, status)

一个进程调 `MPI_Send` 把数据发给编号为 `dest` 的进程，另一个进程调 `MPI_Recv` 从 `source` 收；`tag` 是消息标签（用于区分不同种类的消息），`comm` 是通信域。还有**非阻塞式** `MPI_Isend` / `MPI_Irecv`（立即返回一个请求句柄，稍后用 `MPI_Wait`/`MPI_Test` 确认完成）——用于让通信和计算重叠、以及避免收发次序不当引起的死锁。

`MPI_Send` 是否阻塞、何时返回，和消息大小、实现的缓冲策略有关——小消息常被实现缓冲后立即返回，大消息可能要等对端 `MPI_Recv` 就绪才返回。一个经典死锁是"两个进程都先 `MPI_Send` 给对方、再 `MPI_Recv`"：若消息大到都要等对端先收，双方就互相干等——解法是一方调换收发顺序，或改用非阻塞 `MPI_Isend`/`MPI_Irecv`，或用 `MPI_Sendrecv`。这和 CSP/channel 的同步会合死锁是同一类问题的不同面孔。

### CP-14.4.3 集合通信：一群进程一起动

MPI 的招牌是**集合通信**（collective communication）——通信域里**所有进程一起参与**的一次操作，一行调用完成本来要写一堆点对点的模式。常用几个：

MPI_Bcast    — 广播：一个根进程把同一份数据发给所有进程

MPI_Scatter  — 散射：根进程把一个数组切块、每个进程分到一块

MPI_Gather   — 收集：每个进程的一块数据汇集回根进程（Scatter 的逆）

MPI_Reduce   — 归约：把各进程的值按运算（求和/求最大等）合并到根进程

MPI_Allreduce— 归约后把结果发回所有进程（Reduce + Bcast）

MPI_Barrier  — 栅栏：所有进程都到达此点才一起继续

集合通信是"团体操"——不是两个人递东西，而是全班同时做一个动作。`Scatter`+`Gather` 是典型的"主进程切菜分给大家、各自炒完再收回来"（数据并行的骨架，呼应 CP-14.5）；`Allreduce` 是"每人报个数、当场算出总和再通知每个人"（分布式训练里同步梯度就是它）。用集合操作而非手写点对点，不仅代码短，实现还能用树形/环形算法把通信复杂度从 O(P) 降到 O(log P)——这是 HPC 里 MPI 不可替代的价值。

### CP-14.4.4 本机状态与范式备用实证

本库编排清单把 MPI 标「待核」，本报告坐实：**本机确无 MPI**——`mpicc`、`mpirun`、`mpiexec` 均不存在，无法在本机做 MPI 实机验证（如实标注"未取"）。MPI 语义取自 MPI 标准文本。为给"进程级显式消息传递"一个可跑的范式感受，用 node v22.22.2 的 `worker_threads`（worker 间无共享堆、仅靠 `postMessage`/`on('message')` 传消息，形态上与 actor 邮箱/MPI 收发同源）作**范式备用**实测——3 个 worker 各算一个值、经消息汇总（10+20+30），真实输出：

```
# node worker.js
total: 60
```

这个 node 例子**不是 MPI**，只是借它演示"独立执行体不共享内存、只发消息、由主体汇总"的消息传递骨架（很接近 MPI 的 `Gather`/`Reduce`）。要真跑 MPI，需在装了 Open MPI/MPICH 的环境用 `mpicc` 编译、`mpirun -np N` 启动——本机不具备，留待环境补齐后验证。

#### 来源与时效
- MPI Standard（MPI Forum）：MPI 4.1（2023-11-02 发布）为当前正式版；4.0（2021-06）引入持久化集合、会话模型等；点对点 `MPI_Send`/`MPI_Recv`/`MPI_Isend`、集合 `MPI_Bcast`/`Scatter`/`Gather`/`Reduce`/`Allreduce`/`Barrier` 语义均取自标准文本（mpi-forum.org，核实 2026-07-30；⚙下一主版 MPI 5.0 在推进中，以 MPI Forum 最新发布为准）。
- 实现印证：MPICH、Open MPI 官方文档（作"标准 vs 实现分账"的实现侧举例，非承重）。
- 本机实证：**MPI 未装**（`mpicc`/`mpirun`/`mpiexec` 不存在，坐实「待核」为"未取"）；node v22.22.2 `worker_threads` 消息传递作范式备用，真实输出见正文。
- 交叉一致：SPMD + rank/communicator + 点对点/集合通信为 MPI 标准的稳定核心，各实现一致，无冲突。

## CP-14.5 数据并行 vs 任务并行：划分维度差异与选型

### CP-14.5.1 两种切分工作的维度

并行的本质是"把一堆工作切开、同时做"，而"怎么切"有两个正交维度。**数据并行**（data parallelism）：对**大量数据元素施加同一种操作**，把数据切成块、每个处理器处理一块——切的是**数据**，各处理器跑的是**相同**的代码。**任务并行**（task parallelism）：把工作拆成**若干种不同的任务/功能**，让它们在不同处理器上同时跑——切的是**功能/任务**，各处理器可能跑**不同**的代码。

给一百万个数字每个加一——这是数据并行（同一个"加一"操作，铺到一百万份数据上，切数据）。同时"下载文件 + 解析日志 + 更新界面"三件不同的事一起做——这是任务并行（三个不同的功能同时跑，切任务）。一句话记：**数据并行是"同一件事做很多份"，任务并行是"很多件不同的事一起做"**。它们对应 Flynn 分类里的 SIMD（单指令多数据，数据并行的硬件味）与 MIMD（多指令多数据，任务并行的硬件味）。

### CP-14.5.2 各自的典型落地

CPU 的 **SIMD 向量指令**（一条指令算 8 个 float，SSE/AVX）、**GPU**（成千上万线程对数据网格做同一操作，深度学习训练的主力）、MPI 的 **Scatter/Gather**（把大数组切块分给各进程，CP-14.4.3）、以及各种 **map/parallel-for**（对集合每个元素并行施加同一函数）。数据并行也常叫 **SPMD**——同一份程序、多份数据。

**fork-join**（本课大主题12，把一个问题分叉成可并行的不同子任务再汇合）、**pipeline/流水线**（不同阶段是不同任务，数据流过各阶段，各阶段并行）、**work-stealing 任务调度器**（大主题12.3，把异构任务动态铺到空闲核）、以及 actor/CSP 里"不同 actor 干不同的活"。

CP-14.4 的 MPI 集合通信里，`Scatter`/`Gather`/`Allreduce` 天生是数据并行的骨架（切数据、同操作、再汇总）；CP-14.2/14.3 的 channel/actor 天生适合任务并行（不同执行体干不同的活、靠消息串起来）。所以这一节不是孤立的第五个概念，而是把前四节按"切数据还是切任务"重新归了一次类。

### CP-14.5.3 选型：按什么选，为什么常常混用

选型的第一判据是**工作的结构**。数据量巨大、且对每个元素做的是**同一种规则的操作**（矩阵运算、图像逐像素处理、神经网络前向）——数据并行，它随数据规模线性扩展、且极其适配 GPU/SIMD 这类"同操作大批量"的硬件。工作由**若干性质不同、可独立推进的子任务**组成、或任务量不规则/动态生成——任务并行，它能把异构的活铺到多核、靠 work-stealing 自动均衡负载。

数据并行的强项是**可扩展性好、易映射到 GPU、负载天然均衡**（每块数据活儿差不多），弱点是要求问题"规整"（同操作、弱依赖）；任务并行的强项是**灵活、能表达复杂依赖（DAG）**，弱点是负载可能不均、调度开销更高。现实的大型并行程序几乎总是**两者混合**：外层用任务并行把不同阶段/模块铺开，某个计算密集的阶段内部再用数据并行吃满 GPU/向量单元（例如分布式深度学习：进程间是任务/流水线并行 + 用 MPI/NCCL 的 `Allreduce` 同步梯度是数据并行）。要抓住的领悟是：数据并行 vs 任务并行不是二选一的教条，而是分析一段工作时**先问"这里是同操作切数据、还是异任务切功能"**的一把尺子——用对了尺子，前面四节的范式该用哪个就清楚了。
