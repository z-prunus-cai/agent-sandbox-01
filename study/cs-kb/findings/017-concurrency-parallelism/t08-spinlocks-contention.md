## CP-08.1 TAS vs TTAS：test-and-set 的缓存行失效风暴与先读再试的改进

### CP-08.1.1 自旋锁与最朴素的 TASLock

自旋锁（spin lock）是这样一把锁：线程拿不到锁时不睡眠、不让出 CPU，而是原地循环（"自旋"）不断重试，直到拿到为止。最朴素的实现叫 **TASLock**，用一个硬件原语 test-and-set（TAS）：TAS 原子地把一个布尔变量置为 `true` 并返回它**原来**的值。获取锁就是反复 TAS，直到看见返回 `false`（说明"之前是空的，现在被我占上了"）；释放锁就是把它写回 `false`。

如果临界区很短（比如只改几个变量），线程睡眠再被唤醒的开销（上下文切换、进内核）比"忙等几百纳秒"还大，那还不如原地转圈等着。所以自旋锁是"短临界区、多核"场景的首选。要抓住的直觉是——自旋锁的对错很简单（TAS 的原子性保证了互斥），本大主题从头到尾操心的**不是正确性而是性能**：当很多核同时抢这把锁时，它会不会因为底层缓存/总线流量而"越抢越慢"。

### CP-08.1.2 TAS 为什么不可扩展：缓存行失效风暴

TASLock 在高争用下会**急剧劣化**，根因是每一次 TAS 都是一次**写操作**。在 MESI 类缓存一致性协议下，一个核要写某个内存位置，必须先把该缓存行变成"独占/修改"状态，这就要求**作废（invalidate）所有其他核上这一行的副本**。于是当 n 个核都在自旋、都在反复 TAS 那同一个锁变量时，每个核的每次 TAS 都在总线上广播一次作废，把其他 n−1 个核刚拿到的缓存副本全部打掉，其他核只好重新去总线上取——如此往复形成**缓存行失效风暴**（cache-line invalidation storm），一致性网络被自旋流量占满，连**持锁线程释放锁**所需的那次写都被这股洪流拖慢。结果是核越多锁越慢，完全违背"加核提速"的期望。

问题不在"循环"消耗 CPU，而在循环体里那条 **TAS 是写**。写=要独占=要作废别人。哪怕锁其实没被释放、状态没变，每次 TAS 也照样发起一次"我要独占写"的一致性事务。这就是"忙等本身不贵，忙等时碰共享写变量才贵"。这个观察是理解后面 TTAS、backoff、队列锁全部改进的出发点。

### CP-08.1.3 TTAS：先读再试，把自旋降级为纯读

**TTALock**（test-and-test-and-set，TTAS）的改进只有一句话：**自旋时先用普通读去看锁是不是空的，只有看起来空了才真的去做一次 TAS**。伪代码的核心是：

```
while (true) {
    while (lock == true) { /* 纯读自旋，不写 */ }   // test
    if (TAS(lock) == false) return;                  // test-and-set
}
```

内层 `while (lock == true)` 是**纯读**循环。在 MESI 下，多个核同时**读**同一个缓存行是允许的——大家可以各自持有该行的"共享（Shared）"副本，读命中自己的 L1 缓存，**不产生任何总线流量**。所以只要锁一直被别人持有（值不变），所有等待者都安安静静地在本地缓存里空转，一致性网络是干净的。只有当持锁者释放锁（把值写成 `false`）时，才广播一次作废，等待者们的读这才未命中、去总线取到新值、然后才各自尝试那一次真正的 TAS。这样就把"每次重试一次写"降成了"绝大多数时间是本地读、极少数时刻才写"。

要点在于"先读再试"这层过滤：读是可以多核共享缓存、零总线开销的，写才是要独占、要作废别人的。TTAS 把昂贵的写挡在了"看起来有戏"之后。这也解释了为什么 `volatile`/`_Atomic` 变量的**读**在自旋里是廉价的，而 RMW（读改写）才是贵的——CP-06 的 memory_order 只管正确性，这里管的是它落到缓存一致性上的成本。

### CP-08.1.4 TTAS 仍未根治：释放时刻的争用尖峰

TTAS 大幅改善了"持锁期间"的开销，但**没有根治**争用。问题出在释放的那一瞬间：锁一被写成 `false`，所有等待者的纯读几乎同时未命中、同时去取新值、然后**同时**发起 TAS 争抢。这一刻又爆发一次失效风暴——只不过从"持锁全程持续风暴"缩短成了"每次释放时一次尖峰"。而且只有一个核能抢到，其余 n−1 个核的 TAS 都白做（又各自作废了一轮），失败后退回纯读自旋。争用越高，这种"释放→群体扑抢→只有一个赢"的浪费越明显。

CP-08.2 用**退避**让等待者错开重试时刻、削掉这个尖峰；CP-08.3 用**队列锁**让每个等待者只在自己的私有变量上自旋、释放时只精确唤醒队首一个人，从根上消除群体扑抢。AMP 用真实机器的吞吐曲线展示了 TAS < TTAS < backoff < 队列锁这条递进；本报告不复制其图，但结论一致：TTAS 是关键的第一步，却不是终点。

## CP-08.2 指数退避：backoff 缓解争用

### CP-08.2.1 退避的基本思想

**退避**（backoff）的想法直接来自 CP-08.1.4 的尖峰问题：既然一释放锁大家就一窝蜂扑抢、反而互相拖慢，那就让每个抢锁失败的线程**先等一小段随机时间再重试**，把大家的重试时刻**错开**，降低同一瞬间的碰撞人数。这类似以太网 CSMA/CD 的冲突退避——检测到冲突就退让一会儿再发。

直觉上，争用越激烈，就应该退得越久：一次抢不到，说明现在人多，那下次多等等。退避把"贪婪地每时每刻都试"变成"体面地错峰重试"，用一点点延迟换回被削掉的总线风暴。要注意退避是**启发式**的性能优化，不改变锁的正确性——无论退多久，TAS 的原子性仍然保证只有一个人进临界区。

### CP-08.2.2 指数退避与 TTAS 结合：BackoffLock

**指数退避**（exponential backoff）是退避的标准做法：每次抢锁失败就把等待时长**翻倍**，但不超过一个上限。把它套在 TTAS 外面就是 AMP 的 **BackoffLock**：纯读自旋看到锁空 → TAS → 若失败，随机睡一段 `[0, delay)` 的时间，然后

```
delay = min(maxDelay, delay * 2)
```

再回去自旋重试；成功进临界区后把 `delay` 重置回初始的 `minDelay`。

为什么翻倍而不是固定等？因为最优退避时长事先不可知，且随争用动态变化。指数增长能**自适应**：轻争用时几次就抢到，`delay` 还很小，几乎无额外延迟；重争用时反复失败，`delay` 迅速涨到足够大，把重试频率压下来。上限 `maxDelay` 防止某个倒霉线程退避到"永远醒不过来"的荒谬时长。随机化（在 `[0, delay)` 里取随机点而非固定 `delay`）是关键——如果所有失败者都精确等同样长，它们会**同步**地一起醒来再次扑抢，等于没退；随机化才真正把它们打散。这个"翻倍 + 封顶 + 随机"三件套是初学者最该记住的退避骨架。

### CP-08.2.3 退避的代价与陷阱：不公平、参数敏感、临界区末端空窗

退避不是免费午餐，有三个必须知道的坑。其一，**不公平**：先到的线程可能正好退避到一半在睡，锁被后到的线程抢走，导致"先来不一定先得"，极端下某线程反复错过、饥饿。其二，**参数敏感且不可移植**：`minDelay`/`maxDelay` 的最优值依赖具体机器的缓存/总线延迟，一台机器调好的常数搬到另一台可能反而更差——这正是它被队列锁取代的动因之一。其三，**临界区末端空窗**：如果持锁者刚释放锁的那一刻，本该接手的等待者正退避在睡，锁就会短暂"空着没人用"，浪费了本可以立刻推进的时间。

初学者要把 backoff 理解成"权宜的削峰"而非"根治"：它把 TTAS 的争用尖峰压平了不少、实现也简单，但代价是牺牲公平、依赖调参、且留下空窗。真正从结构上消除群体扑抢、同时给出公平保证的，是下一节的队列锁——它让每个等待者根本不去碰共享变量、释放时只精确唤醒一个后继，于是既无风暴也无需退避。

#### 来源与时效
- AMP 2nd/Revised ch7 §7.4「Exponential Backoff」（核实 2026-07-25）：BackoffLock 算法、`delay = min(maxDelay, delay*2)` 的指数增长与上限、随机化重试时刻的必要性、以及不公平/参数敏感/临界区空窗三项代价。
- MCS 1991 §2–3（核实 2026-07-30）：以"backoff 需机器相关调参、且仍在共享变量上产生流量"作为提出队列锁的动机，交叉印证退避是过渡方案而非终点。
- 交叉一致，无冲突。`delay*2` 与封顶 `maxDelay` 的公式表述以 AMP §7.4 为准。

## CP-08.3 队列锁 MCS / CLH：各自本地变量自旋、公平且可扩展

### CP-08.3.1 队列锁的核心思想

队列锁（queue lock）从结构上根治争用，靠三个绑在一起的设计。第一，**每个线程带一个自己的节点**（qnode），节点里有一个供自己自旋的标志位。第二，等锁的线程排成一条**FIFO 队列**（用节点的指针串起来），谁先到谁排前面。第三，也是最关键的——**每个等待者只在自己节点的那个标志位上自旋**（局部自旋，local spinning），而不是去读那个大家共享的锁变量。释放锁时，持锁者只需把队列里**紧跟自己的那一个后继**的标志位翻一下，精确唤醒下一个人。

这三点合起来同时解决了性能和公平两件事。性能上：既然每个等待者盯着的是**不同的**内存位置，且这些位置在稳态下由各自的核独占持有，那么等待期间**根本没有共享写、没有失效风暴**；释放时也只作废后继那一个人的缓存行，而不是惊动全体。公平上：FIFO 队列天然保证**先来先服务**（bounded waiting），彻底告别 TAS/backoff 的饥饿风险。要记住的一句话是——队列锁把"n 个人抢一个变量"变成了"排成一队，每人守着自己的门铃，前一个人走时按一下你的铃"。

### CP-08.3.2 CLH 锁：自旋在前驱节点上

CLH 锁（Craig, Landin & Hagersten）用一个隐式链表实现队列。锁本身是一个指向队尾节点的指针 `tail`。线程加锁时把自己的节点原子地"挂到队尾"（`swap(tail, myNode)` 取回前驱节点），然后**自旋读前驱节点的 `locked` 标志**，直到前驱把它置为解锁。释放锁时线程把**自己节点的** `locked` 置为 `false`，从而放行后继。一个技巧是：解锁后线程可以回收**前驱**的节点当作自己下次用的节点（节点所有权随队列流动），所以 CLH 每线程只需 O(1) 空间。

CLH 的记忆点是"**盯着前面那个人**"：我自旋在**前驱**的标志上，前驱做完事把标志一翻我就进。它的实现极简（一次 swap 挂队 + 自旋一个远程标志），且不需要显式的 `next` 指针（队列靠"我记得我的前驱"隐式维护）。但注意——我自旋读的是**前驱节点的内存**，不是我自己的。这在缓存一致（cache-coherent）的 SMP 机器上没问题（那块内存会被缓存到我的核，前驱写它时作废我一次，代价可接受）；但在**没有缓存一致性、或跨 NUMA 节点**的机器上，"自旋读一块物理上属于别人的远程内存"就会持续走远程访问，非常慢。这正是 MCS 要改进的地方。

### CP-08.3.3 MCS 锁：自旋在自己节点上

MCS 锁（Mellor-Crummey & Scott, 1991）也用队尾指针 `tail`，但让每个线程**自旋在自己节点的 `locked` 标志上**，并显式维护一个 `next` 指针指向后继。加锁：`swap(tail, myNode)` 取回前驱；若有前驱，就把前驱的 `next` 指向自己，然后**自旋读自己节点的 `locked`** 等前驱放行。解锁：如果 `next` 非空，就把**后继节点的** `locked` 翻成放行；如果 `next` 为空（可能没人排在后面，也可能后继正在挂队的半途），用 CAS 把 `tail` 从自己改回"无"，失败则说明有后继正在半路，自旋等它把 `next` 补好再放行它。

MCS 的记忆点是"**盯着自己的门铃，让前一个人来按**"：我只自旋读**我自己节点**的标志，这块内存永远由我的核独占缓存，稳态下自旋是纯本地 L1 命中、零总线流量——无论机器是否缓存一致、是否跨 NUMA，都成立。代价是要多维护一个 `next` 指针、解锁路径上多一次 CAS 和一个"等后继补 next"的小边界情形。这个"局部自旋在**自有**内存"的性质，就是 MCS 被称为"可扩展同步"经典算法的原因，也是它进 Linux 内核的原因。

### CP-08.3.4 CLH vs MCS 对比

两者都是 FIFO、公平、O(1) 每线程空间的局部自旋队列锁，最本质的区别只有一处：**自旋位置**。CLH 自旋在**前驱**节点的标志上；MCS 自旋在**自己**节点的标志上。由此派生出全部差异：

CLH 更省——不需要 `next` 指针（队列隐式），解锁只是写自己节点一个标志、无 CAS，路径最短；但它假设"自旋读前驱内存"是廉价的，只在**缓存一致**的机器上成立。MCS 更稳——自旋永远命中自有内存，在**无缓存一致性或 NUMA/分布式**机器上仍高效；但要维护 `next`、解锁路径有一次 CAS 和"后继半路"边界情形。

缓存一致的普通 SMP 上两者都好，CLH 略简；一旦跨越缓存一致性边界（NUMA 深、或非一致内存架构），MCS 的"只碰自有内存"胜出。MCS 1991 原论文正是以"避免在远程内存上自旋"为核心卖点提出该算法的，这也预告了 CP-08.5 的 NUMA 主题。

### CP-08.3.5 实践印证：Linux 内核的 qspinlock 基于 MCS

Linux 内核自 4.2 起，架构相关的 `spinlock_t` 默认实现是 **qspinlock**（queued spinlock，`kernel/locking/qspinlock.c`），其排队等待部分正是 **MCS 锁**：每个 CPU 一份 per-CPU 的 MCS 节点，等待者自旋在自己 CPU 的节点上。内核的工程约束是 `spinlock_t` 必须压进 4 字节以兼容既有 ABI，而教科书 MCS 的 `tail`（8 字节指针）+ 节点 `next`（另 8 字节）放不下，于是 qspinlock 把队尾编码成"CPU 号 + per-CPU MCS 数组下标"塞进一个 32 位字，并对"无争用/单一等待者"做了快路径优化（无争用时退化成一次简单的 TAS，不进队列）。

MCS 不是纸面算法而是现役生产代码——一台跑 Linux 的多核机器，其内核自旋锁在争用时走的就是 MCS 局部自旋队列。初学者可由此把前面几节的递进对上号：qspinlock 的快路径 = TAS（无争用时最省），慢路径 = MCS 队列（有争用时可扩展），正好体现"低争用要轻、高争用要队列"的组合智慧。（注：qspinlock 具体的位字段布局与快慢路径条件随内核版本演进，细节以对应版本 `qspinlock.c` 与 `qspinlock_types.h` 为准；本节只锚定"基于 MCS + 4 字节压缩 + 快路径 TAS"这一稳定事实。）

## CP-08.4 缓存一致性与 false sharing：MESI 对自旋成本的支配与伪共享

### CP-08.4.1 MESI 一致性协议如何支配自旋成本

一切自旋锁性能问题的底层都是**缓存一致性协议**（以 MESI 为代表）在起作用。MESI 让每个缓存行处于四态之一——Modified（本核已改、独占）/ Exclusive（本核独占未改）/ Shared（多核可同时持有的只读副本）/ Invalid（无效）。支配自旋成本的只有两条铁律：**读**可以让多核同时持有该行的 Shared 副本、各自本地命中、零一致性流量；**写**必须先把该行升到 Modified/Exclusive，这要求**作废所有其他核的副本**（发出 invalidate），是一次昂贵的一致性事务。

这两条铁律就是前三节全部结论的统一解释：TAS 慢因为每次都是写（每次都作废全体）；TTAS 快因为把自旋降级成共享读（多核各持 Shared 副本、互不打扰）；队列锁最优因为每个等待者读的是**不同的**缓存行、且稳态下由各自核独占、彼此零干扰。初学者只要记住"**读可共享、写要独占（作废别人）**"这八个字，就能自己推出"自旋时该碰什么、不该碰什么"——碰共享写变量必挨风暴，碰自有/只读变量则廉价。

### CP-08.4.2 false sharing：明明没共享数据，却在共享缓存行

**伪共享**（false sharing）是缓存一致性最阴险的性能陷阱：两个线程各自读写**逻辑上互不相干**的两个变量，但这两个变量**恰好落在同一条缓存行**里（x86-64 缓存行 = 64 字节，本机 `getconf LEVEL1_DCACHE_LINESIZE` 实测为 64）。因为 MESI 的一致性粒度是**整条缓存行而非单个变量**，一个线程写它的变量，就会把整条行升到 Modified、作废另一个线程持有的那份副本——哪怕另一个线程碰的根本是行里**另一个**字节。于是两个本该完全并行、零冲突的线程，被硬件按"同一行"当成了争用对象，缓存行在两个核之间反复来回弹跳（cache-line ping-pong），性能暴跌。

这里的"伪"字是要害：数据层面**没有**真正的共享（两个变量各写各的），是缓存行的**物理布局**制造了假的共享。初学者最容易中招的场景就是本大主题的主角——多线程计数器：`long counter[NTHREADS]` 这样一个数组，每个线程 `counter[tid]++`，看起来完美并行，实则 8 个 `long` 挤在一两条缓存行里，线程们为了各自那个 8 字节的计数器把整条行抢来抢去。它和"真共享"（多个线程真的读写同一个变量）在代码上难以区分，只有理解"一致性以行为单位"才能识别。

### CP-08.4.3 用 `_Alignas(64)` 对齐消除伪共享（本机实证）

消除伪共享的标准手法是**填充/对齐**：让每个被不同线程独立写的变量各自独占一整条缓存行，用 C11 的 `_Alignas(64)` 把变量对齐到 64 字节边界，并用 padding 把结构体撑满一行，这样不同线程的变量必然落在不同缓存行，MESI 再也不会把它们绑在一起作废。

本机真跑对比（基线 gcc 13.3 @2026-07-30，4 核 x86-64，缓存行 64 字节）：4 个线程各对自己的 `atomic_long` 计数器 `fetch_add`（relaxed）各 5×10^7 次，唯一区别是计数器**同缓存行紧挨**（伪共享）还是 **`_Alignas(64)` 各占一行**。可复现命令与真实输出：

```
# gcc -std=c11 -O2 -pthread fs.c -o fs && ./fs
packed (false sharing): 3.966 s
padded (_Alignas(64)) : 0.347 s
sizeof(atomic_long)=8
# getconf LEVEL1_DCACHE_LINESIZE -> 64
```

同一段计数逻辑，仅仅因为把 4 个计数器从"挤在一起"改成"各占一条缓存行"，耗时从 3.966 s 降到 0.347 s，**约 11.4 倍**加速——这就是伪共享的真实代价，也是"内存布局即性能"最直观的一课。关键理解：加速**不是**因为算得更少（两版做的加法次数完全一样），而是因为消除了缓存行在 4 个核之间的反复弹跳。这条实证同时印证了 CP-08.4.1 的铁律：把各线程要写的数据在物理上分到不同行，就把"写→作废全体"变成了"写→只动自己那行"。（实证脚本 `fs.c` 仅存于仓库外 scratchpad，跑完即清，不入库；上面的命令 + 输出已自足可复现。）

## CP-08.5 NUMA 与锁放置：跨节点访问的非一致代价

### CP-08.5.1 NUMA：内存访问不再等距

**NUMA**（Non-Uniform Memory Access，非一致内存访问）是大型多核/多插槽机器的内存架构：内存被分成若干**节点**（node），每个节点物理上贴近一部分 CPU 核。一个核访问**本节点**内存快，访问**别的节点**内存要跨节点互连（如 UPI/QPI），显著更慢——"非一致"指的就是"访问延迟随内存位置而不同"。相对地，小型机器多是 **UMA**（一致内存访问），所有核到所有内存等距。

NUMA 对锁的含义是：CP-08.4 讲的"作废一条缓存行"的代价，在 NUMA 上**不再是常数**——如果一致性事务要跨节点完成（锁变量或后继节点的缓存行在远端节点），代价会成倍放大。于是在 NUMA 机器上，一把在 UMA 上表现很好的锁（比如普通 MCS）也可能因为"锁在节点间来回弹跳"而变慢：每次锁易主若跨节点，就付一次昂贵的跨互连一致性开销。初学者可以把 NUMA 理解成 CP-08.4 缓存层级的"再上一层"——延迟的非一致性从"L1 命中 vs 跨核作废"延伸到了"本节点 vs 跨节点"。

### CP-08.5.2 NUMA 感知的锁放置：cohort / 分层锁

针对 NUMA 的优化思路叫**锁放置 / NUMA 感知锁**：核心是**尽量让锁在同一个节点内部易主**，减少跨节点交接。代表性设计是**cohort lock**（分层/队列组合锁，如 NUMA-aware cohort locking、HCLH 分层 CLH）——它维护"每节点一把本地锁 + 一把全局锁"，倾向于把锁连续交给**同节点**的等待者（本地锁内接力，一致性事务留在节点内），攒够一批或超时后才把全局锁交到另一个节点。这样把昂贵的跨节点交接**摊薄**到多次廉价的节点内交接上，代价是牺牲严格 FIFO 公平（同节点插队）换吞吐。

NUMA 感知锁用"局部性"换"全局公平"——让锁"赖在"一个节点多待一会儿，吞吐更高，但远节点的线程要多等。这与 CP-08.3 队列锁的纯 FIFO 是一条延续的取舍线：从 backoff（无公平）→ 队列锁（严格 FIFO）→ NUMA cohort（分层、局部优先）。初学者不必掌握 cohort 的具体协议，只需领会"在 NUMA 上，把交接留在本节点是第一性的性能杠杆"。

### CP-08.5.3 本机拓扑（`lscpu` 实证）与本节可测性

本机拓扑用 `lscpu` 实测：`NUMA node(s): 1`，`NUMA node0 CPU(s): 0-3`——即本机是**单 NUMA 节点、4 核**的 UMA 式机器。因此 CP-08.5 的核心命题（跨节点访问比本节点慢、锁应尽量节点内易主）在本机**无法直接计时验证**——没有第二个节点可"跨"，跨节点代价在本机恒为不适用。如实标：**本机不可测·跨平台待核**；本节结论完全由一手文献（AMP 对 NUMA 局部性的讨论 + MCS 1991 的"避免远程自旋"动机 + NUMA cohort 文献）支撑，不靠本机实证。


```
# lscpu | grep -i numa
NUMA node(s):        1
NUMA node0 CPU(s):   0-3
```

正因为 CP-08.4 的实证已在本机把"缓存层级的非一致代价"演示得很清楚（11.4× 差距），可以外推理解——NUMA 只是把同样的"访问远处更贵、把数据/交接留在近处"的原理放大到节点尺度。真要测 NUMA 效应需要一台多节点机器（`numactl --hardware` 看多个 node、`numactl --cpunodebind/--membind` 绑定后计时跨节点 vs 本节点访问），这属于跨平台工作，本报告不外扩。
