## CP-13.1 TM 编程模型：原子块、乐观并发、自动回滚重试

### CP-13.1.1 原子块（atomic block）：声明式地表达原子性

事务内存的用户接口是一个**原子块**：把一段访问共享内存的代码圈起来，声明"这一整段要作为一个不可分割的事务执行"。程序员只表达**意图**（这些操作合起来要原子、要与其他事务隔离），不再手工指定用哪把锁、加锁顺序、临界区边界。语法上，学术模型写作

atomic { account[from] -= x; account[to] += x; }

而在本机 GCC（GNU Transactional Memory TS）里落地为 `__transaction_atomic { … }`（需 `-fgnu-tm`，见抬头实证），Intel HTM 里则展开为 `XBEGIN … XEND` 指令对（见 13.3）。

这与锁的根本区别在于"声明式 vs 命令式"。用锁你写的是一串命令："lock(m); account[from]-=x; account[to]+=x; unlock(m);"——你要亲自决定 `m` 是哪把锁、它保护哪些数据、和别处的锁按什么全局顺序获取（否则死锁）。原子块把这些实现细节全部交给底层：你说"这段要原子"，系统负责用乐观并发去兑现它。一个直观类比是数据库事务——你写 `BEGIN … COMMIT`，不用管数据库内部用了行锁、MVCC 还是别的；TM 就是把数据库那套"事务"抽象搬到了对**内存**的普通读写上。

初学者最该记住：原子块里**只能放可回滚的内存操作**。因为底层随时可能把你这次执行整个作废重来，块内若做了不可撤销的事（打印、发网络包、`free` 掉内存），回滚时无法收回，就出错——这条限制贯穿全主题，13.4 会再强调。

### CP-13.1.2 乐观并发（optimistic concurrency）：先假设不冲突地跑

事务内存默认采用**乐观并发控制**：不预先加锁排他，而是**乐观地假设"这次事务和别人不会冲突"**，直接推测执行（speculative execution）下去，一边跑一边偷偷记录自己读了哪些地址、要写哪些地址；直到事务末尾才**验证**这段时间内自己读过的数据有没有被别的事务改动。没被改动就说明"乐观赌对了"，提交生效；赌错了才回滚。

这与锁的**悲观并发**正相反。悲观锁的逻辑是"我先假设一定会有人跟我抢，所以进临界区前先把门锁死，宁可让别人等"。乐观的逻辑是"大多数时候其实没人跟我抢，那预先上锁就是白等——我先干着，真撞上了再说"。所以两者的适用面天然不同：**低争用时乐观大胜**（没人冲突，省掉了全部加解锁开销，多个事务真并行跑）；**高争用时乐观可能吃亏**（频繁撞车、反复回滚重来，白做的功远超一把锁的开销），这条权衡在 13.4.3 展开。

用一个比方，悲观锁像进厕所先反锁门，后面的人一律排队；乐观并发像大家都先进去用，出门前瞄一眼刚才有没有人碰过自己用的那格——没有就走人，有就重来。人少时后者明显更快，人挤时反复重来反而更慢。

### CP-13.1.3 自动回滚与重试（abort / rollback / retry）

当验证发现冲突（或硬件容量不足、被中断打断等），事务**中止（abort）**：底层把本次事务所做的**全部推测性写入丢弃、内存恢复到事务开始前的状态（rollback）**，然后**重试（retry）**——通常是自动跳回原子块开头再跑一遍。对程序员而言，中止—重试是**透明**的：一个成功提交的事务，其效果等价于"从头到尾一次干净地原子执行"，中间失败的尝试对外不可见。

这里的心智模型是"存档—读档"：进入原子块相当于存了个档，乐观地往下打，打挂了（冲突）就读档重来，直到一次通关（提交）为止；通关前的所有失败尝试都不算数、外界看不到。要让这套机制成立，底层必须能真正"读档"——所以块内的操作必须可撤销（呼应 13.1.1）。

初学者常见两个疑问。其一，"会不会一直重试、永远提交不了？"——理论上可能发生**活锁**（两个事务反复互相中止对方），实现上靠退避（backoff）、争用管理器（contention manager）或退回加锁来兜底，纯粹的乐观 TM 一般只保证 obstruction-free 而非 wait-free（进展性条件见大主题02）。其二，"重试时读到的还是旧值吗？"——不是，重试会重新读当前最新内存，所以最终提交的那次一定是基于一致的、没被中途改动的数据。

### CP-13.1.4 事务的正确性语义：ACI（无 D）与可串行化

TM 保证的正确性通常概括为数据库 ACID 里的 **A（原子性）、C（一致性）、I（隔离性）三者，但没有 D（持久性）**——因为对象是易失的内存而非磁盘，断电即失，无需"提交后永久保存"。核心承诺是：**所有成功提交的事务看起来像是一个接一个、串行地、原子地执行的**（可串行化 / 对内存事务而言即线性一致），任何事务都观察不到另一个事务的中间半成品状态（隔离）。

把三条性质分开对照来看，原子性是指事务内的多次写"全有或全无"，绝不出现"转账扣了款没入账"这种半截状态；隔离性是指事务执行中别的线程看不见它尚未提交的临时写；一致性是指若每个事务单独看能维持不变量（如总额守恒），事务串行组合后不变量依然成立。之所以强调"看起来像串行"而非"真的串行"，是因为无冲突的事务其实是**真并行**跑的——可串行化只要求存在一个等价的串行顺序，不要求物理上排队，这正是 TM 想同时拿到"锁的简单正确性"和"细粒度的并行性能"的根源。

一个易错点：TM 的原子性只覆盖**块内对共享内存的访问**，不覆盖 I/O、系统调用等外部副作用；这些不在"可回滚"范围内，因此语义上要么禁止出现在事务里，要么由实现特殊处理（见 13.4.4）。

## CP-13.2 STM 软件事务：版本 / 所有权记录、冲突检测与提交

### CP-13.2.1 STM 是什么：纯软件实现事务语义

**软件事务内存（STM）** 不依赖任何特殊硬件，用普通的读写 + 原子指令（如 CAS）在**软件运行时库**里实现事务语义。它把每次事务性的读写都改成经过库函数的"带记录的读/写"（`TxLoad`/`TxStore`），由库维护每个事务的元数据、检测冲突、执行提交或回滚。Shavit & Touitou 1995 首次提出 STM；现代主流实现（TL2、TinySTM、GCC libitm）都属此类。

它的价值是**可移植、灵活、事务大小不受硬件限制**：没有 HTM 那种"缓存装不下就必然中止"的容量上限（对比 13.3.3），能跑任意大的事务，且能在任何 CPU 上运行。代价是**每次内存访问都要走软件记账**，单线程开销显著（常见 2–8 倍慢），这也是 STM 始终未能大规模落地生产的主因之一。本机 GCC 的 `-fgnu-tm` + libitm 就是一个可真跑的 STM 实现（见抬头实证）。

### CP-13.2.2 读集与写集：事务在记录什么

每个进行中的事务维护两份记录：**读集（read-set）**——本事务读过的所有内存位置（及读时看到的版本）；**写集（write-set）**——本事务打算写的位置及新值。读集用于提交时验证"我读过的东西有没有被别人改过"；写集用于提交时把新值真正落地、以及回滚时知道要撤销哪些。

直觉上，读集回答"我这次决策依赖了哪些数据"，写集回答"我这次要改哪些数据"。冲突检测的本质就是比对不同事务的这两个集合：如果事务 A 的写集和事务 B 的读集或写集有交集，且它们并发，就构成冲突（read-write 或 write-write 冲突）。一个易错点：读集必须**全部**记录，哪怕只是"读来做判断、并没写回"的数据——因为你的决策建立在它之上，它若被人改了，你的整个事务逻辑就基于过时前提，必须作废（否则会出现下面 13.2.6 的"僵尸事务"）。

### CP-13.2.3 版本管理：直接更新（undo log）vs 延迟更新（redo log）

事务的写有两种落地时机，对应两种版本管理策略。

**eager / direct-update（急切/直接更新）**：事务**当场就把新值写进共享内存**，同时在一个 **undo log（撤销日志）** 里备份被覆盖的旧值。提交时什么都不用搬（新值已在内存里），只需丢弃 undo log；但中止时要**用 undo log 把旧值逐个还原回去**。

**lazy / deferred-update（延迟/延后更新）**：事务的写**先只写进自己的写集（一个私有 redo 缓冲）**，共享内存暂不动；提交时才把写集里的新值一次性**刷回**内存（redo）；中止时直接**丢弃写集**即可，共享内存从未被污染，回滚是零成本。

两者对照来记，direct-update 是"提交便宜、回滚贵"，deferred-update 是"回滚便宜、提交贵"。选哪种取决于你预期冲突多不多——冲突少（多提交、少回滚）偏向 direct，冲突多偏向 deferred。deferred 的另一好处是共享内存在提交前永远是干净的旧值，天然不会让别的事务读到半成品；direct 则需要更小心地用锁/所有权把未提交的脏值挡住。

### CP-13.2.4 所有权记录、版本时钟与冲突检测时机

STM 需要一套元数据把"某块内存现在归谁管、是第几个版本"记下来，最常见的是**所有权记录（ownership record, orec）**：把内存地址哈希到一组 orec 上，每个 orec 携带一个"版本号 + 锁位"。写者提交时要先"拿下"目标地址对应的 orec（置锁 + 递增版本），读者则通过比对读时/校验时的版本号来判断自己读过的数据有没有被改动。

现代高效 STM（如 **TL2**）用一个**全局版本时钟（global version clock）** 把这套做得很干净：事务开始时读一次全局时钟得到 `rv`（read version）；每次读，检查目标 orec 的版本 ≤ `rv` 且未被锁，是则安全；提交时对全局时钟做原子自增得到 `wv`，锁住写集、**重新校验读集**版本仍 ≤ `rv`，通过则写回并把写集 orec 的版本更新为 `wv`。

冲突检测有两个时机，务必分账：**急切检测（eager / encounter-time）** 在访问发生的当下就检查冲突（读写时立即验版本/抢所有权），冲突早发现、少做无用功，但可能误杀本可成功的事务；**惰性检测（lazy / commit-time）** 把检测推迟到提交时统一做，让事务先跑完，减少误判，但可能白跑很久才发现要回滚。TL2 是典型的"惰性写回 + 提交时校验"。

### CP-13.2.5 提交流程：校验读集 → 锁写集 → 写回 → 释放

以 TL2 式惰性 STM 为例，一次提交大致是：(1) 对写集里每个地址的 orec **加锁**（拿不到就中止重试）；(2) 原子自增全局版本时钟得到本次的写版本 `wv`；(3) **重新校验读集**——逐个确认读过的地址版本仍 ≤ 事务开始时的 `rv` 且未被别人锁住，任一失败则释放已拿的锁、中止；(4) 校验全过则把写集新值**写回内存**、并将这些 orec 版本置为 `wv`；(5) **释放**所有 orec 锁。全过程读者无锁、只有提交的写者短暂持锁。

关键直觉在第 (3) 步的"重新校验读集"：这一步是可串行化的守门员。它确认"从我开始读、到我现在要提交，这中间我依赖过的所有数据没有一个被别人动过"，因此把我的事务**逻辑上安放在 `rv` 到 `wv` 这个时间点上原子发生**是合法的。少了这一步，就会提交一个基于过时数据的事务，破坏一致性。这也解释了为什么读集必须记全（呼应 13.2.2）。

### CP-13.2.6 STM 的经典陷阱：僵尸事务、弱/强原子性、隐私化

**僵尸事务（zombie / doomed transaction）**：一个已经注定要中止（读到了不一致数据）但还在继续跑的事务。它可能基于矛盾的输入进入死循环、除零、越界访问。健壮的 STM 必须做**读的即时校验（incremental validation）或用一致性快照（如版本时钟）**，保证事务全程只看到一致的内存视图，避免僵尸事务把整个程序拖崩。

**弱原子性 vs 强原子性（weak / strong atomicity）**：强原子性保证事务与**非事务代码**之间也隔离——即事务外的裸读写也不能撞破事务的原子性；弱原子性只保证事务**之间**隔离，事务内数据若被块外的普通代码同时访问，行为未定义。大多数 STM 出于性能只提供弱原子性，于是"同一数据要么全程用事务访问、要么全程不用"成为纪律。

**隐私化问题（privatization problem）**：一个事务把某块共享数据"私有化"（逻辑上摘出来只归自己）后想用普通非事务代码去访问它，可能与仍在收尾的其他事务的延迟写回竞争，读到本不该出现的旧值/中间值。这是弱原子性 STM 的著名坑，需要 STM 在语义或实现上额外处理（隐私化安全）。初学者只需记住结论：**STM 不是"随便圈个块就万事大吉"，它和块外普通代码的边界处最容易出错。**

## CP-13.3 HTM 硬件事务：Intel TSX 等、成熟度与平台可用性硬标

> ⚙演进快·锚版本·随时变：本节涉及 Intel TSX 的可用性，多平台经微码更新已禁用，务必以现行官方 SDM/勘误 + 目标机器实测为准，不作跨平台"可用"结论。本机实测见抬头与 13.3.4。

### CP-13.3.1 硬件事务的核心机制：缓存 + 一致性协议侦测冲突

**硬件事务内存（HTM）** 把事务的推测执行、冲突检测和回滚直接做进 CPU。核心思路（源自 Herlihy & Moss 1993）：给缓存行加**事务读位 / 写位**标记，事务期间的读写数据**暂存在缓存里**（推测状态，不外泄到内存）；复用已有的**缓存一致性协议**——当别的核心对本事务标记过的缓存行发出冲突性的读/写（一致性消息如 invalidate）时，硬件立刻察觉冲突并**中止**事务，把推测状态一笔勾销，缓存恢复干净。提交时则把这些缓存行的推测写"一次性对外可见"。

直觉上，HTM 是"白嫖"了 CPU 本就有的缓存一致性机制来做冲突检测——一致性协议原本就在追踪"哪个核心动了哪条缓存行"，HTM 只是搭车用这个信号来判定事务冲突。所以 HTM 的开销极低（无软件记账），但也**受缓存物理容量所限**：事务读写集必须装得进缓存（尤其 L1），装不下就必然中止（容量中止，本机实测 50/50，见抬头），这是 HTM 相对 STM 的根本短板。

### CP-13.3.2 Intel TSX 的两套接口：HLE 与 RTM

Intel 的 HTM 商品名是 **TSX（Transactional Synchronization Extensions）**，提供两套接口。

**HLE（Hardware Lock Elision，硬件锁省略）**：给已有的加解锁指令加 `XACQUIRE`/`XRELEASE` 前缀。CPU 会"假装拿了锁但其实不拿"——把整个临界区当事务乐观执行，多个线程只要不真冲突就能**同时进入同一把锁保护的临界区**（锁被"省略"了）。它的最大卖点是**向后兼容**：老 CPU 忽略前缀、照常真加锁，代码无需分叉。

**RTM（Restricted Transactional Memory，受限事务内存）**：显式指令 `XBEGIN`/`XEND`/`XABORT`/`XTEST`。`XBEGIN` 开始事务并指定一个**回退地址**（fallback），事务中止时 CPU 跳到那里；`XEND` 提交；`XABORT` 主动中止并带一个 8 位中止码；`XTEST` 查询当前是否在事务中。本机实测的正是 RTM：`_xbegin()` 返回 `_XBEGIN_STARTED` 表示进入事务，中止时返回状态字（`_XABORT_EXPLICIT`/`_XABORT_CONFLICT`/`_XABORT_CAPACITY` 等位），程序据此决定重试或走回退路径。

对初学者而言，HLE 是"让现有锁代码免改就享受乐观并发"，RTM 是"给你一套显式事务指令自己控制"。RTM 更灵活也更常用于研究与库实现。

### CP-13.3.3 best-effort 语义：HTM 不保证提交，必须有回退路径

TSX 是 **best-effort（尽力而为）HTM**：硬件**不保证任何事务一定能提交**，即使完全没有冲突。多种原因都会导致中止——**容量中止**（读写集超出缓存，本机实测大事务 50/50 全中止）、**冲突中止**（别的核心撞了你的缓存行）、以及**中断、系统调用、页错误、某些不可事务化指令**等一律强制中止。

这带来 HTM 编程的铁律：**必须写一条非事务性的回退路径（fallback）**，通常是一把真锁。典型惯用法是"先试 N 次 RTM 事务，反复失败就退回去拿那把锁串行执行"。本机实测里空事务能 1000/1000 提交，但只要事务变大（容量）或撞上中断就会中止——所以**任何只依赖 HTM 成功、没有回退的代码都是错的**。

可以把 HTM 当成"运气好时的快车道"，而不是"保证到达的高速路"。快车道随时可能被关（容量/中断/冲突），你永远要留一条一定能走通的辅路（锁）。这也让 HTM 天然适合"给锁做加速"（lock elision）而非彻底取代锁——底下那把锁就是现成的回退。

### CP-13.3.4 成熟度与平台可用性（硬标，⚙演进快）

TSX 的历史是一部"反复被禁用"史，务必分账、不作跨平台结论：

- **2013**：Haswell 微架构首发 TSX（HLE + RTM），首个主流商用 HTM。
- **2014**：Intel 在 Haswell / 早期 Broadwell 上发现 TSX 勘误，通过微码**禁用**了这些部件的 TSX。
- **2019–2021**：因 **TAA（TSX Asynchronous Abort，CVE-2019-11135）** 侧信道安全漏洞，Intel 通过微码在大量客户端与服务器部件上**默认禁用 TSX**（或提供 `TSX_CTRL` MSR 关闭）；Linux 内核也默认关闭 TSX。
- **2021 前后**：Intel 宣布在部分较新客户端处理器上**弃用并移除** TSX（如 Rocket Lake 起客户端 RTM 被移除/永久 abort，出现 `rtm_always_abort` 特性位表示"RTM 存在但总是中止"）。
- **2022**：Linux 内核补丁在启动时**关闭 TSX "开发者模式"**，进一步收紧。
- **现状（截至 2026-07 核实）**：TSX 在多数客户端平台已不可用；**部分服务器至强（含 Sapphire Rapids 一族）仍保留可用的 TSX**，但 Intel 明确**不建议在生产中重新启用**——因为启用后 TAA 的 MD_CLEAR 缓解可能失效。整体上 HTM 硬件支持有限、且方向是收缩。

**本机实测坐实（解决 round3b「CP-13.3 待核」）**：本机为 KVM 虚拟化的 Sapphire Rapids 一族至强，`/proc/cpuinfo` 有 `hle rtm tsx`、**无** `rtm_always_abort`、`tsx_async_abort` = `Not affected`；RTM 事务真跑可提交（1000/1000）、显式/容量中止行为正确（见抬头）。**结论：本机 TSX 可用且功能正常**——这是"少数仍启用 TSX 的服务器部件 + 虚拟化透传"的情形，**不能外推为"TSX 普遍可用"**。任何其他机器都须以其 `/proc/cpuinfo`（是否有 `rtm`、是否有 `rtm_always_abort`）+ 实测为准。

一个直接冲突点如实记：主流技术叙事是"TSX 已被广泛禁用/弃用"（The Register 2021、KitGuru、Phoronix 等二手报道 + Intel 官方安全公告），而本机实测 TSX 确实在跑。两者不矛盾——前者讲的是客户端与"默认"状态的大趋势，后者是特定服务器部件在特定虚拟化环境下的实况。凡遇 TSX 可用性问题，**以目标机器实测 + 该机对应的 Intel SDM/勘误为准**，不凭机型名下结论。

## CP-13.4 TM vs 锁：可组合性优势、性能 / 回滚代价对比

### CP-13.4.1 可组合性（composability）：TM 最被看重的优势

锁**不可组合**：两个各自用锁写对的模块，拼在一起用未必对。经典例子——想把"从账户 A 原子地取钱"和"向账户 B 原子地存钱"合成一个"原子转账"，若 A、B 各自内部加自己的锁，你在外层无法把两次操作合成一个原子步骤，除非侵入两个模块、按全局顺序获取它们的内部锁（否则和别处交叉就死锁）。这要求你了解每个模块的锁实现细节，破坏了封装。

事务**天然可组合**：把两个事务块**嵌套**进一个更大的原子块，整体仍是一个事务、要么全提交要么全回滚。你不需要知道被组合模块内部怎么实现原子性，只要它们也用事务。这就是 TM 支持者最看重的性质——它让"原子性"成为一个可以像积木一样拼装的抽象，而锁做不到。

换个角度看，锁的正确性是**全局**的（谁和谁的锁顺序必须协调），所以拆开写对、拼起来可能错；事务的正确性是**局部可组合**的（每个块声明自己原子，嵌套后语义自动叠加）。这也是它像数据库事务的地方——你可以把小事务嵌进大事务。

### CP-13.4.2 编程简单性：无锁序、无死锁、粗粒度的写法拿细粒度的性能

用锁要在"粗粒度"（一把大锁，简单但并行度低）和"细粒度"（多把小锁，并行度高但极易死锁、极难写对）之间痛苦权衡；还要全局约定加锁顺序防死锁、处理优先级反转、锁护航等一堆问题。TM 让你**用粗粒度的写法（一个 `atomic` 块圈住整段）表达意图，却由乐观并发在运行时提供细粒度的并行度**——不冲突的事务自动并行，程序员完全不碰锁序。

纯 TM 模型下**没有死锁**：没有锁就没有"循环等待"这个死锁条件（对比 L4-01·OS-07 的 Coffman 四条件）；最坏情况是活锁（反复互相中止），由退避/争用管理兜底，而非永久卡死。对初学者这是巨大的认知减负：写并发代码时不必再在脑子里维护一张"谁在等谁的锁"的图。

要澄清的边界：这份"简单"在**混入 HTM 回退锁、I/O、弱原子性**后会打折（见 13.4.4）——实践中 TM 并非无脑简单，只是把复杂度从"锁序设计"挪到了别处。

### CP-13.4.3 性能与回滚代价：乐观的双刃

TM 的性能画像与"乐观"直接绑定：**低争用时优于锁**（无加解锁开销、事务真并行、HTM 几乎零额外成本）；**高争用时可能劣于锁**——冲突频繁导致大量事务中止、回滚、重试，这些**白做的工作**纯属浪费，严重时活锁，总吞吐反而不如一把简单的锁排队执行。此外 STM 有固定的软件记账开销（每次读写走库函数，常见数倍慢），HTM 有容量/中断中止 + 回退路径的开销。

心智模型是"赌局"：乐观并发赌"没人跟我冲突"。赌赢（低争用）省下全部同步开销、多方并行，大赚；赌输（高争用）不但没省，还倒赔一次白跑 + 重来的成本。所以 TM 不是"永远比锁快"，而是**在争用不高、事务不大的场景**才划算——这也是它在通用编程里没能取代锁的现实原因之一。

一个常被忽视的代价：回滚要求保存/恢复状态（STM 的 undo/redo log、HTM 的推测缓存），事务越大、读写集越多，这份簿记越贵；HTM 还会因读写集超缓存而**根本无法完成**大事务（本机实测 50/50 容量中止）。

### CP-13.4.4 TM 的局限：不可回滚的副作用、弱原子性、并非银弹

TM 的原子性只覆盖**可回滚的内存操作**。**I/O、系统调用、发送网络消息、`free`/释放资源**等不可撤销的副作用一旦执行就收不回，因此要么被禁止出现在事务里，要么由实现特殊处理（如 STM 把 I/O 推迟到提交后、或遇到就退回不可回滚模式串行执行）。这是 TM 相对锁的一个实打实的表达力缺口——锁保护的临界区里可以随便做 I/O，事务不行。

还有几处现实摩擦：**弱原子性**下事务与非事务代码的边界易错（呼应 13.2.6 的隐私化）；**HTM best-effort** 逼你始终维护一条回退锁路径，等于"锁 + 事务两套都要写对"；**调试困难**（推测执行 + 回滚让复现和观察变难）；**生态与硬件支持有限**（HTM 多平台已禁用见 13.3.4，STM 性能开销大）。

结论性的分账，供初学者建立正确预期：**TM 是一个漂亮但未成主流的想法**。它在可组合性和"用简单写法拿并行"上确实胜过锁，学术与部分库（如 glibc 的锁省略、GCC libitm、部分数据库/JVM 实验）用到它；但受限于高争用回滚代价、不可回滚副作用、以及 HTM 硬件的收缩，它并没有像 1990s 设想的那样取代锁。实践里更常见的定位是"**给锁做加速**"（HTM lock elision）而非"**取消锁**"。把它理解成锁的一个乐观补充、而非替代，最贴近现状。
