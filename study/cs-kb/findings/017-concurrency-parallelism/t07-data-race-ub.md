## CP-07.1 data race 精确定义：四要件

### CP-07.1.1 标准原文的定义与"冲突访问"

按 ISO C23 §5.1.2.4，数据竞争的定义只有一句话：

```
程序的一次执行含有一个 data race，当且仅当它含有两个"冲突动作"(conflicting actions)，
这两个动作位于不同线程，其中至少一个不是原子的(at least one of which is not atomic)，
且二者之间谁也不 happens-before 谁。任何这样的 data race 都导致未定义行为(undefined behavior)。
```

其中"冲突动作"本身也有精确定义：两次表达式求值**冲突**，当且仅当其中一个**修改**了某内存位置，而另一个**读或修改**了**同一个**内存位置。把这两条拼起来，就得到课程 prompt 说的"四要件"——(1) 两个动作访问**同一内存位置**；(2) **至少一个是写**（这两条合起来 = "冲突"）；(3) 二者之间**没有 happens-before 关系**；(4) **至少一个不是原子访问**。四条同时成立，才是数据竞争，才是 UB。

初学者最容易记错的是第 (4) 条：它是"**至少一个**非原子"，不是"两个都非原子"。这意味着——如果两个冲突访问**都**是原子的（哪怕都是最弱的 `memory_order_relaxed`），那么按定义它**根本不构成数据竞争**，也就没有这条 UB（结果可能仍不符合你的业务逻辑，但那是另一回事，见下一节的辨析）。这正是 07.4 用 relaxed atomic 修竞争的法理依据：把变量变成原子，等于把它从"数据竞争"的定义里摘出去。第 (3) 条同样关键——只要两次访问之间存在 happens-before（比如被同一把锁串起来、或一个 `pthread_create`/`join` 边界隔开），哪怕都是非原子的，也不构成竞争；happens-before 的完整定义在 CP-05，这里直接取用。

### CP-07.1.2 "内存位置"的粒度：相邻字段也可能各自独立

标准把竞争定义在"**内存位置**"(memory location) 这个粒度上，而不是"变量"或"缓存行"。一个内存位置是：一个标量对象（`int`、指针等），或一段**相邻的、宽度非零的位域序列**。关键结论是：两个**不同的**内存位置上的并发访问，**永远不构成数据竞争**——哪怕它们在同一个结构体、同一条缓存行上。

这条对初学者有两个反直觉的推论。其一：结构体里两个相邻的普通字段 `a` 和 `b`，线程 1 只写 `a`、线程 2 只写 `b`，这是**合法无竞争**的程序，标准保证编译器不会把"写 `a`"实现成"读整个字扩、改 `a`、写回整个字"从而踩坏 `b`（C11 起这是硬性要求）。其二：相邻的**位域**（如 `unsigned x:1; unsigned y:1;`）如果被划进同一个内存位置，那么并发写 `x` 和 `y` 就**是**竞争——因为硬件没法只改一个 bit，必须读改写整个存储单元。这也说明"内存位置"是语义概念、不等于"一个变量名"。注意：同缓存行不同内存位置的并发访问虽**无竞争**、语义上完全正确，但会带来 false sharing 的**性能**问题（性能不是正确性，归 CP-08.4）——正确性与性能在这里要分账。

### CP-07.1.3 data race ≠ race condition：两个常被混用的词

要把"数据竞争"(data race) 和"竞态条件/竞争条件"(race condition) 分清：**data race 是内存模型层面的、有标准精确定义的、触发 UB 的技术术语**（就是上面四要件）；**race condition 是泛指"结果依赖于不受控的执行时序"的逻辑 bug**，范围宽得多，不一定触发 UB。

举例说明二者不重合。第一种情况有 race condition 但**无** data race：一个用原子操作实现的计数器，两个线程各 `atomic_load` 读到 5、各自 +1、各 `atomic_store` 回 6——最终是 6 而非 7（丢了一次更新）。所有访问都是原子的，没有数据竞争、没有 UB，但业务逻辑错了，这是 race condition。第二种情况有 data race：非原子变量的并发读写（本报告主角），它既是 race condition 也是 data race，且是 UB。初学者记住这个方向即可：**数据竞争一定伴随时序敏感，但时序敏感的 bug 未必是数据竞争**；本大主题只管前者（UB 那一类），后者的一般性讨论散落在 CP-02（正确性规约）与 OS-07（并发 bug）。

#### 来源与时效
- ISO/IEC 9899:2024（C23）§5.1.2.4「Multi-threaded executions and data races」（核实 2026-07-30）：data race 定义"两冲突动作、不同线程、至少一个非原子、无 happens-before ⇒ UB"；"冲突"= 一个修改另一个读或修改同一内存位置；"memory location"粒度（含相邻位域规则）。措辞较 C11/C17 无实质改变。
- ISO C++ `[intro.races]`（现行 C++23，段落号随版本微移，约 `[intro.races]/2` 冲突定义、`/21` data race 定义；核实 2026-07-30，经 cppreference c++/language/memory_model 指路后回落标准原文）：与 C 表述一致。**冲突项（措辞分歧，非结论分歧）**：C 说"in different threads"，C++ 用"potentially concurrent"并额外覆盖同线程内 signal handler / unsequenced 的情形——C++ 定义面更宽，普通多线程场景两者等价，signal handler 细节两边定位如上。
- cppreference「memory model」「Race condition ≠ data race」条目（指路，核实 2026-07-30；结论回落 ISO）：data race vs race condition 的区分表述。
- Boehm & Adve, PLDI 2008「Foundations of the C++ Concurrency Memory Model」§2（交叉印证"至少一个非原子"这条为何是定义的核心，核实 2026-07-30）。

## CP-07.2 竞争即 UB 的后果：撕裂读写与编译器的激进假设

### CP-07.2.1 UB 意味着"没有任何保证"，不是"偶尔算错"

标准对数据竞争的判罚是最重的一档——**未定义行为**（UB）。UB 的含义不是"这次可能读到旧值"这么温和，而是**整个程序的行为不受任何约束**：可能算错、可能崩溃、可能看起来正常、也可能让**与竞争无关的**别处代码出错。业界把这种语义叫"catch-fire semantics"（着火语义）：一旦有竞争，标准允许实现"做任何事"。

初学者常有的错觉是"竞争最坏也就是数值不准，我能接受"。这是危险的误解。因为编译器和 CPU 的正确性证明**全部建立在"程序无数据竞争"这个前提上**——一旦前提被破坏，它们此前所有"合法"的优化和重排都不再对你负责。所以竞争的后果不是"局部小错"，而是"地基抽掉、全楼不保证"。这也是为什么 07.4 要斩钉截铁地说"没有安全的良性非原子竞争"——你无法给一个 UB 划定"它最多只会坏到这里"的边界。

### CP-07.2.2 撕裂读写（torn read/write）

第一种具体后果是**撕裂**：一个宽度超过硬件原子粒度的非原子对象（例如某些平台上的 64 位量、或结构体、或未对齐访问），它的一次"写"在机器层面可能被拆成多条存储指令；如果另一个线程此时去读，就可能读到**一半是新值、一半是旧值**的、任何一次写入都从未产生过的"缝合怪"值。

用一个直觉图景理解：把 64 位写想象成"先写低 32 位、再写高 32 位"两笔。读线程若卡在两笔中间，读到的就是"新低位 + 旧高位"。这个值可能是一个非法指针、越界下标，进而引爆更严重的错误。撕裂正是"为什么需要原子类型"的最硬核理由之一：原子访问保证"要么全看到写前、要么全看到写后，没有中间态"。注意撕裂**是否发生**依赖平台字长、对齐、以及编译器生成的指令——所以它是典型的"这台机器上碰巧不撕裂，换台机器/换个优化等级就撕裂"的飘忽 bug，这也让它极难靠测试发现。

### CP-07.2.3 编译器的激进优化：本机实证

比撕裂更隐蔽的后果是：**编译器基于"无数据竞争"的假设做激进优化**——它默认一个非原子变量在两次访问之间不会被别的线程动，于是可以自由地把它缓存进寄存器、复用上次读到的值、合并多次写、甚至凭空发明读写。下面用基线机器上的真实反汇编演示这一点。测试程序让 4 个线程各对全局非原子 `long counter` 自增 10 万次（源码见 07.3）：

```
# 环境：gcc 13.3.0 / Linux 6.18.5 x86-64 / -std=c11
$ gcc -std=c11 -O2 -pthread race.c -o race_plain
$ objdump -d --no-show-raw-insn race_plain   # 摘 worker 函数
0000000000001250 <worker>:
    1250:  endbr64
    1254:  addq   $0x186a0,0x2db9(%rip)    # counter
    125f:  xor    %eax,%eax
    1261:  ret
```

十万次循环自增，被编译器整体折叠成了**一条**加法指令 `addq $0x186a0, counter`（`0x186a0` = 十进制 100000）。编译器的推理是：既然按标准没有数据竞争，那这段时间内 `counter` 只有本线程在动，"加 10 万次 1"等价于"加 100000"，合并合法。但当四个线程真的并发跑这条"读-改-写"时，它们互相覆盖，结果全靠运气。这就是"编译器基于无竞争假设做激进优化"的字面演示——你写的 10 万次内存往返，在生成码里根本不存在。

一个反直觉的观测：这个 -O2 版本跑出来常常"看起来是对的"：

```
$ for i in 1 2 3 4 5; do ./race_plain; done
counter = 400000 (expected 400000)      # ×5，全对
```

因为被折叠成单条 `addq` 后，四个线程各自"读 counter、加 100000、写回"，在这台机器上这几条指令碰巧没有交错、结果凑巧正确。这恰恰印证了 07.2.1 的警告：**UB 程序"跑对了"不代表它没错**。把优化关到 -O0，循环没被折叠、10 万次真实往返充分交错，丢失更新立刻现形：

```
$ gcc -std=c11 -O0 -pthread race.c -o race_O0
$ for i in 1 2 3; do ./race_O0; done
counter = 121569 (expected 400000)
counter = 105638 (expected 400000)
counter = 110740 (expected 400000)
```

同一份"有竞争"的源码，-O2 看似正确、-O0 明显算错，结果还随每次运行漂移——这正是数据竞争 UB 的典型面孔：不可靠、不可复现、随编译器/优化等级/调度而变。

#### 来源与时效
- ISO C23 §5.1.2.4 / ISO C++ `[intro.races]`（核实 2026-07-30）：data race ⇒ UB 的定性。
- Hans-J. Boehm「Threads Cannot Be Implemented as a Library」PLDI 2005（交叉印证：编译器合法变换会破坏"看似无害"的竞态代码，正是"必须把内存模型放进语言、竞争必须是 UB"的动因；核实 2026-07-30）。
- Boehm & Adve, PLDI 2008 §2–3（"catch-fire"/DRF-or-UB 语义的正式论证；核实 2026-07-30）。
- 本机实证（gcc 13.3.0 / Linux 6.18.5 / -std=c11，核实 2026-07-30）：`objdump` 显示 -O2 把十万次非原子自增折叠为单条 `addq $0x186a0,counter`（0x186a0 = 100000）；-O2 五次运行全 = 400000（UB 碰巧"对"），-O0 三次运行 = 121569 / 105638 / 110740（丢更新现形）。撕裂 (07.2.2) 在本机 64 位对齐 `long` 上未直接观测到，属平台相关、如实标未复现。

## CP-07.3 TSan 检测：影子内存 + happens-before 追踪

### CP-07.3.1 ThreadSanitizer 的工作原理

**ThreadSanitizer**（TSan，`-fsanitize=thread`）是 gcc/clang 内建的**动态**数据竞争检测器。它在编译期给程序里每一次内存访问和每一个同步操作插桩，运行时维护两套数据：一是**影子内存**(shadow memory)——为应用内存的每个位置保存最近若干次访问的"影子记录"，每条记录压缩了访问它的**线程 id、逻辑时钟(epoch)、读还是写、访问宽度**；二是每个线程一份**向量时钟**(vector clock)，随加锁/解锁、线程创建/汇合、原子操作等同步事件更新，用来判定任意两个事件之间是否存在 **happens-before** 关系。

判定规则直接照搬 07.1 的定义：当一次新访问与影子里记录的某次旧访问**冲突**（同一位置、至少一写），TSan 就查这两次访问的向量时钟——**若二者互不 happens-before**，正好命中数据竞争四要件，立刻报警。可以把它理解成"标准定义的一个可执行版本"：标准说"无 happens-before 的冲突非原子访问 = 竞争"，TSan 就实时地对每对冲突访问算 happens-before。所以 TSan 报的不是"值算错了"，而是"这两次访问在内存模型意义上构成竞争"——哪怕这次结果碰巧正确（呼应 07.2 的 -O2 案例）。

### CP-07.3.2 本机实证：复现 data race 报告

测试程序（4 线程各对非原子全局 `counter` 自增 10 万次）：

```c
/* race.c */
#include <pthread.h>
#include <stdio.h>
static long counter = 0;                 /* 非原子全局 */
static void *worker(void *arg) {
    for (int i = 0; i < 100000; i++) counter++;   /* 非原子读-改-写，冲突访问 */
    return NULL;
}
int main(void) {
    pthread_t t[4];
    for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, worker, NULL);
    for (int i = 0; i < 4; i++) pthread_join(t[i], NULL);
    printf("counter = %ld (expected 400000)\n", counter);
    return 0;
}
```

编译运行（基线 gcc 13.3.0 / Linux 6.18.5）：

```
$ gcc -std=c11 -O1 -g -fsanitize=thread -pthread race.c -o race
$ ./race
==================
WARNING: ThreadSanitizer: data race (pid=18486)
  Read of size 8 at 0x5590d8f09018 by thread T2:
    #0 worker race.c:5
  Previous write of size 8 at 0x5590d8f09018 by thread T1:
    #0 worker race.c:5
  Location is global 'counter' of size 8 at 0x5590d8f09018 (race+0x4018)
  Thread T2 (tid=18490, running) created by main thread at:
    #0 pthread_create
    #1 main race.c:10
  Thread T1 (tid=18489, finished) created by main thread at:
    #0 pthread_create
    #1 main race.c:10
SUMMARY: ThreadSanitizer: data race race.c:5 in worker
==================
```

报告逐字对上了 07.1 的四要件：两个不同线程（T1 写、T2 读）对**同一内存位置**（全局 `counter`，地址 `0x5590d8f09018`，宽 8 字节）的**冲突访问**（一读一写），且 TSan 判定二者**无 happens-before**——四条齐了，判为 data race，精确指到源码 `race.c:5`。这就是把 UB 从"抽象定义"变成"手里一份可定位报告"。

### CP-07.3.3 动态检测的能力边界

必须讲清 TSan 的局限，否则会误用。TSan 是**动态**检测器，它只能看见**本次运行真正执行到的代码路径和真正发生的线程交错**——因此它**会漏报**（false negative）：一条从未被这次运行触发的竞争路径，它看不到；它**不是**静态证明"程序无竞争"的工具。反过来，因为它基于 happens-before 而非猜测，**几乎不误报**（极少 false positive）：它报的通常是真竞争。

给初学者的实用推论：TSan 报了竞争，几乎可以确信是真 bug，去修；TSan 没报，**不等于**程序无竞争，只说明这次跑到的交错里没暴露。所以要配合高覆盖的并发压力测试、多跑几次、多种线程数与调度下跑，才能提高发现概率。此外 TSan 有可观的时空开销（插桩 + 影子内存），一般只在测试/CI 阶段开，不进生产构建；影子内存与应用内存的具体倍率随实现和配置而变，此处不引具体系数（**待核**，如需以 LLVM/gcc 官方文档为准）。

## CP-07.4 "良性竞争"迷思：没有安全的非原子竞争

### CP-07.4.1 为什么"良性数据竞争"是伪概念

工程实践里流行一种说法："这个竞争是**良性的**（benign）——最坏就是读到个稍旧的值/统计计数略偏，不影响正确性，不用管。"按 C/C++ 标准，这个说法**在语言层面站不住脚**：只要落在四要件里，它就是**未定义行为**，而 UB 没有"最坏只会坏到这里"的上界。你以为的"良性"是在假设编译器会老老实实生成"读一次内存、用那个值"的代码——但编译器**没有义务**这么做，它完全可以基于"无竞争"假设把你的访问缓存、复用、合并、撕裂、甚至凭空多读一次。

Boehm 2011 的论文标题就是结论：《如何用"良性"数据竞争把程序编译坏》。它给出一串真实编译器变换，把程序员眼中"顶多读到旧值"的良性竞争，变成读到**半新半旧的撕裂值**、**同一次读的两处使用得到不同结果**（编译器把一次读拆成两次、中间值被改）、或**因假设值不变而走进本不可达的分支**。初学者要接受的观念是：**"良性"描述的是你的意图，UB 描述的是编译器被授予的自由**——两者不在一个层面，前者管不住后者。凡是想"少加个原子省点性能"的地方，几乎都是这种误判的温床。

### CP-07.4.2 正解：用（哪怕 relaxed 的）原子把竞争移出定义

修正数据竞争的**唯一正道**是消灭四要件里的某一条，而最直接的一条就是第 (4) 条"至少一个非原子"——把被竞争的变量声明为**原子类型**，两个访问就都成了原子访问，按定义**不再构成数据竞争**，UB 随之消失。当你只需要"不撕裂、不被激进优化、单个变量读写各自完整"、**并不**需要它和别的变量建立跨线程顺序时，用最弱的 `memory_order_relaxed` 即可——它给你原子性（消除 UB），但不额外付出屏障开销（顺序保证的强弱谱在 CP-06，本报告不展开）。

把 07.3 的竞争程序按此修正——`long` 换成 `_Atomic long`、`counter++` 换成 relaxed 的 `atomic_fetch_add_explicit`：

```c
/* race_fixed.c */
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
static _Atomic long counter = 0;
static void *worker(void *arg) {
    for (int i = 0; i < 100000; i++)
        atomic_fetch_add_explicit(&counter, 1, memory_order_relaxed);
    return NULL;
}
/* main 同前：创建 4 线程、join、打印 */
```

同样开 TSan 编译运行：

```
$ gcc -std=c11 -O1 -g -fsanitize=thread -pthread race_fixed.c -o race_fixed
$ ./race_fixed
counter = 400000 (expected 400000)
$ echo $?
0
```

TSan **一条 race 都不报**、退出码 0，且结果稳定正确 400000。对比 07.3 的满屏 `WARNING`——同一个计数逻辑，仅把非原子访问换成 relaxed 原子，就从"UB + TSan 报警 + 结果漂移"变成"无竞争 + 干净 + 正确"。这就是"良性竞争"迷思的实证反驳：不存在"靠不修也没事"的非原子竞争，存在的只是"改成原子就一劳永逸"的正解。

这里有一个必须点明的边界，免得初学者过度推广：relaxed 原子只解决了"数据竞争 UB"和"单变量原子性"，它**不**提供跨线程的顺序/可见性保证。本例之所以只用 relaxed 就完全正确，是因为业务只要求"总数不丢"这一件事（`fetch_add` 的原子读-改-写天然满足），线程间不依赖"看到 counter 就能推断别的变量已就绪"。一旦你需要"发布一个标志位、让对方看到标志就意味着某段数据已写好"这种跨变量顺序，relaxed 不够，要用 acquire/release 或 seq_cst——那属于 CP-06。

#### 来源与时效
- Hans-J. Boehm「How to miscompile programs with "benign" data races」HotPar 2011（一手，本节主承重：论证不存在安全的良性非原子竞争，给出编译器变换实例；核实 2026-07-30）。
- ISO C23 §5.1.2.4 + §7.17`<stdatomic.h>` / ISO C++ `[intro.races]` `[atomics]`（核实 2026-07-30）："至少一个非原子"是四要件之一 ⇒ 两访问皆原子则非 data race；relaxed 亦为原子访问，故可消 UB。relaxed 的确切排序语义（不建立同步）归 CP-06。
- 本机实证（gcc 13.3.0 / Linux 6.18.5，核实 2026-07-30）：`_Atomic long` + `atomic_fetch_add_explicit(...,memory_order_relaxed)` 版本在 TSan 下零报警、退出码 0、结果稳定 400000（对比 07.3 满屏 race）。
- 交叉一致：标准（"改原子即出定义"）与 TSan 实测（改后转干净）与 Boehm 2011（"别指望良性"）三源互印，无冲突。

## CP-07.5 与抢占交错的根因：竞争如何被"显形"

### CP-07.5.1 竞争是程序的静态属性，交错是它的显形触发面

要厘清一对因果：**数据竞争是否"存在"，是程序 + 内存模型层面的属性——只要源码里有那对"无 happens-before 的冲突非原子访问"，竞争就客观存在，与它这次跑没跑出错无关**；而竞争是否"显形"（真的算出错值/崩溃），取决于运行时两个线程的指令是否真的以坏的方式**交错**(interleave)。制造交错的两大来源是：多核上的**真并行**（两核真的同时访存），以及单核/被抢占场景下**调度器的抢占**——时钟中断随时打断一个线程、切到另一个，把两段本该"各自跑完"的临界操作剁碎、穿插。

这解释了为什么数据竞争 bug 如此难缠：竞争的**存在**是确定的，它的**显形**却是概率性的、依赖调度时机的。抢占正是那只"随机洗牌的手"——你的 `counter++` 在源码里是一行，在机器上是"读、加、写"三步，抢占可以恰好插在"读"和"写"之间，让另一个线程的更新被覆盖（07.2 -O0 那三次漂移的结果 121569/105638/110740，就是不同运行里抢占把三步切在不同位置的产物）。所以"这次没测出问题"从来不是"没竞争"的证据，只是"这次的调度没把它抖出来"。

### CP-07.5.2 与抢占式调度的分账与关联

调度器**如何**实现抢占——时钟中断、内核夺回控制权、上下文切换的机制——属于 L4-01·OS-05（CPU 调度）的内容，本报告不展开。本节只借它一个结论：**抢占式调度会制造出程序员没预期的交错，而这些交错正是数据竞争从"存在"走向"显形"的触发面**。反过来看也成立：即便在**单核**、**协作式**（无抢占）调度下，如果让出点恰好落在临界操作中间，竞争一样能显形——只是概率和形态不同；多核则连"让出"都不需要，两核直接同时踩。

给初学者的整合视角，把本大主题五节串成一条因果链：源码里埋下"无 happens-before 的冲突非原子访问"（07.1 定义）→ 这是标准判定的 UB，编译器据此激进优化、机器可能撕裂（07.2 后果）→ 抢占/多核制造出坏交错把它显形成飘忽的错值（07.5 根因）→ 用 TSan 这类工具在测试期把它逮出来、定位到行（07.3 检测）→ 用锁建立 happens-before、或用（relaxed）原子把它移出竞争定义来根治（07.4 修正）。抓住这条链，就抓住了"数据竞争与 UB"这个大主题的全貌。
