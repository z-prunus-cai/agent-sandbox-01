# L5-15·大主题9 DMA 与高效数据搬运

> 基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25 ｜核实日期：2026-08-01 ｜先修：E-02 处理器与内存架构、E-05 中断与实时响应、E-08 串行通信总线 ｜一手锚点：TM4C123GH6PM Datasheet/SoC Reference Manual「Micro Direct Memory Access（µDMA）」章、Lee & Seshia《Intro to Embedded Systems — CPS Approach》2nd ed Ch10 ｜成熟度：⚙演进快·锚平台 TI EK-TM4C123GXL（Cortex-M4）µDMA·其它 SoC 的 DMA 引擎结构与字段可能不同

DMA（Direct Memory Access，直接存储器访问）是一个能"替 CPU 搬数据"的独立硬件。本报告以 TI TM4C123（Cortex-M4）上的 µDMA 为锚平台讲清 DMA 的通用机制：控制器与通道怎么组织、外设怎么触发一次搬运、内存和外设之间用什么"描述符"约定搬什么、以及乒乓/双缓冲如何让 CPU 几乎不插手就完成连续数据流。DMA 引擎是高度平台相关的部件，具体通道数、寄存器名、描述符字段在不同厂商 SoC 上差异很大，凡涉及具体数值处均以 TM4C123 µDMA 为准并硬标演进快。

## 9.1 DMA 控制器、通道与触发源

### 9.1.1 DMA 是什么，为什么比 CPU 搬运高效

DMA 是一个位于总线上的独立主控（bus master），它能在不占用 CPU 执行流的情况下，把数据从一个地址搬到另一个地址。没有 DMA 时，把 UART 收到的一串字节存进内存要靠 CPU 一个字节一个字节地"读外设寄存器、写内存、判断是否结束、循环"，每个字节都消耗若干条指令；有了 DMA，CPU 只需事先告诉 DMA"从哪搬、搬到哪、搬多少、什么时候搬"，之后 DMA 自己完成，CPU 腾出来去做别的事，全部搬完后 DMA 发一个中断通知 CPU。

理解它的关键直觉是"谁来驱动总线"。CPU 拷贝时，每次内存访问都夹在取指、译码之间，搬运和计算抢的是同一个执行单元；DMA 则是另一个能独立发起总线读写的部件，它和 CPU 分时使用总线（通过仲裁），CPU 大部分时间照常跑自己的指令。所以 DMA 的收益不完全是"更快地搬"（单次总线传输速度未必比 CPU 快），而是"搬运时把 CPU 解放出来"——这在高采样率 ADC、连续串口/音频流这类场景里是决定性的。

一个常见误解是以为 DMA 一定比 CPU 拷贝快。对小批量、地址不规则的搬运，配置 DMA 的开销（填描述符、设通道）可能超过省下的时间；DMA 的优势体现在中到大批量、周期性、外设驱动的搬运上。另一个易错点是忘了 DMA 和 CPU 共享总线带宽：DMA 忙时会和 CPU 的内存访问争用总线，导致 CPU 侧轻微变慢，这叫总线争用（bus contention），不是错误但要计入时序预算。

### 9.1.2 控制器结构：单一引擎 + 多通道 + 仲裁器

TM4C123 的 µDMA 是一个集中式的单引擎控制器，对外提供 32 个可独立配置的通道（channel）。它本身不是 32 个并行搬运器，而是一个引擎按优先级在这些通道间轮流服务：某个通道被触发后，引擎为它搬运"一批"（由仲裁大小决定），然后重新仲裁，可能切到另一个更高优先级的、也被触发了的通道。因此多通道是"逻辑上并发、物理上分时"。

把它想成一个只有一个窗口的银行柜台，32 个通道是 32 条排队线。谁被"叫号"（触发）谁才有资格排队，柜员（引擎）每次处理固定笔数就抬头重新看哪条队优先级最高。这个"每处理固定笔数就重新挑队"的动作就是仲裁（arbitration），保证高优先级、时间敏感的外设不会被一个大块搬运长期饿死。

µDMA 是一个"精简版"DMA：它的设计源自 ARM PrimeCell 系列的轻量 µDMA（业界常称其对应 PL230 一族，具体授权版本以 TI 手册为准，此归属属常见说法·非承重），面向 Cortex-M 这类资源受限 MCU，所以功能比应用处理器上的大型 DMA（多引擎、二维/链表搬运）要克制。初学者不必纠结型号，记住"单引擎、多通道、靠仲裁分时"这个模型即可。

### 9.1.3 通道与外设的固定映射

在 µDMA 上，每个通道号并不是随便用的：它通过一张固定（部分可用通道选择位重映射）的映射表绑定到具体外设的具体请求上，比如某通道对应 UART0 的接收、另一通道对应 UART0 的发送、再一个对应某个 ADC 序列。所以"用 DMA 服务某外设"的第一步，是查手册确认该外设的收/发各走哪个通道号。

这样设计的原因是硬件连线：外设的 DMA 请求信号是物理连到 DMA 控制器的固定输入脚上的，通道号本质上就是这根请求线的编号。初学者最容易踩的坑就是随便挑一个空闲通道号去接某外设，结果那个外设的请求根本不接到这个通道上，DMA 永远不被触发、程序卡在等待。TM4C123 用一组通道映射选择（每个通道有几个候选外设，用配置位选一个）缓解通道不够分的问题，但选择范围仍是手册钦定的，不能任意组合。

不同外设可以同时占用不同通道各干各的，互不干扰。例如通道 A 把 UART 收到的字节持续搬进内存，同时通道 B 把 SPI 收到的数据搬进另一块内存，两者由同一个引擎分时服务但逻辑独立。

### 9.1.4 触发源：软件请求与外设请求，单次与突发

一次 DMA 搬运必须被"触发"才会发生。触发源分两大类。软件请求（software request / auto request）是 CPU 主动写一个寄存器位说"现在开始搬"，常用于内存到内存的整块拷贝。外设请求是外设在某个事件（收到一个字节、FIFO 达到阈值、一次 ADC 转换完成、定时器到点）时自动向 DMA 拉起请求线，这是 DMA 最典型的用法——搬运节奏由外设的数据节奏驱动，CPU 完全不介入。

外设请求又分单次请求（single request，记作 SB 里的 S）和突发请求（burst request，记作 B）。单次请求表示"外设现在只有 1 个数据单位可搬"（如 FIFO 里刚到 1 个字节）；突发请求表示"外设现在攒够了一批可搬"（如 FIFO 达到半满阈值，一次能搬多个）。DMA 可以配置成只响应突发请求（useburst 位），以减少频繁的小搬运带来的仲裁开销。

这里初学者要理解"请求"和"实际搬多少"是两回事：一次请求触发的是"引擎为该通道服务一轮"，一轮到底搬几个由仲裁大小（下一节）和剩余传输数共同决定，而不是"一次请求搬完整个缓冲"。把这两者混为一谈会算错时序和中断次数。

### 9.1.5 通道优先级与仲裁大小

µDMA 提供两级优先级：默认级和高优先级（每个通道可设为高）。同一时刻有多个通道被触发时，高优先级通道先被服务；同级之间按通道号，通道号越小优先级越高（通道 0 最高）。这套规则保证时间敏感的外设（如高速 ADC）能插队到大块低速搬运前面。

仲裁大小（arbitration size）是每个通道单独设置的一个关键参数：引擎为某通道连续搬运多少个数据单位后，就停下来重新做一次优先级仲裁。它可取 1、2、4、8……直到 1024（2 的幂）。设得小，引擎响应更公平、高优先级通道插队更及时，但仲裁次数多、总吞吐略降；设得大，吞吐高但可能让高优先级通道等待更久。

一个直觉例子说明为什么要能配这个值。假设通道 0 服务一个每 1 µs 就必须被服务一次的高速外设，通道 5 在做一大块内存拷贝。如果通道 5 的仲裁大小设成 1024，引擎一旦开始服务它就要连搬 1024 个才回头看通道 0，通道 0 可能已经溢出丢数据；把通道 5 的仲裁大小调小（如 8），引擎每搬 8 个就重新仲裁，通道 0 能及时插队。这就是仲裁大小在实时性和吞吐之间的权衡旋钮。

仲裁大小最好设成不超过外设 FIFO 的可搬深度，且与突发请求阈值匹配，否则可能出现"外设说有 4 个可搬，DMA 却想搬 8 个"的错配，导致行为不符合预期。另外在 auto（软件请求）模式下，仲裁大小对"一次请求搬多少"的意义与外设触发模式不同——auto 模式一次请求会尝试搬完全部剩余，仲裁仍在通道间切换但不受外设逐次请求节流。

## 9.2 内存↔外设搬运模式与传输描述符

### 9.2.1 三种搬运方向

DMA 支持三种基本方向：内存到内存（memory-to-memory，如大块数组拷贝）、内存到外设（memory-to-peripheral，如把一段缓冲发出 UART/SPI）、外设到内存（peripheral-to-memory，如把 ADC 采样或 UART 接收持续存进缓冲）。方向不是一个单独开关，而是由"源地址、目的地址、以及地址是否递增"三者的组合隐式决定的。

理解方向的关键在于地址递增。内存侧通常需要递增（每搬一个就指向下一个内存单元），外设侧通常不递增（反复读/写同一个数据寄存器，因为外设的数据口是固定地址）。所以外设到内存就是"源不增、目的递增"，内存到外设就是"源递增、目的不增"，内存到内存则是"两边都递增"。初学者最常见的 bug 就是把外设侧也设成递增，结果 DMA 越过数据寄存器去访问相邻外设寄存器，数据全错。

### 9.2.2 通道控制表与传输描述符

µDMA 不把"搬什么"存在控制器内部寄存器里，而是要求软件在 SRAM 中开辟一张通道控制表（channel control table），DMA 引擎从这张表里读取每个通道的搬运参数。这张表就是"传输描述符"的集合：每个通道在表中占一个固定大小的槽位，槽位里写着源、目的、数量、模式等。引擎被触发时先去表里读该通道的描述符，据此搬运，搬完再把更新后的状态（如剩余计数）写回表里。

控制表有两条硬性约束（TM4C123）：整张表必须连续存放，且起始地址对齐到 1024 字节边界。每个通道的控制结构占 16 字节，即 4 个 32 位字。之所以要 1024 字节对齐，是因为引擎用通道号作为高位索引、用"主/备"和字段偏移作为低位来定位描述符，对齐让地址计算变成简单的位拼接。初学者若忘了对齐（比如直接 `uint8_t table[1024];` 而没加对齐属性），DMA 会读到错位的描述符，行为完全不可预测——这是配置 µDMA 最经典的坑。

每个通道其实有两份控制结构：主（primary）与备（alternate）。二者结构相同，成对存在正是为下一节的乒乓/散布-聚集模式服务。下面给出单个控制结构的 16 字节布局（块级示意，不内联）：

```
偏移 +0x0 : 源结束指针     (source end pointer,      32-bit)
偏移 +0x4 : 目的结束指针   (destination end pointer, 32-bit)
偏移 +0x8 : 控制字         (control word,            32-bit)
偏移 +0xC : 保留/未用      (unused,                  32-bit)
```

### 9.2.3 源/目的端指针为什么是"结束地址"

µDMA 的描述符里存的不是起始地址而是结束（end）地址，且是包含（inclusive）最后一个被搬元素的地址。引擎内部用一个递减的计数器倒着算，从结束地址减去（剩余个数 × 元素大小）反推当前该访问哪里。这与直觉相反，是初学者常算错的地方。

结束指针的计算方式是"缓冲首地址 + (元素个数 − 1) × 元素字节数"。例如把一个 8 个 32 位字的数组搬出去，源结束指针应指向 `&buf[0] + (8-1)*4`，也就是 `&buf[7]`，而不是 `&buf[0]`，也不是数组末尾之后。对不递增的外设侧（如 UART 数据寄存器），结束指针就直接填该寄存器地址本身（个数视作使地址不动）。

厂商库函数（如 TI 的 `uDMAChannelTransferSet`）通常帮你从"首地址 + 个数"算好结束指针，所以用库时不必手算；但一旦手写描述符或调试底层，务必记得这是结束地址、且 inclusive，差一个元素（off-by-one）就会漏搬或越界。

### 9.2.4 传输模式：Stop / Basic / Auto / Ping-Pong / Scatter-Gather

控制字里的传输模式字段决定引擎如何响应请求。TM4C123 µDMA 定义了以下模式：

```
Stop            : 通道停用/传输结束，不搬运
Basic           : 每次收到请求，搬「仲裁大小」个，直到总数搬完；适合外设逐次触发
Auto            : 一次软件请求即搬完全部剩余；即使请求撤销也继续；适合 mem→mem
Ping-Pong       : 主/备两个结构交替使用，一个搬完自动切到另一个并发中断；适合连续流
Memory Scatter-Gather   : 用一张任务列表把多段不连续内存搬运串成一次自动序列
Peripheral Scatter-Gather : 同上，但由外设请求驱动每一段
```

Basic 与 Auto 的区别是初学者的分水岭。Basic 模式下"每次外设请求 → 引擎搬一批（仲裁大小）→ 等下一次请求"，搬运节奏跟着外设走，适合"外设有一个我搬一个"的流式接收/发送。Auto 模式下一次请求就把整块搬完，中途不再看请求信号，适合 CPU 主动发起的内存到内存整块拷贝。用错模式的典型后果：本该 Basic 的外设接收错设成 Auto，第一次请求就把整块"搬完"（但外设其实还没那么多数据），读进一堆垃圾。

Scatter-Gather（散布-聚集）解决"数据在内存里分散成好几段、或要对多个外设做一串不同搬运"的问题：软件预先在内存里写好一张任务列表（每个任务就是一个完整的控制结构），DMA 用 alternate 结构逐条加载并执行，一次触发自动跑完整串，无需 CPU 在每段之间干预。TM4C123 的散布-聚集任务列表长度有上限（社区转述 TI 手册为最多 256 个任务，具体上限以对应型号手册为准，标「以手册为准」）。这是 µDMA 里最接近"链表式 DMA"的能力。

### 9.2.5 数据宽度与单次传输计数上限

每个通道可独立设置源和目的的数据宽度：8 位、16 位或 32 位。源和目的宽度通常应相同（µDMA 不做位宽转换/打包，宽度不一致会出错）。地址递增步长一般应与数据宽度匹配（搬 32 位就每次 +4）。

单个描述符的传输计数是一个 10 位字段，因此一次描述符最多搬 1024 个数据单位。要搬超过 1024 个，就得靠 Ping-Pong（两结构轮流、每轮各最多 1024）或 Scatter-Gather（多段串接）来接力，或在完成中断里重装描述符。初学者容易忽略这个 1024 上限，试图一次 DMA 搬一个几千元素的大数组而只搬了前 1024 个。

计数与元素个数的关系也要留意：计数是"元素个数"，不是"字节数"。搬 100 个 32 位字，计数填 100（对应 400 字节），别填 400。这与"结束指针用字节偏移算"是两套单位，混用是常见错误。

## 9.3 双缓冲 / 乒乓与 CPU 卸载数据流

### 9.3.1 双缓冲/乒乓：让填与处理永不撞车

连续数据流（如持续 ADC 采样、串口/音频接收）有个根本矛盾：DMA 一直在往缓冲里写，CPU 又想读缓冲去处理，如果读写同一块缓冲，CPU 读到的可能是半新半旧的数据。双缓冲（double buffering）/乒乓（ping-pong）用两块缓冲 A、B 解决它：DMA 填 A 时，CPU 处理上一轮填好的 B；A 填满触发中断后，DMA 立刻切去填 B，CPU 转去处理 A。两者永远在不同缓冲上工作，互不干扰，数据流不中断。

µDMA 的 Ping-Pong 传输模式天生为此设计：主（primary）结构指向缓冲 A、备（alternate）结构指向缓冲 B，一个结构的传输完成后引擎自动切换到另一个并发出中断，无需 CPU 在切换瞬间重配——这正是"每通道两份控制结构"存在的理由。CPU 在中断里只需处理刚填满的缓冲、并（若需要）为下一轮重装该结构，切换本身零延迟。

下面用主机侧纯逻辑仿真验证乒乓的核心不变式"CPU 处理的缓冲永远不是 DMA 正在填的那个"（非硬实时、仅验证逻辑；`基线 Py3.11.15 @2026-08-01`）：

```python
N = 4                    # 每个缓冲容纳的样本数
bufs = {'A': [None]*N, 'B': [None]*N}
sample, active, conflict = 0, 'A', False
log = []
for _ in range(4):                     # 4 次"传输完成中断"
    for i in range(N):                 # DMA 填满 active 缓冲
        bufs[active][i] = sample; sample += 1
    filled, active = active, ('B' if active=='A' else 'A')  # 完成→切换
    if filled == active: conflict = True   # CPU 处理 filled，DMA 已在填新 active
    log.append((filled, list(bufs[filled])))
for name, data in log: print(f"  {name}: {data}")
print("CPU处理缓冲 与 DMA当前缓冲 冲突过吗:", conflict)
```


```
处理顺序(缓冲名, 内容):
  A: [0, 1, 2, 3]
  B: [4, 5, 6, 7]
  A: [8, 9, 10, 11]
  B: [12, 13, 14, 15]
CPU处理缓冲 与 DMA当前缓冲 冲突过吗: False
```

数据 0..15 连续无丢失、无重复，且 CPU 处理的缓冲从未与 DMA 正在填的缓冲相同——这就是乒乓保证的"不撞车"性质。注意这只是逻辑仿真，真实系统里还要保证"CPU 处理一块的时间 < DMA 填另一块的时间"，否则会来不及、下一次切换时旧数据还没处理完就被覆盖。

### 9.3.2 半传输 / 全传输中断驱动的流式处理

除了用两块物理缓冲，另一种等价手法是用一块大缓冲配"半传输中断（half-transfer）+ 全传输中断（transfer-complete）"：DMA 填到一半时发一次中断（CPU 去处理前半），填满时再发一次（CPU 处理后半，DMA 回卷从头继续填前半）。逻辑上等价于把一块缓冲切成两个乒乓半区，好处是配置更简单、地址连续。

它的关键前提同样是"处理速度跟得上填充速度"。若 CPU 处理前半的耗时超过 DMA 填后半的耗时，DMA 回卷时会覆盖尚未处理完的前半数据，造成数据损坏——这类 bug 很隐蔽，低数据率时不出现，一提高采样率就间歇丢数据。设计时要按最坏情况估算处理时间预算。

TM4C123 µDMA 的 Ping-Pong 模式本身就在每个结构完成时给中断，效果与"半/全中断"一致；STM32 等平台则更常直接提供 HT/TC 两个中断标志。两种叫法背后是同一个"分段完成通知，让处理与搬运重叠"的思想。

### 9.3.3 CPU 卸载：轮询 vs 中断 vs DMA 三种 I/O 范式

DMA 是三种 I/O 数据搬运范式里 CPU 参与度最低的一种，把它放在谱系里看最清楚（块级对比，不内联）：

```
范式      CPU 参与度                     适用场景                     代价
轮询      最高：循环里反复查状态位、      简单、低速、时序确定；        CPU 空转、忙等待浪费
(polling) 每个数据都由 CPU 亲手搬        对延迟要求极严的小任务        算力与功耗
中断      中：外设事件时打断 CPU，       中低速、事件稀疏；            每个数据一次中断，
(IRQ)     在 ISR 里搬 1 个/几个数据      需要及时响应但数据量不大      高频时 ISR 开销累积
DMA       最低：CPU 只配置一次，        中高速、大批量、周期性        配置复杂、通道有限、
          搬运全程不介入，完成才中断     连续流(ADC/音频/串口)         有总线争用与一致性问题
```

选择的直觉是"数据率与批量"。低速偶发用轮询或中断即可，简单直接；一旦数据高频到"每个字节都进一次中断，ISR 开销就吃掉大半 CPU"，就该上 DMA——DMA 把"每字节一次中断"降成"每一整块一次中断"，中断频率骤降。这也是 E-05 里三范式对比的落地：DMA 不是替代中断，而是和中断配合（DMA 搬数据、完成时用中断通知），把中断从"数据级"提升到"块级"。

易错点是以为"上了 DMA 就零 CPU 开销"。配置 DMA、处理完成中断、必要时重装描述符、以及可能的缓存维护（见 9.3.4）都要 CPU 花时间；对极小批量，这些固定开销可能得不偿失。DMA 是"高吞吐场景摊薄单位开销"，不是"消灭开销"。

### 9.3.4 缓存一致性问题：DMA 与 CPU 可能看到不同数据

在带数据缓存（D-cache）的处理器上，DMA 与 CPU 会各看各的数据副本，产生一致性（coherency）问题。CPU 读写内存时数据可能停留在 D-cache 里没落到实际 SRAM；而 DMA 直接读写 SRAM、绕过 CPU 的 cache。于是两个方向都会出错：DMA 从外设写进 SRAM 后，CPU 若读到的是 cache 里的旧副本，就拿到过期数据（读方向）；CPU 写好一段要发出去的缓冲若还停在 cache 里没回写 SRAM，DMA 从 SRAM 读到的就是旧数据（写方向）。

必须先讲清锚平台的实情：TM4C123 是 Cortex-M4 内核，没有数据缓存，因此在 TM4C123 上这个一致性问题基本不存在——DMA 和 CPU 看到的就是同一份 SRAM。这个问题主要出现在带 D-cache 的高端 Cortex-M（典型是 Cortex-M7，如 STM32F7/H7），以及应用处理器上。把"DMA 一致性"当成所有 MCU 的通病，是初学者从教程里搬来的常见误解；它是否成立取决于该核是否有 cache。

在有 cache 的平台上，标准解法有两类。其一是缓存维护操作：在 DMA 从内存读之前，CPU 对该缓冲做 clean（把 cache 里的脏数据回写 SRAM），保证 DMA 读到最新；在 DMA 写完内存之后、CPU 读之前，对该缓冲做 invalidate（丢弃 cache 旧副本，强制下次从 SRAM 重读）。其二是把 DMA 缓冲放到不可缓存（non-cacheable）内存区——用 MPU 把某段 RAM 标成不缓存，或用天生不经 cache 的紧耦合内存（TCM），从此这块缓冲不再有一致性问题，代价是 CPU 访问它时享受不到 cache 加速。

invalidate 的粒度是缓存行（cache line，常 32 字节），若 DMA 缓冲没按缓存行对齐、且与其它变量共享同一缓存行，invalidate 会连带丢弃邻居变量的更新，或 clean 时把邻居的旧值写回覆盖 DMA 刚写的新值。所以有 cache 的平台上，DMA 缓冲应按缓存行大小对齐并独占整数个缓存行。

### 9.3.5 volatile、内存屏障与其它常见陷阱

即使在无 cache 的 TM4C123 上，DMA 也有几个必须处理的正确性陷阱。第一是 `volatile`：被 DMA 异步改写的缓冲和标志变量，在 C 里应声明为 `volatile`，否则编译器可能假设"CPU 没写过它就没变"，把对它的读缓存进寄存器、优化掉重复读，导致 CPU 看不到 DMA 的更新。这与缓存一致性是两个层次的问题——`volatile` 管的是编译器优化，缓存管的是硬件副本，二者都要各自处理，`volatile` 不能替代缓存维护，缓存维护也不能替代 `volatile`。

第二是完成的判定与重入。判断"DMA 搬完了"要用完成中断或查通道模式回到 Stop，而不是靠猜时间；在完成中断里重装描述符、切换缓冲要够快，赶在下一轮数据到来前完成，否则丢数据。第三是内存屏障：在弱序内存模型或涉及外设配置的场景，配置好描述符、使能通道之间可能需要数据同步屏障（如 `__DSB()`），确保写配置的动作在启动 DMA 前真正生效；Cortex-M 多数内存访问是强序的，但对"配置外设→启动搬运"这种跨外设顺序，显式屏障更稳妥。

第四是总线争用与优先级饥饿：DMA 大块搬运会与 CPU 争总线，若把某个大搬运通道设成高优先级 + 大仲裁值，可能让时间敏感的通道或 CPU 拿不到总线。设计时用优先级和仲裁大小（见 9.1.5）把时间敏感的小搬运放在前面。第五是地址与计数单位错配（见 9.2.3、9.2.5）：结束指针用字节偏移算、传输计数用元素个数、外设侧地址不递增——这三点各错一次都会搬出乱数据，是 µDMA 调试时最先要核对的清单。
