实时操作系统（RTOS）解决的核心问题是：让一颗单核微控制器"看起来"同时做很多件事，并且对时间要求严格的那几件事能被保证在截止期（deadline）前完成。它和你在 PC 上用的 Linux/Windows 这类通用 OS 有一个根本区别——通用 OS 追求的是平均吞吐和公平，而 RTOS 追求的是时间上的可预测性（determinism）：宁可整体慢一点，也要让关键任务的最坏响应时间有一个可以事先算出来的上界。

这份报告按教学序覆盖六个小主题：任务模型与状态机、抢占式调度与上下文切换、实时调度理论（RMS/EDF 与可调度性判定）、同步原语、优先级反转与继承/天花板协议、以及 WCET 与时序分析。理论部分（RMS/EDF、优先级继承）几十年来结论稳定；涉及具体 RTOS API 和默认行为的部分演进较快，凡触及处均锚版本并标演进快。

## 10.1 任务/线程模型与任务状态机

### 10.1.1 任务（task）作为并发的基本单位

在 RTOS 里，一个"任务"（task，有些 RTOS 叫 thread）就是一段拥有自己独立栈、自己的执行现场（寄存器快照）、自己优先级的顺序代码。程序员把一个大系统拆成若干个各自循环运行的任务——比如"读传感器"一个任务、"驱动电机"一个任务、"刷新显示"一个任务——每个任务写起来像一段独立的死循环，仿佛整台机器只为它一个人服务。RTOS 内核负责在这些任务之间快速切换，制造出"同时运行"的假象。

初学者最容易混淆"任务"和"函数"。函数调用完就返回、栈随之弹空；而任务通常是一个不返回的无限循环（`for(;;){...}`），它的栈在整个生命周期里一直存在，因为随时可能在循环中途被切走、之后还要从原地恢复。每个任务都需要一块单独的栈空间，这正是 RTOS 比裸机"超级循环"（super-loop）吃更多 RAM 的原因：任务越多，栈越多。在只有几十 KB SRAM 的 MCU 上，任务数量和每个任务的栈深度是必须精打细算的预算。

一个典型的 FreeRTOS 任务函数骨架如下（API 名与版本相关，⚙演进快·锚 FreeRTOS kernel v11.x）：

```c
void vSensorTask(void *pvParameters) {
    for (;;) {
        read_sensor();
        vTaskDelay(pdMS_TO_TICKS(10));  /* 让出 CPU 10ms，进入阻塞态 */
    }
}
/* 创建：xTaskCreate(vSensorTask, "sensor", STACK_WORDS, NULL, PRIORITY, &handle); */
```

### 10.1.2 任务状态机：就绪 / 运行 / 阻塞（及挂起、删除）

任何时刻，一个任务处于一组互斥的状态之一。最核心的三态是：运行（Running，此刻正占着 CPU，单核上任一时刻至多一个任务处于此态）、就绪（Ready，一切就绪、只差 CPU，正在排队等调度器挑中）、阻塞（Blocked，在等待某个事件——延时到期、信号量可用、队列有数据——在事件到来前不参与 CPU 竞争）。多数 RTOS 还有挂起态（Suspended，被显式暂停、连事件也不等）和删除/终止态。

状态之间的转移由三类动作驱动：调度器选中（Ready→Running）、任务主动或被动让出（Running→Ready 被抢占，或 Running→Blocked 主动等待），以及事件到达（Blocked→Ready）。理解这张图的关键直觉是：只有 Ready 态的任务才参与调度竞争；一个任务只要在"等什么东西"，它就应当处于 Blocked 而不是 Ready，这样它就完全不消耗 CPU。

```
        调度器选中(最高优先级就绪任务)
   Ready ───────────────────────────▶ Running
     ▲                                   │
     │ 事件到达/延时到期                   │ 被更高优先级抢占 / 时间片用完
     │ (Blocked→Ready)                    ▼
     │                                  Ready
     └──────── Blocked ◀──── 主动等待(vTaskDelay/取信号量/读空队列)
                                 (Running→Blocked)
```

用忙等（busy-wait，如 `while(!flag);` 或空转的 `for` 延时）来"等待"。忙等让任务始终停留在 Running/Ready 态、一直占着 CPU 空转，既浪费能量又阻塞了同优先级甚至更低优先级任务。正确做法是调用会让任务进入 Blocked 的阻塞式 API（延时、等信号量、等队列），把 CPU 真正让出去。这是从裸机思维转向 RTOS 思维的第一道坎。

还要区分"阻塞延时"和"空闲任务"（idle task）。当所有用户任务都 Blocked 时，没有任何任务就绪，内核会运行一个优先级最低、由内核自动创建的空闲任务，它常被用来做低功耗休眠或回收已删除任务的内存。

## 10.2 抢占式优先级调度与上下文切换

### 10.2.1 固定优先级抢占式调度

绝大多数嵌入式 RTOS 的默认调度策略是固定优先级抢占式（fixed-priority preemptive scheduling）。规则一句话讲清：任何时刻，CPU 一定运行当前所有就绪任务里优先级最高的那一个；一旦有更高优先级的任务变为就绪（比如它等待的中断来了），调度器立刻抢占正在运行的低优先级任务、切到高优先级任务。这保证了高优先级（通常也是时间最紧）的任务能尽快拿到 CPU。

"抢占"（preemption）意味着一个任务的运行可能在任意指令边界被打断，而不需要它主动配合。这与协作式调度（cooperative，任务必须自己调用让出函数才会被切走）相对。抢占式的好处是响应快、不依赖任务"自觉"；代价是任何被多个任务共享的数据都可能在读写中途被打断，从而需要同步保护（见 10.4、10.5）。

同一优先级的多个就绪任务如何处理？常见做法是时间片轮转（round-robin / time-slicing）：它们轮流各跑一个时基节拍（tick）。FreeRTOS 中这由编译期配置项 `configUSE_TIME_SLICING` 控制（⚙演进快·锚版本；默认开启，但版本/移植可改）。若关闭时间片，同优先级任务只会在主动阻塞时才让位。

### 10.2.2 上下文切换（context switch）

上下文切换是"把 CPU 从任务 A 切到任务 B"的动作。内核要做的是：把 A 当前的执行现场——通用寄存器 R0–R12、栈指针、程序计数器 PC、状态寄存器等——完整保存到 A 的栈（或任务控制块）里，然后从 B 之前保存的现场里把这些寄存器恢复出来，最后跳到 B 上次被切走的位置继续执行。B 完全感觉不到自己曾被打断。

在 Cortex-M 上，这件事和硬件异常机制深度配合（⚙演进快·锚 ARMv7-M/ARMv8-M + FreeRTOS 移植层）。异常进入时，硬件会自动把一部分寄存器（xPSR、PC、LR、R12、R3–R0，即"栈帧"）压栈；RTOS 的上下文切换通常挂在 PendSV 异常里完成剩余寄存器（R4–R11）的保存/恢复，并切换栈指针。把上下文切换放在最低优先级的 PendSV 里，是为了让它总是在所有中断处理完之后才发生，避免在中断嵌套中途切换任务。程序员一般不需要手写这段汇编，它由 RTOS 移植层（port）提供，但理解"寄存器现场被搬进/搬出栈"这个本质，有助于明白为什么每个任务都要独立栈、以及栈开小了会踩到别的任务导致诡异崩溃。

上下文切换不是免费的：保存/恢复寄存器要花时间和指令。切换本身的开销（加上进/出内核的开销）构成了调度的固定成本。它的绝对周期数高度依赖核心、主频和移植实现，属⚙演进快·锚平台的量，本文不给具体数字（避免编造，标「待核」——需在锚平台实测）。设计上的含义是：优先级层数太多、任务切换过于频繁，会让这些开销累积起来吃掉 CPU 时间，因此实时系统里任务粒度和优先级布局需要权衡。

### 10.2.3 调度时机：何时触发一次调度

调度器不是持续运转的后台程序，而是在特定"调度点"被触发。主要有两类触发源：一是时基节拍中断（tick，通常来自 SysTick 定时器，见大主题6），每个 tick 内核检查是否有更高优先级任务因延时到期而就绪、以及是否要做时间片轮转；二是任务自身或中断服务程序（ISR）调用了会改变就绪集合的内核 API（释放信号量、往队列写数据、任务延时结束等）。

从 ISR 里释放信号量/发队列，可能让一个比"被中断的任务"优先级更高的任务变就绪。这时需要在 ISR 退出时请求一次上下文切换（FreeRTOS 里通过 `...FromISR` 系列 API 返回的 `xHigherPriorityTaskWoken` 标志 + `portYIELD_FROM_ISR`）。忘了这一步，高优先级任务不会立刻运行、要等到下一个 tick 才被调度，白白增加延迟。这属⚙演进快·锚 FreeRTOS API 的用法细节，核实 2026-08-01。

## 10.3 实时调度理论：RMS / EDF 与可调度性判定

### 10.3.1 周期任务模型与利用率

要谈"能不能都按时完成"，先要有一个数学模型。经典的周期任务模型把每个任务 i 抽象为一对参数：执行时间 Cᵢ（每次运行需要的最坏 CPU 时间）与周期 Tᵢ（每隔 Tᵢ 释放一个新的作业，且通常假设截止期 Dᵢ = Tᵢ，即下一个周期到来前必须完成本次）。单个任务对 CPU 的占用率是 Cᵢ/Tᵢ，系统总利用率 U 是所有任务之和：

U = Σ (Cᵢ / Tᵢ)

利用率是可调度性分析的核心量。一个显然的必要条件是 U ≤ 1：单核 CPU 一共就 100% 的算力，需求超过 100% 无论如何都排不下。但 U ≤ 1 并不充分——排得下"总量"不等于每个都能"按时"，还取决于用什么调度策略、以及各周期如何交错。下面两个经典结论回答了"充分"的问题。

### 10.3.2 RMS（速率单调调度）与 Liu & Layland 利用率界

速率单调调度（Rate-Monotonic Scheduling, RMS）是一种固定优先级赋值规则：周期越短（速率越高）的任务，优先级越高。Liu & Layland 1973 年证明：在"周期任务、Dᵢ=Tᵢ、相互独立、可抢占、切换开销忽略"这组假设下，RMS 是最优的固定优先级策略（若 RMS 都排不下，别的固定优先级赋值也排不下）。

他们还给出一个只看总利用率就能下结论的充分（非必要）判据：n 个任务在 RMS 下一定可调度，只要

U ≤ n · (2^(1/n) − 1)

这个界随任务数 n 增大而单调下降，n→∞ 时趋于 ln 2 ≈ 0.6931。也就是说，任务数很多时，只要总利用率不超过约 69%，RMS 保证全部按时完成。下表是本机 Python 实算的界值（sympy/numpy 基线，核实 2026-08-01，与 Liu & Layland 原文一致）：

```
n=1    界 = 1.0000
n=2    界 = 0.8284
n=3    界 = 0.7798
n=4    界 = 0.7568
n=5    界 = 0.7435
n=10   界 = 0.7177
n→∞    界 = ln2 ≈ 0.6931
```

这个利用率界是充分条件，不是必要条件。U 超过这个界并不意味着排不下——很多实际任务集在 U 高达 0.9 甚至接近 1 时用 RMS 依然全部可调度（尤其当周期成谐波关系、即互为整数倍时，界可放宽到 1.0）。所以利用率界只能用来"快速判 YES"：过了界就一定行；没过界要用更精确的方法（见 10.3.4 响应时间分析）才能定论，不能因为没过界就武断判定不可调度。

### 10.3.3 EDF（最早截止期优先）与利用率界

最早截止期优先（Earliest Deadline First, EDF）是一种动态优先级策略：任何时刻，谁的绝对截止期最近，谁的优先级就最高——优先级不再固定绑在任务上，而是随着各作业截止期的临近不断变化。Liu & Layland 同样证明：在单核、可抢占、Dᵢ=Tᵢ 的模型下，EDF 是最优的（含动态优先级在内的所有策略中）动态调度，且它的可调度充要条件极其简洁：

U ≤ 1

也就是说，EDF 能把单核的算力用到理论极限：只要总需求不超过 100%，EDF 就能让所有周期任务按时完成。这是 EDF 相对 RMS 的最大理论优势——RMS 在最坏情况下要牺牲到约 69% 才能保证，而 EDF 能吃满 100%。

既然 EDF 更优，为什么工业界的小型 RTOS 默认几乎都是固定优先级（RMS 家族）而非 EDF？直觉上的权衡：EDF 需要在运行时持续跟踪和比较每个作业的绝对截止期、动态调整优先级，实现更复杂、开销更大；固定优先级只需一次性赋好优先级、调度器逻辑极简、行为更容易预测和调试。此外 EDF 在过载（U>1）时行为较差——会发生"多米诺式"连环误期，而固定优先级过载时是低优先级任务先牺牲、高优先级仍受保护，故障模式更可控。因此多数 MCU 级 RTOS（FreeRTOS、Zephyr 默认）走固定优先级抢占；EDF 更多见于研究与部分对利用率极致要求的系统。

### 10.3.4 精确判据：响应时间分析（RTA）

利用率界胜在快，但太保守。对固定优先级系统，更精确（充要，在标准假设下）的方法是响应时间分析（Response-Time Analysis, RTA）。它逐个计算每个任务的最坏响应时间 Rᵢ（从被释放到完成的最长时间），再检查是否 Rᵢ ≤ Dᵢ。任务 i 的响应时间满足下面这个递推（不动点）方程，其中 hp(i) 表示优先级高于 i 的任务集合：

Rᵢ = Cᵢ + Σ_{j∈hp(i)} ⌈Rᵢ / Tⱼ⌉ · Cⱼ

含义是：任务 i 的响应时间 = 它自己的执行时间，加上在它运行期间所有更高优先级任务抢占它、插队执行所耗的时间（⌈Rᵢ/Tⱼ⌉ 是高优先级任务 j 在这段时间里最多释放的次数）。方程两边都有 Rᵢ，用迭代求解：从 Rᵢ⁽⁰⁾ = Cᵢ 出发反复代入，直到收敛（不再变化，说明找到最坏响应时间）或超过 Dᵢ（判不可调度）。

RTA 比利用率界强在：它能判定那些"没过利用率界但其实可调度"的任务集，也能自然扩展到 Dᵢ<Tᵢ、含阻塞时间（把优先级反转造成的最坏阻塞 Bᵢ 加进等式，见 10.5）等更现实的场景。初学者理解到"利用率界=快速粗判、RTA=精确细判"这一层即可，无需手推收敛证明。

## 10.4 同步原语：信号量 / 互斥量 / 消息队列

### 10.4.1 为什么需要同步原语

一旦有了抢占式多任务，任务之间就会争抢共享资源（同一块全局数据、同一个外设、同一个缓冲区），并且需要互相协调"等对方做完某事"。因为抢占可能在任意时刻发生，两个任务对同一变量的读-改-写若交错进行，结果就可能错乱——这就是竞态条件（race condition）。同步原语是 RTOS 提供的、由内核保证原子性的协调工具，用来实现互斥访问和事件通知。核心三类是信号量、互斥量、消息队列。

### 10.4.2 信号量（semaphore）：计数与信令

信号量本质是一个带原子"取（wait/take/P）"和"给（signal/give/V）"操作的计数器。二值信号量（binary，计数 0/1）常用于事件信令：任务 A 阻塞在"取信号量"上等待，中断或任务 B 在事件发生时"给信号量"，A 随即被唤醒。计数信号量（counting，计数可到 N）用于管理"有 N 个可用单元"的资源池，或统计发生了多少次事件。

信号量的关键特征是它没有"所有者"概念——给信号量的和取信号量的可以是不同主体，这正是它适合做 ISR 到任务的信令的原因（中断里"给"、任务里"取"）。也正因为无所有者，信号量不适合用来做互斥保护共享数据（会引入优先级反转且无法用继承协议缓解，见 10.5）——那是互斥量的活。

### 10.4.3 互斥量（mutex）：带所有权的互斥

互斥量（mutex，mutual exclusion）专门用于保护临界区/共享资源：任务进入临界区前"上锁（lock/take）"，出来时"解锁（unlock/give）"，同一时刻至多一个任务持有锁。它和二值信号量看起来像，但有两个本质区别：一是所有权——只有上锁的那个任务才能解锁（不能张三锁、李四解）；二是多数 RTOS 的互斥量内建优先级继承机制来对抗优先级反转（见 10.5），而信号量没有。

因此选择规则是：保护共享数据用 mutex，任务/中断间事件信令用信号量。一个高频错误是用二值信号量当锁使——功能上"能锁"，但一旦发生优先级反转就无优先级继承来救，可能造成高优先级任务长时间被拖住。另一个错误是在中断里"上锁 mutex"：mutex 因涉及所有权和继承通常不允许在 ISR 中获取（FreeRTOS 里从 ISR 拿 mutex 是禁止的，⚙演进快·锚 API 规则），ISR 与任务间同步应走信号量或队列。

### 10.4.4 消息队列（message queue）：数据传递 + 同步一体

消息队列是一个由内核管理的、线程安全的 FIFO 缓冲区：发送方把一条消息（一小块数据，按值拷贝或拷贝指针）放入队尾，接收方从队首取出；队满时发送方可阻塞等待空位，队空时接收方可阻塞等待数据。它把"数据传递"和"同步/流控"合二为一，是任务间通信（尤其生产者-消费者模式）最常用、也最推荐的机制。

队列相对"共享全局变量 + 锁"的优势在于：它天然避免了裸共享数据的竞态（数据被拷贝进队列，收发双方不直接碰同一块内存），也内建了阻塞等待，代码更简洁、更不容易出错。这体现了 RTOS 里一条常见的设计箴言——用通信代替共享（communicate rather than share），尽量让任务通过队列传消息而不是共享内存加锁。初学者要注意队列传的是拷贝：传大结构体会消耗时间与 RAM，此时常改传指针（但要保证指向的内存在被消费前有效、且所有权清晰），这本身又带来生命周期管理问题，需权衡。

下面是 FreeRTOS 队列 + 二值信号量的最小示意（⚙演进快·锚 kernel v11.x，核实 2026-08-01）：

```c
QueueHandle_t q = xQueueCreate(8, sizeof(sample_t));  /* 深8、每项 sizeof(sample_t) */
SemaphoreHandle_t m = xSemaphoreCreateMutex();        /* 互斥量，内建优先级继承 */

/* 生产者(可在任务里) */   xQueueSend(q, &sample, portMAX_DELAY);
/* 消费者(任务里) */       xQueueReceive(q, &out, portMAX_DELAY);
/* 保护共享资源 */         xSemaphoreTake(m, portMAX_DELAY); /*...临界区...*/ xSemaphoreGive(m);
/* ISR 向任务信令 */       xSemaphoreGiveFromISR(binSem, &woken); portYIELD_FROM_ISR(woken);
```

## 10.5 优先级反转与优先级继承 / 天花板协议

### 10.5.1 优先级反转（priority inversion）

优先级反转是抢占式优先级系统里一个反直觉但危险的现象：一个高优先级任务被一个低优先级任务"卡住"，而系统整体表现得好像优先级被颠倒了。发生场景是：低优先级任务 L 先拿到了某个共享资源的锁并进入临界区；此时高优先级任务 H 就绪、抢占了 L，但 H 也需要同一把锁——锁在 L 手里，H 只能阻塞等 L 释放。到此为止是正常的、有界的等待。真正的问题（无界优先级反转）出现在：当 L 还没解锁时，一个中优先级任务 M（不需要那把锁）就绪了，M 优先级高于 L，于是抢占 L 运行。结果 L 迟迟得不到 CPU 去解锁，H 就被 M（以及一串中优先级任务）无限期地间接拖住——H 的等待时间不再取决于临界区长短，而取决于那些不相干的中优先级任务要跑多久，可能任意长。

```
优先级  H ┤        H就绪,要锁 ▓阻塞等锁────────────────▶ 终于拿到锁运行
        M ┤                    ░░░M就绪抢占L,跑很久░░░░
        L ┤ 拿到锁█临界区… (被H抢,又被M抢,迟迟解不了锁) █解锁
          └────────────────────────────────────────────▶ 时间
   H 的实际等待 ≈ M 的运行时间(与临界区无关) → 无界反转
```

这不是纸上谈兵：NASA 的火星探路者（Mars Pathfinder，1997）着陆器就因优先级反转导致看门狗反复复位系统，是这一现象最著名的真实案例（工程史广泛记载，作为教学经典）。

### 10.5.2 优先级继承协议（priority inheritance）

优先级继承是最常用的对策，多数 RTOS 的 mutex 内建它。规则一句话：当高优先级任务 H 因为某把锁阻塞在低优先级任务 L 上时，临时把 L 的优先级提升到 H 的水平（让 L "继承" H 的优先级），直到 L 释放该锁再恢复原优先级。这样一来，L 在持锁期间就不会被中优先级任务 M 抢占（M 现在没它高了），L 能尽快跑完临界区、解锁，H 随即拿到锁。无界反转被消除——H 的最坏阻塞时间被限制在"L 的那段临界区长度"这一有界量内。

优先级继承缓解但不消除阻塞：H 仍要等 L 把临界区跑完（这段有界阻塞 B 应计入 10.3.4 的响应时间分析）。它也有代价与陷阱：会造成优先级的动态抖动，且在多把锁嵌套时可能出现链式继承、甚至处理不当引入死锁风险。初学者记住核心即可：mutex 通常带优先级继承、信号量不带，这是"保护共享数据要用 mutex 而非二值信号量"的深层原因。

### 10.5.3 优先级天花板协议（priority ceiling）

优先级天花板协议（Priority Ceiling Protocol, PCP；及其简化版 Immediate Ceiling Priority Protocol, ICPP / 也叫 highest locker）是更强的一类协议。核心思路：给每一个共享资源（锁）预先设定一个"天花板"优先级，等于所有可能用到它的任务中的最高优先级。在 ICPP 里，任务一旦拿到某锁，其优先级立即被抬到该锁的天花板；这样它持锁期间不会被任何将来也可能要这把锁的任务抢占。

天花板协议相对纯继承的两个额外好处：一是能防止死锁（在标准假设下 PCP 保证无死锁）；二是把每个任务的最坏阻塞时间进一步压缩到"至多被一个更低优先级任务的一个临界区阻塞一次"，界更紧、更利于 WCET/响应时间分析。代价是需要预先静态分析出每把锁的天花板、实现更复杂，且它比继承"更早"地提升优先级（拿到锁就提，而非等到真被高优先级任务阻塞才提）。工程上，小型 RTOS 多默认提供优先级继承（够用且简单）；天花板协议在对时序保证要求更高、可静态分析的硬实时系统里更常见。三者的对比一句话收束：不加保护会有无界反转；继承把反转限成有界阻塞；天花板在此基础上再防死锁、把界压得更紧。

## 10.6 WCET（最坏执行时间）与时序分析

### 10.6.1 什么是 WCET，为何它是实时分析的地基

最坏执行时间（Worst-Case Execution Time, WCET）是一段代码（一个任务或作业）在最坏情况下、不被打断地跑完所需要的最长处理器时间。它就是前面调度理论里反复出现的那个 Cᵢ。所有可调度性判据——利用率界、响应时间分析——都把 Cᵢ 当作已知输入；如果 Cᵢ 本身估不准，再漂亮的判据也是空中楼阁。所以 WCET 分析是把"实时保证"落地的地基：只有拿到可信的最坏执行时间上界，才谈得上证明"一定按时完成"。

要强调"最坏"和"上界"：实时系统要的不是平均执行时间，而是一个安全的上界——真实执行永远不超过它。低估 WCET 会导致分析判"可调度"但实际误期（危险）；高估会浪费算力、逼你用更贵的 CPU（保守但安全）。理想的 WCET 估计应当既是上界又尽量紧。

### 10.6.2 为什么 WCET 很难：现代硬件的不确定性

初学者常以为"数一数指令周期不就行了"。在最简单的、无缓存无流水线的老式 MCU 上确实近似如此；但在稍复杂的处理器上，同一段代码的执行时间会因运行时状态而大幅波动，来源包括：输入相关的分支与循环次数（不同数据走不同路径）、缓存命中/缺失（首次访问慢、命中快，Cort-M 常无 cache 反而更可预测，⚙锚平台）、流水线冒险与分支预测、以及最麻烦的中断/抢占带来的干扰。这些因素让"精确的最坏值"往往无法简单测出——你没法保证测试恰好覆盖了那条最坏路径。

因此 WCET 分析有两条主要路线，各有取舍：一是静态分析法——不实际运行，而是分析程序控制流图 + 处理器时序模型，对所有路径求上界（安全、是真上界，但依赖精确硬件模型、可能过保守，工具复杂）；二是基于测量法——在真实硬件上大量运行取最大观测值（简单、贴近实际，但无法保证覆盖到真正最坏路径，得到的是观测最大值而非可证上界，通常需加安全裕量）。工业界常混合使用（measurement-based + 静态边界 + 裕量）。

### 10.6.3 时序分析在系统层面的落地

有了各任务的 Cᵢ（WCET 上界），时序分析就是把它们喂进 10.3 的调度判据，回答系统级问题：所有任务在最坏情况下是否都能满足截止期？这里还要把 10.5 的最坏阻塞时间 Bᵢ（因共享资源/优先级反转造成，用继承或天花板协议给出有界值）以及中断处理的干扰计入，得到更贴近现实的响应时间：

Rᵢ = Cᵢ + Bᵢ + Σ_{j∈hp(i)} ⌈Rᵢ / Tⱼ⌉ · Cⱼ

Cᵢ 来自 WCET 分析（10.6），Bᵢ 来自同步与优先级协议（10.4/10.5），求和项是抢占干扰（来自 10.2 的抢占调度），整体判据来自实时调度理论（10.3）。这就是"可预测的实时系统"如何被论证出来的完整逻辑链。

桌面 Linux（本基线环境）不是硬实时系统——它有多级缓存、乱序执行、通用调度器和不可控的后台负载，任何在此测得的"执行时间"都只能作趋势/相对比较的近似，不能当作嵌入式硬实时 WCET 的可证上界。真正的 WCET 取值必须在锚平台（如 Cortex-M4 / TM4C123）上用专用工具或严格测量法获得，本报告不给具体周期数（标「待核」，避免编造）。理解到"WCET 是分析地基、难点在硬件不确定性、桌面测量只能近似"这一层，对初学者已足够。
