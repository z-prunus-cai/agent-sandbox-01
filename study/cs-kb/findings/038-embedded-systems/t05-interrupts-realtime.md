中断（interrupt）是嵌入式系统把「外部世界发生的事」和「CPU 正在跑的代码」缝合起来的核心机制。没有中断，处理器只能靠反复读寄存器去问「按键按了吗、数据到了吗」，既浪费能量又无法保证及时响应。本报告以 ARM Cortex-M（ARMv7-M 架构）与参考板 TI EK-TM4C123GXL（Cortex-M4）为锚，讲清中断从「被触发」到「被处理」再到「返回」的完整链路，以及由此引出的优先级、嵌套、尾链、延迟等实时性概念，最后对比轮询 / 中断 / DMA 三种 I/O 组织方式。

凡涉及具体位宽、优先级位数、周期数的数值，均以锚平台为准并标注来源；换 SoC 或换 Cortex-M 型号可能不同，正文会在相应处提示。

## 5.1 中断向量表与 NVIC 使能 / 挂起 / 清除

### 5.1.1 中断、异常与外设中断的关系

在 Cortex-M 的术语里，「异常（exception）」是上位概念，指任何打断正常指令流、跳去执行专门处理程序的事件；「中断（interrupt，也叫 IRQ）」是异常的一个子类，特指由外设（定时器、GPIO、UART 等）产生的那部分异常。复位、NMI、HardFault、SysTick、SVCall、PendSV 等属于「系统异常」，编号为负或很小的固定编号；外设中断则从异常编号 16 开始向上排列（IRQ0、IRQ1……）。

对初学者最容易混淆的一点是：所有这些事件——不管是硬件故障、系统定时器，还是某个引脚电平变化——都走同一套「查向量表、保存现场、跳转、返回」的机制。把它们统一理解成「异常」，就抓住了主干；「中断」只是其中来自外设、可被单独使能 / 屏蔽 / 排优先级的那一类。之所以要区分，是因为系统异常由内核直接管理，而外设中断由一个叫 NVIC 的专用单元管理，二者的配置寄存器不同。

### 5.1.2 向量表布局与 VTOR

向量表（vector table）是一张放在内存里的地址表：表项 0 是复位后主栈指针（MSP）的初值，表项 1 是复位处理程序入口地址，之后每个表项存放对应异常 / 中断处理程序（handler）的入口地址。每个表项占 4 字节。当某个异常被内核接受时，硬件用异常编号去这张表里取出对应地址，直接跳过去执行——程序员不需要写任何「判断是谁触发」的分发代码，分发是硬件完成的。

向量表的布局（前几项固定）：

```
偏移      表项              内容
0x00      初始 MSP          复位后主栈指针初值
0x04      Reset             复位处理程序入口
0x08      NMI               不可屏蔽中断
0x0C      HardFault         硬件故障
0x10      MemManage         存储器管理故障
0x14      BusFault          总线故障
0x18      UsageFault        用法故障
0x1C-0x28 (保留)
0x2C      SVCall            SVC 指令触发
0x30      DebugMonitor
0x34      (保留)
0x38      PendSV            可挂起系统调用（RTOS 上下文切换常用）
0x3C      SysTick           系统节拍定时器
0x40      IRQ0              第一个外设中断
0x44      IRQ1              ...
```

复位时向量表默认位于地址 0x00000000（在 TM4C123 上即 Flash 起始）。ARMv7-M 提供了向量表偏移寄存器 VTOR（Vector Table Offset Register，地址 0xE000ED08），可以把向量表重定位到别处，例如搬到 SRAM 以便运行时动态改写某个中断的处理程序，或在有 bootloader 的系统里让应用程序使用自己的一张表。初学者常见的错误是把向量表放在了不满足对齐要求的地址：向量表基址必须按表的大小向上对齐（至少 128 字节，表越大对齐要求越严），地址没对齐会导致取向量失败。Cortex-M0（ARMv6-M）没有 VTOR（M0+ 才可选带），所以「能否重定位向量表」是分档特性，不能默认所有 Cortex-M 都支持。

### 5.1.3 NVIC 与外设中断的使能 / 禁用

NVIC（Nested Vectored Interrupt Controller，嵌套向量中断控制器）是 Cortex-M 内核里专门管理外设中断的单元，「Nested」表示支持嵌套（高优先级可打断低优先级），「Vectored」表示由硬件查向量表直接跳到处理程序。它通过一组内存映射寄存器控制每个外设中断的开关、挂起状态和优先级。

要让一个外设中断真正能打断 CPU，通常需要三个层次都打开：外设自身的中断使能位（例如 GPIO 模块里让某引脚的边沿事件产生中断）、NVIC 里对应 IRQ 的使能位、以及全局中断没有被屏蔽（PRIMASK 为 0）。任何一层没开，中断都到不了处理程序。这是新手调试中断「不进 ISR」时最该逐层排查的清单。

NVIC 用「写 1 生效」的分离寄存器来管理使能，而不是让你读改写同一个寄存器：

```
ISER (Interrupt Set-Enable Register)  写 1 使能对应 IRQ，写 0 无效
ICER (Interrupt Clear-Enable Register) 写 1 禁用对应 IRQ，写 0 无效
```

每个 IRQ 占 1 位，每个寄存器管 32 个 IRQ（ISER0 管 IRQ0-31，ISER1 管 IRQ32-63……）。设计成「set/clear 分离」是为了避免读-改-写的竞态：你想使能 IRQ5，直接对 ISER0 写 `(1<<5)` 即可，不会误动其它位，也不需要先读回当前值。这与初学者习惯的「读出来、或上一位、写回去」不同，是嵌入式寄存器设计里很常见的一种模式。

### 5.1.4 挂起（pending）、活动（active）与清除

一个外设中断在被内核实际处理之前，会先进入「挂起（pending）」状态：硬件事件发生 → NVIC 把该 IRQ 标记为 pending → 等到优先级允许、CPU 可以响应时，才真正跳进处理程序，此时状态从 pending 变为 active。理解「触发」与「被处理」是两个分离的时刻，是理解中断时序的关键：事件可能早就来了，但如果当前正在跑更高优先级的处理程序，它只能挂起排队等待。

NVIC 同样用 set/clear 分离寄存器暴露挂起状态，还有只读的活动状态：

```
ISPR (Interrupt Set-Pending)    写 1 手动置挂起（软件触发中断）
ICPR (Interrupt Clear-Pending)  写 1 清除挂起
IABR (Interrupt Active Bit)     只读，指示该 IRQ 是否正在被处理
```

有两个高频易错点。其一，很多外设自己还有一套「中断标志位」，它和 NVIC 的 pending 位是两回事：进入 ISR 后必须在外设寄存器里清掉外设级标志，否则一退出 ISR，外设看到标志还在，立刻又把中断拉起来，程序表现为「反复进同一个 ISR、卡死」。其二，清外设标志的写操作要在 ISR 早期完成并留出时间生效（写缓冲可能延迟），否则同样可能被重复触发；保守做法是清标志后读回一次，确保写已落地再返回。ISPR 允许软件写 1 来「假装」某中断发生了，这在测试 ISR 或用软件触发方式实现延迟处理时很有用。

### 5.1.5 全局中断屏蔽：PRIMASK / FAULTMASK / BASEPRI

除了在 NVIC 里逐个开关中断，Cortex-M 内核还提供三个特殊寄存器用于「批量」屏蔽中断，主要服务于临界区保护：

```
PRIMASK    1 位；置 1 时屏蔽所有可屏蔽中断/异常（NMI、HardFault 除外）
FAULTMASK  1 位；比 PRIMASK 更强，连 HardFault 也屏蔽（NMI 除外）
BASEPRI    8 位（有效位数=优先级位数）；屏蔽"优先级数值≥BASEPRI"的中断，
           更高优先级(数值更小)的仍可打断；写 0 表示不屏蔽
```

PRIMASK 是「一刀切」：用汇编指令 `CPSID i`（关）和 `CPSIE i`（开）快速屏蔽 / 恢复全部中断，适合极短的临界区。BASEPRI 是 ARMv7-M（Cortex-M3/M4/M7）才有的更精细工具：它设一个优先级阈值，只挡住不够高的中断，让最紧急的中断仍能穿透——这对「既要保护共享数据、又不能让关键实时中断被拖延」的场景很重要，也是许多 RTOS 实现临界区的首选。

Cortex-M0/M0+（ARMv6-M）只有 PRIMASK，没有 BASEPRI 和 FAULTMASK。因此「用 BASEPRI 做分级临界区」的写法不能移植到 M0。另一个易错点是屏蔽范围太大、时间太长：长时间关全局中断会直接抬高所有中断的延迟，破坏实时性，临界区应尽量短。

## 5.2 ISR 编写、自动上下文保存与返回（异常入栈帧）

### 5.2.1 异常入栈帧：硬件自动保存的现场

当 Cortex-M 接受一个异常时，硬件会在跳进处理程序之前，自动把一组寄存器压入栈（stacking），构成「异常栈帧（exception stack frame）」。这组寄存器是（按 ARMv7-M 规定的基础帧）：

```
高地址
  xPSR      程序状态寄存器
  PC        返回地址（被打断处的下一条指令）
  LR        R14，链接寄存器
  R12
  R3
  R2
  R1
  R0
低地址  ← 入栈后 SP 指向这里
```

共 8 个字（32 字节）。为什么恰好是这 8 个？因为 ARM 的调用约定（AAPCS）规定 R0-R3、R12 是「调用者保存（caller-saved）」寄存器，一个普通 C 函数在被调用时本就可以自由改写它们；加上 LR、PC、xPSR 这三个描述「返回到哪、处理器处于什么状态」的寄存器，就构成了让被打断的代码能原样恢复所需的最小集合。硬件替你保存了这一组，正是为了让 ISR 可以写成一个普通的 C 函数（见 5.2.3）。

### 5.2.2 EXC_RETURN 与异常返回

进入异常处理程序时，硬件不会把真正的返回地址放进 LR，而是放一个特殊的魔数值 EXC_RETURN（形如 0xFFFFFFFx）。这个值本身不是地址，而是一组标志位，编码了三件事：返回后用主栈指针 MSP 还是进程栈指针 PSP、返回到 Thumb 状态、以及是否需要恢复 FPU 上下文。当处理程序执行 `BX LR`（或任何把 EXC_RETURN 载入 PC 的返回指令）时，内核识别出这个魔数，就触发「异常返回」流程：从栈里弹出 5.2.1 那 8 个字，恢复现场，跳回被打断的位置。

对初学者，关键结论是：ISR 里那条看似普通的返回，实际上被硬件赋予了特殊语义——它不是跳到某个地址，而是启动出栈恢复。因此 ISR 结尾用标准 C 的 `return` 即可，编译器会生成正确的返回指令，你不需要手写弹栈。常见误区是试图在 ISR 里手动修改 LR 或手动 push/pop 通用寄存器去「保存现场」，这既多余又可能破坏 EXC_RETURN 机制。

### 5.2.3 把 ISR 写成普通 C 函数

正因为硬件自动保存了 caller-saved 寄存器并用 EXC_RETURN 管理返回，Cortex-M 上的中断服务程序（ISR）可以直接写成一个无参数、无返回值的普通 C 函数，函数名与向量表中该中断的表项对应（由 startup 文件或链接脚本关联）：

```c
void GPIOF_Handler(void) {         // 名字须与向量表项匹配
    if (GPIO_PORTF_MIS_R & 0x10) { // 判断是哪个引脚事件（外设级）
        GPIO_PORTF_ICR_R = 0x10;   // 清外设中断标志（关键，见 5.1.4）
        count++;                    // 与主程序共享的变量
    }
}
```

这里有两个初学者必须建立的认识。第一，编译器会把这个函数当普通函数编译，函数序言里若用到 R4-R11 这类「被调用者保存（callee-saved）」寄存器，编译器会自己 push/pop 它们——因为硬件只帮你存了 R0-R3/R12，R4-R11 得由函数自己负责，编译器已按 AAPCS 处理妥当，你无需干预。第二，ISR 与主程序之间共享的变量必须加 `volatile`（见 5.2.5），否则优化器可能看不到「值会被中断异步改动」而缓存旧值。

### 5.2.4 FPU 上下文与惰性入栈（lazy stacking）

在带浮点单元（FPU）的 Cortex-M4F / M7 上，浮点寄存器 S0-S15 与 FPSCR 也属于 caller-saved，理论上进异常时也应保存，这会让栈帧从 8 个字扩大到 26 个字，显著增加入栈时间。为避免「每次中断都付浮点保存代价、哪怕 ISR 根本不用浮点」，ARM 设计了惰性入栈（lazy stacking）：进异常时硬件只为浮点上下文预留栈空间但先不真正写入，只有当 ISR 里第一次执行浮点指令时才补上保存。这样纯整数的 ISR 就省下了浮点保存开销。

对初学者，这里要记住的是：中断延迟的数值会因 FPU 上下文而变（见 5.3.6），惰性入栈是默认打开的优化。易错点是在中断优先级 / 栈空间估算时忘了「用浮点的 ISR 栈帧要按 26 字算」，可能导致栈溢出。惰性入栈由 FPCCR 寄存器控制，可关闭。

### 5.2.5 ISR 编写规范：短、清标志、volatile、与主程序通信

写 ISR 有一套广泛认可的纪律，核心是「快进快出」。第一，ISR 要尽量短：它运行在打断主流程、可能还阻塞同级 / 低级中断的上下文里，耗时越长，系统实时性越差。典型做法是 ISR 里只做「必须立刻做」的事（读一个数据、置一个标志、清外设标志），把耗时处理丢回主循环或交给 RTOS 任务。

第二，进 ISR 后要及时清除外设级中断标志（5.1.4），否则会反复触发。第三，ISR 与主程序共享的变量必须声明为 `volatile`：

```c
volatile uint32_t g_flag;   // 被 ISR 异步改写，主循环轮询它
```

`volatile` 告诉编译器「这个变量的值可能在任何时刻被本函数控制流之外的东西改变」，从而禁止把它缓存进寄存器、禁止把对它的读写优化掉。没有 `volatile`，一个 `while(g_flag==0);` 的等待循环可能被优化成死循环（编译器认为 g_flag 不会变）。第四，ISR 里不要做可能阻塞的操作（等待另一个中断、忙等长时间外设），也应避免在裸机 ISR 里调用不可重入的库函数。第五，多字节的共享数据在 32 位机上跨 ISR 访问要注意原子性：单个对齐的 32 位读写是原子的，但「读-改-写」或多字段更新不是，需要临界区（PRIMASK/BASEPRI）保护。这些规范在 ARM 与 Valvano 的资料中反复强调，是嵌入式 bug 的高发区。

## 5.3 优先级 / 抢占、嵌套、尾链、中断延迟

### 5.3.1 优先级数值：越小越高

NVIC 给每个中断分配一个优先级，用「优先级数值」表示，规则是数值越小、优先级越高。0 是最高优先级。这与直觉相反，是初学者的第一个坑：写 0 不是「关掉优先级」，而是「最紧急」。系统异常里复位、NMI、HardFault 有固定的、比任何可配置中断都高的优先级（分别约定为 -3、-2、-1），不可更改。

每个中断的优先级存放在 NVIC 的优先级寄存器（IPR，每个中断占 8 位字段）里。但一个关键事实是：架构规定这 8 位中「实现可以只用高位若干位」，具体用几位由芯片厂商决定。在锚平台 TM4C123（Cortex-M4）上只实现了高 3 位，因此有效优先级只有 8 级（0~7，0 最高），低 5 位读作 0、写无效。这解释了为什么设优先级时要往高位写：

```
IPR 字段（8 位）  bit7 bit6 bit5 | bit4 ... bit0
TM4C123 实际使用   [ 用这 3 位 ]  [ 未实现，恒 0 ]
所以优先级 3 应写成  3<<5 = 0x60，而不是 0x03
```

不同 SoC 实现的位数不同（常见 2~4 位，即 4~16 级），这是移植时必须重新核对的平台相关量。

### 5.3.2 抢占优先级 vs 子优先级（优先级分组）

Cortex-M 把每个中断的优先级字段进一步拆成两部分：高位是「抢占优先级（group / preemption priority）」，低位是「子优先级（subpriority）」。抢占优先级决定「谁能打断谁」——只有抢占优先级更高的中断才能抢占正在运行的中断；子优先级只在「两个中断同时挂起、抢占级又相同」时用来决定先服务哪个，但不能造成抢占（不能中途打断）。

这条分界线由 AIRCR（Application Interrupt and Reset Control Register）里的 PRIGROUP 字段配置：它规定优先级字段里「从第几位开始算子优先级」。举例，若把全部有效位都划给抢占优先级、子优先级 0 位，则任意两个不同优先级的中断都能互相抢占；反之把较多位划给子优先级，则很多中断彼此不抢占、只排先后。初学者容易把「优先级数值小」直接等同于「一定能抢占」，其实要先看抢占优先级是否更高——同一抢占组内即使子优先级不同也不会抢占。许多 RTOS（如 FreeRTOS）建议把 PRIGROUP 设成「全部位用作抢占优先级、无子优先级」以简化推理。

### 5.3.3 抢占与嵌套

嵌套（nesting）指一个中断处理程序正在运行时，被另一个抢占优先级更高的中断打断，转去执行后者，后者结束再回来继续前者。NVIC 的「Nested」正来源于此：它原生支持中断嵌套，不需要软件干预。嵌套让紧急事件（如电机过流保护）能穿透正在运行的次要中断（如串口收发）立即得到响应。

嵌套会消耗栈空间——每层嵌套都压一个异常栈帧（8 或 26 字），嵌套深度取决于有多少不同的抢占优先级同时可能触发，栈必须按最坏情况留够，否则栈溢出。相同或更低抢占优先级的中断不会嵌套进来，只会被挂起排队。控制嵌套深度、合理分配抢占优先级级数，是实时设计的一部分。

### 5.3.4 尾链（tail-chaining）

尾链是 Cortex-M 的一项硬件优化。设想中断 A 刚处理完正要返回，此时又有中断 B 在挂起等待。按朴素流程，应该是「A 出栈恢复现场 → 返回主程序 → 立刻又因 B 入栈保存现场 → 进 B」，一出一进两次栈操作纯属浪费——因为主程序一条指令都没来得及跑。尾链让硬件识别出这种情况：跳过「出栈再入栈」，直接从 A 的处理程序尾部「链」到 B 的处理程序，只做一次取向量。

尾链省下的正是一次完整出栈 + 一次完整入栈的开销。在锚平台 Cortex-M4、零等待存储器条件下，尾链进入下一个 ISR 只需 6 个周期（对比从主程序被打断进入首个 ISR 的约 12 周期）。这对「一串中断接连到来」的高负载场景意义重大：中断密集时系统不会把时间浪费在反复保存 / 恢复同一份现场上。初学者需要建立的心智是——中断之间的切换比「从头进一次中断」便宜得多，这是 Cortex-M 相比老式内核在中断吞吐上的优势之一。

### 5.3.5 迟到异常（late-arriving）

与尾链相关的另一项优化是迟到异常处理。当内核正在为某个异常做入栈（那 12 个周期还没走完），若此时来了一个优先级更高的异常，内核可以「掉头」：因为入栈保存的现场是通用的（就那 8 个字），不依赖于具体去处理哪个异常，所以已经进行的入栈可以复用，内核转而先取高优先级异常的向量、先处理它。这样高优先级异常不必等低优先级的入栈白白做完，进一步压低了它的响应延迟。这是硬件细节，初学者了解「入栈期间高优先级中断仍能优先」即可，不必深究时序。

### 5.3.6 中断延迟（interrupt latency）

中断延迟指从中断被触发（拉起）到其处理程序第一条指令开始执行之间的时间。它由入栈保存现场、取向量、取处理程序首指令等步骤构成。在锚平台 Cortex-M4、访问零等待状态存储器时：

```
基础中断延迟（无 FPU 上下文）           = 12 个周期
含 FPU 上下文且未开惰性入栈             = 29 个周期
尾链到下一个 ISR（省去出栈+入栈）        = 6 个周期
```

这些数字是「无等待状态存储器」下的最好情况；实际系统里，Flash 等待状态、总线争用、更高优先级中断正在运行、以及临界区里关中断的时长，都会加大实际延迟。对实时设计，真正要保证的是「最坏情况响应时间」，它等于最坏中断延迟加上可能先于它运行的所有更高优先级中断的执行时间，再加上被关中断 / BASEPRI 屏蔽的最长时段。初学者最常见的误解是把这 12 周期当成「中断一定在 12 周期内被处理完」——它只是「开始执行第一条指令」的时间，且是理想条件下的值。不同 Cortex-M 型号该值不同（例如 Cortex-M0+ 的基础延迟与 M4 不同），须按具体内核核对，勿跨型号套用。

### 5.3.7 临界区与优先级相关的陷阱

主程序与 ISR、或不同 ISR 之间共享数据时，若一段「读-改-写」被中断从中打断，会导致数据损坏，这段代码就是临界区（critical section），需要保护。裸机上常用两种手段：用 `CPSID i`/`CPSIE i`（PRIMASK）短暂关全部中断，或用 BASEPRI 只关到某优先级（让最高优先级中断仍可穿透）。

其一，临界区要尽量短，因为关中断期间所有（或部分）中断的延迟都被拉长，直接损害实时性。其二，用 BASEPRI 时要清楚它按抢占优先级阈值屏蔽，且比阈值更高的中断不受保护——如果这些高优先级中断也访问同一共享数据，BASEPRI 挡不住它们，仍会出错。其三，嵌套关中断要配对恢复：保存进入前的 PRIMASK/BASEPRI、退出时还原，而不是无脑开中断，否则会在嵌套临界区里过早打开中断。这类问题与 RTOS 里的优先级反转（低优先级任务持锁挡住高优先级任务）在思想上相通，但那属于任务调度层面（见 RTOS 主题），此处的临界区是中断层面的数据保护。

## 5.4 三种 I/O 范式：轮询 vs 中断 vs DMA 的取舍

### 5.4.1 轮询（polling）

轮询是最直接的 I/O 方式：CPU 在循环里反复读外设的状态标志，问「数据准备好了吗 / 发送完成了吗」，直到条件满足才处理。它不依赖中断，控制流完全在程序员手里，代码顺序执行、易于理解和调试，时序也高度可预测。

轮询的代价是 CPU 的时间被「忙等（busy-wait）」白白吃掉：等待期间处理器在空转，既不能做别的事，也无法进入低功耗睡眠，功耗高。它适合几种情形：等待时间极短（等一个转换完成只需几微秒，进出中断的开销反而不划算）、系统只有一件事要做、或对时序确定性要求极高而不希望被中断打乱。初学者常见误区是在需要同时应对多个外设、或要省电的系统里仍用轮询，导致响应迟钝或电池撑不住。轮询里若循环条件涉及外设标志，同样需要 `volatile` 语义避免被优化掉。

### 5.4.2 中断驱动（interrupt-driven）

中断驱动让外设在「事件真正发生时」主动通知 CPU：平时 CPU 去干别的事甚至睡眠，事件一到，硬件触发中断、CPU 暂停当前工作跳去 ISR 处理，处理完回到原处。这消除了轮询的忙等，CPU 利用率和能效大幅提升，也能同时照看多个外设（各自不同优先级）。

代价是复杂度和不确定性上升：需要正确配置向量表、NVIC、优先级；ISR 与主程序共享数据要加锁 / volatile；控制流不再线性，调试更难；每次中断有固定的进入 / 退出开销（5.3.6 的延迟）。中断适合事件稀疏但要求及时响应、需要低功耗、或要并发处理多路 I/O 的场景（按键、通信收发、定时事件）。易错点是「中断风暴」——事件过于频繁时，光是进出中断的开销就能压垮 CPU，此时反而该考虑 DMA 或降低中断频率（如攒够一批再中断）。

### 5.4.3 DMA（直接存储器访问）

DMA（Direct Memory Access）用一个独立的硬件控制器代替 CPU 搬运数据：配置好「从哪搬、搬到哪、搬多少、什么事件触发」之后，外设与内存之间的数据传输由 DMA 控制器自动完成，全程几乎不占用 CPU；通常在整批传输完成（或半满）时才产生一次中断通知 CPU。这样「每个数据都惊动一次 CPU」的开销被彻底省掉。

DMA 的价值在高吞吐、连续数据流场景最突出：ADC 连续采样、音频 / 视频流、大块 SPI/UART 传输。它把 CPU 从逐字节搬运里解放出来，既提速又省电。代价是配置更复杂（通道、触发源、传输描述符、地址递增规则都要设对），且引入新的一致性陷阱：DMA 直接改内存，CPU 侧对同一缓冲区的缓存 / 编译器优化可能看不到变化——在有 cache 的芯片上需处理 cache 一致性，在裸机上共享缓冲区同样要 `volatile`、要用「乒乓 / 双缓冲」避免读到正在被写的半成品数据。DMA 的具体引擎（通道数、触发源、描述符格式）高度平台相关，属另一主题（DMA 与高效数据搬运）详述，此处只做范式对比。

### 5.4.4 三者对比与取舍

把三种范式并排看，取舍主线是「CPU 参与度 vs 复杂度 vs 吞吐 / 功耗」：

```
维度          轮询            中断              DMA
CPU 占用      全程忙等(最高)   仅 ISR 期间       几乎不占(仅配置+完成中断)
响应及时性    取决于轮询频率   由优先级/延迟决定  硬件即时搬运
功耗          高(不能睡)       低(可睡, 事件唤醒) 低(CPU 可睡/做别的)
代码复杂度    最低            中                最高
时序确定性    高              受抢占/延迟影响    高(硬件驱动)
适用场景      极短等待/单任务   稀疏事件/多路 I/O  高吞吐连续数据流
```

没有「最好」的范式，只有「最合适」的：等待极短、追求简单可预测就轮询；事件稀疏、要省电、要并发响应就中断；数据量大、要卸载 CPU 就 DMA。现实系统常三者混用——例如 ADC 用定时器触发、DMA 搬运采样、每攒满一批 DMA 触发一次中断让 CPU 处理，既高吞吐又低中断频率。初学者应把这三者理解成一条「CPU 逐渐从数据搬运中抽身」的光谱，而不是互斥的选项。选择时先问三个问题：等待有多久、事件多频繁、CPU 还有没有别的事要做 / 要不要睡。
