## 2.1 Cortex-M 核心与寄存器模型（R0–R15、xPSR、MSP/PSP）

### 2.1.1 通用寄存器 R0–R12

Cortex-M 是 32 位处理器，程序员可见的核心是 16 个 32 位寄存器 R0–R15。其中 R0–R12 是"通用寄存器"，用来存放运算的操作数、局部变量和函数参数；它们没有硬件强制的专门用途，编译器按调用约定分配。

初学者常问"为什么偏偏是 16 个、每个 32 位"。32 位是因为这是一颗 32 位机——地址、指针、`int` 通常都是 32 位，寄存器要能装下一个完整的地址或字。至于 R0–R12 里还常被分成"低寄存器 R0–R7"和"高寄存器 R8–R12"，是因为 Thumb 的 16 位短指令为了省编码位，很多只能操作 R0–R7；要动 R8–R12 往往得用 32 位的长指令。这在下一节反汇编里能直接看到。按 ARM 过程调用约定（AAPCS），R0–R3 传前四个参数并存返回值，R4–R11 是被调用者需要保存的寄存器，这属于汇编课（L3-03）的细节，此处点到为止。

### 2.1.2 R13 栈指针 SP：主栈 MSP 与进程栈 PSP

R13 是栈指针 SP，但 Cortex-M 特殊之处在于它有**两个**物理栈指针：主栈指针 MSP 和进程栈指针 PSP。任一时刻只有一个是"当前的" R13，由处理器模式和 CONTROL 寄存器的一位共同决定。复位后默认使用 MSP。

为什么要两个栈？这是给操作系统/RTOS 用的隔离机制。裸机小程序全程只用 MSP 就够了，代码里根本感觉不到 PSP 的存在。但一旦跑 RTOS，通常安排：每个应用任务在 Thread 模式下用**自己的** PSP（各任务一块独立栈），而所有中断/异常处理在 Handler 模式下统一用 MSP。这样中断永远在系统栈上跑，不会啃掉某个任务的栈；任务崩了也不至于连累内核栈。一个经典易错点：复位时 MSP 的初值不是代码设置的，而是处理器**从向量表第 0 个字自动加载**的——向量表最开头放的不是第一条指令地址，而是初始栈顶。很多人第一次写链接脚本忘了这条，栈指针指到非法地址，一上电就 HardFault。

### 2.1.3 R14 链接寄存器 LR 与 R15 程序计数器 PC

R15 是程序计数器 PC，指向当前正在取指的指令；写 PC 就等于跳转。R14 是链接寄存器 LR，执行"带链接的跳转"（`BL`，调用子程序）时，硬件自动把返回地址存进 LR，子程序末尾用 `BX LR` 就能返回。

直觉上 LR 是"面包屑"：调用前留下"回来时该去哪"，函数返回顺着它走回去。这也解释了一个初学者困惑——为什么叶子函数（不再调别人的函数）可以很快，因为它不必把 LR 压栈保存；而一旦函数内部还要再调别的函数，LR 会被下一次 `BL` 覆盖，就必须先把 LR 压栈、返回前再弹出。异常场景下 LR 还有个特殊玩法：进入中断时 LR 被写成一个叫 `EXC_RETURN` 的特殊魔数（高位全 1 的模式），处理器靠它在异常返回时知道该回到 Thread 还是 Handler、该用 MSP 还是 PSP。这个细节在中断章（大主题5）展开，这里只需知道"中断里的 LR 不是普通返回地址"。

### 2.1.4 程序状态寄存器 xPSR（APSR / IPSR / EPSR）

xPSR 是程序状态寄存器，是一个 32 位寄存器的"三合一"视图，逻辑上由三部分拼成：APSR（应用程序状态，存条件标志）、IPSR（中断程序状态，存当前异常号）、EPSR（执行程序状态，存 Thumb 位等执行状态）。

三个子寄存器合成一个 xPSR 的分工：

```
xPSR = APSR | IPSR | EPSR   （按位域拼合，同一个 32 位寄存器的三种视图）
  APSR: N Z C V Q ...        条件标志（负/零/进位/溢出/饱和）——比较和运算后置位
  IPSR: 当前异常号            0 = Thread（无异常）；非 0 = 正在处理的异常编号
  EPSR: T 位、IT/ICI 状态     T=1 表示处于 Thumb 状态
```

APSR 的 N/Z/C/V 就是所有架构都有的条件码，`CMP` 之后靠它决定分支走不走。IPSR 是 Cortex-M 判断"我现在是不是在中断里"的官方手段——读 IPSR 为 0 说明在普通线程里，非 0 就是正在服务某个中断，RTOS 和驱动常用它来区分上下文。一个必须记牢的易错点：EPSR 里的 T 位在 Cortex-M 上**永远是 1**，因为 Cortex-M 只有 Thumb 状态、根本没有传统 32 位 ARM 状态。如果某次异常入栈的 PSR 里 T 位被弄成 0（比如函数指针最低位没置 1 就跳过去），异常返回时会立刻触发 UsageFault。这也是为什么 Cortex-M 上所有函数地址的最低位都是 1——那一位不是地址，是"用 Thumb 执行"的标志。

### 2.1.5 特殊寄存器：CONTROL、PRIMASK、FAULTMASK、BASEPRI

除了 R0–R15 和 xPSR，Cortex-M 还有一组"特殊寄存器"，不能用普通数据指令直接读写，得用 `MSR`/`MRS` 专门指令访问。主要有：CONTROL（选 MSP/PSP、选特权/非特权、FPU 上下文位）、PRIMASK（一位总开关，置 1 屏蔽几乎所有可屏蔽中断）、FAULTMASK（比 PRIMASK 更狠，连 HardFault 之外的都挡）、BASEPRI（按优先级阈值屏蔽，只挡比某个优先级低的中断）。

初学者最先用到的是 PRIMASK：写临界区代码、需要"这几行不能被打断"时，`CPSID i`（置 PRIMASK）关中断、`CPSIE i` 开中断，是最粗暴但最可靠的互斥手段。BASEPRI 更精细——它能只关"不太紧急"的中断而放行高优先级的，做实时系统时用它比一刀切关掉所有中断要好。CONTROL 寄存器是 RTOS 切到"任务用 PSP、非特权"配置的开关。这些寄存器的细节归中断/RTOS 章，这里列出是为了让读者知道"Cortex-M 的寄存器模型不止 R0–R15，还有一组管权限和中断屏蔽的特殊寄存器"。

### 2.1.6 处理器模式与特权级：Thread / Handler、特权 / 非特权

Cortex-M 有两种运行模式：Thread 模式（跑普通应用代码）和 Handler 模式（跑异常/中断处理）。复位后从 Thread 模式起步；一旦有异常/中断进来就切到 Handler 模式，处理完再回 Thread。正交地，还有两个特权级：特权（Privileged）和非特权（Unprivileged/User）。Handler 模式永远是特权的；Thread 模式可以是特权也可以是非特权，由 CONTROL 寄存器决定。

这套"模式 × 特权级"是嵌入式做安全隔离的基础，虽然比通用 OS 的用户态/内核态简单得多。裸机程序基本全程待在"Thread + 特权"这一个格子里，感觉不到区别。RTOS 才会用它：内核和中断在特权级跑、能碰所有寄存器；应用任务降到非特权级跑，配合 MPU（见 2.4）就能限制某个任务只能访问自己的内存，一个任务写飞了不会破坏内核或别的任务。这里最容易混的是"模式"和"特权级"是两个独立维度：不是"Handler 就特权、Thread 就非特权"，而是 Handler 恒特权、Thread 特权与否可配。理解这一点，才能看懂 RTOS 的上下文切换为何要同时动 CONTROL 位和栈指针。

## 2.2 流水线与 Thumb-2 指令集子集特征

### 2.2.1 三级流水线（取指 / 译码 / 执行）

Cortex-M3 和 Cortex-M4 采用**三级流水线**：取指（Fetch）、译码（Decode）、执行（Execute）。同一时刻，一条指令在执行、下一条在译码、再下一条在取指，三条指令的不同阶段叠在一起流水，使得多数指令的吞吐接近"每周期一条"。

不必等一条指令彻底做完再开始下一条，把加工拆成三道工序并行推进就能提高吞吐。为什么是三级这么"浅"？因为 Cortex-M 定位低功耗、强确定性——流水线越深，分支预测失败时要冲刷（flush）丢弃的半成品越多，时序越难预测。嵌入式要的是"这段代码到底几个周期"能算得准，浅流水线正好服务这个目标。一个必须澄清的易错点：因为流水线的存在，PC 读出来的值**不是当前指令地址**，而是当前指令地址 +4（Thumb 下超前一条 32 位的量）。这是很多人手算 PC 相对寻址、看反汇编里 `ldr rX, [pc, #N]` 的偏移时对不上账的根源。注意"三级流水线"是 M3/M4 的实现细节，不同内核不同：Cortex-M7 是更深的双发射超标量流水线，Cortex-M0 也有自己的流水结构——所以这条要硬标锚内核。

### 2.2.2 Thumb-2：混合 16/32 位指令集

Cortex-M 只执行 **Thumb** 指令，且用的是 **Thumb-2** 技术：在原来纯 16 位 Thumb 的基础上，加入了一批 32 位指令，于是同一段代码里 16 位短指令和 32 位长指令**混在一起**，处理器逐条按编码长度识别。ARMv7-M（M3/M4）实现的正是这个 Thumb/Thumb-2 子集，**没有**传统的 32 位 ARM 指令状态。

为什么要混合长度？纯 16 位指令代码密度高（省 Flash），但能表达的操作有限（只能碰低寄存器、立即数范围小）；纯 32 位指令表达力强但占空间。Thumb-2 的思路是"常用小操作用 16 位、复杂操作用 32 位"，兼得密度和能力。本机用现装的 `arm-none-eabi-gcc`（非默认·现装·非持久）交叉编译一段 C 并反汇编，可以直接看到这种混合：

```
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -c demo.c -o demo.o
$ arm-none-eabi-objdump -d demo.o        # 工具链 13.2.1 (arm-none-eabi)，2026-08-01 现装

00000000 <add>:
   0:  4408        add   r0, r1              ← 16 位指令（编码只占 2 字节 4408）
   2:  4770        bx    lr                  ← 16 位

00000004 <toggle>:                           ← *GPIO ^= 1
   a:  f083 0301   eor.w r3, r3, #1          ← 32 位指令（编码占 4 字节 f083 0301，.w=宽指令）
   e:  6013        str   r3, [r2, #0]        ← 16 位
```

左栏地址每条递增 2 或 4 字节，正好对应 16 位 / 32 位两种长度混排。`add r0, r1` 只碰低寄存器、能用 16 位塞下；`eor.w`（按位异或立即数）需要 32 位编码，汇编里用 `.w`（wide）后缀标记它是宽指令。一个易错点：不要把这里的"Thumb"跟 ARM64（AArch64，手机/服务器上的 Cortex-A）搞混——那是完全不同的 ISA；Cortex-M 用的是 32 位 ARMv7-M 的 Thumb 子集。

### 2.2.3 ARMv7-M 指令集的架构特征：load/store、条件执行 IT 块

ARMv7-M 是**load/store 架构**：算术逻辑指令只在寄存器之间运算，内存访问只能靠专门的加载（`LDR`）/存储（`STR`）指令，不存在"直接对内存做加法"的指令。此外它保留了 ARM 家族的条件执行能力，但在 Thumb-2 里通过 `IT`（If-Then）块实现——`IT` 指令给紧随其后的最多 4 条指令附加条件，条件不满足就当空操作跳过。

load/store 架构的直觉是"内存和计算分家"：想改内存里的值，得先 `LDR` 搬进寄存器、算完再 `STR` 写回，前面 2.1.2 反汇编里 `toggle` 那段 `ldr → eor.w → str` 就是活教材（读-改-写三步）。这对写驱动很关键：对一个外设寄存器"置某一位"其实是三步操作，不是原子的——多个中断同时读改写同一寄存器会丢更新，这正是 2.3.5 位带机制想解决的问题。`IT` 块的用处是避免短小分支：与其为一个"如果相等就加一"跳来跳去打断流水线，不如用条件执行一条带过，减少流水线冲刷。初学者读反汇编看到 `ITTE`、`addeq` 这类别慌，那就是条件执行块。这些属汇编课细节，此处点到为止、不深入微架构。

### 2.2.4 分支、流水线冲刷与 PC 相对寻址

顺序执行时三级流水线满负荷跑；但一遇到分支/跳转，处理器可能已经预取了"落空"的后续指令，必须把它们从流水线里冲刷（flush）丢掉，再从跳转目标重新取指——这几个被浪费的周期就是分支的代价。Cortex-M 用简单的分支处理策略（不做复杂动态预测），代价小且时序可预测。

理解这一点能解释两件事。其一，为什么紧凑的循环、`IT` 条件执行往往比等价的分支跳转快——它们减少了流水线冲刷。其二，为什么常量、大立即数常以"PC 相对加载"的形式出现：Thumb 指令编码位有限，塞不下一个完整的 32 位常量或地址，编译器就把常量放在函数附近的"文字池"（literal pool），用 `ldr r3, [pc, #偏移]` 去取。2.1.2 里 `toggle` 反汇编末尾那条 `.word 0x00000000` 就是文字池里存的 GPIO 地址（未链接时占位为 0，链接后填真实地址）。而算 `[pc, #偏移]` 的偏移时，务必记得 2.2.1 说的"PC 超前"效应，否则手算必错。

## 2.3 内存映射与存储架构（Flash / SRAM / 外设区 / 位带区）

### 2.3.1 统一 4GB 地址空间与固定区域划分

Cortex-M 用单一、扁平的 32 位地址空间，共 4GB（0x00000000–0xFFFFFFFF），代码、数据、外设寄存器、系统控制寄存器**全都映射进这同一个地址空间**——想访问哪个，就往对应地址读写。架构文档还给这 4GB 划了推荐用途的分区，芯片厂商在此框架内摆放自己的 Flash、SRAM 和外设。

架构规定的分区骨架（ARMv7-M 默认内存映射，容量以锚平台 TM4C123GH6PM 为例）：

```
0x00000000 - 0x1FFFFFFF   Code     代码区（Flash 通常从 0x00000000 起，TM4C123：256 KB Flash）
0x20000000 - 0x3FFFFFFF   SRAM     数据区（TM4C123：32 KB SRAM 从 0x20000000 起）
0x40000000 - 0x5FFFFFFF   Peripheral  片上外设寄存器（GPIO/UART/定时器/ADC …）
0x60000000 - 0x9FFFFFFF   RAM/外部  外部 RAM 等
0xA0000000 - 0xDFFFFFFF   Device   外部设备
0xE0000000 - 0xE00FFFFF   PPB      私有外设总线（NVIC/SysTick/SCB/MPU 等系统控制空间）
0xE0100000 - 0xFFFFFFFF   Vendor   厂商专用
```

这套"内存映射一切"的思想是嵌入式的核心心智模型：在 PC 上你得调 API 才能碰硬件，而在 Cortex-M 上，点亮一个 LED 就是往某个固定地址（比如某 GPIO 数据寄存器）写一个字。这也是 2.4 会讲的——没有 MMU，程序看到的地址就是物理地址，一一对应、无翻译。易错点：**Code 区能放代码不等于只能放 Flash**，SRAM 里的代码也能执行；反过来 Flash 里也能存常量数据（`const`）。区域划分是"建议用途 + 芯片实现"，不是铁律；换一颗芯片，Flash/SRAM 的容量和外设地址都会变，唯独 0xE0000000 的系统区（PPB）由架构固定，所有 Cortex-M 一致。

### 2.3.2 Flash：代码与常量、就地执行（XIP）

Flash 是非易失存储（断电不丢），在 TM4C123 上从 0x00000000 起、容量 256 KB。它存放程序代码（`.text`）、只读常量（`.rodata`）和需要在上电时拷进 RAM 的初值（`.data` 的初始镜像）。处理器可以**直接从 Flash 取指执行**，这叫就地执行（XIP，eXecute In Place），不必先把程序拷到 RAM。

对比 PC 会很清楚：PC 开机要把程序从硬盘/SSD 加载进内存再运行；Cortex-M 的代码本来就"住在"可寻址的 Flash 里，上电从向量表取到复位地址就直接在 Flash 上跑起来，省掉加载这一步。代价是 Flash 比 SRAM 慢——读取有等待周期，主频高时需要配 Flash 等待状态（wait state）或预取缓冲，否则取指跟不上。易错点：Flash 不能像 RAM 那样想写就写，它的写入要按"先擦除整块、再编程"的特殊流程，寿命也有限（擦写次数上限）；所以变量放 SRAM、代码常量放 Flash，别指望对 Flash 地址直接 `= ` 赋值就能改。容量数值 256 KB 是 TM4C123GH6PM 的实现，换芯片不同（⚙锚平台）。

### 2.3.3 SRAM：数据、栈与堆

SRAM 是易失的读写存储（断电即丢），在 TM4C123 上从 0x20000000 起、容量 32 KB。它放全局/静态变量（`.data`/`.bss`）、堆（`malloc` 的来源）和栈（局部变量、函数调用现场）。栈通常从 SRAM 高地址向低地址生长，堆从低地址向高地址生长，两头相对挤。

SRAM 快（多数情况零等待）、可任意读写，但极其有限——32 KB 是什么概念？还不够存一张手机照片。这逼出嵌入式的核心约束（呼应大主题1）：数据结构要精打细算，慎用递归和大数组（爆栈），动态内存（`malloc`）在很多嵌入式规范里干脆被禁，因为碎片化和不确定性在内存这么小的地方是灾难。一个经典且致命的易错点是**栈溢出**：栈向下长、堆向上长，若某次深调用或大局部数组把栈顶压到撞上堆或 `.bss`，就会静默改写别的变量，症状诡异到极难查。没有 MMU 保护页（2.4），越界不会立刻报错，只会悄悄损坏数据。容量 32 KB 为 TM4C123 实现（⚙锚平台）。

### 2.3.4 外设区与存储器映射 I/O

从 0x40000000 起的外设区，摆放着所有片上外设（GPIO、UART、SPI、I²C、定时器、ADC……）的控制寄存器。控制硬件的方式就是读写这些地址——这叫**存储器映射 I/O**（memory-mapped I/O）：外设寄存器被当成普通内存地址，用同样的 `LDR`/`STR` 访问，没有 x86 那种独立的 `IN`/`OUT` 端口指令。

在 C 里，这体现为把一个地址强转成指针再解引用：

```c
#define GPIO_PORTF_DATA_R (*((volatile unsigned int *)0x400253FC))
GPIO_PORTF_DATA_R |= 0x02;   // 往该外设寄存器地址写，硬件随之动作（点灯）
```

关键词是 `volatile`：外设寄存器的值可能被硬件在程序背后改变（比如状态寄存器的"数据就绪"位），也可能"写进去"本身就有副作用（触发发送）。`volatile` 告诉编译器"这个地址每次都老老实实去读/写真内存，别缓存到寄存器、别优化掉"。忘写 `volatile` 是嵌入式头号 bug 之一：编译器一优化，轮询状态位的循环可能被优化成只读一次的死循环，或者连续几次写寄存器被合并成一次。`volatile` 的机制与反汇编对照留给大主题3展开，这里只需记住"碰外设寄存器必加 `volatile`"。地址 0x400253FC 是 TM4C123 的 GPIO Port F 数据寄存器（⚙锚平台，别的芯片外设地址不同）。

### 2.3.5 位带区（bit-band）与别名区：单比特原子访问

Cortex-M3/M4 的 SRAM 区和外设区各有最低 1 MB 是**位带区**（bit-band region），并各自配一个 32 MB 的**别名区**（alias region）。别名区里每一个 32 位字，一一映射到位带区里的某**一个比特**：读别名字返回那个比特（0 或 1），写别名字（最低位）就设置那个比特。这样，"改一个比特"从原本的读-改-写三步，变成对别名地址一次单独的字写，硬件保证是原子的。

别名地址由一个固定公式算出：

```
bit_word_addr = bit_band_base + (byte_offset × 32) + (bit_number × 4)

  bit_band_base = 别名区基址（SRAM: 0x22000000；外设: 0x42000000）
  byte_offset   = 目标字节地址 − 位带区基址（SRAM: 0x20000000；外设: 0x40000000）
  bit_number    = 目标比特在该字节内的位号（0–7）

SRAM 位带区   0x20000000–0x200FFFFF (1MB)  ↔  别名区 0x22000000–0x23FFFFFF (32MB)
外设位带区    0x40000000–0x400FFFFF (1MB)  ↔  别名区 0x42000000–0x43FFFFFF (32MB)
```

为什么需要它？回顾 2.2.3——普通"置一位"是读-改-写三步，不是原子的：中途来个中断也去改同一寄存器，就会丢更新（竞态）。位带把"改一位"压成一次原子写，既免了竞态，又省去读和掩码运算。直觉上"32 倍膨胀"就是拿地址空间换原子性：1 MB 的位带区（8 M 个比特）摊到 32 MB 别名区，每比特独占一个字地址（4 字节 × 8 比特 = 32 字节别名对应 1 字节 = 8 比特，正好每比特 4 字节）。易错点有二：一是位带**只覆盖最低 1 MB**，够不到高地址的 SRAM/外设就用不了；二是这是 M3/M4 的**可选架构特性**，Cortex-M0/M0+ 没有位带，Cortex-M7 上也不保证——迁移代码时别想当然。所以位带虽方便，可移植代码里常改用编译器/CMSIS 提供的原子位操作或关中断临界区替代。地址范围为 ARMv7-M 架构规定，TM4C123 遵循（⚙锚平台/架构版本）。

### 2.3.6 系统控制空间与总线结构（PPB、哈佛式总线 vs 冯诺依曼内存模型）

0xE0000000 起的私有外设总线（PPB）区，是架构固定的系统控制空间，放着所有 Cortex-M 共有的核心外设：NVIC（中断控制器）、SysTick（系统节拍定时器）、SCB（系统控制块）、MPU（若实现）等。因为地址由架构统一规定，同样的内核驱动代码能跨不同厂商的 Cortex-M 芯片复用——这正是 ARM 生态的价值。

关于总线，Cortex-M3/M4 内部是**哈佛式**多总线：有独立的 I-Code 总线（从 Code 区取指令）、D-Code 总线（从 Code 区取数据）和 System 总线（访问 SRAM/外设/系统区）。这让"取指令"和"取数据"能并行、互不抢道，提高吞吐。但要特别澄清一个初学者极易混淆的点：**总线是哈佛式（取指/取数分道），内存模型却是冯诺依曼式（统一地址空间）**——代码和数据共享同一个 4GB 地址空间、同一套地址编号（这正是 2.3.1 的"内存映射一切"）。所以说 Cortex-M"是哈佛还是冯诺依曼"都不完整，准确说法是"冯诺依曼内存模型 + 哈佛总线实现"。这与经典教科书里"哈佛=代码数据物理分开的两块存储、地址空间也分开"（如某些 8 位单片机、DSP）不是一回事，别套用。

## 2.4 无 MMU、MPU 保护、（通常无）cache 特性 vs 通用 OS

### 2.4.1 无 MMU：物理地址直达，无虚拟内存

Cortex-M 内核**不含内存管理单元（MMU）**。程序里用的地址就是真实的物理地址，没有虚拟地址到物理地址的翻译，也就没有分页、没有换页到磁盘、没有"每个进程一套独立地址空间"的假象。你写 `0x20000000`，硬件访问的就是 SRAM 那个物理字节。

这是嵌入式与通用 OS（Linux/Windows，跑在带 MMU 的 Cortex-A/x86 上）最根本的分野之一。通用 OS 靠 MMU 给每个进程独立虚拟地址空间、互相隔离、按需分页、内存超额分配；Cortex-M 上没有这些——所有代码共享同一物理地址空间。好处是**确定性和简单**：地址访问没有页表遍历、没有缺页中断带来的时间抖动，一次访存要几个周期是可算的，正合实时系统所需。代价是没有隔离与虚拟内存：任何代码理论上能访问任何地址，一处野指针可以损坏任意内存。易错点：别把 Cortex-M（M 系列，微控制器，无 MMU）和 Cortex-A（A 系列，应用处理器，有 MMU，跑 Linux）混为一谈——它们是 ARM 面向不同市场的两条产品线。本报告全程讲的是 M 系列。（跨课分账：这正是与 L4-01 通用 OS 的关键差异——那里假设有 MMU。）

### 2.4.2 MPU：内存保护单元（有隔离、但不做地址翻译）

Cortex-M 可以选配**内存保护单元（MPU）**（是否搭载看具体芯片）。MPU 不翻译地址（那是 MMU 的活），它只做"保护"：把地址空间划成若干区域（region），给每个区域设访问权限（可读/可写/可执行、特权/非特权）。越权访问触发 MemManage 异常（内存管理错误），从而把错误挡在现场、而不是让它悄悄破坏数据。

直觉上，MMU 是"既发身份证又设门禁"（虚拟化 + 保护），MPU 是"只设门禁不发身份证"（只保护、不虚拟化）。它填补了 2.4.1 说的"无隔离"短板的一部分：配合 RTOS 和 2.1.6 的特权级，可以让每个非特权任务只被授权访问自己的代码和数据区，某任务的野指针一旦踩到别人的区域就立刻 MemManage 异常，而不是静默损坏。安全关键系统（汽车、医疗）常用 MPU 做这种隔离。易错点：MPU 是**可选**的，不是所有 Cortex-M 芯片都有；且它区域数量有限（常见 8 个区域）、区域大小和对齐有约束，用起来不像 MMU 分页那么自由。别把"有 MPU"当成"有内存虚拟化"。

### 2.4.3 （通常无）cache：M0/M3/M4 无缓存，M7 起才有

Cortex-M0/M0+/M3/M4 内核**没有 cache**（高速缓存）。处理器直接访问 Flash 和 SRAM，中间没有"缓存最近数据加速下次访问"的那一层。（Cortex-M7 起才引入指令/数据 cache，是显著的分水岭。）

为什么低端 Cortex-M 不要 cache？因为 cache 换来平均速度、却牺牲**确定性**：有缓存后，同一段代码"命中"和"未命中"的耗时差很多，最坏执行时间难算，这对硬实时是麻烦。没有 cache，一次访存几个周期是固定的，时序可预测——又是"确定性优先"的体现（呼应大主题1）。Flash 慢的问题不用 cache，而是用简单的**预取缓冲/Flash 加速器**（芯片厂商实现）来缓解。这里有个重要的连带结论：正因为 M0/M3/M4 无数据 cache，程序员通常**不用操心 cache 一致性**——DMA（大主题9）改了 SRAM，CPU 立刻能看到，不像带 cache 的系统那样要手动 clean/invalidate 缓存。但一旦上到 Cortex-M7，cache 回来了，DMA 与 cache 的一致性就重新成为必须处理的坑。所以这条也要硬标锚内核。

### 2.4.4 综合对比：嵌入式 Cortex-M vs 通用 OS 平台

把前三节收拢成一张对照，能看清"为什么嵌入式的编程心智和 PC 上如此不同"：

```
维度          Cortex-M（M0/M3/M4，本报告锚）      通用 OS 平台（Cortex-A / x86）
地址翻译      无 MMU，物理地址直达               有 MMU，虚拟地址 + 分页
进程隔离      无（可选 MPU 做区域保护）          有（每进程独立虚拟地址空间）
缓存          M0/M3/M4 无 cache（M7 起有）        多级 cache（L1/L2/L3）
虚拟内存      无（无换页到磁盘）                 有（按需分页、内存超额分配）
确定性        高（访存周期可算，宜硬实时）        较低（cache/分页带来时间抖动）
存储量级      Flash 数百 KB、SRAM 数十 KB         DRAM 数 GB、存储 TB 级
```

Cortex-M 用"放弃虚拟内存/缓存/进程隔离"换来"确定性、低功耗、低成本、简单"。这不是"功能不全"，而是嵌入式约束（大主题1）下的正确取舍——实时控制要的是"每次都准时"，不是"平均很快"。理解这张表，就能明白为什么嵌入式代码不能想当然套用 PC 上的习惯（随便 `malloc`、假设有虚拟内存保护、指望 cache 加速）。易错点提醒：表中"无 cache""无 MMU"是锚 M0/M3/M4 的结论，Cortex-M7/M85 等高端型号会有 cache（甚至可选 MMU 变体极少见），迁移时必须重新核对。
