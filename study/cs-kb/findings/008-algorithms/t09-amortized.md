## 9.1 聚合分析

### 9.1.1 摊还分析是什么、解决什么问题

摊还分析（amortized analysis）研究的是「一整串操作」的总代价，然后把总代价平摊到每次操作上，得到**每次操作的平均代价**——这个平均值就叫**摊还代价（amortized cost）**。它的关键特征是：这个「平均」是对**最坏情形的操作序列**求的，**不涉及任何概率**。

摊还分析要回答的核心问题是：

一串 n 个操作在最坏情况下总共花多少时间？平摊到每次是多少？

核心说明：很多数据结构有这样的性格——绝大多数操作很便宜，偶尔一次很贵。如果只看单次操作的最坏代价，会严重高估整串操作的真实成本。摊还分析给出一个更诚实的界：即使把最贵的那几次也算进去，平摊到每次操作头上仍然很小。

辅助说明：初学者最容易混淆的一点是**摊还分析 vs 平均情形分析**。两者都出现「平均」二字，但含义完全不同。

- 平均情形分析（average-case）：对**输入的概率分布**求期望，结论形如「随机输入下期望是 O(n log n)」，个别输入可能更差；它依赖「输入是随机的」这个假设。
- 摊还分析（amortized）：对**一串操作**取平均，结论形如「任意 n 个操作总代价 O(n)，故每次摊还 O(1)」，**保证对任何操作序列都成立**，没有任何概率假设。

举个最小对照例子：往一个初始为空的动态数组连续 push n 个元素（9.4 会细讲）。单次 push 的最坏代价是 O(n)（正好触发扩容、要把已有元素全搬走），但 n 次 push 的总代价是 O(n)，所以每次 push 的**摊还**代价是 O(1)——这是对**任意** n 次 push 都成立的保证，不是「平均而言」。

CLRS Ch16 给出三种做摊还分析的方法：**聚合分析**（本节 9.1）、**记账法**（9.2）、**势能法**（9.3）。三者是同一件事的三种记账方式，对同一个操作序列会给出**一致**的摊还界；区别只是「怎么算更顺手」。聚合分析最直接（先算总代价再除以 n，且对所有操作给同一个摊还值）；记账法和势能法更灵活（允许不同操作有不同的摊还值）。本章用两个贯穿全章的例子来对比三种方法：**栈的 MULTIPOP** 和**二进制计数器的 INCREMENT**。

### 9.1.2 聚合分析方法本身

聚合分析（aggregate analysis）的做法是：先直接求出「任意 n 个操作的最坏总代价 T(n)」，再把它平摊：

每次操作的摊还代价 = T(n) / n

核心说明：聚合分析是三种方法里最朴素的一种——不给单个操作单独定价，而是先算整串的总账，再均分。它的特点是**所有操作类型都被赋予同一个摊还代价** T(n)/n。

辅助说明：为什么这样是合法的、而不是「耍赖」？因为 T(n) 是**真实总代价的上界**（对最坏的操作序列成立），把它均分只是换一种表述总代价的方式，并没有偷偷丢掉哪次操作的开销。难点通常在第一步「怎么求出 T(n)」——往往要换个角度数，比如下面二进制计数器例子里「不按操作数、改按每个 bit 被翻转的次数」来数，就能一下子看出总代价是线性的。

### 9.1.3 栈操作 MULTIPOP 的聚合分析

在普通栈的 PUSH、POP 之外，加一个 MULTIPOP(S, k)：连续弹出 k 个元素（若栈中不足 k 个则全部弹出）。它的伪代码是：

```text
MULTIPOP(S, k):
    while not STACK-EMPTY(S) and k > 0:
        POP(S)
        k = k - 1
```

单次 MULTIPOP 的最坏代价是 O(n)（栈里有 n 个元素、k ≥ n 时一次弹光）。

核心说明：单次 MULTIPOP 看起来很贵（O(n)），于是「n 个操作、每个最坏 O(n)」的粗暴估计会给出 O(n²)。但这是**过高估计**：聚合分析给出的真实总代价是 O(n)。

辅助说明：关键观察是——**每个元素只能被弹出一次，而它必须先被 PUSH 进来才能被弹出**。所以在任意 n 个 PUSH/POP/MULTIPOP 混合操作里，POP 动作（无论来自 POP 还是 MULTIPOP 内部）的总次数不可能超过 PUSH 动作的总次数，而 PUSH 至多发生 n 次。因此所有操作加起来的总代价至多是：

T(n) = O(n)

于是每次操作的摊还代价是：

T(n) / n = O(1)

这就是聚合分析的威力：换个角度数（数「元素进出栈的总次数」而非「每次操作各自的最坏值」），O(n²) 的粗估立刻收紧到 O(n)。易错点：这里的 O(1) 是**摊还**代价，不是说「每次 MULTIPOP 都便宜」——某一次 MULTIPOP 仍可能实打实弹出 O(n) 个元素，只是那 O(n) 的开销已经被之前那 O(n) 次 PUSH「预支」掉了。

我实测了一串随机 PUSH/MULTIPOP 操作的总代价，验证每次操作的平摊代价确实是小常数：

```text
stack multipop: n_ops=100000 total_cost=133803 cost/op=1.3380 (O(1) amortized, <=2: True)
```

10 万次随机操作总代价约 13.4 万，平摊每次约 1.34（远小于 O(n)），符合摊还 O(1)。

### 9.1.4 二进制计数器的聚合分析

维护一个 k 位二进制计数器，从 0 开始，反复执行 INCREMENT（加一）。INCREMENT 的代价用「翻转的 bit 数」衡量：

```text
INCREMENT(A):
    i = 0
    while i < A.length and A[i] == 1:
        A[i] = 0        # 把连续的低位 1 翻成 0
        i = i + 1
    if i < A.length:
        A[i] = 1        # 把第一个 0 翻成 1
```

单次 INCREMENT 的最坏代价是 O(k)（当低位全是 1，如 0111…1 加一，要翻转 k 位）。

核心说明：粗估「n 次 INCREMENT、每次最坏 O(k)」给出 O(nk)，但聚合分析给出的真实总代价是 O(n)，与位数 k 无关。

辅助说明：换个角度数——**不按「每次操作翻几位」，改按「每个 bit 在 n 次操作里总共翻几次」**。观察计数模式：A[0]（最低位）每次 INCREMENT 都翻，翻 n 次；A[1] 每两次 INCREMENT 才翻一次，翻 ⌊n/2⌋ 次；一般地第 i 位每 2ⁱ 次操作翻一次，翻 ⌊n/2ⁱ⌋ 次。于是 n 次 INCREMENT 翻转的总位数是：

∑_{i=0}^{k-1} ⌊n/2ⁱ⌋ < n · ∑_{i=0}^{∞} (1/2ⁱ) = 2n

这是一个收敛的几何级数，和小于 2n。因此总代价：

T(n) = O(n)

每次 INCREMENT 的摊还代价：

T(n) / n < 2 = O(1)

易错点：初学者常盯着「最坏一次翻 k 位」而以为总代价含 k。真相是「翻 k 位」这种昂贵操作极其罕见（每 2^{k-1} 次才可能有一次），高位翻转的频率随位数指数级下降，几何级数把它们全部压到常数。

我实测了各规模下的总翻转次数，并逐位核对「第 i 位翻 ⌊n/2ⁱ⌋ 次」：

```text
binary counter: n=      1 total_flips=      1 2n=      2 ratio=1.0000 (<2: True)
binary counter: n=    100 total_flips=    197 2n=    200 ratio=1.9700 (<2: True)

  bit 8 flips=   3 floor(n/2^8)=   3 match=True
```

总翻转数稳定小于 2n 且随 n 增大趋近 2n；逐位翻转数与 ⌊n/2ⁱ⌋ 完全吻合，佐证了几何级数求和。

## 9.2 记账（核算）法

### 9.2.1 记账法的思想：为操作预付信用

记账法（accounting method / 又译核算法）给每种操作指定一个**摊还代价**，这个值可以和它的真实代价不同。当摊还代价 > 真实代价时，多出来的差额存成**信用（credit）**，寄放在数据结构的某些对象上；当某次操作的真实代价 > 它的摊还代价时，用之前存下的信用来支付差额。

核心的合法性条件是：**任何时刻存下的总信用必须非负**。用式子说，对任意 n、任意操作序列：

∑_{i=1}^{n} (摊还代价 ĉᵢ) ≥ ∑_{i=1}^{n} (真实代价 cᵢ)

核心说明：只要总信用永不为负（即摊还代价之和始终 ≥ 真实代价之和），那么摊还代价之和就是真实总代价的一个**上界**，于是我们报出的每次摊还代价就是合法的、可信的界。

辅助说明：可以把信用想成「储蓄」。便宜的操作故意「多付一点」把钱存进数据结构的对象里；将来某次昂贵操作到来时，它的开销已经被这些储蓄提前付清了。要点有两个易错处：其一，信用是记账工具，**不是真实的时间或空间**，数据结构里并没有真的多存东西；其二，必须证明「储蓄账户余额永不透支」——一旦某时刻总信用为负，就意味着我们报的摊还代价低于真实开销，界不成立。设定每种操作的摊还值时有一定艺术性，但设好后验证「余额非负」是硬性的。

### 9.2.2 栈操作的记账法

给三种栈操作定摊还代价：

PUSH：摊还代价 2；POP：摊还代价 0；MULTIPOP：摊还代价 0

（真实代价：PUSH = 1，POP = 1，MULTIPOP = min(k, 栈中元素数)。）

核心说明：PUSH 的真实代价是 1，却收费 2——多收的 1 作为信用**贴在被压入的那个元素上**。将来这个元素被 POP 或 MULTIPOP 弹出时，弹出它的真实代价 1 正好由它自己身上的这 1 点信用支付，所以 POP/MULTIPOP 对外报的摊还代价是 0。

辅助说明：为什么余额永不为负？因为每个在栈中的元素都恰好带着 1 点信用（PUSH 时贴上、还没被弹出），栈里有多少元素就有多少信用，总信用 = 栈中元素数 ≥ 0，永远非负。于是 n 个操作的摊还总代价至多是「PUSH 次数 × 2」≤ 2n = O(n)，与 9.1 聚合分析给出的 O(n) 一致。直觉锚：进栈时先付好将来出栈的「车费」，所以出栈时不用再掏钱——无论是一个一个 POP 还是一次 MULTIPOP 弹一大批，车费早就付过了。

### 9.2.3 二进制计数器的记账法

给 INCREMENT 里的位操作定摊还代价：

把某一位从 0 置 1：摊还代价 2；把某一位从 1 置 0：摊还代价 0

核心说明：INCREMENT 的内层 while 循环把若干个 1 翻成 0，再把一个 0 翻成 1。我们只对「0→1」这一次翻转收费 2，对所有「1→0」翻转收费 0。多收的 1 点信用贴在这个刚变成 1 的位上。

辅助说明：每次 INCREMENT 里「0→1」的翻转**至多发生一次**（就是循环退出后设置的那一位），所以每次 INCREMENT 的摊还代价至多是 2。而「1→0」翻转不收费——因为每个值为 1 的位身上都存着 1 点信用，将来它被翻回 0 时，那次翻转的真实代价 1 正好由它自己的信用支付。余额非负的理由：计数器里每个为 1 的位恰好带 1 点信用，总信用 = 当前 1 的个数 ≥ 0。因此 n 次 INCREMENT 的摊还总代价 ≤ 2n = O(n)，与聚合分析一致。这里可以清楚看到记账法和聚合分析的对应：聚合分析里「几何级数求和 < 2n」，记账法里「每次 INCREMENT 至多付 2」，两条路殊途同归到同一个 2n 上界。

## 9.3 势能法

### 9.3.1 势函数与摊还成本的定义

势能法（potential method）是三种方法里最强大、最常用的一种。它不把信用贴在具体对象上，而是把「预存的势能」整体地表示为数据结构状态的一个函数——**势函数（potential function）** Φ，它把数据结构的每个状态 Dᵢ 映射到一个实数 Φ(Dᵢ)。

设第 i 个操作的真实代价为 cᵢ，操作前状态为 D_{i-1}、操作后为 Dᵢ，则第 i 个操作的**摊还代价**定义为：

ĉᵢ = cᵢ + Φ(Dᵢ) − Φ(D_{i-1})

即「真实代价 + 势能的变化量」。把 n 个操作的摊还代价相加，中间项望远镜式相消（telescoping），得到：

∑_{i=1}^{n} ĉᵢ = ∑_{i=1}^{n} cᵢ + Φ(D_n) − Φ(D_0)

核心说明：如果我们能保证对所有 i 都有 Φ(Dᵢ) ≥ Φ(D_0)（通常取 Φ(D_0) = 0 且 Φ 始终非负），那么摊还总代价 ∑ĉᵢ 就是真实总代价 ∑cᵢ 的一个上界。这样只要逐个操作算出 ĉᵢ 的界，累加就得到真实总代价的界。

辅助说明：势能法和记账法是「同一枚硬币的两面」——记账法把预存的钱贴在一个个对象上（局部视角），势能法把预存的钱汇总成一个数 Φ（全局视角）。式子

ĉᵢ = cᵢ + ΔΦ

的直觉是：一次操作若让数据结构变「更有序/更松弛/更有余力」（Φ 下降），说明它在花掉之前存的势能，此时即便真实代价 cᵢ 很大，摊还代价 ĉᵢ 也可能很小；反之一次便宜操作若让结构变「更紧张」（Φ 上升），它就要多付一点摊还代价来把势能充上去，留给将来那次昂贵操作去释放。易错点有两个：一是必须验证 Φ(Dᵢ) ≥ Φ(D_0)（否则得到的不是上界），二是**势函数的选取是关键技巧**——选得好，每次操作的 ĉᵢ 都是小常数；选不好，分析就闭合不了。势函数怎么选没有机械公式，但选定后验证是纯机械的代入。

### 9.3.2 势能法用于栈操作

取势函数为「栈中元素的个数」：

Φ(D) = 栈中元素数

核心说明：初始空栈 Φ(D_0) = 0，且任何时刻元素数 ≥ 0，故 Φ(Dᵢ) ≥ 0 = Φ(D_0)，合法性满足。逐个算摊还代价：PUSH 使元素数 +1，ĉ = 1 + 1 = 2；POP 使元素数 −1，ĉ = 1 + (−1) = 0；MULTIPOP 弹出 k' = min(k, 栈中数) 个，真实代价 k'、势能变化 −k'，ĉ = k' + (−k') = 0。

辅助说明：三种操作的摊还代价 2、0、0 和 9.2 记账法完全一样——这不是巧合，而是因为这里的势函数 Φ = 栈中元素数，恰好等于记账法里「所有元素身上信用的总和」（每个元素 1 点信用）。可见记账法的「总信用」就是势能法的「Φ 值」，两法本质相同。n 个操作的摊还总代价 ≤ 2n = O(n)。

### 9.3.3 势能法用于二进制计数器

取势函数为「计数器中值为 1 的位数」：

Φ(D) = 计数器中 1 的个数

核心说明：设第 i 次 INCREMENT 把 tᵢ 个 1 翻成 0（内层循环）、再把一个 0 翻成 1（若未溢出）。真实代价 cᵢ = tᵢ + 1。势能变化：少了 tᵢ 个 1、多了 1 个 1，即 ΔΦ = 1 − tᵢ。于是摊还代价：

ĉᵢ = cᵢ + ΔΦ = (tᵢ + 1) + (1 − tᵢ) = 2

辅助说明：每次 INCREMENT 的摊还代价**恰好等于 2**，与 tᵢ（这次翻了多少个 1）无关——这正是势能法优雅之处：昂贵操作（tᵢ 大）会让势能大幅下降，把真实开销「吃掉」，摊还值稳定在常数。初始 Φ(D_0) = 0（计数器全 0），Φ 恒非负，合法性满足，故 n 次 INCREMENT 摊还总代价 ≤ 2n = O(n)，三种方法在此彻底会合。（细节：计数器溢出时最高位从 1 变 0 但不再产生新的 1，此时 ΔΦ 更负、ĉᵢ ≤ 2 仍成立，不影响上界。）

我用势能法定义 ĉᵢ = cᵢ + ΔΦ 直接对计数器逐次累加，验证「摊还总和 = 2n 恰好、且是真实总代价的上界」：

```text
potential(counter): n=5000 sum_actual=9995 sum_amortized=10000 amort/n=2.0 (==2: True)
```

5000 次 INCREMENT：真实总代价 9995，势能法摊还总代价恰好 10000 = 2n，摊还每次恰好 2，且 10000 ≥ 9995 是真实总代价的上界，与理论完全吻合。

#### 来源与时效
- 锚点：CLRS 4th ed (2022) §16.3「The potential method」——摊还代价定义 ĉᵢ = cᵢ + Φ(Dᵢ) − Φ(D_{i-1})、总和 ∑ĉᵢ = ∑cᵢ + Φ(D_n) − Φ(D_0)、要求 Φ(Dᵢ) ≥ Φ(D_0) 方为上界；栈取 Φ = 元素数得摊还 2/0/0；二进制计数器取 Φ = 1 的个数得每次 INCREMENT 摊还恰为 2；核实 2026-07-26。
- 锚点：MIT 6.046J（Spring 2015）syllabus「Amortized Analysis」模块（阅读 CLRS Ch17）——势能法定义式与「Φ 非负则给上界」的框架、两例结论一致；核实 2026-07-26。
- 一致：两源对势能法定义式、望远镜相消、合法性条件、两例的 Φ 取法与摊还值（栈 2/0/0、计数器每次 2）完全一致；与 9.1/9.2 的 2n 上界一致。
- 实测：计数器 n=5000 势能法摊还总和恰 = 2n = 10000 ≥ 真实 9995，摊还每次恰 2（Python 3.11.15）。
- 成熟度：经典，稳定。

## 9.4 动态表

### 9.4.1 装载因子与动态表问题

动态表（dynamic table）是「按需自动伸缩容量」的表（对应现实里的可变长数组 / 动态数组，如 Python 的 list、C++ 的 vector）。用户只管插入和删除，不管底层数组多大；表在装满时自动申请更大的数组、在太空时自动缩小。衡量空间利用率的量叫**装载因子（load factor）**：

α(T) = T 中元素数 / T 的分配槽位数

核心说明：动态表的核心矛盾是——分配的数组是固定大小的，一旦装满就得「换一个更大的数组并把旧元素全部搬过去」，这次搬迁的代价是 O(当前元素数)，很贵。动态表要回答的问题是：如果扩容策略选得好，一串插入操作的**摊还**代价能不能做到 O(1)？答案是能。

辅助说明：装载因子 α 是理解伸缩策略的关键量。我们希望 α 别太小（否则浪费空间，比如只用了 1% 的数组）、也别频繁触发昂贵的搬迁。策略的艺术就在于「多久扩一次、扩多大」。下面先看只插入的情形（9.4.2、9.4.3），再看插入删除都有的情形（9.4.4）。

### 9.4.2 表扩张：倍增策略与聚合分析

扩容策略的关键选择是「扩多大」。**倍增策略**：当表满时，把容量翻倍（1 → 2 → 4 → 8 → …），并把所有旧元素搬到新数组。TABLE-INSERT 的伪代码框架是：

```text
TABLE-INSERT(T, x):
    if T.size == 0:
        allocate T with 1 slot; T.size = 1
    if T.num == T.size:              # 表满，触发扩容
        allocate newtable with 2 * T.size slots
        copy all T.num items into newtable   # 代价 T.num
        free old table; T.size = 2 * T.size
    insert x into T; T.num = T.num + 1        # 代价 1
```

核心说明：单次 TABLE-INSERT 的最坏代价是 Θ(n)（正好触发扩容、要搬走 n 个旧元素）。但从空表连续插入 n 次的**总代价是 O(n)**，故每次插入摊还 O(1)。

辅助说明：为什么倍增能把总代价压到线性？关键是**扩容发生的频率随规模指数级下降**。在 n 次插入中，扩容只在第 1, 2, 4, 8, …, 2^⌊lg n⌋ 次插入时发生，对应的搬迁代价是 1, 2, 4, 8, …，这是一个几何级数。n 次插入的总代价 = n 次「插入本身」的代价（共 n）+ 所有扩容搬迁的代价：

∑ 搬迁代价 = 1 + 2 + 4 + ⋯ + 2^⌊lg n⌋ < 2n

于是总代价：

T(n) < n + 2n = 3n = O(n)

每次插入摊还 O(1)。易错点：这个结论**强依赖「倍增」**。如果改成「每次满了只加固定 c 个槽位」（等差扩容），扩容会发生 Θ(n/c) 次、第 k 次搬迁代价 Θ(kc)，总代价退化成 Θ(n²)、摊还 Θ(n)——所以「翻倍」（几何增长）是关键，不能改成「加常数」。这也解释了为什么真实的动态数组实现都用「乘以一个 >1 的因子」扩容，而不是「加固定量」。

我实测各规模下从空表插入 n 次的总代价，验证 < 3n、摊还常数：

```text
dyn table doubling: n=      1 total_cost=      1 3n=      3 amort=1.0000 finalsize=1 (<3n: True)
dyn table doubling: n=    100 total_cost=    227 3n=    300 amort=2.2700 finalsize=128 (<3n: True)
dyn table doubling: n=   1000 total_cost=   2023 3n=   3000 amort=2.0230 finalsize=1024 (<3n: True)
dyn table doubling: n= 100000 total_cost= 231071 3n= 300000 amort=2.3107 finalsize=131072 (<3n: True)
```

各规模总代价都 < 3n，平摊每次插入 2~3（常数），符合摊还 O(1)。

### 9.4.3 表扩张的势能法

用势能法能更漂亮地得到同一结论。取势函数：

Φ(T) = 2 · T.num − T.size

核心说明：这个 Φ 设计成「刚扩容后 Φ = 0（此时 num = size/2，2·num − size = 0），随着插入把表填向满，Φ 线性涨到 num = size 时的 Φ = num」——正好在下一次扩容前把「搬迁所需的势能」攒够。可以验证 Φ(D_0) = 0 且在倍增策略下 Φ 始终非负（表至少半满，α ≥ 1/2，故 2·num ≥ size）。

辅助说明：逐个算摊还代价。不触发扩容的普通插入：num 加 1、size 不变，ΔΦ = 2，ĉ = 1 + 2 = 3。触发扩容的插入（插入前 num = size = m，扩容后 size = 2m）：真实代价 = m（搬迁）+ 1（插入）= m + 1，Φ 从 (2m − m) = m 变到 (2(m+1) − 2m) = 2，ΔΦ = 2 − m，摊还代价：

ĉ = (m + 1) + (2 − m) = 3

两种情形摊还代价都是 3——昂贵的扩容插入被之前攒的势能吃掉，摊还值稳定在常数 3，故 n 次插入摊还总代价 ≤ 3n = O(n)。

我用势能法 Φ = 2·num − size 对每次插入累加 ĉ = c + ΔΦ 验证：

```text
potential(dyntable): n=5000 sum_actual=13191 sum_amort=14999 max_amort_per_op=3? amort/n=2.9998
```

5000 次插入：真实总代价 13191，势能法摊还总和 14999 ≈ 3n（且 ≥ 真实总代价，是其上界），平摊每次约 3，与理论一致。

### 9.4.4 表的扩张与收缩

如果还允许删除，就希望表太空时缩小以省空间。一个看似自然但**错误**的策略是「装满就翻倍、半空（α < 1/2）就减半」。

核心说明：这个「满则倍增、半空则减半」的策略在最坏情形下会退化——因为可以卡在扩容/收缩的临界点反复横跳，每次操作都触发一次 O(n) 的搬迁，n 个操作总代价 Θ(n²)，摊还 Θ(n)，不再是常数。

辅助说明：怎么卡？让表恰好处在「满」的状态，然后交替执行「插入（触发翻倍，搬 n 个）、删除、删除（触发减半，搬回去）、插入…」——每一步都踩在阈值上触发一次整表搬迁。CLRS 的修正办法是**把收缩的阈值调低**：当装载因子降到 α < 1/4（而不是 1/2）时才把容量减半。这样扩容后 α = 1/2、收缩后 α = 1/2，无论刚扩还是刚缩，表都回到「半满」的舒适区，离下一次触发伸缩都还差「约一半的操作量」，攒够了势能。用势函数

Φ(T) = 2·T.num − T.size    （当 α ≥ 1/2 时）
Φ(T) = T.size/2 − T.num    （当 α < 1/2 时）

可以证明 INSERT 与 DELETE 的摊还代价都是 O(1)，故任意 n 个插入/删除混合操作总代价 O(n)。

关键结论式：

采用「满则倍增、α<1/4 则减半」策略，TABLE-INSERT 与 TABLE-DELETE 的摊还代价均为 O(1)

易错点：阈值取 1/4 是为了在扩容点（α=1/2）和收缩点（α=1/4）之间留出「缓冲带」，杜绝临界点反复横跳；若收缩阈值也取 1/2 就会退化。这个「扩容因子 2、收缩阈值 1/4」的不对称设计，正是现实动态数组库避免抖动的经典做法。

- 锚点：CLRS 4th ed (2022) §16.4「Dynamic tables」——装载因子 α = num/size；只插入时倍增策略下从空表 n 次插入总代价 < 3n（几何级数 ∑2ⁱ < 2n）、摊还 O(1)；势函数 Φ = 2·num − size 给每次插入摊还 3；插入+删除时「满则倍增、α < 1/4 则减半」策略配分段势函数得插入/删除均摊还 O(1)，而「α < 1/2 即减半」会退化到 Θ(n²)；核实 2026-07-26。
- 锚点：MIT 6.046J（Spring 2015）syllabus「Amortized Analysis」模块（阅读 CLRS Ch17）——动态表倍增摊还 O(1)、势能法 Φ = 2·num − size 结论一致；核实 2026-07-26。
