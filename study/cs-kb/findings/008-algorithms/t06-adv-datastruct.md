## 6.1 基本数据结构（CLRS 4e Ch10）

### 6.1.1 基于数组的结构：数组、矩阵、栈、队列

CLRS 4e §10.1 把「用一段连续数组直接实现」的几种结构放在一起讲：一维数组、二维矩阵（行主序/列主序的线性化）、栈、队列。这些是最基础的「容器」，本课关心的不是怎么写代码，而是它们各操作的时间代价与适用场景。

栈（stack）是后进先出（LIFO）：`PUSH` 压入、`POP` 弹出都在同一端。用数组加一个「栈顶下标 top」实现时，两个操作都是：

O(1)

队列（queue）是先进先出（FIFO）：`ENQUEUE` 在队尾入、`DEQUEUE` 在队头出。用数组实现要做成环形（circular）缓冲，用 head、tail 两个下标回绕，两个操作也都是：

O(1)

栈和队列的价值在于「用极简的接口约束访问顺序」，从而让很多算法（DFS 用栈、BFS 用队列、表达式求值、函数调用栈）写起来自然且每步 O(1)。

辅助说明（面向初学者）：为什么强调「同一端 / 两端」？想象一摞盘子——你只能从最上面拿或放，这就是栈；排队买票——先到的先走，这就是队列。数组实现的易错点有两个。其一，栈要判「下溢（underflow）」（空栈还 POP）和「上溢（overflow）」（满数组还 PUSH）。其二，队列如果只用普通数组「头出尾进」而不回绕，head 会一路右移、把前面的空间浪费掉，所以要用**环形**下标（tail = (tail+1) mod 长度）。这些结构与 L2-01 的实现课强重叠；本课记住「接口 + 每操作 O(1)」这一层即可。CLRS 4e 把矩阵的行/列主序也放在这一节，是为后面缓存/磁盘模型（B 树那章）埋「数据在内存里是线性排布的」这个伏笔。

### 6.1.2 链表

链表（linked list）用「每个元素带指针指向下一个（和上一个）」的方式把元素串起来，不要求内存连续。CLRS 4e §10.2 讲单向、双向、带哨兵（sentinel）的双向循环链表。核心操作的代价：

已知节点位置时，插入 / 删除：O(1)
按值查找 SEARCH：O(n)（最坏要走遍整条链）

链表用「不连续 + 指针」换来了「在已知位置处 O(1) 插删」，代价是「不能像数组那样 O(1) 随机下标访问，查找要顺着链走」。

初学者最该建立的对比是「数组 vs 链表」。数组：随机访问 O(1)、但中间插删要搬移后面所有元素 O(n)；链表：随机访问 O(n)、但已知位置插删 O(1)。选哪个取决于操作分布。哨兵（一个不存数据的「假头节点」）是个常用技巧：让空链表和非空链表、边界节点和中间节点的代码长得一样，省掉一堆 `if head == NULL` 的特判——这是易错点集中地，哨兵能显著减少边界 bug。双向链表比单向多一个「前驱指针」，代价是每个节点多存一个指针，好处是能 O(1) 地删除「已知的某个节点」（单向链表删一个节点还得先找到它的前驱）。

### 6.1.3 指针与对象的表示、有根树的表示

CLRS 4e §10.3 讲「怎么表示有根树」，并顺带交代在没有内建指针/对象的语言里如何用数组模拟指针（3e 曾有独立的「实现指针和对象」一节，4e 把这部分并入/精简了）。有根树的两类典型表示：

二叉树：每个节点存 `key`、`left`、`right`、`parent` 三个指针。
分支数不定的树（每个节点孩子数任意）：用「左孩子—右兄弟（left-child, right-sibling）」表示——每个节点只存两个指针：`left-child` 指向它的第一个孩子、`right-sibling` 指向它的下一个兄弟。

「左孩子—右兄弟」表示能用**每节点固定 2 个指针**装下**任意分支数**的树，避免了「不知道要留几个孩子指针」的麻烦。

初学者常卡在「孩子数不固定怎么办」。直觉是：与其给每个节点开一排长度不定的孩子指针，不如把「同一个父亲的孩子们」自己串成一条链（右兄弟指针），父亲只需记住「第一个孩子」。这样任意形状的树都用统一的两指针节点表示。这一节是后面所有树结构（BST、红黑树、B 树、区间树）的表示地基；也和 L2-01 的树实现重叠，本课点到「表示方式 + 为什么这么设计」即可。

## 6.2 散列表（CLRS 4e Ch11）

### 6.2.1 直接寻址表

直接寻址表（direct-address table）是散列表的退化前身：当键取自一个不大的全集 U = {0, 1, …, m−1} 时，直接开一个长度 m 的数组 T，键 k 就放在 T[k]。三个字典操作全是：

SEARCH / INSERT / DELETE：O(1)（最坏情形）

直接寻址用「键即下标」换来最坏 O(1)，但要求数组大小 = 全集大小 m。

这里的关键矛盾是**空间**。如果键是 64 位整数，全集有 2⁶⁴ 个，开这么大的数组不现实——哪怕实际只存几千个键。散列表就是为了解决这个矛盾：用一个「散列函数」把大全集压进一个小数组，代价是可能有两个键撞到同一格（碰撞）。所以直接寻址是「理想但费空间」，散列表是「省空间但要处理碰撞」。

### 6.2.2 散列表、链接法与装载因子

散列表（hash table）用散列函数 h 把键 k 映到槽位 h(k) ∈ {0,…,m−1}，数组长度 m 通常远小于键的全集大小。两个键映到同一槽叫**碰撞（collision）**。CLRS 4e §11.2 讲**链接法（chaining）**解决碰撞：每个槽挂一条链表，映到该槽的键都串在这条链上。

定义**装载因子（load factor）**：

α = n / m （n 个已存键，m 个槽）

在「独立均匀散列」假设下（见 6.2.3），链接法一次查找的期望时间：

Θ(1 + α)

链接法把碰撞的键串成链，一次查找的期望代价正比于「常数 + 平均链长 α」。当 α = O(1)（即 m 与 n 同阶）时，期望查找、插入、删除都是**期望 O(1)**。

初学者要抓住两点。第一，散列表的 O(1) 是**期望**的、有前提的，不是最坏的——最坏情形所有键都撞进同一个槽，退化成一条长度 n 的链，查找 Θ(n)。第二，α 的直觉就是「平均每个槽挂了几个键」。α = 1 意味着平均每槽一个；α = 10 意味着平均每条链 10 个，查找平均要走 10 步。所以实践中要控制 α 不太大（常见做法是超过某阈值就扩容、重散列，这条「倍增扩容」的摊还代价正是大主题9 §9.4 动态表的内容——两大主题在这里咬合）。

### 6.2.3 独立均匀散列假设（4e 术语）

分析散列表要有一个关于「散列函数把键散得多均匀」的假设。CLRS **4e 采用「独立均匀散列（independent uniform hashing）」**这一术语：假设每个键被独立地、等概率地映到 m 个槽中的任意一个。

P[h(k) = j] = 1/m，且不同键的散列值相互独立

这是一个**理想化假设**，用来做期望分析；现实中我们用「全域散列」（6.2.4）来在最坏输入下也逼近这种均匀性。

辅助说明（版本要点）：CLRS **3e 用的词是「简单均匀散列（simple uniform hashing）」**，4e 改成「独立均匀散列」并把假设讲得更精确（强调「独立」这一半）。这是一处实打实的术语升级，引用时要按版本用词，别把两版混着写。为什么需要「独立」？因为链接法分析里要对「其他键是否也落到某槽」求期望，只有独立才好算。初学者不必纠结哲学，记住：这是「为了能算期望而做的理想假设」，全域散列则是「不靠运气、用随机选函数把这个假设的效果坐实」的工程手段。

### 6.2.4 散列函数与全域散列

CLRS 4e §11.3 讲怎么造散列函数。经典启发式方法：

除法法：h(k) = k mod m （m 常取素数，避开 2 的幂）
乘法法：h(k) = ⌊m · (k·A mod 1)⌋ （A 为 0<A<1 的常数）

但任何固定的散列函数都有「最坏输入」——对手若知道函数，可以专挑全撞同一槽的键。**全域散列（universal hashing）**解决这个：不固定一个函数，而是从一族函数 H 中**随机**挑一个用。称 H 是全域的，若对任意两个不同的键 k ≠ l：

P_{h∈H}[h(k) = h(l)] ≤ 1/m

全域散列把「均匀性」从「对输入的假设」变成「对随机选择的保证」——不管对手给什么输入，只要函数是随机从全域族里选的，任意两键碰撞概率就 ≤ 1/m，于是期望性能与独立均匀散列同阶。

这是本章最重要的思想转变，也是「随机化算法」（大主题3）在数据结构里的一次现身。直觉：如果算法自己抛硬币决定用哪个散列函数，对手就无法「事先」构造坏输入，因为他不知道你会抽到哪个函数。一个经典全域族（乘法-移位/取模构造）由参数随机化生成。初学者记住结论即可：全域散列让「期望 O(1)」在**最坏输入**下依然成立（期望是对函数选择取的，不再依赖输入分布假设）。CLRS 4e 把全域散列放在 §11.3 内。

### 6.2.5 开放寻址

开放寻址（open addressing）是另一种解决碰撞的思路：**不挂链表**，所有元素都直接住在数组里；碰撞时按一个「探查序列（probe sequence）」依次试下一个槽，直到找到空槽。三种经典探查：线性探查、二次探查、双重散列。CLRS 4e 特别强调**线性探查**在现代硬件（缓存友好）上的实际高效。

在均匀散列假设下，装载因子 α<1 时，一次**不成功查找**的期望探查次数：

≤ 1 / (1 − α)

开放寻址把所有键塞进数组本体（无链表指针开销、缓存友好），代价是 α 必须 < 1（表满不下），且删除麻烦（不能简单清空一个槽，否则会截断别人的探查序列，要用「墓碑（DELETED 标记）」）。

直觉上 1/(1−α) 说明——α=0.5 时平均探查约 2 次，α=0.9 时约 10 次，α→1 时爆炸。所以开放寻址要留足空槽（保持 α 明显小于 1）。初学者易错点：开放寻址的删除。链接法删除只是从链上摘一个节点；开放寻址若把槽直接置空，会让原本「探查到这里继续往后」的键突然被判定为「查找失败」。解决办法是标记「已删除」而非「空」。为什么 4e 抬高线性探查地位？因为顺序访问相邻槽对 CPU 缓存友好，实测常比理论上「更均匀」的双重散列更快——这是「渐进分析之外还有常数因子/硬件因素」的一个好例子。

### 6.2.6 完美散列（含 4e 版本变更）

完美散列（perfect hashing）针对**静态键集**（键集合固定、不再变化，如编译器关键字表）：目标是构造一个**最坏情形 O(1)** 查找的散列方案。做法是**两级散列**——第一级把 n 个键散到若干桶，第二级对落入某桶的 nⱼ 个键用一个**二次大小**（约 nⱼ²）的表并选一个「在该桶内无碰撞」的全域散列函数。选得当时期望总空间：

O(n)，且查找最坏 O(1)

完美散列用「静态 + 两级 + 二次空间的第二级」把散列从「期望 O(1)」提升到「最坏 O(1)」；第二级取 nⱼ² 大小是因为——由生日悖论式的计数，n 个键散进 n² 大小的表，期望无碰撞。

辅助说明（版本变更，重要，避免张冠李戴）：**「完美散列」在 CLRS 3e 是独立小节 §11.5**；在 **4e 中该独立小节已从正文删除**——4e 的 §11.5 标题是「Practical considerations」（实践考量），不再是「Perfect hashing」（据官方 4e 目录逐字核对）。也就是说，若你手边是 4e 纸质正文，找不到标着「§11.5 Perfect hashing」的那一节，这不是你记错，是版本改了。完美散列的**概念本身与版本无关**（上面的两级构造、O(n) 空间、最坏 O(1) 结论仍成立），本报告据 3e §11.5 及经典文献陈述其概念；其在 4e 的确切落点（正文他处 / 出版社在线补充材料）本报告标**「待核」**、不编造 4e 章节号。

## 6.3 二叉搜索树（CLRS 4e Ch12）

### 6.3.1 二叉搜索树的性质

二叉搜索树（binary search tree, BST）是满足**搜索树性质**的二叉树：对任一节点 x，

左子树中所有键 ≤ x.key ≤ 右子树中所有键

这条「左小右大」的不变式让「中序遍历（inorder walk）」恰好按升序输出所有键，也让查找能像二分一样每步排除一侧子树。

初学者最该记的直觉是「BST = 让二分查找能动态插删的结构」。有序数组能二分查找 O(log n)，但插删要搬移 O(n)；BST 保住了「每步排除一半」的查找思路，同时插删只需改几个指针。中序遍历 O(n) 输出有序序列，是验证/调试 BST 的好工具（下文实测就用它对拍 sorted()）。注意「左小右大」是对**整棵子树**成立，不只是对直接孩子——这是易错点。

### 6.3.2 查询：搜索、最小/最大、前驱/后继

CLRS 4e §12.2 讲一族查询：`SEARCH`（找键）、`MINIMUM`（一路向左）、`MAXIMUM`（一路向右）、`SUCCESSOR`/`PREDECESSOR`（中序意义下的后继/前驱）。它们全都沿树的一条路径走，代价都是：

O(h) （h 为树高）

所有查询都是「沿一条根到叶方向的路径下行」，因此代价由树高 h 决定，而非节点数 n。

这就是「树高决定一切」的第一次出现。h 好则查询快，h 坏则查询慢——这正是后面红黑树（6.4）要把 h 强行压到 O(log n) 的动机。SUCCESSOR 的直觉：若右子树非空，后继是右子树的最小值；否则一路向上找到「第一个使当前节点位于其左子树」的祖先。初学者不必背代码，记住「查询 = 走一条路径 = O(h)」即可。

### 6.3.3 插入与删除

`TREE-INSERT` 像查找一样下行到一个空位挂上新节点；`TREE-DELETE` 分三种情形处理（被删节点无孩子 / 有一个孩子 / 有两个孩子——两孩子时用「后继替换」并借助 4e 的 `TRANSPLANT` 子过程接子树）。两者都是：

O(h)

插入总是发生在叶位置（下行到空位）；删除的难点是「两个孩子」的情形——用中序后继（右子树的最小值）替换被删节点，能维持搜索树性质。

删除的「两孩子」情形是本节唯一的坎。直觉：要删的节点若有两个孩子，不能直接摘，否则两棵子树没地方接；办法是找一个「值最接近、且方便挪」的替身——中序后继正好合适（它必无左孩子，挪起来简单），把它的键搬上来、再删掉那个（较简单情形的）后继节点。CLRS 4e 用统一的 `TRANSPLANT`（用一棵子树替换另一棵）把三种情形写清楚。同样，代价 = O(h)，再次落到「树高」这个命门上。

### 6.3.4 随机构建 BST 的期望高度

BST 的高度 h 可好可坏：若按随机顺序插入 n 个不同的键，最坏（如按升序插入退化成一条链）h = n−1；但**随机顺序**下期望高度很好。CLRS 4e §12.4 的定理：

随机构建 BST 的期望高度 = O(lg n)

n 个不同键的 n! 种插入顺序**等概率**时，得到的 BST 期望高度是 O(lg n)——即「平均而言 BST 是近似平衡的」，坏情形只在特意排布的输入下出现。

这是本章把「概率分析」（大主题3）用到数据结构的高价值例子。为什么随机顺序就平衡？直觉：只有当插入顺序「非常有序」（一直往一边长）才会退化，而随机顺序里这种极端排列占比极小，期望被拉到 O(lg n)。要点是——这解释了「为什么随便插的 BST 通常挺好用」，也说明「为什么不能依赖它」：一旦输入恰好有序（现实中很常见，如已排序数据导入），就退化成 O(n)。红黑树（6.4）就是为「不靠运气、最坏也 O(log n)」而生。

一个可选实测：随机排列插入建 BST，量测高度并与 ln n 比。

```text
BST n=1000:  avg height=20.4, ln n=6.91, ratio h/ln n=2.96, worst-case n-1=999
BST n=4000:  avg height=26.3, ln n=8.29, ratio h/ln n=3.17, worst-case n-1=3999
BST n=16000: avg height=32.2, ln n=9.68, ratio h/ln n=3.33, worst-case n-1=15999
```

高度稳定在约 3·ln n（比值随 n 缓慢变化、有界），远小于最坏的 n−1，与「期望高度 = O(lg n)」一致（Python 3.11.15/40 次随机试验取平均；这里量的是最深节点的边数）。这印证结论、但不替代多来源比对。

## 6.4 红黑树（CLRS 4e Ch13）

### 6.4.1 红黑性质与黑高

红黑树（red-black tree）是一种**自平衡 BST**：每个节点额外存一位颜色（红/黑），并满足 5 条**红黑性质**，从而保证高度始终 O(log n)。CLRS 4e §13.1 的五条性质：

1. 每个节点是红色或黑色。
2. 根节点是黑色。
3. 每个叶子（NIL 哨兵）是黑色。
4. 红节点的两个孩子都是黑色（即不存在两个相邻的红节点）。
5. 从任一节点到其各叶子的所有路径，含有**相同数目的黑节点**。

性质 5 中那个「黑节点数目」叫该节点的**黑高（black-height）**bh(x)。由这五条可证高度界：

一棵含 n 个内部节点的红黑树高度 h ≤ 2·lg(n + 1)

红黑五性质（尤其「无两红相邻」+「各路径黑数相等」）联合保证——最长路径至多是最短路径的两倍，于是 h = O(lg n)，从而所有 BST 操作降到最坏 O(lg n)。

初学者不必背证明，只需抓住「为什么这五条能保证平衡」的直觉。性质 5 说「每条根到叶路径黑节点一样多」；性质 4 说「红节点不能扎堆（红后必黑）」。两条合起来：一条路径上红节点最多和黑节点一样多，所以最长路径 ≤ 2 倍最短路径——树不会一边长得太离谱。黑高就是「路径上黑节点的计数」，是所有平衡论证的核心量。对照 6.3.4：BST 只有「随机时期望平衡」，红黑树是「任何插删序列下最坏也平衡」，这就是它值得多存一位颜色的原因。

### 6.4.2 旋转

旋转（rotation）是维持红黑性质的基本局部操作，它在 O(1) 时间内改变几个指针、**保持中序顺序不变**、只改变局部结构（谁在上谁在下）。左旋 `LEFT-ROTATE(x)` 的效果：

以 x 与其右孩子 y 为轴，把 y 提为子树根、x 降为 y 的左孩子，y 原来的左子树转挂到 x 的右边

一次旋转的代价：

O(1)

旋转是「在不破坏搜索树性质（中序不变）的前提下，O(1) 地调整树形」的原子操作；插入/删除后的所有再平衡都由若干次旋转 + 变色完成。

直觉——旋转像「把跷跷板的支点挪一格」，左右两边谁高谁低变了，但从左到右读出来的顺序没变（中序不变是关键，否则就不是 BST 了）。右旋是左旋的镜像。记住「旋转 O(1)、中序不变」这两点，就能理解为什么红黑树能在 O(log n) 里修复平衡：树高 O(log n)、每层至多常数次旋转/变色。

### 6.4.3 插入

先按普通 BST 把新节点插到叶位置并**染成红色**（染红是为了尽量少破坏性质——红节点不影响黑高），然后调用 `RB-INSERT-FIXUP` 沿根方向修复可能出现的「两红相邻」（违反性质 4）。修复用「变色 + 旋转」，总代价：

O(lg n)，其中旋转次数 O(1)（至多 2 次）

插入染红 → 可能违反「无两红相邻」→ 用 fixup 沿树上行修复；关键结论是**至多 2 次旋转**就能修好（其余是变色，变色沿路径上传但仍 O(lg n)）。

为什么新节点染红而不是染黑？因为染黑会立刻破坏性质 5（那条路径凭空多一个黑节点，黑高不齐），修起来更麻烦；染红只可能破坏性质 4（两红相邻），而这个用局部旋转+变色好修。fixup 分几种情形（叔叔节点是红还是黑、当前节点是内侧还是外侧），初学者记住「插入 = 普通插 + 染红 + 至多 2 次旋转修复」这个骨架即可，具体情形分类属实现细节（L2-01）。

### 6.4.4 删除

删除更复杂：先按 BST 删除，若**被删（或顶替）的节点是黑色**，会破坏黑高（某条路径少一个黑节点），需 `RB-DELETE-FIXUP` 修复。总代价：

O(lg n)，其中旋转次数 O(1)（至多 3 次）

删除的麻烦在于「删掉一个黑节点会让某条路径黑高少 1」，fixup 通过「把缺的那个黑色沿树上推 / 借兄弟子树的黑色」来补齐，最终至多 3 次旋转。

初学者只需把握「删红节点无害（黑高不变）、删黑节点才要修」这个判据，以及「插入至多 2 次旋转、删除至多 3 次旋转、两者都 O(lg n)」这组对比数字。删除 fixup 的情形分类比插入更多（兄弟红/黑、兄弟的孩子颜色组合），是本章最繁的实现部分——本课点名「删除也能 O(log n) 且旋转次数为常数」即可，逐情形推演归 L2-01。红黑树是 C++ `std::map`/`std::set`、Java `TreeMap` 等的底层，这也是它在工程上的分量所在。

## 6.5 扩张数据结构（CLRS 4e Ch17）

### 6.5.1 动态顺序统计与顺序统计树

「扩张（augmenting）」指在已有结构（这里是红黑树）上**附加额外信息**，以支持新操作，同时不破坏原操作的复杂度。CLRS 4e §17.1 的例子是**顺序统计树（order-statistic tree）**：给红黑树每个节点 x 加一个字段

x.size = 以 x 为根的子树中的节点总数

有了 size，可支持两个动态顺序统计操作，都在 O(lg n)：

OS-SELECT(x, i)：返回子树中第 i 小的元素
OS-RANK(T, x)：返回 x 在中序（升序）中的排名

给平衡 BST 每个节点存「子树大小」，就能 O(lg n) 地回答「第 i 小是谁」「某元素排第几」——这是大主题5「顺序统计量」的**动态版**（支持插删的同时查第 k 小）。

直觉——OS-SELECT 靠 size 做「带权二分」：看左子树有 r = left.size + 1 个节点，若 i = r 当前节点就是答案；i < r 往左找第 i 小；i > r 往右找第 (i−r) 小。这正是把「静态数组里 O(1) 取第 i 小」升级为「动态集合里 O(log n) 取第 i 小」。关联：大主题5 的 SELECT 是一次性静态选择；这里是可插删的动态结构，代价从 O(n) 一次性降为每次 O(log n)。

可选实测：把顺序统计的 rank 查询与暴力计数对拍应恒相等（本报告对 BST 侧已在 6.3.4 实测；扩张字段的正确性由「插删时同步维护 size」保证，属实现层）。

### 6.5.2 如何扩张一个数据结构

CLRS 4e §17.2 给出扩张的**方法论**（一条可套用的定理式步骤），核心判据是：

若新增字段 f(x) 只依赖 x 的信息与 x 的孩子的字段 f(x.left)、f(x.right)，则插入/删除（含旋转）时可在 O(1) 内局部更新 f，从而不改变原操作的 O(lg n) 复杂度

扩张能「免费」（不升渐进阶）的充要直觉是——附加字段必须能**由孩子的字段在 O(1) 内合成**，这样旋转/插删只需局部修几处，不必全树重算。

这是本章最有迁移价值的一课——它不是某个具体结构，而是「怎么给结构加功能」的通法。四步：选底层结构（如红黑树）→ 定要维护的附加信息 → 验证插删旋转能 O(1) 维护它 → 用它实现新操作。size 满足「= left.size + right.size + 1」，正是「由孩子字段 O(1) 合成」，所以顺序统计树不升阶。反例警示：若某字段需要遍历整棵子树才能算（无法由孩子字段合成），扩张就会拖慢原操作——这是设计时的易错点。

### 6.5.3 区间树

CLRS 4e §17.3 用扩张法造**区间树（interval tree）**：底层红黑树，键为区间左端点，每个节点附加字段

x.max = 以 x 为根的子树中所有区间右端点的最大值

支持 `INTERVAL-SEARCH(T, i)`：找一个与给定区间 i 重叠的区间，代价：

O(lg n)

区间树是 6.5.2 方法论的实例——附加 max（可由孩子 O(1) 合成：max = 三者取大），即可 O(log n) 查询「哪个已存区间与查询区间重叠」。

直觉——搜索时在每个节点用 max 判断「往左子树还能不能找到重叠」：若左子树的 max < 查询区间左端点，则左子树所有区间都太靠左、不可能重叠，直接转右。这样每步排除一侧，O(log n) 结束。应用场景：日程冲突检测、基因组区间查询等。关联回 6.5.2：max 满足「由孩子字段 O(1) 合成」，所以又是一次「不升阶的扩张」。

- 锚点：CLRS 4th ed (2022) §17.1「Dynamic order statistics」（size 字段、OS-SELECT/OS-RANK，O(lg n)）、§17.2「How to augment a data structure」（扩张方法论、O(1) 局部维护判据）、§17.3「Interval trees」（max 字段、INTERVAL-SEARCH O(lg n)）；核实 2026-07-26。
- 锚点：MIT 6.046J (Spring 2015) syllabus「Augmenting Data Structures / Order Statistics, Interval Trees」——与 CLRS 结论一致（顺序统计树、区间树均基于红黑树扩张，操作 O(log n)）。核实 2026-07-26。

## 6.6 B 树（CLRS 4e Ch18）

### 6.6.1 磁盘模型与 B 树的动机

B 树（B-tree）是为**磁盘（或其他二级存储）**设计的多路平衡搜索树。前提是一个成本模型：读一次磁盘（一个「页/块」）远比 CPU 计算慢，因此代价主要看**磁盘访问次数**，而非比较次数。CLRS 4e §18 引言用这个模型引出 B 树。

B 树的设计目标是**把树高压到极低**（每个节点存很多键、有很多孩子），从而用尽量少的磁盘读取完成查找——树高 ≈ 磁盘访问次数。

为什么二叉树（红黑树）不适合磁盘？因为二叉树每个节点只有 2 个孩子、树高约 log₂n；n=10 亿时 h≈30，意味着约 30 次磁盘读，每次读几毫秒就很慢。B 树让一个节点装几百上千个键（正好填满一个磁盘页），扇出（fan-out）大、树高就低到个位数。这是「让数据结构去适配硬件成本模型」的典范，与 6.2.5 抬高线性探查（缓存友好）同源——渐进阶之外，常数与访存模式也要算进设计。B 树是数据库索引、文件系统（如 B+ 树变体）的核心，下游 L4-03 数据库会大量消费。

### 6.6.2 B 树的定义与高度

CLRS 4e §18.1 用**最小度数（minimum degree）t ≥ 2** 定义 B 树。除根外每个节点：

键数 ≥ t − 1，孩子数 ≥ t
键数 ≤ 2t − 1，孩子数 ≤ 2t

且所有叶子在同一层（完美高度平衡）。含 n 个键的 B 树高度：

h ≤ log_t( (n + 1) / 2 )

t 控制「每个节点多胖」；节点越胖（t 越大）扇出越大、树高 h ≤ log_t((n+1)/2) 越低，磁盘访问越少。

初学者抓两点。第一，「除根外键数 ≥ t−1」这条下界保证节点不会太空，从而树高有上界（不会退化）；「≤ 2t−1」是上界，超了就要分裂。第二，log_t 里底数是 t 而非 2——这正是 B 树相对二叉树的高度优势来源。一个可选数值感受（h ≤ log_t((n+1)/2)）：

```text
B-tree t=2,   n=10^9: height bound = 28.90
B-tree t=50,  n=10^9: height bound = 5.12
B-tree t=500, n=10^9: height bound = 3.22
```

同样 10 亿个键，t=2（退化成类二叉）要约 29 层，t=500 只要约 3 层——差别就是磁盘访问次数从约 29 降到约 3。这直观解释了「胖节点 = 浅树 = 少磁盘 I/O」。

### 6.6.3 基本操作：搜索、分裂与插入

CLRS 4e §18.2 讲搜索、创建、插入。搜索像多路 BST（在节点内的有序键里定位、再下到对应孩子）。插入用**主动分裂（proactive split）**：一趟下行时，遇到「满节点（2t−1 个键）」就先分裂它，保证插入点的父节点不满。各操作的代价：

磁盘访问：O(h) = O(log_t n)
CPU 时间：O(t · log_t n)

分裂一个满孩子（2t−1 键）：把它的**中间键**上提到父节点，左右各 t−1 键分成两个节点，O(1) 次磁盘写

B 树用「下行途中先分裂满节点」的单趟策略，让插入只需 O(log_t n) 次磁盘访问；分裂是把满节点的中位键上提、左右对半劈，是维持「键数 ≤ 2t−1」不变式的原子操作。

为什么「下行时就分裂」而不是「插到底再回溯分裂」？因为提前分裂保证了「当你要往某节点插键时，它的父节点一定不满、能接住上提的中位键」，从而一趟到底、不必回溯，磁盘访问减半。分裂的直觉：一个节点太胖（2t−1 键）就「一分为二」，中间那个键升级去父节点当分隔。初学者记住「搜索/插入都是 O(log_t n) 次磁盘访问、分裂上提中位键」即可。

### 6.6.4 从 B 树删除键

CLRS 4e §18.3 讲删除，对称于插入的「主动分裂」，删除用**主动合并/借键（保证不下溢）**：下行时保证要进入的孩子键数 ≥ t（即删掉一个后仍 ≥ t−1），不够就先向兄弟「借一个键」或与兄弟「合并」。代价同样：

磁盘访问：O(h) = O(log_t n)

删除的不变式风险是「节点键数掉到 t−1 以下（下溢）」；B 树在下行途中用「借键（兄弟富余就转移一个）」或「合并（兄弟也刚好 t−1 就并成一个 2t−1 的节点）」提前保证目标节点够胖，从而一趟删完、O(log_t n) 磁盘访问。

删除是 B 树最细的操作，情形较多（删的键在叶还是内部、兄弟能否借），但核心对偶很清楚：插入怕「太满」→ 分裂；删除怕「太空」→ 借或合并。初学者掌握这个对偶 + 「都是 O(log_t n) 磁盘访问」即可；逐情形推演属实现层（L2-01 / 数据库课）。变体 B+ 树（数据只存叶、内部只存索引，叶间串链表便于范围扫描）是数据库/文件系统的实际主力——归下游 L4-03，本课点名。

## 6.7 不相交集合（并查集）（CLRS 4e Ch19）

### 6.7.1 不相交集合操作

不相交集合（disjoint sets）数据结构（俗称**并查集，union-find**）维护一族互不相交的动态集合，支持三种操作（CLRS 4e §19.1）：

MAKE-SET(x)：建一个只含 x 的新集合
UNION(x, y)：把含 x 与含 y 的两个集合并成一个
FIND-SET(x)：返回 x 所在集合的「代表元（representative）」

并查集回答「x 和 y 是否在同一集合」（比较各自 FIND-SET 的代表元是否相同），并支持把两个集合合并——它是「动态连通性」类问题的基础工具。

典型应用是 Kruskal 最小生成树（大主题11：加一条边前先 FIND-SET 判两端是否已连通，避免成环）、连通分量维护、图像连通域标记等。直觉：把「同一集合」想成「同一个朋友圈」，代表元是这个圈的「圈主」；FIND-SET 就是「你的圈主是谁」，UNION 就是「两个圈合并、认一个共同圈主」。

### 6.7.2 链表表示与「按大小合并」

CLRS 4e §19.2 先给一个简单实现：每个集合用一条链表，表头是代表元，每个元素有指针指回代表元。此实现里 FIND-SET 是 O(1)（直接读回指针），但 UNION 要把一条链表的所有元素的「代表指针」改指向另一条的表头，朴素做很慢。用**按大小合并的加权启发式（weighted-union，总把短表并入长表）**后，m 次操作（其中 n 次 MAKE-SET）的总代价：

O(m + n·lg n)

链表表示下，UNION 的瓶颈是「改指针」；「总把小集合并进大集合」这个加权启发式，保证每个元素的代表指针至多被改 O(lg n) 次，从而把总代价压到 O(m + n lg n)。

为什么「小并大」能限制改指针次数？因为一个元素每次「被改指针」时，它所在集合的大小至少翻倍（它从小集合并入了不小于自己集合的大集合）；大小最多翻 lg n 次就到 n 封顶，所以每个元素至多被改 lg n 次。这是一个漂亮的摊还论证雏形（大主题9 的思想在这里预演）。不过这还不是最优——森林表示（下一节）更快。

### 6.7.3 不相交集合森林：按秩合并 + 路径压缩

CLRS 4e §19.3 给出更快的**不相交集合森林（disjoint-set forest）**：每个集合是一棵树，每个节点只存一个「指向父节点」的指针，树根是代表元。配两个启发式：

按秩合并（union by rank）：合并时让「秩（rank，树高的上界估计）」小的根挂到秩大的根下
路径压缩（path compression）：FIND-SET 找根的途中，把路径上所有节点直接改挂到根上

森林表示把 UNION/FIND 都变成「沿父指针走到根」；「按秩合并」防止树长歪、「路径压缩」把走过的路一次性拍扁，两者合用带来近乎常数的摊还代价（见 6.7.4）。

两个启发式缺一威力大减——只按秩合并（不压缩）：O(m lg n)；只路径压缩（不按秩）：也约 O(m log n) 级；**两者合用**才降到近线性（6.7.4）。直觉：按秩合并保证树一开始就矮；路径压缩让「查过一次的节点下次直接够到根」，越查越平。注意「秩」只是树高的上界（因为路径压缩会让实际树高变矮但秩不减），所以叫 rank 而非 height。

可选实测：森林 + 按秩合并 + 路径压缩，统计 FIND 沿父指针走的步数与总操作数之比。

```text
DSU n=10000:  total ops m=19999,  find parent-steps=19995,  steps/m=1.000
DSU n=40000:  total ops m=79999,  find parent-steps=79998,  steps/m=1.000
DSU n=160000: total ops m=319999, find parent-steps=319997, steps/m=1.000
```

n 放大 16 倍，每次操作的平均「走父指针步数」始终约 1.0（不随 n 增长），直观印证「每操作摊还近乎常数」（Python 3.11.15；随机 union 一条生成链 + n 次随机 find）。这印证近线性、但不替代下节的理论界。

### 6.7.4 逆 Ackermann 函数与近线性分析

CLRS 4e §19.4（标题「Analysis of union by rank with path compression」）证明：森林表示 + 按秩合并 + 路径压缩下，一串 m 次操作（含 n 次 MAKE-SET）的总代价：

O(m · α(n))

其中 α(n) 是**逆 Ackermann 函数**，增长极其缓慢。Ackermann 函数 Aₖ(j) 定义为：

A₀(j) = j + 1
Aₖ(j) = Aₖ₋₁^(j+1)(j)， 对 k ≥ 1（把 Aₖ₋₁ 迭代作用 j+1 次）

α(n) 定义为：

α(n) = min{ k : Aₖ(1) ≥ n }

由于 Aₖ(1) 增长快到离谱（A₄(1) 已远超可观测宇宙的原子数），对**一切现实的 n**：

α(n) ≤ 4

这是本大主题理论上的巅峰结论——最优的并查集每操作**摊还 O(α(n))**，而 α(n) 在任何现实规模下 ≤ 4，故「几乎是常数」（但严格说**不是** O(1)，α(n) 确实随 n 无界增长，只是慢到不可思议）。

初学者最容易误记成「并查集是 O(1)」——严谨表述是「摊还 O(α(n))，实践中因 α(n)≤4 而形同常数，但理论上非常数」。α(n) 为什么这么小？因为 Ackermann 是已知增长最快的「原始递归可定义」函数之一，它的逆自然就是增长最慢的之一。数值感受：A₄(1) 是一个塔状指数（2 的 2 的 2 的…幂，塔高本身就很大），要 n 大到这种天文数字，α(n) 才会取到 5。所以在任何真实计算机上，把并查集当「每操作常数」用是安全的，只是在算法分析里要如实写 O(m α(n))。这也是本课「重分析」的价值点：同一个结构（并查集）在 L2-01 讲实现，在这里讲「为什么它近乎常数、那个 α 到底是什么」。

本节汇总本大主题与相邻课程的边界，便于读者知道「本课讲到哪、更深的去哪门课」。

散列表、平衡搜索树、并查集这三类结构与 **L2-01 数据结构强重叠**：L2-01 讲**实现与逐操作代码**（怎么写旋转、怎么处理开放寻址删除、怎么维护并查集父指针），本课（L3-01）讲**分析与选型/正确性论证**——期望界（散列 Θ(1+α)、随机 BST 期望高度 O(lg n)）、最坏界（红黑树 O(log n)）、摊还界（动态表倍增、并查集 O(m α(n)））、以及各结构的适用场景与设计权衡（数组 vs 链表、链接法 vs 开放寻址、二叉平衡树 vs B 树的磁盘模型）。
