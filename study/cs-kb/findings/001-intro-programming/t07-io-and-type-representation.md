## 7.1 格式化输出 printf

### 7.1.1 printf 与格式串的角色

`printf`（print formatted）是 C 标准库 `<stdio.h>` 里最常用的输出函数：第一个参数是**格式串**（format string），其后跟零个或多个实参。格式串里普通字符原样输出，而以 `%` 开头的**转换说明符**（conversion specifier）是占位符，运行时被对应实参的值按指定格式替换。


    printf("x = %d, name = %s\n", 42, "abc");

输出 `x = 42, name = abc` 并换行。这里 `%d` 吃掉实参 `42`（按十进制整数打印），`%s` 吃掉 `"abc"`（按字符串打印），`\n` 是换行转义。给初学者的关键直觉：**`printf` 是「变参函数」——它自己不知道你到底传了几个、什么类型的实参，全靠格式串「声明」**。也就是说格式串是你和函数之间的一纸合同，函数完全信任这份合同去内存里取值。合同写错（说符与实参类型对不上），后果自负（见 7.1.4）。

### 7.1.2 转换说明符与类型对应表

每个转换说明符对应一类实参类型。最常用的一组（C11 §7.21.6.1）——

    %d, %i   int（十进制有符号整数）
    %u       unsigned int（十进制无符号）
    %o       unsigned int（八进制）
    %x, %X   unsigned int（十六进制，小写/大写）
    %f, %F   double（定点小数）
    %e, %E   double（科学计数法）
    %g, %G   double（自动在 %f/%e 间择优）
    %c       int（按字符输出，实际取一个字符）
    %s       char *（以 '\0' 结尾的字符串）
    %p       void *（指针地址，实现定义格式）
    %%       输出一个字面的百分号

**浮点没有单独的 `float` 说符——`%f` 期望的是 `double`**。原因是变参函数会对实参做「默认实参提升」（default argument promotions）：`float` 自动升为 `double`、`char`/`short` 自动升为 `int`。所以传一个 `float` 给 `%f` 恰好能工作（它已被提升成 `double`），也因此不存在 `%f` 之外的「float 版」。

本机实测（`gcc -std=c11 -Wall`，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）印证了这条与几个常用说符：

    d=3.141590  d=3.14
    f (promoted to double) via %f -> 1.500000
    c=A code=65
    size_t via %zu -> sizeof(int)=4

`%.2f` 里的 `.2` 是精度字段（保留 2 位小数）；同一个 `double` 用 `%c`/`%d` 那种「打字符/整数」的说符则会错位——务必让说符与实参类型匹配。

### 7.1.3 长度修饰符

当实参不是「默认的」`int`/`double`，而是更宽或更窄的整数、或 `size_t` 这类平台相关类型时，要在说符里加**长度修饰符**（length modifier）告诉 `printf` 实参的确切宽度：

    %ld   long              %lld  long long
    %hd   short             %hhd  signed char
    %lu   unsigned long     %zu   size_t
    %zd   ssize_t/有符号 size_t   %Lf   long double

这里最实用的是 `%zu`：`sizeof` 的结果类型是 `size_t`（无符号、平台相关，本机 LP64 下是 64 位），用 `%d` 打印 `sizeof(...)` 在 64 位机上就是类型不匹配（错位/UB），正确写法是 `%zu`。上一节实测里 `sizeof(int)=4` 正是用 `%zu` 打印的。给初学者的规则：**打印 `long` 用 `%ld`、打印 `sizeof`/长度用 `%zu`，别一律用 `%d`**。

### 7.1.4 类型不匹配 = 未定义行为

如果转换说符与对应实参的类型不匹配（如用 `%d` 去打印一个 `double`，或用 `%s` 打印一个整数），行为是**未定义的**（undefined behavior，C11 §7.21.6.1 明确规定）。

未定义意味着：可能打印出垃圾数字、可能崩溃、也可能「碰巧看起来对」——但都不可依赖。直觉上为什么会这样：`printf` 按格式串「以为」的类型去内存/寄存器里取实参，如果实际类型宽度或存放位置不同（比如 `double` 是 8 字节走浮点寄存器，`%d` 却按 4 字节整数去取），取到的就是错位的字节，解释出来自然是乱的。

**开 `-Wall`（甚至 `-Wformat`），让编译器帮你查格式串**。gcc 的 `-Wformat`（`-Wall` 默认含）能在编译期发现大量 `printf`/`scanf` 的说符↔实参不匹配，把一类隐蔽的运行期 UB 提前到编译期警告。这是入门期最划算的一道防线。

#### 来源与时效（本小主题末集中列）
- 一手锚点：K&R 2nd ed Ch7 §7.2「Formatted Output — Printf」（格式串、转换说明、宽度/精度）。C11 §7.21.6.1「The fprintf function」（转换说明符表、长度修饰符、`%%`；明确「若转换说明与实参类型不符则行为未定义」；变参的默认实参提升见 §6.5.2.2 函数调用）。核实 2026-07-26。
- 比对结论：K&R 与 C11 对 `%d/%u/%x/%f/%c/%s/%p` 语义一致；C11 增补了 `%zu`（`z` 长度修饰符，C99 起）与更严格的 UB 措辞，K&R(C89) 无 `z` 修饰符（`size_t` 打印在 C89 需强转为 `unsigned long` 用 `%lu`）——这是版本 delta，非分歧。
- 实测坐实：`%f` 接收被提升的 `float`（输出 1.500000）、`%zu` 打印 `sizeof(int)=4`——本机真实输出（基线串见正文）。
- 冲突/易混点：「`float` 无独立说符、`%f` 吃 `double`」源于变参默认实参提升，非 printf 特例（易被误记为「printf 特殊」）。

## 7.2 格式化输入 scanf 与陷阱

### 7.2.1 scanf 基本用法与转换说明

`scanf`（scan formatted）是 `printf` 的输入对偶：从标准输入按格式串解析文本，把解析出的值**存进实参所指向的内存**。转换说明与 `printf` 大体对称：

    %d   读一个十进制 int          %u   unsigned int
    %ld  读一个 long               %lf  读一个 double（★注意）
    %f   读一个 float              %c   读一个字符
    %s   读一个「空白分隔的词」      %x   读十六进制到 unsigned

一个和 `printf` 不对称、极易错的点：**读浮点时，`float` 用 `%f`、`double` 必须用 `%lf`**。这与 `printf` 不同（printf 里 `%f`/`%lf` 都吃 double，因为有默认实参提升；但 scanf 传的是指针，指针不被提升，所以必须精确区分 `float*` 用 `%f`、`double*` 用 `%lf`）。初学者若对一个 `double` 变量用 `%f` 读入，是类型不匹配的 UB。

### 7.2.2 `&` 的必要性

`scanf` 要把值「写回」调用者的变量，就必须拿到变量的**地址**，所以除字符串外，实参通常要写成 `&变量`：

    int n;
    scanf("%d", &n);     /* 正确：传 n 的地址，scanf 才能写入 n */

如果漏写 `&`，写成 `scanf("%d", n)`，传进去的是 `n` 里那个「未初始化的垃圾值」被当成地址，`scanf` 往那个随机地址写数据——典型的未定义行为，常见后果是崩溃。这正是本主题先修「大主题6 指针」的原因：`&` 取地址、`scanf` 通过指针写回，是「传址修改」的直接应用。

数组名（含 `char` 字符串数组）本身就退化为地址，所以 `scanf("%s", buf)` 里 `buf` 不加 `&`（它已经是地址）。

### 7.2.3 返回值检查

`scanf` 返回**成功赋值的转换项个数**；遇到输入结束（EOF）且未完成任何转换时返回 `EOF`（通常是 −1）。这个返回值是判断「输入是否读成功」的唯一可靠手段，初学者最常忽略。

本机实测（`gcc -std=c11 -Wall`，程序对 `scanf("%d",&n)` 打印返回值，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）：

    --- good input '42' ---
    scanf returned 1, n=42
    --- bad input 'abc' (conversion fails, returns 0) ---
    scanf returned 0, n=-999
    --- EOF (empty input, returns EOF=-1) ---
    scanf returned -1, n=-999

可见：正常读到一个整数返回 `1`；喂非数字 `abc` 时转换失败返回 `0`（且 `n` 未被赋值，仍是原值）；空输入（EOF）返回 `-1`。给初学者的铁律：**永远检查 `scanf` 的返回值**，例如 `if (scanf("%d",&n) != 1) { /* 处理输入错误 */ }`，否则会拿一个没被赋值的垃圾变量继续算。

### 7.2.4 空白与「卡住」陷阱

`scanf` 的数值/字符串转换（`%d`/`%f`/`%s`）会**自动跳过前导空白**（空格、制表、换行）；但 `%c` **不跳空白**——它会把上一次输入残留的换行符当成一个字符读走。这就是初学者写「先读数字再读一个字符」时经常发现 `%c` 读到的是回车而不是想要的字符的原因。常见修法是在 `%c` 前留一个空格 `scanf(" %c", &ch)`，那个空格表示「先跳过任意空白」。

转换失败时，出错的字符**留在输入缓冲里不会被消耗**，若循环里不清理，会造成同一坏输入被反复读、程序「卡死循环」。入门期先记住「检查返回值 + 出错时清理输入」即可，机制细节不在本报告纵深。

#### 来源与时效（本小主题末集中列）
- 一手锚点：K&R 2nd ed Ch7 §7.4「Formatted Input — Scanf」（格式串、`&` 传地址、返回值=成功匹配项数、空白处理）。C11 §7.21.6.2「The fscanf function」（转换说明、`%lf` 读 double 与 `%f` 读 float 的区分、返回值为成功赋值个数或 `EOF`、`%c` 不跳空白）。核实 2026-07-26。
- 比对结论：K&R 与 C11 一致；C11 措辞更精确地区分 `%f`(float*) vs `%lf`(double*)——K&R 也如此要求，非分歧。
- 实测坐实：返回值 1/0/−1（好输入/坏输入/EOF）为本机真实输出（基线串见正文）。
- 冲突/易混点：scanf 的 `%lf`(double) vs printf 的 `%f`(double) 不对称——根因是 scanf 传指针不受默认实参提升影响（易混，两条来源均支持此解释，非冲突）。

## 7.3 标准流与字符 I/O

### 7.3.1 三个标准流：stdin / stdout / stderr

C 程序启动时自动打开三个**标准流**（`<stdio.h>` 提供，类型 `FILE *`）：

    stdin    标准输入（默认：键盘）
    stdout   标准输出（默认：屏幕；行缓冲/全缓冲）
    stderr   标准错误（默认：屏幕；不缓冲，供诊断信息）

`printf(...)` 等价于 `fprintf(stdout, ...)`；`scanf(...)` 等价于 `fscanf(stdin, ...)`。为什么把「正常输出」和「错误信息」分成 `stdout`/`stderr` 两股？因为这样用户可以**只重定向其中一股**——把程序的正常结果存进文件，同时让错误信息仍显示在屏幕上。

本机实测（程序分别向 stdout/stderr 各写一行，把 stdout 重定向到 `/dev/null`，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）：

    --- redirect stdout to /dev/null, only stderr shows ---
    this goes to stderr

可见 `./streams 1>/dev/null` 把标准输出丢弃后，只剩 stderr 的那行显示——证实两股流是独立的。给初学者的直觉：**诊断/错误信息应写 stderr（`fprintf(stderr,...)`），正常数据写 stdout**，这样管道和重定向才干净。

### 7.3.2 getchar / putchar 与 EOF

`getchar()` 从 stdin 读**一个字符**并返回；`putchar(c)` 向 stdout 写一个字符。二者是最基础的「逐字符 I/O」。

一个初学者必须理解的关键点：**`getchar()` 的返回类型是 `int`，不是 `char`**。因为它要能返回一个不同于任何有效字符的哨兵值 `EOF`（end of file，通常为 −1）来表示「读完了」。如果用 `char` 接收，`EOF` 可能与某个合法字符（尤其 0xFF）混淆，导致循环无法正确终止。所以标准写法是：

    int ch;
    while ((ch = getchar()) != EOF) putchar(ch);

本机实测（大写过滤器 `while((ch=getchar())!=EOF) putchar(toupper(ch));`，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）：

    HELLO WORLD

输入 `hello world` 被逐字符读入并转大写输出——这就是经典的「读到 EOF 为止」循环骨架。

### 7.3.3 管道与重定向

Unix shell 提供三种把标准流「接到别处」的方式，这也是标准流设计的价值所在：

    prog < in.txt      把 stdin 接到文件 in.txt
    prog > out.txt     把 stdout 接到文件 out.txt（覆盖）
    prog1 | prog2      把 prog1 的 stdout 接到 prog2 的 stdin（管道）

**程序本身不需要知道输入来自键盘还是文件、输出去屏幕还是管道**——它只管读 stdin、写 stdout，「接到哪」由 shell 决定。上面 7.3.2 的大写过滤器 `echo "hello world" | ./up`，正是 `echo` 的输出经管道成为过滤器的输入。这种「小程序 + 管道组合」是 Unix 哲学的核心，也是为什么标准流被设计成默认存在的三股。

### 7.3.4 缓冲的入门直觉

标准输出通常是**缓冲**的：数据先攒在内存缓冲区里，到一定量或遇到换行（终端下常为行缓冲）才真正写出。stderr 一般**不缓冲**（错误要立刻可见）。初学者会遇到的现象：程序崩溃前用 `printf` 打的信息「没出现」，往往是因为还在缓冲区里没刷出。入门期知道用 `\n` 或 `fflush(stdout)` 触发刷新即可，缓冲机制的纵深不在本报告范围。

- 一手锚点：K&R 2nd ed Ch7 §7.1「Standard Input and Output」（stdin/stdout、getchar/putchar、EOF、重定向与管道）、§7.5「File Access」（stderr 概念）、Ch1 §1.5（字符 I/O 与 EOF 循环骨架）。C11 §7.21.3「Files」（流与缓冲：全缓冲/行缓冲/无缓冲）、§7.21.1（`stdin`/`stdout`/`stderr` 宏、`EOF` 宏）、§7.21.7.6「The getchar function」/§7.21.7.9「The putchar function」（返回 `int`、EOF 语义）。核实 2026-07-26。

## 7.4 整型表示入门

### 7.4.1 位宽与取值范围

一个整数类型能表示多少个不同的值，由它的**位宽**（bit width）决定：`N` 位能表示 `2^N` 个不同的位模式。

    N 位无符号：范围 0 .. 2^N − 1
    N 位有符号（补码）：范围 −2^(N−1) .. 2^(N−1) − 1

本机（x86-64 System V / LP64）常见宽度：`char` 8 位、`short` 16 位、`int` 32 位、`long`/`long long` 64 位（具体字节数属实现定义，见大主题1）。所以 32 位有符号 `int` 的范围是 −2³¹ .. 2³¹−1，即 −2147483648 .. 2147483647。给初学者的直觉：**位宽就是「盒子有几个二进制开关」，开关数决定能数到多大；超出就「溢出」回绕**（有符号溢出在 C 里是未定义行为，见大主题2；无符号溢出是良定义的模 2^N 回绕）。

### 7.4.2 有符号 vs 无符号

同样的 `N` 个位，可以解释成「无符号」（全部用来表示非负数）或「有符号」（拿出一位区分正负，用补码编码）。**同一串位模式，按有符号还是无符号解释，得到的数可能完全不同**。

例如 8 位的 `11111111`：按无符号读是 255，按有符号（补码）读是 −1。这就是大主题1 里「有符号/无符号混合运算」陷阱的根源——负数被转成无符号时，那串位不变，但被重新解释成一个很大的正数。给初学者的直觉：**位模式是死的，「有无符号」只是你戴哪副眼镜去看它**。

### 7.4.3 补码（two's complement）直觉

有符号整数在几乎所有现代机器（含本机 x86-64）用**补码**表示：非负数就是普通二进制；负数 `−x` 的位模式等于「`x` 按位取反再加 1」，等价地也等于 `2^N − x`。

    −1 的 N 位补码 = 全 1（每一位都是 1）
    −x 的位模式  = (~x) + 1

补码的好处（为什么大家都用它）：加减法不用区分正负号，同一套二进制加法电路就能算有符号和无符号，且 0 只有一种表示（不像原码/反码有 +0/−0）。C11（自 C23 起更是强制补码）——入门期只需记住「负数在内存里长成『取反加一』的样子，最高位是符号位」。

### 7.4.4 用 `%x` 看位模式

`printf("%x", ...)` 按十六进制打印，是「直接看见内存里那串位」的最方便窗口（每个十六进制位对应 4 个二进制位）。

本机实测（`gcc -std=c11 -Wall`，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）：

    i=-1 as hex %x -> ffffffff
    (unsigned char)(-1) = 255, as %x -> ff
    short -2 as 16-bit hex -> fffe

`−1`（32 位 `int`）的位模式是 `ffffffff`（全 1），正是补码「−1 = 全 1」的印证；`(unsigned char)(−1)` 是 `ff`（8 位全 1 = 255）；`(short)−2` 是 `fffe`（= `~1 + 1` 的 16 位形式）。给初学者的实用直觉：**看到 `printf("%x")` 打出一长串 `f` 打头的大数，多半是把一个负数当无符号打印了**——这几乎是「有符号被当无符号解释」的即时证据。注意 `%x` 期望 `unsigned int` 实参，严格来说把 `int -1` 传给 `%x` 属类型不严格匹配（实践中在补码平台按位重解释得到期望结果，但入门时知道有此细节即可）。

#### 来源与时效（本小主题末集中列）
- 一手锚点：K&R 2nd ed Ch2 §2.2「Data Types and Sizes」、Appendix B §B.1.1（`<limits.h>` 各整型取值范围）、Ch2 §2.9（位运算，配合看位模式）。C11 §6.2.6.2「Integer types」（有符号整数的符号位与值位表示，含补码/反码/原码三种曾被允许的表示；C23 起仅补码）、§5.2.4.2.1「Sizes of integer types <limits.h>」（`CHAR_BIT`、各类型最小取值范围）、§6.2.5（无符号回绕模 2^N）。核实 2026-07-26。
- 比对结论：K&R 与 C11 一致；关键 delta——C89/C99/C11 允许三种有符号表示（补码/反码/原码），但真实平台（含本机 x86-64）恒为补码，且 **C23 已把补码定为唯一合法表示**。故「补码」在规范上是「实践统一、C23 强制」，标为随标准演进项。
- 实测坐实：`−1`→`ffffffff`、`(unsigned char)−1`→`ff`、`(short)−2`→`fffe`——本机真实输出，印证补码位模式（基线串见正文）。
- 冲突/易混点：「补码是不是标准强制」在 C11 及以前答案是「否（允许三种）」，C23 才是「是」——版本差异须分账，非记忆填。位级/字节序纵深下沉 L3-02。

## 7.5 浮点表示入门直觉

### 7.5.1 为什么需要浮点，以及它不是精确的

整数无法表示小数和极大/极小的数，**浮点数**（floating point）用「科学计数法的二进制版」来近似实数：一个数被拆成「符号 × 尾数 × 2 的指数次幂」。C 的 `float`（单精度）、`double`（双精度）和 Python 的 `float`（就是 C 的 `double`）都遵循 **IEEE 754** 标准。

初学者第一条必须建立的直觉：**浮点是「近似」，不是「精确」**。因为它用有限的位去逼近无限的实数轴，很多十进制小数（如 0.1）在二进制里是无限循环、存不下，只能存最接近的近似值。

### 7.5.2 IEEE 754 的三段结构

一个 IEEE 754 浮点数的位被分成三段：**符号位（sign）+ 指数位（exponent）+ 尾数/小数位（fraction/mantissa）**。本机实测（Python `struct.pack` 看字节，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）：

    float32    1.0: bits=00111111100000000000000000000000 sign=0 exp=01111111 frac=00000000000000000000000
    float32   -2.0: bits=11000000000000000000000000000000 sign=1 exp=10000000 frac=00000000000000000000000
    float32    0.5: bits=00111111000000000000000000000000 sign=0 exp=01111110 frac=00000000000000000000000
    float64    1.0: sign=0 exp(11 bits)=01111111111 frac(52 bits)

由实测可读出字段宽度（与 IEEE 754 一致）：

    单精度 float32：1 位符号 + 8 位指数 + 23 位小数 = 32 位
    双精度 float64：1 位符号 + 11 位指数 + 52 位小数 = 64 位

看 `1.0` 的 float32：符号 0（正）、指数 `01111111`（= 127，即偏移量 bias=127 表示 2^0）、小数全 0（尾数隐含前导 1，即 1.0 × 2^0 = 1.0）。`−2.0` 符号位变 1、指数 `10000000`（=128，即 2^1），正好 −1 × 1.0 × 2^1。给初学者的直觉：**指数段决定「数量级/小数点浮到哪」（这就是「浮点」得名），尾数段决定「有效数字」，符号位决定正负**。

### 7.5.3 浮点不精确与比较陷阱

因为多数十进制小数无法在二进制里精确表示，浮点运算会有**舍入误差**。最经典的初学者坑：

    0.1 + 0.2 == 0.3   ?

本机实测（`python3`，基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）：

    0.1 float64 hex: 3fb999999999999a
    0.1+0.2 ==0.3 ? False   0.1+0.2 = 0.30000000000000004

`0.1` 存的其实是 `3fb999999999999a` 这个最接近的近似（尾部 `...9a` 泄露了它不是精确的 0.1），于是 `0.1+0.2` 得到 `0.30000000000000004`，不等于 `0.3`。这在 C 的 `double` 里同样发生（Python `float` 就是 C `double`）。给初学者的铁律：**永远不要用 `==` 直接比较两个浮点数是否相等**，而应判断「差的绝对值小于一个很小的容差」，例如 `fabs(a-b) < 1e-9`。

### 7.5.4 章节定位待核与深挖边界

**⚠ 待核项（硬标，不臆造）**：浮点/IEEE 754 在 K&R 2nd ed 与 ISO/IEC 9899:2011 (C11) 中的**确切章节号定位为待核**（核实日期 2026-07-26）。本报告不凭记忆填 K&R/C11 的浮点章节编号；上文的 IEEE 754 字段宽度（1/8/23 与 1/11/52）来自**本机 `struct` 实测**与 IEEE 754 标准的公认字段划分交叉印证，未依赖 K&R/C11 的具体章节。C11 对浮点的规范散见于 `<float.h>` 相关条款与附录 F（IEC 60559/IEEE 754 绑定），但精确条号在本轮未逐条落定，故标待核。

深挖边界：**浮点/整数的位级表示纵深（内存层次、字节序、`<float.h>` 各极限常量、非规格化数/无穷/NaN、附录 F 的完整绑定）显式下沉归 L3-02（计算机组成原理）**。本报告只给「三段结构 + 不精确 + 别用 `==` 比较」的入门直觉，不做位级纵深。
