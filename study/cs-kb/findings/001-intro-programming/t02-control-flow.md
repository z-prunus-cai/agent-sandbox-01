## 2.1 条件分支

### 2.1.1 if / else / else-if 阶梯

条件分支让程序按一个布尔判断在两条（或多条）执行路径里选一条走。C 与 Python 都有 `if` / `else`；多路判断时把下一层 `if` 接在 `else` 上形成 else-if 阶梯，从上往下逐个测试，命中第一个为真的分支后其余全部跳过。

C 的骨架（花括号界定语句块，条件用圆括号）：

```c
if (score >= 90)      { grade = 'A'; }
else if (score >= 60) { grade = 'B'; }
else                  { grade = 'F'; }
```

Python 的骨架（用缩进界定块，`elif` 是 `else if` 的合并关键字）：

```python
if score >= 90:
    grade = 'A'
elif score >= 60:
    grade = 'B'
else:
    grade = 'F'
```

对初学者最关键的直觉是"互斥且有序"：阶梯里的分支是从上到下短路的，只要有一个条件为真，就执行它的块并跳出整个阶梯，不会再测后面的条件。所以条件的书写顺序会影响结果——把 `score >= 60` 写在 `score >= 90` 前面会让 95 分也落进 `B` 分支。

两个高频易错点。其一，C 里 `if` 的条件是任意标量表达式，`0` 为假、非 `0` 为真，于是把相等判断 `==` 误写成赋值 `=` 不会报错却语义全变：`if (x = 5)` 是"把 5 赋给 x，再拿 5 当条件"（恒真）。gcc 用 `-Wall` 会对此给 `-Wparentheses` 警告。Python 从语法层面禁止在 `if` 条件里用 `=` 赋值（`:=` 海象运算符是另一回事），从根上堵掉了这个坑。其二，C 里 `if` 后不加花括号只管紧跟的一条语句，后续缩进相同的语句其实在 `if` 之外——所谓"悬空 else / 悬垂语句"陷阱；教学上建议 C 的分支永远带花括号。Python 靠强制缩进天然规避了这一类。

### 2.1.2 switch / case 与 C 的 fall-through

`switch` 是 C 针对"同一个整型表达式与一串常量逐一比较"的多路分支语法。它计算一次控制表达式，跳到匹配的 `case` 标签处开始执行；关键在于——匹配只决定"从哪进入"，不决定"到哪停"。若某个 `case` 末尾没有 `break`，控制会继续"跌落"（fall-through）执行下一个 `case` 的语句，直到遇到 `break` 或 `switch` 结束。

骨架：

```c
switch (x) {
    case 1: /* 无 break，跌落 */
    case 2: handle_1_or_2(); break;
    case 3: handle_3();      break;
    default: handle_other();
}
```

这套"落穿"语义是 C 初学者最经典的踩坑点：漏写一个 `break`，程序就会把本不该执行的后续分支也执行掉。本机实测直观展示了这一点：

```text
$ gcc -std=c11 -Wall -o fallthrough fallthrough.c && ./fallthrough
x=1 -> one two three
x=2 -> two three
x=3 -> three
（基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）
```

`case 1` 没有 `break`，于是 x=1 时把 `one two three` 一路执行到 `case 3` 的 `break` 才停；x=2 从 `case 2` 进入执行 `two three`。可见"匹配点只是入口"。

除非你确实想要跌落（比如多个 `case` 共享同一段处理，如上例 `case 1`/`case 2` 合并），否则每个 `case` 都以 `break` 收尾。有意的跌落最好加注释 `/* fall through */` 说明这是故意的（现代编译器可用 `-Wimplicit-fallthrough` 提醒漏 break）。另外 `switch` 的 `case` 标签必须是整型常量表达式，不能是变量或浮点、字符串；`default` 可放任意位置，无匹配时才走它。Python 没有 C 式 `switch`；3.10 起引入的 `match`/`case`（结构化模式匹配，PEP 634）不是落穿语义——每个 `case` 天然独立、匹配一个就结束，语义更接近"带解构的多路 if"，不要用 C 的落穿直觉去套它。

### 2.1.3 条件（三元）表达式

条件表达式是"用一个表达式而非语句块表达二选一取值"。C 的三元运算符 `?:` 形如 `条件 ? 值A : 值B`：条件为真取值 A，否则取值 B，整体是一个能参与更大表达式或直接赋值的**值**。

C：

```c
int max = (a > b) ? a : b;
```

Python 的对应写法是条件表达式（顺序不同，值在前）：

```python
max_v = a if a > b else b
```

初学者要抓住"语句 vs 表达式"的区别：`if` 语句是"做某件事"（改变控制流、可含多条语句、无返回值），而三元/条件表达式是"算出一个值"，可以嵌在赋值右侧、函数实参、`return` 后面等需要值的位置。它让"根据条件选一个值"这种小逻辑不必展开成四行 `if/else`。

C 的 `?:` 也短路——只求值被选中的那一支，另一支完全不执行（这点和 `if` 一致，可放心把有副作用的表达式放进去而不担心两支都跑）。但 `?:` 优先级很低、且右结合，嵌套时务必加括号，否则 `a ? b : c ? d : e` 读起来歧义（实际按 `a ? b : (c ? d : e)` 结合）。Python 的 `a if cond else b` 同样只求值被选中的分支；注意它把"真值"写在最前面、条件在中间，和自然语序一致但与 C 顺序相反，两种语言来回切换时最容易写反。

## 2.2 循环结构

### 2.2.1 while 循环（先判断后执行）

`while` 是最基本的"当条件为真就反复执行循环体"结构：每轮迭代**先**测试条件，为真才执行一次循环体，然后回到测试；条件一旦为假就退出。因为先测试，循环体可能一次都不执行。

C 与 Python 骨架一致（Python 用缩进、无括号）：

```c
while (n > 0) { sum += n; n--; }
```

```python
while n > 0:
    sum += n
    n -= 1
```

`while` 适合"不知道要循环几次、只知道停止条件"的场景（如读到文件结束、逼近到误差以内）。核心风险是"死循环"——循环体里必须有能让条件最终变假的进展（上例的 `n--`）。忘了递减、或条件写反，程序就会永远转下去。写 `while` 时养成"退出条件何时成立"的自问习惯。

### 2.2.2 for 循环：C 的三段式 vs Python 的遍历

`for` 表达"有计划的重复"，但两语言语义不同。C 的 `for(初始化; 条件; 步进)` 是 `while` 的语法糖，三个部件分别只做一次初始化、每轮先测的条件、每轮体后执行的步进：

```c
for (int i = 0; i < n; i++) { total += a[i]; }
```

Python 的 `for` 不是计数器循环，而是**遍历一个可迭代对象**，每轮把下一个元素绑定到循环变量：

```python
for x in [10, 20, 30]:
    total += x
```

要用计数序列时 Python 用 `range`：

```python
for i in range(n):      # i = 0,1,...,n-1
    total += a[i]
```

初学者最容易带着 C 的"i 是个可自增的计数器"直觉去读 Python 的 `for`，结果水土不服。Python 里 `for i in range(n)` 只是"依次拿 range 产出的每个数"，`range(n)` 生成 `0..n-1`（左闭右开、不含 n）。在循环体里改 `i` 不会影响下一轮取值（下一轮直接从迭代器取下一个）。C 里改循环变量 `i` 则会真的影响下一次条件判断和寻址，这是两者的本质差异。教学上先记住："C 的 for 管的是计数与边界，Python 的 for 管的是遍历元素。"

### 2.2.3 do-while（后判断，至少执行一次）

`do-while` 是 C 的"后测试"循环：先执行一次循环体，**再**测试条件，为真则继续。因此无论条件初值真假，循环体至少执行一次。

```c
do { c = getchar(); process(c); } while (c != '\n');
```

它适合"先做一次、根据结果决定要不要再来"的场景，典型如"至少读一次输入再校验""菜单先显示一次"。易错点是循环末尾的分号 `} while(cond);` 不能漏。Python **没有** `do-while` 语法；惯用的等价写法是"无限循环 + 条件 break"：

```python
while True:
    c = read_one()
    if c == '\n':
        break
```

需要"至少跑一次"时，C 用 `do-while`，Python 用 `while True: ... if 退出条件: break`。

### 2.2.4 循环边界、半开区间与 off-by-one

"off-by-one"（差一错误）指循环少跑一轮或多跑一轮，几乎总是边界条件写错引起：把 `<` 写成 `<=`、把起点从 0 写成 1、把长度 n 当成末索引用。它是数组越界、漏处理最后一个元素等 bug 的头号来源。

主流惯例是用**半开区间** `[0, n)`——起点包含、终点不包含，配 `<`：

```c
for (int i = 0; i < n; i++) { /* 恰好 n 次，访问 a[0]..a[n-1] */ }
```

半开区间的两个好处让它成为默认选择：区间长度直接等于"终点减起点"（`n - 0 = n` 次），且相邻区间 `[0,k)` 与 `[k,n)` 能无缝拼接不重不漏。Python 的 `range(n)` 正是这个约定的内建化——`range(0, n)` 就是 `0..n-1`。

写完循环先手推最小规模（n=0 和 n=1）看跑几次、首末元素有没有恰好覆盖。C 里最危险的是 `i <= n` 访问 `a[i]`——会读到 `a[n]` 即越界（合法下标只到 `n-1`），这在 C 中是未定义行为（见 2.5）。Python 里下标越界会抛 `IndexError` 而不是静默出错，相对安全，但逻辑上的差一（漏算最后一项）照样会得到错误结果。

### 2.2.5 循环的 else 子句（Python 特有）

Python 的 `for` / `while` 可以带一个 `else` 子句：循环**正常跑完（没被 break 打断）**时执行 `else`，若中途 `break` 退出则跳过 `else`。C 没有这个结构。

```python
for x in items:
    if x == target:
        found = x
        break
else:
    found = None   # 没 break，即遍历完也没找到
```

初学者容易把它误读成"循环体不执行时走 else"——不是。判据只有一个：**是否触发过 break**。它专为"搜索循环"设计：`else` 分支恰好对应"整个序列都找过了、没找到"的情形，省去额外的 `found` 标志变量。虽然实用，但因命名反直觉，可读性见仁见智，很多团队规范里少用；作为广度知识了解即可。

## 2.3 短路求值与布尔逻辑

### 2.3.1 短路求值机制（&& 与 ||）

短路求值（short-circuit）指逻辑与 `&&`、逻辑或 `||` 从左到右求值，一旦左操作数已能决定整体结果，就**不再求值右操作数**。`&&`：左为假则整体必假，右侧跳过；`||`：左为真则整体必真，右侧跳过。

C11 明确规定了这一行为并给出保证：

```text
C11 §6.5.13p4：&& 保证从左到右求值；若第二操作数被求值，
              则第一、第二操作数求值之间有一个序列点；
              若第一操作数等于 0，则第二操作数不被求值。
C11 §6.5.14p4：|| 同理，若第一操作数不等于 0，则第二操作数不被求值。
```

对初学者，短路有两层价值。其一是**性能与正确性的安全阀**：把"廉价或起保护作用"的条件放左边。经典惯用法是先判空指针再解引用：

```c
if (p != NULL && p->value > 0) { ... }
```

若 `p` 为 `NULL`，`&&` 左边为假直接短路，右边的 `p->value`（会崩溃的解引用）根本不执行。反过来写就会解引用空指针。其二是它保证了求值顺序：`&&`/`||` 两操作数间有序列点（不同于位运算 `&`/`|` 无此保证，且位运算两边都会算）。易错点：想让两边都产生副作用时别用 `&&`/`||`——它会短路掉一边；也别把 `&&` 当 `&` 用（`&` 是按位、无短路、语义完全不同）。

### 2.3.2 Python 的 and / or 返回操作数而非布尔

Python 的 `and`/`or` 也短路，但有一个 C 没有的特性：它们**返回最后被求值的那个操作数本身，而不是强制转成 `True`/`False`**。官方 Language Reference §6.11 原文：

```text
"neither and nor or restrict the value and type they return to
 False and True, but rather return the last evaluated argument."
x or y   → 若 x 为真返回 x，否则返回 y
x and y  → 若 x 为假返回 x，否则返回 y
```

```text
$ python3
>>> 0 or "default"      -> 'default'
>>> "hi" or "default"   -> 'hi'
>>> 3 and 4             -> 4
>>> 0 and 4             -> 0
>>> [] or {"k": 1}      -> {'k': 1}
>>> None or 42          -> 42
（基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）
```

"`and`/`or` 是选出并交回某个操作数，不是产出真假。" 而 `not x` 不同——它必须造一个新值，永远返回布尔 `True`/`False`（如 `not 'foo'` 得 `False` 而非 `''`）。这是官方文档明确点出的不对称：三个逻辑运算里只有 `not` 归一成 bool。C 则相反：C 的 `&&`/`||`/`!` 一律产出 `int` 的 `0` 或 `1`。

### 2.3.3 真值测试与 `x or default` 惯用法

"真值测试"（truthiness）指非布尔对象在布尔上下文（`if`、`while`、`and`/`or`）里被当真还是假。Python 官方规定这些内建对象为**假**：

```text
None、False；
任意数值类型的零：0、0.0、0j、Decimal(0)、Fraction(0,1)；
空的序列与集合：''、()、[]、{}、set()、range(0)。
其余（非空、非零）一律为真。
```

结合 2.3.2 的"返回操作数"，就有了 Python 极常用的惯用法：

```python
name = user_input or "Anonymous"   # user_input 为空串/None 时取默认值
```

`user_input` 若是非空字符串则为真、`or` 短路返回它本身；若是 `""` 或 `None`（皆为假）则返回 `"Anonymous"`。这就是"或默认值"惯用法。给初学者的提醒也在这里：这个惯用法把"空值"和"合法的假值"一视同仁。若 `0` 是合法输入，`count = n or 10` 会在 `n == 0` 时错误地取到 10——此时应显式判 `None`（`n if n is not None else 10`），别用 `or`。C 没有对象真值的概念，只有"标量是否等于 0"，关系运算符 `==`/`<` 等产出 `0` 或 `1`；C99 起有 `_Bool` 类型和 `<stdbool.h>` 里的 `bool`/`true`/`false` 宏，但底层仍是整型。

## 2.4 跳转与结构化定理

### 2.4.1 break 与 continue

`break` 与 `continue` 是循环内的"受控跳转"：`break` 立即终止**当前所在的**最内层循环（或 `switch`），跳到循环之后继续；`continue` 跳过本轮循环体余下语句、直接进入下一轮（对 `for` 而言仍会执行步进部分）。C 与 Python 语义一致。

```c
for (i = 0; i < n; i++) {
    if (a[i] < 0)   continue;   /* 跳过负数，进入下一轮 */
    if (a[i] == target) break;  /* 找到，退出整个循环 */
    sum += a[i];
}
```

给初学者的关键直觉与易错点：`break`/`continue` 只作用于**最内层**循环。嵌套循环里想跳出外层，C 没有"带标签的 break"，需借助标志变量或 `goto`（见 2.4.2）；Python 同样只跳最内层（可用异常或把内层封成函数 `return` 来跳出多层）。此外 `continue` 在 `while` 与 `for` 里行为略有心智差异：`for` 的 `continue` 仍会执行"步进"，而 `while` 里若把递增写在被 `continue` 跳过的位置，就会造成死循环——这是 `while + continue` 的经典坑。

### 2.4.2 goto 与标签（C 有，Python 无）

`goto 标签;` 让控制无条件跳到同一函数内 `标签:` 处。它是最原始的跳转，能跳过或跳回任意代码位置（但不能跨函数）。Python **没有** `goto`（语言刻意不提供）。

C 里 `goto` 保留下来的、被广泛认可的正当用途是**多重资源的集中清理 / 错误处理**——在没有 `try/finally`、没有析构函数的 C 里，从一段中途失败的初始化里"一路释放已分配资源"：

```c
int f(void) {
    FILE *fp = fopen(...);   if (!fp)  goto fail0;
    char *buf = malloc(...); if (!buf) goto fail1;
    if (do_work(fp, buf) < 0) goto fail2;
    /* 成功路径 */
    free(buf); fclose(fp); return 0;
fail2: free(buf);
fail1: fclose(fp);
fail0: return -1;
}
```

这种"向前跳到清理段、按逆序释放"的写法（Linux 内核大量采用）把散落各处的清理集中到函数尾部，避免每个出错点重复一堆 `free`/`close`。给初学者的边界：`goto` 只能在同一函数内跳；**向后跳**（跳回前面形成循环）、跳进另一个块的中间、跳过变量初始化都极易制造难懂且易错的控制流，除了上面这种"向前跳到清理段"的惯用法外，一般不用。能用结构化语句（`break`/`continue`/函数拆分）表达时就不要用 `goto`。

### 2.4.3 结构化定理与 goto 之争

结构化程序设计的理论基石是 **Böhm–Jacopini 定理（1966）**：任何可计算的流程图都可以只用三种控制结构表达——顺序（sequence）、选择（selection，if/else）、循环（iteration，while）——而无需 `goto`。

```text
结构化三要素：顺序 · 选择(分支) · 循环
（Böhm & Jacopini, 1966：三者足以表达任意控制流）
```

这条定理为"少用/不用 goto"提供了理论正当性。1968 年 Dijkstra 的著名短文《Go To Statement Considered Harmful》进一步论证：滥用 `goto` 会让程序的静态文本与动态执行轨迹脱节、难以推理，主张用结构化控制结构取而代之。此后主流语言与工程实践都以"单入口单出口的结构化块"为默认范式。

对初学者，取走这几点直觉即可：其一，你日常写的 `if`/`while`/`for` 本身就已经"结构化完备"，理论上足以表达任何逻辑，不必依赖 `goto`。其二，"结构化"的价值是**可读、可推理**——控制流沿着缩进块的形状走，读代码就能预测执行路径。其三，定理说的是"能不用 goto"，不是"任何时候都最优雅"；像 2.4.2 的多层清理、或跳出多重嵌套循环，`goto`/`break` 这类受控跳转在 C 里仍是可读性更好的折中。定理给的是"下限保证"，工程上按可读性取舍。

## 2.5 C 未定义行为陷阱

> 说明：本节所有"未定义行为（UB）"均为 **C 语言标准语义**层面的裁决，条款引 ISO/IEC 9899:2011 (C11)；不同实现/优化等级下的**具体表现**（是否崩溃、算出什么值）各异，属实现行为，不能作结论依赖。Python 无此类语言级 UB（越界、溢出等会抛异常或走定义好的语义）。

### 2.5.1 有符号整数溢出

当有符号整数运算的**数学结果超出该类型可表示范围**（如 `int` 上 `INT_MAX + 1`）时，C 标准判定为未定义行为。依据是 C11 对表达式求值的总则：

```text
C11 §6.5p5：若表达式求值中出现"异常条件"（即结果在数学上无定义、
            或不在其类型可表示的范围内），则行为未定义。
```

注意这只针对**有符号**整数。**无符号**整数溢出是**有定义**的——按模 2^N 回绕（C11 §6.2.5p9），这是 C 里少数刻意定义的"溢出"。本机用 UBSan 触发有符号溢出：

```text
$ gcc -std=c11 -fsanitize=undefined -o ovf ovf.c && ./ovf
ovf.c:6:9: runtime error: signed integer overflow: 2147483647 + 1
           cannot be represented in type 'int'
INT_MAX=2147483647
x+1=-2147483648
（基线 Py3.11.15/np2.4.6/gcc13.3 @2026-07-25）
```

这里看到的 `-2147483648`（回绕值）**不是标准保证的结果**——它只是本机本次的表现。因为溢出是 UB，编译器有权假设"有符号溢出永不发生"并据此优化，导致 `if (x + 1 < x)` 这类溢出检测被直接优化掉、程序行为诡异。所以正确做法不是"依赖回绕"，而是**溢出前先检查**（如 `if (a > INT_MAX - b)` 再决定是否相加），或用无符号类型做需要回绕的位运算。`-fsanitize=undefined`（UBSan）能在运行时逮住这类 UB，是学习期排错利器。Python 的 `int` 是任意精度、不会溢出，天然没有这个坑。

### 2.5.2 未初始化读

读取一个从未被赋值的自动（局部）变量的值，是 C 的常见 UB。标准把未初始化对象持有的值称为"不确定值"，并明确读它触发 UB：

```text
C11 §3.19.2：不确定值 = 未指定值 或 陷阱表示（trap representation）。
C11 §6.3.2.1p2：若某自动存储期对象"本可声明为 register"（即从未取过它的地址）
               且未初始化，则对它做左值转换（读它的值）的行为未定义。
```

C 的局部变量声明后**不会自动清零**（不像全局/静态变量默认 0，也不像 Python 变量必须先赋值才能用）。`int x;` 之后 `x` 里是栈上遗留的任意字节，读它可能每次不同、可能是陷阱表示（在某些平台上读取即崩）。危险之处在于它常常"看起来能跑"——某次恰好是 0、测试通过，换个环境或优化等级就出错，属于最难复现的一类 bug。防治很简单：**声明即初始化**（`int x = 0;`），并开 `-Wall -Wmaybe-uninitialized` 让编译器帮忙；`-fsanitize=memory`（Clang）或 valgrind 也能查。Python 里"用未赋值的名字"直接抛 `NameError`/`UnboundLocalError`，是定义好的错误而非 UB。

### 2.5.3 序列点与求值顺序

"序列点"（sequence point）是 C 抽象机里的一个执行分隔标记：它之前的所有副作用（如写入变量、I/O）都已完成，之后的尚未开始。C11 用更细的"sequenced before / unsequenced / indeterminately sequenced"关系描述：

```text
C11 §5.1.2.3p3：两个求值间存在序列点，意味着前者的每个值计算与副作用
               都"先序于"后者的全部值计算与副作用。
C11 §6.5p2：若对同一标量对象的一个副作用，与该对象上的另一副作用、
           或对其值的读取，彼此"无序"（unsequenced），则行为未定义。
C11 §6.5p3：除标准另有规定处，子表达式的副作用与值计算彼此无序。
```

后果就是那些著名的"一句里改同一个变量两次"的表达式是 UB，结果不可依赖：

```c
i = i++;          /* UB：对 i 的两次修改无序 */
a[i] = i++;       /* UB：读/写 i 与改 i 无序 */
```

**同一个表达式里，不要对同一个变量既读又写、或写两次**，除非中间隔着一个序列点。哪些地方有序列点？`;` 语句结尾、`&&`/`||`/`?:`/逗号运算符的左右操作数之间、函数调用"实参都算完到真正调用之间"（见 2.5.4）——这些点保证了顺序。而普通算术如 `+`、`*`、赋值 `=` 的左右两边、函数各实参之间，**没有**序列点，顺序未定，此时藏副作用就会 UB。养成"一句只改一个状态"的习惯即可稳妥避开。

### 2.5.4 函数实参求值顺序未指定

调用一个函数时，各个实参表达式的**求值先后顺序在 C 里是未指定的**（unspecified）——可能从左到右，也可能从右到左，甚至交错。标准只保证"所有实参和函数指示符都求值完之后、真正调用之前"有一个序列点：

```text
C11 §6.5.2.2p10：函数指示符与各实参求值完成之后、真正调用之前，有一个序列点。
（标准未规定各实参之间的先后 → 实参彼此的求值顺序未指定/无序）
```

于是让实参之间产生相互依赖的副作用，结果因编译器而异（甚至同一表达式里对同一变量的重复修改直接变成 UB，见 2.5.3）：

```c
printf("%d %d\n", i++, i++);   /* 两个实参求值顺序未指定 + 改 i 两次：不可依赖 */
f(g(), h());                   /* g 与 h 谁先调用未指定 */
```

初学者常被这个坑到，因为"从左到右读代码"的直觉会让人以为实参就是从左往右算。实际上换个编译器或优化等级，输出的两个数字顺序可能就反了，`f(g(), h())` 里 `g`/`h` 的调用先后也不保证。规避方法很直接：**不要让同一次调用里的多个实参彼此有求值副作用依赖**——需要顺序时，先用独立语句把中间结果算好、存进临时变量，再传进去。这样每条语句结尾的 `;` 就是明确的序列点，顺序确定。Python 对此有明确规定（实参从左到右求值），不存在这个未指定问题——又一处 C 需格外小心而高级语言替你定死的地方。
