## 6.1 地址与指针基础

### 6.1.1 内存、地址与指针是什么

程序运行时，每个对象（变量）都住在内存里某个带编号的位置，这个编号叫地址（address）。指针（pointer）就是一个「值为地址」的变量——它不直接装数据，而是装「数据在哪儿」。

普通变量是「盒子里的东西」，指针是「写着某个盒子门牌号的纸条」。你可以顺着纸条上的门牌号找到那个盒子，再去读或写盒子里的东西。

在 64 位环境（本基线 x86-64）里，地址是 64 位宽，所以任何类型的指针本身都占 8 字节。本机实测（gcc 13.3.0，`-std=c11`）：

```
$ gcc -std=c11 -Wall sizes.c -o sizes && ./sizes
sizeof(char)=1
sizeof(int)=4
sizeof(double)=8
sizeof(int*)=8
sizeof(char*)=8
sizeof(double*)=8
```

指针「指向的东西」大小各异（char 1 字节、int 4 字节、double 8 字节），但「指针自己」在同一 ABI 下一律是地址宽度（这里 8 字节）。初学者常把 `sizeof(int*)` 误当成 `sizeof(int)`，务必分清「指针的大小」和「被指对象的大小」是两回事。

Python 侧对照直觉：Python 的名字（变量）其实也「绑定到对象」，本质上底层是引用/地址，但语言不让你拿到、也不让你做地址算术——C 把这层完全暴露给你，威力和风险都来自这里。

### 6.1.2 取址 `&` 与解引用 `*`

两个核心运算符成对使用：

```
&x    取 x 的地址（得到一个指向 x 的指针）
*p    解引用 p（顺着 p 存的地址，访问那里的对象）
```

`&` 和 `*` 互为逆操作：`*(&x)` 就是 `x` 本身。声明 `int *p = &x;` 读作「p 是一个指向 int 的指针，初值为 x 的地址」；此后 `*p` 既能读 x 的值，也能写 x（通过指针间接改动别处的变量，这正是指针的核心用途）。


```
$ gcc -std=c11 -Wall ptrbasic.c -o ptrbasic && ./ptrbasic
value x       = 42
address &x    = 0x7ffe6e557e0c
pointer p     = 0x7ffe6e557e0c
deref *p      = 42
after *p=99, x= 99
```

可以看到 `p` 的值和 `&x` 完全相同（都是 x 的门牌号），`*p` 取回 42；执行 `*p = 99;` 后 `x` 变成了 99——我们没直接碰 x，而是顺着指针改了它。这就是「指针能修改调用者的变量」（大主题3 里 C 用指针模拟引用传递、swap 需传指针，根子就在这里）。

声明里的 `*`（`int *p`，表示「p 是指针」）和表达式里的 `*`（`*p`，表示「解引用」）是两种不同语境的同一符号，初学时极易混淆。记法：声明看类型，表达式看操作。

### 6.1.3 指针类型与空指针 NULL

指针是有类型的：`int *` 和 `double *` 是不同类型。类型不只是给编译器看的标签，它决定了两件事——解引用时按多大读取/写入（`*p` 读几个字节取决于 `p` 指向的类型），以及指针算术的步长（见 6.3）。所以「指错类型的指针」会以错误的宽度和步长解释内存，是常见 bug 源。

一个特殊值是空指针 NULL：它表示「不指向任何对象」，通常写作宏 `NULL`（定义在 `<stddef.h>` 等头文件，值为一个空指针常量）。约定用它初始化「暂时还没指向谁」的指针，并在解引用前判断 `if (p != NULL)`。

解引用空指针是未定义行为，实践中通常触发段错误（SIGSEGV）使程序崩溃。初学者要养成两个习惯——指针声明时若无合法目标就先置 NULL（避免野指针，见 6.6.2），解引用前对可能为空的指针做非空检查。

- 一手：ISO/IEC 9899:2011 (C11) §6.5.3.2（Address and indirection operators，`&`/`*` 语义）；§6.3.2.3（指针与空指针常量，null pointer constant / NULL）；§6.2.5（类型，指针类型）。

## 6.2 指针与数组

### 6.2.1 数组名退化为指针

C 里数组和指针关系极近，但不是一回事。核心规则：在大多数表达式中，数组名会「退化」（decay）成指向其首元素的指针。也就是说，写 `a`（在传参、参与算术等语境）等价于 `&a[0]`。

```
在表达式中：  a   →   &a[0]   （指向首元素的指针）
```

正因如此，`int *p = a;` 合法且常见——`a` 退化成 `&a[0]`，赋给指针 p。这也是「数组作实参传给函数时，函数收到的其实是指针、丢失了长度信息」的原因（大主题5 已提及，需要额外传长度）。


```
$ gcc -std=c11 -Wall arr.c -o arr && ./arr
a[2]=30  *(a+2)=30
&a[0]=0x7ffc2e415ce0
&a[1]=0x7ffc2e415ce4  (diff=4 bytes)
p=0x7ffc2e415ce0  p+1=0x7ffc2e415ce4  (diff=4 bytes)
sizeof(a)=20  sizeof(p)=8
2[a]=30
```

`p`（由 `int *p = a;` 得来）等于 `&a[0]`，印证了退化。

### 6.2.2 `a[i]` 等价于 `*(a+i)`

下标运算本质上就是指针算术的语法糖。C 标准直接规定：

```
a[i]  等价于  *(a + i)
```

即「取 a 的首地址，向后跨 i 个元素，再解引用」。上面实测里 `a[2]` 和 `*(a+2)` 都得到 30，正是这条等价的现场。

一个能加深理解（也是经典面试彩蛋）的推论：既然 `a[i]` 就是 `*(a+i)`，而加法可交换，那么 `*(a+i)` 也等于 `*(i+a)`，于是 `i[a]` 也合法且等于 `a[i]`——实测 `2[a]` 同样得到 30。这不是鼓励你这么写（可读性差），而是揭示「下标不过是指针加法 + 解引用」这一底层事实。

一旦接受「`a[i]` = `*(a+i)`」，遍历数组用指针（`for (int *q=a; q<a+n; q++) ... *q ...`）和用下标（`for (int i=0;i<n;i++) ... a[i] ...`）就是同一件事的两种写法。

### 6.2.3 等价背后的差异：数组名 ≠ 指针变量

「退化」不等于「数组就是指针」。两者有真实差异，混淆会出 bug：

- `sizeof`：对数组名 `a`（未退化的语境），`sizeof(a)` 是整个数组的字节数；对指针 `p`，`sizeof(p)` 只是指针本身大小。实测 `sizeof(a)=20`（5 个 int × 4），`sizeof(p)=8`（一个指针）——这是判断「我手上是真数组还是退化后的指针」的可靠信号。
- 可赋值性：指针变量可以重新指向别处（`p = p + 1;` 合法）；数组名不是可修改的左值，`a = ...;` 非法（数组名不能整体重新赋值）。
- 取址语义：`&a` 的类型是「指向整个数组的指针」（`int (*)[5]`），与 `&a[0]`（`int *`）地址值相同但类型不同、指针算术步长不同。

正因为「数组传参会退化成指针、丢失 `sizeof` 得到的长度」，在函数内部对形参 `int arr[]` 用 `sizeof(arr)/sizeof(arr[0])` 算元素个数会得到错误结果（那里 `sizeof(arr)` 是指针大小 8，不是数组大小）。长度必须显式传。

#### 来源与时效（本小主题）
- 一手：K&R 2nd ed §5.3（Pointers and Arrays）——「数组名是指向首元素的表达式」、`a[i]` 与 `*(a+i)` 等价、指针与下标遍历等价。
- 一手：ISO/IEC 9899:2011 (C11) §6.3.2.1（Lvalue/array-to-pointer conversion，数组退化为指向首元素的指针，及例外语境如 `sizeof`/`&`）；§6.5.2.1（Array subscripting，规定 `E1[E2]` 等同 `(*((E1)+(E2)))`，并推出下标可交换）。
- 实测比对：本机 gcc 实测 `a[2]==*(a+2)==2[a]==30`；`p==&a[0]`；`sizeof(a)=20` 而 `sizeof(p)=8`。与 K&R/C11 一致。
- 冲突项：无。教材「数组名 ≈ 指针」的口语说法与规范「数组在多数表达式中转换为指针、但 `sizeof`/`&` 等语境例外」并不矛盾——本报告按规范把「退化」和「例外」分账讲清，避免初学者误以为二者完全等同。

## 6.3 指针算术与 sizeof

### 6.3.1 指针加减按「指向类型」缩放

指针加整数不是按字节数走，而是按元素走：`p + 1` 指向「下一个同类型对象」，地址实际增加 `sizeof(*p)` 个字节。这条「按指向类型缩放」是指针算术最关键、也最容易被初学者误解的规则。

```
(char*)(p + n)  的地址  ==  (char*)p + n * sizeof(*p)
```

本机实测，对三种类型各造数组、看 `p+1` 的地址增量：

```
$ gcc -std=c11 -Wall step.c -o step && ./step
char*   : p=0x7ffd507aecf5 p+1=0x7ffd507aecf6 step=1
int*    : p=0x7ffd507aecc4 p+1=0x7ffd507aecc8 step=4
double* : p=0x7ffd507aecd0 p+1=0x7ffd507aecd8 step=8
```

`char*` 步长 1、`int*` 步长 4、`double*` 步长 8，恰好等于各自的 `sizeof`。这正是「指针算术自动帮你按元素跨步」的体现——你写 `p+1`，编译器替你乘上 `sizeof(*p)`。

初学者最常见的错误是「以为 `p+1` 就是地址加 1 字节」。不是；只有 `char*`（元素 1 字节）才碰巧如此。想按字节精确移动时，才显式转成 `char*` 再加。

### 6.3.2 sizeof 与步长的关系

`sizeof(T)` 给出类型 T 一个对象占的字节数（`size_t` 类型，是无符号整型）。指针步长 = 指向类型的 `sizeof`，这就是 6.3.1 那条公式的来源。两者绑定，理解其一即理解其二。

配合 6.2 的下标等价，可以推出遍历的两种等价写法：`a[i]` 落在 `&a[0] + i*sizeof(a[0])` 处；用指针 `p=a; p++` 每次前进一个元素，与 `i++` 完全对应。

小心 `sizeof` 用在指针上的陷阱（已在 6.2.3 出现）：`sizeof(数组名)` 是整个数组，`sizeof(指针)` 是指针本身，二者别混。

### 6.3.3 指针相减、比较与合法范围

同一数组内的两个指针可以相减，结果是它们相隔的元素个数（类型为有符号的 `ptrdiff_t`），而非字节数——同样按元素缩放。指向同一数组的指针也可以用 `<`、`==` 等比较，用于遍历终止判断（`while (p < end)`）。

合法性边界（C11 明确规定，是初学者的高频雷区）：指针算术只在「指向同一数组对象内部，或其末元素之后恰好一个位置（one-past-the-end）」的范围内才有定义。

```
合法：  &a[0] ... &a[n]      （含末尾后一位 &a[n]，即 a+n）
非法：  a - 1，或 a + n + 1  （越出上述范围 → 未定义行为）
```

「末元素后一位」（`a+n`）允许存在、允许比较，但不允许解引用——它是循环终止哨兵的标准位置。越过这个范围（哪怕只是构造出这样一个指针值，不解引用）就是未定义行为。这解释了为什么标准的遍历写法是 `for (p=a; p < a+n; p++)` 而不是 `p <= a+n`（后者会解引用越界元素）。

#### 来源与时效（本小主题）
- 一手：K&R 2nd ed §5.4（Address Arithmetic）——指针加减按元素缩放、同数组内指针相减/比较、one-past-the-end 作为合法终点。
- 一手：ISO/IEC 9899:2011 (C11) §6.5.6（Additive operators，指针 ± 整数的元素缩放语义、同数组内相减得 `ptrdiff_t`、one-past-the-end 合法、越界为未定义行为）；§6.5.3.4（`sizeof` 与 `_Alignof`，`sizeof` 结果为 `size_t`）。
- 实测比对：本机 gcc 实测 `char*/int*/double*` 的 `p+1` 地址增量分别为 1/4/8 字节，等于各自 `sizeof`，坐实「步长=指向类型 sizeof」。
- 冲突项：无。教材与规范一致；步长数值为 ABI 相关（x86-64 下 int=4、double=8），换平台以该平台 `sizeof` 为准，不可套用记忆。

## 6.4 多级指针、指针数组与 argv

### 6.4.1 多级指针（指向指针的指针）

指针本身也是内存里的对象，所以也能取它的地址、得到「指向指针的指针」（二级指针 `int **`）。以此类推有三级、四级，但实践中二级最常见。

```
int   x;
int  *p  = &x;    // p 指向 x
int **pp = &p;    // pp 指向 p
```

解引用要逐层剥：`*pp` 得到 `p`，`**pp` 得到 `x`。本机实测：

```
$ gcc -std=c11 -Wall multi.c -o multi && ./multi
x=7  *p=7  **pp=7
after **pp=100 : x=100
```

`**pp` 一路走两跳读到 x=7；`**pp = 100;` 也能穿过两层改到 x。

当函数需要「修改调用者的指针本身」（不只是指针指向的数据）时，必须传指针的地址，即二级指针。比如「让函数把某个指针指向新分配的内存」，就要 `f(&ptr)`，函数内 `*param = malloc(...)`。这是「用指针模拟引用传递」（大主题3）在指针类型上的再一次应用。

### 6.4.2 指针数组 vs 数组指针

两个长得像、含义相反的构造，务必分清：

```
char *arr[3];    // 指针数组：一个含 3 个「char*」的数组
char (*p)[3];    // 数组指针：一个指针，指向「含 3 个 char 的数组」
```

指针数组（`T *arr[N]`）是「一堆指针排成的数组」，最常见于「字符串数组」——每个元素是指向一个字符串的 `char*`，各字符串长度可不同。数组指针（`T (*p)[N]`）是单个指针，指向一整个数组，常用于二维数组传参。区分靠 `[]` 和 `*` 的结合优先级：`[]` 优先级高于 `*`，`char *arr[3]` 先与 `[3]` 结合成数组、元素类型再是 `char*`；加括号 `char (*p)[3]` 才强制先是指针。

`argv` 就是一个指针数组（见下），字符串表（如菜单项、命令名列表）也常用指针数组。

### 6.4.3 命令行参数 argc/argv

`main` 的标准形式 `int main(int argc, char **argv)`（或等价的 `char *argv[]`）就是指针数组的实战。`argc` 是参数个数，`argv` 是「指向各参数字符串的指针的数组」：`argv[0]` 是程序名，`argv[1]`、`argv[2]`… 是各命令行参数，且标准保证 `argv[argc]` 为 NULL（可作遍历终止标记）。

本机实测（带三个参数运行）：

```
$ gcc -std=c11 -Wall argv.c -o argv && ./argv hello world 42
argc=4
argv[0]=./argv
argv[1]=hello
argv[2]=world
argv[3]=42
argv[argc]==NULL ? yes
```

`argc=4`（含程序名），`argv[argc]`（即 `argv[4]`）确实是 NULL——这是 C 标准对 `argv` 的保证。

遍历 argv 有两种等价写法：按下标 `for (int i=0;i<argc;i++)`，或利用 NULL 终止 `for (char **p=argv; *p!=NULL; p++)`。注意命令行参数永远是字符串——`argv[3]` 是字符 `"42"` 不是数字 42，要用数字需 `atoi`/`strtol` 转换（初学者常见错误）。

- 一手：K&R 2nd ed §5.6（Pointer Arrays; Pointers to Pointers）与 §5.10（Command-line Arguments，`argc`/`argv`、`argv[argc]==NULL`、遍历惯用法）；§5.12（Complicated Declarations，指针数组 vs 数组指针的声明解读）。
- 一手：ISO/IEC 9899:2011 (C11) §5.1.2.2.1（Program startup，`main` 的 `argc`/`argv` 语义，`argv[argc]` 为空指针）；§6.5.3.2 结合 §6.7.6.1（多级指针与指针声明符）。
- 实测比对：本机 gcc 实测 `**pp` 读写穿透两层到 `x`；`argc=4`、`argv[0]` 为程序名、`argv[argc]==NULL`。与 K&R/C11 一致。
- 冲突项：无。`char **argv` 与 `char *argv[]` 是同义写法（形参中数组即退化为指针，见 6.2.3），非冲突。

## 6.5 动态内存管理

### 6.5.1 为什么需要动态分配：栈、堆与生命周期

到目前为止的变量都住在栈（stack）上，随函数进入/退出自动创建/销毁——它们的大小必须在编译期已知、生命周期绑死在所在的块。但很多时候你需要「运行期才知道大小」或「生命周期跨越函数返回」的内存，这就要向堆（heap）申请动态内存，由你手动申请、手动归还。

栈内存是「餐厅自动收拾的餐桌」（坐下即用、离席即清），堆内存是「你自己租的仓库」（自己签合同租、用完必须自己退租，不退就一直占着=泄漏）。

函数里定义的局部数组/变量在栈上，函数返回后其内存作废；把「指向局部变量的指针」返回给调用者是经典 bug（返回后指针悬垂，见 6.6.1）。需要「函数造好、返回给调用者继续用」的内存，必须放堆上（malloc）。

### 6.5.2 malloc / calloc / realloc / free 的语义

C 标准库（`<stdlib.h>`）提供四个核心函数：

```
void *malloc(size_t size);              // 申请 size 字节，内容未初始化
void *calloc(size_t n, size_t size);    // 申请 n*size 字节，且全部清零
void *realloc(void *p, size_t newsize); // 调整已分配块大小，可能搬家
void  free(void *p);                    // 归还先前分配的块
```


- `malloc` 返回指向新块的指针，内容是未初始化的垃圾值（不要假设为 0）；申请失败返回 NULL，所以每次 malloc 后都应检查返回值是否为 NULL 再使用。
- `calloc(n, size)` 申请 `n*size` 字节并保证清零，适合需要初值为 0 的数组。
- `realloc(p, newsize)` 把 `p` 指向的块调整为 `newsize`：可能原地扩、也可能分配新块并拷贝旧内容后释放旧块——所以必须用返回值更新指针（`p = realloc(p, ...)` 的简写有失败丢指针风险，规范做法是先用临时变量接返回值）。
- `free(p)` 归还块；`free(NULL)` 是合法的空操作（无副作用）。

本机实测（malloc/calloc/realloc/free 全流程）：

```
$ gcc -std=c11 -Wall dyn.c -o dyn && ./dyn
malloc: a=1,2,3
calloc: b=0,0,0
realloc: a=1,2,3,4,5
freed both
```

`calloc` 的 b 确实全 0（清零保证）；`realloc` 把 3 元素扩成 5 元素且保留了原有 1,2,3。另测 `free(NULL)` 合法：

```
$ gcc -std=c11 -Wall freenull.c -o freenull && ./freenull
free(NULL) ok
```

### 6.5.3 生命周期与「所有权」直觉

动态内存的黄金法则：每一次成功的 malloc/calloc/realloc，最终都要恰好有一次对应的 free。多则重复释放（double free），少则泄漏（leak），错配都出问题（6.6 详列）。

给初学者的「所有权」直觉（正式化归后续工程课）：每块堆内存想象成有一个「负责人」——谁申请、由谁（或明确移交给谁）负责释放。写代码时问自己「这块内存谁来 free、在哪 free、只 free 一次吗」。养成 malloc 与 free 配对出现、就近考虑释放路径的习惯，是避免整类内存 bug 的根本手段。

C11 用「分配存储期」（allocated storage duration）描述这类对象：它们的生命周期从分配函数返回起，直到被 free/realloc 释放为止——不像栈对象那样自动结束，全靠你手动结束。

#### 来源与时效（本小主题）
- 一手：K&R 2nd ed §5.4 及 §7.8.5（Storage Management，`malloc`/`calloc`/`free` 用法）；附录 B（标准库）内存分配函数条目。
- 一手：ISO/IEC 9899:2011 (C11) §7.22.3（Memory management functions，`malloc`/`calloc`/`realloc`/`free` 语义：失败返回空指针、`calloc` 清零、`free(NULL)` 无操作、`realloc` 保留原内容并可搬移；具体子条号 §7.22.3.1–.5 以标准文本为准）；§6.2.4（Storage durations，allocated storage duration 生命周期）。
- 实测比对：本机 gcc 实测 `calloc` 返回全 0、`realloc` 扩容保留旧内容、`free(NULL)` 无副作用，与 C11 §7.22.3 语义一致。
- 冲突项：无。规范语义与实测一致。注意 `malloc` 内容「未初始化」——实测某次可能碰巧为 0，但不可依赖，须按规范当作不确定值。

## 6.6 悬垂/野指针、越界、泄漏陷阱

### 6.6.1 悬垂指针与释放后使用（use-after-free / double free）

悬垂指针（dangling pointer）指「指向的对象已经不存在了、但指针还留着旧地址」。最常见来源有二：free 之后继续用那个指针（use-after-free），以及返回指向已退栈的局部变量的指针。释放后使用、以及对同一块 free 两次（double free）都是未定义行为，实践中可能读到垃圾、破坏堆结构、甚至被利用为安全漏洞。

本机实测用 AddressSanitizer（`-fsanitize=address`）触发释放后使用，它能精确报出「已释放内存的读」：

```
$ gcc -std=c11 -g -fsanitize=address uaf.c -o uaf && ./uaf
=================================================================
==5436==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010 ...
READ of size 4 at 0x502000000010 thread T0
    #0 ... in main .../uaf.c:7
...
freed by thread T0 here:
    #0 ... in free ...
    #1 ... in main .../uaf.c:6
$ echo $?   # ASan 默认以退出码 1 终止
1
```

ASan 不但报出「在已释放内存上读了 4 字节」，还指出该内存是在 `uaf.c:6` 被 free 的——释放点和误用点一目了然。

防御直觉（初学者可立刻上手）：free 之后立刻把指针置 NULL（`free(p); p = NULL;`），这样后续误用会变成「解引用空指针」的显式崩溃（易发现），而不是隐蔽的悬垂读；对 NULL 再 free 也是安全空操作（6.5.2），顺带防住 double free。

### 6.6.2 野指针与未初始化指针

野指针（wild pointer）指「从未被赋予合法目标就被使用的指针」——典型是声明了指针却没初始化，它里面是栈上的垃圾地址，解引用即通向随机内存，行为未定义。

```
int *p;        // 未初始化：p 里是垃圾地址（野指针）
*p = 5;        // 未定义行为：往未知地址写
```

与悬垂指针的区别：野指针从没指对过（未初始化），悬垂指针曾经指对、但目标已失效（已 free 或已退栈）。两者后果类似，都属「指向不该碰的内存」。

防御：声明指针时若没有立即可用的目标，就初始化为 NULL；解引用前确保它已指向合法对象。这与 6.1.3 的建议一致。

### 6.6.3 缓冲区越界（buffer overflow / out-of-bounds）

越界指访问数组/分配块边界之外的元素，无论读还是写。写越界尤其危险：会踩踏相邻数据或堆管理结构，是崩溃和安全漏洞的重灾区。根子在 6.3.3 的合法范围规则——超出「首元素到末元素后一位」即未定义行为，而 C 本身不做边界检查（不像 Python 越界会抛 `IndexError`）。

本机实测用 ASan 触发堆缓冲越界写（4 元素数组写第 5 个 `a[4]`）：

```
$ gcc -std=c11 -g -fsanitize=address oob.c -o oob && ./oob
=================================================================
==5800==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x502000000020 ...
WRITE of size 4 at 0x502000000020 thread T0
    #0 ... in main .../oob.c:4
```

ASan 精确报出「在堆缓冲之外写了 4 字节」并定位到源码行，随后终止程序。没有 ASan 时，这种越界往往「碰巧不崩」而悄悄破坏数据，等到很久以后才以诡异现象爆发——这正是 C 内存 bug 难查的原因，也是 ASan 这类工具的价值。

Python 的 `list[i]` 越界立刻 `IndexError`（受控）；C 的 `a[i]` 越界是未定义行为（可能崩、可能静默错、可能被攻击），所以 C 里数组边界要自己守。

### 6.6.4 内存泄漏（memory leak）

内存泄漏指「分配了堆内存，但丢失了指向它的所有指针、再也无法 free」，于是这块内存被永久占用直到进程结束。短程序里无伤大雅，长期运行的服务里持续泄漏会耗尽内存。

本机实测用 valgrind 检出泄漏（分配 100 个 int 从不 free）：

```
$ gcc -std=c11 -g leak.c -o leak && valgrind --leak-check=full ./leak
==6164==     in use at exit: 400 bytes in 1 blocks
==6164== 400 bytes in 1 blocks are definitely lost in loss record 1 of 1
==6164== LEAK SUMMARY:
==6164==    definitely lost: 400 bytes in 1 blocks
==6164== ERROR SUMMARY: 1 errors from 1 contexts (suppressed: 0 from 0)
```

valgrind 报「definitely lost（确定丢失）400 字节 1 块」——正是那 100 个 int（100×4=400 字节）没被释放。`definitely lost` 表示程序结束时已无任何指针指向它，是最明确的泄漏。

坚持 malloc/free 配对（6.5.3 的所有权法则）；在早返回/错误分支上别忘了释放已分配的资源（大主题2 提过 C 用 goto 集中清理正是为此）。检测工具二选一即可上手：valgrind（无需重编，运行期检查泄漏与非法访问）或 `-fsanitize=address`（编译期插桩，越界/释放后使用报得更快更精确）。

### 6.6.5 陷阱小结与工具对照

把本小主题的四类陷阱与成因、检测手段并列，便于初学者建立整体地图：

- 悬垂/释放后使用/double free —— 目标已失效仍用 —— free 后置 NULL；ASan 报 heap-use-after-free。
- 野指针/未初始化 —— 从未指对就用 —— 声明即置 NULL；解引用前检查。
- 越界读写 —— 超出合法范围 —— 守住 6.3.3 范围、显式带长度；ASan 报 heap-buffer-overflow。
- 内存泄漏 —— 丢了唯一指针无法 free —— malloc/free 配对、错误分支也清理；valgrind 报 definitely lost。

共同根源都是「C 把内存管理的全部责任交给程序员、且不做运行期检查」。这既是 C 的性能与控制力来源，也是它 bug 密度高的原因——L5-14（Rust 与内存安全）正是针对这类问题在语言层给出的答案，本课只需先建立「这些坑长什么样、怎么用工具抓」的意识。

#### 来源与时效（本小主题）
- 一手：K&R 2nd ed §5.4/§7.8.5（指针悬垂与存储管理配对）；§5.3 结合 §6.3.3 的越界后果（C 不做边界检查，越界为未定义行为）。
- 一手：ISO/IEC 9899:2011 (C11) §6.2.4（对象生命周期结束后指针值变为不确定 indeterminate）；§7.22.3（`free`/`realloc` 后再使用原指针为未定义行为，重复 free 未定义）；§6.5.6（越界指针算术为未定义行为）；Annex J.2（Undefined behavior 清单，含「使用已被 free/realloc 释放的空间所指针」「越界访问」等条目）。
