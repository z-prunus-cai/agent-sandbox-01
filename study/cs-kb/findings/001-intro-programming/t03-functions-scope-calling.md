## 3.1 函数定义、参数与返回值

### 3.1.1 声明、定义与函数原型

函数**定义**（definition）给出完整实现——返回类型、名字、参数列表和函数体；函数**声明**（declaration，在 C 中也叫**原型 prototype**）只告诉编译器函数的接口（返回类型、名字、各参数类型），不含函数体。C 里一个函数只能定义一次，但可以在多处声明。

C 的函数定义骨架独占一行看：

```c
返回类型 函数名(参数类型 形参名, ...) { 函数体; return 值; }
```

C 的函数原型（声明）独占一行看，以分号结尾、无函数体：

```c
int add(int a, int b);   /* 原型：只声明接口 */
```

Python 用 `def` 一步完成定义，没有独立的「声明/原型」概念：

```python
def add(a, b):
    return a + b
```

初学者最容易混的是「声明 vs 定义」为什么要分家。直觉：编译器读你的源文件是**从上往下、一次一个文件**的；当它在第 10 行看到 `add(2,3)` 这个调用时，它必须已经知道 `add` 长什么样（要几个参数、每个什么类型、返回什么），才能正确地检查你有没有传错、并生成传参的代码。如果 `add` 的定义写在第 30 行（在调用之后），或者干脆在**另一个文件**里，编译器读到第 10 行时还不认识它——这时就需要在调用之前先放一个**原型**把接口告诉它。所以经验法则是：**原型放头文件或文件顶部，定义放某个 `.c` 里**（3.5 会展开）。Python 没有这个烦恼，因为函数名是运行时才在名字空间里查的，只要**调用发生时** `add` 已经被 `def` 过即可，源码里的先后位置不重要。

C 里 `int f();`（括号空）和 `int f(void);`（明写 `void`）**不一样**——前者在 C 中是「参数信息未知」的旧式声明，不做实参个数/类型检查；后者才是「明确无参数」。K&R 时代的旧风格会写空括号，现代 C 一律用 `(void)` 表示无参。[K&R Ch4；C11 §6.7.6.3]

### 3.1.2 参数（形参、实参）与返回值

**形参**（parameter）是函数定义括号里的名字，是函数内部的局部变量；**实参**（argument）是调用时实际传进去的值/表达式。调用时，实参被用来**初始化**对应的形参。函数通过 `return` 把一个结果带回调用点；C 中 `return` 的值类型要与声明的返回类型相容，`void` 函数不带值返回。

把形参想成函数这台「机器」入口处贴好标签的空槽位，调用时你把实参一个个塞进这些槽。函数体里对形参名的读写，操作的是这些**槽里的副本或引用**（副本还是引用取决于语言，见 3.2），跟你外面那个实参名叫什么、在哪里都无关——这就是「形参名只在函数体内可见」的由来。

最小例子（C）——形参 `a`、`b` 是局部的，返回值经 `return` 带出：

```c
int add(int a, int b) { return a + b; }
/* 调用点：int s = add(2, 3);  实参 2、3 初始化形参 a、b，返回 5 */
```

C 函数**只能返回一个值**。想「返回多个结果」的常见做法是让调用者传进指针，函数通过指针把额外结果写回去（3.2.2 的 swap 就是这个套路），或返回一个 `struct`。另一个初学者陷阱是**忽略返回值**：C 不强制你接收返回值（如 `scanf` 的返回值常被丢弃），但很多重要信息（是否出错、读了几个）就藏在返回值里。Python 侧则灵活得多——不写 `return` 时函数返回 `None`，且可用元组「一次返回多个值」：`return a, b` 实际返回一个元组 `(a, b)`。[K&R Ch4；CS61A Functions；Python Lang Ref §4]

### 3.1.3 C 无原型的隐式声明（历史陷阱）

在最古老的 C（K&R/C89 之前风格）里，如果你调用一个编译器还没见过声明的函数，编译器会**隐式假定它返回 `int`**、参数不检查——这叫「隐式函数声明」。这是 bug 温床：一旦函数实际返回的不是 `int`（比如返回指针或 `double`），调用点就会按错误的类型解释返回值，行为出错。

现代标准已经收紧：C99 起**删除了隐式 `int`/隐式函数声明规则**，调用未声明的函数不再是合法 C。但出于向后兼容，gcc 13 在默认与 `-std=c11` 下**仍只给警告**而非直接报错。本环境实测：

```
$ gcc -std=c11 -Wall implicit.c -o /dev/null
implicit.c: In function 'main':
implicit.c:2:13: warning: implicit declaration of function 'square'
    [-Wimplicit-function-declaration]
```

**看到 `implicit declaration of function ...` 警告，几乎一定是你忘了 `#include` 某个头文件，或函数原型没写。** 别忽略它——在 64 位平台上，这类不匹配（比如把返回指针的函数当成返回 `int`，指针被截断成 32 位）会直接导致崩溃。

版本与实现分账：把该情形从「警告」升级为「默认错误」是更新的标准/编译器的方向（业界普遍以 C23 与 gcc 14 起默认报错为准；本环境为 gcc 13，仍是警告——**gcc 14/C23 的确切默认行为在本机未实测，标「待核·以官方 release notes 为准」**）。Python 无对应问题：调用未定义的名字直接抛 `NameError`。[K&R Ch4；C11 §6.5.2.2；实测 gcc 13.3.0 @2026-07-26]

## 3.2 传值 vs 指针/引用传递

### 3.2.1 C 的传值语义（pass by value）

C 的参数传递**一律是传值**：调用时，实参的值被**拷贝**一份去初始化形参。函数体内对形参的任何修改，改的都是这份副本，**不会影响调用者的原变量**。

这是初学者第一个大坑。看本环境实测的「坏 swap」：

```c
void swap_bad(int a, int b){ int t=a; a=b; b=t; }  /* 只交换了副本 */
```

```
$ ./swap
after swap_bad:  x=1 y=2      <- 外面的 x、y 纹丝不动
```

`swap_bad(x, y)` 把 `x`、`y` 的**值**（1 和 2）复印进函数的私有槽 `a`、`b`，函数在自己的副本上交换得很起劲，可函数一返回，副本连同整个帧就销毁了（见 3.4），外面的 `x`、`y` 从头到尾没被碰过。记住这句话：**C 里函数拿到的永远是实参的复印件。**

### 3.2.2 C 用指针模拟「引用传递」（swap 需传指针）

既然 C 只有传值，想让函数改到调用者的变量，就传变量的**地址**（指针）。函数拿到的仍是「地址值的一份副本」，但这个副本指向的是**同一块内存**，于是通过解引用 `*p` 就能写回调用者的原变量。这就是 C 模拟「引用传递」的唯一手段。

本环境实测的「对 swap」——传 `&x`、`&y`：

```c
void swap_ok(int *a, int *b){ int t=*a; *a=*b; *b=t; }
```

```
$ ./swap
after swap_ok:   x=2 y=1      <- 通过指针写回，真的交换了
```

传的「指针值」本身还是拷贝的（你在函数里给 `a` 重新赋一个别的地址，不影响外面），但**指针指向的东西**是共享的。初学者常忘了两件事：(1) 调用时要写 `&`（`swap_ok(&x,&y)` 而非 `swap_ok(x,y)`）；(2) 函数里要写 `*` 解引用（`*a` 而非 `a`）。漏掉任一个，轻则编译报类型不符，重则把地址当整数乱改。这也解释了 3.1.2 说的「C 想返回多个值就传指针」——本质是把「输出槽」的地址交给函数去填。[K&R Ch4/Ch5；C11 §6.5.2.2]

### 3.2.3 Python 传对象引用（可变实参会被改）

Python 既不是「传值」也不是传统意义的「传引用」，准确说法是**传对象引用**（call by object reference / call by sharing）：实参传进去的是**对象的引用**，形参名与实参名在调用瞬间**绑定到同一个对象**。于是——如果对象是**可变的**（list/dict/set…），函数内**就地修改**它，调用者能看到；但如果函数把形参名**重新绑定**到一个新对象，只是改了局部名字，调用者原来的绑定不受影响。

本环境实测，一眼看清两种情况：

```python
def append_one(lst): lst.append(1)   # 就地改对象
def rebind(lst):     lst = [99]       # 只重绑局部名字
```

```
after append_one: [1]      <- 可变对象被就地修改，调用者可见
after rebind:     [0]      <- 只重绑了局部名字，调用者不受影响
```

把这套心智模型接回大主题1的「名字绑定对象」。传参就是**再贴一张名字标签到同一个对象上**。`lst.append(1)` 是「顺着标签找到那个 list 对象，往里塞东西」——对象变了，所有贴着它的标签（包括外面的 `xs`）都看得到。`lst = [99]` 是「把 `lst` 这张标签撕下来贴到一个新对象上」——只动了函数内部的标签，外面的 `ys` 还贴在老对象上。

**可变默认参数**与「以为传进去不会被改」。经验法则——**你若不想让函数改到调用者的可变对象，要么在函数内先拷贝（`lst = list(lst)`），要么约定函数「只读」**。C 与 Python 在这里的对照很值得记：C 默认拷贝值（安全但改不到外面，要改就显式传指针）；Python 默认共享对象（能改到外面，要隔离就显式拷贝）。[Python Lang Ref §4.2；CS61A Environments]

### 3.2.4 辨析：三种"传递"术语别混

「传值（pass by value）」= 拷贝值，改副本；C 的默认。「传引用（pass by reference）」= 形参是实参的别名，改形参即改实参；C **没有**真正的传引用（C++ 的 `&` 引用才是），C 用「传指针」来模拟。「传对象引用/传共享（call by sharing）」= Python 的模型：传的是对象引用，可变对象能被就地改，但重绑不外泄。

初学者只要抓住一句话即可分辨：**「函数能不能改到我外面的变量？」** C：默认不能（除非我传了指针）；Python：能改「对象内容」，不能改「我的名字绑定」。把这个问题问清楚，三种术语就不再打架。这是本报告与大主题1「两套心智模型」的直接接续。[K&R Ch5；Python Lang Ref §4.2]

## 3.3 作用域与生命周期

### 3.3.1 局部作用域与全局作用域

**作用域**（scope）指一个名字**在源码中哪些区域可见/可用**；**生命周期**（lifetime/存储期）指一个变量**在运行时哪段时间存在于内存中**。两者是不同维度，别混：作用域是「哪里能叫到它」（空间/编译期概念），生命周期是「它活多久」（时间/运行期概念）。

在 C 里，函数体内声明的变量是**局部（块）作用域**，只在该块 `{...}` 内可见；函数外声明的是**文件作用域**（俗称全局）。直觉：局部变量像「会议室里的白板」，一出这间屋（函数）别人就看不到、也用不了；全局变量像「大厅公告栏」，谁都能看。Python 类似：函数体内**赋值**的名字默认是局部的，模块顶层的是全局（模块级）。

最小易错点（C）：内层块可以声明与外层同名的变量，内层的会**遮蔽**（shadow）外层的——在内层看到的是内层那个。Python 同理：函数里给 `g` 赋值就新建了一个局部 `g`，遮蔽掉同名全局（见 3.3.3 实测 `shadow()`）。[K&R Ch4；C11 §6.2.1；Python Lang Ref §4.2]

### 3.3.2 C 的存储期与 static / extern

C 把「变量活多久」分成几种**存储期**（storage duration）：函数内普通局部变量是**自动存储期**（automatic）——进入块时诞生、离开块时销毁（住在栈上，见 3.4）；用 `static` 修饰的变量是**静态存储期**——整个程序运行期间一直存在，只初始化一次。`static` 和 `extern` 还额外控制**链接**（linkage，见 3.5）。

关键辨析（初学者极易混）：`static` 有**两个不同含义**，看它修饰谁——

- `static` 修饰**函数内局部变量**：把生命周期从「自动」变成「静态」（函数返回后值仍保留，下次进来接着用），但作用域仍是局部。
- `static` 修饰**文件作用域的函数/全局变量**：把链接从「外部」变成「内部」（只在本文件可见，别的文件链接不到），这是 3.5 的多文件话题。

本环境实测「静态局部变量记住上次的值」：

```c
int counter(void){ static int n=0; return ++n; }
```

```
$ ./stat2
1
2
3        <- n 在三次调用间持续存在、累加，而非每次重置为 0
```

`extern` 则相反，用来**声明**「这个全局变量/函数定义在别的文件里，我这里只是引用」，不分配存储。直觉：`static`（文件级）= 「私有，别人别碰」；`extern` = 「我要用的东西在别处，请链接器帮我接上」。[K&R Ch4；C11 §6.2.4 存储期、§6.2.2 链接；实测 gcc 13.3.0]

### 3.3.3 Python 的 LEGB 规则

Python 解析一个名字（读它的值）时，按固定顺序在四层名字空间里从内往外找：**L**ocal（当前函数局部）→ **E**nclosing（外层嵌套函数的作用域）→ **G**lobal（模块级）→ **B**uilt-in（内置，如 `len`、`print`）。找到第一个就停。这个记忆口诀就叫 **LEGB**。

需要标清版本/来源分账：**「LEGB」是社区/教材（Lutz 等）提炼的助记词，不是 Python 语言参考里的官方术语**；官方 §4.2 用的是 local / enclosing / global / built-in 这几层作用域的描述性说法。两者指的是同一套规则，本报告用 LEGB 作口诀、以官方 §4.2 为准。

本环境实测「读全局」与「遮蔽」：

```python
g = 10
def read_g():  return g   # 局部没有 g，沿 L->E->G 找到全局 g
def shadow():  g = 5; return g   # 函数内赋值即新建局部 g，遮蔽全局
```

```
read_g: 10 shadow: 5 g still: 10   <- read_g 读到全局；shadow 用局部；全局 g 未变
```

**在函数里给一个名字赋值，该名字在整个函数里就被当作局部的**（哪怕赋值语句在后面）——这会导致「赋值前引用」报 `UnboundLocalError` 的经典困惑。若你确实想在函数里修改外层的名字，要显式声明 `global` 或 `nonlocal`（见 3.3.4）。[Python Lang Ref §4.2；CS61A Environments]

### 3.3.4 global 与 nonlocal 声明

默认情况下 Python 函数内对名字赋值都会创建局部名字。要打破这个默认、让赋值作用到外层，需要显式声明：`global x` 让 `x` 指向**模块全局**；`nonlocal x` 让 `x` 指向**最近的外层函数作用域**（Enclosing 层）——这正是闭包能「记住并修改」外层状态的机制。

本环境实测闭包计数器（`nonlocal` 让内层函数改到外层的 `n`）：

```python
def make_counter():
    n = 0
    def inc():
        nonlocal n     # 绑定到外层 make_counter 的 n，而非新建局部
        n += 1
        return n
    return inc
```

```
closure: 1 2 3    <- 同一个闭包多次调用，n 在外层帧里持续累加
```

`nonlocal` 之于 Python 闭包，作用有点像 `static` 局部变量之于 C 函数——都能让「状态跨调用存活」。但机制不同（Python 靠闭包捕获外层帧的绑定，C 靠静态存储期），闭包的正式化留给 L3-04。易错点：`nonlocal` 要求外层**确实存在**该名字，否则语法错误；`global` 在模块顶层没有对应名字时则会**创建**一个。[Python Lang Ref §4.2.2；CS61A Environments；闭包深挖→L3-04]

## 3.4 环境模型与栈帧（模型层）

### 3.4.1 环境、帧与名字绑定

**环境模型**（environment model，CS61A 的核心工具）把「程序如何求值」讲成：每次函数调用会创建一个**帧**（frame），帧里是一张**局部绑定表**（名字 → 值/对象）；名字的解析就是在「当前帧 → 其外层帧 → … → 全局帧」这条链上逐层查找（这正是 3.3.3 LEGB 的运行时映像）。

把帧想成一张便签纸，上面记着「这次调用里，各个局部名字现在绑到什么」。调用 `add(2,3)` 时，新建一张便签，写上 `a→2, b→3`，函数体在这张便签的上下文里执行；查名字先看当前便签，没有就顺着「这张便签是从哪个环境里创建的」往外查。这个模型不需要懂任何机器细节，就能准确预测「哪个名字取到哪个值」「为什么局部改不到全局」，所以是初学者理解作用域/递归/闭包的通用心智工具。[CS61A Environments；Python Lang Ref §4.1]

### 3.4.2 调用栈：帧的建立与销毁

多个函数嵌套调用时，这些帧按**后进先出**（LIFO）的顺序管理，构成**调用栈**（call stack）：调用一个函数就**压入**（push）一张新帧，函数返回就**弹出**（pop）销毁它。当前正在执行的永远是栈顶那张帧。

调用栈的深度直觉可独占一行看（每层嵌套调用叠一张帧）：

```
main 帧  →  add 帧  →  （add 返回则 add 帧销毁，回到 main 帧）
```

为什么是栈（LIFO）？因为函数调用天然嵌套——`f` 调 `g`，`g` 一定先于 `f` 返回，最后调用的最先返回，这正是栈的语义。这张图也解释了 3.2.1「坏 swap」为何无效：`swap_bad` 的帧一返回就被弹出销毁，帧里那些交换过的副本随之蒸发。它还是理解**递归**（大主题4）的地基——递归就是同一个函数反复压入多张帧。**注意分账：帧在机器层到底怎么用寄存器和栈内存实现（System V AMD64 调用约定、`rsp/rbp`、返回地址）属于 L3-03，本处只用「压栈/弹栈」的模型直觉。** [CS61A Environments；递归深挖→大主题4；机器落地→L3-03]

### 3.4.3 局部对象的生命周期与"返回局部地址"陷阱

因为自动局部变量的生命周期随帧的销毁而结束（3.3.2），C 里有个经典致命错误：**函数返回一个指向自己局部变量的指针**。函数一返回，那张帧连同局部变量就销毁了，返回的指针成了指向「已失效内存」的**悬垂指针**（dangling pointer），后续解引用是未定义行为。

反面骨架独占一行看（切勿这样写）：

```c
int *bad(void){ int x = 42; return &x; }   /* x 随帧销毁，返回的地址已失效 */
```

这正是「作用域」与「生命周期」两个维度必须分清的现实后果——`x` 的名字作用域是局部的（编译期），`x` 的存储生命周期也是自动的（运行期随帧走）。想把结果带出函数，正确做法是：返回**值**（拷贝出去，如 3.1.2 的 `return a+b`）、用 `static`/全局延长生命周期、或由调用者提供内存（传指针进来，3.2.2）、或动态分配（`malloc`，归大主题6）。Python 无此坑——对象活在堆上、由引用计数/GC 管理，只要还有名字绑着它就不会被回收，函数可以安全「返回」一个局部构造的 list。[K&R Ch5；C11 §6.2.4 自动存储期；对照 Python Lang Ref §3 对象生命周期]

## 3.5 多文件程序结构（分离编译）

### 3.5.1 声明与定义分离、头文件

大程序拆成多个 `.c` 文件时，靠**头文件**（`.h`）共享接口：头文件里放**声明/原型**（以及类型、宏），各 `.c` 用 `#include` 把它「贴」进来；函数的**定义**（实现）放在某一个 `.c` 里。核心原则一句话：**头文件声明「有什么」，源文件定义「是什么」，每个函数/全局变量全程序只定义一次。**

最小工程骨架（本环境实测用）：

```c
/* mymath.h */  int add(int a, int b);            /* 声明 */
/* mymath.c */  int add(int a, int b){return a+b;} /* 定义 */
/* main.c   */  #include "mymath.h"  ...  add(2,3);/* 使用，靠原型对齐 */
```

回到 3.1.1——编译 `main.c` 时编译器看不到 `mymath.c`，全靠 `#include "mymath.h"` 拿到 `add` 的原型来检查调用、生成传参代码；至于 `add` 的机器码在哪，留给链接器去接（3.5.2）。这就是「声明/定义分离」存在的根本原因：让每个源文件能**独立编译**，而不必把整个程序塞进一个文件。[K&R Ch4；C11 §6.9 外部定义]

### 3.5.2 分离编译与链接

C 的构建分两步：**编译**——每个 `.c` 单独编成一个**目标文件**（`.o`），里面是机器码，但对「定义在别处的符号」留下「待填」的记号；**链接**——链接器把多个 `.o` 拼起来，把每个「待填」的符号对应到它真正的定义地址，产出可执行文件。

本环境实测（编译两个 `.o` 再链接）：

```
$ gcc -std=c11 -c mymath.c -o mymath.o
$ gcc -std=c11 -c main.c   -o main.o
$ gcc mymath.o main.o -o prog && ./prog
add(2,3)=5
```

用 `nm` 看符号，能直观看到「待填 vs 已定义」——`main.o` 里 `add` 标 `U`（undefined，待链接器填），`mymath.o` 里 `add` 标 `T`（在代码段，已定义）：

```
$ nm main.o   | grep add   ->    U add
$ nm mymath.o | grep add   ->  0000000000000000 T add
```

`U` 就是「我用到 `add` 但不知道它在哪」，`T` 就是「`add` 的实现在我这」。链接器的活儿就是把每个 `U` 接到某个 `T` 上。两个经典链接期报错由此理解：**undefined reference to `add`**（没有任何 `.o`/库提供该符号的 `T`——通常是忘了把 `mymath.o` 一起链接，或忘了实现）；**multiple definition**（两个文件都给了 `T`——同一函数/全局变量被定义了多次，违反「只定义一次」）。[K&R Ch4；C11 §6.2.2 链接；实测 gcc 13.3.0 + binutils nm]

### 3.5.3 头文件卫士与内部链接（static）

同一个头文件常被多个源文件（或经嵌套 `#include`）重复包含，若头里有类型定义等会「重复定义」报错。**头文件卫士**（include guard）用宏防止重复展开——本环境的 `mymath.h` 就用了它，骨架独占一行看：

```c
#ifndef MYMATH_H
#define MYMATH_H
/* ... 声明 ... */
#endif
```

另一半是**链接控制**（接 3.3.2 的 `static`/`extern`）：文件作用域的名字默认是**外部链接**（别的文件能通过 `extern` 引用到）；给它加 `static` 就变成**内部链接**（只在本文件可见，避免和别的文件撞名）。直觉：把只想在本文件内部用的辅助函数标 `static`，等于「设成私有」，既防命名冲突、也向读者表明「这是本文件的实现细节」。`extern int g;` 则是「`g` 的定义在别的 `.c`，我这儿只声明引用」。初学者易错点：**头文件里通常只放声明**（`extern` 变量声明、函数原型），别在头里放会产生「定义」的东西（如非 `static` 的全局变量定义、函数体），否则被多个 `.c` 包含就会 multiple definition。[K&R Ch4；C11 §6.2.2 链接、§6.10 预处理；实测头文件卫士编译通过]
