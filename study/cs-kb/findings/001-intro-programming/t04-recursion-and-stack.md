## 4.1 基例与递归例

### 4.1.1 递归的定义与「两要素」

递归（recursion）是指一个函数在自己的定义中直接或间接调用自己，用「同一个问题、更小的规模」来表达原问题的解。一个能正常终止的递归函数必须同时具备两个要素：

- 基例（base case）：规模小到可以直接给出答案、不再自我调用的情形；
- 递归例（recursive case）：把当前问题化简为一个或多个更小的子问题，调用自身求解后再组合结果。

这两者缺一不可：没有基例，递归永不停止；没有递归例，就不成其为递归。

对初学者最直观的心智模型是「自我相似的分解」：要算 `n` 的阶乘，只要先算出 `(n-1)` 的阶乘再乘以 `n`；而 `(n-1)` 的阶乘又用同样的办法交给更小的问题。这条链条必须最终撞上一个「不用再问下去」的地板，那就是基例（`0! = 1`）。

一个常见的初学者错误是把递归例写成「规模没有真正变小」，例如 `fact(n)` 里又去调用 `fact(n)` 或 `fact(n+1)`，这样永远逼近不了基例，程序不会终止（4.5 会看到它在两种语言里如何崩溃）。写递归时的自检口诀是：每次自我调用，参数是否都朝基例方向严格缩小了一步？

### 4.1.2 用数学归纳法理解「为什么对」

递归的正确性直觉与数学归纳法（mathematical induction）是同一回事，这是 CS61A / SICP 一脉反复强调的观点。论证一个递归函数正确，只需两步：

- 基础步：基例给出的答案是对的；
- 归纳步：假设对所有更小的规模函数都返回正确结果（归纳假设），证明当前规模在此前提下也返回正确结果。

只要「每次调用规模严格减小 + 基例可达」，归纳链就能覆盖所有输入。

初学者常有的心理障碍是「我脑子里跟不动这么多层调用」。关键领悟是：你不需要在脑中展开全部层次。你只需相信「更小的那次调用会把它那份工作做对」（这被 CS61A 戏称为 recursive leap of faith，递归的信心一跃），然后只检查当前这一层有没有把子结果正确地组合起来、以及基例对不对。把递归写对靠的是「相信归纳假设」，而不是「在脑内模拟递归栈」。

### 4.1.3 最小例子：阶乘与求和

阶乘与从 1 加到 n 的求和是最典型的线性递归（每次只产生一个子调用）。它们的递归定义可以直接写成：

```
fact(0) = 1
fact(n) = n * fact(n-1)      (n > 0)

summ(0) = 0
summ(n) = n + summ(n-1)      (n > 0)
```

翻成 Python 几乎是逐字照抄定义，这正是递归的表达力所在：

```python
def fact(n):
    if n == 0:            # 基例
        return 1
    return n * fact(n-1)  # 递归例

def summ(n):
    if n == 0:
        return 0
    return n + summ(n-1)
```

本机实测（Python 3.11.15）：

```
$ python3 rec.py
fact(5) = 120
summ(100) = 5050
```

`summ(100)` 得到 5050，与高斯求和公式 `n(n+1)/2 = 100·101/2 = 5050` 一致，可作为一次廉价的自校验。

这类「先递归、拿到子结果后再运算」的写法叫非尾递归（4.4 详述）——`n * fact(n-1)` 里的乘法要等里层返回后才执行，所以每一层都必须在栈上「挂起等待」，这正是 4.2 要讲的栈帧堆积的来源，也是 4.5 深递归会崩溃的根因。

## 4.2 递归 = 编译器/运行时管理的调用栈

### 4.2.1 调用栈与栈帧：递归靠什么运行

每一次函数调用（无论是否递归）都会在调用栈（call stack）上分配一块栈帧（stack frame，又称 activation record），用来保存这次调用的实参、局部变量、返回地址等。函数返回时该帧被弹出（销毁）。递归之所以「能记住每一层各自的状态」，靠的就是每层调用都有自己独立的栈帧——语言的运行时（C 由编译器生成的机器代码 + 硬件栈指针，Python 由解释器维护的帧对象栈）替你自动管理这个「待办事项的堆叠」。

对初学者最好的一句话心智模型：递归不是魔法，它只是「函数调用」这件事重复发生、被调用栈自动记账。你在 3.4（环境模型与栈帧）学到的「调用建帧、返回毁帧」在递归里被反复施加，于是形成一叠同名但状态各异的帧。

### 4.2.2 压入与展开：一进一出的两个阶段

线性递归的执行分两个阶段。先是不断压入（每遇到一次递归调用就压一个新帧，规模逐层减小）直到撞上基例；然后是逐层展开/回溯（unwind，基例返回后，挂起的上层依次拿到子结果、完成自己的运算、再返回），栈随之逐帧弹空。

本机实测（gcc 13.3.0，`-std=c11 -g -O0`）用 gdb 在 `fact(n==2)` 处断下、打印调用栈，可以直接「看见」这叠栈帧：

```
$ gcc -std=c11 -g -O0 fact.c -o fact
$ gdb -q -batch -ex "break fact if n==2" -ex run -ex "backtrace" ./fact
Breakpoint 1, fact (n=2) at fact.c:3
#0  fact (n=2) at fact.c:3
#1  0x...179 in fact (n=3) at fact.c:4
#2  0x...179 in fact (n=4) at fact.c:4
#3  0x...179 in fact (n=5) at fact.c:4
#4  0x...195 in main () at fact.c:7
```

`#0`–`#3` 是四个各自 `n` 不同的 `fact` 帧，`#4` 是 `main`——这正是「压到 n=2 尚未触底、上面挂着 n=3/4/5 三层」的快照。注意 `#1`–`#3` 的返回地址完全相同（`...179`，即 `fact.c:4` 那行 `return n*fact(n-1)` 之后），因为它们都是从同一处递归调用回来的；只有栈里的 `n` 不同。这直观说明了「代码只有一份，状态每层一份」。

C11 明确函数具有自动存储期（automatic storage duration）的局部对象在每次进入块时新建、退出时销毁，且允许函数递归调用——这正是每层递归拥有独立局部变量的规范依据。

### 4.2.3 递归的代价用「递归式」刻画

一次递归调用的总代价可以用递归式（recurrence）来记。以线性递归（如阶乘）为例，「处理规模 n 的代价 = 处理规模 n-1 的代价 + 本层常数工作」，写成：

```
T(n) = T(n-1) + O(1),  T(0) = O(1)
```

展开即 `T(n) = O(n)`：线性递归做 n+1 次调用、栈最深达 n+1 层，时间与所用栈空间都是 O(n)。

这条递归式此处只作入门直觉——它告诉你「递归深度 ≈ 栈空间占用」，为 4.5「深递归会耗尽栈」埋下伏笔。递归式的正式求解、主定理等归 L2-01/L3-01，本报告不展开。初学者需要记住的关键因果链是：递归深度 n 大 → 栈上同时挂着 O(n) 个帧 → 栈是有限资源 → 深到一定程度必然出事（4.5）。

## 4.3 树递归与重叠子问题

### 4.3.1 树递归：一层产生多个子调用

当递归例中包含两个或更多次对自身的调用时，调用关系不再是一条线，而是一棵调用树，称为树递归（tree recursion）。典型代表是朴素斐波那契：

```
fib(n) = fib(n-1) + fib(n-2)     (n >= 2)
fib(0) = 0,  fib(1) = 1
```

每个 `fib(n)` 会分叉出 `fib(n-1)` 和 `fib(n-2)` 两个子调用，子调用又各自分叉，形成一棵近似二叉的树。

线性递归是「一条向下的链」，树递归是「一棵向下的树」。树的叶子数目随深度指数增长，这就是下一节「爆炸」的来源。CS61A 把斐波那契、数硬币找零等作为树递归的标准入门例子。

### 4.3.2 朴素斐波那契的指数级爆炸

朴素 `fib` 的调用次数随 n 指数增长——因为它把同一个子问题重复算了无数遍。本机实测（Python 3.11.15，用全局计数器数 `fib` 被进入的总次数）：

```
$ python3 rec.py
fib(10) = 55,      calls = 177
fib(20) = 6765,    calls = 21891
fib(25) = 75025,   calls = 242785
fib(30) = 832040,  calls = 2692537
```

n 每增大约 5，调用次数就翻十倍量级——这就是「指数级」的体感。可核对的规律：朴素 `fib(n)` 的总调用次数恰为

```
calls(n) = 2 * fib(n+1) - 1
```

验证 `fib(10)`：`2 * fib(11) - 1 = 2*89 - 1 = 177`，与实测 177 完全吻合；`fib(30)`：`2 * fib(31) - 1 = 2*1346269 - 1 = 2692537`，与实测吻合。这条封闭式来自「二叉调用树的结点数 = 叶子数×2−1」，作为一次廉价的偏执复核。

### 4.3.3 重叠子问题：爆炸的根因与记忆化直觉

爆炸的根因是重叠子问题（overlapping subproblems）：`fib(n-1)` 和 `fib(n-2)` 的子树里会反复独立地重算 `fib(n-3)`、`fib(n-4)`……同一个值被从头算了成千上万次。

对初学者，解药的直觉有两条（细节与正式化归 L2-01/L3-01，这里只点到）：

- 记忆化（memoization）：把已经算过的 `fib(k)` 缓存起来，下次直接查表，使每个子问题只算一次，总次数从指数级降到线性级。Python 里一行 `@functools.lru_cache` 即可。
- 自底向上迭代：从 `fib(0)`、`fib(1)` 开始只保留最近两个值往上推，同样是线性时间且几乎不占栈（与 4.4 的递归↔迭代对照相通）。

并非所有树递归都「病态」。像归并排序那样的分治，两个子调用处理的是不相交的数据、没有重叠，就不会指数爆炸。指数爆炸特指「树递归 + 重叠子问题」这对组合。

#### 来源与时效（本小主题）
- 一手：Berkeley CS61A（Tree Recursion 讲次；斐波那契指数爆炸、重叠子问题与记忆化），https://cs61a.org/ （核实 2026-07-26）。
- 实测比对：本机 Python 3.11.15 计数朴素 `fib` 调用次数，得 177 / 21891 / 242785 / 2692537，与封闭式 `2*fib(n+1)-1` 逐点核对一致（`fib(10)`、`fib(30)` 均吻合）。
- 冲突项：无。「树递归 + 重叠子问题 → 指数爆炸」为 CS61A 一手结论，实测独立坐实。

## 4.4 尾递归与迭代等价

### 4.4.1 尾调用与尾递归

尾调用（tail call）指一次函数调用是当前函数「最后要做的动作」——调用返回后，本函数不再对结果做任何额外运算，直接把它当作自己的返回值。如果这个尾调用是对自身的递归，就叫尾递归（tail recursion）。对照一下：

```
def fact_nontail(n):
    return n * fact_nontail(n-1)   # 非尾递归：返回前还要做乘法

def fact_tail(n, acc=1):
    return fact_tail(n-1, acc*n)   # 尾递归：调用即最终结果，无后续运算
```

区别在于「递归调用返回后还有没有活要干」。非尾递归（如 `n * fact(n-1)`）必须保留本层栈帧等子结果回来再乘；尾递归则把中间结果用累加器（accumulator）参数一路带下去，返回后无事可做。

理论上尾递归可以被编译器优化成「复用同一个栈帧」（尾调用优化，TCO），从而不增长栈——这在很多函数式语言（如 Scheme，SICP 明确要求实现 TCO）里成立。但在 C 和 CPython 里不能想当然（见 4.4.3）。

### 4.4.2 递归 ↔ 迭代对照

任何递归都能改写成迭代（用显式循环 + 必要时显式的栈/累加器），尾递归尤其能「机械地」翻成循环，两者等价。以阶乘为例三种写法结果相同：

```
fact_rec(10)  == fact_tail(10) == fact_iter(10)
```

本机实测（Python 3.11.15）：

```
$ python3 tail.py
3628800 3628800 3628800
```

`fact_iter` 的循环骨架就是把「累加器 + 逐步逼近基例」显式化：

```python
def fact_iter(n):
    acc = 1
    while n > 0:
        acc *= n
        n -= 1
    return acc
```

递归更贴近「问题的数学定义」、可读性好（尤其树递归、树/图遍历）；迭代不占用调用栈、常数因子通常更小、不会因深度而崩溃。线性的、天然尾递归形状的问题（阶乘、求和、遍历链表）优先考虑迭代或改写；分治、树形结构的问题递归往往更清晰。

### 4.4.3 CPython 不做尾调用优化（重要陷阱）

一个高频误解是「把递归写成尾递归就不会栈溢出了」——在 CPython 里这是错的。CPython 有意不实现尾调用优化，尾递归照样每层新建帧、照样受递归上限约束。本机实测（Python 3.11.15）：一个纯尾递归的 `down(n)` 递归到十万层仍抛 `RecursionError`：

```python
def down(n):
    if n == 0:
        return 0
    return down(n-1)   # 尾调用，但 CPython 不优化
```

```
$ python3 tail.py
...
tail-recursive down(100000): RecursionError (no TCO in CPython)
```

C（gcc）则相反：是否把尾递归优化成循环取决于优化等级，`-O2` 常能消除尾调用、`-O0` 通常不能——所以 C 里「尾递归会不会爆栈」依赖编译选项，不可依赖为语言保证。结论对初学者：在 C/Python 里，不要把「写成尾递归」当作防止栈溢出的手段；要真正避免深栈，就改写成显式迭代。

## 4.5 两种失败面：C 栈溢出→SIGSEGV / Python→RecursionError

### 4.5.1 Python：RecursionError 与递归上限

CPython 用一个「最大递归深度」软上限来拦截失控递归：递归层数超过该上限时，解释器主动抛出 `RecursionError`（Python 3.5 起为此专设的异常类，是 `RuntimeError` 的子类）。官方文档原文：「当解释器检测到超过最大递归深度（见 `sys.getrecursionlimit()`）时抛出。」这个上限可用 `sys.getrecursionlimit()` 读、`sys.setrecursionlimit()` 改。

本机实测（Python 3.11.15）默认上限为 **1000**（官方文档未把具体数值写死，此 1000 为本基线实测值）：

```
$ python3 rec.py
default recursionlimit = 1000
```

一个无限递归会被干净地转成可捕获的异常，而不是让进程崩溃：

```
$ python3 recerr.py
caught: RecursionError - maximum recursion depth exceeded
after setrecursionlimit(50): caught RecursionError
```

`RecursionError` 是一个普通异常，可以 `try/except` 捕获——这是「受控失败」。之所以设这个软上限，官方说得很直白：「这个限制用来防止无限递归导致 C 栈溢出、进而使 Python 崩溃」。也就是说，Python 层的 `RecursionError` 是一道护栏，替你挡在了下一节 C 那种「硬崩溃」之前。

不要随手把 `setrecursionlimit` 调得很大来「解决」深递归——官方警告最高上限与平台相关，设得太高会真的击穿 C 栈、导致解释器直接崩溃（那时就退化成 4.5.2 的硬崩溃、不再有异常可捕获）。正确做法通常是把算法改成迭代。

### 4.5.2 C：栈溢出直接 SIGSEGV（硬崩溃）

C 没有递归深度护栏。无限或过深的递归会不断压栈，一旦越过操作系统分配的栈区边界，就触发段错误（SIGSEGV），进程被内核杀死——没有异常、没有优雅提示，直接崩溃。本机实测（gcc 13.3.0，`-std=c11 -O0`，栈上限 `ulimit -s` = 8192 KiB = 8 MB）：

```c
void recurse(void) {
    depth++;
    char buf[1024];   /* 每帧吃掉约 1 KB 栈 */
    buf[0] = (char)depth;
    recurse();        /* 无基例：无限递归 */
}
```

```
$ gcc -std=c11 -O0 overflow.c -o overflow
$ ./overflow
Segmentation fault
$ echo $?
139
```

退出码 139 = 128 + 11，其中 11 是 SIGSEGV 的信号号——这是「栈溢出撞进未映射内存页」的典型现场。每帧里的 `char buf[1024]` 是为了让栈更快耗尽、便于快速复现；真实程序里即使每帧很小，只要深度足够也一样会溢出。

- Python：软上限（默认实测 1000）→ 抛 `RecursionError` → 可捕获、可恢复（受控失败）。
- C：无上限护栏 → 越过栈边界 → SIGSEGV / 退出码 139 → 进程被杀（硬失败），且行为属未定义，具体崩溃点依栈大小、每帧大小、优化级别而变。

### 4.5.3 定位与修复直觉

两种失败面对应两套廉价定位手段。C 侧：崩溃后用 gdb 看 `backtrace`，若看到成百上千层同一个函数帧，基本就是无限/过深递归；也可用 `ulimit -s` 查看/调整栈上限辅助判断。Python 侧：`RecursionError` 的 traceback 会打印大量重复帧，同样一眼可辨。

修复直觉（细节归后续课程）：

- 先检查是不是漏了基例或递归例没让规模缩小（4.1 的自检口诀）——绝大多数「递归崩溃」其实是逻辑 bug，不是深度不够。
- 确属合理的深递归（如深树遍历），优先改写成迭代 + 显式栈；这既避开 Python 的软上限，也避开 C 的硬栈边界。
- 不要靠调大 `setrecursionlimit`（Python）或 `ulimit -s`（C）来治本——那只是把边界往后挪，深到一定程度仍会崩。

#### 来源与时效（本小主题）
- 一手：Python 3.11 官方文档——`RecursionError`「当解释器检测到超过最大递归深度时抛出，派生自 `RuntimeError`（3.5 起）」，https://docs.python.org/3.11/library/exceptions.html ；`sys.getrecursionlimit`/`sys.setrecursionlimit`「限制防止无限递归造成 C 栈溢出并使 Python 崩溃」「过高的限制可能导致崩溃」，https://docs.python.org/3.11/library/sys.html （均核实 2026-07-26）。
- 一手：ISO/IEC 9899:2011 (C11)——C 未对递归深度设限；栈耗尽属实现层现象、越界访问为未定义行为（标准不保证诊断）。
- 实测比对：本机 Python 3.11.15 实测默认 `recursionlimit=1000`、无限递归抛 `RecursionError`、`setrecursionlimit(50)` 后仍抛；本机 C（gcc 13.3.0）无限递归得 `Segmentation fault`、退出码 139（=128+11=SIGSEGV），栈上限 8192 KiB。数值与官方语义交叉一致。
- 待核 / 分账：默认递归上限「1000」为本基线（CPython 3.11.15）实测值，官方文档未在正文写死该数字，跨版本/发行版可能不同——引用时以「实测@基线」为准，勿当作规范常量。退出码 139 依赖 POSIX「128+信号号」约定，非 C 标准。
- 冲突项：无。Python 官方语义与实测一致；C「无护栏、硬崩溃」与实测一致。
