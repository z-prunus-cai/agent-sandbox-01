## 7.1 非死锁并发 bug

### 7.1.1 两大家族：原子性违背与顺序违背

非死锁 bug 是并发 bug 里的**多数派**。OSTEP Ch32 引用 Lu 等人 2008 年对 MySQL、Apache、Mozilla、OpenOffice 四个成熟开源项目的实证研究（ASPLOS '08）：共分析 105 个并发 bug，其中 **74 个是非死锁 bug、31 个是死锁 bug**；而在这 74 个非死锁 bug 里，**约 97% 属于两类——原子性违背（atomicity violation）与顺序违背（order violation）**。也就是说，只要盯紧这两种模式，就能覆盖绝大多数不涉及死锁的并发错误。

各项目的分布（OSTEP 图 32.1，核实 2026-07-29）：

```
应用        非死锁   死锁
MySQL        14       9
Apache       13       4
Mozilla      41      16
OpenOffice    6       2
合计         74      31
```

对初学者，先建立一个区分：非死锁 bug 里程序**还在跑**，只是结果错了或崩了；而死锁（7.2 起）是程序**整个卡住不动**。二者根因不同、修法也不同，所以要分开学。这份实证数据的意义在于告诉你"该优先防哪种"——不是所有并发 bug 都同等常见，原子性和顺序违背才是日常写多线程代码最该警惕的两个坑。

### 7.1.2 原子性违背（atomicity violation）

原子性违背指的是：一段**本应作为一个不可分割整体执行**的代码，实际执行时被其他线程插了进来，破坏了程序员默认的"这几步中间不会有人动手脚"的假设。Lu 等人的正式定义是"多次内存访问之间期望的串行性被破坏了（一段代码本想是原子的，但执行时没强制其原子性）"。

OSTEP Ch32 给的 MySQL 真实例子（`atomicity.c`）：

```
Thread 1::
  if (thd->proc_info) {          // (a) 检查非空
      fputs(thd->proc_info, ...); // (b) 使用它
  }

Thread 2::
  thd->proc_info = NULL;          // 把它清空
```

线程 1 默认"检查(a)"和"使用(b)"之间 `proc_info` 不会变。但若线程 1 刚过了 (a) 检查、还没执行 (b)，就被切换到线程 2 把 `proc_info` 置为 `NULL`，线程 1 恢复后 `fputs` 就会对空指针解引用而崩溃。

修法是把这段"检查+使用"用**同一把锁**罩成真正的原子块（OSTEP 图 32.3）：给 `proc_info` 配一把 `proc_info_lock`，线程 1 的 if/fputs 整体加锁、线程 2 的置空也加同一把锁。关键不是"加了锁"这么简单，而是**所有访问同一份数据的地方都要用同一把锁**——只锁一处，另一处照样能插进来。初学者最常犯的错，就是只给"写"加锁却漏了"读"，或读写用了不同的锁。

本机用 ThreadSanitizer 复现一个最小原子性违背（两线程各对全局 `counter` 自增十万次、无锁），gcc 13.3.0 `-fsanitize=thread`，Linux 6.18.5 x86_64 @2026-07-29，真实输出：

```
WARNING: ThreadSanitizer: data race (pid=26255)
  Location is global 'counter' of size 4 at 0x... (race+0x4014)
SUMMARY: ThreadSanitizer: data race race.c:3 in inc
```

`counter++` 看似一条语句，机器上却是"读—加—写"三步，两线程交错就会丢更新——这正是原子性违背的最小形态。TSan 的检测原理（影子内存 + happens-before 追踪）与"数据竞争即 UB"的语言级定义归 L4-05 CP-07，本报告只借它作复现工具。

### 7.1.3 顺序违背（order violation）

顺序违背指的是：两组内存访问之间**期望的先后顺序**没有被强制，导致"本该先发生的"可能后发生。Lu 等人的正式定义是"两组内存访问之间期望的顺序被颠倒了（A 本应总在 B 之前执行，但执行时没强制这个顺序）"。

OSTEP Ch32 的 Mozilla 例子（`ordering.c`）：

```
Thread 1::
  void init() {
      mThread = PR_CreateThread(mMain, ...);  // 创建线程，设置 mThread
  }

Thread 2::
  void mMain(...) {
      mState = mThread->State;                 // 使用 mThread
  }
```

线程 2（`mMain`）默认 `mThread` 已经被线程 1 初始化好了。但如果新线程被创建后**立刻**跑起来，`mThread` 可能还没被赋值（仍是 `NULL`），线程 2 就会空指针崩溃。这里没有"互相插入"的原子性问题，而是纯粹的"谁先谁后"没保证。

修法是**用条件变量（或信号量）强制顺序**（OSTEP 图 32.5）：加一个状态变量 `mtInit` 和条件变量 `mtCond`；线程 1 初始化完后 `mtInit=1` 并 `signal`；线程 2 在用 `mThread` 前先

```
pthread_mutex_lock(&mtLock);
while (mtInit == 0)
    pthread_cond_wait(&mtCond, &mtLock);
pthread_mutex_unlock(&mtLock);
```

若线程 2 跑在前面，它会在 `wait` 上睡着等信号；若跑在后面，它检查到 `mtInit==1` 直接放行。注意这里必须用 `while` 而不是 `if` 重检谓词——这条"虚假唤醒纪律"的正确性论证归 L4-05 CP-09，本课只需记住"顺序问题找条件变量"。一个初学者易混点：原子性违背靠**加锁**（保证不被插入），顺序违背靠**条件变量**（保证先后），两者用的工具不同、别张冠李戴。

- OSTEP Ch32「Common Concurrency Problems」[V1.20]（网页版 PDF，核实 2026-07-29）：图 32.1 的 105/74/31 统计与各项目分布、97% 结论、原子性/顺序违背的定义、`atomicity.c`/`ordering.c` 例子与修法。

## 7.2 死锁四条件（Coffman）

### 7.2.1 什么是死锁

死锁（deadlock）指一组线程/进程各自持有某些资源、同时又在等待这组里别人持有的资源，形成一个**首尾相接的等待环**，结果谁也无法前进、集体永久卡住。最经典的最小例子是 AB–BA 加锁（OSTEP 图 32.6）：

```
Thread 1:                 Thread 2:
  pthread_mutex_lock(L1);   pthread_mutex_lock(L2);
  pthread_mutex_lock(L2);   pthread_mutex_lock(L1);
```

注意死锁**不一定**发生——它只在特定交错下才触发：若线程 1 拿到 L1 后恰好被切走，线程 2 拿到 L2 再去要 L1，此刻两者互等，死锁成立。这种"依赖调度时序、时有时无"的特性正是死锁难查的原因：测试一万次都不复现，上线偏偏卡住。

对初学者要澄清一个常见误解：死锁 ≠ 程序慢，也 ≠ 死循环（死循环还在消耗 CPU 空转，那叫活锁 livelock，见 7.3.4）。死锁是**所有相关线程都进入睡眠等待、CPU 占用为零**却永不醒来。

### 7.2.2 四个必要条件

Coffman、Elphick、Shoshani 1971 年的经典论文归纳出死锁发生必须**同时**满足的四个条件（OSTEP Ch32 转述 [C+71]）：

```
1. 互斥（mutual exclusion）：资源是独占的，一次只能一个线程持有（如一把锁）。
2. 持有并等待（hold-and-wait）：线程已持有至少一份资源，同时又在等待获取别的资源。
3. 不可抢占（no preemption）：资源不能被强行从持有者手里夺走，只能由其自愿释放。
4. 循环等待（circular wait）：存在一条线程的环形链，链上每个线程持有的资源正被环里下一个线程请求。
```

**这四条是"必要"条件——只要其中任意一条不成立，死锁就不可能发生**（OSTEP 原文："If any of these four conditions are not met, deadlock cannot occur"）。这一句直接给出了 7.3 死锁预防的全部思路：想预防死锁，破坏四条里的任意一条即可。

初学者可以这样记住四条的"人话版"：互斥="这东西一次只给一个人用"；持有并等待="我攥着这个还想再要那个，但不肯先放手"；不可抢占="没人能从我手里抢走"；循环等待="我等你、你等他、他又等我"。四者缺一，环就断了。

### 7.2.3 "必要" vs "必要且充分"的分歧

一个需要显式标注的跨来源分歧：这四条到底是"必要"还是"必要且充分"？

OSTEP 与 Silberschatz 都表述为**必要条件**（necessary）——四条同时成立只是死锁的**前提**，不保证一定死锁（前面 7.2.1 已说明 AB–BA 也可能侥幸不触发）。而部分教材/课程（如一些高校讲义）把 Coffman 条件表述为"必要且充分"（necessary and sufficient），这在**单实例资源**的资源分配图模型下才成立。

更精确的说法（Silberschatz）：**资源分配图中存在环，是死锁的必要条件；当每类资源只有单个实例时，环也是充分条件（有环即死锁）；但当某类资源有多个实例时，有环只是必要而非充分**——环存在也可能因为环外某进程释放实例而解开。本报告采信 OSTEP/Silberschatz 的"四条件必要 + 单实例下环才充分"这一更严谨表述，把"必要且充分"的说法标为**依模型而定的口径差异**，不和稀泥。

#### 来源与时效
- Coffman, Elphick, Shoshani「System Deadlocks」ACM Computing Surveys 3:2, June 1971（OSTEP [C+71]，一手经典）：四个条件的原始归纳。
- OSTEP Ch32「Deadlock Bugs / Conditions for Deadlock」（核实 2026-07-29）：四条件的现代表述、AB–BA 例子、"任一条不成立则无死锁"、死锁依赖调度时序。
- Silberschatz《Operating System Concepts》Ch7/8「Deadlocks」（安全/资源分配图口径锚点）：四条件表述为"必要"；资源分配图有环为必要、单实例下为充分。
- 冲突显式标注：四条件是"必要"（OSTEP/Silberschatz）vs 部分讲义作"必要且充分"——后者只在单实例资源分配图模型下成立，本报告采信前者。
- CS162 现行 L13「Deadlock」（cs162.org）：与 OSTEP 一致，四条件 + 资源分配图找环。

## 7.3 死锁预防

### 7.3.1 总思路：破坏四条件之一

死锁预防（prevention）的核心逻辑直接来自 7.2.2 的"必要条件"：既然四条件缺一死锁就不可能发生，那就**在设计上让四条里的某一条永远不成立**。OSTEP Ch32 逐条给出了四种破坏手段，下面分述，并标注各自的代价。

预防与"避免"（7.4）的区别要先厘清：预防是**静态地、结构性地**让某条件不可能成立（如规定所有锁按固定顺序获取），不需要运行时算账；避免则是**运行时**每次分配前动态判断"这次给了会不会走进死路"。初学者常把两者混为一谈，记住"预防=改结构、避免=每次算"即可。

### 7.3.2 破坏循环等待：全局锁序（最实用）

破坏"循环等待"是**工程上最常用、最实用**的预防手段。做法是给所有锁定一个**全序**（total ordering），规定任何线程都必须**按同一顺序**获取锁。例如系统只有 L1、L2 两把锁，就规定"永远先 L1 后 L2"——这样就不可能出现"一个线程持 L1 等 L2、另一个持 L2 等 L1"的环。

复杂系统里锁很多，完整全序难做，可退而用**偏序**（partial ordering）：只对那些会被同时持有的锁组定序。OSTEP 举了 Linux 内存映射代码（`mm/filemap.c`）的真实例子，其源码顶部注释列了十组锁获取顺序，如"i_mutex 先于 i_mmap_rwsem"。

当一个函数要拿两把锁、而调用方可能以任意顺序传入时，有个巧妙技巧——**按锁的内存地址定序**（OSTEP TIP）：

```
if (m1 > m2) {                 // 按地址从高到低
    pthread_mutex_lock(m1);
    pthread_mutex_lock(m2);
} else {
    pthread_mutex_lock(m2);
    pthread_mutex_lock(m1);
}
```

无论调用方传 `do_something(L1,L2)` 还是 `do_something(L2,L1)`，实际加锁顺序都由地址大小决定，因而全局一致、不会成环。

锁序的代价：它只是**约定**，编译器/运行时不强制，粗心的程序员一处违反就可能死锁；且它要求对整个代码库"谁在何处调用了谁、会同时持有哪些锁"有深入理解，一处遗漏即出事。锁序作为并发算法惯用法的更深讨论归 L4-05 CP-10。

### 7.3.3 破坏持有并等待：一次性原子获取全部锁

破坏"持有并等待"的做法是：让线程**一次性、原子地拿到它需要的所有锁**，而不是拿一个、再去等下一个。OSTEP 的实现是加一把全局"预防锁"把整个获取过程罩起来：

```
pthread_mutex_lock(prevention);  // 获取开始
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);
...
pthread_mutex_unlock(prevention); // 获取结束
```

拿到 `prevention` 后，中途不会有别的线程插进来抢锁，于是"持有一部分、等待另一部分"的状态被消除。

代价有两点：其一，**破坏封装**——调用一个函数前你必须预先知道它内部会用到哪些锁并提前全拿到，这与"隐藏实现细节"的模块化设计相冲突；其二，**降低并发度**——所有锁都在最开始一次拿齐（而非用到时才拿），持锁时间被拉长，别的线程等待更久。

### 7.3.4 破坏不可抢占：trylock 与活锁

破坏"不可抢占"靠 `pthread_mutex_trylock()`：它尝试获取锁，拿到返回成功，拿不到**立即返回错误码而不阻塞**。于是可以构造"拿不到第二把就把第一把也放掉、退回重试"的协议（OSTEP）：

```
top:
  pthread_mutex_lock(L1);
  if (pthread_mutex_trylock(L2) != 0) {
      pthread_mutex_unlock(L1);   // 放掉已持有的，避免持有并等待
      goto top;
  }
```

这样即使另一线程以相反顺序（L2 后 L1）加锁也不会死锁——因为谁都不会攥着一把死等另一把。

新问题是**活锁（livelock）**：两个线程可能反复地"各拿到一把、各发现拿不到第二把、各自退回重来"，无限循环，谁都不推进。它不是死锁（线程一直在跑、在消耗 CPU），但同样卡住了进展。解法之一是重试前加一段**随机延迟**，降低两者再次撞车的概率。

OSTEP 也点明：严格说这一招并没有真的实现"抢占"（没人从别人手里夺锁），而是让线程**优雅地放弃自己已持有的锁**（自我抢占）。它还有隐患：若中途已分配了别的资源（如 malloc 的内存），退回时必须小心全部释放，否则泄漏。活锁的算法层处理归 L4-05 CP-10。

### 7.3.5 破坏互斥：无锁（lock-free）

破坏"互斥"意味着**根本不用锁**——用硬件原子指令（如比较并交换 compare-and-swap, CAS）直接构造数据结构。OSTEP 给的原子自增例子：

```
void AtomicIncrement(int *value, int amount) {
    do {
        int old = *value;
    } while (CompareAndSwap(value, old, old + amount) == 0);
}
```

不加锁，而是"读旧值 → 试图用 CAS 把它换成新值 → 若期间被别人改过则失败、重试"。既然没有锁，就不可能死锁。

代价与边界：无锁不是万能——上面循环仍可能**活锁**（一直 CAS 失败重试）；且构造一个真正可用的无锁链表/队列（支持插入、删除、查找）极其困难，还会遇到 ABA 等问题。无锁/wait-free 数据结构、ABA、安全内存回收属于 L4-05 CP-10 的主场，本报告只指出"破坏互斥=走无锁路线"这一预防思路，不做算法纵深。

#### 来源与时效
- OSTEP Ch32「Prevention」（核实 2026-07-29）：四条件逐条破坏（循环等待/全局锁序 + 地址定序 TIP、持有并等待/预防锁、不可抢占/trylock + 活锁 + 随机延迟、互斥/CAS 无锁），Linux `mm/filemap.c` 偏序真实例子。
- Coffman 1971 [C+71]：预防思路的理论依据（破坏必要条件之一）。
- Silberschatz Ch8「Deadlock Prevention」：与 OSTEP 一致的四条件逐条破坏框架（互斥/持有并等待/不可抢占/循环等待），可交叉印证。
- 分账指路：锁序惯用法、无锁数据结构、ABA、活锁算法层处理归 L4-05 CP-10。
- 交叉一致，无冲突（OSTEP 侧重锁的工程视角，Silberschatz 侧重通用资源的教材视角，互补不矛盾）。

## 7.4 死锁避免：银行家算法

### 7.4.1 安全状态与安全序列

死锁避免（avoidance）不改结构，而是在**每次分配资源前**动态判断："如果现在把这份资源给它，系统会不会陷入无法保证所有进程都能完成的境地？"若会，就**推迟**这次分配。判断的核心概念是**安全状态**（safe state）。

一个状态是**安全的**，当且仅当存在一个**安全序列**（safe sequence）——即能把所有进程排成一个顺序 <P₁, P₂, …, Pₙ>，使得对每个 Pᵢ，它还需要的资源量都能被"当前可用资源 + 排在它前面的进程完成后归还的资源"满足。只要这样的顺序存在，系统就一定能让所有进程逐个跑完、不死锁。

```
安全 ⟹ 无死锁；不安全 ⟹ 可能死锁（不必然，但避免策略保守地拒绝进入不安全态）
```

把它想成银行放贷。银行（OS）手里有有限现金（资源），每个客户（进程）事先声明了自己的**最大需求**。银行每次只在"放这笔款后，仍能靠现有现金 + 陆续还款满足至少一个客户的全部剩余需求、让他还清、再腾出钱满足下一个……直到所有人都还清"时才放款。这个"总能找到一条把所有人都送到终点的路"就是安全序列，Dijkstra 因此称之为银行家算法。

### 7.4.2 四个矩阵与 Need

银行家算法（多实例资源、Silberschatz 表述）维护四组数据，设 n 个进程、m 类资源：

```
Available[m]      ：每类资源当前可用数量
Max[n][m]         ：每个进程对每类资源声明的最大需求
Allocation[n][m]  ：每个进程当前已分配的数量
Need[n][m]        ：每个进程还需要的数量
```

三者关系（逐进程逐资源）：

```
Need[i][j] = Max[i][j] − Allocation[i][j]
```

Max 必须**事先声明**是这个算法最大的前提——它要求预先知道每个进程一生的资源上限。这也是它现实中少用的原因：多数场景下进程会要多少资源事先并不知道。

### 7.4.3 安全算法（判断当前状态是否安全）

给定上面四个矩阵，安全算法判断"是否存在安全序列"（Silberschatz 安全算法）：

```
1. Work = Available 的副本；Finish[i] = false（所有 i）
2. 找一个 i 使得：Finish[i] == false 且 Need[i] ≤ Work（逐分量比较）
   若找不到这样的 i，跳到第 4 步
3. Work = Work + Allocation[i]；Finish[i] = true；回到第 2 步
4. 若所有 Finish[i] == true，则系统处于安全状态；否则不安全
```

不断找一个"剩余需求能被当前可用资源满足"的进程，假设它跑完并归还全部已占资源（Work += Allocation[i]），可用池变大，再找下一个……若能把所有进程都这样"消化"掉，就找到了安全序列；若中途卡住（谁的 Need 都不满足），则不安全。

### 7.4.4 资源请求算法（要不要批准这次请求）

当进程 Pᵢ 发出资源请求 Requestᵢ 时（Silberschatz 资源请求算法）：

```
1. 若 Request_i ≤ Need[i]  否则报错（超出声明的最大需求）
2. 若 Request_i ≤ Available 否则 Pi 必须等待（资源暂时不够）
3. 试探性分配：
     Available   = Available   − Request_i
     Allocation[i] = Allocation[i] + Request_i
     Need[i]     = Need[i]     − Request_i
   然后跑"安全算法"：若结果安全，正式批准；若不安全，撤销这次试探性分配、让 Pi 等待
```

核心是第 3 步的"先假装给了，跑一遍安全检查，安全才真给、不安全就回滚"。这就是避免比预防"聪明"的地方——它不一刀切禁止某种结构，而是每次动态放行安全的分配。

### 7.4.5 经典例子（本机数值核对）

用 Silberschatz 经典例子：5 个进程 P0–P4，3 类资源 A/B/C，Available=(3,3,2)。

```
        Allocation      Max          Need = Max − Allocation
        A  B  C       A  B  C          A  B  C
P0      0  1  0       7  5  3          7  4  3
P1      2  0  0       3  2  2          1  2  2
P2      3  0  2       9  0  2          6  0  0
P3      2  1  1       2  2  2          0  1  1
P4      0  0  2       4  3  3          4  3  1
```

本机 Python 跑安全算法（Py3.11.15 @2026-07-29），真实输出：

```
Need = [[7,4,3],[1,2,2],[6,0,0],[0,1,1],[4,3,1]]
initial safe? True  sequence P [1, 3, 4, 0, 2]
after P1 req(1,0,0): avail [2,3,2] safe? True  seq P [1, 3, 4, 0, 2]
```

初始状态**安全**，安全序列 <P1, P3, P4, P0, P2>（与 Silberschatz 教材结论一致）。走法：可用 (3,3,2) 先满足 P1 的 Need (1,2,2)，P1 跑完归还 (2,0,0)→可用 (5,3,2)；再满足 P3 (0,1,1)→归还后 (7,4,3)；再 P4→P0→P2，全部完成。

P1 请求 (1,0,0)，试探后可用变 (2,3,2)，跑安全算法仍安全（序列不变），故**批准**。而若此时 P4 请求 (3,3,0)，因 (3,3,0) 已超出可用 (2,3,2)，第 2 步就不满足，P4 必须等待。这演示了资源请求算法如何逐次把关。

#### 来源与时效
- Dijkstra「Een algorithme ter voorkoming van de dodelijke omarming」EWD108, 1964（OSTEP [D64]，银行家算法原始来源，Dijkstra 最早提出死锁并称之为"deadly embrace"致命拥抱）。
- Silberschatz《Operating System Concepts》Ch8「Deadlock Avoidance / Banker's Algorithm」（安全算法、资源请求算法、四矩阵、经典 P0–P4 例子的一手锚点）。
- OSTEP Ch32「Deadlock Avoidance via Scheduling」（核实 2026-07-29）：把避免定位为"需要全局知道各线程会拿哪些锁、据此调度"，明确点名 Dijkstra 银行家算法 [D64]，并指出其只适用于嵌入式等**已知全部任务与所需锁**的受限场景、且会限制并发，非通用方案。
- 本机实证（补充，不替代比对）：Python 数值模拟核对安全序列 <P1,P3,P4,P0,P2> 及 P1 请求 (1,0,0) 后仍安全，Py3.11.15 @2026-07-29，输出与 Silberschatz 教材一致。
- 交叉一致：OSTEP 给定位与局限、Silberschatz 给完整过程，互补印证；安全序列经本机核对，无冲突。

## 7.5 死锁检测与恢复

### 7.5.1 总思路：允许死锁发生，事后收拾

检测与恢复（detect and recover）是第四条思路：**不预防也不避免，允许死锁偶尔发生**，靠一个检测器定期检查、一旦发现就采取行动打破它。OSTEP Ch32 直言：如果死锁**很罕见**（比如系统一年才冻一次），那么"发现了就重启"这种"非解法"反而是相当务实的——这被戏称为**鸵鸟策略**（把头埋进沙子假装看不见）。

这背后是 OSTEP 引 Tom West 的工程格言"并非所有值得做的事都值得做好"：若坏事极少发生、代价又小，就不必花大力气去防。这解释了为什么通用操作系统（如 Linux）对用户态锁死锁基本**不做**内置预防/避免——成本太高、场景太杂，交给程序员用锁序自律更划算。

### 7.5.2 检测：资源分配图 / 等待图找环

检测的核心是**建图找环**。系统周期性地构建一张反映"谁持有什么、谁在等什么"的图，检查其中有没有环——有环即（可能）死锁。两种常见图：

```
资源分配图（resource-allocation graph）：
  进程 →（请求边）→ 资源类   +   资源类 →（分配边）→ 进程
  单实例资源：有环 ⟺ 死锁
  多实例资源：有环是死锁的必要非充分条件（需进一步用检测算法确认）

等待图（wait-for graph）：
  由资源分配图"折叠掉资源结点"得到，只剩 进程 →（等待）→ 进程
  适用于每类资源单实例：有环 ⟺ 死锁
```

初学者要抓住 7.2.3 已铺垫的那条纪律：**单实例资源，有环就是死锁；多实例资源，有环只是嫌疑，还得跑一个类似 7.4.3 安全算法的检测算法确认**（因为环外进程释放实例可能解开环）。检测器多久跑一次是个权衡：跑太勤开销大，跑太稀死锁存在久、卷入的进程多、恢复更贵。

数据库系统是检测+恢复的典型用户（OSTEP）：DBMS 定期建资源图查环，发现死锁就中止（abort）并回滚其中一个事务。造 AB–BA 死锁后可用 `gdb` 附加看两线程互等的调用栈、或 `cat /proc/[pid]/task/*/stack` 看内核栈来定位（本机实证机会，本报告未实跑，如实标注**未取**）。

### 7.5.3 恢复策略

检测到死锁后如何打破环，常见策略（Silberschatz「Recovery from Deadlock」）：

```
一、终止进程（process termination）
   1) 中止所有死锁进程：简单粗暴，代价大（已完成的工作全丢）
   2) 逐个中止：每次杀一个再重跑检测，直到环被打破；
      选"受害者"看代价（已运行时间、已用资源、还需多少等）

二、资源抢占（resource preemption）
   1) 选受害者：抢谁的资源、抢哪些，按代价最小选
   2) 回滚（rollback）：被抢的进程回退到某个安全检查点重启
   3) 防饥饿（starvation）：避免总选同一个进程当受害者，
      否则它反复被回滚、永远完不成——把"被回滚次数"计入代价
```

OSTEP 给的最朴素恢复就是**重启**：环出现就重启系统（数据库则重启/回滚事务），若涉及数据结构的精细修复可能还需人工介入。恢复的共同难点是**代价与公平**：既要打破死锁又要尽量少丢工作，还要防止某个倒霉进程被反复选为受害者而饿死——这正是"防饥饿"要把回滚次数纳入受害者选择的原因。
