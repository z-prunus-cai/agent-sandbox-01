## 14.1 FS 磁盘布局：超级块 / 位图 / inode 表 / 数据块

### 14.1.1 vsfs——一个最简文件系统的整盘分区

OSTEP Ch40 用一个教学文件系统 vsfs（Very Simple File System）说明磁盘怎样分区。把磁盘看成一长串定长的**块**（block，常见 4 KB），文件系统把这些块划成几个功能区，从盘头到盘尾依次是：超级块、inode 位图、数据位图、inode 表、数据块区。

```
| Super | inode bitmap | data bitmap | inode table (I) | data blocks (D...) |
```

对初学者，关键是先接受"磁盘只是一排编了号的格子，文件系统在这排格子上自己划地盘"。超级块记全局参数（有多少 inode、多少数据块、区从哪开始），位图用一个 bit 标记每个 inode / 数据块是空闲还是占用，inode 表是一个"文件属性数组"（第 i 个 inode 描述第 i 个文件），数据块区放真正的文件内容。块大小取 4 KB 是速度与碎片的折中：块越大单次 I/O 搬得越多但小文件浪费越大（内部碎片）。这套分区是后面一切的地基——FFS 只是把它复制成很多份按局部性摆放，journaling 只是在它前面加一段日志区。

### 14.1.2 inode 与多级索引指针

inode（index node）是描述单个文件的定长结构，记录文件的元数据（类型、权限、属主、大小、时间戳、链接计数）和一组指向数据块的**块指针**。文件内容分散在数据块区，inode 就是"这个文件用了哪些块"的索引。经典 Unix inode 用**多级索引**组织指针：

```
直接指针 × 12  →  各指向一个数据块
一级间接指针 × 1  →  指向一个"全是块指针的块"
二级间接指针 × 1  →  指向一个"全是一级间接块"的块
三级间接指针 × 1  →  再多一层
```

对初学者，多级索引是为了兼顾"小文件省、大文件也能撑大"。小文件（≤12 块）只用直接指针，一步就找到数据；文件变大才启用间接块，多绕一次盘。举例：4 KB 块、每个块指针 4 字节，则一个间接块能装 1024 个指针，一级间接就能再多寻址 1024 × 4 KB = 4 MB，二级间接达到 GB 级。代价是大文件读一个远处的块要多次寻址（先读 inode，再读间接块，再读数据块）——这正是"读放大"，也是 ext4 用 extent（连续块范围，一条记录顶一大片）取代间接块的动机。多级索引这种"小文件浅、大文件深"的不对称设计，是因为绝大多数文件都很小。

### 14.1.3 目录是内容为"名字→inode 号"表的特殊文件

目录（directory）在实现上就是一个普通文件，只是它的数据块里装的不是用户数据，而是一张**目录项**表，每条记录一个 (文件名, inode 号) 对。查找 `/a/b` 就是：从根目录 inode 读出根的数据块、在里面按名字找到 `a` 的 inode 号，读 `a` 的 inode、再读 `a` 的数据块找 `b`，逐级下降。

对初学者，"目录也是文件"是理解文件系统的关键一跳。它解释了为什么硬链接可行（两个目录项指向同一个 inode 号，见大主题13）、为什么删除文件叫 unlink（删的是目录里那条"名字→inode"记录，inode 的链接计数减到 0 才真正回收）、为什么路径查找会产生一连串磁盘读（每一级目录都要读一次）。目录项里通常还带一个记录长度字段以支持变长文件名，这样删除项时把前一项的长度加长"跳过"它即可，无需搬移。

### 14.1.4 超级块与分配位图

超级块（superblock）是文件系统的"总目录页"，记录 inode 总数、数据块总数、各区起始位置、块大小、以及一个魔数用于挂载时识别文件系统类型。位图（bitmap）则是分配状态表：inode 位图每 bit 对应一个 inode 空闲/占用，数据位图每 bit 对应一个数据块空闲/占用。分配一个新块 = 在数据位图里找一个为 0 的 bit、置 1、返回其块号。

对初学者，超级块坏了整个文件系统就打不开，所以真实文件系统（如 ext4）会在盘上**多处备份**超级块（`sparse_super`），fsck 能用备份修复。位图是"O(1) 找空闲"的朴素手段，虽然找连续大片空闲要扫，但它小、易备份、崩溃后好校验（把位图和实际 inode/块占用对一遍就知道有没有泄漏）。记住位图和它保护的对象（inode / 数据块）分处两区，一次文件增长要同时改位图和 inode——这个"要改多个块"正是 14.3 崩溃一致性问题的根源。

### 14.1.5 一次 open + read/write 的磁盘 I/O 序列

把布局串起来，读文件 `/foo/bar` 并写它的过程，是对上述各区的一串读写。OSTEP Ch40 给出的典型时序（忽略缓存）是：

```
open("/foo/bar"): 读根 inode → 读根 data → 读 foo inode → 读 foo data → 读 bar inode
read():           读 bar inode（定位块）→ 读 bar data → 写回 bar inode（更新访问时间）
write() 追加一块:  读 data bitmap → 写 data bitmap → 写 bar inode → 写新 data block
```

对初学者，这串时序解释了三件事。其一，为什么文件系统离不开缓存（页缓存/inode 缓存）——否则打开一个深路径文件要读一长串目录 inode 和数据块，慢得离谱；缓存把重复的目录查找和 inode 读命中在内存里。其二，为什么"追加一块"要改好几个磁盘结构（位图、inode、数据块）——这几个写如果只完成一部分就掉电，文件系统就不一致了。其三，为什么写元数据（inode 时间戳）会放大写量。把这三点记住，14.3–14.4 讲的一致性协议就是在解决"write 那三步不是原子的"这一个具体问题。

### 14.1.6 本机实测：用 dumpe2fs 看 ext4 的真实布局

在本机（Linux 6.18.5 x86_64 @2026-07-29）用 `mkfs.ext4` 造一个 64 MB 的 ext4 镜像再用 `dumpe2fs` 打印，能看到上述抽象分区在真实文件系统里的对应物。可复现命令与真实输出节选：

```
dd if=/dev/zero of=/tmp/fs_demo.img bs=1M count=64
mkfs.ext4 -q -F -b 4096 /tmp/fs_demo.img
dumpe2fs /tmp/fs_demo.img
```

```
Inode count:        16384      Block count:  16384      Block size:  4096
Inode size:         256        Blocks per group: 32768   Inodes per group: 16384
Group 0: (Blocks 0-16383)
  Primary superblock at 0, Group descriptors at 1-1
  Reserved GDT blocks at 2-8
  Block bitmap at 9        Inode bitmap at 25
  Inode table at 41-1064   (1024 blocks)
```

对初学者，把这份输出对回 14.1.1 的示意图：`Primary superblock at 0` = 超级块；`Block bitmap` / `Inode bitmap` = 两张位图（各占一个 4 KB 块，一块 32768 bit 正好管一组的 32768 个块）；`Inode table at 41-1064` = inode 表（16384 个 inode × 256 字节 ÷ 4096 = 1024 块，与输出吻合）；其余为数据块。`Block size 4096`、`Inode size 256` 是这版 e2fsprogs 的默认值，与 OSTEP 讲的 4 KB 块一致。真实 ext4 比 vsfs 多了"块组（Group）"和"组描述符"，那正是 14.2 FFS 局部性思想的落地——把一整套超级块/位图/inode 表复制成很多组分散在盘上。

## 14.2 FFS 局部性：柱面组与"把相关数据放近"

### 14.2.1 老 Unix 文件系统为什么慢

FFS（Fast File System，McKusick 等 1984）诞生的背景是：最早的 Unix 文件系统把 inode 表全放在盘的一端、数据块放在另一端，且分配不考虑位置。结果是读一个文件要在"盘头的 inode"和"盘中的数据"之间反复长距离寻道；用久了空闲块散落全盘，一个文件的块也被打散，磁头疲于奔命。OSTEP Ch41 说老 FS 把磁盘当成"随机存取的内存"来用，完全无视磁盘"顺序快、寻道慢"的物理本质。

对初学者，先接受一条硬件事实（承大主题12）：机械磁盘的寻道（磁头移动）和旋转等待是毫秒级，比一次连续读慢几个数量级。所以文件系统性能的第一课不是算法，而是**布局**——把"会被一起访问的东西"放到磁盘上物理相邻的位置，让磁头少动。FFS 的全部聪明都围绕这一句。

### 14.2.2 柱面组 / 块组

FFS 把磁盘划成许多**柱面组**（cylinder group，现代文件系统叫**块组** block group），每组是一段连续的磁道范围，并且**每组内部都放一套完整的结构**：本组的超级块副本、inode 位图、数据位图、inode 表、数据块。等于把 14.1 那张单一布局图复制成 N 份，均匀铺在全盘。

```
| group 0: [sb][imap][dmap][inodes][data] | group 1: [sb][imap][dmap][inodes][data] | ... |
```

对初学者，块组的意义是"就近安家"：一个文件的 inode 和它的数据块可以放在**同一组**里，彼此物理相邻，读时磁头几乎不用长距离移动。每组各带一份超级块副本还顺带提高了可靠性（一处坏了别处能修）。14.1.6 里 `dumpe2fs` 打印的 `Group 0` 就是块组，真实 ext4 的每个块组正是这个结构（ext4 还用 flex_bg 把几组的位图/inode 表聚到一起进一步优化）。

### 14.2.3 分配启发式：相关的放近，无关的摊开

FFS 的分配策略是一组**启发式**，核心是"把相关的东西放进同一组、把无关的东西分散到不同组"。具体规则：同一目录下的文件尽量放同一组（`ls` 一个目录常会连着访问它们）；一个文件的数据块尽量放它 inode 所在的组；新建目录放到"空闲 inode 相对多"的组里以利未来扩展。

对初学者，这里有一个反直觉但关键的例外——**大文件要故意打散**。如果一个巨大的文件全塞进一个组，会把这一组的空闲块吃光，逼得同目录的其它小文件只能流落到远处的组，反而破坏了局部性。所以 FFS 规定大文件超过一定量后就"跳"到别的组继续，用"牺牲单个大文件内部一点点局部性"换"不毁掉整组的局部性"。这体现了系统设计里常见的"为整体最优牺牲局部最优"的权衡思路。

### 14.2.4 内部碎片与子块（fragment）

块选 4 KB 是为顺序吞吐，但对海量小文件（比如很多几百字节的文件）会造成严重**内部碎片**——每个文件占一整块，大半浪费。FFS 的应对是**子块 / 片（fragment）**：允许把一个块再切成更小的片（如 1 KB），小文件的尾部数据用片存放，多个小文件的尾巴能共享一个块的不同片。

对初学者，这是"大块保吞吐、小片省空间"的折中。文件增长到超过一个块时，文件系统再把散落的片拷贝合并成整块。现代文件系统（ext4）多不再用 FFS 的 fragment，而改用其它手段（如把极小文件的数据直接内联进 inode、或延迟分配 delayed allocation 攒够再一次分配连续大片）。但 FFS 提出的"块粒度会同时得罪吞吐和空间、需要一个次级粒度"这个问题，至今仍在。

## 14.3 崩溃一致性与 fsck

### 14.3.1 崩溃一致性问题：多个块的更新不是原子的

崩溃一致性（crash consistency）问题的根源是：一个逻辑操作往往要更新**多个**磁盘块，而磁盘一次只能原子地写一个块（甚至一个扇区），中途掉电就会留下"改了一部分"的状态。OSTEP Ch42 的经典例子是给文件**追加一块数据**，它要写三处：

```
① 数据位图 data bitmap   —— 把新块标记为已占用
② inode                 —— 增大文件大小、加一个指向新块的指针
③ 新数据块 data block    —— 写入实际内容
```

对初学者，关键是想清楚"这三个写之间任意时刻掉电"会怎样。文件系统无法保证这三个写要么全成、要么全不成——它们是三次独立的磁盘写。于是崩溃可能停在中间任何一步，留下自相矛盾的磁盘结构。这就是为什么不能"直接原地改"，必须有一套协议（fsck 事后修、或 journaling 事前记）。这个问题和数据库的事务原子性是同一件事，只是发生在文件系统层。

### 14.3.2 崩溃场景枚举：哪些"改一半"是危险的

把 14.3.1 的三个写任意组合"成/败"，能列出崩溃后的坏状态。OSTEP 归纳几类典型：

```
只写了数据块③：inode/位图没指向它 → 等于没写，不算不一致（数据丢，但结构一致）
只写了 inode②：inode 指向一个"位图说空闲"的块 → 不一致，且将来会把它分给别人（数据串门）
只写了位图①：块被标占用但没人指向它 → 空间泄漏（块永远分不出去）
写了②+③没写①：inode 指向的数据块在位图里是"空闲" → 会被重复分配
写了①+②没写③：结构一致，但数据块是垃圾旧内容（安全隐患）
```

对初学者，注意区分两类严重程度：**空间泄漏**（位图占用但没人用）只是浪费，不致命；而**位图与 inode 打架**（一个说空闲一个在用）会导致同一个块被分给两个文件、互相覆盖，这是真正的数据损坏。一致性协议的首要目标是消灭后一类矛盾。还要分清"数据丢失"和"结构不一致"——崩溃一致性首先保证的是文件系统**结构**能修回自洽（能挂载、不串数据），并不保证你最后一次写的**数据**不丢（那要靠 fsync，见大主题13）。

### 14.3.3 fsck：崩溃后离线扫全盘修复

fsck（file system check）是最早的应对：不在运行时防崩溃，而在**重启后、挂载前**扫描整个文件系统，找出并修复不一致。它的检查项包括：超级块合理性；用位图对照实际 inode/块占用（重建位图，修空间泄漏）；每个 inode 的链接计数是否等于真正指向它的目录项数（不等就修，把无人指向的 inode 挂到 lost+found）；有没有两个 inode 指向同一数据块（重复分配，需拷贝或裁决）；目录结构是否成树。

对初学者，fsck 的心智模型是"事后大扫除"——它不知道崩溃前你想干什么，只能把磁盘现状扫一遍、按规则修成一个**自洽**的状态，但这个自洽状态未必是你想要的（比如它可能保住结构一致而丢掉你追加的数据）。fsck 一致性的判据是"结构无矛盾"，不是"符合用户意图"。

### 14.3.4 fsck 为什么被淘汰：太慢、不保证语义

fsck 有两个致命缺陷。其一是**慢**：它必须扫描**整个**文件系统才能判断一致性，哪怕崩溃只碰坏了一个块。磁盘越大扫得越久，TB 级盘 fsck 要跑几十分钟到几小时，崩溃后系统长时间不可用。其二是**不保证语义正确**：它只能修到结构自洽，无法恢复"崩溃前正在进行的那个操作"的真实意图。

对初学者，记住这句对比：fsck 是"不管崩溃改了什么，事后扫全盘修成一致"；而下一节的 journaling 是"崩溃前就把要改什么记下来，崩溃后只需照日志把那几处补完/回退"。前者代价是全盘扫描（与盘大小成正比），后者代价只与"日志里未完成的事务"成正比（与崩溃时刻在飞的操作量成正比），所以现代文件系统几乎都转向 journaling，fsck 退居"日志也救不回时的最后兜底"。

## 14.4 Journaling：预写日志与 data / ordered / writeback 三模式

### 14.4.1 WAL 核心思想：先写日志，再改本体

journaling（日志）也叫**预写日志**（write-ahead logging, WAL），思想一句话：在原地改磁盘结构之前，先把"我打算改哪些块、改成什么"作为一条记录**顺序追加**写进一段专门的日志区；等这条日志**完整落盘**后，再慢慢把这些改动落到它们最终的位置（checkpoint）。崩溃后，只需重放日志里"已完整提交但可能没 checkpoint 完"的记录，就能把文件系统补到一致。

对初学者，WAL 的精髓是把"多个原地写不原子"这个难题，换成"往日志追加一条记录是否完整"这个**单一的、可判定的**问题。日志是顺序写（快），且带一个提交标记——只要提交标记在，整条日志就有效，可以照做；提交标记不在，整条日志作废，当没发生过。这正是数据库事务的 WAL，也是 xv6 的 log 层做的事。它把 fsck 的"扫全盘"缩小成"只看日志尾部那几条未完成事务"。

### 14.4.2 一次事务的落盘时序与那个关键的写屏障

以 data journaling（把数据也写进日志）为例，一次事务分几步顺序写日志、再 checkpoint。OSTEP Ch42 给出的流程是：

```
1. Journal write     : 把本事务要改的所有块（TxB 事务头 + 元数据 + 数据块）写入日志区
2. Journal commit    : 待上一步全部落盘后，写一个提交块 TxE（含事务号）—— 提交点
3. Checkpoint        : 把这些块从日志搬到它们的最终位置（原地更新）
4. Free              : 事务完成，日志空间可回收
```

对初学者，第 1 步和第 2 步之间**必须有一个写屏障**（磁盘 flush / barrier），这是整个协议的命门。原因：磁盘控制器会为性能乱序完成写。如果不加屏障，磁盘可能先把"提交块 TxE"写下去、"事务内容"还没写完就掉电——恢复时看到 TxE 以为事务有效，照着重放一堆残缺内容，比不记日志还糟。所以必须保证"内容全部落盘"这件事，先于"写下提交块"发生。commit 块本身要小到能一次原子写下（一个扇区），它的"在或不在"就代表整个事务的"成或败"。

### 14.4.3 崩溃恢复：扫描日志，重放已提交事务（redo）

崩溃重启后，恢复过程扫描日志区：对每条**带有效提交块**的事务，把它记录的块**重新写一遍**到最终位置（redo logging，重做）；对没有提交块的事务（写日志写到一半就崩了），直接忽略、当它没发生。重放是**幂等**的——把同样的块内容再写一次到同样位置，结果不变，所以恢复过程本身再崩溃也能重跑。

对初学者，这解释了为什么现代文件系统崩溃后重启**很快**：它不像 fsck 扫全盘，只扫日志区（很小，且是循环缓冲），把尾部几条已提交事务重放一遍即可，时间与"崩溃瞬间未 checkpoint 的事务量"成正比，与盘多大无关。这就是 fsck 被 journaling 取代的核心收益。

### 14.4.4 三种模式：data / ordered / writeback

把数据块也写进日志（data journaling）安全但**每份数据写两遍**（一遍日志、一遍本体），吞吐减半。于是 ext3/ext4 提供三种模式，权衡安全与性能：

```
data      : 元数据 + 数据都写日志。最安全，数据也不会崩坏；最慢（数据写两次）
ordered   : 只把元数据写日志；但强制"数据块先落到最终位置，再写元数据日志"
writeback : 只把元数据写日志；数据块与元数据无先后约束
```

ext3/ext4 的**默认模式是 ordered**（Linux 内核 ext4 文档 `data=ordered`）。ordered 的巧思：它不把数据写进日志（省掉数据的双写），但用"顺序约束"保证元数据日志提交时，它指向的数据块**已经在最终位置**了——于是绝不会出现"inode 指向一个尚未写入的、装着旧垃圾数据的块"这种安全事故。

对初学者，抓住三者的差别在于**元数据和数据的先后关系**。writeback 最快但最危险：崩溃后可能元数据（inode 说文件长了、指向新块）已生效、而那个新块的数据还没写下去，于是文件里出现一段"别人的旧数据"，是安全漏洞。ordered 用"数据先于元数据"这一条约束堵住这个洞，且不需要把数据写两遍，所以成为默认。data 模式只在对数据一致性要求极高、愿付双写代价时才用。默认值不凭记忆断言——本机 `/proc/fs/ext4/<dev>/options` 在此环境未暴露（见 14.4.6），故 ordered 这一默认以 Linux 内核 ext4 文档为准，核实 2026-07-29。

### 14.4.5 循环日志与检查点回收

日志区是一段**有限**的循环缓冲（circular log）。事务不断追加、checkpoint 完成后其占用的日志空间被释放、供后续事务复用。文件系统在日志里维护"最早未 checkpoint 事务"的位置，checkpoint 推进它，新事务从尾部追加，形成一个转圈的生产者-消费者。

对初学者，循环日志意味着日志**不会无限增长**——它是一小段固定区域反复用（14.1.6 那个镜像的日志是 `Total journal size: 4096k`，即 1024 个 4 KB 块）。如果 checkpoint 跟不上事务产生速度，日志写满，新事务就得等空间（表现为写卡顿）。恢复时也正因为日志有界、且已 checkpoint 的部分被回收，才只需扫这一小段。日志本身作为一个特殊文件存在（`dumpe2fs` 显示 `Journal inode: 8`，即 8 号 inode 就是日志文件），这也呼应了 14.1.3"一切皆文件"。

### 14.4.6 本机实测：has_journal 特性与一个有趣的反例

ext4 是否带日志，由文件系统特性 `has_journal` 决定。本机对 14.1.6 造的镜像和真实根分区分别 `dumpe2fs -h` 看特性，得到一个有教学价值的对比：

```
# 新造的镜像（mkfs.ext4 默认）——带日志
Filesystem features: has_journal ext_attr ... extent 64bit flex_bg ... metadata_csum
Journal inode: 8        Total journal size: 4096k        Total journal blocks: 1024

# 本容器根分区 /dev/vda —— 没有 has_journal
Filesystem features: ext_attr resize_inode dir_index sparse_super2 filetype extent 64bit flex_bg ...
（无 has_journal，无 Journal inode 字段）
```

对初学者，这个反例说明两件事。其一，`has_journal` 是 `mkfs.ext4` 的默认（新镜像带日志），但**并非必然**——本容器的根 ext4 是被刻意关掉日志创建的（一次性/短命环境不需要崩溃恢复、还省一份写放大），这印证了"日志是一种可开关的权衡，不是白拿"。其二，`Journal inode: 8` 证实日志就是一个普通文件（8 号 inode），照应 14.4.5。至于三模式中此文件系统跑的是哪个，本环境 `/proc/fs/ext4/vda/options` 不可见，故具体 data 模式**未取（待核）**，但默认 ordered 已由内核文档坐实。

## 14.5 LFS 日志结构文件系统：全盘皆日志与段清理

### 14.5.1 动机：为写而生，把所有写变成一次大顺序写

LFS（Log-structured File System，Rosenblum & Ousterhout 1991）从一个假设出发：内存越来越大，读多半命中缓存，磁盘将主要承受**写**；而磁盘顺序写远快于随机写。传统文件系统一次小更新要东一下（改 inode）西一下（改位图）随机寻道；LFS 干脆把**所有**写——数据、inode、位图、目录——都**追加**到一段连续区域，攒成一大块后一次顺序写下去，彻底消灭随机小写。

对初学者，LFS 的口号是"磁盘当成一个只追加的日志"。它和 14.4 的 journaling 不同：journaling 有"日志区 + 本体区"两处，日志只是临时中转，最终还要原地 checkpoint 回本体；LFS **没有本体区**，日志就是全部，数据写下去就永远待在那，永不原地覆盖。这也让它和 14.6 的 COW（写时复制）思想相通，是 ZFS/btrfs 的先声。

### 14.5.2 段：攒够一批再写，以及 inode 的漂移问题

LFS 把磁盘按大块（**段** segment，如 1 MB）管理。写操作先在内存里攒（buffer），攒满一个段的量，再把整个段一次顺序写到日志尾部。一个段里混装了新数据块和它们对应的新 inode。

```
段 S:  [ data data data | inode | data | inode | ... ]   ← 一次顺序写入日志尾
```

但"永不原地覆盖、总是追加"带来一个新问题：每次改文件都写一个**新的 inode**到新位置，inode 的磁盘位置一直在变。传统文件系统 inode 号能直接算出 inode 在盘上的固定地址（inode 表第 i 项），LFS 里做不到了——inode 到处漂。

对初学者，抓住这个因果链：为了顺序写→永不覆盖→总是追加新版本→inode 位置不固定→于是需要一个东西来记"第 i 号 inode 现在漂到哪了"。这个东西就是下一节的 inode map。

### 14.5.3 inode map 与检查点区

LFS 用一张 **inode map（imap）**解决 inode 漂移：imap 是"inode 号 → 该 inode 最新磁盘地址"的映射表。而 imap 本身也很大、也在不断更新，怎么办？LFS 把 imap 也**切块、也追加写进日志**（和数据、inode 混在段里）；再用磁盘上一个**固定位置**的**检查点区**（checkpoint region, CR）记录"各块 imap 现在在哪"。

```
查找文件 i：CR → 找到 imap 相应块的位置 → 读 imap → 得 inode i 的地址 → 读 inode → 读数据
```

对初学者，这是一个"间接再间接"的定位链，但只有 CR 在固定位置、其余全在日志里漂。CR 更新很不频繁（每隔一段时间刷一次），所以它不破坏"以顺序写为主"的整体性质。imap 块因为常被访问会缓存在内存里，实际查找没这么多次真实磁盘读。记住这条链：固定的 CR 指向漂动的 imap、imap 指向漂动的 inode、inode 指向漂动的数据——一切为顺序写让路。

### 14.5.4 段清理：垃圾回收旧版本

因为 LFS 从不覆盖、只追加，同一个块被改写多次就会在盘上留下多个旧版本，日志尾不断前进、盘迟早写满。**段清理**（segment cleaning，即垃圾回收）负责回收空间：读入若干旧段，判断其中哪些块还是"活的"（最新版本，仍被某 inode 指向），把活块搬到日志尾部写成新段，然后把这些旧段整个标记为空闲、可复用。

判断一个块死活，需要知道"它属于哪个文件的第几块、以及该文件现在是否还指向它"。LFS 在每个段头放一个**段摘要块**（segment summary block）记录段内每个块的 (inode 号, 偏移)，清理时据此回查 imap→inode 验证是否仍被指向。

对初学者，段清理是 LFS 的最大代价与难点，类似 SSD FTL 的垃圾回收（承大主题12.2）。两个工程问题：**何时清**（空闲时后台清 vs 写满前紧急清）与**清哪些段**（优先清"垃圾多、且数据冷不常改"的段最划算——冷段清理后不易马上又产生垃圾）。清理开销是 LFS 能否赢过传统文件系统的关键变量，也是它没能广泛取代 journaling 文件系统的主因之一。

### 14.5.5 崩溃恢复：检查点 + 前滚

LFS 崩溃恢复结合两招。检查点区 CR 提供一个"已知一致的旧时间点"（LFS 会写两份 CR 交替更新，避免写 CR 时崩溃）。恢复时先读最近一份完整的 CR，得到那一刻的一致状态；再从 CR 记录的日志尾位置开始**前滚**（roll forward），扫描 CR 之后新写入的段，把其中有效的更新补进来，尽量多恢复崩溃前最后一段时间的写。

对初学者，把它和 journaling 对照：journaling 恢复是"重放日志里已提交事务"，LFS 恢复是"从最近检查点出发，前滚日志尾新段"——都是"有一个可信基点 + 补上基点之后的日志"。CR 写两份交替，是为了保证任何时刻都有一份完整可信的 CR 可用（写 A 时崩就用 B），这个"双写交替保一份好的"技巧在系统里很常见。

## 14.6 数据完整性与校验和

### 14.6.1 静默数据损坏：磁盘会悄悄把数据弄错

前五节假设磁盘"要么正确写/读、要么整块坏（fail-stop）"。现实更糟：磁盘会发生**静默损坏**（silent corruption）——数据被改错了，但磁盘不报错，你读回一堆看似正常实则错误的字节。OSTEP Ch45 归纳几类：

```
位翻转 / bit rot        : 介质老化、宇宙射线，某些位悄悄反转
lost write（丢写）      : 磁盘声称写成功，实际没写下去，读回旧数据
misdirected write（错址）: 数据写对了内容，却写到了错误的块/盘
```

对初学者，"静默"二字是重点：这些错误不会触发 I/O 报错，上层文件系统若不主动检查就毫无察觉，坏数据一路传给应用甚至备份。前面讲的一致性协议（fsck/journaling）都防不住它们——那些协议保证的是"文件系统结构自洽"，不检查"块里的字节内容有没有被介质悄悄改坏"。这是一个正交的问题，需要正交的手段：校验和。

### 14.6.2 校验和：给数据块附一个"指纹"

校验和（checksum）是对一个块的内容用某个函数算出的一小段固定长度的"指纹"，和数据一起存。读回时重新算一遍，与存下的比对：

```
写入: store(data), store(checksum = C(data))
读取: 若 C(data_read) ≠ stored_checksum  →  检测到损坏
```

常见函数按"强度/开销"排：简单异或/加法校验（弱、快，漏检率高）；Fletcher 校验（中）；CRC（如 CRC32C，硬件加速、常用于检测随机位错）；密码学哈希（SHA-256 等，强到能抗恶意篡改，但慢）。ext4 的 `metadata_csum` 用 **CRC32C**；btrfs 默认 **CRC32C**（新版另可选 xxhash/SHA-256/BLAKE2）；ZFS 默认 **Fletcher4**（可选 SHA-256）。

对初学者，校验和的取舍是"指纹越强越能发现（甚至定位）错误，但每次读写都要算、越强越费 CPU"。它只保证**检测**损坏，不自动修复；要修复得靠别处还有一份好副本（RAID/镜像）或纠错码。选 CRC 而非 SHA，是因为磁盘错误多为随机噪声（非恶意），CRC 足够且有硬件指令，便宜。

### 14.6.3 校验和的布局：和数据放一起，还是分开放

一个设计问题是校验和存哪。若把校验和和数据块**存在同一块内**（挤占一点数据空间），一次读能同时拿到两者、少一次 I/O，但一个块的原子写能同时更新数据和它的校验，简单。另一种是把一批块的校验和**集中存**在别处。

对初学者，"放一起"的隐患恰恰暴露了 14.6.1 的错址/丢写为什么难防：如果磁盘把"数据+它的校验"作为一整块**一起**写错了地方，或者**一起**没写下去（读回一整块旧的数据+旧的校验），二者自洽、校验照样通过，损坏就漏检了。所以单纯的"内容校验和"只能抓位翻转，抓不住错址和丢写——这引出下一节。

### 14.6.4 抓错址与丢写：物理标识与写序号

要抓错址写（misdirected write），在校验里额外记这个块**应该在的物理地址**（磁盘号、块号）。读回时不仅比对内容校验，还核对"这个块自报的地址 == 我要读的地址"，写错了地方就会对不上。要抓丢写（lost write），常用手段是把校验/版本信息**同时**存在两个不同位置（如块内一份、inode 或别处一份），丢写只更新了其中一处，读时两处版本号对不上即暴露。

对初学者，核心直觉是"光看内容不够，要绑定上下文"。错址写内容本身没错、错在位置，所以校验必须把"我是谁、我该在哪"编进去；丢写是"整块都是旧的、块内自洽",所以必须靠一个"块外的、被独立更新过的"引用来揭穿它。这就是为什么强完整性文件系统把校验和放在**父节点**里（见下节 ZFS/btrfs），而不是块内自带。

### 14.6.5 端到端校验与 scrubbing：btrfs / ZFS 的做法

ZFS 和 btrfs 把校验和做成**端到端**：每个块的校验和不存在块内，而是存在**指向它的父块**里，一路向上直到根，形成一棵校验和树（Merkle 式）。配合 COW（copy-on-write，改块不覆盖原块、写新块再自底向上更新父指针+校验，本质是 LFS 追加思想），任何一层损坏都会让父节点的校验对不上而被发现；若有冗余副本（镜像/RAID-Z），还能用好副本自动**修复**（self-healing）。

主动**擦洗**（scrubbing / disk scrubbing）则是后台定期把全盘每个块读出来验一遍校验，趁着还有好副本时尽早发现并修静默损坏，避免"坏块一直躺着、等到另一副本也坏了才发现已无从修"。

对初学者，"校验和存父节点"精准解决了 14.6.3 的漏洞：块和它的校验分处两处、由不同的写更新，错址/丢写再也无法自洽蒙混。这套"COW + 校验和树 + scrub + 冗余自愈"是 ZFS/btrfs 相对 ext4 的核心卖点。ext4 只对**元数据**做校验（`metadata_csum`，保护 inode/位图/目录不被静默改坏），对普通文件**数据**默认不做端到端校验——所以说 ext4 是"日志保结构一致"，ZFS/btrfs 才是"校验保数据不烂"。

### 14.6.6 本机旁证：ext4 的 metadata_csum

14.1.6 造的 ext4 镜像的特性列表里含 `metadata_csum`（本机 `mkfs.ext4` 默认开启），`dumpe2fs` 的每个块组行还打印各结构的校验值：

```
Filesystem features: has_journal ... metadata_csum
Group 0: (Blocks 0-16383) csum 0x624d [ITABLE_ZEROED]
  Block bitmap at 9 ... csum 0xc170e1e6
  Inode bitmap at 25 ... csum 0x2080acc4
```

对初学者，`csum` 就是 14.6.2 说的校验和落地：块组描述符有 `csum 0x624d`、位图各有自己的 CRC32C 校验。这坐实 ext4 给**元数据**都挂了校验（挂载时校验对不上会报错、避免用坏元数据）。但注意输出里**没有**针对普通数据块的校验字段——印证 14.6.5 的结论：ext4 保护元数据、不保护文件数据内容，数据的端到端完整性要靠 btrfs/ZFS。btrfs/ZFS 的默认校验算法（CRC32C / Fletcher4）以其官方文档为准，本机未安装 btrfs/zfs 工具，故其行为**未取（待核）**。
