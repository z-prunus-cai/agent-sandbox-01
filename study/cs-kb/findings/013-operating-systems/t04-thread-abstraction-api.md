## 4.1 线程 vs 进程

### 4.1.1 线程是什么：进程内的一条执行流

线程（thread）是**一个进程内部的独立执行流**——同一个程序里可以同时有多条"正在执行到不同位置"的控制流，每条就是一个线程。传统进程只有一条执行流（一个 PC、一个栈）；多线程进程有多条执行流，它们**运行在同一个地址空间里**，看到的是同一份代码、同一份全局变量、同一个堆。

初学者可以把进程想成一间办公室：里面有共享的文件柜（全局数据）、共享的资料库（堆）、共享的门牌电话（打开的文件）。单线程进程 = 办公室里只有一个员工在干活；多线程进程 = 同一间办公室里有好几个员工同时干活，共用所有家具设备，但**每个人有自己的一张办公桌记当前进度**（自己的栈和寄存器）。OSTEP Ch26 就是这样引入线程的：把进程从"单点执行"扩展成"多点执行"，而这些执行点共享同一片内存。

### 4.1.2 共享什么、独占什么

同一进程的多个线程**共享**进程级的资源，但**各自独占**属于"当前执行到哪儿"的那一小份状态。

共享（进程级，所有线程一份）：

```
地址空间     代码段 / 全局数据 / 堆 / mmap 区（同一份，指针可互通）
打开文件表   同一张 fd 表（一个线程 open 的 fd，别的线程能用）
当前工作目录 / umask / 文件系统根
信号处理表   （信号如何处理是进程级设置）
进程 ID（PID / 内核里的 TGID）
```

独占（每线程一份，线程级）：

```
栈 (stack)        每个线程有自己独立的调用栈（局部变量互不干扰）
寄存器 / PC       每个线程有自己的程序计数器和一组寄存器值（=自己的执行现场）
线程 ID (TID)     内核给每个线程的唯一标识
errno / TLS       线程局部存储；errno 是每线程独立的
```

为什么这样切分？因为"执行到哪一行、局部变量是什么"是**每条执行流私有**的进度信息，必须各自一份，否则两个线程互相踩栈就乱套了；而代码、全局数据、堆、打开的文件是"大家要一起用"的共享资源，正是线程存在的意义——**低成本共享**。这也埋下并发的种子：多个线程同时读写同一份共享内存（全局变量、堆），就可能产生数据竞争，需要同步——这归 L4-05，本课不展开。

### 4.1.3 本机实证：多线程共享 PID、各有 TID

一个创建 3 个工作线程的 pthread 程序，每个线程打印自己的 `getpid()`（进程 ID）和 `gettid()`（线程 ID）：

```
main:     pid=6980 tid=6980
thread 0: pid=6980 tid=6982
thread 1: pid=6980 tid=6983
thread 2: pid=6980 tid=6984
```

四条执行流（主线程 + 3 个工作线程）的 `pid` **全部相同**（6980），说明它们属于同一个进程；但 `tid` **各不相同**（6980/6982/6983/6984），说明内核把每个线程当成一个可单独调度的实体来标识。主线程的 TID 恰好等于 PID，这正是 Linux 的约定：进程的第一个（主）线程的 TID = 进程的 PID = 线程组号 TGID。

从内核视角看，`/proc/[pid]/task/` 目录下**每个线程一个子目录**（目录名就是 TID）：

```
$ ls /proc/6980/task/
6980  6982  6983  6984          # 4 个线程 = 4 个 task 目录

$ grep -E 'Tgid|Pid|Threads' /proc/6980/status
Tgid:    6980                   # 线程组号（= 用户看到的 PID）
Pid:     6980
Threads: 4                      # 内核确认这个进程有 4 个线程
```

`Threads: 4` 和 4 个 task 子目录直接坐实"一个进程 = 多个内核可调度线程"。这也说明 Linux 内部**没有专门的"线程结构"**——每个线程就是一个 `task_struct`（大主题02 的 PCB），同一进程的线程只是共享了一批指针（如指向同一个 `mm_struct` 地址空间），并有相同的 TGID。

### 4.1.4 为什么用线程而不是多进程

既然多进程也能并发，为什么还要线程？两点：**共享成本低**和**创建/切换更便宜**。

第一点是共享成本低。进程之间地址空间互相隔离，要交换数据得走管道、共享内存段、socket 等进程间通信（IPC），既麻烦又有拷贝开销；而同进程的线程直接读写同一个全局变量/堆就完成了"通信"，零拷贝。代价是共享带来同步难题（竞争、死锁），把正确性责任推给了程序员（L4-05）。

第二点是创建与切换更便宜。`fork` 一个新进程要建立新地址空间（即便有写时复制也要复制页表、翻转权限位）；创建线程只需分配一个栈并让新 `task` 共享现成的地址空间，省掉了地址空间那一大块工作。线程间上下文切换也不必切换页表（地址空间没变），省去 TLB 刷新的一部分代价。所以线程常被称为"轻量级进程"（lightweight process, LWP）。

## 4.2 内核线程 vs 用户线程、1:1 vs M:N

### 4.2.1 两层"线程"：内核调度实体 vs 用户可见执行流

"线程"这个词在两个层面上被用，初学者极易混。一层是**内核线程**（kernel-level thread）：内核知道它的存在、把它当作一个**调度实体**排进调度器、可以把它派到某个 CPU 上跑。另一层是**用户线程**（user-level thread）：由用户态的线程库在一个（或几个）内核线程之上"自己模拟"出来的多条执行流，内核**看不见**它们，调度完全由库在用户态完成。

**"谁在调度这条线程？"** 内核线程由内核调度器调度；纯用户线程由用户态库调度，内核只看到承载它们的那一个内核线程。二者的能力差异由此而来：内核线程能被真正分派到多个 CPU 上并行、一个线程阻塞在系统调用时内核能切到同进程另一个内核线程；纯用户线程做不到这两点（除非库配合），因为内核不知道它们各自的存在。

### 4.2.2 三种映射模型：1:1 / N:1 / M:N

用户线程到内核调度实体的映射有三种经典模型：

```
1:1  （一对一）   每个用户线程 ↔ 一个内核线程。内核直接调度每条线程。
N:1  （多对一）   N 个用户线程全部跑在 1 个内核线程上，纯用户态调度。
M:N  （多对多）   M 个用户线程复用 N 个内核线程（通常 N ≈ CPU 数）。
```

1:1（内核线程模型）：创建一个线程就在内核里建一个调度实体，简单直接，能真并行、单线程阻塞不拖累别人；代价是每个线程都有内核开销（创建、内核栈、调度）。

N:1（纯用户线程/"绿色线程"）：所有线程挤在一个内核线程里由库调度，创建/切换极快（不进内核）；但**无法利用多核**（内核只看到一条线程），且**一个线程做阻塞系统调用会卡住整个进程**的所有用户线程（内核把承载它们的那唯一内核线程整个挂起了）。

M:N（混合）：想同时要"用户态切换快"和"多核并行"，让 M 个用户线程动态复用 N 个内核线程；理论最优，但实现极其复杂——用户态调度器和内核调度器要协同，阻塞系统调用、信号、优先级都要特殊处理，历史上被证明难以做对。

### 4.2.3 Linux/NPTL 是 1:1

Linux 现行的线程实现是 **NPTL（Native POSIX Thread Library）**，采用严格的 **1:1 模型**：每个 pthread 对应一个内核可调度的 `task`（有独立 TID），由内核调度器直接调度。本机 glibc 证实：

```
$ getconf GNU_LIBPTHREAD_VERSION
NPTL 2.39
```

NPTL 于 2003 年随 glibc 2.3.2 取代更早的 LinuxThreads，成为 Linux 的标准线程库。它是 1:1 的直接证据就是 4.1.3 的实测：3 个 pthread 各有独立 TID、各是 `/proc/[pid]/task/` 下一个 task——用户线程和内核调度实体一一对应。也正因为 1:1，4.4 的多核实测里 4 个 pthread 能被内核分派到 4 个核上真并行。

### 4.2.4 为什么 Linux 选 1:1 而非 M:N（历史与权衡）

M:N 理论上更优，但 Linux 明确选了 1:1，原因是**工程上的简单与正确**压倒了理论上的省内核开销。NPTL 的设计取舍是：与其在用户态重造一个复杂的调度器去和内核调度器博弈（M:N 的做法），不如把内核线程做得足够轻、让内核调度器直接管所有线程——`clone` 创建线程本就不贵，内核调度器也足够好。历史上 Linux 曾有过 M:N 的尝试（IBM 的 NGPT，Next Generation POSIX Threads），但最终 1:1 的 NPTL 胜出并沿用至今。

作为对照，一些其他系统/运行时仍用 M:N。经典的 Solaris 早期线程模型是 M:N（后来也转向 1:1）；现代语言运行时里 **Go 的 goroutine** 是典型的用户态 M:N（大量 goroutine 复用少量 OS 线程，由 Go 运行时调度）——这属于 4.5 协程/用户态任务的范畴，说明 M:N 在"语言运行时自带调度器"的场景下依然活跃，只是操作系统层面的通用线程库 Linux 选了 1:1。

## 4.3 `clone()` 标志谱与 pthread

### 4.3.1 `clone` / `clone3`：Linux 统一的执行流创建原语

Linux 不用两个不同的系统调用去分别创造"进程"和"线程"——它只有一个底层原语 `clone()`（及较新的、参数放在结构体里的 `clone3()`），通过一组 `CLONE_*` 标志**逐项决定新执行流与调用者共享哪些资源**。共享得越多，新执行流就越像"线程"；共享得越少（尤其不共享地址空间），就越像"进程"。`fork()` 只是 `clone` 的一个特例（几乎什么都不共享）。

这是理解 Linux 线程的核心洞见：**进程和线程不是两种东西，而是同一个 `clone` 原语在"共享标志"这根旋钮上的两个刻度**。旋钮拧到"全共享"是线程，拧到"全独立"是进程，中间还能调出各种半共享的怪东西（如共享 fd 表但不共享地址空间）。

### 4.3.2 关键 `CLONE_*` 标志谱（每条标志控制"共享一样东西"）

以下是与线程/进程语义最相关的标志，每条只做一件事——"打开则共享对应资源"：

```
CLONE_VM          共享地址空间（同一份内存；不设则子进程得到独立地址空间副本）
CLONE_FILES       共享打开文件描述符表
CLONE_FS          共享文件系统信息（cwd、根目录、umask）
CLONE_SIGHAND     共享信号处理函数表（设它必须同时设 CLONE_VM）
CLONE_THREAD      新 task 放入同一线程组（同 TGID）——这才使它成为 POSIX 意义的"线程"
CLONE_SYSVSEM     共享 System V 信号量的撤销（undo）列表
CLONE_SETTLS      按 tls 参数设置线程局部存储（TLS）
CLONE_PARENT_SETTID   把新线程 TID 写回父指定的地址
CLONE_CHILD_CLEARTID  线程退出时清零指定地址并唤醒等待的 futex（pthread_join 的底层机制）
```

另有一个不属于 `CLONE_*` 位、但决定语义的关键参数是**终止信号 exit_signal**：进程（`fork`）用 `SIGCHLD`（子进程死时给父发 SIGCHLD）；线程用 `0`（线程终止不给"父"发信号，因为它根本不是独立进程）。`CLONE_THREAD` 是分水岭：设了它，新 task 与创建者共享 TGID、被当作同一进程里的线程；不设它（如 `fork`），新 task 有自己的 TGID、是独立进程。

### 4.3.3 pthread_create 落地：实证它就是"全共享 clone3"

本机 `strace -f` 跟踪 4.1 的 pthread 程序，`pthread_create` 背后的真实系统调用是 `clone3`（现代 glibc 用 `clone3` 而非老的 `clone`）：

```
clone3({flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|
              CLONE_SYSVSEM|CLONE_SETTLS|CLONE_PARENT_SETTID|CLONE_CHILD_CLEARTID,
        child_tid=0x..., parent_tid=0x...,
        exit_signal=0,                    /* 线程：终止不发信号 */
        stack=0x7fa83a9ff000, stack_size=0x7fff80,
        tls=0x...}) = 8105                /* 返回新线程 TID */
```

逐项对齐 4.3.2 就完全说通了：`CLONE_VM`→共享地址空间（所以线程能直接读写同一全局变量）、`CLONE_FILES`→共享 fd 表、`CLONE_SIGHAND`→共享信号处理、`CLONE_THREAD`→归入同一进程（同 PID/TGID，正是 4.1.3 看到的现象）、`CLONE_SETTLS`+显式 `stack`→给新线程配好独立的 TLS 和栈、`CLONE_CHILD_CLEARTID`→为 `pthread_join` 提供"线程退出时唤醒等待者"的钩子。`exit_signal=0` 表明它不是独立进程。**"线程 = 共享几乎一切的 clone3"** 在这里一览无遗。

### 4.3.4 对比 fork：同一原语的另一个刻度

同机 `strace` 一个 `fork()` 程序，对照鲜明：

```
clone(child_stack=NULL,
      flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD,
      child_tidptr=0x...) = 11761
```

`fork` 落到 `clone`（注意 glibc 的 `fork` 仍走老 `clone`，而 `pthread_create` 走 `clone3`），**几乎不带任何共享标志**：没有 `CLONE_VM`（子进程得到独立地址空间，靠写时复制实现，见大主题02）、没有 `CLONE_FILES`/`CLONE_THREAD`；`child_stack=NULL`（不指定栈，子进程沿用父栈的副本）；终止信号是 `SIGCHLD`（子进程死时通知父进程）。

把两条 `strace` 并排看，就是本大主题最精炼的一句话总结：

```
线程 = clone3(CLONE_VM|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|...,  exit_signal=0,  独立栈)
进程 = clone (无共享标志,                                             exit_signal=SIGCHLD, 无独立栈)
```

同一个 `clone` 家族原语，靠标志把"共享多少"从满调到零，就分别造出了线程和进程。

### 4.3.5 pthread API 速览（POSIX 层的落地接口）

程序员一般不直接调 `clone`，而是用 POSIX 线程（pthread）API，由线程库把它翻译成上面的 `clone3`：

```c
pthread_create(&tid, attr, start_routine, arg);  // 造线程，从 start_routine 开始跑
pthread_join(tid, &retval);                       // 阻塞等某线程结束，取回它的返回值（≈ 线程版 wait）
pthread_detach(tid);                              // 分离：结束后资源自动回收，不需 join
pthread_exit(retval);                             // 当前线程主动结束并留下返回值
pthread_self();                                   // 取当前线程的 pthread_t 句柄
```

`pthread_create` 对应"造一条共享地址空间的执行流"，`pthread_join` 对应"回收"——它靠 4.3.2 的 `CLONE_CHILD_CLEARTID` 机制实现：线程退出时内核清零一个地址并唤醒在那上面等待的 futex，`join` 就是在等这个唤醒。一个易错点是**未 join 又未 detach 的线程结束后会残留**（类似进程的僵尸），长期运行的程序要么 join、要么 detach。注意编译多线程程序须加 `-pthread`（本报告所有实证程序均用 `gcc -std=c11 -pthread` 编译）。

## 4.4 并发 ≠ 并行

### 4.4.1 定义辨析：交错 vs 同时

并发（concurrency）和并行（parallelism）是两个常被当成同义词、实则不同的概念。

并发是**结构性质**：程序被组织成多条逻辑上可独立推进的执行流，它们的执行在时间上**交错（interleave）**——在任一瞬间可能只有一条真正在跑，但系统在它们之间快速来回切换，宏观上"同时都在进展"。单核 CPU 也能并发（靠时分复用轮流跑）。

并行是**运行时性质**：多条执行流在**同一时刻真正同时执行**，物理上需要多个执行单元（多核/多 CPU）。并行一定是并发的，但并发不一定并行——单核上的多线程是并发而非并行。

换句话说，**并发是"看起来同时"（可发生在单核），并行是"真的同时"（必须多核）**。并发是关于如何构造程序（把工作拆成可交错的流），并行是关于用多少硬件真的一起跑。

### 4.4.2 本机实证：单核 vs 多核计时

同一个"4 线程各做一亿次量级纯计算"的 CPU 密集程序，分别用 `taskset` 绑到 1 个核（强制只能交错=纯并发）和放开到 4 个核（可真并行）跑，对比墙上时钟时间（real）与累计 CPU 时间（user）：

```
$ nproc
4

# 4 线程只准用 1 个核：并发但不并行（在一个 CPU 上时间片轮转交错）
$ taskset -c 0 ./cpubound
real  1.193s     user  1.193s     sys  0.000s

# 4 线程可用全部 4 个核：真并行（4 条流同时在 4 个核上跑）
$ taskset -c 0-3 ./cpubound
real  0.376s     user  1.328s     sys  0.000s
```

两组数字把区别讲透了。单核那组 `real ≈ user`（1.193s ≈ 1.193s）：四个线程轮流占用同一个 CPU，总 CPU 时间等于墙上时间——因为任一时刻只有一个线程真在跑，这是纯并发、零并行。多核那组 `real << user`（0.376s vs 1.328s）：累计 CPU 时间约为墙上时间的近 4 倍，说明四个线程在四个核上**真的同时**烧 CPU，把总工作量压进了约四分之一的墙上时间——这是并行。加速比：

```
speedup = 1.193s / 0.376s ≈ 3.2×
```

用 4 个核拿到约 3.2× 加速（未到理想的 4×，因为有线程创建、调度、内存带宽竞争等开销，接近但不等于线性——这正是 L6-06/CP-15 讲的可扩展性上界，本课点到）。而单核无论怎么调度都不可能低于 1.193s，因为一个核的算力是硬上限——这就是"并发救不了算力不足，只有并行能"。

### 4.4.3 为什么这个区分重要

分清二者能纠正两个常见误解。其一，"多线程一定更快"是错的：在单核上（或线程被绑到一个核），多线程 CPU 密集任务不会更快，反而因切换开销略慢——多线程在单核上的价值是**并发结构**（如一个线程等 I/O 时另一个能推进），不是算力。其二，并发是并行的前提但不等于并行：要想真并行加速，先得把程序写成并发的（多线程/多流），再交给多核跑；程序若本身是一条死板的串行流，给再多核也白搭（这也呼应 Amdahl 定律，L6-06/CP-15）。

对 OS 而言，是并发让"看起来同时"成为可能（靠调度器时分复用一个核，大主题05），是多核硬件 + 1:1 线程让"真的同时"成为可能（4.2 的 NPTL 1:1 使每个 pthread 能被派到不同核）。

## 4.5 协程 / 用户态任务

### 4.5.1 协程是什么：协作式让出的执行流

协程（coroutine）是一种比线程更轻的执行流：多个协程可以各自保存执行现场、在指定的点**主动让出（yield）**控制权给另一个协程，之后再从让出点**恢复（resume）**继续执行。它们的调度是**协作式（cooperative）**的——只有协程自己愿意让出时才切换，没人能强行打断它；这与线程的**抢占式（preemptive）**调度相反（线程可能在任意指令处被时钟中断抢走 CPU，大主题05）。

初学者最好的入口是"一个函数能暂停在中间、稍后从暂停处接着跑"。普通函数一旦调用就一路跑到 `return`、栈帧随即销毁；协程可以执行到一半 `yield` 出去、把当前进度（局部变量、执行到哪一行）**保留**着，控制权交给别人，等再被 `resume` 时从那一行继续、局部变量还在。Python 的生成器/`async`、Lua 的 coroutine、C++20 coroutine、Go 的 goroutine 都是这类构造的不同形态。

### 4.5.2 与线程对比：无内核介入、无抢占

协程和线程都提供"多条执行流"，但落地层次完全不同：

```
              线程 (pthread, 1:1)          协程 / 用户态任务
调度者        内核调度器                    用户态运行时/库（内核不知情）
切换方式      抢占式（时钟中断可强夺）      协作式（须自己 yield）
切换成本      较高（进内核、可能刷 TLB）    极低（仅用户态保存/恢复少量寄存器）
真并行        能（可派到多核）              单个协程调度器内不能真并行（除非跑在多个线程上）
一个阻塞的后果 只挂起该线程，别的线程照跑    若阻塞系统调用会卡住整个承载线程上的所有协程
数量级        通常几百~几千               可轻松几十万~上百万
```

协程的最大卖点是**海量 + 廉价**：因为不占内核调度实体、栈可以很小且按需增长，一个进程能开几十万上百万个协程，用来表达高并发 I/O（一个连接一个协程）而不必付出等量内核线程的代价。代价是它默认**不能利用多核**（一个协程调度器本质是 N:1，全在一条线程上跑），且**协作式调度要求协程自觉让出**——一个不 `yield` 又埋头死算的协程会饿死同调度器里的其他协程；此外，若协程里调用了会阻塞的系统调用，会连累承载它的整个线程（这正是 4.2 N:1 模型的老问题）。

### 4.5.3 现代运行时：把协程铺到多核（M:N）

为了既要协程的廉价海量、又要多核并行，现代语言运行时常把协程架在 **M:N** 上：M 个协程复用 N 个 OS 线程（N ≈ 核数），运行时自带调度器在这些线程间分派协程，并把阻塞系统调用特殊处理（换成非阻塞 + 事件通知，或把该 OS 线程临时让出）。**Go 的 goroutine** 是最广为人知的例子：goroutine 是用户态协作式任务，Go 运行时用 M:N 把海量 goroutine 调度到少量 OS 线程上，从而兼得"开百万个执行流"和"真跑在多核上"。

这恰好把本报告串成一个闭环：操作系统层的通用线程库 Linux 选了 1:1（4.2，简单可靠、内核直管），而语言运行时层为了在 1:1 内核线程之上再榨出廉价海量的执行流，又在用户态重造了 M:N 的协程调度。二者不是替代而是分层——协程跑在线程上，线程跑在核上。协程作为并行**范式**（CSP/channel、actor 等）的深入对比归 L4-05 CP-14，本课到此点到为止。
