## 9.1 动态重定位与分段

### 9.1.1 为什么需要"地址翻译"这一层

地址翻译（address translation）解决的是同一台机器上多个进程如何共用一块物理内存却互不打扰的问题。每个进程都以为自己独占一段从 0 开始的连续地址（虚拟地址，virtual address），而硬件在每次取指令、读写数据时，都把这个虚拟地址实时改写成内存条上真正的物理地址（physical address）。这层改写由 CPU 里的内存管理单元（MMU）按操作系统填好的规则完成，OSTEP Ch15 称之为"基于硬件的地址翻译"。

对初学者，关键是把"进程眼中的地址"和"内存里的地址"彻底分开来想。编译器和程序看到的地址（比如某个变量在 `0x1000`）是虚拟的、假的；它到底落在物理内存的哪一格，由 OS 决定、由硬件翻译。这层间接（indirection）带来三件好事：进程被限制在自己的地址范围里动不了别人（保护/隔离）；同一份程序可以被装到物理内存的任意位置（重定位）；操作系统可以灵活地摆放、移动、甚至暂时不给某段地址分配物理内存。分页只是实现这层翻译的一种具体办法，9.1 先看它之前更朴素的两种：动态重定位与分段。

### 9.1.2 静态重定位与它的不足

静态重定位（static relocation）指在程序装入内存时，由加载器一次性把程序里所有地址都加上它被放置的起始地址、改写成最终物理地址，之后运行期不再翻译。这样不需要任何硬件支持，但有致命缺陷。

问题在于：改写之后没有任何保护——程序里的地址已经是真实物理地址，一个越界或恶意的访问可以直接读写别的进程甚至内核的内存；而且程序一旦装入就钉死在那个位置，OS 无法在运行期把它挪走以整理内存。所以静态重定位很快被硬件辅助的动态重定位取代，"动态"指翻译发生在每次访存的运行期、而不是装入期。

### 9.1.3 base/bound（动态重定位）

动态重定位的最小硬件是一对寄存器：基址寄存器（base）和界限寄存器（bound，又叫 limit）。进程的每个虚拟地址都按下式翻译，并做一次越界检查，两步都由硬件在每次访存时完成：

```
physical address = virtual address + base
```

```
若 virtual address ≥ bound  →  硬件触发异常（越界保护）
```

base 记录该进程在物理内存中的起始位置，把进程"整段平移"到物理内存的任意空位；bound 记录该进程地址空间的大小，任何 ≥ bound 的虚拟地址都被判为越界并陷入内核。base/bound 这两个寄存器是特权状态，只有内核态能改，进程自己动不了，这正是隔离的来源。

对初学者，可以把 base 想成"你这栋楼在小区里的门牌起点"、bound 想成"你家这套房的面积"：你按自家户型图（从 0 开始的虚拟地址）找房间，硬件自动加上门牌起点得到小区里的真实位置，并检查你没走出自家面积。它的局限是"整段平移"——一个进程哪怕只用一点点栈和堆，中间大片没用到的虚拟地址也必须在物理内存里连续占着，造成大量浪费（内部碎片）。这个浪费正是分段要改进的地方。

### 9.1.4 分段：给每个逻辑段独立的 base/bound

分段（segmentation）把 base/bound 从"整个地址空间一对"细化为"每个逻辑段一对"。代码段、堆、栈各有自己的 base 和 bound，可以分别放到物理内存里不同的空位，段与段之间的未使用虚拟地址不再需要占物理内存。翻译时硬件先看虚拟地址落在哪个段，再用该段的 base/bound 翻译：

```
physical address = segment_base + offset_within_segment
```

段号通常取虚拟地址的高几位、段内偏移取低位；或由指令类型（取指走代码段、压栈走栈段）隐式决定。栈这种向下增长的段还需硬件记一个增长方向位。分段的好处是地址空间里的"大空洞"（堆和栈之间那片没用到的地址）不再消耗物理内存，稀疏地址空间的支持大幅改善。

初学者要抓住"分段 = 若干个 base/bound"这一句。它比单对 base/bound 灵活，也第一次让"共享"成为可能——把某段的权限设为只读并让两个进程的段表指向同一物理段，就能共享代码。但它引入了新麻烦：见 9.1.5。

### 9.1.5 分段的外部碎片问题

分段的核心缺陷是外部碎片（external fragmentation）。因为每个段长度不一、可变，物理内存被反复分配回收后会碎成许多"大小不一的空洞"，总空闲量够、却没有一整块连续空间放得下一个新段。

设想物理内存里零散剩下 3 个 20KB 的空洞共 60KB，此时来了个要连续 50KB 的段——总量足够却无处安放。OS 只能做代价高昂的"紧凑"（compaction，把已用段搬到一起挤出连续空闲），或用首次适配/最佳适配等策略勉强塞（这归大主题08 空闲空间管理）。变长分配天然招致外部碎片，正是这一痛点催生了分页——把一切都切成**同样大小**的块，任何空闲块都能装下任何页，外部碎片从根上消失。

## 9.2 分页基础

### 9.2.1 页、页帧与分页的核心思想

分页（paging）把虚拟地址空间切成一串定长的小块，叫**页**（page）；把物理内存切成同样大小的小块，叫**页帧**（page frame，简称帧）。任意一个虚拟页都可以映射到任意一个物理帧，映射关系记录在每进程一份的**页表**（page table）里。因为所有块都一样大，任何空闲帧都能装任何页，9.1.5 的外部碎片被彻底消除。

页的典型大小是 4KB（本机 `getconf PAGE_SIZE` 实测为 4096）。分页相对分段的思想转变是"放弃逻辑段这个变长单位，改用统一定长单位"：代价是失去了"一个段一个含义"的语义、并可能在每页最后产生一点点内部碎片（一页没填满的部分），换来的是分配管理极其简单、且能支持稀疏地址空间。OSTEP Ch18 把分页称为不做任何变长假设的最通用方案。

### 9.2.2 地址翻译：VPN 拼 offset

分页下的翻译把虚拟地址切成高位的**虚拟页号**（VPN, virtual page number）和低位的**页内偏移**（offset）。VPN 用来在页表里查出对应的**物理帧号**（PFN, physical frame number，也叫 PPN），offset 原样保留，两者拼起来就是物理地址：

```
virtual address = [ VPN | offset ]
```

```
PFN = PageTable[VPN]        （查页表）
```

```
physical address = (PFN << offset_bits) | offset
```

offset 的位数由页大小决定：4KB 页 = 2^12 字节，故 offset 占 12 位。其余高位是 VPN。举例：32 位虚拟地址、4KB 页，则 offset 12 位、VPN 20 位，共 2^20 个虚拟页。

初学者最容易卡在"为什么 offset 原样不动"。因为翻译只换"哪一页"、不换"页里第几个字节"：虚拟页和物理帧一样大，同一页内第 100 个字节翻译后还是所在帧的第 100 个字节，所以低 12 位直接照抄，只有高位的页号需要查表替换。把 VPN 想成"查字典的词条"、offset 想成"翻到那页后再数多少行"就顺了。

### 9.2.3 页表与页表项（PTE）位域

页表是一个以 VPN 为下标的数组，每个元素叫**页表项**（PTE, page table entry）。一条 PTE 里除了物理帧号 PFN，还打包了一组控制位（标志位）。最核心的是**有效/存在位**和一组**权限位**。不同架构位布局不同，下面并列 x86-64 与 RISC-V 两套一手定义。

x86-64 4KB 页的 PTE 低位标志（来自 Linux `arch/x86/include/asm/pgtable_types.h`，与 Intel SDM 一致，核实 2026-07-29）：

```
bit 0  P    Present   本项是否有效（物理帧是否在内存中）
bit 1  R/W  Read/Write 0=只读, 1=可写
bit 2  U/S  User/Supervisor 1=用户态可访问
bit 3  PWT  Page Write-Through（缓存策略）
bit 4  PCD  Page Cache Disable（缓存策略）
bit 5  A    Accessed  被访问过（由 CPU 置位）
bit 6  D    Dirty     被写过（由 CPU 置位）
bit 7  PS   Page Size 置 1 表示此项直接映射大页（见 9.5）
bit 8  G    Global    全局项，进程切换时 TLB 不刷（见 9.3）
bit 63 NX/XD No-Execute 置 1 表示此页不可执行（需 CPUID 支持）
中间若干位存放 PFN（物理帧号）
```

RISC-V（xv6 `kernel/riscv.h`，分支 riscv，核实 2026-07-29）的 PTE 低 10 位为标志、PPN 存于其上：

```
PTE_V (1<<0) valid  有效位
PTE_R (1<<1) read    可读
PTE_W (1<<2) write   可写
PTE_X (1<<3) exec    可执行
PTE_U (1<<4) user    用户态可访问
（本版 xv6 未定义 A/D 位；RISC-V 规范本身有 Accessed/Dirty 位）
PA2PTE(pa) = ((pa>>12)<<10)   PPN 置于 PTE 的第 10 位起
PTE_FLAGS(pte) = pte & 0x3FF  低 10 位为标志
```

初学者要记住两点。其一，PTE 不只是"帧号"，它同时是这一页的"权限护照"——读写执行权限、用户/内核归属都编码在同一条项里，硬件每次翻译都顺带查权限，越权访问当场触发异常。其二，A（accessed）和 D（dirty）位由 CPU 在访问/写入时自动置 1，操作系统靠读它们来近似"最近有没有用过这页、脏不脏"，这正是页替换算法（大主题10）的原料。注意 x86-64 与 RISC-V 的读/写位含义相同但布局不同，且 x86-64 用单独的 NX 位表达不可执行、而 RISC-X 用一个正向的 `PTE_X` 表达可执行——比对时要认清是哪套。

### 9.2.4 有效位与缺页

有效位（x86-64 的 P、RISC-V 的 PTE_V）标记这条 PTE 是否指向一个真实存在的物理帧。当硬件翻译时发现有效位为 0，就不再继续，而是产生一次**缺页异常**（page fault）陷入内核，由操作系统决定怎么办。

这个机制是整个虚拟内存的枢纽。有效位为 0 可能意味着好几种情况：这段虚拟地址进程根本没申请（非法访问，OS 送 SIGSEGV 杀掉进程）；或申请了但还没分配物理帧（按需分页，OS 现场分配一帧并填好 PTE 后重试）；或这页被换出到了磁盘（OS 从 swap 读回）。权限位违规（往只读页写、在 NX 页取指、用户态碰内核页）同样触发异常。这些"缺页之后怎么处理"的策略属于大主题10，本节只需理解：**有效位 + 权限位让页表成为一张可以'留白'和'设卡'的地图，硬件一撞到留白或卡口就把控制权交回 OS**。

### 9.2.5 分页的两大代价

朴素分页有两个明显代价：翻译变慢，页表占空间。

第一个代价是翻译变慢——每一次程序访存（本来一次内存访问）现在要先访问一次内存去读页表拿 PFN，再访问一次内存拿真实数据，访存次数翻倍，这个代价由 TLB 解决（9.3）。第二个代价是页表占空间——一张覆盖整个地址空间的线性页表可能大到离谱（32 位地址、4KB 页、4 字节 PTE 就要 2^20×4B = 4MB，每进程一份），这个代价由多级/倒排页表解决（9.4）。9.3 和 9.4 正是分别针对这两个代价的优化，本报告后半程都在还这两笔债。

## 9.3 TLB

### 9.3.1 TLB 是什么

TLB（Translation Lookaside Buffer，地址翻译后备缓冲，俗称快表）是 MMU 里一小块专门缓存"VPN → PFN 映射（连同权限位）"的高速硬件缓存。它直接解决 9.2.5 的第一个代价：有了 TLB，绝大多数翻译不必再去内存读页表，命中时几乎零延迟拿到 PFN。

初学者可以把 TLB 理解为页表的"高频词速查卡"。页表是一本厚字典（放在内存里，查一次要跑一趟内存），TLB 是贴在桌边的小卡片，记着你最近查过的几十上百个词的答案。因为程序访问内存有很强的**局部性**（短时间内反复碰同几页），这张小卡片的命中率通常极高（常见 >99%），于是分页"访存翻倍"的代价在实践中被摊薄到几乎可忽略。TLB 是一种**全相联或组相联**的小容量缓存，条目数量级通常是几十到上千（具体型号相关，本机未取硬件计数，见章末）。

### 9.3.2 命中与未命中流程

每次访存，硬件先拿 VPN 查 TLB。命中（hit）就直接用缓存里的 PFN 拼物理地址；未命中（miss）就必须走一趟页表（"页表遍历"，page walk），拿到 PFN 后把这条映射装进 TLB，再重试该指令。流程如下：

```
1. 从虚拟地址取出 VPN
2. 查 TLB：
     命中  → 取出 PFN（顺带查权限位），拼出物理地址，完成
     未命中 → 遍历页表得到 PFN → 填入 TLB → 重试本次访存
3. 若页表项无效/越权 → 触发缺页或保护异常（转 9.2.4 / 大主题10）
```

"未命中之后由谁走页表"分两种实现，比对要分账：x86-64 等是**硬件管理 TLB**——CPU 内建页表遍历器（page-table walker），未命中时硬件自动查页表填 TLB，OS 不介入；MIPS、以及 xv6 所在 RISC-V 的部分实现细节上，则可由软件（内核异常处理程序）填 TLB。OSTEP Ch19 明确区分这两派。有效访存时间可粗略写成：

```
EAT ≈ hit_rate × TLB命中开销 + (1 − hit_rate) × 走页表开销
```

命中率越接近 1，分页的翻译开销就越接近"零额外访存"。

### 9.3.3 覆盖率（TLB reach）与局部性

TLB 覆盖率（TLB reach / coverage）指 TLB 里所有条目加起来能覆盖多大一片虚拟内存，等于条目数乘以页大小：

```
TLB reach = TLB条目数 × 页大小
```

代入 1024 个条目乘 4KB 就是 4MB。这意味着如果程序的活跃工作集超过 4MB 且访问跳来跳去，TLB 就装不下所有需要的映射，命中率骤降、频繁走页表——这正是大页（9.5）的头号动机：把页大小从 4KB 提到 2MB，同样条目数覆盖率直接放大 512 倍。

对初学者，覆盖率把"TLB 大小"和"程序访问模式"联系了起来。TLB 之所以有效，前提是程序有**空间局部性**（连续访问同一页内的数据，一次 miss 换来后续大量 hit）和**时间局部性**（反复访问同几页）。数组顺序遍历这类访问局部性极好、TLB 命中率极高；而在超大数据结构上做随机指针跳转（如遍历一棵散落各页的大树）局部性差、TLB 频繁 miss，就是典型的 TLB 瓶颈场景。

### 9.3.4 TLB 一致性与刷新

TLB 是缓存，就有"缓存和真相不一致"的问题。当 OS 改了页表（回收一页、改权限、换出一页），或切换到另一个进程（页表整个换了）时，TLB 里的旧条目就变成了错误映射，必须被清除，这叫 TLB 刷新（flush）/失效（invalidation）。

最粗暴的做法是上下文切换时清空整个 TLB——正确但代价大，新进程头几十次访存全是 miss。为省这笔钱，硬件提供两条优化，比对要点名：其一是**地址空间标识符**（x86-64 叫 PCID、RISC-V/其他叫 ASID），给每条 TLB 项打上"属于哪个进程"的标签，切进程时不必清空、只认标签，避免张冠李戴；其二是**全局位**（x86-64 的 G 位，见 9.2.3），把内核这类所有进程共享、始终有效的映射标为 global，进程切换刷 TLB 时保留它们不动。改单页映射则用单条失效指令（x86-64 `invlpg`）只踢掉那一条，不必全清。多核系统上一个核改了共享页表还要通知其他核也失效对应条目，即"TLB shootdown"（跨核中断完成，属进阶，本报告只点名）。

## 9.4 多级/倒排页表

### 9.4.1 线性页表为什么装不下

线性（单级）页表是一个覆盖所有 VPN 的连续数组，它的大小 = 虚拟页数 × 每项字节数：

```
线性页表大小 = 2^(VPN位数) × PTE字节数
```

代入 32 位地址、4KB 页、4 字节 PTE：2^20 × 4B = 4MB，**每进程一份**，100 个进程就是 400MB 全花在页表上。到 64 位地址更是天文数字。问题的根源是线性页表不管进程实际用没用到，都要为每一个可能的 VPN 预留一个槽位，而真实进程的地址空间极其**稀疏**（代码、堆、栈中间是大片空洞）。

初学者抓住"稀疏"二字即可：地址空间大部分是没用的空洞，为空洞也建满槽位就是浪费。9.4.2 的多级页表本质上就是"只为用到的部分建表、空洞不建"。

### 9.4.2 多级页表

多级页表（multi-level page table）把一张巨大的线性页表切成许多小页表，再用一层（或多层）"页目录"去索引这些小页表；哪一段虚拟地址完全没用到，对应的整张小页表就**根本不分配**，页目录里那一项标为无效即可。这样页表本身也变成按需分配、稀疏存储，空间开销从"正比于地址空间大小"降到"正比于实际使用量"。

翻译时把 VPN 再切成几段，每段索引一级表，逐级下降，最后一级才拿到 PFN。代价是查一次要走多级、内存访问次数增加（k 级页表 + 1 次取数据 = k+1 次访存），但这正是 TLB（9.3）要摊薄的——TLB 命中时一层都不用走。多级页表是"用时间（更长的 miss 后遍历）换空间（页表小得多）"的经典折中，配 TLB 后时间代价被抹平。

一个 2 级的最小例：VPN 的高位选"页目录项"（指向某张二级页表或标为无效），低位在那张二级页表里选 PTE。地址空间里那些没用到的大段，其页目录项直接无效、下面整张二级表不存在，省下的正是为空洞预留的槽位。

### 9.4.3 x86-64 四级页表（与五级）

x86-64 在 4 级分页下使用 **48 位虚拟地址**，从高到低切成四段各 9 位、加 12 位页内偏移，逐级索引四张表：PML4 → PDPT（页目录指针表）→ PD（页目录）→ PT（页表）。每张表恰好 512 项（2^9）、每项 8 字节，正好占一个 4KB 页。参数（Intel 64 与 Linux 交叉核对，核实 2026-07-29）：

```
48位VA = [ 9位 PML4 | 9位 PDPT | 9位 PD | 9位 PT | 12位 offset ]
每级表项数 = 2^9 = 512，每项 8 字节，整表 512×8 = 4096 B = 一页
页大小 = 4KB（走满四级）
2MB 大页 = 在 PD 级令 PS=1 直接成帧（省最后一级）
1GB 大页 = 在 PDPT 级令 PS=1 直接成帧（再省一级）
```

5 级分页（LA57）再往上加一层 **PML5**，把虚拟地址扩到 **57 位**，可寻址虚拟空间从 256 TiB 增到 128 PiB，物理地址最高 52 位；自 Intel Ice Lake 起提供、Linux 4.14+ 支持，属**可选扩展**。本机实测：`/proc/cpuinfo` 报 "address sizes: 52 bits physical, 57 bits virtual"，但 CPU flags 中**无 `la57`**，即本机运行在 4 级分页（LA57 未启用）——这正好演示了 5 级为可选、需硬件与内核共同开启。

初学者只需记住"48 位地址被切成四个 9 位 + 一个 12 位偏移，每张表 512 项占一页"这个漂亮的自洽结构；9 位对应 512 项、512 项 × 8 字节正好一页，是被特意设计成整除的。为什么虚拟地址只用 48 位而不是全 64 位？因为 64 位空间大到没有必要全支持，硬件只实现低 48 位、高 16 位必须是第 47 位的符号扩展（"规范地址 canonical address"），5 级把这条线推到 57 位。

### 9.4.4 RISC-V Sv39 与 xv6 的 walk（只读源码腿）

RISC-V 特权规范定义了一族分页方案：Sv32（2 级，32 位）、Sv39（3 级，39 位）、Sv48（4 级，48 位）、Sv57（5 级，57 位），层级越多地址越宽，结构思路与 x86-64 完全同构（每级 9 位、每表 512 项）。xv6 教学内核用最简单的 **Sv39**：3 级、39 位虚拟地址，正好对照 x86-64 的四级看"多一级少一级"的差别。

xv6 `kernel/riscv.h` 的注释与宏（真读源码，核实 2026-07-29）把 39 位地址切法写得很清楚：

```
39位VA = [ 9位 L2 index | 9位 L1 index | 9位 L0 index | 12位 offset ]
PXSHIFT(level) = 12 + 9*level     // 第 level 级索引在 VA 里的起始位
PX(level, va)  = (va >> PXSHIFT(level)) & 0x1FF   // 取该级的 9 位索引
MAXVA = 1L << (9+9+9+12 - 1)       // 比 Sv39 上限少 1 位，避免符号扩展
```

`kernel/vm.c` 的 `walk()` 就是"逐级下降取索引"的教科书实现（真读源码）：

```c
// 从 level=2 走到 level=1，每级取 9 位索引进下一张表
for (int level = 2; level > 0; level--) {
  pte_t *pte = &pagetable[PX(level, va)];   // 本级 PTE
  if (*pte & PTE_V) {                        // 有效 → 顺着 PPN 进下一级表
    pagetable = (pagetable_t)PTE2PA(*pte);
  } else {                                   // 无效
    if (!alloc || (pagetable = kalloc()) == 0) return 0;  // 按需分配一张表
    memset(pagetable, 0, PGSIZE);
    *pte = PA2PTE(pagetable) | PTE_V;        // 填入指向新表的目录项
  }
}
return &pagetable[PX(0, va)];                // 返回最后一级（level 0）的 PTE 地址
```

`mappages()` 则对一段 `[va, va+size)` 逐页调 `walk(...,alloc=1)` 拿到 PTE、填入 `PA2PTE(pa) | perm | PTE_V` 建立映射（对已映射页会 `panic("remap")`）；`kvmmap()` 是内核启动期建内核页表时对 `mappages` 的封装（"does not flush TLB or enable paging"）。这段源码把 9.4.2 的抽象落到实处：`walk` 的 `alloc` 分支正是"只为用到的地址按需分配中间页表"，空洞地址永不进入 `walk` 也就永不分配下级表——多级页表省空间的机制在这十几行里一览无余。初学者对照 `PX(level,va)` 与 x86-64 的 9 位切分，会发现两套架构是同一个想法的不同层数。

### 9.4.5 倒排页表 / 散列页表

倒排页表（inverted page table）反过来想：不给每个进程一张"虚拟页 → 帧"的表，而是**全系统一张**"物理帧 → (进程, 虚拟页)"的表，表项数等于物理帧数（正比于物理内存大小，而非地址空间大小），因此极省空间。代价是翻译时不能用 VPN 直接下标，得搜索整张表，通常配一个散列表（hashed page table）加速：用 (pid, VPN) 求哈希定位。

初学者要抓住这个"倒过来"的巧思：线性/多级页表的大小取决于**虚拟**地址空间（可能极大且稀疏），倒排页表的大小取决于**物理**内存（有限且固定），所以在物理内存远小于虚拟空间时特别划算。历史上用于 PowerPC、部分 UltraSPARC；x86-64 用的是多级页表而非倒排，这里只作广度对照。OSTEP Ch20 把多级、倒排、散列并列为"高级页表"三种降空间手段。

#### 来源与时效
- OSTEP Ch20「Advanced Page Tables (Smaller Tables)」（网页版，核实 2026-07-25）：线性页表 4MB 算例、多级页表按需分配省空间、走 k 级 = k+1 次访存、倒排/散列页表。
- Intel 64 4/5 级分页 + Wikipedia「Intel 5-level paging」+ Linux（github torvalds/linux master，核实 2026-07-29）：x86-64 48 位 4 级（PML4/PDPT/PD/PT）、每表 512 项 8 字节、2MB/1GB 大页级别；5 级 LA57 57 位、128 PiB、52 位物理、Ice Lake 起 / Linux 4.14+，可选扩展。
- xv6-riscv `kernel/vm.c`、`kernel/riscv.h`（分支 riscv，核实 2026-07-29，**真读源码**）：Sv39 三级 9/9/9/12 切分、`PX`/`PXSHIFT`/`MAXVA`、`walk`/`mappages`/`kvmmap` 逐级下降与按需分配。
- RISC-V 特权规范：Sv32/Sv39/Sv48/Sv57 方案族（以 xv6 注释"Sv39 三级"坐实其一）。
- 本机实证：`/proc/cpuinfo` = "52 bits physical, 57 bits virtual"、flags 无 `la57`（本机 4 级分页，LA57 未启用），`pdpe1gb` flag 存在（支持 1GB 大页）。
- 交叉一致；仅"x86 用多级、非倒排"为架构选择差异，已点名。

## 9.5 大页（hugepages）

### 9.5.1 大页的动机：放大 TLB 覆盖率、压缩页表层级

大页（huge page / large page）就是比标准 4KB 大得多的页（x86-64 常见 2MB、1GB）。它一石二鸟：其一，一条 TLB 项现在覆盖 2MB 而非 4KB，TLB 覆盖率（9.3.3）成百倍放大，同样条目数能罩住大得多的工作集，TLB miss 骤减；其二，映射一大段内存所需的页表项和页表层级都变少（2MB 页省掉最后一级 PT、1GB 页再省一级 PD），页表内存和遍历深度都下降。

```
TLB reach（4KB, 1024项）= 1024 × 4KB   = 4 MB
TLB reach（2MB, 1024项）= 1024 × 2MB   = 2 GB   （放大 512 倍）
```

对初学者，大页解决的是"页太小 → TLB 装不下大程序的映射 → 频繁走页表"这个 9.3 末尾埋下的痛点。数据库、JVM 大堆、科学计算、虚拟机这类动辄用几十 GB 连续内存的负载，用 4KB 页会被 TLB miss 拖垮，用大页则命中率大幅回升。

### 9.5.2 x86-64 的大页尺寸：2MB 与 1GB

x86-64 用 PTE 里的**页大小位**（PS，bit 7，见 9.2.3）实现大页：在页目录 PD 级把 PS 置 1，该项就不再指向下一级页表、而是直接映射一个 **2MB** 物理帧；在更高的 PDPT 级把 PS 置 1，则直接映射 **1GB** 物理帧。这两个尺寸不是随意取的，恰好等于"少走一级 / 少走两级"时那一级本可索引的整段大小（512 × 4KB = 2MB，512 × 2MB = 1GB）。

`/sys/kernel/mm/hugepages/` 下有 `hugepages-2048kB`（2MB）和 `hugepages-1048576kB`（1GB）两个目录；`/proc/meminfo` 的 `Hugepagesize` = 2048 kB（默认大页 2MB）；`/proc/cpuinfo` flags 含 `pdpe1gb`（CPU 支持 1GB 页）与 `pse`（支持 2MB/4MB 页）。1GB 页需要 CPU 有 `pdpe1gb` 能力，本机具备。

### 9.5.3 Linux 的两条大页路径：hugetlbfs 与 THP

Linux 提供两种用大页的方式，机制不同、比对要分清。其一是显式大页（HugeTLB / hugetlbfs）：管理员预先从内存里预留一批固定尺寸的大页（通过 `/proc/sys/vm/nr_hugepages` 或 `/sys/kernel/mm/hugepages/*`），应用经 `mmap(MAP_HUGETLB)` 或 hugetlbfs 文件系统显式申请，可靠但要手工配额。其二是透明大页（THP, Transparent Huge Pages）：内核在后台自动把符合条件的匿名内存合并（promote）成 2MB 大页、必要时再拆回，应用无需改代码。

`/proc/meminfo` 显示 `HugePages_Total: 0`（未预留任何显式大页）、`/proc/sys/vm/nr_hugepages` = 0、且 `/proc/mounts` 未挂载 hugetlbfs——即显式大页处于"支持但未配置"状态；而 THP 的 `/sys/kernel/mm/transparent_hugepage/enabled` = `always [madvise] never`，当前档位为 **madvise**（仅对显式 `madvise(MADV_HUGEPAGE)` 的区域启用 THP）。`/proc/meminfo` 里 `FileHugePages: 145408 kB` 表明确有文件页以大页形式在用（THP 对文件映射生效）。

初学者理解成"显式大页 = 你手动圈一块专用大页池、要自己申请"，"THP = 系统悄悄帮你合并，省心但不完全可控"。两者可同时存在，面向的场景不同：数据库常用显式大页求确定性，通用负载多靠 THP 自动获益。

### 9.5.4 大页的代价与权衡

大页不是免费午餐。其一，内部碎片放大：一个只用几 KB 的映射若占了整张 2MB 页，浪费的是 MB 级而非 KB 级。其二，内存分配更难：分配一个物理上连续的 2MB/1GB 帧，要求有足够大的连续空闲物理内存，内存碎片化后可能凑不出来（1GB 页尤甚，常需开机预留）。其三，THP 的后台合并/拆分本身耗 CPU，某些延迟敏感负载反而因 THP 的抖动而变慢——这是 THP 默认多为 `madvise` 而非 `always` 的现实原因。

所以大页是"覆盖率/页表开销"与"碎片/分配难度/管理复杂度"之间的权衡：工作集大且连续、访问局部性一般的负载受益明显；小而零碎的负载用大页反而亏。它和 9.3、9.4 一脉相承——都是围绕"页多大、页表多深、TLB 装得下多少"这组耦合参数在不同负载下找平衡点。
