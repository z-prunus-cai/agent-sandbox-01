## 5.1 调度指标与工作负载假设

### 5.1.1 调度器要优化的是几个彼此冲突的指标

调度器好不好，得先说清"用什么尺子量"。最核心的两把尺子是**周转时间（turnaround time）**和**响应时间（response time）**。周转时间衡量一个任务从进入系统到彻底完成经历了多久，是批处理/吞吐视角关心的量；响应时间衡量任务从进入系统到第一次被调上 CPU 等了多久，是交互视角关心的量。

周转时间定义为（块级公式）：

T_turnaround = T_completion − T_arrival

响应时间定义为（块级公式）：

T_response = T_firstrun − T_arrival

一组任务通常看平均值，例如平均周转时间（块级公式）：

T_avg_turnaround = (1/N) · Σ_i (T_completion,i − T_arrival,i)

**这两把尺子经常打架**。一个只顾把平均周转时间压到最低的调度器，会倾向于让某个任务一口气跑完再理下一个，于是后来的任务响应奇慢；一个只顾响应快的调度器，会频繁地把 CPU 在任务间切来切去，让每个任务都能很快"露个脸"，但没有任务能一口气跑完，平均周转反而变差，还多付了切换开销。第三把尺子是**公平（fairness）**——每个任务是否拿到了它"应得"的那份 CPU；公平和性能同样常常对立（最公平的做法未必让平均周转最优）。理解"没有一个调度器能同时把所有指标做到最好"，是理解后面所有算法的前提：每个算法都是在这些冲突里选了一个折中点。

### 5.1.2 批处理假设 vs 交互假设

早期调度理论建立在一串**简化假设**上（OSTEP Ch7 明确列出并逐条推翻）：每个任务运行时间相同、都同时到达、一旦运行就跑到完（不做 I/O）、运行时间事先已知。这套假设对应的是**批处理（batch）工作负载**——一批算好的计算作业排队跑完，没人在终端前等着。

现实里更常见的是**交互式（interactive）工作负载**：任务频繁地跑一小段就阻塞去等 I/O（等键盘、等磁盘、等网络），醒来再跑一小段。对交互任务，用户盯着屏幕，响应时间比总周转更要命。批处理假设与交互假设的分野解释了调度史的走向：越往后的算法（RR→MLFQ→CFS/EEVDF）越是为"运行时间未知 + 大量 I/O 阻塞 + 人在等响应"这套现实假设设计的。初学者可以记住一句话——**假设越贴近现实，算法越复杂**，因为现实剥夺了"运行时间已知""任务不阻塞"这些让问题变简单的前提。

### 5.1.3 为什么"运行时间未知"是核心难点

后面会看到，理论上最优的算法（如 SJF/SRTF 对平均周转最优）都需要"预先知道每个任务要跑多久"。而真实系统里，调度器在任务跑完之前**根本不知道**它还要跑多久。这一条假设的破除，是从"漂亮但不可实现的最优算法"转向"能落地的实用算法"的分水岭。

实用调度器的应对办法是**用过去预测未来**：一个最近一直短时间就阻塞的任务，多半是交互任务，给它高优先级、快响应；一个一直霸着 CPU 满负荷算的任务，多半是计算密集，把它往后放。MLFQ（5.3）正是把这条"观察行为、动态调整"的思路制度化。记住这个难点，就能理解为什么现代调度器都带"反馈"或"记账"机制——它们是在没有先知的情况下逼近先知才能做到的最优。

## 5.2 基本算法：FCFS / SJF / SRTF / RR

### 5.2.1 FCFS（先来先服务）与护航效应

FCFS（First-Come, First-Served，也叫 FIFO）是最朴素的调度：谁先到就先跑，跑到完（或阻塞）再理下一个，非抢占。它实现简单、绝对公平（按到达顺序），在任务长度相近时表现也不错。

它的致命短板是**护航效应（convoy effect）**：一个耗时很长的任务排在前面，后面一堆短任务只能干等，平均周转时间被拖垮。举 OSTEP 的最小例子：三个任务 A、B、C 几乎同时到达，A 需 100 秒、B 和 C 各需 10 秒。FCFS 按 A→B→C 跑，完成时刻是 100、110、120，平均周转 (100+110+120)/3 = 110 秒。一辆慢卡车（A）堵在最前面，后面的小汽车（B、C）全被"护航"着爬行——这就是护航效应的画面。它直接引出下一个算法：要是能让短任务先跑呢？

### 5.2.2 SJF（最短作业优先）：非抢占下对平均周转最优

SJF（Shortest Job First）挑就绪任务里**预计运行时间最短**的先跑。把上面的例子换成 SJF：B→C→A，完成时刻 10、20、120，平均周转 (10+20+120)/3 = 50 秒——比 FCFS 的 110 秒几乎减半。可以证明，在所有任务同时到达且非抢占的前提下，SJF 给出**最小的平均周转时间**（把短的排前面总不吃亏）。

SJF 有两个初学者必须记住的问题。其一，它假设**运行时间事先已知**——这正是 5.1.3 说的核心难点，现实里做不到，所以纯 SJF 不可直接实现，只能靠预测近似。其二，若任务**不是同时到达**（一个长任务先跑上了，短任务后到），非抢占的 SJF 只能等长任务跑完，护航效应又回来了——这引出抢占版本 SRTF。

### 5.2.3 SRTF（最短剩余时间优先）：SJF 的抢占版

SRTF（Shortest Remaining Time First，也叫 PSJF，抢占式 SJF）在 SJF 基础上加入抢占：每当有新任务到达，就比较"新任务的运行时间"与"当前任务的剩余时间"，谁短谁上。这样长任务跑到一半，来了个短任务也会被打断让路。在任务可随时到达的场景下，SRTF 对平均周转时间最优。

代价是它对长任务**可能造成饥饿**——只要短任务源源不断地来，长任务的剩余时间永远不是最短，就一直被插队、迟迟跑不完。而且它同样需要预知运行时间。SRTF 把周转做到极致，却完全不管响应时间也不管公平：一个刚到的长任务可能立刻被后来的短任务反复抢占。要兼顾响应，就需要下一个思路——轮转。

### 5.2.4 RR（轮转）：为响应时间而生，与时间片长短的权衡

RR（Round-Robin）不再让任务跑到完，而是给每个就绪任务一个固定的**时间片（time slice / quantum）**，轮流各跑一片，跑满就切到队尾。它牺牲平均周转（没有任务能一口气跑完，都是走走停停），换来**优秀且可预测的响应时间**——N 个任务时，任何任务最多等 (N−1) 个时间片就能露面。RR 天生适合交互式负载。

时间片长短是 RR 的核心权衡，务必记牢这对矛盾：

时间片太短 → 响应快、公平细，但上下文切换（保存/恢复寄存器、刷 TLB、污染缓存）的开销占比升高，有效吞吐下降；

时间片太长 → 切换开销摊薄、吞吐高，但 RR 退化得越来越像 FCFS，响应时间变差。

所以时间片要选得"**足够长到摊薄切换开销，又足够短到响应可接受**"（典型量级为毫秒到几十毫秒，具体值随系统而定，不凭记忆填死）。这里也埋下一个更深的观察：单纯的 RR 对所有任务一视同仁，既不区分交互还是计算，也不优化周转——真正好用的调度器需要**区别对待不同行为的任务**，这正是 MLFQ 的出发点。

## 5.3 MLFQ（多级反馈队列）

### 5.3.1 MLFQ 要解决的矛盾：不预知未来，还要同时顾好周转与响应

MLFQ（Multi-Level Feedback Queue）的目标野心很大：在**不预先知道任务运行时间**的前提下，既让交互任务响应快（像 RR/SRTF 优待短任务），又让长任务的周转不太差（像 SJF）。它的办法是设多个**优先级队列**，用任务过去的行为动态调整它在哪一级——这就是"反馈（feedback）"二字的由来。

MLFQ 维护若干条队列，优先级从高到低。任何时刻，调度器**总是跑当前最高非空队列里的任务**；同一队列内部用 RR。关键在于任务不是固定在某一级，而是根据它"表现得像不像交互任务"上下浮动。初学者可以把它想成一个不断观察学生的老师：一个总是很快答完就举手等下一题的学生（频繁让出 CPU=交互任务），被留在高优先级快速轮到；一个抱着一道题埋头算很久的学生（用满时间片=计算任务），被慢慢降到低优先级批量处理。

### 5.3.2 MLFQ 的基本规则与优先级升降

MLFQ 的行为由一组规则定义（OSTEP Ch8 逐条给出，这里给教学版）。两条选取规则：优先级高者先跑；同级之间 RR。

关键是优先级**如何变化**的规则。早期朴素版本的思路是：新任务进最高优先级；一个任务若**用满了一个时间片仍未主动让出**（说明它在闷头算，像计算密集型），就降一级；一个任务若在时间片用完前就主动放弃 CPU（比如去等 I/O，像交互型），就保持在原级。这样，交互任务因为老是提前让出而稳居高优先级、响应快；计算任务被逐级下沉、在低优先级以更长时间片批量运行、周转不至于太糟。整个过程完全靠观察行为，不需要预知运行时间——这正是它比 SJF/SRTF 高明、比 RR 聪明的地方。

### 5.3.3 防饿死：周期性提升与防欺骗

朴素 MLFQ 有两个必须堵上的漏洞，否则会被现实击穿。

第一个是**饥饿（starvation）**：交互任务太多时，高优先级队列一直不空，被降到底层的长任务可能永远轮不到，饿死。修法是**周期性提升（periodic boost）**：每隔一段时间 S，把所有任务一次性拉回最高优先级，重新洗牌。这既保证长任务隔一阵总能被跑到（不饿死），也让一个原本是计算型、后来转为交互型的任务能及时"翻身"。

第二个是**被欺骗（gaming the scheduler）**：如果规则是"时间片没用完就保级"，恶意任务可以在每个时间片快结束前故意做一次极短的 I/O，从而永远用不满时间片、永远赖在高优先级，霸占 CPU。修法是**按累计配额记账而非单次时间片**：给每个优先级一个总的时间配额（time allotment），任务在该级用够累计配额（无论中间让出多少次）就降级，堵死"假装让出"的空子。

初学者记住 MLFQ 的精髓是"**用行为代替先知**"：它观察你怎么用 CPU 来猜你是什么任务，再动态调级；而 boost 和累计配额这两个补丁，是让这套猜测在有饥饿风险和有恶意用户的现实里仍然站得住。

## 5.4 比例份额：lottery / stride / CFS

### 5.4.1 比例份额调度的目标：按份额公平，而非优化周转

比例份额（proportional-share / fair-share）调度换了一个完全不同的目标：不再追求最小平均周转，而是保证**每个任务按其"份额"拿到成比例的 CPU**。你给任务分配一个权重（份额/票数），调度器就努力让它拿到的 CPU 时间正比于这个份额。这天然契合"公平"这把尺子，也便于表达优先级（份额多=优先级高）。

一个任务应得的 CPU 比例可写作（块级公式）：

share_i = w_i / Σ_j w_j

其中 w_i 是任务 i 的权重/票数。初学者可以把它想成分蛋糕：总权重是整块蛋糕，你的权重占比多少，就该分到多少 CPU。下面三种机制是实现这个目标的三条不同技术路线——随机的 lottery、确定的 stride、以及 Linux 曾用的 CFS。

### 5.4.2 彩票调度（lottery scheduling）

彩票调度给每个任务发一叠**彩票（tickets）**，票数正比于份额；每个时间片调度器**随机抽一张票**，持有该票的任务上场。长期来看，一个任务被抽中的概率正比于它的票数，于是它拿到的 CPU 时间在**统计意义上**正比于份额。

它的优点是实现极简、天然规避饥饿（只要有票就有非零概率被抽中）、且加入/离开任务时无需重算复杂状态。缺点是**短期不确定**：随机性意味着在短时间窗口内实际份额可能明显偏离理论值（抛硬币十次不一定五正五反），只有长期才收敛。彩票机制还支持一些巧思，如"票据转让"（一个等待者可把票临时让给持锁者帮它快点跑完）。初学者记住一句：lottery 用随机性换来了简单与无饥饿，代价是精确性只在长期成立。

### 5.4.3 步长调度（stride scheduling）：确定性的比例份额

步长调度是 lottery 的**确定性**对应物，消除了短期抖动。给每个任务一个与票数成反比的**步长（stride）**：票越多、步长越小。每个任务维护一个**行程值（pass）**，每次被调度上场后，把自己的 pass 增加一个 stride。调度器每次挑**当前 pass 最小**的任务运行。

步长定义为（块级公式，C 为一个大常数）：

stride_i = C / tickets_i

调度后推进（块级公式）：

pass_i ← pass_i + stride_i

因为票多者步长小、每次只推进一点点，它就会被更频繁地选中，从而精确地拿到成比例的 CPU——而且是**确定性精确**，不像 lottery 要靠长期收敛。代价是引入了每任务的全局状态（pass 值），新任务加入时该把它的 pass 设成多少要小心处理（通常设为当前最小 pass，避免新任务一进来就疯狂追赶或被巨额落后）。stride 与 lottery 的对照是理解"随机 vs 确定"两种公平实现的经典一课。

### 5.4.4 CFS 与 vruntime（Linux 2007–2023 的默认实现）

CFS（Completely Fair Scheduler）是 Linux 从 2.6.23（2007）到 6.5 的默认通用调度器，是比例份额思想的高效工程实现。它不发彩票、不算步长，而是给每个任务维护一个**虚拟运行时间（vruntime）**：任务实际跑了多久，就按其权重折算后累加到 vruntime 上；调度器**总是挑 vruntime 最小的任务**跑（即"最亏欠的先补"）。为高效找到最小者，就绪任务按 vruntime 组织在一棵**红黑树**里，取最左节点即最小、复杂度 O(log N)。

vruntime 的累加按权重折算（块级公式，NICE_0_WEIGHT 为 nice 0 的基准权重 1024）：

vruntime_i ← vruntime_i + Δexec · (NICE_0_WEIGHT / w_i)

权重大（优先级高）的任务，同样跑 Δexec 物理时间，其 vruntime 只增长很小一点，于是显得"更亏欠"、更容易再被选中，从而拿到更多 CPU——这就把"按权重成比例分配"编码进了"追平 vruntime"这一条简单规则里。初学者的直觉：vruntime 是一个"已享用时间"的记账本，权重是折算汇率，CFS 永远服务账面上最吃亏的那个，让大家的加权已用时间趋于一致。**注意时效**：CFS 是理解 Linux 公平调度的教材主线，但**基线 6.18.5 上它已被 EEVDF 取代**（见 5.5），红黑树按 key 组织、按 nice 折算权重的骨架被 EEVDF 继承，但"挑谁"的判据从"min vruntime"变成了"eligible 中 min virtual deadline"。

本机实证——`/proc/self/sched` 直接暴露了这套记账字段（Linux 6.18.5 @2026-07-29，一个 nice 0 任务）：

```
se.vruntime      :    5.366910
se.load.weight   :     1048576      # 反映 nice 权重（nice 0 基准，内核内部为缩放表示）
policy           :           0      # SCHED_OTHER（普通/公平类）
prio             :         120      # nice 0 → 内核优先级 120（120 + nice）
se.slice         :     2100000      # 单位 ns，本任务的时间片/请求（EEVDF 语义，见 5.5）
```

`se.vruntime` 与 `se.load.weight` 这两个字段就是上式里的记账本与权重；`se.slice`（EEVDF 引入的每任务请求时间片）则是 5.5 的伏笔。

## 5.5 Linux 当前实现：EEVDF 与调度类

> ⚙演进快·锚版本·随时变 —— 本节结论锚定基线内核 6.18.5 与内核文档 https://docs.kernel.org/scheduler/sched-eevdf.html（核实 2026-07-29）；EEVDF 内部精确公式/默认常数以内核源码为准，未逐一实测处标「待核」。

### 5.5.1 基线现状：EEVDF 已取代 CFS（≥6.6，2023）

这里必须先分清教材与实现两账。OSTEP/CS162 讲的 CFS 是理解 Linux 公平调度的主线，但它**不是基线机器上此刻在跑的东西**。Linux 6.6（2023 年发布）用 **EEVDF（Earliest Eligible Virtual Deadline First）** 取代了 CFS 作为普通任务（`SCHED_OTHER`/`SCHED_NORMAL`，即 fair 类）的默认调度器。EEVDF 算法本身源自 1995 年 Stoica 与 Abdel-Wahab 的论文，由内核维护者 Peter Zijlstra 落地进内核。

基线 `uname -r` 为 6.18.5（≥6.6），`/proc/self/sched` 里出现了 EEVDF 特有的 `se.slice` 字段（CFS 时代没有的"每任务请求时间片"），普通任务 `policy=0`（`SCHED_OTHER`）走的即 fair 类。初学者只需记住：**读教材理解 CFS 的 vruntime/红黑树心智模型，但谈"我这台 Linux 现在怎么调度普通任务"，答案是 EEVDF**。二者共享"按 nice 折算权重、红黑树里挑一个"的骨架，区别在挑选判据。

### 5.5.2 EEVDF 三个核心概念：lag、eligibility、virtual deadline

EEVDF 在 vruntime 记账之上加了三个概念（依据内核 EEVDF 文档，核实 2026-07-29）。第一个是滞后量 lag，即每个任务"应得 CPU 时间"与"实际已得"之差——lag 为正表示系统还欠这个任务时间（它被亏待了），lag 为负表示它已超额享用，lag 是 EEVDF 判断公平与否的账面量。

第二个是资格 eligibility：只有 lag ≥ 0（即尚未超额、系统还欠着它）的任务才"有资格（eligible）"被立即调度。这一步保证不会让已经超额的任务继续抢在亏欠者前面，是 EEVDF 比 CFS 更强的公平约束。

第三个是虚拟截止时间 virtual deadline（VD），它给每个有资格的任务算出，取决于该任务的请求时间片（request/slice）与权重；调度器在所有 eligible 任务里挑 VD 最早的那个上场。直觉上，请求的时间片越短（越像延迟敏感的交互任务），它的虚拟截止越早、越会被优先调度——这让 EEVDF 能更好地照顾低延迟需求，而不像 CFS 只看 vruntime 一个维度。

EEVDF 选取规则一句话概括为：

在 lag ≥ 0（eligible）的任务中，选虚拟截止时间 VD 最早者运行。

内核文档给出的一个新能力是：任务可通过 `sched_setattr()` 系统调用**请求特定的时间片长度**（`se.slice` 即由此而来），延迟敏感的应用可据此表达"我要短片、快响应"的需求。这是 CFS 时代没有的旋钮。

### 5.5.3 EEVDF 精确公式与默认常数标「待核」

上面三个概念的**精确内核公式与默认参数**（虚拟截止时间的确切算式、基准时间片 `base_slice_ns` 的默认值、lag 的衰减/重置规则、长睡任务的 lag 处理即"deferred dequeue"细节）随内核版本演进，且内核 EEVDF 文档本身未给出完整闭式公式。本报告只落已由文档/实测坐实的定性结论，**具体常数与算式一律标「待核」，不凭记忆填**。

按 EEVDF 原始论文的标准形式，虚拟截止时间可写作如下概念式（块级；ve 为任务的 eligible 虚拟时间、r 为请求、w 为权重，**内核实际实现与此的对应关系待核**）：

vd_i = ve_i + r_i / w_i

内核文档明确提到的两条运行时行为：长时间睡眠的任务其 lag 最终会被重置/衰减，睡眠任务采用"deferred dequeue"（延迟出队、仍在队上标记），以防"睡一小下再回来刷新账面"式的占便宜。初学者不必记住公式细节，只需把握：EEVDF = CFS 的公平记账 + "先看有没有资格（lag≥0）、再按虚拟截止挑最急的"，并把时间片大小变成任务可请求的一等参数。

### 5.5.4 调度类的优先级层级

Linux 不是只有一个调度器，而是若干**调度类（scheduling classes）**按固定优先级叠放，高类里只要有可运行任务就压过低类。基线上从高到低的顺序为：

stop  >  deadline (SCHED_DEADLINE)  >  rt (SCHED_FIFO / SCHED_RR)  >  ext (sched_ext, ≥6.12)  >  fair (EEVDF: SCHED_OTHER/BATCH/IDLE)  >  idle

deadline 类（`SCHED_DEADLINE`）用 EDF（最早截止优先）配合 CBS（恒定带宽服务器）实现，任务用 (Runtime, Deadline, Period) 三参数声明"每 Period 内需要 Runtime 的 CPU、须在 Deadline 前拿到"，是用户可控的最高优先级实时策略。

rt 类（`SCHED_FIFO`/`SCHED_RR`）是固定优先级实时策略，优先级 1–99。`SCHED_FIFO` 跑到自己阻塞、被更高优先级抢占或主动 `sched_yield()` 为止；`SCHED_RR` 是加了时间片轮转的 FIFO（同优先级内轮转）。

fair 类是普通任务的家，基线上由 EEVDF 实现，含 `SCHED_OTHER`（默认）、`SCHED_BATCH`（批处理、弱化唤醒抢占）、`SCHED_IDLE`（极低优先级）。

ext 类（`sched_ext`，≥6.12，2024）是一个新特性，允许用 BPF 程序把调度策略写成可在运行时热插拔的模块，位于 rt 之下、fair 之上；它在基线上是否启用需实测，本报告标「待核」，仅记其存在与层级位置。

本机实证——`chrt -m` 列出基线支持的策略与优先级范围（Linux 6.18.5 @2026-07-29）：

```
SCHED_OTHER    min/max priority : 0/0
SCHED_FIFO     min/max priority : 1/99
SCHED_RR       min/max priority : 1/99
SCHED_BATCH    min/max priority : 0/0
SCHED_IDLE     min/max priority : 0/0
SCHED_DEADLINE min/max priority : 0/0
```

普通类（OTHER/BATCH/IDLE/DEADLINE）静态优先级恒为 0——它们的"优先级"不靠这个数字而靠 nice 值/份额/截止参数表达；只有 FIFO/RR 用 1–99 的实时优先级。用 `chrt` 可查改任务策略，用 `nice`/`renice` 调普通任务的 nice 值（本机 `nice -n 10 …` 实测 niceness 生效为 10）。

## 5.6 多处理器调度

### 5.6.1 从单队列到每 CPU 队列

有了多个 CPU（基线机 `nproc`=4），调度问题多了一维：不只是"谁上"，还有"上哪个 CPU"。最直接的做法是**单一共享就绪队列（SQMS，single-queue）**：所有 CPU 从同一把队列里取任务。它简单、天然负载均衡，但有两个硬伤——那把队列需要**加锁**，CPU 一多，锁争用就成为可扩展性瓶颈；而且任务会被不同 CPU 轮流捡起，破坏缓存亲和。

现代做法是**每 CPU 一条就绪队列（MQMS，multi-queue）**：每个 CPU 维护自己的运行队列，各自独立调度，锁争用小、可扩展性好、天然保留缓存亲和。Linux 正是每 CPU 运行队列。代价是引入了新问题——各队列忙闲不均，需要**负载均衡**把任务在 CPU 间搬动。初学者记住这条主线：多核调度的核心张力是"**per-CPU 队列带来的可扩展性/缓存亲和" 与 "由此产生的负载不均，需要迁移来纠正**"之间的平衡。

### 5.6.2 缓存亲和（cache affinity）

**缓存亲和**指一个任务反复在**同一个 CPU** 上运行是划算的：它的数据还留在那个 CPU 的 L1/L2 缓存（以及 TLB 里的地址翻译）里，重新跑不用再从内存慢慢加载。如果把它换到另一个 CPU，缓存全是冷的，得重新填充，性能受损——这叫"缓存被污染/失效"的迁移代价。

所以好的多核调度器**倾向于让任务留在原 CPU**（affinity），只有在负载明显失衡、迁移收益大于缓存损失时才搬。这解释了为什么 MQMS（每 CPU 队列）天然优于 SQMS：任务默认待在自己那条队列对应的 CPU 上，缓存亲和自动保住。初学者可以把缓存想成 CPU 桌上摊开的资料——同一个人（任务）回到同一张桌子（CPU）接着干，资料还在；换张桌子就得把资料重搬一遍。

### 5.6.3 负载均衡（load balancing）

每 CPU 队列必然带来忙闲不均：有的 CPU 队列排长队、有的空转。**负载均衡**周期性地检查各 CPU 的负载，把任务从繁忙 CPU **迁移（migrate）**到空闲 CPU，让整体利用率均衡。它与缓存亲和是一对矛盾——迁移能均衡负载，却牺牲被迁任务的缓存亲和，所以调度器要在两者间权衡，只在收益够大时才迁。

一种经典的均衡手法是**工作窃取（work stealing）**：负载轻（队列快空）的 CPU 主动去偷看别的 CPU 队列，从繁忙者那里"偷"几个任务过来跑。让空闲者主动找活干，比让繁忙者停下来分发更省事。Linux 的 CFS/EEVDF 使用基于**调度域（scheduling domains）**的分层负载均衡，按 CPU 拓扑（同核超线程 < 同 L3 的核 < 跨 NUMA 节点）由近及远地均衡，越近越倾向迁移、越远迁移越谨慎（因为跨得越远，缓存/内存代价越高）。

### 5.6.4 CPU 亲和性（affinity）与 NUMA

**CPU 亲和性（CPU affinity）** 是允许用户/程序**显式约束**一个任务只能在指定的 CPU 子集上运行的机制，用一个位掩码表示允许哪些 CPU。它用来手动保住缓存亲和、隔离关键任务到专用核、或配合 NUMA 布局。

**NUMA（非一致内存访问）** 是多核的另一层现实：内存分挂在不同节点上，CPU 访问"本地节点"内存快、访问"远端节点"内存慢。NUMA 感知的调度会尽量让任务在**离它内存最近的节点**的 CPU 上跑，负载均衡也会把这层代价计入（跨 NUMA 迁移最贵）。

本机实证——查看和设置亲和性（Linux 6.18.5，4 CPU @2026-07-29）：

```
$ grep -i cpus_allowed /proc/self/status
Cpus_allowed:      f            # 位掩码 0b1111 = 4 个 CPU 全允许
Cpus_allowed_list: 0-3

$ taskset -cp <pid>
current affinity list: 0-3       # 默认可在全部 4 个 CPU 上跑
```

`/proc/[pid]/status` 的 `Cpus_allowed`（位掩码）与 `Cpus_allowed_list`（人读列表）就是这个任务的亲和性掩码；用 `taskset -c 0 <cmd>` 可把任务绑到 CPU 0（缩小掩码到 `1`），常用来做绑核实验或隔离。基线机未暴露多 NUMA 节点（单节点），故 NUMA 的跨节点代价本机不可直测，标为概念性结论。
