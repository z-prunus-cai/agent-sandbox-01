## 1.1 OS 作为资源虚拟化器

### 1.1.1 操作系统的两种视角：资源管理器与抽象机器

操作系统没有单一的精确定义，但两个互补的视角合起来就说清了它是什么。自底向上看，它是**资源管理器（resource manager）**：CPU、内存、磁盘、网卡这些物理资源只有一份或几份，OS 负责在众多要用它们的程序之间做分配、复用与仲裁，决定谁在什么时候用多少。自顶向下看，它是**抽象机器（extended / virtual machine）**：它在裸硬件之上架起一层干净的抽象——进程、地址空间、文件、套接字——让应用程序面对的是「好用的接口」而不是「难缠的寄存器和扇区」。

对初学者来说，可以把 OS 想成一栋公寓楼的物业加建筑设计。物业是资源管理器：一栋楼的水电、电梯、门禁就那么多，物业排班、限流、发钥匙，让几百户人家互不打架地共用。建筑设计是抽象机器：你住进来看到的是「房间、开关、水龙头」，而不是「电网相位、水管压力、承重墙钢筋」——那些又危险又难用的底层细节被包装成了简单接口。Silberschatz 把这两个视角并列为理解 OS 的标准切入点，Tanenbaum 则强调「抽象机器」这一面：OS 最重要的任务是向用户隐藏硬件的丑陋，提供更方便的模型。两本经典教材视角一致，只是侧重不同。

一个常见误解是把 OS 等同于图形界面或一堆自带软件（浏览器、文件管理器）。严格意义上的 OS 核心是**内核（kernel）**——那个常驻内存、掌握特权、真正在管资源的部分；桌面、shell、编译器都是运行在它之上的普通程序。本篇讲的「操作系统」主要指内核及其提供的接口。

### 1.1.2 虚拟化 CPU：让一个处理器看起来像很多个

**虚拟化 CPU** 指 OS 通过快速地在多个进程之间切换，制造出「每个程序都独占了一颗 CPU」的错觉，尽管物理上可能只有一颗核在轮流服务大家。这种在时间维度上的复用叫**时分复用（time sharing）**。

OSTEP 用一个经典例子讲透这件事：写一个只会不停打印自己名字的小程序，同时启动四份，在单核机器上你会看到四个名字**交替**出现，仿佛四颗 CPU 同时在跑——但真相是一颗 CPU 飞快地切来切去。这个「错觉」之所以成立，是因为切换发生得足够快、足够频繁，人眼和大多数程序都察觉不到自己曾被暂停。要实现它，OS 必须解决两个问题：一是**机制（mechanism）**，即怎么保存一个程序的现场、切到另一个（上下文切换，OS-03 详述）；二是**策略（policy）**，即该把 CPU 先给谁、给多久（调度，OS-05 详述）。本篇只需记住「一个 CPU 被虚拟成很多个」这个结果。

与「时分复用」相对的是**空分复用（space sharing）**——把一份资源在空间上切块分给不同用户，磁盘、内存更多用这种方式。CPU 天然是时分的，因为它一次只能执行一条指令流，切块没有意义。

### 1.1.3 虚拟化内存：每个进程都以为自己独占整块内存

**虚拟化内存** 指 OS 给每个进程一份私有的、连续的**地址空间（address space）**假象：进程看到的内存地址是**虚拟地址**，从 0 开始、看起来它独占了整台机器的内存，实际这些虚拟地址被硬件（MMU）加 OS 一起翻译到物理内存中零散、共享的位置。

这里的直觉是「善意的谎言」。如果两个程序都往「地址 0x1000」写数据，它们各自的 0x1000 其实落在物理内存的不同地方，互不干扰——OS 和硬件替它们把地址翻译开了。这带来两个好处：一是**隔离**，一个进程无法读写另一个进程的内存（保护）；二是**简化编程**，每个程序都能假设自己拥有一整块干净、连续的内存，不必操心别人。OSTEP 同样用一个小程序演示：打印某个变量的地址并反复修改它，同时跑多份，会看到它们**打印出相同的地址**却互不影响——因为那是各自地址空间里的虚拟地址。地址翻译、页表、TLB 的具体机制归 OS-08/OS-09，本篇只需建立「内存被虚拟化成人手一份」的图景。

### 1.1.4 抽象与复用设备：把裸硬件包成统一接口

对内存和 CPU 之外的设备（磁盘、终端、网卡），OS 的核心动作是**抽象**加**复用**：把千奇百怪的硬件细节藏进内核，向上暴露少数几种统一的抽象——最典型的是「文件」。磁盘上的字节流、终端的输入输出、网络连接，在 Unix 传统里都被抽象成可以 `open`/`read`/`write`/`close` 的**文件描述符**，应用程序不需要知道背后是 SSD 还是键盘。

初学者可以体会这一层的价值：正因为有统一抽象，`cat` 这个命令既能读普通文件，也能读键盘、读管道、读设备节点——它只管对一个文件描述符 `read`，剩下的由内核按设备类型分派。这就是 Unix「一切皆文件」哲学的落点。同时 OS 负责设备的**复用与仲裁**：多个程序同时要写磁盘，内核排队、缓冲、调度，保证数据不错乱。设备交互、驱动分层的机制归 OS-11，文件接口归 OS-13，本篇只点出「设备被抽象成统一接口并被安全共用」。

### 1.1.5 三块拼图预告：虚拟化、并发、持久化

OSTEP 把整个操作系统的知识组织成**三块拼图（three easy pieces）**：**虚拟化（virtualization）**、**并发（concurrency）**、**持久化（persistence）**。虚拟化讲 OS 如何把物理 CPU 和内存变成人手一份的虚拟资源（进程、地址空间）；并发讲当很多活动同时进行时如何保证正确（线程、锁、条件变量）；持久化讲如何把数据可靠地存到断电也不丢的设备上（I/O、磁盘、文件系统）。

这三块正好对应本课后续大主题的骨架：OS-02~05、08~10 属虚拟化，OS-06~07 属并发，OS-11~14 属持久化。把它当成一张地图——本篇 1.1 是在告诉你「OS 干的事可以归成这三摊」，后面每个大主题都是在往其中一摊里填细节。这个三分法是 OSTEP 独有的组织方式，Silberschatz/Tanenbaum 用的是更传统的「进程管理 / 内存管理 / 存储管理 / 保护与安全」分章，内容覆盖大体相同，只是切法不同，读者不必纠结哪种「更对」。

## 1.2 双模式与特权级

### 1.2.1 为什么需要双模式：不能让用户程序为所欲为

**双模式（dual-mode）** 指 CPU 至少提供两种执行模式——**用户态（user mode）** 与 **内核态（kernel mode，又称管态/特权态/supervisor mode）**——用户程序跑在受限的用户态，只有 OS 内核跑在权力最大的内核态。这是硬件为操作系统提供的**保护（protection）** 基石。

动机很直白，OS 要当可信的资源管理器，就必须防止一个出错或恶意的用户程序做出危险动作——直接关中断、改页表、随意读写别人的内存、独占 CPU 不放。如果所有程序都能执行任意指令，那任何一个程序崩了都可能拖垮整台机器，隔离和公平都无从谈起。于是硬件规定：一部分「危险」指令只有在内核态才能执行，用户态执行它们会被硬件拦下并报错。用户程序想做需要特权的事（读文件、分配内存），只能**请内核代劳**——这就引出了 1.4 的系统调用。可以把内核态想成「管理员权限」，用户态想成「访客权限」：访客能干正常的活，但改系统设置必须去求管理员。

### 1.2.2 模式位：硬件用一个状态区分当前处于哪种模式

教材层面，CPU 用一个**模式位（mode bit）** 记录当前处于用户态还是内核态；硬件在执行每条指令前检查这一位，决定该指令是否被允许。Silberschatz 就是用「mode bit」这个抽象来讲：值为 0 表示内核态、1 表示用户态（具体取值是教学约定，不同机器不同）。

关键点在于**这一位只能由硬件在受控时机改写**，用户程序不能自己「把自己升级成内核态」——否则保护就形同虚设。合法的升权只发生在陷入内核的那一刻：发生中断、异常或执行系统调用指令时，硬件自动把模式切到内核态并跳到内核预设的入口；内核处理完、返回用户程序时再切回用户态。所以用户代码永远无法在自己选定的地址上以内核态运行，这正是保护的要害。初学者容易误以为「模式切换是软件说了算」，其实是**硬件机制**在把关，软件只能触发预定义的、单向受控的入口。

### 1.2.3 x86 的四个 ring 与实际只用两层

在具体的 x86/x86-64 硬件上，特权不是一位而是四个**保护环（protection rings）**：ring 0 权限最高、ring 3 最低，中间还有 ring 1、ring 2。当前特权级叫 **CPL（Current Privilege Level）**，由代码段寄存器 CS 的低 2 位表示。

现实中主流 OS（Linux、Windows）**只用 ring 0 和 ring 3**：内核跑在 ring 0，用户程序跑在 ring 3，ring 1/2 基本闲置。原因是可移植性与简单性——不是所有架构都有 4 层（很多只有 2 层），只用两层最通用；历史上有系统试过用 ring 1/2 放驱动，但收益不抵复杂度。所以「双模式（教材的用户/内核）」与「x86 四 ring」并不矛盾：双模式是抽象的两级，x86 的四 ring 是一种更细的硬件实现，OS 只挑了其中两级用。引入虚拟化后，硬件又加了一层「ring -1」式的 VMX root 模式给 hypervisor（归 OS-15），本篇不展开。

需要给初学者点明一个易混点：教材说的「mode bit（一位）」和 x86 的「CPL（两位、四级）」是同一件事的不同粒度——规范与实现分账。Silberschatz 讲抽象的一位模式，Intel SDM 讲具体的四环 CPL；写代码判断「现在是不是内核态」时，x86 上看的是 CS 的 CPL 而非某个字面的「mode bit」。

### 1.2.4 特权指令与受保护操作：越权即被硬件拦截

**特权指令（privileged instructions）** 是只允许在内核态（ring 0）执行的指令，典型如关/开中断、加载页表基址寄存器、切换处理器状态、直接访问 I/O 端口等。用户态执行特权指令会触发一个**保护异常**（x86 上是 #GP，通用保护错误 General Protection Fault），内核捕获后通常给该进程发信号并杀掉它。

本机可直接演示这条边界。下面的 C 程序在用户态执行 `cli`（清中断标志，ring-0 特权指令）：

```c
#include <stdio.h>
int main(void){
    printf("about to run privileged instruction cli in user mode\n");
    __asm__ __volatile__("cli");   /* clear interrupt flag: ring-0 only */
    printf("survived (should NOT print)\n");
    return 0;
}
```

本机（Linux 6.18.5 x86_64，gcc 13.3.0 `-std=c11`，2026-07-26）编译运行，进程被 SIGSEGV 杀死、`survived` 那行永不打印：

```
about to run privileged instruction cli in user mode
Segmentation fault
exit=139   # 139 = 128 + 11(SIGSEGV)
```

这就是保护边界的实体证据——用户态想直接操作硬件中断，硬件立刻用 #GP 把它拦下，内核转成 SIGSEGV 终结进程。初学者要理解这不是「程序有 bug 崩了」，而是**硬件与内核联手在执行保护策略**——正是这种拦截，让恶意或出错的程序无法绕过 OS 直接摆布硬件。（严格说 x86 上用户态 `cli` 是否触发 #GP 还与 IOPL 有关，默认设置下用户态 IOPL=0，故触发，本机结果与之一致。）

### 1.2.5 三类事件触发进入内核态

从用户态进内核态只有三个合法入口，都由硬件在特定事件发生时自动完成模式切换并跳到内核预设的处理程序：**系统调用（system call / trap，程序主动请求内核服务）**、**异常（exception / fault，如缺页、除零、越权，指令执行中出问题）**、**中断（interrupt，外部设备或时钟异步打断）**。

把三者放在一起看能建立完整图景：系统调用是「我主动敲门求内核办事」（同步、自愿）；异常是「我干的这条指令出事了，内核来收拾」（同步、被动）；中断是「外面有事找内核，跟我当前指令无关」（异步）。这三类事件的详细机制、寄存器如何保存、如何返回，是 OS-03「受限直接执行」的主题；本篇只需记住：**用户态无法随意进内核，只能被这三类事件以硬件受控的方式带进去**，进去后模式位/CPL 变为内核态，返回时再切回。这一约束是 1.2 全部保护逻辑的收口。

## 1.3 内核结构谱系

### 1.3.1 宏内核：所有服务挤在一个内核地址空间里

**宏内核（monolithic kernel，单体内核）** 把操作系统的绝大部分功能——进程调度、内存管理、文件系统、设备驱动、网络协议栈——全部编译进一个大程序，运行在同一个内核地址空间、同一个内核态里，彼此之间是普通的函数调用。Linux、传统 Unix、BSD 都是宏内核。

它的好处是**快**：各子系统在同一地址空间里直接调用，没有跨模块的消息传递和模式切换开销，性能高。代价是**弱隔离与大 TCB（可信计算基）**：任何一个内核组件（哪怕一个第三方驱动）出错，都可能破坏整个内核、拖垮系统，因为大家共享内存、无边界。初学者可以类比成「开放式大办公室」：所有部门在一个大房间里，沟通极快（喊一声就行），但一处失火、烟就灌满全屋。「宏（monolithic）」强调的正是「铁板一块、一个地址空间」，而不是「代码量大」。

### 1.3.2 微内核：内核只留最小核心，服务搬到用户态

**微内核（microkernel）** 走相反路线：内核里只保留最基本、最必须的机制——通常是地址空间管理、线程调度、以及进程间通信（IPC）——把文件系统、设备驱动、网络栈等服务统统移到**用户态**，作为一个个独立的服务进程运行。应用要用文件系统，就通过内核的 IPC 给「文件系统服务进程」发消息。代表有 Mach、MINIX 3、QNX，以及经过形式化验证的 **seL4**。

它的好处是**强隔离与可靠性**：一个驱动崩了只是那个用户态服务进程挂掉，可以重启，不会连累内核；TCB 小到可以被形式化验证（seL4 就做到了）。代价是**慢**：一次原本内核内的函数调用，现在要变成「用户态→内核 IPC→另一个用户态服务→再 IPC 回来」，多次模式切换和消息拷贝，性能损耗明显——这是历史上微内核落地的主要障碍（早期 Mach 因此被诟病）。类比是「把各部门拆成独立小办公室，靠发邮件沟通」：一间失火烧不到别间（隔离好），但凡事发邮件比喊一声慢（性能差）。

### 1.3.3 混合与模块化：Linux 是宏内核 + 可加载模块

现实中的主流系统多是**混合（hybrid）** 或**模块化（modular）** 折中。Linux 本质是**宏内核，但支持可加载内核模块（LKM, Loadable Kernel Modules）**：核心仍是单体的，但驱动、文件系统等可以在运行时以 `.ko` 模块的形式动态加载/卸载进内核，无需重编译整个内核。注意——模块加载进来后仍运行在内核态、内核地址空间里，享受宏内核的性能，只是获得了「按需装配」的灵活性，并**不**因此变成微内核（模块没有被隔离到用户态）。Windows NT、macOS 的 XNU（Mach 微内核骨架 + BSD 宏内核成分）则常被称作 hybrid，把两类结构的元素混在一起。

本机原计划用 `lsmod` / `cat /proc/modules` 展示「模块化宏内核」，但本机（Linux 6.18.5 容器）**未提供 `/proc/modules`、`/lib/modules/` 也不存在**（2026-07-26 实测报 `No such file or directory`），说明此内核构建为无可加载模块支持（模块全部内建，`CONFIG_MODULES` 关闭或裁剪）的形态——这本身是宏内核「可静态全内建、也可支持动态模块」两种配置的一个真实样本。此项实证在本机**未取**，如实标注；不影响 Linux 支持 LKM 这一多来源确认的结论。

### 1.3.4 结构之争：Tanenbaum–Torvalds 论战与工程折中

内核结构的取舍有一场著名公案：1992 年 Andrew Tanenbaum（MINIX 微内核作者）在 Usenet 上发帖「LINUX is obsolete」，主张微内核才是正确设计、单体内核已过时；Linus Torvalds 反驳称宏内核在工程上更实际、性能更好。这场辩论没有「谁赢」的定论，但历史给出的答案是：**Linux（宏内核）在通用桌面/服务器领域大获成功，而微内核在高可靠、安全关键领域（航空、汽车 QNX、形式化验证 seL4）站稳脚跟**——结构选择本质是「性能 vs 隔离/可靠性」的权衡，因目标场景而异，没有普适最优。

这里给初学者一个收束，不要背「宏内核好还是微内核好」，而要理解那条权衡轴——把所有服务塞进一个特权地址空间换来速度但牺牲隔离，拆到用户态换来隔离但牺牲速度，Linux 用「宏内核 + 模块」在这条轴上取了个偏性能的折中点。三本经典教材（OSTEP 较少专门展开结构分类，Silberschatz/Tanenbaum 各有专节）在「宏 vs 微 + 混合折中 + Linux 属宏内核带模块」这一框架上一致。

#### 来源与时效
- Tanenbaum《Modern Operating Systems》4th ed. §1.7「Operating System Structure」：单体（monolithic）、微内核（microkernel）、客户端-服务器模型、模块——结构分类主锚点；作者本人即微内核阵营，观点需与 Torvalds 侧对照。
- Silberschatz《Operating System Concepts》10th ed. §2.8「Operating-System Structure」+ Ch20「The Linux System」：monolithic/microkernel/modular/hybrid 定义、Linux 为宏内核 + 可加载模块、macOS/Windows 为 hybrid。
- Linux 内核文档（kernel.org, `Documentation/`，2024–2025）+ `module`/`insmod`/`lsmod` man：LKM 机制、模块运行于内核态。

## 1.4 系统调用作为受保护接口

### 1.4.1 系统调用：穿越保护边界的唯一受控入口

**系统调用（system call, syscall）** 是用户态程序请求内核代其执行特权操作的受控接口。由于 1.2 已确立「用户态不能直接碰硬件、不能自行进内核态」，那么进程要读文件、分配内存、创建子进程、收发网络包——凡是需要特权的事——**唯一合法的途径就是发起系统调用**，让内核在内核态里替它完成，再把结果交回来。

这是理解 OS 保护模型的关键收口：内核就像一座只有一道旋转门的堡垒，系统调用就是那道门。用户程序不能翻墙（翻墙 = 执行特权指令，会被 #GP 拦下，见 1.2.4），只能走这道门、按内核规定的手续（放好参数、给出调用号、执行陷入指令）递交请求。门内内核会**检查参数合法性**（比如你传的指针是不是指向你自己地址空间、你有没有权限打开这个文件），合法才办——这道检查正是保护得以成立的地方。初学者要抓住「受控」二字：系统调用不是「用户想跳哪就跳哪进内核」，而是只能跳到内核预先登记好的、编好号的那几百个入口之一，且带全套检查。

### 1.4.2 API、系统调用、库函数包装的三层关系

日常编程里你几乎从不直接写系统调用，而是调用**库函数**（如 C 标准库 glibc 的 `printf`、`fopen`、`malloc`），这些库函数在内部才去发系统调用。这里要分清三层：程序员面对的是**API**（如 POSIX 定义的 `open`/`read`），glibc 提供符合该 API 的**包装函数（wrapper）**，wrapper 内部按 ABI 约定发起真正的**系统调用**（如 `openat`、`read`、`write`）。

举一个初学者常踩的坑，`printf` 不是系统调用，`write` 才是；`printf` 会先在用户态的缓冲区里格式化、攒够一批，再调用一次 `write` 系统调用把数据交给内核——所以系统调用次数远少于你写的 `printf` 次数，因为陷入内核有成本（模式切换、检查），能少陷就少陷。同理 `malloc` 多数时候只是在用户态的堆里切一块已向内核要来的内存，只有堆不够时才发 `brk`/`mmap` 系统调用（归 OS-08）。分清这三层能避免「以为每个库函数都是一次进内核」的误解。glibc wrapper 有时并不与内核系统调用一一对应（如 `fork` 底层是 `clone`，`exit` 底层是 `exit_group`），这属规范（POSIX API）与实现（Linux 系统调用）分账。

### 1.4.3 陷入机制：库函数如何真正跨进内核

发起系统调用的动作在硬件层面是一次**陷入（trap）**：用户程序把系统调用号放进约定的寄存器（x86-64 上放 `rax`）、参数放进约定寄存器（`rdi`、`rsi`、`rdx`…），然后执行专门的陷入指令（x86-64 上是 `syscall` 指令），CPU 随即切到内核态、跳到内核登记的统一入口，内核按号分派到对应的处理函数，完成后把返回值放回 `rax`、执行返回指令切回用户态。

本篇只需建立这个「放号→放参→陷入→分派→返回」的骨架，寄存器级细节与 x86-64 System V 约定归 OS-03。本机可用 `strace` 直观看到用户程序运行时向内核发起的系统调用序列。对 `/bin/true` 这个「什么都不做就退出」的极简程序，strace 也抓到一长串系统调用（Linux 6.18.5，2026-07-26）：

```
execve("/bin/true", ...)                = 0
brk(NULL)                               = 0x55a5d1f5f000
mmap(NULL, 8192, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = ...
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
read(3, "\177ELF\2\1\1\3..."..., 832)   = 832
mmap(...) mprotect(...) close(3) ...
```

这串输出正是「用户态每需要一次特权服务，就陷入内核一次」的实体证据：连「什么都不做的程序」也得靠内核帮它把自己（`execve`）装载起来、把 libc 映射进地址空间（`openat`+`mmap`）——可见程序离开内核寸步难行。顺带可见 `/proc/self/maps` 里有 `[vdso]` 段：Linux 把 `gettimeofday` 等极高频、只读、无需真进内核的调用做成 vDSO 映射到用户态直接跑，省掉陷入开销——这是系统调用机制的一个现代优化（细节归 OS-03）。

### 1.4.4 ABI 稳定契约：系统调用是长期不变的承诺

系统调用接口是一份**ABI（Application Binary Interface）稳定契约**：给定架构上，系统调用号、参数寄存器约定、数据结构布局一旦发布就长期不变，这样早年编译的二进制程序在新内核上仍能运行。Linux 尤其以此著称——Linus Torvalds 反复强调的第一铁律是 **"we do not break userspace"（绝不破坏用户态）**：内核内部随便重构，但对用户态暴露的系统调用 ABI 不能改坏，否则视为内核 bug。

这解释了「接口 vs 实现分账」为什么在 OS 里这么重要，也给初学者一个反直觉但关键的认识：**内核可以天翻地覆地改内部实现（调度器从 CFS 换成 EEVDF、文件系统换代），但只要系统调用这层契约不动，你十年前编译的程序照样能跑。** ABI 与 API 的区别值得点明——API 是源代码级契约（函数名、参数类型，重编译即可适配），ABI 是二进制级契约（寄存器、字节布局、调用号，不重编译也要兼容）。系统调用属于 ABI 层，正因为它是二进制级的稳定承诺，才撑得起整个软件生态的向后兼容。这份「稳定接口」是 OS 作为资源管理器对上层世界立下的、最重要的一条公共协议，也是本篇 1.1–1.4 逻辑链条的终点：OS 用双模式（1.2）划出保护边界，用内核（1.3）实现服务，最后用系统调用（1.4）这道稳定的受控门，把资源虚拟化（1.1）的能力安全地交付给每一个用户程序。
