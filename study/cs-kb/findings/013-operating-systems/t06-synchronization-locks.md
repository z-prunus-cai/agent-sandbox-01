## 6.1 锁的接口与目标

### 6.1.1 lock / unlock 接口与临界区

锁（lock）是一个只有两个基本操作的对象：`lock()`（获取/上锁）与 `unlock()`（释放/开锁）。程序员用一对 `lock()`…`unlock()` 把一段访问共享数据的代码包起来，这段被包住的代码就叫**临界区**（critical section）。锁保证：任一时刻最多只有一个线程"持有"这把锁并处在它保护的临界区里，其余想进的线程必须等到持有者 `unlock()` 之后才能进。

最小接口大致如下（POSIX pthread 的对应命名并列）：

```
lock(&L)   →  pthread_mutex_lock(&m)     // 获取；若已被占则等待
unlock(&L) →  pthread_mutex_unlock(&m)   // 释放；放行一个等待者
```

初学者要抓住的直觉是：锁本身不是数据的"保险柜"，它不物理阻止别人访问那块内存——它只是一个所有线程都自愿遵守的**约定**，即"只有先拿到这把锁的人才动这块数据"。OSTEP Ch28 把这点讲得很直白：锁把本来由调度器随意穿插（interleaving）的并发执行，重新拿回程序员手里，让程序员能规定"这一段不许被打断地插进别人"。锁保护的是**代码段所访问的数据**，不是"某个变量"本身——同一份数据被多处访问时，必须用**同一把**锁把这些地方都罩住，才谈得上互斥。

### 6.1.2 三个评价目标：正确性 / 公平 / 性能

OSTEP Ch28 给出评价一把锁"好不好"的三条标准，本报告的机制主线都是在这三者间权衡：

```
1) 正确性（mutual exclusion）：是否真的做到"临界区内至多一个线程"。
2) 公平性（fairness）：等待的线程是否都有机会拿到锁，会不会有人被饿死（starve）。
3) 性能（performance）：加锁/解锁本身的开销，尤其是无争用、单核争用、多核争用三种场景下的代价。
```

正确性是底线：做不到互斥，这把"锁"就根本不是锁。公平性问的是"排队公不公平"——例如简单的 test-and-set 自旋锁不保证先来先得，某个倒霉线程可能反复抢不到而饿死；而票号锁（ticket lock）之类用排号保证了先来先服务。性能则要分场景看：一把锁在完全没人争的情况下开销要极低（这正是 futex 的设计动机，见 6.4），在多核激烈争用下又不能让 CPU 之间的缓存来回失效拖垮整机（这归 CP-08 深挖）。

一个常见误解是"锁越强越好"。恰恰相反：正确性必须满足，但公平和性能往往互相拉扯——保证严格公平的排队锁在低争用时反而比"谁抢到算谁"的锁慢。所以现实中的锁（如 glibc 的 `pthread_mutex`）是针对常见负载做过大量折中的工程产物，而非某个理论最优。

### 6.1.3 与正确性证明的分账

"这把锁到底对不对"若要**形式化地证明**（互斥性、无死锁、无饥饿的精确定义与两/N 线程算法如 Peterson、bakery 的正确性论证），属于 L4-05 CP-01「互斥问题与理论」的主场，本课不展开。本课只从工程角度用"三目标"作为衡量尺，并在后续各节讲清每种机制在这三目标上落在哪。

## 6.2 硬件原语造锁

### 6.2.1 为什么纯软件不够：需要一条原子指令

要实现 `lock()`，最朴素的想法是设一个标志 `flag`：进临界区前看它是不是 0，是 0 就置 1 进去、不是就等。问题是"看它是不是 0"和"把它置 1"是**两条**指令，两个线程可能都先读到 0、都以为没人、都置 1 进临界区——互斥当场破功。根因是"读—判断—写"这三步之间可能被调度器插入别的线程。

解决办法只能来自硬件：提供一条**原子的读—改—写**（read-modify-write, RMW）指令，把"读旧值 + 写新值"合并成一个不可被打断、在多核上也串行化的单一操作。OSTEP Ch28 明确指出，纯软件方案（Peterson 等）虽在理论上可行，但依赖对内存访问顺序的假设、且不实用，现代锁一律建立在硬件原子指令之上。

### 6.2.2 Test-And-Set (TAS) 与自旋锁

最经典的硬件原语是 **test-and-set**（测试并设置）：原子地"把某内存字设为新值，同时返回它的旧值"。它的语义等价于下面这段"假装一步完成"的伪代码：

```
int TestAndSet(int *ptr, int new) {
    int old = *ptr;   // 取旧值
    *ptr = new;       // 写新值
    return old;       // 返回旧值 —— 整个过程原子完成
}
```

用它造一把最简单的**自旋锁**（spinlock）：

```
void lock(lock_t *L)   { while (TestAndSet(&L->flag, 1) == 1) ; /* 空转自旋 */ }
void unlock(lock_t *L) { L->flag = 0; }
```

理解要点：`lock()` 里的 `while` 会一直原子地"设 1 并看旧值"。若旧值是 1，说明锁已被别人持有（我刚把它设成 1 其实没改变什么），继续转；若旧值是 0，说明我是第一个把它从 0 翻成 1 的线程，`TestAndSet` 返回 0、循环退出、我拿到了锁。这把锁正确（互斥成立），但**不公平**（不保证先来先得，可能有人一直抢不到）且**在单核上很糟**——持锁者被切走后，自旋者会白白空转整个时间片才轮到持锁者继续（呼应 6.6.1）。自旋锁只在"临界区极短且运行在多核、持锁者在另一个核上很快会释放"时才划算。

### 6.2.3 Compare-And-Swap (CAS)

另一条更通用的原语是 **compare-and-swap**（比较并交换，x86 上是 `cmpxchg` 指令）：原子地"若某内存字当前等于期望值 expected，就把它改成新值 desired；返回它的原值（或是否成功）"。语义伪代码：

```
int CompareAndSwap(int *ptr, int expected, int desired) {
    int actual = *ptr;
    if (actual == expected) *ptr = desired;
    return actual;               // 整个过程原子完成
}
```

CAS 造自旋锁只需把 `lock()` 写成 `while (CompareAndSwap(&L->flag, 0, 1) != 0) ;`——"当且仅当当前是 0 时把它设成 1"。CAS 比 TAS 强大得多：它是构建**无锁**数据结构的核心积木（"读出旧值→算出新值→CAS 写回，失败就重试"这套 retry loop 是无锁编程的基本骨架）。CAS 的这种"万能性"（consensus number = ∞）与无锁结构、ABA 问题归 L4-05 CP-04/CP-10，本课只把它当作造锁的原子砖块。

### 6.2.4 关中断构建单处理器锁（xv6 的做法）

在**单处理器**上还有一条更省的路子：既然并发只来自"中断（尤其时钟中断）打断当前执行流去跑别的线程"，那进临界区前**关中断**、出来再开，就没人能插进来。xv6 的自旋锁正是这样：它在获取锁时调用 `push_off()` 关中断，释放时 `pop_off()` 恢复，`push_off/pop_off` 还做**嵌套计数**（持有多把锁时，只有最外层那次 `pop_off` 才真正重新开中断）。

要分清两点。其一，关中断**只在单核上够用**：多核上另一个 CPU 上的线程照样能同时进临界区，所以 xv6 的自旋锁是"关中断 + 一条原子指令（riscv 的 `amoswap`，等价于 TAS）"两者叠加——关中断防的是本核被中断抢占，原子指令防的是别的核。其二，关中断是**特权操作**，只有内核能做，用户态程序造锁不能靠它（用户态走 futex，见 6.4）。xv6 关中断还有一层用意：持有自旋锁期间禁止本核被切走，否则持锁者睡着而自旋者在同核上空转会**死锁**——所以 xv6 规定"持自旋锁时不得睡眠"。

（本节 xv6 结论来自 6.1810 讲义与 xv6 教材文字，本机未取源码副本，未逐行读 `spinlock.c`，如实标注。）

### 6.2.5 x86 `LOCK` 前缀：原子性的物理来源

在 x86-64 上，上述"原子 RMW"落到机器码，是靠给指令加一个 **`LOCK` 前缀**（机器码字节 `f0`）实现的：带 `LOCK` 前缀的读—改—写指令在执行期间锁住相应缓存行（或总线），保证该操作对其他核不可分割。本机实证——把 C11 `atomic_fetch_add` 和 `atomic_compare_exchange_strong` 编成机器码看前缀（gcc 13.3.0 `-O2 -std=c11`，objdump 2.42 @2026-07-29）：

```
lock addl   $0x1,0x0(%rip)     # atomic_fetch_add(&c,1)  —— 前缀字节 f0
lock cmpxchg %edx,(%rdi)       # compare_exchange_strong —— CAS 落地为 lock cmpxchg
```

这就把抽象的"原子性"钉在了实处：一次 `atomic_fetch_add` 之所以不会丢更新，正是因为它生成了带 `lock` 前缀的 `addl`；一次 CAS 之所以原子，是因为它是 `lock cmpxchg`。没有 `lock` 前缀的普通 `add`/`cmpxchg` 在多核上就**不**保证原子，会退回 6.2.1 的丢更新问题。至于这些指令在内存序上还建立了什么"边"（happens-before）、`mfence` 从哪来，归 CP-05/06，本课只认"`LOCK` 前缀 = 原子 RMW 的来源"。

### 6.2.6 自旋等待 vs 睡眠等待

有了原子原语，等待方式有两条路：**自旋**（spin，忙等，反复试直到拿到）和**睡眠**（sleep/block，主动让出 CPU、把自己挂到锁的等待队列，被唤醒再跑）。选择取决于"预计要等多久"与"等待期间 CPU 能不能干别的"：临界区极短、多核、马上能拿到 → 自旋（省下两次上下文切换）；临界区长、或单核、或等待者众多 → 睡眠（别霸占 CPU）。真实系统常用**混合**策略：先自旋一小会（乐观等待，赌马上能拿到），超过阈值还没拿到再睡眠——这正是 6.4 futex 与 glibc 自适应互斥锁的思路。xv6 因此把锁分成两类：短临界区用 `spinlock`（关中断+自旋，不许睡），可能长时间持有的用 `sleeplock`（其内部再用一把 spinlock 保护状态，等待时真睡眠）。

## 6.3 条件变量与信号量

### 6.3.1 条件变量：等待"一个条件成真"

光有互斥锁还不够表达一类常见需求："我要等到某个条件成立才继续"——例如消费者要等缓冲区里**有**数据。忙等（`while (!ready) ;`）既浪费 CPU 又易错。**条件变量**（condition variable, CV）就是为此而生：它是一个可以让线程在其上**睡眠等待**、并由别的线程**唤醒**的队列，总是与一把互斥锁配对使用。POSIX 三个核心操作：

```
pthread_cond_wait(&cv, &mutex);   // 原子地：释放 mutex + 让自己睡到 cv 队列上
pthread_cond_signal(&cv);         // 唤醒 cv 队列上的一个等待者
pthread_cond_broadcast(&cv);      // 唤醒 cv 队列上的全部等待者
```

### 6.3.2 wait 为什么必须"原子地释放锁并睡眠"

`pthread_cond_wait` 有一个初学者极易忽视、却是整个机制成立关键的语义：它在把调用线程挂起之前，会**先原子地释放传入的那把互斥锁**；等被唤醒、从 `wait` 返回之前，又会**重新获取**那把锁。

为什么必须原子？设想若"释放锁"和"睡到 cv 上"是分开两步：线程释放了锁、但还没睡下去时，恰好被切走，另一个线程改了条件并 `signal`——这次 `signal` 打在空队列上、丢失了；等原线程回来睡下，就再也等不到唤醒，永久卡死（这叫"lost wakeup"，唤醒丢失）。把"放锁+睡眠"合成一个原子步骤，就堵住了这个缝。这也解释了为什么 `wait` 必须在持有锁的情况下调用：它要靠这把锁来保护"检查条件"和"决定睡眠"之间不被插入。

### 6.3.3 唤醒后必须用 `while` 重检谓词

使用条件变量的铁律是：等待条件要写成 `while` 循环重检，而**不是** `if`：

```
pthread_mutex_lock(&m);
while (!condition)            // 必须 while，不能 if
    pthread_cond_wait(&cv, &m);
/* 此处 condition 一定成立，且持有 m */
pthread_mutex_unlock(&m);
```

原因有二：其一，POSIX 允许**虚假唤醒**（spurious wakeup）——`wait` 可能在没有任何 `signal` 的情况下自己返回；其二，即便是真 `signal`，从被唤醒到重新拿到锁之间，条件可能已被另一个抢先线程改回不满足（Mesa 语义：`signal` 只是"提示条件也许成立"，不移交锁的即时控制）。用 `while` 在返回后再查一遍谓词，两种情况都被兜住。此处点到为止——虚假唤醒的纪律、Mesa vs Hoare 语义、生产者-消费者/读者-写者的完整正确性归 L4-05 CP-09，本课只说明"CV 是内核/库提供的睡眠等待原语、用法上必须 `while` 重检"。

### 6.3.4 信号量：一个带计数的同步原语

**信号量**（semaphore，Dijkstra 提出）是一个内部维护**整数计数**的对象，两个原子操作：

```
wait(S) / P(S) / sem_wait:  计数减 1；若结果为负，则调用者阻塞睡眠
post(S) / V(S) / sem_post:  计数加 1；若有等待者，唤醒其中一个
```

OSTEP Ch31 给出一个好用的心智口诀：信号量的当前计数若为负，其绝对值等于**正在等待的线程数**；若为正，等于**还可无阻塞通过的线程数**（可用许可数）。初始值决定了它的用途。

### 6.3.5 信号量表达互斥与排序

信号量能同时表达两类同步。作**互斥锁**用：初值设 1（二元信号量），`wait` 进临界区、`post` 出临界区，同一时刻至多一个线程通过。作**排序/条件同步**用：初值设 0，让"必须后发生"的线程先 `wait`（计数变 -1 阻塞），"先发生"的事件完成后 `post`（放行）——例如父线程 `wait` 等子线程 `post`，实现"等子线程干完某事"。作**有限资源计数**用：初值设 N（如缓冲槽位数），每占一个 `wait`、每放一个 `post`，天然限流。

信号量比条件变量"更原始"的地方在于它自带计数，`post` 不会丢失（计数记着），不像 CV 的 `signal` 打在空队列会丢；但也正因它把"锁"和"条件"揉进一个计数里，复杂场景下更难推理，工程上生产者-消费者这类问题两者都能写。它们可以互相实现：CV+锁能实现信号量，信号量也能实现锁与近似的条件等待。

## 6.4 futex

### 6.4.1 动机：无争用时不该进内核

早期的用户态锁若每次 `lock/unlock` 都做系统调用进内核排队，代价高得离谱——因为**绝大多数加锁其实没人跟你争**（拿了就走）。Linux 的 **futex**（fast userspace mutex，快速用户态互斥）就是为消除这笔冤枉钱设计的：把锁的状态放在用户态的一个整数里，**无争用时全程在用户态用一条原子指令搞定、根本不进内核**；只有当真的争不到、需要睡眠或需要唤醒别人时，才用 `futex()` 系统调用落进内核。`futex(2)` man page 的原话是：同步操作的大多数在用户空间完成，程序仅在"很可能需要阻塞较长时间"时才调用 `futex()`。

### 6.4.2 `FUTEX_WAIT` / `FUTEX_WAKE` 的内核语义

futex 的核心是两个操作，其中 `FUTEX_WAIT` 的一个细节是整套机制无竞态的关键：

```
futex(uaddr, FUTEX_WAIT, val, timeout, ...)
    // 原子地：加载 *uaddr、与期望值 val 比较，
    // 仅当 *uaddr == val 时才睡眠阻塞；若不等立即返回(EAGAIN)。

futex(uaddr, FUTEX_WAKE, nr, ...)
    // 唤醒至多 nr 个正在此 uaddr 上等待的线程（nr 常为 1，或 INT_MAX 表全唤醒）。
```

`FUTEX_WAIT` 的原子比较-再-睡是防"唤醒丢失"的关键。man page 明确写道："futex 字值的加载、与期望值的比较、以及实际的阻塞，会原子地发生。"设想没有这个原子比较：线程 A 在用户态看到锁被占、决定睡，但在真正 `FUTEX_WAIT` 系统调用陷入内核之前被切走，持锁者 B 此时释放锁并 `FUTEX_WAKE`——这次唤醒打空、丢失；A 回来后一头睡死。有了"内核里再比较一次 `*uaddr == val`"：若 B 已经把锁状态字改了（`*uaddr != val`），A 的 `FUTEX_WAIT` 立即返回 `EAGAIN` 而不睡，缝被堵死。

### 6.4.3 快路径 / 慢路径（本机实证）

一把 futex 互斥锁的典型两条路径：

```
lock():   用户态 CAS 把 state 0→1 成功  →  拿到锁，直接返回，不进内核（快路径）
          CAS 失败（已被占）           →  改状态标记有等待者，futex(FUTEX_WAIT) 陷内核睡眠（慢路径）
unlock(): 用户态把 state 置 0
          若有等待者                    →  futex(FUTEX_WAKE, 1) 陷内核唤醒一个（慢路径）
```

本机实证——`pthread_mutex` 在两线程激烈争用下会走到慢路径，`strace -f` 抓到内核 `futex` 调用（Linux 6.18.5 @2026-07-29）：

```
futex(0x5641..., FUTEX_WAIT_PRIVATE, 2, NULL)  = 0   // 争不到→内核睡眠
futex(0x5641..., FUTEX_WAKE_PRIVATE, 1)        = 1   // 释放→唤醒一个等待者
```

要读懂两点。其一，反复出现的正是 `FUTEX_WAIT`（争不到就睡）与 `FUTEX_WAKE`（释放就唤醒一个）成对出现，印证了慢路径模型。其二，若把程序改成完全无争用（单线程反复 lock/unlock），`strace` 里几乎**看不到** `futex` 调用——这正是快路径全程留在用户态的直接证据。可见 futex 之所以快，不是因为它的系统调用快，而是因为常见情况下**根本不发生系统调用**。

### 6.4.4 `FUTEX_PRIVATE_FLAG` 与对齐要求

实证里的 `FUTEX_WAIT_PRIVATE` 带的 `_PRIVATE` 来自 **`FUTEX_PRIVATE_FLAG`**：它告诉内核这个 futex 只在**同一进程内的线程间**用、不跨进程共享，于是内核可省掉一些跨进程地址换算，走更快的内部路径。glibc 的进程内 `pthread_mutex` 默认就用私有 futex，所以 strace 里看到的是 `*_PRIVATE`。另一条硬性约束：man page 规定 **futex 字是 4 字节整数，必须 4 字节对齐**，即便在 64 位系统上也是 4 字节——这点不凭记忆、以 `futex(2)` 为准。至于 `FUTEX_WAIT_BITSET` 等更细的 op（strace 里也出现过，用于带超时/位掩码的等待），以及 futex2 新接口的演进，属实现细节，本报告不逐一展开，用到的具体 op 语义**以 `futex(2)` man page 当日版本为准**。

## 6.5 RCU

### 6.5.1 读多写少的问题：连读锁都嫌贵

对**读远多于写**的共享数据（如内核里的路由表、设备链表），即便用读写锁，读侧也要对锁的计数做原子加减——在多核上这仍会造成缓存行来回失效、扩展性差。**RCU**（Read-Copy-Update，读-复制-更新）针对这种场景把读侧的同步开销压到近乎为零：读者**不加锁、不用原子指令、不等待、不阻塞**地直接读，代价全部转移给写者去承担。

### 6.5.2 无锁的读侧临界区

读者用一对轻量标记划出读侧临界区：

```
rcu_read_lock();
   p = rcu_dereference(shared_ptr);   // 安全地取出被 RCU 保护的指针
   ... 使用 *p ...                    // 读期间保证 p 指向的旧版本不被释放
rcu_read_unlock();
```

这里最反直觉的一点是，`rcu_read_lock()`/`rcu_read_unlock()` 并**不是锁**——它们不排斥任何人，多个读者、乃至读者与写者可以同时在临界区里跑。内核文档原文说 RCU 让"读者使用轻得多的同步，某些情况下甚至完全不需要同步"。在经典（非抢占）内核实现里，`rcu_read_lock()` 实质只是标记"本 CPU 进入了不可被静止（quiescent）的读区间"，开销极小甚至为零。`rcu_dereference` 则负责安全地把被保护指针取出来（含必要的依赖序保证），供读者解引用。

### 6.5.3 发布-订阅：写者如何安全地换新版本

写者不"就地改"，而是**读旧的、复制一份、在副本上改、再原子地把指针切到新副本**（这正是名字 Read-Copy-Update 的由来）：

```
q = kmalloc(...); *q = *p;           // 复制旧版本
修改 q 的字段;
rcu_assign_pointer(shared_ptr, q);   // 原子发布：新读者从此看到 q，旧读者仍看着 p
... 等待宽限期 ...                    // 见 6.5.4
kfree(p);                            // 确认没有读者还在用 p 后，才释放旧版本
```

`rcu_assign_pointer` 是"发布"动作：它保证在把指针切到 `q` 之前，`q` 指向的内容对将要读它的 CPU 已可见（发布-订阅配对：写者 `rcu_assign_pointer` 发布，读者 `rcu_dereference` 订阅）。发布之后，**新读者看到新版本、已经在读的旧读者仍安全地看着旧版本**——同一时刻允许多个版本并存，这是 RCU 的核心妙处：读写不互斥，靠"多版本 + 延迟回收"而非互相等待来保证安全。

### 6.5.4 宽限期与延迟回收

难点只剩一个：旧版本 `p` 什么时候能安全 `kfree`？答案是——等到**所有在切换指针之前就已进入读侧临界区的读者都退出之后**。这段"等所有先前读者读完"的时间窗口就叫**宽限期**（grace period）。内核提供两条等法：

```
synchronize_rcu();   // 阻塞，直到所有 CPU 上"先前存在的"读侧临界区都结束（宽限期过去），再返回
call_rcu(&p->rcu, cb);  // 不阻塞，登记一个回调，宽限期过后由内核自动调 cb 去释放
```

内核文档给的宽限期定义是：`synchronize_rcu` "阻塞，直到所有 CPU 上先前存在的 RCU 读侧临界区全部完成"。直觉是：写者发布新指针后，任何**新**读者已经看不到旧版本了；只要再等到发布**之前**就已开始读的那批旧读者全部走出临界区，就再没有人能引用旧版本，此时释放它绝对安全。RCU 的整套心智模型因此可归纳为三步——**移除**（发布新指针，切断新读者对旧版本的访问）、**等待**（宽限期，让旧读者读完）、**回收**（安全释放旧版本）。读侧零同步的代价，正是写者要承担这段"等宽限期"的延迟。

### 6.5.5 适用场景与代价

RCU 适合"读极多、写极少、且能容忍读者短时间看到略旧数据"的场景，在 Linux 内核中被大量用于链表、字典、配置等只读遍历热点。它的代价与边界：写侧更复杂更慢（复制+发布+等宽限期）；回收被推迟，宽限期内旧版本占着内存；读者可能读到刚被逻辑删除但尚未回收的旧值（需业务能接受）。RCU 作为**安全内存回收**手段（与 hazard pointer、epoch 并列，回答"无锁结构里何时能安全 free")的算法层讨论归 L4-05 CP-10.5，本课只讲它作为内核同步原语的机制与代价。xv6 没有 RCU，本节完全基于 6.1810 讲义与 Linux 内核文档，无源码腿。

## 6.6 锁的代价

### 6.6.1 让 CPU：自旋 vs 阻塞的代价

用锁不是免费的，第一笔代价就是**等待时 CPU 怎么用**。自旋等待把 CPU 白白烧在空转上：若持锁者被切走，自旋者会耗尽整个时间片却什么都没干（尤其单核上是纯浪费，见 6.2.2）。阻塞等待（让出 CPU、睡眠）省下了空转，但换来**两次上下文切换**（睡下去一次、被唤醒回来一次）的固定开销，还可能带来缓存变冷。所以"让 CPU"本身是权衡：等得短就自旋（省切换）、等得长就睡眠（省 CPU），混合锁先自旋一小会再睡（6.2.6、6.4.3）。这是"性能"目标（6.1.2）在等待策略上的直接体现。

### 6.6.2 优先级倒置与优先级继承

**优先级倒置**（priority inversion）：一个**高**优先级线程 H 因为要的锁被一个**低**优先级线程 L 持有而被迫等待；偏偏此时一个**中**优先级线程 M（不需要这把锁）抢占了 L 去运行——结果 L 迟迟释放不了锁、H 就跟着一直等，出现"中优先级把高优先级堵住"的反常。经典案例是 1997 年火星探路者（Mars Pathfinder）着陆器的反复重启故障，事后定位正是优先级倒置。

标准解法是**优先级继承**（priority inheritance）：当 H 阻塞在 L 持有的锁上时，临时把 L 的优先级**提升到 H 的水平**，让 L 尽快跑完临界区、释放锁，H 就能继续——释放后 L 恢复原优先级。POSIX 通过给互斥锁设 `PTHREAD_PRIO_INHERIT` 协议启用这一机制。另一种解法是**优先级天花板**（priority ceiling）。本课只需理解现象与两种对策名，实时调度细节归调度专题。

### 6.6.3 锁护航（lock convoy）

**锁护航**（lock convoy）：当很多线程频繁争同一把锁、且争不到就睡眠时，会形成一列"护航队"——线程们轮流"睡下→被唤醒→拿锁→很快又释放→下一个被唤醒"，系统的大量时间花在反复的睡眠/唤醒上下文切换上，而不是真正干活，吞吐骤降，即便临界区本身很短。直觉像高速上一个瓶颈处排起长队，车流被迫走走停停。缓解思路包括减小临界区、降低争用（分片锁）、或改用无锁/自适应策略。它与 6.6.1 同源：都是"等待/唤醒的机械开销"盖过了有用工作。

### 6.6.4 持锁被抢占

**持锁被抢占**（preemption while holding a lock）：持锁线程在临界区中途被调度器切走，锁却一直没放——所有等这把锁的线程（尤其自旋者）只能干等到它被重新调度、跑完临界区、释放锁为止。这在单核自旋锁上尤其致命（自旋者和持锁者抢同一个核，持锁者根本没机会跑，见 6.2.4 xv6 为何持自旋锁必须关中断/禁抢占）。内核对此的通用对策就是"持自旋锁期间禁止抢占/关中断"，把临界区变成对本核不可打断；用户态则更倾向睡眠锁 + futex，让被抢占的影响不至于烧 CPU。

### 6.6.5 可扩展性代价的分账

以上是"用锁要付什么代价"的机制层面。锁在多核上**随核数增长的可扩展性代价**——TAS 的缓存行失效风暴、TTAS 改进、MCS/CLH 队列锁、false sharing、NUMA 放置——属于 L4-05 CP-08「自旋锁与竞争」的主场，本课只在此点明其存在，不做专家纵深。核心结论：锁的代价不止"等待时间"，更包括多核缓存一致性协议下"争用本身"制造的通信开销，这往往是并发扩展的真正瓶颈。
