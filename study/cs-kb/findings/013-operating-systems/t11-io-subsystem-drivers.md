## 11.1 设备交互模型：寄存器与两种地址方式

### 11.1.1 设备的规范抽象：状态/命令/数据三类寄存器

从操作系统的角度看，一个硬件设备（磁盘、网卡、串口……）被抽象成**一小组寄存器**，CPU 通过读写这些寄存器与设备打交道。OSTEP Ch36 给出的规范（canonical）设备模型把这些寄存器归成三类：**状态寄存器（status）** 读出来看设备当前忙不忙、上一条命令成没成功；**命令寄存器（command）** 写进去告诉设备"去做某件事"（如"读一个扇区"）；**数据寄存器（data）** 用来在 CPU 与设备之间传一个字/一块数据。设备内部还有 CPU 看不见的固件与机械/电子部件（OSTEP 称之为设备的 internals），但对驱动而言，能碰的只有这几类寄存器构成的**接口（interface）**。

对初学者，最好的类比是"隔着窗口办事"：状态寄存器是窗口上的"忙/闲"牌子，命令寄存器是你递进去的办事单，数据寄存器是收发材料的托盘。你不能直接进屋操作，只能通过这几个口子。理解了这一点，后面所有的 I/O 机制——轮询、中断、DMA——都只是"怎么用好这几个口子、以及谁来盯着忙/闲牌子"的不同答案。

### 11.1.2 规范的程序化 I/O 协议：轮询 + 命令 + 数据传输

OSTEP 给出一段最朴素的、CPU 亲自驱动设备的交互协议（programmed I/O，PIO），它把上面三类寄存器串成一个固定时序：

```
while (STATUS == BUSY)          ; 1) 轮询状态寄存器，等设备空闲
  ;                              （反复读 status，直到 not busy）
write data to DATA register     ; 2) 把要传的数据放进数据寄存器
write command to COMMAND reg    ; 3) 写命令寄存器，启动这次操作
while (STATUS == BUSY)          ; 4) 再轮询，等这次操作完成
  ;
```

这段协议是理解后续一切优化的基线。它的两处"忙等（第 1、4 步的 `while` 轮询）"正是低效的根源：CPU 在原地打转白白烧掉周期，什么也没干成——这就引出 11.2 的中断，把第 4 步的等待换成"设备干完主动通知"。而第 2 步"CPU 亲自把数据一个字一个字写进数据寄存器"在数据量大时同样浪费 CPU，这引出 11.3 的 DMA。换句话说，11.2 和 11.3 分别在优化这段协议的"等"和"搬"。

### 11.1.3 内存映射 I/O（MMIO）vs 端口 I/O（PMIO）

CPU 到底用什么指令去读写那些设备寄存器？有两条路。**端口 I/O（port-mapped I/O，PMIO）** 把设备寄存器放进一个和物理内存**分开的**地址空间——I/O 端口空间，x86 用专门的 `in`/`out` 特权指令按端口号访问（如 `in al, 0x60` 读键盘）。**内存映射 I/O（memory-mapped I/O，MMIO）** 则把设备寄存器映射进**物理内存地址空间**的一段区间，CPU 用普通的 load/store 指令（读写某个物理地址）就能访问它——对这段地址的读写会被总线路由到设备而不是 DRAM。

两者的取舍是初学重点。端口 I/O 需要专用指令、地址空间小（x86 只有 64K 端口）、且这些指令是特权指令只能在内核态发；它是早期设备的历史遗产。MMIO 不需要新指令（load/store 就行）、地址空间和内存一样大、便于用页表权限做保护和用户态映射，是现代设备（尤其 PCIe）的主流。一个关键易错点：MMIO 区域**必须禁用 CPU 缓存并防止编译器/CPU 重排**（否则你写命令寄存器的动作可能被缓存住、或与读状态寄存器乱序），这也是为什么驱动里访问寄存器要用带内存屏障的专用访问器（如 Linux 的 `readl`/`writel`），而不是普通指针解引用。

本机 `/proc/ioports` 直接看到 x86 端口 I/O 空间的经典分配（QEMU 环境 @2026-07-29，节选）：

```
0020-0021 : pic1          ; 中断控制器
0040-0043 : timer0        ; 定时器
0060-0060 : keyboard      ; 键盘控制器
0070-0071 : rtc_cmos      ; 实时钟
03f8-03ff : serial        ; 串口 COM1
```

同一台机器 `/proc/iomem` 看到 MMIO 侧的映射（节选），设备寄存器被摆进物理地址空间的高端：

```
fec00000-fec003ff : IOAPIC 0                    ; 高级中断控制器的 MMIO
4000000000-400007ffff : 0000:00:01.0
    4000000000-400007ffff : virtio-pci-modern    ; virtio 设备的 MMIO 寄存器窗口
```

`00100000-bfffffff : System RAM` 那一段是真正的内存，而 `IOAPIC`/`virtio-pci-modern` 这些不是内存、是被映射进地址空间的设备寄存器——这就是"内存映射"四个字的字面含义。

## 11.2 中断 vs 轮询

### 11.2.1 轮询的代价与中断的思路

**轮询（polling）** 就是 11.1.2 协议里的 `while (STATUS == BUSY)`：CPU 反复读状态寄存器，直到设备就绪。它的代价是**CPU 空转**——在等一块磁盘（毫秒级）或一个网络包时，CPU 本可以跑别的进程，却被钉在原地烧周期。**中断（interrupt）** 反转了这个关系：CPU 发出命令后就去睡（切去跑别的进程），设备干完活时拉高一根中断线通知 CPU；CPU 收到中断后陷入内核、执行该设备的中断处理程序（interrupt handler / ISR），处理完再唤醒等待的进程。

初学者要抓住的直觉是"谁在等、等的时候在干嘛"。轮询是 CPU 主动盯着、盯的时候什么正事都干不了；中断是 CPU 走开去干别的、设备好了来敲门。因此**在长等待场景中，中断能把等待期间的 CPU 让给别的进程，大幅提升利用率**——这正是中断存在的根本理由，也是它与大主题03"受限直接执行"里"时钟中断夺回控制权"同源的机制：都是靠中断把 CPU 从一件事上解放出来。

### 11.2.2 中断并非总是更好：两者的定量权衡

OSTEP 特意强调一个反直觉结论：**中断不总是赢**。中断有固定开销——每次中断都要保存/恢复上下文、陷入内核、跳中断处理程序、可能刷流水线，这套"仪式"本身要花不少周期。如果设备**非常快**（比如数据几乎立刻就绪），那么"发命令→睡→被中断唤醒→上下文切回来"这一圈的开销，可能比"原地轮询几个周期就拿到结果"还大。这时候**轮询反而更快**。

一个更隐蔽的坏情形是**中断风暴（interrupt livelock）**：高速网卡每来一个包就中断一次，包速极高时 CPU 几乎所有时间都在处理中断、进出中断的开销，反而没时间真正处理这些包，系统吞吐不升反降。理解这一点，就能理解为什么需要下面的混合策略：不是"中断 vs 轮询"二选一，而是按负载在两者间切换。

### 11.2.3 混合策略：中断触发、轮询批处理（NAPI 式）

现代高速设备（尤其网卡）用的是**中断 + 轮询的混合**：低负载时用中断（省 CPU、低延迟响应偶发事件）；一旦中断到来，**先关掉该设备的中断，改用轮询在一次内核处理里把已经排队的多个包/请求一次批量处理完**，处理干净后再重新开中断。这样每处理一批只付一次中断开销，把中断风暴摊平成"一次中断带走一批活"。

Linux 网络栈里这套机制叫 **NAPI（New API）**：网卡驱动收到第一个包的中断后，禁用收包中断并把设备挂到一个 poll 列表，由软中断（见 11.5）在 `NET_RX` 上下文里轮询式地批量收包，队列空了再开回中断。本机 `/proc/softirqs` 里的 `NET_RX` 计数（CPU0 上 17342）正是这套批量收包软中断在跑的痕迹。除此之外，还有一种偶尔用的折中——**混合等待（hybrid / adaptive polling）**：先自旋轮询一小段时间，若还不就绪再转为睡眠等中断，兼顾快设备的低延迟与慢设备的省 CPU（Linux 块层的 hybrid polling 即此思路，具体开关随版本变，标「待核」）。

NAPI"关中断转轮询"听起来像退回低效的忙等，其实不是——它只在**已经有活可干（队列非空）** 时轮询，且一次轮询处理一整批，是"批处理换固定开销"，与 11.1.2 那种"设备还没就绪就空转"的忙等有本质区别。

- 锚点：OSTEP Ch36「I/O Devices」§「Lowering CPU overhead with interrupts」与§「The problem with interrupts」（明确"中断不总更好"、livelock、以及 interrupt+polling 混合、coalescing 的讨论）（核实 2026-07-25）；CS162 L17（polling vs interrupt-driven I/O 的代价对比，核实 2026-07-25）；Linux 网络 NAPI 机制（docs.kernel.org networking「NAPI」，核实 2026-07-29）。

## 11.3 DMA：让设备直接搬内存

### 11.3.1 DMA 解决什么问题

即使用了中断解决"等"的问题，11.1.2 协议第 2 步"CPU 亲自把每个字节写进/读出数据寄存器"在大数据量时仍然浪费——搬一块 4KB 的数据要 CPU 执行成千上万条 load/store，这段时间 CPU 就是个昂贵的搬运工，干不了别的。**DMA（Direct Memory Access，直接内存访问）** 引入一个专门的硬件引擎（DMA 控制器/设备自带的 DMA 引擎），让**设备直接读写主存**，整个搬运过程绕开 CPU。

带 DMA 的 I/O 时序变成这样（OSTEP Ch36）：

```
1) CPU 告诉 DMA 引擎：内存缓冲区地址、传输长度、方向（读/写）、目标设备
2) CPU 发出命令后即返回，去调度别的进程运行（不参与搬运）
3) DMA 引擎在设备与主存之间直接搬数据（此时 CPU 在跑别的活）
4) 搬完，DMA 引擎发一个中断通知 CPU："数据已在内存里"
5) CPU 的中断处理程序收尾（如唤醒等待的进程）
```

对比 11.1.2 的纯 PIO：CPU 从"逐字节搬运工"退化成"下单人 + 收货人"，中间几千个周期的搬运彻底交给 DMA。初学者一句话记住：**中断省的是"等"的 CPU，DMA 省的是"搬"的 CPU**，两者常配合使用（DMA 搬完用中断报告）。

### 11.3.2 DMA 涉及的关键概念：物理地址、缓存一致性、IOMMU

DMA 引擎直接访问的是**物理内存**，它不经过 CPU 的 MMU/页表，所以驱动交给 DMA 的必须是**物理地址（或经 IOMMU 翻译的总线地址）**，而不是进程看到的虚拟地址——这是驱动编程里极常见的坑：把虚拟地址直接喂给 DMA 会搬错内存。同理，用于 DMA 的缓冲区在传输期间不能被换出（要 pin 住）、且往往要求物理连续或按设备能力分段（scatter-gather DMA 允许一次 DMA 描述一串不连续的物理块，正好配合分页内存）。

第二个必知点是**缓存一致性（cache coherence）**：DMA 直接改了内存，但 CPU 的缓存里可能还存着这块内存的旧副本；反过来 CPU 写的数据可能还在缓存里没落到内存、DMA 就来读了。所以 DMA 前后需要**缓存刷新/失效**处理（一致性 DMA 或显式 `dma_sync`），否则读到脏数据。第三点，现代系统用 **IOMMU** 给设备做一层"地址翻译 + 访问保护"（类似 CPU 的 MMU 之于进程），既让设备能用连续的"设备虚拟地址"、也防止一个坏/恶意设备用 DMA 乱改任意物理内存（DMA attack 防护）。本机 `/sys/class/iommu` 存在，说明内核编入了 IOMMU 子系统（具体是否为真实硬件 IOMMU 在虚拟环境下意义有限，如实标）。

初学者不必深挖 IOMMU 细节，抓住三句话即可：DMA 用物理地址、DMA 缓冲要 pin 住且注意缓存一致性、IOMMU 给设备加了一层地址翻译与保护。

## 11.4 驱动分层与统一接口

### 11.4.1 为什么要分层：设备无关层 + 设备相关驱动

设备五花八门（每种磁盘、网卡、键盘的寄存器布局与协议都不同），如果让文件系统、网络栈这些上层代码直接对接每种具体设备，会是灾难。操作系统的解法是**分层（layering）与抽象**：上层是**设备无关（device-independent）层**，向应用与内核其余部分暴露一套**统一接口**；下层是**设备相关驱动（device driver）**，把统一接口的操作翻译成对具体设备寄存器的读写。OSTEP Ch36 把这总结为操作系统一贯的手法——用抽象把差异藏在驱动里，让上层"看所有设备都长一个样"。

初学者最熟悉的例子就是 Unix "**一切皆文件**"：应用对磁盘文件、管道、终端、网络设备，用的都是同一套 `open`/`read`/`write`/`close`（用户接口细节归大主题13）。上层不知道底下是 SSD 还是串口，因为设备无关层把它们都包装成了"能 read/write 的对象"，具体差异由各自驱动兜底。分层的代价是"最小公分母"问题：统一接口有时用不上某设备的特殊能力，于是留了 `ioctl` 这种"逃生舱口"传递设备专有命令——这是抽象的常见妥协，初学了解即可。

### 11.4.2 字符设备 vs 块设备

Unix/Linux 把设备大致分两大类。**字符设备（character device）** 按**字节流**访问、通常不可随机寻址、一次一个或一串字符，如键盘、串口、`/dev/null`、终端。**块设备（block device）** 按**固定大小的块（扇区）** 访问、可随机寻址任意块、且经过内核的**缓冲/页缓存**，如磁盘、SSD、U 盘。两者的分界不是绝对的物理属性，而是内核给它们的**访问模型**不同：字符设备走"来一个处理一个"的流式路径，块设备走"按块寻址 + 缓存 + I/O 调度"的路径。

本机 `ls -l /dev` 一眼能分辨两类——**行首 `c` 是字符设备、`b` 是块设备**，紧跟的两个数字是**主设备号,次设备号（major, minor）**：主号选中哪个驱动、次号区分该驱动管的哪个具体设备（@2026-07-29 节选）：

```
crw-rw-rw- 1 root root   1,   3 ... null      ; c=字符设备, major=1  minor=3  (/dev/null)
crw------- 1 root root   1,   1 ... mem       ; c=字符设备, major=1  minor=1
brw------- 1 root root   7,   0 ... loop0     ; b=块设备,   major=7  minor=0  (回环块设备)
brw------- 1 root root   7,   1 ... loop1     ; b=块设备,   major=7  minor=1
```

设备号是"上层如何找到对的驱动"的关键：应用打开 `/dev/loop0` 这个特殊文件，内核看它是块设备、主号 7，就把请求路由到主号 7 注册的驱动、并用次号 0 告诉驱动"是第 0 个 loop 设备"。这就是设备无关层（文件名/设备号）与设备相关驱动（主号注册的具体实现）之间的挂接点。

### 11.4.3 现代设备模型：/dev、/sys 与设备类

现代 Linux 在传统的 `/dev` 节点之上，还有一套 **sysfs（`/sys`）设备模型**，把内核里"总线—设备—驱动—类"的关系导出成目录树，供用户空间（如 udev）查询与管理。其中 `/sys/class/<类名>` 按**功能类别**把设备归类，方便"我要所有网卡 / 所有块设备"这类查询。本机 `/sys/class` 节选：

```
block      ; 所有块设备
net        ; 所有网络接口
tty        ; 终端/串口
input      ; 输入设备
virtio-ports
watchdog
...
```

对初学者，`/dev` 与 `/sys` 的分工可以这样记：`/dev` 是"操作入口"——你 open 它来读写设备；`/sys` 是"信息与配置面板"——你读它来了解设备属性、拓扑、状态，写它来调参数。二者共同构成 Linux 现代设备模型，是"设备无关层"在用户空间的两个投影。

## 11.5 中断下半部：把重活延后做

### 11.5.1 上半部/下半部之分：为什么要拆

中断处理程序（ISR）运行在一个受限的环境里：它常常**关着中断、不能睡眠、必须尽快返回**，否则会拖延甚至丢失其他中断、伤害系统响应。可是很多设备事件"处理起来要花时间"（比如收到网络包后要走一遍协议栈）。矛盾的解法是把中断处理**拆成两半**：**上半部（top half）** 是真正的硬中断处理程序，只做最紧急、最短的事——应答硬件、把数据从设备快速挪走、记下"有活要干"，然后立刻返回并开中断；**下半部（bottom half）** 把耗时的处理**延后**到一个能被打断（甚至能睡眠）的上下文里慢慢做。

上半部像 120 急救电话接线员——只做登记和最紧急调度，几秒内挂断以便接下一个电话；下半部才是真正到场处理的救护车。拆分的目的就是让"接线"这一步足够快、不阻塞后续中断。

### 11.5.2 Linux 的三种下半部机制：softirq / tasklet / workqueue

Linux 提供几种延后执行机制，核心区别在于**运行上下文能否睡眠、以及并发粒度**：

```
softirq   : 软中断。静态编号的一组固定类别，运行在(软)中断上下文，
            不能睡眠；同一类可在多个 CPU 上并行。性能最高、最底层，
            主要给网络/块层等高频路径用，一般驱动不直接写。
tasklet   : 建立在 softirq 之上的动态接口，同一 tasklet 不会并发到多核，
            使用简单；不能睡眠。★已标记 deprecated（见下）。
workqueue : 把活儿交给内核线程执行，运行在【进程上下文】，
            【可以睡眠】、可调用可能阻塞的函数。灵活、适合耗时/可阻塞的活。
```

本机运行内核 6.18.5 的 `/proc/softirqs` 直接列出了当前 softirq 的静态类别（这就是运行内核自证的一手证据，@2026-07-29 节选）：

```
          CPU0     CPU1     CPU2     CPU3
TIMER:   10248     7398     6367     7098     ; 定时器
NET_TX:      5        9        1        1     ; 网络发送
NET_RX:  17342    15433       22       18     ; 网络接收（NAPI 收包，呼应 11.2.3）
BLOCK:      23       82       21    26197     ; 块设备 I/O 完成
TASKLET:    63      177        0        0     ; tasklet 就跑在 TASKLET 这个 softirq 上
RCU:      8784     8829     8676    10441
```

可以看到 `TASKLET` 本身就是一类 softirq——印证了"tasklet 建在 softirq 之上"。选择哪种机制的判据对初学者只需一句：**下半部要不要睡眠/调用可能阻塞的东西？要，就用 workqueue（进程上下文）；不要且追求快，就用 softirq/tasklet（中断上下文、不可睡眠）。**

### 11.5.3 现状与演进：tasklet 弃用、BH workqueue、threaded IRQ ⚙演进快

这一节的机制名与现状**时效敏感**，据 2026-07-29 核实内核官方文档与邮件列表：

- **tasklet 已被标记 deprecated（弃用）**。原因是其 API 有 use-after-free 之类的设计缺陷，且功能可被替代。内核社区正逐步把 tasklet 用户迁走，迁完后计划移除 tasklet。
- 替代品是 **BH workqueue（`WQ_BH` 标志的工作队列）**，自内核 **6.9（2024 年，据 LKML 合并记录）** 引入。它"运行在 softirq 上下文、不能睡眠、per-CPU、按入队顺序执行"，被官方文档描述为"softirq 的便捷接口"——即用统一的 workqueue API 提供 tasklet 那样的中断上下文延后执行，作为 tasklet 的现代替代。（BH workqueue 引入的确切版本以内核提交记录为准，此处标 6.9，随后续版本演进）
- **threaded IRQ（线程化中断，`request_threaded_irq`）** 是另一条现代路线：把中断处理主体放进一个专用内核线程里跑（进程上下文、可睡眠、可被抢占），实时内核（PREEMPT_RT）尤其倚重它。它让"下半部"直接变成一个受调度的线程，是对经典 top/bottom 拆分的重要补充。

softirq/tasklet/workqueue 这套名字要**以你运行的内核版本文档为准**，因为它在演进——tasklet 正在退场、BH workqueue 与 threaded IRQ 是当下推荐方向。但"上半部要短、重活延后到能被打断/能睡眠的上下文"这条**核心原则** 不变，变的只是实现它的具体接口名。
