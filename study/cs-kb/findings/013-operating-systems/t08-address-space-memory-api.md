## 8.1 虚拟地址空间布局

### 8.1.1 什么是虚拟地址空间

虚拟地址空间（virtual address space）是操作系统给每个进程的一个**假象**：进程看到的是一条从地址 0（或某个固定低地址）开始、连续、私有、看起来极大的内存条，仿佛整台机器的内存都归它一个人用。进程里所有的指针、所有 `&x` 取到的地址，都是这条假内存上的**虚拟地址**，而不是内存芯片上的物理地址。真正的虚拟→物理映射由硬件 MMU 配合内核页表完成（那是大主题09 的内容），本节只关心"这条假内存被切成了哪几段、每段放什么"。

**"每个进程独占一整片内存"是骗你的，但骗得很值**。有了这层假象，编译器和链接器可以假定程序总是被加载到固定的地址布局上，不用管别的进程；两个进程即使都用地址 `0x401000`，指的也是各自不同的物理页，互不干扰；这既是**隔离**（一个进程越界改不到另一个进程），也是**抽象**（程序员不必知道物理内存有多大、别人占了哪里）。这正是大主题01"OS 作为资源虚拟化器"里"把一份物理内存虚拟成每进程一份"的落地。

### 8.1.2 经典分段：text / data / bss / heap / stack

一个典型的 C 程序被加载后，它的地址空间从低地址到高地址大致排成这样（OSTEP Ch13 与 CSAPP Ch9 一致给出的经典布局）：

```
高地址  ┌──────────────────────┐
        │  stack（栈，向下增长↓）  │  局部变量、函数调用帧、返回地址
        ├──────────────────────┤
        │        ↕ 空洞          │  栈与 mmap/堆之间的未用空间
        │   mmap 区（共享库/大块）  │  动态库、文件映射、大块匿名内存
        ├──────────────────────┤
        │   heap（堆，向上增长↑）  │  malloc 动态分配区
        ├──────────────────────┤
        │   .bss（未初始化全局）    │  未初始化/初值为 0 的全局与静态变量
        ├──────────────────────┤
        │   .data（已初始化全局）   │  带非零初值的全局与静态变量
        ├──────────────────────┤
        │   .rodata（只读数据）     │  字符串字面量、const 常量
        ├──────────────────────┤
        │   .text（代码，只读可执行）│  机器指令
低地址  └──────────────────────┘
```

各段的分工：`.text` 放机器指令，只读且可执行；`.rodata` 放只读常量（如字符串字面量 `"hi"`）；`.data` 放有非零初值的全局/静态变量；`.bss` 放初值为 0 或未初始化的全局/静态变量——它在可执行文件里**不占空间**，只记一个大小，加载时由内核清零，这是"为什么全局变量默认是 0"的机制来源。堆（heap）紧接在 `.bss` 之上、**向高地址增长**，是 `malloc` 的地盘；栈（stack）在高地址端、**向低地址增长**，放函数调用帧。栈和堆一个往下长、一个往上长，中间留一大片空洞，谁也别轻易撞上谁——这样两者都能弹性伸缩而不必预先瓜分固定大小。

本机实跑印证这个从低到高的顺序（`seg.c`，用 `-no-pie` 关掉位置无关以看到固定加载地址，Linux 6.18.5 / gcc 13.3 @2026-07-29）：

```
text(main)   0x401196     ← .text 最低
rodata       0x402004     ← .rodata 在其上
data(g_init) 0x404030     ← .data
bss (g_bss)  0x404044     ← .bss 紧接 .data
stack(local) 0x7ffc...    ← 栈在极高地址
```

地址严格满足 `text < rodata < data < bss ≪ stack`，与上面的经典布局图吻合。

### 8.1.3 mmap 区与共享库：堆和栈之间的一大片

现代地址空间里，堆和栈中间那片"空洞"并不空——**内存映射区（memory-mapping segment / mmap 区）**就落在这里。动态链接库（如 `libc.so`）、通过 `mmap` 映射的文件、以及大块的匿名内存分配，都放在这一段。本机对任意进程 `cat /proc/self/maps` 可直接看到这层结构（真实输出节选，@2026-07-29）：

```
563cf0d9b000-...  r-xp  /usr/bin/cat            ← 程序 .text
563d1732f000-...  rw-p  [heap]                  ← 堆
7f6b51e00000-...  r-xp  /usr/lib/.../libc.so.6  ← mmap 映射的共享库（高地址）
7f6b52061000-...  r-xp  [vdso]
7ffe3c323000-...  rw-p  [stack]                 ← 栈，最高
```

可以看到 `[heap]` 在低处、共享库映射与 `[stack]` 在高处，中间是大片映射区。`/proc/[pid]/maps` 是理解某个真实进程内存布局最直接的窗口：每行是一段连续映射，含地址范围、权限（`r/w/x/p`）、以及它对应的文件或特殊区（`[heap]`/`[stack]`/`[vdso]` 等）。

关于 `[vdso]`/`[vvar]`/`[vsyscall]`：这些是内核映射进每个进程地址空间的特殊页，用来让某些系统调用（如 `gettimeofday`）不必真正陷入内核就能读到内核维护的数据，属于加速机制，初学阶段知道"它们是内核塞进来的只读页"即可。

### 8.1.4 ASLR：为什么每次运行地址都不一样

现实中如果你直接 `./程序` 反复跑并打印堆或栈地址，会发现每次都不同——这是**地址空间布局随机化**（ASLR, Address Space Layout Randomization）在起作用：内核每次启动进程时把栈、mmap 区、（PIE 程序的）代码段起始地址随机偏移一下，让攻击者难以预知某段代码或数据落在哪里，从而加大栈溢出等攻击利用的难度。

这解释了 8.1.2 里为什么要用 `-no-pie` 才能看到 `0x401196` 这样固定的代码地址：默认的 PIE（位置无关可执行）+ ASLR 会让每次地址都变。初学者要记住：**地址空间的"布局顺序"（谁高谁低、哪段挨着哪段）是稳定的，但每段的"具体起始地址"因 ASLR 而每次随机**。这也是为什么程序里绝不能把某个绝对地址硬编码进去。

## 8.2 malloc/free 语义与误用

### 8.2.1 malloc / free 的接口与契约

C 标准库通过一组函数管理堆上的动态内存，核心是 `malloc` 和 `free`：

```
void *malloc(size_t size);   // 申请 size 字节，返回起始指针；失败返回 NULL
void  free(void *ptr);       // 归还 ptr 指向的那块（此前 malloc 系列返回的）内存
void *calloc(size_t n, size_t sz); // 申请 n*sz 字节并清零
void *realloc(void *ptr, size_t size); // 调整已分配块大小，可能搬家
```

这套 API 背后是一份程序员必须遵守的**契约**（OSTEP Ch14 反复强调）：`malloc` 给你一块**至少** `size` 字节、地址对齐得当、内容未定义（`malloc` 不清零，`calloc` 才清零）的内存；你负责在用完后、且**恰好一次**，把 `malloc`/`calloc`/`realloc` 返回的**原始指针**交回给 `free`。契约的每一条都对应一类误用，下面逐个说。

`malloc` 的返回值**必须检查是否为 `NULL`**（内存耗尽时会返回 NULL，直接解引用就是崩溃）；`free` 只接受"分配器给过你的那个指针"，不能是它的中间地址，也不能是栈上/全局变量的地址。分配和释放是**成对的责任**，谁分配、在哪个生命周期结束时释放，要在写代码时就想清楚。

### 8.2.2 内存泄漏（memory leak）

内存泄漏是指程序 `malloc` 了一块内存，但在不再需要它、且丢失了指向它的最后一个指针之后，**始终没有 `free`**。这块内存于是既用不到、又还不回去，直到进程结束才由内核统一回收。

```
char *p = malloc(1000);
p = malloc(2000);   // 第一块 1000 字节的地址丢了，永久泄漏
```

对短命的命令行小程序，泄漏危害有限（进程退出时内核回收整个地址空间）；但对长期运行的服务（数据库、Web 服务器），泄漏会让进程的堆越涨越大，最终吃光内存被 OOM killer 杀掉。初学者常见的泄漏来源是"提前 return / 异常路径忘了 free""容器/链表节点删除时只摘链不释放"。检测靠工具：`valgrind --leak-check=full` 或 ASan 在退出时报告"还有多少字节未释放、在哪里分配的"。

### 8.2.3 悬垂指针与释放后使用（dangling / use-after-free）

`free` 之后，那块内存被交还给分配器，可能很快被下一次 `malloc` 分配给别处。此时如果还有指针指着它并继续读写，就是**释放后使用**（use-after-free），那个仍指向已释放内存的指针叫**悬垂指针**（dangling pointer）。

```
int *p = malloc(sizeof(int));
free(p);
*p = 5;   // 悬垂：p 指向的内存已还给分配器，此处读写是未定义行为
```

这是 C 里最危险也最难查的一类 bug：`free` 并不会把 `p` 置空，也不会立刻抹掉数据，所以释放后马上访问**往往"看起来还能用"**，直到那块内存被复用、数据被改写，程序才在毫不相干的地方莫名其妙地崩溃或算错——症状与病因隔得很远。本机用 ASan 可以当场抓住它（`-fsanitize=address`，真实输出首行，@2026-07-29）：

```
==22303==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010 ...
READ of size 4 ...
    #0 ... in main .../uaf.c:6
```

防御性习惯是 `free(p);` 后立即 `p = NULL;`——之后再误用会变成对 NULL 的解引用（当场崩、好查），而不是对随机内存的破坏（难查）。

### 8.2.4 双重释放（double free）

对同一块内存调用 `free` 两次（或对一个不是分配器返回的指针调 `free`）就是**双重释放**。分配器内部用元数据（chunk 头、free list 指针）管理空闲块，第二次 `free` 会破坏这些元数据结构，可能导致后续分配返回错乱的指针，甚至被利用为安全漏洞（堆攻击的经典入口）。

```
int *p = malloc(sizeof(int));
free(p);
free(p);   // 双重释放：破坏分配器元数据
```

现代 glibc 对紧邻的重复 free 有一定检测，会打印 `free(): double free detected in tcache 2` 之类信息并 abort；但如果两次 free 之间夹了别的分配，检测未必命中，行为仍是未定义。根因同样是"`free` 后没把指针置空"以及"所有权不清——两处代码都以为自己该释放它"。把内存的所有权（谁负责 free）设计清楚，是避免这类 bug 的根本。

### 8.2.5 其他常见误用：越界、未初始化读、非法 free

除上述三大类，还有几种高频误用，初学者都该认识：

缓冲区越界（buffer overflow/underflow）：写到 `malloc(n)` 得到的块的 `[0, n)` 范围之外，会踩坏相邻块的数据或分配器元数据；`ASan` 报 `heap-buffer-overflow`。

读未初始化内存：`malloc` 不清零，直接读新分配块的内容得到的是垃圾值（想要清零用 `calloc` 或手动 `memset`）；`valgrind` 报 `Use of uninitialised value`。

释放非堆指针 / 中间指针：对栈变量、全局变量取址后 `free`，或对 `malloc` 返回值 `+8` 之后的指针 `free`，都是未定义行为——`free` 只认分配器亲手发出的那个原始指针。

`realloc` 的陷阱：`realloc` 可能把数据搬到新地址并释放旧块，因此**旧指针在 `realloc` 之后可能失效**，必须用返回值更新指针；且 `realloc` 失败返回 NULL 时**不会**释放原块，直接 `p = realloc(p, n);` 会在失败时同时丢失原块指针（泄漏）。

C 把内存安全的责任完全交给程序员，编译器默认不做运行期检查。所以实践上必须靠工具兜底——开发期常态化跑 `-fsanitize=address`（ASan，快、能定位到行）或 `valgrind`（无需重编译、检测更全但慢），是 C/C++ 工程的基本纪律。

## 8.3 brk/sbrk vs mmap 分配路径

### 8.3.1 两条向内核要内存的系统调用

`malloc` 自己不制造内存，它是 C 库里的一层管理器；当库手里的空闲内存不够时，它向内核发系统调用要更多。内核提供两条获取匿名内存（不对应任何文件的可读写内存）的主要途径：

```
int   brk(void *addr);        // 把堆的"程序断点"(program break)直接设到 addr
void *sbrk(intptr_t incr);    // 把程序断点移动 incr 字节，返回旧断点（glibc 封装）
void *mmap(NULL, len, PROT_READ|PROT_WRITE,
           MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);  // 映射一块 len 字节的匿名内存
```

`brk`/`sbrk` 调整的是**堆顶那一根指针**（程序断点，program break）：堆是 `.bss` 之上一段连续区域，`sbrk(+n)` 把这根顶指针往高地址推 n 字节、就多出 n 字节堆空间，`sbrk(-n)` 往回收缩。它只能线性地涨/缩堆这一整段，简单但不灵活。`mmap` 则能在地址空间的映射区里**独立地**要来一整块（页对齐的）匿名内存，用完可以用 `munmap` 单独还掉，彼此不必连续——灵活得多。

`brk` 像"把院子的围墙整体往外推一段来扩地"，只能推最外面那道墙；`mmap` 像"在空地上任意圈一块新地盖房"，可以圈很多块、拆哪块都行。glibc 分配器同时用这两条路，按申请大小自动选。

### 8.3.2 分配路径的分流：小块走堆(brk)，大块走 mmap

glibc 的 malloc 有一个阈值 `M_MMAP_THRESHOLD`：申请的字节数**小于**阈值时，从主堆（由 `brk`/`sbrk` 扩张的那段）里切一块给你；申请**大于等于**阈值时，直接为这块单独 `mmap` 一整段匿名内存，`free` 时对它单独 `munmap` 还给内核。

这个阈值的**默认值是 128 KiB（131072 字节）**（glibc 手册 `M_MMAP_THRESHOLD` 条目与 `mallopt(3)` man page 一致给出）。需要注意 glibc 的阈值是**动态**的：若未用 `mallopt(M_MMAP_THRESHOLD, ...)` 显式固定，释放一块 mmap 分配时分配器会把阈值上调到刚释放的那块大小（上限约 32 MiB，64 位），以适应"程序反复分配某个大尺寸"的模式、减少 mmap 次数。初学阶段记住"**默认约 128 KiB 起走 mmap，且可动态上浮**"即可。

本机 `strace` 清楚地拍到这个分流（`alloc.c`：一次 `malloc(100)` + 一次 `malloc(200*1024)`，真实输出节选，@2026-07-29）：

```
brk(NULL)                 = 0x5607e9825000
brk(0x5607e9846000)       = 0x5607e9846000               ← 小块(100B)：扩堆 0x21000 字节
mmap(NULL, 208896, PROT_READ|PROT_WRITE,
     MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7f483f914000  ← 大块(200KiB>128KiB)：单独 mmap
munmap(0x7f483f914000, 208896) = 0                        ← free 大块：单独 munmap 还内核
small=0x5607e98252a0  big=0x7f483f914010
```

`small` 落在 `brk` 扩出的堆区（`0x5607e982...`），`big` 落在 `mmap` 返回的映射区（`0x7f483f...`），地址段截然不同，且 200 KiB 请求被内核向上取整到页对齐的 208896 字节（= 51 × 4096）。这就是"小块走堆、大块走匿名 mmap"的直接证据。

### 8.3.3 为什么要分两条路

小块用堆（brk）的好处是**摊薄开销**：`sbrk` 一次扩一大段（上例扩了 0x21000 = 132 KiB），之后成千上万次小 `malloc` 都在这段里由库内部切分完成、根本不进内核，系统调用开销被摊到极薄。缺点是堆是一整段线性区，中间的块 `free` 了也不能立刻还给内核（只能等堆顶那块空了才好收缩），容易积累碎片（见 8.4）。

大块用 mmap 的好处是**独立可回收**与**隔离**：每个大块是独立映射，`free` 时 `munmap` 立刻把物理内存和地址空间都还给内核，不会卡在堆中间造成"堆顶下不来"；而且大块独占映射，越界更容易触发缺页被抓到。缺点是每次 `mmap`/`munmap` 都是一次系统调用 + 缺页，还要页对齐（小块用 mmap 会因为最小一页 4 KiB 而极度浪费），所以小块绝不该走 mmap。

初学者可以这样理解这条设计权衡：**频繁的小额分配怕的是系统调用开销，所以批发（brk 一次扩一大片再零售）；偶发的大额分配怕的是长期占着堆下不来，所以单独拿地、用完立刻退（mmap/munmap）**。阈值就是这两种顾虑的分界线。

### 8.3.4 页粒度与 lazy 分配（点到为止）

无论 brk 还是 mmap，内核管理内存的最小单位是**页**（本机 x86-64 为 4 KiB），所以任何向内核要内存的动作最终都按页对齐、按页计。更重要的是：`mmap` 一块匿名内存或 `sbrk` 扩堆返回成功时，内核通常**并没有真的分配物理内存**，只是登记了"这段虚拟地址你可以用"；直到你第一次真正写某一页，才触发缺页、内核此刻才分配一张物理页并（对匿名内存）清零——这叫**按需分页 / 按需置零**。

这解释了一个初学者常困惑的现象：`malloc` 一大块（甚至比物理内存还大）常常"立刻成功"，因为那一刻还没占用一分物理内存。缺页处理、按需置零、COW 的完整机制归本课大主题10，本节只点明"要到虚拟地址 ≠ 已占物理内存"这一层，避免把 `malloc` 成功误当成物理内存已落实。

## 8.4 空闲空间管理

### 8.4.1 分配器要解决的核心问题

分配器（allocator）向内核批发来大段内存（8.3 的 brk/mmap）后，要负责把它零售给成千上万次大小不一的 `malloc`，并在 `free` 时收回、以便复用。核心难题是：**这些块是变长的、分配和释放的顺序是任意交错的**，分配器只能管理由此产生的一堆"空闲洞"，还必须做到 `malloc`/`free` 本身足够快。OSTEP Ch17 把这类问题称为空闲空间管理（free-space management），其经典载体是**空闲链表**（free list）。

分配器手里是一片被"已用块"和"空闲块"交替切分的连续内存。它把所有空闲块用一个链表串起来（free list），每个空闲块的头部就地存着"我有多大、下一个空闲块在哪"这些元数据。`malloc(n)` 时遍历这个链表找一块够大的切给你；`free` 时把块塞回链表，并尽量与相邻的空闲块合并（coalescing）成更大的块，防止越切越碎。

### 8.4.2 内部碎片与外部碎片

碎片（fragmentation）是空闲空间管理的头号敌人，分两种，初学者极易混淆，务必分清：

**外部碎片**（external fragmentation）：空闲内存总量足够，但被切成许多不连续的小块，凑不出一块足够大的连续区来满足某个请求。例如共有 20 KiB 空闲，却分散成两块 10 KiB，此时来一个 15 KiB 的请求就会失败——"总量够、连不成片"。

**内部碎片**（internal fragmentation）：分配给请求的块**比请求实际需要的大**，多出来的那部分在块内部被浪费、又不能给别人用。例如请求 100 字节，分配器为对齐或按固定尺寸取整给了 128 字节，多出的 28 字节就是内部碎片——"给多了、块内浪费"。

**外部碎片是"块与块之间的空隙"，内部碎片是"块内部用不满的部分"**。两者常此消彼长——为减少外部碎片而按固定大小分配（见 8.4.4 slab/buddy）会增加内部碎片；为精确满足请求而任意切分则会加剧外部碎片。合并相邻空闲块是对抗外部碎片的关键手段。

### 8.4.3 分配策略：first-fit / best-fit / worst-fit / next-fit

给定一个空闲链表和一个大小为 n 的请求，"该切哪一块"有几种经典策略（OSTEP Ch17 与 CSAPP Ch9 一致列举）：

```
first-fit  首次适配：从头扫，遇到第一个 ≥ n 的空闲块就用它
next-fit   循环首次适配：从上次停下的位置继续扫（避免每次都从头）
best-fit   最佳适配：扫全部，选 ≥ n 中最小的那块（剩余最少）
worst-fit  最差适配：扫全部，选最大的那块（希望剩下的还够大）
```

first-fit **快**（找到即停，不必扫全表），但倾向于把链表前部切得很碎；next-fit 用一个游标避免每次从头扫，速度类似 first-fit 且碎片分布更均匀；best-fit 直觉上"最省"、能减少大块被切小造成的浪费，但**每次都要扫完整个链表**（慢），且会留下大量几乎没法再用的极小碎片；worst-fit 意图让切剩的块仍然可观，但实测效果通常不好、还得全表扫描，实践中很少用。

**没有普适最优**——策略好坏依赖实际的分配/释放模式。工程实现（如 glibc）不会死用某一种，而是用**分桶 / 分箱**（binning，把相近大小的空闲块归到同一个 bin，如 glibc 的 fastbins/smallbins/largebins）来把"找合适块"变成近似 O(1) 的查表，再辅以合并与缓存（如 tcache 做线程本地小块缓存），本质是在 first/best-fit 思想上做工程加速。

### 8.4.4 更结构化的方案：buddy（伙伴）与 slab

除了通用的空闲链表，还有两种为特定场景优化的经典机制，常见于内核内存管理：

**伙伴系统**（buddy allocator）：把内存按 2 的幂大小管理。分配时若没有正好大小的块，就把一个更大的块**对半劈**成两个"伙伴"，一路劈到需要的大小；`free` 时若某块的伙伴也空闲，就**合并**回上一级。好处是合并极快（伙伴地址可位运算算出）、能有效控制外部碎片；代价是分配总向上取整到 2 的幂，内部碎片可能较大（请求 65 KiB 会拿到 128 KiB）。Linux 内核的物理页帧分配器就是伙伴系统。

**slab 分配器**：为**固定大小、频繁分配释放的同类对象**（内核里如 `task_struct`、inode、dentry）预先切好一批同尺寸的槽（slab），分配就是从空闲槽链表摘一个、释放就是塞回去，几乎零碎片且极快，还能缓存对象的已初始化状态。Linux 内核用 slab/slub 管理这类对象，本机可 `cat /proc/slabinfo` 看到各类内核对象缓存（如 `dentry`/`inode_cache` 的对象数与每 slab 对象数）。

这两者主要活跃在**内核内部**的内存分配，是对通用分配器的补充：伙伴系统管大颗粒（页级），slab 在伙伴之上管小颗粒（同类对象），用户态的 `malloc` 则在 8.3 拿到的大段之上用分桶 free list 零售。它们的完整实现与内核内存管理深挖超出本课范围，本节点到"各自解决什么、代价在哪"为止。
