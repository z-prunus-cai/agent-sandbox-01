## 3.1 受限直接执行协议

### 3.1.1 为什么需要"受限"直接执行

直接执行（direct execution）指的是：让用户程序的指令**直接在物理 CPU 上运行**，而不是让操作系统一条条解释执行。这是性能的根本——如果每条用户指令都要 OS 过一遍手，机器会慢到不可用。OSTEP Ch6 把这称作 baseline：内核建好进程、把 CPU 交给它、程序全速跑自己的指令。

但纯粹的直接执行有两个致命问题，正是"受限"要解决的。其一是**安全/隔离**：如果用户程序能直接执行任意指令（关中断、改页表、直接读磁盘），它就能绕过 OS 为所欲为、越权访问别人的数据。其二是**控制权**：如果 CPU 完全交给用户程序，程序若陷入死循环或就是不还，OS 再也拿不回 CPU，其他进程全部饿死。受限直接执行（Limited Direct Execution, LDE）就是在"直接执行"上加两道约束——用**双模式 + 受保护指令**堵住第一个问题（危险操作只能在内核态做），用**陷入机制 + 时钟中断**堵住第二个问题（内核总能被叫回来）。

初学者可以用"租车"来理解：租车公司（内核）把车（CPU）交给你（用户程序）自己开，全速上路（直接执行，快），但方向盘不能拆、油箱盖锁死、且车上装了个定时器会周期性提醒公司"车还在谁手上"（受限）。你想加油、走高速收费站这类"特权操作"，必须停到指定服务区按喇叭叫工作人员来办（系统调用），不能自己动手。

### 3.1.2 内核先布置陷阱表（trap table）

LDE 的第一步发生在**开机时**：内核在硬件里登记一张**陷阱表 / 中断向量表**（trap table / IDT），告诉 CPU"发生某类事件时，跳到内核的哪个地址去处理"。这一步本身是特权操作，只能在内核态、开机初始化时做一次，用户程序无权修改——否则它就能把陷阱指向自己的恶意代码。

x86-64 上这张表叫**中断描述符表（IDT）**，由特权指令 `lidt` 装载，256 个表项分别对应 256 个中断/异常向量（如向量 0 = 除法错、向量 14 = 缺页）。xv6（RISC-V）上对应的是把内核陷阱入口地址写进 `stvec` 控制寄存器。关键点是：**用户程序不能自己决定陷入后跳哪里，跳哪里由内核在可信的初始化阶段一次性钉死**，这是"受控入口"的硬件基础。

xv6 源码里可以看到这个"钉死入口"的动作。`kernel/trap.c` 的 `usertrap()` 一进来就把陷阱向量从用户态入口切到内核态入口，防止在内核里再次陷入时跳错地方：

```c
// kernel/trap.c usertrap()（xv6 commit 75c4638，只读）
w_stvec((uint64)kernelvec);   // 现在在内核里，后续中断/异常改由 kernelvec 处理
```

### 3.1.3 三步舞：布陷阱 → 启动进程 → 时钟夺权

把 LDE 协议连起来看，是一支"三步舞"（OSTEP Ch6 的两阶段协议 + 时钟补充）：

```
第一步（开机，内核态）：内核初始化陷阱表，登记 syscall/异常/时钟中断的处理入口；启动第一个时钟。
第二步（运行，用户态）：内核经"降权返回"把 CPU 交给用户进程，进程全速直接执行自己的指令。
第三步（夺权，回内核态）：进程主动 syscall / 无意触发异常 / 时钟中断到点 —— 任一发生，
        CPU 自动切内核态、按陷阱表跳到内核入口，内核处理完再降权返回用户态（或切给别人）。
```

这支舞的精髓是**控制权的钟摆**：平时钟摆停在用户态（快），任何一种"陷入事件"都把钟摆强制推回内核态（安全），内核处理完再把钟摆推回去。前两步保证"能安全地把 CPU 借出去且危险操作被拦截"，第三步的时钟中断保证"就算进程不主动还，内核也能定期把 CPU 抢回来"——没有第三步，一个死循环的用户程序就能永久霸占 CPU（这正是早年协作式系统的痛点，3.5 详述）。3.2–3.5 就是把这三步里的每个机制拆开细讲。

#### 来源与时效
- OSTEP Ch6「Mechanism: Limited Direct Execution」（网页版，核实 2026-07-25）：直接执行 baseline、受限的两个动机（受保护操作 / 进程间切换）、trap table、两阶段协议（boot 建表 / run 降权执行）、时钟中断夺权。
- MIT 6.1810 2024「Traps/System calls」讲义 ＋ xv6 `trap.c`（commit `75c4638`，只读）：`w_stvec` 登记陷阱入口、内核态与用户态陷阱入口分离，交叉印证"受控入口由内核钉死"。
- Intel SDM Vol.3A Ch6（核实 2026-07-25）：IDT 256 项、`lidt` 装载 —— 作 x86-64 侧陷阱表的一手对照。
- 交叉一致：OSTEP 的"trap table"= x86 IDT = RISC-V `stvec`，同一机制不同命名，无冲突。

## 3.2 中断、异常与陷入的分类

### 3.2.1 三大来源：中断 / 异常 / 陷入

内核被"叫醒"从用户态切回内核态，触发源可分三类。**中断（interrupt）** 是**异步**的、来自 CPU 外部的信号（时钟、键盘、网卡、磁盘完成），与当前正在执行哪条指令无关，随时可能到达。**异常（exception）** 是**同步**的、由 CPU 执行某条指令时**内部**产生的（除以零、缺页、非法指令、越权访问），一定和"刚执行的那条指令"绑定。**陷入 / 系统调用（trap / syscall）** 是程序**主动**用一条特殊指令（x86-64 的 `syscall`、RISC-V 的 `ecall`）故意触发的、请求内核服务的同步事件。

**看"是不是当前指令引起的"**。外部设备来敲门 = 中断（异步，跟你正在干嘛没关系）；你自己这条指令出事了 = 异常（同步，坏事）；你自己这条指令故意求助 = 陷入/系统调用（同步，好事）。三者最终都走同一套陷入硬件路径（切模式、跳固定入口），区别只在"谁触发、为什么、内核处理完怎么办"。

xv6 `usertrap()` 里能一眼看到内核如何在同一入口分辨这三类——它读原因寄存器 `scause` 分派：

```c
// kernel/trap.c usertrap()（xv6 commit 75c4638，只读）
if (r_scause() == 8) {            // scause==8：系统调用（陷入，主动）
    ...
    syscall();
} else if ((which_dev = devintr()) != 0) {   // 外部/时钟中断（异步）
    // ok
} else if (r_scause() == 15 || r_scause() == 13) {  // 15=写缺页,13=读缺页（异常，同步）
    ... vmfault(...) ...
} else {                          // 其它未预期异常 → 杀掉进程
    setkilled(p);
}
```

### 3.2.2 异常的细分：fault / trap / abort

异常按"能否恢复、在指令的哪个时点报告"再细分三种（Intel SDM Vol.3A 的正式分类）。**fault（故障）** 是**可恢复**的：CPU 在**执行该指令之前/之中**发现问题、报告异常，处理程序修好后可以**重新执行同一条指令**——最典型是缺页（page fault），内核把缺的页调进来后重跑访存指令，程序毫无察觉。**trap（自陷）** 在**指令成功执行之后**报告，返回时接着执行**下一条**指令——如调试断点 `int3`、以及被归为软件 trap 的系统调用。**abort（中止）** 是**不可恢复**的严重错误（如硬件故障、双重故障），无法定位到可重启的精确指令，通常直接终止。

这里有一个**必须显式标注的术语冲突**，初学者极易被绊倒：

```
分歧点：单词 "trap" 在两套一手来源里含义不同。
· OS 教材侧（OSTEP / xv6）：trap 常泛指"一切陷入内核的事件"，或特指"程序主动的系统调用（自愿陷入）"。
· 硬件手册侧（Intel SDM）：trap 是异常里与 fault/abort 并列的一个子类
  —— 指"指令执行完成后才报告、返回执行下一条"的那类异常（如断点）。
本报告的取用：讲 OS 协议时用教材义（trap≈自愿陷入/系统调用，见 3.1/3.3）；
讲异常细分时用 SDM 义（fault/trap/abort 三分），并在此点明，不和稀泥。
```

fault 与 trap 的区别不是咬文嚼字，而是决定"返回后从哪条指令继续"：fault 返回**重执行触发指令**（因为它没成功），trap 返回**执行下一条**（因为它已成功）。缺页之所以能对程序透明，正因为它是 fault——修好页后重跑那条访存指令，程序看不出中间被内核插过手。

### 3.2.3 本机实证：踩两种异常看信号落地

Linux 把大多数 CPU 异常转换成**信号**递给进程：除法错（x86 向量 0，`#DE`，是 fault）→ `SIGFPE`；越权访存/缺页无法满足（向量 14，`#PF`，是 fault）→ `SIGSEGV`。本机跑一个故意除零、故意解引用空指针的程序，看进程被哪种信号打断（Linux 6.18.5 @2026-07-29，gcc 13.3.0）：

```
$ ./sig fpe          # int x = 1; return x / 0;
Floating point exception     ← 内核把 #DE 异常转成 SIGFPE
fpe exit=136                 # 136 = 128 + 8，8 = SIGFPE

$ ./sig segv         # int *p = 0; *p = 1;
Segmentation fault           ← 内核把 #PF 无法满足转成 SIGSEGV
segv exit=139                # 139 = 128 + 11，11 = SIGSEGV
```

退出码规律是 `128 + 信号号`：shell 用 128 以上的退出码表示"进程被信号杀死"，减去 128 就是信号编号（8=SIGFPE，11=SIGSEGV）。这条实证串起了"硬件异常 → 内核陷阱处理 → 转成信号 → 进程终止"的完整链路：CPU 执行 `idiv` 时检测到除零，触发 `#DE` fault，按 IDT 跳进内核异常处理，内核发现是用户态触发的、且进程没装 `SIGFPE` 处理器，于是用默认动作（终止）结束进程。这正是 3.1"受限"的体现——用户程序的一个非法动作被硬件+内核联手拦下，而不是让机器崩溃。

#### 来源与时效
- Intel SDM Vol.3A Ch6「Interrupt and Exception Handling」（核实 2026-07-25）：interrupt（异步/外部）vs exception（同步/内部）；exception 三分 fault（可重启，返回重执行）/ trap（执行后报告，返回下一条）/ abort（不可恢复）；`#DE`=向量0、`#PF`=向量14。
- OSTEP Ch6（核实 2026-07-25）：trap 作"自愿陷入内核"用法 —— 与 SDM 的 trap 子类含义分歧，正文 3.2.2 已显式两边都记。
- xv6 `trap.c` `usertrap()`（commit `75c4638`，只读）：以 `scause` 在同一入口分派 syscall(8)/中断/缺页(13,15)，交叉印证三类来源共用一套陷入路径。
- 本机实证 `./sig fpe|segv`（Linux 6.18.5 @2026-07-29）：SIGFPE 退出 136、SIGSEGV 退出 139，印证"CPU 异常 → 内核 → 信号"链路。
- 冲突项：见 3.2.2 "trap" 术语框，教材义 vs SDM 义两边定位已给。

## 3.3 x86-64 系统调用约定

### 3.3.1 系统调用是"受控的陷入"

系统调用（system call）是用户程序请求内核代办特权操作（读写文件、创建进程、分配内存）的唯一合法途径。它本质是 3.2 里的"主动陷入"：程序把"要调哪个服务、参数是什么"按约定放进寄存器，然后执行一条专门的陷入指令，CPU 随即切到内核态、跳到内核预设的系统调用入口。关键在于——用户程序**不能直接跳进内核代码的任意位置**，它只能通过这条陷入指令跳到内核**钉死的那一个入口**，由内核根据调用号自行决定执行哪段代码。这就是"受控入口"：入口唯一、参数受检、权限由内核把关。

初学者常把"调用系统调用"和"调用普通函数"混为一谈，二者天差地别。普通函数调用（`call`）只是跳到同一地址空间、同一特权级的另一段代码，寄存器约定是"函数调用约定"；系统调用要**跨越特权边界**（ring 3 → ring 0），必须用特殊指令触发硬件切模式，且用的是**另一套**寄存器约定（下面会看到它和函数约定差一个寄存器）。可以说系统调用是"受了硬件监管的、能跨墙的函数调用"。

### 3.3.2 x86-64/Linux 的寄存器约定

在 x86-64 Linux 上，系统调用用 `syscall` 指令触发，寄存器约定如下（这是 Linux 内核 syscall ABI，独立于普通函数的 System V 调用约定）：

```
系统调用号：      rax
参数（最多 6 个）：rdi, rsi, rdx, r10, r8, r9   （按顺序第1~6个参数）
触发指令：        syscall
返回值：          rax
被 syscall 破坏：  rcx（存返回地址 RIP）、r11（存 RFLAGS）
```

必须画重点的**易错点**：系统调用的第 4 个参数用 **`r10`**，而**不是** `rcx`。普通函数调用（System V ABI）的前 6 个整型参数是 `rdi, rsi, rdx, rcx, r8, r9`——注意第 4 个是 `rcx`。系统调用把第 4 个从 `rcx` 换成 `r10`，正是因为 `syscall` 指令本身会用 `rcx` 保存返回地址（把用户态 RIP 存进 rcx）、用 `r11` 保存 RFLAGS，所以 `rcx`/`r11` 不能拿来传参，只好让第 4 参数改用 `r10`。这是初学者手写 syscall 时最常踩的坑。

### 3.3.3 本机实证：内联汇编直发 write，对照 strace

本机用内联汇编按上表直接发一次 `write` 系统调用（号 1，参数 fd=1、buf、count），不经 glibc 包装（Linux 6.18.5 @2026-07-29，gcc 13.3.0，`-std=c11`）：

```c
const char msg[] = "hello via raw syscall\n";
long ret;
__asm__ volatile (
    "syscall"
    : "=a"(ret)                                  // 返回值 ← rax
    : "a"(1), "D"(1), "S"(msg), "d"(sizeof(msg)-1) // rax=1(write), rdi=1(fd), rsi=buf, rdx=count
    : "rcx", "r11", "memory"                     // 显式声明 syscall 破坏 rcx/r11
);
```

程序输出与 `strace` 拦截到的系统调用完全对上：

```
$ ./rawwrite
hello via raw syscall

$ strace -e trace=write ./rawwrite
write(1, "hello via raw syscall\n", 22) = 22    ← 系统调用号1、fd=1、buf、count=22，返回写入字节数22
```

内联汇编里 `"a"`=rax、`"D"`=rdi、`"S"`=rsi、`"d"`=rdx（GCC 约束字母），clobber 列表显式写了 `rcx`、`r11`——正因为 3.3.2 说的它俩会被 `syscall` 冲掉，不声明会让编译器误以为它们还保有原值而出错。`strace` 之所以能逐条打印系统调用，是因为它用 `ptrace` 让内核在每次陷入系统调用入口/出口时停下被 tracer 观察——这本身就是"系统调用必经内核唯一受控入口"的旁证。

### 3.3.4 系统调用号是每架构一张表；返回值与错误约定

系统调用号是**内核为每种架构单独维护的一张表**，同一个调用在不同架构上号可能不同，绝不能跨架构套用。本机 x86-64 从内核头文件 `/usr/include/x86_64-linux-gnu/asm/unistd_64.h` 直接读到（核实 2026-07-29）：

```
__NR_read       0
__NR_write      1
__NR_clone      56
__NR_execve     59
__NR_exit_group 231
__NR_openat     257
```

返回值走 `rax`：成功时是有意义的结果（如 `write` 返回写入字节数），失败时内核返回一个**负的错误码**——具体是把 `-errno` 放进 `rax`（落在 `-4095..-1` 区间）。用户态的 glibc 包装函数会检查这个负值，若在错误区间就把它取反填进全局 `errno`、并让包装函数返回 `-1`；直接发 syscall（如 3.3.3 或 `syscall(2)`）则拿到的是原始的 `-errno`，需自己判读。这解释了初学者的一个困惑："为什么 C 库里失败返回 -1 再看 errno"——那是 glibc 包装层的约定，不是内核的原始约定；内核层面就是一个负数直接编码了错误。RISC-V 的 xv6 约定作对照更清楚："调用号放 `a7`、返回值放 `a0`"，寄存器名换了，但"号一个寄存器、返回值一个寄存器"的结构完全同构：

```c
// kernel/syscall.c syscall()（xv6 commit 75c4638，只读）
num = p->trapframe->a7;                       // 调用号在 a7（RISC-V）
if (num > 0 && num < NELEM(syscalls) && syscalls[num])
    p->trapframe->a0 = syscalls[num]();       // 返回值写回 a0
```

#### 来源与时效
- x86-64 System V AMD64 ABI（核实 2026-07-25）＋ Linux man-pages `syscall(2)`（man7.org，核实 2026-07-25）：`syscall` 指令；号在 `rax`；参数 `rdi,rsi,rdx,r10,r8,r9`（第4参用 `r10` 非 `rcx`）；`rcx`/`r11` 被 syscall 覆盖为 RIP/RFLAGS；返回值在 `rax`；错误以 `-errno`（`-4095..-1`）编码，glibc 包装转 `errno`/`-1`。
- 本机实证内联汇编 `rawwrite` ＋ `strace -e trace=write`（Linux 6.18.5 @2026-07-29）：`write(1,"…",22)=22` 与程序输出一致，印证寄存器约定与"必经受控入口"。
- 本机 `/usr/include/x86_64-linux-gnu/asm/unistd_64.h`（核实 2026-07-29）：read=0/write=1/clone=56/execve=59/exit_group=231/openat=257，印证"号按架构成表"。
- xv6 `syscall.c`（commit `75c4638`，只读）：号在 `a7`、返回写回 `a0` —— RISC-V 对照，结构同构。
- 交叉一致，无冲突；x86-64 与 RISC-V 寄存器命名差异属架构差异，非分歧。

## 3.4 上下文切换机制

### 3.4.1 上下文切换切的到底是什么

上下文切换（context switch）是内核把 CPU 从一个执行流换给另一个执行流的机制：**保存**当前执行流的机器状态、**恢复**下一个执行流之前保存的机器状态，然后跳去继续跑它。所谓"机器状态 / 上下文"，核心是那组决定"下一条指令是谁、栈在哪、寄存器里是什么"的 CPU 寄存器：程序计数器、栈指针、通用寄存器等。切换的瞬间，CPU 仿佛"失忆再唤醒成另一个人"。

要分清两种粒度，这是初学者最容易糊的地方。**线程/内核控制流之间的切换**只需换寄存器组（栈指针一换，就换了栈）。而**进程之间的切换**除了换寄存器，还要**换地址空间**——即切换页表基址寄存器（x86-64 的 `CR3`、RISC-V 的 `satp`），因为不同进程有各自独立的虚拟地址空间（大主题02）。换页表这一下是进程切换比线程切换贵的主要原因，代价见 3.4.3。

### 3.4.2 xv6 源码：swtch 只保存"被调用者保存"寄存器

xv6 的上下文切换函数 `swtch(old, new)` 揭示了一个反直觉但优雅的事实：它**只保存 14 个寄存器**——返回地址 `ra`、栈指针 `sp`、以及 `s0`–`s11` 这 12 个**被调用者保存（callee-saved）寄存器**，其余寄存器一个都不存：

```asm
# kernel/swtch.S（xv6 commit 75c4638，只读）
# void swtch(struct context *old, struct context *new);
swtch:
        sd ra, 0(a0)        # 保存旧上下文：返回地址
        sd sp, 8(a0)        # 栈指针
        sd s0, 16(a0)       # s0..s11（被调用者保存寄存器）
        ...
        sd s11, 104(a0)
        ld ra, 0(a1)        # 加载新上下文
        ld sp, 8(a1)
        ...
        ld s11, 104(a1)
        ret                 # 返回到"新上下文"的 ra 处 —— 即换人成功
```

为什么不用保存 `a0`–`a7`、`t0`–`t6` 这些**调用者保存（caller-saved）**寄存器？因为 `swtch` 是被当作一个**普通 C 函数**调用的——按调用约定，调用者在 `call swtch` 之前，早已把它还需要用的 caller-saved 寄存器自己压到了栈上。既然 caller-saved 的值已经安全地躺在各自的内核栈里，`swtch` 只需保存 callee-saved 的部分，把"栈"整体一换（换 `sp`），那些 caller-saved 值就随各自的栈被正确地留住了。这就是"切换到底切了什么"的精确答案：**切的是 callee-saved 寄存器 + 栈指针 + 返回地址，其余靠"换栈"隐式带走**。对应的 `struct context`（`kernel/proc.h`）字段与 `swtch.S` 严格一一对应，恰好只含这 14 个。

xv6 里进程切换走的是 `进程 → sched() → swtch → scheduler()` 的路径：进程放弃 CPU 时调 `sched()`，`sched()` 调 `swtch` 切到每 CPU 的调度器上下文，`scheduler()` 选中下一个 `RUNNABLE` 进程再 `swtch` 过去。注意 xv6 的地址空间切换（换 `satp`）发生在**返回用户态时**（`prepare_return`/trampoline 里）而非 `swtch` 内，`swtch` 只管内核态寄存器上下文。

### 3.4.3 换页表的代价：TLB 刷新与 PCID 缓解

进程切换换页表（改 `CR3`/`satp`）会带来一笔隐形开销：**TLB（快表，大主题09 详述）需要失效**。TLB 缓存"虚拟地址→物理地址"的翻译结果，是按当前地址空间来的；一旦换了页表，旧翻译对新进程全都作废，若不处理，新进程会用错翻译访问到旧进程的物理页——所以传统上换 `CR3` 会**冲刷整个 TLB**。冲刷后新进程头一批访存全部 TLB 未命中、要走多级页表重新翻译，这就是进程切换"贵"的重要一环。

现代 x86-64 用 **PCID（Process-Context Identifiers，进程上下文标识符）** 缓解这笔开销：给每个地址空间打一个标签，TLB 表项带上标签存放，换 `CR3` 时不必全刷，只需切标签，回到老进程时它的 TLB 项可能还在、直接命中。本机 CPU **支持 PCID**（`/proc/cpuinfo` 的 flags 含 `pcid`，核实 2026-07-29），Linux 会利用它减少切换时的 TLB 刷新。要点是：TLB 刷新是"换地址空间"这件事的固有成本，PCID 是把"全刷"降为"按需刷"的硬件优化，但跨进程的间接开销（缓存被污染等）依然存在，这也是"线程比进程切换便宜"的底层原因之一。

### 3.4.4 本机实证：自愿 vs 非自愿上下文切换计数

`perf stat` 的 `context-switches` 本机不可用（`perf` 未安装，**待核**），改用 `/proc/[pid]/status` 里内核维护的两个计数器观察。跑一个循环 20 次 `usleep(1000)`（每次主动睡眠让出 CPU）的程序，读它自己的计数（Linux 6.18.5 @2026-07-29）：

```
$ ./ctx        # 循环 20 次 usleep 后打印自身 /proc/self/status
voluntary_ctxt_switches:   21
nonvoluntary_ctxt_switches: 0
```

两个计数器精确对应两类抢占时机。`voluntary_ctxt_switches`（自愿切换）是进程**主动**放弃 CPU 的次数——因为等 I/O、等锁、`sleep` 而阻塞，此例 20 次 `usleep` 各触发一次自愿让出，共约 21 次（多的 1 次来自启动/收尾的阻塞）。`nonvoluntary_ctxt_switches`（非自愿切换）是进程**被强制**剥夺 CPU 的次数——时间片耗尽或被更高优先级进程抢占，由内核在时钟中断里动手（正是 3.5 的主题）。此例几乎不做 CPU 密集计算、频繁主动睡眠，故非自愿数为 0。这两个数把"上下文切换"分成了"自己让"和"被抢"两条来源，直观印证 3.1 三步舞里"进程主动陷入"与"时钟中断夺权"两条不同的控制权移交路径。

#### 来源与时效
- OSTEP Ch6「Limited Direct Execution」§保存与恢复上下文（核实 2026-07-25）：context switch = 保存旧/恢复新寄存器；进程切换含地址空间切换。
- xv6 `swtch.S` ＋ `proc.h` `struct context` ＋ `proc.c` `sched()/scheduler()/yield()`（commit `75c4638`，只读）：swtch 仅存 `ra/sp/s0-s11`（callee-saved），caller-saved 靠换栈隐式保留；进程切换路径 `sched→swtch→scheduler`。
- Intel SDM Vol.3A（`CR3`/PCID）＋ 本机 `/proc/cpuinfo` flags `pcid`（核实 2026-07-29）：换地址空间需 TLB 处理，PCID 把全刷降为按需刷，本机 CPU 支持。
- 本机实证 `/proc/self/status`（Linux 6.18.5 @2026-07-29）：`voluntary_ctxt_switches:21`/`nonvoluntary:0`，区分主动让出与被抢占。
- **待核**：`perf stat context-switches` —— `perf` 本机未安装，未取；已用 `/proc` 计数器替代。
- 交叉一致，无冲突。

## 3.5 时钟中断与抢占点

### 3.5.1 时钟中断：内核夺回控制权的硬件保障

时钟中断（timer interrupt）是一个硬件定时器**周期性**产生的中断信号。开机时内核编程让定时器每隔固定时间（一个 tick）就中断 CPU 一次，无论用户程序此刻在干什么，都会被强制陷入内核。这一下就把 CPU 的控制权周期性地、无条件地交还给内核——内核借这个时机检查"当前进程该不该继续跑"，若时间片用尽或有更该跑的进程，就发起一次（非自愿）上下文切换。它是 3.1 三步舞第三步的物理实现，也是**抢占式调度**得以成立的地基。

为什么这是"地基"？设想没有时钟中断的世界（协作式 / cooperative 调度）：内核只能在进程**主动**陷入（系统调用或异常）时才有机会切换，一个只做纯计算、从不调用系统调用、也不出错的死循环程序，将**永久霸占 CPU**，其他进程和内核本身都再也跑不了。OSTEP Ch6 明确点出：早期 Macintosh 等协作式系统正因此脆弱——一个失控程序就能锁死整台机器，用户只能重启。时钟中断把"切换时机"从"全靠进程自觉"变成"内核每 tick 必到场"，这就是**抢占式（preemptive）**调度对**协作式**调度的根本改进。

初学者可以把时钟中断理解成教室里的**下课铃**：不管台上的人讲得多起劲，铃一响（tick）就必须停下、把讲台交回给管理员（内核），由管理员决定下一节让谁上。没有这个铃，一个滔滔不绝的人可以讲到天荒地老，谁也换不下来。

### 3.5.2 xv6 源码：时钟中断如何变成一次让出

xv6 里时钟中断走到 `usertrap()`/`kerneltrap()`，经 `devintr()` 识别为定时器中断（返回 2），随后 `usertrap()` 据此调 `yield()` 主动让出 CPU：

```c
// kernel/trap.c devintr()（xv6 commit 75c4638，只读）
} else if (scause == 0x8000000000000005L) {   // 监督态时钟中断
    clockintr();
    return 2;                                 // 用 2 告知调用者"这是时钟中断"
}

// kernel/trap.c usertrap() 末尾
if (which_dev == 2)   // 若本次陷入是时钟中断
    yield();          // 让出 CPU：置本进程为 RUNNABLE 并调 sched() 切走
```

这段把 3.4 和 3.5 缝在了一起：时钟中断（异步事件）陷入内核 → 内核识别出是定时器 → 调 `yield()` → `yield()` 把当前进程标记为 `RUNNABLE` 再调 `sched()→swtch()` 切到调度器（正是 3.4.2 的上下文切换）。于是"周期性硬件心跳"最终落地成"周期性可能发生的一次上下文切换"。注意 xv6 是**每次 tick 都让出**（简单教学实现），真实 Linux 则由调度器决定这个 tick 要不要真的换人（时间片没到就继续跑当前进程），不是每 tick 必换。

### 3.5.3 本机基线：CONFIG_HZ=250 与 tickless

时钟的"节拍频率"由内核编译参数 `CONFIG_HZ` 决定，表示每秒多少个 tick。本机基线内核实测（读内核配置，Linux 6.18.5 @2026-07-29）：

```
CONFIG_HZ=250              # 每秒 250 个 tick，即每 tick = 1000/250 = 4 毫秒
CONFIG_NO_HZ_IDLE=y        # 动态无节拍（tickless）：CPU 空闲时停掉周期 tick 省电
CONFIG_HZ_1000 is not set  # 未选 1000Hz
```

这里有两个初学者要更新的旧观念。其一，`HZ` 是**可配置**的（常见 100/250/300/1000），不是宇宙常数——本机是 250Hz、每 tick 4ms；教材里若写 "10ms 时间片" 只是举例，别当默认值背。其二，现代 Linux 早已不是"雷打不动每 4ms 必中断一次"：`NO_HZ_IDLE`（动态无节拍 / tickless）让 CPU **空闲时**关掉周期性时钟中断以省电、减少无谓唤醒，只在有任务要跑时才恢复节拍。所以"周期 tick"是抢占的心智模型，但真实内核为省电做了动态优化——机制在（有活干时按 HZ 抢占），但空转时并不真的每 tick 都打扰 CPU。至于具体调度器在每个 tick 如何判断该不该抢占（EEVDF/时间片），归大主题05，本课点到为止。

- xv6 `trap.c` `devintr()`＋`usertrap()`＋`proc.c` `yield()`（commit `75c4638`，只读）：时钟中断 → `devintr` 返回 2 → `yield()` → `sched/swtch`，交叉印证"时钟中断落地为一次上下文切换"；xv6 每 tick 让出属教学简化，与 Linux 由调度器决定是否换人分账。
