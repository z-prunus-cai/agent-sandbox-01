## 09-2.1 关系模型 vs 文档模型

### 09-2.1.1 三大数据模型与"历史钟摆"

数据模型指的是"数据在应用眼中长什么样、彼此如何关联"的抽象层。主流有三类：关系模型（数据是行与表的集合）、文档模型（数据是自包含的嵌套文档，如 JSON）、图模型（数据是顶点与边）。它们不是谁淘汰谁，而是各自擅长不同的数据形状。

历史上这件事反复过好几轮。1970 年 Codd 提出关系模型，到 1980 年代它压倒了更早的层次模型（IBM IMS，树形嵌套）和网状模型（CODASYL，手写指针遍历）而成为主流。2010 年前后 NoSQL 运动（含文档数据库如 MongoDB、宽列如 Cassandra）又以"更好的扩展性、更灵活的 schema、更贴近对象结构"为卖点向关系模型发起挑战。有趣的是，文档模型在"嵌套、需要顺指针访问子记录"这点上与被关系模型取代的层次模型高度相似——所以业界常说数据模型的争论像一只来回摆动的钟摆，而不是一条单向进步的直线。初学者容易误以为"NoSQL 是关系模型的升级版"，实际上它更像是"针对特定数据形状把某些老思路重新捡起来"。

### 09-2.1.2 对象-关系阻抗失配（impedance mismatch）

大多数应用用面向对象语言编写，对象是带嵌套结构的树；而关系数据库把数据摊平成行和表。两者结构对不上，需要一层翻译代码（通常是 ORM 框架，如 Hibernate、SQLAlchemy）在对象和表之间来回搬运——这种模型不匹配、需要额外胶水层的现象叫"阻抗失配"，借自电路里两段线路阻抗不匹配导致信号反射的比喻。

以一份简历为例：一个人有一个姓名，但可能有多段工作经历、多个学历、多项联系方式。在关系模型里这是"一对多"，通常要拆成 `users`、`positions`、`education` 等多张表，查询时再 join 回来；而在文档模型里，整份简历可以自然地存成一个嵌套 JSON 文档，工作经历就是文档里的一个数组。文档模型在这种"一棵自包含的树"结构上确实更贴合应用对象，减少了翻译层。易错点是把"减少阻抗失配"当成文档模型的普适优势——它只在数据天然是一棵树、且几乎总是整体读取时成立；一旦出现大量跨文档的关联，文档模型的短板就暴露了（见 09-2.1.4）。

### 09-2.1.3 数据局部性（locality）

局部性指相关数据在物理存储上是否挨在一起。文档模型把一条记录的所有部分存为一个连续的文档，应用若需要整份文档，一次读取即可拿全，无需多次 join 或多次随机 I/O——这就是文档模型的局部性优势。

这条优势有明确的适用边界。只有当应用"经常需要整份文档"时局部性才划算；如果每次只用文档里的一小段（比如只读简历里的姓名），数据库仍要把整份大文档载入，反而浪费。而且文档越大，更新代价越高：多数文档数据库的更新是"整份文档重写"，即便只改一个字段。因此实践建议是保持文档相对小巧。要注意局部性并非文档数据库专利——关系库也能通过聚簇、把关联数据在物理上放近来获得类似效果（例如 Google Spanner 允许把子表行交错存进父表行附近，Oracle 有类似的多表簇）。所以"局部性"是一种存储布局思想，不等于"必须用文档模型"。

### 09-2.1.4 多对一与多对多关系

关系模型的核心武器是"用外键引用 + join 在查询时把数据拼起来"。多对一（很多人住在同一个城市）和多对多（很多人就读过很多学校、一所学校有很多学生）关系用外键和关联表表达非常自然，join 是数据库内建、优化良好的操作。

文档模型在这里是短板。文档对"一对多的树形嵌套"友好，但对多对多就笨拙：要么把被引用数据复制进每个文档（冗余，更新时要改很多处，容易不一致），要么存对方的 ID 然后在应用代码里手动做多次查询把它们拼起来（等于把 join 逻辑从数据库搬到了应用层，还常常性能更差）。这正是当年层次模型输给关系模型的老问题重演。选型直觉是：如果你的数据关联很稀疏、以自包含的树为主，文档模型合适；一旦多对多关系变多、变密，关系模型（乃至图模型）的优势就回来了。冲突点上 DDIA 明确站关系模型这边——它指出"文档模型规避 join 的初衷，在数据高度关联时反而制造了应用层的复杂性"。

### 09-2.1.5 写时模式 vs 读时模式（schema-on-write / schema-on-read）

关系数据库通常是"写时模式"：schema 显式声明，写入的数据必须符合，数据库强制校验（类比静态类型检查）。多数文档数据库是"读时模式"：不强制统一结构，写什么都收，结构的解释推迟到应用读取时（类比动态类型/运行时解释）。注意"schemaless（无模式）"这个流行说法容易误导——文档并非没有结构，只是结构没有被数据库强制、而是隐含在读取它的代码里，所以 DDIA 更愿意称之为"读时模式"。

两者各有适用场景。当集合里的条目结构不统一（比如来自多个外部源、字段五花八门，或数据类型由外部系统决定、你无法左右）时，读时模式的灵活性很有用。当你期望所有记录结构一致、想要数据库替你挡住脏数据时，写时模式的强制校验更省心。改结构时的差异尤为直观：读时模式加一个新字段，应用直接开始写新字段、读取时对老数据做"有则用、无则给默认值"的兼容处理即可，无需停机迁移；写时模式则往往需要一次 `ALTER TABLE`（多数数据库能秒级完成，但 MySQL 某些历史版本会整表重写、对大表很慢——具体行为随引擎和版本变化，属实现细节）。

### 09-2.1.6 两模型的融合

关系与文档并非非此即彼，近年明显在互相靠拢。主流关系数据库（PostgreSQL 自 9.2/9.4 起、MySQL 自 5.7 起）都内建了 JSON/JSONB 类型，能在一列里存嵌套文档并对其建索引、查询，等于把文档能力吸收进关系库。反过来，一些文档数据库（如 MongoDB）也加入了类似 join 的能力（`$lookup` 聚合阶段），来缓解多对多的短板。

不要把"关系 vs 文档"当成一次不可逆的架构豪赌。更务实的问法是"我这块数据是偏树形自包含、还是偏高度关联"，然后在同一个数据库里对不同数据用不同表达方式。DDIA 把这种融合称作"混合模型"的走向，并预期未来数据库会越来越同时支持两种风格。易错点是以为"关系库存 JSON 就等于文档数据库"——关系库里的 JSON 列在事务、约束、生态成熟度上仍带着关系库的底色，两者定位并不完全重合。

## 09-2.2 图数据模型与图查询语言

### 09-2.2.1 何时用图模型

当数据里的多对多关系成为主角、且关联类型多样时，图模型最合适。图由顶点（vertex，也叫 node，代表实体）和边（edge，代表关系）组成。典型场景包括社交网络（人—关注—人）、道路/地铁网络（地点—路段—地点）、知识图谱（实体—谓词—实体）、推荐与欺诈检测（多跳关联分析）。

图模型的独特价值在于"异构且深度的连接"。关系模型也能表达关联，但当你需要"任意深度的多跳遍历"（比如"我朋友的朋友的朋友里有谁在这家公司"）时，SQL 要写递归公用表表达式（recursive CTE），既笨重又难优化；图查询语言把"可变长度的路径遍历"做成了一等公民，表达同一个查询自然得多。另一个优势是灵活性：往图里加一种新的边类型（新的关系种类）不需要改 schema，很适合数据结构会持续演化的场景。直觉上可以这么记：文档模型擅长"树"，关系模型擅长"表格化的关联"，图模型擅长"任意形状、任意深度的网"。

### 09-2.2.2 属性图（property graph）

属性图模型里，每个顶点有唯一 ID、一组出边、一组入边，以及一组键值对属性；每条边有唯一 ID、起点顶点、终点顶点、一个标签（表示关系类型）、以及一组键值对属性。可以粗略地把它想象成两张关系表（一张顶点表、一张边表），但边表里显式记录了首尾顶点，使得"顺着边走"成为高效原语。

它的灵活性体现在：顶点之间可以有任意类型的关系，不需要预先规定"哪种顶点只能连哪种顶点"；给某类顶点或边加属性也不影响其他记录。代表系统是 Neo4j、以及支持 Apache TinkerPop/Gremlin 的一批图数据库。初学者容易把"属性图"和下面的"三元组存储"混为一谈——它们都是图，但数据的最小单元和查询语言生态不同（属性图的边能自带属性，三元组则把一切都拆成最小的三元组）。

### 09-2.2.3 三元组存储与 RDF（triple-store / RDF）

三元组存储把所有信息都表示成形如 (主语, 谓词, 宾语) 的三元组，例如 (小明, 住在, 北京)。主语总是一个顶点；宾语要么是一个原始值（如字符串"北京"，此时谓词像是主语的一个属性），要么是另一个顶点（此时谓词表示两个顶点之间的边）。W3C 的 RDF（Resource Description Framework）是这套模型的标准化形态，最初为"语义网/万维网数据互联"设计，用 URI 给实体和谓词命名，以便跨组织的数据能拼接成一张全球大图。

和属性图相比，三元组模型更"原子化、更统一"（万物皆三元组），代价是表达同样的信息通常需要更多条三元组，且边本身不能直接挂属性（要给一条关系加属性，得把这条关系本身变成一个顶点再挂三元组，即"具体化/reification"，稍显绕）。RDF 带着浓厚的语义网血统，术语（如 IRI、命名空间）对初学者门槛偏高；实际工程里若不需要跨组织数据互联，很多团队会选属性图而非 RDF。

### 09-2.2.4 Cypher（属性图查询语言）

Cypher 是为属性图设计的声明式查询语言，最早来自 Neo4j。它最有辨识度的是"ASCII 艺术"式的模式匹配语法：用 `()` 画顶点、用 `-[]->` 画有向边，让查询读起来就像在画一张要匹配的子图。下面是一个"找出所有从美国移民到欧洲的人"的示意（顶点标签、边类型为演示）：

```cypher
MATCH (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (us {name:'United States'}),
      (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu {name:'Europe'})
RETURN person.name
```

这里 `-[:WITHIN*0..]->` 表示"沿 WITHIN 边走零到任意多跳"，即可变长度路径——正是图查询相对 SQL 的表达力优势所在：你只描述"想要什么样的路径模式"，怎么遍历交给数据库。要注意 Cypher 是声明式的，你不指定从哪个顶点开始搜、按什么顺序遍历，查询优化器自行决定；这与在应用代码里手写遍历（命令式）形成对比。Cypher 有开源规范 openCypher，也是后文 GQL 标准的重要蓝本。

### 09-2.2.5 SPARQL（RDF 查询语言）

SPARQL 是 W3C 为 RDF 三元组模型设计的声明式查询语言（名字是"SPARQL Protocol and RDF Query Language"的递归缩写），是 W3C 推荐标准。它同样以模式匹配为核心，但匹配的是三元组模式：你写出一批带变量的 (主语, 谓词, 宾语) 模式，数据库找出所有能让这些模式同时成立的变量绑定。

```sparql
PREFIX : <urn:example:>
SELECT ?personName WHERE {
  ?person :name ?personName .
  ?person :bornIn  / :within* / :name "United States" .
  ?person :livesIn / :within* / :name "Europe" .
}
```

其中 `:within*` 是属性路径（property path），表达"沿 within 谓词零到多跳"，作用与 Cypher 的可变长路径类似。SPARQL 与 Cypher 的定位差别主要在数据模型：SPARQL 面向 RDF/三元组、天生带语义网与跨库数据联邦的取向；Cypher 面向属性图。两者都是声明式、都靠模式匹配，思路相通但不能互换。初学者不必纠结语法细节，关键是记住"哪个模型配哪个语言"。

### 09-2.2.6 Datalog

Datalog 是一种更老、更偏学术的声明式查询语言（源自逻辑编程，与 Prolog 同源），底层数据也可视作三元组（写作 `谓词(主语, 宾语)`）。它的独特之处是用规则（rule）把小的谓词组合成新的、可复用的谓词，且规则可以递归地引用自身——这让它特别擅长表达"可达性/传递闭包"这类需要重复应用同一逻辑的查询。

```datalog
within_recursive(Location, Name) :- name(Location, Name).
within_recursive(Location, Name) :- within(Location, Via),
                                    within_recursive(Via, Name).
```

上面两条规则合起来递归地定义了"某地（直接或间接）位于某个命名区域内"。写 Datalog 需要换一种思维：不是一次写完整个查询，而是定义一批规则，让数据库反复套用规则直到不再产生新事实。它对初学者不直观，但表达复杂递归查询时非常强大，也因此在一些现代系统（如 Datomic、以及若干程序分析/数据谱系工具）里复活。DDIA 用它作为"声明式查询也能优雅处理递归"的例证。

### 09-2.2.7 图查询语言的标准化：GQL 与 SQL/PGQ ⚙演进快·锚版本·随时变

长期以来图查询语言缺乏像 SQL 那样的统一标准，各家（Cypher、Gremlin、PGQL 等）自成一派。这一局面在 2023–2024 年被两项 ISO 标准改变，二者由制定 SQL 的同一委员会（ISO/IEC JTC1/SC32 WG3）推出，共享同一套图模式匹配语法：

| 标准 | 编号与年份 | 定位 | 一句话 |
|---|---|---|---|
| SQL/PGQ | ISO/IEC 9075-16:2023（SQL:2023 第 16 部分） | SQL 内嵌的属性图查询 | 在关系表上定义属性图，用 `GRAPH_TABLE(...)` 在 SQL 里做图模式匹配，无需另起一个图数据库 |
| GQL | ISO/IEC 39075:2024 | 独立的图查询语言 | 不依赖关系表示的、专门面向属性图的独立语言；以 openCypher 等为蓝本 |

SQL/PGQ 让你在已有关系数据库里"顺带"查图；GQL 是一门站得住的独立语言。GQL 被称为自 1987 年 SQL 以来 ISO 发布的第一门全新数据库查询语言标准。实现进展快速演进：Oracle Database 23ai 已支持 SQL/PGQ，PostgreSQL 也在推进 `GRAPH_TABLE`（社区路线图指向 19 版附近，具体落地版本以官方发布为准，待核）。因为标准新、各厂商实现程度参差，凡涉及"某语言/某标准在某产品里可用"的结论都请核对当时的官方文档；本节数值均标核实日期 2026-08-01。

## 09-2.3 声明式 vs 命令式查询

### 09-2.3.1 命令式与声明式的区别

命令式查询（imperative）要你一步步写出"怎么做"：遍历哪个集合、用什么循环、按什么顺序、把中间结果放哪。声明式查询（declarative，SQL、Cypher、SPARQL 都属此类）只让你说"要什么"——你描述想要的结果满足什么条件，由数据库的查询优化器决定具体执行方案。

从一堆动物里筛出所有鲨鱼。命令式风格是"建一个空列表，遍历每只动物，若 family 等于 Sharks 就加进列表，最后返回列表"，顺序和步骤都被你钉死。声明式风格是一句 `SELECT * FROM animals WHERE family = 'Sharks'`——你没说怎么遍历、要不要用索引、结果如何排序，这些都留给数据库。这个"要什么 vs 怎么做"的分界是理解后续两条优势的钥匙。

### 09-2.3.2 为什么声明式利于优化与演进

因为声明式查询只描述结果、不锁定执行路径，数据库就有自由去选择当下最优的执行方式，而且可以随时改进——不改你的查询，就能换更好的索引、更好的 join 算法、更好的存储布局，你的同一条 SQL 自动受益。命令式代码则把执行细节写死了，数据库无从替你优化，换了底层实现你还得重写代码。

这条对"随时间演化"尤其重要。数据库版本升级、数据量增长、数据分布变化，声明式查询的最优计划可能随之改变，优化器会自动适配；而命令式查询里"先扫这张表再嵌套循环"的决定一旦写死，环境变了它也不会变，往往从曾经的最优退化成瓶颈。易错点：声明式不是"一定更快"，而是"把择优的权力交给了能持续改进的优化器"，长期看更省心、更可维护。

### 09-2.3.3 为什么声明式利于并行

命令式代码通常规定了执行顺序（先做这条、再做那条），这种顺序依赖使它难以自动切分到多核/多机上并行。声明式查询只说明结果的模式、不规定单步顺序，数据库因而能自由地把工作拆片、分发到多个 CPU 核或多台机器上并行执行，再把结果汇总。

当你不关心"按什么顺序算"，系统就有权"同时算"。这正是声明式在现代多核与分布式环境下越来越重要的原因——硬件的性能增长如今主要来自核数增加而非单核变快，能自动并行的查询模型才吃得到这份红利。命令式那种"一步接一步"的写法，天然是并行的绊脚石。

### 09-2.3.4 网页里的类比：CSS/CSS 选择器 vs JavaScript

DDIA 用一个网页开发的类比把这件事讲透。想把当前选中的导航项标蓝：声明式做法是写一条 CSS 规则（如 `li.selected > p { color: blue; }`），你只描述"哪些元素、长什么样"，浏览器负责在 DOM 变化时自动、高效地保持样式正确。命令式做法是用 JavaScript 手动遍历 DOM 找到这些元素、逐个设置 `style.color`——一旦页面结构变化，你的代码可能失效，而且换个更快的实现你得自己重写。

这个类比之所以好，是因为几乎所有前端开发者都亲历过"用 CSS 声明比用 JS 手改 DOM 更省心、更抗变化"。数据库里声明式 SQL 相对命令式查询 API 的胜出，是同一个道理的另一现场：把"怎么做"交给底层引擎，你只管"要什么"。记住这个类比，就抓住了本小主题的核心。

### 09-2.3.5 MapReduce：介于声明式与命令式之间

MapReduce 是一种在多机上处理大规模数据的编程模型（源自 Google，Hadoop 是著名开源实现），它既不是纯声明式、也不是纯命令式，而是夹在中间。你提供两段代码片段：map 函数（对每条记录做转换、产出键值对）和 reduce 函数（对同一键的所有值做归并）；框架负责调度、分发、把相同键的数据聚到一起——这部分的并行与调度是框架代劳的（偏声明式的好处），但查询逻辑本身是你手写的代码片段（命令式的一面）。

map 和 reduce 必须是"纯函数"（只依赖输入、无副作用），框架才能安全地在任意机器上、以任意顺序、失败后重跑地执行它们——这正是它能大规模并行与容错的前提。缺点是表达一个查询要拆成 map/reduce 两段代码，对本可一句 SQL 搞定的分析并不友好。所以后来出现了 SQL-on-Hadoop（如 Hive）和更高层的声明式接口，把用户从手写 map/reduce 里解放出来。这个例子提醒初学者：声明式与命令式不是非黑即白，而是一条光谱。（MapReduce 作为批处理框架的完整讨论属大主题 09-10，此处只用它说明查询范式的谱系。）

## 09-2.4 模型-负载匹配与多模数据库

### 09-2.4.1 按数据的关联结构选模型

选数据模型的第一性问题不是"哪个模型更先进"，而是"我的数据天然是什么形状、以及主要怎么被访问"。一个可操作的判据：数据以自包含的树/文档为主、且通常整体读写，倾向文档模型；数据是规整的、有大量多对一/多对多且需要灵活 join，倾向关系模型；数据是任意深度、任意类型的网状连接、常做多跳遍历，倾向图模型。

| 数据形状 / 访问模式 | 倾向模型 | 主因 |
|---|---|---|
| 自包含树、整体读写、关联稀疏 | 文档 | 局部性好、贴合应用对象、减少阻抗失配 |
| 规整表格、多对一/多对多、灵活即席查询 | 关系 | join 内建且优化良好、写时模式挡脏数据 |
| 异构、深度、多跳遍历、结构常演化 | 图 | 可变长路径为一等公民、加新关系类型不改 schema |

这张表是心智起点而非铁律。真实系统里同一个应用的不同数据块往往形状各异（比如用户档案偏文档、社交关系偏图、账务偏关系），不必强求一个模型通吃。DDIA 反复强调：模型是为数据服务的，别让数据去将就一个不合身的模型。

### 09-2.4.2 多模（multi-model）数据库

多模数据库指在同一个数据库产品里同时支持多种数据模型（如关系 + 文档 + 图），让你用一套系统、一套运维、甚至一套事务边界去处理不同形状的数据，而不必为每种模型各起一个专门数据库。前面提到的融合趋势（关系库内建 JSON、SQL/PGQ 让 SQL 直接查图）正是多模化的具体表现；也有产品从设计之初就主打多模。

它的吸引力在于减少"多套数据库"带来的运维负担、数据同步复杂度和跨库一致性难题。取舍则是"样样通可能样样不够精"：一个多模数据库在某一模型上的深度，通常不及该模型的专用系统（专用图数据库在超大规模深度遍历上的性能与工具链，往往强于关系库里的图扩展）。因此选型要看你对某一模型的需求有多重、规模有多大——需求是"顺带用一点"就多模很划算，需求是"这是核心且要压榨极致性能"则可能仍需专用系统。这里的产品能力与性能对比演进较快，具体请核对当时文档（待核）。

### 09-2.4.3 选型的常见误区

第一个误区是"跟风选型"：因为某种数据库当红就采用，而不看自己数据的形状与访问模式。第二个误区是"一个模型打天下"：强行把高度关联的数据塞进文档模型，最后在应用层手写一堆 join，或把树形数据硬拆成许多关系表制造无谓的阻抗失配。第三个误区是"把 schema 灵活当成没有 schema"：读时模式只是把结构约束移到了应用代码里，结构依然存在，只是不再由数据库替你守门，演化时的兼容责任落到了你身上。

数据关联密不密、查询要不要多跳、结构稳不稳定、是否需要强 schema 校验与事务、规模多大。把这些问题回答清楚，模型选择往往自然浮现；剩下的多模/专用之争，则看该模型对你是"主菜"还是"配菜"。这也呼应本大主题的总纲——先看数据与负载，再选模型与查询语言，而不是反过来被工具牵着走。
