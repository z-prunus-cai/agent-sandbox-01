这一份从"跨副本一致性选型"的应用视角出发：不教单机事务怎么用锁和日志实现（那在 L4-03 讲并发控制与恢复、L6-04 讲 MVCC 内幕与分布式事务协议），而是回答"我的应用该要多强的隔离、弱隔离会漏出哪些并发异常、为此要付什么代价"。核心心智模型是：数据库给的"事务"是一段可选强度的安全承诺，强度由隔离级别决定，级别越弱越快但漏洞越多，选型就是在"性能"和"我的业务能容忍哪些异常"之间定一个点。

## 09-7.1 事务的意义与"弱保证"常见误区

### 09-7.1.1 事务是什么：把一组读写打包成一个"要么全成、要么全不成"的单位

事务（transaction）是应用把若干读写操作组合成一个逻辑单元的方式，数据库对这个单元提供两类保证：这组操作要么整体成功提交（commit），要么整体失败回滚（abort/rollback）不留半成品；并且在并发和故障面前，这组操作看起来像是"独占地、完整地"执行过。事务的价值在于让应用不必自己去处理"写了一半崩溃了""两个人同时改同一行"这些棘手的部分失败与并发场景，把错误处理大幅简化成"重试整个事务"。

初学者常把事务理解成"一段被 BEGIN/COMMIT 包起来的 SQL"，这只是语法外壳。真正的内涵是那组保证。没有事务时，任何一步失败、任何一个并发交错，应用都要自己想清楚数据会停在什么中间状态、怎么补救；有了事务，数据库承诺你只会看到"全做了"或"全没做"两种干净状态之一。要注意事务不是免费的，也不是万能的——它提供的保证强度是可调的，很多默认配置给的保证比你以为的弱得多，这正是本章要揭穿的误区。

### 09-7.1.2 ACID 四个字母：一个被市场话术稀释的口号

ACID 是 Atomicity（原子性）、Consistency（一致性）、Isolation（隔离性）、Durability（持久性）四个词的首字母缩写，由 Härder 与 Reuter 在 1983 年为"给数据库容错保证起个统一名字"而确立。DDIA 的关键提醒是：ACID 如今更多是营销术语而非精确定义——不同数据库声称自己"ACID"时，各字母的实际含义、尤其是隔离性的实际强度，差别很大；与之相对的 BASE（Basically Available, Soft state, Eventual consistency）则更是一个"不是 ACID"的模糊标签。

逐字拆开看直觉。原子性说的不是并发（那是隔离性管的），而是"可中止性"：一个事务在中途出错时，已做的部分写入能被干净地丢弃，就像从没开始过。持久性说的是一旦提交成功，数据不会因为随后的崩溃而丢失（单机靠 WAL 落盘，多副本靠复制到多个节点，见 09-5）。隔离性说的是并发执行的多个事务互不干扰，理想形态是"看起来像一个接一个串行跑过"（可串行化）——但这正是实践中被大幅打折的一项。

四个字母里最"格格不入"的是一致性（C）。DDIA 明确指出：这里的一致性不是数据库能独立保证的性质，而是应用层面的不变量（invariant，如"账户余额之和守恒""每门课选课人数不超上限"）。数据库只提供原子性、隔离性、持久性这些工具，应用得靠正确使用它们来维持自己的不变量；一致性本质是应用的责任，被塞进 ACID 主要是为了凑成一个顺口的词。记住这一点能避免"数据库声称 ACID 所以我的业务规则自动被守住"的误解。

### 09-7.1.3 单对象操作 vs 多对象事务

事务的保证有两个作用范围要分清。单对象操作指对单独一行/一个文档/一个键的写入，几乎所有存储系统即使不叫"事务"也会对单对象写提供原子性和隔离性（例如写一个大 JSON 文档写到一半崩了不会留下半个文档，两个并发递增同一计数器不会互相覆盖）。真正需要"事务"这个词的是多对象事务：需要把跨多行、多表、多个文档的若干写入协调成一个原子单元，比如转账要同时借记一个账户、贷记另一个账户，二者必须同生共死。

这个区分对选型很重要。很多 NoSQL 系统早期只提供单对象原子操作，就宣称"支持原子性"，但缺多对象事务；如果你的业务有跨对象不变量（外键、多表冗余同步、多对多关系维护），单对象原子性远远不够。判断"我到底需不需要多对象事务"的方法是看有没有跨对象的不变量必须同时成立——有，就需要；没有，单对象原子写往往就够，还更容易扩展。

### 09-7.1.4 为何"有事务"不等于"安全"：默认隔离级别很弱

这是本大主题的题眼。理论上最安全的隔离级别是可串行化，但它代价高，所以绝大多数数据库默认并不开它。历史上很多系统默认是读已提交（如 PostgreSQL、SQL Server、Oracle），有些默认是快照隔离一类（MySQL/InnoDB 默认"可重复读"），而这些弱级别都会放过一整类并发异常——脏读虽被挡住，但不可重复读、丢失更新、写偏斜、幻读中的某些仍可能发生。也就是说，你写了 `BEGIN...COMMIT`，数据库照样可能让两个事务交错出你没预料的结果。

危险之处在于这些并发 bug 极难被发现。它们只在特定的并发时序下才触发，在低负载测试中几乎复现不出来，往往到生产环境高并发、且造成了数据损坏（钱少了、库存超卖）之后才被发现，且难以事后追查。DDIA 反复强调：不要假设"用了事务就安全"，而要具体问"我用的是哪个隔离级别、它会放过哪些异常、我的业务能不能容忍"。Oracle 甚至把它的隔离级别叫作"Serializable"，实际提供的却是快照隔离——名字和保证对不上，是另一个常见陷阱（见 09-7.2 命名辨析）。

### 09-7.1.5 事务的中止与重试：面向失败设计

事务模型的一大好处是把各种运行时错误统一成"中止 + 重试"这一种处理方式：网络抖动、死锁、约束冲突、乐观并发检测到冲突——数据库都以中止事务来响应，应用只要重试整个事务即可，无须为每种错误单独写补救逻辑。这是事务相较"手工处理部分失败"的核心简化价值。

但重试不是无脑循环，有几个易错点。如果事务实际已提交成功、只是提交确认在网络上丢了，盲目重试会导致重复执行（这引出 09-7.5 的幂等与去重）。如果失败是因为负载过载，立刻重试会雪上加霜，应加指数退避。如果事务里有对外部系统的副作用（发邮件、扣款），重试前要保证这些副作用本身幂等或可去重，否则数据库回滚了、邮件却发了两封。还有一类永久性错误（违反约束）重试多少次都不会成功，要能识别并放弃。可串行化快照隔离（SSI）这类乐观机制把"中止—重试"当成常规路径，所以应用侧写好幂等重试是用好它的前提。

## 09-7.2 弱隔离级别：读已提交、快照隔离/MVCC、防丢失更新

### 09-7.2.1 隔离级别谱与"异常↔级别"映射

隔离级别是数据库给并发事务的隔离强度分的档位，从弱到强越强越安全也越慢。理解它最好的方式不是背定义，而是记住"每个级别挡住哪些并发异常"。下表把常见异常与级别对应起来（本表以 DDIA 术语为主，兼列 SQL 标准与主流引擎差异，各来源命名不一处见本节命名辨析与来源与时效）：

| 异常现象 | 读未提交 RU | 读已提交 RC | 快照隔离 SI（多称"可重复读"） | 可串行化 |
|---|---|---|---|---|
| 脏写 dirty write（覆盖未提交的写） | 挡住 | 挡住 | 挡住 | 挡住 |
| 脏读 dirty read（读到未提交的值） | 可能发生 | 挡住 | 挡住 | 挡住 |
| 读偏斜 / 不可重复读（同一事务内两次读到不同值） | 可能发生 | 可能发生 | 挡住 | 挡住 |
| 丢失更新 lost update（读-改-写被覆盖） | 可能发生 | 可能发生 | 视实现（SI 常需额外机制） | 挡住 |
| 写偏斜 write skew | 可能发生 | 可能发生 | 可能发生 | 挡住 |
| 幻读 phantom | 可能发生 | 可能发生 | 部分挡住（对快照读）/ 视实现 | 挡住 |

这张表是本大主题的骨架：向下选级别就是在这张表里向左移，换来性能、放进更多异常。要特别注意 SI 那一列有几处"视实现/需额外机制"——快照隔离能干净挡住不可重复读，但对丢失更新、写偏斜、幻读的处理各家引擎不一致，这正是弱隔离最容易踩坑的地带，后面逐一展开。SQL 标准最初只定义了 RU/RC/RR/Serializable 四级、且用"哪些异常被禁止"来定义级别，但它的定义早于快照隔离被发明，导致"快照隔离到底算 RR 还是介于 RC 和 Serializable 之间"至今口径混乱。

### 09-7.2.2 读已提交（Read Committed）：不脏读、不脏写

读已提交是最常见的默认级别，提供两个保证：读的时候只会读到已提交的数据（无脏读），写的时候只会覆盖已提交的数据（无脏写）。脏读指读到另一个事务还没提交、随后可能回滚的中间值；脏写指两个事务的写交错，后写的覆盖了前一个尚未提交的写，导致数据混杂。RC 把这两样挡在门外，但仅此而已。

实现直觉能帮助理解它的边界。防脏写普遍用行级写锁：事务要改一行就先拿该行的排他锁，持有到提交，别人只能等，从而写与写串起来。防脏读则通常不用读锁（读锁会让读等写、影响并发），而是让数据库为每一行同时记住"当前已提交的旧值"和"正在被某事务修改的新值"，读操作一律返回旧值，直到那个事务提交。正因为读不加锁、每次读都取"当下最新已提交值"，同一个事务里先后两次读同一行，若中间别人提交了修改，两次会读到不同的值——这就是 RC 放过的"不可重复读/读偏斜"。

### 09-7.2.3 读偏斜（不可重复读）与它为何是个问题

读偏斜（read skew，也叫不可重复读，nonrepeatable read）指一个事务在执行过程中，同一份数据前后两次读到不一致的结果，或跨多行读到一个"从未同时存在过"的组合。经典例子：Alice 有两个各 500 元的账户，她在一个转账事务（从账户1转 100 到账户2）执行到中间时去查余额——先读账户1（已被扣，剩 400），转账事务此时提交，她再读账户2（还是 500，因为她读的是转账前的值……或读到已加的 600），于是她看到两账户合计 900 或 1100，凭空多出或少掉 100 元。数据其实没错（转账前后都守恒），但她这一瞬的快照跨越了另一个事务的提交点，看到了不一致的中间态。

在 RC 下这是允许发生的。对多数只读一两行的业务，读偏斜转瞬即逝、无伤大雅；但有三类场景不能容忍：备份（备份过程持续很久，期间不断有写提交，备份文件里就会混入"部分旧部分新"的不一致快照）、分析查询与完整性检查（扫描整库做统计，若期间数据在变，得出的数字自相矛盾）、以及任何需要"看到某一时刻整库一致视图"的操作。解决读偏斜正是快照隔离要解决的核心问题。

### 09-7.2.4 快照隔离（Snapshot Isolation）与 MVCC

快照隔离让每个事务从"它开始那一刻的、整个数据库的一致快照"中读取：事务全程看到的都是这个冻结时刻的已提交数据，别人后来的提交它一概看不见。这样同一事务内任意多次读都一致，读偏斜被彻底挡住；而且它的一大工程优点是"读不阻塞写、写不阻塞读"——长时间的只读分析查询可以和高频写入并发跑，互不等待。这使 SI 成为分析型/混合负载数据库的主流选择。

实现快照隔离的标准技术是 MVCC（Multi-Version Concurrency Control，多版本并发控制）：数据库为每一行保留多个带版本号（事务 ID）的版本，一个事务读某行时，按可见性规则挑出"在我的快照时刻已提交、且不晚于我"的那个版本返回。（版本链的具体存储、可见性判定、旧版本回收 vacuum 等实现内幕在 L6-04 04-9 讲，这里只用它的性质。）RC 可以看成 MVCC 的一个特例——它对每条读语句都取一个新快照，而 SI 对整个事务只取一个快照，区别就在快照的粒度。

命名辨析（本章头号大坑）：很多数据库把快照隔离叫作别的名字。PostgreSQL 和 MySQL/InnoDB 的"Repeatable Read（可重复读）"实际提供的就是快照隔离（各有细节差异）；Oracle 把快照隔离称为"Serializable"（但它并非真正可串行化，仍会放过写偏斜）。所以看到"Repeatable Read"或某家的"Serializable"时，不能望文生义，必须查该引擎该版本文档确认它到底挡住哪些异常。SQL 标准里的"Repeatable Read"定义模糊、早于 SI 出现，不能直接等同于快照隔离，两边口径都要记。

### 09-7.2.5 丢失更新（Lost Update）：读-改-写的经典竞态

丢失更新发生在两个事务同时对同一数据做"读—修改—写回"（read-modify-write）循环时：两者都读到同一个旧值，各自在其上做修改，先后写回，后写的覆盖了先写的，先写的那次修改就凭空消失了。典型场景：两个请求同时给同一计数器加一（都读到 42，都写回 43，本该 44 变成 43）；两人同时编辑同一 wiki 页面（各自基于旧文本改，后保存的整段覆盖前一个人的改动）；同时给购物车加不同商品却整体覆盖。

快照隔离本身并不能自动阻止丢失更新。SI 保证两个事务各自读到一致快照，但没规定"你写的东西不能覆盖别人在你快照之后提交的写"，所以两个 read-modify-write 仍可能互相覆盖。DDIA 列出的几种应对手段，选型时按场景挑：

原子写操作——把"读—改—写"交给数据库一步完成，如 `UPDATE t SET n = n + 1 WHERE id = ?`，数据库对该行加锁一气呵成，天然无丢失更新；能用原子操作就优先用，最简单可靠。

显式加锁——应用用 `SELECT ... FOR UPDATE` 把要改的行锁住再改，把并发的读-改-写串行化；适合逻辑复杂、无法用单条原子语句表达的情形，但要小心锁范围和死锁。

自动检测丢失更新——数据库允许并发的读-改-写并行，但在提交时检测到"这次更新基于的读已被别的提交作废"就中止该事务，让应用重试（PostgreSQL 的可重复读、以及 SI 下部分实现会这么做）。它对应用透明、不易漏，但需要应用配合重试。

CAS（compare-and-set，比较并设置）——写回时附带条件"仅当该值仍等于我读到的旧值才写"，否则失败重试；`UPDATE ... SET x=new WHERE x=old`。要注意在 SI/MVCC 下 CAS 的 WHERE 条件是否读的是快照旧值，可能让 CAS 失效，须确认引擎语义。

在多副本（多主/无主，见 09-5）环境下，加锁与 CAS 因为没有单一权威副本而失效，此时改用后写者取胜（LWW，会丢数据）或冲突合并（版本向量/CRDT）——这是把丢失更新问题推给了复制层解决。

- 一手（引擎默认级别）：PostgreSQL 官方文档"Transaction Isolation"（默认 Read Committed，"Repeatable Read"实为快照隔离）；MySQL 8 官方文档（InnoDB 默认 Repeatable Read）；Oracle 文档（其"Serializable"实为快照隔离）。核实 2026-08-01。
- ⚠ 命名分歧（两边都记）：DDIA 称为"快照隔离"者，PostgreSQL/MySQL 命名为"Repeatable Read"、Oracle 命名为"Serializable"；SQL 标准的"Repeatable Read"定义早于快照隔离、不等同之。属命名/口径分歧，非机制冲突。
- ⚙演进快 / 待核：各引擎各版本的默认隔离级别与在该级别下对丢失更新/写偏斜的具体处理（是否自动检测并中止）随版本变化，落到某数据库某版本须查对应版本文档，标「待核」。

## 09-7.3 写偏斜（write skew）与幻读（phantom）的成因与规避

### 09-7.3.1 写偏斜：丢失更新的一般化

写偏斜是比丢失更新更微妙的一类并发异常：两个事务读取了同一组对象（做了某个判断），然后各自去更新不同的对象，两次更新单看都合法，合在一起却破坏了一个跨对象的不变量。它是丢失更新的推广——丢失更新是"两个事务改同一个对象"，写偏斜是"两个事务基于同一份读，改不同对象"。因为改的对象不同，行级锁和 CAS 都拦不住它。

规则是"任意时刻至少留一名医生在岗"。当前 Alice、Bob 两人在岗，两人同时申请请假。两个事务并发执行，各自先查"现在在岗几人"——都读到 2（≥1，判断可以走人），于是 Alice 的事务把自己置为休假、Bob 的事务把自己置为休假，两个提交都成功。结果在岗人数变成 0，"至少一人在岗"的不变量被打破。每个事务单看都遵守了规则（我走的时候还有另一个人），但它们基于同一个"过时的读"各改各的，合起来出事。类似场景还有：会议室重复预订（都查到某时段空闲，各自订下）、账户余额跨转导致透支、抢注同一用户名、多人游戏移动到同一格。

写偏斜的时序骨架如下（两个事务基于同一读、写不同对象）：

```
事务 T1                              事务 T2
------                               ------
读: 在岗医生数 = 2 (Alice,Bob)
                                     读: 在岗医生数 = 2 (Alice,Bob)
判断 2 >= 1，可请假
                                     判断 2 >= 1，可请假
写: 设 Alice = off_call
                                     写: 设 Bob = off_call
提交 (成功)
                                     提交 (成功)
------------------------------------------------------
结果: 在岗 = 0，"至少一人在岗"被打破
两次写各改不同的行，行锁/CAS 拦不住；
问题出在"读到的前提"被对方的写作废了
```

### 09-7.3.2 幻读：一个事务的写改变了另一个事务的查询结果

幻读（phantom）指一个事务先执行一个"按条件搜索一批行"的查询，另一个事务插入（或删除、更新）了一行使其满足或不再满足该条件，导致前一个事务若再查会得到不同的行集——凭空多出或消失的行就是"幻影"。写偏斜的根子往往就是幻读：值班表例子里，事务读的是"满足'在岗'条件的行的集合/计数"，对方的更新改变了这个集合的构成，而这个"集合被改变"无法通过锁住某几行已存在的行来防止——因为你要防的是"还不存在或即将改变归属"的行。

幻读和不可重复读的区别要分清：不可重复读是"同一行"前后读到不同值，快照隔离能挡；幻读是"一个查询条件命中的行集合"发生变化，快照隔离对基于快照的只读查询能给出一致结果，但当事务读了集合、又基于该读去写时（写偏斜模式），SI 就挡不住了。这也是为什么"防幻读"通常要上更重的手段。

### 09-7.3.3 规避写偏斜/幻读的手段

按代价从轻到重，DDIA 给的规避路径如下，选型时结合业务频率与冲突概率挑：

真正可串行化的隔离级别——最省心、最彻底：把级别设为 Serializable（2PL 或 SSI 实现，见 09-7.4），数据库替你保证结果等价于某种串行执行，写偏斜和幻读都不会漏。代价是性能，但对正确性要求高、又不想手工加锁的业务这是首选。

显式物化冲突 + 加锁（materializing conflicts）——如果无法用可串行化，可以人为制造一个可以被锁住的行来代表"冲突点"。例如会议室预订，预先为"每个房间每个时段"建一行占位记录，预订时 `SELECT ... FOR UPDATE` 锁住对应时段行，把"是否冲突"变成对一个确实存在的行的争用，从而用行锁挡住写偏斜。这是把幻读转化成对已存在行的锁竞争，属"没有更好办法时"的手法，繁琐且易错，能用可串行化就别用它。

谓词锁 / 索引范围锁（predicate lock / index-range lock）——2PL 的实现用它来防幻读：不是锁具体的行，而是锁"满足某谓词条件的所有行（包括还不存在、将来可能插入的）"，工程上退化为锁一段索引范围。这是数据库内部实现可串行化时防幻读的机制，应用一般不直接接触，但要知道"可串行化能防幻读"背后靠的是它（细节在 09-7.4 与 L4-03 03-10 并发控制）。

对单主/单副本，上述手段都建立在"有一个权威节点能仲裁冲突"之上；在多主/无主复制下写偏斜更难防，往往只能靠业务层补偿或收敛到单点仲裁。

## 09-7.4 可串行化实现路径：真串行执行、两阶段锁（2PL）、可串行化快照隔离（SSI）

### 09-7.4.1 可串行化是什么、为什么值得

可串行化（serializability）是最强的隔离级别，它保证：即使多个事务并发执行，最终结果也等价于它们"按某种串行顺序一个接一个执行"的结果。它是唯一能一次性挡住前述所有并发异常（脏读、不可重复读、丢失更新、写偏斜、幻读）的级别——只要你把级别设成可串行化，就不用再逐一操心各种竞态，数据库替你兜底。

它的价值正在于"心智负担归零"：应用开发者可以假装没有并发、按单线程逻辑写业务代码，正确性由数据库保证。代价是性能与实现复杂度，所以历史上大量系统默认不开它。DDIA 指出可串行化在实践中有三条实现路径，各有适用场景，下面逐一说明。

### 09-7.4.2 路径一：真串行执行（Actual Serial Execution）

最简单粗暴的可串行化：干脆让所有事务在单个线程上一个接一个地串行执行，根本不并发，自然就"等价于串行"。这在多年里被认为不可行，但两个变化让它复活——内存变得足够便宜（活跃数据集能整个放进 RAM，省掉了等磁盘 I/O 的时间）、以及人们发现 OLTP 事务通常又短又快。代表系统有 VoltDB/H-Store、Redis（单线程命令执行）、Datomic。

要让真串行执行跑得快，有几个硬约束和配套设计。事务必须短小且不能中途等待外部（不能在事务里等用户输入、等网络往返），否则单线程会被一个慢事务堵死全局吞吐；因此这类系统要求事务以存储过程（stored procedure）形式一次性提交给数据库，数据库内部无 I/O 等待地跑完，而不是应用来回多次交互。为了突破单线程只用一个 CPU 核的瓶颈，通常按数据分区（见 09-6），每个分区一个单线程串行执行，跨分区事务才需要协调（代价陡增）。所以它的甜区是：数据能放内存、事务短、且大多数事务能限定在单分区内。

### 09-7.4.3 路径二：两阶段锁（Two-Phase Locking, 2PL）

2PL 是数十年来最经典的可串行化实现（注意别和分布式提交的 2PC 两阶段提交混淆，两者名字像、毫不相干）。规则是每个事务读一个对象要先拿共享锁（读锁，多个读可共享）、写一个对象要拿排他锁（写锁，独占），并且这些锁一旦获取就一直持有到事务结束才释放——"两阶段"指锁只增不减的加锁阶段、和提交时一次性全放的解锁阶段。读写互斥、写写互斥，从而强制并发事务串起来。为了防幻读，2PL 还需要谓词锁/索引范围锁去锁住"满足条件的行的集合"。

2PL 提供真正的可串行化，但代价明显。并发度低：读要等写、写要等读，长事务会长时间霸占锁、拖垮吞吐，延迟尤其是尾延迟很不稳定。死锁频繁：两个事务互相等对方持有的锁，数据库要检测死锁并中止其中一个让应用重试，中止—重试的开销在高冲突下很可观。因此 2PL 适合冲突不激烈、对延迟不极端敏感、又要强正确性的传统 OLTP；在高并发高冲突下它的性能塌陷正是 SSI 想改进的。

### 09-7.4.4 路径三：可串行化快照隔离（Serializable Snapshot Isolation, SSI）

SSI 是相对年轻（Cahill 等 2008 年提出，PostgreSQL 从 9.1 起实现）的乐观并发控制方案，目标是"既有快照隔离的高并发（读写互不阻塞），又达到完整可串行化"。做法是：事务照常在快照上乐观地跑（不加读写锁、不互相等待），数据库在后台追踪每个事务读了哪些数据、又有谁改了这些数据；到提交时刻检查——如果发现某事务提交会导致它"读到的前提已被别的已提交事务作废"（即形成了不可串行化的读写依赖环），就中止它、让应用重试。

和前两条路径对比能看清它的定位。相对 2PL（悲观：先抢锁防冲突），SSI 是乐观：先干起来、提交时才验，冲突少时性能大幅优于 2PL，因为没有锁等待和读写互斥。相对普通快照隔离，SSI 多做了"检测危险的读写依赖并在提交时中止"这一步，从而补上了 SI 放过的写偏斜和幻读，把 SI 升级成真正可串行化。它的代价是：冲突多时中止率高、白跑很多事务，且需要应用把"提交时被中止"当常规情况来写幂等重试逻辑（呼应 09-7.1.5）。适用甜区是冲突不太密集、又想要可串行化又不想牺牲太多并发的负载。

三条路径速览：真串行执行适合"数据入内存 + 事务短 + 可分区"；2PL 是通用、成熟、悲观，高冲突下慢；SSI 乐观、高并发下优，靠重试兜冲突。选型看你的冲突密度、事务时长和数据规模。

- 一手（SSI 原始文献）：Cahill, Röhm, Fekete, "Serializable Isolation for Snapshot Databases", SIGMOD 2008 / ACM TODS 2009——SSI 机制出处；PostgreSQL 官方文档确认自 9.1 起实现 SSI（其"Serializable"级别即 SSI）。核实 2026-08-01。

## 09-7.5 恰好一次（exactly-once）语义与幂等/去重

### 09-7.5.1 为什么"恰好一次"很难，且常被误解

在有故障和重试的系统里，一条操作可能被执行零次（丢了）、一次或多次（重复）。恰好一次（exactly-once）指"效果上等价于正好执行了一次"——不丢也不重。它难在：网络会丢包和超时，客户端发出请求后若没收到响应，无法区分是"请求没到、没执行"还是"执行了但响应丢了"，于是只能重试，而重试就可能造成重复执行（重复扣款、重复下单）。

真正的"恰好一次投递"在分布式下一般做不到，工程上追求的是效果恰好一次（effectively-once / exactly-once processing）——底层允许"至少一次"投递（会重复），但通过让重复不产生额外效果，使最终结果看起来像只执行了一次。也就是说，exactly-once 不是靠"保证只发一次"，而是靠"发多次也无所谓"来实现的。这一点想通了，后面的手段就都顺理成章。

### 09-7.5.2 幂等性（idempotence）：让重复执行无害

幂等操作指"执行一次和执行多次，效果相同"的操作。它是实现效果恰好一次的核心武器：只要操作幂等，客户端就可以放心重试，重复的那几次不会改变最终状态。天然幂等的例子如"把开关置为 on""把某字段设为固定值 x"（`SET x = 5` 无论跑几次结果都是 5）；天然不幂等的例子如"余额加 100""计数器加一"（跑两次就多加一次）。

工程上把不幂等的操作改造成幂等，常用的办法是给每个操作附一个唯一的操作 ID/请求 ID，服务端记录"哪些 ID 已处理过"，遇到已见过的 ID 就直接返回上次结果、不再重复执行。这样"加 100"这种非幂等操作，配上"这次加钱的请求 ID = abc123，若已处理过就跳过"，整体就变幂等了。要注意幂等常带条件与作用域：一个操作可能只在"数据处于某状态"时幂等（如"仅当订单未支付才标记支付"），且去重记录要覆盖到重试可能发生的时间窗口，太早清掉去重记录会让迟到的重试再次生效。

### 09-7.5.3 去重（deduplication）与操作标识

为每个逻辑操作生成一个稳定的、可在重试间保持不变的唯一标识（幂等键 / 去重键 / 操作 ID），接收方维护一个"已处理 ID"的集合，处理前先查、见过就丢弃或直接回放旧结果。这个 ID 必须由发起方在第一次发出时就固定、并在所有重试中原样携带（不能每次重试新生成，否则去重失效）。

落地时几个易错点。去重表本身的写入要和业务操作在同一个事务里原子完成——"处理业务"和"记下这个 ID 已处理"必须同生共死，否则可能业务做了但 ID 没记上，下次重试又做一遍；这正是把事务的原子性用在去重上。去重 ID 的保留期要覆盖最长可能的重试延迟，权衡存储成本与安全窗口。在消息/流处理里（呼应 09-11），"exactly-once"同样是靠幂等写 + 去重（或 checkpoint + 事务性写）达成的效果恰好一次，不是真的只投递一次。

### 09-7.5.4 端到端论证：恰好一次要贯穿整条链路

DDIA 强调恰好一次是一个端到端（end-to-end）性质：光靠某一层（比如消息中间件声称"exactly-once"）并不足以保证整体不重复，因为重复可能在任何一个环节（客户端重发、网关重试、消费者重启重放）引入。真正可靠的去重键/幂等逻辑必须一路贯穿到最终产生副作用、改变状态的那一层（数据库写、扣款、发货），在那里做最终的幂等判定。

中间任何一层的"恰好一次"承诺，都可能被它上游或下游的重试破坏；只有在"效果真正落地"的终点处，用一个从源头带下来的去重键做最终把关，才能保证整体效果恰好一次。这与网络里的端到端原则同源——可靠性最好在端点保证，而非指望中间每一跳。对应用开发者的落地建议：为每个会改变状态的关键操作设计稳定的幂等键，把去重判定和业务写放进同一个事务，别指望"我用了支持 exactly-once 的中间件所以不用管了"。
