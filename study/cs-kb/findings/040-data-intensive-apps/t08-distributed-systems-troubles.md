# L6-09·大主题09-8 分布式系统的麻烦

本报告讲一件让所有分布式数据系统头疼的事：一旦把数据放到多台机器上协作，你就必须面对单机世界里几乎不存在的一类问题——网络会丢包和拖延、机器的时钟各说各话、进程会毫无征兆地停顿好几秒。这些不是罕见的灾难，而是每天都在发生的常态。本大主题的目标不是教你怎么用共识算法解决这些问题（那属于分布式一致性理论，留给后续以算法证明为主的课程），而是先把"敌人"看清楚：分布式系统究竟会以哪些方式出错、为什么这些错误如此难以处理、以及工程上有哪些朴素但有效的应对直觉。

一条贯穿全章的心智模型要先立起来。单机程序是"要么全对、要么整个崩"——CPU 指令要么执行成功要么进程被杀，没有中间态，这种确定性让我们习惯了"结果可预测"。分布式系统打破了这个前提：一次跨网络的请求发出去后，可能成功、可能失败、也可能对方成功处理了但回复丢在了半路，而发起方无法区分这三种情况。这种"部分失败"（partial failure）加上"不确定性"（nondeterminism）就是分布式系统一切麻烦的总根源。本章围绕它拆成四个小主题：不可靠的网络、不可靠的时钟、不可预测的进程暂停，以及在这样一个充满谎言的环境里如何定义"真相"。全章的落脚点是一种务实态度——不要假装这些问题不存在，而要把容错建立在"最坏情况一定会发生"的假设之上。

## 09-8.1 部分失败与不可靠网络

### 09-8.1.1 部分失败：分布式系统区别于单机的根本

单机程序的故障是"全有或全无"：要么整台机器正常，要么整台机器宕掉，不存在"一半 CPU 在工作、一半坏了但你不知道"这种局面。分布式系统则天生带有部分失败——系统的某些部分坏了，另一些还在正常运转，而且没有任何一个节点掌握全局状态，因此谁也说不清到底哪里坏了、坏没坏。

理解这一点是理解整章的钥匙。单机的确定性来自"共享内存 + 同一时钟 + 同生共死"：一条指令的结果立刻可见，出错就整体崩溃，你不必怀疑"这条指令到底执行了没有"。一旦跨越网络，这三个前提全部消失。部分失败最折磨人的地方不是"会失败"，而是"不确定"——你发出一个请求却收不到回复时，根本无法判断是请求没送到、对方没处理，还是对方处理完了但回复丢了。构建可靠分布式系统的核心任务，就是用一堆不可靠的部件搭出一个整体上仍可预期的服务，而第一步是承认并直面这种不确定性，而不是假装它不存在。

### 09-8.1.2 无共享架构与不可靠网络

本章讨论的对象主要是"无共享"（shared-nothing）架构：一堆各自独立、只通过一个不可靠的网络互相发消息的机器，彼此不共享内存也不共享磁盘。这是当今互联网服务和多数分布式数据库的主流形态，因为它便宜、易扩展、云上现成。

选无共享架构的代价，就是要把网络当作系统里最不可信的一环来对待。这类网络绝大多数是异步分组网络（asynchronous packet network）：一个节点把消息发出去，网络不保证它何时到达、甚至不保证它会到达。可能发生的坏事有一长串——请求在路上丢失、请求排在某个拥塞队列里迟迟发不出去、远端节点已经挂了、远端节点只是暂时卡住稍后才响应、或者对方明明处理完了但回复在返程中丢失。对发送方而言，这些情况在"迟迟收不到回复"这个表象上完全一样，无法分辨。

### 09-8.1.3 超时与宕机不可区分

当你向一个远端节点发请求却在预期时间内没等到回复，你唯一能做的动作是等待超时（timeout）然后放弃。但超时给不出诊断：它无法告诉你对方究竟是彻底宕机了、还是只是慢、还是回复正在路上。"超时"和"对方已死"在信息上是不可区分的两件事。

```
发送方视角下无法区分的几种情况（都表现为"没按时收到回复"）：

  [请求丢失]     发送方 --X          节点          请求根本没到
  [节点已宕]     发送方 ---->  [节点已死]           没人处理
  [节点很慢]     发送方 ---->  节点(卡住)           稍后才会处理
  [回复丢失]     发送方 ---->  节点(已处理) X-->    对方做了但你不知道

  → 在发送方眼里，以上四种在"超时"这一刻长得一模一样。
```

这个"不可区分"是分布式系统最反直觉、也最危险的地方。它带来一个直接的两难：如果对方其实还活着，你却因为超时而重发或转移它的工作，就可能造成重复执行（比如同一笔转账被扣两次）；反过来，如果你一直傻等一个已经死掉的节点，整个系统就被它拖死。后面讲的幂等、fencing token、法定人数判定，本质上都是在这个"分不清死活"的前提下，尽量把危害控制住的手段。要牢牢记住：网络上收不到回复，永远不能被解读为"对方一定没做"。

### 09-8.1.4 现实中的网络故障

网络故障不是理论上的可能性，而是经过大量运营数据证实的常态。DDIA 引用的多项研究表明，即便在管理良好的数据中心内部，交换机、网卡、配置错误、链路抖动等导致的网络异常也频繁发生；有的故障还很诡异，比如网络单向可达（A 能发给 B，但 B 发不回 A）、或者出现网络分区（network partition，一部分节点与另一部分被切断，各自都以为对方死了）。

不要因为"我们用的是高质量数据中心网络"就假设网络可靠。哪怕故障率很低，只要系统规模足够大、运行时间足够长，罕见故障就会变成日常事件。工程上正确的姿态是主动测试系统在网络异常下的行为——刻意注入丢包、延迟、分区（这类做法即"混沌工程"的一部分），看系统会不会做出危险决定，而不是等生产环境替你暴露问题。一个从没在网络故障下被测过的容错机制，等同于没有容错机制。

### 09-8.1.5 检测故障的难处

很多系统需要自动检测节点死活：负载均衡要把死节点摘掉、单主复制要在主库挂掉时选新主。但由于上面说的不确定性，你无法可靠地判定一个节点是真死了还是只是慢。有时你能拿到一点明确的坏消息——比如目标机器进程已退出，操作系统会回一个 TCP RST 或 ICMP "端口不可达"；但在很多情况下你什么明确信号都拿不到，只能靠"多久没响应"来猜。

因此故障检测在根子上是一种基于超时的猜测，而不是确定性的判断。这带来一个绕不过去的取舍：超时设得短，能快速发现真故障、缩短不可用窗口，但更容易把只是暂时卡顿的健康节点误判为死亡，触发不必要的故障切换（可能引发数据重复处理或雪崩式转移负载）；超时设得长，误判少了，但真出故障时用户要等更久才恢复。没有一个"正确"的超时值——它是延迟与误判之间的权衡，且依赖具体系统的延迟特征。

### 09-8.1.6 超时时长与网络延迟的抖动

要设一个合理的超时，理想上你得知道"正常往返最多要多久"，但异步网络恰恰不给这个上界。真实网络的延迟高度可变：队列排队（queueing）是延迟抖动的头号来源——交换机端口拥塞时分组要排队、目标机器 CPU 忙时请求要排队、虚拟化环境里整个虚拟机可能被暂停几十毫秒。负载越高，延迟的方差越大。

```
往返延迟的分布（示意，非某具体网络实测值）：

  概率
   │      ╭─╮  多数请求很快
   │     ╱   ╲
   │    ╱     ╲___
   │   ╱          ╲________ 长尾：偶发的高延迟（拥塞/暂停）
   └───┴──────────┴──────────────→ 延迟
       常态         尾部（可达常态的数十倍甚至更多）
```

正因为延迟有这样一条"长尾"，用固定常量当超时往往两头不讨好。更稳妥的做法是持续测量实际响应时间的分布（例如观察一段时间内的抖动 jitter），据此动态调整超时——这也是成熟系统（如一些故障检测器）采用自适应超时的原因。这里要建立的直觉是：网络延迟不是一个"值"而是一个"分布"，任何对"最多多久"的硬性假设，在长尾面前都可能被打脸。数值层面，尾部相对常态可放大到数十倍乃至更多，但具体倍数强依赖网络与负载，属「待核」，不宜当作固定结论。

### 09-8.1.7 同步网络 vs 异步网络

有没有可能造出一个"延迟有确定上界"的网络？有——传统电话网络的电路交换（circuit-switched）就是这样：通话建立时预留一条固定带宽的电路，数据以恒定速率流动，延迟有界且稳定，这类叫同步网络（synchronous network）。相比之下，互联网和数据中心用的是分组交换（packet switching）的异步网络，带宽按需动态共享，代价就是延迟无界。

这个对比解释了"为什么我们不干脆用同步网络省掉所有麻烦"。答案是取舍：电路交换为突发流量预留固定带宽会造成严重浪费，而分组交换按需复用带宽、吞吐利用率高得多，代价是放弃了延迟上界。互联网选择了后者——它是为"高吞吐、能容忍延迟波动的批量数据"优化的，而不是为"每个分组都准时到达"优化的。所以无界延迟不是工程没做好，而是这类网络的设计取舍所固有的。理解这点就能接受：在异步网络上，任何算法都不能假设消息在有限时间内一定送达，容错设计必须以此为前提。

## 09-8.2 不可靠的时钟

### 09-8.2.1 时钟的两类用途与两类时钟

时间在系统里有两种截然不同的用法，混淆它们是很多 bug 的根源。一类是问"现在几点"这种时间点（point in time），用于给日志打时间戳、判断缓存是否过期、显示"3 分钟前"；另一类是量"过了多久"这种时间段（duration/interval），用于测量请求耗时、判断超时。对应地，计算机里有两种时钟：墙钟（time-of-day clock，也叫实时时钟）和单调钟（monotonic clock）。用错时钟会出微妙且难查的错。

关键在于两种时钟解决的问题不同、保证也不同。墙钟回答"现在是 UTC 几点几分"，它可以和外部标准（NTP）对齐，因而能跨机器比较，但也正因为要对齐外部时间，它可能被向前或向后猛地跳一下。单调钟只保证读数单调不减、用来测两次读数之间的间隔，它的绝对值毫无意义、不能跨机器比较，但测"过了多久"很可靠。记住一句话：要"几点"用墙钟，要"多久"用单调钟——把这两件事分清，能避开一大类时间相关的坑。

### 09-8.2.2 墙钟（time-of-day clock）

墙钟返回按某个日历（通常是 UTC）计的当前日期和时间，例如 Java 的 `System.currentTimeMillis()`、Linux 的 `clock_gettime(CLOCK_REALTIME)`。它通常与 NTP 同步，因此不同机器的墙钟原则上应该大致一致。

墙钟的致命缺陷是它会跳变。当 NTP 发现本地墙钟与服务器偏差太大时，可能把本地时间猛地向前拨、甚至向后拨；机器重启、手动改时间、闰秒调整也会造成跳变。所以墙钟不适合测量时间间隔——如果你用两次墙钟读数相减来算一段代码耗时，恰好中间发生一次 NTP 回拨，你可能算出一个负的耗时。这也是为什么墙钟不能用来给分布式事件可靠排序：两台机器的墙钟即使都同步过，仍会有毫秒级偏差，且各自都可能跳变，"谁的时间戳大谁就更晚发生"这个假设并不成立。

### 09-8.2.3 单调钟（monotonic clock）

单调钟保证读数永远向前、不会倒退，适合测量时间段。典型 API 是 Linux 的 `clock_gettime(CLOCK_MONOTONIC)`、Java 的 `System.nanoTime()`。你在操作开始和结束各读一次、相减就得到可靠的时长；NTP 的校正只会平滑地微调它前进的速率（slewing），而绝不会让它倒退或猛跳。

要理解它，抓住"绝对值无意义、差值才有意义"这一点。单调钟的读数本身可能是一个自开机以来的任意大数字，你不能拿它跟别的机器比、也不能解读成"几点"；它唯一的用处是同一台机器上两次读数相减。多核机器上每个 CPU 可能有各自的计时器，操作系统会做补偿以维持单调假象。凡是"测超时、测延迟、限流窗口"这类需求都该用单调钟，用墙钟去测会在时钟跳变时出灵异 bug。

### 09-8.2.4 时钟同步的准确性问题

墙钟要有用就得和真实时间对齐，这靠 NTP（Network Time Protocol）向时间服务器请求校正。但这个过程本身充满误差，DDIA 列举了一长串来源：机器的石英晶振会漂移（drift），随温度变化时快时慢；如果本地时钟偏离 NTP 太远，可能被拒绝校正或被强制跳变；网络往返延迟给 NTP 校正设了精度下限，拥塞时误差更大；闰秒会制造一分钟有 61 或 59 秒的诡异分钟，曾搞崩过不少系统；虚拟机里的时钟在 VM 被挂起时会"冻结"，恢复后突然跳一大段。

这些误差合起来意味着：你永远不知道自己的墙钟到底偏了多少，而且这个偏差是会变的。给几个量级感受一下（均为文献常见值，随硬件与配置变化，属 ⚙演进快·随时变）：普通石英钟漂移常在数十 ppm 量级（一天一同步约漂移 2–3 秒）；而常被引用的"一天一同步约漂移 17 秒"其实对应约 200 ppm 的最坏假设（Google 在其分布式数据库设计中即取此值）——换算关系是 1 ppm≈0.0864 秒/天，故 17 秒/天正是约 200 ppm，而非数十 ppm；而 NTP 跨公网同步的误差在网络良好时可低至数十毫秒、拥塞时可达到秒级。这些具体数字不要当作精确常量记忆，重点是结论：墙钟带着一个未知且波动的误差，任何"两台机器时间戳可直接比较"的设计都建立在流沙上。

### 09-8.2.5 用时间戳排序事件的陷阱

一个极常见的错误用法是拿墙钟时间戳给跨节点的事件排序，尤其是无主/多主复制里的"最后写入胜出"（last-write-wins, LWW）冲突解决——两个节点各自给自己的写打上本地墙钟时间戳，谁的时间戳大就保留谁。问题是两节点的墙钟有未知偏差，时间戳大的那个不一定是真正后发生的那个，于是 LWW 会悄悄丢掉本应保留的写入。

```
LWW 因时钟偏差而丢写（时序示意）：

  真实先后：  写A(节点1) ───先───▶  写B(节点2) ───后───▶
  节点1墙钟快了几十毫秒：
     写A 打上时间戳 t=100
     写B 打上时间戳 t= 99   （节点2墙钟偏慢）
  → LWW 比时间戳：100 > 99，判定"A 更新"，B 被丢弃。
  → 但 B 其实发生在 A 之后，真正该保留的 B 被静默丢失。
```

这个陷阱的杀伤力在于它无声无息：没有报错、没有崩溃，只是数据莫名其妙少了一条，事后极难复现和归因。根子上，物理时钟无法可靠表达事件之间的"先后（happens-before）"因果关系。正确的替代是用逻辑时钟（logical clock，如版本向量/version vector）来捕捉因果序——它不依赖任何物理时间，只靠事件间的依赖关系计数，因而不受时钟偏差影响（版本向量的细节属复制冲突解决话题，见 09-5）。这里的教益是：需要"谁先谁后"时，别信墙钟，要用逻辑时钟。

### 09-8.2.6 时钟读数的置信区间与 TrueTime

既然墙钟带着未知误差，一个更诚实的做法是：不要把时钟读数当成一个精确的点，而当成一个区间——"现在大约在 t 之前 x 毫秒到 t 之后 y 毫秒之间"。多数系统的时钟 API 并不暴露这个不确定区间，于是程序员误以为读数是精确的。Google 的 Spanner 用 TrueTime API 显式返回一个时间区间 [earliest, latest]，并靠原子钟/GPS 把区间压得很窄。

理解这个思路，关键是"承认不确定并把它量化"。Spanner 在提交事务时会主动等待一小段时间（commit-wait），直到确信这个不确定区间已经过去，从而保证两个事务的时间戳区间不重叠、可以据此安全排序。这属于分布式一致性实现的范畴，本报告只引其结论、不展开机制：把时钟不确定性显式建模，是把"物理时间"安全用于排序的前提；而绝大多数没有原子钟的系统拿不到足够窄的区间，因此不该依赖墙钟做强一致的排序。TrueTime 的具体精度依赖 Google 的专用硬件与部署，属特定实现，不作通用数值结论。

### 09-8.2.7 时钟用于分布式快照

数据库里的多版本并发控制、可重复读快照等都需要给事务一个单调递增的"时间戳"来标识版本先后。诱惑在于直接拿墙钟当这个时间戳，因为它"看起来"是全局的。但正如前面所说，跨节点墙钟不可靠，直接这么做会破坏快照的正确性。

因此单机数据库通常用一个逻辑计数器（如自增事务 ID）而非墙钟来生成版本号，因为在单机上这个计数器天然全局有序、无误差。到了分布式场景，如何生成一个"既全局单调又高效"的时间戳就成了难题——要么引入一个中心化的定序器（可能成为瓶颈），要么像 Spanner 那样用带界的物理时间。这里要带走的认识是：把时钟用于版本排序时，"逻辑单调"比"物理准确"更重要，天真地用墙钟当版本号是分布式数据系统里的经典反模式。

## 09-8.3 进程暂停与响应时间保证

### 09-8.3.1 进程暂停如何破坏"我还持有锁"的假设

设想一个持有分布式租约（lease）的节点，它周期性续租、并在自认为持有租约时对存储写入。危险场景是：这个节点在两条语句之间被暂停了很久（比如卡住 15 秒），期间租约早已过期、别的节点已被推举接管；等它恢复过来，它对此一无所知，仍以为自己持有租约，继续写入——于是两个节点同时以为自己是唯一的写者，造成数据损坏。

```
进程暂停导致"两个持锁者"（时序示意）：

  节点1:  拿到租约(有效30s) ──写…──▶ [长暂停15s+] ──▶ 恢复,以为仍持租约 → 写!
  租约:   ─────────────────────过期──────────────────────────────
  节点2:              (发现租约过期) 接管,成为新持有者 ──写──▶
  结果:   同一时刻节点1与节点2都在写 → 数据损坏
```

这个例子把前两小主题的麻烦串了起来：节点自己无法感知"我刚才被暂停了多久"，就像收不到回复的发送方无法感知对方死活一样。它教给我们一条硬道理：任何"我在 X 时刻检查过租约还有效，所以现在写入是安全的"的推理都是错的——检查和写入之间可以插进一段任意长的暂停。这正是下一小主题 fencing token 要解决的问题。

### 09-8.3.2 进程暂停的来源

进程可以在任意一条指令之间被暂停任意长时间，而代码对此毫无察觉。DDIA 列了一串常见来源：垃圾回收（GC）的"stop-the-world"停顿会冻结所有应用线程，大堆场景下偶尔可达数秒；虚拟机可以被挂起再恢复（live migration 时整个 VM 冻结）；操作系统的抢占式调度可能把线程切走很久；操作系统换页（paging/swapping）时一次内存访问可能触发磁盘 I/O 而卡住；笔记本合盖、发送 SIGSTOP 信号等也会冻结进程。

这些暂停对被暂停的代码是完全透明的——它不会收到"你刚被冻了 10 秒"的通知，从它自己的视角看时间是连续的，一条语句执行完紧接着下一条，只是墙上的时钟已经过去了很久。这就和"一个线程运行在有界延迟的实时系统里"的假设彻底冲突。所以在普通服务器上，你不能假设"两行相邻代码之间只过了几微秒"，也不能靠"我刚才还活着"来推断"我现在还持有资源"。把服务器线程想象成随时可能被按下暂停键、且不知道自己被按过——这个心智模型能帮你写出更防御性的代码。

### 09-8.3.3 响应时间保证与实时系统

有没有办法彻底消除这类暂停？在硬实时（hard real-time）系统里可以——飞机、汽车、工业控制这类场景，软硬件全栈都为"最坏情况执行时间有确定上界"而设计：用实时操作系统（RTOS）、避免会引入不确定停顿的动态内存分配、GC 要么禁用要么用有界暂停的实现，并做详尽的最坏情况分析。

但这套东西代价极高、开发效率极低，且吞吐通常更差，所以绝大多数服务端/数据系统并不采用。要建立的直觉是：实时不等于"快"，而是"准时"——它保证的是响应时间的上界确定，哪怕平均更慢。对普通分布式数据系统而言，追求硬实时既不现实也无必要；正确的路线不是消灭暂停，而是承认暂停会发生，并让系统在某个节点被暂停时仍不出错（这又回到 fencing、幂等、法定人数这些"容忍而非杜绝"的手段）。

### 09-8.3.4 限制垃圾回收影响的手段

既然 GC 停顿是服务端最常见的暂停来源之一，工程上有若干缓解办法。DDIA 提到的思路包括：把 GC 停顿当作节点的一次计划内短暂"下线"来对待——在一个节点即将做长 GC 前，先让负载均衡把请求路由到别的节点、等 GC 完再放回；或者只用 GC 回收短命对象、对长命对象改用定期重启进程来清理（rolling restart），从而把大停顿变成可控的、错峰的、不影响可用性的事件。

理解这些手段的共同思路很有价值：它们都不试图消灭停顿，而是把停顿变得可预测、可调度，让它发生在不伤害用户的时刻。这与全章的务实哲学一致——不可靠的部件不可能变可靠，但可以通过编排让系统整体表现得可靠。具体 GC 算法的停顿量级随语言运行时、堆大小、回收器实现（如不同的低延迟回收器）差异极大且持续演进，属 ⚙演进快·随时变，本文不给固定数值，仅记结论：把 GC/暂停当作"会发生的运维事件"来主动管理，而非当作"不该发生的意外"。

## 09-8.4 知识、真相与谎言

### 09-8.4.1 真相由多数决定

既然单个节点既不能信任网络、也不能信任自己的时钟、还随时可能被暂停，那么在分布式系统里"什么是真的"就不能由任何单个节点说了算。DDIA 给出的答案是：真相由多数决定（the truth is defined by the majority）——系统靠一组节点投票，只有获得法定多数（quorum，通常是过半数）同意的判断才算数。

这条原则是分布式容错的基石，直觉其实很朴素。一个节点可能因为网络分区而"感觉"自己被全世界抛弃，但它无权单方面宣布自己或别人的死活；反过来，别的节点也可能一致认为它已经死了（哪怕它其实还活着，只是网络到它的链路断了）。让多数派来裁决，就能避免"少数派各说各话"造成的分裂——因为任何两个多数派必然有交集，不可能同时存在两个互相矛盾的多数决定。这正是为什么 quorum 要求过半数，也是为什么下面的领导者选举、锁分配都要挂靠在多数派共识之上。至于"如何让多数派达成一致"本身（即共识算法），属分布式一致性理论，本报告只用其结论、不展开证明。

### 09-8.4.2 领导者与锁：一个节点可能不知道自己已被废黜

很多系统里某个角色需要唯一性：只能有一个主库接受写、只能有一个节点持有某把锁、只能有一个消费者处理某个分区。危险在于，一个节点常常错误地相信自己仍是那个"天选之子"，哪怕多数派早已选出了别人。前面进程暂停的例子就是典型——旧主被暂停期间新主已上任，旧主醒来仍以为自己是主。

要抓住的核心矛盾是：一个节点的自我认知，和多数派对它的认定，可能不一致，而且它自己无从得知这种不一致。它可能因为 GC 停顿、网络分区而在"客观上"已被取代，但在"主观上"毫不知情，继续行使早已被收回的权力。仅靠"节点自己检查一下我还是不是主"解决不了问题，因为检查完到行动之间又可能被暂停。于是必须有一个不依赖节点自觉的外部机制，在写入的那一刻拦住过期的旧主——这就是 fencing token。

### 09-8.4.3 fencing token（防护令牌）

fencing token 是一个每次授予锁/租约时都会递增的单调数字。持有者每次去访问被保护的资源（如存储服务）时，必须带上自己拿到的 token；资源端记住见过的最大 token，并拒绝任何携带比它小的 token 的请求。这样即使一个过期的旧持有者醒来后还想写，它手里的是旧（更小）的 token，会被存储端直接拒绝。

```
fencing token 拦截过期写入（时序示意）：

  客户端1: 获锁,拿到 token=33 ──[长暂停]────────▶ 带 token=33 写存储 → 拒绝!
  客户端2:            获锁,拿到 token=34 ── 带 token=34 写存储 → 接受(存储记住 max=34)
  存储端规则: 只接受 token ≥ 已见最大值；33 < 34 → 客户端1的迟到写被挡下
```

fencing 的精妙之处在于，它把"判断谁有权写"的责任从不可信的客户端，转移到了资源端这个单一裁判点。客户端可以撒谎、可以被暂停、可以自以为还持锁，但它无法伪造一个更大的 token（token 由授予锁的服务单调发放）。这样即便客户端的自我认知是错的，错误也会在写入的最后一刻被资源端挡下。要用好 fencing，前提是资源端必须真的检查 token——只发 token 不检查等于没用；这也是很多"分布式锁"看似安全实则不安全的原因（锁服务给了保证，但被保护的资源没配合检查）。fencing 的适用性依赖资源端支持带 token 的条件写，某些外部系统不支持时就需要别的办法，这属工程落地细节。

### 09-8.4.4 拜占庭故障

前面所有讨论都默认一个"善意"假设：节点可能宕机、可能慢、可能失联，但只要它响应，它说的就是实话——它不会故意撒谎或发送恶意伪造的消息。这种"节点要么正确要么沉默"的故障模型叫崩溃故障（crash/fail-stop 或 fail-crash）。而拜占庭故障（Byzantine fault）指更坏的情况：节点可能任意行为，包括故意发送矛盾的、错误的、恶意伪造的消息来欺骗其他节点。能在存在拜占庭节点时仍正确工作的系统叫拜占庭容错（Byzantine fault tolerant, BFT）。

"拜占庭"这个名字来自"拜占庭将军问题"（Byzantine Generals Problem）——几位将军要靠信使协调进攻，其中可能有叛徒故意传假消息，如何让忠诚的将军仍达成一致。理解这个模型的关键是分清适用边界：在一个受你自己掌控的数据中心内部，节点通常被假设为"非恶意"（硬件坏了会宕机，但不会主动骗人），所以多数分布式数据库不做拜占庭容错，因为 BFT 协议代价高得多（通常需要更多冗余节点、更复杂的多轮投票）。真正需要 BFT 的是参与方互不信任的场景，比如去中心化的区块链、航天器（宇宙射线可能翻转比特造成"错误但非恶意"的行为）、多组织协作系统。对绝大多数企业内部数据系统，工程上的正确判断是：假设崩溃故障、不假设拜占庭，把资源花在防网络/时钟/暂停这些真实高频的麻烦上。

### 09-8.4.5 系统模型：对时序与故障的假设

要在这样一个不可靠的世界里论证"我的算法是对的"，得先把假设写清楚。DDIA 把假设分成两个维度。时序假设有三档：同步模型（synchronous，假设网络延迟、暂停、时钟误差都有已知上界——现实中几乎不成立）、部分同步模型（partially synchronous，系统大多数时候表现同步、但偶尔会超出上界——最贴近现实）、异步模型（asynchronous，不对时序做任何假设，连超时都不能用）。故障假设也有几档：崩溃-停止（节点崩了就永久消失）、崩溃-恢复（节点可能崩溃后带着持久化状态重启回来）、拜占庭（节点任意作恶）。

一个算法的"正确性"永远是相对于某个模型而言的，脱离模型谈对错没有意义。现实世界最常用的组合是"部分同步 + 崩溃-恢复"——它承认网络和暂停偶尔会失控、承认节点会崩溃后又回来，同时不假设恶意，这恰好匹配数据中心内部的真实情况。选模型是一种取舍：模型越弱（假设越少、越贴近现实），算法越难设计但越健壮；模型越强（假设越多），算法越好写但越容易在现实中被打破。设计或选型分布式系统时，先问清楚"它假设的是哪个模型"，能帮你判断它在你的环境里到底靠不靠谱。

### 09-8.4.6 算法正确性：安全性与活性

评判一个分布式算法是否正确，通常从两类性质入手。安全性（safety）意为"坏事永不发生"——比如"绝不会有两个节点同时被授予同一把独占锁"；活性（liveness）意为"好事最终会发生"——比如"请求最终一定会得到响应"。这两个词是分布式算法讨论里的标准术语，值得先建立印象。

安全性一旦被违反就无法挽回（脏数据已经写下去了、钱已经被扣两次了），而活性的违反通常只是"暂时卡住、还没好"，往往能靠等待或重试恢复。因此工程上通常把安全性看得比活性更重——宁可系统暂时不可用（牺牲活性），也不能返回错误结果或损坏数据（守住安全性）。这也解释了很多系统在网络分区时的选择：宁愿拒绝服务，也不愿在无法确认多数派的情况下贸然写入。至于如何形式化证明某算法满足这些性质，属分布式一致性理论的范畴，本报告仅点到概念、不做证明。
