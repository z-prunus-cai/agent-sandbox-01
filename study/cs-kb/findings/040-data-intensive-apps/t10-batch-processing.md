MapReduce 与 HDFS 是 2000 年代的开创性技术，如今在生产中已大量被 Spark/Flink 等取代，但它们奠定的思想（把计算移到数据、物化中间结果换容错、不可变输入可重跑）仍是理解一切现代批处理引擎的地基，所以先讲透它，再讲后继者如何改进它。

## 09-10.1 Unix 哲学与批处理思想

### 09-10.1.1 三类系统：服务、批处理、流处理

理解批处理，先要把它和另外两类系统摆在一起区分。**在线服务（online service / online system）**等待客户端请求，收到就尽快处理并返回，最看重响应时间与可用性。**批处理系统（batch processing / offline system）**接收一大批已经攒好的输入数据，跑一个作业把它处理完，产出结果，通常由定时调度触发（比如每天凌晨跑一次），最看重吞吐量，用户不会守在旁边等。**流处理系统（stream processing / near-real-time system）**介于两者之间：输入像批处理一样是"数据"而非"请求"，但不是一次性给定，而是事件持续不断地到达，处理在事件出现后不久就发生（09-11 详述）。

初学者容易把"批处理"简单理解成"慢"或"离线"，但更本质的区分是**输入是否有界**。批处理的输入是一份大小已知、内容固定的数据集；这一点决定了它能采用很多流处理和在线服务用不了的策略——比如整份重排序、失败了整段重跑、结果一次性输出。抓住"有界输入 + 追求吞吐 + 可整体重跑"这三点，后面所有机制都能顺下来。

### 09-10.1.2 从 Unix 工具链看批处理的雏形

批处理的思想最早不是从大数据来的，而是从 Unix 命令行工具来的。DDIA 用一个经典例子开场：分析 Web 服务器日志，统计访问量最高的 5 个页面。用 Unix 工具一行管道就能完成：

```
cat access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -n 5
```

这条命令的思路——`awk` 抽出 URL 字段、`sort` 把相同 URL 排到一起、`uniq -c` 数每组出现次数、再 `sort -rn` 按次数倒序、`head` 取前 5——正是一个完整的批处理作业：读入一份固定的日志文件，做投影、分组、计数、排序、取 Top-N，输出结果。

这个小例子里藏着批处理的两个关键手法。其一，**排序是分组的前提**：要统计每个 URL 出现几次，先把相同 URL 排到相邻位置（`sort`），分组就变成了"扫一遍、遇到不同的就换组"（`uniq`）。这个"排序 → 顺序扫描分组"的套路，正是后面 MapReduce 里 reduce 侧 join/分组的核心（09-10.3）。其二，Unix 的 `sort` 能处理**大于内存的数据**：它在内存不够时会把中间结果溢写到磁盘、分块排序再归并（外部归并排序），并且能利用多核并行——这正是大数据排序要解决的同一个问题，只是规模从单机放大到了集群。

### 09-10.1.3 Unix 哲学：统一接口、逻辑与配线分离

Unix 工具能像上面那样自由拼接，靠的是一套设计哲学，它直接被 MapReduce 等批处理系统继承。核心有几条。**统一接口**：所有 Unix 工具都读写"字节流 / 文本行"这一种格式，所以任意两个工具都能用管道 `|` 串起来，上一个的输出就是下一个的输入。**逻辑与配线分离（separation of logic and wiring）**：程序本身只管从 stdin 读、往 stdout 写，至于输入从哪来、输出到哪去，由外部（shell 的管道、重定向）决定，程序不关心。**做好一件事**：每个工具功能单一（`sort` 只排序、`grep` 只过滤），组合起来解决复杂问题。

这套哲学的价值对初学者最直观的一点是**可组合性与可实验性**：因为接口统一、逻辑与配线分离，你可以在管道任意位置插入 `| head` 看看中间结果、或把某一段输出重定向到文件反复调试，而不用改任何一个工具的代码。MapReduce 把这套思想搬到了集群：把"计算逻辑"（map/reduce 函数）和"数据从哪读、往哪写、怎么在机器间搬"（框架负责的配线）彻底分开——你只写逻辑，框架管配线。这也是它相比手写分布式程序易用得多的根本原因。

Unix 管道的局限也要点明，正是它催生了分布式文件系统：管道里的中间数据只存在于内存/单机，一个工具的输出直接喂给下一个，无法分散到多台机器、也无法在中途失败后从半路续跑。要把这套思想放大到集群，就需要一个能被所有机器共享读写的"大文件系统"来接住中间结果（09-10.2）。

### 09-10.1.4 不可变输入、可重跑与幂等

批处理还有一条贯穿性的原则：**输入是不可变的（immutable）**，作业只读输入、把结果写到新的输出位置，绝不原地修改输入。Unix 命令里 `cat access.log | ...` 从不改动 `access.log` 本身，正是这个原则的体现。

这条原则带来几个初学者要记牢的好处。**可重跑（re-runnable）/幂等（idempotent）**：因为输入没被动过，作业失败了、或者你改了代码想重算，直接重跑一遍即可，结果一样，不会因为"上次跑了一半改坏了输入"而无法恢复——这让容错和调试都变得极其简单。**便于实验与回溯**：老的输出留着，新代码写到新目录，两边一比就知道改动的效果；出错了随时切回旧输出。**天然适合并行与容错**：既然任何一段计算都能安全重算，那么某台机器挂了，把它负责的那块任务在别处重跑就行，不影响正确性。后面 MapReduce 用"物化中间结果 + 失败重跑任务"来容错（09-10.2.4）、dataflow 引擎用"血缘重算"来容错（09-10.4.3），根子上都依赖"输入/中间数据不可变、计算可重放"这一条。

## 09-10.2 MapReduce 模型与分布式文件系统

### 09-10.2.1 分布式文件系统（HDFS 等）：无共享架构上的大文件

MapReduce 作业读写的不是单机文件系统，而是**分布式文件系统（distributed filesystem）**。最有代表性的是 **HDFS（Hadoop Distributed File System）**，它是 Google GFS（Google File System）的开源再实现。它的核心思路是：把很多台普通机器上的本地磁盘"拼"成一个逻辑上的大文件系统，一个文件被切成若干**块（block）**分散存放在不同机器上，每块再**复制（replicate）**到多台机器（HDFS 默认副本数为 3，可配置）以容忍单机故障。

这是典型的**无共享（shared-nothing）架构**：机器之间不共享磁盘或内存，只通过普通网络通信，靠软件层面的复制和协调来提供可靠性，因此可以用廉价商用机器堆出巨大容量，且能近乎线性地扩容。HDFS 的架构上有一个中心节点（NameNode）记录"哪个文件的哪一块在哪台机器上"这份元数据，实际数据块存在众多 DataNode 上。初学者要抓住的关键是：分布式文件系统提供了一个所有集群机器都能读写的"共享大硬盘"，这正是把 Unix 管道思想放大到集群所缺的那块拼图——中间结果有地方落脚了。

### 09-10.2.2 MapReduce 编程模型：map 与 reduce 两个函数

MapReduce 让程序员只需写两个函数就能表达一个分布式批处理作业。**Mapper**：框架对输入文件的每一条记录调用一次 map 函数，map 从这条记录里提取出若干 **键值对（key-value pair）** 并输出。**Reducer**：框架把所有 mapper 输出的键值对按**键**收集到一起，对每一个不同的键，调用一次 reduce 函数，把该键对应的**所有值**作为一个集合交给它，reduce 据此产出输出。

用前面"统计每个 URL 访问量"的例子对应：mapper 读日志的每一行，输出 `(URL, 1)`；框架把相同 URL 的所有 `1` 汇到一起；reducer 对每个 URL 收到一串 `1`，求和即得访问量。这里的思维模型和 09-10.1.2 的 Unix 管道完全同构——map 相当于 `awk` 抽字段、`sort` 把相同键排到一起是框架自动做的、reduce 相当于 `uniq -c` 的聚合。初学者常见误解是以为要自己写"把相同键聚到一起"的逻辑，其实那是框架的核心职责（下面的 shuffle），你只写 map 和 reduce 两段无状态的逻辑。

mapper 之间彼此独立、reducer 之间也彼此独立，map/reduce 函数本身不保存跨记录的状态、不产生副作用（除了输出键值对）。正是这种"无状态、可独立重算"的约束，让框架可以放心地把任务分散到成百上千台机器、并在失败时随意重跑某个任务（09-10.2.4）。

### 09-10.2.3 作业执行：把计算移到数据 + shuffle

MapReduce 一个作业的执行分成三个阶段，中间那步是理解全局的关键。下面是数据流示意（独占块级）：

```
输入文件(HDFS, 分块)
   │  每个输入块 → 一个 map 任务
   ▼
[map 任务1] [map 任务2] ... [map 任务m]      ← 尽量在存有该数据块的机器上运行
   │           │              │
   │  各自输出 (key,value)，按 key 的哈希分区、分区内排序、写本地磁盘
   ▼           ▼              ▼
========== shuffle：按 key 跨网络重新分发 ==========
   │           │              │
   ▼           ▼              ▼
[reduce任务1][reduce任务2]...[reduce任务r]    ← 每个 reduce 收到"某些 key 的全部值"，已排序
   │           │              │
   ▼           ▼              ▼
输出文件(HDFS, 每个 reduce 一个输出文件, 通常各存 3 副本)
```

第一步，**把计算移到数据（moving computation to the data）**：框架尽量把 map 任务调度到"恰好存有它要读的那个输入块"的机器上，这样读输入走本地磁盘、不走网络，省掉海量数据的网络搬运——这是无共享架构下的关键优化，因为跨网络搬 PB 级数据远比搬"几行 map 代码"昂贵。第二步，**shuffle**：map 输出按键分区（同一个键必然落到同一个 reduce 分区，靠对键做哈希取模——这正是 09-6 分区思想的应用）、排序后写到 mapper 本地磁盘，reduce 任务再从各个 mapper 那里把属于自己分区的数据拉过来并归并。shuffle 是唯一必然发生大规模跨网络数据移动的地方，也是 MapReduce 作业最耗时的部分。第三步，reduce 对每个键顺序处理其全部值，输出写回分布式文件系统。

mapper 数量由输入块数决定，reducer 数量由人配置（决定了输出被切成几份、并行度多少）；"相同键去同一个 reducer"是靠对键分区实现的，所以 join 和分组才能在 reduce 侧完成（09-10.3）。

### 09-10.2.4 容错：物化中间状态 + 失败重跑

MapReduce 的容错策略朴素而有效：**把中间结果物化（materialize）到磁盘，任务失败就重跑**。每个 map 任务把输出**完整写到本机磁盘**后才算完成；每个 reduce 任务从磁盘拉数据。如果某台机器在跑 map/reduce 任务时挂了，框架检测到后，只需把那个失败的任务在另一台机器上**重新跑一遍**——因为输入不可变、任务无副作用（09-10.1.4），重跑结果与原来一致。

这个设计的代价与收益要一起看。收益是**容错极其简单且能扛大规模、长时间作业**：一个跑几小时、用几千台机器的作业，期间难免有机器故障，MapReduce 只重跑受影响的少量任务，而不必整个作业从头再来。代价是**慢**：中间结果被完整写盘（还常伴随复制），下一个作业又从盘里读回来，大量时间花在磁盘和网络 I/O 上；而且 reduce 必须等它依赖的所有 map 任务全部完成才能开始（因为要保证某个键的值收齐），存在"木桶效应"——一个掉队的慢任务（straggler）会拖住整个阶段。dataflow 引擎正是针对这两点代价做改进（09-10.4）。

### 09-10.2.5 MapReduce 工作流：把多个作业串起来

单个 MapReduce 作业只能表达"一趟 map + 一趟 reduce"，能力有限；真实分析往往需要多步。做法是把多个作业**链接（chain）成工作流（workflow）**：前一个作业把结果写到分布式文件系统的某个目录，后一个作业以该目录为输入，如此串成一条（或一张 DAG）流水线。

这带来两个要点。其一，**作业间的耦合靠目录名约定**：MapReduce 本身没有"工作流"概念，是靠上一个作业写好整个输出目录、下一个作业才启动来隐式串联的，所以后续作业必须等前序作业**完全结束**才能开始（不能流水线重叠）。其二，因此实践中普遍使用**工作流调度器**（如 Apache Oozie、Airflow、Luigi 等）来管理作业间的依赖、失败重试、定时触发。初学者要体会到的痛点是：每一步都要把中间数据完整落盘再读回，串得越长越慢——这正是后来 Spark/Flink 用"一个作业内表达整张 DAG、中间不必落盘"来解决的问题（09-10.4）。（工作流调度器的具体产品与用法属分布式与云系统课程范畴，此处只点其角色。）

## 09-10.3 批处理中的 join 与分组

### 09-10.3.1 为什么批处理里 join 很常见也很关键

批处理作业里经常要把两份数据"关联"起来：比如一份是用户活动日志（每条含 user_id），另一份是用户资料表（user_id → 年龄/地区），要统计"各年龄段的活动量"就得把日志按 user_id 关联到资料表。这就是 **join**。

单机数据库里 join 靠索引点查（拿一条日志的 user_id 去用户表的索引里查）就能做，但批处理里这样做是灾难：对海量日志逐条去远程数据库点查，会产生海量随机网络请求，慢到不可接受，还可能压垮那个数据库。批处理的原则是**顺序、批量、本地**地处理数据，所以它换了完全不同的 join 思路——把要关联的两份数据都作为批处理的输入，用排序或哈希在集群内部把它们凑到一起，避免任何逐条远程查询。批处理 join 主要分两大类：**reduce 侧 join** 和 **map 侧 join**，选哪种取决于数据的大小与是否已分区（下面逐一讲，最后给对比表）。

### 09-10.3.2 reduce 侧 join：sort-merge join 与二次排序

**reduce 侧 join（reduce-side join）**是最通用、对输入无任何前提假设的做法。思路：让两份输入的 mapper 都以 **join 键**（如 user_id）作为输出键。这样 shuffle 之后，同一个 user_id 的"日志记录"和"用户资料记录"必然被分到**同一个 reducer**、并排到一起；reducer 顺序扫过这个键的所有值，就能把日志和资料配对输出。因为这本质是"两边按键排序后归并"，也叫 **sort-merge join**。

有个实现细节值得点明——**二次排序（secondary sort）**：reducer 处理某个 user_id 时，希望先看到"用户资料"记录、再看到一串"活动"记录，这样可以把资料暂存在内存里、然后逐条拼接活动。框架通过让 mapper 在键里附带一个"记录类型"次级排序字段，保证同一 user_id 下资料排在活动前面。这就是 secondary sort 的用途。

reduce 侧 join 的最大优点是**通用**：不要求输入数据事先按什么方式组织，任意两份数据都能这么 join。代价是要经过完整的 shuffle（两份数据都得跨网络重排），开销大。初学者记住：**当两份数据都很大、且都没有预先按 join 键分区时，reduce 侧 join 是默认选择**。

### 09-10.3.3 分组（GROUP BY）与热键处理

**分组（GROUP BY）**在 MapReduce 里和 join 用同一套机制：让 mapper 把"要分组的键"作为输出键，同一组的记录就被 shuffle 到同一个 reducer，reducer 对该组做聚合（求和、计数、取 Top-N 等）。09-10.2.2 统计 URL 访问量就是最简单的分组。

分组和 join 共同的痛点是**热键（hot key）/ 倾斜（skew）**（呼应 09-6.2）：如果某个键的数据量极大（比如某名人账号 ID 对应海量日志），负责这个键的那个 reducer 会收到远超其他 reducer 的数据，成为拖慢整个作业的掉队者。缓解手法与分区那章一脉相承：把热键的数据**打散（salting）**到多个 reducer 先做部分聚合、再汇总（一些系统提供"倾斜 join / sharded join"支持，如 Pig 的 skewed join、Hive/Spark 的倾斜优化，会先采样探测热键再单独处理）。初学者要建立的直觉是：MapReduce 的并行度上限被"最大的那个键"卡住，处理倾斜就是把大键拆小。

### 09-10.3.4 map 侧 join 之一：广播哈希 join

当有前提可利用时，可以彻底跳过昂贵的 shuffle，直接在 map 阶段完成 join，即 **map 侧 join（map-side join）**。第一种是 **广播哈希 join（broadcast hash join）**：适用于"**两份数据一大一小，小的那份能装进单台机器的内存**"的情况。做法：把小表（如用户资料表）整体加载到**每个** mapper 的内存里建成一张哈希表；每个 mapper 顺序扫描大表（日志）的一部分，对每条记录直接用 join 键去内存哈希表里查配对，边扫边输出。

"广播"指的就是小表被复制分发到所有 mapper。它的巨大好处是**没有 reduce、没有 shuffle**：大表只被顺序读一遍、无需跨网络重排，速度远快于 reduce 侧 join。前提是小表真的小到能放进内存（否则内存放不下）。初学者记住选型口诀：**一大一小、小的能进内存 → 广播哈希 join**。

### 09-10.3.5 map 侧 join 之二：分区哈希 join 与合并 join

第二种 map 侧 join 用在"**两份数据都很大，但都已经按相同方式（相同的 join 键、相同的分区数）分好了区**"时。既然 user_id=x 的日志和资料本来就在编号相同的分区里，那么第 3 号 map 任务只需读两边各自的第 3 分区，在本地就能配对，无需跨分区、无需 shuffle——这叫 **分区哈希 join（partitioned hash join，Hive 里称 bucketed map join）**。若两边分区内还都按 join 键**排序**过，则可以直接归并（**map 侧合并 join / map-side merge join**），连建哈希表都省了，内存占用极小。

它的收益是把 reduce 侧 sort-merge join 的重活提前"摊销"掉了：数据是在**之前**某个作业里被分好区/排好序的（通常是它们本来就以这种方式存储），join 时就能白捡好处。代价是有前提约束——两边必须分区数一致、分区键一致。初学者要理解的取舍是：map 侧 join 快，但要求输入"长得合适"；reduce 侧 join 慢，但对输入无要求。框架（如 Hive）在优化时会根据数据的元信息自动判断能否用 map 侧 join。

下面把批处理 join 的几种方式对比放在一起（独占块级）：

| join 方式 | 前提条件 | 是否需要 shuffle/reduce | 代价与适用 |
|---|---|---|---|
| reduce 侧 sort-merge join | 无前提，任意两份大数据 | 需要（两份都跨网络重排、排序） | 最通用但最慢；两大表且未分区时的默认选择 |
| 广播哈希 join（map 侧） | 一大一小，小表能进单机内存 | 不需要（小表广播到各 mapper） | 快；小表必须放得下内存 |
| 分区哈希 join（map 侧） | 两边按相同 join 键、相同分区数预先分区 | 不需要（各分区本地配对） | 快；要求输入预先同构分区 |
| map 侧合并 join | 两边预先分区且分区内按 join 键排序 | 不需要，直接归并 | 最省内存；前提最严 |

## 09-10.4 dataflow 引擎与 MPP 数据仓库对比

### 09-10.4.1 MapReduce 的局限

MapReduce 虽然开创了商用机集群批处理，但用久了暴露出明显短板，理解这些短板才能理解后继者为什么长成那样。其一，**中间状态全物化到磁盘**：每个作业把输出完整写盘（还常复制多份），下一个作业再读回，多步工作流里大量时间浪费在反复读写磁盘/网络上。其二，**表达力弱、串联笨重**：一个作业只有 map+reduce 两阶段，稍复杂的逻辑要拆成一长串作业，每个作业启动都有开销，且必须前一个完全结束后一个才能开始，无法重叠。其三，**掉队者与阶段屏障**：reduce 必须等所有 map 完成，慢任务拖累整体。

MapReduce 的每一步都"落地成盘、彻底断开"，容错简单但效率低。后来的 **dataflow 引擎** 的核心改进，就是把"一整个多步计算"作为一个作业统一优化、中间结果尽量留在内存、不必要的排序和物化都省掉。

### 09-10.4.2 dataflow 引擎：把整个工作流当一个作业

**dataflow 引擎（dataflow engine）**——代表有 Apache Spark、Apache Flink（批模式）、Apache Tez——把一个批处理作业建模成一张**算子（operator）构成的有向无环图（DAG）**：数据从输入流经一连串算子（map、filter、join、aggregate 等），最后写出。相比 MapReduce 只有固定的 map/reduce 两种算子、只能两阶段，dataflow 引擎允许任意组合算子、任意长的流水线，并且由引擎统一调度这整张图。

关键改进有几点。**中间结果不强制落盘**：算子之间的数据能留在内存里直接传给下游，只在必要时（如需要重排的宽依赖 shuffle 边界，或内存放不下时）才写盘，省掉大量 I/O。**避免不必要的排序/物化**：MapReduce 每次 shuffle 都强制排序，而 dataflow 引擎只在真正需要排序的算子处才排。**流水线执行**：不需要像 MapReduce 那样"整个 map 阶段结束才开始 reduce"，很多算子可以边产出边消费。这些改进叠加起来，同样的多步作业，dataflow 引擎常比 MapReduce 快一个数量级。初学者抓住一句话：dataflow 引擎 = 把一长串 MapReduce 作业压缩成"一个能整体优化、中间尽量不落盘"的 DAG 作业。（Spark/Flink 的具体算子 API、部署模式属分布式与云系统课程范畴，本报告不展开。⚙演进快·锚版本·随时变：Spark 与 Flink 的版本与算子集持续演进，具体以 Spark 3.5.x/4.0、Flink 1.19/1.20/2.0 官方文档为准，此处版本号待核。）

### 09-10.4.3 dataflow 引擎的容错：血缘重算

放弃"每步都物化落盘"后，容错怎么办？dataflow 引擎（以 Spark 为典型）用**血缘（lineage）重算**：引擎记住每一份中间数据是"由哪些输入、经过哪些算子算出来的"这张计算图；如果某份留在内存里的中间数据因机器故障丢了，就沿着血缘图**重新计算**它，而不是从磁盘恢复。Spark 把这种带血缘、可重算的分布式数据集抽象叫 **RDD（Resilient Distributed Dataset，弹性分布式数据集）**。

这依赖 09-10.1.4 的老原则：输入不可变、算子是确定性的纯函数，所以重算结果一致。要点与取舍：重算容错省去了物化开销，但要求算子必须**确定性（deterministic）**——若算子带随机数、依赖当前时间或有外部副作用，重算结果可能和原来不同，导致数据错误，所以这类算子要特别当心（比如给随机种子固定值）。另外，若某份中间结果重算代价太高（血缘链很长），引擎也允许把它**检查点（checkpoint）**到可靠存储，用少量物化换重算时间——这是介于"全物化"（MapReduce）和"全重算"之间的折中。初学者记住：MapReduce 靠磁盘物化容错，dataflow 引擎靠血缘重算容错，各有代价。

### 09-10.4.4 图与迭代计算：Pregel / BSP 模型

有一类批处理任务是**迭代**的：反复在同一份（图）数据上循环，直到收敛，典型如 PageRank（网页排名）、最短路径、连通分量。用 MapReduce 做这类任务极其低效——每一轮迭代都是一个独立作业，要把整份图数据反复读写磁盘几十上百次。

针对图/迭代计算有专门的模型 **Pregel（由 Google 提出，对应开源 Apache Giraph）**，它基于 **BSP（Bulk Synchronous Parallel，整体同步并行）** 计算范式。心智模型是"**像顶点一样思考（think like a vertex）**"：每个图顶点是一个小计算单元，一轮迭代（称一个 superstep）里每个顶点接收上一轮邻居发来的消息、更新自己的状态、再给邻居发消息；所有顶点这一轮都算完并同步后，进入下一轮，直到没有顶点再更新。顶点状态在内存中跨轮保持、只有消息跨网络传递，从而避免了 MapReduce 每轮重读全图的浪费。初学者只需知道：图/迭代型任务有专门模型（Pregel/BSP），也常在 Spark（GraphX）、Flink（Gelly）上以库的形式提供，比朴素 MapReduce 迭代高效得多。（本项为概念点到，图算法本身属算法课范畴。）

### 09-10.4.5 高层声明式 API：Hive / Pig / Spark SQL

直接写 map/reduce 或 dataflow 算子既繁琐又难优化，所以业界普遍在批处理引擎之上加一层**高层查询语言/API**：早期有 **Hive**（把类 SQL 的 HiveQL 编译成 MapReduce/Tez/Spark 作业）、**Pig**（数据流脚本语言），如今主流是 **Spark SQL / DataFrame**、**Flink SQL** 等。

这层带来的最大价值是**声明式换来自动优化**（呼应 09-2 声明式查询哲学）：你写"要什么结果"（SQL），由引擎的优化器决定"怎么算"——自动选 join 算法（能否用广播 join、要不要 shuffle）、自动决定算子顺序、下推谓词。这既让不懂分布式细节的分析师也能写批处理作业，又常常比手写的低层代码更快（因为优化器比人更会挑执行计划）。初学者要建立的关联：09-10.3 讲的四种 join、09-10.4.2 的算子 DAG，在实际使用中大多不是手写的，而是这层高层引擎根据 SQL 和数据统计信息自动生成和选择的。

### 09-10.4.6 dataflow 引擎 vs MPP 数据仓库

处理大规模分析数据，除了 dataflow 引擎（Spark/Flink），还有 **MPP（Massively Parallel Processing，大规模并行处理）数据仓库**（如 Teradata、Vertica、Greenplum，以及云上的 Snowflake、BigQuery、Redshift 等偏 MPP 架构的产品）。两者能做的事高度重叠（都在一群机器上并行跑分析查询），但取向不同。

| 维度 | dataflow 引擎（Spark/Flink 批） | MPP 数据仓库 |
|---|---|---|
| 数据存储 | 读分布式文件系统/对象存储上的**任意格式**文件（文本、Parquet、Avro…），schema-on-read | 数据先按其**专有格式导入**内部存储，schema-on-write，通常带列存与精心设计的索引/统计 |
| 计算模型 | 通用：可跑 SQL，也可跑任意用户代码（ML、自定义函数、图算法） | 专注 SQL 分析查询，优化器高度成熟 |
| 典型性能 | 灵活，重 ETL/机器学习/半结构化数据处理见长 | 纯 SQL 分析查询上通常更快（存储与优化器为此专门打磨） |
| 容错取向 | 面向长作业、大集群，任务级重算/重跑，能扛作业中途机器故障 | 传统上更偏"查询失败整体重试"，面向相对短的交互式查询 |
| 数据加载 | 直接读原始文件，无需预先导入（适合数据湖） | 需要 ETL 导入，前期成本高但换来查询性能 |
| 适用场景 | 数据湖、异构/半结构化数据、ETL 管道、ML 特征工程 | 结构化 BI 报表、交互式 SQL 分析 |

**MPP 数据仓库把数据"请进"自家精心设计的存储和优化器，换来 SQL 分析的极致速度，但只吃结构化数据、只做 SQL**；**dataflow 引擎"就地"处理各种格式的原始数据、能跑任意代码，灵活度和容错性更好，适合数据湖与复杂 ETL/ML，但纯 SQL 性能上未必胜过专用数仓**。两者的界线近年在模糊——数仓开始支持读外部文件与半结构化数据，dataflow 引擎的 SQL 优化器也越来越强，"湖仓一体（lakehouse）"正是这种融合（呼应 09-1.3）。这块演进快，具体产品能力以官方文档为准。⚙演进快·锚版本·随时变·待核（各云数仓/引擎的具体特性边界未逐一核对到版本）。
