# L6-09·大主题09-4 编码与演化

本报告讲一件贯穿所有数据系统的基础工程：内存里的数据结构（对象、列表、哈希表）无法直接写进文件或穿过网络，必须先翻译成一段自包含的字节序列，读的一方再翻译回来。前一步叫编码（encoding）、序列化（serialization）或封送（marshalling），后一步叫解码、反序列化、解封送——这几组词是同义反复，选哪个纯看社区习惯。围绕"怎样编码"以及"当代码和数据的格式随时间各自变化时怎样还能互通"这两个问题，本大主题拆成五个小主题：语言内建序列化为什么不能用于持久化与跨系统、文本格式（JSON/XML/CSV）在哪里力不从心、带 schema 的二进制格式（Thrift/Protobuf/Avro）如何编码、schema 演进的前向/后向兼容规则，以及编码实际流经数据库、服务调用、异步消息这三种载体时各自的兼容性要求。

一条贯穿全章的主线要先立起来：现实系统几乎不可能让所有代码在同一瞬间升级完毕。服务端通常滚动升级（rolling upgrade，一次升一部分节点），客户端则可能几个月都不更新。这意味着新旧两版代码、以及新旧两种数据格式，会在同一时刻共存于系统中。于是数据的编码格式必须同时满足两个方向的兼容——后向兼容（backward compatibility，新代码能读旧数据）和前向兼容（forward compatibility，旧代码能读新代码写出的数据）——这是评判一切编码格式好坏的核心尺子，也是本章反复回到的落脚点。

## 09-4.1 语言内建序列化的可移植性与安全问题

### 09-4.1.1 编码与解码：为什么需要它

程序里的数据以两种形态存在。在内存中，它是对象、结构体、列表、数组、哈希表等，被优化成便于 CPU 用指针高效访问的形式；一旦要写入文件或经网络发送，就必须转成一段不依赖内存布局的、自包含的字节序列。把内存形态转成字节序列叫编码，反过来叫解码。

理解这个转换为什么"非做不可"，关键在于内存里的指针对别的进程毫无意义——一个指针只是本进程地址空间里的一个地址，另一台机器、甚至同机的另一个进程拿到它都无法解引用。因此编码的本质是把"用指针串起来的对象图"摊平成一串"无需指针也能自解释"的字节。这也解释了为什么编码格式的设计如此重要：它是两个可能用不同语言、不同版本代码写成的程序之间唯一的契约。

### 09-4.1.2 语言内建的序列化机制

许多编程语言自带把对象转字节的内建设施：Java 有 `java.io.Serializable`（及 Kryo 等第三方库）、Python 有 `pickle`、Ruby 有 `Marshal`。它们的最大卖点是方便——用极少的代码就能把内存对象存盘或发出去，几乎不用额外写映射代码。

初学者第一次接触序列化往往就是从这些内建机制开始，因为它们"开箱即用"。它们之所以诱人，是因为省去了为每个类手写编码逻辑的功夫：一句 `pickle.dumps(obj)` 就把任意 Python 对象变成字节。但正是这种"什么都能塞进去"的便利，埋下了下面几条严重问题的根，使 DDIA 明确建议：除了非常短暂的用途，不要用语言内建序列化做持久化或跨进程通信。

### 09-4.1.3 语言锁定与可移植性

内建序列化把编码格式和某一门语言绑死了：Java 序列化出来的字节，别的语言几乎无法读取。这等于把系统未来的技术选型永久锁在当前语言上，也让与其他组织、其他系统的数据交换变得极其困难。

这一点对数据系统尤其致命，因为数据的寿命往往远长于写它的那份代码——今天用 Java 写库，五年后团队可能想用 Go 或 Python 读同一批历史数据。如果当初用了 Java 内建序列化，这批数据就成了只有旧 Java 代码才能解开的"死数据"。跨语言互通是采用 JSON 或 Thrift/Protobuf/Avro 这类中立格式的首要理由。

### 09-4.1.4 安全问题：反序列化即任意代码执行

内建序列化最危险的一点是：解码过程往往需要实例化任意类，攻击者只要能让应用解码一段精心构造的字节，就可能触发任意代码执行、远程命令执行等严重漏洞。Python 官方文档对 `pickle` 有醒目警告——绝不要 unpickle 来自不可信来源的数据；Java 反序列化的"gadget chain"攻击也曾是一大类真实 CVE 的根源。

理解这个风险要抓住一点：解码器为了重建对象，被赋予了"根据字节内容去构造类实例、调用其方法"的能力，而这类格式通常没有对"允许构造哪些类"做限制。于是一段字节就变成了一个小程序，能指挥解码器做非设计意图的事。这正是"数据即代码"的反面教材，也是为什么把不可信输入交给内建反序列化被视为高危操作。相比之下，后面讲的 JSON/Protobuf/Avro 解码器只把字节还原成纯数据结构，不会凭数据去实例化任意类，攻击面小得多。

### 09-4.1.5 效率与版本问题

内建序列化通常还伴随三个次要但现实的缺点：编解码性能与产出体积往往不佳（Java 内建序列化以又慢又臃肿著称）；它一般不认真处理版本演进，新旧字段的前向/后向兼容支持薄弱；而且因为编码逻辑常与内存布局耦合，数据格式很难在不破坏旧数据的前提下平滑变化。

把这些缺点合起来看就是一句话：内建序列化优化的是"当下、同一份代码、同一语言"的便利，而数据系统真正需要优化的恰恰是"跨语言、跨版本、跨时间"的持久互通。二者目标错位，所以内建序列化只适合缓存这类可随时丢弃重建的短暂场景，不适合承载长期数据。

## 09-4.2 文本格式 JSON、XML、CSV 的局限

### 09-4.2.1 文本格式概览与它们的优点

JSON、XML、CSV 是三种最普及的文本编码格式：人类可读、跨语言、生态成熟。JSON 尤其成为 Web API 的事实标准，XML 曾在企业系统广泛使用，CSV 则是表格数据交换的最小公分母。DDIA 承认它们"足够好、足够流行"，其局限多是"够用但有坑"，而非"不能用"。

它们流行的根本原因是文本可读带来的低门槛：出问题时能直接用眼睛看、用文本工具处理，调试友好。这也是为什么即便有更高效的二进制格式，文本格式在对外接口、配置、日志等场景仍占主流。理解它们的局限，目的不是弃用，而是知道在精度、体积、契约这几个维度上何时该换更严格的格式。

### 09-4.2.2 数值的精度与类型模糊

文本格式在数字上有两处著名的坑。其一，JSON 不区分整数和浮点数，也不规定精度，很多解析器（尤其 JavaScript）用 IEEE 754 双精度浮点表示所有数字，无法精确表示大于 2^53 的整数，于是超过这个量级的 int64（如 Twitter/雪花 ID）在经过 JS 解析后会丢精度——常见规避是把大整数当字符串传。其二，XML 和 CSV 根本不区分数字与恰好由数字组成的字符串（除非另有 schema），"0123"这样的值会引发歧义。

这个坑的杀伤力在于它悄无声息：数据在编码时看着没问题，读出来才发现末几位对不上，且往往只在数值足够大时才暴露。抓住"文本格式默认不携带精确的数值类型信息"这一点，就能预判：凡是要传大整数 ID、货币金额、高精度小数，就不能天真地依赖 JSON 数字，要么用字符串、要么用带 schema 的二进制格式。

### 09-4.2.3 二进制数据支持缺失

JSON 和 XML 都没有对二进制字节串（如图片、加密数据）的原生支持，通常只能把二进制先 Base64 编码成文本再塞进去。Base64 会让数据体积膨胀约三分之一（每 3 字节变 4 个字符），而且需要额外约定"这个字段其实是 Base64"，属于绕过格式限制的 hack。

理解这里的代价：约 33% 的体积膨胀在大对象、高吞吐场景下并不便宜，且 Base64 让数据不再"所见即所得"。这是文本格式为"人类可读"付出的结构性代价——它假定内容都是文本，遇到真正的二进制就只能变通。需要频繁传二进制的系统，这一点会成为选择二进制格式的实在理由。

### 09-4.2.4 schema 支持可选且复杂

JSON 和 XML 都有可选的 schema 语言（XML 有 XSD/DTD，JSON 有 JSON Schema），但功能强大、学习曲线陡，且因为是可选的，许多基于 JSON/XML 的工具干脆不用 schema。没有 schema 时，字段的类型和取值约束就只能靠应用代码里的硬编码逻辑来兜底。

这一点是文本格式与后面二进制格式最本质的分野。schema 的价值在于把"数据长什么样"从代码里抽出来变成一份显式、可版本化、可校验的契约；缺了它，数据的正确性就散落在各处应用代码里，难以统一保证，演进时也没有一份权威描述来判断新旧是否兼容。这也是为什么真正需要严格演进管理的系统会转向带强制 schema 的格式。

### 09-4.2.5 CSV 的特有局限

CSV 没有任何 schema，全靠位置约定列的含义；它对特殊字符（逗号、换行、引号）的转义规则处理得含糊且各实现不一，虽有 RFC 4180 试图规范，现实中方言林立。任何增删列或改变列顺序的改动，都得靠人工在生产者和消费者之间协调。

CSV 的坑集中体现了"无 schema"的代价：一个字段里若本身含逗号或换行，就要靠引号包裹和引号转义，而不同工具对此的处理并不一致，极易在导入导出之间悄悄错行。它适合最简单的表格交换，一旦数据里出现自由文本、需要嵌套结构、或格式要长期演进，就明显力不从心。

### 09-4.2.6 二进制 JSON 变体

针对 JSON/XML 体积偏大的问题，社区发展出一批保留 JSON 数据模型但改用二进制编码的格式，如 MessagePack、BSON、BJSON、UBJSON 等。它们不需要预定义 schema，只是把同样的字段名、类型标记、值用更紧凑的字节表示，体积和解析速度略优于纯文本 JSON。

它们省下的主要是"文本 vs 二进制"的那点开销，但因为仍然在每条记录里内嵌字段名，压缩幅度有限（DDIA 举的例子里，MessagePack 相对 JSON 的缩减并不惊人）。真正大幅缩小体积、并支撑严格演进的，是下一小主题里"字段名不进字节、靠 schema 描述"的 Thrift/Protobuf/Avro——二进制 JSON 变体只是文本格式到强 schema 格式之间的一个折中过渡。

## 09-4.3 二进制 schema 格式：Thrift、Protobuf、Avro

### 09-4.3.1 带 schema 的二进制编码是什么

Thrift（Facebook 起）、Protocol Buffers（Google 起）、Avro（Hadoop 生态）都是把数据编成紧凑二进制的格式，它们的共同点是要求一份显式的 schema（用一种接口定义语言 IDL 或 JSON 写成），并据此工作。字段名等描述信息不进入编码后的字节，只留在 schema 里，因此产出比 JSON 小得多。

抓住"schema 与数据分离"这个核心就理解了这类格式的全部优势来源：既然读写双方都持有 schema，字节里就不必重复携带字段名和类型标签，省下大量空间；schema 本身又成了一份可校验、可版本化的正式契约（本身就是有价值的文档），并能让工具生成各语言的类型安全代码。代价是数据不再自解释——脱离 schema 的字节几乎无法读懂，所以这类格式主要用于系统内部而非对外开放接口。

### 09-4.3.2 Thrift 的两种编码协议

Thrift 用自己的 IDL 描述 schema，并提供多种运行时编码协议，最常对比的是 BinaryProtocol 与 CompactProtocol。BinaryProtocol 里每个字段前带一个字节的类型标记、一个两字节的字段编号（field tag/ID），再接字段值；CompactProtocol 则把字段类型和相对上一字段的编号差（delta）打包进单字节，并对整数用变长编码，因而更紧凑。

理解 Thrift 的关键是"字段靠数字编号定位"：schema 里每个字段都被指定一个整数 tag（如 `1: string userName`），编码后的字节用这个数字而非字段名来标识字段，读方按 tag 到 schema 里查这个字段是什么。这个"用 tag 而非名字"的设计，正是后面 schema 演进能安全增删字段的机制基础。BinaryProtocol 直白但费空间，CompactProtocol 通过 delta 编号和 varint 把常见情形压到更少字节，二者读的是同一份 IDL、可按需选用。

### 09-4.3.3 Protobuf 的编码机制

Protocol Buffers 与 Thrift CompactProtocol 思路相近但只有一种主要二进制编码。每个字段编码为：一个 varint 形式的"键"（key），其后跟字段值。这个键把字段编号和线型（wire type）打包进同一个 varint，公式为：

field_key = (field_number << 3) | wire_type

线型（wire type）占键的最低 3 位，官方定义如下几种：

| 线型值 | 名称 | 用于的类型 |
|--------|------|-----------|
| 0 | VARINT | int32/int64/uint32/uint64/sint32/sint64/bool/enum |
| 1 | I64 | fixed64/sfixed64/double |
| 2 | LEN | string/bytes/嵌套 message/packed 重复字段 |
| 5 | I32 | fixed32/sfixed32/float |

（线型 3/4 为已废弃的 group start/end。）

整数用 varint（可变长整数）编码：每字节最高位是"续位"（continuation bit），为 1 表示后面还有字节，低 7 位按小端序拼出数值；这样小整数只占 1 字节，大整数才用多字节，比定长省空间。但 varint 对负数很吃亏——负数在补码下最高位全是 1，直接 varint 会占满 10 字节；为此有符号整型可用 sint32/sint64，它们先做 ZigZag 变换再 varint：把正数 p 映射成偶数 2p、负数 n 映射成奇数 2|n|−1，使绝对值小的数（无论正负）都编码得短。官方给出的按位公式为：

ZigZag(n) = (n << 1) ^ (n >> 31)   // sint32；sint64 用 >> 63

一个直觉例子帮理解字节布局：一个字段号为 1、线型为 2（字符串）的字段，其键的 varint 值是 `(1 << 3) | 2 = 0x0A`，随后是一个 varint 表示的字节长度，再是 UTF-8 内容本身。读方拿到 `0x0A` 就知道"这是字段 1、是长度前缀型"，再到 schema 查字段 1 是什么。要点是：字段名完全不在字节里，只有数字 tag。

### 09-4.3.4 Avro 的编码机制

Avro 走了一条与前两者不同的路：它的二进制编码里既没有字段名、也没有字段 tag，甚至没有任何类型标记，字节就是一个个值紧挨着拼起来（整数用变长 ZigZag、字符串用长度前缀加 UTF-8）。要正确解析这串字节，读方必须精确地知道写这段数据时用的那份 schema（称 writer's schema），严格按 schema 里字段的声明顺序逐个取值。

这带来一个初学者常困惑的问题：既然字节里连字段边界都没有，怎么读？答案是"schema 就是解析的地图"——读方拿 writer's schema 按序读，schema 说第一字段是 string 就先读一个长度前缀再读那么多字节，说下一字段是 int 就接着读一个变长整数，以此类推。因为没有 tag、没有默认值内嵌，Avro 的字节最紧凑，但也最依赖"读方能拿到 writer's schema"这个前提——这个前提如何满足，是 09-4.4 的核心话题，也是 Avro 与 Thrift/Protobuf 在演进机制上分道扬镳的地方。

### 09-4.3.5 三种格式对比

把三者放在一起对比，差异集中在"字段靠什么定位"和"读方需要哪份 schema"两点：

| 维度 | Thrift | Protocol Buffers | Avro |
|------|--------|------------------|------|
| schema 描述 | Thrift IDL | .proto IDL | JSON（或 Avro IDL） |
| 字段在字节中的定位 | 字段数字 tag + 类型标记 | 字段数字 tag（打包进 varint 键）+ 线型 | 无 tag、无字段名、无类型标记，靠顺序 |
| 主要二进制编码 | BinaryProtocol / CompactProtocol | 单一 varint 键 + 值 | 值紧凑拼接（变长 ZigZag / 长度前缀） |
| 读方需要的 schema | 读方自己的 schema | 读方自己的 schema | writer's schema + reader's schema 都要 |
| 演进主机制 | tag 号不变、字段可选/删除 | tag 号不变、字段皆 optional（proto3） | reader/writer schema 按字段名解析 + 默认值 |
| 对动态生成 schema 的友好度 | 一般 | 一般 | 好（无 tag，天然适合从数据库表结构生成） |

Thrift 和 Protobuf 用"数字 tag"给每个字段一个稳定身份，即使字段名改了、位置动了，只要 tag 不变就能对上；Avro 干脆不放身份标记，改用"读写两份 schema 按字段名做匹配解析"。这两条路线导致它们的演进规则形态不同，但都能做到前向/后向兼容——下一小主题正是把这两套规则讲清楚。

## 09-4.4 schema 演进与前向 / 后向兼容

### 09-4.4.1 前向兼容与后向兼容

兼容性有两个方向，务必分清。后向兼容（backward compatibility）指新代码能读旧代码写的数据——因为新代码是作者写的、知道旧格式，这个方向通常较易实现。前向兼容（forward compatibility）指旧代码能读新代码写的数据——旧代码不知道新格式里多出来的东西，必须能优雅地忽略它，这个方向更难。

理解这对概念要回到本章开头的现实：滚动升级时新旧代码共存，新写的数据可能被尚未升级的旧节点读到（要求前向兼容），旧写的数据也会被已升级的新节点读到（要求后向兼容），两个方向同时需要。一个记忆法：以"新代码"为参照，"能读过去写的"是后向（回头看），"过去的代码能读现在写的"是前向（旧代码向前看）。带 schema 的格式之所以受青睐，正因为它们把这两个方向的规则设计得清晰可控。

### 09-4.4.2 Thrift 与 Protobuf 的演进规则

在 Thrift 和 Protobuf 里，兼容性的支点是字段的数字 tag：schema 里可以改字段名（因为名字不进字节），但绝不能改已用的 tag 号，那会让所有旧数据错位。加字段时，给它一个新的 tag 号即可——旧代码读到不认识的 tag 会按线型跳过它（前向兼容成立）；新代码读旧数据时，缺失的新字段则需能容忍其不存在。

具体规则围绕"字段是否必填"展开。可以随时新增字段，但新增字段不能是 required（Thrift 的 required / proto2 的 required），否则旧数据里没有该字段、新代码会读取失败——新增字段必须是 optional 或带默认值，这样后向兼容才成立。删字段则相反：只能删 optional 字段，且被删的 tag 号要永久保留、不可复用（Protobuf 用 `reserved` 关键字标记退役 tag），以防将来新字段误用旧 tag 造成新旧语义串味。proto3 索性取消了 required，所有字段皆可选，正是为把这类演进坑从语言层面堵死。

### 09-4.4.3 Avro 的演进规则

Avro 没有字段 tag，它的兼容性靠 reader's schema 与 writer's schema 的匹配解析：解码时把两份 schema 并排比对，按字段名对应，把 writer 写的数据翻译成 reader 想要的形状。字段顺序不同没关系（按名字匹配）；writer 有而 reader 没有的字段会被忽略；reader 要而 writer 没写的字段，用 reader schema 里为该字段声明的默认值填上。

由此推出 Avro 的加删规则：加字段和删字段都只允许操作带默认值的字段。加一个带默认值的字段——旧数据（writer 无此字段）被读时用默认值补齐（后向兼容），旧 reader 读新数据时忽略这个多出来的字段（前向兼容）。删一个带默认值的字段同理对称成立。要注意 Avro 里 union 类型（如 `["null","string"]`）的默认值取该 union 的第一个分支，改一个字段的类型或往 union 里加删分支都有细则约束——核心口诀仍是"只有带默认值的字段能安全增删"。

### 09-4.4.4 Avro 如何知道 writer's schema

既然 Avro 解码非要 writer's schema 不可，它怎么拿到？答案随数据流场景而异，这也是 Avro 设计的精巧处。大文件存大量同类记录时（如 Hadoop），把 writer's schema 在文件开头写一次即可（Avro 对象容器文件格式），整份文件共用。数据库里逐条记录版本可能不同时，给每条记录带一个很小的版本号，另用一张 schema 版本表按号查出对应 writer schema。通过网络双向 RPC 时，两端在连接建立时协商各自的 schema 版本。

这套机制的价值在于把 schema 这份"重"契约从"每条记录"降到"每文件/每连接/一张小表"的粒度，于是即便字节里不带任何字段标记也不担心读不出。更进一步，因为 Avro 不需要人工维护 tag 号，它特别适合 schema 由程序动态生成的场景——比如直接从数据库表结构导出 Avro schema，表加一列就重新生成一份 schema，无需像 Protobuf 那样人工给新列指派并守护 tag 号。这是 Avro 相对 Thrift/Protobuf 的一个独特优势。

### 09-4.4.5 兼容性规则速查

把三格式的演进要点并列，便于对照：

| 演进操作 | Thrift / Protobuf | Avro |
|----------|-------------------|------|
| 加字段 | 用新 tag 号；新字段须 optional 或带默认值 | 加带默认值的字段 |
| 删字段 | 只删 optional 字段；tag 号永久保留不复用（`reserved`） | 删带默认值的字段 |
| 改字段名 | 可以（名字不进字节，靠 tag） | 可以（有别名 alias 机制辅助按名匹配） |
| 改 tag / 顺序 | 绝不可改 tag 号；顺序无关 | 无 tag；字段顺序无关（按名匹配） |
| 前向兼容靠什么 | 旧代码按线型跳过未知 tag | 旧 reader 忽略 writer 多出的字段 |
| 后向兼容靠什么 | 新代码容忍缺失的 optional 字段 | reader 用默认值补 writer 缺的字段 |

看这张表要抓住两条主线的对称美：Thrift/Protobuf 靠"tag 号是字段的永久身份证、未知 tag 可跳过、缺失 optional 可容忍"实现双向兼容；Avro 靠"按字段名匹配、多出的忽略、缺的用默认值填"实现双向兼容。两条路都把"增删字段"限制在"该字段可有可无"（optional / 带默认值）这一前提上——这是所有 schema 演进规则背后共同的安全边界。

### 09-4.4.6 required、默认值与数据类型的改动

几个易错细节值得单列。required 字段是演进的敌人：它使加字段（新加的 required 让旧数据非法）和删字段（删掉的 required 让旧代码期待落空）都变危险，所以实践与 proto3 都倾向于全用 optional。默认值是兼容的润滑剂：无论哪种格式，"字段可缺失时读到什么"由默认值兜底，缺了默认值就无法安全增删。改字段数据类型（如 int32 改 int64）风险最高：可能丢精度或改变解析，通常不被视为安全演进，要格外谨慎或视作不兼容变更。

理解这些细节的统一视角是：演进安全 = "任一版本代码读到任一版本数据都不崩、且语义不悄悄漂移"。required 破坏"不崩"，缺默认值破坏"可缺失字段的读取"，类型改动破坏"语义不漂移"。凡拿不准某项改动是否兼容，回到这条定义逐一验证即可，不必死记规则。

## 09-4.5 数据流中的编码三载体：数据库、服务、消息

### 09-4.5.1 通过数据库的数据流

数据存进数据库是把数据发给"未来的自己"去读。这里前向兼容尤其关键：滚动升级期间，新代码写入的记录可能被尚未升级的旧代码读到，旧代码不认识新字段。一个著名的坑是——旧代码读一条含新字段的记录、修改后写回时，若解码-编码链路不小心把它不认识的新字段丢掉了，就会造成数据静默丢失。

数据的寿命长于代码（data outlives code）。数据库里可能躺着五年前某版代码写入、至今没被重写过的记录，因此各种版本的数据会长期并存。应对之道是让格式与代码都保证"未知字段原样保留"——读到不认识的字段不丢弃、写回时带回去。带 schema 的二进制格式配合正确的读改写逻辑能做到这点，这也是为什么"能读但要小心保留未知字段"成为数据库编码的头号纪律。此外，把整库迁移到新 schema 代价高昂，多数数据库更倾向用可空默认值做轻量的在线 schema 变更，让旧数据按需惰性升级。

### 09-4.5.2 通过服务调用的数据流

当数据经由网络在服务之间流动时，常见两种风格：REST（基于 HTTP 的资源风格，多用 JSON）和 RPC（远程过程调用，让网络调用看起来像本地函数调用，如 gRPC 基于 Protobuf、Thrift、以及历史上的 SOAP 等）。面向公众的 API 多用 REST + JSON 以求通用与可读；组织内部服务间调用则常用 RPC + 二进制 schema 格式以求性能与强类型。

服务场景的兼容性要求是双向且长期的：客户端和服务端各自独立部署、独立升级，你无法强制所有客户端同时更新，所以服务的请求/响应编码必须同时前向和后向兼容，且这份兼容承诺往往要维持很久。RPC 让远程调用"看起来像本地调用"，但初学者要警惕这层抽象的漏洞——网络调用会超时、会失败、会重试导致重复、延迟不可预测，这些都是本地函数没有的，不能被"像本地一样"的外表掩盖。正因如此，RPC 框架的演进规则（如 gRPC 直接复用 Protobuf 的字段兼容规则）就是服务能平滑迭代的基础。

### 09-4.5.3 通过异步消息传递的数据流

第三种载体是异步消息：生产者把消息发给消息中间件（message broker，如 Kafka、RabbitMQ 等），消费者从中读取，二者时间上解耦、不必同时在线。与 RPC 相比，broker 提供缓冲、可重投、一对多广播、且发送方不需知道接收方是谁，代价是通常单向、无返回值（需要回复要另开一条消息通道）。

从编码角度看，消息传递与前两者的兼容性诉求一致却更松耦合：生产者和消费者各自独立演进，消息的编码同样需要前向/后向兼容，因为一条消息可能被多个、且版本各异的消费者读取，也可能在队列里滞留一段时间后才被处理。同属这一类的还有 actor 模型（如 Akka、Erlang/OTP）——actor 之间只通过异步消息通信，跨节点通信时同样面临消息编码的版本兼容问题。三种载体（数据库、服务、消息）看似形态各异，落到编码上是同一个要求：因为收发双方几乎永远不会同时升级，所以格式必须让新旧代码、新旧数据自由互读——这正是全章开篇立下、贯穿始终的那把尺子。
