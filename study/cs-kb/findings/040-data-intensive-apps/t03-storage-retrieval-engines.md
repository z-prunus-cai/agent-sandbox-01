## 09-3.1 LSM 树 vs B+树：读/写/空间放大与读写比取舍

### 09-3.1.1 两大存储引擎家族：原地更新 vs 日志结构

绝大多数持久化存储引擎可以归到两个家族。一类是"原地更新"（update-in-place），代表是 B+树：数据按固定大小的页组织成一棵平衡树，更新一条记录时找到它所在的页，直接在原位置改写。另一类是"日志结构"（log-structured），代表是 LSM 树（Log-Structured Merge-Tree）：所有写入都先追加到内存中的有序结构，攒够一批后作为一个不可变的有序文件（SSTable）顺序刷到磁盘，后台再把这些文件合并（compaction），从不在原位置改写。

理解这个分野是本章所有选型判断的地基。原地更新意味着"一次写 = 一次随机 I/O 到目标页"，读的时候一步到位；日志结构意味着"写永远是顺序追加"，代价是同一个 key 的多个版本散落在不同文件里，读的时候可能要翻好几个文件。几乎所有关系库（PostgreSQL、MySQL/InnoDB、SQLite）默认走 B+树；很多为写密集设计的 NoSQL 与嵌入式引擎（Cassandra、HBase、RocksDB、LevelDB）走 LSM。这不是新旧之分，而是为不同负载做的不同权衡。

### 09-3.1.2 三种放大：写放大、读放大、空间放大

"放大"（amplification）指的是"实际付出的工作量 / 逻辑上应付出的工作量"，是衡量存储引擎效率的三把尺子。三者定义如下（各自独占一行）：

写放大 = 实际写入存储介质的字节数 / 应用逻辑写入的字节数

读放大 = 一次逻辑查询实际访问的存储单元（页/块/文件）数

空间放大 = 磁盘上实际占用的字节数 / 逻辑数据的字节数

应用只想写 100 字节的一行，但 B+树要把整个 4KB 或 8KB 的页写回磁盘，还要先写一份 WAL（预写日志），这就是写放大远大于 1。LSM 树里一条记录会在它的生命周期内被 compaction 反复重写好几遍，也是写放大。读放大在 LSM 里尤其明显：查一个不存在的 key，最坏要逐层查很多个 SSTable。空间放大在 B+树里来自页内碎片和分裂留下的半空页；在 LSM 里来自同一 key 的旧版本和已删除记录（墓碑）在被 compaction 清理前会一直占着空间。

初学者容易只盯着"快不快"，但这三个量往往是此消彼长的——省了这个就多付那个，下一节说明为什么。

### 09-3.1.3 放大三角：三者不可兼得

这三种放大不能同时都压到最低，构成一个"三选二"式的权衡三角（学术上称 RUM conjecture：Read、Update、Memory 三者的开销互相牵制）。一个存储引擎的设计本质上是在这个三角里选一个点。

```
              读放大低
               /\
              /  \
             /    \
            /      \
   写放大低 -------- 空间放大低
   （LSM 偏这条边，靠激进 compaction 可换低空间但抬高写放大）
```

直观理解：想让读快（读放大低），就要把数据保持得高度有序、少而集中，这需要不停地整理数据，也就是多写（写放大高）或多占临时空间。想让写快（写放大低），就先随手追加、以后再整理，代价是数据暂时凌乱、旧版本堆积，读的时候要多翻、空间要多占。B+树天然读放大低、但写放大偏高；LSM 天然写放大可调低、但读放大和空间放大要靠 Bloom filter 和 compaction 去补。选型就是在问"你的负载最怕哪一种放大"。

### 09-3.1.4 LSM 的性质与代价

LSM 的核心优势是写吞吐高、且写入是顺序 I/O。因为写只落到内存 memtable 再批量顺序刷盘，天然对机械盘友好，对 SSD 也能减少随机写带来的磨损与写放大。它还天生适合高压缩：SSTable 是不可变的紧凑有序块，压缩率通常比 B+树的半空页更好，空间效率有优势。

代价有三个要记住。其一是读放大：一个 key 可能存在于 memtable 加多层 SSTable 中，点查最坏要查多处；工程上用 Bloom filter（快速判定"某 key 一定不在这个文件里"）把不存在 key 的查询挡在磁盘访问之外，很大程度缓解但不消除读放大。其二是 compaction 带来的性能抖动：后台合并会突然抢占磁盘带宽和 CPU，造成延迟毛刺（尾延迟变差），这对要求稳定 p99 的场景是硬伤。其三是空间放大的瞬时峰值：compaction 进行时旧文件还没删、新文件已生成，磁盘要预留额外空间。

### 09-3.1.5 B+树的性质与代价

B+树的核心优势是读路径短且稳定：任何一次点查都是从根到叶固定几跳（树高通常 3～4 层就能覆盖极大数据量），延迟可预测、没有 compaction 那种抖动。它对读密集、以及需要稳定低延迟点查/范围查的 OLTP 负载非常合适，也是几十年生产考验下来最成熟、最好调的结构。

代价主要是写放大。一次逻辑更新往往要写两次：先写 WAL 保证崩溃可恢复，再改写数据页本身；而改一个字节也要写回整页。页分裂（节点满了要一分为二）会带来额外随机写和空间碎片。因此在极端写密集、顺序摄取海量数据的场景，B+树的写放大和随机 I/O 会成为瓶颈——这正是 LSM 的主场。

### 09-3.1.6 按读写比与访问模式选型

把上面两节合起来，选型的第一原则是看读写比和写的形态。写密集、尤其是高吞吐顺序摄取（时序数据、日志、事件流、写多读少的键值场景）倾向 LSM，因为它把随机写变成顺序写、写放大可控、压缩好。读密集、点查为主、且要求稳定可预测延迟（典型 OLTP、金融交易、需要严格 p99 的在线服务）倾向 B+树，因为读路径短且无 compaction 抖动。

还要看两个附加因素。一是范围扫描：两者都支持有序范围扫描，但 B+树叶子页用链表相连，范围扫描连续性好；LSM 需要跨多个 SSTable 做归并，范围扫描要合并多路。二是介质：SSD 的随机读代价低，缩小了 LSM"顺序写"相对 B+树的优势，但 LSM 减少写放大对延长 SSD 寿命仍有价值。DDIA 强调这些是经验规律而非铁律，真实系统还受实现质量和参数影响，务必以目标负载实测为准。

### 09-3.1.7 compaction 策略如何改变放大（选型含义）

LSM 的三种放大不是固定的，很大程度由 compaction 策略调出来，选型时要知道这个旋钮存在。两大策略：leveled compaction（分层：每层文件不重叠、逐层放大容量）偏向压低读放大和空间放大，代价是写放大更高；tiered/size-tiered compaction（把同样大小的文件攒够几个再合并）偏向压低写放大，代价是读放大和空间放大更高。

实现细节留在 L6-04，这里的选型含义是：同一个 LSM 引擎（如 RocksDB）通过换 compaction 策略，可以在放大三角里移动到不同的点。因此"选 LSM 还是 B+树"之后，往往还有"选哪种 compaction / 怎么调"这一层，且这些默认值随引擎版本而变，落到具体数字要以对应版本文档为准（本报告不锁定具体默认值，见本节来源与时效）。

## 09-3.2 行存 vs 列存与数据仓库存储选型

### 09-3.2.1 行式存储与列式存储的布局区别

行存（row-oriented）把一行（一条记录）的所有字段连续存放，一行接一行；这是 OLTP 数据库的默认布局。列存（column-oriented）把同一列（同一字段）的所有行的值连续存放，一列接一列。同样一张有一百列的表，行存里"取某一整行"很便宜（相邻字节），"对某一列做聚合"很贵（要跳着读每一行）；列存正好相反。

用一张小表直观对比布局（块级示意）：

```
逻辑表：            行存磁盘布局（按行连续）：
id name  age       [1,Ann,30][2,Bob,25][3,Cy,41] ...
1  Ann   30
2  Bob   25        列存磁盘布局（按列连续）：
3  Cy    41        id: [1,2,3,...]
                   name: [Ann,Bob,Cy,...]
                   age:  [30,25,41,...]
```

布局决定了"哪种访问是顺序读、哪种是跳读"。分析查询典型是"扫几亿行、但只碰其中三五列做聚合"，列存让这三五列各自连续、其余列完全不用读，I/O 直接省一大截。

### 09-3.2.2 列存为何在分析负载收益大

三个叠加的收益。其一是只读需要的列：OLAP 查询往往只涉及宽表里的少数列，列存可以只把这几列的数据从磁盘读上来，跳过其余几十上百列，扫描的数据量成倍下降。其二是压缩率高：同一列的值类型相同、取值相近甚至重复度高，非常适合轻量压缩（下一项详述），压得越狠、要读的字节越少。其三是执行高效：连续同类型的列数据天然适合向量化执行和 SIMD，CPU 一条指令处理一批值，摊薄每行开销。

这三点是相乘而非相加的关系，合起来能让分析查询比行存快一到两个数量级，这也是所有现代数据仓库（Snowflake、BigQuery、Redshift、ClickHouse、DuckDB）都以列存为底座的原因。DDIA 2e 把列存放在"面向分析的数据存储"一节，与 OLTP 的行存明确分账。

### 09-3.2.3 列压缩编码与压缩比直觉

列存之所以压得好，靠的是针对"同列同类型"的轻量编码。常见几种：字典编码（把重复出现的字符串/类别值映射成小整数 id，只存 id 和一张字典，适合低基数列如"国家""状态"）；游程编码 RLE（把连续重复的值记成"值×次数"，排序后的列尤其有效）；位图编码（对低基数列，每个取值配一个位图，配合位运算做过滤极快）；还有 delta 编码、frame-of-reference（存相对基准的差值，适合递增的 id、时间戳）。

这些编码把"数据的规律性"直接变成"更少的字节"。一列"订单状态"只有五六种取值，字典编码后每个值只占几个 bit；一列排好序的时间戳用 delta 编码后几乎全是小差值。更妙的是很多操作能"在压缩态上直接算"（比如在位图上做 AND 完成过滤），不必先解压，进一步省 CPU。具体压缩比高度依赖数据分布，不是固定数字，落到某列某格式要实测。编码机制的实现细节在 L6-04，这里只需知道"列存 + 轻量编码"是分析存储省 I/O 的核心手段。

### 09-3.2.4 何时列存收益不大甚至有害

列存不是万金油。点查/取整行的场景它很吃亏：要拼出完整一行，得从每一列各读一处再重组（tuple reconstruction），OLTP 那种"按主键取一整条记录"用列存反而慢。行级写入和更新也是列存的软肋：插一行要往几十个列文件分别追加，改一个字段可能触发整列的重编码或版本管理；因此传统列存偏向"批量加载、极少更新"的追加型分析数据。事务支持通常也较弱。

读多写少、扫描聚合为主、宽表少列查询 → 列存；点查、频繁行级增删改、强事务、要取完整记录 → 行存。这正对应 OLAP 选列存、OLTP 选行存的大分野。混合负载（HTAP）则需要折中方案，见 09-3.2.6。

### 09-3.2.5 数据仓库存储格式与云数仓（选型视角）

在数仓/湖仓语境里，列存往往落成开放文件格式：Parquet 和 ORC 是两大主流，都把数据按列分块（row group / stripe）存储、内嵌每块的 min/max 等统计信息以支持谓词下推（能根据 WHERE 条件跳过整块不读）。选它们的好处是"存储与计算解耦、格式开放、多引擎都能读"，一份 Parquet 数据可被 Spark、DuckDB、Trino、ClickHouse 共用。这也是"湖仓"（lakehouse）架构的存储地基：对象存储上放开放列存格式，上层挂多种计算引擎。

⚙演进快·锚版本·随时变（核实 2026-08-01）：云数据仓库（Snowflake、BigQuery、Redshift 等）与湖仓表格式（Apache Iceberg、Delta Lake、Apache Hudi）是本主题演进最快的部分，产品能力、默认压缩、格式版本频繁更新；DDIA 2e 也把"Cloud Data Warehouses"作为分析存储的新小节。选型结论会随版本变化，任何具体能力/默认值须以当前版本官方文档为准，本报告不锁定。

### 09-3.2.6 混合布局与 HTAP 取向（点到）

现实中有介于两者之间的方案。PAX（Partition Attributes Across）在一个页内先按行分区、区内再按列存，兼顾"取整行不必跨页"和"扫单列有局部性"，是行列混合布局的经典思路。面向 HTAP（同时扛 OLTP 与 OLAP）的系统常用"双存储"：行存副本服务事务、列存副本（或 delta store + 列存主体）服务分析，后台把行存增量转成列存。

这里点到为止即可：选型上要意识到"行存 vs 列存"不是非此即彼，当一个系统必须同时扛事务和分析时，答案往往是"两种布局都要，加一层同步"。具体架构（delta store、行列混合引擎）属内核实现，见 L6-04 的 HTAP 相关内容。

## 09-3.3 OLTP 索引结构选型：聚簇 / 覆盖 / 多列

### 09-3.3.1 聚簇索引 vs 非聚簇（堆表 + 二级索引）

表的行本身按什么组织。聚簇索引（clustered index）把整行数据直接存在主键索引的叶子节点里，行的物理顺序就是主键顺序（MySQL/InnoDB 的主键即聚簇索引）。非聚簇方案里行存在一个无序的堆（heap file）中，索引的叶子只存指向堆中行位置的指针（PostgreSQL 走这条路，所有索引都是二级索引，指向堆里的 tuple）。

聚簇索引让"按主键点查/范围查"极快，因为找到索引叶子就拿到了整行、且相邻主键物理相邻；代价是二级索引要间接一跳（先查到主键、再用主键查聚簇索引），且行变大或更新可能引起页分裂/搬迁。堆表方案下所有索引地位平等、二级索引指针直达行，但任何查询都要"索引 → 堆"两步。DDIA 把"聚簇索引 / 非聚簇 / 覆盖索引"作为一组连续概念讲，选型时先定这一层。

### 09-3.3.2 覆盖索引与包含列：消除回表

回表（也叫二次查找）指的是：二级索引只存了被索引的列和一个行定位符，查询要的其它列不在索引里，于是查完索引还得再去主表/堆把整行捞回来，多一次随机 I/O。覆盖索引（covering index）指一个索引恰好"覆盖"了某查询需要的所有列——索引里就能取到全部结果，完全不用回表。很多数据库支持"包含列"（include columns）：把不参与排序/查找、但想顺带存进叶子的列挂在索引上，专门用来做覆盖。

覆盖索引是用"索引体积变大、写入更慢"换"读少一次随机 I/O"，对高频、固定列集的读查询收益巨大。易错的是把很多列都塞进包含列，导致索引臃肿、写放大、缓存命中率下降——覆盖要针对具体高频查询精准设计，不是越覆盖越好。判断某查询是否走了覆盖索引，可用 `EXPLAIN`（如 PostgreSQL 里看到 Index Only Scan 即表示无需回表）。

### 09-3.3.3 多列（复合）索引与最左前缀

多列索引（复合索引）把几个列按给定顺序拼成一个排序键建索引，例如 (last_name, first_name)。它的关键性质是"最左前缀"（leftmost prefix）：这个索引能高效服务"按 last_name"或"按 last_name 再按 first_name"的查询，但不能高效服务"只按 first_name"的查询——因为数据是先按第一列排、第一列相同时才按第二列排，跳过第一列就失去了有序性。

以为建了 (a, b) 索引就等于同时有了 a 的索引和 b 的索引，其实只等于有了 a 的索引和 (a,b) 的索引，单独查 b 用不上。选型上，多列索引的列顺序要按查询模式定：最常用作等值过滤的列放最左，范围过滤的列放后面。列顺序错了，索引形同虚设。DDIA 也提到多维/地理查询需要专门的多维索引（如 R-tree），普通多列 B+树索引处理不了"同时对两个维度做范围"的查询。

### 09-3.3.4 二级索引里存什么：主键 vs 行指针

二级索引的叶子存"指向行的什么"有两种设计，直接影响性能特征。一种存物理行指针/位置（如堆表里的 tuple id）：查得快、直达行，但行一旦物理搬迁（更新变大、页分裂）指针就要维护，否则失效。另一种存主键值（聚簇索引方案，如 InnoDB 二级索引存主键）：行搬迁不影响二级索引（因为主键不变），但每次二级索引查询都要多一次"用主键查聚簇索引"的跳转。

这不是用户能随便改的旋钮，而是引擎的既定设计，但了解它能解释很多性能现象——比如为什么 InnoDB 里主键选得又大又长会让所有二级索引都变胖变慢（因为它们都内嵌主键值），从而"主键要短"成为一条经验法则。

### 09-3.3.5 索引的写代价：不是越多越好

每一个索引都是一份需要与主数据同步维护的冗余结构。加一个索引，读可能变快，但每次插入/更新/删除都要顺带维护这个索引（可能触发它自己的页分裂或 compaction），写入变慢、空间变大、缓存被稀释。因此索引数量本身是一个要控制的成本。

选型原则是"按真实查询建索引，定期清理没用上的索引"。常见反模式：为每个列都建单列索引、或建了一堆从没被查询命中的索引，白白拖慢写入。判断方法是结合慢查询和索引使用统计（如 PostgreSQL 的 `pg_stat_user_indexes`）找出零命中索引删掉。写密集表尤其要克制索引数量——这也呼应 09-3.1：底层是 LSM 还是 B+树，会进一步放大或缓解索引维护的写代价。

### 09-3.3.6 特殊索引点到：部分 / 表达式 / 全文 / 向量

除了常规 B+树索引，几类特殊索引在特定负载下是选型利器（点到为止）。部分索引（partial index）只对满足条件的行建索引（如只索引 `status='active'` 的行），索引更小、更新更省，适合查询总是带某固定过滤条件的场景。表达式/函数索引对某个表达式的结果建索引（如 `lower(email)`），让基于该表达式的查询也能走索引。全文索引针对文本做分词与倒排，服务关键词检索。向量索引（针对 embedding 的近邻搜索，如 HNSW/IVF）服务语义检索与 RAG。

⚙演进快·锚版本·随时变（核实 2026-08-01）：全文检索与向量索引是本主题演进最快的部分，DDIA 2e 专门新增了"Full-Text Search"与"Vector Embeddings"小节反映这一趋势；各库（PostgreSQL 的 pgvector、专用向量库）的索引类型、参数与默认值频繁更新，选型结论须以当前版本文档为准，本报告不锁定具体算法参数。

## 09-3.4 内存数据库与持久化 / 耐久性取舍

### 09-3.4.1 内存数据库是什么、为何快

内存数据库（in-memory database）把数据集主要保存在内存（RAM）里，而不是以磁盘为主存储、内存只作缓存。代表有 Redis、Memcached（缓存型），以及 VoltDB、部分内存 OLTP 引擎（数据库型）。DDIA 用一个小节"Keeping Everything in Memory"专门讨论它。

一个关键澄清（也是常见误解）：内存数据库快，主要原因并不是"省掉了读磁盘"。因为磁盘型数据库若内存够大，热数据本来就被缓存在内存里，读命中缓存时也不碰磁盘。内存数据库真正的性能来源，是它可以省掉"为了能落盘而设计的一整套编码开销"——不需要把数据编码成适合磁盘读写的页格式、不需要管理 buffer pool 的换入换出，可以用更适合内存的数据结构（如直接用指针连接的对象）。这才是它相对磁盘引擎的结构性优势。

### 09-3.4.2 内存数据库如何做持久化

"数据在内存里"和"断电就丢"不是必然绑定的——内存数据库通常仍提供持久化，只是把落盘从"主存储路径"挪到了"旁路"。常见手段有三类，往往组合使用：写预写日志（WAL / append-only log），把每个改动顺序追加到磁盘日志，崩溃后重放恢复；周期性快照（snapshot / checkpoint），把整个内存状态定期整体转储到磁盘，缩短恢复时重放的日志量；以及复制到其它节点，靠多副本冗余而非单机落盘来抗故障。

以 Redis 为例，它提供 AOF（append-only file，近似 WAL）和 RDB（快照）两种持久化，可单用或组合。要点是：这些持久化是为了"崩溃/重启后能恢复"，而正常读写仍在内存进行，磁盘只在旁路记账，因此不拖累在线性能。

### 09-3.4.3 耐久性不是全有全无：fsync、组提交与复制的权衡

耐久性（durability，ACID 里的 D）指"已提交的数据不会因崩溃而丢失"，但它在工程上是一个连续谱，不是开关。写日志到操作系统缓冲区不等于真的落到磁盘介质——必须调用 `fsync` 把缓冲刷到持久介质才算真正落盘，而 `fsync` 很慢。于是出现权衡：每次提交都 `fsync`（最强耐久、最慢），还是攒一批提交一起 `fsync`（组提交 group commit，吞吐高但崩溃时可能丢最后一小段未刷的提交），还是干脆异步刷盘（最快、丢失窗口最大）。

DDIA 明确指出：单机 `fsync` 也可能因磁盘固件、断电时机等原因不完全可靠，所以严肃系统往往不把耐久性只押在"单机落盘"上，而是叠加复制——数据写到多个节点后才算提交，用冗余换耐久。选型时要问的是"能容忍丢多少、丢多久的数据"（对应 RPO 概念），据此在 fsync 频率、组提交、同步/异步复制之间取一个点。绝对的"零丢失"代价极高，多数系统选择明确界定的弱一点的保证。

### 09-3.4.4 数据大于内存：反缓存与溢出

内存数据库的天然约束是"数据得装得进内存（或内存加持久介质的组合）"。当数据集超过内存怎么办？一种思路是反缓存（anti-caching）：把最近最少用的数据从内存驱逐到磁盘、只在被访问时再拉回，与传统"磁盘为主、内存做缓存"正好方向相反（内存为主、磁盘兜底冷数据）。另一种是分层/溢出到磁盘或用非易失内存（NVM/持久内存）扩展容量。

内存数据库不是"数据无限大也能用"，它的性价比在"热数据集能被内存容纳"时最高；一旦大量冷数据被迫在内存和磁盘间搬进搬出，它相对磁盘引擎的优势就被侵蚀。容量规划（数据规模 vs 内存成本）是选它之前必须算的账。

### 09-3.4.5 何时选内存数据库、何时选持久磁盘引擎

当负载是小而热的数据集、要求极低延迟和高吞吐、且能接受"用复制/日志换耐久"或本身可容忍少量丢失（缓存、会话状态、排行榜、实时计数、消息队列中转、特征服务）时，内存数据库是很好的选择。当数据规模远超内存、要求强耐久与完整事务、以持久化为第一位（核心业务记录、账务、需长期可靠留存的数据）时，仍应选以磁盘为主存储的引擎（B+树或 LSM，按 09-3.1 再细分）。

很多系统用"内存数据库/缓存 + 磁盘数据库"两层组合——热路径走内存拿速度，权威数据留在持久引擎拿耐久，用缓存失效/写穿策略把两者串起来。这样就不必让单一引擎同时满足"极快"和"极耐久"这对矛盾诉求。内存 OLTP 与持久内存引擎的更底层实现属内核话题，见 L6-04 相关内容。
