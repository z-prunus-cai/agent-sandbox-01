评估是把「这个语言模型到底好不好用」这个模糊问题，拆成一组可测量、可复现、可比较的数字的工程学。它是分类器评估纪律在语言模型上的系统化延伸：同样讲任务、指标、划分与防泄漏，但对象从「一个预测标签」变成「一段自由生成的文本」，而且要在质量之外同时盯住延迟与成本。这篇按三条线展开——先讲方法学（怎么设计一次公正的测量），再讲基准与污染（用什么题、题为什么会失效），最后讲正确性×性能的联合评估（系统视角下质量不能脱离速度和钱单独看）。

本篇所有具体基准的分数、排行、饱和程度都随时点漂移，正文只讲「机制在该锚点下如此」，不给排名、不下定论；引用到的第三方测得数值一律标注来源并按需标「待核」。

## 08S-10.1 评测方法学

### 内在评估与外在评估的分野

评估语言模型有两条互补的路子。内在评估直接量模型的「语言建模本领」本身，最典型的是困惑度（perplexity）——在一批留出文本上，模型平均有多「意外」。外在评估把模型放到具体下游任务上（问答、数学、代码、指令遵循），量它在任务上的成败。两者测的不是同一件事：内在指标反映分布拟合，外在指标反映能力，二者相关但不等价，一个困惑度更低的模型未必在某个下游任务上更强。

对初学者，最好的直觉是「体检指标 vs 实战成绩」。困惑度像血压心率，稳定、连续、便宜，训练时每一步都能看，适合监控和早期比较；下游任务成绩像真打一场比赛，贵、离散、噪声大，但它才是用户真正在意的东西。系统实践里两者都要：训练中用内在指标盯收敛，交付前用外在指标验能力。一个常见的初学者误区是只看训练 loss 就宣称模型「更好」——loss 下降只说明它更会预测这批语料的下一个词，不代表它更会做题。

### 困惑度与 bits-per-byte

困惑度是把交叉熵损失换算到更好读的尺度，定义为每个 token 平均负对数似然的指数：

PPL(x) = exp( − (1/N) · Σ_{i=1}^{N} log p(x_i | x_{<i}) )

它可以读成「模型在每一步平均在多少个等概选项之间犹豫」——困惑度 10 约等于每个词都在 10 个候选里猜。困惑度越低越好，下界是 1（完全确定）。

困惑度依赖分词，不能跨不同 tokenizer 直接比。同一段文本，词表更大、平均每 token 覆盖更多字符的分词器，token 数 N 更少，per-token 困惑度天然更低，但这不代表模型更懂语言。为消除这个偏差，跨模型比较应改用与分词无关的 bits-per-byte（每字节比特数）：

BPB = − (1/n_bytes) · Σ log2 p(x_i | x_{<i})

它把对数似然摊到原始字节数而非 token 数上，让不同词表的模型站上同一把尺子。有第三方分析报告分词差异可使传统 per-token 困惑度相差达约 21.6%（待核，来自单一来源的量化实验），无论具体数字如何，结论是稳的：跨分词器只信 bits-per-byte 或 bits-per-character，不信裸困惑度。另一个易错点是困惑度只在自然文本上有意义，对结构化输出或经过指令微调、分布已偏移的模型，困惑度与实际能力可能脱钩。

### 任务、指标与协议的三件套

一次评估的设计要同时定清三样东西：任务（考什么能力）、指标（怎么打分）、协议（在什么条件下测）。任务决定覆盖面——单一任务（只测数学）会给出片面画像，所以成规模的评估用一整套任务谱系（理解、推理、代码、常识、安全等）。指标决定「对」的定义——精确匹配、F1、pass@k、校准度各测不同侧面。协议决定可比性——同样的题，few-shot 示例给几个、prompt 模板怎么写、用对数似然打分还是让模型自由生成再判分，都会显著改变分数。

初学者最容易忽略协议这一层，却正是它让「同一个模型在两篇论文里分数不同」成为常态。举个最小例子：MMLU 这类多选题有两种评分法，一种是比较模型给每个选项字母（A/B/C/D）的对数概率、取最高者，另一种是让模型生成答案再解析文本。两种协议在同一模型上能差出几个百分点。因此报告分数时必须连协议一起报——few-shot 数、prompt 版本、评分方式——否则数字不可比。这也是标准化评估工具存在的理由：把协议冻结成代码和配置，让不同模型跑在「同一份输入、同一套代码」上。

### 生成式输出为什么难打分

分类任务的输出是一个标签，对错一目了然；生成任务的输出是一段自由文本，正确答案往往不唯一。这让打分从「查表」变成「判断」。对有唯一客观答案的任务（数学最终数、代码能否通过测试），可以用精确匹配或执行测试自动、可靠地打分；对开放式任务（写摘要、答建议、多轮对话），没有唯一标准答案，只能靠参考答案的重叠度指标（如 BLEU/ROUGE，但与人类判断相关性弱）、人类评审，或用另一个强模型当裁判。

代码类任务的标准指标是 pass@k：生成 k 个候选、只要有一个通过全部单元测试就算过。为降低采样方差，通常生成 n≥k 个样本、数出其中通过的 c 个，用无偏估计：

pass@k = 1 − C(n−c, k) / C(n, k)

这个式子的直觉是「从 n 个样本里随机抽 k 个、一个都不通过的概率」的补。它体现了生成式评估和分类评估的一个根本差异：生成有随机性，一次采样的成败噪声大，必须多采样、报统计量而非单点。这也提醒初学者，任何生成式分数都应带上采样温度、样本数等设定，否则不可复现。

### LLM 当裁判（LLM-as-judge）及其偏置

面对没有客观答案的开放式任务，一条近年被广泛采用的捷径是用一个强语言模型充当裁判，给候选回答打分或做两两胜负判定。它便宜、快、可扩展，在设计良好时与人类偏好有相当高的一致性——引入 MT-Bench 与 Chatbot Arena 的工作报告强裁判（如当时的 GPT-4）与人类的一致率可超过 80%，与人类之间的一致率相当（arXiv 2306.05685）。

但这条捷径带着系统性偏置，必须知情使用。同一工作明确点出至少三类失效：位置偏置（偏好排在前面的回答，该工作报告对首位回答的偏好在某些设置下可高达约 75%，待核为该论文测得值）、冗长偏置（偏好更长的回答，哪怕质量没更高）、自我增强偏置（模型偏爱与自己风格相近或自己产出的回答）。给初学者的直觉：裁判本身也是个有主观倾向的模型，不是中立的尺子。缓解手段包括交换两个回答的位置各评一次再取一致结果（消位置偏置）、控制长度、用多个不同家族的裁判取共识。切忌把「某模型在某 LLM 裁判榜上更高」直接当成客观真理——裁判、被测、协议三者纠缠。

### 人类评估与竞技场式排名

在没有客观答案、又不完全信任模型裁判时，人类评估是金标准。规模化的做法不是让人给绝对分（人对绝对分标准不一），而是做两两对比（pairwise）：给评审两个匿名回答，问哪个更好。众包对战平台（Chatbot Arena 一类）把大量这种匿名两两对战汇集起来，再用评分模型把胜负记录换算成一个排名分。

常用的换算是 Elo 或其统计基础 Bradley-Terry 模型，核心假设是每个模型有一个隐含实力分 R，A 胜 B 的概率随分差单调上升：

P(A 胜 B) = 1 / (1 + 10^{(R_B − R_A)/400})

直觉上这就是国际象棋的排位逻辑——赢了预期会输的对手加分多，输给预期会赢的对手扣分多。它的好处是把海量两两比较压成一维可比的分，且对新模型可增量更新。易错点：这类排名是相对的、随参与者集合和投票分布漂移，不同时点的分不能硬比；且众包投票有群体偏好（偏爱特定风格），高分不等于在你的具体任务上更强。

### 统计严谨与可复现性

评估分数是带噪声的估计量，不是精确真值。噪声来自采样随机性、few-shot 示例的选择、题目子集的抽样。因此严谨的报告要给不确定性——多个随机种子取均值与标准差、给置信区间、在比较两个模型时看差异是否超出噪声，而不是只报一个孤零零的数字就宣布胜负。两个模型差 0.3 个百分点、但各自的波动就有 1 个百分点时，这个「领先」没有意义。

可复现性是另一条系统红线。要让别人复现你的分数，必须固定并公开：题目版本、prompt 模板、few-shot 数与示例、评分脚本、解码参数、随机种子。标准化评估框架（如 EleutherAI 的 lm-evaluation-harness）正是为此而生——它把公开的 prompt、任务定义、评分逻辑集中管理，并给任务打版本号，使得任务修 bug 后旧分数仍可按旧版本复现，让不同论文的结果做到「同一输入、同一代码」的苹果对苹果比较。给初学者的落地建议：报分数时连同工具版本和任务版本一起报，别口头说「我们测了 MMLU」。

## 08S-10.2 基准与污染

### 基准全景与它们各自考什么

基准（benchmark）是一套固定的题目加标准答案加评分规则，让不同模型在同一张考卷上比。常见的一手基准各有分工：MMLU 考跨 57 学科的多选知识与理解（arXiv 2009.03300）；GSM8K 考小学数学多步推理（arXiv 2110.14168）；HumanEval 考从函数签名+文档生成可通过测试的代码（arXiv 2107.03374）；GPQA 考研究生级、专家都难做对的科学难题，专门抵抗「靠背题」（arXiv 2311.12022）。它们共同点是有客观可自动判分的答案，因而便宜可复现。

没有单一基准能代表「模型好」。每个基准只照亮能力的一个切面，组合起来才成画像；而且基准会随模型进步而「饱和」——当顶尖模型都逼近满分，这个基准就失去区分力。近一两年 MMLU、GSM8K、HumanEval 这类经典基准在前沿模型上普遍逼近或超过 90% 而趋于饱和（多来源综述报道，待核具体数值随时点变），于是社区不断推出更难的新卷（如 GPQA、以及各种「-Pro/-Hard」变体）来重新拉开差距。选基准时要问：它还没被你的模型考满吗？它测的是你在意的能力吗？

### 综合评测套件：多指标、标准化

单个基准+单个指标容易以偏概全，于是有了把很多任务和很多指标系统组织起来的评测套件。HELM（Holistic Evaluation of Language Models，arXiv 2211.09110）是代表：它主张评估不能只看准确率，而应在同一批场景上同时测多个维度——其论文报告在 16 个核心场景上尽可能测量 7 类指标（准确率、校准度、鲁棒性、公平性、偏见、毒性、效率），覆盖数十个场景，目的是把「准确率之外的维度」和「模型间的权衡」显式摆出来，并把所有模型放到同一套标准化条件下密集比较。

与 HELM 这种「场景×指标矩阵」互补的是执行层的标准化框架，如前面提过的 lm-evaluation-harness，它统一 prompt、任务定义与评分代码，是很多论文与实验室事实上的评测底座。给初学者的直觉：HELM 回答「该测哪些维度、哪些场景」（测量的设计蓝图），harness 回答「怎么把它一致地跑出来」（测量的执行工具）。两者都强调透明与可比，是对抗「各测各的、分数没法比」这一乱象的系统性回应。要点是这些套件是活的（living benchmark），会持续加新场景、新指标、新模型，引用时要锚版本与时点。

### 什么是数据污染

数据污染（contamination，也叫测试集泄漏）指基准的测试题——或其答案——出现在了模型的训练数据里。因为前沿模型的训练语料是从整个网络海量抓取的，而基准题目和题解也在网上流传，测试题被无意「学过」几乎是默认风险。后果是分数虚高：模型看着像在「推理」，其实是在「回忆」见过的答案，评估因此失真，甚至给出误导性的能力结论。

这就像考试前老师不小心把真题连答案发到了公开论坛，学生背下来再进考场。分数很漂亮，但没测出真本事。污染有两种形态需要区分：精确污染（测试样本逐字出现在训练数据）与句法/语义污染（以改写、翻译、加前缀等表面变体重现）。后者更隐蔽，能绕过简单的字符串比对，却照样抬高分数——有工作指出泄漏甚至能跨语言，对表面重叠检测隐形。这是为什么「我们做了去污染」这句话本身要追问「去到哪一层」。

### 污染怎么检测、为什么难

检测污染的方法随「你能不能看到训练数据」分两类。训练数据可得时，最直接的是重叠检测——用 n-gram 或子串匹配，看测试题是否出现在训练语料里；开源数据集常这样做「去污染」。但绝大多数模型不公开训练数据，这类方法就失效了。

对只能通过 API 访问的黑盒模型，检测转向推理时的行为信号：成员推断攻击（membership inference）试图判断某条样本是否「被训练过」；有的方法比较模型在原题与等价改写题上的表现差（见过原题会异常地好）；还有工作在推理时重采样或重写 prompt 做校准（如重复采样校准、用辅助模型改写 prompt 的推理时去污染）。这些方法都不完美，且与改写型污染是持续的攻防。文献里报告过相当规模的污染——例如某工作（NAACL 2024 一项测量）称约 29% 的 MMLU 测试项显出污染迹象，换成干净镜像题后某些模型分数明显回落（这些具体百分比来自单篇研究、标「待核」，本篇不据以下定论）。无论确切数字，稳的结论是：把高基准分直接当真本事，在污染普遍的今天是危险的。

### 饱和、失效与防污染基准的走向

静态基准有生命周期：发布→被追赶→饱和/污染→失去区分力。应对这个宿命，社区转向抵抗污染的基准设计。一条路是私有测试集（题目不公开，只公开结果），但牺牲透明与可复现。另一条近年活跃的路是动态/时序刷新——持续用「模型训练之后才出现」的新素材出题，从时间上杜绝泄漏。LiveBench 是代表（ICLR 2025 Spotlight）：每月放出新题，题源取自近期数学竞赛、arXiv 论文、新闻等，且尽量用有客观 ground-truth、可自动判分的题，从而既防污染又不依赖 LLM 裁判。此外还有通过自动构造「基于新知识」的题来防泄漏的路线（如 AntiLeakBench 类）、以及刻意做成「抗污染」的 MMLU 变体。

基准不是永恒的真理尺，而是有保质期的测量工具。选用时要同时问三件事——它饱和了没、它可能被污染了没、它测的能力对不对口。这也是「系统视角」的一部分：评估基础设施本身需要被维护、被更新、被质疑，而不是一劳永逸。这些防污染方案本身仍在快速演进，⚙演进快·随时变，不宜排名或下定论。

- CS336 Spring 2026 L12（Evaluation）作为课程锚点。
- 冲突记录：不同污染检测研究对「污染程度」估计差异大（取决于检测方法与阈值），属方法分歧，两边都记不裁定；「私有测试集 vs 公开动态基准」在透明性与防污染上各有取舍，并存无定论。

## 08S-10.3 正确性 × 性能联合评估

### 为什么系统视角要把质量和性能一起看

前两节测的是「模型答得对不对」。但把模型部署成服务后，用户体验和运营成本还取决于「答得多快、多贵」。同样准确率的两个方案，一个每次回答要等 5 秒、每百万 token 花 10 元，另一个 1 秒、1 元，对产品是天壤之别。所以系统视角下的评估必须把正确性（质量）与性能（延迟、吞吐、成本）放到同一张表里联合看，而不是先选质量最高的、再事后担心它跑不起。

这就像买车不能只看最高时速，还得看油耗、价格、能不能塞下全家。一个只优化单一指标（比如榜单准确率）的选择，很可能在真实约束下是坏选择——最强模型可能贵到无法规模化，或慢到违反交互式产品的响应要求。联合评估的目标，是在「够好」的质量门槛下，把速度和成本一并纳入决策。这里的性能指标正是推理/serving 一节讲过的那套（TTFT、TPOT、吞吐），此处把它们和质量指标拼到一起。

### 三根轴：质量、延迟、成本

联合评估的常见做法是沿三根轴度量。质量轴用前两节的基准分数或人类/裁判偏好。延迟轴用面向用户的时间指标：首 token 时延 TTFT（用户等多久看到第一个字）、每输出 token 时间 TPOT（后续吐字快慢），二者共同决定「感觉快不快」。成本轴用单位产出的钱，最常见是每百万 token 价格，或折算到「每完成一个任务/请求的成本」。

对初学者要点破一个反直觉处：这三根轴常常互相拉扯。提高吞吐（多请求拼批）往往抬高单请求延迟；用更大模型换质量会同时抬高延迟和成本；用量化、投机解码等手段压延迟/成本又可能损一点质量。因此不存在「全都最好」的方案，只有在特定权衡下的合适方案。还有一个吞吐 vs 延迟的经典张力：面向吞吐优化的批处理让 GPU 更省钱，却可能让单个用户等更久——评估交互式产品要看单请求延迟，评估离线批处理要看总吞吐，两者不能混谈。

### Pareto 前沿：多目标下「谁更好」的正确问法

当有多个互相冲突的目标时，「哪个方案最好」这个问题本身没有单一答案，正确的工具是 Pareto 前沿。一个方案 A「支配」方案 B，是指 A 在所有轴上都不差于 B、且至少一根轴上严格更好：

A 支配 B  ⟺  ∀ 轴 i: A_i ≥ B_i，且 ∃ 轴 j: A_j > B_j （各轴已统一为「越大越好」）

没有被任何方案支配的那些方案，构成 Pareto 前沿——它们代表「要在某根轴上更好，就必然在另一根轴上更差」的最优权衡集合。

把每个候选模型/配置画成质量-成本平面上的一个点，左上（高质量、低成本方向）的外沿连线就是前沿；被前沿「压在里面」的点是应当被淘汰的（有别的方案在各方面都不比它差）。前沿上的点则无法互相碾压，选哪个取决于你的偏好（预算紧就往低成本端选，质量优先就往高质量端选）。要注意加一根轴会改变结论：一个又便宜又准但很慢的方案，在二维（质量-成本）里可能在前沿上，一旦把延迟作为第三轴，它可能被一个「稍贵一点但快得多」的方案支配掉。所以联合评估要一次性把在意的轴都放进来。有独立操作性基准（如 BELLS-O）就明确沿检出率、误报率、延迟、成本四轴画 per-use-case 的 Pareto 前沿来暴露权衡（arXiv 2606.20668，待核为单一来源示例，不作背书）。

### 公平比较的前提：把系统条件钉死

联合评估最容易出错的地方，是拿不可比的数字比较。同一个模型，换了硬件代际、批大小、序列长度、量化精度、推理框架，延迟、吞吐、成本会大幅变化；换了 prompt、few-shot 数、解码参数，质量也会变。因此报告联合评估结果时，必须把这些系统条件一并钉死并公开，否则「A 比 B 快 2 倍」这类结论毫无意义——可能只是 A 跑在更新的卡上。

报质量要连协议（题目版本、few-shot、评分方式、解码温度、样本数）；报性能要连硬件（型号/代际）、批大小、并发、输入/输出长度、精度（如 FP16/FP8/INT8）、框架与版本。特别提醒量化——它是拿一点质量换显存和速度的典型手段，做联合评估时必须在同一质量口径下比，不能拿量化后省下的成本去和未量化的质量比，那是偷换前提。一个稳妥的比较范式是「等质量比成本/延迟」或「等成本比质量」：先对齐一根轴，再看另一根，避免两根轴同时变导致的混淆。这里的「质量」也要用前两节的干净、未污染基准来定，否则联合评估的质量轴本身就是虚的。
