这一大主题是"系统度量学"的入口：拿到一个语言模型，怎么在动手训练前就把它要花多少参数、多少算力、多少显存这三本账估出来。核算不是为了精确到个位，而是为了在数量级上判断"这个模型/这块卡/这个批大小能不能跑得起来"。下面五章分别讲：怎么用 einops 把张量形状说清楚（2.1），怎么数参数（2.2），怎么估算力 FLOP（2.3），怎么估显存（2.4），以及 PyTorch 里落地这些核算要懂的系统级用法（2.5）。

## 08S-2.1 einops 张量重排

### einops 是什么，为什么要声明式重排

einops 是一个第三方张量操作库，核心思想是用一个带命名维度的"模式字符串"来描述张量形状怎么变，而不是靠一串难懂的 `reshape`/`transpose`/`permute` 数字下标。它后端无关，同一套写法能作用在 numpy、PyTorch、JAX、TensorFlow 的张量上。三个主函数是 `rearrange`（重排/合并/拆分维度）、`reduce`（带聚合的重排，如求和求均值）、`repeat`（复制扩展维度）。

初学者最容易被张量形状操作绕晕：`x.permute(0, 2, 1, 3)` 这行代码你得记住每个位置原来是什么维度，读代码的人还要反推。einops 让你把同一件事写成

```
rearrange(x, 'b h s d -> b s h d')
```

字母是你给每个维度起的名字（batch、head、seq、dim），箭头左边是输入布局、右边是想要的布局。这行代码自解释：把"头"和"序列"两维交换。声明式的意思就是你只说"要什么形状"，具体怎么 reshape/permute 由库去算。这在 Transformer 代码里价值极大——多头注意力反复在 `(batch, seq, heads*dim)` 和 `(batch, heads, seq, dim)` 之间切换，用 einops 写出来一眼能读懂维度语义。

### rearrange：reshape 与 permute 的统一

`rearrange` 把"换轴顺序"（permute/transpose）和"合并/拆分维度"（reshape/view）统一到一个模式里。合并维度就是把右边几个名字并到一起，拆分维度就是在右边把一个名字拆成两个并给出其中一个的大小。

比如多头注意力里把 `d_model` 拆成 `heads × head_dim`：

```
rearrange(x, 'b s (h d) -> b h s d', h=num_heads)
```

括号 `(h d)` 表示输入的最后一维实际是 `h*d` 打平的，用 `h=num_heads` 告诉库怎么拆；同时右边把 `h` 提到 `s` 前面，等价于先 reshape 再 permute。反过来把多头拼回去：

```
rearrange(x, 'b h s d -> b s (h d)')
```

要理解的关键是维度顺序有语义：`(h d)` 和 `(d h)` 打平出来的数据排列不同，写错了数据就错位但形状还对，不会报错——这是最隐蔽的 bug，所以名字顺序必须和真实内存/语义一致。

### reduce：带聚合的重排

`reduce` 在重排的同时对"消失的维度"做聚合。凡是出现在左边、不出现在右边的名字，就沿那一维按指定方式（`mean`/`sum`/`max`/`min`/`prod`）归约掉。

对一个 `(batch, seq, dim)` 张量沿序列求平均（做句向量池化）：

```
reduce(x, 'b s d -> b d', 'mean')
```

它的好处是把"沿哪一维聚合"写在形状里，比 `x.mean(dim=1)` 更不容易数错轴。初学者常犯的错是搞不清 `dim=1` 是哪一维、聚合后维度是被删掉还是保留（`keepdim`）；einps 里维度删没删，看箭头右边有没有那个名字就知道，很直观。

### repeat：复制扩展维度

`repeat` 是 `reduce` 的逆向操作：在右边引入左边没有的新名字，就沿这个新维度把数据复制若干份。

把一个 `(seq, dim)` 的张量扩成一个 batch：

```
repeat(x, 's d -> b s d', b=batch_size)
```

典型用途是把位置编码、掩码这类"对所有样本相同"的张量广播成批。要注意 `repeat` 是真的复制数据（占显存），而 PyTorch 的广播（broadcasting）在很多算子里是虚拟展开不额外占内存——能靠广播就别显式 `repeat`，这是省显存的小习惯。

### einsum：命名维度的矩阵乘

einops 还提供 `einsum`（也见于 numpy/torch 原生的 `einsum`），用命名下标描述任意的张量收缩（矩阵乘、批量矩阵乘、点积等）。规则是：出现在输入、但不出现在输出的名字，就是要"求和收缩"掉的维度。

带 batch 和多头的注意力打分 `Q·Kᵀ`：

```
einsum(Q, K, 'b h s d, b h t d -> b h s t')
```

这里 `d` 只在输入两边出现、不在输出里，于是沿 `d` 做乘加求和——正是内积；`s` 和 `t` 分别是查询位置和键位置，输出成一张 `s×t` 的注意力分数表。einsum 的价值是把"哪些维度对齐相乘、哪些求和、哪些保留"用一行讲清，避免手动 `transpose` + `bmm` 的下标地狱。它的代价是可读性换来的抽象，写错收缩维度时同样是静默的数值错误。

### 易错点：view / reshape / contiguous 与 einops 的关系

einops 底层仍然落到 PyTorch 的 `reshape`/`permute` 等算子，所以它继承了一个底层约束：`permute`/`transpose` 只是改了"怎么看这块内存"（步长 stride），并没有真正搬数据，得到的张量在内存里是非连续（non-contiguous）的；而某些操作（如 `.view()`）要求内存连续，此时需要先 `.contiguous()` 触发一次真实拷贝。

初学者常见报错是 permute 之后直接 view 报 "view size is not compatible ... use .reshape()"。`reshape` 会在必要时自动帮你 `contiguous`（可能悄悄多一次拷贝），`view` 不会。einops 的 `rearrange` 内部通常用 `reshape` 语义，一般不会抛这个错，但你要意识到：某些重排会引发一次真实数据搬运，是有显存和带宽成本的，不是纯符号操作。这一点在 2.5 的内存布局里还会再碰到。

## 08S-2.2 参数量核算

### 为什么要逐层数参数

参数量 N 指模型里所有可训练权重的总数。会数参数是资源核算的地基：显存里参数/梯度/优化器状态三本账都按 N 缩放（2.4），训练算力 C≈6ND 也直接用 N（2.3）。数参数的方法就是把模型拆成各层，对每层按它的权重矩阵形状算出元素个数，再求和。

一个形状 `(m, n)` 的权重矩阵有 `m×n` 个参数；偏置向量长度 `n` 就是 `n` 个参数。整模型参数量 = 各层相加。真正要记的是 Transformer 每种子层的形状。下面用统一记号：`d` 为隐藏维 `d_model`，`d_ff` 为前馈中间维（常取 `4d`），`L` 为层数，`V` 为词表大小。

### 嵌入层与输出投影

词嵌入把每个 token id 映射成 `d` 维向量，本质是一张 `V×d` 的查表矩阵，参数量为

```
V · d
```

输出侧的语言模型头（把 `d` 维隐藏态投回 `V` 维词表 logits）又是一个 `d×V` 矩阵，参数量同样 `V·d`。很多模型把输入嵌入和输出投影"权重绑定"（weight tying）共用同一张表，这时只算一份 `V·d`；不绑定则要算两份。

这两块要单独拎出来讲，是因为 Kaplan et al. 2020 定义缩放律用的参数量 N 特意"排除嵌入"（non-embedding parameters）——因为嵌入量随词表大小走、和模型深度/宽度的缩放规律不同。核算算力 6ND 时用的 N 一般也指非嵌入参数。初学者容易把 `V·d` 这一大块（词表几万、d 几千，乘起来上亿）算进去又用错公式，要分清"总参数量"和"非嵌入参数量 N"两个口径。

### 注意力子层参数

标准多头自注意力有四个权重矩阵：查询 `W_Q`、键 `W_K`、值 `W_V`、输出 `W_O`，每个都是 `d×d`（多头是把 `d` 切成若干头，但合起来的矩阵仍是 `d×d`）。所以注意力子层参数量为

```
4 · d²   （若带偏置再加 4d）
```

多头不改变参数总量。把 `d` 拆成 `h` 个头、每头 `d/h` 维，`W_Q` 仍把 `d` 维映到 `d` 维，只是逻辑上分块用；所以头数 `h` 影响的是计算的组织方式，不影响 `4d²` 这个参数量。偏置项在很多现代实现（如很多 LLaMA 系）里被去掉，核算时要按具体架构定，不确定就两种口径都标。

### 前馈子层参数

前馈网络（FFN/MLP）通常是"升维再降维"两个线性层：先 `d→d_ff`，再 `d_ff→d`。参数量为

```
d · d_ff + d_ff · d = 2 · d · d_ff
```

当 `d_ff = 4d`（最常见约定）时即 `8d²`。要注意门控变体（如 SwiGLU）会多一个投影矩阵，变成三个矩阵，参数量结构不同（这属于 08S-3 架构取舍，此处只提示核算时要看清 FFN 是两矩阵还是三矩阵，别套错公式）。

### 归一化与偏置项

每个归一化层（LayerNorm 或 RMSNorm）带的可学习参数很少：LayerNorm 有缩放 `γ` 和平移 `β` 各 `d` 个，共 `2d`；RMSNorm 只有缩放，`d` 个。一个 Transformer 块通常有两个归一化层（注意力前、FFN 前）。

这些项相对 `d²` 量级是小头（`d` vs `d²`），做数量级估算时常被忽略，但写"精确参数量"时不能漏。初学者容易只记大矩阵、忘了 norm 和 bias，导致数出来的参数比框架 `sum(p.numel())` 报的略少——差的往往就是这些线性项。

### 每层与整模型合计：N ≈ 12·L·d²

把一个 Transformer 块的主要参数相加：注意力 `4d²` + 前馈 `8d²`（取 `d_ff=4d`）≈ `12d²`（忽略 norm/bias 的线性小项）。乘以层数 `L`，得到非嵌入参数量的经验估

```
N ≈ 12 · L · d²
```

这正是 Kaplan et al. 2020 用的近似（其记法 N ≈ 12 · n_layer · d_model²）。要理解这个"12"的来历：4 来自注意力的四个 `d×d`，8 来自前馈的两个 `d×4d`，加起来 12。它是估算利器——只要知道层数和隐藏维，心算就能报出模型大概几亿几十亿参数。

这个 `12d²/层` 假设了 `d_ff=4d`、无门控、weight tying 视口径而定，且只是非嵌入部分。真实模型要加回嵌入 `V·d`（一份或两份）。做精确核算请以框架实际的 `sum(p.numel() for p in model.parameters())` 为准，`12Ld²` 只用于估数量级。门控 FFN、不同 `d_ff` 比例会让系数偏离 12，具体架构的确切系数标「待核」、按实际形状算。

## 08S-2.3 FLOP 核算

### 什么是 FLOP，矩阵乘的 2mkn

FLOP（floating-point operation）是一次浮点运算（一次乘或一次加）。FLOPs（带 s，也常写作 FLOP 数）指完成某计算要多少次浮点运算，用来度量算力开销。深度网络的算力几乎全花在矩阵乘上，所以核算 FLOP 的地基是一条：两个矩阵相乘 `(m×k)·(k×n)` 得到 `(m×n)`，需要

```
2 · m · k · n  FLOPs
```

那个因子 2 的来历要讲清：输出矩阵有 `m×n` 个元素，每个元素是长度 `k` 的向量点积，即 `k` 次乘法 + `k` 次加法 ≈ `2k` 次浮点运算（一次乘加 MAC 记作 2 FLOP）。所以总数 `m·n·2k = 2mkn`。初学者常漏掉这个 2、或把它和别的因子混淆，记住"一次乘加=2 FLOP"是全篇算力核算的原子。

### 前向传播 ≈ 2N FLOPs / token

把矩阵乘的 `2mkn` 推广到整个前向：一个权重矩阵参与前向时，本质是输入向量和它做一次矩阵乘，每个权重元素恰好被用于一次乘加，即贡献约 2 FLOP。于是处理一个 token、走完前向，算力约为

```
前向 ≈ 2 · N  FLOPs / token
```

其中 N 是（非嵌入）参数量。直觉是"每个参数每个 token 出两次力"：一乘一加。这条把 2.2 数出的参数量直接翻译成算力，是核算最爽的一步——不用逐层重算，参数量 ×2 就是每 token 前向 FLOP。

前提要标清：这条只统计矩阵乘（线性层、注意力的投影），忽略归一化、激活函数、偏置加法这些逐元素小算子（它们相对矩阵乘是小头）。它还忽略了注意力里 `QKᵀ` 和 `注意力权重·V` 这两步随序列长度平方增长的项——短上下文时可忽略，长上下文时要单独加（见下"边界"）。

### 反向传播 ≈ 2× 前向，训练 ≈ 6N / token

反向传播的算力约是前向的两倍：

```
反向 ≈ 2 · 前向 ≈ 4 · N  FLOPs / token
```

原因在于每个线性层反向要算两组梯度，各约等于一次前向矩阵乘的成本：一组是"对输入的梯度"（把误差往前一层传，需要一次和权重的矩阵乘），另一组是"对权重的梯度"（用输入和上游误差外积，又一次矩阵乘）。前向 1 次矩阵乘、反向 2 次，合计 3 次同量级矩阵乘；再乘以每次乘加 2 FLOP，就是前向 2N、反向 4N、合计每 token

```
训练 ≈ 6 · N  FLOPs / token
```

### C ≈ 6ND 的成立条件与边界

把每 token 的 6N 乘以训练总 token 数 D，得到训练一个模型的总算力经验估

```
C ≈ 6 · N · D
```

这是 Kaplan et al. 2020 和 Chinchilla（Hoffmann et al. 2022）都采用的核算基石，也是 CS336 L2 反复强调的一条。它的威力在于把三件事（参数、数据、算力）用一根绳串起来，缩放律和 compute-optimal 配比（08S-8）全建在它上面。

必须标清这是经验近似，成立条件是：(1) 算力被矩阵乘主导，N 用非嵌入参数量；(2) 忽略了注意力中与序列长度相关的项——更完整的写法要加一项，形如

```
C ≈ 6ND + 6 · L · D · s · d   （注意力 QKᵀ 与 AV 的贡献，随上下文长度 s 增长）
```

当隐藏维 `d` 远大于序列长度 `s`（即模型"宽而上下文不太长"）时，附加项相对 6ND 可忽略，6ND 就够用；长上下文（`s` 逼近或超过 `d`）时附加项不可忽略，纯 6ND 会低估。附加项的确切系数和形式各家推导略有出入（有的把注意力算力单列、有的并入），此处系数标「待核」，用时以所锚论文的具体定义为准。此外反向的"2×"是不做激活重算时的估计；开了梯度检查点（activation recomputation）会多一次前向重算，训练算力上浮到约 8N/token 量级——这属于用算力换显存的工程手段，具体倍数标「待核」、看重算策略。

### 前向/反向 FLOP 的直观拆解（每层）

想更细可以按层拆。一个 Transformer 层前向的主要矩阵乘 FLOP（批 B、序列 s、隐藏维 h、`d_ff=4h`）约为

```
每层前向 ≈ 24 · B · s · h²  +  4 · B · s² · h
```

前一项 `24Bsh²` 来自四个注意力投影（`8Bsh²`：`W_Q/W_K/W_V` 三个各 `2Bsh²` 合 `6Bsh²`，输出投影 `2Bsh²`）加前馈两层（`16Bsh²`）；后一项 `4Bs²h` 来自 `QKᵀ`（`2Bs²h`）和注意力加权求和 `A·V`（`2Bs²h`），正是随序列长度平方增长的部分。把 `24Bsh²` 对所有层、所有 token 累加，正好回到 `≈2N` 每 token 的估计（因为每层 `12h²` 参数 ×2 FLOP ×`Bs` 个 token = `24Bsh²`）。这条拆解让"6ND 忽略了 `s²` 项"变得具体可见：忽略的就是那个 `4Bs²h`。（该拆解系数与 Korthikanti et al. 2022 activation recomputation 论文一致。）

- CS336 L2 lecture_02 trace（"训练总 FLOP = 6 × 参数数 × token 数"的明确表述、矩阵乘 2mkn），核实 2026-08-01。
- Korthikanti et al. 2022「Reducing Activation Recomputation in Large Transformer Models」arXiv:2205.05198（每层 `24Bsh²+4Bs²h` 前向 FLOP 拆解、反向≈2×前向、逐元素项忽略），核实 2026-08-01。
- 交叉核对与冲突：四来源对"6ND、乘加=2FLOP、反向2×前向"一致。分歧点在"注意力 s² 项是否并入 6ND"：Kaplan 主用 6ND 并把注意力项作为附加/次要项，长上下文语境的推导（如 Korthikanti、各推理算术笔记）显式单列 s² 项——两口径都记，短上下文用 6ND、长上下文加 s² 项；附加项确切系数「待核」。`⚙演进快·锚论文时点`。

## 08S-2.4 显存预算

### 四本账总览

训练时显存主要花在四处，逐一核算再相加就是显存预算：参数（权重本身）、梯度（每个参数一份梯度）、优化器状态（Adam 的动量与方差）、激活（前向中间结果，反向要用）。前三本账都按参数量 N 线性缩放、和批大小无关；第四本账"激活"和批大小 B、序列长度 s、层数 L 都相关，是唯一随批大小涨的账，也是最常爆显存的一本。

前三本是"模型自带的固定开销"，激活是"跑起来才产生的动态开销"。推理只需要参数（加一点激活和 KV cache），所以推理显存远小于训练。下面按每参数占多少字节来算，字节数取决于 dtype（见 2.5）：float32 每个数 4 字节，float16/bfloat16 每个 2 字节。

### 参数

参数就是模型的所有权重，占用 = 参数量 × 每个数的字节数。

```
参数显存 = N · bytes_per_param
```

全 float32 训练是 `4N` 字节；混合精度训练里通常保留一份 float16/bf16 的参数副本用于前向反向计算，即 `2N` 字节（但同时还要一份 fp32 主权重放在优化器账里，见下）。初学者要分清"用于计算的低精度副本"和"用于更新的 fp32 主权重"是两份不同的东西，别只算一份。

### 梯度

反向传播为每个参数算出一个梯度，梯度张量和参数张量一样大，所以

```
梯度显存 = N · bytes_per_grad
```

fp32 是 `4N`，混合精度里梯度常以 fp16/bf16 算即 `2N`。梯度在一个训练步内产生、参数更新后即可释放/复用，但峰值时它和参数、优化器状态同时在显存里。

### 优化器状态

这是最容易被初学者忽略、却往往是最大的一本账。Adam（及 AdamW）为每个参数额外维护两个 fp32 状态：一阶动量 `m` 和二阶动量 `v`，各 `4N` 字节，合计 `8N`。混合精度训练里优化器还持有一份 fp32 主权重 `4N`（低精度算、高精度累加更新以保数值稳定）。所以按 ZeRO 论文的经典口径，混合精度 Adam 的"优化器相关"部分是

```
K = 4 (fp32 主权重) + 4 (fp32 动量 m) + 4 (fp32 方差 v) = 12  字节/参数
```

对比之下，纯 SGD 无动量则没有这两个状态，带动量的 SGD 只多一份 `m`。要理解为什么优化器状态用 fp32：动量/方差是长期累加量，用低精度累加会丢失小量、损害收敛，所以坚持 fp32。这也解释了为什么"换优化器能省显存"——从 Adam 换到 SGD 直接省掉 `8N`~`12N`。

### 激活

激活是前向传播中每层产生、需要缓存供反向使用的中间张量（各层的输入、注意力分数、FFN 中间态等）。它不按 N 缩放，而是随批大小 B、序列长度 s、隐藏维 h、层数 L 增长，量级大致

```
激活显存 ∝ B · s · h · L   （确切系数依架构与实现而定，标「待核」）
```

它是唯一随批大小和序列长度线性（注意力部分甚至平方）增长的账，所以"批开大一点""上下文拉长一点"就可能把它顶爆，而参数/梯度/优化器三本账纹丝不动。省激活的主要手段是激活重算（gradient/activation checkpointing）：反向时不缓存全部中间态、需要时重跑一段前向，用算力换显存（呼应 2.3 反向"2×"变"约3×前向"）。确切的激活显存系数各实现差异大（是否重算、是否融合、注意力是否落矩阵），此处只给缩放关系、常数标「待核」。

### 混合精度下的 16 字节/参数合计

把前三本账（不含激活）按混合精度 Adam 口径相加，ZeRO 论文给出每参数总计

```
2 (fp16 参数) + 2 (fp16 梯度) + 12 (fp32 主权重+m+v) = 16  字节/参数
```

也就是训练一个 N 参数模型，光参数+梯度+优化器状态就要 `16N` 字节（激活另算）。举例心算：一个 7B（70 亿）参数模型，`16 × 7e9 ≈ 112 GB`——这就是为什么 7B 模型全量微调放不进一块 80GB 卡、需要分片（ZeRO/FSDP，见 08S-7）或换省显存优化器。这个 16N 是判断"能不能训得下"的一把尺，务必记住。

要标清前提：16 字节是混合精度 + Adam + 不分片的单卡口径。纯 fp32 Adam 会更高（参数4+梯度4+主权重视实现+m4+v4）；用 8-bit 优化器、SGD、或 ZeRO 分片会显著更低。这些数字是"约定俗成的核算口径"，具体框架实现可能差一两字节，用时以所锚框架文档为准。

### 峰值显存与省显存手段一览

真实峰值显存 = 参数 + 梯度 + 优化器状态 + 激活 + 一些框架/碎片开销（CUDA context、显存分配器碎片等，量级不定标「待核」）。核算时把四本账加起来能估到八九不离十，剩下的碎片开销是安全余量。

常见省显存手段与它们各砍哪本账，便于对号入座：激活重算砍激活（换算力）；混合精度砍参数/梯度（fp32→fp16 减半，但优化器仍 fp32）；8-bit/分页优化器砍优化器状态；ZeRO/FSDP 把三本账跨卡分片（08S-7）；梯度累积用"多步小批"等效大批而不增激活峰值。初学者遇到 OOM，第一步就该按这四本账定位是哪本爆了，再选对应手段，而不是盲目减小模型。

## 08S-2.5 PyTorch 系统级用法

### dtype：float32 / float16 / bfloat16 及字节账

dtype 决定每个数值占几字节、动态范围和精度，是连接 2.4 显存核算和实际代码的关键。常用：float32（fp32，4 字节，1 符号+8 指数+23 尾数）是默认全精度；float16（fp16，2 字节，1+5+10）省一半显存但指数位少、动态范围窄，容易上溢/下溢；bfloat16（bf16，2 字节，1+8+7）指数位和 fp32 一样宽（范围相同）、只是尾数精度低，训练时数值更稳，是当代大模型训练的主流低精度。

要理解 fp16 与 bf16 的取舍：两者都 2 字节、都省一半显存，区别在"范围 vs 精度"。fp16 精度略高但范围小，训练里梯度容易下溢成 0，往往需要损失缩放（loss scaling）救回；bf16 范围等同 fp32、几乎不用缩放，但尾数只有 7 位、精度粗。初学者记一句：显存核算时 fp16 和 bf16 都按 2 字节/数算（对上 2.4 的 `2N`），选哪个是数值稳定性问题不是显存问题。fp8（e4m3/e5m2，1 字节）在新硬件上用于训练/推理，属快速演进、支持度和默认用法随硬件与框架版本变，具体标「待核」`⚙演进快`。

### 混合精度：autocast 与 GradScaler

混合精度训练在 PyTorch 里用 `torch.autocast`（自动把合适的算子跑在 fp16/bf16、把对精度敏感的算子留在 fp32）配合梯度缩放实现。fp16 路径通常还要 `torch.cuda.amp.GradScaler`（把损失乘一个大系数、避免梯度下溢，反向后再缩回）；bf16 路径因为范围够宽，一般不需要 GradScaler。

这就是 2.4 里"fp16 计算副本 + fp32 主权重"在代码层的落地：autocast 让前向反向用低精度算（省显存省算力），优化器仍在 fp32 主权重上更新（保稳定）。易错点是把 GradScaler 用在 bf16 上（多此一举）或 fp16 训练忘了加 scaler（梯度悄悄下溢、loss 不降）。具体哪些算子被 autocast 归到 fp32、默认行为随 PyTorch 版本微调，标「待核」、以当前版本文档为准。

### device：cpu / cuda 与张量搬运

张量有 `device` 属性（`cpu` 或 `cuda:0` 等），运算要求参与的张量在同一设备上，否则报错。用 `.to(device)` 或 `.cuda()`/`.cpu()` 搬运，模型和数据都要搬到同一块卡。

CPU↔GPU 搬运走 PCIe，比 GPU 内部访存慢得多，是常见性能坑——训练循环里每步把数据从 CPU 拷到 GPU 是必要的，但反复在两端来回搬中间结果会严重拖慢。初学者常犯 "Expected all tensors to be on the same device" 错误，根因就是模型在 GPU、某个新建张量还在 CPU（如手动 new 的掩码/位置索引忘了 `.to(device)`）。显存核算意义上，只有在 GPU（`cuda`）上的张量才占显存。

### 张量内存与 profiler

一个张量占的字节数 = 元素个数 × 每元素字节数，即 `tensor.numel() * tensor.element_size()`，这正是 2.2/2.4 核算落到代码的验证方式——数出来的参数量乘字节数应对上 `sum(p.numel() for p in model.parameters())` 的实际值。要测真实显存/耗时，PyTorch 提供 `torch.cuda.memory_allocated()`/`max_memory_allocated()` 看显存占用，`torch.profiler`（记录各算子的时间和显存、可导出到 TensorBoard/trace 查看）做性能剖析。

profiler 的价值是把 2.3/2.4 的"纸上核算"和"实际观测"对照：算力核算告诉你理论 FLOP，profiler 告诉你真实耗时和哪个算子是瓶颈（往往受访存而非算力限制，接 08S-5 roofline）；显存核算告诉你四本账理论值，`max_memory_allocated` 告诉你真实峰值（含碎片）。profiler 的 API、字段和默认输出随 PyTorch 版本演进较快，具体用法标「待核」`⚙演进快`、以当前版本文档为准。本机（无 GPU/torch，见基线）不就地实证，仅讲清概念与核算对应关系。

### 张量视图与内存布局

张量在显存里是一维连续的字节块，`shape`/`stride` 决定怎么解释它。`view`/`transpose`/`permute` 只改元数据（怎么看这块内存）不搬数据，得到共享底层存储的"视图"；`reshape` 在必要时会拷贝，`.contiguous()` 强制按当前逻辑顺序重排成连续内存（真实拷贝、占额外显存）。

这一条把 2.1 的 einops 和显存核算连起来：声明式重排读起来干净，但底层某些重排会触发真实拷贝、短时多占一份显存和带宽。理解视图 vs 拷贝，才能解释"为什么某个 reshape 之后显存突然涨了一截""为什么 permute 后 view 报错要先 contiguous"。核算峰值显存时，这类临时拷贝也是一笔（通常小、量级看张量大小），精确值标「待核」、按具体算子定。
