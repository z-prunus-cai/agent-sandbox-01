## G-03.1 三角形 setup 与遍历（边函数 / 包围盒扫描）

### G-03.1.1 光栅化要回答的第一个问题：哪些像素被三角形覆盖

三角形光栅化的第一步是覆盖测试：给定屏幕空间的三个顶点，判定屏幕上每个像素的采样点（约定取像素中心，坐标形如 (x+0.5, y+0.5)）是否落在三角形内部。落在内部的像素被"点亮"（生成一个片元 fragment），落在外部的被跳过。

朴素做法是遍历整个屏幕的每个像素逐个判断，代价太大。实际做法分两层：先算出三角形的轴对齐包围盒（bounding box），只在包围盒内的像素里做测试；包围盒外的像素一定在三角形外，直接跳过。

x_min = ⌊min(x₀, x₁, x₂)⌋,  x_max = ⌈max(x₀, x₁, x₂)⌉

y_min = ⌊min(y₀, y₁, y₂)⌋,  y_max = ⌈max(y₀, y₁, y₂)⌉

三角形通常只占屏幕一小块，包围盒把"要检查的像素数"从整屏降到三角形附近的一小片，这是最基本、几乎零成本的加速。为什么用三角形而不用四边形或任意多边形做基本图元？因为三角形永远是平面的、永远是凸的、三个点永远能唯一确定一个平面，覆盖测试和属性插值都因此变得简单且无歧义——这是整条实时管线选三角形作为唯一填充图元的根本原因（RTR4、FCG4 都在光栅化章开篇强调这一点）。

### G-03.1.2 边函数（edge function）：用三次符号判定内外

判断一个点在不在三角形内，最优雅的工具是边函数。对三角形的一条有向边，从顶点 A 指向顶点 B，定义关于查询点 P 的边函数：

E_AB(P) = (P_x − A_x)(B_y − A_y) − (P_y − A_y)(B_x − A_x)

它其实是向量 AP 与向量 AB 叉积的 z 分量（G-01 的叉积直觉在这里落地）。它的符号告诉你 P 在有向边 A→B 的哪一侧：一侧为正、另一侧为负、恰在线上为零。

对三角形的三条有向边（按同一绕向，比如逆时针 V0→V1→V2）分别算三个边函数值。如果 P 在三角形内，P 一定在三条边的"同一侧"，也就是三个边函数值同号（都非负，或都非正，取决于绕向）：

P 在三角形内  ⟺  E₀(P), E₁(P), E₂(P) 三者同号

这个方法的漂亮之处在于全部是加减乘、无除法、无三角函数，且边函数关于 P 是线性的——相邻像素之间边函数只差一个常量增量，可以增量式递推，硬件极其喜欢。CMU 15-462 的 Rasterization lecture 正是以边函数（point-in-triangle via three edge tests）作为覆盖测试的标准讲法；RTR4 与 FCG4 用等价的"有符号面积/半平面测试"表述，本质相同。

一处 numpy 加固（脚本见本节末，真实输出）：对逆时针三角形 V0=(1,1), V1=(5,1), V2=(1,5)，中心点 (2,2) 三个边函数值为 (−8, −4, −4)，同号，判定"在内"；点 (4,4) 得到 (8, −12, −12)，异号，判定"在外"。符号一致性与几何位置吻合。

### G-03.1.3 top-left（左上）填充规则：解决共享边像素归属

当两个三角形共享一条边时，边上的像素采样点恰好落在两者边界（边函数为零）上。如果两个三角形都画这个像素，会重复着色（半透明混合时出现双重覆盖的接缝亮线）；如果都不画，会漏出背景（裂缝 crack）。为保证共享边上每个像素恰好被一个三角形画一次，光栅化器采用一致的平局裁决规则，最常见的是 top-left（左上）规则。

规则内容：当采样点恰好落在某条边上（边函数为零）时，只有当这条边是三角形的"左边"或"上边"时才算覆盖。左边指该边在三角形左侧且自下向上；上边指水平且在三角形上侧。落在"右边"或"下边"上的边界像素判为不覆盖，留给相邻三角形。

初学者不必背死"左/上"的精确判定，只需抓住目的：这是一条打破平局的约定，保证边界像素不重不漏、恰好一次。Direct3D 和 Vulkan 规范都明文规定了 top-left 规则（RTR4 光栅化章引用）；OpenGL 规范同样要求"每个像素恰好属于一个三角形"的不重不漏语义但措辞不同。这是一个"规范强制、实现遵守"的点：不同 API 措辞有别，但效果一致——共享边不会画两遍也不会漏。这属于易被初学者忽视却在做半透明或描边时立刻暴露的坑。

```python
# 本节末：边函数覆盖测试（scratchpad，真实输出）
def edge(a,b,p):
    return (p[0]-a[0])*(b[1]-a[1]) - (p[1]-a[1])*(b[0]-a[0])
V0,V1,V2=(1,1),(5,1),(1,5)
for p in [(2,2),(4,4)]:
    w=(edge(V1,V2,p), edge(V2,V0,p), edge(V0,V1,p))
    print(p, w, "in" if (all(v<=0 for v in w) or all(v>=0 for v in w)) else "out")
# 输出：
# (2, 2) (-8, -4, -4) in
# (4, 4) (8, -12, -12) out
```

## G-03.2 重心坐标与顶点属性线性插值

### G-03.2.1 重心坐标：把三角形内一点写成三顶点的加权平均

三角形内（乃至平面上）任意一点 P，都能唯一写成三个顶点 V0、V1、V2 的加权组合，权重 (α, β, γ) 就是重心坐标（barycentric coordinates）：

P = α·V0 + β·V1 + γ·V2,  其中 α + β + γ = 1

当 P 在三角形内部时，三个权重都在 [0,1]（且和为 1）；在边上时有一个为 0；在顶点处对应权重为 1、其余为 0。

重心坐标的几何意义是面积比：α 等于"P 与对面边 V1V2 围成的子三角形面积"占总面积的比例，β、γ 类推。这直接把 G-03.1 的边函数复用过来——边函数值正是有符号面积的两倍，所以覆盖测试算出的三个边函数值，除以总面积（三者之和）就直接得到重心坐标，一举两得。

α = Area(P,V1,V2) / Area(V0,V1,V2)

β = Area(V0,P,V2) / Area(V0,V1,V2)

γ = Area(V0,V1,P) / Area(V0,V1,V2)

重心坐标就是"P 离哪个顶点近，哪个顶点的权重就大"。P 越靠近 V0，α 越接近 1。这套坐标不依赖具体的 xy 数值，只依赖 P 相对三个顶点的位置，因此天然适合"把顶点上的数据摊到三角形内部每一点"。

### G-03.2.2 顶点属性的线性插值

顶点上不只有位置，还挂着一堆属性：颜色、纹理坐标 (u,v)、法线、深度等。要给三角形内某个像素算这些属性的值，就用该像素的重心坐标对三个顶点的属性做同样的加权平均：

attr(P) = α·attr(V0) + β·attr(V1) + γ·attr(V2)

例如顶点颜色分别是红、绿、蓝，三角形内部就会呈现平滑过渡的彩色渐变（经典的 RGB 三角形），每个像素颜色由它的重心坐标混合而来。

这一步是光栅化把"稀疏的顶点数据"变成"稠密的逐像素数据"的核心机制。为什么用线性插值（而不是别的）？因为三角形是平面图元，顶点属性在三角形所在平面上做线性变化是最自然、也是硬件最容易增量计算的选择——和边函数一样，重心坐标沿扫描线是线性递推的。

一处 numpy 加固（真实输出）：对三角形 V0=(1,1), V1=(5,1), V2=(1,5)，中心点 (2,2) 的重心坐标为 (0.5, 0.25, 0.25)，和为 1.0；把顶点标量属性 (0, 10, 20) 按此插值得 0.5×0 + 0.25×10 + 0.25×20 = 7.5，与直接加权一致。

```python
def edge(a,b,p):
    return (p[0]-a[0])*(b[1]-a[1]) - (p[1]-a[1])*(b[0]-a[0])
V0,V1,V2=(1,1),(5,1),(1,5); p=(2,2)
A=edge(V0,V1,V2)
a0,a1,a2 = edge(V1,V2,p)/A, edge(V2,V0,p)/A, edge(V0,V1,p)/A
print((a0,a1,a2), a0+a1+a2)            # (0.5, 0.25, 0.25) 1.0
print(a0*0 + a1*10 + a2*20)            # 7.5
```

### G-03.2.3 一个关键的坑：屏幕空间线性插值对投影后的属性是错的

上面这套"直接用屏幕空间重心坐标插值属性"的做法，对颜色这种可以容忍的情形常被凑合使用，但对纹理坐标、深度等，在透视投影下会产生肉眼可见的错误。原因是透视投影不是线性映射：屏幕上等距的两点，在三维世界里并不等距（远处的东西被压缩了）。因此屏幕空间里的重心坐标 α、β、γ 不等于三维空间里的重心坐标，直接拿它插值三维属性就会失真。

这个问题的修正就是 G-03.3 的透视校正插值。这里先埋下伏笔并点破常见误解：初学者常以为"重心坐标插值"天然正确，其实它只在正交投影（或属性本身随屏幕线性变化）时正确；一旦经过透视除法，必须先对 1/w 做处理。深度值 z 的插值也涉及类似问题，将在 3.3、3.4 一并说明。

## G-03.3 透视校正插值（1/w 插值）与错误对照

### G-03.3.1 为什么需要透视校正

经过透视投影和透视除法后，一个顶点属性（如纹理坐标 u）沿三角形内部相对屏幕位置并不是线性变化的，但 u/w 与 1/w 这两个量相对屏幕位置是线性的。透视校正插值就是利用这一事实：不直接插值 u，而是分别对 u/w 和 1/w 做屏幕空间的重心坐标线性插值，再相除还原：

u_correct(P) = [ α·(u₀/w₀) + β·(u₁/w₁) + γ·(u₂/w₂) ] / [ α·(1/w₀) + β·(1/w₁) + γ·(1/w₂) ]

这里 w 是顶点在裁剪空间（clip space）的第四个齐次分量（G-02.4 的 w，透视投影下大致正比于顶点到相机的深度），α、β、γ 是屏幕空间的重心坐标。

直接插值 u 是错的，插值 u/w 和 1/w 是对的，最后把两者相除把 w 消掉。这也解释了为什么硬件光栅化要一路把 1/w（有时记作深度相关量）带到片元阶段——它是所有透视校正插值的公共分母。

### G-03.3.2 仿射插值 vs 透视校正插值的数值对照

用一个最小例子把差距量化。设一条边的两端点：端点 A 属性 u=0、w=1（近处），端点 B 属性 u=1、w=4（远处），在屏幕上取中点 t=0.5。

仿射（错误）插值直接线性混合：

u_affine = (1−t)·u_A + t·u_B = 0.5·0 + 0.5·1 = 0.5

透视校正（正确）插值：

u_correct = [(1−t)·(u_A/w_A) + t·(u_B/w_B)] / [(1−t)·(1/w_A) + t·(1/w_B)]

代入得分子 0.5×(0/1)+0.5×(1/4)=0.125，分母 0.5×(1/1)+0.5×(1/4)=0.625，商 = 0.125/0.625 = 0.2。

numpy 实测（真实输出）：仿射 u = 0.5，透视校正 u = 0.2。差距达 0.3，绝非可忽略。直观理解：屏幕中点在世界里其实更靠近近处的 A（远处被透视压缩了），所以正确的 u 应该更接近 A 的 0，而不是天真的 0.5。

```python
uA,wA=0.0,1.0; uB,wB=1.0,4.0; t=0.5
affine=(1-t)*uA+t*uB
num=(1-t)*(uA/wA)+t*(uB/wB); den=(1-t)*(1/wA)+t*(1/wB)
print("affine",affine,"perspective-correct",num/den)   # affine 0.5 perspective-correct 0.2
```

### G-03.3.3 视觉症状与深度的特殊情形

透视校正缺失的经典视觉症状：给一个大地板（两个大三角形）贴棋盘格纹理，用仿射插值时，纹理会沿三角形对角线出现明显的"折断/扭曲"，棋盘格在三角形边界处不连续、像被拉歪，透视校正后才恢复笔直延伸到远方。早期缺乏透视校正硬件的游戏机（如初代 PlayStation）就有这种标志性的纹理游动/抖动。

深度值的处理。在标准的透视投影下，写入深度缓冲的 NDC 深度 z_ndc 关于屏幕 xy 本身就是线性的（可以直接用屏幕空间重心坐标插值 z_ndc），因为投影矩阵被设计成让 z_ndc 与 1/w_eye 成线性关系；而眼空间的真实线性深度 z_eye 则不是屏幕线性的，需要透视校正（等价于插值 1/z_eye）。所以"深度要不要透视校正"取决于你插的是哪个深度量——NDC 深度不用、线性眼深度要用。这个区分 RTR4 与 FCG4 都有讨论，是深度精度话题（见 G-03.4）的前置。

- 锚点：RTR4 光栅化/插值章（perspective-correct interpolation 公式与视觉伪影）；FCG4 相应节。核实 2026-07-30。
- 冲突/约定差异：不同资料对 w 的具体定义与符号（clip-space w 常正比于 −z_eye 或 z_eye，取决于投影矩阵约定，见 G-02.4 的左右手/深度约定）表述略有差异，但"插值 attr/w 与 1/w 再相除"的公式结构一致，无实质分歧。NDC 深度线性 vs 眼深度非线性的区分两源一致。

## G-03.4 深度缓冲 Z-buffer 与逐像素可见性

### G-03.4.1 Z-buffer 算法：逐像素记住最近深度

当多个三角形投影后覆盖同一个像素时，必须决定哪个可见（离相机最近的挡住后面的）。Z-buffer（深度缓冲）是实时管线的标准解法：为每个像素额外维护一个深度值。渲染开始时把整块深度缓冲初始化为"最远"（通常 1.0 或 +∞）。每生成一个片元，就拿它插值出的深度 z 与该像素当前存的深度比较：

if z_frag < z_buffer[x, y]:  z_buffer[x, y] = z_frag;  color_buffer[x, y] = color_frag

也就是"更近就覆盖，否则丢弃"。所有三角形处理完后，颜色缓冲里留下的就是每个像素最近可见表面的颜色。

Z-buffer 最大的优点是它与三角形提交顺序无关（画家算法那种"从后往前排序再画"的方案对相互穿插的三角形会失败，Z-buffer 不会），且实现简单、可硬件并行——每个像素独立比较，天然适合 GPU。代价是额外一块与帧缓冲同尺寸的内存，以及每片元一次读-比较-写。

一处 numpy 加固（真实输出）：给像素 0 依次送入深度 0.8、0.3、0.9 的片元，像素 1 送入 0.5，最终 z-buffer 为 [0.3, 0.5, ∞]，颜色为 [2, 3, 0]——像素 0 正确保留了最近的 0.3（对应颜色 2），后来更远的 0.9 被丢弃，与提交顺序无关。

```python
import numpy as np
zbuf=np.full(3,np.inf); color=np.zeros(3,dtype=int)
for px,z,c in [(0,0.8,1),(0,0.3,2),(1,0.5,3),(0,0.9,4)]:
    if z<zbuf[px]: zbuf[px]=z; color[px]=c
print(zbuf, color)          # [0.3 0.5 inf] [2 3 0]
```

### G-03.4.2 深度约定与精度：[0,1] 编码、z-fighting 与非线性分布

深度缓冲存的是投影后的深度，常规约定把可见深度范围映射到 [0,1]（近平面 0、远平面 1）。这里有一个跨 API 的约定差异需要显式记账：裁剪空间 NDC 深度范围，OpenGL 传统上是 z ∈ [−1, 1]，而 Direct3D、Vulkan、Metal 是 z ∈ [0, 1]（OpenGL 4.5+ 也可通过 glClipControl 切到 [0,1]）。存进深度缓冲前会再映射到 [0,1]。两种约定投影矩阵的对应行不同，混用会导致深度全错——这是 G-02 深度约定问题在光栅化端的延续。

深度精度的核心陷阱是 z-fighting（深度冲突/闪烁）：两个表面深度极其接近时，有限精度的深度值无法区分谁前谁后，逐帧/逐像素随机胜出，产生斑驳闪烁。更糟的是标准透视投影下深度精度分布极不均匀——非线性地把绝大部分精度堆在近平面附近，远处精度稀薄。这是因为写入的 NDC 深度与 1/z_eye 成线性关系：

z_ndc  ∝  A + B/z_eye  （A、B 为投影矩阵决定的常数）

结果是近处 z_eye 变化一点，z_ndc 变化很大（精度高）；远处 z_eye 变化很多，z_ndc 几乎不动（精度低）。缓解手段包括：把近平面推远、拉近近远平面比值，使用更高位深（如 24-bit、32-bit float 深度），以及 reversed-Z（把近平面映射到 1、远平面到 0，配合浮点深度的分布特性大幅改善远处精度，现代引擎常用）。reversed-Z 属于⚙演进的实现技巧、非规范强制，具体收益依硬件浮点深度实现而定。

深度精度在近平面密、远平面疏；两个几乎共面的表面会 z-fighting，靠 offset（多边形偏移/polygon offset）或调整近远平面缓解。

### G-03.4.3 早期深度测试（early-Z）与它何时失效

标准管线里深度测试发生在片元着色之后（因为要先算出片元颜色和深度）。但如果片元不修改深度、也不做丢弃（如 discard/alpha test），GPU 可以把深度测试提前到片元着色之前——early-Z（早期深度测试）：先比深度，被遮挡的片元直接丢弃、连着色都省了，大幅节省被浪费在看不见像素上的着色开销。

early-Z 在两种情形会被硬件自动关闭或退化：片元着色器里写了 gl_FragDepth（自定义深度，光栅化前算的深度作废）、或用了 discard/alpha 测试（是否保留要等着色结果才知道）。理解这一点有助于初学者明白"为什么先画不透明物体、按由近到远大致排序能提速"——让 early-Z 尽早剔除后面被挡住的片元。这属于⚙实现优化，非规范语义，不同 GPU 触发条件细节有别。

## G-03.5 裁剪、背面剔除与覆盖 / 多重采样覆盖

### G-03.5.1 裁剪（clipping）：去掉视锥外与近平面后的几何

光栅化前，落在视锥（view frustum）外的几何应当被裁掉，避免绘制看不见的东西，更关键的是处理跨越近平面的三角形——顶点跑到相机后面（w ≤ 0）时透视除法会除以零或翻转符号，产生错误坐标。裁剪在裁剪空间（透视除法之前）进行，判据是齐次坐标满足视锥不等式：

−w ≤ x ≤ w,  −w ≤ y ≤ w,  以及深度约定下的 −w ≤ z ≤ w（OpenGL）或 0 ≤ z ≤ w（Vulkan/D3D）

完全在视锥内的三角形直接通过；完全在外的整体丢弃；跨越边界的三角形被切割成更小的多边形（再重新三角化）。经典算法是 Sutherland-Hodgman 多边形裁剪，对每个裁剪平面依次裁一遍。

初学者最该记住的是"为什么必须在透视除法之前、在 clip 空间裁"：一旦除以 w，相机后方的点会被错误地映射到屏幕上（负 w 翻转），信息已被破坏。近平面裁剪（near-plane clipping）尤其不可省——它专门处理"三角形一部分在相机前、一部分在相机后"的情形。实践中许多硬件只强制做近平面裁剪，其余边界靠 guard-band（护带）+ 光栅化阶段的剪裁（scissor/像素级丢弃）来省去昂贵的几何切割，这属于⚙实现优化。

### G-03.5.2 背面剔除（back-face culling）：丢弃背朝相机的三角形

对封闭实体（如一个球、一个立方体），朝向相机背面的三角形一定被前面的面挡住、看不见，可以在光栅化前直接丢弃，省掉约一半三角形的光栅化与着色开销。判据有两种等价视角。

屏幕空间视角：投影到屏幕后，看三角形顶点的绕向（winding order）。约定逆时针（CCW）为正面，则投影后有符号面积为正的是正面、为负的是背面（或反之，取决于配置）。有符号面积正是 G-03.1 的边函数之半：

2·SignedArea = E(V0, V1, V2)

世界/眼空间视角：用三角形法线 N 与从三角形指向相机的视线方向 V 做点积，同向（背对相机）则剔除：

若 N · V < 0 则为背面（剔除），> 0 为正面

（不等号方向依法线定义与视向定义的约定而定，需与绕向约定自洽。）

一处 numpy 加固（真实输出）：逆时针三角形 [(0,0),(1,0),(0,1)] 的有符号面积（本文边函数约定下）为 −0.5，顺时针 [(0,0),(0,1),(1,0)] 为 +0.5——符号随绕向翻转，正是背面剔除据以判定的信号。剔除保留哪个符号由 API 的 front-face + cull-mode 配置决定（OpenGL glFrontFace/glCullFace、Vulkan pipeline 的 frontFace/cullMode）。

```python
def edge(a,b,p): return (p[0]-a[0])*(b[1]-a[1]) - (p[1]-a[1])*(b[0]-a[0])
sarea=lambda t: 0.5*edge(t[0],t[1],t[2])
print(sarea([(0,0),(1,0),(0,1)]), sarea([(0,0),(0,1),(1,0)]))  # -0.5 0.5
```

绕向约定、front-face 设定、法线朝向三者必须自洽，一处配反就会"整个模型只剩内壁/整个消失"。半透明物体、双面材质（如树叶、纸片）通常要关闭背面剔除。

### G-03.5.3 覆盖与多重采样（MSAA）：抗锯齿的覆盖近似

单点覆盖测试（每像素只测像素中心一个采样点）会在三角形边缘产生锯齿（jaggies）——边缘像素要么全画要么不画，出现阶梯状硬边。多重采样抗锯齿（MSAA, multi-sample anti-aliasing）的做法是：每个像素放多个覆盖采样点（如 4×、8×），分别做覆盖测试和深度测试，统计该像素被三角形盖住了几个采样点，据此得到 0～100% 的部分覆盖率，边缘因此呈现平滑过渡而非硬跳变。

MSAA 的关键性价比设计（也是它与超采样 SSAA 的根本区别）：覆盖与深度按每个采样点算，但片元着色只对每个像素执行一次（在被覆盖的采样点里取一个代表位置着色），着色结果按覆盖的采样点数写入。也就是采样点数 ≠ 着色次数——MSAA 用"多采样点解决几何边缘锯齿"，但不为每个采样点重复跑一遍昂贵的片元着色，所以远比 SSAA（每个子样本都完整着色）便宜。SSAA 对几何边缘和纹理/着色内部走样都抗，MSAA 主要抗几何边缘锯齿。采样点在像素内的具体位置（sample pattern，如旋转网格 rotated-grid）由 GPU/API 决定，属⚙实现细节。

（注：G-03 只交代覆盖/多重采样在光栅化端的机制。采样定理、混叠成因、重建滤波、SSAA/MSAA 与预滤波的系统展开，以及为什么"多采样能减轻走样"的信号处理原理，归大主题 G-04 采样、走样与信号处理，此处仅点到。）

锯齿来自"每像素二值覆盖判定"；MSAA 通过每像素多个覆盖采样点得到部分覆盖率来软化边缘；MSAA 省钱的秘密是覆盖多采样、着色仍每像素一次。本节 MSAA 的硬件覆盖/着色采样分离行为为文档腿（本机无 GPU，未实机取证），仅依 RTR4 与规范描述。
