## G-06.1 GPU 固定功能 vs 可编程阶段的分工演进

### G-06.1.1 固定功能管线：算法焊死在硬件里

固定功能（fixed-function）指 GPU 某个管线阶段的算法是硬件内置、不可改写的：程序员只能通过设置参数（开关、系数、模式）来调它的行为，不能替换它执行的计算本身。早期图形硬件（以及 OpenGL 1.x/2.x 的固定管线）整条流水线都是这样——变换用固定的矩阵栈、光照用内置的 Blinn-Phong 公式、纹理用固定的组合器，你只能"配置"不能"编程"。

给初学者的直觉是把固定功能想成一台只有旋钮的相机：曝光、白平衡可以拨，但成像算法是厂商定死的。好处是简单、快、行为可预测；坏处是想要一个内置公式之外的效果（比如自定义的卡通着色、程序化变形）就根本做不到。这个"做不到"正是可编程着色器出现的动机。今天的 GPU 里，图元装配、光栅化、深度/模板测试、混合等阶段仍是固定功能（见 6.2.3、6.3.3），因为它们规则统一、极其适合硬件专用电路。

### G-06.1.2 可编程着色器的引入与阶段演进

可编程阶段指程序员可以用着色语言（GLSL / SPIR-V / HLSL 等）写一小段程序，GPU 对该阶段的每个数据元素各执行一遍这段程序。演进的大致顺序是：先开放顶点着色器（vertex shader）与片元着色器（fragment shader，D3D 叫 pixel shader），这是 2001 年前后的可编程管线起点；随后加入几何着色器（geometry shader）、曲面细分的两个可编程阶段（tessellation control / evaluation）；再后来加入不属于图形光栅管线的计算着色器（compute shader）；最新一代是网格着色器（mesh / task shader）路线，用可编程的方式替代传统的顶点装配前端。

初学者要抓的主干，是把可编程化理解成"逐步把固定功能阶段替换成'你写的小程序'"的历史过程，但并非全部阶段都被开放——真正核心、每个现代管线都用的是顶点着色器和片元着色器这两个，其余（几何/细分/网格）是可选增强。为什么叫"着色器"却不只做着色？这是历史命名：最早只有算颜色的片元阶段可编程，"shader"就成了"GPU 上可编程小程序"的统称，即使顶点着色器根本不算颜色（它做变换）。

### G-06.1.3 当前分工：哪些可编程、哪些仍固定

现代实时光栅管线的阶段分工，可编程与固定功能交替排列。一个便于记忆的近似顺序是：

顶点着色器（可编程） → [曲面细分/几何着色器，可选可编程] → 图元装配·裁剪·透视除法·视口变换（固定） → 光栅化·属性插值（固定） → 片元着色器（可编程） → 深度/模板测试·混合·写帧缓冲（固定，输出合并阶段）

这里的关键分账在于，变换和最终着色是"你的程序"（可编程），而"把三角形切成片元""决定谁在前""把颜色混进屏幕"这些规则统一的步骤是硬件固定功能。RTR4 的管线章与两套规范的管线概览都是这个骨架，差别只在术语（OpenGL 叫 fragment shader / per-fragment operations，Vulkan 叫 fragment shader stage / color blend state）。初学者常误以为"深度测试写在片元着色器里"——不是，深度测试默认发生在片元着色器之后的固定功能输出合并阶段（early-Z 是优化，把它提前，但语义上仍是固定功能）。

### G-06.1.4 统一着色器架构与 SIMT 直觉

统一着色器架构（unified shader architecture）指现代 GPU 不再为顶点、片元各设一批专用处理单元，而是用一大片通用的可编程核心，动态调度去跑任意着色器阶段。这带来负载均衡：一帧里顶点多就多分核心给顶点着色器，片元多就多分给片元着色器。

配套的执行直觉是 SIMT（单指令多线程），也就是 GPU 把大量数据元素（成千上万个顶点或片元）分组，每组用同一段着色器代码、锁步执行，只是各自的数据不同。这解释了为什么着色器要写成"针对单个顶点/单个片元"的形式——你写的是"一个元素怎么处理"，硬件负责把它并行铺到海量元素上。这也是为什么着色器里发散的 if-else（不同元素走不同分支）会变慢：同组元素锁步，必须两条分支都走一遍再各取所需。SIMT 的硬件细节、warp/occupancy 属 L6-06 H-05，此处只取"同一段代码并行跑在海量元素上"的直觉，不展开。

## G-06.2 顶点着色器阶段职责（变换/属性输出，复用 G-02 直觉）

### G-06.2.1 顶点着色器做什么：每顶点跑一次的变换程序

顶点着色器是管线里第一个可编程阶段。GPU 对你提交的每一个顶点各执行一遍这段程序，最核心的强制职责是：把该顶点的位置从物体空间变换到裁剪空间（clip space），把结果写进内置输出（GLSL 的 `gl_Position`）。这正是 G-02 讲的 MVP 变换落到 GPU 上的位置——变换矩阵由 CPU 传进来，逐顶点的矩阵乘法由顶点着色器执行。

一段最小 GLSL 顶点着色器的主体就是一行：

gl_Position = projection * view * model * vec4(position, 1.0);

初学者可以把顶点着色器想成一个"逐顶点的加工站"，输入一个原始顶点、输出一个已经落到裁剪空间的顶点，附带把颜色/纹理坐标/法线等属性往下游传。它对每个顶点独立处理、彼此不知道对方，因此天然并行。它不能创建或删除顶点（那是几何/细分/网格着色器的活），一进一出。

### G-06.2.2 输入属性与输出 varying

顶点着色器的输入叫顶点属性（vertex attributes）：位置、法线、纹理坐标、颜色等，逐顶点各一份，由 CPU 端准备在顶点缓冲里、按顶点喂进来。输出除了必填的 `gl_Position`，还有一组用户自定义的输出变量，早期 GLSL 叫 varying，现在写作 `out` 变量——这些是要"沿着三角形插值后交给片元着色器"的数据。

初学者要建立的关键链条，是顶点着色器输出的 `out`/varying 不会原样到片元着色器，而是先被固定功能的光栅化阶段按重心坐标做插值（见 6.3.1），片元着色器收到的是插值后的值。举例：三个顶点各写出自己的纹理坐标，三角形内部某个片元收到的是这三个纹理坐标的加权混合。"varying"这个词本身就在说"它的值沿三角形表面变化"。这也解释了为什么法线要在顶点着色器输出、在片元着色器归一化——插值会让单位向量变短，需要重新归一。

### G-06.2.3 顶点着色器之后、片元着色器之前的固定功能

这里的分账很重要，顶点着色器只负责逐顶点变换，它之后到片元着色器之间有一串固定功能步骤，不是任何着色器写的。按顺序大致是：图元装配（把顶点按 draw 调用指定的拓扑组装成三角形/线/点）、裁剪（clipping，把伸出视锥的图元裁掉，G-02 的 clip 空间就是为它准备的）、透视除法（clip 空间各分量除以 w，得到 NDC）、视口变换（NDC 映射到屏幕像素坐标）、背面剔除（按绕向丢弃背对相机的三角形）、光栅化（把三角形切成覆盖的片元）。

初学者最容易混淆的一点是透视除法，它不是顶点着色器做的。顶点着色器只输出带 w 的 clip-space 坐标（`gl_Position`），除以 w 这一步由固定功能硬件在顶点着色器之后自动完成。这正是 G-02.5 讲的"透视除法→NDC→视口"链条在 GPU 上的归属。RTR4 与两套规范都把这段列为固定功能几何后处理。理解这点后，"为什么顶点着色器要输出 4 维带 w 的坐标而不是直接给 3 维 NDC"就有了答案：把除法留给硬件，同时 w 还要留给光栅化做透视校正插值（6.3.1）。

一处 numpy 可选加固（CPU 模拟顶点着色器逻辑，非真实 GPU，脚本见 6.3 节末）：对透视投影矩阵（fovy=60°, aspect=1, n=0.1, f=100）作用于物体空间顶点 (1, 0.5, −5, 1)，得 clip 坐标 [1.7321, 0.866, 4.8098, 5.0]（w=5.0），透视除法后 NDC = [0.3464, 0.1732, 0.962]。w=5.0 恰等于该点到相机的 −z_eye 距离，与 G-02.4 的投影约定一致。

## G-06.3 光栅化插值 → 片元着色器阶段职责（复用 G-03/G-05 直觉）

### G-06.3.1 光栅化插值：把顶点属性透视校正地送进片元

光栅化把每个三角形切成它覆盖的片元（fragment），并为每个片元把顶点着色器输出的 varying 按重心坐标插值出一份值。这一步是固定功能。关键是它必须做透视校正插值（perspective-correct interpolation，G-03.3）：不是直接对属性做线性插值，而是对"属性除以 w"和"1/w"分别线性插值、再相除。对屏幕重心坐标 (b₀,b₁,b₂) 与三顶点的属性 aᵢ、clip-space wᵢ：

a_frag = ( Σ bᵢ · aᵢ / wᵢ ) / ( Σ bᵢ / wᵢ )

从直觉上看，屏幕上均匀走的一步，在 3D 世界里因为透视不是均匀走的（远处压缩），所以属性不能在屏幕空间线性插——必须用 w 校正回来。这就是 6.2.3 里"w 要留给光栅化"的用途。深度值 z 则相反：为了深度测试用，插值的是屏幕空间线性的 NDC 深度。

一处 numpy 可选加固（脚本见本节末）：三顶点颜色为红/绿/蓝、clip-space w 分别为 2/4/1，片元屏幕重心 (0.3,0.3,0.4)，仿射（错误）插值得 [0.30, 0.30, 0.40]，透视校正插值得 [0.24, 0.12, 0.64]——w 小（更近）的第三顶点权重被放大，与透视校正的预期一致。

### G-06.3.2 片元着色器做什么：每片元跑一次算颜色

片元着色器是第二个核心可编程阶段。GPU 对光栅化产生的每一个片元各执行一遍这段程序，主要职责是计算该片元的输出颜色（写进内置输出，GLSL 现代写法是自定义 `out vec4`），可以采样纹理、做光照计算、算透明度。G-05 的 Blinn-Phong 着色、纹理采样，落到 GPU 上就发生在这里。

初学者可以把片元着色器想成一个"逐片元的上色站"，输入是插值来的属性（纹理坐标、法线、世界坐标等）＋可采样的纹理，输出是这个片元的颜色。它和顶点着色器一样逐元素独立、天然并行，但数量通常大得多（一个三角形一个顶点着色器实例可能对应成百上千个片元实例），所以片元着色器往往是性能瓶颈。片元着色器还能用 `discard` 丢弃片元（做 alpha 测试/镂空），但一般不能改自己的屏幕位置。

一处 numpy 可选加固：对上面透视校正得到的片元颜色，用 N=(0,0,1)、光 L 归一化、Blinn-Phong（高光指数 32）着色，得 [0.161, 0.092, 0.392]——演示片元着色器"插值属性→光照公式→颜色"的纯逻辑。

### G-06.3.3 输出合并阶段：深度/模板测试与混合（固定功能）

片元着色器算出的颜色不是直接写进屏幕。它先经过固定功能的输出合并（output merger / per-fragment operations）阶段：深度测试（Z-buffer，G-03.4，比较片元深度与已存深度，决定是否保留）、模板测试（stencil，按掩码接受/拒绝）、混合（blending，把片元颜色按透明度与帧缓冲已有颜色合成，G-04.5 的 over 运算符），最后才写进帧缓冲。

这里的要点在于，这一整段是固定功能、由状态配置控制，不是片元着色器代码。初学者常把"深度测试/混合"当成片元着色器的一部分——不是。你在 API 里"开启深度测试""设置混合方程"，配置的是这个固定功能阶段。为效率，硬件常做 early-Z：在片元着色器之前就做深度测试丢弃被遮挡片元，避免白算颜色；但这是优化，语义归属仍是输出合并阶段（片元着色器里用 `discard` 或写深度会关掉 early-Z）。两套 API 与 RTR4 都把它列为固定功能可配置阶段。

### G-06.3.4 片元 ≠ 像素 的辨析

片元（fragment）和像素（pixel）不是一回事，这是初学者高频混淆点。片元是"某个三角形在某个采样位置上生成的、还没最终确定的候选数据"（带颜色、深度、属性）；像素是帧缓冲里屏幕上一个实际的格子。一个像素可能由多个片元竞争（多个三角形都覆盖它，靠深度测试决出胜者），也可能在多重采样（MSAA，G-03.5/G-04.4）下一个像素含多个采样点、对应多个片元。

抓住这个区分之所以重要，是因为片元只是"候选"、还要过深度/模板/混合，才有输出合并阶段的存在意义。OpenGL 规范精确地用 fragment 指代片元着色器处理的对象、用 pixel 指帧缓冲元素；Direct3D 历史上把片元着色器叫 pixel shader，是命名习惯不同，处理的其实仍是片元。理解了 6.2/6.3，整条可编程管线就串起来了：顶点着色器逐顶点变换 → 固定功能几何后处理 → 光栅化插值 → 片元着色器逐片元上色 → 固定功能输出合并写屏。

```python
# 6.2/6.3 节末：CPU 模拟顶点/片元着色器逻辑（scratchpad，真实输出；非真实 GPU）
import numpy as np
np.set_printoptions(precision=4, suppress=True)

def perspective(fovy, aspect, n, f):
    t = np.tan(np.radians(fovy)/2); M = np.zeros((4,4))
    M[0,0]=1/(aspect*t); M[1,1]=1/t
    M[2,2]=-(f+n)/(f-n); M[2,3]=-2*f*n/(f-n); M[3,2]=-1
    return M

# 顶点着色器：MVP -> clip -> 透视除法（固定功能）-> NDC
P = perspective(60, 1.0, 0.1, 100)
v_clip = P @ np.array([1.0, 0.5, -5.0, 1.0]); w = v_clip[3]
print("VS clip =", v_clip, " w =", round(w,4))     # [1.7321 0.866 4.8098 5.] w=5.0
print("   ndc  =", v_clip[:3]/w)                     # [0.3464 0.1732 0.962]

# 光栅化透视校正插值 + 片元着色器 Blinn-Phong
cols = np.array([[1,0,0],[0,1,0],[0,0,1]], float); ws = np.array([2.,4.,1.])
bary = np.array([0.3,0.3,0.4])
c_affine = bary @ cols
c_persp  = (bary[:,None]*cols/ws[:,None]).sum(0) / (bary/ws).sum()
print("FRAG affine =", c_affine)                     # [0.3 0.3 0.4]
print("     persp  =", c_persp)                       # [0.24 0.12 0.64]
N=np.array([0,0,1.]); L=np.array([1,1,1.]); L/=np.linalg.norm(L)
H=(L+np.array([0,0,1.])); H/=np.linalg.norm(H)
out=np.clip(c_persp*max(N@L,0)+max(N@H,0)**32,0,1)
print("     shaded =", out)                           # [0.161 0.0917 0.3919]
# 真实输出（本机 Py3.11.15/np2.4.6 @2026-07-30）与上方注释一致
```

## G-06.4 OpenGL 4.6 Core 状态机与绘制提交模型 🔴（⚙演进快·锚版本；4.6 已冻结，末次 spec 2022-05-05）

### G-06.4.1 OpenGL 是一台隐式全局状态机

OpenGL 的核心心智模型是一台大型全局状态机：存在一个当前上下文（context），里面保存着海量的当前状态（当前绑定的缓冲、纹理、着色器程序、混合/深度开关、当前视口等）。你的调用大多是"修改某个当前状态"或"用当前状态执行一次操作"。绘制时，GPU 用的是"此刻上下文里的所有当前状态"，而不是你在 draw 调用里显式传进去的一整套配置。

打个比方，OpenGL 像操作一台你不断拨旋钮的机器——先 `glBindTexture` 把某纹理设为"当前纹理"，再 `glEnable(GL_DEPTH_TEST)` 打开深度测试开关，最后 `glDrawArrays` 说"按现在的所有设置画一批"。状态是隐式携带的、粘滞的（sticky，你不改它就一直保持）。好处是上手直观、样板代码少；坏处是状态全局且隐式，大型程序里"谁改了什么状态没复原"极难追踪，这正是 Vulkan 要用显式模型解决的痛点。

### G-06.4.2 对象与绑定模型：bind-to-edit

OpenGL 里 GPU 资源被抽象成对象（object），用一个整数名字（name，由 `glGen*` 生成）标识：顶点缓冲对象 VBO、顶点数组对象 VAO（记录顶点属性布局）、纹理对象、帧缓冲对象 FBO、着色器程序对象等。经典操作模式是 bind-to-edit（绑定后编辑）：先把对象绑定到上下文的某个绑定点（`glBind*`），随后的调用都作用于"当前绑定的那个对象"。

一段典型的经典风格片段（示意）：

glBindBuffer(GL_ARRAY_BUFFER, vbo); glBufferData(GL_ARRAY_BUFFER, size, data, GL_STATIC_DRAW);

初学者要理解 bind 的双重角色带来的坑：绑定既用于"选中要编辑的对象"，又用于"选中绘制时要用的对象"，两种意图混在同一套绑定点上，容易互相干扰（编辑 A 时不小心改了绘制要用的 B 的绑定）。OpenGL 4.5/4.6 引入了直接状态访问（DSA, Direct State Access），提供 `glNamedBufferData` 等函数直接按对象名字操作、无需先绑定，缓解了这个问题——这是 4.x 后期的重要现代化，但经典 bind-to-edit 代码仍大量存在。

### G-06.4.3 绘制提交：立即触发的 draw 调用

OpenGL 提交绘制用 `glDrawArrays`（按顶点数组顺序画）或 `glDrawElements`（按索引缓冲画）等一族命令。调用它就是向 GPU 提交一次"用当前所有状态画这批图元"的绘制。OpenGL 的执行模型是命令逐条提交、驱动在后台负责排队/流水（对应用是即时式 immediate 语义：你调一条它就"生效"），程序员不直接管理命令缓冲、不直接管队列提交。

落到写代码上，一帧的典型循环是"清屏 → 绑好程序/VAO/纹理、设好 uniform 与开关 → glDraw* → （换一批状态再 draw…）→ 交换缓冲"。你只管发命令、改状态，命令什么时候真在 GPU 上跑、怎么同步 CPU/GPU，几乎全由驱动隐式处理。这种"驱动替你管一切"的便利，正是与 Vulkan 显式模型（6.5）最根本的分野。为减少 draw 调用开销，4.x 提供了多重绘制/间接绘制（`glMultiDrawElementsIndirect` 等），把多批绘制参数放缓冲里一次提交，但这仍在 OpenGL 的隐式状态框架内。

### G-06.4.4 版本与成熟度：4.6 Core 已冻结

OpenGL 4.6 是 OpenGL 的最后一个版本，Core Profile 规范末次更新为 2022-05-05（本文核实 2026-07-30 仍为最终版）。Khronos 已把未来主要精力放在 Vulkan 上，OpenGL 不再有新核心版本，处于"已冻结/维护"状态——功能定义稳定、驱动仍广泛支持，但不会再演进。Core Profile 指去除了古老的即时模式（`glBegin/glEnd`）等遗留固定管线的现代精简子集，与保留遗留 API 的 Compatibility Profile 相对。

在时效认知上要明白，说"OpenGL 4.6 冻结"不是说它不能用（它依然是学习与许多产品的主力），而是说这条 API 线不再增加新特性、新硬件能力要通过 Vulkan 暴露。因此本节内容硬标 ⚙演进快·锚版本——但方向是"已定格"而非"频繁变"，与 Vulkan（6.5，活跃演进）的演进性质正相反。规范文本很详尽，但"驱动隐式管理内存/同步/命令队列"的具体行为属于实现，规范只定义可见语义，本报告不深挖实现。

- 成熟度硬标：OpenGL 4.6 ⚙演进快·锚版本，但性质为"已冻结/最终版"，方向是定格而非频繁变（与 Vulkan 相反）。核实日期 2026-07-30。

## G-06.5 Vulkan 1.4 显式模型 🔴（⚙演进快·锚版本；1.4 首发 2024-12-02，活跃线）

### G-06.5.1 显式哲学：程序员显式管理一切

Vulkan 的设计哲学与 OpenGL 相反：显式、低开销、多线程友好。它把 OpenGL 里由驱动隐式代管的东西——内存分配、命令的记录与提交、CPU/GPU 与 GPU 内部的同步、管线状态——全部摊开，交给程序员显式管理。驱动做得极少、极可预测，因此开销低、行为可控、可扩展到多线程录制命令，但代价是样板代码量大幅增加，一个"画三角形"的最小示例往往要几百上千行。

打个比方，如果 OpenGL 是自动挡（驱动替你换挡、离合），Vulkan 就是手动挡加上要自己管油路——你能压榨出更高性能和确定性，但必须懂并正确处理每一个显式步骤，任何同步/内存错误后果自负（GL 里驱动会替你兜底的错误，Vulkan 里可能直接崩或渲染错乱）。这就是"显式"的全部含义：控制权和责任一起交给你。本报告只讲这套模型的四大支柱骨架，不做逐结构体的专家纵深。

### G-06.5.2 队列与命令缓冲：录制一次、提交执行

Vulkan 不逐条即时执行绘制命令，而是先把一批命令录制（record）进命令缓冲（command buffer），再把命令缓冲整体提交（submit）到一个队列（queue）由 GPU 执行。队列是 GPU 上实际消费命令的通道（图形队列、计算队列、传输队列等，从设备的队列族 queue family 里取得）。

这就像"先写好一张施工清单（命令缓冲），再把清单交给施工队（队列）"。好处一是可复用：同样的命令缓冲录一次可多帧重复提交；好处二是多线程：多个线程可各自并行录制不同命令缓冲，再统一提交——这是 OpenGL 隐式即时模型做不到的，也是 Vulkan 低开销的重要来源。对照 6.4.3：OpenGL 是"发一条 draw 就即时生效、驱动隐式排队"，Vulkan 是"你显式录进缓冲、显式提交到队列"。

### G-06.5.3 管线对象（PSO）：状态烘焙进不可变对象

Vulkan 把渲染所需的大量状态——用哪些着色器、顶点输入布局、光栅化设置、深度/模板/混合配置等——预先烘焙进一个图形管线对象（graphics pipeline object，业界常称 PSO, pipeline state object），创建后不可变（immutable）。绘制时绑定一个已建好的管线对象，而不是像 OpenGL 那样在 draw 前逐个拨状态开关。

拿来和 OpenGL 对照，OpenGL 的状态是零散、可随时改的全局旋钮（6.4.1）；Vulkan 把这些状态凝固成一个个整体对象，切换效果就是切换整个管线对象。好处是驱动能在创建管线时一次性完成所有验证与编译、绘制时几乎零开销且行为可预测（避免了 GL 驱动在 draw 时因状态组合变化而临时重编译着色器的卡顿）。代价是状态组合爆炸：每种状态组合都要一个管线对象。为缓解，Vulkan 后续引入了动态状态（dynamic state，允许部分状态在录制时改而不必换管线对象），这属于持续演进内容，硬标 ⚙演进快·锚版本。

### G-06.5.4 同步原语与显式内存管理

因为 Vulkan 不替你同步，程序员必须用显式同步原语协调并发。核心几类：栅栏（fence）用于 GPU→CPU 同步（CPU 等 GPU 干完某批活）；信号量（semaphore）用于队列之间/队列内 GPU→GPU 同步（比如"渲染完成"再"呈现到屏幕"）；管线屏障（pipeline barrier）与内存屏障用于同一队列内保证执行顺序与内存可见性、以及图像布局转换（image layout transition）。此外内存要显式分配（`vkAllocateMemory`）并把资源绑上去，而不是 GL 里创建缓冲即隐式有内存。

从直觉上说，Vulkan 假设一切默认并行、乱序、内存不自动可见，你必须显式声明"这一步要等那一步""这块内存写完要让后面读得到"。漏写同步是 Vulkan 最常见的 bug 来源，症状是画面闪烁/撕裂/损坏且难复现（竞态）。这与 OpenGL"驱动默默替你插同步"形成最尖锐的对照——便利与控制的取舍在这里最直观。注意：Vulkan 的 compute 队列可做 GPU 通用计算，但那属 L6-06 H-05/H-06 的性能/GPGPU 视角，本报告只在此点到、不展开。

### G-06.5.5 版本与成熟度：1.4 活跃线，GL vs Vulkan 总对照

Vulkan 1.4 由 Khronos 于 2024-12-02 发布（SIGGRAPH Asia 东京，2024-12-03 公布），是当前活跃演进线（本文核实 2026-07-30）。1.4 的主旋律是把大量此前的扩展/可选特性提升为核心强制（如 push descriptors、dynamic rendering local read、scalar block layout 等），降低碎片化、简化跨平台开发。与 OpenGL 4.6 的"已冻结"相反，Vulkan 仍在按次要版本持续演进，因此硬标 ⚙演进快·锚版本，具体新特性清单随版本变、以官方 spec 为准，本报告不逐条固化以免过时。

把两套模型并到一起对照，就是本大主题的落点：

OpenGL 隐式全局状态机 / bind-to-edit / draw 即时生效 / 驱动隐式管内存与同步 / 单线程提交友好 / 已冻结（4.6, 2022-05-05）
Vulkan 显式命令缓冲＋队列提交 / 不可变管线对象 / 显式 fence·semaphore·barrier 同步 / 显式内存分配 / 多线程录制友好 / 活跃演进（1.4, 2024-12-02）

在取舍上，OpenGL 换来的是低样板、快速上手、驱动兜底，适合学习与中小项目；Vulkan 换更低 CPU 开销、更可预测的性能、多线程可扩展与对硬件的精细控制，代价是复杂度和责任。两者面向的是同一块 GPU 硬件、同一条光栅管线（6.1～6.3 的阶段完全通用），差别纯粹在"API 怎么驱动它"这一层。RTR4 第 3 章正是以此对照收束现代实时渲染 API 一节。
